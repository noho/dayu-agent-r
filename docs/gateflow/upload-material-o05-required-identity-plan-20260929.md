## 目标、判断和对齐

目标：所有 action 的 material `form_type`、`material_name` 在共同 Fins material identity admission owner 无条件必填；`None`、`""`、纯空白在 direct stream、observation、job record、SEC/CN/HK 独立 workflow 的稳定 ID、started event 和任何业务读写前，按字段产生同一可行动的 typed usage 拒绝。direct CLI 不出现 `upload.started`，用法错误退出 `2`；Service、tool、job 与独立 workflow 沿用同一 owner。合法材料相对已集成的 O17 基线保持稳定：form 从 O17 唯一 canonical 函数派生，material name 与稳定 ID 算法不因 O05 另行改变。

第一性原理判断：字段是材料稳定身份的输入，而删除也要先定位该身份；因此不能等到 pipeline `build_material_ids()` 才发现字段缺失。严重性在失败时机与错误语义；现有冻结证据没有证明错误材料已发布。当前 HEAD 直接证据：

1. `dayu/fins/ingestion_runtime.py` 的 `FinsUploadMaterialRequest` 把两字段定义为 `str | None = None`；`_normalize_upload_request()` 当前只准入 ticker/action/source kind。`FinsIngestionRuntime.upload()`、`prepare_observed_upload()`（`start_observed_upload()` 委托它）、`start_upload()` 都在建立 stream/observation/queued record 前调用 `_validate_runtime_upload_request()`，material 分支再调用 `_normalize_upload_request()`。但这个私有 request 入口不能覆盖独立 workflow；须由本模块的公开、只接收两字段的 material identity admission 函数成为唯一规则 owner，runtime 和 workflow 均调用它。
2. `dayu/service/fins_direct.py::upload_material()` 只构造 request 并调用 runtime `upload()`；`dayu/cli/commands/fins.py::_upload_material_stream()` 把 CLI 缺值/空白名称投影为 `None`；`run_fins_direct_command()` 已把 `FinsUploadUsageError.failure.message` 映为 exit `2`。Service 和 CLI 不应各自重建必填规则。
3. `dayu/fins/tools/upload_tools.py::_upload_request_from_arguments()` 当前用 `_required_text()` 提前拒绝 tool 的缺失/空白，且对合法字符串做 `strip()`；现有 `_optional_raw_nullable_text()` 对字符串原样返回、对非字符串报类型错误。tool callable 经 `prepare_observed_upload()` 启动，并把 `ValueError` 映为 `invalid_argument`。新私有输入投影 helper 应只让缺失/null/空白抵达同一 Fins 业务 owner，同时保留合法文本既有的 `strip()` 投影及非字符串类型拒绝；tool schema 已在字段说明中写明 material 必填，无需改 schema。
4. `dayu/fins/service_runtime.py::_run_material_upload()` 仅在 runner 阶段拒绝 `None`。`sec_upload_workflow.py::run_upload_material_stream()` 与 `cn_pipeline.py::CnPipeline.upload_material_stream()` 可独立调用：当前先做 ticker/company/period 投影，再调用 `build_material_ids()`；该 builder 对空白抛 raw `ValueError`，之后才有显式 ID 校验、action/files selection、仓储读取和 `UPLOAD_STARTED`。同步 `upload_material()` 都委托各自 stream。只改 runtime 会形成两种错误语义；workflow 必须直接调用同一 owner，且该调用应移到各自 stream 执行体开头，在 ticker/company/period 投影及 ID、事件、业务读写之前。

状态转移：非法输入在 `raw fields -> shared material identity admission` 处抛 typed usage；runtime 不得产生 `ValidatedFinsEventStream`、observation handle、job queued record 或 `upload.started`，独立 workflow 不得调用稳定 ID builder、产生 `UPLOAD_STARTED`/failed event 或做业务读写/发布。合法 runtime 输入保持 `admission -> direct/observation/job -> runner -> workflow`，合法独立 workflow 输入从同一 admission 进入现有 ID/动作流程。CLI 仅渲染 `failure.message` 并 exit `2`；Service 原样透传异常；tool 将它经既有 `ValueError` 分支投影为 `ToolFailedOutcome(error="invalid_argument", message=owner 文案)`。job 入口在创建 record 前原样抛异常，因此不会产生失败 job 来代替准入拒绝。无需新增错误投影分支。
