## 目标与第一性原理判断

目标是让 storage 的封闭完整性预检原因，经 Fins download 公共失败对象、direct RESULT、CLI/等待投影保持同一事实；真正未知的 direct download 异常仍给用户安全的 generic 失败，同时在 operator 日志留下**不含异常原文和用户路径**的异常类型及可定位调用栈。成功信号为 `unsafe_publication` 显示 `storage`、可操作且不鼓励盲目重试，未知异常有可查看的安全诊断，owner 测试、受影响测试、pyright 和隔离真实 CLI 验证通过。

动机成立：`dayu/fins/storage/source_integrity.py` 的 `SourceIntegrityPreflightReason` 是四值封闭枚举，`classify_source_integrity_preflight` 在 UNSAFE inventory 上抛 `SourceIntegrityPreflightError(UNSAFE_PUBLICATION)`；`dayu/fins/ingestion_runtime.py:_run_direct_stream_producer` 捕获异常后只生成 RESULT；`_download_public_failure_from_exception` 的现有未提交分支已将该异常映射为 storage，而未知异常仍映射 execution。issue #198 的事故与此代码路径一致，但事故文字不是本 plan 的唯一依据。`dayu/cli/commands/fins.py:run_fins_direct_command` 外层未知异常目前用 `_LOGGER.exception` 写原始 traceback，现有 `tests/cli/test_fins_commands.py` 甚至断言秘密异常文本进入日志；因此只在 producer 增加安全日志不足以满足 download 的脱敏目标。

## 边界、语义 owner 与契约

- storage `source_integrity.py` 独占完整性事实及四值 `SourceIntegrityPreflightReason`；不改变任何完整性判定、repair 选择或下载来源行为。Fins `ingestion_runtime.py` 独占异常到 download public failure/direct error kind 的映射；`direct_events.py:FinsPublicFailure` 独占公共字段及校验、JSON 投影；CLI `output.py` 只打印已验证的公共字段。公开 `reason_code` 在唯一映射点由 storage enum 派生，不能从 `str(exc)`、路径、日志或 CLI 反推。
- CN/HK 的 `cn_download_filing_workflow.py` 已在单 filing Phase A 与 Phase B 抛出 `SourceIntegrityPreflightError(UNSAFE_PUBLICATION)`；`cn_download_workflow.py:run_cn_download_stream_impl` 拥有单 filing `async for` 外的异常收口、已完成 filing 结果及候选循环。该边界在一般 filing failure 投影前消费 typed preflight，保留原异常对象及已有 filing 事实，形成一次 typed abort；若之前已发布候选，不能只让裸异常越过 collector 而丢掉部分结果。`cn_pipeline.py:CnDownloadAdapter` 将 workflow 快照按现有严格投影规则转成 `FinsDownloadResultSummary`，Fins runtime 独占 storage 异常到 public failure 的映射与唯一 RESULT。不得从普通 filing 行、进度、日志、展示、异常字符串或事件顺序反推公共原因或部分摘要。CN 与 HK 共用这条 workflow；SEC 路径已经透传，无需修改。
- 不让共享的 `direct_events.py` 导入 `dayu.fins.storage`：storage 包的 `__init__.py` 聚合多个具体仓储实现，而 `FinsPublicFailure` 是 CLI、Service、等待路径共用的轻量公共契约，直接持有 storage enum 会把仓储实现依赖带入所有消费者。在 `direct_events.py` 定义仅含四个当前公开值的 `FinsDownloadFailureReason(str, Enum)`，将未提交 `FinsPublicFailure.reason_code: str | None` 收紧为该公共 enum 或 `None`；`__post_init__` 只接受该 enum 或 `None`，且非空 reason 只允许 `kind=STORAGE`、`transport_category=None`。`ingestion_runtime.py` 在唯一异常投影点用显式、全覆盖 `SourceIntegrityPreflightReason -> FinsDownloadFailureReason` 映射，直接消费 `exc.reason`，不反解析字符串；测试断言映射键全集等于 storage enum 全集、映射值全集等于公共 enum 全集，并对每一对语义对应的枚举成员断言 `.value` 相等。公开词汇必须保留四个 storage 原值；未来更名须显式裁决公开合同，不能静默漂移或靠字符串偶合穿透。`to_json_value()["reason_code"]` 输出公共 enum `.value` 或 `null`；CLI 失败详情行的 `reason_code=` 输出同一 `.value` 或既有空占位符 `"-"`；下载文档行的自由文本 `reason=` 保持原语义。不存在旧值兼容读取。业务展示仍用 `safe_message` 与 `retry_hint`；LLM 可见内容不要求模型凭内部代码推理，若该 JSON 进入 LLM 上下文，需同源附带现有可读消息。
- 对四个 preflight reason 均用同一个 storage public failure 分类和安全消息，保留枚举原值；`UNSAFE_PUBLICATION` 的恢复提示明确先检查/修复工作区来源状态，重复下载不会自行修复。其它三个 repair 选择失败不得误称非法文件；统一提示写“检查并修复工作区来源状态”，不猜具体损坏原因。direct `error_kind=STORAGE` 与 `failure.kind=STORAGE` 一致。provider、OSError、unknown 现有分类不变，unknown `reason_code=None`。
- 未知 `EXECUTION` 异常的 Fins `retry_hint` 由 `ingestion_runtime.py` 给出入口无关的恢复语义“请保存脱敏诊断并排查失败原因后重试。”；不得包含 `--log-file` 等 CLI 参数。CLI 展示 owner 在 `dayu/cli/output.py` 独占一处 CLI 日志提示常量，文案为“请使用 --log-file PATH 重试并查看日志”；这里的“日志”指运行日志，不承诺每个 `EXECUTION` 均有 `fins.download.*` unknown 异常诊断。仅在已验证的 `FinsPublicFailureKind.EXECUTION` download 失败详情后追加同一提示，不改变公共 `retry_hint` 或 JSON/Service 投影；此分类也包含非异常的无来源文档失败，其运行日志可含普通 INFO 文档行，而已有文档 RESULT 详情仍可用于排查，不期待 unknown 诊断。CLI 提示不按异常字符串或 `reason_code` 重新分类；有无 `--log-file` 均给出可执行指引，显式指定时日志文件必须可读。storage 等其它分类不附加该运行日志提示。无来源文档的现有 Fins `retry_hint` 在默认临时日志下仍欠可操作，归后续 `fins-download-no-source-retry-hint` work unit，本轮不以 CLI 提示冒充 Service/JSON 路径的修复。
- 诊断产生点有两个：Fins producer 捕获 **download 且公共分类为 EXECUTION** 的异常；CLI 外层 catch 捕获在 producer/stream 之外逃逸的 **download 未知异常**。producer 先构造公共失败并发出失败 RESULT，再尝试记录安全 operator 日志；无来源文档是非异常 RESULT 路径，不产出 unknown 诊断。`run_fins_direct_command` 的 typed except 已先于最后的 `except Exception` 返回；最后一支当前对所有 direct 命令调用 `_LOGGER.exception`，会把原始 traceback 放进日志。只在最后一支按 `args.command_name == COMMAND_DOWNLOAD` 分流日志：download 使用安全记录，非 download 保留现有 raw traceback 日志行为；不得改动 typed except，也不得让 producer 已转成 RESULT 的失败被 CLI 重复记录。两点共用 `dayu.runtime.log` 的层中立 `safe_exception_trace(exc: Exception, *, source_root: Path) -> str`，由调用点传入各自文件定位出的 `dayu` 包根，不让 runtime import Fins/CLI。它只负责结构安全，不负责业务分类、日志装配或公开 failure。前者记录 `fins.download.unexpected_failure`，后者记录 `fins.download.command_unexpected_failure`，均为 ERROR；默认 INFO 阈值可接收记录，但未传 `--log-file` 时 CLI 使用进程期临时文件，退出后不可查看，因此 CLI 必须明确提示用户显式保存。外层所有 direct 命令的固定错误由“命令执行失败，”加 `output.py` 唯一日志提示组合，退役 `fins.py:_FINS_DIRECT_UNKNOWN_FAILURE_MESSAGE`；非 download 最终文案必须逐字保持现有“命令执行失败，请使用 --log-file PATH 重试并查看日志”（连同既有 `dayu-cli {command_name}: ` 前缀），仅日志分流发生变化。非 download 的 raw traceback 日志风险仍列为独立残余。
- `safe_exception_trace` 用 `traceback.walk_tb(exc.__traceback__)` 取 frame 的代码位置，不调用 `traceback.format_exception`、`exc_info=True`、`logger.exception`、`str/repr(exc)`、`linecache`，不读取 locals、异常 args、cause/context/notes。输出单行有界 `exception_type=<安全类型> custom_type=<安全指纹或 redacted> stack=<帧列表>`：沿 `type(exc).__mro__` 只取第一个能以 `vars(builtins).get(name) is class` 证实身份的内建异常类型；自定义异常类型只取其类型对象的 `__module__` 与 `__qualname__`，两者均须为 `str`，以 UTF-8 编码 `module + "\0" + qualname` 作 SHA-256 输入，仅输出摘要前 16 个小写 hex 字符，不输出原始名称/模块名；任一元数据读取、类型校验、编码或哈希失败时 `custom_type=redacted`。内建异常的 `custom_type=redacted`，该指纹只是 operator 诊断标签，不是业务原因或公开分类。每帧仅在 `frame.f_globals` 与 `sys.modules` 中真实 `dayu.*` 模块的字典同一、模块 `__file__` 与 `frame.f_code.co_filename` 经严格解析同一且位于传入的受信 `dayu` 包根、相对 `.py` 路径各片段为合法 Python 标识符时，输出包内相对路径和正整数行号；其它帧仅输出固定 `[external]`，不输出函数名、外部路径或源码行。最多保留最后 16 帧（包含抛出点），以固定 `truncated` 标志表示省略；无 traceback 输出固定 `[unavailable]`。禁止绝对路径、URL、源码行和任意异常文本进入生成串。用 `deque(maxlen=16)` 有界保存帧片段；函数有中文完整 docstring 与严格类型签名，常数有命名，输出只由受信片段构造而非事后正则替换原始 traceback。这是两处日志共享的最小层中立格式化能力，不新增日志治理框架或状态。
- helper 对 `Exception` 输入的**整个格式化过程不抛出**：逐帧路径/元数据校验失败降级 `[external]`，而遍历、类型指纹、容器或其它内部步骤出现非预期 `Exception` 时统一返回固定 `exception_type=redacted custom_type=redacted stack=[unavailable]`，绝不把失败异常或原始异常交给 logger。兜底只在 `dayu.runtime.log` 的共用 helper 内实现一次；producer 和 CLI 不各自复制宽泛 catch。故 helper 自身失败不能阻断原有 RESULT/CLI 固定失败投影；这不扩展为 RESULT 构造等其它二次失败的兜底承诺。
- 公开 RESULT、CLI stdout/stderr 和等待 JSON 不承载调用栈或异常类型；CLI 外层仍给固定未知失败提示。诊断也不进入 LLM-facing trace/memory。若后续发现 log handler 另行追加原始 `exc_info`，该 slice 不得宣告通过。

目标/对齐：实现“storage reason 保真、可行动、非盲目重试”，包括**可证明已发布**的中途 abort 后 direct RESULT 与后台 job failed record 对同一文档事实的守恒；不承诺所有 company commit 失败的摘要守恒。允许代码文件：`dayu/fins/ingestion_runtime.py`、`dayu/fins/direct_events.py`、`dayu/fins/pipelines/cn_download_workflow.py`、`dayu/fins/pipelines/cn_pipeline.py`、`dayu/service/fins_wait_adapter.py`、`dayu/cli/output.py`；允许测试：`tests/fins/test_fins_ingestion_runtime.py`（同时覆盖 direct 与后台 job）、`tests/fins/test_cn_download_workflow.py`、`tests/fins/test_cn_download_runtime.py`（`cn_pipeline.py` 的既有 owner 测试归属）、`tests/cli/test_output.py`、`tests/service/test_fins_wait_adapter.py`、`tests/service/test_fins_direct.py`；另仅检查并按职责更新三份 README 的 #198 句子。`cn_pipeline.py` 是真实 CN/HK event collector 与 adapter 的共同文件，必须在这里保留 workflow 给出的部分事实并严格投影；wait adapter 仅拥有 LLM-facing 失败说明。两者直接对应 goal 的 public summary 一致性与可读性，不是新增业务目标。不将 `cn_download_filing_workflow.py`、`download_contract.py`、storage inspector 或 SEC workflow 加入修改范围；不新增公开字段、枚举值、extra payload 或存储 schema。以前述未提交候选 hunk 为起点，在公共失败契约定义独立的封闭 reason enum；Fins 异常投影点逐项映射 storage enum。owner 测试同时断言映射键全集等于 `SourceIntegrityPreflightReason` 全集、映射值全集等于 `FinsDownloadFailureReason` 全集，并对每对成员断言 `.value` 一致；不在运行时增加第二份白名单。JSON/CLI 在公共契约边界取 `.value`。

CN/HK 的单 filing Phase A/B typed preflight 在 `run_cn_download_single_filing_stream` 已原样抛出。`cn_download_workflow.py` 的单 filing 收口先于普通 `except Exception` 专门捕获它：单 filing storage batch 已由自身 owner 回滚；workflow 将当前候选记为一个私有、脱敏的 `failed` filing（通用 `source_integrity_preflight` 类别，不复制四值 public reason），保留此前 `filings` 中真正完成的 `downloaded/skipped/rejected/failed` 结果，发当前 `FILING_FAILED` 进度，随即终止候选循环。workflow 用已有 `_build_result/_build_summary` 从该同一 `filings` 快照构造私有 `integrity_failed` 结果（含实际 filters 与 missing periods），通过私有 typed `CnDownloadIntegrityAbort` 一起携带**原始** `SourceIntegrityPreflightError`；不发 `PIPELINE_COMPLETED`，不进入 `project_cn_filing_failure`，不生成 `filing_execution_failed` 行。首候选循环前的 whole-kind preflight 抛出时，`filings` 尚空，原始 `SourceIntegrityPreflightError` 裸透传，**不构造私有 abort 或伪造 filing 行**；无 repair 时、候选循环前调用 `_publish_cn_company_after_repair`，若 company `commit_batch` 在 physical swap 前抛同一 typed preflight，此时尚无已处理候选：原始异常裸透传，不构造空 `filings` 的私有 abort、快照或伪 filing 行；direct/job 均使用请求级 `FAILED` 零候选摘要。该函数还被 post-repair 路径调用，私有快照 catch 只能放在后者的调用点，不能放进共享函数内部或包住循环前调用点；Fins 对 direct 与 job 均用 `_empty_download_summary_from_request(..., terminal_disposition=FAILED)` 生成相同的结构化零候选摘要，并经同一公共失败映射取得四值 reason 与安全消息，job 将该摘要的 `to_json_summary()` 写入 failed record，不落 generic `{}` 或 `str(exc)`。此规则只适用于确实尚无已处理候选的初始 whole-kind typed 或循环前 company pre-swap typed；已处理 filing 后的异常不得套用零候选口径；no-source 与普通异常仍按各自既有形状收口。mid-filing identity churn 耗尽抛出的 `SourceIntegrityRevisionConflictError` 仍由单 filing 的普通 `except Exception` 投影为 `filing_execution_failed`，随后继续候选循环；这是 `fins-download-storage-sibling-errors` 待修的已知残余，不称为 S1 typed reason 保真，也不把它并入 preflight catch。`run_cn_download_stream_impl` 的中文 Raises 在既有参数/仓储异常外，只列真实 typed 裸出口：`SourceIntegrityPreflightError`（首候选前）与 `CnDownloadIntegrityAbort`（已处理 filing 后），不列单 filing 内已被吞下的裸 revision conflict；`CnPipeline.download_stream`、`collect_cn_download_result_from_events` 与同步包装 `CnPipeline.download` 的中文 Raises 同步列明实际透传的私有 abort、初始 typed preflight 及其既有异常。

`cn_download_workflow.py` 的后置守恒只覆盖 owner 可证明文档 durable 保持的封闭路径：候选循环内单 filing `try` **之后**、进入 company batch **之前**的 post-repair 分类整块：`classify_source_integrity_preflight` 可抛 `SourceIntegrityPreflightError`，其返回 `SelectedSourceRepairRequired` 时由 workflow 显式抛 `SourceIntegrityRevisionConflictError`；typed catch 必须同时覆盖 classifier 调用和随后这项显式检查，不得只包住 classifier；以及 company `commit_batch` 中 `_validate_complete_source_tree` 在 physical swap 前抛出的 typed `SourceIntegrityPreflightError`。后者的可信依据是 storage owner 的调用序：staging whole-tree 校验先于 publication guard、backup 与 target swap；该 typed 从 pre-swap 校验抛出时，原 target 未被物理替换。即使随后 `_rollback_precommit_batch` 的 journal/staging cleanup 失败，`commit_batch` 以 `raise commit_error from rollback_error` 保留原 typed 与 cleanup 异常链，已确认文档的旧字节仍可由同一 `filings` 快照表达；只允许声明文档未被本次 swap 改动，**不得**声明 rollback/cleanup 成功或以是否存在 `__cause__` 判定已发布文档归零。对这些路径只在 post-repair 已处理 filing 后的对应调用点专设 typed catch，不改变循环前 company 调用，复用同一个私有快照构造路径，以当前 `filings`（含刚完成的 repair filing 及此前终态行）抛 `CnDownloadIntegrityAbort`，携带**原 cause 对象及既有异常链**，不让它裸越 collector；revision conflict 公开业务分类仍按既有 EXECUTION，不能借守恒修复私造新 public reason。这里**不新增**该 filing 的 `failed` 行或第二次 `FILING_FAILED`：它已有 `downloaded/skipped` 等终态；后续候选未处理。`CnDownloadCancelledError` 先保留原取消控制流和唯一终态合同，不被后置 catch 转为 FAILURE。首候选前的初始 whole-kind typed 与循环前 company pre-swap typed 均保留原异常和请求级 `FAILED` 零候选摘要，不能经空 `filings` 快照派生 `SUCCEEDED`。不得对 company `commit_batch` 的 ValueError、OSError、post-commit release 或其它物理失败使用泛 `except Exception` 保留快照；若 owner 证据显示 target 已动，或 physical swap/restore 及发布状态不确定，触发停止条件并转独立 work unit，不能从异常文本、日志、时间顺序或再读目录猜状态。

`cn_pipeline.py` 的 collector 不从已发事件顺序、progress sink 或日志回填部分结果；它让私有 typed abort 原样越过同步边界。仅 `CnDownloadAdapter.download` 捕获该私有 abort：保留 `_summary_from_pipeline_result` 对正常 `ok/cancelled` 的封闭校验，把其中校验 request/ticker、filings、filters、missing periods、storage locator、rows/counts 的**纯投影**抽为模块内共享私有 helper；私有 `integrity_failed` 快照先按自身允许的失败 status 严格校验，再调用同一纯投影 helper 形成 `FinsDownloadResultSummary`。不得把失败快照暂改成伪 `ok`、放宽正常入口 status，或绕过 row/locator 校验。adapter 抛 `ingestion_runtime.py` 中定义的私有 `FinsSourceDownloadAdapterFailure`，其中直接持有**原始** `SourceIntegrityPreflightError | SourceIntegrityRevisionConflictError` 对象与上述同一个完整、已验证的 `persisted_summary`；只允许这些既有 typed cause，不把 revision conflict 改装为 preflight 或新增公开失败枚举。`_execute_download_request` 在 adapter 边界对异常携带的 summary 执行 `_bounded_download_summary` 与 `_validate_download_summary_request_identity`，验证后仍抛该私有 failure，异常路径不得发正常 `download.completed`。direct producer 与 job 只能对这一已验证 snapshot 构造 public summary / failed record，禁止分别读进度、日志或重算 raw filings；尚无已处理候选的其它异常仍沿既有零候选失败口径，不以 adapter 是否已启动判断。Fins 在共用的异常分类/公共失败投影入口对私有 failure **单点 unwrap**，取得其原 cause 对象，再把同一 cause 交给现有 `_classify_direct_error` 与 `_download_public_failure_from_exception`；direct/job 只消费这一共用投影与安全消息，不各自遍历 `__cause__`、解析字符串或复制四值映射。裸的初始 whole-kind `SourceIntegrityPreflightError` 在同一入口保持原对象并走同一四值映射；revision conflict 保留既有 EXECUTION 分类，非 typed 异常不得伪装为 preflight。严禁在 CN workflow、adapter、CLI 或测试夹具复制映射、从私有 filing `reason_code`、字符串、路径或展示数据反推公开码。

计数口径：只有已产生终态 filing 事实且发布状态可由 storage owner 证明的候选计入 `discovered_count`，且它精确等于四类互斥 row 数之和；已 commit 的先前候选保留 `downloaded` 与 storage locator，已 skip/reject/普通失败的先前候选保留原分类，单 filing Phase A/B typed abort 的当前候选计一次 `failed`，可证明的 post-repair abort 则保留该 filing 已有的唯一终态行，后续未开始候选不计数、不造 `failed/skipped` 行。`FILING_STARTED`/文件级传输进度不代表持久化；回滚的当前候选不能算 `downloaded`，已提交的候选不能被归零。例：三候选依次成功、Phase B typed 失败、未开始，summary 为 `discovered=2, downloaded=1, failed=1, skipped=rejected=0`，`terminal_disposition=partial_failure`；`FinsResultSummary` 为 `status=FAILURE/exit_code=1`，`error_kind=STORAGE`、`failure.kind=STORAGE`、`reason_code=unsafe_publication`。post-repair gate 在唯一已完成 filing 后 typed 失败时，摘要只有这一真实 `downloaded` 或 `skipped` 行，`failed_count=0`，由现有 row 机械派生 `terminal_disposition=SUCCEEDED`（只表示已处理文档的结果），请求 RESULT 仍为 `FAILURE`、job record 仍为 `FAILED`；不得为使 terminal 看似失败而篡改 row/count。`direct_events.py:FinsResultSummary` 的跨操作 owner 校验在 `status=FAILURE` 且存在已验证 public failure、并携带 download 时，允许该 download 根据已有 counts/rows/terminal owner 校验呈 `FAILED`、`PARTIAL_FAILURE` 或 `SUCCEEDED`；`failure.kind`、`reason_code` 只描述失败原因，均不是已处理进度、发布确定性或放宽谓词的证明。`FinsResultSummary` 不新增「FAILURE 必须携带 download」的跨操作不变量；现有无 failure、错误 counts/disposition、`SUCCESS`/`CANCELLED` 与 failure 混用仍按各自实际 owner 规则拒绝，成功与取消自身的终态约束不变。download wait 失败帧缺 summary 的拒绝只属于 `fins_wait_adapter.py:_failure_message`，由该 adapter 测试固定。`FinsDownloadPublicSummary` 自身仍由 row 机械派生终态，不能强置 `FAILED`、放松守恒或新增 enum/schema。`OSError -> STORAGE` 无 reason 的公共形状，在**已确认**的后置失败中可以有真实文档摘要，在前置失败中可以只有零候选 `FAILED` 摘要；此 dataclass 的机械校验不替代 storage 发布事实证明。每次 direct 流恰有一个最后的 RESULT；异常快照和进度不得另发一个终态。CLI、Service wait 与 JSON 均只消费该 RESULT 的同一 public summary/failure；后台 failed record 也须从同一已验证 typed summary 派生，不得以 `{}` 代替已确认发布事实。

后台 `ingestion_runtime.py:_run_download_job` 在 `_UnsupportedDownloadSourceError` 后、普通 `except Exception` 前分别收口私有 `FinsSourceDownloadAdapterFailure` 与裸 `SourceIntegrityPreflightError`。私有 failure 的 `persisted_summary` 须已由 `_execute_download_request` 执行 `_bounded_download_summary`、`_validate_download_summary_request_identity` 验证；job 按现有 terminal 幂等读取最新 record，以该 summary 的 `to_json_summary()` 传入 `_save_failed(..., result_summary=...)`。裸的初始 whole-kind 或循环前 company pre-swap typed 没有 adapter partial summary，job 从已校验请求用 `_empty_download_summary_from_request(..., terminal_disposition=FAILED).to_json_summary()` 保存结构化零候选摘要，不能经 generic `_save_failed_from_exception` 落 `{}`。两条 typed 路径均只取 Fins 共用异常投影的 `FinsPublicFailure.safe_message`，与 direct 使用同一 reason/message；不写 `str(exc)`、存储异常原文、用户路径或四值映射副本。两条 typed catch 的二次读取/保存失败只复用 `_save_failed_from_exception` 的 terminal 幂等读取与**不逃逸**控制流；新增 WARN 必须独立遵守本段固定标识合同，不能复用其记录动态类型和 `exc_info` 的日志写法；新增 WARN 仅记录固定事件标识 `fins.download.typed_failed_record_save_failed`，不设置 `error_type` 字段、不记录任何动态异常信息（包括异常类名、`str/repr`、`exc_info`、路径、秘密或 traceback）；该标识只表示 typed job 的二次读取/保存失败。WARN 只诊断二次保存失败，不虚称 job 已保存终态，也不以 `{}` 覆盖原摘要。`_save_failed` 继续使用 job store 的原子 failed terminal 保存；普通未知异常仍走 `_save_failed_from_exception` 既有边界，no-source 维持现有摘要。direct producer 从相同的已验证 `persisted_summary` 派生 `_public_download_summary` 并发唯一 RESULT；job 与 direct 的已处理文档事实都来自 CN `filings` → adapter owner `FinsDownloadResultSummary`，初始 whole-kind 与循环前 company pre-swap typed 则共同来自 Fins 的请求级零候选 helper，只允许入口投影格式不同。job `failure_summary.message` 安全、`result_summary` 的 counts/rows/terminal 与 direct 同源；持久摘要如含其它现有字段也由 `to_json_summary()` 原样导出，不另组装。
