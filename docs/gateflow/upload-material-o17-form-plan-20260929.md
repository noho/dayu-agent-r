## 唯一 owner 与数据流

- **函数 owner**：在 `dayu/fins/pipelines/docling_upload_service.py` 的现有 material identity builder/validator 边界新增唯一公开纯函数 `normalize_material_form_type(form_type: str) -> str`。material identity、request、US/CN/HK material stream 与 batch material form 文本规范化都调用它；不在各入口复制 `.strip().upper()`。只对有效非空文本产生 `strip().upper()` 结果；传入空白时维持 identity builder 现有 `ValueError("form_type 不能为空")` 拒绝，不把该函数当作 `None` 或空白的公开 usage 分类器，不新设 form 枚举、长度或业务别名。函数需完整中文参数、返回、异常 docstring。`build_material_ids` 调用该函数，并测试其既有空白 form、空白 material name 两类非法值拒绝；保持原 seed 拼接顺序、SHA-1、`mat_` 前缀、name 和 fiscal 字段的现有独立含义。与 `build_cn_filing_ids`、`build_sec_filing_ids`、SEC form parser、download form filter 隔离，不将 material 类别解释为 filing form。
- **请求入口**：`ingestion_runtime.py` 的模块函数 `_normalize_upload_request` 仅当 material `form_type` 为有效非空文本时调用同一函数，生成 `replace(request, form_type=canonical)`；`None` 和空白原样留在 request 中，沿现有后续边界失败，不在本项提前变成 O05 typed usage，也不改失败类型、时序或 durable job 副作用。`None` 不传给签名为 `str` 的函数，空白不在 admission 调用它；不得用 `str(None)` 或默认值制造 canonical form。direct、observed、legacy job 分别在 producer/observation/job 创建前经过 `_validate_runtime_upload_request`。有效值使 `_upload_request_summary`、后续 runner 与事件从同一 canonical request 取值；不在 summary renderer 单独改写。O05 后续在请求准入 owner 前置缺失/空白的 typed 拒绝并复用这个有效值函数，O17 不预支其错误契约。
- **batch 与 CLI 边界**：`dayu/fins/upload_batch.py::_validated_material_form` 对非 `None` override 调用同一函数得到 canonical 文本，再由 batch routing owner 独立校验 `_MATERIAL_FORM_TYPES` 封闭集合，保留现有 `UploadBatchPlanUsageError` 分类及校验顺序；函数本身不吞并或扩张这个集合。`_match_material_form` 仍按既有文件名 routing table 返回三个已是 canonical 的类别字面值；override 只覆盖已路由 material，二者进入 `UploadBatchMaterialEntry.form_type` 的同一 typed fact。`dayu/cli/commands/fins.py::_single_batch_material_form` 只拆分 `--material-forms`、检查单值与空白，不产生规范化后的 form：返回唯一原始非空 item（保留大小写与两端空白）给 batch owner，删除独立 `.upper()`；空值/多值的 CLI 错误与其发生时点不变。生成脚本仍机械地将 typed entry 的 canonical `form_type` 放进 `upload_material --forms`；regeneration argv 若含 override 则保留 CLI 原始候选，重新生成时仍由 batch owner 规范化。`--forms` 单条 CLI 现有空值/基数解析不在本项改变，其有效值继续由 request/stream owner 规范化。
- **市场入口**：US `run_upload_material_stream` 与 CN/HK `CnPipeline.upload_material_stream` 可被直接调用，均在计算 ID、发 `upload.started`、启动公司批次前调用同一函数，并把局部 canonical 值传给 `build_material_ids`、started payload、`prepare_upload(form_type=...)`、成功与失败结果。上游已 canonical 时同一函数幂等；对本修复后新写或此前由同版代码写入的 material，不产生另一条 raw form 的 durable/可读副本。历史已发布 raw form 不在该承诺内。
- **持久化/结果**：`prepare_upload` 的 material prepared mutation 使用传入 canonical form；storage 只保存该 `SourceDocumentUpsertRequest.form_type`，manifest 继续从完整 source meta 派生。结果由市场 workflow 使用同一局部值；不在 repository、manifest、UI、summary 或结果 adapter 添加 fallback/重算。`meta` 字典不得另写一个 form_type 覆盖显式参数。

当前依赖方向允许该共享：`ingestion_runtime.py:121-127` 已从 `docling_upload_service` 导入身份/上传规则，两条 workflow 已导入 `build_material_ids`；`upload_batch.py` 与 `docling_upload_service.py` 当前没有互相导入，batch 可单向调用该函数；storage manifest 已直接依赖 source meta。`upload_batch.py:799-814` 的 override 与 `fins.py:413-414` 的 `--forms` 指向同一 material form 事实，独立的是 batch routing 允许域，并非另一套文本 canonical 语义。没有必须跨越反向依赖或双 owner 的代码反例，故本计划可进入实现。实施时若发现任何入口使同一个 material form 必须绕过该函数，或 meta/manifest/结果只能各自从 raw 值重建，停止并带直接调用反例回到 owner 裁决，不做下游补偿。

## 串行集成与剩余风险
