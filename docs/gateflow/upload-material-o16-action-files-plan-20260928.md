## 契约与实施决策

- 共享函数在 Fins owner 内规范化 action，封闭接受 `auto/create/update/delete`；独立 workflow 的 `None`/空串按既有 auto 语义，大小写和首尾空白规范化。它先拒未知动作并产生 typed `INVALID_ACTION`，再校验组合：`delete` 且 `files` 非空抛 `FinsUploadUsageError(FILES_NOT_ALLOWED_FOR_DELETE)`，`auto/create/update` 且 `files` 为空复用既有 `FinsUploadUsageCode.MISSING_FILES`；合法时返回同一次判定的最小 typed `requested_action`/`pipeline_action`，其中 auto 对应 `("auto", None)`，其它动作对应两个同值的 canonical 字符串。在 owner `_USAGE_MESSAGES` 将 `MISSING_FILES` 文案改为同时涵盖 auto/create/update；filing 与 material 共用同一个 code/message，不新增同义 code，也不保留 filing auto 的误导文案。runtime 的 `_normalize_upload_action("")` 与 tool 的 `_required_upload_action("")` 在调用共享函数前按既有 plain `ValueError` 拒绝空串/未知动作；CLI argparse 不产生空动作且以 choices 拒绝未知动作；独立 workflow 则在 `try` 外由 owner typed 拒绝。保持入口原有词法边界：CLI 只收精确小写 choices，tool 可收大小写但不 strip 首尾空白，runtime 可收大小写和首尾空白，独立 workflow 经 owner 接受 `None`/空串及大小写、首尾空白变体；这些差异不扩大为 CLI/tool 新规范化承诺。不发明新动作或公开 schema。
- `_normalize_upload_request` 在现有 ticker→action→source 规范化后，**仅在 `isinstance(request, FinsUploadMaterialRequest)` 分支的 `replace(request, action=action)` 前**调用共享函数作 admission，此处只需通过校验，可忽略 typed 结果；filing 分支不接入。`request.action` 继续保留当前规范化后的公共表示，包括 literal `"auto"`，不得把 canonical pipeline `None` 写回 runtime request、summary、job 或 observation。非法组合不进入 `_upload_request_summary`、`_DirectUploadProducer` 或任何 job/observation 创建。组合校验早于未来目标状态读取/检查；本切片不添加该目标检查。ticker→action→source→组合是 **runtime 内部** 的多错误优先级，不外推为 CLI 全入口顺序。
- `ProductionFinsUploadRunner._run_material_upload` 将已 admission 的 `request.action` 与原始 `request.files` 再交给同一个 owner，显式消费结果的 `pipeline_action` 后传给 US `SecPipeline.upload_material` 或 CN/HK `CnPipeline.upload_material`；结果的 `requested_action` 确认同一规范化请求事实，但不写回公开 `request.action`，也不要求修改现有 façade 签名。删除 `service_runtime._pipeline_upload_action` 中自编码的 `strip/lower/auto→None` 规则，优先直接调用 owner，不留下仅透传的 wrapper。workflow 在自己的独立入口（包括 runner 传来的 `None`）再次调用该 owner，并从结果取 `requested_action`；不得在 workflow 单独编写 `None→"auto"` 或从最终动作反推。这个 handoff 仍不改变 runtime request/summary 的公共 action 表示；同一 owner 对原始 tuple 的再次检查用于独立 runner 边界，不能在 service_runtime 重写规则。若实现证据显示 runtime 请求表示和共享 typed 结果无法并存，停止并请总控重新裁定。
- CLI 在 `_run_fins_direct_command_async` 的 Service factory 前，对 `upload_material` 的 argparse `args.action` 和 `args.files` 构造不读取文件的 `Path` tuple，调用共享函数；`_validated_upload_files` 随后仍负责合法路径的存在/普通文件/格式检查，`_upload_material_stream` 仍交付原有 tuple。`_validated_upload_files(None)` 的 `for_delete()` 是合法无文件 delete 的有效 selection 构造，应保留。delete 携任意文件（包括错误后缀或不存在路径）先得到组合 usage，且 fresh workspace 不为此装配 Service。`run_fins_direct_command` 现有 `FinsUploadUsageError` 分支直接投影 message 与 `EXIT_USAGE_ERROR`；不得另加 CLI 组合判断。
- tool 在 `_upload_request_from_arguments` 按 kind 分支：filing 原样调用 `_upload_files_from_arguments(arguments, action=action)`，保留其原有组合拒绝、文件检查、英文文案及 schema；material 先用 `_optional_text_tuple` 校验 JSON 形态并将每个文本机械解析为 `Path` tuple（可 `expanduser().resolve(strict=False)`，但不得 `is_file`/`stat`），再调用共享函数，然后才用现有 `_resolve_upload_file_path` 检查合法 upsert 的普通且非空文件。合法 delete 空 tuple 不读文件。不得在 material 分支复制缺文件或 delete 带文件条件。`FinsUploadUsageError` 是 `ValueError` 子类，现有 `FinsUploadToolCallable.__call__` 失败 outcome 机械投影其 message；测试断言 owner code/message 与 tool outcome 同源，不能只比字符串常量。取消已先被观察时沿用取消优先级。
- SEC 与 CN/HK workflow 在任何 selection 构造、旧 meta read、`UPLOAD_STARTED`、company batch/文件读取前，将原始 `files or []` 机械转成 `tuple(file_list)` 交给同一函数，并显式消费两个字段：以 `decision.pipeline_action == "delete"` 选择 `for_delete()`，其它合法动作选择 `from_upsert_paths`；将 `decision.pipeline_action` 传给 `resolve_upload_action`，不得再传 raw literal auto 或自行映射 auto。owner 调用放在现有 `try`/终态捕获之前，使未知 action 和非法组合均 typed 拒绝；合法 upsert 的 `from_upsert_paths` 格式错误仍按原有 workflow failure 路径处理，合法 delete 仍由 `for_delete()` 建 selection。两条 workflow 将 `decision.requested_action` 原样传入 material `UPLOAD_STARTED` payload、成功/失败 `_build_result` 的 `requested_action` 字段；`resolved_action` 仍只来自 `resolve_upload_action(decision.pipeline_action, previous_meta)`。同一规范化 auto 请求无论经 runtime runner（façade 收到 `None`）还是独立 SEC/CN/HK façade（可收到 `"auto"`/`None`/空串），事件/结果都记录 `requested_action="auto"`，fresh/existing 的 `resolved_action` 分别为 `"create"`/`"update"`；显式 create/update/delete 的 requested/resolved pair 按既有目标状态规则验证。不得用入口 raw echo、`pipeline_action is None`、`resolved_action` 或显示层补偿产生 `requested_action`。filing 的 `requested_action` 投影保持原样。不得改 `resolve_upload_action`、`DoclingUploadService` 或结果计数公式。独立 pipeline 非法调用抛相同 typed usage；runtime 的非法调用则更早被 admission 拒绝。受影响的 runtime `upload`/`start_upload`/`prepare_observed_upload`、Service `upload_material` 与 SEC/CN stream/sync façade 的中文 Raises 契约须写明此 typed usage；SEC 与 Service façade 仅作 docstring 修改。
- 多错误优先级明确为：CLI material 在 Service factory 前先判组合，再进入 `_upload_material_stream` 的 ticker/form/文件检查；因此组合同时与坏 ticker 或不存在/错误后缀文件出现时，先报组合。runtime direct/job handoff 在 `_normalize_upload_request` 内按 ticker→action→source→组合；tool 自身先校验 kind/action/JSON 参数形态，进入 material 组合判定后才检查单文件。未知 action 由 CLI argparse、tool `_required_upload_action` 或 runtime `_normalize_upload_action` 先拒；独立 workflow 绕开这些入口时由共享 owner 在 `try` 外 typed 拒绝。各入口消费同一组合事实，但多错误的入口局部优先级允许不同；O16 只承诺组合先于目标状态和文件读取，不承诺所有输入字段跨入口同序。
- 无需新状态机：非法请求不产生 started/progress/RESULT、job/observation、company/source/blob/meta/manifest 变更；合法请求的状态转换和 `requested_file_count`、`stored_file_count` 仍从同一原始请求与既有结果 owner 投影，material `requested_action` 则从同一 owner 的 typed 结果投影到事件与成功/失败结果。若实现时证实 owner 关系不能由直接调用链支持、runtime `request.action` 的既有公共表示与共享 `requested_action`/`pipeline_action` 结果无法并存、两条入口的 requested/resolved pair 无法同源、filing 行为必须在本 goal 扩权、合规 raw 请求在 `resolve_upload_action` 仍因 literal auto 退化或触达 Docling mismatch，或修订必须增加公开 schema/状态/产品语义，停止并给总控具体证据与问题，不用兼容 shim、下游 fallback 或旧测试倒逼计划。
