## Goal confirmation 与授权

用户要求优先修复首轮完整 PR197 review 的全部成立项，包含 F4；本目标复用 `docs/gateflow/pr-197-full-review-adjudication-20260929.md` 和 handoff 的 storage owner 边界。开发只在主工作树 `codex/upload-material-oracle`，全部成果进入现有 PR197。

目标：HK selected 批次的既有来源身份解析不再对每候选多次全量读取 D 份 meta/分别获取 publication guard；从 storage 所拥有的一致 publication 窗口读取，统一同 provider/source_id 的身份绑定以及财期纠正后新候选 ID 的分配。成功信号是 storage 在一个 publication guard 内批量交付身份解析所需的既有读取事实，窗口内身份消费者复用同一批量结果与内存索引；以身份解析为目的的逐条公开 list/meta 与独立锁循环消失。复用物理 integrity inspection 是可以评估的技术路径，不是原裁决要求的唯一 API，不能为选定该路径而改变用户已裁行为。既有 Phase A/B 和 commit 的全树完整性扫描及其成本保持，不承诺整个下载 run 的扫描/索引总工作量 O(D+S)。后续写身份在单 filing 的当前准备窗口确定，不能由批初绑定授权写入；批量读取窗口内事实一致，现有 duplicate/internal-ID/修复与取消约束保留。

## 直接证据与语义 owner

`cn_download_identity.resolve_cn_download_ids` 每个 HK candidate 遍历 list_source_document_ids 并逐条 get_source_meta；`cn_download_workflow` 为 accepted IDs、repair sort、filing-start 再次调用，`cn_download_filing_workflow` 又调用。storage `_fs_source_document_core.get_source_meta` 每条取得/释放 publication guard。缺陷是重复读取和独立读取窗口，不由 adapter/cache 局部弥补。

一致读取、publication 生命周期和版本事实的 owner 为 `dayu.fins.storage` 仓储协议/实现；provider/source_id 身份映射的 owner 为下载身份模块，workflow只消费同一受信结果。没有发现可直接复用的全批次 meta 公共 API；现有单文档 source snapshot 与 integrity inventory 应先评估是否可组合或窄扩展，不提前规定新增架构。

## 非目标与约束

不改财期推断、来源选择、表单词表、manifest成功语义，不引入跨 publication 全局cache、不绕过 storage 直接文件读取、不将传入旧快照当当前写入授权；不得为了性能吞掉异常或放宽不完整/重复来源校验。来源被修复或发布后必须清楚确定旧快照适用范围，不能固定复用到以后下载写入。

不将既有 resolve→commit 窗口内跨 writer 同 source 新绑定的 target-only 重验局限升级为本项事务性集合唯一约束；该增强另登记 residual/后续候选，不动 batch 生命周期或新增 staged API 来顺带修复。完整性 owner 判定 UNSAFE 的库存不能被默认为 MISSING 或默认空 meta；可信 COMPLETE/REPAIR_REQUIRED 身份不能遗漏。所有读取、绑定、拒绝和对外错误投影以用户现成裁决及现有 owner 契约为准，禁止为了批量优化新增拒绝规则或单方面迁移错误原因。总控此前接受 HK 损坏输入 ValueError/FileNotFoundError 改成 UNSAFE_PUBLICATION 的表述已撤回，该变更只是未授权建议，不能成为实施前提。若现有 owner 契约无法保全且确需业务行为变化，先给具体反例、公开投影差异及最小方案，停在计划交用户裁决；owner 测试须覆盖实际损坏、直调 filing stream 和成员资格边界。

F5 的本地 COMPLETE 年度证据可能也需要可信批量读取，存在潜在基础能力依赖；Sol plan须基于真实接口决定 F4是否先于F5，不能在F4中顺带实现F5或添加未来字段。新风险登记主队列与独立裁决。
