## 第一性原理判断与边界

动机成立，但「所有下载异常都要新诊断」「所有入口统一重做日志」过宽。异常文本既非可信业务事实，也非安全日志材料；真正缺口是 download runtime 捕获了未知异常却没有可定位的安全记录，而后台同一类异常还把不可信文本写进 durable job。最小成功信号是：未知异常在 direct 与 legacy download job 的实际 owner 控制流中留下有界、可定位、无原文的 operator 记录；公开失败和 job 终态沿各自 S1 已集成合同投影且不泄漏；S1 preflight typed 来源完整性失败不被报作未知异常。用户可见建议应指向保存诊断与排查，不暗示重复下载本身会修复未知错误。

本轮不改变 S1 storage/source reason、download summary 守恒、仓储发布、上传/处理、其它来源策略、无来源文档的非异常 RESULT、schema、Host/Engine/Service 分层或 LLM-facing trace/memory。外部 CLI/UI 不从日志重建失败分类；日志不是 source/storage 或 durable terminal 真源。不建立全局异常注册、日志治理或兼容层。

## 语义 owner、合同与实现决策

1. **唯一业务 owner**：`dayu.fins.ingestion_runtime` 的 `_download_public_failure_from_exception(exc, request)` 继续独占 download 公开失败分类、固定安全文案和恢复建议；direct RESULT 与 generic download job 的 `failure_summary["message"]` 从其同一 `FinsPublicFailure.safe_message` 派生。direct 异常 catch 的安全诊断判据为已验证的 `kind == EXECUTION` 且非 `_UnsupportedDownloadSourceError`；job 仅在 S1 typed catch 之后的 generic catch 应用此判据，绝不把 S1 typed catch 改走 generic。它是 **EXECUTION 档诊断判据**，不宣称其中每个 sibling 都是未知业务原因。provider/configuration、storage（包括 S1 接入后映为 storage 的 preflight typed 完整性失败）不打 `unexpected_failure`；普通 `OSError` 沿现有 storage 分类。本判据若与 S1 已集成 owner 不符，停止重审，不加兼容分支。
2. **唯一安全栈 owner**：消费 S1 已裁决的 `dayu.runtime.log.safe_exception_trace(exc: Exception, *, source_root: Path) -> str` 或集成后语义完全等价的唯一层中立 contract。若 S1 尚未实现该 S2 预设计，S2 只在 `dayu/runtime/log.py` 实现；若已实现，S2 只在该 owner 原位扩展深栈选帧，不另建 helper。调用点由自身模块位置给出经定位的 `dayu` 包根；runtime 不 import Fins/CLI/Service/Host/Engine，不分类、持久化或决定日志时机。函数及辅助函数按 AGENTS.md 有严格类型签名和完整中文 docstring。
3. **从允许字段构造安全类型与栈**：不调用 `str/repr(exc)`、`traceback.format_exception/format_tb`、`linecache`，不读 `args`、locals、源码行、cause/context/notes 或 provider payload；不传 `exc_info`、`stack_info`，不调用 `logger.exception`。单行格式逐字为 `exception_type=<安全内建祖先或 redacted> custom_type=<安全指纹或 redacted> stack=<安全帧列表>`。沿 `type(exc).__mro__` 只取第一个经 `vars(builtins).get(name) is class` 证实身份的内建异常类型；自定义类型只从类型对象的 `__module__`、`__qualname__` 两个 `str` 计算 `SHA-256((module + "\0" + qualname).encode("utf-8"))` 前 16 个小写 hex，不输出原名/模块名，元数据读取、校验、编码或哈希失败则 `custom_type=redacted`；内建类型也用 `redacted`。指纹只是 operator 诊断标签，不是 public reason。用 `traceback.walk_tb` 逐帧核对 `sys.modules` 中真实 `dayu.*` module 的 globals 身份、module 文件与 code 文件严格解析同一、规范文件位于传入的受信 `dayu` 包根、相对 `.py` 路径各片段均为合法标识符；仅合格帧输出 `dayu/…py:<正整数行号>`，其余只输出 `[external]`，不输出函数名或绝对路径。

   选帧以命名上限保留末端抛出帧和尾部窗口；遍历时另外保留**最深可信 Dayu 帧**，若它已在窗口中则不重复，否则替换尾窗最早的非末端槽位，按原 traceback 顺序输出。连续外部帧可压缩为固定 `[external]`，省略只用固定 `truncated` 标志，不输出外部帧数、原文件名或其它不可信值；最多 16 个帧标记，另有命名的总长度上限。帧标记以单个空格分隔，`truncated` 放在被省略区间与其后首个保留帧之间；例如 `exception_type=RuntimeError custom_type=0123456789abcdef stack=dayu/fins/ingestion_runtime.py:4320 truncated [external]`（路径/行号/指纹仅示例值，表示较早可信帧、被省略区间与末端外部帧，不作为实际运行值断言）。外部抛出点只可表示 `[external]`，不能谎称其文件/行号；有可信 Dayu 帧时，即使其后 >16 个外部帧也必须同时保留该 Dayu 位置与末端 `[external]`。无 traceback 输出 `[unavailable]`。逐帧校验失败局部降级 `[external]`；遍历、指纹、容器等非预期 `Exception` 由同一 helper 整体收口为固定 `exception_type=redacted custom_type=redacted stack=[unavailable]`，不抛给业务调用点。若 S1 实际 helper 的格式/失败合同不同，先回计划重审，不能偷偷分叉。
4. **direct 与 CLI 时序**：`_run_direct_stream_producer` 构造公共失败后先用既有 `_emit_direct_result` 发唯一 FAILURE，再为符合判据者准备安全串和固定 `fins.download.unexpected_failure` ERROR。CLI 仅在 `run_fins_direct_command` 最后一个 `except Exception` 且 `args.command_name == COMMAND_DOWNLOAD` 时准备 `fins.download.command_unexpected_failure` ERROR；typed CLI except 与非 download raw 日志行为不变。两处不重复记录 producer 已收口的失败。只把固定事件名与安全串暂存为标量，不能把原异常对象存入待发记录。**只在各自业务 `try` 语句及其 `finally` 正常结束后的语句位置**检查 `sys.exc_info() is None` 并发射；不得在 `except`、`finally` 或任何原/次异常传播路径发射。direct 发射仍在唯一 RESULT 与队列 Done 之后，CLI 发射仍在固定 stderr/退出码形成之前；现有队列 Done 顺序以 owner 测试固定。若 RESULT 构造/投递失败，正常后置位置不可达，跳过 S2 事件；RESULT 自身 failsafe 泄漏独立归 `fins-direct-projection-failsafe`。发射失败须被窄边界吞下，不使 worker/CLI 逃逸原异常；既有 RESULT、取消、队列 Done、固定 CLI stderr/退出码不变。正常配置下 ERROR 进入 operator 日志，不进入 direct event/LLM-facing 内容。
5. **job 时序与持久化**：S1 typed catch 保持先于 generic catch。generic download catch 改用下载专属 `_save_download_failed_from_exception(job_id, request, exc)`：由相同公共 failure 取 `safe_message`，读取最新 record，沿 `_save_failed` 的 `save_failed_or_cancelled_if_active` 保存 `failure_summary={"message": safe_message}`、`result_summary={}`，保留 `FAILED/CANCELLED` 幂等仲裁与现有 key；不能从 traceback、日志或 S1 typed summary 反推 generic 摘要。保存或发现已有终态后，符合 EXECUTION 且非 unsupported 的判据才准备一次 `fins.download.unexpected_failure` ERROR；二次读取/保存失败只追加固定 WARN `fins.download.failed_record_save_failed`，unsupported-source 二次失败只用固定 WARN `fins.download.unsupported_failed_record_save_failed`，均无动态 `error_type`、异常串、job id、路径、`exc_info`、`stack_info` 或 formatter 栈线索。helper 在其内层 catch 只返回待发的固定 WARN 标识；outer job catch 只暂存安全 ERROR/固定 WARN 标量，**只在整个业务 `try` 正常结束后的语句位置**检查 `sys.exc_info() is None` 并发射，不能在任一 `except`、`finally` 或原/次异常传播路径发射，防止 handler 自诊断沿隐式异常链复制原秘密。S1 typed 二次 WARN 继续只用 `fins.download.typed_failed_record_save_failed`；三类 download 终态二次失败一致采用固定事件强度，不虚称 durable terminal 已保存。共享 `_append_job_event_warn` 与 `_emit_progress_event` 也在其日志 owner 去除 `type(exc).__name__`：仅记固定 `fins.ingestion.job_event_append_failed` WARN 与可信枚举 `event_type`（progress 固定为 `PROGRESS`），不传 job id、source event type、payload key/count、异常类名/message、路径、`exc_info` 或 `stack_info`；两者须在自身 append 的 `try/except` 正常结束且 `sys.exc_info() is None` 后发射，以免 handler 自诊断沿二次异常链复制秘密。共享 helper 的非 download 调用仅改变日志材料，不改变事件追加、状态或结果。业务异常的安全 ERROR 仍尝试发射，二次失败不改变其 public failure；日志失败不回滚已保存终态。job store 本身失败时不能承诺 durable terminal 可读，测试和报告须区分。
6. **公开恢复建议与 CLI 展示**：`_download_public_failure_from_exception` 只对 `kind == EXECUTION` 且非 `_UnsupportedDownloadSourceError` 的异常逐字使用「请保存脱敏诊断并排查失败原因后重试。」；此判据与决策 1 的安全诊断判据同构，在唯一投影 owner 内窄分支处理共享 default 分支。direct `_UnsupportedDownloadSourceError` 仍投影 `safe_message="下载执行失败"`、`retry_hint="请重新发起下载；若持续失败，请检查运行日志中的脱敏分类。"`，逐字不变且不承诺不存在的安全事件；job unsupported 保留既有独立公开文案和终态路径。不把 CLI flag 放进 Fins/LLM 共享对象。`dayu/cli/output.py` 独占「请使用 --log-file PATH 重试并查看日志」，用于已验证的 EXECUTION download 详情和所有 direct 命令外层固定错误；退役 `fins.py:_FINS_DIRECT_UNKNOWN_FAILURE_MESSAGE`，不复制文本到新常量。非 download 最终外层文本与既有 `dayu-cli {command_name}: ` 前缀逐字不变。既有 `FinsPublicFailure` shape、`FinsResultStatus`/exit code、job schema 不变；根 README 解释 `--log-file PATH` 的实际保存方式。若需新增公开字段、变动终态状态/退出码/summary key，立即停止交总控。

### EXECUTION sibling 的 direct/job 事件矩阵

本表只规定诊断事件；业务 reason/summary 继续由 S1 与既有 owner 决定。`SourceIntegrityRevisionConflictError`、`SourceIntegrityRepairBlockedError` 等 sibling 仍落 EXECUTION 是已知分类残余，归 `fins-download-storage-sibling-errors`，S2 不新增业务分类。实际 catch 路由须在 S1 accepted+integrated 后复核。

| 异常入口与 S1 路由 | direct `fins.download.unexpected_failure` | job `fins.download.unexpected_failure` | 原因 |
| --- | --- | --- | --- |
| 未知 generic 异常 → EXECUTION | 记一次 | generic catch 记一次 | 两边均有异常捕获且无 typed owner。 |
| `FinsSourceDownloadAdapterFailure` 包含 revision conflict（S1 允许的私有 cause），S1 typed job catch | 记一次 | 不记 | direct 按公共 EXECUTION 档；job 在 generic catch 之前由 typed catch 收口，保留 S1 固定 WARN 政策。 |
| `FinsSourceDownloadAdapterFailure` 携非 typed cause（S1 防御测试形状），S1 typed job catch | 记一次 | 不记 | 单点 unwrap 后按 EXECUTION 投影，direct 记一次；job 已由 typed catch 收口，不误当 STORAGE preflight。该形状的业务分类仍归 sibling work unit。 |
| 裸 revision conflict 或 repair blocked 等 EXECUTION sibling，job 落 generic catch | 记一次 | generic catch 记一次 | 同一公共分类，job 路由不同；此观测不对称归已登记 sibling work unit。 |
| `SourceIntegrityPreflightError` → STORAGE，裸或 adapter 包裹 | 不记 | typed catch 不记 | 同源安全 reason 与结构化 job 摘要属 S1。 |
| provider/configuration → 各自封闭分类，或 `OSError` → STORAGE | 不记 | generic catch 不记 | 均非 EXECUTION 档；generic job 的消息仍必须安全。 |
| `_UnsupportedDownloadSourceError`；无来源文档的非异常 RESULT | 不记 | 不记 | job 有独立 unsupported 路由，direct 走共享 default 投影但须保留旧 message/hint；后者没有异常，普通 INFO 与文档 RESULT 不冒充 unknown 事件。 |

- handler 自诊断断言（OQ1/F3）：用会在 `emit` 失败并调用 stdlib `handleError` 的 handler，分别验证 Fins/CLI 与 event-append/progress 固定 WARN 日志失败时 stderr 允许 handler **自身** stack/`Traceback`，但其 `Message:`/`Arguments:` 只能是固定事件名与安全串或可信枚举，整个 stderr 无原业务/二次异常消息、秘密类名、URL、用户路径或原异常链；`threading.excepthook` 不收到原业务异常及原始 traceback，已发 RESULT/已保存 job/固定 CLI 失败不变。日志调用时断言 `sys.exc_info() is None`；测试还要覆盖 logger 直接抛错而非自行 `handleError` 的路径。另注入 direct RESULT 投递失败 + handler 自诊断失败的双故障，断言因后置正常路径不可达而**没有 S2 事件行、S2 handler 未被调用**；RESULT 自身可能进入 `threading.excepthook` 并泄漏的风险单独记入 `fins-direct-projection-failsafe`，不把该残余混入 S2 handler 隐私断言。
- 非目标与停止：不解决非 download 旧的 raw 日志、job store 本身不可写、direct RESULT 自身二次失败、默认临时日志退出后不可查、`--quiet` 显式抑制；这些均在报告分类，不作为本 slice 的新增修复。若任何测试显示安全格式必须读取原始消息/路径才能定位，或既有终态合同无法保持，停止交总控。
