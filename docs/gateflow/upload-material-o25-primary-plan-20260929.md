## 第一性原理、owner 与非目标

动机成立：当前 material CLI 未注册 `--primary`，tool 明确拒绝 material `primary`；`FinsUploadMaterialRequest` 也无 selector。`DoclingUploadService._build_pending_assets` 取首个转换结果为 `primary_document`，而 material 指纹只按 original 名、内容等排序，不含角色。source meta 保存 primary；storage snapshot 的 `get_primary_source()` 与 read runtime 使用它。故多文件的输入顺序可决定跨命令读取的业务源，改变顺序却可能因同指纹跳过。冻结 S24/S25 是旧 validation commit、不同 fresh workspace 的观察；同 workspace skip 是当前代码推导的风险，不能写成冻结实测。修复严重性是默认读取源可能违背用户明确意图，不是显示顺序问题。

唯一语义 owner 是 Fins 上传文件选择与资产规划边界：从 raw exact selector 产生一个 authoritative primary original，并以 O04/O23 已实施的**唯一**原件到 Docling 派生名契约确定 primary derived storage name。CLI、Service、tool 只传 raw selector；Docling 服务消费已验证选择与计划，负责读取、转换和准备发布；storage 负责最终完整性验证及 meta→manifest 投影；read 只消费完整 snapshot 的 primary。不得在 CLI、read adapter、仓储或事件展示层按首项、basename、转换结果、旧 meta 或文件质量重选，也不得为该语义在 `dayu.runtime` 新建业务 helper。

非目标：不实施 O04/O23、O16 的 action/files 规则、O05 的 form/name 规则、O19/O24、O33/O34 或其他 oracle；不改 Docling 内容/格式能力、并发模型、旧库迁移、历史冻结 evidence/registry/readiness；不改变 filing 的 primary、指纹、skip、转换范围和发布行为；material 所有合法原件仍逐个转换。material document ID 继续由 form type、material name、期间等业务身份产生，不纳入 primary 角色。

## 最小公开 selector 契约与 typed handoff

1. CLI `upload_material --primary PATH` 采用 filing 已有的可重复解析方式，以便 owner 看到 occurrence 数；tool 的可选 `primary` 仍是单个字符串字段；Service 的显式参数和 material raw request 保存 `tuple[Path, ...]`，保留 occurrence，不用 nullable 单值或 `extra payload`。各入口只做机械路径投影，不自行判断主文件。tool JSON schema 的单值字段不可能表达重复键；数组/非字符串是类型失败，重复 occurrence 的 owner case 由 CLI 与直接 Service/raw request 测。CLI help 明示 `--primary`/`--files`，tool schema 明示 JSON `primary`/`files`，分别从 Fins 规则真源说明同一规则：“单文件可省略、多文件必须恰好一个、主文件路径精确匹配本次文件路径之一、delete 不得提供”，并说明主文件决定后续默认读取的转换产物。
2. Fins admission 先区分 raw material request 与不可变 validated handoff，后者必须持有同一次 O04/O23 资产计划及唯一 primary original/其对应 pair；不以可空 `plan` 或下游重建兼容旧入口。单文件省略 selector 时由该 owner 选唯一原件；多文件省略返回封闭 `missing_multi_file_primary`；多于一个 occurrence（即使文本相同）返回 `multiple_primary_selectors`；一个 selector 经**与 files 同一个规范路径 owner**规范化后，必须与本批次一个原件的规范绝对路径区分大小写 exact 相等，未命中返回 `primary_not_in_files`。不能只匹配 basename、stem、派生名或 glob。规划结果只保存一个 pair 的引用/稳定索引，不另算名字。
3. **前置准入与错误归属**：已集成的 O16 owner 负责所有 action/files 组合；upsert 无文件和 delete 携文件由其 typed usage 拒绝，O25 不重复判断、不在 CLI/tool/adapter 补偿。O25 只为合法 action/files 输入增加 selector 规则：delete 携任意 selector occurrence 返回 `primary_not_allowed_for_delete`，不进入资产规划；upsert 的 selector cardinality（缺失/多次）先于 exact membership，单文件给错 selector 也拒绝。cardinality 须在文件读取、converter、observation/job 与发布前拒绝；membership 在与 files 同源的规范路径及唯一资产身份确定后拒绝，且不改 O04/O23 内部已接受的优先级。`delete + files + selector` 是 O16 与 O25 的复合非法输入：集成后按同一 owner 的实际 typed 决策断言各入口归属，不预设本计划的 selector 或 files 错误优先。O16 action/files、O05 form/name（若集成）、O04 规划与 O25 selector 共边界时，实施前共同核对复合错误次序和入口可达性；本计划只固定 O25 自有规则组内部次序，不单方锁定全局 admission 总序。失败从 owner 的封闭 reason 投影到 Fins usage、CLI exit 2 和 tool 可行动的有界中文错误；文件标签只用既有 public label 规则，不回显绝对路径、raw exception 或内部派生名。
4. **共享 usage 文案**：四个 selector reason 复用现有封闭 `FinsUploadUsageCode`，不新增 material 同义 code。O04/O23 集成后，在实际唯一 usage owner 将四条共享 message 改为 CLI/tool 均可理解的业务句：`MISSING_MULTI_FILE_PRIMARY` →“多文件必须指定一个主文件”；`MULTIPLE_PRIMARY_SELECTORS` →“主文件只能指定一次”；`PRIMARY_NOT_IN_FILES` →“主文件路径必须精确匹配本次上传文件路径之一”；`PRIMARY_NOT_ALLOWED_FOR_DELETE` →“删除时不得指定主文件”。这些句子只改表达，不改变单文件自动选择、多文件唯一 selector、规范路径 exact 匹配或 delete 禁止 selector 的规则与 typed reason。同一 owner 产生 reason/message，CLI 与 tool 原样投影；tool 错误不指示 CLI `--primary`/`--files`。CLI help 保留 `--primary`/`--files` 选项名，tool schema 保留 JSON `primary`/`files` 字段名，各自用同一 Fins 规则真源说明操作，不在消费者复制失败文案。owner 测试逐字断言四条 message、reason 映射和 kind 中性；入口测试核对 CLI/tool 同一 reason/message 与 CLI exit 2。本 WU 只处理这四句；其它全局 usage 文案归独立 `fins-upload-usage-message-channel-neutral`。
5. CLI 必须在 Service factory/stream 前取得同一 validated handoff；tool 与非 CLI runtime 在 observation/job 前取得它；SEC/CN/HK 独立 pipeline 直调在事件、company batch、converter 前取得它。Service、runtime、facade、Docling service 只原样传同一个 typed selection/plan。O04/O23 最终接口集成后，在其实际 owner 上扩充 primary 角色；不再做第二次规划。delete 沿用空 selection，无 primary pair。若已集成 handoff 无法承载单次计划的 pair 与 primary 选择，先回到 plan review 明确 owner，不造下游兼容分支。

## 派生名、指纹、持久化及读取同源

- O25 只选择 O04/O23 计划中的一个 original→derived pair。primary Docling storage name 直接读该 pair 的已规划名称；不复制候选计划中的函数签名，不用 `Path.stem`、索引、字符串拼接或转换完成顺序重算。`_build_pending_assets` 不再以首产物定 primary；仍处理 material 的全部 converter pairs。发布前核对 primary derived 恰好命中一项 planned/pending Docling asset，且每项 original、derived 名及来源关系与计划一致；storage 的最终完整性检查保持独立。
- material source fingerprint 由同一次计划的 canonical original descriptors（O04/O23 已接受的名字、字节 SHA-256、size、source）与 **primary original 的计划身份**共同构造；以固定版本标识区别旧无角色公式。companions 按稳定名字排序，primary 用计划原件名定位，绝不包含 argv 顺序、绝对路径、时间戳或输出顺序。相同 bytes、相同文件集合、相同 primary 在正逆序下指纹相同；只换 primary 则指纹不同。单文件新版本可能使旧 source 首次重传一次，这是新鲜起库契约的预期验证点，不加旧指纹 fallback。若 identical descriptors 无法唯一定位角色，应由 O04 的唯一身份约束前置拒绝，而非在 skip 阶段猜测。
- material 角色指纹的 `identical_skip_safe=True`：O04/O23 已集成的唯一原件身份保证同一计划内角色可区分，且 primary 明确引用其中唯一 pair；若最终契约不能保证此条件，停止而不是强设 True。`_can_skip_upload` 除指纹相等，还保留既有 overwrite/repair/deleted 和 `identical_skip_safe` 门；`_resolve_document_version` 同样消费这一门。primary 改变时指纹不等，进入转换/发布并递增版本；相同角色重放时安全跳过且版本不变。`_build_upsert_meta`、prepared mutation、`_store_upload_assets` 都传同一 role-aware 指纹和计划 primary derived；meta 中 `primary_document` 与 `source_fingerprint` 必须同次发布。`MaterialManifestItem.from_source_meta` 现只投影 `source_fingerprint`，没有独立 primary 字段：保持该 schema，从 meta 投影同一指纹，不增平行角色真源。storage 完整 snapshot 验证 meta primary 精确命中文件；read runtime 的 `snapshot.get_primary_source()` 原样消费。测试从 meta/manifest/read 反查一致性，不在 read 侧反推角色。
- 同一 workspace、相同原件字节的 A→B→B：A 首次发布为 `v1`；以 B、`auto` 上传时 document ID 不变、角色指纹变化、不返回 skipped、版本递增为 `v2`，meta primary、manifest 指纹和跨命令 `process_material`/read 均转到 B；再次传 B（含逆序）必须 skipped，`document_version` 仍为 `v2`，converter 与发布均未执行。另以 A 的正逆序对照证明顺序不改变角色指纹及 skip 决策。filing 的既有 role-aware fingerprint 算法和 primary 选择原样保留，不共用 material 新版本标识。
