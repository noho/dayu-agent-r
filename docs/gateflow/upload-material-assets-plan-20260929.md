## typed 失败和跨入口 handoff

planner 以封闭 `FinsUploadAssetPlanReason` 及 `FinsUploadAssetPlanError` 表达资产输入错误；关联文件仅投影 `canonicalize_fins_public_file_label(Path.name)`，数量不附文件标签。错误不含绝对路径、派生内部名或原始异常文本。两套 public closed code 按下表逐项投影，不从异常文本猜测：

| planner reason | `FinsUploadUsageCode`（`upload_usage_contract.py`） | `FinsUploadFailureCode`（`upload_failure.py`，kind=`USAGE`） |
| --- | --- | --- |
| `MISSING_FILES`（仅 upsert 空 `files`）/ `TOO_MANY_FILES` | 复用 `MISSING_FILES` / `TOO_MANY_FILES` | 新增同名 code |
| `DUPLICATE_FILE_PATH` | 复用 `DUPLICATE_FILE_PATH` | 新增同名 code |
| `DUPLICATE_ORIGINAL_BASENAME` | 新增同名 code | 新增同名 code |
| `ASSET_NAME_COLLISION` | 新增同名 code | 新增同名 code |
| `RESERVED_CONTROL_NAME` | 新增同名 code | 新增同名 code |
| `INVALID_ASSET_NAME`（非原样组件或长度超限） | 新增同名 code | 新增同名 code |

reason 判定先用 storage owner 的保守键比对**所有** original/derived 与 document 控制名：exact 控制名及其 case/Unicode 变体统一归 `RESERVED_CONTROL_NAME`，例如 `META.JSON`；其余真实业务 original/derived 相撞才归 `ASSET_NAME_COLLISION`。控制名分类不依赖原件遍历顺序；重复规范路径与重复 original basename 仍按各自前置 reason 处理。

planner 只产生封闭 typed reason、canonical 文件标签和数量上限等参数，不拥有或拼接用户文案。新的低层 Fins usage owner `upload_usage_contract.py` 迁入现有 `_USAGE_MESSAGES` 的唯一 message 模板，持有 reason→`FinsUploadUsageCode` 投影；现有 `FinsUploadUsageFailure`/工厂并无 retry hint 字段或旧模板可迁。三个复用 code `MISSING_FILES`、`TOO_MANY_FILES`、`DUPLICATE_FILE_PATH` 必须复用原有 usage 文案，其中 `TOO_MANY_FILES` 的模板由调用方传入已判 source 上限：material 传 `MAX_MATERIAL_UPLOAD_FILES`，filing 传 `ingestion_runtime.py` 既有 `_MAX_TUPLE_ITEMS`，当前均为 100，输出逐字不变且不传裸 `100`。新 planner reason 的有界中文 message 与新增 retry hint 模板只在该低层 usage owner 定义；`ingestion_runtime.py` 的 usage 构造消费其 message，`upload_failure.py` 的 planner 异常分类消费同一 reason 的 message/hint 并独立映射 public failure code。`upload_failure.py` 既有非 planner public failure retry hint 保持原 owner，不声称迁移或复制。CLI prevalidation 把同一 usage fact 装成 `FinsUploadUsageError`，由既有 handler 投影 exit 2；`upload_failure.py` 在 `_USAGE_FAILURE_CODES` 登记新 code 并维持分组互斥/完备断言，`fins_upload_failure_from_exception` 显式分类 planner typed error，使**本 work unit 的资产数量/身份规划错误**在独立 pipeline catch-all 得到同一业务原因而非 `UNEXPECTED_RUNTIME`。两套 enum 独立封闭，均由同一 planner reason 映射；格式错误沿既有 `FinsUploadFormatError` 路径。`MISSING_FILES` 严格只指 material upsert 的空 `files`，绝不指某个已列文件不存在或不是普通文件。本项只校验已确认的资产数量/身份；逐文件存在性和普通文件错误保留当前行为，非 CLI 入口可能仍落 `UNEXPECTED_RUNTIME`，CLI 的既有缺失路径文案也不由本项修复，故“不含绝对路径”只承诺新 planner reason 的投影。该缺口登记后续独立 work unit `fins-material-file-existence-admission`，届时以 Fins 公共文件标签及已有 `FILE_NOT_FOUND`/`FILE_NOT_REGULAR` 为真源另做 goal/plan；当前切片不得借 `MISSING_FILES` 或新增 fallback 处理它。owner 级测试直接断言每个 planner reason 的两种 code、三个复用 code 的旧文案、新 planner reason 的同源 retry hint、分类器、长度上界及路径安全，合法已存在普通文件样本保持可用。
