## 目标、动机、成功信号

全新公司在 material `create` 或由 `auto` 解析出的 `create` 中缺少名称，或既有公司元数据需要按当前 resolver 刷新而缺名时，`resolve_upload_company_meta_decision` 已知道输入不足。当前 material 的 SEC 与 CN/HK workflow 却在 `UPLOAD_STARTED` 后才开启 company batch 并调用该决策；异常进入普通失败映射。UM-A19 观察到 `unexpected_runtime`、已发 started、无公司/材料业务发布但有辅助目录与锁。因此问题成立：字段错误分类和拒绝时序均错误；“完全零文件变化”尚未由当前代码或旧运行保证，不能把它和零业务发布混同。

成功信号：

1. 对**身份字段有效**的 material 请求，Fins 在 direct stream、observed operation 或 durable job/runner 创建以及任何 `upload.started` 前，按同版已发布公司/目标状态解析实际动作，并复用公司 meta 决策。缺名仅在该决策要求名称时产生 `FinsUploadUsageError`，其 `failure.code == FinsUploadUsageCode.COMPANY_NAME_REQUIRED`，消息指出 `--company-name`；CLI 把它显示为运行参数错误。`delete` 不要求名称。
2. 已发布且当前 resolver 版本有效、无需名称变更的公司，即使 `auto/create/update` 对材料产生 upsert，省略名称仍可通过；既有 meta 版本过期而确实需要刷新时不得误放行。对请求别名的合法合并仍由原公司决策决定，不从是否存在目录推断是否缺名。
3. **接收时稳定状态**下的缺名拒绝没有公司 identity/meta、material source/meta/manifest、blob、job、observation 或业务事件发布；分别记录只读 preflight 的目录/锁辅助痕迹，真实 CLI 补跑查明能否零文件变化。合法公司 identity/meta 在独立 company batch 正常提交后，即使材料转换失败、取消或其后 source guard 冲突，仍是已合法发布的公司事实；材料无权威 manifest 条目则文档未成功。已接收状态漂移按下文阶段投影 typed 冲突，绝不重判为输入缺名或 generic `unexpected_runtime`。alias 冲突仍由 storage commit-time uniqueness guard 决定，不由前置快照代判。

## 非目标与范围

不改 argparse 使 `--company-name` 无条件必填；不改变公司名称合并、freshness、alias 存储和冲突发布真源；不在 CLI、Service、工具或各市场 workflow 重算“fresh”；不实施 O05、O16、O14、O15，也不重设计 material 完整状态机、tombstone、并发 overwrite 或 schema。此 work unit 的隔离实现测试只以有效的 `form_type`、`material_name`、文件组合和 material 目标身份触发 O12，避免用本项替代其它已裁决修复。任何额外缺陷记录给对应 work unit，不能吸收进本 plan。

## 可直接实施的契约和数据流

### 1. storage 同版状态与分阶段 guard

在 `dayu.fins.storage` 定义窄、不可变的 `MaterialUploadPublishedState`（exact canonical `ticker`/`document_id`、`company_meta: CompanyMeta | None`、source integrity status、完整可信 canonical business `source_meta`、独立 opaque source revision）和 `MaterialUploadStateRepositoryProtocol.read_material_upload_state(ticker, document_id)`。一次 ticker publication guard 内用 strict 公司读取与 exact material inspector 形成同版 snapshot；嵌套 JSON 深度冻结/独立复制，不能把可变 raw mapping 放入 admission。公司比较五字段全等：`company_id`、`company_name`、`ticker_identity`（含 canonical/market/exchange/accepted aliases）、`resolver_version`、`updated_at`。source 比较 status/presence/tombstone、全部 canonical business meta 字段与同版 revision，不列字段白名单，不丢时间或未知 canonical 字段。

状态类型与仓储 owner 强制：`MISSING`/`UNSAFE` 的公开 `source_meta=None` 且 revision=None，**即使 UNSAFE 私有 inspector 仍保留 business meta 也不得向下游投影**，二者由 typed status 区分；`COMPLETE` 的正常源和可信 tombstone 均有完整 meta+revision 同版在场，tombstone 保留 `is_deleted=true`、`deleted_at`、旧 `document_version`、`first_ingested_at`、`created_at` 等全部 canonical 字段；`REPAIR_REQUIRED` 仅在完整可信 meta+revision 同版在场时可返回，缺任一可信值由 storage owner 抛 typed source-integrity 错误，绝不伪装 MISSING。构造时校验 status、presence/tombstone、`is_deleted`/`deleted_at` 与 meta/revision 的关系。UNSAFE 与 REPAIR_REQUIRED 均不得进入普通 material action 解析。I/O/锁失败保持 operational 类别，损坏保持 typed integrity 类别；无 ticker tree 的只读路径不建目录，已有 tree 的锁痕迹如实记录。不能借 filing source kind、裸目录存在性或宽松 parsing 派生状态。

新增 material 专属窄 facade/core read，复用现有 strict 公司读取、exact material inspector 和 publication guard；`DefaultFinsRuntime` 与 SEC/CN pipeline 共享装配，runtime 只依赖协议。写侧只增加两种直接参数化、batch-scoped precondition：公司 batch 注册 admission 的 `expected_company_meta` 并 stage 原 `UploadCompanyMetaDecision`；材料 batch 注册 admission 的 `expected_source_state`（status、完整可信 meta、revision）和**公司阶段完成后**的 `expected_company_meta`（stage 取 `CompanyMetaCommitOutcome.company_meta`，keep/skip 取 admission.company_meta）。注册只检查 typed identity/batch 归属并记录到 `_ActiveBatchState`，不预读、不比较、不用 callback/extra payload。storage 唯一比较函数在对应 commit 的 ticker publication guard 内、首次 backup/swap 前重读 published view；company commit 比较公司五字段，material commit 比较 source 全值及 post-company meta。guard 内重读必须调用 unguarded 内部读取，不能重取非重入锁。两类 precondition 任一不等均由 `dayu.fins.storage.repository_protocols` 定义的单一 `MaterialUploadPublishedStateConflictError` 表示；storage core 在 guarded 比较处抛出，facade 透传，异常不携带路径、raw meta 或可供下游重算的字符串 reason。Fins failure owner 将它仅在 material 语境投影为已有 `storage/source_publication_conflict`；不用 `CompanyMetaConcurrentUpdateError` 冒充材料 source 漂移，也不新增 public code。alias/identity uniqueness 在 company commit 的 storage owner 最终检查，不下放 workflow。`keep/skip` 无公司 intent 时不为比较制造空物理发布。material skip 无 mutation 时在同一 storage guard 下只读比较 expected source/company 后才报告 skipped，不以空 batch 重发布 ticker tree。

### 2. Fins material admission 与失败真源

在 `dayu/fins/ingestion_runtime.py` 增加单一 material validator：`FinsUploadMaterialRequest` + `MaterialUploadPublishedState` → 不可变 `MaterialUploadAdmission`，显式携带规范化 request、canonical ticker、稳定 `document_id`/`internal_document_id`、resolved `create/update/delete`、**接收时同版 observed state**、`UploadCompanyMetaDecision` 和已验证的 `file_selection: FinsUploadMaterialFiles`。静态 admission 按规范化 request 的有序文件一次构造该 selection；delete 为 `for_delete()`，upsert 为 `from_upsert_paths(...)`，校验它与动作及 request 文件一致，作为 converter 的唯一文件选择真源。runner、两市场 workflow 和 `prepare_upload` 只消费 admission 的 selection，不从 raw files 再造一个。先沿用 ticker/action 规范化及 `build_material_ids`/`validate_material_upload_ids` 的身份规则定位 exact target；O05/O16 的静态字段/文件组合拒绝先于状态读取，O14/O15 后续 target 状态条件应先于公司缺名。无效身份不解释为缺名。

核对 snapshot 身份和状态不变量后，`UNSAFE` 与 `REPAIR_REQUIRED`（无论底层私有 meta 是否在场）都在 action 解析前 fail closed：UNSAFE 和有可信 meta 的 REPAIR_REQUIRED 由 validator 抛 `FinsUploadPrevalidationError`；无可信完整 meta 的 REPAIR_REQUIRED 由 storage read owner 抛 typed integrity 错误。两路经 Fins failure owner 投影 material 适用、业务可读、path-free 的 `storage/source_integrity_unsafe`，不得变成 `COMPANY_NAME_REQUIRED`、`unexpected_runtime` 或一般 `storage_io`；不在 O12 实施 repair。仅 `MISSING` 以 `None`、`COMPLETE` 以完整可信 meta 调用现有 `resolve_upload_action`；COMPLETE tombstone 的 `auto` 因 meta 在场解析为 `update`。再调用 `resolve_upload_company_meta_decision`，只将 `UploadCompanyNameRequiredError` 投影为 `FinsUploadUsageError(COMPANY_NAME_REQUIRED)`，提示 `--company-name`；`delete` 的公司决策为 `skip`。identity mismatch、损坏、I/O 不宽泛 catch 为缺名。

`FinsIngestionRuntime._validate_runtime_upload_request` 的 material 分支读取同版状态、调用该 validator，`upload`、`prepare_observed_upload`、`start_upload` 均先走此入口，再建 stream/observation/job。`FinsUploadRunner`、`ProductionFinsUploadRunner`、SEC/CN/HK facade 与底层 material workflow 的执行签名一律要求**必传** `MaterialUploadAdmission`；不设 `admission=None`、raw kwargs 双形态、默认值或执行期 fallback。runtime 已接收路径透传同一个对象；独立公开 material pipeline 的 raw request 入口先在首个事件前调用 `_material_upload_admission.py` 的共享 initial-admission helper，得到 typed admission 后才调用必传签名。helper 复用同一个静态校验、同版状态读取与 validator，不自行解释名称/freshness；接收后不得第三次自由读 published state、重建 selection 或重判缺名。CLI 在 `FINS_DIRECT_SERVICE_FACTORY` 前只构造一次 `FinsUploadMaterialRequest`，同一对象给只读 workspace prevalidation 和 `FinsDirectCommandService.upload_material(request, ...)`；Service 交给 runtime，不重建、不塞 extra payload。CLI 预检和 runtime 接收是两个时点，后者再次读当前状态；在接收前变为需名仍属 usage，接收后状态变化只由 storage guard 给 typed conflict。

**O12-PR4-F1：**`dayu/fins/upload_failure.py` 为 material 增 path-free、覆盖公司或材料状态变化的 `source_publication_conflict` reason 构造器，保留 filing 原文案；为 UNSAFE/REPAIR_REQUIRED 提供 material 适用的 `source_integrity_unsafe` 文案。failure owner 新增明确的 material 语境异常映射入口：先取 `FinsUploadFailureError.failure`，再将 material 语境的 `CompanyMetaConcurrentUpdateError` 与 `MaterialUploadPublishedStateConflictError` 投影到 material conflict 构造器，其余复用现有安全分类；既有 `fins_upload_failure_from_exception` 的 `CompanyMetaConcurrentUpdateError → STORAGE_IO` 分支和 filing 文案保持不变。两个市场 material workflow、direct、observation 与 upload job 使用同一 material 映射入口，filing 继续使用既有映射；不在各入口按异常文本/字符串重算。workflow、direct RESULT、observation completion、durable job 的 `failure_summary`/`result_summary.failure` 均从同一 `FinsUploadFailureReason` 派生 `kind/code/message/retry_hint`。已接收的公司决策绝不因后置变化再次抛缺名；alias 唯一性冲突保留 `ticker_alias_conflict`；损坏/I/O 仍分别保持 integrity/operational 类别。

**O12-PR4-F3：**upload job 的 `except Exception` 在 `ingestion_runtime.py:_run_upload_job` 调用 upload 专属 typed 终态保存路径：由 failure owner 按已接收 request 的 filing/material 语境取得同一 reason，形成带 `source_kind`、请求文件数、`stored_file_count=0`、`status=failed` 和 `failure_reason=reason` 的 `FinsUploadResultSummary`，并把 `failure_summary=reason.to_json()` 与 `result_summary=summary.to_json_summary()` 一次保存为同一 failed terminal。正常返回 summary 的既有 typed 路径保持同一投影。`_save_failed_from_exception` 及其 message-only `_save_failed` 继续专用于 preprocess/download 等既有调用，不塞 upload code 或可选 typed 参数；download 泛异常的 `failure_summary`/`result_summary` 形状和 terminal disposition 不变。异常终态的 `stored_file_count=0` 只表示本次没有确认返回的材料成功结果，不用于推断 post-commit durable manifest 不存在；R2 的不确定性仍须单列。

**O12-PR4-F2：**CLI 的 `FinsUploadPrevalidationError` catch 继续仅渲染 `exc.failure.message` 并返回 `EXIT_FAILURE`，但日志中的命令名和 `dayu-cli ...:` 前缀均由已解析的 `args.command_name` 给出；对 `upload_material` 的 UNSAFE/REPAIR_REQUIRED 不得显示 `upload_filing`。usage 的 `EXIT_USAGE_ERROR` 路径保持原 contract。

### 3. O34 独立 publication 与竞态时序

前置 snapshot 只裁决接收时缺名，不是发布许可。**O12-PR4-F4：**SEC/CN/HK material workflow 删除 `stage_company_meta_for_upload` 的重新读/重判，改用 admission 的 typed decision；同时从 `upload_company_meta.py` 删除已无生产调用的该函数、`__all__` 导出、仅为它服务的 `_load_existing_company_meta` 与 `Sequence` import，不保留可重新读/重判的兼容入口。测试中两处旧 helper 引用分别迁为 `resolve_upload_company_meta_decision` + `stage_upload_company_meta_decision`（非法 alias 测试）及基于仓储已发布 meta 的纯 decision + stage（跨进程 alias commit 测试），不在测试夹具复制旧 helper。若 decision 为 `stage`，**先开启独立 company batch**，注册 admission expected company meta、stage 原 intent，storage 在 identity/alias guard 和 ticker publication guard 下比较、合并并 commit；正常返回的 `CompanyMetaCommitOutcome.company_meta` 是后续 expected company。若为 `keep/skip`，不建空 company batch，expected company 保持 admission 值。stage 公司 commit 之前的公司漂移（包括仅 `updated_at`、`resolver_version` 变化）是 typed `source_publication_conflict`，无本请求公司或材料发布；alias 与漂移同轮命中时 storage identity/alias 冲突优先，仍为 `ticker_alias_conflict`。当前 `_prepare_company_identity_commit` merge 早于 alias scan，实施需在 storage owner 内以现有 authoritative uniqueness 规则安排 alias 优先，且保留最终 staged identity 校验；不得在 workflow 预判别名。若 source 在公司 commit 前已漂移，独立公司事实仍可合法提交；公司 batch 在 `begin_batch` 时复制当时已发布 tree，ticker writer lock 覆盖 batch 生命周期，不能用 admission 的旧 source tree 覆盖它。

公司阶段后调用 `prepare_upload(selection=admission.file_selection, previous_meta=admission.observed_state.source_meta)`，不再调用 `_safe_get_document_meta` / `_safe_get_upload_document_meta`，也不从文件列表重新构造 selection；同一 COMPLETE tombstone meta 供 auto 解析、转换准备、版本与首次时间连续性。转换/内容失败或取消时不创建材料 batch，不反向回滚已正常提交的公司 identity/meta；材料 source/meta/blob/manifest 未发布，文档不能报成功。`prepare_upload` 返回 skipped 时先执行 storage guard 下的 expected source/post-company 比较；通过才返回 skipped，不发布材料。返回 prepared mutation 时开启**材料自己的 batch**，注册 admission expected source 与 post-company expected meta，在该 batch stage source mutation，由 `commit_prepared_upload_batch` 完成最终取消检查、材料 manifest 与 source 同源 staging 和**仅此材料 batch** commit。材料 batch 的 source/status/revision/presence/tombstone 或 post-company meta 漂移，在首次 backup/swap 前 typed `source_publication_conflict`，材料零发布；前序合法公司提交可保留。材料目标与权威 material manifest 条目同源且材料 commit 正常返回后才可报 `ok`；只有 staging 条目、Docling 产物或公司事实均不算上传成功。commit 后 guard 释放异常与 pre-commit 拒绝分开记录，不倒推“失败必无已发布 manifest”。

分阶段验收矩阵：**A** admission 后、公司 commit 前公司漂移/alias 抢占 → typed conflict/alias、零本请求公司与材料事实；**B** 公司 commit 已正常返回、转换失败或取消 → 合法公司事实可留，材料无 manifest/成功；**C** admission 后、材料 commit 前 source 漂移（含在公司 commit 前已发生的 source 漂移）、或公司 commit 后再次公司漂移 → material typed conflict、材料零发布，已经合法提交的公司事实可留；**D** material skip 的 expected 状态漂移 → typed conflict，不虚报 skipped，合法公司事实可留。首事件可以早于 A/C 冲突，但稳定缺名必须早于任何事件、job/observation 和业务写入。A/C 的 direct/job/observation/CLI/tool 只消费同源 typed reason，不降级 `unexpected_runtime`；内容错误和取消保持各自原有 typed 终态，不伪装成状态冲突。此方案只新增各 owner 必需的 guarded precondition，不扩大 binding goal/schema，不建跨公司与材料事务或重试框架；O05/O16/O14/O15 仍按既定依赖串行接入。
