### 1-未修复-严重-web-tools-getattr 类型逃逸——违反 getattr/hasattr 编码硬约束

- **入口/函数**: `_resolve_full_page_content`、`_http_fetch`、`_build_http_response_text` 及 `web_tools.py` 中多处函数
- **文件(行号)**: `dayu/tools/web/web_fetch_orchestrator.py:152,243-245,264,366,517,819,835,856,876`；`dayu/tools/web/web_tools.py:677-681,1907,1939`；`dayu/tools/web/web_http_encoding.py:205,212,217,221,240,255`
- **输入场景**: 处理 `httpx.Response` 对象时，代码依赖 `getattr(response, "url", default)` 等模式访问已知类型属性。
- **实际分支**: `httpx.Response` 是项目依赖中已声明的类型。代码使用 `getattr` + 默认值绕过 pyright 类型检查。
- **预期行为**: 直接使用属性访问（如 `response.url`），让类型检查器验证正确性。
- **实际行为**: 使用宽松的 `getattr` + 默认值模式，掩盖属性缺失错误、静默传播空默认值，并使 pyright 的类型检查在该路径完全无效。
- **直接证据**: `web_fetch_orchestrator.py:243-245`: `http_status=getattr(response, "status_code", None)` 等；`web_http_encoding.py:205`: `headers = getattr(response, "headers", {})` 等。
- **影响**: 违反 CLAUDE.md "禁止使用 `hasattr`、`getattr` 必须有充分理由，不能把它当作逃避类型与边界设计的手段"的硬约束。若 `httpx` 响应结构发生变化，默认值会传播错误数据。
- **建议改法和验证点**: 在 web fetch 层入口使用 `isinstance(response, httpx.Response)` 窄化类型。若存在非 `httpx.Response` 的响应类型，定义 Protocol 或窄化 Union。补充测试验证字段缺失时快速失败。
- **修复风险（中）**: 调用方可能依赖当前"缺失字段时静默回退默认值"的行为。

### 2-未修复-严重-fins-read-runtime-getattr 类型逃逸——processor 能力探测绕过类型系统

- **入口/函数**: `_collect_xbrl_taxonomy`、`_collect_page_content`、`_collect_financial_statement`、`_collect_xbrl_facts`
- **文件(行号)**: `dayu/fins/tools/read_runtime_helpers.py:1314,1320`；`dayu/fins/tools/read_runtime.py:1142,1221,1325,2091`
- **输入场景**: processor 对象通过 `getattr(processor, "get_xbrl_taxonomy", None)` 等探测方法/属性存在性。
- **实际分支**: processor 可能来自不同类型（XBRL vs. text vs. statement）。代码使用 `getattr` + `None` 默认值在运行时探测能力。
- **预期行为**: 应定义 Protocol 或具名 Union 表示"具有可选 XBRL 能力的 processor"。
- **实际行为**: 运行时探测方法存在性完全绕过类型检查。若方法名拼写错误，将静默失败。

- **修复风险（中）**: 需要重新设计 read_runtime 中 processor 能力分发架构。

### 3-未修复-高-cancel-run-predispatch-race cancel_run 对 predispatch STARTING→WORKER_ACCEPTED 竞态窗口处理不完整

- **入口/函数**: `_CancelRunOperation.__call__` → `_cancel_predispatch_starting_or_none` → `_cancel_active_attempt`
- **文件(行号)**: `dayu/host/admission.py:1541-1553, 1648-1712, 1778-1847`
- **输入场景**: Run 状态为 `RUNNING`，Attempt 状态为 `STARTING`，但 dispatch_record 已被 worker accept（`WORKER_ACCEPTED`），Attempt 尚未被 `ATTEMPT_RUNNING` 事件更新为 `RUNNING`。
- **实际分支**: `_cancel_predispatch_starting_or_none` 调用 `cancel_predispatch_starting_in_transaction` 要求 dispatch 为 `WAITING_FOR_LANE` 或 `DISPATCHING` 且无 `worker_accept_event_id`。当 dispatch 已 `WORKER_ACCEPTED` 时 CAS 失败返回 `None`。回退到 `_cancel_active_attempt`，调用 `request_active_attempt_cancel_in_transaction`，该函数期望 Attempt 状态为 `RUNNING`。但此时 Attempt 仍为 `STARTING`，CAS 返回 `INVALID_STATE`，`_raise_for_cancel_transition_status` 抛出 `HostApiError(INVALID_STATE)`。
- **直接证据**: dispatch.py 的 `_start_worker` 在 worker accept 后立即将 dispatch 标记为 `WORKER_ACCEPTED`，但 `ATTEMPT_RUNNING` 事件的写入发生在 worker accept 成功后的异步 task 中。此窗口期内 cancel 会失败。
- **影响**: 在 worker accept 与 `ATTEMPT_RUNNING` 事件写入之间的狭窄窗口（通常毫秒级）中，cancel 请求收到 `INVALID_STATE` 错误而非正确进入 CANCELLING 流程。可能导致 Cancel 被上层误认为"Run already terminal"而放弃重试。
- **建议改法和验证点**: 在 `_cancel_active_attempt` 中增加 `STARTING` + `WORKER_ACCEPTED` dispatch 组合的判断分支，将此窗口视为 active worker cancel。单测覆盖 `STARTING+WORKER_ACCEPTED` 组合。
- **修复风险（中）**: 需确保状态转换矩阵全部覆盖，不引入新竞态。

## Architecture & Design Observations

以下观察不是 defect，但作为架构层面的发现记录：

### A1. 层边界强制执行良好

- `dayu/runtime/` 无任何对 `dayu.engine`、`dayu.host`、`dayu.service`、`dayu.fins` 的 import —— 严格遵守层中立约束。
- `dayu/contracts/` 无任何对 `dayu.engine`、`dayu.host` 的 import —— 严格保持契约包独立性。
- `dayu/engine/` 无任何对 `dayu.host`、`dayu.service` 的 import —— Engine 只依赖 contracts 和 runtime。
- 分层架构 `UI -> Service -> Host -> Engine` 在 import 层面得到严格验证。

### A2. 类型安全

- pyright 1.1.409 报告 **0 errors, 0 warnings, 0 informations** —— 全仓零类型错误。
- 所有模块使用 `from __future__ import annotations` 启用延迟注解求值。
- 使用 Python 3.11+ 特性（`StrEnum`、`assert_never`、`dataclass(slots=True)`、`match` 语句）。

### A3. 测试覆盖

- **3795 条测试** 被收集，5 条 deselected（stress marker）。
- 测试按子系统组织：`tests/host/`（60+ 文件）、`tests/engine/`、`tests/fins/`、`tests/runtime/`、`tests/service/`、`tests/contracts/`、`tests/tools/`。
- Host 子系统测试覆盖 admission、dispatch、recovery、compaction、memory、tool runtime、waiting、event log、projection、steer 等关键路径。
- smoke 测试覆盖多轮闭环、conversation memory continuity、awaiting entrypoint 和 provider 连通性。

### A4. Recovery 设计

Recovery 模块使用多证据 positive orphan proof 方法：
- PID 存在性检查（`os.kill(pid, 0)`）
- start token 匹配（防止 PID 复用）
- boot ID 匹配（防止系统重启）
- heartbeat 新鲜度检查（`_DEFAULT_STALE_AFTER_SECONDS = 30`）
- 只有 positive proof 成立时才 closeout 旧 Attempt 或创建 recovery Attempt

这种方法避免了误判活跃进程为孤儿。

### A5. Admission Idempotency

每个 admission 操作（start_run、submit_followup、cancel_run、retry_run、replay_run）都有独立的 `IdempotencyScope`，在 durable transaction 内检查幂等。idempotency record 保存首次操作结果引用（`IdempotencyResultRef`），重放时返回既有结果而非重复执行。

### A6. SSE Parser Edge Cases

SSE parser 处理了以下边界条件：
- 单行长度上限：1MB（`_MAX_SSE_LINE_CHARS`）
- data 行数上限：256（`_MAX_SSE_DATA_LINES`）
- 非法 UTF-8 字节序列
- 截断的 UTF-8 尾部
- 缺失 terminal finish_reason
- 格式错误的 usage 字段
- provider error payload 提取

### A7. 代码整洁度

- 全仓搜索无 `TODO`、`FIXME`、`HACK`、`XXX`、`WORKAROUND` 标记 —— 没有已知的未完成临时方案。
- Engine 层和 core Host 层 `hasattr`/`getattr` 使用极少（runtime 层仅 3 处）。但在 `dayu/tools/web/` 和 `dayu/fins/tools/` 中存在严重 `getattr` 类型逃逸（见 Finding 1、2），需优先修复。
- 生产代码中无 magic string（工具 schema 除外，schema 内允许字面量）。
- Compact 管线中发现英文 LLM-facing 前缀（见 Finding 26），与中文导向代码库不一致。

## Open Questions

1. **Process-backed tool 超时治理策略**：Finding 18 指出 process-backed 工具无超时上限。若为 process-backed 工具增加 Host 级超时，是否会对当前依赖长执行时间的工具（如 Docling convert）产生 breaking change？per-tool 超时配置的粒度如何设计？
2. **evidence_kind 字段的语义 owner**：Finding 20 指出 Host 硬编码所有 fact 的 evidence_kind。该字段应由 LLM 产出（需改 prompt）还是 Host 从 material pack 派生？若 Host 派生不可行，是否应删除该字段和未使用的枚举值？
3. **Compact 管线中 LLM-facing prompt 的合规性**：Compact prompt 由 `dayu/host/llm_compaction.py` 和 `dayu/host/compact_material.py` 构建，这些 prompt 是否完全遵守 CLAUDE.md LLM-facing 文本约束（如不自洽地暴露内部术语，不使用代码类型名），需要专门的 prompt audit。Finding 26 已发现英文前缀混入中文 prompt。
4. **Fins storage 并发安全**：`dayu/fins/storage/` 下的 filesystem repository 实现在多进程写入同一 ticker 时的事务安全边界，以及 batch token 是否已在上层保证单 writer（见 Finding 4），本 review 未完整覆盖。
5. **SSE stream robustness**：`_iter_response_bytes_with_idle` 中的三方 race（pending、timeout、cancellation）——当 `readany()` 在 timeout 边界刚好返回数据时的竞态窗口，本 review 未穷举验证。
6. **Compact 重复触发保护**：Finding 24 指出的 reactive compact 无限循环风险需要确认是否有其他隐性 circuit breaker（如 max_iterations 或 dispatch 层保护）。

## Residual Risk

1. **ToolRuntime 拆分风险**：`dayu/host/tool_runtime.py`（7613 行）是当前最大的单一风险面。Finding 18、19 均在此文件中。任何修改都可能引入回归。建议优先拆分。
2. **Process-backed 工具超时缺失**：Finding 18 的修复涉及变更执行合约，可能影响 Fins 工具的长时间 ingest 操作（Docling PDF 转换等）。需要 per-tool 可配置的超时策略和充分的集成测试。
3. **getattr 类型逃逸**：Finding 1、2 的修复涉及 web tools 和 Fins read_runtime 的类型重构，修改范围较大。修复时需确保不引入新的属性访问错误。
4. **宽泛异常捕获的未审计路径**：全仓约 30+ 处 `except Exception`。部分在清理路径可接受，但在 durable 写入/提交路径的需要进一步审计。
5. **Prompt 资产 LLM-facing 合规性未审计**：`dayu/config/prompts/` 下的 scene prompt、fragment 和 compactor prompt 是否符合 CLAUDE.md LLM-facing 文本约束，本 review 未覆盖。
6. **Fins 处理器注册表完备性**：`dayu/fins/processors/` 下的 30+ 处理器文件的注册完整性和多 processor 选择逻辑的确定性未完整验证。
7. **Web/WeChat/Render 入口**：这些入口当前仅返回诊断信息，未实现真实功能，不在本 review 范围内。
8. **SSE stream 取消竞态**：`readany()` 在 timeout 取消边界的数据丢失风险（subagent 3 指出），需要专门的流式健壮性测试。
9. **Durable idempotency store 的 IntegrityError 重试**：`dayu/host/durable/idempotency.py` 中 SQLite busy 时的重试退避逻辑未穷举验证。
10. **跨层取消传播**：Engine 级取消如何通过 Host 到达 `BatchToolExecutionContext` 中的 `CancellationToken` 的完整链路未逐层追踪。
