## Material Findings

### F1 — S2 periodic reconciliation 机制语义不够明确

- **位置**: plan §4.5 第 6 条、§4.7（Service observation）mailbox-empty reconcile、S2 §7（Exact changes/dataflow 第 7 条）
- **问题类型**: 不可直接实施
- **当前写法**: "mailbox空时，等待 level readiness 或周期 timer；timer 触发 bounded durable reconciliation"（§4.5.6）；"mailbox空时用level ready + periodic timer驱动bounded reconcile"（S2.7）
- **反例/失败场景**: 若 implementation agent 把 "periodic timer" 理解为 `asyncio.create_task` 后台循环，会违反 §4.3 不变量 "Host subscription不创建 per-watcher background task"。反过来，若用 `wait_ready(timeout=N)` 的 timeout 做 reconcile trigger，则 reconcile interval 与 wait timeout 语义耦合——timeout 短会无谓唤醒，timeout 长会推迟跨 opener terminal 发现。
- **为什么有问题**: plan 把两个不同机制（level-ready wake 和 periodic reconcile）压缩在同一个 "等待" 语义下，但没有明确声明 reconcile 的驱动方式是 timeout-based retry loop 在 `__anext__` 内部，还是独立的 asyncio timer handle。S2 是 data-plane correctness 的基础 slice，这一语义模糊会导致 implementation agent 做架构决策而非机械翻译。
- **直接证据**: plan §4.3 不变量明确 "Host subscription不创建 per-watcher background task"，但 S2.7 "periodic timer" 未绑定到具体实现机制；Host design.md:519 同样声明 "Host subscription 自身不创建 per-watcher background task"。
- **影响**: implementation agent 可能引入后台 task（违反不变量），或把 reconcile 与 wait timeout 语义错误合并（导致跨 opener terminal 发现延迟不可控）
- **建议改法和验证点**: 在 S2 exact changes 中显式声明：reconcile 由 `__anext__` 内部 `wait_ready(timeout=reconcile_interval_seconds)` 的 timeout 分支驱动，timeout 后执行一次 bounded durable scan（最多 page_size rows），然后回到 wait_ready；不创建独立 timer task。reconcile_interval_seconds 可以是 Host-internal 合理常量（如 5s），不进入 public policy。测试验证：空 mailbox + 无 local notice 场景下，跨 opener terminal 在 reconcile_interval 内最终交付。
- **修复风险**: 低 — 只需补充实现语义，不改变 contract
- **严重程度**: 中

### F2 — S3 port factory 循环依赖的 binder 生命周期可能比 scheduler 更短

- **位置**: plan §5.3（terminal producer qualified-callsite 闭集）、S3 §10（Exact changes/dataflow 第 10 条）
- **问题类型**: 并发恢复风险
- **当前写法**: "HostDispatchScheduler.open使用一个仅Host-internal、由循环依赖充分理由支持的typed port factory；scheduler对象构造后、任何heartbeat/watchdog/worker terminal producer可运行前必须完成non-optional port bind。factory接收scheduler ordinary promotion能力并返回open_host coordinator；factory/bind失败必须关闭未启动scheduler资源。禁止可在运行期重新bind的setter。"
- **反例/失败场景**: factory 返回的 coordinator 持有 scheduler 的 promotion port 引用。若 coordinator 因任何原因先于 scheduler 被清理（例如 open_host 构造中途失败、partial close），scheduler 的 heartbeat/watchdog 继续运行并调用已失效的 terminal port → 未定义行为或静默丢失 terminal notice。
- **为什么有问题**: 当前 plan 描述了 factory 的 happy-path 构造顺序和 bind 失败关闭，但没有描述 coordinator 与 scheduler 的相对生命周期——特别是 scheduler 的 background heartbeat/watchdog 可能在 coordinator 被清理后继续运行。terminal port 的 local-only 语义意味着这种失败不会被 durable DB 自动修复（因为同一 opener 没有第二个 coordinator 接管）。
- **直接证据**: plan S3.10 "factory接收scheduler ordinary promotion能力并返回open_host coordinator" + plan §4.6 coordinator 是 opener-local runtime scalar + design.md:380 "TerminalPostCommitPort 的实现 owner 是 producer 所属 open_host opener 内的 terminal post-commit coordinator"
- **影响**: scheduler background task 调已释放 coordinator → 静默丢失 terminal notice → 本地 watcher 不唤醒 → 依赖下次 periodic reconcile 恢复（延迟可达 reconcile_interval）
- **建议改法和验证点**: 在 S3.10 明确 coordinator close 顺序：先停止 scheduler heartbeat/watchdog/worker（使 terminal producer 不再产生新 notice），再关闭 coordinator port，最后释放 coordinator。若 coordinator close 时仍有 in-flight notice，记录 operator diagnostic 但不阻塞 close。测试验证：open_host 构造中途失败 → scheduler 未启动 → coordinator 正确清理；Host close → heartbeat 先停 → coordinator 再关。
- **修复风险**: 低 — 补充生命周期约束，不改变 contract
- **严重程度**: 中

### F3 — S4 `asyncio.to_thread` callback job 无超时收口

- **位置**: plan §4.7（Service observation 状态机）、S4 §7（Exact changes/dataflow 第 7 条）
- **问题类型**: 并发恢复风险
- **当前写法**: "_invoke_callback创建并shield一个asyncio.to_thread task，consumer await其完成；callback original error转换为CALLBACK_FAILED。outer cancellation时先等待已启动job完成/失败并使late commit失效，再继续consumer/iterator cleanup"
- **反例/失败场景**: renderer callback 内部调用 `threading.Lock.acquire()` 或阻塞 I/O（例如写 stderr 时终端 buffer 满、网络文件系统卡住），thread job 无限期阻塞。consumer 在 outer cancellation 时 `await` 该 job 完成 → 永远等不到 → consumer cleanup（包括 `aclose()`）永不执行 → Host reservation 泄漏、session subscription cap 永久减少。
- **为什么有问题**: plan 承认 callback 应在 thread 执行域隔离，但没有给 thread job await 提供超时保护。虽然 contract 要求 callback "快速、同步、非阻塞"，但 production 环境下 renderer 阻塞是现实风险（尤其在 CI/headless/TTY 异常场景）。当前设计中 consumer cleanup 的正确性完全依赖 callback 在有限时间内返回。
- **直接证据**: plan S4.7 "consumer await其完成" + plan §3.3 non-goal "不让慢 watcher对 Agent/Engine/promotion/其它 watcher形成被动 backpressure" — 但这里 callback thread 阻塞会反压 Service consumer cleanup，不属于 Host 侧 backpressure 承诺范围。
- **影响**: 阻塞的 callback thread → consumer cleanup 永久悬挂 → reservation 泄漏 → Session cap 永久减少 → 后续 `watch_session_events` 可能被 `RESOURCE_EXHAUSTED` 拒绝直到 Host restart
- **建议改法和验证点**: 给 `await job` 增加有界超时（例如 5s）；超时后记录 `WATCHER_DIAGNOSTIC`、放弃该 callback result、late commit 自动失效，然后继续 cleanup。超时值可以是 Service-internal 合理常量，不进入 public contract。测试验证：注入永不返回的 callback → consumer cleanup 在超时后完成 → reservation 释放。
- **修复风险**: 低 — 只增加超时保护，不改变 happy-path contract
- **严重程度**: 中

### F4 — S2 跨 opener barrier 测试对现有 fixture 能力的依赖未确认

- **位置**: plan S2 Allowed tests 列表、S2 Tests/assertions 第 4 条
- **问题类型**: 测试缺口
- **当前写法**: "双opener共享DB：watcher+B在C，A terminal在A，C无local notice；B fence迫使C多页catch-up先交付A terminal"；allowed tests 包含 `tests/host/test_open_host_runtime.py`、`tests/host/test_watch_session_events.py` 及 "为双openerfixture涉及的现有Host support files"
- **反例/失败场景**: 若现有 Host test fixtures 不支持同进程双 opener（两个独立 `open_host` 实例共享同一 SQLite DB），implementation agent 需要先搭建双 opener fixture 基础设施才能写 S2 barrier 测试。这会扩大 S2 scope，把 fixture 搭建风险混入 causal fence correctness 验证。
- **为什么有问题**: S2 是 data-plane correctness 的基础 slice。若双 opener fixture 不可用，S2 的跨 opener barrier 测试无法独立验证，implementation agent 要么跳过（留下 correctness gap），要么在 S2 中搭建 fixture（增加 slice 复杂度和失败风险）。plan 当前只说 "为双openerfixture涉及的现有Host support files"，没有确认这些 support files 是否已支持双 opener。
- **直接证据**: plan S2 allowed tests 列表未列出具体 fixture 文件；`tests/host/public_smoke_support.py` 通常提供单 opener helper；plan §8.1 S2 focused gate 命令只有单 opener 测试。
- **影响**: S2 最关键的正确性 barrier（跨 opener terminal 交付）可能在实施时发现缺乏测试基础设施，导致阻塞或测试覆盖降级
- **建议改法和验证点**: 在 S2 实施前，先确认现有 fixture 是否支持双 opener 共享 DB（例如 `public_smoke_support.py` 是否有 `open_second_host()` helper）。若不支持，在 S2 scope 内增加最小 fixture（第二个 `open_host` 调用），或把双 opener fixture 作为 S1 的交付物。
- **修复风险**: 低 — 只需确认或补充 fixture，不改变 contract
- **严重程度**: 低

### F5 — S4 CLI `runtime_display.py` 的 `threading` 锁与 `asyncio.to_thread` 的串行化语义在 close 路径可能产生微妙的清理顺序问题

- **位置**: plan S4 §8（Exact changes/dataflow 第 8 条）、S4 §9（blocking renderer deterministic test）
- **问题类型**: 并发恢复风险
- **当前写法**: "RuntimeDisplayController拥有threading串行锁和typed activity/thinking recorder入口；CLI传controller入口给Service，不再传raw renderer method。toggle、finish、cancel/local-exit render、close也经asyncio.to_thread和同一锁串行化；caller finally仍是renderer lifecycle owner。"
- **反例/失败场景**: close 操作经 `asyncio.to_thread` 发送到 thread 执行域，但 caller finally 在 main event loop 中执行。若 close 的 thread job 尚未完成，caller finally 已经尝试清理 renderer 资源（例如关闭 terminal、释放 file handle），两个执行域可能竞争同一 renderer 资源。`threading` 锁只保护 controller 入口，不保护 renderer 的内部状态。
- **为什么有问题**: plan 把 renderer lifecycle owner 声明为 "caller finally"，但同时把 renderer 操作（包括 close）推入 thread 执行域。这两个声明之间存在生命周期时序竞争：finally 在 main loop 执行，thread close 可能尚未完成。
- **直接证据**: plan S4.8 "caller finally仍是renderer lifecycle owner" + plan S4.8 "close也经asyncio.to_thread和同一锁串行化"
- **影响**: renderer close 与 caller finally cleanup 的竞争可能导致 `RuntimeError`、丢失最后 renderer 输出、或资源泄漏（非 Host reservation 泄漏，而是 CLI 进程级资源）
- **建议改法和验证点**: 明确 close 的同步点：caller finally 必须先 `await` controller 的 close 完成（即 await 最后一次 `asyncio.to_thread` job），再清理 renderer 本地资源。或改为 controller close 是 async 方法，内部先通过 thread job 清理 renderer，返回后 caller finally 再清理本地资源。测试验证：close 过程中的异常不阻止 caller finally 执行。
- **修复风险**: 低 — 明确同步点，不改变 contract
- **严重程度**: 低

### F6 — plan §3.3 non-goal "不让慢 watcher对 Agent/Engine/promotion/其它 watcher形成被动 backpressure" 与 S4 callback thread 阻塞的现实差距

- **位置**: plan §3.3 第 4 条、plan §4.7 callback 执行域描述、S4 §9
- **问题类型**: 契约缺失
- **当前写法**: "不让慢 watcher对 Agent/Engine/promotion/其它 watcher形成被动 backpressure；Host publish只允许 non-blocking offer与当前订阅隔离" — 这是 Host 侧承诺。但 S4 的 callback 执行域设计让 Service consumer 在 callback 完成前不调用下一次 `anext()`，因此慢 callback 会反压 Service consumer，但不反压 Host publisher。
- **反例/失败场景**: 如果 reader 把 "不让慢 watcher backpressure" 理解为 "整个系统端到端无 backpressure"，会认为 S4 callback thread 阻塞是 plan 矛盾。实际上 plan 的 contract 边界是清晰的：Host publish 不等待 consumer，但 consumer 内部的 callback 执行不归 Host 管。
- **为什么有问题**: plan §3.3 的 non-goal 表述是 Host 视角的 "慢 watcher 不反压 Agent/Engine/promotion"，但没有显式声明 Service consumer 自身可能因 callback 而减速。虽然这在 owner boundary 上是正确的，但 non-goal 的措辞可能让 implementation agent 误以为需要保证端到端无阻塞。
- **直接证据**: plan §3.3.4 + plan S4.7 "consumer await其完成" + Host design.md:358 "同一 event loop 上的阻塞 callback、CPU 饥饿或同步 O(N) fanout 成本不属于物理隔离承诺"
- **影响**: 低 — implementation agent 可能过度设计 callback 超时/队列/丢弃机制
- **建议改法和验证点**: 在 §3.3 non-goal 中增加一条显式说明："Service consumer 内部 callback 执行时间不受 Host 治理；慢 callback 只减速当前 consumer（可能导致该 consumer 的 mailbox overflow），不反压 Host publish、Agent/Engine 或其它 watcher。"
- **修复风险**: 低 — 只补充说明
- **严重程度**: 低

## Slice Sequencing Review

4 slices 的语义闭环与依赖关系验证：

- **S1 → S2**: S2 依赖 S1 的 public iterator、resource state 和 single-pop mailbox。依赖方向正确，S1 的 iterator/policy/mailbox 是 S2 causal merge 的前提。
- **S2 → S3**: S3 依赖 S2 的 delivery watermark readiness 与 causal merge。S3 的 terminal coordinator 使用 S2 的 local notice hook。依赖方向正确。
- **S3 → S4**: S4 依赖 S1-S3 全部完成。S4 的 sole consumer 需要完整的 Host delivery contract。依赖方向正确。

4 slices 的理由（§6）：S2（data-plane correctness）与 S3（control-plane correctness）有独立 deterministic barrier 和失败风险。合并 S2+S3 会将 "跨 opener 只靠 DB fence" 和 "同 opener low-latency/promotion" 混淆。合并 S3+S4 将失去独立 static manifest/runtime fake 证明 Host producer 闭集的能力。**理由成立**。符合 control doc 中超过 3 slices 的显式说明要求。

每 slice 的 allowed modules、输入/输出、stop conditions、验证矩阵均达到 code-generation-ready 级别。

### Durable/transient merge（§4.5）

**验证通过。** 反例：catch-up 期间 caller cancel → plan S2 Failure/release paths "保留retained accounting到cleanup" 覆盖。

### Service observation（§4.7）

容量为一，generation-tagged，5 类 disposition 各有固定处理路径。cleanup 顺序：先 stop consumer、再 aclose、primary 不被 close failure 覆盖。

**验证通过。** 反例：callback + close double failure → plan §4.7 fixed disposition "最多一次去敏 WATCHER_DIAGNOSTIC" 覆盖。
