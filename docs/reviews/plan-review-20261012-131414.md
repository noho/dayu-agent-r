## Findings

### 1-未修复-[中]-事实获取/解析失败的爆炸半径未裁决：单条非目标 FY 候选失败会中止整个 ticker 的 discovery

- **位置**: plan 第 12/56/74/110/118/120 行（D1 失败契约、测试断言 1/3）；`dayu/fins/pipelines/cn_download_protocols.py:55-63`（协议契约）；workflow discovery 调用点 `dayu/fins/pipelines/cn_download_workflow.py:267-273`。
- **问题类型**: 契约缺失 / 目标漂移（失败语义）/ 测试缺口。
- **当前写法**: “原文解析错误映射 `FinsDownloadProviderError(..., retryable=False, safe_message='巨潮年度报告原文无法确认财年或全文性质')`……未解析财年时尚不能安全分配 filing ID，因此本轮 discovery 失败，既有来源不改写。”（plan:74）且测试要求空/损坏/加密/无标签/多财年/混合标签全部 fail closed（plan:118），风险表把未覆盖失败归入“assigned to later work unit / 未来未知 fail closed”（plan:174）。
- **反例/失败场景**: 任一新窗口公司的某条 FY 候选（该候选甚至不参与最终选择，例如落选摘要）封面是扫描件、标签缺失或含混合 year/kind。facts 解析抛 `ValueError` → 映射为不可重试 provider 错误 → `list_report_candidates` 抛出 → `run_cn_download_stream_impl` 在 line 267 直接失败，该 ticker 本次 **连 H1/Q、其它年份、已完整来源的增量维护全部不执行**。当前生产代码下同一公司不会因为“某条候选 PDF 封面不可解析”而整体失败（旧行为最多是年投影有瑕疵仍可下载；PDF 级失败只影响被选中的 candidate）。协议本身明示“HEAD/GET 失败、PDF magic bytes 校验失败等候选层失败仅影响该 candidate，不能让整个 ticker 流程崩”（`cn_download_protocols.py:58-59`），plan 未声明此契约对 CN FY facts 的修订。
- **为什么有问题**: 目标确认只要求“无年份的财年识别、全文/摘要选择、跨年去重与已有摘要阻挡问题，仅在证实其对本目标必要时纳入”，plan 也确实把这些失败面判给后续 work unit；但 plan 选择的失败行为（fail closed）被放大到 ticker 级且未显式决策/未测试，等于把通用系统的可用性边界变成了本 slice 的隐含非目标外溢；plan 自己的测试断言 3 只覆盖 HTTP owner 级 typed 失败，没有覆盖“facts 失败时公共工作流的行为”。
- **直接证据**: plan:74“本轮 discovery 失败”；plan:118 列出会被判 fail closed 的输入类；`cn_download_workflow.py:246-273`（discovery 异常在 try 内无候选级 catch）；`cn_download_protocols.py:58-59` 协议契约；证据侧 13 份封面中有 8 份存在重复标签（页眉+封面），说明解析对版式敏感是现实常态（`pypdf-cover-probe.json`）。
- **影响**: 对存在任一不可解析 FY 候选的公司，公共 CLI 从“可能年份不精确但可下载”退化为“整公司不可下载”，且无逃生门（非 overwrite/rebuild、无 bypass）；故障本身安全（不改写既有来源），但用户可见且不可恢复直到代码变更；验收（只跑 601225）无法暴露。
- **建议改法和验证点**: 由总控在实施前明确裁决其中一种：(a) facts 失败限于该候选：从 selection 排除并保留 typed/可观察的失败记录（该 FY 若因此无候选，则表现为 missing 或 uncertain，而不是全 ticker 失败）；或 (b) 维持 ticker 级 fail closed，但同步修订协议 docstring 的候选级隔离契约、在 plan 与 README 写明爆炸半径，并补一条端到端边界测试（引用真实 raw + 一个受控损坏封面 fixture，断言 typed 错误、安全文案、既有来源零改写、无半成品）。无论哪种，需在验收 artifact 中可观察该失败而非沉默。
- **修复风险（低/中/高）**: 中（(a) 需要定义候选排除的对外语义；(b) 只需文档+测试）。
- **严重程度（低/中/高/严重）**: 中。

### 2-未修复-[中]-D3 新身份规则与既有 repair/preflight 契约的交互未定义：legacy 财期槽损坏占位者会让整个增量运行硬失败

- **位置**: plan 第 25/96-98/105-107/110 行（D3 规则与“沿用原预检/修复合同”“损坏源 repair 退化=blocker”）；`dayu/fins/pipelines/cn_download_workflow.py:284-296`（accepted set 生成与 preflight）；`dayu/fins/storage/source_integrity.py:331-343`；identity 规则 plan:86-92。
- **问题类型**: 状态机漏洞 / 契约缺失 / 测试缺口。
- **当前写法**: “REPAIR_REQUIRED / UNSAFE：继续原预检与修复合同；facts 本地复用不能把损坏源当完整；unsafe 不发成功。”（plan:107）D3 之后，原财期槽的摘要/旧来源只要与新候选 source_id 不同，就不再是任何 accepted candidate 解析出的 document_id（全文改走 sha1 来源 ID）。
- **反例/失败场景**: 某 base 的 FY2021 周期槽位存有 legacy 摘要（source_id=1213161682），且该 source 因声明文件缺失/大小不符处于 `REPAIR_REQUIRED`。旧代码：摘要即 FY2021 选中候选 → accepted 包含该 document_id → `SelectedSourceRepairRequired` → 先修复该 source。新代码：facts 判摘要并从 selection 排除、全文取得新 sha1 source ID，损坏摘要既不在 accepted 也不在 rejected → `classify_source_integrity_preflight` 抛 `SourceIntegrityPreflightError(UNSELECTED_REPAIR_REQUIRED)`，整个 ticker 运行失败（H1/Q 与其它年份也不下载）。若实现者试图把该 ID 塞进 accepted，修复 gate 也不会被执行到（没有任何 candidate 解析到该 ID），company meta 发布会被跳过、损坏源静默保留——同样不可接受。
- **为什么有问题**: plan 声称“沿用原预检/修复合同”，但“selected”的语义已被 D3 改变：旧合同假定“在编损坏源 = 本次会下载的源”；新身份规则使 legacy 占位者既非本次下载对象也不再被修复，落在 preflight 的硬失败分支。plan 的验收（clean base + COMPLETE 摘要 seed）不产生 REPAIR_REQUIRED，测试清单只保留“选中损坏修复”boundary case，没有覆盖“unselected legacy 占位损坏源”。这与 plan 自列的 blocker“损坏源 repair 退化”直接相关，却无裁决。
- **直接证据**: `source_integrity.py:331-343`（未选中修复目标 → `UNSELECTED_REPAIR_REQUIRED`；加入 rejected 则 → `SELECTED_REJECTED_REPAIR_REQUIRED`，均硬失败）；`cn_download_workflow.py:290-305`（accepted/repair 排序）、`425-478`（repair gate 只有命中 repair_document_id 的 candidate 才推进）；D3 规则 2/3（plan:89-90）使全文不再映射到旧摘要 ID；seeded 证据只覆盖 COMPLETE 摘要（`seeded-owner-replay.json` integrity=complete）。
- **影响**: 升级用户在存在损坏 legacy 年度来源时，本修复把“普通增量自愈”变成“公共 CLI 硬失败”，且现有交付物无法发现该回归；实施 Agent 若顺带发明缓解逻辑还可能超出 owner 边界。
- **建议改法和验证点**: 在 plan 内显式裁决并落到 owner（workflow/preflight）：(a) 定义 legacy 财期槽占位者在 D3 下的修复/跳过策略（例如：当占位者与某财期槽同 key 且其 source 已被 facts 判为不适格/被替换时，将“重新获取旧来源”作为一次显式修复目标，或明确将其归入不修复集合并且不接受其阻塞），或 (b) 声明“unselected legacy 损坏年度来源导致 preflight 失败”为预期行为，并在 S1 边界测试 + README 固化（含错误可读文案与用户可执行路径，如 rebuild 是否适用需在该处说明）。验证点：真实隔离 Fs 构造 legacy 损坏摘要 + 正确全文候选，断言所选策略的确定行为（修复成功或 typed 失败且来源零改写），并断言同一场景下 COMPLETE 摘要仍成功保留全文。
- **修复风险（低/中/高）**: 中（涉及 preflight/repair 语义，必须最小化且不扩新框架）。
- **严重程度（低/中/高）**: 中。

- **影响**: 轻微成本回归（每轮最多 4 次额外 GET，其中一条为全文）被写成“可能”，验收口径不可比较；未来误把该行为当回归处理或反之。

- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高）**: 低。
