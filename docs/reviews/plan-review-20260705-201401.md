## Material Findings

### F1-未修复-中-切片数据流不完整

- **位置**: S1 Exact changes / `_tooling_options_from_discovery` 数据流
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: plan S1 写 "在 Fins wait adapter module 增加最小 builder，例如 `build_fins_wait_poll_adapter_registry(runtime, tool_names) -> WaitPollAdapterRegistry`"，以及 "`dayu/service/host_assembly.py` 为启用的 Fins awaiting providers 同时设置 `wait_poll_adapter_registry`"
- **反例/失败场景**: `_tooling_options_from_discovery` 当前签名接收 `fins_awaiting_runtime: FinsObservationRuntime | None`，其类型是 `FinsObservationRuntime`（协议），但 `FinsIngestionWaitPollAdapter.__init__` 也需要 `runtime: FinsObservationRuntime`。plan 在 S1 的 "Exact changes" 中没有显式写出 `_tooling_options_from_discovery` 中调用 `build_fins_wait_poll_adapter_registry` 的完整调用链，implementation agent 需要自行推断：是用 `fins_awaiting_runtime` 参数直接传入 builder，还是需要做类型收窄（当前参数是 `FinsObservationRuntime | None`，而 builder 需要非 None runtime）。此外，当前 `_tooling_options_from_discovery` 对 `wait_adapter_registry` 和 `wait_activation_registry` 的构造有明确的 guard（先检查 `fins_awaiting_runtime is not None` 且 `isinstance(fins_awaiting_runtime, FinsIngestionRuntime)`），但 plan 没有说明 `wait_poll_adapter_registry` 的构造是否需要相同的 runtime type guard。
- **为什么有问题**: implementation agent 在缺乏显式数据流描述时，可能在 `None` guard、类型收窄或 builder 调用位置上产生漂移，导致 S1 的 `tests/service/test_host_assembly.py` 测试无法覆盖所有边界（例如 `fins_awaiting_runtime` 为 `None` 时 poll registry 应为 `None`）。
- **直接证据**: `dayu/service/host_assembly.py:1687-1742` 中 `_tooling_options_from_discovery` 的实现；`dayu/fins/ingestion/wait_adapter.py:108-118` 中 `FinsIngestionWaitPollAdapter.__init__` 签名。
- **影响**: 实施 Agent 跑偏 / 后续返工（implementation report 可能标为 blocked 或 S1 测试覆盖不足）。
- **建议改法和验证点**: 在 S1 "Exact changes" 中显式补充 `_tooling_options_from_discovery` 对 `wait_poll_adapter_registry` 的赋值逻辑：当 `fins_awaiting_runtime is not None` 且存在可绑定的 Fins awaiting 工具名时，调用 `build_fins_wait_poll_adapter_registry(runtime=fins_awaiting_runtime, tool_names=...)`；否则 `wait_poll_adapter_registry=None`。同步更新 S1 tests 中的断言项，覆盖 "Fins awaiting providers 启用时 `HostToolingOptions.wait_poll_adapter_registry` 非空" 和 "无 awaiting provider 时 poll registry 为 None"。
- **修复风险（低）**: 只需在 plan 中补充一句数据流说明，不影响 slice 边界。
- **严重程度（中）**:

### F2-未修复-中-deterministic poll adapter 状态管理未指定

- **位置**: S2 Exact changes — deterministic poll adapter 行为描述
- **问题类型**: 不可直接实施 / 测试缺口
- **当前写法**: plan S2 写 "poll adapter 通过 production `WaitPollAdapterRegistry` 注册，返回 `WaitPollNotReady` 后再返回 `WaitPollReady(ResolveWaitCompletedOutcome(...))`"
- **反例/失败场景**: `WaitPollAdapter.poll_wait(wait_record: WaitRecordRow) -> WaitPollResult` 是每次调用的无状态协议。deterministic adapter 需要跨多次 `poll_wait` 调用管理状态（"第 N 次调用返回 X"）。plan 没有指定：
  1. 状态载体（实例字段？闭包变量？模块级计数器？）
  2. 状态生命周期（adapter 实例是否在 smoke 全程存活？poller 是否可能在同一次 poll cycle 内多次调用 `poll_wait`？）
  3. 并发安全性（poller 内部是否对同一条 wait record 有重试/重入？）

  如果 implementation agent 使用简单的模块级计数器，且 poller 因 backoff/retry 逻辑在同一条 wait record 上多次调用 `poll_wait`，计数器可能在预期之前耗尽，导致 adapter 过早返回 ready（在测试观察到 WAITING 之前就完成 resolution）。
- **为什么有问题**: `WaitPollAdapter` 协议本身是无状态的；在协议边界内引入状态是测试专用的实现细节，但缺少状态管理规约会导致 implementation agent 做出不同选择，进而影响测试的稳定性和可重复性。
- **直接证据**: `dayu/host/wait_adapter.py:186-209` — `WaitPollAdapter` 协议定义，`poll_wait` 无状态约束；`dayu/host/wait_adapter.py:768` — `WaitPoller` 构造接受 `WaitPollAdapterRegistry`。
- **影响**: 实施 Agent 可能实现出在特定 poller timing 下 flaky 的 smoke / 测试不稳定。
- **建议改法和验证点**: plan S2 应在 "Exact changes" 中明确 deterministic adapter 的状态管理方式。推荐方案：adapter 实例持有 `_call_count: int = 0` 字段，`poll_wait` 内递增并在 count==1 时返回 not-ready、count>=2 时返回 ready。该 adapter 实例在 smoke 全程存活（与 `open_host` 生命周期一致）。同时建议 smoke 在断言 WAITING 之前先等待至少一次 activity callback 观察到 `EntrypointActivityStatus.WAITING`，再允许后续 poll 返回 ready。
- **修复风险（低）**: 只需在 plan 中补充 adapter 状态管理说明，不改变整体设计。
- **严重程度（中）**:

### F3-未修复-低-WAITING 观察与 poller resolution 竞态窗口

- **位置**: S2 Exact changes — live watcher WAITING 观察
- **问题类型**: 并发恢复风险
- **当前写法**: "在 `on_activity` 或并发 public polling 中观察 `EntrypointActivityStatus.WAITING` / `HostActivityStatus.WAITING`，并用 `host.get_run(accepted_run_id)` 断言曾进入 `RunStatus.WAITING`"
- **反例/失败场景**: 当前 `_wait_for_terminal`（`entrypoint_runtime.py:993-1049`）的轮询循环以 `poll_interval_seconds`（默认 0.05s）运行。在每次循环中，先 drain watcher queue（消费 HostEvent），再调用 `get_run` 检查 RunStatus。如果 poller 在第一次 `poll_wait`（返回 not-ready）和第二次 `poll_wait`（返回 ready）之间的间隔极短（deterministic adapter 无 I/O 延迟），可能的时序是：
  1. Run 进入 WAITING → Host 发出 WAITING activity event
  2. Poller 第一次 poll → not-ready
  3. Poller sleep（`poll_interval_seconds`）
  4. Poller 第二次 poll → ready → `resolve_wait` → Run 进入 terminal
  5. `_wait_for_terminal` 的 watcher drain 可能先收到 terminal event，再收到 WAITING activity event（取决于 HostEvent 的 event_sequence 顺序和 watcher queue 的到达顺序）

  关键问题：`_drain_available_watcher_items` 只消费当前 queue 中已到达的 item，如果 WAITING activity event 和 terminal event 都在 queue 中，drain 会先处理 WAITING（通过 `_emit_entrypoint_activity_from_host_event`），再命中 terminal。但 activity callback 去重逻辑（`seen_activity_dedupe_keys`）只在 `_emit_entrypoint_activity_from_host_event` 中生效——如果 WAITING activity 的 `event_sequence` 排在 terminal 之后，且 terminal event 先被 drain 到，则 `_terminal_result_from_live_event` 会直接返回 terminal result，不再继续 drain 后续的 WAITING activity。
- **为什么有问题**: plan 的 "曾进入" 语义依赖 `get_run(accepted_run_id).status == RunStatus.WAITING` 作为兜底，但这只能证明 Run 曾经处于 WAITING 状态（通过 durable status 查询），不能证明 live watcher 确实发出了 WAITING activity。如果 smoke 的核心验收目标是 "UI / Service 真实入口能观察 WAITING"，那么仅靠 `get_run` 回查是不够的——它没有验证 activity projection 路径。
- **直接证据**: `dayu/service/entrypoint_runtime.py:993-1049` — `_wait_for_terminal` 的 drain-then-poll 循环；`dayu/service/entrypoint_runtime.py:1068-1110` — `_drain_available_watcher_items` 的 queue.get_nowait() 逻辑。
- **影响**: smoke 可能通过 `get_run` 回查验证 "曾进入 WAITING"，但未能验证 live activity callback 确实发出了 WAITING activity。这削弱了 smoke 作为 "production-grade public workflow 验收" 的完整性。
- **建议改法和验证点**: 两种方案：(a) 在 smoke 中断言 `on_activity` callback 确实收到了 `EntrypointActivityStatus.WAITING` 的 activity（通过共享的 `asyncio.Event` 或收集列表），而不仅依赖 `get_run` 回查；(b) 让 deterministic adapter 在第一次 poll 和第二次 poll 之间引入可控延迟（如 `asyncio.Event.wait()`），由测试在观察到 WAITING activity 后再 set event 允许 poller 继续。
- **修复风险（低）**: 方案 (b) 需要在 adapter 和测试之间引入同步机制，但仍是 public contract 内操作。
- **严重程度（低）**:

## Optimal-Solution Review

- **poller vs callback**: 选择 production poller path 是正确的。callback endpoint 需要 `wait_id` 输入，当前 ordinary UI/Service public event/activity 不暴露 wait id（代码证据：`dayu/service/wait_callback_endpoint.py` 的 callback envelope 接收 `wait_id`，但 `HostEvent` 和 `EntrypointActivity` 均不含 wait id 字段）。强行从 durable row 拿 wait id 违反本 WU 红线。**通过**。
- **typed override vs runtime config**: S1 选择 typed `ServiceAssemblyOverrides.wait_poller_policy` 而非 runtime config schema 是合理的——当前目标是 smoke/public workflow validation，config 产品化可后续独立处理。**通过**。

## Open Questions

1. **FinsIngestionWaitPollAdapter 的 `poll_wait` 接收 `WaitRecordRow`（durable 类型）** — 该类型来自 `dayu/host/durable/state`，属于 Host 内部模块。S2 的 deterministic test adapter 如果放在 `tests/service/awaiting_smoke_support.py`，是否需要导入 `WaitRecordRow`？若需要，该导入是否违反 "smoke 只能使用 public contracts" 的约束？
   - **初步判断**: `WaitPollAdapter` 是 Host public protocol（从 `dayu/host.wait_adapter` 导出），其 `poll_wait` 签名包含 `WaitRecordRow` 是协议的一部分。test adapter 实现该协议时必然需要导入 `WaitRecordRow`。这不违反 public contract 约束——adapter 是协议实现者，不是 durable store reader。但 plan 应在 S2 中明确这一点，避免 implementation agent 产生困惑。

2. **是否需要为 deterministic adapter 单独建一个 `WaitPollAdapter` 协议测试实现模块** — 当前 plan 允许新增 `tests/service/awaiting_smoke_support.py`，但未明确该模块是否可以导入 `dayu.host.wait_adapter` 中的 `WaitPollNotReady`、`WaitPollReady` 等协议类型。建议 plan 明确：support 模块可以导入 `dayu.host.wait_adapter` 中的 public protocol 类型（`WaitPollAdapter`, `WaitPollResult`, `WaitPollNotReady`, `WaitPollReady` 等），但不得导入 `dayu/host/durable/` 下的任何模块。
