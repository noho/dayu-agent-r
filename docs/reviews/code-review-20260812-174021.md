## Findings

### 1. 未修复-低-`_build_pending_assets` 中重复计算 Docling SHA-256

- **入口/函数**: `DoclingUploadService._build_pending_assets`
- **文件(行号)**: `dayu/fins/pipelines/docling_upload_service.py:690`
- **输入场景**: 任何通过 `_build_pending_assets` 的上传文件转换
- **实际分支**: `DoclingConversionResult` 返回后，对 `conversion.json_bytes` 重新计算 SHA-256
- **预期行为**: `DoclingConversionResult` 已在构造时完成 `size` 与 `sha256` 校验（`docling_process_converter.py:112-124`），消费者应直接使用 `conversion.sha256`，而非从 `json_bytes` 重算
- **实际行为**: `docling_sha256 = hashlib.sha256(docling_data).hexdigest()` 在已校验的 bytes 上重复计算 SHA-256
- **直接证据**:
  - `DoclingConversionResult.__post_init__` (line 112-124) 在构造时已校验 `sha256 == hashlib.sha256(json_bytes).hexdigest()`
  - `_build_pending_assets` line 688-690: 从 `conversion.json_bytes` 获取 `docling_data`，然后 line 690 重新计算 `docling_sha256`
  - Plan §11.2: "不各自重算 JSON、digest 或 cancel status"
- **影响**: 轻微性能浪费（重复 SHA-256 计算），不导致语义错误。非 correctness bug
- **建议改法和验证点**: 使用 `conversion.sha256` 替代 `hashlib.sha256(docling_data).hexdigest()`；验证 `conversion.size` 与 `len(docling_data)` 一致（已在 Result 构造时校验）
- **修复风险（低）**: 仅替换一行表达式，`DoclingConversionResult` contract 已承诺 SHA-256 一致性
- **严重程度（低）**:

### 2. 未修复-信息-`_upload_completed_progress_type` 对 cancelled summary 仍返回 completed

- **入口/函数**: `_upload_completed_progress_type` → `_produce_direct_upload` / `_run_upload_job`
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:6655-6670`（定义），`3247-3253`（direct 调用点），`3693-3698`（durable 调用点）
- **输入场景**: runner 返回 `status="cancelled"` 的 `FinsUploadResultSummary`（S2 新增路径：interruptible converter 使转换中取消成为可达路径）
- **实际分支**: `_upload_completed_progress_type` 只检查 `status == "failed"`，对 cancelled 返回 `_PROGRESS_UPLOAD_COMPLETED`
- **预期行为**: cancelled summary 不应产生 `upload.completed` progress；应产生 cancelled progress 或不产生 completed progress
- **实际行为**: cancelled summary 先投影 `upload.completed` progress，再由后续 `cancellation_checker()` 检查尝试修正（direct 路径 line 3254）或读 job store 修正（durable 路径 line 3700-3703）。修正依赖外部状态，非 summary 自身语义
- **直接证据**:
  - `_upload_completed_progress_type` (line 6655-6670): 仅两个分支 — `failed` → `completed_with_failures`，其他 → `completed`
  - `_produce_direct_upload` (line 3247-3256): 先 emit `_upload_completed_progress_type(summary)`，后 `if context.cancellation_checker()` → cancelled
  - `_run_upload_job` (line 3693-3703): 先 emit progress，后 `if latest.cancellation_requested` → save cancelled
  - Plan §2.1 将此定性为 owner 级缺陷，plan §10 将此修正分配至 S3
- **影响**: cancelled summary 产生短暂 `upload.completed` progress event，在 direct 路径被后续 cancel check 修正为 cancelled RESULT，在 durable 路径同样被 job store 终态覆盖。不影响 publication correctness（batch rollback 由 workflow 层保障），但 event 序列不符合 plan 预期
- **建议改法和验证点**: 此修正属于 plan §10 / Slice UF-FIX09-S3，不在 S2 scope。S3 实现时应：建立 `FinsUploadTerminalDisposition` closed enum；`_produce_direct_upload` 先读 typed disposition，cancelled 不投影 completed；`_run_upload_job` 同理
- **修复风险（低，S3 专项）**:
- **严重程度（信息）**: 属于已知 S3 待修正项，非 S2 新引入缺陷。S2 使 cancelled summary 成为可达路径（之前 converter 不可中断），但终态修正由 S3 负责

### 3. 未修复-信息-`_resolve_upload_status` 在 cn_pipeline.py 与 sec_upload_workflow.py 重复定义

- **入口/函数**: `_resolve_upload_status`
- **文件(行号)**: `dayu/fins/pipelines/cn_pipeline.py:1805-1820`，`dayu/fins/pipelines/sec_upload_workflow.py:515-530`
- **输入场景**: 上传结果状态映射（`"uploaded"` → `"ok"`）
- **实际分支**: 两个模块各自定义相同的函数
- **预期行为**: 单一真源映射；`"uploaded"` → `"ok"` 的语义应由单一 owner 定义
- **实际行为**: 两个独立但相同的函数，同步修改需跨两个模块
- **直接证据**: 两个函数的实现完全相同：`if upload_status == "uploaded": return "ok"; return upload_status`
- **影响**: 维护时可能仅修改一处导致漂移。当前不导致行为错误
- **建议改法和验证点**: plan §5 将 `uploaded` → `ok` 映射归给 workflow owner。当前 S2 实现中两个 pipeline 各自映射，可接受。计划中的 unified status mapping（plan §10.1）将在 S3 以 `FinsUploadTerminalDisposition` 形式统一
- **修复风险（低）**:
- **严重程度（信息）**: 非 S2 新引入，属于现有模式随 S2 call-site migration 自然显现
