## Findings

### 1-未修复-中-SEC/CN workflow 不执行 plan §6.2.1 要求的 authoritative recheck

- **入口/函数**: `sec_upload_workflow.run_upload_filing_stream` 与 `cn_pipeline.CnPipeline.upload_filing_stream`
- **文件(行号)**: `dayu/fins/pipelines/sec_upload_workflow.py:167-183`、`dayu/fins/pipelines/cn_pipeline.py:835-852`
- **输入场景**: 任何 filing upload 成功路径
- **实际分支**: runner 做 fresh recheck 后传 `action=fresh_request.resolved_action`；workflow 收到后重新调用 `resolve_upload_action(action, previous_meta)`，其中 `action` 已非 `None`，因此 `previous_meta` 对 action 解析无效。workflow 同时独立读取 `previous_meta` 供 `prepare_upload` 使用。
- **预期行为**: plan §6.2.1 要求 workflow "对 `preflight.request` 再调用同一 `validate_fins_upload_filing_request`，得到 `authoritative_request`；只允许 `authoritative_request.resolved_action/published_state/company_meta_decision` 驱动 prepare/stage/commit"。
- **实际行为**: workflow 不调用 `validate_fins_upload_filing_request`，不读取 `FilingUploadPublishedState`，不使用 `company_meta_decision`。action 通过 runner 参数传递等效，但 company decision 和 published state 未传递给 workflow。
- **直接证据**: `sec_upload_workflow.py:167-183` 只做 `resolve_upload_action(action, previous_meta)` 而非完整 validator 调用；`cn_pipeline.py:835-852` 同样模式。runner 在 `service_runtime.py:175-183` 做了 fresh recheck 但只传 `action` 和 `normalized_fiscal_period`。
- **影响**: 当前功能正确（action 通过 runner 传递等效；company freshness 由 `upsert_company_meta_for_upload` 独立保证），但 authority 分散在 runner 和 workflow 两处，与 plan 的 "workflow 持有 authoritative recheck" 设计意图不一致。未来修改可能引入 runner/workflow 状态不一致。
- **建议改法和验证点**: SEC/CN workflow 应接收 `ValidatedFinsUploadFilingRequest`（或至少 `FilingUploadPublishedState` + `UploadCompanyMetaDecision`），用 `fresh_request.resolved_action` 直接驱动，不再自行读 `previous_meta` 做 action 解析。或在实现文档中明确记录此 authority 划分是 deliberate deviation。
- **修复风险（低/中/高）**: 中 — 涉及 SEC/CN workflow 签名变更
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-低-company_meta_decision 计算但未用于 workflow staging

- **入口/函数**: `validate_fins_upload_filing_request` → `ValidatedFinsUploadFilingRequest.company_meta_decision`
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:978-996`、`dayu/fins/pipelines/sec_upload_workflow.py:231`、`dayu/fins/pipelines/cn_pipeline.py:900`
- **输入场景**: create/update filing upload with fresh or stale company meta
- **实际分支**: validator 计算 `UploadCompanyMetaDecision`（disposition=keep/skip/stage），runner 的 fresh recheck 也计算一个新 decision。但 SEC/CN workflow 调用旧 `upsert_company_meta_for_upload` 而非 `stage_upload_company_meta_decision`。
- **预期行为**: plan §6.5 要求 workflow 使用 authoritative `company_meta_decision` stage 到同一 batch。
- **实际行为**: `upsert_company_meta_for_upload` 内部重新做 freshness 判断，行为等效但绕过了 pre-computed decision。
- **直接证据**: `sec_upload_workflow.py:231` 调用 `upsert_company_meta_for_upload`；`upload_company_meta.py:87-112` 定义了 `stage_upload_company_meta_decision` 但未被 workflow 调用。
- **影响**: freshness 判断逻辑在 `resolve_upload_company_meta_decision` 和 `_existing_company_meta_is_fresh`（被 `upsert_company_meta_for_upload` 内部调用）两处执行。当前行为等效，但违反 "同一 decision 从 validator 到 workflow 原样传递" 的 single source of truth 原则。
- **建议改法和验证点**: SEC/CN workflow 应调用 `stage_upload_company_meta_decision(repository, decision, batch)` 替代 `upsert_company_meta_for_upload`。需确保 `decision.disposition == "skip"` 时确实不写 company meta。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 3-未修复-低-prepare_upload 独立读取 previous_meta 接受 state 参数

- **入口/函数**: `DoclingUploadService.prepare_upload`
- **文件(行号)**: `dayu/fins/pipelines/docling_upload_service.py:287`
- **输入场景**: 任何非 delete filing upload
- **实际分支**: `prepare_upload` 内部调用 `self._safe_get_document_meta(normalized_ticker, document_id, source_kind)` 读取 `previous_meta`，与 runner/workflow 的独立读取构成第三处 state read。
- **预期行为**: plan §4 表格要求 "prepare_upload(previous_meta=...) 不再自行读取 state"。
- **实际行为**: 方法签名无 `previous_meta` 参数；内部自行读取。TOCTOU 窗口：runner 读 state → workflow 读 state → `prepare_upload` 读 state，三次读取可能看到不同版本。
- **直接证据**: `docling_upload_service.py:287` — `previous_meta = self._safe_get_document_meta(...)`。
- **影响**: 实际风险低 — `prepare_upload` 只产生 plan 不做 mutation；skip/fingerprint 判断在 `prepare_upload` 内部，使用最新 state 反而更准确。但与 plan 设计意图不一致。
- **建议改法和验证点**: 要么给 `prepare_upload` 增加 `previous_meta` 参数，要么在实现文档中记录此为 deliberate choice（`prepare_upload` 内部读取保证 fingerprint 判断基于最新 state）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 4-未修复-低-FileExistsError 映射到 STORAGE_IO 而非 RUNTIME

- **入口/函数**: `fins_upload_failure_from_exception`
- **文件(行号)**: `dayu/fins/upload_failure.py:128-133`
- **输入场景**: `prepare_upload` 在 `CREATE_TARGET_EXISTS` 且 `source_kind is FILING` 时抛出 `FileExistsError`
- **实际分支**: `FileExistsError` 是 `OSError` 子类，被 `isinstance(error, OSError)` 匹配，映射到 `FinsUploadFailureKind.STORAGE` / `FinsUploadFailureCode.STORAGE_IO`。
- **预期行为**: 这是 precondition 不满足，不是 storage I/O 错误。更合适的映射是 `RUNTIME` / `UNEXPECTED_RUNTIME` 或专用 code。
- **实际行为**: 用户看到 "上传产物读写失败，请稍后重试"，但实际问题是 "目标已存在"。
- **直接证据**: `upload_failure.py:128` — `isinstance(error, OSError)` 匹配 `FileExistsError`；`docling_upload_service.py:296-297` — `raise FileExistsError(...)`。
- **影响**: 正常流程不会触发（runner 验证已在 factory 前拒绝 `CREATE_TARGET_EXISTS`）。仅在 runner→workflow TOCTOU 竞争时触发。用户看到误导性错误消息。
- **建议改法和验证点**: 在 `fins_upload_failure_from_exception` 中把 `FileExistsError`/`FileNotFoundError` 作为 admissibility failure 单独处理，或在 `OSError` 分支前加 `isinstance(error, FileExistsError | FileNotFoundError)` 映射到 `RUNTIME`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
