### 1-已修复-高-`_append_worker_failure_if_needed` 在 `ToolRuntimeOwnerScope` 进入前调用 `_scope_appender()` 导致 worker 异常被吞

- **入口/函数**: `LocalRunHarness._run_to_store` -> `_append_worker_failure_if_needed`
- **文件(行号)**: `dayu/host/_run_harness.py:870-877` (调用点), `:1834` (`_scope_appender()` 调用), `:607-611` (durable 路径无 scope 时 raise RuntimeError)
- **输入场景**: `self.proxy.stream_engine_events()` (line 850) 在 `async with self._attempt_owner_scope()` (line 894) 进入前抛出非 `AttemptFencingError` 异常（例如网络错误、Engine 装配失败等）
- **实际分支**: `except Exception as exc` (line 870) 捕获异常后调用 `_append_worker_failure_if_needed` (line 872)，该方法内部调用 `self._scope_appender()` (line 1834)，`_scope_appender()` 在 durable 路径检测到 ContextVar 中无 active scope，抛出 `RuntimeError`
- **预期行为**: 应将 worker 异常正确记录为 Host-owned terminal `RUN_FAILED` RunEvent，使 RunStream 订阅方收到终态事件
- **实际行为**: 原始 worker 异常被 `RuntimeError` 覆盖，RunEvent 未写入，`_finish_attempt_if_durable` 通过外层 finally (line 1170) 仅推进 `host_attempts` 诊断态，但 EventLog 中无对应 terminal RunEvent；RunStream 订阅方在 background task 退出后收不到 terminal event，`get_run_result()` 返回 `None`
- **直接证据**:
  - line 850: `engine_events = self.proxy.stream_engine_events(...)` 在 owner scope 之前
  - line 870-877: `except Exception as exc` 调用 `_append_worker_failure_if_needed`
  - line 894: `async with self._attempt_owner_scope(current_active_attempt)` 在此之后才进入
  - line 1834: `_append_worker_failure_if_needed` 使用 `self._scope_appender()` 而非 `self._resolve_attempt_appender(active_attempt)`
  - line 607-611: `_scope_appender()` 在 durable 路径无 active ContextVar scope 时 `raise RuntimeError`
  - 对比第二个调用点 line 919：位于 `async with` 块内部，正常命中 ContextVar scope
- **影响**: worker 异常被静默吞掉，无 terminal RunEvent 写入 EventLog；RunStream 订阅方永远收不到终态；上层 Service 无法推导 RunResult
- **建议改法和验证点**:
  1. `_append_worker_failure_if_needed` 增加 `active_attempt: _ActiveAttempt | None` 参数
  2. 内部改用 `self._resolve_attempt_appender(active_attempt)` 替代 `self._scope_appender()`
  3. 或者将 `stream_engine_events()` 调用移到 `async with self._attempt_owner_scope()` 内部
  4. 验证：构造 `stream_engine_events()` 在 scope 之前抛异常的测试用例，确认 terminal RunEvent 正确写入
- **修复风险（低）**: 改动范围小，仅涉及一个 helper 签名和两个调用点
- **严重程度（高）**: worker 异常被吞、RunStream 无终态、上层无法感知 Run 失败

### 3-已修复-中-`_handle_owner_lost` 在 `append_terminal_and_close` 抛出非 `AttemptFencingError` 异常时未关闭 `lease_exit_stack`

- **入口/函数**: `LocalRunHarness._handle_owner_lost`
- **文件(行号)**: `dayu/host/_run_harness.py:1349-1388`
- **输入场景**: `supervisor.append_terminal_and_close` (line 1350) 抛出 `sqlite3.DatabaseError`（非 `AttemptFencingError`），例如磁盘 I/O 错误、DB 损坏
- **实际分支**: 异常传播经过 `except AttemptFencingError` (line 1356) 未被捕获，也跳过 line 1379 的 `lease_exit_stack.aclose()`；调用方 (line 860-866) 的 finally 设置 `current_active_attempt = None`，外层 finally (line 1170) 因 `current_active_attempt is None` 不调用 `_finish_attempt_if_durable`
- **预期行为**: `lease_exit_stack` 仍应在异常传播前关闭，确保 renew loop 停止
- **实际行为**: `lease_exit_stack` 永不关闭，renew loop 作为后台 asyncio task 继续运行直到进程退出
- **直接证据**:
  - line 1350: `link = await supervisor.append_terminal_and_close(...)`
  - line 1356: `except AttemptFencingError as fence_exc:` — 仅捕获 AttemptFencingError
  - line 1379: `await active_attempt.lease_exit_stack.aclose()` — 仅在 CAS hit 路径执行
  - line 860-866: 调用方 finally 设 `current_active_attempt = None` 阻止外层 finally 补关
- **影响**: renew loop 泄漏为孤儿 task；在灾难性 DB 错误场景下（极低概率），进程无法干净清理
- **建议改法和验证点**: 将 `lease_exit_stack.aclose()` 移到 try/finally 中，或在 `except AttemptFencingError` 之外增加通用 except 做 `aclose()` 后 re-raise
- **修复风险（低）**: 仅在灾难性 DB 错误路径触发
- **严重程度（中）**: 极低触发概率，但确为资源泄漏

### 4-已修复-中-`_fetch_more` 中 cursor 记录从内存移除先于 EventLog 规范事实追加（root-cause fix: pure build + deferred commit）

- **入口/函数**: `InMemoryToolRuntime._fetch_more`
- **文件(行号)**: `dayu/host/_tool_runtime.py` — `_build_cursor_creation` / `_commit_cursor_creation` / `_build_cursor_from_record` / `_fetch_more`
- **输入场景**: `_fetch_more` 执行期间 owner 被 fencing（lease 过期或被其他进程替换），EventLog append 抛 `AttemptFencingError`
- **根因**: 原实现 `_store_cursor_from_record` → `_create_cursor` 立即写入 `_records_by_cursor` / `_cursor_by_fingerprint` 内存 maps，然后才做 EventLog append。内存变更与 EventLog 事实之间无原子性保证。
- **修复方案**: 将 cursor 创建拆为纯构建（`_build_cursor_creation`）+ 延迟提交（`_commit_cursor_creation`）。`_fetch_more` 新流程：
  1. 纯构建 next cursor（不写入内存 maps，无副作用）
  2. append COMPLETED fact
  3. append ISSUED fact（如有 next cursor）
  4. 所有 append 成功后：remove old cursor + commit next cursor
  5. 任何 append 失败：内存 maps 从未变更，无需回滚
- **直接证据**:
  - `_build_cursor_creation`: 纯函数，生成 cursor token / fingerprint / scope / record / issued_event，不写 maps
  - `_commit_cursor_creation`: 仅将 `_CursorCreation` 写入 `_records_by_cursor` / `_cursor_by_fingerprint`
  - `_fetch_more`: `_build_cursor_from_record` → append COMPLETED → append ISSUED → `_remove_cursor` + `_commit_cursor_creation`
- **影响**: fencing 发生时内存 maps 不会被部分修改，old cursor 始终可重新 fetch
- **修复风险（低）**: 纯内部重构，接口不变，3 个新测试覆盖 completed-fencing / issued-fencing / success-path
- **严重程度（中）**: 仅在 fencing 恰在 cursor 操作期间触发时命中，但有数据一致性问题
- **已知 residual risk**: EventLog multi-fact append 非原子——若 COMPLETED append 成功但 ISSUED append 失败，EventLog 中有 COMPLETED 事实但无 ISSUED 事实（partial fact）。此为 EventLog 架构层面限制，非 `_fetch_more` 逻辑 bug。

### 5-已修复-低-`_ATTEMPT_TERMINAL_STATES` 将 fencing 终态判断与 atomic close 有效状态混用同一集合

## Open Questions

1. `_fetch_more` 的多次独立 EventLog append（REQUESTED、COMPLETED、CURSOR_ISSUED）是否需要包裹在外层事务中以保证原子性？当前设计每次 append 是独立 `BEGIN IMMEDIATE`，fencing 可能发生在任意两次之间，导致 EventLog 中出现不完整的事实序列。是否需要在 ToolRuntime 层引入 "fetch_more 事务" 概念？

2. Cursor 记录为纯内存存储（`_records_by_cursor` / `_cursor_by_fingerprint` 字典），跨进程不可见。当进程被 fencing 后恢复进程接管时，进行中的 fetch_more cursor 全部丢失。这是否为 P8 阶段的已知设计限制？是否有计划将 cursor 状态持久化到 `host_cursors` 表？

3. 测试覆盖中缺少以下 adversarial 场景的验证：lease 在长事务内过期、owner 在 context compact 期间丢失 lease、asyncio 取消在 lease acquire 事务中间。这些是已知不覆盖的 gap 还是有明确的后续阶段计划（P8-Sx）？
