## Adversarial Re-review

### 1. 共享 converter cancel 线性化

**审查路径**: `DoclingUploadService.prepare_upload` → `_build_pending_assets` → `DoclingConverter.convert_to_json_bytes`

- `_build_pending_assets` 在每个文件迭代前检查 `_is_cancelled(cancellation)`，若已取消则 break。
- 若 converter 抛出 `DoclingConversionCancelledError`，caller 捕获并返回 cancelled plan（`docling_upload_service.py:272-281`）。
- `prepare_upload` 在 `_build_pending_assets` 返回后再做一次 `_is_cancelled` 检查。
- 三种取消入口（循环前、converter 内、循环后）均收敛为 cancelled plan，不创建 document batch。

**结论**: 正确。测试 `test_prepare_maps_shared_converter_cancel_without_starting_publication` 覆盖 converter cancel 路径。

### 2. commit ownership transfer 线性化

**审查路径**: `commit_prepared_upload_batch` → `publish_prepared_upload` → `_is_cancelled` → `commit_batch`

- `commit_prepared_upload_batch` 是 publication lifecycle 唯一 owner。
- `publish_prepared_upload` 内 `_do_write_upload` 在写入每个 asset 前、写入 source meta 前、写入后均检查 `_is_cancelled`。
- `publish_prepared_upload` 返回非 cancelled result 后，`commit_prepared_upload_batch` 在 `commit_batch` 前做最后一次 `_is_cancelled` 线性化检查。
- `batch_terminal_started` 标志确保 `commit_batch` 开始后不 rollback。
- `finally` 块用 `_rollback_precommit_upload_batch` 恰好一次 rollback precommit 异常。

**结论**: 正确。测试 `test_commit_winner_ignores_cancel_after_ownership_transfer` 用 `_CommitBarrierBatchingRepository` 验证 ownership transfer 后 cancel 不触发读取/rollback/结果改写。

### 3. `_RuntimeJobCancellationChecker` 线程安全

**审查路径**: `ingestion_runtime.py:1163-1240`

- 旧版本 `@dataclass(frozen=True)` → 新版本 `@dataclass`（需添加 `_lock`/`_cancel_reason`/`_requested_at` 可变字段）。
- 所有对 `_cancel_reason`/`_requested_at` 的读写均在 `with self._lock:` 下。
- `is_cancelled` 方法：首次检测到取消时设置 `_cancel_reason`/`_requested_at`。重复调用时 `_cancel_reason is not None` 短路返回，不再读取 durable store。
- `cancel_reason`/`requested_at` 方法：先调用 `is_cancelled()` 确保值已初始化，再在锁下返回。
- `job_store`/`job_id` 字段在构造后不再修改，无线程安全问题。
- 双重锁获取（`is_cancelled` 内部 + `cancel_reason`/`requested_at` 外部）不会死锁——Python `Lock` 不可重入，但两段临界区不嵌套。

**结论**: 正确。测试 `test_durable_checker_freezes_first_persisted_cancellation_record` 覆盖首次 cancelling record 冻结语义。

### 4. `_DirectCancellationChecker` 外部 token 传播

**审查路径**: `ingestion_runtime.py:1440-1495`

- `is_cancelled` 观察外部 token，首次取消时调用 `self.cancellation_state.request_cancel(reason=..., requested_at=...)`。
- `cancellation_token.cancel_reason()` 返回 `None` 时使用 `_DIRECT_CANCELLATION_REASON` fallback——外部 token 已取消但未提供 reason 是安全的默认行为。
- `cancellation_token.requested_at()` 返回 `None` 时 `request_cancel` 使用 `datetime.now(timezone.utc)` fallback。
- `_DirectStreamCancellationState.request_cancel` 在锁下设置 `_cancel_reason`/`_requested_at`，首次生效时返回 `True`。

**结论**: 正确。测试 `test_direct_checker_freezes_external_reason_and_time_across_threads` 覆盖跨线程传播。

### 5. `_canonical_cancellation` 类型守卫

**审查路径**: `cn_download_filing_workflow.py:886-905`

- `cancel_checker is None` → 返回 `None`（无取消源）。
- `not isinstance(cancel_checker, CancellationToken)` → `TypeError`（拒绝纯 callable）。
- 否则原样返回 `cancel_checker`（保留 canonical identity）。
- 替代旧的 `_required_cancellation_checker`/`_never_cancelled`；不再有 fallback callable。

**结论**: 正确。下载路径的类型安全由 workflow 边界 `isinstance` 守卫保证。
