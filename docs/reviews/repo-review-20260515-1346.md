### 003-[中]-dispatch drain_loop 空队列提前退出导致 wakeup 丢失

- **入口/函数**: `HostDispatchScheduler._drain_loop`
- **文件(行号)**: `dayu/host/dispatch.py` (451-465)
- **输入场景**: dispatch scheduler 后台 drain 循环运行中，队列暂时为空但 sleep 期间有新 record 入队
- **实际分支**: 第一次 `self._queue.empty()` 为 True -> sleep -> 第二次 `self._queue.empty()` 为 True -> return 退出循环
- **预期行为**: drain loop 应持续运行直到 scheduler 关闭，或至少确保所有已入队的 record 都被处理
- **实际行为**: 在 sleep 期间有新 record 入队时，第二次 empty check 可能仍为 True（取决于 asyncio 调度时序），导致循环提前退出。下一次 `wake_dispatch` 调用会重新创建 drain task，但在两次 wake 之间的 record 会被延迟处理
- **直接证据**:
  ```python
  # dispatch.py:451-465
  async def _drain_loop(self) -> None:
      while not self._closed:
          if self._queue.empty():
              await asyncio.sleep(
                  self._local_execution.dispatch_poll_interval_seconds
              )
              if self._queue.empty():
                  return  # <-- 提前退出
          await self.drain_once()
  ```
- **影响**: dispatch 延迟增加。在低频 wake_dispatch 场景下，record 可能等待一个完整 poll interval + 下一次 wake 才被处理
- **建议改法和验证点**: 移除提前 return 逻辑，改为 `continue`；或在 sleep 后直接调用 `drain_once`（不检查 empty）。验证：构造 sleep 期间入队的场景，确认 record 不被延迟
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 004-[中]-lane._release_token 在 asyncio.shield CancelledError 后内存状态不一致

- **入口/函数**: `LaneController._release_token`
- **文件(行号)**: `dayu/runtime/lane.py` (693-698)
- **输入场景**: 调用方在 heartbeat loop 正在执行 `token.refresh()` 时发起 `token.release()`，且此时外层 task 被 cancel
- **实际分支**: `asyncio.shield(release_task)` 本身被外层 cancel 时抛出 `CancelledError`，但 `release_task`（内部 `_release_claim_sync`）继续在后台运行；`token.released = True` 和 `_held_tokens.pop` 均未执行
- **预期行为**: release 操作要么成功完成并清理内存状态，要么抛出异常且内存状态一致
- **实际行为**: `CancelledError` 传播后，token 仍在 `_held_tokens` 中，`token.released` 仍为 `False`。后台 release_task 可能随后成功删除 DB row，但内存状态未同步
- **直接证据**:
  ```python
  # lane.py:693-698
  release_task = asyncio.create_task(
      asyncio.to_thread(self._release_claim_sync, token.name, token.claim_id)
  )
  await asyncio.shield(release_task)  # CancelledError here skips lines below
  token.released = True               # never reached
  self._held_tokens.pop(...)           # never reached
  self._wake_waiters()                 # never reached
  ```
- **影响**: 内存状态与 DB 状态不一致。heartbeat loop 的 `_mark_token_lost` 最终能修复，但中间窗口内 controller 状态不干净，且 `_wake_waiters()` 未执行导致等待中的 acquire 无法及时被唤醒
- **建议改法和验证点**: 在 `except asyncio.CancelledError` 中等待 `release_task` 完成后再更新内存状态并重新抛出；或在 `finally` 中处理。验证：编写测试在 heartbeat refresh 执行中对 token 调用 release 并同时 cancel 外层 task
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

1. **Runner 注入时机**: 当前 `_build_runner` 在 `run_agent_messages` 内部构造 Runner。如果改为注入模式，是放在 `AgentRunRequest` 中还是作为 `run_agent_messages` 的额外参数？前者保持函数签名稳定，后者更显式。
2. **`_is_sse_response` 的 fallback 设计意图**: 当前对未知 Content-Type 默认走 SSE 是有意为之（best effort）还是需要收紧？需确认现有 provider 在 stream=True 时的 Content-Type 行为。
3. **lane `asyncio.shield` CancelledError 修复优先级**: 修复需要在 CancelledError handler 中等待 task 完成，但这会增加 release 路径的延迟。是否接受当前"最终一致性"设计（依赖 heartbeat 修复不一致状态），还是要求严格一致？
4. **`_close_terminal` 中 payload descriptor 写入时序**: `_write_terminal_summary` 在 `terminal_closeout_in_transaction` 之前调用。若后者因 CAS 失败抛出异常，整个事务回滚——这是正确行为。但当前实现是否已文档化这一隐式依赖？
5. **`DefaultLocalEngineWorker.cancel()` 的 no-op 语义**: cancel 是 no-op，取消依赖 Host cancellation token。调用方 `dispatch.py` 的 `cancel_active_worker` 是否知晓这一语义？

## Residual Risk

1. **cancellation polling 精度**: `dayu.runtime.cancellation` 使用 50ms 轮询间隔检测取消。在高并发场景下，取消延迟可达 50ms。这是 cooperative cancellation 的固有限制。
2. **lane 的 SQLite 跨进程并发安全性**: 当前设计依赖 `BEGIN IMMEDIATE` + busy timeout。WAL 模式下多读者单写者语义正确，但极端高并发场景（>10 进程同时 claim）的 busy timeout 行为未被端到端测试覆盖。
3. **filelock 不提供 stale lock takeover**: 当前设计明确不提供 break lock 能力。如果使用不支持 OS 级锁的文件系统（如 NFS），可能存在 stale lock 风险。
4. **`engine_ingest.py` 作为最大单文件**（1915 行）：`_TerminalPlan` dataclass 有 16 个字段，接近 God dataclass 的边界。随着 Phase 7/10/11 扩展，该结构可能需要拆分。
5. **`stream_run_events` 性能**: `read_events_after` 扫描全局 EventLog 并按 `run_id` 过滤。当 EventLog 增长到大量事件时，长期需要考虑索引优化。
6. **测试覆盖缺口**: lane 测试缺少 token.release 与 heartbeat refresh 竞态场景（保护 Finding 004/005）；filelock 测试缺少并发 acquire 竞争场景；host 测试缺少 SQLite busy timeout / write retry 边界场景。
