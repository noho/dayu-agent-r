## Material findings

### DS-F18-RR3-001-未修复-高 — feasibility band 比较了非 action-owner token 字段，Phase A 三次 retention 可达性未被证明

- **位置**：Slice 2 / Global frozen setup 与 Shared PTY adaptive phase（plan `:138-141,153-157,168-173`）。
- **问题类型**：错误 owner 字段 / 不成立的前置校准。
- **当前写法**：plan 固化 `20,316 < 20,971 < 20,998`，把 Trial2 的 ordinary candidate `20,998` 解释为跨越 soft threshold，从而声称最多三个 retention Runs 能自然形成首个 baseline compact。
- **反例**：Host 的唯一 action owner `_pressure_and_decision` 明确用 `predicted_input_tokens` 比较 soft/hard thresholds，不读取 `conservative_input_tokens`（`dayu/host/context_budget.py:1309-1332`）。现有 Trial2 只读 typed owner state 显示：
  - seq115 continuation：conservative/predicted `20,316/20,316`；
  - seq125 ordinary：`20,363/20,363`；
  - seq139 ordinary：`20,575/19,274`；
  - seq153 ordinary：`20,998/19,707`；
  - seq167 ordinary：`21,208/19,988`；
  - seq181 ordinary：`21,318/20,104`；
  - seq194 ordinary：`21,548/20,339`。

  seq139 起均是 `usage_anchored`；plan 引用的 `20,998` 是 conservative diagnostic，不是 pressure/action basis。即使扩展到六个 no-tool ordinary candidates，最高 observed predicted 也只有 `20,339 < 20,971`。因此“随后 ordinary candidate 到 20,998 首次越线”的绑定裁决前提与 owner data 不一致。
- **候选 ratio `0.018` 的独立检验**：它派生 threshold `floor(1,048,576*0.018)=18,874`。initial ordinary predicted `9,048 < 18,874`，同 Run continuation即使达到 `20,316` 也因 stage matrix继续 `ALLOW_DISPATCH`；首个 post-tool ordinary predicted `20,363 > 18,874`，确实可在第一 retention pre-start触发 baseline。但这不是完整可行解：baseline accepted后的 FY2025 pre-start sample predicted `20,902 > 18,874`，会在 FY2025工具尚未运行前触发 premature proactive compact。floor 0 让 baseline Run 的 completed delta group eligible，current FY2025 input只作为独立 anchor，不会令 boundary 为空，所以该提前 operation不能靠 selection floor自然消失。
- **为什么重要**：Phase A 最多只允许三个 retention Runs。按现有直接数据，三次之后首 compact 仍可能根本未触发；这不是模型 stochastic branch 未覆盖，而是 plan 用错误字段声明了 provider-independent feasibility。三条真实链都可能在 baseline 前消耗 provider 后必然 seal，无法观察 B2 target。
- **建议修复**：首次 provider 前的 calibration 必须逐 candidate 保存 `sizing_stage`、`estimate_method`、`predicted_input_tokens`、soft/hard thresholds、pressure 和 action。现有 owner sample要求 baseline threshold `<=20,363` 才能在首 retention触发，同时要求 threshold `>20,902` 才能让 FY2025 pre-start先运行工具；单一 ratio无法同时满足。应调整合法 phase/source layout或其它真正 owner input并重新证明两边界，不能只把 ratio从 `0.02` 改成 `0.018`，也不能再以 conservative diagnostic 代替 predicted action input。
- **未修风险**：浪费真实 MiMo 调用，并把 plan-calibration defect错误标成自然 `needs-more-evidence`。

### DS-F18-RR3-002-未修复-高 — Phase B 的 reactive target 无法包含同一 Run 新产生的 FY2025 tool evidence

- **位置**：Slice 2 / Phase B target（plan `:158-164`）。
- **问题类型**：source-boundary reachability / immutable snapshot contract 冲突。
- **当前写法**：plan 允许 target 在“FY2025 tool Run 取得真实工具结果后的 reactive boundary”触发，并要求该 immutable initial input 直接包含 FY2025 evidence material。
- **反例**：reactive ingress 在当前 Run 的 pre-dispatch view 上冻结 source snapshot（`dayu/host/engine_ingest.py:2451-2467`）；material query 严格使用 `event_sequence < current_input_event_sequence`（`dayu/host/compact_material.py:3000-3039`）；reactive material 只是在该 view 后追加 current-input anchor（`dayu/host/engine_ingest.py:5226-5248`）。随后 compactor request直接由这个 frozen `source_snapshot`构建（同文件 `:2763-2789`）。当前 Run 的 FY2025 `TOOL_RESULT_ACCEPTED` 发生在 current input 和 initial dispatch 之后，不可能逆向进入该 pre-dispatch immutable snapshot。
- **为什么重要**：reactive target 即使自然触发，也必然缺失 mandatory FY2025 EvidenceFact，必须 seal。唯一结构上可包含该 evidence 的候选是下一 no-tool Run 的 proactive pre-start boundary。现有 post-baseline Trial2 ordinary owner state在 seq213 的 predicted 为 `20,902`，距计划 threshold `20,971` 仅 69 tokens；而新计划还给 FY2025 prompt加入旧 Trial2 未有的 unsupported `21.7%/18.2%`材料，没有 owner 证明 FY2025 Run pre-start 不会提前消耗第二次 operation。
- **建议修复**：删除 reactive target 作为合法 success path，只保留下一个 no-tool pre-start target；然后用同一个 production candidate/material owner做 provider-independent preflight，证明 FY2025 tool Run 的 pre-start predicted/action 保持 allow，而下一 target pre-start 的 immutable boundary同时含 FY2024 previous、FY2025 accepted tool evidence、unsupported material和caps并触发 compact。若该窄 band无法稳定成立，应重新设计合法、bounded source layout，不得让 analyzer 或 current prompt复述替代 tool provenance。
- **未修风险**：错误接纳一个天然缺 mandatory evidence 的 operation，或在 FY2025 evidence产生前提前消耗 target operation。

### DS-F18-RR3-003-未修复-高 — per-Run proactive/reactive 上界与“两 operations / 十 compactor calls”硬预算矛盾

- **位置**：Slice 2 / frozen profile 与 execution matrix（plan `:130-136,181-201`）。
- **问题类型**：状态机上界漏算。
- **当前写法**：profile 冻结每 Run 两次 reactive operations、每 operation 五次 attempts，却声明每链最多两次 compact operations / 十次 compactor calls。
- **反例**：proactive 对同一 Run/input snapshot最多一个 operation；reactive 的上限则是**每 Run**，同一 Run 可在 accepted recovery 后再次 overflow并创建第二次 reactive operation（`docs/host/design.md:95,3740,4010`）。直接 owner test 证明默认 `max_reactive_compactions_per_run=2` 允许第二条 reactive request（`tests/host/test_engine_ingest_mapping.py:3276-3319`），scheduler test 证明同一 Run 可提交两条 `CONTEXT_COMPACTION_REQUESTED` 和两条 `CONTEXT_COMPACTED` 后才因第三次 overflow fail closed（`tests/host/test_dispatch_scheduler.py:9528-9579`）。在已有 Phase A baseline operation 1 的前提下，Phase B target Run 可以先发生 proactive operation 2，随后同一 active Run再发生 reactive operations 3、4；external harness只能在该 Run terminal后重新取得控制。因此当前执行协议的 hard upper bound 可达 `4*5=20` compactor calls。
- **为什么重要**：external harness无法在单个 active Run内部、两次 reactive recovery之间执行“不得增加第三个 operation”的检查。plan 的 operation/call table不是可强制的 hard bound，可能超出对外声明后才被发现。
- **建议修复**：用现有 Host contract执行时，把 per-chain hard upper bound改为四次 operations / 二十次 compactor calls，并同步 execution index、branch seal和provider budget评估；若 formal scenario必须强制总计两次 operations，则需要先明确能够在 active Run 内阻止第三次 operation 的真实 owner。仅把 `max_reactive_compactions_per_run` 从 2 降为 1 仍不够，因为已有 baseline 后的 target Run仍可能产生一次 proactive加一次 reactive，使总数到 3；该字段又要求正整数（`dayu/host/context_policy.py:59-105`）。不能用 Run terminal后的 observation guard声称阻止了同一 Run 内的额外 reactive operation。
- **未修风险**：真实执行超过声明预算，或第三次 operation已经发生后才被错误标记为 unexpected setup。

### DS-F18-RR3-004-未修复-高 — `force_answer` 使 ordinary Runner hard upper 少算每 Run 一次调用

- **位置**：Slice 2 / fixed AgentPolicy 与 provider-call matrix（plan `:136,181-201`）。
- **问题类型**：Engine fallback状态机上界漏算。
- **当前写法**：plan以 `max_iterations=24` 直接派生六 Runs `6*24=144`、七 Runs `7*24=168`，并称为 product-owner hard upper。
- **反例**：主 loop确实是 `range(max_iterations)`（`dayu/engine/agent.py:881-887`），但如果第24次 iteration仍给出 tool calls，Engine会调用 `_fallback_after_tools`（同文件 `:1094-1101`）。当前 profile 的 `fallback_mode="force_answer"`（`dayu/config/execution_profiles.json:80-84`）会追加 fallback prompt，并通过 `_run_force_answer` 再执行一次 `_run_runner_iteration`（`dayu/engine/agent.py:2316-2366,2369-2395`）。因此单 Run worst case是25 calls；六 Runs为 `6*25=150`，含 reconnect七 Runs为 `7*25=175`。
- **为什么重要**：plan的 hard call cap会在合法 Engine行为下被单 Run内部越过，外部 terminal checkpoint无法预先阻止第25次 call。
- **建议修复**：把 matrix、execution-index validator和 per-chain budget统一改为 `150/175`；expected `21(+1)` 仍可保留为历史成本 checkpoint，但不得替代此 hard upper。若改 fallback mode，则属于 frozen profile语义变化，必须重新做 ConfigLoader/Service typed preflight，不能只改报告算术。
- **未修风险**：正式 execution产生合法第145/169次 call时被误判为 cap violation，或实际 provider消耗超过公开预算。

## Assumptions challenged

1. **“20,998 越过 20,971 即证明 ordinary 会 compact”**：不成立。20,998 是 conservative diagnostic；action owner使用 predicted 19,707。
2. **“current Run tool result可进入其 reactive initial input”**：不成立。reactive snapshot冻结在 pre-dispatch，工具结果发生在其后。
3. **“两次 reactive/run 等于每链总共两次 operations”**：不成立。baseline proactive不计入 reactive/run cap，target Run 自身还可同时拥有一次 proactive和两次 reactive。
4. **“max_iterations=24 等于每 Run最多24次 Runner calls”**：不成立。tool-loop exhaustion后的 `force_answer` 是额外一次真实 call。
5. **“natural non-trigger可以覆盖 plan contract错误”**：不成立。自然分支未出现可如实 needs-more-evidence；但错误字段、不可达 source boundary和错误 hard upper bound必须在 provider 前修正。

## Open questions

1. 采用 owner `predicted_input_tokens` 后，哪一个 fixed ratio/threshold 能在 bounded Phase A 内触发 baseline，同时让 FY2025 tool Run pre-start保持 allow、下一 no-tool target pre-start触发？需要逐边界 typed dry calibration，不接受 conservative 值代替。
2. 如果保留真实 usage-anchored estimator的 provider-dependent signed delta，是否存在足够宽的稳定 band？若不存在，scenario 应如何用合法 source material设计使两个目标边界可达，而不靠 padding、hot-switch或输出注入？
3. 每链 hard contract是接受现有 profile 的四次 operations / 二十次 calls上界，还是先建立能在 active Run内强制总计两次 operations的新 owner？两者必须在 profile、matrix、execution-index validator和wall/call预算中一致。
4. ordinary calls按 `150/175` 修正后，expected terminal checkpoints与每链 wall cap是否仍足以支持 bounded observation？若不够只能提前 seal，不能回写更低 hard upper。
