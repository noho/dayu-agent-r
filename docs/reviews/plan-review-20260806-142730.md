## Controller 三项关键拒绝/替代的深度挑战

### 挑战 1：request/accepted union 子集关系（F9 rejected-with-reason）

**Controller 决定**: 拒绝"request available evidence union 必须等于 accepted aggregate"，改为子集关系。

**挑战问题**: 子集关系是否足够强？是否存在 accepted aggregate 包含 request union 之外的 refs 的路径？

**分析**:
- accepted aggregate 有两个约束：(a) 等于 per-fact refs 的 ordered unique union（第 90-91 行），(b) 是 request union 的有序子集（第 189 行）
- 约束 (a) 保证了 aggregate 不包含 per-fact refs 之外的 refs
- per-fact refs 来自 boundary entry 的 `canonical_evidence_refs`（第 171-172 行公式）
- boundary entry 的 refs 来自 material provenance（第 68-80 行）
- 所有 boundary entry 的 refs 的 union 就是 request union（第 86 行）
- 因此 per-fact refs ⊆ request union（每个 fact 的 refs 是其 selected boundary entries 的 refs union，而这些 entries 都在 boundary 中）
- 因此 aggregate（per-fact refs union）⊆ request union

**结论**: 子集关系逻辑自洽。不存在 accepted aggregate 包含 request union 之外 refs 的路径。Controller 拒绝正确。

### 挑战 2：fresh schema fail-closed（MiMo F02/F05 rejected-with-reason）

**Controller 决定**: 拒绝"schema-4 rolling 时静默省略旧 facts 并走 fallback"，坚持 strict fail closed。

**挑战问题**: strict fail closed 是否在 reconnect 路径产生不可恢复的 session 损坏？

**分析**:
- 修订 plan 第 424-425 行 residual risks 明确："strict reader遇到schema-4 compact必须fail closed并保留原durable数据；本work unit的实现验证与后续formal scenario必须新建workspace/session"
- 这意味着：旧 workspace 的 durable 数据保留在磁盘上，但 v4 代码无法读取。用户需要新建 workspace/session 来使用 v4
- 这是已确认的 fresh schema 边界，不是意外行为
- 如果采用"静默省略旧 facts"的 fallback，会导致：(a) 用户不知道数据被省略，(b) 省略后的 Conversation Memory 不完整，(c) 后续 rolling compact 基于不完整的 Memory 产生新的污染
- strict fail closed + 明确错误信息 比静默降级更安全

**结论**: Controller 拒绝正确。静默省略会在用户无感知的情况下丢失信息，违反 fail closed 原则。

### 挑战 3：S1 C1-C3 替代方案（F3/MiMo F01 fixed-with-alternative）

**Controller 决定**: 拒绝"把 S1 拆成可提交 S1a/S1b"，采用 C1-C3 不提交 checkpoint。

**Controller 理由**（第 437-438 行）: "删v3后的跨consumer切换无法形成两个都完整、无双owner的accepted checkpoint"

**挑战问题**: C1-C3 是否充分解决了原 F3 的 review 有效性问题？是否存在 C1-C3 本身的结构性弱点？

**分析**:

Controller 拒绝子 slice 的理由成立：
- v3 symbols 删除后（step 1），所有 consumer 的 import 都会断裂
- 不存在一个"v4 types 已定义但 consumers 未切换"的中间 checkpoint 可以编译通过
- 强行拆成可提交的子 slice 意味着要么保留 v3 alias（违反 fresh schema），要么 commit broken code（违反"可提交"）

C1-C3 方案的强度：
- C1 聚焦 types + prompts（约 3-4 个文件的实质变更 + structure descriptor），review scope 显著缩小
- C2 聚焦 binding + payload（约 6-8 个文件），是最关键的 provenance 逻辑，含手工复算验证
- C3 聚焦 consumers（约 8-10 个文件），是 read-model 投影
- 每个 checkpoint 有 focused tests，reviewer 只需审该 cluster 的文件

C1-C3 方案的结构性弱点：
1. **re-validation 规则缺失**: plan 不说 C2 发现需要改 C1 代码时如何处理。隐含需要迭代（C1 修改后重新过 C1 check），但未写成显式规则
2. **非提交状态下的 review 基准**: reviewer 审的是 working tree diff，不是 commit diff。如果 C1-C2 之间有大量未提交变更，reviewer 难以区分"C1 已审过的代码"和"C2 新增的代码"
3. **Controller 记录证据的格式和持久化**: "每个checkpoint由Controller记录证据"——证据以什么格式记录？存放在哪里？如果证据只是 Controller 内存中的判断，re-review 无法追溯

**结论**: Controller 拒绝子 slice 的理由成立；C1-C3 是合理替代，但存在上述三个结构性弱点。其中弱点 1 和 3 应作为新 finding 要求 plan 补充。详见新 finding R1。
