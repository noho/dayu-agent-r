### 001-已修复-严重-ToolRuntime事件分组键不匹配导致ProjectionSchemaError

- **入口/函数**: `ToolTraceObserver.process()` → `_tool_call_group_key()` → `_emit_tool_call()`
- **文件(行号)**: [\_tool_trace_projection.py:592-623](dayu/host/_tool_trace_projection.py#L592-L623), [\_tool_trace_projection.py:246-255](dayu/host/_tool_trace_projection.py#L246-L255)
- **输入场景**: 工具执行结果触发截断（`TOOL_RESULT_TRUNCATED`），或发生 `TOOL_FETCH_MORE_COMPLETED`、`TOOL_CURSOR_DENIED`、`TOOL_CURSOR_EXPIRED` 等 ToolRuntime 事件
- **实际分支**: `_tool_call_group_key` 对 `TOOL_CALL_REQUESTED` 返回 `(data.iteration_id, data.tool_call_id)`（如 `("iter-1", "call-1")`），对 `ToolResultTruncatedData` 等 ToolRuntime 事件返回 `(_iteration_id_for_tool_runtime(), data.tool_call_id)`，而 `_iteration_id_for_tool_runtime` 硬编码返回 `""`。结果: `("iter-1", "call-1")` ≠ `("", "call-1")`，ToolRuntime 事件进入**不同的** `_ToolCallGroup`。
- **预期行为**: 同 `tool_call_id` 的所有事件（含 truncation / fetch_more / cursor 维度）应归于同一 group，由 `_emit_tool_call` 一次性聚合为完整 `ToolCallRecord`。
- **实际行为**:
  1. `("", "call-1")` 的 group 中只有 ToolRuntime 事件，`group.requested` 为 `None`，`_emit_tool_call` **必定抛出 `ProjectionSchemaError`**。
  2. 即使不抛异常，`("iter-1", "call-1")` 的 group 中 `group.truncated` 等字段为 `None`，截断/补读/cursor 维度数据**静默丢失**。
- **直接证据**:
  - `_tool_call_group_key` 的 6 个 `isinstance` 分支对 ToolRuntime 类型全部调用 `_iteration_id_for_tool_runtime`（L608-L619），该函数返回 `""`（L640）。
  - `ToolResultTruncatedData` / `ToolFetchMoreCompletedData` / `ToolCursorDeniedData` / `ToolCursorExpiredData` 均不携带 `iteration_id` 字段（contracts.py L308-L451）。
  - `_emit_tool_call` L247: `if group.requested is None or group.accepted is None: raise ProjectionSchemaError(...)`
- **影响**: 任何产生截断/补读/cursor 事件的 run 都会导致 trace observer 抛 `ProjectionSchemaError`，`ProjectionCoordinator` 将其标记为 `BLOCKED_FAILED`，checkpoint 不再前进，**所有 observer（含 memory / timeline / audit）投影全部卡死**。该 bug 阻碍整个 P7 trace 功能在真实场景中使用。
- **建议改法和验证点**:
  1. 将 tool 维度事件的 group key 改为仅 `tool_call_id`（`tool_call_id` 在 run 内已唯一），或
  2. 为 `ToolResultTruncatedData` / `ToolFetchMoreCompletedData` / `ToolCursorDeniedData` / `ToolCursorExpiredData` 增加 `iteration_id` 字段。
  3. 验证点：构造含 TOOL_RESULT_TRUNCATED 的 batch 进行 observer 单元测试，确认 truncation 字段正确写入 tool_call record；构造含 TOOL_FETCH_MORE_COMPLETED 的 batch 同理。
- **修复风险（中）**: 两种方案均为局部修改。方案1 更简单但丢失 `iteration_id` 在 group key 中的维度信息（当前仅用于分组，无其它语义）；方案2 需要修改多处契约与序列化。
- **严重程度（严重）**:

### 002-已修复-中-`_resolve_source_kind` 存在不可达死代码

- **入口/函数**: `_resolve_source_kind()`
- **文件(行号)**: [\_run_input_context_fact.py:243-256](dayu/host/_run_input_context_fact.py#L243-L256)
- **输入场景**: 任意包含 SystemMessage 的 `RunInput.messages`。
- **实际分支**:
  ```python
  if not seen_first_system and index == 0:   # 分支 A
      return _SOURCE_KIND_CALLER_SYSTEM
  if not seen_first_system:                   # 分支 B
      return _SOURCE_KIND_CALLER_SYSTEM
  ```
  分支 A 的条件 `not seen_first_system and index == 0` 被分支 B 的 `not seen_first_system` 完全覆盖——当 `index == 0` 且 `not seen_first_system` 时，分支 A 命中并返回；若 `index > 0` 且 `not seen_first_system`，分支 B 命中并返回。分支 A 的 `index == 0` 条件在语义上无区分度（两分支返回相同值），是冗余代码。
- **预期行为**: 若意图为"仅 `index == 0` 的 SystemMessage 标记为 `caller_system`"，则分支 B 应返回 `_SOURCE_KIND_MEMORY_BLOCK`。但当前 docstring（L230-234）明确说明"所有处于消息序列前缀（在出现第一条 SystemMessage 之前或本身即为第一条 SystemMessage 的位置）的 SystemMessage 归入 caller_system"，即两分支行为一致是有意设计。因此 `index == 0` 条件只是 dead code。
- **实际行为**: 无功能影响，但增加阅读负担。
- **直接证据**: L245-L248，两个条件返回同一常量。
- **影响**: 仅代码可读性，无功能影响。
- **建议改法和验证点**: 删除 `if not seen_first_system and index == 0:` 分支（保留 `if not seen_first_system:`），或合并为单条件。无需额外测试。

### 004-后移-低-`_select_jsonl_file` 滚动后可能向已满文件追加

- **入口/函数**: `ToolTraceJsonlSink._select_jsonl_file()`
- **文件(行号)**: [\_tool_trace_jsonl_sink.py:211-230](dayu/host/_tool_trace_jsonl_sink.py#L211-L230)
- **输入场景**: 进程 crash 重启后，JSONL 文件已落盘但 coordinator checkpoint 未推进，导致同一 session 下 replay 产生重复 record。
- **实际分支**: `_select_jsonl_file` 通过 `sorted(target_dir.glob("tool_calls_*.jsonl"))` 选择最新文件，若最新文件 `size < 10MB` 则追加，否则 `next_index = len(existing) + 1` 创建新文件。但 crash replay 场景下 observer 的 `idempotency_key` 去重仅在 analyzer 侧生效，JSONL 文件本身会追加重复行。若 crash 发生时最新文件已接近阈值，replay 追加的行可能使文件**显著超过 10MB**（而非滚动到新文件）。
- **预期行为**: 滚动逻辑应容忍 crash replay 产生的额外数据量，或在文件已满时无条件创建新分片。
- **实际行为**: 对已满文件的追加可能使单文件达到 15-20MB（取决于 crash 时待重放的数据量）。阈值是软性的，不影响正确性，仅影响文件管理可预测性。
- **直接证据**: L219-L230，`size < _FILE_BYTE_THRESHOLD` 判定后直接 `return latest`，不考虑 replay 场景下可能追加的数据量。
- **影响**: 轻微偏离 10MB 滚动设计意图，不影响正确性（`idempotency_key` 在 analyzer 去重）。
- **建议改法和验证点**: 可在 `append_record_line` 写入后检查文件大小，超过阈值时在下一次写入时自动滚动。非必须，可 deferred。

## Open Questions

1. **`ToolResultTruncatedData` 是否应在 P8 补充 `iteration_id` 字段？** 当前 ToolRuntime 事件不携带 iteration 维度，不仅导致 Finding 001 的 group key 问题，也限制了 trace record 中 `iteration_id` 的精度（当前用空字符串占位）。这应作为 P8 schema 演进议题。
   **[已落地]**：本轮一并扩展 `ToolResultTruncatedData` / `ToolCursorIssuedData` / `ToolFetchMoreRequestedData` / `ToolFetchMoreCompletedData` / `ToolFetchMoreFailedData` / `ToolCursorExpiredData` / `ToolCursorDeniedData` 7 个 dataclass，添加 `iteration_id: str` 字段；ToolExecutor / ToolRuntime 调用链显式透传 `request.context.iteration_id`（业务工具）或 `request.iteration_id`（framework `fetch_more` 自身 iteration）；durable EventLog serializer/deserializer roundtrip 同步更新。`_tool_call_group_key` 保持 `(iteration_id, tool_call_id)` 不退化。

2. **`final_response` record 的 `iteration_id` 为空字符串的长期影响？** 当前 `FinalAnswerData` 不携带 `iteration_id`，因此 observer 写空字符串（L407）。analyzer 中依赖 `run_id` 分组时不依赖 `iteration_id`，暂时无问题。但若未来需要在 trace 中关联 final_response 与最后一个 iteration 的 usage/context_snapshot，则需 schema 变更。

## Residual Risk

1. **smoke 测试未在 CI 中运行**: `utils/smoke_host_p7_tool_trace.py` 依赖真实 Engine/LLM，难以作为自动化测试。人工 smoke 是当前主要的集成验证手段，存在回归漏检风险。

2. **并发 drain + tool trace observer 未测试**: 当前 `ProjectionCoordinator.drain()` 的并发串行化测试（`test_coordinator_drain_lock_serializes_concurrent_drains`）使用 memory/timeline/audit observer，不包含 tool_trace observer。若 JSONL 文件写入或 `os.replace` 在并发场景有线程安全问题，未被覆盖。

3. **`raw_payloads/` 目录下 blob 文件无清理机制**: crash replay 场景下 `os.replace` 保证原子覆盖，但 old attempt 的 `raw_payloads/<run_id>_<old_iteration_id>/` 目录不会被清理。长时间运行会累积孤儿文件，需在后续 phase 引入保留策略。

4. **`utils/analyze_tool_trace_host.py` 仅识别 `tool_trace_v2_host` schema**: 这是设计选择（明确拒绝混用 OLD/NEW schema），但若未来存在迁移需求，analyzer 需适配。当前风险低。
