# PR #16 Review

## Findings

1. 中-`start_run` public API 的同步签名隐式要求调用方已经处于 running event loop

   - 位置：
     - `dayu/host/_run_harness.py:135`
     - `dayu/host/_run_harness.py:147`
     - `dayu/host/_run_harness.py:246`
     - `docs/host/design.md:199`
     - `docs/host/design.md:245`
     - `docs/host/design.md:270`
     - `tests/host/test_phase1_run_harness.py:385`
   - 问题：当前 public `dayu.host.start_run(request)` 是同步函数，但 `LocalRunHarness.start_run()` 内部直接调用 `asyncio.create_task(...)`。这只有在调用点已经有 running event loop 时才成立；同步 Service / CLI 调用方若按普通函数调用，会在真正返回 `RunStream` 前抛出 `RuntimeError: no running event loop`。同时 `docs/host/design.md` 的候选接口与示例均表达为 `async def start_run(...)` / `await host.start_run(...)`，当前实现与设计口径不一致。
   - 后果：P1 的“start_run 调用即接纳并启动后台执行”语义依赖一个未体现在类型签名和 README 当前事实里的运行环境前提。后续接入 Service、CLI 或非流式调用方时，调用方可能以为 `start_run` 是普通同步入口，实际在无 event loop 环境直接失败；现有测试也都在 `pytest.mark.asyncio` 内调用，没有覆盖这个边界。
   - 建议：将 public `start_run` 与 `LocalRunHarness.start_run` 改为 `async def`，调用方通过 `await start_run(request)` 完成接纳与后台 task 创建；或者如果 P1 明确要保留同步签名，则必须在契约 / README 中声明“只能在 running event loop 中调用”，并增加同步上下文调用失败或适配层行为测试。考虑 Host 设计文档已经倾向 async，推荐前者。
