### 1-未修复-严重-TOOL_CALL_REQUESTED 和 TOOL_RESULT_ACCEPTED 事件被静默拒绝，工具调用 trace 数据丢失

- **输入场景**: Engine Agent 正常执行工具调用，发出 `TOOL_CALL_REQUESTED`（每条工具调用一次）和 `TOOL_RESULT_ACCEPTED`（每条接受结果一次）。

- **直接证据**:

  - Engine agent 发出它们 (agent.py:1501, 1590)

### 2-未修复-高-`_start_worker` 中 `worker.accept()` 的非 TimeoutError 异常导致 lane claim 泄露且 dispatch record 状态不一致

- **入口/函数**: `HostDispatchScheduler._start_worker` → `_dispatch_one`
- **文件(行号)**: dayu/host/dispatch.py:616-624, dispatch.py:488
- **输入场景**: `worker.accept()` 抛出非 `TimeoutError` 的异常（如 `RuntimeError`、`ValueError`、`ConnectionError`）。

- **预期行为**: 所有异常路径都应释放 lane token 并留下可恢复的 dispatch record 状态。
- **实际行为**: 非 TimeoutError 异常无任何 lane release 路径。Lane capacity 被永久消耗（直到 claim TTL 过期）；dispatch record 卡在 `DISPATCHING` 状态，无法被自动恢复。

- **建议改法和验证点**: 在 `_start_worker` 增加通用 `try/except Exception` 包裹 `worker.accept()`，异常时释放 lane token 并调用 `_closeout_worker_startup_timeout`。

- **建议改法和验证点**: 在 `_dispatch_one` 中对 lane token 使用 `try/finally` 保护，确保在 CancelledError 或任意异常时调用 `await token.release()`。

## Open Questions

1. **`_HostCancellationToken` 与 `CancellationToken` Protocol 的结构子类型关系**: `_HostCancellationToken` 实现了 `is_cancelled()`、`cancel_reason()`、`requested_at()` 方法，在 dispatch.py:664 通过 `token: CancellationToken = cancellation_token` 赋值。Python 结构子类型应能通过，PR 声称 `python -m pyright dayu/ tests/ utils/ → 0 errors`，故假设通过。

2. **Retry/replay 的 continuity 投影策略**: Finding 6 指出 RUN_FAILED/CANCELLED/LOST 被静默丢弃。但 retry 属于 Phase 11，replay 逻辑也尚未完整实现。当前是否为有意留到后续 phase？若是，建议至少在代码注释中标记 `# TODO(phase11): project failure context for retry`。

3. **`_DefaultLocalWorkerHandle.cancel()` 空实现的设计意图**: Phase 5 docstring 标注 "Phase 5 当前只通过 Host cancellation token 观察取消"。但 Engine 侧 token 检查频率不可控。确认是否 Phase 11 计划增加 asyncio task cancel 或 `aclose()` 调用。

4. **`_HostCancellationToken` 与 durable cancel 状态的整合**: dispatch.py:604 每次创建新的 `_HostCancellationToken` 对象，总是从未取消的干净状态开始。`_is_worker_acceptable`（line 913-943）依赖 `dispatch_record.cancelled_event_id is None` 做第三重检查。若 cancel 写入的 durable 状态与 dispatch_record 更新在同一 SQLite 事务中，检查有效；若不在同一事务，存在竞争窗口。需确认 `cancel_active_attempt` 的 durable transition 的事务边界。

## Residual Risk

1. **无 active cancel watchdog**: 如果 Engine 忽略或未及时响应 `CancellationToken`，Run 将永久停留在 CANCELLING。PR description 将此归于 Phase 11。

2. **Lane coordinator 的跨进程一致性**: 当前测试使用内存/in-process lane，但生产环境使用 SQLite-based lane coordinator。跨进程 lane claim/release 的边界条件（如进程崩溃导致 lane 泄漏）未被集成测试覆盖。

3. **_consume_worker_events finally 块中异常覆盖原始异常**: dispatch.py:871-878 — `handle.close()` 可抛 `RuntimeError`，`token.release()` 可抛 `RuntimeLaneError`。若 consume 循环本身已因异常退出，finally 内的异常会覆盖原始异常，影响根因排查。

4. **_drain_loop/close() 的 task 生命周期顺序依赖脆弱**: dispatch.py:438-465, 641-652 — `_start_worker` 中 `asyncio.create_task` → `_active_tasks.add` 的顺序依赖同步执行前提。若未来在两者之间插入 await，close() 的 active task 收集可能遗漏新创建的 task。当前正确但脆弱。

5. **ActiveWorkerRegistry.cancel() 锁外操作 entry 对象**: dispatch.py:196-205 — cancel() 在锁内查找 entry，锁外调用 `entry.cancellation_token.request_cancel()` 和 `entry.handle.cancel()`。并发 `register()` 可能覆盖该 slot，cancel 可能发送给错误的新 worker。durable 状态是真源，实际影响有限。

6. **`_closeout_worker_startup_timeout` 未检查返回值**: dispatch.py:761-792 — `self._transaction_runner.run_write(_operation)` 的返回值被忽略。若 terminal closeout 因状态冲突失败（cancel 已先执行），失败被静默忽略。
