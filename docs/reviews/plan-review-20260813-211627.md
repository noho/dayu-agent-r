### N2 — 合法超长 basename 固定隐藏且保持 known content kind/code，pathful 拒绝

**事实前提验证：成立。**

- `_MAX_DETAIL_CHARS = 240`（direct_events.py:34）；POSIX NAME_MAX 255 字节、APFS 亦允许 >240 码点 basename，
  因此 241–255 长度合法 basename 真实存在且超过 public label 上限，N2 反例成立。
- `_validate_safe_text` 当前守卫集为 empty/长度/URL/fragment/job-id/绝对路径（direct_events.py:1067–1104），
  不含 Unicode `Cc/Cf`，与 plan §4（plan:115）描述的接受集缺口一致。

**plan 修复验证：成立。**

- §5.4（plan:266–277）：canonicalizer 对合法超长 basename、fragment/URL/job/path guard 命中、`Cc/Cf` 统一确定性返回
  固定标签 `输入文件（文件名已隐藏）`；**pathful 输入仍直接拒绝**（非空、无 `/`、`\\`、非 `.`/`..`）。
- 分类不变量（plan:274–275）：filing producer 先 canonicalize 再构造 reason；超长合法 basename 的 empty/conversion
  failure 必须保留原 closed content kind/code，“绝不能因 label 处理降级为 runtime/unknown failure”。
- 固定标签可验证性（本 review 独立核对）：`输入文件（文件名已隐藏）` 不含 `_DISALLOWED_TEXT_FRAGMENTS` 中任何
  fragment（fragments 为 job_id/job id/event sequence/sequence=/sequence:/cursor/resume token/resume_token/
  tool_call_id/storage path/raw payload/provider payload/.dayu/fins_ingestion/财报正文，均不命中）、无 `://`、
  无绝对路径、无 job-id pattern、长度 11 << 240 —— 必能通过既有 `_validate_safe_text`，canonicalize 产出落在
  validator 接受集内，闭环成立。
- 接受集自洽（plan:272–273）：validator 只接受 canonicalizer 可能产生的 public label；raw 超长**未 canonicalize**
  label 经 reason constructor 拒绝——这是“先 canonicalize 再构造”的强制手段，与“canonicalizer 对超长返回固定标签”
  不矛盾（固定标签本身在接受集内）。
- 测试落实：S2 断言 5（plan:538–541）覆盖普通 basename 原样、fragment、`Cc/Cf`、合法超长、pathful 拒绝，且对每个
  合法 basename 场景断言原 empty/conversion closed kind/code 保持、所有 consumer label 一致、known typed failure
  不降级；§8.1 label safety 行（plan:607）同步。
- 全 plan 无“canonicalizer 对 oversized 拒绝”的旧文本残留（grep 核对 `240/超长/拒绝` 全部命中点为新语义）。

**结论：N2 闭合。** 原“拒绝 → 分类漂移”的失败路径已被固定标签方案结构性关闭。

### N3 — `reason.__post_init__` 调唯一 validator，parser 只 delegation

**事实前提验证：成立。**

- `FinsUploadFailureReason.__post_init__` 现存且只校验 message/retry_hint（upload_failure.py:79–94），
  `file_label` 是新字段，若不加校验将成为唯一无守卫字段——与 N3 描述一致。
- 依赖方向无环：`direct_events` 模块 imports 仅为 `dayu.contracts.json_value`、`download_contract`、
  `domain.filing_semantics`（direct_events.py:9–27），不 import `upload_failure` 或 `docling_upload_service`；
  `upload_failure -> direct_events`（validator）与 `docling_upload_service -> direct_events`（canonicalizer）
  均为新增单向下游依赖，不会成环，无需 lazy import/glue seam。

**plan 修复验证：成立。**

- §5.4（plan:254–257）：`FinsUploadFailureReason.__post_init__()` 为 reason-level label 接受集的唯一强制边界，
  `file_label is not None` 时调用唯一 `validate_fins_public_file_label(...)`；owner tests 直接构造合法/`None`/非法
  label 证明任何 factory、parser 或未来 direct constructor 都受同一 invariant 约束。
- parser 职责（plan:255–256、:378）：`upload_failure_reason_from_json(...)` 只做 five-field exact key/type 读取并调用
  constructor，“不得自己调用 validator、复制长度/fragment/control/path规则或维护第二套接受集”。
- 与代码事实的衔接：现行 parser（upload_failure.py:206–235）已是 exact-key frozenset 比对 + 类型读取 +
  `FinsUploadFailureReason(...)` 单点构造；扩为五键后保持同一结构即可，不需要新增解析逻辑。
- 测试落实：S2 断言 4（plan:535–537）要求 label rejection “来自 reason constructor 调唯一 validator，parser只做
  exact key/type读取”；S2 断言 6（plan:542–544）以受控 constructor delegation test 证明 parser 原样传递五字段值，
  且明确禁止在 parser 测试复制 label 接受规则表；§8.1（plan:607）、§12（plan:789）同步。
- 单 validator 结构（plan:262–263）：canonicalizer 与 validator 共享一个私有判定实现并复用 `_validate_safe_text`
  与 `_DISALLOWED_TEXT_FRAGMENTS`，无重复 validator，不新建模块/value type/registry。

**结论：N3 闭合。** 接受集分裂（parser 与 constructor 两套规则）的缺口被 constructor 唯一边界关闭，且 delegation
test 防止 parser 复制规则。
