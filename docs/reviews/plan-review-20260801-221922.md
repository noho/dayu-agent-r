## 2. Findings

### 001-未修复-中-所有 15 个 builder call site 均无 identity 数据，5-file delta 描述误导性

- **位置**: §2.3 inventory、§3.2 五文件机械迁移边界
- **问题类型**: 非最优方案 / 契约缺失
- **当前写法**: Proposal 将问题框定为"5 个测试文件不在 allowed boundary"，暗示已允许的 3 个文件不受影响，5-file delta 是自包含的机械闭包。
- **反例/失败场景**: 实际验证发现：**所有 8 个测试文件的所有 15 个 builder call site 都是 bare 的**——没有任何一个携带 `run_id`、`iteration`、`attempt_id`、`execution_id` 或 `provider_request_id`。根因是 builder 函数签名本身不接受这些参数（`dayu/host/context_events.py` 第 1092 行和第 1352 行）。实现 agent 不能只修改 5 个 gap 文件，必须先扩展两个 builder 的生产签名，然后更新全部 15 个 call site。
- **为什么有问题**:
  - 3 个"已允许"文件（test_context_compact_events: 4 CB + 3 RB、test_compaction_operation: 1 RB、test_dispatch_scheduler: 1 CB + 1 RB）同样需要签名迁移，但 proposal §3.2 只列出了 5 个新文件的迁移边界。
  - Proposal 的"该测试已有的同一次成功 response / operation / attempt fixture 提供"约束在 5 个 gap 文件中不成立——这些 helper 函数没有任何 Engine identity fixture 数据。
  - §3.1 point 2 将 5-file delta 冻结为"补齐新增 required `successful_response_identity` 参数"，但未说明这个参数首先需要在生产 builder 中新增。
- **直接证据**:
  - `build_context_compacted_payload` 签名（context_events.py:1092）：无 identity 参数
  - `build_context_compaction_attempt_rejected_payload` 签名（context_events.py:1352）：无 identity 参数
  - 8 个测试文件的 15 个 call site 全部 bare（已由独立 `rg -B2 -A2` 验证）
  - `test_dispatch_scheduler.py:10548-10549` 的 identity 数据在 `EventLogAppendRequest` envelope 上，不在 payload builder 内
- **影响**: 实施 Agent 可能只修改 5 个 gap 文件，遗漏已允许 3 个文件的同一签名迁移；或在不理解全貌的情况下修改生产 builder，导致部分 call site 编译失败。
- **建议改法和验证点**:
  - §3.2 增加明确说明：S5 首先需要扩展 `build_context_compacted_payload` 和 `build_context_compaction_attempt_rejected_payload` 的签名以接受 `successful_response_identity` 参数，这属于 `dayu/host/context_events.py` 的生产代码变更（已在 §9.1 allowed production 文件中）。
  - §3.2 补充：签名扩展后，全部 8 个测试文件的 15 个 call site 都需要机械迁移。5-file delta 是 allowed test boundary 的新增，不是迁移范围的全部。
  - 对于"该测试已有的同一次成功 response fixture"约束：明确说明 identity fixture 需要在 helper 函数中新增（accepted 场景用 test-only 常量，rejected failure 场景用 `null`），不要暗示数据已存在。
- **修复风险（低/中/高）**: 低——只需澄清文本，不改变 amendment 的实质闭包
- **严重程度（低/中/高/严重）**: 中——不阻塞 amendment 通过，但会误导实施 agent

### 002-未修复-低-rejected failure 场景的 identity 处理规则需要显式确认

- **位置**: §3.2 第五行（test_proactive_compaction_operation.py 迁移边界）
- **问题类型**: 契约缺失
- **当前写法**: "给既有 rejected attempt fixture 补符合原 rejection 场景的 required mapping 或 `null` exact field"
- **反例/失败场景**: 目标 plan §9.4 规定 rejected 的 `successful_response_identity` 是 "required field but value may be mapping or null"。对于 proactive failure 场景（quality_check_rejected、exhausted budget），`null` 是正确值。但 proposal 未显式确认：这些测试的 `failure_category` 和场景是否全部属于"没有 successful Engine final"的类别。
- **为什么有问题**: 如果某个 rejected 测试实际上有 successful Engine final（例如 parse rejection 在 accepted 之后），则 `null` 是错误值。实施 agent 需要逐场景判断。
- **直接证据**: `test_proactive_compaction_operation.py` 的 3 个调用 `_rejected_payload` 的测试函数全部是 failure/rejection 场景（orphan、incomplete、exhausted），无 Engine final。`provider_request_id` 在 `_requested_payload` 中显式为 `None`。
- **影响**: 低——当前 3 个场景确实都是 failure，`null` 正确；但 proposal 应显式确认而非让实施 agent 猜测。
- **建议改法和验证点**: §3.2 对 test_proactive_compaction_operation.py 的迁移边界补充一句："当前 3 个调用场景（orphan、incomplete、exhausted）均无 successful Engine final，`successful_response_identity` 值应为 `null`。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## 5. Conclusion

**pass-with-risks**

Proposal 的核心判断正确：第二次 premise invalidation 成立，8-file builder inventory 精确，30-file total mechanical union 准确，5-file delta 的 allowed boundary 扩展合理。目标 plan 的 §10.5 已包含所需的 pre/post inventory 命令。

主要风险是 Finding 001：proposal 将问题框定为"5-file delta"但实际影响范围是全部 8 个文件的 15 个 call site，且 identity fixture 在所有 call site 中都不存在。这不阻塞 amendment 通过（因为 §3.1 的 8-file inventory 完整列出了所有受影响文件），但 §3.2 的"五文件机械迁移边界"表述会误导实施 agent。建议 controller 在接受 amendment 前要求修正 §3.2 的表述。

Finding 002 是低严重度的 clarity 问题，可在 amendment 接受后、S5 实施前由实施 agent 自行确认。
