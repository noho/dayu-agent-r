## Material Findings

### F1 — 终端诊断可见性路径欠规格：未指定在哪个分层边界构造诊断后缀（中）

- **位置**: Plan §6 "Possible Public Interface Change For Terminal Diagnostic", §7 Decision 7, §8 Slice 4
- **问题类型**: 不可直接实施 / 架构边界
- **当前写法**: Plan 给出两种选项（error_message 后缀 vs typed 字段），Decision 7 展示期望输出格式，Slice 4 说"Pick the smaller interface path from section 6"，但没有指定具体在哪个代码边界构造诊断后缀。
- **反例/失败场景**: 实现 Agent 有三个可选位置构造诊断后缀：
  1. `engine_ingest.py`：在构造 terminal payload 的 `message` 字段时追加（Host 内部 ingest 层）
  2. `read_api.py` 的 `_failed_host_event()`：在构造 `HostEvent.error_message` 时追加（Host public API 投影层）
  3. `entrypoint_runtime.py`：在构造 `EntrypointRunTerminalResult.error_message` 时追加（Service 层）

  三个位置有不同后果：
  - 位置 1：修改的是 durable EventLog payload 的 `message` 字段，影响所有下游消费者（Tool Trace、Audit、replay），且 `message` 改变会影响 `payload_digest`。
  - 位置 2：只在 `HostEvent` 投影时追加，不影响 durable payload，但 `OutboxTerminalItem` 走的是独立投影路径（`outbox.py`），需要在 outbox 投影中重复实现。
  - 位置 3：最接近用户展示，但 `EntrypointRunTerminalResult` 只能拿到 `HostEvent.error_message`，拿不到 `provider_request_id` 和 `client_correlation_id`（HostEvent 当前无这两个字段）。
- **为什么有问题**: Plan 说"using fields already present in terminal payload"，但没有说明是在哪一层读取 payload 并追加。如果不指定边界，实现 Agent 可能选错位置，导致数据不可达（位置 3 拿不到原始字段）或改变 durable truth（位置 1 改变 digest）。
- **直接证据**:
  - `read_api.py:960-984`：`_failed_host_event()` 当前只读 payload 的 `message` 字段，不读 `provider_request_id` 或 `client_correlation_id`
  - `entrypoint_runtime.py:1342-1353`：`EntrypointRunTerminalResult` 直接从 `HostEvent.error_message` 透传，无额外字段
  - `outbox.py` 的 outbox terminal item 投影独立于 `read_api.py` 的 live HostEvent 投影
- **影响**: 实现 Agent 可能选错边界导致：(a) 改了 durable payload 影响 digest；(b) live watcher 和 outbox fallback 展示不一致；(c) 实现后发现字段不可达需要返工。
- **建议改法和验证点**: 在 plan 中明确：诊断后缀在 `read_api.py` 的 `_failed_host_event()` 和 `outbox.py` 的对应 outbox 投影函数中分别追加到 `error_message`，来源是 durable payload 中已存在的 `provider_request_id` 和 `client_correlation_id` 字段。两条投影路径必须使用相同的格式化逻辑（抽取为模块级私有 helper）。验证点：(a) live watcher 失败终端展示包含 fallback id；(b) outbox fallback 展示包含相同 fallback id；(c) durable payload 的 `message` 字段不变（digest 不变）。

### F2 — Runner 日志行扩展需要未声明的私有方法签名变更（低/中）

- **位置**: Plan §7 Decision 4, §8 Slice 2 Step 4
- **问题类型**: 不可直接实施
- **当前写法**: "Extend existing `runner.http.response` debug message to include `client_correlation_id` only if implementation can thread request identity into `_request_once(...)` without awkward coupling."
- **反例/失败场景**: `_do_attempt()`（即 plan 所称 `_request_once`）当前签名是 `async def _do_attempt(self, payload, options, *, headers: Mapping[str, str])`。`request_identity` 在调用方 `_call_impl` 中可用，但未传入 `_do_attempt`。要扩展日志，必须增加参数。Plan 用 "if ... without awkward coupling" 回避了这个必须做出的决定。
- **为什么有问题**: 这不是 "awkward coupling" 的问题——这是一个私有方法，从同一个类的另一个私有方法调用。传一个额外参数是标准做法。Plan 的不确定性可能让实现 Agent 跳过这个日志扩展（"如果耦合不好就算了"），导致 `client_correlation_id` 不出现在任何 Runner 日志中。而 Runner 日志是运行中唯一能实时看到 `client_correlation_id` 的地方（Tool Trace 是 post-hoc）。
- **直接证据**:
  - `runner.py:383`：`_call_impl` 调用 `self._do_attempt(payload, effective_options, headers=headers)`，`request_identity` 在作用域内但未传入
  - `runner.py:558`：`_do_attempt` 签名不包含 `request_identity`
  - `runner.py:607-612`：目标日志行 `runner.http.response` 当前只有 `provider_request_id`
  - Plan §8 Slice 2 Step 4："Extend existing runner.http.response debug message to include client_correlation_id only if implementation can thread request identity..."
- **影响**: 低风险——即使跳过日志扩展，Tool Trace 和终端诊断仍能满足可见性。但 plan 应明确是否做，而不是留给实现 Agent 判断"awkwardness"。
- **建议改法和验证点**: 移除 "if ... without awkward coupling" 限定语，改为明确决定：(a) 扩展 `_do_attempt` 签名增加 `client_correlation_id: str | None` 参数并在日志行追加；(b) 或在 `_call_impl` 中在调用 `_do_attempt` 前后分别打日志。推荐 (a) 因为简单且在同一日志行。验证：开启 DEBUG 日志确认 `runner.http.response` 行包含 `client_correlation_id`。

### F3 — Provider request id header allowlist 可能引入语义混淆（低/中）

- **位置**: Plan §7 Decision 5
- **问题类型**: 范围漂移 / 最佳实践偏离
- **当前写法**: 建议增加 `x-requestid`, `x-correlation-id`, `x-trace-id`, `x-amzn-requestid`, `cf-ray` 到提取 allowlist
- **反例/失败场景**:
  - `x-trace-id` 和 `x-correlation-id` 是 W3C 分布式追踪 headers，不是 provider 分配的 request id。将它们赋值给 `provider_request_id` 字段会在 Tool Trace 查询 `find_tool_trace_by_provider_request_id()` 时返回不相关的 trace rows（因为拿到的是 tracing middleware 注入的 id，不是 provider 内部分配的 id）。
  - `cf-ray` 是 Cloudflare edge 的 ray id，不代表上游 provider 的 request id。如果 Dayu 请求经过 Cloudflare（直接或通过代理），`cf-ray` 会在每个 response 中存在，但与 provider 内部排障无关。
- **为什么有问题**: Plan 自己承认"如果实现 Agent 无法论证 provider-independent allowlist，使用更保守的 header-name-only diagnostic"。但第一条路径（扩展 allowlist）的语义风险没有被充分评估——给 operator 一个不是 provider 分配的 "provider_request_id" 比不给更危险，因为它会误导排障方向。
- **直接证据**:
  - `runner.py:94`：当前 `_PROVIDER_REQUEST_ID_HEADER_NAMES = ("x-request-id",)`
  - `runner.py:114-129`：`_extract_provider_request_id` 只检查 allowlist 中的 header name
  - `tool_trace.py` 的 `find_tool_trace_by_provider_request_id()` 把提取值当作 provider request id 查询
  - Plan §7 Decision 5 正文列出 `x-trace-id`, `x-correlation-id`, `cf-ray` 等
- **影响**: 如果 operator 用 allowlist 中的 `x-trace-id` 值去联系 provider 厂商，厂商无法根据 tracing middleware 分配的 id 定位请求。比返回 `None` 更差。
- **建议改法和验证点**: 两种安全路径二选一：(a) 保持当前 `x-request-id` 唯一提取，不扩展 allowlist——因为 #63 的当前证据是 mimo 不返回 `x-request-id`，不是返回了别的 header name；(b) 如果确需扩展，仅接受 provider-specific headers（如 `x-amzn-requestid` for Bedrock、`x-request-id` for OpenAI-compatible），并明确 exclude W3C trace context headers 和 infrastructure headers。验证：测试中每个 allowlisted header name 必须注释说明哪个 provider 使用它。

### F4 — 终端诊断可见性涉及 live watcher 和 outbox fallback 两条独立投影路径，plan 未区分（中）

- **位置**: Plan §8 Slice 4
- **问题类型**: 切片过粗 / 架构边界
- **当前写法**: Slice 4 只说 "For live HostEvent failed terminal path... For outbox terminal fallback path..." 但没有指出这两条路径在代码中是**独立实现**的。
- **反例/失败场景**:
  - Live watcher path：`read_api.py` 的 `_failed_host_event()` → `HostEvent.error_message` → `entrypoint_runtime.py` → `cli/output.py`
  - Outbox fallback path：`outbox.py` 的 terminal item projection → `OutboxTerminalItem.error_message` → `entrypoint_runtime.py`（outbox 分支）→ `cli/output.py`
  - 两条路径各自从 durable payload 读取 `message` 字段构造 `error_message`。如果在其中一条追加诊断后缀而另一条不追加，会导致 live 展示有 fallback id 而 outbox 重连后丢失。
- **为什么有问题**: Plan 没有指出两条投影路径需要一致的诊断后缀逻辑，实现 Agent 可能只在 live path 实现而忽略 outbox path，导致离线补读时丢失 `client_correlation_id`。
- **直接证据**:
  - `read_api.py:960-984`：live `_failed_host_event()` 投影
  - `outbox.py`：独立的 outbox terminal item 投影（独立于 `read_api.py`）
  - Plan §8 Slice 4 Step 2-3 未提及两条路径的一致性问题
- **影响**: 实现 Agent 可能只改了一条路径导致行为不一致。
- **建议改法和验证点**: Plan 应明确要求抽取共享的 `_diagnostic_suffix(provider_request_id, client_correlation_id) -> str` helper 供两条投影路径复用。Slice 4 测试必须同时覆盖 live watcher 和 outbox fallback 两条路径。

### F5 — Service assembly 默认启用后，现有可能测试被静默影响的范围未评估（低）

- **位置**: Plan §8 Slice 1, §9
- **问题类型**: 测试缺口
- **当前写法**: "Add or update tests asserting ordinary baseline and compactor baseline runner specs from compose_open_host_options(...) use OPENAI_X_CLIENT_REQUEST_ID" 和 "Existing disabled policy tests still pass."
- **反例/失败场景**: `tests/service/test_host_assembly.py`（80KB+）和 `tests/runtime/test_smoke_host_public_multiturn_assembly.py` 中有大量测试通过 `compose_open_host_options(...)` 或直接构造 `RunnerSpec` 创建 assembly。这些测试当前运行在 `DISABLED` 默认下。改为 `OPENAI_X_CLIENT_REQUEST_ID` 后：
  - 使用 `compose_open_host_options` 的测试会自然获得新默认——这是期望行为
  - 但如果某个 smoke 测试依赖 exact `RunnerSpec` 字段比较（frozen dataclass equality），它会失败
  - `test_smoke_host_public_multiturn_assembly.py` 的 public smoke 测试会实际创建 Runner 并可能发起网络调用——如果 provider 拒绝 `X-Client-Request-Id` header，smoke 会失败（这正是 plan 的 stop condition，但测试本身没准备好处理这个失败）
- **为什么有问题**: Plan 没有要求先跑一遍现有测试看看哪些会因默认启用而失败，就直接断言"Existing disabled policy tests still pass"。这是一个未经证实的假设。
- **直接证据**:
  - `tests/service/test_host_assembly.py` (80KB) 和 `tests/runtime/test_smoke_host_public_multiturn_assembly.py` 无任何 `ClientCorrelationPolicy` 断言
  - `runner_spec.py:298-329`：`RunnerSpec.__post_init__` 使用 frozen dataclass，任何 exact equality 比较会受 `client_correlation_policy` 字段影响
- **影响**: 实现阶段可能发现现有测试意外失败，需要额外 debug 时间。
- **建议改法和验证点**: 在 Slice 1 实施前，先跑 `pytest tests/service/test_host_assembly.py tests/runtime/test_smoke_host_public_multiturn_assembly.py -q` 确认当前全部通过，作为基线。如果默认启用后出现失败，区分：(a) 期望的行为变化（更新断言）；(b) 意外的 regression（需要在 plan 中增加对应处理）。

## Architecture Boundary Review

- **分层**: Plan 正确遵守 `Service -> Host -> Engine` 分层。Default enablement 在 Service assembly 层（类型化 policy 进入 `RunnerSpec`），Host 不解释 provider 字符串，Engine 只消费 typed spec。✅
- **依赖方向**: 无反向依赖引入。Service 依赖 Engine contracts（`ClientCorrelationPolicy`, `RunnerSpec`）是现有依赖方向。✅
- **公共契约**: Plan 正确识别 `HostEvent` / `OutboxTerminalItem` / `EntrypointRunTerminalResult` 可能需要扩展，并优先选择不扩展 schema 的方案。⚠️ 见 F1、F4。
- **Schema / 状态机**: Plan 明确不改变 Run/Attempt 状态机、不新增 EventLog canonical fact、不新增 durable schema。✅

## Best-Practice Review

- **可测试性**: 每个 slice 可独立测试。Slice 1 不依赖 Slice 2-4。Slice 3（Tool Trace）不依赖 Slice 4（终端诊断）。✅
- **可维护性**: 类型化 policy 优于 provider 字符串分支。默认在单一 assembly 点设置优于分散在多处。✅
- **可观测性**: 复用现有日志站点和级别，不新增日志基础设施。✅
- **失败处理**: Plan 包含明确的 stop conditions：provider 拒绝 header、静态 header 冲突无法 fail fast、无现有边界可暴露 id、header 提取会泄漏敏感数据。✅

## Optimal-Solution Review

Plan 的最小修复路径（改一行默认值 + 修复 Tool Trace skip 条件 + 追加终端诊断后缀）是正确方案。相比可能的替代方案：
- 新增配置项 → 过度设计，违反 reopen comment 要求 ✅ 避开了
- Provider 字符串分支 → 脆弱的治理模式 ✅ 避开了
- 新增专用日志事件 → 违反用户约束 ✅ 避开了
- 新增 EventLog fact → 过度设计 ✅ 避开了

## Overengineering Review

无 overengineering 发现。Plan 使用现有 typed contract、现有日志站点、现有投影边界、现有终端展示路径。Provider request id header allowlist 有轻微过度扩展风险（见 F3），但 plan 自带了保守回退方案。

## Overcoupling Review

F4 指出了 live watcher 和 outbox fallback 两条投影路径需要在 plan 中明确为独立但需一致实现的路径。这不是过度耦合——这是两条独立投影路径的本职工作——但 plan 应明确要求逻辑一致性。
