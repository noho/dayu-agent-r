## Findings

### F1-未修复-中-移除 after-commit/after-compact catch-up budget 缺少替代延迟安全边界

- **位置**: Implementation Decisions #6, Slice 4, Risks / Open Questions Risk 3
- **问题类型**: 最佳实践偏离
- **当前写法**: "After-commit / after-compact catch-up 同样不保留语义预算"；"若担心 commit 后 hook 同步耗时，本 WU 不引入新的 stop budget；后续如需异步 projection worker，应作为独立 work unit 设计"
- **反例/失败场景**: 当 Session 积累了大量 matching memory facts（如长会话、大量 tool calls），after-commit catch-up 在无上限情况下同步执行多页循环。commit hook 是 Host command path 的一部分，长时间阻塞会影响用户可见的 dispatch 延迟。`open_host.py:152-170` 当前 `_after_commit_memory_projection_budget` 使用 `_OPPORTUNISTIC_AFTER_COMMIT_MEMORY_PROJECTION_BATCH_COUNT` 限制批次数；`dispatch.py:324-344` 使用 `_OPPORTUNISTIC_AFTER_COMPACT_MEMORY_PROJECTION_BATCH_COUNT`。这些不是 "semantic budget"（correctness 停止条件），而是 latency safety bound（command path 延迟保护）。移除它们会把 latency safety 也一并移除。
- **为什么有问题**: plan 把 "semantic budget"（LIMIT N 作为 correctness 停止条件）和 "latency safety bound"（限制 command path 同步执行时间）混为一谈。前者确实应移除，后者是独立的工程安全约束。当前预算值（如 `max_batches=3`）不是 "伪装 correctness 的 LIMIT N"，而是 "保护 commit hook 不无限执行" 的合理边界。
- **直接证据**: `open_host.py:164-169` `MemoryProjectionCatchupBudget(max_batches=_OPPORTUNISTIC_AFTER_COMMIT_MEMORY_PROJECTION_BATCH_COUNT, max_scanned_events=batch_size * _OPPORTUNISTIC_AFTER_COMMIT_MEMORY_PROJECTION_BATCH_COUNT, purpose=BEST_EFFORT_AFTER_COMMIT)`；`dispatch.py:338-344` 同理。plan Slice 4 明确要求删除 `_opportunistic_memory_projection_catchup_budget(...)` 和 `_after_commit_memory_projection_budget(...)`。
- **影响**: production 环境中长会话的 after-commit hook 可能同步执行过久，影响 dispatch 延迟；implementation agent 删除 budget 后没有替代保护。
- **建议改法和验证点**: 区分 "semantic budget" 和 "latency safety bound"。correctness path（dispatch 前 required catch-up）不设总预算，追到 target/idle/failure。opportunistic path（after-commit/after-compact）保留 max page count 作为 latency safety bound，但更新 docstring 说明它不是 semantic budget。或者，如果认为 after-commit/after-compact 本身应改为异步，明确标记为 deferred 且当前 WU 保留现有 page count。验证：after-commit catch-up 测试断言 max page count 仍在生效。
- **修复风险（低/中/高）**: 低 — 只需在 Slice 4 中区分两种 budget 语义
- **严重程度（中）**: 不阻塞核心 correctness，但 production 延迟风险真实存在

### F2-未修复-低-Filter-aware covered cursor 实现细节需要更精确规格

- **位置**: Implementation Decisions #3, Slice 3 Exact changes
- **问题类型**: 不可直接实施
- **当前写法**: "当有匹配 row 且达到 page limit 时，covered cursor 是最后一条匹配 row。未达到 page limit 时，covered cursor 是 `max_event_sequence` 或当前 latest EventLog sequence，表示匹配 filter 的 rows 已读尽，可以越过中间不相关 rows。"
- **反例/失败场景**: 当 `max_event_sequence` 被指定（如 inline repair 场景）且 EventLog 中没有 sequence 正好等于 `max_event_sequence` 的 row 时，`covered_event_id` 无法对应到真实 EventLog row。例如 `max_event_sequence=100` 但 EventLog 最新 row sequence=95，covered cursor 应该是 95（有真实 row）还是 100（无真实 row）？
- **为什么有问题**: `advance_projection_checkpoint` 要求 `event_id` 引用真实 EventLog row（`durable/projection.py:152-206`）。如果 `covered_event_sequence` 对应的 EventLog row 不存在，checkpoint advance 会失败。plan 说 "covered row 可以不匹配 filter，但必须存在于 EventLog"，但没有明确当 `max_event_sequence` 超出 EventLog 范围时如何处理。
- **直接证据**: `durable/projection.py:177` `if event_sequence <= checkpoint.checkpoint_event_sequence` 检查；`durable/projection.py:183-188` UPDATE 语句使用 `event_id`。
- **影响**: implementation agent 可能在边界条件下写出无法工作的 covered cursor 逻辑；测试可能不覆盖 `max_event_sequence` 超出 EventLog 范围的场景。
- **建议改法和验证点**: 在 Slice 3 中明确：当 `max_event_sequence` 超出 EventLog 范围时，covered cursor 使用 EventLog 中实际存在的最大 sequence row；当 `max_event_sequence` 在 EventLog 范围内但无精确匹配 row 时，covered cursor 使用 `max_event_sequence` 之前最近的真实 row。测试应覆盖这两种边界。
- **修复风险（低/中/高）**: 低 — 补充规格即可
- **严重程度（低）**: 有 stop condition 兜底（"如果 checkpoint schema 不允许以 non-matching covered row 作为 checkpoint event id，停止"），但规格补充可以避免 implementation 返工

### F3-未修复-低-Slice 5 filter 共源方案存在 import cycle 风险但未明确偏好

- **位置**: Slice 5 Exact changes, Stop condition
- **问题类型**: 过度耦合
- **当前写法**: 提供两个可选方案：(1) 实例化 `ConversationMemoryProjectionConsumer` 并读 `.event_filter`；(2) 在 `memory.py` 提供 `conversation_memory_projection_event_filter()` helper。Stop condition 说 "如果引入 consumer 实例造成 import cycle，改为 helper"。
- **反例/失败场景**: 方案 1 让 `run_input.py` 依赖 `durable/memory.py` 的 `ConversationMemoryProjectionConsumer` 类。当前 `run_input.py` 已经依赖 `durable/memory.py` 的 `project_conversation_memory_event` 等函数（`run_input.py:1211`），所以 import direction 已存在。但实例化 consumer 需要 `MemoryProjectionPolicy`，而 `run_input.py` 中的 `DurableMemorySnapshotProvider` 已经持有 `_policy`（通过构造函数传入）。所以方案 1 不会产生新 import cycle。方案 2 更干净但需要确保 consumer 的 `event_filter` 也从同一 helper 生成。
- **为什么有问题**: plan 没有明确偏好哪个方案，留给 implementation agent 选择。两个方案的 contract 略有不同：方案 1 是 "consumer 是 filter 真源"，方案 2 是 "helper 是 filter 真源，consumer 和 inline repair 都调用它"。
- **直接证据**: `run_input.py:1211` 已 import `project_conversation_memory_event` from `durable.memory`；`memory.py:240-247` consumer 构造 filter 使用 `_EVENT_TYPE_FILTER`。
- **影响**: implementation agent 可能选择方案 1 后发现需要额外暴露 consumer 内部状态，或选择方案 2 后忘记让 consumer 也从 helper 生成 filter，导致两份列表。
- **建议改法和验证点**: 偏好方案 2（helper 作为 filter 真源），并在 plan 中明确：`conversation_memory_projection_event_filter()` 返回 `ProjectionEventFilter`，`ConversationMemoryProjectionConsumer.__init__` 调用同一 helper，`run_input.py` 的 inline repair 也调用同一 helper。验证：断言 consumer.event_filter 和 inline repair 使用的 filter 是同一对象或语义等价。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: stop condition 已兜底

## Architecture Boundary Review

plan 正确遵守分层边界：
- durable EventLog read filter 定义在 `durable/event_log.py`，不 import projection 层
- projection 层通过 `_event_log_read_filter_from_projection_filter(...)` 转换，是单向依赖
- RunInputBuilder 通过 shared helper 或 consumer 实例获取 filter，不自行维护 memory type 列表
- Engine contract 不变，Host ingest 决定 durable 语义

## Best-practice Review

plan 的 no-overdesign rationale 合理：只改三处直接根因，不引入新 stream subsystem、不改 public API、不改 durable schema。filter-aware read 使用现有 EventLog class/type/sequence 列即可表达。

## Overengineering Review

未发现过度设计。plan 没有引入不必要的 abstraction layer、builder pattern 或 generalization。

## Overcoupling Review

Slice 5 的 filter 共源有轻微耦合风险（import direction），但现有代码已有同方向 import，且 stop condition 兜底。不构成 blocking finding。

## Conclusion

**pass-with-risks**

plan 的动机正确、架构方向安全、slice 划分合理。核心 correctness 变更（delta non-durable、filter-aware ProjectionRunner、semantic budget removal）有充分代码证据支撑且设计连贯。

1 个中等 finding（F1: after-commit/after-compact latency safety bound 被一并移除）需要在 implementation 前明确处理：要么保留 opportunistic path 的 page count 作为 latency bound（更新 docstring 区分 semantic budget），要么明确标记为 deferred 且当前 WU 不动该 bound。2 个低 severity findings 属于 implementation 前规格补充，不阻塞 plan gate。
