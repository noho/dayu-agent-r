## 四、Findings

### DS-1-未修复-[中]-异常时间值的拒绝是静默丢弃，计划自身的停止条件在生产运行中缺少触发机制
- **位置**：计划 §语义 owner 和不变式·1 输入边界（L15）、§验收测试与执行门槛·日期 owner（L33）、§依赖、停止条件与后续 gate（L41）；实现落点 `dayu/fins/downloaders/cninfo_downloader.py:_format_announcement_date` / `_parse_raw_announcement`。
- **问题类型**：最佳实践偏离（可观测性）/ open question 未收敛。
- **当前写法**：DTO owner 对 `bool`、浮点、负号或带符号字符串、非 ASCII 数字、非整数、不可表示的越界值一律 `return None`，"沿 `_parse_raw_announcement` 既有 DTO 丢弃路径处理，不在下游猜测或补偿"（L15）；L41 的停止条件是"若真实目标公告出现与统一 epoch 毫秒解释冲突的形态，立即停止，提交同源证据供 provider 协议及 owner 裁决"。
- **反例/失败场景**：provider 或其中间层把 `announcementTime` 序列化为指数/浮点写法（如 JSON 数字 `1.7431776E12` → Python `float`），或未来出现 8 位形态：`_format_announcement_date` 判 `None` → `cninfo_downloader.py:842` 的 `not announcement_date` 直接丢弃**整条公告** → 当日 `discovered=0`。该结果与"当日确实无公告"在 CLI 摘要（`discovered/downloaded/failed`）、事件流、日志中完全同形：`_query_announcements`（`:455-505`）不记录原始条数或丢弃计数，`_format_announcement_date` 拒绝分支无任何日志。
- **为什么有问题**：计划把"出现冲突形态即停止并裁决"当作协议漂移安全网，但同时禁止下游补偿且未要求 owner 输出任何诊断，安全网没有触发机制。EXCEPT 03-29 目标样本这一条验收（要求 `discovered=1`）会把冲突形态暴露成验收失败；其它 ticker/日期的同类漂移会长期静默漏财报——正是本 WU 要消灭的失败类型。项目约束要求"失败不被隐藏"，同模块对更轻的情形（HEAD 失败 `:657`、翻页保护 `:500`）已用 `Log.warn`。
- **直接证据**：`cninfo_downloader.py:839-843`（`None` 即丢公告）、`:871-905`（现状接受 `float`/非 ASCII 数字，本计划收窄拒绝面）、`:455-505` 与 `:871-905` 无计数/无诊断、`:500`/`:657` 的 `Log.warn` 先例；计划 L15/L33/L41 原文；A3 的收窄实测。
- **影响**：协议漂移或异常值造成静默漏财报，排障只能靠逐日人工比对 provider 原始响应；L41 停止条件在自动运行路径不可触发。
- **建议改法和验证点**（二选一，优先前者，均不违反"禁止下游补偿"）：
  1. 最小行动：在 owner 的拒绝分支加一条不含凭据、不落原文的 `Log.warn`（可含 `announcement_id` 与原始 JSON 类型名或长度，如"announcementTime 形态不受支持: type=float"），并在 L41 写明停止条件由该告警或独立只读探针触发；验收补一条断言拒绝路径有可观察信号。
  2. 备选（需总控重新裁决，非本审查主张）：在"统一整数毫秒"合同内接受**可精确表示**的整数毫秒浮点（`float.is_integer()` 且范围可表示后转 int），只拒绝 NaN/Inf/非整数/负值/越界——不引入长度或年份 heuristic，也不动摇 PR2-F1 防 `bool`/垃圾值的动机。
- **修复风险**：低（方案 1）。
- **严重程度**：中。**备注**：本条与已接受裁决 PR2-F1（float → None）相邻；若总控维持原接受/拒绝集合，最小行动是补告警，不改已裁决集合。

### DS-2-未修复-[低]-缺省窗口锚点仍是宿主本地日期，"中国本地日"只覆盖显式窗口，计划未显式登记该口径差
- **位置**：计划 §语义 owner 和不变式·2 请求与选择（L16）、§验收测试与执行门槛·真实隔离 CLI（L37，全部使用显式 `--start/--end`）、§依赖、停止条件（L41）。
- **问题类型**：范围/语义 owner 未收敛（open question）；**不构成范围扩张主张**。
- **当前写法**：L16 只声明"`start_date/end_date` 与 `seDate` 继续是用户闭区间，保持原样，不增加天数"，未区分"用户显式给定"与"缺省锚点"。
- **反例/失败场景**：`dayu-cli download --ticker X --forms FY`（不带日期）时，`cn_form_utils.resolve_window` 用 `dt.date.today()`（**宿主本地**日期）作缺省 `end_date`，并原样拼进 `seDate`。宿主时区落后中国（如 UTC-7）时，中国 09-30 上午的公告在宿主仍是 09-29，缺省窗口 `seDate=…~09-29` 拿不到它；修复后 `filing_date` 改按中国本地日，窗口锚点却是宿主本地日，"请求窗口与候选日期同历法"在**缺省窗口路径**上仍不成立（显式窗口路径成立）。同一文件 `resolve_window` docstring 写"生产调用传 `None` 即取当天 UTC 日期"（`cn_form_utils.py:273`），实现却取宿主本地日（`:282`），三者（docstring / 实现 / 新日期语义）口径不一。
- **为什么有问题**：这不是本计划引入的回归（旧代码同样如此），也不影响计划任何验收用例（验收全用显式日期），但它落在已确认 goal「中国本地披露日」的语义外侧却未被登记为 non-goal 或 residual；code review 阶段必然被问"为什么只修一半历法"。按最小 scope 原则，正确处置是显式登记而非本 WU 内扩张。
- **直接证据**：`cn_form_utils.py:254-290`（`today` 缺省 `dt.date.today()`，docstring 与实现不一致）；`cn_download_workflow.py:105/179-180`（`resolve_window` 结果进 `CnReportQuery.end_date`）；`cninfo_downloader.py:551`（原样进 `seDate`）；计划 L16/L37/L41 原文。
- **影响**：缺省窗口最多让发现滞后到宿主日期追上中国日期（不会写错 `filing_date`）；主要风险是 plan/code review 口径不清与后续返工。
- **建议改法和验证点**：在 L16 或 L41 增加一行显式登记："缺省窗口锚点（`resolve_window`/`resolve_period_windows` 的 `today`）取宿主本地日期，本 WU 不改；其与中国本地日的口径差按 residual risk 另立 work unit"，并把 `resolve_window` 的 docstring/实现不一致列为待核事实。若总控决定在本 WU 内修，owner 是窗口 owner（`cn_form_utils`），需同源裁决"缺省 today"取中国本地日还是 UTC，且证据须来自用户窗口语义而非本样本。
- **修复风险**：低（仅登记）/ 中（若改锚点）。
- **严重程度**：低。
