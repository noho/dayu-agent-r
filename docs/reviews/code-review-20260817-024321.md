### 1-未修复-中-different-ticker 并发只证明正确性，未证明计划承诺的"无全局锁"（成功信号 7 / §10.2 test 6 的确定性 barrier 证据缺失）

- **输入场景**: 两个不同 ticker（AAPL/MSFT）的 auto 请求并发执行
- **实际分支**: 两条线程在 converter barrier 汇合（都在 `prepare_upload` 阶段）后各自独立进入 `execute_prepared_filing_publication` → `begin_batch` → fresh read → arbitration → commit
- **预期行为**: 按 plan §3.2 成功信号 7 与 §10.2 test 6 的冻结承诺："两个 publication owner 可同时越过 test barrier 并各自 ok，证明无 global lock"——需要两个 owner 在 batch 段内（`begin_batch` 之后、rollback/commit 之前）同时越过确定性 barrier
- **实际行为**: barrier 只放在 Docling conversion 处。越过 barrier 后即使代码里存在全局锁把两个不同 ticker 的 batch 串行化，两请求仍各自 ok，全部断言照样通过；测试无法区分"并行持有各自 writer"与"串行执行"
- **直接证据**: 测试体（2309-2385 行）中 `_BarrierDoclingConverter(ThreadBarrier(2))` 是唯一同步点，`_run_two_sec_uploads` 只提交线程并取回结果；batch 段无 barrier、无"同时占用"断言。全仓亦无其它"两个不同 ticker 同时持有 writer"的测试（test_fins_storage_atomicity.py 只有单 ticker lock 错误路径用例，无跨 ticker 同时占用用例）。生产代码静态可见无全局锁——shared owner 只消费 per-ticker `BatchingRepositoryProtocol`，`_begin_publication_batch_or_raise`（filing_upload_publication.py:578-603）无任何跨 ticker 协调
- **影响**: 计划冻结的成功信号与测试承诺未被实际证明；若未来引入全局/跨 ticker 锁导致并发退化，测试套件无法察觉。这是证据缺口而非 correctness 缺陷
- **建议改法和验证点**: 在两个不同 ticker 的 `read_filing_upload_state_in_batch` 测试替身中放 barrier（各自 `begin_batch` 后都阻塞在 batch read 上），主线程用两个 Event 确认两个 worker 均已进入 batch 段后再释放，断言两者同时持有各自 writer 并各自 ok；或者 controller 裁决把该成功信号的证明方式降级为静态审查
- **修复风险（低）**: 只改测试，不触及生产
