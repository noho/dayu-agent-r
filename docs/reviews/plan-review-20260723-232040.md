## 2. Findings

### 01-未修复-高-`_pressure_and_decision` stage-independent 无法实现 9-cell matrix

- **位置**：plan §5.5 pressure/action contract；production `context_budget.py:959-984`
- **问题类型**：契约缺失 / 实现缺口
- **当前写法**：plan §5.5 冻结了 9-cell matrix（ORDINARY soft→COMPACT_SOFT_THRESHOLD，
  POST_COMPACT/DISPATCH_FALLBACK soft→ALLOW_DISPATCH），但未显式指出
  `ContextSizingResult.__post_init__` 的验证逻辑（`context_budget.py:535-543`）也需要同步
  修改为 stage-aware
- **反例/失败场景**：implementation agent 修改 `_pressure_and_decision` 接受 stage 参数，
  但忘记更新 `__post_init__` 验证，导致 `ContextSizingResult` 构造时 stage-aware decision
  与旧 stage-independent `_pressure_and_decision` 输出不一致，抛出 `ValueError`
- **为什么有问题**：`__post_init__` 是 `ContextSizingResult` 的构造守门人，它当前调用
  `_pressure_and_decision` 并期望返回值与传入的 `pressure_level`/`budget_decision` 完全
  匹配。如果 `_pressure_and_decision` 变为 stage-aware 但 `__post_init__` 不同步更新，
  所有 POST_COMPACT/DISPATCH_FALLBACK soft 场景构造 `ContextSizingResult` 都会失败
- **直接证据**：`context_budget.py:535-543`
  ```python
  expected_pressure, expected_decision = _pressure_and_decision(
      predicted_input_tokens=self.predicted_input_tokens,
      soft_threshold_tokens=self.soft_threshold_tokens,
      hard_threshold_tokens=self.hard_threshold_tokens,
  )
  if self.pressure_level is not expected_pressure:
      raise ValueError("ContextSizingResult.pressure_level mismatch")
  if self.budget_decision is not expected_decision:
      raise ValueError("ContextSizingResult.budget_decision mismatch")
  ```
  当前 `_pressure_and_decision` 不接受 `stage` 参数，`__post_init__` 也不传 `stage`。
- **影响**：implementation agent 可能只修改 `_pressure_and_decision` 签名而不更新
  `__post_init__`，导致所有 post-compact/fallback soft 构造失败
- **建议改法和验证点**：
  - `_pressure_and_decision` 增加 `stage: ContextSizingStage` 参数
  - `__post_init__` 调用时传入 `self.stage`
  - 测试必须覆盖 9 个 cell 的 `ContextSizingResult` 构造，特别是 POST_COMPACT soft
    应构造为 `pressure=SOFT_THRESHOLD_EXCEEDED, decision=ALLOW_DISPATCH`
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：高

### 02-未修复-中-`_prepare_and_commit_start_in_transaction` post-compact/fallback hard 无 terminal failure

- **位置**：plan §6.5、§8.2；production `dispatch.py:2434-2435`
- **问题类型**：状态机漏洞
- **当前写法**：plan §6.5 要求 "post-compact/fallback hard 均产生 Run terminal fact，
  零 silent accepted Run"，§8.2 exact changes #8 要求 "post-compact/fallback hard 返回
  closed terminal outcome"
- **反例/失败场景**：`_prepare_and_commit_start_in_transaction` 当前对 hard 也返回
  `None`（与 soft 相同），没有调用 `_fail_unstarted_in_transaction`。post-compact hard
  后 Run 静默停在 accepted 状态，无 terminal transition
- **为什么有问题**：这是 Controller adjudication 明确指出的 blocker（"post-compact hard
  不得普通返回 None 让 Run 静默停在 accepted"），但 plan 的 exact changes 只描述了目标
  行为，未明确指出当前 production 代码的 `return None` 是需要修改的具体位置
- **直接证据**：`dispatch.py:2434-2435`
  ```python
  if sizing.budget_decision is not ContextBudgetDecision.ALLOW_DISPATCH:
      return None
  ```
  该行对 soft 和 hard 返回相同结果，没有区分 terminal failure。
- **影响**：implementation agent 可能遗漏该修改点，post-compact/fallback hard 后 Run 无
  terminal fact
- **建议改法和验证点**：
  - `_prepare_and_commit_start_in_transaction` 中，对 POST_COMPACT/DISPATCH_FALLBACK
    stage 的 hard decision 调用 `_fail_unstarted_in_transaction` 并返回 terminal_notice
  - 测试断言 post-compact hard 后 Run status 为 terminal，EventLog 有 Run failure fact
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### 03-未修复-低-plan §5.5 未显式说明 `build_conservative_context_sizing_result` 需要 stage-aware decision

- **位置**：plan §5.5；production `context_budget.py:810`
- **问题类型**：契约缺失
- **当前写法**：plan §5.5 描述了 `_pressure_and_decision` 的 stage-aware contract，
  但 `build_conservative_context_sizing_result` 也调用 `_pressure_and_decision`（行 810），
  plan 未显式说明该函数也需要同步更新
- **反例/失败场景**：implementation agent 修改 `_pressure_and_decision` 但忘记更新
  `build_conservative_context_sizing_result` 的调用
- **为什么有问题**：`build_conservative_context_sizing_result` 是构造 `ContextSizingResult`
  的主要入口，它调用 `_pressure_and_decision` 时也需要传入 stage
- **直接证据**：`context_budget.py:810`
  ```python
  pressure, decision = _pressure_and_decision(
      predicted_input_tokens=predicted,
      soft_threshold_tokens=estimate.soft_threshold_tokens,
      hard_threshold_tokens=estimate.hard_threshold_tokens,
  )
  ```
  未传入 `stage`。
- **影响**：低，因为 plan §5.5 的 contract 描述已足够清晰，implementation agent 应能推断
- **建议改法和验证点**：在 plan §5.5 或 §8.2 exact changes 中显式提及
  `build_conservative_context_sizing_result` 需要传入 stage
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低

## 5. Verdict

**pass-with-risks**

Plan amendment 正确识别并修复了两个 accepted blocker：

1. **compact coverage owner**：`compact_payload.py` 需新增 `current_input_ref`/`compacted_source_refs`
   typed fields，`memory.py` 需按 typed covered refs 过滤 selected window。production 直接
   证据确认当前代码缺失这些字段和逻辑。
2. **stage-aware action**：`_pressure_and_decision` 需接受 stage 参数，实现 9-cell matrix。
   production 直接证据确认当前 stage-independent 逻辑导致 post-compact/fallback soft/hard
   都返回 `None`。

Plan 的 3 slices 结构、两项独立产品修改、schema full-new decision、consumer audit 和
test matrix 均正确。未发现过度设计、compat shim 或 schema ambiguity。

3 个 findings 均为 implementation agent 可自行修复的 low-friction 修改，不构成 blocker：
- finding 01（高）：`__post_init__` 验证需同步 stage-aware，plan §5.5 contract 已隐含
- finding 02（中）：`_prepare_and_commit_start_in_transaction` hard path 需 terminal failure，
  plan §6.5/§8.2 已明确目标行为
- finding 03（低）：`build_conservative_context_sizing_result` 需传入 stage

建议 implementation agent 在开始 Slice 1 前先修复 finding 01–03 对应的 production 代码，
然后进入正常 slice implementation flow。
