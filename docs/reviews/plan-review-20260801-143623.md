## Findings

### 001-未修复-高-F11 reactive compaction terminal writer 不在 S4 allowed files 中

- **位置**: §8.1 Allowed files/modules、§8.2 F11
- **问题类型**: 范围漂移 / 不可直接实施
- **当前写法**: S4 allowed production files 只列 `proactive_compaction.py`、`dispatch.py`、`session_attachment.py`。§8.2 设计只提"proactive paths"（"dispatch.py 内所有可能写 CONTEXT_COMPACTED / CONTEXT_COMPACTION_FAILED 的 proactive 路径"）。
- **反例/失败场景**: 代码证据确认 `engine_ingest.py`（reactive compaction path）也写 CONTEXT_COMPACTED（line 3195）和 CONTEXT_COMPACTION_FAILED（line 3279），且使用相同的 `stale_compaction_result` failure reason（line 2944）。若 reactive 路径存在同样的 duplicate terminal 问题，implementation agent 无法在 S4 内修复它，因为 `engine_ingest.py` 不在 S4 allowed files 中。实现者可能被迫在 S5 再改同一文件，违反 slice 边界。
- **为什么有问题**: plan §1.1 goal 明确包含"compaction terminal/single-flight"的完整修复。冻结裁决 F11 的 I0543 证据虽然来自 proactive 路径，但 reactive 路径使用完全相同的 terminal writer pattern 和 stale_compaction_result reason。plan 的 F11 标题是"同一 compaction operation 出现两个 canonical terminal"——这不区分 proactive/reactive。
- **直接证据**: Agent Explore grep 确认 `engine_ingest.py` 是唯二 terminal writer 之一。S4 allowed files（plan line 397-409）不含 `engine_ingest.py`。§8.2 设计语言只说"proactive paths"（plan line 416）。
- **影响**: implementation agent 跑偏——要么在 S4 越界改 S5 文件，要么漏掉 reactive 路径的 terminal guard，导致 F11 不完整。
- **建议改法和验证点**: 将 `engine_ingest.py` 加入 S4 allowed files，并在 §8.2 设计中显式覆盖 reactive compaction terminal guard。或者在 §8.2 中明确声明 reactive 路径当前不会产生 duplicate terminal（需要提供证据），并将 reactive guard 作为 S5 范围。验证：grep `CONTEXT_COMPACTED`/`CONTEXT_COMPACTION_FAILED` 的全部 append_event 调用点都经过同一 terminal disposition guard。
- **修复风险（低/中/高）**: 低——只需扩展 allowed files 列表并补充设计语言。
- **严重程度（高）**: 高——直接影响 F11 的完整性，且 implementation agent 无法自行判断是否需要改 reactive 路径。

### 002-未修复-中-Ctrl+C idle 状态机对"非空 draft"行为未完全确定

- **位置**: §6.5 状态转移表、§6.5 关键实现要求
- **问题类型**: 状态机漏洞
- **当前写法**: 状态机表只列了"空 draft"的 Ctrl+C 行为（首次重绘、连续第二次 exit 130）。§6.5.3 说"Ctrl+D phase-aware：idle empty buffer 为 EOF；非空按 prompt_toolkit 删除光标下字符/末尾 no-op"——但没有对应的 Ctrl+C phase-aware 说明。
- **反例/失败场景**: oracle interactive.10 说"非空或纯空白 draft 的第一次 Ctrl+C 清空 draft 并留在 composer"。但 plan 的状态机表只覆盖了"空 draft"场景。implementation agent 需要自行推断：非空 draft Ctrl+C 清空后，是否设置 pending exit？如果不设置，用户需要再按一次 Ctrl+C 才能登记退出意图（总共 3 次：清空 + 登记 + exit）。如果设置，用户只需 2 次（清空并登记 + exit）。oracle 说"空 composer 第一次 Ctrl+C 登记退出意图，连续第二次 Ctrl+C 清理后 exit 130"——暗示非空→空的转换不自动登记。
- **为什么有问题**: 两种解读都合理，但实现不同。plan 应该明确非空 draft Ctrl+C 后的 pending exit 状态。
- **直接证据**: plan §6.5 状态表只有 idle + 空 draft + Ctrl+C 行。oracle interactive.10 说"非空 draft 第一次 Ctrl+C 清空"但不提 pending exit。
- **影响**: 实现 agent 可能选择与用户预期不符的实现，需要返工。
- **建议改法和验证点**: 在状态表中增加一行"idle + 非空 draft + Ctrl+C → 清空 draft，不设置 pending exit，仍 idle"。或明确说"清空后立即设置 pending exit"。验证：PTY test 覆盖非空→Ctrl+C→清空→Ctrl+C 的精确行为。
- **修复风险（低/中/高）**: 低——只需在表中增加一行。
- **严重程度（中）**: 中——用户可见行为歧义，但两种实现都不会导致数据丢失或状态不一致。

### 003-未修复-中-S4/S5 对 dispatch.py 的修改可能重叠

- **位置**: §8.1、§9.1 allowed files
- **问题类型**: 过度耦合 / 切片过粗
- **当前写法**: S4 allowed files 包含 `dispatch.py`（F11 terminal guard + F12 single-flight）。S5 allowed files 也包含 `dispatch.py`（F13 identity payload）。两个 slice 都修改同一文件。
- **反例/失败场景**: S4 在 dispatch.py 中引入 `_commit_proactive_compaction_terminal` guard 函数和 `_PreStartGovernanceFlight`。S5 在同一文件中扩展 accepted/rejected event payload 以携带 response_identity。如果 S4 的 guard 函数在 S5 需要扩展以支持 identity payload，implementation agent 可能需要重构 S4 已写的代码。
- **为什么有问题**: 两个 slice 对同一文件的修改有逻辑依赖：S4 的 terminal guard 决定"是否写 event"，S5 的 payload 变更决定"写什么字段"。guard 函数的签名可能需要在 S5 扩展。
- **直接证据**: S4 allowed files（plan line 397）和 S5 allowed files（plan line 494）都包含 `dispatch.py`。
- **影响**: implementation agent 可能在 S4 写的 guard 签名在 S5 需要修改，导致 S4 测试需要更新。
- **建议改法和验证点**: 在 §8.2 设计中预先声明 guard 函数的签名应接受 optional identity payload（即使 S4 暂不填充），或在 S5 设计中明确说明对 S4 guard 的扩展方式。验证：S4 完成后 S5 无需重构 S4 已测试的 guard 函数。
- **修复风险（低/中/高）**: 低——只需在设计中预留签名。
- **严重程度（中）**: 中——增加返工风险但不阻塞实施。

### 004-未修复-低-exit-after-cancel 期间第三次及后续 Ctrl+C 未指定

- **位置**: §6.5 状态转移表
- **问题类型**: 状态机漏洞
- **当前写法**: "cancelling + 后续 Ctrl+C → 只设 exit_after_cancel=true"。"exit-after-cancel → 等当前 cancel target canonical terminal...停止接收新输入...后 130"。
- **反例/失败场景**: 用户在 exit-after-cancel 等待期间再次按 Ctrl+C。plan 说"停止接收新输入"，但这是在 exit-after-cancel 状态设置后的描述。在"cancelling + 后续 Ctrl+C"之后到"exit-after-cancel"之间，如果用户再按 Ctrl+C，行为未指定。
- **为什么有问题**: minor gap。implementation agent 可能合理选择忽略或记录 diagnostic。但 plan 应该明确。
- **直接证据**: 状态表没有"cancelling + exit_after_cancel 已设置 + Ctrl+C"的行。
- **影响**: 低——实现差异不会导致数据丢失。
- **建议改法和验证点**: 增加一行"cancelling + exit_after_cancel 已 true + Ctrl+C → no-op，不取消 cancel task"。或在 §6.5.5 明确说"exit_after_cancel 设置后，后续 Ctrl+C 为 no-op"。
- **修复风险（低/中/高）**: 低。
- **严重程度（低）**: 低。

### 005-未修复-低-F13 repair/multiattempt identity 串线测试描述可更精确

- **位置**: §9.6 Tests
- **问题类型**: 不可直接实施
- **当前写法**: "ordinary/compactor 相邻 attempt 使用不同 engine run/client correlation/provider request id，断言不串线"。
- **反例/失败场景**: implementation agent 需要构造的具体场景是：(1) 一次 ordinary Run 产生 FinalAnswerData with identity A；(2) 同一 Session 触发 compaction，compactor 第一 attempt rejected with identity B；(3) 第二 attempt accepted with identity C。断言 A≠B≠C 且 rejected event 携带 B、accepted event 携带 C。但 plan 没有明确说"ordinary final answer 的 identity 不得出现在 compactor rejected/accepted event 中"。
- **为什么有问题**: "不串线"需要明确定义什么是串线。当前描述只说"不同"，没说"不得跨 attempt 泄漏"。
- **直接证据**: plan §9.6（line 587-588）。
- **影响**: 低——implementation agent 大概率能自行推断，但明确更好。
- **建议改法和验证点**: 在测试描述中增加："每个 rejected/accepted event 的 response_identity 必须来自对应 attempt 的实际 Engine final answer；不得携带前一 attempt、ordinary Run 或相邻 compactor attempt 的 identity"。
- **修复风险（低/中/高）**: 低。
- **严重程度（低）**: 低。
