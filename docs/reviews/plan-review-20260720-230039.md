## Findings

### F-01 — Slice 1 跨 10 个生产文件、4 个架构层，实现 Agent 上下文负担重（accepted-candidate，中）

- **位置**: §7 Slice 1、§6.1 生产代码
- **问题类型**: 切片过粗
- **当前写法**: Slice 1 一次提交完成 Host public contract、validated publish、runtime fanout、public watch union、Service reasoning projection、CLI identity 迁移和 durable reasoning row 删除，涵盖 §6.1 全部 10 个生产文件。
- **反例/失败场景**: 实现 Agent 必须在同一上下文中理解 `EngineEventIngestor._finish_ingest` publish 位点、`_PublicHostHandle` 的 hub composition + merge loop + close 顺序、Service `_drain_watcher` backpressure 传播、CLI renderer identity 迁移 4 个正交关注点。任一关注点的边界条件遗漏（如 `_finish_ingest` 在 `ingest` sync path vs `ingest_async` async path 的 publish 一致性、hub.close() 在既有 `_close_owned_resources` 顺序中的精确插入位置、Service 多个 queue 中哪个需要 bounded）都可能导致运行时缺陷。
- **为什么有问题**: Plan 自身论证 "不能把'删除 reasoning durable row'和'CLI 接入 transient reasoning'分成两个可接受 production commit" 成立——删除 durable 前必须有替代 live path。但 Slice 1 不仅包含这组因果链，还同时包含了 `HostEvent.thinking` 删除、`HostThinkingView` 删除、`HostPreviewEventType.REASONING_DELTA` 删除、`read_api._thinking_from_row` 删除、Service union 分支、CLI identity 迁移。这些删除/迁移虽然与主因果链语义相关，但 **不强制要求在同一 transaction 内原子完成**——完全可以在 Slice 1A（Host hub + public contract + watch union + ingest publish）和 Slice 1B（删除 durable thinking + Service/CLI 迁移）两个切片中实现，且 Slice 1A 本身已是可验证的行为闭环（三类 delta 走 transient path，EventLog delta row 为零，watcher 可接收 HostSessionEvent，只是 Service/CLI 仍消费旧的 HostEvent.thinking）。
- **直接证据**:
  - Plan §7 Slice 1 列出 10 个生产文件，覆盖 Host public API、Host 内部 hub/ingest/dispatch/open_host、Service projection、CLI renderer
  - 文件规模: `engine_ingest.py` 7118 行、`api.py` 3915 行、`dispatch.py` 4904 行、`open_host.py` 1975 行、`entrypoint_runtime.py` 1867 行——合计约 20K 行现有代码，即使修改只触及局部，理解正确行为边界需要跨文件追踪
  - 主总控 Slice 切分原则（`issues-implementation-control.md` §128-151）要求 "slice 必须满足模型上下文窗口与 review 可承载复杂度"
- **影响**: 实现 Agent 可能遗漏跨边界交互（如 close + overflow 组合、ingest sync/async 双路径 publish 一致性）
- **建议改法和验证点**:
  - 方案 A（推荐）: 将 Slice 1 拆为 Slice 1A（Host-only: contract + hub + ingest publish + watch union）和 Slice 1B（delete durable thinking + Service/CLI migration）。Slice 1A 独立验证：三类 delta zero-row、fanout 身份一致性、overflow/detach/close；Slice 1B 独立验证：CLI `--thinking` 回归、Service union 穷举分支。
  - 方案 B（若坚持单 slice）: 在 plan 中显式列出 Slice 1 内部实现的 sub-step 顺序与 sub-step 间 invariant，确保每个 sub-step 完成后行为可观测。
  - 若不拆分：plan 必须在 §7 中增加 "Slice 1 内部 sub-step 与关键 invariant" 段，至少覆盖：先建 hub + contract，再改 ingest publish，再改 watch merge，再删 durable thinking，最后迁移 Service/CLI——并标注每步的独立验证点。
- **修复风险**: 低（拆分不会改变最终行为，只改变中间状态的可验证性）
- **严重程度**: 中

### F-02 — Service bounded relay backpressure 传播链未精确指定，实施者需自行推断（accepted-candidate，低-中）

- **位置**: §12.1 实施风险控制、§8.4 Service/CLI 测试矩阵
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: §12.1 控制措施："新增有名常量 `_ENTRYPOINT_LIVE_EVENT_BUFFER_CAPACITY = 256`，Service relay 同样 bounded，让阻塞最终体现为 Host typed overflow；不得反压 EventLog。" §8.4 测试断言："bounded relay 不吞掉 Host overflow；watch failure 仍走现有 typed diagnostic/outbox terminal fallback，不把 delta 伪装成 terminal。"
- **反例/失败场景**:
  1. Service 当前有多个 `asyncio.Queue()` 创建点（`entrypoint_runtime.py:647,707,719,770`），均为 `maxsize=0`（无界）。实施者需自行判断：是全部改为 bounded，还是只改 `_WatchAndWaitRuntime.queue`？如果改了错误队列（如 startup terminal drain 的内部队列），可能引入不必要的阻塞。
  2. 如果 Service bounded queue 填满、`_drain_watcher` 的 `await queue.put()` 阻塞、进而阻塞 Host watcher `__anext__`、再进而阻塞 Host merge loop、触发 Host subscription queue overflow——这条因果链成立，但 plan 未显式写出。实施者不熟悉 asyncio backpressure 语义时，可能错误地在 Service 侧做 try-except-QueueFull 丢弃，而不是让阻塞自然传播。
  3. 容量 256 在 Service 层作为一个单独常量，与 Host subscription capacity 256 之间的关系（sum、cascade、independent）未说明。如果两个容量相同，Host 256 → Service 256 → CLI 消费，在稳态下 Host queue 先满（因为 Host 是 publisher、Service drain task 是 consumer），但 Service queue 被 drain task 快速清空。压力场景下，CLI 渲染慢 → Service queue 先满 → drain task 阻塞 → Host queue 满 → overflow。Host 先 overflow 还是 Service 先 overflow 取决于 drain task 的处理速度与 put 开销。
- **为什么有问题**: Plan 声明的 Service bounded relay 是慢消费者保护的关键一环——如果 Service relay 实现不正确，慢消费者可能绕过 Host overflow 保护、直接在 Service 层丢事件或死锁。当前 plan 只有意图声明，缺少足够的实施细节让 implementation agent 直接生成正确代码。
- **直接证据**:
  - `entrypoint_runtime.py:647`: `queue: asyncio.Queue[...] = asyncio.Queue()` — 无界队列
  - Plan §12.1: "新增有名常量 `_ENTRYPOINT_LIVE_EVENT_BUFFER_CAPACITY = 256`"
  - Plan §8.4: "bounded relay 不吞掉 Host overflow"
- **影响**: Service relay 实现错误 → 慢消费者场景下 behavior 不符合 plan 预期（可能丢 terminal、可能不抛 Host typed overflow、可能死锁 drain task）
- **建议改法和验证点**:
  - 在 §4.3 或 §12.1 中显式说明 backpressure 传播链：Service bounded queue put 阻塞 → `_drain_watcher` `__anext__` 不再被调用 → Host merge loop 暂停在 `yield` → Host subscription queue 被 publish 填满 → `put_nowait` overflow → detach + `UNAVAILABLE/slow_consumer`
  - 指定受影响的 queue 变量名或 dataclass 字段名：例如 `_WatchAndWaitRuntime.queue` 改用 `asyncio.Queue(maxsize=_ENTRYPOINT_LIVE_EVENT_BUFFER_CAPACITY)`
  - 在 §8.4 中增加一条测试断言："Service bounded queue 满后，Host subscription queue 在 N 次 publish 内触发 overflow"
- **修复风险**: 低（只需补充说明，不改变设计）
- **严重程度**: 低-中
