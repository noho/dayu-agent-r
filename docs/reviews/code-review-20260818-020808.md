## Findings

### 001-未修复-低-tool schema「只支持 FY/H1/Q1/Q2/Q3/Q4」未按 upload_kind 限域，对 material 过度承诺

- **入口/函数**: `_upload_parameters_schema()` 的 `fiscal_period` description（`dayu/fins/tools/upload_tools.py:253-259`）
- **文件(行号)**: `dayu/fins/tools/upload_tools.py:253-259`；对照 `dayu/fins/ingestion_runtime.py:7694-7714`、`dayu/fins/pipelines/docling_upload_service.py:2027-2041`、`dayu/fins/pipelines/sec_upload_workflow.py:474`
- **输入场景**: LLM 调用 `start_fins_upload` 且 `upload_kind=material`，携带闭集之外的 `fiscal_period`（如 `"annual"`、`"9M"`、`"banana"`）
- **实际分支**: material 请求走 `_normalize_upload_request`（`ingestion_runtime.py:7712-7713` 只替换 action，无任何财期校验）；material 管道 `sec_upload_workflow.py:474` 只做 `strip().upper()`，无闭集判定；`build_material_ids`（`docling_upload_service.py:1844`）把该值作为 material document ID seed 持久化
- **预期行为**: schema 文案「只支持 FY、H1、Q1、Q2、Q3、Q4」对两个 upload_kind 均承诺闭集；若对 material 也承诺，则 admission 应拒绝闭集外值；若只对 filing 承诺，则文案应把闭集限域到 filing
- **实际行为**: material 携带任意非空财期文本上传成功，strip+upper 后进入 durable material ID seed 与 source meta；后续 read 路径 `_parse_source_document_meta`（`dayu/fins/tools/read_runtime.py:629`）经 `normalize_fiscal_period` 严格解析会抛 `ValueError`，即该文档的 list/read 会持续失败（上传成功、读取失败的不对称结果）
- **直接证据**: `_normalize_upload_request` 对 `FinsUploadMaterialRequest` 仅 `replace(request, action=action)`（`ingestion_runtime.py:7712-7713`）；`_normalize_optional_upload_fiscal_period` 无闭集校验（`docling_upload_service.py:2027-2041`）；`_parse_source_document_meta` 对 meta 中 `fiscal_period` 调用 `normalize_fiscal_period`（`read_runtime.py:629`，其 `ValueError` 见 `filing_semantics.py:312-313`）
- **影响**: LLM-facing schema 对 material 过度承诺；模型一旦违反承诺值，产生「上传成功但后续读取失败」的 durable 数据，且失败原因与输入字段的因果链被延后到 read 阶段，排障困难。此前该 material admission 缺口为既有问题，但本 slice 新增的「只支持」文案正是该字段唯一的 LLM-facing 闭集承诺处，属于本次变更引入的语义不闭合
- **建议改法和验证点**: 最小修复是把闭集限域到 filing，例如「财报期间。上传 filing 时必填且只支持 FY、H1、Q1、Q2、Q3、Q4；上传 material 时可选。」；同步更新 schema contract 测试的 exact 断言与 `tests/README.md` 的 UF-FIX01 coverage 段。若产品要求 material 也闭集，则应在 material admission owner（非本 slice）补齐校验，并禁止在 schema 承诺前上线文案。验证点：`test_upload_tool_calendar_year_schema_and_usage_messages_are_business_neutral` 中 fiscal_period 断言；root README 无需改动（其新段已正确限域在「上传 filing 时」）
- **修复风险（低）**: 仅文案与对应测试断言；不触碰 admission 逻辑
- **严重程度（低）**: 非 filing 主链路回归；但属于 LLM-facing 契约与实现语义不闭合，且与 read 路径严格解析叠加后有 durable 影响

## Open Questions

1. `_upload_request_summary`（`dayu/fins/ingestion_runtime.py:7806-7811`）对 validated filing 请求持久化的是 raw `fiscal_period`（例如 `"fy"`），而同字段 `action` 用的是 `resolved_action`（resolved 语义）——同一摘要内 raw 回显与 resolved 语义混用，durable record 中的财期与 pipeline 持久化的 canonical 值不一致。该函数只服务于 `start_upload` durable 路径（observed upload 路径不建 durable record），不属于本 slice 的 admission contract，且属既有行为；但「同一业务事实在 durable state 与 storage 中一致」的 owner 约束是否应让摘要改用 `normalized_fiscal_period`，需 controller 裁决（建议 deferred-with-owner）。
