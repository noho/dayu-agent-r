## Assumptions Tested

1. Plan 假设 EventLog 有足够的 durable atoms 支撑 `previous_compacted_view` 构造。
2. Plan 假设 `build_compact_material_pack` 可以在不传 `memory_snapshot` 的情况下从 material view 构造完整 pack。
3. Plan 假设 Slice 1 和 Slice 2 的交接边界是 material view dataclass。
4. Plan 假设 bounded budget 可以通过扩展 `ConversationMemoryProjectionRepairResult` 而不改变 `ProjectionRunner`。
5. Plan 偣设 reactive compact path 的 `memory_snapshot=None` 问题可以在 Slice 2 内最小适配。

## Findings

### 1-未修复-中-`_proactive_represented_evidence_refs` 去重源混合 memory snapshot 与 compact event

- **位置**：Slice 2 "删除或废弃 `_proactive_material_blocks` 与 `_proactive_represented_evidence_refs` 的 governance 拼接职责"
- **问题类型**：架构边界
- **当前写法**：plan 要求 Slice 2 把 `_proactive_represented_evidence_refs` 降级为 source builder 内部 helper，且不读取 memory snapshot。但 plan 在 Slice 1 的 "accepted evidence refs 从 latest compact accepted mapping 排除，不从 memory snapshot 排除" 只描述了目标，没有说明 `_proactive_represented_evidence_refs` 当前同时读取 memory snapshot（`dayu/host/dispatch.py:3708-3717`）和 compact event（`dayu/host/dispatch.py:3718-3720`）的双源去重如何在 Slice 1 builder 内完成。
- **反例/失败场景**：若 Slice 1 builder 只从 compact event 排除 evidence refs，但 memory snapshot 中有 compact event 未覆盖的 accepted evidence（例如 memory projection 在 compact 之后消费了新 evidence），会导致同一 evidence 在 compact material 中重复出现，compactor 看到冗余 material。
- **为什么有问题**：plan 声称 compact material truth 从 EventLog 构造，但 evidence 去重依赖 memory snapshot 中的 `evidence_backed_facts`。这两个真源可能在 projection lag 下不一致。plan 需要明确 builder 的去重策略只依赖 EventLog 还是允许读取 memory snapshot 作为去重辅助（不是作为 truth source）。
- **直接证据**：`dayu/host/dispatch.py:3708-3721` 读取 memory snapshot 和 compact event 双源去重。
- **影响**：implementation agent 不确定 Slice 1 builder 是否可以读取 memory snapshot 做去重；若不读取，可能遗漏已物化的 evidence refs；若读取，违反 plan "Builder 不读取 Conversation Memory snapshot" 的 invariant。
- **建议改法和验证点**：在 Slice 1 的 invariant 或 exact changes 中明确：evidence 去重只使用 latest accepted compact event 的 `accepted_evidence_mapping`，不使用 memory snapshot。若 memory snapshot 有 compact event 未覆盖的 evidence，那是 projection lag 正常状态，由 compact 后 projection 消费后在下一轮 compact 处理。验证点：测试覆盖 compact event 有 evidence mapping 时，builder 输出的 `represented_evidence_refs` 与 compact event 一致，与 memory snapshot 无关。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### 2-未修复-中-Slice 3 budget 接口设计缺少 `ConversationMemoryProjectionCatchupPort` 改造路径

- **位置**：Slice 3 "Exact changes" 和 "catch_up_conversation_memory_projection 接收可选 internal budget"
- **问题类型**：切片过粗 / 接口缺失
- **当前写法**：plan 要求 `catch_up_conversation_memory_projection(...)` 接收可选 internal budget，且 `_MemoryProjectionCatchupPort.catch_up_projection()` 使用 after-commit best-effort budget。但 plan 没有说明 `ConversationMemoryProjectionCatchupPort`（`dayu/host/memory_repair.py:58-103`）当前是 `open_host.py` 注入的 port，它的 `catch_up_projection()` 签名不接收 budget。plan 需要明确：是修改 port 接口、还是在 port 内部 hardcode 默认 budget、还是让 port 构造时注入 budget。
- **反例/失败场景**：implementation agent 可能选择在 `_MemoryProjectionCatchupPort` 内部 hardcode 小 budget，但 `ConversationMemoryProjectionCatchupPort` 是公开注入的 port（虽然不是 public API），其它调用方可能依赖当前无界行为。
- **为什么有问题**：plan 的 Slice 3 allowed files 包含 `open_host.py`，但没有明确 `ConversationMemoryProjectionCatchupPort` 的 budget 注入方式。这个 port 是 `OpenHostOptions` 组装时创建的，修改它需要同时修改 `open_host.py` 的 port 构造和 `memory_repair.py` 的 port 接口。
- **直接证据**：`dayu/host/open_host.py:136-158` 的 `_MemoryProjectionCatchupPort` 调用 `catch_up_conversation_memory_projection` 时无 budget 参数；`dayu/host/memory_repair.py:58-103` 的 `ConversationMemoryProjectionCatchupPort` 构造时只有 `batch_size`。
- **影响**：implementation agent 需要自行决定 budget 注入方式，可能产生不一致的设计。
- **建议改法和验证点**：在 Slice 3 exact changes 中明确：`ConversationMemoryProjectionCatchupPort.__init__` 新增可选 `budget: MemoryProjectionCatchupBudget | None` 参数；`_MemoryProjectionCatchupPort` 构造时传入 best-effort budget。验证点：port 的 `catch_up_projection()` 在 budget exhausted 时不抛异常、不阻断 command path。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

- **为什么有问题**：plan 自己承认 "可不新增该文件"，但把选择权留给 implementation agent。这不是 blocker，但 plan 应该给出更明确的判断。
- **直接证据**：`compact_material.py` 当前是 compact material 的单一 owner，新增 builder 与现有函数有直接数据流关系。

### 4-未修复-中-Reactive compact path 的 `memory_snapshot=None` 适配范围不明确

- **位置**：Slice 2 Allowed files "dayu/host/engine_ingest.py，仅限共享 builder 适配，避免 reactive path 继续分叉"
- **问题类型**：范围漂移 / 切片过粗
- **当前写法**：plan 在 Motivation 和 Design Alignment 中提到 reactive compact 也存在 `memory_snapshot=None` 的 previous view 缺口，但明确 "本 WU 以 pre-dispatch proactive 为主"。Slice 2 的 allowed files 包含 `engine_ingest.py`，但只说 "仅限共享 builder 适配"。
- **反例/失败场景**：`_reactive_compaction_request`（`dayu/host/engine_ingest.py:3575-3617`）当前直接调用 `build_compact_material_pack(..., memory_snapshot=None)`，不经过任何 source builder。如果 Slice 2 只改 proactive path，reactive path 继续用 `memory_snapshot=None`，则 reactive compact 的 `previous_compacted_view` 仍然为空。plan 的 "避免 pre-dispatch 与 reactive 继续分叉" 意图无法实现。
- **为什么有问题**：plan 的 scope risk 已承认 "若共享 builder 适配 reactive 需要大规模 multi-pass 重写，应停止"。但 plan 没有定义 "最小适配" 的边界：是否让 reactive path 也调用 `build_pre_dispatch_compact_material_view`？还是只让 reactive path 从 compact event 读取 previous view？
- **直接证据**：`dayu/host/engine_ingest.py:3592-3598` 的 `build_compact_material_pack` 调用 `memory_snapshot=None`，没有构造 previous compacted view。
- **影响**：implementation agent 可能过度扩展 reactive path 改造，或完全不改 reactive path 导致 "分叉" 继续存在。
- **建议改法和验证点**：在 Slice 2 exact changes 中明确 reactive path 的最小适配边界：reactive path 是否应复用 `build_pre_dispatch_compact_material_view`（需要传入 run + display_text + event_log_store），还是只做从 latest accepted compact event 读取 previous view 的最小 helper。验证点：reactive compact 的 `material_pack.previous_compacted_view` 非空（有 previous compact 时）。
- **修复风险（低/中/高）**：中
- **严重程度（低/中/高/严重）**：中

### 5-未修复-低-`MemoryProjectionCatchupBudget` 的 `timeout_seconds` 判断标准不明确

- **位置**：Slice 3 Internal contract "是否增加 timeout_seconds 由 implementation 证据裁决，若需要 async / clock 注入则停止评估是否过度设计"
- **问题类型**：open question 未收敛
- **当前写法**：plan 把 `timeout_seconds` 作为可选字段，由 implementation 裁决。但 plan 的 stop condition 说 "若需要 async / clock 注入则停止"。
- **反例/失败场景**：memory projection catch-up 是同步循环，不需要 async。但 `timeout_seconds` 需要 clock 注入来测试。如果 implementation agent 选择不加 timeout，只用 `max_batches` 和 `max_scanned_events`，那是否足够？如果 EventLog 单行处理很慢（例如 large payload），`max_scanned_events` 可能不能有效限制时间。
- **为什么有问题**：plan 没有给出 `timeout_seconds` 的必要性判断标准，只说 "由 implementation 证据裁决"。这把设计决策推迟到了 implementation 阶段。
- **直接证据**：plan Slice 3 Internal contract 字段描述。
- **影响**：implementation agent 可能花时间评估 timeout 必要性，或忽略时间维度的风险。
- **建议改法和验证点**：plan 应明确：第一版不加 `timeout_seconds`，只用 `max_batches` + `max_scanned_events`。若后续 production profiling 发现单行处理时间不可控，再追加。这符合 plan 的 "最小化满足需求" 约束。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低

### 7-未修复-低-`PreDispatchCompactMaterialView` 字段 `latest_compacted_event_id` 类型为 `str | None` 但语义需要更明确

- **位置**：Slice 1 "新增 PreDispatchCompactMaterialView"
- **问题类型**：契约缺失
- **当前写法**：`latest_compacted_event_id: str | None` 和 `latest_compacted_event_sequence: int | None`。当为 None 时，表示 session 首次 compact，delta 从 session 起点开始。
- **反例/失败场景**：plan 说 "不存在 latest compact 时从 session relevant cursor 起算"。但 "session relevant cursor" 是什么？是 `run.created_event_sequence`？是 session 的第一个 event？plan 没有定义。
- **为什么有问题**：implementation agent 需要知道首次 compact 时 delta 的起始 cursor。这个值决定了 builder 从 EventLog 读取多少历史。
- **直接证据**：plan Slice 1 Invariants "不存在 latest compact 时从 session relevant cursor 起算"。
- **影响**：implementation agent 可能选择不同的起始 cursor，导致首次 compact material 范围不一致。
- **建议改法和验证点**：明确 "session relevant cursor" 为 session 的第一个 committed canonical fact 的 event sequence，或 `run.created_event_sequence`（取决于 EventLog 中 session 起点的定义）。验证点：首次 compact 时 `post_compact_delta_start_sequence` 等于 session 起点 cursor。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低

## Conclusion

plan 整体架构方向正确，与 design truth source 对齐，scope boundary 和 stop conditions 清晰。7 条 findings 中 0 条 blocker、3 条中等、4 条低。中等 findings 均可通过在 plan 中补充明确说明解决，不需要重写 plan。

plan 是 code-generation-ready 的，但 implementation agent 需要在 Slice 1/2/3 开始前先解决上述 3 条中等 finding 的设计模糊点。建议 controller 裁决是否需要 plan fix gate，或在 implementation gate 中作为 first-slice preflight 处理。
