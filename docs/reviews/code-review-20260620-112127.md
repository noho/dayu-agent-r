## Findings

### 1-未修复-中-reactive acceptance 未断言旧种子 marker 在 recovery dispatch 中被排除

- **入口/函数**: `_assert_reactive_compact_acceptance` (line 3457) / `_deterministic_dropped_old_marker` (line 3712)
- **文件(行号)**: `utils/smoke_host_public_conversation_memory_scenarios.py:3457-3506, 3712-3724`
- **输入场景**: `--suite memory-reactive-compact` 运行完成后，`_SMOKE_REACTIVE_OLD_MARKER` (`DAYU_SMOKE_REACTIVE_OLD_SEED_V1`) 已在 r1 轮作为用户 prompt 注入，Host reactive compact 应根据 policy caps 将旧材料丢弃。
- **实际分支**: `_deterministic_dropped_old_marker(SuiteMode.MEMORY_REACTIVE_COMPACT)` 返回 `None`（line 3720-3721）。`_assert_reactive_compact_acceptance` 内无任何对 `observation.dropped_old_marker` 的检查——它永远不会被执行，因为 `dropped_old_marker is None` 时 `_assert_marker_absent` 不会被调用。
- **预期行为**: Plan 明确要求 reactive suite "old seed marker is dropped or excluded when fallback/compact policy caps require it"（plan line 200-201）。`_SMOKE_REACTIVE_OLD_MARKER` 常量已定义（line 284），但从未被 assertion 消费。
- **实际行为**: Reactive acceptance 静默跳过了旧 marker 排除验证。Smoke 仍然 PASS，但它不证明 Host reactive compact 实际丢弃了旧种子材料。
- **直接证据**:
  - `_deterministic_dropped_old_marker` 对 `MEMORY_REACTIVE_COMPACT` 返回 `None`（line 3720-3721）
  - `_assert_reactive_compact_acceptance` 中无 `dropped_old_marker` 检查（line 3457-3506）
  - Plan line 200-201 明确列出此断言需求
- **影响**: 静默覆盖缺口——reactive compact smoke 不验证 Host 在 compact 后是否确实丢弃了旧材料。如果未来 Host compact policy 变更导致旧材料泄露进 recovery dispatch，本 smoke 不会捕获。
- **建议改法和验证点**: 将 `_deterministic_dropped_old_marker(MEMORY_REACTIVE_COMPACT)` 改为返回 `_SMOKE_REACTIVE_OLD_MARKER`，并在 `_assert_reactive_compact_acceptance` 中对 `recovery` dispatch 调用 `_assert_marker_absent`（仅当 `observation.dropped_old_marker is not None` 时，与 fallback 处理一致）。验证：运行 `DEEPSEEK_API_KEY=test-provider-key python utils/smoke_host_public_conversation_memory_scenarios.py --suite memory-reactive-compact --log-level CRITICAL`，确认旧 marker 确实被排除且 smoke 仍然 PASS。
- **修复风险（低）**: 仅新增 assertion，不改变 smoke 执行路径。如果 Host reactive compact 当前确实保留了旧材料（policy 允许），则 smoke 会在修复后首次失败——这正是 plan 预期的发现。
- **严重程度（中）**: Plan 明确要求此断言但实现缺失。不影响生产正确性（focused tests 已覆盖），但降低了 public smoke 对 reactive compact 材料选择正确性的验收能力。

### 2-未修复-低-fallback pressure 观测与 padding 计算存在近似但可接受的 token 估算不一致

- **入口/函数**: `_fallback_pressure_observation` (line 3372) vs `_compact_pressure_padding_with_reserve` (line 4233)
- **文件(行号)**: `utils/smoke_host_public_conversation_memory_scenarios.py:3393-3397, 4260-4268`
- **输入场景**: fallback suite 运行时，pressure padding 由 `_compact_pressure_padding_with_reserve(options, reserve_tokens=160_000)` 计算，而 pressure 观测由 `_fallback_pressure_observation` 独立计算。
- **实际分支**: Padding 计算使用 `max(MIN_PROMPT_TOKENS, target - reserve - tool)`（line 4265-4268），观测计算使用 `prompt_tokens + tool + reserve`（line 3394-3397）。两者的 `prompt_tokens` 来源不同：padding 的 `prompt_tokens` 来自 `_estimate_chars_as_tokens(len(result))`（在 `_fallback_compact_pressure_padding` 调用 `_compact_pressure_padding_with_reserve` 内部），观测的 `prompt_tokens` 来自 `_estimate_chars_as_tokens(len(_fallback_compact_pressure_padding(options)))`。
- **预期行为**: 观测 token 应等于 padding 内部计算的实际目标 token。
- **实际行为**: 由于 `_estimate_chars_as_tokens` 使用 ceiling division（line 4318: `(char_count + CHARS_PER_TOKEN - 1) // CHARS_PER_TOKEN`），且 `_repeat_to_chars` 可能产生略多于 `target_chars` 的文本（line 4330-4332），观测的 `prompt_tokens` 可能略高于 padding 内部使用的目标值。差异最多为 `DEFAULT_ESTIMATOR_CHARS_PER_TOKEN` 对应的 1 token。
- **直接证据**: `_estimate_chars_as_tokens` ceiling division（line 4318），`_repeat_to_chars` 截断逻辑（line 4332）。
- **影响**: 1 token 量级差异不改变 pressure 落在 soft/hard 之间的判断，但使 pressure 观测不是 padding 计算的精确逆运算。
- **建议改法和验证点**: 可考虑让 `_compact_pressure_padding_with_reserve` 返回 `(padding_text, effective_prompt_tokens)` 元组，观测直接使用返回值而非独立重算。非阻塞，当前实现在实际阈值差距下不会误判。
- **修复风险（低）**: 纯重构，不改 smoke 行为。
- **严重程度（低）**: 不影响 smoke 通过/失败判断，仅在极端边界（pressure 恰好等于 soft threshold）时理论上有 1 token 不确定性——而 plan 已要求 `pressure_tokens < hard_threshold_tokens`（不含等号），安全边际充足。

## Residual Risk

1. **Reactive 旧 marker 排除未验证**（见 Finding 1）。若 Host reactive compact policy 变更导致旧材料泄露进 recovery dispatch，当前 smoke 不会捕获。已由 focused tests（`test_dispatch_scheduler.py`）在 production path 覆盖，但 public smoke 层面存在缺口。

2. **Compactor runner module-level patching**。`_patched_compactor_runner` 修改 `llm_compaction._run_agent_request` 模块全局变量。当前 smoke 是单线程 CLI 工具，实际风险极低。若未来 smoke 脚本被扩展为并发运行多个 suite，需注意 patch scope 隔离。

3. **Fallback pressure padding 对 context window size < 1M tokens 的行为**。`_compact_pressure_reserve_tokens` 对所有 window size 返回相同的 `575_000`（line 4295-4297），但 `_fallback_compact_pressure_padding` 硬编码 `160_000` reserve。如果小窗口模型（如 128K）被配置为 fallback smoke 的 execution profile，pressure 估算可能不准确。当前 smoke 使用 `standard-256k` profile，不受影响。
