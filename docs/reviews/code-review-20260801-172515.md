## Findings

### 01-未修复-低-`_drive_interactive_tty_repl` 中 `InteractiveComposerCompletionResult` 类型别名过宽且仅用于一处

- **入口/函数**: `_drive_interactive_tty_repl` 内部 wait_tasks set 定义
- **文件(行号)**: `dayu/cli/session_execution.py:1237, 1480`
- **输入场景**: 任何 TTY REPL 循环迭代
- **实际分支**: `wait_tasks: set[asyncio.Task[InteractiveComposerCompletionResult]]` 作为类型注解，但该 set 实际包含 `Task[_InteractiveComposerCompletion]`、`Task[int]`、`Task[EntrypointRunTerminalResult]`、`Task[str]` 四种不同具体类型，`InteractiveComposerCompletionResult` 别名定义为 `_InteractiveComposerCompletion | EntrypointRunTerminalResult | str | int` 只是为了通过 pyright 检查。
- **预期行为**: 类型注解应准确反映实际任务类型集合。
- **实际行为**: 使用一个覆盖四种完全不同语义类型的宽联合别名，且该别名仅在 `wait_tasks` set 一处被使用，造成类型误导。
- **直接证据**: 第 1480 行的 `InteractiveComposerCompletionResult = _InteractiveComposerCompletion | EntrypointRunTerminalResult | str | int` 与第 1237 行的唯一使用点。实际代码中每个 task 都是通过 `if X in done: await X` 按具体 task 变量分别处理，宽类型从未被用作统一返回值解构。
- **影响**: 不造成运行时错误（`set` 使用 identity-based `in` 检查），但增加了类型审计负担，使后续维护者误以为这些任务类型在语义上可互换。属于 maintainability 小问题。
- **建议改法和验证点**: 将类型注解改为 `set[asyncio.Task[object]]` 或直接省略泛型参数（让 pyright 推导）；删除第 1480 行的别名定义。不影响任何行为，仅简化类型表达。
- **修复风险（低）**: 纯类型注解变更，无运行时影响。
- **严重程度（低）**: 无 runtime defect，无安全风险，只影响类型可读性。

### 02-未修复-低-OS SIGINT 处理路径中 `sigint_task` 在 `exit_after_cancel` 后仍被重建

- **入口/函数**: `_drive_interactive_tty_repl` 循环尾部 sigint_task 重建逻辑
- **文件(行号)**: `dayu/cli/session_execution.py:1461-1463`
- **输入场景**: exit-after-cancel 路径中 OS SIGINT 已被消费后
- **实际分支**: 第 1453 行的 `accepting_input` 条件正确地阻止了 composer_task 重建（符合 plan "停止新输入"），但第 1461-1463 行 `if sigint_task is None: sigint_task = asyncio.create_task(...)` 没有对应的 guard。在 exit_after_cancel 已为 true 后，sigint_task 仍会被重建。
- **预期行为**: exit-after-cancel 阶段创建新的 sigint_task 是计划内的（用于检测第三次及更多 OS SIGINT 并做 no-op），当前行为是正确的。但 plan §6.5 第 6 条明确说 "第三次及之后一律 no-op；绝不再次发 cancel、Task.cancel() canonical waiter 或强关 Host/attachment"。
- **实际行为**: 当前代码中，第三次及更多 OS SIGINT 确实被正确处理为 no-op（第 1437 行 `elif exit_intent is not _InteractiveExitIntent.EXIT_AFTER_CANCEL` 条件在 exit_after_cancel 已为 true 时为 False，分支不命中，无任何 action）。sigint_task 重建是合理的——它只是等待下一次 OS 信号，不会触发任何副作用。这与 "no-op" 的 plan 语义一致。
- **直接证据**: 第 1461-1463 行无 exit_intent 检查地重建 sigint_task；第 1417-1443 行的 OS SIGINT 处理在 exit_after_cancel 后正确跳过所有副作用分支。
- **影响**: 无运行时缺陷。在 exit_after_cancel 后多创建一个永不产生副作用的后台 task，在 driver 退出时的 finally 被正确清理（第 1467-1468 行）。资源开销可忽略。
- **建议改法和验证点**: 可以考虑为 sigint_task 重建也添加 guard 使意图更明确，但当前行为是正确的。优先级极低，可作为可选 clarity 改进。
- **修复风险（低）**: 若错误添加 guard 可能阻止 exit-after-cancel 后检测到被用户 kill 时做 finally 清理。
- **严重程度（低）**: 无 runtime defect，仅为代码意图显式化建议。

### F05-F09 逐项验证

#### F05 — exact Shift+Enter

- **代码**: `composer.py:27` 定义 `XTERM_MODIFY_OTHER_KEYS_SHIFT_ENTER` 常量；`composer.py:363-379` 的 `c-m` binding 中 `_is_exact_xterm_shift_enter(event)` 严格检查 `len(event.key_sequence)==1`、`key is Keys.ControlM` 和 `data == XTERM_MODIFY_OTHER_KEYS_SHIFT_ENTER`。不满足任一条件时按普通 Enter 提交，不会误判。
- **测试**: `test_ctrl_j_and_exact_xterm_shift_enter_insert_lf_before_submit` 用 pipe input 验证 Ctrl+J 和 exact Shift+Enter 都插入 LF。`test_real_posix_pty_exact_sequences_and_terminal_mode_restore` 在 Darwin/POSIX 真实 PTY 写入 exact bytes 并验证 draft 包含 `\n`，同时验证 ECHO/ICANON/ISIG/IEXTEN 恢复。`test_complete_csi_alt_and_bracketed_paste_do_not_emit_cancel` 参数化覆盖 Up CSI、Alt、bracketed paste，均不被误投影为 cancel。
- **结论**: PASS。exact bytes 识别准确，不猜测未知 CSI-u，不修改 prompt_toolkit 全局 ANSI_SEQUENCES。

#### F06 — non-TTY whole stdin

- **代码**: `session_execution.py:1104-1123` 的 `_read_interactive_non_tty_text()` 使用 `binary_stdin.read()` 一次读到 EOF、strict UTF-8 decode（失败抛稳定错误 `"interactive stdin is not valid UTF-8"`）、`\r\n → \n` 再 `\r → \n`、一次 outer strip。`session_execution.py:1126-1183` 的 `_run_interactive_non_tty_batch()` 空白 batch 直接 exit 0，非空 batch 只创建一个 `QUEUE,target=None` turn。
- **测试**: `test_interactive_non_tty_reads_whole_stdin_as_zero_or_one_batch` 参数化覆盖 empty、whitespace、single line、multiline、CRLF、CR、no-final-newline、literal `0x04` 共 8 种输入。`test_interactive_non_tty_invalid_utf8_is_stable_and_redacted` 验证非法 UTF-8 稳定错误不含 bytes/codec/traceback。`test_interactive_non_tty_exits_after_first_terminal` 参数化覆盖 SUCCEEDED/FAILED/CANCELLED/LOST 后均不进入第二轮。
- **结论**: PASS。one read、CRLF/CR 规范、0/1 Run、无 `dayu>`、literal 0x04 保留、invalid UTF-8 脱敏均已验证。

#### F07/F08 — Escape/Ctrl+C active lifecycle

- **代码**: `composer.py:429-443` 的 Escape binding 使用非 eager sequence resolution（`filter=active_phase`），只在 prompt_toolkit parser timeout/flush 后将 standalone Escape 投影为 `CANCEL_ACTIVE`。`session_execution.py:1684-1722` 的 `_request_interactive_cancel()` 按 `cancel_reason is None` 做 single cancel 去重，run_id 未知时创建 acceptance_task 跨 barrier 等待。`session_execution.py:1417-1443` 的 OS SIGINT 路径与 composer Ctrl+C 共用同一 cancel 入口。
- **测试**: `test_interactive_escape_crosses_pre_acceptance_barrier_once` 使用 `_DelayedAcceptanceControlledHost` 证明 pre-accept Escape 等 exact run id 后只发一次 graceful cancel。`test_interactive_escape_cancels_once_across_active_stages` 参数化覆盖 provider/tool/closeout 三个阶段和 Escape/Ctrl+C 两种 source，均只创建恰好一个 cancel request。`test_interactive_cancel_waiter_failure_propagates_before_submit_terminal` 证明 cancel waiter 先失败时立即传播，不等永不出现的 submit terminal。`test_interactive_ctrl_c_first_cancels_second_exits_and_third_is_noop` 证明 Ctrl+C 三阶段：第一次 cancel、第二次 exit-after、第三次 no-op（waiter 未被 cancel）。`test_interactive_os_sigint_first_second_and_third_follow_same_lifecycle` 证明 OS SIGINT 三阶段与 composer Ctrl+C 一致。
- **结论**: PASS。Escape 仅在 active phase 触发 cancel，完整 CSI/Alt/paste 不误取消。Ctrl+C 三阶段生命周期（single cancel → exit-after → no-op）已被确定性测试覆盖。canonical waiter 从未被 cancel。

#### F09 — type-ahead/sole QUEUE

- **代码**: `session_execution.py:1334-1376` 的 SUBMIT 处理：idle + non-empty → current turn；active + no queued → sole QUEUE follow-up；active + queued occupied → draft 保留并提示。`session_execution.py:1281-1287` 的 terminal 完成后将 sole queued 提升为 current。`session_execution.py:1663-1681` 的 `_promote_interactive_queued_followup()` 复用原 submit/terminal waiter。`session_execution.py:1634-1660` 的 `_create_interactive_submit_task()` 明确 `behavior=FollowupBehavior.QUEUE, target_run_id=None`，绝不 STEER。
- **测试**: `test_interactive_typeahead_creates_sole_queue_and_preserves_rejected_draft` 验证第一个 type-ahead Enter 创建 QUEUE、第二个 draft 保留并输出提示、两个 QUEUE 均 `target_run_id=None`。`test_interactive_terminal_enter_race_submits_exactly_once` 参数化 terminal/Enter 双序，证明两种顺序下最终均有且仅有两个 QUEUE Run。`test_interactive_exit_after_cancel_waits_accepted_sole_queue_terminal` 参数化 queued acceptance 在 exit intent 之前/之后的场景，证明两种情况下 queued Run 均恰好执行一次并终态，exit 130。
- **结论**: PASS。sole QUEUE、不 STEER、恰好一次、draft/cursor 保留、terminal/Enter race 裁决正确均已验证。

### Adversarial failure pass

- **输入攻击面**: non-TTY invalid UTF-8 脱敏（不含 bytes/codec/traceback）；`\r\n`/`\r` 双步规范；literal `0x04` 保留为数据；pure whitespace 不创建 Run。
- **取消竞态**: Escape/Ctrl+C 在 acceptance barrier 前合并为 single cancel intent；acceptance 后的 cancel 使用 generation 去重确保不重复 cancel；第三次及更多 Ctrl+C 均为 no-op；canonical waiter 从不被 Task.cancel()。
- **状态一致性**: `exit_after_cancel` 后 composer_task 不重建（停止输入），但 sole queued submit task 不被取消，必须等其 terminal 后才退出。`normal_completion` flag 区分正常退出与异常取消。
- **资源清理**: `_drive_interactive_tty_repl` 的 finally 块在异常路径正确取消 compose/sigint/acceptance/cancel/submit/queued tasks；正常退出路径（normal_completion=True）跳过 task cancel 因为 terminal 已完整收口。
- **结论**: 未发现可通过静态分析证明的 adversarial failure case。

### Semantic ownership drift pass

- **stdin ownership**: interactive TTY 的 stdin 只有 `PromptToolkitInteractiveComposer` 一个 owner；`RunningKeyMonitor` 收窄为 prompt one-shot 专用。`run_keys.py` 明确标注 "本模块只服务 prompt one-shot，interactive 不使用本模块"。
- **draft/cursor/history ownership**: 完全由 composer 独占；REPL 只消费 typed event，不访问 prompt_toolkit buffer/key types。
- **cancel intent ownership**: `_InteractiveActiveTurn.cancel_reason` 是 single cancel 的真源；`_request_interactive_cancel()` 是其唯一写入者。
- **queued followup ownership**: `_InteractiveQueuedFollowup` 是 sole queued slot 的唯一 holder；`_promote_interactive_queued_followup()` 是其唯一提升者。
- **结论**: 每个关键语义都有唯一清晰 owner，未发现 ownership drift。

### 过度耦合/God function 检查

- `_drive_interactive_tty_repl()` 约 280 行，承载完整 TTY REPL 状态机。plan §6.5 明确要求它是 "唯一竞态裁决者；等待 composer event、OS SIGINT count、current terminal与queued terminal"。该函数虽然长，但职责收敛——它只做 "等待多源事件 → 按固定优先级裁决 → 驱动状态转移" 这一件事。`_start_interactive_turn`、`_request_interactive_cancel`、`_finish_interactive_terminal`、`_promote_interactive_queued_followup` 等私有函数承担明确定义的子职责。
- **结论**: 复杂度在当前 plan 要求的 "单裁决者" 架构下是必要的，不属于过度耦合或 God function。
