## Findings

### F-01 — SEC `_try_fetch_*` auxiliary 三个方法的"全部传播"决策可能过度：部分方法语义上是纯 supplementary，不应操作级 fatal

- **位置**: Amendment §6.5 / §8.4（index JSON, index headers, linked-primary propagation）
- **问题类型**: 目标漂移 (goal drift) — 将"防止 provider error 被误分类"的正确目标过度扩展为"所有 auxiliary HTTP 失败都必须终止 operation"
- **当前写法**: Amendment §8.4 要求: "index JSON, index headers, and linked-primary provider failures propagate and cannot produce empty evidence that later becomes 6-K/XBRL rejection"
- **反例/失败场景**:
  1. `_try_fetch_index_items`（`sec_downloader.py:2061-2098`）的调用方是 `list_filing_files:1431`——它仅在 `include_xbrl or include_exhibits` 时调用，用于收集 XBRL instance、taxonomy 和 exhibit 文件名。当前返回 `[]` 意味着该 filing 下载时缺少 XBRL/展示文件，但 primary document 仍然完整下载成功。将其改为 fatal 意味着：一次 transient `index.json` 失败导致整个 ticker 下载（可能包含多个 filing）全部终止，包括已经成功获取 submissions 的那些 filing。
  2. `_try_fetch_index_header_documents`（`sec_downloader.py:2100-2141`）同理——仅用于 6-K exhibit discovery。
  3. `_try_fetch_primary_linked_html_files`（`sec_downloader.py:2143-2182`）同理——仅用于主文档内的相对 HTML 链接补链。
  4. 这三个方法服务于 `list_filing_files` 的文件列表完整性，而非 candidate discovery/filtering/company resolution。它们的失败不改变"该 filing 是否需要下载"的判断。
- **为什么有问题**: Amendment §6.5 说 "Auxiliary network/protocol failures that can affect resolution, discovery, direction, or filtering propagate as FinsDownloadProviderError." 但 index/headers/linked-html 失败不影响 resolution/discovery/direction/filtering——只影响**单 filing 的文件列表丰富度**。将它们升级为 operation-fatal 与 Stop Condition 4 直接冲突："An allegedly fatal auxiliary response is proven semantically optional; resolve the owner distinction before coding."
- **直接证据**:
  - `sec_downloader.py:1429-1447`：`include_xbrl` 和 `include_exhibits` 控制是否拉取 index；这些是可选项
  - `sec_downloader.py:2091-2096`：`_try_fetch_index_items` catch `RuntimeError` 返回 `[]`，注释只写 "读取 index.json 失败"
  - `sec_downloader.py:2135-2140`：`_try_fetch_index_header_documents` 同理
  - `sec_downloader.py:2173-2178`：`_try_fetch_primary_linked_html_files` 同理
  - 当前 behavior：缺少 index → XBRL 文件缺失但不影响 primary_document 下载 → filing 仍成功
- **影响**: 实现 agent 将三个 supplementary 方法改为 fatal，导致 transient network 错误将整个 ticker 下载终止，引入比当前漏洞更严重的新 regression
- **建议改法和验证点**:
  1. 将 `_try_fetch_*` 三个方法与 browse-ticker、SC13 roles、historical submissions、6-K preview 分开处理
  2. `_try_fetch_*` 保持当前 `[]` 退化但将日志从 `Log.warn(...transport_category=...)` 改为不携带 URL/raw exception 的安全诊断
  3. 在 stop condition 中增加区分: "supplementary file discovery failure" 不属于 "fatal auxiliary"
  4. 验证: 一个 `index.json` 返回 500 时，filing 仍以 primary document 完成下载，日志只含 closed category
- **修复风险（低）**: 只需区分 auxiliary 类型，不需要重写 propagation 逻辑
- **严重程度（高）**: 违反 Stop Condition 4，直接导致行为回归

### F-02 — `_is_cancel_requested` 的 `except Exception` wrap 会吞掉 `FinsDownloadProviderError` 的 typed 类型

- **位置**: Amendment §6.3（CN/HK workflow exception preservation）；`cn_download_workflow.py:431-434`
- **问题类型**: 契约缺失——取消检查路径的异常包裹未在 amendment 中处理
- **当前写法**: `cn_download_workflow.py:431-434`:
  ```python
  except Exception as exc:
      if isinstance(exc, CnDownloadCancelledError):
          raise
      raise RuntimeError(f"取消检查失败: {exc}") from exc
  ```
- **反例/失败场景**:
  1. `FinsDownloadProviderError` 继承链：`FinsDownloadProviderError → RuntimeError → Exception`
  2. `CnDownloadCancelledError` 继承链：`CnDownloadCancelledError → RuntimeError → Exception`
  3. 当 `cancel_checker()` 内部抛出任何非 `CnDownloadCancelledError` 的异常（包括 `FinsDownloadProviderError`）时，被 line 431 的 `except Exception` 捕获，line 432 的 `isinstance` 检查为 False（它不是 `CnDownloadCancelledError`），line 434 将其 wrap 为 bare `RuntimeError`。
  4. 虽然 cancel_checker 通常是元数据读取不太可能抛 provider error，但 `_RuntimeJobCancellationChecker` 读取 job record 可能触发 OSError——这不是 provider error 所以无影响。关键问题在于：如果未来任何实现抛出了 `FinsDownloadProviderError`，它被降解为 generic `RuntimeError`。
- **为什么有问题**: Amendment §6.3 声称 "typed provider, storage, and execution exceptions cross run_cn_download_stream_impl unchanged"，但 `_is_cancel_requested` 在 line 351 的 catch 路径中被调用，其内部 wrap 逻辑与 amendment 的 propagation 目标不一致
- **直接证据**:
  - `cn_download_workflow.py:351`: `except Exception as exc:` → `_build_result(status="failed", message=str(exc))`
  - `cn_download_workflow.py:431`: `except Exception as exc:` → wrap as `RuntimeError`
  - `cn_download_models.py:79`: `CnDownloadCancelledError(RuntimeError)`
  - `download_contract.py:89`: `FinsDownloadProviderError(RuntimeError)`
- **影响**: 中概率低影响——cancel_checker 极少抛 provider error；但若发生则 provider 事实被丢失，runtime 将其映射为 EXECUTION 而非 PROVIDER_TRANSPORT
- **建议改法和验证点**:
  1. 在 `_is_cancel_requested` 中增加对 `FinsDownloadProviderError` 的显式 re-raise（在 `CnDownloadCancelledError` 检查之后）
  2. 或者改为只 catch `Exception` 中非 typed 的部分——但 Python 没有 "catch all except specific subtypes" 语法，需要用 if/raise 实现
  3. 测试: mock cancel_checker 抛出 `FinsDownloadProviderError`，断言它原样传播到 runtime
- **修复风险（低）**: 增加一个 isinstance 检查
- **严重程度（中）**: 边缘 case，但与 amendment 声称的 "unchanged" propagation 目标不一致

### F-03 — CN/HK per-candidate `except Exception`（line 310）将 OSError 的路径暴露在 failed row 的 `reason_message` 中

- **位置**: Amendment §3.2 / §6.3；`cn_download_workflow.py:310-316`
- **问题类型**: 最佳实践偏离——document-local 失败行的安全脱敏不完整
- **当前写法**: `cn_download_workflow.py:310-316`:
  ```python
  except Exception as exc:
      failed_item = _build_candidate_failed_result(
          ticker=normalized_ticker,
          candidate=candidate,
          reason_code=_reason_code_from_exception(exc),
          reason_message=str(exc),
      )
  ```
- **反例/失败场景**:
  1. After the fix, `FinsDownloadProviderError` from downloader has safe `str()` (because `super().__init__(self.safe_message)` at `download_contract.py:134`). ✓
  2. But `OSError` from storage operations inside `run_cn_download_single_filing_stream` (blob write, source meta write) will have `str(exc)` containing filesystem paths.
  3. This `reason_message` goes into the filing result → adapter's `_project_cn_document_row` → `FinsDownloadDocumentResult.reason_message` → eventually public projection.
  4. `FinsDownloadDocumentResult.__post_init__` calls `_validate_public_text` on `reason_message`, which checks for `://` and absolute paths. An OSError message like `[Errno 13] Permission denied: '/home/user/workspace/...'` WILL trigger the absolute path check and fail closed. But an OSError message like `No space left on device` will pass the validator but still contains operational details.
- **为什么有问题**: Amendment §3.2 声称 "The newly typed downloader exception has a fixed safe message when a filing workflow converts it to a row, so it does not leak URL/raw payload." 这个 claim 只对 `FinsDownloadProviderError` 成立；对 `OSError` 从 storage 操作中抛出时不成立。虽然 `FinsDownloadDocumentResult.__post_init__` 的 `_validate_public_text` 提供后防线，但 amendment 没有识别到这个 gap。
- **直接证据**:
  - `cn_download_workflow.py:310`: `except Exception` catches everything
  - `cn_download_workflow.py:315`: `reason_message=str(exc)` — 对 OSError 可能含路径
  - `download_contract.py:251-252`: `_validate_public_text(self.reason_message)` — 后防线，但非绝对
- **影响**: OSError 的文件路径可能通过 `reason_message` → public contract 泄露；`_validate_public_text` 的绝对路径检查提供部分保护但不覆盖所有 OSError 消息模式
- **建议改法和验证点**:
  1. 在 `_build_candidate_failed_result` 调用处对 `reason_message` 做安全包裹：对 `FinsDownloadProviderError` 使用 `exc.safe_message`，对其他异常使用固定安全文本
  2. 或在 `_build_candidate_failed_result` 内部增加安全校验
  3. 测试: 注入 `OSError("Permission denied: /path/to/file")` 到单 filing 下载流程，断言产生的 failed row 的 `reason_message` 不含路径
- **修复风险（低）**: 局部修改 `_build_candidate_failed_result` 行为
- **严重程度（中）**: 信息泄露路径存在，但 `_validate_public_text` 提供后防线

### F-04 — CN/HK downloader `httpx` 异常分类缺乏现有实现基础，amendment 要求从零构建 —— 实现范围可能被低估

- **位置**: Amendment §6.2（CNINFO/HKEX provider owners）
- **问题类型**: 不可直接实施——plan 假定了 CN/HK downloader 已有与 SEC downloader 类似的 typed exception mapping infrastructure，但当前代码没有任何 `httpx` 异常分类逻辑
- **当前写法**: Amendment §6.2 要求 "source-private module helpers that map captured exceptions to FinsDownloadTransportCategory, retryability, and a fixed source-specific safe message"，与 SEC 的 `_sec_transport_category`/`_sec_transport_retryable`/`_sec_transport_safe_message` 相同模式
- **反例/失败场景**:
  1. CNINFO downloader 当前使用 `httpx.Client`（同步），不是 `httpx.AsyncClient`。重试逻辑在 `_http_get_json`、`_http_post_form`、`_http_download_bytes` 中各自实现，抛出 `RuntimeError(f"...url={url} error={last_exc}")`——URL 和 raw exception 内嵌在异常消息中
  2. HKEX downloader 同理
  3. 当前 catch 类型是 `(httpx.HTTPError, json.JSONDecodeError, ValueError)`，没有区分 `TimeoutException`/`NetworkError`/`HTTPStatusError`/`ProtocolError`
  4. 从零构建 typed mapping 需要：重构重试循环以保留 `last_exc` 的类型信息、分离 `httpx.HTTPError` 子类检查顺序（`TimeoutException` IS-A `NetworkError`）、确定 JSON 解析失败归属（当前与 HTTP 错误混在同一 except 子句中）
- **为什么有问题**: Amendment §6.2 的描述粒度假设了与 SEC downloader 相当的 infrastructure 已经存在，但实际上 CN/HK downloader 的错误处理是 pre-typed 的 bare `RuntimeError`。实现工作量被低估。
- **直接证据**:
  - `cninfo_downloader.py:581`: `except (httpx.HTTPError, json.JSONDecodeError, ValueError) as exc:` — 三种异常混合捕获
  - `cninfo_downloader.py:588`: `raise RuntimeError(f"GET JSON 失败: url={url} error={last_exc}")` — URL 和 raw exception 在消息中
  - `hkexnews_downloader.py` 相同的模式
  - SEC 对照 `sec_downloader.py:888-911`: `_sec_transport_category` 使用 `isinstance` 链（需注意异常继承顺序）
- **影响**: Implementation agent 需重写 CNINFO/HKEX 的 retry loop 和异常处理，工作量远超 plan 描述的"添加 source-private helper"
- **建议改法和验证点**:
  1. Amendment 应显式说明 CN/HK downloader 的 retry loop 需要重构（不仅仅是加 helper）
  2. 增加 stop condition: 如果 CN/HK retry loop 重构导致已有测试失败超过阈值，stop 并重新评估
  3. 验证: `httpx.TimeoutException` → `TIMEOUT + retryable`；`httpx.HTTPStatusError(404)` → `HTTP_STATUS + not retryable`；`json.JSONDecodeError` → `PROTOCOL + not retryable`
- **修复风险（中）**: 需要重构两个 downloader 的核心重试逻辑
- **严重程度（中）**: 不是 plan 逻辑错误，但实现范围被显著低估可能导致 implementation agent 跑偏或超时

### F-05 — `_reason_code_from_exception` 未被 amendment 提及，但它是 CN/HK workflow 构建 `status="failed"` 结果的关键依赖

- **位置**: Amendment §6.3；`cn_download_workflow.py:122-128, 332-338, 351-357`
- **问题类型**: 契约缺失——关键 helper 的语义 change 未在 amendment 中说明
- **当前写法**: 多处 `_build_result(status="failed", reason_code=_reason_code_from_exception(exc), message=str(exc))` 调用
- **反例/失败场景**:
  1. Amendment §6.3 说 workflow 不再将 operation-terminal 异常序列化为 `status="failed"`
  2. 但 `_reason_code_from_exception` 是 `cn_download_workflow.py` 的模块级函数（未在已读代码片段中出现但被调用），它接收异常并返回一个原因码字符串
  3. 如果 amendment 的意图是 `FinsDownloadProviderError`/`OSError`/其他异常全部 propagate，那 `_reason_code_from_exception` 在 operation-terminal 路径上变成 dead code
  4. 但如果某些非 typed 异常仍应转换为 `status="failed"`（例如 `ValueError` from form parsing），`_reason_code_from_exception` 仍然需要
- **为什么有问题**: Amendment 没有明确规定哪些异常类型 propagate、哪些仍转换为 `status="failed"`。§6.3 的 "operation-terminal provider, storage, and execution exceptions cross...unchanged" 似乎暗示**所有**三类异常都 propagate，但 `ValueError` 属于 "execution" 也 propagate 吗？如果是，`_build_result(status="failed")` 路径完全变成 dead code。如果不是，amendment 没有给出分类边界。
- **直接证据**:
  - `cn_download_workflow.py:122`: rebuild 异常 → `status="failed"`
  - `cn_download_workflow.py:332`: discovery 异常 → `status="failed"`
  - `cn_download_workflow.py:351`: cancel check 异常 → `status="failed"`
  - 三处都使用 `_reason_code_from_exception(exc)` 和 `message=str(exc)`
- **影响**: Implementation agent 需要自行判断哪些异常 re-raise、哪些转换——amendment 没有给出明确规则，可能导致实现偏差
- **建议改法和验证点**:
  1. Amendment 应增加一个明确的异常分类表：`FinsDownloadProviderError` → propagate；`OSError` → propagate；`CnDownloadCancelledError` → caught + cancelled result；其他 `Exception` → propagate（作为 execution）
  2. 明确 `_reason_code_from_exception` 在 operation-terminal 路径的命运：保留给 document-local 失败行使用，operation-terminal 路径不再调用它
  3. 测试: 注入 `ValueError("invalid form")` → 断言它 propagate 到 runtime 且被分类为 EXECUTION
- **修复风险（低）**: 仅需文档澄清，不需额外代码
- **严重程度（中）**: 缺乏分类边界定义，可能导致实现 agent 做出与 amendment 意图不一致的选择

### F-06 — R01 dead code 清理引入次要 invariant 风险：`discovered_count` 参数删除后函数语义"证明"依赖外部不变量

- **位置**: Amendment §6.1（download contract owner）
- **问题类型**: 最佳实践偏离——删除 defensive check 增加了 future change 的脆弱性
- **当前写法**: Amendment §6.1: "Make `_terminal_disposition_from_counts` exhaustive without a dead final branch"
- **反例/失败场景**:
  1. 当前 `_terminal_disposition_from_counts` 的 line 506 `if discovered_count > 0` 和 line 508 `return FAILED` 构成 defensive pattern：即使不变量被破坏（`discovered_count == 0` 但 `failed_count > 0`），函数仍返回合理终态
  2. 删除 `discovered_count` 参数后，函数变为：
     ```python
     if failed_count == 0: return SUCCEEDED
     if downloaded_count == 0 and rejected_count == 0: return FAILED
     return PARTIAL_FAILURE
     ```
  3. 如果将来有人放宽 `FinsDownloadResultSummary.__post_init__` 的 invariant（例如允许 `discovered_count != sum(dispositions)`），这个函数会静默返回 `PARTIAL_FAILURE` 而非 fail closed
  4. 虽然 code review R01 正确识别了 dead code 可删除，但删除 `discovered_count` 参数是额外的纯粹化——不是必要的
- **为什么有问题**: 当前 defensive 模式不是 bug；它是不变量文档化的运行时见证。删除它降低了系统对 invariant violation 的 resilience
- **直接证据**:
  - `download_contract.py:480-508`: `_terminal_disposition_from_counts` 函数
  - `download_contract.py:330`: `__post_init__` 强制 `discovered_count == sum(counts[1:])`
  - `download_contract.py:349-360`: `__post_init__` 调用此函数且允许 `empty_terminal_override`
- **影响**: 低概率——只有当 `__post_init__` invariant 被放宽时才暴露；但删除 defensive check 使得 bug 的 blast radius 更大
- **建议改法和验证点**:
  1. 保留 `discovered_count` 参数但加注释 `# 由 __post_init__ invariant 保证 discovered_count > 0，此检查为 defensive`
  2. 或删除 line 508 (`return FAILED`) 但保留 `discovered_count` 参数和 line 506 的 `if discovered_count > 0` 检查——这样 invariant violation 时仍 fail closed
  3. 无论哪种方案，同时修改 `from_document_rows` 的调用方（line 408）保持一致
- **修复风险（低）**: 保留参数即可
- **严重程度（低）**: 极低概率场景，但属于可避免的 regression 风险

### F-07 — SEC 6-K precheck 的 `classify_6k_remote_candidates` RuntimeError 传播会改变现有的 per-filing skip 语义，可能与 amendment 的 document-level vs operation-level 边界冲突

- **位置**: Amendment §6.5 / §8.4；`sec_pipeline.py:1727-1732`
- **问题类型**: 过度耦合——单个 filing 的 6-K preview HTTP 失败不应终止整个 ticker operation
- **当前写法**: `sec_pipeline.py:1727-1732`:
  ```python
  except RuntimeError as exc:
      Log.warn(f"6-K 预下载失败: ... error={exc}")
      return False, "DOWNLOAD_FAILED", selected_name
  ```
- **反例/失败场景**:
  1. `classify_6k_remote_candidates` 在 `_precheck_6k_filter` 中——这是 per-filing 的预筛选
  2. 当前行为：6-K preview 失败 → 该 filing 被标记为 `DOWNLOAD_FAILED`（rejection）→ 其他 filing 继续
  3. Amendment 要求此失败 propagate → 整个 ticker 下载终止
  4. 但这与 amendment §3.2 对 CN/HK document-local failure 的处理形成不对称：CN/HK 侧 per-candidate failure 仍然被转为 failed row 并继续，但 SEC 侧 6-K preview failure 变为 operation-fatal
- **为什么有问题**: Amendment §3.2 正确地将 CN/HK 的 per-candidate 失败界定为 document-outcome 语义，但 §6.5 没有对 SEC 6-K preview 做同样的区分。`classify_6k_remote_candidates` 的失败是单 filing 的预筛选失败——它不影响其他 filing。将其升级为 operation-fatal 导致：一个有 20 个 6-K filing 的 ticker，因第 3 个的 preview HTTP 超时而全部失败——包括前 2 个已成功下载的
- **直接证据**:
  - `sec_pipeline.py:1670-1746`: `_precheck_6k_filter` 是 per-filing 方法
  - 调用链: `_run_download_single_filing_stream` → `_precheck_6k_filter` → `classify_6k_remote_candidates`
  - CN/HK 对照: `cn_download_workflow.py:310` per-candidate `except Exception` 仍转换为 failed row
- **影响**: 一个 per-filing 的 HTTP failure 终止整个 ticker download，与 CN/HK 侧的 document-local continuation 行为不一致
- **建议改法和验证点**:
  1. 区分：`classify_6k_remote_candidates` 的 provider failure 应转换为该 filing 的 FAILED row（与 CN/HK per-candidate 一致），而非 operation-terminal
  2. 或：如果确实要 fatal，在 amendment 中显式说明为什么 SEC 6-K preview 与 CN/HK per-candidate 有不对称处理
  3. 验证: 6-K preview HTTP timeout → 仅该 filing 标记为 FAILED，其余 filing 继续下载
- **修复风险（中）**: 需要重新评估 `_precheck_6k_filter` 的异常处理策略
- **严重程度（中）**: 引入 CN/HK vs SEC 的 per-filing failure 行为不对称

### F-08 — 测试计划 8.1 未覆盖 `httpx` 异常继承顺序检查

- **位置**: Amendment §8.1（CNINFO/HKEX transport matrix）
- **问题类型**: 测试缺口——关键 correctness 条件未被测试覆盖
- **当前写法**: "For each provider, inject timeout, connection failure, client/server HTTP status, malformed JSON/protocol response, and an unknown transport exception."
- **反例/失败场景**:
  1. `httpx.TimeoutException` IS-A `httpx.NetworkError` IS-A `httpx.HTTPError`
  2. 如果 CN/HK helper 的 `isinstance` 顺序写错（先检查 `NetworkError` 再检查 `TimeoutException`），timeout 会被误分类为 CONNECTION 而非 TIMEOUT
  3. SEC downloader 的 `_sec_transport_category` 顺序正确（TimeoutException 在 NetworkError 之前），但 CN/HK helper 是从零构建的——没有现有代码可对照
- **为什么有问题**: Amendment §8.1 的测试描述仅要求"注入各类异常并断言分类"，但未要求验证 `isinstance` 检查顺序——这是同一组输入但不同代码顺序可能产生不同输出的场景
- **直接证据**:
  - `sec_downloader.py:903-911`: 正确的顺序——TimeoutException before NetworkError
  - httpx 源码: `class TimeoutException(NetworkError)`
- **影响**: 如果 implementation agent 写错顺序，timeout 被误分类为 CONNECTION——测试仍通过（因为测试只注入一种异常类型），但 production 中 `httpx.TimeoutException` 被 `isinstance(exc, httpx.NetworkError)` 先捕获
- **建议改法和验证点**:
  1. 在 §8.1 的 transport matrix 中增加 "exception hierarchy ordering" 测试：注入 `httpx.TimeoutException` 并断言分类为 TIMEOUT（不是 CONNECTION），明确要求 helper 检查顺序为 TimeoutException → NetworkError → HTTPStatusError → ProtocolError
  2. 增加一个 cross-check：同时注入 `httpx.NetworkError`（非 TimeoutException 子类）断言为 CONNECTION
- **修复风险（低）**: 增加两个测试用例
- **严重程度（低）**: 如果 helper 写对则无影响，但测试不保证写对

## 专项压测结果

### 1. CN/HK operation 与 document-local failure 边界

**PASS with F-03 note.** Amendment §3.2 正确排除了 `cn_download_filing_workflow.py`。
Operation-terminal 异常（discovery/company/rebuild/cancel-check failure）正确识别为

在 excluded scope。F-03 的 OSError 泄露风险是 document-local 路径的 residual gap，
不影响 operation-terminal 的 provenance 修复。

### 2. Provider typed exception 被 filing workflow 消费的情况

**PASS with F-05 note.** After fix, `FinsDownloadProviderError` 在 per-candidate loop
（`cn_download_workflow.py:310`）被 `except Exception` 捕获并转换为 failed row。
`str(exc)` 返回 `safe_message`（因为 `super().__init__(self.safe_message)`），
所以 row 的 `reason_message` 是安全的。这是正确的 document-local 消费语义。

在 operation-terminal 路径（line 332, 351），amendment 要求 propagate——这意味着
这些 `except Exception` 块需要重构以 re-raise typed exceptions。F-05 指出分类边界
未明确。

### 3. OSError/ValueError/cancellation 传播与 broad catch

**PASS with F-02 note.** 异常继承链验证:
- `FinsDownloadProviderError → RuntimeError → Exception`
- `CnDownloadCancelledError → RuntimeError → Exception`
- `SecDownloadCancelledError → Exception`（NOT RuntimeError——独立继承链）
- `SecUserAgentConfigurationError → FinsDownloadProviderError → RuntimeError`

`_is_cancel_requested`（`cn_download_workflow.py:431`）的 wrap 逻辑在 F-02 处理。
`collect_cn_download_result_from_events`（`cn_pipeline.py:164-189`）无 try/except——
异常直接通过 async generator propagation 到达 runtime。这是正确的。

Runtime `_run_direct_stream_producer`（`ingestion_runtime.py:2739-2771`）catch `Exception`
然后调用 `_download_public_failure_from_exception` 做正确的 closed 映射：
`FinsDownloadProviderError → PROVIDER_TRANSPORT/CONFIGURATION`、`OSError → STORAGE`、
其他 → `EXECUTION`。验证通过。

### 4. httpx 异常类顺序、4xx/5xx retryability、JSON/protocol/PDF 错误归属

**SEC 侧 PASS；CN/HK 侧 OPEN (见 F-04).**

SEC downloader `_sec_transport_category` 顺序验证:
1. `httpx.TimeoutException` → TIMEOUT (checked first ✓)
2. `httpx.NetworkError` → CONNECTION (checked second ✓)
3. `httpx.HTTPStatusError` → HTTP_STATUS (checked third ✓)
4. `httpx.ProtocolError` / `ValueError` → PROTOCOL
5. 其他 → UNKNOWN

`_sec_transport_retryable`: 4xx → False, 5xx → True ✓
`_http_get_json` 的 `handled_exceptions=(httpx.HTTPError, ValueError)` —— JSON 解析失败
被正确分类为 PROTOCOL ✓

CN/HK 侧目前使用 `(httpx.HTTPError, json.JSONDecodeError, ValueError)` 混合捕获，
没有子类区分。Amendment §6.2 要求构建 typed mapping——需要从零实现。
`_http_head_meta`（`cninfo_downloader.py:636-657`）catch `httpx.HTTPError` 返回
`CnReportHeadMeta(content_length=None, ...)` ——按 amendment 的 "optional HEAD only for metadata"
分类，这是正确的 optional degradation。

PDF magic bytes 校验在 `hkexnews_downloader.py` 的 `_PDF_MAGIC_BYTES`——这属于
protocol 验证，应分类为 PROTOCOL（non-retryable）。Amendment §6.2 正确包含此分类。
