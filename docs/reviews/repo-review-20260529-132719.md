### 1-严重-Audit JSONL 文件写与 DB marker 不在同一事务导致回滚时产生重复行

- **入口/函数**: `LogAuditSink.apply_event` → `insert_audit_sink_marker_if_absent`
- **文件(行号)**: `dayu/host/audit.py:232-238`
- **输入场景**: Audit projection consumer 处理 EventLog canonical fact，marker 检查通过，构建 audit line，append 到 JSONL 文件，然后 DB transaction 内的 marker insert 或 checkpoint advance 失败导致事务回滚。
- **实际分支**: `_append_line(line)` (行 232) 在 `insert_audit_sink_marker_if_absent` (行 233) 之前执行。`_append_line` 是对文件系统的写入，不参与 SQLite 事务。
- **预期行为**: JSONL line 和 DB marker 要么同时存在，要么都不存在（原子持久性）。
- **实际行为**: JSONL 已写入文件（不可回滚），但 DB marker 未提交。下次 catch-up 重放该 event 时，marker 检查返回 None，再次构建 line 并追加到 JSONL，产生重复行。
- **直接证据**: `audit.py:232 self._append_line(line)` 在事务内但不在 DB 事务边界内；`audit.py:233-238` 之后才写 marker。
- **影响**: Audit JSONL 在恢复场景下产生重复行，违反 append-only audit log 的去重要求。
- **建议改法和验证点**: 先写 marker（事务内），再写 JSONL（事务外）。验证：模拟 DB commit 失败场景，检查 JSONL 是否有重复行。
- **修复风险（中）**: 调整写入顺序需确保 JSONL 写入失败不影响 marker 已提交事实。
- **严重程度（严重）**:

### 4-严重-stale-heartbeat 默认探针无法检测 PID 复用真 orphan

- **入口/函数**: `recovery.py:329` → `recovery_process.py:267` `_classify_stale_owner`
- **文件(行号)**: `dayu/host/recovery_process.py:308-343`, `dayu/host/recovery_process.py:70-115`
- **输入场景**: Host 进程 A crash，操作系统将 PID 回收给新进程 B。恢复扫描发现 Run owner heartbeat 已 stale，但 PID 仍存活（被 B 占用）。`StdlibPidLivenessProbe` 不采集 `observed_start_token` 和 `observed_boot_id`。
- **实际分支**: `evidence.exists` 为 True（PID 存活），`observed_start_token` 恒为 None，所有身份比对分支被跳过。唯一产生 positive proof 的路径只有 `not evidence.exists`（PID 不存在）。返回 `OrphanProofInconclusive(PID_LIVE_WITHOUT_IDENTITY)`。
- **预期行为**: 应能通过进程 start_token 或 boot_id 不一致判定 PID 已被复用，确认为 positive orphan proof。
- **实际行为**: 返回 inconclusive，被 `_classify_active_or_cancelling` 的 inconclusive 分支捕获，Run 保持 RUNNING/CANCELLING 但 worker 已真实死亡，Run 永久挂起。
- **直接证据**: `StdlibPidLivenessProbe.collect()` 中 `observed_start_token` 恒为 `None`，`observed_boot_id` 恒为 `None`；`_classify_stale_owner` (line 308-343) 仅在 PID 不存在时产生 positive proof。
- **影响**: 生产环境中 PID 复用场景下真 orphan 无法被检测。桌面 Linux/macOS（PID 回收频繁）和容器环境下均有发生可能。
- **建议改法和验证点**: 为 `StdlibPidLivenessProbe` 添加 `/proc/<pid>/stat` 的 starttime 采集用于身份验证，或将 "PID 存活但无身份证明" 从 inconclusive 升级为 positive proof（heartbeat stale 本身就暗示异常）。
- **修复风险（中）**: 需要跨平台进程身份采集方案。
- **严重程度（严重）**:

### 未发现实质问题的领域

以下方面经过逐行追溯，确认处理正确：

1. **架构导入纪律**: `dayu.runtime` 零反向依赖；`dayu.contracts` 零 upper layer import；所有 `getattr` 使用（3 处）均有明确书面理由。5 层 import boundary 测试全面守护。
2. **SSE 行级缓冲**: `_line_carry` 正确处理跨 chunk 边界行断点。
3. **`[DONE]` 终态处理**: 先于 JSON 解析，与 `_finalize_success` 通过 `_terminated` 互斥，无双重终态。
4. **ToolCallAggregator 双键路由**: 原生 index 优先 → id 回退 → position 兜底，三段式覆盖 OpenAI 流式协议的各种归属形态。
5. **stream_idle_timeout 三方 race**: pending/cancellation/heartbeat 的 WaitOutcome 处理正确，heartbeat 到点不取消 pending task。
6. **取消安全**: `_RunnerInterrupted` 顶层统一捕获；`finally: response.release()` 在所有异常路径执行。
7. **重试"已产出事件不重试"防护**: `attempt_yielded_event` 标志正确阻止部分内容已提交后的重试。
8. **幂等设计**: `event_id` 去重 + scope/idempotency_key 去重 + drain request 幂等 + `BEGIN IMMEDIATE` 事务保护，多层防护。
9. **错误分类体系**: `classify_exception` 通过 `raise TypeError` 确保仅已知异常类型被归类，关闭了静默分类未知异常的安全漏洞。

## Open Questions

1. **截断 cursor 跨 attempt 持久性**: `TruncationManager` cursor 存在内存 dict。Attempt 被暂停后 resume，新 attempt 创建新 `TruncationManager`，cursor 全部丢失。`fetch_more` cursor 是否应在 resume 后仍可用？
2. **duplicate governance registry 清理时机**: `InMemoryRunScopedDuplicateGovernanceRegistry` 按 `run_id` 持有内存索引，Run 结束后无明确清理时机。内存是否持续增长？
3. **LaneController clock 同步依赖**: `_LaneClock` 使用 `time.monotonic() + datetime.now(UTC)` 锚点。进程 suspend/resume 后 clock 落后，是否需 wall-clock 双保险？
4. **多 drainer 并发排空语义**: 是否有计划支持多 drainer？若否，建议明确文档声明单 drainer 设计。
5. **StdlibPidLivenessProbe 定位**: 当前默认探针是"安全但保守"的临时实现还是生产就绪方案？若为后者需补充 `/proc` 级别 start_time 采集支持 PID 复用检测。
6. **RECOVERING Run 超时**: 当前无 "RECOVERING Run 超时自动转 LOST" 机制。若 recovery dispatch 始终无法调度，Run 永久卡在 RECOVERING。
7. **Compaction budget_after_compact 准确性**: 使用 `chars_per_token=3` 保守估算，实际 LLM 差异可能导致估算与实际差距较大。是否需要根据实际 usage observation 校准？
8. **Position 回退路由（OLD 兼容路径）**: 是否所有 provider 都不再产生无 index 且无 id 的后续 arguments delta？是否可移除此兼容路径？

## Residual Risk

1. **生产环境对真实 LLM 响应的行为（高风险）**: 系统对真实 LLM 提供者错误/格式错误响应的行为从未在 CI 中测试。所有 LLM 路径被 monkeypatch 或脚本化 runner 替换。
2. **压缩正确性（高风险）**: LLM 压缩器产生的事实摘要、固定状态补丁和证据引用仅通过 fake 压缩器测试。这些决策影响持久化状态、内存投影和未来 run 执行。
3. **PID 复用 orphan 漏检（高风险）**: 默认探针在 PID 存活时无法区分新旧进程，生产环境中真 crash 可能漏检。
4. **发件箱交付一致性（中等风险）**: 发件箱公共 API 稀疏测试 + drain 批量 UPDATE 缺 CAS → 投递重复或丢失可能未被发现。
5. **并发下的操作安全性（中等风险）**: lane 系统、恢复扫描器和调度器从未在真实并发下测试。跨进程竞争条件在生产环境可能表现为罕见、不可重现的故障。
6. **ProjectionRunner 单 event 事务粒度（中等风险）**: 每个 event 在独立事务内处理。同 consumer 多个 event 间无事务保证——cold JSONL 写入失败导致部分已处理、部分未处理。
7. **Flaky 测试回归（中等风险）**: 97 个基于 sleep 的同步点和 202 个 monkeypatch 调用使 CI 脆弱。
8. **Schema 迁移（低风险）**: 当前 policy 将 schema 变更视为全新系统，无迁移测试。
9. **Cancellation helper watcher 泄漏（低风险）**: finally 块中的 await 可被外层 CancelledError 中断。
