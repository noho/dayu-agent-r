## Findings

### 1-未修复-中-`_RuntimeTerminalChecker.is_terminal` 全量加载 RunEvent

- **入口/函数**: `HostToolRuntime.execute_tool_call` -> `_default_manager.fetch_more` -> `terminal_checker.is_terminal`
- **文件(行号)**: `dayu/host/_tool_runtime.py:180-184`
- **输入场景**: LLM 调用 `fetch_more` framework 工具时触发
- **实际分支**: `is_terminal` 调用 `event_store.list_events(run_id=run_id, after=None)` 获取该 run 的**全部** RunEvent，然后 `reversed` 线性扫描
- **预期行为**: 终态检查应使用 O(1) 或 O(log N) 的终态标志查询，而非全量加载
- **实际行为**: 对于长 run（多轮对话 + 大量工具调用），每次 `fetch_more` 都会加载全部事件到内存
- **直接证据**: `_tool_runtime.py:180` — `events = await self.event_store.list_events(run_id=run_id, after=None)`；`_tool_runtime.py:181` — `for event in reversed(events)`
- **影响**: 长 run 场景下 `fetch_more` 延迟随事件数线性增长；内存压力随 run 长度增加。当前 `fetch_more` 由 LLM 发起、频率有限，且 cursor TTL 为 300 秒，所以实际触发频率不高，但设计上属于 O(N) 热路径中的冷操作
- **建议改法和验证点**: 在 `RunEventStore` 或 `DurableRunEventStore` 上增加 `is_terminal(run_id) -> bool` 方法，利用已有 SQLite 索引做单行查询；或在 attempt 终态时写入一个内存标志位供 `RuntimeTruncateManager` 读取
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Residual Risk

1. **`_runtime_truncate_manager.py` 的 `binary_bytes` 策略补读路径**：集成测试未覆盖 base64 编码的 chunk 续读行为，仅靠 `_build_chunk` 的类型守卫间接保证。
2. **`_run_harness.py` 的 `_task_aware_event_stream` drain 窗口**：`_TASK_AWARE_STREAM_DRAIN_SECONDS = 0.05` 是启发式值，在极端慢 I/O 场景下可能导致最后几个事件丢失。当前设计通过 EventLog 持久化保证数据不丢，但 stream 订阅方可能收不到最后事件。
3. **CI 无 check**：PR 显示 `no checks reported on the 'migration/host-p8-5-stabilization' branch`，无法确认 pyright / pytest 是否在 CI 中通过。
4. **Engine SSE parser malformed usage fix**（`sse_parser.py:438-443`）：这是一个真实 correctness fix，旧代码在 malformed usage 后 `return` 但未设置 `_fatal_terminated` / `_terminated` 或 yield `RunnerDoneData(ERROR)`，导致 parser 无 terminal event。新代码正确修复。对应测试 `test_sse_usage_malformed_after_tool_delta_is_fatal` 已覆盖。
