## Findings

### 1-未修复-[低]-§33 未钉死 workflow `requested_action` 事件字段的取值来源，两种合规读法产生分歧的用户可见事件载荷

- **位置**: 契约与实施决策 §33（"`requested_action` 事件字段如保留原始请求表示，须与 canonical/resolved action 的含义分别明确，不能另起动作判定规则"）；测试 §47（façade 变体输入断言未覆盖该字段）。
- **问题类型**: 契约缺失（精度缺口，非设计错误）
- **当前写法**: §33 要求 workflow 消费 owner 返回的 canonical action 做 delete 分支选择与 `resolve_upload_action` 入参，"不得再传 raw literal auto 或自行映射 auto"；对事件载荷中的 `requested_action` 只说"如保留原始请求表示……不能另起动作判定规则"，未说明现有规范化行（sec_upload_workflow.py:487、cn_pipeline.py:1103，`str(action or "").strip().lower() or None`）是保留为展示投影、改为 raw 原样、还是改用 owner 返回值。
- **反例/失败场景**: 独立 façade 调用 `SecPipeline.upload_material(action="AUTO", files=[ok.pdf])`：保留 487 行 → 事件 `requested_action="auto"`（现状）；改 raw 原样 → `"AUTO"`；改用 owner 返回值 → `None`。三种实现互不相同且都"合规"于 §33 字面；后续 gate 评审任一选择都可能判另一种为跑偏，造成返工。同理空串输入下"保留 487"得 `None`、"raw 原样"得 `""`。
- **为什么有问题**: 事件载荷是用户可见契约；plan 应 code-generation-ready，不应把用户可见字段的取值留给实施者临场三选一。该字段今日不参与任何判定（修复后 delete 分支与 resolve 均用 canonical），故无论哪种选择都无正确性风险，但跨实现分歧真实存在。
- **直接证据**: sec_upload_workflow.py:487（规范化行）、:507（事件载荷 `requested_action`）、:580/:608（结果载荷同名字段）；cn_pipeline.py:1103/:1123 同构；plan §33 原文；grep 确认现有测试不断言 material 事件 `requested_action`（无兼容固化风险）。
- **影响**: 实施 Agent 自裁用户可见事件字段取值；后续 review 争议或返工；不影响判定正确性、持久化事实与 goal 目标。
- **建议改法和验证点**: plan 一句话钉死二选一——(a) 推荐：保留 487/1103 行作为请求展示投影（维持现状事件语义，明确其不再是判定依据），或 (b) 事件 `requested_action` 改用 raw 入参原样。并在 §47  façade 变体测试（`"AUTO"`/`" auto "`/空串）补一条 `requested_action` 期望值断言锁定所选语义。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
