## Findings

### 1-未修复-低-transaction runner 在 COMMIT 失败后连接可能进入脏状态

- **入口/函数**: `HostTransactionRunner.run_write()`
- **文件(行号)**: `dayu/host/durable/transaction.py` (276-312)
- **输入场景**: SQLite COMMIT 失败（极罕见，如磁盘满、IO 错误），且后续 ROLLBACK 也失败
- **实际分支**: `finally` 块在 COMMIT 失败后执行 `_active_transaction_count -= 1`，计数器归零；但 `_rollback()` 内部（第 497-500 行）仅捕获 `sqlite3.Error` 并静默返回，若 ROLLBACK 失败，SQLite 连接仍可能持有 active transaction
- **预期行为**: COMMIT 失败后，如果 ROLLBACK 也失败，应将连接标记为不可用或强制重置
- **实际行为**: 计数器归零但 SQLite 连接可能仍持有 active transaction；下一次 `run_write` 调用 `BEGIN IMMEDIATE` 会失败（"cannot start a transaction within a transaction"），且该错误不是 SQLITE_BUSY/SQLITE_LOCKED，不会触发重试，直接抛出 `HostDurableError`
- **直接证据**: 第 288 行 `_active_transaction_count -= 1` 在 `finally` 块中；第 497-500 行 `_rollback` 捕获 `sqlite3.Error` 后静默返回
- **影响**: 极低概率触发；一旦触发，当前 `HostTransactionRunner` 实例的所有后续写操作都会永久失败，需要重建连接（Host 重启）
- **建议改法和验证点**: 在 `_rollback` 失败后检测连接状态并标记 runner 为不可用；或将 `_active_transaction_count -= 1` 移到 COMMIT 成功之后。验证点：构造 COMMIT 失败 + ROLLBACK 失败的 mock 场景
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低（极罕见触发条件，但一旦触发影响不可自愈）

### 2-未修复-低-run_read 复用 write 重试策略参数

- **入口/函数**: `HostTransactionRunner.run_read()`
- **文件(行号)**: `dayu/host/durable/transaction.py` (324-326)
- **输入场景**: 读事务遇到 SQLITE_BUSY
- **实际分支**: `run_read` 使用 `self._sqlite_policy.write_busy_retry_count`、`write_retry_initial_delay_seconds`、`write_retry_backoff_multiplier`、`write_retry_max_delay_seconds`
- **预期行为**: WAL 模式下读-读不冲突、读-写冲突概率远低于写-写冲突，读事务可以用独立的重试配置
- **实际行为**: 读事务与写事务共用同一套 `write_` 前缀的重试参数，语义不精确但功能正确
- **直接证据**: 第 325-326 行引用 `self._sqlite_policy.write_busy_retry_count` 和 `write_retry_initial_delay_seconds`
- **影响**: 功能无影响；代码可读性上 `write_` 前缀用于 read path 容易造成误解
- **建议改法和验证点**: 为 `HostSQLiteStoragePolicy` 增加 `read_busy_retry_count` / `read_retry_initial_delay_seconds` 等字段，或在 `run_read` 中使用独立的重试配置
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低（纯配置/命名问题，不影响正确性）

### 3-未修复-低-StdlibPidLivenessProbe 不采集进程身份信息导致 macOS 上 orphan proof 能力受限

- **入口/函数**: `StdlibPidLivenessProbe.collect()`
- **文件(行号)**: `dayu/host/recovery_process.py` (73-115)
- **输入场景**: Host 进程崩溃后 PID 被新进程复用，startup recovery 扫描到 stale heartbeat
- **实际分支**: `collect` 只用 `os.kill(pid, 0)` 检测 PID 存在性，始终返回 `observed_start_token=None`、`observed_boot_id=None`；在 `_classify_stale_owner` 中，PID 存活但无法提供 identity proof，落入 `OrphanProofInconclusive`
- **预期行为**: 当 owner heartbeat 已超过 stale 阈值且 PID 被新进程复用时，应能通过进程身份比对得出 positive orphan proof
- **实际行为**: 在 macOS 上，PID 存活时永远返回 inconclusive，recovery 不会自动触发，Run 永久卡在 RUNNING 状态
- **直接证据**: 第 109-114 行返回 `observed_start_token=None`、`observed_boot_id=None`
- **影响**: 在 macOS 开发环境中，Host 崩溃后 PID 被复用的场景下，旧 Run 无法自动 recovery。Linux 上可通过 `/proc/<pid>/stat` 获取 start_time 来缓解
- **建议改法和验证点**: 为 `StdlibPidLivenessProbe` 补充平台适配的进程身份采集（Linux: `/proc/<pid>/stat` start_time；macOS: `proc_pidinfo` 或 `kinfo_proc` 的 `kp_proc.p_starttime`）
- **修复风险（低/中/高）**: 中（需要平台特定实现）
- **严重程度（低/中/高/严重）**: 低（仅影响开发环境，生产环境通常有 liveness probe）
