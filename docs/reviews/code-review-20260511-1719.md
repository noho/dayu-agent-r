### 02-未修复-中-raw payload side-store 无清理策略

- **入口/函数**: `put_run_input_raw_payloads`
- **文件(行号)**: `dayu/host/_run_input_raw_payload_store.py:26-48`
- **输入场景**: 每次 attempt 启动前无条件写入 2 条记录（`input_messages` + `tool_schemas`），compact retry 路径同样写入
- **实际分支**: DDL 无 `created_at` 索引、无 TTL 列、无 cleanup job
- **预期行为**: 有生命周期的存储应有清理策略或至少有便于后续清理的索引
- **实际行为**: 表会随 session 数量无限增长，大 context 场景下每条 payload 可达数百 KB
- **直接证据**: `_run_input_raw_payload_store.py:26-48` DDL 无索引；`_run_harness.py:2332-2341` 每次 attempt 前无条件写入
- **影响**: 长期运行的数据库中该表无限增长，最终影响存储和查询性能
- **建议改法和验证点**: 至少为 `created_at` 添加索引；增加基于 session 过期的 cleanup 策略（如删除已 terminal 且超过 N 天的 session 的 raw payload）
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Residual Risk

1. **可观测性降级**: 旧代码通过 7 种 RunEvent 类型记录截断生命周期完整轨迹。新代码将截断内化为 tool result payload 的一部分，EventLog 不再有截断专属事件。调试截断问题只能依赖 tool result JSON 中的 hint 字段和 VERBOSE 日志。
2. **内存态 cursor 数据放大**: `_RuntimeCursorRecord.data` 存储完整原始数据，cursor 生命周期内（默认 300 秒 TTL）内存占用与原始数据量线性相关，无上限保护。
3. **`_RuntimeTerminalChecker` 性能**: 每次 `fetch_more` 调用触发全量 EventLog 扫描（O(n)），在长生命周期 run 下可能成为瓶颈。既有问题，非本次引入。
4. **repair 路径 startup 延迟**: 大库场景下 `_conversation_memory_durable.py` repair 两次全表扫描加数万次 JSON decode，可能阻塞 startup 数秒。
5. **PartialToolCallSummary 传播链路**: Runner -> Engine -> EventLog -> trace JSONL 全链路已验证正确，但 Host 序列化层缺少 round-trip 测试。
6. **`_EXPLICIT_CREDENTIAL_KEYS` 边界**: 不覆盖 `session_token` / `refresh_token` / OAuth token。当前无实际泄漏路径，但未来若有新工具使用这些字段，需人工扩展。
7. **Breaking schema changes**: `ToolTruncationInfo` 移除、7 种 RunEvent 类型移除、`RunInputContextSnapshotBuiltData` 字段重命名。均符合 CLAUDE.md "全新 schema 起库" 约束，但需确认部署流程覆盖。
