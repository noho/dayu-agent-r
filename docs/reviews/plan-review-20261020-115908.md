## Material findings

### P1-部分修复-中-Host `fetch_more` 为单次使用，计划中的“小 limit 连续取回余量”无法按既有契约执行

- **位置**: plan §6.1 第 8 项（当前版第 177 行）；关联 §3.2（第 102 行）与 §5 工具层范围（第 148 行）。
- **问题类型**: 契约缺失 / 验证缺口 / 计划与既有 API 事实冲突。
- **当前写法**: §6.1-8 要求“测试驱动实际 `fetch_more`，以小 limit 和每次新返回的参数连续取回余量，直到当前页无待续内容”；§3.2 要求模型“先按本次返回的 `fetch_more` 参数取齐当前页，再用 `next_start` / `next_offset` 继续下一页”。
- **反例/失败场景**: Host 截断 `text` 后，模型看到 `{truncated:true,value:<可见前缀>,fetch_more:{cursor,scope_token}}`。若它按计划用一个小 `limit` 调用 `fetch_more`，Host 只返回剩余文本的前缀并立即消费唯一 cursor；返回结果没有新的 cursor/scope_token。模型再调用 `fetch_more` 会得到 `truncation cursor is missing or no longer available`，本 Fins 页的剩余内容无法继续取回。若模型随后按 `next_start` 读下一页，被 Host 截掉的当前页尾部会永久丢失，正好复现 P1 要消除的静默漏读。
- **为什么有问题**: 该写法把 `fetch_more.limit` 当成可分页续读的单位，但 Host 的当前契约是“cursor 单次使用 + 一次补读取回全部余量（省略 `limit`）或仅取前缀”。计划同时要求“不新增 Host 状态机/自建 cursor”，因此不能通过修改 Host 来支持“每次新返回的参数连续取回”。这也会让 LLM-facing schema 的命令产生歧义：模型可能主动传小 `limit`，从而丢失本页余量。该句是本轮 P1 修订新增；旧版只要求保留工具层截断元信息与 Fins 页范围，没有这条不可执行的连续补读指令，因此属于本次变更触发的新问题，不是旧问题重复。
- **直接证据**:
  - `dayu/host/tool_runtime.py:1946–1951`：`TruncationManager` 文档明确“所有 cursor 都是单次使用；一次 `fetch_more` 成功后即失效，不支持分页式多次补读同一个 cursor”。
  - `dayu/host/tool_runtime.py:1091–1096`：`FetchMoreRequest.limit` 为“可选补读上限；无则返回全部剩余内容”。
  - `dayu/host/tool_runtime.py:2085–2099`：`fetch_more` 调用 `_fetch_more_value(cursor.remaining_ref, request.limit)`，随后 `if cursor.single_use: self._cursors.pop(...)`，返回值为普通 `ToolResultSuccess`，不含新 cursor。
  - `dayu/host/tool_runtime.py:6096–6097`：`TextCharsRemainderRef` 在给定 `limit` 时只返回 `remaining_text[:limit]`。
  - `tests/host/test_toolruntime_truncation_fetch_more.py:311` 与 `:453`：既有测试分别固定“cursor 单次使用”和“limit 只返回剩余前缀”。
- **影响**: 实施 Agent 若照计划写测试，会遇到无法连续取回余量的失败；若为了让测试通过而修改 Host，则超出“不新增 Host 状态机/自建 cursor”的已确认边界。若新工具 schema 沿用“按参数取齐当前页”的模糊表述，真实模型也可能传小 `limit` 后丢失当前页尾部，联合验收无法证明“先取齐当前页再按 `next_start` 前进”的契约。
- **建议改法和验证点**:
  1. 将 §6.1-8 改为：调用一次 `fetch_more`，省略 `limit`（现有契约返回全部剩余内容；或使用 `limit >= 余量`），将可见前缀与返回余量拼接，断言精确等于该 runtime 页原文；然后再按 `next_start` 读下一页。删除“以小 limit 和每次新返回的参数连续取回余量”的表述。
  2. 若仍要验证 `limit` 前缀语义，应作为既有 Host 单次使用契约的独立断言（取前缀后 cursor 失效），不能把它放入“取齐当前页”的联合路径。
  3. 在 §3.2/§5 的 LLM-facing 说明中补一句：本页未显示内容用**一次** `fetch_more` 取回；`limit` 分段会消耗唯一 cursor，不能用于取齐本页；`cursor/scope_token` 只续读本次调用被截内容。
  4. 不要求修改 Host；验证点用现有 `fetch_more` 契约与新增联合测试即可，不需新增状态机或 cursor。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。
