### 详细分析

#### 1. Empty/Corrupt PDF+DOCX/Mixed 原子失败真链

**empty filing chain**：`_build_original_assets` 逐文件 `read_bytes()` → filing 零字节 → `canonicalize_fins_public_file_label(raw_basename)` → `fins_upload_empty_input_failure(file_label)` → `FinsUploadFailureError(failure)` → workflow `except FinsUploadFailureError` → `_build_*_filing_failure_event(failure_reason=exc.failure)`。整条链无 fallback、无字符串重分类、converter calls = 0、batch begin = 0。

**corrupt filing chain**：`_build_pending_assets` 逐文件 `convert_to_json_bytes()` → `DoclingConversionError` → `canonicalize_fins_public_file_label(raw_basename)` → `fins_upload_failure_from_exception(exc, file_label)` → `FinsUploadFailureError(failure) from exc` → workflow same typed catch。`__cause__` 保留，原始 exception text 不泄漏到 public reason。

**mixed filing**：fail-fast 设计——首个 bad 文件立即 raise，后续文件不转换。测试覆盖 bad-first（converter calls = ["bad.pdf"]）与 valid-before-bad（converter calls = ["valid.pdf", "bad.docx"]）两种模式。SEC 与 CN/HK 各有独立 workflow 级 mixed 测试，断言 batch begin/commit/rollback = 0、company/source stage = 0、published tree 为空、terminal stored = 0。

**判定**：原子失败链完整，真链上每个节点均直接证据可追溯。

#### 2. FinsUploadFailureReason 五字段 closed schema 与唯一 typed owner

**schema**：`kind`、`code`、`message`、`retry_hint`、`file_label`——exact five-field frozen dataclass。`__post_init__()` 调用唯一 `validate_fins_public_file_label`，拒绝未 canonicalize 的 label。

**唯一 typed owner**：`FinsUploadFailureReason` 是 failure reason 的唯一构造点。所有 producer（`fins_upload_failure_from_exception`、`fins_upload_empty_input_failure`、`fins_upload_prevalidation_io_failure`、`fins_upload_prevalidation_corruption_failure`）均通过该构造点产出 reason，无旁路。

**typed exception**：`FinsUploadFailureError(RuntimeError)` 携带已校验的 `failure` 属性，workflow 通过 `exc.failure` 直接投影，不进入 `_classify_direct_error` 或 `_safe_direct_error_message`。

**parser**：`upload_failure_reason_from_json` exact-key 校验 `frozenset(value) == _FAILURE_KEYS`（5 keys），拒绝旧四字段 JSON；label 原样传入 constructor，由 `__post_init__` validator 校验。测试证明 parser 不复制 label 规则。

**判定**：五字段 closed schema 契约完整，typed owner 唯一。

#### 3. direct_events label canonicalizer/validator 语义

**canonicalizer** `canonicalize_fins_public_file_label(raw_basename)`：
- 普通安全 basename（如 `report.pdf`）→ 原样保留
- fragment（如 `job_id_notes.pdf`，命中 `_DISALLOWED_TEXT_FRAGMENTS` 中 `"job_id"`）→ 固定隐藏标签
- 中文（如 `财报正文.pdf`，命中 fragment `"财报正文"`）→ 固定隐藏标签
- Unicode Cc/Cf（如 `U+202E`）→ `unicodedata.category()` 检测 → 固定隐藏标签
- 超长（>240 chars）→ 固定隐藏标签
- pathful（含 `/` 或 `\`）→ ValueError 拒绝
- 空/dot-segment → ValueError 拒绝

**validator** `validate_fins_public_file_label(value)`：
- `_HIDDEN_PUBLIC_FILE_LABEL` → 接受
- 普通安全 basename → 接受
- 需要隐藏的 basename → 拒绝（"必须先经过 canonicalizer"）
- pathful/empty/dot-segment → 拒绝

**语义是否符合计划**：计划要求"普通 basename 原样保留；命中 fragment/public guard、Unicode Cc/Cf 或长度超过 240 时投影固定标签；pathful、空与 dot-segment 输入拒绝"。实现完全对齐。

**是否过度隐藏**：`_public_file_label_requires_hiding` 对合法安全 basename（如 `report.pdf`、`annual_report_2024.pdf`）不触发隐藏。只有真正不安全的输入才被隐藏。测试覆盖了普通 basename 原样保留的正向路径。

**判定**：canonicalizer/validator 语义严格符合计划，不过度隐藏。

#### 4. workflow/runtime/direct 是否仅消费 typed projection、无字符串重分类

**SEC workflow**：`except FinsUploadFailureError as exc:` → `failure_reason=exc.failure`。monkeypatch 禁用 `fins_upload_failure_from_exception` 后测试仍通过，证明 typed exception 不穿透到 generic mapper。

**CN/HK workflow**：同形 `except FinsUploadFailureError as exc:` → `failure_reason=exc.failure`。monkeypatch 禁用后测试仍通过。

**ingestion_runtime._upload_result_details**：从 `summary.failure_reason`（已校验的 `FinsUploadFailureReason`）机械投影 `kind.value`、`code.value`、`message`、`retry_hint`、`file_label`。无字符串分类、无 fallback、无重计算。

**direct RESULT**：`test_direct_upload_typed_failure_projection_bypasses_string_classifiers` monkeypatch 禁用 `_classify_direct_error` 和 `_safe_direct_error_message` 后，typed reason 仍正确产生 `error_message`、`retry hint`、`file` details。证明 direct 路径不进入字符串分类。

**判定**：workflow/runtime/direct 全链路仅消费 typed projection，无字符串重分类。
