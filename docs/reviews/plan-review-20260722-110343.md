## Findings

### F-01 — needs-evidence — 中 — `resolve_wait` 被排除在 mutation gate 外，但可通过 wait resolution 间接触发 Run 状态迁移

- **位置**: Plan §5.2 Mutation classification，明确将 `resolve_wait` 列入不 gate 列表；design doc §27 recovery scan path 将 `WAITING` Run 保持在 `WAITING` 并恢复 wait adapter observation
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: Plan 5.2: `resolve_wait` 是"已存在durable wait的background continuation，不是UI新Session mutation"，不 gate。Design 27: recovery scan 对 `WAITING` Run "只恢复 wait adapter observation"
- **反例/失败场景**:
  1. A (RW) 提交 Run X，X 进入 `WAITING`
  2. A detach（mutex 释放）
  3. B (fresh RW) attach，recovery scan 对 X 分类为 `WAITING`，恢复 wait observation
  4. B 的 wait poller 收到结果，通过 `resolve_wait` 触发 `RUN_STARTED(start_reason=recovery)` → 创建新 Attempt → dispatch
  5. 此时 B 在没有显式用户 submit 的情况下推进了 Run X 的状态迁移
  6. 这与 design doc 的设计一致（recovery 是正确行为），但 plan 将 `resolve_wait` 归为"不需要 gate"与"不推进治理"之间存在语义张力

  更关键的 race：
  1. A (RW) 提交 Run X，X `WAITING`
  2. A detach，B (fresh RW) attach recovery scan 将 X 分类为需等待
  3. A 的旧 wait poller（detach 后仍存活直到 scheduler close）收到结果并调用 `resolve_wait`
  4. A 的 scheduler 已经 detach（不应 promotion），但 A 的 durable actor 仍在运行
  5. `resolve_wait` 的 after-commit wake 到达 A 的 scheduler → A 的 scheduler 已无 work lease → drop
  6. B 的 periodic reconciliation 应在 `dispatch_poll_interval_seconds` 内发现并 promotion
  7. **但这是 liveness gap**：如果 A 的 wait poller 在 detach 后、scheduler close 前收到结果并成功 resolve，terminal 已写入但 promotion 被 drop

- **为什么有问题**: plan 将 `resolve_wait` 简单归类为"不 gate"是正确的语义判断（它是 background continuation），但未分析 detach 后旧 opener 的 wait poller 仍可能 resolve 并产生 after-commit wake 被旧 scheduler drop 的 liveness gap。这不是 gate 缺失问题，而是 wake routing 问题。
- **直接证据**:
  - Plan §5.2: "resolve_wait：已存在durable wait的background continuation，不是UI新Session mutation" → 不 gate ✓
  - Plan §5.5: "terminal producer触发旧scheduler promotion时，旧registry无RW会drop。当前RW opener通过下面的bounded periodic reconciliation推进queued work" → 已预判此场景
  - 但 plan 没有分析 `resolve_wait` 成功后产生的 terminal 是否也会经过同一 drop-then-reconcile 路径
  - `dispatch.py` 中 terminal notice coordinator 在 closing 时 drop notice（`open_host.py:425-427`）
  - Design doc §27 recovery scan 明确 `WAITING` Run 保持 `WAITING`，不创建 Attempt — 这意味着 wait result 到达后不是 recovery 路径而是正常 resolve 路径
- **影响**: 中等。在最坏情况下，detach 后的 wait result 可能在 `dispatch_poll_interval_seconds` + 一次 durable retry 延迟后才被 promotion，而不是立即处理。这不是正确性 bug（结果最终会处理），但 plan 的 liveness 分析不完整。
- **建议改法和验证点**:
  1. Plan §5.5 应显式说明 `resolve_wait` 的 after-commit promotion wake 也会经过同一 drop→reconcile 路径
  2. 测试应覆盖：A detach 后 A 的 wait poller resolve → terminal 写入 → B periodic reconcile 在 poll interval 内 promotion
  3. 验证点：assert B 在 `dispatch_poll_interval_seconds * 2` 上界内推进
- **修复风险（低）**: 仅需补充 plan 分析和测试覆盖，不改变架构
- **严重程度（中）**

### F-02 — accepted-candidate — 中 — 同 handle 重复 attach 与多 UI 共享 handle 时 attachment mode 语义存在歧义

- **位置**: Plan §5.1 "一个Host handle对同一Session至多一个RW record；该handle再次attach得到RO，除非先关闭原RW并fresh attach"
- **问题类型**: 架构边界 / 契约缺失
- **当前写法**: Plan §5.1 声明 capability 是"当前 Host handle 对该 Session 是否存在 live ACTIVE RW attachment"，每个 handle 至多一个 RW record
- **反例/失败场景**:
  1. UI 持有 Host handle H
  2. H.attach_session("S1") → RW attachment A1
  3. 同一 H.attach_session("S1") → 按 plan 应返回 RO attachment A2（因为已有一个 RW record）
  4. 此时 H 对 S1 同时持有 A1(RW) 和 A2(RO)
  5. 用户调用 H.submit_followup("S1", ...) → gate 检查"当前 Host handle 对该 Session 是否存在 live ACTIVE RW" → 存在(A1) → 放行 ✓
  6. 用户调用 A1.aclose() → RW record 释放，A2 仍为 RO
  7. 用户调用 H.submit_followup("S1", ...) → gate 检查 → 无 live ACTIVE RW → PERMISSION_DENIED
  8. **但是**：用户可能期望"我关了 RW attachment 后应该能重新提交"——这是正确行为，用户需要先 close A2 再 fresh attach

  真正的问题场景：
  1. 同一 handle 先 RW attach → 再 RO attach（同 Session）
  2. 用户可能混淆两个 attachment 对象的语义
  3. Plan 未定义 `HostSessionAttachment` 对象是否可独立使用（如 `attachment.submit_followup(...)` 还是必须通过 Host handle）
  4. Plan 明确选择后者（"capability 是当前 Host handle 对该 Session 是否存在 live ACTIVE RW attachment"）——这是正确的
  5. **但歧义在于**: 用户拿到 RO attachment 对象后，调用 Host handle 的 submit —— gate 如何知道用户"意图"使用哪个 attachment？
  6. 答案: gate 不关心意图，只看 registry 中是否有 live RW record —— 这是正确的设计

  真正的 material 问题：
  1. Plan §5.1: "不把attachment对象传入每个command；capability是'当前Host handle对该Session是否存在live ACTIVE RW attachment'"
  2. 这意味着 gate 检查 `registry.has_active_rw(session_id)` 而不是 `caller_holds_rw_attachment(session_id)`
  3. **但**：如果同一 handle 对 S1 同时有 RW(A1) 和 RO(A2)，用户 close A1 后 RO(A2) 仍存活
  4. 用户此时调用 submit → gate 检查 → 无 RW → 拒绝
  5. 但用户手中仍持有 A2 对象，可能误认为"我有 attachment 为什么被拒绝"
  6. 这是 UX 问题而非正确性问题，但 plan 未说明 RO attachment 对象在 RW 释放后的"存在但无用"语义

- **为什么有问题**: attachment mode 作为 per-object public 承诺（每个 `HostSessionAttachment` 有不可变 mode）与 Host-handle 级 mutation gate（只看 registry 全局状态）之间缺少一个明确的 bridge 说明。plan 的设计是正确的，但未充分解释这种"对象 mode 不可变但 gate 看全局"的语义对调用方意味着什么。
- **直接证据**:
  - Plan §5.1: "不把attachment对象传入每个command"
  - Plan §4: "capability是'当前Host handle对该Session是否存在live ACTIVE RW attachment'。这使调用方不能伪造attachment/mode，access truth仍只由registry产生"
  - Plan §1.1: "attachment mode在attachment生命周期内不可变"
  - Design doc §9: "mode 在该 attachment 生命周期内不可变"
- **影响**: 低至中。不影响正确性，但可能在 CLI/Service integration 时造成调用方困惑。plan 需要在 §5.1 或 §5.9 中增加说明：RO attachment 对象在 handle 仍有 RW 时是"观察者"角色，在 RW 释放后是"过期观察者"——其存在不授予写权限，其 mode 终身不变。
- **建议改法和验证点**:
  1. Plan §5.1 应增加: "同一 handle 对同 Session 同时持有 RW 和 RO 时，mutation gate 只看 registry 全局 RW record 是否存在；RO attachment 对象本身在任何时刻都不授予写权限"
  2. CLI integration test: 同 handle 先 RW attach → 再 RO attach → close RW → submit 被拒 → close RO → fresh attach 成功
- **修复风险（低）**: 仅需澄清语义，不改变设计
- **严重程度（中）**

### F-03 — accepted-candidate — 中 — detach 后旧 scheduler pre-start governance 的"drain 边界"不精确

- **位置**: Plan §5.4 状态迁移: "drain已进入actor的mutation和尚未形成stable Attempt owner的pre-start work"；§5.5: "existing Attempt继续由原execution owner管理"
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: Plan §5.4: 旧 scheduler "不得再为该 Session 接受新用户 command、启动新的 unowned Run governance 或 promote 下一 Run"；§5.5: "lease覆盖到Attempt+dispatch record在同一事务稳定创建或pre-start operation terminal/fallback完成为止"
- **反例/失败场景**:
  1. A (RW) 的 scheduler 正在 `_run_pre_start_governance` 中执行 proactive compaction
  2. compaction 的 `CONTEXT_COMPACTION_REQUESTED` 已写入（在事务内），但 compactor LLM call 尚未完成（事务外）
  3. A detach → drain 等待 pre-start work 收口
  4. LLM compactor 返回结果 → A 的 scheduler 尝试写入 `CONTEXT_COMPACTED`
  5. **此时 A 的 work lease 是否仍有效？** Plan 说"lease覆盖到...pre-start operation terminal/fallback完成为止"
  6. 如果 lease 在 detach drain 期间仍然有效 → A 的 scheduler 可以完成 compact → 正确
  7. 如果用户 cancel 了 detach 等待（caller cancellation） → Plan §5.4: "caller取消只取消等待，close task继续"
  8. **但**: 如果 Host close（不是 attachment close）触发，Plan §5.4 的 Host close 顺序是 "registry begin-host-close → ... → registry drain/close全部attachment并释放mutex（scheduler仍活着让pre-start收口）→ scheduler close"
  9. 这意味着 Host close 时 scheduler 先 drain pre-start 再 close — 顺序正确

  真正的问题场景：
  1. A detach S1 → drain 开始
  2. A 对 S2 仍有 RW attachment
  3. S1 的 pre-start work（proactive compaction）持有 work lease
  4. 该 work lease 阻止 S1 mutex 释放 → 正确
  5. **但**: plan 未定义 work lease 是否有 timeout 或上界。如果 LLM compactor 调用超长（例如 5 分钟），detach 会被阻塞 5 分钟
  6. Plan §11.2 residual risk 2 承认 "graceful detach必须等待已经开始的provider call按既有Runner timeout/cancellation收口"
  7. 但没有讨论：如果 provider call 没有 timeout（或 timeout 极大），detach 是否会无限阻塞
- **为什么有问题**: plan 的 drain 语义依赖"pre-start work 最终会 terminal"，但没有定义 drain 的上界或 forced cancellation 策略。这是设计选择（安全优先于延迟），但 plan 应在 invariants checklist 或 residual risks 中显式记录这个 tradeoff。
- **直接证据**:
  - Plan §5.4: "lease覆盖到...pre-start operation terminal/fallback完成为止"
  - Plan §11.2 risk 2: "graceful detach必须等待已经开始的provider call按既有Runner timeout/cancellation收口，不能为了缩短等待提前unlock"
  - Plan §10: "lease跟随底层Future/task，而非caller awaiter；caller cancellation不释放资源"
  - Design doc §9: "drain已进入其durable actor的Session command，并停止/收口尚未形成stable Run/Attempt execution owner的pre-start governance（包括事务外proactive compaction），然后才可释放mutex"
- **影响**: 中等。正常操作下 Runner timeout 提供上界。但在极端情况下（Runner timeout 配置极大或缺失），detach 可能长时间阻塞。plan 已意识到此风险但未提供上界保证。
- **建议改法和验证点**:
  1. Plan §11.2 应增加 detach drain 的最坏情况上界分析（基于 Runner timeout + max_compaction_attempts_per_operation * per-call timeout）
  2. 测试: 验证 provider call 超时后 detach 能完成（不永久阻塞）
  3. 如果当前 Runner 无强制 timeout，plan 应记录这是 pre-existing risk
- **修复风险（低）**: 仅需补充分析和测试
- **严重程度（中）**

### F-04 — accepted-candidate — 中 — cancel reconcile 依赖 "durable cancel link 在 Run terminal 后仍可读"，但当前 durable schema 未保证此 invariant

- **位置**: Plan §5.8 "即使Run已被另一scheduler watchdog置为CANCELLED，durable cancel link仍须可读"
- **问题类型**: 状态机漏洞 / schema drift
- **当前写法**: Plan §5.8: "只接受dispatch owner等于本scheduler host instance且identity完全相同的target"；"即使Run已被另一scheduler watchdog置为CANCELLED，durable cancel link仍须可读"
- **反例/失败场景**:
  1. A (RW) 提交 Run X，worker 在 A 的 scheduler 中运行
  2. B (fresh RW) cancel Run X → durable cancel 写入，`CANCEL_REQUESTED` appended
  3. B 的 watchdog 立即 closeout：CAS `CANCELLING` → `CANCELLED`，`RUN_CANCELLED` appended
  4. A 的 scheduler 在 poll interval 内 reconcile：读取 cancel link
  5. **问题**: 如果 B 的 watchdog 在 A reconcile 之前已将 Run 置为 `CANCELLED` terminal，A 读取到的 Run 状态是 `CANCELLED`
  6. Plan 要求 "durable cancel link仍须可读" — 这意味着即使 Run terminal 了，cancel request 的 fact 仍必须可查询
  7. **当前代码**: cancel link 通过 EventLog 中的 `CANCEL_REQUESTED` fact 表达。该 fact 在 Run terminal 后不会被删除（EventLog 是 append-only）
  8. 但: dispatch.py 的 cancel watchdog closeout 在 CAS 成功后直接写 `RUN_CANCELLED` 并 clean up — 当前 watchdog 逻辑在 `dispatch.py` 中
  9. **关键问题**: plan 要求 owner scheduler "读取Run cancel request link" —— 这具体是什么 durable query？
  10. Plan §5.8 提到 `read_cancelling_runs_for_session` 用于 watchdog，但 owner reconcile 需要的是 "给定 exact (run_id, attempt_id, execution_id)，该 Run 是否被 cancel 了"
  11. **该 query 在 plan 中未被明确定义**

- **为什么有问题**: plan §5.8 的 cancel reconcile 算法依赖于一个尚不存在的 durable query primitive：按 exact Attempt identity 读取 cancel truth。`read_cancelling_runs_for_session` 只覆盖 `CANCELLING` 状态的 Run，但 watchdog 可能在 reconcile 之前已将 Run 置为 `CANCELLED` terminal。plan 承认了这个问题（"即使Run已被...置为CANCELLED"）但未给出具体的 query 设计。
- **直接证据**:
  - Plan §5.8: "一个bounded read transaction按exact identities读取Run cancel request link、Attempt/dispatch identity及owner_host_instance_id；即使Run已被另一scheduler watchdog置为CANCELLED，durable cancel link仍须可读"
  - Plan §5.8: "只接受dispatch owner等于本scheduler host instance且identity完全相同的target"
  - Plan §6 文件表中 `dayu/host/durable/state.py` 变更包含 "execution-owner cancel所需exact identities query"
  - 但 §5.8 未给出该 query 的 signature、输入输出和 durable 读取路径
  - 当前 `dispatch.py` 的 watchdog 在 `_run_active_cancel_watchdog_closeout` 中执行 CAS + `RUN_CANCELLED` append
- **影响**: 中等。如果 implementation agent 在 Slice 4 需要自行设计该 query，可能产生与 plan 意图不一致的实现。query 设计错误会导致 owner reconcile 漏读 cancel truth。
- **建议改法和验证点**:
  1. Plan §5.8 应给出 exact identity cancel query 的 typed signature 和 durable 读取路径（读 EventLog 中的 `CANCEL_REQUESTED` fact？读 Run 的 `cancel_requested_at` 字段？读单独的 cancel link table？）
  2. 在 Slice 4 的 prerequisites 中增加：确认 durable cancel link 在 Run terminal 后仍可读
  3. 测试: A worker 持有 Attempt → B watchdog 先置 CANCELLED → A reconcile 仍读到 cancel → A 传播到 worker
- **修复风险（低）**: 只需明确 query contract，不改变架构
- **严重程度（中）**

### F-05 — accepted-candidate — 中 — Slice 2 与 Slice 3 之间存在可触发错误的 crash 路径

- **位置**: Plan §7 Slice 2 non-goals: "本slice不改proactive request schema/count/config；existing incomplete request仍由Slice 3收敛"；Slice 3 prerequisites: "Slice 2保证同Session仅一个eligible scheduler"
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: Slice 2 完成 attachment + gate + target recovery 但不改 proactive schema；Slice 3 完成 proactive single-operation state machine。两个 slice 之间，旧的 count-based proactive logic 与新的 single-eligible-scheduler invariant 共存。
- **反例/失败场景**:
  1. Slice 2 完成后：同 Session 只有一个 eligible scheduler（attachment gate 保证）
  2. 旧的 `_run_pre_start_governance` 仍在使用 `max_proactive_compactions_per_run` count（值为 2 in packaged profiles）
  3. 因为只有一个 eligible scheduler，重复 proactive compact 的跨 opener race 已被消除 ✓
  4. **但是**：process crash 后 fresh RW attach → target recovery → scanner 对 `ACCEPTED` Run 分类为 `ACCEPTED_WAKE` → wake queue promotion → `_run_pre_start_governance` → count check
  5. 如果该 Run 在 crash 前已有 incomplete `CONTEXT_COMPACTION_REQUESTED`（没有 terminal），旧 count logic 会看到 count=1（packaged max=2），因此**追加第二个 request**！
  6. 这就是 plan 自己描述的 exact 问题：crash recovery 被错误建模为第二个 proactive operation
  7. Slice 2 的 target recovery 不处理 incomplete operation recovery（这是 Slice 3 的职责）
  8. **因此 Slice 2 完成后，crash → fresh RW attach → target recovery → 可能创建第二个 proactive request**

- **为什么有问题**: plan 承认 Slice 2 "existing incomplete request仍由Slice 3收敛"，但 Slice 2 的 target recovery 会在 scanner 看到 `ACCEPTED` Run 时无条件 wake promotion，而 promotion 进入的 governance 仍使用旧 count logic。这导致 crash recovery 窗口内可能创建重复 operation。虽然 Slice 3 会修复 root cause，但在 Slice 2→Slice 3 的过渡期间，系统存在已知的不正确行为。
- **直接证据**:
  - Plan §7 Slice 2 non-goals: "本slice不改proactive request schema/count/config；existing incomplete request仍由Slice 3收敛"
  - Plan §7 Slice 2: scanner 将 `ACCEPTED` Run 保持 `ACCEPTED`，"等待 scheduler / pre-start governance"
  - Plan §7 Slice 3: "crash在manifest commit后/provider result前：fresh RW以同operation从N+1继续"
  - Plan §2.1 代码证据表: `_run_pre_start_governance` "先count proactive request，再按policy.max_proactive_compactions_per_run判限"
  - Control doc Slice 原则: "不得留下只有类型、没有路径，或只有存储、没人调用的孤立半成品" — Slice 2 不留下半成品类型，但留下半成品行为（旧的 count logic + 新的 single-scheduler invariant）
- **影响**: 中等。在 development 环境中（Slice 2 已部署但 Slice 3 未部署），crash recovery 可能创建重复 proactive operation。这不是 production risk（两个 slice 应在同一 PR 中实现），但 plan 应明确标注此过渡风险并要求 Slice 2 和 3 在同一 PR 中连续实现，或 Slice 2 增加临时保护。
- **建议改法和验证点**:
  1. Plan §7 Slice 2 completion signal 应增加: "本 slice 不能独立部署；必须与 Slice 3 在同一 PR 中完成"
  2. 或在 Slice 2 中增加最小保护：target recovery scanner 对已有 `CONTEXT_COMPACTION_REQUESTED` 但无 terminal 的 `ACCEPTED` Run 不 wake promotion（defer 到 Slice 3 的 typed state reader）
  3. 验证: Slice 2 单测中，已有 incomplete request 的 Run 在 target recovery 后不产生第二个 request
- **修复风险（低）**: 增加一个 scanner 分类规则即可
- **严重程度（中）**

### F-06 — accepted-candidate — 低 — mutation 分类中 `close_session` 和 `drain_outbox_terminal_items` 的 gate 语义与既有 idempotency 存在交互

- **位置**: Plan §5.2 将 `close_session` 和 `drain_outbox_terminal_items` 列入必须 gate 的 mutation
- **问题类型**: 最佳实践偏离
- **当前写法**: Plan §5.2: `close_session` 和 `drain_outbox_terminal_items`（"它会改变delivery durable state，不属于RO read"）需要 gate
- **反例/失败场景**:
  1. Plan 正确识别 `drain_outbox_terminal_items` 写 durable state → 需要 gate ✓
  2. Plan 正确识别 `close_session` 是 Session mutation → 需要 gate ✓
  3. **但**: `drain_outbox_terminal_items` 是幂等的（Outbox drain 使用 idempotency key）。RO opener 调用它会收到 `PERMISSION_DENIED`，这是正确行为
  4. 但如果 Service layer（非 UI）在 reconnect 时调用 `drain_outbox_terminal_items` 补读 terminal items，而 Service 不持有 attachment...
  5. Plan §5.9: "Service调用发生时，UI已持有attachment" — 这解决了上述场景
  6. 但如果 Service 在 UI 未 attach 时被调用（例如 headless mode），Service 需要自己持有 attachment
  7. Plan §5.9 说 "Service不代理或重新推断access" — 这意味着 headless Service 也需要显式 attach
  8. 这是正确的设计但 plan 未在 §5.9 中显式覆盖 headless/non-UI 场景

- **为什么有问题**: 门控分类正确，但非 UI 场景的 lifecycle owner 未在 plan 中明确。这不是设计缺陷，而是 scope 覆盖不完整。
- **直接证据**:
  - Plan §5.2 mutation 分类表
  - Plan §5.9 "Service调用发生时，UI已持有attachment"
  - Plan §3.1 in scope: "CLI prompt/interactive attachment生命周期"
  - Plan §3.1 未显式列出 "headless/programmatic API attachment lifecycle"
- **影响**: 低。当前所有已知调用方都经过 CLI/Service with UI。未来 headless API 使用方需要自行持有 attachment，这是 design doc 的预期行为。
- **建议改法和验证点**:
  1. Plan §5.9 应增加说明：非 UI 场景（headless API、script、test harness）调用方必须在 mutation 前显式 attach_session
  2. 测试：不经过 CLI 直接使用 Host handle submit → RO rejection
- **修复风险（低）**: 仅需补充说明
- **严重程度（低）**

### F-07 — accepted-candidate — 中 — Slice 4 将 cancel reconcile、docs 更新、full regression 和 coverage 合并，可能掩盖 cancel 的独立 race matrix

- **位置**: Plan §7 Slice 4 "Execution-owner cancel reconcile、product/docs integration 与 final verification"
- **问题类型**: 切片过粗
- **当前写法**: Slice 4 包含: (1) execution-owner cancel reconcile 完整闭环，(2) 6 个 README 更新，(3) full regression + per-file coverage + pyright。Plan 解释 "没有第五个slice，因为CLI/docs/全量验证可在cancel闭环后作为同一final integration收口"
- **反例/失败场景**:
  1. Cancel reconcile 是跨 opener 物理传播，涉及: exact identity snapshot、durable cancel link 读取、owner scheduler poll-based reconcile、watchdog closeout、caller fast path、detach old owner 例外
  2. 这是 plan 中 race condition 密度最高的部分（见 plan §5.8 的 5 步 reconcile 算法和 §11.2 risk 4 的 poll-based liveness）
  3. 将 cancel reconcile 的 focused tests（plan §8.4）与 full regression + coverage（plan §8.5-8.6）+ 6 个 README（plan §9）合并在同一 slice 意味着：如果 cancel 测试失败，implementation agent 需要在一个大 slice 中调试 cancel + docs + coverage + regression
  4. Plan §7 声称 "单独拆成docs-only slice不会增加可回滚语义" — 这正确，但 cancel 不是 docs-only
  5. 如果将 cancel reconcile 独立为 Slice 4，docs/regression 独立为 Slice 5，cancel 失败可以独立回滚

- **为什么有问题**: plan 将最复杂的跨 opener race 逻辑与 mechanical 的 docs/coverage 工作合并。这不会导致正确性问题（cancel 逻辑在 focused tests 中验证），但会降低 implementation agent 的调试效率和 review 的聚焦度。在 plan 的 4-slice budget 内这可能是合理选择，但需要承认 tradeoff。
- **直接证据**:
  - Plan §7 Slice 4 exact changes 5 项
  - Plan §7 Slice 4 allowed files: 6 production + 11 test + 6 docs = 23 files
  - Control doc Slice 原则: "slice 不是按代码行数切...好的 slice 必须有明确输入、输出、non-goals、allowed files/modules、验证命令"
  - Plan §7 对 4 slices 的辩护: "cancel要求在已经detach的old execution owner上继续传播，是有意绕开'新Session工作gate'的existing-owner例外；与普通mutation合并会掩盖其独立race matrix" — 这解释了为什么 cancel 不与 Slice 2 合并，但没有解释为什么 cancel 不与 docs 分离
- **影响**: 低至中。不影响最终正确性，但可能延长 Slice 4 的 debug 周期。
- **建议改法和验证点**:
  1. 保持当前 4-slice 结构，但在 Slice 4 non-goals 中说明如果 cancel reconcile 测试发现需要额外设计裁决，该部分可以降级为独立 Slice
  2. 或者: 将 Slice 4 拆为 4a (cancel reconcile + focused tests) 和 4b (docs + regression + coverage)，两个 slice 在同一 PR 中连续实现
- **修复风险（低）**: 仅影响 slice 结构
- **严重程度（中）**

## Final plan review conclusion

**pass-with-risks**

### Rationale

Plan 的 architecture direction、semantic ownership assignment、public contract design 和 slice decomposition 均与 design doc §9/§25/§27 的裁决一致。Plan 正确识别 root cause（Session-level eligibility owner 缺失 + proactive uniqueness 被错误建模为 count），提出的 Host-owned per-Session immutable attachment registry + strict-native mutex + typed durable operation state machine 方案是最小可行修复。
