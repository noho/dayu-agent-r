## Findings

### 1-未修复-高-delete 规则与 O16-F01 边界冲突，且“确定性优先级”过度声明
- **位置**: 计划 §「最小公开 selector 契约与 typed handoff」第 3 条（确定性前置时序）；关联 §「非目标」与 goal 边界段。
- **问题类型**: 目标漂移 / 范围边界冲突 / open question 未收敛（含 O16/O05 交界）。
- **当前写法**: “先校验 action；delete 时 `files` 非空沿用现有 files/delete usage，selector 非空用 `primary_not_allowed_for_delete`，不进入资产规划。……若同时违反多个规则，明确沿用 action/delete → O04 admission → selector cardinality → exact membership 的优先级”。
- **反例/失败场景**:
  1. 实施 Agent 按“沿用现有 files/delete usage”理解为在 material admission 落 `FILES_NOT_ALLOWED_FOR_DELETE`（该 code 现仅 filing 在 `ingestion_runtime.py:1291-1295` 使用）→ 实质实施了 O16-F01 的 delete 半边：goal 明文“O16 action/files……独立 work unit 不在此实现”，且 O16-F01 自带未完成的次序协调要求（“与 UM-O15 的 target-missing 前置校验协调顺序”“无文件组合的校验优先级应稳定”）与补跑验证清单，O25 的验证矩阵并无 delete 带 files 场景 → 未验证的跨 unit 行为被落地，O16 后续被迫在既成次序上返工。
  2. 按“保持现状”理解 → material 的 delete+files 现状是入口分裂的：tool 层已拒（`upload_tools.py:480-483` “files must be omitted for delete uploads”），SEC workflow 静默丢弃 files（`sec_upload_workflow.py:473/491-492`，即 O16 裁决 S17 的直接代码原因），filing 是 typed usage。此时 delete 同时带 files+selector 的错误随入口而变（tool 报 files 文案，直调 Service 报 `primary_not_allowed_for_delete`），计划声称的“确定性前置时序”无法跨入口成立。
- **为什么有问题**: 两种读法分别导致 goal 漂移（侵入 O16 已接受修复项，且违背 O04/O23 计划“不增加 action 规则”“delete 携 files 的旧入口差异属于 action 规则非目标”）或计划自相矛盾（宣称确定性却依赖入口分裂的“现有”行为）。O25 oracle 对 delete 的修复要求只有“delete 携带 **selector**……typed 拒绝”，delete+files 属 O16-F01 已接受、未实施的独立修复项。此外 O05-F01 将把 form/name 必填前置到同一输入边界，其与 selector 检查的相对次序也未被该链覆盖，计划以“明确沿用……优先级”口吻给出的总序会被后续 O05/O16 实施不断打补丁。
- **直接证据**:
  - goal：“O16 action/files、O13/O14/O15 发布状态、O33 并发等独立 work unit 不在此实现，但集成时需用共同 owner 回归”。
  - O25 oracle 修复要求：“多文件缺 selector、重复 selector、未精确命中原件、delete 携带 selector 均在转换前 typed 拒绝”（无 delete+files 项）。
  - O16 oracle UM-O16-F01（已接受未实施）：“auto/create/update 无文件时、delete 带任何文件时，都在上传开始与公司/材料业务持久化前拒绝……与 UM-O15 的 target-missing 前置校验协调顺序”；语义 owner 是“Fins material 请求的 action/files admission contract”。
  - `ingestion_runtime.py:1291-1295`（filing delete 顺序：files 先、primary 后）、`upload_tools.py:480-483`（tool delete+files 现行为）、`sec_upload_workflow.py:473/491-492`（SEC 静默丢 files）、`docling_upload_service.py:433-434`（深层裸 `ValueError`）。
  - O04/O23 候选计划：“delete 携 files 的旧入口差异属于 action 规则非目标，不因本计划顺手改变”“不增加 action 规则”。
- **影响**: 实施 Agent 要么越界实施 O16 半边（无对应验收、打乱 O16/O15 次序协调），要么交付一个跨入口不一致的“确定性”错误优先级；后续 O16/O05 落地时被迫返工 admission 次序；review 无法按“确定性”验收 S1/S2 的失败投影。
- **建议改法和验证点**:
  1. §3 明确：O25 在 delete 下只实现 `primary_not_allowed_for_delete`（selector 非空即拒，含多 occurrence）；delete+files 的 typed 化与次序完全归 O16-F01，本项不改其任何入口现行为。
  2. 把优先级链改写为仅覆盖 O25 自有规则组（selector cardinality → exact membership，及其相对 O04 admission 的位置），并显式登记：action/files 组合次序（O16）与 form/name 必填次序（O05）落同一 admission 边界时须共同裁决，不得由本计划单方锁定。
  3. 验证点：S1 增加“delete+files+selector 复合输入在各入口的错误归属”测试并按上述边界断言；在 Open Questions 登记 O16/O05 次序协调。
- **修复风险（低/中/高）**: 低（改计划文本与测试断言，不动实现方向）。
- **严重程度（低/中/高/严重）**: 高。

### 3-未修复-中-三片切片存在用户可见语义窗口，中间态未声明防护

### 4-未修复-低-指纹/skip 描述遗漏 `identical_skip_safe` 门条件
- **位置**: 计划 §「派生名、指纹、持久化及读取同源」第二、三条。
- **问题类型**: 契约描述不完整（可能诱发实现丢条件）。
- **当前写法**: “`_can_skip_upload` 仍只比较 owner 生成的本次指纹与已发布 source meta 的指纹及既有 overwrite/repair/deleted 条件”；“`_resolve_document_version` 使用同一指纹”。

- **为什么有问题**: 计划对既有函数给出精确枚举却遗漏真实条件；该标志同时支配 skip 与版本两条路径。

- **建议改法和验证点**: §指纹 明确 material 角色指纹的 `identical_skip_safe` 规则（O04 唯一命名下角色无歧义，应保持 True，或给出明确判据）；S3 矩阵补 `document_version` 一致性断言（A→B 递增、B→B skip 不变）。

- **严重程度（低/中/高/严重）**: 低。
