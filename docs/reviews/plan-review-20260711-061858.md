## Findings

### F1-未修复-高-S2 未明确区分 direct stream 文本与 job event sidecar 文本的移动范围

- **位置**: S2 "Exact allowed changes" - `direct_event_text.py` 的 helper 职责描述
- **问题类型**: 不可直接实施
- **当前写法**: Plan 声称 helper 拥有 "Direct progress messages for current direct stages such as `download.preparing`, `download.started`, preprocess selected/document states/completed, and upload preparing/started/completed states." 同时 S2 stop condition 写道 "If a direct runtime string is both durable machine state and user-visible projection, first identify the consumer path. Only move the user-visible projection; do not change durable job state semantics in this WU."
- **反例/失败场景**: `ingestion_runtime.py` 中有两类用户可见文本：(1) 通过 `_emit_context_progress` / `_emit_direct_result` 发出的 direct stream 进度/结果消息；(2) 通过 `_append_job_event_warn` 发出的 job event sidecar 消息（如 "job 已进入队列"、"job 已开始执行"、"job 已取消"、"job 已成功完成"、"job 已失败"）。两类消息都是用户可见的中文文案，但传播路径不同。Plan 的 helper 范围描述只提到了 direct stream 的进度消息，没有明确 job event sidecar 消息是否也需要移动。实施 Agent 可能只移动 direct stream 消息而遗漏 job event 消息，导致源扫描无法覆盖遗漏的文案。
- **为什么有问题**: `ingestion_runtime.py` 中至少有 25+ 处中文可见文案，其中约 10 处是 job event sidecar 消息。如果 plan 不明确这些消息的处置，实施 Agent 会在 "是否移动" 上做隐式决策，可能产出不完整的 helper 或遗漏 regression 扫描。
- **直接证据**: `ingestion_runtime.py:3198` ("已记录取消请求"), `:3254` ("job 已进入队列"), `:3432` ("job 已开始执行"), `:3439` ("job 已取消"), `:6630` ("job 已成功完成"), `:6632` ("job 已失败"), `:6635` ("job 状态未终结") — 这些都是通过 `_append_job_event_warn` 发出的 job event sidecar 消息，不是通过 `_emit_context_progress` / `_emit_direct_result` 发出的 direct stream 消息。
- **影响**: 实施 Agent 做出错误的范围判断 → 不完整的 helper → 源扫描遗漏 → 用户可见文案仍由 runtime 拥有。
- **建议改法和验证点**: 在 S2 中明确列出 `direct_event_text.py` 拥有的完整文案清单（按传播路径分组），或明确声明 "job event sidecar 消息不属于本 WU 范围，由后续 WU 处理"。验证点：helper 移动后，源扫描覆盖所有声称移动的文案。
- **修复风险（低）**: 补充 plan 文本即可，不改变架构。
- **严重程度（高）**: 不明确的范围会导致实施偏差。

### F2-未修复-高-源扫描遗漏约 23 处 Fins runtime 用户可见文案

- **位置**: S3 "Required source scans" - Fins runtime/wait scan
- **问题类型**: 测试缺口
- **当前写法**: `rg -n "请检查 Fins ingestion|如仍需要该财报资料|Fins operation was cancelled before completion|下载准备中|预处理准备中|上传准备中|上传已开始|操作已取消|操作完成|下载失败|预处理失败|上传失败" dayu/fins/ingestion_runtime.py dayu/fins/ingestion/wait_adapter.py`
- **反例/失败场景**: 这个扫描只覆盖 11 个 pattern，但 `ingestion_runtime.py` 中至少有 34 处用户可见中文文案。遗漏的关键文案包括：`"已记录取消请求"` (3198), `"job 已进入队列"` (3254), `"job 已开始执行"` (3432), `"job 已取消"` (3439), `"预处理已选择源文档"` (3510), `"预处理源文档已开始"` (3529), `"预处理源文档不支持"` (3550), `"预处理源文档失败"` (3565), `"预处理源文档已完成"` (3580), `"预处理源文档已跳过"` (3594), `"预处理请求已完成"` (3618), `"下载已开始"` (3661), `"下载已完成"` (5895), `"上传已完成"` (6016), `"job 已成功完成"` (6630), `"job 已失败"` (6632), `"job 状态未终结"` (6635), `"操作失败"` (182), `"执行失败"` (184), `"下载请求未写入任何源文档"` (2813), `"没有任何请求文档完成预处理"` (2871), `"上传运行时返回失败状态"` (2957)。
- **为什么有问题**: 源扫描是 plan 的 regression 防线。如果扫描不覆盖所有声称移动的文案，实施后残留的文案不会被发现。这直接违反 plan 的 success signal "source scans prove the accepted P3-H literal/protocol leaks are removed."
- **直接证据**: `ingestion_runtime.py` 中至少有 23 处用户可见中文文案不在扫描 pattern 中。这些文案通过 `_emit_context_progress`、`_emit_direct_result` 或 `_append_job_event_warn` 进入用户可见的 direct event stream 或 job event sidecar。
- **影响**: 实施完成后源扫描通过，但仍有 23+ 处文案残留在 runtime 中 → plan 的 success signal 被虚假满足。
- **建议改法和验证点**: 扩展 Fins runtime scan pattern，或改用函数名扫描（如 `rg -n "_DIRECT_CANCELLED_MESSAGE|_DIRECT_FAILURE_TITLE|_DIRECT_SUCCESS_TITLE|_DIRECT_ERROR_TEXT_FALLBACK|_emit_context_progress|_emit_direct_result|_append_job_event_warn"`），再辅以具体文案 pattern。验证点：扫描 pattern 覆盖 `ingestion_runtime.py` 中所有用户可见中文文案。
- **修复风险（低）**: 补充 scan pattern 即可。
- **严重程度（高）**: 源扫描是 plan 的核心验证手段，遗漏会导致虚假通过。

### F3-未修复-中-源扫描遗漏 `_build_search_web_preferred_summary` 中的中文文案

- **问题类型**: 测试缺口
- **当前写法**: `rg -n "_build_search_web_hint|_build_search_web_next_action|当前没有可直接抓取|优先抓取首选结果正文" dayu/tools/web/web_search_providers.py tests/tools/web`
- **反例/失败场景**: 扫描覆盖了 `_build_search_web_hint` 和 `_build_search_web_next_action` 的函数引用和两个中文 hint 片段，但遗漏了 `_build_search_web_preferred_summary` 函数中的中文文案：`"未找到可直接抓取正文的公开网页结果。"` (834), `"首选结果"` (844), `f"标题：{title}"` (846), `f"日期：{published_date}"` (848), `f"摘要：{snippet_preview}"` (852)。这些文案直接进入 `SearchWebOutput.preferred_result_summary`，是 LLM 可见的输出字段。

- **修复风险（低）**: 补充 scan pattern 即可。
- **严重程度（中）**: 影响范围比 F2 小（5 处 vs 23 处），但性质相同。

### F4-未修复-中-Web display name / description 的 owner 归属与现有 `@tool` 装饰器契约冲突

- **位置**: S1 "Exact allowed changes" - `web_tool_projection_text.py` 拥有 `SEARCH_WEB_DISPLAY_NAME` 和 `FETCH_WEB_PAGE_DISPLAY_NAME`
- **问题类型**: 架构边界
- **当前写法**: Plan 声称 `web_tool_projection_text.py` 拥有 display name 常量，`web_tools.py` 的 `build_web_tool_definitions(...)` 消费这些常量。
- **反例/失败场景**: 当前 `@tool(...)` 装饰器契约（`dayu/contracts/tool_declaration.py:244-284`）将 `display_name` 作为装饰器参数，与 `description`、`tags`、`truncate_spec` 等一起在工具声明现场定义。`ToolDefinition` 持有 display 信息，`to_tool_schema()` 投影时剥离。将 `display_name` 抽到单独的 projection text helper 会将声明元数据与声明现场分离，引入不必要的间接层。
- **为什么有问题**: `display_name` 和 `description` 是工具声明的一部分，不是独立的投影文本。当前 `web_tools.py` 在 `@tool(...)` 装饰器中内联定义这些值是符合项目契约的设计。将它们抽到 `web_tool_projection_text.py` 会让未来的工具开发者需要在两个文件间跳转才能理解一个工具的完整声明。这不是 semantic ownership drift 的修复，而是引入了新的 coupling。
- **直接证据**: `dayu/contracts/tool_declaration.py:244-284` — `@tool(...)` 装饰器接收 `display_name` 作为参数；`web_tools.py:1188-1205` 和 `:1225-1243` — `search_web` 和 `fetch_web_page` 的 `@tool(...)` 装饰器内联定义 `display_name` 和 `description`。
- **影响**: 引入不必要的间接层 → 工具声明与 display 信息分离 → 维护成本增加 → 违反 "最小化满足需求" 的架构约束。
- **建议改法和验证点**: `display_name` 和 `description` 保持在 `web_tools.py` 的 `@tool(...)` 装饰器中。`web_tool_projection_text.py` 只拥有 cancellation 文案（`WEB_SEARCH_CANCELLED_MESSAGE`、`WEB_FETCH_CANCELLED_MESSAGE`、`WEB_CANCELLED_HINT`）。验证点：display name 和 description 仍在工具声明现场定义。
- **修复风险（低）**: 减少 helper 职责，不改变架构。
- **严重程度（中）**: 不会导致实施失败，但会引入不必要的复杂度。

### F5-未修复-中-`web_cancellation_text.py` 的删除/替换策略未明确

- **位置**: S1 "Exact allowed changes" - `web_cancellation_text.py` only for deletion/replacement
- **问题类型**: 不可直接实施
- **当前写法**: Plan 写道 "`web_cancellation_text.py` only if it is deleted/replaced; do not keep compatibility re-export" 和 "Do not keep `web_cancellation_text.py` as a compatibility re-export. Either update imports to the new helper and delete the old file, or keep the old file only if it remains the real owner and is renamed is not needed."
- **反例/失败场景**: `web_cancellation_text.py` 被 3 个文件导入：`web_tools.py`、`web_search_providers.py`（用于 `WebSearchCancelledError` 的 hint）、`tests/tools/web/test_web_tools_provider.py`。Plan 提供了两个选项但没有明确选择哪个。实施 Agent 需要自行决定：(1) 删除 `web_cancellation_text.py`，将 `WEB_CANCELLED_HINT` 移到 `web_tool_projection_text.py`，更新所有 import；或 (2) 保留 `web_cancellation_text.py` 但将它重命名或合并。Plan 的歧义会让实施 Agent 在两种路径间犹豫。
- **为什么有问题**: 选项 (1) 涉及修改 3 个文件的 import，选项 (2) 保留旧文件但增加命名混乱。Plan 应该明确选择一条路径。
- **直接证据**: `web_cancellation_text.py` 被 `web_tools.py:69`、`web_search_providers.py:19`、`tests/tools/web/test_web_tools_provider.py:69` 导入。
- **影响**: 实施 Agent 做出不同选择 → 测试更新范围不同 → 可能遗漏 import 更新。
- **建议改法和验证点**: 明确选择选项 (1)：删除 `web_cancellation_text.py`，将 `WEB_CANCELLED_HINT` 移到 `web_tool_projection_text.py`，更新 3 个文件的 import。验证点：`web_cancellation_text.py` 不存在，所有 import 指向新 helper。
- **修复风险（低）**: 明确选择即可。
- **严重程度（中）**: 歧义会导致实施路径不一致。

### F6-未修复-低-S2 stop condition 过于模糊

- **位置**: S2 "Stop condition"
- **问题类型**: 不可直接实施
- **当前写法**: "If a direct runtime string is both durable machine state and user-visible projection, first identify the consumer path. Only move the user-visible projection; do not change durable job state semantics in this WU."
- **反例/失败场景**: `ingestion_runtime.py` 中有些文案同时出现在 FinsEvent（用户可见）和 job event sidecar（也是用户可见）中。例如 "下载失败" 出现在 `_produce_direct_download` 的 result title 中，也出现在 `_execute_download_request` 的 job event 中。Plan 的 stop condition 假设 "durable machine state" 和 "user-visible projection" 有清晰边界，但实际上两者都是用户可见的。
- **为什么有问题**: 实施 Agent 需要逐个判断每个文案是 "durable machine state" 还是 "user-visible projection"，但 plan 没有提供判断标准或具体例子。
- **直接证据**: `ingestion_runtime.py` 中的文案同时服务于 direct stream 和 job event sidecar，两者都是用户可见的。
- **影响**: 实施 Agent 做出不一致的判断 → 部分文案移动、部分文案保留 → 源扫描无法验证完整性。
- **建议改法和验证点**: 提供具体例子说明哪些文案属于 "durable machine state"（如 job record 中的 internal status text），哪些属于 "user-visible projection"（如 FinsEvent.message）。或简化 stop condition：所有进入 FinsEvent、wait outcome 或 tool result 的文案都属于 user-visible projection。
- **修复风险（低）**: 补充 plan 文本即可。
- **严重程度（低）**: 不会阻塞实施，但会增加实施 Agent 的判断负担。

### F7-未修复-低-S2 helper 与 `direct_events.py` 的关系未明确

- **位置**: S2 "Exact allowed changes" - `direct_event_text.py` 的定位
- **问题类型**: 架构边界
- **当前写法**: Plan 写道 "`direct_event_text.py` with complete Chinese docstrings and typed functions/constants. It may import `FinsErrorKind`, `FinsOperationKind`, and `FinsResultStatus` from `dayu.fins.direct_events`."
- **反例/失败场景**: `direct_events.py` 是合约层（类型 + 验证），`direct_event_text.py` 是文本层（中文文案）。Plan 说 "may import" 但没有说明 helper 的函数签名应该是什么样的。是返回 `str` 的函数？还是 `dict[FinsOperationKind, str]` 的 mapping？实施 Agent 需要自行设计 helper 的 API。
- **为什么有问题**: 如果 helper 的 API 设计不当，可能会引入新的 coupling 或让 `ingestion_runtime.py` 的调用代码变得更复杂。
- **直接证据**: `direct_events.py` 定义了 `FinsOperationKind`、`FinsResultStatus`、`FinsErrorKind` 等类型，但 plan 没有说明 helper 如何使用这些类型来组织文案。
- **影响**: 实施 Agent 设计的 helper API 可能不够类型安全或不够可维护。
- **建议改法和验证点**: 提供 helper 的初步 API 设计，例如：`def direct_progress_message(kind: FinsOperationKind, stage: str) -> str` 和 `def direct_result_title(kind: FinsOperationKind, status: FinsResultStatus) -> str`。验证点：helper 的函数签名使用 `direct_events.py` 的类型。
- **修复风险（低）**: 补充 API 设计即可。
- **严重程度（低）**: 不会阻塞实施，但会影响 helper 的设计质量。

## Open questions

1. **Fins job event sidecar 消息是否属于 P3-H 范围？** Plan 的 S2 描述提到了 "direct progress messages" 和 "direct result/failure messages"，但没有提到 job event sidecar 消息（如 "job 已进入队列"、"job 已成功完成"）。这些消息也是用户可见的中文文案，但传播路径不同。需要明确：是 P3-H 一并处理，还是留给后续 WU？

2. **`web_search_projection.py` vs `web_tool_projection_text.py` 的职责边界？** Plan 提到了两个新文件：`web_search_projection.py`（拥有 search output 的 LLM-facing 字段构建）和 `web_tool_projection_text.py`（拥有 display name 和 cancellation 文案）。但 display name 与 `@tool` 装饰器耦合（见 F4），cancellation 文案与 search/fetch 两个工具都相关。两个文件的职责是否有重叠？

3. **新的 helper 模块是否需要独立的测试文件？** Plan 提到 "Add direct helper unit coverage through existing Fins tests or a focused new test file"，但没有明确选择。如果 helper 有复杂的 mapping 逻辑，可能需要独立测试。

## Residual risks

- **Fins direct text scope risk**（plan 已识别）: `ingestion_runtime.py` 包含 direct-stream 可见文案和 durable job/internal 消息。实施必须按传播路径分类，不能机械地移动所有中文文案。
- **Coverage risk**（plan 已识别）: 新 helper 模块需要 focused 测试以满足单文件覆盖率目标。
- **Web output contract risk**（plan 已识别）: 测试或下游代码可能依赖 `SearchWebOutput` 类型。实施应直接更新 import，不添加兼容别名。
- **Source scan incompleteness**（本次 review 发现）: Fins runtime scan 遗漏 23+ 处文案，Web provider scan 遗漏 5 处文案。需要补充 scan pattern。

## Final plan review conclusion

**pass-with-risks**

Plan 的架构方向正确：将 LLM-facing prose 和用户可见文案从 provider/downloader/adapter 移到 projection/helper 边界。DS12 evidence-invalid disposition 经验证正确。设计对齐、合约变更分析、propagation audit 标准都足够详细。

但存在两个需要在实施前修复的高严重度问题：

1. **F1**: S2 未明确区分 direct stream 文本与 job event sidecar 文本的移动范围，实施 Agent 可能做出不完整的移动。
2. **F2**: Fins runtime 源扫描遗漏 23+ 处用户可见文案，会导致虚假通过。

修复 F1 和 F2 后，plan 可以安全交给实施 Agent。F3-F7 是中/低严重度问题，可以在实施过程中逐步解决。

**Blockers**: 无（F1 和 F2 是 plan 文本补充，不改变架构方向）。
