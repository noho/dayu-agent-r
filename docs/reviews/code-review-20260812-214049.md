**新增测试**: `test_durable_upload_projection_failure_preserves_accepted_terminal`（第 3916 行）

**执行路径走读**:

1. **触发机制**: monkeypatch `FsFinsIngestionJobStore.save_accepted_upload_terminal_if_active`，先调用原始 `original_save` 完成真实持久化，再返回一个 `result_summary.status` 被篡改为 `projection_status` 的 fake record。后续 `_upload_terminal_disposition_from_job_record(saved)` 读取该 fake record 的 `result_summary`，发现 `record.status`（SUCCEEDED/FAILED）与 `result_summary.status`（failed/ok）不一致，抛出 `ValueError`。

2. **异常收口**: `ValueError` 传播到 `_run_upload_job` 的 `except Exception` → `_save_failed_from_exception`。该 helper 调用 `read_job(job_id)` 读取 durable record，发现 `record.status in _TERMINAL_STATUSES`，直接 return，不做二次写入。

3. **SUCCEEDED/FAILED 覆盖**: 参数化 `("ok", "failed", SUCCEEDED)` 和 `("failed", "ok", FAILED)`。Case 1: 保存 SUCCEEDED，投影层报告 "failed" → disposition mismatch → ValueError。Case 2: 保存 FAILED，投影层报告 "ok" → disposition mismatch → ValueError。两条路径都进入 `_save_failed_from_exception` 并被终态守卫拦截。

4. **durable record 不改写**: 断言 `record == accepted_records[0]`，即最终持久化 record 与原始 save 返回的 record 值相等。断言 `record.result_summary["status"] == status`（原始 status，非 projection_status）。

5. **无第二 terminal event**: 断言 `terminal_events == ()`。因 `_save_failed_from_exception` 在终态守卫处 return，`_append_terminal_job_event_warn` 从未被调用。

6. **fallback 读取验证**: monkeypatch `read_job` 记录 fallback 读取，断言 `fallback_reads == accepted_records`，证明异常收口确实从 durable store 重读了真实终态。

7. **无生产 hook**: 测试只 monkeypatch 了 `FsFinsIngestionJobStore`（Protocol 实现），不修改 `_run_upload_job` 内部逻辑、不注入异常抛出点、不使用 `side_effect` 模式。触发 projection 失败的方式是通过 Protocol 边界返回不一致数据，利用既有 `_upload_terminal_disposition_from_job_record` 的一致性校验。

**结论**: A1 测试通过既有 `_upload_terminal_disposition_from_job_record` 校验边界准确触发 save 后 ValueError，覆盖 SUCCEEDED/FAILED 两种终态，证明 durable record 不改写且无第二 terminal event，未引入生产 hook 或脆弱测试。**裁决 A1 已修复。**
