### 5-未修复-低-错误文案“不回显路径”是 plan 自创解释，与同模块既有路径错误约定相反
- **位置**: plan「目标、动机和边界」首段、「唯一 owner 与具体设计」末段（“报错文字不回显用户路径，以免 stderr 泄露本地绝对路径”）、测试方案（“stderr …不含 `storage_io`/绝对路径”）。
- **问题类型**: 过度验收标准 / open question 未收敛。
- **当前写法**: 把“路径安全”解释为“stderr 不含用户路径”，并固化为测试断言。
- **反例/失败场景**: 同一模块的既有路径类用法错误全部回显 resolve 后的绝对路径（fins.py:98-99 “upload file does not exist: {path}”、“upload path is not a file: {path}”，fins.py:1143-1145）；init 与 upload_script 的错误同样回显路径。本地 CLI 的 stderr 本来就持续输出绝对路径，新错误不回显并不能提供实质“防泄露”，反而在默认 `./workspace` 触发时降低可操作性（用户未显式传 `--base`，错误不告诉他哪个路径是文件）。
- **为什么有问题**: goal 原文“路径安全的用法错误”含义未裁决（结合 goal 第 14 行“用户原有普通文件内容和路径保持不变”，更可能指处理过程不破坏路径，而非文案脱敏）；plan 把一个未确认解释升级为硬测试断言，若 controller/用户认为应遵循模块内既有约定（回显路径、更可操作），测试断言必须整体翻转。
- **直接证据**: goal 第 13-14 行；plan 第 10、28、44 行；fins.py:98-99、1143-1145。
- **影响**: 文案层面返工风险；不构成架构问题。
- **建议改法和验证点**: plan 把该点改写为 open question 交 controller 裁决，或直接对齐模块内既有约定（回显 resolved 路径，与“upload path is not a file”风格一致）；测试断言按裁决结果固定。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。
