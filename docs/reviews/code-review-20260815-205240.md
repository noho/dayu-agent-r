## Findings

### 1-未修复-低-两个生产 helper 的 docstring Raises 声明与实际异常路径不符

- **入口/函数**: `_build_stored_file_entry`、`_build_upload_source_fingerprint`
- **文件(行号)**: `dayu/fins/pipelines/docling_upload_service.py:1611-1613`（Raises: 无）、`docling_upload_service.py:1237-1239`（Raises: 无）
- **输入场景**: filing 分支构建 stored entry 或 source fingerprint 时，asset 携带空或 `None` 的 `original_filename`（例如未来某调用方把 material 资产或字段漏填的 filing 资产传入）
- **实际分支**: filing 分支执行 `_require_filing_original_filename(asset)`（行 1627、行 1244、行 1252 的 sort key），该函数对 `original_filename is None or not original_filename` 抛 `ValueError("filing asset 必须携带 original_filename")`（行 1166-1167）
- **预期行为**: docstring 的 Raises 段应完整声明可抛异常——项目编码硬约束（AGENTS.md/CLAUDE.md）要求函数 docstring 至少包含参数、返回值、异常
- **实际行为**: 两个 helper 的 docstring 均声明「Raises: 无」，但 filing 分支存在真实 `ValueError` 抛出路径，调用方按 docstring 理解异常契约时会被误导
- **直接证据**: 行 1611「Raises:\n        无。」与行 1627 的 `_require_filing_original_filename` 调用同处一函数；行 1237-1239 同样与行 1244/1252 的调用矛盾
- **影响**: 文档契约不准确；维护者可能假定这两个 helper 永不抛异常，从而遗漏 ValueError 处理（当前生产调用点均由 `_build_original_assets` 先保证字段非空，暂无运行期故障）
- **建议改法和验证点**: 把两个 docstring 的 Raises 段改为「ValueError: filing asset 缺少 original filename 时抛出」；验证点：pyright 不变、`test_docling_upload_service.py` 全量重跑
- **修复风险（低）**: 仅改 docstring，无行为变化
- **严重程度（低）**

### 2-未修复-低-fresh target 的 blob store 失败缺少直接零发布断言

- **入口/函数**: `_store_upload_assets` 的 blob 写入循环 + `commit_prepared_upload_batch` 的 finally rollback
- **文件(行号)**: `dayu/fins/pipelines/docling_upload_service.py:547-584`；测试缺口位于 `tests/fins/test_docling_upload_service.py:3020`（仅 `test_existing_replacement_blob_failure_keeps_entire_published_tree`）
- **输入场景**: filing fresh target（无 previous_meta）在第 N 个 blob `store_file` 失败（如磁盘满/注入异常）
- **实际分支**: publish 抛 OSError/RuntimeError → `commit_prepared_upload_batch` 中 `batch_terminal_started=False` → finally 调 `rollback_prepared_upload_batch`（行 1015-1020）
- **预期行为**: accepted plan Slice 3 tests 明确要求「第 N 次 blob store/final source/commit failure：rollback exactly once；fresh target 零发布，existing update 的 tree SHA 不变」——blob store 失败同时要求 fresh 与 existing 两个变体
- **实际行为**: rollback 路径本身由 `test_filing_final_source_failure_rolls_back_once_with_zero_publication`（fresh + final source）与 `test_filing_commit_failure_leaves_fresh_target_unpublished`（fresh + commit）覆盖；但 blob store 失败只有 existing-update 变体（断言旧 tree 不变），没有 fresh target 变体直接断言「begin=1/commit=0/rollback=1/零发布」三件套
- **直接证据**: `grep -n "def test.*blob.*failure"` 仅命中 `test_existing_replacement_blob_failure_keeps_entire_published_tree`（行 3020）；plan 第 567-568 行明确要求 blob/final/commit 三类失败均含 fresh 零发布与 existing 不变
- **影响**: 测试覆盖缺口。风险较低——blob 失败与 final source 失败共享同一条 `publish → finally rollback` 路径，且 storage batch rollback 语义另有 `test_fins_storage_atomicity.py` 大量覆盖——但 plan 的 acceptance criterion 未逐项兑现，若未来 `_store_upload_assets` 在 blob 循环内引入部分资源泄漏，fresh 变体缺失会让回归延迟暴露
- **建议改法和验证点**: 复用 `_BatchIdentityUploadBatchingRepository` + 一个 fresh-target blob 失败注入仓储，断言 `begin_calls == 1`、`commit_calls == 0`、`rollback_calls == 1`、`published_tree_sha256 == {}`、`get_source_meta` 抛 FileNotFoundError
- **修复风险（低）**: 纯测试新增
- **严重程度（低）**
