### 1-未修复-中-diagnostic artifact 文件写入与 SQL descriptor 不在同一事务边界，rollback 后产生含 raw 文本的孤儿文件

- **入口/函数**: `write_compaction_rejected_attempt_diagnostic_artifact()` → `LocalArtifactStore.write_artifact_bytes()` → `PayloadStore.write_payload_descriptor_for_artifact()`
- **文件(行号)**: `dayu/host/compaction_operation.py:980-982`
- **输入场景**: 调用方事务（`_write_compaction_rejected_diagnostic` 或 `_write_reactive_compaction_rejected_diagnostic`）在 artifact 文件写入成功后、EventLog append 完成前被 SQLite 层回滚（例如 write busy retry 耗尽、CAS 冲突导致的 RuntimeError 等）
- **实际分支**: `artifact_store.write_artifact_bytes()`（文件系统写入，无事务性）先于 `payload_store.write_payload_descriptor_for_artifact(transaction, ...)`（SQLite 写入，受事务保护）
- **预期行为**: 事务回滚后不应留下无法通过 descriptor 索引到的 artifact 文件，尤其是标记了 `confidential: true` 且包含 raw block text 的诊断 artifact
- **实际行为**: 文件系统中残留一个 content-addressed artifact 文件，其 `payload_descriptors` 行随事务回滚而消失，EventLog 中也无对应 `CONTEXT_COMPACTION_ATTEMPT_REJECTED` 行。该文件成为孤儿，当前代码路径无逆操作（文件删除）补偿
- **直接证据**: `compaction_operation.py:980-982` 先写文件再写 SQL；`compaction_operation.py:981` 的 `canonical_json_dumps(diagnostic.artifact_body).encode("utf-8")` 包含 `previous_compacted_view[*].text`（raw block text，见 `compaction.py:422` 的 `CompactMaterialBlock.to_json()` 输出 `"text": self.text`）和 `offending_block.raw_text`（`compaction_operation.py:1814`）；plan artifact 已将此列为 residual risk："Artifact file orphan after SQL rollback: tracked by existing artifact maintenance model"
- **影响**: 含 raw 文本的 orphan 文件残留在磁盘上，无法通过 `payload_descriptors` 或 EventLog 追踪或清理。若存在独立的 artifact 清理策略（如按时间/大小清理），该文件会一直保留到该策略触发
- **建议改法和验证点**: 在 `write_compaction_rejected_attempt_diagnostic_artifact()` 的 docstring 中明确此 tradeoff；确认现有 artifact maintenance model 确实覆盖孤儿清理，并在其测试中增加 diagnostic artifact orphan 场景。若 maintenance model 不覆盖，考虑在调用方的 `except HostDurableError` 分支中增加 best-effort 文件删除（通过 `artifact_store` 已知的 `artifact_relative_path`）
- **修复风险（低）**: 仅增加 best-effort 清理逻辑，不改动正常路径
- **严重程度（中）**: 孤儿文件包含 `confidential: true` raw 材料，但仅影响回滚异常路径；plan 已预识别此风险

### 3-未修复-低-`_offending_block_artifact_json` 缺少 ordinal 边界校验

- **入口/函数**: `_offending_block_artifact_json()`
- **文件(行号)**: `dayu/host/compaction_operation.py:1802`
- **输入场景**: `offending_block is not None` 但其 `block_ordinal` 与 `previous_blocks` tuple 长度不匹配（例如未来序列化/反序列化 `CompactionRejectedAttemptOffendingBlock` 后 ordinal 漂移，或代码演进中 offending block 与 previous_blocks 来自不同请求）
- **实际分支**: `block = previous_blocks[offending_block.block_ordinal]` — 若 ordinal 越界则 `IndexError`
- **预期行为**: 越界时应 fail-safe（返回 `None` 或不含 raw_text 的 degraded offending block JSON），不让 diagnostic artifact 构造因单个 block 定位失败而整体中断
- **实际行为**: `IndexError` 会穿透 `_proposal_failure_diagnostic_unchecked()` 到达 `_proposal_failure_diagnostic()` 的 `except Exception` 兜底，返回 `None`（不生成 diagnostic），丢失了整个 material pack 的诊断信息
- **直接证据**: `compaction_operation.py:1802` 的无保护索引访问；`compaction_operation.py:1507` 的 `except Exception` 兜底会将任何 diagnostic 构造异常吞掉并返回 `None`
- **影响**: 单个 ordinal 漂移导致整个 diagnostic（含 material_pack_digest、所有 previous block locator summaries）丢失。当前代码路径中 ordinal 总是从同一个 `previous_blocks` 的 `enumerate()` 派生，实际不会触发，但缺少防御性编程
- **建议改法和验证点**: 在 `_offending_block_artifact_json` 中增加 `if offending_block.block_ordinal >= len(previous_blocks): return None` 守卫；或保留 `offending_block` 结构但丢掉 `raw_text` 字段
- **修复风险（低）**: 增加一个边界检查
- **严重程度（低）**: 当前调用链中 ordinal 与 previous_blocks 同源，不会触发；仅影响未来代码演进的安全性

## Residual Risk

- **Orphan artifact 清理**: Finding 1 的孤儿文件风险已由 plan 预识别，但现有 artifact maintenance model 的具体清理策略（触发条件、覆盖范围）未在本 review scope 内验证。若 maintenance model 依赖 `payload_descriptors` 表反向索引来发现可清理 artifact，则 orphan 文件（无 descriptor 行）会被永久遗漏。
- **Diagnostic 构造失败静默**: `_proposal_failure_diagnostic()` 的 `except Exception` 兜底（`compaction_operation.py:1507`）会静默吞掉所有 diagnostic 构造异常。当前代码路径中 diagnostic 构造是纯内存操作（digest 计算、JSON 序列化），失败概率极低；但若未来 `block.to_json()` 或 `sha256_digest_json()` 因意外输入抛出异常，整个 diagnostic 会静默丢失，只留下一条 warning 日志。
- **`material_pack_to_compact_input` stage 覆盖不完整**: 当前 `_proposal_failure_stage()` 对 `proposal_manifest_reference is None` 的非 reference-continuity 异常统一归类为 `material_pack_to_compact_input`。但 generic path（`compaction_operation.py:910`）中 `conversation_compact_input_vnext_from_material_pack()` 的异常和 `compactor.compact()` 的异常都走同一个 `except Exception` 分支且 `proposal_manifest_reference=None`，两者的 stage 都会被归类为 `material_pack_to_compact_input`，即使异常实际发生在 compactor 执行阶段。测试仅覆盖了 reference continuity parse failure 场景，未覆盖非 reference-continuity 的 material projection 异常与其他异常的分类准确性。
- **Engine ingest 的 diagnostic sub-index 偏移**: `engine_ingest.py:2095` 使用 `20 + rejected.attempt_number` 作为 `CONTEXT_COMPACTION_ATTEMPT_REJECTED` 事件的 `sub_index`。这是一个硬编码偏移，依赖 Engine ingest 的 event id 派生算法。若未来 event id 派生逻辑变化，可能产生 id 碰撞。此偏移在 proactive path（dispatch.py）不使用（dispatch 使用 `_new_event_id()` 直接生成独立 id），因此两个路径的 event id 方案不一致，但不影响正确性。
