## Findings

### F1-未修复-严重-filelock `__exit__` 在释放锁失败时丢失 token 导致永久锁死

- **入口/函数**: `RuntimeFileLock.__exit__` (dayu/runtime/filelock.py:198-201)
- **文件(行号)**: `dayu/runtime/filelock.py:198-201`
- **输入场景**: Context manager `__exit__` 被调用（正常退出流程或 `__exit__` 中的异常），`self._active_token` 指向一个未释放的 token。若 token 对应底层 fcntl/msvcrt 锁，且文件系统或操作系统层释放失败（如 `OSError`），触发 `RuntimeFileLockError`。
- **实际分支**:

```
198: token = self._active_token
199: self._active_token = None      # ← 先置空
200: if token is not None:
201:     token.release()             # ← 这里可能 raise
```

- **预期行为**: 如果 `release()` 失败，`_active_token` 应保留指向该 token，使实例处于可观测的"仍持有锁"状态，允许后续恢复或明确报错。`acquire()` 中的 re-entrancy 检查（line 135-140）应能检测到未释放的锁。
- **实际行为**: `self._active_token` 在第 199 行被设为 `None`（在 `release()` 成功之前）。若 `release()` 在第 201 行抛出异常：
  - `_active_token` 已为 `None` → 实例表面看起来空闲
  - `token` 引用仅存在于局部变量，异常传播后丢失 → 旧锁无法恢复
  - 旧锁对应的底层 OS 锁可能仍被持有（取决于 release 为何失败）
  - 下次 `acquire()` 调用时：`_active_token is None` → re-entrancy 检查通过 → 尝试获取新锁 → 可能死锁或无限阻塞（旧 OS 锁从未释放）
  - **后果**: 永久锁死，需进程重启恢复
- **直接证据**: filelock.py:198-201，`self._active_token = None` 在 `token.release()` 之前执行。没有 try/finally 保护。
- **影响**: 在 `release()` 失败场景（文件系统异常、权限问题等）中，RuntimeFileLock 实例进入不可恢复的死锁状态。对于 Host durable 的文件锁，这意味着整个 SQLite 数据库被永久锁定，阻止所有后续写入。
- **建议改法和验证点**: 交换第 199 行和第 201 行的顺序——先 `release()`，成功后再 `self._active_token = None`。最优方案：将 `self._active_token = None` 放在 try/finally 中，确保无论 release 成功与否都能正确标记状态。验证：用 mock 模拟 `token.release()` 抛出 OSError，测试 `__exit__` 后 `_active_token` 状态和后续 `acquire()` 行为。
- **修复风险（低）**: 单行顺序调整，不改变任何正常路径行为。
- **严重程度（严重）**: 生产环境中可导致进程级死锁。

### F2-未修复-中-`_record_failure` 异常覆盖原始 consumer 错误，丢失所有诊断信息

- **入口/函数**: `ProjectionRunner.run_once` → `_record_failure` (dayu/host/projection.py:395-402)
- **文件(行号)**: `dayu/host/projection.py:395-402, 540-571`
- **输入场景**: Consumer `apply_event` 抛出 `HostDurableError` → 在 `_process_next_event` 中被 `run_write` 捕获 → 包装为 `_ProjectionApplyFailed` → 在 `run_once` 中被 `except _ProjectionApplyFailed` 捕获 → 调用 `self._record_failure(...)`。此时 `_record_failure` 自身又打开一个 `run_write` 事务来写 failure row。若该事务因 `SQLITE_BUSY` 重试耗尽而失败，抛出 `HostTransactionRetryExhaustedError`。
- **实际分支**: `_record_failure` 的 `run_write` 失败 → 异常从 `except _ProjectionApplyFailed` 处理块中传播出去 → `run_once` 的调用方收到 `HostTransactionRetryExhaustedError`，而非原始 consumer 错误。
- **预期行为**: 调用方应能获取原始 consumer 错误信息（至少通过 chained exception 或日志），以便诊断问题根因。
- **实际行为**: `exc.original_exception`（consumer 的真实错误）永远丢失。调用方只看到"transaction retry exhausted"，完全无法判断是哪个 consumer 失败、什么原因失败、哪个 event 触发失败。checkpoint 未推进（`finished_cursor = started_cursor`），状态一致，但可观测性严重受损。
- **直接证据**: projection.py:395-402，`_record_failure` 调用不在 try/except 内，其异常直接传播出 `except` 块。`_record_failure` 内部（line 540-571）的 `run_write` 可能因任意 durable 错误而失败。
- **影响**: Operators 在 `_record_failure` 失败时无法获取 consumer 的根因异常。同一问题也存在于 `_ProjectionEventViewFailed` 路径（line 404-412）。
- **建议改法和验证点**: `_record_failure` 内部 catch `run_write` 异常并 log 原始 consumer exception，或使用 `raise ... from exc.original_exception` chain 保留根因。次优方案：在 `run_once` 的 `except` 块中用 try/except 包裹 `_record_failure`。
- **修复风险（低）**: 仅涉及异常包装和日志，不改变状态写入路径。
- **严重程度（中）**: 可观测性和可调试性缺陷，状态一致性未受损。

### F3-未修复-中-`reset_minimal_read_model_projection` 对数据表无条件全量 DELETE，缺少 consumer 隔离

- **入口/函数**: `reset_minimal_read_model_projection` (dayu/host/durable/read_model.py:280-301)
- **文件(行号)**: `dayu/host/durable/read_model.py:292-301`
- **输入场景**: 当 `repair_minimal_read_models` 以 `reset_checkpoint=True` 调用时，投影 runner 执行此函数以清空并重建 minimal read model。
- **实际分支**: 函数执行：
  - `DELETE FROM host_session_timeline_items` — 无条件全表删除
  - `DELETE FROM host_run_results` — 无条件全表删除
  - `DELETE FROM host_projection_failures WHERE consumer_id = ?` — 正确过滤
  - `DELETE FROM host_projection_checkpoints WHERE consumer_id = ?` — 正确过滤
- **预期行为**: 如果采用多 consumer 架构，每个 consumer 只应操作自己拥有的数据。checkpoint 和 failure 表正确地按 `consumer_id` 过滤删除，但数据表（timeline, run_results）没有 `consumer_id` 列，无条件删除。
- **实际行为**: 如果将来有第二个 projection consumer 写入 `host_run_results` 或 `host_session_timeline_items`，此函数会破坏性地清除所有数据，不仅是当前 consumer 的数据。
- **直接证据**: durable/read_model.py:292-293 — DELETE 语句不带 WHERE 子句。对比 line 294-300，checkpoint 和 failure 表有 `WHERE consumer_id = ?`。Schema 中 timeline 和 run_results 表没有 `consumer_id` 列。
- **影响**: 当前架构中只有一个 consumer（MinimalReadModelProjectionConsumer），所以暂不触发。但这是架构脆弱点——如果 schedule 中新增第二个 consumer，或同一 consumer 有两个 instance 并发运行，数据将静默丢失。至少应在 docstring 或设计文档中明确记录此单租户假设。
- **建议改法和验证点**: 短期：在模块级 docstring 中明确记录数据表的单 consumer 所有权假设。长期：为数据表添加 `consumer_id` 列并在 DELETE 中过滤。
- **修复风险（低）**: 当前行为不变，只是文档化。
- **严重程度（中）**: 架构假设未文档化，对多 consumer 场景构成静默数据丢失风险。

### F4-未修复-低-`_ensure_checkpoint` 在读多写少场景使用 write transaction

- **入口/函数**: `ProjectionRunner._ensure_checkpoint` (dayu/host/projection.py:466-479)
- **文件(行号)**: `dayu/host/projection.py:466-479`
- **输入场景**: `run_once` 为每个 consumer 调用 `_ensure_checkpoint`，checkpoint 已存在时只需读取（最常见场景）。
- **实际分支**: `_ensure_checkpoint` 调用 `run_write` → 执行 `BEGIN IMMEDIATE` → `ensure_projection_checkpoint` → 99.9% 情况下只做 `read_projection_checkpoint`（SELECT）→ `COMMIT`。实际无写入，但持有了 write lock。
- **预期行为**: checkpoint 已存在时应使用 `run_read` 读取。
- **实际行为**: `BEGIN IMMEDIATE` 获取 reserved lock，阻塞其他 writer。在高并发下增加不必要的 lock contention。
- **直接证据**: projection.py:471 — `self._transaction_runner.run_write(...)`。durable/projection.py:106 — `ensure_projection_checkpoint` 先读后写，绝大多数场景下 checkpoint 已存在仅需读。
- **影响**: 轻微性能影响，不涉及正确性。
- **严重程度（低）**: 性能优化点，非阻塞。

## Architecture Notes

以下不是 findings，而是对架构选择的可追溯记录：

1. **Schema 版本 4→5 无迁移路径**: 与项目约定一致——只支持 fresh (0) 或完全匹配的 schema 版本。需要 ops 团队知晓升级意味着重建数据库。
2. **Read API 不使用 projection 表**: `get_session` / `get_run` / `stream_run_events` 直接从 durable 状态表和 event_log 读取，不查询 `host_run_results` / `host_session_timeline_items`。Projection 表在此 phase 为"只写"——它们是 projection consumer 的输出，不是公共 reads 的输入。如果 Phase 8 的意图是切换到 projection-based reads，这是集成遗漏。
3. **`HostEventClass` 桥接正确**: `EventLogRow.event_class` (内部 `EventClass` StrEnum) → `_event_view_from_row` → `HostEventClass(row.event_class.value)` 转换是类型安全的，因为两个 enum 的 `.value` 字符串完全一致。但如果 durable `EventClass` 新增成员而未同步更新 public `HostEventClass`，会在运行时抛出 `ValueError`——两层之间缺少编译期枚举成员一致性检查。
4. **`reset_minimal_read_model_projection` 单租户假设**: 数据表（timeline, run_results）无 `consumer_id` 列，重置是无条件全量 DELETE。当前只有一个 consumer，安全但脆弱。
5. **`advance_projection_checkpoint` 为所有事件无条件推进**: 正确——checkpoint 语义是"已扫描到此"，不是"已应用到此"。
6. **`failure_count` 语义正确**: 记录自上次成功推进以来的连续失败次数，恢复后清零。
7. **Wait adapter 异常隔离从 `RuntimeError` 扩到 `Exception`**：正确——一个 adapter 失败不应停止 poll 循环。
