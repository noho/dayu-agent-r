### 01-未修复-严重-Web 抓取的私网策略可被 redirect、meta refresh 与浏览器导航绕过

- **入口/函数**: `fetch_web_page` -> `_fetch_web_page_business(...)` -> requests / Playwright 抓取链。
- **文件(行号)**: `dayu/tools/web/web_tools.py:1786-1824`；`dayu/tools/web/web_fetch_orchestrator.py:340-395, 561-566, 611-624, 794-840`；`dayu/tools/web/web_playwright_backend.py:1110-1129`。
- **输入场景**: 默认 `allow_private_network_url=False`，调用一个安全公网 URL；该站点以 HTTP 30x、即时 meta refresh 或浏览器导航跳到 `127.0.0.1`、RFC1918、link-local/云 metadata 地址。
- **实际分支**: 只在初始 URL 上调用 `_is_safe_public_url`；requests 的 warmup、HEAD/GET probe 和正文 GET 均允许自动 redirect，且不复验 `response.url`；meta refresh 目标仅做 normalize/防环后成为下一轮 `current_url`；Playwright route 只过滤资源类型，`page.goto` 的后续导航不复验目的地址。
- **预期行为**: 禁用私网时，每一个网络 hop 和最终解析地址都必须经过同一个安全 owner 校验；任何公网到私网、loopback 或 link-local 的跳转都应 fail closed。
- **实际行为**: 攻击者控制的公网页面可以诱导工具访问宿主内网或 metadata 服务，并把响应转换为 Markdown 投影给 LLM。
- **直接证据**: 初始检查只发生在 `web_tools.py:1811`；三条 requests 路径显式 `allow_redirects=True`（`web_fetch_orchestrator.py:561-566,611-624,802-807`）；`_resolve_meta_refresh_follow_target` 在 `395` 直接返回目标，`832-840` 直接继续抓取；Playwright 在 `1110-1129` 未注入 URL safety checker。主审复核纯函数时，link-local meta refresh 目标会被直接返回。
- **影响**: SSRF，可读取本机/内网服务、云凭据或管理端点；结果还会进入 Agent 上下文，形成高成本机密泄漏。
- **建议改法和验证点**: 建立单一安全 transport owner：禁自动重定向并逐 hop 校验 `Location` 与 DNS 解析结果，复验最终 peer/URL；meta refresh 和所有 Playwright navigation request 复用同一校验；覆盖公网到 loopback/private/link-local、跨协议、DNS rebinding、warmup/probe/正文/browser 全路径。
- **修复风险（低/中/高）**: 高。
- **严重程度（低/中/高/严重）**: 严重。

### 02-未修复-严重-Fins 同 ticker 并发任务共享无 owner 的 batch，成功写入可被另一任务回滚

- **入口/函数**: `FinsIngestionRuntime.activate_observation(...)` -> `FinsIngestionThreadExecutor.submit(...)` -> FS repository `_execute_with_auto_batch(...)`。
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:1165-1188,2462-2496`；`dayu/fins/service_runtime.py:347-370`；`dayu/fins/storage/_fs_repository_factory.py:13-21`；`dayu/fins/storage/_fs_storage_infra.py:118-120,149-199,259-335`。
- **输入场景**: 两个 download/preprocess/upload observation 同时写同一 ticker；任务 A 已开启 batch，任务 B 随后进入任意仓储写入口。
- **实际分支**: 默认 executor 为每次 observation 新建线程，所有窄仓储共享一个 core；`_execute_with_auto_batch` 只检查 ticker 是否存在于全局 `_active_batches`，命中后直接在当前 staging 执行 B 的 operation，不校验 token、线程或 operation owner，也不获取 ticker lock。
- **预期行为**: 只有当前 batch owner 持显式 token 才可重入；不同任务必须在 ticker lock 上串行化或 fail fast，返回成功的写入必须拥有独立可提交事务。
- **实际行为**: B 把数据写进 A 的 staging 后即可返回成功；A 随后 rollback 会删除 B 的结果，A commit 也可能把两条业务操作交叉提交。无锁 `_active_batches` 还允许 begin/commit/rollback 竞态。
- **直接证据**: 多线程提交在 `ingestion_runtime.py:1183-1188,2493-2496`；共享 core 在 `service_runtime.py:347-370`；batch token 只按 ticker 存储（`_fs_storage_infra.py:118-120,198`）；关键绕过位于 `317-320`；rollback 删除 staging 位于 `259-293`。
- **影响**: 财报数据丢失、交叉污染、返回成功但持久化失败、manifest/blob/meta 不一致，且故障取决于并发时序，难以审计和恢复。
- **建议改法和验证点**: storage owner 将 batch 与显式 transaction token/线程上下文绑定；所有写入口验证 owner，非 owner 必须等待文件锁或拒绝。增加共享 core 同 ticker 多线程测试：A rollback/B 已返回、A commit/B 写入、begin/commit/rollback 竞争、不同 ticker 并发。
- **修复风险（低/中/高）**: 高。
- **严重程度（低/中/高/严重）**: 严重。

### 07-未修复-高-promotion 瞬时异常会丢弃唯一 session wakeup，使已接受 Run 无限期不启动

### 08-未修复-高-异步 Host 公共面在 event loop 直接执行同步 SQLite 与 time.sleep backoff

- **入口/函数**: `_PublicHostHandle` async commands/reads；scheduler heartbeat/promotion/dispatch/ingest。

- **输入场景**: 另一进程或独立 wait-poller connection 持 SQLite write lock，public cancel/read/submit 或后台 ingest/heartbeat 同时执行。

- **建议改法和验证点**: 建立拥有 SQLite connection 的单线程 DB actor/executor 或真正 async access 层；不要把现有 thread-affine connection 直接 `to_thread`。用外部 connection 持锁，断言 event-loop tick、cancel/watch/heartbeat 仍可推进。
- **修复风险（低/中/高）**: 高。
- **严重程度（低/中/高/严重）**: 高。
