### 1-未修复-[中]-trace analyzer 仍按旧 fetch_more 维度判断，P8.5 普通工具调用链路会误报或漏报
- **入口/函数**: `utils.analyze_tool_trace_host.analyze_trace_root` -> `_detect_truncation_gaps` / `_detect_fetch_more_unknown_cursor`
- **文件(行号)**: `utils/analyze_tool_trace_host.py:400`, `utils/analyze_tool_trace_host.py:420`, `utils/analyze_tool_trace_host.py:442`, `utils/analyze_tool_trace_host.py:473`; 生产 trace 写入点在 `dayu/host/_tool_trace_projection.py:257`, `dayu/host/_tool_trace_projection.py:282`
- **输入场景**: 一个业务工具返回 `truncation_has_more=True`，随后模型按 P8.5 新链路发起普通 `tool_name="fetch_more"` 工具调用，cursor / scope_token 位于该 `fetch_more` 记录的 `arguments_json` 中。
- **实际分支**: `ToolTraceObserver` 写 `ToolCallRecord` 时把 `fetch_more_consumed_cursor`、`fetch_more_next_cursor`、`fetch_more_chunk_size`、`fetch_more_has_more` 固定写成 `None`；analyzer 仍只检查 `fetch_more_consumed_cursor` 是否存在。
- **预期行为**: P8.5 plan 明确要求删除专属 facts 后，analyzer 仍要能从 ordinary tool payload / trace record 识别 truncation 未续读、`fetch_more` unknown cursor / wrong scope、重复 `fetch_more` 与失败 outcome。
- **实际行为**: `_detect_truncation_gaps` 对每条 `truncation_has_more=True` 的业务工具记录都会认为同一 `(run_id, tool_call_id)` 没有 fetch_more；真实 `fetch_more` 是另一条普通 tool call 记录，且不会设置旧的 `fetch_more_consumed_cursor` 字段。`_detect_fetch_more_unknown_cursor` 同样不会解析 `tool_name="fetch_more"` 的 `arguments_json`，因此无法发现 unknown cursor / wrong scope。
- **直接证据**: `dayu/host/_tool_trace_projection.py:282-285` 将所有 fetch_more 维度字段写为 `None`；`utils/analyze_tool_trace_host.py:420-431` 只用 `fetch_more_consumed_cursor` 判定是否已续读；`utils/analyze_tool_trace_host.py:467-484` 只用 `truncation_cursor`、`fetch_more_next_cursor`、`fetch_more_consumed_cursor` 维护 cursor 集合，不读取 ordinary `fetch_more` arguments。
- **影响**: trace 诊断会对已正确续读的 run 产生 truncation gap 误报，同时漏掉模型传入未知 cursor / 错误 scope 的真实问题；P8.5 把 fetch_more 收回普通 tool call 后，核心验收工具失去有效性。
- **建议改法和验证点**: 更新 analyzer 以 `tool_name=="fetch_more"` 的普通 tool call record 为补读事实源，解析 `arguments_json.cursor` / `arguments_json.scope_token` 和 failed outcome；将 truncation cursor 与后续 fetch_more arguments 按 run 和 source_event_position 关联，而不是按原业务 `tool_call_id` 的旧 fetch_more 字段关联。同步改 `tests/utils/test_analyze_tool_trace_host.py`，用当前 `ToolTraceObserver` 真实输出格式构造 fixture。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-[中]-字符串形式的 Authorization 凭证不会被 scrub，普通工具结果可把显式凭证写入 EventLog/trace
- **入口/函数**: `translate_engine_event` / `serialize_run_event_data` / `ToolTraceObserver._emit_tool_call` 经 `scrub_tool_execution_outcome` 和 `scrub_explicit_credentials`
- **文件(行号)**: `dayu/host/_credential_scrub.py:22`, `dayu/host/_credential_scrub.py:38`, `dayu/host/_credential_scrub.py:64`; 测试覆盖缺口在 `tests/host/test_phase6_run_event_serializer.py:135`
- **输入场景**: 工具结果或工具失败消息是字符串，例如 `Authorization: Bearer sk-live`，或普通字段内包含 `x-api-key: sk-live` 文本。
- **实际分支**: `scrub_explicit_credentials` 对字符串只调用 `_scrub_text_credential_assignments`；该正则只匹配 `api_key`、`credential`、`password`、`client_secret`、`private_key`，没有匹配 `authorization` 或 `x-api-key`。
- **预期行为**: 当前 Host README 和 P8.5 plan 都把 `Authorization` / API key / explicit credentials 作为 EventLog / trace 必须 scrub 的明确凭证；字段名形式和常见 header 文本形式都应被同一策略覆盖。
- **实际行为**: 对象字段名为 `"authorization"` 时会在 `_EXPLICIT_CREDENTIAL_KEYS` 命中，但字符串 payload 中的 `Authorization: Bearer ...` 完全不命中，随后会被序列化到 EventLog 或 trace 的 `result_value_json` / `failure_message`。
- **直接证据**: `_EXPLICIT_CREDENTIAL_KEYS` 包含 `"authorization"` 与 `"x-api-key"`（`dayu/host/_credential_scrub.py:26-27`），但 `_TEXT_CREDENTIAL_ASSIGNMENT_PATTERN` 不包含这两个 key（`dayu/host/_credential_scrub.py:38-40`）；字符串路径直接调用该正则（`dayu/host/_credential_scrub.py:64-65`）。新增 serializer 测试只覆盖对象字段 `"API_KEY"` 和 `"api_key"`，没有覆盖字符串 header 场景（`tests/host/test_phase6_run_event_serializer.py:142-160`, `tests/host/test_phase6_run_event_serializer.py:173-206`）。
- **影响**: 工具或 provider adapter 只要把 Authorization header 放进错误文本、调试文本或字符串结果，就会绕过本次新增 scrub，进入 durable EventLog、trace JSONL 和后续调试导出；这与“只保留普通 cursor/scope_token，但 scrub 明确凭证”的边界相冲突。
- **建议改法和验证点**: 将文本 scrub 的 key 集合与 `_EXPLICIT_CREDENTIAL_KEYS` 同源，至少覆盖 `authorization`、`x-api-key`、`api-key`，并正确处理 `Authorization: Bearer <token>` 这类带 scheme 的值，避免只替换 `Bearer` 而留下 token。补充 serializer、event translation 和 trace projection 的字符串 payload 测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
