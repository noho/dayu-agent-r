### F3-未修复-低-_task_aware_event_stream 的 drain timeout 可能在极端负载下过早结束事件流

- **入口/函数**: `LocalRunHarness._task_aware_event_stream`
- **文件(行号)**: `dayu/host/_run_harness.py:738-801`（特别是 line 776-787）
- **输入场景**: `_run_to_store` 后台 task 因 owner-lost CAS miss 提前退出，但 EventLog subscription 中仍有已落库但尚未被拉取的事件
- **实际分支**: `background_task` 先于 `next_task` 完成 → 进入 drain 窗口 → 等待 `_TASK_AWARE_STREAM_DRAIN_SECONDS`（0.05 秒）→ 若该窗口内无事件则 `return` 结束流
- **预期行为**: 应确保所有已在 EventLog 中落库的事件都被拉取到
- **实际行为**: 0.05 秒的硬超时可能在极端负载（如磁盘 I/O 严重拥塞、SQLite 在 WAL 模式下 checkpoint 阻塞）下不足以拉取已持久化的事件
- **直接证据**: `_run_harness.py:26` 定义 `_TASK_AWARE_STREAM_DRAIN_SECONDS: float = 0.05`，line 776-787 用此值做 `asyncio.wait` timeout
- **影响**: 极端负载下上层 `async for` 可能在仍有可拉取事件时提前结束，导致 RunResult 缺失终态事件。但需注意：owner-lost 路径下 task 已退出不会再写新事件，subscription 中是否还有待拉取事件取决于 EventStore 的 notify 时机——在 `DurableRunEventStore` 实现中，append 在事务提交后 notify，因此 50ms 窗口通常足够
- **建议改法和验证点**: 可将 timeout 默认值提高到 1-2 秒以增加安全边际，或在 drain 循环中做多次重试（最多 N 次而非单次 timeout）。当前值对正常负载足够，但作为防御性编程可适当放宽
- **修复风险（低）**: 仅影响事件流结束时机，不影响数据正确性（事件已经落库，下次查询可见）
- **严重程度（低）**: 仅极端负载下的理论边界，实际触发概率低

## Open Questions

1. **DurableConversationMemoryStore 的 `_lock`（asyncio.Lock）与 DurableRunEventStore 的事务锁交互**：`_conversation_memory_durable.py:151` 的 `_lock` 在 `project_run_events` 中获取（line 167），但 `project_run_events_in_transaction` 在 observer 路径中不获取 `_lock`（line 192 注释说明 observer 进入是单线程串行）。如果在 coordinator 之外的其他路径（如 `apply_patch`）与 observer 并发访问，`apply_patch` 持有 `_lock` 而 observer 不持有——是否存在 observer 写入与 `apply_patch` 写入之间的竞争？当前设计依赖 coordinator 的串行化保证 observer 不与自身冲突，但 observer 与 `apply_patch` 之间的隔离仅靠 `_lock` 的一侧持有——需确认所有 observer 外部路径都正确持有 `_lock`。

2. **Multiprocess stress tests 中 fake clock 的跨进程行为**：`test_phase8_multiprocess_stress.py` 在多进程场景下使用 fake clock。子进程中 fake clock 的状态如何传递？如果是模块级共享状态，多进程下的 fork 行为（copy-on-write）可能导致每个子进程看到不同的 clock 快照。需确认测试的 fake clock 注入路径不依赖进程间共享可变状态。

3. **ToolRuntime cursor registry 在多进程部署下的可用性**：`_tool_runtime.py:365` 的 `_records_by_cursor` 是进程内内存状态。在负载均衡的多进程部署中，创建 cursor 的进程与处理 `fetch_more` 请求的进程可能不同，导致 cursor not found。当前代码将此定义为 transient coordination state（line 339-340），但未在 README 或 design doc 中明确说明这一限制对部署拓扑的约束。

4. **`_append_overflow_acquire_failure_terminal` 非 atomic 路径的 terminal draft 风险**：`_run_harness.py:1658` 在 `_can_atomic_terminal_close` 为 False 时走 `_resolve_attempt_appender(active_attempt).append(draft)`，其中 `draft` 为 terminal type。虽然实际触发概率低（supervisor 路径下 `_can_atomic_terminal_close` 通常为 True），若触发将与 F11/F12 同模式 ValueError。需确认该路径是否需要防御性升级。

5. **`recover_stale_attempts` 使用快照 `now` 贯穿整个 scan 链路**：`_attempt_supervisor.py:778` 捕获 `now` 后再未更新。recovery scan 处理多个候选 attempt 期间 `now` 可能已过时，与 F14 叠加放大竞态窗口。建议将 `now` 获取下推到 `_process_recovery_candidate` 事务内部。

6. **`_collect_missing_session_ids` 将运行中 session 也纳入 repair 候选**：`_conversation_memory_durable.py:349-359` 查询条件为 `e.kind = CANONICAL AND s.session_id IS NULL`，未限制 terminal event type。每个运行中且暂无 snapshot 的 session 触发一次无效的全 EventLog 扫描后才被 `_has_terminal_event` 过滤跳过。建议在 SQL 中直接加 `e.type IN (FINAL_ANSWER, RUN_FAILED, ...)` 条件。

## Residual Risk

1. **多进程并发竞争**：虽然 `test_phase8_multiprocess_stress.py` 提供了多进程压力测试，但真实生产中进程崩溃、信号丢失、部分写入等场景无法在单元测试中完整模拟。SQLite 在并发写入（特别是多进程 + WAL 模式）下的行为依赖文件系统语义，不同 OS/文件系统可能有不同表现。

2. **Lease TTL 与 real-world latency 的匹配**：默认 lease TTL 为 30 秒（`_DEFAULT_LEASE_TTL_SECONDS`），renew interval 为 10 秒。在极端网络延迟或 Engine API 响应时间超过 30 秒的场景下，lease 可能在正常 attempt 执行期间过期，触发不必要的 owner-lost 收口。当前没有机制根据实际 Engine 延迟动态调整 TTL。

3. **DurableConversationMemoryStore repair 的大 session 性能**：`_repair_missing_session_snapshots_locked` 对每个缺失 session 做全量 EventLog 扫描（`_fetch_canonical_events_for_session` 按 position 分页拉取全库事件再按 session_id 过滤，见 F15）。在 EventLog 积累大量事件后（如千万级），repair 多个 session 的耗时可能显著增长。PR body 中已将此标记为 P9 关注项。

4. **端到端集成测试缺口**：以下生产场景缺少自动化回归保护：
   - Engine 在 attempt 执行中返回 malformed response 时的 harness 行为
   - Observer drain 与 attempt close 的并发时序
   - Context compaction 在 durable 路径下与 attempt lease 的完整交互
   - 多 run session repair 的正确性（见 F13）
   - Recovery scan 与正常 renew 的并发竞态（见 F14）

5. **`_compact_or_fail` / `_append_compact_exception_failure` 的 terminal draft 拒绝传播链**：F12 描述的 ValueError 从 `_compact_or_fail` → `_append_compact_exception_failure`（同样抛出 ValueError）→ 外层 finally 的 `_finish_attempt_if_durable`。此链路上 `_run_to_store:1055` 的 `except AttemptFencingError` 不匹配 `ValueError`，导致异常未被任何收口分支捕获后转为可控终态闭合。F12 修复后此风险自动消失。
