### 2. manual corruption acceptance 是否显式映射

**结论: 通过。**

Plan amendment 显式处理了 Issue #41 的 `manual corruption` acceptance signal：

- Line 49: "Issue #41 的 `manual corruption` 不作为独立 failure kind；手动 SQL 修改 durable row 导致的损坏会被 `invalid_json`、`schema_mismatch`、`digest_mismatch`、`unsupported_item_kind` 或 `storage_read_failed` 捕获。"
- Line 55: S1 测试矩阵包含 "manual SQL corruption mapped to digest mismatch"。
- Line 84: S2 测试包含 "digest mismatch classification via manual SQL corruption"。

映射逻辑自洽：手动 SQL 修改可能破坏 JSON 语法（→ `invalid_json`）、改变 JSON shape（→ `schema_mismatch`）、导致 digest 不匹配（→ `digest_mismatch`）、写入旧 `verified_fact` item kind（→ `unsupported_item_kind`），或触发无法归入前四类的读取错误（→ `storage_read_failed`）。不需要独立的 `manual_corruption` kind。

### 3. storage_read_failed 测试触发是否具体可验

**结论: 通过。**

Plan amendment（line 86）将 monkeypatch 策略从原先模糊的 "classifier/read operation" 细化为：

> "monkeypatching the classifier's module-private snapshot row reader helper to raise `sqlite3.OperationalError`"

明确了三个关键要素：
- **monkeypatch 目标**: classifier 内部的 module-private snapshot row reader helper（per-row 粒度的辅助函数，非全表 scan）
- **注入异常类型**: `sqlite3.OperationalError`
- **语义保证**: "production corruption semantics remain unchanged"

此外，plan 还区分了两个 `storage_read_failed` 触发路径：
1. **scan query 自身失败**（line 50）→ `storage_read_failed` with `snapshot_id=None`
2. **per-row reader helper 被 monkeypatch**（line 86）→ `storage_read_failed` with row identity

两条路径覆盖了"全表扫描失败"和"单行读取失败"两种场景，测试可验。

**直接证据**: 当前 `dayu/host/durable/memory.py:1006` 已有 `_snapshot_row_from_host_row(transaction, row)` 作为 per-row reader；classifier 的 helper 可复用类似模式但 catch exception 而非 raise。
