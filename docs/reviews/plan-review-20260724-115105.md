### 3.2 裁决2：O(1) cold snapshot lock critical section

**Controller 要求**: 锁内只做 binary open + fstat prefix capture；释放锁后从同一 handle 精确读 prefix；覆盖短读、追加、替换/截断可观察失败。

- §7.4 覆盖：lock timeout/acquire/release failure → fatal，无 unlocked fallback。

**代码证据**:

- 现有 producer 在 `dayu/host/tool_trace.py` 行 491-501 使用 `with file_lock(...)` context manager，timeout=`_LOCK_TIMEOUT_SECONDS=5.0`。

**验证结果**: ✅ **已闭合**。临界区设计完整，所有失败路径有明确 fatal reason code。

**可实现性攻击——锁外长读的测试稳定性**:

计划 S1 测试要求："用 barrier 将 reader 的 prefix read 阻塞在释放 lock 之后，启动真实 producer append；断言 writer 在其既有 5 秒 timeout 前完成且无 RuntimeFileLockTimeoutError，再释放 reader，并断言本次 snapshot 不含新 append、下一次包含。"

此测试设计不依赖 `time.sleep`，使用 barrier（`threading.Barrier` 或等价原语）精确协调：
1. Reader 获取锁 → open → fstat → 释放锁 → barrier.wait()（阻塞）
2. Writer 线程：barrier.wait() → 获取锁 → append cold line → 释放锁
3. Reader：barrier.wait() 返回 → read prefix → 断言不含新行
4. 第二次分析：read prefix → 断言包含新行

Barrier 机制确保 writer 在 reader 释放锁之后、读取 prefix 之前执行，不依赖时间竞态。✅

**可实现性攻击——同一 handle 在锁释放后的语义**:

POSIX 语义下，已打开的 fd 在 close 前始终引用同一 inode。`os.fstat(fd)` 返回的 `st_dev`/`st_ino` 在 fd 生命周期内不变。因此 "同一 handle 的 file identity 变化" 检查在 POSIX 上是 trivially true（除非 kernel bug）。计划将此检查列为 defense-in-depth，不是唯一安全依赖。

Windows 语义下 `st_ino` 可靠性较低。计划写 "至少保留平台可用的 device/inode identity" 准确表达了平台差异。

**可实现性攻击——live writer 在 reader 持锁期间的阻塞**:

Reader 临界区为：`acquire → open(path, "rb") → os.fstat(fd) → release`。在本地 SSD 上，这通常 < 1ms。Producer 的 lock timeout 为 5 秒。即使 reader 在慢盘/NFS 上需要 100ms，producer 也有 50x 余量。不可能因 reader 导致 producer lock timeout。

但有一个边缘场景：reader 在 `open()` 调用中被阻塞（例如路径是挂载点、网络文件系统无响应）。此时 reader 持有锁，producer 等待。计划将此映射为 fatal（open 失败 → `cold_snapshot_read_failed`），reader 不会无限期持锁。`filelock` 库的 `acquire` 在 context manager `__exit__` 中释放锁，因此即使 open 抛异常，锁也会释放。✅

### 4.2 Lock 机制：binary open+fstat，锁外精确读 prefix

**攻击目标**: 验证在 append/replace/truncate/short-read/close failure 和 live writer 下的完整性。

**逐个失败场景分析**:

| 场景 | 计划处理 | 评估 |
|---|---|---|
| **正常 prefix read** | lock → open("rb") → fstat st_size → release → handle.read(st_size) in loop → close | ✅ |
| **Append after prefix capture** | 追加 bytes > st_size，reader 只读 st_size bytes，追加部分留待下次 | ✅ |
| **Truncate below prefix** | `handle.read(st_size)` 返回 < st_size bytes → fatal `cold_snapshot_read_failed` | ✅ |
| **Short read (non-truncate)** | 循环读取直到 exact st_size bytes；中途 EOF → fatal | ✅ |
| **File replaced (different inode)** | Handle 仍引用旧 inode → 读取旧内容 → fstat identity 一致 → 旧 prefix 有效；path 替换后不切新 path | ✅ |
| **Close failure** | `handle.close()` 通常不失败；失败时作为 fatal | ✅ |
| **Lock acquisition timeout** | `RuntimeFileLockTimeoutError` → fatal `cold_snapshot_lock_timeout` | ✅ |
| **Lock acquisition failure** | `RuntimeFileLockError` → fatal `cold_snapshot_lock_failed` | ✅ |
| **Lock release failure** | Context manager `__exit__` 中 release 失败 → `RuntimeFileLockError` → fatal | ✅ |
| **open() failure** | Path 在 discovery/load 间消失 → `cold_snapshot_read_failed`；锁在 context manager exit 中释放 | ✅ |

**live writer 并发测试分析**:

计划测试设计（S1 §14.1 行 1726）：
```
Reader:  acquire → open → fstat → release → BARRIER_WAIT → read prefix
Writer:                                    BARRIER_WAIT → acquire → append → release
Reader:                                                                     → 断言不含新行
Second analysis:                                                              → 断言包含新行
```

Barrier 机制确保 writer 在 reader 释放锁之后、读取 prefix 之前执行，不依赖 `time.sleep`。Writer 完成 append 后 reader 才从 barrier 释放。因此：
- Writer 在 reader 不持锁期间获取锁 → 不会 timeout
- Reader 读取 prefix 时 writer 已释放锁 → reader 不阻塞 writer
- 新 bytes 在 prefix 之后 → 本次不可见
- 下次分析读取更新后的 prefix → 新 bytes 可见

**反例尝试**:
- 如果 writer 在 reader fstat 之后、release 之前尝试 acquire lock → writer 等待（最多 5 秒）→ reader 在 O(1) 时间内 release → writer 获取锁 → writer 在 5 秒 timeout 前完成。✅
- 如果 reader 的 barrier 永远不被释放（测试设计错误）→ 测试会超时失败，不会产生 false positive。✅

**结论**: lock 机制覆盖所有声称的失败场景，测试设计可稳定证明锁外长读。✅

```
    # read transaction closed HERE — 不持 SQLite snapshot 进入 lock
    store.close()

  # Step 2: cold read (如果 cold_jsonl_path 存在)
  lock_path = _tool_trace_cold_lock_path(source.cold_jsonl_path)
  with file_lock(lock_path, ...):
    handle = open(source.cold_jsonl_path, "rb")
    st = os.fstat(handle.fileno())
    prefix_length = st.st_size
    identity = (st.st_dev, st.st_ino)
  # lock released
  cold_bytes = b""
  while len(cold_bytes) < prefix_length:
    chunk = handle.read(prefix_length - len(cold_bytes))
    if not chunk:
      raise fatal
    cold_bytes += chunk
  handle.close()
  cold_lines = strict_parse_jsonl(cold_bytes.decode("utf-8"))

  # Step 3: join
  if hot_watermark is not None and hot_rows empty and cold_lines not empty:
    # hot-empty + cold-late → all input_changed_during_analysis
  elif hot_watermark is not None and hot_rows empty and cold_lines empty:
    # hot-empty + cold-empty → normal empty report
  ...
```

1. Hot read transaction → close ✓（在获取 cold lock 前关闭，避免同时持有 SQLite snapshot 和 file lock）
2. Cold lock acquire ✓
3. Cold binary open + fstat + release ✓

## 5. Additional adversarial probes

### 5.1 Empty cold file with valid hot rows

**场景**: Workspace directory mode，cold JSONL 文件存在但为空（0 bytes），hot DB 有 N 行。

**计划处理**:
- §7.4: cold snapshot 读取 0 bytes → 0 cold lines
- §8.3 join: hot rows 存在但 cold 缺失 → `missing_cold_trace` confirmed integrity error
- 这是正确的：producer 在提交 hot transaction 前已 append cold line，因此 hot 有行但 cold 为空是 confirmed mismatch。

**验证**: ✅ 正确处理。空 cold 文件不会导致 parser error（0 bytes 产生 0 lines）。

### 5.2 Cold file with only empty lines

**场景**: Cold JSONL 包含空行。

**计划处理**:
- §8.2: strict parser 对空行记录 input diagnostic（不是 finding）
- 空行不进入后续 rules
- 这是正确的：空行不是 valid record 也不是 malformed record，只是空白。

**验证**: ✅ 正确处理。

### 5.3 Analyzer run during producer catch-up

**场景**: Operator 在 producer catch-up（批量写入 cold lines）期间运行 analyzer。

**计划处理**:
- §7.4: lock 确保 reader 获取一致 snapshot（prefix at lock time）
- Producer 追加的 lines 在 prefix 之后 → 本次不可见
- Hot watermark 捕获 reader 的 hot snapshot → cold rows 中 `event_sequence > watermark` 的标记为 `input_changed_during_analysis`
- 这是正确的：不是损坏，只是观察窗口变化。

**验证**: ✅ 正确处理。

### 5.4 read_tool_trace_page 的 API 形状
