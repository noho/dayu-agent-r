### 2-未修复-低-`_ManagedHostSessionAttachment.aclose()` 的 `_close_task` 竞态仅在 asyncio 单线程模型下安全

- **入口/函数**: `_ManagedHostSessionAttachment.aclose`
- **文件(行号)**: `dayu/host/open_host.py:787-791`
- **输入场景**: 两个并发 coroutine 同时调用同一 managed attachment 的 `aclose()`。
- **实际分支**: `if self._close_task is None:` 检查与 `asyncio.create_task(...)` 之间无 `await`，因此在单 event loop 合作式调度下原子。
- **预期行为**: 只启动一个 cleanup task，重复调用共享同一 task。
- **实际行为**: 当前实现依赖 Python asyncio 的单线程合作式调度保证原子性。若未来迁移到多 event loop 或出现 `asyncio.create_task` 在特定条件下 yield（当前不会），该检查将不再安全。
- **直接证据**: `dayu/host/open_host.py:787-791`：`_close_task is None` 检查与 `create_task` 赋值之间无 `await`，Python asyncio 文档明确 `create_task` 不会 yield 控制权。
- **影响**: 当前实现正确。仅在架构演化为多 event loop 共享 managed attachment 时成为真实竞态。
- **建议改法和验证点**: 可考虑使用 `asyncio.Lock` 或 `_close_task` 的双重检查模式加文档说明"单 event loop 下安全"。非当前阻塞项。
