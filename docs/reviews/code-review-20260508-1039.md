## Findings

### 1. [Medium][已修复] `_log_runner_call_completed` 异常路径与类内其它 state-is-None 处理不一致

**文件**: [dayu/engine/agent.py:1874-1902](dayu/engine/agent.py#L1874-L1902)

**问题**: 当 `_last_iteration_state is None` 时，`_log_runner_call_completed` 直接 `raise RuntimeError`。但同文件中所有其它检查 `state is None` 的位置（L554、L663、L1566）均采用 `_LOGGER.critical(...)` + `yield _make_failed_or_cancelled_terminal_with_close(...)` 模式，显式记录 CRITICAL 日志后再返回 terminal event。

此处 RuntimeError 会被 `_run_one_iteration` 的 `except Exception` 捕获并转为 `RUN_FAILED` terminal，但日志级别降为 ERROR 而非 CRITICAL，且错误上下文（iteration_id、iteration_index）丢失在异常消息中而非结构化日志字段里。

**可能后果**: 运维排查时，`state is None` 的异常路径日志不一致，增加定位难度。

**建议**: 与类内其它路径对齐：如果 `_log_runner_call_completed` 能接受 state-is-None 是可恢复的，则不抛异常、降级跳过；如果是不可恢复的，则调用方应改为显式 CRITICAL log + terminal return，而非依赖异常传播。

**修复**: `_log_runner_call_completed` 现在在 state 缺失时记录包含 session/run/iteration 结构化字段的 CRITICAL 日志，并返回不可恢复 `missing_terminal` failure；调用方直接产出受控 terminal。`_run_runner_iteration` 的异常分支也补齐 state 缺失保护，避免继续触发二次 `AttributeError`。

### 2. [Low][已修复] `last_run_input_messages_by_run` 诊断缓存与生产 trace 缓存共用 limit，可能持有大量消息

**文件**: [dayu/host/_run_harness.py:235-240](dayu/host/_run_harness.py#L235-L240)

**问题**: `last_run_input_messages_by_run` 缓存与 `last_run_input_build_trace_by_run` 共用 `run_input_trace_cache_limit`（默认值通常为较小的正整数）。但 `tuple[AgentMessage, ...]` 的内存占用远大于 `RunInputBuildTrace`——尤其在多轮场景下，单条 run 的输入消息可能包含完整 conversation history + memory block + tool results。

**可能后果**: 在极端多轮场景下，N 条 run 的消息缓存可能占用可观内存。当前默认 limit 较小（应为个位数），实际风险有限。

**建议**: 如果该缓存确实只服务于 smoke 观察，可考虑单独设置更小的 limit 或使用 weakref / 只保留消息计数而非消息本体。

**修复**: `LocalRunHarness` 新增独立 `run_input_message_cache_limit`，默认小于 trace 缓存，并专门用于 `last_run_input_messages_by_run`；补充了 trace 与 message cache 独立淘汰测试，保留 smoke 读取最近 run input 的能力。

### 3. [Low][已修复] `_project_truncation_for_llm` 的 `has_more=False` 路径缺乏显式测试

**文件**: [dayu/engine/agent.py:266-291](dayu/engine/agent.py#L266-L291)

**问题**: `_project_truncation_for_llm` 当 `has_more=False` 时只返回 `{"has_more": false}`，不包含 `next_action` / `fetch_more_args` / `ttl_seconds`。当前测试（`test_llm_projection_shapes`、`test_engine_tool_projection_includes_llm_fetch_more_hint`）只覆盖了 `has_more=True` 的路径。

代码逻辑本身正确（`if truncation.has_more` 条件短路），但缺少 `has_more=False` 的回归保护。

**可能后果**: 如果未来有人误改 `if truncation.has_more` 条件，不会被现有测试捕获。

**建议**: 补充一个 `has_more=False` 的测试用例，断言投影结果不包含 `next_action` 和 `fetch_more_args`。

**修复**: 新增 `has_more=False` projection 回归测试，断言只保留 `{"has_more": false}`，不包含 `next_action`、`fetch_more_args`、`ttl_seconds`、`scope_token` 或 `scope_hash`。

### 4. [Info] `_redact_tool_result_truncation` 在 `ToolResultSuccess.truncation=None` 时仍执行 replace

**文件**: [dayu/host/_event_translation.py:137-153](dayu/host/_event_translation.py#L137-L153)

**问题**: 当 `result.truncation is None` 时（绝大多数非截断工具调用），函数提前 return，无性能问题。但当 `truncation` 不为 None 时，`replace(result, truncation=None)` 会创建一个新 `ToolResultSuccess` 实例。由于 `ToolResultSuccess` 是 frozen dataclass，这是正确的做法，但值得注意：`meta` 字段会被正确保留（`replace` 只改变指定字段）。

**结论**: 实现正确，仅作记录。
