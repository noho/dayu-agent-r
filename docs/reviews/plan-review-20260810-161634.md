## Findings

### F01-未修复-高-HKEX 全 results category code `t2code=-2` 缺少 API 文档验证

- **位置**: §5.3 Provider category discovery, §4.2 Root cause 证据矩阵
- **问题类型**: 契约缺失
- **当前写法**: plan 指定 `t1code=10000, t2_group_code=3, t2code=-2` 作为全 results category spec，声称 `-2` 是"全类"标记。
- **反例/失败场景**: HKEX title search API 的 `t2code=-2` 语义未在 plan 中引用任何 API 文档或真实抓包证据。若 `-2` 在 `t2_group_code=3` 下不表示"業績全类"而是"公告及通告全类"，则查询范围将远超预期，引入大量非财报公告。反之若 `-2` 在该 group 下无效或返回空集，则 DL-F13 根本不会被修复。
- **为什么有问题**: plan 的 §4.2 声称"直接查询 HKEX `公告及通告 -> 業績` 全组后，现有通用分类器能够额外识别 Q2 和 Q4"，但 goal confirmation 中的真实 HKEX 调查使用的是具体 category (`中期業績`/`末期業績`)，不是 `t2code=-2`。两者之间缺少直接证据桥接。
- **直接证据**:
  - goal confirmation: "直接查询 HKEX `公告及通告 -> 業績` 全组后"——未说明具体 API 参数
  - plan §5.3: "新增一个命名的全 results category spec：`t1code=10000`、`t2_group_code=3`、`t2code=-2`"
  - 生产代码 `hkexnews_downloader.py:71`: `_HKEXNEWS_T2_GROUP_ALL: Final[str] = "-2"` 仅用于 FY/H1 的 `t2_group_code`，不用于 `t2code`
  - 生产代码 `hkexnews_downloader.py:75`: `_HKEXNEWS_T2_QUARTERLY_RESULTS: Final[str] = "13600"` 是当前 quarters 使用的具体 `t2code`
- **影响**: 若 `t2code=-2` 语义不符预期，实现 agent 可能写出无法通过真实 provider 验证的代码，或引入大量非财报噪音。evidence run 阶段才发现问题会导致返工。
- **建议改法和验证点**:
  1. 在 plan 中补充 HKEX API 文档引用或真实抓包证据，证明 `t1code=10000, t2_group_code=3, t2code=-2` 返回"業績"全子类
  2. 或改为使用已知的具体子类 codes 并列（如 `中期業績` + `末期業績` + `季度業績`），在 selection 层统一处理
  3. 验证点：evidence run 中 0700 的 HKEX raw rows 必须包含 `中期業績` 和 `末期業績` 类别的公告
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### F02-未修复-高-period 分类 token 优先级在 results vs report 场景下存在误分类风险

- **位置**: §5.3 一般化分类规则, `_infer_fiscal_period_from_text` 当前实现
- **问题类型**: 状态机漏洞
- **当前写法**: plan §5.3 第 3 点要求"results 类结合一般化 category 和 duration/quarter token"，先按 provider material category 区分 report 与 results，再产 identity/coverage。
- **反例/失败场景**: 当前 `_HK_PERIOD_INFERENCE_TOKENS` 中 Q2 的 token 包含 `"SIX MONTHS"`, `"六個月"`, `"半年"`, `"HALF YEAR"`；H1 的 token 包含 `"HALF YEAR"`, `"半年"`, `"半年報"`。两者共享 `"HALF YEAR"` 和 `"半年"`。`_infer_fiscal_period_from_text` 当前逻辑对非"季度"类 category 使用 `order = ("H1", "FY", "Q4", "Q3", "Q2", "Q1")`，即 H1 优先于 Q2。因此当 HKEX 返回 `category_text="中期業績"`、标题含"六個月"时：
  - 若 classifier 先检查 category 不含"季度"，走 H1 优先路径，"六個月"匹配 Q2 token 但 H1 先被检查——但 H1 token 不含"六個月"，所以实际不会误匹配 H1
  - 然而 "HALF YEAR" 同时在 H1 和 Q2 token 中。若标题含 "HALF YEAR" 且 category 为"中期業績"（非"季度"），当前逻辑会先匹配 H1（因为 H1 优先），将 Q2 result 误判为 H1 report
- **为什么有问题**: plan 声称"先按 provider material category 区分 report 与 results"，但没有明确说明如何在代码中实现这一区分。当前 `_infer_fiscal_period_from_text` 只检查 `category_text` 是否含"季度"/"QUARTER"，不区分"業績"vs"報告"。新 classifier `_classify_hk_period_projection` 的设计细节不够 code-generation-ready。
- **直接证据**:
  - `cn_report_selection.py:98-104`: Q2 tokens 包含 `"HALF YEAR"`, `"半年"`; H1 tokens 包含 `"HALF YEAR"`, `"半年"`
  - `cn_report_selection.py:418-420`: 非"季度"category 时 `order = ("H1", "FY", "Q4", "Q3", "Q2", "Q1")`，H1 优先
  - 冻结 HKEX 事实：`11793094` category 为 `中期業績`（含"業績"不含"季度"），标题含"六個月"
- **影响**: implementation agent 需要自行设计 category-first 分类逻辑，可能导致不一致实现或回归。
- **建议改法和验证点**:
  1. 在 plan 中明确 `_classify_hk_period_projection` 的伪代码：先检查 `category_text` 是否含"業績"/"RESULTS"→results 路径；否则→report 路径
  2. results 路径的 token 优先级应为 Q4 > Q3 > Q2 > Q1 > H1 > FY（季度优先）
  3. report 路径的 token 优先级保持 H1 > FY
  4. 验证点：参数化测试必须覆盖 `category_text="中期業績"` + 标题含"六個月"→Q2，`category_text="中期報告"` + 标题含"六個月"→H1
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### F03-未修复-中-slice allowed files 可能不完整，`fiscal_period` 消费者未穷举

- **位置**: §6 Slice 2 & Slice 3 allowed production files
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: Slice 3 列出 13 个 allowed production files，但 plan §6 总则说"发现额外 production call site 时先更新本计划/由 gate owner 裁决，禁止越界顺手修改"。
- **反例/失败场景**: `CnReportCandidate.fiscal_period` 的消费者可能超出已列出的 13 个文件。例如 `dayu/fins/pipelines/cn_pipeline.py` 虽已列出，但 `dayu/cli/commands/fins.py`（CLI entry point）可能在 summary 投影中直接读取 `fiscal_period`。又如 `dayu/fins/pipelines/cn_download_workflow.py` 中的 `_candidate_document_id` 函数（agent 报告位于 lines 806-827）直接使用 `candidate.fiscal_period`，但该文件同时出现在 Slice 2 和 Slice 3 中。
- **为什么有问题**: implementation agent 若在 Slice 3 中发现未列出的 `fiscal_period` 消费者，按 plan 规则必须停止并更新计划，这会造成不必要的中断。更关键的是，若消费者被遗漏但未被发现，可能导致 `fiscal_period` 旧字段与 `period_projection` 新字段并存，违反"不保留 compatibility property"的约束。
- **直接证据**:
  - agent 调查报告：`_candidate_document_id`（cn_download_workflow.py:806-827）使用 `candidate.fiscal_period`
  - agent 调查报告：`_build_base_meta`（cn_download_source_upsert.py:255-260）使用 `candidate.fiscal_period`
  - plan §6 Slice 2 与 Slice 3 均包含 `cn_download_workflow.py`，存在跨 slice 修改同一文件的时序依赖
- **影响**: 实施过程中频繁停止更新计划，或遗漏消费者导致旧新字段并存。
- **建议改法和验证点**:
  1. 在 plan 中预先执行 `rg` 扫描，列出所有 `\.fiscal_period` 的 production 消费者（不包括定义处），确认全部在 allowed files 中
  2. 对 Slice 2/3 共有的文件（`cn_download_workflow.py`, `hkexnews_downloader.py`），明确哪些修改属于哪个 slice
  3. 验证点：§7.3 的 `rg` guard 已覆盖"不存在 candidate compatibility `.fiscal_period`"，但应在 plan 中确认该 guard 的扫描范围
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F04-未修复-中-`covered_fiscal_periods` 新字段对下游 JSON 消费者的兼容影响未评估

- **位置**: §5.3 Identity、durable state 与 public projection
- **问题类型**: 架构边界
- **当前写法**: plan 要求 `FinsDownloadDocumentResult` 与 `FinsDownloadPublicDocument` 新增 `covered_fiscal_periods: tuple[str, ...]`，JSON key 为 `covered_fiscal_periods`。声称"runtime public projection 机械复制"。
- **反例/失败场景**: `FinsDownloadPublicDocument` 的 JSON 序列化被 `dayu/fins/ingestion_runtime.py`、`dayu/cli/output.py`、wait adapter、以及可能的外部消费者使用。新增字段会改变 JSON schema。虽然 plan 说"本 WU 不改 JSON schema/registry 文件"，但运行时 JSON 输出的变化等效于 public contract 变化。若有任何外部脚本、测试 fixture 或下游系统解析 `FinsDownloadPublicDocument` 的 JSON，新增字段可能导致 schema validation 失败或解析错误。
- **为什么有问题**: `FinsDownloadPublicDocument` 是 public contract（名字含 "Public"）。其 JSON 形式是 `FinsDownloadPublicSummary.document_rows` 的元素。任何消费该 JSON 的下游（包括 `tests/cli/test_output.py`、wait adapter tests、以及可能的外部集成）都需要处理新字段。
- **直接证据**:
  - `direct_events.py:255-341`: `FinsDownloadPublicDocument` 是 frozen dataclass，有严格的 `__post_init__` 校验
  - plan §6 Slice 3 allowed test files 包含 `tests/cli/test_output.py` 和 `tests/service/test_fins_wait_adapter.py`，说明 plan 意识到这些消费者需要更新
  - plan §10 风险表："public row 新增 coverage 造成下游漏迁移"→residual owner 为 "download public contract"
- **影响**: 若下游消费者未同步更新，可能在 evidence run 或生产中出现 schema 不匹配。
- **建议改法和验证点**:
  1. 在 plan 中明确 `FinsDownloadPublicDocument` 的 JSON 序列化是否使用 dataclass `asdict` 或自定义 serializer，新字段是否自动进入 JSON
  2. 列出所有 `FinsDownloadPublicDocument` 的 JSON 消费者（rg 扫描 `form_or_period` 或 `document_id` 的使用点）
  3. 验证点：evidence run 中 CLI JSON output 必须包含 `covered_fiscal_periods` 字段且 pyright 通过
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F05-未修复-低-HK bare effective forms 与 CLI summary 显示可能造成用户困惑

- **位置**: §5.2 DL-F14 表格, §9.4 HK Main Board baseline issuer
- **问题类型**: 最佳实践偏离
- **当前写法**: HK bare default 的 effective_periods = `(FY, H1)`，discovery_periods = `(FY, H1, Q1, Q2, Q3, Q4)`。`filters.forms` 只写 `effective_periods`。发现的 optional quarter 出现在 document_rows 但不在 effective forms 中。
- **反例/失败场景**: 用户执行 `dayu-cli download --ticker 0700`，CLI summary 显示 "forms: FY, H1"，但 document_rows 包含 Q2 result。用户可能困惑：为什么 forms 只有 FY/H1 却下载了 Q2？或者更糟：用户以为系统只下载了 FY/H1 而忽略了 Q2 行。
- **为什么有问题**: 这不是 bug，但 plan 没有明确 CLI 如何向用户解释"mandatory baseline"与"optional discovery"的区别。CLI output.py 的 `_print_download_summary` 在 summary line 中显示 `filters.forms`，而 document_rows 是独立逐行显示。用户需要理解这两个层次。
- **直接证据**:
  - `cli/output.py:409-445`: `_print_download_summary` 先打印 summary line（含 forms），再逐行打印 document_rows
  - plan §5.2: "HK bare optional quarter 被发现后可以出现在 document rows，但不会进入 missing baseline"
  - goal confirmation: "mandatory baseline 与实际可选材料 discovery 是两个独立判断"
- **影响**: 用户体验 confusion，可能导致 support 问题或用户误以为系统出错。
- **建议改法和验证点**:
  1. 在 plan 中明确 CLI summary 是否需要区分 "mandatory forms" 和 "discovered materials"，或在 document row 中标注 "optional"
  2. 验证点：evidence run 中 0700 的 CLI output 必须让用户能区分 mandatory baseline (FY/H1) 与 optional discovery (Q2/Q4)
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F06-未修复-中-ingestion_runtime.py 覆盖率要求可能过度膨胀测试范围

- **位置**: §7.2 单文件 coverage
- **问题类型**: 过度验收标准
- **当前写法**: "对 §6 所有实际修改的 production `.py` 文件用同一 focused union 采集 branch-aware coverage，输出 file-level 表；每个文件逐项 `>=80%`"
- **反例/失败场景**: `dayu/fins/ingestion_runtime.py` 是超大文件（agent 报告 5000+ 行）。本次修改可能只是在 `_execute_download_request` 中新增一行 `covered_fiscal_periods=document.covered_fiscal_periods`。但 80% 覆盖率要求是针对整个文件，而非增量行。为满足该要求，可能需要为 `ingestion_runtime.py` 的大量无关路径编写测试。
- **为什么有问题**: plan 的约束是"单文件测试覆盖率目标为 >= 80%"（来自 AGENTS.md），但 AGENTS.md 也说"`dayu/render/` 和 `utils/` 下的脚本默认无需测试、无覆盖率要求"。对 `ingestion_runtime.py` 这样的大文件，增量修改触发全文件 80% 覆盖是不合理的资源分配。
- **直接证据**:
  - AGENTS.md: "单文件测试覆盖率目标为 >= 80%"
  - plan §7.2: "若 `ingestion_runtime.py` 等大文件因本次 public projection 变更进入 diff，也必须达到同一门槛"
  - `ingestion_runtime.py` 实际行数超 5000 行
- **影响**: 实施 agent 可能花费大量时间在无关测试上，或被迫使用 omit/pragma 绕过（违反 plan 约束）。
- **建议改法和验证点**:
  1. 在 plan 中明确覆盖率要求适用于"本次修改的函数/方法"而非整个文件，或明确 `ingestion_runtime.py` 的覆盖率豁免条件
  2. 验证点：只检查 `_execute_download_request` 和 `_public_download_summary` 的覆盖率
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F07-未修复-低-plan §11 "为什么不是过度设计" 缺少与 goal confirmation 的直接映射

- **位置**: §11
- **问题类型**: 目标漂移

- **反例/失败场景**: `CnDownloadPeriodPolicy` 新增了 `notes: tuple[str, ...]` 字段，但 goal confirmation 没有要求 policy 携带 notes。plan 也没有说明 notes 的消费者是谁、什么内容会进入 notes。这可能是小的 scope creep。

  - plan §5.2: `CnDownloadPeriodPolicy` 包含 `notes: tuple[str, ...]`
  - goal confirmation: 没有提到 policy 需要携带 notes
- **影响**: 很小。notes 可能只是诊断用途，但如果消费者不明确，它可能是不必要的复杂度。
- **建议改法和验证点**:
  1. 在 plan 中说明 `notes` 的消费者和用途，或删除该字段
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Conclusion

**pass-with-risks**

1. **F01** (高): HKEX 全 results category code `t2code=-2` 缺少 API 文档验证。这是 DL-F13 修复的核心假设，若不成立则整个 F13 slice 无法工作。建议在 plan 中补充直接证据或改用已知具体子类 codes。

其余 findings 为中/低严重度，不阻塞 implementation 但应在 slice 实施中处理。
