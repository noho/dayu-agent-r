## Findings

### 001-未修复-严重-S2-async-sync-bridge-plan-does-not-resolve

- **位置**: Slice S2 "Wire Pipeline Progress into Fins Ingestion Runtime"，exact changes 与 state transitions
- **问题类型**: 不可直接实施
- **当前写法**: Plan 要求 "SecDownloadAdapter / CnDownloadAdapter 改为消费 download_stream(...)，每个 DownloadEvent 先 event_sink.emit_progress(...)，同时聚合最终 summary"。Plan 同时要求 `FinsSourceDownloadAdapter.download(...)` 增加必填 `event_sink` keyword 参数。
- **反例/失败场景**: 当前 `SecDownloadAdapter.download()` 是同步方法（`sec_pipeline.py:1720`），它内部调用 `self._pipeline.download()`（`sec_pipeline.py:1742`），而 `SecPipeline.download()` 已经是 `download_stream()` 的同步桥接包装（`sec_pipeline.py:487-500`，通过 `_run_async_download_sync`）。Plan 要求 adapter "消费 download_stream" 意味着 adapter 需要变成 async，但:
  - (a) 如果 adapter 变成 async，`_execute_download_request` 也需要变成 async，因为它是同步方法（`ingestion_runtime.py:1881`）且在 daemon thread 中运行（`ingestion_runtime.py:1464`）。
  - (b) 如果 `_execute_download_request` 变成 async，`FinsIngestionThreadExecutor` 需要支持 async job（当前只支持 `Callable[[], None]`）。
  - (c) 如果 thread executor 支持 async job，整个 Fins ingestion runtime 的线程模型需要重构。
  - (d) 备选：adapter 保持同步，内部使用已有的 `_run_async_download_sync` 桥接消费 stream 并 emit progress。但这要求 `event_sink.emit_progress()` 是同步方法（因为 adapter 是同步的），而 plan 的 `FinsIngestionEventSink.emit_progress` 签名未指定 sync/async。
- **为什么有问题**: Plan 没有裁决 async/sync 桥接方案，直接把实现决策推给 implementation agent。代码中已有的 `_run_async_download_sync` 桥接表明同步 adapter 内部消费 async stream 是可行的，但 plan 没有利用这个已有模式。Implementation agent 可能选错方案导致 `asyncio.Runner` 在已有 event loop 下崩溃，或引入隐蔽的 thread-safety bug。
- **直接证据**:
  - `ingestion_runtime.py:291`：`def download(self, request) -> FinsSourceDownloadAdapterResult:`（同步 Protocol）
  - `ingestion_runtime.py:1881`：`def _execute_download_request(self, record, normalized, request) -> FinsDownloadResultSummary:`（同步）
  - `ingestion_runtime.py:1464`：`self.executor.submit(start.job_id, lambda: self._run_download_job(...))`（daemon thread）
  - `sec_pipeline.py:487-500`：`SecPipeline.download()` 内部调用 `_run_async_download_sync(collect_download_result_from_events(self.download_stream(...)))`
  - `sec_pipeline.py:330-344`：`_run_async_download_sync` 检查 `asyncio.get_running_loop()` 并在有 loop 时抛 `RuntimeError`
  - `sec_pipeline.py:502`：`async def download_stream(...) -> AsyncIterator[DownloadEvent]:`
  - `dayu/fins/ingestion_runtime.py:107-125`：`FinsIngestionThreadExecutor` 使用 `Thread`，不是 async executor
- **影响**: Implementation agent 可能选错桥接方案导致生产崩溃。最可能的错误是尝试在 adapter 中 `asyncio.run(download_stream(...))`，但 daemon thread 中已有 `_run_async_download_sync` 创建的 loop，导致嵌套 loop 崩溃。
- **建议改法和验证点**:
  1. **推荐路径（最安全）**: 不修改 adapter protocol。在 `_execute_download_request` / `_run_upload_job` 的 runtime 层，在 adapter 调用前后和 per-document loop 内直接 emit coarse progress events。具体来说：
     - `_execute_download_request` 在调用 `adapter.download()` 前 emit `PROGRESS(message="开始下载", ...)`
     - `_execute_preprocess_request` 在每个文档处理循环内 emit `PROGRESS(message="处理文档 {n}/{total}", ...)`
     - `_run_upload_job` 在调用 `upload_runner.run_upload()` 前后 emit progress
  2. **备选路径**: 如果需要细粒度 progress（per-filing download progress），adapter 需要变成 async，同时 `_execute_download_request` 需要变成 async，`FinsIngestionThreadExecutor` 需要支持 async job。这需要更大的重构范围，应作为独立 work unit。
  3. 验证：无论选哪条路径，必须测试 daemon thread 中 emit progress 不会崩溃、不会丢失事件。
- **修复风险（低/中）**: 推荐路径风险低（零协议变更）；备选路径风险中高。
- **严重程度（严重）**: 阻塞 implementation——agent 无法从 plan 确定如何实现，且可能选错方案导致生产崩溃。

### 002-未修复-高-S2-protocol-breaking-change-blast-radius

- **反例/失败场景**: 完整的 adapter 实现者清单：
  - `SecDownloadAdapter`（`sec_pipeline.py:1698`）

- **为什么有问题**: Protocol 增加必填参数是对所有实现者的 breaking change。Plan 没有做完整的 adapter 实现者盘点。
- **直接证据**:
  - `ingestion_runtime.py:288`：`FinsSourceDownloadAdapter` Protocol 当前只有 `request` 参数

  - `tests/fins/test_fins_ingestion_runtime.py:236`：`_FakeUploadRunner(FinsUploadRunner)` 需要同步更新
- **影响**: 遗漏 adapter 更新 → 运行时 `TypeError` → job 失败；测试替身未更新 → 测试误报。
- **建议改法和验证点**:
  1. 如果采用 Finding 001 的推荐路径（不改 adapter protocol），此 finding 自动消除。
  2. 如果仍改 protocol，plan 应显式列出所有需要更新的 adapter 实现类完整路径。
  3. 在 S2 stop condition 中增加：如果发现未列出的 adapter 实现，必须先更新 allowed files 列表。
- **修复风险（低）**: 盘点+列表更新即可；或采用推荐路径消除 protocol 变更。
- **严重程度（高）**: 如果不处理会导致 implementation 遗漏 adapter 更新。

### 003-未修复-高-S2-progress-event-failure-kills-job

- **位置**: Slice S2 error handling，"单个 pipeline event 映射失败应使对应 job failed，而不是悄悄丢失业务进度"
- **问题类型**: 状态机漏洞 / 最佳实践偏离
- **当前写法**: Plan 要求单个 progress event 映射或写入失败时，整体 job 应 failed。
- **反例/失败场景**: 下载 500 个 filing 时，第 498 个 filing 的 progress event 写入因临时磁盘满失败。按当前设计，整个下载 job 会变成 FAILED，尽管 497 个文件已成功写入仓储。用户看到 job 失败，但实际数据已经部分到位——这是一个不一致状态：job record 说 failed，但仓储中有成功写入的文档。
- **为什么有问题**: Progress event 是观测信号，不是业务事实真源。让观测信号的写入失败反作用于业务结果违反了 plan 自身声明的原则（"event sequence 是 per-job 递增游标，不是业务事实，不替代 job record 状态真源"，plan line 178）。把观测失败等同于业务失败是不正确的故障传播。
- **直接证据**:
  - Plan line 178："Event sequence 是 per-job 递增游标，不是业务事实，不替代 job record 状态真源"
  - `ingestion_runtime.py:1728-1740`：当前下载逻辑根据 downloaded/failed/rejected 计数决定 succeeded/failed。这个业务判断不应该被 progress event IO 失败影响。
  - Plan S1 error handling 已正确裁决："terminal event append 失败不得回滚已经保存的 terminal job record"——但 S2 对 progress event 的裁决与此矛盾。
- **影响**: 磁盘满等运维问题导致 job 错误标记为 failed，而实际业务数据可能已经部分成功。用户无法区分"业务真的失败了"还是"只是进度报告写不进去"。
- **建议改法和验证点**:
  1. Progress event 写入失败应记录 WARN 日志并继续，不应导致 job failed。
  2. 只有 terminal event 写入失败时才需要考虑——plan 已经对此做了正确裁决。
  3. 在 job result summary 中可选增加 `events_emitted_count` / `events_failed_count` 字段。
  4. 验证：测试 progress event write failure 后 job 仍然 succeeded（如果业务成功）。
- **修复风险（低）**: 改变故障传播策略即可。
- **严重程度（高）**: 当前设计会在运维故障时产生虚假的业务失败。

### 004-未修复-中-S1-event-sidecar-file-locking-underspecified

- **位置**: Slice S1 "Fins Job Event Contract and Store"，exact changes 中 "FsFinsIngestionJobStore 使用 `<job_id>.events.jsonl` sidecar 追加事件；在 file lock 下读取最后 sequence 并写入下一条"
- **问题类型**: 契约缺失
- **当前写法**: Plan 说 "在 file lock 下读取最后 sequence 并写入下一条"，但没有明确 sidecar JSONL 是否共享 `FsFinsIngestionJobStore` 已有的 `RuntimeFileLock`，还是需要独立 lock。
- **反例/失败场景**: 如果 sidecar JSONL 使用独立 lock，可能出现：
  - (a) Job record 和 sidecar 的写入不在同一 lock 保护下，导致 job record 已 terminal 但 sidecar 还没有 terminal event（race window）。
  - (b) 如果使用独立 lock，需要额外的 lock 文件路径管理。
  如果共享已有 lock，需要确认已有 lock 的粒度——是 per-job 还是 per-store？当前 `FsFinsIngestionJobStore` 的 lock 是 per-store（整个 jobs 目录），这意味着 event append 会与 job record 读写竞争同一把锁。
- **为什么有问题**: Implementation agent 需要自行决定 locking 策略，可能选错导致 race condition 或性能问题。
- **直接证据**:
  - `ingestion_runtime.py` 中 `FsFinsIngestionJobStore` 使用 `RuntimeFileLock` 保护 job record
  - Plan S1 说 "在 file lock 下" 但未指定哪个 lock
- **影响**: Race condition 导致 event sequence 不连续或 terminal event 缺失（触发 S3 的 synthesized terminal fallback）。
- **建议改法和验证点**:
  1. Plan 应明确：sidecar JSONL append 与 job record 读写共享同一 `RuntimeFileLock`。这是因为 job record 和 sidecar 是同一 job 的两个持久化组件，原子性应由同一 lock 保证。
  2. 验证：测试并发 append 和 terminal save 不产生 race condition。
- **修复风险（低）**: 补充说明即可。
- **严重程度（中）**: Implementation agent 可能选错 locking 策略。

### 005-未修复-中-S3-poll-interval-unspecified

- **位置**: Slice S3 "Service Fins Direct Event Subscription"，`stream_job_events_until_terminal` 方法签名
- **问题类型**: 契约缺失
- **当前写法**: Plan 描述 `stream_job_events_until_terminal(handle, after_sequence=0)` 为 async generator，"轮询 runtime read_job_events(handle.job_id, after_sequence=cursor, limit=100)"。但没有指定轮询间隔。
- **反例/失败场景**: 如果没有显式 poll interval，implementation agent 可能：(a) 不做 sleep，导致 tight loop 吃满 CPU；(b) 使用默认 1s，但对快速完成的 job（<1s）可能漏掉中间 progress events；(c) 使用过长的 interval，导致 progress UI 更新迟钝。
- **为什么有问题**: Poll interval 直接影响用户可见的 progress 刷新率和系统资源消耗。现有 `wait_for_terminal` 使用 `DEFAULT_FINS_DIRECT_POLL_INTERVAL_SECONDS = 1.0`（`fins_direct.py:32`），但 event stream 的场景不同。
- **直接证据**:
  - `fins_direct.py:32`：`DEFAULT_FINS_DIRECT_POLL_INTERVAL_SECONDS = 1.0`
  - `fins_direct.py:448-460`：当前 `wait_for_terminal` 使用 `self.poll_interval_seconds`
  - Plan S3 未提及 poll interval 参数或默认值
- **影响**: Implementation agent 需要自行决定 poll interval，可能与预期行为偏差。
- **建议改法和验证点**:
  1. 在 S3 中显式声明 `stream_job_events_until_terminal` 的 poll interval，建议复用 `FinsDirectCommandService` 的 `poll_interval_seconds`（默认 1.0s）。
  2. 验证：测试确认 poll interval 生效，不会 tight loop。
- **修复风险（低）**: 补充参数即可。
- **严重程度（中）**: Implementation agent 可自行合理推断，但缺少显式契约可能导致行为偏差。

### 007-未修复-低-S3-synthesized-terminal-event-masks-bug

- **位置**: Slice S3 error handling，"若 read_job() 已 terminal 但尚未看到 terminal event，合成一条 terminal FinsDirectJobEvent 后停止"
- **问题类型**: 最佳实践偏离
- **当前写法**: Service 在 job record terminal 但无 terminal event 时合成 terminal event。
- **反例/失败场景**: 如果 terminal event 写入存在系统性 bug（例如 `_save_succeeded` 后忘记 append terminal event），Service 的合成逻辑会静默掩盖这个 bug。Operator 永远看不到 event gap，bug 永远不会被发现。
- **为什么有问题**: Fallback 合成是正确的防御性设计，但必须同时发出可观测信号（WARN 日志），否则会掩盖生产 bug。
- **直接证据**: Plan S3 error handling 没有提到合成时需要 WARN。
- **影响**: 系统性 event 写入 bug 被静默掩盖。
- **建议改法和验证点**:
  1. 在 S3 中增加：合成 terminal event 时必须发出 WARN 日志，说明 "job {job_id} reached terminal status {status} without terminal event, synthesized for consumer"。
  2. 验证：测试确认合成路径产生 WARN 日志。
- **修复风险（低）**: 加一行日志即可。
- **严重程度（低）**: 可观测性改进，不阻塞功能。

### 008-未修复-中-S1-FinsIngestionJobEventType-类型混合

- **位置**: Slice S1 "Contract / Schema / State-machine / Public-interface Changes"，Fins job event schema
- **问题类型**: 最佳实践偏离
- **当前写法**: Plan 定义 `FinsIngestionJobEventType` 包含 `JOB_QUEUED`、`JOB_RUNNING`、`PROGRESS`、`CANCEL_REQUESTED`、`JOB_SUCCEEDED`、`JOB_FAILED`、`JOB_CANCELLED`。
- **反例/失败场景**: 这个 enum 混合了两种不同性质的事件：
  - **状态机转换事件**: `JOB_QUEUED`、`JOB_RUNNING`、`JOB_SUCCEEDED`、`JOB_FAILED`、`JOB_CANCELLED` — 对应 job status 变化
  - **观测事件**: `PROGRESS`、`CANCEL_REQUESTED` — 不改变 job status
  Plan 自身在 line 178-179 已经区分了这两种性质："event append 不改变 job status" 和 "CANCEL_REQUESTED event 是观察信号"。但 enum 设计没有体现这个区分。
- **为什么有问题**: Implementation agent 可能混淆两种事件的语义，例如在 `PROGRESS` 事件中检查 job status，或在 `JOB_RUNNING` 事件中附加 progress payload。更清晰的设计是分为两个 enum，或至少用命名前缀区分（如 `STATUS_*` vs `OBSERVATION_*`）。
- **直接证据**:
  - Plan line 178："event append 不改变 job status"
  - Plan line 179："CANCEL_REQUESTED event 是观察信号；durable cancel truth 仍是 job record"
  - Plan S1 定义的 enum 混合了两种性质
- **影响**: 轻微——实现可能正确但代码可读性降低，未来维护者可能误解事件语义。
- **建议改法和验证点**:
  1. 考虑拆分为 `FinsIngestionJobStatusEventType`（状态机转换）和 `FinsIngestionJobObservationEventType`（观测），或至少在命名中体现区分。
  2. 验证：docstring 明确说明每种事件类型的性质。
- **修复风险（低）**: 重命名或拆分 enum 即可。
- **严重程度（低）**: 不阻塞功能，但影响代码可读性。

## Architecture Boundary Review

Plan 对分层边界的处理总体正确：

- **✅ UI → Service → Fins 边界清晰**: CLI 只通过 Service `stream_job_events_until_terminal` 消费事件，不直接 import Fins storage 或 pipeline。Plan S4 明确 "CLI 不直接调用 read_job_events，只调用 Service stream"。
- **✅ Fins job event 不是 Host EventLog**: Plan 多次声明 Fins job event sidecar 是 Fins 自有 schema，不属于 Host durable schema、Engine contract 或 Host EventLog。这与 `docs/engine/design.md` 的 stream 术语边界一致。
- **✅ 不创建 Host Run**: Plan 明确 "不把 Fins direct commands 改造成 Host run"。Fins direct 保持为 Service/Fins boundary 内的独立路径。
- **✅ Fins runtime 是事件产生和持久化 owner**: Plan 正确划分了 ownership——Fins runtime 产生事件，Service 消费和投影，CLI 只是 UI renderer。
- **⚠️ 见 Finding 001**: Adapter protocol 变更涉及 async/sync 边界，如果处理不当可能破坏 Fins runtime 的线程模型。
- **⚠️ 见 Finding 002**: Adapter protocol breaking change blast radius 需要完整盘点。

## Best-practice Review

- **✅ Bounded payload**: Plan 在 S1/S2 中要求 progress event payload bounded，不含绝对路径、财报原文、raw provider payload。有测试覆盖。
- **✅ Terminal event 不回溯 job record**: Plan 正确裁决 terminal event append 失败不回滚已保存的 terminal job record。
- **⚠️ 见 Finding 003**: Progress event 写入失败导致 job failed 不是最佳实践——观测信号失败不应反作用于业务结果。
- **⚠️ 见 Finding 007**: Fallback 合成 terminal event 不记录 WARN，静默掩盖 bug。
- **✅ Cancel 语义完整**: Plan S4 正确处理了 SIGINT → durable request_cancel → 继续等待 terminal → 二次 SIGINT → 本地退出的完整 cancel 语义。

## Optimal-solution Review

- **✅ Event sidecar + polling 方案合理**: 匹配现有 filesystem job store 模型，不需要跨进程 event bus、WebSocket 或平台化 observer。比引入通用 event bus 更简单、更可维护。
- **⚠️ 见 Finding 001**: Adapter protocol 变更路径可能不是最优方案。已有的 `_run_async_download_sync` 桥接模式表明，可以在 runtime 层 emit coarse progress 而不改 adapter protocol。这更简单、风险更低。
- **✅ Service event stream 复用性**: `stream_job_events_until_terminal` 作为 async generator，未来 GUI/WeChat 可复用，设计合理。
- **✅ CLI 日志装配复用已有 helper**: Plan S5 正确识别了 `dayu/runtime/log.py` 的已有装配能力，虽然描述方式暗示手动映射（见 Finding 006），但方向正确。

## Overengineering Review

- **✅ 无过度设计**: Plan 只新增 workspace-scoped JSONL sidecar + runtime event sink + Service async iterator + CLI renderer。不引入通用 bus、WebSocket、平台化 observer registry、Host/Engine schema 变更。
- **✅ 不过度抽象**: `FinsIngestionEventSink` 只暴露一个 `emit_progress` 方法，不是通用 event bus interface。
- **✅ Slice 粒度合理**: 6 个 slice 各自形成可验证闭环，依赖关系清晰（S1 契约 → S2 生产 → S3 消费 → S4 UI → S5 日志 → S6 文档）。
- **✅ Non-goals 裁决合理**: prompt/interactive streaming 被正确排除，`upload_filings_from` 被正确排除。

## Overcoupling Review

- **✅ Fins job event schema 独立**: 不耦合到 Host durable schema、Engine contract 或 Host EventLog。
- **✅ CLI 不耦合 Fins storage**: CLI 通过 Service 消费，不直接 import `dayu.fins.storage`。
- **⚠️ 见 Finding 002**: Adapter protocol 增加必填 `event_sink` 参数会将 progress 关注点耦合到所有 adapter 实现者。备选方案（runtime 层 emit）可减少耦合面。
- **✅ Service event stream 不耦合 CLI**: Service 提供 async generator，CLI 只是 consumer，未来 WeChat/GUI 可复用。

## Open Questions

1. **OQ1（Blocking）**: `FinsSourceDownloadAdapter.download()` 是否需要变成 async？如果采用 Finding 001 的推荐路径（runtime 层 emit coarse progress），则不需要。如果需要细粒度 per-filing progress，则需要更大的重构。Plan 当前未裁决。**建议**: 采用推荐路径，细粒度 progress 作为后续 work unit。

2. **OQ2（Clarification）**: S2 中 `_execute_preprocess_request` 的 progress emit 粒度是否足够？Plan 说 "在选中文档、单文档开始、processed/skipped/failed/not_supported、完成时发出 bounded progress"。当前 preprocess 没有独立 pipeline stream model，这个粒度是否足够让用户感知进度？**建议**: 对 preprocess 来说这个粒度足够，因为每个文档处理通常需要数秒。

3. **OQ3（Verification）**: Plan 要求 `upload_filings_from` 不调用 event stream。当前 `_run_upload_filings_from`（`fins.py:232`）是同步函数，不经过 `_run_fins_direct_command_async`。**建议**: 在 S4 测试中增加显式断言：`upload_filings_from` 路径不调用 `stream_job_events_until_terminal`。

4. **OQ4（Clarification）**: `FinsDirectJobEvent` 的 `terminal_result` 字段引用已有的 `FinsDirectTerminalResult`。但 plan 的 event schema 中 `status: FinsIngestionJobStatus | None` 与 `terminal_result.status` 存在冗余。**建议**: terminal event 只通过 `terminal_result` 携带 status，非 terminal event 的 `status` 字段为 `None`。
