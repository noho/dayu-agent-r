### 2. tier 1/2/3 顺序执行

**结论: PASS。** 完整 trace 从 `_execute_proactive_compaction_async`（`dispatch.py:1315-1477`）：

**正常 compact（tier 0）**（line 1328-1335）：
```

```

**Conditional recovery entry**（line 1338）：
```

```
仅当 normal compact 未产生 accepted candidate / quality result 或有 failure reason 时进入。

**Tier 1 — fallback caps**（lines 1508-1517）：
- 使用 `select_compact_segment` + `max_selected_item_count`/`max_selected_size_units` 从 `memory_policy` 的 fallback caps 参数产生 bounded selection
- `previous_compacted_view = pending.material_view.previous_compacted_view`（完整 previous view）

**Tier 2 — section degrade**（lines 1518-1534，条件追加）：

- 使用 `pending.request.segment_selection`（原始 normal compact selection）而非 bounded selection
- `previous_compacted_view = degraded_previous_view`

**Tier 3 — delta only**（lines 1535-1544，始终追加）：
- `selected_segment = bounded_selection`（同 tier 1 的 bounded selection）
- `previous_compacted_view = ()`（清空 previous view）

**Recovery loop 执行**（lines 1339-1364）：
```
for recovery in attempts:
    if cancellation_token.is_cancelled(): break     # stale guard (before tier)
    tier_result = await run_compaction_operation(...)  # max_attempts=1
    if cancellation_token.is_cancelled(): break     # stale guard (after proposal)
    if _compaction_result_accepted(tier_result):
        accepted_request = recovery.request
        accepted_result = tier_result
        break                                      # first accepted tier wins
```

**All tiers fail**（line 1412）：
```
if not _compaction_result_accepted(accepted_result):
    fallback_dispatch = self._append_compaction_failed_with_proactive_fallback(...)
    → one CONTEXT_COMPACTION_FAILED event → tier 4/5 dispatch fallback
```

**Accepted recovery**（lines 1445-1472）：
```
self._append_compacted_event(transaction, ..., request=accepted_request, ...)
→ one CONTEXT_COMPACTED event（走既有 _append_compacted_event 路径）
```

**结论**：tier 严格按 1 → 2（条件）→ 3 顺序执行；每 tier `max_attempts=1`；accepted 走既有 `_append_compacted_event`；全部失败只写一次 `CONTEXT_COMPACTION_FAILED` 并进入 tier 4/5。✓

### 4. select_compact_segment 新参数语义隔离

**结论: PASS。** 新增 `max_selected_item_count`（`compact_material.py:892`）与 `budget_blocked` flag 的行为分析：

**对 reactive selection 的影响**：reactive 调用 `select_compact_segment` 不传 `max_selected_item_count`（默认 `None`），行为不变 ✓

- Tier 1/3 使用 strict item cap + strict char cap（`budget_blocked` 激活），防止更晚小 block 绕过 caps ✓

**结论**：新参数仅影响 S4 recovery 路径的 fallback caps 语义，不破坏 normal compact / reactive selection。✓

### 5. section-aware degrade 语义

**结论: PASS。** `degrade_previous_compacted_view_for_recovery`（`compact_material.py:987-1016`）：

**优先级**（`_RECOVERY_PREVIOUS_VIEW_KIND_PRIORITY`，line 169-174）：
```
EVIDENCE_BACKED_FACT > REFERENCE_CONTINUITY > ANSWER_ANCHOR > FORWARD_INTENT > SESSION_SUMMARY
```

**算法**：
1. 按优先级顺序遍历 kind
2. 收集所有匹配 `block.kind is kind` 的 blocks（保留原始 material index）
3. 第一个非空 kind 的所有 blocks 即为保留集；`_sort_recovery_previous_blocks` 排序后返回
4. 无任何 block 时返回空 tuple `()`

**排序**（`_sort_recovery_previous_blocks`，lines 1532-1559）：
- 若所有候选 block 的 source refs 均可解析为 `eventlog-seq:<N>` → 按最大 sequence 降序、material order 升序、block_label 升序
- 否则 → 按 material order 升序、block_label 升序（fallback stable sort）

**whole-drop 特性**：
- 只 whole-drop 整个 kind section，不截断、不改写文本、不合成新 summary
- 返回原始 `CompactMaterialBlock` 对象，文本 byte-exact
- 测试 `test_degrade_previous_compacted_view_keeps_highest_priority_section_exact` 验证：SESSION_SUMMARY/ANSWER_ANCHOR/REFERENCE_CONTINUITY 被 whole-drop，EVIDENCE_BACKED_FACT 保留且文本 `"fact must stay byte exact"` / `"second fact must stay byte exact"` 逐字不变
- 测试 `test_degrade_previous_compacted_view_sorts_source_sequences_descending` 验证：同 section 内按 `eventlog-seq:30 > 20 > 10` 降序排列，低优先级 section（`eventlog-seq:40`）被 whole-drop

**Source sequence 解析**（`_recovery_source_event_sequence`，lines 1579-1591）：
- 仅识别 `eventlog-seq:<N>` 格式的 ref，不匹配则返回 `None`
- 单个 ref 无法解析 → 该 block 的全部 source sequence 标记为不可解析 → 排序回退到 material order
- 负数 `eventlog-seq:<N>` → `ValueError`

**结论**：section-aware degrade 正确执行 whole-drop item/section；优先级顺序正确；source sequence/order 规则正确；无截断/重写/新 summary。✓

**结论: PASS。** artifact 记录的 residual risk 准确且充分：

## Residual Risk

- **Reactive recovery 缺失**：proactive-only 是 deliberate scope decision，但意味着 reactive compaction failure 仍直接进入 tier 4/5 fallback，无 tier 1-3 recovery 尝试。已在 implementation artifact 中记录。

- **`_ReadCompactionCancelReasonOperation` 的 Session 检查无法用于 reactive**：reactive 路径不使用 `_DurableRunCancellationToken`，因此新增的 Session 检查仅对 proactive 生效。reactive 路径的 Session 状态保障依赖其自身的 `engine_ingest` 逻辑。
- **无 tier 专属 durable metadata**：若 recovery 成功，无法从 `CONTEXT_COMPACTED` event 中区分是 normal compact 还是 tier N recovery。artifact 已记录此局限性。
