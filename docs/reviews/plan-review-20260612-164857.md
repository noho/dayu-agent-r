## 1. Motivation Assessment

### 1.1 Is the motivation valid?

**Yes.** The motivation is valid for three independently sufficient reasons:

1. **Issue #95 is OPEN and properly unblocked.** Issue #81 (parent) is closed, and WU-CM-05/WU-CM-06 (sibling work units) are completed. The preflight conclusion in the plan is correct: the motivation is valid, but the scope must stay narrow.

2. **Test maintainability is a real, observable concern.** The current `test_compact_material.py` is 2173 lines and `test_public_compact_smoke.py` is 1207 lines, both with significant inline assertion logic. The plan correctly diagnoses that inline assertions make boundary failures harder to classify. This is not speculative—it's a direct observation from the code.

3. **Stale naming risk is real.** Issue #95 body still references `stable_input` / `history_input` / `evidence_input`, which are legacy names. The plan correctly calls out that the current design truth uses `previous_compacted_view` / `trace_material` / `evidence_material` / `answer_material` / `current_input_anchor`. Preventing regression to stale names has direct evidence: the forbidden terms list in `test_public_compact_smoke.py` (lines 111-113) already includes `stable_input`, `history_input`, `evidence_input` — so the plan's concern about stale names is grounded in existing defense.

### 1.2 Is the severity correctly assessed?

**Yes.** The plan correctly rates this as a maintainability/readability cleanup, not a semantic change. It explicitly declines to:
- Change memory snapshot schema
- Introduce new compact material sections or compactor JSON fields
- Redesign Conversation Memory categories
- Change public Host API or compactor baseline contracts

These non-goals are the correct bounding box for a test-maintenance WU that follows two completed sibling WUs (WU-CM-05, WU-CM-06).

## 3. Slice-by-Slice Review

### 3.1 Slice 1: Focused Compact Material Test Readability

#### Finding 1 (Slice 1) — Stale name exclusion test is partially pre-existing; plan should acknowledge and justify strengthening

**Evidence:** `tests/host/test_compact_material.py` lines 379-382 already assert:
```python
assert "stable_input" not in vnext_json
assert "history_input" not in vnext_json
assert "evidence_input" not in vnext_json
```
This is inside `test_conversation_compact_input_vnext_maps_material_without_citable_current_anchor`, which already partially covers the stale legacy name exclusion that the plan proposes as new work.

**Risk:** Without acknowledging the existing coverage, the implementation agent may either:
- Duplicate the existing assertion verbatim (wasted effort).
- Not realize the existing test only checks for *absence* of stale names but doesn't positively assert *presence* of all current section names in the JSON top-level keys.

**Recommendation:** Amend Slice 1 to:
1. Acknowledge the existing stale-name exclusion assertion at line 379-382.
2. Clarify that the "strengthened" test should additionally **positively assert** that all six current top-level JSON keys are present: `previous_compacted_view`, `trace_material`, `evidence_material`, `answer_material`, `current_input_anchor`, `instruction`.
3. The existing test checks one pack shape (initial material); the new/strengthened test should also cover the post-compaction pack shape (via `build_compact_material_pack` → `conversation_compact_input_vnext_from_material_pack`).

#### Finding 2 (Slice 1) — "Summarize material pack / vNext input shape" is too vague for code-generation-ready

**Evidence:** The plan says: "Add small test-only assertion helpers that summarize material pack / vNext input shape by section labels and section counts."

**Risk:** "Summarize" and "shape" are underspecified. The implementation agent could interpret this as:
- A generic `assert_material_shape(pack)` that checks arbitrary properties (too broad).
- A simple label-count helper that doesn't add value beyond existing assertions (too narrow).
- A full material JSON snapshot helper (violates the non-goal of "Do not add broad golden snapshots").

**Recommendation:** Specify the helper contract concretely. For example:
- A helper that takes a `CompactMaterialPack` and returns a typed `MaterialPackShape` (e.g., `NamedTuple` with `previous_count: int`, `trace_count: int`, `evidence_count: int`, `answer_count: int`, `evidence_labels: tuple[str, ...]`, `trace_labels: tuple[str, ...]`, `answer_labels: tuple[str, ...]`).
- A helper that takes a `ConversationCompactInputVNext` and returns a typed `VNextInputShape` with the six top-level key names and item counts per section.
- Assertion helpers that use these shapes to produce boundary-specific failure messages like `"evidence_material: expected 3 items, got 2; labels: E1, E2"`.

#### Finding 3 (Slice 1) — Allowed files list is incomplete for conditional production fix path

**Evidence:** The plan says "Do not modify `dayu/host/compact_material.py` unless the new tests expose a real production defect." But `dayu/host/compact_material.py` is not listed in allowed files.

**Risk:** If the new tests DO expose a production defect (e.g., a section name mismatch between `CompactMaterialSection` enum and actual JSON output), the implementation agent won't know whether fixing it is in-scope. Additionally, if the fix requires changing `dayu/host/compaction.py` (where `CompactMaterialSection`, `CompactMaterialBlockKind`, and `ConversationCompactInputVNext` are defined), neither file is in the allowed list.

**Recommendation:** Either:
- Add `dayu/host/compact_material.py` and `dayu/host/compaction.py` to Slice 1 allowed files as **conditional** (only if tests expose a real production defect, and only for narrow fixes), OR
- Explicitly state that if a production defect is found, it must be reported as a finding and NOT fixed in this WU (deferred to a new issue), keeping Slice 1 strictly test-only.

### 3.2 Slice 2: Public Compact Smoke Failure Localization

#### Finding 4 (Slice 2) — `tests/host/public_smoke_support.py` is a significant dependency not in allowed files

**Evidence:** `test_public_compact_smoke.py` imports heavily from `tests/host/public_smoke_support.py` (1534 lines). The extracted assertion helpers in Slice 2 may need to import from or refactor code in this support module. For example:
- `assert_at_most_one_system_message` is imported from `public_smoke_support` and used throughout the smoke tests.
- `PROVIDER_CASES`, `FinalAnswerWorkerFactory`, `ToolCallingWorkerFactory`, `api_key_or_skip`, etc. are all in this module.

**Risk:** If Slice 2 extracts helpers that depend on `public_smoke_support` utilities, and `public_smoke_support.py` is not in allowed files, the implementation agent has an ambiguous boundary. The agent might:
- Duplicate helper logic from `public_smoke_support` into `test_public_compact_smoke.py` (code duplication).
- Avoid refactoring helpers that should move to `public_smoke_support` (missed cleanup opportunity).
- Unnecessarily broaden the scope by editing `public_smoke_support.py` without clear authorization.

**Recommendation:** Add `tests/host/public_smoke_support.py` to Slice 2 allowed files, with the constraint: "Only extract or relocate compact-smoke-specific assertion helpers; do not change the signature or behavior of general-purpose smoke support functions."

#### Finding 5 (Slice 2) — Extracted assertion helpers lack correctness validation

**Evidence:** Slice 2 proposes extracting focused assertion helpers for five specific boundaries, but the validation section only lists `pytest` and `pyright`. There is no mention of tests that verify the helpers themselves produce correct signals.

**Risk:** Extracted helpers can develop two failure modes over time:
1. **False negative**: Helper accepts invalid material silently (assertion too weak).
2. **False positive**: Helper rejects valid material (assertion too strict), causing test maintenance burden.

Without explicit counterexamples or edge-case tests for the helpers, these failure modes are undetectable until a real production change trips them.

**Recommendation:** Add a validation item: "Each extracted assertion helper must have at least one positive (valid input passes) and one negative (invalid input fails with correct boundary message) test case, either inline in the smoke test or as dedicated parametrized tests." This does not require a separate test file — inline parametrized tests within `test_public_compact_smoke.py` are sufficient.

## 4. Cross-Cutting Findings

### Finding 6 (Cross-cutting) — Residual risk tracking and control doc update are not addressed

**Evidence:** The plan defines acceptance signals and validation commands, but does not mention:
- How residual risks from this WU will be tracked in `docs/host/issues-implementation-control.md`.
- What control doc state transitions are expected after Slice 1 and Slice 2 completion.
- What artifacts (implementation reports, review artifacts) should be produced and where.

The control doc (line 146) currently shows `gate: review` and `active work unit: WU-CM-08`. After plan review passes, the gate should advance to `implementation` or a slice-specific state. The plan should explicitly state this.

**Risk:** Without explicit control doc update instructions, the implementation agent may complete the work without updating the control doc, leaving stale state that confuses the next work unit.

**Recommendation:** Add an "Artifacts and State Transitions" section to the plan:
- After plan acceptance: update control doc gate to `implementation`.
- After Slice 1: write implementation report to `docs/reviews/wu-cm-08-s1-implementation-report.md` (already listed in allowed files).
- After Slice 2: write implementation report to `docs/reviews/wu-cm-08-s2-implementation-report.md` (already listed in allowed files).
- After both slices and aggregate review: update control doc with accepted commits, residual risks, and next entry point (WU-CM-09 or WU-OBS-00).

## 7. Slicing Quality and Missing Risks

### 7.1 Is the two-slice split optimal?

**Yes.** The split by test file ownership is clean and respects the control doc's slice principles:

- **Context and review capacity:** Each slice modifies one test file plus one review artifact. This is well within one agent context.
- **Code dependency boundary:** `test_compact_material.py` tests unit-level material construction; `test_public_compact_smoke.py` tests end-to-end public paths. They have different fixture requirements and different failure modes.
- **Independent verification:** Each slice has its own pytest command and can be verified independently. Slice 1 does not depend on Slice 2, and vice versa.

### 7.2 Are there missing blocking risks?

**One medium-severity risk not addressed:** The `tests/host/fake_compaction.py` module (used by Slice 2's fake compactor proposal path) contains a `cast(...)` call (line 12: `from typing import cast`) that was noted as a residual risk in WU-CM-05 closeout. The plan says "Keep fake compactor behavior deterministic and label-only." If the assertion helpers in Slice 2 need to inspect fake compactor behavior more precisely, the existing `cast(...)` usage could mask type errors that the new helpers would expose.

**Recommendation:** Add a note to Slice 2: "If new assertion helpers interact with `fake_compaction.py`'s `cast(...)` path, document but do not fix the cast — it is a pre-existing residual risk from WU-CM-05. If the cast causes a pyright error in the new helpers, report as a finding rather than silently working around it."

### 7.3 Are there better slicing alternatives?

**No.** The current two-slice split is the natural decomposition. A single combined slice would mix unit-level and end-to-end concerns, making review harder. Further splitting (e.g., one slice per helper) would produce slices too small to form an independently verifiable behavior closure.

Slice 1's "current section names" check should include `instruction` as the sixth top-level key, not just the five material sections.

Slice 2's "forbidden internal terms in LLM-facing material" helper can verify that the forbidden terms list itself is complete and does not contain false positives (terms that are actually LLM-appropriate).

3. **The 1 skipped test:** Baseline shows 41 passed, 1 skipped. The skipped test is almost certainly `test_real_compactor_public_opener_compacts_and_preserves_continuity` (requires `DAYU_RUN_REAL_COMPACTOR_SMOKE=1`). This is expected and should remain skipped by default.

4. **No dependency on WU-CM-05/WU-CM-06 completion artifacts:** The plan's baseline validation (41 passed) was run on the current HEAD which includes WU-CM-05 and WU-CM-06 accepted commits. This is the correct baseline.
