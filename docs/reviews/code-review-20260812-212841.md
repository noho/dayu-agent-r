## Findings

### 001-未修复-中-durable save 后 progress/event 投影异常时 `_save_failed_from_exception` 安全网依赖读盘终态检查

- **入口/函数**: `FinsIngestionRuntime._run_upload_job` (line 3827) → `save_accepted_upload_terminal_if_active` (line 3892) → `_upload_terminal_disposition_from_job_record` (line 3899) → `_emit_progress_event` (line 3902)
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:3892-3913`，异常处理入口 `dayu/fins/ingestion_runtime.py:3914-3915`
- **输入场景**: `save_accepted_upload_terminal_if_active` 成功保存 SUCCEEDED/FAILED 后，`_upload_terminal_disposition_from_job_record`、`_emit_progress_event`、`_upload_context_persisted_summary_progress_payload` 或 `_append_terminal_job_event_warn` 中任一抛出异常。
- **实际分支**: 异常被 `except Exception as exc: self._save_failed_from_exception(job_id, exc)` 捕获（line 3914-3915）。`_save_failed_from_exception` 读取当前 job record（line 4864），检查 `record.status in _TERMINAL_STATUSES`（line 4865），因刚保存的 SUCCEEDED/FAILED 是终态，安全返回不覆盖。
- **预期行为**: 不产生第二终态、不把已保存的 SUCCEEDED/FAILED 改写为 FAILED。
- **实际行为**: 当前实现正确——`_save_failed_from_exception` 的终态检查提供了安全网。但如果未来 `_save_failed_from_exception` 中的 `read_job` 返回陈旧数据（如另一个并发写入者还没刷盘），或者终态检查被移除/弱化，就会产生双终态。
- **直接证据**: `dayu/fins/ingestion_runtime.py:4863-4867`（`_save_failed_from_exception` 中 `read_job` → `status in _TERMINAL_STATUSES` → return）；`tests/fins/test_fins_ingestion_runtime.py:1430-1538`（`test_durable_upload_cancel_after_atomic_save_keeps_single_terminal` 覆盖了 save 完成后 progress/event 投影前取消的终态唯一性，但未直接覆盖投影代码自身抛异常的场景）。
- **影响**: 静默冗余——当前实现下该安全网可靠，但缺少针对投影异常路径的直接测试；若未来误删终态检查，可能制造双终态。
- **建议改法和验证点**: 增加一个测试用例：在 `_emit_progress_event` 或 `_upload_terminal_disposition_from_job_record` 抛出模拟异常后，断言 record 保持原终态且无第二 terminal event。该测试可防御未来重构。
- **修复风险（低）**: 仅加测试，不改生产代码。
- **严重程度（中）**: 安全网生效但缺少直接覆盖；现有 barrier tests 间接证明了终态唯一性（`test_durable_upload_cancel_after_atomic_save_keeps_single_terminal` 断言 `len(terminal_events) == 1`），但未显式覆盖"投影代码自身异常"路径。

### 002-未修复-低-`_run_upload_job` 中 CANCELLED disposition 走 `save_cancelled_if_active`，若已有 completed terminal 则投影 winner 终态，与 runner 的 cancelled 决策不一致

- **入口/函数**: `FinsIngestionRuntime._run_upload_job` (line 3827)
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:3877-3881, 3899-3913`
- **输入场景**: Runner 返回 CANCELLED summary（`disposition is FinsUploadTerminalDisposition.CANCELLED`），但并发写入者已通过 `save_accepted_upload_terminal_if_active` 保存了 SUCCEEDED。`save_cancelled_if_active` 的 file lock 内看到 `record.status in _TERMINAL_STATUSES`，返回已有 SUCCEEDED 记录。
- **实际分支**: `saved` = 已有 SUCCEEDED 记录；`saved_disposition = _upload_terminal_disposition_from_job_record(saved)` → COMPLETED；progress 按 COMPLETED 投影（`upload.completed`），terminal event 为 JOB_SUCCEEDED。
- **预期行为**: 第一终态获胜。Runner 的 cancelled 决策因到达过晚被忽略。progress/event 从 winner 终态投影。
- **实际行为**: 行为正确——第一终态不被覆盖，投影同源。但代码读者可能误以为 `disposition is CANCELLED` 分支中的 `saved` 必然是 CANCELLED record，而实际上可能不是。
- **直接证据**: `dayu/fins/ingestion_runtime.py:1956`（`save_cancelled_if_active` 中 `record.status in _TERMINAL_STATUSES: return record`）；`dayu/fins/ingestion_runtime.py:3899`（`saved_disposition = _upload_terminal_disposition_from_job_record(saved)` 从 winner record 读取 disposition）。
- **影响**: 仅代码可读性——行为正确，第一终态获胜语义已由既有 record-level atomic save 保证。两个并发 runner 对同一 job 不会在正常生产中出现。
- **建议改法和验证点**: 可选在 `saved = self.job_store.save_cancelled_if_active(...)` 后添加注释说明 `saved` 可能是已有非-cancelled 终态，progress 从 winner 投影。不需要修改行为。
- **修复风险（低）**: 仅注释。
- **严重程度（低）**: 行为正确，仅可读性。
