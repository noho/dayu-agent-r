## Assumptions tested

1. Lock ordering：proposed `writer → recovery → identity → publication` 不会形成死锁环路。
2. Swap-before-COMMITTED crash 窗口：identity guard 在 recovery guard 之后取得，确保 crash orphan 被先恢复再做 alias validation。
3. 并发 exactly-one：identity guard 是全局单一锁，serialize 所有 meta commit 和 read。
4. 冲突在 published mutation 前：identity validation 在 target publication guard 之前执行。
5. Rollback/release error：identity guard release failure 遵循现有 post-commit 语义。
6. Read route 与 commit interleaving：identity guard serialize 读写，不会死锁。
7. S1 可独立验证：S1 不破坏现有 storage 行为。
8. S2 failure transport：`CompanyTickerAliasConflictError` 能被现有 terminal chain 原样携带。

## Findings

### 01-未修复-中-recovery sweep 持有 identity guard 期间阻塞全部读写

- **位置**: §7.4 step 4–5、§7.5
- **问题类型**: 并发恢复风险
- **当前写法**: `commit_batch` 在 `company_meta_staged=True` 时，先取得 recovery guard，执行 orphan batch + backup sweep，然后才取得 identity guard。recovery sweep 内部对每个 orphan batch 执行 `_recover_single_batch_dir`，该函数取得 ticker writer（non-blocking）和 publication guard 后做文件恢复。identity guard 在 recovery sweep **之后**取得。
- **反例/失败场景**: 若 recovery sweep 本身需要取得 identity guard（§7.5 提到"在 recovery guard 与 nonblocking ticker writer之后、publication guard前统一取得 identity guard"），则 recovery sweep 持有 identity guard 期间，所有 alias read 和 concurrent meta commit 都被阻塞。若 workspace 中有多个 orphan batch（例如进程 crash 后重启），recovery sweep 耗时可能较长，导致用户可见的读写延迟。
- **为什么有问题**: §7.3 锁序表中 `recovery` 路径为 `recovery guard → ticker writer → identity guard → publication guard`。这意味着每次 recovery 都会取得 identity guard，即使 recovered batch 不涉及 CompanyMeta。这比 §7.5 声称的"recovery 不依赖未持久化的 `company_meta_staged`，因此对所有 recovered ticker tree 使用 guard"更宽泛。
- **直接证据**: §7.3 锁序表明确列出 `recovery: recovery guard → ticker writer → workspace company identity guard → ticker publication guard`；§7.5 声称"对所有 recovered ticker tree 使用guard"。
- **影响**: 启动时 recovery 若有多个 orphan batch，identity guard 持有时间较长，阻塞所有 alias read。不导致正确性问题，但可能导致用户可见延迟。
- **建议改法和验证点**: 在 implementation 中确认 identity guard 只在 recovered batch 涉及 CompanyMeta 时取得（通过检查 staging 目录中是否存在 `meta.json`），而非所有 recovered batch 都取得。若无法安全判断，则在 recovery sweep 开始前记录当前 published alias index snapshot，recovery 完成后再做 identity validation。验证点：recovery 测试中注入多个 non-meta orphan batch，断言 identity guard 未被取得。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 02-未修复-中-S2 新增 read path lock 改变并发语义

- **位置**: §5.4、§7.3、§10 S2 step 4
- **问题类型**: 并发恢复风险 / 架构边界
- **当前写法**: 当前 `resolve_existing_ticker` 在 read path 只取得 per-ticker publication guard。S2 切换为 `resolve_company_ticker` 后，read path 增加了 workspace identity guard，lock order 为 `identity → publication`。这是新增的全局锁获取点。
- **反例/失败场景**: 若 identity guard 文件锁因 NFS/网络文件系统/权限问题无法获取，所有 alias read 都会失败。当前 read path 没有这个全局锁，一个 ticker 的 read 不会影响另一个 ticker 的 read。S2 后所有 alias read 都需要这个全局锁。
- **为什么有问题**: §5.4 声称 `resolve_company_ticker` 是"canonical/alias 到 canonical corpus 的唯一 route"。如果 identity guard 获取失败，整个 alias read 路径不可用。当前代码中 `resolve_existing_ticker` 没有这个单点故障。
- **直接证据**: §7.3 锁序表 `alias read route: workspace company identity guard → ticker publication guards`；§5.4 声称"storage 用 `try_normalize_ticker` 对单个查询 token 应用唯一 grammar；无法接受时返回 `None`"，但未讨论 identity guard 获取失败的行为。
- **影响**: identity guard 文件锁成为 alias read 的单点故障。若锁文件损坏或文件系统异常，所有 alias read 失败，而非仅受影响 ticker 的 read 失败。
- **建议改法和验证点**: 在 `resolve_company_ticker` 实现中，identity guard 获取失败应 fail-closed（抛 typed exception），不让错误静默传播。同时在测试中注入 identity guard 获取失败场景，断言 read 返回明确错误而非 hang 或 silent fallback。验证点：`test_fins_read_runtime.py` 增加 identity guard 获取失败的 parametrized case。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 03-未修复-低-S1 可独立部署但不关闭冲突窗口

- **位置**: §10 S1 Non-goals、§16.2
- **问题类型**: 切片过粗 / 目标漂移
- **当前写法**: S1 声称是"可独立验证的 identity 语义增量"。S1 Non-goals 明确"不在本 slice 修改 `commit_batch` lock/validation，不新增 conflict failure code"。
- **反例/失败场景**: S1 部署后、S2 未完成前，系统具有统一的 identity contract 但没有 workspace uniqueness enforcement。两个不同 ticker 可以提交相同 alias，published state 进入歧义状态。这与当前行为相同，但 S1 改变了 CompanyMeta 内部结构（`ticker_identity` 替代 `ticker`/`ticker_aliases`），如果 S2 延迟，旧的 `resolve_existing_ticker` 仍能工作（因为它消费 `lookup_tickers()`），但语义漂移风险增加。
- **为什么有问题**: S1 声称"可独立验证"，但 goal confirmation success signal 4 要求"同一 alias 指向多个 canonical corpora 的顺序和并发场景都在发布前原子失败"。S1 不满足这个 success signal。S1 是必要的准备步骤，但不是可独立验收的增量。
- **直接证据**: S1 Non-goals（line 439）"不在本 slice 修改 `commit_batch` lock/validation，不新增 conflict failure code"；goal confirmation success signal 4（line 110）"冲突必须在 canonical corpus 发布前原子失败"。
- **影响**: 若 S2 延迟或取消，系统处于中间状态：identity contract 统一但 uniqueness 未 enforcement。不比当前状态更差，但也不满足 goal confirmation。
- **建议改法和验证点**: 在 S1 completion signal 中明确声明"S1 不满足 success signal 4；S2 是完成本 WU 的必要后续"。验证点：S1 完成后运行现有 storage duplicate-alias 测试，确认 late-failure 行为不变。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-低-recovery 与 identity guard 交互的测试覆盖缺口

- **位置**: §11.3 test matrix
- **问题类型**: 测试缺口
- **当前写法**: §11.3 测试矩阵覆盖了"crash interleaving：A在target swap后、COMMITTED前留下orphan，B已持不同ticker writer准备声明A的旧alias；B必须先在recovery guard内恢复A，再做identity validation并以typed conflict失败"。但没有覆盖以下场景：
- **反例/失败场景**:
  1. Recovery sweep 持有 identity guard 期间，一个 alias read 请求到达。read 应该被阻塞直到 recovery 完成，然后成功返回。
  2. Recovery sweep 恢复了一个 non-meta orphan batch（没有 `meta.json`），但 identity guard 仍被取得。这验证了 §01 的 performance concern。
  3. Recovery sweep 期间 identity guard 文件锁获取失败（模拟 filesystem error）。recovery 应该 fail-closed，不恢复任何 batch。
- **为什么有问题**: §11.3 声称覆盖了"recovery order与swap-before-COMMITTED crash interleaving"，但只覆盖了 meta commit 与 recovery 的交互，没有覆盖 read 与 recovery 的交互。
- **直接证据**: §11.3 test matrix（line 498–499）只描述了"A在target swap后、COMMITTED前留下orphan，B已持不同ticker writer准备声明A的旧alias"场景。
- **影响**: 若 recovery 与 read 的交互存在 bug（例如 read 在 recovery 期间看到不一致状态），该 bug 不会被现有测试发现。
- **建议改法和验证点**: 在 §11.3 增加"recovery 期间 alias read 被阻塞，recovery 完成后 read 成功返回"的测试。验证点：barrier-controlled test 中 recovery 和 read 并发执行，断言 read 在 recovery 完成后才返回正确结果。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 05-未修复-低-`_STORAGE_FAILURE_CODES` 常量不存在且需同步更新 mapper

- **位置**: §5.6
- **问题类型**: 契约缺失
- **当前写法**: §5.6 声称"新增 `_STORAGE_FAILURE_CODES` closed set，包含 `STORAGE_IO` 与 `TICKER_ALIAS_CONFLICT`；JSON parser 的 kind/code 一致性从该 set 派生"。但代码中不存在 `_STORAGE_FAILURE_CODES` 常量。当前 `_CONTENT_FAILURE_CODES` 是 frozenset（line 156），用于 `fins_upload_failure_from_exception` 中的 code 校验。
- **反例/失败场景**: 若 implementation agent 只添加 `TICKER_ALIAS_CONFLICT` 到 `FinsUploadFailureCode` 枚举但忘记创建 `_STORAGE_FAILURE_CODES` 常量和更新 mapper，`CompanyTickerAliasConflictError` 会落入 generic handler 产生 `UNEXPECTED_RUNTIME`，而非 `storage/ticker_alias_conflict`。
- **为什么有问题**: `CompanyTickerAliasConflictError` 是 `ValueError` 子类。当前 `fins_upload_failure_from_exception` 的 exception chain 是 `DoclingConversionError → OSError → generic`。`ValueError` 不在任何已识别的 exception 类型中，会落入 generic handler。
- **直接证据**: `upload_failure.py` line 161 的 `fins_upload_failure_from_exception` 只 catch `DoclingConversionError` 和 `OSError`；`ValueError`（包括 `CompanyTickerAliasConflictError`）落入 `else` 分支产生 `UNEXPECTED_RUNTIME`。
- **影响**: conflict error 的 failure code 不正确，用户/LLM 看到 `unexpected_runtime` 而非 `ticker_alias_conflict`，无法采取正确行动。
- **建议改法和验证点**: 在 S2 implementation 中，必须在 `fins_upload_failure_from_exception` 的 `OSError` catch 之前增加 `CompanyTickerAliasConflictError` catch。验证点：unit test 断言 `fins_upload_failure_from_exception(CompanyTickerAliasConflictError(...))` 产生 `kind=storage, code=ticker_alias_conflict`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Final plan review conclusion

**pass-with-risks**

Plan 在架构设计、锁序正确性、crash recovery、并发 exactly-one、conflict-before-mutation 和 failure transport 方面均通过 adversarial review。锁序分析确认 proposed `writer → recovery → identity → publication` 不形成死锁环路；identity guard serialize 了 meta commit 和 read，确保 exactly-one 和一致 alias index。

5 个 findings 均为低严重程度：§01 和 §02 是 performance/reliability concern（非正确性问题），§03 是 slice 语义澄清，§04 是测试覆盖补充，§05 是 implementation 时需注意的 mapper 同步。无 blocker。建议 implementation agent 在 S2 实现时关注 §01（recovery guard 取得时机优化）和 §05（mapper 更新），并在 §11.3 补充 §04 覆盖的测试场景。
