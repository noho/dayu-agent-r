## 6. Findings

### 1-未修复-中-allocated_periods 缺席键语义未钉死，热路径 ID 分配规则存在误实现口

- **位置**：plan §5 步骤 5（"无匹配：allocated ID 的 period/year 仍按 JSON 值与 candidate 直接比较…若不同，原 SHA1 分配…否则 allocated"）与 §9 identity 测试行（"无匹配、allocated period/year 未纠正/纠正 digest"）。
- **问题类型**: 契约缺失 / 测试缺口。
- **当前写法**：build"按 document_id 保存 (fiscal_period, fiscal_year)"于成功前缀；resolve 对 `allocated_periods` 查询 allocated[0] 的 period/year 与 candidate 直接比较。但**当 allocated 文档不存在（不在前缀、无 key）时**，"比较"没有定义：是"未变更→allocated"还是"取默认值比较"？计划未写。
- **反例/失败场景**：实施者写 `index.allocated_periods.get(allocated[0], (None, None))` 后直接比较——每个**首次下载的新 HK filing**（allocated 文档尚不存在，这是热路径）都会被判"财期不同"而走纠正 digest `fil_cn_{sha1(ticker|provider|source_id)}`，而不是 allocated `fil_cn_{sha1(ticker|form|year|period|amended)}`。两个 digest 外形相似但种子不同（本轮探针实测 `fil_cn_3b0b…` vs `fil_cn_6998…`）。upload 侧 `ingestion_runtime.py:1194` 对同一 filing 独立用 `build_cn_filing_ids` 计算 ID，若 download 走错分配规则，同一业务 filing 会出现两个 document ID，跨 owner 身份连续性断裂——正是 F4 所处的 duplicate 身份问题族。§9 网格只写"未纠正/纠正"两态（均为文档在场），未显式列"文档缺失→allocated"，新 owner 测试可能不钉该分支；行为自洽的 workflow 测试若不断言 ID 字面也可能放过。
- **为什么有问题**：goal 将"财期纠正后新候选 ID 的分配"列为身份绑定 owner 的职责；旧实现的语义是"仅当在扫描中见到 allocated 文档且 period/year 与 candidate 直接比较不同时才分配"（`cn_download_identity.py:35-38,49-53`；候选 §3 表也写了"无匹配 allocated 财期变更**才** SHA1 分配"），缺席=未变更。该分支是代码生成必经判断点，按 CLAUDE.md"不得让实施者重新设计/靠下游兼容补救"的标准，一句话规则必须写死在 plan。
- **直接证据**：`cn_download_identity.py:34-38`（`allocated_period_changed` 初值 False，仅在 `document_id == allocated[0]` 且比较不同时置位）、`:49-53`（仅 changed 才 digest）；`cn_form_utils.py:190-193`（allocated 种子）与 digest 种子 `ticker|provider|source_id` 不同；`ingestion_runtime.py:1188-1200`（upload 独立消费 allocated 约定）；plan §5/§9 原文；本轮探针 `workspace/tmp/pr197-f4-planrereview-mimo-20260930-01/probe_allocated_absent.py`（空真实 Fs 仓储上当前 resolve 返回 allocated ID、不等于纠正 digest，exit 0）。

### 2-未修复-低-未读取空索引与已读空索引不可区分，HK resolve 可静默走分配

- **位置**：plan §5 `CnDownloadIdentityIndex` 类型与 `read_cn_download_identity_index`（"无 HK 或空集合返回 ticker 对应空的只读索引，零仓储读取"）及 resolve 步骤 2（仅校验 `index.ticker` 相等）。
- **问题类型**: 契约缺失（防御性）。
- **当前写法**：index 冻结形状只有 ticker/source_matches/allocated_periods/read_error；"空的只读索引"与"读了但 D=0"的值相同；规则层面禁止误用（"调用方不能自行过滤掉即将消费的 HK candidate；不将空索引作失败 fallback"），但 resolve 对 HK candidate 遇空索引时的行为仍是"无匹配→allocated"。
- **反例/失败场景**：未来调用方（或实施中临时代码）对 HK candidate 传入"因候选集不含 HK 而未读取"的空索引：resolve 不报错，静默返回 allocated，仓储中已有的同 source 文档被无视 → 新写入与旧文档形成重复绑定。与 F1 的错误分配同族，且更隐蔽（无异常）。
- **为什么有问题**：本 WU 的目标之一就是消除"批初绑定/陈旧观察导致写错身份"类风险；计划对 ticker 误用加了 ValueError 开发契约护栏，却对更危险的"空索引冒充已读"无护栏，防御不对称。合法生产路径（§6 六个 caller 均经 read helper 取 index）不会触发，故仅为低。
- **直接证据**：plan §5 两段原文；`read_cn_download_identity_index` 的"无 HK 或空集合返回空索引零读取"语义；resolve 步骤 2-5 对空索引的自然推演结果为 allocated。
- **影响**：实施 Agent 或后续 WU 误用时静默产生错误绑定；测试若只覆盖 helper 路径则长期不可见。
- **建议改法和验证点**：最小改法二选一：(a) index 增加一个开发契约字段（如 `view_loaded: bool`），resolve 对 HK candidate 在 `view_loaded=False` 时抛与 ticker 误用同类的开发契约 ValueError；(b) 若坚持冻结形状，则在 §5 明文"空索引只允许来自'候选集无 HK'的 helper 调用，HK resolve 不接受空索引"并加负例测试（直接手工构造空 index 调 resolve 断言拒绝）。验证点：`test_cn_download_identity.py` 负例一条。
- **修复风险（低/中/高）**：低。
- **严重程度（低/中/高/严重）**：低。
