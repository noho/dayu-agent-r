### 001-未修复-[中]-material delete 的原始文件状态守卫只落在 CLI，Service/pipeline 可带着缺失文件执行删除

- **入口/函数**: `admit_fins_upload_material_request`、`FinsIngestionRuntime.upload/start_upload`、`SecPipeline.upload_material_stream`。
- **文件(行号)**: `dayu/fins/upload_asset_plan.py:332-335`；`dayu/fins/ingestion_runtime.py:1496-1532`、`1476-1480`；`dayu/fins/pipelines/sec_upload_workflow.py:460-551`；对照 CLI guard `dayu/cli/commands/fins.py:1167-1172`。
- **输入场景**: 已存在 material 目标，请求 `action="delete"`，但 `files` 中放一个不存在的普通路径，例如 `missing.pdf`；通过 raw Service/pipeline 入口提交。
- **实际分支**: `plan_upload_assets` 只检查 raw 数量，delete 分支直接返回空 `FinsUploadMaterialFiles` 和空 `UploadAssetPlan`，没有规范化或检查 raw 文件；validated handoff 保留原始 `request.files` 但权威 selection/plan 为空，workflow 随后按空 plan 执行 source delete。
- **预期行为**: Gateflow I-R2 明确要求恢复 material delete 原始文件存在性/普通文件守卫，并让数量事实同源；在 O16 尚未裁决 delete+files 规则前，不应由 Service/pipeline 静默忽略无效 raw evidence。
- **实际行为**: 可执行探针 `admit_fins_upload_material_request(... action="delete", files=(missing,))` 返回 `file_selection.is_empty=True`、`asset_plan.ordered_pairs=()`、`validated_fins_upload_file_count=0`；真实 `SecPipeline.upload_material_stream` 在该输入下产生 `upload_started`、`upload_completed(deleted)`，已存 material source 被删除，missing 路径从未验证。CLI 单独补的 guard 因此不是共享 contract。
- **影响**: 破坏性 delete 可在原始请求携带不存在/非法 evidence 的情况下执行；不同入口行为不一致，后续审计无法证明 delete 请求的 raw 文件输入经过同一准入。file_count 本身在合法 raw 文件和 delete 空 selection 下是一致的 0，但不能弥补原始文件守卫缺口。
- **建议改法和验证点**: 在 material admission owner（或其直接上游 raw request validator）统一执行 delete raw 文件存在性和普通文件校验，仍由同一 plan 产出空 selection/0 count；若 O16 最终决定拒绝 delete+files，则在同一 owner 直接 typed reject。补 Service/runtime、SEC/CN raw façade 和真实 CLI 的缺失文件、目录、101 项、合法文件四类回归，并断言 observation/job/source mutation 前失败或保持既有 delete 语义。
- **修复风险（低/中/高）**: 中。需要先锁定 O16 的业务语义，避免把现有“delete raw files 不参与目标选择”的规则误改成文件驱动删除。
- **严重程度（低/中/高/严重）**: 中

- **严重程度（低/中/高/严重）**: 中
