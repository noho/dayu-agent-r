## 2. Re-review 新发现（修复文本自身引入的残余问题）

### RF1-未修复-中-冻结的 `_inspect_source_kind_unguarded` 签名未定义 whole-kind inventory / commit 的调用约定

- **位置**：§6.1 冻结签名（`requested_document_id: str` 为 required，`_SourceKindPublicationInspection.target` 非 Optional）
- **问题类型**：不可直接实施 / 契约缺失
- **当前写法**：函数只接受单一 `requested_document_id`，返回结构以单一 `target` 为轴；§6.1 三类 caller 规则与 §6.2 同时要求 `list_source_integrity`（inventory 无单一 target）与 commit validator（"用 inspector 遍历 staging source kinds"）复用同一函数，但 plan 未定义这两个 whole-kind 调用怎么传入 `requested_document_id`、`target` 字段怎么投影。
- **反例/失败场景**：inventory 需要为每个实际 source 投影 shared manifest reason，若实现逐 doc 调用同一函数，`shared_manifest_reasons`/`canonical_manifest_items` 会在每次调用重算（结果必须逐次一致）；若实现选一个 doc 当 target，则 `target` 语义被污染且非对称。commit validator 同理。implementation agent 需要在 Slice 2 自行决定调用形状，与"冻结签名、禁止重设计 guard 接口"的 slice 纪律冲突。
- **直接证据**：修订 plan §6.1 冻结代码块（`_inspect_source_kind_unguarded(*, ticker, source_kind, ticker_dir, source_root, requested_document_id)`）与 §6.1 caller 规则、§9 Slice 2 step 2 的原文；现有代码 `_fs_source_document_core.py:514-567`（`list_source_integrity` 逐 doc 循环 + manifest 校验）与 `_fs_storage_infra.py:1142-1170`（commit validator 遍历 source kinds）证明两个 caller 天然没有单一 target。
- **影响**：Slice 2 返工风险 / shared reason 跨调用一致性无保证 / review 不可验收
- **建议改法和验证点**：在 §6.1 补一句调用约定：inventory 与 commit validator 按 document ID 顺序逐 doc 调用（`requested_document_id` 为当次 doc），`target` 即当次 doc 的 inspection，`shared_manifest_reasons`/`canonical_manifest_items` 为 source-kind 级事实、在同一 guard/batch 内多次调用必须相等；或把签名改为 `requested_document_id: str | None` 并定义 None 时 target 投影规则。§11.1 增加 "同一 guard 内连续两次 inventory 的 shared reasons/canonical items 相等" 断言。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### RF2-未修复-中-canonical remaining items 的载体在 §6.1 与 §6.2 step 5 之间存在读取歧义，误读会使多 source 的 target-local repair 全部被 CANONICAL_MANIFEST_UNAVAILABLE 阻断

- **位置**：§6.1（`canonical_manifest_items` 非空条件）vs §6.2 step 5（canonical remaining items 来源）
- **问题类型**：契约缺失 / 不可直接实施
- **当前写法**：§6.1 规定 "`canonical_manifest_items` 只有 inventory 每个 source 的 `content_classification=COMPLETE` 时才非空"；§6.2 step 5 规定 "canonical remaining items 只取 inspector 已从每个 trusted non-target persisted meta 调用 ManifestItem owner 的结果；若无法生成全量唯一 items，抛 `SourceIntegrityRepairBlockedError(CANONICAL_MANIFEST_UNAVAILABLE)`"。plan 未写明 step 5 消费的是 aggregate tuple 还是每个 non-target inspection 的单点 `canonical_manifest_item` 字段。
- **反例/失败场景**：最常见的 repair 场景——target original 缺失（target `content_classification=REPAIR_REQUIRED`）+ 一个 complete sibling + manifest 存在且投影一致。此时按 §6.1 的 aggregate 规则 `canonical_manifest_items` 为空 tuple；若 step 5 读取 aggregate，则 "无法生成全量唯一 items" → blocked，**所有存在 sibling 的 target-local repair 必然失败**，直接违背 §11.3 "multi-file repair……不丢 non-target item" 与 goal #4/#6。只有 step 5 明确消费每个 non-target 的 `canonical_manifest_item`（其可用性以该 source 自身 content COMPLETE/trusted meta 为条件，与 target 无关）才能闭合。
- **直接证据**：修订 plan §6.1 末段与 §6.2 step 5 原文；`_fs_storage_infra.py:1237-1255`（commit 时逐 source 生成 `FilingManifestItem.from_source_meta(meta).to_dict()` 的既有模式）证明 per-source 生成是现有事实，aggregate 条件只是 §6.1 新增的收紧。
- **影响**：生成错误代码 / 核心修复路径被误阻断 / 后续返工
- **建议改法和验证点**：§6.2 step 5 改为显式 "remaining items = 每个 non-target inspection 的 `canonical_manifest_item` 按 document ID 排序的 tuple（其单点可用性只依赖该 source content=COMPLETE/trusted meta），不使用 `_SourceKindPublicationInspection.canonical_manifest_items` aggregate"；§11.3 增加 "target content REPAIR_REQUIRED + ≥1 complete sibling + manifest 一致 → repair 成功且 remaining items 来自 per-source 字段" 节点。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### RF3-未修复-低-`reset_source_document_for_repair` step 3 与 `has_same_source_publication_identity` 的 UNSAFE-ValueError 机制未写明，存在 raw ValueError 逃逸回 UNEXPECTED_RUNTIME 的窄缝

- **位置**：§5.1（`has_same...` 对 UNSAFE 抛 ValueError）、§6.2 step 3/4
- **问题类型**：状态机漏洞 / 契约缺失
- **当前写法**：§5.1 规定任一参数 UNSAFE 时 `has_same_source_publication_identity` "立即 ValueError"（非返回 False）；§6.2 step 3 写 "要求 `has_same_source_publication_identity(expected, staged)` 为真，且 staged 仍为 REPAIR_REQUIRED；否则立即抛 SourceIntegrityRevisionConflictError"——把该函数当作布尔谓词使用。step 4 首句虽覆盖了 "content_classification 变为 MISSING/UNSAFE → conflict" 的语义归属，但没有写明 step 3 在调用比较函数前必须 gate 掉 UNSAFE（或把比较函数抛出的 ValueError 转换为 conflict）。

- **影响**：窄缝重开 typed failure 缺口 / 实施 Agent 二义实现
- **建议改法和验证点**：§6.2 step 3 增加一句 "调用 `has_same_source_publication_identity` 前先检查 expected/staged 任一为 UNSAFE 或 public status 非 REPAIR_REQUIRED，直接抛 `SourceIntegrityRevisionConflictError`；比较函数自身的 ValueError 也必须在方法内转换为同一 conflict，禁止向外传播"。§11.3 的 "变 unsafe 分别 stale 失败" 节点断言异常类型为 conflict 映射后的 `SOURCE_REVISION_STALE`。

### RF4-未修复-低-§7.2 "download whole manifest missing 必须以 typed SourceIntegrityPreflightError fail closed" 的绝对表述与单 source 场景的实际行为不符

- **位置**：§7.2 download 与 snapshot
- **问题类型**：open question 未收敛 / 测试缺口
- **当前写法**：§7.2 宣称 whole manifest missing 时 download whole-tree preflight "必须以既有 typed `SourceIntegrityPreflightError` fail closed"。但 `classify_source_integrity_preflight`（现有纯函数）在只有单一 REPAIR_REQUIRED target 且该 target 是 accepted filing 时返回 `SelectedSourceRepairRequired`，不抛 error——单 source 场景下 download 会走既有 repair 路径（reset → 下载重建 → upsert 重建 manifest → commit 校验），行为安全但并非 "fail closed"。
- **反例/失败场景**：ticker 下只有 1 个 filing、manifest 缺失。preflight 返回 SelectedSourceRepairRequired → download 继续 → 重建后 commit 通过。plan 文本说 "必须 fail closed"，实施 agent 可能按文本在 download 侧新增无条件拒绝，改变既有可用行为（scope 外变更），或发现文本与机制不符而困惑。

- **影响**：实施 Agent 跑偏 / 无谓回归
- **建议改法和验证点**：§7.2 改为 "whole manifest missing 投影为 shared reason 后，download preflight 在存在多 source/非 selected target 时以既有 typed preflight error fail closed；单一 accepted filing 场景保持既有 selected repair 重建行为，并用 §11.4 既有 download 回归保护"。补一个单 source manifest-missing 的 download 回归节点。
