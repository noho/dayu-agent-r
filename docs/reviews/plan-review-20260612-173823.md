## Findings

### F01-未修复-中-classifier 测试文件放置与 S1 验证边界不完全匹配

- **位置**: S1, Implementation Slices > S1: Durable Integrity Classifier, Files 与 Validation
- **问题类型**: 切片过粗 / 测试缺口
- **当前写法**: S1 新增 `dayu/host/memory_snapshot_integrity.py` 并修改 `dayu/host/durable/memory.py`，但测试文件只列出 `tests/host/test_memory_projection.py`，验证命令为 `pytest tests/host/test_memory_projection.py -q`。
- **反例/失败场景**: `memory_snapshot_integrity.py` 是全新模块，包含 `MemorySnapshotIntegrityFailureKind`、`MemorySnapshotIntegrityIssue` 和 `inspect_memory_snapshot_integrity(transaction)` 三类新符号。放到 `test_memory_projection.py` 虽然是合理的（操作同一组 durable tables），但如果 implementation agent 把大量 classifier-only 测试（逐 row 扫描逻辑、五种 failure kind 的覆盖、空 DB 返回空 tuple、异常只在查询级别抛出等）混入一个已承担 memory projection 语义测试的文件，review agent 需要同时理解两套不相关的语义才能安全审查。
- **为什么有问题**: 计划没有说明 classifier 测试的最小覆盖矩阵，也没有明确 classifier 的独立语义闭环测试应该如何与 memory projection 已有测试分开。这增加了 implementation agent 把这些测试塞进现成文件的尾部、导致测试文件语义混杂的风险，也增加了 review agent 的判断负担。
- **直接证据**: S1 Files 列表只列出 `tests/host/test_memory_projection.py`，没有新增独立测试文件；S1 Validation 只运行该文件，没有验证 classifier 覆盖矩阵。
- **影响**: 实施 Agent 跑偏（测试组织混乱）/ review 不可验收（review agent 需要额外判断哪些测试属于 classifier、哪些属于原有 projection）
- **建议改法和验证点**:
  1. S1 要么显式声明 "新测试函数追加到 `test_memory_projection.py` 并在 docstring 中明确标注 `[WU-CM-09] classifier`"，要么新增 `tests/host/test_memory_snapshot_integrity.py`。
  2. S1 应包含 classifier 的最小覆盖矩阵：空 DB、valid snapshot 返回空 tuple、invalid JSON、schema mismatch、digest mismatch、unsupported item kind、storage_read_failed、混合损坏、以及 classifier 自身查询失败（非单个 row 失败）。
- **修复风险（低）**:
- **严重程度（中）**:

### F02-未修复-低-`HostStorageMaintenanceResult.__post_init__` 字段校验未提及

- **位置**: S2, Changes: "Extend `HostStorageMaintenanceResult` with `memory_snapshot_integrity_issues`"
- **问题类型**: 契约缺失
- **当前写法**: S2 Changes 提到扩展 `HostStorageMaintenanceResult` 和更新 `json_value()`，但未显式说明需要更新 `__post_init__` 的字段校验逻辑。
- **反例/失败场景**: `HostStorageMaintenanceResult.__post_init__` 当前对每个字段做严格类型检查（`isinstance` + 类型特定校验）。新增 `memory_snapshot_integrity_issues: tuple[MemorySnapshotIntegrityIssue, ...]` 后，如果 `__post_init__` 不更新，类型错误不会被防御性捕获。虽然 frozen dataclass + pyright 可以静态检查大部分类型错误，但 `__post_init__` 的运行时防御是现有契约的一部分，不能省略。
- **为什么有问题**: 现有 `HostStorageMaintenanceResult.__post_init__` 对每个字段都做了运行时校验（usage、physical_artifact_bytes、orphan_artifact_candidates、reclaimed_artifact_paths、file_errors、wal_checkpoint），新增字段不更新会导致该字段享受不到同等级的运行时防御，形成不一致。
- **直接证据**: `dayu/host/storage_maintenance.py:162-197` `HostStorageMaintenanceResult.__post_init__` 逐字段校验。
- **影响**: 状态不一致（字段无运行时防御）/ 后续返工（review 必定要求补齐）
- **建议改法和验证点**: S2 Changes 显式列出 "extend `HostStorageMaintenanceResult.__post_init__` with tuple-of-`MemorySnapshotIntegrityIssue` validation"。
- **修复风险（低）**: 一行描述修改即可。
- **严重程度（低）**:

### F03-未修复-低-S2 测试对 `storage_read_failed` 的 monkeypatch 策略未充分定义

- **位置**: S2, Changes: "storage-read failure classification through a controlled test monkeypatch of the classifier/read operation, without changing production corruption semantics"
- **问题类型**: 测试缺口
- **当前写法**: 计划用 monkeypatch 模拟 storage-read failure，但没有说明如何在不改变生产语义的前提下构造一个"行可读取但恢复过程出错"的场景。`storage_read_failed` 是 catch-all: "读取或字段恢复过程中出现不能归入前述类别的 durable row 读取错误"。
- **反例/失败场景**: 如果 monkeypatch 的方式是替换 `transaction.fetchall` 或 `transaction.fetchone` 抛出异常，那么它会阻止 classifier 扫描所有行而不是单个行，测试无法区分 "单行读取失败" 和 "全表扫描失败"。如果 monkeypatch 在 classifier 内部 hook，测试耦合于实现细节，可能随 classifier 重构而失效。
- **为什么有问题**: 计划未说明用什么具体机制构造 `storage_read_failed` 的测试场景。`storage_read_failed` 的语义边界（"不能归入前述类别"）在测试实现中是最容易模糊的类别，容易写成 "什么都测不到" 或 "什么都归入此类"。
- **直接证据**: S2 原文 "through a controlled test monkeypatch of the classifier/read operation" — monkeypatch 对象不明确。
- **影响**: 实施 Agent 跑偏（可能用不正确的 monkeypatch 伪造通过）/ review 不可验收
- **建议改法和验证点**:
  1. 明确 monkeypatch 的具体目标，例如 "构造一个 `snapshot_json` 列本身为 NULL 的行"（这会触发 `_require_text(row.get("snapshot_json"), ...)` 抛出，被 classifier 归入 `storage_read_failed` — 前提是它不会被 invalid_json 拦截）。
  2. 或者用 SQL 直接写入不合法的行（例如 `snapshot_json` 为 NULL、或 `snapshot_id` 违反 CHECK 约束），然后用 classifier 扫描证明它归入 `storage_read_failed` 而非静默跳过。
  3. 测试至少包含 2 个不同的 storage_read_failed 触发路径。

## Open Questions

### Q1: classifier 对 multi-session / multi-snapshot 的扫描是否需要 session_id 过滤？

Plan 说 classifier 扫描 `host_memory_snapshots` 逐 row 分类。对于有大量 session 和大量历史 snapshot 的生产 DB，全表扫描可能返回大量 issues。当前 plan 没有 session_id 过滤参数。作为 operator-facing maintenance，全量报告是正确的默认行为，但 plan 应该显式确认这是意图。

### Q2: `host_memory_items` 的 `item_kind` CHECK 约束是否已阻止 `verified_fact` 写入？

当前 `host_memory_items` DDL 的 CHECK 约束只允许 6 种 item kind（`evidence_backed_fact`、`selected_recent_window`、`reference_continuity`、`answer_anchor`、`forward_intent`、`session_summary`），不包含 `verified_fact`。这意味着新写入不可能产生 `verified_fact` 行。classifier 的 `unsupported_item_kind` 只对存量旧数据有效。plan 应该确认这一退化风险并记录（可以在设计文档中注明 `unsupported_item_kind` 主要是防御已有旧数据和新代码 bug，不是持续增长的威胁面）。

## Review Lenses 摘要

### Architecture Boundary
- **通过**。所有变更停留在 Host 层；classifier 只依赖 `HostTransaction`（已是 Host durable primitive）；不修改 Engine、Service、UI、Fins；public result 扩展是现有 `HostStorageMaintenanceResult` 的向后兼容字段添加。

### Best Practice
- **通过**。read-only classifier + 返回 issue tuple 而非抛异常 + 不修改任何 row + 保留已有 fail-closed 行为，符合工程最佳实践。

### Optimal Solution
- **通过**。挂到 `run_storage_maintenance` 而非独立入口是合理选择——已有 maintenance surface 已捆绑多种 diagnostic 扫描，新增的 snapshot integrity 报告属于同类 operator-facing read-only diagnostic。

### Overengineering
- **通过**。不新增 quarantine 表、不实现 rebuild/overwrite、不新增独立 CLI 命令、不做 scheduler-driven scan。三个 slice 只实现当前 Issue #41 acceptance signals 要求的最小能力。

### Overcoupling
- **通过**。`memory_snapshot_integrity.py` 只依赖 `HostTransaction`，不依赖 storage maintenance、artifact lifecycle 或 WAL checkpoint。Classified 与 maintenance result 的集成是单向消费关系。

## Plan Review Conclusion

**PASS-WITH-RISKS**

三个 findings 均为低或中严重度，无 blocker。F01（测试文件组织）建议在进入 implementation gate 前收敛；F02（`__post_init__` 更新）是实施时会自然发现的小遗漏；F03（`storage_read_failed` monkeypatch）可在 S1 implementation 时细化。Open questions 和 residual risks 有明确 owner/deferred destination，不阻塞当前 WU。

五个用户指定重点挑战的审查结论：

1. **`run_storage_maintenance` surface**: **成立**。已有 maintenance 入口捆绑 read-only diagnostic 扫描是合理选择。Classifier 不执行 destructive 操作，不与 orphan reclaim 的写事务耦合。
2. **Classification 基于直接证据**: **成立**。五个分类都是直接检查 durable row 字段（`snapshot_json` parse、typed shape recovery、digest computation、`item_kind` value、exception catch），不依赖间接推断。Manual corruption 会自然归入前四个分类或 `storage_read_failed`。
3. **不会把 snapshot 抬成 truth 或诱导 silent rebuild/overwrite**: **成立**。Plan 明确 non-goals 排除了自动 overwrite、silent rebuild、snapshot-as-truth、command-path rebuild。Classifier 只返回 issue tuple，不修改任何 row。
4. **Public result/export/README 触发完整**: **成立但 F02 需修**。S2 覆盖了 `HostStorageMaintenanceResult`、`json_value()`、root exports、package exports 测试；S3 覆盖了 design doc、host README、tests README、control doc。F02 指出 `__post_init__` 遗漏。
5. **Slice 大小合理**: **成立**。S1（classifier）→ S2（maintenance integration）→ S3（docs closure）的递进是可独立验证的闭环；每个 slice 有明确的输入、输出、non-goals、文件列表和验证命令。
