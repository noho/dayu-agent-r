- **入口/函数**: `SecPipeline.upload_material_stream` 经 `run_upload_material_stream`；CN/HK 对应入口为 `CnPipeline.upload_material_validated_stream`。

- **输入场景**: 正常 CLI/tool material create 请求，文件名和格式均合法，但任一文件转换失败；最小反例是一个可转换文件加一个会被 converter 拒绝的 `corrupt.docx`。
- **实际分支**: 流程先发出 `UPLOAD_STARTED`，在 `:506-519` 将 company name/aliases 写入独立 batch 并 commit；随后 `:520` 才读取原件和转换。转换异常进入 `:585` 的统一 catch，只构造 `UPLOAD_FAILED`，没有回滚已经提交的 company batch。
- **预期行为**: terminal 为 upload failure 且 source 未发布时，company metadata 不应留下本次失败请求产生的持久变更。company 与 source 应在同一 publication boundary 提交，或至少在 prepare/conversion 失败时回滚 company stage。

- **直接证据**: SEC 在 `sec_upload_workflow.py:506-519` 显式 `commit_batch(company_batch)`，失败 catch 在 `:585-615` 不接触该 batch；CN 在 `cn_pipeline.py:1146-1159` 重复同一顺序。相对照，CN filing 的 owner 测试 `tests/fins/test_cn_pipeline.py:1480-1519` 明确要求 company/source stage 失败回滚同一 batch 且 published tree 不变。
- **影响**: 失败上传仍会更新公司名称、ticker aliases 或其持久版本；重试、审计和用户看到的 company state 与“上传失败、零 source 发布”不一致，属于 durable partial state。
- **建议改法和验证点**: owner 修复应把 material company stage 与 source prepare/publication 收束到同一 batch capability，或先完成所有可失败的读取/转换再提交 company stage。SEC/CN 各补 converter 失败、storage 失败、取消路径测试，断言 company bytes/tree 与失败前完全一致、source 未发布、唯一 terminal 为 failed。
- **修复风险（低/中/高）**: 中（涉及 SEC/CN 两个 workflow 的事务边界；不能只在 catch 中做下游补偿）。
- **严重程度（低/中/高/严重）**: 高。
