## Material findings

### 1-未修复-中-Host 截断与 Fins 分页的续读合同缺少验证

- **位置**: §5 工具层说明；§6.1 验证清单第 2、7 项；§6.3 实际输入复验。
- **问题类型**: 测试缺口 / 契约缺失
- **当前写法**: §5 要求“工具层的 Host 截断元信息和 Fins 页范围各自显式保留，只有取回该 runtime 页全部内容后才能按其 `next_start` 前进”，但 §6.1 只验证 runtime 范围/续读和输出泄漏，§6.3 只重放现有调用；没有一项测试或验收断言 Host 截断后的 `fetch_more` 补读与 Fins `next_start` 的联合行为。
- **反例/失败场景**: `read_original_text` 返回一个 runtime 页（`truncated=false`，`next_start=X`），但 Host `ToolTruncateSpec` 因配置上限较低把 `text` 字段替换为 cursor 包装对象。模型只看到可见前缀，忽略包装对象并直接按 `next_start=X` 读取下一页；中间被 Host 截掉的文本永久跳过。或者模型调用 `fetch_more`，但只补读一次而未取完，仍按 `next_start` 前进。两种情况下 API 的“连读无间隙/无重复”承诺在工具层被破坏，而 runtime 结果本身仍显示 `truncated=false`。
- **为什么有问题**: Plan 已经识别这是高风险交接点，却没有把该行为列入 owner 级测试或真实复验；实现 Agent 很容易只验证 runtime 分页，而把工具层的 Host 截断当作既有基础设施默认正确。项目要求范围完整性是公共 contract，不能只靠文档声明。
- **直接证据**: `host/tool_runtime.py:2006-2030` 与 `:6052-6070` 的字段替换；`fins_tools.py:559` 的 `_text_truncate(limits.read_section_max_chars, "content")`；plan §5 和 §6.1/§6.3 的对应文字。
- **影响**: 调用方可能在大文档中静默漏读一段原文，且无法从返回的 `truncated/next_start` 看出遗漏；这正是 R2 要消除的“未声明范围缺失”在工具层的复发。
- **建议改法和验证点**: 在 §6.1 增加一个集成断言：构造一个 runtime 页大于 Host 截断上限的 `read_original_text` 结果，断言 Host 返回 cursor 包装、`fetch_more` 补读完整 remainder、拼接后等于 runtime 页 `text`，并且只有在该页补齐后才允许按 `next_start` 前进；在 `fins_tools.py` 的新工具说明中明确这一步。若实现选择让 Host 截断上限始终大于 runtime `max_chars` 上限，则用测试固化该不变式，并说明理由。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-storage typed 角色投影与现有 raw-meta 角色解析形成平行真源

- **位置**: §2.1 “文件角色只投影 storage 已验证的声明……不让消费者解析 raw `source_meta.files`”；§5 生产范围（未列 `report_original_source.py`）。
- **问题类型**: 架构边界 / 语义所有权
- **当前写法**: Plan 新增 `is_reading_primary`、原件/派生角色、`original_filename`、`derived_from` 的 storage typed 投影，并规定消费者不得解析 raw `source_meta.files`；但现有 `project_report_original` 仍直接从 raw meta 推导 `source=="original"` 和 PDF 角色，且不在 §5 的修改范围内。
- **反例/失败场景**: 实现 Agent 只在新的 snapshot 接口上增加 typed 角色，`project_report_original` 继续从 raw `source_meta.files` 独立判断。未来 storage 对角色声明做规范化、拒绝或投影调整时，两条路径可能给出不同结论；例如 raw meta 的 `source` 字段仍存在但 descriptor 的 typed 角色因投影规则变化而不同，或新代码修复了角色歧义而旧路径未修复。测试也会分别固化两套行为。
- **为什么有问题**: 这直接违反项目 `语义所有权与修复边界` 规则中“多个消费者需要同一语义时，必须复用同一个 source of truth / public contract / projection helper”，也与 plan 自己写的“不让消费者解析 raw `source_meta.files`”不一致。它不一定破坏 R1–R3 的当前行为，但会留下两个 owner 对同一角色语义的平行实现。
- **直接证据**: `report_original_source.py:42-58` 直接读取 `snapshot.source_meta["files"]`；plan §2.1 的规则；`_fs_source_integrity.py` 已有 `_DeclaredSourceFile.source/original_filename/derived_from` 可作为同一投影来源。
- **影响**: 角色语义漂移、后续修复只落在一条路径、测试无法证明唯一真源；如果实现 Agent 为避免重复而顺手改 `report_original_source.py`，又可能超出 plan 明确的生产范围而没有对应测试/README 说明。
- **建议改法和验证点**: 二选一并写入 plan：(a) 将 `report_original_source.py` 纳入本 slice，改为使用 snapshot 的 typed 角色投影，并复用同一校验；或 (b) 明确该规则只约束新原文 API，现有 CN/HK 原件路径保持不变，并把“角色语义双路径”列为有 owner 的 residual risk。无论哪种，都应在 owner 测试中断言 storage typed 角色与 raw 声明冲突时 fail closed，且不要由下游 fallback。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open questions

1. **`query_original_facts` 的 namespace 输入如何被 LLM 发现**：Plan 要求 `concepts` 每项必填 `namespace_uri`、`local_name`，并规定 URI 必须来自原文、不得从 filing meta 推断；但四个 API 中没有独立的 namespace 清单，`read_original_structure` 只在节点属性中带 namespace 声明。请总控明确：工具说明是否强制模型先读原文结构/根节点发现 `xmlns:dei` 等绑定，或是否允许以 `prefix:local` QName 输入并由文档作用域解析。若不明确，实际调用方可能只能预先硬编码按年变化的 DEI namespace URI，降低 R1 的可用性；这不构成当前 plan 的真实阻断，但应在 implementation 前收敛。
2. **是否需要在 R3 结果中暴露 storage revision**：Plan 的 `SourceAssetIdentity` 只含内容 sha/size，不替代 storage revision；这能绑定同版字节，但调用方无法区分“同字节重发”的 publication revision。若 goal 的“版本信息”仅指内容身份，当前设计成立；若要求 publication revision，应明确从哪里公开且遵守 LLM-facing 的 opaque 引用约束。
3. **`search_document`/`list_tables`/`get_table` 是否也需要 `source_asset`**：Plan 只把新资产绑定覆盖四个原文 API 和章节/目录结果；这些便利结果仍只有 filing 级 citation。请确认这是有意的范围边界（不把便利视图当完整原件），而不是遗漏 R3 的“每份原文返回”要求。

## Conclusion

**pass-with-risks**

Plan 对 R1–R3 的根因、owner 边界、最小方案、cache/version/取消/错误语义和验证范围整体充分：新原文能力复用 storage snapshot、现有 processor 与 `FinsReadRuntime`，没有新建平行文件仓储/缓存/版本真源；资产身份、原文字符坐标、结构/事实契约、范围续读和 A/H、SEC 正向能力保留均有明确方向；真实输入锚点与 TSO/TSM 证据核对未发现 plan 的事实性错误。

未发现阻止进入 implementation 的真实 scope/contract/architecture blocker。Material findings 均为可在实现前收敛的验证或所有权细化：Host 截断/分页联合测试、typed 角色投影与现有 raw-meta 消费者的边界、回归测试命令覆盖。建议总控将 Finding 1、2 作为 implementation checklist，Finding 3 作为 §6.2 命令修订，并把 Open Questions 中 namespace 发现路径在启动实现前明确；完成这些后可按 plan 的单一 implementation slice 推进。
