### 1-未修复-中-seed 门控谓词未定义，显式空 document_id 断言被错误绑定在种子门控上
- **位置**: 计划「Owner、契约与精确修改范围」`ingestion_runtime.py` 行（第 21 行）、「停止条件检查」段（第 12 行）、「残余风险」段（第 56 行）
- **问题类型**: 契约缺失 / 状态机漏洞（时序）
- **当前写法**: 「针对具备 `form_type`/`material_name` 的请求调用 `build_material_ids` 和上述断言」；并声明「此处不发明其缺失值规则」。
- **反例/失败场景**: Service API 调用 `upload_material(form_type=None, material_name=None, document_id="")`（或 `form_type=""`）：门控判定跳过 → admission 通过 → `upload.preparing`/`upload.started` 已发出 → runner 抛 `ValueError("material 上传必须提供 form_type")`，exit 1 泛化错误；O08 裁决的「显式空 `document_id` 非法」这一形状规则从未以字段级 typed usage 投影。另一分支：若实施者把「具备」理解为非 None，`form_type=""` 会让 `build_material_ids` 在 admission 抛非 typed 的 `ValueError("form_type 不能为空")`（exit 1 泛化），与「不发明 O05 缺失值规则」冲突；若理解为规范化后非空，则落入前一分支。
- **为什么有问题**: 显式空/纯空白是输入形状规则，不需要身份种子即可判定；goal 第 13 行要求「不匹配及显式空值……尽可能在 upload.started 前拒绝」。plan 把 EMPTY 与 MISMATCH 一起绑在种子门控内，且未定义门控谓词（None 判定还是空白判定），实施 Agent 必须二选一，两种选择分别违反 plan 的一条声明。CLI 与 tool 通道在各自入口预拒空值（`fins.py:1225-1227`、`_ingestion_tool_helpers._optional_nullable_text`），owner 的 EMPTY reason 唯一可达受众就是 Service/direct request，恰好是缺口通道。
- **直接证据**: `ingestion_runtime.py:4745`（material 分支现仅 `_normalize_upload_request`）；`service_runtime.py:227-230`（runner 检查 `is None` 且晚于 started）；`upload_tools.py:358` + `_ingestion_tool_helpers` 空值预拒；`fins.py:96/1227`（O08 文案）；goal 第 13 行；plan 第 12/21/56 行。
- **影响**: O08 语义在 Service 通道对无种子请求失效（错误晚于 started 且错因错位）；typed 时序验收口径含糊；可能把过渡性门控固化成脆弱分支（AGENTS.md 禁止脆弱分支）。
- **建议改法和验证点**: (a) 写死门控谓词（建议：`form_type` 与 `material_name` 均非 `None`，与 runner 现有判定对齐）；(b) `document_id` 显式空/纯空白在 material admission **无条件**拒绝并投影 `MATERIAL_DOCUMENT_ID_EMPTY`（不需要种子），仅 MISMATCH 断言按种子门控；(c) 明示该门控为 O05-F01 落地前的过渡态，O05 将必填校验前移后删除门控、断言改为无条件。验证点：补一条 Service 直构请求（无种子+空 document_id）断言早于 started 的 typed EMPTY；补 `form_type=""` 的口径测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-runtime usage 消息以 CLI flag 措辞充当跨通道公开投影真源
- **位置**: 「typed 错误与时序」段与 owner 表格的两条消息（`--document-id 不能为空`、`--document-id 与材料稳定文档 ID 不一致；请省略或填写系统生成的 ID`）
- **问题类型**: 架构边界（LLM-facing 语义）/ 语义所有权
- **当前写法**: 「runtime 的 closed usage code/message 是公开错误投影真源」，CLI 直接渲染 `exc.failure.message`，tool 走 `ValueError` 分支投影 invalid argument。
- **反例/失败场景**: tool 通道 mismatch：`FinsUploadUsageError` 是 `ValueError` 子类（`ingestion_runtime.py:748-762`，`super().__init__(failure.message)`），`upload_tools.py:116-122` 以 `message=str(exc)` 把 `--document-id 与材料稳定文档 ID 不一致；…` 投影给 LLM——模型面对的是 CLI flag 名而非 tool 字段 `document_id`。EMPTY 消息更甚：CLI/工具都在入口预拒空值，`--document-id 不能为空` 的唯一可达受众是 Service/Python API 调用方，对他们 `--document-id` 是不存在的入口形态。
- **为什么有问题**: AGENTS.md LLM-facing 文本约束要求投影给模型/调用方的文本自足、业务可读、不依赖 CLI 实现术语；错误语义的 owner（runtime closed message）把单一通道的入口措辞广播到所有通道。
- **直接证据**: `ingestion_runtime.py:748-762`；`upload_tools.py:116-122`（`message=str(exc)`）；`fins.py:198-200`（CLI 渲染 `exc.failure.message`）；`fins.py:96`（O08 CLI 空值文案由 CLI 自持，不受影响）。
- **影响**: LLM-facing 错误文本违反项目硬约束措辞要求；Service 调用方收到指向错误入口的指引；后续若 WeChat/Web 通道复用 runtime 消息会放大错位。
- **建议改法和验证点**: closed message 改通道中立措辞（`document_id 不能为空`、`document_id 与材料稳定文档 ID 不一致；请省略或填写系统生成的 ID`），或 runtime 只携带 typed reason、由各入口映射各自文案（CLI 的 O08 空值文案继续由 `_document_ids_from_arg` 持有，不动）。验证点：tool 失败 outcome 的 message 不含 `--` flag 形态；CLI mismatch 输出可行动。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
