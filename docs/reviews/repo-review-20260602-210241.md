### 1-[CRITICAL]-LLM Compaction Material Prompt Injection 风险

- **入口/函数:** `_candidate_from_final_answer()` → `llm_material_json()` → `json.dumps(request.llm_material_json())`
- **文件(行号):** `dayu/host/llm_compaction.py` L383-388; `dayu/host/compaction.py` L453-466; `dayu/host/compaction_evidence.py` L202
- **输入场景:** 工具执行结果包含对抗性文本（如 JSON 闭合括号 `"}, ignore previous...`）
- **实际分支:** `raw_result_text` 通过 `CanonicalJsonDumps` 序列化后直接进入 LLM prompt JSON 字段，无 sanitization
- **预期行为:** 注入 LLM 的工具输出应有 sanitization 或至少标记为 untrusted
- **实际行为:** 工具输出原文直接嵌入 compaction prompt 的 JSON 结构，对抗性内容可能操纵 compactor LLM
- **直接证据:** `llm_compaction.py` L383 直接 `json.dumps(request.llm_material_json(), ...)`; `compaction.py` L464 暴露 `raw_result_text`
- **影响:** 工具输出中的对抗性内容可能引导 compactor 产生错误或恶意的压缩结果（虚假 fact、错误 state patch）
- **建议改法和验证点:** 对注入 prompt 的工具输出做 JSON string escape；用 markdown code fence 包装并标记为 untrusted
- **修复风险（中）:** sanitization 不能破坏财报数据 LLM 理解
- **严重程度（严重）**

### 2-[CRITICAL]-Compaction Budget Token Estimation 中文场景严重偏低

- **入口/函数:** `_estimate_text_tokens()` / `_estimate_preserved_context_tokens()`
- **文件(行号):** `dayu/host/llm_compaction.py` L1387-1394; `dayu/host/context_budget.py` L35
- **输入场景:** 中文财报纸本，compact 后估算 token 数
- **实际分支:** `DEFAULT_ESTIMATOR_CHARS_PER_TOKEN = 3`，即 `ceil(len(text) / 3)`；中文每个字符 1.5-3 tokens，严重低估
- **预期行为:** 应对多语言文本有合理精度或保守估计
- **实际行为:** 3000 个中文字符估算为 1000 tokens，实际可能 6000-9000 tokens，误差最高 9x
- **直接证据:** `context_budget.py` L35 常量定义; `llm_compaction.py` L1387-1394 估算函数
- **影响:** compact 后 dispatch 可能因实际 token 远超估算而再次失败，浪费 LLM compactor 调用
- **建议改法和验证点:** 对 CJK 范围使用 `chars_per_token=1`，Latin 使用 `3`；增加 1.5x safety margin
- **修复风险（低）:** 纯数值调整
- **严重程度（严重）**

### 3-[HIGH]-工具重复治理 InMemoryAttemptDuplicateGovernance 永久阻塞

- **入口/函数:** `InMemoryAttemptDuplicateGovernance.decide_duplicate()`
- **文件(行号):** `dayu/host/tool_duplicate_governance.py` L383-428
- **输入场景:** 协程 A 获得 ALLOW 后崩溃，协程 B 在同样 key 上调用 `decide_duplicate`
- **实际分支:** B 进入 `while in_flight.state is OWNER_RUNNING: await condition.wait()` 永久等待，因为 A 崩溃后无人调用 `record_accepted/record_durable_missing`
- **预期行为:** 等待者应在有限时间内超时
- **实际行为:** 无超时机制。所有等待相同 duplicate_key 的并发工具调用永久挂起，导致整个 Attempt 卡住
- **直接证据:** L405-406 设置 in_flight 记录; L412-413 while 循环无超时; `record_accepted` 和 `record_durable_missing` 仅由原始所有者调用
- **影响:** Run 无法完成，worker 永久阻塞
- **建议改法和验证点:** 添加 `asyncio.wait_for` 超时；超时后检查状态仍为 `OWNER_RUNNING` 时提升为 `DURABLE_MISSING`
- **修复风险（中）:** 需要处理超时后原始协程仍然存活的 TOCTOU 场景
- **严重程度（高）**

### 6-[HIGH]-Drain loop 收到 RetryExhausted 时队列中剩余 dispatch 被丢弃
