## Accepted Findings Verification

### F01 — Dispatch wakeup gap

- **原始问题**: Plan 要求 Host callback adapter 直接调用 `DefaultHostResolveWaitService`，绕过 command.py 的 dispatch wakeup 逻辑，导致 callback-triggered resume 永远不执行。
- **Fix 声称**: CallbackWaitResolvePort 返回 `RunSnapshot` + `idempotent_replay`，保证 non-replay dispatch 唤醒一次，replay 不唤醒。
- **Plan 直接证据**:
  - 第 304 行: "Host adapter must not call `DefaultHostResolveWaitService` directly. It calls an injected `CallbackWaitResolvePort` implemented in the command layer. This port returns `RunSnapshot` plus `idempotent_replay`, converts internal rows before producing the adapter result, and guarantees dispatch wakeup for non-replay resolves that create dispatch."
  - 第 358 行: "Accepted callback that creates resume dispatch wakes dispatch exactly once."
  - 第 359 行: "Same callback replay returns `REPLAYED`, appends no new EventLog, and does not wake a second dispatch."
- **Code 交叉验证**: `command.py:769-770` 确认 dispatch wakeup 逻辑（`result.dispatch_record is not None and not result.idempotent_replay` → `wake_dispatch`）。Plan 将此逻辑移入 command-layer `CallbackWaitResolvePort` 实现，adapter 不再直接调用 service。
- **判定**: **已修复** ✅

### F02 — Digest formula

- **原始问题**: `payload_digest` 与 wait resolution digest 的关系不明确，`observed_at`/`completed_at` 是否影响 replay 冲突未说明。
- **Fix 声称**: digest 对齐 `wait_id + idempotency_key + outcome`；`observed_at`/`completed_at` 不影响 replay。
- **Plan 直接证据**:
  - 第 188 行: "This intentionally matches the existing wait resolution digest semantics: `wait_id + idempotency_key + outcome`. `observed_at` and `completed_at` are excluded and must not affect replay conflict."
  - 第 367 行: "Same callback replay with changed `observed_at` or `completed_at` still returns `REPLAYED` when outcome is unchanged."
- **Code 交叉验证**: `waiting.py:1132-1146` 确认 `_wait_resolution_digest` 仅使用 `{wait_id, idempotency_key, outcome}`。
- **判定**: **已修复** ✅

### F03 — Transport vs Host statuses separated

- **原始问题**: `TRANSPORT_REJECTED` 和 `MALFORMED_PAYLOAD` 混入 Host adapter status 枚举。
- **Fix 声称**: 从 Host adapter 移除，定义为 Service/Web transport mapper diagnostics。
- **Plan 直接证据**:
  - 第 127 行: "`TRANSPORT_REJECTED` and `MALFORMED_PAYLOAD` are not Host adapter statuses. They are Service/Web transport mapper diagnostics used before a Host envelope exists:"
  - 第 370 行: "Host adapter tests do not include HTTP method/content-type/path-body mismatch or malformed JSON shape; those belong to Service mapper tests."
- **Code 交叉验证**: `WaitCallbackAdapterStatus` 枚举（plan 第 108-117 行）不包含 transport 状态；Host/Slice 1 测试列表（第 355-370 行）明确排除 HTTP transport cases。
- **判定**: **已修复** ✅

### F04 — INVALID_STATE mapping

- **原始问题**: adapter 解析 `HostApiError.message` 做 secondary classification，fragile 且 TOCTOU 不安全。
- **Fix 声称**: 禁止解析 message，races 安全 collapse 为 `INVALID_WAIT_STATE`。
- **Plan 直接证据**:
  - 第 338 行: "Do not parse `HostApiError.message`. `INVALID_STATE` from the resolve port maps to `INVALID_WAIT_STATE` unless the adapter already made a stable pre-resolve classification such as `LATE_WAIT_CANCELLED`, `LATE_WAIT_LOST`, or `STALE_CALLBACK`. Concurrent races may safely collapse to `INVALID_WAIT_STATE`. A more precise raced late-state classification requires a future structured subcode/result and is not part of this WU."
  - 第 362-363 行: 测试覆盖 stable pre-resolve classification 和 concurrent race collapse。
- **Code 交叉验证**: `waiting.py:609-629` 确认多种 `INVALID_STATE` 抛出场景均使用非结构化 message。Plan 的 "不解析 message + safe collapse" 策略与代码事实一致。
- **判定**: **已修复** ✅

### F05 — All four outcome JSON shapes

- **原始问题**: 仅 `completed` 有 JSON 示例，`failed`/`cancelled`/`lost` 形状未定义。
- **Fix 声称**: 四种 outcome JSON 形状全部指定。
- **Plan 直接证据**:
  - 第 230-244 行: `completed` JSON 示例（含 `result` 对象）
  - 第 247-258 行: `failed` JSON 示例（含 `failure.error_code`/`message`/`meta`）
  - 第 261-271 行: `cancelled` JSON 示例（含 `cancelled.reason_code`/`message`）
  - 第 274-282 行: `lost` JSON 示例（含 `reason_code`/`message`/`provider_status_ref`）
  - 第 370 行: Slice 2 测试覆盖四种 outcome kind 解析
- **Code 交叉验证**: `api.py` 中 `ResolveWaitFailedOutcome`（需 `ToolResultFailure`）、`ResolveWaitCancelledOutcome`（需 `ToolCancelledOutcome`）、`ResolveWaitLostOutcome`（需 `reason_code`+`message`）与 plan JSON 形状一致。
- **判定**: **已修复** ✅

### F06 — Deadline/expires semantics

- **原始问题**: `expires_at` 始终为 `None`，stale check 语义不清晰。
- **Fix 声称**: 基于 current-code 语义明确 `deadline_at` vs `expires_at`，测试覆盖。
- **Plan 直接证据**:
  - 第 192 行: "Current code only populates `WaitRecordRow.deadline_at`; `expires_at` exists in schema but is currently reserved and written as `None` by the wait creation path. Adapter stale classification therefore depends on `deadline_at` today."
  - 第 194 行: "If both fields are absent, callback must not be rejected as stale."
  - 第 365 行: "Wait with `deadline_at=None` and `expires_at=None` is not rejected as stale."
- **Code 交叉验证**: `waiting.py:2008` 确认 `expires_at=None` 始终写入；`durable/state.py:430-431` 确认 schema 预留字段。
- **判定**: **已修复** ✅

### F07 — completed_at usage

- **原始问题**: `completed_at` 被收集但用途不透明，是否进入 EventLog 未说明。
- **Fix 声称**: `completed_at` 仅用于 stale check 和 digest 验证，不持久化，不改变 resolve payload schema。
- **Plan 直接证据**:
  - 第 190 行: "`completed_at` is transport/audit input only for callback validation and stale classification in this WU. It is not persisted by `resolve_wait`, not added to `ResolveWaitRequest` payload, and not included in wait resolution digest. `ResolveWaitRequest.observed_at` remains the Host-observed callback time used by the existing EventLog path."
- **Code 交叉验证**: `waiting.py:998` 确认 EventLog 使用 `request.observed_at`；`_wait_resolution_digest` 不含 `completed_at`。
- **判定**: **已修复** ✅

### F08 — Deterministic 401/403 mapping

- **原始问题**: auth 失败的 HTTP status mapping 未指定。
- **Fix 声称**: 确定性 401/403 mapping 基于 `WaitCallbackAuthRejected.reason_code`。
- **Plan 直接证据**:
  - 第 292 行: "`AUTH_FAILED` -> 401 when credential is missing, malformed, expired, or otherwise not authenticated; 403 when credential is authenticated but lacks permission for the wait/callback action. This mapping is deterministic and based on `WaitCallbackAuthRejected.reason_code`, not exception text."
- **判定**: **已修复** ✅

### F09 — RunRow/RunSnapshot conversion

- **原始问题**: adapter 调用 `DefaultHostResolveWaitService` 返回 `RunRow`，但 `WaitCallbackAdapterResult.run` 期望 `RunSnapshot`，转换未指定。
- **Fix 声称**: CallbackWaitResolvePort 负责转换。
- **Plan 直接证据**:
  - 第 304 行: "This port returns `RunSnapshot` plus `idempotent_replay`, converts internal rows before producing the adapter result"
  - 第 162 行: `run: RunSnapshot | None` in `WaitCallbackAdapterResult`
- **Code 交叉验证**: `command.py:783` 确认 `run_snapshot_from_row(result.run)` 转换模式。Plan 将此转换职责移入 `CallbackWaitResolvePort`。
- **判定**: **已修复** ✅
