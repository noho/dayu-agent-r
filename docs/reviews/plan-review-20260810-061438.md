## Findings

### 1-未修复-严重-prepared-rejected-callable-是胶水-seam

- **位置**: Amendment §5.2 "Rejected artifact 的锁外 prefetch"；§12 evidence 风险表 "prepared rejected callable可能退化为glue/compat seam"
- **问题类型**: 过度耦合 / 架构边界 / 兼容性 wrapper
- **当前写法**: Amendment 提出在 `sec_downloader.py` 提供一个 prepared materialization callable，该 callable 输入是 `tuple[PrefetchedDownloaderEvent, ...]` 与 prefetch request facts，输出签名匹配 `DownloadFilesStream` Protocol；要求 callable 重放 started/skipped/failed facts 并对 `file_prefetched` 使用 persistence owner 传入的 `StoreDownloadedFile` 与 batch materialize，同时校验 request identity exact equality。

- **反例/失败场景**:

  1. `DownloadFilesStream` Protocol（`sec_download_persistence.py:75-107`）的签名是 `(remote_files, overwrite, store_file, *, batch, existing_files, primary_document, cancellation_checker) -> AsyncIterator[DownloaderEvent]`。prepared callable 必须接受这些参数但不执行 HTTP——它本质上是一个 **adapter**，把 `PrefetchedDownloaderEvent` 元组翻译成 `DownloaderEvent` 流。

  2. 该 callable 需要校验 `remote_files`、`overwrite`、`existing_files`、`primary_document` 与预取 request exact equality。这个校验逻辑不属于 downloader（它产出的 prefetch events 已经携带了 identity 信息），也不属于 persistence（persistence 只应关心 materialization）。它创造了一个中间层，其唯一存在理由就是**让 persistence 的 `DownloadFilesStream` Protocol 不被修改**。

  3. 若未来 `DownloadFilesStream` Protocol 签名变化（例如新增参数），prepared callable 的 request-identity 校验必须同步更新——这是典型的 **shotgun surgery** 耦合模式。

  4. 该 callable 将 `file_prefetched.content` 传给 `StoreDownloadedFile` 的时机在 persistence 的 `download_files_stream(...)` 调用内部，这意味着 **materialization 仍然发生在 persistence 的 `begin_batch`/commit/rollback 区间内**（这正是锁内 I/O 的 storage 部分，是正确的），但 callable 本身成为了 prefetch domain 和 persistence domain 之间的 translation layer。

- **为什么有问题**: AGENTS.md 明确禁止"兼容性 wrapper / facade：方法体仅透传到真源模块，不增加有效语义"和"胶水 seam"。该 prepared callable 的语义是：
  - 把 prefetch events 翻译成 `DownloaderEvent`（投影）
  - 把 `file_prefetched.content` 传给外部 `StoreDownloadedFile`（延迟 materialization）
  - 校验 request identity（defense-in-depth）

  其中，"投影"和"延迟 materialization"**本身有独立语义**——不是纯粹的透传。但"匹配 `DownloadFilesStream` 签名"这一设计选择的动机是**避免修改 `sec_download_persistence.py`**，而非因为 `DownloadFilesStream` Protocol 是 prefetch→materialization 的自然契约。Prefetch result 的自然契约是一个 typed events 集合，不需要伪装成 streaming download API。

  正确的 owner boundary 应该是：
  - `sec_downloader.py` 产出 `PrefetchedDownloaderEvent` 流
  - `sec_download_persistence.py`（或 `SecPipeline`）消费 `PrefetchedDownloaderEvent` 流，在 batch 内 materialize
  - 中间不需要一个"签名匹配 `DownloadFilesStream` 但语义是 replay"的 adapter

- **直接证据**:
  - `sec_download_persistence.py:75-107`：`DownloadFilesStream` Protocol 的文档写的是"逐文件下载并在每次存储回调 invocation 显式传入 batch"——它是为"下载并存储"设计的，不是为"重放已下载内容"设计的
  - `sec_download_persistence.py:255-272`：`persist_rejected_filing_artifact` 调用 `download_files_stream(remote_files=..., overwrite=..., store_file=..., batch=..., ...)`——所有参数都是 HTTP download 语义
  - Amendment §5.2 自述："callable 的公开调用签名结构化满足现有 `DownloadFilesStream`"——承认这是为了满足现有 Protocol 而非表达自然契约
  - Amendment §12："prepared rejected callable可能退化为glue/compat seam"——amendment 自身已识别此风险

- **影响**: Implementation agent 将实现一个 translation layer，其存在理由是为避免修改一个 allowlist 文件。后续维护者需要理解为什么 rejected artifact 路径通过一个"看起来像 download stream 但实际不做下载"的 callable。这违反了 `DownloadFilesStream` Protocol 的语义契约（它的文档承诺"逐文件下载"），造成接口语义与实现行为不一致。

- **建议改法和验证点**:

  **推荐方案**：将 `sec_download_persistence.py` 加入 Slice 4 production allowlist。

  具体做法：
  1. 在 `sec_downloader.py` 只增加 `prefetch_files_stream`（storage-neutral typed prefetch contract），**不**增加 prepared callable
  2. 在 `sec_download_persistence.py`（或其调用方 `SecPipeline._persist_rejected_filing_artifact`）：
     - 先调用 `prefetch_files_stream` 完成锁外 HTTP
     - 再进入 `begin_batch`
     - 在 batch 内消费 `PrefetchedDownloaderEvent` 流：started/skipped/failed 投影为 `DownloaderEvent`；`file_prefetched` 通过 `StoreDownloadedFile` + 真实 batch materialize
  3. 删除或不再使用 prepared callable

  **备选方案**（若坚持不修改 `sec_download_persistence.py`）：
  - 必须证明 prepared callable 有独立有效语义而非 compat seam
  - 必须给出证据：为什么 `DownloadFilesStream` Protocol 是 prefetch→materialization 的自然接口而非"凑签名"
  - 必须说明：当 `DownloadFilesStream` Protocol 未来变化时，prepared callable 的变更属于 downloader owner 还是 persistence owner
  - 必须显式命名该 callable（如 `ReplayPrefetchedMaterializer`）并赋予独立 Protocol/contract，而非匿名"满足 `DownloadFilesStream`"

- **修复风险**: 中。修改 `sec_download_persistence.py` 需要调整其内部 `download_files_stream` 消费方式，但该文件当前约 550 行且只服务于 SEC rejected artifact 路径，改动范围可控。
- **严重程度**: **严重**。若 prepared callable 被接受为 compat seam，它违反了 AGENTS.md 的胶水 seam 禁令和 semantic ownership 原则，且为后续维护埋下接口语义不一致的隐患。Amendment §5.2 和 §12 自身已承认此风险；按 amendment §11 stop condition："rejected artifact 仍在持 writer lock 时访问 provider，或修复它需要无有效语义的 compat/glue seam"即应停止。

### 2-未修复-中-prefetch-typed-state-与-DownloaderEvent-语义重叠

- **位置**: Amendment §4.1 "新增 typed event"；`PrefetchedDownloaderEvent` 字段定义
- **问题类型**: 语义所有权 / 过度设计
- **当前写法**: 新增 `PrefetchedDownloaderEvent` dataclass，包含 `event_type`、`name`、`source_url`、`http_etag`、`http_last_modified`、`http_status`、`content`、`reason_code`、`reason_message`、`error`。`__post_init__` 封闭校验 transport facts。

- **反例/失败场景**:
  1. `PrefetchedDownloaderEvent` 与现有 `DownloaderEvent`（`sec_downloader.py:189-202`）共享 8 个字段中的 7 个名称和语义（name、source_url、http_etag、http_last_modified、http_status、reason_code、reason_message、error）。唯一差异是 `PrefetchedDownloaderEvent` 有 `content: bytes | None` 而 `DownloaderEvent` 有 `file_meta: FileObjectMeta | None`。
  2. 这两个类型承载的是**同一 transport event 在不同阶段的状态**——prefetch 阶段携带 bytes，materialization 阶段携带 FileObjectMeta。从 event sourcing 角度，它们是同一个 event 的两种投影。
  3. Amendment §4.1 说"禁止把 `DownloaderEvent.file_meta` 扩成同时承载 bytes"，理由是避免"optional god bag"——这个理由成立。但它没有讨论另一种可能：定义单一的 `SecTransportEvent` 类型，用 discriminated union 区分 prefetched/materialized 阶段，而非两个独立 dataclass。

- **为什么有问题**: 两个高度重叠的 dataclass 意味着：
  - `download_files_stream` 需要在内部做 `PrefetchedDownloaderEvent → DownloaderEvent` 投影（amendment §5.1 已描述此投影）
  - 投影逻辑中，`file_prefetched` → `file_downloaded` 需要从 `content` 构造 stream、调 `StoreDownloadedFile`、取 `FileObjectMeta`——这是 materialization 逻辑，不应是简单的字段映射
  - 但 `file_download_started`、`file_skipped`、`file_failed` 的投影只是字段复制
  - 这创造了两个类型之间的隐式映射表，未来新增 transport fact 需要同时更新两个类型和映射逻辑

  更好的设计可能是：保留 `DownloaderEvent` 作为公开类型，新增 `PrefetchedDownloaderEvent` 作为内部 intermediate type（annotated 为 `_PrefetchedDownloaderEvent` 表达私有性），并显式文档化映射关系。或者使用单一 `SecTransportEvent` + discriminated union。

  当前方案**技术上可行**，但未论证为什么两个独立 dataclass 优于 discriminated union 或 private intermediate type。这增加了维护者需要理解的类型数量。

- **直接证据**:
  - `sec_downloader.py:189-202`：`DownloaderEvent` 字段 = (event_type, name, source_url, http_etag, http_last_modified, http_status, file_meta, reason_code, reason_message, error)
  - Amendment §4.1：`PrefetchedDownloaderEvent` 字段 = (event_type, name, source_url, http_etag, http_last_modified, http_status, content, reason_code, reason_message, error)
  - 二者差异仅 `file_meta` ↔ `content`，其余 7 个字段完全相同

- **影响**: 中等。两个类型的维护成本、投影逻辑的正确性验证、未来 transport fact 的双重更新。不会导致功能失败。
- **建议改法和验证点**:
  1. 将 `PrefetchedDownloaderEvent` 标注为模块私有（`_` 前缀）或使用 `@internal` 标记，明确它只是 downloader 内部 intermediate，不暴露给 pipeline/workflow
  2. 在 `download_files_stream` 重构中显式文档化 `PrefetchedDownloaderEvent → DownloaderEvent` 的映射表（一个模块级 `_project_prefetched_to_downloader_event(...)` 函数）
  3. 或者考虑使用 discriminated union 统一两个阶段，减少重复字段定义
- **修复风险**: 低。纯类型设计调整，不影响 transport logic。
- **严重程度**: 中。不影响功能正确性，但增加了不必要的类型维护负担和概念重复。

### 3-未修复-中-prepared-callable-的-request-identity-校验逻辑归属不清

- **位置**: Amendment §5.2 "callable 的公开调用签名结构化满足现有 `DownloadFilesStream`，但调用时必须校验 `remote_files`、`overwrite`、`existing_files`、`primary_document` 与预取 request exact equality"
- **问题类型**: 语义所有权
- **当前写法**: prepared callable 在调用时做 request-identity 校验：比较传入参数与 prefetch 时的 request facts，不匹配时 fail closed。

- **反例/失败场景**:
  1. 这个校验本质上是一个 **defense-in-depth assertion**：它检查"persistence owner 传给 prepared callable 的参数是否与 prefetch 时的参数一致"。这个语义属于 **caller contract validation**——应该是 persistence/SecPipeline 的责任，而不是 downloader 的责任。
  2. 如果 request-identity 校验放在 prepared callable 内部，那么 downloader 模块需要理解"什么构成合法的 request identity"——这耦合了 downloader 与 pipeline/workflow 的调用契约。
  3. 如果 persistence 传入错误的 `existing_files`（例如空 `{}` 而非 Phase A 的 snapshot），prepared callable 会 fail closed——但这个错误的根因在 persistence，而非 downloader。由 downloader 来检测这个错误是 responsibility inversion。

- **为什么有问题**: Request-identity 校验的唯一目的是防止"Phase B materialization 使用了错误的 prefetch data"。这个校验的正确 owner 是 **调用 prepared callable 的代码**（`SecPipeline` 或 workflow），而非 prepared callable 本身。把校验放在 callable 内部意味着 downloader 需要知道它的调用方应该传什么参数——这是向上依赖。

- **直接证据**:
  - AGENTS.md semantic ownership："每个业务事实...都必须有唯一清晰 owner：负责产生、校验、持久化、投影和对外承诺该语义的层、模块、类型、状态机、schema 或 API"
  - Amendment §5.2 未指定 request-identity equality 的定义（是按 `RemoteFileDescriptor` 列表的 name/url 相等？还是 exact object equality？），也未指定 mismatch 时的错误类型和错误消息 owner
  - `SecPipeline._persist_rejected_filing_artifact`（L1648）当前直接把 `self._downloader.download_files_stream` 作为 `DownloadFilesStream` 传入——如果换成 prepared callable，`SecPipeline` 需要持有 prefetch 结果和 callable，且需要确保传给 callable 的参数正确。这个正确性责任在 `SecPipeline`

- **影响**: 中等。校验逻辑放错 owner 不会导致功能失败（fail closed 是安全的），但会造成职责混淆，后续维护者不清楚 request-identity 校验的正确性应由哪个模块的测试覆盖。
- **建议改法和验证点**:
  1. 如果保留 prepared callable，request-identity 校验应放在 `SecPipeline._persist_rejected_filing_artifact` 中（在调用 callable 之前 assert），而非 callable 内部
  2. 或者：callable 不接收 `remote_files`/`overwrite`/`existing_files`/`primary_document` 参数，只接收 `StoreDownloadedFile` + `batch` + `cancellation_checker`，从而根本不需要校验 request identity——callable 的输入只是"请将这些已确认的 prefetch events materialize"
  3. 如果坚持在 callable 内校验，必须定义明确的不变量（用什么相等性标准？），并提供独立的错误类型和错误消息
- **修复风险**: 低。
- **严重程度**: 中。

### 4-未修复-中-test-matrix-覆盖-but-not-provable

- **位置**: Amendment §7 "Test amendment" 测试矩阵；§8 "Workflow/race tests 与 call-graph/AST gate"
- **问题类型**: 测试缺口 / 可执行性问题
- **当前写法**: 测试矩阵包含 11 个 prefetch contract assertion cases 和 6 个 workflow/race 验收条件，以及 6 条 AST/static gate。

- **反例/失败场景**:

  1. **"cancel after fetch/before materialize"（§7 第 8 行）**：要求在 `prefetch_files_stream` 已产生 `file_prefetched` 但 `download_files_stream` 尚未调用 callback 之间命中 cancel。在确定性测试中没有 production timing hook 的情况下，无法精确控制取消发生的时机——除非 prefetch 和 materialization 之间有显式的 checkpoint（如 async barrier）。Amendment 未描述如何在 deterministic test 中实现这一点。

  2. **"Phase B staged classification barrier 必须先于首个真实 storage callback"（§8 第 2 条）**：要求在测试中证明 staging classification 发生在首个 callback 之前。这需要在 `begin_batch` 和首个 `store_file` 调用之间插入 observable side effect。但 `begin_batch` 和 `store_file` 的调用者是 workflow，observability 需要通过 spy/fake 实现——amendment 未指定 spy 接口。

  3. **"后 writer revision 变化后，旧 prefetch digest 永不进入 callback"（§8 第 3 条）**：这是 race condition 测试。需要在两个并发 writer 中精确控制时序：writer A prefetch → writer B commit → writer A begin_batch → writer A 检测 revision 变化。这需要 barrier/event 协调，amendment 提到了 barrier 但未给出具体的 barrier placement 策略。

  4. **"overwrite True 即使 latest COMPLETE 也不得转 skip"（§8 第 4 条）**：这个测试的正确性依赖 Phase A 的 `classify_source_integrity` 返回 COMPLETE，然后 Phase B 的 `classify_staged_source_integrity` 也返回 COMPLETE（identity 相同），最后 policy 按 overwrite=True 执行 apply 而非 skip。所有中间步骤都需要确定性的 fake/stub 返回值——amendment 未描述 fake 的最小接口。

- **为什么有问题**: 这些测试是**正确且必要的**，但 amendment 把它们列为"增加明确验收"而非"需要在实现前完成设计"。Implementation agent 在写测试时会发现：
  - cancel timing 无法在不引入 concurrency primitive 的情况下确定性地控制
  - Phase B barrier 需要 spy/mock 接口，但 amendment 未定义这些接口
  - race condition 测试的 barrier placement 是一个设计决策，不是实现细节

  这不是说这些测试不应该存在——而是说 amendment 应该**承认这些测试的实现需要额外的设计决策**（spy 接口、barrier placement、cancel timing strategy），并将这些决策作为 implementation 的前置条件或 open question。

- **直接证据**:
  - Amendment §7 测试矩阵第 8 行："cancel after fetch/before materialize" 要求 callback 零调用，但未指定如何在不使用 sleep/timing hook 的情况下实现
  - Base plan §9："新增 process/concurrency tests 必须使用 deterministic Event/barrier 和 bounded deadline，不使用 sleep 猜时序"——但 cancel timing 无法仅通过 Event/barrier 控制，因为 cancel 发生在 prefetch 完成和 materialization 开始之间的"间隙"，这个间隙的长度不可控
  - Amendment §8 barrier tests 提到了 barrier 但没有描述 barrier 的具体位置和 spy 接口

- **影响**: 中等。Implementation agent 在实现阶段需要自行设计 spy 接口和 barrier placement，增加了 plan→implementation 的信息损失。最坏情况下，某些 race condition 测试可能被标记为 flaky 或改用宽松断言。
- **建议改法和验证点**:
  1. 为 "cancel after fetch/before materialize" 明确策略：是在 `prefetch_files_stream` 返回后、`begin_batch` 前由测试主动取消？还是需要在 prefetch→materialize 的 pipeline 中插入显式 awaitable checkpoint？
  2. 为 Phase B 测试定义最小 spy 接口：`SpyStoreFile`（记录调用次数和参数）、`SpyBatchRepository`（记录 begin/commit/rollback 时序）
  3. 将 "同 target 双 overwrite last-writer" race test 的 barrier placement 作为 open design decision 记录下来，而非留给 implementation agent 自行决定
  4. 考虑将无法确定性测试的 race condition（如 cancel 恰好在 prefetch 和 materialize 之间）标记为 `defensive/unreachable` 或使用 code review + AST gate 代替运行时测试
- **修复风险**: 低。这只是测试设计层面，不影响 production contract。
- **严重程度**: 中。不会导致 product bug，但可能导致测试实现阶段的返工。

### 5-未修复-低-rejected-artifact-路径的-prepared-replay-provider-调用计数不变-验证不精确

- **位置**: Amendment §8 第 5 条："rejected artifact 路径先完成 typed prefetch，再进入 persistence batch；prepared replay 期间 provider 调用计数保持不变"
- **问题类型**: 测试缺口
- **当前写法**: 要求 test 验证 "prepared replay 期间 provider 调用计数保持不变"。

- **反例/失败场景**:
  1. 如果 prepared callable 正确实现（不调用 HTTP），provider 调用计数自然保持不变——这是一个**恒真断言**（tautological assertion）。真正应该验证的是：prepared callable 的内部实现路径不会意外触发 HTTP。
  2. 更好的验证方式是 AST gate（amendment §8 AST gate #2 已覆盖）："`_http_download`、`_http_download_if_modified` 及 provider client 调用只可从唯一 prefetch transport core 到达；`download_files_stream`、prepared replay、SEC Phase B 均不可直接调用"。AST gate 比运行时计数验证更强。
  3. "provider 调用计数不变"作为运行时测试需要在 `SecDownloader` 上挂载 spy——但这个 spy 的粒度（方法级？`_execute_sec_request` 级？`httpx` client 级？）amendment 未指定。

- **为什么有问题**: 运行时验证 "provider 调用计数不变" 不如 AST gate 强，且需要额外的 spy 设计。建议直接依赖 AST gate 作为主要证据，运行时测试只验证端到端行为（prefetch → materialize 产生正确结果）。

- **直接证据**: Amendment §8 AST gate #2 与运行时测试 #5 有重叠——AST 已经静态证明不可达，运行时计数是冗余的弱验证。

- **影响**: 低。不影响正确性，但增加了不必要的测试复杂度。
- **建议改法和验证点**: 删除 "prepared replay 期间 provider 调用计数保持不变" 的运行时验证要求，改为依赖 AST gate #2。运行时不验证 provider 调用计数，只验证端到端结果（rejected artifact 正确落盘）。
- **修复风险**: 极低。
- **严重程度**: 低。测试冗余，不构成功能风险。

### 6-未修复-低-repair-mode-304-禁令的-download_files_stream-实现细节未定

- **位置**: Amendment §6 第 6 条："repair mode 必须按 base plan 强制取得完整 replacement，不能让 304 复用损坏 physical file"
- **问题类型**: 实现细节缺失
- **当前写法**: 要求 repair mode 不能接受 304 skip。

- **反例/失败场景**:
  1. 在 `prefetch_files_stream` 中，304 的处理逻辑是：当 `overwrite=False` 且 conditional request 返回 304 时，产生 `file_skipped(not_modified)`。当 `overwrite=True` 时，跳过 conditional request，直接 `_http_download`。
  2. base plan 的 repair mode 要求：即使 `overwrite_existing=False`，repair target 也必须强制取得完整 replacement。这意味着 repair 路径需要传入 `overwrite=True` 给 `prefetch_files_stream`——但 `overwrite` 参数控制的是"是否跳过 conditional request"，repair 的逻辑是"需要完整 replacement"。
  3. 当前 `download_files_stream` 中 `overwrite` 参数直接控制是否做 HTTP conditional request（见 `sec_downloader.py:1534`：`if not overwrite:` 分支走 conditional；else 分支走无条件下载）。amendment §6 第 6 条隐含了一个新的语义：repair target 的 prefetch 必须等同于 `overwrite=True` 的 transport 行为（强制完整下载，不接受 304）。

- **为什么有问题**: Amendment 将 repair 的 "不接受 304" 作为 workflow 层面的要求，但没有明确这个语义如何在 `prefetch_files_stream` 的 API 中表达。如果 workflow 在 repair 场景下传 `overwrite=True` 给 prefetch，但这与 `overwrite_existing`（request-level 语义）混淆——`overwrite_existing` 控制的是"source 是否应被覆盖"，而 `overwrite` 在 downloader 层面控制的是"是否跳过 conditional HTTP"。这两个概念在 repair 场景下需要解耦。

- **直接证据**:
  - `sec_downloader.py:1534`：`if not overwrite:` 分支决定了 conditional vs unconditional HTTP
  - Base plan §5.6："repair mode 必须按 base plan 强制取得完整 replacement，不能让 304 复用损坏 physical file"
  - Amendment §6 第 6 条重复了这个要求，但没有说明 `prefetch_files_stream` 的 `overwrite` 参数如何映射到 repair semantics

- **影响**: 低。这个问题在 implementation 阶段可以解决（workflow 在 repair 场景下传 `overwrite=True` 给 prefetch，同时在 Phase B policy 中按 `overwrite_existing` 原始值决定 apply/skip）。但 amendment 应该说明这个映射关系，避免 implementation agent 自行解释。
- **建议改法和验证点**: 在 amendment 中增加一句说明："repair target 的 prefetch 强制使用无条件下载（`overwrite=True` 传入 `prefetch_files_stream`），独立于 request-level `overwrite_existing` 语义；后者仅在 Phase B policy 中影响 apply/skip 决策"
- **修复风险**: 极低。
- **严重程度**: 低。

## Conclusion

**FAIL**

核心原因：**Finding 1（prepared rejected callable 是胶水 seam）达到严重级别，且 amendment §5.2 和 §12 自身已预判此风险**。按 amendment §11 stop condition："rejected artifact 仍在持 writer lock 时访问 provider，或修复它需要无有效语义的 compat/glue seam"即应停止——该 stop condition 已命中。

**修订路径**：
1. 将 `sec_download_persistence.py` 加入 Slice 4 production allowlist（或明确裁决：不让 prepared callable 匹配 `DownloadFilesStream` Protocol，改为让 `SecPipeline._persist_rejected_filing_artifact` 直接消费 `PrefetchedDownloaderEvent` 流）
2. 删除 prepared callable
3. 重新评估 rejected artifact 路径的 prefetch→materialize 调用链，确保没有引入新的胶水 seam
4. 其他 findings（2-6）为中/低严重度，可以在修订后的 plan 中一并解决

**不变的部分**：
- `prefetch_files_stream` 的设计（§4）是正确的——storage-neutral typed prefetch contract 是锁外 I/O 的正确抽象
- `download_files_stream` 的单一 core 组合模式（§5.1）是正确的——现有 materializing API 应复用 prefetch core
- Phase A/B 状态机（§6）基于 base plan §5.6 的 identity-first 逻辑，amendment 正确地未改写它
- AST/static gate（§8）的定义是充分且可执行的
- Scope 最小性原则（§3）是正确的，只应在 rejected artifact 问题上做 targeted 调整
