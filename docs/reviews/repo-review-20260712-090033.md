### Finding 2-严重：`_get_creation_lock` 内存泄漏 — 创建锁永不回收

- **入口/函数**：`FinsReadRuntime._get_creation_lock()` / `FinsReadRuntime._get_or_create_processor()`
- **文件(行号)**：`read_runtime.py`（~2580-2600），`_creation_locks` 字典
- **输入场景**：对多个不同 `(ticker, document_id)` 组合依次调用搜索/读取工具
- **实际分支**：`_get_creation_lock` 只创建 `Lock` 并插入 `_creation_locks`，永不删除
- **预期行为**：锁在 Processor 构建完成后应可被清理，避免无限增长
- **实际行为**：`_creation_locks: dict[ProcessorCacheKey, Lock]` 随文档访问单调增长，在长生命周期进程中（如多公司多文档批量分析），该 dict 会无限膨胀
- **直接证据**：`_get_creation_lock` 中只有 `self._creation_locks[cache_key] = created`，没有任何删除路径；`_creation_locks` 暴露的唯一消费者就是此方法自身的 `get` 和 `set`
- **影响**：长运行 session 中随着访问文档数增加，内存持续增长，最终可能导致 OOM
- **建议改法**：在 `_get_or_create_processor` 的 `with lock:` 块结束后，从 `_creation_locks` 中删除该 `cache_key`；或使用 `WeakValueDictionary`
- **严重程度**：严重

### Finding 3-高：`_store_downloaded_document` 中 batch rollback 无法恢复物理状态 — 数据丢失风险

- **入口/函数**：`FinsIngestionRuntime._store_downloaded_document()`（含 blob 文件写入 + cross-repo 副作用）
- **文件(行号)**：`ingestion_runtime.py:3747-3813`
- **输入场景**：已存在的 source document 走入 overwrite 路径；`reset_source_document` 成功删除原有文件后，后续 `store_file` 循环中某个文件写入失败；或 source batch 的 `commit_batch` 失败触发 `rollback_batch`
- **实际分支**：(a) blob repository 的 `store_file()`（`ingestion_runtime.py:3835`）不参与 source repository 的 batch 事务，rollback 时 blob 文件残留为孤立数据。(b) processed repository 的 `mark_processed_reprocess_required`（`ingestion_runtime.py:3804-3805`）在 batch 内但操作不同仓储，source batch 回滚时 processed 标记未回滚
- **预期行为**：batch 内所有持久化副作用应全部成功或全部回滚
- **实际行为**：batch 失败回滚后，(a) blob repository 中残留孤立文件，source document 记录未被创建，blob 失去引用链；(b) processed 文档被标记为需重处理但触发重处理的 source 更新并未生效
- **直接证据**：`ingestion_runtime.py:3790 token = self.source_repository.begin_batch(ticker)`，`ingestion_runtime.py:3811 self.source_repository.rollback_batch(token)`。`_store_downloaded_file` 调用 `self.blob_repository.store_file()`（L3835），blob_repository 不在 batch 事务管辖范围内。`_mark_processed_reprocess_required_if_present`（L5481-L5483）直接写 processed_repository
- **影响**：(a) 下载失败/取消后残留孤立 blob 文件，长期积累导致存储膨胀；(b) processed 产物被无故标记重处理，引发不必要的预处理计算开销
- **建议改法**：方案一（根本）：在 blob_repository 协议中增加 batch/rollback 语义。方案二（最低侵入）：将 `_mark_processed_reprocess_required_if_present` 移到 `commit_batch` 成功之后；延迟 blob 写入到 commit 成功后或在 rollback 路径中清理已写入 blob
- **严重程度**：高

### Finding 7-中：Ingestion `cancel_observation` 在 drain 队列前做状态分支决策 — 竞态条件

- **入口/函数**：`FinsIngestionRuntime.cancel_observation()` - 在 `_drain_observation_queue` 之前检查 `record.status`
- **文件(行号)**：`ingestion_runtime.py:2428-2442`
- **输入场景**：producer 线程已完成并将 RESULT 事件放入 `record.queue`，但尚未被任何 poll 的 drain 消费。此时 Host 调用 `cancel_observation`
- **实际分支**：`cancel_observation` 在 L2432 检查 `record.status not in _TERMINAL_OBSERVATION_STATUSES`，此时 status 仍是 RUNNING，分支进入 if 体做 cancel 决策。之后 L2442 调用 `_observation_snapshot_locked`，内部 `_drain_observation_queue` 才会处理 RESULT 并覆盖状态
- **预期行为**：cancel 应基于最新状态做决策——如果 RESULT 已经在队列中等待消费，应先消费它再决定 cancel 分支
- **实际行为**：分支决策基于过时状态。对于 `submitted=False` 的 record，cancel 写入 `status=CANCELLED` 和 `result=_observation_cancelled_result`，随后 drain 可能再次覆盖为真正的 RESULT 状态。返回的 snapshot 状态不反映真实终态
- **直接证据**：L2428 进入 `with self._observation_lock` 后未调用 drain，直接在 L2432 检查 status
- **影响**：`cancel_observation` 返回的 snapshot 在并发场景下可能不准确。调用方 `FinsIngestionWaitPollAdapter.abandon_wait`（L176）依赖 `snapshot.status` 做分支决策，若拿到过时状态可能触发错误的 no-op/abandon 路径
- **建议改法**：在 `cancel_observation` 的 `if record.status not in _TERMINAL_OBSERVATION_STATUSES` 判断之前，先调用 `self._drain_observation_queue(record)` 消费已有事件
- **严重程度**：中

### Finding 8-中：Observation 路径缺少死 producer 检测机制

- **入口/函数**：`FinsIngestionRuntime._drain_observation_queue()` - 无超时/线程存活检测
- **文件(行号)**：`ingestion_runtime.py:2619-2653`
- **输入场景**：observation path 的 producer 线程因严重异常（如 segfault、`os._exit()`）意外终止，未执行 finally 块，`_DirectStreamProducerDone` 从未放入队列
- **实际分支**：`_drain_observation_queue` 用 `queue.get_nowait()` 非阻塞读取，队列空时立即 break。每次 poll 调用都因队列空而 break。observation record 的 status 永远停留在 RUNNING，不会变成终态
- **预期行为**：应检测到 producer 已死亡，将 observation 收口为 FAILED 或 LOST 终态
- **实际行为**：observation 永久 stuck 在 RUNNING。对比 direct stream path 的 `_direct_queue_get`（L4563）会检查 `thread.is_alive()`，observation path 无等效检测
- **直接证据**：L2619 `_drain_observation_queue` 只做非阻塞队列读取，无超时或线程存活逻辑。L2541 `_FinsObservedOperationRecord` 定义中没有 `thread` 字段。`activate_observation` L2494-L2497 创建线程但不保存引用
- **影响**：极端异常场景下 observation 永久不终结，Host poller 永远看到 RUNNING，需进程重启才能清理
- **建议改法**：在 `_FinsObservedOperationRecord` 中增加 producer 线程引用；`_drain_observation_queue` 在队列空时检测线程存活状态
- **严重程度**：中

### Finding 9-中：`ProcessorLRUCache` 无失效机制 — 文档重处理后 Processor 仍返回旧数据
