## 2. Findings

### 1-未修复-[低]-CLI `FinsUploadPrevalidationError` catch 硬编码 `upload_filing` 命令名，material UNSAFE/REPAIR_REQUIRED fail-closed 将被误标

- **位置**: plan §2（“UNSAFE 和有可信 meta 的 REPAIR_REQUIRED 由 validator 抛 `FinsUploadPrevalidationError`……CLI 仅复用 Fins 预校验和既有渲染”）；测试 5。
- **问题类型**: 契约缺失（展示层文案归属）/ 测试缺口。
- **当前写法**: plan 让 material validator 对 UNSAFE/可信 REPAIR_REQUIRED 抛 `FinsUploadPrevalidationError`，CLI 预检复用既有渲染；但既有 catch 写死 filing 命令名：`fins.py:204-207` — `_LOGGER.exception("upload_filing prevalidation operational failure")` 与 `render_cli_error(f"dayu-cli upload_filing: {exc.failure.message}")`。
- **反例/失败场景**: S1 落地后，真实 CLI `dayu-cli upload_material` 对一个 UNSAFE（或可信 REPAIR_REQUIRED）material 目标做 bootstrap 前预检 → validator 抛 `FinsUploadPrevalidationError` → `run_fins_direct_command` 的 catch（`fins.py:204`）渲染 **`dayu-cli upload_filing: <material 文案>`**——命令名误标，日志行同样误标。该路径在 S1 完成之时即可达（plan 测试 5 的真实 CLI 补跑若覆盖 UNSAFE 输入必现）。
- **为什么有问题**: goal 要求 CLI 显示可执行、不误导的修正方向；命令名错标会把 material 完整性拒绝误导到 filing 命令排障路径。错误本身仍是 typed（`exc.failure` 的 kind/code/message 正确），所以严重度限于展示层。
- **直接证据**: `fins.py:204-207`（硬编码文本）；plan §2 的 material `FinsUploadPrevalidationError` 投影路径；`run_fins_direct_command` 的 catch 链（`fins.py:184-222`）对该异常类型不按 `args.command_name` 分流。
- **影响**: 用户可见错误行命令名错误；真实 CLI 补跑若记录双流会固化误标。
- **建议改法和验证点**: plan 一句话钉死——material 预检接入时把该 catch 的命令名改为 `args.command_name` 派生（`fins.py` 已在白名单），并在测试 5/CLI hermetic 单测补一条 material UNSAFE/REPAIR_REQUIRED 预检拒绝的渲染断言（命令名为 `upload_material`、exit 码与文案来自同一 `exc.failure`）。
- **修复风险（低/中/高）**: 低——一行渲染修正 + 一条断言。
- **严重程度（低/中/高/严重）**: 低（展示层误标；failure 事实本身正确）。
- **残余风险**: 无。
