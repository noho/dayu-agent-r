### 4. process group terminate-grace-kill-reap-close

- **`_wait_for_terminal`** (`docling_process_converter.py:477-554`):
  - 轮询间隔: `0.05s`
  - cancel observed → `_interrupt_child(handle, use_kill=False, grace=2.0s)` → 若未 exit → `_interrupt_child(handle, use_kill=True, grace=1.0s)` → 若仍未 exit → `CLEANUP` error
  - kill 后 exited → `request_cancelled=True`; kill 后未 exited → `DoclingConversionError(CLEANUP)`
- **`_close_handle`** (`docling_process_converter.py:616-667`):
  - shielded cleanup: 循环重试 `handle.close()`，每次 catch `CancelledError` 保留首个 outer_cancellation identity
  - 普通 close 异常 → `_CloseOutcome(failure=..., outer_cancellation=...)` 返回
  - close 成功后返回 `_CloseOutcome(failure=None, outer_cancellation=outer_cancellation)`
- **`convert_to_json_bytes` 主流程** (`docling_process_converter.py:336-474`):
  - handle is not None 时必然调用 `_close_handle`
  - close 失败 → `primary_error = _cleanup_error(...)` (CLEANUP 优先级最高)
  - close 的 outer_cancellation 覆盖 primary_error
  - temp cleanup (`shutil.rmtree`) 在所有路径执行，失败 → `_cleanup_error`
  - 所有清理完成后才 raise primary_error 或返回 result
- **`InterruptibleProcessHandle.close()`** (`interruptible_process.py:410-445`):
  - 幂等（`_closed` flag）
  - `asyncio.shield(cleanup_task)` 防止外层取消中断
  - `_run_cleanup_attempt`: kill + join + queue close 独立推进，首个异常记录但不阻止后续 checkpoint
- **结论**: terminate-grace-kill-reap-close 链路正确；POSIX process group 覆盖由 runtime `interrupt_multiprocessing_process` 保证。

### 7. direct/durable first-committer publication boundary

- **`commit_prepared_upload_batch`** (`docling_upload_service.py:799-852`):
  - `batch_terminal_started = False` 初始
  - `publish_prepared_upload(...)` 返回后检查 `result.status == "cancelled"` 或 `_is_cancelled(cancellation)`: 命中 → `batch_terminal_started = True` → rollback → return cancelled

  - **finally**: `batch_terminal_started` 为 False → `_rollback_precommit_upload_batch`（恰好一次 rollback）
  - `_rollback_precommit_upload_batch` 在 rollback 失败时保留原异常链
- **ownership transfer 语义**: `batch_terminal_started = True` 设置后，不再读取 cancel，不再 rollback。与 plan §9.1 一致。
- **direct stream** (`ingestion_runtime.py:3393-3464`):
  - `_direct_upload_terminal_events(...)` 先纯构造 progress+RESULT（不入队）——S3 A2 fix
  - `claim_upload_summary(disposition)` 原子提交（同一 lock 内检查 consumer_aborted/existing terminal/cancel_requested）
  - claim 返回 None → 静默返回（已有终端或 consumer 已 abort）
  - claim 成功 → `_put_direct_queue(terminal_progress)` + `_put_direct_queue(terminal_result)` ——两者均不抛异常（`_put_direct_queue` 使用 `queue.put(timeout=0.05s)` 循环重试 + consumer_abort 检查，永不抛异常）
- **durable job** (`ingestion_runtime.py:3837-3925`):
  - `summary.terminal_disposition()` 读取唯一 disposition
  - `CANCELLED` → `save_cancelled_if_active(...)`（已有终端时原样返回）

  - save 返回后 → `_upload_terminal_disposition_from_job_record(saved)` 读取 winner

  - `_save_failed_from_exception` 在 exception handler 中读取已保存终态并拒绝覆盖
- **cancelled 不投影 completed**: direct path `_direct_upload_terminal_events` (`ingestion_runtime.py:5429-5430`): `if disposition is not FinsUploadTerminalDisposition.CANCELLED` 时才有 progress；durable path `_run_upload_job` (`ingestion_runtime.py:3909-3910`): `if saved_disposition is not FinsUploadTerminalDisposition.CANCELLED` 时才投影 progress。
- **结论**: first-committer boundary 干净，publication commit ownership transfer 唯一，cancelled summary 不产生 completed。符合同意的 plan §9-10。

### 9. 异常与 race

- **`_DirectStreamCancellationState`**: 所有状态读写均在 `threading.Lock` 内。`is_cancelled`/`cancel_reason`/`requested_at` 都返回同一 locked snapshot。
- **`_RuntimeJobCancellationChecker`**: 首次观察取消后，在 lock 内冻结 `_cancel_reason`/`_requested_at`，后续调用返回冻结值——稳定，不重复查询 job store。
- **`JobStore.save_accepted_upload_terminal_if_active`**: `file_lock` 内 atomic read-check-write，`record.status in _TERMINAL_STATUSES` → return existing，first-committer 安全。
- **`ProcessDoclingConverter`**: 无跨调用可变状态；每次 `convert_to_json_bytes` 创建独立的 `InterruptibleProcessHandle`、temp tree、input/output files。shared instance 没有 operation mutable state。
- **`_close_handle` while 循环**: S1 裁决已正确拒绝"无上界循环"finding——循环只在 CancelledError 时重入，普通异常立即返回。close 使用 shielded task。
- **`_store_upload_assets` per-file cancel check**: 处于同一 batch 内，cancel 返回后由 `commit_prepared_upload_batch` 统一 rollback。batch 级事务保证一致性。
- **`_canonical_cancellation` 类型守卫** (`cn_download_filing_workflow.py:889-908`): 在 converter 边界前严格校验 `isinstance(cancel_checker, CancellationToken)`，拒绝仅 callable 的旧 checker。download workflow 的普通 checkpoint 仍使用 `cancel_checker()` callable 接口。符合 plan §11.1。
- **结论**: race 和异常处理正确；没有发现状态撕裂、双终态或静默丢事件窗口。
