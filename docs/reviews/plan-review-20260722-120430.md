## PRR-001 — Host close 在 execution owner quiesce 前释放 mutex

### 判定：已修复

**Fix requirement recap**（总控裁决原文）：
Host close 专用顺序必须改为：关闭 public/new-work gate → stop wait poller → durable actor drain → 等待全部 attachment mutation/pre-start work lease 收口但继续持有 native mutex → 在 mutex 仍持有时完成 scheduler lifecycle close → 最后释放 native mutex/关闭 attachment record → 其余 owner close。单独 attachment close 仍保持 existing stable Attempt 继续、无需关闭 scheduler 的原语义。

**Plan 修改位置（fix-codex 第二轮修订）**：

| 位置 | 修改内容 |
| --- | --- |
| §1.3 success signal 第 5 条 | Host close 在 mutex 持有时完成 scheduler lifecycle close，release 后 fresh RW 在同一次 target recovery 看到旧 owner `STOPPED` |
| §2.1 direct evidence 表 `open_host.py` 行 | 更新为"Host-close 专用 registry release 必须后移到完整 scheduler lifecycle close 之后" |
| §2.1 direct evidence 表 `dispatch.py::HostDispatchScheduler.close` 行 | 明确"成功完成必须成为 Host unlock barrier；mandatory cleanup/STOPPED 未完成时不得把 scheduler 或 attachment 宣称安全关闭，必须保留 mutex/record 并允许重试" |
| §4 semantic owners 表 Host execution owner quiescence 行 | owner contract 冻结："mutex 仍持有时停止 background/promotion、传播 worker lifecycle cancel、关闭 task/handle/lane 并提交 `STOPPING -> STOPPED`；成功结果授权 registry release"，并明确"cleanup 失败不得 release" |
| §5.4 状态迁移 Host close 步序 | 冻结为 7 步闭环：gate → poller stop → actor drain → mutation/pre-start drain（继续持 mutex）→ scheduler lifecycle close（promotion/background stop、token/on_cancel、worker/task/handle/lane、STOPPING→STOPPED）→ release mutex/record → 其余 owner |
| §5.4 cleanup 异常路径 | "任一 mandatory cleanup 或 durable STOPPED 收口异常时，Host close 必须继续尝试当前阶段可安全执行的清理，保留首个错误并允许重复 close 从未完成阶段重试；在 barrier 未完成期间 health gate 与 attachment 保持 CLOSING、native mutex/record 保持持有，不得执行 registry release 或后续 owner 关闭，不得记录 close_done/调用 mark_closed()，也不得把 scheduler 的 _close_cleanup_done 标真" |
| §6 affected files | `open_host.py` 行描述更新为"Host-close 专用 scheduler-before-unlock 顺序" |
| Slice 2 exact changes 第 8 条 | "调整 Host close 专用顺序：actor/pre-start 收口后继续持 mutex，完整完成 scheduler promotion/background/active worker/task/lane 与 host instance STOPPING -> STOPPED lifecycle close，最后才 release mutex/attachment record" |
| Slice 2 tests Host close barrier | "Host close 使用确定性双 opener barrier 证明专用顺序：A 进入 close 并完成 actor/pre-start drain、但 scheduler lifecycle close 尚未完成时，B 对同 Session 的 fresh attach 只能得到 RO；scheduler lifecycle barrier 内必须先让 active worker cancellation token 和 LocalWorkerHandle.on_cancel(...) 调用可观察，再取消/await worker/task、关闭 handle/lane 并 durable 标记 old owner STOPPED。barrier 完成后 A 才 release；B 关闭原 RO 并 fresh attach，在这一次 target recovery 中必须读取 old owner STOPPED、推进 recoverable 旧 Attempt 到 LOST/Run 到 RECOVERING 并创建新 Attempt/dispatch，不调用第二次 attach、不等待 periodic reconcile" |
| Slice 2 tests cleanup 异常 | "scheduler mandatory cleanup 或 STOPPED 写入注入异常时，close 返回错误但 Host health/attachment 保持 CLOSING、mutex 仍 busy、第二 opener 仍只能 RO，close_done/mark_closed/_close_cleanup_done 均不可宣称成功，后续 owner 尚未关闭；重复 close 补完 quiescence 与 STOPPED 后才 release 并继续其余 owner。更新当前'普通 cleanup 异常即 _close_cleanup_done=True'的偶然测试，不保留该行为。best-effort on_cancel hook 抛错不阻断 token 与其余 mandatory cleanup，但必须证明 hook 已在 unlock 前被调用" |
| §10 invariants 第 3 条 close 顺序 | 冻结为"单 attachment release 顺序永远是 new-work gate→本 attachment actor-bound mutation drain→pre-start work lease drain→native close，且不关闭 scheduler/existing stable Attempt；Host close 专用顺序严格为 public/new-work gate→wait poller stop→actor 全局 drain→全部 attachment mutation/pre-start drain 但保持 mutex→scheduler lifecycle close（background/promotion stop、token/hook 传播、active worker/task/handle/lane 清理、host instance STOPPING -> STOPPED）→native close/attachment record 删除→其余 owner" |
| §10 invariants scheduler cleanup 异常 | "scheduler lifecycle close 的 mandatory cleanup 与 durable STOPPED 未完成时，attachment 保持 CLOSING 且 mutex/record 不释放；close 可重试，cleanup 异常不得通过 _close_cleanup_done、best-effort 日志或继续关闭下游 owner 伪装成旧 execution owner 已安全 quiesce" |
| §14 self-check | 新增"Host-close scheduler-before-unlock barrier、pre-unlock token/hook、same-attach target recovery 读取 old owner STOPPED 与 cleanup 异常不误 release" |

**直接代码证据核验**：

1. **当前 close 顺序**（`open_host.py::_close_owned_resources` 行 1419-1544）：
   - 顺序为 health gate → wait poller → actor drain → `scheduler.close()` → terminal coordinator → delivery hub → projection → actor handle → executor → scheduler_store → `mark_closed()`
   - **当前没有 attachment registry/mutex 层**（这是 WU-CTX-04 要新增的），因此当前不存在"先 release mutex 再 scheduler close"的问题——但这正是 plan 要正确建立的边界

2. **当前 `HostDispatchScheduler.close()`**（`dispatch.py` 行 2747-2797）：
   - 入口 `_best_effort_mark_host_instance_stopping` → 停止 heartbeat/drain/promotion/watchdog → `active_registry.cancel_all(...)` → cancel/await active tasks → close worker handles/lane → `_best_effort_mark_host_instance_stopped`
   - **关键缺陷**（行 2790-2792）：cleanup 异常时 `self._close_cleanup_done = True` 后重新抛出——当前行为在异常后把 scheduler 标记为"cleanup 完成"并继续下游 Host close
   - Plan 已精确指认此缺陷并要求修复（§5.4 cleanup 异常路径、Slice 2 tests cleanup 异常、§10 invariants）

3. **orphan classifier**（`recovery_process.py::classify_orphan_candidate` 行 242-249）：
   - `row.status is HostInstanceStatus.STOPPED` → 直接返回 `PositiveOrphanProof(reason=_ORPHAN_REASON_OWNER_STOPPED)`——无需 process probe
   - `row.status not in (RUNNING, STOPPING)` → 返回 inconclusive
   - 这直接证明：fresh RW 必须看到旧 owner `STOPPED` 才能安全推进 recovery；若 scheduler close 在 mutex release 之后完成，fresh RW 会在旧 owner 仍 RUNNING/STOPPING 时正确跳过 recovery

4. **设计真源 §27.1**（`design.md` 行 3941）：
   - "Host opener 正常 close 若在 terminal 到达前停止本地 worker，只能传播 lifecycle cancel 与关闭本地 runtime，不能写用户 cancel facts；重启并 fresh READ_WRITE attach 目标 Session 后，由 owner STOPPED lifecycle proof 直接推进 recovery"
   - 这直接确认 plan 的 scheduler-before-unlock 顺序是设计真源要求

5. **llm_compaction.py timeout 证据**（`llm_compaction.py` 行 338-347）：
   - `_run_agent_request` 执行 `asyncio.wait_for(run_agent_and_wait(request), timeout=timeout_seconds)` 并在 `TimeoutError` 后传播 cancellation token
   - 总控已判定 `DS-RRN-01` evidence-invalid：compactor proposal 确有 `RunnerSpec.default_timeout_seconds` 包裹
   - Plan §5.4 的 drain 有界性论证成立；保留"若发现其它 pre-start provider 绕过既有 timeout 则阻塞"的实施守卫

**未覆盖项**：

- Plan 要求 Host close barrier 测试中"在 scheduler lifecycle close 尚未完成时 B 只能得到 RO"——这需要一个可观察的同步点（在步骤④ drain 完成与步骤⑤ scheduler close 之间）。Plan 描述了断言但未指定实现该同步点的具体机制（如 asyncio.Event / 内部 hook）。这不影响 correctness——实现 agent 可以设计——但需要在 Slice 2 review 时确认测试确实证明了 barrier 语义。
- `_close_cleanup_done` 的行为修改虽然精确定位到行 2790-2792，但 plan 未说明 scheduler.close() 在 cleanup 异常后应如何"保留首个错误并允许重复 close 从未完成阶段重试"——当前方法幂等性基于 `_closed and _close_cleanup_done` 的早退。实施 agent 需要设计正确的重试语义。

**PRR-001 结论：已修复。** Plan 在 §1.3、§2.1、§4、§5.4、§6、Slice 2 exact changes/tests、§10、§14 七处一致冻结了 Host-close scheduler-before-unlock 顺序、cleanup 异常处理、token/hook 传播和 STOPPED 收口。直接代码证据（`open_host.py` 当前 close 顺序、`dispatch.py` `_close_cleanup_done` 缺陷、`recovery_process.py` STOPPED → positive orphan、设计真源 §27.1）均支持 fix requirement。
