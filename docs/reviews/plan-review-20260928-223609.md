### A1. `Path.resolve(strict=False)` + `Path.stat()` 能按 goal 分类目标类型 —— 成立（实验证据）

在 `$TMPDIR` 隔离目录用 Python 3.11.15（与 `requires-python >=3.11` 一致）对 plan 第 24 行设计逐类实测：

| 输入目标 | resolve(strict=False) 结果 | stat 分类 | plan 覆盖 |
| --- | --- | --- | --- |
| 普通文件 | 原路径 | `S_ISREG` → 用法错误 | ✅ 且测试计划点名 |
| 指向文件的 symlink | 解析到目标文件 | `S_ISREG` → 用法错误 | ✅ plan 明确归入非法最终目标 |
| 指向目录的 symlink | 解析到目标目录（身份变为目标路径） | `S_ISDIR` → 放行 | ✅ 符合 goal“不把正常目录 symlink 当非法文件” |
| 尚不存在路径 | 原路径 | `FileNotFoundError` → 放行 | ✅ 保留现有装配规则 |
| 悬空 symlink（目标缺失） | 解析到目标字面路径 | `FileNotFoundError` → 按“尚不存在”放行 | 与当前 resolve 行为一致（见 Open Questions Q1） |
| 父路径为文件（`file/sub`） | 返回拼接路径 | `NotADirectoryError`(errno 20)，非 FileNotFoundError | plan 非目标已声明“不承诺解决父路径非目录” |
| symlink 环 | resolve 自身抛 `RuntimeError: Symlink loop` | —— | plan 明确保持 `RuntimeError` 操作异常传播，与现状一致 |
| 含空格/Unicode 目录 | 正常解析 | `S_ISDIR` → 放行 | ✅ goal 正常语义保持 |

结论：plan 选 `Path.stat()` + `stat.S_ISDIR` 而非 `Path.is_dir()` 是正确决策——`is_dir()` 内部吞掉 OSError 会把权限/ENOTDIR 故障误分类为“非目录”用法错误，plan 的分类边界（仅 `FileNotFoundError` 视为不存在，其余 `OSError`/`RuntimeError` 操作异常传播）与 goal“不承诺解决权限/父路径非目录/竞争”一致。`run_fins_direct_command` 的 `except Exception`（fins.py:224 附近）与 `run_session_command` 的 `except Exception`（session.py:165）都能接住操作异常并投影 exit 1，不会裸 traceback。

### 1-未修复-中-fins `_BASE_OPTION` 被误判为 resolver 专用，删除指令将波及生成脚本 argv 构造

- **位置**: plan《唯一 owner 与具体设计》item 3：“删除私有 `_resolve_workspace_root` 和它专用的 `_BASE_OPTION`”；连带 S1 允许文件 `dayu/cli/commands/fins.py`。
- **问题类型**: 不可直接实施（基于错误代码事实的指令）/ 其它（root cause 与证据不同源）。
- **当前写法**: plan 声称 `_BASE_OPTION` 是 `_resolve_workspace_root` “专用”的常量，并要求一并删除。
- **反例/失败场景**: 实施 Agent 按 plan 字面删除 `_BASE_OPTION` 后，`_upload_batch_command_argv`（fins.py:406）与 `_upload_batch_regeneration_argv`（fins.py:473）两处 NameError/编译失败；实施者被迫即席决定——直接内联 `"--base"` 字面量（违反 AGENTS.md 禁止魔法字符串）、或自行改常量归属——在 plan review 之外引入未裁决的设计决定；若改坏 argv token，`upload_filings_from` 生成的用户脚本参数契约（`python -m dayu.cli upload_* --base ...`）被破坏，`tests/cli/test_upload_filings_from_command.py` 多处 `"--base"` 断言会失败，返工定位成本落在实施 gate。
- **为什么有问题**: `_BASE_OPTION` 在 fins.py 共 3 个使用点：resolver 空文本报错 1 处（fins.py:1105），生成脚本 argv 构造 2 处（fins.py:406、473）。plan 的“专用”判断与代码事实直接冲突，属于用间接印象替代代码事实；对照 plan 对 `agent_entrypoint.BASE_OPTION_NAME` 的同款判断（确实 resolver 专用、准确）可知该结论未经逐点核对。

- **影响**: 实施 Agent 跑偏 / 生成错误代码 / 生成脚本 argv 契约破坏 / plan 外即席设计。
- **建议改法和验证点**: 修正 plan 文本：只删 `_resolve_workspace_root`；`_BASE_OPTION` 保留给脚本 argv 构造（它是 CLI argv token，归属与 `arg_parsing` 的 `--base` 契约同源），或明确改由共享常量 owner 提供并在两处复用；新模块内 `--base` 报错字段名常量由 `workspace_root.py` 自持。验证点：`_BASE_OPTION` 的 3 个使用点逐点有归属；`tests/cli/test_upload_filings_from_command.py` 全绿；fins.py 无魔法字符串新增。
- **修复风险（低/中/高）**: 低（改一句 plan 文本 + 实现期保持常量）。
