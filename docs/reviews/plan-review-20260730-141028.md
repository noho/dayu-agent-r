## Findings

### 01-未修复-高-EOF/reset confirmation 退出码契约与现有测试直接冲突

- **位置**：§6.4 Init interaction state machine，`RESET_CONFIRM` 转换；oracle `init.interactive-validation-and-exit`
- **问题类型**：契约缺失 / 状态机漏洞
- **当前写法**：plan state machine 写 `RESET_CONFIRM -- Enter/No --> FAILURE(1)`，将 Enter 与 EOF 合并为同一个 `FAILURE(1)` 出口
- **反例/失败场景**：现有测试 `test_reset_eof_and_interrupt_have_zero_mutation`（`tests/cli/test_init_command.py:838`）明确断言 EOF → `EXIT_SUCCESS`(0)；`test_reset_default_no_has_zero_bootstrap_or_managed_mutation`（line 814）断言 Enter/空字符串 → `EXIT_SUCCESS`(0)。plan 的 state machine 与这两个测试直接矛盾
- **为什么有问题**：oracle 明确区分两种语义——"reset 确认时直接 Enter 选择默认 No，workspace 不变并退出 0" 与 "Ctrl+D 是 EOF 而不是默认 No，退出 1"。plan 将两者合并为 `FAILURE(1)`，丢失了 oracle 要求的区分。implementation agent 无法判断应改写测试还是保留旧行为
- **直接证据**：
  - oracle predicate `init.interactive-validation-and-exit`：`"reset 确认时直接 Enter 选择默认 No，workspace 不变并退出 0；Ctrl+D 是 EOF 而不是默认 No，退出 1"`
  - `init.py:720-721`：`EOFError` 被捕获，`answer = _DEFAULT_CONFIRM`（`"n"`），EOF 与 Enter 行为相同
  - `test_init_command.py:850-853`：`assert cli_main.main(...) == EXIT_SUCCESS`
- **影响**：implementation agent 要么错误地保留 EOF=0（违反 oracle），要么改写测试但没有 plan 指导如何区分 Enter 与 EOF（`_confirm` 当前不区分两者）
- **建议改法和验证点**：
  1. state machine 应明确区分：`Enter/No --> CANCELLED_SUCCESS(0)`，`EOF --> FAILURE(1)`
  2. plan 应指定 `_confirm` 的修改方式：EOF 不再被捕获为默认值，而是传播为 `CliInitOperationError` 或专用 `EOFSignal`
  3. 明确列出需要修改的测试：`test_reset_eof_and_interrupt_have_zero_mutation` 的 EOF 断言改为 `EXIT_FAILURE`
  4. 验证：reset Enter 仍 exit 0，reset EOF 改为 exit 1，SIGINT 仍 exit 130
- **修复风险（低/中/高）**：中——需要修改 `_confirm` 的 EOF 处理逻辑并更新测试，但改动范围清晰
- **严重程度（低/中/高/严重）**：高——直接违反 oracle 冻结契约，implementation agent 无法自行决定

### 02-未修复-中-PRESERVE 补齐 root config 文件的语义边界不清晰

- **位置**：§6.5 Workspace mode / repair state machine，PRESERVE 行；§9 S4 exact changes 1
- **问题类型**：契约缺失
- **当前写法**：plan 写"PRESERVE 补齐五个 `config_file_names()` 与 prompts"（S4 change 1），§6.5 写"PRESERVE 先逐字节复制用户 config，再只补缺失的 `config_file_names()` 与 package prompt ordinary files"
- **反例/失败场景**：当前 PRESERVE 实现（`init_workspace.py:816-832`）使用 `shutil.copytree` 复制整个 config 目录到 staging，然后只调用 `_copy_missing_prompt_files` 补 prompt 文件。它不单独处理 5 个 root config 文件。如果 plan 意图是"只补缺失的 root config 文件"，需要新增逻辑逐个检查 `config_file_names()` 是否存在；如果意图是"覆盖"，则违反 PRESERVE "保留用户已有文件" 的 oracle 语义
- **为什么有问题**：oracle `init.preserve` 说"补齐当前 package managed manifest 中缺失的普通配置和 prompt 文件"——"补齐"暗示只补缺失，不覆盖已有。但 plan 的措辞"PRESERVE 先逐字节复制用户 config，再只补缺失的"在当前实现中已由 `shutil.copytree` 完成 config 目录复制，问题是 `copytree` 之后是否需要额外逐文件检查 root config 的缺失。当前 `_copy_missing_prompt_files` 只处理 prompt 目录，不处理 config 根目录下的 JSON 文件
- **直接证据**：
  - `init_workspace.py:816-832`：PRESERVE 模式先 `shutil.copytree(workspace_config_dir, staged_config_root, symlinks=True)`，再调用 `_copy_missing_prompt_files`
  - `init_workspace.py:857-872`：`_copy_package_config_defaults`（FIRST/OVERWRITE/RESET 使用）逐个复制 `config_file_names()` 的 5 个文件
  - 当前 PRESERVE 没有调用 `_copy_package_config_defaults`
- **影响**：如果用户的 config 目录缺少某个 root config JSON（如 `models.json`），PRESERVE 不会补齐它，导致后续 `ConfigLoader.load` 失败。plan 的意图正确但当前实现缺口未被明确描述
- **建议改法和验证点**：
  1. S4 exact changes 应明确：PRESERVE 在 `copytree` 后，逐个检查 `config_file_names()` 是否存在于 staging 目录，缺失的从 package 复制
  2. 已存在的 root config 文件零改写
  3. 测试应覆盖：config 目录存在但缺少单个 root config JSON 的 PRESERVE 场景
- **修复风险（低/中/高）**：低——逻辑清晰，只是明确补充缺失文件的步骤
- **严重程度（低/中/高/严重）**：中——可能导致 PRESERVE 无法修复部分损坏的 workspace

### 03-未修复-中-package default 迁移的测试影响未充分识别

- **位置**：§6.3 Config/schema decision，§9 S3，§14.2 Implementation risks 2
- **问题类型**：测试缺口
- **当前写法**：plan 承认"package execution profile baseline 改为 Mimo 可能暴露依赖旧 DeepSeek baseline 的偶然测试"（§14.2.2），但没有列出具体受影响的测试
- **反例/失败场景**：当前 4 个 execution profiles 的 `run_baseline.model_id` 和 `compactor_baseline.model_id` 都是 `deepseek-v4-flash`。改为 `mimo-v2.5-pro-plan` 后，以下测试可能需要更新：
  - `test_host_assembly.py` 中引用 `deepseek-v4-flash` 的断言
  - `test_config_loader.py` 中验证 execution profile 默认值的测试
  - `test_init_smoke.py` 中的 `_validate_published_config` 虽然用 Ollama 模型（不受影响），但可能有隐式依赖
- **为什么有问题**：plan 将此标记为 risk 但没有提供 mitigation 的具体步骤。implementation agent 可能遗漏某些测试更新，导致测试失败但不知道是预期的还是意外的
- **直接证据**：
  - `execution_profiles.json`：所有 4 profiles 的 `run_baseline.model_id` 和 `compactor_baseline.model_id` 都是 `"deepseek-v4-flash"`
  - `conversation_compaction.json`：`default_model_id` 是 `"deepseek-v4-flash"`
  - plan §6.3：改为 `"mimo-v2.5-pro-plan"`
- **影响**：implementation agent 在 S3 可能遇到测试失败，不确定是需要更新测试还是实现有误
- **建议改法和验证点**：
  1. S3 应明确列出需要更新的测试文件和断言类型
  2. 验证：`grep -rn 'deepseek-v4-flash' tests/` 找出所有引用，逐一判断是否需要迁移
  3. 迁移后的测试必须断言 owner 级 contract（新 model id），不能保留旧值兼容
- **修复风险（低/中/高）**：低——grep 即可定位，逐一更新
- **严重程度（低/中/高/严重）**：中——不阻塞实现但可能导致 implementation agent 在 S3 卡住

### 04-未修复-低-Service primary_default_selection 的必要性说明可更充分

- **位置**：§6.2 Model-family contract，Service selection 顺序
- **问题类型**：过度设计（边界）
- **当前写法**：plan 定义了三个 selection：`primary_default_selection`（无 override）、`ordinary_selection`（有 override）、`compactor_selection`（无 override），并比较 primary_default 与 compactor 的 family identity
- **反例/失败场景**：如果 workspace config 正确（init 投影后所有 scene 同 family），primary_default_selection 与 compactor_selection 的 family identity 必然相同。只有用户手动编辑 workspace config 造成 drift 时，这个校验才有价值。这是否属于"当前需求"还是"防御性设计"？
- **为什么有问题**：架构硬约束要求"不做过度设计，以最小化满足需求为标准"。如果 init 正确投影了所有 scene，且 package defaults 同源，那么 primary_default 与 compactor 的 family mismatch 只能来自用户手动编辑——这是 accepted oracle 未明确覆盖的场景
- **直接证据**：
  - `host_assembly.py:606-615`：当前 compactor selection 只用 execution profile baseline，不校验 family
  - oracle 没有要求"运行时校验 compactor 与主 scene 的 family 一致性"
  - plan §6.2 step 4："比较 `primary_default_selection.model` 与 `compactor_selection.model` 的 family identity"
- **影响**：新增的 primary_default_selection 调用增加了 Service assembly 的复杂度。如果这是必要的防御性校验，应明确说明触发场景；如果只是"以防万一"，可能违反过度设计约束
- **建议改法和验证点**：
  1. plan 应明确：这个校验是为了 catch 用户手动编辑 workspace config 导致的 family drift
  2. 或者：如果 init 保证了同源，且 package defaults 同源，运行时校验可以 defer 到后续 work unit
  3. 如果保留，测试应覆盖 intentionally mismatched compactor manifest 的 fail closed 场景（plan S3 tests 已列出）
- **修复风险（低/中/高）**：低——保留或删除都清晰
- **严重程度（低/中/高/严重）**：低——不影响正确性，只影响设计决策

### 05-未修复-低-PERSIST_CONFIRM 与 RESET_CONFIRM 的 Enter 语义差异需要显式说明

- **位置**：§6.4 Init interaction state machine
- **问题类型**：契约缺失
- **当前写法**：state machine 中 `PERSIST_CONFIRM -- Enter/No --> FAILURE(1)` 与 `RESET_CONFIRM -- Enter/No --> CANCELLED_SUCCESS(0)` 使用相同的 `Enter/No` 标记但出口不同
- **反例/失败场景**：implementation agent 可能困惑为什么同一个 `Enter/No` 在两处产生不同的退出码
- **为什么有问题**：PERSIST_CONFIRM 的 Enter=No+exit(1) 是安全设计（拒绝持久化 secret 则 init 失败），RESET_CONFIRM 的 Enter=No+exit(0) 是取消语义（取消 reset 保持现状）。两者语义不同但标记相同，容易混淆
- **直接证据**：
  - oracle `init.secret-handling`："拒绝或 EOF 时 workspace 不发生部分发布"
  - oracle `init.interactive-validation-and-exit`："reset 确认时直接 Enter 选择默认 No，workspace 不变并退出 0"
  - plan §6.4 state machine 两处 `Enter/No` 标记
- **影响**：implementation agent 可能错误地让 PERSIST_CONFIRM 的 Enter 也 exit 0，或让 RESET_CONFIRM 的 Enter 也 exit 1
- **建议改法和验证点**：
  1. state machine 应使用不同标记区分两者：RESET_CONFIRM 用 `Enter=No → CANCELLED(0)`，PERSIST_CONFIRM 用 `Enter=No → FAILURE(1)`
  2. 添加行内注释说明安全设计意图
- **修复风险（低/中/高）**：低——只需明确标记
- **严重程度（低/中/高/严重）**：低——已有 oracle 支持，但 plan 表述可更清晰

## Final plan review conclusion

**pass-with-risks**

Plan 整体架构清晰、语义 owner 划分合理、slice 依赖顺序正确、不过度设计。但存在一个高严重度问题（Finding 01）：EOF/reset confirmation 退出码契约与 oracle 和现有测试直接冲突，plan 的 state machine 将 Enter 与 EOF 合并为同一个 `FAILURE(1)` 出口，丢失了 oracle 要求的区分。implementation agent 无法自行决定如何处理这个冲突。

建议 controller 裁决 Finding 01 后即可进入 implementation。其余 findings 为中/低严重度，可在 implementation 过程中按建议改法处理。
