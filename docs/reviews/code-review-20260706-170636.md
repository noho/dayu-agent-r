### Analysis

以下是对 review 重点的逐项 evidence-based 验证：

#### 1. idle `dayu>` 下 Ctrl+C 行为对齐验证

**代码走读** (`dayu/cli/commands/interactive.py:504-517`):

```python
idle_interrupt_exit_pending = False          # L504: 函数局部状态
try:
    while True:
        try:
            user_prompt = await effective_composer.read(INTERACTIVE_INPUT_PROMPT)
        except EOFError:
            idle_interrupt_exit_pending = False  # L510: EOF 重置
            return EXIT_SUCCESS
        except KeyboardInterrupt:
            if idle_interrupt_exit_pending:      # L513: 第二次 → 退出
                return EXIT_KEYBOARD_INTERRUPT
            idle_interrupt_exit_pending = True   # L515: 第一次 → 标记
            continue                             # L516: 重新 read → prompt 重绘
        idle_interrupt_exit_pending = False      # L517: 正常输入重置
```

**行为矩阵验证**：

| 场景 | 预期行为 | 实际行为 | 对齐 |
|---|---|---|---|
| 第一次 Ctrl+C（空 prompt） | 重绘 prompt，不退出 | `idle_interrupt_exit_pending=True`，`continue` → 下次 `read` 重绘 | ✓ |
| 连续第二次 Ctrl+C | 退出，exit code 130 | `idle_interrupt_exit_pending` 已为 True → `return EXIT_KEYBOARD_INTERRUPT` | ✓ |
| 正常输入后 Ctrl+C | 按第一次处理 | L517 重置 `idle_interrupt_exit_pending=False`，下次 Ctrl+C 走"第一次"分支 | ✓ |
| prompt redisplay alone | 不重置 pending 状态 | `continue` 跳过 L517，pending 保持 True | ✓ |
| EOF（Ctrl+D） | 退出，exit code 0 | L510-511 重置并返回 `EXIT_SUCCESS` | ✓ |

**对齐 accepted plan** (`docs/host/wu-cli-smoke-01-dayu-cli-core-usability-plan.md:121-123`):

- plan: "First idle Ctrl+C at an empty prompt must clear/cancel the current input attempt, record an exit-pending idle interrupt, redisplay a clean prompt, and continue the REPL without exiting." → 实现匹配
- plan: "Second consecutive idle Ctrl+C at an empty prompt must exit locally with the existing keyboard interrupt exit code." → 实现匹配
- plan: "Prompt redisplay caused by the first idle Ctrl+C does not reset the exit-pending state." → 实现匹配（`continue` 跳过 L517）
- plan: "The exit-pending idle interrupt state must reset when the user performs non-interrupt input activity, including submitting a prompt, EOF handling" → 实现匹配（L510 EOF 重置，L517 正常输入重置）

**prompt-toolkit composer 边界验证** (`dayu/cli/composer.py:116-124`):

`_clear_or_interrupt` key binding 在非空 draft 中清空 buffer（不抛异常），空 draft 中 `event.app.exit(exception=KeyboardInterrupt)`。因此 `_run_interactive_repl` 只会在空 prompt 时收到 `KeyboardInterrupt`，非空 draft 的 Ctrl+C 由 prompt-toolkit 内部消化。实现只处理空 prompt 中断，与 composer 协议一致。

#### 3. running-state cancellation 路径验证

`_run_interactive_repl` 的运行态取消路径（`_submit_interactive_turn_handling_sigint`）完全未改动：

- `sigint_monitor_factory()` 创建 `CliSigintMonitor`（`dayu/cli/agent_entrypoint.py:31`），安装 asyncio SIGINT handler。
- 第一次 SIGINT → `cancel_entrypoint_run_and_wait(...)` 走 Host public cancel path。
- 第二次 SIGINT → 本地返回 `None` → `_run_interactive_repl` 返回 `EXIT_KEYBOARD_INTERRUPT`。
- idle Ctrl+C 的 `KeyboardInterrupt` 在 `effective_composer.read()` 处被 catch，不会逃逸到运行态 `sigint_monitor` 或 `submit_task`。

**结论**：running-state cancellation 仍走现有 Host public cancel path，未被 idle Ctrl+C 逻辑干扰。

## Residual Risk

- **blank line 与 pending 状态交互**：用户按 Ctrl+C 后连续输入多条空白行再按 Ctrl+C 仍会退出。这符合 plan 的 "prompt redisplay alone does not reset" 设计意图，且空白行在 REPL 中无业务语义。若未来产品要求空白行也重置 pending，需在 L517 前或 `stripped_prompt == ""` 分支中增加重置。当前不构成 defect。
- **raw typing 不可观察**：`_run_interactive_repl` 无法观察用户在 prompt-toolkit 中的 raw typing（未提交的字符输入），只能在 `read` 返回或抛异常时获得信号。这是当前 `InteractiveComposer` 协议的已知边界，plan 已明确记录为 "boundary of the current composer protocol rather than a Host/Service risk"。不构成 defect。
- **real provider running-state Ctrl+C**：本 slice 的测试使用 fake Host 和 scripted composer。real provider `dayu-cli interactive` 运行态 Ctrl+C 的手工验证仍在 WU-CLI-SMOKE-01 final closeout 前完成，不阻塞 slice review。
