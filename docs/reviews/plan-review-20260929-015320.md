## Findings

### 1-未修复-[中]-plan §23 的 auto→create/update 机制描述与代码事实相反，workflow 入口 action 值域缺口未裁定，§46"合法 auto"façade 测试承诺不可按字面实施
- **位置**: 直接调用链与 owner 裁定 §23（"合规 `auto` 带文件在 `resolve_upload_action` 中仅解析为 create/update，不会解析为 delete"）；契约 §28（auto 属"四个允许动作"）、§32（"不得改 `resolve_upload_action`"）；测试 §42（owner 矩阵含"大小写/空白 auto"）、§46（"合法 create/update/auto 与无文件 delete 维持旧文件事实与摘要"）；停止条件 §24/§46（"合规 raw 触达 Docling mismatch 即停"）。
- **问题类型**: 不可直接实施 / 契约缺失（计划含被代码证伪的机制声明 + 未收敛的值域边界）
- **当前写法**: plan 把分层写成 `raw action/files -> 共享 material usage owner -> FinsUploadMaterialFiles -> resolve_upload_action -> Docling 不变量`，并声称合规 auto 经 `resolve_upload_action` 解析为 create/update；owner 按 §28 把 `auto/create/update` 归为非 delete 类（auto+空 files→`MISSING_FILES`，auto+files→放行）；§42 owner 矩阵显式包含大小写/空白 auto；§46 承诺独立 façade 上"合法…auto…维持旧文件事实与摘要"。
- **反例/失败场景**: 独立 façade 调用 `SecPipeline.upload_material(action="auto", files=[existing.pdf])`（或 `"AUTO"`/`" auto "`）：共享 owner 判合规放行 → `from_upsert_paths` 成功 → `resolve_upload_action("auto", meta)`（sec_upload_workflow.py:500 / cn_pipeline.py:1116 传 raw action）→ `_normalize_optional_upload_action("auto")` 因 `UPLOAD_ACTIONS = {"create","update","delete"}`（docling_upload_service.py:77）不含 auto 而抛 plain `ValueError("不支持的 action: auto")`（:2006-2023）→ 该抛出位于 workflow `try` 内（sec:489 / cn:1105）→ `fins_upload_failure_from_exception` 无 ValueError/FinsUploadUsageError 分类分支（upload_failure.py:280-286）→ **unexpected_runtime**——正是 goal 要消灭的错误类别，且发生在一个完全合法的请求上。auto→None 的归一化只存在于 runtime handoff（service_runtime.py:273-289）与 filing validator（ingestion_runtime.py:1496 `None if requested_action == _UPLOAD_ACTION_AUTO else requested_action`）；material workflow 缺这一层，既有测试从未以 literal "auto" 覆盖 workflow（test_sec_pipeline_upload_material_stream.py 仅 "create"/None）。
- **为什么有问题**: (1) §23 是 F2 修复（总控"所有权关系修正"）的证据句，被代码直接证伪，"Docling mismatch 不可达"的论证链以错误机制表述给出——mismatch 确不可达，但合规请求仍可能在 resolve 处退化为 unexpected_runtime，plan §69 要求的"合规请求不触发 Docling mismatch"证明按字面能过、按 goal 精神（"用户输入被迟报为 unexpected_runtime"不应存在）有漏；(2) §46 的"合法…auto…"façade 测试按字面（literal auto）不可实施：实施者要么改 workflow 归一化（§32 只禁改 `resolve_upload_action`，未禁改 workflow，但这属于计划未授权的 façade 行为变更，goal §12 的"既有语义保持一致"未授权），要么把测试悄悄换成 None 掩盖缺口——两种自裁都会在后续 gate 被判跑偏或削弱断言；(3) §28 owner 接纳 auto/大小写变体而 workflow 值域是 `None|create|update|delete`，同一 raw 输入跨层值域不一致，恰是 CLAUDE.md 语义所有权要求在 owner 边界定案的问题；(4) §24/§46 的停止条件只覆盖 Docling mismatch，不覆盖 resolve 处的同类退化，实施者无 stop 信号。附带同源问题：未知 action（如 `"del"`）经 owner 放行后同样在 resolve 处退化为 unexpected_runtime，§28"未知 action 仍交现有各入口 action validator/`resolve_upload_action`"在 workflow 入口的落地就是这种退化投影，与 §44 对 CLI/runtime"不得退化为 unexpected_runtime"的承诺范围存在缝隙。
- **直接证据**: docling_upload_service.py:77（`UPLOAD_ACTIONS` 无 auto）、2006-2023（auto→ValueError）、1892-1914（`resolve_upload_action` 仅 None→create/update 或原样返回）；sec_upload_workflow.py:500 与 cn_pipeline.py:1116（raw action 直传 resolve，在 try 内）；service_runtime.py:273-289（auto→None 仅 runtime handoff）；ingestion_runtime.py:1496（filing validator 的 auto→None 先例）；upload_failure.py:280-286（ValueError 兜底 unexpected_runtime）；plan §23/§28/§32/§42/§46/§69 原文；test_sec_pipeline_upload_material_stream.py（action 取值仅 "create"/None，grep `"auto"` 零命中）。
- **影响**: 实施 Agent 跑偏（无授权改 workflow 语义）或测试固化掩盖缺口；F2 修复的证据层失真，双路 review 若放行等于为错误机制背书；auto 字面量请求在非 CLI 入口持续 unexpected_runtime，goal 动机类问题残留而 stop 条件探测不到。
- **建议改法和验证点**: plan 在契约节收敛 workflow 入口 action 值域并改写 §23 机制句，二选一写死：(a) 推荐——在两个 workflow 入口按 ingestion_runtime.py:1496 先例把 auto 语义（`auto`/大小写/空白变体、None、空串）归一为 None 后再 resolve（属 §40 允许文件内的显式子项，作为本 slice 一并写入 §46 测试与 stop 条件），机制句改为"auto 语义在 workflow 边界归一为 None，由 `resolve_upload_action` 依 previous_meta 解析为 create/update"；或 (b) 明确独立 façade 值域为 `None|create|update|delete`，literal auto 保持现状失败、登记 residual 与 tracking owner，§46 的 auto 用例改为 None/auto 语义并显式断言 literal auto 的现状行为。无论哪种，验证点：owner 通过的每个合法组合在 façade 不产生 in-try plain ValueError；§42 的大小写/空白 auto 用例在选定值域内有明确期望；未知 action 的 workflow 入口期望写明（现状退化或 typed 拒绝，不得留给实现巧合）。
