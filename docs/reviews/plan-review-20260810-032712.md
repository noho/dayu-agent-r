## 3. 逐项核验

### F01 — async generator 异常传播机制 → RESOLVED

**原问题**: amendment 未指定 collector/adapter 是否 catch 异常，导致 provenance 修复可能无效。

**修订内容**:

1. §3.1 新增明确的异常传播链路图：`run_cn_download_stream_impl async generator -> CnPipeline.download_stream async-for（无 catch） -> collect_cn_download_result_from_events async-for（无 catch） -> CnDownloadAdapter.download（无 catch/重分类） -> Fins runtime producer catch -> _download_public_failure_from_exception`
2. §3.1 point 4 明确："`CnPipeline.download_stream` 和 `collect_cn_download_result_from_events` 明确不新增 catch/转换；它们只让异常越过 generator/collector 边界。"
3. §3.1 owner decision 明确四组 operation-terminal `except Exception` 的处理方式：除 `CnDownloadCancelledError` 进入 cancelled 语义外，`FinsDownloadProviderError`、`OSError`、`ValueError`、`RuntimeError` 及其它 `Exception` 都原样抛出。
4. §6.3 明确："`CnPipeline.download_stream` 和 `collect_cn_download_result_from_events` 保持 no-catch pass-through layers。`CnDownloadAdapter.download` 也不 catch/重建这些异常。"
5. §8.2 新增 rebuild path 的传播测试："Rebuild provider/storage/execution failures each propagate through generator -> pipeline stream -> collector -> adapter; the exact object/cause is not replaced by a failed result."

**核验**: 传播链路的每一层都被显式指定为 no-catch。Python async generator 异常在 `async for` 中自然传播——如果 generator raise，`async for` 会把异常抛给调用者。collector 的 `async for` 同理。adapter 也不 catch。runtime producer 的 catch（已存在于 `ingestion_runtime.py`）是唯一的 catch 点，它调用 `_download_public_failure_from_exception` 做正确映射。

**直接代码证据验证**: `CnPipeline.download_stream` 和 `collect_cn_download_result_from_events` 确实没有 try/except（需在实现时验证，但 amendment 的规格足够让实现 agent 完成）。

**判定**: **RESOLVED。** 异常传播链路的每一层都被显式指定，无歧义。

### F03 — downloader retry-loop 重构 → RESOLVED

**原问题**: 重试循环 catch 块混合 httpx/JSON/ValueError，不能只在 raise 时做 granular mapping。

**修订内容**: §6.2 新增完整的 from-zero retry-loop refactor 规格：

1. "Validate method inputs and provider/API preconditions before entering the retry loop. Those `ValueError` instances remain API misuse and are never converted to provider failure."
2. "Inside the loop, perform only the HTTP request plus `raise_for_status`. Catch `httpx` transport/status exceptions, classify them, log only operation/attempt/category, and retry only when the classification says retryable."
3. "For JSON methods, parse `response.json()` after a successful request in a separate parser boundary. `json.JSONDecodeError` or response-decoding `ValueError` becomes immediate `PROTOCOL/non-retryable`; it is not retried as transport."
4. "Validate stock-list/title-search/provider schema after parsing. Provider-shape violations and HKEX `HkexnewsProviderProtocolError` become `PROTOCOL/non-retryable`."
5. "Validate PDF size/magic after successful byte download. Failure is `PROTOCOL/non-retryable`."

闭合分类表（8 行）明确每个 captured failure 的 category、retryable 和 ordering/boundary。

§8.1 transport matrix 新增：
- "The timeout case is a hierarchy-ordering test: a real `httpx.TimeoutException` must be `TIMEOUT`, never `CONNECTION`."
- "Malformed JSON/schema/PDF performs no transport retry after a successful HTTP response and becomes `PROTOCOL/non-retryable`."
- "A pre-request invalid ticker/provider/API argument raises the original `ValueError` and makes zero HTTP calls."

§4 review adjudication table 明确："MiMo F03 + DS F04/F08 Accepted: CN/HK retry loops are rebuilt, parser/API misuse are separated, and exception inheritance order is binding."

**核验**: 五步重构规格把 HTTP request、response parsing、schema validation 分离为独立边界。JSONDecodeError 在 parser boundary 被捕获为 PROTOCOL non-retryable（不在 retry 循环中）。pre-loop ValueError 保持为 ValueError。httpx 异常在 retry 循环中按分类处理。继承顺序（Timeout before NetworkError）被显式测试。

**判定**: **RESOLVED。** 重构规格足够详细，可直接实施。
