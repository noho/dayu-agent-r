### 001-未修复-中-compactor prompt 包含 accepted evidence envelopes 但没有 bounded token guard

- **入口/函数**: `_user_prompt()` → `_accepted_evidence_envelope_lines()`
- **文件(行号)**: dayu/host/llm_compaction.py:320-329（_user_prompt），llm_compaction.py:327-330（_accepted_evidence_envelope_lines）
- **输入场景**: 一个 Session 内累积了大量 accepted evidence envelopes（例如 100+ 个），每个 envelope 都携带 full result_preview（最多 1200 字符），在 proactive compaction 时传入 LLM。
- **实际分支**: `_user_prompt()` 无条件调用 `_accepted_evidence_envelope_lines()`，展开所有 envelope 的 tool_name、tool_call_id、query digests、result_preview、source_refs、locator_refs 为 prompt 行。
- **预期行为**: 每个 envelope 展开后的文本总量应有上限，防止单次 LLM 调用 prompt 过大。evidence candidates 有 MAX_EVIDENCE_BACKED_FACT_CANDIDATES=64 和 claim_text 2000 字符上限，但 envelope 展开到 prompt 没有自己的 token guard。
- **实际行为**: 存在理论可能：在充分积累 accepted evidence 的 Session 中，envelope 展开文本加上结构化 JSON schema prompt 会超过模型 context window，导致 compaction 失败，进而 block Run dispatch。
- **直接证据**: `_accepted_evidence_envelope_lines()` (llm_compaction.py:327-330) 遍历所有 envelope 并无条件展开每个 envelope 的 14+ 行文本；`_user_prompt()` (llm_compaction.py:320) 无条件将展开结果插入 prompt。
- **影响**: 退化为 compaction 不可用，后续 dispatch 走 go-straight path 或失败。
- **建议改法和验证点**: 在收集 envelope 时按 envelope 数量或展开后文本总量设上限（例如最多 128 个 envelope 或 16K 字符 envelope text），超出部分记录 diagnostic 并截断。验证点：构造 200+ envelope 的 Session 并发起 proactive compaction。
- **修复风险（低）**: 只影响边界 Session 的 LLM prompt 长度治理。
- **严重程度（中）**:

### 002-未修复-低-durable snapshot 读取时对旧 `verified_fact` item kind 的 fail-closed 可能中断旧 Session 恢复

- **入口/函数**: `_validate_snapshot_item_kinds()`
- **文件(行号)**: dayu/host/durable/memory.py:936-939（调用点），durable/memory.py:945-967（校验逻辑）
- **输入场景**: 升级前已有 durable memory snapshots 包含 `verified_fact` item kind 的旧 Session。升级后 Host 尝试读取这些 snapshot。
- **实际分支**: `_validate_snapshot_item_kinds()` 查询 `host_memory_items` 表中属于该 snapshot 的 item rows，遇到 `item_kind == 'verified_fact'` 时抛出 `HostDurableError("old durable memory item kind verified_fact is not supported")`。
- **预期行为**: 按 PR body 声明的 "fail closed on old schema keys"，旧 snapshot 应被拒绝读取，走 `snapshot_damaged` 或 `snapshot_missing` 的 rebuild path。
- **实际行为**: 确实 fail-closed 并抛 `HostDurableError`，但调用方 `_snapshot_row_from_host_row` 把这个异常直接向上传播，最终在 `run_input.py` 的 `load_memory_snapshot()` 中以 `snapshot_damaged` diagnostic 处理。这条路径在 test 中已有覆盖。
- **直接证据**: durable/memory.py:946-948 对旧 kind 抛出 HostDurableError；run_input.py 的 `_load_memory_from_provider()` 捕获该异常并产生 snapshot_damaged diagnostic。
- **影响**: 旧 Session 在升级后的首次 dispatch 会走 snapshot_damaged → rebuild 路径，功能可恢复但首次 dispatch 有额外延迟。符合设计意图，无数据丢失。
- **建议改法和验证点**: 在升级说明中明确记录这是故意 breaking change，旧 snapshot 读取会失败并触发自动重建。建议在 memory diagnostic 中增加 "schema_migration_repair" reason 以区别于真正的 snapshot corruption。
- **修复风险（低）**: 只是 diagnostic 增强，不改变行为。
- **严重程度（低）**:

### 003-未修复-低-compact artifact schema version 升级到 2 但没有 version migration 逻辑

- **入口/函数**: compact artifact 读写 (`_COMPACT_ARTIFACT_SCHEMA_VERSION`)
- **文件(行号)**: dayu/host/compact_artifact.py:123
- **输入场景**: 升级前已有 v1 版本的 compact artifact（`preserved_fact_refs` 包含旧 `tool_fact_refs` / `verified_fact_refs` 字段）。升级后 Host 尝试读取旧 artifact。
- **实际分支**: 常量 `_COMPACT_ARTIFACT_SCHEMA_VERSION = 2`，但没有 version-gated 解析逻辑。artifact 读取时不检查 schema version。
- **预期行为**: artifact 读取时应检查 version 字段，v1 artifact 应被拒绝或 at least 产生 diagnostic。
- **实际行为**: compact artifact JSON 写入格式的是新字段名（`accepted_evidence_refs`、`evidence_backed_fact_refs`），但读取路径没有明确的 version discriminator。如果某个旧 artifact 被回读，其 JSON 中 `preserved_fact_refs` 下的旧字段会被 `_reject_old_preserved_fact_ref_fields()` 拒绝（在 context_events validation 中），但这个校验只在 `validate_context_compacted_payload()` 走 CONTEXT_COMPACTED 路径时触发，compact artifact 作为独立文件读取时不走这条校验。
- **直接证据**: compact_artifact.py:123 常量升级到 2；compact_artifact.py:198-210 写入新字段；没有 version-gated 读取分支。
- **影响**: 如果旧 artifact 被回读（例如在 compact artifact store replay 或 diagnostic dump 场景），JSON 字段名不匹配可能导致解析错误或静默返回空值。

## Open Questions

1. **compaction_budget.py 删除后的 token 估算常数**: 删除的 `compaction_budget.py` 中包含 `estimate_compacted_context_budget()` 和 `estimate_text_tokens()` 两个 public 函数。新代码将 budget 估算移到 `llm_compaction.py` 内部并以 `_budget_after_compact()` 等价替代。需确认没有外部模块直接 import 了 `dayu.host.compaction_budget` 的 public 函数。——已通过 Grep 确认无外部引用。
2. **`_TRUNCATED_PREVIEW_SUFFIX = "...[truncated]"` 的 UTF-8 安全性**: 截断发生在 Python 字符串切片层面（code point），如果恰好切在多字节 Unicode 字符的 code point 边界不会产生问题（Python 按 code point 切片），但组合字符序列（emoji ZWJ、combining diacritics）可能被截断。reviewer 认为风险极低，因为 tool outcomes 的 canonical JSON 通常不包含此类字符。
3. **result_preview 对 FAILED/CANCELLED outcome 的语义合适性**: `_accepted_tool_outcome_preview()` 对所有非 REUSE outcome 都生成 canonical JSON 预览。对 FAILED/CANCELLED outcome，预览包含错误信息，可能对 LLM compactor 有价值（帮助理解为何某工具调用失败了），但也有可能引入噪音。当前设计让 LLM 自己判断，暂无不妥。
