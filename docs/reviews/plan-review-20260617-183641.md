# Plan Review: WU-CLI-INTERACTIVE-RESUME-01

- **Reviewed target**: `docs/reviews/wu-cli-interactive-resume-01-plan-codex-20260617.md`
- **Work unit**: WU-CLI-INTERACTIVE-RESUME-01
- **Review 日期**: 2026-06-17
- **Review 结论**: **PASS-WITH-RISKS**

## Reviewed Target and Scope

本 review 针对 CLI `prompt` / `interactive` 已有 Session 启动语义对齐的 implementation plan。Review 范围包括 plan 的 state boundaries、implementation slices、API boundary risks、cursor store design、outbox watermark/seen-id handling、active_run handling、queued-only cases、prompt side effects、test coverage、docs 和 AGENTS constraints 遵守情况。

## Assumptions Tested

1. **Host public API 足以支撑 startup reconnect**：`SessionSnapshot.active_run_id`、`read_outbox_terminal_items`、`watch_session_events` 三件套可以完成 interactive attach/reconnect。
2. **cursor store 作为 CLI client state 可行**：JSON 文件 + file lock + atomic replace 方案在单机和多进程场景下安全。
3. **prompt 语义保持不变**：prompt 路径不调用 startup helper，不引入任何补读/观察行为。
4. **Service helper 不保存 CLI 状态**：Service 层只编排 Host public API，cursor 管理留给 CLI。
5. **不修改 Host/Engine public API**：现有 API 足以满足无漏投要求。

## Findings

### 1-未修复-中-startup active run 发现的 TOCTOU 窗口

- **位置**: Plan §Startup Attach/Reconnect，步骤 2-7；Implementation Slice A §Exact changes
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: Plan 的 startup 序列为：先 drain Outbox（步骤 2-4），再读取 Session snapshot 获取 `active_run_id`（步骤 5），再 open live watcher 观察该 active Run（步骤 7）。
- **反例/失败场景**:
  1. 用户在 interactive 入口启动时，Session 有一个 queued Run 等待 promotion。
  2. Outbox drain 完成（步骤 2-4），此时该 queued Run 尚未 promotion。
  3. 在步骤 5（读 `active_run_id`）和步骤 7（attach watcher）之间，Host 将 queued Run promotion 为 active，且该 Run 因某种原因迅速到达 terminal（如工具调用失败快速返回 `FAILED`）。
  4. 此时 Outbox 已排空（不再覆盖这个新 terminal），watcher 尚未 attach（无法接收 live terminal event）。该 terminal 丢失。
  5. 用户进入 REPL 后，该 Run 的 final answer/error 永不展示。
- **为什么有问题**: `docs/host/design.md:1183` 和 `1825` 明确要求 "必须依靠 terminal_event_id / event_sequence / run_id 去重，并证明两步之间没有漏投 terminal 的窗口"。当前序列是先 drain Outbox 再 attach watcher，中间读 `active_run_id` 的步骤存在非零窗口。Plan 未提供该窗口的 closure proof。
- **直接证据**:
  - `docs/host/design.md:1825`："实现上可以先建立 watch_session_events(session_id) 再 drain Outbox，也可以先 drain Outbox 再打开 live watch，但必须依靠 terminal_event_id / event_sequence / run_id 去重，并证明两步之间没有漏投 terminal 的窗口。"
  - Plan §Startup Attach/Reconnect 步骤顺序：先 drain Outbox（步骤 2）再读 active_run_id（步骤 5）再 attach watcher（步骤 7），中间没有 re-drain。
- **影响**: 低概率但真实的 terminal 漏投，用户在 interactive 入口错过 Run 结果。
- **建议改法和验证点**:
  1. 在 watcher attach 之后，再做一次 Outbox tail read（用 attach 前最后已知 cursor），以覆盖 attach 窗口内的 terminal。
  2. 或者：先 attach watcher，再 drain Outbox（按 design.md 推荐的第一种顺序），用 `terminal_event_id` / `run_id` 去重处理 overlap。
  3. 测试用例：模拟 queued Run 在 outbox drain 与 watcher attach 之间 promotion 并 terminal，验证 terminal 不丢失。
- **修复风险（低）**: 调整顺序或增加 tail read 是局部修改，不影响其他 slice。
- **严重程度（中）**: 窗口窄但后果是用户可见的 terminal 丢失，违反 design.md 显式要求。

### 2-未修复-中-同步 filelock 在 async CLI 路径中阻塞 event loop

- **位置**: Plan §Terminal Cursor Store，§Slice B §Exact changes
- **问题类型**: 最佳实践偏离 / 并发恢复风险
- **当前写法**: Plan 要求 "写入使用原子 replace；多进程并发使用 `dayu.runtime.filelock` 或等价已存在 runtime file lock wrapper"。
- **反例/失败场景**: `dayu/runtime/filelock.py` 是纯同步实现（`FileLock.acquire()` 阻塞线程）。CLI 命令入口 `_execute_interactive_on_existing_session` 和 `_execute_prompt_on_existing_session` 都是 `async` 函数，运行在 asyncio event loop 中。在 async 上下文中调用同步 filelock 会阻塞 event loop，导致：
  1. 并发 watcher drain task 无法及时处理 HostEvent。
  2. 如果 filelock 因多进程竞争而阻塞较久（秒级），UI 会完全卡住。
  3. 无法被 asyncio task cancellation 干净中断。
- **为什么有问题**: 项目架构硬约束要求 "各层需要公共运行时能力时，必须优先复用或扩展 `dayu.runtime`"。`dayu.runtime.filelock` 是层中立同步基础设施，但直接在 async CLI 热点路径上使用会导致 event loop 阻塞。Plan 没有说明如何在 async 上下文中安全使用同步锁。
- **直接证据**:
  - `dayu/runtime/filelock.py:148-180`：`acquire()` 是同步阻塞方法，内部调用 `self._third_party_lock.acquire(timeout=effective_timeout)`。
  - `dayu/cli/commands/interactive.py:300`：`_execute_interactive_on_existing_session` 是 `async` 函数。
  - Plan §Slice B §Exact changes："写入时使用 file lock 与原子 replace"。
- **影响**: 多 CLI 进程并发时 event loop 阻塞，UI 假死，极端情况下触发 asyncio 内部的 "blocking call in async context" 诊断。
- **建议改法和验证点**:
  1. 在 cursor store 的写入路径上使用 `asyncio.to_thread()` 或 `loop.run_in_executor()` 将同步 filelock 卸载到线程池。
  2. 或者在 `dayu.runtime` 中新增 async filelock wrapper（如 `dayu.runtime.async_filelock`），但需要评估是否属于过度设计。如果只有 cursor store 一个 consumer，用 `run_in_executor` 是更轻量的方案。
  3. 测试用例：模拟两个 async task 并发写 cursor store，验证不阻塞 event loop。
- **修复风险（低）**: 用 `run_in_executor` 包裹同步调用即可，不影响架构。
- **严重程度（中）**: 当前概率低（cursor 写入极快），但如果 filelock 因 OS 级别锁竞争而阻塞，后果是 event loop 卡死。

### 3-未修复-低-seen ids 窗口大小使用魔法数字

- **位置**: Plan §Terminal Cursor Store
- **问题类型**: 最佳实践偏离
- **当前写法**: "seen ids 只保留有限窗口，例如最近 100 个 terminal ids，用于 overlap 去重；窗口常量必须命名。"
- **反例/失败场景**: Plan 说 "例如最近 100 个" 但没有给出窗口大小的选择依据，也没有命名常量。AGENTS.md 编码硬约束明确规定 "禁止魔法数字、魔法字符串"。
- **为什么有问题**: 100 这个数字没有工程依据。如果 Session 有大量短轮次（比如 200+ 轮 interactive session），100 的窗口可能导致旧 terminal ids 被裁剪后，outbox 返回的重复 item 无法通过 seen ids 去重，造成 CLI 重复展示旧 terminal。
- **直接证据**:
  - AGENTS.md："禁止魔法数字、魔法字符串；工具 schema 例外，schema 内允许直接写字面量字符串。"
  - Plan §Terminal Cursor Store："seen ids 只保留有限窗口，例如最近 100 个 terminal ids"。
- **影响**: 实施 Agent 可能直接用 100 作为字面量，不做命名和依据说明。长 Session 场景下 potential 重复展示。
- **建议改法和验证点**:
  1. 在 plan 中明确窗口常量的名字（如 `CLI_TERMINAL_CURSOR_SEEN_IDS_MAX_SIZE`）和选择依据（如 "覆盖典型 interactive session 中所有轮次的 terminal ids，避免无限增长"）。
  2. 或者改用 `last_seen_terminal_event_sequence` 水线去重为主，seen ids 仅作 overlap 去重（此时窗口可以更小，因为水线已经覆盖了大部分去重需求）。
  3. 测试用例：模拟 seen ids 超过窗口上限，验证 oldest ids 被裁剪后不影响新 terminal 去重。
- **修复风险（低）**: 命名常量即可，不影响实现。
- **严重程度（低）**: 实施阶段可自然修正，不阻塞 plan 验收。

### 4-未修复-低-queued-only Session 的 interactive 行为未定义

- **位置**: Plan §Active Run Semantics，§Residual Risks
- **问题类型**: open question 未收敛
- **当前写法**: "如果 session snapshot 只有 queued_run_ids 且无 active_run_id，当前 plan 不直接等待 queued Run；这应作为 residual risk 记录，除非实施时已有 Host 行为能证明 queued 会被 promotion 成 active。"
- **反例/失败场景**: 用户 `interactive --label X` 进入一个有 queued Runs 但无 active Run 的 Session。Plan 说直接进入 REPL。用户在 REPL 中输入新 prompt 后，新 prompt 以 QUEUE 排到已有 queued Run 后面，但 queued Run 会先被 Host promotion 执行。用户在 REPL 中看到：
  1. 旧 queued Run 的 activity（通过 live watcher 出现在终端上）
  2. 旧 queued Run 的 terminal result
  3. 然后才是自己刚输入的 prompt 的回复

  这会让用户困惑：为什么我刚进入 Session 就看到旧 Run 在跑？为什么我的 prompt 排在后面？
- **为什么有问题**: 这是合理的 UX 问题。Plan 将其标记为 residual risk 需要 controller decision，但没有给出具体的 behavior specification（等待？警告？直接进入？），实施 Agent 只能按 "不等待" 实现。
- **直接证据**:
  - Plan §Active Run Semantics："如果 session snapshot 只有 queued_run_ids 且无 active_run_id，当前 plan 不直接等待 queued Run"
  - Plan §Residual Risks："requiring controller decision if tests reveal queued-only Session can persist without promotion"
- **影响**: 实施 Agent 可能选择直接进入 REPL，导致 UX 异常；后续可能需要返工。
- **建议改法和验证点**:
  1. 在 plan 中给出默认行为：queued-only 时先等待第一个 queued Run 被 promotion 为 active，然后走 active Run 观察流程。
  2. 或者显示提示信息告知用户有 N 个排队的 Run 将在后台执行，用户输入将排在它们后面。
  3. 至少应在 plan 中要求实施时先实证验证 "queued-only Session 是否能在没有 active Run 的情况下持续存在"。
- **修复风险（低）**: 只是行为规范补充，不改变架构。
- **严重程度（低）**: 已标记为 residual risk，可后续裁决。

### 5-未修复-低-bounded poll 控制权归属模糊

- **位置**: Plan §Slice A §Exact changes，§Implementation Decisions §1
- **问题类型**: 切片过粗 / 契约缺失
- **当前写法**: Plan 说 Service helper 应 "page through read_outbox_terminal_items until caught up or bounded poll rules require retry"，但同时说 "Service helper 不负责... 选择是否对 prompt 启动 backfill"。
- **反例/失败场景**: Service helper 若自行决定 bounded poll 上限（如最大轮询次数、超时），则违背了 "Service helper 不保存 CLI 状态" 的原则（poll policy 是 CLI/UI 层关注点）。若 Service helper 不做 bounded poll，则调用方（CLI）需要在外层套 polling loop，但 CLI 不应直接理解 `OutboxProjectionStatus.LAGGED` 等 Host 投影状态。
- **为什么有问题**: poll policy 的归属不清晰。按照分层架构 `UI -> Service -> Host`，poll policy（超时、最大重试、间隔）属于 UI 层，但 `LAGGED` / `CAUGHT_UP` 判断需要理解 Host projection 语义。当前 plan 把两者都放在 Service helper 中但未定义 poll boundary。
- **直接证据**:
  - Plan §Implementation Decisions §1："Service helper 负责：page through read_outbox_terminal_items until caught up or bounded poll rules require retry"
  - Plan §Implementation Decisions §1："Service helper 不负责：选择是否对 prompt 启动 backfill"
  - 现有 `_wait_for_terminal` 使用 `poll_interval_seconds` 参数由调用方传入（`dayu/service/entrypoint_runtime.py:521`），这是正确的 poll policy 归属模式。
- **影响**: 实施 Agent 可能在 Service helper 中硬编码 poll policy，或反过来让 CLI 理解 projection status，两种都违反分层。
- **建议改法和验证点**:
  1. 明确 Service helper 的 backfill 接口接受 `poll_interval_seconds` 和可选的 `max_poll_attempts` 参数（对标现有 `submit_entrypoint_turn_and_wait` 的接口风格）。
  2. CLI 传入 poll 参数，Service helper 只负责 page loop 和 projection status 判断。
- **修复风险（低）**: 接口微调，不改变核心逻辑。
- **严重程度（低）**: 实施阶段可自然解决，但提前收敛可减少返工。

## Open Questions

1. **queued-only Session 行为**：当 interactive 进入只有 queued_run_ids 无 active_run_id 的 Session 时，应该 a) 直接进入 REPL，b) 等待 promotion 后走 active Run 观察，还是 c) 显示提示？需要 controller 确认。当前 plan 标记为 residual risk 是合理的，但建议在进入 Slice C 前收敛。

2. **cursor store 路径的 workspace 所有权**：Plan 建议 `<workspace_root>/workspace/.dayu/cli/terminal_cursors.json`。路径中的 `.dayu` 目录是否已由 Host 或其他组件声明所有权？如果 future Host 也要用同一目录，会有命名冲突风险。Plan 在 Slice B stop condition 中提到了 "workspace .dayu state path ownership"，这是正确的谨慎做法。

3. **prompt cursor advancement 语义**：Plan Slice D 建议可选地在 prompt terminal 渲染后更新 cursor store。如果 prompt 和 interactive 共享 cursor store，prompt 的 cursor 更新可以帮 interactive 避免重复展示。但这也意味着 prompt 有了 "写 cursor store" 的 side effect。需要确认这是否改变 prompt 的语义边界。Plan 在 Slice D stop condition 中说 "若 cursor advancement 被认为改变 prompt 语义，移出本 WU"，这是正确的 defensive 设计。

## Residual Risks

以下风险 plan 已正确识别并分类，本 review 确认其分类合理：

1. **多 CLI 客户端共享 workspace cursor**：一个客户端看过的 terminal 对另一个客户端不再 backfill。Plan 分类为 "requires explicit product decision"，合理。当前单用户单 workspace 场景不受影响。

2. **Startup active Run 长时间 WAITING**：interactive 入口停在运行态。Plan 分类为 "accepted behavior"，合理——用户可以通过 Ctrl+C cancel 退出。

3. **Outbox drain state 不表达 UI delivery**：Plan 已通过 CLI cursor store 解决此问题（`OutboxTerminalItemState` 不代表 UI 已展示），不需要额外处理。

## Final Plan Review Conclusion

**PASS-WITH-RISKS**

Plan 的动机成立、根因判断正确、scope boundary 清晰。核心语义（prompt 不做 backfill、interactive 做 attach/reconnect）被正确保留。Implementation slices 粒度合理，test coverage 计划覆盖 happy path 和关键 failure path。AGENTS constraints 和分层架构约束被遵守。

三个 material findings 需要在实施前或实施中处理：

- **Finding 1（中）**：startup TOCTOU 窗口需要 closure proof 或 re-drain 策略。建议在 Slice A 实施时调整启动顺序（先 attach watcher 再 drain outbox，或 attach 后做 tail read）。
- **Finding 2（中）**：同步 filelock 在 async 路径中的 event loop 阻塞风险。建议在 Slice B 实施时用 `run_in_executor` 包裹。
- **Finding 3-5（低）**：魔法数字、queued-only 行为、poll 控制权归属——可在实施中自然解决，不阻塞 plan gate。

无严重（critical）finding。无结构性不安全。Plan 可以进入 implementation gate，但建议在 Slice A 启动前对 Finding 1 和 Finding 2 给出明确修复方案。
