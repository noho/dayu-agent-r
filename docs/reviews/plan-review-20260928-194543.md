## Findings

### 1-未修复-低-外层固定错误文案的常量归属未收敛，“复用同一常量”与“非 download 保持原行为”可被两种实现读法满足

- **位置**: plan「边界、语义 owner 与契约」第 4 段（“`dayu/cli/commands/fins.py` 的外层 download 未知异常固定错误复用同一常量，不再另写一份同义文案”与前句“只在最后一支按 `args.command_name == COMMAND_DOWNLOAD` 分流：download 使用安全记录，非 download 保持原行为”）
- **问题类型**: 不可直接实施 / 契约缺失
- **当前写法**: download 分支的固定错误要求复用 `output.py` 的提示常量且“不再另写一份同义文案”；同段又要求非 download “保持原行为”，但未说明“原行为”是否包含旧文案 `_FINS_DIRECT_UNKNOWN_FAILURE_MESSAGE`（fins.py:104，“命令执行失败，请使用 --log-file PATH 重试并查看日志”）的保留。
- **反例/失败场景**: 实施 Agent 读法一：仅 download 用新常量，非 download 连文案带 raw traceback 日志全部保持——代码里同时存在新旧两份 `--log-file` 同义提示，违反“不再另写一份同义文案”的字面约束，code review 时无法判定是否违约。读法二：全部命令的固定错误统一改用新常量，非 download 的用户可见文案随之改变——与“保持原行为”冲突。两种实现都能通过部分验收措辞，gate 争议落在文字解释而非行为。
- **为什么有问题**: plan 以“不再另写一份同义文案”作为硬约束，却把同一文案的另一持有者（非 download 分支的旧消息）留在“保持原行为”的模糊地带；总控裁决原文是“CLI 外层既有同类提示复用同一 CLI 文案真源”，意图是既有提示归一到单一真源，当前 plan 未把“保持原行为”的作用域限定到日志行为还是连文案在内。
- **直接证据**: plan 边界节第 4 段原文；`dayu/cli/commands/fins.py:104` 与 `:216-222`（外层 catch 对所有 direct 命令共用 `_FINS_DIRECT_UNKNOWN_FAILURE_MESSAGE` 渲染固定错误）；裁决表 MiMo F3 行“CLI 外层既有同类提示复用同一 CLI 文案真源”。
- **影响**: 实施 Agent 需自行猜测；后续 review/closeout 对“同义文案是否已归一”无法客观验收；轻微的用户可见文本不一致风险。
- **建议改法和验证点**: plan 补一句明确作用域，二选一：(a) “非 download 保持原行为”仅指保留 raw traceback 日志分支，外层固定错误文案对全部 direct 命令统一由 `output.py` 常量组合生成，`_FINS_DIRECT_UNKNOWN_FAILURE_MESSAGE` 退役；(b) 明确非 download 保留旧文案是刻意取舍，旧常量保留不算“同义文案”并说明原因。验证点：S2 测试断言 download 与非 download 外层错误文本的来源关系符合所选读法。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 2-未修复-低-CLI 日志提示按 EXECUTION 分类附着，覆盖无安全诊断记录的“无来源文档”失败，文案承诺与日志实际内容有语义偏差

- **位置**: plan 边界节第 4 段（“仅在已验证的 `FinsPublicFailureKind.EXECUTION` 失败详情后追加该提示”“storage 等其它分类不附加这条未知异常日志提示”）与 S2（诊断点仅为“download 且公共分类为 EXECUTION”的未知异常）
- **问题类型**: 其它（提示语义与诊断产生范围不一致）
- **当前写法**: 提示常量文案为“请用 --log-file PATH 保存脱敏诊断并查看该文件；已指定时请查看该文件。”，附着条件是公共分类为 EXECUTION；但安全诊断记录（`fins.download.unexpected_failure`）只在 producer catch 的未知异常路径产生。
- **反例/失败场景**: download 全部候选落选（`ingestion_runtime.py:4387-4394`，EXECUTION + “无来源文档”消息，非异常路径）时，用户看到“保存脱敏诊断”的提示，按提示用 `--log-file` 重跑后日志里没有任何 `fins.download.*` 诊断记录，只有普通 INFO 文档行——提示承诺的“脱敏诊断”与实际落盘内容不符。该失败的 retry_hint（4393，“若持续失败，请检查运行日志中的脱敏分类”）也在默认临时日志模式下指向不可查看的文件，本次修订只改写了未知异常分支的 hint（6886），此句未动。
- **为什么有问题**: plan 把该提示称为“这条未知异常日志提示”，却把附着条件写成分类而非“存在未知异常诊断”；展示层被明确禁止按字符串/`reason_code` 重新分类（该约束本身正确），因此 plan 有责任把分类附着的已知外溢写明或调整文案，否则实施/验收方对“提示⟺存在诊断记录”这一不变量的预期会被打破。
- **直接证据**: `ingestion_runtime.py:4388-4394`（EXECUTION 构造点一，无异常、无诊断）；`:6881-6887`（构造点二，未知异常，plan 改写其 hint）；`:7290-7296`（构造点三，observation 收口，仅进 Service JSON、不渲染 CLI 提示）；plan 提示常量原文与附着条件原文。
- **影响**: 低概率误导（该失败模式的 RESULT 详情本身已含文档行，用户可从摘要定位）；主要是验收不变量模糊，可能在实施测试里固化错误预期。
- **建议改法和验证点**: 二选一：(a) plan 明示“提示按 EXECUTION 分类附着，含无来源文档失败，此时日志内容为普通 INFO 文档行而非 unknown 诊断”，测试按此断言；(b) 把常量文案改中性（如“请用 --log-file PATH 保存运行日志并查看该文件”），不承诺“诊断”一词。顺带决定 4393 的 hint 是否登记为残余（默认日志模式下同样不可查看，但属裁决范围外）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
