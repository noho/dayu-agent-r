## Findings

### 01-未修复-[高]-原文读取与远端 PDF 获取越过 preflight，错误和 repair 优先级未封闭

- **位置**：Plan D2 `601225-annual-fulltext-plan.md:65-80`、S1 数据流 `:100-110`；Goal SS2/3。
- **问题类型**：架构边界 / 状态机漏洞 / 并发恢复风险。
- **当前写法**：workflow 在 `list_report_candidates` 前读取所有 COMPLETE CN FY 本地 PDF；downloader 在 selection 前对 FY 候选真实 GET PDF 并解析首页。现有 ticker preflight 位于 discovery 与 selection 之后（`cn_download_workflow.py:267-294`）。
- **反例/失败场景**：
  1. base 中存在 UNSAFE publication，同时远端某个 FY PDF 获取失败或首页无法解析。新链会先报 provider protocol failure，而不是先报告本地 UNSAFE，掩盖更高优先级的完整性事实。
  2. 唯一 selected source 为 REPAIR_REQUIRED。远端 PDF 已在 discovery 中获取，随后 repair owner 才决定是否允许修复；prepared payload 是否作为 repair 输入、何时丢弃、失败后保留什么没有状态契约。
  3. 本地 snapshot 在逐文件读取期间取消或 publication 变化；计划只写“调用 checkpoint、原样传播”，没有列出读取前/每个 PDF 后/远端 GET 前后的精确 stop points。
- **为什么有问题**：当前 protocol 把 candidate PDF GET 放在 filing acquisition，且 candidate 层失败只影响该 candidate（`cn_download_protocols.py:55-60`）；当前 preflight / repair gate 决定 company publication 和 selected repair 顺序。把仓储和远端实体读取前移，却不重写状态优先级，会让同一 durable integrity 事实出现不同诊断和处理路径。
- **直接证据**：Plan `:70-78` 同时要求“非 COMPLETE 不提前读失败”和“discovery 中真实 GET”；`cn_download_filing_workflow.py:165-255` 显示现有 Phase A、preparation 和 acquisition 顺序；`source_integrity.py:309-344` 显示 UNSAFE / repair disposition 的 owner；现有 repair tests 通过 `download_report_pdf` 注入 acquisition 失败（`tests/fins/test_cn_download_workflow.py:3468-3515`），未覆盖 discovery-time acquisition。
- **影响**：UNSAFE / REPAIR_REQUIRED 诊断被网络或 PDF parser 错误遮蔽；repair 可能消费或错误丢弃预取 payload；取消后留下不可解释的远端获取；实现 Agent 必须自行发明状态优先级。
- **建议改法和验证点**：
  - 在 plan 中画出明确顺序：先观察 integrity inventory 并裁决无需候选身份即可确定的 UNSAFE/结构错误；再取得 raw candidate identity；再按本次候选精确读取 COMPLETE 原文或 gated GET；最后执行 selected repair / Phase A。
  - 明确 REPAIR_REQUIRED + prepared asset、UNSAFE + remote GET、snapshot change、每个取消点的保留/丢弃/异常类型。
  - 增加顺序断言：UNSAFE 在任何远端 PDF GET 前失败；selected repair 在 acquisition 后仍由 repair owner 收口；取消点均无 source mutation，且异常 identity 不被 provider error 替换。
- **修复风险（低/中/高）**：中。
- **严重程度（低/中/高/严重）**：高。
- **Controller status 建议**：`accepted-candidate`。

### 02-未修复-[高]-同 source_id 的 URL 变化会让本地复用、身份复用和 COMPLETE 检查互相矛盾

- **位置**：Plan D2 `:70-78`、D3 `:84-98`、S1 `:102-108`。
- **问题类型**：契约缺失 / 状态机漏洞 / 并发恢复风险。
- **当前写法**：本地 PDF 只按 `source_id + exact source_url` 复用；身份 index 按 `(provider, source_id)` 返回旧 document ID；CN FY COMPLETE skip 又要求 `provider/source_id/source_url` 全部精确一致。
- **反例/失败场景**：同一官方 announcementId 的 raw URL 从 `http://.../old.PDF` 变为 `https://.../new.PDF`，或 provider 调整路径格式。downloader 因 URL 不同必须 GET，identity 却复用旧 document ID，Phase A 在 COMPLETE 上因 `source_url` 不同抛 `source_identity_conflict`，永久失败；即使 PDF SHA 完全相同也不能复用或安全更新 locator。
- **为什么有问题**：plan 同时把 URL 当“可复用字节键”、又不当“身份键”、再当“COMPLETE publication identity”，三个 owner 对同一来源身份给出不同答案。相同 source 的再增量目标因此不能稳定成立。
- **直接证据**：Plan `:72`、`:88`、`:96`；`cn_download_identity.py:30-55,103-116` 当前 source match 只用 provider/source_id；`cn_download_source_upsert.py:270-275` 持久化 source_url；`build_remote_fingerprint`（`:82-103`）也把 URL 纳入 fingerprint。
- **影响**：合法 URL 漂移变成永久 COMPLETE 冲突；实现 Agent 可能引入 URL loose parsing、临时覆盖或新的 fallback，进一步破坏来源身份 owner。
- **建议改法和验证点**：
  - 先做唯一决策：`source_url` 是稳定 publication identity，还是可变 locator。
  - 若是 identity，local match 与 identity index 必须使用同一完整 key，并规定 URL 改变时分配新来源身份。
  - 若是 locator，同 source_id 的 URL 变化应允许下载后以 PDF/remote fingerprint 判定内容，安全更新 locator 或保留原 URL，不能在 COMPLETE 上永久失败。
  - 测试同 source_id URL 变化且 PDF 相同、PDF 不同、仅 scheme/path 格式变化三种矩阵，并验证 A/B/retry 最终一致。
- **修复风险（低/中/高）**：中。
- **严重程度（低/中/高/严重）**：高。
- **Controller status 建议**：`accepted-candidate`。

### 03-未修复-[高]-单一 PDF 首页事实失败会中止整个 discovery，与现有 candidate failure contract 冲突

- **位置**：Plan D1 `:53-59`、D2 `:72-76`。
- **问题类型**：最佳实践偏离 / 契约缺失 / 测试缺口。
- **当前写法**：所有通过标题准入的 FY 都必须取得原文事实；空文本、加密、无标签、多年份、full/summary 冲突均抛 `ValueError`，downloader 再映射为 discovery 级 `FinsDownloadProviderError`，不能返回部分候选。
- **反例/失败场景**：窗口内一个非目标 FY PDF 是扫描首页或加密文件。即使三条目标 PDF 完全正常，整个 `list_report_candidates` 也失败，H1/Q 与可确认 FY 全部不可用。另一个候选网络临时失败同样中止整个 ticker 请求。
- **为什么有问题**：现有公共 protocol 明确承诺 HEAD/GET/PDF candidate failure 只影响该 candidate，不能让 ticker 崩（`cn_download_protocols.py:55-60`）。fail-closed 可以防止错误财年，但“不能猜测”不自动等于“一个不可解析候选必须抹掉所有可证明结果”。plan 没有区分目标必要候选、被淘汰候选和独立财期。
- **直接证据**：Plan `:56,59,74`；`cn_download_protocols.py:55-60`；13 份当前封面可解析只证明本窗口 happy set，不证明该全有或全无失败面可接受。
- **影响**：一个远端坏件导致全请求不可用；错误分类从 candidate failure 变为 provider-wide failure；实现和验收无法判断应保留哪些合法结果。
- **建议改法和验证点**：
  - 明确 failure disposition：至少隔离到 FY selection 范围，不能让 H1/Q 因 FY 首页失败而消失；若竞争完整性要求 FY fail-closed，应返回明确 FY 级失败而不是笼统 ticker discovery 失败。
  - 更新 protocol 的 failure scope，并测试“一条坏 FY + 三条正常目标 + H1/Q”的结果与诊断。
  - 对网络失败、PDF magic 失败、首页解析失败分别断言 typed reason、retryable 和作用域。
- **修复风险（低/中/高）**：中。
- **严重程度（低/中/高/严重）**：高。
- **Controller status 建议**：`accepted-candidate`。

### 04-未修复-[中]-首页正则会把带括号的摘要标签识别为全文

- **位置**：Plan D1 `:53-57`、测试断言 `:118`。
- **问题类型**：契约缺失 / 测试缺口。
- **当前写法**：删除 Unicode 空白后使用 `(?P<year>[1-9]\d{3})年?(?:年度报告|年报)(?P<summary>摘要)?`；没有紧邻 `摘要` 的匹配默认返回 full。
- **反例/失败场景**：首页标题为 `2024年年度报告（摘要）` 或 `2024年年度报告 [摘要]`。正则在 `报告` 后即匹配完整标签，`摘要` 因括号存在而未进入 optional group，于是被分类为 full，可能参与年度优胜并冒充全文。
- **为什么有问题**：当前 13 个样本只覆盖 `年度报告摘要` 的直接拼写。计划把该 grammar 提升为所有 FY 的共享业务真源，却把常见排版符号变化当作 full；这会产生错误 durable fiscal/kind 事实，而不是安全失败。
- **直接证据**：Plan `:56-57` 的精确 pattern；`pypdf-cover-probe.json` 中现有标签均为直接后缀，没有覆盖括号/方括号/未知后缀。
- **影响**：摘要被保存为全文；summary/full 身份和年度选择从源头错误，后续 COMPLETE 一致性只会稳定地保存错误事实。
- **建议改法和验证点**：
  - 把“标签结束”定义成封闭 grammar：明确允许的空白、全半角括号、冒号和 full/summary 后缀；出现 `摘要`、`摘要版`、`说明`、`补充` 等未知后缀时 fail closed。
  - 增加 `年度报告（摘要）`、`年度报告 [摘要]`、`年度报告摘要版`、未知后缀和同页 full/summary 混合 fixtures。
  - 不靠页数、大小、announcementType 或披露年补判。
- **修复风险（低/中/高）**：低。
- **严重程度（低/中/高/严重）**：中。
- **Controller status 建议**：`accepted-candidate`。

### 05-未修复-[高]-新 prepared/local/retry 路径缺少 failure-path owner tests，真实 CLI 也未证明零目标 GET 的独立事实

- **位置**：Plan 测试 `:114-133`、真实 CLI `:135-162`。
- **问题类型**：测试缺口 / 不可直接实施。
- **当前写法**：真实 CLI 覆盖 clean、seeded、两次 repeat 的 happy/incremental 结果；取消、转换失败、unsafe、repair、Phase B 变化和 rollback 说“用既有 boundary tests 验证”。零目标 GET 主要由 operator debug 行数证明。
- **反例/失败场景**：
  1. `prepared_asset` 的 candidate/source_id/URL/SHA 与最终 candidate 不一致，但结果校验或 retry 误接受，提交了错误 PDF。
  2. discovery 已 GET prepared PDF，Phase B identity churn 后 retry 丢弃 payload 再 GET；普通 repeat 和旧 `download_report_pdf` tests 都数不到这次额外 acquisition。
