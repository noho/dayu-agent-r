## Findings

### MIMO-F18-PR-001-未修复-高-把 handle 级 construction-time 约束误判成 Session 级 frozen profile contract

- **位置**: `First-principles judgment 与架构对齐` 第二条、owner boundary 表、Slice 2 第 5 步的
  “若 cause 指向动态 profile harness”分支。
- **问题类型**: 架构边界 / 契约缺失 / open question 未收敛
- **当前写法**: 计划已经断言 Trial2 在同一 attached Session 的相邻 CLI 进程之间改写 profile/caps
  “不是正式 scenario 可接受的固定 setup”，并把“动态 profile harness”预置为 scenario/setup cause。
- **反例/失败场景**: Trial2 每个 CLI 进程都重新执行 production assembly 并打开一个新 Host handle；如果配置只在
  opener 打开前改变，那么没有发生“Host handle 打开后改写 opener policy”。若 public/durable contract 没有把 profile
  digest 冻结在 Session 上，下一 opener 读取新完整 typed policy 可能是合法输入。此时固定 consumer checkpoint 只按
  `consumer_id` 前进，而 snapshot 又按 `policy_digest` 分区；新 policy 从已前进 checkpoint 接续却找不到旧 policy
  snapshot，可能是 projection owner 的真实跨-opener缺陷，而不是错误 setup。
- **为什么有问题**: 用户明确要求先验证 attached Session 切 profile/caps 是否违反 frozen configuration、manifest 或
  runner-input contract，并强调这只是待验证假设。计划用 handle-level设计文字直接回答了 Session-level问题，没有找到
  profile manifest / attach validation / durable Session contract owner，也没有证明 public contract 拒绝该输入，违反 binding
  goal 的 root-cause proof threshold。
- **直接证据**:
  - `docs/host/design.md:123` 的原义是 opener 参数“在 Host handle 打开后”不由 scene 或单个 Run 改写；没有写“Session
    首次 attach 后跨 opener 永久冻结”。
  - `docs/host/design.md:1204-1206` 区分 opener baseline 与 per-Run override，也没有定义 Session 级 execution profile
    identity 或 attach mismatch rejection。
  - `dayu/cli/commands/interactive.py:113` 每个 interactive 进程重新
    `open_host(prepared.runtime.host_assembly.options)`；`dayu/service/host_assembly.py:924-952` 从当前 profile 重新构造
    context / memory policy。
  - `dayu/host/durable/memory.py:267-304` 的 snapshot read 使用当前 policy digest，但 consumer id 保持稳定；
    `dayu/host/durable/schema.py:929` 的 projection checkpoint 主键只有 `consumer_id`。Trial2 直接数据又显示 wide digest
    snapshot 到 sequence 324、constrained digest snapshot 在 sequence 325 从空状态开始。
- **影响**: implementation agent 可能把产品 owner 缺陷错误归类为 harness 问题，只改正式 setup；跨进程合法配置变更仍会
  产生 memory 事实丢失或 candidate 失败。反方向也可能未经设计 gate 把 unsupported profile transition 误当产品能力。
- **建议改法和验证点**:
  1. 删除计划中对 Trial2 setup 合法性的预判，新增独立 contract-decision step：在 public Host request、Session/slot rows、
     admission-frozen config 与 attach/reconnect validation 中寻找 profile/policy identity owner，并明确记录“存在/不存在
     Session 级冻结字段与拒绝规则”。
  2. 若 contract 允许新 opener 使用新 policy，root-cause调查必须继续落在 projection checkpoint / policy snapshot owner；
     修复方向只能是 owner 级 policy transition 语义或 opener 上游 fail-fast validation，并在改变 public行为前回 Controller。
  3. 若 contract 确实禁止，则计划必须引用该 Session 级直接契约和 owner-level typed rejection；不能用 handle lifecycle 文字替代。
  4. 无论 legality 结论如何，正式 B2 仍可采用从起始固定 profile 的最小 setup；但这不能反向证明 Trial2 是 setup error。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### MIMO-F18-PR-002-未修复-高-sequence 324“完整治理重放”没有可恢复的 owner state，不能产生原失败的 exact reproduction

- **位置**: Slice 2 第 1-5 步及其完成断言。
- **问题类型**: 不可直接实施 / 状态机漏洞 / 最佳实践偏离
- **当前写法**: 从 Trial2 sequence 324 的隔离 SQLite clone“恢复 typed Session/Run/memory/checkpoint state”，再通过
  production attach/follow-up 进入完整 `_run_pre_start_governance`，以捕获具体 exception chain。
- **反例/失败场景**: 现存唯一物理 SQLite 已包含 sequence 325-327 及其 run、projection checkpoint、host instance、audit、
  payload/idempotency 等写入。`sqlite-before.json` 虽记录 `event_log=324`，但 `selected_rows` 只有 event、attempt、memory
  snapshot、run、slot、session、hot trace 等部分表，不包含完整 projection checkpoint、payload descriptor、SQLite payload、
  idempotency 与 runtime transactional state。手工删除后置 rows / 改 run status 不是任何 durable owner 的恢复 API；而重新走
  public follow-up 会创建新的 Run/event/host identity，证明的只是一个新 occurrence，不是原 sequence 325-327 的 exact exception。
- **为什么有问题**: plan 的 hard gate 要求 typed state + actual exception chain + 唯一 owner line 三者同源，但现有输入不能无歧义
  构造原 transaction snapshot。当前 `workspace/tmp/f18_owner_reproduction.py` 只对 final DB/current config 直接调用 private
  candidate function；它没有运行完整 governance，也没有恢复 sequence 324 全状态。其 `candidate_prepared` 结果只能反证该次
  近似调用，不能证明原错误不存在或锁定原 root cause。
- **直接证据**:
  - Trial2 segment 11 `sqlite-before.json` 的 counts 为 `event_log=324`，但 `selected_rows` 不含
    `host_projection_checkpoints`、`host_sqlite_payloads`、`payload_descriptors`、`idempotency_records` 等完整恢复所需 rows。
  - final DB 已有 sequence 327，memory projection checkpoint 已推进；历史 SQLite 没有 MVCC snapshot 可回到原事务。
  - `dispatch.py:1889-1927` 的 candidate 构造发生在新的 write transaction snapshot 中；新的 public submit 必然产生新
    `USER_INPUT_ACCEPTED` / `RUN_ACCEPTED` identity 与 cursor。
- **影响**: implementation agent 要么编造一个非 owner 的“回滚”数据库，要么把新 occurrence 的成功/失败错误归因给原
  sequence 327；两种结果都不满足用户要求，Slice 3 将永久卡在一个实际上不可执行的硬门或被错误放行。
- **建议改法和验证点**:
  1. Slice 2 必须先列出可接受的 exact restore source：原始 pre-command physical SQLite backup、完整 transaction-safe backup，
     或项目已有的 canonical rebuild/restore public owner。没有其中之一，就明确记录 original exception evidence
     non-recoverable，不得写“从 sequence 324 恢复”。
  2. 若只做 fresh/new occurrence reproduction，计划必须把它标成“同输入契约的新复现”，逐项冻结 code commit、完整 config、
     `EffectiveToolFacts` digests/source refs、filesystem artifact digests 和 cursor，而不能称为原 transaction重放；若不能复现，
     结论只能是 original cause unresolved。
  3. Controller 需在 plan gate 决定：接受 F18 因原日志/快照缺失而 blocked，还是重新确认一个前瞻性的 owner-observability
     work unit；不能让 implementation agent在 Slice 2 临场发明 durable restore。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### MIMO-F18-PR-003-未修复-中-B1 accepted 更新没有冻结唯一 public evidence projection，存在旧 bundle 与 B2 状态混写风险

- **位置**: Slice 1 实现要求、Affected owner boundaries。
- **问题类型**: 契约缺失 / 不可直接实施 / 过度耦合
- **当前写法**: 要求写入“当前 immutable public bundle/report digest、mandatory relative refs”，但没有列出确切 bundle id、
  report/summary/secret-scan digest、B1-only relative refs 与 cold limitation 的字段落点。
- **反例/失败场景**: 当前 scenario 仍引用旧 `interactive-memory-v3-...` bundle 与绝对 report path；新的
  `pr190-formal-g1a2xu` public report 同时包含 B1 accepted 输入和 B2 `needs-more-evidence`。若 implementation agent只替换
  report digest或笼统引用整个 bundle，可能把 B2 Trial1/Trial2 observation 一并投影进 B1 accepted record；若继续保留旧 refs，
  又会让用户此次裁决绑定到错误 observation identity。
- **为什么有问题**: B1 与 B2 的裁决边界是 Goal Confirmation 的核心。Oracle registry 是稳定 source of truth，不能把 exact
  evidence identity 留给 implementation阶段重新设计或从 mixed report 猜测。
- **直接证据**:
  - 当前 B1 record 的 `bundle_ids/report_ids/report_sha256/relative_refs` 仍指向旧 S4 evidence。
  - 新 public `observation-summary.json` 的 B1 投影明确是 `hot_owner_exact_comparison_count=6`、
    `hot_owner_canonical_equality=true`、`cold_compactor_response_count=0`；同一文件也包含独立 B2 状态。
  - 新 public digests 已存在且可冻结：report `de7ee64d...`、summary `dfe3604b...`、digest manifest
    `567d5539...`、secret scan `6f33e30c...`。
- **影响**: accepted Oracle 可能绑定错误或过宽 evidence；B2 未裁决事实被 B1 的 accepted status 间接带入，后续 readiness
  validation 无法审计“用户究竟接受了哪一组行为”。
- **建议改法和验证点**:
  1. 在 plan 中写明精确 B1 public bundle identity、report/summary/secret-scan digests和只用于 B1 的 relative refs；B2 refs 不得
     出现在 B1 scenario record。
  2. 明确 cold `compactor_responses=0` 与 provider request id unavailable 落在 Oracle limitation / residual question，而不是
     `gap_kind`；目标 scenario 的 `gap_kind` 保持 `none`。
  3. 给出四个目标文件的字段级 diff contract，并断言 B2 scenario record 的 `status/user_adjudication_identity/applicable_from`
     完全不变。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### MIMO-F18-PR-004-未修复-中-真实链只声明“bounded”，没有可审计的 provider budget 与依赖停止条件

- **位置**: Slice 3 `合法 setup` 第 3 条、mandatory report assertions、Verification matrix。
- **问题类型**: 不可直接实施 / 测试缺口 / 最佳实践偏离
- **当前写法**: 允许 accepted replacement、bounded repair、exhausted fallback 使用独立 fresh real chains，并说每条只做
  mandatory evidence 所需 bounded attempts，但没有定义链数、每链最大 ordinary Run、compact operation、repair attempt、
  reconnect次数与前置失败后的 stop rule。
- **反例/失败场景**: MiMo 自然输出可能首轮就 accepted、反复 accepted，或始终不触发同一 repair/fallback分支。实施 agent
  可能不断追加 filler Run / prompt 追分支，既消耗超出“最小次数”的真实 provider，又让多个 chain 的事实互相替代；也可能在
  accepted replacement 尚未形成时仍继续 reconnect/后置审计，产生不可验收 evidence。
- **为什么有问题**: 用户明确要求 bounded observation 只允许取得 mandatory evidence 的最小次数，失败原样保留，且独立真实链
  不能用 unit test替代。没有预先冻结的 call budget和 dependency gate，事后无法证明执行是 bounded，也不能稳定交给 formal
  observation agent。
- **直接证据**: Slice 3 只给出概念性三类链和 `max_compaction_attempts_per_operation` 的产品策略背景，没有正式 execution
  matrix；Verification matrix也没有 provider-call count、attempt terminal count、每链 stop reason 与禁止继续条件的断言。
- **影响**: provider成本失控、失败证据被后续尝试稀释、真实分支 coverage 不可审计，或因自然未触发而被 implementation agent
  临场设计 output-influencing prompt。
- **建议改法和验证点**:
  1. 新增三链 execution matrix：每链唯一目标、固定输入序列、最大 ordinary Run 数、最大 compactor operation/response 数、最多
     reconnect 次数、dependency gate 和停止原因；所有数量必须从 scenario precondition 与 Host attempt budget直接推导。
  2. 明确任一 prerequisite Run non-succeeded、config digest漂移、非 MiMo plan、secret/path scan failure、unexpected provider reach
     或 immutable capture failure 都立即停止该链，不以新 run 覆盖。
  3. 自然没有触发目标分支时，在到达预定 cap 后写 `needs-more-evidence`；不得临时扩次数或修改 prompt 注入期望 JSON。
  4. 为 public/private publication 写出固定目录与 digest manifest owner，明确 raw SQLite/log/绝对路径只留 private，public report
     只保留 relative refs 与脱敏 typed projection。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Residual risks and suggested tracking destination

- B1 cold analyzer `compactor_responses=0` 与 provider-native request id unavailable：保留在
  `cli.interactive.core-execution@2` adjudication history/notes 的 limitation / residual evidence question；不进入当前 scenario
  mandatory gap，也不扩成 F18 analyzer enhancement。
- public `runner_candidate_invalid` 无 durable typed cause：若 exact/new reproduction证明某个稳定 owner cause 对 operator 或恢复
  决策必需，应由 Controller 新开 public-contract design gate；本计划不得公开 raw traceback /异常文本。
- MiMo 自然输出不触发某分支：只进入 B2 observed report 的 `needs-more-evidence`，不得降低 Oracle predicate或注入输出；B2
  保持 `unadjudicated`，overall readiness 保持非 ready。
- fixed-profile formal setup 即使成功，也不能反向裁决 Trial2 的 profile transition 合法性；两者必须在 root-cause report 中分开。

## Final plan review conclusion

`fail`

两个高严重度问题使计划尚不能 code-generation-ready：它在缺少 Session-level contract 的情况下提前把 profile transition
裁成 setup error，同时提出了一个现有 evidence 无法无歧义实现的 sequence 324 durable restore。应先修正这两个 gate，再冻结
B1 exact evidence projection与 Slice 3 bounded execution matrix，之后重新 plan review。
