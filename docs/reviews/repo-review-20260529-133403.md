### 01-未修复-严重-Audit JSONL 写入先于 marker 插入，崩溃窗口导致重复审计行

- **入口/函数**: `AuditSinkProjection.apply_event`
- **文件(行号)**: `dayu/host/audit.py:231-239`
- **输入场景**: 任意 `canonical_fact` event 被 audit sink 消费
- **实际分支**: `_append_line(line)` 在 `insert_audit_sink_marker_if_absent(transaction, ...)` 之前执行
- **预期行为**: JSONL 行写入应在 marker 插入成功之后，或两者在同一原子操作内完成
- **实际行为**: 进程在 JSONL 写入后、marker 插入前崩溃时，下次 catch-up 因 marker 不存在会重复写入同一 event 的 JSONL 行
- **直接证据**: `audit.py:231` 先调用 `self._append_line(line)`，`audit.py:233-239` 后调用 `insert_audit_sink_marker_if_absent`。JSONL 是 append-only 文件，无法撤回已写入行
- **影响**: 审计记录幂等性被破坏；重复行可能导致下游审计分析结果不准确
- **建议改法和验证点**: 将 `_append_line` 移到 marker 插入成功之后。若担心 marker 成功但 JSONL 写入失败的反向问题，可接受"marker 存在但 JSONL 行缺失"作为可检测的不一致状态。验证：模拟 marker 插入成功后进程崩溃，确认不产生重复行
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 严重

### 02-未修复-严重-pinned state 的 current_goal 只在首次设置永不更新，user_constraints 不去重

- **入口/函数**: `_pinned_state_with_user_input`
- **文件(行号)**: `dayu/host/memory.py:2206-2239`
- **输入场景**: 用户在多轮对话中改变目标方向，或频繁输入相似约束
- **实际分支**: `current_goal` 仅在 `None` 时设置（行 2213-2214）；`user_constraints` 每次无条件追加（行 2225）
- **预期行为**: `current_goal` 应在用户目标变更时更新；`user_constraints` 应做 normalized text 去重
- **实际行为**: `current_goal` 首次设置后永不更新；`user_constraints` 持续增长直到被 `_limit_pinned_state` 截断丢弃旧条目

### 03-未修复-高-Projection failure 后 checkpoint 永久阻塞，无自动跳过机制

- **入口/函数**: `ProjectionRunner.run_once`
- **文件(行号)**: `dayu/host/projection.py:454-471`；`dayu/host/audit.py:373`；`dayu/host/memory_repair.py:251`
- **输入场景**: 单个 event 导致 consumer `apply_event` 抛出异常（如 JSON 序列化瞬态错误）
- **实际分支**: `if batch_result.failures > 0 or batch_result.events_scanned < batch_size: break` 立即中断整个批次
- **预期行为**: 一个损坏的 event 不应永久阻塞后续所有 event 的 catch-up
- **实际行为**: failure 后整个 projection checkpoint 停滞，直到外部 repair 流程介入
- **直接证据**: `projection.py:454-471` failure 后 break；`audit.py:373` 和 `memory_repair.py:251` 相同模式。memory projection、outbox projection、read model projection 均受此影响
- **影响**: 一个损坏的 event 永久阻塞该 consumer 的 catch-up，下游消费者（如 outbox drain）无法获取新数据
- **建议改法和验证点**: 在 `run_once` 中支持 `skip_on_failure` 模式（记录 failure 后继续处理后续 event），或在 failure row 中增加 `retry_after` 字段被 runner 尊重。验证：注入一个会导致 consumer 异常的 event，确认后续 event 仍被处理
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open Questions

1. **Recovery scan 的 `_DEFAULT_RECOVERY_DISPATCH_LIMIT = 1`**：每个 Run 只允许一次 startup automatic recovery dispatch。如果 recovery dispatch 也失败，Run 会被标记为 LOST。这个限制是否过于严格？
2. **`_classify_active_or_cancelling` 对 `CANCELLING` 状态的处理**：`CANCELLING` 状态的 orphan 在 orphan proof 成立时 `recoverable` 为 `False`，直接标记为 LOST。正在取消的 Run 的 orphan 是否应该被恢复？
3. **Outbox 终态 item 清理策略**：`host_outbox_terminal_items` 中 drained 状态的 item 永久保留。是否有 TTL 或定期清理机制？
4. **Memory snapshot 增长控制**：`host_memory_snapshots` 每次 projection event 都 upsert。旧 snapshot 是否被清理？

## Residual Risk

1. **测试覆盖**: 测试代码本身的质量未做独立审查。测试覆盖缺口已通过生产代码行为分析间接识别（如 audit 幂等性、pinned state 去重等场景的测试是否存在需进一步确认）。
2. **SQLite 单写者瓶颈**: 所有 durable 操作都通过同一个 `HostTransactionRunner`，高并发场景下 `SQLITE_BUSY` 可能导致 `HostTransactionRetryExhaustedError`。
3. **PID 回收窗口**: `StdlibPidLivenessProbe` 只做 `os.kill(pid, 0)` 探测，无法区分 PID 被新进程重用。在高 PID 周转率的容器环境存在误判风险。
4. **After-commit callback 失败**: `transaction.py:_run_after_commit` 在 durable commit 成功后执行 callback，callback 失败会导致半完成状态。
5. **Engine 空 content 正常迭代与 force-answer 语义不一致**: 正常迭代中模型返回空 STOP 会被接受为最终回答，但 force-answer 模式下会触发失败。虽然场景罕见，但语义不一致可能在调试时造成困惑。
6. **`_ChunkAggregationKind` 枚举未使用**: `_types.py:195-203` 定义了 `BY_INDEX` 和 `BY_ID` 但未被引用，是早期设计迭代的残留。
7. **non-stream parser 对非 dict 的 raw tool call 元素静默跳过**: `non_stream_parser.py:435-436` 不记录 warning，可能掩盖协议异常。
