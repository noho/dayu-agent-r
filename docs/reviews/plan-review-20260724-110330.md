## 4. Findings

### F001-未修复-高-file lock 读侧 contract 缺失

- **位置**: §7.3 File consistency and concurrent writers
- **问题类型**: 契约缺失
- **当前写法**: "当前 Dayu 相邻 `.lock` 存在时，读取 cold snapshot 使用现有 file lock primitive"
- **反例/失败场景**: Analyzer 在 live producer 正在 append cold JSONL 时读取。若 reader 不持锁，可能读到 partial line（被截断的 JSON）。当前 `_append_line` 使用 `_append_text_if_absent`（write 侧），但 cold reader 的 lock contract 未指定。
- **为什么有问题**: 实现 agent 不知道 reader 侧是否需要 `FileLock`、锁粒度（整个文件 vs 行级）、锁超时、或仅依赖 OS atomic write。若实现选择"不持锁"，concurrent writer 场景可能产生 malformed line，触发 `input.invalid_json_line` finding，这不是真实的 integrity 问题。
- **直接证据**: Plan §7.3 声称使用 "现有 file lock primitive"，但 `ToolTraceSinkOptions.lock_path` 是 write 侧参数；reader 侧代码无对应 contract。
- **影响**: 实现 Agent 可能实现不一致的 reader locking 策略；concurrent 场景测试无法确定预期行为。
- **建议改法和验证点**: 在 §7.3 明确 reader lock 策略：(1) 是否使用 `FileLock`；(2) 锁粒度和超时；(3) 或声明"依赖 OS atomic write，不持锁，partial line 归入 `input.invalid_json_line` finding 并继续"。选择 (3) 时需确认 `filelock` 在 macOS/Linux 上的原子性。
- **修复风险（低/中/高）**: 低
- **严重程度（高）**: concurrent reader/writer 是生产真实场景

### F002-未修复-高-corrupt hot DB 的 fail-closed vs degrade 语义矛盾

- **位置**: §8.4 Read-only durable opener / §13 Slice 1 Error handling
- **问题类型**: 契约缺失
- **当前写法**:
  - §8.4："打开前要求 DB regular file 已存在"
  - §13 S1 invariants："显式提供的 hot DB 是 corrupt/non-Dayu DB 时 fail analysis，不静默当作不存在"
  - §13 S1 invariants："DB/schema/open failure 若使 hot source 不可读，目录分析可在 cold 存在时降为 limitation"
- **反例/失败场景**: `workspace_directory` 模式发现 `dayu_host.sqlite3` 存在但文件损坏（例如 WAL checkpoint 中断后 DB header 损坏）。按第一条应 fail analysis；按第二条应 degrade to cold-only。两条规则在 directory input 的 auto-discovered DB 上冲突。
- **为什么有问题**: 实现 agent 需要在"DB 存在但损坏"的 directory input 场景做选择：fail 还是 degrade？两种行为都有合理性，但 plan 未明确区分"explicitly provided path"与"auto-discovered path"。
- **直接证据**: §13 S1 的两条 invariant 相邻但未说明适用条件。
- **影响**: 实现 agent 可能选择不一致策略；测试无法确定预期行为；operator 排障时行为不可预测。
- **建议改法和验证点**: 明确规则：
  1. `cold_file` 模式：不涉及 hot DB，不适用
  2. 目录模式 auto-discovered DB：DB 文件存在但 `validate_host_durable_schema` 失败或 open 失败时，degrade to cold-only + `hot_store_unavailable` limitation（记录具体错误原因）
  3. 未来若支持 `--hot-db` 显式参数：corrupt 时 fail analysis
  这保持 directory input 的容错性，同时为未来显式 hot DB 参数留 fail-closed 空间。
- **修复风险（低/中/高）**: 低
- **严重程度（高）**: 影响 S1 核心 error handling 设计

### F003-未修复-中-S4 跨层 README + production code 混合

- **位置**: §13 Slice 4 Allowed files
- **问题类型**: 切片过粗
- **当前写法**: S4 allowed files 包含 5 production files + 4 test files + 5 READMEs = 14 文件。README 更新与 Service/CLI 实现混合在同一 slice。
- **反例/失败场景**: S4 implementation agent 同时处理 Service path discovery、CLI arg parsing、report publication、5 个 README 的内容审计和编写。README 内容依赖 S1-S3 的最终实现细节（public types、rule ids、CLI command shape），若 S3 有 late change，S4 README 内容需要同步更新。
- **为什么有问题**: Control doc 要求 slice "大到能形成可测试语义，小到能一次实现、一次验证、一次 review"。S4 的 review 需要同时审查 Service/CLI 生产代码、4 个测试文件和 5 个 README 的内容正确性。README 修改是低风险但高噪音的 review 内容，会稀释 Service/CLI 核心逻辑的 review 注意力。
- **直接证据**: §13 S4 allowed files 列表；control doc slice 切分原则。
- **影响**: Review agent 可能在 README 内容审计上花费过多注意力，而忽略 Service/CLI 边界问题。但 S4 是最后一个 slice，不存在阻塞后续 slice 的风险。
- **建议改法和验证点**: 考虑将 README 更新从 S4 分离为 S4b（仅 README + docs 同步），或在 S4 completion signal 中明确 README 更新是机械同步、不需深度 review。当前写法不阻塞实现，但增加 review 成本。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 影响 review 效率，不影响 correctness

### F004-未修复-中-contracts.py 跨 3 slices 连续修改

- **位置**: §13 S1/S2/S3 Allowed files 均包含 `dayu/host/tool_trace_analysis_contracts.py`
- **问题类型**: 过度耦合
- **当前写法**: S1 创建 contracts（types + policy + source）；S2 扩展 contracts（report type、finding type）；S3 再扩展 contracts（vendor block type）。
- **反例/失败场景**: S1 定义的 `ToolTraceAnalysisReport` 结构在 S2 扩展时发现需要调整 S1 的 `ToolTraceAnalysisDataset` 结构；S3 的 vendor block 需要 S2 的 finding 结构支持 `diagnostic_refs`。三次连续修改同一文件，每次都需要理解前一次的完整上下文。
- **为什么有问题**: Implementation agent 执行 S2 时需要完整理解 S1 的 contracts 设计；S3 需要理解 S1+S2。若 S1 contracts 设计有误，S2/S3 会在错误基础上扩展。但 plan 的 contracts 设计足够详细（§8.1 列出所有 types 和 signatures），可以减少漂移风险。
- **直接证据**: §13 S1/S2/S3 allowed files 均包含 `tool_trace_analysis_contracts.py`。
- **影响**: 增加 sequential implementation 的上下文负担；但 plan 已列出完整 type inventory，实现 agent 可以在 S1 预定义所有 types，S2/S3 只填充 rules。
- **建议改法和验证点**: 在 §8.1 或 §13 S1 中明确：S1 创建 contracts.py 时预定义所有 public types 的骨架（包括 S2/S3 需要的 report、finding、vendor block types），S2/S3 只填充 rules 和 renderer 逻辑，不修改 type 定义。这消除跨 slice type 修改风险。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 增加实现 agent 上下文负担

### F005-未修复-中-S1 read-only store PRAGMA 配置风险

- **位置**: §8.4 Read-only durable opener
- **问题类型**: 最佳实践偏离
- **当前写法**: "配置 busy timeout、foreign keys 与 `PRAGMA query_only=ON`；不得执行 `journal_mode=WAL`、bootstrap 或 DDL"
- **反例/失败场景**: 现有 `configure_connection_pragmas` 设置 `journal_mode=WAL`。S1 实现 read-only opener 时若复用 `configure_connection_pragmas`，会在 `mode=ro` 连接上设置 `journal_mode=WAL`，这在 SQLite 中对 read-only 连接可能产生 warning 或 error（取决于 SQLite 版本）。若不复用，需要写一个 "read-only PRAGMA helper"，这是新代码路径。
- **为什么有问题**: 实现 agent 需要决定是复用还是新建 PRAGMA 配置。plan 说"不得执行 `journal_mode=WAL`"，暗示新建路径。但新建路径意味着 `configure_connection_pragmas` 的其它有用配置（如 `busy_timeout`、`foreign_keys`）需要手动复制。
- **直接证据**: Plan §8.4 与 `transaction.py:457` `configure_connection_pragmas` 的对比。
- **影响**: 实现 agent 可能创建不一致的 PRAGMA 配置，或在 read-only 连接上设置不兼容的 PRAGMA。
- **建议改法和验证点**: 在 §8.4 明确 read-only opener 的 PRAGMA 列表：`busy_timeout`、`foreign_keys=ON`、`query_only=ON`，不设置 `journal_mode`、`wal_autocheckpoint`。可复用 `configure_connection_pragmas` 的部分逻辑但跳过 WAL 相关 PRAGMA。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 影响 SQLite 兼容性

### F006-未修复-低-dual file publish partial failure 不报告具体哪个文件失败

- **位置**: §10.3 Output publication and exit codes
- **问题类型**: 最佳实践偏离
- **当前写法**: "首版允许两个最终文件在第二次 replace 失败时出现旧/新组合；CLI 返回 failure 并明确文件路径"
- **反例/失败场景**: JSON publish 成功但 Markdown publish 失败。CLI 返回 exit code 1 并报告路径，但 operator 不知道哪个文件是新的、哪个是旧的（或缺失的）。
- **为什么有问题**: operator 需要知道哪个 report 文件可信。plan 说"明确文件路径"，但未说明是否区分"成功发布的文件"和"失败的文件"。
- **直接证据**: §10.3 的描述。
- **影响**: Low。operator 可以通过文件 mtime 或内容判断，但体验不佳。
- **建议改法和验证点**: 在 error message 中明确"JSON published: <path>; Markdown publish failed: <path>"，让 operator 知道哪个文件可信。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: UX 问题

### F007-未修复-低-policy 参数无 CLI 暴露

- **位置**: §9.2 Large payload policy / §7.1 CLI contract
- **问题类型**: 契约缺失
- **当前写法**: `ToolTraceAnalysisPolicy` 有 5 个可注入参数，但 CLI contract 只定义 `INPUT --output-dir OUTPUT_DIR`，无 policy flags。
- **反例/失败场景**: operator 想调整 `large_payload_threshold_bytes` 从 128KB 到 64KB，但 CLI 不支持。需要编程调用 Host API。
- **为什么有问题**: Plan 说 policy "可由 WU-OBS-01 直接传入"，暗示首版 CLI 使用默认值。这不是 bug，但 operator 无法从 CLI 调整阈值。
- **直接证据**: §7.1 CLI contract 不包含 policy flags；§9.2 说 "policy 可由 WU-OBS-01 直接传入，无需 plugin/profile/DSL"。
- **影响**: Low。首版 CLI 使用合理默认值；WU-OBS-01 可通过 API 传入自定义 policy。
- **建议改法和验证点**: 首版接受默认值。在 §7.1 或 §16 residual risks 中记录"CLI policy flags 为未来增强"。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 不影响首版功能

## 7. Architecture / Best-practice / Optimal / Overengineering / Overcoupling Lenses

### Architecture boundary

- CLI -> Service -> Host 分层正确：CLI 只 import Service，Service 只 import Host public contracts。
- Read-only store 是现有 durable foundation 的 capability boundary，不是新 storage layer。正确。
- `dayu/host/__init__.py` 新增 analyzer public surface 是 intentional expansion，不是兼容 re-export。正确。
- Report 不注册为 Host durable public read model。正确。

### Best-practice

- Strict cold parser、strict schema validation、fail-closed malformed record。正确。
- Deterministic finding ordering and id assignment。正确。
- Markdown 从 structured report 单向渲染，避免双真源。正确。
- Policy 参数显式注入，不从数据推断。正确。

### Optimal-solution

- Read-only opener 是正确选择：复用 `open_host_durable_store` 会 bootstrap schema，operator 工具不能修改输入 DB。
- 4 slices 的切分理由成立（见下方 overcoupling 分析）。
- Analyzer 作为 typed functions + stable rule ids，不引入 engine/registry/plugin/DSL。正确。

### Overengineering

- 14 public types：每个 type 对应 report 结构的一部分，没有冗余。不过度。
- 5 policy 参数：每个参数解决不同的阈值需求，有明确默认值。不过度。
- Read-only store wrapper：防止 operator 工具意外写 DB 的最小 correctness 能力。不过度。
- **结论**: plan 没有 overengineering。

### Overcoupling

- `contracts.py` 跨 S1/S2/S3 修改（F004）：增加 sequential 上下文负担，但 plan 已列出完整 type inventory。低风险。
- S4 README + code 混合（F003）：增加 review 噪音，但 S4 是最后 slice。低风险。
- S2/S3 共享 dataset 但分离 review：provider identity 是高风险边界，分离合理。不过度耦合。
- **结论**: plan 没有 overcoupling。
