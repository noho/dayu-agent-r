## Findings

### 1-未修复-中-commit boundary 在 runner 异常路径不生效

- **入口/函数**: `_AsyncAgent._run_runner_iteration` (L937-997) → caller 主循环 (L544-546)
- **文件(行号)**: `dayu/engine/agent.py` L544-546, L961-997
- **输入场景**: Runner 抛出非 `CancelledError` 异常（如网络层异常未被 Runner 内部消化），同时 `cancellation_token` 已被触发
- **实际分支**: `except Exception` 分支设置 `state.failure_candidate`，`done_seen` 保持 `False`；caller 的 `if self._is_cancelled() and not state.done_seen:` 因 `done_seen=False` 跳过取消检查
- **预期行为**: commit boundary 注释声称"Runner done 后已接受的 final/tool/failure 候选不能被迟到取消改写"。在 runner 异常路径中，`failure_candidate` 已设置但 `done_seen` 仍为 `False`，导致 commit boundary 不保护该候选。实际行为是失败候选被直接分类为 `RUN_FAILED`，同时取消被静默丢弃
- **实际行为**: `failure_candidate` 被 `_classify_iteration` 返回为 `RunFailedData`，caller 产出 `RUN_FAILED` 终态。同时触发的取消不生效
- **直接证据**: L544 `if self._is_cancelled() and not state.done_seen:` — `done_seen` 在异常路径中保持 `False`（L904 初始化为 `False`，异常路径不修改它）；L992 `state.failure_candidate = RunFailedData(...)` 设置候选但不设置 `done_seen`
- **影响**: 当 runner 异常与取消同时发生时，run 以 `RUN_FAILED` 结束而非 `RUN_CANCELLED`。这是设计意图（runner 失败优先于取消）但未被测试覆盖，且 commit boundary 注释在此路径上具有误导性
- **建议改法和验证点**:
  - 方案 A（推荐）：在 caller 中将 `done_seen` 检查改为 `done_seen or state.failure_candidate is not None`，使 commit boundary 也保护异常路径的失败候选。同时更新注释说明"runner 异常 + 同时取消 → RUN_FAILED"的预期行为
  - 方案 B：在 `_run_runner_iteration` 的异常路径中也设置 `done_seen = True`
  - 补充测试：max_iterations=1 + runner 异常 + 同时取消 → 验证终态是 `RUN_FAILED`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-低-RunSuspendedData 缺少 reason 与 await_spec/snapshot 的一致性不变量

- **入口/函数**: `RunSuspendedData` dataclass 构造
- **文件(行号)**: `dayu/engine/contracts/engine_events.py` L314-327
- **输入场景**: 任何代码路径构造 `RunSuspendedData(reason="tool_awaiting", resume_hint=None, await_spec=spec, snapshot=None)`
- **实际分支**: dataclass 允许 `snapshot=None` 即使 `reason="tool_awaiting"`
- **预期行为**: 当 `reason="tool_awaiting"` 时，`await_spec` 和 `snapshot` 应为恢复所需的机器可读事实，不应为 `None`
- **实际行为**: `snapshot` 字段类型为 `ToolAwaitSnapshot | None`，允许 `None` 值。当前生产代码（`_make_suspended_terminal_with_close`）从 `ToolAwaitingOutcome.snapshot` 取值，该字段本身为 `None | ToolAwaitSnapshot`，因此 `snapshot=None` 是合法的 outcome 值
- **直接证据**: L327 `snapshot: ToolAwaitSnapshot | None`；`tool_outcome.py` 中 `ToolAwaitingOutcome.snapshot` 也为 `None | ToolAwaitSnapshot`
- **影响**: Host 拿到 `RUN_SUSPENDED` + `reason="tool_awaiting"` + `snapshot=None` 时，无法执行基于快照的恢复，只能依赖 `resume_token`。如果 Host 预期 snapshot 存在，可能导致恢复逻辑缺陷
- **建议改法和验证点**:
  - 在 `RunSuspendedData.__post_init__` 中增加校验：当 `reason == RUN_SUSPENDED_REASON_TOOL_AWAITING` 时，`await_spec` 必须非 `None`（snapshot 仍可选，因为某些工具可能无快照）
  - 或在 docstring 中明确说明 `snapshot=None` 的合法场景
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 3-未修复-低-工具超时-取消竞争测试依赖 executor 内部行为

- **入口/函数**: `test_tool_execution_timeout_wins_over_cleanup_cancel`
- **文件(行号)**: `tests/engine/test_agent_phase3_tool_call.py` L1338-1368
- **输入场景**: `_HangingToolExecutor` 在 `asyncio.CancelledError` 时触发 token
- **实际分支**: 超时命中 → `await_or_cancel_or_timeout` 取消 target task → `_HangingToolExecutor.execute` 捕获 `CancelledError` → 触发 token → `_close_runner_once` → token 已取消
- **预期行为**: 超时终态 `RUN_FAILED` 不被清理阶段的迟到取消覆盖
- **实际行为**: 测试通过，但依赖 `_HangingToolExecutor` 在 `CancelledError` 时触发 token 的行为。如果 executor 不触发 token（如 executor 内部吞掉 `CancelledError`），则 `_close_runner_once` 后 token 未取消，测试场景不同
- **直接证据**: `_HangingToolExecutor.execute` L350-355: `except asyncio.CancelledError: self.cancelled = True; if self.token_to_cancel_on_cancel is not None: self.token_to_cancel_on_cancel.trigger(); raise`
- **影响**: 测试只覆盖了"executor 在取消时触发 token"的场景。未覆盖"executor 不触发 token 但 token 在其他路径被触发"的场景
- **建议改法和验证点**: 补充测试：使用不触发 token 的 executor，但通过其他方式在 `_close_runner_once` 期间触发取消（如 monkeypatch `_close_runner_once`），验证超时终态仍不被覆盖
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 4-未修复-低-EngineEvent 移除 event_id 和 sequence 是 breaking change

- **入口/函数**: `EngineEvent` dataclass 定义
- **文件(行号)**: `dayu/engine/contracts/engine_events.py` L387-406
- **输入场景**: 任何依赖 `EngineEvent.event_id` 或 `EngineEvent.sequence` 的上层代码
- **实际分支**: 字段已从 dataclass 中移除
- **预期行为**: 上层代码不再能访问这些字段
- **实际行为**: 移除了 `event_id` 和 `sequence` 字段。`event_id` 原本用于唯一标识事件，`sequence` 用于单调递增排序。当前无替代机制
- **直接证据**: diff 中移除了 `event_id: str` 和 `sequence: int` 字段，以及 `_next_sequence` 计数器
- **影响**: 如果 Host / Service / UI 层依赖 `event_id` 做去重或 `sequence` 做排序，将编译失败。`occurred_at` (datetime) 可作为替代排序键，但同一毫秒内多个事件可能产生相同时间戳
- **建议改法和验证点**: 确认所有上层消费者已更新。如果需要事件唯一标识，考虑在 Host 层自行生成
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
