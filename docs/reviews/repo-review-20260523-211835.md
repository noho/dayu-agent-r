### F1-已确认-中: 多个 dispatch 创建点 `owner_host_instance_id=None` 导致启动恢复扫描孤儿检测盲区

- **入口/函数**: `_PromoteNextQueuedRunOperation`, `_create_steer_attempt_result`, `_create_queued_admission_result`, `_start_governed_in_transaction`, `_resolve_resume`, `_StartReactiveRecoveryOperation`
- **文件(行号)**: `admission.py:1446,2561,2920`, `dispatch.py:1202`, `waiting.py:951`, `engine_ingest.py:409`
- **输入场景**: 进程在 dispatch record 创建后、worker accept 前 crash
- **实际分支**: `recovery_process.py:215-222` 当 `owner_host_instance_id is None` 时返回 `OrphanProofInconclusive(reason=MISSING_OWNER)`
- **预期行为**: 所有 dispatch record 应能被 startup recovery 正确判定 orphan 并 closeout
- **实际行为**: 6 处本地 dispatch 创建时 `owner_host_instance_id=None`。若 crash 发生在创建后、worker accept 前（owner 尚无值），启动恢复返回 inconclusive，dispatch record 将永久悬挂在 `DISPATCHING` 状态
- **直接证据**: 
  - 上述 6 处 `owner_host_instance_id=None` 的 dispatch 构造
  - `recovery_process.py:215-222`: `owner_host_instance_id is None` → `OrphanProofInconclusive(MISSING_OWNER)`
  - `dispatch.py:2655-2661`: owner 仅在 worker accept 时写入
- **影响**: 中 — crash 后 dispatch record 悬挂在 PENDING/DISPATCHING 状态，需依赖 lane TTL 或外部监控清理
- **建议改法**: 对本地 worker dispatch，在创建时立即写入 scheduler 的 `host_instance_id`。本地 worker 与 scheduler 处于同一进程，crash 后 owner pid 必然不存在，不会产生 false-positive orphan proof
- **严重程度**: 中

## Open Questions

1. **Working assumptions 的预期生产者**：文档和 dataclass 设计充分但无实现。这是计划中的功能还是可 clean up 的死代码？
2. **compact 后 context 渲染的实际 token 数**：`_budget_after_compact()` 使用估算而非精确计数，当前的 typed + proportional estimate max() 策略是否经真实 provider feedback 校验？
3. **`evidence_backed_fact_candidates_accepted` 双重约束**：`validate_context_compacted_payload()` 要求 `EVIDENCE_BACKED_FACT_CANDIDATES_ACCEPTED=True`，但 `_validate_compacted_payload_for_memory_projection()` 在 fact 非法时降级接受。两个约束是否应统一？
4. **`recent_raw_turns_floor` 的语义范围**：为何 floor 只保护用户输入而不保护 assistant 结论？是有意设计还是遗漏？
5. **Transaction retry 透明性**：`HostTransactionRunner.run_write` 的 busy/locked 重试对 operation 透明——若 operation 在第一次尝试中产生外部可见 side effect（如 ID 生成、clock.now() 调用），重试时这些 side effect 会重复执行。当前所有 operation 均通过 CAS 保证幂等，但未来新增 operation 时需注意此约束

## Residual Risk

1. **Durable dispatch record 悬挂**：6 处本地 dispatch 创建时 `owner_host_instance_id=None`，crash 后 startup recovery 返回 inconclusive。需依赖 lane TTL 或外部监控清理
2. **EventLog 无限增长**：EventLog 表无分区、截断或归档机制。高吞吐场景下全局扫描性能随增长下降
3. **compaction 失败时的状态回退**：proactive compaction 失败后不写回退 EventLog，调用方需自行判断重试策略
4. **memory projection rebuild 的跨事务安全**：`rebuild_conversation_memory_projection()` 先 reset 再 catch-up，中间间隙若新 EventLog 提交需正确处理
5. **`_DEFAULT_STALE_AFTER_SECONDS=30` 与 dispatch_claim_ttl 的时间窗口**：在默认可接受范围内，但极端并发下可能需调优
