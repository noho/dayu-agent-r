## New findings（fix 后新引入/遗留，非首轮重复）

### N1-新发现-低-§5.2 pipeline 状态矩阵漏 `cancelled`，且 fix artifact C4 的事实前提错误

- **位置**: plan §5.2 Pipeline terminal JSON contract；fix artifact C4（“避免给pipeline虚构cancelled状态”）
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**: §5.2 不变量只列 `ok → stored>=1`、`skipped/deleted/failed → stored==0`，没有 cancelled 行；C4 以“pipeline 没有 cancelled 状态”为由从矩阵中排除
- **反例/失败场景**: pipeline 状态闭集实测**包含** cancelled：`_UPLOAD_TERMINAL_DISPOSITIONS` 映射 `"cancelled" → CANCELLED`（ingestion_runtime.py:300–305），`_resolve_upload_status` 对 `"cancelled"` 原样透传（sec_upload_workflow.py:649–651），cancelled `UploadOperationResult` 生产点存在（sec:287、cn:907、docling:1409、prepare_upload 取消分支 :301–302），tests/README 亦记录 “pipeline/result summary 共用 ok/skipped/deleted/failed/cancelled exact status owner”。若实施者按 §5.2 字面实现，cancelled+positive 会通过 pipeline 校验；若实施者改为在 pipeline 拒绝 cancelled（按 C4 的错误前提），现有 direct cancelled 上传流会直接崩
- **为什么有问题**: C4 是 controller 裁决要求，fix artifact 声称已落实，但其依据事实与代码矛盾；plan 声称的 owner-level closed 校验因此不 closed
- **直接证据**: ingestion_runtime.py:300–305；sec_upload_workflow.py:649–651,287；cn_pipeline.py:907；docling_upload_service.py:301–302,1409
- **影响**: 实施者实现不完整矩阵或误拒 cancelled 造成回归；实际行为层影响有界——§6.1 把所有 cancelled producer 固定 stored=0，summary 矩阵（§5.3 有 cancelled 行）会在终端构造时兜底，S1 断言 3 的 “non-ok+positive 拒绝” 措辞也能覆盖该用例
- **建议改法和验证点**: §5.2 增补 `cancelled → stored_file_count == 0` 行，并显式写出 pipeline 状态闭集 `{ok, skipped, deleted, failed, cancelled}`；S1 断言 3 明确包含 cancelled+positive 用例；修正 fix artifact C4 的理由表述
- **修复风险**: 低（纯 plan 文本一行 + 一条断言）
- **严重程度**: 低

### N2-新发现-低-canonicalizer 对 241–255 字符合法 POSIX basename 的拒绝路径未指定，typed content 分类丢失

- **位置**: plan §5.4 canonicalizer 契约（“长度 `<=240`…pathful/oversized值直接拒绝”）
- **问题类型**: 契约缺失
- **当前写法**: canonicalizer 只对 fragment/Cc/Cf 返回固定标签，pathful/oversized 直接拒绝（raise）
- **反例/失败场景**: POSIX NAME_MAX 255，241–255 字符的 basename 合法；损坏或空内容时，filing producer 在逐文件 catch 内调 canonicalize → ValueError 从 except handler 内抛出 → 逃逸 typed content failure 包装 → workflow generic catch（sec:341）按 `fins_upload_failure_from_exception(ValueError)` 分类为 `runtime/unexpected_runtime`。用户得到 bounded typed 失败（无 raw 泄漏、无 F3 式崩塌），但丢失 content 分类与 hidden label；与 §5.4 “无法原样展示的 raw basename 由 owner 确定性产生同一业务标签” 的承诺对 oversized 类不成立
- **为什么有问题**: canonicalizer 契约对“合法 basename 全集”不是 total 的，producer 路径对拒绝值未指定处理，实施者大概率按字面实现出上述分类丢失
- **直接证据**: plan §5.4；sec_upload_workflow.py:341–349（generic catch → runtime 分类）；docling_process_converter.py:216,242
- **影响**: 长文件名损坏文件的分类漂移（content → runtime）、无 label；无安全泄漏
- **建议改法和验证点**: 二选一并在 plan 明示：(a) canonicalizer 对 oversized 也返回固定标签（对合法 basename 全集 total）；(b) 明示 oversized 走 runtime 分类 bounded failure 并补对应 owner test
- **修复风险**: 低
- **严重程度**: 低

### N3-新发现-低-`FinsUploadFailureReason.__post_init__` 未明确要求对非 null `file_label` 执行同一 validator

- **位置**: plan §5.4 Closed failure contract（five-field reason 构造）
- **问题类型**: 契约缺失 / 最佳实践偏离
- **当前写法**: 只规定 parser 侧用 `validate_fins_public_file_label` 拒绝 raw label；producer 侧靠“先 canonicalize 再写 reason”保证合法
- **反例/失败场景**: 若未来/实现中任一 in-owner producer 漏掉 canonicalize 直接把 raw fragment/Cc/Cf label 写入 reason，`to_json()` 会照原样输出，`_upload_result_details` 构造 `FinsEventDetail("file", label)` 时 `_validate_safe_text` 抛 ValueError，F3 的崩塌模式复现。当前 `__post_init__` 已校验 message/retry_hint（upload_failure.py:79–94），file_label 是唯一不校验的字段
- **为什么有问题**: 五字段 reason 是 closed public contract，owner 内已有一致的 `__post_init__` 校验模式；parser 只守 JSON 注入边界，构造器边界留空
- **直接证据**: upload_failure.py:79–94；direct_events.py:1079–1104
- **影响**: 防御纵深缺口；当前所有 producer 路径实测均写 None 或 canonicalizer 输出，无现实触发
- **建议改法和验证点**: §5.4 明确 `__post_init__` 对非 null `file_label` 调用同一 validator；补一条 direct constructor 注入 raw label 被拒的 owner test
- **修复风险**: 低
- **严重程度**: 低
