## 2. Findings

### 1-未修复-[高]-缺名拒绝的错误投影契约只覆盖 admission 同步路径，后置校验点可复现 A19 已拒收的降级投影

- **位置**: plan「可直接实施的契约和数据流」§2（workflow 第一次 yield 前重校验、“FinsUploadUsageError …原样上抛，不被转为 unexpected_runtime”）、§3（“保留 stage_company_meta_for_upload”）、成功信号 3、风险 R2/R3、测试第 2/3 条。
- **问题类型**: 契约缺失 / 架构边界 / 非最优方案 / 并发恢复风险。
- **当前写法**: admission 产出具名 `FinsUploadUsageError`；workflow pre-yield 再校验并“原样上抛”；发布阶段保留 `stage_company_meta_for_upload`（会在 batch 内重新读取、重新 resolve 公司决策）；R2 以“需另行裁决 reservation/重校验契约”把 started 后缺名失败整体后移。
- **反例/失败场景**:
  1. durable job：`start_upload` 在 T0 通过 admission 并创建 queued job（`ingestion_runtime.py:4695-4712`）；执行前（队列窗口，可达秒/分级）公司 meta 被维护操作改写/删除，使名称变为必填。workflow pre-yield 重校验拒绝 → `FinsUploadUsageError` 逃出 generator → `_run_upload_job` 的 `except Exception` → `_save_failed_from_exception`（5986）→ `_save_failed`（5902）只写 `{"message": str(exc)}`，**没有 typed failure code**；direct 路径则经 `_run_direct_stream_producer`（4286）→ `_classify_direct_error`（7046，`FinsUploadUsageError` 是 `ValueError` 子类 → 通用 `USER_INPUT`）。两条路都拿不到 goal/测试第 2 条承诺的同一 failure fact（`failure.code == company_name_required`），且该 job/observation 已创建，与成功信号 3 的绝对表述（“缺名拒绝没有…job、observation…发布”）冲突。
  2. [pre-yield 快照通过 → batch 内 `stage_company_meta_for_upload` 重读变为需名] 的窄窗口：`UploadCompanyNameRequiredError` 原始抛出 → workflow `except Exception` → `fins_upload_failure_from_exception` fallthrough → **`unexpected_runtime`**——正是裁决明确拒收的 A19 失败形态原样复现（`upload_failure.py:288-295`）。
- **为什么有问题**: goal 成功信号 2 要求“跨 US/CN/HK、direct/job/observation、Service、tool/CLI 消费同一状态判断和错误投影”；裁决要求缺名“以字段明确的 typed usage 错误拒绝”。plan 只把投影契约写到了 admission 同步路径；workflow 公开流还能被独立调用（plan 自己承认“覆盖可独立调用的 pipeline”），其拒绝在不同消费端降级成不同事实。更关键的是 plan 放弃了已校验的 `MaterialUploadAdmission.company_meta_decision`（§2 明明把 `UploadCompanyMetaDecision` 列为 validator 输出），发布时重走 `stage_company_meta_for_upload` 第三次决策——而 filing 既定模式是携带决策发布：`sec_upload_workflow.py:242-244`、`cn_pipeline.py:873-875`、`filing_upload_publication.py:810/853-855` 均为 `stage_upload_company_meta_decision(decision=…)`；filing 对后置校验点的 state-dependent usage codes 有明确收敛（`filing_upload_publication.py:71-78`、746-749：`COMPANY_NAME_REQUIRED` 等 → `source_publication_conflict`），fresh 重校验的 operational 失败投影也有唯一 owner（`_filing_upload_fresh_validation.py:30-70`）。plan 说“需另行裁决 reservation/重校验契约”，低估了既有 filing 投影/携带模式已经给出的最小答案；语义 owner 不清就交给实施 Agent，正是项目约束禁止的情形。
- **直接证据**: 见上列各行号；另：`upload_company_meta.py:156-196`（`stage_company_meta_for_upload` 重新 `_load_existing_company_meta` + `resolve_upload_company_meta_decision`，可抛 `UploadCompanyNameRequiredError`）；`ingestion_runtime.py:4707-4710`（job 创建先于 runner 执行）；`sec_upload_workflow.py:118-141`（`collect_upload_result_from_events` 不吞 workflow 异常）；`upload_failure.py:265-272`（`CompanyMetaConcurrentUpdateError` → 既有 STORAGE 失败映射，可承担漂移）。
- **影响**: 实施 Agent 需自行发明后置拒绝的投影语义（三种入口各写各的，或误把 R2 当“可以不投影”）；竞态下用户可见错误退回裁决已拒收的 `unexpected_runtime`/message-only 形态；测试第 2 条“direct/durable/observation 消费同一 failure fact”按现设计无法在漂移路径成立；后续 O13/O14/O15 若要接 target 状态错误会继承同一投影缺口。
- **建议改法和验证点**:
  1. workflow 发布段改为 stage 已校验决策：batch 内 `stage_upload_company_meta_decision(decision=MaterialUploadAdmission.company_meta_decision)`（filing 同款），删除发布路径的第三次 re-decide；状态漂移由 `CompanyMetaCommitIntent` 的 `observed_meta` 乐观并发（`CompanyMetaConcurrentUpdateError` → 既有 STORAGE 映射）承担，天然满足“不发布 preflight snapshot”又不产生 post-started 缺名。
  2. 明确 pre-yield 拒绝的投影 owner：按 filing `resolve_fresh_filing_request` 模式把该共享“读 snapshot + 调 validator + 投影”收敛为单一 helper（避免 SEC/CN 各写一份读取与投影胶水——plan 白名单未给这个共享边界留位置，两个 workflow 只能复制或越白名单新增文件），失败要么 yield typed failure 事件后 return，要么在 runner/job/direct 边界按 `FinsUploadUsageError.failure` 写 usage failure summary；若接受“输入在接收时合法、状态随后变化”的语义，可按 `filing_upload_publication.py:71` 先例把 state-dependent usage codes 在后置校验点收敛为 publication conflict，但必须写进 plan，不能留给实施 Agent。
  3. 成功信号 3 的“没有…job、observation…发布”限定为接收时/稳定状态拒绝（与 R2 口径一致），或承诺 job/observation 的晚拒绝收口形态。
  4. 验证点：注入“admission 后、执行前公司 meta 被改写”的 durable job 用例，断言终态 failure 是 typed（code 明确，绝不出现 `unexpected_runtime`）且无公司/材料业务发布；`[pre-yield→stage]` 窗口注入同理；filing 路径回归不漂移。
- **修复风险（低/中/高）**: 低——两个改法都是复用既有模式（`stage_upload_company_meta_decision`、`CompanyMetaConcurrentUpdateError` 映射、`_filing_upload_fresh_validation` 形态）；若新增 failure code 才需动 `upload_failure.py`（当前白名单未含，复用现有 code 可不改）。
- **严重程度（低/中/高/严重）**: 高（adjudication 已拒收的失败形态仍可达 + goal“同一错误投影”缺口 + owner 不清将直接传导给实施 Agent；竞态窗口有宽有窄但后果与承诺直接冲突）。
- **残余风险**: 即便按建议收口，跨 lifecycle 的“绝不出现 started 后失败”仍不可只读保证（R2 本质），该残余应登记给 O13/O14/O15/并发 work unit 的状态机裁决。
