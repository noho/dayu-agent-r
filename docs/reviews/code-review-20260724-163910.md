### 1-LOW-`_validate_source` bare `else` 静默捕获未来 enum 值为 TRACE_DIRECTORY

- **入口/函数**: `_validate_source`
- **文件(行号)**: `dayu/host/tool_trace_analysis_contracts.py:802-803`
- **输入场景**: 将来 `ToolTraceInputMode` StrEnum 新增第五种模式后调用 `ToolTraceAnalysisSource.__post_init__`
- **实际分支**: `elif source.mode is ToolTraceInputMode.DAYU_DIRECTORY` 不命中 → 落入 `else:` → 调用 `_validate_trace_directory_source`
- **预期行为**: 穷举 match，对未知枚举值 raise `ValueError` 而非静默走 TRACE_DIRECTORY 路径
- **实际行为**: 任何前三种 `if`/`elif` 未匹配的 enum 值被当成 TRACE_DIRECTORY 校验路径布局与类型
- **直接证据**: `contracts.py:800-803`
  ```python
  elif source.mode is ToolTraceInputMode.DAYU_DIRECTORY:
      _validate_directory_source(source, dayu_root=source.requested_path)
  else:                                                    # line 802
      _validate_trace_directory_source(source)             # line 803
  ```
- **影响**: 当前四值枚举下无害；一旦新增第五模式，路径布局校验将错位，可能把 workspace/dayu 目录当成 trace 目录接受
- **建议改法和验证点**: 将 `else:` 改为 `elif source.mode is ToolTraceInputMode.TRACE_DIRECTORY:` 并追加 `else: raise ValueError(f"unsupported input mode: {source.mode}")`；在 `test_tool_trace_analysis_input.py` 增加模式穷举测试
- **修复风险（低）**: 不改变当前四模式行为，仅增加防御性分支
- **严重程度（低）**

## Residual Risk

1. **Issue #64 — native Anthropic / Claude Code gateway**: 当 agent 通过 native gateway 运行时，provider request identity 只能在 gateway 完成该能力后由当前 analyzer 验证。当前 limitation 已正确标记，不产生虚假 finding。residual risk 为 "当前无法验证 native gateway path 的 provider 报障信号"——这已记录在 vendor debugging block 的 limitations 中。

2. **`input_changed_during_analysis` limitation 覆盖率**: 该场景仅在 production Tool Trace fixture 上通过 integration 级测试验证（真实 workspace + 真实 producer baseline 后追加行）。unit 级测试因需模拟 producer 并发写入，当前不作为首版 unit test 覆盖目标。residual risk 为 "mock-based unit test 可能无法完全模拟真实文件系统并发行为"——但 production integration test 已覆盖该路径。

3. **large payload threshold 默认值 131,072 bytes**: 该值是基于一般工具 payload 经验的静态默认，不是从当前数据 percentile 推导。若实际工具 payload 普遍超过此阈值，会生成大量 `payload.large_payload` finding。residual risk 为 "默认阈值可能不完全匹配特定 use case 的 operator 预期"——但 policy 可显式注入，WU-OBS-01 可覆盖。

4. **首版无 `--fail-on` policy**: plan 明确不在此 WU 实现 finding severity-based exit code policy。operator 必须阅读 report 自行判断严重性。residual risk 为 "自动化 pipeline 无法仅凭 exit code 判断分析结果严重性"——由 WU-OBS-01 或后续 WU 承接。

5. **partial last line 场景**: 当前实现不把 partial last line 当正常并发态，也不做无锁重试。若 producer 在 reader 获取 lock 后、open 前写入并发生 partial flush，snapshot 可能出现损坏的行。该 risk 理论上存在但极低——因为 file lock 在 O(1) 临界区内保护 open+fstat，且当前 producer 使用同一 lock contract。
