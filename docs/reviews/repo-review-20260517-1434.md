### 1-未修复-严重-`reset_minimal_read_model_projection` 无条件删除所有 timeline 行

- **入口/函数**: `reset_minimal_read_model_projection()`
- **文件(行号)**: `dayu/host/durable/read_model.py:292`
- **输入场景**: 多 consumer 部署时，一个 consumer 调用 reset 重建自己的 read model 投影
- **实际分支**: `DELETE FROM host_session_timeline_items` 无 WHERE 子句
- **预期行为**: reset 应只清理当前 consumer 的 timeline 数据
- **实际行为**: 无条件删除表中全部行，所有 consumer 的 timeline 数据被一并清除
- **直接证据**: `read_model.py:292` 的 SQL 语句为 `f"DELETE FROM {TABLE_HOST_SESSION_TIMELINE_ITEMS}"`，未带 consumer_id 过滤；而 `host_session_timeline_items` 表 schema 中无 consumer_id 列（无法按 consumer 过滤）。同文件中 `projection_failures` 和 `projection_checkpoints` 的 DELETE 则有 `WHERE consumer_id = ?` 过滤（行 295, 299）。
- **影响**: 多 consumer 部署下，一个 consumer 重建会导致所有 consumer 的 session timeline 数据丢失，需要全部 consumer 重新全量投影
- **建议改法和验证点**: 方案 A — 如果 timeline 是全局共享视图，reset 应拒绝在非开发/测试环境下执行，或要求显式 force flag；方案 B — schema 增加 consumer_id 列以支持 scoped reset。最小修复：在 docstring 和调用方明确"本操作为全局破坏性操作"，增加调用方 guard
- **修复风险（低）**: 当前单 consumer 部署不受影响；修复方案需确认 timeline 的 consumer 语义设计意图
- **严重程度（严重）**: 多 consumer 场景下静默数据丢失

### 2-未修复-高-`_handle_usage()` 在 token 计数字段格式错误时终止整个 SSE 流

- **入口/函数**: `SSEParser._handle_usage()`
- **文件(行号)**: `dayu/engine/runners/openai/sse_parser.py:464-484`
- **输入场景**: Provider 返回的 `usage` 对象中 `prompt_tokens` / `completion_tokens` / `total_tokens` 任一不是 int 类型（例如 provider 返回了字符串 `"123"` 或浮点数 `123.0`）
- **实际分支**: `isinstance` 检查失败 → yield `RunnerProtocolErrorData` → 设置 `self._terminated = True` → yield `RunnerDoneData(ERROR)`
- **预期行为**: usage 是辅助元数据，格式异常应降级为 warning 并继续消费流中后续有效内容
- **实际行为**: 流被立即终止，本已成功累积的 content / tool_calls 全部作废，Run 进入 ERROR 终态
- **直接证据**: `sse_parser.py:477-484` 设置 `_terminated` 并 yield ERROR done；`sse_parser.py:200-206` 的 `_abort_with_error` 同样模式。对比 content delta 处理（行 330-334），content 类型不对只是 skip 并 continue，不会终止流
- **影响**: Provider 的 usage 格式变化会导致正常运行失败；这是一个可恢复的非致命协议差异被升级为致命错误
- **建议改法和验证点**: 将 usage 字段类型校验失败降级为 `RunnerDiagnosticData` warning，不设置 `_terminated`；仅在使用 `usage` 值时做防御性 fallback（如 `int(prompt_tokens) if isinstance(...) else None`）
- **修复风险（低）**: 修改仅影响 usage 处理路径，不影响内容/工具调用/完成原因的核心解析逻辑

### 6-未修复-中-`_enqueue_or_steer` 异常处理中原始异常可能丢失

- **入口/函数**: `HostDispatchScheduler._enqueue_or_steer()`
- **文件(行号)**: `dayu/host/dispatch.py:529-538`
- **输入场景**: worker 启动失败（触发 `except Exception`），随后 `_closeout_worker_startup_timeout()` 也抛出异常
- **实际分支**: 内层 `try: _closeout_worker_startup_timeout(record)` 抛出异常 → `finally: _safe_release_lane_token(token)` 执行 → 异常从内层 try 向外传播，覆盖原始 Exception
- **预期行为**: 原始启动失败异常不应被 `_closeout_worker_startup_timeout` 的异常覆盖；两者应分别记录
- **实际行为**: `_closeout_worker_startup_timeout` 异常替换了原始 worker 启动失败的异常，故障诊断时看到的根因是 closeout 失败而非真实启动失败

- **影响**: 故障排查时根因被掩盖
- **建议改法和验证点**: 在内层 `try` 增加 `except Exception: _LOGGER.exception(...)` 记录 closeout 失败但不重新抛出；或使用 `ExceptionGroup`（Python 3.11+）同时携带两个异常
- **修复风险（低）**: 仅影响异常传播路径，lane token 释放不受影响
- **严重程度（中）**: 异常掩盖导致故障诊断困难

### 8-未修复-中-`_DefaultLocalWorkerHandle` 存在 async 竞态窗口

- **入口/函数**: `_DefaultLocalWorkerHandle.events()` / `close()`
- **文件(行号)**: `dayu/host/local_proxy.py:92-103`, `117-129`
- **输入场景**: 两个协程并发访问同一个 handle 实例（coroutine A 调用 `events()`，coroutine B 调用 `close()`）
- **实际分支**: A 通过 `_closed` 检查 → B 设置 `_events = None`, `_closed = True` → A 返回 `self._events`（此时为 None）

- **建议改法和验证点**: `close()` 和 `events()` 使用 `asyncio.Lock` 互斥；或 `events()` 返回后检查 `_closed`
- **修复风险（低）**: 加锁在单线程 asyncio 下几乎无性能影响
