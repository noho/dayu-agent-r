### 01-未修复-高-wait deadline/expiry 由 callback、poll adapter 与 provider 分支分别裁决

- **入口/函数**: `DefaultWaitCallbackAdapter.resolve_callback(...)`、`WaitPoller.poll_once(...)`、`FinsWaitPollAdapter.poll_wait(...)`、`DefaultHostResolveWaitService.resolve_wait(...)`
- **文件(行号)**: `dayu/host/wait_callback.py:393`、`dayu/host/wait_callback.py:423`、`dayu/host/wait_callback.py:525`、`dayu/host/wait_adapter.py:194`、`dayu/host/wait_adapter.py:924`、`dayu/host/wait_adapter.py:951`、`dayu/host/wait_adapter.py:967`、`dayu/fins/ingestion/wait_adapter.py:392`、`dayu/fins/ingestion/wait_adapter.py:422`、`dayu/fins/ingestion/wait_adapter.py:606`、`dayu/host/waiting.py:935`
- **Semantic fact or contract involved**: wait 的 `deadline_at` / `expires_at` 是否已经失效、失效后是否仍允许接受外部结果，以及非法持久化边界应被视为 storage corruption 还是业务 `LOST`。
- **Correct owner**: Host wait durable state 与 common `resolve_wait` precondition/state machine；poll、callback、manual 和 Fins adapter 只能提供 typed provider observation，不应各自裁决 Host deadline。
- **Where ownership drifted**: callback 在进入 resolver 前自行解析 deadline；Fins poll adapter 只在 `TRANSIENT_UNAVAILABLE` 分支解析同一字段；正常 pending/terminal snapshot 跳过边界；common resolver 完全不检查 deadline。
- **输入场景**: 同一个仍为 `WAITING`、但 `deadline_at` 已过期的 wait record，分别收到 callback completed、Fins terminal snapshot、Fins pending snapshot 或 transient unavailable。
- **实际分支**: callback 返回 `STALE_CALLBACK` 且不调用 resolver；terminal snapshot 返回 `WaitPollReady` 并进入 `resolve_wait`；pending snapshot 返回 `WaitPollNotReady`；transient unavailable 返回 `WaitPollLost` 并把 Run 收口为 `LOST`。
- **预期行为**: 所有 source 必须消费同一个 Host-owned eligibility/expiry decision；相同 durable boundary 与相同 observation time 不应因 transport/provider 分支不同而改变 canonical accept、继续等待或 terminal closeout 结论。
- **实际行为**: 同一 deadline fact 当前可以产生拒绝、继续等待、成功 resume/failed closeout、或 `LOST` 四种互斥治理事实。非法 boundary 在 callback 被标为 invalid state，在 Fins transient 分支却被转换成业务 `LOST`。
- **直接证据**: `WaitPollAdapter.poll_wait` 直接接收完整 `WaitRecordRow`（`wait_adapter.py:194-203`），poller 原样传入（`924-925`）；callback `_stale_status_or_none` 在 resolver 外解析并拦截（`wait_callback.py:525-558`）；Fins `_poll_error_result` 仅在 transient error 调 `_wait_boundary_lost`（`wait_adapter.py:392-408`），而 `_poll_snapshot_result` 的 pending/terminal 分支不检查边界（`422-442`）；poller 对 ready/lost 才统一调用 resolver（`dayu/host/wait_adapter.py:951-981,1154-1173`）；`resolve_wait` 的 resume/failed/lost path 使用 `observed_at` 写状态但不读取 deadline（`dayu/host/waiting.py:935-1139`）。
- **影响**: 过期结果可能在 poll 路径被 canonical accepted 并创建新 Attempt，而 callback 路径拒绝同一业务完成；provider 暂时不可用还可能把损坏的 Host 时间字段伪装成不可恢复的业务 `LOST`。这会造成状态、审计与恢复行为按入口分裂。
- **为什么 local-minimum design 会失败或变贵**: P3-F 已关闭旧的 Fins 300 秒本地 timeout，但当前修复只让 adapter 读取 Host 字段，没有把“如何解释该字段”的 authority 收回 Host。新增 source、provider 状态或 expiry policy 时必须继续在 callback、poller和各 adapter 同步分支。
- **建议改法和验证点**: 在 Host wait owner 增加单一 typed boundary/eligibility classifier，并在 claim/resolve common path 对 `POLL` / `CALLBACK` / `MANUAL` 一致执行；明确过期后的 terminal policy与非法持久化字段的 fail-closed错误。adapter 改收最小 provider observation input，不再读取完整 `WaitRecordRow` 或决定 Host expiry。删除 `_stale_status_or_none` 与 Fins `_wait_boundary_lost` 的独立裁决。owner tests 增加 past/equal/future/none/invalid boundary × poll ready/not-ready/error × callback/manual parity matrix；验证 claim -> poll -> resolve、callback endpoint -> resolve、late result、cancel race、restart/poller retry，且 invalid boundary 不写业务 `LOST`。
- **修复风险（低/中/高）**: 高；会修改 wait state machine、callback status contract、poll adapter port 与 late-result policy。
- **严重程度（低/中/高/严重）**: 高

### 02-未修复-高-RunnerEvent 的 type/data 判别关系只存在于测试与 adapter 私有映射

- **入口/函数**: `AsyncRunner.call(...)` -> `Agent._consume_runner_event(...)`
- **文件(行号)**: `dayu/engine/contracts/runner_events.py:298`、`dayu/engine/contracts/runner_events.py:313`、`dayu/engine/contracts/runner.py:21`、`dayu/engine/runners/openai/non_stream_parser.py:94`、`dayu/engine/runners/openai/sse_parser.py:101`、`dayu/engine/agent.py:1309`、`tests/engine/test_runner_event_contract.py:28`
- **Semantic fact or contract involved**: 每个 `RunnerEventType` 唯一对应哪个 `RunnerEventData`，以及 malformed Runner extension event 是否能推进 Agent 状态机。
- **Correct owner**: Engine public `RunnerEvent` contract；构造时应 derive 或校验 discriminant/data pairing，Agent ingestion 应 fail closed。
- **Where ownership drifted**: `RunnerEvent` dataclass 不校验 pairing；SSE/non-stream parser 各自维护 class -> type mapping；完整闭集映射只在测试文件；Agent 实际按 `data` 的 `isinstance` 分派而忽略 `type`。
- **输入场景**: public/custom `AsyncRunner` 返回 `RunnerEvent(type=RUNNER_CONTENT_DELTA, data=RunnerDoneData(STOP), ...)`。
- **实际分支**: Agent 进入 `RunnerDoneData` 分支，设置 `done_seen` / finish reason；后续可按正常完成路径产出 final answer，而事件的公开 type 明明声明为 content delta。
- **预期行为**: malformed discriminated union 应在 `RunnerEvent` 构造或 Agent ingress 被拒绝并转成 typed provider/runner protocol failure，不能被解释为成功终止。
- **实际行为**: public contract 允许矛盾 event；具体 adapter 的私有 factory 恰好生成正确 pairing，但替换 Runner 或测试替身可绕过，Agent 用另一套隐式 owner 解释 data。
- **直接证据**: `RunnerEventData` union 与 `RunnerEvent` 字段定义无 `__post_init__`（`runner_events.py:298-327`）；唯一完整 `RUNNER_EVENT_TYPE_TO_DATA` 位于测试（`test_runner_event_contract.py:28-45`）；non-stream 和 SSE 分别实现 `_make_event` / `_event_type_for`（`non_stream_parser.py:94-117`、`sse_parser.py:101-144`）；`AsyncRunner` 是 runtime-checkable public protocol（`runner.py:21-49`）；Agent 的消费分支按 data class 展开，type 只用于外围事件记录，不拥有分派（`agent.py:1309-1577`）。
- **影响**: malformed/custom Runner 可把错误、delta 或 done 事件错解为另一种状态，最坏产生错误成功 answer；同时新增 event type 需要同步两个 parser、Agent 和测试 registry。
- **为什么 local-minimum design 会失败或变贵**: 当前“内置 adapter 都通过私有 factory”只是局部正确，公开扩展 contract 没有承诺同一 invariant；测试反而成了生产 schema registry。
- **建议改法和验证点**: 在 Engine contract 提供单一 event factory 或 `RunnerEvent.__post_init__` pairing validator，所有 adapter 复用；Agent ingress 对无效 pairing typed fail closed。删除 parser/test 中重复映射。owner tests 遍历全部 event type/data pair，并明确构造 `DELTA + RunnerDoneData`、`DONE + protocol error data` 等负例；验证 SSE、non-stream、custom Runner、异常/取消/正常完成路径。
- **修复风险（低/中/高）**: 中；contract 收紧会暴露现有 fake/custom Runner 违约，但不应保留兼容分支。
- **严重程度（低/中/高/严重）**: 高

### 03-未修复-中-CANCEL_REQUESTED 时刻被 propagation token 的稍后时刻覆盖

- **入口/函数**: `cancel_run(...)` / `cancel_session_runs(...)` -> active worker token -> Engine `RunCancelledData` -> Host ingest closeout
- **文件(行号)**: `dayu/host/admission.py:1778`、`dayu/host/durable/run_transition.py:3927`、`dayu/host/command.py:628`、`dayu/host/command.py:1619`、`dayu/host/dispatch.py:694`、`dayu/engine/agent.py:2454`、`dayu/host/engine_ingest.py:1425`、`dayu/host/durable/run_transition.py:4289`
- **Semantic fact or contract involved**: 用户取消请求被 Host durable accepted 的 canonical `requested_at`。
- **Correct owner**: committed `CANCEL_REQUESTED.occurred_at` EventLog fact；Engine/token 只观察传播，不应重定义用户请求时刻。
- **Where ownership drifted**: admission 在事务内用 Host clock 写 canonical event；commit 后 cancellation token 又以 `datetime.now(UTC)` 生成第二个 requested time；Engine 回显该值；Host ingest 已读取 linked canonical event，却仍把 Engine 值写入 `ATTEMPT_CANCELLED` / `RUN_CANCELLED` payload。
- **输入场景**: cancel transaction 在 `t0` commit，传播因调度/锁等待在 `t1 > t0` 才写 token，Engine 在 `t2` 收口。
- **实际分支**: `CANCEL_REQUESTED.occurred_at=t0`，terminal payload 的 `requested_at=t1`。
- **预期行为**: terminal cancel payload 应引用/投影 `CANCEL_REQUESTED` 的 canonical发生时刻；传播接受时间可另作为 diagnostic `accepted_at`，不能覆盖请求事实。
- **实际行为**: 同一 Run 的 canonical facts 对“请求发生时间”给出两个值，且时间差随进程调度变化。
- **直接证据**: admission `self.clock.now()` 进入 `CancelActiveAttemptInput.occurred_at`（`admission.py:1794-1811`），EventLog 使用该值（`run_transition.py:3944-3966`）；command 在 commit 后调用 registry（`command.py:661-675,1619-1634`）；`_HostCancellationToken.request_cancel` 写新的 wall clock（`dispatch.py:761-771`）；Engine 将 token time 放入 `RunCancelledData`（`agent.py:2454-2468`）；Host ingest 读取 `cancel_requested` row（`engine_ingest.py:1425-1435`）却把 `data.requested_at` 传入 closeout（`1436-1453`）；terminal payload持久化该字符串（`run_transition.py:4289-4299,4338-4349`）。
- **影响**: audit、trace、terminal payload 与 canonical cancel intent 不一致，取消延迟分析、SLA 与事件重放无法确定哪一个 requested time 是真源。
- **为什么 local-minimum design 会失败或变贵**: token 为 Engine 提供取消观察很方便，但把 token 的本地传播时间复用成业务请求时刻，使 Host 明明已经读取 owner fact仍接受下游回显。
- **建议改法和验证点**: terminal closeout 从 linked `CANCEL_REQUESTED.occurred_at` 派生 requested time；Engine/token time 删除或降级为传播诊断。删除 ingest 对 `data.requested_at` 的 canonical写入依赖。owner tests 注入 `t0 != t1`，覆盖 cancel_run、cancel_session_runs、Engine terminal、watchdog terminal、synthetic EOF/custom worker，断言所有 durable requested time 与 cancel event 同源。
- **修复风险（低/中/高）**: 中；涉及 Engine cancel event contract 与 Host terminal payload，但不应改变状态迁移结论。
- **严重程度（低/中/高/严重）**: 中

### 04-未修复-中-compactor repair/retry trigger 由 attempt 序号猜测并与 policy fact 冲突

- **入口/函数**: `run_compaction_operation(...)` -> `_prepare_compactor_proposal(...)` -> `_compactor_runner_call_manifest_body(...)`
- **文件(行号)**: `docs/host/design.md:2779`、`dayu/host/compaction_operation.py:619`、`dayu/host/compaction_operation.py:633`、`dayu/host/compaction_operation.py:746`、`dayu/host/compaction_operation.py:1122`、`dayu/host/compaction_operation.py:1378`、`tests/host/test_compaction_operation.py:721`
- **Semantic fact or contract involved**: runner-call trigger 是 proposal 初次调用、semantic repair，还是 execution retry。
- **Correct owner**: compaction operation state 与上一 `CompactionAttemptRejected.failure_category/next_policy_decision`；runner-call manifest 只持久化这个 typed intent。
- **Where ownership drifted**: operation 已知道上一 attempt 是 proposal execution failure、quality rejection 或 hard-threshold rejection，但 manifest helper只接收 ordinal；所有 attempt > 1 统一写 `context_compaction_retry_attempt`。
- **输入场景**: attempt 1 产生 `QUALITY_CHECK_REJECTED`，policy 允许 semantic repair，attempt 2 再次调用 compactor。
- **实际分支**: loop 记录 `repairable=True` / `RETRY_SEMANTIC_REPAIR` 后递增 attempt；manifest 只看 `compaction_attempt_number=2`，写 `context_compaction_retry_attempt`。
- **预期行为**: quality/budget semantic rejection 后的下一 call 应写 `context_compaction_repair_attempt`；proposal execution failure后的重试应按明确 policy 写 retry；两者不能由 ordinal替代。

- **为什么 local-minimum design 会失败或变贵**: ordinal 只能表达“第几次”，不能表达“为什么再调用”；实现丢掉已经存在的 typed policy fact，再从偶然顺序反推业务语义。
- **建议改法和验证点**: 把 next-attempt intent 作为 operation loop typed state，由 prior failure category/policy decision 产生，并显式传给 recorder/manifest；建立 Host-owned `RunnerCallKind` / `RunnerCallTriggerReason` contract与合法组合 validator，删除 `run_input`、`engine_ingest`、`compaction_operation` 的重复字符串。tests走真实两-attempt路径：quality reject -> repair、execution error -> retry、hard-threshold reject -> policy-defined repair、cancel -> 无 next call；断言 rejected fact、manifest、hot payload和 Tool Trace 一致。
- **修复风险（低/中/高）**: 中；会修改 compaction operation/manifest contract和相关 reconstruction tests。
- **严重程度（低/中/高/严重）**: 中
