## Findings

### 1-未修复-中-单文件80%覆盖率可能存在不足风险

- **位置**: §8.5 Coverage-supporting owner cases、§9.2 单文件 coverage
- **问题类型**: 测试缺口 / open question 未收敛
- **当前写法**: Plan §8.5 列出 coverage-supporting cases 覆盖 `resolve_docling_device_name`、`_plan_conversion_attempts`、`build_docling_pdf_pipeline_options`、`build_docling_pdf_converter`/`_resolve_backend_class`、`_build_attempt_converter`、`_build_docling_document_stream`，并声明"若不足 80%，只能增加同一文件内对现有分支的测试，禁止为了 coverage 改 production"
- **反例/失败场景**: `docling_runtime.py` 共 668 行。核心 owner tests 主要覆盖 `convert_pdf_bytes_with_docling`→`run_docling_pdf_conversion`→callback 路径（约 150 行），而 `build_docling_pdf_converter`（约 50 行）、`build_docling_pdf_pipeline_options`（约 60 行）、`_resolve_backend_class`（约 28 行）、`_is_windows_cuda_available`（约 16 行，含 `torch` lazy import）、`_should_prefer_docling_parse_first_on_windows`（约 10 行）以及各类异常分支（如 `DoclingRuntimeInitializationError`、`ImportError` 分支、`ValueError` 路径）的总行数可能超过 134 行（20% 阈值）。修复改动只有 3 行的 code diff，但 coverage 目标要求覆盖大量未修改的既有分支。若 coverage-supporting cases 执行后仍不足 80%，implementation agent 需要在同一文件补更多测试，但 plan 未给出此时的具体回退策略（除了"禁止改 production"）
- **为什么有问题**: 修复的动机是修复 3 行 bug，但 coverage 门禁要求覆盖整个 668 行文件中的 ~534 行。这可能导致 implementation agent 花大量时间在非修复相关的测试编写上，且若真的无法达标，实现会卡住。Plan §10 的风险表未列入"80% coverage 不可达"这一 risk
- **直接证据**: 
  - `docling_runtime.py` 668 行
  - `pytest --cov=dayu/documents/docling_runtime.py --cov-report=term-missing` 当前覆盖率未知（无现有 test file）
  - Plan §8.5: "若上述 owner cases 仍不足 80%，只能增加同一文件内对现有 `docling_runtime.py` 分支的测试"——这暗示 plan 本身不确定 §8.5 的 cases 是否足够
- **影响**: implementation agent 在 coverage 不达标时可能被迫扩 scope 补测试，或面临"改 production vs 放弃 coverage"的两难
- **建议改法和验证点**: 在 plan §10 风险表增加一行："80% coverage 不可达 → 保持当前最高 coverage 百分比，记录 missing lines，交由总控裁决；不因此修改 production 或放宽门禁"。或在 plan 接受前，先在当前 HEAD 上用 minimal placeholder tests 估算 coverage 天花板
- **修复风险**: 低（仅 plan 文本补充）
- **严重程度**: 中

### 2-未修复-低-证据run下载全量pipeline可能超出单文档证据需求

- **位置**: §9.4 独立 production CLI + 真实 Docling evidence
- **问题类型**: 范围漂移 / 过度验收标准
- **当前写法**: `dayu-cli download --base <fresh-workspace> --ticker 0700 --forms Q3 ...` 运行全量 Q3 download + conversion pipeline，然后 `dayu-cli process --document-id fil_cn_54602897a720227b36458950300dffda20b5cd66` 精确消费目标文档
- **反例/失败场景**: 0700 Q3 可能有多个 document（从 evidence 可知至少有一个 failed document plus possibly others）。`dayu-cli download --forms Q3` 会下载并 Docling 转换所有 Q3 文档，创建完整的 download workspace。若 provider 返回了新的 Q3 文档或已有文档的 PDF 内容变化，这些文档也会被转换并产生新的 Docling JSON。虽然 plan 明确说"不重做或裁决 DL-F12～F14、HK 分类、Oracle/readiness"，但全量 pipeline 运行本身就会产生新的 conversion artifact。若其中某个文档失败（非 target），implementation agent 可能被迫排查，导致 scope creep
- **为什么有问题**: plan 的目标是验证修复生效，核心证据只需要"目标 document 的 conversion 不再出现 closed-file 错误"。`dayu-cli process --document-id` 单独执行即可覆盖 conversion 路径（因为 `ProcessCnDoclingConversionRunner` 会调用 `convert_pdf_bytes_with_docling`）。先跑 `download` 再跑 `process` 固然更接近 production 路径，但 download 阶段会触发全部 Q3 文档的 conversion，引入不必要的变量。如果 provider 不可用或返回了意外数据，可能导致证据收集受阻
- **直接证据**:
  - Plan §9.4: `dayu-cli download --ticker 0700 --forms Q3 ...` — 全量 download pipeline
  - Plan §9.4 裁决规则: "download 与 process 均 exit 0；目标文档 downloaded" — 要求 download 整体成功，不仅 target
  - Plan §10: "provider 不再返回冻结的 0700 Q3 → 使用既有 0066 Q2 作为替代" — 已考虑 provider 不可用，但未考虑 download 中非 target 文档引入的额外变量
- **影响**: evidence collection 可能因非 target 文档的无关问题受阻，或产生超出需要的 conversion artifact
- **建议改法和验证点**: 考虑将 evidence run 的最小范围定为仅 `dayu-cli process --document-id <target>` 配合手动准备的 PDF bytes（若 process 命令支持从已有 source artifact 读取）。如果 production `dayu-cli download` 路径的端到端验证是必需的，在 §10 增加"非 target 文档 conversion failure 不影响 target evidence 验收"的明确豁免规则
- **修复风险**: 低（仅 plan 文本或 evidence 步骤调整）
- **严重程度**: 低

### 3-未修复-低-core owner tests 通过 fake converter 绕过了真实 Docling converter 构造路径

- **位置**: §8.4 Core owner tests — "factory 只替换 `build_docling_pdf_converter`"
- **问题类型**: 测试缺口
- **当前写法**: Core owner tests 使用 recording converter/factory 替换 `build_docling_pdf_converter`，使 `_build_attempt_converter` 拿到 fake converter，再通过 fake converter 的 `convert(stream)` 记录 stream identity
- **反例/失败场景**: 如果真实 `build_docling_pdf_converter`（或它调用的 `build_docling_pdf_pipeline_options`、`_resolve_backend_class`）在 converter 构造过程中以某种方式缓存或引用了 stream 或 stream 相关状态，这个耦合不会被 core owner tests 发现。不过，根据当前代码审查，这些函数只涉及 converter options/backend class 映射，不接触 stream。因此这个风险在当前代码下是理论性的
- **为什么有问题**: core owner tests 只验证了 stream 重建的正确性，未验证真实 Docling converter 拿到独立 stream 后的完整行为。虽然 §8.5 的 coverage-supporting tests 会单独测试 `build_docling_pdf_converter` 等函数，但它们不会把真实 converter 构造与 stream 生命周期组合测试。这个 gap 由 §9.4 的真实 evidence run 弥补
- **直接证据**:
  - Plan §8.4: "factory 只替换 `build_docling_pdf_converter`，使真实 `_plan_conversion_attempts -> _build_attempt_converter -> run_docling_pdf_conversion -> convert callback` 保持在测试路径中"
  - `_build_attempt_converter` (line 464-507) 调用 `build_docling_pdf_converter(...)` 构造 converter
- **影响**: 低；核心 contract（stream identity 独立）已通过 fake converter 验证；真实 converter 集成由 §9.4 evidence run 覆盖
- **建议改法和验证点**: 无需修改 plan。在 implementation closeout 中明确说明"real converter integration 由 evidence run 覆盖，core owner tests 只验证 stream lifecycle contract"
- **修复风险**: 不适用（不修改 plan）
- **严重程度**: 低

## Overcoupling Check

Plan 不引入新的抽象、factory、profile、schema、protocol、shared mutable state 或跨层引用。修复是纯局部的（在 callback 内移动一行构造代码），不改变任何 public signature。无过度耦合。

## Overengineering Check

Plan 只做最小的 stream 构造位置移动 + docstring，没有新的 helper、builder、wrapper、migration 或 generalization。无过度设计。

## Optimal-solution Check

Plan 的方案（在 callback 内每次重建 `DocumentStream(BytesIO(raw_bytes))`）是直接、最简单的修复。替代方案如：
- 在 converter 不关闭 stream 的前提下 seek(0) 复用：依赖第三方行为，不可靠
- 在 `run_docling_pdf_conversion` 内管理 stream 生命周期：会改变该函数的公开语义（它当前只关心 converter 调度，不关心 stream）
- 在 process runner 层补偿：语义 owner 错误，且其他 caller 不受保护

当前方案是最优路径。
