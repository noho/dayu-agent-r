## Findings

### 01-未修复-[低]-plan 未要求在透传边界更新 `run_cn_download_stream_impl` 的 Raises docstring

- **位置**: S1 slice（plan 第 36/38 行）与 `dayu/fins/pipelines/cn_download_workflow.py:88-90`（该函数 docstring 的 Raises 段现仅列 `ValueError`、`OSError`）
- **问题类型**: 契约缺失 / 最佳实践偏离
- **当前写法**: amendment 使 `SourceIntegrityPreflightError` 经设计从 `run_cn_download_stream_impl` 显式传播（"该边界必须在一般 filing failure 投影前原样透传 typed preflight"），但 plan 的 S1 修改清单只提 except 子句与测试，未要求同步该函数 docstring 的 Raises 段
- **反例/失败场景**: 实施 Agent 严格按 plan 加 `except SourceIntegrityPreflightError: raise` 后，该函数的公开异常契约与其 docstring 不符；单 filing 侧两个 owner（`run_cn_download_single_filing_stream:159`、`_commit_cn_filing_assets_batch` Raises 段）均已声明同一 typed raise，唯独新透传边界不声明，违背 AGENTS.md"函数必须提供完整中文 docstring，至少包含参数、返回值、异常"的硬约束
- **为什么有问题**: 本次修改恰好触及该函数的异常契约本身；docstring 缺口会让下游调用方（`CnPipeline.download_stream`、测试作者、后续 reviewer）无法从边界文档得知 typed 透传是设计行为而非泄漏
- **直接证据**: `cn_download_workflow.py:88-90` Raises 段现状；plan 第 36–38 行未列 docstring 更新；对照 `cn_download_filing_workflow.py:159` 已声明同一异常。附带既有缺口：同函数 `:342` 已传播 `SourceIntegrityRevisionConflictError` 而未声明（既有松散，可一并补齐但不强制扩大）
- **影响**: 实施产物违反编码硬约束的 docstring 条款 / 边界契约不自述，后续 review 需返工
- **建议改法和验证点**: 在 S1 fix 中把 `SourceIntegrityPreflightError`（可连同已传播的 `SourceIntegrityRevisionConflictError`）写入 `run_cn_download_stream_impl` docstring 的 Raises 段；验证点为 code re-review 时检查该 Raises 段与实际传播一致
