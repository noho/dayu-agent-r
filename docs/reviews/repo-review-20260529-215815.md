### 1-未修复-高-dispatch `drain_loop` 静默吞掉所有非 `CancelledError` 异常

- **入口/函数**: `HostDispatchScheduler._drain_loop`
- **文件(行号)**: `dayu/host/dispatch.py:1935-1945`
- **输入场景**: dispatch 处理过程中发生持久化异常（如 durable store corruption、schema mismatch）。
- **实际分支**: 裸 `except Exception` 捕获所有异常，仅记录 WARNING 日志后 sleep 一段时间继续循环。
- **预期行为**: 持久性故障应向上传播或触发 scheduler 的 fail-close 语义，让上层感知到不可恢复错误。
- **实际行为**: 无限重试循环，每次记录 WARNING 后 sleep `dispatch_poll_interval_seconds`，故障被永久隐藏。
- **直接证据**:
  ```python
  # dispatch.py:1935-1945
  except Exception as exc:
      _LOGGER.warning(
          _LOG_DRAIN_LOOP_UNEXPECTED_EXCEPTION,
          self._host_handle_id,
          exc.__class__.__name__,
          exc_info=True,
      )
      if not self._closed:
          await asyncio.sleep(
              self._local_execution.dispatch_poll_interval_seconds
          )
  ```
- **影响**: 持久性故障无法被上层感知，调度器持续空转。如果结合 `drain_once` 的 `while not self._queue.empty()` 循环，可能在重放持久化异常时导致 CPU 空转。
- **建议改法和验证点**: 区分可恢复异常与不可恢复异常；对 `HostDurableError` 等持久性异常应 fail-close scheduler 或向上传播；验证点：模拟 durable store 损坏后 dispatch loop 的行为。
- **修复风险（中）**: 需要仔细定义哪些异常可恢复、哪些应终止，避免过度终止导致可用性下降。
- **严重程度（高）**:

### 5-未修复-高-durable 层无 WAL checkpoint 管理

- **入口/函数**: `configure_connection_pragmas`
- **文件(行号)**: `dayu/host/durable/transaction.py:384`
- **输入场景**: 持续写入负载下运行（大量 EventLog append、state 更新）。
- **实际分支**: WAL 模式在连接建立时启用，但整个 durable 层没有调用 `PRAGMA wal_checkpoint`。SQLite 默认 auto-checkpoint (1000 pages / ~4MB) 在持续写入且无并发读者时可能无限期推迟。
- **预期行为**: 应有定期或事务后 WAL checkpoint，防止 WAL 文件无界增长。
- **实际行为**: WAL 文件可能无界增长，导致磁盘空间耗尽。进程崩溃后重启时 WAL 重放可能很慢。
- **直接证据**: 全仓 `grep` 无 `wal_checkpoint` 调用。
- **影响**: 持续写入下磁盘空间耗尽风险；崩溃后慢启动恢复。
- **建议改法和验证点**: 添加定期或 post-transaction WAL checkpoint（如每 N 次写入后 `PRAGMA wal_checkpoint(PASSIVE)`），或调整 `wal_autocheckpoint` pragma。验证点：长时间写入后 WAL 文件大小是否受控。
- **修复风险（低）**: PASSIVE checkpoint 不阻塞读写，风险很低。
- **严重程度（高）**:

### 6-未修复-中-ToolCallAggregator `setdefault` 导致跨 index 的 id 重映射被静默忽略

- **入口/函数**: `ToolCallAggregator.feed` → `_resolve_index`
- **文件(行号)**: `dayu/engine/runners/openai/tool_call_aggregator.py:230-250`
- **输入场景**: 流式 tool call delta 序列中：(1) 第一个 delta 带 `id="call_abc"` 但无 `index` 字段，(2) 后续 delta 带 `index=0` 和 `id="call_abc"`。
- **实际分支**: 第一个 delta 经 `_resolve_index` 分配合成 index（如 -1），并设置 `_index_by_id["call_abc"] = -1`。第二个 delta 的 `index=0` 使 `_resolve_index` 立即返回 0，跳过 id 查找。在 `feed()` 中 `self._index_by_id.setdefault("call_abc", 0)` 因 key 已存在而保持旧值 -1。同一个 tool_call_id 的两个 partial 分别位于 index -1 和 index 0 且互不相通。
- **预期行为**: 当后续 delta 携带已映射 id 的新 index 时，应将旧 partial 合并到新 index。
- **实际行为**: 两个独立 partial 被创建，`finalize()` 时可能产生 `tool_call_missing_name` fatal error 或 arguments 缺失的残缺 tool call。
- **直接证据**:
  ```python
  # line 230: _resolve_index returns 0 immediately
  delta_index = delta.get("index")  # 0
  if _is_tool_call_index(delta_index):  # True
      return delta_index  # returns 0, id lookup skipped
  # line 250:
  self._index_by_id.setdefault(delta_id, index)  # NO-OP, already -1
  ```
- **影响**: 非标准流式 provider 下可能产生残缺或丢失的 tool call。OpenAI 标准 provider 通常首帧即带 `index`，故实际触发概率低。
- **建议改法和验证点**: 将 `setdefault` 改为直接赋值 `self._index_by_id[delta_id] = index`；添加逻辑：当 `delta_id` 已映射到不同 index 时，将旧 partial 内容合并到新 index 并删除旧 partial。验证点：构造上述 delta 序列并验证 `finalize()` 输出正确。
- **修复风险（中）**: 涉及 partial 合并逻辑，需要仔细处理 name 拼接、arguments buffer 迁移和 provider_state 合并。
- **严重程度（中）**:

### 未覆盖的高风险区域

1. **并发 recovery race condition** (未测试): 两个进程同时执行 startup recovery scan 并尝试恢复同一孤儿 Run/Attempt，可能产生重复 dispatch record 或不一致的 EventLog 序列。`test_recovery_multiprocess.py` 只测试了一个 live 进程不恢复的场景，未测试两个进程同时恢复的竞争。
