## Findings

### [已修复，待复查] Finding 1 — `last_run_input_build_trace_by_run` 无界增长，存在内存泄漏风险

**严重程度**: 中
**文件**: [dayu/host/_run_harness.py:166-169](dayu/host/_run_harness.py#L166-L169)

`LocalRunHarness.last_run_input_build_trace_by_run` 是一个 `dict[str, RunInputBuildTrace]`，每次 `start_run` 都会向其中追加条目，但没有任何淘汰或清理机制。在长时间运行的 Host 进程中（如多轮 session 服务），该 dict 会持续增长，每个 `RunInputBuildTrace` 还持有完整的 `tuple[RunInputTraceItem, ...]`，每个 item 含 `text` 字段，内存占用不可忽略。

**建议**: 添加容量上限或 LRU 淘汰策略；或将 trace 存储到有生命周期管理的 store 中。

---

### [已修复，待复查] Finding 2 — `_format_tool_fact` 使用错误的 section header `"## Evidence Anchors"`

**严重程度**: 低-中
**文件**: [dayu/host/_run_input_builder.py:857-872](dayu/host/_run_input_builder.py#L857-L872)

`_format_tool_fact` 的返回值使用了 `"## Evidence Anchors"` 作为 section header，但 tool facts 应该有自己的 `"## Tool Facts"` header。当前实现中，tool facts 和 evidence anchors 都在 `_append_evidence_anchors` 中通过 `collector.include` 写入，渲染后 tool facts 会出现在 `## Evidence Anchors` section 下，对 LLM 的语义理解产生误导。

**建议**: 将 `_format_tool_fact` 的 header 改为 `"## Tool Facts"`，或在 `_append_evidence_anchors` 中拆分为两个独立 section。

---

### [已修复，待复查] Finding 3 — `_append_recent_raw_turns` 每个 turn 重复写入 section header

**严重程度**: 低-中
**文件**: [dayu/host/_run_input_builder.py:722-759](dayu/host/_run_input_builder.py#L722-L759)

`_append_recent_raw_turns` 在 `for turn in snapshot.recent_raw_turns` 循环内，每次迭代都写入 `"## Recent Raw Turns\n{text}"`。当存在多个 recent turn 时，最终 memory block 中会出现多个 `## Recent Raw Turns` header，产生重复 section 标记。

**建议**: 将 section header 提取到循环外部，只写入一次；各 turn 内容拼接在 header 之后。

### [已修复，待复查] Finding 4 — `InMemoryConversationMemoryStore.apply_patch` 对非 SESSION scope 的 `ScopeClearPatch` 静默忽略

**严重程度**: 低
**文件**: [dayu/host/_conversation_memory.py:452-459](dayu/host/_conversation_memory.py#L452-L459)

`apply_patch` 中 `ScopeClearPatch` 的 match 分支只处理 `scope=MemoryScope.SESSION`，其他 scope 直接 `return`，无日志、无异常。P3 文档说明只实现 SESSION scope，但对调用方而言，传入一个非 SESSION scope 的 clear patch 会静默成功，没有任何反馈表明操作未执行。

**建议**: 对非 SESSION scope 至少记录 warning 日志，或在 docstring 中明确说明 P3 仅支持 SESSION scope、其他 scope 静默忽略。

---

### [已修复，待复查] Finding 5 — `_MemoryBlockCollector.reserve()` + `append_reserved_text()` 分离模式的隐式耦合

**严重程度**: 低
**文件**: [dayu/host/_run_input_builder.py:444-503](dayu/host/_run_input_builder.py#L444-L503)

`reserve()` 消耗预算并记录 trace，但不将文本写入 `_parts`；调用方必须随后调用 `append_reserved_text()` 才能完成写入。当前仅 `_append_older_raw_turns` 使用该模式且调用顺序正确，但该隐式两步协议没有类型或运行时保护。若未来有新调用方遗漏 `append_reserved_text()`，会导致预算已消耗但文本未写入的不一致状态。

**建议**: 考虑让 `reserve()` 返回一个 token 对象，`append_reserved_text()` 接受该 token 作为参数，从而在类型层面强制两步调用顺序。

---

### [已修复，待复查] Finding 6 — Engine 无终态事件时 memory projection 被跳过

**严重程度**: 低
**文件**: [dayu/host/_run_harness.py:241-289](dayu/host/_run_harness.py#L241-L289)

`_run_to_store` 中 `_project_run_events` 仅在 `terminal_seen=True` 时调用。若 Engine event stream 正常结束（`StopAsyncIteration`）但未产出终态事件（如引擎实现 bug），则 `terminal_seen` 保持 `False`，`USER_INPUT_ACCEPTED` 事件不会被投影到 memory，该轮用户输入将丢失。

当前 Engine 协议保证产出终态，但作为防御性设计，可在 `finally` 块中无条件投影（幂等操作，重复投影无副作用）。

总控评估：finding 动机成立，但“无条件投影”会弱化 P3 的 terminal 后投影语义。已采用替代修复：
Engine stream 正常结束但未产出 terminal 时追加 Host-owned canonical `RUN_FAILED`，错误码
`engine_stream_ended_without_terminal`，再触发 memory projection。这样用户输入与中性 failure summary
都进入下一轮 memory，同时 RunResult / EventLog / memory 仍保持 terminal 同源。
