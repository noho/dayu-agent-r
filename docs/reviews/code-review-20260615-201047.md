### 01-未修复-低-CLI 与 Service 重复 `_log_verbose` / `_bounded_payload_keys` helper

- **入口/函数**: `dayu/cli/commands/fins.py:_log_verbose`、`dayu/cli/commands/fins.py:_bounded_payload_keys`、`dayu/service/fins_direct.py:_log_verbose`、`dayu/service/fins_direct.py:_bounded_payload_keys`
- **文件(行号)**: `dayu/cli/commands/fins.py:676-673`、`dayu/service/fins_direct.py:883-880`
- **输入场景**: 所有 VERBOSE 日志调用和 DEBUG payload key 日志调用。
- **实际分支**: `fins.py` 和 `fins_direct.py` 各自独立实现 `_log_verbose`（相同逻辑，不同模块 logger）和 `_bounded_payload_keys`（完全相同）。
- **预期行为**: `CLAUDE.md` 编码硬约束要求"数据处理、存储、工具调用职责必须分离，重复逻辑必须抽取"、"模块间依赖最小化"。
- **实际行为**: 两个模块各自持有 `_log_verbose` 和 `_bounded_payload_keys` 副本。`_VERBOSE_LEVEL_NAME` 和 `_LOG_PAYLOAD_KEY_LIMIT` 常量也各写一份。
- **直接证据**: `fins.py:81-82`、`fins.py:676-687`、`fins.py:665-673`；`fins_direct.py:41-42`、`fins_direct.py:883-894`、`fins_direct.py:872-880`。两处 `_bounded_payload_keys` 实现逐字相同。
- **影响**: 不影响正确性；增加维护耦合——若 `VERBOSE` level name 或 key limit 需调整，必须同时改两处。
- **建议改法和验证点**: 将 `_bounded_payload_keys` 提取到 `dayu.runtime.log` 或新建 `dayu.runtime.log_helpers`；`_log_verbose` 因绑定各模块 logger 实例，可保留各自实现，但常量 `_VERBOSE_LEVEL_NAME` 和 `_LOG_PAYLOAD_KEY_LIMIT` 应统一到一处。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 02-未修复-低-CLI 层 exception 日志与 Service 层 exception 日志重复

- **入口/函数**: `dayu/cli/commands/fins.py:_consume_fins_direct_events`、`dayu/cli/commands/fins.py:_wait_for_terminal_handling_sigint`
- **文件(行号)**: `fins.py:627-633`、`fins.py:582-587`
- **输入场景**: Service event stream 失败或 cancel request 失败时。
- **实际分支**: CLI `_consume_fins_direct_events` 在 except 块中调用 `_LOGGER.exception(...)` 后 `raise`；异常传播到 `run_fins_direct_command` 后被 `except Exception` 再次捕获并 `render_cli_error`。Service 层 `stream_job_events_until_terminal` 也有 `_LOGGER.exception` 调用。
- **预期行为**: CLI 是 UI adapter，职责是渲染错误给用户；内部日志应由 Service 层（有 job_id / command_name 上下文）统一负责。
- **实际行为**: CLI 层 `_consume_fins_direct_events` 和 Service 层 `stream_job_events_until_terminal` 对同一异常各记一条 `_LOGGER.exception`，产生两条含重叠上下文的日志。cancel path 同理。
- **直接证据**: `fins.py:627-633`（CLI exception log + raise）；`fins_direct.py:569-575`（Service exception log + raise）。两者记录同一异常。
- **影响**: 不影响正确性；日志审计时同一失败出现两条记录，增加噪声。
- **建议改法和验证点**: 移除 CLI 层 `_consume_fins_direct_events` 和 `_wait_for_terminal_handling_sigint` 中的 `_LOGGER.exception` 调用，仅保留 `raise`；Service 层已有完整上下文日志。验证：stream failure / cancel failure 测试仍通过，日志输出不出现重复条目。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 03-未修复-低-默认日志测试依赖间接断言，未显式验证 logger level

- **入口/函数**: `tests/cli/test_fins_commands.py:test_fins_direct_default_log_does_not_pollute_progress_output`
- **文件(行号)**: `test_fins_commands.py:373-387`
- **输入场景**: 不带 `--verbose` / `--debug` 的 Fins download 命令。
- **实际分支**: 测试断言 `"Fins direct command start" not in captured.out`——验证 VERBOSE 消息未出现。
- **预期行为**: 测试应直接验证 logger level 为 INFO（或至少验证 `set_level_from_flags` 被调用并生效），而非仅靠"消息不存在"间接推断。
- **实际行为**: 若 `set_level_from_flags` 未被调用（例如 main 路径变更），logger 默认 WARNING，VERBOSE 消息同样不会出现——测试仍通过，但原因不同。
- **直接证据**: `test_fins_commands.py:384`——断言基于消息缺失，不基于 level 配置。
- **影响**: 测试覆盖间接；若 main 路径变更移除 `set_level_from_flags` 调用，测试不会捕获回归。
- **建议改法和验证点**: 增加对 `runtime_log.set_level_from_flags` 被调用的 spy 断言（类似 `test_arg_parsing.py` 中的做法），或显式 caplog 断言 logger level 为 INFO。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
