### F-DS-01: `try_acquire_new_work_lease` RECOVERING 状态下 period-reconcile 可能错误排除 lease

**Severity**: Low（当前 production 路径未触发，但语义有缺口）

**Direct evidence**:

- `dayu/host/session_attachment.py:512-516`：
```python
if (
    record.state is _AttachmentLifecycleState.RECOVERING
    and record.new_work_lease_count == 0
):
    return None
```
- `dayu/host/session_attachment.py:519-535`：`active_read_write_session_ids()` 只返回
  `state is ACTIVE and access_mode is READ_WRITE`
- `dayu/host/dispatch.py:3480-3493`：`_owned_session_reconciliation_loop` 调用
  `reconcile_owned_sessions_once`，后者先取 `active_read_write_session_ids()` 快照再逐
  Session 申请 work lease。

**分析**: 当前 production 路径安全，因为：

1. `active_read_write_session_ids()` 在 RECOVERING 时返回空，periodic reconciliation
   不会对接 RECOVERING 状态的 record。
2. RECOVERING 状态唯一可申请 lease 的路径是 `_acquire_recovery_work_lease`（由
   `_AttachmentAllocation.acquire_recovery_work_lease()` 调用），它会先 `acquire_lease`，
   增加 `new_work_lease_count` 到 1 后再返回。
3. Target recovery scanner 在 lease 已持有时调用 `run_queue_promotion_with_lease`，
   不走 `try_acquire_new_work_lease`。

**但是**：`try_acquire_new_work_lease` 的 docstring 声称"尝试为 ACTIVE RW Session 获取
pre-start/new-work lease"，但代码实际上在 `RECOVERING + count > 0` 时也返回 lease。
这意味着该方法的名义 contract（仅限 ACTIVE）与实际行为（也覆盖 RECOVERING-with-lease）
存在语义漂移。

此外，语义上存在一个理论路径：如果在 `_AttachmentAllocation.activate()` 被调用前，
某个外部 caller（如测试 helper 直接调用 `try_acquire_new_work_lease`）能在 recovery
lease 被释放后、activate 前的极小窗口获得 lease。当前代码中 `activate` 前有
`recovery_lease.release()`（`open_host.py:1061`），但 recovery lease 释放与 `activate`
之间没有显式 barrier。如果在此窗口内 reconciliation loop 调用
`try_acquire_new_work_lease`，会成功（因为 record 已是 ACTIVE），这实际是正确行为
——activate 前的 promotion 仍是 valid new work。

**Root cause**: `try_acquire_new_work_lease` 的 RECOVERING-with-count 分支是 recovery
半状态的 gate-keeping 实现细节，但它被标记为 public Protocol 方法，语义 contract
（`ACTIVE RW`）与实际 state machine 不完全一致。

**Semantic owner**: `HostSessionAttachmentRegistry` 拥有 this lease 判定逻辑。

**Fix boundary**: 方法 docstring 应明确 RECOVERING 分支是 recovery-only path，行为不变量
是"只有已经在执行 target recovery 的同一 attachment 可以从 RECOVERING 取得额外 lease"。
不改变行为。

**Owner test needed**: 直接测试 RECOVERING state 下 `try_acquire_new_work_lease` 在
`new_work_lease_count == 0` 时返回 `None`，在 `> 0` 时返回非空 lease（当前缺少直接单测）。

**影响**: 低。production path 不触发，period reconciliation 也无法接触 RECOVERING
records。不影响正确性，仅影响 code readability 与 contract clarity。

def _operation(transaction: HostTransaction) -> _GovernanceStageResult:

**Retraction**: F-DS-02 撤回，其"跨 transaction"前提为事实错误。controller counterexample
recheck 确认该路径不存在反例。

## Controller counterexample recheck

Controller 要求对 `_project_state`（`proactive_compaction.py:356-617`）的
`len(requested_rows)==0 → return _absent_state()` 早期返回路径做精确阻断分析，
并复核 F-DS-02 的事务声明。以下为逐场景直接控制流证据。

### 关键前提：单次 `run_write` 事务边界

`_run_pre_start_governance`（`dispatch.py:1540-1819`）将所有 governance 阶段的 durable
read（projection）与 write（prepare）封装在同一个 `_operation` closure 内，由单次
`self._transaction_runner.run_write(_operation)`（line 1819）执行。`transaction` 参数在
整个 closure 中始终指向同一个 write transaction。因此 **不存在**"projection read 与
prepare write 在两个不同事务中"的 TOCTOU 窗口。F-DS-02 的该前提为事实错误，已撤回。

### 场景 1：完全无 compaction request、但有孤立 terminal/rejection/compactor manifest

**路径**（`proactive_compaction.py:373-401`）：

```python
# 第一遍：只扫描 REQUESTED rows → 全部非 REQUESTED row 被 line 378 的 continue 跳过
for row in rows:
    if row.event_type != CONTEXT_COMPACTION_REQUESTED:  # ← 孤立 terminal/rejection/manifest
        continue                                         # ← 全部跳过
    # ... REQUESTED 处理（本场景不命中）...

if len(requested_rows) == 0:       # ← line 398: TRUE（无任何 REQUESTED row）
    return _absent_state()          # ← line 399: 立即返回 ABSENT
```

**阻断位置**: line 399 的 `return` 在执行第二遍扫描（line 427）**之前**返回。因此孤立
terminal/rejection/manifest rows 的 `operation_id` 从未被检查。

**判决**：**非反例**。孤立 rows 的 `operation_id` 在 `operation_owners` 中无对应项，
它们无法归因到任何已存在的 operation。没有 operation 就没有需要 fail-close 的"现有操作"。
`_decision_from_state(ABSENT) = CREATE_NEW` 是唯一正确决策。

从 plan 约束验证：
- Plan lines 700/782 "malformed fail closed, 不追加第二request"：不存在第一 request，
  追加的是**首个**（非第二）request。不违反。
- Plan line 782 "fallback不能安全构造时Run按现有governance failure终结"：此处不适用，
  因为没有需要 fallback 的现有 operation。

**残余风险**：若有孤立 `CONTEXT_COMPACTION_FAILED` row（operation_id 无对应 REQUESTED），
CREATE_NEW 会静默忽略该历史。该 row 是 durable schema 不一致的外部证据（写入 FAILED 但
未写入 REQUESTED），但 `_project_state` 的设计意图是投影已存在的 operations，不应把
无法归因的孤立 row 解释为 operation。这符合 plan 语义。

### 场景 3：有合法 reactive request 但另有 unknown-operation row

### 场景 4：malformed request 无法安全确定 trigger owner 时 `_earliest_requested_event_id` 是否会误取 reactive id

**分析路径**（`proactive_compaction.py:310-318` + `861-872`）：

```python
# read_proactive_compaction_projection
except (HostDurableError, TypeError, ValueError) as exc:
    operation_id = _earliest_requested_event_id(rows)  # ← line 311


def _earliest_requested_event_id(rows):                 # line 861
    for row in rows:
        if row.event_type == CONTEXT_COMPACTION_REQUESTED:
            return row.event_id                         # ← 第一个 REQUESTED row 的 id
    return None
```

该函数遍历 rows 并按 `event_sequence` 顺序（由 `_read_operation_rows` 保证升序）返回
第一个 `CONTEXT_COMPACTION_REQUESTED` row 的 `event_id`，**不区分** proactive/reactive。

**理论反例路径**：存在一个 reactive REQUESTED（低 event_sequence），随后一个 proactive
REQUESTED（高 event_sequence）。proactive REQUESTED 的 payload 在
`validate_context_compaction_requested_payload`（line 381）中 raise `ValueError`
（例如 `frozen_material_list_digest` 非法）。异常在 line 381 立即传播：
- `requested_rows` 可能为空（若该 malformed proactive 是唯一的 proactive REQUESTED）
- 或可能非空（若前面有 valid proactive REQUESTED 已加入）
- 无论哪种，异常直接跳到 `except` handler → `_earliest_requested_event_id(rows)` 返回
  **第一个** REQUESTED row 的 event_id

若第一个 REQUESTED 是 reactive，则 `operation_id` 为 reactive event_id。

**但这在 production 中不可达**：

1. Proactive REQUESTED 由 `_run_pre_start_governance` 的 `_prepare_compact_before_dispatch`
   写入，发生在 dispatch **之前**。其 `event_sequence` 必然小于后续 Engine 处理中写入的
   reactive REQUESTED。proactive 始终是第一个 REQUESTED。

2. `validate_context_compaction_requested_payload` 对 proactive payload 做 strict schema
   校验（`_require_exact_fields`，line 264 of context_events.py），且 `build_context_compaction_requested_payload`
   使用 keyword arguments，当前所有 proactive call sites（`dispatch.py:2567-2597`）传入
   完整必填字段。仅当 durable corruption（bit flip 或恶意修改 SQLite）会导致 payload
   不通过校验，此时已是数据损坏，fail-closed 是正确的。

**判决**：**非反例**。Production 路径中 proactive REQUESTED 的 `event_sequence` 始终最小，
`_earliest_requested_event_id` 始终返回 proactive event_id。Malformed payload 场景不可达
（除非 durable corruption），此时 fail-closed 安全。

### F-DS-02 复核结论

见上文"关键前提：单次 `run_write` 事务边界"。F-DS-02 撤回，不成立。
