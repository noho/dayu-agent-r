## Findings

### 1-未修复-中-`_scope_appender()` 静默退化为 `PlainRunEventAppender` 与 `_resolve_attempt_appender()` 的 fail-fast 语义不对称

- **入口/函数**: `LocalRunHarness._scope_appender()` / `LocalRunHarness._resolve_attempt_appender()`
- **文件(行号)**: `dayu/host/_run_harness.py:588-606` vs `dayu/host/_run_harness.py:541-586`
- **输入场景**: durable 路径下, `ToolRuntimeOwnerScope` 的 ContextVar 因代码路径错误或重构失误未正确设置 active appender, 而 `_scope_appender()` 被调用 (当前仅 `_compact_or_fail()` 使用此 helper)
- **实际分支**: `_scope_appender()` 在 `active_tool_runtime_appender()` 返回 `None` 时走到 line 606: `return PlainRunEventAppender(event_store=self.event_store)`, 静默退化为无 fencing 的裸 `EventLog.append`
- **预期行为**: durable 路径上, 所有 ToolRuntime canonical fact append 必须走 fencing-aware 路径; 若 ContextVar 未设置应 fail fast, 与 `_resolve_attempt_appender()` 的 durable 分支 (line 574: `raise RuntimeError(...)`) 保持一致
- **实际行为**: `_scope_appender()` 静默返回 `PlainRunEventAppender`, 后续 `TOOL_RESULT_TRUNCATED` / `TOOL_CURSOR_*` / `TOOL_FETCH_MORE_*` 事件绕过 `verify_owner` CAS 检查写入 EventLog
- **直接证据**:
  - `_scope_appender()` line 603-606: ContextVar 为空时直接返回 `PlainRunEventAppender`, 无任何 `is_durable` 检查或异常抛出
  - `_resolve_attempt_appender()` line 562-577: durable 路径下 ContextVar 为空时明确 `raise RuntimeError`
  - 两个 resolver 对同一场景 (durable + 无 owner scope) 的行为不一致
- **影响**: 当前所有 `_scope_appender()` 调用点 (`_compact_or_fail()`) 均在 `async with _attempt_owner_scope` 内, 实际不会触发此路径。但如果未来重构 `_compact_or_fail()` 的调用链、或新增其他使用 `_scope_appender()` 的 helper 而上下文管理不当, TOOL 事件将静默绕过 fencing, 导致 stale owner 写入新 run 的 EventLog, 破坏 attempt isolation 不变量。影响等级为中而非高, 因为当前无触发路径
- **建议改法和验证点**:
  1. `_scope_appender()` 增加 `is_durable` 检查: 当 `self.is_durable` 为 `True` 且 ContextVar 无 active appender 时应 `raise RuntimeError`, 与 `_resolve_attempt_appender()` 一致
  2. 或至少加 `_LOGGER.warning` 记录 "durable path scope_appender fallback", 使生产环境可观测
  3. 补充测试: durable 路径、无 owner scope 时调用 `_scope_appender()` 应 fail fast
- **修复风险（低）**: 仅收紧 `_scope_appender()` 的 fallback 条件, 不影响当前正确调用路径
- **严重程度（中）**: 当前无触发路径, 但构成 latent fencing bypass risk; 设计不对称性会误导未来维护者

### 2-未修复-低-`_verify_run_id_matches()` 将 run_id 不匹配映射为 `OWNER_MISMATCH` 混淆两类不同语义的失败

- **入口/函数**: `AttemptScopedRunEventAppender._verify_run_id_matches()`
- **文件(行号)**: `dayu/host/_attempt_supervisor.py:383-418`
- **输入场景**: ToolRuntime 持有的旧 `AttemptScopedRunEventAppender` (绑定 run_id=R1) 在 attempt 边界 race 期间被用于写入新 run (run_id=R2) 的 EventLog
- **实际分支**: `draft.run_id != self.owner_context.run_id` (line 398) → 抛出 `AttemptFencingError(reason=AttemptFencingReason.OWNER_MISMATCH)` (line 411-418)
- **预期行为**: run_id mismatch 是内部不变量违反 (appender 绑定的 run 与 draft 声称的 run 不一致), 与真正的 owner fencing (token hash / fencing_token 不匹配) 属于不同故障类别。两者应有不同的错误类型或至少不同的 `reason` 值, 使上层恢复路径能区分 "我被 fenced 了" 和 "内部状态不一致"
- **实际行为**: `AttemptFencingError(reason=OWNER_MISMATCH)` 同时覆盖两种场景: (a) store 层 `verify_owner()` 返回的 token hash 不匹配 (真 fencing); (b) `_verify_run_id_matches()` 检测到的 run_id 不匹配 (内部违反)。上层 `_handle_owner_lost()` (line 1228-1315) 对 `AttemptFencingError` 统一处理, 将两类失败都视为 "owner lost → diagnostic close"
- **直接证据**:
  - line 398-418: `_verify_run_id_matches` 对 run_id 不匹配使用 `AttemptFencingReason.OWNER_MISMATCH`
  - `_run_state_store.py` 中 `_diagnose_fence()` 对 store 层 CAS 失败也返回 `OWNER_MISMATCH`
  - 两个不同语义的失败共用同一 `reason` 枚举值, 上层无法区分
- **影响**: 如果 `_verify_run_id_matches()` 触发 (极端边界: ToolRuntime cursor 跨越 attempt 边界), 上层会将其当作 "被 fenced" 处理并走 `_handle_owner_lost` → `append_terminal_and_close`。但实际的 `owner_context` 可能仍然有效, 错误地将健康 attempt 标记为 terminal。影响为低, 因为触发场景 (ToolRuntime cursor race across attempt boundary) 在当前架构中极难出现
- **建议改法和验证点**:
  1. 为 `_verify_run_id_matches()` 引入独立的 `AttemptFencingReason.RUN_ID_MISMATCH` 枚举值, 与 store 层的 `OWNER_MISMATCH` 区分
  2. 或使用独立异常类型 (如 `AttemptRunIdMismatchError` 继承 `AttemptFencingError`), 让上层可选择性地处理
  3. 补充测试: `_verify_run_id_matches` run_id 不匹配时抛出的异常类型/reason 应与 store 层 OWNER_MISMATCH 可区分
- **修复风险（低）**: 新增枚举值或异常子类, 不影响现有 catch `AttemptFencingError` 的上层代码 (子类仍被捕获)
- **严重程度（低）**: 触发场景极端边界, 实际影响小; 但语义混淆降低代码可维护性

## Residual Risk

1. **`_scope_appender()` 静默退化缺少测试覆盖**: 当前测试 (`test_phase8_tool_runtime_fencing.py`) 覆盖了 ToolRuntime owner scope 正常路径, 但未测试 `_scope_appender()` 在 durable + ContextVar 未设置时是否应 fail fast。如果后续重构改变了 `_compact_or_fail()` 的调用时机, 缺少 regression test 作为安全网。

2. **`_fetch_canonical_events_for_session()` O(N×M) 全 EventLog 扫描** (`dayu/host/_conversation_memory_durable.py:331-364`): repair 路径对每个缺失 session 做全 EventLog 分页扫描并 filtering by `session_id`。当 EventLog 行数 N 很大且缺失 session 数 M 也大时, 时间复杂度为 O(N×M)。当前标记为非热路径 (仅 recovery 时触发), 且已有分页机制限制单批加载量, 实际风险可控。若未来 recovery 触发频率上升 (如多进程频繁 crash), 应考虑按 `session_id` 建索引或直接走 `fetch_events_by_session` API。

3. **`_SCHEMA_VERSION` 硬编码无迁移机制** (`dayu/host/_conversation_memory_durable.py:538, 606-607`): `_decode_snapshot()` 对版本不匹配的 snapshot 直接抛 `ValueError`, 导致旧版本快照被静默跳过, `repair_missing_session_snapshots()` 将尝试重建 (若 session 已 terminal) 或放弃 (若 session 仍在进行)。当前 `_SCHEMA_VERSION = 1` 为首版, 暂无迁移需求。如果后续版本升级, 缺少 migration 机制意味着旧快照只能丢弃后重建, 不能原地升级。

4. **`_verify_run_id_matches()` 的 OWNER_MISMATCH 与 store 层 `OWNER_MISMATCH` 语义重叠无测试区分**: 当前测试未覆盖 `AttemptFencingError` 的 `reason` 字段在两类场景下的可区分性。如果未来 `_handle_owner_lost()` 对不同 reason 做差异化处理, 缺少 baseline 测试可能导致回归。

5. **多进程 stress 测试覆盖有限** (`tests/host/test_phase8_multiprocess_stress.py`): 虽然覆盖了并发 CAS 冲突场景, 但 stress 测试的时间窗口和进程数受 CI 环境限制, 极端并发下的 lease expiry race、renew loop 与 CAS 竞争交互可能未被充分暴露。生产环境首次部署时应监控 `AttemptFencingError` 发生率和 renew loop 异常日志。
