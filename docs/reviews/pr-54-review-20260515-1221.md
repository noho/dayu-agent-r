- **输入场景**: `_start_worker` 内部 `_closeout_worker_startup_timeout` 自身抛异常（例如 `EventLogStore.append_event` 写入失败）
- **实际分支**: `_start_worker` 的 `except` 块调用 `_closeout_worker_startup_timeout`，该调用抛异常 -> 异常传播到 `_dispatch_one` 的 `except Exception` 块 -> 再次调用 `_closeout_worker_startup_timeout`
- **预期行为**: 每个 dispatch record 的 terminal closeout 只执行一次
- **实际行为**: 第一次 closeout 的事务已回滚（异常导致），第二次 closeout 看到相同前置状态重新执行。功能上安全但浪费且掩盖了第一次失败的根因
- **直接证据**: `dispatch.py` 第 636-639 行和第 507-510 行都有 `_closeout_worker_startup_timeout` 调用
- **影响**: 正常路径无影响；异常路径下 terminal closeout 会被重复尝试，第一次失败的根因被吞掉
- **建议改法和验证点**: 让 `_start_worker` 的异常处理在调用 `_closeout_worker_startup_timeout` 后 `return "timed_out"` 而非让异常传播到外层。使用 safe wrapper 捕获 closeout 异常
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 15-未修复-低-_attempt_terminal_payload / _run_terminal_payload 对 SUCCEEDED/FAILED 状态的可选字段不区分 None 语义

- **入口/函数**: `_attempt_terminal_payload`, `_run_terminal_payload`
- **文件(行号)**: `dayu/host/durable/run_transition.py` (1881-1911, 1932-1963)

- **严重程度（低/中/高/严重）**: 低
