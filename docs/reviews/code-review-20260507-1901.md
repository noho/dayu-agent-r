## Findings

### 1. [低] [已修复，待复查] Engine context overflow 后 Host 未防御性处理正常终态

`dayu/host/_run_harness.py:373` — `_run_to_store` 内层循环中，`CONTEXT_COMPACTION_REQUESTED` 事件会设置 `overflow_trigger_seen = True` 并 `continue`。但如果 Engine 随后发送的终态不是 `RUN_FAILED(context_compaction_required)`（例如正常的 `FINAL_ANSWER` 或其他 `RUN_FAILED`），内层循环走正常终态路径 `return`，`overflow_trigger_seen` 虽然为 `True` 但永远不会被检查。

结果：EventStore 中会留下孤立的 `CONTEXT_COMPACTION_REQUESTED` 事件，没有后续的 `CONTEXT_COMPACT_COMPLETED` / `CONTEXT_COMPACT_FAILED` / `CONTEXT_ATTEMPT_RETRYING`。这打破了事件序列的闭合语义。

**触发条件**：Engine 侧 bug 或意外行为。当前 Engine 实现中 `CONTEXT_COMPACTION_REQUESTED` 必然后跟 `RUN_FAILED(context_compaction_required)`，所以实际不会触发。但 Host 作为治理层应假设 Engine 可能不完美。

**建议**：在内层循环处理正常终态时，若 `overflow_trigger_seen` 为 `True`，记录 warning 日志或追加一条 Host-owned 的 `CONTEXT_COMPACT_FAILED(INTERNAL_ERROR)` 事件以闭合序列。

**修复说明**：Host 已在 `CONTEXT_COMPACTION_REQUESTED` 后遇到非 `context_compaction_required` 终态时，先追加 Host-owned `context_compact_failed(reason=internal_error)` 事实闭合 compact 序列，再保留 Engine 原终态收口；新增测试覆盖 `context_compaction_requested -> final_answer`，订阅可结束且 run 有终态。

### 2. [低] [已修复，待复查] `ContextBudgetSnapshot` 使用全零占位值

`dayu/engine/agent.py:861-865` — 当 Runner 报告 context overflow 时，Agent 构造的 `ContextCompactionRequestedData.budget_state` 使用 `prompt_tokens=0, completion_tokens=0, total_tokens=0`。

这是设计选择：Runner 层在 HTTP error 时没有 usage 数据。但 Host 侧 `HostContextCompactRequestedData.before_token_estimate` 依赖自己的 estimator，所以信息未丢失。只是 `budget_state` 字段在 overflow 场景下永远是零，对下游诊断价值有限。

**建议**：可在 docstring 中补充说明该字段在 overflow 场景下为 placeholder。

**修复说明**：已在 `ContextBudgetSnapshot` 中文 docstring 与 Engine README 中说明 HTTP overflow 无 usage 时 `0/0/0` 是占位，Host compact before / after 诊断来自 Host estimator。

### 3. [低] [已修复，待复查] `_extract_accepted_start_input` 错误消息不够精确

`dayu/host/_run_harness.py:1023,1035` — 所有验证失败路径复用同一个 `_ERROR_CURRENT_USER_INPUT_SINGLE_MESSAGE` 常量。P4 已将入口扩展为"多条 leading SystemMessage + 一条末尾 UserMessage"，但错误消息仍沿用旧的"单条消息"措辞，对调用方调试不友好。

**建议**：区分"无消息""多条 UserMessage""非 System/User 消息类型""System 出现在 User 之后"等不同错误路径，或至少更新常量措辞。

**修复说明**：入口校验错误码已改为 P4 契约口径：若干 leading `SystemMessage` + 末尾唯一非空 `UserMessage`；关键错误路径区分空输入、末尾不是 user、多 user、历史 assistant/tool 混入与空 user，并更新测试断言具体错误消息。

### 4. [信息] [接受不修] `event_count` 跨 retry attempt 累加

`dayu/host/_run_harness.py:313` — `event_count` 在 `_run_to_store` 外层 `while True` 循环内共享，retry 后继续累加。最终日志中的 `event_count` 包含所有 attempt 的事件总数，不能区分各 attempt 的事件量。

这不是 bug（日志仅为诊断），但如果需要精确诊断每次 attempt 的事件数，可考虑在每次外层循环开始时 reset 或分别记录。

**接受说明**：总控接受当前实现口径；`event_count` 记录同一 run 后台任务跨 retry attempt 的总 Engine 事件数，是总事件数诊断字段，不要求按 attempt 拆分。

### 5. [信息] [已修复，待复查] `_INTERNAL_ECHO_MARKERS` 部分标记较宽泛

`dayu/host/_event_translation.py:56-74` — 标记列表中 `"tool facts"`、`"evidence anchors"` 等英文短语是子串匹配，理论上可能在正常中文回答中被误命中（如"这些工具事实上…"包含 "tool facts" 子串）。

但实际风险很低：(1) 匹配是 `content.lower()` 子串匹配；(2) 正常 LLM 回答不太会包含这些精确短语；(3) 误命中的后果仅是返回 filtered 占位内容，用户可重试。

**修复说明**：已收窄 marker：内部段落按 `## Host Memory`、`## Tool Facts` 等标题匹配，内部 provenance 按 `tool_fact_id=`、`cursor_fingerprint=`、`source_event_cursor=` 等字段形式匹配；新增正常回答包含 `tool facts` 自然语言短语不被过滤的测试。

## 未发现的问题类型

- **架构约束违反**：Engine 不 import Host，Host 不反向依赖，`dayu.runtime` 未被污染。分层边界正确。
- **类型安全**：所有 dataclass 使用 `frozen=True, slots=True`，联合类型封闭，无 `Any` 或无类型参数。
- **逻辑正确性**：compact coordinator 的"变短 + 保真"双重校验逻辑正确；retry limit 边界正确；`_extract_accepted_start_input` 的消息形状验证正确。
- **异常处理**：compact 分支异常通过 `_append_compact_exception_failure` 收口为 Host-owned terminal，不泄漏。
- **测试覆盖**：P4 新增测试覆盖了 overflow retry、retry limit、tool fact 合并、trace cache 淘汰、caller system prompt 顺序、非法入口拒绝、echo 过滤、token estimator 等关键路径。
