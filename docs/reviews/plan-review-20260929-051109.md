### 02-未修复-低-document 控制名集合将有三处字面表达，纯契约入口与完整性 walker 的成员可能失同步
- **位置**: §唯一 owner 与纯规划契约 → storage 纯判定入口句；§文件范围 → "storage 私有常量只读取复用，不改…`_fs_source_integrity.py` 的发布/完整性行为"
- **问题类型**: 语义所有权 / 过度保守边界
- **当前写法**: 新 `asset_filename_contract.py` "复用 `_normalize_filename` 与 `_SOURCE_META_FILENAME`、`_IDENTITY_DESCRIPTOR_FILENAME`…判断原样单组件合法性、document 目录保留控制名"；同时禁止改动 `_fs_source_integrity.py`，生产白名单不含该文件。
- **反例/失败场景**: "哪些名字是 document 目录保留控制名"的**成员判定**目前以内联集合形式写在 `_fs_source_integrity.py:669` 与 `:856` 两处。新契约入口落地后成员判定将出现第三处表达。将来 storage 布局新增控制名（如历史上出现过 `_PROCESSED_META_FILENAME`、`_download_rejections.json` 这类扩展）时，只改 walker 不改契约（或反之），planner 将放行会与控制名相撞的 original——恰是 MiMo F1 的失败类原样复发：admission 通过、转换付费、发布阶段损坏/回滚。
- **为什么有问题**: CLAUDE.md 语义所有权要求同一业务事实只有一个 source of truth；plan 钉了"复用常量"却没钉"集合成员单源"，把成员语义留在两个内联字面量与一个新契约共存的状态。
- **直接证据**: `_fs_source_integrity.py:667-672`（declared name 校验内联 `{_SOURCE_META_FILENAME, _IDENTITY_DESCRIPTOR_FILENAME}`）、`:856`（物理树校验同样内联集合）；plan 该句原文；CLAUDE.md 语义所有权条款。
- **影响**: 控制名集合后续演进失同步；F1 类碰撞回归；owner 级测试若只测契约侧则发现不了漂移。
- **建议改法和验证点**: 最小改法——契约导出保留名 frozenset，并加 owner 级一致性测试断言契约集合 == walker 使用的集合（不改 walker 行为）；或允许一次行为不变的 walker 改造改为消费契约导出集合（相应扩白名单一句）。验证点：新增控制名的演练（改一处看测试是否红）。
- **修复风险（低/中/高）**: 低

### 03-未修复-低-material 逐文件存在性/普通文件错误的 typed 归属未钉死，非 CLI 路径仍会落 `unexpected_runtime`
- **位置**: §typed 失败和跨入口 handoff → reason 映射表 `MISSING_FILES` 行；§admission 检查清单句
- **问题类型**: 契约缺失 / open question 未收敛
- **当前写法**: 封闭 reason 含 `MISSING_FILES`（映射"复用"既有 code），admission 检查计数 1..100、重复、命名、控制名、碰撞、长度、可转换资格；未提逐文件存在性/普通文件检查的归属。既有 `FinsUploadUsageCode.MISSING_FILES` 文案是 "create/update 上传必须提供 --files"（`ingestion_runtime.py:1049`，空 files 语义）；同枚举另有 `FILE_NOT_FOUND`/`FILE_NOT_REGULAR`（`:1051-1052`，带去路径化 label 的文案，filing admission 在 `:1311-1313` 已 typed 使用）。
- **反例/失败场景**: (a) 实施 Agent 把"文件不存在"映射进 `MISSING_FILES`，用户得到错误文案"必须提供 --files"；(b) 不映射：tool/SEC/CN 直调路径上不存在的文件经 `_validate_source_files` 抛 `FileNotFoundError`（`docling_upload_service.py:1610-1611`）进入 pipeline catch-all → `UNEXPECTED_RUNTIME`，与本工作单"用户可修正错误不写成 unexpected_runtime"的叙事相悖（该类虽不在 O04 枚举四类内，属相邻缺口）；(c) CLI 侧既有检查保留全路径文案 `_MISSING_UPLOAD_FILE_TEMPLATE.format(path=path)`（`fins.py:1143-1145`），与 plan 自设"错误不含绝对路径"边界不一致。
- **为什么有问题**: reason 名的语义边界有两种合理读法，产生不同的 code/message/测试形态；plan 自设的路径安全与 typed 分类承诺没有覆盖这一相邻用户可修正类。
- **直接证据**: `ingestion_runtime.py:697-700,1049-1052,1311-1313`；`docling_upload_service.py:1592-1613`；`fins.py:1137-1147`；plan 映射表与 admission 句原文。
- **影响**: 实施 Agent 跑偏（错映射或漏映射）；tool/facade 路径同类输入错误体验不一致；review 对 `MISSING_FILES` 验收口径争议。
- **建议改法和验证点**: plan 钉一句"`MISSING_FILES` = upsert 空 files"；并明确逐文件存在性二选一——纳入 admission 复用 `FILE_NOT_FOUND`/`FILE_NOT_REGULAR`（文案已带安全 label），或显式登记为本 WU 外残余（注明非 CLI 路径现状）。验证点：tool 路径传不存在文件的 typed 断言或残余登记。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-低-filing 与 material 的重复规范路径检查将各持一份实现，plan 未指定共享关系
- **位置**: §admission "按规范绝对路径的 exact 值拒绝重复"句 vs §数量真源句 "filing 静态 admission 的既有限额是独立契约"
- **问题类型**: 语义所有权 / 重复逻辑
- **当前写法**: material planner 自查规范路径重复（exact 值）；filing 保留其静态 admission 的既有重复路径检查（`_fins_upload_path_identity` case-sensitive exact string，`ingestion_runtime.py:1224-1239`）与 `_normalize_fins_upload_path`（`:1215-1221`）。两条 code 收敛到同一 closed code（`DUPLICATE_FILE_PATH` 复用）、同一文案投影，但"什么算重复规范路径"的判定实现将是两份。
- **反例/失败场景**: 未来路径规范化语义调整（如 Windows 大小写盘符、尾点空格策略）时只改一处，filing 与 material 对同一输入给出不同 typed 结果；或实施 Agent 为求一致把 filing admission 意外重写，触碰"独立契约"边界。

- **直接证据**: `ingestion_runtime.py:1215-1239`（filing 路径规范化与重复判定）、plan 两处原文；A17。
- **影响**: 低概率语义漂移；实施边界判断成本。规则本身极简，影响面有限。
- **建议改法和验证点**: plan 补一句共享关系（推荐：路径规范化/重复判定 helper 归资产规划 owner，filing 静态 admission 消费同一 helper，或明确声明 filing 侧保持独立实现并在 owner 测试中对拍两侧行为）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
