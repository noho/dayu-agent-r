## Findings

### F20-RR4-MIMO-001-未修复-高-post-segment evidence gate把pre-compact trigger误当成actual accepted snapshot sizing
- **位置**: binding goal success signal 2；plan §5.2 formal gate、§5.3 R2/R3/R4 state machine、Slice 2 validation。
- **问题类型**: 语义所有权错误 / 状态机漏洞 / 验收契约不一致。
- **当前写法**: goal `:52-54`与plan `:345-351`都要求“每个actual accepted snapshot对应的下一ordinary boundary”满足
  `soft <= predicted < hard`且action=`compact_soft_threshold`，并把该fact作为accepted truth能否计入B2的证据门。plan没有冻结
  sizing stage，也没有区分触发compaction的pre-accept ordinary candidate与接受replacement后真正准备dispatch的post-compact
  candidate。
- **反例/失败场景**: R2的ordinary candidate达到soft并产生`compact_soft_threshold`，随后operation接受replacement。Host会重新
  assembly完整candidate并以`stage=post_compact`执行sizing；只要低于hard，normal或soft都必须`allow_dispatch`，不可能再次
  `compact_soft_threshold`。同理R3第二次accepted后，R4若满足计划要求的operation count仍为2，其ordinary action必须是
  `allow_dispatch`；若为`compact_soft_threshold`则必然开启第三operation并使reconnect predicate失败。由此：
  - 若实现读取pre-compact ordinary fact，predicate可以PASS，但该candidate不包含刚accepted的replacement，不能证明actual snapshot；
  - 若实现读取真正post-compact fact，candidate正确绑定accepted truth，但action必为`allow_dispatch`或hard block，无法满足当前predicate；
  - 若把predicate应用到第二次accepted后的R4，则`compact_soft_threshold`与“operation count仍为2”互斥。
- **为什么有问题**: Host design明确把`ordinary`与`post_compact`设为不同semantic owner。把两者合并会再次用错误阶段的正确数值替代
  actual snapshot事实，违反本项目“逻辑/数据同源”和唯一语义owner约束。post-segment gate虽不再声称external interception，但当前
  contract仍无法同时证明“两次合法trigger”“accepted replacement实际进入dispatch candidate”和“R4同truth reconnect”。
- **直接证据**:
  - `docs/host/design.md:3728-3734`：ordinary soft → `compact_soft_threshold`；post_compact normal/soft →
    `allow_dispatch`，hard → `block_hard_threshold`。
  - `dayu/host/dispatch.py:1886-2009`：pre-compact candidate以`ContextSizingStage.ORDINARY`估算并在soft时追加trigger budget fact。
  - `dayu/host/dispatch.py:2539-2567`：accepted compact追平Memory后重新以`ContextSizingStage.POST_COMPACT`准备同一Run。
  - `dayu/host/dispatch.py:2619-2687,2815-2883`：post-compact重新构造完整candidate；allow路径在manifest后提交其独立budget fact再启动
    Attempt，hard路径在dispatch前fail closed。
  - plan `:376-384`：R2/R3是两个proactive targets；R4只有operation count仍为2才能证明reconnect。
- **影响**: implementation Agent必须猜测该选哪条budget fact。选ordinary会产生“trigger正确但actual snapshot未证明”的伪PASS；选
  post_compact会让所有成功链被错误拒绝；对R4应用当前规则则使replacement+reconnect角色在逻辑上不可满足。正式provider成本可能在
  一个不可验收的状态机上被消耗。
- **建议改法和验证点**: 将证据门拆成两个owner级predicate并同步修正goal/plan：
  1. 每个目标operation的trigger predicate：唯一`stage=ordinary` budget fact与pre-compact manifest/candidate、
     `CONTEXT_COMPACTION_REQUESTED`及同operation accepted/failed terminal exact linkage；要求soft区间与
     `compact_soft_threshold`。它只证明trigger，不声称包含accepted replacement。
  2. 每个accepted replacement的consumption predicate：`CONTEXT_COMPACTED`后Memory catch-up形成的唯一
     `stage=post_compact` manifest/candidate/budget fact必须直接绑定该accepted truth；要求`predicted < hard`且
     action=`allow_dispatch`，并与随后`RUN_STARTED`/`ATTEMPT_STARTED`/dispatch identity相等。hard时应由现有Host owner在dispatch前
     block并如实seal。
  3. R4单独要求`stage=ordinary`、candidate消费第二次accepted truth、action=`allow_dispatch`且operation count仍为2；若soft触发第三
     operation则按既有needs-more branch处理。
  corruption/self-test必须交换ordinary/post_compact refs、用pre-compact digest冒充accepted consumption、把R4 compact action冒充
  reconnect时二值FAIL。
- **修复风险（中）**: 不需要新增产品或wrapper，只需按已有canonical stage/action owner修正goal、evidence projection和self-test。
- **严重程度（高）**: 当前formal success path与owner状态机不能同时成立。
