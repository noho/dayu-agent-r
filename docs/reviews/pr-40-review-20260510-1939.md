### 1-未修复-严重-AttemptFencingError 被 execute_tool_call 的 catch-all 吞掉，fencing 信号链断裂

- **入口/函数**: `InMemoryToolRuntime.execute_tool_call`
- **文件(行号)**: `dayu/host/_tool_runtime.py:516`
- **输入场景**: durable 路径下，tool 执行期间 owner lease 过期或被 recovery 替换；`AttemptScopedRunEventAppender.append()` 在 `_append_tool_result_truncated` / `_append_tool_cursor_issued` / `_append_tool_fetch_more_*` 等 7 个 helper 中抛出 `AttemptFencingError`
- **实际分支**: `execute_tool_call` 的 `try` 块内调用 `_append_tool_result_truncated` 等方法 → `AttemptScopedRunEventAppender.append()` 抛 `AttemptFencingError` → 被第 516 行 `except Exception as exc:` 捕获 → 返回 `ToolFailedOutcome(error="tool_runtime_failed")`
- **预期行为**: `AttemptFencingError` 应透传到 harness 层，由 `_run_to_store` 的 `except AttemptFencingError` 分支捕获并走 `_handle_owner_lost` 原子 terminal + close 路径
- **实际行为**: fencing 异常被伪装成普通 tool 失败 outcome，harness 看到正常 tool failure，engine 继续用 stale owner 迭代，后续 harness 自身的 fact append 也可能 fence，导致级联 missed signals
- **直接证据**:
  - `execute_tool_call` 第 420 行 `try:` 开始，第 516 行 `except Exception as exc:` 捕获所有异常
  - 7 个 `_append_*` 方法（行 1158、1203、1235、1278、1324、1359、1400）都调用 `_resolve_appender().append()`，durable 路径下解析为 `AttemptScopedRunEventAppender`，其 `append()` 方法（行 224-260）在 owner CAS 失败时抛 `AttemptFencingError`
  - `_tool_runtime.py` 未 import `AttemptFencingError`，无 dedicated re-raise 分支
- **影响**: 整个 P8 fencing 设计的核心信号链被切断。owner-lost 检测依赖 `AttemptFencingError` 从 scoped appender 透传到 harness 的 `_handle_owner_lost`，该路径被 bypass 后：(1) stale owner 继续写入；(2) 原子 terminal + close 路径不触发；(3) Run 可能通过非原子路径收口，破坏 "fencing 失败时 EventLog 不残留 stale terminal RunEvent" 不变量
- **建议改法和验证点**: 在 `execute_tool_call` 的 `except Exception` 之前插入 `except AttemptFencingError: raise`，需要在 `_tool_runtime.py` 顶部 import `AttemptFencingError`。验证：(1) 运行 `test_phase8_attempt_fencing.py` 和 `test_phase8_tool_runtime_fencing.py` 确认 fencing 信号正确透传；(2) 检查 harness 的 `_run_to_store` 中所有 `except AttemptFencingError` 分支是否被正确命中
- **修复风险（低/中/高）**: 低（两行改动，不影响非 fencing 路径）
- **严重程度（低/中/高/严重）**: 严重

### 2-未修复-中-recover_stale_attempts 的 scan 与 process 之间存在 TOCTOU 窗口

- **入口/函数**: `AttemptSupervisor.recover_stale_attempts`
- **文件(行号)**: `dayu/host/_attempt_supervisor.py:772-791`
- **输入场景**: 多进程并发 recovery scan；进程 A 列出候选后、处理前，进程 B 已经把同一 attempt 推到终态
- **实际分支**: 第 773 行在 `scan_tx` 事务内 `list_recovery_candidates` 取得候选列表；第 779 行 `for candidate in candidates` 循环中，每个候选在独立事务 `_process_recovery_candidate` 处理
- **预期行为**: 并发 recovery 应通过 CAS 正确收敛，不产生副作用
- **实际行为**: 设计上已正确处理——`_process_recovery_candidate` 内部的 `mark_stale_or_lost` 使用 `fencing_token` CAS，`rowcount==0` 时返回 `NOOP_TERMINAL`。但 scan 事务（第 773 行）在 `list_recovery_candidates` 返回后立即 commit，此时候选的 state 可能已被并发进程改变。`_process_recovery_candidate` 重新读取 state 做 CAS，所以不会产生错误写入，但可能对已经是终态的 attempt 做无意义的 CAS 尝试
- **直接证据**: `mark_stale_or_lost`（`_run_state_store.py:996-1014`）使用 `WHERE state IN ('running', 'created') AND fencing_token = ?`，终态行 rowcount==0 返回 `NOOP_TERMINAL`，无副作用
- **影响**: 功能正确，但并发 recovery scan 会产生无意义的 CAS 尝试和日志噪声；不影响收敛性
- **建议改法和验证点**: 当前实现在正确性上可接受。如需优化，可在 `_process_recovery_candidate` 入口二次检查 attempt 是否仍为非终态，但 ROI 不高。验证：`test_phase8_attempt_recovery.py` 的并发场景
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 3-未修复-中-_handle_owner_lost 抛非 AttemptFencingError 异常时 current_active_attempt 未置 None，finally 块二次 close

- **入口/函数**: `LocalRunHarness._run_to_store` 中 `_OwnerLostDuringEngineWait` / `AttemptFencingError` 分支调用 `_handle_owner_lost`
- **文件(行号)**: `dayu/host/_run_harness.py`（diff 偏移约 890-901、912-925）
- **输入场景**: `_handle_owner_lost` 内部 `append_terminal_and_close` 或 `lease_exit_stack.aclose()` 抛出非 `AttemptFencingError` 异常（如 `sqlite3.DatabaseError`）
- **实际分支**: `_handle_owner_lost` 只 catch `AttemptFencingError`（diff 约 1335 行），其它异常透传 → 调用方 `_run_to_store` 中 `current_active_attempt = None` 赋值被跳过 → 异常传播到外层 `finally` 块 → `_finish_attempt_if_durable` 对已部分清理的 attempt 再次操作
- **预期行为**: 无论 `_handle_owner_lost` 成功与否，`current_active_attempt` 都应被置 None，避免 finally 块二次操作
- **实际行为**: 异常路径下 `current_active_attempt` 保持非 None，finally 块的 `_finish_attempt_if_durable` 可能对已关闭的 `lease_exit_stack` 再次 aclose（幂等但语义不干净）或再次尝试 `close_attempt_with_diagnostic_state` CAS（可能再次失败）
- **直接证据**: diff 第 890-901 行和 912-925 行中，`_handle_owner_lost` 的 await 和 `current_active_attempt = None` 赋值在同一 try 块内，无 finally 保护
- **影响**: Run 可能卡在非终态，RunResult 为 None。不 corrupt 数据但违反 terminal 不变量
- **建议改法和验证点**: 将 `_handle_owner_lost` 调用包在 try/finally 中确保 `current_active_attempt = None`；或在外层 `_run_to_store` 的 finally 块中增加防御性 catch-all，在 `terminal_seen=False` 时写 best-effort `RUN_FAILED` terminal
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-低-_ATTEMPT_TERMINAL_STATES 缺少 STALE，_diagnose_fence 语义不精确

- **入口/函数**: `AttemptLeaseStore._diagnose_fence`
- **文件(行号)**: `dayu/host/_run_state_store.py:57-65,1125-1144`
- **输入场景**: renew / verify_owner CAS 失败，当前行状态为 STALE
- **实际分支**: `_diagnose_fence` 第 1125 行检查 `state in _ATTEMPT_TERMINAL_STATES`，STALE 不在该集合 → 落入第 1135 行 `state is not AttemptState.RUNNING` → 返回 `FENCED` + `ATTEMPT_NOT_RUNNING`
- **预期行为**: STALE 是诊断终态（`finished_at` 已写入，无出迁移），应返回 `ATTEMPT_TERMINAL`
- **实际行为**: 返回 `ATTEMPT_NOT_RUNNING`，语义暗示状态是瞬态而非终态
- **直接证据**: `_ATTEMPT_TERMINAL_STATES`（行 57-65）包含 SUCCEEDED/FAILED/CANCELLED/SUSPENDED/LOST 但不含 STALE；`_ATTEMPT_FINISHED_STATES`（行 69-80）包含 STALE
- **影响**: 诊断日志中 reason 字段语义不精确；功能上 decision 仍为 FENCED，不影响 fencing 正确性
- **建议改法和验证点**: 在 `_ATTEMPT_TERMINAL_STATES` 中添加 `AttemptState.STALE`，或在 `_diagnose_fence` 中对 STALE/RECOVERING 做单独处理。验证：现有 lease store 测试仍通过
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Residual Risk

1. **测试覆盖**: PR 包含大量新测试（`test_phase8_attempt_fencing.py`、`test_phase8_attempt_lease_store.py`、`test_phase8_attempt_recovery.py`、`test_phase8_attempt_supervisor.py`、`test_phase8_durable_invariant.py`、`test_phase8_durable_memory_recovery.py`、`test_phase8_multiprocess_stress.py`、`test_phase8_tool_runtime_fencing.py`），覆盖了 attempt 生命周期的主要路径。但 Finding 1（fencing 信号链断裂）说明 `test_phase8_tool_runtime_fencing.py` 可能未真正验证 `AttemptFencingError` 从 tool runtime 透传到 harness 的完整链路——如果测试中 tool runtime 的 append 抛出 `AttemptFencingError`，它会被 `execute_tool_call` 吞掉，测试可能只验证了 tool failure outcome 而非 harness 的 owner-lost 收口路径。
2. **CI 状态**: PR 无 CI check 报告（`no checks reported on the branch`），无法确认自动化测试是否在 CI 中运行。
3. **multiprocessing 路径**: `test_phase8_multiprocess_stress.py` 覆盖了 P8-S7 的多进程场景，但本文 review 未深挖 multiprocessing 平台层（`_multiprocess_platform.py`）的实现细节。
4. **docs 目录膨胀**: PR 新增了 20+ 个 `docs/host/phase8-*` review/plan 文档和 10+ 个 `docs/reviews/` 文档，这些是过程产物而非最终设计文档。建议在 PR merge 前清理或归档，避免 `docs/` 目录成为 dump yard。
5. **owner-lost 优先级丢弃有效 terminal**: `_next_engine_event_or_lose_owner` 在 Engine event 和 owner-lost 同时就绪时优先 owner-lost（diff 约 1233 行）。代码注释说明这是 intentional（"防止旧 owner 把已经 fenced 后到达的 stale Engine event 写进 EventLog"），但意味着 Engine 已成功产出 `FINAL_ANSWER` 时用户可能看到 `RUN_FAILED(attempt_lease_lost)`。这是 design tradeoff 而非 defect，但值得在设计文档中明确记录。
