## 逐 Finding 对照裁决

### F-01（原 高）— SEC `_try_fetch_*` 三个方法过度传播

- **原问题**: Amendment §8.4 要求三个 supplementary file-evidence helper 全部 propagation，但它们是纯 supplementary——不影响 candidate discovery/filtering/company resolution
- **修订后**: §3.4 裁决表明确三个 helper 传播到 `list_filing_files` → `sec_download_filing_workflow` 捕获 → 发出唯一 FAILED filing row → ticker workflow 继续后续 filing。不再 operation-fatal
- **直接证据**:
  - §3.4 表: "helper 原样传播到 `list_filing_files`，再到 `sec_download_filing_workflow`；当前 filing 唯一 FAILED row，后续 filing 继续"
  - §6.5: "sec_download_filing_workflow.run_download_single_filing_stream catches only the typed provider error around list_filing_files, emits exactly one FAILED filing terminal... The ticker workflow consumes that terminal row and continues later filings."
  - Controller 裁决 (line 135): "Partially accepted: empty evidence is rejected, but operation-fatal is rejected; sec_download_filing_workflow owns a single FAILED filing row."
- **结论**: **RESOLVED** — 三层 blast radius 精确定义为 filing-local FAILED，不再触发 Stop Condition 4

### F-02（原 中）— `_is_cancel_requested` RuntimeError wrap 吞 typed provider error

- **原问题**: `cn_download_workflow.py:431-434` 的 `except Exception: raise RuntimeError(...)` 会降解 `FinsDownloadProviderError`
- **修订后**: §3.1: "`_is_cancel_requested` 对 `CnDownloadCancelledError` 维持 cancelled；对 `FinsDownloadProviderError`、`OSError` 与其它异常均不字符串包装。前两者原样到 runtime 的 provider/storage 分类，其它原样到 execution 分类。"
- **直接证据**:
  - §3.1 (line 53): 明确不包装，typed 类型原样传播
  - §6.3 (line 233): "`_is_cancel_requested` does not wrap exception text. CnDownloadCancelledError preserves cancellation; FinsDownloadProviderError and OSError preserve provider/storage; every other exception propagates to runtime's execution classification."
  - §8.2: "Cancellation checker raising `CnDownloadCancelledError` remains cancelled; raising `FinsDownloadProviderError` or `OSError` preserves the exact object; raising another exception reaches runtime as execution"
- **结论**: **RESOLVED** — `_is_cancel_requested` 不再 wrap，typed exception 原样传播

### F-03（原 中）— per-candidate `except Exception` OSError 路径泄露

- **原问题**: `cn_download_workflow.py:310-316` 使用 `str(exc)` 作为 `reason_message`，OSError 可能含文件路径
- **修订后**: §3.2: "provider errors use `safe_message`; `OSError` uses a fixed storage-safe reason; all other exceptions use a fixed execution-safe reason. No document row writes `str(exc)`."
- **直接证据**:
  - §3.2 (line 60): per-candidate catch 使用 closed helper 三分支安全文本
  - §6.3 (line 234): "provider -> category-derived stable reason plus `safe_message`; `OSError` -> `storage_failed` plus fixed safe text; other -> `filing_execution_failed` plus fixed safe text"
  - §8.2: "A document-local provider failure uses `safe_message`; a path-bearing `OSError` and raw execution exception each produce fixed safe failed-row text"
  - §9 static scan: "per-candidate rows have no `reason_message=str(exc)`"
- **结论**: **RESOLVED** — per-candidate 行全部使用固定安全文本，无 `str(exc)` 泄露路径

| **Operation-fatal** | browse company HTTP/XML, browse→submissions, SC13 role, historical submissions | §3.4 裁决表 + §6.5 逐项明确；传播路径验证 ✓ |

无未归类或模糊项。Stop Condition 4 的封闭性满足。

### 2. `cn_download_workflow` operation 与 per-candidate 安全边界

**PASS.**

- Operation-terminal（4 路径: rebuild / company+discovery / outer / final cancel-check）: `CnDownloadCancelledError` → cancelled; 所有其他 `Exception` → propagate unchanged。§3.1 (line 50), §6.3 (line 231)
- Per-candidate（1 路径: per-candidate loop catch）: closed helper 三分支（provider → `safe_message`; OSError → fixed storage text; other → fixed execution text）。§3.2 (line 60), §6.3 (line 234)

- 边界不交叉：operation 异常不进入 document row；document failure 不升级为 operation failure

### 3. `_is_cancel_requested` 对 provider/OSError

**PASS.**

## 新问题扫描

对修订版全文做 adversarial scan，未发现 new material finding。以下为低严重度观察（不构成 finding，不阻塞 PASS）：

1. **4xx "Stop without consuming remaining retries" 与 SEC 行为不一致**: §6.2 要求 CN/HK 在 4xx 时立即停止。SEC downloader 的 `_execute_sec_request` 对 4xx 仍然通过完整重试循环（只是不标记 retryable）。这是 CN/HK downloader 的改进行为（4xx 不应重试），但如果是刻意的不对称设计，建议在 amendment 中注明理由。**非 blocking**。

2. **`_execute_sec_request` 自身对 4xx 的 unnecessary retries**: 此为现有行为，不在当前 scope。可作为后续 slice 的低优先级改进。

3. **Historical submissions operation-fatal 的 tradeoff**: §11 已明确承认"candidate collection precedes filing mutation, this avoids publishing a silently incomplete selection." Tradeoff 是已知且有文档记录的。**Deferred to residual risk**。
