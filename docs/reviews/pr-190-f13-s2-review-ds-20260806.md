## F1: `accepted_evidence_facts` DTO 默认 `=()` — NEEDS_FIX

**位置**: `tool_trace_analysis_contracts.py` L484

```python
accepted_evidence_facts: tuple[ResolvedCompactorEvidenceFact, ...] = ()
```

**反例**: 若未来调用方构造 `ToolTraceCompactorResponseSummary` 用于 ACCEPTED
terminal 但遗忘显式传入 `accepted_evidence_facts`，默认 `=()` 使 facts 静默丢失。
`__post_init__` 只防御 ATTEMPT_REJECTED 不得有 facts，不防御 ACCEPTED 遗漏传入。

**直接证据**: 当前唯一调用点 `_compactor_response_summaries`（rules L336）显式传入了
`accepted_evidence_facts=response.accepted_evidence_facts`，但 DTO 的 public API 不强制
此行为。`ResolvedCompactorResponseIdentity` 无默认值（resolver L430），而 summary DTO
有默认值——两处 contract 不一致。

**修法**: 移除默认值或使用 sentinel `_MISSING = object()` 并在 `__post_init__`
中校验 `accepted_evidence_facts is not _MISSING`。

**严重程度**: MEDIUM — 当前调用正确，但 public DTO 设计构成 compat 陷阱。

## F2: `ResolvedCompactorEvidenceFact` 校验与上游重复 — ACCEPTED

**位置**: `tool_trace.py` L155-179

`ResolvedCompactorEvidenceFact.__post_init__` 校验 claim 非空、refs tuple 非空且
unique。上游 `CompactAcceptedEvidenceFactV4.__post_init__`（`compaction.py` L1515-1537）
已做相同校验（`_require_non_empty` + `_require_non_empty_unique_string_tuple`）。

**评估**: 这是 defense-in-depth，Tool Trace resolver 不假设上游 parser 已完成校验。
两个 owner（compaction domain vs. Tool Trace projection）各自拥有自己的 contract
enforcement。保留。

### 最终 verdict
