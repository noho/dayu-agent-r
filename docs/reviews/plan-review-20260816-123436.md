## 1. RF1-RF4 逐项裁决

### RF1：frozen inspector 未定义 whole-kind inventory/commit 调用形状 —— **已修复**

- 原问题：`_inspect_source_kind_unguarded(requested_document_id: str)` 单一 target 轴，`list_source_integrity` 与 commit
  validator 两个 whole-kind caller 无调用约定。
- 修订落点：§6.1 冻结两种调用形状——exact-target mode（`requested_document_id=<canonical document ID>`，一次 scan 返回非空
  `target` + 完整 source-kind `inventory/shared_manifest_reasons/canonical_manifest_items`）与 whole-kind mode
  （`requested_document_id=None`、`target=None`，返回整个 source-kind payload，含空 inventory 与无法归属单一 target 的
  manifest/root facts）；inventory 与 commit validator 每个 source kind 只调用一次 whole-kind mode，并在同一 guard/batch 内消费
  单一 payload，禁止逐 document 重扫或跨 guard/batch 拼接；§11.1 补 "同一 guard/batch 中 exact-target 与 whole-kind payload 的
  inventory/shared/canonical facts 完全相等、whole-kind target is None、每 source kind 恰好调用一次" 断言；Slice 2 step 2/3/5 同步。
- 验证：修复同时解决了 RF1 的两个来源（无单一 target 的调用形状 + shared facts 跨调用一致性），且 whole-kind mode 的
  "空 inventory/不可归属 facts" 与 §6.1 末段 `SourceIntegrityPreflightError(UNSAFE_PUBLICATION)` 的触发条件自洽。

### RF2：canonical remaining items 载体歧义 —— **已修复**

- 原问题：§6.1 aggregate `canonical_manifest_items` "全部 content COMPLETE 才非空" 与 §6.2 step 5 需要的 per-non-target
  items 载体冲突，误读会使所有带 sibling 的 target-local repair 被 `CANONICAL_MANIFEST_UNAVAILABLE` 阻断。
- 修订落点：§6.1 明确单点可用性——"每个 source 的 `canonical_manifest_item` 可用性只取决于该 source 自身的 trusted persisted
  meta 与 `content_classification=COMPLETE`，不受其它 source（包括 requested target）损坏影响"，aggregate 非空条件保持不变；
  §6.2 step 5 明确 "只取同一次 exact-target inspection payload 中每个 non-target 的单点 `canonical_manifest_item`，按 canonical
  document ID 稳定排序……绝不消费 aggregate……target-local damage 会使 aggregate 为空，但不得因此丢弃 complete sibling 的单点
  canonical item"；§11.3 新增 "target content REPAIR_REQUIRED + 至少一个 complete sibling + 原 manifest 一致 → repair 成功，
  remaining items 逐项来自单点字段，aggregate 为空不得阻断或丢项"；Slice 4 step 3/5 同步。
- 验证：与 `_fs_storage_infra.py:1244-1248` 既有 per-source `FilingManifestItem.from_source_meta(meta).to_dict()` 模式一致，
  原矛盾的两个读法已被单点/aggregate 的职责切分消除。

### RF3：reset 中 UNSAFE ValueError 逃逸窄缝 —— **已修复**

- 原问题：`has_same_source_publication_identity` 对 UNSAFE 抛 ValueError 而非返回 False，`reset_source_document_for_repair`
  step 3 按布尔谓词使用时存在 raw ValueError 逃逸 → `UNEXPECTED_RUNTIME` 的窄缝。
- 修订落点：§6.2 step 3 改为 "比较前先 gate：expected 或 staged 任一为 `UNSAFE`，或任一 public status 不是 `REPAIR_REQUIRED`，
  立即抛 `SourceIntegrityRevisionConflictError`。通过 gate 后才调用 `has_same_source_publication_identity`；返回 false 同样抛
  conflict。该比较函数在 storage method 内若仍抛 `ValueError`（包括 identity/unsafe invariant 漂移），必须由 method 捕获并转换为
  同一个 path-free conflict，禁止 raw ValueError 逃逸；上述转换只包围 staged comparison，不吞掉第 1 步 invalid input
  `ValueError`"；§11.3 断言 "storage method 在比较前拒绝非 `REPAIR_REQUIRED/UNSAFE` 并把 comparison ValueError 转换为
  conflict；service 最终只投影 `SOURCE_REVISION_STALE`，不得出现 raw ValueError/UNEXPECTED_RUNTIME"；Slice 4 step 3/5 补 staged
  UNSAFE 与非 `REPAIR_REQUIRED` gate 测试。
- 验证：gate 前置 + 转换范围限定（不吞 invalid-input ValueError）同时消除了逃逸窄缝与误吞风险，与 §6.2 protocol Raises
  列表（ValueError 仅限 invalid capability/identity/expected classification）一致。

### RF4：download whole-manifest-missing 表述过宽 —— **已修复**

- 原问题：§7.2 "download whole manifest missing 必须以 typed preflight error fail closed" 的绝对表述与单 source 场景实际
  行为（`classify_source_integrity_preflight` 返回 `SelectedSourceRepairRequired` → 既有 repair 重建）不符。
- 修订落点：§7.2 改为 "存在多个实际 source、accepted selection 不是唯一 repair target，或出现非 selected repair target 时，
  whole-tree preflight 以既有 typed `SourceIntegrityPreflightError` fail closed；只有一个实际 filing 且它正是 accepted selected
  target 时，保持既有 `SelectedSourceRepairRequired` 路径，由 download reset、重新下载并通过 upsert 重建 canonical manifest。
  该单-source 行为不是把 upload rewrite 授权泛化到 download"；Slice 6 step 1 与 §11.4 补多-source/非-selected typed 拒绝与单一
  accepted selected filing 继续 repair 重建的 SEC/CN 回归（断言完成后 source/manifest COMPLETE）。
- 验证：与 `source_integrity.py:213-226`（单一 repair target 走 selected repair）与 `sec_download_workflow.py:580-590` 的既有
  行为一致；多-source 场景由 `MULTIPLE_REPAIR_REQUIRED` 闭合。

**RF1-RF4 裁决汇总：全部 已修复。**

## 2. 第二轮修订引入的新问题检查

### RF5-未修复-低-exact-target mode 每次调用对 whole source-kind 全量 inspect，SEC/CN download 的 per-filing Phase A/B 会把单 ticker 批次完整性检查成本放大到 O(文档数²) 级，plan 未声明接受或缓解

- **位置**：§6.1（exact-target mode "一次调用在同一 scan 中返回该 exact `target` 与完整 source-kind inventory/shared/canonical
  payload"）、§7.2 download Phase A/B、`sec_download_filing_workflow.py` 的 per-filing 调用结构
- **问题类型**：非最优方案 / 其它（性能回归未被声明）
- **当前写法**：exact-target mode 每次调用返回完整 inventory（含每个 sibling 的 `content_classification`，即全量 sibling
  file hashing）；SEC download `run_download_single_filing_stream` 对每个 filing 各执行一次 Phase A `classify_source_integrity`
  与 Phase B `classify_staged_source_integrity`（`sec_download_filing_workflow.py:230-242/494-499`），SEC/CN whole-tree preflight
  又已先行一次全量 inventory（`sec_download_workflow.py:580-581`）。plan 未声明该成本，也未规定 download 复用 preflight
  inventory 或限制 per-call 扫描范围。
- **反例/失败场景**：单 ticker 下载批次含 N 个 filing（财报历史批次常见 10-40 个），每个 filing 的 Phase A/B 各触发一次
  whole-kind scan（全部文档全量 sha256），总代价从 O(N) 次单文档哈希变为 O(N²) 级；大 ticker 历史下载耗时显著膨胀，且 Phase B
  在 staging 上同样全量重扫。
- **为什么有问题**：RF1 修复选择了"exact-target mode 也返回全量 inventory"来保证 shared facts 同源，代价是 per-doc 调用
  变为 whole-kind 调用；download 的 per-filing Phase A/B 循环是既有的高调用频度入口，plan 没有把这个成本显性化，implementation
  agent 可能无意识地让每个 Phase A 重算全 kind，或反过来在 workflow 层发明 inventory 缓存（scope 外设计）。
- **直接证据**：round-2 plan §6.1 exact-target mode 定义与 §7.2 原文；`sec_download_filing_workflow.py:230-250`（per-filing
  Phase A）与 `:492-505`（per-filing Phase B）；`sec_download_workflow.py:580-581`（批次级 `list_source_integrity` preflight）。
- **影响**：性能回归（大 ticker 下载批次耗时）/ 实施 Agent 在 workflow 层自行优化导致 scope creep
- **建议改法和验证点**：plan 补一句成本声明与约束：exact-target mode 的 whole-kind 扫描是本 work unit 接受的代价（正确性优先），
  workflow 不得自建 inventory 缓存或跨 filing 复用 stale inspection；或明确 SEC/CN download 的 per-filing Phase A 复用
  whole-tree preflight 的同一 inventory（若同 guard 内），并写死选择其一。实现 review 时用大批次 fixture 做耗时回归观测。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低

## 3. 其它观察（不构成 finding，供 implementation review 参考）

1. **state core 的调用形状未在三类 caller 规则中点名**：§6.1 "三类 caller" 只列 `_fs_source_document_core`、`_fs_source_snapshot`、
   `_fs_storage_infra`；`read_filing_upload_state`（`_fs_filing_upload_state_core.py`）实际使用哪种 mode 只由 §5.3 + 签名推断
   （exact-target mode）。可推断性强，但建议 implementation review 确认其使用 exact-target mode 且只投影
   `inspection.target.classification/business_meta`。
2. **commit validator 的 whole-kind 调用在 staging root 无法归属的损坏下会抛 `SourceIntegrityPreflightError(UNSAFE_PUBLICATION)`**：
   该异常类型以 download preflight 命名，出现在 upload commit 路径时会落入 workflow generic 收口（path-free），与现状（commit
   validation ValueError → generic）同级的失败面。实现时确认该异常在 commit 路径的投影不泄漏内部文案。
3. **step 4 "content reasons 出现非repairable事实" 实际不可达**：`content_classification` 的 REPAIR_REQUIRED 不变量只允许
   repairable reasons，该条款是防御性冗余，无害。
