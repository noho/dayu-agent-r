### 1-未修复-高-filelock release 失败时错误标记 released 状态

- **入口/函数**: `RuntimeFileLock.release`
- **文件(行号)**: dayu/runtime/filelock.py:101-105
- **输入场景**: 第三方 `FileLock.release()` 抛出异常时
- **实际分支**: except 块中在抛出异常**之前**将 `self.released = True`（第 104 行），然后 raise
- **预期行为**: release 失败时应保持 `released = False`，允许调用方重试
- **实际行为**: 已标记 `released=True`，后续重试 `release()` 会因第 98-99 行 `if self.released: return` 直接返回，锁实际未被释放
- **直接证据**:
  ```python
  try:
      self._third_party_lock.release()
  except Exception as exc:
      self.released = True  # 第104行：抛出异常前标记 released
      raise RuntimeFileLockError(...) from exc
  self.released = True  # 第106行
  ```
- **影响**: 调用方无法区分"已成功释放"和"释放失败但状态已标记"；锁泄漏后文件资源无法被其他进程获取
- **建议改法和验证点**: 只在 release 成功后设置 `self.released = True`；失败时直接 raise 不改变状态
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高 — 锁泄漏影响跨进程资源安全

### 2-未修复-高-_LaneClock UTC 推导在 NTP 校正下产生跨进程时钟偏差

- **入口/函数**: `_LaneClock.now`
- **文件(行号)**: dayu/runtime/lane.py:305-342
- **输入场景**: 长时间运行进程中系统时钟经历 NTP 大幅校正
- **实际分支**: `_LaneClock.now()` 使用 `time.monotonic()` 的增量从启动时的 `datetime.now(UTC)` 锚点推导 UTC。`time.monotonic()` 不受 NTP 影响，但系统 UTC 锚点会被 NTP 调整，导致进程内推导的 UTC 与真实 UTC 之间产生累积偏差
- **预期行为**: lane claim 过期判定应基于真实系统时间，确保跨进程一致性
- **实际行为**: 不同进程的 `_LaneClock.now()` 在 NTP 校正后不一致，一个进程可能认为某 claim 已过期并清理，而持锁进程的 heartbeat 尚未同步
- **直接证据**: `lane.py:332-335` 用 `self.utc_anchor + timedelta(seconds=elapsed_seconds)` 推导 UTC；`_refresh_token_sync` 和 `_try_claim_once_sync` 用此值做 stale cleanup 的 `expires_at` 比较
- **影响**: 极端情况下同 lane capacity 被突破，跨进程公平性受损
- **建议改法和验证点**: stale cleanup 判定改用 `datetime.now(UTC)` 而非 `_LaneClock.now()`，或在 DB 中存储 monotonic 偏移量作为 TTL 计算唯一来源
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高 — 跨进程资源竞争正确性
