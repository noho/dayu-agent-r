## Findings

### Finding DS-1: `PromptLocalProvenanceEntry` 对 non-evidence kind 的 `canonical_evidence_refs` 校验 accept 空 tuple 但不 accept 含空白字符串的 tuple

- **Severity**: low
- **File/line**: `dayu/host/compaction.py:296-299` (`_require_unique_string_tuple`), `dayu/host/compaction.py:323-334`
- **Evidence**: `_require_unique_string_tuple` 调用 `_require_string_tuple`，后者对空 tuple 不抛异常（循环不执行），对非空 tuple 逐项校验非空字符串。随后 `__post_init__` 行 330-334 对 non-evidence kind 拒绝非空 refs。因此 `canonical_evidence_refs=("",)` 会在 `_require_string_tuple` 被拒绝（空字符串），但 `canonical_evidence_refs=()` 对 non-evidence kind 正确通过。
- **Impact**: 行为正确，但校验链分散在两处（`_require_unique_string_tuple` 的宽松语义 + `__post_init__` 的 kind 分支），未来维护者可能误解 `_require_unique_string_tuple` 是否已保证非空。
- **Suggested fix**: 不需要修改。`_require_unique_string_tuple` 正确设计为"唯一性但不强制非空"，kind-specific 非空约束由调用方显式施加。这是有意的关注点分离，不是缺陷。
- **Verdict**: accepted（行为正确，设计合理）

### Finding DS-2: `derive_compact_accepted_replacement_v4` 中 retained label kind 双重校验

- **Severity**: info
- **File/line**: `dayu/host/compaction.py:1677-1680` 与 `dayu/host/compaction.py:1664-1669`
- **Evidence**: `compact_proposal_boundary_binding_issues_v4`（行 1664）已用 `allowed_kinds=COMPACT_RETAIN_SOURCE_KINDS_V4` 校验 retained labels 的 kind。若校验通过（issues 非空则抛 ValueError），后续循环中行 1677 的 `entry.source_kind is not CompactSourceKindV4.PREVIOUS_EVIDENCE_FACT` 永远不会触发。该检查是防御性冗余。
- **Impact**: 无功能影响。代码阅读时可能产生"为何双重检查"的疑问。冗余检查本身不引入 bug，且作为 defense-in-depth 有微弱价值。
- **Suggested fix**: 可保留现状，或在行 1677 改为 `assert`（语义更明确表达"此处不可达"）。不建议删除——它作为局部不变量文档有价值。
- **Verdict**: accepted（无害冗余，属于 belt-and-suspenders 防御编程）

### Finding DS-3: Prompt 手动文本与 `<<compact_output_rules>>` 存在结构性信息重复

- **Severity**: low
- **File/line**: `dayu/config/prompts/scenes/conversation_compaction_user.md:40-46`
- **Evidence**: Prompt 中手动描述了七字段类型规则（如 `"retained_previous_evidence_fact_labels"：string array，可为空。只能选择 previous_evidence_fact。`），而 `<<compact_output_rules>>` 占位符注入的 `compact_output_prompt_rules_v4()` 也包含相同的字段类型信息。如果 `compact_structure.py` 的 descriptor 修改了字段结构（如改名、改类型），代码生成的 rules 会自动更新，但手动文本可能漂移。
- **Impact**: 模型可能同时看到手动规则和生成规则；若两者不一致，生成规则（经 parser 强制）是权威真源，手动文本可能造成混淆。当前两者一致，无实际缺陷。
- **Suggested fix**: 不要求立即修改。长期建议：手动文本只写"动作规则"（如 retain 语义、combined caps 公式、质量要求），不重复字段类型/必填性/允许值——这些全由 `<<compact_output_rules>>` 和 `<<compact_output_template>>` 覆盖。当前状态可接受。
- **Verdict**: accepted（当前一致，属维护性风险而非代码缺陷）
