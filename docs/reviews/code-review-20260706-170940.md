### Adversarial Failure Pass

**空输入/空白行：** L517 `idle_interrupt_exit_pending = False` 在任意 `composer.read()` 成功返回后执行，包括空字符串。随后 L519 `if stripped_prompt == "": continue` 回到输入循环。这意味着空白行（按 Enter 不输入内容）会重置退出待确认状态。行为与 Codex/Claude Code 一致：提交空白行是用户有意的输入动作。无缺陷。

**非 KeyboardInterrupt/EOFError 异常：** 内层 try 只捕获 `EOFError` 和 `KeyboardInterrupt`。其他异常（如 `asyncio.CancelledError`、运行时错误）会穿透外层 try，触发 `finally: effective_run_view.close()` 后向上传播。正确——不应静默吞掉未知异常。

**`continue` 语义：** L516 `continue` 在内层 `try-except` 中，但 Python 的 `continue` 作用于最内层循环（`while True`），正确回到 `effective_composer.read(...)` 调用处。

**多个 `_run_interactive_repl` 并发调用：** 每个 REPL 实例有独立的 `idle_interrupt_exit_pending` 局部变量，无共享状态冲突。asyncio 单线程协作式调度下无线程安全问题。

**top-level `run_interactive_command` 的 `except KeyboardInterrupt` (line 206)：** 作为安全网仍然保留。如果 `KeyboardInterrupt` 发生在 `_run_interactive_repl` 之外的路径（如 session 创建、startup reconnect），该 catch 仍会将其映射为 EXIT_KEYBOARD_INTERRUPT。新实现不会导致双重处理，因为 `_run_interactive_repl` 已将空闲输入态的 KeyboardInterrupt 在内部消费。

**prompt-toolkit 非空 draft Ctrl+C：** prompt_toolkit key binding (composer.py:121-124) 在非空 draft 中按 Ctrl+C 只清空 buffer，不抛出 KeyboardInterrupt。因此用户在第一次 idle Ctrl+C 后开始输入原始文本（未按 Enter），再按 Ctrl+C 时：第一次 Ctrl+C 清空 buffer（不抛异常），buffer 变空后再次 Ctrl+C 才抛出 KeyboardInterrupt，此时 `idle_interrupt_exit_pending=True` → 退出。实际体感：第一次 idle Ctrl+C → 重绘；用户输入文本 → 按 Ctrl+C 清空；再按 Ctrl+C → 退出。总按键 3 次 Ctrl+C（与 Codex/Claude Code 一致）。无缺陷。

**`_ScriptedComposer` 的 `exception_type: type[BaseException]`：** `KeyboardInterrupt` 继承自 `BaseException` 而非 `Exception`，因此类型标注为 `type[BaseException]` 是正确的。这是测试代码，不进入生产路径。

## Findings

### F01-未修复-低-idle-interrupt-typing-level-reset-contract-未实现

- **入口/函数**: `_run_interactive_repl` — 输入态 KeyboardInterrupt 处理
- **文件(行号)**: `dayu/cli/commands/interactive.py:504-517`
- **输入场景**: 用户在第一次 idle Ctrl+C 后开始输入原始文本（未按 Enter 提交），再按 Ctrl+C
- **实际分支**: prompt_toolkit key binding (composer.py:121-124) 在非空 draft 中按 Ctrl+C 只清空 buffer 不抛异常；需再次 Ctrl+C 在空 draft 才抛出 KeyboardInterrupt，此时 `idle_interrupt_exit_pending=True` 导致退出
- **预期行为**: accepted plan (plan.md:123) 要求 "Typing-level reset is part of the user-visible contract"，即原始输入应重置退出待确认状态，之后的 Ctrl+C 应视为第一次而非退出
- **实际行为**: 由于 `_run_interactive_repl` 无法观测 prompt_toolkit 内部的原始输入（只能通过 `composer.read()` 的返回值或异常观测），计数器未重置。但实际用户体感与 Codex/Claude Code 一致：用户输入文本后按 Ctrl+C 清空 buffer，再按 Ctrl+C 才退出（共 3 次 Ctrl+C），而非输入文本后一次 Ctrl+C 就直接退出
- **直接证据**: 
  - Plan contract (plan.md:123): "Typing-level reset is part of the user-visible contract"
  - 实现限制 (implementation-codex.md:35): "`_run_interactive_repl(...)` cannot observe raw typing inside prompt-toolkit before the composer returns"
  - composer key binding (composer.py:121-124): 非空 draft Ctrl+C 只清空 buffer，不抛 KeyboardInterrupt
- **影响**: 用户体感正确（与 Codex/Claude Code 一致），但 plan contract 中的 typing-level reset 未被满足。这是一个 contract compliance gap，不是行为缺陷
- **建议改法和验证点**: 两种可选方向：(a) 接受当前行为并更新 plan contract，因为 prompt_toolkit 的内部清空机制已提供等效 UX；(b) 如需严格满足 typing-level reset，需修改 composer 协议使 prompt_toolkit 在非空 draft Ctrl+C 时通知 REPL 层。方案 (a) 优先——当前体感正确，不应为满足文字契约而引入不必要的协议变更
- **修复风险（低）**: 如选择方案 (a)，仅需更新 plan contract 文档，无代码风险
- **严重程度（低）**: 用户可见行为正确，是 plan contract 与 prompt_toolkit 实现机制之间的语义间隙
