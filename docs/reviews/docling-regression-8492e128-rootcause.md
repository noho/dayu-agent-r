## 5. docling 处理过程观测与根因判定（步骤 3，Tier-0）

对 p331 单页复现（与整档同症状）并用插桩观察 TableFormer 调用
（`workspace/tmp/docling-regression/p331/instrumented_run.py`，探针数据
`probe_dump.json`）：

1. **输入无损**：174 个 word token 送入 `tf_predictor.multi_table_predict`，
   含全部目标数字（`1,348,243,150`、`(5,300,000)`、`5,300,000`、
   `5,000,000,000`、`1,342,943,150`、`(4,700,000)` 各在其位）。
2. **模型输出退化**：TableFormer（accurate，模型 artifacts revision v2.3.0，
   推理代码 docling-ibm-models 4.0.2）对该表生成的 OTSL 结构序列
   `rs_seq` 长 **1023 tokens**（config `predict.max_steps=1024`，触顶），
   全为结构 token（fcel/lcel/ecel/nl），**零内容 token**，解码为 111 行全空网格
   ——生成不收敛、未正常终止，属退化输出。
3. **匹配丢弃数据行**：cell matcher 日志
   `MatchingPostProcessor WARNING 98 of 174 pdf cells matched neither a row
   nor a column band of the 111x5 grid and were dropped from the table`
   ——98/174 个 token（含全部数据行数字）因退化网格而被丢弃；幸存 19 个
   框架单元格经行列压缩后成为最终输出。
4. 失败环节在 **TableFormer accurate 模型对该输入的预测本身**（非 token 抽取、
   非 layout 聚类、非 cell matching 实现——matching 只是按退化网格执行了丢弃）。

根因判定：**docling 上游回归**（引入版本 = docling 2.118.0，见第 6 节），
属"准确模式 TableFormer 对特定表格结构（同页含授权表与 movements 表两个
子表的合并聚类）生成触顶不收敛 + 2.118 起解析路径变化导致的匹配退化"，
不是 dayu 配置或该 PDF 的文档特例损坏（文本层完好）。

### 6.1 代码回归 vs 权重回归的隔离证据（关键，Tier-0）

对好版本 2.117 与坏版本 2.118 分别插桩 `multi_table_predict` 输入输出
（`workspace/tmp/docling-regression/tf-input-2117.json` 与 `tf-input-2118.json`，
两次独立运行各版本结果可复现）：

| 观察项 | 2.117（好） | 2.118（坏） |
|---|---|---|
| docling-ibm-models | 3.15.0 | 3.15.0（相同） |
| TableFormer 模型权重 revision | v2.3.0 | v2.3.0（相同） |
| 输入 word tokens（91 个唯一 text × 计数，含顺序与 bbox） | 174 | 174（逐项相同） |
| 输入 table crop（2x 坐标） | [138, 282, 1086, 1222] | [138, 282, 1088, 1222]（差 2pt） |
| 模型输出 rs_seq 长度 | 1023 | 1023（同为触顶序列） |
| 后处理/匹配结果 | 16 行×12 列 → 18 单元格，含全部数据行 | 14 行×16 列 → 19 框架单元格，数据行全失 |

- 模型权重（v2.3.0）、推理包（docling-ibm-models 3.15.0）、解析后端
  （docling-parse 7.20.0）、输入 tokens（文本、顺序、bbox 逐项相同）全部相同，
  唯一实质差异是 docling 2.118 自身代码（其 `models/stages/layout/layout_model.py`
  与 `pipeline/standard_pdf_pipeline.py` 在 2.117→2.118 之间有变更，导致 crop
  右边界差 2pt 及匹配路径行为变化）。**回归点定位到 docling 2.118.0 自身的
  layout/pipeline 变更**；同一触顶 OTSL 序列（1023 tokens，模型生成到
  `max_steps` 上限不收敛）在 2.117 被正确解析为含数据网格，在 2.118 起被
  解释为退化网格并执行丢弃。不是"新模型权重看不懂老表格"，是
  "docling 2.118 对边界序列的解析路径变化"。

## 7. 配置层规避评估（步骤 5，Tier-0）

在 2.127 生产环境对 p331 单页实测（`dayu.documents.docling_runtime` 生产入口）：

| 配置 | 结果 |
|---|---|
| 生产默认（accurate + do_cell_matching=True） | 数据行全失（复现） |
| accurate + `do_cell_matching=False` | 数据行仍失（0 命中）；dummy 匹配路径同样被退化网格拖垮 |
| **`table_mode=fast`** | **全部数字找回**：`1,348,243,150`/`5,000,000,000`/`5,300,000`×2/`1,342,943,150`/`(4,700,000)` 及 `(10,468)`/`(78,031)`/`88,499`/`136`/`885`/`135`/`882` 全命中，单元格逐格干净，**优于 2.90 基线**（基线缺的 `1,342,943,150`、`88,499` 也齐了） |

- `table_mode=fast` 是 dayu 既有参数（`build_docling_pdf_converter(table_mode=...)`），
  切换零代码成本；但它是**文档级全局开关**，对非退化表格的整体质量影响未在本
  报告范围内评估（需另做全量 A/B）。
- `do_cell_matching=False` 不可作为规避路径。
