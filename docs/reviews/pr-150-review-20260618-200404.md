## Findings

### 1-未修复-低-context_fallback.py 不可达 None 检查导致诊断消息不精确

- **入口/函数**: `_load_context_fallback_tx`
- **文件(行号)**: `dayu/host/context_fallback.py` (370-378)
- **输入场景**: `window_current_ref` 为 `None`（`_optional_text` 返回 `None`）
- **实际分支**: 第 374 行 `if window_current_ref != current_input_ref` 命中（`None != "some_ref"` → `True`），抛出 `"fallback current_input_ref mismatch"`
- **预期行为**: 当 `window_current_ref` 为 `None` 时，错误消息应为 `"fallback current_input_ref is missing"` 以区分"字段缺失"与"字段值不匹配"
- **实际行为**: 第 376-378 行的 `None` 检查不可达；错误消息始终为 `"mismatch"` 而非 `"missing"`
- **直接证据**: 第 374 行 `if window_current_ref != current_input_ref: raise HostDurableError("fallback current_input_ref mismatch")`；第 376-378 行 `actual_current_input_ref = window_current_ref; if actual_current_input_ref is None: raise HostDurableError("fallback current_input_ref is missing")` 不可达
- **影响**: 仅诊断消息不精确；行为正确（fail closed），不影响正确性
- **建议改法和验证点**: 将第 374-378 行重写为先检查 `None` 再检查 `mismatch`；或删除不可达代码
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 2-未修复-中-_fallback_caps_allow_append 零测试覆盖

- **入口/函数**: `_fallback_caps_allow_append`
- **文件(行号)**: `dayu/host/context_fallback.py` (765-781)
- **输入场景**: fallback selected window 追加候选 block 时，memory_policy 的 item_cap 和 char_cap 决定是否允许追加
- **实际分支**: 函数被 `build_recent_window_fallback_selection` 在第 547 行调用，控制 fallback window 大小
- **预期行为**: 该函数是 fallback selected window caps 的唯一执行点，应有独立测试覆盖 item cap 超限、char cap 超限、memory_policy=None 三种场景
- **实际行为**: `tests/host/` 中零引用 `_fallback_caps_allow_append` 或 `allow_append`
- **直接证据**: grep `_fallback_caps_allow_append` 和 `allow_append` 在 tests/host/ 返回零结果
- **影响**: 函数回归时无法被测试捕获；当前行为正确但缺乏回归保护
- **建议改法和验证点**: 新增 3 个测试：(1) item cap 超限返回 False；(2) char cap 超限返回 False；(3) memory_policy=None 返回 True
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 3-未修复-低-Recovery tier rejected attempts 未写入 EventLog

- **入口/函数**: `_execute_proactive_compaction` `_operation` closure
- **文件(行号)**: `dayu/host/dispatch.py` (1399-1405, 1414, 1431)
- **输入场景**: 正常 compact 失败后 recovery tier 1-3 运行，tier 产生 rejected attempts
- **实际分支**: 第 1399-1405 行只迭代 `result.rejected_attempts`（原始结果），不迭代 recovery tier 的 rejected attempts
- **预期行为**: `CONTEXT_COMPACTION_FAILED` 的 `attempt_count` 和 `CONTEXT_COMPACTED` 的 `accepted_attempt_number` 应反映全 tier 累计
- **实际行为**: `attempt_count` 使用 `len(result.rejected_attempts)` 仅计原始结果；recovery tier 的 rejected attempts 不写入 EventLog；`accepted_attempt_number` 正确累计但 EventLog 中无对应 rejected 事件
- **直接证据**: 第 1399 行 `for rejected in result.rejected_attempts`；第 1414/1431 行 `attempt_count=len(result.rejected_attempts)`；recovery tier 的 `tier_result.rejected_attempts` 从未被写入
- **影响**: 诊断 gap，不影响 compaction 正确性；设计 plan 使用 "may" 而非 "must" 记录 recovery tier rejections
- **建议改法和验证点**: 如需完整诊断，可在 recovery 循环内累积所有 tier 的 rejected attempts 并在 `_operation` closure 中统一写入
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
