### F01: Recovery scanner and watchdog reopen ordering

- **Controller required**: Explicit ordering/ownership between startup recovery and active cancel watchdog for `CANCELLING` runs; decide whether watchdog runs before recovery, recovery skips/delegates, or recovery invokes timeout; cover clean-close-reopen owner `STOPPED`, crash/inconclusive orphan, and watchdog-disabled behavior.
- **Fix artifact claim**: 已修复
- **Plan evidence**:
  - "Recovery scanner and watchdog ordering" (lines 193-203) now defines a 4-step startup/reopen sequence:
    1. Construct watchdog
    2. Run watchdog startup tick **before** `StartupRecoveryScanner.scan()` so already timed-out runs close as `CANCELLED`
    3. Run recovery scan with policy deferring remaining `CANCELLING` runs to watchdog, even when owner is `STOPPED`
    4. Start watchdog runtime loop for not-yet-timed-out deferred runs
  - Clean-close-reopen owner `STOPPED`: watchdog-enabled path closes accepted-cancel runs to `CANCELLED`; recovery must not write `ATTEMPT_LOST`/`RUN_LOST` (line 201)
  - Crash/inconclusive orphan: same timeout policy applies; inconclusive proof may make recovery skip but watchdog still closes as `CANCELLED` after timeout (line 202)
  - Watchdog disabled: recovery keeps existing orphan policy; positive proof may close `CANCELLING` as `LOST` (line 203)
- **Design truth alignment**: Host design.md §27 (line 3447-3450) defines `RUNNING`/`CANCELLING` recovery classification; plan fix correctly overrides the `CANCELLING` + positive orphan proof → `LOST` path when watchdog is enabled, consistent with the design truth's provision that recovery scan rules can be refined by later phases.
- **Verdict**: **已修复** — ordering is explicit (watchdog before recovery), ownership is assigned (watchdog owns accepted-cancel CANCELLING runs), deferral policy is defined, both clean-close STOPPED and crash/inconclusive are covered, and watchdog-disabled fallback is specified.

### F02: Late terminal race after RUN_CANCELLING

- **Controller required**: Read and cite existing ingest behavior; explicitly state accept/reject rules for `final_answer`, `run_failed`, `run_suspended` after `RUN_CANCELLING`.
- **Fix artifact claim**: 已修复
- **Plan evidence**:
  - First-principles section now cites direct code evidence:
    - `_invalid_terminal_precondition(...)` currently only allows terminal closeout from `RunStatus.RUNNING` (line 61) — this means `final_answer`/`run_failed` after `CANCELLING` are already rejected by existing ingest.
    - `_validate_waiting_confirmation(...)` only confirms `run_suspended`/`tool_awaiting` when Run is `WAITING` + Attempt `SUSPENDED` + Host accepted wait refs exist (line 63) — `CANCELLING`-state awaiting/suspend can only be diagnostic/rejected.
  - "Late terminal handling" (lines 185-191) now explicitly prescribes:
    - `final_answer` after `RUN_CANCELLING`: **reject** with diagnostic `late_terminal_after_active_cancel`, write no success terminal
    - `run_failed` after `RUN_CANCELLING`: **reject** with diagnostic `late_terminal_after_active_cancel`, write no failure terminal
    - `run_suspended`/`tool_awaiting` after `RUN_CANCELLING`: **reject/diagnose** as waiting confirmation without Host accepted wait refs, write no wait record, no `RUN_WAITING`, no `ATTEMPT_SUSPENDED`
    - Worker terminal after timeout closeout: **reject** as terminal already closed
  - Slice 1 tests explicitly cover all four late-terminal scenarios (lines 261-264)
- **Design truth alignment**: Host design.md cancel state machine (line 633) treats `CANCELLING` as the post-acceptance waiting state; late terminals after cancel intent is durable-accepted should not override user cancel intent. Plan's reject policy is consistent.
- **Verdict**: **已修复** — code evidence is cited, explicit accept/reject rules are stated for all three late-terminal types plus post-timeout worker terminal, and focused tests are specified.

### F03: Watchdog scheduling model

- **Controller required**: Choose scheduling model (deterministic tick + hybrid: wake on cancel commit + periodic fallback); define interval ownership and default; state interval affects detection latency not timeout threshold.
- **Fix artifact claim**: 已修复
- **Plan evidence**:
  - "Watchdog scheduling model" (lines 158-165) now specifies:
    - Deterministic `tick(now)` method plus hybrid runtime loop
    - `tick(now)` performs one SQL scan and zero or more timeout closeouts
    - Runtime loop wakes immediately on `cancel_run`/`cancel_session_runs` commit
    - Periodic fallback scan using configured interval (required so lost wakeup or crash between commit and wakeup cannot leave `CANCELLING` suspended)
    - Default interval owner: existing `dispatch_poll_interval_seconds`
    - Interval controls detection latency only; timeout eligibility computed from durable timestamps + Host UTC clock
  - Tests call `tick(now)` directly without sleeping (line 161)
- **Verdict**: **已修复** — scheduling model is hybrid (event + periodic), interval owner is identified, latency-vs-threshold distinction is explicit, and deterministic test entry point is specified.
