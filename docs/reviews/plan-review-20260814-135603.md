### 2-未修复-中-日期年份绑定 1000..9999 缺乏 frozen/用户裁决直接支持，且 date owner 与 year owner 过度耦合
- **状态**: accepted-candidate
- **位置**: plan §5 API contract（`parse_iso_calendar_date` “年份委托 `parse_calendar_year`”）、§6 “日期年份同样落在 shared 1000..9999 owner 范围；0999-12-31 拒绝”、§8 download contract “year <1000…由 shared owner 判为 invalid date”、§11 test matrix “strict ISO date 拒绝 … owner year 范围外日期”
- **问题类型**: 目标漂移 / 过度耦合 / 契约缺失
- **当前写法**: plan 让 ISO date 的年份合法性与 fiscal-year 共用同一 `parse_calendar_year`（1000..9999），并把“年份范围外日期拒绝”作为 owner 测试矩阵的一部分。
- **反例/失败场景**: 本机 Python 3.11 实测 `datetime.date.fromisoformat("0999-12-31")` 成立且 `isoformat()` round-trip 完全相等——它满足 frozen oracle “实际存在的 ISO YYYY-MM-DD calendar date”与 goal “严格 YYYY-MM-DD 且为实际存在的公历日期”的字面契约，但被 plan 判为非法。download 的 year-only/year-month/full-date 输入 0001..0999 当前被接受（`_YEAR_PATTERN ^\d{4}$` + `dt.date`），修复后全部拒绝；goal 成功信号却要求“download 的合法 year…保持成立”。若无 controller 补裁决，实现即按 plan 字面执行一个未被确认的用户可见收紧。
- **为什么有问题**: frozen oracle 把“正四位年份”绑定在 fiscal-year 上，日期条款只要求 ISO 形状 + 实际存在；goal confirmation 确认的日期契约同样无年份范围。plan 通过 date→year 委托把 fiscal-year 的业务范围强加给 calendar date 域，是未经确认的契约扩展，并使 date owner 的合法域被 year owner 绑架（若未来业务需要 <1000 的 ISO 日期，必须解耦重做）。
- **直接证据**: oracle predicate `upload_filing.date-and-year-domain` expected 原文（“filing-date/report-date 必须是实际存在的 ISO YYYY-MM-DD calendar date；fiscal-year 必须是业务有效的正四位年份”）；goal artifact “Confirmed goal and motivation” 与 “Success signals”；`download_contract.py:44-46, 797-808`；本机实测 `date(999,12,31)` 合法且 round-trip canonical、`date(10000,...)` 拒绝。所有冻结 download scenario 最小年份为 1900，无 <1000 场景（故不破坏冻结 evidence，但也不构成裁决）。
- **影响**: 未经确认的用户可见行为收紧（upload 拒绝 0999-12-31 等；download 拒绝 0001..0999 bounds）；语义 ownership 上 date 域与 fiscal-year 域被强制耦合；若 controller 事后否决，S1/S3 需返工。
- **建议改法和验证点**: (a) 由 controller/用户显式裁决并回写 goal artifact，裁决时明确列出受影响行为变化清单（upload date 0999-12-31 拒绝；download 0001..0999 从接受变拒绝），或 (b) 解耦：`parse_iso_calendar_date` 自行验证 4 位年份 shape + `datetime.date` 真实性（Python 日历真源天然覆盖 0001..9999），不委托 `parse_calendar_year`；`parse_calendar_year` 只服务 fiscal_year 与 download year-only bound。验证点：owner 测试矩阵中日期年份用例与裁决一致；若选 (b)，S3 download year-only bound 是否仍要 1000..9999 也需单独裁决（“正四位年份”或“4 位 shape + 日历真实”二选一）。
- **修复风险（低）**: 仅 plan 裁决文案或 S1 内解耦实现
- **严重程度（中）**: 中
