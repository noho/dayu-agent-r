### 1-未修复-严重-recovery scanner 将全量非终态 Run 扫描与 mutations 放在单个 write transaction 中

- **入口/函数**: `StartupRecoveryScanner.scan()`
- **文件(行号)**: `dayu/host/recovery.py:183-210`
- **输入场景**: 进程重启后数据库中存在大量非终态 Run（例如数千个）。
- **实际分支**: `read_non_terminal_runs(transaction)` 返回所有非终态 Run，for 循环中对每个 Run 执行 `_close_positive_orphan`、`_start_recovery_dispatch_or_ready` 等 durable 写入。所有这些操作在一个 `run_write` transaction 内完成（line 211）。
- **预期行为**: 单次 scan 应分批（每批 N 个 Run 各自独立事务提交），任一 Run 的 mutation 失败不应影响其他 Run 的 closeout/dispatch。
- **实际行为**: 一个 transaction 中读全量 + 写全部 mutations。事务窗口极大，可能触发 SQLite 锁超时，导致整个 recovery scan 失败回滚，所有 orphan closeout 全部丢失。
- **直接证据**: `recovery.py:211` — `result = self.transaction_runner.run_write(operation)`，其中 `operation`（line 183-209）在 for 循环中累积 `actions`、`pending_dispatches`、`queue_promotion_sessions`，同时在同一事务内执行写入操作。
- **影响**: 启动恢复可能在大量 orphan 场景下失败（整个 scan 回滚），导致 Agent/Runner 永远无法恢复，且阻塞所有其他 durable 写入。
- **建议改法和验证点**: 改为逐 Run 或小批次独立事务提交。每个 Run 的 classification 在独立 write transaction 中完成。测试: (1) 大量 orphan（1000+）的启动恢复，(2) 中间某个 Run 的 CAS 冲突不影响其他 Run 的 closeout。
- **修复风险（中）**:
- **严重程度（严重）**:

### 2-未修复-严重-compaction retry 使用不可变输入，重试无实际修复语义

- **入口/函数**: `run_compaction_operation`
- **文件(行号)**: `dayu/host/compaction_operation.py:87-170`
- **输入场景**: LLM compactor 对给定的 `CompactionRequest` 返回了被 quality checker 拒绝的 candidate 或 proposal 失败。
- **实际分支**: 循环内每次 `compactor.compact(request)` 传入完全相同的不可变 `CompactionRequest`。`CompactionRequest` 是 frozen dataclass，字段不可变。
- **预期行为**: retry 时应将上一轮失败原因（`quality.rejection_reasons`）注入下一次请求，让 LLM 修正。
- **实际行为**: 循环体仅靠 LLM 非确定性采样来碰运气获得不同输出。第 2...N 次尝试的输出分布不会发生变化。
- **直接证据**: 循环体 `for attempt_number in range(1, max_attempts + 1):` 中 `compactor.compact(request)` 的 `request` 参数在整个循环中从未被修改。
- **影响**: 若 `max_compaction_attempts_per_operation >= 2`，浪费 Engine 调用成本，且 compaction 最终失败率会显著高于必要值。
- **建议改法和验证点**: `CompactionRequest` 或其委托接口应支持 `repair_hints` 字段，携带前一次 quality check 拒绝原因。验证: 单元测试创建 2 次尝试的场景，确认第 2 次尝试的 prompt 包含第 1 次的 rejection reason。
- **修复风险（中）**: 需要修改 `CompactionRequest` contract 或 `ContextCompactor` protocol。

### 3-未修复-高-filelock.py token.release() 异常后锁状态不确定性

- **入口/函数**: `RuntimeFileLockToken.release()`
- **文件(行号)**: `dayu/runtime/filelock.py:99-108`
- **输入场景**: `self._third_party_lock.release()` 抛出 Exception（例如底层文件系统错误），但第三方 `FileLock` 在抛异常之前可能已经部分或完全释放了锁。
- **实际分支**: L101-102 捕获 Exception，包装为 `RuntimeFileLockError` 抛给调用方。`self.released` 仍为 `False`。但在 `RuntimeFileLock.__exit__` 的 finally 块中（L209-210），`self._active_token` 被无条件清零。
- **预期行为**: 锁状态应可判定，要么锁已释放（token.released=True），要么锁仍持有（token.released=False 且下次 acquire 会因为 active token 而拒绝）。
- **实际行为**: `__exit__` 后 `_active_token = None`，下次 `acquire()` 会成功（因为 L159 检查 `self._active_token` 已为 None），但底层文件锁的实际状态不确定。可能导致两个调用方同时"持有"锁。
- **直接证据**: L102 `raise RuntimeFileLockError(...)` 在 `self.released = True` (L103) 之前，异常从 release() 传播到 `__exit__` 的 L207-208，L210 `self._active_token = None` 清空后无法追回真实锁状态。
- **影响**: 文件锁语义被破坏，可能出现并发写冲突。
- **建议改法和验证点**: `release()` 应在 try 块内先标记 `self.released = True`，或 `__exit__` 应在 token.release() 失败时不清空 `_active_token`。补充测试：模拟 `FileLock.release()` 抛异常后再次尝试 acquire。

## Residual Risk

1. **整体架构风险分层清晰**: Durable 层作为纯 SQLite 操作层，事务 runner 正确使用 `BEGIN IMMEDIATE` + WAL + busy timeout + 有限重试。CAS mutation 模式使状态迁移具有防御性。Schema 使用 CHECK constraints + partial unique indexes 在数据库层实现了业务不变量。Concurrency model 正确：`isolation_level=None` + `BEGIN IMMEDIATE` 确保每次只有一个 writer，WAL mode 允许并发 reader。

2. **Contracts 层架构合规**: 无任何向上 import（engine/host/service/ui/fins），所有类型均为 `@dataclass(frozen=True, slots=True)` 或 `TypeAlias` / `Protocol`。`ToolExecutionOutcome` 四态封闭联合完整。`CancellationToken` Protocol 无取消异常泄漏。

3. **Engine Agent 状态机完整**: `run_agent_messages` 和 `run_agent_and_wait` 的调用链完整覆盖正常路径、工具调用路径、取消路径、失败路径和 suspension 路径。`_make_terminal_event` 有重复终态检测（RuntimeError）。Runner close 有幂等保护。取消检查在多个 commit boundary 处进行。

4. **Recovery scan 的最终一致性**: startup recovery scanner 在事务外通过 wake_dispatch 和 wake_queue_promotion 唤醒后续流程。若 scheduler 在 scan 事务提交后、wakeup 调用前被关闭，pending dispatch 会被丢弃——但下次启动时 recovery scan 会重新处理，最终一致性有保证。

5. **Wait adapter 失效时的孤儿 wait**: WaitPoller 发现 adapter 未注册时只记录 warning 并计入 error 计数，但 wait record 不会被自动 resolve 为 LOST。需要外部运维干预或依赖未来的 deadline-based 自动 LOST 机制。

6. **Compaction safety net 存在但可改进**: quality checker 验证了结构约束（preservation evidence、tool fact refs、input retention），但不验证 LLM 产出的语义正确性。LLM 摘要被 trust-but-verify 的结构化检查所保护（ref 完整性），但摘要文本本身可能包含幻觉。

7. **EventLog append-only 属性得到保障**: `append_event` 使用 event_id UNIQUE + digest 对比来保证事件体不变性。append 操作使用先读后写（check-then-act），在事务内是安全的。

8. **测试覆盖**: 测试数量大（200+ 测试文件），覆盖各层核心路径。但若干 adversarial failure 场景未被测试覆盖：UTF-8 BOM 开头的 SSE 流、tool call index 冲突、recovery scan 大批量 orphan、filelock release 异常恢复、WaitPoller resolve 异常传播。
