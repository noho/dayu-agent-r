## 3. 候选阻断逐项裁决

### 3.1 B1（完整批次 O(D+S) 与 publication 有效性不能同时满足）——**不成立为硬阻断**

- B1 的算术（plan 行 134：刷新式 D+(D+1)+…+(D+S-1)）只在"每次发布后必须全量刷新身份库存"这一前提下成立。代码事实证伪此前提的唯一性：
  1. 每候选 Phase A / Phase B / commit 三次全树扫描**已经存在且必须保留**（plan 行 136 自己也声明"本 WU 不擅自改它"）。把每候选的身份事实从"另起 list+D meta 独立 guard 读取"改为"从 Phase A 同次全 kind 扫描投影中重解析"，**身份归因边际读取为 0**。
  2. 批次内自发布不影响他候选绑定：selected 两两 source_id/allocated ID 不同（第 2.2 节末条），候选 j 的提交不进入候选 i 的匹配集；repair 只重写 repair 目标自身文档。
  3. 外部 churn 的当前性由 Phase A 窗口重解析 + Phase B staged 断言承载（见 3.2），不需要刷新批初索引；批初索引只服务 accepted 集合簿记/排序/事件标签。
- 因此 plan 行 17"整个 selected 批次 O(D+S) 与 publication 有效性不可兼得"是把**未限定口径的目标量化**当成硬约束得出的结论。plan 行 136 已摸到分界（"区分 identity 额外读取与现有完整性校验"）但得出"不能说成 O(D+S)"的错误结论：复用既有扫描 ≠ 在扫描上"每次重建全量身份索引"；前者边际身份读取为零，后者才是 plan 反对的形态。
- **裁决**：B1 作为"无新生命周期/持久 schema 则不可解"的阻断被代码事实推翻。真实缺口是 (a) binding goal 的量化口径（见第 4 节）与 (b) plan 缺少每候选写身份 dataflow 规格（Finding F4）。按本报告第 6 节路径，**有限 API 内可改正 F4：不建持久 index、不加长锁、不建 generation 系统**。

- **归类一（既有局限，非 F4 引入）**：上述竞态在今天的逐候选读取下同样存在——今日身份读取的新鲜度只能覆盖到流内 resolve（行 164）时刻，resolve→commit 窗口内无任何集合断言。这是首轮裁决未列的既有增强议题，**不能因 F4 自动升级为"当前必须的新系统"**；但它不需要新系统即可关闭（下条）。
- **归类二（批量缓存的真实回归，必须防）**：若设计只做批初预取并保留 target-only Phase B，身份决定点从今日的"流内 resolve（≈Phase A 时刻）"退化到"批初"，陈旧窗口从每候选放大到整批——这是新方案**必须消除的回归**，而非既有议题。消除路径零边际 I/O：Phase A 改发 `read_source_inventory`（替换现有 `classify_source_integrity` 同一次全 kind 扫描），身份 owner 从该窗口投影重解析本候选绑定；写身份永远来自 Phase A 当前窗口，批初索引不作写入授权。新鲜度语义不劣于今日（今日 resolve 与 Phase A 是相邻两次独立 guard 读取；新设计身份与 Phase A 分类同一次扫描，反而更新）。
- **可选的顺手关闭（强化，需明示裁决）**：Phase B 发 batch 作用域的 staged 库存投影（与 published 投影同一私有 helper，capability 校验沿用 `classify_staged_source_integrity` 先例），身份 owner 断言"staged 树内 provider/source_id=X 的匹配集 ⊆ {目标文档}（新建时为空）"。由于 `begin_batch` 复制点是 writer lock 内的 published 快照、持 batch 期间无人可发布，该断言**完全关闭** B2 竞态（锁外发布的 B 必出现在 staging），成本是一条断言、零新增扫描。它把今日"静默重复绑定提交"变为封闭 retry/失败——**是行为强化，超出原 F4 字面范围**，纳入与否须总控/用户明示（推荐纳入：边际成本一条对称投影 + 一条断言；不纳入则登记 deferred，不阻塞 F4 主体，见 Finding F2）。
- plan 行 142 自己已声明"不将未触发的竞态夸大成当前生产事故……不得把该差异偷偷转为新的持久 uniqueness schema"，方向正确；但其把该反例整体作为"新批量复用方案要通过的必要条件"并据此阻断，等于把增强议题默然升为接受条件，且未识别零成本关闭路径。

### 3.3 B3（invalid source 的错误边界）——**成立但可即时裁决，不构成契约阻断**

- plan 前提属实：今日身份 owner 读 raw meta（`_fs_source_document_core.py:801-867` 只做 identity 一致性校验，无 manifest/provenance 信任管线），对"匹配但缺内部 ID"抛 `ValueError`（`cn_download_identity.py:41-43`）；inspection 对同一文档会分类 META_UNTRUSTED 且不投影 meta（第 2.2 节）。
- 但 B3 不需要"先对真实损坏样本裁决异常先后再定 API"（plan 行 146）。两条既有闸门使 sentinel 差异**对写入不可达**：
  1. preflight 对 inventory 任一 UNSAFE 即抛（`source_integrity.py:310`），且 preflight 与 accepted IDs 在新设计中消费**同一库存**——任何 UNSAFE filing/material 存在时，批次在任何 FILING_STARTED 之前终止；
  2. 即使 UNSAFE 文档在 preflight 后被外部发布，commit 期 `_validate_complete_source_kind_tree` 要求 staged 全部 COMPLETE（`_fs_storage_infra.py:1131-1151`），写入同样无法发布。
- 因此唯一变化是**错误投影顺序**：今日 HK 特有的"raw 匹配 + 缺内部 ID → identity `ValueError`"（CN 路径今日本就无此分支，行 28-29 直接返回，同类损坏走 preflight 错误）被统一的 `SourceIntegrityPreflightError(UNSAFE_PUBLICATION)` 取代。**无新错误词表**（plan 行 146 的约束满足）；损坏 meta 的错误原因从身份 owner 移回完整性 owner，语义所有权更正确（身份 owner 本就无法区分"损坏"与"合法缺 ID"）。
- 另一个精确推论：凡持可信 meta 的 filing 必有合法 internal_document_id（manifest owner 强制，第 2.2 节），故身份 owner 的"缺内部 ID 拒绝"在新投影下**对可信集合恒真保持**（不变量上移给 manifest owner）；重复绑定 `ValueError` 保持可达（两个可信文档同 source_id，例如经 B2 既有竞态产生的历史重复）。今日"匹配缺 ID 拒绝"条款不放宽——它在损坏情形由更早的 typed preflight 错误承接。
- plan 第 5 节行 90 已规定 UNSAFE"不跳过、不默认空字典、不分配新 ID"，方向正确；但该句与第 7 节 B3"异常先后未定"自相矛盾——第 5 节已经给出了可裁决的规则（sentinel 不匹配→走分配→同窗口 preflight 抛错→写入不可达），plan 却把已可定案的事项升级为阻断。
- **裁决**：B3 是可在本轮裁决的设计细节：采用第 5 节 sentinel 语义 + 记录 HK 特有 `ValueError` 被 `UNSAFE_PUBLICATION` 承接的用户可见错误投影变化；测试必须用真实损坏样本（repairable/unsafe 网格在 `test_fins_storage_atomicity.py` 已有先例），不得只造 COMPLETE fake——plan 行 146 这一测试要求予以确认。
