## 2. Findings

### 01-未修复-高-pressure/action function 缺少 REACTIVE_POST_COMPACT hard→ALLOW 分支

- **位置**: `context_budget.py:961-985` `_pressure_and_decision`；plan §5.5 12-cell matrix
- **问题类型**: 状态机漏洞 / 不可直接实施
- **当前写法**: plan §5.5 冻结了 12-cell matrix：`REACTIVE_POST_COMPACT` 的 hard 行为是 `ALLOW_DISPATCH`，soft 也是 `ALLOW_DISPATCH`。`ContextSizingResult.__post_init__`（`context_budget.py:474-483`）通过调用 `_pressure_and_decision` 交叉验证 pressure 与 decision。
- **反例/失败场景**: 当前 `_pressure_and_decision` 对所有 stage 的 hard 无条件返回 `BLOCK_HARD_THRESHOLD`。若 implementation agent 只在 `__post_init__` 里加 `REACTIVE_POST_COMPACT` 特例而不改 `_pressure_and_decision`，结果会自相矛盾：函数返回 `BLOCK` 但 `__post_init__` 要求 `ALLOW`。若反过来只改函数不改 `__post_init__`，`__post_init__` 的交叉验证仍会 catch mismatch。
- **为什么有问题**: `_pressure_and_decision` 是 pressure/action 的唯一 truth owner（plan §4 明确声明）。12-cell matrix 中 `REACTIVE_POST_COMPACT` 的 hard 必须返回 `(HARD_THRESHOLD_EXCEEDED, ALLOW_DISPATCH)`，这与当前函数对 hard 的无条件 `BLOCK` 直接矛盾。implementation agent 必须同时修改函数和 `__post_init__` 的 Slice 1 conservative-only 约束（`context_budget.py:445-446` 强制 `estimate_method is CONSERVATIVE_FALLBACK`），但 plan 没有指出这个具体修改点。
- **直接证据**:
  - `context_budget.py:970-974`: hard 对所有 stage 返回 `BLOCK_HARD_THRESHOLD`
  - `context_budget.py:975-984`: soft 只对 `ORDINARY` 返回 `COMPACT_SOFT_THRESHOLD`，其余返回 `ALLOW_DISPATCH`
  - `context_budget.py:474-483`: `__post_init__` 调用 `_pressure_and_decision` 并严格比对
  - plan §5.5 action table: `REACTIVE_POST_COMPACT` hard = `ALLOW_DISPATCH`
- **影响**: implementation agent 若只按 plan 文本推断修改范围，会遗漏 `_pressure_and_decision` 函数本身的修改，导致 `__post_init__` 校验失败或 12-cell 行为不正确。
- **建议改法和验证点**: plan 应明确指出 `_pressure_and_decision` 需要新增 stage-aware hard 分支：当 `stage is REACTIVE_POST_COMPACT` 时 hard 返回 `ALLOW_DISPATCH`。验证点：12-cell test matrix 中 `REACTIVE_POST_COMPACT × HARD_THRESHOLD_EXCEEDED` 断言 `budget_decision is ALLOW_DISPATCH`。
- **修复风险（低/中/高）**: 低
- **严重程度（高）**: 不修改则 Slice 1 无法实现 reactive hard allow

### 02-未修复-高-recovery start 缺少 transaction-local terminated Attempt loader 设计

- **位置**: plan §4 transaction B；§5.1 `run_input.py`；amendment §4 `strict-load source Attempt manifest/candidate`
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: amendment §4 要求 "strict-load source Attempt prepared candidate" 并 "reuse its frozen policy/tool schemas/disable-tools/tool-execution-mode"。plan §5.1 引用 `run_input.py` 的 transaction-local strict loader。
- **反例/失败场景**: 当前 `load_prepared_runner_call_candidate`（`run_input.py:2448-2525`）需要 `AttemptDispatchSnapshot(attempt_id, execution_id, run_id, ...)`，该 snapshot 来自正在 dispatch 的 Attempt。但 recovery start 时 source Attempt 已经 terminal，不存在 `AttemptDispatchSnapshot`。implementation agent 需要：(1) 从 source Attempt 的 durable state 构造等效 lookup key；(2) 找到该 Attempt 的 `RUNNER_CALL_INPUT_ASSEMBLED` event；(3) 从其 manifest 读取 candidate payload。但 plan 没有指定这个 lookup 入口应该在哪里、叫什么、签名是什么。
- **为什么有问题**: `run_input.py` 现有 loader 是为 ordinary dispatch 设计的，其 `AttemptDispatchSnapshot` 假设 Attempt 正在被 dispatch。recovery 的 lookup 需要不同的入口参数（source Attempt ID + run ID），且需要在事务内完成。plan 引用了 "transaction-local strict loader" 但没有定义其接口，迫使 implementation agent 自行设计。
- **直接证据**:
  - `run_input.py:2448-2453`: `load_prepared_runner_call_candidate` 签名需要 `AttemptDispatchSnapshot`
  - `engine_ingest.py:692-723`: 当前 `_StartReactiveRecoveryOperation` 不读取任何 manifest/candidate
  - plan §8.2 change 9: "通过`run_input.py` transaction-local strict loader读取source Attempt frozen candidate"
- **影响**: implementation agent 被迫自行设计 loader 接口，可能与 plan 其他部分的 candidate/manifest 同源约束不一致。
- **建议改法和验证点**: plan 应在 §5.1 或 §8.2 中明确新增 `load_source_attempt_prepared_candidate(transaction, event_log_store, run_id, source_attempt_id) -> PreparedRunnerCallCandidate` 的接口定义，说明它如何从 source Attempt 的 `RUNNER_CALL_INPUT_ASSEMBLED` event 读取 manifest 并加载 candidate。验证点：source Attempt manifest 缺失 / digest mismatch 时 fail closed 且不 start。
- **修复风险（低/中/高）**: 中
- **严重程度（高）**: 不定义则 implementation agent 需要自行设计关键接口

### 03-未修复-高-memory catch-up failure 当前只 warning 不阻止 recovery start

- **位置**: `engine_ingest.py:2724-2740` `_complete_reactive_recovery`；plan §8.2 change 9
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: 当前 `_complete_reactive_recovery` 中 catch-up failure 被 `try/except` 捕获后只记录 `_LOGGER.warning`，随后继续调用 `_StartReactiveRecoveryOperation`。amendment §4 要求："catch Conversation Memory up to exact CONTEXT_COMPACTED.event_sequence; if target not reached: do not start, do not wake, keep RECOVERING"。
- **反例/失败场景**: 若 memory catch-up 因 EventLog 读取错误、projection 计算错误或超时失败，当前代码仍会创建 recovery Attempt 并 wake worker。此时 candidate 可能基于不完整的 memory projection（含 covered older raw），导致 conservative estimate 高估、provider 实际收到旧 material。更严重的是，若 catch-up 部分成功但未达目标 sequence，candidate 中的 selected recent window 可能包含已被 compact 覆盖的 raw，使 exact candidate 不 exact。
- **为什么有问题**: catch-up 是 candidate freeze 的前置条件（plan §5.1："memory projection catch-up / lag repair 必须移动到 candidate freeze 之前完成"）。若 catch-up 失败仍 start，candidate 的 memory projection 不正确，导致 (1) conservative estimate 可能高估；(2) manifest 中的 `input_snapshot_digest` 不代表真正的 post-compact view；(3) actual request 的 messages 可能包含已 compact 的旧 raw。
- **直接证据**:
  - `engine_ingest.py:2732-2740`: `except Exception as exc: _LOGGER.warning(...)` 后继续 start
  - plan §8.2 change 9: "catch-up未达到目标...不wake...Run留在RECOVERING"
  - plan §6.4 failure table: "reactive accepted compact后memory catch-up/candidate/start CAS失败...本调用不创建/不wake Attempt"
- **影响**: recovery Attempt 基于不完整 memory projection，candidate digest 与 post-compact truth 不一致，可能导致 provider 收到错误 messages 或 estimate 不准。
- **建议改法和验证点**: plan 应明确指出 `_complete_reactive_recovery` 中 catch-up failure 必须转为 `_ReactiveRecoveryAccepted` 的 rejection 或保持 `RECOVERING` 不 start。验证点：catch-up failure test 断言零 wake、零 `RUN_STARTED`、Run 仍为 `RECOVERING`、accepted compact 保持不变。
- **修复风险（低/中/高）**: 低
- **严重程度（高）**: 不修复则 candidate 基于错误 memory projection

### 04-未修复-中-Reactive recovery rollback 使用 HostDurableError 而非 plan 要求的 private signal

- **位置**: `engine_ingest.py:730`；plan §5.6 CAS/rollback 方案；amendment §4
- **问题类型**: 并发恢复风险 / 最佳实践偏离
- **当前写法**: `_StartReactiveRecoveryOperation.__call__` 在 transition 返回非 `UPDATED` 或 rows 不完整时 raise `HostDurableError("reactive recovery start precondition failed")`。amendment §4 要求 "owner-local private rollback signal; run_write 外收敛为本调用不wake"。
- **反例/失败场景**: `HostDurableError` 是通用 durable 错误，会被 `run_write` 的异常处理捕获并 rollback transaction（正确），但它也会向上传播为 caller 的异常。当前 `_complete_reactive_recovery`（`engine_ingest.py:2741-2746`）没有 catch 这个异常，会导致整个 ingest 失败并可能被上层当作 unexpected error 处理。plan 要求的 private signal 应该被 caller 优雅捕获并收敛为 "不wake、保留accepted compact"。
- **为什么有问题**: `HostDurableError` 混淆了两种语义：(1) transient concurrency 问题（precondition miss）应被静默处理；(2) 真实 integrity 错误应传播。当前实现对两者使用同一异常类型，caller 无法区分。
- **直接证据**:
  - `engine_ingest.py:730`: `raise HostDurableError("reactive recovery start precondition failed")`
  - `engine_ingest.py:2741-2746`: `_complete_reactive_recovery` 无 try/except 包裹 `_StartReactiveRecoveryOperation`
  - amendment §4: "owner-local private rollback signal; run_write 外收敛为本调用不wake"
  - plan §5.6: 定义 `_ReactiveRecoveryStartCasMissRollback` 为 `engine_ingest.py` 私有异常
- **影响**: recovery start precondition miss 可能被上层当作 unexpected error 处理，导致不正确的 error logging 或 retry，而非 plan 要求的 "不wake、保留 accepted compact"。
- **建议改法和验证点**: plan §5.6 已定义 `_ReactiveRecoveryStartCasMissRollback`，但 amendment §4 没有重申这个私有异常类型。plan 应明确在 amendment 中引用 §5.6 的 rollback 方案，并指出 `_complete_reactive_recovery` 需要 catch 该私有异常。验证点：precondition miss test 断言零 wake、零矛盾 terminal facts、Run 仍 RECOVERING。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 当前实现可工作但语义不精确，容易在 future maintenance 中引入 bug

### 05-未修复-中-PreparedRunnerCallCandidate 缺少 tool_execution_mode 字段

- **位置**: `run_input.py:489-594`；plan §5.1
- **问题类型**: 契约缺失
- **当前写法**: plan §5.1 要求 `PreparedRunnerCallCandidate` 包含 `tool_execution_mode: ToolExecutionMode` 并纳入 `input_snapshot_digest`。amendment §4 也要求 "reuse its frozen policy/tool schemas/disable-tools/tool-execution-mode"。
- **反例/失败场景**: 当前 `PreparedRunnerCallCandidate`（`run_input.py:489-594`）没有 `tool_execution_mode` 字段。recovery candidate freeze 时无法将 mode 纳入 digest，导致 (1) 不同 mode 的 candidate 可能产生相同 digest；(2) actual request 无法验证 mode 一致性。
- **为什么有问题**: `tool_execution_mode` 影响 tool execution 行为（strict/lenient），是 candidate snapshot 的必要组成部分。若不纳入 digest，mode 漂移不会被检测到。
- **直接证据**:
  - `run_input.py:489-594`: `PreparedRunnerCallCandidate` 字段列表无 `tool_execution_mode`
  - plan §5.1: "`tool_execution_mode`必须进入candidate projection与`input_snapshot_digest`"
  - amendment §4: "复用其frozen policy/tool schemas/disable-tools/tool-execution-mode"
- **影响**: implementation agent 需要在 Slice 1 中新增此字段并修改 digest 计算，但这在 plan 的 "Exact changes" 列表中没有明确列出。
- **建议改法和验证点**: plan §8.2 应在 change 4 或 change 6 中明确列出 `tool_execution_mode` 的新增。验证点：不同 mode 的 candidate 产生不同 digest；recovery candidate 的 mode 来自 source Attempt manifest 而非当前 local config。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 影响 candidate 完整性但不阻塞主流程

### 06-未修复-低-PLAN 未说明 reactive sizing 使用 complete candidate 还是 display_text 的过渡路径

- **位置**: `engine_ingest.py:1669-1680`；plan §8.2 change 9
- **问题类型**: 切片过粗
- **当前写法**: 当前 `_start_reactive_context_recovery` 使用 `_display_text_from_input_event` 构造 `BudgetEstimateInput`（`engine_ingest.py:1669-1680`）。plan §5.1 要求所有 dispatch-relevant sizing 使用 complete candidate。Slice 1 仍只使用 conservative fallback。
- **反例/失败场景**: amendment §4 要求 recovery start transaction 内 "freeze identity-free complete candidate -> conservative sizing(stage=REACTIVE_POST_COMPACT)"。但 plan §8.2 change 9 的文字描述侧重于 manifest-before-start 与 CAS rollback，没有明确指出 reactive sizing 必须从 display_text 切换到 complete candidate。若 implementation agent 只加了 `REACTIVE_POST_COMPACT` stage 但继续用 display_text 估算，sizing 结果会基于不完整输入。
- **为什么有问题**: Slice 1 的核心目标之一是 "complete candidate 单一真源"。reactive path 的 sizing 也必须使用 complete candidate，否则形成两个 sizing 真源。
- **直接证据**:
  - `engine_ingest.py:1669-1680`: 使用 display_text 构造 `BudgetEstimateInput`
  - plan §8.2 change 9: "freeze identity-free complete candidate...conservative sizing(stage=REACTIVE_POST_COMPACT)"
  - plan §1.1: "Run 不因 usage 缺失或 usage 不可用失败" + "对当前完整候选输入调用同一个 conservative estimator"
- **影响**: 若 reactive sizing 继续用 display_text，与 ordinary pre-start 的 complete candidate sizing 不一致，形成两个 sizing 真源。
- **建议改法和验证点**: plan §8.2 change 9 应明确指出 `_start_reactive_context_recovery` 中的 sizing 必须从 display_text 切换为 complete candidate adapter。验证点：reactive sizing 的 `candidate_input_digest` 与 recovery manifest 的 `input_snapshot_digest` 一致。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: Slice 1 的 completion signal 已覆盖此约束，但 explicit 更好

## 6. Verdict

**pass-with-risks**

Plan amendment 在架构层面正确解决了 reactive post-compact 的 stage/action/owner 问题。4-stage/12-cell matrix 逻辑自洽，`run_transition.py` 零 diff 有 production evidence 支撑，reactive hard allow 与现有 bounded reactive loop 的衔接设计完整。

但存在 3 个高 severity finding 阻碍 code-generation-ready：

1. `_pressure_and_decision` 的 REACTIVE_POST_COMPACT hard→ALLOW 分支需要明确指出
2. recovery start 的 transaction-local terminated Attempt loader 接口未定义
3. memory catch-up failure 必须阻止 recovery start（当前代码只 warning）

建议在恢复 Slice 1 implementation 前，由 Controller 裁决是否需要在 plan 中补充这 3 点的具体修改指引。它们不改变 plan 的架构方向，但会显著降低 implementation agent 的返工风险。
