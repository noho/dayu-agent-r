### Finding 1 (Medium) — Type module placement creates layer violation risk

**上一轮问题：** Plan 原文 S1 Files 列出 `dayu/host/memory_snapshot_integrity.py`，types 定义在 host 层而 classifier 在 durable 层返回它，导致 `durable.memory` 必须反向 import host 层模块，违反架构硬约束。

**Amendment 状态：已关闭 ✅**

当前 plan S1 Files 列表已改为：

> - `dayu/host/durable/memory.py`
> - `tests/host/test_memory_projection.py`

且 plan 明确写道：

> 在 `dayu.host.durable.memory` 内新增 Host durable-owned typed enum/dataclass，避免 durable 层反向 import Host 上层模块：`MemorySnapshotIntegrityFailureKind`、`MemorySnapshotIntegrityIssue`

**代码核对确认：** `dayu/host/storage_maintenance.py` 已从 `dayu.host.durable.*` 导入（如 `HostStorageUsageReport` 来自 `dayu.host.durable.storage_lifecycle`），因此从 `dayu.host.durable.memory` 导入新的 integrity types 符合现有依赖方向。无反向依赖风险。

### Finding 2 (Low) — `manual corruption` acceptance signal mapping is implicit

**上一轮问题：** Issue #41 验收信号要求覆盖 6 个类别（含 manual corruption），plan 只定义了 5 个 classifier categories，未显式说明 manual corruption 的归属。

**Amendment 状态：已关闭 ✅**

当前 plan S1 第 49 行明确写道：

> Issue #41 的 `manual corruption` 不作为独立 failure kind；手动 SQL 修改 durable row 导致的损坏会被 `invalid_json`、`schema_mismatch`、`digest_mismatch`、`unsupported_item_kind` 或 `storage_read_failed` 捕获。

映射关系显式且完整。S1 测试矩阵也包含 `manual SQL corruption mapped to digest mismatch` 测试场景。

### Finding 3 (Low) — `storage_read_failed` test strategy needs concrete trigger

**上一轮问题：** Plan 未指明 monkeypatch 目标和异常类型，implementation agent 无法确定具体测试策略。

**Amendment 状态：已关闭 ✅**

> storage-read failure classification by monkeypatching the classifier's module-private snapshot row reader helper to raise `sqlite3.OperationalError`；production corruption semantics remain unchanged。
