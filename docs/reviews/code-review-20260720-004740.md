### 2) Controller 拒绝 DS 对 setx timeout 和 R11 returncode=1 的证据不足单因结论 → 确认正确

Controller adjudication 对两项分歧的裁决经独立复核：

**setx timeout**：
- DS 将 setx timeout 完全归因于 reader decode failure → pipe drain 失败 → subprocess timeout。
- 证据链：setx timeout 与 decode failure 共用同一 `_run_init` consumer（均使用 `text=True` 无 `encoding=`），reader thread 崩溃后 `subprocess.run` 内部 pipe 排空不可靠，timeout 是可能的下游症状。
- 但直接证据只到 "reader thread 崩溃导致 stdout/stderr 不可读"——从 pipe drain 失败到 `subprocess.run(timeout=180)` 超时之间存在中间环节（进程等待、pipe buffer、OS 调度），没有直接证据证明这一链路必然导致 timeout 而非更早的错误返回。
- **Controller 的保守裁决正确**：当前证据支持下，decode failure 是最可能的原因，但不能排除 setx 本身在特定 Windows runner 上的性能问题。第四轮 rerun 若 setx 仍 timeout，必须以新 artifact 建立独立 root cause。

**R11 generated CLI script `returncode=1`**：
- DS 将 `returncode=1` 完全归因于 reader decode failure，认为 consumer 端 reader 异常导致子进程异常退出。
- 但 `CompletedProcess.returncode` 是 `cmd.exe` 的真实退出码——reader exception 在父进程侧发生，不能反向导致子进程返回 1。Reader exception 可以解释 stdout/stderr 变为 `None`，但不能解释子进程退出码。
- **Controller 的保守裁决正确**：第四轮若仍返回非零，必须保留 strict UTF-8 stderr 并重新裁决 root cause。
