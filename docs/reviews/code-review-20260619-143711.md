### 1-未修复-高-Recovery tier rejected attempts 不写入 EventLog，审计链断裂

- **入口/函数**: `HostDispatchScheduler._execute_proactive_compaction()` → recovery loop → `_operation()` transaction
- **文件(行号)**: `dayu/host/dispatch.py:1343-1407`
- **输入场景**: proactive compaction 首次 operation 全部 rejected，进入 recovery tier 循环；recovery tier 也全部 rejected 或部分 rejected
- **实际分支**: recovery loop 中每个 `tier_result.rejected_attempts` 从未写入 EventLog；transaction 中只迭代 `result.rejected_attempts`（初始 operation 的 rejected attempts）
- **预期行为**: 所有 proposal attempt 的 rejected 事件都应写入 EventLog，包括 recovery tier 的 rejected attempts。Plan 明确要求 `CONTEXT_COMPACTION_ATTEMPT_REJECTED` 覆盖每个 proposal attempt
- **实际行为**: `for rejected in result.rejected_attempts:` (行 1401) 只遍历初始 operation 的 rejected attempts。recovery tier 的 `tier_result.rejected_attempts` 被丢弃，不写入 EventLog，也不计入 `attempt_count`
- **直接证据**: 行 1343-1376 recovery loop 只保存 `accepted_result` 和 `accepted_request`；行 1401 `for rejected in result.rejected_attempts` 只读初始 `result`；行 1433 `attempt_count=len(result.rejected_attempts)` 只计初始 result
- **影响**: recovery tier 的 proposal failure diagnostic（包括 `CompactionRejectedAttemptDiagnostic` artifact ref）从 durable 审计链中消失。当 recovery tier 1-3 都失败时，EventLog 中只有初始 operation 的 rejected attempts，丢失了 3 个 recovery tier 的诊断信息。这对排查 compact 失败根因造成信息缺失
- **建议改法和验证点**: 在 recovery loop 结束后、transaction 前，将所有 recovery tier 的 `tier_result.rejected_attempts` 合并到一个统一列表，transaction 内遍历全部 rejected attempts 写入 EventLog。`attempt_count` 也应使用合并后的总数。验证：构造 recovery tier 失败场景，断言 EventLog 中存在 recovery tier 的 `CONTEXT_COMPACTION_ATTEMPT_REJECTED` 行
- **修复风险（低/中/高）**: 中 — 需要调整 recovery loop 和 transaction 之间的数据传递结构，但不改变 compaction 决策逻辑
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-中-Session state check 双重检查但无 stale result 保护

- **入口/函数**: `HostDispatchScheduler._execute_proactive_compaction()` → `_operation()` transaction
- **文件(行号)**: `dayu/host/dispatch.py:1343-1376 (recovery loop), 1408-1423 (transaction check)`
- **输入场景**: Session 在 recovery loop 期间关闭，recovery tier 产出 accepted result
- **实际分支**: 行 1343-1376 recovery loop 不检查 session 状态；行 1408-1423 transaction 内检查 session 状态，若 session 已关闭则写入 `stale_compaction_result` failed event
- **预期行为**: recovery loop 期间 session 关闭时，不应继续执行 recovery tier 或产出 accepted result
- **实际行为**: recovery loop 在事务外执行，不检查 session 状态。若 session 在 recovery loop 期间关闭，recovery tier 仍会执行并可能产出 accepted result。transaction 内的 session check 会拦截并写入 `stale_compaction_result`，但 recovery tier 的 rejected attempts 仍被丢弃（见 Finding 1）
- **直接证据**: 行 1343-1376 无 session 检查；行 1408 `if not _run_session_allows_proactive_compaction(transaction, run)` 只在 transaction 内检查；行 1409-1419 `stale_compaction_result` 路径使用 `result.rejected_attempts` 而非合并后的 attempts
- **影响**: session 关闭后 recovery tier 的计算资源被浪费；且 stale result 的 rejected attempts 丢失（与 Finding 1 复合）
- **建议改法和验证点**: 在 recovery loop 每个 tier 开始前检查 `cancellation_token.is_cancelled()`（已做）；考虑在 recovery loop 中增加 session 状态检查，或在 session check 失败时确保所有 rejected attempts（含 recovery tier）都被写入
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-低-`_completed_compaction_proposal_attempt_count` 对 accepted_result 语义不一致

- **入口/函数**: `_completed_compaction_proposal_attempt_count()`
- **文件(行号)**: `dayu/host/dispatch.py:4118-4143`
- **输入场景**: recovery tier 成功后计算 `accepted_attempt_number`
- **实际分支**: 行 1358-1361 `accepted_attempt_number = completed_attempt_count + _accepted_attempt_number(tier_result)`
- **预期行为**: `completed_attempt_count` 应包含初始 operation 的所有已完成 proposal call（不含 cancellation），加上 recovery tier 的已完成 proposal call
- **实际行为**: `completed_attempt_count` 在行 1342 初始化为 `_completed_compaction_proposal_attempt_count(result)`（初始 operation），行 1374-1376 累加每个失败 recovery tier 的 count。当 recovery tier 成功时，`_accepted_attempt_number(tier_result)` 返回 `len(tier_result.rejected_attempts) + 1`，包含了成功 tier 内部的 rejected attempts。这在语义上正确但不直观
- **直接证据**: 行 1342 `completed_attempt_count = _completed_compaction_proposal_attempt_count(result)`；行 1374-1376 累加失败 tier；行 1358-1361 成功时用 `completed_attempt_count + _accepted_attempt_number(tier_result)`
- **影响**: 轻微 — 当前逻辑在数值上正确，但命名和累加方式增加了认知负担。若未来 recovery tier 逻辑变更，容易引入 off-by-one
- **建议改法和验证点**: 补充测试覆盖 attempt number 计算逻辑，特别是跨 tier 的累加场景
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 5-未修复-低-Recovery tier 共享 operation_id 导致 EventLog 归属模糊

- **入口/函数**: `HostDispatchScheduler._execute_proactive_compaction()` → recovery loop
- **文件(行号)**: `dayu/host/dispatch.py:1353`
- **输入场景**: 多个 recovery tier 使用同一个 `pending.operation_id`
- **实际分支**: 行 1353 `compaction_operation_id=pending.operation_id`
- **预期行为**: 每个 proposal attempt 的 EventLog 事件应可唯一归属到具体的 attempt
- **实际行为**: 所有 recovery tier 共享 `pending.operation_id`，若写入 EventLog，`CONTEXT_COMPACTION_ATTEMPT_REJECTED` payload 的 `operation_id` 相同。区分 attempt 只能靠 `attempt_number`，但 attempt_number 跨 tier 的语义由 `_completed_compaction_proposal_attempt_count` 隐式定义
- **直接证据**: 行 1353 `compaction_operation_id=pending.operation_id`；行 1347 `run_compaction_operation(..., compaction_operation_id=pending.operation_id, ...)`
- **影响**: 当前因 Finding 1 不写入 recovery tier 的 EventLog，此问题暂不可见。若修复 Finding 1，需同时考虑 operation_id 归属
- **建议改法和验证点**: 修复 Finding 1 时，在 EventLog payload 中增加 recovery tier 标识（如 `recovery_tier_reason`），或使用带 tier 后缀的 operation_id
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
