## Findings

### 01-未修复-中-tier 2 section-aware degrade 的 within-section item 排序字段未由 plan 选定，且缺少排序确定性测试

- **位置**: Section 7 Decision 5 (line 96), Section 8 S4 (line 239-274), Section 9 Expected Assertions (line 312-323)
- **问题类型**: 不可直接实施 / 测试缺口
- **当前写法**: plan Section 7 Decision 5 写"Within a section, retain by source recency descending when an EventLog sequence exists; otherwise retain by material order, then stable block id"。S4 exact changes 写"Tier 2: apply section-aware compacted view degrade with fixed section priority...Within each section, use source recency descending when available, otherwise material order then stable block id"。Expected Assertions 写"Section-aware degrade never truncates semantic item text, rewrites summary/fact/anchor/intent/reference continuity, creates a new summary or creates Session Semantic Memory"。
- **反例/失败场景**: 实现 agent 可能选择不同的"source recency"字段实现（如 `event_sequence`、`created_at`、`last_updated_cursor`），或选择不同的 stable block id 排序方向（升序/降序），导致 tier 2 degrade 行为在不同路径间不一致。更关键的是，没有测试断言排序是确定性的——即使实现了排序，测试只验证"不截断""不生成新 summary"，不验证"排序正确且可复现"。
- **为什么有问题**: design.md re-review（DS F1 fix）明确要求"后续 code-generation-ready plan 必须基于该原则选择稳定排序字段和排序方向，并确保 ordinary / compact / fallback 路径复用同一规则"。DS re-review residual risk 1 写"若后续 plan 遗漏此项，或选定的字段不满足'业务可解释、稳定、确定性复现'三条约束，F1 的风险会重新出现。plan review 应将此项作为必检项"。plan 未选定具体排序字段，将决策进一步推迟到实现阶段，违反了 design review 的明确 handoff 要求。
- **直接证据**:
  - design.md line 3263: "后续 code-generation-ready plan 必须基于该原则选择稳定排序字段和排序方向"
  - `docs/reviews/wu-cm-12-design-writeback-rereview-ds-20260618.md` residual risk 1: "plan review 应将此项作为必检项"
  - plan Section 9: 无排序确定性断言
- **影响**: 实施 agent 跌入设计决策，可能选择不满足三条约束的字段；测试无法验证排序正确性；ordinary / compact / fallback 路径可能使用不同排序策略。
- **建议改法和验证点**:
  1. plan Section 7 Decision 5 应选定具体排序字段，例如"within-section item ordering 使用 `event_sequence` descending（有 EventLog sequence 时）或 material block order（无 sequence 时）"。
  2. Expected Assertions 应增加"tier 2 degrade 后 section 内 item 按 `event_sequence` descending 排列（有 sequence 时），排序在相同 input cursor 和 policy 下可确定性复现"。
  3. S4 tests 应增加排序确定性断言：构造含多个同 section item 的 material，degrade 后验证保留 item 的顺序。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-中-tier 1/2/3 各 tier 缺少独立行为测试

- **位置**: Section 8 S4 (line 239-274), Section 9 Expected Assertions (line 312-323)
- **问题类型**: 测试缺口
- **当前写法**: S4 completion signal 写"Tests show tier 1/2/3 accepted output commits CONTEXT_COMPACTED; tier 4/5 dispatch fallback writes CONTEXT_COMPACTION_FAILED without compact artifact; all section-aware degrade forbidden actions are asserted absent"。Expected Assertions 写"Tier 1-3 accepted compact recovery writes CONTEXT_COMPACTED; tier 4-5 dispatch fallback does not write compact artifact...has CONTEXT_COMPACTION_FAILED diagnostic evidence"。
- **反例/失败场景**: 如果测试只验证"tier 1-3 作为一个整体写 CONTEXT_COMPACTED"，不区分各 tier 的具体行为，可能出现：tier 2 的 section-aware degrade 逻辑有 bug 但被 tier 1 或 tier 3 的成功路径掩盖；tier 3 delta-only 逻辑未测试空 compacted view 场景；tier 1 的 tighter recent window 未验证使用了 `fallback_selected_recent_window_*` caps 而非 normal caps。
- **为什么有问题**: design.md 为每个 tier 定义了不同的 material assembly 语义（tier 1: tighter recent window; tier 2: degraded compacted view + tighter recent window; tier 3: delta-only）。如果测试不区分各 tier，无法验证每个 tier 的特定行为是否正确实现。这是 behavioral coverage gap，不是 merely cosmetic。
- **直接证据**:
  - design.md line 3208-3241: tier 1/2/3 各自不同的 assemble 参数
  - plan S4 completion signal: "tier 1/2/3 accepted output commits CONTEXT_COMPACTED" — 未区分各 tier
  - plan Expected Assertions: 同上
- **影响**: 某个 tier 的实现 bug 可能被其它 tier 的成功路径掩盖，直到生产中触发特定 tier 条件时才暴露。
- **建议改法和验证点**:
  1. S4 Expected Assertions 应分别断言：
     - tier 1: 使用 `fallback_selected_recent_window_*` caps 构造 compact input，accepted output 写 `CONTEXT_COMPACTED`
     - tier 2: 使用 section-aware degraded compacted view + fallback caps，degrade 后 section priority 正确，禁止动作断言通过
     - tier 3: 使用空 compacted view + bounded delta，accepted output 写 `CONTEXT_COMPACTED`
  2. S4 tests 应为每个 tier 构造独立的触发场景（如 tier 1 需要 tighter window，tier 2 需要 oversized compacted view，tier 3 需要所有 section 都超出 budget）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-低-S1 范围较宽，跨三个模块

- **位置**: Section 8 S1 (line 106-147)
- **问题类型**: 切片过粗
- **当前写法**: S1 allowed files 包含 `compact_material.py`、`memory.py`、`run_input.py`，涉及 turn_group_id 添加、CURRENT_INPUT_ANCHOR_TEXT_MAX_CHARS 移除、_bounded_text 替换、evidence chunk provenance 强化等多个变更。
- **反例/失败场景**: 单个实现 agent 需要在三个模块中做协调变更，可能在某个模块中遗漏或不一致。例如，在 `compact_material.py` 中添加了 `turn_group_id` 但忘记在 `memory.py` 的 builders 中填充。
- **为什么有问题**: S1 的变更目标是内聚的（统一 material policy owner），但跨模块协调增加了实现出错概率。不过，这是架构现实——material block 在三个模块中创建/使用——不是 plan 的切分失败。
- **直接证据**: plan S1 allowed files 列出三个模块；每个模块的变更都服务于同一个 "single policy owner" 目标。
- **影响**: 低。实现 agent 有明确的 allowed files、functions 和 call paths 列表，可以按图索骥。
- **建议改法和验证点**: 可接受当前切分。建议实现 agent 在 S1 completion 时运行 `rg -n 'turn_group_id' dayu/host/compact_material.py dayu/host/memory.py dayu/host/run_input.py` 确认所有 builders 都已填充。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-低-selected-id/source-ref provenance guard 未覆盖 turn-group 内一致性

- **位置**: Section 8 S3 (line 195-230)
- **问题类型**: 契约缺失
- **当前写法**: S3 exact changes 写"Strengthen `_fallback_context_messages` to check not only missing ids but also current input source ref, duplicate ids, selected source refs and fallback digest consistency when available"。
- **反例/失败场景**: fallback selection 选中了同一 turn_group_id 的多个 block，但其中某个 block 的 payload 已损坏或 source ref 不一致。当前 check 只验证"selected id 存在于 material view""source ref 一致""无重复 id"，不验证同一 turn group 内的 block 是否具有相同的 `turn_group_id`。如果 selection 逻辑有 bug 错误混合了不同 turn group 的 block，当前 guard 不会捕获。
- **为什么有问题**: design.md 要求"selected material provenance 不一致，继续 dispatch 会污染事实边界"作为 fail closed 条件。如果同一 selection 中的 block 来自不同 turn group（provenance 不一致），应 fail closed。当前 guard 不覆盖此场景。
- **直接证据**:
  - design.md line 3265: "selected material provenance 不一致，继续 dispatch 会污染事实边界"
  - plan S3: guard 列表未包含 turn-group 内一致性
- **影响**: 低概率但高影响——如果 selection 逻辑有 bug，provenance 不一致的 material 可能进入 LLM prompt。
- **建议改法和验证点**: S3 `_fallback_context_messages` 强化应增加：如果 selected blocks 中属于同一 protected turn group 的 block 的 `turn_group_id` 不一致，raise `HostDurableError`。测试应构造 turn-group 混合场景验证该 guard。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 05-未修复-低-S1/S2 未显式处理 durable payload 损坏场景

- **位置**: Section 8 S1 error handling (line 128-133), Section 8 S2 error handling (line 170-176)
- **问题类型**: 状态机漏洞
- **当前写法**: S1 error handling 写"Missing turn_group_id is allowed only for stable semantic material"和"LLM-facing text cannot be silently shortened"。S2 error handling 写"Floor wins over item/char caps"和"Selected ids must be unique"。
- **反例/失败场景**: 构建 material block 时，EventLog 中的 payload reference 指向已损坏或缺失的 payload。当前 S1/S2 error handling 不覆盖此场景。虽然 plan Risks section (line 336) 提到"If any material path lacks run_id...implementation must trace the EventLog source"，但这只覆盖了 `run_id` 缺失，不覆盖 payload 损坏。
- **为什么有问题**: design.md line 3265 明确将"durable EventLog、payload 或 artifact 损坏，导致 Host 无法构造可信 LLM-facing 输入"列为 fail closed 条件。S1/S2 是 material block 构建阶段，如果在此阶段遇到 payload 损坏，应有明确的 error handling 路径。
- **直接证据**:
  - design.md line 3265: fail closed 条件 #2
  - plan S1/S2: error handling 未覆盖 payload 损坏
- **影响**: 低。plan 的 stop condition 和 Risks section 已覆盖部分场景，且现有代码 (`_fallback_context_messages` 的 missing id check) 已有 fail-closed 机制。但 S1/S2 新增的 `turn_group_id` 填充逻辑可能在 payload 损坏时产生未处理异常。
- **建议改法和验证点**: S1 error handling 增加"如果 EventLog payload 损坏导致 material block 无法构造，emit memory budget diagnostic 并 whole-drop 该 block；如果 drop 后剩余 material 不足以满足 floor，按 fail closed 处理"。测试应构造 payload 损坏场景。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open Questions

### OQ-1: `MemoryProjectionPolicy` 是否已包含 fallback selected window caps

S2 要求"Apply `fallback_selected_recent_window_item_cap` and `fallback_selected_recent_window_char_cap` from `MemoryProjectionPolicy` in fallback selection"。plan Section 4 提到 `MemoryProjectionPolicy` 已有 typed fields 和 fallback caps 验证，但未明确这两个字段是否已存在于当前代码中。如果不存在，S2 需要将它们添加到 `MemoryProjectionPolicy`、`host_assembly.py` 映射和 `config_loader.py` 映射——这会扩大 S2 的范围并可能触及 plan Section 5 未列出的文件。

**建议**: implementation agent 在 S2 开始前先 `rg -n 'fallback_selected_recent_window_item_cap\|fallback_selected_recent_window_char_cap' dayu/` 确认字段是否已存在。若不存在，在 S2 allowed changes 中增加字段定义和配置映射。

### OQ-2: `context_window_size` 是否应作为 selected recent window caps 的比例参数

design.md DS review residual risk 4 指出 `context_window_size` 在设计中未显式声明"不作为 selected recent window caps 的比例参数"。讨论稿明确说"不是 selected_recent_window_policy 的直接比例参数"，但 design.md 未写此否定句。plan 未提及此问题。

**建议**: 不阻塞 plan，但 implementation agent 应注意 `selected_recent_window_*` caps 是绝对值而非 `context_window_size` 比例。
