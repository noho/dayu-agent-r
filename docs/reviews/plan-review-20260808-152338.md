- 绑定依据：`docs/gateflow/pr-190-f18-goal-confirmation-amendment-20260808.md`、`docs/gateflow/pr-190-f18-fixed-profile-path-adjudication-20260808.md`

- 复审范围：R1-R14 source boundary、premature compaction、provider/operation/wall budget、B1 raw outcome、publication finalizer、再次出现 `runner_candidate_invalid` 时的停止条件

## 结论

**fail**。当前 plan 不应进入真实 provider 执行。`0.001` soft ratio 与 protected recent floor 的 owner 语义不支持“R7 首次 baseline、R13 第二次 target”的时序；按当前 fixed profile，首个有 citable boundary 的 operation 会在目标状态形成前出现。另有 provider-call/wall cap 未被冻结 harness 强制、B1 raw `execution_outcome` 错配、final scan 文件名违反 tracked helper contract 三项 material gap。

## 已直接验证并成立的部分

1. ordinary-call 算术本身一致：`R1=10`、`R2-R7=6`、`R8=7`、`R9-R13=5`，合计 `28`；reconnect `R14=1`，合计 `29`。两个 operation、每个最多五次 compactor attempt，对应 `10` 次 compactor calls；三条候选链各 `600s` 相加为 `1800s`（`docs/gateflow/pr-190-f18-plan-20260808.md:164-177`）。这只证明预算表算术，不证明可执行时序或 hard enforcement。
2. adaptive branch 顺序没有把自然未触发伪装成 PASS；缺失 branch 才启动独立链，单链结果不得覆盖另一链失败（同文件 `:171-177`）。
3. 再次出现 `runner_candidate_invalid` 时停止整个 B2、禁止其它成功链掩盖并重新进入 owner investigation，符合 goal amendment（同文件 `:179-182`）。
4. B1 六个 planned digest 与既有 public bundle 的实际 digest 一致；问题不在 digest，而在 raw process outcome 的字段投影。

## Material findings

### F18-DS-RR-001 — 高 — R1-R14 的 protected-floor/soft-trigger 时序不成立，两个 operation 会在 R7/R13 前被消耗

- **受影响 slice / 步骤**：Slice 2，fixed profile、Shared PTY Run state machine、premature compaction seal。
- **当前写法**：profile 固定 `standard-256k`、soft ratio `0.001`、recent turn floor `4`；plan 预期 R7 才触发 baseline，R13 才触发 target，并声称 R13 时保护的是 R9-R12、R8 此时才首次离开 floor；只在 R7 与 R13 之间出现额外 request 时 seal（`docs/gateflow/pr-190-f18-plan-20260808.md:128-132,143-160`）。
- **失败场景 / 反例**：
  1. `standard-256k` 的 `context_window_size=262144`（`dayu/config/execution_profiles.json:26`），owner 以 `floor(window * ratio)` 计算 soft threshold，因此 `0.001` 得到 **262 tokens**（`dayu/host/context_budget.py:1561-1571`）。现有 Trial2 typed owner projection 已直接观察 production candidate `estimated_input_tokens=21548`、soft threshold `1048`；同一生产 candidate 量级显著高于新 profile 的 262-token threshold，不存在等到 R7/R13 才越 soft threshold 的数据依据。
  2. 当前 `USER_INPUT_ACCEPTED` 也进入 delta material：source view 读取到 current event sequence，并把 user row 映射为带当前 `run_id` 的 turn group（`dayu/host/compact_material.py:620-635,3104-3131,3187-3212`）。floor owner 按 event sequence 逆序保护最近 N 个 group（同文件 `:2267-2303`）。因此 R5 pre-dispatch 时保护的是 **R5、R4、R3、R2**，R1 已是第一个 eligible group；selection 会选择所有未被 floor 排除的 atomic unit（同文件 `:1074-1156`）。soft threshold 已越界且 boundary 非空时，dispatch 会真正创建 compact request；只有 boundary 为空才 ordinary fallback（`dayu/host/dispatch.py:2964-3044`）。所以首个 operation 的 owner 时点是 R5，不是 R7。
  3. 即使人为假定 R7 baseline 已 accepted，R1-R3 被消费后，R4-R7 仍是 unconsumed recent groups；到 R8 时最近四组为 R8-R5，R4 已 eligible。低 soft threshold 会立即产生第二个 operation，而不是等 R13。
  4. R13 pre-dispatch 的最近四组包含当前 R13，因此 protected set 是 **R13、R12、R11、R10**，不是 plan 所写的 R9-R12；R8 在 R12 已离开 floor，R9 在 R13 离开 floor。R13 可以在“没有提前 operation”的反事实下同时选到 R8/R9，但当前 ratio 不允许该反事实持续到 R13。
- **影响**：baseline/target operation identity、initial source boundary、FY2025/unsupported material coexistence和两-operation budget均不可按 plan 取得。直接执行只会提前 seal 或浪费真实 MiMo calls，不能形成 B2 mandatory evidence。
- **建议改法和验证点**：
  1. 在任何 provider call 前，用冻结后的 production candidate estimator 与 selection owner生成 provider-independent dry plan，逐 R 列出 exact `estimated_input_tokens`、soft/hard threshold、unconsumed group ids、protected group ids、selected source refs和预计 operation ordinal；不得沿用 Trial2 hot-switch 时序推断 fixed-profile cadence。
  2. 重新设计 fixed profile threshold与turn grouping，使 baseline 前只有目标 FY2024 source 首次触发，baseline 后直到 FY2025 evidence和unsupported material同时 eligible才触发第二次；可选择调整 threshold/R13触发输入或把新事实与unsupported material放入同一合法 atomic turn，但必须由上述 exact owner projection证明，不得凭 Run ordinal猜测。
  3. premature seal 应覆盖 **首个 provider call之后到 target accepted之前的任何 unexpected operation/request**，而不只是 R7-R13；每轮 canonical terminal后核对 typed selection/operation state再决定是否进入下一轮。

### F18-DS-RR-002 — 高 — 29/28 provider calls 与 600/1800 秒目前是估算，不是 plan 所称 hard cap

- **受影响 slice / 步骤**：Slice 2，frozen harness 与 Evidence-calibrated execution matrix。
- **当前写法**：plan 说更小 external call caps authoritative，冻结 `AgentPolicy.max_iterations=24`，复用不修改的 harness，并把每链 `600s`、总计 `1800s`称为硬封顶（`docs/gateflow/pr-190-f18-plan-20260808.md:132-137,164-177`）。
- **失败场景 / 反例**：冻结 harness digest 对应的 CLI surface 只有 per-segment `--timeout-seconds`，没有 cumulative ordinary-provider-call/compactor-call guard；单个 Host Run 内模型可以继续迭代到 fixed `max_iterations=24`。历史 R1=10、R8=7只是观测值，真实 MiMo 自然路径可在某一 Run 内超过估算，executor只能在 Run terminal后发现累计 calls 已超 29/28。类似地，如果每个 PTY segment都传 `600`，多 segment chain 的总 wall time可以远超 600；只有维护 chain monotonic deadline并把“剩余时间”传给每个 segment才能形成 chain hard cap。
- **影响**：当前 matrix不能兑现“bounded observation”的硬上限；source timing修好后仍可能超用 provider，且 public execution index无法诚实声称硬预算得到强制。
- **建议改法和验证点**：把 `29/28`明确降级为估算，或在不破坏 fixed configuration的 observation owner 中增加可验证的 cumulative provider-call guard；若仍保持“hard cap”，必须说明 owner、停止动作和单 Run 内如何阻止 overshoot。wall budget必须冻结 `chain_started_monotonic`/`chain_deadline`，每次 harness调用传入 exact remaining seconds，并在 public summary对账三条 attempted chain 的 elapsed sum `<=1800s`。两 operation/十 compactor calls可继续依赖 Host attempt cap加逐 Run operation ledger，但要在每次下一 prompt 前 fail closed。

### F18-DS-RR-003 — 中 — B1 把 non-zero raw process 结果投影为 `execution_outcome="success"`

- **受影响 slice / 步骤**：Slice 1，B1 exact adjudication projection。
- **当前写法**：同一记录写 `execution_outcome="success"` 与 `exit_codes=[1]`，并用 canonical `RUN_SUCCEEDED`解释 cleanup EOT/process exit不改变业务正确性（`docs/gateflow/pr-190-f18-plan-20260808.md:81-92`）。
- **失败场景 / 反例**：handbook 明确把 `execution_outcome` 定义为 per-scenario **raw process observation**，只能记录实际 `success/error/timeout/cancel`；canonical correctness/evidence/oracle是独立维度（`docs/cli_ci.md:370-383`）。`RUN_SUCCEEDED`足以支持 accepted Oracle，但不能把 exit 1 的 raw process outcome改写为 success。合法 `error`不会自动使 observation incomplete，也不会阻止 accepted adjudication（同文件 `:365-373`）。
- **影响**：B1 accepted 结论本身仍可成立，但 registry/handbook会持久化跨 owner 的矛盾事实，违反 exact projection要求。
- **建议改法和验证点**：将 B1 `execution_outcome`按 raw owner改为 `error`（若现有 schema以其它 typed mapping表示，则先给出该 owner 的直接证据），保留 `exit_codes=[1]`；同时继续写 `evidence_status="sufficient"`、`gap_kind="none"`、`conformance_at_observation="matches-accepted-oracle"`和 accepted adjudication。逐字段 JSON/diff check证明 B2/readiness未变化。

### F18-DS-RR-004 — 中 — final scan 文件名与 tracked final-tree helper 的 fail-closed contract冲突

- **受影响 slice / 步骤**：Slice 3，public/private publication finalizer。
- **当前写法**：public tree和最后 writer使用 `secret-path-scan.json`（`docs/gateflow/pr-190-f18-plan-20260808.md:201-213`）。
- **失败场景 / 反例**：handbook要求 final metadata先落盘，随后 tracked helper独占创建唯一 `secret-scan.json`，且该文件是唯一允许自排除项（`docs/cli_ci.md:1394-1400`）。tracked helper把文件名定义为常量并对任何其它名字直接 `ValueError`（`utils/cli_ci_run_observation.py:39-45,856-879`）。plan又明确不修改冻结 tooling，因此 `secret-path-scan.json`不可能由合法 helper产生。
- **影响**：按 plan 执行会在 final publication失败，或迫使 executor绕开/修改 tooling；两者都使 digest、execution index和registry refs无法形成单一公开真源。
- **建议改法和验证点**：全量改回 exact `secret-scan.json`；先落盘 report、accepted projections、summary、final execution index与digest，再让 tracked helper独占写 scan，之后零写入。execution index只能预写 scan的relative record path，不得复制尚未产生的 status/digest；冻结并记录实际 finalizer/helper digest，扫描 descriptor必须包含 digest与此前全部 public files，只排除 scan自身。

## Assumptions challenged

1. **“四个 completed turns后R8才离开floor”**：不成立；current pre-dispatch group参与最近四组，R8在R12离开，R9在R13离开。
2. **“低ratio只负责在指定R触发”**：不成立；threshold owner只看完整candidate estimate，不知道scenario指定的R7/R13语义。
3. **“历史calls数量等于hard cap”**：不成立；历史值只能校准估算，冻结 harness没有累计call guard。
4. **“canonical Run成功可以覆盖process exit”**：不成立；两者有独立owner和字段。
5. **“final scan可自行换名”**：不成立；tracked helper精确拒绝非 `secret-scan.json`。
