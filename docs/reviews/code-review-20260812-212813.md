### 1. Strict status owner

`_upload_terminal_disposition_from_status` 通过 `_UPLOAD_TERMINAL_DISPOSITIONS` dict 做 exact lowercase 匹配，不做 strip/lower/别名/默认值。`_required_upload_result_status` 从 pipeline result 读取原始 status 字符串，不做归一化。`FinsUploadPipelineResult.from_pipeline_json` 和 `FinsUploadResultSummary.__post_init__` 各自调用 `_upload_terminal_disposition_from_status` 做入口校验。非法值（`"uploaded"`, `"unknown"`, `"OK"`, `" ok"`, `"ok "`, `""`, `"CANCELLED"`）全部被 `ValueError` 拒绝，测试 `test_upload_status_owner_rejects_unknown_case_and_whitespace_variants` 覆盖。**无问题。**

### 2. FinsUploadPipelineResult / FinsUploadResultSummary 同源

两者共用同一个 `_upload_terminal_disposition_from_status` 做 status 闭集校验。pipeline result 的 `from_pipeline_json` 在构造前校验，summary 的 `__post_init__` 在构造后校验。两者对同一 status 值产生相同 disposition，测试 `test_upload_status_owner_maps_only_exact_production_statuses` 验证了 `ok/skipped/deleted/failed/cancelled` 五个值的双端一致性。**无问题。**

### 3. claim_upload_summary 四时点与 cancelled/failed/completed 单终态

`_DirectStreamCancellationState.claim_upload_summary` 在 `_lock` 内原子操作：检查 `_consumer_aborted` 和 `_terminal_status`，已有终态返回 `None`。不检查 `_cancellation_requested`（与 `claim_terminal` 不同），因为 upload runner 的 summary 本身已反映了取消语义——runner 在 final checkpoint 前观察到取消返回 `cancelled`，publication 已提交后返回 `ok/skipped/deleted/failed`。

四个时点测试覆盖：
- **时点 a**（final checkpoint 前取消）：`test_direct_upload_cancel_before_final_checkpoint_returns_only_cancelled_terminal` / `test_durable_upload_cancel_before_final_checkpoint_saves_only_cancelled` — 只产出 cancelled，不产出 completed。
- **时点 b**（publication commit 后、summary 返回前取消）：`test_direct_upload_cancel_after_commit_before_summary_keeps_completed` / `test_durable_upload_cancel_after_commit_before_summary_keeps_completed` — completed 不被 late cancel 改写。
- **时点 c**（accepted summary 返回后、claim/save 前取消）：`test_direct_upload_cancel_around_summary_claim_keeps_progress_result_atomic` / `test_durable_upload_cancel_before_atomic_save_keeps_accepted_summary` — accepted summary 不被改写。
- **时点 d**（claim/save 后取消）：同上参数化 / `test_durable_upload_cancel_after_atomic_save_keeps_single_terminal` — 不产生第二终态。

**无问题。**

### 4. Late cancel 不覆盖 accepted summary

`claim_upload_summary` 不读取 `_cancellation_requested`，只检查 `_terminal_status`。一旦 claim 成功，后续 `request_cancel()` 虽然设置 `_cancellation_requested=True`，但 `_terminal_status` 已非 `None`，任何后续 claim/terminal 操作都返回 `None`。`test_direct_upload_summary_claim_is_single_terminal_and_ignores_late_cancel` 验证了 claim 后 late cancel 和 second claim 都返回 `None`。**无问题。**

### 5. durable save_accepted_upload_terminal_if_active 在 file lock 内处理 CANCELLING/已有 terminal/字段一致性

`FsFinsIngestionJobStore.save_accepted_upload_terminal_if_active` 实现：
1. 调用 `_validate_accepted_upload_terminal_fields` 做前置校验（disposition 非 cancelled、result_summary/failure_summary 有界、status 与 disposition 一致、completed 无 failure_summary、failed 有 failure_summary）。
2. 在 `file_lock` 内：检查 `operation_kind is UPLOAD`，检查 `record.status in _TERMINAL_STATUSES`（CANCELLING 不在终态集中，所以 CANCELLING 状态的 record 会被覆盖），`replace()` 保留原 record 的 `cancellation_requested` 字段。

`test_accepted_upload_terminal_store_rejects_mismatch_and_preserves_existing_terminal` 覆盖了：cancelled disposition 被拒绝、status/disposition 不一致被拒绝、completed 带 failure_summary 被拒绝、failed 无 failure_summary 被拒绝、已有终态不被覆盖。**无问题。**

### 6. save 后 projection 或 append event 失败是否制造双终态/错误改写

在 `_run_upload_job` 中，`save_accepted_upload_terminal_if_active` 之后调用 `_upload_terminal_disposition_from_job_record`、`_upload_context_persisted_summary_progress_payload`、`_emit_progress_event`、`_append_terminal_job_event_warn`。若任何一步抛异常，传播到 `except Exception` → `_save_failed_from_exception`。该方法读取 record 后检查 `record.status in _TERMINAL_STATUSES`，已是终态则直接 return，不做二次写入。**不会制造双终态。**

### 7. cancellation_requested audit flag

`save_accepted_upload_terminal_if_active` 使用 `replace(record, status=..., updated_at=..., finished_at=..., result_summary=..., failure_summary=...)`。`replace()` 只替换显式列出的字段，`cancellation_requested` 保留原值。若 `request_cancel` 先执行（设 `cancellation_requested=True`、`status=CANCELLING`），后续 save 读取该 record 并 `replace` 时保留 `cancellation_requested=True`。`test_durable_upload_cancel_after_commit_before_summary_keeps_completed` 验证了 `record.cancellation_requested is True` 且 `record.status is SUCCEEDED`。**无问题。**

### 8. cancelled 无 completed

direct 路径：`_produce_direct_upload` 中 `if disposition is not FinsUploadTerminalDisposition.CANCELLED` 才发 completed progress。cancelled 只发 RESULT（exit 130）。durable 路径：`_run_upload_job` 中 `if saved_disposition is not FinsUploadTerminalDisposition.CANCELLED` 才发 progress。cancelled 走 `save_cancelled_if_active`，只 append terminal event。**无问题。**

### 9. failed progress/result 一致

`_upload_completed_progress_type(FAILED)` 返回 `completed_with_failures`。direct 路径 `_emit_claimed_direct_result` 中 `disposition is FAILED` 时设 `error_kind=EXECUTION`、`error_message=direct_upload_failed_status_message()`。durable 路径 `_run_upload_job` 中 failed 走 `save_accepted_upload_terminal_if_active` 并写 `failure_summary`，`_upload_terminal_disposition_from_job_record` 校验 `record.status=FAILED` 与 `result_summary.status=failed` 一致。`test_start_upload_failed_status_emits_completed_with_failures_progress` 验证了 record.status=FAILED、failure_summary 非空、progress 类型正确。**无问题。**
