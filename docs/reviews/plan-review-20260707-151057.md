## Findings

### F01-未修复-中-`<when_tag fins>` block 粒度不足导致 prompt scene 泄漏 ingestion 指引

- **位置**: Plan "过滤规则" 章节（line 82-87）; `dayu/config/prompts/base/tools.md` lines 39-65
- **问题类型**: 架构边界 / 契约缺失
- **当前写法**: Plan 定义 `<when_tag TAG>` 过滤规则为"仅当本 scene selected tools 中至少一个工具拥有 TAG 保留 block body"。`tools.md` 中 `<when_tag fins>` block（lines 39-65）包含 Fins 全量指引，涵盖 download、preprocess、upload 等 ingestion 操作。
- **反例/失败场景**: `prompt.json` 的 `tool_tags_any` 为 `["fins-read", "web", "utils"]`。fins-read 工具（如 `get_financial_statement`、`get_company_profile`）携带 `fins` tag。按 plan 的过滤规则，`<when_tag fins>` block 会被保留，因为 selected tools 中有工具拥有 `fins` tag。但该 block 包含 ingestion 指引（download/preprocess/upload 说明），这些指引对 prompt 单轮场景不适用。
- **为什么有问题**: Plan 的成功信号 line 49 要求"prepared prompt 不包含未选中工具的指引"，但 `<when_tag fins>` block 粒度太粗，fins-read 和 fins-download/preprocess/upload 共享 `fins` tag，无法区分。Plan 没有要求拆分 `<when_tag fins>` block 或引入更细粒度 tag（如 `fins-read` vs `fins-ingestion`）。
- **直接证据**:
  - `tools.md` line 39: `<when_tag fins>` — 包含全文 Fins 指引
  - Plan line 82: `<when_tag TAG>` 过滤规则仅检查 tag 存在性
  - `prompt.json` line 20-24: `tool_tags_any` 包含 `fins-read`
  - fins-read 工具携带 `fins` tag（代码事实）
- **影响**: 实施 Agent 按 plan 实现后，prompt scene 的 system prompt 仍会包含 download/preprocess/upload 的使用指引，LLM 可能尝试调用未暴露的长事务工具。
- **建议改法和验证点**:
  1. 将 `tools.md` 中 `<when_tag fins>` 拆分为 `<when_tag fins-read>`（只包含 read 指引）和 `<when_tag fins-ingestion>`（包含 download/preprocess/upload 指引），或对 ingestion 指引改用 `<when_tool start_fins_download>` 等更精确的标记
  2. 验证：prompt scene 的 system_prompt 不包含 "download"、"preprocess"、"upload" 相关指引文本
- **修复风险（低/中/高）**: 低 — 只需调整 `tools.md` 标记结构
- **严重程度（低/中/高/严重）**: 中

### F04-未修复-低-`<when_tag>` 过滤需要 tag 到 selected tools 的反向映射，Plan 未指定实现路径

- **位置**: Plan "过滤规则" line 83; "Scene 条件块过滤" line 78
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: "`<when_tag TAG>`：仅当本 scene selected tools 中至少一个工具拥有 TAG 保留 block body"
- **反例/失败场景**: `SceneToolCatalog` 没有 `tags_for_name(name)` 方法，只有 `names_for_any_tag(tags)` 正向查询。实现条件块过滤时，需要从 selected tool names 反查 tags。Plan 没有指定是：
  1. 给 `SceneToolCatalog` 新增 `tags_for_names(names)` 方法
  2. 在过滤前构建 `selected_tool_name -> tags` 映射
  3. 直接用 `catalog.tools` tuple 遍历
- **为什么有问题**: 实施 Agent 需要自行决定实现路径，可能导致不同 slice 的实现不一致。
- **直接证据**:
  - `scene_prepare.py` line 171: `names()` 返回 `frozenset[str]`
  - `scene_prepare.py` line 179: `names_for_any_tag(tags)` 是唯一 tag 查询方法
  - `SceneToolInfo` line 108: 有 `name` 和 `tags` 字段
- **影响**: 低 — 实施 Agent 可以从 `catalog.tools` 遍历构建映射，但 plan 缺少明确指引。
- **建议改法和验证点**: Plan 应指定实现路径，例如"在过滤函数内部构建 `selected_tags = frozenset.union(*(t.tags for t in catalog.tools if t.name in selected_names))`，然后用 `selected_tags` 检查 `<when_tag TAG>`"。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/严重）**: 低

## Architecture Boundary Review

Plan 的分层落点总体正确：
- `dayu.runtime.scene_prepare` 只做层中立条件块过滤 — **符合约束**
- `dayu.fins.resolver` 放 FMP 公司信息 public contract — **符合约束**
- `dayu.service.prompt_context` 放 LLM-facing slot function — **符合约束**

但 F01 暴露了一个边界问题：`tools.md` 的 `<when_tag fins>` block 粒度不足，导致 runtime 过滤无法区分 read-only 和 ingestion 指引。这是 prompt asset 设计问题，不是 runtime 实现问题。

## Overengineering Review

Plan 没有过度设计：
- 不引入 workflow、动态 tool profile、Host/Engine contract 变更或 durable schema
- FMP resolver 只迁移最小公司信息 public contract
- 条件块过滤只补全已有 manifest 语义

## Overcoupling Review

Plan 的 3 slices 耦合度合理：
- S1（runtime 过滤）独立于 S2（FMP resolver + slot builder）
- S3（docs + validation）依赖 S1/S2 完成
- 但 S2 内部耦合了 FMP resolver 和 CLI slot builder，如果 FMP resolver 实现延迟，slot builder 仍可独立完成（fallback to ticker-only）

## Optimal-Solution Review

Plan 的方案是 credible alternatives 中最实际的路径：
- 条件块过滤放在 ScenePrepare（已有 manifest 解释权）比放在 CLI/Service/Engine 都更合理
- FMP resolver 放在 `dayu.fins.resolver` 比放在 CLI 或 Service 更可复用
- Slot function 放在 Service 比放在 CLI 更避免复制

## Conclusion

**pass-with-findings**

Plan 的 root cause 识别准确，分层落点正确，slices 切分合理。主要问题是 F01（`<when_tag fins>` block 粒度不足）需要在 S1 实现时解决，以及 S1 的 plan 文本与 checkpoint 状态不同步（F02）。其余 findings 为低风险的契约规格补充。
