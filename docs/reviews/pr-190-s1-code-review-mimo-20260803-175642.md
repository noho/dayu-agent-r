## Findings

### S1-01-未修复-低-修复 marker 定义与当前 renderer 输出不一致

- **入口/函数**: `_user_prompt_vnext`（`dayu/host/llm_compaction.py` line 667）与两份 prompt asset
- **文件(行号)**:
  - `dayu/config/prompts/scenes/conversation_compaction.md:17` — 定义 `REPAIR_FEEDBACK_JSON_BEGIN` / `REPAIR_FEEDBACK_JSON_END`
  - `dayu/config/prompts/scenes/conversation_compaction_user.md:72` — 同上
  - `dayu/host/llm_compaction.py:667` — 当前 renderer 使用 `PREVIOUS_VALIDATION_REPORT_JSON`
- **输入场景**: 模型首次输出被 Context Governance 拒绝后，renderer 触发 repair 路径
- **实际分支**: S1 prompt 定义了 `REPAIR_FEEDBACK_JSON_BEGIN` / `REPAIR_FEEDBACK_JSON_END` 作为 repair block 的起止 marker；renderer 仍使用 `PREVIOUS_VALIDATION_REPORT_JSON` 作为单行 marker
- **预期行为**: prompt 对模型描述的 marker 与 renderer 实际输出的 marker 一致
- **实际行为**: 模型收到 prompt 指令"如果请求末尾出现 `REPAIR_FEEDBACK_JSON_BEGIN` 与 `REPAIR_FEEDBACK_JSON_END`"，但实际 repair prompt 中出现的是 `PREVIOUS_VALIDATION_REPORT_JSON`。模型不会看到 `REPAIR_FEEDBACK_JSON_BEGIN`，prompt 中关于该 marker 的规则不会激活；同时模型看到一个 prompt 未定义的 marker
- **直接证据**:
  - prompt line 17: `收到由 \`REPAIR_FEEDBACK_JSON_BEGIN\` 与 \`REPAIR_FEEDBACK_JSON_END\` 包围的修复反馈时`
  - renderer line 667: `+ "\n\nPREVIOUS_VALIDATION_REPORT_JSON\n"`
  - 测试 line 260-261: `assert "PREVIOUS_VALIDATION_REPORT_JSON" not in first_prompt` / `assert "PREVIOUS_VALIDATION_REPORT_JSON" in repair_prompt`（断言 renderer 当前行为）
  - 测试 line 302-303: `assert "REPAIR_FEEDBACK_JSON_BEGIN" in user_prompt` / `assert "REPAIR_FEEDBACK_JSON_END" in user_prompt`（断言 prompt 定义）
- **影响**: 低。repair 路径在首次 candidate 被拒后才触发，且当前 model 仍可从 `PREVIOUS_VALIDATION_REPORT_JSON` 后的 JSON 内容推断修复意图；但 prompt 定义与 renderer 输出的不一致增加认知负担，且在 S1→S2 过渡窗口内，若 prompt asset 先于 renderer 更新部署，模型可能忽略 repair feedback
- **建议改法和验证点**: S2 统一 renderer 的 repair marker 为 `REPAIR_FEEDBACK_JSON_BEGIN` / `REPAIR_FEEDBACK_JSON_END`，同步更新 `test_llm_compaction.py` line 260-261 的断言；验证 rendered repair prompt 包含新 marker 且 JSON 可解析
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低（S2 已计划闭合，当前 renderer 行为未变）
