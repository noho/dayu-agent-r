## Findings

### 1-未修复-中-download/upload `completed_with_failures` progress 事件无直接测试覆盖

- **入口/函数**: `_download_completed_progress_type`、`_upload_completed_progress_type`
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:3639-3654`、`dayu/fins/ingestion_runtime.py:3760-3776`
- **输入场景**: download adapter 返回 `failed_count > 0`；upload runner 返回 `status == "failed"`
- **实际分支**: `_download_completed_progress_type` 走 `summary.failed_count > 0` 返回 `_PROGRESS_DOWNLOAD_COMPLETED_WITH_FAILURES`；`_upload_completed_progress_type` 走 `summary.status.strip().lower() == "failed"` 返回 `_PROGRESS_UPLOAD_COMPLETED_WITH_FAILURES`
- **预期行为**: 有测试直接证明 `completed_with_failures` source_event_type 和对应 message 被正确写入 event sidecar
- **实际行为**: 全部 download/upload progress 测试只覆盖 `download.completed` / `upload.completed` 路径，无测试覆盖 `download.completed_with_failures` / `upload.completed_with_failures`
- **直接证据**: `tests/fins/test_fins_ingestion_runtime.py` 中所有 progress event 断言只检查 `"download.started"` / `"download.completed"` / `"upload.started"` / `"upload.completed"`；`grep completed_with_failures tests/` 无结果
- **影响**: 若 `_download_completed_progress_type` 或 `_upload_completed_progress_type` 的条件判断写反或阈值错误，无测试能捕获回归
- **建议改法和验证点**: 新增测试用例，使用 fake adapter 返回 `failed_count=1`，断言 `source_event_type == "download.completed_with_failures"` 和 `message == "下载已完成，存在失败候选"`；同理为 upload 新增 `status="failed"` 测试
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-低-preprocess 循环内 `_emit_progress_event` 使用快照 record 而非最新 latest

- **入口/函数**: `_execute_preprocess_request`
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:2180-2256`
- **输入场景**: preprocess 文档处理循环内每次迭代
- **实际分支**: 循环内已通过 `self.job_store.read_job(record.job_id)` 读取 `latest` 检查取消，但 `_emit_progress_event(record, ...)` 仍使用函数入口传入的 `record` 快照
- **预期行为**: progress event 的 `status` 字段反映 event 追加时刻的 job 状态
- **实际行为**: progress event 的 `status` 始终为 `RUNNING`（来自函数入口快照），在当前 S2 范围内恰好等价于最新状态，但语义上与 `_append_job_event_warn` 传 `record.status` 的模式一致
- **直接证据**: `dayu/fins/ingestion_runtime.py:2180` 调用 `_emit_progress_event(record, ...)` 而非 `_emit_progress_event(latest, ...)`；`_append_job_event_warn` 在 `_mark_job_running_or_cancelled` 中也使用同样的 `record` 快照模式
- **影响**: 当前无实际行为差异（job 运行中 status 始终为 RUNNING）；若未来 progress event 需要在 cancel 路径也写入，使用快照会导致 status 字段不准确
- **建议改法和验证点**: 当前可接受，与 `_append_job_event_warn` 模式一致；若后续需要在 cancel 路径写 progress，应改传 `latest`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
