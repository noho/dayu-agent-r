### D-F3 验证 — 两个真实 commit 的 fresh 时间/version/opaque revision

- **两个真实 commit**：`_CommitSnapshotTrackingBatchingRepository.commit_batch`（test:497-508）先 `super().commit_batch(batch)` 执行真实 durable commit，再经公开 `list_source_document_ids` + `read_source_snapshot(materialize_files=False)` 读取同版 snapshot；每 stream 的 begin→commit 恰好一次（workflow 非 delete 路径唯一 begin 在 publication owner，sec_upload_workflow.py:261-269），两个 commit 均为生产路径产生。
- **确定性边界，无时间窗口**：`begin_batch`（test:452-490）以 `Lock` 分配 begin 序号，第二个 begin 以 `Event.wait(timeout=10)` 等待第一个 commit 的 snapshot 已记录（`_first_snapshot_recorded` 在第一个 `commit_batch` 记录后 set）。Event 是确定性同步原语而非 sleep/时间窗口；10 秒仅为失败上界（TimeoutError → stream typed failure → 断言响亮失败）。该边界同时使 rebase 路径确定性成立：第二个 writer 的 fresh read 必然观察到第一个 commit 的 published 状态（此前两 begin 可能先于任一 commit，rebase 路径有竞态窗口），且无循环等待（第一个 writer 从不等待该 Event）。overwrite=False 分支不注入该 subtype（test:2666），既有 conflict 断言不受影响。
- **fresh 时间/version/opaque revision**：test:2703-2712 断言两 commit 同一 document ID、`first_ingested_at`/`created_at` 保持（"fresh 时间"由 winner fresh meta 保持）、`source_fingerprint` 保持、`document_version` 相等且为 `"v1"`——"v1" 是生产 `_resolve_document_version` 对 previous_meta=None 的 fresh 默认值（docling_upload_service.py:1754-1755）与 `SourceDocumentMeta.document_version` 域默认（document_models.py:870），测试固定该契约期望值而非重算版本规则；`second_commit.revision != first_commit.revision` 对照 `SourceDocumentRevision.token`（storage publication owner 生成的 opaque equality token，document_models.py:293-305），证明 rebase 由 storage owner 写入新 revision。
