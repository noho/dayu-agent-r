### A2 — direct upload claim 后事件构造异常导致 RESULT 丢失窗口（accepted, fixed in current slice）

裁决要求：在 `dayu/fins/ingestion_runtime.py` 的 direct upload owner 内先用 pure typed helper 构造可见 progress/result（不入队），构造成功后再执行单次 `claim_upload_summary`，claim 成功后只按顺序调用不会抛异常的 `_put_direct_queue`。构造失败发生在 claim 前，外层既有异常路径可正常 claim 并投影唯一 FAILURE。

**修复实现走读**:

1. **旧顺序（已删除）**: `_produce_direct_upload` 先调用 `_emit_context_progress`（completed progress）→ 检查 cancel → 调用 `_emit_direct_result`（RESULT）。`_emit_direct_result` 内部先 `claim_terminal`，再构造 `FinsEvent` 并 `_put_direct_queue`。claim 在构造之前，构造失败导致外层 catch 再次 `_emit_direct_result(FAILURE)`，但 `claim_terminal` 返回 None（已有 terminal），stream 以 done 结束且没有 RESULT。

2. **新顺序**: `_produce_direct_upload` 先调用 `_direct_upload_terminal_events`（纯构造，不入队），再调用 `claim_upload_summary`，claim 成功后只调用 `_put_direct_queue`。

3. **关键路径走读**（第 3449-3464 行）:
   ```python
   disposition = summary.terminal_disposition()
   terminal_progress, terminal_result = _direct_upload_terminal_events(  # 纯构造
       context=context, request=request, summary=summary,
       disposition=disposition, emitted_at=datetime.now(timezone.utc),
   )
   cancellation_state = context.cancellation_state
   if cancellation_state is None:
       raise RuntimeError("direct upload 缺少 terminal claim owner")
   if cancellation_state.claim_upload_summary(disposition) is None:  # 单次 claim
       return
   if terminal_progress is not None:
       _put_direct_queue(context, terminal_progress)  # 不抛异常入队
   _put_direct_queue(context, terminal_result)        # 不抛异常入队
   ```

4. **构造失败路径**: `_direct_upload_terminal_events` 内部调用 `_direct_progress_event` 和 `_direct_result_event`，两者都做 typed contract 校验（`FinsEvent` 构造、`FinsResultSummary` 构造、bounded text 校验）。若校验失败，异常在 `claim_upload_summary` 之前抛出，传播到 `_run_direct_stream_producer`（第 3227-3264 行）的 `except Exception` → `_emit_direct_result(FAILURE)`。此时 `_terminal_status` 仍为 None，`claim_terminal` 成功，唯一 FAILURE RESULT 被投递。

5. **`_put_direct_queue` 安全性**: 该函数（第 3463-3464 行调用）只做 `context.direct_queue.put_nowait(event)`。direct queue 在 `_prepare_observed_stream` 中创建为 `Queue(maxsize=_DIRECT_EVENT_QUEUE_MAX_SIZE)`。入队操作在 claim 成功后执行，不涉及 contract 校验。

**测试验证**: `test_direct_upload_projection_failure_before_claim_emits_single_failure_result`（第 2759 行）

- 使用 121 字符 `document_id`（超过 `_direct_document_label` 的 120 字符上限），summary-valid 但 event-invalid。
- `_FakeUploadRunner` 返回该 summary → `_direct_upload_terminal_events` 调用 `_direct_progress_event` → `FinsEvent` 构造触发 `_bounded_text` ValueError → 异常在 claim 前传播。
- 断言: `progress_stages == ("upload.preparing", "upload.started")`（只有 runner 前的两个 progress）、`len(results) == 1`、`results[0].status is FinsResultStatus.FAILURE`、`all(result.status is not FinsResultStatus.SUCCESS for result in results)`。

**结论**: A2 修复正确实现了"先纯构造、再单次 claim、claim 后只入队"的顺序。构造失败在 claim 前收口为唯一 FAILURE。**裁决 A2 已修复。**
