# 当前代码改动 Review

## Findings

1. 高 — 终态事件后仍会继续消费并 append 后续事件，破坏 Run 终态一致性

位置：

- `dayu/host/_run_harness.py:176`
- `dayu/host/_run_harness.py:193`
- `dayu/host/_event_store.py:126`
- `dayu/host/_event_store.py:243`

问题原因：

`LocalRunHarness._run_to_store()` 在 `terminal_result_from_event(stored_event) is not None` 后只把 `terminal_seen` 置为 `True`，但没有停止消费 `engine_events`。同时 `InMemoryRunEventStore.append()` 只记录第一个 terminal cursor，不拒绝 terminal 之后继续 append 的事件。

这会造成同一 run 的事实层出现“terminal 后还有事件”的状态。`subscribe()` 在一次批量 replay 中遇到 terminal 会立刻 `return`，但 `list_events()` 仍能补读 terminal 之后的事件；如果调用方以 terminal cursor 作为 `after` 重连，`stream_run_events(after=terminal.cursor)` 又会先返回 terminal 之后的事件，因为 `_subscribe()` 先检查 `_events_after_locked()`，只有没有事件时才检查 `_terminal_reached_locked()`。如果后续事件里还有第二个 terminal，`get_run_result()` 反向扫描还可能返回后一个 terminal，与正常 stream 观察到的第一个 terminal 不同源。

可能后果：

- `RUNNING -> terminal` 的最小状态机不再封闭。
- 正常流式消费、断线补读和 `get_run_result()` 可能对同一 run 得到不同终态或不同事件集合。
- P1.5 要求的 terminal event 与 RunResult 同源会被打破，后续 P2-P6 依赖 EventLog 时会继承这个边界漏洞。

建议修复：

在 harness 层看到第一个 canonical terminal RunEvent 后立即停止消费 worker stream，或在 `RunEventStore.append()` 边界拒绝同一 run terminal 之后的普通 RunEvent；如果未来确实需要 terminal 后审计事实，应使用明确不同的事件类别和订阅语义，不能混在当前 `RunStream.events` 的 RunEvent 流里。测试需要补上 terminal 后跟随非终态事件、terminal 后跟随第二个 terminal、`list_events` / `stream_run_events(after=terminal)` / `get_run_result` 三者一致性的覆盖。

修复状态：

已修复。`InMemoryRunEventStore.append()` 现在拒绝同一 run terminal 后的任何新 `RunEventDraft`，包括非终态事件和第二个 terminal；`LocalRunHarness._run_to_store()` 在首个 terminal 入 store 后停止继续 append，并显式关闭支持 `aclose()` 的 worker stream。新增测试覆盖 terminal 后非终态事件、terminal 后第二个 terminal，以及 `list_events` / `stream_run_events(after=terminal)` / `get_run_result` 的同源一致性。

2. 中 — public `start_run` 路径无法观察后台任务中的 Host 内部错误，现有回归测试绕过了真实行为

位置：

- `dayu/host/_run_harness.py:122`
- `dayu/host/_run_harness.py:190`
- `tests/host/test_phase1_5_run_harness_eventlog.py:494`

问题原因：

`start_run()` 用 `asyncio.create_task(self._run_to_store(...))` 启动后台任务，但不保存 task handle，也没有 done callback 或事件流错误通道。`_run_to_store()` 目前只把 worker / proxy 取事件异常转为 Host-owned failure；`translate_engine_event()`、`event_store.append()`、`terminal_result_from_event()` 的异常会从后台 task 直接冒出。

这符合“不把 Host / 契约错误伪装成 Host-owned worker failure”的方向，但 public `RunStream.events` 没有办法观察这些异常。若异常发生在 terminal append 之前，例如未来持久 store append 失败或注入 store 失败，订阅者会一直等待新事件；若异常发生在 terminal result 推导阶段，事件流最多只能看到已 append 的事件，后台 task 异常会变成未被取回的 task exception。当前 `test_terminal_result_error_does_not_append_host_failure` 直接调用私有 `_run_to_store()`，因此能 `pytest.raises(TypeError)`，但这没有覆盖真实 `start_run()` 创建 detached task 后的 public 语义。

可能后果：

- Host 内部错误在 public API 上表现为挂起、静默丢失或 “Task exception was never retrieved”，稳定性和可诊断性不足。
- 后续把 `RunEventStore` 换成持久实现时，append/list/订阅异常会更现实；当前测试不会阻止 public 事件流永久等待。
- review 文档中“契约错误不追加 Host-owned failure，且 `get_run_result` 暴露同一 terminal 契约错误”的结论只覆盖私有直调路径，没有锁住 `start_run` 的实际用户路径。

建议修复：

为后台任务建立明确的错误观测策略：至少保证非 worker/proxy 的 Host 内部错误不会让 `RunStream.events` 永久等待；可以选择在订阅流中传播内部错误、在 RunStream/handle 中保留 task 供 supervisor 观测，或在 append 前做足数据校验使这类错误变为同步可诊断失败。对应测试应通过 `harness.start_run()` 构造 failing store 或 terminal data mismatch，用超时断言事件流不会无界等待，并验证不会追加 Host-owned failure。

修复状态：

已按 P1.5 范围修复诊断观测。`start_run()` 创建的后台 task 已注册 done callback，取回异常并记录 ERROR 日志；新增 public `start_run()` 路径测试验证 terminal data mismatch 不追加 Host-owned failure，且后台异常可通过 ERROR 日志观测。完整 supervisor、事件流传播 Host 内部错误、append 前失败时的 run 治理收口属于 P7 supervisor / governance 范围，本轮不实现，也不把这类 Host 内部错误伪装成 Host-owned worker failure。
