## Assumptions Tested

1. **Watchdog owner is Host lifecycle supervisor direction** — verified against existing `WaitPollerSupervisor` (thread-based) and `HostDispatchScheduler` (async task-based) patterns in `dayu/host/dispatch.py` and `dayu/host/wait_adapter.py`.
2. **`cancel_cancelling_run_row` CAS is safe for concurrent timeout closeout** — verified: SQL UPDATE uses `WHERE status = CANCELLING AND current_attempt_id = ? AND terminal_refs_unset`; concurrent cooperative closeout will cause CAS miss, transaction rolls back.
3. **`RUN_CANCELLING` payload carries `cancel_request_event_id`** — verified in `dayu/host/engine_ingest.py::_close_active_cancel` and `_cancel_request_event_id_from_cancelling`.
4. **Terminal closeout appends events then CAS-updates rows in one transaction** — verified in `active_cancel_closeout_in_transaction` (run_transition.py:2129-2208); if CAS fails, entire transaction rolls back.
5. **`ActiveWorkerRegistry` unregister happens in `_consume_worker_events` finally block** — verified (dispatch.py:3671-3690); after timeout terminal closeout, worker coroutine may still be blocked on `anext(events)`.
6. **`cancel_session_runs` replay checks run status before active propagation** — verified (command.py:657-698); if run is terminal (CANCELLED), replay returns terminal snapshot without active propagation.
7. **Scheduler close does not write terminal facts** — verified (dispatch.py:2318-2364); `_PublicHostHandle.close()` docstring explicitly states "不写 cancel / failed terminal facts".
8. **`StartupRecoveryScanner` handles non-terminal runs at reopen** — verified (open_host.py:891-896, recovery.py); classifies orphans via heartbeat staleness + PID liveness. CANCELLING runs are non-terminal and will be processed by recovery scanner.

## Findings

### 01-未修复-中-Reopen 路径 recovery scanner 与 watchdog 交互未指定

- **位置**: Implementation Decisions > Scheduler close boundary; Implementation Slices > Slice 2 > Exact changes > "Ensure startup/reopen path scans already CANCELLING runs"
- **问题类型**: 状态机漏洞 / 不可直接实施
- **当前写法**: Plan 说 "reopening Host with watchdog enabled should be able to scan existing CANCELLING runs and apply timeout based on durable RUN_CANCELLING / CANCEL_REQUESTED timestamps"。Slice 2 要求 "Ensure startup/reopen path scans already CANCELLING runs"。
- **反例/失败场景**: `StartupRecoveryScanner.scan()` 在 `open_host.__aenter__` 中执行（line 891-896）。它读取所有 non-terminal runs 并基于 owner heartbeat staleness + PID liveness 分类 orphan。对于 CANCELLING runs:
  - 如果前一个 Host 实例已经 stopped（heartbeat stale + PID dead），recovery scanner 可能尝试为 CANCELLING run 创建 recovery dispatch（`PositiveOrphanProof`）。此时 run 进入 RECOVERING 状态，watchdog 扫描时不会再看到 CANCELLING run。
  - 如果 recovery scanner 把 CANCELLING run 标记为 `OwnerStillLive`（前一个 Host 实例仍在运行），recovery scanner 会跳过该 run。但前一个 Host 实例已经 stopped 了（因为 reopen 意味着新实例），所以这种情况不应该发生。
  - 如果 recovery scanner 把 CANCELLING run 标记为 `OrphanProofInconclusive`，run 状态不变，watchdog 可以扫描到。
- **为什么有问题**: Plan 没有指定 watchdog tick 与 recovery scanner 的执行顺序。如果 recovery scanner 先运行并为 CANCELLING run 创建了 recovery dispatch，watchdog 看到的就不再是 CANCELLING 状态。实现 Agent 不知道应该修改 recovery scanner（跳过 CANCELLING runs 让 watchdog 处理），还是在 watchdog startup scan 中处理 recovery scanner 已经处理过的 runs。
- **直接证据**:
  - `dayu/host/open_host.py` line 891-896: `StartupRecoveryScanner(...).scan()` 在 scheduler open 之后、Host handle 创建之前执行。
  - `dayu/host/recovery.py`: recovery scanner 读取所有 non-terminal runs 并分类 orphans。
  - Plan "Implementation Slices > Slice 2 > Exact changes" 没有提到修改 recovery scanner。
- **影响**: 实现 Agent 可能跳过 reopen 路径的 watchdog 集成，或者错误地假设 recovery scanner 不会处理 CANCELLING runs。
- **建议改法和验证点**:
  - 在 Slice 2 中明确：watchdog startup scan 在 recovery scanner 之后执行；recovery scanner 对 CANCELLING runs 的处理方式（跳过、或者 watchdog 在 recovery scanner 之后覆盖 recovery 结果）。
  - 或者：明确 recovery scanner 不修改 CANCELLING runs 的状态（已有证据表明 `startup_orphan_recoverable_rejects_cancelling_expected_status` 测试存在），让 watchdog 独立处理。
  - 验证点：`test_active_cancel_watchdog_reopen_closes_existing_cancelling_run` 测试必须覆盖 recovery scanner 已经运行过但 CANCELLING run 未被修改的场景。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-低-Watchdog tick clock source 未作为正向实施要求

- **位置**: Implementation Slices > Slice 2 > Stop condition
- **问题类型**: 不可直接实施
- **当前写法**: Stop condition 说 "Stop if deterministic tests require sleeping real timeout longer than focused test budget; add injectable clock/tick instead of making tests flaky"。
- **反例/失败场景**: 实现 Agent 使用 `asyncio.get_event_loop().time()` 或 `datetime.now(UTC)` 作为 clock source。测试必须 sleep real timeout 或使用极短 timeout（可能导致 race condition）。Stop condition 被触发，但 plan 没有说明如何处理（是修改 plan 还是放弃 slice）。
- **为什么有问题**: Clock injectability 是实现决定，不是 stop condition。如果实现 Agent 不预先设计 injectable clock，测试要么 flaky 要么触发 stop condition，导致 slice 不完整。
- **直接证据**: Plan "Implementation Slices > Slice 2 > Stop condition" 把 clock injectability 放在 stop condition 而非 "Exact changes"。
- **影响**: 实现 Agent 可能产出不可测试的 watchdog 实现。
- **建议改法和验证点**:
  - 在 Slice 2 "Exact changes" 中添加：watchdog 接受可注入的 clock callable（默认 `datetime.now(UTC)`），测试通过注入 deterministic clock 控制时间推进。
  - 验证点：所有 watchdog timeout 测试使用 injectable clock，无 sleep。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 03-未修复-低-Diagnostic payload field mapping 与现有 helper 的关系不明确

- **位置**: Contract / Schema / State-machine / Public-interface Changes > Terminal payload
- **问题类型**: 契约缺失
- **当前写法**: Plan 列出 timeout closeout payload 字段：`run_id`, `terminal_attempt_id`, `attempt_terminal_event_id`, `dispatch_record_id`, `cancel_request_event_id`, `reason`, `timeout_seconds`, `cancel_requested_at`, `timed_out_at`, `watchdog_owner`, `worker_lifecycle_signal`, `last_observed_worker_event_index`, `last_accepted_event_id`。
- **反例/失败场景**: 现有 `ActiveCancelCloseoutInput` 字段为 `run_id`, `attempt_id`, `attempt_cancelled_event_id`, `run_cancelled_event_id`, `actor`, `source`, `reason`, `cancel_request_event_id`, `engine_event_ref`, `requested_at`, `accepted_at`, `finished_at`。Plan 说 "Add a typed internal input dataclass, e.g. ActiveCancelTimeoutCloseoutInput"，但没有说明新 dataclass 与现有 `ActiveCancelCloseoutInput` 的关系。实现 Agent 可能创建完全独立的 dataclass 和 transaction helper，或者复用现有 helper 并添加字段。
- **为什么有问题**: 两种路径有不同的实现风险。独立 dataclass 意味着更多代码和维护成本；复用意味着修改现有 helper 的签名和 payload 构建逻辑。
- **直接证据**:
  - `dayu/host/durable/run_transition.py`: `ActiveCancelCloseoutInput` 和 `active_cancel_closeout_in_transaction` 是现有的 cooperative cancel closeout 实现。
  - Plan "Implementation Slices > Slice 1 > Exact changes" 说 "Add a typed internal input dataclass, e.g. ActiveCancelTimeoutCloseoutInput"。
- **影响**: 实现 Agent 可能在两种方案之间犹豫，或者选择不符合 plan 意图的方案。
- **建议改法和验证点**:
  - 明确 `ActiveCancelTimeoutCloseoutInput` 是独立 dataclass（不继承 `ActiveCancelCloseoutInput`），因为 timeout closeout 缺少 `engine_event_ref`/`accepted_at`/`finished_at` 且有额外 timeout-specific fields。
  - 明确 `active_cancel_timeout_closeout_in_transaction` 是独立 transaction helper，复用 `cancel_running_attempt_row` 和 `cancel_cancelling_run_row` 但构建自己的 EventLog event requests。
  - 验证点：Slice 1 测试覆盖 timeout closeout payload 包含所有必填字段。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-低-Slice 2 watchdog 需要扫描 CANCELLING runs 的查询效率

- **位置**: Implementation Slices > Slice 2 > Exact changes > "scan durable CANCELLING runs with current RUNNING Attempt and accepted dispatch record"
- **问题类型**: 最佳实践偏离
- **当前写法**: Plan 说 watchdog tick 要 "scan durable CANCELLING runs with current RUNNING Attempt and accepted dispatch record"。
- **反例/失败场景**: 如果每次 tick 都执行一次 SQL 查询扫描所有 CANCELLING runs，在 Host 有大量历史 runs 时可能有性能问题。但如果使用 in-memory set 追踪 CANCELLING runs，则需要在 cancel commit 后添加/移除，增加复杂度。
- **为什么有问题**: 这是实现细节，但 plan 应该给出方向，避免实现 Agent 过度设计查询或追踪机制。
- **直接证据**: 现有 `WaitPollerSupervisor` 使用 SQL 查询扫描 active wait records（`wait_adapter.py` poll loop）。
- **影响**: 低。实现 Agent 可以合理选择 SQL 查询或 in-memory set。
- **建议改法和验证点**:
  - 可选：plan 注明 "使用 SQL 查询扫描，不引入 in-memory tracking set"，与现有 poller 模式一致。
  - 验证点：watchdog tick 在 Host 有 0 个和多个 CANCELLING runs 时都能正确工作。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
