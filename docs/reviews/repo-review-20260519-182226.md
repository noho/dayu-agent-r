### 1-未修复-高-Host LLM Compaction `_budget_after_compact` 预算估算严重低估

- **入口/函数**: `_budget_after_compact`
- **文件(行号)**: `dayu/host/llm_compaction.py:290-299`
- **输入场景**: LLM compactor 返回摘要后，Host 校验 compact 后上下文 token 预算。
- **实际分支**: `min(summary_tokens, estimate.hard_threshold_tokens - 1)` 其中 `summary_tokens = max(1, (len(summary) + 3) // 4)`，仅计算摘要文本自身的 token 估算，**不包含** preserved recent_raw_turn_refs、preserved tool_fact_refs、current_user_input、system_message 等保留内容。
- **预期行为**: `budget_after_compact` 应为摘要 + preserved 内容 + 当前输入 + system message 等全部保留上下文的 token 总和估算。
- **实际行为**: 对 200 字符摘要返回约 50 tokens，远低于实际 compact 后上下文（可能仍有数千 tokens 的保留内容）。quality check 的 hard threshold gate 几乎永远通过，即使 compaction 后实际上下文远超 hard threshold。
- **直接证据**: `_budget_after_compact` 第 299 行 `return min(summary_tokens, estimate.hard_threshold_tokens - 1)`，从未引用 `request` 中 preserved 内容的大小信息。fake_compaction.py 的 `_budget_after_compact`（仅用 `half_estimate`）也有同类低估。
- **影响**: adversarial 场景下（超大 preserved recent raw turns 或 tool facts 仍在上下文中），compact quality check 假性通过，导致实际超预算的上下文进入下一轮 Engine run，可能引发 provider context overflow。
- **建议改法和验证点**: `_budget_after_compact` 应接收 request 中 preserved 部分的大小信息，至少用比例估算（如 `estimate.estimated_input_tokens * (preserved_refs_count / total_input_refs_count)`）。验证：构造 older_raw_turn_refs 占 90%、recent_raw_turn_refs 占 10% 的场景，assert `budget_after_compact` 明显大于摘要 tokens。
- **修复风险**: 低。只修改 `_budget_after_compact` 和 `_estimate_summary_tokens` 的计算逻辑。
- **严重程度**: 高

### 4-未修复-中-`_budget_after_compact` 与 `_estimate_text_tokens` 的 char-per-token 常数不一致

- **入口/函数**: `_estimate_text_tokens`（context_budget.py）vs `_estimate_summary_tokens`（llm_compaction.py）
- **文件(行号)**: `dayu/host/context_budget.py:285` vs `dayu/host/llm_compaction.py:299`
- **输入场景**: 同一上下文分别被 context_budget 和 compactor 估算 token 数。

- **直接证据**: `context_budget.py:285` 和 `llm_compaction.py:299` 使用不同常数。
- **影响**: 叠加 Finding 1 的低估问题，偏差进一步放大。
- **建议改法和验证点**: 统一使用 `context_budget.py` 导出的 `DEFAULT_ESTIMATOR_CHARS_PER_TOKEN`，并统一用 `ceil` 确保保守估算。
- **修复风险**: 低。
- **严重程度**: 中

### 5-未修复-中-`_close_runner_once` 异常路径 `_closed` 未置位导致 Runner close 非幂等

- **文件(行号)**: `dayu/engine/agent.py:2380-2405`
- **输入场景**: `self._runner.close()` 抛出非 `CancelledError` 的普通异常（如 `ConnectionResetError`）。
- **实际分支**: 异常被 `except Exception` 捕获后记录 warning（行 2398-2403），`_closed` 保持 `False`（`else` 分支未执行）。

- **实际行为**: 下次调用仍会尝试 `self._runner.close()`，可能对已半关的底层连接再次操作。
- **直接证据**: 行 2398-2403 的 `except Exception` 后没有 `self._closed = True` 写入；2404 行 `else` 只在成功时才设置。

- **建议改法和验证点**: 在 `except Exception` 分支中加 `self._closed = True`。
- **修复风险**: 低。
- **严重程度**: 中
