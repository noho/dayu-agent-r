## 2. Findings

### 1-未修复-[中]-竞态窗口 B 的原子收拢应断言而非条件化，测试注入点未钉死单一 commit 边界，两段 commit 实现可过测而半发布公司事实

- **位置**: 「可直接实施的契约和数据流」§3（“若现有公司 batch 与材料 commit 的分段边界无法保证冲突前零业务发布，实施必须把 precondition 与相关业务 stage 收拢到同一原子提交边界……此所有权在 storage/publication 层审查后才可过 gate”）、S1 完成信号、测试第 3 条窗口 B、风险 R4。
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口。
- **当前写法**: 把「收拢到同一原子提交边界」写成条件触发项，条件宾语（现有分段边界）在 plan 自己的证据表里已被证实；测试 3 窗口 B 的注入点写为“pre-yield 已通过后、company/material batch stage/commit 前”。
- **反例/失败场景**: 现状是**两段 commit**：`sec_upload_workflow.py:523-536` company batch 先 `commit_batch`（公司事实已发布）→ :537 `prepare_upload`（慢，docling 转换）→ :562-568 另起 batch `commit_prepared_upload_batch`（`cn_pipeline.py:1139-1152`/`1178-1181` 同构）。若实施保留两段并给两个 batch 各自注册 precondition：测试 3 的注入发生在两段之前时全部断言可通过（首段 precondition 拒绝→零发布）；但可达序列 [pre-yield 通过 → company batch commit 成功（公司业务事实已发布）→ 并发改写公司 meta → material batch precondition 拒绝 → typed `source_publication_conflict`、`stored_file_count=0`] 中**公司业务事实已发布**，直接违反成功信号 3「不发布公司/材料业务事实」，而 plan 现有测试措辞抓不到 commit 间注入点。
- **为什么有问题**: goal 成功信号 3 与裁决测试句对「任何接收后漂移」承诺零公司/材料业务发布；验证套件若不能区分收拢（单 commit）与未收拢（两段 commit）两种实现，plan 的完成信号就无法被证伪，implementation agent 还可能把 R4「若不行返回 plan gate」读成可以带两段边界进实施。
- **直接证据**: 上述工作流行号；`_fs_storage_infra.py:533-611`（pre-commit 失败 `_rollback_precommit_batch` 零发布、单 publication guard swap）；filing 单 batch 先例证明收拢有既定形状：`sec_upload_workflow.py:240-260`（delete 路径 `begin_batch` → `stage_upload_company_meta_decision` → `commit_prepared_upload_batch` 同一 batch）与 `filing_upload_publication.py:810-860`（stage decision 与 prepared commit 同 batch）。
- **影响**: 违反 goal 的半发布实现可通过现有测试措辞；实施期被迫现场重设计发布时序（company staging 移入 material 提交 batch、prepare 前移出 batch）或触发 R4 退回，S1 的「逐层验收」在 workflow 层失去判据。
- **建议改法和验证点**:
  1. 把条件句改为**断言式设计要求**：material 发布必须镜像 filing delete/publication 的单 batch 形状——`prepare_upload` 完成后**一个** `begin_batch` → 注册 observed-state precondition + `stage_upload_company_meta_decision(decision=admission.company_meta_decision)` → `commit_prepared_upload_batch` 同一 batch；明确写出现状两段 commit 的行号为必须消除项。
  2. 测试 3 窗口 B 的注入点改为「唯一 commit 边界之前」，并明确覆盖迁移前的旧时序点（原 company commit 与 material commit 之间）至少一条回归；或直接断言「提交路径只存在一个 `commit_batch` 调用承载公司+材料业务 stage」。
  3. R4 的「若不行返回 plan gate」保留为安全阀，但补一句「收拢为设计要求，不得降级为按 batch 各自 precondition」。
  4. 验证点：注入 [company 已 commit、material 未 commit] 时刻的漂移（迁移期回归）与 [唯一 commit 前] 漂移，均断言 typed conflict + 公司/材料均无业务发布。
- **修复风险（低/中/高）**: 低——收拢形状完全复用 filing 既有单 batch 模式，无新机制。
- **严重程度（低/中/高/严重）**: 中（可达反例违反 goal 终态承诺且现有测试措辞不闭合；但 plan 已含收拢 mandate，读懂全文的实施者可正确执行，未达首轮 F1 的「裁决拒收形态必现」级别）。
- **残余风险**: `commit_batch` 的 post-commit 段（publication guard 释放失败、cleanup 失败，`_fs_storage_infra.py:585-611`）本就不回滚 durable tree——「零业务发布」承诺仅覆盖 pre-commit 失败路径，属既有 storage 语义，登记 storage owner 知悉即可。

### 2-未修复-[中]-batch precondition 的比较语义、注册/执行 owner 边界、提交次序与 previous_meta 出处未钉死，同一描述可实现出三种用户可见行为

- **位置**: §1 实现选择（“该协议另提供 batch-scoped observed-state 前置条件，由 storage 在提交同一 publication guard 内重读并比较公司与 exact material target；……比较失败返回明确 typed publication conflict”）、§2（validator 用 snapshot 解析动作后 workflow 消费 admission）、§3（“company intent 的 observed_meta 乐观合并与 alias identity/uniqueness guard 仍由 storage 最终裁决”）、测试 1/3。
- **问题类型**: 契约缺失 / 语义所有权。
- **当前写法**: 「重读并比较」未定义等价形式与比较函数 owner；注册 API 挂在只读 `MaterialUploadStateRepositoryProtocol`（“该协议另提供”write 侧能力），执行在 commit guard，两者跨 facade/core/infra 三处；alias guard 与 precondition 同时命中时的归属未声明；`prepare_upload` 的 `previous_meta` 出处未指明。
- **反例/失败场景**:
  1. 实施 A 做严格全等（`CompanyMeta.updated_at/resolver_version` 计入，`document_models.py:426-438`；既有 `_company_meta_non_identity_snapshot`，`company_meta_contract.py:328-348`，也含 `updated_at`）：另一请求仅刷新公司事实的良性并发使本请求 conflict——与 §3「乐观合并仍由 storage 最终裁决」的吸收语义（`company_meta_contract.py:245-250`）相互矛盾，成功信号 2 的「合法变化」边界随实现漂移。
  2. 实施 B 做 presence-only/宽松比较：并发改名后 `keep` 请求静默发布，违反裁决「状态变化归发布冲突」与测试 3 的注入断言。

  5. drift 与 alias 冲突同时成立时：现次序（`_commit_batch_with_identity_guards` 先 merge/alias 后 publication guard，`_fs_storage_infra.py:642-643`）报 `ticker_alias_conflict`，plan 未声明该归属，测试 3 只覆盖纯 alias 场景。
- **为什么有问题**: 项目约束要求业务事实/派生判定的语义 owner 唯一且在 owner boundary 定义；「什么算状态漂移」直接决定 conflict 频率、成功信号 2 的省略名放行边界和测试断言的可写性，留给实施 Agent 就是首轮 F1 被裁决拒收的「owner 不清」形态重演（轻量版）。
- **直接证据**: 见反例各行号；另：`_fs_storage_infra.py:65-67/1124` 证明 guard 内重读 material source 已有可用 helper（无 callback seam 必要），比较函数可落为新 material state 契约/core 的纯函数或 infra 内联——两条路都可行但行为不同，需选定。

- **建议改法和验证点**:

## 3. 专项裁决：batch precondition 是否过度设计 / owner 是否不清

- **过度设计：否**。必要性反证见 A4（keep/skip 静默发布反例、material target lost-update 反例、merge 吸收语义与裁决冲突）；最小替代（只靠 `observed_meta` 乐观合并 + prepare 时 target 校验）覆盖不了 keep/skip 与 guard-原子性要求，且需要给 merge 加 strict 模式的契约变更，复杂度不低于单一 precondition。
- **owner：基本清晰，钉死项见 F2**。判定语义归 storage/publication 层（plan 已声明且加 gate 复核），失败投影归 Fins failure owner（plan 已声明）；剩余歧义是比较形式/次序/出处三处一句话可收敛的钉死项，不是所有权真空。
- **原子实现能力：具备**。单 publication guard、swap 前检查、pre-commit rollback 零发布、infra 已有 guard 内读 helper（A5）；前提是 F1 的单 commit 收拢成立。
- **最小替代（如最终裁决要收缩机制）**：仅对 keep/skip 注册纯 precondition intent（无写入、只带 expected snapshot）走既有 commit 通道 + material target 以 prepared `previous_meta` 在 commit guard 内重检——但该替代仍需同一 commit 边界与严格比较语义，收益有限，不推荐。
