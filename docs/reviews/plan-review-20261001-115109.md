## 5. Findings

### 01-未修复-中-共享 `_build_sec_download_result` 丢掉正常路径的 `status="cancelled"` 投影

- **位置**：plan D2（`docs/gateflow/pr-197-r1-f6-plan-20261001.md:89-93` 签名、`:99` “沿原 builder 默认 status='ok'”）；受影响代码 `dayu/fins/pipelines/sec_download_workflow.py:743-762`（`:761` 显式传 `status="cancelled" if cancelled else "ok"`）；受影响测试 `tests/fins/test_sec_pipeline_download_stream.py:984、:1012`；与 plan `:107`（“single-filing 原取消 return/协作式检查…仍按原逻辑”）及 `:134`（“取消…原测试保持”）冲突。
- **问题类型**：契约缺失 / 不可直接实施（计划内部不一致）。
- **当前写法**：`_build_sec_download_result(..., warnings, filing_results, elapsed_ms) -> dict[str, JsonValue]`，由“正常完成与 typed 中止共同调用”，且“沿原 builder 默认 status='ok'”，参数中无 status/cancelled。
- **反例/失败场景**：SEC 下载在 collection 完成后收到取消（`cancel_checker` 第二次返回 True，或首检查即 True）→ `:627-633`/`:671-676` 置 `cancelled=True` 并 break → 落到 `:707+` 统一尾部。若照签名实现，`host._build_result(...)` 缺省 `status='ok'`（`sec_pipeline.py:1721` 默认值），PIPELINE_COMPLETED 的 result.status 由 `"cancelled"` 变 `"ok"`；`use_cancel` 的两条既有测试（`:984`、`:1012`）失败。计划同时承诺这些测试保持，且 cancel 是非目标（plan `:16`）。
- **为什么有问题**：同一行为 slice 内“共同调用”与“保持取消语义/测试”不能同时按字面成立；实现 agent 要么破坏承诺的既有断言，要么被迫自行发明未批准的签名（超计划）。
- **直接证据**：plan `:89-93`（无 status 参数）、`:99`（默认 ok）；代码 `:761`；测试 `:984`/`:1012`（断言 `final_result["status"] == "cancelled"`，均为经过统一尾部的 mid-loop/首检查取消路径）。
- **影响**：取消终态在 OLD SEC 结果面上失真；实现期出现“计划外设计决策”或错误地改写既有 cancel 测试（弱化 owner 级 contract）。
- **建议改法和验证点**：给 `_build_sec_download_result` 增加显式 `status: str`（或 `cancelled: bool`）参数：正常完成传 `"cancelled" if cancelled else "ok"`，typed abort 传 `"ok"`（不新造状态值，符合 D2 原则）；在两处调用点各留一条断言（正常 cancel 仍 `cancelled`、abort 快照不 yield）。验证点：`test_sec_pipeline_download_stream.py` 两条既有 cancel 测试保持原断言不变。
- **修复风险**：低。
- **严重程度**：中。

### 02-未修复-中-SEC mid-filing typed catch 把既有 `SELECTED_REJECTED`/`UNSAFE` 单 filing 抛点转为 abort，计划未陈述该行为变化且未迁移既有测试

- **位置**：plan D3.2/D3.3（`:107-108`）；受影响 raise 点 `dayu/fins/pipelines/sec_download_filing_workflow.py:238、275、383、505`（单 filing 内、无 terminal）；既有测试 `tests/fins/test_sec_pipeline_download.py:6148-6197`（`:6189` 期望裸 `SourceIntegrityPreflightError`、`:6192` 断言 reason）；plan E（`:117-134`）无 SEC 旧节点迁移项，`:134` 反而宣称“6k_filtered…原测试保持”。
- **问题类型**：状态机漏洞 / 测试缺口 / 契约缺失（未陈述行为变化）。
- **当前写法**：“仅包住当前 `async for event in host._download_single_filing_stream(...)` 的 typed catch，捕获 `(SourceIntegrityPreflightError, SourceIntegrityRevisionConflictError)`”；typed 异常且 `filing_terminal_seen=False` 时“构造当前失败行、append、log、yield FILING_FAILED”，随后抛 abort。
- **反例/失败场景**：`test_sec_selected_repair_that_6k_policy_rejects_fails_before_mutation` 的真实场景——TCOM 唯一 selected repair target 的 payload 被改坏（Phase A=REPAIR_REQUIRED），6-K 政策拒绝保留该 filing（无 XBRL、无 EXHIBIT、判定 NO_MATCH）→ 单 filing 在 `:383` 抛 `SourceIntegrityPreflightError(SELECTED_REJECTED_REPAIR_REQUIRED)`。现行为：该异常裸穿 `pipeline.download`（无行、空摘要）。计划实现后：被新 catch 捕获 → 新增一条当前 filing 的 FILING_FAILED 行并抛 `SecDownloadIntegrityAbort` → `pytest.raises(SourceIntegrityPreflightError)` 失败；同理适用于 `:238`（Phase A UNSAFE）、`:275`（registry 命中 repair 拒绝）、`:505`（Phase B UNSAFE）等 mid-filing preflight 抛点。
- **为什么有问题**：(a) 这是仓库内可枚举的既有行为变化，计划通篇未描述（只描述了 churn、postrepair、mid-filing churn 三类），implementation 只能自行决定“是否造 failed 行/是否包 abort”；(b) E 的迁移清单只列 CN/HK 旧节点，SEC 该节点必然翻红且不在计划内；(c) E `:134` 的“6k_filtered…原测试保持”对该节点不成立（它正是 6-K 政策路径）；(d) 新增的 mid-filing preflight abort 路径（截断行 + 摘要保全）没有任何新测试断言。
- **为什么必须收口**：root F6-P1 裁决要求 SEC 产生层 typed cause + 中止快照 + adapter 保全，mid-filing preflight 的 summary 保全方向正确；但“是否给这一行建 failed 行”与“SELECTED_REJECTED 是否继续保持裸抛（fails-before-mutation 语义）”是计划必须显式选择的语义，不是实现细节。
- **直接证据**：代码 raise 点 `:238、275、383、505`；既有测试 `6148-6197`（种子/file 描述/断言可复现该路径）；plan `:107-108`（无例外的 pair catch 与建行规则）；plan `:132`（CN/HK 迁移列表）、`:134`（保持清单）。
- **影响**：实施 agent 要么静默发明行/计数语义（G3 摘要守恒断言失真风险），要么改动 catch 范围从而偏离计划；既有 `fails_before_mutation` 契约无迁移说明。
- **建议改法和验证点**：在 D3 明确枚举四个 mid-filing preflight 抛点及各自预期（建议统一为“当前 filing 无 terminal → 一条 failed 行 + abort 快照”，与 CN 同构）；在 E 增列迁移节点 `test_sec_selected_repair_that_6k_policy_rejects_fails_before_mutation`（断言 abort、cause 原对象/原 reason、zero mutation、快照 total=1/failed=1），并补一条 mid-filing preflight abort 的新断言（可用该节点直接承担）；或若作者意图保留 `SELECTED_REJECTED` 裸抛，则收窄 catch 范围并在计划中说明其与 `:505` UNSAFE 语义差异。验证点：上述测试在实施后能同时证明“摘要保全”和“零 mutation”。
- **修复风险**：低-中（涉及一条既有测试的语义迁移）。
- **严重程度**：中。
