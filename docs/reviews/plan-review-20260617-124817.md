### F001-未修复-高-HostEvent.event_class / event_type 枚举未定义

- **位置**: 第 5 节 Public contract / API / schema / state-machine decision
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan 描述了 `HostEvent` 需要新增 `event_class: HostEventClass` 和 `event_type: str`，但未定义 `HostEventClass` 的具体枚举值。
- **反例/失败场景**: Implementation agent 在实现 Slice A 时，无法确定 `HostEventClass` 应该包含哪些成员，需要自行设计枚举，可能导致与设计意图不符或与其他 reviewer 裁决不一致。
- **为什么有问题**: `docs/host/design.md` 第 1227-1229 行明确 `HostEvent` 是 "Service-facing typed event"，必须是强类型契约。Plan 未提供足够信息让 implementation agent 直接生成代码。
- **直接证据**: Plan 第 167-168 行只列了 `HostActivityKind` 枚举值，但未列 `HostEventClass` 枚举值。`docs/host/design.md` 第 1227-1229 行要求 "typed event"。
- **影响**: Implementation agent 需要重新设计 `HostEventClass`，可能导致不同 agent 产出不一致，或需要额外 design gate 裁决。
- **建议改法和验证点**: 在 plan 中明确 `HostEventClass` 枚举至少包含的成员，例如 `RUN_LIFECYCLE`、`TOOL_CALL`、`TOOL_RESULT`、`TOOL_BATCH`、`TOOL_AWAITING`、`CONTEXT_COMPACTION`、`PROVIDER_DIAGNOSTIC`、`CONTENT_DELTA`、`REASONING_DELTA` 等。验证点：枚举值必须覆盖第 198-213 行 projection allowlist 所列事件类型。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

- **直接证据**: Plan 第 168 行只写了 `event_type: str`，未说明来源。`docs/host/design.md` 第 1386-1387 行定义了 EventLog 的 `event_type`。
- **影响**: Implementation agent 需要猜测 `event_type` 的语义，可能导致与设计真源不一致。
- **建议改法和验证点**: 明确 `HostEvent.event_type` 必须与 EventLog row 的 `event_type` 一致，是 public identity 的一部分。验证点：`_host_event_from_row(...)` 必须从 row 的 `event_type` 直接复制。

### F005-未修复-中-Slice B Service activity DTO 字段与 HostActivityView 不完全一致

- **位置**: 第 8.2 节 Slice B
- **问题类型**: 过度耦合 / 契约缺失
- **当前写法**: Plan 第 318-320 行列出 Service activity DTO 字段包含 `run_id | None` 和 `event_sequence | None`，但第 172-188 行定义的 `HostActivityView` 不包含这些字段。
- **反例/失败场景**: Service 在投影 Host public activity 时，需要从 `HostEvent` 中提取 `run_id` 和 `event_sequence` 放入 DTO，但这需要 Service 读取 `HostEvent` 的非 activity 字段，增加了耦合。
- **为什么有问题**: Plan 第 28 行要求 "CLI 只消费 Service 投影后的 public activity，不读取 Host durable internals"。如果 Service DTO 包含 `run_id` / `event_sequence`，虽然不是 durable internals，但增加了 Service 对 HostEvent 结构的依赖。
- **直接证据**: Plan 第 318-320 行 DTO 字段包含 `run_id | None` 和 `event_sequence | None`，但第 172-188 行 `HostActivityView` 不包含这些字段。
- **影响**: Service 需要从 `HostEvent` 的多个字段组装 DTO，增加耦合和实现复杂度。
- **建议改法和验证点**: 明确 Service DTO 的 `run_id` 和 `event_sequence` 来自 `HostEvent` 的哪些字段，以及这些字段是否属于 "public activity" 范畴。验证点：Service 不得因为需要 `run_id` 而读取 Host durable internals。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F006-未修复-低-快捷键 Ctrl+X Ctrl+E 外部编辑器实现细节不足

- **位置**: 第 7.4 节 Run-state key handling、第 8.4 节 Slice D
- **问题类型**: 不可直接实施
- **当前写法**: Plan 第 353 行描述 "Ctrl+X Ctrl+E：打开外部编辑器，优先使用 `$VISUAL`，其次 `$EDITOR`，否则使用 prompt_toolkit 默认编辑器行为"，但未说明如何处理编辑器返回空白、编辑器启动失败、或用户在编辑器中取消的场景。
- **反例/失败场景**: Implementation agent 可能对这些边界场景自行设计行为，导致不同实现不一致。
- **为什么有问题**: prompt_toolkit 的外部编辑器行为可能因平台、终端、环境变量而异，需要明确的 fallback 策略。

- **影响**: Implementation agent 需要自行设计边界行为，可能导致不一致或用户体验问题。
- **建议改法和验证点**: 补充边界场景说明：编辑器返回空白时不 submit；编辑器启动失败时 fallback 到普通输入；用户在编辑器中取消时不 submit。验证点：Slice D 测试应覆盖这些场景。

### F007-未修复-中-REASONING_DELTA 和 CONTENT_DELTA 的 activity 投影规则不够具体

- **位置**: 第 5 节 Projection 规则、第 8.1 节 Slice A
- **问题类型**: 契约缺失
- **当前写法**: Plan 第 212-215 行描述 "`REASONING_DELTA` 不展示 raw 内容；可以保留 identity 且 `activity=None`，或只给无内容的 bounded status" 和 "`CONTENT_DELTA` 默认不作为 activity"，但未明确选择哪种方式。
- **反例/失败场景**: Implementation agent 可能选择 "保留 identity 且 `activity=None`" 或 "只给无内容的 bounded status"，导致不同实现不一致。
- **为什么有问题**: 这两种方式在 Service/CLI 的消费行为上有差异：如果 `activity=None`，Service 可以选择不调用 callback；如果提供 bounded status，Service 可以展示通用进度。
- **直接证据**: Plan 第 212-215 行使用了 "或" 的表述，未明确选择。
- **影响**: Implementation agent 需要自行选择，可能导致不一致。
- **建议改法和验证点**: 明确选择一种方式并说明理由。建议选择 `activity=None`，因为 reasoning delta 和 content delta 对用户 activity 展示价值有限，且 bounded status 可能误导用户。验证点：Slice A 测试应覆盖 `REASONING_DELTA` 和 `CONTENT_DELTA` 的 `activity` 字段值。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F008-未修复-中-Slice E 对 prompt_toolkit 与 async run-state key handling 的兼容性风险未充分评估

- **位置**: 第 8.5 节 Slice E Stop condition
- **问题类型**: 并发恢复风险
- **当前写法**: Plan 第 617-618 行 stop condition 提到 "如果 prompt_toolkit 与 async run-state key handling 无法在不重写 REPL 主循环的情况下可靠组合，停止并拆分方案"，但未说明如何判断 "可靠组合" 或预期的验证方式。
- **反例/失败场景**: prompt_toolkit 的 `Application.run()` 是阻塞调用，可能与 async activity callback 冲突。如果 implementation agent 在 Slice E 才发现这个冲突，可能需要大幅返工。
- **为什么有问题**: prompt_toolkit 3.x 支持 async，但其 `Application` 的 key binding 处理可能与外部 async 事件（如 activity callback）存在竞争。Plan 未评估这个风险。
- **直接证据**: Plan 第 617-618 行承认风险但未提供验证方式。`dayu/cli/commands/interactive.py` 当前使用同步 `input()`，未涉及 prompt_toolkit。
- **影响**: Slice E 可能无法按预期实现，需要大幅返工或降级方案。
- **建议改法和验证点**: 在 Slice D 中增加一个 early validation step：用最小 prompt_toolkit Application 验证 async key binding 与外部 async event 的兼容性。验证点：prompt_toolkit Application 可以在 async context 中接收外部事件并触发 key binding。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
