## Findings

### 001-未修复-高-S2-async-sync-boundary-gap

- **位置**: Slice S2 "Wire Pipeline Progress into Fins Ingestion Runtime"，exact changes 部分
- **问题类型**: 不可直接实施
- **当前写法**: Plan 要求 "SecDownloadAdapter / CnDownloadAdapter 改为消费 download_stream(...)，每个 DownloadEvent 先 event_sink.emit_progress(...)，同时聚合最终 summary"。
- **反例/失败场景**: 当前 `FinsSourceDownloadAdapter.download()` 是同步协议（`ingestion_runtime.py:291`），`_execute_download_request` 是同步方法（`ingestion_runtime.py:1881`），运行在 daemon thread 中。但 `download_stream()` 是 `async` 方法（`sec_pipeline.py:502`、`cn_pipeline.py:562`）。同步方法无法直接 `await` 或 `async for` 消费 async stream。Implementation agent 将面临三种选择：(a) 在 adapter.download() 内部用 `asyncio.run()` 桥接——在已有 event loop 的进程中会崩溃；(b) 把 `_execute_download_request` 改为 async——需要同时改造 `FinsIngestionThreadExecutor` 和整个后台 job 执行模型；(c) 放弃消费 stream，改为在 runtime 层手动 emit coarse progress——plan 未描述此备选路径。
- **为什么有问题**: Plan 没有裁决 async/sync 桥接方案，直接把实现决策推给 implementation agent。这违反了 "code-generation-ready" 要求——agent 必须自行设计线程/协程边界，可能选错方案导致生产崩溃。
- **直接证据**: 
  - `ingestion_runtime.py:291`：`def download(self, request: FinsSourceDownloadAdapterRequest) -> FinsSourceDownloadAdapterResult:`（同步）
  - `ingestion_runtime.py:1881`：`def _execute_download_request(self, record, normalized, request) -> FinsDownloadResultSummary:`（同步）
  - `ingestion_runtime.py:1464`：`self.executor.submit(start.job_id, lambda: self._run_download_job(...))`（提交到 thread executor）
  - `sec_pipeline.py:502`：`async def download_stream(self, request, ...) -> AsyncIterator[DownloadEvent]:`（异步）
  - `dayu/fins/ingestion_runtime.py:107-125`：`FinsIngestionThreadExecutor` 使用 `Thread`，不是 async executor
- **影响**: Implementation agent 可能选错桥接方案导致 `asyncio.Runner` 在已有 event loop 下崩溃，或引入隐蔽的 thread-safety bug。
- **建议改法和验证点**:
  1. Plan 必须在 S2 中显式裁决 async/sync 边界方案。推荐两个可行路径：
     - **路径 A（推荐）**：不改动 adapter protocol。在 `_execute_download_request` / `_run_upload_job` 的 runtime 层，在 adapter 调用前后和 per-document loop 内直接 emit coarse progress events（document started/completed/skipped）。不消费 pipeline stream。优点：零协议变更，无 async 桥接，progress 粒度足够用户感知。
     - **路径 B**：把 `FinsSourceDownloadAdapter.download()` 改为 `async def download(self, request, *, event_sink)`，同时把 `FinsIngestionExecutor` 改为支持 async job。这需要更大的重构范围。
  2. 无论选哪条路径，必须在 plan 中写清楚 threading model 和 event loop 假设。
  3. 验证：mock adapter 的 async download 或 sync download + runtime-emitted progress 都必须有测试覆盖。
- **修复风险（中）**: 路径 A 风险低；路径 B 风险中高。
- **严重程度（高）**: 阻塞 implementation——agent 无法从 plan 确定如何实现。

### 002-未修复-中-S2-protocol-breaking-change-blast-radius

- **位置**: Slice S2 exact changes，"FinsSourceDownloadAdapter.download(...) 必须接收 event_sink" 和 "FinsUploadRunner.run_upload(...) 必须接收 event_sink"
- **问题类型**: 切片过粗 / 架构边界
- **当前写法**: Plan 要求在 `FinsSourceDownloadAdapter.download()` 和 `FinsUploadRunner.run_upload()` 增加必填 `event_sink` keyword 参数。所有 production adapter（SecDownloadAdapter、CnDownloadAdapter、ProductionFinsUploadRunner）和所有 fake/test adapter 必须同步更新。
- **反例/失败场景**: 如果存在未在 allowed files 中列出的 adapter 实现（例如 HK pipeline adapter、未来新市场 adapter、或测试中通过 mock/patch 创建的匿名 adapter），这些实现会在运行时因缺少 `event_sink` 参数而 `TypeError`。Plan 的 allowed files 列表只列出了 `sec_pipeline.py` 和 `cn_pipeline.py`，没有覆盖可能的其他 adapter。
- **为什么有问题**: Protocol 增加必填参数是对所有实现者的 breaking change。Plan 没有做完整的 adapter 实现者盘点，没有列出所有需要更新的具体 adapter 类名和测试替身。Implementation agent 可能遗漏某个 adapter 导致运行时崩溃。
- **直接证据**: 
  - `ingestion_runtime.py:288`：`FinsSourceDownloadAdapter` Protocol 当前只有 `request` 参数
  - `ingestion_runtime.py:638`：`FinsUploadRunner` Protocol 当前只有 `request` 和 `cancellation_checker`
  - Plan allowed files 没有列出 HK pipeline adapter（如果存在）
  - `tests/service/test_fins_direct.py:34`：`_FakeIngestionRuntime` 使用 mock，如果 mock 不更新也会在测试中 `TypeError`
- **影响**: 遗漏 adapter 更新 → 运行时 `TypeError` → job 失败；测试替身未更新 → 测试误报。
- **建议改法和验证点**:
  1. Plan 应显式列出所有需要更新的 adapter 实现类（至少包括 SecDownloadAdapter、CnDownloadAdapter、ProductionFinsUploadRunner 的具体类路径）。
  2. 做一次全仓库 `grep -r "FinsSourceDownloadAdapter\|FinsUploadRunner"` 盘点所有实现者和测试替身。
  3. 在 S2 stop condition 中增加：如果发现未列出的 adapter 实现，必须先更新 allowed files 列表。
  4. 或者：考虑方案调整——不让 adapter 承担 event_sink 职责，改为在 runtime 的 `_execute_download_request` / `_run_upload_job` 中包裹 adapter 调用，由 runtime emit coarse progress。这消除 protocol 变更风险。
- **修复风险（低）**: 盘点+列表更新即可。
- **严重程度（中）**: 不阻塞 plan 逻辑，但如果不处理会导致 implementation 遗漏。

### 003-未修复-中-S2-progress-event-failure-kills-job

- **位置**: Slice S2 error handling，"单个 pipeline event 映射失败应使对应 job failed，而不是悄悄丢失业务进度"
- **问题类型**: 状态机漏洞 / 最佳实践偏离
- **当前写法**: Plan 要求单个 progress event 映射或写入失败时，整体 job 应 failed。
- **反例/失败场景**: 下载 500 个 filing 时，第 498 个 filing 的 progress event 写入因临时磁盘满失败。按当前设计，整个下载 job 会变成 FAILED，尽管 497 个文件已成功写入仓储。用户看到 job 失败，但实际数据已经部分到位——这是一个不一致状态：job record 说 failed，但仓储中有成功写入的文档。
- **为什么有问题**: Progress event 是观测信号，不是业务事实真源。让观测信号的写入失败反作用于业务结果违反了 plan 自身声明的原则（"event sequence 是 per-job 递增游标，不是业务事实，不替代 job record 状态真源"）。把观测失败等同于业务失败是不正确的故障传播。
- **直接证据**: 
  - Plan 自身声明 event sequence 不是业务事实（line 178）
  - `ingestion_runtime.py:1728-1740` 当前下载逻辑：adapter 返回结果 → 检查 cancellation → 根据 downloaded/failed/rejected 计数决定 succeeded/failed。这个业务判断不应该被 progress event IO 失败影响。
- **影响**: 磁盘满等运维问题导致 job 错误标记为 failed，而实际业务数据可能已经部分成功。用户无法区分"业务真的失败了"还是"只是进度报告写不进去"。
- **建议改法和验证点**:
  1. Progress event 写入失败应记录 WARN 日志并继续，不应导致 job failed。
  2. 只有 terminal event 写入失败时才需要考虑——plan 已经对此做了正确裁决（terminal event 写入失败不回溯已保存的 job record）。
  3. 在 job result summary 中增加 `events_emitted_count` / `events_failed_count` 字段，让 operator 知道存在 progress event gap。
  4. 验证：测试 progress event write failure 后 job 仍然 succeeded（如果业务成功）。
- **修复风险（低）**: 改变故障传播策略即可。
- **严重程度（中）**: 当前设计会在运维故障时产生虚假的业务失败。

### 004-未修复-中-S3-poll-interval-unspecified

- **位置**: Slice S3 "Service Fins Direct Event Subscription"，`stream_job_events_until_terminal` 方法签名
- **问题类型**: 契约缺失
- **当前写法**: Plan 描述 `stream_job_events_until_terminal(handle, after_sequence=0)` 为 async generator，"轮询 runtime read_job_events(handle.job_id, after_sequence=cursor, limit=100)"。但没有指定轮询间隔。
- **反例/失败场景**: 如果没有显式 poll interval，implementation agent 可能：(a) 不做 sleep，导致 tight loop 吃满 CPU；(b) 使用默认 1s，但对快速完成的 job（<1s）可能漏掉中间 progress events；(c) 使用过长的 interval，导致 progress UI 更新迟钝。
- **为什么有问题**: Poll interval 直接影响用户可见的 progress 刷新率和系统资源消耗。现有 `wait_for_terminal` 使用 `DEFAULT_FINS_DIRECT_POLL_INTERVAL_SECONDS = 1.0`（`fins_direct.py:32`），但 event stream 的场景不同——events 可能以 sub-second 频率产生（例如快速下载小文件），1s poll 合理但应显式声明。
- **直接证据**: 
  - `fins_direct.py:32`：`DEFAULT_FINS_DIRECT_POLL_INTERVAL_SECONDS = 1.0`
  - `fins_direct.py:448-460`：当前 `wait_for_terminal` 使用 `self.poll_interval_seconds`
  - Plan S3 未提及 poll interval 参数或默认值
- **影响**: Implementation agent 需要自行决定 poll interval，可能与预期行为偏差。
- **建议改法和验证点**:
  1. 在 S3 中显式声明 `stream_job_events_until_terminal` 的 poll interval，建议复用 `FinsDirectCommandService` 的 `poll_interval_seconds`（默认 1.0s）。
  2. 或者在方法签名中暴露 `poll_interval_seconds` 参数，允许 CLI 覆盖。
  3. 验证：测试确认 poll interval 生效，不会 tight loop。
- **修复风险（低）**: 补充参数即可。
- **严重程度（中）**: Implementation agent 可自行合理推断，但缺少显式契约可能导致行为偏差。

### 005-未修复-低-S5-log-assembly-duplicates-existing-helper

- **位置**: Slice S5 exact changes，"main 在 parse_cli_args(argv) 成功后、runner 执行前调用 runtime 日志装配"
- **问题类型**: 非最优方案
- **当前写法**: Plan 描述 main 需要做 `debug -> LogLevel.DEBUG`、`verbose -> LogLevel.VERBOSE` 等映射。
- **反例/失败场景**: `dayu/runtime/log.py:137-174` 已经提供了 `set_level_from_flags(log_level=..., debug=..., verbose=..., info=..., quiet=...) -> LogLevel`，它内部已经完成完全相同的优先级映射，并直接调用 `configure(level=resolved)`。Plan 的写法暗示 main 需要自己实现映射逻辑，这会导致重复实现。
- **为什么有问题**: 重复实现违反了 DRY 原则，且如果 `set_level_from_flags` 的优先级逻辑未来调整，main 中的重复映射可能漂移。Implementation agent 可能没有注意到已有 helper 而自行实现。
- **直接证据**: `log.py:137`：`def set_level_from_flags(*, log_level, debug, verbose, info, quiet) -> LogLevel:` 已存在且完成完全相同的映射。
- **影响**: 轻微——重复代码或行为漂移。
- **建议改法和验证点**:
  1. Plan 应明确写："main 调用 `dayu.runtime.log.set_level_from_flags(log_level=args.log_level, debug=..., ...)`"，而不是列出手动映射。
  2. 如果 `ParsedCliArgs` 的字段名与 `set_level_from_flags` 参数不完全匹配，需要一个薄适配层，但映射逻辑不应重复。
  3. 验证：测试确认 main 调用了 `set_level_from_flags` 或等价的 `configure`。
- **修复风险（低）**: 改描述即可。
- **严重程度（低）**: 不影响正确性，但可能产生不必要的重复代码。

### 006-未修复-低-S3-synthesized-terminal-event-masks-bug

- **位置**: Slice S3 error handling，"若 read_job() 已 terminal 但尚未看到 terminal event，合成一条 terminal FinsDirectJobEvent 后停止"
- **问题类型**: 最佳实践偏离
- **当前写法**: Service 在 job record terminal 但无 terminal event 时合成 terminal event。
- **反例/失败场景**: 如果 terminal event 写入存在系统性 bug（例如 `_save_succeeded` 后忘记 append terminal event），Service 的合成逻辑会静默掩盖这个 bug。Operator 永远看不到 event gap，bug 永远不会被发现。
- **为什么有问题**: Fallback 合成是正确的防御性设计，但必须同时发出可观测信号（WARN 日志），否则会掩盖生产 bug。
- **直接证据**: Plan line 140 描述 terminal event fallback 但不要求日志信号。Plan S3 error handling 没有提到合成时需要 WARN。
- **影响**: 系统性 event 写入 bug 被静默掩盖。
- **建议改法和验证点**:
  1. 在 S3 中增加：合成 terminal event 时必须发出 WARN 日志，说明 "job {job_id} reached terminal status {status} without terminal event, synthesized for consumer"。
  2. 验证：测试确认合成路径产生 WARN 日志。
- **修复风险（低）**: 加一行日志即可。
- **严重程度（低）**: 可观测性改进，不阻塞功能。

## Architecture Boundary Review

Plan 对分层边界的处理总体正确：

- **✅ UI → Service → Fins 边界清晰**：CLI 只通过 Service `stream_job_events_until_terminal` 消费事件，不直接 import Fins storage 或 pipeline。Plan S4 明确 "CLI 不直接调用 read_job_events，只调用 Service stream"。
- **✅ Fins job event 不是 Host EventLog**：Plan 多次声明 Fins job event sidecar 是 Fins 自有 schema，不属于 Host durable schema、Engine contract 或 Host EventLog。这与 `docs/engine/design.md` 的 stream 术语边界一致。
- **✅ 不创建 Host Run**：Plan 明确 "不把 Fins direct commands 改造成 Host run"。Fins direct 保持为 Service/Fins boundary 内的独立路径。
- **⚠️ 见 Finding 001**：Adapter protocol 变更涉及 async/sync 边界，如果处理不当可能破坏 Fins runtime 的线程模型。

## Best-practice Review

- **✅ Bounded payload**：Plan 在 S1/S2 中要求 progress event payload bounded，不含绝对路径、财报原文、raw provider payload。有测试覆盖（S1 tests: "event sidecar 不包含 workspace 绝对路径"）。
- **✅ Terminal event 不回溯 job record**：Plan 正确裁决 terminal event append 失败不回滚已保存的 terminal job record。
- **⚠️ 见 Finding 003**：Progress event 写入失败导致 job failed 不是最佳实践——观测信号失败不应反作用于业务结果。
- **⚠️ 见 Finding 006**：Fallback 合成 terminal event 不记录 WARN，静默掩盖 bug。

## Optimal-solution Review

- **✅ Event sidecar + polling 方案合理**：匹配现有 filesystem job store 模型，不需要跨进程 event bus、WebSocket 或平台化 observer。比引入通用 event bus 更简单、更可维护。
- **⚠️ 见 Finding 001**：Adapter protocol 变更路径可能不是最优方案。备选方案 A（runtime 层 emit coarse progress，不改动 adapter protocol）更简单、风险更低、不涉及 async/sync 桥接。Plan 应考虑将此作为首选路径。
- **✅ Service event stream 复用性**：`stream_job_events_until_terminal` 作为 async generator，未来 GUI/WeChat 可复用，设计合理。

## Overengineering Review

- **✅ 无过度设计**：Plan 只新增 workspace-scoped JSONL sidecar + runtime event sink + Service async iterator + CLI renderer。不引入通用 bus、WebSocket、平台化 observer registry、Host/Engine schema 变更。
- **✅ 不过度抽象**：`FinsIngestionEventSink` 只暴露一个 `emit_progress` 方法，不是通用 event bus interface。
- **✅ Slice 粒度合理**：6 个 slice 各自形成可验证闭环，依赖关系清晰（S1 契约 → S2 生产 → S3 消费 → S4 UI → S5 日志 → S6 文档）。

## Overcoupling Review

- **✅ Fins job event schema 独立**：不耦合到 Host durable schema、Engine contract 或 Host EventLog。
- **✅ CLI 不耦合 Fins storage**：CLI 通过 Service 消费，不直接 import `dayu.fins.storage`。
- **⚠️ 见 Finding 002**：Adapter protocol 增加必填 `event_sink` 参数会将 progress 关注点耦合到所有 adapter 实现者。备选方案（runtime 层 emit）可减少耦合面。

## Open Questions

1. **OQ1（Follow-up）**: `FinsIngestionThreadExecutor` 是否需要升级为支持 async job？如果 S2 选择路径 A（runtime 层 emit），则不需要。如果选择路径 B（adapter async），则需要。Plan 当前未裁决。

2. **OQ2（Clarification）**: S2 中 `_execute_preprocess_request` 的 progress emit 粒度是否足够？Plan 说 "在选中文档、单文档开始、processed/skipped/failed/not_supported、完成时发出 bounded progress"。当前 preprocess 没有独立 pipeline stream model，这个粒度是否足够让用户感知进度？例如 50 个文档的预处理，用户能看到 "document 3/50 processing..." 吗？
