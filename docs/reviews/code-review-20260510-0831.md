### 001-未修复-[accepted→S3]-高-owner-lost 后旧 owner 绕过 fencing 写入 Run terminal failure
- **入口/函数**: `LocalRunHarness._handle_owner_lost`
- **文件(行号)**: `dayu/host/_run_harness.py:1007`
- **输入场景**: 当前 attempt 的 renew loop 已判定 owner 丢失，或 recovery 已接管/推进同一 run；旧 harness 在等待 Engine event 时先收到 `_OwnerLostDuringEngineWait`。
- **实际分支**: `_run_to_store` 捕获 `_OwnerLostDuringEngineWait` 后调用 `_handle_owner_lost`；该函数先用 `_finish_attempt_if_durable` 尝试把旧 attempt 标记为 `LOST`，随后在 `terminal_seen == False` 时直接调用 `self.event_store.append(...)` 写入 `RUN_FAILED(error_code=attempt_lease_lost)`。
- **预期行为**: P8 契约要求所有 attempt-scoped 写入必须携带当前 owner secret 与全局单调 fencing token；lease 过期后旧 owner 的 append 必须被拒绝，非 owner / stale owner 不应污染 canonical facts。
- **实际行为**: owner 已丢失后仍通过裸 `DurableRunEventStore.append` 写入 terminal RunEvent，绕过 `AttemptScopedRunEventAppender` 的 `verify_owner` 与 terminal append + attempt close 的同事务 fencing。
- **直接证据**: `docs/host/phase8-plan.md:12` 要求所有 attempt-scoped 写入携带 owner/fencing；`docs/host/phase8-plan.md:19` 明确 fenced late write 不写 EventLog；`docs/host/phase8-plan.md:24` 要求 lease 过期后旧 owner append 被拒绝。实现中 `_handle_owner_lost` 在 `dayu/host/_run_harness.py:1051` 关闭旧 attempt 后，于 `dayu/host/_run_harness.py:1060` 直接 `self.event_store.append(host_failure_draft(...))`。
- **影响**: 多进程 recovery 或 owner 丢失场景下，旧进程仍可能把 run 推到 terminal failed，污染 EventLog / Run state / projection；新的 recovery attempt 即使已创建，也会遇到 run 已 terminal 或事实序列被旧 owner 终结，形成错误状态。
- **建议改法和验证点**: owner-lost 之后不要写 canonical terminal RunEvent；如果需要对调用方可见，应通过 owner-aware/recovery-aware 的 run lifecycle 决策入口写入，或只记录安全日志/typed result。新增测试应覆盖：旧 owner lost 后 `host_run_events` 不出现 `attempt_lease_lost` terminal event；已创建 recovery attempt 时旧 owner 无法改变 `host_runs` terminal 状态。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 002-未修复-[accepted→S5]-高-recovery 创建的新 attempt 丢失 owner secret，无法续约或继续执行
- **入口/函数**: `AttemptSupervisor.recover_stale_attempts` -> `_process_recovery_candidate`
- **文件(行号)**: `dayu/host/_attempt_supervisor.py:805`
- **输入场景**: startup / 诊断流程调用 `recover_stale_attempts(run_id=...)`，发现旧 attempt 处于 `RUNNING` 且 `lease_expires_at <= now`。
- **实际分支**: `_process_recovery_candidate` 为新 recovery attempt 生成局部 `owner_token` 与 `owner_id`，调用 `mark_recovering_and_create_attempt` 插入 `state='running'` 的新 attempt，然后只返回 `AttemptRecoveryDecision`。
- **预期行为**: recovery 创建的新 attempt 应有可继续治理的 owner context，至少能被当前 supervisor 注册 session、启动 renew loop，并作为后续 append / terminal close 的授权来源；否则“新 recovery attempt 继续治理”的契约无法成立。
- **实际行为**: 新 owner secret 只在局部变量 `owner_token` 中存在，`AttemptRecoveryDecision` 只返回 `recovery_attempt_id` / `recovery_attempt_index` / `reason`，不包含 `AttemptOwnerContext`；代码也没有把 recovery attempt 加入 `_sessions` 或启动 `_renew_loop`。函数返回后明文 owner token 不可恢复，库里只有 hash，新 `RUNNING` attempt 没有任何进程能合法 renew、append 或 close。
- **直接证据**: `AttemptRecoveryDecision` 字段定义只有 action/source/recovery id/index/reason，见 `dayu/host/_attempt_lease.py:292`。`_process_recovery_candidate` 在 `dayu/host/_attempt_supervisor.py:839` 生成 `owner_token`，在 `dayu/host/_attempt_supervisor.py:845` 写入新 attempt，随后 `dayu/host/_attempt_supervisor.py:875` 直接返回 decision。正常 `lease_context` 路径会创建 `_LeaseSession` 并启动 renew task，见 `dayu/host/_attempt_supervisor.py:560`，recovery 路径没有等价动作。
- **影响**: recovery scan 会把旧 attempt 标为 `RECOVERING`，再制造一个不可被任何 owner 继续推进的 `RUNNING` recovery attempt；该行只能等 lease 再次过期进入下一轮 recovery，形成恢复循环或长期悬挂，run 无法可靠完成。
- **建议改法和验证点**: recovery 的“创建新 attempt”应与可执行 owner 生命周期同源：要么返回完整 `AttemptOwnerContext` 并注册 renew session/执行调度，要么只做旧 attempt 诊断收口，不插入不可执行的 running attempt。新增测试应验证 `recover_stale_attempts` 成功后，新 attempt 可通过当前 owner context append 一条 fenced fact / renew / terminal close，而不是只检查行存在。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### 003-未修复-[accepted→S2]-中-外部 fetch_more 路径在 durable harness 下退化为无 fencing append
- **入口/函数**: `LocalRunHarness.fetch_more_tool_result` -> `InMemoryToolRuntime.fetch_more`
- **文件(行号)**: `dayu/host/_run_harness.py:2007`
- **输入场景**: durable harness 已启用 `AttemptSupervisor`，run 尚未 terminal；调用方通过 harness 的 `fetch_more_tool_result` 补读某个仍有效 cursor，而调用发生在 Engine attempt owner scope 之外。
- **实际分支**: `fetch_more_tool_result` 直接委派 `self.tool_runtime.fetch_more(request)`，没有传入或解析 attempt owner；`InMemoryToolRuntime._resolve_appender` 在没有 `ToolRuntimeOwnerScope` 的 ContextVar 时返回 `PlainRunEventAppender`；后续 `_append_fetch_requested` / `_append_fetch_completed` / `_append_cursor_issued` 等 facts 都通过裸 EventStore append。
- **预期行为**: P8 明确 `TOOL_FETCH_MORE_REQUESTED`、`TOOL_FETCH_MORE_COMPLETED`、`TOOL_FETCH_MORE_FAILED`、`TOOL_CURSOR_EXPIRED`、`TOOL_CURSOR_DENIED`、`TOOL_CURSOR_ISSUED` 均属于 attempt-scoped Host-owned canonical facts，durable 路径每条 fact append 都必须在同一事务内完成 `verify_owner` + EventLog append。
- **实际行为**: harness 暴露的补读入口在 durable 路径没有 owner scope 时仍可写 EventLog，且 `PlainRunEventAppender` 不做 owner CAS。
- **直接证据**: ToolRuntime 契约在 `dayu/host/_tool_runtime.py:138` 说明 durable 路径应由 `ToolRuntimeOwnerScope` 安装绑定 owner 的 appender；`dayu/host/_tool_runtime.py:144` 的 plain fallback 只面向非 durable / 测试路径。实现中 `LocalRunHarness.fetch_more_tool_result` 于 `dayu/host/_run_harness.py:2018` 直接调用 runtime；`InMemoryToolRuntime._resolve_appender` 于 `dayu/host/_tool_runtime.py:378` 读取不到 active appender 时，在 `dayu/host/_tool_runtime.py:381` 返回 `PlainRunEventAppender`；`fetch_more` 于 `dayu/host/_tool_runtime.py:823` 起追加补读 facts。
- **影响**: 旧进程、外部调用方或 attempt 边界之外的补读请求可在 run 仍 active 时写入工具补读事实，绕过 owner/fencing；tool trace、memory snapshot 或后续 replay 会看到不属于当前有效 owner 的 facts。
- **建议改法和验证点**: durable harness 的外部补读入口必须显式解析当前 run/attempt owner 并使用 fenced appender；如果没有有效 owner，应返回 typed refusal，不应 fallback 到 plain append。新增测试应直接走 `build_durable_harness(...).harness.fetch_more_tool_result(...)`，在无 owner scope / 旧 owner / lease 过期时断言不写任何 `TOOL_FETCH_MORE_*` EventLog。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
