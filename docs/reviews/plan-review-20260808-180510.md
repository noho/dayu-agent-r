## Findings

### F19-PR-001-未修复-高-deadline 数值与 identity 校验 fail-open，不能强制 1800/180/540 预算

- **位置**: plan `Fresh setup and budgets` 第33-39行；driver `_positive_number` 第98-113行、`_deadline` 第151-236行、`_harness_argv` 第239-281行。
- **问题类型**: 状态机漏洞 / 测试缺口 / 契约缺失。
- **当前写法**: plan声称 real mode强制校验global/chain identity、global file引用和1800秒run、180秒reserve、540秒chain窗口；driver只检查数字 `> 0`、run window `<=1800`、reserve `>=180`、chain window `<=540`，再取三个remaining值的最小值。
- **反例/失败场景**:
  1. argparse和Python JSON都接受 `NaN`。provider-free直接调用得到 `requested=NaN -> effective=NaN -> --timeout-seconds nan`；frozen PTY owner用 `elapsed >= timeout_seconds` 判断超时，对NaN永远为false。
  2. deadline JSON中的NaN也可穿过 `_positive_number` 和全部比较；实测仍返回正的effective timeout。
  3. `run_window=1700`、reserve `=300` 被接受，和plan规定的 `start+1800` / `deadline-180` 不同。
  4. `chain_start=5000`、`chain_deadline=5540`、当前monotonic=1200且requested=1800时，driver接受并返回1420秒，超过每链540秒cap；它没有要求chain start不晚于当前时刻、chain deadline不晚于global cutoff。
  5. `run_id` 与 `chain_id` 只要求非空；wrapper没有expected run/chain identity输入，任意字符串都能通过。global SHA引用只能证明两个文件相关，不能证明它们属于当前run root、workspace、label或chain。
- **为什么有问题**: deadline文件是provider预算的唯一 owner input。非有限值和未绑定identity若在该边界不fail closed，后续harness无法恢复正确预算；诊断或publication不能事后证明调用守住了授权窗口。
- **直接证据**: driver第108-113、168-224行；frozen PTY owner超时判断 `elapsed >= timeout_seconds`；provider-free反例输出依次为 `REQUESTED_NAN_EFFECTIVE nan`、`NON_EXACT_1700_300_ACCEPTED 440.0`、`NAN_ACCEPTED 440.0`、`FUTURE_CHAIN_EFFECTIVE 1420.0`。
- **影响**: provider进程可能超过global/chain wall cap；错误deadline可被当作合法identity并污染execution index，正式evidence不可验收。
- **建议改法和验证点**:
  - 所有requested/JSON monotonic值必须先 `math.isfinite` 且严格为正；JSON parser必须拒绝NaN/Infinity。
  - global window必须按声明的容差精确等于1800秒，cutoff reserve精确等于180秒；chain window必须在 `(0, 540]`，且 `global_start <= chain_start <= now < chain_deadline <= global_cutoff`。
  - driver接收并严格比对expected run/chain identity，或读取Controller冻结且绑定run-root/workspace/label/chain的manifest；不能只校验非空。
  - provider-free测试必须覆盖requested NaN/Inf、JSON NaN/Inf、1700/300、future start、chain超过global cutoff、wrong run/chain identity与closed gate，全部断言spawn计数为0且路径无变化。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### F19-PR-002-未修复-高-冻结 production CLI 与 MiMo model identity 未在 provider 前强制

- **位置**: Goal Confirmation第15-16行；plan `Pre-provider gate` 第19-24行；driver常量第19-28行、参数第39-53行、`_preflight` 第301-327行；frozen harness v2 provenance第95-120行与model透传第221-223行。
- **问题类型**: 契约缺失 / 外部协议边界 / 测试缺口。
- **当前写法**: plan冻结target commit、production CLI SHA、formal harness SHA和PTY owner SHA。driver只强制后两个SHA；model接受任意非空字符串。frozen harness只校验repo target/clean与CLI“是文件”，记录但不比较CLI SHA，并把任意model原样传给production CLI。
- **反例/失败场景**: provider-free preflight以不存在的repo/CLI路径仍返回0；把model设为 `deepseek-chat` 也返回0，输出只证明prompt/harness/PTY owner，不记录或拒绝错误CLI/model。若real mode传入另一个实际存在的CLI文件和DeepSeek model，harness的现有pre-provider检查不会按plan冻结identity拒绝。
- **为什么有问题**: “真实production CLI + MiMo plan、禁止DeepSeek”是Goal Confirmation binding contract，不是运行后的说明性metadata。identity必须在首次可能spawn provider的直接上游校验。
- **直接证据**: driver没有expected CLI SHA、target commit或expected model常量/比较；frozen harness v2第104-120行只比较commit且只要求CLI存在，第221-223行直接透传model；错误model preflight的 `spawn_performed=false/provider_started=false` 仍返回success。
- **影响**: 可能消耗被禁止provider、用错误CLI生成无法归属于target commit/runtime的证据；事后记录SHA不能把该运行变为合法。
- **建议改法和验证点**:
  - 在wrapper preflight和real mode共同调用的identity owner中，严格比较plan冻结的CLI file SHA、detached target commit/clean状态、formal harness SHA、PTY owner SHA与exact MiMo model id；输出仅记录非秘密identity/digest。
  - preflight保持纯只读，不需要spawn harness即可验证repo/CLI；real mode在spawn前再次校验以防漂移。
  - provider-free负测使用wrong CLI bytes、wrong commit/dirty repo、DeepSeek/空白/未知model，全部要求fail closed、spawn 0、provider 0、formal路径不创建。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 高。

### F19-PR-003-未修复-高-R1-R4 ordinal、freshness与最多三链没有可执行的状态 owner

- **位置**: Goal Confirmation第20-21行；plan `Adaptive chain state machine` 第41-59行；driver参数第48行、argv第254-280行；frozen harness v2 terminal trigger第238-255行及PTY owner `run-terminal-count`逻辑。
- **问题类型**: 状态机漏洞 / 不可直接实施 / open question 未收敛。
- **当前写法**: plan声明最多三条fresh chain、每workspace一条，R1-R4依序执行；driver暴露 `--accepted-ordinal-offset`，默认值为0，只检查非负，没有chain ordinal、segment id、fresh workspace identity或previous terminal typed precondition。
- **反例/失败场景**: frozen harness把cleanup trigger构造成 `accepted_ordinal_offset + 1`，PTY owner比较的是workspace累计terminal count。R1完成后已有一个terminal；若R2沿用driver默认offset 0，R2 input发送后 `run-terminal-count:1` 已经满足，cleanup EOT可在R2的新terminal形成前发出。另一个调用方可以换evidence-dir但重复同一workspace、重复segment或启动第四条chain，driver均不会拒绝。
- **为什么有问题**: 同链durable sequence与chain预算是F19观察语义，不应由调用者猜offset或从历史现象推断。错误offset会直接改变PTY动作时序；publication只能记录错误，不能补救。
- **直接证据**: driver第48行默认0、第254-280行仅透传；plan没有R1/R2/R3/R4 offset映射或每段前previous accepted/terminal exact断言；frozen harness v2使用 `terminal_ordinal=offset+1`，PTY owner在累计terminal count达到该值时触发EOT。
- **影响**: R2/R3/R4可能被提前关闭、产生not-started/invalid evidence；同workspace可能重跑或超过三条chain，违反freshness和provider预算授权。
- **建议改法和验证点**:
  - 在plan给出exact invocation/state matrix：R1/R2/R3/R4 expected previous accepted/terminal count分别为0/1/2/3；`accepted-ordinal-offset`改为required且不得有默认值。
  - 每段spawn前从同一typed owner核对previous canonical terminal恰好succeeded、workspace/label/chain deadline identity一致；不满足立即seal且provider不启动。
  - Controller-owned execution ledger为chain分配唯一ordinal 1..3并在R1前证明`.dayu`不存在；wrapper读取该冻结allocation并拒绝重复workspace、重复segment、ordinal>3和第四条chain。
  - provider-free测试覆盖R2 offset 0、跳段、重复R1、复用另一chain workspace、第四chain、previous terminal非succeeded，全部spawn 0。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### F19-PR-004-未修复-中-preflight 可递归创建任意输出父目录

- **位置**: Goal Confirmation `Gate decision` 第40-41行；plan第17、24行；driver参数第52-53行、`_emit` 第330-346行、preflight return第378-380行。
- **问题类型**: sequencing / 副作用边界 / 测试缺口。
- **当前写法**: plan要求双review PASS前不创建formal bundle/deadline，preflight不spawn harness/CLI/provider。driver默认stdout模式确实无这些副作用，但 `--preflight-output` 会执行 `output.parent.mkdir(parents=True, exist_ok=True)` 并独占创建文件，且对目标根没有约束。
- **反例/失败场景**: review前若把preflight output指向尚不存在的F19 run root或evidence目录，wrapper会递归创建formal tree；preflight JSON仍硬编码 `spawn_performed=false/provider_started=false`，无法表示路径副作用。
- **为什么有问题**: pre-provider gate明确依赖“review前不创建formal路径”的可审计顺序。提供一个可绕过该顺序的正常CLI参数，使Controller必须靠调用纪律弥补wrapper contract。
- **直接证据**: driver第344-346行直接mkdir/open；stdout-only真实preflight前后验证五个传入的nonexistent repo/CLI/run-root/workspace/evidence路径均未创建，说明无副作用路径已经存在，不需要mkdir分支。
- **影响**: formal ownership边界可在review前出现，后续freshness、before snapshot与“deadline后创建”证明变得含混。
- **建议改法和验证点**:
  - 最小方案是preflight只输出stdout，移除 `--preflight-output` 与mkdir；由Controller在允许的既有review记录边界捕获文本。
  - 若必须支持文件输出，只允许已存在、明确为provider-free review scratch的父目录，禁止mkdir，并把output path policy与before/after path inventory写入plan；不得允许F19 run/public/private roots。
  - 负测传入不存在父目录、formal root与symlink target，全部fail closed且不创建任何路径。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。

## Architecture / best-practice / optimality / overengineering lenses

- **Goal-bound minimal design**: plan没有扩展产品或schema，publication修复直接对应F18 findings；四个finding都位于外部observation wrapper/Controller输入边界，不要求改产品。
- **Architecture boundary**: `s_0003 -> s_0013` 通过Fins public tool schema和grounding contract，不绕过`dayu.fins.storage`；publication从Host public resolver/Tool Trace owner投影，方向正确。deadline、identity、chain state则缺少同等级的typed owner绑定。
- **Best practice**: argv list避免shell重新分词，prompt/NUL/UTF-8验证合理；缺口集中在非有限浮点、TOCTOU/identity和stateful segment preconditions等高风险负路径。
- **Optimal solution**: 无需新增产品抽象。最小可维护路径是在现有external driver中收紧有限数/identity/offset输入，并由Controller冻结一个小型chain allocation/ledger；不应在CLI、Host或analyzer加fallback。
- **Overengineering / overcoupling**: publication字段和per-attempt analysis是已确认contract，不属于过度设计；不建议让wrapper解析raw SQLite来推断offset或freshness，那会把外部观察脚本耦合到private schema，应复用现有typed terminal projection或Controller-owned已验证ledger。
