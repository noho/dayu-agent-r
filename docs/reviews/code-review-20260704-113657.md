## New Material Findings

未发现新的实质性缺陷。

复审过程中检查了以下潜在风险点，均确认为安全：

1. **反向 first-committer-wins 场景**（timeout 先收口，cooperative closeout 后到）：`active_cancel_closeout_in_transaction` 的 `_invalid_active_cancel_closeout_precondition` 要求 `run.status is RunStatus.CANCELLING`，timeout 后 Run 已为 CANCELLED，cooperative closeout 返回 INVALID_STATE。行为正确，虽无直接测试但由 `test_active_cancel_timeout_closeout_first_committer_wins_after_cooperative_cancel` 的对称逻辑间接覆盖。非阻塞。

2. **跨模块私有 import**：`engine_ingest.py` 导入 `run_transition.py` 的 `_cancel_request_event_id_from_cancelling`。`_` 前缀在 Python 约定中表示模块私有，跨模块导入有违惯例。但 controller adjudication 明确要求 "Keep the helper internal to Host implementation and avoid adding a public export"，`_` 前缀阻止了通过 `__init__.py` 或 `__all__` 的意外公开导出，符合裁决意图。非缺陷。

3. **`_cancel_request_event_id_from_cancelling` 直接 `json.loads`**：`EventLogRow.payload_json` 由 `EventLogStore.append_event` 序列化为 JSON 字符串存储，`read_latest_run_event_by_type` 返回原始行。`json.loads` 是正确的反序列化方式，与原实现中 `_payload_object` 的语义等价。非缺陷。

4. **late_terminal 拒绝优先级**：`_late_rejection_reason` 先检查 `terminal_already_closed`（Attempt 已终态），再检查 `late_terminal_after_active_cancel`（Run CANCELLING 中迟到 terminal）。timeout closeout 后的 Run CANCELLED + Attempt CANCELLED 会被第一条规则捕获为 `terminal_already_closed`；仅发出 cancel 请求但尚未收口（Run CANCELLING）的迟到 terminal 被第二条规则捕获为 `late_terminal_after_active_cancel`。分支顺序正确，两个场景均有测试覆盖。非缺陷。

5. **`_normalized_event_occurred_at` 在 `ValueError` 时抛 `HostDurableError`**：timeout closeout 调用方（Slice 2 watchdog）需要处理此异常。这是 fail-fast 行为，非法 timestamp 不会静默产生错误 payload。符合预期。
