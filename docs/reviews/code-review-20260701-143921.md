## Findings

### 01-未修复-低-claim_wait_record_for_poll 候选读取与 UPDATE 在同一事务内，非授权源

- **入口/函数**: `claim_wait_record_for_poll` (state.py:2039-2125)
- **文件(行号)**: `dayu/host/durable/state.py:2068-2125`
- **输入场景**: 任何 poll 场景下 `_ClaimWaitRecordOperation.__call__` 调用 `claim_wait_record_for_poll`
- **实际分支**: `transaction.fetchone(SELECT ...)` 读取候选 wait_id → `transaction.execute(UPDATE ... WHERE ...)` 以相同 eligibility 谓词原子写入 claim 字段
- **预期行为**: plan 要求在单个原子写操作中完成 eligibility 检查和 claim 字段赋值；UPDATE WHERE 谓词是唯一授权源
- **实际行为**: 候选 `SELECT` 和 `UPDATE` 在同一个 `BEGIN IMMEDIATE` write transaction 内执行（`run_write` 包装，transaction.py:279-288）。SQLite write 序列化保证此事务在提交前不受其他 writer 干扰。`UPDATE WHERE` 重复了所有 eligibility 谓词（`resume_policy`、`status`、`poll_abandoned_at`、`poll_next_observe_at`、`poll_claim_id`/`poll_claim_expires_at`），是真正的 claim 授权门。若候选读取与 UPDATE 之间行变不可达（同一事务且只有此函数修改该行），则 SELECT 仅用于选 wait_id，不构成授权源。
- **直接证据**: `claim_wait_record_for_poll` 第 2068-2088 行 SELECT 候选 → 第 2093-2121 行 UPDATE 重复全部 eligibility 谓词；`run_write` 在 transaction.py:279-288 以 `BEGIN IMMEDIATE` 包裹整个 operation。
- **影响**: 无功能影响。代码结构与 plan 的 "单一原子写操作" 措辞在字面上有差异（多了候选读），但语义正确。codex 实现报告已标注此点。
- **建议改法和验证点**: 无需修改。若追求 plan 的字面一致性，可将 `claim_wait_record_for_poll` 改为单条 `UPDATE ... WHERE ... RETURNING *`（SQLite 3.35+ 支持），消除候选 SELECT，但当前实现已经正确。若保持现状，建议在 `claim_wait_record_for_poll` docstring 中补充说明候选 SELECT 仅优化选行、UPDATE WHERE 是唯一授权源（当前 docstring 第 2049-2051 行已有此说明）。
- **修复风险（低）**: 无需修改或仅需 docstring 补充。
- **严重程度（低）**: 不影响正确性；是 plan 字面措辞与实现的微小偏差，codex 报告已自标注。

### 02-未修复-低-测试未显式覆盖 double-release CAS 冲突场景

- **入口/函数**: `_release_with_backoff` → `_ReleaseWaitRecordClaimOperation.__call__` → `release_wait_record_poll_claim`
- **文件(行号)**: `dayu/host/wait_adapter.py:835-861` → `state.py:2128-2198`
- **输入场景**: poller A claim wait → release with backoff 成功。poller B 在 release 后 claim 同一 wait（backoff 到期后）。poller A 的旧 claim_id 被 B 的新 claim 覆盖。若 A 用旧 claim_id 再次 release（不会发生，因为 poll_once 中每个 claim 只 release 一次），应 CAS 失败。
- **实际分支**: `release_wait_record_poll_claim` 的 WHERE 子句包含 `AND poll_claim_id = ?`（state.py:2180），确保只有匹配当前 claim_id 才可 release。测试 `test_stale_poll_release_cannot_clear_newer_claim`（test_wait_record_state.py）覆盖了 stale claim_id 被拒绝的场景，但仅在 state helper 层测试，未在 `WaitPoller.poll_once` 集成路径中模拟 release CAS 冲突。
- **预期行为**: 若 poller 尝试 release 一个已被他人覆盖的 claim，应检测 rowcount=0 并返回 CAS_LOST，不覆盖新 claim 的字段。
- **实际行为**: `release_wait_record_poll_claim` 的 CAS 正确检测不匹配的 claim_id（state.py:2180），`_wait_record_poll_mutation_result` 对 rowcount=0 且行仍为 WAITING/CANCELLED 时返回 CAS_LOST。`_release_with_backoff` 在 CAS_LOST 时返回 1。调用方将 1 加到 `claim_conflicts`。行为正确，但 poll_once 集成路径缺少此场景的测试。
- **直接证据**: state.py:2180 `AND poll_claim_id = ?`；state.py:5957-5960 CAS_LOST 分支；wait_adapter.py:858-860 返回 0/1。
- **影响**: 测试覆盖不完整 — release CAS 冲突在集成路径未被触发验证，但代码逻辑正确，state helper 层已有覆盖。
- **建议改法和验证点**: 可选：在 `test_wait_adapter_polling.py` 中增加一个集成测试，模拟 adapter 在 poll 中篡改 claim 字段（类似 `_AbandonClaimStealingAdapter`），导致 release 时 claim_id 不匹配，验证 `claim_conflicts` 递增且下一轮 poll 可正常重试。
- **修复风险（低）**: 仅新增测试。
- **严重程度（低）**: state helper 层已覆盖 CAS 逻辑；集成路径的正确性可从代码走读推导。不阻塞 merge。
