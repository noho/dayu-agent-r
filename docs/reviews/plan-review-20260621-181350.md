## Assumptions Tested

1. **Submit-before-accept root cause exists** — Confirmed. `dayu/fins/ingestion_runtime.py:_start_observed_stream` calls `executor.submit` at line 2336-2339 BEFORE returning the handle. The tool callable converts the handle to `ToolAwaitingOutcome` AFTER submit. Host `_accept_awaiting` only runs AFTER the callable returns. Root cause is verified.

2. **Host is the correct owner of activation** — Confirmed. `docs/engine/design.md` Engine boundary (section 1, 11): Engine only does bounded handshake via `ToolExecutor.execute`, does not host external job lifecycle. `docs/host/design.md` lines 2268-2288: Host accept transaction is the awaiting canonical owner.

3. **Existing PENDING status can express prepared-but-not-active** — Confirmed. `dayu/fins/ingestion/observation_handle.py:FinsObservationStatus.PENDING` exists. `dayu/fins/ingestion/wait_adapter.py:_poll_snapshot_result` maps `PENDING` to `WaitPollNotReady`. No new status needed.

4. **Duplicate fanout correctly bypasses activation** — Confirmed. `dayu/host/tool_runtime.py:_execute_one` catches `AWAITING_FANOUT` at line 2334-2338, BEFORE entering `_accept_awaiting`. Fanout waiters receive the owner's prior `ToolAwaitingOutcome` without calling the business callable or activation.

5. **WaitAdapterRegistry pattern can support activation extension** — Confirmed. `WaitAdapterKey` is a stable string key used across binding, poll adapter, and wait record. The plan's `WaitActivationRegistry` keyed by the same `WaitAdapterKey` follows the existing pattern.

6. **No activation concept exists today** — Confirmed. Grep for `activate`, `activation`, `post_accept`, `after_accept`, `on_awaiting_accepted` in `dayu/host/` returned zero results. The plan introduces activation as a new concept.

7. **Process-local observation loss is acceptable** — Confirmed. `_observations` is an in-memory dict. If process dies after accepted wait, the poller (when wired) would find the wait record, poll the missing observation, get `LOST`, and resolve via existing path. Consistent with current lightweight observation design.

## Findings

### F01-unfixed-high-activation-exception-guarantee

- **位置**: Section 7 "Implementation Decisions" — "Activation failure 收口" and "Fins prepare / activate API"
- **问题类型**: 状态机漏洞
- **当前写法**: Plan states: "Fins activation adapter must convert executor submit failure into a terminal observable failure snapshot on the prepared observation" and "ToolRuntime should catch unexpected activation adapter exceptions, emit bounded diagnostic through existing diagnostic emitter, and still return awaiting outcome because Host wait truth has already been accepted."
- **反例/失败场景**: If the adapter's `executor.submit` raises an unexpected exception BEFORE the adapter can write a terminal failure state to the observation, the observation remains `PENDING` forever. The Host wait record exists (accepted ack succeeded). The poller sees `PENDING` → `WaitPollNotReady` indefinitely. The wait record is permanently stuck in `WAITING` state with no resolution path.
- **为什么有问题**: The plan explicitly guarantees "activation failure after accepted wait 被 Fins observation 映射为 failed / lost / diagnostic" but the exception handling specification has a gap. The adapter's exception handling must guarantee terminal observation state on ANY failure path, not just on `executor.submit` failure. Without this guarantee, an implementation agent might write an adapter that catches `executor.submit` exceptions but lets other exceptions (e.g., `KeyError` from observation lookup, `RuntimeError` from lock acquisition) propagate without writing terminal state.
- **直接证据**: Plan section 7 "Activation failure 收口": "Fins activation adapter must convert executor submit failure into a terminal observable failure snapshot" — this only specifies `executor.submit` failure, not all failure paths. Plan section 7 "Fins prepare / activate API": "If executor.submit fails, activation writes a failed observation state" — same gap.
- **影响**: If the adapter throws without writing terminal state, the poller loops indefinitely on the stuck wait record. The Run is permanently `WAITING` with no resolution, violating the success signal "activation failure after accepted wait 被 Fins observation 映射为 failed / lost / diagnostic，不让 Run 永久卡在不可解释的 WAITING."
- **建议改法和验证点**: Add explicit specification: "The activation adapter MUST guarantee that the observation reaches a terminal state (FAILED or LOST) before re-raising ANY exception. The adapter must wrap the entire activate_observation body in a try/except that writes a terminal failure snapshot on any exception path. ToolRuntime activation catch should be a safety net, not the primary failure recording path." Verify with a test that simulates adapter throwing an unexpected exception (not executor.submit failure) and asserts the observation reaches terminal state.
- **修复风险（低/中/高）**: 低
- **严重程度（高）**: High — violates a stated success signal and can cause permanent wait record stuckness in production.

### F02-unfixed-medium-unified-activation-registry

- **位置**: Section 6 "Contract / Schema / State-machine / Public-interface Changes" — "Host internal contract" and Section 7 "Implementation Decisions"
- **问题类型**: 过度设计
- **当前写法**: Plan proposes a new `WaitActivationRegistry` (separate from `WaitAdapterRegistry`) keyed by `WaitAdapterKey`, with a new `WaitActivationAdapter` protocol and `WaitActivationRequest` dataclass, all in `dayu.host.wait_adapter`.
- **反例/失败场景**: Three separate registries (`WaitAdapterRegistry`, `WaitPollAdapterRegistry`, `WaitActivationRegistry`) all keyed by the same `WaitAdapterKey` create parallel lookup patterns that an implementation agent must wire independently. If a new Fins tool is added, the agent must update three registries instead of one. The existing `WaitAdapterBinding` already carries `(tool_name, await_kind, adapter_key, resume_policy, external_job_ref_source)` — adding an optional activation callback to this binding would unify the lookup.
- **为什么有问题**: The plan introduces a new `WaitActivationRegistry` parallel to existing patterns. While individually each registry is simple, the cumulative effect is three registries keyed by the same key type, constructed from the same provider configs, and wired through the same `ToolRuntimeBuildRequest`. This is not severe overdesign, but it's more abstraction than the minimum needed. The alternative — extending `WaitAdapterBinding` with an optional activation callback — would require expanding `dayu.host.api.py` (Host public contract), which the plan explicitly avoids. The plan's approach is defensible as a deliberate choice to avoid changing the Host public contract.
- **直接证据**: Plan section 6: "Add a minimal Host-layer activation adapter contract in dayu.host.wait_adapter, keyed by existing WaitAdapterKey." Plan section 7 "Why this is not overdesigned": "It adds one Host-layer activation adapter keyed by existing WaitAdapterKey." The existing `WaitAdapterRegistry` at `dayu/host/wait_adapter.py:226` already resolves bindings by `(tool_name, await_kind)` and carries `adapter_key`.
- **影响**: Minor. Adds a small amount of parallel wiring that could be unified. Not a blocker for implementation, but the implementation agent should be aware that unification is possible if the Host public contract expansion is acceptable.
- **建议改法和验证点**: Acceptable as-is if the plan's constraint of not expanding Host public contract is maintained. If the controller decides Host public contract expansion is acceptable, the activation callback could be added to `WaitAdapterBinding` in `api.py`, eliminating the need for a separate registry. Otherwise, document the three-registry pattern as intentional construction-time wiring.
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: Low — design choice, not a defect. Plan's approach is defensible.

### F03-unfixed-low-observation-prepared-cancel-after-reject

- **位置**: Section 7 "Implementation Decisions" — "Pre-activation cancel" and Section 8 Slice 2
- **问题类型**: 契约缺失
- **当前写法**: Plan states: "Rejected / timeout / stale / pre-accept cancellation: callable may have prepared a local observation, but ToolRuntime does not activate it. prepared observation must be cancellable/abandonable and must not start executor."
- **反例/失败场景**: When accept is rejected, the callable has already prepared an observation in the in-memory `_observations` dict. No wait record exists. The observation is orphaned — it cannot be polled (no wait record), cannot be activated (no accept), and cannot be explicitly cancelled (no cancel path is triggered). It remains in memory until process exit.
- **为什么有问题**: This is actually acceptable behavior, but the plan doesn't explicitly state it. The orphaned observation is process-local, has no wait record, and is unreachable by any production path. It's equivalent to a callable that prepared state but was never called. However, the plan should explicitly acknowledge this as expected behavior to prevent an implementation agent from adding unnecessary cleanup logic.
- **直接证据**: Plan section 7: "prepared observation must be cancellable/abandonable and must not start executor." This implies cleanup is expected, but no cleanup path is triggered for rejected-accept orphaned observations.
- **影响**: Low. Orphaned observations are harmless (no wait record, no executor, no external side effect). But the plan's wording "cancellable/abandonable" might lead an implementation agent to add unnecessary cleanup.
- **建议改法和验证点**: Add a note: "Observations prepared before accept-rejection are orphaned in memory with no wait record. They are unreachable by production paths and require no explicit cleanup. This is equivalent to a callable that prepared partial state before failing." No test needed for this case.
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: Low — clarification, not a defect.

## Conclusion

**pass-with-risks**

Plan is code-generation-ready and correctly addresses the submit-before-accept root cause. The two-layer design (Host activation hook + Fins prepare/activate) is well-scoped, respects Host/Engine/Fins boundaries, and reuses existing patterns. Three slices align with the control doc Slice 切分原则. No overdesign detected beyond one minor design choice (separate activation registry).

**1 high-severity finding** (F01: activation exception guarantee gap) should be addressed before implementation to prevent permanent wait record stuckness. **1 medium-severity finding** (F02: registry unification) is a design choice, not a blocker. **1 low-severity finding** (F03: orphaned observation clarification) is informational.
