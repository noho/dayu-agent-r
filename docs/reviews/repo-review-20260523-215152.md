### 1-未修复-中-敏感信息脱敏过度保守导致诊断信息丢失

- **入口/函数**: `_exception_diagnostic_message`
- **文件(行号)**: `dayu/engine/agent.py` (206-230)
- **输入场景**: Provider 返回包含 "token"、"header" 等常见词的正常错误消息，例如 "JWT token has expired"、"Content-Type header is invalid"
- **实际分支**: 子串匹配命中 `_SENSITIVE_EXCEPTION_MARKERS`，整条消息被替换为 `"exception message redacted"`
- **预期行为**: 只脱敏真正包含 secret 值的消息（如 `Bearer sk-xxx`），保留正常诊断描述
- **实际行为**: "token"、"header" 等常见英文词作为 marker，导致大量正常诊断信息被误杀
- **直接证据**: `_SENSITIVE_EXCEPTION_MARKERS` 包含 `"token"` 和 `"header"`，匹配方式为大小写不敏感子串匹配
- **影响**: 生产环境问题诊断效率降低，运维人员无法从 EventLog 获取 provider 返回的真实错误原因
- **建议改法和验证点**: 将 marker 改为更精确的模式（如正则匹配 `Bearer\s+\S+`、`api[_-]?key\s*[:=]\s*\S+`），或改为只在消息包含疑似 secret 值（长随机字符串、key-value 格式中的 value 部分）时才脱敏。验证：构造包含 "token" 但不含 secret 的消息，确认不再被误杀
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-低-compaction 诊断路径异常消息未脱敏

- **入口/函数**: `_exception_diagnostic_suffix`
- **文件(行号)**: `dayu/host/compaction_operation.py` (272-282)
- **输入场景**: Provider 返回包含 Bearer token 或 API key 的异常消息
- **实际分支**: `str(exc)` 直接拼接到诊断后缀，未经脱敏
- **预期行为**: 与同模块的 `_safe_exception_message` 保持一致的脱敏策略
- **实际行为**: 同一个异常对象通过两条路径处理：`_safe_exception_message` 脱敏，`_exception_diagnostic_suffix` 不脱敏
- **直接证据**: 第 279 行 `message = str(exc)` 无脱敏；第 355-359 行 `_safe_exception_message` 对 Bearer token 和 assignment-style secret 做正则替换
- **影响**: 异常消息如果包含 provider 返回的 headers / payload 片段，理论上可进入 durable EventLog，导致 secret 持久化
- **建议改法和验证点**: 将 `_exception_diagnostic_suffix` 的 `str(exc)` 替换为 `_safe_exception_message(exc)`，或抽取公共脱敏函数。验证：构造包含 Bearer token 的异常，确认 diagnostic_refs 中不包含原始 token
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 3-未修复-低-Config Loader 递归继承无最大深度限制

- **入口/函数**: `_resolve_record`
- **文件(行号)**: `dayu/runtime/config_loader.py` (963-1018)
- **输入场景**: 配置文件构造极深的 extends 继承链（A extends B, B extends C, ... 几百层）
- **实际分支**: 递归调用 `_resolve_record`，无深度计数器
- **预期行为**: 设置最大递归深度（如 32 层），超出时抛出明确错误
- **实际行为**: 依赖 Python 默认递归限制（~1000），最终抛出 `RecursionError`，错误信息不直观
- **直接证据**: `_resolve_record` 通过 `visiting` 列表检测循环继承，但未设置最大递归深度
- **影响**: 恶意或错误配置文件可导致 `RecursionError`，错误信息不指向配置问题
- **建议改法和验证点**: 添加 `max_depth` 参数，在递归计数超出时抛出 `ConfigError("extends chain too deep")`。验证：构造 3 层继承链正常工作，构造 100 层继承链抛出明确错误
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 5-未修复-低-Lane 无限等待循环无超时断路器

- **入口/函数**: `_await_task_after_outer_cancellation`
- **文件(行号)**: `dayu/runtime/lane.py` (1017-1024)
- **输入场景**: 底层 SQLite 线程操作永久挂起（如磁盘 I/O 故障）
- **实际分支**: `asyncio.shield` 被外层 cancel 后，以 10ms 间隔无限轮询等待 shielded task 完成

- **建议改法和验证点**: 添加 `max_wait` 参数，超时后 `task.cancel()` 并记录 WARN 日志。验证：正常路径在超时内完成，异常路径在超时后正确退出
- **修复风险（低/中/高）**: 低

### 6-未修复-低-Truncation cursor 字典无界增长

- **输入场景**: 大量不同工具各自产生截断，cursor 创建速率持续高于清理速率
- **实际分支**: 扫描限制（256）和清理限制（64）导致未被扫描到的过期 cursor 永远不被清理

- **建议改法和验证点**: 在 `_store_cursor` 中添加字典大小检查，超出阈值时强制清理。验证：高频率截断场景下字典大小有上界

### 8-未修复-低-Duplicate governance key 不含 attempt_id

- **入口/函数**: `InMemoryRunLocalDuplicateGovernance.decide_duplicate`
- **文件(行号)**: `dayu/host/tool_runtime.py` (1691-1716)
- **输入场景**: Run 经历 cancel + retry（新 Attempt），新 Attempt 调用与旧 Attempt 相同的工具
- **实际分支**: `_duplicate_key` 由 `tool_name + tool_identity_digest + normalized_arguments_digest + semantic_duplicate_key` 组成，跨 Attempt 共享
- **预期行为**: Duplicate governance 应按 attempt_id 隔离，或文档明确说明 Run-scoped 行为
- **实际行为**: 同一 Run 内不同 Attempt 的相同工具调用会被识别为"重复"
- **直接证据**: `InMemoryRunScopedDuplicateGovernanceRegistry` 按 `run_id` 隔离，不按 `attempt_id` 隔离
- **影响**: 合法的重试调用可能被 duplicate governance 拦截。实际风险低（默认策略是 `ALLOW`，`HARD_STOP` 需显式配置）
- **建议改法和验证点**: 在 key 中加入 `attempt_id`，或在 retry/replay 路径中重置 duplicate governance 状态。验证：cancel + retry 场景下新 Attempt 的工具调用不被误判为重复
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
