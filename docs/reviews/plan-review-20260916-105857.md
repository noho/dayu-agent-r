# Plan Review: Docling 2.90.0 → 2.127.0 升级方案

- **Reviewed target**: `docs/plans/docling-2-127-upgrade.md`
- **Review scope**: 技术正确性 — 版本选择依据、依赖冲突结论、API 兼容性验证、平台可行性
- **Review date**: 2026-09-16

## Assumptions Tested

1. 目标版本与 docling 官方 uv.lock 对齐
2. 依赖冲突逐包核对结论可复现
3. API 兼容性验证覆盖所有项目实际使用的 API
4. 平台可行性证据充分
5. 回退方案可行
6. 回归验证计划可执行

---

## Findings

### 01-未修复-[中]-版本选择偏离官方 uv.lock 验证基线

- **位置**: 2.1 依赖冲突盘点 — docling-core、docling-parse 目标版本
- **问题类型**: 非最优方案 / 假设不成立
- **当前写法**: plan 声称"对齐 docling 官方 uv.lock 在 py3.11 的验证基线"，目标 docling-core 2.96.1、docling-parse 7.20.0
- **反例/失败场景**: 官方 uv.lock（2026-09 main 分支）在 py3.11 锁定的是 docling-core **2.96.0**（非 2.96.1）和 docling-parse **7.19.0**（非 7.20.0）。2.96.1 相比 2.96.0 仅新增 `requests>=2.34.2` 依赖（修复遗漏依赖 PR #764）；7.20.0 相比 7.19.0 是新 patch。两者均满足上游约束，但都不是官方 lock 实际验证的版本。
- **为什么有问题**: plan 的核心说服力来自"与官方验证基线对齐"，但实际选择了未经官方 lock 验证的更新 patch。若2.96.1 的 requests 新引入依赖与项目已有依赖树冲突（虽然概率低），或 7.20.0 引入未被官方覆盖的行为变化，将无法用"官方已验证"作为安全背书。
- **直接证据**:
  - uv.lock: `docling-core: 2.96.0`（从 `https://raw.githubusercontent.com/DS4SD/docling/main/uv.lock` 提取）
  - uv.lock: `docling-parse: 7.19.0`
  - PyPI: docling-core 2.96.0 requires_dist 无 `requests`；2.96.1 新增 `requests<3.0.0,>=2.34.2`
- **影响**: 版本选择依据可信度降低；若出现依赖冲突，无法直接引用官方验证作为兜底
- **建议改法和验证点**: 二选一：(a) 改回官方 lock 版本 2.96.0 + 7.19.0，requests 2.33.1 已满足 docling-core 2.96.0 的要求（无 requests 依赖）；(b) 保留 2.96.1 + 7.20.0 但明确说明偏离原因（2.96.1 修复了遗漏依赖 bug），不声称"与官方 lock 对齐"。验证点：无论选哪个，都需要在 CI 安装冒烟中验证完整依赖树可解。
- **修复风险**: 低
- **严重程度**: 中

### 02-未修复-[中]-docling-core API 兼容性未验证

- **位置**: 2.2 项目所用 docling API 兼容性
- **问题类型**: 契约缺失 / 测试缺口
- **当前写法**: section 2.2 仅验证 docling 包的 API（DocumentConverter、PdfFormatOption 等），声称"代码层无需改动"
- **反例/失败场景**: `docling_processor.py` 重度使用 docling-core 的类型 API（22 个 minor 版本跨度 2.74.0→2.96.1）：`DoclingDocument.load_from_json()`（line 554）、`document.iterate_items()`（line 573）、`TextItem`/`NodeItem`/`TableItem` 类型（lines 17, 20, 73, 99 等 30+ 处引用）。v2.87.0 将 `document.py` 拆分为子模块（PR #664），类型迁移到 `items/text.py`、`items/node.py`、`items/table/`。虽然 document.py 保留了 re-export，但 plan 完全未验证这些 API。
- **为什么有问题**: plan 的"代码层无需改动"结论只覆盖了 docling 包 API，遗漏了 docling-core 的 API 兼容性验证。项目对 docling-core 的依赖深度（类型定义、方法调用、属性访问）远超 docling 包本身。
- **直接证据**:
  - `dayu/documents/processors/docling_processor.py` line 17: `from docling_core.types.doc.document import TextItem`
  - line 549: `from docling_core.types.doc.document import DoclingDocument`
  - line 554: `DoclingDocument.load_from_json(str(source_path))`
  - line 573: `document.iterate_items(with_groups=False)`
  - docling-core v2.87.0 changelog: "Split the monolithic `document.py` into focused modules (#664)"
  - docling-core main branch `document.py` lines 107, 138, 146: re-exports from `items/node`, `items/table/table`, `items/text`
- **影响**: 升级后 docling_processor.py 可能在 import 或运行时失败，而 plan 未将其纳入回归范围
- **建议改法和验证点**: 在 section 2.2 补充 docling-core API 兼容性验证，至少覆盖：`DoclingDocument.load_from_json()`、`iterate_items()`、`TextItem`/`NodeItem`/`TableItem` 的 import 路径和属性访问。验证方法：对一份样本 JSON 用 docling-core 2.96.1 执行 `load_from_json` + `iterate_items` 全流程。由于 re-export 存在（实测确认），结论很可能也是兼容，但需显式验证。
- **修复风险**: 低
- **严重程度**: 中

### 03-未修复-[中]-export_to_dict 风险定位与代码实际语义不匹配

- **位置**: 2.4 行为变化风险 #1、步骤 2 回归动作 #1、风险清单第1行
- **问题类型**: 目标漂移 / 架构边界
- **当前写法**: plan 将"export_to_dict schema 变化"列为最高风险（高），声称"破坏 LLM-facing 投影与持久化契约"，回归动作要求"确认 `dayu.fins.upload_format_contract` 与 LLM-facing 投影路径仍满足"
- **反例/失败场景**: 代码实际行为：(1) `docling_process_converter.py:294` 将 `export_to_dict()` 输出视为不透明 JSON blob，仅验证 `_is_closed_json_value`（无 NaN/Infinity），然后 `json.dumps` 写入文件；(2) `upload_format_contract.py` 只验证文件后缀（`.pdf`/`.docx` 等），与 docling JSON schema 完全无关；(3) `docling_processor.py` 用 `DoclingDocument.load_from_json()` 解析 JSON，访问的是 docling-core 的 Pydantic 模型属性，不直接操作 dict key。
- **为什么有问题**: plan 的风险定位和缓解措施指向了错误的 contract 边界。真正的风险面是：(a) `DoclingDocument.load_from_json()` 能否正确解析新版 `export_to_dict()` 的输出（这是 docling-core 内部的序列化/反序列化契约）；(b) LLM 消费的文本/表格/heading 内容是否因 docling 输出变化而退化。plan 引用 `upload_format_contract` 作为验证目标是误导。
- **直接证据**:
  - `docling_process_converter.py:293-305`: `exported = cast(JsonValue, conversion.document.export_to_dict())` → 不透明 blob
  - `upload_format_contract.py`: 仅验证 `Path.suffix`，无 JSON schema 检查
  - `docling_processor.py:554`: `DoclingDocument.load_from_json(str(source_path))` → 通过 Pydantic 模型访问
- **影响**: 实施 Agent 可能在 upload_format_contract 上浪费精力做无意义的 schema 验证，而遗漏真正的回归点（load_from_json 兼容性 + LLM 投影语义）
- **建议改法和验证点**: 将风险 #1 重新定位为："docling-core 升级后 `DoclingDocument.load_from_json()` 能否正确解析旧版/新版 `export_to_dict()` 输出；LLM 投影的文本/表格/heading 内容是否退化"。回归步骤 2.1 改为"对样本执行 `load_from_json` + `iterate_items` 全流程，验证解析成功 + 内容一致性"。删除对 `upload_format_contract` 的引用。
- **修复风险**: 低
- **严重程度**: 中

### 04-未修复-[低]-回退方案描述不完整

- **位置**: 5. 回退方案
- **问题类型**: 状态机漏洞
- **当前写法**: "constraints 文件为纯版本锁定变更、无代码改动；回滚 constraints 并重建环境即可回到 2.90.0 基线"
- **反例/失败场景**: (1) `pyproject.toml` 的 `transformers` 约束从 `>=4.57.6,<5.0.0` 改为 `>=5.16.1,<6.0.0`，这是代码改动；(2) `lock-macos-x64-py311.txt` 被删除，回退需从 git 恢复；(3) 若步骤 2 已对250 份样本执行了新版 docling 转换并覆写了旧 `_docling.json`，回退 docling 版本不会恢复旧产物。
- **为什么有问题**: 回退方案低估了变更范围，可能导致实施 Agent 在回退时遗漏 pyproject.toml 恢复或 git 历史恢复步骤。
- **直接证据**: plan section 3 步骤 1 明确包含 pyproject.toml 修改和 macOS x64 lock 文件删除
- **影响**: 回退操作不完整，残留不一致状态
- **建议改法和验证点**: 补充回退步骤清单：(1) git revert pyproject.toml 变更；(2) git restore lock-macos-x64-py311.txt；(3) 恢复 constraints 文件；(4) 重建环境。明确说明：若样本库 `_docling.json` 已被新版覆写，需从备份恢复或重新转换。
- **修复风险**: 低
- **严重程度**: 低

### 05-未修复-[中]-Linux CUDA 依赖链体积未量化

- **位置**: 2.3 平台可行性评估 — Linux x64、风险清单
- **问题类型**: 不可直接实施
- **当前写法**: "Linux 平台 lock 需补充锁定这些包（版本已被 torch `==` 固定，解析不受影响，锁定仅为严格复现）"；风险清单标记为"中"："安装体积显著增大"
- **反例/失败场景**: torch 2.14.0 在 Linux 上强制拉入 CUDA 13.0 依赖链：nvidia-cudnn-cu13 **1541MB**、triton **2714MB**、nvidia-cusparselt-cu13 522MB、nvidia-nccl-cu13 411MB、cuda-bindings 266MB、nvidia-nvshmem-cu115MB，合计约 **5.5GB**。对于 CPU-only 推理的 Linux 部署（如 CI runner、轻量服务器），这是显著的磁盘和下载开销。plan 未提供缓解方案（如 `--no-deps` 安装 + 手动锁 CPU-only 子集、或使用 `torch` 的 `cpu` extra）。
- **为什么有问题**: 实施 Agent 在步骤 1 锁定 Linux platform lock 时，可能未意识到完整 CUDA 链的体积影响，导致 CI 磁盘溢出或部署失败。plan 建议"Linux CI/部署磁盘配额需提前确认"但未给出量化数据或替代方案。
- **直接证据**: PyPI 下载体积：nvidia-cudnn-cu13 1541MB、triton 2714MB（合计5.5GB+）
- **影响**: Linux CI/部署磁盘不足；无缓解方案时实施 Agent 被动接受全量 CUDA 安装
- **建议改法和验证点**: 在 plan 中量化 CUDA 链体积（~5.5GB），评估是否需要 CPU-only 变体（torch 的 `--index-url https://download.pytorch.org/whl/cpu`）。若项目 Linux 部署确实只用 CPU 推理，可考虑在 Linux lock 中用 CPU-only wheel 替代默认 CUDA wheel。
- **修复风险**: 中
- **严重程度**: 中

### 06-未修复-[中]-250 样本回归计划缺乏可执行细节

- **位置**: 步骤 2：样本库输出回归
- **问题类型**: 不可直接实施
- **当前写法**: 描述了回归目标（schema diff、语义 diff、退化判定），但未提供执行方法
- **反例/失败场景**: 实施 Agent 面对250 份样本需要：(a) 一个脚本或命令来批量执行 docling 转换；(b) 一个 diff 工具或脚本来对比新旧 `_docling.json`；(c) 通过/失败的判定标准。plan 均未提供。
- **为什么有问题**: 步骤 2 的描述停留在"做什么"层面，缺少"怎么做"。实施 Agent 需要自行设计 diff 脚本、定义判定标准、处理250 份样本的批量执行逻辑。这增加了实施不确定性。
- **直接证据**: plan section 3 步骤 2 无脚本路径、无 diff 工具名、无判定阈值
- **影响**: 实施 Agent 可能跳过批量 diff 或使用不一致的判定标准
- **建议改法和验证点**: 至少指定：(a) 使用 `dayu` 的 docling 转换入口批量处理样本；(b) 使用 `diff` 或 Python 脚本对比顶层 key 集合 + 文本内容 hash；(c) 定义"退化"判定标准（如 key 缺失、文本内容差异 > N%、表格结构变化）。
- **修复风险**: 低
- **严重程度**: 中

## Open Questions

1. **docling-core v2.87.0 的 document.py 拆分是否影响 `DoclingDocument.load_from_json()` 对旧版 `_docling.json` 的解析？** 已确认 re-export 存在、`load_from_json` 和 `iterate_items` 方法保留，但未用实际旧版 JSON 文件验证。建议在步骤 2 中用一份样本显式验证。

2. **torch 2.14.0 的 MPS 后端（macOS arm64）精度修复是否会导致表格结构识别结果与 2.4.1 显著不同？** plan 提及但未量化。建议在步骤 2 的含表格样本中重点关注。

3. **docling-slim 的 transformers darwin 排除列表（5.0~5.3、5.9~5.15）的具体原因是什么？** 已确认排除列表存在且 5.16.1 不在排除范围内，但未了解排除原因。若原因是 macOS ARM64 特定 bug，5.16.1 是否已修复需确认。

4. **docling-core 2.96.0 → 2.96.1 的 `requests` 新依赖是否会导致与项目已有 requests 版本冲突？** 当前锁定 requests 2.33.1，2.96.1 要求 >=2.34.2。需升级 requests。若选择 2.96.0（官方 lock 版本），则无需升级 requests。

## Final Plan Review Conclusion

**pass-with-risks**

方案整体技术方向正确，版本选择合理，依赖冲突分析大部分可复现。主要问题是：(1) 声称与官方 uv.lock 对齐但实际偏离了两个包的版本（中）；(2) API 兼容性验证遗漏了 docling-core 的 API（中）；(3) export_to_dict 风险定位指向了错误的 contract 边界（中）。这三个问题均为可修复的 plan 描述问题，不构成结构性阻塞。

修复 findings 01-03 后，方案可安全交给实施 Agent。
