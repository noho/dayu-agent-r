## Findings

### 01-未修复-[高]-covered_fiscal_periods 的 tuple/list canonical 比较未定义

- **位置**：P4.2 `_require_matching_cn_annual_publication(meta, candidate)` 的 `covered_fiscal_periods` 比较（plan `:188`）；关联 P3.2 expected_meta 同版校验（`:115`）、P5.2/P5.3 矩阵（`:283-301`）。
- **问题类型**：契约缺失 / 不可直接实施 / 测试缺口。
- **当前写法**：plan 只写“比较 provider/source_id、fiscal_year、fiscal_period、covered_fiscal_periods”，没有规定 candidate 的 canonical tuple 如何与持久化 JSON list 比较，也没有指定非法 list 形状的 typed rejection。
- **反例/失败场景**：合法 source meta 为 `covered_fiscal_periods: ["FY"]`，candidate 为 `period_projection.covered_periods == ("FY",)`。若实现按“严格相等”直接比较，`["FY"] != ("FY",)`，合法 CN FY COMPLETE 会被判为 `period_metadata_mismatch`，不能 skip；增量请求会继续远端 GET/转换，或直接产生失败行，破坏“合法完整源零 PDF GET/零转换”。若实现各自做隐式转换，又没有 owner-level contract，fake/fixture 可能固化错误表示。
- **为什么有问题**：实际类型真源已经分裂为 tuple 与 JSON list：`cn_download_models.py:171-172` 定义 tuple，`cn_download_source_upsert.py:260` 写入 list；现有 HK 逻辑 `cn_download_filing_workflow.py:198` 明确使用 `list(candidate.period_projection.covered_periods)`。P4.2 是新 CN FY COMPLETE 证明的 owner 边界，必须在该边界声明 canonical projection，不能留给消费者猜测或在下游补救。
- **直接证据**：`dayu/fins/pipelines/cn_download_models.py:171-202`、`dayu/fins/pipelines/cn_download_source_upsert.py:249-261`、`dayu/fins/pipelines/cn_download_filing_workflow.py:191-199`；plan `:188` 仅列字段名，无转换/形状规则。
- **影响**：所有合法 CN FY COMPLETE skip 可能被错误拒绝，增量行为退化为重复获取/转换或整体失败；测试若只用同一 Python 容器 fake，无法发现真实 Fs JSON list 的契约偏差。
- **建议改法和验证点**：在 P4.2 明确唯一 canonical 比较为 `meta["covered_fiscal_periods"] == list(candidate.period_projection.covered_periods)`（或明确投影为 canonical tuple 后比较），并要求持久化值只能是非空 canonical JSON list、顺序固定、无重复；缺字段/非 list/顺序或值不一致统一 `period_metadata_mismatch`。P5.2/P5.3 增加真实 Fs `["FY"]` vs `("FY",)` 的合法 skip、tuple/list 错配、缺字段和重复/乱序反例，并保留 HK 现有 `list(...)` 行为回归。
- **修复风险（低/中/高）**：低。
- **严重程度（低/中/高/严重）**：高。
