## Findings

### S5-F01-未修复-低-CLI 与 Service 之间异常传播产生双重 ERROR 日志

- **入口/函数**: `_wait_for_terminal_handling_sigint`（CLI）/ `request_cancel`（Service）、`_consume_fins_direct_events`（CLI）/ `stream_job_events_until_terminal`（Service）
- **文件(行号)**:
  - `dayu/cli/commands/fins.py:582-587` 与 `dayu/service/fins_direct.py:634-636`（cancel 路径）
  - `dayu/cli/commands/fins.py:627-633` 与 `dayu/service/fins_direct.py:569-575`（event read 路径）
- **输入场景**: Service 层 `self._runtime.request_cancel(job_id)` 或 `self._runtime.read_job_events(...)` 失败时，Service 层先通过 `_LOGGER.exception(...)` 记录 ERROR（含 traceback），然后 re-raise；异常传播到 CLI 层后，CLI 层再次通过 `_LOGGER.exception(...)` 记录 ERROR 并 re-raise。
- **实际分支**: Service 层 `except Exception` 分支（`fins_direct.py:569`、`634`）→ CLI 层 `except Exception` 分支（`fins.py:582`、`627`）。
- **预期行为**: 同一 root cause 只应在最内层（Service）产生一条 ERROR 日志；外层可以在 WARNING 或 DEBUG 级别记录传播事实，避免重复 ERROR。
- **实际行为**: 同一 root cause 产生两条 ERROR 日志（分别来自 `dayu.service.fins_direct` 和 `dayu.cli.commands.fins` logger），每条都包含完整 traceback。在默认 INFO 及以下级别时两条都会出现在日志输出中。
- **直接证据**:
  - Service 层：`fins_direct.py:634` 行 `_LOGGER.exception("Fins direct cancel request failed; ...")` + `raise`
  - CLI 层：`fins.py:582` 行 `_LOGGER.exception("Fins direct cancel request failed; ...")` + `raise`
  - 两条日志消息文本几乎一致，语义指向同一失败事件。
- **影响**: 运维排障时可能看到重复错误信息，增加噪音但不影响正确性；异常仍正确传播到最终 `run_fins_direct_command` 的 `except Exception` → `render_cli_error` → `EXIT_FAILURE` 路径。
- **建议改法和验证点**: 选择一层作为 ERROR 真源（推荐 Service 层，因为它是异常首发现场）；外层在 re-raise 前降级为 `_LOGGER.warning(...)` 或 `_LOGGER.debug(...)` 记录传播事实。验证：确认同一失败只产生一条 ERROR，但 WARNING/DEBUG 仍可追踪传播路径。
- **修复风险（低）**: 仅调整日志级别，不改控制流或异常语义。
- **严重程度（低）**: 不影响正确性、状态机、用户体验；属于可观测性冗余。

### S5-F02-未修复-低-`_bounded_payload_keys` 与 `_log_verbose` 在 CLI 和 Service 层重复定义

- **入口/函数**: `_bounded_payload_keys`、`_log_verbose`、常量 `_VERBOSE_LEVEL_NAME` 与 `_LOG_PAYLOAD_KEY_LIMIT`
- **文件(行号)**:
  - `dayu/cli/commands/fins.py:80-81`（常量）、`665-673`（`_bounded_payload_keys`）、`676-687`（`_log_verbose`）
  - `dayu/service/fins_direct.py:41-42`（常量）、`872-880`（`_bounded_payload_keys`）、`883-894`（`_log_verbose`）
- **输入场景**: 两个模块各自定义了语义完全相同的私有辅助函数和常量。
- **实际分支**: 不适用（不是分支问题，是结构性重复）。
- **预期行为**: 项目中 `CLAUDE.md` 编码硬约束要求"重复逻辑必须抽取"。虽然分层架构原则上尽量避免跨层耦合，但纯工具性质的日志辅助函数（`_log_verbose` 依赖 `logging.getLevelName` + `_LOGGER.log`，`_bounded_payload_keys` 依赖 `sorted(payload.keys())`）不涉及任何层特定语义，可以放在层中立的 `dayu.runtime.log` 或等效公共位置。
- **实际行为**: 两份逐字相同的代码分布在两个模块中。若未来 `VERBOSE_LOG_LEVEL` 值变更、`_LOG_PAYLOAD_KEY_LIMIT` 调整、或日志格式需要统一修改，需要同时改动两个文件。
- **直接证据**: diff 显示 `_bounded_payload_keys` 和 `_log_verbose` 在两个文件中逐行一致（仅 `_LOGGER` 引用不同模块的 logger，这是 `logging.getLogger(__name__)` 的正常行为）。
- **影响**: 维护负担轻微增加；当前两份代码一致且简单（各约 6 行），短期内不会产生分歧。
- **建议改法和验证点**: 考虑将 `_log_verbose` 和 `_bounded_payload_keys` 提取到 `dayu.runtime.log` 模块（该模块已是层中立的基础设施，已注册 VERBOSE level）。两个模块的调用方只需传入各自的 `_LOGGER` 实例。验证：确保现有 verbose/debug 日志测试仍然通过，pyright 0 errors。
- **修复风险（低）**: 纯重构，不改变日志输出行为。
- **严重程度（低）**: 不影响正确性；属于可维护性改进。当前分层架构下，保留重复作为有意识的分层选择也是可接受的防御策略（避免 Service 层依赖 CLI 工具模块或反之）。建议在 S6 或后续清理中统一裁决，不作为 S5 blocking。

## Residual Risk

- **S5-R1**: 当前 `dayu.runtime.log` 在模块导入时注册 VERBOSE level（`dayu/runtime/log.py:69`），但 `set_level_from_flags` 调用后才配置 handler/logger 的 effective level。如果未来 CLI 入口在 `set_level_from_flags` 之前有日志调用路径，VERBOSE/DEBUG 消息在 level 注册后、handler 配置前会被直接丢弃（不报错也不输出）。当前 `main()` 中 `set_level_from_flags` 紧跟在 `parse_cli_args` 之后，不存在此窗口，但未来修改者需要意识到这个时序依赖。建议在 `dayu.runtime.log` 模块 docstring 中注明此约束，或考虑将 handler 默认配置与 level 注册放在同一导入时点。
- **S5-R2**: `test_fins_direct_verbose_log_outputs_execution_skeleton` 和 `test_fins_direct_debug_log_outputs_event_details` 断言日志消息出现在 `captured.out` 中。这依赖于 `dayu.runtime.log` 将日志 handler 配置为输出到 stdout。如果未来 runtime log 配置改为 stderr-only 或文件输出，这些测试将因输出流不匹配而失败。当前配置行为由 `dayu.runtime.log` 的 handler 安装逻辑决定，测试与实现之间的这个隐式契约未在测试 docstring 或 runtime log 文档中显式说明。
- 上述两条均为低风险 indirect dependency/时序假设，不影响 S5 正确性；建议在后续 runtime log 清理或 S6 文档同步时裁决是否需要显式化。
