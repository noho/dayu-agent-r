## 2. New Findings (Post-Fix)

### N1-未修复-中-`compact_pipeline_source_snapshot_from_pre_dispatch_view` 构造函数未列在 function signatures 中

- **位置**: §5.2 Function Signatures vs §6.1/6.2 Caller Wiring Pseudocode
- **问题类型**: 不可直接实施
- **当前写法**: §6.1 和 §6.2 的伪代码都调用 `source_snapshot = compact_pipeline_source_snapshot_from_pre_dispatch_view(trigger_source=..., run=..., material_view=...)`，但 §5.2 的 7 个函数签名中没有这个函数。
- **反例/失败场景**: Implementation agent 需要自行设计从 `PreDispatchCompactMaterialView`（包含 `material_blocks`、`previous_compacted_view`、`source_boundary`、`current_input_text` 等）到 `CompactPipelineSourceSnapshot`（包含 `material_view_digest`、`material_source_refs`、`input_event_sequence` 等）的转换逻辑。关键问题：`material_view_digest` 和 `material_source_refs` 的计算逻辑是什么？是从 `PreDispatchCompactMaterialView` 的现有字段提取，还是需要新增 hash/ref extraction？
- **为什么有问题**: 这不是 trivial field mapping — `input_event_sequence` 来自 `run.input_event_sequence`（外层 lifecycle 知识），`material_view_digest` 需要由 pipeline 内部或 material builder 计算。如果 constructor 被遗漏，implementation agent 需要猜测哪些字段来自 `PreDispatchCompactMaterialView`、哪些来自 `run`、哪些来自 pipeline 计算。
- **直接证据**:
  - §6.1: `source_snapshot = compact_pipeline_source_snapshot_from_pre_dispatch_view(trigger_source=..., run=run, material_view=material_view)`
  - §5.2: 7 个 listed functions，无此 constructor。
  - `CompactPipelineSourceSnapshot` 字段：`session_id`（从 run）、`run_id`（从 run）、`input_event_sequence`（从 run）、`trigger_source`（caller 参数）、`current_input_ref`（从 run）、`current_input_text`（从 material_view）、`material_blocks`（从 material_view）、`previous_compacted_view`（从 material_view）、`source_boundary`（从 material_view）、`material_view_digest`（需计算）、`material_source_refs`（需计算）。
- **影响**: Implementation agent 在 S1 中需要设计构造函数逻辑，可能选择不同的 digest/source_refs 计算方式，导致 proactive/reactive caller 产生不可比较的 snapshots。
- **建议改法和验证点**: 在 §5.2 添加 `compact_pipeline_source_snapshot_from_pre_dispatch_view(...)` 的函数签名，明确 `material_view_digest` 的计算来源（建议 `selected_material_view_digest(material_view.material_blocks)` 或等价的已有函数）。验证 `material_view_digest` 对同一 material 的 proactive 和 reactive snapshot 相等。
- **修复风险（低）**: 新增一个函数签名。
- **严重程度（中）**: snapshot 构造是 shared pipeline 的正确性前提。

### N2-未修复-低-`policy_digest` 参数语义在 proactive/reactive wiring 中不一致

- **位置**: §5.2 `build_normal_compact_request_plan(...)` 签名 vs §6.1/6.2 wiring
- **问题类型**: 不可直接实施
- **当前写法**: §5.2 的函数签名要求 `policy_digest: str` 参数。§6.1 proactive caller 传 `policy_digest=estimate.estimator_digest`；§6.2 reactive caller 传 `policy_digest=source_snapshot.material_view_digest`。
- **反例/失败场景**: `estimate.estimator_digest`（来自 budget estimate 的 estimator）和 `source_snapshot.material_view_digest`（来自 material view 的 digest）算的是不同东西。如果 `policy_digest` 最终写入 `CompactSegmentSelection.policy_digest`，那么 proactive 和 reactive 对同一 material 会写出不同的 `policy_digest` 值。这可能导致：
  1. 同一 material 下的 proactive/reactive compact request 的 `selection_digest` 不同。
  2. Audit/trace 无法关联 proactive 和 reactive 的同一 compact attempt。
- **为什么有问题**: `policy_digest` 的语义应该是 "决定本次 selection 的 policy snapshot 的 digest"，不是 "material view 的 digest" 或 "estimator 的 digest"。两个 caller 传了不同来源的值，说明函数签名没有清晰定义参数语义。
- **直接证据**:
  - §6.1: `policy_digest=estimate.estimator_digest`
  - §6.2: `policy_digest=source_snapshot.material_view_digest`
  - 当前的 `select_compact_segment(...)` (compact_material.py:885+) 接受 `policy_digest` 并写入 `CompactSegmentSelection.policy_digest`。
- **影响**: 如果两个 caller 对同一 material view 产出的 `selection_digest` 不同，proactive/reactive compact request 的审计可追溯性受损。
- **建议改法和验证点**: 明确 `policy_digest` 的语义：(a) 它应是 policy 配置本身的 digest（如 `sha256_digest_json(policy.to_payload())`），不应是 estimate 或 material view 的 digest；(b) proactive 和 reactive 对相同 policy 应传相同值。或统一让函数内部从 `source_snapshot` 派生，不暴露为参数。
- **修复风险（低）**: 语义澄清。
- **严重程度（低）**: 不影响 compact 行为正确性，仅影响 audit consistency。

### N3-未修复-低-`CompactPipelineFallbackSelectedMaterialHandoff` 在 wiring pseudocode 中未被消费

- **位置**: §5.1 dataclass definition vs §6.3/6.4 wiring
- **问题类型**: 不可直接实施
- **当前写法**: §5.1 定义了 `CompactPipelineFallbackSelectedMaterialHandoff` 含 8 个字段。§6.4 说 "是测试和 provider 校验用的 focused handoff，不进入 ordinary branch。" 但 §6.3 的 fallback branch pseudocode 仍消费 `ActiveRecentWindowFallback` 和 `fallback.material_blocks`，不消费此 handoff。
- **反例/失败场景**: Implementation agent 在 S2c 看到 handoff 定义，但 wiring pseudocode 中只用于 "测试和校验"，不进入 production rendering 路径。如果 handoff 只在测试中构造而 production fallback 继续用 `ActiveRecentWindowFallback`，那 handoff 就不是真正的 shared path — 它只是测试辅助类型。
- **为什么有问题**: Plan 定义了 handoff 但没说明它如何在 production 路径中被 produce。`build_fallback_decision_input(...)` 的返回值包含 `selected_material_blocks` 和 `failed_payload_input.fallback_input_digest`，部分字段与 handoff 重叠。如果 handoff 只是从 `FallbackDecisionInput` 提取字段的 view，应在 plan 中说明关系。
- **直接证据**:
  - §5.1: `CompactPipelineFallbackSelectedMaterialHandoff` 8 字段定义。
  - §6.4: "不进入 ordinary branch"。
  - §6.3 fallback branch: "仍消费 ActiveRecentWindowFallback 和 fallback material blocks"。
  - §5.2 `build_fallback_decision_input(...)` 返回值不包含此 handoff。
- **影响**: Implementation agent 可能困惑 handoff 的 production 用途，可能在 S2c 时把它实现成测试专用的 dead code 类型。
- **建议改法和验证点**: 在 §6.4 补充：(a) handoff 是否由 `build_fallback_decision_input(...)` 内部构造并作为其返回值的一部分；(b) 或 handoff 是否只在 `test_compact_pipeline.py` 中使用，为其添加 `@visible_for_testing` 注释；(c) 或删除 handoff 定义，直接使用 `FallbackDecisionInput` 的现有字段。
- **修复风险（低）**: 澄清或简化类型。
- **严重程度（低）**: 不导致 production bug，但可能留下 dead type。

### N4-未修复-低-`build_tier_recovery_request_plans` 内部依赖 `build_compact_material_pack` 未在允许依赖中列出

- **位置**: §5.2 `build_tier_recovery_request_plans(...)` 签名 vs §5.1 allowed imports
- **问题类型**: 契约缺失
- **当前写法**: §5.2 说 `build_tier_recovery_request_plans(...)` "只构造 tier 1/2/3 request plans，不调用 compactor。"但 tier 1 使用不同 `selected_segment`（fallback caps），tier 2 使用 degraded `previous_compacted_view`，tier 3 使用 empty `previous_compacted_view`。三种 tier 都需要调用 `build_compact_material_pack(...)` 产生新的 `material_pack`，然后构造 `CompactionRequest`。
- **反例/失败场景**: 如果 `build_tier_recovery_request_plans` 内部调用 `build_compact_material_pack(...)`，这需要 import `compact_material.py`（§5.1 允许："可以 import compact_material.py"）。但当前的 `_proactive_compaction_recovery_request(...)` (dispatch.py:1570-1620) 和 reactive 无对等实现都各自调用了 `build_compact_material_pack(...)` + `CompactionRequest(...)` 构造。如果 `build_tier_recovery_request_plans` 不包含这些调用，它只返回配置参数而非完整 request plans，caller 仍需自己做 material pack 和 request 构造，达不到 "替代 proactive/_proactive_compaction_recovery_attempts" 的目标。
- **为什么有问题**: Plan 函数签名返回 `tuple[CompactPipelineRecoveryRequestPlan, ...]` 其中 `CompactPipelineRecoveryRequestPlan` 包含 `request_plan: CompactPipelineRequestPlan`，而 `CompactPipelineRequestPlan` 包含 `request: CompactionRequest`。也就是说每个 recovery plan 需要包含完整构造的 `CompactionRequest`。要构造 `CompactionRequest`，函数必须内部调用 `build_compact_material_pack(...)`。Plan 允许 import `compact_material.py` 所以技术上可行，但函数签名没有体现 `build_compact_material_pack` 的依赖。
- **直接证据**:
  - §5.2: `build_tier_recovery_request_plans(source_snapshot=..., root_request_plan=..., memory_policy=...) -> tuple[CompactPipelineRecoveryRequestPlan, ...]`
  - `CompactPipelineRecoveryRequestPlan.request_plan.request: CompactionRequest` 需要 `material_pack` field。
  - `dispatch.py:1585-1593` 的 recovery request 构造调用 `build_compact_material_pack(...)`。
- **影响**: Implementation agent 在 S1 可能设计一个不完整的 `build_tier_recovery_request_plans`（只返回 config dict 而非完整 requests），导致 S2a wiring 时集成失败。
- **建议改法和验证点**: 在 §5.2 的 `build_tier_recovery_request_plans` docstring 中明确它调用 `build_compact_material_pack(...)` 构造 material pack，或确认当前 allowed import 已覆盖 `compact_material.py` → `build_compact_material_pack`。
- **修复风险（低）**: 补充 docstring。
- **严重程度（低）**: 如果 implementation agent 参考了 dispatch.py 的现有 recovery attempt 构造逻辑，自然会做对。
