## Findings

### 1-未修复-中-`_normalize_upload_request` 对 `form_type=None`/空白的处置未钉死，实现 Agent 将被迫自设必填规则

- **位置**：`唯一 owner 与数据流` 第 2 条（请求入口）；`最小实施切片与精确白名单` 第 2 条；`验证与验收` 第 1/5 条测试；goal `边界、依赖与停止条件`（"form 必填/空白 typed usage 由 O05"）。
- **问题类型**：契约缺失 / open question 未收敛 / 不可直接实施（含目标漂移风险）。
- **当前写法**：plan 要求 `_normalize_upload_request` 在 material 分支"调用同一函数，生成 `replace(request, form_type=canonical)`"，函数签名为 `normalize_material_form_type(form_type: str) -> str`；同时声明"空白输入的拒绝与 O05 共享这个边界"与"缺失/空白的 typed usage 由其请求准入 owner 负责，本项复用其结果，不制造第二套错误规则"。
- **反例/失败场景**：`FinsUploadMaterialRequest.form_type` 类型是 `str | None`（`ingestion_runtime.py:1567`，默认 `None`，CLI `--forms` 可省略）。对 `None` 不存在可 `replace` 的 canonical str：
  1. 若实现无条件把 `None` 当空白拒绝，则本项在 request admission 实施了 O05-F01 的"form 必填校验移至请求输入边界"（`upload-material-um-o01-o06-oracle-adjudication.md:99`），并改变 legacy job 的耐久语义——`start_upload` 在 `_create_queued_record_with_start_lock`（`ingestion_runtime.py:4696`）之前抛错，而不是留下 durable failed job；这正是 plan 自己禁止的"第二套错误规则"。
  2. 若实现仅在 `form_type is not None` 时替换、`None` 透传，则空白 `" "` 在 admission 被函数拒绝、`None` 却继续穿透到 `service_runtime._run_material_upload:223-224`（"material 上传必须提供 form_type"）或 `build_material_ids:1845`，同一 unit 内出现两种失败面，plan 与 slice 5 测试均未描述该分叉。
- **为什么有问题**：goal 把"form 必填/空白 typed usage"划给 O05，plan 又要求本项函数拒绝空白并在 admission 调用它；三者对"谁在本 unit 内拒绝 None/空白、以什么错误面拒绝"没有唯一答案，implementation gate 只能自行发明，随后与 O05 合并时极易产生两套规则或行为回退。
- **直接证据**：`ingestion_runtime.py:1567`（`form_type: str | None = None`）；`ingestion_runtime.py:7710-7713`（现仅归一化 action）；`service_runtime.py:223-224`（runner 处拒绝 None）；`docling_upload_service.py:442-443`、`:1845-1846`（prepare/build 处拒绝空白）；goal 边界节原文"form 必填/空白 typed usage 由 O05"；plan 原文"生成 replace(request, form_type=canonical)"。
- **影响**：实施 Agent 跑偏（自设必填规则）/ 生成与 O05 冲突的错误投影 / legacy job 耐久行为被静默改变而无测试锁定 / review 不可验收。
- **建议改法和验证点**：在 plan 中钉死三条契约再进实现——(1) `normalize_material_form_type` 只接受非空 `str`，空白输入 `ValueError`（与 `build_material_ids` 现行为同一边界，O05 后续只做 typed usage 包装）；(2) `_normalize_upload_request` 仅当 `form_type is not None` 时替换，`None` 保持缺失、留给 O05 的准入 owner，禁止在本项把 None 提前判为 usage error；(3) slice 5 测试显式断言 `None` 透传后各入口失败面不变、空白输入在 admission 被拒绝且零 durable 副作用。
- **修复风险（低/中/高）**：低（计划层三句话 + 两个测试用例）。
- **严重程度（低/中/高/严重）**：中。

### 2-未修复-低-真实 CLI 配对验收缺裁决补跑清单中的"跨命令读取一致"

- **位置**：`验证与验收` 第 3 条（CLI 两次配对）；对照 O17 裁决"待补跑与 scenario 处置"。
- **问题类型**：测试缺口。
- **当前写法**：CLI 配对记录 exact argv、退出码、双流、start/terminal 事件、`meta.json`、`material_manifest.json`、文件树差异，并断言所有存在 form 字段的事件/summary/meta/manifest 为 `MATERIAL_OTHER`。
- **反例/失败场景**：write 侧同源正确，但读回链路（如 `read_runtime_helpers._resolve_document_type` 的 material form 映射、processed 列表的 `summary.form_type != query.form_type` 精确匹配 `_fs_source_document_core.py:1086`）把新数据投影成别的可见值时，配对全绿而用户跨命令读取仍不一致；closeout 若按裁决清单验收将被打回。
- **为什么有问题**：goal 声明"本 goal 沿用裁决"，裁决待补跑明确要求补跑后核对"canonical 身份、meta/manifest、事件/summary**及跨命令读取一致**"；plan 的验收集是该清单的真子集，少一项。
- **直接证据**：`upload-material-um-o17-oracle-adjudication.md`（待补跑节原文含"跨命令读取一致"）；plan 验证第 3 条无读回命令；`read_runtime_helpers.py:150-163`（material form→document_type 映射与别名表）。
- **影响**：review 不可验收 / closeout 返工补跑。
- **建议改法和验证点**：CLI 配对在 A/B 各加一步只读命令（list/read 类）核对读回 form 为 `MATERIAL_OTHER` 且 document_type 映射正确；或在 plan 明确该项为 residual 并指定 closeout 跟踪点。
- **修复风险（低/中/高）**：低。
- **严重程度（低/中/高/严重）**：低。
