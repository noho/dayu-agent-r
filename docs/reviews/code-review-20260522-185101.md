## Findings

### 1-未修复-低-`_safe_read_error_body_bytes` docstring 声称"有界文本"但实现无 size bound

- **入口/函数**: `AsyncOpenAIRunner._safe_read_error_body_bytes`
- **文件(行号)**: `dayu/engine/runners/openai/runner.py:895-909`
- **输入场景**: `response.text()` 因 `UnicodeDecodeError` 失败后进入该 fallback 路径；此时调用 `response.read()` 无限制读取整个响应体。
- **实际分支**: `response.read()` 不做分块读取或上限截断。
- **预期行为**: docstring 承诺"有界文本"，应施加合理的字节上限（如 64 KiB）。
- **实际行为**: 无界 `read()` 可能导致恶意或异常大响应体耗尽内存，且 docstring 与实现不一致。
- **直接证据**: 第 906 行 `body = await await_or_cancel(response.read(), token=self._token)` 无 max_size 或分块限制；第 909 行 `body.decode("utf-8", errors="replace")` 直接对整个 body 解码。
- **影响**: 极端场景下内存耗尽；实际风险很低（错误体通常 < 1KB），但 docstring 误导。
- **建议改法和验证点**: 在 `response.read()` 上增加 `_READ_ERROR_BODY_MAX_BYTES = 65536` 上限，或改为分块读取并在超过阈值后截断；更新 docstring 移除"有界"或明确标注上限值。
- **修复风险（低）**: 仅影响错误路径，不会改变正常流。
- **严重程度（低）**:

### 2-未修复-低-`_safe_log_message` 中 "token" marker 可能过度脱敏 CONTEXT_LENGTH_EXCEEDED 消息

- **入口/函数**: `_AsyncAgent._classify_runner_event` → `_safe_log_message`
- **文件(行号)**: `dayu/engine/agent.py:180-189`（`_SENSITIVE_EXCEPTION_MARKERS` 定义含 "token"）、`:243`（`_safe_log_message` 中 `any(marker in lowered_message ...)`）、`:1275`（调用点）
- **输入场景**: provider 返回 context overflow 错误，消息体包含 "maximum context length is 8192 tokens" 等含 "token" 词语的常规描述。
- **实际分支**: `_safe_log_message` 检测到 "token" marker → 返回 `_EXCEPTION_MESSAGE_REDACTED`。
- **预期行为**: provider 错误消息中 "token" 作为上下文窗口描述词不应触发全量脱敏；脱敏应仅针对 secret/token 值。
- **实际行为**: 整条 provider 消息被替换为 `"exception message redacted"`，丢失了 provider 返回的精确失败描述。
- **直接证据**: `_SENSITIVE_EXCEPTION_MARKERS` 元组（`:180-189`）包含裸字符串 `"token"`；`_safe_log_message` 的 `:243` 行 `any(marker in lowered_message for marker in _SENSITIVE_EXCEPTION_MARKERS)` 不区分 "token" 是安全描述词还是敏感值。
- **影响**: 仅丢失日志诊断细节；`error_code` 与 `http_status` 仍被日志记录，可定位到 context overflow 类别。实际影响低。
- **建议改法和验证点**: 将 `_SENSITIVE_EXCEPTION_MARKERS` 中的 "token" 改为更精确的匹配（如正则 `token[=:]\s*[A-Za-z0-9]`），或在 `_safe_log_message` 调用处使用不同的 marker 集合。也可将 `_safe_log_message` 与 `_SENSITIVE_EXCEPTION_MARKERS` 解耦，定义更窄的日志专用脱敏集合。
- **修复风险（低）**: 仅影响日志输出，不改变任何行为路径。

## Residual Risk

- Engine 层移除 inline 64KB guard 后，从 oversized tool result → provider context overflow → `CONTEXT_COMPACTION_REQUESTED` → Host compaction 的端到端路径缺少引擎级集成测试。当前 Engine 测试 (`test_agent_phase3_tool_call.py`) 使用 mock runner 返回 `FINAL_ANSWER`，不触发 `RunnerHTTPErrorData(CONTEXT_LENGTH_EXCEEDED)` 分支；该分支的正确性仅通过 Runner 层 (`test_http_error_event.py`、`test_context_overflow`) 间接保证。建议后续补充 Engine 层 mock runner 返回 `CONTEXT_LENGTH_EXCEEDED` 并验证 `CONTEXT_COMPACTION_REQUESTED` 事件的测试。
- `_exception_diagnostic_suffix` (`compaction_operation.py:253-263`) 将 `str(exc)` 原样写入 `diagnostic_refs` — 该 refs 进入 `CompactionOperationResult.rejected_attempts` 并由 Host context governance 调用方持久化。本次改动新增的 `_log_rejected_attempt` 在日志层做了脱敏，但 durable payload 侧的诊断 refs 仍未经脱敏。这是 pre-existing 问题，本次未改善也未劣化；若 compactor proposal 异常消息中包含 API key 类敏感信息，可能写入 durable state。
- `run_read` 新增的 busy retry 使用同步 `time.sleep`；所有 `run_read` 调用方均为 Host 内部同步方法（`command.py`、`read_api.py`、`dispatch.py`、`run_input.py`、`wait_adapter.py`），若从 async 事件循环线程调用且 retry 触发，会短暂阻塞事件循环。SQLite WAL 模式下读事务 busy 极少见，实际阻塞风险很低；与已有 `run_write` 的 `time.sleep` 风险一致。
- `docs/host/runtime-defaults-audit.md` 标记 `_TOOL_RESULT_SIZE_LOG_THRESHOLD_BYTES = 65536` 建议归属 Host diagnostic/log policy。该阈值在本次改动中从治理阈值降级为纯日志触发阈值，审计文档已正确反映，但阈值值（65536）与 legacy 的 64KB payload inline threshold 相同，未来可调整。
