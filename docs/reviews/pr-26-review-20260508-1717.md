## Findings

### Finding 1 — P0：Memory observer `process()` sink 失败导致 `_pending_by_run` 状态不可恢复 [已修复]

**文件**: `dayu/host/_memory_projection.py:85-97`

**问题**: `process()` 在调用 sink (`_run_async(memory_store.project_run_events(...))`) **之前**先执行 `self._pending_by_run.pop(event.run_id)`。若 sink 抛出异常（被 `_run_once_locked` 捕获为 `RETRYABLE_FAILED` 或 `BLOCKED_FAILED`），以下后果发生：

1. `_pending_by_run` 中该 run 的累积事件已被 pop 丢失。
2. checkpoint 未前进，下次 drain 会重放同一批事件。
3. 重放时 terminal 事件再次到达 `process()`，但 `_pending_by_run[run_id]` 已空，`tuple([])` 投影到 memory store 的是空事件集。
4. 用户输入与 assistant 回答永久丢失在 memory read model 中。

这是一个破坏 at-least-once 投影语义的正确性 bug：observer 内部状态先于 sink 成功被修改，违反了 "checkpoint 前进之前 observer 状态可重放" 的不变量。

**后果**: 若 `memory_store.project_run_events` 在 drain 期间失败（当前内存实现不太可能，但未来 durable memory store 或有 IO 异常），memory read model 将永久丢失该 run 的用户输入。

**建议修复**: 在 sink 调用成功之前不要 pop；改为先收集待投影事件、调用 sink、成功后再 pop。或改为先深拷贝 events 再投影，失败时保留 `_pending_by_run` 不变：

```python
if event.type in TERMINAL_RUN_EVENT_TYPES:
    pending = self._pending_by_run.get(event.run_id)
    if pending is not None:
        events = tuple(pending)
        _run_async(self.memory_store.project_run_events(events))
        # sink 成功后才清除
        del self._pending_by_run[event.run_id]
```

### Finding 2 — P1：进程崩溃后 read model 无法自动恢复 [已修复]

**文件**: `dayu/host/_memory_projection.py:99-120`、`dayu/host/_run_harness.py:1006-1028`

**问题**: `MemoryProjectionObserver.rebuild_from_events()` 已实现全量 rebuild 逻辑，但整个 P6 代码路径中没有任何调用点。当前的 read model 推进依赖 `_project_terminal_run` 在 `_run_to_store` 的 `finally` 块中调用 `coordinator.drain()`。

若进程在 terminal event 持久化成功之后、`coordinator.drain()` 执行之前崩溃：
- EventLog 中已有完整的 terminal event 与 RunResult snapshot。
- memory / timeline / audit read model 均为空或不完整。
- 重启后 `build_durable_harness` 不会调用 `rebuild_from_events`，read model 永久落后。

**后果**: required memory projection 的 "用户输入永不丢失" 承诺在进程崩溃场景下不成立。

**建议修复**: 在 `build_durable_harness` 或 `ProjectionCoordinator.initialize` 中增加 startup reconcile 路径：检查 observer lag > 0 时触发 `drain()` 补齐。由于 `rebuild_from_events` 已存在，只需在 startup 时调用 `coordinator.drain()` 即可自动补齐。

### Finding 3 — P2：`_run_async` sync-async bridge 在 observer 链中引入不必要的线程开销 [后移-P7/P8]

**文件**: `dayu/host/_memory_projection.py:123-170`

**问题**: `MemoryProjectionObserver.process()` 是同步方法，但需要调用 `memory_store.project_run_events`（async 协程）。`_run_async` 通过两种路径桥接：

1. 无 running loop：创建临时 `new_event_loop` 并 `run_until_complete`。
2. 有 running loop（正常路径）：启动新线程 → 新 event loop → `run_until_complete`。

每次 drain 中每个 terminal event 都会触发一次 `threading.Thread` 创建和销毁。这是非平凡的开销，且引入了线程同步复杂度（`error_box` 列表跨线程传递异常）。

**根因**: `ObserverSink.process` 协议是同步的，但 `ConversationMemoryStore.project_run_events` 是 async 的。这个 impedance mismatch 由 `_run_async` 弥合。

**后果**: 当前不影响正确性（测试通过），但增加了复杂度和运行时开销。未来如果 memory store 需要访问 caller event loop 状态（如共享 cache），线程隔离会导致问题。

**建议**: 考虑将 `ObserverSink.process` 改为 async 协议，或提供同步版本的 `ConversationMemoryStore` 接口供 observer 使用。当前可接受为 P6 的临时方案，但应在 P7/P8 中重新评估。

### Finding 4 — P2：多个模块通过 `storage._connection` 访问 HostStorage 内部实现 [已修复]

**文件**:
- `dayu/host/_durable_event_store.py:471` (`ensure_host_schema`)
- `dayu/host/_durable_event_store.py:1089-1090` (`_configure_row_factory`)

**问题**: `ensure_host_schema` 和 `_configure_row_factory` 直接访问 `storage._connection` 并用 `noqa: SLF001` 抑制 lint 警告。HostStorage 的 `_connection` 是 `init=False` 的内部字段，不属于稳定接口。

**后果**: 若 HostStorage 内部重构连接管理（如连接池、多连接），这些直接访问点都会断裂，且 `noqa` 抑制会掩盖类型检查器的警告。

**建议修复**: 为 HostStorage 增加公共方法如 `apply_schema(statements)` 和 `configure_row_factory()`，让 store 模块通过公共接口操作，消除 `_connection` 直接访问。

### Finding 5 — P3：`_run_event_serializer.py` 1290 行 isinstance chain 维护成本高 [后移-P7]

**文件**: `dayu/host/_run_event_serializer.py`

**问题**: `_encode_fields` 和 `_decode_fields` 各包含约 25 个 isinstance 分支，覆盖所有 `RunEventData` 变体。每新增一个事件类型需要同时修改：
1. `_DATA_CLASS_BY_TYPE` 映射
2. `_encode_fields` 中的 isinstance 分支
3. `_decode_fields` 中的 type_name 分支

三个修改点分散在文件不同位置，漏改任何一个都会导致运行时 ValueError。

**后果**: 不影响当前正确性（封闭映射 + 测试覆盖），但增加后续维护出错概率。每新增一个 RunEventType 都需要同步修改 3 处。

**建议**: 可考虑用注册表 + 自动字段提取（dataclasses.fields）减少样板代码。当前作为 P6 可接受，但应在 P7 新增事件类型时优先重构。

### Finding 6 — P3：Memory observer `process()` sink 失败的路径无测试覆盖 [已修复]

**文件**: `tests/host/`（缺失）

**问题**: 现有 P6 测试覆盖了正常 drain 路径、幂等重放、checkpoint 回退、并发 drain 等场景，但缺少以下测试：

1. `MemoryProjectionObserver.process()` 在 sink 抛异常时 `_pending_by_run` 的状态（验证 Finding 1）。
2. `ProjectionCoordinator.drain()` 中 observer `BLOCKED_FAILED` 后其余 observer 是否继续处理。
3. 进程重启后 read model 恢复路径（验证 Finding 2）。
4. `MemoryProjectionObserver` 跨 batch 累积事件后 terminal 到达的正确性。

**后果**: Finding 1 描述的状态 corruption bug 没有测试捕获。

### Finding 7 — P3：`_finish_attempt_if_durable` docstring 声称 `terminal_event` 与 `state` 二选一，但代码不校验 [已修复]

**文件**: `dayu/host/_run_harness.py:1098-1150`

**问题**: docstring 写 "state: 显式 attempt state；与 terminal_event 二选一"，但实现中 `terminal_event` 存在时会无条件覆盖 `resolved_state`（L1128: `resolved_state = _attempt_state_from_terminal(terminal_event)`）。同时传入两者时 `state` 被静默忽略，不会报错。

**后果**: 当前调用方均正确使用，不会同时传入。但违反最小惊讶原则，未来调用方可能误用。

**建议**: 增加 `if terminal_event is not None and state is not None: raise ValueError` 校验，或在 docstring 中明确说明优先级。
