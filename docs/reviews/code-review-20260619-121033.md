## Findings

### 1-未修复-中-`_print_round()` 与 `_print_session_observation()` 缺少 `flush=True`，与 compact audit 打印不一致

- **入口/函数**: `_print_round()` 行 3015-3033，`_print_session_observation()` 行 3036-3051，`_print_assembly_diagnostics()` 行 2926-2970
- **文件(行号)**: `utils/smoke_host_public_conversation_memory_scenarios.py:3015-3051`
- **输入场景**: 长轮次 smoke（`--suite memory-compact --long-rounds 25`）运行时，多轮 `_print_round` 和 `_print_session_observation` 的 stdout 输出在 Python 默认行缓冲策略下可能不立即刷出
- **实际分支**: `_print_round` 中 `print(f"{_STDOUT_PREFIX_ROUND_DONE} ...")` 和 `print(f"{_STDOUT_PREFIX_FINAL_PREVIEW} ...")` 均无 `flush=True`；`_print_session_observation` 同样无 `flush`
- **预期行为**: 所有 stdout 诊断行应使用 `flush=True`，确保在长时间运行的 smoke 中观察者能实时看到每轮状态，且异常退出时缓冲区内容不丢失
- **实际行为**: compact audit 路径（`_print_compact_audit_summary`、`_print_compact_operation`、`_print_compact_histogram`、`_print_compact_reject_detail`）全部使用了 `flush=True`，但轮次级打印和 assembly 诊断未使用。若 `_assert_round_result` 在 `_print_round` 之后抛出异常（行 2092-2098），`ROUND_DONE` 和 `FINAL_PREVIEW` 可能仍在缓冲区中未被刷出，降低故障定位效率
- **直接证据**: `run_smoke` 主循环行 2091 调用 `_print_round(result)`（无 flush），行 2092-2098 `_assert_round_result` 可能 `raise RuntimeError`；异常沿 `main()` 的 `except Exception` 路径输出到 stderr 并 `flush=True`（行 4075），但 stdout 缓冲区中的轮次摘要已丢失。对比 follow-up doc 行 75-76 明确要求"failure、audit、tool summary 都独立换行并 flush"
- **影响**: 长轮次 smoke 异常退出时，stdout 可能缺失触发失败轮次的 `ROUND_DONE` 和 `FINAL_PREVIEW` 输出，排障效率下降
- **建议改法和验证点**: 在 `_print_round()` 的两处 `print` 添加 `flush=True`；在 `_print_session_observation()` 的 `print` 添加 `flush=True`；在 `_print_assembly_diagnostics()` 的关键 `print` 添加 `flush=True`（至少尾行）。验证：运行 `--suite memory-compact --long-rounds 25` 并中途 `kill` 进程，确认 `ROUND_DONE` 输出不丢失
- **修复风险（低）**: 每行 `flush=True` 仅增加 syscall 开销，对 smoke 工具可忽略
- **严重程度（中）**: 属于故障时可观测性缺口，不影响正确性判定逻辑；但 follow-up doc 明确要求修复 stdout 粘连，当前修复只覆盖了 compact audit 路径而未覆盖轮次打印路径

### 2-未修复-低-`_compact_payload_int()` 对 JSON 浮点数静默返回 None，缺少文档说明

- **入口/函数**: `_compact_payload_int()` 行 3880-3892
- **文件(行号)**: `utils/smoke_host_public_conversation_memory_scenarios.py:3880-3892`
- **输入场景**: EventLog payload 中 `attempt_number` 或 `budget_after_attempted_compact` 为 JSON 浮点数（例如 `1.0` 或 `1e3`），这在 JSON 规范中合法但 Python `json.loads` 会解析为 `float`
- **实际分支**: `isinstance(value, int) and not isinstance(value, bool)` 对 `float` 返回 `False`，进入 `return None`
- **预期行为**: 返回 `None` 并让上游以 `<none>` 打印是合理的防御策略，但函数 docstring 未说明浮点数会被静默拒绝
- **实际行为**: 返回 `None`，上游 `_compact_optional_text` 渲染为 `<none>`，不报错
- **直接证据**: 行 3889-3892 的类型守卫设计正确（拒绝 `bool` 子类、拒绝 `float`），但 docstring 行 3884-3885 只说了"字段缺失或类型不匹配时返回 None"，未提浮点数这一具体场景
- **影响**: 若 production 代码未来以浮点数写入 payload 字段，smoke audit 会静默丢失该字段值而不报警。当前 production 不会写入浮点数 `attempt_number`，风险极低
- **建议改法和验证点**: 在 docstring 补充"JSON 浮点数会被视为类型不匹配并返回 None"；可选在 DEBUG 模式下对非预期类型打印 warning。验证：现有测试 `test_compact_audit_report_handles_empty_missing_and_malformed_payloads` 已覆盖字符串代替整数的场景
- **修复风险（低）**: 纯文档补充
- **严重程度（低）**: 行为正确，仅文档不完整

### 3-未修复-低-`_print_compact_operation()` 不输出 per-operation 的 failure_categories 与 diagnostic_histogram

- **入口/函数**: `_print_compact_operation()` 行 3105-3136
- **文件(行号)**: `utils/smoke_host_public_conversation_memory_scenarios.py:3105-3136`
- **输入场景**: 一个 compact operation 有多个 rejected attempts 且 failure categories 分布多样
- **实际分支**: `_print_compact_operation` 只输出 timeline（seq、counts、final status），不输出 `operation.failure_categories` 和 `operation.diagnostic_histogram`
- **预期行为**: 按 follow-up doc 行 57-70 的设计目标，per-operation timeline 应与 attempt reject histogram 分层输出。当前设计是 per-operation timeline + 全局 histogram，per-operation histogram 存在于 dataclass 中但未渲染到 stdout
- **实际行为**: per-operation 的 `failure_categories` 和 `diagnostic_histogram` 仅在 `_compact_audit_report_from_rows` 中用于聚合全局 histogram，不单独打印
- **直接证据**: `_print_compact_operation` 行 3116-3136 的 print 语句不包含 `failure_categories` 和 `diagnostic_histogram` 字段；但 `CompactOperationAudit` dataclass 行 729-730 定义了这两个字段并通过 `_compact_operation_audit` 正确填充
- **影响**: 当多个 operation 有不同的 failure pattern 时，全局 histogram 会混合所有 operation，无法区分哪个 operation 的哪类 failure 占比更高。需回到 EventLog 才能拆分。对于 smoke 快速诊断场景，全局 histogram 通常足够
- **建议改法和验证点**: 可选在 `_print_compact_operation` 末尾追加 `failure_categories` 摘要行（如 `failure_categories=invalid_candidate:2,source_boundary:1`），但当前设计合理，建议作为 deferred enhancement。验证：现有测试 `test_compact_audit_report_prints_operation_histograms_and_manifest_stage` 确认了全局 histogram 的正确性
- **修复风险（低）**: 仅影响 stdout 信息密度，不影响验收逻辑
- **严重程度（低）**: 设计权衡，非缺陷

### 4-未修复-低-`_compact_artifact_files()` 使用 `rglob("*")` 无深度限制

- **入口/函数**: `_compact_artifact_files()` 行 4027-4038
- **文件(行号)**: `utils/smoke_host_public_conversation_memory_scenarios.py:4027-4038`
- **输入场景**: compact artifact root 目录下存在非常深的嵌套子目录或大量非 compact 文件
- **实际分支**: `compact_root.rglob("*")` 递归遍历所有子目录，无深度限制

- **建议改法和验证点**: 可改为 `compact_root.glob("*.json")`（非递归）或添加文件数上限。但当前实现与 compact artifact 的预期目录结构匹配，改动优先级低
- **修复风险（低）**
- **严重程度（低）**

## Residual Risk

- **未测试 I/O 边界**: `_compact_audit_report()` 依赖 `open_host_durable_store()` 和 `EventLogStore` 的真实 I/O，纯函数测试不覆盖 durable store 打开失败、事务失败、pagination 中断等场景。这些由集成 smoke 运行覆盖。
- **per-operation histogram 不独立打印**: 当多个 compact operation 有不同的 failure 模式时，全局 histogram 混合后可能模糊 per-operation 特征。当前设计依赖全局 histogram 做快速诊断，如需 per-operation 细分需回 EventLog。对日常诊断足够，对深度调查需额外工具。
- **`_print_round` 无 flush 的故障丢失**: Finding 1 描述的场景（`_assert_round_result` 异常时 `ROUND_DONE` 仍在缓冲区）在长轮次 smoke 中确实可能发生。但 smoke 异常退出时会输出 `SMOKE FAIL` 到 stderr（已 flush），配合 DEBUG 日志通常足以定位问题轮次。
- **smoke 不验证 conversation memory correctness**: README 已明确声明"当前 smoke 不覆盖 conversation memory correctness 的全量验证"，这是有意的 coverage boundary。issue 80 的全量 eval 目标应由独立的 eval/regression suite 覆盖，不应塞入日常 smoke。
