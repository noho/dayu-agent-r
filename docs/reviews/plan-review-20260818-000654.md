## Findings

### 001-未修复-中-derive_report_kind 的 None 处理未明确

- **位置**: Slice S1, "Exact allowed changes" 第 4-5 点
- **问题类型**: 契约缺失
- **当前写法**: plan 说"derive_report_kind 直接调用 normalize_fiscal_period，对 None 显式视为 invariant failure"
- **反例/失败场景**: `normalize_fiscal_period` 返回 `Optional[FiscalPeriod]`（None 输入返回 None）。`derive_report_kind` 当前签名是 `(fiscal_period: str) -> str`，不接受 None。如果实现者简单改为调用 `normalize_fiscal_period` 而不处理 None 返回值，会导致 `derive_report_kind` 在合法 None 输入时返回 None 而非报错，破坏下游 `report_kind` 字段的非空契约。
- **为什么有问题**: `derive_report_kind` 被 `cn_pipeline.py:860` 和 `sec_upload_workflow.py:229` 调用，返回值直接写入 `report_kind` metadata 字段。该字段在 `describe_prepared_filing_publication` 中被 `_require_prepared_filing_meta_text` 要求为非空字符串。None 泄漏会导致 publication 阶段 ValueError，而非 admission 阶段的清晰 usage error。
- **直接证据**:
  - `dayu/fins/domain/filing_semantics.py:293-314`: `normalize_fiscal_period` 返回 `Optional[FiscalPeriod]`，None 输入返回 None
  - `dayu/fins/pipelines/docling_upload_service.py:2008-2026`: `derive_report_kind` 当前调用 `normalize_cn_fiscal_period`（返回 `str`，不返回 None）
  - `dayu/fins/pipelines/docling_upload_service.py:1246`: `_require_prepared_filing_meta_text` 要求非空字符串
- **影响**: 实现者可能写出编译通过但运行时泄漏 None 的代码，导致 publication 阶段 ValueError 而非 admission 阶段 usage error
- **建议改法和验证点**: plan 应明确 `derive_report_kind` 的实现策略：要么先调用 `normalize_fiscal_period` 并在 None 时 raise `ValueError("fiscal_period 不能为空")`，要么保持签名 `(fiscal_period: str) -> str` 并在内部调用 `normalize_fiscal_period` 后 assert 非 None。测试应覆盖 None 输入抛出异常。
- **修复风险**: 低
- **严重程度**: 中

### 002-未修复-低-type 收窄对下游 pipeline 的影响未评估

- **位置**: Slice S1, "Exact allowed changes" 第 3 点
- **问题类型**: 过度耦合 / 契约缺失
- **当前写法**: plan 说"将两个 normalized_fiscal_period 字段标注为 FiscalPeriod"
- **反例/失败场景**: `cn_pipeline.py:816` 和 `sec_upload_workflow.py:185` 将 `normalized_fiscal_period` 赋值给局部变量 `normalized_period`，随后用作 `form_type` 和传给 `build_cn_filing_ids`/`build_sec_filing_ids`。这些函数签名接受 `str`。虽然 `FiscalPeriod` 是 `str` 的子类型（`Literal[...]`），pyright 不会报错，但 plan 没有评估是否需要同步收窄这些下游函数的签名。
- **为什么有问题**: 如果不收窄下游签名，类型收窄只在 admission 边界有意义，下游仍接受任意 `str`。这不会导致运行时错误，但会让类型系统的保护半途而废。
- **直接证据**:
  - `dayu/fins/pipelines/docling_upload_service.py:1916-1951`: `build_cn_filing_ids` 签名 `(fiscal_period: str)`
  - `dayu/fins/pipelines/docling_upload_service.py:1954-1986`: `build_sec_filing_ids` 签名 `(fiscal_period: str)`
  - `dayu/fins/pipelines/cn_pipeline.py:816`: `normalized_period = authoritative_request.normalized_fiscal_period`
- **影响**: 类型收窄的价值被稀释，但不会导致运行时错误。属于"做了但没做完"的问题。
- **建议改法和验证点**: plan 应明确这是有意为之（只在 admission 边界收窄）还是需要同步收窄下游。如果是有意为之，应在 plan 中说明理由。
- **修复风险**: 低
- **严重程度**: 低

### 003-未修复-低-build_cn_filing_ids 仍自行 strip().upper()

- **位置**: Slice S1, Non-goals / 不在范围
- **问题类型**: 最佳实践偏离
- **当前写法**: plan 未提及 `build_cn_filing_ids` 和 `build_sec_filing_ids` 的内部 normalization
- **反例/失败场景**: `build_cn_filing_ids`（line 1944）和 `build_sec_filing_ids`（line 1979）仍然自行执行 `fiscal_period.strip().upper()`。虽然在 admission 之后调用时这是冗余的，但如果有人绕过 admission 直接调用这些函数，仍然会接受非法值（只要 strip().upper() 后是空字符串或其他值会被后续检查拒绝）。
- **为什么有问题**: 这是第二份 normalization 逻辑，虽然在当前调用链中是安全的（admission 已验证），但违反了"唯一 owner"原则的精神。
- **直接证据**:
  - `dayu/fins/pipelines/docling_upload_service.py:1944`: `normalized_period = fiscal_period.strip().upper()`
  - `dayu/fins/pipelines/docling_upload_service.py:1979`: `normalized_period = fiscal_period.strip().upper()`
- **影响**: 不会导致当前 bug，但保留了第二份 normalization 逻辑。属于 residual risk 而非 blocker。
- **建议改法和验证点**: 可以记录为 residual risk，后续 slice 统一。或者在当前 slice 中将这两个函数的 `fiscal_period` 参数改为 `FiscalPeriod` 类型，强制调用方传入已 canonical 的值。
- **修复风险**: 低
- **严重程度**: 低

### 004-未修复-中-US 分支的 else 逻辑需要显式处理

- **位置**: Slice S1, "Exact allowed changes" 第 4 点
- **问题类型**: 状态机漏洞
- **当前写法**: plan 说"static admission required/length check 后调用 normalize_fiscal_period；所有 market 共享同一分支"
- **反例/失败场景**: 当前代码（`ingestion_runtime.py:1275-1281`）有 `if normalized_ticker.market in {"CN", "HK"}:` 分支。plan 要求删除这个分支，改为统一调用 `normalize_fiscal_period`。但 plan 没有明确说明如何处理 `normalize_fiscal_period` 抛出的 `ValueError`：应该映射到哪个 usage code？
- **为什么有问题**: 当前 CN/HK 分支捕获 `ValueError` 并映射到 `UNSUPPORTED_CN_FISCAL_PERIOD`。plan 要求改为 `UNSUPPORTED_FISCAL_PERIOD`。但如果实现者只是简单删除 market 分支而没有正确映射异常，可能会导致 `ValueError` 逃逸到上层，变成 generic runtime error 而非 typed usage error。
- **直接证据**:
  - `dayu/fins/ingestion_runtime.py:1275-1281`: 当前 market 分支逻辑
  - `dayu/fins/ingestion_runtime.py:1277`: `normalized_period = normalize_cn_fiscal_period(period_text)`
  - `dayu/fins/ingestion_runtime.py:1279`: `_raise_upload_usage(FinsUploadUsageCode.UNSUPPORTED_CN_FISCAL_PERIOD)`
- **影响**: 如果实现不当，US 非法 period 可能逃逸为 runtime error，与 UF-A21 evidence 中的 bug 表现相同。
- **建议改法和验证点**: plan 应明确写出伪代码：`try: normalized_period = normalize_fiscal_period(period_text, field_name="--fiscal-period") except ValueError: _raise_upload_usage(FinsUploadUsageCode.UNSUPPORTED_FISCAL_PERIOD)`。测试应覆盖 US/CN/HK 三个市场的非法值都返回同一 usage code。
- **修复风险**: 低
- **严重程度**: 中

### 005-未修复-低-UNSUPPORTED_CN_FISCAL_PERIOD 删除的破坏面未完全评估

- **位置**: Slice S1, "Changed closed contract"

- **当前写法**: plan 说"UNSUPPORTED_CN_FISCAL_PERIOD 删除"且"不提供旧 enum 名称、旧值或旧文案的 re-export/alias/compatibility mapping"
- **反例/失败场景**: `tests/fins/test_fins_ingestion_runtime.py:1452` 断言 `FinsUploadUsageCode.UNSUPPORTED_CN_FISCAL_PERIOD` 的 message。如果删除该 enum member，该测试会立即失败。plan 提到了更新测试，但没有明确列出哪些测试需要修改。
- **为什么有问题**: 这不是 blocker（plan 确实要求更新测试），但 plan 的 "Exact allowed changes" 没有显式列出需要修改的测试断言，可能导致实现者遗漏。

- **修复风险**: 低

## Residual Risks

1. **`_normalize_optional_upload_fiscal_period` 未统一**: `docling_upload_service.py:2050` 的 `_normalize_optional_upload_fiscal_period` 仍然自行 `strip().upper()` 而不校验闭集。这是 material upload 的可选字段，plan 正确排除在范围外。分类为 `assigned to later work unit`。

2. **`build_cn_filing_ids`/`build_sec_filing_ids` 保留内部 normalization**: 如 finding 003 所述，这两个函数仍自行 `strip().upper()`。分类为 `accepted residual`，不影响当前 bug 修复。

3. **download filter aliases 仍多于 filing closed values**: `_FISCAL_PERIOD_FILTER_ALIASES` 包含中文别名（如"年报"、"半年报"），这些不是 filing upload 的 closed values。plan 正确识别这是独立 filter owner 的有意承诺。分类为 `rejected-with-reason`。

4. **旧 durable 非法 fiscal period 的兼容读取**: schema 规则要求全新设计且用户未要求升级。分类为 `assigned to later work unit`。

## Plan Review Conclusion

**pass-with-risks**

Plan 整体设计合理，正确识别了 root cause（US 分支绕过 closed set 校验）、唯一 owner（`filing_semantics.normalize_fiscal_period`）和修复边界（admission 层）。两个 slice 分离清晰：S1 负责语义 owner 统一，S2 负责入口证据和文档。

主要风险点：
1. `derive_report_kind` 的 None 处理需要明确实现策略（finding 001）
2. US 分支异常映射需要显式伪代码（finding 004）

这两个都是实现细节层面的风险，不构成结构性 blocker。plan 可以在 "Exact allowed changes" 中补充相关说明来降低风险。

无 blocking finding，plan 可进入 implementation。
