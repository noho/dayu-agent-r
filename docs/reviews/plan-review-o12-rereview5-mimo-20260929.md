## 2. Findings

### 1-未修复-[低]-durable job `failure_summary` 同源派生不变量未覆盖 `upload_runner` 不支持路径，plan 自设"均派生"承诺与实施/测试范围不闭合
- **位置**: §2 O12-PR4-F1 段（"workflow、direct RESULT、observation completion、durable job 的 `failure_summary`/`result_summary.failure` 均从同一 `FinsUploadFailureReason` 派生 `kind/code/message/retry_hint`"）与 O12-PR4-F3 段（"upload job 的 `except Exception`……调用 upload 专属 typed 终态保存路径……正常返回 summary 的既有 typed 路径保持同一投影"）；测试 3（仅断言"job 异常 catch 的 `failure_summary` 与 `result_summary.failure`"一致）。
- **问题类型**: 契约缺失 / 测试缺口。
- **当前写法**: plan 把 durable job 失败记录的 typed 双摘要收口钉在 `_run_upload_job` 的 `except Exception`（:5052）与既有正常返回路径（:5024-5028），并宣称 durable job 的 `failure_summary`/`result_summary.failure` 均从同一 reason 派生。
- **反例/失败场景**: `FinsIngestionRuntime.create` 的 `upload_runner: FinsUploadRunner | None = None` 是**文档化的受支持配置**（docstring："不传入时上传 job 会失败为不支持"；`start_upload` docstring 亦承认直接创建的 runtime 可无 runner）。该路径在 `_run_upload_job` 内走 `:4986-5001`：构造了完全符合 F3 要求形状的 typed `FinsUploadResultSummary`（含 `failure_reason=fins_upload_failure_from_exception(RuntimeError(),...)`）却经 `_save_failed(record, message=_UNSUPPORTED_UPLOAD_RUNTIME_MESSAGE, ...)` 落盘——`_save_failed`（:5902-5933）恒写 `failure_summary={"message": _UNSUPPORTED_UPLOAD_RUNTIME_MESSAGE}`，**不是** `reason.to_json()`，message 也与 reason 的 message 不同。S1 落地后该 job record 的 `failure_summary` 仍无 `kind/code/retry_hint`，plan 的"均派生"承诺为假；测试 3 只断言异常 catch，该路径不红。direct 侧同形残留（`_produce_direct_upload` :4499-4518 的 `error_message=direct_upload_runtime_unavailable_message()` 与 details 内 reason 并存）亦不在任何验收断言内。
- **为什么有问题**: durable job 失败投影的同源性是 O12-PR4-F1/F3 注册项自设的 owner 级承诺（"failure_summary/result_summary.failure 均从同一 FinsUploadFailureReason 派生"）；一个文档化可达路径不满足该承诺，gate 复审无法据 plan 文本验收"同源"，实施 Agent 亦无法判断该路径该迁移还是该保留——两种实施产生两种 durable job 可见形状。
- **直接证据**: `ingestion_runtime.py:4986-5001`（unsupported 路径 `_save_failed` + typed result_summary）、`:5902-5933`（`_save_failed` 恒 message-only failure_summary）、`:5024-5028/:5052`（plan 收口的两条路径）、`:3531-3532`（`upload_runner` 可选的文档化语义）；plan 两段原文与测试 3 原文对照。
- **影响**: 低——该路径仅在无 runner 的 runtime 配置下可达，typed 信息已在 `result_summary.failure` 兜底，无错误业务事实；但 plan 承诺与实施/验收面不闭合，属"显示正确但记录不全"的投影分叉。

### 2-未修复-[低]-selection"校验它与动作及 request 文件一致"对 delete+files 的语义未钉死，存在吸收 O16 静态拒绝或留死文本的两向分叉
- **位置**: §2 Fins material admission 段（"静态 admission 按规范化 request 的有序文件一次构造该 selection；delete 为 `for_delete()`，upsert 为 `from_upsert_paths(...)`，校验它与动作及 request 文件一致，作为 converter 的唯一文件选择真源"）；非目标（"不实施 O05、O16……任何额外缺陷记录给对应 work unit，不能吸收进本 plan"）；集成顺序（"O16 action/files 静态拒绝先于状态读"）。
- **问题类型**: 契约缺失 / 范围边界。
- **当前写法**: plan 要求 admission 构造 selection 后"校验它与动作及 request 文件一致"，但未说明当 `action=delete` 且 `request.files` 非空时该校验是拒绝、还是仅做构造自检（delete→空 selection 与 upsert→request 文件的机械一致性）。
- **反例/失败场景**: 现状 `_normalize_upload_request`（`ingestion_runtime.py:7694-7714`）不拒绝 delete+files，SEC workflow 的 `for_delete()` 分支（`sec_upload_workflow.py:486-490`）静默忽略 files——delete+files 的静态拒绝正是 O16（action/files 组合）的裁决域。若实施 Agent 把"校验一致"读成业务拒绝，O12 将抢先实施 O16 的行为（违反非目标"不能吸收进本 plan"），O16 gate 须回头裁决已被占的行为；若读成构造自检，delete+files 仍被静默忽略，则该句是死文本、gate 无验收锚点。O12 测试矩阵只用有效组合（非目标明文），两种实施都不红。
- **为什么有问题**: 语义 owner 未定：delete+files 的拒绝归属 O16，selection 的构造一致性归属 admission。plan 在同一句混写两个可能语义，与自设的"O05/O16 不吸收"边界存在张力，实施可产生两种用户可见行为。
- **直接证据**: `ingestion_runtime.py:7707-7713`（normalize 无 delete+files 检查）；`sec_upload_workflow.py:486-490`（delete 分支忽略 files）；plan §2 原文、非目标与集成顺序原文对照。
- **影响**: 低——delete+files 是边缘输入且 O12 测试不触达；主要风险是 O16 的行为被 O12 静默预占或条款空转，跨 WU gate 摩擦。
- **建议改法和验证点**: plan 一句话钉死 selection 一致性只是**构造不变量**（selection 按动作机械构造且与 request 推导结果一致，防止消费方重建漂移），delete+files 的接受/拒绝留给 O16 在其 gate 裁决；或如确要 O12 拒绝，必须写进成功信号/测试并明示这是 O16 的临时前置、O16 须核对。验证点：实施 gate 检查 admission 对 delete+files 的行为与该句一致，且 O16 plan 核对此边界。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。
