## Findings

### 1-unfixed-medium-help-projection-懒加载边界未给出实现路径

- **位置**: §5.1 "help/schema 投影只能读取轻量静态 capability，不得在参数解析/模块导入阶段加载 Docling"
- **问题类型**: 不可直接实施
- **当前写法**: plan 要求 help projection 不触发 Docling import，但未给出实现路径。Slice 1 stop condition 说"若无法在不 eager-import Docling 的前提下提供 help projection，停止并回到 Controller"。
- **反例/失败场景**: `DoclingConverterCapability` 的 `primary_suffixes` 如果在模块级常量 `DOCLING_CONVERTER_CAPABILITY` 初始化时就需要解析 `InputFormat` 枚举，则 import 该模块即触发 Docling import。实现 agent 可能被迫在模块级 hardcode suffix 列表（失去与第三方元数据的同源校验），或在 help 生成时 lazy import（增加启动延迟和失败路径）。
- **为什么有问题**: plan 将此作为 stop condition 而非 design decision，意味着实现 agent 遇到此问题时没有明确的 fallback 策略。如果 stop，整个 work unit 阻塞。
- **直接证据**: plan §5.1 "help/schema 投影只能读取轻量静态 capability，不得在参数解析/模块导入阶段加载 Docling" + Slice 1 stop condition。
- **影响**: 实施 Agent 可能在此处卡住或做出不一致的设计选择。
- **建议改法和验证点**: 在 plan 中明确推荐实现路径——例如：`DOCLING_CONVERTER_CAPABILITY` 在模块级以 hardcode suffix tuple 初始化（受控声明），构造期 lazy 校验与 `FormatToExtensions` 的一致性；help projection 直接读取 hardcode 的静态 suffix。这样 hardcode 与第三方校验同源（同一个 capability 对象），而非两个独立列表。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 2-unfixed-low-XML-歧义后缀投影需明确处理策略

- **位置**: §5.1 候选格式列表与 suffix 投影
- **问题类型**: 契约缺失
- **当前写法**: plan 选择 `XML_XBRL`（映射 `.xml` + `.xbrl`），并说"`.xml` 的多格式歧义必须通过 constructor allowed_formats 消除"。
- **反例/失败场景**: `DoclingConverterCapability` 的 `primary_suffixes` 会包含 `.xml`。当用户上传一个 JATS XML 文件（`.xml` 扩展名），suffix 校验通过，但 converter 因 `allowed_formats` 只含 `XML_XBRL` 而在转换时失败或产生错误解析结果。虽然 plan 说"suffix 只负责确定路由资格，不证明内容转换成功"，但 help/schema 投影列出 `.xml` 可作为 primary 可能误导用户。
- **为什么有问题**: 用户看到 `.xml` 在可接受列表中，可能误以为任意 XML 文件都可作为 primary 上传。这不违反 oracle（因为转换确实会尝试），但降低了用户体验的可预测性。
- **直接证据**: `FormatToExtensions`: XML_XBRL→[xml,xbrl], XML_JATS→[xml,nxml], XML_USPTO→[xml,txt]。
- **影响**: 用户可能上传非 XBRL XML 文件，在转换阶段失败后困惑。不构成 blocker，但 help 文案应明确。
- **建议改法和验证点**: help/schema projection 中列出 `.xml` 时附加说明"仅支持 XBRL 格式"，或考虑只暴露 `.xbrl` 作为 primary suffix（将 `.xml` 从 XBRL 的 suffix 声明中排除）。后者更安全但可能遗漏 Inline XBRL `.xml` 文件。需实现 agent 与 Controller 确认。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Architecture Boundary Review

- **layering**: plan 正确限定在 `dayu.documents`（converter capability）和 `dayu.fins`（upload role contract）以及机械消费者的 CLI / Service 路径。Host / Engine / runtime 不被修改。
- **dependency direction**: capability 从 `documents` 层向下投影，Fins role contract 从 `fins` 层消费 capability，CLI/Service 消费 role contract。无反向依赖。
- **ownership**: 每个语义事实（converter format、primary/companion role、companion-only 集合、actual conversion success、primary_document、atomic publication）都有唯一明确 owner。plan §4 的 ownership table 清晰。
- **schema/storage boundaries**: 不修改 storage schema、原子 batch 协议或 public contract。
- **implementation detail leakage**: help projection 使用轻量静态 capability，不泄漏 Docling 内部 enum 名给 LLM。

## Best-Practice Review

- **testability**: 每个 slice 都有明确的 tests/assertions 和 stop condition。测试断言 owner 级 contract 行为（如 format id 与 `FormatToExtensions` 精确一致），而非偶然行为。
- **maintainability**: 消除重复 allow-list，建立单一 source of truth。companion-only 集合硬编码 `.xsd` 有明确的证据基础。
- **failure handling**: converter 元数据漂移 fail-fast，primary 转换失败零发布，错误 bounded/path-free。
- **minimal dependency**: Fins role contract 不复制 converter allow-list，只投影。

## Overengineering Review

- 无过度设计。plan 没有引入 plugin 注册表、动态 capability discovery、MIME sniffing 或 attachment 生态系统。
- companion-only 集合只包含当前证据明确要求的 `.xsd`。
- 保留现有函数名和调用结构，只删除重复 allow-list 与下游反推。

## Overcoupling Review

- 无过度耦合。Slice 1（capability owner）和 Slice 2（role contract）可独立实现和测试。Slice 3（Service 消费）依赖前两个 slice 但不引入双向依赖。
- batch scanner 使用 `accepts_primary` 投影，不直接依赖 converter capability 内部结构。
- SEC/CN workflow 的 fresh validation → file_selection → Service 的 typed handoff 是单向数据流。

## UF-FIX07 边界检查

- plan §3.2 明确列出 UF-FIX07 的非目标：不做显式 primary selector、不解决重复输入/同名文件/派生名碰撞。
- plan §5.4 保持"首文件隐式 primary"，不引入新参数。
- plan §7 invariant #1："首文件隐式 primary；本 work unit 不引入新参数或重排。"
- Slice 3 stop condition: "若发现同名/派生名碰撞，记录为 UF-FIX07 residual，不在本 slice 修复。"
- **结论**: plan 严格遵守 UF-FIX06/07 边界，未越界。

## Converter Capability Owner 与 DocumentConverter Constructor 同源性验证

- 当前 `build_docling_pdf_converter` 构造 `DocumentConverter(format_options={InputFormat.PDF: ...})`，未传 `allowed_formats`，意味着 Docling 使用默认全格式枚举。
- plan 要求同一函数显式传入 `allowed_formats=capability.resolve_allowed_formats()`，使 constructor 的格式接受范围与 capability 声明严格一致。
- 校验逻辑：构造期从 capability 的稳定格式标识解析 `InputFormat`，并与 `FormatToExtensions` 精确比较。不匹配则 `DoclingRuntimeInitializationError`。
- **结论**: 同源性设计成立。capability 声明 → 解析 → 校验 → constructor 使用同一集合。

## 受控格式与第三方完整 suffix 投影是否意外扩面

- plan 选择 9 个格式：PDF, DOCX, PPTX, HTML, MD/TXT, CSV, XLSX, XML_XBRL, JSON_DOCLING。
- 排除的格式：IMAGE, AUDIO, VTT, LATEX, XML_JATS, XML_USPTO, METS_GBS, ASCIIDOC。均有明确理由（非已证明产品能力）。
- 排除的 legacy：DOC, PPT, XLS, ZIP。有冻结 UF-O12 证据支撑。
- 第三方 suffix 投影中的额外扩展名（如 DOCX 的 `.dotx/.docm/.dotm`，MD 的 `.text/.qmd/.rmd`）会进入 capability 的 suffix tuple。
- **结论**: 未意外扩面。选择集有明确的产品需求和冻结证据基础。第三方额外扩展名是该格式的完整 suffix 投影，plan 要求测试精确断言每个格式的完整 suffix 集合。

## Conclusion

**pass-with-risks**

plan 在架构边界、语义 ownership、依赖方向、UF-FIX06/07 边界、测试覆盖和可实施性方面均满足要求。两个 finding 均不构成 blocker：

1. **help projection 懒加载边界**（medium）：plan 将此作为 stop condition，但未给出推荐实现路径。建议在 plan 中补充"模块级 hardcode 静态 suffix + 构造期 lazy 校验"的实现建议，避免实施 agent 在此处卡住或做出不一致选择。
2. **XML 后缀歧义 help 文案**（low）：help/schema projection 列出 `.xml` 时应附加 XBRL 限定说明，避免误导用户。

两个 residual risk（R1 Docling 版本漂移、R6 函数命名）已在 plan 中有明确处理策略。UF-PF06/PF12 等后续 work unit 不在本 plan 范围内。
