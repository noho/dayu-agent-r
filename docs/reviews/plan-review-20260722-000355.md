## Architecture Boundary Review

**Owner map 一致性**: PASS。

Plan §4.1 的 owner map 明确：

- `local terminal watermark/promotion顺序` → owner = `open_host` coordinator
- 跨 opener correctness → 不依赖 local notice，依赖 durable DB causal fence/reconciliation

当前测试（line 1442-1446）使用 `monkeypatch.setattr(HostTransientDeltaHub, ...)` 做 **class-level** mock，这在 S2 是正确的——S2 尚未接线 terminal coordinator，任何对 `advance_committed_terminal_event_sequence_high_watermark` 的调用都是意外。

S3 接线后，owner 事实变为：
- opener A 的 coordinator **应当**调用 A 的 hub instance 的该方法
- opener C 的 hub instance **不应当**被 A 的 action 触发

Amendment 要求在 **C instance 局部状态** 层面观测，这精确对齐 owner map 的 "local terminal watermark" owner 边界。class-level mock 跨越了 opener A 和 C 的 instance boundary，违反了 "每个 opener 独立拥有 coordinator" 的语义。

### F2-未修复-低-C-side assertion 保留依赖 implementation agent 判断

- **位置**: plan amendment S3 Tests/assertions 新增段落（"C的local watermark/hook必须与A动作前一致"）
- **问题类型**: 测试缺口
- **当前写法**: Amendment 要求证明 "C的local watermark/hook必须与A动作前一致，C watcher保持pending且C reconcile clock未推进时不得发生page read或其它wake"。当前测试已有 C-side watermark 断言（line 1490-1496: `host_c._transient_delta_hub.committed_terminal_event_sequence_high_watermark(session.session_id) == 0`）和 page_read 断言（line 1488: `assert page_read_spy.cursors == []`），但没有显式 C-side hook call 断言。
- **反例/失败场景**: Implementation agent 可能只删除全局 `call_count == 0` 断言，而忘记添加 C-side positive evidence（例如 "C instance 的 hook 调用数为 0" 或 "A instance 的 hook 调用数为 1"）。
