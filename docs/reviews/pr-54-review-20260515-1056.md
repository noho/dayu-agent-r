### F1-未修复-[严重]-Dispatch timeout/cancelled 路径留下孤儿 dispatch record，Attempt/Run 状态不一致

- **入口/函数**: `HostDispatchScheduler._dispatch_one`
- **文件(行号)**: dayu/host/dispatch.py:481-483, 621-624, 761-793
- **输入场景**: 三种超时/取消场景：(1) lane acquire 超时 (`LaneAcquireTimedOut`)；(2) worker startup 超时 (`TimeoutError`)；(3) lane acquire 被取消 (`LaneAcquireCancelled`)
- **实际分支**:
  - 场景1：`_closeout_worker_startup_timeout(record)` 关闭 Attempt/Run 为 FAILED，但 dispatch record 仍停留在 WAITING_FOR_LANE
  - 场景2：同上，dispatch record 停留在 DISPATCHING（无 worker_accept 也无 cancelled）
  - 场景3：直接 `return "skipped"`，不修改任何 durable 状态——dispatch record 停留在 WAITING_FOR_LANE，Attempt 停留在 STARTING，Run 停留在 RUNNING
- **预期行为**: dispatch record 应被 CAS 推进到 CANCELLED；Attempt/Run 应被 closeout 到终态；所有 durable 状态应保持一致
- **实际行为**: 场景1/2 只关闭 Attempt/Run 但不更新 dispatch record；场景3 不修改任何 durable 状态
- **直接证据**: dispatch.py:481-483 (LaneAcquireTimedOut 直接调用 closeout_worker_startup_timeout 不更新 dispatch record)、dispatch.py:621-624 (worker TimeoutError 同上)、dispatch.py:484-485 (LaneAcquireCancelled 仅 return "skipped")、dispatch.py:761-793 (_closeout_worker_startup_timeout 只调 terminal_closeout_in_transaction，不调 cancel_starting_dispatch_record_row)、run_transition.py:672-748 (terminal_closeout_in_transaction 只更新 Attempt/Run row，不更新 dispatch record)
- **影响**: (1) dispatch record 永久停在非终态（DISPATCHING 或 WAITING_FOR_LANE），`worker_accept_event_id` 和 `cancelled_event_id` 都为 NULL——诊断工具无法判断此 dispatch 的真实状态；(2) 场景3最严重：Attempt 永久 STARTING、Run 永久 RUNNING，无任何恢复机制，lane controller 关闭后不会再有 scheduler drain 处理；(3) `read_dispatch_record_by_attempt_id` 返回最新的 dispatch record，孤儿记录可能干扰后续 retry/replay 的 dispatch record 查询
- **建议改法和验证点**: (1) 在 `_closeout_worker_startup_timeout` 的 `_operation` 内增加 `cancel_starting_dispatch_record_row` 调用，将 dispatch record CAS 推进到 CANCELLED；(2) 为 `LaneAcquireTimedOut` 新增独立的 lane acquire timeout closeout 方法，在同一 write transaction 中同时 cancel dispatch record + terminal closeout Attempt/Run；(3) 为 `LaneAcquireCancelled` 区分"scheduler close 导致的取消"（不需要 closeout，scheduler close 自身会清理）和"heartbeat error 导致的取消"（需要 closeout），对后者执行与 LaneAcquireTimedOut 相同的 closeout 逻辑。验证：构造 timeout/cancelled 场景测试，确认 dispatch record 最终状态为 CANCELLED
- **修复风险（中）**: `cancel_starting_dispatch_record_row` 的 CAS 条件要求 `status IN (PENDING, WAITING_FOR_LANE, DISPATCHING) AND worker_accept 为空`，与 timeout 路径的 dispatch record 状态完全匹配，CAS 安全。LaneAcquireCancelled 需要区分 scheduler close vs heartbeat error
- **严重程度（严重）**: 场景3留下永久非终态的 Run，无恢复机制；场景1/2 留下诊断状态不一致的 dispatch record

### F2-未修复-[高]-HostCommandHandleOptions.local_execution 已定义和校验但从未被消费

- **入口/函数**: `create_host_command_handle`
- **文件(行号)**: dayu/host/command.py:195-219
- **输入场景**: 调用方传入 `HostCommandHandleOptions(local_execution=HostLocalExecutionOptions(...))` 创建 handle
- **实际分支**: `create_host_command_handle` 调用 `_durable_options_from_public_options(options)` 时完全忽略 `options.local_execution`，`HostCommandHandle.__init__` 没有 scheduler/lane/registry 槽位
- **预期行为**: 根据 phase5 plan P5-S3，`create_host_command_handle` 应当检查 `local_execution` 选项，当非 `None` 时打开 `HostDispatchScheduler`、注册 wakeup port、在 `HostCommandHandle.close()` 时关闭 scheduler/lane/worker registry
- **实际行为**: `local_execution` 仅在 `HostCommandHandleOptions.__post_init__` 中被校验（字段类型和值约束），但 `create_host_command_handle` 和 `HostCommandHandle` 均不消费它。`HostCommandHandle.close()` 只关闭 `durable_store`，不关闭任何 scheduler/lane/registry
- **直接证据**: command.py:206-219（create_host_command_handle 未使用 local_execution）、command.py:100-105（HostCommandHandle __slots__ 无 scheduler）、command.py:139-148（close 只关闭 durable_store）、api.py:775（local_execution 字段定义）
- **影响**: (1) 通过公共 handle 的 `start_run` 只会持久化 dispatch 意图，永远不会自动 dispatch 到 worker；(2) handle 关闭时不会清理 scheduler/lane/registry 资源；(3) 调用方设置了 local_execution 却得不到本地执行能力，行为与 `local_execution=None` 完全一致；(4) 已校验但未消费的字段违反 CLAUDE.md "禁止魔法字符串"精神和"参数有效性"要求
- **建议改法和验证点**: 在 `create_host_command_handle` 中消费 `options.local_execution`：当非 `None` 时，`await HostDispatchScheduler.open(...)` 并将 scheduler 作为 wakeup port 传给 admission service；在 `HostCommandHandle` 添加 `_scheduler` 槽位；在 `close()` 中 `await self._scheduler.close()`。验证：设置 local_execution 后 `start_run` 应自动 dispatch 并完成 worker 执行
- **修复风险（中）**: 需要修改 `HostCommandHandle.__init__`、`close()`、`create_host_command_handle`，可能影响 `HostCommandHandle` 的同步/异步边界（`open` 是 async 但 `create_host_command_handle` 是 sync，需要设计协调机制）
- **严重程度（高）**: 核心功能选项完全无效，影响本地执行闭环在公共 handle 路径上的可用性

### F3-未修复-[高]-Session continuity 投影对失败 Run 产生孤立 UserMessage

- **入口/函数**: `DurableSessionContinuityProvider._load_session_continuity_tx` + `_continuity_message_from_event`
- **文件(行号)**: dayu/host/run_input.py:437-442, 886-912
- **输入场景**: Session 内存在一个前序 Run: USER_INPUT_ACCEPTED -> RUN_FAILED。当前 Run 为后续 Attempt
- **实际分支**: `read_run_input_continuity_events` 返回 5 种事件类型（含 RUN_FAILED / RUN_CANCELLED / RUN_LOST），`_continuity_message_from_event` 仅投影 USER_INPUT_ACCEPTED 和 RUN_SUCCEEDED，对其余三种返回 None
- **预期行为**: 连续对话结构中 user/assistant 交替出现，或显式决策排除失败 Run 的 user input
- **实际行为**: 前序失败 Run 的 USER_INPUT_ACCEPTED 被投影为 UserMessage，但无对应 AssistantMessage。最终 messages 中出现连续两条 UserMessage（前序失败 Run 的 user input -> 当前 Run 的 user input），中间无 assistant 响应
- **直接证据**: run_input.py:437-442 遍历所有 continuity events 仅通过 `_continuity_message_from_event` 过滤；run_input.py:894 处理 USER_INPUT_ACCEPTED 返回 UserMessage，run_input.py:902 处理 RUN_SUCCEEDED 返回 AssistantMessage，run_input.py:912 对其余所有类型返回 None。event_log.py:47-53 确认查询包含 RUN_FAILED / RUN_CANCELLED / RUN_LOST
- **影响**: (1) 违反 LLM 对话交替约定，可能导致模型异常行为（如模型尝试"补答"被丢弃的历史提问）；(2) 同一 Session 多次失败 Run 的 user input 会持续累积为连续孤立 UserMessage，放大上下文噪声；(3) 确定性不受影响（同一 EventLog 投影结果一致），但对话结构语义不完整
- **建议改法和验证点**: 在 `_load_session_continuity_tx` 中增加 Run 终态跟踪：对每个 Run 判断其最后事件是否为 RUN_SUCCEEDED；仅对终态为 RUN_SUCCEEDED 的 Run 投影其 USER_INPUT_ACCEPTED + RUN_SUCCEEDED 消息对；跳过终态为 RUN_FAILED / RUN_CANCELLED / RUN_LOST 的 Run 的全部 continuity 事件。验证：(1) 构造 Session 含一个失败 Run + 一个成功 Run + 当前 Run，验证 continuity 只包含成功 Run 的 user/assistant 消息对；(2) 构造 Session 仅含失败 Run，验证 continuity 为空
- **修复风险（中）**: 需确保不误过滤跨 Run 的 USER_INPUT_ACCEPTED（当前 Run 的 user_input 不在 continuity 中，已在 L438 通过 run_id 过滤隔离）
- **严重程度（高）**: 对话结构语义错误直接影响 LLM 输出质量

### F5-未修复-[中]-_is_dispatchable_recheck 只接受 WAITING_FOR_LANE 不接受 pending，偏离设计约束

- **文件(行号)**: dayu/host/dispatch.py:881-910

- **实际行为**: 只接受 WAITING_FOR_LANE。当前 scheduler 流程中 `_mark_waiting_for_lane` 先于 `acquire` 执行，所以在正常流程中 dispatch record 一定是 WAITING_FOR_LANE，pending 场景在当前实现中不会出现

- **修复风险（低）**: 单行条件修改，不改变正常流程行为
- **严重程度（中）**: 当前无生产影响但偏离设计约束

### F6-未修复-[中]-scheduler close() 循环中 handle.close() 抛异常会中断后续清理

- **入口/函数**: `HostDispatchScheduler.close`
- **文件(行号)**: dayu/host/dispatch.py:443-448
- **输入场景**: scheduler close 时多个 active handle，其中某个 handle.close() 或 handle.cancel() 抛异常
- **实际分支**: for 循环中 handle.cancel() / handle.close() 抛异常 -> 后续 handle 未被 close -> active_task 也不被 cancel
- **预期行为**: best-effort 关闭所有 handle 和 task，单个失败不应阻止其余
- **实际行为**: 异常传播出 close()，后续 handle 的 cancel/close 不执行
- **直接证据**: dispatch.py:443-448 无 try/except 保护
- **影响**: scheduler close 不完整，可能留下未关闭的 worker handle 和未取消的 event 消费 task
- **建议改法和验证点**: 在循环体内添加 try/except，记录但不抛出异常，确保所有 handle 都有机会被 close。对 active_task 的 cancel 循环同理
- **修复风险（低）**: 添加异常保护，不改变成功路径行为
- **严重程度（中）**: close 路径是进程退出关键路径

### F11-未修复-[高]-_duplicate_terminal_event_ids 不覆盖 RUN_SUSPENDED / TOOL_AWAITING，重复 candidate 返回 REJECTED 而非 DUPLICATE

- **入口/函数**: `_duplicate_terminal_event_ids` → `_duplicate_terminal_result` → `_late_rejection_reason`
- **文件(行号)**: dayu/host/engine_ingest.py:1236-1335, 273-295, 258-264
- **输入场景**: 同一 RUN_SUSPENDED 或 TOOL_AWAITING candidate（相同 execution_id + worker_event_index）重复到达，且 Attempt/Run 已被首次处理关闭到终态
- **实际分支**: `_duplicate_terminal_event_ids` 对 RUN_SUSPENDED/TOOL_AWAITING 返回空元组 `()`；`_duplicate_terminal_result` 在 `event_ids == ()` 时返回 `None`；流程走到 `_late_rejection_reason`，terminal 已关闭时返回 `"terminal_already_closed"`；最终调用 `_append_rejected_diagnostic` 写入新的 DIAGNOSTIC 事件，返回 `EngineIngestStatus.REJECTED`
- **预期行为**: 重复 candidate 返回 `EngineIngestStatus.DUPLICATE`，附带已有 event rows，不追加任何新事件（设计约束 #12：重复 candidate 返回 existing result，不追加第二条 canonical event）
- **实际行为**: 返回 `EngineIngestStatus.REJECTED`，追加新的 `ENGINE_EVENT_REJECTED` diagnostic 事件到 EventLog
- **直接证据**: engine_ingest.py:1236-1335（`_duplicate_terminal_event_ids` 只覆盖 FINAL_ANSWER / RUN_FAILED / RUN_CANCELLED / CONTEXT_COMPACTION_REQUESTED，RUN_SUSPENDED 和 TOOL_AWAITING 走 `return ()` 于 L1335）；engine_ingest.py:273-295（`_duplicate_terminal_result` 在 `event_ids == ()` 时返回 `None`）；engine_ingest.py:258-264（流程走到 `_late_rejection_reason`，terminal 已关闭时进入 `_append_rejected_diagnostic`）
- **影响**: (1) 违反设计约束"重复 candidate 返回 existing result"；调用方无法区分"真正的拒绝"和"重复被误判为拒绝"，监控和幂等性跟踪失准；(2) 每次重复 candidate 额外写入一条 DIAGNOSTIC 事件，EventLog 产生噪音；(3) 与 F4 互补：F4 是缺少首次处理的测试，F11 是重复处理路径的语义错误
- **建议改法和验证点**: 在 `_duplicate_terminal_event_ids` 中增加 RUN_SUSPENDED 和 TOOL_AWAITING 分支，返回与 `_diagnostic_then_failed_waiting` 写入一致的 event_ids（DIAGNOSTIC sub_index=0, ATTEMPT_FAILED sub_index=1, RUN_FAILED sub_index=2）。验证：(1) 对 RUN_SUSPENDED / TOOL_AWAITING 重复 candidate 调用 `ingest()`，验证返回 DUPLICATE 且无新事件；(2) 验证 events 中包含 diagnostic + ATTEMPT_FAILED + RUN_FAILED 三条
- **修复风险（低）**: 仅在 `_duplicate_terminal_event_ids` 增加分支，不改变首次处理路径逻辑
- **严重程度（高）**: 违反幂等性设计约束，每次重复产生额外 EventLog 噪音，监控误判风险

### F12-未修复-[中]-cancel_starting_dispatch_record_row 对已 CANCELLED 的 dispatch record 返回 INVALID_STATE 而非吸收

- **入口/函数**: `cancel_starting_dispatch_record_row`
- **文件(行号)**: dayu/host/durable/state.py:2274-2294
- **输入场景**: dispatch record 已经处于 CANCELLED 终态时再次调用 cancel（例如并发 cancel_run 和 timeout closeout 同时取消同一 dispatch record）
- **实际分支**: CAS UPDATE WHERE `status IN (PENDING, WAITING_FOR_LANE, DISPATCHING)` 不匹配 → rowcount=0 → diagnostic branches 不匹配 CANCELLED → 返回 `StateMutationStatus.INVALID_STATE`
- **预期行为**: CANCELLED 是终态吸收状态，重复 cancel 应返回 `CAS_LOST`（幂等吸收，表示"已经处于目标终态"）
- **实际行为**: 返回 `INVALID_STATE`，调用方（`_raise_for_cancel_transition_status`）将其转换为 `HostApiError(code=INVALID_STATE)` 抛出
- **直接证据**: state.py:2236-2262（CAS UPDATE WHERE 不覆盖 CANCELLED 状态），state.py:2274-2294（diagnostic branches 只匹配 PENDING/WAITING_FOR_LANE/DISPATCHING+worker_accept_NULL，CANCELLED 走 INVALID_STATE），admission.py:2438-2442（`_raise_for_cancel_transition_status` 将非 UPDATED/NOT_FOUND 统一转为 INVALID_STATE API 错误）
- **影响**: (1) F1 修复中在 `_closeout_worker_startup_timeout` 内调用 `cancel_starting_dispatch_record_row` 时，若并发 cancel 已将 dispatch record 推进到 CANCELLED，会得到 INVALID_STATE 而非被吸收，可能阻碍 closeout 事务完成；(2) `cancel_run` 对 pre-dispatch starting 的取消路径中，若 dispatch record 已被另一并发操作取消，会通过 `_raise_for_cancel_transition_status` 抛出 INVALID_STATE API 错误，而非返回幂等成功
- **建议改法和验证点**: 在 `cancel_starting_dispatch_record_row` 的 diagnostic branches 中增加对 `DispatchRecordStatus.CANCELLED` 的处理：`if latest.status == DispatchRecordStatus.CANCELLED: return DispatchRecordMutationResult(status=StateMutationStatus.CAS_LOST, row=latest)`。验证：构造并发 cancel 场景，确认第二次 cancel 返回 CAS_LOST 而非 INVALID_STATE
- **修复风险（低）**: 仅增加一个 elif 分支，不改变已有 CAS 逻辑
- **严重程度（中）**: 阻碍 F1 修复路径的正确性；并发 cancel 场景下产生误导性 API 错误
