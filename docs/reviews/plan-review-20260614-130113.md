## Findings

### 01-未修复-高-HostCallContext 构造职责未指定

- **位置**: CLI-01-S2 `EntrypointTurnRequest` 定义 (line 415: `context: HostCallContext`)，CLI-01-S3/S4 数据流
- **问题类型**: 契约缺失
- **当前写法**: `EntrypointTurnRequest` 包含 `context: HostCallContext` 字段，但 plan 未说明谁构造该 context、使用什么值。`HostCallContext` 要求 5 个必填字段：`actor: str`、`source: str`、`request_id: str`、`authorization_claims: tuple[AuthorizationClaim, ...]`、`operation_context: OperationContext`，且 `actor`/`source`/`request_id` 不能为空。
- **反例/失败场景**: 实现 agent 不知道 `HostCallContext` 应由 CLI 层构造还是 Service helper 构造。如果由 CLI 构造，`actor`、`source`、`authorization_claims`、`operation_context` 应填什么值？如果由 Service helper 构造，`EntrypointTurnRequest.context` 字段多余。不同 slice 的实现 agent 可能做出不同假设，导致不一致或重复实现。
- **为什么有问题**: `HostCallContext` 是 Host public API 的必填输入，每次 `submit_followup`、`cancel_run`、`create_session` 都需要。旧 CLI 没有等价概念（旧 Host 没有此类型）。这是新架构引入的新契约，plan 必须显式指定。
- **直接证据**: `dayu/host/api.py:1317` 定义 `HostCallContext` 为 frozen dataclass，5 个必填字段全部有 `__post_init__` 非空校验。现有 smoke scripts（`utils/smoke_host_public_multiturn.py:675`）各自硬编码 helper 函数构造 context，无共享 factory。
- **影响**: 实现 agent 被迫自行决定 context 构造策略，可能导致 slice 间不一致、测试 fixture 与生产代码构造方式不同、或遗漏必填字段校验。
- **建议改法和验证点**:
  - 在 S2 的 `EntrypointTurnRequest` 说明中明确：CLI 层负责构造 `HostCallContext`，Service helper 只消费它。
  - 在 S3/S4 的 CLI 命令实现中指定 context 构造策略：`actor="cli-user"`、`source="cli"`、`request_id` 使用 UUID hex 前缀、`authorization_claims` 为空元组或按 CLI 身份填充、`operation_context` 按 scene/command 填充。
  - 或者从 `EntrypointTurnRequest` 中移除 `context`，让 Service helper 内部构造（但这样会丢失 UI adapter 身份信息）。
  - 验证：测试中断言 `HostCallContext` 字段值符合预期。
- **修复风险（低/中/高）**: 低
- **严重程度（高）**: 高 — 阻塞 code-generation-ready，实现 agent 必须猜测

### 02-未修复-中-init --reset 删除范围未明确枚举

- **位置**: CLI-01-S7 Exact allowed changes (line 764)
- **问题类型**: 契约缺失
- **当前写法**: "`--reset` 只删除本项目当前 init 拥有的 workspace config / `.dayu` runtime dirs；禁止删除用户财报数据，除非有专门参数和确认流程。"
- **反例/失败场景**: 实现 agent 不知道 "本项目当前 init 拥有的" 具体是哪些路径。是否包含 `workspace/config`？`workspace/.dayu`？`workspace/runtime_lanes.sqlite3`？`workspace/fins` 下的 job store？如果删除范围过宽，可能破坏 Fins 数据；如果过窄，可能遗留脏状态导致 init 后配置不一致。
- **为什么有问题**: 旧 CLI 的 `init --reset` 删除 `.dayu`、`config`、`assets`。新 CLI 的 workspace 结构不同（`workspace/config`、`workspace/.dayu`、`workspace/fins`、`workspace/runtime_lanes.sqlite3`），plan 必须明确哪些属于 init 可删除范围。
- **直接证据**: 旧 CLI `commands/init.py` 使用 `_reset_workspace()` 删除 `.dayu`、`config`、`assets` 目录。新架构下 `dayu/fins/ingestion/job_store` 使用 `workspace/fins` 下的文件存储 job records（`FsFinsIngestionJobStore`）。
- **影响**: 实现 agent 可能删除不该删除的 Fins 数据，或遗漏应删除的脏配置。
- **建议改法和验证点**:
  - 明确枚举 `--reset` 删除范围：`workspace/config/`、`workspace/.dayu/`。
  - 明确排除：`workspace/fins/`（Fins 业务数据）、`workspace/runtime_lanes.sqlite3`（runtime lane coordinator，非 init 管理）。
  - 验证：测试中断言 reset 后 Fins 数据目录和 runtime lane DB 仍存在。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中 — 不阻塞核心功能，但可能导致数据丢失

### 03-未修复-中-prompt.json context slot 名称映射未验证

- **位置**: CLI-01-S3 Stop condition (line 540-541)
- **问题类型**: 不可直接实施
- **当前写法**: "若当前 `prompt` scene 无法承载旧 `--ticker` slot，停止并报告需要先改 scene manifest，不在 CLI 中注入隐式 prompt 文本。"
- **反例/失败场景**: plan 假设 `--ticker` 可以映射到 `prompt.json` 的 context slot，但未验证实际 slot 名称。当前 `prompt.json` 声明 `context_slots` 包含 `fins_default_subject`（string 类型）和 `base_user`（string 类型）。`--ticker` 应映射到 `fins_default_subject`，但 plan 未明确写出这个映射关系。如果实现 agent 使用错误的 slot 名称，`ScenePrepare` 会报 required slot missing。
- **为什么有问题**: plan 的 Stop condition 把验证责任推给实现阶段，但 plan 本身应该在 design alignment 阶段完成这个验证。这是 plan 的 code-generation-ready 缺口。
- **直接证据**: `dayu/config/prompts/manifests/prompt.json` 声明 `context_slots` 为 `[{name: "fins_default_subject", type: "string"}, {name: "base_user", type: "string"}]`。
- **影响**: 实现 agent 在 S3 可能遇到 stop condition 而被迫中断，浪费一个 slice 周期。
- **建议改法和验证点**:
  - 在 S3 的 Exact allowed changes 中明确：`--ticker` 映射为 `context_slot_values["fins_default_subject"] = ticker_value`。
  - 验证：测试中断言 `compose_submit_followup_request` 收到的 `scene_inputs` 包含正确的 slot value。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中 — 可能在实现时被发现并修复，但增加返工风险

### 04-未修复-低-Fins direct job 轮询间隔未指定

- **位置**: CLI-01-S5 Data flow (line 640) 和 State transitions (line 645-651)
- **问题类型**: 契约缺失
- **当前写法**: "循环 `read_job(job_id)`：`QUEUED` / `RUNNING` / `CANCELLING`：继续等待并输出进度。"
- **反例/失败场景**: 实现 agent 不知道轮询间隔。如果间隔太短（如 10ms），会对 job store 产生不必要的 IO 压力（`FsFinsIngestionJobStore` 使用文件锁 + 原子写入）。如果间隔太长（如 30s），用户会感觉命令卡住。
- **为什么有问题**: 旧 CLI 使用 streaming progress events 实时输出进度。新架构下 Fins ingestion runtime 不提供 streaming progress，只有 `read_job` 轮询。plan 应指定合理的默认轮询间隔。
- **直接证据**: `FsFinsIngestionJobStore.read_job` 使用 `filelock` + JSON 文件读取，每次调用涉及文件锁获取。`FinsIngestionWaitPollAdapter` 的 Host wait adapter 路径由 Host dispatch poll interval 控制（`host_runtime.json.dispatch_poll_interval_seconds`），但 CLI 直接轮询路径没有等价配置。
- **影响**: 实现 agent 可能选择不合理的轮询间隔，影响用户体验或系统性能。
- **建议改法和验证点**:
  - 在 S5 中指定默认轮询间隔为 1-2 秒，可选 `--poll-interval` 参数。
  - 或者复用 `host_runtime.json` 的 `dispatch_poll_interval_seconds` 作为参考。
  - 验证：测试中断言轮询间隔在合理范围内。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — 不阻塞功能，可在实现时决定

### 05-未修复-低-S2 Service helper 的 HostCallContext 构造指导缺失

- **位置**: CLI-01-S2 Exact allowed changes (line 392-438)
- **问题类型**: 最佳实践偏离
- **当前写法**: S2 定义了 `EntrypointTurnRequest` 包含 `context: HostCallContext`，但 helper 方法签名中未说明 context 来源。
- **反例/失败场景**: 与 Finding 01 关联。S2 的 `submit_entrypoint_turn_and_wait(...)` 需要 `HostCallContext` 来调用 `Host.submit_followup`。如果 S2 helper 内部构造 context，则 `EntrypointTurnRequest.context` 字段多余；如果由调用方构造，则 S2 应明确说明调用方职责。
- **为什么有问题**: 现有 smoke scripts 的模式是每个调用点自行构造 `HostCallContext`（`utils/smoke_host_public_multiturn.py:675`）。S2 应遵循同一模式，让 CLI 层构造 context 并传入 helper。
- **直接证据**: `tests/host/public_smoke_support.py:997` 的 `host_context(request_id)` 是最接近共享 factory 的实现，但它在 test 包中，不在 Service 或 Runtime 包中。
- **影响**: 实现 agent 可能在 S2 helper 内部硬编码 context 值，导致 CLI 身份信息丢失。
- **建议改法和验证点**:
  - 在 S2 的 `submit_entrypoint_turn_and_wait` 签名说明中明确：`context` 由调用方构造并传入，helper 不负责 context 构造。
  - 验证：测试中使用显式构造的 `HostCallContext`，断言 helper 透传到 `Host.submit_followup`。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — 与 Finding 01 关联，修复 01 后此 finding 自然收敛

### 06-未修复-低-interactive run fatal/non-fatal 分类规则未指定

- **位置**: CLI-01-S4 Error handling (line 581-582)
- **问题类型**: 契约缺失
- **当前写法**: "单轮 Host failed -> 输出错误，interactive 继续或按 fatal classification 退出；fatal classification 必须由 Service error type 决定。"
- **反例/失败场景**: 实现 agent 不知道哪些 Host terminal 状态是 fatal（应退出 interactive）vs non-fatal（应继续 REPL）。例如：`FAILED` with `error_code="runner_exception"` 是 fatal 还是 non-fatal？`FAILED` with `error_code="context_compaction_required"` 呢？
- **为什么有问题**: 旧 CLI 的 interactive 模式在单轮失败时继续 REPL（除非是 instance lock conflict）。新架构下 Host terminal `FAILED` 有多种 error code，plan 应明确分类规则。
- **直接证据**: `RunSnapshot.status` 包含 `SUCCEEDED`、`FAILED`、`CANCELLED`、`LOST` 终态。`HostEvent.error_message` 和 `HostEvent.cancel_reason` 提供额外信息。
- **影响**: 实现 agent 可能对所有 `FAILED` 一律退出 interactive，或一律继续，都不是最优行为。
- **建议改法和验证点**:
  - 在 S4 中指定默认规则：`FAILED` 继续 REPL 并输出错误；`LOST` 退出 interactive；`CANCELLED` 继续 REPL。
  - 或者指定：所有非 `SUCCEEDED` 终态都继续 REPL，只有 Host handle 关闭才退出。
  - 验证：测试中断言 `FAILED` 后 interactive 仍可接受下一轮输入。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — 默认规则可在实现时确定，不影响架构

## Final Plan Review Conclusion

**pass-with-risks**

Plan 整体质量高，架构边界清晰，slice 切分合理，race-free terminal observation 设计正确，Fins direct command cancel 语义完整，旧 CLI command surface audit 详尽。6 个 findings 均非结构性缺陷：

- **Finding 01**（HostCallContext 构造）是最高优先级，需在 S2/S3 实现前明确，否则实现 agent 必须猜测。修复风险低。
- **Finding 02-06** 均为契约补充或验证前置，不阻塞架构方向，可在 slice 实现前或实现中收敛。

Plan 可以进入 implementation gate，但建议先修复 Finding 01（HostCallContext 构造职责）再启动 S2/S3 的代码生成。
