## 3. 架构评审

### 3.1 Host/Engine 边界 ✅

- poller 严格在 Host 层内，不侵入 Engine。
- `_CommandHandleWaitResolver` 通过 command handle 调用 `resolve_wait`，不直接操作 durable store。
- `_OpenHostWaitPollerFactory` 为每轮 poll 创建独立 durable store + command handle，通过 `_ClosingWaitPoller` 在 `poll_once` 结束后关闭，避免连接泄漏。

### 3.2 分层依赖 ✅

- `wait_adapter.py` 只依赖 `dayu.host.durable.state`、`dayu.host.durable.transaction`、`dayu.host.api` 和 `dayu.contracts`，不依赖 `open_host`。
- `open_host.py` 导入 `wait_adapter.py` 的公共类型，方向正确（上层依赖下层）。
- 无反向依赖。

### 3.3 状态机正确性 ✅

- poll claim CAS 使用 `SELECT ... WHERE ... LIMIT 1` + `UPDATE ... WHERE` 两步在同一 write transaction 内，保证原子性。
- claim 条件正确覆盖：`resume_policy=poll AND (status=waiting OR (status=cancelled AND poll_abandoned_at IS NULL)) AND (poll_next_observe_at IS NULL OR poll_next_observe_at <= now) AND (poll_claim_id IS NULL OR poll_claim_expires_at <= now)`。
- release CAS 要求 `poll_claim_id = ? AND status IN (waiting, cancelled)`，防止 stale release。
- abandon CAS 要求 `status = cancelled AND poll_abandoned_at IS NULL`，幂等保护。
- 终态 transition（`_mark_wait_record_terminal_row`）正确清空所有 poll claim 字段并重置 `poll_backoff_attempt`。

### 3.4 Backoff 策略 ✅

- 指数退避：`initial_delay * multiplier^(attempt-1)`，capped at `max_delay`。
- 默认值：30s 初始、2x 倍率、300s 上限，合理。
- `poll_next_observe_at` 在 release 时写入 durable，保证 crash 后恢复正确。

### 3.5 Shutdown 语义 ✅

- close 顺序：public gate → wait poller → scheduler → projection flush → durable store。
- `_release_shutdown_skipped` 释放 claim 但不推进 backoff attempt（复用 `_release_with_backoff` 但设置 `SHUTDOWN_SKIPPED` outcome），使 wait 在下次 open 后可立即重试。
- `close_drain_timeout_seconds=5.0` 提供诊断超时，不中断 join。
- poller 线程中 lifecycle gate 检查点覆盖：claim 前、adapter 调用后、resolve 前。

### 3.6 Thread Safety ✅

- `WaitPollerSupervisor` 使用 `threading.Event` 做 close 信号，`threading.Lock` 保护 diagnostics state。
- `_ThreadsafeSchedulerWakeupPort._run_on_loop` 使用 `call_soon_threadsafe` + `Future.result()` 实现同步跨线程调用，正确处理异常传播。
- `_is_current_event_loop` 避免同线程死锁。

## 7. 发现

### F-01: `poll_claim_expires_at` CHECK 约束缺失与 `poll_claimed_at` 的时序关系校验

- **严重性**: Low
- **状态**: Not a blocker
- **描述**: DDL 中 claim 四列 all-or-none CHECK 约束保证了它们同时为 NULL 或同时非 NULL，但没有约束 `poll_claim_expires_at > poll_claimed_at`。这是一个 SQLite CHECK 约束的表达力限制，Python 层的 `_validate_poll_claim_inputs` 也未校验时序。
- **风险**: 低。应用层逻辑保证 `claim_expires_at = now + ttl`，不可能出现 `expires_at <= claimed_at`。DDL 的 all-or-none 约束已足够防止部分写入。
- **建议**: 保持现状，SQLite CHECK 不适合表达时序比较。

### F-02: `_OpenHostWaitPollerFactory.create_wait_poller` 每轮创建新 durable store

- **严重性**: Low
- **状态**: Design decision — acceptable
- **描述**: `create_wait_poller` 每次调用 `open_host_durable_store`，为每轮 poll 创建独立 SQLite connection。这保证了线程安全（poller 在独立线程运行），但增加了 connection 开销。
- **风险**: 低。默认 `poll_interval_seconds=1.0`，每秒一次 connection open/close 对 SQLite 来说开销可接受。设计上正确优先——避免跨线程共享 connection。
- **建议**: 保持现状。如未来需要优化，可考虑 connection pool，但当前不必要。

### F-03: `claim_wait_record_for_poll` 中 SELECT + UPDATE 非原子竞态窗口

- **严重性**: Low
- **状态**: Not a blocker
- **描述**: `claim_wait_record_for_poll` 先 `SELECT wait_id ... LIMIT 1` 获取候选，再 `UPDATE ... WHERE wait_id = ?` 尝试 claim。两次操作在同一 write transaction 内（`run_write`），但 SELECT 结果可能在 UPDATE 时已被其他 poller claim。UPDATE 的 WHERE 子件包含了与 SELECT 相同的条件（`poll_claim_id IS NULL OR poll_claim_expires_at <= now`），所以 CAS 失败时 `rowcount=0`，调用方正确处理为 `CAS_LOST`。
- **风险**: 无实际风险。这是标准的 claim-on-candidate 模式，UPDATE WHERE 提供了 CAS 保证。唯一的"浪费"是一次无效 UPDATE，这在 SQLite write lock 下开销极低。
- **建议**: 保持现状。

### F-04: `_resolve_claimed_wait` 中 exception → read latest → 判断终态的模式

- **严重性**: Info
- **状态**: OK
- **描述**: 当 `resolve_wait` 抛出异常时，poller 读取最新 wait record 判断是否已到终态。如果已到终态返回 `CAS_LOST`（表示另一个 resolve 已成功），否则返回 `INVALID_STATE`。
- **风险**: 无。这是一个正确的 defensive check。`resolve_wait` 内部的 idempotency 机制保证了重复 resolve 不会产生副作用，这里的 read 只是诊断用。

### F-05: `_ClosingWaitPoller` 在 `poll_once` 的 finally 中关闭 command handle

- **严重性**: Info
- **状态**: OK
- **描述**: `_ClosingWaitPoller.poll_once()` 在 finally 中调用 `command_handle.close()`，确保每轮 poll 结束后释放独立的 durable connection。
- **风险**: 无。`poll_once` 内部所有 DB 操作都在 `command_handle` 的 transaction runner 上，close 后不再有引用。

### F-06: `WaitPollerSupervisor` 不支持 reopen

- **严重性**: Info
- **状态**: Design decision — by design
- **描述**: `open()` 在 `_opened=True` 时抛出 `RuntimeError("stopped wait poller supervisor cannot be reopened")`。这是 intentional 设计——一个 supervisor 实例只服务一个 `open_host` 生命周期。
- **风险**: 无。`open_host` 的 context manager 语义保证了 supervisor 与 Host handle 同生命周期。
