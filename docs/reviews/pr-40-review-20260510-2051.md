## Findings

### 1-已修复-[低]-`lease_context` 在 `try/finally` 之前注册 session，`create_task` 异常泄漏

- **入口/函数**: `AttemptSupervisor.lease_context`
- **文件(行号)**: `dayu/host/_attempt_supervisor.py(570-576)`
- **输入场景**: `asyncio.create_task` 在事件循环关闭时抛 `RuntimeError`
- **实际分支**: 行 571 注册 `self._sessions[attempt_id] = session`；行 572 `asyncio.create_task(...)` 抛异常；`try: yield` 从未进入，`finally` 中 `_stop_session` 不执行
- **预期行为**: session 注册与 try/finally 保护一致，异常时 session 应被清理
- **实际行为**: session 泄漏在 `_sessions` 中，后续 `is_owner_active` / `wait_owner_lost` 对该 attempt_id 返回错误结果
- **直接证据**: 行 571 在 try 之前；行 589 的 try 仅包裹 yield
- **影响**: 仅在事件循环关闭等极端场景触发；正常运行中 `create_task` 不会失败。若触发，attempt 会永久显示为"活跃"
- **建议改法和验证点**: 将 `_sessions[attempt_id] = session` 移入 `try` 块内 yield 之前，或在 `create_task` 外增加异常保护回滚 `_sessions` 注册。验证：mock `create_task` 抛异常，确认 `_sessions` 中无残留
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 3-已修复-[低]-零事件场景下 observer 永远无法从 IDLE 转到 CAUGHT_UP

- **入口/函数**: `ProjectionCoordinator._run_once_locked`
- **文件(行号)**: `dayu/host/_event_observer.py(230-244)`
- **输入场景**: observer 已 `ensure`（`last_success_position=None`，status=`IDLE`），EventLog 全库零事件
- **实际分支**: `not rows` 为 True → `checkpoint.status is not CAUGHT_UP` 为 True → 进入 ternary → `last_success_position is not None` 为 False → `advance_success` 调用被跳过
- **预期行为**: 已追平的 observer 应转为 `CAUGHT_UP`
- **实际行为**: observer 停留在 `IDLE`，`startup_reconcile` 返回的 checkpoint 仍然是 `IDLE`
- **直接证据**: 行 244 `advance_success(...) if checkpoint.last_success_position is not None else None` — 当 `last_success_position` 为 None 时整行求值为 None，advance 被跳过
- **影响**: 低。当前 `DurableHarnessBundle.startup_reconcile` 丢弃返回值不做断言。但如果未来有健康检查或外部系统依赖 `CAUGHT_UP` 状态作为"ready"信号，会误报 lag
- **建议改法和验证点**: 在 `not rows` 分支内，当 `last_success_position is None` 时也显式写入 `CAUGHT_UP`。补测试：零事件 → drain → 断言 status=CAUGHT_UP
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 4-已修复-[低]-`_append_in_transaction` 中 `lastrowid or 0` 掩盖潜在异常，与 fencing token 防御风格不一致

- **入口/函数**: `DurableRunEventStore._append_in_transaction`
- **文件(行号)**: `dayu/host/_durable_event_store.py(322)`
- **输入场景**: AUTOINCREMENT INSERT 后取 `lastrowid`
- **实际分支**: `int(cursor.lastrowid or 0)`
- **预期行为**: `lastrowid` 为 None 时应 fail-fast（与 `_allocate_fencing_token` 行 1072-1078 的 `RuntimeError` 一致）
- **实际行为**: 静默 fallback 到 position=0，若真发生 None 情况，会写入 position=0 的事件行，与 AUTOINCREMENT 从 1 开始的 schema 契约矛盾
- **直接证据**: `_run_state_store.py:1072-1078` — fencing token 分配对相同场景显式抛 `RuntimeError`；`_durable_event_store.py:322` — 静默 fallback
- **影响**: 极低。SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` 保证 INSERT 后 `lastrowid` 非 None，路径不可达。但不一致的防御风格降低代码审查可信度
- **建议改法和验证点**: 对齐 fencing token 的防御风格：`if lastrowid is None: raise RuntimeError(...)`。pyright 无变化
- **修复风险（低/中/高）**: 无（路径不可达）
- **严重程度（低/中/高/严重）**: 低

## Open Questions

1. **owner-lost + lease-expired 路径无 terminal RunEvent**: FENCED/lease-expired 场景下 harness 走 `close_attempt_with_diagnostic_state`（不写 terminal event），attempt 直接从 RUNNING 跳到 LOST/STALE。下游 observer/projection 是否需要感知这类无 terminal event 的终态变化？当前 `AttemptTerminalLink` 只在有 terminal event 时产出。

2. **`close_terminal` 验证集包含 STALE/LOST**: `_ATTEMPT_TERMINAL_STATES` 包含 STALE/LOST，但 `close_terminal` 设计意图是"正常终态 (SUCCEEDED/FAILED/CANCELLED/SUSPENDED)"。STALE/LOST 诊断态走 `update_state_owner_aware` 路径。是否需要收紧 `close_terminal` 的验证集合？

## Residual Risk

1. **`_renew_loop` 的 `except Exception` 捕获范围较广**（行 977），将编程错误（如 TypeError）也归类为 `STORAGE_ERROR`。虽然通过 masked ERROR 日志暴露，但可能掩盖非存储类 bug。
2. **多进程场景仅 4 个 worker append**: `test_cross_process_append_preserves_cursor_and_position` 使用 4 workers x 5 events = 20 条，未覆盖 SQLite WAL 在高并发写入下的 BUSY 超时重试行为。
3. **`build_durable_harness` 异常回滚路径**: 如果在 `storage = HostStorage(...)` 之后的步骤抛异常，storage connection 可能泄漏，当前无 try/except 包裹。
4. **Memory projection `_pending_by_run` 无界增长**: 如果某 run 只产生 `USER_INPUT_ACCEPTED` 但永远不产生 terminal 事件，pending 列表持续增长，当前无 TTL/上限机制。
5. **`_terminal_cursor` 全量扫描 O(n)**: `_tool_runtime.py:1138-1143` 对 `list_events` 结果做反向全量扫描，durable EventLog 随 run 增长后可能成为 `fetch_more` 路径的性能瓶颈。
