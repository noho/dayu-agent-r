### 001-未修复-[中]-`UploadAssetPlan.validate()` 未执行完整资产名准入，直接 service 边界可消费 planner 会拒绝的计划

- **入口/函数**: `DoclingUploadService.prepare_upload` 的 material 分支，经 `_prepare_upload_asset_plan`；计划契约入口为 `UploadAssetPlan.validate()`。
- **文件(行号)**: `dayu/fins/upload_asset_plan.py:109`、`dayu/fins/upload_asset_plan.py:124`、`dayu/fins/upload_asset_plan.py:139`、`dayu/fins/upload_asset_plan.py:161`；`dayu/fins/pipelines/docling_upload_service.py:1469`、`dayu/fins/pipelines/docling_upload_service.py:1472`、`dayu/fins/pipelines/docling_upload_service.py:1477`；对照完整规划规则 `dayu/fins/upload_asset_plan.py:372`、`dayu/fins/upload_asset_plan.py:385`、`dayu/fins/upload_asset_plan.py:392`、`dayu/fins/upload_asset_plan.py:402`、`dayu/fins/upload_asset_plan.py:419`。
- **输入场景**: 调用方直接构造规范化绝对路径的 `UploadAssetPair`，例如 `Deck.txt` 与 `deck.txt` 的 material 计划，或包含 `meta.json`、`deck.zip` 的计划，再将 `UploadAssetPlan` 传给 `DoclingUploadService.prepare_upload(..., source_kind=SourceKind.MATERIAL, action="create", ...)`。
- **实际分支**: `_prepare_upload_asset_plan` 只对 material 调用 `selection.validate()`，而 `UploadAssetPlan.validate()` 只检查 tuple/条目类型、规范化路径、`original_name`/`docling_name` 的派生一致性和 exact 保序集合；没有调用 `source_asset_name_collision_key`、`is_document_source_control_name`、格式 capability 或 255 字节上限。只读探针中，casefold 碰撞、`meta.json` 控制名、`.zip` 非法后缀三种计划均被 `UploadAssetPlan` 构造为 `accepted`。
- **预期行为**: `UploadAssetPlan` 是转换和发布的完整资产计划契约，构造/直接消费边界应执行与 `plan_upload_assets` 同一套业务名规则；或者 service 只能接收具有准入 provenance 的 typed handoff，不能以裸 `UploadAssetPlan` 代表“已准入”。至少应在读取原件、converter 或 storage mutation 前拒绝上述计划。
- **实际行为**: 裸计划通过 `_prepare_upload_asset_plan` 后进入 `_build_original_assets`/`_build_pending_assets`；casefold 碰撞可进入同一 source 文件集合，控制名可进入 document 业务资产集合，非法后缀可走到 converter 后才失败。正常 CLI/tool/runtime/SEC/CN 链当前由 `admit_fins_upload_material_request` 先调用 `plan_upload_assets`，所以该缺口不是已观察到的公共入口回归，但 service/plan 公共边界没有同一 owner 防线。
- **直接证据**: `UploadAssetPlan.validate()` 的分支只做 exact `seen_names` 去重和派生名校验；`plan_upload_assets()` 在 `seen_originals`/`keyed_names`/`FINS_UPLOAD_FORMAT_CAPABILITY.require_material_path` 中执行完整规则；`_prepare_upload_asset_plan()` 的 material 分支只执行 `selection.validate()` 后原样返回。纯逻辑探针结果为 `casefold_plan_validate=accepted`、`unsupported_suffix=accepted`、`reserved_control=accepted`。
- **影响**: 直接 service 调用可绕过转换前资产名唯一性、控制名和格式约束；在大小写不敏感卷上可产生物理文件冲突，在任何卷上可写入与 storage 控制事实冲突的资产名，非法格式则把本应在 admission 拒绝的输入推迟到 converter/工作流失败。当前公共入口虽有前置 planner，但 contract 仍存在下游可绕过缝隙。
- **建议改法和验证点**: 将完整资产名/格式/长度不变量收束到 `UploadAssetPlan` 构造和 `validate()`，或让 `DoclingUploadService` 只接受不可伪造的 validated handoff；补直接构造 casefold 碰撞、控制名、非法后缀、超长派生名的 owner 和 service 负例，并断言在文件读取/converter/batch 前拒绝。
- **修复风险（低/中/高）**: 中。需要明确 `UploadAssetPlan` 是完整 public contract 还是仅由 admission factory 产生的 provenance payload，避免把 planner 规则重复成第二真源。
- **严重程度（低/中/高/严重）**: 中。

- **预期行为**: 当前注释明确写明“整批先完成控制名与非法名分类，再判断业务资产互撞”，且已有测试对控制名与碰撞/超长混合输入要求 `RESERVED_CONTROL_NAME`；reserved control name 应在所有业务资产冲突之前稳定胜出，或规则必须显式改为固定优先级并同步测试和文案。
- **实际行为**: 同一批输入按重复 basename 失败，用户/LLM 会先被要求重命名同名原件，实际更根本的 `META.JSON` 控制名冲突没有被报告；错误 code、message、retry hint 和 tool 的 asset-plan category 均随之改变。

- **建议改法和验证点**: 先收集整批 normalized entries 的控制名/非法名分类并按原始输入索引选首错，再检查 duplicate basename、派生名和碰撞；补两个顺序的 `same.txt`、`META.JSON` 参数化回归，断言 `RESERVED_CONTROL_NAME` 及安全标签稳定。
- **修复风险（低/中/高）**: 低。只调整原因分类顺序和对应 owner 测试，不改变合法输入或发布结果。
- **严重程度（低/中/高/严重）**: 低。
