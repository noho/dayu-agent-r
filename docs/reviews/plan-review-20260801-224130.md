## 4. Architecture boundary review

- **Semantic owner**: `dayu/host/context_events.py` 是 strict payload builder/validator/parser 的唯一 owner。Proposal 保持此划分不变，不新增 adapter/helper/schema owner。
- **Owner-first sequencing**: S5 先改 owner signature，再迁移 consumer——这是正确依赖方向（owner → consumer），不产生循环依赖。
- **S4 → S5 依赖**: `test_compaction_terminal.py` 同时出现在 S4 allowed files 和 S5 delta 中。S4 不预埋 optional identity（§8.2.2），S5 在 winner 路径上做 required 扩展。Sequencing 正确。

## 5. Best-practice / Overcoupling / Overengineering review

- **非过度设计**: 不新增 abstraction、wrapper、compatibility layer。只增加 required typed 参数和机械 consumer migration。
- **非过度耦合**: 15-call migration 是 owner signature 变更的 mechanical 必然结果，不是人为绑定。
- **最佳实践**: bug fix 修 root cause（owner signature），不局部止血（不加 optional/default）。

## 6. Findings

### 001-未修复-低-§6 residual risks 表分类与 proposal 修正文本不一致

- **位置**: proposal §6 residual risks 表第 1 行和第 3 行
- **问题类型**: 契约缺失
- **当前写法**: 两行均分类为 `covered by later approved slice`，暗示需要后续 slice 处理。但 proposal §3.2 已明确冻结 file-local deterministic typed identity 规则：允许构造 deterministic、非敏感、typed identity，禁止 manifest/config 反推，identity 只用于满足 strict event contract fixture 自洽。
- **反例/失败场景**: 若实施 agent 读到 §6 residual risks 表，可能误以为 file-local identity 构造规则尚未确定，需要等待后续 controller 裁决。实际上 §3.2 已提供完整、可执行的规则。
- **为什么有问题**: §6 与 §3.2 的信息不一致。§3.2 的规则是完整的，§6 的分类标签过时。
- **直接证据**:
  - §6 第 1 行: `file-local deterministic typed identity 与 sibling run/operation/attempt/manifest 语义不一致 → covered by later approved slice`
  - §3.2: `允许由各自 file-local fixture owner 构造 deterministic、非敏感、typed SuccessfulRunnerResponseIdentity；该 identity 必须与同一 event 的 sibling run/operation/attempt/manifest 语义一致`
  - §6 第 3 行: `实现者只更新 builder call，遗漏 exact payload fixture → covered by later approved slice`
  - §3.2 已定义完整 fixture 构造规则
- **影响**: 低——实施 agent 若以 §3.2 为主则不受影响，但 §6 的分类可能造成困惑
- **建议改法和验证点**: 将 §6 第 1 行和第 3 行的分类从 `covered by later approved slice` 改为 `fixed in current amendment`，并引用 §3.2 作为修复依据
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 002-未修复-低-§3.2 mapping/null 分类中 proactive 场景的 failure_category 验证需逐场景确认

- **位置**: proposal §3.2 mapping/null 分类规则
- **问题类型**: 契约缺失
- **当前写法**: `rejected 的 parse/schema/semantic/quality/budget post-success category 为 mapping；transport/timeout/cancel/Engine failed 且没有 successful final 时才为 null`。并以 `test_proactive_compaction_operation.py::_rejected_payload()` 当前 `failure_category="quality_check_rejected"` 为例说明必须为 mapping。
- **反例/失败场景**: §3.2 正确识别了 `quality_check_rejected` 必须为 mapping。但未显式确认：`test_proactive_compaction_operation.py` 中调用 `_rejected_payload()` 的 3 个测试场景（orphan、incomplete、exhausted）是否全部属于"有 successful Engine final 后的 rejection"类别。若某个场景实际没有 successful final，则 mapping 是错误值。
- **为什么有问题**: 实施 agent 需要逐场景判断 mapping 还是 null，proposal 应显式确认而非让 agent 猜测。
- **直接证据**:
  - `test_proactive_compaction_operation.py` 第 268 行 `_rejected_payload()` 使用 `failure_category="quality_check_rejected"`
  - 3 个调用场景（test_...orphan、test_...incomplete、test_...exhausted）的 failure_category 均为 `quality_check_rejected`
  - Controller adjudication §2: `quality_check_rejected 语义上已有 successful response，应填安全 typed mapping`
  - 因此 3 个场景均为 mapping，§3.2 的规则正确
- **影响**: 低——当前 3 个场景确实都是 post-success rejection，mapping 正确；但 proposal 应显式确认
- **建议改法和验证点**: 在 §3.2 对 `test_proactive_compaction_operation.py` 的迁移边界补充一句："当前 3 个调用场景（orphan、incomplete、exhausted）均使用 `failure_category='quality_check_rejected'`，按 event semantic 均为 post-success rejection，`successful_response_identity` 值应为 mapping。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
