## Findings

### 01-未修复-高-现有测试固化 T1 断言与 plan 替换示例直接冲突，S1 实现必崩

- **位置**: Slice S1 "Exact allowed changes"、test matrix "Example contract"、`tests/host/test_public_compact_smoke.py:204`
- **问题类型**: 测试缺口 / 不可直接实施
- **当前写法**: plan S1 写"用本文 PS1/PF1/PA1/PI1/PR1/T1/E1/A1/T2 完整 example pair 替换当前 T1 最小形状示例"，test matrix 写"删除固定未定义 T1 oracle"。但未列出具体需要修改的测试断言。
- **反例/失败场景**: 实施 agent 替换 prompt example 后，`test_default_compactor_prompt_is_llm_facing_and_self_contained` 第 204 行 `assert '"source_labels": ["T1"]' in user_prompt_template` 立刻失败，因为新 example 的 session_summary.source_labels 会包含多个 label（如 `["PS1", "PF1"]`）而非单个 `T1`。实施 agent 必须自行判断如何修改该断言，可能导致不一致的修复。
- **为什么有问题**: plan 的 "Allowed files" 包含 `tests/host/test_public_compact_smoke.py`，但 "Exact allowed changes" 没有列出该测试的具体断言修改。按 CLAUDE.md "测试必须跟着实现边界迁移" 要求，plan 应明确哪些旧断言被替换、新断言是什么。
- **直接证据**: `tests/host/test_public_compact_smoke.py:204` 写死 `'"source_labels": ["T1"]'`；plan Slice S1 "Exact allowed changes" 第三条只说"替换当前 T1 最小形状示例"，未提该测试行。
- **影响**: 实施 agent 到达该测试时必须自行设计新断言，增加不一致风险；若 agent 不修改测试则 S1 validation 失败。
- **建议改法和验证点**: 在 S1 "Exact allowed changes" 明确列出：删除 `assert '"source_labels": ["T1"]' in user_prompt_template`，替换为解析 example input/output JSON、验证所有 output label 均来自 example input 的 source_boundary labels、且 production parser 接受该 output。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 02-未修复-中-real provider smoke 指定 DeepSeek 与原冻结"Mimo 优先"冲突

- **位置**: Slice S3 "Exact allowed changes" 第一条、Residual Risks 第二行
- **问题类型**: 目标漂移
- **当前写法**: plan S3 写"复用现有 `DAYU_RUN_REAL_COMPACTOR_SMOKE=1` 和 `PROVIDER_CASES[1]` credential/skip 分类"。Residual Risks 写"真实 provider 输出存在随机性或 credential/network/quota 不可用"。
- **反例/失败场景**: 原冻结要求"真实 provider 优先 Mimo plan，不可用才 DeepSeek"。四个 package execution profile 的 `compactor_baseline.model_id` 都指向 `mimo-v2.5-pro-plan`。若 `PROVIDER_CASES[1]` 是 DeepSeek，smoke 验证的不是 production compactor 实际使用的 provider/model。当 DeepSeek 特有的行为差异（temperature 处理、JSON mode、context window）掩盖或制造问题时，smoke 结果不可信。
- **为什么有问题**: `dayu/config/README.md` 明确写"四个 package execution profile 的 `run_baseline.model_id` 与 `compactor_baseline.model_id` 当前都指向 `mimo-v2.5-pro-plan`"。production compactor 不使用 DeepSeek。用 DeepSeek smoke 验证 Mimo prompt contract 是间接证据，不直接。
- **直接证据**: `dayu/config/README.md:181-183`；plan Slice S3 "Exact allowed changes" 第一条。
- **影响**: smoke 可能漏掉 Mimo 特有的 prompt 解析差异，或在 DeepSeek 上通过但在 Mimo 上失败。
- **建议改法和验证点**: 明确说明为何选择 DeepSeek 而非 Mimo 作为 smoke provider。若因 Mimo credential 不可用，应记录为 precise skip classification；若因 DeepSeek 是现有 seam 且 plan 判断风险可接受，应显式说明 tradeoff 并在 residual risk 中标注"smoke provider 与 production compactor model 不同"。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-中-cap feedback 改法欠规格，_collect_policy_issues 当前不含数值

- **位置**: Contract decisions 第 4 条 "Exact policy feedback"、Slice S2 "Exact allowed changes" 第四条
- **问题类型**: 不可直接实施
- **当前写法**: plan 写"从同一 policy instance 生成精确 cap feedback"、"actual 与 cap 均在 `_collect_policy_issues/_section_caps` 已有数据流中产生"。Slice S2 写"policy reject message 按本文 Exact policy feedback 输出 actual、cap、计量对象和直接动作"。
- **反例/失败场景**: 当前 `_section_caps` 在 `context_governance.py:546-562` 生成的 message 是 `"{section} 超过 Memory policy item cap。"` 和 `"{section} 超过 Memory policy size cap。"`，不含任何数值。`_collect_policy_issues` 对 session_summary 的 message 也是 `"session_summary 超过 Memory policy size cap。"`。plan 声称"已有数据流中产生"不准确——数据流有 policy instance 和 actual 计量值，但 message 不含它们。实施 agent 需要自行决定：(a) 修改 `_issue()` 调用的 message 字符串嵌入数值；(b) 在 `CompactValidationIssueV2` 增加字段；(c) 在 repair projector 读取 policy 并重算。方案 (c) 违反 plan 的"projector 不读取 policy"约束；方案 (b) 改变了 internal feedback schema；方案 (a) 最自然但 plan 没有明确。
- **为什么有问题**: plan 的 S2 "Error handling/invariants" 写"projector 只接收 typed feedback，不接受 raw mapping"和"renderer 不读取 policy，不重算 cap"，排除了方案 (b) 和 (c)。但方案 (a) 需要修改 `_section_caps` 的 message 格式，这不是 plan 显式列出的 "Exact allowed changes"。
- **直接证据**: `context_governance.py:546-562` 的 `_section_caps` 函数；plan Contract decisions 第 4 条。
- **影响**: 实施 agent 到达该步骤时必须自行决定改法，可能选择与 plan 约束不一致的方案。
- **建议改法和验证点**: 在 S2 "Exact allowed changes" 明确：修改 `_section_caps` 和 `_collect_policy_issues` 的 message 字符串，嵌入 `len(texts)` / `item_cap` / `total` / `size_cap` 的具体数值；或在 `_issue()` 调用处追加格式化后的 actual/cap 信息。明确 "Memory policy" 术语在 LLM-facing message 中必须替换为业务可读表述（如"字符上限"）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 04-未修复-低-repair projector 从 to_json() 还是从 typed feedback 投影未明确

- **位置**: Contract decisions 第 3 条 "Unified repair projection"
- **问题类型**: 契约缺失
- **当前写法**: plan 写"在 `llm_compaction.py` 增加模块级私有纯函数，例如 `_repair_feedback_prompt_json_vnext(feedback) -> Mapping[str, JsonValue]`；函数只投影 required_action 和 issues"。
- **反例/失败场景**: `CompactRepairFeedbackV2.to_json()` 返回 `{previous_attempt_number, issues, additional_issue_count, required_action}`。projector 若从 `to_json()` 结果 dict 过滤 key，则与"不接受 raw mapping"的 invariant 矛盾。projector 若从 typed `CompactRepairFeedbackV2` 对象直接读取 `.required_action` 和 `.issues`，则逻辑更清晰。plan 没有明确输入类型。
- **为什么有问题**: S2 "Error handling/invariants" 写"projector 只接收 typed feedback，不接受 raw mapping"，暗示输入是 typed object。但函数签名示例 `(feedback) -> Mapping[str, JsonValue]` 的 `feedback` 参数类型未标注。
- **直接证据**: plan Contract decisions 第 3 条；S2 "Error handling/invariants" 第一条。
- **影响**: 轻微。实施 agent 大概率会选择 typed input，但 plan 应明确以避免歧义。
- **建议改法和验证点**: 明确函数签名为 `_repair_feedback_prompt_json_vnext(feedback: CompactRepairFeedbackV2) -> Mapping[str, JsonValue]`，输入为 typed feedback 对象，不经过 `to_json()` 中间步骤。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 05-未修复-低-trust boundary 测试只验证 prompt 文本存在，未验证模型行为

- **位置**: Test matrix "Renderer adversarial"、Slice S1 "Validation"
- **问题类型**: 测试缺口
- **当前写法**: test matrix 写"原文不被 production 过滤；全部位于 untrusted block；控制规则位于 block 外并明确禁止执行"。S1 validation 写"参数化注入材料位置为 current/trace/evidence/answer；断言原文仍在 data block、prompt 明确禁止执行、没有 production filter"。
- **反例/失败场景**: 这些都是 static prompt contract 断言——验证 prompt 文本包含信任边界规则、注入文本仍在 data block 内。但没有测试验证模型实际遵守该规则。plan 的 S3 real provider smoke 部分覆盖了这一点（"注入 canary 不成为输出控制语义"），但 S1 的 deterministic adversarial 只做静态检查。
- **为什么有问题**: 这不是 plan 的缺陷——deterministic test 无法验证模型行为，real provider smoke 正是为此设计。但 plan 应明确区分：S1 的 adversarial 测试是 static prompt contract（验证 prompt 包含规则），S3 的 real provider smoke 是 behavioral（验证模型遵守规则）。当前 plan 的 test matrix 和 S1 描述可能让实施 agent 误以为 S1 已覆盖行为验证。
- **直接证据**: test matrix "Renderer adversarial" 行的 assertion 描述；S1 "Exact allowed changes" 第四条。
- **影响**: 低。实施 agent 大概率理解分层，但 plan 可以更明确。
- **建议改法和验证点**: 在 test matrix "Renderer adversarial" 行补充说明"deterministic static check only; behavioral verification in real provider smoke (S3)"。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Final plan review conclusion

**pass-with-risks**

Plan 的架构方向正确：只改三个真正的 owner boundary（prompt asset、repair projector、policy feedback message），不引入新 verifier/filter/loop/schema 版本。Goal Confirmation、non-goals、ownership table、data flow 和 implementation slices 结构完整。

但有三个需要在实施前或实施中解决的问题：

1. **Finding 01 (高)**: `test_public_compact_smoke.py:204` 的 `'"source_labels": ["T1"]'` 断言与 plan 的"替换最小形状示例"直接冲突。plan 应在 S1 Exact allowed changes 中显式列出该测试断言的替换方式。这是一个确定性的实施 blocker。
2. **Finding 02 (中)**: real provider smoke 指定 DeepSeek 而非 production compactor 使用的 Mimo plan，与原冻结要求不一致。plan 应显式说明 tradeoff。
3. **Finding 03 (中)**: `_collect_policy_issues/_section_caps` 当前 message 不含数值，plan 声称"已有数据流中产生"不准确，需明确改法。

Finding 01 是硬 blocker——实施 agent 到达该测试时必定失败，且 plan 没有给出修复指引。Finding 02 和 03 不阻塞实施但增加 agent 自行决策的风险。

建议：plan 更新 S1 Exact allowed changes 补充测试断言替换说明后，可进入 implementation gate。
