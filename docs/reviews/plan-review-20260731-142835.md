- target：`docs/reviews/aapl-download-canonical-ticker-layout-plan.md`
- scope：SEC primary document 规范化、ticker locator schema、transaction/recovery、
  company alias lookup、九个 read Fins tools、测试与文档决策
- gate：plan review
- reviewed at：`2026-07-31 14:28:35 +0800`

## Assumptions tested

1. SEC submissions 的带路径 `primaryDocument` 只包含可安全剥离的展示转换前缀。
2. canonical ticker 可直接作为单路径组件，且 storage 能拒绝非 canonical identity。
3. company alias/company name lookup 不会把非 ticker 候选送入严格 ticker locator。
4. ticker locator 变化不会泄漏到 `dayu.fins.tools` 或 processor。
5. R06/R07 transaction、recovery 与 document private identity 可在不重写状态机的前提下保留。
6. 现有九工具综合测试能证明 read tools 在 fresh canonical ticker 布局上的行为。

## Findings

### PR-01-未修复-[高]-primaryDocument 规则仍会把含中间遍历或尾随分隔符的值降成合法文件名

- **位置**: “设计决定 / SEC primary document owner”
- **问题类型**: 契约缺失 / 最佳实践偏离 / 测试缺口
- **当前写法**: trim 后按 `/` 分段并“取最后一个非空组件”，同时笼统写“拒绝
  `.`、`..`、反斜杠、绝对路径”。
- **反例/失败场景**: `xsl/../primary_doc.xml`、`xsl/primary_doc.xml/` 或
  `xsl//primary_doc.xml` 都可能按“最后一个非空组件”得到 `primary_doc.xml`，使非法
  输入被无声修复。这样 normalization helper 同时承担路径清洗和文件名投影，未来 SEC
  异常/恶意元数据不会 fail closed。
- **为什么有问题**: 项目要求在 owner 或直接上游输入边界校验，禁止 loose parsing 或
  下游补偿。目标只授权识别 SEC 展示转换前缀，不授权容忍任意路径语法。
- **直接证据**: 目标 accession 只有
  `xslSCHEDULE_13G_X02/primary_doc.xml`；没有证据需要接受 empty segment、dot segment
  或 trailing separator。storage `_normalize_filename(...)` 当前对 separator 严格拒绝。
- **影响**: 实施 Agent 可能写出 `split("/")[-1]` 或 basename 式容错，使异常路径被改写
  成另一个远端文件，下载/持久化错误内容且难以诊断。
- **建议改法和验证点**:
  - 明确 raw value 去空白后不得以 `/` 结尾、不得以 `/` 开头、不得含 `\\`；
  - 按 `/` 拆分后每个 segment 必须非空且不得为 `.` / `..`；
  - 最后一个 segment 再经过单文件名 contract 校验；
  - 测试覆盖目标 transform 路径、普通单组件、absolute、backslash、dot/dotdot、
    double separator 与 trailing separator。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-[高]-alias direct lookup 方案会让公司名候选在进入 alias index 前被严格 ticker locator 拒绝

- **位置**: “设计决定 / ticker locator owner”与 Slice 2
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施
- **当前写法**: ticker locator 只接受 exact canonical ticker；同时让
  `resolve_existing_ticker(...)` 的 direct lookup “复用
  `_canonicalize_ticker_alias(...)`”。
- **反例/失败场景**: `_canonicalize_ticker_alias("Apple Inc.")` 在
  `try_normalize_ticker(...)` 失败后会返回安全路径组件 `APPLE INC.`。若把它送入只接受
  canonical ticker 的 `_target_ticker_dir(...)`，会在 alias index fallback 前抛
  `ValueError`，破坏 read runtime 已承诺的公司名/alias 查询。
- **为什么有问题**: `_canonicalize_ticker_alias(...)` 的语义是“ticker 或公司检索
  alias”，不是“canonical ticker”。把它用于物理 ticker locator 仍然混用了 alias
  channel 与 ticker identity channel。
- **直接证据**:
  - `dayu/fins/storage/_fs_storage_utils.py::_canonicalize_ticker_alias(...)`
    对无法识别的 ticker 明确回退 `strip().upper()`；
  - `dayu/fins/tools/read_runtime.py::_resolve_canonical_ticker(...)` 明确保留公司名通过
    `ticker_aliases` 反查的行为；
  - `tests/fins/test_fins_storage_atomicity.py` 已断言
    `resolve_existing_ticker(["apple"]) == "AAPL"`。
- **影响**: `list_documents` 及全部依赖 `_resolve_canonical_ticker(...)` 的 read tools
  对公司名/非 ticker alias 回归为参数错误或 storage failure。
- **建议改法和验证点**:
  - direct locator lookup 只在 `try_normalize_ticker(candidate)` 成功时执行，并使用其
    canonical 值；
  - 无法解析为 ticker 的候选跳过 direct locator，继续进入现有 company alias index；
  - alias index 仍使用 `_canonicalize_ticker_alias(...)`；
  - 测试 `AAPL`、`aapl.us` 与 `apple` 都解析到 `AAPL`，未知 alias 返回 `None`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

## Special lenses conclusion

- Goal-bound minimal design：两个 slice 均映射到用户已确认目标，无 goal drift。
- Architecture boundary：read tools 保持 repository-only；PR-02 修复后 alias/ticker
  owner 分离成立。
- Best practice / optimal solution：保留 descriptor、transaction 与 document private
  mapping，比整体回滚 R07 更小、更安全。
- Overengineering：未引入 migration、dual-read、registry 或新 public abstraction。
- Overcoupling：两个 slice 可独立验证；ticker slice 的综合 read tool 测试是必要消费面
  验证，不要求工具层改代码。
