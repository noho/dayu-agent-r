## 2. Findings

### 1-未修复-[中]-`CompanyMetaConcurrentUpdateError` 的 typed 投影分叉与机制未钉死，共享 mapper 的自然实施会连带改写 filing 的既有 `storage_io` 投影

- **位置**: §2 Fins material admission 与失败真源（“`CompanyMetaConcurrentUpdateError` 与两个 guarded precondition conflict 映射 typed `source_publication_conflict`，alias 唯一性冲突保留 `ticker_alias_conflict`”）；同段“为 material 增……`source_publication_conflict` reason 构造器，**保留 filing 原文案**”；测试 4（“确保共享 state/guard、failure mapper 和 filing 文案不漂移”）。
- **问题类型**: 契约缺失 / 语义所有权。
- **当前写法**: §2 以全称陈述要求 `CompanyMetaConcurrentUpdateError` 映射 `source_publication_conflict`，未说明该映射只限 material 语境、filing 维持既有 `STORAGE_IO`，也未说明分叉机制（共享 mapper 加语境、material 边界单独构造、还是全局改分支）；“保留 filing 原文案”只约束 message 文案，未约束 code；且 material/filing 各有一个 `source_publication_conflict` 构造器（material 新增“公司或材料状态变化”文案 vs filing 既有“目标 filing 在上传准备期间已由另一请求发布”，`upload_failure.py:399-418`），该异常归哪个构造器同样未定。
- **反例/失败场景**: 实施 Agent 面对共享 `fins_upload_failure_from_exception`（filing 与 material workflow 均消费：`sec_upload_workflow.py:321/:330/:603`、`ingestion_runtime.py:4511/:4994`），最直接的实施是改 :264-271 的全局分支 `STORAGE_IO→SOURCE_PUBLICATION_CONFLICT`。filing 的 company batch 同样经 `stage_upload_company_meta_decision`（`filing_upload_publication.py:810/:853`）触发 merge precondition（`company_meta_contract.py:221-252` 抛 `CompanyMetaConcurrentUpdateError` 的三处），于是 filing 该异常的可观测投影从 `storage_io` 漂移为 `source_publication_conflict` + material 文案。实测 `tests/fins/test_filing_upload_publication.py` 只锁 `storage_io` 的 acquire/fresh-read 路径（:1774/:1808），**没有**断言该异常的投影——漂移不会被 focused suite 抓住，测试 4 的“filing 不漂移”缺命令级锚点。
- **为什么有问题**: 前轮 review RR5 已按“filing 维持既有 STORAGE_IO、material→source_publication_conflict”的双投影口径登记（accepted oracle 边界）；plan 修订未把该分叉写进 owner 契约，两种实施产生两种 filing 可见行为。同一异常的 public code 由 kind 决定，属“失败原因”语义的 owner 边界，按既定“owner 契约须在 plan gate 定死”口径不能留给实施 Agent 猜。
- **直接证据**: `upload_failure.py:264-271`（全局 `CompanyMetaConcurrentUpdateError→STORAGE_IO`）；`company_meta_contract.py:221-252`（merge 三处抛点，filing/material 共用）；`filing_upload_publication.py:810/:853`（filing stage）；`test_filing_upload_publication.py:1774/:1808`（无该异常投影断言）；plan §2 原文与测试 4 原文对照。
- **影响**: filing accepted 行为漂移（oracle 边界破坏）且测试不红；或实施 Agent 为避漂移自行发明分叉机制，形态不可控；gate 复审无法验收“filing 不漂移”。
- **建议改法和验证点**: plan §2 一句话钉死：material 语境的 `CompanyMetaConcurrentUpdateError` 与两个 guarded precondition conflict 投影 material `source_publication_conflict` 构造器；filing 语境的同异常维持既有 `STORAGE_IO` 投影与文案不变（写明分叉机制归属：failure owner 提供 kind/语境化的构造入口，或 material 边界映射；不得改共享 mapper 全局分支连带 filing）。测试 3/4 补一条 filing company batch merge precondition 失败仍断言 `storage_io` 的回归锚点，并断言 material 同异常断言 `source_publication_conflict`。
- **修复风险（低/中/高）**: 低——plan 文本钉死 + 一条回归断言，无结构变更。
- **严重程度（低/中/高/严重）**: 中（用户/调用方可见 code 漂移 + oracle 边界 + 测试无锁，实施分叉多形态；非 O12 主路径，缺名/独立 commit 主承诺不依赖它）。
