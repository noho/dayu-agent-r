## 3. 新 Material Findings

### N01-未修复-中-PRESERVE copytree 未明确要求 `symlinks=True` 与 `ignore_dangling_symlinks=False`

- **位置**：plan §6.5 PRESERVE 调用级顺序第1步；S4 exact changes 第1点。
- **问题类型**：契约缺失 / 状态机漏洞
- **当前写法**：§6.5："copytree 把用户 config 逐字节复制到 staged config，保留用户额外内容"。S4 exact changes 第1点："PRESERVE 先 copytree 用户 config 到 staged config"。
- **反例/失败场景**：`shutil.copytree` 默认 `symlinks=False`，会 follow symlinks 并把目标内容当作普通文件复制。若用户 config 目录内存在指向 workspace 外部的 symlink（如 `config/models.json -> /etc/passwd`），默认 copytree 会把外部文件内容复制到 staged config 中，绕过后续 no-follow shape 检查（因为 staged 中的副本已是 regular file）。
- **为什么有问题**：plan §6.5 行 402-413 明确要求"symlink/dangling/special 不当作'缺失'覆盖"和"已有非法文件不宽松解析"。但 copytree 在 shape 检查之前已将 symlink 转为 regular file，使 shape 检查失去意义。与 plan 自身的安全边界承诺冲突。
- **直接证据**：
  - `dayu/cli/init_workspace.py:822-826` 当前 PRESERVE 实现使用 `shutil.copytree(public_config, staged_config_root, symlinks=True)`。
  - Python 文档：`shutil.copytree` 默认 `symlinks=False`，follows symlinks。
  - plan §6.5 行 398-413 的 managed mode/repair state machine：所有 mode 对 symlink/dangling/reparse/special 都是"安全拒绝"。
- **影响**：实施 Agent 若使用默认 copytree 参数，会引入静默 symlink dereference 漏洞，破坏 workspace boundary safety。
- **建议改法和验证点**：在 plan §6.5 和 S4 中明确要求 `shutil.copytree(src, dst, symlinks=True, ignore_dangling_symlinks=False)`。S4 tests 增加：用户 config 内含 symlink 到外部文件时，staged copy 保留为 symlink（而非 dereference 后的 regular file），后续 validation fail closed。
- **修复风险（低）**：仅需在 plan 文本中增加两个参数约束。
- **严重程度（中）**：不影响 plan 结构正确性，但若遗漏会导致安全边界退化。

### N02-未修复-低-`_PrivatePathShape` 未指定枚举值与 stat 模式的精确映射

- **位置**：plan §6.5 行 415-417。
- **问题类型**：契约缺失
- **当前写法**：`_PrivatePathShape(StrEnum)`，值域精确为 `REGULAR_FILE="regular_file"` 与 `ORDINARY_DIRECTORY="ordinary_directory"`。
- **反例/失败场景**：实施 Agent 可能用 `path.is_file()` / `path.is_dir()` 做 shape 判定，而这些方法默认 follow symlinks。若 quarantine 中残留 symlink（理论上不应出现但 defensive 编程要求），`is_file()` 对指向 regular file 的 symlink 返回 `True`，导致 symlink 被当作 `REGULAR_FILE` 处理。
- **为什么有问题**：plan §6.5 行 421-437 的 dispatch 顺序要求"no-follow actual identity 读取"和"no-follow unlink"。但 shape 枚举本身没有明确要求使用 `stat.S_ISREG` / `stat.S_ISDIR` 而非 `Path.is_file()` / `Path.is_dir()`。实施 Agent 可能选用错误的判定方法。
- **直接证据**：`dayu/cli/init_workspace.py:1267-1309` 当前 `_cleanup_private_path` 使用 `_require_ordinary_directory`（内部使用 `stat.S_ISDIR`）。plan §6.5 未明确 `_PrivatePathShape` 的判定必须基于 no-follow stat。
- **影响**：低概率实施偏差，但在存在 symlink 的边缘场景可能导致 shape 误判。
- **建议改法和验证点**：在 plan §6.5 中补充：`_PrivatePathShape` 的判定必须基于 `_path_identity` 返回的 `stat.S_ISREG(mode)` / `stat.S_ISDIR(mode)`，不得使用 `Path.is_file()` / `Path.is_dir()`。S4 tests 增加 symlink-to-regular-file 在 quarantine recheck 阶段被 `REGULAR_FILE` shape 拒绝的 case。
- **修复风险（低）**：仅需在 plan 中增加半行约束说明。
- **严重程度（低）**：当前代码已使用 stat-based 判定，plan 扩展偏离现有模式的风险小。

### N03-未修复-中-S2 ConfigLoader 调用在 PRESERVE 路径中可能加载到用户已编辑的 execution profiles

- **位置**：plan §4.3 行 209-217；S2 exact changes 第4点。
- **问题类型**：状态机漏洞 / 架构边界
- **当前写法**：plan 指定 `ConfigLoader(package_config_dir=_PACKAGE_CONFIG_ROOT).load_execution_profiles(workspace_config_dir=None)` — `workspace_config_dir=None` 明确只从 package 加载。
- **反例/失败场景**：此调用正确地从 package 加载。但 plan 同时要求 PRESERVE 保留用户已有的 config 文件（包括 `execution_profiles.json`）。如果用户之前编辑了 workspace 中的 `execution_profiles.json` 并改了 `default_execution_profile_id` 或降低了 `min_context_window_tokens`，那么 init 用 package 默认 minimum 验证通过的 Custom/Ollama context 值，在后续 runtime 使用用户已编辑的 workspace profile 时可能仍然不兼容。这不是 bug——plan §6.2 runtime owner necessity 段已说明 PRESERVE/后续用户编辑可制造 drift，runtime `validate_execution_profile_context_window` 会 fail closed。但 S2 init 时只 load package default 而不对用户已有 workspace profile 做兼容性提示，用户可能在 init 成功后立即遇到 runtime 失败。
- **为什么有问题**：这严格来说是 plan 已接受的 residual risk（§14.3）。但 plan 未在 S2 或 §4.3 中说明：当 workspace config 已存在（PRESERVE 场景）时，init 可选地对用户已有 execution profiles 做 compatibility read 并给出 non-blocking warning。当前 plan 完全跳过 user workspace profiles，可能导致令人困惑的"init 成功但 runtime 立即失败"体验。
- **直接证据**：
  - plan §4.3：`workspace_config_dir=None`。
  - plan §6.2 runtime owner necessity：PRESERVE 保留用户编辑。
  - plan §6.5 PRESERVE 只补缺失文件和 owner 字段，不校验已有值。
- **影响**：PRESERVE 路径中 init 成功但 runtime 立即可复现失败（若用户 workspace profile 与所选模型不兼容）。
- **建议改法和验证点**：方案 A（推荐）：在 S2 的 `ConfigLoader` 调用点增加一个 optional 段落：若 workspace config 已存在，在 load package default 后额外 load workspace execution profiles 并对 default profile 的 `min_context_window_tokens` 做 compatibility read；若用户的 `min_context_window_tokens` 高于 package default，使用用户值作为 minimum；若用户 profile 损坏，发出明确 warning 但不阻止 init（因为 PRESERVE 语义是保留用户内容）。方案 B：在 plan 的 residual risk 中明确记录此场景为 deferred non-blocking issue。推荐方案 B——当前 plan 结构不应为此扩 scope。
- **修复风险（低/中）**：方案 B 仅需在 residual risk 中追记。
- **严重程度（中）**：不是 plan 结构错误，但 PRESERVE 用户体验 gap 值得在 residual risk 中明确记录。

### N04-未修复-低-S1 argparse post-parse `config_dir` 检查可能在 argparse 内部 error 后不可达

- **位置**：plan §6.1 行 273-275。
- **问题类型**：不可直接实施
- **当前写法**：`parse_cli_args(...)` 在 parse 后、返回 typed namespace 前，对 `command_name=init && config_dir is not None` 调用 `parser.error(...)`。
- **反例/失败场景**：plan S1 描述 common/runtime 两种 parent。若 init 使用 common parent（不含 `--config`），则 `dayu-cli --config path init` 中 `--config` 被 root parser（使用 runtime parent）解析。这要求 root parser 和 init subparser 使用不同的 parents——argparse 支持这种模式。但若 `--config` 出现在 init 之后的 position（`dayu-cli init --config path`），init subparser 会因不识别的参数直接触发 argparse 内置 error，plan 的 post-parse 检查不会被执行。plan 对此已有意识——S1 stop condition："argparse 无法同时保持非-init command-before option 语义时返回 plan review，不在 runner 加 shim"。
- **为什么有问题**：这不是 plan 缺陷，而是 argparse 的双位置覆盖需要精确的 parents 编排。plan 的 stop condition 已设好安全阀。
- **直接证据**：plan S1 exact changes 第1-2点、stop condition。
- **影响**：若 argparse 行为与预期不符，S1 会在实施中被 stop condition 拦截。
- **建议改法和验证点**：无需修改 plan。实施 Agent 在 S1 中应先用最小 prototype 验证 common/runtime parent 模式在目标 argparse 版本中的行为。
- **修复风险（不适用）**：plan 已通过 stop condition 覆盖。
- **严重程度（低）**：plan 已有安全阀。
