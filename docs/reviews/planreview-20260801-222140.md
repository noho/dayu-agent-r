## Architecture boundary review

### Builder owner → test consumer 方向

`dayu/host/context_events.py` 的两个 strict builder 是 payload contract 的唯一 owner。5 个 gap 文件是纯测试消费者——它们调用 builder 构造测试用 payload。当 owner 增加 required 参数时，所有消费者的迁移是机械且必然的。amendment 正确地将此归类为"mechanical closure"而非新功能或边界变更。

### S4 → S5 依赖

`tests/host/test_compaction_terminal.py` 同时出现在 S4 allowed files（§8.1）和本次 amendment 的 S5 delta 中。S4 创建/修改此文件的 compaction terminal guard 测试；S5 再对其中的 builder call 做 required identity 扩展。amendment 的 sequencing 假设是：

1. S4 在不预埋 optional identity 的前提下完成 terminal guard 实现
2. S5 增加 builder required 参数后，对该文件的 builder call 做机械迁移

这是正确的依赖顺序，不产生循环依赖或跨 slice 冲突。S4 §8.2.2 明确禁止预埋 optional identity，因此 S5 的 retroactive 迁移是必要且唯一的路径。

### 与其他 allowed boundary 的关系

5 个 gap 文件均不在第一 amendment 的 25-file identity/typed-return closure 中（它们不直接构造 `FinalAnswerData` 或实现 `ContextCompactor`），也不在原 S5 owner-level test 清单中。这是一个独立且完整的 closure 缺口——amendment 正确识别了它。

### 1-未修复-低-plan §16 路径清单存在过期声称

- **问题类型**: 其它（plan inventory 准确性）
- **当前写法**: plan §16 将 `tests/host/test_compaction_terminal.py` 标记为 "S4 明确 planned-new"，与 `dayu/host/compaction_terminal.py` 并列
- **反例/失败场景**: `ls tests/host/test_compaction_terminal.py` 确认该文件已存在于 HEAD `ec9342ed`，并非 "planned-new"
- **为什么有问题**: 过期 inventory 可能误导 implementation agent：若 agent 认为需要创建该文件（而非修改已有文件），可能覆盖已有 S4 实现或产生文件冲突。此外，该错误暗示 plan 在 S4 的前置提交中可能已部分落地，与 plan 声称的"implementation 尚未开始"存在表面张力
- **直接证据**:
  - `ls tests/host/test_compaction_terminal.py` → EXISTS
  - `git log --oneline -1 -- tests/host/test_compaction_terminal.py` 可确认首次引入 commit
  - plan §16: `2 条为 S4 明确 planned-new (dayu/host/compaction_terminal.py、tests/host/test_compaction_terminal.py)`
- **影响**: 实施 Agent 对文件创建/修改的预期偏差（低概率、低影响）
- **建议改法和验证点**: 在 plan §16 中修正该条目为 `1 条 planned-new (dayu/host/compaction_terminal.py)`，并将 `tests/host/test_compaction_terminal.py` 移入"已存在"类别。或在 amendment 中增加一条说明：该文件已存在于 HEAD，S4 只做修改而非创建
- **修复风险**: 低（只涉及 plan 文档一处文本修正）
- **严重程度**: 低

**注**：此问题在本次 amendment 之前已存在，不是 amendment 引入的新错误。不阻塞 amendment 通过，但建议在 amendment 应用时附带修正。

### 2-未修复-中-5-file delta 中部分测试场景可能缺少 Engine response identity 数据

- **位置**: amendment §3.2、§6 residual risks 表第一行
- **问题类型**: open question 未收敛 / 切片过粗
- **当前写法**: amendment §3.2 要求"所有值必须由该测试已有的同一次成功 response / operation / attempt fixture 提供"，§6 将"fixture 无法在不改变场景语义下提供 mapping/null"列为 residual risk
- **反例/失败场景**:
  1. `tests/host/test_compaction_terminal.py:_append_terminal()`（第 650 行）：该 helper 是 S4 compaction terminal guard 的测试工具，测试焦点是 terminal 唯一性而非 Engine 响应。当前 fixture 可能不包含 `SuccessfulRunnerResponseIdentity`。若 S4 实现不预埋 optional identity（按 §8.2.2），S5 实现者将面临：要么从无到有构造一个 identity（可能引入与测试场景不匹配的数据），要么改变测试场景（被 amendment 明确禁止）
  2. `tests/host/test_compact_material.py:_compacted_payload()`（第 3605 行）：该 helper 用于 compact material 相关测试，测试焦点是 material 构造而非 Engine 响应。同样可能缺少 identity 数据
  3. `tests/host/test_run_input_builder.py`（第 7134 行）：内联 builder call，上下文是 run input builder 测试
- **为什么有问题**: amendment 正确识别了此风险并 defer 到 controller，但没有为 S5 实现者提供具体的 fallback 指导。当 fixture 确实缺少 identity 数据时，实现者只有两个选择：a) 构造一个 synthetic identity（在测试场景中"伪造"成功 Engine 响应），或 b) 停止并退回 controller。前者可能违反"不改变场景语义"的约束（引入原本不存在的 Engine final），后者会阻塞 S5
- **直接证据**:
  - amendment §6 第一行: `planreview 发现某个 5-file fixture 无法在不改变场景语义下提供 mapping / null → requiring explicit controller decision`
  - `test_compaction_terminal.py:650` 调用 `build_context_compacted_payload` 的场景是 terminal guard 测试，不必然包含 Engine response
  - `test_compact_material.py:3605` 同理
- **影响**: S5 implementation 可能因无法在不改变场景语义的前提下提供 identity 而 stall
- **建议改法和验证点**:
  1. 建议 amendment 增加一条规则：当测试场景确实不包含成功 Engine final 时，对于 accepted builder call（要求 mapping），允许构造一个 minimal synthetic `SuccessfulRunnerResponseIdentity`，但必须显式标注为 test-only synthetic identity，并注明"此测试不验证 identity 内容，仅满足 builder required contract"
  2. 或者，在 S5 开始前先做 preflight：逐一检查 5 个文件是否能在不改变场景语义的前提下提供 identity，将无法提供的文件单独列为 controller decision item
- **修复风险**: 低（只涉及 amendment 文本的策略澄清，不改变代码边界）
- **严重程度**: 中（deferred risk，不阻塞 amendment 通过但需要在 S5 前收敛）

## Plan review conclusion

**结论: `pass-with-risks`**

### 通过理由

1. **Inventory 准确**: 独立 `rg` 复核确认 accepted builder `8 calls / 6 files`、rejected builder `7 calls / 4 files`、union `8 files`、delta 精确 `5 files`，与 amendment 声称完全一致。
2. **Scope 正确**: 5 个文件确实不在原 S5 allowed boundary 内（不在 owner-level test 清单，也不在 25-file identity/typed-return closure），是真实的 closure 缺口。
3. **边界清晰**: amendment 正确保持了 semantic owner（`dayu.host.context_events`）、不改变测试场景语义、不引入 optional/default/compatibility seam、不增加新 abstraction。
4. **Non-goals 完整**: 明确禁止 implementation、commit、push、PR，不改变第一 amendment 的 25-file closure，不裁决 G06/行为项 29。
5. **第一性原理正确**: 当 accepted contract 要求 strict builder 增加 required 参数时，所有直接 consumer 的机械迁移是必然结果——不是 goal drift，而是对已接受 contract 的完整性修复。

### 附带风险

- **Finding 2（中）**: 5 个 gap 文件中的部分测试场景（特别是 S4 的 compaction terminal guard 测试）可能不包含 Engine response identity 数据，S5 实现时可能 stall。建议在 amendment 中增加 minimal synthetic identity 允许规则，或在 S5 开始前做 preflight 检查。
- **Finding 1（低）**: plan §16 的路径清单有一处过期声称（`test_compaction_terminal.py` 不是 "planned-new"），建议附带修正。

这两个风险均不阻塞 amendment 通过。Finding 2 是 S5 implementation 的前置收敛条件，不是 amendment 本身的设计缺陷；Finding 1 是 pre-existing 文档问题。
