## Findings

### 1-未修复-中-pathful basename 使 known content failure 降级为 runtime/unexpected_runtime

- **入口/函数**: `DoclingUploadService._build_original_assets`（空文件分支）与
  `DoclingUploadService._build_pending_assets`（逐文件 `DoclingConversionError` catch）
- **文件(行号)**:
  - `dayu/fins/pipelines/docling_upload_service.py:708-714`（empty：先 `canonicalize_fins_public_file_label(...)` 再
    `raise FinsUploadFailureError(...)`）
  - `dayu/fins/pipelines/docling_upload_service.py:782-792`（corrupt：先 canonicalize 再
    `raise FinsUploadFailureError(failure) from exc`）
  - `dayu/fins/direct_events.py:1129`（`_validate_public_file_basename_shape` 对 `\` 抛 `ValueError`）
  - `dayu/fins/pipelines/sec_upload_workflow.py:316-324` / `dayu/fins/pipelines/cn_pipeline.py:936-944`
    （generic `except Exception` → `fins_upload_failure_from_exception(exc, file_label=None)`）
- **输入场景**: POSIX 合法文件名含反斜杠（如 `a\b.pdf`；`Path.name` 可含 `\`），且该文件为空或 Docling 转换失败。
- **实际分支**: 内容失败被判定后，producer 调唯一 label canonicalizer；shape 校验因 `\` 抛 `ValueError`，
  `FinsUploadFailureError` 从未构造；`ValueError` 冒出 `prepare_upload`，落入 workflow 最末 generic catch，
  以 `file_label=None` 走 exception mapper 的 fallback 分支。
- **预期行为**: 按 plan §5.4 不变量与 §12 N2 gate completion
  （“pathful仍拒绝且known content kind/code不降级”）与 N2 adjudication 直接证据句
  （“拒绝会让原本已知 content failure 无法形成 typed reason，违背唯一 typed owner 与 bounded public reason 目标”），
  label 拒绝不得摧毁已判定的 content 分类。
- **实际行为**: 已知的 `content/empty_input_file` 或 `content/docling_*` 失败被分类为
  `runtime/unexpected_runtime`，公开 message 变为“上传执行失败，请检查运行日志后重试”，file_label 丢失。
- **直接证据**:
  1. `_validate_source_files`（`docling_upload_service.py:984-1008`）与
     `_validate_fins_upload_filing_static`（`ingestion_runtime.py:891-900`）只校验 exists/is_file/suffix，
     不拒绝反斜杠 basename —— 因此该输入可达 canonicalizer；plan §5.4 明言
     “源文件存在性、filesystem basename 合法性继续由既有 upload input validation owner 负责”，该 owner 目前未负责。
  2. `direct_events.py:1129` 对 `\` 抛 `ValueError`（pathful 拒绝按 plan 保留，正确）。
  3. producer 两处先 canonicalize 后构造 typed error，canonicalize 抛错即短路 —— 与 N2 adjudication 描述的
     “>240 拒绝会让 known content failure 无法形成 typed reason”同一机制，仅输入类别换为 pathful。
  4. 无任何测试覆盖“pathful basename + empty/corrupt 文件”的 producer 行为（owner 级 pathful 拒绝测试存在，
     producer 级不存在）。
- **影响**: 错误 answer / 仅局部行为错误。用户对空/损坏文件得到错误的 runtime 语义与丢失文件名标签；
  无泄漏（仍 typed、bounded、无路径/traceback/raw cause），无状态写入错误，无原子性破坏。
- **建议改法和验证点**: 需 controller 裁决三种收口之一：
  (a) 在输入校验 owner（`_validate_fins_upload_filing_static` 或 `_validate_source_files`）拒绝含 `\` 的 basename
  （新增 closed usage code），使 producer 处 canonicalize 拒绝不可达，content 分类永不降级 —— 最符合
  “pathful 仍拒绝”且把拒绝前移到 request 边界；
  (b) producer 捕获 canonicalize 的 `ValueError`，仍以 fixed hidden label 构造原 content reason（语义上把 pathful
  视为“无法原样公开”，需承认与“pathful 仍拒绝”的措辞冲突）；
  (c) 若裁决认为 pathful-producer 降级可接受，须在 plan/artifact 显式记录该例外，不得默认吞掉。
  验证点：任一方案落地后补 producer 级测试：`a\b.pdf` 空文件与 corrupt 文件分别断言
  `empty_input_file`/`docling_*` code 保持、label 为方案规定值、batch begin/commit/rollback 为 0。
- **修复风险（低）**: 方案 (a) 仅在输入校验加一条拒绝规则与测试；方案 (b)/(c) 需改 plan 措辞。
- **严重程度（中）**: 罕见输入（反斜杠文件名）、无泄漏、链路仍 typed/bounded，但违反 plan 明文不变量
  “known content kind/code 不降级”，且 N2 adjudication 的裁决理由逐字适用于该路径。

## 审查要点判定（按委托 review 重点逐项）

1. **empty/corrupt PDF+DOCX/mixed 原子失败真链 —— 成立**
   - empty：`_build_original_assets` 读字节后、converter 与 `begin_batch` 前抛 typed error；
     SEC/CN 均先 `prepare_upload` 后 `begin_batch`（`sec_upload_workflow.py:211/236`、
     `cn_pipeline.py:831/856`），故失败时 batch/company/source/blob 零写入。
   - corrupt：`_build_pending_assets` 逐文件 catch，`raise ... from exc` 保留 `__cause__`，sequential fail-fast
     （后续 converter call 0）；先转换成功的内容只在内存/临时对象中，不进 batch。
   - `DoclingConversionCancelledError` 继承 `RuntimeError` 而非 `DoclingConversionError`
     （`docling_process_converter.py:216/242`），新 catch 不吞取消语义；`prepare_upload` 的 cancelled catch 保持生效。
   - workflow 捕获顺序：`FinsUploadFailureError` 位于 Docling/OSError/generic 之前（SEC:290 / CN:910），
     直接投影 `exc.failure`；测试断言 begin/commit/rollback/stage 全部 0、published tree SHA 不变、stored=0。

2. **FinsUploadFailureReason 五字段 closed schema 与唯一 typed owner —— 符合计划**
   - `_FAILURE_KEYS` exact 五键；`to_json()` 五键（`file_label` 允许 `null`）；parser `frozenset(value) != _FAILURE_KEYS`
     拒绝旧四字段/缺失/未知键；`_optional_failure_text` 只做 str-or-None 类型读取，不复制 label 长度/fragment/control
     规则（parser delegation 测试证明五字段原样传入 constructor）。
   - `__post_init__` 对非 None label 调唯一 `validate_fins_public_file_label`，是 reason 级 label 接受集唯一强制边界；
     生产代码无 owner 之外的 `FinsUploadFailureReason(...)` 构造点。
   - `EMPTY_INPUT_FILE` 入 `_CONTENT_FAILURE_CODES`，parser kind/code 一致性校验强制 content。
   - 依赖方向 `upload_failure -> direct_events` 单向成立（direct_events 无反向 import）。

3. **direct_events label canonicalizer/validator 语义 —— 严格符合计划且不过度隐藏**
   - 普通 basename（含普通中文，如 `report.pdf`、非 fragment 中文名）原样返回；
   - fragment（`job_id_*`、`财报正文`）、Unicode `Cc`/`Cf`（换行、U+202E）、合法但 `>240` 长度 → 固定
     `输入文件（文件名已隐藏）`，与 plan 字面值一致；pathful/空/dot-segment → `ValueError` 拒绝；
   - validator 接受集 = {固定隐藏标签} ∪ {通过 shape 且不需隐藏的 basename}，与 canonicalizer 可能输出集闭合相等；
   - 未放宽/收紧 `FinsEventDetail` 通用 safe-text 守卫（复用 `_validate_safe_text` 与 `_DISALLOWED_TEXT_FRAGMENTS`，
     无第二套 validator）；`_MAX_PUBLIC_FILE_LABEL_CHARS=240` 与 `_MAX_FAILURE_TEXT_CHARS` 一致；
   - 唯一缺陷为 Finding 1 的 pathful-producer 降级问题，与“不过度隐藏”无关。

4. **workflow/runtime/direct 仅消费 typed projection、无字符串重分类 —— 符合计划**
