- **入口/函数**: `AsyncOpenAIRunner._call_impl` 的 SSE 重试决策。
- **文件(行号)**: `dayu/engine/runners/openai/runner.py:295,300,329`。
- **输入场景**: SSE 流先成功 yield `RUNNER_USAGE_RECORDED`（usage 事件），随后 TCP 连接断开，产生 `_AttemptFailedRetriable`。
- **实际分支**: `attempt_yielded_event` 在任意事件（包括 usage 事件、tool_call_delta）首次 yield 后立即设为 `True`。后续 retriable 异常被 329 行检查拦截，直接产出 `RUNNER_HTTP_ERROR` + `RUNNER_DONE(ERROR)` 而不重试。
- **预期行为**: 只有"对调用方可见的内容产出"（content delta、completed tool call）才应阻止重试。Usage 事件和 tool_call_delta（未完成工具调用的部分字节）不会改变调用方状态，网络瞬断后重试不造成内容重复。
- **实际行为**: Usage 记录后、content delta 前的网络错误导致 iteration 永久失败，尽管 token 成本已发生但 content 未传递。
- **直接证据**: `runner.py:300`：`attempt_yielded_event = True` 对所有 yield 事件无条件置位。`runner.py:329`：`if attempt_yielded_event: ... yield RunnerHTTPErrorData(...) + RunnerDoneData(ERROR) ... return`。
- **影响**: 不稳定网络下，usage-only chunk 后的断连导致不必要的 iteration 失败。token 成本已消耗但 content 未送达。
- **建议改法和验证点**: 将 `attempt_yielded_event` 改为 `attempt_yielded_content`，仅在 yield 了 `RunnerContentDeltaData`、`RunnerContentCompletedData`、`BatchToolCallExecutionRequest` 后置位；或为 usage/tool_call_delta 等只读诊断事件单独排除。补充 flaky network 场景的集成测试。
- **修复风险（低/中/高）**: 中。需确认所有 Runner 事件类型的内容语义，避免遗漏应阻止重试的事件。
- **严重程度（低/中/高/严重）**: 中

### 9-未修复-[中]-跨进程 lane `_mark_token_lost` 丢失 waiter 唤醒
- **入口/函数**: `LaneController._heartbeat_loop` → `_mark_token_lost`。
- **文件(行号)**: `dayu/runtime/lane.py:884-891`。
- **输入场景**: Lane 心跳检测到 token 已从 SQLite 丢失（过期或被外部清理）。
- **实际分支**: `_mark_token_lost` 设置 `token._lost=True` 并从 `_held_tokens` 移除，但**不调用** `_wake_waiters()`。对比 `_mark_token_released`（`lane.py:739`）正确调用了 `_wake_waiters()`。
- **预期行为**: 释放的容量应立即通知等待中的 acquire 调用方，与 release 路径一致。
- **实际行为**: 待唤醒的 acquire waiter 不在本条代码路径被通知，依赖下一次 poll 间隔（默认 50ms）发现释放的容量。高争用下增加最多 50ms 延迟。

- **建议改法和验证点**: 在 `_mark_token_lost` 返回前添加 `self._wake_waiters()`。补充并发压力测试验证唤醒延迟。

- **严重程度（低/中/高/严重）**: 中

### 10-未修复-[中]-`RuntimeFileLock` 非线程安全——`_active_token` TOCTOU race
- **入口/函数**: `RuntimeFileLock.acquire`。
- **文件(行号)**: `dayu/runtime/filelock.py:142-148`。
- **输入场景**: 两个线程对同一 `RuntimeFileLock` 实例并发调用 `acquire()`。
- **实际分支**: `_active_token` 的 check-then-set 非原子操作。两线程可能先后通过 `if self._active_token is not None` 检查，第二个线程的 `self._active_token = token` 覆盖第一个的引用，导致第一个 token 在 wrapper 跟踪中变成孤儿。
- **预期行为**: 底层 `filelock.FileLock` 提供 OS 级锁（flock/fcntl），因此文件本身只有一个线程持有。但 wrapper 层的 token 跟踪可能不一致，影响 `release()` 的 token 校验与 `__exit__` 正确性。
- **直接证据**: `filelock.py:142-148`：`if self._active_token is not None ... self._active_token = token`。
- **影响**: 多线程并发使用同一 `RuntimeFileLock` 实例时 token 跟踪错乱。若该类仅限单线程使用（docstring 标注"同步"），则不构成实际 bug；若文档未明确声明线程安全性，应明确。
- **建议改法和验证点**: 若需多线程支持，加 `threading.Lock` 保护 acquire/release/__exit__。若仅限单线程，在类和 `acquire()` 文档中明确标注"非线程安全"。
- **修复风险（低/中/高）**: 低（仅文档约束或小范围加锁）
- **严重程度（低/中/高/严重）**: 中

### 11-未修复-[中]-Host Durable Schema 中 `RECOVERING` Run 状态有 DDL/索引/CAS 守卫但零转换代码
- **入口/函数**: 所有 Run 状态转换函数 + UNIQUE 部分索引 + NOT EXISTS 子查询守卫。
- **文件(行号)**: `dayu/host/durable/schema.py:408`（`INDEX_HOST_RUNS_ONE_ACTIVE_PER_SESSION` 包含 `RECOVERING`）、`dayu/host/durable/state.py:2249,2620,3987`（`promote_queued_run_row`、`resume_waiting_run_row`、`_run_mutation_result_for_active` 均识别 `RECOVERING`）、`dayu/host/durable/run_transition.py`（零处写入 `RECOVERING`）。
- **输入场景**: 任一需要推进 Run 状态的操作（队列提升、等待恢复、取消、终态关闭）。
- **实际分支**: `RECOVERING` 在 UNIQUE 部分索引中被列为"活跃"状态，占用 Session 的单活跃 Run 槽。`promote_queued_run_row` 和 `resume_waiting_run_row` 的 NOT EXISTS 子查询将 `RECOVERING` 视为活跃 Run 阻止队列提升/恢复。但所有产品代码中**没有**任何函数能将 Run 写入 `RECOVERING`，没有函数能从 `RECOVERING` 转出。`_run_mutation_result_for_active` 将 `RECOVERING` 归类为 CAS_LOST 源状态，但没有调用方会在此状态下触发它。

- **实际行为**: 死代码路径——Run 永远无法进入 `RECOVERING`，但如果通过未来代码或手动 DB 操作进入，会永久阻塞同 Session 的队列提升和等待恢复，无退出路径。

- **影响**: 当前无运行时影响（不可达），但每次修改活跃 Run 守卫逻辑时都需注意 `RECOVERING` 的存在。若未来实现 `RECOVERING` 但遗漏退出路径，会导致 Session 级死锁。
- **建议改法和验证点**: 若为未来预留，在 `schema.py` 的索引定义处添加 `-- future-reserved: not yet reachable in Phase 3` 注释，在 `state.py` 各识别点同样标注。若为废弃设计，从 `INDEX_HOST_RUNS_ONE_ACTIVE_PER_SESSION` 的 WHERE 子句和所有 NOT EXISTS 子查询中移除 `RECOVERING`。补充 DDL 与代码一致性验证测试：对所有 `RunStatus` 枚举值断言存在至少一条入边转换和一条出边转换（或确认其为终态/预留状态）。

### 12-未修复-[中]-`cancel_active_wait_records_for_run` 批量取消存在 TOCTOU 竞争
- **入口/函数**: `cancel_active_wait_records_for_run()` → `cancel_waiting_run_in_transaction`。
- **文件(行号)**: `dayu/host/durable/state.py:2138-2181`、`dayu/host/durable/run_transition.py:1394-1541`。
- **输入场景**: 一个 Run 有多个活跃 WAITING 等待记录。`cancel_run` 命令与外部 `resolve_wait` 回调几乎同时到达（在不同事务中）。
- **实际分支**: `cancel_active_wait_records_for_run` 在 2138 行通过 `read_active_wait_records_for_run` 读入快照，随后在 2147 行执行批量 `UPDATE ... WHERE run_id = ? - **预期行为**: 取消操作应对剩余 WAITING 记录部分成功（或提供明确可重试诊断）。当前全有或全无语义导致外部 resolver 抢先解决一条记录就使整个 Run 取消失败。
- **直接证据**: `state.py:2138` 快照读、`state.py:2147` 批量 UPDATE 无 `wait_id` 过滤、`state.py:2174` `rowcount != len(before_rows)` 触发 CAS_LOST。`run_transition.py:1483-1493` `_require_wait_record_mutation_updated` 将 CAS_LOST 转为 `HostDurableError` 并中止事务。
- **影响**: 并发 cancel + resolve 竞赛下，cancel_run 被拒绝而外部 resolver 成功。用户取消请求需重试。SQLite 串行写事务限制了竞争窗口（两操作不可能在同一事务中），但确实存在跨事务竞争窗口。
- **建议改法和验证点**: 将批量 UPDATE 改为逐 `wait_id` 过滤的 UPDATE 循环，允许部分成功；或改为 `UPDATE ... WHERE wait_id IN (...) AND status = ?` 后用受影响行数构造部分成功结果而非全部 CAS_LOST。补充并发 cancel + resolve 压力测试。
- **修复风险（低/中/高）**: 中。需修改批量取消语义，确保部分成功取消不违反 WaitRecord 状态机契约。
- **严重程度（低/中/高/严重）**: 中
