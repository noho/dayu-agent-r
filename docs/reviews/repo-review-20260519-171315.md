## Findings

### 1-未修复-[高]-已发布 console scripts 指向不存在的模块，安装后的用户入口全部失败

- **入口/函数**: `dayu-cli` / `dayu-web` / `dayu-wechat` / `dayu-render` console scripts
- **文件(行号)**: `pyproject.toml:97`, `README.md:149`
- **输入场景**: 用户按根 README 安装后执行 `dayu-cli --help`、`dayu-render --help`、`dayu-web --help` 或 `dayu-wechat --help`
- **实际分支**: console script 读取 `pyproject.toml` 中的入口 `dayu.cli.main:main`、`dayu.render.render:main`、`dayu.web.__main__:main`、`dayu.wechat.main:main`
- **预期行为**: README 宣称的安装验证命令应能导入对应模块并展示帮助；如果当前 Host 重写分支不再提供这些入口，发布元数据和用户手册必须同步移除或标注不可用
- **实际行为**: 当前 `dayu/` 包内没有 `cli/`、`render/`、`web/`、`wechat/` 子包；四个入口均以 `ModuleNotFoundError` 失败
- **直接证据**: `pyproject.toml:98-101` 仍声明四个 console scripts；`README.md:149-158` 要求用户执行这些命令验证安装；`rg --files dayu | rg '(^|/)cli/|(^|/)web/|(^|/)wechat/|(^|/)render/'` 无输出；实际执行 `source .venv/bin/activate && dayu-cli --help` 报 `ModuleNotFoundError: No module named 'dayu.cli'`，`dayu-render --help` 报 `No module named 'dayu.render'`，`dayu-web --help` 报 `No module named 'dayu.web'`，`dayu-wechat --help` 报 `No module named 'dayu.wechat'`
- **影响**: 包安装后最主要的用户入口不可用；根 README 的快速开始、初始化、财报下载、问答、写作、渲染路径全部变成不可执行说明；发布 wheel 会生成必然失败的脚本
- **建议改法和验证点**: 二选一，不能保留半状态：若 CLI/Web/WeChat/Render 是当前发布面，恢复对应 `dayu.cli` / `dayu.web` / `dayu.wechat` / `dayu.render` 实现并补 console script smoke；若当前分支只冻结 Host/Engine public contract，则从 `pyproject.toml` 移除这些 scripts 和无实现的 package-data，重写根 README 为当前真实可用入口。验证点至少包括 `python -c "import dayu.cli.main"` 或确认 scripts 不再生成，以及 README 中所有命令都对应真实模块。
- **修复风险（中）**: 恢复入口会触及旧 UI/Service/Fins 依赖边界；移除入口会改变发布面与用户文档，但这是对当前实现事实的同步
- **严重程度（高）**: 当前用户可见入口确定性失败，阻断安装后使用

### 2-未修复-[高]-Host 测试导入面与冻结的包根 public contract 冲突，pytest 与 pyright 全仓 gate 已阻断

- **入口/函数**: 全仓 `pytest` collection；全仓 `pyright dayu tests`
- **文件(行号)**: `dayu/host/__init__.py:10`, `dayu/host/api.py:1342`, `tests/host/test_public_run_api.py:13`, `tests/host/test_package_exports.py:110`
- **输入场景**: 执行 `source .venv/bin/activate && pytest -q` 或 `source .venv/bin/activate && pyright dayu tests`
- **实际分支**: 多个 Host 测试从 `dayu.host` 包根导入 `HostInput`；但 `dayu.host.__init__` 没有从 `dayu.host.api` 导入 `HostInput`，`__all__` 也不包含该符号
- **预期行为**: 测试应与当前 public contract 同源；若 `HostInput` 是 internal API，测试应从 `dayu.host.api` 导入；若它是 Service/UI 需要的 public API，包根导出白名单应同步更新
- **实际行为**: `from dayu.host import HostInput` 在 collection 阶段直接 `ImportError`；pyright 报 10 个 `HostInput is unknown import symbol`
- **直接证据**: `HostInput` 定义在 `dayu/host/api.py:1342`；`dayu/host/__init__.py:10-77` 的导入列表与 `dayu/host/__init__.py:101-187` 的 `__all__` 都不含 `HostInput`；`tests/host/test_public_run_api.py:13-22` 从包根导入 `HostInput`；`tests/host/test_package_exports.py:110-119` 又把 `HostInput` 放入 `ROOT_INTERNAL_API_NAMES`，明确期望它不从包根导出。实际执行 `pytest -q` 得到 10 个 collection errors，均为 `ImportError: cannot import name 'HostInput' from 'dayu.host'`；执行 `pyright dayu tests` 得到 10 个 `reportAttributeAccessIssue`。
- **影响**: 全仓测试无法进入断言阶段，pyright 全仓 gate 失败；当前测试无法证明 Host public API、dispatch、waiting、read model 等关键路径仍可工作，也违反项目“任何新增或修改代码都必须通过 pyright”的硬约束
- **建议改法和验证点**: 先裁决 contract ownership。若维持 `HostInput` 为低层/internal 类型，修改受影响测试从 `dayu.host.api` 导入，并保留 `test_package_exports.py` 对包根不导出的断言；若决定它是 public contract，则在 `dayu.host.__init__` 与 `tests/host/test_package_exports.py` 中同步纳入白名单，并更新 `dayu/host/README.md`。验证点：`pytest -q` 至少不再 collection fail，`pyright dayu tests` 为 0 errors，`tests/host/test_package_exports.py` 继续表达同一个导出真源。
- **修复风险（低）**: 测试导入修正风险低；若选择扩大 public export，需重新确认 Host package boundary
- **严重程度（高）**: 当前质量门禁确定性失败，且测试自身与 public contract 真源互相矛盾
