### 1-严重-memory catch-up 在事务外执行，失败导致 Run 永久卡在 RECOVERING
- **入口/函数**: `EngineEventIngestor._complete_reactive_recovery` → `catch_up_conversation_memory_projection`
- **文件(行号)**: `dayu/host/engine_ingest.py:2318-2332`
- **输入场景**: Reactive compaction 在 T2 事务中成功提交 `CONTEXT_COMPACTED` event（`_execute_reactive_compaction` 事务已 commit），随后 `_complete_reactive_recovery` 在事务外调用 `catch_up_conversation_memory_projection`。若 memory catch-up 抛出异常（例如 EventLog 读取失败、consumer 内部错误），异常向上传播到 `ingest_async`（line 720），`_finish_ingest` 不会被调用。
- **实际分支**: `catch_up_conversation_memory_projection` 在事务外执行（line 2319-2324），失败后 recovery-start 事务从未执行。重试同一 candidate 会被 `_duplicate_terminal_result`（line 833-844）返回 `DUPLICATE` with `terminal_closeout=False`。由于 `ingest_async` 看到的是 `EngineIngestResult` 而非 `_ReactiveRecoveryAccepted`，`_complete_reactive_recovery` 不会被重新调用。
- **预期行为**: Memory catch-up 失败不应阻止 recovery。要么 catch-up 应放入事务内执行，要么 catch-up 失败应降级为 diagnostic 警告并继续 recovery start。
- **实际行为**: Run 永久卡在 `RECOVERING` 状态。已提交的 `CONTEXT_COMPACTED` fact 存在于 EventLog，但没有后续 recovery attempt。无自动化路径完成 recovery。
- **直接证据**: Line 2319 `catch_up_conversation_memory_projection(...)` 不在任何 try/except 保护内；line 2325 `self._transaction_runner.run_write(_StartReactiveRecoveryOperation(...))` 仅在 catch-up 成功后执行。
- **影响**: 数据损坏（durable stuck state）。Run 永久停留在 RECOVERING，compacted event 已提交但 recovery 永远无法完成。
- **建议改法和验证点**: 将 `catch_up_conversation_memory_projection` 包装在 try/except 中，失败时记录 diagnostic 并继续执行 recovery start；或将 catch-up 移入 `_StartReactiveRecoveryOperation` 事务内。
- **修复风险**: 中。需要确认 memory catch-up 在事务内执行不会引入新的锁竞争或超时问题。
- **严重程度**: 严重

## Open Questions

1. **engine_ingest.py 中 `len(existing) == N` 的 duplicate 检测模式**：当 `len(existing) == 1`（partial write）时，检测失败。这取决于底层 transaction 的原子性保证。如果 SQLite transaction 是真正原子的（同事务内所有写入全部 commit 或全部 rollback），partial write 不可能发生，duplicate 检测逻辑安全。需要确认 EventLog primitive 和 state transition 是否在同一 SQLite transaction 内执行。答案为"是"则此问题不成立。

2. **Reactive compaction 的 budget 跳过**：`_requires_budget_acceptance` 对 REACTIVE 始终返回 `True`（跳过 budget gate）。如果 estimator 系统地低估 token count，可能触发 compaction storm（compaction → overflow → compaction → ...）。设计文档中是否有针对此场景的 circuit breaker 机制（如连续 reactive compaction 计数限制）？当前 `max_reactive_compactions_per_run` 提供硬上限，但默认值未知。

3. **Session summary "全或无" 策略**：`_session_summary_from_accepted_event` 对超长 summary 采用"全丢弃"而非截断。这是有意为之的设计决策（认为不完整的 summary 比没有 summary 更危险）还是实现疏忽？设计文档未明确说明。
