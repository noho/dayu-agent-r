## 3. Findings

### 1-未修复-低-当次进程内映射记录的采集路径未钉住，失败路径默认抛出会丢句柄，易致全向量过度 blocked
- **位置**: 计划 §5 P0-B「每一路的『实际读取/映射目标』只由**该次 Docling 运行**中可核的进程内加载/映射记录，或与该次进程及子进程、时间窗和输入绑定的 OS 文件访问 trace 支撑」及「该次证据不可得…记 `blocked: run evidence unavailable`」。
- **问题类型**: 不可直接实施 / 测试缺口（采集路径歧义导致证据不可得风险；与 PR5 轮 finding 1 同族，落点从「来源未定约」推进到「来源已定约但取得路径未钉住」）。
- **当前写法**: 计划与 fix 判定了合法来源（当次进程内记录 / OS trace）与禁止项（重放、预期布局、新增产品 hook），但没有写出无 hook 的取得路径，也未提失败路径的句柄保留。
- **反例/失败场景**: 实施者照抄现有 probe 模式（`DocumentConverter().convert(path)` 默认 `raises_on_error=True`），typed/载入异常路径直接抛 `RuntimeError`（probe `docling-probe.stdout` 实证），拿不到结果句柄；又因「不造 hook」不敢做任何进程内采集，同时 macOS 无 OS trace——于是三个合成向量（混合引用图、①绝对 schemaRef、②绝对 linkbaseRef）的 Docling 侧全部记 `blocked: run evidence unavailable`。P0-B 对 zip/catalog 可用性的判定（§3「zip 实际可用性仍需 P0-B 复测」）永远无法收敛，S1 硬停，受控 XBRL 目标被非安全原因卡死；或实施者顶不住压力把独立 Arelle 重放贴进「实际映射」栏（被计划禁止但恰是压力所在）。
- **为什么有问题**: 当次进程内记录是 catalog 映射向量唯一可行的证据来源（OS trace 对 zip 内 entry 结构性不可见，见 §1.2.3），取得路径却只存在于源码事实里（SimplePipeline 不 unload + `result.input._backend.model_xbrl` + `raises_on_error=False`），计划未把它写成可执行规格；「可执行」依赖实施者自行发现，失败模式是过度 blocked 或违反禁止项的诱惑，而不是显式失败。
- **直接证据**: 计划 §5 该句原文；`xbrl_backend.py:154,181`（裸 Cntlr、model 挂在 backend）；`base_pipeline.py:185-186` 与 `document_converter.py:858-870`（SimplePipeline 路径不 unload）；`document_converter.py:515-523`（`raises_on_error` 公开参数，默认 True）；`ModelDocument.py:535,678,681,1488-1496`（urlDocs/referencesDocument 留痕）；`FileSource.py:570-580`（zip entry 内存读）；probe `docling-probe.stdout`（默认模式只留异常栈）。

- **建议改法和验证点**: 在该句后补一句取得路径定约，例如「当次进程内记录可在转换进程内以非抛出模式取得该次结果并快照其 XBRL 模型的请求 URI→实际加载目标与逐条引用边（含引用元素）；失败路径同样须保留该次结果/模型快照；OS trace 不可得时以该快照为准」。验证点：P0-B 产物中每路映射记录注明取得路径与模式（抛出/非抛出）；`blocked: run evidence unavailable` 仅在快照与 trace 双缺时出现。
