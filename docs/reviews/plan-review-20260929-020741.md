## Findings

### 01-未修复-[低]-修复后旧非法 fiscal 身份文档永久不可再寻址，plan residual 未登记该后果
- **位置**：plan「依赖、residual 与修复项登记」表（仅登记 O05/O11/O16/O17）；goal 动机段“错误业务身份已发布”；成功信号 3“非法值在身份生成之前被拒绝”。
- **问题类型**: 其它（residual 风险未登记 / 难恢复行为）
- **当前写法**: plan 只做输入域前置拒绝（O09 1800..2100、O10 六枚举），residual 表登记的是其它修复项；对“修复前已按非法 fiscal 发布的存量 material 文档”只字未提。
- **反例/失败场景**: 某工作区在修复前执行过 `upload_material --fiscal-year -1`（冻结证据 UM-S03/S04/S05 已证明该路径 exit 0 且持久化、参与身份，见 O09 裁决表）。修复上线后：（a）同 form/name + `fiscal_year=-1` 的任何 update/delete 请求在 admission 处被 `INVALID_MATERIAL_FISCAL_YEAR` 拒绝，永远到不了 ID 计算；（b）改传合法 year 会生成不同 seed 的新 ID，显式 `document_id` 会因 `validate_material_upload_ids` 的一致性检查报“显式 document_id 与…稳定 document_id 不一致”（`docling_upload_service.py:1883-1888`）；（c）省略 year 的 seed 又与含 year 的 seed 不同。结论：该文档通过 `upload_material` 既不能更新也不能删除，只能文件系统手工处置。
- **为什么有问题**: seed 含 fiscal 输入（`docling_upload_service.py:1849-1853`）+ 修复把非法输入变为不可表达，二者合取导致旧错误身份变成不可达孤儿。这与 plan 自身“错误身份已发布”的严重性判断相呼应，却没有任何处置去向登记；一旦真实用户工作区存在此类文档，将演变成需要另行裁决的数据修复问题。
- **直接证据**: `docling_upload_service.py:1849-1856`（seed 含 year/period）、`1883-1888`（显式 ID 必须等于稳定 ID）；plan contract #1/#3（非法值在身份生成前拒绝）；O09 裁决表 S03/S04/S05 与 O10 表 S07/S08（非法 fiscal 已完成 publication）。
- **影响**: 难恢复；后续发现时需要新 work unit/维护命令或人工数据手术，且届时可能被误判为本修复引入的回归。
- **建议改法和验证点**: 不扩本项范围、不实现清理；在 plan residual 表增加一行明确登记：“修复前已发布的非法 fiscal 身份文档在本修复后不可由 `upload_material` 再寻址（update/delete），存量处置/修复命令属未裁决事项，待 controller 裁决后另立 work unit”。实现 gate 的完成报告按该项如实核对冻结证据工作区是否存在此类文档。若确认真实工作区存在，则升级为需裁决的数据修复问题。
- **修复风险（低）**: 仅补登记文字，不改实现。
- **严重程度（低/中/高/严重）**: 低（upload_material 尚未进入 readiness scope，暴露面主要是校准/开发工作区；若发现真实用户工作区存在则升为中）。

## Open Questions

1. **tool 测试“同一错误 message”对类型垃圾的适用层**：tool 参数层 `_optional_int` 对 bool/非整数先抛 `"fiscal_year must be integer or null"`（`_ingestion_tool_helpers.py:224-226`），不到 admission 的 Fins usage message。plan S1 测试契约“tool 验证同一错误 message”应明确限定为**域值错误**（`-1/0/10000/nonsense/241 字符`）断言 Fins usage message，bool 类型面由 owner 层测试（plan 已列入 owner 覆盖）与 tool 参数层既有行为各自归属，避免实现 Agent 写出错误面断言而返工。
2. **覆盖率测量口径**：plan 的 `--cov` 命令只跑 6 个测试文件测 5 个生产文件；`ingestion_runtime.py`（9144 行）与 `cn_pipeline.py`（2048 行，含下载面）在该子集下数值可能低于全量口径。plan 已有“补充已有相关测试并记录基线、不虚报达标”的兜底；gate 执行时需把“子集口径 vs 全量口径”记录清楚，避免 80% 门槛口径争议。

## 结论

**pass-with-risks**。

计划的动机、owner 判定（year 规则归 `docling_upload_service` 身份 builder、period 复用 `filing_semantics.normalize_fiscal_period`、runtime 只做 usage 映射）、同源数据流（canonical 局部值贯穿 ID/事件/source meta/result）、filing 边界保护（不复用 1000..9999 code、不改 filing 年域）、入口覆盖（runtime 三入口 + US/CN/HK 直接 facade + 公开 builder 复用同一底层规则）、零副作用顺序（admission 早于 producer/observation/job/仓储读写）以及真实 CLI/tool 验证矩阵，经本 HEAD 代码逐条独立重证全部成立；无 goal drift，无过度设计，文件白名单完整覆盖全部语义变更点，S1 单切片对共享前置校验是合理的最小切法。唯一 finding 是 residual 登记缺口（修复前非法 fiscal 存量身份不可再寻址），不影响本项实现正确性，但必须补登记去向后再进入 implementation，避免后续被误判为回归或需要临时扩围处置。
