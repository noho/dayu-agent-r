### 1-未修复-中-Recovery scan batch transaction 中单个 Run CAS miss 导致同批全部 rollback

- **入口/函数**: `recovery.py::SessionAttachmentRecoveryScanner._classify_recovering` → `_start_recovery_dispatch_or_ready`
- **文件(行号)**: `dayu/host/recovery.py:244-255`（batch loop）、`760-872`（`_start_recovery_dispatch_or_ready`）、`864`（raise rollback）
- **输入场景**: scan 批次包含多个 recovering Run，其中第 N 个 Run 的 start CAS miss（如并发 recovery 已抢占该 Run）
- **实际分支**: `_start_recovery_dispatch_or_ready` 先写 manifest（行 837-847）再调 `start_recovery_run_with_starting_attempt_in_transaction`（行 848-852），CAS miss 时 raise `_StartupRecoveryStartRollback`（行 864）
- **预期行为**: 单个 Run 的 CAS miss 不应影响同批其他有效 Run；该 Run 应返回 `INVALID_STATE` action 跳过，同批其他 Run 继续处理
- **实际行为**: `_StartupRecoveryStartRollback`（继承 `HostDurableError`）在 `_SessionAttachmentRecoveryBatchOperation.__call__` 的 `for run in runs:` 循环内（行 244-255）无 per-run try/except，异常直传到 `run_write`（行 338），导致同批次最多 `batch_size` 个其他有效 Run 的 recovery 进度丢失
- **直接证据**: 行 244-255 batch loop 无 per-run error handling；行 864 `raise _StartupRecoveryStartRollback(...)` 在方法内无 try/except 捕获；行 338 `self.transaction_runner.run_write(...)` 接收到异常后 rollback 整批
- **影响**: 并发 recovery 场景下，一个 Run 的 CAS miss 导致同批其他有效 Run 的恢复进度丢失，需下一轮 scan 重试。功能正确性无影响（最终一致），但资源浪费且增加不必要的 recovery 延迟
- **建议改法和验证点**: `_start_recovery_dispatch_or_ready` 不 raise，改为返回 `INVALID_STATE` action；或 batch operation 内加 per-run try/except 隔离单 Run 失败。验证并发 recovery 场景下 batch 内独立 Run 的失败隔离
- **修复风险（中）**: 需重新设计 `_start_recovery_dispatch_or_ready` 的异常传播语义；当前 `_StartupRecoveryStartRollback` 继承 `HostDurableError`，若改为不 raise 需确保上层 scan loop 不依赖该异常做流控
- **严重程度（中）**: 并发场景下可能导致 recovery 延迟累积，但不影响最终一致性
