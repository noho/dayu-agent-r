### 新 Finding RRN-01 — needs-evidence — 中 — close/drain 的 timeout 边界依赖未被代码直接确认

- **位置**: Plan §5.4 "关闭等待只复用既有 Runner/provider 有界边界"，宣称 "LLMContextCompactor.run_prepared_compactor_proposal 已用 asyncio.wait_for(..., timeout=RunnerSpec.default_timeout_seconds) 包住完整 run_agent_and_wait"
- **问题类型**: 契约缺失 / open question 未收敛
- **当前写法**: Plan §5.4 引用既有 `LLMContextCompactor` 的 `asyncio.wait_for` 和 `RunnerSpec.default_timeout_seconds` 作为 detach drain 的上界；Plan §5.4 blocker 条款 "若实施时发现任何 pre-start provider call 绕过 LLMContextCompactor 的上述 timeout owner，必须作为本 slice blocker 回 plan/review"
- **反例/失败场景**:
  1. 本 review 扫描 `dayu/host/compaction_operation.py:186-196`（`run_prepared_compactor_proposal` 方法体），未发现 `asyncio.wait_for` 调用
  2. `RunnerSpec.default_timeout_seconds` 用于 Engine Runner HTTP transport 层（`dayu/engine/runners/openai/runner.py:358`），但 compactor 的 LLM 调用路径可能不经过同一 Runner
  3. 若 compactor 的实际调用路径没有 timeout，则 detach drain 可能无限阻塞，违反 plan §10 的 "close不得force unlock或引入新默认timeout" 约束
- **为什么有问题**: plan 的 drain 有界性论证依赖一个可能不存在的既有 timeout。plan 已用显式 blocker gating condition 防御此风险（"若实施时发现...必须作为本 slice blocker 回 plan/review"），因此这不是 plan 设计缺陷，而是需要在 Slice 2 实施第一步验证的前置条件
- **直接证据**:
  - Plan §5.4 对既有 timeout 的断言
  - `dayu/host/compaction_operation.py:186-196` 未发现 `asyncio.wait_for`
  - `dayu/engine/contracts/runner_spec.py:315-318` 确认 `default_timeout_seconds` 必须为正
  - `dayu/engine/runners/openai/runner.py:358` 确认 Runner HTTP transport 使用该 timeout
- **影响**: 中等。若 compactor 没有 timeout，Slice 2 按 plan 自身规则被 blocked，需要回 plan 补充 timeout 或接受 force unlock。不影响 plan 的 architecture 方向
- **建议改法和验证点**:
  1. Slice 2 实施第一步：验证 compactor LLM 调用路径是否受 `RunnerSpec.default_timeout_seconds` 约束
  2. 若不受约束：在 Slice 2 中为 compactor proposal call 增加 `asyncio.wait_for`（复用既有 `RunnerSpec.default_timeout_seconds`），或回到 plan gate 讨论替代方案
  3. 不可绕过此检查直接实施 drain 逻辑
- **修复风险（低）**: plan 已有显式 blocker gating condition；实施时补充 timeout 不改变 architecture
- **严重程度（中）**
