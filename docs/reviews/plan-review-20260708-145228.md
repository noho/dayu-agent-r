# Plan Review: 收敛 prompt 与 interactive 的 --detail / --thinking 清理逻辑

- **Reviewed target**: 收敛 prompt 与 interactive 的 `--detail` / `--thinking` 清理逻辑，防止漂移
- **Scope**: `dayu/cli/commands/prompt.py`、`dayu/cli/commands/interactive.py`、`dayu/cli/arg_parsing.py`、`dayu/cli/thinking.py`、`dayu/cli/activity.py`、`dayu/cli/run_view.py`、`dayu/cli/runtime_display.py`、`dayu/service/entrypoint_runtime.py`
- **Review date**: 2026-07-08

## Assumptions Tested

1. prompt 与 interactive 的 `_new_thinking_renderer()` 实现完全相同 → **确认**（prompt.py:332-339 vs interactive.py:427-434，逐字相同）
2. `--detail` / `--no-detail` 参数注册在两个命令中重复 → **确认**（arg_parsing.py:449-463 vs 487-501，逐行相同）
3. dedupe 过滤逻辑在 CLI 层有三处独立实现 → **确认**（activity.py:136-146、run_view.py:275-285、thinking.py:95-103）
4. Service 层也有独立的 dedupe 过滤 → **确认**（entrypoint_runtime.py:1236-1238）
5. thinking 优先于 activity 的清理时序在两处独立维护 → **确认**，但已由 `RuntimeDisplayController` 协调（runtime_display.py:124-134）

---

## Findings

### 01-未修复-低-`_new_thinking_renderer()` 重复定义是明确漂移点

- **位置**: prompt.py:332-339、interactive.py:427-434
- **问题类型**: 最佳实践偏离 / 过度耦合（反向：耦合不足导致漂移）
- **当前写法**: 两个命令文件各定义一个完全相同的 `_new_thinking_renderer()` 私有函数，返回 `CliThinkingRenderer(options=CliThinkingRendererOptions(enabled=True))`
- **反例/失败场景**: 如果未来 thinking renderer 需要新增参数（如 `terminal_columns`），必须同时修改两处；只改一处即产生行为漂移，且不易通过测试发现
- **为什么有问题**: 违反 AGENTS.md 编码硬约束"重复逻辑必须抽取"
- **直接证据**: prompt.py:332-339 与 interactive.py:427-434 逐字相同，均为 5 行函数体
- **影响**: 实施 Agent 只改一处即漂移；review 不易发现因为两个文件距离远
- **建议改法和验证点**: 从 `dayu/cli/thinking.py` 或 `dayu/cli/runtime_display.py` 导出一个公共工厂函数 `new_enabled_thinking_renderer() -> CliThinkingRenderer`，两个命令改为导入调用。验证：现有 thinking renderer 测试不变，补充一个直接测试公共工厂的用例
- **修复风险**: 低
- **严重程度**: 低（当前代码正确，风险在维护期）

### 02-未修复-低-`--detail` 参数注册重复，与 `--thinking` 已有公共 helper 形成不对称

- **位置**: arg_parsing.py:449-463（prompt 命令）、arg_parsing.py:487-501（interactive 命令）
- **问题类型**: 最佳实践偏离
- **当前写法**: `--detail` / `--no-detail` 的互斥组注册在 `_register_prompt_command()` 和 `_register_interactive_command()` 中逐行复制；而 `--thinking` / `--no-thinking` 已通过 `_add_agent_execution_arguments()` 共享
- **反例/失败场景**: 如果需要给 `--detail` 增加新选项（如 `--detail=activity` 多值模式），必须同步修改两处注册代码；漏改一个命令即产生参数解析不一致
- **为什么有问题**: `--thinking` 已有共享路径证明这个模式可行；`--detail` 不共享是历史遗留，不是设计意图。AGENTS.md 要求"重复逻辑必须抽取"
- **直接证据**: arg_parsing.py:449-463 与 487-501 的 `detail_group` 注册代码逐行相同；`--thinking` 在 `_add_agent_execution_arguments()`（行 669-724）中已共享
- **影响**: 新增或修改 `--detail` 行为时必须记得改两处，否则漂移
- **建议改法和验证点**: 抽取 `_add_display_arguments(parser)` helper（类似 `_add_agent_execution_arguments`），内部注册 `--detail` / `--no-detail`。prompt 和 interactive 各调用一次。验证：现有 detail 相关 argparse 测试不变
- **修复风险**: 低
- **严重程度**: 低

### 03-未修复-低-dedupe 过滤模式在 CLI 层三处独立实现，存在语义漂移风险

- **位置**: activity.py:136-146、run_view.py:275-285、thinking.py:95-103
- **问题类型**: 最佳实践偏离 / 重复逻辑
- **当前写法**: 三个 renderer 各自维护 `_seen_dedupe_keys` 集合和 `_last_event_sequence`，各自实现相同的"dedupe key 去重 + event_sequence 乱序过滤"模式。实现细节略有差异：thinking.py 行 98-100 的 event_sequence 检查缺少 `is not None` guard（直接 `thinking.event_sequence < self._last_event_sequence`），而 activity.py 和 run_view.py 有 `is not None` guard
- **反例/失败场景**: thinking.py 缺少 `is not None` guard 意味着如果 `event_sequence` 为 `None`，`<` 比较会抛 `TypeError`。虽然当前 DTO 保证 `event_sequence` 非 `None`，但这是一个潜在的防御性缺口，且与 activity/run_view 的防御性写法不一致
- **为什么有问题**: AGENTS.md 要求"重复逻辑必须抽取"；三处独立实现中已有细微差异（`is not None` guard），证明漂移已经开始
- **直接证据**: activity.py:138-143 有 `activity.event_sequence is not None and self._last_event_sequence is not None` 双 guard；thinking.py:98-100 只检查 `self._last_event_sequence is not None`，未检查输入 DTO 的 `event_sequence`
- **影响**: 如果未来修改 dedupe 规则（如改为滑动窗口），必须同步三处；当前已有的细微差异可能在极端输入下导致行为不一致
- **建议改法和验证点**: 考虑两种路径：(a) 轻量方案 — 提取一个 `_filter_deduped_event()` 模块级私有函数到 `dayu/cli/runtime_display.py`，三个 renderer 调用；(b) 更重方案 — 定义 `DedupeState` dataclass 封装 seen_keys + last_sequence + 过滤逻辑。推荐 (a)，因为它不引入新抽象层，只消除重复。验证：同步修复 thinking.py 的 `is not None` guard，补充边界测试（`event_sequence=None` 的输入）
- **修复风险**: 低
- **严重程度**: 低（当前代码在正常输入下正确）

### 04-未修复-低-Service 层 dedupe 与 CLI 层 dedupe 是有意分层，不应合并

- **位置**: entrypoint_runtime.py:1236-1238 vs activity.py/thinking.py/run_view.py 的 dedupe
- **问题类型**: 非此 finding 的问题 — 确认当前分层合理
- **当前写法**: Service 层 (`_emit_entrypoint_thinking_from_host_event`) 做 run_id 过滤和 dedupe key 去重后，才调用 CLI 回调；CLI renderer 再做自己的 dedupe key 去重和 event_sequence 过滤
- **为什么不应合并**: Service 层 dedupe 防止重复事件到达 UI 回调（减少跨层传输），CLI 层 dedupe 是 renderer 内部的防御性检查（防止回调被意外重复调用）。两层职责不同：Service 层过滤 Host event 投影噪声，CLI 层保护渲染器内部状态。合并会违反分层架构约束（UI -> Service -> Host -> Engine）
- **直接证据**: entrypoint_runtime.py:1232-1238 的 Service 层只检查 `dedupe_key`，不做 `event_sequence` 排序；CLI renderer 同时做 dedupe key + event_sequence。合并意味着 Service 层需要理解 CLI 渲染时序，违反"设计下层组件接口时，必须假设上层组件不存在"
- **建议**: 不合并，保持当前分层

## prompt vs interactive 必须保留的差异

以下差异反映了 prompt（单轮）和 interactive（多轮 REPL）的本质区别，不应硬合并：

| 维度 | prompt | interactive | 为什么不能合并 |
|---|---|---|---|
| Activity 展示载体 | 独立 `CliActivityRenderer` | `InteractiveRunView`（含 activity + transcript 双模式） | interactive 需要 view mode 切换（activity ↔ transcript），prompt 不需要 |
| Renderer 生命周期 | 整个命令生命周期一个 renderer | 每轮 REPL 循环创建新 `thinking_renderer`（行 557） | interactive 每轮需要独立的 dedupe 状态，防止跨轮去重误判 |
| Terminal result 渲染 | `_render_prompt_terminal_result()` | `run_view.render_terminal_result()` 或 `render_interactive_terminal_result()` | interactive 有 run_view 模式切换，渲染路径不同 |
| 取消路径 | `_cancel_prompt_turn_after_local_request()` | `_cancel_interactive_turn_after_first_sigint()` | interactive 需要处理轮次索引和 REPL 循环状态 |

## 架构边界验证

- **分层约束（AGENTS.md）**: 未发现违反。所有 `--detail` / `--thinking` 逻辑都在 CLI 层（`dayu/cli/`），不向 Service/Host 泄漏 UI 实现细节。`RuntimeDisplayController` 及其 Protocol（`RuntimeActivityDisplay`、`RuntimeThinkingDisplay`）定义在 `dayu/cli/runtime_display.py`，属于 CLI 层公共基础设施
- **docstring/type 约束**: 所有相关函数和类均有完整中文 docstring，类型标注完整。未发现 `object`、`Any` 或无类型参数
- **`dayu.runtime` 边界**: CLI 层的 `runtime_display.py` 在 `dayu/cli/` 下，不属于 `dayu.runtime`，不违反 `dayu.runtime` 的 import 约束

## 防漂移测试建议

1. **工厂函数一致性测试**: 如果抽取公共 `_new_thinking_renderer()`，需测试返回值的 `enabled` 属性为 `True`，且后续可扩展新参数
2. **argparse 对称性测试**: 如果抽取 `_add_display_arguments()`，需测试 prompt 和 interactive 两个子解析器都注册了 `--detail` / `--no-detail`，且互斥行为一致
3. **dedupe `is not None` guard 边界测试**: 为 thinking renderer 补充一个 `event_sequence=None` 输入的测试用例，验证不抛异常
4. **跨命令行为一致性测试**: 一个参数化测试覆盖 prompt 和 interactive 在 `--detail` / `--thinking` 各组合下的行为，确保两命令语义一致

## Residual Risks

- dedupe 逻辑的 `is not None` guard 差异（thinking.py vs activity.py/run_view.py）当前不触发，但如果 Host event DTO 的 `event_sequence` 语义变化，可能暴露。建议作为 tech debt 跟踪
- Service 层 dedupe 和 CLI 层 dedupe 的 `seen_dedupe_keys` 集合独立增长，在极端长会话下可能消耗较多内存。当前不是问题，但值得监控

## Final Plan Review Conclusion

**pass-with-risks**

当前代码功能正确，`RuntimeDisplayController` 已经有效协调 thinking/activity 时序。收敛方案的目标成立（消除重复、防止漂移），但收益有限（三处重复均为 5-10 行的简单逻辑）。建议实施时：

1. **必做**: 抽取公共 `_new_thinking_renderer()` 工厂函数（消除最明确的漂移点）
2. **推荐**: 抽取 `_add_display_arguments()` 注册 helper（与 `--thinking` 的共享路径对称）
3. **可选**: 提取 dedupe 过滤的轻量公共函数到 `runtime_display.py`（消除三处重复，修复 `is not None` guard 差异）
4. **不做**: 合并 Service 层和 CLI 层 dedupe（违反分层）、合并 prompt/interactive 的 renderer 生命周期管理（本质差异）

所有修改均为 CLI 层内部重构，不影响 Service/Host/Engine 边界，不触发 README 更新。
