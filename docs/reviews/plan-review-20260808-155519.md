## Controller candidate correction assessment

Controller提出把soft ratio候选改为`0.018`并把ordinary hard bound改为`25 calls/Run`。只读owner复核结论如下：

| Candidate | 结论 | Direct basis / remaining gap |
| --- | --- | --- |
| `floor(1,048,576 * 0.018)=18,874` | 阈值计算成立 | `ContextBudgetPolicy`按ratio向下取整派生threshold |
| initial seq5 ordinary `9,048 < 18,874` | 成立 | 首Run可进入provider，不会在空history上尝试有效baseline |
| same-Run seq104/115 continuation `19,174/20,316 > 18,874`仍dispatch | 成立 | `CONTINUATION` soft/hard pressure均为`ALLOW_DISPATCH` |
| first post-tool seq125 ordinary `20,363 > 18,874`可触发baseline | 对旧Trial2 typed input成立 | 该row的owner值就是`predicted_input_tokens=20,363`；fresh floor=0/profile/prompt仍须持久校准，不应称精确ordinal保证 |
| no-tool baseline accepted后，下一条FY2025 pre-start不会提前触发第二operation | **没有owner证据，仍是plan blocker** | 现有accepted compact sample的immediate post-compact prediction为21,776，下一ordinary prediction为20,902，均高于18,874；它们不是seq125 exact replay，不能证明必然失败，但足以否定“已证明安全” |
| hard ordinary bound改为`6*25=150`、reconnect `7*25=175` | 成立 | 24个loop calls加最多1个force-answer call |

因此`0.018`不能只替换ratio后保留当前Phase A顺序。更可信、且符合现有owner boundary的最小scenario correction是：

1. 首Run完成FY2024真实工具证据；
2. 让紧接着的FY2025 acquisition input成为候选baseline trigger，而不是先发送no-tool retention；该pre-start operation的
   `source_boundary`只含已completed FY2024 material，FY2025请求仍是不可compact的current anchor；
3. baseline accepted后，同一Run走`POST_COMPACT` dispatch。soft pressure在该stage允许dispatch，且18,874远低于524,288 hard
   threshold的现有candidate band；随后同Run continuation也不会因soft pressure主动compact，因而可以自然取得FY2025工具证据；
4. FY2025 Run canonical succeeded后，下一条no-tool target ordinary才允许承担第二operation。该boundary可同时拥有previous
   FY2024 atom、completed FY2025 evidence、current unsupported percentages与真实caps；是否自然越线仍按owner prediction
   逐项验证，未触发则`needs-more-evidence`。

这条排序利用了current-anchor、`POST_COMPACT`和`CONTINUATION`现有语义，不需要hot switch或产品修改；但在plan正式采用前，仍须用
production candidate owner保存第一条FY2025 pre-start与下一target ordinary的typed sizing/material proof。当前plan尚未采用该排序，
所以review verdict不变。

## Findings

### MIMO-F18-RR3-001-未修复-高-Feasibility band比较了错误token字段，Phase A在当前上限内没有被直接数据证明可触发

- **位置**: Slice 2 Global frozen setup、Shared PTY adaptive phase state machine 与 plan-fix 第二轮 `F18-RRA-01` resolution。
- **问题类型**: owner错配 / sequencing / provider前置校准失真
- **当前写法**: 用 `20,316 < 20,971 < 20,998` 声称 ratio=0.02 形成“tool continuation先dispatch、随后ordinary首次越线”的provider-independent可行带；Phase A只允许 FY2024 tool Run 后最多三个 retention Runs。
- **反例/失败场景**: Trial2 canonical `CONTEXT_BUDGET_EVALUATED` rows中，seq125 ordinary为`predicted=20,363/conservative=20,363`；seq139为`19,274/20,575`；seq153为`19,707/20,998`；seq167、181、194的predicted也只有`19,988`、`20,104`、`20,339`。因此20,998不是参与pressure判定的值。按20,971 threshold，FY2024后前三个retention的owner prediction均未越线，Phase A会按计划自身规则seal `needs-more-evidence`，不会建立FY2024 previous atom。
- **为什么有问题**: usage-compatible路径的唯一决策值是`P_current = U_anchor + (E_current - E_anchor)`，canonical/public字段名为`predicted_input_tokens`；`conservative_input_tokens`只参与signed delta或在anchor失效时作为fallback。用后者代替前者违反Context Governance唯一owner，也让“provider调用前已证明可行”这一授权前提不成立。
- **直接证据**:
  - `docs/host/design.md` Context Governance usage-anchor段明确：anchored路径以`P_current`比较固定threshold；public `predicted_input_tokens=P_current`。
  - `dayu/host/context_budget.py::_pressure_and_decision`只接收`predicted_input_tokens`派生pressure/action。
  - Trial2只读typed rows：seq139 `predicted_input_tokens=19274`、`conservative_input_tokens=20575`；seq153 `19707/20998`，两条`pressure_level=normal`、`budget_decision=allow_dispatch`。
- **影响**: 三条真实MiMo链都会基于错误calibration进入provider gate，最直接结果是Phase A全部自然non-trigger并消耗provider预算；B2 previous-vs-new replacement、repair、fallback与reconnect均不可达。即使fresh usage有差异，也只能说明结果随机，不能恢复当前plan声称的provider-independent direct proof。
- **建议改法和验证点**:
  1. 只用canonical `predicted_input_tokens`/anchor diagnostic重做阈值校准，逐候选保存`U_anchor/E_anchor/E_current/P_current`、stage、pressure与decision；禁止把conservative estimator值直接当anchored decision。
  2. 重新设计baseline与FY2025 acquisition的相对边界。`0.018`的可信候选不是“先no-tool baseline、再FY2025”，而是让FY2025 acquisition input自身触发只覆盖FY2024的baseline，再由同Run post-compact dispatch取得FY2025；第二次operation开始前FY2025 completed evidence必须已经进入eligible boundary。
  3. 在不调用新provider的前提下，先用既有typed Trial2 rows与production owner做dry feasibility table；若不存在满足上述不等式的固定profile/cadence，应先修scenario，而不是把三条必seal链当正式观察。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### MIMO-F18-RR3-002-未修复-高-`max_iterations=24`不能推出单Run provider-call硬上界24

- **位置**: Slice 2 Evidence-calibrated execution matrix、Validation与 plan-fix `F18-RRA-02` resolution。
- **问题类型**: 资源治理契约错误 / budget不可执行
- **当前写法**: 把每Run `max_iterations=24`机械乘以Run数，声明六Run/七Run的ordinary provider-call硬上界分别是144/168。
- **反例/失败场景**: standard-256k冻结`fallback_mode=force_answer`。若第24个iteration仍返回工具调用，Engine在loop budget耗尽后调用`_fallback_after_tools`，再由`_run_force_answer`发起第25次真实Runner/provider call。六Run最多150次，七Run最多175次；terminal后checkpoint无法阻止同一Run内已经发生的额外调用。
- **为什么有问题**: `max_iterations`拥有普通Agent loop iteration语义，不拥有包含force-answer在内的全部provider call语义。计划把两个不同owner的上限合并，且没有冻结`raise_error`或其它可消除额外调用的合法policy。
- **直接证据**:
  - `dayu/engine/agent.py::run_messages`先执行`range(max_iterations)`中的Runner call；最后一轮工具结果后进入`_fallback_after_tools`。
  - `dayu/engine/agent.py::_run_force_answer`再次调用`_run_runner_iteration`。
  - `dayu/config/execution_profiles.json`的standard-256k AgentPolicy为`max_iterations=24`且`fallback_mode=force_answer`。
- **影响**: execution index无法同时证明actual calls不超过matrix与production policy未改变；三链最坏可比计划多21次ordinary provider call，违反用户要求的bounded minimal observation。
- **建议改法和验证点**:
  1. 保持production policy时，将单Run typed硬上界改为25，matrix改为`6*25=150`、`7*25=175`，并重新核对1800秒预算；或在首opener前合法冻结另一个明确允许的policy，但不得运行中突变。
  2. 单独记录loop iterations、continuation calls与force-answer call；用runner-call manifest count验证，而不是从Run terminal数反推。
  3. 若外部harness声称可在第24次后硬停，必须先给出实时call gate的现有owner与直接测试；terminal后统计不是pre-call enforcement。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### MIMO-F18-RR3-003-未修复-高-`2 operations * 5 calls`不是当前Host policy的per-chain硬上界

- **位置**: Slice 2 Global frozen setup、Evidence-calibrated execution matrix及operation stop规则。
- **问题类型**: 资源治理契约错误 / 状态机遗漏
- **当前写法**: profile冻结`max_reactive_compactions_per_run=2`，随后把每链最多2 operations、每operation最多5 calls推导为compactor call硬上界10。
- **反例/失败场景**: Phase A已产生一个proactive baseline后，任一后续FY2025/target Run仍可因真实provider overflow在同一Run内自然产生最多两个reactive operations；该链可达3 operations/15 compactor calls。若某个Run自身先有proactive operation，post-compact dispatch后仍可进入reactive operation。计划又明确把reactive FY2025 target列为合法路径，不能假设reactive数量恒为零。
- **为什么有问题**: Host typed policy只限制“单Run reactive次数”，而proactive每Run/input另有唯一一次状态机不变量；没有per-chain operation policy。当前plan只明确在Run terminal后核对ordinary calls，也没有证明冻结PTY harness能在active Run的第三个operation/provider call前实时取消。
- **直接证据**:
  - `dayu/host/context_policy.py::ContextBudgetPolicy.max_reactive_compactions_per_run`的docstring与校验均定义为单Run上限，当前值为2。
  - `docs/host/design.md` Context Governance contract明确区分每Run/input一个proactive operation与同Run最多`max_reactive_compactions_per_run`个reactive operations。
  - `dayu/host/engine_ingest.py`只用当前Run已提交reactive count比较该字段，不读取chain累计operation数。
- **影响**: compactor真实调用可能越过10而harness尚未取得Run terminal；“到operation/call cap即停”缺少可执行owner，formal observation budget不能被复核为hard bound。
- **建议改法和验证点**:
  1. 从proactive与reactive两个owner重算真正最坏operation/call上界；或证明已有harness在每个`CONTEXT_COMPACTION_REQUESTED`前/后能实时、无竞态地阻止第三个operation继续调用provider。
  2. 若必须保持10-call预算，固定profile与phase必须排除会超过两operation的合法路径，并给出产品状态机上的直接证明；不能只写执行意图。
  3. execution index分别记录proactive/reactive operation及attempt count，并对所有在途Run做cap后zero-new-call断言。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### MIMO-F18-RR3-004-未修复-中-FY2025同Run reactive compact不能把刚产生的工具结果放进其immutable source boundary

- **位置**: Slice 2 Phase B中“FY2025 tool Run取得真实工具结果后的reactive target也合法”的分支。
- **问题类型**: material owner错配 / 不可达分支
- **当前写法**: 允许FY2025工具结果后的reactive operation作为target，前提是其immutable initial input直接含FY2025 evidence material。
- **反例/失败场景**: Engine在同一active Run的tool follow-up遇到overflow后，Host reactive path重新调用`build_pre_dispatch_compact_material_view`。该builder把delta终点固定为当前Run的`USER_INPUT_ACCEPTED.event_sequence`（排他边界）；同Run后续`TOOL_RESULT_ACCEPTED`序列更大，不进入`material_view.material_blocks`。`_frozen_reactive_material_blocks`只追加current input anchor，不追加active-run工具结果。因此该reactive input不可能含本Run刚取得的FY2025 canonical evidence。
- **为什么有问题**: current input中“请读取FY2025”或模型工作消息不等于accepted tool evidence；analyzer也不得补足。计划虽规定缺项即seal，但仍把结构上必缺项的分支描述为合法target，会错误消耗第二operation并误导coverage判断。
- **直接证据**: `dayu/host/compact_material.py::build_pre_dispatch_compact_material_view`以`end_sequence=current_event.event_sequence`构造delta；`dayu/host/engine_ingest.py::_frozen_reactive_material_blocks`只使用该pre-dispatch view加current anchor。
- **影响**: 自然reactive overflow只可能成为premature-boundary/needs-more-evidence，不能覆盖B2 target；若它已消耗第二operation，本链必须停止，不能再用后续ordinary operation补偿。
- **建议改法和验证点**:
  1. 从合法target集合删除“同一FY2025 Run工具结果后的reactive boundary”，把它明确归类为premature/non-covering observation；或另开产品设计goal改变reactive material contract，本F18不得在scenario层假设。
  2. target gate必须逐label/ref验证FY2025 evidence来自target开始前已completed Run，而非current input、active working messages或answer文本。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
