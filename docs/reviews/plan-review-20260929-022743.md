## Findings

### F1（低-中）：初始 whole-kind typed（零候选）的 job 侧形状未钉死，「零候选摘要」措辞在 job 侧不成立

plan 42/44 行称首候选循环前的初始 whole-kind typed「仍传原始异常与零候选摘要」。direct producer 侧成立：`_run_direct_stream_producer` 4314–4331 对 download 异常构造 `_empty_download_summary_from_request` 结构化零候选摘要 + typed public failure。但 job 侧该原异常不携带 summary，不落 plan 50 行的新 typed catch（那只覆盖「携带已验证 summary 的私有 typed adapter failure」），而是落 `_run_download_job` 4962 行普通 `except Exception` → `_save_failed_from_exception` → `result_summary={}`（`_EMPTY_SUMMARY`，ingestion_runtime.py:172）+ `message=str(exc)`（typed message 模板「source integrity preflight 失败: unsafe_publication」）。证据：5935 行 `result_summary or dict(_EMPTY_SUMMARY)`、6007 行 `message=str(exc) or type(exc).__name__`。

后果：(1) 与 `_save_download_unsupported`（5972–5978 用结构化零候选 `to_json_summary()`）同为零候选失败却形状不对称；(2) job failure message 与 direct/public 的安全 `safe_message`（「本地来源完整性预检失败」）不同源——typed message 当前不含路径/URL，无泄漏，但违反「同一业务事实从同一真源派生」的同源约束；(3) plan 42 行「零候选摘要」措辞会让实施者无法判断 job 侧应写 `{}` 还是结构化零候选摘要。注意真实 CLI 验证（plan 78 行）正是 whole-kind preflight 场景，但只覆盖 direct 入口。

建议裁决方向（二选一）：(a) plan 明确初始 whole-kind typed 在 job 侧也消费 `_download_public_failure_from_exception` 安全消息并写结构化零候选摘要（与 unsupported source 对齐），或 (b) plan 明确该形状差异为 S1 接受残余并登记去向。不阻塞主链（无已发布文档被掩盖），但当前文本存在实施歧义。

### F2（低-中）：私有 typed adapter failure 的类型定义位置与 `_classify_direct_error`/`_download_public_failure_from_exception` 的 cause 解包机制未钉死

`_classify_direct_error` 7084–7089 与 `_download_public_failure_from_exception` 6852–6897 均以 `isinstance(exc, SourceIntegrityPreflightError)` 识别 typed。私有 adapter failure（总控 52 行称 `FinsSourceDownloadAdapterFailure`）包装后 `exc` 本身不是 typed preflight，两函数会把它落 EXECUTION/generic——分类与 public reason 同时失真。plan 46 行「对封闭 preflight cause 仍由 Fins 唯一映射四值 public reason」要求按 cause 映射，但未指明解包发生在函数内（isinstance 私有类型 + 读 cause）还是调用点（typed catch 先解包再传入）。

另：`FinsSourceDownloadAdapter` 协议定义在 `ingestion_runtime.py:586`，cn_pipeline.py:39 已 import 该模块，故私有 failure 类型定义在 `ingestion_runtime.py`（允许文件内）时依赖方向自然闭合；但 plan 全文未写明该类型的定义位置与模块归属。方向唯一、不阻塞，但两处写法分叉会直接影响 job/direct 同源断言的写法。

### F3（低）：`_summary_from_pipeline_result` 复用与 `ok/cancelled` 封闭校验的张力未指明解法

`cn_pipeline.py:1424–1426` 拒绝非 `ok/cancelled` 的 status；私有 abort 快照 status 为 `integrity_failed`（plan 42 行自定）。plan 46 行要求 adapter「复用 `_summary_from_pipeline_result`」且「不能把异常快照伪装为 `ok`」——实施必须给该函数加私有入口或拆出内部投影 helper，plan 未钉死方式。方向明确，不阻塞。

### F4（低）：wait scope 文案的 JSON 帧字段名未指定

plan 60 行定了常量名与逐字文本，但未定该说明在 `_failure_message` JSON 帧内的字段名。逐字断言文本即可兜底，不阻塞；若总控希望帧 schema 稳定，可在裁决时顺手钉字段名。

### F5（低/观察）：job 二次失败 WARN 的既有 `exc_info=True` 会把二次异常 traceback 写入日志

`_save_failed_from_exception` 6009–6015 与 `_save_download_unsupported` 5981–5986 的 WARN 均带 `exc_info=True`，二次异常（如 job store OSError）traceback 可能含路径进 operator 日志。S1 复用该 pattern 会继承此行为；plan 90 行 `fins-other-raw-diagnostics-audit` 覆盖 generic job `str(exc)` 消息审查，未明确含 WARN `exc_info`。建议该 WU 登记时补明。非 S1 引入，非阻塞。
