## Findings

### 1-未修复-中-[F11-S1-01] `parse_context_compaction_attempt_rejected_terminal_binding` 中 validator 与 parser 对 `parse_successful_runner_response_identity` 存在双重调用

- **入口/函数**: `parse_context_compaction_attempt_rejected_terminal_binding` (`context_events.py:1634`)
- **文件(行号)**: `dayu/host/context_events.py:1649`（validator 调用），`dayu/host/context_events.py:1654`（parser 再次调用）
- **输入场景**: 任何包含非 null `successful_response_identity` 的 `CONTEXT_COMPACTION_ATTEMPT_REJECTED` payload
- **实际分支**: `validate_context_compaction_attempt_rejected_payload` 在 line 1625 调用 `parse_successful_runner_response_identity(successful_response_identity)` 完成校验；随后 `parse_context_compaction_attempt_rejected_terminal_binding` 在 line 1654 再次调用同一函数解析同一个 payload
- **预期行为**: validator 负责 payload 级 schema 校验（字段存在性、类型、category-identity 关系）；parser 负责构造 typed binding。validator 已调用 `parse_successful_runner_response_identity` 证明 identity shape 合法，parser 应复用同一已验证结果，或至少不应完全重新解析
- **实际行为**: `parse_successful_runner_response_identity` 对同一 JSON payload 被执行两次（一次在 validator，一次在 parser），包括 `_require_exact_fields` 的字段集合校验、`build_runner_request_identity` 的构造、`client_correlation_id` 的 canonical 校验等全部步骤
- **直接证据**:
  - `context_events.py:1620-1625`：validator 分支中 `parse_successful_runner_response_identity(successful_response_identity)`
  - `context_events.py:1650-1654`：parser 中 `else parse_successful_runner_response_identity(_required_mapping(payload, _FIELD_SUCCESSFUL_RESPONSE_IDENTITY))`
  - 两处调用之间没有任何 mutation 或 boundary change
- **影响**: 不是正确性 bug，但违反 AGENTS.md "多个消费者需要同一语义时，必须复用同一个 source of truth" 原则——validator 与 parser 各自独立重建 typed identity，增加了未来 identity schema 变更时两个调用点漂移的风险。当前行为是过度防御性编程，parser 应该信任 validator 已完成的契约校验
- **建议改法和验证点**:
  1. 让 validator 校验 identity shape 后缓存已解析的 typed identity（例如通过 `_validate_*` 返回可选的 pre-parsed identity）
  2. parser 接收该缓存值而非重新解析
  3. 或保守方案：保持双重调用但明确注释这是 intentional defense-in-depth，并在 parser docstring 中记录 validator 已做前置校验
- **修复风险（低）**: 涉及 validator/parser 的 contract 微调，但两者已在同一模块且调用关系明确
- **严重程度（中）**: 违反语义复用原则，长期维护风险

### 2-未修复-低-[F11-S1-02] `_resolve_compactor_response_identity` 全页 cursor 推进检查对退化 page reader 实现的防御不完整

- **入口/函数**: `_resolve_compactor_response_identity` (`tool_trace.py:567`)
- **文件(行号)**: `dayu/host/durable/tool_trace.py:608-634`
- **输入场景**: `read_run_events_by_types_page` 返回满页（`len(page) == _COMPACTOR_TERMINAL_SCAN_PAGE_SIZE`），但返回行中存在重复 `event_sequence` 或非严格递增的序列
- **实际分支**:
  - 页内检查（line 610）：`if row.event_sequence <= previous_sequence` — 能捕获连续两行的非严格递增
  - 跨页检查（line 630）：`if previous_sequence <= cursor` — 只检查最后一行的 sequence 是否超过本次查询的起始 cursor
- **预期行为**: 任何形式的 cursor 不推进都应 fail closed
- **实际行为**: 页内检查已覆盖连续行的非递增情况。但若 page reader 返回 `[seq=5, seq=10, seq=6, seq=128]`（非单调但在页内每个行对前一行递增），页内检查会通过（5→10 OK, 10→6 触发 line 610 错误）。然而若 page reader 返回 `[seq=100, seq=101, ..., seq=227]`（满 128 行），但 `after_event_sequence=0` 时这些行实际来自不同的 run——`read_run_events_by_types_page` 已按 `run_id` 过滤，所以此场景不应发生。防御有效但不完整：若未来 EventLog reader 实现变化且不再保证 `after_event_sequence` 语义，则跨页检查只验证 max(sequence) > cursor，不验证每行都 > cursor
- **直接证据**: `tool_trace.py:608-634`；页内检查已在 `test_compactor_response_resolver_rejects_non_advancing_cursor` 中测试，但该测试通过 monkeypatch 替换整个 `read_run_events_by_types_page` 为返回重复行的 stub，未测试 page reader 返回乱序但单调解的情况
- **影响**: 当前实现正确（因为 `read_run_events_by_types_page` 的 SQL 保证 `ORDER BY event_sequence` 且 `WHERE event_sequence > ?`），但防御层依赖下游实现契约而非在本层做完整校验。若未来 EventLog reader 行为变化，可能漏过退化
- **建议改法和验证点**: 在页内循环中对每行增加 `row.event_sequence > cursor` 的显式断言（而非仅依赖 `previous_sequence` 的递推），使防御不依赖循环内状态累积；或在 docstring 中明确声明本函数依赖 `read_run_events_by_types_page` 的 `after_event_sequence` 契约
- **修复风险（低）**: 增加一行断言，不影响现有行为
- **严重程度（低）**: 当前无实际 bug，但防御层设计可更健壮

## Open Questions

1. **`_POST_SUCCESS_REJECTION_CATEGORIES` 与 `_NO_SUCCESS_REJECTION_CATEGORIES` 的闭集是否应文档化为 public contract？** 当前两个 frozenset 是模块级私有常量。如果未来新增 failure category 未加入任一集合，validator 会静默接受该 category 的任意 identity 状态（既可为 null 也可非 null）。建议在 `context_events.py` 的 `validate_context_compaction_attempt_rejected_payload` docstring 中明确说明这两种 category 集合是 closed set，并注明新增 category 必须显式选择所属集合。

2. **`CompactorResponseResolutionError` 在 `analysis_input.py` 中 re-raise 后，调用方的错误处理路径是什么？** 当前 `CompactorResponseResolutionError` 继承自 `HostDurableError`，在 `analysis_input.py:649-650` 被 re-raise。需要确认 Service/CLI 层对此类错误的用户可见表现（是 crash with traceback 还是 structured error report）。这不阻塞 S1 acceptance，但建议在后续 integration 中验证。

## Residual Risk

1. **仓外 Tool Trace JSON consumer 的 v1→v2 迁移**：schema v2 增加了 `compactor_responses` 字段并改变了顶层 key 集合。仓外自建 Tool Trace report consumer 如依赖 v1 shape 需要显式升级。已在 implementation artifact 中记录为 "assigned to later work unit"，本 review 确认为 acceptable residual risk。

2. **`CompactorResponseResolutionError` 传播到 Service/CLI 层的用户体验**：当前未在 S1 中实现用户可见的错误消息或 recovery 提示。若生产环境中 terminal payload 损坏，用户会收到 `HostDurableError` 的 generic message。建议在后续 integration slice 中增加 operator-readable 错误上下文。不阻塞 S1。

3. **`_COMPACTOR_TERMINAL_SCAN_PAGE_SIZE = 128` 的性能特性未经大规模数据验证**：当前测试使用小数据集（<10 个 terminal event）。若未来出现单 parent run 包含数百个 compaction attempt 的场景（例如 repair budget 极大且全部 rejected），keyset exhaustion 的 I/O 成本未被测试覆盖。当前 compaction attempt budget 上限使此场景在现实中极不可能发生，但仍建议在 S4 real-provider evidence 中记录最大 observed terminal scan page count。

4. **S1 未覆盖 `dayu/host/README.md` 的 `Agent更新约束` 章节要求**：README 已按 implementation artifact 声明更新了 Tool Trace resolver 与 compactor response 段落，内容与代码一致。无 residual README risk。
