### F01-未修复-中-async generator 异常传播机制未完全规格化

- **位置**: §3.1 owner decision 第2点、§6.3、§8.2 provenance matrix
- **问题类型**: 契约缺失
- **当前写法**: "re-raises typed provider errors, OSError, and execution exceptions across the stream/collector boundary so runtime receives their real type"
- **反例/失败场景**:
  当前 `run_cn_download_stream_impl` 是 async generator，其 collector 在 `CnPipeline.download_stream` 中迭代该 generator。当前实现中，workflow 通过 `yield PIPELINE_COMPLETED(payload={"result": _build_result(status="failed", ...)})` 报告失败——异常从未离开 generator。amendment 要求 typed exception 跨 generator 边界传播，但未指定：
  1. collector 是否仍 catch Exception 并转换？若是，provenance 二次丢失；若否，collector 如何知道不 catch？
  2. `CnDownloadAdapter.download()` 对 result dict 和 exception 的双重处理逻辑如何统一？
  3. 现有 `CnPipeline.download_stream` 的 `async for event in run_cn_download_stream_impl(...)` 循环在 generator 抛异常时的行为是否已被验证？

  直接代码证据：`cn_download_workflow.py:332` — `except Exception as exc` 把所有异常转为 `status="failed"` JSON。amendment 要求删除此转换，但 collector/adapter 的具体修改点未指定。

- **为什么有问题**: amendment 声称"不改 runtime/schema"，但 exception propagation 需要 collector 和 adapter 的行为变更。如果 collector 不改，它会继续把异常转为 `status="failed"` JSON，provenance 再次丢失。如果 collector 改了但 adapter 不知道，adapter 会收到非预期的异常而非 result dict。
- **直接证据**: `cn_download_workflow.py:110-172`（rebuild path）、`cn_download_workflow.py:329-366`（discovery path）— 所有 operation-terminal 异常都被 `except Exception` 捕获并转为 JSON result。amendment §3.1 说"re-raises across stream/collector boundary"但未指定 collector 的修改。
- **影响**: 实现 agent 可能只改 downloader 而不改 collector/adapter，导致 provenance 修复无效；或改了 collector 但 adapter 行为不一致导致运行时异常。
- **建议改法和验证点**:
  1. 在 §6.3 中显式指定 `run_cn_download_stream_impl` 的哪些 `except Exception` 块需要改为 re-raise（只改 operation-terminal 块，保留 per-candidate 块）。
  2. 指定 `CnPipeline.download_stream` 的 collector 逻辑：当 generator 抛出 typed exception 时，collector 不 catch，直接传播给 adapter。
  3. 指定 `CnDownloadAdapter.download()` 的变更：删除 `status="failed"` 检查，改为 try/except 捕获 typed exception 并直接 re-raise。
  4. §8.2 provenance matrix 已有 discovery/storage/execution 三类传播测试，需补充：rebuild path exception propagation 测试。
  5. 验证点：`test_cn_download_workflow.py` 中测试 workflow generator 抛 `FinsDownloadProviderError` 时，adapter 收到的是同一 typed exception 而非 `status="failed"` result。
- **修复风险（低/中/高）**: 中 — 改动点明确但需要三个文件协调
- **严重程度（低/中/高/严重）**: 中

### F02-未修复-中-SEC auxiliary fatal/optional 边界需要逐项验证

- **位置**: §3.4、§6.5
- **问题类型**: 契约缺失
- **当前写法**: "A genuinely optional HEAD used only for metadata may still return None; its diagnostic is limited to a typed category/fixed event and contains neither URL nor raw exception. Optional metadata failure must not alter document disposition."
- **反例/失败场景**:
  当前 SEC downloader 有 7 个 catch-and-return-None/[] 的 auxiliary helper。amendment 正确区分了"optional metadata"和"required for resolution/discovery/direction/filtering"，但未给出每个 helper 的明确分类。以下是直接代码证据支持的逐项分析：

  | Helper | 当前行为 | 正确分类 | 证据 |
  |---|---|---|---|
  | `_resolve_company_via_browse_edgar_ticker` | catch RuntimeError → return None（ticker not found） | **必须传播** — 直接影响 company resolution | `sec_downloader.py:1174-1183` — caller 把 None 当 ticker-not-found |
  | `fetch_sc13_party_roles` | catch RuntimeError → return None | **必须传播** — 直接影响 direction evaluation | `sec_downloader.py:1357-1369` — caller 把 None 当方向不匹配 |
  | `_try_fetch_index_items` | catch RuntimeError → return [] | **必须传播** — 影响 candidate discovery | `sec_downloader.py:2085-2096` — empty list 减少 candidates |
  | `_try_fetch_index_header_documents` | catch RuntimeError → return [] | **必须传播** — 影响 candidate discovery | `sec_downloader.py:2126-2140` — 同上 |
  | `_try_fetch_primary_linked_html_files` | catch RuntimeError → return [] | **必须传播** — 影响 candidate discovery | `sec_downloader.py:2164-2178` — 同上 |
  | `_http_head` | catch RuntimeError → return None，无日志 | **可选** — 仅 metadata | `sec_downloader.py:1989-2001` — docstring 声明可选 |
  | `_filter_filings` (history) | catch RuntimeError → continue | **必须传播** — 影响 discovered filings count | `sec_pipeline.py:1200-1208` — silent skip 减少 candidates |
  | `_precheck_6k_filter` | catch RuntimeError → DOWNLOAD_FAILED | **必须传播** — 但需改为 typed error | `sec_pipeline.py:1720-1732` — DOWNLOAD_FAILED 是业务分类不是 provider error |

  关键反例：`_resolve_company_via_browse_edgar_ticker` 的 Block A（HTTP 失败）和 Block B（XML 解析失败）都被 catch 为 RuntimeError 并返回 None。caller 把 None 解释为"ticker not found"——这是 provider transport failure 被误标为业务结果的直接证据。

  类似地，`fetch_sc13_party_roles` 的网络失败返回 None，caller 把它解释为"方向不匹配"。

- **为什么有问题**: amendment 说"SEC auxiliary provider errors propagate"但没列出哪些 helper 需要改。如果实现 agent 只改了部分 helper（例如只改了 index 而没改 browse-ticker），provenance 修复不完整。更危险的是，如果 agent 把 `_http_head`（genuinely optional）也改成 propagate，会破坏正常的 optional metadata 降级行为。
- **直接证据**: 上表中每个 helper 的 line number 和 catch-return 模式。
- **影响**: 实现 agent 可能错误分类某些 helper，导致：(a) 必须传播的 helper 没传播 → provenance 仍然丢失；(b) 可选的 helper 被传播 → 正常降级行为被破坏。
- **建议改法和验证点**:
  1. 在 §3.4 或 §6.5 中增加明确的 helper 分类表，列出每个 helper 的名称、当前行为、正确分类（必须传播/可选）和修改方式。
  2. 对"必须传播"的 helper：catch 块改为 re-raise `FinsDownloadProviderError`（如果 caught exception 已经是 typed）或先映射再 re-raise。
  3. 对"可选"的 helper（仅 `_http_head`）：保留 catch-and-return-None，但日志改为 typed category + fixed safe event，不含 URL/raw exception。
  4. §8.4 SEC auxiliary failures 测试矩阵已覆盖大部分场景，但需补充：browse-ticker HTTP failure 传播测试、SC13 HTTP failure 传播测试。
  5. 验证点：每个 helper 的 owner test 证明 (a) provider failure 时返回正确类型（propagate or None），(b) 日志不含 URL/raw exception。
- **修复风险（低/中/高）**: 低 — 每个 helper 的修改方式明确
- **严重程度（低/中/高/严重）**: 中

### F03-未修复-中-downloader granular mapping 需要重构重试循环

- **位置**: §6.2
- **问题类型**: 不可直接实施
- **当前写法**: "Required categories: timeout, connection, HTTP status, protocol, unknown. HTTP status is retryable only for server-side status; timeout/connection are retryable; protocol is not."
- **反例/失败场景**:
  当前 CNINFO/HKEX downloader 的重试循环 catch `(httpx.HTTPError, json.JSONDecodeError, ValueError)` 并在重试耗尽后 raise `RuntimeError(f"... url={url} error={last_exc}")`。amendment 要求区分五类 transport category，但当前代码结构不支持：

  1. `json.JSONDecodeError` 和 `httpx.HTTPError` 在同一个 catch 块。JSONDecodeError 表示 provider 返回了 malformed JSON（应为 PROTOCOL non-retryable），但当前被一起重试且最终被当作 UNKNOWN retryable。
  2. `ValueError` 也在同一 catch 块。部分 ValueError 是 API misuse（如 ticker format，应保持 ValueError），部分是 provider response 问题（如 JSON schema 异常，应为 PROTOCOL）。当前代码不区分。
  3. `httpx.HTTPStatusError` 需要区分 4xx（non-retryable）和 5xx（retryable），但当前只看是否超过重试次数。

  直接代码证据：`cninfo_downloader.py:571-588`（`_http_get_json`）— catch 块同时 catch `httpx.HTTPError`、`json.JSONDecodeError`、`ValueError`。`cninfo_downloader.py:672-689`（`_http_download_bytes`）— 只 catch `httpx.HTTPError`，不含 JSONDecodeError。

  对比 SEC downloader：`sec_downloader.py:1747-1862`（`_execute_sec_request`）— 已有 granular `_sec_transport_category` 映射，区分 timeout/connection/HTTP status/protocol/unknown。CNINFO/HKEX 需要类似结构。

- **为什么有问题**: amendment 列出了需要的 categories 但没指定重试循环的重构方式。如果实现 agent 只在 raise 时做映射而不改 catch 块，`json.JSONDecodeError` 会被错误分类。如果 agent 把 `ValueError` 全部当作 provider error，API misuse（如 invalid ticker）会被误标为 provider transport。
- **直接证据**: `cninfo_downloader.py:571-588`（重试循环 catch 块）、`sec_downloader.py:885-986`（SEC 的 granular mapping 参考实现）。
- **影响**: (a) JSONDecodeError 被误标为 TIMEOUT/CONNECTION（retryable），导致无限重试 malformed response；(b) ValueError API misuse 被误标为 provider transport，导致用户看到"来源请求失败"而非"参数错误"。
- **建议改法和验证点**:
  1. 在 §6.2 中明确：重试循环需要为每个 caught exception 类型单独做 category 映射，而非在 raise 时统一映射。
  2. 指定 JSONDecodeError 的分类：PROTOCOL non-retryable（provider 返回了 malformed JSON）。
  3. 指定 ValueError 的分类规则：来自 provider response parsing 的 ValueError → PROTOCOL；来自参数校验的 ValueError → 保持 ValueError（不转为 provider error）。
  4. 指定 httpx.HTTPStatusError 的分类：status ≥ 500 → HTTP_STATUS retryable；status < 500 → HTTP_STATUS non-retryable。
  5. §8.1 transport matrix 已覆盖 timeout/connection/HTTP status/protocol/unknown，需补充：JSONDecodeError → PROTOCOL、ValueError API misuse → 保持 ValueError 的测试。
  6. 验证点：每个 category 的 owner test 证明 (a) 正确分类、(b) 正确 retryable flag、(c) safe message 不含 URL/raw exception。
- **修复风险（低/中/高）**: 中 — 需要重构重试循环结构
- **严重程度（低/中/高/严重）**: 中

### F04-未修复-低-rebuild missing_periods producer contract 测试缺口

- **位置**: §3.3、§6.4、§8.3
- **问题类型**: 测试缺口
- **当前写法**: "Rebuild with zero local documents, matching documents, failed local documents, and cancellation always emits the required `missing_periods` list."
- **反例/失败场景**:
  当前 `rebuild_cn_download_artifacts`（`cn_download_rebuild.py:106-124`）不包含 `missing_periods` key。`_summary_from_pipeline_result`（`cn_pipeline.py:1463-1467`）有 rebuild-only fallback。amendment 要求 rebuild producer always emit `missing_periods` 并删除 adapter fallback。

  §8.3 测试矩阵测试了**消费者**的 strict behavior（fake result 缺 `missing_periods` → adapter fail），但没有测试**生产者**是否真的 emit 了该字段。如果实现 agent 改了 adapter（删除 fallback）但忘了改 producer（加 `missing_periods`），rebuild path 会直接 crash——而这个 crash 只在真实 rebuild 运行时才暴露，不会被 producer-level 测试捕获。

- **为什么有问题**: 测试矩阵的 §8.3 只覆盖消费者侧（adapter strict validation），不覆盖生产者侧（rebuild actually emits the field）。这是一个 coverage gap。
- **直接证据**: `cn_download_rebuild.py:106-124` — result dict 没有 `missing_periods` key。§8.3 测试矩阵只描述 adapter behavior，不描述 rebuild producer output 测试。
- **影响**: 如果 producer 没改但 adapter 改了，rebuild path 会在运行时 crash。测试矩阵不会捕获这个 regression。
- **建议改法和验证点**:
  1. 在 §8.3 中增加 producer-level 测试：直接调用 `rebuild_cn_download_artifacts` 并断言 result dict 包含 `missing_periods` key 且值为 list。
  2. 测试覆盖：zero local documents、matching documents、failed local documents、cancellation 四种场景。
  3. 验证点：删除 producer 的 `missing_periods` 后，测试失败。
- **修复风险（低/中/高）**: 低 — 只需增加测试
- **严重程度（低/中/高/严重）**: 低

### F05-未修复-低-`_reason_code_from_exception` dead code 未在 amendment 中处理

- **位置**: §6.3
- **问题类型**: 过度耦合
- **当前写法**: amendment 要求删除 `status="failed"` → provider UNKNOWN 转换，但未提及 `_reason_code_from_exception` 函数。
- **反例/失败场景**:
  `_reason_code_from_exception`（`cn_download_workflow.py:809-814`）只在 `_build_result(status="failed", ...)` 路径中使用。如果 amendment 成功删除所有 operation-terminal 的 `status="failed"` 构建，该函数成为 dead code。但 per-candidate 路径（`_build_candidate_failed_result`）仍然使用 `_reason_code_from_exception`（通过 `cn_download_filing_workflow.py`）。

  实际上，`_reason_code_from_exception` 在 `cn_download_workflow.py:809-814` 定义，在 `cn_download_workflow.py:337`（discovery failure）和 `cn_download_workflow.py:147`/`353`（cancel check failure）使用。如果这些路径改为 re-raise，函数在 `cn_download_workflow.py` 中变为 dead code。但 `cn_download_filing_workflow.py`（frozen）可能有自己的 `_reason_code_from_exception` 或类似逻辑。

- **为什么有问题**: 不是 correctness 问题，但 dead code 如果不清理会误导 future contributor 认为这些路径仍然需要。
- **直接证据**: `cn_download_workflow.py:809-814` — 定义。`cn_download_workflow.py:337,147,353` — 使用点。amendment §5.5 explicitly excluded `cn_download_filing_workflow.py`。
- **影响**: 低 — dead code 不影响正确性但增加维护负担。
- **建议改法和验证点**:
  1. 在 §6.3 中增加：删除 `_reason_code_from_exception`（如果 operation-terminal path 不再需要）或保留（如果 per-candidate path 仍需要）。
  2. 验证点：AST/rg 证明该函数在 amendment 后只被 frozen 文件使用，或已从 non-frozen 文件删除。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F06-未修复-低-日志脱敏变更可能破坏现有测试断言

- **位置**: §6.2、§9 validation plan
- **问题类型**: 测试缺口
- **当前写法**: "Retry/HEAD diagnostics contain only operation kind, attempt count, and typed category/fixed safe event. No URL or `error={exc}`."
- **反例/失败场景**:
  当前 CNINFO/HKEX downloader 的日志包含 `url={url} error={last_exc}`（如 `cninfo_downloader.py:588`）。amendment 要求删除这些。但现有测试可能通过 log scanning 断言这些日志的存在。

  同时，SEC downloader 的 `_try_fetch_index_items` 等 helper 已经使用 `transport_category={_provider_error_category(exc).value}` 日志（`sec_downloader.py:2087`），不含 URL/raw exception。这证明 SEC 已部分遵循 amendment 的日志规范。但 CNINFO/HKEX 的日志尚未遵循。

  测试风险：如果现有 test_cn_download_runtime.py 或 test_cninfo_downloader.py 的测试通过 log scanning 断言 `url=` 或 `error=` 的存在，日志脱敏变更会导致测试失败。

- **为什么有问题**: amendment §9 的 validation plan 包含 "no `url=`, `error={exc}`, raw exception interpolation" 静态扫描，但未提及现有测试是否需要更新以匹配新的日志格式。
- **直接证据**: `cninfo_downloader.py:588` — `RuntimeError(f"GET JSON 失败: url={url} error={last_exc}")`。SEC 已有脱敏日志：`sec_downloader.py:2087` — `transport_category={_provider_error_category(exc).value}`。
- **影响**: 低 — 测试更新是常规工作，但如果不提前识别可能导致 review-fix 阶段的意外失败。
- **建议改法和验证点**:
  1. 在 §9 中增加：现有测试中任何 log scanning 断言需要同步更新以匹配脱敏后的日志格式。
  2. 验证点：`grep -rn "url=" tests/fins/test_cn*` 和 `grep -rn "error=" tests/fins/test_cn*` 列出所有需要更新的测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F07-未修复-低-adapter 对 legacy `status="failed"` result 的行为需显式测试

- **位置**: §6.3、§8.2
- **问题类型**: 测试缺口
- **当前写法**: "A fake/legacy workflow result containing `status="failed"` without a typed exception fails strict projection as `ValueError`; adapter must not guess provider."
- **反例/失败场景**:
  amendment 正确要求 adapter 对 legacy `status="failed"` result fail closed（raise ValueError）。但这个行为在 §8.2 provenance matrix 中没有明确测试。矩阵测试了"typed exception 传播"和"storage/execution mapping"，但没有测试"legacy result → ValueError"。

  如果实现 agent 删除了 `status="failed"` → provider UNKNOWN 转换但没有添加 ValueError fail-closed，adapter 会因为 `_required_cn_text(result, "status") == "failed"` 仍然触发旧逻辑（如果旧逻辑没完全删除），或者因为 strict projection 不认识 `status="failed"` 而抛出未预期的异常。

- **为什么有问题**: fail-closed behavior 需要显式测试证明。如果测试不覆盖，实现 agent 可能遗漏这个防御性逻辑。
- **直接证据**: §8.2 provenance matrix — "A fake/legacy workflow result containing `status="failed"` without a typed exception fails strict projection as `ValueError`" 在文字描述中但不在测试矩阵的 bullet list 中。
- **影响**: 低 — fail-closed 是防御性逻辑，遗漏不会导致错误分类但会导致未预期的异常类型。
- **建议改法和验证点**:
  1. 在 §8.2 provenance matrix 中增加 explicit test case：构造 `status="failed"` 的 fake result，断言 adapter raises ValueError（而非 FinsDownloadProviderError）。
  2. 验证点：`test_cn_download_runtime.py` 中新增 test case。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## 4. Open Questions

### OQ-1: `sec_filing_collection.py` 是否需要加入 allowlist？

amendment 的 allowlist 包含 `sec_pipeline.py` 但不包含 `sec_filing_collection.py`。`classify_6k_remote_candidates`（`sec_filing_collection.py:198-262`）调用 `downloader.fetch_file_bytes()`，失败时 raise RuntimeError。如果 downloader 改为 raise `FinsDownloadProviderError`，`classify_6k_remote_candidates` 的 behavior 不变（因为 `FinsDownloadProviderError` 是 `RuntimeError` 子类）。pipeline 的 `_precheck_6k_filter` catch `RuntimeError` 并 re-raise typed error。

当前 allowlist 允许 `sec_pipeline.py` 做这个转换，不需要改 `sec_filing_collection.py`。但如果未来想让 `classify_6k_remote_candidates` 自己 raise typed error（更干净的 provenance），就需要把它加入 allowlist。

**当前判定**: 不需要加入。pipeline 层的转换已足够。但需在实现时验证 `classify_6k_remote_candidates` 确实 propagate `FinsDownloadProviderError`（不 catch 它）。

### OQ-2: `cn_download_filing_workflow.py` 的 per-candidate exception 分类是否受影响？

amendment 明确排除 `cn_download_filing_workflow.py`。per-candidate PDF/conversion 失败继续由该文件处理。但 amendment 改变了 downloader 的异常类型（从 RuntimeError 改为 FinsDownloadProviderError）。如果 `cn_download_filing_workflow.py` catch `RuntimeError` 处理 per-candidate 失败，它仍然能 catch `FinsDownloadProviderError`（因为继承关系）。

**当前判定**: 不受影响。继承关系保证 backward compatibility。但实现 agent 应验证 `cn_download_filing_workflow.py` 的 catch 块确实能处理新的异常类型。

### OQ-3: HKEXNEWS `HkexnewsProviderProtocolError` 如何映射到 amendment 的 categories？

`HkexnewsProviderProtocolError` 是 `RuntimeError` 子类，表示 title search 协议违规。amendment 的 categories 包括 PROTOCOL（non-retryable）。`HkexnewsProviderProtocolError` 应映射为 PROTOCOL non-retryable。

**当前判定**: 映射明确。HKEXNEWS downloader 应把 `HkexnewsProviderProtocolError` 映射为 `FinsDownloadProviderError(source=HKEXNEWS, transport_category=PROTOCOL, retryable=False)`。

## 6. 结论

**PASS with risks。**

amendment 的核心设计正确：R02 的 owner 定位（downloader → workflow → adapter → runtime 异常传播链）能在不改 `cn_download_filing_workflow`/runtime/schema 的情况下保留 provenance。SEC auxiliary 的 fatal/optional 区分方向正确。downloader granular mapping 的五类 category 覆盖所有实际入口。allowlist 完整。rebuild missing_periods 的 producer-consumer 修复方案正确。

关键风险点：
1. **F01（中）**: async generator/collector 异常传播机制需要更明确的 specification。amendment 的 intent 清楚，但实现细节（collector 是否 catch、adapter 如何处理双重路径）需要在 §6.3 中补充。
