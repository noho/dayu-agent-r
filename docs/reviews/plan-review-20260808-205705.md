## 3. Adversarial findings

### F20-RR2-DS-001 — `high` — 计划声称的 actual pre-forward wrapper seam 在 production CLI 装配中没有 owner 证据

**违反的契约**

Binding goal 要求每个实际 accepted snapshot 在下一次 ordinary dispatch 前，使用 production 完整 renderer/estimator 做 fail-closed hard-bound guard。修订计划进一步要求 guard 在真实请求转发前取得 complete prepared candidate/manifest，并在 `predicted >= hard` 时保证零 forward；R4 出现第三次 operation 时也要在任何后续 runner/provider call 前停止。

**直接证据**

1. 计划第 280–286 行把实现依赖描述为“既有 audited transparent transport wrapper seam”，但 affected-files 与 Slice 1/2 没有给出该 seam 的 owner、生产装配入口、文件 ref、API contract 或 activation proof。
2. `dayu/service/host_assembly.py:568-570` 的 production assembly public entry 只接收 `ServiceOpenHostAssemblyRequest`；`dayu/service/host_assembly.py:890-923` 无条件装配 `DefaultLocalEngineWorkerFactory()`，没有 external observation driver 可传入的 worker/transport wrapper port。
3. `dayu/host/local_proxy.py:31-42` 的默认 factory 忽略 dispatch snapshot并创建默认 worker；`dayu/host/local_proxy.py:48-80` 只接收已构造的 `AgentRunRequest`；`dayu/host/local_proxy.py:116-135` 打开 events 后直接调用 `run_agent_messages(request)`。该路径没有暴露计划要求的 Host-private complete prepared candidate、manifest、anchor atoms与 sizing decision 的透明 pre-forward callback。
4. 仓库检索到的 worker-factory替换均是 Host public API 的直接调用或测试装配；没有发现 production CLI 支持的 before-forward hook。测试 monkeypatch、`sitecustomize`、私有 import替换或自建 opener都不能冒充“production CLI + 既有 audited seam”。

**可复现反例**

按计划规定的 production CLI argv/POSIX PTY 启动一条 chain。external driver只能观察 durable/event/PTY边界；在 stock service assembly内，默认 worker已经被固定。driver无法 race-free 地在 `run_agent_messages(request)` 前同时取得 Host complete sizing truth并决定零 transport forward。事后检查即使发现 `predicted >= hard`，也已经违反 hard guard；轮询 operation count也无法保证 R4 第三个 operation的第一笔 compactor call为零。

**影响**

- PA02 的 formal actual-snapshot guard尚不可执行，不能靠 Slice 1 的场景 candidate proof替代。
- PA03 的 99 calls算术虽正确，但“第三 operation一出现即停止后续调用”缺少 race-free enforcement boundary。
- PA05 的 provider-free tripwire只证明 proof阶段零真实 network，不能证明 formal production CLI里的 guard已被安装。
- 计划把 seam 不存在降为 Slice 1 `setup-blocked`，但同时在第 530 行宣称无 blocking open question；这不是 code-generation-ready closure。

**最小修订要求**

在计划中绑定一个当前 production CLI 确实可用的唯一 seam：给出 owner文件/符号/public contract、装配路径、external driver如何合法激活、wrapper看到的typed inputs、request digest不变证明，以及 `predicted >= hard`/第三 operation时 transport constructor、call、socket均为零的self-test。若仓库不存在该 seam，必须把它作为 blocking owner question回到 Controller 裁决；不得用 monkeypatch、私有入口或观察后取消补偿。若需要新增产品 seam，则已超出当前“不改产品”的 goal，必须重新 goal-confirm。

### F20-RR2-DS-002 — `high` — chain deadline 的 allocation owner 与 active 540s deadline 未分型，预算和 publication 无法同时 exact

**违反的契约**

计划要求每条 chain wall deadline为 540s，三条 provider窗口合计恰为 1,620s；同时要求 allocation 在任何 provider call 前完成，并要求 `attempted` 与 `provider_not_started` 都发布自身 chain/global deadline ref与 byte SHA。publication self-test还必须从 typed deadline owner独立重算 exact equality。

**直接证据**

1. 计划第 295 行要求三条 chain在任何 provider call前一次性 allocation；第 325–332 行又定义每 chain独立 540s wall deadline、三条合计 1,620s与remaining-time最小值。
2. 第 340–359 行的封闭 union只提供一个 `chain_deadline_relative_ref`/SHA，并断言 deadline owner在 allocation时先于任何 provider创建；`provider_not_started`也必须填同一字段。
3. 第 361–365 行要求 typed projection从 deadline owner独立重算，但没有定义该 ref指向的是 allocation-time budget reservation、未来slot、activation-time absolute deadline，还是一个包含状态机的 discriminated owner。

**可复现反例**

- 若三条 540s absolute deadline都在初始 allocation时启动，它们会同时到期，后启动的 chain不能各自拥有540s，`3×540=1620`不成立。
- 若 ref只是“540s额度”而非实际 absolute deadline，它不能证明 attempted chain的activation/cutoff identity，也不能支持第331行的remaining-time计算。
- 若 provider-not-started被写成一个正常 active deadline，则 publication把“未激活”伪装成“已存在运行deadline”；若留空，又违反当前 exact common-key contract。

**影响**

PA04要求的 skipped-chain deadline variant仍未在typed层闭合。formal driver、summary schema、execution index与 corruption matrix无法从同一 source of truth区分“已分配预算但未启动”和“已激活且有absolute cutoff”，也无法可靠审计每chain 540s与global cutoff。

**最小修订要求**

把 immutable allocation owner 与 activation-time deadline分成明确 typed state，并固定 publication schema。例如所有chain都有 allocation ref/SHA；`attempted`额外且必须有 active deadline ref/SHA，`provider_not_started`明确记录 active deadline为 `not_created`并绑定skip seal。若 Controller要求 common deadline-owner ref，则该 owner本身必须是封闭 state machine，包含 allocation identity、`not_started|active|expired`状态、activation/cutoff字段的必填/禁填规则；self-test从它重算remaining time与540s约束。不得为 skipped chain伪造 active deadline。
