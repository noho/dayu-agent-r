### 挑战 1：batch/CRT 三层编码在真实 cmd phase ordering 下是否成立

**入口/函数**：`_quote_windows_batch_argument` (`dayu/cli/upload_script.py:206-236`)
**调用链**：`_render_windows_script` → 逐 argument 调用 `_quote_windows_batch_argument` → 拼接 `f"{fixed} %*"` → CRLF 输出

**三层 phase ordering 逐字符验证**：

cmd.exe 解析 batch 文件的三个 phase：
- Phase 1（Percent expansion）：`%%` → `%`。renderer 对 `%` doubling（line 228）。`DisableDelayedExpansion`（line 22）确保 `!VAR!` 不展开。
- Phase 2（Special char processing / caret）：`^X` → literal `X`。renderer 用 `^"` 包裹整个 token（line 215, 235），对 metacharacters `^&|<>()` 加 caret（line 229-230）。
- Phase 3（Command execution→CreateProcess→CRT `CommandLineToArgvW`）：CRT 只解析 `"` 和 `\`。

关键正确性验证：每个 phase 的编码互不冲突：
- `%` → `%%`（Phase 1 doubling，不走 caret）
- `&|<>()` → `^X`（Phase 2 caret，不依赖 percent）
- `"` → `\` * (2n+1) + `^"`（CRT backslash-quote + Phase 2 caret）
- trailing `\` → `\` * (2n) + `^"`（CRT even-backslash close）

**直接证据**：测试 oracle `_decode_windows_batch_fixed_token`（`test_upload_filings_from_command.py:952-978`）
先做 batch `%%`→`%` + `^X`→`X` 解码，再由独立 CRT parser `_parse_single_windows_crt_argument`
（line 919-949）恢复 argv。两个 oracle 不复用 production helper，避免自证。

**adversarial 边界重挑战**：

1. **literal `"` 后紧跟 metacharacter**（如 `a"&b`）：
   - renderer：`^"a\^"^&b^"`（`\` = 1 backslash because backslash_count=0 before `"`：`0*2+1=1`，`^` before `&`）
   - Batch Phase 2：`"a\"&b"`（caret 全部去除）
   - CRT：`"` opens quote，`a` literal，`\"` → odd backslash → literal `"`（still in quotes），`&` literal（in quotes），`b` literal，`"` closes quote
   - Result：`a"&b` ✓

2. **trailing `\`**（如 `path\`）：
   - renderer：`^"path\\^"`（backslash_count=1 at close：`\\` * 2 = `\\`）
   - CRT：`"path\\"` → 2 backslashes + `"` → 1 literal `\`，even → quote toggles
   - Result：`path\` ✓

3. **`^` 字面量**（如 `a^b`）：
   - renderer：`^"a^^b^"`（`^` → `^^`）
   - Batch Phase 2：`"a^b"`（`^^` → `^`）
   - CRT：`a^b` ✓

4. **`!` 不被二次展开**：
   - `!` 不在 `_WINDOWS_BODY_METACHARACTERS` 中，不经过 caret 转义
   - `DisableDelayedExpansion` 确保 `!VAR!` 不被展开
   - 真实 cmd test 覆盖了 `!` 作为 fixed argv（`test_upload_filings_from_command.py:793`）

**结论**：PASS。三层编码在真实 cmd phase ordering 下正交且自洽。

### 挑战 2：raw `%*` appended argv 边界与 injection

**入口**：`_render_windows_script` line 200: `f"{fixed} %*"`

**adversarial 分析**：

- `%*` 在 batch Phase 1 展开为所有传入参数（字面量，保留原始引号）。与 fixed 参数之间有一个空格，CRT 将 fixed 的 closing `"` 和 `%*` 展开内容视为独立的命令行 token。
- `DisableDelayedExpansion` 防止 `%*` 内容中的 `!` 被二次展开。
- 真实 cmd test（`test_windows_cmd_script_round_trips_adversarial_argv_with_real_cmd`，line 767-824）：
  - `appended = ("appended value", f"& type nul > {marker}")` — 注入形状的 appended argv
  - 断言顺序：先 `assert not marker.exists()`（注入 marker 不存在），再 `assert rows == [[*fixed, *appended]]`
  - subprocess 使用 `("cmd.exe", "/d", "/c", str(script), *appended)`，`shell=False`
- **正确边界**：如果调用方在调用 `cmd.exe` 时未正确引用含 `&` 的参数，`cmd.exe` 会在解析调用方命令行时将其解释为命令分隔符 — 这是调用方 cmd shell 的标准行为，不在脚本 renderer 的安全边界内。脚本 renderer 的正确责任是：当调用方正确引用参数时，fixed argv 不因 batch/CRT quoting 错误而被截断或重新解释。本实现满足此责任。

**injection 阻断链**：
```
caller: cmd.exe /d /c script.cmd "appended value" "& type nul > marker"
  → cmd Phase 1: %* → "appended value" "& type nul > marker"
  → CreateProcess → CRT parses: ["appended value", "& type nul > marker"]
  → Python sys.argv[2:] = ["appended value", "& type nul > marker"]
  → recorder writes exact argv to JSONL
  → test asserts: not marker.exists() AND rows == [[*fixed, *appended]]
```

**结论**：PASS。`%*` 是 intentional passthrough 设计，injection marker 测试直接证明
appended argv 中的 `&` 不被解释为命令分隔符。

### 挑战 3：CLI TextIOWrapper owner 边界

**入口/函数**：`_configure_cli_standard_stream` (`dayu/cli/main.py:143-156`)

**调用时序**：`main()` line 84-85，在任何参数解析和输出之前：

1. **isinstance guard 是否过于宽松？** — `isinstance(stream, io.TextIOWrapper)` 的意图是"只对真实 OS 文件描述符上的 Python 文本包装器生效"。在 Windows redirected stdout/stderr 场景，这正是 `chcp 65001` 无法触及的层。Python 在创建 `TextIOWrapper` 时已缓存编码；`reconfigure` 是 Python 3.7+ 的正确修正 API。测试 `test_cli_standard_stream_owner_preserves_non_wrapper_capture`（line 538-550）直接证明 `StringIO` 不被改写。

3. **是否存在未覆盖的 TextIOWrapper 子类？** — Python 标准库中 `TextIOWrapper` 的已知子类极少（如 `codecs.StreamReaderWriter` 在某些条件下）。若未来出现不兼容的 `TextIOWrapper` 子类，`reconfigure` 会抛出 `ValueError`/`OSError`，CLI 进程 fail-closed。这是正确的 fail-safe 语义。

**结论**：PASS。CLI stream owner 是唯一进程边界，reconfigure 在所有输出之前执行，
