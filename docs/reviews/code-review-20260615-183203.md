### F001-未修复-中-`_last_event_sequence_locked` 每次 append 全量读取 event sidecar 文件

- **入口/函数**: `FsFinsIngestionJobStore.append_job_event` -> `_last_event_sequence_locked`
- **文件(行号)**: dayu/fins/ingestion_runtime.py:1462-1483, 1364-1367
- **输入场景**: 任何 event append 操作，包括 S1 的少量 status 事件和 S2 将引入的频繁 PROGRESS 事件。
- **实际分支**: `_last_event_sequence_locked` 无条件调用 `_iter_event_records_locked(event_path)`，后者 `open("r")` 完整读取 JSONL 文件并逐行 JSON 解析，遍历全部已持久化事件以找到最后一条 sequence。
- **预期行为**: 获取最后一条 sequence 只需要读取最后一行（或从文件尾部反向扫描），不需要完整解析全部历史事件。
- **实际行为**: 每次 append 都完整读取并解析整个 JSONL 文件，复杂度 O(n) 随事件数量线性增长。对 S1 每次 job 最多 ~5 个事件无实际影响；S2 引入频繁 PROGRESS 事件后将造成每次 append 的 I/O 和 CPU 开销随历史事件数量线性增长。
- **直接证据**:
  - 行 1467: `last_sequence = 0`
  - 行 1479: `for record in self._iter_event_records_locked(event_path):` — 遍历全部事件
  - 行 1482: `last_sequence = record.sequence`
  - 行 1499-1509: `_iter_event_records_locked` 逐行 `json.loads` 解析全部行
  - 行 1367: `sequence = self._last_event_sequence_locked(event_path) + 1`
- **影响**: 随事件数量增加，append 延迟逐步增大；S2 引入 PROGRESS 后可能显著影响吞吐。不影响正确性。
- **建议改法和验证点**: 将 `_last_event_sequence_locked` 改为只读取最后一行（如 seek 到文件尾部反向扫描换行符），或在内存中缓存当前 job 的 last_sequence（锁内更新）。验证点：构造有大量历史事件的 sidecar，确认 append 延迟不随历史事件数量增长。
- **修复风险（低）**: 优化只影响内部实现，不改变 API 契约。
- **严重程度（中）**:

## 逐项审查结论

以下项目经过完整代码路径走读，未发现实质性问题：

### event append/read API correctness
- `FsFinsIngestionJobStore.append_job_event`（行 1343-1389）：持 `.store.lock` → 验证 job 存在 → 计算 sequence → 构造 record → `_event_record_to_json` 校验（含 payload 合法性校验）→ JSON 序列化 → O_APPEND 写入 → stream flush + fsync → 目录 fsync。路径完整，锁覆盖一致。
- `FsFinsIngestionJobStore.read_job_events`（行 1391-1428）：先校验读取窗口 → 持锁 → 验证 job 存在 → 全量读取并过滤/分页 → 返回元组。正确。
- `FinsIngestionRuntime.read_job_events`（行 1808-1835）：正确透传参数到 store，默认值 `after_sequence=0, limit=100`，边界 `_MAX_JOB_EVENT_READ_LIMIT=1000`。

### sequence allocation
- 使用 `_last_event_sequence_locked` + 1，与 job record 操作共享同一 `.store.lock`。
- `_last_event_sequence_locked` 还执行 monotonicity 校验（行 1480-1481）：若已持久化事件中存在 sequence 不递增，立即抛出 `ValueError`，阻止后续写入。
- 并发测试 `test_job_event_store_concurrent_append_allocates_unique_monotonic_sequences` 验证 8 线程 40 次并发 append，所有 sequence 唯一且连续。

### JSONL sidecar atomicity
- 使用 Python `open("a")` (O_APPEND)，同锁保护下无并发写入。
- `stream.flush()` + `os.fsync(stream.fileno())` 保证数据落盘。
- `_fsync_directory(self.root_dir)` 保证目录元数据落盘。
- 单次写入行大小约 < 5KB（payload 4096 字节上限 + 其他字段约 600 字节），远小于典型 PIPE_BUF，O_APPEND 下原子性有保障。

### status transition events 不改变 job status truth
- 所有事件追加路径（`_append_job_event_warn`、`_append_terminal_job_event_warn`）只读取 `record.status` 填充事件的 `status` 字段，不写回 job record。
- `is_status_transition_job_event` / `is_observation_job_event` 明确分离两类事件：状态转换事件是 job record 状态保存后的观察，`PROGRESS` / `CANCEL_REQUESTED` 只是观察/进度信号。
- `FinsIngestionJobEventType` 的 docstring（ingestion_events.py:26-36）明确："状态转换事件……只表示 job record 已经由 runtime/store 保存到对应状态；job record 仍是状态真源"；"观察 / 进度事件……不能被当作 job state transition"。

### request_cancel / running claim / terminal save 事件追加时序
- `request_cancel`（行 1837-1860）：先 `job_store.request_cancel()` 更新 job record → 再 `_append_job_event_warn(CANCEL_REQUESTED)`。正确。
- `_mark_job_running_or_cancelled`（行 2050-2085）：先 `job_store.claim_running_or_cancelled()` → 再按结果追加 `JOB_RUNNING` 或 `JOB_CANCELLED`。正确。
- `_save_succeeded` / `_save_cancelled` / `_save_failed`（行 2595-2682）：先调用 terminal save → 再 `_append_terminal_job_event_warn`。正确。
- 幂等性：`save_succeeded_or_cancelled`、`save_cancelled_if_active`、`save_failed_or_cancelled_if_active` 在 store 内对已是终态的 job 返回原 record，不重复写。`_append_terminal_job_event_warn` 可能对已是终态的 job 重复追加 terminal event（runtime 层未做幂等判断），但 store 内无幂等守卫——多次调用 `_append_terminal_job_event_warn` 会追加多条 terminal event。当前调用链保证每个终态只调用一次，无需额外幂等。

### terminal rollback safety
- `test_save_cancelled_does_not_overwrite_current_terminal_record`（行 1690-1714）：验证 `_save_cancelled` 传入旧 active record 时，store 侧按当前终态原样返回，不覆盖。
- `test_save_failed_uses_current_cancelling_record_instead_of_stale_active_record`（行 1717-1741）：验证 `_save_failed` 在 cancel 请求后调用时，store 侧收口为 cancelled，不会覆盖为 failed。
- `test_terminal_event_append_failure_warns_without_rolling_back_terminal_record`（行 1625-1687）：验证 terminal event append 失败时，job record 维持 SUCCEEDED 终态不变。

### event append failure WARN 策略
- `_append_job_event_warn`（行 2770-2821）：捕获所有 `Exception`，记录结构化 WARN 日志，不向上传播。
- 当前 S1 所有调用方均传入 `payload={}`，始终通过 payload 校验，不会触发因 payload 非法导致的异常被静默吞掉。
- WARN 策略的设计意图正确：event sidecar 是观察投影，其持久化失败不得影响 job record（状态真源）的终态收敛。
- S2 引入带自定义 payload 的 PROGRESS 事件后，若 payload 构造存在 bug（例如类型错误），`ValueError` 会被 `_append_job_event_warn` 捕获并仅输出 WARN。这可能导致编程错误被延迟发现。但 WARN 日志包含 `job_id`、`event_type`、`error_type`、`payload_keys`，具备可发现性。此行为是设计权衡而非缺陷，见下方 Residual Risk。
