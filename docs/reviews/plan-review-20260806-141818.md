### F1-未修复-高-retain-only 场景的 empty evidence_facts 与 empty-output 校验冲突

- **位置**: plan §2（LLM proposal v4）第 96 行 `evidence_facts 只表达本轮新 facts` + §3（Host accepted replacement）第 135 行 combined check
- **问题类型**: 状态机漏洞
- **当前写法**: `evidence_facts` 只表达本轮从 `evidence_material` 形成的新 facts。retained facts 通过 `retained_previous_evidence_fact_labels` 选择。最终 combined accepted facts 做 duplicate/info/caps audit。
- **反例/失败场景**: 当 policy 允许 5 条 evidence facts，且 5 条旧 facts 全部被 retain 时，LLM 合法地返回 `evidence_facts: []` + `retained_previous_evidence_fact_labels: ["P1","P2","P3","P4","P5"]`。当前 v3 accept owner（`context_governance.py:90-147`）在 `_collect_information_issues` 中对 candidate 做 empty/low-information 检查。如果 v4 实现机械地把 empty `evidence_facts` 当成 empty semantic output 拒绝，合法 retain-only compact 会被误杀。
- **为什么有问题**: plan 说"只对 combined accepted facts"做 info check（第 135 行），但没有显式声明 candidate-level empty check 必须排除 retained-only 场景。implementation agent 可能按 v3 习惯直接在 proposal 层面做 empty check。
- **直接证据**:
  - plan 第 96 行："evidence_facts 只表达本轮新 facts"
  - plan 第 135 行："只对 combined accepted facts 做 exact whitespace-canonical duplicate 检查、information check"
  - 当前 `context_governance.py:119`：`_collect_information_issues(compact_input, candidate, represented, issues)` 在 label/kind check 之后、combined 之前执行
- **影响**: retain-only rolling compact 被错误拒绝 → repair → 可能 exhaustion → 不必要 fallback
- **建议改法和验证点**:
  1. 在 plan §3 显式声明："empty/low-information 检查只对 combined accepted facts（retained atoms + new facts）执行；单独 empty `evidence_facts` 配合非空 retained labels 是合法 proposal"
  2. owner test 新增：full-retain scenario — 全部旧 facts 被 retain，新 facts 为空，combined 非空 → accept
- **修复风险**: 低
- **严重程度**: 高

### F5-未修复-中-canonical_evidence_refs 四重语义同名风险

- **位置**: plan §1、§3、§4、§5
- **问题类型**: 契约缺失
- **当前写法**: 同一字段名 `canonical_evidence_refs` 出现在四个不同语义位置：
  1. `CompactSourceBoundaryEntryV4.canonical_evidence_refs` — durable boundary 中每条 source entry 的 evidence refs
  2. `PromptLocalProvenanceEntry.canonical_evidence_refs` — material provenance map 中每个 prompt-local label 的 evidence refs
  3. `CompactionRequest.canonical_evidence_refs` — 整个 request 的 boundary-order unique union
  4. `CompactAcceptedEvidenceFactV4.canonical_evidence_refs` — 每条 accepted fact 的 per-fact evidence refs
- **反例/失败场景**: implementation agent 在 governance expansion 阶段把 boundary entry 的 refs（角色 1）直接赋给 accepted fact（角色 4），而跳过了 per-fact union computation。代码 review 时因为字段名相同，容易误认为赋值是正确的。
- **为什么有问题**: 四个角色的语义不同：(1) 是 source 级别、(4) 是 fact 级别且可能是多个 source 的 union。同名可能导致 implementation agent 混淆角色，或 code reviewer 无法快速区分正确赋值与错误赋值。
- **直接证据**:
  - plan 第 62-63 行：boundary entry 的 invariant
  - plan 第 69-70 行：`PromptLocalProvenanceEntry.canonical_evidence_refs`
  - plan 第 74 行：`CompactionRequest.canonical_evidence_refs`
  - plan 第 110 行：`CompactAcceptedEvidenceFactV4.canonical_evidence_refs`
- **影响**: 实现时字段赋值错误 → per-fact refs 实际等于 boundary entry refs（而非 support labels union）→ 多 source fact 丢失部分 provenance → 被同名字段掩盖，review 难以发现
- **建议改法和验证点**:
  1. 这不是要求改名，而是要求在 plan 中显式写出每个角色的赋值路径（从哪个输入、经过什么计算、得到哪个输出）
  2. 在第 129-143 行的构造顺序中，显式写出 per-fact refs 的构造伪代码：`fact.refs = unique_union(entry.canonical_evidence_refs for entry in boundary where entry.label in fact.selection_labels)`
  3. owner test 必须显式验证角色 1 ≠ 角色 4（多 source fact 场景）
- **修复风险**: 低
- **严重程度**: 中
