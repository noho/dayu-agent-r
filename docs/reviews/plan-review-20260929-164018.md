## 1. Reviewed Target And Scope

本轮按 `planreview` 对 PR7-F1 后的 P0 evidence/probe 计划做 adversarial review，重点反证：

1. `DocumentConverter.convert(..., raises_on_error=False)` 在成功与 typed 转换失败时是否返回 `ConversionResult`；
2. `result.input._backend.model_xbrl` 的 `urlDocs`/`referencesDocument` 能否诚实提供同次请求 URI 到实际加载目标及完整引用边；

## 2. Assumptions Tested

### 2.1 `raises_on_error=False` 的返回边界

**成功路径可取得同次 result/model。** Docling 2.127.0 `document_converter.py:569-577` 让 `convert` 返回单元素 `convert_all` 的结果；`pipeline/base_pipeline.py:79-112` 先创建 `ConversionResult(input=in_doc)`，SimplePipeline 调用 backend，正常完成后返回该结果。XBRL 使用 `SimplePipeline`（`document_converter.py:242-245`），而 `BasePipeline._unload` 为 no-op（`base_pipeline.py:185-186`），故返回时 `result.input._backend.model_xbrl` 仍可访问。

**typed 转换阶段失败也可取得同次 result/model。** `xbrl_backend.py:181` 在导出前已赋值 `self.model_xbrl = model`；typed dimension 在 `xbrl_backend.py:344` 解引用 `memberQname`。该 `AttributeError` 被 `base_pipeline.py:98-108` 捕获；`raises_on_error=False` 时写入 `conv_res.errors` 并返回 `conv_res`。因此 PR7-F1 对“成功与 typed 转换失败保留同次 result”的核心修复成立。

**初始化/导入失败不保证返回 result。** `xbrl_backend.py:95-99` 在 backend 的 `try` 之前直接抛 `ImportError`；`datamodel/document.py:317-323` 只把 `DocumentLoadError` 记为 input rejection，其他异常原样传播。故 `raises_on_error=False` 不是全局非抛出边界，可能根本没有 `ConversionResult`，更没有 `model_xbrl`。计划虽允许模型缺失和属性失效 blocked，但没有把“异常逃出 `convert`”与“返回 result 但无 model”明确分成两类采集路径。

### 2.2 `urlDocs`/`referencesDocument` 的证据能力

**成功加载文档的 URI 到加载目标可以部分证明。** Arelle `ModelDocument.py:75` 先规范化请求 URI；`ModelDocument.py:127-132` 计算 catalog/package 映射后的 `filepath`；`ModelDocument.py:668-681` 保存 `uri`、`filepath` 并以 `urlDocs[uri] = self` 登记。因此对已成功创建的 `ModelDocument`，`urlDocs` key 是规范化请求 URI，`modelDocument.filepath` 是映射后的文件或 archive-entry 形状目标。

**完整请求/引用边不能由该快照证明。** `ModelDocument.py:79-80,139-147` 把失败/不可加载请求放入 `urlUnloadableDocs`，不在 `urlDocs`；`ModelDocument.py:1488-1496` 的 `referencesDocument` 以目标 `ModelDocument` 为 key，同源到同目标的多次引用会合并 `referenceTypes`，且只保留第一个非空 `referringModelObject`。所以两次不同引用元素指向同一目标时，第二个元素及引用次数永久丢失。`hrefObjects` 虽按成功 href 保存元素（`ModelDocument.py:1278-1281`），但 `doc is None` 的失败 href 不进入该列表。计划中的“逐条请求 URI→实际目标和引用边/引用元素”因此不可执行。

### 2.3 临时目录、zip 与 OS trace

`xbrl_backend.py:122-181` 的 `TemporaryDirectory` 在模型赋值前退出；计划明确临时路径不能事后重读，这一点正确。zip 内读取由 `FileSource.py:555-582` 在 archive `ZipFile.read` 内存中完成，OS 文件 trace 不会暴露逐条 entry 内容读取；`FileSource.py:482-492` 的 `isInArchive` 甚至只表示路径形状落入 archive，不要求 entry 已存在。计划把 OS trace 限定为“可见文件访问”并禁止其冒充 zip/catalog 逐条映射，这一限度正确，但在 `referencesDocument` 有损的前提下没有替代的完整当次映射证据。

### 2.4 PR1-PR6 与范围不变量

程序核对当前 plan 中 PR1-PR6 关键不变量均存在：版本真源与 E01 argv 缺口、同根散文件/zip 组合、绝对 `schemaRef`/`linkbaseRef` 分测、每个合成输入先 Arelle 离线 `--validate --validationExitCode`、持久证据双份回读、三平台 pass/blocked、OS 强制零出站、S1 唯一 owner 硬停、无 typed 真实正样本及能力声明上限、独立 Arelle 重放不得冒充。没有发现 blocked 被冒称 pass，也没有发现把无 typed 微型样本扩大为一般 `XML_XBRL` 支持。

## 3. Findings

### 1-未修复-高-`referencesDocument` 无法提供计划声称的逐条请求映射和引用边
- **位置**: 计划 §5 `P0-B 当次模型证据探针（仅 Docling 2.127.0）` 中 `urlDocs`、`referencesDocument`、请求 URI→实际目标和引用边快照要求。
- **问题类型**: 契约缺失 / 证据规格不可执行 / 测试缺口
- **当前写法**: 计划要求遍历 `urlDocs` 保存请求 URI、文档 URI、`filepath` 加载目标，并遍历 `referencesDocument` 保存来源/目标、引用类型及引用元素，随后核对请求映射与“逐条引用边”。
- **反例/失败场景**: 同一 source document 对同一目标 document 先后出现两个不同 `schemaRef`/`linkbaseRef` 元素。Arelle 第一次调用 `addDocumentReference(target, type1, element1)` 后，第二次只向同一 record 合并 `type2`，保留 `element1`、丢弃 `element2` 与次数。计划快照只能看到一个代表元素和类型集合，却可能将其解释为完整边集。另一个失败引用因无目标 `ModelDocument` 而不进 `urlDocs`/`hrefObjects`，请求和映射尝试也会缺失。
- **为什么有问题**: `referencesDocument` 的 owner 语义是“source 到目标文档的聚合引用摘要”，不是原始引用事件日志。计划把它提升为逐边 provenance 真源，违反语义 owner 边界；对 zip/catalog、重复 import、失败映射和安全反例会造成假完整证据，不能满足 P0 的同次可审计要求。
- **直接证据**: Arelle 2.45.3 `ModelDocument.py:681` 将字段定义为 `dict[ModelDocument, ModelDocumentReference]`；`ModelDocument.py:1488-1496` 明确按目标 document 合并 `referenceTypes` 并只设置一次 `referringModelObject`；`ModelDocumentReference` 只有一个 `referringModelObject`（`ModelDocument.py:2171-2174`）。失败文档走 `urlUnloadableDocs`（`ModelDocument.py:79-80,139-147`），成功 href 才追加 `hrefObjects`（`ModelDocument.py:1278-1281`）。
- **影响**: P0 可能把有损摘要误当完整请求/引用 provenance，无法证明 catalog 将每个请求映射到哪个 entry，也无法证明无遗漏/无额外引用；安全矩阵与真实样本可能在证据不完整时被错误接受，后续裁决和上游归因不可审计。
- **建议改法和验证点**: 将证据契约拆成成功文档集合、失败/不可加载请求集合和原始逐引用事件集合；明确 `urlDocs` 的 key 是规范化 URI。对成功 href 可使用经实测的 `hrefObjects` 等逐引用结构，对失败请求保留原始引用元素/URI 与 `urlUnloadableDocs`/errors，并以合成重复同目标引用直接验证 multiplicity 与每个元素均被保留。zip entry 目标必须来自同一当次模型/文件源记录，OS trace 仍只作可见访问旁证。任一来源不能逐边完整保存时，该向量按 `blocked: run evidence unavailable`，不得给 pass。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### 2-未修复-中-非抛出转换没有覆盖全部初始化失败路径
- **位置**: 计划 §5 `P0-B 当次模型证据探针` 的 `raises_on_error=False` 返回、backend 初始化/模型赋值前失败及 blocked 出口。
- **问题类型**: 状态机漏洞 / 失败处理不完整 / 不可直接实施
- **当前写法**: 计划要求每一路调用 `convert(source, raises_on_error=False)` 并保留返回的 `result`；初始化或赋值前失败时称 `raises_on_error=False` “也可能只留下失败结果而没有 `model_xbrl`”，再保存原始异常/拒绝信息并 blocked。
- **反例/失败场景**: Arelle 未安装时 `XBRLDocumentBackend.__init__` 在进入 `try` 前抛 `ImportError`；`InputDocument._init_doc` 对非 `DocumentLoadError` 原样抛出，`DocumentConverter.convert(..., False)` 不返回 `ConversionResult`。同类 backend 构造异常也可直接逃出。执行者若只写 `result = convert(...)`，探针进程会崩溃；若只读 `result.errors`，会误称已取得同次失败结果。
- **为什么有问题**: `raises_on_error=False` 的实际 owner 是 pipeline 转换阶段异常捕获，不是输入构造/backend 导入的统一异常边界。计划把三类状态混在一起，导致失败证据采集路径不闭合。
- **直接证据**: Docling 2.127.0 `backend/xml/xbrl_backend.py:95-99` 在 try 前抛 `ImportError`；`datamodel/document.py:317-323` 仅捕获并记录 `DocumentLoadError`，其他异常传播；`pipeline/base_pipeline.py:98-108` 只覆盖 pipeline 内转换异常并按 `raises_on_error` 决定捕获或抛出。
- **影响**: 初始化/缺依赖路径可能没有 result、没有 model，且异常/trace 不按计划归档；执行者可能把技术失败误记为属性不可用，或漏掉真正首因。
- **建议改法和验证点**: 明确定义三条互斥路径：正常/typed pipeline 失败返回 result 且可有 model；`DocumentLoadError` 返回 invalid-input result 但无 backend/model；构造/导入/pydantic 等异常逃出时没有 result。第三类必须由探针最外层显式捕获并保存异常类型、cause/trace、双流与版本后走 blocked。用缺 Arelle、taxonomy 初始化失败和 typed 导出失败三个最小反例分别验证。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。

## 5. Residual Risks And Tracking

- **R1 失败/不可加载引用仍可能无法恢复原始映射尝试**：即使补入 `hrefObjects`，`doc is None` 的 href 也不被追加。跟踪去向：P0-B 证据 owner 以原始引用事件和 `urlUnloadableDocs`/errors 对账；缺失即 blocked。
- **R2 zip entry 只能在 Arelle 当次 archive/file-source 语义中证明**：OS trace 看不到 `ZipFile.read` 的 entry 内容访问。跟踪去向：P0-B 当次模型/文件源快照；P0-C OS trace 仅作旁证。
- **R3 `referencesDocument` 有损且 Arelle 版本升级会漂移**：结论只能绑定 Arelle 2.45.3，并须用重复引用反例校验采集 schema。跟踪去向：P0-A 生产候选/升级重跑。
- **R4 初始化异常分类仍需运行期探针**：静态源码已给出直接反例，但缺 Arelle、坏 taxonomy、typed 导出三路的实际 result/异常组合尚未实测。跟踪去向：P0-B 明确三路 fixture 和采集协议。
- **R5 三平台 OS 强制机制、真实 taxonomy/无 typed 正样本、真实 CLI/manifest、证据双份回读仍全部未证**：保持现有 blocked，不得由本轮文档 review 转为 pass。跟踪去向：P0-A/B/C、后续 S1 implementation plan、goal/总控平台与 capability 裁决。
