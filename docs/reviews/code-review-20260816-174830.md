### 003-未修复-低-durable job path 的 `FinsUploadUsageError` 会落入 generic exception 而非 typed failure

- **入口/函数**: `_run_upload_job()` in `ingestion_runtime.py:4911`
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:5000-5001`, `dayu/fins/pipelines/sec_upload_workflow.py:97-98`
- **输入场景**: pre-validated request 经 `start_upload(validated)` 进入 durable job；fresh state 在 `_resolve_fresh_filing_request` 中 re-validate 时产生 `FinsUploadUsageError`（如 `UPDATE_TARGET_MISSING` 或 `EXISTING_SOURCE_REPAIR_REQUIRES_AUTO`）
- **实际分支**: `FinsUploadUsageError` 在 `_resolve_fresh_filing_request` 中被 re-raise；workflow 无 handler，异常穿透 async generator 被 `_run_upload_job` 的 `except Exception` 捕获
- **预期行为**: `FinsUploadUsageError` 应产生 typed usage failure event，与 `FinsUploadPrevalidationError` 同构处理
- **实际行为**: `_save_failed_from_exception(str(exc))` 产生 `{"message": "<exc message>"}` 而非 `{"kind":"usage","code":"...","message":"...","retry_hint":"...","file_label":null}` typed JSON
- **直接证据**: `sec_upload_workflow.py:97-98` re-raises `FinsUploadUsageError`；`ingestion_runtime.py:5000-5001` catches `Exception` and calls `_save_failed_from_exception`；`ingestion_runtime.py:5953` uses `str(exc)` as message
- **影响**: 极低。此路径在实践中几乎不可达——pre-validated request 的 static validation 已通过，fresh re-validate 使用同一 `FinsUploadFilingRequest`，只有 published state 变化才可能触发 usage error；而 state 变化更可能触发 `UNSAFE`/`REPAIR_REQUIRED`/`MISSING` 路径。当前无测试覆盖此 edge case
- **建议改法和验证点**: (a) 在 `_resolve_fresh_filing_request` 中也将 `FinsUploadUsageError` 转为 typed failure（使用 `fins_upload_failure_from_exception`），或 (b) 在 `_run_upload_job` 中对 `FinsUploadUsageError` 做 typed 处理，或 (c) 记录为已知 residual edge case 并在后续 slice 补测试
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Conclusion

**PASS（附低严重程度 findings）**

Slice 5 实现正确完成了 accepted plan §7/§10 的核心目标：

1. **fresh authoritative boundary 精确收敛**: `_resolve_fresh_filing_request()` 正确区分 `FinsUploadPrevalidationError`（typed failure）、`FinsUploadUsageError`（re-raise）、`OSError`（IO failure）和 `ValueError`（corruption failure），catch order 经 MRO 验证无误吞
2. **workflow 机械消费 typed failure**: 无 raw meta 解析、无 path 判定、无字符串重分类；fresh resolution 产生的 `FinsUploadFailureReason` 由 `_build_*_filing_failure_event()` 唯一投影
3. **failed event 唯一且 path-free**: fresh failure 在 `UPLOAD_STARTED` 之前返回；failure JSON 由 `upload_failure.py` factory 产生，不含路径/revision/异常 repr
4. **SEC 五类 repair 均命中真实 filesystem**: original_missing/digest/docling_missing/meta_digest/manifest_missing 各有参数化测试，断言 COMPLETE/new revision/primary/assets/digest/manifest/requested=stored/atomic company-source
5. **CN/HK 各有独立 wiring assertion**: repair success + UNSAFE typed terminal + Phase B stale + rollback，不以"共用 CN facade"替代 HK 测试
6. **snapshot/process_filing 只消费新 primary**: `_RepairPrimaryConverter` 产生逐次不同 bytes，snapshot 与 process entry 均断言 exact new primary
7. **durable job typed failure**: `fins_upload_source_integrity_unsafe_failure().to_json()` 完整等于 `failure_summary` 与 `result_summary.failure`
8. **scope 守护**: frozen files 无 diff，production 无 `Any/object/getattr/hasattr`，pyright 0 errors，coverage >= 80%
