## 4. Findings

### F-DS-01 — 中 — `input_changed_during_analysis` 缺少 stable rule_id

- **位置**: §7.3 (line 323-325), §9.1 integrity rules table
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: §7.3 描述了 "cold-only row 的 `event_sequence` 高于本次 hot snapshot watermark 时，不直接报 mismatch，产生 `input_changed_during_analysis` limitation"。但 §9.1 integrity rules 表中列出了 `integrity.missing_cold_trace`、`integrity.missing_hot_trace`、`integrity.hot_cold_source_mismatch`，却没有 `limitation.input_changed_during_analysis` 或等价 rule_id。
- **反例/失败场景**: Implementation agent 在实现 join 逻辑时，看到 §7.3 的 prose 描述需要生成 limitation，但 §9.1 没有对应的 rule_id 枚举值。Agent 可能：(a) 自行发明一个 rule_id，导致与后续 slice 的 rule_id 命名不一致；(b) 错误地将其归类为 `integrity.*` error 而非 limitation；(c) 忽略该 case，让高于 watermar 的 cold-only rows 被误报为 `missing_hot_trace`。
- **为什么有问题**: Plan 在 prose 和 rule table 之间存在不一致。rule table 是 implementation agent 实现 join 逻辑时的直接参考；prose 中的特殊处理如果没有对应的 rule_id，会被遗漏。
- **直接证据**:
  - Plan §7.3 line 323-325 明确描述了该行为
  - Plan §9.1 line 482-501 列出了所有 integrity rule_ids，但不包含 `input_changed_during_analysis`
  - Plan §10.1 的 limitation 字段设计没有为该场景预留明确的 `reason_code`
- **影响**: Implementation agent 可能遗漏该边界条件，导致并发写入场景下的 false positive `missing_hot_trace` finding。
- **建议改法和验证点**: 在 §9.1 新增 `limitation.input_changed_during_analysis` rule_id，并在 §10.1 limitation 示例中体现。S1 测试矩阵应包含 "cold row with event_sequence > hot watermark → limitation (not error)" 场景。
- **修复风险**: 低（纯 plan 文本补全，不改变设计）
- **严重程度**: 中

- **位置**: §13 Slice 2 (line 1041-1123) 与 Slice 3 (line 1125-1206)

### F-DS-03 — 低 — `cold_line` 作为 payload category 参与统一阈值排名

- **位置**: §9.2 payload categories (line 546-555)
- **问题类型**: 最佳实践偏离
- **当前写法**: `cold_line` 与 `source_event_payload`、`tool_arguments`、`runner_input_projection` 等 resolver-verified payload 一起列入 payload categories，参与同一 `large_payload_threshold_bytes` 阈值判定和 ranking。
- **反例/失败场景**: Cold line 的大小直接来自 JSONL 文件的行字节数，不需要 resolver。一条 cold line 可能因为 bounded summary 文本较长而超过 131KB 阈值（例如 `TOOL_RESULT_ACCEPTED` 的 bounded result summary）。但 cold line "large" 的原因（bounded summary 长度）与 resolved payload "large" 的原因（原始 arguments/result 大小）是不同的风险类别。把它们放在同一个 ranking 表中，operator 可能误以为 cold line 的大小等于原始 payload 的大小。
- **为什么有问题**: `cold_line` 和 resolver-verified payload 的 size 来源不同（行字节数 vs. descriptor `payload_size_bytes`），但阈值相同。这可能导致：(a) cold line 触发 large payload finding，但实际原始 payload（如果有）可能更小；(b) ranking 表中 cold line 和 resolved payload 的 size 不可直接比较。
- **直接证据**:
  - Plan §9.2 line 546-548: `cold_line` 列在 payload categories 中
  - Plan §9.2 line 533-537: 所有 category 使用同一 `large_payload_threshold_bytes` 阈值
  - `sha256_digest_json` 计算的是 canonical JSON digest，不是字节大小；cold line 的字节大小是文件行字节数
- **影响**: Operator 可能误解 cold line size 的含义。低影响因为 131KB 阈值很高，当前 workspace 的 cold lines (~25KB total for 9 lines) 远低于阈值。
- **建议改法和验证点**: 考虑将 `cold_line` 移出 unified payload ranking，单独作为 "cold line size distribution" 统计；或至少在 report 中明确标注 `cold_line` 的 size 是 JSONL line bytes，不是 resolved payload bytes。
- **修复风险**: 低
- **严重程度**: 低

### F-DS-04 — 低 — `TOOL_AWAITING` / `RUN_WAITING` 聚合行为未定义

- **位置**: §9.3 duplicate/failure/latency rules, §10.1 run aggregation
- **问题类型**: 契约缺失
- **当前写法**: Plan §9.3 详细定义了 Host duplicate、tool failure、policy block、latency、truncation/fetch_more 的规则。`TOOL_AWAITING` 和 `RUN_WAITING` 出现在真实 workspace（各 1 条），但没有被任何 rule 显式覆盖。Plan §6.1 attribution table 说 "unknown event 保留在 run aggregation，不产生猜测性 finding"，但 `TOOL_AWAITING` 和 `RUN_WAITING` 是 known events。
- **反例/失败场景**: Implementation agent 在处理 wait chain 时，发现 `TOOL_AWAITING` → `RUN_WAITING` → ... → `TOOL_RESULT_ACCEPTED` 的链路，但不清楚是否应该：(a) 产生一个 "wait occurred" info finding；(b) 记录 wait timing；(c) 校验 wait chain 完整性（有 `TOOL_AWAITING` 无后续 `TOOL_RESULT_ACCEPTED` 是否为异常）。当前 plan 对此完全沉默。
- **为什么有问题**: 这不是"rule 应该产生什么 finding"的问题，而是"wait chain event 在 run aggregation 中的角色"没有定义。真实 workspace 中存在这些 event，analyzer 必须决定它们是纯粹出现在 run chain timeline 中，还是需要做任何校验。
- **直接证据**:
  - Plan §5.2: 真实 workspace 有 `TOOL_AWAITING` × 1 和 `RUN_WAITING` × 1
  - Plan §9.3 无 wait chain rule
  - Plan §6.1: "unknown event 保留在 run aggregation" 不适用（这些是 known events）
  - Goal confirmation §5 矩阵中有 "等待 / 恢复链路发生了什么" 行，标记为 `available`，但只说了按 typed refs 关联
- **影响**: 低。Implementation agent 可能安全地将这类 event 仅记录在 run timeline 中而不产生 finding。但这应该在 plan 中明确。
- **建议改法和验证点**: 在 §9.3 或 run aggregation 规则中明确：`TOOL_AWAITING` / `RUN_WAITING` 作为 run timeline fact 记录，除 wait chain 中存在 `TOOL_AWAITING` 但 run 已结束且无后续 `TOOL_RESULT_ACCEPTED` 时产生 info-level observation 外，不单独产生 diagnostic finding。或在 non-goals 中声明首版不覆盖 wait chain 完整性检查。
- **修复风险**: 低
- **严重程度**: 低

### F-DS-06 — 低 — 测试 fixture 强制全量 producer 生成可能拖慢 S1

- **位置**: §12.2 (line 888-890), §13 Slice 1 completion signal
- **问题类型**: 最佳实践偏离
- **当前写法**: "测试基线 fixture 必须通过当前 production Tool Trace projection 生成 valid hot/cold/descriptor，然后只对 Analyzer 输入副本做目标破坏；不得手写旧 schema、修改 producer 或让 mock 成为语义 owner。"
- **反例/失败场景**: S1 的 cold parser 需要测试 corrupt JSON、non-object、unsupported version、invalid field、digest mismatch 等场景。如果每个测试 fixture 都必须通过 production Tool Trace projection 生成 valid baseline 再做破坏，则每个 parser 测试都需要：(a) 启动 EventLog → Tool Trace projection pipeline；(b) 生成有效的 hot row + cold line；(c) 在 cold JSONL 副本上手动破坏。对于纯 parser 测试（如 "JSON decode error on line 3"），这套流程过于昂贵，且引入了不必要的 producer 依赖。
- **为什么有问题**: Plan 的出发点是正确的（不让 mock 成为语义 owner）。但对于 S1 的 parser 层，cold JSONL 的格式契约是公开的（JSONL, one JSON object per line, fixed schema_version=1, specific field names and types）。Parser 测试应该能直接构造合法/非法的 cold JSONL 文本来验证 parser 行为，不需要绕道 producer。让 producer 成为 parser 测试的唯一 fixture 来源，反而把 parser 测试耦合到了 producer 的实现细节上。
- **直接证据**:
  - Plan §12.2 line 888-890
  - Plan §8.2: cold parser contract 是 self-contained 的（JSON parse → field validation → digest recomputation）
  - Parser 的正确性不依赖 producer 的正确性（它们是不同的 owner）
- **影响**: S1 实现和测试可能不必要地复杂。对于 integrity 相关测试（digest mismatch, cold/hot source key conflict），必须走全量 producer 是合理的；但对于纯 parser 测试（JSON 格式、字段类型），手写 fixture 更直接。
- **建议改法和验证点**: 分层测试策略：(a) Parser unit tests：允许手写合法/非法 cold JSONL 文本，验证 parser 的 JSON decode、field type check、schema_version check；(b) Integrity integration tests：使用 production projection 生成 valid baseline，验证 digest recomputation、hot/cold join、resolver orchestration。S1 的 coverage target 仍然适用。
- **修复风险**: 低（澄清约束，不改变 coverage 目标）
- **严重程度**: 低

## 5. Architecture Boundary Review

### 5.1 Layering

Plan 的分层方案是正确的：

```
CLI (dayu/cli/commands/tool_trace.py)
  → Service (dayu/service/tool_trace_analysis.py)
    → Host public API (dayu/host/__init__.py exports)
      → Host Analyzer (dayu/host/tool_trace_analysis*.py)
        → Host durable read-only (dayu/host/durable/)
```

**验证通过的点**：
- CLI 只 import Service/public contracts，不 import `dayu.host.durable`（§13 Slice 4 line 1249）
- Service 拥有 path discovery 和 report publication（§12.1）
- Host 拥有 analyzer rules 和 report contract（§6 ownership table）
- 无反向依赖

**需关注的点**：
- `dayu/host/__init__.py` 新增 analyzer exports 与现有 Host API exports 同在一个 flat namespace。这是有意为之（非兼容 re-export，§12.1 line 866-867），但可能让 `__init__.py` 进一步膨胀。当前 `__init__.py` 已经有 328 行 `__all__`。建议在 plan 中备注：如果 `tool_trace_analysis` exports 超过 ~10 个符号，考虑使用 `from dayu.host import tool_trace_analysis` 的子模块访问模式，而非全部挤进 root `__all__`。

### 5.2 Dependency Direction

**验证通过**：Analyzer 只读不写，不反向驱动 Host truth。Plan §3.2 明确 "Analyzer 不 repair 输入，不重写 JSONL，不修复 descriptor，不 catch up projection。"

### 5.3 Public Contracts

Plan 定义的 public contracts 是完整的：
- `analyze_tool_trace(source, policy) -> ToolTraceAnalysisReport`
- `tool_trace_analysis_report_to_json(report) -> str`
- `render_tool_trace_analysis_markdown(report) -> str`

两个 renderer 只消费 report，不读取 source（§8.1 line 372-373）。这是正确的 single source of truth 设计。

## 6. Overcoupling Review

**未发现实质性过度耦合**。Plan 的模块拆分是合理的：
- `tool_trace_analysis_contracts.py`：纯类型定义
- `tool_trace_analysis_input.py`：parser + join + resolver orchestration
- `tool_trace_analysis_rules.py`：aggregation + rules
- `tool_trace_analysis.py`：orchestration + renderer

四个模块之间有清晰的依赖方向：contracts ← input ← rules ← analysis。唯一的跨 slice 共享文件风险已在 F-DS-02 中记录。

## 7. Overengineering Review

**未发现过度设计**。Plan 明确拒绝：
- 通用 rule engine / plugin framework / DSL（§3.1）
- Config profile/schema 用于 policy（§17）
- 递归目录扫描、archive/cloud 输入（§3.1）
- 把 report 写成 durable truth（§3.1）

`ToolTraceAnalysisPolicy` 的五个参数（threshold, limit, sample_count, multiplier, delta_ms）都是验收直接需要的，没有多余抽象。

## 8. Best-Practice Review

### 8.1 正确做法

- **Atomic report publication**: temp-write + `os.replace`（§10.3）。两个文件不做跨文件事务（§10.3 line 819），这是务实的取舍。
- **Exit code 语义**: 0=success regardless of findings; 1=read/orchestration/publish failure; 2=usage error（§10.3）。清晰且不与 finding severity 耦合（non-goal §3.1）。
- **Finding/limitation 分离**: §3.2.2 和 §9.1 明确区分证据成立的 finding 和无法证明的 limitation。Report schema 中 `findings` 和 `limitations` 是两个独立数组。
- **Deterministic finding IDs**: `TT-HOST-0001` 格式，按 layer/severity/priority/rule_id/event_sequence 排序（§10.1）。相同 input/policy 结果稳定。

### 8.2 可改进点

- **Markdown escaping**: Plan §10.2 要求 "所有用户/工具可读文本做 Markdown escaping"，但没有指定 escaping 策略（例如是否 escape 反引号、管道符、HTML tags）。建议引用具体的 escaping 规则或库。
- **`payload_ranking_limit` 默认值 20**: 这个值的 tradeoff 没有解释（为什么是 20 不是 10 或 50？）。对于 9 行 trace 的 workspace，20 足够了；但对于大规模 trace，top-20 可能不够。

## 9. Optimal-Solution Review

Plan 选择的方案（typed analyzer + fixed report schema + 单一 CLI action）是此问题域的最简可行方案。与替代方案比较：

- **方案 A（当前 plan）**: Typed analyzer, fixed JSON/Markdown report, single CLI action. 复用现有 resolver/query.
- **方案 B（更通用）**: Generic trace query language + pluggable report templates. 过度设计，当前无需求。
- **方案 C（更简单）**: 只做 cold JSONL grep + summary. 无法做 hot/cold join、payload resolution、vendor block.

Plan 的 A 方案是最佳选择。不引入 query language、plugin system、config profile 的决策是正确的。
