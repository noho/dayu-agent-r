## Findings

### 1-未修复-中-`_resolve_document_version` 行为规格未绑定到函数签名或实现指令

- **位置**：§4.2（精确函数签名）、§4.4（不可区分 duplicate descriptor 的 conservative contract）
- **问题类型**：契约缺失 / 不可直接实施
- **当前写法**：§4.2 给出 `_resolve_document_version` 的签名：
  ```python
  def _resolve_document_version(
      previous_meta: Mapping[str, JsonValue] | None,
      source_fingerprint: _UploadSourceFingerprint,
  ) -> str:
  ```
  参数类型从 `str` 升级为 `_UploadSourceFingerprint`，但签名节无行为说明。§4.4 另一处写道：
  > 有 previous meta 且 `identical_skip_safe=False` 时，无论 digest 是否相等，都在现有 previous version 上增长一次

  当前生产代码 `docling_upload_service.py:1275-1295` 只检查 `previous_fingerprint != source_fingerprint`；没有 `identical_skip_safe` 的概念。
- **反例/失败场景**：实现 agent 按 §4.2 签名实施，只改类型不改逻辑，则 `identical_skip_safe=False` 且 digest 相同时，version 不增长——保守 update 语义静默失效。skip 正确被阻（`_can_skip_upload` 检查 `identical_skip_safe`），但 version 不变意味着持久化 meta 的 `document_version` 不反映这次"保守 update"。
- **为什么有问题**：amendment 的核心 contract 是"ambiguous descriptor 每次 re-upload 都 update/version increment"。如果 `_resolve_document_version` 不检查 `identical_skip_safe`，version increment 行为依赖实现 agent 跨 §4.2/§4.4 两处自行推断，而非代码级可验证的指令。这违反 amendment 自身"typed result 控制 skip/version"的 data flow（§4.5）。
- **直接证据**：
  - §4.2 签名节无 `identical_skip_safe` 行为说明
  - §4.4 行为规格与 §4.2 签名分离
  - 当前生产代码 `_resolve_document_version`（`docling_upload_service.py:1275-1295`）无 bool 检查
- **影响**：实现 agent 可能只改类型不改逻辑；测试若只断言 "uploaded" 而不断言 version 值，该错误不会被发现；保守 update 的 version 增长语义静默失效。
- **建议改法和验证点**：在 §4.2 的 `_resolve_document_version` docstring 或签名节明确写出：`identical_skip_safe=False` 且有 previous meta 时，无论 digest 是否相等，都在 previous version 上增长一次。测试矩阵 §5.2 的 assertions 补充显式 version 值断言（如 `version == "v3"`）。
- **修复风险（低）**：只在 docstring/签名节补充一句话行为规格，测试矩阵补一个 version 断言。
- **严重程度（中）**：保守 update 语义的核心路径，但不影响 skip 正确性。

### 2-未修复-低-测试矩阵 §5.2 未显式断言 version increment 值

- **位置**：§5.2（不可区分 duplicate descriptors 测试矩阵）
- **问题类型**：测试缺口
- **当前写法**：§5.2 的 assertions：
  > create(primary=P1) 后，原样 auto upsert(primary=P1) 仍 uploaded/version increment；再仅翻转为 P2 也 uploaded/version increment。

  只描述"uploaded"与"version increment"的定性行为，未指定具体 version 值（如 v1→v2→v3）。
- **反例/失败场景**：实现 agent 写测试断言 `result.status == "uploaded"` 但不断言 `result.payload["document_version"] == "v3"`，则 version 不增长的实现也能通过测试。结合 Finding 1，这形成一个可逃逸的验证缺口。
- **为什么有问题**：§4.4 明确要求 version increment（"在现有 previous version 上增长一次"），但测试矩阵不强制验证该行为。amendment 的 contract 需要 test-level 可验证断言，不能依赖实现 agent 自行推断。
- **直接证据**：§5.2 assertions 只写"version increment"，不写具体值；§4.4 要求"在现有 previous version 上增长一次"。
- **影响**：version 不增长的实现可能通过测试；保守 update 的 version 语义无法被测试矩阵强制执行。
- **建议改法和验证点**：§5.2 补充具体 version 断言：
  - create(primary=P1) → `version == "v1"`
  - auto upsert(primary=P1) → `version == "v2"`
  - flip to primary=P2 → `version == "v3"`
  这三个断言完整覆盖 ambiguous descriptor 的 version increment 链。
- **修复风险（低）**：只在测试矩阵补充三个 version 断言。
- **严重程度（低）**：依赖 Finding 1 的修复；单独不构成 blocker，但与 Finding 1 组合会放大风险。
