### 001-未修复-低-混合批次 RESERVED 与 INVALID 分类仍随输入顺序翻转
- **入口/函数**: `plan_upload_assets` material 命名分类（`dayu/fins/upload_asset_plan.py:268-283`）；测试面 `tests/fins/test_upload_asset_plan.py:112-124`（本轮 R1 新增行）
- **文件(行号)**: `dayu/fins/upload_asset_plan.py:268-283`（单个逐文件循环内交错「长度/键 → INVALID」「控制名 → RESERVED」两检查，首个命中即抛）；对照 plan 契约 `docs/gateflow/upload-material-assets-plan-20260929.md:45`「控制名分类不依赖原件遍历顺序」；对照 `tests/fins/test_upload_asset_plan.py:118-119`（只钉 RESERVED×业务碰撞混合）
- **输入场景**: 同一 material upsert 批次同时含一个长度超限名（如 `"a"*243+".pdf"`，派生名 260 字节>255）与一个控制名变体（`META.JSON`），以两种 CLI 文件顺序提交。
- **实际分支**: 循环按迭代序逐文件先做键/长度检查再做控制名检查，先命中者抛出；超限名在前则整循环在控制名被分类前终止于 `INVALID_ASSET_NAME`，控制名在前则抛 `RESERVED_CONTROL_NAME`。
- **预期行为**: plan 明文「reason 判定先用 storage owner 的保守键比对**所有** original/derived 与 document 控制名……控制名分类不依赖原件遍历顺序」；同一集合的 closed reason 不应随输入顺序改变（R1 的全部动机即此）。
- **实际行为**: 本 reviewer 探针实测 `["a"*243+".pdf", "META.JSON"]` → `invalid_asset_name`，`["META.JSON", "a"*243+".pdf"]` → `reserved_control_name`；同集合两种顺序两种 LLM/CLI 可见 closed reason 与 usage code。RESERVED×业务碰撞混合已被本轮 R1 测试钉住（两遍分类第二遍兜底），RESERVED×INVALID 混合无任何正逆序测试，现状无回归锚。
- **直接证据**: `upload_asset_plan.py:274-283`（同一循环内两个 raise，迭代序首命中）；探针输出 `ORDER_invalid_then_reserved`/`ORDER_reserved_then_invalid` 两 reason 不同；`rg` 测试面无 RESERVED 与长度超限同批用例。
- **影响**: 同一批次的用户可见失败原因与 usage code 随参数顺序漂移（错误 answer 层面，无状态写入/发布影响——两序均在 converter 前拒绝且零发布）；LLM 按 closed code 决定下一步时得到不一致信号；与 plan 的顺序无关性承诺直接冲突。
- **建议改法和验证点**: 在 owner 边界把分类改为显式、确定的批次级 reason 优先级（按 plan 文本：前置 duplicate 之后、控制名全批分类先于逐文件有效性，即 RESERVED 稳定优先于 INVALID；或总控裁决相反优先级后同步修订 plan 文本），并在 `test_material_rejects_name_conflicts_before_conversion` 补 RESERVED×INVALID 两序参数行钉住同 reason。验证点：新正逆序参数行 + 既有 26 项 owner 测试 + 相邻矩阵回归。注意保持 R1 已钉住的 RESERVED×碰撞行为不变。
- **修复风险（低/中/高）**: 低（planner 内分类顺序收敛 + 纯测试增量；不触发布、identity 或 action 合同）。
