## Findings

### 1-未修复-严重-reactive-diagnostic-wiring-placed-in-wrong-method

- **位置**: Plan Slice 2 "Proactive / Reactive EventLog Wiring and Logging", lines 289–314; code at `dayu/host/engine_ingest.py:1604`
- **问题类型**: 不可直接实施
- **当前写法**: The implementation diff adds `diagnostic_reference = self._write_reactive_compaction_rejected_diagnostic(transaction, operation_id=operation_id, rejected=rejected)` inside `_append_reactive_compaction_requested_event()` (line 1604)
- **反例/失败场景**: 
  - `_append_reactive_compaction_requested_event(self, transaction, *, context, data, estimate, decision, frozen_material_list_digest, frozen_material_refs)` — this method does NOT have `operation_id` or `rejected` as parameters
  - The correct method is `_append_reactive_compaction_attempt_rejected_event(self, transaction, *, context, operation_id, rejected)` (line 2075), which has both `operation_id` and `rejected` in scope but does NOT call `_write_reactive_compaction_rejected_diagnostic`
  - Meanwhile the call at line 1604 would raise `NameError` at runtime because `operation_id` and `rejected` are undefined in that scope
  - pyright confirms this: 19 `reportUndefinedVariable` errors at lines 2142–2181 in engine_ingest.py, which is downstream of the missing definition
- **为什么有问题**: The implementation placed the durable diagnostic write call in the wrong method. `_append_reactive_compaction_requested_event` writes the `CONTEXT_COMPACTION_REQUESTED` event — this has nothing to do with rejected attempts. The rejected attempt event writer (`_append_reactive_compaction_attempt_rejected_event`) is where the diagnostic must be persisted, matching the dispatch.py pattern.
- **直接证据**: 
  - `grep` output shows `diagnostic_reference` is defined at line 1604 (wrong method) and consumed at lines 2127–2181 (correct method, but undefined)
  - pyright: `"diagnostic_reference" is not defined (reportUndefinedVariable)` × 19 occurrences
  - dispatch.py lines 2308–2404 show the correct pattern: `diagnostic_reference` is defined at the start of `_append_compaction_attempt_rejected_event` before `append_event`
- **影响**: 实施 Agent 生成错误代码 / 运行时 NameError / reactive compact diagnostic 永远无法写入
- **建议改法和验证点**:
  1. Remove the erroneous `diagnostic_reference = ...` block from `_append_reactive_compaction_requested_event()` (lines 1604–1608)
  2. Add `diagnostic_reference = self._write_reactive_compaction_rejected_diagnostic(transaction, operation_id=operation_id, rejected=rejected)` at the start of `_append_reactive_compaction_attempt_rejected_event()` before the `append_event` call (around line 2088)
  3. Run `pyright dayu/host/engine_ingest.py` — must show zero errors
- **修复风险（低）**: Mechanical fix, pattern already proven in dispatch.py
- **严重程度（严重）**: Runtime would fail on every reactive rejected attempt with a diagnostic body

### 3-未修复-中-重复-offending-block-helper-函数

- **位置**: `dayu/host/dispatch.py` lines 4482–4573, `dayu/host/engine_ingest.py` lines 6248–6331
- **问题类型**: 过度耦合 / 最佳实践偏离
- **当前写法**: Five identical module-level helper functions (`_diagnostic_offending_section`, `_diagnostic_offending_kind`, `_diagnostic_offending_label`, `_diagnostic_offending_ordinal`, `_diagnostic_offending_text_digest`, `_diagnostic_offending_text_length`) are copy-pasted into both `dispatch.py` and `engine_ingest.py`. Each is ~8 lines and pattern-identical.
- **反例/失败场景**: 
  - 未来添加新的 offending block 字段时，必须同步修改两个文件
  - 如果其中一个漏改或改法不一致，proactive 和 reactive path 的 EventLog payload 会不同
  - 这 6 个函数是纯数据访问器，不应按调用方复制
- **为什么有问题**: 违反 project CLAUDE.md "禁止胶水 seam" 和 "模块间依赖最小化" 原则。这些 helper 应该放在 `compaction_operation.py`（与 `CompactionRejectedAttemptDiagnosticReference` 定义同模块）或 `context_events.py`（EventLog payload 构造模块），由两个 caller 共享导入。
- **直接证据**: `grep -n '_diagnostic_offending_' dayu/host/dispatch.py dayu/host/engine_ingest.py` 显示两个文件各有一份完整副本
- **影响**: 后续维护负担 / 可能出现 proactive/reactive payload 形状不一致
- **建议改法和验证点**: 将 6 个 helper 移至 `compaction_operation.py`，与 `CompactionRejectedAttemptOffendingBlock` / `CompactionRejectedAttemptDiagnosticReference` 定义放在一起；dispatch.py 和 engine_ingest.py 从 compaction_operation 导入
- **修复风险（低）**: 纯代码移动，语义不变
- **严重程度（中）**: 当前功能不受影响，但 maintenance 风险真实

### 4-未修复-低-plan 中的冗余常量未集中管理

- **位置**: Plan lines 86–120 in current `compaction_operation.py` code (已实现)
- **问题类型**: 最佳实践偏离
- **当前写法**: `compaction_operation.py` 定义了 15+ 个模块级 `_DIAGNOSTIC_*` 私有常量。其中 `_COMPACTION_REJECTED_DIAGNOSTIC_SCHEMA_VERSION`、`_COMPACTION_REJECTED_DIAGNOSTIC_MEDIA_TYPE` 等与 schema 契约强相关，当前只在 `compaction_operation.py` 中定义，外部需要引用时需通过 `__all__` 或 import。
- **反例/失败场景**: 如果未来有其他模块（如 smoke 脚本、诊断工具）需要按 media type 或 descriptor_kind 查找 diagnostic artifact，当前没有统一的常量导出点
- **为什么有问题**: Plan line 33 说 "define any new kind/media/schema strings in the owning Host module unless implementation evidence shows a cross-module constant is needed"。当前常量散布在 `compaction_operation.py`，而 `descriptor_kind` 字符串 `"compaction_rejected_attempt_diagnostic"` 在 `write_compaction_rejected_attempt_diagnostic_artifact()` 中硬编码。consistent with plan 但缺乏明确的 export surface
- **直接证据**: `_DIAGNOSTIC_DESCRIPTOR_KIND_COMPACTION_REJECTED_ATTEMPT` 常量存在，但 `__all__` 只导出 4 个符号（不含 diagnostic 常量）。如果有测试需要构造 descriptor query，无法按常量引用
- **影响**: 轻微——plan 明确说暂不集中管理，后续可演进
- **建议改法和验证点**: 当前可接受；若未来跨模块引用增多，应提升到 `compaction_operation.py` 的 `__all__` 或抽到独立 schema 模块
- **修复风险（低）**
- **严重程度（低）**: 不影响当前功能

## Final Plan Review Conclusion

**FAIL** — plan 不是 code-generation-ready。

### 阻塞因素

1. **严重缺陷**: `engine_ingest.py` 的 reactive diagnostic wiring 放错方法。`_append_reactive_compaction_requested_event` （没有 `operation_id`/`rejected` 参数）中被错误插入了 diagnostic write 调用，而正确的 `_append_reactive_compaction_attempt_rejected_event` 缺少这个调用。pyright 证实 19 个 `reportUndefinedVariable` 错误。修复方法明确（移除错误调用，在正确方法中添加），risk 低。

2. **零测试覆盖**: Plan 要求的 8 个测试场景一个都没有实现。1,116 行新代码无测试保护，无法证明 core invariants（raw text 不进 EventLog、descriptor metadata 正确、best-effort failure 安全降级）。

### 非阻塞发现

3. `_diagnostic_offending_*` helper 在 dispatch.py 和 engine_ingest.py 中重复定义，应提取到共享模块。
4. 常量导出面偏窄，但不影响当前功能。
