## Findings

### 1-已修复-中-`AgentRunRequest.stream` 字段已声明但 Agent 实现中从未消费

- **Controller decision status**: accepted
- **Fix status**: fixed
- **Re-review status**: fixed
- **入口/函数**: `_AsyncAgent.run_messages` / `run_agent_messages`
- **文件(行号)**: `dayu/engine/contracts/agent_run.py:80`（声明），`dayu/engine/agent.py:447-701`（Agent 主循环）
- **输入场景**: 调用方传入 `AgentRunRequest(stream=False, ...)`，期望 Agent 不产出 delta 事件或只产出 completed 事件。
- **实际分支**: Agent 主循环无条件产出所有事件。`self._request.runner_options.stream` 被传给 Runner 控制 HTTP 流式行为，但 `self._request.stream` 从未被读取。
- **预期行为**: 要么 `stream=False` 时 Engine 跳过 `CONTENT_DELTA` / `REASONING_DELTA` 事件，只产出 `CONTENT_COMPLETED`；要么该字段应明确标注为预留字段或直接移除。
- **实际行为**: 无论 `stream` 取何值，Agent 行为完全一致，所有 delta 事件均被产出。
- **直接证据**: `dayu/engine/agent.py` 全文搜索 `self._request.stream` 无任何匹配（第 447-701 行的 `run_messages` 方法无该引用）。Runner 调用传递的是 `self._request.runner_options`（第 918 行），其中 `RunnerCallOptions.stream` 控制的是 HTTP 层面流式行为，与 Engine 事件层面"流式提升"是不同的语义层。
- **影响**: 调用方根据文档设置 `stream=False` 但实际行为不变，属于契约与实现不一致的静默失效。若上层依赖此字段做 UI 流式展示控制，会出现预期非流式但仍收到 delta 事件的情况。
- **建议改法和验证点**:
  1. 决策该字段的语义归属：如果"流式提升"的控制应属于 `RunnerCallOptions.stream`，则从 `AgentRunRequest` 删除 `stream` 字段。
  2. 如果 Engine 确实需要独立的"流式提升"开关（区别于 Runner HTTP streaming），则应在 `_consume_runner_event` 中根据 `self._request.stream` 跳过 delta 事件。
  3. 无论哪种方案，都需要补充测试证明 `stream=False` 的行为差异。
  4. 同步更新 `dayu/engine/README.md` 中关于 `stream` 字段的描述。
- **修复风险（中）**: 若选择方案 1（删除字段），需确认所有调用方构造 `AgentRunRequest` 时传入的 `stream` 参数不受影响；若选择方案 2（实现分支），需确认 delta 事件的跳过不影响 `CONTENT_COMPLETED` 的内容拼接正确性。
- **严重程度（中）**
- **Gateflow 回写**: 已删除 `AgentRunRequest.stream`，保留 `RunnerCallOptions.stream` 为唯一流式控制真源；见 `docs/reviews/gateflow-fix-agent-run-request-stream-20260511.md` 与 `docs/reviews/gateflow-re-review-engine-contract-readme-20260511.md`。

### 2-已拒绝-低-`EngineEvent` 移除 `event_id`/`sequence` 后消费者失去内置幂等与排序锚点

- **Controller decision status**: rejected-with-reason
- **Fix status**: not-fixed-by-design
- **Re-review status**: not-required
- **入口/函数**: `EngineEvent` dataclass
- **文件(行号)**: `dayu/engine/contracts/engine_events.py:300-319`
- **输入场景**: Host observer（如 tool trace、审计、指标采集）需要持久化事件并在恢复/重连后去重。
- **实际分支**: N/A（设计决策，非代码分支）。
- **预期行为**: 旧版 `EngineEvent` 提供 `event_id`（`f"{run_id}:{sequence}"`）作为幂等写入键，`sequence` 作为 run 内单调递增序号。
- **实际行为**: 新版 `EngineEvent` 不含 `event_id`、`sequence`。设计文档定位为："事件顺序由 EngineEvent 异步流产出顺序定义；EngineEvent 不提供事件 id、事件序号、持久化游标或幂等写入键"。
- **直接证据**: `engine_events.py:314-319` 仅包含 `occurred_at`、`session_id`、`run_id`、`type`、`data`、`metadata` 六个字段。`agent.py:1763` 的 `_make_event` 方法不再生成 `event_id` 或推进 `sequence`。测试 `test_agent_phase2.py:374-375` 移除了 `sequence` 单调性与 `event_id` 唯一性断言，代之以 `session_id`/`run_id` 一致性断言。
- **影响**: 每个 Host observer 需要自行实现事件去重与排序机制。若多个 observer 各自实现且不一致，会导致 trace/审计/指标之间的事件关联困难。这不是 bug，是架构取舍——Engine 不承担基础设施责任，但增加了消费者的实现负担。
- **建议改法和验证点**: 当前设计决策明确且一致，不建议回退。但建议在 `dayu/engine/README.md` 或 `docs/engine/design.md` 中补充说明：消费者如需幂等写入，推荐以 `(run_id, 事件在流中的序号)` 或 `(run_id, occurred_at, type)` 组合作为幂等键。同时建议在 Host 实现阶段验证各 observer 的去重行为是否一致。
- **修复风险（低）**: 不涉及代码修改，仅文档补充。
- **严重程度（低）**
- **Gateflow 回写**: 用户已明确确认 `event_id` / `sequence` 移除是 Engine 边界决策；EngineEvent 不承担事件持久化游标、事件序号或幂等写入键职责，因此不修复、不补上层实现建议。
