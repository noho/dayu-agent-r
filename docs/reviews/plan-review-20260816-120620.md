# UF-FIX08 existing-source-auto-repair Plan Review

## Reviewed Target

- artifact：`docs/gateflow/uf-fix08-existing-source-auto-repair-plan-20260816.md`
- goal confirmation：`docs/gateflow/uf-fix08-existing-source-auto-repair-goal-confirmation-20260816.md`
- scope：Adversarial plan review，重点攻击完整性分类封闭性、trusted revision、manifest 缺失与 sibling source、staged recheck、snapshot/download 同源、public contract 耦合、slice sequencing。

## Assumptions Tested

1. 四态分类（MISSING/COMPLETE/REPAIR_REQUIRED/UNSAFE）可以形成封闭事实集合，覆盖所有 source publication 状态。
2. UNSAFE 的 `revision=None` 策略可以防止 consumer 把部分可信 revision 当 repair authority。
3. 统一 inspector 可以替代 classifier、snapshot、commit validator 三处重复解析。
4. `reset_source_document_for_repair()` 的 staged recheck 可以防止 stale publication 覆盖。
5. 6 个 implementation slice 可以独立保持 pyright 可检查且测试边界清楚。
6. `_can_skip_upload` 在 repair 时可以正确短路为 false。
7. manifest missing repair 可以从 staged tree 唯一重建 canonical manifest。
8. repair disposition contract 可以避免 `ingestion_runtime` 与 Docling pipeline 循环依赖。

## Findings

### 01-未修复-中-`_can_skip_upload` 缺少 repair disposition 传入机制

- **位置**: §7.1 filing auto repair、§8.1 `docling_upload_service.py` 修改说明
- **问题类型**: 不可直接实施
- **当前写法**: plan 声明 "`DoclingUploadService.prepare_upload()` 新增 required keyword `repair_disposition`" 且 "`repair 时 `_can_skip_upload()` 必须短路为 false`"。但 `_can_skip_upload` 是 `prepare_upload` 内部调用的模块级私有函数，签名仅为 `(previous_meta, source_fingerprint, overwrite) -> bool`，不接收 `repair_disposition`。
- **反例/失败场景**: implementation agent 可能选择在 `prepare_upload` 内部用 `if isinstance(repair_disposition, ExistingSourceAutoRepair): skip = False` 包裹 `_can_skip_upload` 调用，这虽然能工作但绕过了函数签名契约；或者 agent 可能忘记传递导致 repair 时仍然 skip。
- **为什么有问题**: plan 的 §4 semantic owner 表明确实要求 "repair 时禁用 identical skip"，但没有给出从 `prepare_upload` 到 `_can_skip_upload` 的精确传参路径。implementation agent 需要自行决定是修改 `_can_skip_upload` 签名还是在调用处短路，两种方案都有合理性但 plan 没有指定。
- **直接证据**: `docling_upload_service.py:1214` 的 `_can_skip_upload` 签名不含 disposition 参数；plan §7.1 说 "repair bypass identical skip" 但未指定机制。
- **影响**: implementation agent 需重新设计，可能引入不一致的 bypass 方案。
- **建议改法和验证点**: 在 §7.1 或 §8.1 明确 `_can_skip_upload` 签名扩展为 `(previous_meta, source_fingerprint, overwrite, *, repair_disposition: NoExistingSourceRepair | ExistingSourceAutoRepair) -> bool`，或明确在 `prepare_upload` 内部用 `if not isinstance(repair_disposition, NoExistingSourceRepair): skip = False` 包裹。测试需覆盖 "fingerprint 相同 + repair → converter 被调用且不 skip"。
- **修复风险**: 低
- **严重程度**: 中

### 02-未修复-中-`read_filing_upload_state` 语义变更缺乏内部实现路径

- **位置**: §5.3 upload published state、§8.1 `_fs_filing_upload_state_core.py` 修改说明
- **问题类型**: 不可直接实施
- **当前写法**: plan 要求 "`_FsFilingUploadStateMixin.read_filing_upload_state()` 在同一 publication guard 内取得 company meta 和 source inspection"，且 `FilingUploadPublishedState` 新增 `source_integrity: SourceIntegrityClassification` required field。但当前实现（`_fs_filing_upload_state_core.py:71`）只在 guard 内读取 `company_meta` 和 `source_meta`，不运行 inspector。
- **反例/失败场景**: implementation agent 需要在 publication guard 内调用 unified inspector，但 inspector 是新模块（slice 2 创建），而 `read_filing_upload_state` 修改在 slice 3。如果 slice 2 的 inspector 接口不支持 "在同一 guard 内同时获取 company meta + source inspection"，slice 3 可能需要重构 inspector 或引入新的 guard 嵌套。
- **为什么有问题**: plan 的 §5.3 说 "不能先 classify 再调用 public `get_source_meta()` 二次加锁/回读"，这意味着 inspector 必须在同一个 guard hold 内完成。但 plan 没有指定 inspector 函数是否接受 guard token 参数，或者是否在 guard 内部调用时自动复用已持有的锁。
- **直接证据**: `_fs_filing_upload_state_core.py:71-105` 的 `read_filing_upload_state` 只读取 company_meta 和 source_meta；`_fs_source_integrity.py` 尚不存在（slice 2 新建）。
- **影响**: slice 2 和 slice 3 之间可能出现接口不匹配，迫使 implementation agent 返工 inspector 设计。
- **建议改法和验证点**: 在 §6.1 明确 inspector 的调用约定——是否接受已持有的 publication guard token，还是在 guard 内直接调用时自动检测。建议 inspector 函数签名包含可选的 `guard_token` 参数，或在 guard 内调用时使用 `_unguarded` 变体。
- **修复风险**: 低
- **严重程度**: 中

### 03-未修复-低-UNSAFE 对 `has_same_source_publication_identity` 的 ValueError 语义

- **位置**: §5.1 状态不变量
- **问题类型**: 契约缺失
- **当前写法**: "``has_same_source_publication_identity()`` 只接受同 target 的 `MISSING/COMPLETE/REPAIR_REQUIRED`；任一参数 `UNSAFE` 立即 `ValueError`"。
- **反例/失败场景**: 当前 `has_same_source_publication_identity` 已有 "任一 `UNSAFE` → ValueError" 的契约（plan §5.1 声明），但现有代码的 `SourceIntegrityClassification.__post_init__` 不允许构造 `UNSAFE` 状态（只有 3 个 enum 值）。这意味着 UNSAFE 的 ValueError 行为只能在 slice 1 扩展 enum 后测试，而 slice 1 的测试文件只列了 `test_fins_storage_atomicity.py` 和 `test_fins_ingestion_runtime.py`。
- **为什么有问题**: 这不是 plan 设计缺陷，而是 slice 1 的测试覆盖需要显式包含 `has_same_source_publication_identity(UNSAFE, COMPLETE)` 的 ValueError 断言。plan 的 §11.1 test matrix 已覆盖 "has_same... 拒绝 unsafe"，但 slice 1 的 allowed files 没有明确包含这个测试点。
- **直接证据**: plan §9 Slice 1 的 "先写 contract tests，证明 invalid combinations 不能构造" 涵盖了此场景，但没有在 test matrix 中显式列出 `has_same_source_publication_identity` 对 UNSAFE 的行为。
- **影响**: 轻微——implementation agent 大概率会在 slice 1 的 contract tests 中覆盖，但 plan 没有强制。
- **建议改法和验证点**: 在 §11.1 补充 "`has_same_source_publication_identity(UNSAFE, *) -> ValueError` 且 `has_same_source_publication_identity(*, UNSAFE) -> ValueError`"。
- **修复风险**: 低
- **严重程度**: 低

### 04-未修复-中-commit validator URI 验证归属不清

- **位置**: §6.1 私有 inspector、§9 Slice 2
- **问题类型**: 架构边界
- **当前写法**: plan 要求 "commit validator 改用同 inspector 并只接受 `COMPLETE`"。但当前 `_validate_complete_source_files`（`_fs_storage_infra.py:1362`）额外验证 URI 模式 `local://{staging_ticker_key}/{source_kind_dir}/{document_key}/{name}`，这是 staging 特有的验证，published inspector 不需要。
- **反例/失败场景**: 如果 commit validator 完全委托给 inspector，URI 验证会丢失（inspector 不验证 URI）。如果 inspector 增加 URI 验证，published classifier 会因为没有 staging context 而无法验证 URI。implementation agent 需要决定 URI 验证留在 commit validator 还是移入 inspector。
- **为什么有问题**: plan §6.1 说 "commit validator 用 inspector 遍历 staging source kinds，要求每个 source=`COMPLETE`"，但没有说明 commit validator 是否保留 URI 验证作为 inspector 之外的额外检查。
- **直接证据**: `_fs_storage_infra.py:1397-1407` 的 URI 验证逻辑是 staging 特有的；`_classify_source_integrity_unguarded` 不验证 URI。
- **影响**: implementation agent 可能错误地把 URI 验证移入 inspector（破坏 published classification），或者在 commit validator 中保留重复的文件验证逻辑（违背 plan 的 "消除重复" 目标）。
- **建议改法和验证点**: 在 §6.1 明确 "commit validator 在 inspector 返回 `COMPLETE` 后，额外验证 URI 模式和 staging containment；inspector 不验证 URI"。§11.1 test matrix 已覆盖 "staged URI mismatch"（22 个 failure case 之一），但需要确认这个测试在 refactor 后仍然测试 commit validator 而非 inspector。
- **修复风险**: 低
- **严重程度**: 中

### 05-未修复-低-slice 2 和 slice 3 的依赖顺序风险

- **位置**: §9 Slice 2、§9 Slice 3
- **问题类型**: 切片过粗
- **当前写法**: slice 2 创建 inspector 并重构 classifier/snapshot/commit validator；slice 3 修改 `read_filing_upload_state` 和 validator eligibility。slice 2 的 allowed files 包含 `_fs_source_document_core.py` 和 `_fs_storage_infra.py`，slice 3 也包含 `_fs_filing_upload_state_core.py`。
- **反例/失败场景**: slice 2 修改 `_fs_source_document_core.py` 的 classifier 委托 inspector 后，slice 3 需要在 `_fs_filing_upload_state_core.py` 中调用 inspector。如果 slice 2 的 inspector 接口不支持 slice 3 的 "同一 guard 内获取 classification + meta" 需求，slice 3 可能需要回头修改 slice 2 已经重构的代码。
- **为什么有问题**: 这不是严重的 sequencing 问题，因为 slice 2 和 slice 3 的 allowed files 不重叠（slice 2 不含 `_fs_filing_upload_state_core.py`，slice 3 不含 `_fs_source_document_core.py`）。但 slice 3 依赖 slice 2 的 inspector 接口，如果接口设计不当会导致返工。
- **直接证据**: plan §9 slice 2 和 slice 3 的 allowed files 列表。
- **影响**: 轻微——合理的 inspector 接口设计可以在 slice 2 时一次性完成。
- **建议改法和验证点**: 在 §6.1 补充 inspector 的 public function signatures（至少 `inspect_published_source` 和 `inspect_staged_source` 的参数和返回类型），确保 slice 3 可以直接消费。
- **修复风险**: 低
- **严重程度**: 低

### 06-未修复-低-repair 期间 snapshot 可见性窗口

- **位置**: §7.2 download 与 snapshot
- **问题类型**: 状态机漏洞
- **当前写法**: "snapshot 只接受 `COMPLETE` inspection。`REPAIR_REQUIRED/UNSAFE` 不打开 consumer-visible source；因此 downstream 不可能在 repair commit 前读到半状态。"
- **反例/失败场景**: 在 repair 的 begin batch 和 commit 之间，published tree 仍为 old（COMPLETE）。如果此时 snapshot 读取 published tree，它会看到 old COMPLETE 状态——这是正确行为。但如果 repair 的 `reset_source_document_for_repair()` 已经 reset 了 staging 中的 target（步骤 5），而 commit 还没完成，此时 `classify_staged_source_integrity()` 对 staging 会看到什么？reset 后的 target directory 不存在 → MISSING。这不会影响 published snapshot，但如果有代码错误地读取 staging snapshot，会看到 MISSING。
- **为什么有问题**: plan 已正确设计了 "published tree 仍为完整 old" 保证，staging 的 MISSING 是预期行为（reset 后等待新 assets 写入）。这不是漏洞，但值得在 test matrix 中显式验证 "repair 期间 published snapshot 仍为 COMPLETE"。
- **直接证据**: plan §7.1 步骤 "reset target directory" 在 begin batch 之后、commit 之前。
- **影响**: 极低——plan 已有正确设计，只需测试确认。
- **建议改法和验证点**: 在 §11.3 补充 "repair 期间 published snapshot 仍返回 old COMPLETE" 测试。
- **修复风险**: 低
- **严重程度**: 低

### 07-未修复-中-manifest rewrite 时 non-target source 的 canonical items 来源

- **位置**: §6.2 staged repair recheck 与 manifest rewrite
- **问题类型**: 契约缺失
- **当前写法**: "取得所有非 target staged sources 的可信 canonical manifest items；若任一非 target 不是 `COMPLETE`，抛 typed unsafe/conflict"。reset 后 "用第 4 步的 canonical items 重写该 source-kind manifest"。
- **反例/失败场景**: plan 说 "无剩余 source 时写合法空 manifest 或按现有 storage canonical empty 规则处理"。但 "canonical items" 的生成方式没有明确：是从 staged sources 的 meta 重新计算 `FilingManifestItem.from_source_meta(meta).to_dict()`，还是直接读取 staging 中已有的 manifest 文件？如果 staging 的 manifest 本身已损坏（这正是 REPAIR_REQUIRED 的一种 reason），从 manifest 读取会得到损坏数据。
- **为什么有问题**: plan §5.2 第 7 点说 manifest missing 可修复的条件是 "所有 source metas 可唯一产生整份 canonical manifest"。这意味着 canonical items 应该从 meta 计算，而不是从 manifest 文件读取。但 plan §6.2 步骤 4 没有明确说明这一点。
- **直接证据**: plan §5.2 第 7 点和 §6.2 步骤 4。
- **影响**: implementation agent 可能从 staging manifest 读取 items（如果 manifest 存在但内容损坏），导致损坏数据被写入新 manifest。
- **建议改法和验证点**: 在 §6.2 步骤 4 明确 "canonical manifest items 从每个 COMPLETE source 的 meta 计算 `FilingManifestItem.from_source_meta(meta).to_dict()`，不从 manifest 文件读取"。§11.3 test matrix 已覆盖 "manifest missing repair 会基于所有 remaining complete sources 重写全量 canonical manifest"，但需确认测试断言 canonical items 来源。
- **修复风险**: 低
- **严重程度**: 中

## Plan Review Conclusion

**pass-with-risks**
