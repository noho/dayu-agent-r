以下是对 8 个审查维度的逐项 evidence-based 结论：

### 1. Context Governance 仍为 reject truth owner；9 条 section cap issue 精确

- **直接证据**: `context_governance.py:492-505` 中 `session_summary.text` 的 actual 来自同一执行路径的 `estimate_memory_size_units(candidate.session_summary.text).units`，cap 来自 `policy.session_summary_char_cap`；message 包含精确数字和直接缩减动作。`_section_caps`（行 559-577）同样从 `len(texts)` 和 `estimate_memory_size_units` 获取 actual，从调用方传入的 policy instance 获取 cap，新增 `size_measurement` 参数携带业务可读计量说明。renderer（`llm_compaction.py:667-677`）只调用 `_repair_feedback_prompt_json_vnext(feedback)` 并序列化，不读取 policy、不重算 cap。
- **测试覆盖**: `test_all_section_cap_violations_preserve_nine_exact_actionable_issues` 构造 summary + 4 section × (item + size) = 9 条越界，逐条断言 exact message（含 actual/cap/计量/动作），验证 `additional_issue_count == 0`，projected block 9 条完整且总长不超过 `MAX_COMPACT_REPAIR_FEEDBACK_CHARS`。
- **结论**: reject truth owner 未漂移；cap 反馈精确、可执行、来自同源 policy instance。

### 2. `_repair_feedback_prompt_json_vnext` 只接受 typed input，精确投影

- **直接证据**: `llm_compaction.py:680-703` 函数签名 `feedback: CompactRepairFeedbackV2`，首行 `isinstance` 检查拒绝非 typed input，直接读取 `feedback.required_action` 和 `feedback.issues`，逐 issue 读取 `issue.code.value`、`issue.json_path`、`issue.message`、`issue.source_labels`。不调用 `feedback.to_json()`，不接受 raw Mapping。projected block 顶层精确为 `required_action` + `issues`，issue 精确为 `code/json_path/message/source_labels`。
- **测试覆盖**: `test_repair_feedback_is_separate_and_requires_whole_candidate` 验证 `isinstance(feedback, CompactRepairFeedbackV2)`，断言 `projected == {"required_action": ..., "issues": [...]}`，对 raw dict 输入 `pytest.raises(TypeError)`。
- **结论**: 投影函数类型安全、字段精确、无 raw mapping 泄漏。

### 3. Internal durable serialization 完整；LLM-facing block 不暴露治理字段

- **直接证据**: `CompactRepairFeedbackV2.to_json()`（`compaction.py:1662-1673`）仍返回 `previous_attempt_number`、`issues`、`additional_issue_count`、`required_action` 四字段；docstring 已改为"durable/internal serialization JSON"。`_compactor_input_projection_json`（`llm_compaction.py:624`）仍调用 `feedback.to_json()` 写入 durable artifact。LLM-facing projector 只输出 `required_action` + `issues`。
- **测试覆盖**: `test_repair_feedback_is_separate_and_requires_whole_candidate` 断言 `internal_json` 包含全部四字段，projected 只含两字段，`forbidden_internal_term` 列表（`previous_attempt_number`、`additional_issue_count`、`CompactRepairFeedbackV2`、`CompactValidationIssueV2`、`Memory policy`）均不出现在 serialized block 中。
- **结论**: 内部 truth 完整保留；LLM-facing block 不暴露治理字段或内部类型名。

### 4. First attempt 无 repair block；repair attempt 恰一对新 marker；旧 marker 已移除

- **直接证据**: `_user_prompt_vnext`（`llm_compaction.py:665-677`）`if repair_feedback is None: return rendered` 确保 first attempt 无 repair block。repair path 追加 `f"\n\n{_REPAIR_FEEDBACK_BEGIN}\n" + json.dumps(...) + f"\n{_REPAIR_FEEDBACK_END}"`，独占行配对。`grep -r 'PREVIOUS_VALIDATION_REPORT' dayu/` 返回空，旧 marker 已从 production path 完全移除。
- **测试覆盖**: 测试断言 first_prompt 不含 `_REPAIR_FEEDBACK_BEGIN/END`，repair_prompt 恰各一行；`_OLD_REPAIR_FEEDBACK_MARKER` 不出现在 first/repair prompt 中。
- **结论**: marker 行为正确，旧 marker 清除干净。

### 5. 两份 prompt 自足、无歧义、schema/example 一致

- **直接证据**: system prompt（`conversation_compaction.md:17-20`）说明 marker 含义、顶层两必填字段、issue 四字段类型/必填性、`source_labels` 非业务材料、whole-candidate 动作。user prompt（`conversation_compaction_user.md:72-87`）补充完整字段说明含"必填"标记、业务可读含义、最小 JSON 示例。两份 prompt 对 `required_action`/`issues`/`code`/`json_path`/`message`/`source_labels` 的描述一致。示例 JSON 与 `json.dumps(sort_keys=True)` 输出字段顺序一致（`issues` 在 `required_action` 前）。user prompt 示例中 `required_action` 文本与 production `COMPACT_REPAIR_REQUIRED_ACTION` 常量一致。
- **测试覆盖**: `test_prompt_assets_are_self_contained_for_fresh_v2_contract` 断言两份 prompt 包含全部必要 marker/schema/字段说明/非业务材料声明。`test_repair_feedback_is_separate_and_requires_whole_candidate` 断言 `COMPACT_REPAIR_REQUIRED_ACTION in user_prompt`。
- **结论**: prompt 自足、无歧义、认知负担低、schema/example 真实一致。

### 6. All-section simultaneous cap test 真实触发 9 条且证明无截断

- **直接证据**: `_all_section_cap_candidate()` 构造 2 items × 4 section + summary = candidate；`item_cap=1, char_cap=1` 使每个 section 产生 item + size 两条 issue，summary 产生 size 一条，共 9 条。测试断言 `len(rejected.issues) == 9`、`len(feedback.issues) == 9`、`additional_issue_count == 0`。逐条比对 expected_messages dict（从同源 policy + estimate_memory_size_units 计算 actual），projected block 9 条完整且 `len(json.dumps(projected)) <= MAX_COMPACT_REPAIR_FEEDBACK_CHARS`。
- **结论**: 测试是 owner-level 的，不固化 fixture 错误语义；9 条完整保留、未截断。
