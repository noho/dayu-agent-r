### 1-HIGH-read_model reset 无条件删除全部 timeline items 与 run results，多 consumer 场景下数据丢失

- **入口/函数**: `reset_minimal_read_model_projection` (`dayu/host/durable/read_model.py:280-301`)
- **文件(行号)**: `read_model.py:292-293`
- **输入场景**: 两个不同的 projection consumer 共享同一数据库；consumer A 需要 reset 自己的投影
- **实际分支**: `DELETE FROM host_session_timeline_items` 和 `DELETE FROM host_run_results` 不带 WHERE 子句
- **预期行为**: reset 应按 `consumer_id` 限定范围，只删除当前 consumer 的数据
- **实际行为**: 无条件全表删除，consumer B 的数据也被销毁
- **直接证据**:
  ```python
  # read_model.py:292-293 — 无 WHERE consumer_id 过滤
  transaction.execute(f"DELETE FROM {TABLE_HOST_SESSION_TIMELINE_ITEMS}")
  transaction.execute(f"DELETE FROM {TABLE_HOST_RUN_RESULTS}")
  # 而同函数的 projection_checkpoints / projection_failures 则有 consumer_id 过滤:
  transaction.execute(
      f"DELETE FROM {TABLE_HOST_PROJECTION_FAILURES} WHERE consumer_id = ?",
      (consumer_id,),
  )
  ```
- **影响**: 多 consumer 场景下数据丢失（当前单 consumer 部署不受影响，但防御深度不足）
- **建议改法和验证点**: 若 `host_session_timeline_items` 和 `host_run_results` 表无 `consumer_id` 列，需先加列再在 DELETE 中增加 WHERE 过滤；或至少在此函数中增加"仅单 consumer"前置断言
- **修复风险**: 中。涉及 schema 变更（加列）和已有数据迁移
- **严重程度**: 高

### 2-HIGH-dispatch_one 对所有非 CancelledError 异常统一按 worker_startup_timeout 关闭，误分类可恢复暂态错误

- **入口/函数**: `HostDispatchScheduler._dispatch_one` (`dayu/host/dispatch.py:533-539`)
- **文件(行号)**: `dispatch.py:533-539`
- **输入场景**: `_start_worker` 或 `_mark_dispatching_after_recheck` 抛出 `HostTransactionRetryExhaustedError`（DB busy 耗尽重试次数）或 WorkerProxy 初始化时的瞬时网络错误
- **实际分支**: `except Exception as exc` 捕获所有非 `CancelledError` 异常，执行 `_safe_closeout_worker_startup_timeout(record, original_error=exc)`，触发 terminal closeout
- **预期行为**: `HostTransactionRetryExhaustedError` 等可恢复暂态错误应让 dispatch loop 重试而非 terminal closeout
- **实际行为**: DB 瞬时压力下，Run 被错误地 terminal closeout，用户需重试整个 Run
- **直接证据**:
  ```python
  # dispatch.py:533-539
  except Exception as exc:
      try:
          self._safe_closeout_worker_startup_timeout(
              record, original_error=exc
          )
      finally:
          await _safe_release_lane_token(token)
  ```
- **影响**: DB 瞬时压力下 Run 被错误终止；用户需重试
- **建议改法和验证点**: 区分 `HostTransactionRetryExhaustedError` 等可重试错误与不可恢复错误；对可重试错误返回特定状态让 drain loop 延迟重试
- **修复风险**: 中。需修改 dispatch 错误分类逻辑，确保不引入无限重试
- **严重程度**: 高

## Open Questions

1. **terminal_attempt_row SUSPENDED 路径**：当前 `terminal_attempt_row` 不支持 SUSPENDED 源状态。是否所有 upstream cancel 路径都有独立 closeout 机制处理 SUSPENDED Attempt？需要沿 `cancel_run` → `closeout_attempt_terminal` → `terminal_attempt_row` 完整链路验证
2. **_HostCancellationToken 的 is_cancelled() 和 cancel_reason() 分两次获取锁**（`dispatch.py:235-251`）：当前因 cancel 是单向操作无 TOCTOU 问题，但若未来引入 `reset_cancel()` 需改为原子读取
3. **MemoryProjectionRepairRequired 的阈值 50 是否应参数化**：高吞吐场景下一次 dispatch 产生超过 50 条 EventLog event 是可能的，导致频繁 rebuild
4. **DurableMemorySnapshotProvider cursor 计算是否存在竞态**：`read_checkpoint` 和 `read_event_log_tail_cursor` 不在同一事务中读取

## Residual Risk

1. **并发投影 consumer 竞争**：当前单连接 + BEGIN IMMEDIATE 序列化保证安全，但缺乏测试覆盖
2. **Wait adapter poll 在外部系统调用期间无事务保护**：已通过幂等键缓解，但 adapter 可能产生额外外部调用（计费影响）
3. **InMemoryRunLocalDuplicateGovernance 进程重启丢失**：docstring 已声明为已知限制，后续 phase 需 durable duplicate ledger
4. **测试覆盖集中于 happy path**：failure paths、boundary conditions、async race conditions 测试严重不足
5. **`assert_never` -O 模式风险**：生产部署需避免 `-O` 标志，或替换为显式 raise
