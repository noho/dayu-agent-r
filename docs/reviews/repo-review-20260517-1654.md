## Findings

### 01-未修复-中-session cancel 幂等重放只重新传播一个 active worker 的 cancel

- **入口/函数**: `_CancelSessionRunsOperation.__call__` -> `_idempotent_session_cancel_result` -> `_active_cancelling_targets_for_session_replay`
- **文件(行号)**: `dayu/host/admission.py` L1384-1402（幂等记录）, L2273-2312（幂等重放）
- **输入场景**: Session 下有多个 active worker Run（例如 2 个 RUNNING Attempt），调用 `cancel_session_runs` 成功取消全部，之后同一 `client_request_id` 重放
- **实际分支**: 首次操作在 `first_active_cancel_event_id` 中只记录了第一个 active cancel event id；重放时 `_active_cancelling_targets_for_session_replay` 只从该 event id 读回一个 Run，返回最多一个 `ActiveCancelTarget`
- **预期行为**: 幂等重放应重新传播所有原始操作中取消的 active worker cancel，确保 best-effort 传播的完整重试
- **实际行为**: 只重新传播第一个 active worker 的 cancel，其余 active worker 的 cancel 传播在重放时丢失
- **直接证据**: `admission.py:1391-1399` 幂等记录只存一个 `first_active_cancel_event_id`；`admission.py:2291` 只 `read_event_by_id(record.created_event_id)` 读一个 event；`admission.py:2294` 只 `read_run_by_id(event.run_id)` 读一个 run；返回单元素 tuple `admission.py:2305-2312`
- **影响**: 如果首次 session cancel 的 worker cancel 传播部分失败（例如 worker 2 的 cancel 未到达），幂等重放不会补救。Worker 可能在 Session 已被取消后继续运行，直到自然超时或完成
- **建议改法和验证点**: 将幂等记录改为存储所有 active cancel event ids 列表（或改为 session-scope 的 run 级别幂等键），重放时遍历所有已取消的 CANCELLING Run 重新传播。验证点：构造多 active worker session cancel 场景，首次传播部分失败后重放，确认所有 worker 均收到 cancel
- **修复风险（低/中/高）**: 中 -- 需要修改幂等记录 schema 或改用 run-scope 幂等
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-中-Engine Agent 硬编码依赖 AsyncOpenAIRunner 实现

- **入口/函数**: `_build_runner()` / `run_agent_messages()` / `run_agent_and_wait()`
- **文件(行号)**: `dayu/engine/agent.py` L109（import）, L258-261（实例化）
- **输入场景**: 任何 `run_agent_messages` / `run_agent_and_wait` 调用
- **实际分支**: `_build_runner` 无条件构造 `AsyncOpenAIRunner`
- **预期行为**: Engine 层只依赖 `AsyncRunner` Protocol，不直接依赖具体 Runner 实现；`agent.py` 作为 Engine 公共入口应通过协议抽象解耦 runner 选择
- **实际行为**: `agent.py` 直接 import 并硬编码实例化 `AsyncOpenAIRunner`，违反分层架构中 "下层组件接口必须假设上层组件不存在" 的约束
- **直接证据**: `from dayu.engine.runners.openai.runner import AsyncOpenAIRunner`（L109），`return AsyncOpenAIRunner(spec=request.runner_spec, ...)`（L258-261）。代码中有 TODO 注释："后续如果需要其它 Runner，必须先新增明确的 runner 选择契约"
- **影响**: Engine Agent 与 OpenAI Runner 实现强耦合；若需新增 Runner（如 Anthropic native），必须修改 Agent 层代码；也无法在测试中方便地注入 mock Runner
- **建议改法和验证点**: 将 `_build_runner` 提升为 `AgentRunRequest` 上的一个 factory callback 字段（如 `runner_factory: Callable[[AgentRunRequest], AsyncRunner]`），或由 Host 在构造 `AgentRunRequest` 时直接注入 `runner` 实例。`agent.py` 只 import `AsyncRunner` Protocol。验证点：构造自定义 Runner 注入的 AgentRunRequest，确认 Agent 不直接依赖具体实现
- **修复风险（低/中/高）**: 低 -- `_build_runner` 是纯工厂函数，提取为 callback 不影响状态机逻辑
- **严重程度（低/中/高/严重）**: 中 -- 当前只有一个 Runner 实现，耦合尚未造成实际问题，但随着 provider 增多会成为维护障碍

### 03-未修复-低-OperationContext 可选字段校验不一致

- **入口/函数**: `OperationContext.__post_init__`
- **文件(行号)**: `dayu/host/api.py` L872-894
- **输入场景**: 构造 `OperationContext` 时 `business_object_type=""` 或 `scenario=""`
- **实际分支**: `business_object_type` 和 `scenario` 未调用 `_require_optional_non_empty`；`business_object_id` 和 `correlation_id` 调用了
- **预期行为**: 所有 `str | None` 可选字段应一致地校验：存在时非空
- **实际行为**: `business_object_type` 和 `scenario` 设为空字符串 `""` 时通过校验，而同类字段 `business_object_id` 和 `correlation_id` 会抛 `ValueError`
- **直接证据**: `api.py:886-894` 只校验了 `business_object_id` 和 `correlation_id`，遗漏了 `business_object_type`(L867) 和 `scenario`(L869)
- **影响**: 空字符串 `business_object_type` 或 `scenario` 可进入 semantic digest 计算，导致相同语义内容产生不同 digest，破坏幂等性
- **建议改法和验证点**: 在 `__post_init__` 中为 `business_object_type` 和 `scenario` 补充 `_require_optional_non_empty` 调用。验证点：构造 `business_object_type=""` 的 `OperationContext` 确认抛出 `ValueError`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-低-session cancel 对 RECOVERING Run 直接失败而非跳过

- **入口/函数**: `_CancelSessionRunsOperation._read_supported_targets_or_raise` -> `_session_cancel_target_for_run`
- **文件(行号)**: `dayu/host/admission.py` L1414-1438 和 L2360-2361
- **输入场景**: Session 下有 Run A（RUNNING）、Run B（RECOVERING），调用 `cancel_session_runs`
- **实际分支**: `_session_cancel_target_for_run` 对 RECOVERING 返回 `None`；`_read_supported_targets_or_raise` 遇到 `None` 直接抛 `UNSUPPORTED_OPERATION`
- **预期行为**: RECOVERING 是少见的中间状态，session cancel 应跳过 RECOVERING Run 而非整体失败，允许取消其他可取消的 Run
- **实际行为**: 整个 `cancel_session_runs` 操作因一个 RECOVERING Run 而全部失败，RUNNING 的 Run A 也不会被取消
- **直接证据**: `admission.py:2360-2361` `if run.status == RunStatus.RECOVERING: return None`；`admission.py:1427-1436` `if target is None: raise HostApiError(UNSUPPORTED_OPERATION, ...)`
- **影响**: 存在 RECOVERING Run 时，用户无法通过 `cancel_session_runs` 取消其他可取消的 Run，必须等 RECOVERING 结束或单独取消每个 Run
- **建议改法和验证点**: 将 `_read_supported_targets_or_raise` 中对 `None` 的处理改为跳过而非抛错（或增加 `skip_unsupported` 选项）。验证点：构造 RECOVERING + RUNNING 混合 Session，确认 RUNNING Run 被成功取消
- **修复风险（低/中/高）**: 低 -- 改为跳过即可，不影响已有正确路径
- **严重程度（低/中/高/严重）**: 低（RECOVERING 是少见状态，且有单 Run cancel 替代路径）

### 05-未修复-低-dispatch drain_loop 异常静默丢失

- **入口/函数**: `HostDispatchScheduler._drain_loop`
- **文件(行号)**: `dayu/host/dispatch.py` L482-494
- **输入场景**: `drain_once` 内部因未预期异常（非 `CancelledError`）崩溃
- **实际分支**: `_drain_loop` 无 try/except 包裹 `drain_once`，异常导致 task 静默完成（exception 被 asyncio task 框架吞掉）
- **预期行为**: drain loop 意外退出时应有诊断日志，便于排查 dispatch 停滞
- **实际行为**: drain loop 因异常退出后无任何日志；下次 `wake_dispatch` 会创建新 task，但中间所有 pending dispatch 会被延迟到下次 wakeup
- **直接证据**: `dispatch.py:482-494` `_drain_loop` 方法体无 try/except；`dispatch.py:411` `wake_dispatch` 通过 `self._drain_task.done()` 检测并重建 task，但无日志说明前一个 task 异常退出
- **影响**: dispatch scheduler 在未预期异常后静默停止处理队列，直到下一次 `wake_dispatch` 调用。期间所有 pending dispatch 被延迟，可能导致 Run 卡在 QUEUED 状态
- **建议改法和验证点**: 在 `_drain_loop` 中加 try/except 捕获非 CancelledError 异常并记录 warning 日志。验证点：注入异常确认日志输出且后续 `wake_dispatch` 能恢复
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 06-未修复-低-ToolResultFailure 缺少构造期校验

- **入口/函数**: `ToolResultFailure` dataclass
- **文件(行号)**: `dayu/contracts/tool_result.py` L54-69
- **输入场景**: 任意构造 `ToolResultFailure(error="", message="", ...)` 的场景
- **实际分支**: `ToolResultFailure` 没有 `__post_init__` 校验；`error` 可为空字符串、`message` 可为空字符串或纯空白
- **预期行为**: 与同模块的 `ToolCancelledOutcome`（`tool_outcome.py` L124-127）保持一致的最小完整性校验：`error` 必须非空、`message` 必须非空非纯空白
- **实际行为**: `ToolCancelledOutcome` 校验了 `message`（非空非纯空白）和 `hint`（非空非纯空白）。同模块的 `ToolResultFailure` 对 `error` 和 `message` 无任何校验，允许构造出无效的失败记录
- **直接证据**: `tool_outcome.py` L124-127 有 `__post_init__` 校验；`tool_result.py` L54-69 无 `__post_init__`
- **影响**: 当前消费方都传入了合法值，但契约层自身不保证 invariant，后续新消费方可能构造出空 error code / 空 message 的 `ToolResultFailure`
- **建议改法和验证点**: 为 `ToolResultFailure` 添加 `__post_init__`，校验 `self.error.strip() != ""` 和 `self.message.strip() != ""`
- **修复风险（低/中/高）**: 低 -- 当前所有构造点都已传入合法值
- **严重程度（低/中/高/严重）**: 低
