## Assumptions tested

1. `s_0003 -> s_0013` 是 owner-legal、source-isolated 且在 `read_section_max_chars=80000` 内可完整读取的 material chain。
2. production effective `max_iterations=20` 来自 `scene_override`，typed hard cap 是 `20 + 1 force_answer = 21`，`25` 只作外部 ceiling。
3. prompt-file 是唯一 prompt owner；strict UTF-8、NUL absent、strip 后非空，并以唯一一个 `--prompt` 后的单一 argv 元素传递。
4. preflight-only 不创建 run/workspace/evidence 路径，不 spawn harness/CLI/provider；empty/NUL fail closed。
5. real mode 会 fail closed 地冻结 target/CLI/model、global/chain identity、1800/180/540 窗口和 current gate。
6. 最多三条 fresh chain 的数量、workspace identity 与每 workspace 一链具有可执行的强约束 owner。
7. real attempt 的 wrapper projection 可由 owner 持久化，而不是靠事后重算 preflight-only 状态。
8. F19 publication补齐F18缺失的per-chain summary、per-attempt public analysis、execution index和显式file-byte digest；F18 tree保持immutable。
9. B2继续为`unadjudicated`，registry保持`calibration`，Agent不会提前接受或标ready。

## Findings

### 01-未修复-[高]-冻结 execution identity 未覆盖 production CLI 与 model
- **位置**: plan `Pre-provider gate` 第19-24行；wrapper `_parse_args`、`_harness_argv`、`_preflight`（`workspace/tmp/f19_formal_driver.py:38-53,258-281,301-327`）
- **问题类型**: 契约缺失 / 状态机漏洞 / 测试缺口
- **当前写法**: plan冻结target commit、production CLI SHA、formal harness SHA与PTY owner SHA，并要求真实MiMo plan；wrapper只把`--cli`和`--model`原样放入argv，`_preflight`只比对harness与PTY owner两项SHA。
- **反例/失败场景**: 调用方给出另一可执行CLI或DeepSeek model，同时仍传入正确harness/PTY owner，preflight会通过，real mode随后会把错误CLI/model交给harness。冻结harness会验证target commit与CLI“是文件”，但只记录CLI SHA，不会与plan冻结的production CLI SHA比较。
- **为什么有问题**: 当前验证只冻结了执行链的一部分，不能证明真实provider调用发生在已确认的production CLI/MiMo identity上；错误identity产生的任何terminal或evidence都不能用于B2。
- **直接证据**: wrapper常量只有`EXPECTED_HARNESS_SHA256`和`EXPECTED_PTY_OWNER_SHA256`（第19-28行）；`_preflight`第301-306行只校验这两项。provider-free实测把`--cli`替换为`/bin/true`，`--preflight-only`仍exit 0并输出合法argv contract。`--model`没有allowlist或expected identity检查。
- **影响**: implementation Agent可能在错误CLI或禁止的provider/model上花费真实调用并生成不可验收 evidence；发现时只能整链作废，浪费bounded budget。
- **建议改法和验证点**: 在wrapper owner中加入冻结的expected CLI file SHA与expected model id，并在任何argv构造/real spawn前直接比对；provider-free preflight同时验证repo HEAD/clean target（或明确引用并验证一个包含target/CLI/model的immutable execution manifest）。新增wrong CLI、wrong model、wrong target均非零退出且`spawn_performed=false/provider_started=false`的自测；正确identity仍保持唯一`--prompt`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 02-未修复-[高]-deadline校验允许错误identity、非法数值与未开始的chain通过
- **位置**: plan `Fresh setup and budgets` 第33-39行；wrapper `_positive_number`、`_json_object`、`_deadline`（`workspace/tmp/f19_formal_driver.py:98-113,134-148,151-236`）
- **问题类型**: 状态机漏洞 / 契约缺失 / 并发恢复风险
- **当前写法**: plan声明global文件必须满足`deadline=start+1800`、`cutoff=deadline-180`，chain文件必须绑定当前chain/global且同链复用；wrapper只检查run/chain id非空、global窗口不超过1800、reserve不少于180、chain窗口不超过540及global文件SHA相等。
- **反例/失败场景**: 任意非空run/chain id、1000秒global window+300秒reserve、尚未到`chain_start`的future chain，甚至JSON/Python可表示的`NaN`时间字段均可被`_deadline`接受并产生正timeout；文件也没有与当前`run-root`、workspace、label或expected run/chain identity绑定。
- **为什么有问题**: “不超过cap”不能替代plan冻结的deadline identity；NaN与future-start绕过使gate不再fail closed。任意合法格式的另一chain文件也可被复用，无法证明R1-R4属于同一已授权chain。
- **直接证据**: `_positive_number`只执行`result <= 0`，没有`math.isfinite`；Python `json.loads`默认接受NaN。第184-190行使用不等式上限而非plan的1800/180 exact identity；第195-203行只读取任意非空`chain_id`并比对global SHA；第204-224行不要求`start <= chain_start <= now <= chain_deadline <= cutoff`。provider-free直接调用实际`_deadline`复现：`short_global_and_300_reserve`、`future_chain_start`和`nan_deadlines`三组均`accepted=true`，NaN组返回effective 540秒。
- **影响**: provider可以在错误run/chain identity或尚未开始的chain窗口内启动；budget evidence与实际执行不再同源，1800/180/540 bounded claim无法审计。
- **建议改法和验证点**: 使用拒绝NaN/Infinity的strict JSON/numeric parser；传入并精确比对expected run id、chain id及immutable chain manifest identity；以明确容差验证global `deadline-start=1800`、`deadline-cutoff=180`，并验证`global_start <= chain_start <= now < chain_deadline <= cutoff`、`chain_deadline-chain_start <= 540`。对short/long window、wrong reserve、future start、NaN/Infinity、wrong ids、wrong global SHA、closed gates逐项断言非零退出且未spawn。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 03-未修复-[高]-real mode计算wrapper projection后直接丢弃，无法满足每attempt owner evidence
- **位置**: plan `Evidence and publication` 第63-64、70-72行；wrapper `main`（`workspace/tmp/f19_formal_driver.py:356-394`）
- **问题类型**: 契约缺失 / observability gap / review不可验收
- **当前写法**: plan要求每个attempt private capture保存wrapper projection，并发布wrapper summary；wrapper在real mode算出包含prompt SHA/argv contract/deadline budget的`preflight`对象，但仅在`--preflight-only`分支调用`_emit`。
- **反例/失败场景**: real调用通过deadline后在第372-377行形成正确projection，随后第381-394行直接spawn并返回，projection没有stdout、文件或下游参数owner；若spawn失败或进程被中断，real prompt/budget projection永久缺失。preflight-only输出的budget固定为`not_frozen_preflight_only`，不能证明real invocation使用的deadline或timeout。
- **为什么有问题**: F18 publication失败的根因之一就是public/private execution identity缺口；F19若仍靠事后从prompt/deadline/command重算，会再次制造第二真源，违反plan自己要求的wrapper projection与项目语义所有权约束。
- **直接证据**: 第372行把结果赋给`preflight`；第378-380行只在preflight-only emit；real分支没有任何`_emit`或projection传递，直接在第388行`subprocess.run`。plan第63行明确把wrapper projection列为每attempt private minimum。
- **影响**: 即使provider行为正确，attempt仍缺少可与real argv/deadline同源的owner evidence，publication可能再次判nonconforming并浪费真实调用。
- **建议改法和验证点**: 为real mode增加必填、attempt-owned且位于harness evidence目录之外的exclusive projection输出；在spawn前原子写入包含execution identity、prompt source/forwarded SHA、唯一argv contract、deadline/chain identity与effective timeout的projection，失败也保留。harness结束后只追加独立terminal ref文件或由execution index引用，禁止回写原projection。验证real spawn被测试替身阻断时projection已存在且hash稳定；preflight-only不得冒充real projection。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 04-未修复-[中]-“最多三条fresh chain”只有文字约束，没有冻结manifest供driver验证
- **位置**: goal第20-21行；plan `Adaptive chain state machine` 第43-56行；wrapper参数与deadline读取（`workspace/tmp/f19_formal_driver.py:38-53,192-214`）
- **问题类型**: 契约缺失 / 过度耦合 / 资源治理漏洞
- **当前写法**: plan要求最多三条fresh有效候选链、每workspace一条，并把所有attempt写入execution index；driver接受任意workspace/evidence-dir及任意非空chain id，不读取预冻结的allowed-chain集合。
- **反例/失败场景**: 在global cutoff仍开放时，调用方可以为第四个workspace创建新的chain deadline并再次调用driver；现有校验会接受，因为它只验证该文件自身窗口和global SHA。事后execution index记录第四条不能恢复“最多三条”的先验治理。
- **为什么有问题**: bounded observation次数是用户明确的成本与证据约束，不能只靠调用者纪律或事后publication统计；driver与Controller之间缺少最小的immutable authorization contract。
- **直接证据**: plan第43行声明最多三条，但没有定义run-owned allowed-chain manifest；wrapper没有chain ordinal/role/allowed workspace输入，第195-197行只要求`chain_id`非空。
- **影响**: 错误编排可消耗超出授权的真实provider链数，并使formal observation不符合用户限定；旧attempt不能覆盖删除，只能整体披露为越界。
- **建议改法和验证点**: deadline前由Controller独占冻结最多三个chain entries的run manifest（chain id、role、workspace/profile/input digest）；driver real mode必须验证当前chain/workspace属于该manifest，同一workspace只对应一条chain，R1-R4复用相同chain deadline。provider-free测试第四chain、unknown workspace、重复role/错workspace均fail closed且未spawn。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
