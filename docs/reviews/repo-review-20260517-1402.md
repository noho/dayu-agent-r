### 05-未修复-中-lane.py asyncio.shield 双调用模式可能导致内存状态与 DB 不一致

- **入口/函数**: `_try_claim_once`（L549-571）、`_release_token`（L698-728）、`_release_untracked_claim`（L741-770）
- **文件(行号)**: `dayu/runtime/lane.py:553, 712, 715, 759, 762`
- **输入场景**: 外层 task 在 `await asyncio.shield(release_task)` 期间被 `task.cancel()` 取消
- **实际分支**: 第一个 `shield` 抛 `CancelledError`；`except` 块中第二个 `shield(release_task)` 重新等待
- **预期行为**: 第二个 `shield` 应等待 inner task 完成后再更新内存状态
- **实际行为**: 根据 CPython 文档，`shield` 不抑制外层 task 的 `CancelledError`。如果外层 task 的 `cancel()` 已被调度，第二个 `await asyncio.shield(release_task)` 可能在第一个 `await` 点立即抛 `CancelledError`，导致 `_mark_token_released` 未执行
- **直接证据**: `lane.py:715` 的 `await asyncio.shield(release_task)` 在 `except CancelledError` 块内；`lane.py:726` 的 `self._mark_token_released(token)` 在 shield 之后
- **影响**: 内存中 `token.released` 为 `False` 但 DB claim 可能已被删除；后续对 token 的操作会尝试删除不存在的 DB row（幂等无害），但 `_held_tokens` 中残留该 token。DB 层由 TTL 兜底清理
- **建议改法和验证点**: 将第二个 `shield` 替换为直接 `await release_task`（已取消的 outer context 下，改用 `asyncio.wait` 确保 inner task 完成）；构造外层 cancel 在 DB release 已提交但 `_mark_token_released` 未执行的窗口验证
- **修复风险（低/中/高）**: 中（需改动三处相同模式，需同步更新测试）
- **严重程度（中）**

## Open Questions

1. **`_build_runner` 的演进路线**: 当前 `agent.py` 硬编码 `AsyncOpenAIRunner`。未来需要支持非 OpenAI 兼容协议时，Runner 创建逻辑应放在哪一层？是 Host 层通过 `AgentRunRequest` 注入，还是 Engine 层维护 Runner registry？

2. **Memory projection 的 unsupported event type 前向兼容策略**: 当前遇到未知 event type 会产出 `SNAPSHOT_DAMAGED` diagnostic，但不会阻止 projection 推进。如果新版本 Host 写入了新 event type，旧版本 Host 读取时会产生 misleading diagnostic。是否需要版本协商机制？

3. **Host instance liveness 的 crash detection 由谁触发**: `liveness.py` 定义了 `CRASHED_SUSPECTED` 状态，但当前代码中没有模块将实例标记为此状态。这是否由外部 recovery 流程完成？

4. **`asyncio.shield` 双调用模式在 CPython 3.11+ 下的确定性行为**: F05 的实际影响取决于 `await asyncio.shield(release_task)` 在 outer task cancelled 状态下是否立即抛 `CancelledError`。建议用最小复现脚本验证。

5. **Engine contracts 到 Host API 的类型传递是否需要 adapter 层**: 当前 `api.py` 直接引用 Engine types，import boundary test 允许此路径。但长期看，Engine 的 `AgentRunRequest` 变更会直接影响 Host 公共 API 的兼容性。
