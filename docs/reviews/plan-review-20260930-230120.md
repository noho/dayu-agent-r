## 3. Lenses 审查

### 3.1 项目指令 / Goal-bound minimal design

- 每个 slice 决定（5 个符号、4+3+2 文件边界、测试矩阵、README 决定）均可直接映射到 binding goal 的成功信号（唯一封闭真源、生产/解析直接消费、移除私有常量 import、非法仍拒绝、serialized 与 direct/job 投影保持）；未发现 goal drift、额外验收标准或 future-slice 工作。
- 计划显式拒绝了会扩大目标的做法：不选 StrEnum、不做 get_args 反射生成词表、不加 runtime validation 分支、不迁移每文档词表/reason_code、不搬迁 `CnPipelineDownloadResult`、不改取消与完整性分类。与用户冻结裁决和「不新增 status/错误/取消/manifest 成功语义」约束一致。
- 「空库/全部文档失败 rebuild 仍为 ok」「strip 接受」「legacy failed 拒绝」等易被实现者好心改坏的行为被显式锁进验收，符合最小保全设计。

### 3.2 架构边界 / 语义所有权

- 词表是 workflow 产生、adapter 校验的跨边界协议事实；owner 放 `cn_download_models`（跨 workflow/downloader 的 typed model 与字面量模块，无 IO）与该模块既有职责一致，且 `cn_pipeline` 已从该模块导入其它字面量，不新增依赖方向。
- 迁移后 adapter 对 workflow 的依赖只剩 `CnDownloadIntegrityAbort` 与 `run_cn_download_stream_impl` 正常符号，删除对私有 `_INTEGRITY_FAILED_STATUS` 的跨模块私有 import——正是「语义 owner 唯一」的修法位置，不是下游补偿。
- 层次不变：仍为 fins pipelines 内部收敛，不触碰 Host/Engine/Service/UI、schema、durable state。顶层终态在 adapter 校验后不持久化（`_project_cn_pipeline_summary` 不消费顶层 status），变更面比持久化协议更小。

### 3.3 过度耦合 / 过度设计 / 最优性

- 单 slice S1 覆盖 4 个生产文件是该问题的最小内聚单元（owner 定义 + 全部 producer + 全部 consumer 必须同改，拆开只会留下混合词表中间态）；不过粗。
- 5 个符号、无新模块/协议/DTO/状态机，无 wrapper/re-export/兼容层；`CN_DOWNLOAD_NORMAL_TERMINAL_STATUSES` 子集 tuple 是「普通入口合法子集」语义的直接声明，非多余抽象。
- 在 credible alternatives 中（StrEnum / 新模块 / 分散常量保留 + 仅删私有 import），Literal+Final 单 owner 是与现有风格和 JSON 原生 str 投影最贴合、改动面最小的路径；未发现更简单或更安全的替代。
- 测试计划要求独立字面量预期、交叉拒绝、全 producer 断言，不允许同源常量自证；与「测试断言 owner 级 contract」约束一致。
