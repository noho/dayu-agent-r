### 2-1-[HIGH]-S1 event_type 闭集范围被严重低估，blast radius 把一个"small cleanup"变成了全仓 event type 重定向

- **位置**: Section 5 S1, "Allowed files / modules" (plan lines 418-448)
- **问题类型**: 切片过粗 / 不可直接实施 / 范围漂移
- **当前写法**: Plan 列出 20+ consumer 文件，但描述 slice 为 "small-cleanup budget"。S1 的 allowed files 包括 `engine_ingest.py`（6000+ 行）、`dispatch.py`、`waiting.py`、`tool_runtime.py` 等 Hot Path 模块，以及 12 个 consumer 文件。Concrete allowed changes 说 "Update event-type producers to pass typed values or owner-serialized values."
- **反例/失败场景**: 当前代码中 event type 字符串分散在 ~20 个模块的 ~35 个不同值中，每个模块定义自己的 `_EVENT_TYPE_*` 私有常量。Implementation agent 必须：
  1. 扫描所有 20+ 文件找到所有 event type 字面量
  2. 确定完整合法集合（plan 未提供）
  3. 在每个 producer 把 `event_type="RUN_STARTED"` 替换为 typed 引用
  4. 在每个 consumer 把 `if event.event_type == "TOOL_CALL_REQUESTED"` 替换为 typed 比较
  5. 更新所有使用 `TYPE_A`、`host.test`、`TEST_EVENT` 等任意 event type 的测试
  6. 确保 admission.py、run_transition.py、engine_ingest.py 等关键 Hot Path 模块不因 event type 变更引入回归

  这不是 "small cleanup"——这是一次横跨几乎所有 EventLog producer/consumer 的全仓重构。
- **为什么有问题**: Plan 自称 "matching the control document's small-cleanup budget"（plan line 402），但 S1 的实际 blast radius 与 small-cleanup 预算矛盾。Controller adjudication 明确警告 "This is intentionally not first in P3 because it can turn into broad schema churn"（adjudication line 225）。Plan 没有采纳这个警告——S1 就是 broad schema churn。
- **直接证据**:
  - `grep -rn '_EVENT_TYPE_' dayu/host/ --include="*.py"` 返回 50+ 个私有常量定义分布在 admission.py, run_transition.py, engine_ingest.py, tool_trace.py, read_api.py, outbox.py, memory.py, waiting.py, dispatch.py, compact_material.py, run_input.py, compaction_operation.py, accepted_result_projection.py, tool_runtime.py, payload_resolution.py 等模块
  - Controller adjudication line 225: "This is intentionally not first in P3 because it can turn into broad schema churn."
  - Plan line 402: "matching the control document's small-cleanup budget"
- **影响**: Implementation agent 要么陷入多日跨模块回归调试，要么被迫做表面修复（只加 DDL CHECK 不重定向 consumer）而达不到 owner boundary 目标。
- **建议改法和验证点**:
  1. **首选方案（缩小 S1 范围）**: S1 只做 EventLog append validation + DDL CHECK + `EventLogAppendRequest.event_type` 类型化，不做 consumer 重定向。Consumer 重定向延后到后续 phase，让 S1 真正保持 small-cleanup 规模。
  2. **次选方案（拆分 S1）**: 按 event type 类别拆成子 slice：S1a（lifecycle event types，已有 HostRunEventType/HostAttemptEventType owner）、S1b（tool event types）、S1c（context/diagnostic event types）。每种子 slice 可以独立验证。
  3. 在 plan 中提供完整的当前 production event type 枚举（从代码扫描产出），而不是让 implementation agent 自行发现。
- **修复风险（中）**: 缩小范围或拆分 slice 需要重新规划，但不影响已接受的 finding disposition。

### 2-2-[HIGH]-queue_policy "alias" 写法与项目"禁止兼容性 re-export"约束直接矛盾

- **位置**: Section 5 S1, "Concrete allowed changes" (plan lines 462-464)
- **问题类型**: 架构边界 / 不可直接实施
- **当前写法**: "Replace admission-local `AdmissionPolicy` duplication or make it an alias to the single owner without compatibility re-export."
- **反例/失败场景**: Plan 说 "make it an alias ... without compatibility re-export." 但 alias（`AdmissionPolicy = RunQueuePolicy`）**就是** compatibility re-export——它让旧名字继续可用，只是转发到新 owner。CLAUDE.md 明确禁止：
  > "兼容性 re-export：仅为保持旧导入路径而转发符号。"

  正确的做法只有一种：删除 `AdmissionPolicy`（当前仅在 `admission.py` 内使用，无外部 consumer），在 durable 层定义 `RunQueuePolicy`，把 `admission.py` 内所有引用改为 `RunQueuePolicy`。Plan 的 "or make it an alias" 给了 implementation agent 一个被项目约束禁止的选项。
- **为什么有问题**: 模糊或不一致的指令会让 implementation agent 选择最省力的路径（alias），直接违反项目最高约束。
- **直接证据**:
  - Plan line 462-464: "Replace admission-local AdmissionPolicy duplication or make it an alias to the single owner without compatibility re-export."
  - CLAUDE.md: "禁止兼容性代码：兼容性 re-export：仅为保持旧导入路径而转发符号。"
  - `grep -rn 'AdmissionPolicy' dayu/ --include="*.py" | grep -v test` 确认 `AdmissionPolicy` 仅在 `admission.py` 内定义和使用，无外部 consumer——删除是安全的。
- **影响**: Implementation agent 可能引入被项目明确禁止的 compatibility re-export。
- **建议改法和验证点**: 删除 "or make it an alias" 措辞。明确写：删除 `AdmissionPolicy` 枚举，在 durable 层定义 `RunQueuePolicy` 为唯一 owner，更新 `admission.py` 所有引用。验证点：`grep -rn 'AdmissionPolicy' dayu/` 返回零结果。
- **修复风险（低）**: 仅需修改 plan 措辞，不改变实现意图。
- **严重程度（高）**:

- **问题类型**: 不可直接实施 / open question 未收敛

- **建议改法和验证点**:

### 2-4-[MEDIUM]-S2 idempotency scope/result kind DDL CHECK 可能锁死未来扩展

- **位置**: Section 5 S2, "Concrete allowed changes" (plan line 559)
- **问题类型**: 过度设计 / 状态机漏洞
- **当前写法**: "DDL CHECK for both columns is allowed only after the audit confirms no intentionally open extension point."
- **反例/失败场景**: Idempotency scope 本质上是 operation-level 的——每个新的 Host operation（如新的 admission 策略、新的 wait 类型）都可能引入新的 scope_kind。把 scope_kind 锁在 DDL CHECK 里意味着：
  1. 新增 operation type 需要 schema migration（不仅是 Python enum 更新）
  2. 旧数据库无法接受新 scope kind，即使该 scope 只在代码路径中产生
  3. 测试需要处理 DDL CHECK 拒绝 vs Python validation 拒绝的两层 fail-closed 行为

  当前代码中 `_SESSION_FACT_SCOPE_KINDS`（`dayu/host/durable/purge.py:139`）已经表明某些 scope 需要作为集合查询——这表明 scope 是可扩展的，不是 closed set。
- **为什么有问题**: Plan 的 stop condition "after the audit confirms no intentionally open extension point" 把决策推给了 implementation agent，但 plan 没有提供 audit 的结果。当前代码证据显示 scope_kind 是 operation-driven 的——新 operation = 新 scope_kind——这是一个 intentionally open extension point。DDL CHECK 会制造不必要的 schema migration 负担。
- **直接证据**:
  - `dayu/host/durable/purge.py:139`: `_SESSION_FACT_SCOPE_KINDS = (...)` — scope 作为集合查询，暗示新 scope 可能被添加
  - `dayu/host/admission.py:161-167`: 7 个 operation 常量用作 scope_kind——每个新 operation 需要新 scope_kind
  - Plan line 559: "DDL CHECK for both columns is allowed only after the audit confirms..."
- **影响**: 未来添加新 operation type 需要 schema migration；旧数据库拒绝新 scope kind；增加不必要的运维复杂度。
- **建议改法和验证点**:
  1. S2 只做 Python-level typed validation（`IdempotencyScope.scope_kind` 类型化），不做 DDL CHECK。
  2. 在 plan 中明确：idempotency scope/result kind 的 DDL CHECK 仅在 scope set 被设计证明为 closed（不会因新 operation 扩展）时才添加。当前代码证据不支持 closed 假设。
- **修复风险（低）**: 去掉 DDL CHECK 不影响 Python-level 类型安全。
- **严重程度（中）**:

### 2-5-[MEDIUM]-S2 descriptor kind fail-closed 引入 producer-consumer 耦合

- **位置**: Section 5 S2, "Concrete allowed changes" (plan line 563)
- **问题类型**: 过度耦合
- **当前写法**: "`payload_resolution` must parse descriptor kind through the owner and fail closed on unknown / missing / mismatched values."
- **反例/失败场景**: `payload_resolution.py` 是 consumer——它消费其他模块写入的 payload descriptor。Plan 要求 consumer fail closed on **unknown** values。这意味着：
  1. 任何新 producer 添加新 descriptor kind（例如新的 tool type 引入新的 payload 格式），必须同时更新 `payload_resolution.py` 的合法值列表
  2. 这引入了之前不存在的 producer→consumer 耦合——之前 `_validate_descriptor_kind` 只验证 expected kind（调用方指定），不验证 "known set"
  3. 如果 `payload_resolution` 维护一个 "all known descriptor kinds" 集合，它就成了 descriptor kind 的第二个 owner（dual owner with descriptor kind owner module）

  当前代码中 `_validate_descriptor_kind` 只做 expected-kind 匹配（`metadata.get("descriptor_kind") != expected_kind`）——调用方自己指定期望值。Plan 的 "fail closed on unknown" 改变这个语义，让 consumer 承担 owner 职责。
- **为什么有问题**: "Fail closed on unknown" 是 producer 端验证职责（在写入时拒绝未知 descriptor kind），不是 consumer 端职责。Consumer 应该只验证它需要的是否匹配，不应该维护一个全局已知 descriptor kind 注册表。
- **直接证据**:
  - `dayu/host/payload_resolution.py:338`: `if metadata.get(_FIELD_DESCRIPTOR_KIND) != expected_kind` — 当前只做 expected match，不验证 "known set"
  - Plan line 563: "fail closed on unknown / missing / mismatched values"
- **影响**: 新增 descriptor kind 需要同时修改 producer、owner、consumer 三处；payload_resolution 变成事实上的第二个 descriptor kind owner。
- **建议改法和验证点**: Consumer 只 fail closed on missing/mismatched（保持当前行为），不 fail closed on unknown。Unknown descriptor kind 的拒绝应在 producer 端（payload writer）通过 typed owner 完成。在 plan 中删除 "unknown" 从 consumer 的 fail-closed 列表中。
- **修复风险（低）**: 仅修改 plan 措辞，不影响 producer 端验证。
- **严重程度（中）**:

### 2-6-[MEDIUM]-Event type 单一 flat enum vs 类别层次结构未解决

- **位置**: Section 3.1, "Owner" (plan lines 67-69)
- **问题类型**: 架构边界 / 最佳实践偏离
- **当前写法**: "Implementation may extend `dayu/host/lifecycle_events.py` if it remains the single event-type owner, or introduce a new `dayu/host/event_types.py` only if all existing lifecycle event helpers are redirected to that owner in the same slice."
- **反例/失败场景**: 当前架构中 `lifecycle_events.py` 已经定义了 `HostRunEventType`（10 个 lifecycle event type）和 `HostAttemptEventType`（6 个 attempt event type），以及多个 typed subset（`HOST_RUN_TERMINAL_EVENT_TYPES`、`HOST_RUN_LIFECYCLE_EVENT_TYPES` 等）。这些 enum 被 `event_type_values()` helper 消费，用于 projection、read API、outbox、tool trace 等模块。

  如果引入一个统一的 flat `EventType` enum，会破坏现有类别层次：
  - `HostRunEventType` 和 `HostAttemptEventType` 的独立类型安全性丢失
  - `HOST_RUN_TERMINAL_EVENT_TYPES` 等 typed subset 变成从 flat enum 中手动筛选
  - 已有 P3-A 的 lifecycle 收敛工作被重新打开

  Plan 没有解决 `HostRunEventType` + `HostAttemptEventType` + 其他 event type（tool, context, session, diagnostic）如何在单一 owner 中共存。
- **为什么有问题**: 35+ event type 放进一个 flat enum 违反关注点分离原则。Lifecycle event type 的消费者（read model projection、dispatch closeout）不应该看到 tool trace event type。Plan 的 "single owner" 概念需要澄清是单一**模块** owner 还是单一**枚举** owner。
- **直接证据**:
  - `dayu/host/lifecycle_events.py:17-43`: `HostRunEventType` 10 成员 + `HostAttemptEventType` 6 成员，带有 typed subset
  - `dayu/host/tool_trace.py:214-225`: `_CANONICAL_EVENT_TYPES` 通过 `event_type_values(HOST_RUN_LIFECYCLE_EVENT_TYPES)` 组合 lifecycle + tool event types
  - Plan lines 67-69: 二选一 "extend lifecycle_events.py" 或 "new event_types.py"，未解决类别层次
- **影响**: Implementation agent 可能创建 flat enum 破坏现有类型安全层次，或在两个方案之间反复，无法完成 S1。
- **建议改法和验证点**: 在 plan 中明确：event type owner 采用类别枚举结构——保留 `HostRunEventType` 和 `HostAttemptEventType` 在 `lifecycle_events.py`，新增 `HostToolEventType`、`HostContextEventType`、`HostSessionEventType`、`HostDiagnosticEventType` 等类别枚举，由一个统一的 `all_host_event_type_values()` helper 或 `HostEventType = HostRunEventType | HostAttemptEventType | ...` 联合类型提供 DDL CHECK 所需的全集。
- **修复风险（中）**: 需要 plan 阶段设计类别层次，但避免 flat enum 破坏架构。
- **严重程度（中）**:

### 2-7-[LOW]-S1 与 S2 同时修改 admission.py，存在 sequencing 风险

## 3. Findings By Lens

### Architecture Boundary Review

- **Event type owner boundary**: Plan 方向正确（单一 owner），但未解决 `HostRunEventType`/`HostAttemptEventType` 与 flat EventType enum 的层次冲突。见 Finding 2-6。
- **Runtime boundary**: S3 正确识别 `legacy_config_file_names()` 不属于 runtime public API。移入 CLI init 不违反 layering。见 verified assumption A7。
- **Durable layer as owner**: queue_policy 和 idempotency 类型归于 durable 层正确。admission.py 从 owner 降级为 consumer。

### Best-Practice Review

- **"Alias" anti-pattern**: Plan 建议的 "make it an alias" 违反项目禁止兼容性 re-export 约束。见 Finding 2-2。
- **Stop condition as deferred decision**: Plan 把 2 个关键设计决策（event type 完整集合、idempotency 是否 intentionally open）推迟到 implementation agent 的 stop condition，而不是在 plan 阶段解决。这不是最佳实践——plan 应该提供 code-generation-ready 的决策，而不是把 open question 伪装成 stop condition。见 Findings 2-3, 2-4。

### Optimal-Solution Review

- **S1 范围缩小方案**: 把 S1 限制为 EventLog append validation + DDL CHECK + `EventLogAppendRequest` 类型化（不做 consumer 重定向）是更优方案。它达到核心目标（阻止 invalid event type 写入 durable store）但 blast radius 缩小 80%。Consumer 重定向可以延后到 S1 验证通过后的后续 phase。见 Finding 2-1。
- **DDL CHECK 过度**: 对 idempotency scope/result kind 加 DDL CHECK 在当前代码证据下不是最优方案。Python-level typed validation 提供同样的类型安全但不需要 schema migration。见 Finding 2-4。

### Overengineering Review

- **Consumer fail-closed on unknown**: 让 `payload_resolution` fail closed on unknown descriptor kinds 是 overengineering——它把 producer 端职责复制到 consumer 端，引入了不必要的 dual-owner 风险。见 Finding 2-5。
- **RunResultRow 类型化收益**: 将 `terminal_status: str` 改为 `RunStatus` 在 row decoder 已经验证的前提下收益有限。但改动范围可控，不算 overengineering。

### Overcoupling Review

- **S1 event_type owner 耦合 20+ 模块到一个 enum**: 单一 owner 引入的耦合是预期内的（这是 owner 收敛的目标），但 plan 未评估 blast radius。见 Finding 2-1。
- **S1+S2 admission.py 交叉**: 两个 slice 修改同一文件的不同方面，存在轻量 sequencing 风险。见 Finding 2-7。
- **Descriptor kind consumer coupling**: fail-closed on unknown 引入 producer→consumer 耦合。见 Finding 2-5。

## 7. Final Plan Review Conclusion

**Conclusion: pass-with-risks**

Source finding dispositions 经当前代码验证正确。Plan 的动机、非目标和显式禁令设计合理。S3（legacy config cleanup）slice 可直接实施。

**但 S1 和 S2 有两个 material risks 需要在 implementation 前解决**：

1. **S1 的 blast radius（Finding 2-1，严重程度高）**: 当前 scope 把 "small cleanup" 变成了全仓 event type 重定向。建议缩小 S1 为 EventLog append validation + DDL CHECK only，consumer 重定向延后。

2. **queue_policy "alias" 矛盾（Finding 2-2，严重程度高）**: Plan 建议的 "alias" 方案违反项目禁止兼容性 re-export 约束。建议删除 "or make it an alias" 措辞，明确要求删除 AdmissionPolicy。

S2 的 descriptor kind 和 idempotency DDL CHECK 风险（Findings 2-3, 2-4, 2-5，严重程度中）需要在 plan 修订或 implementation 早期阶段解决。

**Material findings: 8（2 高, 4 中, 2 低）**

**Blocking open questions: 5**（见 Section 5），其中 Q1（S1 blast radius）和 Q2（event type 层次）应在 plan 修订阶段解决后再进入 implementation gate。
