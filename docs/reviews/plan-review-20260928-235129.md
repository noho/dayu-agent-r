## 专项复核一：多 filing 中途 typed abort 的守恒语义（上轮 MiMo R1 / Finding 1）

**结论：同源守恒设计成立，事实与 public RESULT 走同一 `filings` 快照与同一 owner 投影，与既有机械终态派生精确吻合。**

| --- | --- | --- |
| 已发布先前候选 | 单 filing owner 事件 `FILING_COMPLETED/FAILED` 的 `filing_result` → workflow `filings`（`cn_download_workflow.py:293-305`）→ `_build_result/_build_summary`（`:366-383`，typed abort 路径复用同一函数构造 `integrity_failed` 快照）→ `CnDownloadIntegrityAbort` 携带 → adapter 复用 `_summary_from_pipeline_result`（`cn_pipeline.py:1403`）→ `_project_cn_document_row` 对 downloaded 行经 `source_repository.get_source_document_locator` 取 storage locator（`cn_pipeline.py:1494-1510`）→ `FinsDownloadResultSummary.from_document_rows` 机械派生计数（`download_contract.py:411-460`） | 与 durable 已 commit 事实同源；不从事件顺序或日志反推 |
| 失败当前候选 | workflow typed 收口自建脱敏 `failed` filing（通用 `source_integrity_preflight` 类别，不复制四值 public reason）→ 同一 `filings` 快照 → `_project_cn_document_row` FAILED 分支（`cn_pipeline.py:1524-1535`，`reason_category=reason_code or "cn_document_failed"`，owner 固定安全 message） | 与既有普通失败行同一投影路径；公开四值 reason 只由 Fins 唯一映射点从原始异常派生 |
| 未开始候选 | 不入 `filings`、不发 `FILING_STARTED`/行、不计数 | 与「不暗示已处理」一致 |

- 计数守恒：`FinsDownloadResultSummary` 既有校验强制 `discovered_count == downloaded+skipped+rejected+failed` 且 `len(document_rows) == discovered_count`（`download_contract.py:359-380`），plan 的「只有已产生终态 filing 事实的候选计入 discovered_count」恰好落进该不变量。`dayu/fins/README.md:567`「total/discovered 必须等于这些分类之和」与 `:598`「对同一候选集合互斥且守恒」在计数集合内保持成立；该口径与既有取消分支同一记账方式（`cn_download_workflow.py:356-383` 只汇总已收集 `filings`）。

- `FinsResultSummary` 放宽点精确存在：`direct_events.py:678-682` 现状拒绝 `FAILURE + PARTIAL_FAILURE`（"failed download result requires failed disposition"）；plan 的修订条件「有 typed public failure 且 failed_count>0」恰好只打开该拒斥，零候选空终态例外（`:465-469`）与 `SUCCESS+PARTIAL_FAILURE`（正常混合完成，`ingestion_runtime.py:4389-4415`）不受影响。

## Findings

### 1-未修复-低-Phase B mutation 配方对未发布候选二的目标目录取得方式未钉死
- **位置**: S1「真实 Phase B mutation 配方」段：「向**候选二目标 source 文档目录**写入真实未声明普通文件 `undeclared.bin`；使用仓储 locator/identity 规则取得目标」。
- **问题类型**: 不可直接实施 / 测试缺口
- **当前写法**: 要求以「仓储 locator/identity 规则」定位候选二目标目录，但未说明 fresh 候选二（未发布）时用哪条规则。
- **反例/失败场景**: fresh 候选二尚无 published meta，`get_source_document_locator` 直接抛 `FileNotFoundError`；目录名是 storage 私有派生 `id-<sha256("filing_document\0"+document_id)>`（`_fs_identity.py:97-144`），仓库测试无既有先例。实施 agent 可能 (a) 在测试内重算哈希（复制 storage 私有规则，脆弱且违反语义所有权约束）、(b) 把文件放错路径（任意名目录只会置 `unassignable_root_fact`，exact-target+MISSING 不升级 UNSAFE，`_fs_source_integrity.py:300/351`），失败将落到 `commit_batch` whole-tree——触发 plan 的「post-commit typed 抛错即停止」条款，空转一轮交总控、或 (c) 改用先发布候选二再 overwrite 复跑的变体（locator 可得，但与「以同请求重跑断言候选一按既有完整来源 skip」的 overwrite=False 前提冲突）。
- **为什么有问题**: 该配方是本轮裁决（MiMo R2）的核心验收点；进入 Phase B 的真实性取决于一个未钉死的路径取得机制，误放会把「Phase B 证据」变成「commit-time 触发」，与「不将未经过目标 Phase B 的测试算作通过」直接冲突。
- **直接证据**: `fs_source_document_repository.py:628-655` 与 `_fs_source_document_core.py:755-784`（locator 要求 meta 存在）；`_fs_identity.py:44-47/97-144`（私有 key 派生）；`tests/fins/test_cn_download_workflow.py:1920` 的既有 mutation 先例是**已发布**目录（locator 可得）；plan 配方段原文未区分已发布/未发布。
- **影响**: 测试缺口或实施 agent 误放路径后误触发停止条款、返工一轮；极端情况下把 commit-time 触发误报为 Phase B 证据（被既有断言拦下，但成本已花）。
- **建议改法和验证点**: plan 配方补一句钉死取得方式：允许测试经 `dayu.fins.storage._fs_identity` 的 identity 派生（`_identity_directory_path`/`_derive_storage_key`）取得未发布目标目录，或改为 fixture 先以 locator 规则创建候选二目录（含 identity descriptor 或仅含 mutation 文件）；明示禁止在测试内重算哈希。验证点：新测试断言 typed 异常确实来自 Phase B（batching phases 为 begin/rollback、无 reset/commit），且 mutation 后 `classify_staged_source_integrity` 真实返回 UNSAFE。
- **修复风险（低/中/高）**: 低（一句话钉死 + 一条断言）
- **严重程度（低/中/高/严重）**: 低
