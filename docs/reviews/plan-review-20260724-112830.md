## 3. Spot-Check 攻击结果

### Spot-check 1: cold_lock_path 的 public reachability 跨层矛盾

**问题**: 计划说 Service 负责构造 `ToolTraceAnalysisSource`（§12.2: `discover_tool_trace_analysis_source(input_path: Path) -> ToolTraceAnalysisSource`），而 Source 需要 `cold_lock_path` 字段（§7.3）。但 lock path 计算逻辑在 Host 内部（`open_host.py` 的 `_default_tool_trace_lock_path` 是私有函数），且计划说 Host root 只导出 analyzer functions/contracts（§8.1: `dayu.host.__init__` 只把 analyzer function 与 public contracts 纳入 package public surface），CLI/Service 不得 import internal（§13 S4: CLI module 只 import Service/public contracts，不 import `dayu.host.durable`）。

**代码事实**:
- `_default_tool_trace_lock_path` 是 `open_host.py:2621` 的私有函数（以 `_` 开头）
- `_LOCK_TIMEOUT_SECONDS = 5.0` 是 `tool_trace.py:224` 的模块级私有常量
- 当前 `dayu/host/__init__.py` 的 `__all__`（97 个符号）不包含任何 tool trace lock 相关符号
- 计划§12.1 说 S1 将在 `dayu/host/tool_trace.py` 新增 `tool_trace_cold_lock_path(cold_jsonl_path: Path) -> Path` 共享 helper

**矛盾**: Service 需要调用 `tool_trace_cold_lock_path` 来构造 Source，但该函数在 Host 内部模块。如果不在 Host public surface 导出，Service 无法合法访问；如果导出，则扩大了 Host public API（计划§8.1 说只导出 analyzer functions/contracts）。

**可能解决方案**:
1. 把 `tool_trace_cold_lock_path` 加入 Host public surface（`__all__`）— 但这与"只导出 analyzer functions/contracts"矛盾
2. 让 `discover_tool_trace_analysis_source` 是 Host public API 而不是 Service API — 但这改变了 Service/Host 边界
3. 让 `ToolTraceAnalysisSource.__post_init__` 自己计算 lock_path — 但这把 Host 内部逻辑泄漏到 public contract
4. 让 Service 调用一个 Host public helper `build_tool_trace_analysis_source(cold_jsonl_path, ...)` 来构造完整 Source

**严重程度**: 高 — 这是一个真实的跨层依赖矛盾，implementation agent 需要重新设计 Service/Host 边界

**建议**: 在§7.3 或§12.1 中明确 Service 如何获取 lock path。最干净的方案是让 Host 拥有一个 public helper `build_tool_trace_analysis_source(requested_path, mode, cold_jsonl_path, hot_db_path, artifact_root) -> ToolTraceAnalysisSource`，内部调用 `tool_trace_cold_lock_path`；Service 只负责路径发现和调用这个 Host public helper。

### Spot-check 2: busy_timeout_seconds 的显式 contract 缺失

**问题**: 计划§8.4 定义 `configure_read_only_connection_pragmas(connection, *, busy_timeout_seconds)` helper，说"由 Host storage policy 秒数转换的非负整数毫秒"。但：
- CLI 声明不使用全局 config（§7.1: 全局 `--base/--config` 对此命令不参与输入发现）
- `ToolTraceAnalysisPolicy` 只有 5 个参数（large_payload_threshold_bytes 等），没有 SQLite timeout
- 计划没有说明 `busy_timeout_seconds` 从哪个显式 contract 取得

**代码事实**:
- `configure_connection_pragmas` 接受 `HostSQLiteStoragePolicy` 参数（`transaction.py:457`）
- `HostSQLiteStoragePolicy.busy_timeout_seconds` 是 timeout 的真源
- 但 CLI 不使用全局 config，所以无法获取 `HostSQLiteStoragePolicy`

**矛盾**: Implementation agent 需要决定 busy_timeout 的值，但计划没有给出显式 contract。可能的选择：
1. 硬编码一个合理默认值（如 5 秒）— 但这违反"禁止魔法数字"约束
2. 从 `HostSQLiteStoragePolicy` 获取 — 但这需要 CLI/Service 传入 policy，与"CLI 不使用全局 config"矛盾
3. 在 `ToolTraceAnalysisPolicy` 中新增字段 — 但这改变了 policy contract

**严重程度**: 中 — Implementation agent 需要自行设计，可能导致不一致

**建议**: 在§8.4 或§9.2 中明确 busy_timeout 的来源。最合理的方案是在 `ToolTraceAnalysisPolicy` 中新增 `sqlite_busy_timeout_seconds: float = 5.0` 字段，或在 `configure_read_only_connection_pragmas` 中使用一个命名常量默认值。

### Spot-check 3: cold lock 阻塞 live producer 风险

**问题**: 计划§7.4 说 reader 持锁期间"打开一次 cold file、读取到 EOF 并复制 immutable bytes snapshot"。现有 producer 获取同一独占锁仅等 5 秒（`_LOCK_TIMEOUT_SECONDS = 5.0`）。如果 cold 文件很大（例如 100MB+），reader 持锁复制整个文件可能需要很长时间（慢盘上可能超过 5 秒），导致 producer timeout 和 projection 失败。

**代码事实**:
- `_LOCK_TIMEOUT_SECONDS = 5.0`（`tool_trace.py:224`）
- reader 也使用同一 5 秒 timeout（§7.4: `TOOL_TRACE_COLD_FILE_LOCK_TIMEOUT_SECONDS = 5.0`）
- `RuntimeFileLock` 是独占锁（`filelock.py:119-218`）
- 当前 workspace cold file 只有 9 行 ~25KB，但计划§17.1 承认"极大 cold 文件的内存/运行时成本"是 tracked risk（Issue #36）

**反例**: 如果 cold 文件增长到 100MB，reader 在慢盘上持锁复制可能需要 10+ 秒。producer 在 5 秒 timeout 后失败，导致 Tool Trace projection 失败，违背 read-only/non-interference 目标。

**短临界区方案**: 锁内只做 open + fstat 获取文件大小和 inode，释放锁后从同一 fd 读取。这更符合 append-only owner 的语义：锁只保护"确认文件边界"的临界区，不保护"读取全部内容"的长操作。

但计划§7.4 明确说"reader 持锁期间...读取到 EOF"，这与短临界区不同。

**严重程度**: 中 — 当前 workspace 文件很小（25KB），不触发；但 Issue #36 的 cold rotation 前，大文件场景是真实风险

**建议**: 在§7.4 中讨论大文件场景的锁持有时间风险，并考虑短临界区方案作为 future optimization。首版可以接受当前设计，但应在§17.1 residual risks 中明确标注。

**问题**: 计划§10.1 JSON 示例使用复数字段：

**严重程度**: 低 — 这是一个 schema 一致性问题，不影响功能

**建议**: 在§10.1 中修正示例为单数字段（`cold_jsonl_path`、`cold_lock_path`），或在§7.3 中将 Source 改为复数字段（`cold_jsonl_paths: tuple[Path, ...]`）。考虑到首版只支持单个 cold file，单数更合理。

### Spot-check 5: "不修改producer"与S1修改共享helper的表述矛盾

**问题**: 计划§3.1 说"不修改 Tool Trace event filter、extract/render、hot/cold producer 或 line schema"。但§12.1 说：
- `dayu/host/tool_trace.py` — 新增 cold lock path/timeout contract
- `dayu/host/open_host.py` — 删除本地重复的 lock suffix/timeout 派生，改用 Tool Trace owner helper

这确实是在修改 producer 相关代码（`open_host.py` 是 producer 的调用点）。

**代码事实**:

- 这改变了 producer 的代码路径，但不改变 producer 的语义行为

**严重程度**: 低 — 这是表述不精确，不是设计错误。正确表述应该是"不修改 producer 的语义行为（event filter、cold schema、append ordering）"，而不是"不修改 producer 代码"。

**建议**: 在§3.1 中修正表述为"不修改 Tool Trace producer 的语义行为：event filter、cold schema、append ordering 和 line digest 计算"。

### Spot-check 6: hot-empty watermark=0 时的 join/limitation 行为

**问题**: 计划§7.4 说"hot store 可用但无 rows 时 watermark 固定为 `0`"。§8.3 join 逻辑说"cold-only row 的 `event_sequence` 高于本次 hot snapshot watermark 时，产生 `input_changed_during_analysis` limitation"。

**推导**: hot-empty (watermark=0) 时：
- 没有 hot rows
- 所有 cold rows 的 event_sequence >= 1（假设从 1 开始）
- 所有 cold rows 都 > 0 = watermark
- 所以所有 cold rows 都会产生 limitation

这意味着 hot-empty 时，整个分析结果全是 limitation，没有正常 findings。

**问题**: 这是否是预期行为？计划没有明确说明 hot-empty 场景的预期输出。

**可能解释**:
1. hot-empty 时，所有 cold rows 都是"input changed during analysis" — 但这意味着 analyzer 无法产生任何 findings
2. hot-empty 时，应该跳过 watermark 检查，直接以 cold-only 模式运行 — 但这需要额外逻辑

**严重程度**: needs-evidence — 需要确认 hot-empty 时的预期行为

**建议**: 在§8.3 或§14.1 中明确 hot-empty 场景的预期行为。如果预期是"所有 cold rows 产生 limitation"，应在 validation matrix 中增加测试场景；如果预期是"跳过 watermark 检查"，应修改 join 逻辑。
