## Findings

### 01-未修复-低-tool 边界 fiscal_period 空值/纯空白行为与 schema「空值语义」未收敛
- **位置**: 「最小实现契约与数据流」第 4 条（tool schema 描述"trim/uppercase/空值语义"）；「S1 测试契约」tool 段（只覆盖域值错误与 bool/非整数）。
- **问题类型**: 契约缺失 / LLM-facing 文本准确性风险。
- **当前写法**: 要求 schema 写明 material fiscal_period 的"trim/uppercase/空值语义"，测试只断言进入 admission 的域值错误（`nonsense`/241 字符）与 tool 参数层类型错误（bool/非整数 year）；`""`/纯空白在 tool 边界的行为既无契约文字也无测试。
- **反例/失败场景**: tool 现状 `_optional_nullable_text` 对 `fiscal_period: ""` 或 `"   "` 直接抛 `ValueError("fiscal_period must be a non-empty string or null")` → tool `invalid_argument`（`_ingestion_tool_helpers.py:152-157`），**不会**像 CLI（`_optional_stripped_text` 空→None）与 owner（`normalize_fiscal_period` 空→None）那样"视为未提供"。实施者按 goal 成功信号 2（"`None`、`""`、纯空白都成为 `None`"）把 schema 写成"空字符串视为未提供"，即与 tool 真实行为相反，LLM 传 `""` 会撞参数错误；或实施者为对齐 schema 改 `_optional_nullable_text`/透传空值，越出文件白名单且违背 OQ1"不得倒逼 adapter 透传"的裁决精神。
- **为什么有问题**: AGENTS.md LLM-facing 文本约束要求 schema 自足且与真实行为一致；OQ1 裁决只收口了 bool/非整数的参数层类型错误，未覆盖空值/纯空白字符串这一 shape 分歧。plan 的"schema 文本准确且自足"验收在该输入上不可判定。
- **直接证据**: `_ingestion_tool_helpers.py:138-157` 与 `upload_tools.py:360`（material `fiscal_period=_optional_nullable_text(...)`）；CLI 对照 `fins.py:1263-1276`；owner 对照 `filing_semantics.py:314-318`；plan 第 4 条与 S1 测试契约 tool 段均未提及 `""`/纯空白。
- **影响**: LLM-facing schema 与工具行为不一致（违反硬约束），或实施越界改动共享参数 helper；两者都可事后发现，但会在 tool 验收面留下未测空白。
- **建议改法和验证点**: plan 显式 pin 一条：tool 边界保持现有参数层拒绝，schema 的"空值语义"写成"省略该参数或传 null 表示未提供；空字符串/纯空白会被参数校验拒绝"，并补一条 tool 测试断言 `""`/纯空白 → `invalid_argument`（不进 Fins admission、零 awaiting handle）。若总控裁决要求 tool 与 CLI 端到端一致（空→None），则该改动必须扩白名单至 `_ingestion_tool_helpers.py` 或改用独立读取分支，并重新裁决（注意 O11 日期字段共享同一 helper，属同模式问题）。
- **修复风险（低）**: 低——一行契约文字 + 一条测试；仅在选择"透传成 None"方案时升为中（牵动共享 helper 与 O11）。
- **严重程度（低/中/高/严重）**: 低

### 02-未修复-低-验证命令依赖本工作区 `.venv`，当前隔离工作区缺失（Sol 失败 command 的可复现根因）
- **位置**: 「验证命令与证据」首句"实现 gate 在本工作区先 `source .venv/bin/activate`"及后续 pytest/pyright/coverage 命令。
- **问题类型**: 最佳实践偏离 / 不可直接实施（环境前置未声明）。
- **当前写法**: 所有 gate 命令假定 `/private/tmp/dayu-upload-fiscal/.venv` 存在。
- **反例/失败场景**: 本工作区当前无 `.venv`：`source .venv/bin/activate` 逐字失败（`no such file or directory`）；无 venv 直跑 pytest 在收集期即 `ModuleNotFoundError: No module named 'docling_core.types.doc.items'`（系统 Python 依赖版本不齐）；`pyrightconfig.json` 的 venv 设置也被 pyright 报 `venv .venv subdirectory not found`。实施 Agent 若随手换解释器，可能收集失败或得到不可比覆盖率输出。
- **为什么有问题**: gate 的验证证据质量依赖正确解释器；plan 对唯一环境前置无一句说明。这与"Sol plan fix JSONL 有失败 command"的信号吻合，独立重证可稳定复现。
- **直接证据**: 本复审实测：`source .venv/bin/activate` 失败；系统 `python3 -m pytest tests/fins/test_fins_ingestion_tools.py --collect-only` 报上述 `docling_core` ImportError；以依赖完整的解释器 + 本 checkout 代码收集六文件得 **771 tests collected**，五生产文件 pyright **0 errors**（命令形式本身有效）。
- **影响**: 实施 gate 第一步即失败，或在错误解释器下产出假阴性/不可比的测试与覆盖率证据。
- **建议改法和验证点**: plan 的验证节补一句环境前置——实现 gate 前在本工作区创建并激活 `.venv`（如 `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`）或明确记录总控指定的解释器；实施验证 artifact 记录所用解释器路径与 `python -V`，coverage 输出注明同一解释器。
- **修复风险（低）**: 低。
- **严重程度（低/中/高/严重）**: 低
