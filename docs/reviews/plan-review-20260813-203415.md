- **Reviewed target**: `docs/gateflow/uf-fix03-summary-bounded-errors-plan-20260813.md`
- **Binding goal contract**: `docs/gateflow/uf-fix03-summary-bounded-errors-goal-confirmation-20260813.md`

- **Lenses applied**: architecture, best-practice, optimal-solution, overengineering, overcoupling

## Assumptions tested

1. `_PendingFileAsset.source` 是 loose `str`，需要收紧为 closed provenance
2. `stored_file_count` 可以从 `stored_entries` 计数中过滤 original 资产
3. `FinsUploadResultSummary` 所有构造点可以机械补齐 counts
4. `upload_failure_reason_from_json` exact-key parser 可以从 4 字段迁移到 5 字段
5. `_build_pending_assets` 逐文件 conversion catch 可以关联唯一 basename
6. 混合 valid+bad 场景下整批零 publication 可以通过 prepare 阶段失败实现
7. CLI generic catch 可以安全替换为固定文案
8. direct path 负断言可以通过 filesystem/API 观察完成

## Findings

### 1-未修复-高-`_FAILURE_KEYS` exact-key parser 迁移未明确旧格式处理路径

- **位置**: §5.4 Closed failure contract, "JSON parser 要求五个 exact keys；不接受旧四字段"
- **问题类型**: 契约缺失 / 过度验收标准
- **当前写法**: plan 要求 `upload_failure_reason_from_json` 的 `frozenset(value) != _FAILURE_KEYS` 检查从 4 key 迁移到 5 key，且"不接受旧四字段"。
- **反例/失败场景**: 当前 `upload_failure.py` line 220: `frozenset(value) != _FAILURE_KEYS` 是一个 frozen set literal 比较。若实施 agent 直接把 `_FAILURE_KEYS` 从 `frozenset({"kind", "code", "message", "retry_hint"})` 改为加 `"file_label"` 的 5 元素 frozenset，任何已持久化的 4 字段 JSON（如 durable job record 中的 failure summary）将立即 `raise ValueError`。plan §3.1 声称"不保留兼容字段"，§9.2 也把"legacy旧summary不可读"归为 residual risk，但 §5.4 没有明确说明这是 breaking change 还是 migration。
- **为什么有问题**: `upload_failure_reason_from_json` 不仅被 `FinsUploadPipelineResult.from_pipeline_json` 调用，也被 durable job record 的 failure summary 恢复路径调用（`ingestion_runtime.py` 中 `_upload_persisted_terminal_progress_payload` 等处）。如果存在未迁移的旧 job record，runtime 会 crash。
- **直接证据**: `upload_failure.py` line 220: `frozenset(value) != _FAILURE_KEYS`；`ingestion_runtime.py` 中多处调用 `upload_failure_reason_from_json`。
- **影响**: 实施 agent 可能不确定是否需要 migration helper 或是否可以纯 breaking；若选错路径会导致 runtime crash 或引入不该有的兼容代码。
- **建议改法和验证点**: plan 应明确：(a) 这是 breaking change，旧 4 字段 JSON 必须 rejected；(b) 需要一次性 migration（删除旧 job record 或写 migration script）；或 (c) parser 暂时接受 4 字段并把 `file_label` 默认为 `None`。选项 (c) 是最安全的实现路径，但 plan 当前禁止它。
- **修复风险（低/中/高）**: 中
- **严重程度（高）**: breaking change 影响持久化数据恢复路径

### 2-未修复-中-`FinsUploadResultSummary` 4 个构造点未全部显式列出

- **位置**: §6.1 Production files — `dayu/fins/ingestion_runtime.py` 和 `dayu/fins/service_runtime.py`
- **问题类型**: 不可直接实施
- **当前写法**: plan §6.1 提到 `ingestion_runtime.py` 中 "runner unavailable、early cancel、direct/job内部 summary 构造点：显式 counts"，但没有列出具体行号或函数名。
- **反例/失败场景**: 实际有 4 个构造点：
  - Site A: `service_runtime.py:131` — early cancelled（当前无 `uploaded_files`，默认 `()`）
  - Site B: `service_runtime.py:303` — `_upload_summary_from_result`（当前从 `request.files` 填 `uploaded_files`）
  - Site C: `ingestion_runtime.py:3874` — direct runner-unavailable（当前无 `uploaded_files`）
  - Site D: `ingestion_runtime.py:4350` — job runner-unavailable（当前无 `uploaded_files`）
  
  若实施 agent 只改了 Site B 而遗漏了 Site A/C/D，`FinsUploadResultSummary` 的 `requested_file_count`/`stored_file_count` 将在部分路径缺失，`__post_init__` 新增的 count 不变量校验会 crash。
- **为什么有问题**: plan 把所有 4 个构造点压缩成一句话描述，没有给实施 agent 明确的行号或函数名指引。
- **直接证据**: 经搜索确认 4 个构造点的行号如上。plan §6.1 只列了文件和大类描述。
- **影响**: 实施 agent 可能遗漏构造点，导致部分路径 count 缺失或 `__post_init__` crash。
- **建议改法和验证点**: 在 §6.1 的 `ingestion_runtime.py` 和 `service_runtime.py` 条目下，显式列出每个构造点的函数名和行号范围。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 遗漏会导致部分路径 crash，但 plan 的 stop condition 和静态审计可以覆盖

### 3-未修复-中-progress payload key rename 是 breaking change 未标注影响范围

- **位置**: §5.3 Runtime terminal/durable contract — "started/preparing progress 将含糊的 `file_count` breaking rename 为 `requested_file_count`"
- **问题类型**: 契约缺失
- **当前写法**: plan 声称要 break-rename `_PAYLOAD_FILE_COUNT`（当前值 `"file_count"`）为 `"requested_file_count"`。
- **反例/失败场景**: `_upload_context_request_progress_payload`（`ingestion_runtime.py:7495`）在 4 个调用点输出 progress payload。如果 CLI renderer 或 Service direct consumer 解析 `"file_count"` key，rename 后它们将拿不到值。plan 没有说明哪些下游 consumer 解析这个 key，也没有说明 rename 的验证方式。
- **为什么有问题**: plan §5.3 说"breaking rename"，但没有标注影响的下游 consumer 和验证策略。
- **直接证据**: `_upload_context_request_progress_payload` 定义在 `ingestion_runtime.py:7495`，使用 `_PAYLOAD_FILE_COUNT` 常量（值 `"file_count"`）。CLI renderer 和 direct event consumer 解析 progress payload。
- **影响**: 若下游 consumer 硬编码 `"file_count"`，rename 后静默丢失数据。
- **建议改法和验证点**: plan 应明确：(a) 下游 consumer 列表；(b) 验证方式（grep `"file_count"` 确认无硬编码）。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: breaking change 但影响范围有限

### 4-未修复-低-`_PendingFileAsset.source` 收紧对 fingerprint 的隐式影响

- **位置**: §5.1 Publication result contract — "使用私有 closed provenance"
- **问题类型**: 最佳实践偏离
- **当前写法**: plan 要求把 `_PendingFileAsset.source` 从 loose `str` 收紧为 `Literal["original", "docling"]` 或私有 enum。
- **反例/失败场景**: `_build_upload_source_fingerprint`（`docling_upload_service.py:1018`）把 `asset.source` 纳入 fingerprint hash。当前 `"original"` 和 `"docling"` 是唯一的两个值，收紧类型不影响行为。但如果未来新增 provenance 类型，fingerprint 计算会变，导致同一文件的 fingerprint 不一致。
- **为什么有问题**: 这不是当前 blocker，但 plan 没有提及 fingerprint 与 provenance 的耦合关系。
- **直接证据**: `docling_upload_service.py:1018` — `"source": asset.source` 纳入 fingerprint payload。
- **影响**: 低。当前只有两个值，收紧类型不影响。
- **建议改法和验证点**: 在 plan 中注明 fingerprint 与 provenance 的耦合关系，作为 future maintenance note。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 当前不影响行为

### 5-未修复-中-`__post_init__` count 不变量校验的具体实现未明确

- **位置**: §5.3 Runtime terminal/durable contract — count 不变量表
- **问题类型**: 不可直接实施
- **当前写法**: plan 给出了 status/requested/stored 的不变量表，但没有说明在哪实现这些校验。当前 `FinsUploadResultSummary.__post_init__`（`ingestion_runtime.py:1233`）只校验 `failure_reason` 与 status 的对应关系，不校验 counts。
- **反例/失败场景**: 若实施 agent 把 count 校验放在 `__post_init__`，需要先确认所有 4 个构造点都传入了正确的 counts（参见 Finding 2）。若某个构造点遗漏了 counts，`__post_init__` 会 crash。
- **为什么有问题**: plan 的不变量表是 contract 级别的，但没有指定实现位置。实施 agent 需要自行决定是在 `__post_init__` 还是其它位置实现。
- **直接证据**: 当前 `__post_init__` 只校验 failure_reason，不校验 counts。plan 的不变量表没有映射到具体代码位置。
- **影响**: 实施 agent 可能把校验放在不同位置，导致 contract 不一致。
- **建议改法和验证点**: plan 应明确 count 校验放在 `__post_init__`，并列出需要通过校验的 4 个构造点。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 影响实施一致性

### 6-未修复-低-S2 测试依赖真实 Docling 转换行为的稳定性

- **位置**: §7 S2 — Tests first / exact assertions 第 2 条
- **问题类型**: 测试缺口
- **当前写法**: plan 要求 "converter分别对 `.pdf`/`.docx` 抛每个代表性 closed Docling failure：public code映射稳定"。
- **反例/失败场景**: plan §9.2 承认"真实 Docling 对损坏样本的底层异常差异"是 residual risk。但 S2 的 assertion 2 要求 "public code映射稳定"。如果 Docling 底层异常类型在不同平台/版本变化，该 assertion 会 flaky。
- **为什么有问题**: plan 的 stop condition（S2）说"若converter错误无法在逐文件边界关联唯一basename，停止"，但没有说"若Docling底层异常类型不稳定，停止"。
- **直接证据**: plan §9.2 residual risk 已识别此风险。§7 S2 stop condition 只覆盖 basename 关联，不覆盖异常类型稳定性。
- **影响**: 测试可能在某些平台/版本上 flaky。
- **建议改法和验证点**: S2 assertion 2 应明确：deterministic owner tests 覆盖映射逻辑，真实 Docling samples 的 assertion 可以标记为 `xfail` 或 `skip` on platform variance。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: plan 已识别为 residual risk

### 7-未修复-中-`_build_pending_assets` 逐文件 catch 的控制流未明确

- **位置**: §5.4 Closed failure contract — "`_build_pending_assets(...)` 在逐文件 `DoclingConversionError` catch 中"
- **问题类型**: 不可直接实施
- **当前写法**: plan 说在 `_build_pending_assets` 中逐文件 catch `DoclingConversionError`，包装 typed upload failure。
- **反例/失败场景**: 当前 `_build_pending_assets`（`docling_upload_service.py:715-746`）是顺序循环，没有 try/catch。如果一个文件转换失败，当前代码会直接抛异常。plan 要求逐文件 catch 后抛 `FinsUploadFailureError`，但没有说明：(a) 是否只 catch 第一个失败然后立即抛出；(b) 是否继续转换后续文件然后汇总失败。
- **为什么有问题**: 混合 valid+bad 场景（S2 assertion 3）要求"converter可先处理valid但坏文件使whole request failed"。这暗示 bad 文件不阻止 valid 文件的转换，但最终整批失败。plan 没有明确这个控制流。
- **直接证据**: `_build_pending_assets` 当前没有 try/catch。plan §5.4 和 §7 S2 assertion 3 的描述不完全一致。
- **影响**: 实施 agent 可能实现不同的控制流（fail-fast vs. try-all-then-fail）。
- **建议改法和验证点**: plan 应明确：第一个 conversion failure 立即 raise `FinsUploadFailureError`（fail-fast），不继续后续文件。或者明确 try-all-then-fail 策略。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 影响实施一致性
