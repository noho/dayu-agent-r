## DS Finding 01 Analysis

### Original Finding

From `pr-165-review-20260701-164627.md` Finding 01:

> `_abandon_cancelled_wait` 中 `adapter.abandon_wait(record)` 成功后 lifecycle gate 关闭导致 durable `poll_abandoned_at` mark 被跳过。外部 abandon 已成功，但 durable 状态未写入。下一轮 poller 实例会重新 claim 此 cancelled wait 并再次调用 `adapter.abandon_wait()`，造成 double-abandon。

Root cause: lines 921-922 (now removed) checked `self._lifecycle_gate.is_closed()` AFTER `adapter.abandon_wait(record)` returned successfully. If the gate closed between the adapter call and that check, the durable mark was skipped with a `SHUTDOWN_SKIPPED` release, leaving `poll_abandoned_at IS NULL` and making the wait re-claimable.

### Fix Applied

**`dayu/host/wait_adapter.py`** — Removed 2 lines (post-abandon lifecycle gate check):

```diff
-        if self._lifecycle_gate.is_closed():
-            return 0, 0, self._release_shutdown_skipped(record, claim_id), 1
```

The two lines were between `adapter.abandon_wait(record)` success (line 900) and the `_MarkWaitRecordAbandonedOperation` write transaction (lines 921-932). After removal, successful external abandon always proceeds directly to the durable mark — no gate check intervenes.

**Preserved invariants**:
- Pre-adapter gate check (line 877) retained — shutdown before any external side effect still releases as `SHUTDOWN_SKIPPED`
- `poll_once` loop-level gate check (line 747) retained — gate closed before per-record processing skips the record entirely
- Adapter calls remain outside Host transactions
- CAS-based claim verification in `_MarkWaitRecordAbandonedOperation` unchanged

### Test Analysis

`test_cancelled_abandon_success_marks_abandoned_when_close_gate_closes` (lines 454-493):

- **Setup**: Creates a cancelled wait record, then constructs a `_CloseGateDuringAbandonAdapter` that sets `lifecycle_gate.closed = True` inside `abandon_wait()` before returning successfully
- **Race simulation**: The adapter closes the gate during the external abandon call, mimicking the exact race window (gate closes between pre-adapter check and durable mark)
- **Assertions**:
  - `result.abandoned == 1` — abandoned count reflects the successful external abandon
  - `result.shutdown_skipped == 0` — not erroneously counted as shutdown-skipped
  - `result.claim_conflicts == 0` — CAS succeeded (claim was still valid)
  - `second.observed == 0` — second poller instance cannot re-claim the wait (because `poll_abandoned_at IS NOT NULL` now excludes it from eligibility)
  - `adapter.abandoned == [seeded.wait_id]` — adapter's `abandon_wait` called exactly once
  - `wait_record.poll_abandoned_at is not None` — durable mark was written
  - `wait_record.poll_claim_id is None` — claim was cleared by the terminal abandon mutation

The test fixtures (`_MutableLifecycleGate`, `_CloseGateDuringAbandonAdapter`) are self-contained, properly documented, and follow existing test patterns. The `_poller()` helper's new `lifecycle_gate` parameter is optional and backward-compatible with all existing callers.

## Shutdown Semantics Assessment

**Question**: Does removing the post-abandon gate check violate the supervisor's close drain semantics?

**Answer**: No.

Rationale:
1. The fix adds at most one write transaction (`_MarkWaitRecordAbandonedOperation`) per cancelled wait that was in-flight during shutdown. This is a fast CAS UPDATE on a single row.
2. The supervisor's `close()` method calls `thread.join()` (potentially with a diagnostic timeout), which waits for the poller thread to complete its current `poll_once()` iteration. The durable mark runs inside that same iteration.
3. The `open_host` close order (poller → scheduler → projection → durable) ensures the durable store is still open when the poller thread runs its final write.
4. The number of cancelled waits being abandoned during any single shutdown is bounded by `claim_batch_size` (default 100), and in practice much smaller.
5. The close drain timeout is diagnostic-only (per plan: "close doesn't return early"), so the extra write doesn't cause premature close return.

## Stale-Claim CAS Behavior

**Question**: What happens if the claim is stolen between successful `adapter.abandon_wait()` and the durable mark?

**Answer**: The CAS in `_MarkWaitRecordAbandonedOperation` checks `claim_id` match. If stolen, returns `CAS_LOST` → method returns `(0, 0, 1, 0)` (abandoned=0, claim_conflicts=1). The external abandon has already happened, but `poll_abandoned_at` is not written. A future poller with the stolen claim will re-attempt abandon.

This is a **pre-existing design trade-off**, not introduced by the fix. The Codex fix report explicitly acknowledges this: "CAS conflict after external abandon success still preserves existing stale-claim behavior: if the claim is no longer current, durable mark is not forced." The CAS invariant (never write under a stale claim) takes priority over the idempotency concern. The fix only removes the guaranteed double-abandon from the gate-skip path; the CAS-conflict double-abandon is a much rarer window.
