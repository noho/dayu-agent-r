## Reviewed Scope

- Review target：`docs/plans/sec-html-image-assets-plan.md`
- Binding artifacts：`docs/plans/sec-html-image-assets-goal.md`、`docs/plans/sec-html-image-assets-control.md`

- 本次仅审核，不修复 plan/代码，不运行真实网络，不修改 control、业务文件或其它 reviewer 文件。

## Assumptions Tested

1. Goal Confirmation 是 binding scope；“实际引用且属于同申报的图片”必须覆盖正式下载 HTML 的真实图片依赖，而不是只覆盖某一种属性写法。
2. 图片发现必须以同一次正式预取的 HTML bytes 为真源，且同申报 URL 边界、仓储资产名和去重规则有唯一 owner。
3. 旧来源普通增量补齐必须同时通过 Phase A 与 Phase B 的当前下载版本资格；本地 rebuild 不得授予正式下载认证版本。
4. 发现/下载失败不得发布新的 complete publication；并发、取消、blob/upsert/commit 失败必须保留旧 publication。
5. S1 的 owner 测试、真实独立临时 base、失败诊断、版本/指纹/重复行为和 README 更新必须能够直接验证成功信号 1 至 5。

## Findings

### SECIMG-001-未修复-[高]-实际图片引用范围被收窄为 `<img src>`

- **位置**: plan“图片发现、URL 与名称契约”第 93-102 行；goal 成功信号 1/3；residual risk R4。
- **问题类型**: 范围漂移 / 契约缺失 / goal-bound minimal design。
- **当前写法**: plan 只遍历 `<img>` 的 `src`，明确排除 `img/srcset`、`picture/source`、CSS、脚本和浏览器布局求值，并把更宽的图片引用能力放入后续需求。
- **反例/失败场景**: 一个正式下载 HTML 使用 `<img srcset="small.jpg 1x, large.jpg 2x">`、`<picture><source srcset="...">` 或其它浏览器实际会选择的直接图片属性；生产 extractor 只看到 `src`，把这些同申报图片当成不存在，随后发布缺少必要图片的 complete 来源。
- **为什么有问题**: goal 第 24 行要求发现“实际引用且属于同申报的图片”，并未把范围限定为 `img[src]`；“不做通用爬虫”不能推出可以忽略 HTML 自身的直接图片候选。当前 plan 因而可能满足自身窄口径测试，却不满足已确认的成功信号 1/3。
- **直接证据**: goal 第 24、26 行；plan 第 93-95 行明确排除 `srcset`/`picture/source`；preflight JSON 只证明两个样例含 `<img src>`，不能证明其它正式 HTML 没有其它直接图片引用。
- **影响**: 旧来源和新来源都可能被错误标记完整；财务表/演示图片缺失但结果显示成功，后续读取、processed 或人工排障无法从下载集合恢复；实现测试会固化窄口径并掩盖回归。
- **建议改法和验证点**:
 1. 由总控重新确认 binding scope：要么在 goal 中明确本 work unit 只负责 `img[src]`，要么把有限的直接图片属性集合（至少 `img[srcset]`、`picture/source` 的候选 URL）纳入 downloader owner。
 2. 不引入通用爬虫；只为已接受 HTML 的有限直接图片属性建立可测试的 URL 解析契约。
 3. 增加一个不含 `src`、但含 `srcset`/`picture` 的同申报样例测试，断言图片进入 `files[]`、可由 `get_source` 读取且完整集合指纹包含它们；另加旧来源普通补齐和失败回滚断言。
- **修复风险（低/中/高）**: 中。
- **严重程度（高）**。
- **裁决候选**: `accepted-candidate`。
- **初始状态**: 未修复。

### SECIMG-002-未修复-[高]-相对图片 URL 未处理 HTML `<base href>` 语义

- **位置**: plan“图片发现、URL 与名称契约”第 95-98 行；`SecDownloader.list_filing_image_files` 新接口说明第 84-89 行。
- **问题类型**: 架构边界 / 契约缺失 / 状态与数据一致性。
- **当前写法**: plan 规定所有地址都以 HTML 的 archive URL 为基准，并对同目录、同申报根路径和绝对地址做同申报检查；没有定义或拒绝 `<base href>`。
- **反例/失败场景**: HTML 含 `<base href="/Archives/edgar/data/1046179/000119312519110066/">` 或同申报内的另一个 base 目录，同时 `<img src="g733154txs8g1.jpg">`；浏览器实际解析到 base 指定的文件，而计划按 HTML archive URL 解析到错误文件名，可能下载错误资产、误判同申报边界，或把真实必要依赖报为失败。
- **为什么有问题**: HTML 文档的相对 URL 解析依赖文档 base URL；只按 HTML 自身 archive URL 解析不是“实际引用”的可靠语义。该问题发生在 downloader 依赖发现 owner 内，不能由存储、读图工具或测试夹具补偿。
- **直接证据**: plan 第 95 行直接规定“以该 HTML 的 archive URL 为基准”；goal 第 24 行要求实际引用；现有 `extract_same_filing_linked_html_files` 只覆盖 `a[href]`，不能作为图片 base 解析契约的证据。
- **影响**: 发现结果、source URL、文件名、去重键、source fingerprint 和 hash 可能对应错误资源；即使 HTTP 200 且非空，也可能发布错误图片集合，且失败或重复执行难以诊断。
- **建议改法和验证点**:
 1. 在 downloader owner 中明确 HTML base URL 规则：支持同申报 base、拒绝外部/跨申报 base，或在无法安全判定时产生 `html_image_reference_invalid`；禁止隐式按 archive URL 修正。
 2. 增加带同申报 `<base href>`、带外部 `<base href>`、带 query/fragment base 的 parser 测试，断言最终 canonical URL、同申报边界、去重和失败原因。
 3. 真实 CLI 验证矩阵至少包含一个 base 解析案例；没有实际样例时使用最小 HTML fixture 只验证 URL 解析 owner，不扩大为浏览器渲染。
- **修复风险（低/中/高）**: 中。
- **严重程度（高）**。
- **裁决候选**: `accepted-candidate`。
- **初始状态**: 未修复。

### SECIMG-003-未修复-[中]-同申报子目录图片被定义为发现失败，goal 的同申报资产承诺未闭合

- **位置**: plan“图片发现、URL 与名称契约”第 96-100 行；residual risk R4；`asset_filename_contract.py` 的单组件资产约束。
- **问题类型**: 范围漂移 / 最佳实践偏离 / 可实施性。
- **当前写法**: plan 只允许 archive 直接子文件作为可登记图片；同申报子目录图片明确 `html_image_asset_collision`/发现失败，不 flatten、不改写 HTML。
- **反例/失败场景**: 已接受 HTML 引用同申报 `images/chart.jpg`。该资源属于同申报且是必要图片，但仓储只接受单组件文件名，plan 将整个 filing 失败而不提供可执行的合法地址映射；目标成功信号 1 的“下载并登记为可通过来源仓储寻址的资产”无法对该合法依赖成立。
- **为什么有问题**: 失败关闭比静默丢弃安全，但 goal 没有把“同申报子目录”列为非目标。若这是有意限制，必须由 goal/plan 的 binding contract 明确；否则 plan 将仓储实现限制误当成业务边界，导致正常同申报依赖无法完成。
- **直接证据**: goal 第 24、35 行把同申报图片发现/地址交 SEC downloader 与 storage owner；plan 第 98 行明确只接受直接子文件；`_fs_storage_utils.py:_normalize_filename` 及 `asset_filename_contract.py` 只允许单组件文件名。
- **影响**: 对存在目录化图片的 SEC HTML，普通增量会稳定失败；用户无法从 CLI 完成补齐，且 plan 的真实 TSM 两个样例不能代表该边界。
- **建议改法和验证点**:
 1. 由总控裁决：将同申报子目录明确列为本 work unit 的非目标并要求诊断可执行，或在 storage/source asset owner 设计可逆、可寻址的路径映射后再实施。
 2. 若保持失败关闭，补充明确 reason、用户可执行的处理方式和测试：子目录引用不得下载 basename、不得发布 complete、不得污染旧 publication。
 3. 增加一个同申报子目录 fixture，断言 URL 边界、错误分类、事务保留和诊断；不要用样例文件名或 ticker/accession 特判。
- **修复风险（低/中/高）**: 中。
- **严重程度（中）**。
- **裁决候选**: `needs-evidence`。
- **初始状态**: 未修复。

## Lens Results

- **Goal-bound minimal design review**: 发现 SECIMG-001、SECIMG-003；plan 的版本升级、rebuild 版本认证、事务保留和真实验证均可映射到成功信号，但引用范围/同申报路径仍有 binding contract 缺口。
- **Architecture boundary review**: downloader 发现、workflow 状态门、source upsert/storage 发布的 owner 划分总体正确；未发现跨层 fallback 或独立图片存储。SECIMG-002 暴露 downloader URL 解析契约不完整。
- **Best-practice review**: typed discovery error、真实 prefetch bytes、原子 batch、严格 UTF-8、owner 级测试和 opt-in 真实 CLI 方案合理；SECIMG-001/002/003 是具体 failure path，不是风格意见。
- **Optimal-solution review**: 复用现有 `build_source_fingerprint`、`prefetch_files_stream`、source upsert 和 Fs batch 是当前最小可行路径；没有证据支持额外图片 manifest/数据库或读取端补偿。
- **Overengineering review**: 未发现无需求支撑的抽象；真实验证的 transport hook 仅用于故障证据，不是生产 seam。
- **Overcoupling review**: 1 个 S1 将发现、版本资格和原子发布绑定是有理由的 correctness 原子性；但 SECIMG-001/003 表明引用契约在实施前仍需收敛，否则单 slice 会把范围缺口固化。
- **State/concurrency/cancellation review**: Phase A/B 身份重试、batch rollback、旧 publication 保留、begin 前取消和 Event/barrier 并发矩阵均有明确 owner 断言，未发现额外 blocking finding。
- **Version/fingerprint/reprocessing review**: 当前版本严格相等、完整 descriptor fingerprint、rebuild 不授予下载版本、processed marker 由 source upsert owner 处理；远端内容在缺少 validators 时的身份风险已由 R3 诚实分类，不作为本次无证据架构强化。
- **Validation/code-generation-ready review**: 单元/真实 CLI/故障/重复/6-K/SC13/诊断矩阵具体；但 SECIMG-001/002/003 未被现有计划测试闭合，当前 plan 不能无条件交给 implementation agent。

## Open Questions

1. binding goal 的“实际引用”是否明确等价于 `<img src>`，还是包括 HTML 标准的其它有限直接图片候选属性？需由总控/goal owner 明确，不应由 implementation worker 自行缩小。
2. 同申报子目录图片是否属于本 work unit 必须支持的资产？若属于，storage asset 地址契约的 owner 方案是什么；若不属于，goal/非目标是否明确允许失败关闭。
3. `<base href>` 的同申报 base 是否必须支持，还是发现到 base 时应 typed failure？这是 SECIMG-002 的具体验收分支。

## Conclusion

**fail**

计划的下载 owner 链、版本升级、rebuild 版本认证、事务/取消/并发、真实临时 base 和失败不发布的主方案是可验证且基本正确的；但 SECIMG-001 与 SECIMG-002 使“实际引用图片”契约仍不闭合，SECIMG-003 需要明确同申报子目录边界。应先由总控裁决上述 binding scope/地址契约并补足对应最小验证，再进入 implementation。
