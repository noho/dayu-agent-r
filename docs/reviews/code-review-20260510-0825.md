## Findings

### 01-未修复-高-owner-lost 路径 terminal append 与 attempt close 非原子

- **入口/函数**: `LocalRunHarness._handle_owner_lost` -> `_finish_attempt_if_durable` + `event_store.append`
- **文件(行号)**: `_run_harness.py` (`_handle_owner_lost` 方法)
- **输入场景**: renew loop 检测到 owner 失活 (fenced 或 storage error)，harness 在 `_next_engine_event_or_lose_owner` 的 race 中收到 `_OwnerLostDuringEngineWait`
- **实际分支**: `_handle_owner_lost` 先调用 `_finish_attempt_if_durable(state=LOST)` 把 attempt 推到 LOST，再调用 `self.event_store.append(host_failure_draft(...))` 写 terminal RUN_FAILED
- **预期行为**: attempt LOST 状态与 terminal EventLog 事件应在同一事务内完成，或有等价 reconcile 机制保证一致性
- **实际行为**: attempt close (CAS update `host_attempts`) 与 terminal event append (`event_store.append`) 是两步独立操作，中间存在 crash 窗口：进程在 attempt 已标 LOST 但 terminal RUN_FAILED 未写入时崩溃，导致 run 无 terminal 事件
- **直接证据**: `_handle_owner_lost` 先 `await self._finish_attempt_if_durable(active_attempt=active_attempt, state=AttemptState.LOST, ...)` 再 `await self.event_store.append(host_failure_draft(...))`，两步之间无事务绑定
- **影响**: crash 场景下 run 有 LOST attempt 但无 terminal EventLog 事件，startup_reconcile 无法确定 run 终态；run 可能永久停留在非终态
- **建议改法和验证点**: 将 `_handle_owner_lost` 的 terminal append 改为通过 `self.event_store.append` 写入后，在同一事务中 update attempt 状态；或者在 `startup_reconcile` 中增加 "attempt 已 LOST 但无 terminal event" 的 reconcile 路径，由 reconciler 补写 Host-owned failure terminal
- **修复风险（低/中/高）**: 中 — 需要在 startup_reconcile 增加新的 reconcile 分支，或重构 owner-lost 路径的事务边界
- **严重程度（高）**: crash 窗口虽窄但影响不可恢复，run 会永久丢失终态

### 02-未修复-中-P8 新增 schema 列在已有 P6 库上不会自动生效

- **入口/函数**: `open_durable_event_store` -> `ensure_durable_event_store_schema`
- **文件(行号)**: `_durable_event_store.py` (schema 定义)
- **输入场景**: 用户从 P6 升级到 P8，使用已有的 SQLite 数据库文件
- **实际分支**: `CREATE TABLE IF NOT EXISTS host_attempts` — 表已存在时跳过，新列 (`owner_id`, `owner_token_hash`, `fencing_token`, `lease_expires_at`, `lease_renewed_at`, `recovered_from_attempt_id`, `stale_marked_at`) 不会被添加
- **预期行为**: 升级用户应能平滑使用 P8 能力，或至少得到明确错误提示
- **实际行为**: `AttemptLeaseStore.acquire_new_attempt` 的 INSERT 包含新列，SQLite 对缺少的列会报错（`table host_attempts has no column named owner_token_hash`），但错误信息不够明确，用户可能误以为是 bug 而非 schema 迁移问题
- **直接证据**: P6 schema `CREATE TABLE IF NOT EXISTS host_attempts` 仅包含 8 列；P8 扩展到 15 列，但 `CREATE TABLE IF NOT EXISTS` 不会 ALTER 已有表
- **影响**: 升级用户在不删库重建的情况下无法使用 P8 功能，错误提示不友好
- **建议改法和验证点**: 在 `ensure_durable_event_store_schema` 中增加 `ALTER TABLE ... ADD COLUMN` 迁移逻辑，或在 `build_durable_harness` 入口检测 schema 版本并给出明确提示 "需要删库重建"。根据 CLAUDE.md "按全新 schema 起库处理" 的约束，至少应在文档 / 启动路径中给出明确指引
- **修复风险（低/中/高）**: 低 — 增加 ALTER TABLE 或版本检测即可
- **严重程度（中）**: 影响升级用户体验，不影响新库正确性

### 03-未修复-中-scoped appender 的 owner_context 在 renew 后变成 stale snapshot

- **入口/函数**: `AttemptSupervisor.lease_context` -> yield `owner_context` -> `scoped_appender(owner_context)` -> `AttemptScopedRunEventAppender`
- **文件(行号)**: `_attempt_supervisor.py` (`lease_context` 方法, line ~538-580), `_attempt_lease.py` (`AttemptOwnerContext` frozen dataclass)
- **输入场景**: attempt 持续时间超过一个 renew 周期 (默认 10s)，renew 成功后 `lease_expires_at` 已更新，但 appender 持有的 `owner_context` 仍引用 acquire 时的旧 snapshot
- **实际分支**: `AttemptOwnerContext` 是 `frozen=True` dataclass，`lease_context` yield 的是 acquire 时构造的实例；renew 成功后 `_LeaseSession.owner_context` 被替换为新实例，但已 yield 出去的旧实例不会被更新
- **预期行为**: appender 持有的 `lease_expires_at` 应始终反映当前有效 lease
- **实际行为**: appender 的 `owner_context.lease_expires_at` 是 acquire 时的值 (now + 30s)，不是 renew 后的最新值；但 `verify_owner` 的 CAS WHERE 条件用的是 `lease_expires_at > now`（从 DB 读取当前值），不依赖 `owner_context.lease_expires_at`，所以 CAS 校验仍然正确
- **直接证据**: `verify_owner` SQL `WHERE ... AND lease_expires_at > ?` 中的 `?` 是 `self.clock.now()`（当前时间），不是 `owner_context.lease_expires_at`
- **影响**: 无实际正确性影响 — CAS 真源是 DB 当前值，不依赖 snapshot；但 `owner_context.lease_expires_at` 的语义已不准确，可能导致依赖该字段的诊断日志输出过期时间
- **建议改法和验证点**: 可在 renew 成功后通过某种机制（如 ContextVar 或 yield 新 context）更新 appender 持有的 context；但鉴于 CAS 真源在 DB 层，当前实现可接受，建议在 `AttemptOwnerContext` docstring 中标注 "lease_expires_at 为 acquire 时快照，实际 CAS 以 DB 当前值为准"
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 无正确性影响，仅诊断字段语义不精确

## Open Questions

- `startup_reconcile` 当前未覆盖 "attempt 已 LOST 但无 terminal event" 的 reconcile 路径。设计文档 §8.3 提到 "旧 attempt 没有 terminal RunEvent 时，`terminal_event_position` 可以为空"，但未明确说明 run 级终态如何恢复。P9 或后续阶段是否需要补充此 reconcile 能力？
- recovery scan (`recover_stale_attempts`) 当前未自动接入 `build_durable_harness` 或 Session 生产启动链路。这是 P8 已知的 scope 限制，但用户可能误以为 "P8 支持 recovery" 意味着自动恢复已生效。

## Residual Risk

- 多进程 stress 测试 (`test_phase8_multiprocess_stress.py`) 使用 spawn-only 平台 helper，不覆盖 fork 场景或真实分布式环境。
- `DurableConversationMemoryStore.repair_missing_session_snapshots` 的 repair 路径仅在 `startup_reconcile` 后触发，不覆盖运行中 snapshot 被运维误删的场景。
- P8 不实现 observer claim / lease，多进程下多个 observer 可能同时写同一 sink（由 ProjectionCoordinator 进程内锁保护单进程场景）。
- `_handle_owner_lost` 的 `RUN_FAILED` append 使用 `self.event_store.append`（非 scoped appender），因为此时 owner lease 已关闭；但如果 `event_store` 本身有 durability 问题，terminal event 写入可能失败且无重试。
- 未覆盖 pyright 全量检查，仅检查了变更文件；已有文件中若因 P8 引入新的类型依赖产生间接错误，本次 review 未捕获。
