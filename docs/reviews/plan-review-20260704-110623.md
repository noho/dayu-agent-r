### F03: Watchdog scheduling model — 已修复

**Controller requirement**: Choose a scheduling model (preferred: deterministic tick + hybrid runtime); define interval ownership; state interval affects detection latency, not timeout threshold.

**Plan fix evidence** (Implementation Decisions lines 159-165):

1. **Scheduling model**: "Use a deterministic `tick(now)` method plus hybrid runtime loop." (line 160)
2. **Cancel-commit wakeup**: "Runtime loop wakes immediately after `cancel_run` / `cancel_session_runs` commits or replays an active cancel target" (line 163)
3. **Periodic fallback**: "also runs a periodic fallback scan using the configured interval." (line 163) — "The periodic fallback is required so a lost wakeup or crash between commit and wakeup cannot leave `CANCELLING` suspended until another cancel command." (line 164)
4. **Interval owner**: "Default interval owner is existing Host local execution `dispatch_poll_interval_seconds` unless implementation introduces a narrower construction-time watchdog interval for a concrete reason." (line 164)
5. **Latency vs threshold**: "Interval controls detection latency only. Timeout eligibility is computed from durable `RUN_CANCELLING` / linked `CANCEL_REQUESTED` UTC timestamp plus the injected/current Host UTC clock." (line 165)

**Verdict**: The scheduling model is fully specified as deterministic tick + hybrid (event wakeup + periodic fallback), with clear interval ownership and latency/threshold distinction.

### F04: Injectable UTC clock and clock skew residual risk — 已修复

**Controller requirement**: Add injectable clock as implementation requirement; state production comparison uses durable UTC timestamps + Host UTC clock; add cross-instance clock skew as residual risk.

**Plan fix evidence** (Implementation Decisions lines 169-171):

1. **Injectable clock**: "Watchdog and timeout helper tests must use an injectable UTC now provider; do not depend on real sleeps or wall-clock races." (line 169)
2. **Production comparison**: "Production comparison uses durable UTC event timestamps written in EventLog and current Host UTC time from the now provider." (line 170)
3. **Clock skew residual risk**: "Cross-instance UTC clock skew can make reopen timeout detection slightly early or late; this is a bounded residual risk owned by Host lifecycle watchdog runtime tuning under #87, not a reason to change the terminal policy." (line 171)
4. **Also in Risks section** (line 400): "Risk: timeout detection compares durable UTC event timestamps from one Host instance with current UTC time from another instance after reopen; clock skew may make detection early or late by the skew amount."

**Verdict**: All three controller requirements are addressed. Clock injectability is a positive implementation requirement, production comparison is specified, and cross-instance skew is documented as residual risk.
