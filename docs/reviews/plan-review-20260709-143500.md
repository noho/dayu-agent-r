## Design Source Alignment

### Host design (`docs/host/design.md`)

- Host 是 Run / Attempt lifecycle、取消、EventLog、durable facts、memory / context governance 与 projection 的 owner。
- EngineEvent 进入 Host 前不是 durable truth，必须经 Host ingest 校验后才能影响 durable state。
- Tool Trace、Outbox、Read Model、Conversation Memory 是派生视图，不能反向驱动 Run / Attempt 状态。
- Cancellation linkage、terminal event type、terminal status 属于 Host durable contract 或 Host projection contract，不能由每个消费者各自定义或 back-query。
- RunInputBuilder / memory / compact material 必须把 Host 内部 id、payload ref、digest、cursor、policy、dispatch 状态改写为 LLM-facing 自解释输入。

### Engine design (`docs/engine/design.md`)

- Runner 只表达 provider 调用边界的 RunnerEvent；Agent 才提升为 EngineEvent。
- `RunnerDoneData.finish_reason` 应表达本次 Runner 调用完成原因的最终裁定；中间 content completion 不应成为 finish reason 权威。
- `usage_reported` 是 provider usage 事实，若 provider request id 存在，应从 Runner 边界一路透传到 EngineEvent。
- Engine 可以描述 awaiting tool result 行为，但进入模型上下文的 tool schema / prompt 不能要求模型理解 Host wait id、poll adapter、runtime 状态或其它等待治理标识。
- Runtime config / Service assembly 应向 Engine 提供已解析 policy；Engine `AgentPolicy` 不应持有独立 LLM-facing fallback prompt 默认文本真源。

## Findings

### 01-未修复-高-P0-A 推荐 contract 的两个选项迁移成本差异巨大，缺少决策标准

- **位置**: Section 6, P0-A, "预期 contract/schema/state/public-interface 变化"
- **问题类型**: 不可直接实施
- **当前写法**: plan 推荐 "从 `RunnerContentCompletedData` 和 `ContentCompleteData` 移除 `finish_reason`"，但同时给出最小替代方案 "Agent 在 `RunnerDoneData` 到达时无条件以 done finish reason 覆盖 state"。plan 说"若 plan review 认为迁移影响过大"则用替代方案，但没有给出判断标准。
- **反例/失败场景**: 方案 (a) 移除 `ContentCompleteData.finish_reason` 是 EngineEvent 公共契约变更，会影响 Host ingest (`engine_ingest.py:4346` 直接使用 `data.finish_reason.value`)、所有消费 `content_completed` EngineEvent 的测试、以及任何外部依赖该字段的代码。方案 (b) Agent 端覆盖是局部行为变更，不改变公共契约。两者迁移成本差异巨大，implementation agent 无法自行裁决。
- **为什么有问题**: plan 应在 plan review 阶段就确定选择哪个方案，或给出明确的决策标准和验证步骤，而不是把决策留给 implementation agent。当前写法可能导致 implementation agent 选择高成本方案后在 code review 阶段被否决，造成返工。
- **直接证据**:
  - `dayu/engine/contracts/runner_events.py:120-131` — `RunnerContentCompletedData.finish_reason` 字段存在。
  - `dayu/engine/contracts/engine_events.py` — `ContentCompleteData` 携带 `finish_reason`。
  - `dayu/host/engine_ingest.py:4346` — `_final_answer_plan` 使用 `data.finish_reason.value`。
  - `dayu/engine/agent.py:1449-1469` — Agent 在 RunnerDoneData mismatch 时静默选择 `state.finish_reason`。
- **影响**: 实施 Agent 跑偏 / 生成错误代码 / 后续返工。
- **建议改法和验证点**: plan review 阶段裁决使用方案 (b)（Agent 端覆盖）作为默认路径，理由是：(1) 不改变 EngineEvent 公共契约；(2) 代码证据显示 Agent 已经在 `_consume_runner_event` 中处理 RunnerDoneData，只需改为无条件覆盖而非静默选择；(3) Host ingest 不需要修改。若 controller 认为方案 (a) 更优，必须在 plan 中明确列出所有受影响的 EngineEvent 消费者和迁移步骤。
- **修复风险（低/中/高）**: 中
- **严重程度（高）**: 高 — 阻塞 P0-A implementation，因为方案选择直接影响 allowed files、slice 切分和验证矩阵。

### 02-未修复-中-P1-B RUN_LOST public outbox 行为的 design confirmation 缺乏可执行标准

- **位置**: Section 6, P1-B, "Residual risk" 和 "Stop condition"
- **问题类型**: open question 未收敛
- **当前写法**: plan 说 "`RUN_LOST` public outbox behavior 可能是设计意图，不应机械加入 status map。S1 必须先确认 design。" 但没有说明如何确认、在哪里确认、谁裁决。
- **反例/失败场景**: implementation agent 进入 S1 后发现需要 design decision，但 plan 没有给出确认路径，导致 S1 阻塞或 implementation agent 自行裁决。
- **为什么有问题**: 代码直接证据显示 `_TERMINAL_STATUSES` 不含 `lost`，而 `_TERMINAL_EVENT_TYPES` 包含 `RUN_LOST`，watermark 计算使用 event types 但 item 写入使用 statuses，导致 `RUN_LOST` 触发无意义 catch-up。这是一个真实的行为问题，需要在 plan 阶段就给出 design decision，而不是推迟到 implementation 阶段。
- **直接证据**:
  - `dayu/host/durable/outbox.py:63-67` — `_TERMINAL_STATUSES` 不含 `lost`。
  - `dayu/host/durable/outbox.py:71-76` — `_TERMINAL_EVENT_TYPES` 包含 `RUN_LOST`。
  - `dayu/host/durable/outbox.py:752` — watermark 计算使用 `*_TERMINAL_EVENT_TYPES`。
  - `dayu/host/durable/outbox.py:839` — item 写入检查 `_TERMINAL_STATUSES`。
- **影响**: 实施 Agent 跑偏 / 状态不一致 / 后续返工。
- **建议改法和验证点**: plan 应在 plan review 阶段明确 design decision：`RUN_LOST` 是否应产生 public outbox item。如果否，watermark 计算应排除 `RUN_LOST`；如果是，`_TERMINAL_STATUSES` 应包含 `lost`。建议基于 Host design 真源中 "Outbox 是派生视图" 的定位，裁决 `RUN_LOST` 不产生 public outbox item，但 watermark 应排除 `RUN_LOST` 以避免无意义 catch-up。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中 — 不阻塞整个 P1-B，但阻塞 S1 的具体实现方向。

### 03-未修复-中-P1-A allowed files 范围较广，implementation agent 上下文压力大

- **位置**: Section 6, P1-A, "Allowed files/modules"
- **问题类型**: 切片过粗
- **当前写法**: P1-A 列出 13 个 allowed files/modules，加上受影响测试。S1 确认 contract choice，S2 生产端 typed projection，S3 消费端迁移。S3 需要同时修改 Tool Trace、Memory、RunInput、CompactMaterial、Read API 五个消费者。
- **反例/失败场景**: S3 的 implementation agent 需要同时理解五个消费者的当前 back-query / blacklist / heuristic fallback 模式，并全部替换为同一 helper。上下文压力可能导致遗漏某个消费者的某个 fallback 路径，或在替换时引入不一致。
- **为什么有问题**: 控制文档 Slice 切分原则要求 "slice 必须控制模型一次实施和 reviewer 一次审查能够稳定承载的上下文规模"。S3 同时修改五个消费者，每个消费者的 back-query 模式不同，implementation agent 需要理解每个消费者的当前实现才能正确替换。
- **直接证据**:
  - `dayu/host/tool_trace.py:1283-1334` — `_tool_request_summary_from_tool_result` 回读 request EventLog。
  - `dayu/host/durable/memory.py:464-503` — `_tool_result_query_text` 回读 request EventLog。
  - `dayu/host/memory.py:1690-1706` — `_selected_evidence_text` 使用预解析字段。
  - `dayu/host/run_input.py` — `_llm_facing_evidence_source_text` 使用 blacklist。
  - `dayu/host/compact_material.py` — `_readable_query_text_from_envelope` back-query。
- **影响**: 生成错误代码 / review 不可验收 / 后续返工。
- **建议改法和验证点**: 可接受当前切分，但 plan 应在 S3 的 implementation artifact 中要求 implementation agent 列出每个消费者的当前 fallback 路径和替换方案，作为 implementation completeness checklist。review agent 应逐个消费者验证替换完整性。若 S3 实际上下文压力过大，可拆为 S3a (tool_trace + read_api) 和 S3b (memory + run_input + compact_material)。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中 — 不阻塞 plan，但增加 implementation 阶段返工风险。

### 04-未修复-中-P2-A session resume public boundary 缺少具体方案选择

- **位置**: Section 6, P2-A, "预期 contract/schema/state/public-interface 变化"
- **问题类型**: 不可直接实施
- **当前写法**: plan 说 "为 existing-session prompt/interactive 提供 public reusable CLI/Service boundary，或把 session resume 逻辑下沉到 Service entrypoint helper"，但没有裁决使用哪个方案。
- **反例/失败场景**: implementation agent 需要在两个方案之间自行裁决。方案 1（public CLI imports）保持 CLI 层内复用但暴露更多 CLI 内部函数；方案 2（Service entrypoint helper）下沉到 Service 层但需要改变 session resume 的调用路径。两者架构方向不同。
- **为什么有问题**: 代码直接证据显示 `session.py` 从 `prompt.py` 和 `interactive.py` 导入四个私有函数。这些函数的职责是准备和执行 existing session 上的 prompt/interactive 操作。方案选择影响 CLI/Service 边界。
- **直接证据**:
  - `dayu/cli/commands/session.py:36-44` — 从 `interactive` 和 `prompt` 导入四个私有函数。
  - `dayu/cli/commands/session.py:251-283` — 使用这些函数执行 session resume。
- **影响**: 实施 Agent 跑偏 / 架构边界不一致 / 后续返工。
- **建议改法和验证点**: plan 应裁决使用方案 2（Service entrypoint helper），理由是：(1) 控制文档 P2-A 目标明确说 "Service-owned 或 CLI public narrow entrypoint"；(2) session resume 的核心逻辑（准备输入、执行 turn、等待结果）属于 Service 职责，CLI 只负责参数解析和输出渲染；(3) 代码证据显示 `session.py` 的 resume 逻辑与 `prompt.py` / `interactive.py` 高度耦合，下沉到 Service 可以解耦。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中 — 阻塞 P2-A S1 implementation。

### 05-未修复-低-P2-B S2 memory/final-answer/test fixture audit 的 obsolete finding 判断标准不具体

- **建议改法和验证点**: plan 应在 S2 的 root-cause confirmation 阶段明确判断标准：(1) 检查 `_memory_projection_payload_view` 是否仍变异 payload；(2) 检查 `read_api.py` 是否仍独立实现 terminal artifact 读取；(3) 检查 `run_input.py` 是否仍只读 inline field。如果三个检查中有任何一个成立，finding 不是 obsolete。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — 不阻塞 plan，但增加 implementation 阶段的不确定性。

## Residual Risks

1. **P0-A 非 OpenAI Runner 覆盖**：plan 提到 "非 OpenAI Runner 如有同类 event construction，implementation 前必须扫描确认"。当前代码库只有 `AsyncOpenAIRunner`，风险低，但 implementation 前应确认。
2. **P1-A EventLog payload schema migration**：既有 EventLog payload 没有新 fields；按全新 schema 起库处理。这意味着旧 workspace 的 accepted evidence envelope 没有新字段，消费者需要处理缺失 typed projection 的 fail-closed diagnostic。
3. **P1-B Schema 变更**：`cancel_request_event_id` 从 payload JSON 移到 durable state 列需要全新 schema 起库。如果当前工作区已有 DB，需要 controller 裁决是否接受数据丢失。
4. **P2-C test migration breadth**：大量 tests 直接构造 `AgentPolicy`，迁移是机械但广泛的。plan 已识别此风险。
5. **Full-repository deepreview rounds**：plan 要求 "至少两个独立 full-repository semantic ownership deepreviews"，但没有明确是否由不同 agent 执行、review scope 是否需要变化、或是否需要覆盖之前未覆盖的模块（如 `dayu/fins/`、`dayu/cli/`、`dayu/service/`）。
