以下为 adversarial 检查项的逐一证据结论：

### 1. provider id / client id / per-event identity 严格分离

`_vendor_group_key` (tool_trace_analysis_rules.py:1250-1262) 仅按三层 key 分组：
1. `provider_request_id` → `("provider", id)`
2. `client_correlation_id` → `("client", id)`
3. 兜底 → `("event", source_path + event_id)`

**不使用** run_id、attempt_id、iteration_id、event_sequence、timestamp 或任何 time/order 隐式归组。每个 fallback record 获得唯一 key `{source_path}\0{event_id}`，不可能跨调用合并。

`_is_vendor_trigger` (tool_trace_analysis_rules.py:1218-1247) 对 `_VENDOR_TERMINAL_EVENT_TYPES` (RUN_SUCCEEDED/FAILED/CANCELLED/LOST) 仅在 record 自身携带 direct provider refs（provider_request_id、client_correlation_id、diagnostic_refs、provider_error_ref、engine_event_ref）时返回 True。不从 run/attempt/time 推断。

**结论：严格分离，无隐式跨调用归组。**

### 2. local refs 只源于可证明 typed/source facts

- `session_id`、`run_id`：来自 `_RuleRecord` 的 direct cold/hot 字段（S1 owner 已校验）。
- `attempt_id`、`execution_id`：来自 cold record `fields["attempt_id"]`/`fields["execution_id"]` 或 hot row direct 字段。
- `iteration_id`：`_direct_iteration_id` (tool_trace_analysis_rules.py:1627-1646) 优先取 resolver 证明的 `source_event_payload.iteration_id`，fallback 到 `trace_summary.iteration_id`（producer 已校验）。不从时间/顺序推断。
- `provider_request_id`、`client_correlation_id`：来自 cold/hot direct 字段。
- `diagnostic_refs`：来自 cold/hot `trace_summary.diagnostic_refs`，通过 `_text_tuple` 严格类型校验。

**结论：所有 local refs 均来自 typed/source facts，无推断/补偿逻辑。**

### 3. partial absent / explicit none / present 严格区分

`_vendor_partial_signal_status` (tool_trace_analysis_rules.py:1512-1546)：
- **absent**（protocol record 的 trace_summary 中无 partial_tool_call_signal 字段）→ `_mapping()` 返回 None → `LIMITED_SIGNAL`
- **explicit none**（summary_status="none"，partial_tool_call_count=0）→ signal object 存在 → `AVAILABLE`
- **present**（summary_status="present"，partial_tool_call_count≥1）→ signal object 存在 → `AVAILABLE`

`_engine_record_findings` (tool_trace_analysis_rules.py:1150-1190)：
- absent → 生成 `engine.partial_tool_call_signal_missing` finding，summary 明确"不能解释为明确无 partial"
- explicit none → 不生成 partial finding
- present → 生成 `engine.partial_tool_call_present` finding

测试 `test_partial_signal_absent_none_and_present_remain_distinct` 直接验证三种状态的 block-level signal 和 finding-level 区分。

**结论：三态严格区分，无合并/降级。**

### 4. 同 provider id 冲突 refs 报告 finding 而非静默合并

`_vendor_conflict_fields` (tool_trace_analysis_rules.py:1265-1299)：仅在 provider_id group 中检查，对 client_correlation_id、session_id、run_id、attempt_id、execution_id、iteration_id 六个 identity 字段做 `_sorted_values` 去重，len > 1 即为冲突。

冲突时：
- 生成 `engine.vendor_correlation_conflict` finding (ERROR severity)
- 生成 `vendor_correlation_conflict` limitation
- block status 设为 `LIMITED_SIGNAL`

测试 `test_same_provider_id_conflicting_client_and_local_refs_is_finding` 验证：同 provider_request_id、不同 attempt_id/execution_id/client_correlation_id/iteration_id → conflict finding + limited block。

**结论：冲突显式报告，不静默合并。**

### 5. usage 零参与 vendor trigger/grouping

`_is_vendor_trigger` 仅接受 `_EVENT_PROVIDER_DIAGNOSTIC`、`_EVENT_PROVIDER_PROTOCOL_ERROR` 和 `_VENDOR_TERMINAL_EVENT_TYPES`。`USAGE_REPORTED` 不在其中。

测试 `test_file_only_provider_signal_is_limited_and_usage_never_joins`：USAGE_REPORTED 事件与 PROVIDER_PROTOCOL_ERROR 共享同一 provider_request_id，但 USAGE_REPORTED 不出现在 vendor block 的 tool_trace_refs 中，block iteration_ids 为空（因为 usage 的 iteration_id 来自 trace_summary 但 usage 不是 vendor group member）。

**结论：usage 完全不参与 vendor trigger/grouping。**

**结论：无 semantic ownership drift。**
