### 1-未修复-[高]-Tool trace 文件路径直接拼接未校验的逻辑 id，允许写出 trace root

- **入口 / 函数**: `ToolTraceJsonlSink.append_record_line`, `ToolTraceJsonlSink.write_raw_payload_blob`, `_payload_ref`
- **文件行号**: `dayu/host/_tool_trace_jsonl_sink.py:141`, `dayu/host/_tool_trace_jsonl_sink.py:173`, `dayu/host/_tool_trace_jsonl_sink.py:175`, `dayu/host/_run_input_raw_payload_store.py:367`
- **输入场景**: 调用方通过 `StartRunRequest.session_id` / `run_id` 传入包含 `/`、`\` 或 `..` 的 id；`iteration_id` 由 `run_id` 派生为 `f"{run_id}-attempt-{attempt_index:02d}"`，`blob_id` 又拼入 `run_id` 与 `iteration_id`。
- **实际分支**: trace sink 直接执行 `root_path / "sessions" / session_id`；raw payload sink 直接执行 `root_path / "raw_payloads" / f"{run_id}_{iteration_id}"` 和 `target_dir / f"{blob_id}.json"`。
- **预期行为**: Host trace sink 应把 session/run/iteration/blob id 当作逻辑 id，统一校验或编码为安全 path segment，保证所有 JSONL 与 raw payload 文件落在 `root_path` 内。
- **实际行为**: 逻辑 id 未校验、未编码、未做 `resolve()` 后的 root containment 检查。`StartRunRequest` 只声明 `session_id: str` / `run_id: str`，未在 Host 入口建立可绕不过去的 id grammar。
- **直接证据**: `StartRunRequest` 对 `session_id` / `run_id` 只有裸 `str` 字段；`_tool_trace_jsonl_sink.py:141`、`:173-176` 直接拼路径；`_run_input_raw_payload_store.py:367-375` 直接用未清洗 id 生成 `blob_id`。
- **影响**: trace JSONL / raw payload 可写到 trace root 之外，破坏本地 trace 目录隔离；非事务 observer 写文件成功后 checkpoint 可能继续推进，后续 replay 不会自动修复已写错位置的文件。
- **建议改法和验证点**: 在 Host ingress 对 `session_id`、`run_id`、`iteration_id`、`blob_id` 建立稳定 grammar，或在 sink 层统一 percent/base64url 编码 path segment；写入前断言最终路径 `resolve()` 后仍在 `root_path.resolve()` 下。补测试覆盖 `/`、`\`、`..`、空字符串与长 id。
- **修复风险**: 中。会影响既有 trace 文件路径和 README 示例，需要同步 path 断言与文档。
- **严重程度**: 高。

### 2-未修复-[高]-fetch_more / 截断 cursor mutation 只在入口前 fencing，owner 丢失后仍可消费或签发 cursor

- **入口 / 函数**: `HostToolRuntime.execute_tool_call`, `RuntimeTruncateManager.apply_truncation`, `RuntimeTruncateManager.fetch_more`
- **文件行号**: `dayu/host/_tool_runtime.py:296`, `dayu/host/_tool_runtime.py:311`, `dayu/host/_tool_runtime.py:322`, `dayu/host/_runtime_truncate_manager.py:265`, `dayu/host/_runtime_truncate_manager.py:371`
- **输入场景**: durable attempt 入口 `verify_active_owner` 通过后，业务 executor 或 framework `fetch_more` await 期间 lease 被 recovery / supervisor 判定 owner-lost，或新 owner 替换旧 owner。
- **实际分支**: `execute_tool_call()` 只在执行前调用一次 `appender.verify_active_owner(run_id=...)`；随后 framework 分支直接进入 `manager.fetch_more()`，业务分支在 executor 返回后直接 `apply_truncation()`。两条路径在 cursor registry mutation 前没有再次 owner CAS。
- **预期行为**: 文档声明 ToolRuntime 在业务 executor、framework `fetch_more` 与截断 manager mutation 前验证 active owner；cursor 消费 / 签发应与仍可落库的 owner 绑定。
- **实际行为**: `fetch_more` 可在 owner-lost 后执行 `_commit_cursor(next_record)` 与 `_remove_cursor(record.cursor)`；业务成功结果可在 owner-lost 后 commit 新 cursor。后续 Engine / Host 写 `TOOL_RESULT_ACCEPTED` 时即使被 appender fencing 拦住，cursor registry 的内存副作用已经发生。
- **直接证据**: `_tool_runtime.py:296-297` 是唯一 owner verification；`:311-321` framework `fetch_more` 执行后直接返回；`:322-335` 业务 executor await 后直接截断；`_runtime_truncate_manager.py:265-271` 与 `:371-374` 在 state lock 内修改 cursor registry，但没有 owner verifier。
- **影响**: stale owner 可消费旧 cursor、签发 next cursor 或移除旧 cursor，却没有对应 durable accepted tool result。新 attempt 从 EventLog 只能看到旧 `fetch_more_args`，但旧 cursor 已被删，补读链路可能变成 `cursor_not_found`，造成可恢复续读被旧 attempt 静默破坏。
- **建议改法和验证点**: 给 `RuntimeTruncateManager` 注入最小 `OwnerVerifier` protocol，或在 ToolRuntime manager mutation 前再次 CAS；至少覆盖 `fetch_more` 消费旧 cursor / 签发 next cursor 前、`apply_truncation` commit cursor 前。新增测试：第一次 verify 通过、await 后 owner lost 时不消费旧 cursor、不签发 next cursor，业务 executor 返回后也不产生可用 cursor。
- **修复风险**: 中。需要调整 ToolRuntime 与 manager 边界，但不需要恢复专属 RunEvent。
- **严重程度**: 高。

### 3-未修复-[高]-RunInput raw payload 对 AssistantMessage.tool_calls 参数不做凭证清洗，trace 冷层可能落明文凭证

- **入口 / 函数**: `build_run_input_context_fact`, `_message_to_dict`, `ToolTraceObserver._emit_iteration_context_snapshot`
- **文件行号**: `dayu/host/_run_input_context_fact.py:311`, `dayu/host/_run_input_context_fact.py:323`, `dayu/host/_run_input_context_fact.py:330`, `dayu/host/_tool_trace_projection.py:518`
- **输入场景**: `RunInput.messages` 中存在 `AssistantMessage.tool_calls`，其 `arguments` 包含 `api_key`、`password`、`client_secret`、`Authorization` 等显式凭证字段。
- **实际分支**: `_message_to_dict()` 对 assistant tool call 执行 `"arguments": dict(call.arguments)`，未复用 `scrub_tool_arguments()` / `scrub_explicit_credentials()`；projection 读取 side-store 后把 `payload_json` 原样写入 trace raw payload 文件。
- **预期行为**: 项目当前策略是 EventLog / trace 只保留普通 payload，但必须 scrub `API_KEY`、`api_key`、`Authorization`、password、client secret 等明确凭证字段；RunInput raw payload 既然会落到 trace 冷层，也应同源清洗显式凭证。
- **实际行为**: EventLog serializer / tool trace tool result 路径已有 credential scrub，但 RunInput raw input messages side-store 旁路了该策略。
- **直接证据**: `dayu/host/README.md:52-55` 说明 EventLog / trace 必须 scrub 明确凭证；`_run_input_context_fact.py:323-338` 直接序列化 assistant tool call arguments；`_tool_trace_projection.py:518-529` 将 side-store raw payload 原样写入 trace 文件。
- **影响**: 明确凭证可能进入 `run_input_raw_payloads` 与 `<trace_root>/raw_payloads/...json`，并因为 trace 文件是诊断冷层长期材料而扩大泄漏面。
- **建议改法和验证点**: 在 raw input message encoder 中对 assistant tool call `arguments` 复用同源 credential scrub；若 raw payload 的契约是精确 replay，则需要定义“lossless + scrubbed”的 AgentMessage encoder，并显式说明哪些字段不进入 replay。补测试覆盖 assistant tool call 参数中的 `api_key` / `password` 被替换为 `"***"`。
- **修复风险**: 中。若依赖 raw payload 做精确 replay，需要同步契约与测试预期。
- **严重程度**: 高。

### 4-未修复-[中]-ToolTraceObserver 只在单个 checkpoint batch 内配对 tool request/result，跨 batch 会永久阻断 trace projection

- **入口 / 函数**: `ProjectionCoordinator._run_once_locked`, `ToolTraceObserver._process_sync`, `ToolTraceObserver._emit_tool_call`
- **文件行号**: `dayu/host/_event_observer.py:270`, `dayu/host/_tool_trace_projection.py:198`, `dayu/host/_tool_trace_projection.py:221`, `dayu/host/_tool_trace_projection.py:264`
- **输入场景**: `TOOL_CALL_REQUESTED` 与对应 `TOOL_RESULT_ACCEPTED` 在 EventLog 中被 `ProjectionCoordinator.batch_limit` 切到不同 batch，例如中间插入大量 preview/canonical events，或显式配置较小 batch limit。
- **实际分支**: coordinator 每次按 `batch_limit` 取一批事件；trace observer 在 `_process_sync()` 内创建本 batch 局部 `groups`，批处理结束立即对每个 group 调 `_emit_tool_call()`；缺少 requested 或 accepted 即抛 `ProjectionSchemaError`。
- **预期行为**: tool request/result 的配对不应依赖 checkpoint batch 边界；batch 只是投影吞吐控制，不应改变可投影事件语义。
- **实际行为**: pair 被拆到不同 batch 时，第一批只含 requested，`_emit_tool_call()` 抛错；非 required observer 被记录为 `BLOCKED_FAILED`，`last_success_position` 不前进，后续 drain 会重放同一 split batch 并再次失败。
- **直接证据**: `_event_observer.py:270` 按 `batch_limit` fetch；`_tool_trace_projection.py:198-222` 使用本地 `groups`；`:264-265` 对不完整 pair fail-fast。现有 replay 测试覆盖 checkpoint failure 后 analyzer 去重，但未覆盖 request/result split batch。
- **影响**: trace projection/read-side 可永久落后；required observer 不阻塞主线，但 trace 完整性与后续诊断能力受损。
- **建议改法和验证点**: 不要要求 request/result 同 batch。可将 pending requested 写入 durable projection state，或按单事件投影并由 analyzer/read-side 合并。新增回归测试：`batch_limit=1` 或 request/result 被其它事件隔开时 projection 能最终 caught up。
- **修复风险**: 中。需要改变 trace record 生成策略或新增 pending state。
- **严重程度**: 中。

### 5-未修复-[中]-业务结果已有 `truncation` 字段时会被 Host 截断 hint 覆盖
