## Assumptions tested

1. root cause 判定（`announcements: null` = 空结果编码）是否被直接证据支撑，替代假设是否排除。
2. 修复位置是否为语义 owner boundary；缺 key / null / list / 其它类型四分语义是否安全。
3. “downloaded=1”成功预期是否与选择层真实行为一致（FY 窗口 2 条公告的筛选结果）。
4. 新测试与既有测试是否冲突或留下回归缺口。
5. 验收“无未解释的失败、拒收或缺失项”在修复后的终态输出上是否可满足；`missing_periods` / `omitted` 投影行为是否被 plan 预判。
6. 元数据核验交付项（document_id / meta.json / revision / source_fingerprint / SHA / 财务报表正文路径）是否有明确的 owner 真源。
7. slices 是否过粗、是否有 goal drift、是否过度设计 / 过度耦合。

## Findings

### 1-未修复-中-修复后终态必现的 `Fins missing periods` 未纳入验收预期与交付解释，可能诱发越权“修缺失”或验收被拒
- **位置**: §1 success signal（“终态无未解释 failure / reject / 缺失”）、§9 CLI 复验预期（“无 failed / rejected / 未解释缺失”）、§12 completion report format
- **问题类型**: 测试缺口 / 过度验收标准风险 / 不可直接实施（交付解释缺位）
- **当前写法**: plan 只要求“无未解释的缺失项”，未预判修复后终态**必然**打印缺失财期行，也未给出解释口径与禁止事项。
- **反例/失败场景**: 修复后 bare 请求 discovery 为 `FY,H1,Q1,Q3`（`cn_form_utils.py:40`），FY 命中而 H1/Q1/Q3 在 filing 窗口
  `2025-01-01~2025-03-31` 内无任何报告（H1/Q1 报告 4 月后才披露）→ workflow 的
  `_resolve_missing_periods`（`cn_download_workflow.py:577-595`，missing_eligible 减去 found）产出 `(H1,Q1,Q3)` →
  终态**必然**出现 `Fins missing periods: H1,Q1,Q3`（`dayu/cli/output.py:443-445`）。实施 Agent 面对两条路都错：
  （a）把该行当“未解释缺失项”去改 missing 投影 / 期间策略（越权扩 scope，污染 `cn_form_utils` / workflow 语义）；
  （b）原样交付不解释 → 任务书验收“无未解释的……缺失项”被判定不通过。
- **为什么有问题**: plan 的 success signal 以任务书验收口径为唯一裁判，却没有把修复后真实终态形态映射到该口径；
  实施 Agent 缺少解释口径与禁止事项，存在高概率的 scope drift 或验收返工。
- **直接证据**:
  - `cn_form_utils.py:40` `CN_BARE_DEFAULT_PERIODS = ("FY", "H1", "Q1", "Q3")`；
  - `cn_download_workflow.py:577-595` `_resolve_missing_periods` 不做窗口感知，found=FY → missing=(H1,Q1,Q3)；
  - `dayu/cli/output.py:443-445` 非空即打印 `Fins missing periods: ...`；
  - 事件时间线：窗口内 FY 类公告仅 `2024年年度报告` 与 `2024年年度报告摘要`（2026-09-25 实测巨潮响应），H1/Q1/Q3 类为空。
- **影响**: 实施 Agent 跑偏（改 missing 语义）或交付因“缺失项未解释”被验收拒绝、二次返工。
- **建议改法和验证点**: 在 §9 预期断言中写明：终态预期出现 `Fins missing periods: H1,Q1,Q3`，其语义为
  「主源在该 filing 窗口没有这些财期的候选」（既有 designed semantics，非 document outcome，见 `_build_result` docstring），
  属可解释缺失，**不得**为消除该行修改期间策略 / missing 投影；§12 交付格式中加入该解释项。验证点：复验终态含该行且
  交付文本给出上述解释。
- **修复风险（低/中/高）**: 低（仅 plan 文案补充）。
- **严重程度（低/中/高/严重）**: 中。

### 2-未修复-低-元数据核验交付项未钉死字段真源，存在从非 owner 层反推事实的余地
- **位置**: §9 元数据核验段、§12 交付字段列表
- **问题类型**: 契约缺失 / 不可直接实施（交付步骤）
- **当前写法**: “通过 `dayu.fins.storage` 仓储语义读取受管 workspace 权威 meta（只读）”，列出 document_id、meta.json 路径、
  revision、`source_fingerprint`、财务报表正文路径、SHA，但未指明各字段取自 meta 的哪个真源字段、SHA 对象是哪个文件。
- **反例/失败场景**: 交付时实现 Agent 自行 glob workspace 找 PDF 计算 SHA 与 meta 无关字段比对（违反“该路径须取自元数据”），
  或把 `pdf_sha256` 与 docling JSON SHA 混淆、把 `document_version` 当 revision 报出 → 交付核验不成立。
- **为什么有问题**: 任务书明确要求这些值来自 Dayu 权威元数据；plan 未钉死取值口径时，验收核验可能来自非 owner 真源。
- **直接证据**: `dayu/fins/pipelines/cn_download_source_upsert.py:187-191` meta 真源字段为
  `download_version` / `remote_fingerprint` / `source_fingerprint` / `pdf_sha256` / `document_version` 等；
  plan §9 未建立任务书措辞与这些字段的映射。
- **影响**: 交付核验错误或被验收退回；轻微返工。
- **建议改法和验证点**: §9 写明核验口径：`source_fingerprint` 与 `pdf_sha256` 直接取 meta 字段；SHA 校验 = 对 meta 指名的
  PDF 文件重算 sha256 与 `pdf_sha256` 比对；财务报表正文路径取 meta `primary_document` 类字段（以 meta 实际字段名为准，
  若与任务书措辞不同按 meta 字段名上报）；revision 取 meta/仓储的 revision 真源。验证点：交付中每个值标注来源字段。
- **修复风险（低/中/高）**: 低（plan 文案补充）。
- **严重程度（低/中/高/严重）**: 低。

## Goal-bound minimal design / architecture / overengineering / overcoupling 结论

- **Goal-bound minimal design**: 通过。四分解析语义、测试、docstring 说明均可映射到已确认 goal / success signal /
  “不把失败改成空成功”正确性条件；诊断增强与 HK 扩展正确放置于 deferred，无 goal drift。
- **Architecture boundary**: 通过。修复在 `hisAnnouncement/query` wire → 领域语义的唯一 owner（`_query_announcements`），
  未在 workflow / selection / CLI 做补偿；缺 key fail-closed 与 AGENTS.md 语义所有权一致。
- **Best practice / optimal**: 通过。对比过的备选（按 `totalRecordNum` 判空、在 `_http_post_form` 层统一 null→[]）
  均劣于 owner 处最小三分支；`null`/`[]` 双编码归一与本模块 `_format_announcement_date` 双形态先例一致。
- **Overengineering / overcoupling**: 通过。单文件 + 其测试，无新抽象、无跨层联动。
- **Slices**: 通过。单 slice 边界为可验证行为增量（空财期不再中断 + fail-closed 保持），gate 成本合理。
