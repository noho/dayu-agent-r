# Plan Review: 修复 dayu-cli prompt 创建 workspace/workspace

**审查目标**: 修复 dayu-cli prompt 创建 workspace/workspace 的问题
**审查范围**: workspace_root 与 project_root 语义、public contract 位置、runtime location 默认 overlay、默认配置路径、nested workspace 风险
**审查时间**: 2026-07-08 13:45:25
**审查结论**: **fail** - 存在结构性语义混淆，需要重新设计路径解析架构

---

## Assumptions Tested

1. `workspace_root` 和 `project_root` 是同一概念的不同命名
2. 用户通过 `--base` 指定的路径应该直接作为配置查找的根目录
3. `location.py` 中的 `project_root` 参数应该与 CLI 层的 `workspace_root` 语义一致
4. 默认配置路径应该是 `workspace/config`，而不是 `workspace/workspace/config`

---

## Findings

### 1-未修复-严重-语义混淆：workspace_root 与 project_root 参数名不一致

- **位置**: `dayu/runtime/location.py:32-75`, `dayu/cli/agent_entrypoint.py:131-145`, `dayu/service/entrypoint_runtime.py:514`
- **问题类型**: 架构边界 / 契约缺失
- **当前写法**:
  - `location.py` 的 `resolve_runtime_locations()` 使用 `project_root` 参数名
  - CLI 层和 Service 层统一使用 `workspace_root`
  - `entrypoint_runtime.py` 第 514 行将 `workspace_root` 直接传给 `project_root` 参数
- **反例/失败场景**:
  - 用户执行 `dayu-cli prompt --base ./my-workspace "分析财报"`
  - CLI 解析 `workspace_root = ./my-workspace`
  - `location.py` 收到 `project_root = ./my-workspace`
  - 实际查找配置路径: `./my-workspace/workspace/config`（错误！）
  - 应该查找: `./my-workspace/config`
- **为什么有问题**:
  - 违反了 AGENTS.md 的 "设计下层组件接口时，必须假设上层组件不存在" 原则
  - `location.py` 硬编码了 `workspace/config` 子路径，假设 `project_root` 是 workspace 的父目录
  - 但 CLI 层传入的 `workspace_root` 就是 workspace 本身
- **直接证据**:
  - `location.py:51`: `workspace_config = project_root / "workspace" / "config"`
  - `entrypoint_runtime.py:514`: `project_root=request.workspace_root`
  - `arg_parsing.py:14`: `DEFAULT_WORKSPACE: str = "./workspace"`
- **影响**: 用户无法正确使用 `--base` 参数，配置查找路径错误，导致 runtime 无法找到 overlay 配置
- **建议改法和验证点**:
  1. 统一参数名为 `workspace_root`
  2. `location.py` 应直接从 `workspace_root / "config"` 查找配置
  3. 验证: `dayu-cli prompt --base ./test "test"` 应查找 `./test/config`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 严重

---

### 2-未修复-严重-路径嵌套：默认 workspace 导致双重嵌套

- **位置**: `dayu/cli/arg_parsing.py:14`, `dayu/runtime/location.py:51`
- **问题类型**: 状态机漏洞 / 数据损坏
- **当前写法**:
  - `DEFAULT_WORKSPACE = "./workspace"`（arg_parsing.py:14）
  - `location.py` 在 `project_root / "workspace" / "config"` 查找配置
- **反例/失败场景**:
  - 用户执行 `dayu-cli init`（无 `--base` 参数）
  - 默认 `workspace_root = ./workspace`
  - `init.py` 创建 `./workspace/config/`
  - 但 `location.py` 查找 `./workspace/workspace/config/`（不存在！）
  - 结果: overlay 配置永远无法被找到
- **为什么有问题**:
  - `init.py` 和 `location.py` 对 workspace 结构的理解不一致
  - `init.py` 假设: `workspace_root/config/`
  - `location.py` 假设: `project_root/workspace/config/`
  - 这两个假设在默认情况下冲突
- **直接证据**:
  - `init.py:90`: `config_dir = workspace_root / _WORKSPACE_CONFIG_DIR_NAME`
  - `location.py:51`: `workspace_config = project_root / "workspace" / "config"`
- **影响**: 默认配置 overlay 永远无法生效，用户自定义配置被忽略
- **建议改法和验证点**:
  1. 修改 `location.py` 从 `workspace_root / "config"` 查找
  2. 或者修改 `DEFAULT_WORKSPACE = "."` 并调整 `init.py`
  3. 验证: `dayu-cli init && dayu-cli prompt "test"` 应能正确加载 overlay 配置
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 严重

### 3-未修复-中-架构边界：public contract 分散在多层

- **位置**: `dayu/cli/agent_entrypoint.py:294-301`, `dayu/runtime/config_loader.py:40`, `dayu/runtime/location.py:32`
- **问题类型**: 架构边界 / 过度耦合
- **当前写法**:
  - `package_config_root()` 定义在 CLI 层 (`agent_entrypoint.py:294`)
  - `_CONFIG_ROOT` 定义在 runtime 层 (`config_loader.py:40`)
  - `resolve_runtime_locations()` 定义在 runtime 层 (`location.py:32`)
  - 三者都计算包内配置根目录，但位置不同
- **反例/失败场景**:
  - 如果包结构变化，需要同时修改三处
  - CLI 层的 `package_config_root()` 和 runtime 层的 `_CONFIG_ROOT` 可能不同步
- **为什么有问题**:
  - 违反了 AGENTS.md 的 "各层需要公共运行时能力时，必须优先复用或扩展 dayu.runtime" 原则
  - 路径解析逻辑应该集中在 runtime 层，作为 public contract 供上层使用
- **直接证据**:
  - `agent_entrypoint.py:301`: `return Path(__file__).resolve().parents[1] / "config"`
  - `config_loader.py:40`: `_CONFIG_ROOT: Final[Path] = Path(__file__).resolve().parents[1] / "config"`
  - 两者计算方式相同，但位置不同
- **影响**: 维护成本高，容易出现不一致
- **建议改法和验证点**:
  1. 在 `dayu/runtime/` 下新增 `paths.py` 或扩展现有模块
  2. 提供 `get_package_config_root()` 和 `get_workspace_config_dir(workspace_root)` 作为 public contract
  3. CLI 层和 runtime 层统一使用这些 contract
  4. 验证: 所有路径解析都通过 runtime 层的 public contract
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-中-最佳实践偏离：workspace 字符串硬编码散落

- **位置**: `dayu/runtime/location.py:51`, `dayu/cli/arg_parsing.py:14`, `dayu/cli/commands/init.py:30`
- **问题类型**: 最佳实践偏离 / 魔法字符串
- **当前写法**:
  - `"workspace"` 字符串在多处硬编码
  - `location.py:51`: `project_root / "workspace" / "config"`
  - `arg_parsing.py:14`: `DEFAULT_WORKSPACE = "./workspace"`
  - `init.py:30`: `_WORKSPACE_CONFIG_DIR_NAME = "config"`
- **反例/失败场景**:
  - 如果需要修改 workspace 目录名，需要搜索并修改多处
  - 容易遗漏，导致不一致
- **为什么有问题**:
  - 违反了 AGENTS.md 的 "禁止魔法字符串" 原则
  - 用户建议: "workspace 字符串原则上只应作为 --base 默认值出现"
- **直接证据**:
  - 多处硬编码 `"workspace"` 字符串
- **影响**: 维护困难，容易出错
- **建议改法和验证点**:
  1. 在 runtime 层定义常量 `WORKSPACE_CONFIG_DIR_NAME = "config"`
  2. 提供 `get_workspace_root()` 函数，接受 `base_dir` 参数
  3. `DEFAULT_WORKSPACE` 应该是 `"."` 或 `"./"`，而不是 `"./workspace"`
  4. 验证: 所有 workspace 路径都通过 public contract 构造
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 5-未修复-低-nested workspace 风险：用户可能意外创建嵌套目录

- **位置**: `dayu/runtime/location.py:51`, `dayu/cli/commands/init.py:134`
- **问题类型**: 数据损坏 / 用户可见错误
- **当前写法**:
  - `location.py` 从 `project_root / "workspace" / "config"` 查找
  - `init.py` 使用 `workspace_root.mkdir(parents=True, exist_ok=True)` 创建目录
- **反例/失败场景**:
  - 用户在 workspace 目录内执行 `dayu-cli init`
  - 默认 `workspace_root = ./workspace`
  - 如果当前目录已经是 workspace，会创建 `./workspace/workspace/`
  - 这会导致嵌套的 workspace 目录结构
- **为什么有问题**:
  - 用户可能不理解 `--base` 参数的语义
  - 默认值 `./workspace` 容易导致嵌套
- **直接证据**:
  - `init.py:134`: `workspace_root.mkdir(parents=True, exist_ok=True)`
  - 没有检查是否已经在一个 workspace 内
- **影响**: 用户可能创建意外的嵌套目录结构
- **建议改法和验证点**:
  1. 在 `init.py` 中添加检查，如果当前目录已经是 workspace，给出警告
  2. 或者修改默认值为 `"."`，避免嵌套
  3. 验证: 在 workspace 内执行 `dayu-cli init` 应给出明确提示
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Final Plan Review Conclusion

**fail** - 存在结构性语义混淆，需要重新设计路径解析架构。

核心问题是 `location.py` 中的 `project_root` 参数名和 `workspace/config` 硬编码路径与 CLI 层的 `workspace_root` 语义不一致。这导致:
1. 用户无法正确使用 `--base` 参数
2. 默认配置 overlay 无法生效
3. 可能创建嵌套的 workspace 目录

建议:
1. 统一参数名为 `workspace_root`
2. 修改 `location.py` 从 `workspace_root / "config"` 查找配置
3. 在 runtime 层提供路径解析的 public contract
4. 将 `DEFAULT_WORKSPACE` 改为 `"."` 或提供更清晰的语义
