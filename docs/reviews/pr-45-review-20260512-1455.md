## Findings

### 1-已修复-中-AgentPolicy 构造期未校验 max_iterations 与 fallback_prompt

> **Controller status (2026-05-12)**：accepted → 已修复。`AgentPolicy.__post_init__`
> 新增 `max_iterations >= 1` 与 `fallback_prompt.strip() != ""` 校验，并补
> `tests/engine/test_agent_phase3_tool_call.py::test_agent_policy_rejects_invalid_values`。

- **入口/函数**: `AgentPolicy.__post_init__` 构造期校验
- **文件(行号)**: `dayu/engine/contracts/agent_policy.py:68-91`
- **输入场景**: 调用方构造 `AgentPolicy(max_iterations=0)` 或 `AgentPolicy(fallback_prompt="  ")`
- **实际分支**: `__post_init__` 仅校验 `tool_execution_timeout_seconds`、`continuation_max_attempts`、`continuation_prompt`、`max_consecutive_failed_tool_batches`，对 `max_iterations` 和 `fallback_prompt` 未做任何校验
- **预期行为**: 作为公共契约 dataclass，所有影响状态机正确性的字段都应在构造期 fail-fast
- **实际行为**: `max_iterations < 1` 在 Agent 入口 `run_messages()`（agent.py:599）才被检测；`fallback_prompt` 为空时在 `FORCE_ANSWER` 路径产生空 UserMessage 注入 LLM context，LLM 行为未定义
- **直接证据**: `__post_init__` 中四个校验逐个枚举了被校验字段（line 75-91），明显遗漏 `max_iterations` 和 `fallback_prompt`；而 `max_iterations` 校验推迟到 agent.py:599
- **影响**: 非法 `AgentPolicy` 对象可在构造后、使用前在系统中传递，违背 fail-fast 原则；`fallback_prompt` 空字符串不会被任何校验拦截，导致 force-answer 轮向 LLM 注入空消息
- **建议改法和验证点**: 在 `__post_init__` 中补齐 `max_iterations < 1` 和 `fallback_prompt.strip() == ""` 的 ValueError 抛出；补充对应参数化测试
- **修复风险（低）**: 纯校验新增，不改变现有合法路径行为
- **严重程度（中）**

### 2-documented-低-_make_failed_or_cancelled_terminal_with_close 方法命名与实际行为不一致

> **Controller status (2026-05-12)**：documented only。运行期由
> `run_messages.finally` 通过 `_close_runner_once` 幂等收口，无 runner
> 泄漏；未引入重命名 / 行为统一改动，作为后续 Engine 内部 refactor 的
> residual risk 记录。

- **入口/函数**: `_AsyncAgent._make_failed_or_cancelled_terminal_with_close`
- **文件(行号)**: `dayu/engine/agent.py:1970-1983`
- **输入场景**: 调用方传入 `RunFailedData` 且当前 token 未取消
- **实际分支**: `if self._is_cancelled():` 为 `False`，走 `return self._make_terminal_failed(failure)`（line 1982）
- **预期行为**: 方法名含 `_with_close` 后缀，暗示本方法内部会关闭 Runner
- **实际行为**: 未取消路径直接调用 `_make_terminal_failed`，不关闭 Runner。Runner 关闭实际由 `run_messages()` 的 `finally` 块（line 831-833）中的 `_close_runner_once()` 完成
- **直接证据**: Line 1982 调用 `_make_terminal_failed`（不含 close）；对比同类方法 `_make_cancelled_terminal_with_close`（line 2049）和 `_make_tool_timeout_terminal_with_close`（line 1984）均在返回前显式调用了 `await self._close_runner_once()`
- **影响**: 当前无运行时 bug（外层 finally 兜底），但方法契约不清晰，后续维护者若在其他上下文调用此方法可能遗漏 Runner 关闭
- **建议改法和验证点**: 统一行为：未取消路径也先 `await self._close_runner_once()` 再构造 terminal，与另两个 `_with_close` 方法一致；或重命名为去掉 `_with_close` 后缀
- **修复风险（低）**: 调用方路径均已受 finally 保护，增加 close 调用是幂等的（`_close_runner_once` 有 `_closed` 守卫）
- **严重程度（低）**

## Residual Risk

1. **批次双射校验无独立单元测试**：`_validate_batch_bijection`（agent.py:1683-1713）未在单独测试中验证 record 重复 ID、record 缺失 ID、record 多余 ID 等边界。当前由集成测试路径间接覆盖（executor 返回正确 records 的 happy path），但 bijection violation 的 fail-closed 语义缺乏直接验证。

2. **ToolCancelledOutcome LLM 投影不含 meta**：`_project_tool_cancelled_for_llm`（agent.py:311-328）不投影 `meta` 字段（含 tool_name / started_at / finished_at），与其他 outcome 类型的投影一致，但 cancelled 场景的 timing 信息对 LLM 判断是否重试可能有参考价值。当前为有意设计选择，非 bug。

3. **`docs/engine/design.md` 与 `docs/host/design.md` 真源定位**：CLAUDE.md 和 AGENTS.md 中删除了这两个文件是"接口与架构边界真源"的声明。PR 中仍修改了这两个文件，说明它们仍承载有效设计信息。删除声明后，新开发者可能不知道这些文件的存在与权威性。建议在 `dayu/engine/README.md` 或 `dayu/host/README.md` 中补充对 design.md 的引用。
