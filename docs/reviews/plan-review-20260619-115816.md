## Findings

### 01-未修复-中-缺少 `_durable_options_from_open_host_options()` 实现细节

- **位置**: Data Flow 章节，step 2（line 149）
- **问题类型**: 契约缺失
- **当前写法**: plan 声称通过 `_durable_options_from_open_host_options()` 打开本次 smoke durable store，但未说明该函数是否已存在或需要新增
- **反例/失败场景**: 如果该函数不存在，implementation agent 需要自行设计从 `OpenHostOptions` 获取 durable store 的路径，可能引入与 production Host 内部实现的耦合
- **为什么有问题**: plan 的 stop condition 要求"如果只能通过读取 production compact artifact 正文、memory 表或修改 production compact 行为才能输出上述信息，停止并报告"，但未明确 `_durable_options_from_open_host_options()` 的实现边界
- **直接证据**: `utils/smoke_host_public_conversation_memory_scenarios.py` 中未找到该函数定义；现有 `_compact_audit_report()` 调用签名暗示需要从 `OpenHostOptions` 获取 session 的 EventLog rows
- **影响**: implementation agent 可能需要探索 Host 内部 API 来获取 durable store，增加耦合风险
- **建议改法和验证点**: 
  - 明确 `_durable_options_from_open_host_options()` 是新增 helper 还是调用现有 public API
  - 如果是新增，明确其只使用 Host public API（如 `open_host()` 返回的 handle）
  - 验证点：该函数不应 import `dayu.host` 内部模块
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-中-`_compact_audit_report_from_rows()` 测试复用路径不明确

- **位置**: Slice 1 Allowed changes（line 177）和 Tests（line 197）
- **问题类型**: 切片过粗
- **当前写法**: plan 新增 `_compact_audit_report_from_rows()` 供单元测试不打开真实 DB，但未说明如何从 `_compact_audit_report()` 复用逻辑
- **反例/失败场景**: implementation agent 可能写出两套独立逻辑，导致 `_compact_audit_report()` 和 `_compact_audit_report_from_rows()` 行为不一致
- **为什么有问题**: plan 的 completion signal 要求"当前 pyright 的 `_compact_audit_report` / `_print_compact_audit_report` 未定义错误消失"，但未强制两个函数共享核心逻辑
- **直接证据**: 现有 `_compact_audit_summary_from_rows()` 已经是从 rows 构造 summary 的独立函数（line 3186），暗示 pattern 是"from_rows 做核心逻辑，外层函数负责打开 DB"
- **影响**: 可能产生代码重复或行为不一致
- **建议改法和验证点**: 
  - 明确 `_compact_audit_report()` 内部调用 `_compact_audit_report_from_rows()`
  - 测试只覆盖 `_compact_audit_report_from_rows()`，不重复测试 `_compact_audit_report()` 的 DB 打开逻辑
  - 验证点：`_compact_audit_report()` 的实现应是 `_read_compact_event_rows()` + `_compact_audit_report_from_rows()` 的组合
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-低-`proposal_manifest_ref` 缺失时的 failure_stage 映射过于绝对

- **位置**: Implementation Decisions #4（line 121-127）
- **问题类型**: 最佳实践偏离
- **当前写法**: plan 硬编码 `proposal_manifest_ref` 缺失时 `failure_stage=prepare_or_material_projection`，present 时 `failure_stage=proposal_or_quality`
- **反例/失败场景**: 未来如果 `proposal_manifest_ref` 在其它阶段也可能缺失（如 manifest 写入后但 proposal 质量不合格），这个映射会误导诊断
- **为什么有问题**: `conversation-memory-smoke-compact-followup.md` 明确指出"manifest 是在 `prepare_compactor_proposal_run_input` 成功后才记录"（line 144），因此当前映射是准确的，但 plan 应注明这个映射依赖当前 Host 实现细节
- **直接证据**: followup doc line 144: "manifest 是在 `prepare_compactor_proposal_run_input` 成功后才记录；因此 `proposal_manifest_ref` 为空说明主失败发生在 runner call manifest 写入前"
- **影响**: 低，当前映射正确，但未来可能需要调整
- **建议改法和验证点**: 
  - 在 plan 中注明 `failure_stage` 映射依赖当前 Host 实现，未来如果 Host 行为变化需要重新校准
  - 验证点：测试应覆盖 `proposal_manifest_ref` present 和 missing 两种情况
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-中-stdout 换行规则缺少具体实现指导

- **位置**: Implementation Decisions #6（line 134-137）
- **问题类型**: 不可直接实施
- **当前写法**: plan 要求"不通过 partial write 输出 `SMOKE TOOL_CALLS_BY_KEY`，避免和 `SMOKE FAIL` 粘连"，但未说明如何检测和修复现有粘连问题
- **反例/失败场景**: implementation agent 可能只修复新增代码的换行，而忽略现有 `main()` 中的粘连问题
- **为什么有问题**: followup doc 明确指出"long25 日志中 `SMOKE TOOL_CALLS_BY_KEY ...SMOKE FAIL` 粘在同一行"（line 75），说明现有代码有粘连 bug
- **直接证据**: `utils/smoke_host_public_conversation_memory_scenarios.py` line 2093-2103 显示 `print(calls_by_key_summary(...))` 和后续 print 之间没有显式 flush
- **影响**: 即使新增代码正确，现有粘连仍会导致诊断输出混乱
- **建议改法和验证点**: 
  - 明确需要修改 `main()` 中的现有 print 语句，确保每个 `SMOKE` 前缀独立一行
  - 使用 `print(..., flush=True)` 或在关键点手动 flush
  - 验证点：capsys 测试应断言每个 `SMOKE` 前缀独占一行
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 05-未修复-低-Slice 2 README 边界说明可能过于详细

- **直接证据**: README.md line 22: "不写未来计划、未落地能力或内部治理术语；若必须提到尚未实现的用户入口，只能作为用户可见限制简短说明"

- **严重程度（低/中/高/严重）**: 低

## Residual Risks

1. **Production memory compact failure 未修复**
   - plan 明确这是后续 work unit（line 220）
   - 风险：本 work unit 只改善可观测性，不解决 root cause

2. **Real LLM long25 验证成本高**
   - plan 承认"Real LLM long25 may remain costly or flaky"（line 322）
   - 风险：unit / assembly tests 可能无法覆盖真实 LLM 交互的 edge cases

3. **EventLog payload 字段稳定性**
   - plan 依赖 `diagnostic_refs`、`proposal_manifest_ref`、`failure_category` 等 payload 字段
   - 风险：如果 Host 未来修改 payload schema，smoke 诊断可能失效

4. **`fallback_action=dispatch` 的 hard fail 语义**
   - plan 强调"不因为 `fallback_action=dispatch` 放宽验收"（line 63）
   - 风险：如果用户误解 dispatch fallback 为 compact 成功，可能导致混淆

## Plan Review Conclusion

**pass-with-risks**

Plan 整体结构清晰，scope 合理，non-goals 明确，slices 可执行。主要风险点在于：

1. **`_durable_options_from_open_host_options()` 实现路径不明确**（Finding 01）- 中等风险，需要 implementation agent 探索 Host API
2. **`_compact_audit_report_from_rows()` 复用逻辑未强制**（Finding 02）- 中等风险，可能导致代码重复
3. **stdout 换行规则缺少具体实现指导**（Finding 04）- 中等风险，现有粘连 bug 可能未修复

这些风险不构成 true blockers，但 implementation agent 需要在 Slice 1 开始前澄清 Finding 01 和 02 的实现路径。建议 controller 在 adjudicate 时要求 implementation agent 先确认 `_durable_options_from_open_host_options()` 的实现方案。

其余 findings 为低风险或可接受的 tradeoff，不阻塞 implementation。
