## 原 Findings 关闭核验

### DL-PR-01（原 HIGH）：Slice 4 integrity repair 与 "HTTP 在 begin_batch 前" 矛盾

**原问题**：原 plan 同时要求 integrity check 在 publication guard 下（需持锁）且 HTTP 在 `begin_batch` 前（不能持锁），形成互斥不变量。

**修订后 plan 直接证据**（§5.6）：

- Phase A："短publication guard内只读取并返回identity/revision+integrity" → 释放 guard → 锁外 prefetch（HTTP/PDF/Docling）
- Phase B："预取完成后调用 `begin_batch`；writer lock获取后必须复制最新published tree。workflow在该batch owner内调用staged classification，先比较Phase A publication identity/revision与latest staged identity/revision"
- Identity-first decision："只要latest target的presence/identity/revision相对Phase A发生变化，无论latest status是 `COMPLETE`、`REPAIR_REQUIRED` 还是 `MISSING`，都必须rollback、释放writer/reservation、丢弃陈旧预取并回到Phase A"
- 最大 3 轮 revision churn，超出抛 typed integrity-repair conflict failure
- Slice 4 stop condition 明确："AST/call-graph与barrier双证据证明所有外部I/O在writer/publication lock外"

**代码真源验证**：

- `_fs_storage_infra.py` L1490-1504 `_acquire_publication_guard` 可独立于 `begin_batch` 调用（使用 `blocking=True`），Phase A 短持 publication guard 只读后释放，不获取 writer lock
- `_fs_storage_infra.py` L1464-1488 `_acquire_ticker_lock` 在 `begin_batch` 中获取，Phase B 在此之后操作
- 锁顺序：Phase A（publication guard only）→ 释放 → HTTP → Phase B（writer lock only）→ 不获取 publication guard（staging 读取）。无嵌套锁，无死锁路径。

**裁决**：**resolved**。Two-phase 设计清晰分离了 Phase A（短读）与 Phase B（staging），HTTP 严格在锁外，identity-first 比较处理了跨 phase 的并发变更。原矛盾已消除。

### 检查项 1：§5.5 operation_task 语义完整性

**Plan 声称**：runtime 创建并保存单次私有 `operation_task`，该 task 拥有 producer thread 与 queue pump；正常完成、取消和 consumer abort 都由此 task 收口。

**验证**：
- Plan 明确 operation_task 的生命周期："正常完成、取消和 consumer abort 都必须由它收口"
- Consumer abort 路径："consumer异常关闭或runtime shutdown时，runtime先request cancellation；必要时只由Fins owner对其私有 `operation_task.cancel()`，并在task内部捕获取消、用shielded cleanup继续等待producer thread与其下游资源退出"
- `ValidatedFinsEventStream.aclose()` 必须等待 owner cleanup 完成
- 取消路径中 adapter/provider 先退出、Docling runner 完成 process cleanup、storage batch commit/rollback 并释放锁，producer 才把唯一 cancelled RESULT 入 queue → operation task join producer → drain RESULT → clean exhaustion

**评估**：operation_task 的创建、所有权、三条终态路径（正常/取消/consumer abort）、与 `aclose()` 的契约均已充分指定。无缺失。

**结论**：无新 finding。

### 检查项 2：§5.6 identity-first two-phase 的 overwrite true/false 语义

**Plan 声称**（CTRL-R01 修复后）：

- Phase A 中 `COMPLETE + overwrite_existing=False`：立即 skip，不做 HTTP/PDF/Docling 或 `begin_batch`
- Phase A 中 `COMPLETE + overwrite_existing=True`：进入 Phase B
- Phase B 中 identity/revision 变化 → 回 Phase A（无论 latest status）
- Phase B 中 same identity + `COMPLETE + overwrite_existing=True`：按显式 overwrite apply
- Phase B 中 same identity + `COMPLETE + overwrite_existing=False`：丢弃预取并 skip

**验证**：
- 代码真源：`cn_download_filing_workflow.py` 公开参数契约 "`overwrite=True` 时禁止复用和skip"，`_resolve_fast_skip_result` 在 overwrite 时返回 None
- Plan §14.5 CTRL-R01："旧计划按latest COMPLETE直接skip违反request owner"

**反例压力测试**：
1. Phase A: COMPLETE + overwrite=True → 进入 Phase B（正确，用户明确要求 overwrite）
2. Phase B: latest identity 变化为 COMPLETE → 回 Phase A（正确，有新 revision 需重新评估）
3. 第二轮 Phase A: COMPLETE + overwrite=True → 再进入 Phase B（正确，overwrite 仍然 True）
4. 第二轮 Phase B: same identity + COMPLETE → apply overwrite（正确，无需再 skip）

**评估**：overwrite=True 在任何路径都不会被意外转成 skip；identity 变化总是触发重新评估而不是静默使用旧 prefetch。

**结论**：无新 finding。

### 检查项 3：same-target last-writer / different-target union

**Plan 声称**（§5.6）：
- "同target两个合法overwrite writer的语义是序列化后的last-writer：后获得writer的一方若看到前一方新revision，必须丢弃旧prefetch、基于新revision重新获取remote replacement后再发布；两方都成功，最终内容来自最后一次经revision复核的overwrite"
- "不同target writer在latest tree副本上只改各自target，最终published集合必须保留并集"

**反例压力测试**：

Scenario A（同 target 双 overwrite）：
1. Writer A: Phase A → 预取 Payload_A → Phase B（same identity）→ apply → commit（revision r2）→ release
2. Writer B: Phase A（读 revision r1）→ 预取 Payload_B → Phase B → 发现 latest revision r2 ≠ r1 → rollback → 回 Phase A
3. Writer B: Phase A（读 revision r2）→ 预取 Payload_B' → Phase B（same identity r2）→ apply → commit（revision r3）→ release
4. 最终 target = Payload_B'（last-writer），两方都成功

Scenario B（不同 target 双 writer）：
1. Writer A: 修改 target_1 → commit（tree = {target_1: rev_a1, target_2: rev_original}）
2. Writer B: 基于 latest tree → 修改 target_2 → commit（tree = {target_1: rev_a1, target_2: rev_b1}）
3. 最终并集：{target_1: rev_a1, target_2: rev_b1}

**评估**：Last-writer 语义正确，identity-first 比较防止陈旧 prefetch 覆盖新 revision。不同 target 的并集保留由各自独立 staging 保证。Slice 4 stop condition 包含了对应的 barrier 测试矩阵。

**结论**：无新 finding。

### 检查项 4：§5.5 cancellation 的 terminal gate 原子性

**Plan 声称**：
- "terminal gate由Fins runtime原子裁决：token在RUNNING期间先被接受则状态进入 `CANCELLATION_REQUESTED`"
- "若success/failure已先完成owner决策，晚到SIGINT不得改写"
- "取消路径中adapter/provider先退出、Docling runner完成process cleanup、任何open storage batch commit/rollback并释放锁，producer再把唯一cancelled RESULT作为最后业务event入queue并退出"

**反例压力测试**：

Scenario C（取消与 success 竞速）：
1. Producer thread 即将完成最后一个 document → RESULT 入 queue
2. 同时 SIGINT 到达 → runtime 请求 cancellation
3. 由于 success RESULT 已先入 queue，terminal gate 判定 success 先完成 → SIGINT 不改写
4. Validator 读到 success RESULT → CLI 使用 success exit code

Scenario D（取消先于 success）：
1. SIGINT 到达 → runtime 请求 cancellation → token 被接受 → 状态 = CANCELLATION_REQUESTED
2. Producer 后续的 provider/child 异常只作诊断 → 不产生 failure RESULT
3. Producer 等待 Docling runner close + storage rollback → 入 queue 唯一 cancelled RESULT
4. Validator 读到 cancelled RESULT → CLI exit 130

**评估**：Terminal gate 的原子性由 "谁先完成决策" 保证，与 plan §5.5 状态机一致。CLI 无权超时/强杀/合成 terminal。

**结论**：无新 finding。
