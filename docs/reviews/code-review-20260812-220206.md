## Findings

### 001-未修复-低-durable upload 路径 save→projection 仍存在 TOCTOU 窗口，但安全网生效

- **入口/函数**: `FinsIngestionRuntime._run_upload_job` (line 3856)
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:3902-3923`
- **输入场景**: `save_accepted_upload_terminal_if_active` 返回 saved record 后、`_emit_progress_event` 或 `_append_terminal_job_event_warn` 执行前，外部并发写入者覆盖了该 job 的 terminal record。
- **实际分支**: projection 使用 `saved` (line 3909-3923) 投影 progress/event。若外部并发在 save 返回后修改了 record，projection 基于 stale `saved`。
- **预期行为**: projection 应始终基于最新 durable record。
- **实际行为**: progress/event 基于 save 返回时的快照。若外部并发覆盖，projection 可能 emit 不一致的 progress。
- **直接证据**: line 3909 `saved_disposition = _upload_terminal_disposition_from_job_record(saved)` 使用函数局部变量 `saved`，而非重新 `read_job`。line 3912-3922 的 `_emit_progress_event` / `_append_terminal_job_event_warn` 同样使用 `saved`。若 save 返回后、projection 前外部并发写入（如另一个 process），projection 基于旧快照。
- **影响**: 极低——file lock 在 save 内部已释放，但同一 job_id 的并发写入在生产中不存在（同一 job 只有一个 writer）。即使发生，`_append_terminal_job_event_warn` 内部 catch+WARN 不抛异常，且 `_save_failed_from_exception` 的 terminal check (line 4875) 阻止终态覆盖。
- **建议改法和验证点**: 不要求修复。该窗口仅在 file-lock 外并发写入场景存在，而生产架构不产生此场景。若未来引入 job 级别的并发 writer，应在 projection 前重新 `read_job` 取最新 record。
- **修复风险（低）**: 无需修复。
- **严重程度（低）**: 既有架构模式，非本 WU 引入，触发条件在生产中不存在。
