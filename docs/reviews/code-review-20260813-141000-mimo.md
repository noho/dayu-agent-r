### (2) flush 双异常：DoclingRuntimeInitializationError 分类保留，success/flush-only/restore/close/FD leak 路径

**结论：通过。**

生产代码变更（`docling_process_converter.py:84-91`）：

```python
active_error = sys.exception()
try:
    try:
        stderr_stream.flush()
    except Exception:
        if active_error is None:
            raise
finally:
    os.dup2(inherited_stderr_copy, stderr_file_descriptor)
```

逐路径分析：

| 场景 | `active_error` | flush 结果 | 传播异常 | FD2 恢复 | 复制 FD 关闭 |
|---|---|---|---|---|---|
| 主体成功，flush 成功 | `None` | 正常 | 无 | ✅ `dup2` | ✅ `close` |
| 主体成功，flush 失败 | `None` | `OSError` | flush `OSError` | ✅ `finally` | ✅ `finally` |
| 主体失败（如 `DoclingRuntimeInitializationError`），flush 成功 | 非 `None` | 正常 | 主体异常 | ✅ `dup2` | ✅ `close` |
| 主体失败，flush 也失败 | 非 `None` | `OSError`（被抑制） | 主体异常（不被改写） | ✅ `finally` | ✅ `close` |

`sys.exception()` 在 Python 3.11 中返回当前正在处理的异常。在 `contextmanager` 的 generator 中，`yield` 被 `throw()` 唤醒时 `sys.exception()` 正确返回被 throw 的异常。`active_error` 在进入 flush try 之前捕获，确保捕获的是主体异常而非 flush 次生异常。
