## Findings

### 01-未修复-[高]-取消把 durable admission 的未知结果误判为“Run 未接受”

- 类型：correctness / lifecycle / semantic ownership drift
- 位置：`dayu/cli/session_execution.py:818-980`；`dayu/service/entrypoint_runtime.py:1035-1068`；`dayu/host/_durable_actor.py:1-6,88-105`
- 入口或调用路径：`dayu-cli prompt` → `_submit_prompt_turn_handling_sigint` → `submit_entrypoint_turn_and_wait` → `Host.submit_followup` → `DurableActor.call`
- 触发输入：第一次 Ctrl+C 或 Escape 命中 Host durable submit 已经开始、甚至已经提交 `RUN_ACCEPTED`，但 `host.submit_followup(...)` 的结果尚未返回、`on_run_accepted` 尚未执行的窗口。
- 实际分支：`_cancel_prompt_turn_after_local_request` 先执行 `submit_task.cancel()`；取消 awaiter 后只检查本地 `_PromptAcceptedRunState.run_id`，为空便直接返回 `None` 并最终退出 130。可是 Host durable actor 明确用 `asyncio.shield` 保证 caller cancellation 不取消已开始的 durable operation，所以底层 submit 仍可完成提交。Service 只有在 `await host.submit_followup(...)` 返回后才 bind/callback；被取消的上层 task 不再把已接受的 run id 交给 CLI。
- 预期行为：submit disposition 不确定时，生命周期 owner 必须先获得或按稳定 `client_request_id` 协调 canonical admission 结果；若 Run 已接受，则只通过 Host public cancel 发起一次取消并等待 canonical terminal state，退出 130 前不得留下 running Run/attempt。
- 实际行为：CLI 可以在屏幕和 exit code 上表现为“已取消”，却没有发出 Host cancel；底层随后仍产生 accepted/running Run，缺少 `CANCEL_REQUESTED`、`RUN_CANCELLED` 或等价 canonical terminal state。
- 直接证据：`dayu/host/_durable_actor.py:3-6,94-104` 将“调用方取消不会取消已经开始的 durable operation”写成 owner contract；`dayu/cli/session_execution.py:969-973` 却把被取消 awaiter 且 callback 未写入，等价为“未接受”。`tests/cli/test_prompt_command.py:2782-2820` 使用的 blocking fake 在 task cancellation 后不会像真实 durable actor 一样继续 commit，因此不能证明该窗口。现有 real scenarios 要么在无 DB 的更早窗口触发，要么在 accepted callback 已完成后触发，也没有 durable-commit/response-undelivered barrier。
- 影响：直接违反 repeated Ctrl+C、Escape 与 active cancellation 的冻结 contract；可能在 CLI 已退出 130 后留下 running Run/attempt，破坏 Host 作为生命周期真源的核心不变量。该项阻断合并与 work unit closeout。
- 修复建议：把“submit admission 的确定结果”归还给 Service/Host admission boundary，不得依赖易丢失的 UI callback。可让 submit admission await 在 caller cancellation 下继续到 typed result，或提供按既有 `client_request_id` 查询/协调 admission 的 public contract；确定 accepted run id 后再调用单一 Host cancel-and-wait 路径。禁止 CLI 假终态、SQLite 补写或 sleep。
- 测试建议：用真实 durable actor/Host 建立确定性 barrier：operation 已进入并可 commit，但 public result/callback 尚未交付时注入 Ctrl+C 与 Escape，再释放 barrier；断言退出 130、只发一次 cancel、EventLog 有 canonical cancel terminal fact、Run/attempt 均非 running，并覆盖快速连续 Ctrl+C。
- 修复风险：高。修复跨越 CLI cancellation 与 Service/Host admission handoff，若错误地扩大为 Host close 自动取消，会改变现有 Host owner 语义；必须保持显式 public cancel。

### 02-未修复-[中]-进程最早启动窗口仍会返回原始 signal code 或 traceback

- 类型：correctness / public CLI contract
- 位置：`dayu/cli/__main__.py:1-24,27-47`；`pyproject.toml:95-96`
- 入口或调用路径：installed `dayu-cli` console script 或 `python -m dayu.cli` → 模块定位/导入 → `run_module` 的 `try` boundary。
- 触发输入：进程刚启动、Python 尚未执行到 `run_module()` 内的 `try`，或 module bootstrap/import 仍在该 boundary 之外时收到 Ctrl+C。
- 实际分支：新的 `KeyboardInterrupt` catch 只覆盖 `run_module` 函数体；它无法覆盖 console wrapper 导入入口模块、`python -m` 定位并执行模块、以及执行到该函数前的 bootstrap。`exit_module` 中屏蔽后续 SIGINT 也只发生在 `run_module` 已经返回 130 之后。
- 预期行为：冻结 `prompt.14` 声明从 `dayu-cli` 进程启动到 Run accepted 的任意阶段，Ctrl+C 都稳定退出 130，不输出 Python traceback，不返回 `-2`，且不创建业务状态。
- 实际行为：installed console 在 delay `0/0.001/0.005s` 的重复实测均返回 `-2`；`0.01s` 可返回 1 并输出 fatal Python/KeyboardInterrupt traceback。`python -m` 同样可在 `0–0.01s` 返回 `-2` 或 traceback。冻结的 installed-console `0.05s` scenario 通过，只证明更晚的已装配窗口，不足以兑现 oracle 的“从进程启动开始”。
- 直接证据：`dayu/cli/__main__.py:5-8` 的模块 import 在 `run_module` try 之外；`dayu/cli/__main__.py:19-24` 才开始 catch。专项实测每个 timing 重复 10 次：installed console `0/0.001/0.005 => {-2:10}`，`0.01 => {1:10 + traceback}`，`0.02/0.05 => {130:10}`；`python -m` 在 `0/0.001/0.005` 均为 `-2`，`0.01` 为 1+traceback，`0.05` 仍混合 `-2/130`。
- 影响：用户要求的 startup cancellation 仍不稳定；自动化调用方可观察 raw signal status 或 traceback。该项相对 literal frozen oracle 阻断“六项全部完成”的结论，即便当前 0.05 秒单点 scenario 为绿。
- 修复建议：先明确 invocation bootstrap 的真正 owner，并让 signal normalization boundary 覆盖 distribution launcher 进入 Python application 前的窗口；若技术上决定不承诺 OS/Python 尚未取得控制权的瞬间，则必须由 oracle owner正式裁决 contract 起点，不能由实现或 evidence 静默收窄，也不能修改冻结 expected behavior 来迁就当前实现。
- 测试建议：对 installed console 与 `python -m` 建立启动阶段矩阵，至少覆盖 process spawn 后立即、模块导入中、main import 中、hook 装配前、Run 创建前；分别断言 exit 130、stderr 可编码且无 traceback、Host/runtime SQLite 无业务记录。
- 修复风险：中。真正覆盖 pre-module bootstrap 可能涉及 distribution launcher；局部再包一层 Python catch 仍会留下更早窗口。
