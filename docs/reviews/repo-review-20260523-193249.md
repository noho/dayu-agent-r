### 1-未修复-严重-测试构造缺陷导致核心路径未覆盖

- **入口/函数**: `test_schema_mapping_with_non_string_key_is_rejected`
- **文件(行号)**: `tests/runtime/test_tools_discovery_digest.py`(306-335)
- **输入场景**: 构造 `ToolParametersSchema` 时 `properties={1: {"type": "string"}}`（整数 key），`required=("company_id",)`
- **实际分支**: `ToolParametersSchema.__post_init__` 先校验 `required` 字段必须在 `properties` 中存在。`"company_id"` 不在 `{1: ...}` 中（整数 key 与字符串不匹配），抛出 `ValueError("ToolParametersSchema.required fields must exist in properties")`
- **预期行为**: 测试应命中 `_tool_definitions_digest` → `normalize_json_value` 中的 `TypeError("JsonValue object key must be str")` 路径
- **实际行为**: 抛出 `ValueError` 而非 `TypeError`，测试验证的是 `required` 校验而非 `non-string key` 校验
- **直接证据**: `tool_schema.py:61-65` 的 `required` 校验在 `properties` key 类型校验之前执行；测试 `pytest.raises(TypeError)` 实际被 `ValueError` 触发（但 pytest 会因异常类型不匹配而 FAIL）
- **影响**: `normalize_json_value` 的非字符串 key 校验路径在 discovery 上下文中未被测试覆盖
- **建议改法**: 将 `required` 改为 `required=()`，使 `ToolParametersSchema` 构造通过，让 digest 计算走到 `normalize_json_value` 的 key 校验路径

### 3-未修复-高-幂等记录写入存在 TOCTOU 竞态，异常分类不精确

- **入口/函数**: `record_idempotent_result` / `append_event`
- **文件(行号)**: `dayu/host/durable/idempotency.py`(127-186)、`dayu/host/durable/event_log.py`(315-395)
- **输入场景**: 两个并发事务对同一 `(scope_kind, scope_id, idempotency_key)` 执行写入
- **实际分支**: 两个函数都采用"先 SELECT，不存在则 INSERT"模式。两个并发事务同时读到不存在的记录并尝试 INSERT 时，后提交者遇到 SQLite UNIQUE constraint 错误
- **预期行为**: 幂等写入应优雅处理并发插入冲突，要么重试读取返回既有记录，要么抛出精确的幂等冲突异常
- **实际行为**: `_classify_sqlite_error` 将 UNIQUE constraint 错误转为 `HostUniqueConstraintError`，但调用方期望 `HostIdempotencyConflictError` 或 `HostEventIdentityConflictError`
- **直接证据**: `idempotency.py:148-154` 先 `read_idempotency_record` 再 INSERT，无 `HostUniqueConstraintError` 捕获；`transaction.py:412-413` 的 `_classify_sqlite_error` 将 UNIQUE constraint 转为 `HostUniqueConstraintError`
- **影响**: 高并发场景下（SQLite 单写入者模型下概率低）调用方收到错误分类的异常，导致错误的用户提示
- **建议改法**: 在 `record_idempotent_result` 和 `append_event` 中捕获 `HostUniqueConstraintError`，重新读取既有记录：若 digest 匹配则返回既有记录（幂等成功），若不匹配则抛出对应的幂等冲突异常
- **修复风险（低/中/高）**: 低。只需在两个函数中增加 try/except 分支
- **严重程度（低/中/高/严重）**: 高

## Residual Risk

1. **durable/memory.py 的 import 边界修复范围大**: 涉及类型定义迁移、多个模块的 import 调整和大量测试同步更新，是本次审查中修复成本最高的问题。
2. **幂等竞态在单进程 SQLite 下触发概率极低**: Python sqlite3 模块的全局解释器锁和 SQLite 单写入者模型使并发 INSERT 同一 key 的概率极低，但仍需正确处理以保证语义完整性。
3. **tool_runtime.py 和 engine_ingest.py 体积过大**: 分别承载 ToolRuntime 和 EngineEvent ingest 的全部逻辑（46000+ / 34000+ tokens），虽内部有清晰分层但影响可维护性。
4. **macOS 平台 recovery 自动恢复能力受限**: PID 复用场景下 orphan detection 退化为 inconclusive，需人工介入。生产环境部署在 Linux 上则无此问题。
5. **Provider 协议变更风险**: SSE 解析器和 non-stream 解析器依赖 OpenAI-compatible 协议字段名，provider 未通知变更字段结构时会以 `RunnerProtocolErrorData` 收口，不会 crash 但可能导致功能降级。
