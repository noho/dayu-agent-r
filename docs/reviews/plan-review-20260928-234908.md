## Findings

### 01-未修复-[低]-后台 download job 路径的中途 typed abort 终态未规定，与「legacy 持久摘要」句存在双重读法

- **位置**: plan 第 43 行「legacy 持久摘要若写入也由同一 `FinsDownloadResultSummary` 派生，不能与 RESULT 分叉」；`dayu/fins/ingestion_runtime.py:4947`（`_run_download_job` 调 `_execute_download_request`）、`:4962-4963`（`except Exception -> _save_failed_from_exception`）、`:5989-6016` 与 `:5935`（`result_summary or dict(_EMPTY_SUMMARY)`，`_EMPTY_SUMMARY={}`，`:172`）
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: plan 规定了 direct 流 RESULT、CLI、Service wait 的同一 public summary/failure，但对后台 job（`:4599` 生产可达）在中途 typed abort 时的 terminal record 只字未提；「legacy 持久摘要若写入……」一句未指明 `_save_failed_from_exception` 写入的 `{}` 是否算「写入的 legacy 持久摘要」
- **反例/失败场景**: 多候选后台 download job，候选一已发布、候选二 Phase B typed abort。`FinsSourceDownloadAdapterFailure` 沿 `_execute_download_request` 抛入 `_run_download_job` 的宽 `except`，job record 终态为 `result_summary={}` + `failure_summary.message=str(exc)`：同一 abort，direct RESULT 携带守恒部分事实，job record 为空。实施 Agent 读法 A（job record 的 `{}` 也是「写入的 legacy 持久摘要」）会去改 `_save_failed_from_exception` 线程化 abort summary；读法 B（job 路径保持既有行为）不动它——两种读法产出不同代码，code re-review 无可验收合同，也无对应测试
- **为什么有问题**: 修订引入的新异常类型改变了 `_run_download_job` 对多候选场景的既有终态行为（修订前 typed 被吞为 filing 行，job 拿真实部分摘要甚至可能 `_save_succeeded`），属于本 amendment 行为半径内的消费者；plan 已用一句「legacy 持久摘要」触碰该边界但未钉死语义
- **直接证据**: `ingestion_runtime.py:4939-4963`（job 收口）、`:5935`（空摘要默认）、`:6007`（`message=str(exc)`）；注意 whole-kind 零候选 typed 逃逸今天已走同一路径，本修订是把该既有行为扩展到多候选场景，而非新造
- **影响**: 实施 Agent 跑偏 / review 不可验收；job 消费者（Host 异步下载）看到与 durable state 不一致的空摘要而无合同依据
- **建议改法和验证点**: plan 二选一并写一句话合同：(a) 显式声明「后台 job 路径保持既有 `_save_failed_from_exception` 行为（空 result_summary + 安全 message），与 whole-kind 零候选既有行为一致」并列入残余风险；或 (b) 规定 job 终态摘要由同一 `FinsDownloadResultSummary.to_json_summary()` 派生并加一条 job 路径测试。验证点：code re-review 检查该句与实现/测试一致
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 02-未修复-[低]-post-repair gate 的中途 typed 逃逸不在新收口覆盖范围，「首候选前」表述未覆盖首候选后的 whole-kind 抛出点

- **位置**: plan 第 39 行「whole-kind preflight 在首候选前抛出时仍传原始异常，属于真正零候选失败」；`dayu/fins/pipelines/cn_download_workflow.py:336-342`（post-repair `classify_source_integrity_preflight`）与 `:349-355`（`_publish_cn_company_after_repair` 的 `commit_batch` whole-tree 检查）
- **问题类型**: 契约缺失 / 状态机漏洞（边界情形）
- **当前写法**: plan 的 typed 收口只包单 filing `async for`（Phase A/B/commit 三入口），并声明 whole-kind preflight 抛出属于「首候选前」「真正零候选失败」

- **为什么有问题**: plan 的「whole-kind = 首候选前 = 零候选」等价式只覆盖 `:227` 的循环前预检与 `:249-256` 的循环前 company 发布；`:336-355` 是首候选**之后**的 whole-kind/company-commit 抛出点，「零候选失败」的归类对它不成立，实施与 review 无从得知该路径是接受残余还是漏网

- **建议改法和验证点**: 在 plan 残余风险中显式登记「post-repair gate 与 company meta commit 的中途 typed 逃逸仅在两次预检间并发外部修改时可达，本轮保持 raw 透传与零摘要行为」；或将 typed 收口上移覆盖整个候选循环体（成本更高，非必要）。验证点：code re-review 确认登记在案
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
