## Findings

### 01-未修复-中-HostToolingOptions.wait_adapter_registry 未进入 durable 行或 per-run request

- **入口/函数**: `HostToolingOptions.__post_init__` (`dayu/host/tooling.py:142`)
- **文件(行号)**: `dayu/host/tooling.py:140`
- **输入场景**: 构造 `HostToolingOptions` 时传入 `wait_adapter_registry`
- **实际分支**: `wait_adapter_registry` 存储在 frozen dataclass 上，但注释明确说"仅用于本地 ToolRuntime awaiting production wiring，不进入 durable row 或 per-run request"
- **预期行为**: 注释承诺此字段是临时的 production wiring 占位
- **实际行为**: `tool_runtime.py` 从 `HostToolingOptions` 读取 `wait_adapter_registry`，但 `WaitAdapterRegistry` 在 `tool_runtime.py` 的 `EffectiveToolBundleBuilder` 中被消费后，其 binding 决定会影响 `ToolAwaitingOutcome` 的 `adapter_key` 写入 durable wait record。如果 registry 仅用于 construction 期但结果进入 durable，则 registry 本身不持久化意味着 recovery 后 binding 不可重建
- **直接证据**: `tooling.py:140` 注释 "仅用于本地 ToolRuntime awaiting production wiring"；`wait_adapter.py:206` 中 `WaitAdapterBinding.external_job_ref` 直接从 `ToolAwaitSpec.resume_token` 派生 `ExternalJobRef`，该 ref 写入 durable wait record
- **影响**: 当前阶段 acceptable（Phase 7 wiring），但 recovery 路径（Phase 11）启动后，如果 WaitAdapterRegistry binding 不可从 durable state 重建，poller 无法恢复对已持久化 wait record 的 poll 能力
- **建议改法和验证点**: 跟踪 Phase 11 设计：是否需要将 adapter binding 持久化到 wait record 本身（已通过 `adapter_key` 字段做到），还是需要 registry 在 recovery 时可重建。当前 `adapter_key` 已持久化，只需确保 Phase 11 的 `WaitPollAdapterRegistry` 能通过 `adapter_key` 匹配到正确的 poll adapter
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-中-duplicate governance 内存索引无 size bound

- **入口/函数**: `InMemoryRunScopedDuplicateGovernanceRegistry`（`dayu/host/tool_runtime.py`）
- **文件(行号)**: `dayu/host/tool_runtime.py`（InMemoryRunScopedDuplicateGovernanceRegistry 类）
- **输入场景**: 长 Run 中大量工具调用产生 accepted 记录
- **实际分支**: `_DuplicateAcceptedEntry` 按 `(tool_identity_digest, normalized_arguments_digest)` 索引，无 TTL 或 size bound
- **预期行为**: run-scoped 内存索引应有上限或淘汰策略
- **实际行为**: 索引只在 `clear_run` 时清理，单次 Run 内可无限增长
- **直接证据**: `_DuplicateAcceptedEntry` 是 frozen dataclass 存入 `dict`，无 eviction 逻辑
- **影响**: 极长 Run（如大量工具调用的财报分析）可能导致内存持续增长；但因 run-scoped、进程内，实际风险取决于单 Run 工具调用上限
- **建议改法和验证点**: 评估是否需要 LRU 或 size cap；当前如果 `AgentPolicy.max_iterations` × 每轮工具数有上限，则内存增长有隐式 bound。确认该 bound 是否足够
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 07-未修复-低-WaitPoller 无并发保护

- **入口/函数**: `WaitPoller.poll_once` (`dayu/host/wait_adapter.py:324`)
- **文件(行号)**: `dayu/host/wait_adapter.py:324-377`
- **输入场景**: 多个 poller 实例或外部调用者同时调用 `poll_once`
- **实际分支**: `poll_once` 读取 wait records → 调用 adapter → 调用 `resolve_wait`，全程无锁
- **预期行为**: 如果多个进程或线程可能同时运行 poller，需要防重复 resolve
- **实际行为**: 依赖 `resolve_wait` 的 idempotency 机制（幂等键基于 `wait_id + source=POLL`）防止重复处理
- **直接证据**: `_poll_idempotency_key` 使用 `wait_id + WaitResolutionSource.POLL` 构造稳定幂等键
- **影响**: idempotency 机制可以防止重复 resolve，但 adapter 的 `poll_wait` 调用仍可能重复发生（浪费外部 API 调用）。当前设计可接受，因为 Host 单进程运行
- **建议改法和验证点**: 如果未来支持多进程 poller，需要在 read 阶段加 lease 或 fencing。当前单进程假设下 idempotency 足够
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
