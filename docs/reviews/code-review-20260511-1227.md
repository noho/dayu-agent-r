### 1-未修复-严重-_build_chunk 返回 (None, 0) 导致 fetch_more 无限循环

- **入口/函数**: `RuntimeTruncateManager.fetch_more` → `_build_chunk`
- **文件(行号)**: `dayu/host/_runtime_truncate_manager.py:922-947`（`_build_chunk`），`dayu/host/_runtime_truncate_manager.py:267-349`（`fetch_more`）
- **输入场景**: cursor 记录的 `strategy` 字段不匹配任何已知策略（例如 `"unknown_strategy"`）。虽然当前代码路径中 `_build_cursor` 总是从合法 `ToolTruncateSpec.strategy` 构造记录，但 `_build_cursor_record` 接受任意 `strategy: str` 参数，且 `_RuntimeCursorRecord.strategy` 是无约束的 `str` 类型。
- **实际分支**: `_build_chunk` 的四个 `if` 分支全部不命中，返回 `(None, 0)`。
- **预期行为**: `_build_chunk` 应对未知策略返回失败信号或抛异常，使 `fetch_more` 能正确收口。
- **实际行为**:
  1. `chunk_value = None`，`chunk_size = 0`
  2. `new_offset = record.offset + 0 = record.offset`（未前进）
  3. `has_more = record.offset < record.total` 为 `True`（假设 `total > 0`）
  4. 签发新 cursor（offset 相同），移除旧 cursor
  5. 返回 `ToolCompletedOutcome(value=None, truncation=新cursor)`
  6. LLM 看到 `truncation.has_more=True`，继续调用 `fetch_more` → 无限循环
- **直接证据**: `_build_chunk` 第 947 行 `return None, 0`；`fetch_more` 第 317 行 `chunk_value, chunk_size = _build_chunk(record=record, limit=limit)`；第 323 行 `new_offset = record.offset + chunk_size`；第 324 行 `has_more = new_offset < record.total`。
- **影响**: LLM 工具调用无限循环，消耗 token 和时间直到超时或达到 max iterations。
- **建议改法和验证点**:
  1. `_build_chunk` 对未知策略应 `raise RuntimeError(f"unsupported truncate strategy: {record.strategy}")`
  2. 或者在 `fetch_more` 中检查 `chunk_size == 0` 时直接返回失败 outcome
  3. 补充测试：构造 strategy 为非法值的 cursor record，验证 `fetch_more` 返回失败而非无限循环
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 严重

### 2-未修复-高-_cleanup_expired 在 apply_truncation 路径中无锁调用

- **入口/函数**: `RuntimeTruncateManager.apply_truncation` → `_build_cursor` → `_cleanup_expired`
- **文件(行号)**: `dayu/host/_runtime_truncate_manager.py:223-265`（`apply_truncation`），`dayu/host/_runtime_truncate_manager.py:429-471`（`_build_cursor`），`dayu/host/_runtime_truncate_manager.py:608-622`（`_cleanup_expired`）
- **输入场景**: 并发执行 `apply_truncation`（业务工具完成后的截断）和 `fetch_more`（framework 工具读取）。
- **实际分支**: `apply_truncation` 不持有 `_read_lock`，直接调用 `_cleanup_expired` 修改 `_records_by_cursor` 和 `_cursor_by_fingerprint`。`fetch_more` 持有 `_read_lock` 并读取 `_records_by_cursor`。
- **预期行为**: 所有对共享状态 `_records_by_cursor` / `_cursor_by_fingerprint` 的写入应通过 `_read_lock` 保护。
- **实际行为**: `_cleanup_expired` 在 `_build_cursor` 内被调用（第 454 行），而 `_build_cursor` 由 `apply_truncation` 调用，`apply_truncation` 不获取锁。虽然当前 asyncio 单线程模型下，`_cleanup_expired` 是纯同步代码不会 yield，因此不会在 `_cleanup_expired` 执行期间切换到 `fetch_more`，但这是一个脆弱的隐式保证——如果未来 `_cleanup_expired` 引入任何 await 点（例如日志 I/O），竞态就会发生。
- **直接证据**: `_read_lock` 仅在 `fetch_more`（第 278 行 `async with self._read_lock:`）中获取；`apply_truncation`（第 223-265 行）和 `_build_cursor`（第 429-471 行）中无锁。
- **影响**: 当前 asyncio 下不会触发实际 bug，但设计脆弱。若 `_cleanup_expired` 未来被改为 async 或在同步路径中引入 yield，会导致 `_records_by_cursor` 字典在迭代中被修改。
- **建议改法和验证点**:
  1. 将 `_read_lock` 重命名为 `_state_lock`，在 `apply_truncation` 的关键路径（`_cleanup_expired` + `_commit_cursor`）也获取该锁
  2. 或者将 `_cleanup_expired` 从 `_build_cursor` 中拆出，在 `apply_truncation` 入口处单独调用（仍需加锁）
  3. 补充并发测试：同时调用 `apply_truncation` 和 `fetch_more`，验证无异常
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高（当前不触发，但随代码演进风险增大）

### 3-未修复-中-CredentialScrub 凭证键列表与设计文档不一致

- **入口/函数**: `_EXPLICIT_CREDENTIAL_KEYS` 常量
- **文件(行号)**: `dayu/host/_credential_scrub.py:22-37`
- **输入场景**: 工具调用参数或结果中包含 `openai-organization`、`cookie`、`anthropic-api-key` 等字段名。
- **实际分支**: `_is_explicit_credential_key` 仅检查 `_EXPLICIT_CREDENTIAL_KEYS` 中的键。
- **预期行为**: 根据 `docs/host/design.md:949-951`（P8.5 前的文字），应 scrub 的键包括 `api_key`、`cookie`、`x-api-key`、`openai-organization`、`anthropic-api-key` 等。
- **实际行为**: `openai-organization` 和 `cookie` 不在 `_EXPLICIT_CREDENTIAL_KEYS` 中。`anthropic-api-key` 虽然不在列表中，但会被正则 `_TEXT_CREDENTIAL_ASSIGNMENT_PATTERN` 匹配（因为包含 `api-key` 模式），所以文本内的赋值会被 scrub，但作为 JSON key 时不会被替换。`cookie` 不在列表中也不在正则中。
- **直接证据**: `_EXPLICIT_CREDENTIAL_KEYS` 第 22-37 行不包含 `openai-organization`、`cookie`、`anthropic-api-key`。正则第 38-42 行不包含 `cookie` 或 `openai-organization` 模式。
- **影响**: 如果工具调用结果中包含 `cookie` 字段（例如浏览器工具返回的 cookie），该字段值不会被 scrub。Dayu 是本地 Agent，风险相对可控，但与设计文档承诺不一致。
- **建议改法和验证点**:
  1. 在 `_EXPLICIT_CREDENTIAL_KEYS` 中补充 `cookie`、`openai-organization`、`anthropic-api-key`、`anthropic-version`
  2. 或者在正则中补充 `cookie` 模式
  3. 补充测试验证这些键被正确 scrub
  4. 同步更新设计文档中的 scrub 键列表，确认哪些是当前实际需要的
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-中-ToolTraceObserver 对已 scrub 数据重复 scrub

- **入口/函数**: `ToolTraceObserver._emit_tool_call`
- **文件(行号)**: `dayu/host/_tool_trace_projection.py:234-238`
- **输入场景**: EventLog 中的 `TOOL_RESULT_ACCEPTED` 事件数据（已在 `_event_translation.py:107-109` 中 scrub 过）被 trace observer 再次 scrub。
- **实际分支**: 第 234 行 `scrubbed_outcome = scrub_tool_execution_outcome(accepted_data.outcome)`。
- **预期行为**: trace observer 应直接使用已 scrub 的 EventLog 数据，或明确声明其独立 scrub 策略。

- **建议改法和验证点**:

  2. 或者移除 trace observer 中的 scrub，直接使用 EventLog 中已 scrub 的数据
  3. 确认 EventLog scrub 与 trace scrub 的策略是否应该一致
