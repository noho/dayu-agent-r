## Findings

### 01-未修复-高-保留名碰撞无 typed 责任，且"既有 storage filename/保留名规则"在本 HEAD 不存在
- **位置**：plan「Owner、计划结果与调用链」段（typed 封闭 reason 集合）、「文件白名单与实现切片」S1 依赖、「风险、依赖、停止与报告」段第 2 句
- **问题类型**：契约缺失 / open question 未收敛 / 语义所有权未判定
- **当前写法**：typed reason 封闭集合为「数量、重复规范路径、重复 original basename、全局名字碰撞、不可原样存储/过长」；保留名问题写成"S1 应用既有 storage filename/保留名规则核实并在同一 preflight 处理，若这要求改变仓储完整性合同则停止"。
- **反例/失败场景**：用户 material 上传一个名为 `meta.json` 的文件（`.json` 是合法转换后缀，admission 全部放行）。按 plan 的规划规则：original 名 `meta.json`、派生名 `meta.json_docling.json`，批次内无冲突，全部通过。进入 `_store_upload_assets` 后 blob 写入 `document_dir/meta.json`（`_fs_storage_infra.py:2605` key = `.../{document_key}/{filename}`），随后 `_create_source_document` 把 source meta 写到同一路径（`:3072-3077` `document_dir / _SOURCE_META_FILENAME`）→ 用户文件内容被 source meta 覆盖，file entry 仍记录其 sha256 → commit 阶段完整性校验不符 → 回滚。即 O04 要消除的"转换付费后通用失败"模式原样复现。同理 `.identity.json` 会命中 identity descriptor（`_fs_identity.py:40`），造成 descriptor 级损坏。
- **为什么有问题**：(1) plan 的 S1 指令建立在"既有 storage filename/保留名规则"之上，但 `_normalize_filename`（`_fs_storage_utils.py:71-84`）只做形状校验，**没有任何保留名语义**——执行 S1 的 Agent 要么按停止条件中断工作单元，要么即兴发明规则，两者都不可验收。(2) 该碰撞类不在封闭 reason 集合内（"不可原样存储"是否涵盖保留名是歧义），也不在测试矩阵内。(3) 保留名语义的真源在 storage 布局（控制文件常量在 `_fs_storage_utils.py`/`_fs_identity.py`），若放进 planner 是 storage 布局知识泄漏到业务规划层；若放进 storage 新校验入口则超出"只开放既有纯 filename 校验"的白名单。owner 未判定，与 AGENTS.md「语义所有权」条款直接冲突。(4) plan 对碰撞面的列举不准确：`material_manifest.json`/`filing_manifest.json` 在 source root（`_fs_storage_infra.py:3137/3168`），用户同名文件落在 document 目录，实际**不**冲突；真正冲突的是 `meta.json` 与 `.identity.json`。
- **直接证据**：`_fs_storage_utils.py:20-21/29-84`、`_fs_identity.py:40`、`_fs_storage_infra.py:2605/3072-3077`、`docling_runtime.py:232`、plan 对应段落原文。
- **影响**：实施 Agent 跑偏或 S1 中断；`meta.json`/`.identity.json` 输入产生数据损坏或转换后回滚；review 无法按封闭 reason 集合验收。
- **建议改法和验证点**：在 plan 阶段先裁决保留名 owner（推荐：storage filename rule 暴露纯校验，包含控制名保留集合与长度边界，planner 只消费判定结果——这与 plan 已有的"复用公开纯校验入口"一致，但把"开放既有"改为"storage 新增并公开纯校验，不改存储接受/完整性语义"）；把"保留名冲突"显式纳入封闭 reason 集合与测试矩阵（`meta.json`、`.identity.json` 两个反例，断言 converter 未调用即 typed 拒绝）；修正风险段的碰撞面表述。
- **修复风险（低/中/高）**：低（纯输入校验，不动仓储完整性合同；若 S1 发现必须改完整性合同则按 plan 既有停止条件上报）
- **严重程度（低/中/高/严重）**：高

### 02-未修复-中-plan 对象 handoff 契约双解，与自设"禁止 nullable plan"禁令冲突
- **位置**：plan「Owner、计划结果与调用链」段"一次规划的 handoff"句
- **问题类型**：契约缺失 / 过度耦合 / 不可直接实施
- **当前写法**：「CLI 在 Service factory/stream 前由 Fins material admission 得到 validated request/selection 与 plan，Service 原样转交；工具与非 CLI runtime 在 observation/job 前用同一 admission，传相同 typed 值；独立调用 SEC/CN/HK pipeline 时在事件和 company batch 前创建一次 plan。禁止 CLI 只检查后丢掉 selection、runner 再规划……不用 nullable `plan`、`getattr` 或'没有就重建'的兼容分支。」
- **反例/失败场景**：Service 路径带 admission 产出的 plan 转交给 `run_upload_material_stream`（现签名 `files: list[Path] | None`，`dayu/fins/pipelines/sec_upload_workflow.py:424`），独立调用（tests、HK 经 CN facade）无 admission。实施 Agent 面临二选一：(a) pipeline 入口接收可选 plan、缺失则自建 → 正是 plan 明文禁止的"nullable plan / 没有就重建"；(b) plan 参数改为必填、所有独立调用方先跑 admission → 与"独立调用 pipeline 时创建一次 plan"字面矛盾，且 `cn_pipeline.py:1107-1109` 等直接构造 selection 的调用点全部要改调用序。两种解读产生不同的签名与不同的测试形态。
- **为什么有问题**：plan 把"同一计划对象保持到消费点"作为核心正确性主张（防 source of truth drift），但没有钉死 plan 对象在 pipeline 入口的类型地位（必填参数 vs 入口内建）。核心 handoff 契约含糊会直接导致实施 Agent 落入兼容分支，违反 AGENTS.md「禁止兼容性代码」。
- **直接证据**：plan 原文；`sec_upload_workflow.py:424-493`（`files` 参数与 `FinsUploadMaterialFiles.from_upsert_paths` 直构点）；`cn_pipeline.py:1107-1109`；`dayu/service/fins_direct.py:299-358`（Service 直构 `FinsUploadMaterialRequest`）；`ingestion_runtime.py:4717-4748`。
- **影响**：实施 Agent 生成 forbidden 兼容分支或改错调用序；两切片验收时对"同一计划对象"无法举证。
- **建议改法和验证点**：plan 明确二选一并写死——推荐：pipeline 入口参数改为必填 validated handoff（raw/validated 显式区分，与 filing 的 `ValidatedFinsUploadFilingRequest` 同型），一切独立调用方先调用同一 Fins material admission 得到 plan 再进入 pipeline；"独立调用时创建一次 plan"改写为"独立调用方在事件和 company batch 前经同一 admission 创建一次 plan"。验证点：grep 全库无 `plan is None`/`getattr(plan` 形态；S2 测试断言 Service 路径与直调路径进入 `_build_pending_assets` 的 plan 对象同一（同一标识/字段逐项相等）。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### 03-未修复-中-case/Unicode 变体碰撞在目标平台会复现"转换后失败"，与 goal 成功信号语义冲突
- **位置**：plan「Owner、计划结果与调用链」段精确值判定 +「风险」段"case-insensitive 文件系统别名与跨平台 Unicode 规范化不得被假装已由 exact string 集合证明无冲突"
- **问题类型**：范围漂移（相对 goal 成功信号）/ 需用户裁决
- **当前写法**：冲突判定用"规范绝对路径的区分大小写精确值"和 exact 名集合；case/Unicode 声明为不假装已解决，靠"真实仓储最终验证仍保留"兜底。
- **反例/失败场景**：macOS/APFS（默认大小写不敏感，即本工作区平台）上 `dir1/Deck.txt` + `dir2/deck.txt`：basename exact 不同（不触发同名拒绝），派生名 exact 不同（不触发全局冲突），全部通过规划并完成两次 Docling 转换，随后在同一 document 目录写 blob 时别名到同一文件 → 完整性校验失败 → 回滚。NFC/NFD 规范化等价名同理。这正是 UM-F21/F22 类"转换付费后 unexpected_runtime"的复现路径。
- **为什么有问题**：goal 成功信号 1 承诺"规划后的真实 original/derived 名碰撞……在 Docling 启动前给出 typed usage"。在大小写不敏感文件系统上，大小写变体就是"真实名字碰撞"。plan 的 exact-string 域比存储实际命名空间窄，二者对"真实碰撞"的定义不一致；plan 虽诚实声明未解决，但把 O04 的消除目标局部降级为"最后防线兜底"，需要用户明确接受该边界，或在 planner 冲突键上引入 casefold/NFC 归一。
- **直接证据**：plan 原文；`ingestion_runtime.py:1219-1231` `_fins_upload_path_identity` 明示"不进行 case folding"；工作区平台为 darwin（`Platform: darwin`）。
- **影响**：同一失败模式对一类常见输入（大小写变体文件名）残留；验收口径争议。
- **建议改法和验证点**：二选一并回填 goal 确认：(a) 明确接受 exact-string 边界，把 case/Unicode 别名登记为 residual risk 并注明"转换后回滚可复现"，向用户复核；(b) planner 冲突键与 basename 键改用 NFC+casefold 归一后比较（保守多拒），并补大小写变体反例测试。无论哪种，S2 真实仓储测试补一个大小写变体场景记录实际行为。
- **修复风险（低/中/高）**：低（(b) 只改比较键）
- **严重程度（低/中/高/严重）**：中

### 04-未修复-低-S1/S2 切片边界与 filing identity 迁移归属矛盾

- **问题类型**：切片边界 / 测试缺口
- **当前写法**：S1 限于"仅 owner/格式/失败契约及其测试"；同时又要求 filing identity 算法迁移且"调用/测试改用新 owner，不留兼容别名"。

- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低

### 05-未修复-低-长度边界只覆盖 material 派生名，original 名未纳入
- **位置**：plan「Owner」段"对 material 派生名以 UTF-8 字节数 `<=255` 作保守、显式的可规划边界"
- **问题类型**：契约缺失（边界不闭合）
- **当前写法**：255 边界只约束派生名；original 名只做"原样可存的单路径组件"校验。
- **反例/失败场景**：源文件来自 NAME_MAX 更大的文件系统（网络盘等），original 名 260 字节：派生名 273 字节会被拒（覆盖到了），但若只上传一个派生名恰好不超限的组合不可想象（派生=original+13，original>242 必然派生超限）——真正缺口在：original 名 ≤255 但存储目标文件系统 NAME_MAX 更小（跨挂载 `--base`），plan 声明"最终发布仍由存储检查实际文件系统限制"，即 original 过长仍走"转换后 OSError"。
- **为什么有问题**：goal 要求"无法唯一规划的输入在转换前给 typed 可修正失败"；original 长度超界属于同一失败类，闭合判定应同时约束 original 与 derived 两个名字。
- **直接证据**：plan 原文；`_fs_storage_utils.py:71-84` 无长度校验；A5 实测 255。
- **影响**：小类输入残留转换后失败；边界主张"保守显式"不完全成立。
- **建议改法和验证点**：长度判定对"每个将要写入的 storage 名"（original 与 derived）统一应用；S1 测试补 original 超长反例。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低

### 06-未修复-低-真实 CLI 100 成功转换的完成门槛可能超出 goal 要求，资源受限时工作单元不可收口
- **位置**：plan「测试、真实证据与文档决定」段"若因资源不能做 100 个完整转换，owner 级 100/101 仍必须通过，但真实 CLI 的 100 成功证据标记未覆盖，不能报整体完成"
- **问题类型**：过度验收标准
- **当前写法**：100 个文件的真实 CLI 完整成功转换（requested=stored）成为整体完成的硬门槛。
- **反例/失败场景**：goal 成功信号 1 的措辞是"成功边界为 100 可进入正常处理"，goal 验证要求是"隔离真实 CLI 新证据核对成功/失败、转换是否启动"——"进入正常处理/转换是否启动"与"100 个完整转换落盘"不同。100 个真实 Docling 转换（每个一个子进程）耗时可观；若环境资源不足，按 plan 措辞工作单元永远不能报完成，而 goal 级证据（owner 100/101 + 真实 CLI 101 拒绝 + 真实 CLI 100 进入处理/转换启动 + 小样本完整成功对照）已可满足验收。
- **为什么有问题**：验收标准高于已确认 goal，制造不可收口风险；也与"不发明新阈值/不扩写 goal"的纪律取向不一致。
- **直接证据**：goal「目标与成功信号」1/3 原文 vs plan 该句原文。
- **影响**：closeout 被资源性门槛卡死；或为凑证据做与数量无关的重活。
- **建议改法和验证点**：把 100 侧真实 CLI 证据分级：必需=101 typed 拒绝（转换未启动、无发布）+ 100 侧进入正常处理且转换启动计数=100 + 至少一个小 N 完整成功对照（requested=stored）；100 完整成功转换列为"资源允许则做"的增强项。与用户确认分级口径后回填 plan。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低

### 07-未修复-低-100 上限同源化未指明常量 owner，且与 `_MAX_TUPLE_ITEMS` 的通用语义混淆
- **位置**：plan「Owner」段"`maxItems=100`、runtime 现有 `TOO_MANY_FILES` 和共享上限须从同一 Fins 常量读取，避免第三个数值真源"
- **问题类型**：语义所有权未判定（轻度）
- **当前写法**：要求三处读同一 Fins 常量，但未指明常量放哪个模块。
- **反例/失败场景**：`_MAX_TUPLE_ITEMS`（`ingestion_runtime.py:167`）同时约束 ticker_aliases（`:1180`）、metadata（`:7912`）、values（`:7530`）——是通用 tuple 上限而非"上传文件数上限"。若未来文件数与别名数分叉（合法演进），单一常量会错误绑定；若常量放进 planner 而 `ingestion_runtime` 反向导入，又是层级内不必要的耦合方向。tool schema `maxItems`（字面量，按编码约束 schema 允许字面量）改读常量时也需说明。
- **为什么有问题**：goal 要求"数量上限须由唯一 owner 定义"，plan 需指明该 owner 是谁、通用 tuple bound 与文件数 bound 是同一语义还是同值两语义。
- **直接证据**：`ingestion_runtime.py:167/1180/7530/7912`；`upload_tools.py:243`；goal「动机」段。
- **影响**：第三个数值真源仍可能出现（常量无主）；或错误耦合。
- **建议改法和验证点**：plan 指明文件数上限常量归 Fins 上传资产规划 owner（或 format contract），`TOO_MANY_FILES` 文案与 tool `maxItems` 由其派生；`_MAX_TUPLE_ITEMS` 保留为通用 tuple bound 并注释与文件上限当前同值、不承诺同步。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低
