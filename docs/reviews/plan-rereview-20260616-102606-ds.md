**验证结论**: ✅ **FIXED**。D0-C-D 的三段式 sequencing 消除了原来的循环依赖。D0 作为 contract-only gate 在 C 删除任何东西之前验证 observation source 可替代性，C 有显式 precondition 和 guard（不能删除 poll 真源直到 D0 替代确认），D 基于已验证的 contract 实现。

API 语义（lines 265-273）:
- 创建者：Fins runtime（tool helper 调用 start_observed_*，handle_id 写入 resume_token）
- 消费者：Fins wait adapter（从 resume token 解析 handle）
- Observation source：process-local registry，不 durable
- Terminal 映射表完整:
  - SUCCEEDED → ResolveWaitCompletedOutcome
  - FAILED → ResolveWaitFailedOutcome
  - CANCELLED → ResolveWaitCancelledOutcome

- Transient：TRANSIENT_UNAVAILABLE → 保持 pending 并重试
- Abandon：释放 process-local record，不删除 storage 产物
- Cancel：best-effort，operation-scoped token

Durability / Recovery 裁决（lines 193, 275-281, 406）:
- 默认：process-local lightweight handle，Host restart / runtime crash → LOST，不无限 pending
- Durable mini-design 触发条件明确列举（cross-process / cross-restart / 用户需要跨重启追踪）
- 若触发 durable，只允许最小 ledger 字段（handle_id, operation_kind, status, created_at, updated_at, terminal result, error, cleanup deadline），禁止恢复 job event sidecar

**验证结论**: ✅ **FIXED**。Lightweight observation handle 现在具备完整 typed contract、poll/cancel/abandon API、terminal/error 映射表、durability 裁决和 recovery 收口。Implementation agent 进入 Slice D0 时可以直接按 contract 生成代码，不需要自行设计。

## 新增潜在问题扫描

在逐区域验证之外，快速扫描 plan 修订版是否引入了新的 material issue：

1. **D0 的 contract-only 定位**: D0 被定义为"contract-only checkpoint"，允许文件包含 `dayu/fins/ingestion_runtime.py`（仅用于声明 protocol 或导入 contract）。这可能导致 implementation agent 在 D0 中提前做 Slice C 的 runtime 实现。但 D0 的 allowed files 说明（"仅用于声明 FinsObservationRuntime protocol 或导入 contract"）和 stop condition 已足够约束。**判定**: 非 material issue。

2. **FinsObservationRuntime protocol 的 sync/async 混合**: `start_observed_*` 方法是 sync（返回 handle），`poll_observation` / `cancel_observation` / `abandon_observation` 是 async。这是合理设计——start 只注册 observation 并返回 opaque handle，不需要 await；poll 可能需要检查 runtime 状态因此是 async。**判定**: 非 issue。

3. **exit code 130 的 Unix 约定**: CANCELLED → exit_code 130 对应 SIGINT 语义，是标准做法。**判定**: 非 issue。

4. **Slice A 和 C 仍共享 `dayu/fins/ingestion_runtime.py`**: 这是 DS-002 的残余风险，已在区域 3 中评估。通过 ownership 定义 + stop condition + precondition 已足够管理。**判定**: Residual risk，不阻塞。

## Open Questions

1. **D0 的 "contract-only" 是否会与 Slice C 的 runtime 实现产生协议不匹配？** D0 定义的 `FinsObservationRuntime` protocol 签名可能与现有 `FinsIngestionRuntime` 的实现约束冲突（例如 `start_observed_*` 的返回值类型）。这可以通过 D0 只做 contract module（不修改 `ingestion_runtime.py`）来规避。Plan 的 allowed files 设计（D0 可以修改 `ingestion_runtime.py` "仅用于声明 protocol 或导入 contract"）给了灵活性，但也给了误用空间。建议 implementation gate 在 D0 review 时重点检查是否只做了 contract 定义。

2. **Process-local registry 的并发安全性**: Plan 没有讨论 process-local observation registry 的线程安全性。Fins runtime 可能从不同线程访问 registry（tool helper 线程 vs wait adapter 线程 vs async stream consumer）。这不是 plan 级别的 blocker，但应该在 implementation gate 注意。
