### CR-01-未修复-高-新 oracle 被用于追溯判定 calibration target 为 fail

- **入口/函数**: 第 4.5 节 oracle 生效时点与第 13 节三维状态规则
- **文件(行号)**: `docs/cli_ci.md:322`、`docs/cli_ci.md:1123`
- **输入场景**: 第一轮观察当前实现 A，用户裁决预期 B，并把 B 作为从后续 run/版本生效的 accepted oracle。
- **实际分支**: 第 4.5 节规定 accepted oracle “从后续指定 run 开始参与正式 pass/fail”，但第 13 节允许当前产品违反
  “新 accepted oracle”时同时形成 `fail`。
- **预期行为**: 当前 calibration target 保留实际 observation，并形成 implementation finding；只有 oracle effective
  scope 覆盖当前 target 时才能产生正式 validation `fail`。
- **实际行为**: 同一 handbook 同时禁止和允许用未来生效的 oracle 追溯打分。
- **直接证据**: 第 322 行明确限定后续 run 生效；第 1123-1124 行没有 effective-scope 条件，直接允许 `fail`。
- **影响**: 历史 verdict 失去可解释性，first-round calibration 又退化成用事后标准给当前 run 判错。
- **建议改法和验证点**:
  - 第 13 节改为：新 oracle 对当前 observation 形成 implementation finding，不追溯改变 run verdict；
  - 只有 existing hard/current-design contract 或 effective oracle 覆盖 target 时才形成正式 `fail`；
  - 全文扫描 “新 accepted oracle + fail” 不再存在无 scope 条件的表述。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### CR-02-未修复-高-SQLite required observation 未收束 Fins 文档存取边界

- **入口/函数**: 第 11.2 节 SQLite checklist
- **文件(行号)**: `docs/cli_ci.md:1046-1069`，对照 `docs/cli_ci.md:751`
- **输入场景**: `download/upload/process` 的相关 SQLite rows 包含 Fins 文档内容、转换 payload 或私有 storage layout。
- **实际分支**: 第 11.2 节要求内嵌“schema/关键 rows”，只限制 CI-owned/read-only/bounded，没有禁止通过 SQLite
  直接读取 Fins document payload；第 10.1 节则要求被测 Agent/SUT 的所有财报文档读取必须经过
  `dayu.fins.storage`。
- **预期行为**: SQLite 只能观察 Host/存储 metadata、row identity/count/status/digest 等 bounded diagnostic；
  财报 document content、section/table/fact 必须通过 `dayu.fins.storage` 仓储协议/read tools 读取。
- **实际行为**: 执行 Agent 可以按“关键 rows”直接读取并展示 Fins 私有文档内容，绕过唯一仓储 owner。
- **直接证据**: 第 1046-1069 行没有 Fins payload exclusion；项目硬约束与第 751 行明确规定财报文档存取唯一边界。
- **影响**: 语义所有权漂移、private schema 被事实消费、敏感/大 payload 泄漏到人类报告。
- **建议改法和验证点**:
  - 在第 11.2 节明确禁止从 SQLite 读取/重建/展示 Fins document body、section/table/fact 或 provider payload；
  - Fins SQLite 只允许 metadata/status/count/digest 等诊断，业务内容通过仓储 public read evidence 展示；
  - 报告冲突时仍以仓储/public owner 为真源。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### CR-03-未修复-中-Retention 会删除首轮 calibration 仍需裁决的旧 raw evidence

- **入口/函数**: 第 2.8 节 Retention
- **文件(行号)**: `docs/cli_ci.md:219-223`
- **输入场景**: 第一轮 campaign 因新交互 branch 分成多个 run；新 run 成为最新 baseline，但用户仍需对旧 report 中的
  screen/cast/artifact/DB delta 做 oracle 裁决。
- **实际分支**: 完整 evidence 仅在“未关闭 finding”引用或最新 baseline 时保留；新 baseline 可删除旧 run 大
  evidence。未裁决/已接受 oracle 和 readiness proof 引用没有被列为 retention owner。
- **预期行为**: campaign 未完成时，所有被 unresolved adjudication、accepted oracle、scenario coverage claim 或
  readiness proof 引用的证据必须保留；完成后才能按可复核的 bounded retention policy 收缩。
- **实际行为**: 旧 report digest 仍存在，但其关键 raw refs 可能已被删除，用户无法完成或复核裁决。
- **直接证据**: 第 219-223 行的 retention 条件只提 active finding/latest baseline；新第 4.6 节要求 readiness proof
  引用 frozen report digests 和 sufficient evidence。
- **影响**: 第一轮无法审计、oracle authority 证据断链、补跑可能重复高成本外部操作。
- **建议改法和验证点**: 扩展 retention owner，覆盖 unresolved adjudication、accepted registry record、
  readiness proof；只有新 evidence 明确 supersede 且引用已迁移后才删除。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
