## Findings

### 1-已拒绝-中-await_or_cancel_or_timeout 超时路径存在 TOCTOU 竞态窗口

- **Gateflow decision**: `rejected-with-reason`
- **Gateflow reason**: `asyncio.wait(..., timeout=...)` 返回 timeout 分支后，timeout 已赢得当前 handshake race；target cleanup 阶段触发的 token 属于 late cancel，不能覆盖 timeout。否则会重引入已修复的 Engine bug：`ToolExecutor.execute` timeout 被清理阶段 cancel 改写成 `run_cancelled`。当前实现已在 timeout 分支取消 target 前 re-check `token.is_cancelled()`，用于吸收 cancel watcher 轮询延迟；不再在 target cleanup 后二次覆盖 timeout。
- **Fix status**: `not-fixed`
- **Re-review status**: `rejected decision reviewed: supported`
- **Traceability**:
  - Decision: `docs/reviews/gateflow-additional-review-decision-engine-cancel-20260512.md`
  - Re-review: `docs/reviews/gateflow-additional-re-review-engine-cancel-20260512.md`

- **入口/函数**: `await_or_cancel_or_timeout` (`dayu/runtime/cancellation.py:191`)
- **文件(行号)**: `dayu/runtime/cancellation.py:237-251`
- **输入场景**: token 在 `asyncio.wait` 超时返回后、`_cancel_task_and_wait(target_task)` 执行前被取消
- **实际分支**: `asyncio.wait` 返回后 `done` 为空集（timeout 命中），进入 line 247 的 `token.is_cancelled()` 检查
- **预期行为**: 若 token 在超时窗口内被取消，应返回 `WaitCancelled` 而非 `WaitTimedOut`
- **实际行为**: `cancel_watcher` 以 50ms 间隔轮询 token。若 token 在 `asyncio.wait` 超时返回后的微秒级窗口内被取消，`cancel_watcher` 尚未感知，line 247 的 re-check 可能仍未命中。返回 `WaitTimedOut` 而非 `WaitCancelled`
- **直接证据**: `dayu/runtime/cancellation.py:237-251` — `asyncio.wait` 使用 `FIRST_COMPLETED` + `timeout`；line 242 检查 `cancel_watcher in done`；line 247 re-check `token.is_cancelled()`；line 250 在 re-check 之后才调用 `_cancel_task_and_wait(target_task)`
- **影响**: 调用方收到 `WaitTimedOut` 而非 `WaitCancelled`。当前消费方 `_execute_one_tool` 对两者都产出 terminal（`RUN_FAILED` vs `RUN_CANCELLED`），语义不同但均为终态。窗口极窄（微秒级），实际触发概率极低
- **建议改法和验证点**: 在 `_cancel_task_and_wait(target_task)` 之后、return `WaitTimedOut` 之前，再做一次 `token.is_cancelled()` 检查；若命中则返回 `WaitCancelled`。或在 docstring 中明确说明此竞态窗口为已知行为。验证：补充一个测试，token 在 timeout 窗口内被并发取消，断言返回类型
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
