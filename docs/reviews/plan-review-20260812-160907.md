## 特别挑战项压测

### 挑战 1: canonical CancellationToken — direct/durable checker 能否完整且同源实现？

**压测**: 修订 plan §6.2 要求 `_RuntimeJobCancellationChecker` 和 `_DirectCancellationChecker` 都实现 `is_cancelled/cancel_reason/requested_at`。

- **Direct 路径**: `_DirectStreamCancellationState` 当前有 `_cancellation_requested: bool`（L1240-1266）。需扩展 `cancel_reason` 和 `requested_at` 字段。`claim_terminal` 当前用 `FinsResultStatus.CANCELLED if self._cancellation_requested else requested_status`——需迁移为 typed `FinsUploadTerminalDisposition`。
- **Durable 路径**: `_RuntimeJobCancellationChecker` 需从 job store record 读取 `cancellation_requested` 和 `CANCELLING/CANCELLED` status。`cancel_reason()` 可返回固定 `"job_cancel_requested"`；`requested_at()` 可从 record 的 `updated_at` 解析。数据来源明确且同源（同一 record snapshot）。
- **同源性**: direct 和 durable 的数据源不同（内存 lock vs job store），但这是正确的设计——它们服务于不同的 ingestion path。两者都实现同一 `CancellationToken` Protocol，converter 只依赖 Protocol 不依赖实现。

**结论**: ✅ 可实施。direct checker 需在 `_DirectStreamCancellationState` 中增加 `cancel_reason`/`requested_at` 字段；durable checker 从 job record 派生。两者都从各自唯一真源读取，不引入第二 flag。

### 挑战 2: child normal-return failure descriptor 与 runtime wrapper 是否可实施？

**压测**: child target 的三段 try/catch 必须发生在 `_run_process_target`（`interruptible_process.py` L621-641）的 `try: result_queue.put(_ProcessSucceeded(value=target()))` 调用内部。

- Child target `__call__` 内部: try construction → catch → 构造 failure descriptor dict → return dict（normal return）。runtime wrapper 的 `target()` 调用正常返回 → `_ProcessSucceeded(value=failure_descriptor_dict)` → 父进程 `InterruptibleProcessCompleted(value=failure_descriptor_dict)`。
- 父进程收到 `InterruptibleProcessCompleted` → 读取 `value` → 校验 descriptor schema → 按 `status` 和 `failure_kind` 映射。
- 如果 child target 内部**未** catch 的异常逃逸 → `_run_process_target` 的 `except Exception` catch → `_ProcessFailed(error_type, message)` → 父进程 `InterruptibleProcessFailed` → 无可信 descriptor → `CHILD_CRASH`。
- 这个设计与 runtime wrapper 完全兼容。child target 是唯一决定"正常 return"还是"异常逃逸"的 owner。

**结论**: ✅ 可实施。三段 try/catch 在 child target `__call__` 内部完成，descriptor 作为 normal return value。runtime wrapper 不需要修改。

### 挑战 3: sync facade async wiring

**压测**: `CnPipeline.upload_filing()` (L713-773) 当前是同步方法，调用 `_run_async_upload_sync(collect_cn_upload_result_from_events(self.upload_filing_stream(...)))`。

- `_run_async_upload_sync` 内部调用 `asyncio.run()`——在 producer thread 创建私有 event loop。
- `upload_filing_stream()` 是 async generator，当前内部同步调用 `self._upload_service.prepare_upload(...)`。

### 挑战 4: commit ownership transfer/helper — 是否引入错误 owner 或重复 rollback？

**压测**: 修订 plan §9.1 规则 1 定义 `commit_prepared_upload_batch` helper 为共享的 publication lifecycle owner。

- 当前 `_store_upload_assets` (L371-503) 内部逐文件 `store_file` 循环中有 cancel checkpoint（L440, L468, L485），返回 `cancelled` result。但它**不执行 rollback**——只是停止写入并返回 cancelled。
- 修订 plan 说 helper 对 precommit cancel/failure **恰好调用一次** `rollback_batch`，"service/workflow 不重复 rollback"（§9.1 规则 1）。
- 这意味着 `_store_upload_assets` 的 cancel 分支返回 cancelled result 后，由 `commit_prepared_upload_batch` helper 执行一次 rollback。workflow/service 不额外 rollback。
- 风险点：如果 `_store_upload_assets` 在 cancel 前已经 `store_file` 了部分文件（L445-462），这些文件在 batch 内，rollback 需要回滚这些 blob。当前 `BatchingRepositoryProtocol` 是否有 `rollback_batch` 方法？需确认。

**结论**: ✅ 可实施，但有一个实施注意点。helper 是唯一 rollback owner，不会重复。需确认 `BatchingRepositoryProtocol` 支持 `rollback_batch`（或等价 batch abort 语义）——plan 假定存在但未在生产代码中验证。这不构成 material finding，因为 plan 未承诺新增 storage 能力；若不存在，实现时需在 storage owner 边界补齐。

### 挑战 9: UF-PF09 sampler/5.05s 是否可执行？

**压测**:
- **macOS (Darwin)**: `/usr/bin/sample` 是系统自带工具，无需安装。用法: `sample <pid> 1 -file /tmp/stack.txt` 采集 1 秒样本。权限：需与目标进程同用户或 root——CLI 和 sampler 在同一用户下运行，应无权限问题。
- **Linux**: `py-spy dump --pid <pid>` 需安装 `py-spy`（`pip install py-spy`）。
- **5.05s 预算**: poll(0.05) + terminate(2.0) + kill(1.0) + 2.0s harness margin = 5.05s。
  - poll 0.05s: 一轮 `await asyncio.sleep(0.05)`——实际 ~50-100ms。
  - terminate 2.0s: `asyncio.to_thread(process.join, 2.0)`——实际 2.0-2.1s。
  - kill 1.0s: `asyncio.to_thread(process.join, 1.0)`——实际 1.0-1.1s。
  - margin 2.0s: 覆盖 `asyncio.to_thread` 调度延迟（通常 <10ms）、`/usr/bin/sample` 采样延迟（1s 采样窗口内）、进程树扫描、文件 I/O。**充足**。
- **可重复性**: 使用相同 HK PDF / US DOCX 输入，相同的 50ms ps 采样 + stack sampling protocol。`conversion-entered` 证据独立于 wall-clock——只要 stack 显示正确调用链即可。

**结论**: ✅ 可执行。`/usr/bin/sample` 在 macOS 上可用，5.05s margin 充足，protocol 可重复。
