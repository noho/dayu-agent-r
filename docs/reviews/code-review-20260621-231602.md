## Findings

### F01-未修复-中-request_id 缺失时 "missing" sentinel 值与真实 request_id 不可区分

- **入口/函数**: `handle_wait_callback_completion` → `_request_id_from_transport`
- **文件(行号)**: `dayu/service/wait_callback_endpoint.py:351-367`
- **输入场景**: callback 请求缺少 `X-Dayu-Callback-Request-Id` header 且 body 中无 `request_id` 字段
- **实际分支**: `_optional_string_from_transport` 在 header 和 body 均未找到时返回 `None`，触发 `if request_id is None: return "missing"`（第 366 行）
- **预期行为**: plan 将 `X-Dayu-Callback-Request-Id` 列为 route form header，`WaitCallbackCompletionEnvelope.request_id: str` 为非 optional。应提供可区分"缺失"与"字面值"的机制——要么像 `correlation_id` 一样声明为 `str | None`，要么在 request_id 缺失时返回 transport_rejected
- **实际行为**: 返回硬编码字符串 `"missing"`，与合法的 `request_id="missing"` 不可区分。多个缺失 request_id 的 callback 共享同一 sentinel，丢失 traceability
- **直接证据**: 第 366 行 `return "missing"`，无任何 namespace prefix（如 `"none:"` 或类似区分手段）。对比第 265 行 `correlation_id` 的处理：`correlation_id: str | None`，nullable 允许下游区分缺失与存在
- **影响**: 下游 audit/log/correlation 消费方无法区分"确实缺失 request_id"和"request_id 恰好等于 'missing' 字符串"。这是一个数据质量与可观测性合约歧义，不阻塞 callback 处理但降低排障效率
- **建议改法和验证点**: 两种方案：方案 A——将 `WaitCallbackCompletionEnvelope.request_id` 标注改为 `str | None`（需 Host contract 变更，与 `correlation_id` 一致）；方案 B——缺失 request_id 时返回 `transport_rejected`，因为 plan 将 request_id header 列为 route form 固定部分。方案 A 更温和且与现有 correlation_id 模式一致，但需回到 Slice 1 合约修改。当前阶段可接受，但应在 issue-90 或最终 Web route 部署前解决
- **修复风险（低）**: 方案 A 需 Host 合约微调；方案 B 需 Web route 部署前确认 caller 始终发送 request_id
- **严重程度（中）**:

### F02-未修复-低中-测试未覆盖 body 非对象、unknown outcome kind、非法时间戳与 fail-closed 路径

- **入口/函数**: 多个测试场景
- **文件(行号)**: `tests/service/test_wait_callback_endpoint.py`（缺失测试）
- **输入场景**: 以下可证明 fail-closed 行为的输入组合缺少直接测试
- **实际分支**: 各输入经由 `_json_object_or_none` → `None`、`WaitCallbackOutcomeKind(StrEnum)` 构造、`_required_utc_datetime` 等路径最终被 `handle_wait_callback_completion` 的 `except (TypeError, ValueError)` 捕获并返回 `malformed_payload`
- **预期行为**: 所有 fail-closed 路径应返回 400 `malformed_payload`，不调用 adapter
- **直接证据**:
  - `_json_object_or_none`（第 631-643 行）对非 Mapping 值（数组、字符串、数字、布尔、null）返回 `None`，随后 `_require_json_object` 抛出 `TypeError` → `malformed_payload`——代码行为正确，但无测试验证
  - `WaitCallbackOutcomeKind(_required_string(raw, "kind"))`（第 413 行）对未知 kind 抛出 `ValueError` → `malformed_payload`——代码行为正确，`test_supported_outcome_kinds_map_to_host_outcome_dataclasses` 只覆盖四个合法 kind
  - `_required_utc_datetime`（第 545-559 行）对非 UTC 时区或非法格式抛出 `ValueError` → `malformed_payload`——代码行为正确，无测试验证
  - `_tool_cancelled_reason`（第 532-542 行）对不在 `ALLOWED_TOOL_CANCELLED_REASONS` 的 reason_code 抛出 `ValueError` → `malformed_payload`——代码行为正确，无测试验证
  - `_transport_rejection_or_none`（第 223 行）method 不是 POST → `transport_rejected`（400）——代码行为正确，无测试验证
  - `request_id`/`correlation_id`/`auth_source`/`credential_ref` 从 body 字段读取（非 header）——`_optional_string_from_transport` header 优先逻辑正确，但 body 回退路径无测试验证
  - `RunSnapshot` 为 `None` 时 response body 不应包含 `run_id`/`run_status`——`_service_response` 第 775 行 `if run is not None` 逻辑正确，但所有测试 fixture 始终提供非 None RunSnapshot
- **影响**: 当前代码行为正确，但缺失测试意味着 future 重构可能意外改变 fail-closed 行为。这是测试覆盖缺口，不是实现缺陷
- **建议改法和验证点**: 补充测试用例覆盖：body 为非对象（数组、字符串、null）；unknown outcome kind（如 `"pending"`）；非法 ISO 时间戳与非 UTC 时区；不支持的 cancelled reason_code；method 为 GET/PUT/DELETE；各可选 transport 字段仅存在于 body 时的提取；RunSnapshot=None 时 response 不含 run_id/run_status
- **修复风险（低）**: 纯测试补充，不影响生产行为
- **严重程度（低中）**:

## Open Questions

1. `request_id="missing"` sentinel 与 `auth_source="missing"`、`credential_ref="missing"` 共享同一命名空间——如果 caller 恰好发送 `request_id="missing"`、`auth_source="missing"` 或 `credential_ref="missing"` 作为合法值，下游无法区分。`auth_source` 和 `credential_ref` 按 plan "缺失认证字段交给 adapter 分类" 是可接受的；但 `request_id` 的缺失处理在 plan 中未明确定义。是否需要统一这些 sentinel 的语义？（计划在 issue-90 或 Web route 部署前解决）

2. `_credential_ref_from_authorization`（第 305-322 行）对非 Bearer Authorization header 返回完整 stripped 值（含 auth scheme 前缀如 `Basic xxx`）。plan 只定义 `Authorization: Bearer <token>` 形态。非 Bearer 凭据交给 adapter 分类是否完全安全？当前 adapter 有 classify→AUTH_FAILED 兜底，风险可控。

## Residual Risk

- **未覆盖 fail-closed 测试路径**：见 F02，当前代码行为正确但缺乏测试保护，重构时可能意外改变行为
- **未测试 `run=None` 响应形态**：如果未来 adapter 对某些 status 返回 `run=None`，Service mapper 正确不包含 `run_id`/`run_status`，但该行为无测试守卫
- **未测试 header casing 极端情况**：`_headers_by_lower_name` 使用 `.lower()` 归一化，对 `Content-type`、`CONTENT-TYPE` 等变体处理正确，但无显式测试
- **未测试空字符串 content-type**：`_transport_rejection_or_none`（第 226 行）对 `content_type.strip() == ""` 返回 415，该分支行为正确但无显式测试
- **未测试 `authorization_claims` body 字段中 claim 元素非对象或字段缺失**：代码会在 `_require_json_object` 或被 forced string 校验时抛出，走 malformed_payload，行为正确但无测试
- **未测试 `payload_ref` 和 `provider_status_ref` 对象形态字段缺失/非法**：代码会在 `_required_string` / `_require_json_object` 时抛出，走 malformed_payload，行为正确但无测试
- **residual risk 归属**：F02 中的测试缺口和上述未覆盖路径应作为低优先级测试补充，可在 issue-90（生产 poller loop）或 Web route 部署前补齐，不阻塞 Slice 2 通过
