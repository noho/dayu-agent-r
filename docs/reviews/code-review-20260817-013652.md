### 1-未修复-中-rebase 用 skip 语义 flag 伪造 identical_skip_safe=True，造成 document_version 路径依赖
- **入口/函数**: `rebase_prepared_filing_create_overwrite()`（S2 create-overwrite changed 分支的 owner 内 fresh rebase）
- **文件(行号)**: `dayu/fins/pipelines/docling_upload_service.py:1254`（函数）、`:1293-1297`（`source_fingerprint = _UploadSourceFingerprint(value=candidate.source_fingerprint, identical_skip_safe=True)`）、对照 `:1689`（fingerprint builder 置 `identical_skip_safe = primary_descriptor not in companion_descriptors`）、`:1712-1737`（`_resolve_document_version` 在 flag 为 False 时无条件 `_increment_document_version`，`:1732`）
- **输入场景**: 多文件 filing 且 primary original 的 descriptor 与某个 companion 完全相等（两个不同路径下同 basename、同 hash、同 size 的文件），`identical_skip_safe=False`；raw explicit `create` + `overwrite=True`，initial `MISSING` → fresh `COMPLETE`（§7.4 rebase 格）。
- **实际分支**: rebase helper 不携带 candidate 的原始 flag，直接以 `identical_skip_safe=True` 重解版本（:1293-1297）；`_resolve_document_version` 走指纹相等分支（:1732 不命中）→ 同指纹保持 fresh `document_version`，异指纹递增。
- **预期行为**: 同一请求、同一最终树内容，无论 sequential 还是并发执行，durable `document_version` 应一致；或至少 rebase 与既有 prepare 版本规则显式同源。
- **实际行为**: 路径依赖分歧。顺序二次 create-overwrite：`prepare_upload` 用原始 `identical_skip_safe=False` 指纹 → `_resolve_document_version` 无条件递增（同内容也从 v1 → v2）。并发 loser 走 rebase：伪造 True → 同指纹保持 fresh v1。同一内容、同一请求序列，durable version 依执行时序为 v1 或 v2。
- **直接证据**: `_build_upload_source_fingerprint` 在 :1689 对 role 歧义文件置 False；:1732 `if not source_fingerprint.identical_skip_safe: return _increment_document_version(...)` 与指纹无关地递增；rebase 在 :1295 硬编码 True。三条路径在同一逻辑链（fingerprint → version）上产生两种规则。
- **影响**: durable `document_version` 出现执行时序依赖；下游按 version 推断内容变更时审计不一致。无数据丢失（方向为版本号分歧，非内容丢失）。同时 helper 在永不 skip 的 publish-only 路径制造一个名为 "skip safety" 的 flag，属语义 conflation。
- **建议改法和验证点**: 在 rebase 内改用显式指纹相等判定，去掉伪造 flag：`document_version = _resolve_document_version(normalized_fresh_meta, _UploadSourceFingerprint(value=candidate.source_fingerprint, identical_skip_safe=normalized_fresh_meta.get("source_fingerprint") != candidate.source_fingerprint))` 或等价地直接比较 `fresh_previous_meta["source_fingerprint"]` 与 `candidate.source_fingerprint` 后选择 keep/increment，并在 docstring 固定"同指纹保持 fresh version"规则。补一个 S1 测试：用两个同 basename 同 hash 文件构造 `identical_skip_safe=False` 的 candidate，断言 rebase 同指纹保持、异指纹递增，并把与 sequential prepare 的分歧写入 README/风险登记（或另立 work unit 统一 `_resolve_document_version` 语义——修改 prepare 行为超出 S1/S2 冻结范围）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
