# Plan Review: WU-CLI-INTERACTIVE-RESUME-01

- **Reviewed target**: `docs/reviews/wu-cli-interactive-resume-01-plan-codex-20260617.md`
- **Scope**: CLI `prompt` / `interactive` existing-session startup 语义对齐
- **Date**: 2026-06-17
- **Reviewer**: AgentMiMo (adversarial plan review)

## Assumptions Tested

1. Host public API 已提供 `read_outbox_terminal_items`、`get_session`、`watch_session_events`，startup reconnect 不需要新 API。
2. CLI cursor store 可作为 UI client state 独立于 Host truth 存在。
3. `read_outbox_terminal_items` 的 read（非 drain）语义可安全用于 startup backfill。
4. 现有 `_TerminalObservationState` / `_wait_for_terminal` 可被 startup helper 复用。
5. prompt 不做 startup backfill 是正确的语义边界。
6. interactive startup 只需观察 `active_run_id`，不需要处理 `queued_run_ids`。
7. `workspace/.dayu/cli/` 路径与现有 workspace state 布局一致。

## Findings

### 1-未修复-高-Outbox backfill 不过滤 run_id 但现有 helper 按 run_id 过滤，复用路径不自洽

- **位置**: Implementation Decisions §1, Slice A, Direct Evidence `_read_outbox_terminal`
- **问题类型**: 架构边界 / 不可直接实施
- **当前写法**: Plan 声明"复用现有 `_new_terminal_observation_state()`"并"新增私有 helper 将 `OutboxTerminalItem` 转为 `EntrypointRunTerminalResult`"。
- **反例/失败场景**: 现有 `_read_outbox_terminal` 的核心是 `_scan_outbox_terminal_items(items, run_id, state)`，它按 `item.run_id == run_id` 过滤单个目标 Run 的 terminal。但 startup backfill 需要读取 session 下**所有**离线 terminal items（多个 run），不限定 run_id。Plan 说"复用"但实际需要一个语义不同的 backfill 循环——不按 run_id 过滤、分页直到 CAUGHT_UP 或 LAGGED、返回 tuple 而非单个 result。
- **为什么有问题**: 实施 Agent 看到"复用 `_new_terminal_observation_state`"和"复用 outbox terminal mapping"会尝试在 `_read_outbox_terminal` 周围包装，但该函数的 CAUGHT_UP-without-match 抛异常行为对 startup backfill 是错误的（startup 不期望每个 session 都有匹配的 terminal）。实际需要写一个全新的 backfill helper，与现有 `_read_outbox_terminal` 共享底层 `_scan_outbox_terminal_items` 的去重逻辑但不共享 run_id 过滤和异常语义。
- **直接证据**: `entrypoint_runtime.py:1089` `_read_outbox_terminal` 按 run_id 过滤；`entrypoint_runtime.py:1152` `_scan_outbox_terminal_items` 只返回匹配 run_id 的 item；plan Slice A 写"复用 `_new_terminal_observation_state()`"但 startup 不按 run_id 过滤。
- **影响**: 实施 Agent 可能错误复用 `_read_outbox_terminal` 导致 startup backfill 只能读到第一个 terminal item 后抛异常（CAUGHT_UP without match），或需要重新设计 backfill 循环，增加实施不确定性。
- **建议改法和验证点**: 明确区分两类 outbox 操作——(a) session-scoped backfill: 不按 run_id 过滤、分页读取所有 terminal items、CAUGHT_UP 时正常结束（不抛异常）、返回 `tuple[EntrypointRunTerminalResult, ...]`；(b) run-scoped fallback: 现有 `_read_outbox_terminal` 保持不变。Plan 应明确 startup helper 使用 (a)，不复用 `_read_outbox_terminal`，只复用 `_scan_outbox_terminal_items` 的去重逻辑和 `_terminal_result_from_outbox_item` 的转换逻辑。
- **修复风险**: 低
- **严重程度**: 高

### 2-未修复-中-Queued-only session 的 startup 行为未定义

- **位置**: State Boundaries §Active Run Semantics, Residual Risks
- **问题类型**: 状态机漏洞
- **当前写法**: "如果 session snapshot 只有 `queued_run_ids` 且无 `active_run_id`，当前 plan 不直接等待 queued Run；这应作为 residual risk 记录。"
- **反例/失败场景**: 用户提交 prompt 后 Host 将 Run 放入 queue（可能因为有另一个 active Run 正在执行）。在 active Run 完成之前，用户退出 interactive 并重新 `interactive --label`。此时 session snapshot 有 `queued_run_ids` 但无 `active_run_id`（因为 promotion 还没发生）。Plan 直接进入 REPL 输入态，用户提交新 prompt，新 prompt 排在 queued Run 后面——但用户完全不知道有一个 queued Run 等待执行。更糟的是，如果 queued Run 随后被 promotion 为 active 并产出 terminal answer，这个 answer 会在用户不知情的情况下出现。
- **为什么有问题**: 设计文档 `design.md:1183` 要求 Service 进入 attach/reconnect 时先补 terminal 再接入 live watch。queued Run 是"已接受但未执行"的 Run，它最终会产出 terminal。如果 startup 不观察它，用户会在同一个 session 里看到"凭空出现"的 terminal answer。这违反了 interactive startup 的核心目标：恢复可见性。
- **直接证据**: `api.py:2174` `SessionSnapshot.active_run_id` + `queued_run_ids`；plan Residual Risks 承认"queued_run_ids 无 active_run_id 时是否应阻塞 interactive startup 未完全由当前证据证明"。
- **影响**: 用户在 interactive session 中看到意外的延迟 terminal answer，或新 prompt 被排在未知 queued Run 后面。
- **建议改法和验证点**: 至少在 plan 中明确 queued-only 的预期行为——(a) 如果 Host 保证 queued Run 会被自动 promotion，startup 可以等待一个短暂窗口（如 2-3 秒）看是否出现 active_run_id；(b) 如果等待后仍无 active_run_id，向用户展示 queued Run 存在的提示，然后进入 REPL；(c) 如果实施中发现 Host 行为不确定，触发 stop condition。关键是不能 silently ignore queued runs。
- **修复风险**: 中
- **严重程度**: 中

### 3-未修复-中-Live watcher 与 outbox backfill 之间的 terminal 漏投窗口未被方案覆盖

- **位置**: Startup Attach/Reconnect §步骤 2-5, Design `design.md:1825`
- **问题类型**: 并发恢复风险
- **当前写法**: Plan 步骤是：(1) 读 cursor, (2) read_outbox_terminal_items 补读, (3) 渲染, (4) 读 active_run_id, (5) 若有 active Run 打开 live watcher。
- **反例/失败场景**: 在步骤 (2) 完成 outbox 读取、步骤 (4) 读取 session snapshot 之间，Host 可能完成了一个 active Run 并写入 EventLog + Outbox。此时步骤 (5) 打开的 live watcher 不会收到这个已完成 terminal（因为它发生在 watch attach 之前），而 outbox 读取也不会包含它（因为读取已经完成）。这个 terminal 被漏投。
- **为什么有问题**: 设计文档 `design.md:1825` 明确要求"必须证明两步之间没有漏投 terminal 的窗口"。Plan 的顺序（先读 outbox、再读 snapshot、再开 watcher）在步骤 (2) 和 (5) 之间存在时间窗口。正确做法是：先开 watcher（开始缓存事件），再读 outbox，再从 watcher 缓存中消费已有的 terminal events。这样即使 terminal 发生在 outbox read 和 watcher attach 之间，watcher 也会捕获它。
- **直接证据**: `design.md:1825`："必须依靠 `terminal_event_id` / `event_sequence` / `run_id` 去重，并证明两步之间没有漏投 terminal 的窗口"；现有 `submit_entrypoint_turn_and_wait` 在 submit 前就 attach watcher（line 545），正是为了避免这个窗口。
- **影响**: 极端情况下 startup 可能漏投一个 terminal answer，用户进入 REPL 后不知道上一个 Run 已经完成。
- **建议改法和验证点**: 调整 startup 步骤顺序为：(1) 读 cursor, (2) attach live watcher 开始缓存事件, (3) read_outbox_terminal_items 补读, (4) 从 watcher 缓存中消费已有的 terminal events 并去重, (5) 读 active_run_id, (6) 若有 active Run 继续消费 watcher，否则进入 REPL。这与现有 submit helper 在 submit 前 attach watcher 的模式一致。
- **修复风险**: 低
- **严重程度**: 中

### 4-未修复-中-Cursor store 写入时机与 crash safety 的矛盾

- **位置**: Implementation Decisions §2, Slice B
- **问题类型**: 最佳实践偏离
- **当前写法**: "成功渲染 terminal 后再写 cursor；渲染前崩溃允许下次重复展示，优先不漏投。"
- **反例/失败场景**: 用户看到 terminal answer 后，CLI 在写 cursor 之前崩溃。下次启动时，同一个 terminal 会被重复展示。对 interactive 来说这是 startup backfill 阶段的重复展示——用户会看到已经看过的旧 answer。虽然 plan 说"优先不漏投"，但对 interactive startup 场景，重复展示旧 terminal 可能比不展示更困惑（特别是当 answer 很长时）。
- **为什么有问题**: 这不是 bug，而是一个 tradeoff 的不完整讨论。Plan 只说了"优先不漏投"但没有讨论 startup 场景下重复展示的用户体验影响。更重要的是，plan 没有讨论 `prompt` 的可选 cursor advancement（Slice D）是否会加剧这个问题——如果 prompt 也写 cursor，那么 prompt 的 cursor 写入失败会导致 interactive startup 重复展示 prompt 已经展示过的 terminal。
- **直接证据**: Plan Implementation Decisions §2："成功渲染 terminal 后再写 cursor；渲染前崩溃允许下次重复展示"；Slice D："可选：本次 prompt terminal 渲染后更新 cursor store"。
- **影响**: 用户在 interactive startup 时看到重复的旧 answer；如果 prompt 也写 cursor，两个入口的 cursor 写入时序可能不一致。
- **建议改法和验证点**: 明确 (a) startup backfill 重复展示是可接受的 UX——因为用户确实需要知道 session 的当前状态；(b) 在 startup backfill 渲染前检查 terminal 是否已经在本次 startup 中展示过（用内存 seen set 去重）；(c) Slice D 的 prompt cursor advancement 移出本 WU，因为它引入了 prompt 和 interactive 之间的 cursor 写入竞争。
- **修复风险**: 低
- **严重程度**: 中

### 5-未修复-低-Startup helper 的 bounded poll 语义未具体化

- **位置**: Implementation Decisions §1, Startup Attach/Reconnect §步骤 4
- **问题类型**: 不可直接实施
- **当前写法**: "projection `LAGGED` 且未追平，按 bounded poll 继续读取"。
- **反例/失败场景**: 现有 `_read_outbox_terminal` 对 LAGGED 的处理是 `return None`（让 `_wait_for_terminal` 的外层循环通过 sleep + get_run 重试）。但 startup helper 没有外层循环——它需要自己实现 LAGGED 的 poll 重试。Plan 没有指定 poll 上限、重试次数、超时时间或放弃条件。
- **为什么有问题**: 实施 Agent 需要自行决定 LAGGED 的 poll 策略。如果没有明确约束，可能实现为无限循环（风险：startup 永不完成），或实现为立即放弃（风险：漏投 terminal）。
- **直接证据**: `entrypoint_runtime.py:1089` `_read_outbox_terminal` 对 LAGGED 返回 None；plan 步骤 4 写"按 bounded poll 继续读取"但未定义 bounded。
- **影响**: 实施 Agent 可能实现不一致的 poll 策略，或在极端情况下 startup 阻塞过长。
- **建议改法和验证点**: 明确 LAGGED poll 策略参数——最大重试次数（如 3 次）、每次间隔（复用 `poll_interval_seconds`）、超时后行为（打印 warning 并继续进入 REPL，而非阻塞）。
- **修复风险**: 低
- **严重程度**: 低

### 6-未修复-低-Slice D prompt cursor advancement 语义不明确

- **位置**: Slice D
- **问题类型**: 范围漂移
- **当前写法**: "可选：本次 prompt terminal 渲染后更新 cursor store；不读取 cursor，不补读旧 terminal。" Stop condition: "如果 cursor advancement 被认为改变 prompt 语义，移出本 WU。"
- **反例/失败场景**: 如果 prompt 写入 cursor store，那么 interactive startup 后来读取 cursor 时会跳过 prompt 已展示的 terminal。这改变了一个隐含假设：cursor store 只被 interactive startup 写入。如果 prompt 也写入，cursor 的写入方从 1 个变成 2 个，增加了并发写入风险（虽然 filelock 保护了原子性，但语义上增加了复杂度）。
- **为什么有问题**: Plan 把这个决定留给了实施 Agent（"可选"），但这是一个需要 controller 裁决的产品决策。如果 prompt 不写 cursor，interactive startup 会重复展示 prompt 已展示的 terminal（但这是 startup 的正常行为）。如果 prompt 写 cursor，需要确保 prompt 和 interactive 的 cursor 写入不会互相干扰。
- **直接证据**: Plan Slice D 标记为"可选"和 stop condition；但 cursor store 的设计假设（"只被 interactive 写入"）没有被显式声明。
- **影响**: 实施 Agent 可能自行决定是否实现 prompt cursor advancement，导致与后续设计假设不一致。
- **建议改法和验证点**: 本 WU 明确不实现 prompt cursor advancement（移出 scope），cursor store 只由 interactive startup 和 interactive REPL 写入。这样 cursor 的写入方语义清晰：只有 interactive 路径维护 cursor state。
- **修复风险**: 低
- **严重程度**: 低

## Open Questions

1. **workspace root 解析**: Plan 写 `<workspace_root>/workspace/.dayu/cli/terminal_cursors.json`，但 CLI 的 workspace root 解析逻辑在哪里？现有 `workspace/.dayu/` 目录已存在（含 `batch_locks`、`fins_ingestion` 等），cursor store 路径需要与现有 workspace state 路径解析一致。实施前需确认 workspace root 的来源（`--base` 参数？环境变量？配置文件？）。
2. **OutboxTerminalItem 的 terminal_status 到 HostTerminalStatus 的映射**: Plan 说"convert `OutboxTerminalItem` to `EntrypointRunTerminalResult(source=OUTBOX_READ)`"。现有 `_terminal_result_from_outbox_item` 已有这个映射，但需要确认 `OutboxTerminalItem` 的 `item_state` 字段是否包含足够的 status 信息来区分 `SUCCEEDED` / `FAILED` / `CANCELLED` / `LOST`。

## Residual Risks

1. **多 CLI 客户端共享 cursor store**: 已在 plan 中记录。当前按本机 CLI client 共享 workspace state 处理，不做 per-client isolation。
2. **Queued-only session**: 已在 finding #2 中详细讨论。需要 controller 决定是否阻塞。
3. **Startup active Run 长时间 WAITING**: 已在 plan 中记录。用户可通过 cancel 语义退出。建议实施时添加用户可见的等待提示。
4. **Prompt cursor advancement**: 已在 finding #6 中建议移出 scope。

## Conclusion

**PASS-WITH-RISKS**

Plan 的核心设计方向正确：prompt 不做 startup backfill、interactive 在输入态前执行 attach/reconnect、cursor store 作为 UI client state、不修改 Host/Engine public API。方案不过度设计，实现边界清晰。

但有 3 个需要在实施前明确或修正的问题：

1. **(高)** Outbox backfill 的 session-scoped 语义与现有 run-scoped `_read_outbox_terminal` 不兼容，plan 需明确不复用该函数，而是写新的 session-scoped backfill helper。
2. **(中)** Live watcher 与 outbox read 的顺序需要调整——先开 watcher 再读 outbox，避免漏投窗口。
3. **(中)** Queued-only session 的 startup 行为需要至少一个明确的决策点，不能作为 silent gap 留给实施 Agent。

修复风险均为低-中，不阻塞整体方案方向，但需要在实施 slice 中具体化。
