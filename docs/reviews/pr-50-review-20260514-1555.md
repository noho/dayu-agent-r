### 1-[未修复]-[高]-`_followup_queue_semantic_digest` 未包含 `resolved_execution_target`，导致幂等冲突漏检

- **入口/函数**: `_SubmitFollowupQueueOperation.__call__` → `_followup_queue_semantic_digest`
- **文件(行号)**: `dayu/host/admission.py:1787-1805`
- **输入场景**: 调用方对同一 `client_request_id` 发送两次 submit_followup_queue 请求，但两次的 `resolved_execution_target` 不同（例如调用方修正了 target）
- **实际分支**: `_followup_queue_semantic_digest` 不包含 `resolved_execution_target`，两次请求算出相同 digest → 幂等层判定为重复请求 → 返回第一次请求创建的 Run（其 `execution_target` 是旧值）
- **预期行为**: digest 应包含 `resolved_execution_target`，使得不同 target 的请求产生不同 digest，触发 `SEMANTIC_CONFLICT` 错误，强迫调用方显式处理冲突
- **实际行为**: 第二次请求被静默当作幂等重放，调用方收到旧 target 的 Run 且无任何冲突提示
- **直接证据**:
  - `_followup_queue_semantic_digest` (line 1797-1804) 的 digest 输入仅包含 `operation`、`input_digest`、`behavior`、`caller_semantic_digest`、`call_context_digest`，不含 `resolved_execution_target`
  - `_start_run_semantic_digest` (line 1775-1784) 作为对照，包含了 `execution_target`
  - `resolved_execution_target` 在 line 1107 被持久化到 `CreateRunningRunInput.execution_target`，说明其对 Run 语义是决定性的
  - `_validate_followup_queue_input` (line 1369-1370) 对 `resolved_execution_target` 做了非空校验，确认该字段是必填关键参数
- **影响**: 调用方调整 resolved target 后重试，可能被路由到错误执行目标的 Run，且无法通过返回结果感知差异
- **建议改法和验证点**: 将 `admission_input.resolved_execution_target` 加入 `_followup_queue_semantic_digest` 的 digest JSON 输入。验证：两个相同 `client_request_id` 但不同 `resolved_execution_target` 的请求，确认第二次返回 `SEMANTIC_CONFLICT` 而非幂等重放
- **修复风险（低）**: 仅增加一个 digest 字段，不影响现有幂等记录
- **严重程度（高）**: 幂等语义冲突漏检，可能导致调用方在不知情的情况下使用错误执行目标

### 2-[未修复]-[中]-`_promote_after_release` 在 promotion 前调用 wakeup，若 wakeup 抛出则 queued Run 永久滞留在队列中

- **入口/函数**: `_promote_after_release` → `HostAdmissionService.cancel_run` / `HostAdmissionService.closeout_attempt_terminal`
- **文件(行号)**: `dayu/host/admission.py:1598-1609`
- **输入场景**: active slot 被 cancel_run (pre-dispatch) 或 closeout_attempt_terminal 释放后，wakeup port 实现抛出异常（例如消息队列不可达、网络错误）
- **实际分支**: `service.wakeup_port.wake_queue_promotion(session_id)` 抛出异常 → `service.promote_next_queued_run(session_id)` 不执行
- **预期行为**: wakeup 是 best-effort 通知，不应阻塞 promotion；promotion 应在 wakeup 之前执行，或 wakeup 失败被静默吞掉
- **实际行为**: cancel/closeout 事务已 commit（slot 已释放），但 promotion 未发生，queued Run 永久滞留在队列中；调用方看到 cancel/closeout 成功但不知道 queue 被阻塞
- **直接证据**:
  - `_promote_after_release` 在 `admission.py:1598-1609` 先调用 `wakeup_port.wake_queue_promotion(session_id)`
  - 然后才调用 `service.promote_next_queued_run(session_id)`
  - `cancel_run` 在 `admission.py:465-477` 检查 `released_active_slot` 后调用 `_promote_after_release`
  - `closeout_attempt_terminal` 在 `admission.py:501-503` 同样调用
  - 当前 `NoopAdmissionWakeupPort` (`admission.py:350-372`) 不会抛出，但如果上层替换为真实实现则暴露风险
  - **额外发现**: promotion 在独立事务中执行（closeout 事务已 commit），即使调换顺序，promotion 事务仍可独立失败（如 Session 被并发删除），形成部分成功状态。调用方看到异常但 closeout 已生效无法回滚
- **影响**: 在后续 phase 引入真实 wakeup 实现后，一个异常的 wakeup 即可导致 Session 下所有 queued Run 被永久阻塞，且外部无感知
- **建议改法和验证点**: 将 wakeup 调用移到 promotion 之后，并将 wakeup 包裹在 try-except 中静默吞掉异常。对于 promotion 独立事务失败的情况，可考虑在 promotion 失败时记录日志后返回 `promotion=None` 而非传播异常。验证：mock wakeup 抛出异常，确认 promotion 仍然执行
- **修复风险（低）**: 只改变两个函数调用的顺序或增加异常保护，不影响事务语义
- **严重程度（中）**: 当前默认 no-op 实现不会触发，但属于对未来扩展的防御性设计缺陷

### 3-[未修复]-[中]-`_handle_active_run` 的 ATTACH_ACTIVE 路径不记录 EventLog 事件，审计事实缺失

- **入口/函数**: `_StartRunOperation._handle_active_run`
- **文件(行号)**: `dayu/host/admission.py:648-669`
- **输入场景**: `start_run` 以 `ATTACH_ACTIVE` 策略命中已存在的 active Run
- **实际分支**: 直接写入幂等记录后返回既有 Run，不追加任何 EventLog 事件
- **预期行为**: EventLog 是 canonical fact 的完整记录，ATTACH_ACTIVE 操作应追加类似 `USER_INPUT_ATTACHED` 的事件，记录"该 client_request_id 被 attach 到哪个已有 Run"这一事实
- **实际行为**: ATTACH_ACTIVE 分支完全静默——调用方获知已 attach，但 EventLog 中无任何痕迹。对比 QUEUE 分支（追加 `USER_INPUT_ACCEPTED` + `RUN_ACCEPTED` + `RUN_QUEUED` 事件），ATTACH_ACTIVE 在 EventLog 中不可见
- **直接证据**:
  - `admission.py:648-669` — `_handle_active_run` 的 ATTACH_ACTIVE 分支仅调用 `self.idempotency_store.record_idempotent_result()` 和构造返回结果，无 `event_log_store.append_event` 调用
  - `admission.py:670-677` — QUEUE 分支委托给 `_create_queued_admission_result`，该函数内部追加了完整的事件链
- **影响**: 审计/重建/调试时丢失"该 client_request_id 被 attach 到哪个已有 Run"这一事实；EventLog 作为 canonical fact 的完整性受损
- **建议改法和验证点**: 在 ATTACH_ACTIVE 分支追加 `USER_INPUT_ATTACHED`（或类似语义的 canonical fact 事件），将关联的 `run_id`、`attempt_id` 和 `client_request_id` 记录到 EventLog。验证：确认 ATTACH_ACTIVE 路径在 EventLog 中产生可审计的事件记录
- **修复风险（低）**: 仅新增事件追加，不影响现有返回值和幂等语义
- **严重程度（中）**: EventLog 完整性缺口，影响审计和重建能力

### 5-[未修复]-[低]-`_CloseoutAttemptTerminalOperation` 缺少幂等保护，不可幂等重放

- **入口/函数**: `HostAdmissionService.closeout_attempt_terminal`
- **文件(行号)**: `dayu/host/admission.py:480-510, 1011-1050`
- **输入场景**: 调用方对同一个 (run_id, attempt_id) 重复调用 closeout_attempt_terminal（例如网络超时后重发）
- **实际分支**: 第一次调用：terminal closeout 成功，Run/Attempt 推进到终态。第二次调用：`_invalid_terminal_precondition` (`run_transition.py:1469-1474`) 检测到 Run 已非 RUNNING → 返回 INVALID_STATE → `_raise_for_terminal_transition_status` 抛出 HostApiError
- **预期行为**: 幂等重放应返回原始 closeout 结果，而非抛出 INVALID_STATE 错误
- **实际行为**: 重复调用抛出 INVALID_STATE 错误，调用方收到异常而非幂等重放
- **直接证据**:
  - `_CloseoutAttemptTerminalOperation` (line 1011-1017) 仅携带 `event_log_store`、`clock`、`id_factory`，未携带 `idempotency_store`
  - 对比 `_StartRunOperation` (line 566-577) 和 `_CancelRunOperation` (line 813-824)，均携带 `idempotency_store` 并在 `__call__` 中先做幂等读
  - 当前仅靠 durable 层 CAS 保护（`terminal_run_row` line 1521 `WHERE status IN (RUNNING, WAITING) AND current_attempt_id = ?`）确保重复调用不产生副作用，但调用方体验为错误而非重放
- **影响**: 低 — 这是 internal 操作（docstring 明确标注），CAS 保证重复调用不会产生副作用；但调用方需处理 INVALID_STATE 错误而非期待幂等重放
- **建议改法和验证点**: 若后续变为 public API，需增加 `idempotency_store` 依赖并在 Run/Attempt 状态检查前做幂等作用域读。当前状态下，建议在 docstring 中明确标注"本操作不提供幂等重放，重复调用返回 INVALID_STATE 错误"
- **修复风险（低）**: 仅文档补充
- **严重程度（低）**: 设计决策，非缺陷；CAS 层保证数据安全

### 6-[未修复]-[低]-`_require_event_sequence` 绕过 EventLogStore 抽象直接查询 event_log 表

- **入口/函数**: `_require_event_sequence`
- **文件(行号)**: `dayu/host/admission.py:1659-1662`
- **输入场景**: cancel_run queued 或 pre-dispatch 路径中，需要读取刚 append 的 CANCEL_REQUESTED event 的 event_sequence 以写入幂等记录
- **实际分支**: 函数直接执行 `SELECT event_sequence FROM {TABLE_EVENT_LOG} WHERE event_id = ?`，而非通过 `EventLogStore.read_event_by_id`
- **预期行为**: admission 模块通过 `EventLogStore` 接口读取 EventLog 数据，不直接依赖 `TABLE_EVENT_LOG` schema 常量
- **实际行为**: admission.py 同时 import 了 `EventLogStore`（用于 append）和 `TABLE_EVENT_LOG`（用于 query），对 EventLog 的访问路径不统一
- **直接证据**:
  - `admission.py:52` import `TABLE_EVENT_LOG`
  - `admission.py:1659-1662` 使用 `transaction.fetchone(f"SELECT event_sequence FROM {TABLE_EVENT_LOG}...")`
  - `admission.py:40-45` 也 import 了 `EventLogStore`，其 `read_event_by_id` 方法可直接返回 `EventLogRow.event_sequence`
- **影响**: 低 — 同属 Host 层内，schema 常量是 durable 模块的公共常量，不是实现细节；但如果 EventLog 表结构变更，admission 模块也被迫同步修改
- **建议改法和验证点**: 在 `EventLogStore` 上增加 `read_event_sequence` 方法，或直接使用 `EventLogStore.read_event_by_id(transaction, event_id).event_sequence`
- **修复风险（低）**: 仅重路由读取路径，行为等价
- **严重程度（低）**: 不影响正确性，属于 maintainability 改进
