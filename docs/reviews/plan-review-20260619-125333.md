# Plan Review: Compact Rejected Attempt Diagnostic Artifact

- **Review target**: `docs/reviews/wu-cm-compact-rejected-diagnostic-plan-20260619-124435.md`
- **Work unit**: Compact rejected attempt diagnostic artifact (Conversation Memory smoke/log diagnostics)
- **Review date**: 2026-06-19
- **Review posture**: adversarial plan review per planreview skill

## Reviewed Target and Scope

The plan proposes creating durable diagnostic artifacts for compact proposal attempts rejected before a proposal manifest exists, specifically when `material_pack -> compact input -> previous_compacted_view` parsing fails with `ValueError: previous reference continuity text is invalid`. The plan extends `CompactionAttemptRejected` with an optional `diagnostic_reference`, adds a recorder protocol + durable implementation, extends EventLog payload fields, and wires proactive/reactive callers. Changes are scoped to `compaction_operation.py`, `context_events.py`, `dispatch.py`, `engine_ingest.py`, and corresponding tests.

## Assumptions Tested

1. **A1**: `run_compaction_operation()` is transaction-free, and the diagnostic recorder can safely use its own independent transaction.
2. **A2**: Offending block detection can be done by mirroring parser checks without calling the private parser, and the two will stay in sync.
3. **A3**: Stable `failure_stage` values can be reliably determined from exception type/message alone in the generic proposal path.
4. **A4**: `payload_ref` using `compaction-diagnostic:<uuid>` format is sufficiently unique across recovery tiers and retries.
5. **A5**: The diagnostic artifact containing raw `previous_compacted_view` text—including user input, tool output, and reference continuity text—is safe in the artifact root, as it is DEBUG-only and not in EventLog or LLM-facing material.
6. **A6**: Best-effort recorder failure (catch, log, return None) is sufficient; orphan artifacts or dangling payload descriptors from partial writes are acceptable.
7. **A7**: Tests covering the material projection failure scenario are sufficient to validate the full wiring path.
8. **A8**: The recorder can be constructed alongside the existing `CompactorProposalManifestRecorder` using the same `LocalArtifactStore` + `PayloadStore` without additional transaction coordination.

## Findings

### F1-未修复-中-诊断 recorder 事务边界与 EventLog payload_ref 的一致性窗口

- **位置**: Slice 1 "Core Diagnostic Artifact Contract and Operation Recorder" / State-machine invariant / Implementation Decision 3
- **问题类型**: 状态机漏洞
- **当前写法**: "Diagnostic recorder failure is best-effort: catch, log a warning with structured context, and continue returning a rejected attempt without `diagnostic_reference`." 且 recorder 使用自有 transaction runner（"Use the same transaction runner style as `DurableCompactorProposalManifestRecorder`"）。
- **反例/失败场景**: recorder 在自己的 transaction 内写入了 artifact + `payload_descriptors` 并返回 `CompactionRejectedAttemptDiagnosticReference`（含 `payload_ref` 和 digest），随后 `run_compaction_operation()` 返回该 ref 给调用方。调用方（`dispatch.py` 或 `engine_ingest.py`）在**另一个** Host transaction 中调用 `_append_compaction_attempt_rejected_event()`，将 `diagnostic_artifact_ref` 写入 EventLog。如果第二个 transaction 失败（CAS miss、durable retry exhausted 等），EventLog 中不会有 `diagnostic_artifact_ref`，但 `payload_descriptors` 行和 artifact 文件已经持久化，成为无引用的孤儿数据。

  反向窗口同样存在：如果 `run_compaction_operation()` 先于 recorder transaction 被取消（cancellation check 在 line 479，在 recorder 调用之前），不会有孤儿数据。但如果 recorder 成功返回后、EventLog 写入前发生进程崩溃，ref 在内存中丢失，artifact 和 descriptor 成为孤儿。

- **为什么有问题**: 这与 `DurableCompactorProposalManifestRecorder` 的模式不同——proposal manifest recorder 在**同一 transaction** 内写入 manifest artifact/descriptor 和 `RUNNER_CALL_INPUT_ASSEMBLED` EventLog row（见 `compaction_operation.py:250-336`），因此 artifact 和 event 是原子的。但 diagnostic recorder 的 transaction 与 rejected attempt event 的 transaction 是分离的，因为 `run_compaction_operation()` 本身不在事务内运行。

- **直接证据**:
  - `compaction_operation.py:44` docstring 明确 "本模块只执行事务外 compaction proposal attempt 循环"。
  - `compaction_operation.py:250-336` manifest recorder 在 `_operation(transaction)` 闭包内同时写 artifact/descriptor 和 EventLog，实现原子性。
  - `dispatch.py:2296-2338` `_append_compaction_attempt_rejected_event()` 在 dispatch 自己的写事务中执行。
  - Plan line 179-180: "Recorder failure must not turn a rejected attempt into accepted compact, dispatch fallback, a different tier, or a different failure category." 但没有规定反向：rejected attempt event 写入失败不应导致已写入的 diagnostic artifact 产生错误追溯。

- **影响**: 孤儿 artifact/descriptor 占据磁盘空间，长期累积后可能混淆运维人员（看到 `payload_descriptors` 行但没有对应的 EventLog 引用）。在极端的 durable retry exhausted 场景下，可能产生难以清理的垃圾数据。不过由于是 DEBUG-only 且不影响正确性，严重程度为中。

- **建议改法和验证点**:
  1. 在 plan 中显式声明孤儿 diagnostic artifact 是可接受的运维成本，并说明清理策略（例如 artifact TTL 或依靠 artifact root 的定期清理）。
  2. 或者在 `_append_compaction_attempt_rejected_event()` 调用前，先做一次 dry-run 验证（读回刚写入的 descriptor），降低 ref dangling 风险。
  3. 测试应覆盖：recorder 写成功 + EventLog 写失败的场景，验证系统不会崩溃或产生错误诊断。

- **修复风险（低）**: 只需补充 plan 文本说明或加一条日志。
- **严重程度（中）**: 不影响正确性，但长期运维可能积累垃圾数据。

### F2-未修复-中-offending block 检测逻辑与 parser 的隐式耦合

- **位置**: Implementation Decision 4 "Offending block detection"
- **问题类型**: 过度耦合
- **当前写法**: "Keep this helper diagnostic-only; do not change parser behavior. If the implementation mirrors parser checks instead of calling the private parser, its docstring must state which parser contract it mirrors and tests must cover the current error message."
- **反例/失败场景**: 假设后续 work unit 修复了 `_parse_previous_reference_continuity_text()` 的 root cause，例如改变 `REFERENCE_CONTINUITY` 文本协议格式或放宽解析规则。此时 diagnostic helper 中 mirror 的检测逻辑不会同步更新（因为它被标记为 diagnostic-only 且明确不应修改 parser），导致：
  1. 新格式的 block 不再触发 `ValueError`，但 diagnostic helper 仍然可能标记它为 offending。
  2. 或者新错误消息不再匹配，offending block 检测返回 `null`，失去了诊断价值。
- **为什么有问题**: 这违反了 "单一真源" 原则。parse contract 的真源是 `_parse_previous_reference_continuity_text()` 的实现，但 diagnostic helper 维护了一份独立的副本。两份逻辑在没有强制同步机制的情况下必然漂移。Plan 自己也承认了这个风险（要求 docstring 说明 mirror 的 parser contract），但没有给出漂移检测或防御措施。
- **直接证据**:
  - `compact_material.py:155` 路径中 `_parse_previous_reference_continuity_text()` 是私有函数，parser contract 由其实现隐式定义。
  - Plan line 201: "If the implementation mirrors parser checks instead of calling the private parser..."
  - `docs/host/conversation-memory-smoke-compact-followup.md:182-184`: "查 `_parse_previous_reference_continuity_text` 依赖的文本协议... 该文本协议是否可能被 business text 中的 `; `、换行、prefix 碰撞或旧 block shape 破坏。" —— 说明文本协议本身可能就是 bug 的根源。
- **影响**: 后续 parser 修复后，diagnostic helper 可能产生误导性的 offending block 标记，使运维人员追错方向。
- **建议改法和验证点**:
  1. 不 mirror parser 逻辑，而是直接调用 `_parse_previous_reference_continuity_text()` 来确认哪个 block 会失败。将私有函数临时暴露为 package-private（加 `_` 前缀但允许同包调用）比复制逻辑更安全。
  2. 或者：不在 diagnostic helper 中做精确的 offending block 检测，而是记录所有 `REFERENCE_CONTINUITY` block 的 locator summaries，让运维人员人工判断。
  3. 测试应包含：修改 parser 行为后，验证 diagnostic helper 的检测结果仍然与 parser 的实际错误一致。
- **修复风险（低/中）**: 暴露私有函数为 package-private 需要微调 import，但风险可控。
- **严重程度（中）**: 不影响当前正确性，但制造了未来必然漂移的技术债务。

### F3-未修复-中-`failure_stage` 判定逻辑欠规格

- **位置**: Contract / Schema / State-Machine Changes "Stable `failure_stage` values" / Implementation Decision 4
- **问题类型**: 契约缺失
- **当前写法**: Plan 定义了三个 `failure_stage` 值（`material_pack_to_compact_input`、`previous_compacted_view_parse`、`proposal_execution`），并说明 "material_pack_to_compact_input: compact material pack could not be projected into compact input before a proposal manifest existed" 和 "previous_compacted_view_parse: offending material is localized to previous compacted view parsing"。但**没有指定如何从异常中判定 failure_stage**。
- **反例/失败场景**: `_prepare_compactor_proposal()` 的 generic 路径（line 777-784）直接调用 `conversation_compact_input_vnext_from_material_pack(request.material_pack)`。如果该函数因非 `previous_compacted_view` 原因失败——例如 `trace_material` 处理抛异常、`evidence_material` 构造失败、或 `current_input_anchor` 构造失败——异常消息不包含 "previous reference continuity text is invalid"，此时：
  1. `failure_stage` 应该设为 `material_pack_to_compact_input`，但实现者如何判断？仅靠 `isinstance(exc, ValueError)` 不够。
  2. `offending_block` 检测逻辑假设异常是 REFERENCE_CONTINUITY 解析失败，对其它失败类型返回 `null`，但没有明确规定 generic 投影失败时的行为。
- **为什么有问题**: `failure_stage` 是 EventLog payload 中的诊断字段，如果它的值不稳定（同一种错误在不同 run 中可能产生不同的 stage 值），后续基于 stage 的聚合查询和告警将不可靠。
- **直接证据**:
  - `compact_material.py:598-621` `conversation_compact_input_vnext_from_material_pack()` 调用 `_previous_compacted_view_vnext()`、`_trace_material_vnext()`、`_evidence_material_vnext()`、`_answer_material_vnext()` 等多个子函数，任何一个都可能抛异常。
  - Plan line 111-114 只定义了三个 stage 值，但 line 201 的 offending block 检测只针对 `ValueError("previous reference continuity text is invalid")` 一种情况。
- **影响**: 实施 Agent 需要自行设计 failure_stage 判定逻辑，可能产生不一致的结果。
- **建议改法和验证点**:
  1. 在 plan 中明确 failure_stage 判定算法：基于异常类型 + 异常消息的模式匹配，还是基于异常传播路径上的 sentinel。
  2. 增加 `failure_stage` 的 fallback 值如 `material_projection_unknown`，覆盖无法精确定位的失败。
  3. 测试应覆盖至少两种不同的 projection 失败路径，验证 stage 判定一致。
- **修复风险（低）**: 只需补充 plan 的判定规则说明。
- **严重程度（中）**: 不影响功能正确性，但影响诊断可用性。

### F4-未修复-低-diagnostic artifact 中 raw text 的数据敏感性未处理

- **位置**: Artifact JSON schema v1 `previous_compacted_view` / `offending_block.raw_text` / Implementation Decision 3
- **问题类型**: 契约缺失
- **当前写法**: Artifact JSON 包含 `previous_compacted_view`（含 raw `text`）和 `offending_block.raw_text`。Plan 只在 non-goals 中说明不将 raw block text 写入 EventLog payload 或 LLM-facing material，但没有说明 diagnostic artifact 本身的数据保护策略。
- **反例/失败场景**: `previous_compacted_view` 中的 compact material block 可能包含用户输入文本、工具查询参数、工具返回数据。如果 artifact root 被备份、被运维工具扫描、或在 debug 时被粘贴到 issue tracker，敏感数据可能泄漏。
- **为什么有问题**: DEBUG artifact 虽然不是 EventLog canonical payload，但它仍然是持久化到磁盘的 durable 数据。项目已有 `redact_sensitive_diagnostic_values()` 工具（`compaction_operation.py:1421`），但对 artifact JSON 中的 raw block text 没有应用任何 redaction。
- **直接证据**:
  - `compaction_operation.py:52-55` import `redact_sensitive_diagnostic_values` 和 `truncate_diagnostic_text`，说明项目已有脱敏基础设施。
  - Plan line 33: "EventLog canonical payload contains only small structured refs... it never contains raw block text." 但 artifact JSON 可以包含完整 raw text。
  - Artifact schema (line 154-173) 中 `previous_compacted_view` 包含 `raw text` 和 `offending_block.raw_text`。
- **影响**: 用户数据可能通过 DEBUG artifact 间接泄漏。虽然风险较低（需要访问 artifact root 文件系统），但在安全审计场景中是合规问题。
- **建议改法和验证点**:
  1. 在 plan 中声明 diagnostic artifact 的访问控制策略：仅本地文件系统访问、不进入备份、不在 issue tracker 中粘贴。
  2. 或者对 `offending_block.raw_text` 应用与 EventLog 相同的脱敏规则（`redact_sensitive_diagnostic_values`）。
  3. 如果选择保留 raw text，必须在 artifact 文件名或 metadata 中标记 `confidential`。
- **修复风险（低）**: 可以只补充文档说明，也可以对 raw text 做脱敏。
- **严重程度（低）**: 需要文件系统访问才能利用，但合规场景下可能被标记。

### F5-未修复-低-`payload_ref` 格式在 recovery tier 上下文中的信息丢失

- **位置**: Artifact descriptor contract "Payload descriptor `payload_ref`"
- **问题类型**: 契约缺失
- **当前写法**: `payload_ref` 格式为 `compaction-diagnostic:<event-compaction-rejected-diagnostic-uuid>`。Plan 说明 "Do not use only `<operation-id>:<attempt-number>` because proactive recovery tiers can reuse operation id and attempt number." 但 descriptor metadata 中仍然包含 `compaction_operation_id` 和 `compaction_attempt_number`（line 123-124）。
- **反例/失败场景**: Proactive recovery tier 1-3 都使用同一个 `operation_id`。如果 tier 1 的 attempt 1 和 tier 2 的 attempt 1 都产生了 diagnostic artifact，两个 artifact 的 descriptor metadata 中 `compaction_attempt_number` 都是 1，但来自不同的 recovery tier。如果不查看 artifact JSON 内的完整上下文（`session_id`, `failure_stage`），仅通过 descriptor metadata 无法区分它们。
- **为什么有问题**: Descriptor metadata 是本应提供快速索引的字段。如果 `compaction_attempt_number` 在不同 recovery tier 之间不唯一，按 operation_id + attempt_number 查询会返回多条记录，降低诊断效率。
- **直接证据**:
  - `dispatch.py:1342-1372` recovery loop 对 tier 1-3 分别调用 `run_compaction_operation()`，传入相同 `operation_id`，但 attempt 编号独立从 1 开始。
  - Plan line 118: "Do not use only `<operation-id>:<attempt-number>` because proactive recovery tiers can reuse operation id and attempt number." 但 line 123-124 descriptor metadata 仍然保留这两个字段。
- **影响**: 运维人员按 descriptor metadata 查询时需要额外区分 recovery tier，增加排查复杂度。
- **建议改法和验证点**:
  1. 在 descriptor metadata 中增加 `recovery_tier: int | None` 字段，明确标识产生该 diagnostic 的 recovery tier。
  2. 或者在 artifact JSON 的顶层增加 `recovery_tier` 字段（已在 plan 的 artifact schema 中有 `failure_stage` 和 `failure_category` 可部分区分）。
- **修复风险（低）**: 在 descriptor metadata 加一个 optional 字段。
- **严重程度（低）**: 不影响正确性，仅影响诊断效率。

### F6-未修复-低-测试覆盖不足：缺少 recorder 失败和 reactive 路径的验证

- **位置**: Implementation Slices / Slice 1 Tests / Slice 2 Tests
- **问题类型**: 测试缺口
- **当前写法**: Slice 1 测试覆盖 material projection 失败场景（含 artifact readback、EventLog payload redaction）、validator 负面测试。Slice 2 测试 "one focused integration-style test if existing unit tests do not prove EventLog payload wiring."
- **反例/失败场景**:
  1. Recorder 写入失败（例如磁盘满、artifact root 权限不足）→ 应返回 `None` 且不阻断 rejected attempt 的正常流程。Plan 有状态机约束（line 179），但没有对应的测试。
  2. Reactive 路径（`engine_ingest.py:2064-2122`）的 `_append_reactive_compaction_attempt_rejected_event()` 也需要传递 diagnostic 字段，但 Slice 2 测试描述偏向 proactive 路径。
  3. `offending_block=null` 场景（无法识别具体 offending block 时）→ 应仍然写入 artifact 并包含所有 block locator summaries。
- **为什么有问题**: Plan 的 stop condition 是 "若 artifact 无法写入...停止并报告"，但如果测试不覆盖写入失败路径，实施 Agent 可能仅实现 happy path，导致首次磁盘满时才发现未处理的边缘情况。
- **直接证据**:
  - Plan line 251-257 Slice 1 测试列表未包含 recorder failure test。
  - Plan line 282-285 Slice 2 测试偏向单元级 payload builder 测试，未明确覆盖 reactive wiring。
- **影响**: 实施 Agent 可能遗漏 best-effort failure 路径的实现或测试。
- **建议改法和验证点**:
  1. 增加测试：mock `LocalArtifactStore.write_artifact_bytes()` 抛异常，验证 `run_compaction_operation()` 仍然返回有效的 `CompactionAttemptRejected`（`diagnostic_reference=None`），不抛异常。
  2. 增加测试：offending block detection 全量返回 `null` 时 artifact JSON 仍包含 `all_previous_compacted_view_blocks`。
  3. Slice 2 如果无法方便地做 reactive 集成测试，应在 closeout 中显式说明 residual risk。
- **修复风险（低）**: 增加测试用例。
- **严重程度（低）**: 可以通过补充测试覆盖来降低。

## Open Questions

1. **OQ1**: Plan 提到 `_log_rejected_attempt()` 需要输出 diagnostic reference 的字段，但该函数当前只接收 `CompactionAttemptRejected`。Plan 是否应显式说明日志字段从 `rejected.diagnostic_reference` 展开，而不是修改 `CompactionAttemptRejected` 的顶层结构？当前 plan text（line 210）已说明 "do not flatten the diagnostic reference into many top-level dataclass fields"，此点需要实施时确保。

2. **OQ2**: `exception_message` 字段（EventLog payload line 92）使用 "existing safe exception redaction/truncation helper"。当前 `_safe_exception_message()` 的 max chars 是 240。对于 `ValueError("previous reference continuity text is invalid")` 这种短消息，240 足够。但未来如果 parser 抛出包含详细上下文的异常（例如包含 offending line 内容），240 chars 可能截断关键信息。是否需要为 diagnostic artifact 的 `exception_message` 提供更宽松的长度限制？

3. **OQ3**: Reactive 路径（`engine_ingest.py:1646-1847`）中 `_execute_reactive_compaction()` 也调用 `run_compaction_operation()`，且也构造 `DurableCompactorProposalManifestRecorder`。Plan Slice 2 说在 `engine_ingest.py` 中 "construct the same recorder for reactive compaction"，但没有说明 reactive path 的 `context_compactor` 和 `compact_artifact_root` 是否可能为 `None`（见 `engine_ingest.py:1656-1666` 的 guard）。如果 reactive compactor 或 artifact root 为 `None`，diagnostic recorder 的构造是否也应被跳过？此场景是否需要在 plan 中覆盖？

## Residual Risks and Suggested Tracking

1. **RR1 — Parser root cause remains unresolved**: 已由 plan 明确归属到后续 work unit。这个 risk 已知且合理。

2. **RR2 — Offending block detection drift**: 见 F2。建议在后续 parser fix work unit 中包含同步更新 diagnostic helper 的 checklist 项。

3. **RR3 — Orphan diagnostic artifacts**: 见 F1。建议在运维文档或 README 中说明 artifact root 下可能存在少量无引用的 diagnostic artifact，可定期清理。

4. **RR4 — long25 不会因本 work unit 而通过**: Plan 已明确此点。实际效果需在 implementation 后通过 `--suite memory-compact --pressure-mode auto --long-rounds 25` 验证 diagnostic artifact 是否确实提供了足够的故障定位信息。

## Final Plan Review Conclusion

**`pass-with-risks`**

Plan 的 scope 控制得当（严格限定为 observability-only，不改变 parser/accept/reject/fallback 行为），架构模式复用现有 `DurableCompactorProposalManifestRecorder` 的 `LocalArtifactStore` + `PayloadStore` 路径，EventLog redaction 约束清晰。

存在三个中等问题需要关注：
- **F1**（事务边界与 orphan artifact）是架构层面的技术债务，但不影响正确性。
- **F2**（offending block 检测与 parser 耦合）是未来必然漂移的隐式依赖，建议改为直接调用 parser 而非 mirror 逻辑。
- **F3**（failure_stage 判定欠规格）可能让实施 Agent 做出不一致的 stage 分类。

三个低严重度问题（F4 数据敏感性、F5 payload_ref 上下文、F6 测试覆盖）可以在实施中自然收敛。

没有发现应阻止 plan 进入 implementation gate 的 blocker 级问题。建议实施前解决或显式接受 F2 和 F3，并将 F1 的孤儿数据策略写入 plan 或 closeout。
