## Findings

### DS-001-未修复-低-`_terminal_result_for_event` 在 terminal event 与 job record 状态不一致时抛出语义不匹配的 `FinsDirectUsageError`

- **入口/函数**: `FinsDirectCommandService.stream_job_events_until_terminal` → `_terminal_result_for_event` → `_terminal_result`
- **文件(行号)**: `dayu/service/fins_direct.py:579-592`（`_terminal_result_for_event`），`dayu/service/fins_direct.py:657-664`（`_terminal_result` else 分支）
- **输入场景**: `read_job_events` 返回一个 terminal event type（如 `JOB_SUCCEEDED`），但随后 `read_job(event.job_id)` 返回的 job record status 并非终态。这是 Fins runtime 的数据一致性问题（设计保证 terminal job record 保存先于 terminal event append），理论上"不应发生"但无防御。
- **实际分支**: `_is_terminal_event_type(event.event_type)` 为 `True` → `_terminal_result(self._runtime.read_job(event.job_id))` → `record.status` 不是 `SUCCEEDED/FAILED/CANCELLED` → 进入 `else` 分支 → `raise FinsDirectUsageError(f"job is not terminal: {record.status.value}")`
- **预期行为**: 异常应该表达"runtime 数据不一致"而非"调用方参数错误"。`FinsDirectUsageError` 的类 docstring 是"Fins direct Service 参数错误"，这会误导调用方排查方向。
- **实际行为**: 抛出 `FinsDirectUsageError("job is not terminal: running")` 或类似消息，调用方可能误以为是自己使用方式错误。
- **直接证据**: `dayu/service/fins_direct.py:664` — `raise FinsDirectUsageError(f"job is not terminal: {record.status.value}")`；`dayu/service/fins_direct.py:59-60` — `FinsDirectUsageError` docstring "Fins direct Service 参数错误"。
- **影响**: 误导调用方的错误排查方向。调用方若针对 `FinsDirectUsageError` 做参数修正重试，会陷入无效循环。
- **建议改法和验证点**:
  1. 在 `_terminal_result_for_event` 中 catch `FinsDirectUsageError` 并重新抛出为更明确的内部错误（如 `RuntimeError`），或在 docstring 中显式说明此异常可能由 runtime 数据不一致触发。
  2. 验证点：构造 fake runtime 使其 `read_job_events` 返回 terminal event 但 `read_job` 返回非终态 record，断言异常类型不是 `FinsDirectUsageError` 或至少包含明确的"数据不一致"语义。
- **修复风险（低）**: 只改异常类型或增加一层 catch-wrap，不影响正常路径行为。
- **严重程度（低）**: 设计保证此分支在正常操作下不可达；即使触发，异常仍会传播给调用方，不会静默吞错。

## Open Questions

1. **Synthetic terminal event sequence 碰撞风险**: 在极端 race condition 下（empty `read_job_events` 后、`read_job` 前，后台线程恰好写入新的 progress event 和 terminal job record），synthetic terminal event 的 `sequence = cursor + 1` 可能与 sidecar 中实际已存在的 progress event 共享同一 sequence 号。但由于 (a) sequence 只是读取游标而非业务事实（plan 明确"它只是读取游标，不是业务事实"），(b) synthetic event 从不写回 sidecar，且 (c) consumer 在收到 synthetic terminal 后即停止，此碰撞不产生状态不一致。若未来需要在 `after_sequence` 恢复消费或做 event replay，需重新评估此风险。

2. **`_terminal_result_for_event` 每 terminal event 调用 `read_job`**: 当前设计在遇到 terminal event 时额外调用 `read_job` 获取 `result_summary`/`failure_summary`。这是必要的（event record 的 `payload` 只有 bounded 摘要），但增加了一次 I/O。plan 已认可此设计，且由于 terminal event 是 job 的最后一个 event，额外 I/O 只在 job 结束时发生一次，不构成性能问题。

## Residual Risk

- **Synthetic terminal event 只防 Service/UI 悬挂，不修正 sidecar**: `stream_job_events_until_terminal` 的 terminal fallback 通过 WARN + 合成事件防止 consumer 无限等待，但不会把缺失的 terminal event 写回 sidecar。这符合 plan 要求（"terminal event 缺失时的合成事件不会写回 sidecar；它只防止 Service/UI 消费方悬挂，job record 仍是终态真源"）。风险是：若 sidecar 系统性问题导致 terminal event 经常缺失，WARN 日志可能淹没问题根因。当前实现通过 bounded WARN（只含 job_id、status、固定 reason 字符串，不含 payload）降低此风险。

- **测试未覆盖 `after_sequence` 负数校验与 terminal event 后 `read_job` 失败路径**: 见 DS-002、DS-003。两项均为低严重度测试缺口，不阻塞 merge。

- **S3 依赖 S1/S2 的 event sidecar 产生能力**: S3 只消费 S1/S2 已产生的 event sidecar。若 S1/S2 的 event 产生粒度不够（如缺少 per-document preprocess progress），S3 的 stream 接口本身不受影响（它只是读取和投影已存在的事件），但 consumer 可见的进度细度受限于上游事件粒度。此风险由 plan R1 跟踪，owner 为后续 Fins pipeline live-event refinement work unit。

- **`wait_for_terminal` 与 `stream_job_events_until_terminal` 可并行调用但无互斥保护**: 两个方法都读取 `read_job`，但 `wait_for_terminal` 的 `read_job` 与 `stream_job_events_until_terminal` 的 `read_job`（在 terminal event 或 fallback 路径中）没有互斥。若同一 `FinsDirectCommandService` 实例上同时调用两个方法，可能产生混淆的终端输出。然而，当前 CLI 只使用其中一个路径（S4 实现后将只使用 stream 路径），且 plan 未要求两者互斥。此风险为理论风险，不阻塞 S3 merge。
