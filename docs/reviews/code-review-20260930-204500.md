- 直接证据：移入循环后每次迭代仍逐项断言 `result.download is download`、`replace(result, failure=None)` 抛 `requires public failure`（owner 消息 `failed download result requires public failure`，`dayu/fins/direct_events.py:679-680`）、`replace(result, status=SUCCESS, exit_code=...)` 抛 `only valid for FAILURE`（owner 消息 `public failure is only valid for FAILURE result`，`:675-676`）。取消拒绝断言由改前只对最后一次迭代（`succeeded` 基线）执行 1 次，变为对三个基线各执行 1 次；match 字符串 `cannot contain cancelled disposition` 与 owner 消息 `failed download result cannot contain cancelled disposition`（`:681-682`）一致，未放宽。无断言被删除或弱化。

### 核对三：三个基线的取消拒绝断言有效且命中 owner 分支

- source：循环内 `replace(result, download=replace(zero, terminal_disposition=FinsDownloadTerminalDisposition.CANCELLED))`。
- trigger / 分支证据：`FinsResultSummary.__post_init__` 在 `status is FAILURE` 且 `download.terminal_disposition is CANCELLED` 时抛出带 `cannot contain cancelled disposition` 的 `ValueError`（`dayu/fins/direct_events.py:677-682`）；`replace(zero, CANCELLED)` 先经 `FinsDownloadPublicSummary.__post_init__`，`zero` 的 discovered_count=0 命中 `empty_terminal_override`（`:465-471`）而可构造，因此异常确定由 `FinsResultSummary` owner 抛出。测试通过（本路实跑 1 passed）反证 match 命中的正是 owner 消息——若被下载摘要自身的守恒校验（`terminal_disposition does not match public counts`）抢先抛出，match 将失败。
- 对取消替换固定使用 `zero` 基变体（而非 `replace(download, ...)`）的审查：对 `partial`/`succeeded` 基线，改 `terminal_disposition=CANCELLED` 会先被 `FinsDownloadPublicSummary` 计数守恒拒绝（`discovered_count != 0` 不适用 override），根本到不了 `FinsResultSummary` 分支；`zero` 基 CANCELLED 摘要（“启动前零候选取消”语义，`:465` 行内注释）是这组 fixture 中唯一可表达、能到达 owner 分支的取消输入。owner 拒绝逻辑只依赖 `status` 与 `download.terminal_disposition`（`:678-682`），三次迭代各自从三个不同基线 result 发起，同一 owner 分支被三路验证。
- 结论：三个基线断言均有效且语义落在 owner contract 上，成立。
