### 1-未修复-严重-Orphaned COMPACTION_REQUESTED 事件无恢复扫描器

- **入口/函数**: `HostDispatchScheduler._run_pre_start_governance` → `_prepare_compact_before_dispatch` → `_execute_proactive_compaction`
- **文件(行号)**: `dayu/host/dispatch.py`, lines 901, 918, 921, 1242-1271
- **输入场景**: Run 在 queue promotion 阶段触发 proactive compaction。`_prepare_compact_before_dispatch` 在持久化事务中写入 `CONTEXT_COMPACTION_REQUESTED` 事件并提交。随后 `_execute_proactive_compaction` 在事务外执行 LLM 压缩。若进程在事务提交后、压缩结果写回前崩溃，Run 被留在 ACCEPTED/QUEUED 状态，EventLog 中存在已提交的 `CONTEXT_COMPACTION_REQUESTED` 但无对应的 `CONTEXT_COMPACTED` 或 `CONTEXT_COMPACTION_FAILED`。
- **实际分支**: 压缩请求已持久化（line 918 提交事务），但压缩执行在 line 921 异步进行。崩溃窗口存在于 line 918 与压缩结果写入之间。`StartupRecoveryScanner` 不扫描孤儿压缩请求。
- **预期行为**: 重启后恢复扫描器应发现孤儿 `CONTEXT_COMPACTION_REQUESTED` 事件，重试压缩或将 Run 标记为失败。
- **实际行为**: Run 永久停留在 ACCEPTED/QUEUED 状态，Session 活动位被占用。无用户可见错误。
- **直接证据**: `dispatch.py:901`（压缩请求写入事务内），`dispatch.py:918`（事务提交），`dispatch.py:921`（压缩执行在事务外）。`open_host.py:461` 的 `StartupRecoveryScanner` 只扫描丢失的 active worker，不扫描孤儿压缩请求。
- **影响**: Run 永久卡死，Session slot 被占用，该 Session 无法接受新 Run。需要手动干预才能清理。
- **建议改法和验证点**: 在 `StartupRecoveryScanner`（或独立扫描遍）中增加对已提交 `CONTEXT_COMPACTION_REQUESTED` 但缺少对应 `CONTEXT_COMPACTED`/`CONTEXT_COMPACTION_FAILED` 的 Run 的检测。对每个孤儿请求，可重试压缩或写入 `CONTEXT_COMPACTION_FAILED` 后标记 Run 为 FAILED。
- **修复风险（中）**: 需要仔细设计重试语义，避免在压缩结果已部分写入时重复执行压缩。
- **严重程度（严重）**:

### 2-未修复-高-损坏的 EventLog payload_json 导致整个恢复扫描事务回滚

- **入口/函数**: `count_recovery_dispatches_for_run()` → `count_committed_events_by_run_and_type()` → `_payload_mapping_from_text()`
- **文件(行号)**: `dayu/host/durable/event_log.py`, lines 584-597, 709-714; `dayu/host/durable/transaction.py`, lines 287-289
- **输入场景**: EventLog 中某行 `payload_json` 损坏（非合法 JSON）。恢复扫描在处理某 Run 时读取该 Run 的 EventLog 事件以统计恢复派发次数。
- **实际分支**: `_payload_mapping_from_text`（event_log.py:709-714）捕获 `json.JSONDecodeError` 后抛出 `HostDurableError`。此异常向上传播到 `count_committed_events_by_run_and_type`（无 try/except），最终到达 `transaction.py:287-289`，导致整个扫描事务回滚。
- **预期行为**: 单个损坏的 EventLog 行不应阻止其他 Run 的恢复。应跳过损坏事件，记录诊断日志，继续处理后续 Run。
- **实际行为**: 整个恢复扫描事务回滚。所有在此之前已成功执行的 closeout 和分类操作被原子回滚。下次启动时重新遇到同一损坏行，再次回滚，形成启动循环（boot loop）。
- **直接证据**: `event_log.py:709-714`（raise HostDurableError），`event_log.py:584-597`（循环中无 try/except 包裹 payload 解析），`transaction.py:287-289`（捕获 HostDurableError 后回滚整个事务）。
- **影响**: 一个损坏的 EventLog payload 阻止所有非终态 Run 的恢复。系统无法自愈，需要手动删除损坏行。
- **建议改法和验证点**: 在 `count_committed_events_by_run_and_type` 循环中对每个事件的 payload 解析增加 try/except，跳过损坏事件并记录诊断日志。或把恢复扫描改为 per-run 事务粒度，使单个损坏 Run 不影响其他 Run。
- **修复风险（低）**: 跳过损坏事件时需确保不引入计数偏差；可在跳过时写入诊断事件。
- **严重程度（高）**:

### 3-未修复-高-压缩预算估算使用 ref ID 字符串长度而非实际内容 token 数

- **入口/函数**: `estimate_compacted_context_budget` → `_estimate_preserved_context_tokens`
- **文件(行号)**: `dayu/host/compaction_budget.py`, lines 49-71, 75-90
- **输入场景**: LLM compactor 产出 `CompactionCandidate`，其中 `budget_after_compact` 由 `estimate_compacted_context_budget` 计算。Host 在 `compaction_operation.py:140-143` 使用该值与 `hard_threshold_tokens` 比较以判断压缩是否充分。
- **实际分支**: `_estimate_preserved_context_tokens`（line 60-67）调用 `estimate_text_tokens` 处理 `_preserved_ref_texts(request)` 的返回值。`_preserved_ref_texts`（line 75-90）返回的是 opaque ref ID 字符串（如 `"event-user-input-accepted-sha256:abc123..."`），长度约 70-130 字符，每个 ref ID 约占 34 tokens，而非被引用实际内容（可能数千 tokens）。
- **预期行为**: 压缩后预算估算应反映保留内容的实际 token 开销。
- **实际行为**: 系统性低估压缩后 token 预算。一个表面上通过 hard threshold 检查的压缩候选，实际内容可能远超阈值。压缩后的 LLM 调用可能触发 provider context overflow。
- **直接证据**: `compaction_budget.py:60-67`（将 ref ID 当作文本内容计算 token），`compaction_budget.py:75-90`（返回 ref ID 字符串而非实际内容）。
- **影响**: 压缩后仍可能 context overflow，导致 LLM 调用失败，Run 进入 fallback 或失败路径。压缩本身消耗的 LLM token 被浪费。
- **建议改法和验证点**: 方案 A：读取被引用 EventLog 事件的实际内容估算 token 数。方案 B：使用保守的每 ref 固定估算值（如 tool result 1000 tokens、raw turn 500 tokens），基于 `UsageObservation` 校准。
- **修复风险（中）**: 方案 A 需要额外的 EventLog 读取 I/O。方案 B 可能与实际差异较大。
- **严重程度（高）**:

### 5-未修复-中-恢复扫描在单个写事务中运行阻塞所有并发写入

- **入口/函数**: `StartupRecoveryScanner.scan()`
- **文件(行号)**: `dayu/host/recovery.py`, lines 167-207
- **输入场景**: 数据库中有 N 个非终态 Run（如 N=100）。恢复扫描在单个 `BEGIN IMMEDIATE` 写事务中遍历所有 N 个 Run。
- **实际分支**: `recovery.py:203` 将整个扫描循环（lines 180-201）包裹在 `transaction_runner.run_write(operation)` 中。`BEGIN IMMEDIATE` 立即获取写锁。
- **预期行为**: 锁持有时间应受控，不应因扫描 Run 数量线性增长。
- **实际行为**: 写事务持续时间 O(N + K × 每个 closeout 的 EventLog 追加和状态变更)。持有写锁期间，所有正常操作（创建 session、启动 run、取消、心跳等）被阻塞。
- **直接证据**: `recovery.py:180-203`（全部操作在单个写事务中）。
- **影响**: 多租户或大量非终态 Run 场景下，恢复扫描导致明显延迟尖峰。SQLite busy timeout + retry 机制部分缓解但不可靠。
- **建议改法和验证点**: 分批处理——每批固定数量 Run（如 10-20 个）后提交事务，再开启下一批。
- **修复风险（中）**: 分批可能引入跨批一致性问题，需要确保同一 Session 的多个 Run 不会在不同批次中被冲突处理。可利用 session 级 active-run UNIQUE 约束作为天然防御。
- **严重程度（中）**:

### 6-未修复-中-StdlibPidLivenessProbe 不提供 start_token/boot_id，PID 复用导致孤儿检测失效

- **入口/函数**: `StdlibPidLivenessProbe.collect()` → `_classify_stale_owner()`
- **文件(行号)**: `dayu/host/recovery_process.py`, lines 72-114, 305-332
- **输入场景**: 原始 owner 进程死亡，PID 被 OS 回收后分配给另一无关进程。心跳过期，但 PID 仍然存活。
- **实际分支**: `StdlibPidLivenessProbe.collect()` 所有路径均返回 `observed_start_token=None` 和 `observed_boot_id=None`（lines 85-89, 93-98, 101-107, 108-114）。在 `_classify_stale_owner`（lines 305-332）中：start_token 不匹配检查永不触发（`observed_start_token is None`），boot_id 不匹配检查永不触发（`observed_boot_id is None`），进程身份匹配检查永不触发（`observed_start_token == row.process_start_token` 为 `None == "token"` 即 False）。代码落入 `OrphanProofInconclusive(reason='owner_pid_live_without_identity_proof')`。
- **预期行为**: 应能通过读取 `/proc/<pid>/stat` 获取进程启动时间作为 start_token，读取 `/proc/sys/kernel/random/boot_id` 获取 boot_id，从而启用强身份验证。
- **实际行为**: PID 复用场景下，孤儿 Run 永远被分类为 inconclusive，不会被恢复。Run 永久停留在 RUNNING/CANCELLING 状态不回收。
- **直接证据**: `recovery_process.py:85-114`（所有 probe 路径 start_token/boot_id 为 None），`recovery_process.py:305-332`（身份检查不可达）。
- **影响**: 在 PID 复用频繁的环境（Linux 常见），孤儿 Run 无法被恢复。恢复系统依赖 PID 缺失作为正向孤儿证据，但 PID 复用使该信号不可靠。
- **建议改法和验证点**: 实现更丰富的 probe，读取 `/proc/<pid>/stat`（进程启动时间）和 `/proc/sys/kernel/random/boot_id`，启用 `_classify_stale_owner` 中已存在但不可达的强身份检查路径。
- **修复风险（低）**: 仅新增 probe 实现，不改变分类逻辑。Linux only；macOS/Windows 继续使用当前实现。
- **严重程度（中）**:

### 7-未修复-中-累积式恢复派发计数器永不复位

- **入口/函数**: `count_recovery_dispatches_for_run()` → `count_committed_events_by_run_and_type()`
- **文件(行号)**: `dayu/host/durable/event_log.py`, lines 601-626; `dayu/host/recovery.py`, lines 67-69, 265-268, 405-409
- **输入场景**: Run 被恢复一次（恢复派发计数 = 1），恢复成功，Run 正常终态。后续 Run 被重试/重放并再次遇到需要恢复的场景。
- **实际分支**: `count_recovery_dispatches_for_run()` 统计该 Run **整个生命周期**中所有 `RUN_STARTED` 事件（含 `start_reason='recovery'`）。这是单调递增计数器，从不复位。默认 `recovery_dispatch_limit=1`，Run 在 recovery.py:268 命中限制，在 line 281 被标记为 LOST。
- **预期行为**: 恢复派发限制应考虑 Run 生命周期边界。成功恢复并终态的 Run 在新 Attempt 中应可被再次恢复。
- **实际行为**: 默认策略下每个 Run 整个生命周期最多自动恢复一次。对合法需要多次恢复的场景（如重试 Run 遇到与原始 Run 相同的孤儿场景），恢复被拒绝。
- **直接证据**: `event_log.py:601-626`（跨生命周期累积计数），`recovery.py:56-69`（限制常量）。
- **影响**: 合法恢复请求被拒绝，Run 被错误标记为 LOST。
- **建议改法和验证点**: 将恢复派发计数范围限定为当前 Attempt 生命周期（仅统计 `event_sequence > source_attempt.terminal_event_sequence` 的事件），或使用 per-Run 计数器在成功完成时复位。或使 `recovery_dispatch_limit` 可 per-Run 配置。
- **修复风险（中）**: 计数器范围变更可能改变现有恢复行为语义。
- **严重程度（中）**:

### 10-未修复-中-ATTACH_ACTIVE 策略拒绝 ACCEPTED 状态 Run

- **入口/函数**: `_StartRunOperation._handle_active_run`
- **文件(行号)**: `dayu/host/admission.py`, lines 1015-1021
- **输入场景**: `start_run` 请求使用 `queue_policy="attach_active"`，Session 当前有一个 ACCEPTED 状态的 Run（已被接纳但尚未 dispatch）。
- **实际分支**: `admission.py:1016-1021`：`if active.status == RunStatus.ACCEPTED: raise HostApiError(code=CONFLICT, ...)`。
- **预期行为**: `ATTACH_ACTIVE` 文档描述为"返回已有活动 Run"。ACCEPTED 的 Run 是 Session 当前活动 Run，应可 attach。
- **实际行为**: 抛出 CONFLICT 错误，强制调用方处理错误并重试。
- **直接证据**: `admission.py:1016-1021`（显式拒绝 ACCEPTED），对比 `admission.py:1033-1041`（RUNNING/WAITING 等状态成功 attach）。
- **影响**: 调用方使用 `attach_active` 策略时无法 attach 到尚未 dispatch 的新提交 Run，产生时序依赖的失败模式。
