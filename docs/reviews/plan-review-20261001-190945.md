### 01-未修复-中-§4 同 source_id 冲突条款与现有 fail-closed 去重守卫及既有测试直接矛盾
- **位置**: plan v2 §4「同来源去重不制造报告数量；同 source_id 真正冲突保留一条未知，只投影各版本一致的已知日期，不任挑标题。」
- **问题类型**: 契约缺失 / 不可直接实施（与既有 fail-closed 行为的未声明冲突）
- **当前写法**: 该句未声明是否为行为变更；「各版本一致」以同 source_id 存在多版本为前提，多版本只在去重前存在。
- **反例/失败场景**: 同一 document_id 两行核心事实（title/filing_date/category/source_url/language）不一致时，现状 `_deduplicate_hk_announcements` 直接 raise ValueError（`cn_report_selection.py:750-758`），整次 discovery 以 provider 协议异常失败；既有 owner 测试 `test_hkexnews_selection_fails_closed_on_same_source_id_fact_conflict`（`tests/fins/test_cn_report_selection.py:721`）断言该行为；v1 plan 明确写过「同 source_id remote 核心 facts 冲突仍 `_deduplicate_hk_announcements` 原 ValueError（不伪造 fiscal error）」（`pr-197-r1-f5-plan-20261001.md:186`）。按 v2 字面实施=静默弱化 fail-closed 并撞既有测试；按保留 raise 理解=该句为死规格且 §9 无验收行。
- **为什么有问题**: provider 数据完整性冲突属运输/协议可信性，财期证据不足属业务推断边界；混入 unknown 会伪造 fiscal 语义、改变 `FinsPublicFailure` kind/retry_hint，且 plan 未裁决、未更新测试清单。
- **直接证据**: 上述四处冻结字节。
- **影响**: 实施 Agent 被迫二选一重设计 / 静默弱化安全边界 / review 不可验收。
- **建议改法和验证点**: 二选一写清——(a) 保留 raise：改写为「同 source_id 核心事实冲突维持 fail-closed 原异常，不进入 unknown」并删除或重指「各版本一致日期」；(b) 改为 unknown：显式标记为既有行为变更、给出去重冲突→unknown 的判定口径，迁移 721 测试并加 §9 验收行。验证点：721 测试去留与断言。
