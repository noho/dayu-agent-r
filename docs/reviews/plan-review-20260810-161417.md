### 3-未修复-中-`FinsDownloadEffectiveFilters` 持续承载两个 mode bool 但不含互斥不变量，存在防御缺口

- **位置**: §5.1 DL-F12 固定不变量；`dayu/fins/download_contract.py` line 162-204
- **问题类型**: 契约缺失 / 架构边界
- **当前写法**: 计划将唯一 validation owner 定为 `FinsDownloadRequest.__post_init__`。`FinsDownloadEffectiveFilters` 继续持有 `overwrite_existing: bool` 和 `rebuild_local_artifacts: bool` 两个字段，其 `__post_init__` 只校验均为 bool 但不校验互斥。
- **反例/失败场景**: `FinsDownloadEffectiveFilters` 是独立公开构造的 frozen dataclass。虽然正常 data flow 从 `FinsDownloadRequest` → workflow → `FinsDownloadEffectiveFilters` 不应产生 `True,True`，但：
  1. `FinsDownloadEffectiveFilters` 出现在 public contract `FinsDownloadResultSummary.effective_filters` 中
  2. `FinsDownloadPublicSummary.effective_filters` 同样暴露它
  3. 测试、fixture、rebuild 路径中可能独立构造 `FinsDownloadEffectiveFilters`
  4. 没有 compile-time 或 runtime guard 阻止 `True,True`
- **为什么有问题**: 计划将 invariant 收缩到单一 owner (`FinsDownloadRequest`)，这是正确方向。但 `FinsDownloadEffectiveFilters` 是独立公开类型，同时承载两个 mode bool 而不防御，违反了 "同一业务事实必须有唯一 owner" — 这里 `FinsDownloadEffectiveFilters` 实际上在**投影**（而非拥有）mutation mode 组合合法性，但它持有的两个 bool 字段名暗示它也在表达这一语义。
- **直接证据**:
  - `dayu/fins/download_contract.py` line 175-176: `overwrite_existing: bool` / `rebuild_local_artifacts: bool`
  - `dayu/fins/download_contract.py` line 193-196: `__post_init__` 仅校验 `isinstance`，不校验互斥
  - Plan §5.1: "runtime、source adapter、CN/HK/SEC workflow 不含 mode precedence、冲突 fallback 或二次 validation" — 说明 plan 知道不应有二次判断，但未提及 `FinsDownloadEffectiveFilters` 自身防御
- **影响**: 防御缺口 / 后续维护者可能在 fixture/测试中误构造非法组合
- **建议改法和验证点**:
  1. 方案 A（推荐）：在 `FinsDownloadEffectiveFilters.__post_init__` 增加与 `FinsDownloadRequest` 相同的互斥断言，使 invariant 在任何构造路径都成立
  2. 方案 B：若认为这是有意设计的 "投影类型不做业务校验"，必须在 docstring 明确说明 `FinsDownloadEffectiveFilters` 不拥有 mode 组合合法性，只是上游已校验值的投影
  3. 无论哪种方案，在 §6 Slice 1 owner test matrix 中增加 `FinsDownloadEffectiveFilters(overwrite=True, rebuild=True)` 的防御测试
- **修复风险**: 低
- **严重程度**: 中
