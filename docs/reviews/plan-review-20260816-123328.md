## RF1-RF4 逐项终审

### RF1 frozen inspector 未定义 whole-kind inventory/commit 调用形状

**最终状态：已修复**

修订后 plan §6.1 做了三处精确变更：

1. `requested_document_id` 类型从 `str` 改为 `str | None`（§6.1 冻结签名代码块第 358 行）。
2. `target` 类型从 `_SourcePublicationInspection` 改为 `_SourcePublicationInspection | None`（§6.1 数据类定义第 346 行）。
3. 新增 "冻结 inspector 有且只有两种调用形状" 段落（§6.1 第 379-387 行）：
   - exact-target mode：`requested_document_id=<canonical document ID>`，`target` 非 `None`。
   - whole-kind mode：`requested_document_id=None`，`target` 为 `None`。inventory 与 commit validator 每个 source kind 只能调用一次 whole-kind mode；在同一 guard/batch 内消费同一份 payload，不得逐 document 重扫、重新聚合或跨 guard/batch 拼接结果。

这直接解决了原 finding 指出的 "inventory 需要为每个实际 source 投影 shared manifest reason" 和 "commit validator 遍历 source kinds" 没有单一 target 的问题。implementation agent 有了明确的调用约定，不需要自行决定调用形状。

### RF2 canonical remaining items 的载体在 §6.1 与 §6.2 step 5 之间存在读取歧义

**最终状态：已修复**

修订后 plan §6.2 step 5（第 447-453 行）做了精确重写：

- "canonical remaining items 明确只取同一次 exact-target inspection payload 中每个 non-target `_SourcePublicationInspection.canonical_manifest_item`，按 canonical document ID 稳定排序"。
- "此步骤绝不消费 `_SourceKindPublicationInspection.canonical_manifest_items` aggregate——target-local damage 会使 aggregate 为空，但不得因此丢弃 complete sibling 的单点 canonical item"。
- "也绝不读取、merge 或复制损坏 manifest 中的 item"。
- "任一 non-target 单点 item 为空、重复或不能组成全量唯一 remaining items 时，抛 `SourceIntegrityRepairBlockedError(CANONICAL_MANIFEST_UNAVAILABLE)`"。

同时 §6.1（第 369-371 行）补充了单点可用性条件："每个 source 的 `canonical_manifest_item` 可用性只取决于该 source 自身的 trusted persisted meta 与 `content_classification=COMPLETE`，不受其它 source（包括 requested target）损坏影响"。

这直接解决了原 finding 指出的 "最常见 repair 场景——target original 缺失 + complete sibling + manifest 存在" 会因 aggregate 为空而被阻断的问题。step 5 现在明确消费 per-source 单点字段，不依赖 aggregate。

### RF3 `reset_source_document_for_repair` step 3 与 `has_same_source_publication_identity` 的 UNSAFE-ValueError 机制

**最终状态：已修复**

修订后 plan §6.2 step 3（第 432-437 行）做了精确重写：

- "比较前先 gate：expected 或 staged 任一为 `UNSAFE`，或任一 public status 不是 `REPAIR_REQUIRED`，立即抛 `SourceIntegrityRevisionConflictError`。"
- "通过 gate 后才调用 `has_same_source_publication_identity(expected, staged)`；返回 false 同样抛 conflict。"
- "该比较函数在 storage method 内若仍抛 `ValueError`（包括 identity/unsafe invariant 漂移），必须由 method 捕获并转换为同一个 path-free `SourceIntegrityRevisionConflictError`，禁止 raw `ValueError` 逃逸。"
- "上述转换只包围 staged comparison，不吞掉第 1 步 invalid capability/identity/expected classification 的 input `ValueError`。"

这直接解决了原 finding 指出的 "Phase A 后 published 被外部篡改为 UNSAFE → staged inspection 为 UNSAFE → `has_same...` 抛 ValueError → 逃逸为 UNEXPECTED_RUNTIME" 的窄缝。gate + try/except 转换确保了 UNSAFE 场景走 typed conflict 路径。

### RF4 download whole-manifest-missing 表述过宽

**最终状态：已修复**

修订后 plan §7.2（第 530-533 行）做了精确重写：

- "只有一个实际 filing 且它正是 accepted selected target 时，保持既有 `SelectedSourceRepairRequired` 路径，由 download reset、重新下载并通过 upsert 重建 canonical manifest。"
- "该单-source 行为不是把 upload rewrite 授权泛化到 download，多-source/非-selected 仍严格拒绝。"

这直接解决了原 finding 指出的 "ticker 下只有 1 个 filing、manifest 缺失时 preflight 返回 SelectedSourceRepairRequired → download 继续" 的行为与 "必须 fail closed" 绝对表述的矛盾。plan 现在区分了单 source（走既有 repair）和多 source/非 selected（typed fail closed）。

## 修订是否引入新 blocker

经逐节审查 round-2 修订的增量变更（§6.1 的两种调用形状、§6.1 的单点可用性条件、§6.2 step 3 的 gate + try/except、§6.2 step 5 的 per-source 消费、§7.2 的 download 区分），未发现新 blocker：

1. **类型变更安全**：`requested_document_id: str | None` 和 `target: _SourcePublicationInspection | None` 是向后兼容的放宽，不影响已有 exact-target mode 调用方。
2. **调用形状约束清晰**：whole-kind mode 的 "每个 source kind 只调用一次" 约束与现有 `_fs_source_document_core.py` 的 `list_source_integrity` 逐 doc 循环（第 514-567 行）和 `_fs_storage_infra.py` 的 commit validator 遍历 source kinds（第 1142-1170 行）的调用模式一致——它们都是在一个 guard/batch 内遍历所有 doc，只是现在统一为一次 whole-kind mode 调用。
3. **per-source canonical item 消费**：与现有 `_fs_storage_infra.py:1237-1255` 的 `FilingManifestItem.from_source_meta(meta).to_dict()` 逐 source 生成模式一致。
4. **gate + try/except 转换**：只包围 staged comparison，不吞 input ValueError，是精确的异常边界。
5. **download 区分**：保持了既有 `classify_source_integrity_preflight` 的单 repair target → `SelectedSourceRepairRequired` 行为，没有引入新 preflight 逻辑。
