### 1-未修复-严重-`_compact_or_fail` / `_append_missing_terminal_failure_if_needed` 将 terminal draft 路由到 `append()` 而非 `append_terminal_and_close()`，durable 路径运行时崩溃

- **入口/函数**: `_compact_or_fail`、`_append_compact_exception_failure`、`_append_missing_terminal_failure_if_needed`
- **文件(行号)**: `dayu/host/_run_harness.py:1440,1481,1528,1701,1899`
- **输入场景**: durable/supervisor 路径下 context compact 失败（retry limit / trace missing / internal error）或 Engine stream 正常结束但无终态
- **实际分支**: `_scope_appender().append(host_context_compact_failure_terminal_draft(...))` 和 `_scope_appender().append(host_failure_draft(...))`，两者都返回 `type=RunEventType.RUN_FAILED` 的 terminal draft
- **预期行为**: terminal RunEvent 应通过 `append_terminal_and_close()` 原子写入（verify_owner + append + close 在同一事务），与 `_handle_owner_lost`（line 1352）和 `_append_worker_failure_if_needed`（line 1860）的实现一致
- **实际行为**: `AttemptScopedRunEventAppender.append()`（`_attempt_supervisor.py:248`）对 `TERMINAL_RUN_EVENT_TYPES` 抛 `ValueError("AttemptScopedRunEventAppender.append cannot accept terminal RunEventType; use append_terminal_and_close")`。durable 路径下 `_scope_appender()` 返回 `AttemptScopedRunEventAppender`，5 处调用全部崩溃
- **直接证据**: `_attempt_supervisor.py:248-249` guard；`_run_harness.py:1440` `_scope_appender().append(host_context_compact_failure_terminal_draft(...))`；`_event_translation.py:266` `type=RunEventType.RUN_FAILED`；`_run_harness.py:1853-1863` 中 `_append_worker_failure_if_needed` 正确使用 `append_terminal_and_close()` 作为对比
- **影响**: durable 路径下任何 context compact failure 或 Engine stream 无终态场景都会抛 `ValueError`，Run 残留无 terminal event，RunResult 无法推导，RunStream 订阅方 hang
- **建议改法和验证点**: 将 5 处 `_scope_appender().append(terminal_draft)` 替换为 `self.attempt_supervisor.append_terminal_and_close(owner_context=..., draft=...)`，与 `_append_worker_failure_if_needed` 保持一致。验证：在 durable 装配下触发 compact failure，确认 terminal event 正常落库
- **修复风险（低/中/高）**: 低（模式与 `_append_worker_failure_if_needed` 一致，仅替换调用点）
- **严重程度（低/中/高/严重）**: 严重（durable 路径下 compact failure 必然崩溃，无测试覆盖此路径）

### 2-未修复-高-`repair_missing_session_snapshots` 跨 run 批量投影丢失早期 run 的 raw turns

- **入口/函数**: `DurableConversationMemoryStore.repair_missing_session_snapshots` → `_project_in_tx`
- **文件(行号)**: `dayu/host/_conversation_memory_durable.py:331`
- **输入场景**: session 包含多个 run（如 run A → run B），且 snapshot row 因运维误操作或 read model 损坏而缺失
- **实际分支**: line 331 `self._project_in_tx(tx=tx, events=canonical_events)` 将整个 session 的所有 canonical events（跨多个 run）作为单 batch 传入
- **预期行为**: repair 路径应按 run 分组投影，保留每个 run 的 `user_event` / `final_event`，与 observer 路径（per-run accumulation in `_pending_by_run`）语义一致
- **实际行为**: `_project_raw_turn`（line 480-528）对 `user_event` / `final_event` 执行 last-writer-wins：当 run B 的事件覆盖 `user_event` / `final_event` 后，run A 的对应值被丢弃。repair 写入的 snapshot 只包含最后一个 run 的 raw turn
- **直接证据**: `_project_raw_turn` line 506-528 中 `user_event` 和 `final_event` 赋值无 run_id 隔离；repair 路径 line 331 传入跨 run 的 `canonical_events`；observer 路径 line 165-189 通过 `_pending_by_run` dict 按 run_id 分组，在 terminal 时逐 run 投影
- **影响**: 多 run session 的 repair snapshot 丢失早期 run 的 user/final raw turns；memory 重建后对话历史不完整。单 run session 不受影响
- **建议改法和验证点**: repair 路径应按 run_id 分组事件，逐 run 调用 `_project_in_tx`；或在 `_project_raw_turn` 内按 run_id 隔离 `user_event` / `final_event`。验证：构造多 run session，删除 snapshot row，调用 repair，断言所有 run 的 raw turns 都保留
- **修复风险（低/中/高）**: 中（需改造 repair 路径或 _project_raw_turn 语义）
- **严重程度（低/中/高/严重）**: 高（多 run session 的 memory 丢失，影响对话连续性）

### 3-未修复-中-overflow retry 后 ContextVar 指向旧 attempt 的 scoped appender

- **入口/函数**: `LocalRunHarness._run_to_store` → `_attempt_owner_scope` → `ToolRuntimeOwnerScope`
- **文件(行号)**: `dayu/host/_run_harness.py:895,1145`
- **输入场景**: Engine 触发 context overflow → compact 成功 → 新 attempt acquire → 旧 attempt 关闭 (STALE) → 新 engine 再次触发 overflow 或需要 `_scope_appender()` 的路径
- **实际分支**: line 895 `_attempt_owner_scope(current_active_attempt)` 创建 `ToolRuntimeOwnerScope` 设置 ContextVar 为旧 attempt 的 scoped appender；line 1145 `current_active_attempt = new_active_attempt` 更新变量但 ContextVar 未更新
- **预期行为**: `current_active_attempt` 变更后，`_scope_appender()` 应返回新 attempt 的 scoped appender
- **实际行为**: ContextVar 仍指向旧 attempt 的 `AttemptScopedRunEventAppender`；旧 attempt 已 STALE，`verify_owner` 将抛 `AttemptFencingError`
- **直接证据**: `ToolRuntimeOwnerScope`（`_tool_runtime.py:203-239`）在 `async with` 进入时 `set(appender)` 一次，退出时 `reset(token)`；`_attempt_owner_scope`（`_run_harness.py:617-648`）在 line 895 只调用一次；line 1145 更新 `current_active_attempt` 后无重新进入 scope 的逻辑
- **影响**: overflow retry 后若新 engine 再次触发需要 `_scope_appender()` 的路径（如 `_append_overflow_observed`），会抛 `AttemptFencingError`；被 `_handle_owner_lost` 正确捕获并收敛到 owner-lost 路径，无数据丢失，但触发不必要的 error handling 开销
- **建议改法和验证点**: overflow retry 后重新进入 `_attempt_owner_scope`（将 `async with` 移入循环内，或在 `current_active_attempt` 变更后显式更新 ContextVar）。验证：构造 double-overflow 场景，确认第二次 overflow 的 `_append_overflow_observed` 不抛 `AttemptFencingError`
- **修复风险（低/中/高）**: 中（需重构 `_run_to_store` 的 scope 生命周期）
- **严重程度（低/中/高/严重）**: 中（error handling 正确兜底，无数据丢失，但增加不必要的 fencing error 路径）

## Residual Risk

- **compact failure terminal routing 测试缺失**: finding 1 中 durable 路径下 compact failure 必然崩溃，但无测试覆盖此路径（测试使用非 durable 装配，`PlainRunEventAppender` 不 guard terminal types）。

- **`_fetch_more` 非原子多 fact append**: 与 finding 4 相关，生产 crash 在两步 append 之间会导致相同半写状态。旧 cursor 仍可用，但 observer 投影需容忍此 transient 状态。
- **fencing test coverage gap**: finding 6 中 expired/denied 路径的 fencing 测试缺失。
- **multiprocess 仅验证 file SQLite**: P8-S7 stress 测试使用 file SQLite (WAL + `BEGIN IMMEDIATE`)，未覆盖 `:memory:` 或 shared-memory 模式。
- **repair 路径 memory 丢失**: finding 2 中多 run session 的 repair snapshot 丢失早期 run 的 raw turns，影响对话连续性。
