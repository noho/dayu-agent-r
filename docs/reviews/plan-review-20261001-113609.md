## 三、Lenses（逐项显式应用结果）

1. **Goal-bound minimal design**：G1（churn typed 中止+区别原因）↔ SEC/CN churn 路径与 `SOURCE_REVISION_CONFLICT`；G2（新损坏表达仍需修复）↔ postrepair 产生层新 typed cause 与 `SOURCE_REPAIR_REQUIRED`；G3（rows/counts/manifest/company/rejected 守恒）↔ `filing_results` 真源快照 + 严格投影 + 独立 company/registry 事务（`sec_download_workflow.py:770-878` 实读：company batch 独立 begin/commit/rollback，事实不回滚）；G4（四公共入口同源）↔ runtime 唯一 mapping + wait/CLI 消费 `to_json_value`；G5（无 raw 文本/回归/≥80%/pyright）↔ E1 命令与断言。未发现 goal drift：新增仅 1 typed cause + 2 enum 值 + SEC abort/共用 builder/失败行 builder，均落在 F6-P1 已裁必要修正与 goal 明示允许的接口变化内；完整 structured reason durable、RepairBlocked 下载 mapping、indeterminate 等均按已裁边界排除，未塞入必修。
2. **Architecture boundary**：storage 产生 integrity 事实（`source_integrity.py` 异常族 + classifier 返回 disposition）；workflow 状态机拥有"repair 后仍需修复"的语义（初始 `SelectedSourceRepairRequired` 是调度信号、postrepair 同一 disposition 是致命事实——异常在 workflow 分支构造、不在 storage classifier 内抛，owner 判定正确）；adapter 严格投影不重算；runtime 唯一 public 语义 owner；CLI/wait 纯消费。无反向依赖、无跨层穿透。RepairRequired 无 payload 构造与 `SourceIntegrityRevisionConflictError.__init__(self) -> None` 同构（`source_integrity.py:211-227` 实读）。
3. **Best-practice**：封闭 cause 集合、`raise … from cause` 保链、fail-closed 严格投影、测试断言 owner 级 contract、禁 fake throw——符合项目约束。发现一处最佳实践偏离：共享 builder 抽取边界未规格化（Finding 1），含成功完成日志的归属问题（观测语义）。
4. **Optimal-solution**：对比过的替代（只加 runtime isinstance / 只改 workflow / CLI/wait 各自分类 / 新 job schema）在计划 §历史 8 与 root 裁决中已驳回，驳回理由与代码事实一致；"产生层 typed → workflow abort 快照 → adapter 保摘要 → runtime 唯一 mapping"确是 credible alternatives 中最短闭合路径。
5. **Overengineering**：未发现。一个 cause、两个 enum 值、一个行为 slice；未泛化 repair 引擎/发布事务/新 schema/新 status；cancellation 旧逻辑明示不顺带统一（`_cancelled_pipeline_completed_event` 保留）。
6. **Overcoupling**：8 生产文件 + 10 测试文件单 slice 是行为闭合的最小集（下游 mapping 依赖上游 typed cause，机械拆文件会产生"上游假 cause/下游已承诺 hint"半成品——计划 D 节动机成立）；共享 builder 走"直接参数朴素接口"而非 callback/factory（D2 明示），符合 AGENTS 接口偏好。风险点仅在 Finding 1 的合同缺口可能倒逼测试迁就实现。

## 四、Findings

### 1-未修复-中-D2 共享 `_build_sec_download_result` 合同缺失取消/status 维度与完成日志归属，与"cancel/repair gate 原测试保持"自相矛盾

- **位置**：计划 D2（`_build_sec_download_result` 签名块与"沿原 builder 默认 status='ok'"、"将原 `:718-759` 正常结果构造原位抽出并由正常完成与 typed 中止共同调用"）；D 表 `sec_download_workflow.py` 行"抽正常/abort 共用构造，既有取消结果保留原构造"；E 节"取消/repair gate/普通repair失败/公司独立发布/6k_filtered与SC13 registry-only原测试保持"。
- **问题类型**：契约缺失 / 状态机漏洞（兼计划内部矛盾）。
- **当前写法**：D2 给出的签名是 `def _build_sec_download_result(*, host, normalized_ticker, normalized_market, form_windows, end_date, overwrite, warnings, filing_results, elapsed_ms) -> dict[str, JsonValue]`，无 status/cancelled 参数；正文称"沿原 builder 默认 status='ok'"；抽取范围写 `:718-759`。同时 E 节要求 cancel/repair-gate 既有测试"保持"。
- **反例/失败场景**（触发数据 → branch → 状态链）：
  1. 触发：SEC 下载，repair filing 成功后 postrepair classifier 返回 `NoSourceRepairRequired`，随后 repair-gate 前 `cancel_checker` 第二次返回 True（现成测试 `tests/fins/test_sec_pipeline_download_stream.py:943` `test_download_stream_repair_gate_rechecks_cancel_before_company_batch` 即此场景，`:984` 断言 `final_result["status"] == "cancelled"`）。代码链：`sec_download_workflow.py:688-693` `cancelled=True; break` → `:707-762` 正常结果构造 → `:761` `status="cancelled" if cancelled else "ok"` → PIPELINE_COMPLETED。按 D2 签名实施（"原位抽出 :718-759" + 默认 'ok'）：mid-run cancel 的结果 status 变 `'ok'`，`:984` 断言失败；因该测试文件在允许更新清单内且计划未列其为必保 node，实施 Agent 可能"迁移"断言迁就实现，**静默丢失 `SecPipelineDownloadResult.status`（`sec_pipeline.py:198` typed 字段）的取消事实**，直接违反 G3"已确认事实守恒"与 D 节"保留原结果形状"。
  2. 同一抽取范围 `:718-759` 内含完成日志 `Log.info("美股下载完成: …")`（`sec_download_workflow.py:734-742`）。若随"原位抽出"进入共享 builder，typed abort 调用方会在操作中止路径打出**假的下载完成日志**（含 total/downloaded 计数），失败路径观测语义失真；若为保日志而拒绝抽取，则"既有取消结果保留原构造"（D 表）只能靠复制整段构造实现，又产生两份计数/构造真源（违反"重复逻辑必须抽取"）。
- **为什么有问题**：`SecPipelineDownloadResult.status` 是 SEC 结果契约的显式字段，mid-run cancel 的 `'cancelled'` 值有现成测试断言；D2 的签名+默认值与 E 节"原测试保持"两条指令不能同时成立。计划对 SEC abort 侧的 status='ok'（"这个私有 result 只描述行快照，typed exception 承担中止事实"）语义正确，但没有把"正常完成但 cancelled"这一第三种取值写进合同。实施 Agent 面对矛盾指令，最优结局是停下来重新设计（不可直接实施），最坏结局是回归取消语义或伪造完成日志。
- **直接证据**：`sec_download_workflow.py:718-733`（计数）、`:734-742`（完成日志）、`:743-762`（`_build_result(..., status="cancelled" if cancelled else "ok")`）；`sec_pipeline.py:1721`（`payload.pop("status", "ok")` 默认）、`:180-202`（`SecPipelineSummary`/`SecPipelineDownloadResult.status: str`）；`tests/fins/test_sec_pipeline_download_stream.py:984`（cancelled 断言）、`:1012`（早期取消走 `_cancelled_pipeline_completed_event`，`:880-952` 独立构造 `status="cancelled"`，该路径计划明示保留）；计划 D2 签名块与 E 节保持句。
- **影响**：实施 Agent 跑偏 / 生成错误代码；取消结果状态不一致（公共结果形状回归）；abort 路径假成功日志；或测试被错误迁移固化错误语义——任一outcome都使 G3 验收不可信。

- **修复风险（低/中/高）**：低（一个参数 + 一句日志归属声明 + 一条 keep 断言）。
- **严重程度（低/中/高/严重）**：中。

### 2-未修复-低-CN postrepair typed catch 扩为三类型 union 未在当前前缀显式化

- **位置**：计划 D1 CN/HK 既定流程 bullet 2-3（catch 顺序与 "SelectedSourceRepairRequired 改新 RepairRequired"）；对照 D3.4（SEC 明写"同封闭 typed catch（三类型 union）"）。

- **当前写法**：D1 明写 mid-filing catch 顺序为 `CnDownloadCancelledError` → `(SourceIntegrityPreflightError, SourceIntegrityRevisionConflictError)` → ordinary Exception，并只写 "SelectedSourceRepairRequired 改新 RepairRequired"（抛点替换）与 "`_integrity_abort` cause union 扩展"；未像 SEC D3.4 那样明写 postrepair try/except 的 except-tuple 同步扩为三类型。
