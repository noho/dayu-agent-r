### 1-未修复-低-`runner.http.response` 日志在 `client_correlation_id=None` 时输出字面量 `client_correlation_id=None`

- **入口/函数**: `AsyncOpenAIRunner._do_attempt`
- **文件(行号)**: `dayu/engine/runners/openai/runner.py:617-623`
- **输入场景**: Runner 调用时 `request_identity` 为 `None`（例如 Engine 内部不传 request identity 的路径），或 `request_identity.client_correlation_id` 为 `None`。
- **实际分支**: `client_correlation_id` 参数为 `None`，Python `%s` 格式化输出 `None`。
- **预期行为**: 日志格式 `%s` 对 `None` 输出 `None` 是 Python 标准行为，语义上正确表达了"无 client correlation id"。这与同日志行已有的 `provider_request_id=%s`（在无 provider id 时同样输出 `None`）一致。
- **实际行为**: 日志行包含 `client_correlation_id=None`，对 operator 可读性无负面影响，只是终端显示与 `provider_request_id=None` 一致。
- **直接证据**: `runner.py:618` 格式字符串 `"provider_request_id=%s client_correlation_id=%s"`；Python `logging` 的 `%s` 格式化对 `None` 输出 `"None"`。
- **影响**: 极低。不影响任何状态、不污染任何持久化数据、不进入 LLM 上下文。纯粹是日志可读性的微调项（可改为 `client_correlation_id=%s` 并在传参时做 `client_correlation_id or "-"`），但当前行为与已有 `provider_request_id` 完全一致，具有一致性优势。
- **建议改法和验证点**: 无需修改。当前行为与同日志行的 `provider_request_id` 处理一致，且 `None` 明确表达"不存在"。若未来统一调整 Runner 日志的 None 占位策略，应同时处理 `provider_request_id` 和 `client_correlation_id`。
- **修复风险（低）**: N/A。
- **严重程度（低）**: 不阻塞。属于一致性与可读性微调。

## Residual Risk

### 已记录且已裁决

1. **`_lost_host_event` 未来同步风险**（Finding 2）：已在 code-review gate 被 controller 明确 `rejected-with-reason`。该风险仅在后续 WU 改变 `_lost_lifecycle_plan` 的 correlation ids 时才会触发，届时应在对应 WU plan gate 中复核。当前状态安全。

2. **`_terminal_diagnostics` 模块未来维护风险**：已在 code-review fix gate 通过新增 8 个直接单元测试关闭。`test_terminal_diagnostics.py` 覆盖了所有分支组合（仅 provider id、仅 client id、双 id、双 absent、message=None、message=""、id 截断），显著降低了后续格式回归风险。

3. **Tool Trace `diagnostic_ref=None` 且 `client_correlation_id` 存在时的行为**：已在 code-review fix gate 通过新增 `test_diagnostic_trace_uses_raw_payload_ref_without_provider_id` 测试关闭。同时覆盖了 raw_payload_ref 存在时的 `diagnostic_ref` fallback 行为。

### 结构 residual risk

4. **非 `x-request-id` 响应 header 的 provider request id 采集**：当前实现只从 `x-request-id` 提取 provider request id。如果生产环境中 mimo 或其他 provider 使用不同响应 header（如 `X-Request-ID` 已被 case-insensitive 覆盖，但完全不同的 header name 不会被采集），`provider_request_id` 将为 None，仅剩 `client_correlation_id` 作为 fallback。这是 plan 明确接受的设计决策（Decision 5），且 `client_correlation_id` 已可在 terminal diagnostic 和 Tool Trace 中作为厂商报障 fallback。该风险由外部 provider 行为变化触发，不在本 WU 处理。

5. **`x-request-id` header name 变化的常规风险**：市场实践中 `x-request-id` 是事实标准，但个别 provider 可能使用变体。当前 case-insensitive 提取覆盖了常见大小写变体，但未覆盖完全不同的 header name。`client_correlation_id` fallback 在此场景下已足够用于厂商报障，且 terminal diagnostic 后缀会明确展示 `client_correlation_id=<id>`，不会给 operator 产生"有 provider id"的误导。

### 已排除的风险

6. **Static header 冲突**：`RunnerSpec.__post_init__` 已有 fail-fast 校验。`test_runner_spec_rejects_static_client_request_id_header` 覆盖了 Service assembly 路径。

7. **Provider 拒绝未知 header**：plan 明确列为 stop condition。实现阶段未发现证据表明默认配置的 provider 拒绝 `X-Client-Request-Id`。如果出现该问题，`client_correlation_policy` 仍可通过直接构造 `RunnerSpec(... DISABLED ...)` 关闭，只是不再作为 Service 默认。
