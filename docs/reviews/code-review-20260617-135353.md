## Findings

### 1-未修复-中-`_terminal_result_from_live_event` 共享 `seen_dedupe_keys` 域可能因非终态 dedupe_key 碰撞导致终态事件被静默抑制

- **入口/函数**: `_drain_available_watcher_items` → `_terminal_result_from_live_event`
- **文件(行号)**: `dayu/service/entrypoint_runtime.py:1012`
- **输入场景**: Host 发出的某个非终态 progress 事件的 `dedupe_key` 与后续同 Run 或不同 Run 的终态事件 `dedupe_key` 恰好相同（Host contract bug）。
- **实际分支**: `_terminal_result_from_live_event` 对所有经过的事件（含非终态）都会在 `state.seen_dedupe_keys` 中记录其 `dedupe_key`（行 1018）。后续任何事件（含终态）若 `dedupe_key` 已存在于该集合，`duplicate` 为 True（行 1012），直接 `return None`（行 1017），终态被丢弃。
- **预期行为**: 非终态事件的去重不应影响终态事件的到达判断；终态事件应仅按 `event_id` 去重（已有 `seen_event_ids`），或两域使用独立去重集合。
- **实际行为**: 若 Host 异常复用了 dedupe_key，终态被抑制，`_wait_for_terminal` 只能依赖 outbox 补读（若 outbox 也有同样 dedupe_key，则 outbox 路径 `_scan_outbox_terminal_items` 行 1138 也会因同键被 dedupe）。在极端情况下可能导致 `EntrypointRuntimeError("caught up without matching terminal item")`。
- **直接证据**: 行 1012 `duplicate = event.event_id in state.seen_event_ids or event.dedupe_key in state.seen_dedupe_keys`；行 1018 `state.seen_dedupe_keys.add(event.dedupe_key)` 在 `duplicate` 判断之后对所有事件（含非终态）执行。
- **影响**: 静默失效——Host contract bug 场景下终端用户得不到终态结果，且无直接诊断信号指出 dedupe_key 碰撞是根因。
- **建议改法和验证点**: 在 `_terminal_result_from_live_event` 中将终态去重的 dedupe_key 域与非终态分开（如仅当 `event.terminal_status is not None` 时才将 dedupe_key 写入用于终态去重的集合），或用另一个独立 set。验证点：构造非终态与终态共享 dedupe_key 的异常 Host 场景，确认终态不被抑制。
- **修复风险（低）**: 改动触及现有终端去重语义，需确认不影响 live→outbox 跨路径去重。
- **严重程度（中）**: 需要 Host contract bug 才能触发，但触发后影响严重（终态静默丢失），且 Slice B 增加了流经 `_terminal_result_from_live_event` 的非终态事件数量（此前非终态 progress 也被消费但仅被丢弃，现在增加了 activity 投影），略微放大了碰撞面。

### 2-未修复-低-`cancel_entrypoint_run_and_wait` 不支持 `on_activity` 参数

- **入口/函数**: `cancel_entrypoint_run_and_wait`
- **文件(行号)**: `dayu/service/entrypoint_runtime.py:579`
- **输入场景**: 用户在 running 状态按 Ctrl+C 触发 cancel，CLI 传入 `on_activity` 回调期望在 cancel 等待期间继续接收 activity 更新。
- **实际分支**: `cancel_entrypoint_run_and_wait` 签名不接受 `on_activity`，内部 `_wait_for_terminal` 调用（行 632）也未传入。
- **预期行为**: cancel 等待期间应继续推送 activity（如 TOOL_AWAITING、RUN_LIFECYCLE CANCELLING 等），与 `submit_entrypoint_turn_and_wait` 一致。
- **实际行为**: cancel 等待期间 activity 回调不会被调用，用户在 CANCELLING 状态下看不到任何进度反馈。
- **直接证据**: 行 632 `_wait_for_terminal(...)` 调用未传入 `on_activity` 参数；`submit_entrypoint_turn_and_wait` 行 565 传入了。
- **影响**: CANCELLING 状态下的 UI 静默——用户在请求取消到收到终态之间看不到任何 activity。
- **建议改法和验证点**: 设计决策——plan 中 Slice B 只要求改 `submit_entrypoint_turn_and_wait`。cancel helper 的 activity 支持可在 Slice E（interactive activity integration）中补齐。当前不视为 Slice B 的 defect，但需记录为已知缺口。
- **修复风险（低）**: 纯增量，不影响现有 cancel 行为。
- **严重程度（低）**: 按 plan scope 属于后续 Slice 的职责，不在 Slice B 允许变更范围。

### 3-未修复-低-activity callback 异常传播行为无测试覆盖

- **入口/函数**: `_emit_entrypoint_activity_from_host_event` → callback 调用
- **文件(行号)**: `dayu/service/entrypoint_runtime.py:817`
- **输入场景**: `on_activity` 回调内部抛出异常（如 renderer 状态异常、stderr 写入失败等）。
- **实际分支**: 行 817 `on_activity(...)` 直接调用，无 try/except 包裹。异常会向上透传经过 `_drain_available_watcher_items` → `_wait_for_terminal` → `submit_entrypoint_turn_and_wait`，导致整个 turn 失败。
- **预期行为**: 行为与现有 `on_run_accepted`（行 564）一致——回调异常透传，调用方负责保证回调安全。
- **实际行为**: 与 `on_run_accepted` 一致。
- **直接证据**: 行 817 及 docstring 行 807 明确声明 `:raises Exception: callback 抛出的异常会向调用方透传。`
- **影响**: 若 CLI renderer 实现有 bug，异常会导致 turn 失败而非优雅降级。但这是设计选择（fail-fast on programmer error），与已有 `on_run_accepted` 行为一致。
- **建议改法和验证点**: 要么补充测试验证该行为（如 mock callback 抛异常，验证异常透传），要么在后续 Slice CLI renderer 测试中覆盖此路径。当前测试未覆盖。
- **修复风险（低）**: 仅需补测试。
- **严重程度（低）**: 行为与既有模式一致，实际风险由 CLI renderer 的正确性决定。

## Residual Risk

1. **seq_dedupe_collision（低）**: `_terminal_result_from_live_event` 的 `seen_dedupe_keys` 与非终态共享域（见 Finding 1）。缓解：Host contract 保证 dedupe_key 唯一性；若 Host 遵守 contract，此风险不触发。
2. **cancel_no_activity（低）**: `cancel_entrypoint_run_and_wait` 不支持 `on_activity`（见 Finding 2）。缓解：plan 将 cancel activity 归入 Slice E；当前 cancel 仍正确返回终态，仅缺运行中 activity 反馈。
3. **callback_exception_untested（低）**: activity callback 异常传播未测试（见 Finding 3）。缓解：行为与 `on_run_accepted` 一致；CLI renderer 应在后续 Slice 保证回调简单且无异常。
4. **enum_sync_contract（低）**: `_entrypoint_activity_kind_from_host` / `_entrypoint_activity_status_from_host` / `_entrypoint_activity_severity_from_host` 使用 `raise AssertionError` 作为未覆盖枚举的兜底。若 Host 新增枚举值而 Service 未同步更新，将在运行时触发 AssertionError。缓解：两枚举均在同一 PR 的关联 Slice 中定义，类型检查可捕获大部分不匹配；AssertionError 比静默映射错误值更安全。
5. **outbox_terminal_dedupe_collision（低）**: `_scan_outbox_terminal_items` 与 `_terminal_result_from_live_event` 共享 `seen_dedupe_keys`。若 live 端已记录某非终态事件的 dedupe_key，outbox 中同键的终态 item 会被跳过（行 1138–1141）。缓解：outbox 仅包含终态 item，其 dedupe_key 与非终态事件不重叠。
