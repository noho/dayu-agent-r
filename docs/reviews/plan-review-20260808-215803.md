## Findings

### F20-RR5-DS-001-未修复-高-pre-compact compact分支不存在计划要求的runner-call manifest

- **位置**: plan §5.2第309–318、357–385行；§5.5第484–512行；§8 formal/trigger-proof self-test；binding goal success signal 2(a)。
- **问题类型**: 语义所有权 / 契约缺失 / 不可直接实施 / 测试缺口。
- **当前写法**: R2/R3每个pre-compact`ordinary`trigger都要求一个complete manifest，其kind为`initial_user_dispatch|followup_user_dispatch`，包含sizing snapshot并与budget fact、candidate projection、source refs/material exact binding；`trigger-proof.json`与private projection还要求该trigger的manifest ref/digest，并把ordinary/post_compact manifest互换纳入corruption matrix。
- **反例/失败场景**: 当ordinary decision为`compact_soft_threshold`时，Host不会dispatch该candidate，也不会生成Attempt/execution/dispatch identity或记录runner-call manifest。stock production CLI最终只留下attempt-free`CONTEXT_BUDGET_EVALUATED`及proactive compaction request/terminal。formal driver因此找不到计划要求的pre-compact manifest/ref/SHA；若自行构造一个，就把未dispatch的candidate伪装成runner-call事实，或者必须用被禁止的产品hook/private mutation补偿。
- **为什么有问题**: pre-compact candidate的owner contract与post-compact allow candidate不同。RR4正确拆开了stage/action语义，但计划仍把allow-only runner manifest contract强加给compact分支，导致trigger证据再次依赖不存在的durable fact。logical`candidate_input_projection_ref`不是runner-call manifest，也不承诺kind、sizing snapshot、source refs或payload可读取。
- **直接证据**:
  1. `dayu/host/dispatch.py:1984-1999`只在ordinary decision为`ALLOW_DISPATCH`时调用`_commit_dispatch_candidate_in_transaction`。
  2. compact/hard分支在`dayu/host/dispatch.py:2000-2009`仅追加`CONTEXT_BUDGET_EVALUATED`，且`attempt_id=None`、`execution_id=None`；随后进入compaction/failure路径，没有调用runner manifest recorder。
  3. `dayu/host/dispatch.py:2815-2888`明确把`record_prepared_runner_call_candidate_in_transaction`、complete sizing snapshot、Attempt/execution identities和start commit封装在allow-only`_commit_dispatch_candidate_in_transaction`中。
  4. `dayu/host/context_events.py:103-132`的durable budget payload只包含candidate cursor、logical projection ref、input digest、stage/policy/estimator/prediction/action等字段；没有runner-call kind、runner manifest ref/SHA、source refs或selected materials。
  5. 相比之下，accepted后的`post_compact + allow`确实走`_commit_dispatch_candidate_in_transaction`，所以post-compact和R4 allow manifest要求成立；问题只限pre-compact compact branch。
- **影响**: provider-free proof和formal publication无法同时满足冻结schema；正常成功trigger会因missing manifest被误判FAIL，或implementation Agent被迫发明下游manifest/重算shim，违反唯一owner、stock CLI和无产品修改约束。RR5当前不能进入Slice 1。
- **建议改法和验证点**:
  1. 将pre-compact trigger contract限定为产品实际持久化的canonical facts：attempt-free`CONTEXT_BUDGET_EVALUATED`的stage/cursor/candidate projection ref/input digest/prediction/action，加`CONTEXT_COMPACTION_REQUESTED`及同operation terminal linkage；不得要求runner-call manifest、kind、Attempt/execution/dispatch identity。
  2. 若provider-free场景仍需完整candidate/source/material审计，只能在冻结checkpoint经production candidate builder产生明确标为run-owned proof projection的artifact，并以input digest/ref与canonical budget fact exact equality；不得命名或发布为Host runner-call manifest。formal stock CLI只能使用其真实durable budget/request/terminal与compactor material facts，不能用proof artifact补成正式Host事实。
  3. 从`trigger-proof.json`与publication typed union中把pre-compact`manifest_ref/SHA`改为candidate/budget typed fields；post-compact与R4 allow继续要求真实runner manifest。corruption matrix应增加“为pre-compact compact分支伪造runner manifest”必FAIL，并保持pre-compact candidate digest冒充post-compact consumption必FAIL。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

## 已验证未退化项

- `_stage_pressure_action`直接支持三分型：ordinary soft→`compact_soft_threshold`；post_compact normal/soft→`allow_dispatch`、hard→`block_hard_threshold`；R4 ordinary allow与第三operation互斥。
- `_start_governed_after_compact`先Memory catch-up再以`POST_COMPACT`重建candidate；allow路径记录真实manifest并创建Run/Attempt/dispatch，hard路径在这些identity创建前fail closed。post-compact consumption contract本身已闭合。
- R4要求独立ordinary candidate消费第二次truth、allow且operation count=2；compact/第三operation只能bounded terminal后needs-more。corruption matrix已拒绝pre-digest冒充consumption与R4 compact冒充reconnect。
- Proof仍只经`HostDispatchScheduler.open`消费同一`HostLocalExecutionOptions.worker_factory/context_compactor`，两个ledger分离；OS sandbox独占process-tree deny，parent hook仅parent outbound；formal没有wrapper/interception/zero-call claim。
- Storage只采用repository API owner；materials/clean-seed隔离、global/allocation/active deadline、`99/73/73=245`、attempted/skipped publication union、terminal exact complement及last-writer均未退化。
