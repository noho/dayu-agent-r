### A1 设计判定

**判定：ACCEPTED，测试正确且无生产代码修改。**

- 不引入生产 hook：monkeypatch 仅作用于 `FsFinsIngestionJobStore` 的 public method，不触及 `FinsIngestionRuntime` 内部方法。
- 触发路径为既有 contract boundary：`_upload_terminal_disposition_from_job_record` 的 status 一致性检查是设计内校验，非测试专用代码。

- fake record 的不一致 status 模拟了投影层消费错误数据的最坏场景（corrupted in-memory record），比直接 monkeypatch `_emit_progress_event` 抛异常更贴近真实风险面。

## Findings

### 001-未修复-低-direct stream claim_upload_summary 后的 progress/result 投影无独立安全网

- **入口/函数**: `FinsIngestionRuntime._produce_direct_upload` (line 3374) → `_run_direct_stream_producer` (line 3190)
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:3434-3454, 3208-3241`
- **输入场景**: `claim_upload_summary` 成功设置 `_terminal_status` 后，`_emit_context_progress`（line 3439）或 `_emit_claimed_direct_result`（line 3446）因 queue full 或内部异常抛出。
- **实际分支**: 异常被 `_run_direct_stream_producer` catch 块（line 3210）捕获，调用 `_emit_direct_result(context, status=FAILURE, ...)`（line 3233）。该函数内部 `cancellation_state.claim_terminal(FAILURE)` 因 `_terminal_status is not None` 返回 None，无 RESULT emit。
- **预期行为**: 已 claim 的正确终态 RESULT 仍应 emit。
- **实际行为**: claim 已成功但 RESULT 静默丢失。stream consumer 等待 RESULT 超时或收到 stream close 无 RESULT。
- **直接证据**: `_DirectStreamCancellationState.claim_terminal` line 1515: `if self._consumer_aborted or self._terminal_status is not None: return None`；`_run_direct_stream_producer` line 3233 不区分"terminal 已被 claim"与"terminal 未 claim 但 claim 失败"。
- **影响**: 低——queue.put_nowait 在正常 buffer 容量内不抛异常，且该模式为既有 download/preprocess 同路径架构，非本 WU 引入。
- **建议改法和验证点**: 不要求在 S3 修复。可在后续 WU 中为 `_run_direct_stream_producer` 的 except 块增加 terminal-already-claimed 判别，当 `cancellation_state.is_terminal_claimed()` 时不覆盖 RESULT。
- **修复风险（低）**: 需增加 `_DirectStreamCancellationState` 的 terminal query 接口。
- **严重程度（低）**: 既有架构模式，非本 WU 引入，触发概率极低。
