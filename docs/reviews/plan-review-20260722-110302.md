## Findings

### 001-未修复-中-Host close 顺序中 scheduler 关闭与 pre-start work drain 的交互未明确

- **位置**: Section 5.4 "Host close顺序固定"
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: "registry drain/close全部attachment并释放mutex（scheduler仍活着让pre-start收口）→ scheduler close"。scheduler "活着让pre-start收口" 的含义是 scheduler 的 event loop task 仍在运行，但它没有说明 scheduler 自己的 `close()` 是否会等待 scheduler-owned task 完成。
- **反例/失败场景**: 若 scheduler 的 `close()` 立即 cancel 其所有 task，而某个 pre-start governance 正在 `_promotion_drain_loop` 中执行 proactive compaction（事务外 provider call），cancel 会中断该 provider call。虽然 EventLog 已 append `CONTEXT_COMPACTION_REQUESTED`，但 provider result 不会写回。这本身不是 correctness 问题（fresh RW attach 可恢复），但它让 "scheduler仍活着让pre-start收口" 的保证落空 — scheduler 实际上没有让 pre-start 完成，而是 cancel 了它。
- **为什么有问题**: 当前代码中 `HostDispatchScheduler.close()` 确实会 cancel 其 `_critical_tasks`。plan 声称 "scheduler仍活着让pre-start收口"，但未说明 scheduler close 如何与 in-flight pre-start work 交互。若 implementation agent 按字面理解实现，可能在 actor stop 之后才 close scheduler，导致 scheduler task 在 actor 已停止时尝试 durable write 失败。
- **直接证据**:
  - Plan Section 5.4: "registry drain/close全部attachment并释放mutex（scheduler仍活着让pre-start收口）→ scheduler close → terminal/delivery/projection/actor handle/executor/store close"
  - 当前 `HostDispatchScheduler` 有 `_critical_tasks` set，close 时 cancel 并 join
  - proactive compaction 的 provider call 在事务外执行（`run_compaction_operation` 使用 `compactor` 参数调用外部 LLM）
- **影响**: 实现 agent 可能创建一个 Host close 顺序，其中 scheduler cancel 了正在执行的 pre-start work，导致 provider call 中断。虽然 durable state 一致（request 已 commit），但 "scheduler 收口 pre-start" 的语义不成立。
- **建议改法和验证点**: plan 应明确：(a) scheduler close 必须先 signal 不再接受新 promotion/wake，然后 join 已入队的 promotion task，使其自然完成当前 pre-start work；或 (b) 如果选择 cancel pre-start work，应明确说明这是可接受行为，且 fresh RW attach 的 incomplete operation recovery 会处理残留状态。验证点：测试 Host close 期间有 in-flight proactive compaction 时，fresh reattach 能否以同 operation id 恢复。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 002-未修复-低-Slice 2 范围大但 completion signal 未覆盖所有受影响测试

- **位置**: Section 7, Slice 2 "Tests / expected assertions" 与 "Completion signal"
- **问题类型**: 测试缺口
- **当前写法**: Slice 2 allowed test 列表包含 30+ 测试文件。completion signal 只列了 focused 矩阵与 "无 `StartupRecovery*` 生产符号"，未逐文件确认现有测试是否需要更新。
- **反例/失败场景**: `test_phase5_local_execution_integration.py`、`test_phase7_waiting_integration.py`、`test_transient_delta_stress.py`、`test_host_production_stress.py`、`test_transient_delivery_interruption_path.py` 等集成测试可能不直接调用 mutation，但其 `open_host` fixture 可能隐式依赖 startup recovery 行为。Slice 2 删除 startup recovery 后，这些测试可能静默通过但不再覆盖预期行为。
- **为什么有问题**: 控制文档要求 "测试必须跟着实现边界迁移"。如果 Slice 2 的 completion signal 不逐项确认每个受影响测试的更新状态，implementation agent 可能遗漏需要更新的测试。
- **直接证据**: 当前 `test_recovery_multiprocess.py` 测试 startup recovery 在 `open_host` 后立即生效。Slice 2 将 recovery 移到 `attach_session`，该测试的 recovery 触发点将改变。
- **影响**: 低。completion signal 已有 "pyright 对本 slice 通过" 和 focused tests，但缺少逐测试确认。
- **建议改法和验证点**: 在 Slice 2 completion signal 中增加："所有 listed test 文件中调用 `open_host` 的 fixture/helper 已确认 recovery 行为迁移正确；不直接调用 mutation 的测试证明 `open_host` 本身无 Session 治理副作用"。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 003-未修复-低-`dispatch.py` 已 5110 行，plan 进一步增加职责

- **位置**: Section 6 affected files, `dayu/host/dispatch.py`
- **问题类型**: 过度耦合 / 最佳实践偏离
- **当前写法**: plan 在 `dispatch.py` 中增加：(a) mandatory eligibility check、(b) owned-session periodic reconcile、(c) proactive state consumption、(d) attempt owner cancel reconcile、(e) scoped watchdog。
- **反例/失败场景**: `dispatch.py` 已有 5110 行，是项目中最大的单一生产文件。继续向其中添加 eligibility、reconciliation 和 scoped watchdog 逻辑会加剧 God function / God module 风险。虽然 plan 引入了 `session_attachment.py` 和 `proactive_compaction.py` 两个新模块来分离关注点，但 dispatch.py 仍然承担了 scheduler eligibility gate、periodic reconcile loop、cancel reconcile 和 watchdog scoping 等多项新职责。
- **为什么有问题**: 控制文档 11.2 风险 6 已指出 "大型现有 scheduler 文件：修改集中但不得继续把 registry/proactive projection 塞入 `dispatch.py`"。plan 引入了新模块但仍在 dispatch.py 中增加大量新逻辑。
- **直接证据**: `dispatch.py` 当前 5110 行。plan 的 Slice 2 和 Slice 4 都修改该文件。
- **影响**: 低。当前 plan 的新模块设计已经缓解了大部分风险，但 dispatch.py 的增长趋势值得关注。
- **建议改法和验证点**: review 阶段关注 dispatch.py 的新增函数是否可提取到 `session_attachment.py` 或 `proactive_compaction.py`。不作为 plan blocker。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 004-未修复-中-periodic reconcile 的测试设计未明确

- **位置**: Section 5.5 "scheduler-owned periodic loop"
- **问题类型**: 测试缺口
- **当前写法**: plan 描述了 periodic reconcile 的行为（每 `dispatch_poll_interval_seconds` 从 registry 获取 ACTIVE RW Session id 快照，投递去重 promotion/accepted reconciliation），但未在任何 Slice 的 tests/assertions 中列出 periodic reconcile 的具体测试场景。
- **反例/失败场景**: plan 的 success signal 要求 "A terminal后A不promotion，B在poll bound内promotion且不takeover旧Attempt"。但测试如何验证 "poll bound 内" 的行为？如果测试依赖 `dispatch_poll_interval_seconds` 的真实等待，测试会很慢；如果使用确定性 gate，plan 应说明 gate 机制。
- **为什么有问题**: Section 11.2 风险 4 提到 "测试必须使用确定性gate和明确上界，不能依赖sleep碰运气"，但未说明具体 gate 机制。implementation agent 需要知道如何测试 periodic reconcile 的时序行为。
- **直接证据**: plan Section 5.5: "registry closing后Session立即离开快照，旧scheduler不得推进下一Run"。plan Section 11.2 风险 4: "poll-based cross-opener liveness...测试必须使用确定性gate"。
- **影响**: 中。如果测试设计不明确，implementation agent 可能写出 flaky 测试或遗漏时序边界测试。
- **建议改法和验证点**: 在 Slice 2 或 Slice 4 的 tests/assertions 中明确 periodic reconcile 测试策略：(a) 通过注入可调 clock 或 mock poll interval 实现确定性 gate；或 (b) 使用 event-driven signal（如 registry state change event）触发 reconcile，而非 timer。验证点：A detach 后 B 的 scheduler 在确定性条件下（非 sleep）推进 queued work。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 005-未修复-低-`max_proactive_compactions_per_run` 删除是 breaking config change

- **位置**: Section 5.7, Slice 3, Section 11.2 风险 5
- **问题类型**: 最佳实践偏离（已知）
- **当前写法**: plan 在 Slice 3 删除 `max_proactive_compactions_per_run` 字段链，并明确 "旧 config 字段被 packaged/workspace strict schema 拒绝"。
- **反例/失败场景**: 现有用户的 workspace `execution_profiles.json` overlay 若包含 `max_proactive_compactions_per_run`，升级后 config 加载将失败。plan 已在 11.2 风险 5 中承认这是 fresh schema boundary，但未说明升级路径。
- **为什么有问题**: 这不是 plan 缺陷，而是已知的 breaking change。plan 正确选择了 fresh schema 而非兼容 parser。但 implementation agent 应确保错误消息清晰，帮助用户理解哪个字段被拒绝。
- **直接证据**: `dayu/config/execution_profiles.json` 四个 profile 均包含 `max_proactive_compactions_per_run: 2`。`dayu/runtime/config_loader.py` 的 `_parse_context_budget` 使用 `_require_positive_int_field` 解析该字段。
- **影响**: 低。已由 plan 风险 section 覆盖。
- **建议改法和验证点**: Slice 3 的 tests 应覆盖 "包含旧字段的 workspace config overlay 产生清晰的 rejection error message"。plan 已在 tests 中提到此场景，确认覆盖即可。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
