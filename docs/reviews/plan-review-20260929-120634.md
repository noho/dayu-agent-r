## 3. Findings

### 1-未修复-高-`XbrlTaxonomyInput.layout` 枚举无法表达真实财报所需的「相对树 + catalog zip 同根」混合形态，F3 轮廓对 goal 3 主路径不可实施

- **位置**: 计划 §3「taxonomy/sidecar 最小接口轮廓」：`XbrlTaxonomyInput(taxonomy_root: Path, layout: Literal["relative_tree", "zip_catalog"])` 及两 layout 定义句；§2 F3 行「接口轮廓可审」；§5 P0-B 真实正样本步骤。
- **问题类型**: 契约缺失 / 不可直接实施 / 过度耦合（把 Docling 单目录混合能力裁成互斥两态）。
- **当前写法**: `relative_tree`「要求受信根下保留 schemaRef 的相对 XSD/linkbase 布局」；`zip_catalog`「要求 root 是目录，其中一份指定顶层 `.zip` 含 `META-INF/taxonomyPackage.xml` 和 `META-INF/catalog.xml`，catalog 映射绝对 URI」；二者为互斥 `Literal`。
- **反例/失败场景**: P0-B 取得真实合规财报 instance（例如 AAPL 同构：instance 的 `schemaRef` 是相对 `aapl-20240928.xsd`，该 XSD 又 `import` 10 个绝对 `https://` SEC/FASB/XBRL taxonomy——本仓库 fixture 实测如此）。`relative_tree` 布局下绝对 import 在 `workOffline=True` 无 catalog 时离线不可解析；`zip_catalog` 布局下相对 `schemaRef`/linkbaseRef 按 instance 基 URI（临时目录）解析，落不到 zip 内（OASIS catalog 只能映射稳定 URI 前缀，映不了每次变动的临时目录基路径）。两种互斥布局各自失败，实施者被迫临场改枚举或误记「goal 3 blocked: 样本转换失败」——把接口缺陷伪装成样本/转换失败，正是 evidence slice 最坏的假证据归因。
- **为什么有问题**: Docling 2.127.0 的 `taxonomy` 选项本身就是**单目录混合形态**：`backend_options.py:505-521` 原文为「include schemas (`.xsd`) and linkbases (`.xml`) referenced … in their relative locations. Optionally, it can also include taxonomy packages (`.zip`) referenced … with absolute URLs and mapped … with a taxonomy catalog」；`xbrl_backend.py:125-148` 对同一 copytree 目录既取散文件又收集顶层 zip。计划 §3 转述了这套机制（「整树 copytree，收集顶层合法 zip」），却把输入形态裁成互斥两态，与自己的源码转述矛盾。goal 成功信号 3 的真实财报正样本恰是相对+绝对混合引用形态，F3 的「接口轮廓可审」在此主路径上不成立；MiMo 上轮 F2 要求 plan 层冻结接口轮廓的全部意义就是提前暴露这类设计缺口。
- **直接证据**: 计划 §3 两 layout 定义句；`tests/fins/fixtures/aapl_xbrl/fil_0000320193-24-000123/aapl-20240928.xsd` 的 10 个绝对 `schemaLocation`（`https://xbrl.sec.gov/ecd/2024/ecd-2024.xsd` 等）与 4 个相对 `linkbaseRef`；Docling `docling/datamodel/backend_options.py:509-521`、`docling/backend/xml/xbrl_backend.py:125-148`；probe P3 已证工作 Offline 下绝对 URL 无 catalog 不可解析、相对引用靠临时目录布局解析。
- **影响**: P0-B 真实正样本步骤产假性 blocked 归因 / 实施期重开已宣称「可审」的接口（F3 未真正闭合）/ goal 3 的证据链被接口缺陷污染。
- **建议改法和验证点**: 把 layout 改为可组合形态：或第三值 `relative_tree_with_catalog_zip`，或 `relative_tree` 显式允许并要求「恰一份指定顶层 catalog zip」与散文件共存（Docling 原生形态），并写明各自解析分工——相对 schemaRef/linkbase 走散文件布局、绝对 URL import 走 zip catalog 映射；P0-B 真实样本步骤指明使用该组合形态。验证点：用 AAPL 同构引用图（相对 schemaRef + 绝对 import + 相对 linkbase）的合成样本在 Arelle 离线 `--validate --validationExitCode` exit 0，再进 Docling 对照。
- **修复风险（低/中/高）**: 低（接口表述修订 + 一条合成验证，不动产品）。
- **严重程度（低/中/高/严重）**: 高。

### 2-未修复-中-P0-A 的 pin 选取完成判据在三平台 runner blocked 下有二义，可致永久停摆或 macOS 充数 pin

- **位置**: 计划 §5 P0-A：「对 2.45.3/2.44.8 做有依赖安装、`pip check`，留…再选生产 pin」＋「Linux/Windows runner…目前各记 `blocked: runner unavailable`」＋「每个平台须有独立真实安装证据；交叉解析仅辅助，不用 macOS 充数」；§5 末「若 P0-A/B/C 以后全 pass，另写可执行 implementation plan」。
- **问题类型**: 状态机漏洞 / 不可直接实施（完成态未定义）。
- **当前写法**: 一方面要求「每个平台须有独立真实安装证据」，另一方面 runner 缺失只记 blocked；未定义在 Linux/Windows 持续不可得时 pin 是否允许选定、P0-A 记 pass 还是 blocked、由谁裁决。

- **影响**: gate 状态不可审计 / 永久停摆 / 或产出仅 macOS 验证的锁冒充三平台支持。
- **建议改法和验证点**: P0-A 明确部分完成规则，例如「macOS 真实安装 + `pip check` 完成即记 `P0-A: macos-pass; linux/windows blocked: runner unavailable`，生产 pin 选取可基于 macOS 证据先行但锁文件分平台更新须待各平台真实安装后才记支持；runner 持续不可得超期即回 goal/总控裁决平台承诺收窄」。验证点：P0-A 决策记录逐平台标注 pass/blocked 与 pin 依据，gate 状态词表闭合。

### 4-未修复-低-P0-B 把无外部依赖的自足机制探针排在许可盘点之后，外部阻断会无谓拖住 zip+catalog 可用性实测

- **位置**: 计划 §5 P0-B：「**先**以许可清晰的管理员来源盘点 SEC/FASB/XBRL 传递闭包、逐 URL→本地映射及 digest。重跑本轮自包含裸目录相对样本；再构造最小合法顶层 zip+catalog…」。
- **问题类型**: 切片过粗 / sequencing 缺陷。
- **当前写法**: 许可/闭包盘点（外部资源、许可审查、SEC 抓取合规）置于最前，自足合成样本的裸目录重跑与 zip+catalog 构造排在其后。
- **反例/失败场景**: SEC/FASB 许可或抓取合规审查停滞（外部资源阻断），P0-B 整段排队；而 zip+catalog 可用性——计划 §2 F7 行自认「未测 zip 不承诺可用」、§7 未证清单明列的缺口——本来只需合成文件即可实测，被无谓延后；F7 的修复意图（形态/成本实测）反而最后才动。

### 5-未修复-低-§4「最低安全承诺」的网络措词窄于 §6 矩阵与平台表的零出站验证口径，存在按措词实现出真实网络绕过面的空间

- **严重程度（低/中/高/严重）**: 低。

### 6-未修复-低-C0–C7 矩阵只覆盖 schemaRef/catalog/zip 形态逃逸，未列非 schemaRef 读取向量，「OS trace 无越界」只对被尝试的逃逸成立

- **位置**: 计划 §6「C0–C7」场景清单。
- **问题类型**: 测试缺口（验证矩阵覆盖不全）。
- **当前写法**: C1–C5 覆盖 `file:`/绝对路径/`../`/HTTP(S)/编码变体，C6 覆盖 symlink/hardlink/reparse/zip 内路径/catalog 重定向，C7 覆盖 Windows 名称形态；未列 DOCTYPE/ENTITY（XXE 式读取）、XInclude/XSLT import、非 `file/http` scheme、Arelle 插件/扩展加载面。
- **反例/失败场景**: 一个只拦截 schemaRef/linkbaseRef 形状引用、OS profile 又留有缺口的实现通过 C0–C7（所有被试逃逸都拒绝、trace 无越界），但 instance 内嵌 `<!DOCTYPE … ENTITY … SYSTEM "file:///…">` 或其它向量的读取未经尝试、无从发现；「OS trace 无越界」是全称承诺，却只由有限枚举尝试支撑。
- **为什么有问题**: 矩阵是 P0-C 与后续 owner 测试的**共同验收真源**（§6 自述），其枚举即验证边界；漏一类向量等于该向量的强制从未被验证。OS 级 trace 判据本身向量无关，但未尝试的逃逸不会出现在 trace 里。
- **直接证据**: 计划 §6 C0–C7 原文（无 DOCTYPE/ENTITY/XInclude/plugin 项）；probe P3 已证绕过可经任意引用机制发生（合成 `file:` schemaRef 即成功加载根外 XSD），机制不限于 schemaRef。
- **影响**: 隔离验证对漏列向量不设防 / 假实现可通过矩阵 / 安全承诺超出手段证明范围。
- **建议改法和验证点**: C 矩阵补 C8（或并入 C6）「非 schemaRef 读取向量：DOCTYPE/ENTITY、XInclude、样式/链接导入、非常规 scheme」，并在 P0-C 的 OS trace 判据写明「对全部尝试向量均无根外读取/出站」；后续 owner 测试同源引用。验证点：每个新增向量有最小合成样本与预期拒绝行为。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。

### 7-未修复-低-「workspace 外受控根」不变量与 provenance 记录无校验 owner 与拒绝行为，运行时校验枚举不含该项

- **位置**: 计划 §3「管理员来源须是 workspace 外受控根，记录来源、许可、SHA、完整相对布局；只接普通文件，拒绝 symlink/hardlink/特殊文件、重复或不规范路径，限制文件数、总字节、zip 展开比与临时占用」；CLI `--xbrl-taxonomy-root <绝对管理员路径>`。
- **问题类型**: 契约缺失 / 语义 owner 漂移风险。
- **当前写法**: 「workspace 外」是祈使句不变量，「记录来源、许可、SHA」无归属者；紧随的运行时校验枚举（普通文件/symlink/数量/字节/展开比）不含「必须绝对、必须在 workspace 外」的检查，也未写明违反时拒绝还是仅告警。
- **反例/失败场景**: 管理员（或冒充管理员的调用）把 `--xbrl-taxonomy-root` 指进 workspace 内用户可写目录；Documents runtime 按枚举校验通过，用户随后替换目录内容（或在两次调用间改写），受信输入树实际不可信；「记录来源/许可/SHA」若只是口头纪律，审计记录缺失，与计划 §3 自己要求「记录…SHA」的意图脱节。
- **为什么有问题**: 计划 §1 owner 纪律要求不变量有唯一 owner；`dayu.documents.docling_runtime` 拥有「taxonomy 输入校验与运行边界」（§1 已定），则「绝对路径 + workspace 外 + provenance 记录」必须落进该校验契约，否则不变量处于无主状态。与「禁止用下游 fallback 补救」同理，信任边界校验不能靠管理员自觉。
- **直接证据**: 计划 §3 原文两处（不变量句 vs 校验枚举句）；§1 owner 划分句；CLI 参数句。
- **影响**: 信任边界绕过（用户可写树冒充受信 taxonomy）/ 审计记录缺失 / owner 契约不闭合。
- **建议改法和验证点**: §3 校验枚举补「路径必须为绝对规范路径且位于 workspace 外，违反即拒绝」；provenance 记录指定 owner（管理员侧受控清单由运维保留、或 Documents runtime 转换日志登记 root SHA 布局 digest，二选一写明）。验证点：未来实施计划的 Documents runtime 校验契约含该拒绝分支及测试。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。

## 7. 结论

**fail**（最小修复后可快速重审）。

理由：修订版的诚实度与证据纪律显著提升——版本矛盾纠偏、typed/explicit 两支分离、S1/S2 未证承诺撤下、三平台 blocked 出口与「不以 macOS 冒充」硬边界、探针一手证据（哈希逐项复核吻合）都成立；停止条件中「无真实隔离机制仍声称支持通过」未触发（计划明确当前全部 blocked）。但作为其自称交付物——P0 evidence slice 的可执行规格——存在一个高等级结构性缺陷：§3 接口轮廓的 layout 枚举无法表达真实财报「相对引用 + 绝对 import catalog 映射」的混合形态（仓库 AAPL fixture 即此形态，Docling 原生单目录混合能力被裁成互斥两态），P0-B 真实正样本步骤将产出假性「转换失败/样本不可用」归因，F3「接口轮廓可审」不成立；叠加 P0-A pin 完成态二义（可致永久停摆或 macOS 充数 pin）与 P0 证据留存位置缺失（重演 E01 证据丢失争议），当前形态交 P0 执行会产生不可审计 gate 状态与污染的证据链。按 planreview 口径，一个在核心验收路径上产假证据的 evidence 计划不能 pass。
