- **入口/函数**: `dayu/host/durable/tool_trace.py` 的模块级 import
- **文件(行号)**: `dayu/host/durable/tool_trace.py:17`
- **输入场景**: 任何触发 `durable/tool_trace.py` 模块加载的代码路径
- **实际分支**: `from dayu.host._runner_call_manifest import (RunnerCallHotAtoms, RunnerCallHotDiagnostic, parse_runner_call_hot_payload, parse_runner_call_manifest, ...)`
- **预期行为**: durable 层作为 Host 的基础存储层，依赖只能沿 `UI -> Service -> Host -> Engine` 主链路向下发生（`dayu/README.md` line 8）。durable 层应只依赖 `dayu.contracts`、`dayu.host.durable.*` 和标准库
- **实际行为**: `durable/tool_trace.py` import 了 `dayu.host._runner_call_manifest`，该模块自身 import 了 `dayu.engine.contracts.engine_events` 和 `dayu.host.context_budget`，形成 durable → host-private → engine 的反向依赖链
- **直接证据**:

  - `dayu/host/_runner_call_manifest.py` imports `dayu.engine.contracts.engine_events`

- **建议改法和验证点**: 把 `RunnerCallHotAtoms` / `parse_runner_call_hot_payload` 等类型和解析逻辑下沉到 `dayu.contracts` 或 `dayu.host.durable` 内部，使 durable 层不再 import host-level 私有模块；或在 `_runner_call_manifest` 中将 engine-facing 类型与 durable-facing 解析逻辑分离

### 2-未修复-中-Service 与 Host contracts 路径布局常量重复定义

- **入口/函数**: `dayu/service/tool_trace_analysis.py` 路径发现逻辑
- **文件(行号)**: `dayu/service/tool_trace_analysis.py:31-36` vs `dayu/host/tool_trace_analysis_contracts.py:35-40`
- **输入场景**: 任何涉及 workspace/directory 模式路径发现的场景
- **实际分支**: Service 定义 `_DAYU_DIRECTORY_NAME = ".dayu"` 等 6 个私有常量；Host contracts 定义相同的 6 个常量
- **预期行为**: 路径布局的 source of truth 应唯一。Service 做路径发现、Host 做 Source 校验，但路径常量值应从同一公共来源派生
- **实际行为**: 两个模块各自独立定义相同的路径布局字符串常量，无共享机制

- **建议改法和验证点**: 统一使用 `stat()` 语义，使 Service 的候选检查与 Host 的严格校验一致
