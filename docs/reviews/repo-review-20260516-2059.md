### 1-高-RuntimeFileLock 嵌套上下文管理器导致 token 泄漏

- **入口/函数**: `RuntimeFileLock.__enter__` / `RuntimeFileLock.__exit__`
- **文件(行号)**: `dayu/runtime/filelock.py:169-198`
- **输入场景**: 同一 `RuntimeFileLock` 实例在嵌套 `with` 块中使用（可重入场景）
- **实际分支**: 内层 `__enter__` 覆盖 `_active_token` 为 token2，外层 token1 引用丢失；内层 `__exit__` 释放 token2 并将 `_active_token` 设为 None；外层 `__exit__` 检测到 `_active_token is None` 静默跳过释放
- **预期行为**: 嵌套使用应被检测并拒绝，或 token1 应被正确保留和释放
- **实际行为**: token1 永不释放，持有的 OS 级文件锁在进程退出前一直有效
- **直接证据**: 第 176-178 行 `__enter__` 无条件调用 `acquire()` 并赋值 `_active_token`；第 195-198 行 `__exit__` 读取 `_active_token` 后置 None 并释放。嵌套场景没有重入检测。
- **影响**: OS 级文件锁泄漏，阻塞其他进程获取同一锁，可能导致跨进程互斥失效
- **建议改法和验证点**: 在 `__enter__` 中检测已存在 `_active_token` 并抛出 `RuntimeError`；或使用计数机制支持重入。补测嵌套 `with` 场景。
- **修复风险（低）**: 紧耦合路径，修改范围小
- **严重程度（高）**

### 3-中-`RuntimeFileLock._active_token` 在 `acquire()` 中未校验，混合 API 调用可产生重叠锁获取

- **入口/函数**: `RuntimeFileLock.acquire`
- **文件(行号)**: `dayu/runtime/filelock.py:139-167`
- **输入场景**: 调用方混用上下文管理器 API 和显式 `acquire()`/`release()` API
- **实际分支**: `acquire()` 无条件创建新 `RuntimeFileLockToken` 并返回，不检查 `_active_token`。显式 `acquire()` 获取 token1 后再通过 `with lock:` 进入上下文管理器获取 token2，产生两个活跃 token 对应同一底层 FileLock
- **预期行为**: 应检测已有活跃 token 并拒绝或使用同一 token
- **实际行为**: 两个 token 各自持有同一锁的引用，释放其中一个后另一个仍认为持有锁但 OS 级锁已释放
- **直接证据**: `acquire()` (line 139) 无 `_active_token` 守卫；`__enter__` (line 176) 无条件覆盖 `_active_token`
- **影响**: 锁语义被破坏，调用方可能在不持有锁的情况下执行临界区代码
- **建议改法和验证点**: 在 `acquire()` 中检测已有活跃 token 并抛出 `RuntimeError`；或实现引用计数
- **修复风险（低）**: 紧耦合路径
- **严重程度（中）**

### 5-中-`after_commit` callbacks 链在第一处异常中断，后续 callback 静默丢失

- **入口/函数**: `_run_after_commit`
- **文件(行号)**: `dayu/host/durable/transaction.py:324-339`
- **输入场景**: `run_write` 传入多个 `after_commit` callbacks（如 `(notify_scheduler, trigger_wakeup)`），第一个 callback 抛出异常
- **实际分支**: `_run_after_commit` 在首次 `callback()` 抛异常时循环终止，后续 callback 永不执行
- **预期行为**: 所有 callback 都应被尝试执行（best-effort），或至少记录哪些已执行
- **实际行为**: 首个异常导致后续 callback 静默跳过，此时 COMMIT 已成功、锁已释放
- **直接证据**: line 332-339: `for index, callback in enumerate(callbacks):` 内 `callback()` 失败 → `raise HostAfterCommitError` → 循环终止
- **影响**: 如果业务逻辑依赖 after-commit 触发队列推进、poller 唤醒等，某个 callback 异常导致下游 callback 静默丢失
- **建议改法和验证点**: 收集异常并在循环结束后统一抛出，或逐个 try/except 保证每个 callback 被尝试
- **修复风险（中）**: 改变异常抛出语义，需检查所有依赖 `after_commit` 的调用方
- **严重程度（中）**

## Residual Risk

1. **RuntimeFileLock 重入**: 嵌套上下文管理器场景未被测试覆盖（Finding 1），且 `_active_token` 机制在混合 API 使用下缺乏防护（Finding 3）。
2. **SSE parser 错误路径一致性**: 四个错误终止路径均不设置 `_finish_reason=ERROR`，代码依赖外层 `parse()` 的 `if self._terminated: return` 间接防护，但此防护未在测试中显式验证。重构风险存在。
3. **大规模 wait record 场景**: `read_wait_records_for_poll_observation` 无 LIMIT，CANCELLED record 无终态，两者组合在大规模部署或突发取消场景下可能导致 poll 性能退化。当前测试未覆盖此类场景。
4. **幂等重放状态一致性**: awaiting accept 和 tool fact accept 的幂等重放路径跳过状态重校验（Finding 8），依赖事务隔离性和 EventLog 不变性。在异常恢复场景（崩溃后重试 + 期间状态由并发操作改变）下的行为未在测试中覆盖。
5. **测试缺口**: 888 个测试全部通过，pyright 0 errors，但全仓审查发现以下未充分覆盖的测试面：
   - 嵌套/重入 RuntimeFileLock 使用（零点覆盖）
   - SSE parser 双重终结防护验证（零点覆盖）

   - after_commit 多 callback 异常恢复（零点覆盖）
   - WaitPoller 非 RuntimeError 异常处理（零点覆盖）
   - 大 event volume 下 projection catch-up 性能边界（零点覆盖）
