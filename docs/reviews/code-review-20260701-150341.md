## Findings

### 01-未修复-中-_DirectWaitPollerFactory-默认复用构造线程-transaction-runner-后台线程-unsafe

- **入口/函数**: `WaitPollerSupervisor.__init__` → 默认 `_DirectWaitPollerFactory` → `_poll_once` → `create_wait_poller`
- **文件(行号)**: `dayu/host/wait_adapter.py:1104-1116`（默认 factory 构造）、`wait_adapter.py:1250-1257`（`_poll_once` 调用 factory）、`wait_adapter.py:404-432`（`_DirectWaitPollerFactory` 定义）
- **输入场景**: 调用方构造 `WaitPollerSupervisor` 时未传 `poller_factory`，随后调用 `open()` 启动后台 daemon 线程。后台线程通过默认 `_DirectWaitPollerFactory.create_wait_poller()` 创建 `WaitPoller`，传入 supervisor 构造时所在线程的 `HostTransactionRunner`。
- **实际分支**: `_DirectWaitPollerFactory` 在 `__init__` 中存储 `self.transaction_runner`（第 408 行，来自 supervisor 构造线程），在 `create_wait_poller`（第 423 行）将其传给 `WaitPoller.__init__`。`open()` 方法（第 1142-1148 行）在 daemon 线程中运行 `_run_loop` → `_poll_once` → `create_wait_poller`。若 supervisor 构造线程与后台 daemon 线程不同（生产环境几乎必然如此），后台线程持有的 `HostTransactionRunner` 包装了另一线程的 `sqlite3.Connection`。
- **预期行为**: SQLite 连接默认 `check_same_thread=True`，跨线程使用会抛出 `sqlite3.ProgrammingError`。后台线程必须持有自己线程内创建的 SQLite connection / `HostTransactionRunner`。Slice 3 `open_host` wiring 通过提供自定义 `WaitPollerFactory` 来保证这一点。
- **实际行为**: 默认 `_DirectWaitPollerFactory` 跨线程传递 `transaction_runner`，无运行时防护。若调用方（Slice 3 集成者或直接使用 supervisor API 的代码）不传 `poller_factory` 而直接调用 `open()`，会在后台线程首次 `run_write` 时触发 `sqlite3.ProgrammingError`。
- **直接证据**:
  1. `_DirectWaitPollerFactory` 第 408 行存储 `transaction_runner: HostTransactionRunner`，第 423 行原样传给 `WaitPoller`
  2. `WaitPollerSupervisor.__init__` 第 1104-1116 行：`poller_factory is None` 时创建 `_DirectWaitPollerFactory(transaction_runner=transaction_runner, ...)`
  3. `open()` 第 1142-1148 行：`threading.Thread(target=self._run_loop)` — 后台线程
  4. `_run_loop` 第 1250-1257 行：`self._poller_factory.create_wait_poller(self)` — 在后台线程中调用
  5. docstring 第 1088-1089 行标注了此限制："后台线程需要由 factory 提供线程内可用的 durable runner"
  6. 所有后台线程测试均提供了自定义 `_HandlePollerFactory`（test_wait_poller_runtime.py 第 123-169 行），避免了此问题
- **影响**: 静默失效 — 直接使用默认 factory 的 `open()` 路径在首次 durable 操作时崩溃，抛出 `sqlite3.ProgrammingError`。不影响 Slice 2 测试（测试始终提供自定义 factory），但构成 Slice 3 调用方的 footgun。
- **建议改法和验证点**:
  1. 将 `poller_factory` 改为 `open()` 方法参数而非 `__init__` 参数，`__init__` 只保留无线程亲和性的组件（policy、clock），构造时不需要 `transaction_runner`。或者：
  2. 保持当前 API，但在 `open()` 开头检查 `poller_factory` 是否来自默认 `_DirectWaitPollerFactory`，若后台线程创建时检测到默认 factory，发出 warning 或直接 raise。或者：
  3. 接受当前设计，但在 `WaitPollerSupervisor` class docstring 和 `open()` docstring 中更显式标注默认 factory 仅限单线程场景，后台线程必须提供自定义 factory。Slice 3 `open_host` integration 必须在 wiring 中显式传递 `poller_factory`。
- **修复风险（低）**: 选项 3 仅需 docstring 补充；选项 1/2 涉及 API 调整，需同步更新测试。
- **严重程度（中）**: 不影响 Slice 2 测试正确性，但默认 API behavior 在生产路径下必然失败，docstring 警告不足以防止 Slice 3 wiring 出错。

### 02-未修复-低-WaitPollerSupervisor-构造函数冗余参数

- **入口/函数**: `WaitPollerSupervisor.__init__`
- **文件(行号)**: `dayu/host/wait_adapter.py:1067-1121`
- **输入场景**: Slice 3 `open_host` 构造 supervisor 时提供自定义 `poller_factory`
- **实际分支**: 当 `poller_factory is not None` 时，`transaction_runner`（第 1097 行）、`adapter_registry`（第 1098 行）、`resolver`（第 1099 行）、`context`（第 1100 行）、`clock`（第 1102 行）仅用于传给默认 `_DirectWaitPollerFactory`（第 1105-1115 行）。这些参数在自定义 factory 路径成为死参数——它们被存储在 `self._transaction_runner` 等实例属性中但从未被读取。
- **预期行为**: 构造函数参数应只包含无论 factory 路径都需要的值（policy、owner_id），加上可选的 factory。当前所有 adapter/resolver/context/runner 参数在两个路径中之一会成为死参数。
- **实际行为**: Slice 3 调用方需要传递 6 个仅被默认 factory 使用的参数，即使它提供了自定义 factory。参数存在但不被消费，增加了调用方的认知负担和误传风险。
- **直接证据**:
  1. `self._transaction_runner` 第 1097 行被赋值，但在类中无其他读取点（仅在 `__init__` 中传给默认 factory）
  2. `self._adapter_registry`、`self._resolver`、`self._context`、`self._clock` 同理
  3. `_poll_once`（第 1250-1257 行）仅通过 `self._poller_factory` 创建 poller，不读取上述字段
- **影响**: maintainability — Slice 3 集成时需理解哪些参数实际被消费，容易误传错误值（虽然不会被使用）
- **建议改法和验证点**: 将 supervisor 的构造拆分为两种路径：提供 `poller_factory` 时不再接受 `transaction_runner`/`adapter_registry`/`resolver`/`context`；不提供 factory 时由 supervisor 内部构造默认 factory。可用 `classmethod` 提供两个构造入口：`WaitPollerSupervisor.with_factory(...)` 和 `WaitPollerSupervisor.with_components(...)`。
- **修复风险（低）**: 需要调整测试中的 supervisor 构造调用，但语义等价。
- **严重程度（低）**: 不影响正确性，属于 API 整洁性 concerns。Slice 2 测试不受影响（测试路径覆盖了两种 factory 模式）。

### 03-未修复-低-double-close-中间状态从-STOPPED-跳变到-CLOSING

- **入口/函数**: `WaitPollerSupervisor.close()`
- **文件(行号)**: `dayu/host/wait_adapter.py:1150-1187`
- **输入场景**: 对已 `close()` 完成的 supervisor 再次调用 `close()`
- **实际分支**: 第一次 `close()` 完成后 `self._thread` 仍指向已死线程（第 1119 行未重置为 None），`self._diagnostics.status` 为 `STOPPED`。第二次 `close()` 进入 `thread is not None` 分支（第 1157-1169 行），条件 `self._diagnostics.status is not WaitPollerLoopStatus.FAILED` 对 `STOPPED` 为 True，将 diagnostics 设为 `CLOSING`（第 1166 行）。随后 `thread.join()` 立即返回（线程已死），最终 diagnostics 恢复为 `STOPPED`（第 1183-1187 行）。
- **预期行为**: 已 `STOPPED` 的 supervisor 应直接返回，不经过 `CLOSING` 中间态。
- **实际行为**: diagnostics 经历 `STOPPED → CLOSING → STOPPED` 的短暂跳变。功能上 `close()` 仍幂等（线程 join 无副作用，终态正确），但对并发读取 `diagnostics_snapshot()` 的观察者可见中间 `CLOSING` 状态。
- **直接证据**:
  1. 第 1119 行：`self._thread` 在 close 完成后未置 None
  2. 第 1157-1158 行：`thread is None` 检查 — 线程死后仍为非 None，走入 thread 分支
  3. 第 1165-1168 行：条件 `status is not FAILED` 允许 STOPPED 被覆盖为 CLOSING
  4. 测试 `test_close_is_idempotent`（test_wait_poller_runtime.py:379-395）验证了终态为 STOPPED，但未验证中间无 CLOSING 跳变
- **影响**: diagnostics 观察者可能短暂看到 CLOSING 状态，不影响功能正确性
- **建议改法和验证点**: 在 close() 开头增加对已终端状态（STOPPED、FAILED）的早期返回；或将 `self._thread` 在 close 完成后置 None。测试应增加中间状态断言（在第二次 close 的 join 返回后、status 更新前验证状态）。
- **修复风险（低）**: 微调控制流，不影响行为语义
- **严重程度（低）**: 不影响功能，仅 diagnostics 观测精度问题

### 04-未修复-低-plan-declares-close_drain_timeout_seconds-as-float-or-None-实现要求正浮点数

- **入口/函数**: `WaitPollerRuntimePolicy.__post_init__`
- **文件(行号)**: `dayu/host/wait_adapter.py:292-294`
- **输入场景**: Slice 3 `OpenHostOptions` 期望 `close_drain_timeout_seconds: float | None`（plan 第 183 行），用户传入 `None` 表示"无超时"
- **实际分支**: `_require_positive_float(self.close_drain_timeout_seconds, ...)` 拒绝 `None` 和 `<= 0` 值。默认值为 `5.0`
- **预期行为**: plan 定义 `close_drain_timeout_seconds: float | None`，`None` 表示无超时。实现对此语义的直接支持是允许 `None`（并在 `close()` 中无条件 `thread.join()`）。
- **实际行为**: 实现不支持 `None`，要求调用方显式传入一个很大的正浮点数来模拟"无超时"。功能等价，但 contract 与 plan 声明不一致。
- **直接证据**: plan 第 183 行：`close_drain_timeout_seconds: float | None`；plan 第 192 行："All numeric policy values must be positive except close_drain_timeout_seconds, which may be None for no timeout or positive when set"；实现第 267 行：`close_drain_timeout_seconds: float = 5.0`；第 292-294 行要求 positive。
- **影响**: Slice 3 `OpenHostOptions` wiring 需做 `None → large_float` 翻译，或修改 policy 字段类型。不阻塞 Slice 2。
- **建议改法和验证点**: 接受当前实现并同步更新 plan（或 control doc）关于此字段的声明；或扩展 policy 支持 `float | None`，在 `close()` 中通过 `thread.join()` vs `thread.join(timeout)` 分支处理。
- **修复风险（低）**: 两种方向都是局部的
- **严重程度（低）**: Slice 2 不受影响，Slice 3 需注意 contract 差异
