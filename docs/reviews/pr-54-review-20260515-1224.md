### 1-未修复-严重-`_consume_worker_events` try 前代码引发 lane token 永久泄露

- **入口/函数**: `HostDispatchScheduler._consume_worker_events`
- **文件(行号)**: `dayu/host/dispatch.py` 第 847-864 行（try 块前），第 919-926 行（finally 释放）
- **输入场景**: `_consume_worker_events` 被创建为 asyncio 任务后开始执行。第 848 行的 `_read_run_session_id(record.run_id)` 因数据库中 Run 已删除等原因抛出 `RuntimeError`。或者第 847-857 行 `LocalEngineEnvelope` 构造函数因校验失败抛出异常。或者第 858-861 行 `EngineEventIngestor` 构造函数抛出异常。
- **实际分支**: 第 847-864 行的 envelope/ingestor 构造、变量初始化代码全部位于第 865 行 `try:` 块**之前**。第 919 行的 `finally` 块仅在 `try` 被进入后执行。
- **预期行为**: 所有代码路径都必须释放 lane token、从 active registry 注销、关闭 worker handle。
- **实际行为**: 若第 847-864 行抛出任何异常，`finally` 块不执行：
  - lane token 未被 `_safe_release_lane_token` 释放 → **lane 容量槽位永久泄露**
  - handle 未被从 `_active_handles` 丢弃 → 僵尸条目
  - registry 条目未被移除 → cancel 调用会访问死引用
- **直接证据**: `try:` 语句在第 865 行。第 847 行 `envelope = LocalEngineEnvelope(...)` 到第 864 行 `last_accepted_event_id = None` 全部在 try 保护范围之外。第 919-926 行的 finally 块（`unregister` + `close handle` + `release token`）只有 try 块被执行过才会运行。
- **影响**: 高。每次此类故障永久消耗一个 lane 槽位，直到 scheduler 重启且 lane coordinator SQLite 中的 claim TTL 过期。在容量小的 lane 配置下，`WAITING_FOR_LANE` 任务会反压整个调度。
- **建议改法和验证点**: 将第 847-864 行的 envelope/ingestor 构造和变量初始化移入 `try:` 块内（第 865 行之后）。或者在最外层包一个 `try/finally`。验证点：注入一个 mock worker handle，使其 `local_worker_id` 属性抛出异常，验证 `_safe_release_lane_token` 被调用。
- **修复风险**: 低。将约 18 行代码移入 try 块不影响正常控制流。

### 2-未修复-高-active cancel closeout 不更新 dispatch record，留下孤立 DISPATCHING 诊断记录

- **入口/函数**: `active_cancel_closeout_in_transaction`
- **文件(行号)**: `dayu/host/durable/run_transition.py` 第 751-830 行
- **输入场景**: Engine 完成 active cancel，确认 Attempt 和 Run 应收口到 CANCELLED。此时 dispatch record 处于 `DISPATCHING` 且 `worker_accept_event_id` 非空。
- **实际分支**: 函数在第 768-770 行读取 `dispatch_record` 后，仅将其用于拼 event payload（第 784、788、793、798 行）和最终 `RunTransitionResult`（第 829 行）。**全程不调用任何 dispatch record CAS 写函数**。
- **预期行为**: dispatch record 应与 Attempt 和 Run 一同进入一致状态。对比 `cancel_predispatch_starting_in_transaction`（同一文件 L1035-1044）显式调用了 `cancel_starting_dispatch_record_row` 将 dispatch record 同步到 CANCELLED。
- **实际行为**: dispatch record 留在 `DISPATCHING` 状态，`cancelled_event_id` 仍为 NULL。Attempt 和 Run 已为 `CANCELLED`。dispatch record 显示"仍在派发中"，但已无活的 Attempt 绑定。
- **直接证据**: 对比 `cancel_predispatch_starting_in_transaction` 调用 `cancel_starting_dispatch_record_row`（显式 CAS write），而 `active_cancel_closeout_in_transaction` 中 dispatch record 仅有 read（第 768 行），无任何 write。第 829 行返回的 `dispatch_record` 变量自读取后从未被修改。
- **影响**: 监控/诊断误导：查询 dispatch record 表会看到 `dispatching` 状态且 `worker_accept_event_id` 非空的记录，但关联 Attempt 已 CANCELLED。依赖 dispatch record 状态做调度的未来逻辑可能误判为"派发中"而触发超时重试。同属 cancel 路径，pre-dispatch cancel 和 active cancel closeout 对 dispatch record 处理不对称。
- **建议改法和验证点**: 新增或扩展 dispatch cancel helper 以支持从 `DISPATCHING + worker_accept_event_id IS NOT NULL` 到 `CANCELLED` 的转换。注意现有 `cancel_starting_dispatch_record_row` 的 WHERE 子句包含 `worker_accepted_at IS NULL`，不能直接用于 active cancel 场景。需要新增 helper 并可能调整 schema DDL 中 `cancelled` 分支的 CHECK 约束（当前要求三者 NULL）。
- **修复风险**: 中。需要修改 schema CHECK 约束和对应的 state.py INSERT 校验，涉及 `HOST_SCHEMA_VERSION` bump。

- **修复风险**: 低。改动范围限于 `_ingest_validated` 的 preview 分支结构和 `_is_preview_event` 函数。

### 5-未修复-中-`_run_mutation_result_for_active` 中并发 CAS 丢失被误归类为 INVALID_STATE

### 9-未修复-中-close() 中 worker handle 被双重关闭

- **入口/函数**: `HostDispatchScheduler.close`
- **文件(行号)**: `dayu/host/dispatch.py` 第 444-449 行，第 919-926 行
- **输入场景**: 调用 `close()` 关闭 scheduler。
- **实际分支**: `close()` 第 444-446 行先直接关闭所有 worker handle。然后第 447-449 行取消活跃任务，触发每个任务的第 919-926 行 `finally` 块，其中又调用 `_safe_close_worker_handle(handle)` 关闭同一个 handle。同一个 handle 被关闭两次。
- **预期行为**: 每个 handle 应恰好关闭一次。
- **实际行为**: 每个 handle 被关闭两次。对默认实现（`_DefaultLocalWorkerHandle`），第二次 `close()` 作用在已关闭的 async generator 上，在 CPython 3.12+ 中无害（抛出 `StopAsyncIteration` 被 `_safe_close_worker_handle` 吞掉）。但 `LocalWorkerHandle` Protocol 未规定 `close()` 必须幂等。第三方实现若关闭已关闭的状态机，可能损坏或抛未处理异常。
- **直接证据**: 第 444-446 行直接 close handle；第 447-449 行 cancel 任务触发 finally 块；第 925 行 finally 块中 `await _safe_close_worker_handle(handle)`。
- **影响**: 对默认实现无害，但违反资源所有权分离原则。自定义 handle 实现分配原生资源时二次关闭可能使进程崩溃。
- **建议改法和验证点**: 移除 `close()` 中第 444-446 行的手动 handle 关闭。让各任务的 finally 块处理自身资源清理。
- **修复风险**: 中。改变了 shutdown 排序：若任务 finally 块抛出异常，shutdown 可能 hang。

## Residual Risk

- **Lane 泄露安全网缺失**: 当前 `_consume_worker_events` 的 lane 释放仅依赖 `finally` 块。若有其他未来代码路径在 try 前创建 lane token 但未进入 try，会出现类似的泄露。建议在 `LaneClaimToken` 上增加 `__del__` 或 context manager 防护。
- **预览事件类型安全**: Finding 3 指出 preview 事件缺少 isinstance 校验。除 preview 外，`USAGE_REPORTED`（第 461 行）和 `PROVIDER_PROTOCOL_ERROR`（第 469 行）已正确校验。但 `_is_terminal_event` 函数（用于 duplicate 检测）也应检查是否存在类似遗漏。
- **Worker handle 二次关闭**: 当前默认实现可容忍二次关闭，但 Protocol 未规定幂等性。未来若有自定义 handle 实现（如 RemoteProxy），此问题可能变为 crash bug。
- **多 scheduler 实例**: 当前 `DEFAULT_ACTIVE_WORKER_REGISTRY` 模块级单例假设单进程单 scheduler。若未来扩展为多 scheduler（如多 lane group），取消传播需重新设计。
- **Admission 模块大小**: `admission.py` 2719 行，是项目最大单文件。虽然当前功能正确，但未来修改的风险较高。建议后续 phase 按 Operation 功能域拆分。
- **EventLog 幂等性**: Finding 8 依赖 `EventLogStore.append_event` 的 event_id 唯一性保护。若 `append_event` 无此保护，需在 ingest 层补重复检测。
- **测试覆盖**: 虽然测试文件约 16000 行，但以下场景需要确认覆盖：
  - Finding 1 的 try 前异常路径（`_read_run_session_id` 抛异常 → lane 仍被释放）
  - Finding 2 的 active cancel → dispatch record 状态一致性
  - Finding 3 的每种 preview event type 的 data=None 和 data=错误类型
  - Finding 5 的并发 terminal closeout CAS 丢失
  - Finding 12 的死代码路径是否在 coverage 报告中被标记
- **CI 状态**: 无 CI checks 数据。PR body 自述 `pytest tests/host tests/runtime -q → 334 passed`、`pyright dayu/host tests/host → 0 errors`。建议在 merge 前通过 CI 验证。
