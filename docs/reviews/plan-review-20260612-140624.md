## Findings

### F01-未修复-中-双验证边界可能导致规则漂移

- **位置**: Risks / Open Questions 章节; Implementation Decisions #6; Slice 1 data flow
- **问题类型**: 过度耦合 / 最佳实践偏离
- **当前写法**: Plan 在 Risks 中提到"parser validates raw JSON field type/path/enum/count and then still constructs `ConversationCompactOutputVNext` as the final Host contract; shared constants remain the single limits source"。
- **反例/失败场景**: `ConversationCompactOutputVNext.__post_init__` 已有验证逻辑（如 `source_labels must be non-empty`，见 `test_compaction_contract.py:195`）。proposal DTO 若独立实现相同的结构性约束（如 source_labels 非空、evidence_kind 枚举），当 `compaction.py` 中的 candidate dataclass 修改约束时，proposal DTO 可能不同步。shared constants 只覆盖数值上限和枚举值，不覆盖结构性不变量。
- **为什么有问题**: 两套验证规则维护在不同位置：一套在 proposal DTO 构造时（`llm_compaction.py`），一套在 `ConversationCompactOutputVNext.__post_init__`（`compaction.py`）。结构性约束（如哪些字段必填、哪些字段允许空）没有单一真源。
- **直接证据**: `tests/host/test_compaction_contract.py:195` 验证 `SessionSummaryCandidateVNext` 的 `source_labels` 必须非空；`llm_compaction.py:626` 使用 `_required_string_tuple` 读取 `source_labels`（允许空数组但不校验非空）。Proposal DTO 和 candidate 的 source_labels 非空约束不在同一位置。
- **影响**: 实施 Agent 可能在 proposal DTO 中重复实现 candidate 已有的约束，或遗漏某些约束，导致两个验证边界行为不一致。
- **建议改法和验证点**: 在 plan 中明确：proposal DTO 只负责 raw JSON 到 typed 结构的字段/类型/枚举/数量校验，不重复 candidate 的结构性不变量（如 source_labels 非空）。`_proposal_to_compact_output_vnext` 构造 `ConversationCompactOutputVNext` 时由 candidate `__post_init__` 统一执行结构性验证。测试应验证：proposal DTO 通过但 candidate 拒绝的场景（如空 source_labels）会抛出 `LLMCompactionProposalError`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F02-未修复-中-平行类型层次增加维护成本

- **位置**: Contract / Schema 章节; Slice 1 exact changes
- **问题类型**: 过度耦合
- **当前写法**: Plan 引入 8 个私有 proposal DTO（`_LLMCompactionProposalVNext`、`_LLMSessionSummaryProposalVNext` 等），与已有的 8 个 candidate 类型（`ConversationCompactOutputVNext`、`SessionSummaryCandidateVNext` 等）平行。声明 "These are private module-level dataclasses or equivalent typed contracts" 且 "mirror the already frozen vNext output JSON shape"。
- **反例/失败场景**: 当 vNext JSON shape 新增字段（如 `evidence_backed_facts` 新增 `confidence` 字段）时，需要同时修改 proposal DTO 和 candidate type。Proposal DTO 是 `llm_compaction.py` 私有，candidate 在 `compaction.py`，修改者必须知道两处都需要更新。
- **为什么有问题**: Plan 声称 vNext output shape 已 frozen（"already frozen vNext output JSON shape"），但如果 shape 真的 frozen，proposal DTO 的存在价值有限——它们只是临时中间结构。如果 shape 会演进，平行层次就是真实的维护负担。Plan 没有明确 shape frozen 的保证来源。
- **直接证据**: `docs/host/design.md:3145` 说 "compactor 输出 schema、candidate 字段和 source label 规则以第 24 章的 vNext compact I/O contract 为准"——这是设计约束但不是 frozen 保证。`docs/host/issues-implementation-control.md:879` 非目标说"不改变 compact output 的业务含义"，但这是 WU-CM-05 的非目标，不是永久 frozen。
- **影响**: 后续 WU（如 WU-CM-06、WU-CM-08）若需修改 vNext shape，必须同时更新 proposal DTO 和 candidate type，增加跨文件联动修改。
- **建议改法和验证点**: 在 plan 中明确：proposal DTO 的字段列表直接从 `ConversationCompactOutputVNext` 及其嵌套类型的 `__init__` 签名派生，不自行定义字段。若 vNext shape 演进，proposal DTO 跟随 candidate type 自动失效（类型错误）。这比让实施 Agent 自行维护两套字段列表更安全。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F03-未修复-低-cast 消除在 json.loads 边界的实现路径不明确

- **位置**: Implementation Decisions #3; Slice 1 stop condition
- **问题类型**: 不可直接实施
- **当前写法**: "Keep `json.loads(...)` at the raw external boundary, then immediately validate top-level object and recursively read fields into typed private dataclasses. Do not use `cast(...)` to bless parsed JSON." Stop condition: "If pyright requires introducing `Any`, `object`, untyped parameters, or a broad `cast(...)` to make the parser type-check, stop and redesign the helper boundary instead of landing weak typing."
- **反例/失败场景**: `json.loads` 在 Python 类型存根中返回 `Any`。当前代码 `parsed = json.loads(raw)` 使 `parsed` 推导为 `Any`。要避免 `cast`，实施 Agent 需要用显式类型注解如 `parsed: JsonValue = json.loads(raw)`，但这引入了 `JsonValue` 到 `Mapping[str, JsonValue]` 的 narrowing 问题。pyright 对 `isinstance(parsed, Mapping)` 后的 narrowing 行为取决于 `JsonValue` 的定义和 pyright 版本。如果 pyright 不能自动 narrow，实施 Agent 被 stop condition 卡住，但 plan 没有给出具体的替代实现路径。
- **为什么有问题**: Plan 的 stop condition 说"stop and redesign the helper boundary"，但没有说明 redesign 方向。实施 Agent 可能在 `cast` 消除上花费大量时间尝试不同方案，最终被迫引入一个 plan 未预见的 `JsonValue` 注解。
- **直接证据**: `dayu/contracts/json_value.py` 定义 `JsonValue` 为 `str | int | float | bool | None | list[JsonValue] | Mapping[str, JsonValue]`。`isinstance(parsed, Mapping)` 对 `JsonValue` 的 narrowing 在 pyright 中应能工作（`JsonValue` 不包含不可 narrow 的类型），但 plan 没有验证这一点。
- **影响**: 实施 Agent 可能在 Slice 1 遇到 pyright 阻塞，被迫在 plan 的 stop condition 和实际实现之间做选择。
- **建议改法和验证点**: 在 plan 中补充：`json.loads` 返回 `Any`，使用 `parsed: JsonValue = json.loads(raw)` 显式注解，然后 `isinstance(parsed, Mapping)` narrow 到 `Mapping[str, JsonValue]`。如果 pyright 不能 narrow，可以使用 `_json_object(parsed, "proposal")` helper（接受 `JsonValue`，返回 `Mapping[str, JsonValue]`，内部 `isinstance` 检查），而不是 `cast`。这比 stop condition 更具体。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F04-未修复-低-Slice 2 测试对 proposal 内部结构的假设可能随 Slice 1 变化

- **位置**: Slice 2 data flow
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: "Tests should mutate `_proposal_json(compact_input)` or a local minimal valid proposal builder." 每个 invalid test "should call `parse_conversation_compact_output_vnext(compact_input, json.dumps(...))`"。
- **反例/失败场景**: `_proposal_json` 当前返回 `dict[str, JsonValue]`（line 334-348），直接操作 dict 字段。如果 Slice 1 改变了 `_parse_vnext_proposal` 的内部结构（如引入 proposal DTO 后移除了某些宽 mapping helper），`_proposal_json` 的构造方式可能需要调整。但 plan 没有明确 Slice 2 对 Slice 1 实现细节的依赖。
- **为什么有问题**: Slice 2 说 "only to fix parser diagnostics exposed by tests"，暗示 Slice 2 只修 parser，但 Slice 2 的测试构造依赖 Slice 1 的 parser 内部结构。如果 Slice 1 的 proposal DTO 构造方式改变了字段验证顺序，Slice 2 的测试可能需要调整错误消息断言。
- **直接证据**: `tests/host/test_llm_compaction.py:334-348` 的 `_proposal_json` 使用 `fake_compaction_proposal_from_material_json` 生成 proposal，然后 `json.loads` 得到 dict。这个 helper 不依赖 parser 内部结构，只依赖 proposal JSON shape。所以 Slice 2 的测试构造实际上是安全的。
- **影响**: 实际影响较小，因为 `_proposal_json` 只依赖 proposal JSON shape，不依赖 parser 内部实现。
- **建议改法和验证点**: 在 plan 中明确：Slice 2 的测试通过 `json.dumps` 构造 raw JSON 字符串，不依赖 Slice 1 的内部数据结构。`_proposal_json` 只用于构造合法 proposal 基线，invalid 场景直接构造 dict 并 `json.dumps`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open Questions

1. **Proposal DTO 的字段构造是否复用现有 field helpers？** Plan 说 "Add private field helpers that report exact field paths"，但现有 helpers（`_required_string`、`_required_string_tuple` 等）已经报告 field path。新 helpers 是替代还是增强？如果替代，现有 section parser 的 field path 格式是否保持一致？
2. **`_parse_vnext_proposal` 的返回类型变更是否影响 `LLMContextCompactor.compact` 的调用链？** `compact` 方法调用 `parse_conversation_compact_output_vnext`，后者调用 `_parse_vnext_proposal`。如果 `_parse_vnext_proposal` 返回类型从 `Mapping[str, JsonValue]` 变为 `_LLMCompactionProposalVNext`，`parse_conversation_compact_output_vnext` 的内部实现会变化，但公共签名不变。这是预期行为吗？

## Final Conclusion

**pass-with-risks**

Plan 整体质量高，动机成立，设计真源对齐正确，non-goals 边界清晰，slice 切分合理，测试覆盖目标明确。Plan 已经具备 code-generation-ready 的基本条件。

主要风险是双验证边界（F01）和平行类型层次（F02）：proposal DTO 和 `ConversationCompactOutputVNext` 之间可能存在验证规则漂移。这两个风险不阻塞实施，但需要在实施过程中通过明确的分工（proposal DTO 只做 raw JSON 校验，candidate `__post_init__` 做结构性不变量验证）和测试覆盖来缓解。

`cast` 消除路径（F03）的 stop condition 足够清晰，但可以更具体。其余 findings 为低严重程度，不阻塞实施。

**Blocking open questions**: 无。Plan 可以进入 implementation gate。
