## Adversarial Failure Pass — 新 Findings

### NEW-001-未修复-低-Host close 顺序中 lifecycle cancel 传播未显式列出

- **位置**: §5.4 Host close 顺序
- **问题类型**: 最佳实践偏离
- **当前写法**: Host close 顺序为 "① health gate begin_closing 与 registry begin_host_close 共同关闭所有 public/new-work 入口 → ② 停止 wait poller → ③ durable_actor.stop_and_drain() → ④ registry 等待所有 attachment 的 pre-start/new-work lease → ⑤ 关闭全部 native mutex → ⑥ scheduler.close() → ⑦ 其余 close"。
- **反例/失败场景**: 设计真源 §27 明确要求 Host close "必须向 active worker registry 传播 lifecycle cancel，使 Host 注入 Engine 的 cancellation token 可见，并通知 `LocalWorkerHandle.on_cancel(reason)`"。当前计划的 Host close 顺序未列出 lifecycle cancel 传播步骤。若 implementation agent 严格按计划顺序实现，可能遗漏 worker registry cancel 传播。
- **为什么有问题**: 设计真源 §27 是 Host close 的 canonical 行为规范。计划虽然引用了既有 Runner timeout，但 close 顺序中缺少 lifecycle cancel 传播这一显式步骤。
- **直接证据**: 设计真源 §27 line 1189: "close 流程必须停止 scheduler / promotion / background supervisor，不再启动新的 Attempt；必须向 active worker registry 传播 lifecycle cancel"。计划 §5.4 的 7 步顺序无 "lifecycle cancel to active workers"。
- **影响**: 低。lifecycle cancel 传播是既有 `HostDispatchScheduler.close()` 行为的一部分（scheduler close 时会 cancel 其 critical tasks），但计划的 close 顺序描述不够完整，可能导致 implementation agent 在重构 close 时遗漏此步骤。
- **建议改法和验证点**: 在 §5.4 Host close 顺序的步骤 ③ 或 ④ 中显式加入 "向 active worker registry 传播 lifecycle cancel"。验证点：测试 Host close 期间有 active worker 时，worker cancellation token 可见。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### NEW-002-未修复-低-reconcile_owned_sessions_once 的 reconciliation 逻辑未展开

- **位置**: §5.5 "production scheduler 的 `_owned_session_reconciliation_loop`"
- **问题类型**: 不可直接实施
- **当前写法**: plan 定义了 `reconcile_owned_sessions_once(fixed_now) -> OwnedSessionReconciliationResult` 的签名和语义（"逐 Session 重新申请 work lease，并只做 target-scoped queued promotion/accepted reconciliation"），但未说明 reconciliation 内部具体做什么。
- **反例/失败场景**: implementation agent 需要知道 reconciliation step 内部的精确逻辑：是否只做 queued promotion？是否做 accepted wake？是否检查 incomplete proactive operation？若 plan 不展开，agent 可能过度实现（扫描全 workspace）或不足实现（只做 promotion 不做 accepted reconciliation）。
- **为什么有问题**: plan 已在 §5.5 说明 "target-scoped queued promotion/accepted reconciliation"，但这是行为描述而非实现指导。agent 需要知道 reconciliation 的输入、输出和精确动作序列。
- **直接证据**: plan §5.5: "逐 Session 重新申请 work lease，并只做 target-scoped queued promotion/accepted reconciliation"。这是唯一描述 reconciliation 内部行为的文本。
- **影响**: 低。plan 已足够让 agent 理解目标行为（target-scoped、queued promotion + accepted reconciliation），但更精确的动作序列会减少实现歧义。
- **建议改法和验证点**: 在 §5.5 中补充 reconciliation step 的内部动作序列伪代码或 bullet list。例如：(1) 获取 ACTIVE RW Session id 快照；(2) 逐 Session 申请 work lease；(3) 持 lease 检查该 Session 是否有可 promotion 的 queued Run；(4) 持 lease 检查该 Session 是否有 accepted Run 需要 pre-start governance；(5) 返回结果。验证点：测试覆盖 promotion 和 accepted reconciliation 两个路径。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### NEW-003-未修复-低-Slice 2 内部 proactive 子步骤的 allowed files 与 Slice 2 主体有重叠但未说明合并关系

- **位置**: §7 Slice 2 内部 proactive 子步骤 "Allowed production/config files"
- **问题类型**: 范围漂移
- **当前写法**: Slice 2 主体的 allowed production files 列表与内部 proactive 子步骤的 allowed production/config files 列表有大量重叠（`dayu/host/dispatch.py`、`dayu/host/context_events.py`、`dayu/host/compaction_operation.py` 等）。plan 说明"以下 allowed files/tests 是 Slice 2 全集中的职责分组"，但两个列表独立列出可能导致 implementation agent 困惑。
- **反例/失败场景**: implementation agent 可能认为 proactive 子步骤的 allowed files 是独立于 Slice 2 主体的额外修改范围，从而过度扩展 scope。或者 agent 可能只看 Slice 2 主体的 allowed files 列表而忽略 proactive 子步骤的补充列表。
- **为什么有问题**: 这不是 correctness 问题，而是 plan 可读性问题。两个列表的重叠是合理的（同一文件的不同职责），但独立列出可能造成混淆。
- **直接证据**: plan §7 Slice 2 主体 allowed files 包含 `dayu/host/dispatch.py`、`dayu/host/context_events.py` 等；proactive 子步骤也列出相同文件。
- **影响**: 极低。plan 已明确"是 Slice 2 全集中的职责分组，不构成可单独发布的 checkpoint"。
- **建议改法和验证点**: 可考虑在 proactive 子步骤中只列出 Slice 2 主体未包含的额外文件（如 `dayu/host/proactive_compaction.py`），其余标注"同 Slice 2 主体"。但此为可选优化，不作为 blocker。
