## 3. Findings

### 1-未修复-[高]-「显式 create-existing × 同内容（±同标记）」单元归属未收敛，三个来源互相矛盾
- **位置**: plan §3 状态机表第 6 行；§4.2 skip 门条件「允许动作」；§3 尾注「本项不定义其未裁决分支」；§1 非目标「不改 O14/O15 动作准入」；§7「不能让显式 create-existing 变成 skip」。
- **问题类型**: 状态机漏洞 / open question 未收敛 / 不可直接实施
- **当前写法**: 表第 6 行写「active + 显式 `create` 无 overwrite → 由 O14 的准入裁决拒绝，即使内容和标记相同也不 skip / 不变」；§4.2 把 skip 门条件之一写为「允许动作」；§3 尾注又称显式 create/update 的存在性属 O14/O15、「本项不定义其未裁决分支」。
- **反例/失败场景**: 用户 `--action create`（无 overwrite）对已存在 material 上传同内容、仅 `--amended` 不同。当前代码 `_can_skip_upload`（`docling_upload_service.py:479-499`）对 action 无差别，直接 early skip 返回 `already_uploaded`——元数据变更被指纹去重吞掉，直接违反 goal「不能被相同指纹 skip 吞掉元数据变更」。实现 Agent 面对三个互相冲突的读法：(a) 保持现状 skip（违反 goal 与表第 6 行）；(b) 让 create-existing 走 metadata-only 或全量发布后以 `FileExistsError` 失败（前者违反表第 6 行「不变」，后者是行为变更且错误形状是仓储层偶然产物而非 O14 typed 错误）；(c) 把「允许动作」实现成 action 门（这是 O14 准入工作的最小前移，与非目标边界纠缠）。「允许动作」在 plan/goal 中均无定义，其 closed set 归未合并的 O14 所有。
- **为什么有问题**: plan 自称 §3 是「新发布契约与状态机」，但该单元的行为在 plan 内部自相矛盾且未标注哪一格由 O18 实施、哪一格留给 O14；实施 Agent 被迫重新设计或猜，且测试要么固化旧 skip、要么断言 O14 拥有的错误形状（违反「测试必须断言 owner 级行为」）。
- **直接证据**: `docling_upload_service.py:457-465`（create-existing 准入仅对 FILING 抛 `FileExistsError`，material 落空）、:479-499（action 无差别 early skip）、:685（`replace_existing` 对 create 无 overwrite 为 False，最终 `_create_source_document`→`create_material` 在 `_fs_source_document_core.py:148-149` 抛 `FileExistsError`）；plan 表第 6 行与 §3 尾注、§7、非目标的对撞文本。
- **影响**: 实施 Agent 跑偏（错把 O14 准入做进 O18，或留下 goal 违反面）；create 请求的标记变更被 skip 吞掉成为用户可见缺陷；测试固化偶然行为；后续 O14 落地时返工。
- **建议改法和验证点**: 在 plan §3 显式钉死该单元的 O18 过渡行为，推荐：「O18 的 identical-skip 与 metadata-only 仅覆盖解析为 `update`（含 auto 解析）的动作；显式 create-existing 一律不进 skip/metadata-only，沿用现有发布路径拒绝（行为变更：同内容 create 从 skip 变为失败，须在 plan 变更面记录），typed 准入错误仍归 O14」；把「允许动作」替换为明示的动作 closed set 或声明其临时定义；Slice 1 验收组补一条该单元的零副作用断言（不写 source meta/manifest、不 skip）。验证点：create-existing × 同内容 × 同/异标记 4 象限各有 owner 测试，且不出现 `already_uploaded`。
- **修复风险（低/中/高）**: 低（plan 文本修订即可，实现侧只影响 skip 门条件）。
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-[中]-metadata-only 终态的对外协议未定义，撞上 ingestion 闭集状态机
- **位置**: plan §3 表第 4 行（metadata-only publication）、§4.5（payload/事件/摘要投影）、§5 Slice 2 完成信号（「成功、skipped、metadata-only、delete/恢复结果」）。
- **问题类型**: 契约缺失
- **当前写法**: §3 只规定「不得返回 already_uploaded」「stored_file_count=0 的元数据更新不生成转换/文件上传事件」；§4.5 规定成功 `UploadOperationResult.payload["amended"]` 承载已发布值、skip 取现存发布值、deleted/failed/cancelled 需标注或取最后发布值。但 plan 从未规定 metadata-only 的 `UploadOperationResult.status` 取值，也未说明如何在用户可见结果里区分「内容发布」与「仅标记切换」。
- **反例/失败场景**: 实施 Agent 若返回 `status="uploaded"`，经 `sec_upload_workflow._resolve_upload_status`（:635-650）映射为 `ok`，与内容发布在状态上不可区分，§5 枚举的「metadata-only 结果」只能靠 payload 细节表达；若另造新 status（如 `metadata_updated`），将撞上 `ingestion_runtime.py:264-267、328-331` 的闭集（`ok/skipped/deleted/failed`）与 `FinsUploadPipelineResult`/`FinsUploadResultSummary` 的 `__post_init__` 闭集校验（:1726、:1844），需要一次 plan 未预告的跨层状态词表扩展。两种选择的验收口径不同，测试只能猜。
- **为什么有问题**: 结果/摘要是 goal 明列的「用户可见结果一致」表面；plan 把语义规则写了却没写协议值，属于把 schema/协议字段决定推给实施 Agent，违反「结构化输出必须自足说明字段名、含义、类型、必填性、允许值」的可实施性标准（该约束直接约束 LLM-facing 输出，但同一纪律要求 plan 先钉死 owner 契约）。
- **直接证据**: `ingestion_runtime.py:264-267`（`_UPLOAD_RESULT_STATUS_*` 常量）、:328-331（status→disposition 闭集映射）、:1726/:1844（闭集校验）；`docling_upload_service.py:2104-2115`（`_build_skipped_result` 固定 `status="skipped"`/`skip_reason="already_uploaded"`）；plan §3/§4.5/§5 均无 status 取值。
- **影响**: 状态/摘要跨层临时发明导致字段漂移或「显示正确但协议错误」；review 无法验收 metadata-only 结果口径；后续为了可辨识性补状态词表造成返工。
- **建议改法和验证点**: 在 plan §3 或 §4.5 钉死：(1) metadata-only 的 `UploadOperationResult.status` 值（推荐继续 `uploaded` 并新增 payload 标记字段，或明确新增 status 并列出须扩展的闭集位置）；(2) `FinsUploadResultSummary` 是否新增已发布 `amended` 字段（goal 要求摘要消费同一事实，答案应当是是）及其对 filing 路径是否同步；(3) skip/delete/failed 各终态里 amended 字段的命名（如 `requested_amended` vs `amended`）与必填性。验证点：入口测试对 4 类终态逐一断言字段名与取值来源（请求值/现存发布值/本次发布值）。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中

### 3-未修复-[中]-条件元数据发布的机制事实缺失：opaque revision 对 preparation 不可见，且权威边界校验需要 commit 期钩子；验证口径不足以锁定边界
- **位置**: plan §2 尾段、§4.3、§7 停止点、§8 风险 1、§6 owner 测试（「stale 目标拒绝」）。
- **问题类型**: 并发恢复风险 / 不可直接实施
- **当前写法**: §4.3 要求「经 storage owner 校验目标仍是预期 active 同版、同 fingerprint/旧标记后，精确替换 source meta」「若提交时状态已变，返回 typed stale/conflict」；「新增的窄仓储 precondition 若必要，应以 opaque revision 和 staged/published state 为参数直接表达」；§8 要求先用真实仓储测试证明「窄条件校验可在权威写入边界完成」，证明不了就触发停止点。
- **反例/失败场景**: (1) plan 偏好的 precondition 参数是 opaque revision，但 preparation 持有的 `previous_meta` 来自 `get_source_meta`→`_get_source_meta_unguarded`→`_source_meta_without_revision`（`_fs_source_document_core.py:822-827`、:1781-1800），`_published_source_revision` 已被剥离——按 plan 字面实现会发现该参数取不到，Agent 要么扩读契约（超出「严格读取或条件发布接口」的既定理由）、要么改用业务字段等价比较，plan 未指定走哪条。(2) 校验若做在 staging 写入时（`replace_source_meta` 内），与 commit 提升之间仍有窗口：A 校验通过后 B 提交新内容 v2，A 的 stale meta（含旧 files URI）随后 commit，指纹/版本回退 + files 悬空，正是 §8 想防的「拿旧 previous_meta 静默覆盖」。权威边界实际是 `_commit_batch_with_publication_guard`（`_fs_storage_infra.py:676-692`）持有 per-ticker publication guard 的提升时刻，需要一个 commit 期校验钩子，当前 batch 框架没有。(3) §6 的「stale 目标拒绝」测试用单线程插队即可通过，无法证明校验落在权威边界——浅实现可绿测通过而窗口仍在。
- **为什么有问题**: plan 把最关键的新机制建立在一个取不到的参数和一个不存在的钩子上，且「若必要」的措辞与 §8 的强制证明互相稀释；验证口径没有并发交错测试要求，无法履行 §8 的证明义务。
- **直接证据**: `_fs_source_document_core.py:827`（返回前剥离 revision）、:1781-1800（`_source_meta_without_revision`）；`_fs_source_integrity.py:67`（`_published_source_revision` 字段名）、:1759-1778（revision 仅从 persisted meta 读取）；`_fs_storage_infra.py:676-692`（commit 在 publication guard 下提升）；`docling_upload_service.py:1616-1648`（skip 判定在 prepare 期用 stale `previous_meta`）。
- **影响**: 实现 Agent 按 plan 字面做 revision 参数会卡壳或临时改接口；校验放错边界导致并发下 source meta 回退/文件悬空（数据损坏级）；测试绿但风险未消，§8 的「已证明」变成空头承诺。
- **建议改法和验证点**: §4.3 钉死 precondition 的可观测输入与位置：要么 (a) 明确 expected 依据为业务字段等价（document_version、source_fingerprint、旧 amended、is_deleted=false）并接受 ABA 之外的强度，要么 (b) 扩一条窄读接口把 persisted revision 显式交给 preparation（写进白名单理由）；明确「校验必须在 commit 提升时、publication guard 持有下执行」；§6 把验证口径改为「双 batch 交错测试（A prepare → B commit → A commit 必须 stale 拒绝）+ 单线程 stale 拒绝」。验证点：交错测试在真实仓储上可复现拒绝，且被拒后无任何 meta/manifest 写入痕迹。
- **修复风险（低/中/高）**: 中（涉及窄仓储接口设计，但方向已在 plan 的停止点保护下）。
- **严重程度（低/中/高/严重）**: 中

- **问题类型**: 契约缺失 / 最佳实践偏离（LLM-facing 语义）
- **当前写法**: §3/§4.5 要求「事件中的请求字段应明示为 requested amended」「不能无标签混用」，但只覆盖事件/结果；tool schema 中 `amended` 描述仍为「上传文件是否为修订版本。」（`upload_tools.py:276-280`），`_upload_request_summary` 的请求回显键仍为无标注 `amended`（`ingestion_runtime.py:7812`），与未来结果摘要里的已发布 `amended` 并存于同一 job record。
- **反例/失败场景**: metadata-only toggle 上线后，LLM 从 job record 同时读到 `request.amended`（请求值）与 `result.amended`（发布值），键名相同语义不同；tool schema 也未告知「同内容改标记只更新元数据、不升版」的新行为，无状态 LLM 仍按旧心智重复上传或误判 skip。
- **为什么有问题**: 项目 LLM-facing 约束要求投给 LLM 的字段自解释、请求/事实不混用；plan 自己立了规则却没把这两个表面纳入检查面。
- **直接证据**: `upload_tools.py:276-280`；`ingestion_runtime.py:7780-7812`（请求摘要）；白名单 §5 无 `upload_tools.py`/`_ingestion_tool_helpers.py`。
- **影响**: LLM 消费面字段混淆或语义滞后；轻微至中（有 §5 白名单逃逸阀兜底，但逃逸阀要求先修订 plan，成本后移）。
- **建议改法和验证点**: §6 增加一条判定：实现后复核 tool schema `amended` 描述与 job record 请求/结果字段命名（请求回显改 `requested_amended` 或在摘要结构上分区），若变更则把 `upload_tools.py` 补进白名单；验证点：tool schema 文本与结果字段名在 review 时逐一对照 §3 规则。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低

## 4. 其它 lens 结论（无独立 finding）

- **Goal-bound minimal design**：无目标漂移。metadata-only mutation、条件发布、requested/published 标注均能映射回 goal 的「同内容仅改标记」「不能被指纹去重吞掉」「同一事实投影」要求；filing 身份规则、O13/O14/O15/O33 独立合同未被改写；无 future-slice 夹带。
- **架构边界**：amended 的 owner 判定正确——Fins 请求校验（精确 bool）→ 共同 preparation/publication owner（状态转换）→ source meta（持久化真源）→ manifest/read/结果（投影）；入口只传输；未在 CLI/展示层补偿；`MaterialManifestItem.from_source_meta` 保持唯一投影点（`_fs_source_integrity.py:1233-1235` 的 canonical 比较随类型自然同步）。
- **切片过度设计**：Slice 1（owner 行为）/Slice 2（入口传播）边界合理，允许一次 pass 合并并保留两组验收；`_PreparedMaterialMetaMutation` 与窄仓储 precondition 均有直接风险支撑，不算过度抽象。
- **schema 新库契约**：material source meta/manifest 的 amended 必填精确 bool、fail closed、全新起库、测试只用 fresh workspace、filing 旧规则独立——与「禁止兼容代码」约束一致；`MaterialManifestItem.from_source_meta` 现状对 `is_deleted` 等仍宽松（`is True`），plan 只收严 amended，范围最小，可接受。
- **测试与真实 CLI**：验证面完整（owner 测试断言精确 bool/同源/版本/文件字节/revision/零写入；真实 CLI canary 9 步含 toggle/skip/版本/delete/恢复/fresh identity/A16-A17 复跑；US/CN/HK 对照并允许标注不可离线项；逐文件 coverage ≥80%；不以 fake 调用参数代替读回）。缺口仅是 F3 的并发交错口径与 F2 的终态字段断言口径。
