## Findings

### 1-未修复-中-FinsSourceDownloadAdapterRequest.cancellation_checker 类型标注为 Callable 而非 CancellationToken

- **入口/函数**: `FinsSourceDownloadAdapterRequest` dataclass 定义
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:427`
- **输入场景**: 任何 download adapter request 构造
- **实际分支**: `cancellation_checker: Callable[[], bool]`
- **预期行为**: 按 plan 第 6.2/11.1 节，adapter request 中的 checker 同时实现 `CancellationToken`；类型标注应反映实际 contract，使 pyright 能在构造时捕获类型不匹配
- **实际行为**: 字段标注为 `Callable[[], bool]`。运行时 `DefaultFinsRuntime` 传入 `_RuntimeJobCancellationChecker`（`FinsJobCancellationChecker` 子类，同时满足 `Callable` 和 `CancellationToken`），download workflow 边界 `_canonical_cancellation` 用 `isinstance(checker, CancellationToken)` 做运行时类型守卫并 cast。若外部构造方传入纯 `Callable` lambda，运行时 TypeError 在 workflow 边界抛出，但 pyright 无法在构造时捕获
- **直接证据**:
  - `ingestion_runtime.py:427`: `cancellation_checker: Callable[[], bool]`
  - `ingestion_runtime.py:1553` (`_FinsIngestionExecutionContext`): `cancellation_checker: FinsJobCancellationChecker`（内部 context 已用更精确类型）
  - `cn_download_filing_workflow.py:897-898`: `if not isinstance(cancel_checker, CancellationToken): raise TypeError(...)`
- **影响**: 类型安全缺口——pyright 无法在 adapter request 构造时验证 `cancellation_checker` 满足 `CancellationToken` contract；运行时由 workflow 边界 `isinstance` 兜底，但错误发现延后
- **建议改法和验证点**:
  1. 将 `FinsSourceDownloadAdapterRequest.cancellation_checker` 类型改为 `FinsJobCancellationChecker`（与 `_FinsIngestionExecutionContext` 一致）或 `CancellationToken`
  2. 运行 pyright 确认无新增报错
  3. 确认所有 adapter request 构造点仍通过类型检查
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
