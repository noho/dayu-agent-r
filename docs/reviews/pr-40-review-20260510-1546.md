## Findings

### 1-未修复-中-update_state_owner_aware 绕过注入的 UtcClock

- **入口/函数**: `AttemptLeaseStore.update_state_owner_aware`
- **文件(行号)**: `_run_state_store.py:598-599`
- **输入场景**: 任何 attempt 终态收口（owner-lost diagnostic close、`_finish_attempt_if_durable`）
- **实际分支**: `state in _ATTEMPT_FINISHED_STATES` 为 True 时直接调用 `datetime.now(tz=timezone.utc)`
- **预期行为**: `AttemptLeaseStore` 契约声明 "所有时间使用 timezone-aware UTC，由 UtcClock 注入"（`_run_state_store.py:389`），`finished_at` 应使用 `self.clock.now()`
- **实际行为**: 使用 `datetime.now(tz=timezone.utc)` 直接取系统时钟，绕过注入的 `UtcClock`
- **直接证据**: `_run_state_store.py:598-599` — `datetime.now(tz=timezone.utc).isoformat()`；对比同文件 `renew`（line 436）、`verify_owner`（line 519）、`close_terminal`（line 664）均使用 `self.clock.now()`
- **影响**: 测试中使用 `_FakeClock` 时 `finished_at` 写入真实墙钟而非 fake clock，导致时间断言不可靠；生产环境无功能影响
- **建议改法和验证点**: 改为 `self.clock.now().isoformat()`；补测试断言 `finished_at` 与 fake clock 一致
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中高-AttemptScopedRunEventAppender.append_in_transaction 零测试覆盖

- **入口/函数**: `AttemptScopedRunEventAppender.append_in_transaction`
- **文件(行号)**: `_attempt_supervisor.py:262-294`
- **输入场景**: `LocalRunHarness._resolve_attempt_appender` 在 harness 已持有外层事务时调用此方法（`_run_harness.py:2071`），是主 run loop 的生产路径
- **实际分支**: 调用方传入已有 `HostStorageTransaction`，方法在该事务内执行 `verify_owner` + `_verify_run_id_matches` + `append_with_position_in_transaction`
- **预期行为**: 与 `async append`（独立开事务）语义一致，但走不同代码路径
- **实际行为**: 无任何测试覆盖此方法；9 个 P8 测试文件均未调用
- **直接证据**: `grep -rn "append_in_transaction" tests/` 返回空；生产路径 `_run_harness.py:2071` 确认使用
- **影响**: 如果 `append_in_transaction` 内的 `verify_owner` + append 顺序与 `async append` 路径产生回归差异，无法被测试发现
- **建议改法和验证点**: 补充测试：在已有事务内调用 `append_in_transaction`，验证 verify_owner CAS miss 回滚、run_id mismatch 抛 `AttemptFencingError`、正常 append 写入成功
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中高

### 3-未修复-中-多进程 terminal close race 测试是确定性的，未覆盖真实 CAS 竞争

- **入口/函数**: `test_phase8_multiprocess_stress.py` terminal close race 场景
- **文件(行号)**: `tests/host/test_phase8_multiprocess_stress.py:491-591`
- **输入场景**: worker-a 和 worker-b 同时尝试 terminal close 同一个 attempt
- **实际分支**: `_create_running_attempt_synchronously` 创建 attempt 时写入 `secret_a` 的 hash；`secret_b` 是随机生成的新 token，其 hash 从未入库
- **预期行为**: 测试应验证两个都持有有效 owner token 的进程在 `close_terminal` 的 `UPDATE WHERE lease_expires_at > now` 上的真实 CAS 竞争
- **实际行为**: worker-b 的 `verify_owner` 因 `owner_token_hash` 不匹配直接 `OWNER_MISMATCH`，结果预先确定，不涉及 SQLite 并发 CAS
- **直接证据**: `_create_running_attempt_synchronously`（line 319）只写入一个 owner token hash；worker-b 使用全新随机 secret
- **影响**: 测试提供关于 terminal close CAS 正确性的虚假信心；真正的双有效 token CAS 竞争未被验证
- **建议改法和验证点**: 需要构造两个不同 attempt_id 但竞争同一 attempt 行的场景（受 UNIQUE(run_id, attempt_index) 约束限制，可能需要测试层面放宽约束或使用不同 attempt_index 的 recovery attempt）
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-低-IntegrityError 捕获范围大于文档说明

- **入口/函数**: `AttemptLeaseStore.acquire_new_attempt`
- **文件(行号)**: `_run_state_store.py:470-475`
- **输入场景**: `INSERT INTO host_attempts` 触发 `IntegrityError`
- **实际分支**: `except sqlite3.IntegrityError` 捕获所有 IntegrityError，包括 `UNIQUE(run_id, attempt_index)` 冲突和 `PRIMARY KEY(attempt_id)` 碰撞
- **预期行为**: 文档（line 414-415）只说明 `UNIQUE(run_id, attempt_index)` 冲突触发 BUSY
- **实际行为**: PK 碰撞也走 BUSY 路径，`_build_busy_result` 查询 `(run_id, attempt_index)` 可能返回不同 attempt 的诊断信息
- **直接证据**: `_run_state_store.py:470` — `except sqlite3.IntegrityError:` 无进一步区分
- **影响**: 极低概率（UUID PK 碰撞概率可忽略）；诊断 payload 可能描述错误的 attempt
- **建议改法和验证点**: 可在 `except` 内检查异常消息是否包含 `run_id` UNIQUE 约束名，或接受当前行为并更新文档
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 5-未修复-低-owner-lost 路径双重 AttemptFencingError 导致错误报告降级

- **入口/函数**: `LocalRunHarness._run_to_store` 内层循环
- **文件(行号)**: `_run_harness.py:802-811`
- **输入场景**: Engine event 赢了 owner-lost race，返回后 owner 已失活，`append()` 抛 `AttemptFencingError`
- **实际分支**: `except Exception` → `_append_worker_failure_if_needed` → 再次 `append()` → 再次 `AttemptFencingError`
- **预期行为**: 原始 stale event 的 `AttemptFencingError` 应被记录
- **实际行为**: 第二次 `AttemptFencingError`（failure append）替换原始异常，日志只记录 failure append 错误
- **直接证据**: `_run_harness.py:802` catches Exception → `_append_worker_failure_if_needed` (line 804) also calls `append()` which fails again
- **影响**: 诊断日志降级，不影响正确性；attempt 最终由 `_finish_attempt_if_durable` 或 recovery 收口
- **建议改法和验证点**: 在 `_append_worker_failure_if_needed` 内捕获 `AttemptFencingError` 时记录原始异常上下文
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 6-未修复-低-context overflow retry 时 acquire 失败导致 Run 无 terminal event

- **入口/函数**: `LocalRunHarness._run_to_store` context overflow retry 路径
- **文件(行号)**: `_run_harness.py:936-949`
- **输入场景**: context overflow 后旧 attempt 标记为 STALE，`_begin_attempt_if_durable` 创建新 attempt 失败（如 `AttemptFencingError`）
- **实际分支**: 异常传播到 `except Exception` → `_append_worker_failure_if_needed`，但此时 `current_active_attempt` 已被 `_finish_attempt_if_durable(STALE)` 关闭
- **预期行为**: Run 应有 terminal event
- **实际行为**: `terminal_seen=False`，Run EventLog 有 `CONTEXT_COMPACT_REQUESTED` 和 `CONTEXT_COMPACT_COMPLETED` 但无 terminal event
- **直接证据**: `_run_harness.py:944-949` — `_begin_attempt_if_durable` 失败后异常传播，`finally` 块中 `_finish_attempt_if_durable` 对已 STALE 的 attempt CAS 返回 False
- **影响**: 极低概率（需要 acquire 在全新 attempt_index 上失败）；Run 残留无 terminal 状态
- **建议改法和验证点**: 在 acquire 失败时追加 Host-owned `RUN_FAILED` terminal event
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open Questions

1. **`update_state_owner_aware` 的 `finished_at` 是否应使用 `self.clock.now()`？** 该值是诊断性时间戳，不影响 lease/fencing 逻辑。但与 `AttemptLeaseStore` 的 "所有时间由 UtcClock 注入" 契约不一致。如果故意区分 lease 时间和诊断时间，应在 docstring 中说明。

2. **`AttemptOwnerToken.value` 是否应覆写 `__repr__`？** 当前明文 `value` 字段公开可访问。虽然契约要求 "明文不入库、不进日志"，但 enforcement 纯靠代码 convention。覆写 `__repr__` 返回 `masked()` 可防止 stack trace / debugger / logging framework 意外泄漏。

## Residual Risk

1. **`append_in_transaction` 生产路径零测试覆盖**：harness 主循环中非终态 scoped append 通过此方法写入，任何回归不可检测。
2. **多进程 terminal close 未覆盖真实双有效 token CAS 竞争**：当前测试结果预先确定。
3. **`_finish_attempt_if_durable` 中 `close_attempt_with_diagnostic_state` 抛 `DatabaseError` 时 `lease_exit_stack` 泄漏**（`_run_harness.py:1921-1927`）：renew loop 会继续运行最多 TTL 秒（默认 30s）后自然退出。
4. **`recover_stale_attempts(run_id=None)`（全局扫描）路径无测试**：SQL 结构与过滤扫描相似但 WHERE 子句不同。
5. **`next_attempt_index` 无直接测试**：`MAX(attempt_index) + 1` 逻辑简单但回归会导致 attempt_index 碰撞。
