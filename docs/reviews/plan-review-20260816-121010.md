## 2. Findings

### F1-未修复-严重-whole-manifest-missing 修复在 plan 内部自相矛盾，§11.3 承诺的成功场景必然失败

- **位置**：§5.2 规则 7（manifest 分类）、§6.2 step 4（Phase B 非 target 检查）、§11.3（"manifest missing repair 会基于所有 remaining complete sources 重写全量 canonical manifest，不丢 non-target item"）、goal #4/#6/#9
- **问题类型**：不可直接实施 / 契约缺失 / open question 未收敛
- **当前写法**：§5.2 规则 7 规定 manifest 完全缺失时 "为 `SOURCE_MANIFEST_MISSING`"（可修复原因，随每个 per-target classification 产生）；§6.2 step 4 规定 "取得所有非 target staged sources 的可信 canonical manifest items；**若任一非 target 不是 `COMPLETE`，抛 typed unsafe/conflict**"；§11.3 同时断言 manifest-missing repair 会成功并保留 non-target items。
- **反例/失败场景**：manifest 完全缺失且存在 ≥2 个 source（target + 任意 non-target）。按规则 7 的投影，所有 per-doc classification 都携带 `SOURCE_MANIFEST_MISSING` → 全部为 `REPAIR_REQUIRED` → 按 step 4，任何 non-target 都不是 `COMPLETE` → 抛 conflict → **repair 永远失败**，与 §11.3 的成功断言、goal #4（"重建……manifest"）直接冲突。若采取另一种读法（manifest 事实只挂到被查询的 target，non-target 仍为 `COMPLETE`），则 download 的 whole-ticker preflight（`classify_source_integrity_preflight`，`sec_download_workflow.py:580`、`cn_download_workflow.py:224`）会看到全部 `COMPLETE` → 无 repair target → 下载继续，随后 commit 时 `_validate_complete_source_kind_tree` 因 manifest 缺失/投影不一致抛 raw `ValueError` → 违反 goal #2/#8 的 typed fail closed。两种读法至少违背一个成功信号。
- **为什么有问题**：manifest disposition 是 source-kind 级事实，plan 没有指定它如何投影到 per-target classification 与 Phase B 的 "non-target COMPLETE" 判定；§6.2 step 4 的严格 `COMPLETE` 与规则 7 的 reason 传播在 whole-manifest-missing 上不可同时成立。这是 plan 自身承诺的测试场景（§11.3）与机制（step 4）的矛盾，implementation agent 无法机械落地。
- **直接证据**：plan §5.2 规则 7、§6.2 step 4、§11.3 三处原文；goal confirmation 成功信号 #4（"重建 originals/primary Docling/meta/manifest"）与 #9（"manifest missing……owner-level tests 覆盖"）；现有代码 `_fs_source_document_core.py:712-715`（manifest 缺失且有 directories 时抛 `ValueError`，证明该场景今日就是旁路点，必须被新分类闭合）。
- **影响**：实施 Agent 跑偏 / review 不可验收 / 后续返工；若按自然读法实现，manifest-missing repair 是死代码（永远 conflict），goal #4/#6/#9 无法达成。
- **建议改法和验证点**：明确投影规则，二选一并写死：(a) 规则 7 只把 `SOURCE_MANIFEST_MISSING` 挂到被查询的 exact target（inventory 时挂到全部，因为 inventory 是 whole-ticker 事实），且 §6.2 step 4 的判定改为 "non-target 必须为 `COMPLETE` 或除 `SOURCE_MANIFEST_MISSING` 外无其它 reason（即 canonicalizable）"；或 (b) 把 whole-manifest-missing 从 repair 场景中剔除（升级为 `UNSAFE` 或仅 target-only mismatch 可修），并同步删除 §11.3 的成功断言。无论哪种，都要补一个 ≥2 sources 且 manifest 全缺的明确测试节点（download preflight typed 失败 + upload repair 行为）。
- **修复风险（低/中/高）**：低（纯 plan 文本与测试矩阵修订，不涉架构）
- **严重程度（低/中/高/严重）**：严重

### F2-未修复-高-Phase B 非 target 损坏的失败类型未闭合，会被错误映射为 "目标已变化" 或落入 UNEXPECTED_RUNTIME

- **位置**：§6.2 step 4（"抛 typed unsafe/conflict"）、§5.5（只定义 `SourceIntegrityRevisionConflictError` → `SOURCE_REVISION_STALE` 的映射）、§7.1（Docling publication 捕获 exact revision conflict）
- **问题类型**：契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**：step 4 规定非 target staged source 非 `COMPLETE` 时 "抛 typed unsafe/conflict"，但未指定异常类型；§5.5 只承诺 Docling publication 把 exact `SourceIntegrityRevisionConflictError` 转换为 `SOURCE_REVISION_STALE`（文案 "目标 filing 在上传准备期间已发生变化，本次上传未提交"）。`sec_upload_workflow.py:281-306` / `cn_pipeline.py:910-935` 的 typed catch 只有 `FinsUploadFailureError`、`OSError`、`Exception`。
- **反例/失败场景**：目标 filing 损坏可修，但同 ticker 下另一个 material 或 filing 也损坏（物理缺文件）。Phase A 只分类 exact filing target（`_fs_filing_upload_state_core.py:111-123` 单 target 读取）→ validator 授权 repair → begin_batch 复制整树 → step 4 发现 non-target 非 COMPLETE。若实现把该情况也抛 `SourceIntegrityRevisionConflictError` → 用户收到 "目标 filing 已发生变化"（事实错误，目标没变）；若抛未定义的新异常且 service 不转换 → workflow generic `except Exception` → `fins_upload_failure_from_exception` → `UNEXPECTED_RUNTIME`，违反 success signal #8/#9 的 typed bounded 文案。
- **为什么有问题**：同一 Phase B 方法存在两类不同业务失败（target presence/revision/status 漂移 vs non-target/cross-source 损坏），plan 只给第一类定义了异常与 public failure 映射；第二类既无异常类型也无 closed failure code，文案真源（`upload_failure.py` 模块级 factory）也没有预留。这正是 goal confirmation 里 "损坏涉及不能由本次 target 重建的其它 source" 必须 fail closed 的语义，不能与 stale 共用文案。
- **直接证据**：plan §6.2 step 4、§5.5 原文；`upload_failure.py:37-50` 现有 closed codes（无对应 code）；`sec_upload_workflow.py:298-306` 的 `except Exception` 兜底；`_fs_storage_infra.py:1142-1255` 证明 commit validator 会拒绝含损坏 non-target 的整树，step 4 是唯一早期 fail-closed 点。
- **影响**：生成错误代码 / 用户可见错误文案失真 / review 不可验收 / 后续返工
- **建议改法和验证点**：为 step 4 指定唯一异常类型（建议 storage 层 typed `SourceIntegrityUnsafeError` 或直接 `FinsUploadFailureError`，或复用 `SOURCE_INTEGRITY_UNSAFE` 增加 distinct message），并在 §5.5 增加该异常 → public failure 的显式映射（新文案如 "工作区中存在与本次上传无关的损坏源，无法原子重建"）；§11.3 增加 "non-target material/filing 损坏 → 该 typed failure、old tree SHA 不变、rollback exactly once" 测试节点。
- **修复风险（低/中/高）**：低-中（plan 文本 + 一个新 failure factory/文案 + 一个测试节点）
- **严重程度（低/中/高/严重）**：高

### F3-未修复-中-`FinsUploadPrevalidationError`（RuntimeError）在 validator 的传播契约未闭合，runtime 入口与 workflow fresh 路径会绕过 typed failure owner

- **位置**：§5.4 precedence step 2（validator 抛 prevalidation error）、§5.5、§8.1 affected files（未列 `service_runtime.py`、`ingestion_runtime.py` 的 start/runner 异常契约、`sec_pipeline.py`/`cn_pipeline.py`）
- **问题类型**：契约缺失 / 架构边界 / 测试缺口
- **当前写法**：plan 规定 `UNSAFE` 时 `validate_fins_upload_filing_request` 抛 `FinsUploadPrevalidationError`；但该函数有三个 call site：①`service_runtime.prevalidate_fins_upload_filing_request_for_workspace`（CLI 已 catch，OK）；②`ingestion_runtime._validate_runtime_upload_request:4414`（Raises 契约文档化 ValueError/OSError，`start_upload` 同样）；③SEC/CN workflow fresh validation（`sec_upload_workflow.py:165-168`、`cn_pipeline.py:794-797`，位于 stream 的 `try:` 块之外）。
- **反例/失败场景**：preflight 时目标 REPAIR_REQUIRED，fresh read 时因并发/篡改变为 UNSAFE（或 runtime 直接以 raw request 启动，preflight 与 fresh 是同一状态）。路径③：`FinsUploadPrevalidationError` 从 async generator 首个 `__anext__` 抛出 → `_run_upload_job:4750-4751` 的 `except Exception` → `_save_failed_from_exception(job_id, exc)` → job record 只存 `str(exc)`（`ingestion_runtime.py:5685-5703`），**没有 `failure_reason` typed JSON、没有 retry_hint**，违反 success signal #8（"unsafe……使用既有 typed bounded failure owner"）。路径②：`start_upload` 的 RuntimeError 不属于其文档化 Raises（ValueError/OSError），service/host 侧只 catch ValueError 的调用方（`dayu/service/` 对 ValueError 的多处处理）不会接住它。
- **为什么有问题**：plan 新增了异常类型却没更新任何消费方的契约/处理链；"CLI/Service 只投影既有 failure" 的非目标意味着这些边界必须已经被既有机制覆盖，但 `FinsUploadPrevalidationError` 是 RuntimeError 而非 ValueError，恰好不在既有机制内。UNSAFE 是这个 work unit 的核心 fail-closed 语义，不能靠 generic job 失败记录表达。
- **直接证据**：`ingestion_runtime.py:4414-4447`（Raises 契约）、`4661-4751`（`_run_upload_job` 收口）、`service_runtime.py:61-94`（catch ValueError/OSError 转换）、`sec_upload_workflow.py:160-306`（fresh validation 在 try 外，typed catch 只覆盖 `FinsUploadFailureError/OSError/Exception`）、`upload_failure.py:53-72`（`FinsUploadPrevalidationError` 为 RuntimeError）。
- **影响**：生成错误代码 / 用户可见失败丢失 typed reason / 后续返工（一旦 UNSAFE 在 fresh 窗口出现，验收信号 #8 不成立）
- **建议改法和验证点**：plan 明确两条传播规则：(a) SEC/CN workflow 的 fresh `validate_fins_upload_filing_request` 捕获 `FinsUploadPrevalidationError` 并转换为 typed `UPLOAD_FAILED` 事件（或把 fresh validation 移入 try 并增加显式 catch）；(b) 更新 `_validate_runtime_upload_request`/`start_upload` 的 Raises 契约并确认 service/host 消费方处理该异常（或由 runtime 在启动边界将 UNSAFE prevalidation error 转换为既有 typed failure）。补充测试：fresh 时 UNSAFE → 有 typed failure_reason 的 failed event/job。
- **修复风险（低/中/高）**：低（plan 文本 + 少量既有边界的 catch 改动，均落在已列文件的直接相邻处）
- **严重程度（低/中/高/严重）**：中

- **问题类型**：契约缺失
- **当前写法**：plan 规定 snapshot 拒绝不完整 source，但不指定异常类型；§8.1 明确不改 `read_runtime.py`。
- **反例/失败场景**：`read_runtime._read_source_snapshot`（`read_runtime.py:3087-3120`）的契约是 FileNotFoundError/ValueError/OSError + 把 `SourceSnapshotConsistencyError` 单点映射为 business error。若实现用新异常类型表达 REPAIR_REQUIRED/UNSAFE 拒绝，该异常会穿透 `read_runtime` 进入 process/read 工具链（LLM-facing），既不是 typed business failure 也不是 bounded 文案；若用 ValueError 表达，则与既有 "snapshot 不完整" 语义重合但未在 plan 中声明，测试断言（§11.4 "repair 前 light/full snapshot 拒绝不完整 source"）没有可断言的异常契约。
- **为什么有问题**：read path 是 repair 之后的下游一致性核心（goal #7），"拒绝"的对外语义必须和既有 read contract 对齐；plan 把行为写了一半，留了异常类型这个唯一对外接口给实施 agent 自行决定，且该决定的正确性取决于一个不在 affected files 里的消费者。
- **直接证据**：`read_runtime.py:3087-3120` 的 Raises 契约与 `except SourceSnapshotConsistencyError` 单点映射；`_fs_source_snapshot.py:494-623`（`_read_source_snapshot` 现有异常面）；plan §7.2 与 §8.1 原文。
- **影响**：生成错误代码 / LLM-facing read 工具泄漏未定义异常 / 后续返工
- **建议改法和验证点**：plan 明确 snapshot 对 REPAIR_REQUIRED/UNSAFE 抛 `ValueError`（owner 级 bounded 文案，复用现有 read contract）并说明因此无需改 `read_runtime.py`；或若引入新 typed 异常，必须把 `read_runtime.py` 列入 affected files 并定义映射。§11.4 的 snapshot 拒绝测试断言到具体异常类型与 path-free 文案。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

## 3. Open Questions

1. **§5.2 规则 5/6 precedence**：declared-but-physically-missing 的 entry（规则 5 → repairable）与 "multiple Docling / duplicate identity"（规则 6 → UNSAFE）同时存在时，按 precedence 会判 REPAIR_REQUIRED——因为 reset+rebuild 本就会整体替换 target，该结果或许是有意的（"声明缺失总可修复，身份冲突只在实体存在时危险"），但 plan 未明说。建议在规则 6 中补充 "冲突仅限 physically present 的 entries" 或反向调整 precedence，并加矩阵用例。
2. **§7.1 `_assert_authoritative_filing_identity` 扩展语义**："同时断言 fresh repair expected target 与 identity 一致" 未定义具体断言字段。`ValidatedFinsUploadFilingRequest.__post_init__` 已保证该一致性，需明确这是冗余防御（可接受）还是另有字段（如 `expected_integrity.ticker/document_id == authoritative.normalized_ticker/document_id`），避免实施 agent 自行发明比较逻辑。
3. **deleted + damaged target 的 repair 行为**：`is_deleted=True` 且物理损坏的目标分类为 REPAIR_REQUIRED，repair 会重建并置 `is_deleted=False`（与现有 auto→update 不 skip 恢复行为一致）。plan 未显式声明，建议在 §11.2/§11.3 增加该用例或声明行为不变。
4. **inspector 对 volatile file-entry 字段的处理**：`meta.files` entries 含 `etag/last_modified/ingested_at`（`docling_upload_service.py:1683-1698`），canonical projection 与 manifest 双向比较（§5.2 规则 7、`FilingManifestItem.from_source_meta`）必须明确哪些字段参与 canonical 比较，否则同一文件 re-ingest 会造成假性 `SOURCE_MANIFEST_PROJECTION_MISMATCH`。建议 plan 指出 canonical item 的字段白名单。
