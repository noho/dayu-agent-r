### Finding 1 — [已修复] `_truncate_text` 在两个模块中重复定义（中）

**文件**: [dayu/host/_conversation_memory.py:960-973](dayu/host/_conversation_memory.py#L960-L973)、[dayu/host/_run_input_builder.py:1022-1035](dayu/host/_run_input_builder.py#L1022-L1035)

**原因**: 两个模块各自定义了语义相同、仅在 limit≤0 返回值上有细微差异的 `_truncate_text`（`_conversation_memory.py` 返回 `_EMPTY_TEXT`，`_run_input_builder.py` 返回 `""`）。违反 CLAUDE.md "重复逻辑必须抽取"。

**后果**: 未来修改截断行为需要同时修改两处，容易不一致。

**建议**: 将 `_truncate_text` 提升为 `_conversation_memory.py` 中模块级公开函数（该模块已有 `summarize_raw_turn_for_builder` 被 builder 模块引用），builder 模块直接导入复用；或抽取到 `dayu.host` 内一个私有 `_text_utils` 模块。

### Finding 2 — [已修复] `InMemoryConversationMemoryStore.project_run_events` 对并发调用无保护（低）

**文件**: [dayu/host/_conversation_memory.py:536-563](dayu/host/_conversation_memory.py#L536-L563)

**原因**: `project_run_events` 是 async 方法，但内部无 await 点，完全同步执行。当同一 session 的两个 run 的 `_project_run_events` 在不同 task 中被并发调用时（当前 harness 不会，但 store 本身无防护），存在 snapshot 读-改-写竞争：

```
snapshot = self._snapshot_by_session.get(session_id, ...)  # task A 读
snapshot = self._snapshot_by_session.get(session_id, ...)  # task B 读（读到旧值）
self._snapshot_by_session[session_id] = snapshot_A         # task A 写
self._snapshot_by_session[session_id] = snapshot_B         # task B 写（覆盖 A）
```

**后果**: P3 当前只在 `_run_to_store` finally 中顺序调用，且不同 run 的事件投影无交集（`_replace_turn` + `_merge_*` 均按 id 去重），因此实际触发概率极低。但 store 作为独立组件缺乏自防护，对后续 Phase 引入的并发使用场景构成隐患。

**建议**: 在 docstring 或 README 中明确声明该 store 的并发安全语义（当前 P3 只保证单事件循环内顺序调用）；或使用 `asyncio.Lock` 保护 `_snapshot_by_session` 的读写。

### Finding 3 — [确认不修/可接受] `_conversation_memory.py` 中 `_project_raw_turn` 冗余 `isinstance` 检查（低）

**文件**: [dayu/host/_conversation_memory.py:701-703](dayu/host/_conversation_memory.py#L701-L703)

```python
if user_event is None or not isinstance(
    user_event.data, UserInputAcceptedData
):
    return None
```

**原因**: 循环内（line 687-689）已通过 `isinstance(event.data, UserInputAcceptedData)` 过滤后才赋值 `user_event`。该二次 `isinstance` 在正常类型流中永远不会为 `False`——只有通过 `cast` 或类型系统绕过时才会命中。虽然有防御价值，但冗余代码增加了读者的认知负担。

**后果**: 无功能影响。但与此同类的 `final_event`（line 710）和 `host_failure_event`（line 718）也做了同样的二次检查——三者构成一致的防御模式。

**建议**: 可保留（与另外两处一致），不强制修改。

### Finding 4 — [已修复] `MemoryResetPatch` 和 `ClaimCorrectionPatch` 无单元测试覆盖（低）

**文件**: [dayu/host/_conversation_memory.py:589-613](dayu/host/_conversation_memory.py#L589-L613)、[tests/host/test_phase3_conversation_memory_projection.py](tests/host/test_phase3_conversation_memory_projection.py)

**原因**: `apply_patch` 的三个 patch 类型中，只有 `ScopeClearPatch`（非 SESSION scope 的 fail fast）有测试覆盖。`MemoryResetPatch` 和 `ClaimCorrectionPatch` 的路径在测试中未被执行。

**后果**: 如果 `ClaimCorrectionPatch` 的 `replace(snapshot, verified_claims=snapshot.verified_claims + (claim,))` 逻辑错误（如应替换而非追加），当前测试无法发现。P3 虽然文档声明这些是 "internal-only patch 形状"，但若后续 Phase 开始使用它们，可能继承隐藏 bug。

**建议**: 补充 `MemoryResetPatch` 清空 snapshot 和 `ClaimCorrectionPatch` 追加 claim 的基础测试。

- **`_replace_turn` / `_merge_tool_facts` / `_merge_evidence_anchors` 按 id 去重**: 对同一 run 重复投影安全。
- **trace cache FIFO 淘汰**: `_remember_run_input_build_trace` 有容量限制 (default 32) + FIFO 淘汰，有测试覆盖。

### Findings

#### Finding R1 — [已修复/待复查] `_run_input_builder` 依赖 `_conversation_memory._truncate_text` 私有 helper（中）

**文件**: [dayu/host/_run_input_builder.py:15-24](dayu/host/_run_input_builder.py#L15-L24)、[dayu/host/_conversation_memory.py:965-978](dayu/host/_conversation_memory.py#L965-L978)

**原因**: `_truncate_text` 的重复定义已经消除，但新方案是从 `_run_input_builder.py` 直接导入 `_conversation_memory.py` 的私有函数 `_truncate_text`。两者虽然都属于 Host 内部模块，但 `_truncate_text` 本身是通用文本截断 helper，不携带 conversation memory 领域语义；让 RunInputBuilder 依赖 ConversationMemory 模块的私有实现细节，会扩大 `_conversation_memory.py` 作为事实工具模块的职责，也不符合 AGENTS.md 中“模块间依赖最小化”和“优先模块级私有辅助函数”的约束意图。

**后果**: 后续维护者可能把 `_truncate_text` 视为 `_conversation_memory.py` 的内部可随意调整实现，却已经被 `_run_input_builder.py` 复用；同时通用 helper 继续挂在 conversation memory 模块下，会让 Host 内部边界变得含混。

**建议**: 将文本截断抽到 Host 内部独立小模块，例如 `dayu/host/_text_utils.py`，由 `_conversation_memory.py` 与 `_run_input_builder.py` 同向依赖；或提供一个明确非私有、语义归属清晰的 Host 内部 helper。不要从另一个模块导入下划线私有函数作为去重手段。
