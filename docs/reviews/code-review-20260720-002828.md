### 2) 七个 strict UTF-8 调用点是否都真正消费 Dayu CLI/转发输出，是否错误修改 native command 契约

- **registry `reg.exe`**：native Windows 命令，不消费 Dayu CLI 输出。

**结论：没有错误修改 native command 契约。`reg.exe`、junction、prewarm 继续使用平台默认编码。**

### 3) `text=True` + `encoding`/`errors` 跨 Python 3.11 平台行为

Python 3.11 文档明确：`subprocess.run(..., text=True, encoding="utf-8", errors="strict")` 是合法组合。当同时指定 `text=True` 和 `encoding` 时，`encoding` 覆盖默认 locale 编码。`errors="strict"` 确保任何非 UTF-8 字节序列立即抛 `UnicodeDecodeError`，而非静默替换。

在 Windows 上：
- 无 `encoding` 时，`text=True` 使用 `locale.getpreferredencoding()`，即 `cp1252`。
- 有 `encoding="utf-8"` 时，`text=True` 使用 UTF-8 解码。
- `errors="strict"` 与 `encoding="utf-8"` 组合确保行为与 Darwin/Linux 一致。

`subprocess.Popen` 同样支持 `text=True, encoding="utf-8", errors="strict"` 组合。

**结论：Python 3.11 跨平台行为正确，`text=True` + `encoding`/`errors` 组合是标准做法。**

### 4) module-help 中文断言能否形成 owner contract

`test_python_module_help_decodes_cli_output_as_strict_utf8` 在 `test_arg_parsing.py:1102-1120`：

```python
result = subprocess.run(
    [sys.executable, "-m", "dayu.cli", "--help"],
    capture_output=True,
    text=True,
    encoding="utf-8",
    errors="strict",
    check=False,
)
assert result.returncode == EXIT_SUCCESS
assert "Dayu 财报分析命令行入口。" in result.stdout
assert "dayu-cli" in result.stdout
assert "interactive" in result.stdout
```

此测试形成三层 owner contract：
1. **进程退出码 contract**：模块入口 `python -m dayu.cli --help` 必须返回 0。
2. **编码 contract**：如果输出包含非 ASCII 字符（中文），`errors="strict"` 确保 UTF-8 解码成功；若 consumer 按 cp1252 解码，中文部分会抛 `UnicodeDecodeError`。
3. **内容 contract**：help 输出必须包含中文标题 `Dayu 财报分析命令行入口。`，这是 CLI 公开 surface 的 owner 级断言。

此测试在 Darwin 上运行（`tests/cli/test_arg_parsing.py` 无 `skipif`），能有效验证编码契约。Windows 覆盖由真实 Windows workflow 的 R11/R12 gate 提供。

**结论：module-help 中文断言在 Darwin 上形成有效的 owner contract，能检测编码回归。**

### 5) R11/R12 第三轮失败是否存在另一个未分类 root cause

R11 失败链路：
- `test_windows_generated_script_runs_real_cli_into_temp_storage` 中的 `subprocess.run` 无显式 encoding → Windows ambient cp1252 → reader thread 在 `encodings/cp1252.py` 抛 `UnicodeDecodeError` → `execution.stderr` 变为 `None`。
- R11 JUnit：`3 passed / 1 failed`。真实 batch/CRT argv node 已通过，CLI storage consumer 失败。

R12 失败链路：
- `_run_init` 无显式 encoding → cp1252 → `result.stdout` 为 `None` → `_assert_init_result` 在 `mode=first not in result.stdout` 抛 `TypeError`。
- setx 节点在同一 `_run_init` consumer 中 timeout。
- R12 JUnit：init 9 nodes 中 7 个通过，2 个失败。

关键问题：**setx timeout 是否为独立 root cause？**

分析证据链：
1. `_run_init` 是单次 `subprocess.run` 调用，有 `timeout=180` 参数。
2. 如果 consumer 解码失败，`stdout`/`stderr` 变为 `None`，但 `subprocess.run` 本身不会因此 timeout。
3. setx timeout 更可能是 Windows runner 环境因素：setx 修改用户环境变量后广播 `WM_SETTINGCHANGE`，某些 runner 配置下可能延迟。
4. 但 evidence 中 setx timeout 与 decode failure 出现在同一个 test 函数（`test_windows_real_setx_round_trip_is_name_safe_and_cleaned`）的不同 `_run_init` 调用中。第一次 `_run_init`（init 操作）因 decode failure 返回 `stdout=None`，第二次 `_run_init`（setx round-trip）timeout。

**判定**：setx timeout 与 decode failure 出现在同一 test 函数的不同调用中，但 evidence 不足以证明因果关系。setx timeout 可能是：
- a) decode failure 导致 pipe drain 异常，间接影响后续进程调度（弱证据）；
- b) Windows runner 环境独立因素（setx 本身慢）（合理推测）；
- c) 其它未分类原因。

encoding 修复解决 decode failure 后，如果 setx 仍 timeout，则证明是独立 root cause。当前不能过度归因。

**结论：encoding 修复是 proven root cause；setx timeout 是否为独立问题需要第四轮 rerun 验证。Codex artifact 正确标记为 `WINDOWS_RERUN_REQUIRED`，不提前关闭。**
