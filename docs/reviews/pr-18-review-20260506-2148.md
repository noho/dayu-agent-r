## Findings

### Finding 1-已修复 — [Medium] `_handle_failure` 对所有失败路径统一设置 `denied=True`，语义不准确

**文件**: `dayu/host/_tool_runtime.py:1052-1074`

`_handle_failure` helper 在构造 `ToolFetchMoreHandleFailedResult` 时无条件设置 `denied=True`，但该 helper 被用于三种不同失败场景：

| 场景 | 调用位置 | 实际是否"权限拒绝" |
|---|---|---|
| cursor not found | `_tool_runtime.py:287-291` | 否，是资源不存在 |
| run terminal | `_tool_runtime.py:293-298` | 否，是生命周期状态 |
| binding denied | `_tool_runtime.py:299-314` | 是 |

契约 `ToolFetchMoreHandleFailedResult.denied` 的 docstring 明确定义为"是否为权限拒绝"。将"cursor 不存在"和"run 已终态"标记为 `denied=True` 会导致 API 消费方误判失败原因。

**建议**: 给 `_handle_failure` 增加 `denied: bool` 参数，对 cursor_not_found 和 run_terminal 场景传 `denied=False`。

**修复状态**: 已为 `_handle_failure` 增加显式 `denied` 参数；cursor_not_found、run_terminal、cursor_expired 返回 `denied=False`，binding/scope mismatch 返回 `denied=True`。

### Finding 2-已修复 — [Medium] `fetch_more` 中 `denied` 字段存在同样的语义膨胀

**文件**: `dayu/host/_tool_runtime.py:354-466`

`fetch_more` 方法中，以下失败路径同样无条件设置 `denied=True`：

- **cursor not found** (line 356-361): `_fetch_failure_without_event(denied=True)` — 资源不存在，非权限拒绝。
- **run terminal** (line 363-372): 直接构造 `ToolFetchMoreFailedResult(denied=True)` — 生命周期状态，非权限拒绝。

`ToolFetchMoreFailedResult.denied` docstring 同样定义为"是否为权限拒绝"。与 Finding 1 属于同一类问题。

**建议**: 对 cursor_not_found 和 run_terminal 路径设置 `denied=False`。

**修复状态**: 已修正 `fetch_more` 的 cursor_not_found、run_terminal、cursor_expired 失败语义；只有 binding、fingerprint、scope token mismatch 标记 `denied=True`。

### Finding 3-已修复 — [Low] `_replace_path` 在中间路径不匹配时静默返回未替换的副本

**文件**: `dayu/host/_tool_runtime.py:1414-1441`

```python
child = copied.get(key)
if isinstance(child, Mapping):
    copied[key] = _replace_path(...)
return copied
```

当 `field_path` 声明了嵌套路径（如 `("a", "b", "c")`），但实际数据中 `a.b` 不是 `Mapping` 时，函数静默返回原始副本，截断后的 chunk 不会被写入。这意味着：如果工具返回的 wrapper dict 结构与 `ToolTruncateSpec.field_path` 声明不一致，截断操作会静默失效，调用方拿到的是完整的原始字段值。

当前测试 `test_wrapper_requires_explicit_target` 只覆盖了"无 target"和"正确 target"两种情况，未覆盖"target 路径中间节点类型不匹配"的边界。

**建议**: 当中间路径不匹配时，至少记录一条 warning 日志；或者在 `_extract_target` 阶段就对路径做完整校验，不匹配则返回 `None`（不截断），这比静默返回错误结果更安全。

**修复状态**: 已让 `_replace_path` 在模板中间路径不匹配时显式抛出安全失败，不再返回未替换副本；并补充 field_path 中间路径不匹配不生成截断结果的测试。

### Finding 4-已修复 — [Low] 截断函数内部 `_TruncatedValue` 构造缩进不一致

**文件**: `dayu/host/_tool_runtime.py:1256-1264, 1287-1295, 1317-1325, 1354-1362`

四个截断函数（`_truncate_text_chars`、`_truncate_text_lines`、`_truncate_list_items`、`_truncate_binary_bytes`）中，`_TruncatedValue` 构造调用的后续参数比首行参数多缩进了一级：

```python
return _TruncatedValue(
    value=_apply_chunk_to_template(original, target.field_path, chunk),
        data=text,           # <- 多了一级缩进
        offset=len(chunk),
        ...
)
```

Python 语法允许此写法，但与项目其它位置的 dataclass 构造风格不一致。

**建议**: 统一为与 `value=` 同级缩进。

**修复状态**: 已统一四个截断函数中 `_TruncatedValue` 构造参数缩进。

---

### Finding 5-已修复 — [Low] `_fetch_denied_reason` 重复检查已在上层完成的 binding 校验

**文件**: `dayu/host/_tool_runtime.py:730-756`

`_fetch_denied_reason` 内部调用 `_binding_denied_reason`（line 744-751），但在 `fetch_more` 方法中，binding 校验已在 line 373-391 独立完成。如果 binding 不通过，`fetch_more` 已经提前返回 `_fetch_failure`，不会到达 line 408 调用 `_fetch_denied_reason` 的位置。

因此 `_fetch_denied_reason` 中的 `_binding_denied_reason` 调用是死代码路径。不影响正确性，但增加了理解成本。

**建议**: 将 `_fetch_denied_reason` 拆分为只校验 fingerprint + scope_token 的 `_scope_denied_reason`，去掉冗余的 binding 检查；或在函数 docstring 中说明保留原因（如防御性编程）。

**修复状态**: 已重命名为 `_scope_denied_reason`，只校验 cursor fingerprint 与 scope token；binding 校验保留在上层唯一入口。

### Finding 6-已说明 — [Low] `_terminal_cursor` 每次调用遍历全量事件列表

**文件**: `dayu/host/_tool_runtime.py:758-770`

```python
async def _terminal_cursor(self, run_id: str) -> RunEventCursor | None:
    events = await self.event_store.list_events(run_id=run_id, after=None)
    for event in reversed(events):
        if terminal_result_from_event(event) is not None:
            return event.cursor
    return None
```

`get_tool_fetch_more_handle` 和 `fetch_more` 每次调用都会触发 `_terminal_cursor`，后者读取该 run 的全部事件并遍历。对于事件量大的 run，这是 O(n) 操作。当前 P2 内存态实现可接受，但需注意后续持久化实现需要优化（如 EventStore 维护 per-run terminal cursor 缓存）。

**建议**: 无需当前修改，但建议在 `_terminal_cursor` docstring 中标注性能特征，提醒后续 Phase 优化。

**修复状态**: 已在 `_terminal_cursor` docstring 标注当前内存态实现为 O(n)，并说明 P6 持久化 EventStore 应维护 run 级终态 cursor 索引或缓存。

### Finding 7-已修复 — [Info] 测试覆盖缺口

以下边界场景在现有测试中未覆盖：

1. **executor 返回 `ToolFailedOutcome` / `ToolAwaitingOutcome` 时 `execute_tool_call` 的行为** — 当前所有测试的 fake executor 都返回 `ToolCompletedOutcome`。应验证非成功 outcome 透传且不创建 cursor。
2. **同一 cursor 的并发 `fetch_more` 调用** — single-use 语义下，第二个调用应返回 `cursor_not_found`。当前测试只覆盖了顺序调用。
3. **`_build_chunk` 策略与 data 类型不匹配** — 如 `strategy="text_chars"` 但 `record.data` 是 `list`，当前返回 `(None, 0)`，应有测试确认此行为。
4. **`_explicit_field_path` 同时设置 `field_path` 和 `target_field`** — 当前代码优先使用 `field_path`，但无测试覆盖优先级语义。

**修复状态**: 已补充非成功 outcome 不创建 cursor、同 cursor 并发 single-use、策略与 data 类型不匹配、field_path 优先级高于 target_field 的测试。
