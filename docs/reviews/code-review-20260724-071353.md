### 1-未修复-低-`ContextAnchorQuery.candidate_input_digest` 被校验但从未被 resolver 消费

- **入口/函数**: `resolve_context_anchor()` → 整个 scan loop（`context_anchor.py:404-439`）
- **文件(行号)**: `dayu/host/context_anchor.py:185-188`（校验）、`context_anchor.py:384-439`（未消费）
- **输入场景**: 任意合法 `ContextAnchorQuery` 传入 `resolve_context_anchor()`
- **实际分支**: `__post_init__` 校验 `candidate_input_digest` 为合法 sha256 digest（line 185-188），但 `resolve_context_anchor()` 扫描过程的全部逻辑（compatibility mismatch、barrier、anchor 选择）均不读取 `query.candidate_input_digest`
- **预期行为**: query 的 digest 字段若仅为 identity metadata 用途，应在 docstring 明确说明；若意图参与 integrity 校验，应实际比较
- **实际行为**: digest 校验通过后即被丢弃 — 扫描中的 `_compatibility_mismatch` 不比较 `candidate_input_digest`，也不与 anchor manifest 的 `input_snapshot_digest` 做 cross-validation
- **直接证据**: `context_anchor.py:404-439` 的整个 scan loop 中 `query` 仅用于 `before_sequence` 边界（line 465-468）、`session_id`（line 481）、以及传给 `_build_scan_items` 和 `_compatibility_mismatch`；`_compatibility_mismatch`（line 1079-1115）不读取 `candidate_input_digest`
- **影响**: 维护者可能误以为该字段提供了 anchor manifest 与当前 candidate 之间的 input-digest 一致性校验，但它只存在于 query identity 中且未被实际比较。对算法正确性无影响，但对安全审计和 code review 是误导
- **建议改法和验证点**: 在 `ContextAnchorQuery` docstring 明确标注 `candidate_input_digest` 为 "query identity only, not consumed by the resolver algorithm"；或在 `_compatibility_mismatch` 中增加对 `manifest.sizing_snapshot.input_snapshot_digest` 与 `query.candidate_input_digest` 的可选比对（需评估是否引入不必要的 barrier — 不同 candidate 的输入自然不同）

### 2-未修复-低-`ContextAnchorQuery.candidate_input_cursor` 语义耦合到 budget 模块的 token 上限

- **入口/函数**: `ContextAnchorQuery.__post_init__()`
- **文件(行号)**: `dayu/host/context_anchor.py:182-183`
- **输入场景**: `candidate_input_cursor` 为 EventLog 事件序号（非 token 数），但验证时与 `MAX_CONTEXT_TOKEN_COUNT`（2^63-1，`context_budget.py` 定义的 token ceiling）比较
- **实际分支**: `if self.candidate_input_cursor > MAX_CONTEXT_TOKEN_COUNT: raise ValueError("candidate_input_cursor exceeds supported range")`
- **预期行为**: 事件序号的上限验证不应依赖 token ceiling 常量。若将来调整 token 上限（如改为 2^31-1），anchor scan 的事件序列边界也会意外变化
- **实际行为**: 功能无问题（2^63-1 远超实际事件序列），但模块间存在不必要的常量耦合
- **直接证据**: `context_anchor.py:17-22` import `MAX_CONTEXT_TOKEN_COUNT` from `context_budget`，在 line 182-183 使用

### 3-未修复-低-`build_context_sizing_result` 调用方 `fallback_reason=None` 与 `anchor_resolution=None` 的组合约束为隐式契约

### 5-未修复-低-`_build_scan_items` 中 link parse 失败产生的 barrier 未消费链接的 usage/completion

- **入口/函数**: `_build_scan_items()` → `_BARRIER` for bad link
- **文件(行号)**: `dayu/host/context_anchor.py:550-559`
- **输入场景**: 一个 accepted iteration link row 存在但 parse 失败（`HostDurableError/TypeError/ValueError`）
- **实际分支**: line 551-558: 直接 append `_Barrier(sequence=row.event_sequence, reason=ITERATION_LINK_INVALID)`，不调用 `_consume_identity_events` 标记 usage/completion 为 consumed
- **预期行为**: 无效 link 的 usage/completion 也应在 orphan 遍历中被 consume（line 622-637），产生各自的 barrier，这是正确的 — 它们最终都会变成 barrier，只是 reason 不同
- **实际行为**: parse 失败的 link 不会被加入 `links` 列表（因为 append 到 items 而非 links），因此 orphan 遍历（line 614-621）不会检测到该 link 为 unconsumed。这不会导致错误 anchor 被选（barrier 已存在），但该 link 的 usage/completion 会作为独立 orphan barrier 出现在 items 中，reason 为 `USAGE_INVALID`/`LINEAGE_GAP` 而非 `ITERATION_LINK_INVALID`
- **直接证据**: `context_anchor.py:551-558` 不调用 `consumed_link_ids.add(row.event_id)`（无法加，因为 parse 失败拿不到 identity）；line 614-621 检测 unconsumed links 时该 link 不在 links 列表中

## Residual Risk

1. **长 session anchor scan 性能未量化**: 固定 page size 64 的 reverse keyset scan 在跨数千个 event 的 session 中可能需要多次 page fetch。当前无上限（仅在 compact boundary 停止），对于从未 compact 的超长 session（数万 events），scan 成本线性增长。这不是 correctness 风险，但应在性能 profile 中跟踪。

2. **`_build_scan_items` 中的 `Exception` catch scope**: docstring 声明 "不主动把历史损坏传播为Run失败；统一转barrier"，但 handler 只 catch `(HostDurableError, TypeError, ValueError)`。如果未来新增的 durable 操作抛出其他异常类型（如 `KeyError`、`IndexError`），会绕过 barrier 向上传播为 Run failure。建议定期审计或扩大 catch scope。

3. **`ContextSizingResult.fallback_reason` 从 non-nullable 变为 nullable 的回归面**: Slice 2 中该字段为 `ContextSizingFallbackReason`（不可为 None）；Slice 3 改为 `ContextSizingFallbackReason | None`。所有 consumer（`context_events.py`、`read_api.py`、Service mapper）均已更新处理 None 值，且测试通过。但 downstream 的 private utility / future consumer 若仍假设 non-nullable 可能产生 `AttributeError`（访问 `.value`）。当前代码库中未发现遗漏 consumer。

4. **Engine continuation 不通过 `resolve_prepared_runner_call_context_anchor_in_transaction` 统一入口**: `engine_ingest.py:3821-3841` 直接构造 `ContextAnchorQuery` 并调用 `resolve_context_anchor`，而 dispatch/admission/waiting 均通过 `run_input.py` 的 `resolve_prepared_runner_call_context_anchor_in_transaction` helper。两个路径的 query 构造逻辑不同（engine_ingest 从 manifest fields 构造，其他从 `PreparedRunnerCallCandidate` 构造）。这种并行实现增加了 query 语义不一致的风险，但当前两路径的字段映射正确（已逐项对账，见 evidence file `engine_ingest.py:3824-3839` vs `run_input.py:2537-2547`）。

5. **未有直接命中 `ContextAnchorDiagnostic.__post_init__` 的非法构造测试**: 所有测试通过 builder 函数间接创建 diagnostic，未直接构造非法 diagnostic 并验证其 `__post_init__` fail closed。由于 diagnostic 只由 `build_context_sizing_result_from_atoms` 内部创建，此覆盖缺口不影响 production 安全。
