## Assumptions Tested

1. R3 and R5 are the same boundary problem and should be in one work unit.
2. `dayu.runtime.log` currently writes diagnostic logs to stdout via `_build_marker_handler`.
3. `dayu/cli/output.py` redacts absolute paths in `_safe_text_value` treating paths as secrets.
4. `dayu/cli/commands/fins.py` `_log_fins_direct_event_received` only logs `operation`, `event_type`, and `result_status`.
5. `FinsEvent` fields are validated by `direct_events._validate_safe_text` which already rejects absolute paths.
6. `main.py` correctly forwards CLI flags to `set_level_from_flags`.
7. Slices are code-generation-ready and validation covers all relevant boundaries.
8. The plan does not touch issue-144 activity UI, issue-145 session management, or Engine/provider diagnostic redaction.

## Findings

### F01-unfixed-low-R3/R5 同 work unit 耦合依据偏弱

- **位置**: "First-Principles Judgment" 章节
- **问题类型**: 过度耦合
- **当前写法**: plan 声称 R3 和 R5 "should be handled together because both are the same boundary problem viewed from opposite sides"。
- **反例/失败场景**: R5（log stream 分离）是纯 channel 路由问题，改 `runtime/log.py` 和 `cli/main.py`；R3（path redaction 移除 + Fins diagnostic enrichment）是内容策略问题，改 `cli/output.py` 和 `cli/commands/fins.py`。二者没有数据依赖、状态机依赖或契约依赖。即使分开实施，也不存在必须同步修改的文件。
- **为什么有问题**: 从第一性原理看，这两个 residual 的 root cause 不同：R5 是 handler stream 配置错误，R3 是 redaction 策略过度泛化。把它们说成"同一边界问题的两面"是修辞，不是技术论证。
- **直接证据**: R5 的 fix 只需改 `_build_marker_handler` 的默认 stream；R3 的 fix 只需移除 `_looks_like_absolute_path` / `_redact_absolute_path_match`。两个 diff 没有交叉行。
- **影响**: 低。组合处理不会导致实施错误，只是 coupling 理由不精确。
- **建议改法和验证点**: 在 "First-Principles Judgment" 中补充："组合处理的理由是减少 coordination overhead 和共享 test 更新成本，而非技术耦合。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F02-unfixed-medium-stream 默认值变更影响全部 configure 调用方

- **位置**: Implementation Decisions #1 "Logging channel separation"
- **问题类型**: 契约缺失
- **当前写法**: "Default the runtime diagnostic stream to current `sys.stderr`, not `sys.stdout`."
- **反例/失败场景**: `_build_marker_handler` 当前硬编码 `stream=sys.stdout`。plan 改为参数默认 `sys.stderr`，意味着所有不传 `stream=` 的 `configure()` 调用方行为都会改变。虽然当前仓库内只有 `set_level_from_flags` -> `configure` 这条链路，但这是一个公共 runtime API，未来任何调用方（包括非 CLI 场景）都会受影响。
- **为什么有问题**: plan 的 stop condition 提到"Stop if moving runtime logs to stderr breaks non-CLI callers"，但没有分析当前是否真的存在非 CLI 调用方。代码核对显示 `configure()` 只被 `set_level_from_flags()` 和测试调用，非 CLI caller 风险当前为零。plan 应明确这一事实，而非留一个未分析的 stop condition。
- **直接证据**: `dayu/runtime/log.py:250` `_build_marker_handler` 使用 `stream=sys.stdout`；grep 仓库中 `configure(` 和 `set_level_from_flags(` 的调用点只有 `dayu/cli/main.py` 和测试。
- **影响**: 低。当前无非 CLI 调用方受影响，但 plan 的论证不够完整。
- **建议改法和验证点**: 在 Implementation Decisions #1 中补充："代码核对确认当前 `configure()` 只被 `set_level_from_flags()` 和测试调用，无非 CLI 生产调用方。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F03-unfixed-medium-main.py --verbose/--debug flag 未转发

- **位置**: Implementation Decisions #1; Slice 1 "Exact allowed changes"; Slice 3 "Expected assertions"
- **问题类型**: 不可直接实施
- **当前写法**: plan 声称 "argparse already normalizes `--debug`, `--verbose`, `--quiet` into `args.log_level`"，并要求 Slice 3 验证 "`--verbose` emits event summaries to `captured.err`"。
- **反例/失败场景**: `main.py:69-75` 当前把 `debug=False, verbose=False, info=False, quiet=False` 硬编码传给 `set_level_from_flags`，只用 `args.log_level`。即使 `--verbose` 被 argparse 解析为 `args.verbose=True`，该值也不会传到 `set_level_from_flags`。因此 `--verbose` / `--debug` flag 当前对日志级别没有效果。Slice 3 的 `--verbose` 测试会因为日志级别停留在 INFO 而失败——不是因为 channel 分离有问题，而是因为 flag 没被转发。
- **为什么有问题**: plan 的 "Design Alignment" 章节引用 `args.log_level` 作为证据说 "this is not a flag parsing problem"，但实际上 flag 确实没被正确使用。plan 没有在 Slice 1 的 allowed changes 中要求修复 `main.py` 的 flag 转发。
- **直接证据**: `dayu/cli/main.py:69-75`:
  ```python
  runtime_log.set_level_from_flags(
      log_level=args.log_level,
      debug=False,
      verbose=False,
      info=False,
      quiet=False,
  )
  ```
- **影响**: 中。Slice 3 的验证命令会失败，implementation agent 需要自行发现并修复 flag 转发，否则无法通过测试。
- **建议改法和验证点**: 在 Slice 1 的 "Exact allowed changes" 中增加："`main()` 把 `args.debug`、`args.verbose`、`args.quiet` 传给 `set_level_from_flags`，替代当前硬编码的 `False`。" 验证：`pytest tests/cli/test_arg_parsing.py -q` 确认 `--verbose` / `--debug` 能正确映射到日志级别。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F04-unfixed-low-path redaction 移除依赖上游 FinsEvent 验证

- **位置**: Slice 2 "Exact allowed changes"; Non-Goals "Sensitive-data policy"
- **问题类型**: 契约缺失
- **当前写法**: plan 移除 `_safe_text_value` 的 path redaction，只保留 truncation。stop condition 说 "Stop if existing Fins direct events can contain resolved provider API key values or provider headers in user-visible message/detail fields"。
- **反例/失败场景**: `direct_events._validate_safe_text` (line 418-423) 已经在 FinsEvent 构造时拒绝包含绝对路径的字段。这意味着 `_safe_text_value` 的 path redaction 对 FinsEvent 来源的数据是冗余的。但如果 `_safe_text_value` 未来被非 FinsEvent 调用方使用，path redaction 的移除会让这些调用方暴露路径。
- **为什么有问题**: plan 没有明确指出 path redaction 移除的安全性依赖于 `direct_events._validate_safe_text` 这个上游验证。这是一个隐式安全依赖，未来维护者可能不知道为什么 CLI output 不需要做 path redaction。
- **直接证据**: `dayu/fins/direct_events.py:418-423`:
  ```python
  if _ABSOLUTE_POSIX_PATH_PATTERN.search(value):
      raise ValueError(f"{field_name} contains an absolute path")
  if _ABSOLUTE_WINDOWS_PATH_PATTERN.search(value):
      raise ValueError(f"{field_name} contains an absolute path")
  ```
- **影响**: 低。当前 `_safe_text_value` 是 `output.py` 模块私有函数，只被 Fins 相关渲染调用。但 plan 应显式记录这个安全前提。
- **建议改法和验证点**: 在 Slice 2 的 "Non-goals" 或 "Expected assertions" 中补充："path redaction 移除的安全性依赖于 `direct_events._validate_safe_text` 在 FinsEvent 构造时已拒绝绝对路径。`_safe_text_value` 当前只被 Fins event 渲染调用；若未来扩展到非 FinsEvent 场景，需重新评估 path redaction 需求。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open Questions

### OQ1: Slice 3 诊断 enrichment 是否需要同步修改 `_failure_message_or_fallback`？

`_failure_message_or_fallback` 调用 `_safe_text_value(result.error_message)`。移除 path redaction 后，`error_message` 中若包含路径（虽然 `direct_events._validate_safe_text` 会拒绝），将不再被 redact。plan 的 Slice 2 没有显式提到 `_failure_message_or_fallback` 的行为变化。这不是 blocker，但 implementation agent 应确认该函数的测试覆盖。

### OQ2: Fins diagnostic enrichment 的 DEBUG log 字段是否与 `_fins_event_line` 重复？

Slice 3 要求 DEBUG log 包含 "filing kind, progress completed/total units, result title, error kind, exit code, and a bounded details summary"。而 `_fins_event_line` 已经在 stdout UI 输出中包含 `filing_kind`、`stage`、`status`、`message` 等字段。enrichment 后 DEBUG log 和 stdout UI 的信息重叠度较高。plan 应说明 DEBUG log 相比 stdout UI 增加了哪些独有信息（如 `error_kind`、`exit_code`、`completed_units/total_units`、`details`），避免 implementation agent 简单复制 UI 渲染逻辑。

## Review Conclusion

**pass-with-risks**

Plan 整体结构合理：4 个 slice 沿模块边界切分，non-goals 清晰，stop conditions 覆盖关键失败模式，validation 命令具体可执行。没有发现 blocker 级别的架构边界违反、隐藏耦合、状态机漏洞或数据安全风险。

主要风险：
- **F03（中）**: `main.py` 的 `--verbose`/`--debug` flag 未转发会导致 Slice 3 验证失败。implementation agent 需要在 Slice 1 中一并修复，而非依赖 plan 当前的 Slice 1 allowed changes。
- **F01/F02/F04（低）**: R3/R5 耦合论述、stream 默认值影响分析、path redaction 安全前提记录等方面的论证可以更精确，但不影响实施正确性。

建议在实施前将 F03 纳入 Slice 1 allowed changes。
