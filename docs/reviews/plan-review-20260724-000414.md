## 3. Findings

### F1-UNRESOLVED-CRITICAL-缺少 sizing_stage 字段与 manifest v2 contract 不全

- **位置**：plan §5.3（manifest v2 sizing snapshot table）、`_runner_call_manifest.py:260-290`
- **问题类型**：契约缺失 / 不可直接实施
- **当前写法**：plan §5.3 table 列出 `sizing_stage` 为 manifest v2 `sizing_snapshot` 的必填字段（closed enum），并列出了完整 validation invariant。但当前 production `RunnerCallSizingSnapshot` 不包含此字段。
- **反例/失败场景**：若无 `sizing_stage` 字段，`engine_ingest.py` 在 continuation 或 reactive recovery 中无法从 manifest 读取 stage 来构造正确的 `ContextSizingStage`，必须另建推断逻辑 — 这违反了 "no second owner" 和 "manifest is single truth" 的设计原则。
- **为什么有问题**：plan 称 manifest 是 sizing stage 的持久化载体（§5.3 "sizing_stage field: closed ordinary/post_compact/reactive_post_compact/dispatch_fallback"），但 manifest contract 尚未列出该字段，implementation agent 会在两个冲突的 plan assertion 之间自行选择，可能选错。
- **直接证据**：
  - plan §5.3 table: `sizing_stage` row with type `closed ordinary/post_compact/reactive_post_compact/dispatch_fallback`
  - `_runner_call_manifest.py:260-290`: `RunnerCallSizingSnapshot` 无 `sizing_stage` 字段
  - plan §7.4 consumer audit table: `_runner_call_manifest.py` row says "strict sizing snapshot接受四stage"
- **影响**：实施 Agent 可能 (a) 把 stage 从 manifest 中省略而改用调用方推断、(b) 放入 extra payload、(c) 另建 stage resolver — 三种都是语义所有权错误
- **建议改法和验证点**：
  1. 在 `RunnerCallSizingSnapshot` 增加 `sizing_stage: str | None` 字段，并在 plan §5.3 的 validation invariant 中同步更新（complete 时必填，not_applicable 时 null）
  2. `complete_runner_call_sizing_snapshot` builder 接受 stage 参数
  3. `parse_runner_call_manifest` 校验 stage 为 closed enum 四值之一
  4. 测试：manifest round-trip 保留 stage、unknown stage fail closed
- **修复风险（低/中/高）**：低 — 字段新增，不破坏现有 consumer
- **严重程度（严重）**：严重 — manifest contract 是 Slice 1 foundation，缺失此字段会导致所有 reactive/manifest consumer 找错 owner

### F2-UNRESOLVED-MEDIUM-REACTIVE_POST_COMPACT conjunction gate 无 false-positive 测试

- **位置**：plan §5.5 第四stage eligibility conjunction、plan amendment §3 frozen contract
- **问题类型**：测试缺口 / 状态机漏洞
- **当前写法**：plan 和 amendment 给出 7 条件 conjunction gate（reactive trigger + accepted CONTEXT_COMPACTED + memory caught up + Run=RECOVERING + source Attempt terminal + recovery Attempt 不存在 + complete candidate available），并声明 "不得由 pressure、runner-call kind 字符串或是否存在 Attempt 反推"
- **反例/失败场景**：
  1. proactive accepted compact（Run 仍 `ACCEPTED/QUEUED`，非 `RECOVERING`）— 合法走 `POST_COMPACT`
  2. reactive accepted compact 后 memory **未** catch-up（catch-up 失败）— 应 gate 在 conjunction 失败，走 reconciliation retry
  3. reactive accepted compact 后 recovery Attempt **已存在**（并发 winner 已 start）— 应识别 winner
  4. Run 已经 `RECOVERING` 但 source Attempt **尚未 terminal**（race with closeout）— 必须 gate
  5. 同一 Run 无 `CONTEXT_COMPACTED` 但通过 startup recovery 进入 `RECOVERING`（startup orphan recovery）— `context_compacted_event_id=None`，不属于 reactive post-compact
- **为什么有问题**：plan 只在文字中描述 conjunction，没有给出每个条件的 **negative test case name/list**，implementation agent 可能只写 happy path 的 `setUp` 而漏掉 false-positive 反例。
- **直接证据**：plan amendment §7 "Required tests" 列出 "stage选择：proactive accepted=`POST_COMPACT`、reactive accepted=`REACTIVE_POST_COMPACT`" 但未对 conjunction gate 每个条件做 false-positive 反例
- **影响**：实施 Agent 可能把 startup orphan recovery（无 compact）或 proactive accepted compact 误标为 `REACTIVE_POST_COMPACT`
- **建议改法和验证点**：在 Slice 1 test plan 中为 5 个 false-positive 场景增加 test case：proactive accepted 不走进 `REACTIVE_POST_COMPACT`、catch-up 失败 gate、recovery Attempt 已存在 gate、source Attempt 未 terminal gate、startup orphan 不走进
- **修复风险（低/中/高）**：低 — 测试增量，不改 production contract
- **严重程度（中）**：中 — 漏掉 false-positive 会导致 stage 误判，但 correction 成本低

### F3-UNRESOLVED-MEDIUM-next overflow bounded loop 的 exhausted 路径不够具体

- **位置**：plan §5.5 reactive hard + allow、plan §6.5 post-compact/fallback stage flow、plan amendment §3
- **问题类型**：状态机漏洞 / 契约缺失
- **当前写法**：plan 说 "若新的 recovery dispatch 再次收到 provider overflow，existing `max_reactive_compactions_per_run` 计数与状态机决定是否创建下一条 reactive operation；超过上限后才写真实 failed fact 并可选 tier 4/5，fallback hard 再由 existing recovering failure transition 收口。"
- **反例/失败场景**：
  1. recovery dispatch **正常完成**（不再 overflow）— Run 正常 terminal，不触发 next reactive operation
  2. recovery dispatch **再次 overflow**，`max_reactive_compactions_per_run` 内 — 创建下一条 reactive operation，`REACTIVE_POST_COMPACT` 再次 ALLOW_DISPATCH
  3. recovery dispatch 再次 overflow，**已达上限** — 写 `CONTEXT_COMPACTION_FAILED`，进入 tier 4/5 dispatch fallback
  4. tier 4/5 fallback candidate **仍 hard** — 调用 `fail_recovering_run_in_transaction` 收口 `RUN_FAILED`
- **为什么有问题**：plan 对上限 exhausted → tier 4/5 → hard → `fail_recovering_run_in_transaction` 的完整路径描述是高层的；implementation agent 需要自行推导 `engine_ingest.py` 中 reactive closeout → tier fallback → fail transition 的具体 control flow。当前 production 中 `_RECOVERY_FAILURE_POLICY_DECISION = "reactive_compact_failed"`（`engine_ingest.py:307`）似乎存在，但 plan 未 audit 它是否与新的 bounded loop 语义一致。
- **直接证据**：
  - plan §6.5: "超过上限后才写真实 failed fact 并可选 tier 4/5，fallback hard 再由 existing recovering failure transition 收口"
  - `engine_ingest.py:307`: `_RECOVERY_FAILURE_POLICY_DECISION = "reactive_compact_failed"`
  - `run_transition.py:591-615`: `FailRecoveringRunInput` 必填 `context_compaction_failed_event_id`
- **影响**：实施 Agent 可能把上限 exhausted 的 compact failed fact 写错 owner，或漏掉 tier 4/5 fallback sizing
- **建议改法和验证点**：在 plan §6.5 或 amendment 中给出 exhausted → failed fact → tier fallback → sizing → hard → fail transition 的 event ordering 序列（参考 ordinary allow 的显式序列写法）；补 test case 验证上限 exhausted 后 `CONTEXT_COMPACTION_FAILED` 真实存在且 `fail_recovering_run_in_transaction` 正常消费
- **修复风险（低/中/高）**：低 — 澄清路径，不改 contract
- **严重程度（中）**：中 — 路径可推导但不够显式，implementation agent 可能走弯路

### F4-UNRESOLVED-MEDIUM-`_pressure_and_decision` 重构未给出 exact 实现映射

- **位置**：plan §5.5 12-cell action table、`context_budget.py:961-993`
- **问题类型**：不可直接实施
- **当前写法**：plan §5.5 给出 12-cell table，但未给出从当前 9-cell `_pressure_and_decision` 到 12-cell 的具体 Python 伪代码/实现指南。当前函数 hard 一律返回 `BLOCK_HARD_THRESHOLD`，不检查 stage。
- **反例/失败场景**：implementation agent 可能 (a) 在 `_pressure_and_decision` 外面包一层 stage check、(b) 在内部加 if-elif、(c) 另写一个新函数 — 三种方案影响 `__post_init__` validation（line 535-544）和 `build_conservative_context_sizing_result`（line 811-815）。
- **为什么有问题**：`_pressure_and_decision` 的返回值被 `ContextSizingResult.__post_init__` 直接用于 validation（line 535-544）：`expected_pressure, expected_decision = _pressure_and_decision(...)` 然后 `if self.pressure_level is not expected_pressure: raise ValueError(...)`。如果 implementation agent 修改 `_pressure_and_decision` 的调用签名或行为但漏掉同步 `__post_init__`，会导致 `ContextSizingResult` 构造在合法输入上抛 `ValueError`。
- **直接证据**：
  - `context_budget.py:961-993`: `_pressure_and_decision` 当前无 stage-switch on hard
  - `context_budget.py:535-544`: `__post_init__` 调用 `_pressure_and_decision` 并断言 pressure/decision 一致
  - `context_budget.py:811-815`: `build_conservative_context_sizing_result` 也调用 `_pressure_and_decision`
- **影响**：实施 Agent 修改 `_pressure_and_decision` 但不同步更新两处调用方，导致 `ContextSizingResult` 构造失败
- **建议改法和验证点**：在 plan §5.5 增加 `_pressure_and_decision` 的 Python 伪代码（hard 分支加 `if stage is REACTIVE_POST_COMPACT: return (HARD_THRESHOLD_EXCEEDED, ALLOW_DISPATCH)`）；test 必须覆盖 12 个 cell 的 (stage, pressure) → (expected_pressure, expected_decision) 映射
- **修复风险（低/中/高）**：低 — 函数重构边界清楚
- **严重程度（中）**：中 — 两处调用方依赖同一函数，不同步会导致 runtime 崩溃

### F5-RESOLVED-BY-DESIGN-REACTIVE_POST_COMPACT hard 无矛盾 terminal facts

- **位置**：plan §5.5 reactive hard + allow、plan amendment §3
- **问题类型**：已裁决 — Controller adjudication 已冻结
- **原 blocker**：implementation-resume-codex.md 发现 reactive post-compact hard 无合法 terminal owner（`fail_unstarted_run_in_transaction` 拒绝 `RECOVERING`，`fail_recovering_run_in_transaction` 要求 `CONTEXT_COMPACTION_FAILED`）

- **验证**：路径逻辑自洽。(a) 12-cell 一致 — REACTIVE_POST_COMPACT 三种 pressure 都 ALLOW_DISPATCH；(b) `fail_recovering_run_in_transaction` 只在 `CONTEXT_COMPACTION_FAILED` 真实存在时调用（上限 exhausted），语义合法；(c) `run_transition.py` 零 diff。
- **处置**：**accepted-resolved**。Controller adjudication 已冻结此裁决。无需 plan 继续修改。
- **严重程度**：不适用（已裁决）

### F6-RESOLVED-BY-DESIGN-POST_COMPACT / DISPATCH_FALLBACK / REACTIVE_POST_COMPACT eligibility 不混淆

- **位置**：plan §5.5 第四 stage conjunction、plan amendment §3
- **问题类型**：已裁决
- **当前写法**：三条路径的 eligibility 边界清晰：

- **验证**：三条路径的 Run state、trigger source、terminal owner 互不重叠。不存在歧义。
- **处置**：**accepted-resolved**。
- **严重程度**：不适用（已裁决）

### F7-UNRESOLVED-LOW-actual request 同源验证的 digest pairing 缺少 error branch

- **位置**：plan §5.1 "AgentRunRequest 构造阶段必须读取该 frozen candidate，复核..."
- **问题类型**：契约缺失
- **当前写法**：plan §5.1 给出 `AgentRunRequest` 构造阶段要复核 4 项（Run/session/policy identity、descriptor digest、normalized messages/tool schemas re-digest、current Attempt 仍允许 dispatch），任一 mismatch 为 "input integrity failure, fail closed"
- **反例/失败场景**：worker 端 load manifest → 读 candidate payload → digest 不匹配时，应该 (a) 不 dispatch 且不写矛盾 terminal fact（因为 start transaction 已提交 manifest + RUN_STARTED + ATTEMPT_STARTED，不能回滚）、(b) 通过 Attempt terminal 收口（例如 `ATTEMPT_FAILED` with input integrity reason）— 但 plan 只说 "fail closed"，没说具体收口方式。
- **为什么有问题**：`RUN_STARTED` / `ATTEMPT_STARTED` 已 commit，worker 端 digest mismatch 无法回滚 start facts。需要明确的 terminal path。
- **直接证据**：
  - plan §5.1: "任一 mismatch 是 input integrity failure，fail closed；禁止静默重新 assemble 另一份 request"
  - production `dispatch.py::_build_frozen_run_input`: worker 按 Attempt/execution 查 manifest 并加载 candidate
- **影响**：实施 Agent 可能 (a) 抛异常导致 worker crash-loop、(b) 静默跳过、(c) 写 `RUN_FAILED` — 需要明确定义
- **建议改法和验证点**：澄清 worker 端 candidate digest mismatch 的收口方式（建议：写 `ATTEMPT_FAILED` + `RUN_FAILED` 通过 Attempt-scoped terminal closeout，不写 `CONTEXT_COMPACTION_FAILED`）。或明确 defer 到 Slice 1 后（因为这是 pre-existing worker integrity check，不是本次新增语义）。
- **修复风险（低/中/高）**：低 — 澄清现有 worker path
- **严重程度（低）**：低 — 这是既有 worker integrity path，不属于本次新引入 gap；但 plan 未说明 defer 边界
