## Accepted Findings Fix Status

### DS F1: S4 tier 1-3 recovery loop 缺少 cancellation/stale-state 观测机制

**状态: 已修复**

- **adjudication 要求**: S4 每次 tier attempt 前、proposal 返回后、commit 前的 durable Run state / input cursor / cancellation / stale-state 检查和测试。
- **plan 修复证据**:
  - §7 Decision 6: "The recovery loop must observe cancellation/stale-state before every tier attempt, after every proposal returns and immediately before commit. Proactive path uses a durable Run state observation token because no worker token exists before dispatch; reactive path reuses the run-local cancellation token from the Engine envelope."
  - §8 S4 Exact allowed changes: "Before each tier attempt, after its proposal returns and immediately before `_append_compacted_event(...)`, check durable Run state, input cursor, session state, execution identity and cancellation/stale-state. Stale, cancelled, session closed, execution replaced or cursor mismatch stops the recovery loop and must not write `CONTEXT_COMPACTED`."
  - §8 S4 Error handling: "Tier fallback must also recheck durable Run status, input cursor, session closed state, execution replacement and cancellation/stale-state before every tier attempt and immediately after every tier proposal returns."
  - §8 S4 Completion signal: "stale-state tests cover cancellation between tier 1 failure and tier 2 attempt, cancellation after tier proposal returns, and cursor/execution mismatch before commit; each case must not write `CONTEXT_COMPACTED`."
  - §9 Expected Assertions: "Tier 1-3 recovery loop cancellation/stale-state tests cover checks before tier attempt, after proposal return and before commit. Proactive path uses durable Run state observation token; reactive path reuses run-local cancellation token."
- **验证**: 三处检查点（before attempt, after proposal return, before commit）、两种路径（proactive durable token / reactive run-local token）、五种 stale 条件（stale/cancelled/session-closed/execution-replaced/cursor-mismatch）均已覆盖。与 design.md:3190 对齐。

### DS F2: S2 fallback selected caps 与 budget estimator loop 集成方式未指定

**状态: 已修复**

- **adjudication 要求**: S2 fallback selection 的 floor、fallback item cap、fallback char cap、hard budget estimator 优先级。
- **plan 修复证据**:
  - §7 Decision 4: 完整的五步 floor/cap/budget 优先级算法：
    1. 先构建 protected floor（不受 fallback caps 削减）
    2. floor-only 经 hard budget estimator 估算；若超标，路由到 tier 5 / fail closed
    3. floor 之后按 reverse material recency 追加 non-floor candidates，同时受 item_cap 和 char_cap 约束；超标 candidate 整体跳过
    4. 每次追加后经 hard budget estimator 检查；超标则回滚该 block 并停止追加
    5. 最终集合 = floor + accepted appended blocks
  - §8 S2 Exact allowed changes: 完整嵌入五步算法
  - §8 S2 Completion signal: "floor/cap/budget priority, including floor-only over hard threshold, an appended block that exceeds fallback item/char caps, an appended block that exceeds hard budget and is whole-block rolled back"
  - §9 Expected Assertions: "fallback_selected_recent_window_item_cap and fallback_selected_recent_window_char_cap are enforced... with fixed floor/cap/budget priority: floor first, floor-only hard budget check, append whole candidates under fallback caps, estimator check after each append, whole-block rollback on hard budget overflow, and tier 5 / fail closed if floor-only exceeds hard threshold."
- **验证**: 三方优先级完整且可实施，不再需要 implementation agent 自行设计 selector 语义。
