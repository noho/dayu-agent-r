# UF-FIX10 same-request-concurrency Plan Review

## Reviewed target

- **文件**: `docs/gateflow/uf-fix10-same-request-concurrency-plan-20260816.md`
- **范围**: 同请求并发 filing upload 的 batch-time recheck、canonical skip 与 typed conflict 裁决
- **日期**: 2026-08-16
- **分支**: `codex/upload-filing-oracle`

## Assumptions tested

1. per-ticker writer lock 确实串行化同 ticker 的 `begin_batch()` 等待。
2. `begin_batch()` 的 `shutil.copytree` 复制完整 ticker tree（含 company meta）到 staging。
3. `_inspect_source_kind_unguarded` 只检查 source kind，不读取 company meta。
4. 准备阶段 `_can_skip_upload` 的 identical skip 基于 source fingerprint 而非 publication identity。
5. `FilingUploadPublicationIdentity` 字段集可从 prepared 和 durable 两端完整构造。
6. `SOURCE_REVISION_STALE` 语义 owner 与新 conflict code 不重叠。
7. SEC/CN/HK 三条 workflow 的 batch 结构高度同构。

## Findings

### 01-未修复-中-§7.2 "source observation 未变" 定义与 MISSING→COMPLETE 测试断言矛盾

- **位置**: §7.2 source observation 未变精确定义，§10.1 测试断言 4
- **问题类型**: 状态机漏洞
- **当前写法**: §7.2 定义 "任一 MISSING 与 present 切换 -> 已变"。MISSING→COMPLETE 属于 "已变"，应走 CONFLICT 分支。但 §10.1 断言 4 写 "unchanged MISSING...分别 publish"，且 §9.8 说 "changed-but-equivalent exact auto 是唯一 skip 例外"。
- **反例/失败场景**: 实施 agent 严格按 §7.2 实现时，MISSING→COMPLETE 走 CONFLICT 而非 PUBLISH，导致同 document 首次并发上传的 loser 不是 skip 而是 typed conflict，与成功信号 1 矛盾。或者实施 agent 自行解读 "unchanged MISSING" 语义，产生不一致实现。
- **为什么有问题**: §7.2 的 "未变" 定义要求 initial 和 fresh 状态相同，但 MISSING→COMPLETE 是状态变化。§7.3 的 skip 条件基于 raw action 而非 resolved action，而 §7.2 要求 resolved action 一致——这两个维度在 MISSING→COMPLETE 场景下冲突。§9.8 暗示存在 "changed-but-equivalent" 路径，但 §7.2 未定义该路径的判断规则。
- **直接证据**: plan §7.2 "任一 MISSING 与 present 切换 -> 已变"；§10.1 断言 4 "unchanged MISSING...publish"；§9.8 "changed-but-equivalent exact auto 是唯一 skip 例外"。
- **影响**: 实施 agent 跑偏——可能实现为 CONFLICT（过于严格，阻断正常首次并发），或实现为 PUBLISH（违反 §7.2 定义，引入未规格化的判断逻辑）。
- **建议改法和验证点**: 在 §7.2 中明确 MISSING→COMPLETE 场景的裁决路径。建议增加规则：当 initial MISSING、fresh COMPLETE、raw requested_action == "auto"、identity exact equal 且 company keep 时，归类为 "changed-but-equivalent auto"，走 PUBLISH/SKIP 路径而非 CONFLICT。同时明确 resolved action 不等（prepared=create, fresh=update）在此场景下不触发 invariant failure。验证点：§10.1 断言 4 的 "unchanged MISSING" 应改为 "changed MISSING→COMPLETE, exact auto, equivalent identity"。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-中-§6.2 batch fresh read 的 company meta 来源未指定实现路径

- **位置**: §6.2 Batch fresh read API，§7.1 步骤 4
- **问题类型**: 契约缺失
- **当前写法**: §6.2 说 "company meta 与 filing exact target 来自同一次 writer-owned 稳定 view"，"只读该 state 的 staging_ticker_dir"，"复用现有 `_inspect_source_kind_unguarded(...)`"。
- **反例/失败场景**: `_inspect_source_kind_unguarded` 只检查 source kind（filing/material），不读取 company meta。现有 `read_filing_upload_state` 通过 `_get_company_meta_unguarded` 从 published tree 读取 company meta。如果 batch 版本也用 `_get_company_meta_unguarded`，则读的是 published tree 而非 staging，违反 "来自同一次 writer-owned 稳定 view" 的契约。如果 winner 刚 commit 了 company meta 变更，loser 的 batch read 看到的 company meta 可能与 staging source 不一致。
- **为什么有问题**: `_inspect_source_kind_unguarded` 的 ticker_dir 参数确实可以指向 staging，但它不负责读取 company meta。company meta 的读取需要单独的实现路径（要么新增从 staging 读取 company meta 的 helper，要么修改 `_get_company_meta_unguarded` 支持 staging 路径）。plan 只指定了复用 `_inspect_source_kind_unguarded`，未指定 company meta 的 staging 读取方式。
- **直接证据**: `_fs_source_integrity.py:162` 的 `_inspect_source_kind_unguarded` 签名和逻辑只处理 source kind；`_fs_filing_upload_state_core.py:111` 的 company meta 通过 `_get_company_meta_unguarded` 从 published tree 读取。
- **影响**: 实施 agent 可能直接复用 `_get_company_meta_unguarded` 读 published tree 的 company meta，导致 batch view 不是真正的 "同版" 视图。在 winner 刚修改 company meta 并 commit 的场景下，loser 看到的 company meta 与 staging source 不匹配。
- **建议改法和验证点**: 在 §6.2 中明确 company meta 的 batch 读取方式。建议新增 `_get_company_meta_from_staging(staging_ticker_dir)` helper，从 staging ticker 目录读取 company meta（因为 `begin_batch` 的 `shutil.copytree` 已复制完整 ticker tree）。或者在 `_FsFilingUploadStateMixin` 中新增 `read_filing_upload_state_in_batch` 的完整实现描述，明确 company meta 来源。验证点：测试中 spy `_get_company_meta_unguarded` 确保 batch read 不调用 published path。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-低-§7.2 与 §7.3 resolved action 一致性要求在 auto 场景下不成立

- **位置**: §7.2 步骤 "未变分支仍要求 fresh validator 的 resolved action 与 initial prepared action 一致"
- **问题类型**: 状态机漏洞
- **当前写法**: §7.2 要求 "fresh validator 的 resolved action 与 initial prepared action 一致、repair disposition 同类"，否则是 "internal invariant failure"。
- **反例/失败场景**: 当 source 从 MISSING 变为 COMPLETE 时，prepared action 是 `create`（基于 MISSING 状态），fresh action 是 `update`（基于 COMPLETE 状态）。如果实施 agent 严格执行 §7.2 的 resolved action 一致性检查，会触发 "internal invariant failure"，而非 §9.8 描述的 "changed-but-equivalent exact auto" 路径。
- **为什么有问题**: §7.2 和 §9.8 对同一场景给出了矛盾的裁决。§7.2 说 resolved action 不一致是 invariant failure；§9.8 说 changed-but-equivalent exact auto 是 skip 例外。实施 agent 无法同时满足两者。
- **直接证据**: plan §7.2 "未变分支仍要求 fresh validator 的 resolved action 与 initial prepared action 一致"；§9.8 "changed-but-equivalent exact auto 是唯一 skip 例外"。
- **影响**: 实施 agent 需要自行解读哪个优先。如果 §7.2 优先，MISSING→COMPLETE 场景失败；如果 §9.8 优先，§7.2 的一致性检查被绕过。
- **建议改法和验证点**: 在 §7.2 中明确：对于 "changed-but-equivalent" 路径（MISSING→COMPLETE 且 identity exact equal），resolved action 一致性检查不适用。建议将 §7.2 的一致性检查限定为 "source observation 未变" 分支，而非 "已变但等价" 分支。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-低-§6.1 FilingUploadPublicationIdentity 的 source 字段隐式跨模块常量对齐

- **位置**: §6.1 Storage typed publication identity
- **问题类型**: 契约缺失
- **当前写法**: `FilingUploadAssetDescriptor.source: FilingUploadAssetSource` 类型为 `Literal["original", "docling"]`。
- **反例/失败场景**: prepared 端使用 `docling_upload_service.py` 的 `_ASSET_SOURCE_ORIGINAL` / `_ASSET_SOURCE_DOCLING`；durable 端使用 `_fs_source_integrity.py` 的 `_FILE_SOURCE_ORIGINAL` / `_FILE_SOURCE_DOCLING`。如果这两组常量值不同，identity equality 永远为 False，所有 canonical skip 失败。
- **为什么有问题**: plan 假设两端使用相同的字面量值，但未显式验证或要求共享常量。当前代码中两组常量值恰好相同（`"original"` 和 `"docling"`），但这是实现巧合而非契约保证。
- **直接证据**: `docling_upload_service.py:76-77` 定义 `_ASSET_SOURCE_ORIGINAL = "original"`, `_ASSET_SOURCE_DOCLING = "docling"`；`_fs_source_integrity.py:63-64` 定义 `_FILE_SOURCE_ORIGINAL = "original"`, `_FILE_SOURCE_DOCLING = "docling"`。
- **影响**: 低概率但高影响——如果任一常量被修改而未同步，所有 canonical skip 失败，每次并发都产生 typed conflict。
- **建议改法和验证点**: 在 §6.1 中要求 `FilingUploadAssetSource` 的字面量值从 `FilingUploadPublicationIdentity` contract 层导出，prepared 和 durable 两端都必须使用该导出值，禁止各自定义私有常量。或在 identity equality 测试中断言两端的 source 值来自同一定义。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open questions

1. **MISSING→COMPLETE 的精确裁决路径**: §7.2 和 §9.8 对该场景的裁决矛盾，实施 agent 应以哪个为准？建议 plan 明确 "changed-but-equivalent" 分支的完整判断规则。
2. **company meta 的 batch 读取实现**: §6.2 的 contract 要求从 staging 读取，但未指定实现路径。实施 agent 是否需要新增 helper？还是修改现有 `_get_company_meta_unguarded`？

| explicit create 在 MISSING→COMPLETE 场景下的精确行为：plan 说 CONFLICT，但未覆盖 "auto resolved to create → fresh target exists" 的边界 | 状态机完整性 | 当前 work unit，plan 需明确 |

## Final plan review conclusion

**pass-with-risks**

Plan 的 root cause 分析准确，语义 ownership 划分清晰，per-ticker writer lock 作为线性化点选择正确，FilingUploadPublicationIdentity 字段集覆盖完整，shared publication owner 消除了三条 workflow 的重复逻辑。两个 slice 的拆分按行为增量而非模块机械划分，gate 成本与风险相称。

主要风险：
1. **Finding 01**（中）：§7.2 的 "source observation 未变" 定义与 MISSING→COMPLETE 场景的测试断言矛盾，实施 agent 可能跑偏。
2. **Finding 02**（中）：§6.2 的 company meta batch 读取实现路径未指定，可能读到 published tree 而非 staging。
3. **Finding 03/04**（低）：resolved action 一致性检查与 source 常量对齐的边界条件。

建议 plan 在进入 implementation 前修复 Finding 01 和 02 的规格缺口。
