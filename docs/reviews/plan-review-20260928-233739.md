### 3-未修复-[低]-fallback 建本地 `.venv` 后 pyright 依赖 venv 未重绑定，沿用示例命令会静默绑回主工作区
- **位置**: plan「验证路径与预期」fallback 段（「则在隔离 worktree 移除该链接，以 Python 3.11 创建真正本地 `.venv`……重跑全部身份检查、受影响测试与 pyright」）与上方示例命令第 4 行（`--venvpath /Users/leo/workspace/dayu-agent-r`）。
- **问题类型**: 契约缺失 / 不可直接实施（验证证据规格）。
- **当前写法**: 示例命令把 `--venvpath` 硬编码为依赖 venv 的父目录（主工作区）；fallback 段要求「重跑……pyright」但未定义该场景下的命令形态。
- **反例/失败场景**: 实施 gate 走 fallback 建好真本地 `.venv` 后，照抄示例命令运行 pyright → `--venvpath` 仍指向主工作区，pyright 的 site-packages/类型解析继续用主 venv，与 `source .venv/bin/activate` 后测试所用解释器身份分叉；因 missing-venv 诊断不会出现，plan 自设判据（「无 missing-venv、import 或代码树身份歧义」）全绿，错误绑定**不可从输出发现**，与 fallback 的目的（解耦主工作区）自相矛盾。
- **为什么有问题**: plan 把「pyright 诊断身份」列为 gate 证据条件，但唯一给出的 pyright 命令只在符号链接方案下成立；fallback 场景缺命令即缺证据规格。本轮微实验已证明分析对象仍会被 `--project` 配置目录钉在 worktree（影响面有限：仅第三方类型解析身份漂移），但「本地锁定依赖 venv 重跑」的证据陈述会名不副实。
- **直接证据**: `--venvpath` 语义为 venv 父目录 + config `venv=".venv"`（本轮实测解析）；fallback 段全文无替代命令；示例命令硬编码 `/Users/leo/workspace/dayu-agent-r`。
- **影响**: 验证结论名实不符、closeout 无法验收「本地锁定依赖」证据；或实施 agent 自行改命令引入新歧义。
- **建议改法和验证点**: fallback 段补一句：本地真 `.venv` 就绪后，pyright **去掉 `--venvpath`**（config `venvPath="."` 自然绑定 worktree/.venv）或改为 `--venvpath "$DAYU_WORKTREE"`，其余参数不变；验证点为命令输出无 venv 诊断、且实施记录注明该命令绑定的是本地 `.venv`。
- **修复风险（低/中/高）**: 低（只补 plan 一句话，不动设计）。
- **严重程度（低/中/高/严重）**: 低。
