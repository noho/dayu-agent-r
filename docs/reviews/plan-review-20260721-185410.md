## Findings

### 001-未修复-低-S1 entrypoint_runtime.py scope 边界需 implementation agent 显式约束

- **位置**: §7 S1 Allowed production/config modules, `dayu/service/entrypoint_runtime.py` 条目
- **问题类型**: 切片过粗 / 可能引入中间不一致状态
- **当前写法**: plan 将 `entrypoint_runtime.py` 列入 S1 allowed modules，注释说明"本slice只做async factory source propagation，使branch保持可类型检查；sole-consumer重写在S4"。
- **反例/失败场景**: implementation agent 在 S1 修改 `entrypoint_runtime.py` 时，可能误触碰 `_WatchAndWaitRuntime.queue`、`_drain_host_events` 或 `_WatcherFailure`，这些是 S4 才删除的 Service relay 组件。S1 的 scope 是"机械传播 async factory 调用"，但实际文件中 `_watch_and_wait_runtime(...)` 函数在同一文件中创建 queue 和 drain task。
- **为什么有问题**: S1 和 S4 共享同一文件的 allowed modules 列表，但语义边界不同。implementation agent 需要精确知道 S1 只改 `await host.watch_session_events(session_id)` 调用点的签名传播，不触碰 relay 组件。
- **直接证据**: `dayu/service/entrypoint_runtime.py:1009` 是唯一 production direct caller；`:1027` 创建 queue，`:1028` 创建 drain task，`:491` 定义 `_WatcherFailure`。这些在同一文件中与 `:1009` 的调用点交织。
- **影响**: 低。plan 已在注释中说明 S1 scope，但 implementation agent 可能因文件上下文过长而误操作。
- **建议改法和验证点**: 在 S1 的 Exact changes/dataflow 中增加一条显式约束："S1 不得删除或修改 `_WatchAndWaitRuntime`、`_WatcherFailure`、`_drain_host_events`、queue 创建或 drain task；这些组件在 S4 删除。S1 只修改 `:1009` 调用点为 `await`，并传播 async factory 返回类型。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 002-未修复-低-Scheduler/coordinator 构造环 resolution 细节充分但需 implementation agent 严格遵守

- **位置**: §7 S3 Exact changes/dataflow 第10条
- **问题类型**: 架构边界 / 过度耦合风险
- **当前写法**: plan 描述 `HostDispatchScheduler.open` 使用 "typed port factory" 解决构造环，factory 接收 scheduler ordinary promotion 能力并返回 `open_host` coordinator。plan 要求 "scheduler对象构造后、任何heartbeat/watchdog/worker terminal producer可运行前必须完成non-optional port bind"，并禁止运行期重新 bind 的 setter。
- **反例/失败场景**: 如果 implementation agent 允许 scheduler 在 port bind 前运行 heartbeat/watchdog，terminal producer 会调用 no-op port 而非真实 coordinator，导致 terminal notice 丢失。或者如果 factory 返回的 coordinator 捕获了尚未完全初始化的 scheduler 状态，会产生 stale reference。
- **为什么有问题**: 这是本 WU 中最复杂的构造依赖 resolution。plan 的约束是正确的，但实现细节（factory 的类型签名、bind 的时序保证、失败时的资源清理）需要 implementation agent 高度精确。
- **直接证据**: `dayu/host/dispatch.py:1118` 定义 `wake_queue_promotion`，`:1153` 定义 `tick_active_cancel_watchdog`，`:1862` 定义 `_fail_unstarted_in_transaction`。这些是 scheduler-owned terminal producer，需要在构造后立即可用。
- **影响**: 低。plan 已充分描述约束，implementation agent 只需严格遵守。
- **建议改法和验证点**: S3 的测试矩阵应包含一个显式测试：scheduler 构造后、port bind 前调用 terminal producer，断言 fail fast 而非静默 no-op。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 003-未修复-低-asyncio.to_thread callback 执行域隔离的线程池耗尽风险

- **位置**: §4.7 Service observation 状态机, callback 执行描述
- **问题类型**: 并发恢复风险
- **当前写法**: plan 描述 Service 用 `asyncio.to_thread` 执行 callback，"outer cancellation时先等待已启动callback job收口并禁止late slot commit，再继续consumer/iterator cleanup"。
- **反例/失败场景**: 如果 CLI renderer callback 阻塞时间过长（例如大量 output 需要写入 TTY），`asyncio.to_thread` 可能耗尽默认线程池。虽然 plan 限制 "同一consumer同时最多一个callback job"，但如果多个 Session 的 consumer 同时阻塞，可能影响 Host event loop 的其他 `to_thread` 调用。
- **为什么有问题**: 这是 plan 已识别的风险（"避免CLI renderer/I/O阻塞opener event loop"），但 plan 未明确线程池大小约束或 timeout。当前 Python 默认线程池大小为 `min(32, os.cpu_count() + 4)`。
- **直接证据**: `dayu/service/entrypoint_runtime.py` 当前使用同步 callback（如 `on_activity`、`on_thinking`），CLI renderer 在同一执行域。plan 要求迁移到 `asyncio.to_thread`。
- **影响**: 低。单个 Session 最多一个 callback job，且 CLI 通常是单用户场景。但极端情况下（interactive 模式快速连续 submit）可能短暂阻塞。
- **建议改法和验证点**: 在 S4 的 Tests/assertions 中增加一个显式测试：callback 阻塞期间 Host 其他 `to_thread` 调用（如 durable operation）仍可完成。或在 plan 中明确 "callback 使用独立线程池 executor"。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
