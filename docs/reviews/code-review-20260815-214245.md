## Findings

### 1-未修复-中-skip 指纹不含 authoritative primary 角色，primary 变更被静默丢弃
- **入口/函数**: `DoclingUploadService.prepare_upload` → `_build_upload_source_fingerprint` →
  `_can_skip_upload`
- **文件(行号)**: `dayu/fins/pipelines/docling_upload_service.py:346-367`（skip 判定）、
  `1223-1272`（filing fingerprint 公式）、`1275-1295`（version 判定）
- **输入场景**: 同一 filing 以同一组文件、相同内容再次 `auto` 上传，但把 `--primary` 从文件 A 改声明为文件 B
  （A/B 内容不变；A/B 可为同 basename 不同目录，也可为不同 basename）。
- **实际分支**: fingerprint 由 `original_filename`、`sha256`、`size`、`source` 的排序多集构成，不含角色事实；
  角色翻转后 descriptor 集合完全相同 → fingerprint 相同 → `_can_skip_upload` 返回 True →
  `prepare_upload` 在 `_build_pending_assets`（唯一消费 `require_primary()` 的位置）之前返回 skipped。
- **预期行为**: 按本 work unit 的核心 contract，primary 是显式 validated fact（goal 3.1.6-3.1.9）；用户变更
  primary 声明后，published `primary_document` 与 downstream 消费的 derived 内容应跟随新 primary，
  或者至少以 typed 失败/更新路径暴露该变更，而不是宣称“文档已存在且未变更”。
- **实际行为**: 静默 skip；storage 的 `primary_document`/`derived_from` 继续指向旧 primary identity；
  当 A/B 内容不同时，`process_filing`/read runtime 继续处理旧 primary 的 Docling 内容，用户新声明的
  主文件角色被无事件、无警告地忽略。`--overwrite` 可以绕过（`_can_skip_upload` 对 overwrite 返回 False），
  但默认 auto 路径没有任何信号。
- **直接证据**: 指纹 payload 只含四字段且按 `(original_filename, sha256, size, source)` 排序
  （`docling_upload_service.py:1241-1258`）；skip 判定只比较 `previous_fingerprint == source_fingerprint`
  （`1195-1220`）；`selection.require_primary()` 在 skip 分支不可达（`prepare_upload` 控制流 342-367 先于
  370 的 `_build_pending_assets`）；测试目录 grep 无任何“换 primary 重传”覆盖。
- **影响**: 静默语义失效——持久化 primary 指针与用户显式声明分歧，下游消费内容与用户意图分歧；
  恰好发生在 UF-FIX07 要消灭“primary 是副作用”的边界上（旧系统按顺序推断 primary 时同样存在该盲点，
  属携带缺陷，但显式 primary 使被丢弃的事实成为 authoritative 事实）。
- **建议改法和验证点**: 在 filing fingerprint 中纳入 validated selection 的角色事实（如 primary 的
  `original_filename` 或独立 role 标记），使 primary 翻转触发 update/version increment；或让 skip 决策在
  比较指纹前核对 `selection` 与已发布 primary 的一致性。补充 owner 级测试：同文件集、内容不变、仅
  `--primary` 翻转的 auto 重传必须 update（`primary_document` 指向新 primary derived），而非 skipped。
  注意：修改 fingerprint 公式会同时影响既有旧 schema source 的首次重传行为（见 Residual R1），
  需与 UF-FIX08 边界联合裁决。
- **修复风险（中）**: 公式变更触及 plan §6.6 冻结的 fingerprint contract 与已断言 move-identical-skip
  语义，需 controller 裁决是否在本 work unit 内修订或转入后续 work unit。

### 2-未修复-低-Fins README 声明“按输入顺序读取”，实现按角色顺序（primary 优先）读取
- **入口/函数**: `DoclingUploadService.prepare_upload` 的 original 读取与 `files[]`/事件顺序投影
- **文件(行号)**: `dayu/fins/README.md:572`（声明）vs `dayu/fins/upload_format_contract.py:402-418`
  （`ordered_files = (primary, *companions)`）与 `docling_upload_service.py:298-301, 329`
  （`_validate_source_files(selection_preparation.ordered_files)`）
- **输入场景**: 多文件 filing 且 primary 位于 `--files` 非首位置（本 work unit 新增的核心场景）。
- **实际分支**: `_build_original_assets` 迭代 role order（primary 在前，companions 保持原相对顺序），
  因此 primary 非首项时，originals 的读取顺序、storage `files[]` 顺序与 `file_uploaded` 事件顺序均为
  primary 优先，不是输入顺序。
- **预期行为**: 与 plan 一致——plan §6.2 只冻结 companions 相对顺序，未承诺输入顺序读取；README 应如实
  描述角色顺序。
- **实际行为**: README 断言“全部 originals 会在 publication batch 开始前按输入顺序读取”，与实现不符。
- **直接证据**: 上述行号对照；100-file 测试（`test_docling_upload_service.py:2965-3011`）只断言集合与计数，
  未断言顺序，因此该漂移未被任何测试捕捉。
- **影响**: 文档契约与行为漂移；未来维护者按 README 理解 `files[]` 顺序会误判。当前无运行时消费者依赖
  顺序（fingerprint 排序、snapshot 按 meta 顺序），不构成数据错误。
- **建议改法和验证点**: 将 `dayu/fins/README.md:572` 改为“按角色顺序读取（authoritative primary 在前，
  companions 保持原相对顺序）”；或在测试中显式断言 `files[]` 顺序以固化所选语义。
- **修复风险（低）**: 纯文档措辞或单一测试补充。

- R1：filing fingerprint 从旧 `name`-keyed 公式迁移为 `original_filename`-keyed 公式后，既有旧 schema
  source 的首次重传必然不命中旧 fingerprint，触发全量 update/version increment。plan §12 已分类给
  UF-FIX08，本次不判为 finding，但 F2 若修订公式应一并考虑该迁移面。
- R2：`original_filename`/`derived_from` 只存在于持久化 raw meta；storage snapshot 的 typed
  `SourceSnapshotFileDescriptor` 不承载这两项，当前无消费者。若未来增加 LLM-facing 文件列表投影，
  必须在 snapshot typed 投影中补充字段，禁止从 raw meta fields 反推（semantic ownership drift 风险）。
- R3：同 basename 的 original 与 derived 会生成同名 `file_uploaded` 事件（仅 payload.source 区分），
  属 plan §6.6 冻结的事件映射，用户事件层存在展示歧义，当前无下游依赖。
- R4：SEC/CN 上传完成 result 的 `files` 字段投影 raw 请求的绝对本地路径（`sec_upload_workflow.py:261`、
  cn 同构），属 diff 外既有行为，不是本次回归；若路径隐私要求收紧需另行裁决。
- R5：optional real Docling integration 默认 skip，UF-PF07/UF-PF12 真实 evidence 未执行（plan 已授权
  后续 evidence gate）；本地验证覆盖 deterministic owner 契约。
- R6：tool adapter 层既有的文件存在性/非空预检与 delete+files 拒绝使用英文文案，slice-2 acceptance
  已分类为非本 work unit 范围，仍有 LLM-facing 文案不统一风险。
- R7：`_build_filing_original_asset_identity` 的防御性二次 resolve 在 symlink 目标于 validation 与
  preparation 之间变化时（TOCTOU）以内部不变量 ValueError fail closed，映射为无文件标签的通用失败；
  概率极低，未进一步处理。
