## Findings

### 1-未修复-中-compact 异常路径丢失 AttemptFencingError 导致 RunStream 无终态

- **入口/函数**: `_run_to_store` -> `_append_compact_exception_failure`
- **文件(行号)**: `_run_harness.py:916-924`, `_run_harness.py:1528-1535`
- **输入场景**: owner lease 在 `_compact_or_fail` 执行 `_scope_appender().append(...)` 期间被 fencing（renew loop 检测到 storage error 或被其他进程 CAS 替换）。compact 方法抛出 `AttemptFencingError`。
- **实际分支**: `except Exception as exc:` (line 916) 捕获 `AttemptFencingError`，路由到 `_append_compact_exception_failure`。该方法在 line 1528 再次调用 `_scope_appender().append(context_compact_failed_draft(...))`，内部 `verify_owner` 再次失败抛出第二个 `AttemptFencingError`。该异常不被同一 `except` 块捕获，沿 `ToolRuntimeOwnerScope.__aexit__` -> `_close_engine_events_if_supported` (finally) -> `_finish_attempt_if_durable` (finally) 传播。`_finish_attempt_if_durable` 调用 `close_attempt_with_diagnostic_state`（CAS miss，静默返回 False），不写 terminal RunEvent。
- **预期行为**: 当 compact 异常路径遇到 `AttemptFencingError` 时，应路由到 `_handle_owner_lost`（使用 `supervisor.append_terminal_and_close` 原子 CAS 写入 `RUN_FAILED(error_code=attempt_lease_lost)` 终态事件），与 `_OwnerLostDuringEngineWait` 路径 (line 793-804) 行为一致。
- **实际行为**: RunStream 订阅者永久等待不到终态事件。attempt 在 `host_attempts` 中被标记为 STALE/FAILED，但 EventLog 无终态 RunEvent。recovery scan (P8-S6) 可将 attempt 标记为 LOST，但不写 EventLog 诊断事件。
- **直接证据**:
  - `_run_harness.py:916`: `except Exception as exc:` 捕获所有异常含 `AttemptFencingError`
  - `_run_harness.py:1528`: `_scope_appender().append(...)` 使用 scoped appender，内部 `verify_owner` 会再次抛 `AttemptFencingError`
  - `_run_harness.py:1177-1232`: `_handle_owner_lost` 正确使用 `supervisor.append_terminal_and_close` 原子路径
- **影响**: RunStream 订阅者 hang（无终态），RunResult 查询永远返回 None。窗口虽窄（owner 必须在 compact append 期间丢失），但 storage 压力或慢 I/O 时 renew 可失败使此路径可达。
- **建议改法和验证点**:
  1. 在 `_append_compact_exception_failure` 入口捕获 `AttemptFencingError` 并路由到 `_handle_owner_lost`：
     ```python
     except AttemptFencingError:
         return await self._handle_owner_lost(...)
     ```
  2. 或在 `_run_to_store` 的 line 916 `except Exception` 中增加 `AttemptFencingError` 分支，优先于通用异常处理。
  3. 验证点：构造 owner 在 compact append 期间被 fencing 的场景，确认 RunStream 收到终态。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 3-未修复-中-owner token hash 比较未使用 timing-safe 函数

- **入口/函数**: `AttemptLeaseStore.renew` / `_diagnose_fence`
- **文件(行号)**: `_run_state_store.py:1145`
- **输入场景**: 任何 fencing 判断路径（renew、close_terminal、verify_owner 等内部调用 `_diagnose_fence`）。
- **实际分支**: `if current_hash != expected_hash:` 使用普通字符串 `!=` 比较 SHA-256 hex digest。
- **预期行为**: 使用 `hmac.compare_digest` 进行 timing-safe 比较，与项目自身 precedent 一致（`_tool_runtime.py:1119` 对 scope token 使用了 `hmac.compare_digest`）。
- **实际行为**: 普通 `!=` 比较，理论上存在 timing side-channel。
- **直接证据**: `_run_state_store.py:1145`: `if current_hash != expected_hash:` vs `_tool_runtime.py:1119`: `if not hmac.compare_digest(...)`。
- **影响**: 实际风险极低（SHA-256 hex digest 64 字符，timing 差异微小），但与项目自身安全实践不一致。模块 docstring 声称 "timing-safe verification"。
- **建议改法和验证点**: 改为 `if not hmac.compare_digest(current_hash, expected_hash):`，导入 `hmac`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中（安全实践一致性）

### 4-未修复-低-Repair 路径全 EventLog 扫描效率问题

- **入口/函数**: `DurableConversationMemoryStore._fetch_canonical_events_for_session`
- **文件(行号)**: `_conversation_memory_durable.py:349-364`
- **输入场景**: `startup_reconcile` -> `repair_missing_session_snapshots` 被调用且存在 session snapshot 缺失。
- **实际分支**: 按 position 顺序遍历 **全部** EventLog 事件，在 Python 层按 `session_id` 过滤。
- **预期行为**: 使用 `session_id` 范围查询或索引过滤，避免 O(total_events) 全扫描。
- **实际行为**: `_REPAIR_FETCH_BATCH_LIMIT=256` 控制内存但不控制总工作量。对大型 EventLog（数千 session），每个需修复的 session 都触发一次全表扫描。
- **直接证据**: `_conversation_memory_durable.py:349-364`: `fetch_events_by_position(after=after, limit=...)` 无 `session_id` 过滤。
- **影响**: 仅 startup 路径，生产中 snapshot 误删罕见。但若发生，启动延迟与 EventLog 大小成正比。
- **建议改法和验证点**: 考虑在 `DurableRunEventStore` 增加 `session_id` 范围查询方法，或在 `host_run_events` 表增加 `(session_id, kind)` 索引。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F1/F2 CAS hit / CAS miss 行为说明

`_handle_owner_lost` 内部统一调用 `AttemptSupervisor.append_terminal_and_close`,
在单事务 `BEGIN IMMEDIATE` 内做:

1. CAS hit: `verify_owner` 通过 → 写入 terminal `RUN_FAILED(error_code=attempt_lease_lost)`
   RunEvent + 收口 `host_attempts(state=LOST, terminal_event_position, failure_summary)`;
   RunStream 订阅 condition variable 由 InMemoryRunEventStore / DurableRunEventStore 在
   subscribe loop 检测到 terminal RunEvent 后自然 break, 上层 `async for` 顺序结束。
2. CAS miss: `verify_owner` 失败 (例如 recovery scan 已先把 fencing_token 推进) →
   ROLLBACK, **不**向 EventLog 追加任何 stale RunEvent; 真正终态由 recovery scan 真源补齐。
   此情况下后台 `_run_to_store` task 完成后无 EventLog terminal, 旧实现会让 RunStream
   永远阻塞在 `_subscribe` 的条件变量上 → 本次修复在 `start_run` 引入
   `_task_aware_event_stream` 包装: `events` 在 (a) subscription 自然终结、
   或 (b) 后台 task 完成且 0.05s drain 窗口内无新事件时, 主动 break async for,
   不抛 user-visible 异常。RunStream 公共 dataclass 字段不变, 不引入新的 close API。
