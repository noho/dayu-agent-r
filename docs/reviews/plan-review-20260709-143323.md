## Scope

本 review 对 umbrella plan 做 adversarial plan review，判断它是否足够 code-generation-ready，能否安全交给后续 sub WU implementation。重点挑战目标成立性、scope、sub WU sequencing、slice 切分、owner boundary、状态机/Schema 风险、LLM-facing 文本约束、测试矩阵、residual risk 和后续 full-repository deepreview 阶段是否足够明确。

用户指定压测重点：
- P0-B 是否足够处理 preprocess/upload typed result、`ingest_method` 和 success rule 真源。
- P1-C 是否区分业务可读"等待工具结果"与 Host治理"等待状态/后续调度"。
- P2-A 是否真的把 session resume、Fins direct result fallback、HostApiError 映射放回正确 owner boundary。
- P2-C 是否能消除 Engine/Runtime fallback prompt 双真源，而不引入反向依赖或兼容 wrapper。
- 全部 sub WU 完成后追加多轮全仓 deepreview 的 gate 是否足够可执行。

## Assumptions Tested

1. P0-B allowed files/modules 覆盖了全部 `ingest_method` 使用点。
2. P1-C 的 "等待工具结果" 分类标准对 implementation agent 可执行。
3. P2-A 的 session resume boundary 方案已收敛到唯一可实施路径。
4. P2-C 的 `AgentPolicy` prompt 必填化迁移范围已被充分评估。
5. 每个 sub WU 的 stop condition 覆盖了合理失败场景。
6. Full-repository deepreview phase 的终止条件和执行方式足以防止过早 closeout。
7. 8 个 sub WU 的依赖顺序不会导致 P0-B → P1-C 的工具语义漂移。

### 02-高-P1-C "等待工具结果" 分类标准对 implementation agent 不充分

- **位置**: Umbrella plan §6 P1-C "非目标" (line 429) 与 "预期 contract" (line 431-436)
- **问题类型**: 不可直接实施 / open question 未收敛
- **当前写法**: 非目标写 "不把所有'等待工具结果'字样机械删除；只删除或改写会让模型承担 Host治理判断的文本"。预期 contract 写 "Fins tool schema/error/hint 改为业务动作与业务结果描述，不出现'等待状态''后续调度'等 Host治理概念"。但 plan 没有给 implementation agent 提供可操作的分类标准。
- **反例/失败场景**: Implementation agent 面对以下文本时无法独立裁决：

  - `"下载任务启动失败，未进入等待状态"` (download_tools.py:105) — "未进入等待状态" 是明确的治理泄漏，但 implementation agent 可能因为 "等待" 二字出现在工具失败消息中而犹豫是否保留。
- **为什么有问题**: Plan 承认 Engine design 允许 "等待工具结果返回" 出现在 tool schema 中（line 421），但 review source 将此列为 finding。Plan 的非目标说 "不机械删除"，但没有给 implementation agent 裁决边界。Agent 可能过度删除（把 Engine-design-approved 的业务描述也删了）或保留过多（因为不确定而保留所有含 "等待" 的文本）。

- **影响**: 实施 Agent 跑偏 —— 可能删除 Engine-design-approved 文本导致工具 schema 降低 LLM 理解能力，或保留 governance 文本导致 review 发现不被关闭。

  2. "未进入等待状态" / "等待状态" / "后续调度" — 当出现在 tool outcome/failure message 时属于 Host governance 泄漏，删除或改写。
  3. "宿主取消" / "不要把本次取消视为业务失败" — Host governance LLM-facing 文本，其默认值必须从 runtime 移除。
  4. `tool_duplicate_governance.py` 的 "相同工具请求已经进入等待状态" — 需裁决：此文本是否进入 LLM 上下文？如果是，它是治理泄漏。
- **修复风险（低）**: 纯分类标准补充，不改变 plan 结构。
- **严重程度（高）**: 高 —— Engine design 与 review source 对同一短语有不同立场，plan 承认矛盾但不裁决。Implementation agent 无权裁决 design 真源与 review 真源的冲突。

### 03-高-P2-A session resume boundary 方案未收敛，implementation agent 需自行做架构决策

- **位置**: Umbrella plan §6 P2-A "预期 contract" (line 510-513)
- **问题类型**: 架构边界 / 不可直接实施
- **当前写法**: "为 existing-session prompt/interactive 提供 public reusable CLI/Service boundary，或把 session resume 逻辑下沉到 Service entrypoint helper" — 两种方向性不同的方案以 "或" 并列。
- **反例/失败场景**:
  - 方案 A（CLI public boundary）：将 `_execute_prompt_on_existing_session` 等四个私有函数改为公开，加入 `__all__`。风险：`prompt.py` 和 `interactive.py` 的公开 API 膨胀，且 session.py 仍跨模块导入 CLI 内部实现——CLI-to-CLI coupling。
  - 方案 B（Service entrypoint helper）：在 `dayu/service/entrypoint_runtime.py` 新增 `resume_session_prompt(...)` / `resume_session_interactive(...)` 公开 helper。风险：需要在 Service 层定义 session resume 语义，当前 `entrypoint_runtime.py` 是否已有相关接口？是否需要新增 contract？
  - 方案 C（隐式）：不做任何新 public API，保持现状但标记为技术债。不符合 P2-A 目标。
- **为什么有问题**: 这两个方案涉及不同的 owner boundary、不同的测试矩阵、不同的 README 更新需求。让 implementation agent 在 sub WU plan 阶段做这个选择，相当于把架构裁决从 umbrella controller 层级下放到 sub WU implementer——而 implementer 的上下文只有 P2-A，没有全貌。
- **直接证据**:
  - `session.py:38-44`: 从 prompt.py 导入 `_execute_interactive_on_existing_session`, `_prepare_interactive_existing_session_execution`, `_execute_prompt_on_existing_session`, `_prepare_prompt_existing_session_execution` — 全部是 `_` 前缀私有函数。
  - prompt.py `__all__` 和 interactive.py `__all__` 均不包含这四个函数。
- **影响**: 实施 Agent 跑偏 —— Agent 可能选择表面上工作量最小的方案（改为公开 + 加入 `__all__`），但这是 CLI-to-CLI coupling，违反分层架构。Controller 在 P2-A review 阶段可能否决，导致返工。
- **建议改法和验证点**: Controller 在 P2-A plan 之前裁决：
  1. 如果选方案 A（CLI public），必须在 plan 中说明为什么 CLI-to-CLI coupling 是可接受的，以及未来 prompt/interactive 重构时的 contract 稳定性保证。
  2. 如果选方案 B（Service），必须在 P2-A root-cause confirmation 阶段确认 `entrypoint_runtime.py` 的当前接口能否承载 session resume，或需要新增什么 contract。
  3. 方案 A 和 B 的测试矩阵不同——方案 B 需要新增 Service 层测试。
- **修复风险（中）**: 需要 controller 做架构裁决后再进入 P2-A plan。
- **严重程度（高）**: 高 —— umbrella plan 在架构边界问题上使用 "或" 并列，等于把设计裁决推给 implementation agent。CLAUDE.md 要求 "优先选择可维护、可测试、可演进的方案"，但 plan 没有给出选择依据。

### 04-高-P2-C prompt 必填化迁移范围被低估，且未区分 Engine 自身构造路径

- **位置**: Umbrella plan §6 P2-C "Residual risk" (line 684-686) 与 "预期 contract" (line 652-656)
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: Residual risk 仅写 "Many tests directly construct `AgentPolicy`; migration is mechanical but broad. Do not add test-only defaults to production." 预期 contract 写 "所有 production and test `AgentPolicy(...)` 构造路径显式传入 prompts。"
- **反例/失败场景**:
  1. plan 没有提供 `AgentPolicy(...)` 构造路径的数量级估计。如果 50+ 处测试构造 `AgentPolicy`，mechanical migration 会触及大量测试文件，P2-C 作为最后一个 sub WU 可能被测试迁移拖慢 umbrella closeout。
  2. Engine 内部 `agent.py` 是否自己构造 `AgentPolicy`？如果是，Engine 需要从何处获得 fallback_prompt 和 continuation_prompt？Engine design §5 说 `AgentPolicy` 是 "Agent loop 的运行策略真源" 且 "fallback_prompt 是 force-answer 模式追加给 Runner 的用户消息"——如果 prompt 变为必填，Engine 的 `_build_runner` 或 `_AsyncAgent` 是否需要新增参数？
  3. `dayu/runtime/assembly.py` 当前通过 `code_default.fallback_prompt` 作为 fallback source——把 prompt 变为必填后，`assembly.py` 的 role 从 "提供 fallback" 变为 "必须提供 resolved value"，需确认 assembly 在所有调用路径上都有有效的 prompt 来源。
- **为什么有问题**: Plan 声称 "不引入反向依赖或兼容 wrapper"，但要把 Engine `AgentPolicy` 的默认值移除，必须有一个替代的真源在 Engine 调用方（Service assembly）传入。如果 assembly 路径上存在未覆盖的调用点（例如 Engine 测试中直接构造 `AgentPolicy` 且没有 assembly context），implementation agent 可能：
  - 在 Engine 侧新增 config loader 依赖（反向依赖，违反架构约束）。
  - 在测试中引入 test-only default helper（兼容 wrapper，违反 CLAUDE.md "禁止兼容性代码"）。
- **直接证据**:
  - `agent_policy.py:62-63`: `fallback_prompt` 和 `continuation_prompt` 有 Engine 级默认值。
  - `config_loader.py:41-43`: `_DEFAULT_FALLBACK_PROMPT` 在 runtime 层另有独立定义。
  - `config_loader.py:923`: `default_fallback_prompt()` 返回 runtime 默认值。
  - 两处默认值的文本不同：Engine 版是 "请基于目前已经获得的上下文直接给出最终回答，不要再调用工具。"；runtime 版是 "请基于已获得的信息直接回答问题。信息不足时必须说明不确定性，不得编造。"
- **影响**: 实施 Agent 跑偏 —— 可能引入 Engine → runtime config 的反向依赖，或在 Engine 测试中保留旧默认值为 test-only fallback，形成新的双真源。
- **建议改法和验证点**:
  1. 在 P2-C plan 前，用 `rg "AgentPolicy\(" dayu/ tests/` 全量统计构造点数量并按层分类（Engine 内部 / Service assembly / Host assembly / 测试）。
  2. 明确 Engine 侧的 `AgentPolicy` prompt 字段改为必填后，Engine 自身（`agent.py`, `_default_runner.py`）是否还构造 `AgentPolicy`——如果是，这些点必须从 request 中获得 prompt。
  3. 不要在 `AgentPolicy.__post_init__` 中恢复 config loader 默认值——这会把 runtime config 反向依赖引入 Engine。正确做法是 Service assembly 统一从 runtime config 解析后传入。
- **修复风险（低）**: 纯前置统计和设计澄清，不改变 plan 方向。
- **严重程度（高）**: 高 —— P2-C 涉及跨层依赖风险（Engine ← runtime config），plan 未说明如何避免反向依赖。且 Prompt 双真源消除是最容易引入新架构违规的操作之一。

### 05-中-Full-repository deepreview phase 的执行细节不足以防止过早 closeout

- **位置**: Umbrella plan §8 "Full-repository deepreview phase" (lines 714-732)
- **问题类型**: open question 未收敛 / 不可直接实施
- **当前写法**: "Run at least two independent full-repository semantic ownership deepreviews over current workspace" → "Controller adjudicates every finding" → "Repeat until a round produces no new accepted current-umbrella findings"
- **反例/失败场景**:
  1. "at least two independent" — 由哪两个 agent 执行？当前原始 review 是 AgentMiMo + AgentDS 双路。deepreview phase 是用同样的两个 agent 还是不同组合？如果用相同 agent，可能因为相同的盲区而漏检。
  2. "over current workspace, not only changed files" — 当前一次 full-repo deepreview 的 token 成本很高（原始 review 产生了两份 artifact，覆盖 5 个 shard）。多轮 deepreview 的成本没有被估算。
  3. "until a round produces no new accepted current-umbrella findings" — controller 是同一人吗？如果 controller 在连续多轮 review 后产生裁决疲劳，可能放宽 accepted 标准以加速 closeout。
  4. plan 没有定义 "round" 的边界：一轮 deepreview = 一次双路 review + controller 裁决 + 修复全部 accepted findings？还是一轮 = 一次双路 review，修复和 deepreview 交替？
- **为什么有问题**: 如果 deepreview phase 的执行方式不明确，controller 可能：
  - 在第一轮 deepreview 发现 0 个 finding 时就 closeout（因为盲区未覆盖）。
  - 在连续发现 low-severity findings 时无限循环（没有 exit budget）。
  - 因为成本压力而降低 review 深度。
- **直接证据**: Plan line 723: "Repeat full-repository deepreview until a round produces no new accepted current-umbrella findings, or all new accepted findings have explicit owner/destination." — 缺乏 agent assignment、review dimension checklist 和 cost budget。
- **影响**: review 不可验收 —— deepreview phase 可能形式化执行（两个 agent 都只做 shallow scan）就宣布 "no new findings"。
- **建议改法和验证点**:
  1. 在 umbrella plan 中明确第一轮 deepreview 的 review agent 组合（建议至少一个不同于原始 MiMo/DS 的 agent，或指定一个 adversarial reviewer role）。
  2. 定义 deepreview 的 minimum review dimensions：至少覆盖 Engine contracts、Host durable、Host projection、Fins contracts、CLI/Service boundary、LLM-facing text、config/prompt、tests import boundary。
  3. 设定退出条件：至少两轮 deepreview 无新增 accepted finding，或连续两轮只产出 severity ≤ Medium 且 controller 裁决 deferred-with-owner 的 finding。
  4. 如果 deepreview 轮数超过 3 轮仍有 new accepted findings，controller 必须写 escalation artifact 说明是否继续或 defer。
- **修复风险（低）**: 纯流程细化，不改变架构。
- **严重程度（中）**: 中 —— 不阻塞 sub WU 启动，但 umbrella final closeout 的验收严谨性取决于此 phase 的执行质量。

### 06-中-P0-B preprocess success rule 的 typed helper 范围与 Fins storage 持久化边界未澄清

- **位置**: Umbrella plan §6 P0-B "预期 contract" S1 (line 223-226)
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: "提供单一 `preprocess_result_status(summary)` 或等价 helper，direct/job/awaiting 均复用"
- **反例/失败场景**: `FinsPreprocessResultSummary` 当前已经在 `ingestion_runtime.py:597-618` 定义。`to_json_summary()` 方法已经在产出 JSON。S1 的 "提供单一 helper" 是指：
  - 在 dataclass 上增加 `is_successful() -> bool` 方法？（范围最小，只影响 `ingestion_runtime.py`）
  - 还是在 Fins domain 层新建 `FinsPreprocessOutcomeStatus` 枚举 + helper？（需要在 `dayu/fins/domain/` 新增模块）
  - 两者的 allowed files 和测试矩阵不同。
- **为什么有问题**: Plan 说 "具体命名由 sub WU plan 按现有 Fins pattern 确认"，但 `is_successful()` 的返回值和 `preprocess_result_status()` 的返回类型是不同的语义层。前者是 boolean 判定，后者可能是枚举（success / partial / failed）。如果 sub WU plan 选了枚举但下游只需要 boolean，会增加不必要的类型转换。
- **直接证据**:
  - `ingestion_runtime.py:2769-2784` 和 `ingestion_runtime.py:3198-3204` 使用相同布尔表达式判定失败——这是两个消费者。
  - `FinsPreprocessResultSummary` 的 `to_json_summary()` 已经将 summary 序列化为 JSON，用于 job record 持久化和 direct stream 返回。
  - 如果 `is_successful()` 的计算逻辑需要变更（例如 `not_supported_count > 0` 不再算失败），需要同时更新 job record 消费者和 direct stream 消费者。
- **影响**: 实施 Agent 跑偏 —— Agent 可能只在 dataclass 上加 `is_successful()` 方法而忽略 job record / direct stream 的 JSON 消费者也依赖同一语义。
- **建议改法和验证点**: P0-B sub WU plan 在 root-cause confirmation 阶段确认：
  1. `is_successful()` / `preprocess_result_status()` 的返回类型和消费者列表。
  2. job record 中持久化的 `skipped_count` / `not_supported_count` 在修复后的兼容策略（按全新 schema 起库处理，P0-B non-goal 已声明）。
  3. direct stream 返回的 JSON summary 中是否增加 `not_supported_count` 字段。
- **修复风险（低）**: 纯 scope clarification。
- **严重程度（中）**: 中 —— 不影响 P0-B 整体方向，但 sub WU plan 的 scope 目前不够具体。

### 07-中-P1-B `RUN_LOST` public outbox 行为裁决缺失

  - `durable/outbox.py:63-69`: `_TERMINAL_STATUSES` 不含 `"lost"`。
  - `durable/outbox.py:71-76`: `_TERMINAL_EVENT_TYPES` 包含 `RUN_LOST`。

- **影响**: 后续返工 —— P1-B S1 可能因 design gap 而暂停，等待 design doc 更新，打乱 sub WU 顺序。

### 08-中-P2-B memory/test hardening 的 finding obsolete 判定标准缺失

- **位置**: Umbrella plan §6 P2-B "Residual risk" (line 615-617)
- **问题类型**: open question 未收敛
- **当前写法**: "Some findings may be obsolete due to recent fixes. Controller should accept evidence-based no-op for obsolete findings rather than force churn."
- **反例/失败场景**: P2-B 的 MiMo 08 (final-answer continuity) 和 MiMo 12 (pending digest sentinel) 的 finding 状态依赖于 WU-CLI-SMOKE-01 的最近修复。Plan 自身承认 "`dayu/host/_terminal_answer.py` 和 `dayu/host/terminal_payload.py` 已存在 final-answer continuity helper，说明 MiMo 08 已部分关闭"。如果这些 finding 在 root-cause confirmation 阶段被确认 obsolete，P2-B 的 S2 slice 可能变成 0 工作量 slice——但 umbrella plan 仍要求 "implementation, review, fix, re-review, accepted commit"。
- **为什么有问题**: Plan 的 "Controller should accept evidence-based no-op" 和 umbrella execution protocol 的 "每个 sub WU 必须独立完成 implementation artifact" 存在矛盾。如果 finding 是 obsolete，sub WU 不应该有 implementation slice——它应该产出 "finding-obsolete-confirmation" artifact 并跳过 implementation/commit gates。
- **直接证据**:
  - Plan line 572: "`dayu/host/_terminal_answer.py` 和 `dayu/host/terminal_payload.py` 已存在 final-answer continuity helper，说明 MiMo 08 已部分关闭。"
  - Plan line 573: "未找到精确 `snapshot_digest=\"pending\"` 模式" — MiMo 12 的 pending digest finding 可能已经是 obsolete。
- **影响**: 后续返工 —— Controller 可能在 P2-B review 时被迫裁决 obsolete finding 的 gate 流程，浪费 implementation + review 的 token 成本。
- **建议改法和验证点**: P2-B 的 root-cause confirmation 阶段产出明确的 finding 状态表：active（需要实现）/ obsolete-with-evidence（跳过实现）/ needs-design-update（先更新设计真源）。Obsolete finding 只需 confirmation artifact + controller acceptance，不需要 implementation/commit artifact。
- **修复风险（低）**: 纯流程优化。
- **严重程度（中）**: 中 —— 不阻塞 sub WU 启动，但可能浪费实现和 review 资源。

### 09-低-Umbrella execution protocol 缺少 sub WU 失败的全局回滚策略

- **位置**: Umbrella plan §5 "Umbrella execution protocol" (lines 69-93)
- **问题类型**: 状态机漏洞
- **当前写法**: "任何 sub WU 有 unclassified residual risk、accepted finding 未修复、re-review 未通过、schema/contract owner 无法裁决或验证失败，controller 必须停下裁决，不得进入下一个 sub WU。"
- **反例/失败场景**: Controller 停下裁决后，已完成的 sub WU（例如 P0-A 和 P0-B）的 commit 已经 accepted。如果 P1-A 的 schema 变更与 P0-B 的 typed contract 冲突（例如 accepted evidence envelope 的 `query_text` 字段命名与 P0-B 的 `FinsUploadPipelineResult` 字段名冲突），controller 需要回滚 P0-B 的 commit 还是修改 P1-A 的 schema 选择？
- **为什么有问题**: Plan 说 sub WU 是串行的且每个都有 accepted commit，但没有说明如果后续 sub WU 发现与已接受 sub WU 的 contract 冲突时如何处理。这不太可能发生（因为 sub WU owner boundary 不同），但 P0-B（Fins typed result）和 P1-A（Host accepted evidence）可能在 "tool result summary" 的语义边界上有交集。
- **直接证据**: plan 没有定义 sub WU commit 之间的冲突解决策略。
- **影响**: 风险后移 —— 如果真的发生冲突，controller 需要临时裁决，可能打破 umbrella 的串行顺序。
- **建议改法和验证点**: 在 umbrella plan 中增加 "Sub WU contract 冲突处理"：如果已完成 sub WU 的 contract 与当前 sub WU 的 contract 冲突，先更新受影响的设计真源，再决定是修改已完成 sub WU（amend commit）还是在当前 sub WU 中做 schema mapping。
- **修复风险（低）**: 纯流程补充。
- **严重程度（低）**: 低 —— 不太可能发生，但 umbrella plan 作为 8 个 sub WU 的总控文档应覆盖此场景。

### 10-低-P0-A RunnerContentCompletedData.finish_reason 移除的迁移影响未量化

- **位置**: Umbrella plan §6 P0-A "预期 contract" (line 127-128)
- **问题类型**: 不可直接实施
- **当前写法**: "推荐 contract：从 `RunnerContentCompletedData` 和 `ContentCompleteData` 移除 `finish_reason`；若 plan review 认为迁移影响过大，最小替代方案是 Agent 在 `RunnerDoneData` 到达时无条件以 done finish reason 覆盖 state"
- **反例/失败场景**: Plan 没有回答 "迁移影响有多大"——这个量化应该是 plan review 的一部分。如果 `RunnerContentCompletedData.finish_reason` 被 Host ingest 消费（直接或间接），移除字段会导致 Host 侧 `AttributeError`。
- **为什么有问题**: Plan 把一个需要在 plan review 阶段回答的问题（"迁移影响有多大"）推给了 P0-A sub WU plan 的 root-cause confirmation。但 root-cause confirmation 是在 sub WU plan 阶段做的，不是在 umbrella plan review 阶段做的。如果迁移影响过大导致 P0-A 只能选最小替代方案，umbrella 的 "消除双真源" 目标未完全达成——content-completed 的 `finish_reason` 仍然存在，只是不再被 Agent 消费。
- **直接证据**:
  - Plan line 127-128: 两个方案以 "若...最小替代方案" 并列。
  - Review MiMo 01: 推荐方案 (a) "从 `RunnerContentCompletedData` 移除 `finish_reason` 字段"。
- **影响**: 风险后移 —— 如果最小替代方案被采用，`RunnerContentCompletedData.finish_reason` 字段仍然存在（只是不再作为权威源），未来可能被新代码重新消费。
- **建议改法和验证点**: P0-A sub WU plan 的 root-cause confirmation 必须量化 `ContentCompleteData.finish_reason` 的全部消费方（Host ingest、投影层、test fixtures）。如果消费方数量 ≤ 3 且都不是契约关键路径，坚持方案 (a) 移除字段。如果消费方数量 > 5 或涉及 public contract external consumer，才考虑方案 (b)。
- **修复风险（低）**: 纯 quantification 要求。
- **严重程度（低）**: 低 —— plan 已给出两个清晰方案，只是未量化取舍条件。

## Architecture Boundary Review

整体架构边界检查通过。8 个 sub WU 的 owner boundary 定义与 Host/Engine/Fins/CLI/Config 分层一致：

- P0-A（Engine Runner authority）→ Engine contracts，不跨层。
- P0-B（Fins typed result）→ Fins domain/ingestion，不跨层。
- P1-A（Host evidence projection）→ Host evidence/ingest/projection，不跨层。
- P1-B（Host event/cancel durable）→ Host durable state/transition，不跨层。
- P1-C（LLM-facing cleanup）→ Fins tools + Host compact/prompt + Runtime，跨层但按文本投影边界（不是架构反向依赖）。
- P2-A（CLI/Service boundary）→ CLI + Service，方向正确（Service 在 CLI 下层）。
- P2-B（Memory/test hardening）→ Host + Tests，不跨层。
- P2-C（Config fallback prompt）→ Engine contract + Runtime config + Service assembly，涉及三层但方向正确：Runtime config → Service assembly → Engine `AgentPolicy`。

需要注意的风险：
- P2-C：Engine `AgentPolicy` prompt 必填化后，Engine 自身不能反向依赖 Runtime config。Plan 当前没有说明 Engine 侧如何获得 resolved prompt 值——如果 Engine 内部还需要构造 `AgentPolicy`（例如 Engine 测试中），需要从调用方传入而非从 config loader 读取。
- P1-C 涉及 Runtime 层的 `tool_call_projection.py`——把 `message` 和 `hint` 改为必填后，调用方（`doc_tools.py`, `web_tools.py`, `fins_tools.py`）需要在自身层级提供文本。这是正确的 owner boundary 移动（从 Runtime 移到 Tool 层），不引入反向依赖。

## Best-Practice Review

- **Single source-of-truth pattern**：每个 sub WU 的目标都是为此 pattern 服务，方向正确。
- **Slice 切分**：P0-A 3 slices / P0-B 3 slices / P1-A 3 slices / P1-B 3 slices / P1-C 3 slices / P2-A 2 slices / P2-B 2 slices / P2-C 2 slices。总计 21 slices，每个 sub WU 的 slice 数在 control doc 的默认 budget 内（1-3 个 slices）。P2-A 和 P2-C 的 2-slice 拆分合理（contract+behavior vs test+doc）。
- **测试矩阵**：每个 sub WU 列出了验证命令，使用 `pytest` + `pyright` + `git diff --check`。但部分测试命令的覆盖面需要 sub WU plan 阶段确认——例如 P0-B 的测试命令包含了 `tests/fins` 但没有区分哪些测试覆盖 `ingest_method` typed contract 迁移。
- **README 触发规则**：每个 sub WU 列出了 README 检查要求，与 CLAUDE.md 的 README 更新触发规则对齐。
- **Propagation audit**：每个 sub WU 要求在 closeout 时做 propagation audit，覆盖 durable state → trace → memory → UI 路径。这是正确的但 P0-B 的 propagation audit 范围不够明确（Fins direct stream → CLI rendering → Service awaiting → Host wait-adapter result 的链路需要端到端验证）。

## Optimal-Solution Review

- 拆成 8 个 sub WU 而不是一次大改：正确的选择。语义 owner 不同、验证矩阵不同、回滚风险不同。Finding 06 对此有补充观察。
- P0-A → P1/P2 的先行顺序：正确的选择。Host durable usage 和 terminal facts 必须消费 corrected Engine events。
- P2-C 放在最后：理由合理（涉及最多测试文件修改，放到最后减少 rebase churn）。但如果 P0-A/P0-B 的 contract 变更导致 AgentPolicy 构造路径变化，P2-C 的 prompt 迁移可能需要在更早阶段部分执行——plan 应该标记这是低概率但高影响的依赖反转风险。
- P1-C 放在 P1-A 之后：正确。如果 P1-A 没有建立 typed evidence projection contract，P1-C 的文案清理会变成在 loose contract 上做表面文字替换，无法根治问题。

## Overengineering Review

- 无过度设计发现。每个 sub WU 只围绕一个语义闭环，没有引入新平台层、通用 registry、或 "以后可能" 的抽象。
- P0-B 的 `FinsPreprocessOutcomeSummary` / `FinsUploadPipelineResult` / `FinsIngestMethod` 三个 typed contract 是必要的，不是过度设计——它们各自服务不同的语义 owner（preprocess result, upload result, source classification）。
- P1-A 选择了 "扩展 envelope 或新增 sibling atom" 两种路径——plan 没有预选一种，这是正确的，留给 root-cause confirmation 决定。不是过度设计。

## Overcoupling Review

- P1-A 的 consumer migration (S3) 触及 5 个消费者（Tool Trace, Memory, RunInput, CompactMaterial, Read API）。所有消费者从同一个 typed projection helper 读取——这是正确的去耦合方向，不是过度耦合。
- P2-A 的 session resume 边界如果选择方案 A（CLI public），会创建 CLI-to-CLI coupling。Finding 03 已覆盖。
- P1-C 的 S2（compaction prompt/schema ownership）涉及 Host 预标注 evidence/trace category——需要注意预标注逻辑不应耦合到具体的 tool provider 实现。Review DS 08 已指出 wait_adapter 和 tool schema description 的脱节问题，P1-C 如果引入 tool-type-aware 预标注，需要避免 wait_adapter 对 tool provider 的耦合。
