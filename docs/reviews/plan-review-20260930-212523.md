## 2. 总控待裁决问题的裁决（结论先行）

1. **候选阻断 B1：不成立（作为单 slice 的 fundamental blocker）**。plan 的不可能性证明建立在两个非必需前提上：(a) 把 G1“读取/索引次数”记账成含既有完整性扫描的整 run 总账、并要求跨 publication 索引持续有效；(b) plan §4 自设的“一次解析同时喂 accepted IDs/repair 排序/filing-start/Phase A”dataflow（与 G2 直接冲突，又被 plan §6 自己否定）。按“新增身份读取/重复锁”口径、每个稳定 publication 窗口一次 inventory、复用已有 inspection 事实，O(D+S) 在有限 API 内可达（详见 §7），不需要持久 index、长锁或新 generation 系统。
2. **候选阻断 B2：部分成立但分类错误**。跨 writer 并发同 source 新绑定在**今天就检测不到**（Phase B 为 target-only revision 比较；今日 resolve 也在 stream 开始处一次定身份），属既有局限，不能升为本 slice 必须的“写入前集合唯一性”新系统。批量缓存真正会引入的新回归只存在于 plan 假设的“run 级一次索引”设计；按 per-stream 窗口解析则新鲜度与今日逐次 resolve 完全一致，且 HK 候选 source_id 结构性唯一使自碰撞不可达（§5.2）。
3. **候选阻断 B3：成立（作为必须钉死的契约规则），且 plan 自己的候选 API 不足以实现它**。UNSAFE 当 None-as-missing 是真实回归，有具体失败路径（§5.3）；但 §5 的 `SourceInventoryEntry(classification, source_meta|None)` 只投影可信业务 meta，**投影不了今日身份 owner 实际消费的 raw 身份字段**，必须扩展 typed identity observation（§4-F2）。
4. **当前目标是否过强：是（as elaborated）**。“完整 selected run O(D+S) 读取/索引次数”（plan §8 验收行）+ G2 字面“任何 publication 变化后不得复用”+ §8“另一个 document 新绑定同 source 即使旧 target revision 未变也不可错误发布”三者合计超出原 F4 的“消除重复 meta/独立锁读取、storage 一致批量 snapshot、不跨发布 stale cache”。这是 goal drift 放大器，不是用户数学复杂度硬约束。建议总控按下文 §6 措辞钉死度量，**不建新系统**。
5. **最小可行下一入口**：总控钉死 G1 度量口径（goal clarification，按 plan 规则若改 goal 文本须走 goal confirmation）→ Sol 修订 plan（单 slice、per-window 消费、B3 API 修形、B2 降级）→ 同版复审/总控裁决 → 实施。**全程不需要超原范围 public 生命周期**；唯一可能越界的是 commit 内集合唯一性检查（会碰 `_fs_storage_infra.py`），按 §10 作为独立 issue 候选交总控，不并入 F4。

## 4. Findings

### 4-1-未修复-高-目标度量被记账成整 run 总账，B1 成为 goal drift 放大器

- **位置**：binding goal G1 成功信号“单批次 O(D+S) 的读取/索引次数”；plan §1 结论、§7 B1、§8 验收行“完整 selected run 的复杂度”。
- **问题类型**：目标漂移 / 过度验收标准。
- **当前写法**：plan 把 G1 解释为完整 selected run（含所有 publication 之后的刷新）读取与索引总量 O(D+S)，并把每次发布后为剩余候选刷新全量库存的 `S·D+S(S-1)/2` 读取量当作 G1 的账（B1 反例），进而断言“逐次刷新全量快照只改变常数，仍可能 O(S·D)”“不能把在这些扫描上每次重建全量身份索引说成 O(D+S)”。
- **反例/失败场景**：实现 agent 若按此验收记账，只有两条路：要么删/绕既有 Phase A/B 全树正确性扫描（goal 明令不改），要么建跨 publication 增量契约/持久索引（plan 自己列为禁止替代路径）——死路。
- **为什么有问题**：原 F4（`pr-197-full-review-adjudication-20260929.md`）的缺陷是“重复 meta 读取 + 独立锁窗口 + stale cache 风险”，修法是“同 guard 批量快照”。goal 的“读取/索引次数”最自然口径是**身份可归因的读取/锁操作次数**（今日每 resolve = 1 次 list + D 次独立 guard 的 `get_source_meta`，×~4S 调用点；这正是动机）。把既有正确性扫描（A3 证实本来就 O(D)）计入身份成本、再要求整 run 总账 O(D+S)，是把低优先性能项升级成数学复杂度硬约束。plan 一边承认两者要区分（§7 B1 第 2 段），一边拒绝按可归因口径记账，自相矛盾。
- **直接证据**：原裁决 F4 三段（动机/修法/禁止项）；goal G1 文本；`_inspect_source_kind_unguarded` 两种模式全量扫描（`_fs_source_integrity.py:170-183`）；plan §7 B1 的 `D+(D+1)+…` 算式本身假设“每发布后为剩余候选 eager 刷新”。
- **影响**：实施 Agent 跑偏（过度建设或死路）；review 不可验收；总控被倒逼批准新系统。
- **建议改法和验证点**：按 §6 措辞钉死度量（每稳定 publication 窗口一次 inventory、复用已有 inspection 事实、身份查询 O(1)/候选、不计既有扫描）；B1 改写为“度量澄清项”而非契约缺口；验收行改为按窗口计新增身份读取/锁次数（window-1 一次 + 每 filing stream 一次共享读取 + O(S) 查询）。
- **修复风险（低/中/高）**：低。
- **严重程度（低/中/高/严重）**：高。

### 4-2-未修复-高-候选 SourceInventoryEntry 形状无法实现 plan 自设的 B3 约束，照抄会产生持久 duplicate 绑定

- **位置**：plan §5 `SourceInventoryEntry` 候选与“UNSAFE 无可信 meta 时保留 typed classification 与 None，不跳过、默认成空字典或分配新 ID”；§7 B3。
- **问题类型**：契约缺失 / 会导致错误代码。
- **当前写法**：entry 只有 `(integrity: SourceIntegrityClassification, source_meta: Mapping[str, JsonValue] | None)`，meta 仅来自 inspection 的**可信** business_meta。
- **反例/失败场景**：存在 source A：meta 可解析、含 `source_provider/source_id=X/internal_document_id`，但因 provenance/文件声明等问题被 inspection 判 UNSAFE（`business_meta=None`）。今日 `resolve_cn_download_ids` 读 raw meta（`cn_download_identity.py:32-44`）**会匹配并绑定 A**，随后 Phase A 对 A 判 UNSAFE 抛 `SourceIntegrityPreflightError` fail-closed（`cn_download_filing_workflow.py:172-173`），不产生写入。换成 None-as-missing：索引看不见 A → candidate 走 allocated 分配新 ID B → Phase A 对 B 为 MISSING → 正常提交 → **A、B 两份文档同时携带 source_id=X，持久 duplicate**；后续 run 的 resolve 将抛“同一下载来源对应多个文档”（`cn_download_identity.py:45-46`）。direct 调用 `run_cn_download_single_filing_stream`（tests 直接调用、模块 `__all__` 导出）无 ticker preflight 兜底，此路径今天就能走到提交。另一方向：meta 不可解析时今日 resolve 扫描即抛 `FileNotFoundError/ValueError`（`_fs_source_document_core.py:829-867` 的 get_source_meta 语义经 resolve 透传），None-as-missing 会把它变成静默或 UNSAFE_PUBLICATION，同样是错误投影变化。
- **为什么有问题**：G3“缺内部 ID 拒绝”、G4“duplicate、internal-ID、异常语义保留”被破坏；错误从“绑定后 fail-closed”漂移成“重新分配并写入”；语义 owner 边界被绕过（identity 的拒绝规则依赖的输入事实没有 owner 投影）。
- **直接证据**：`cn_download_identity.py:32-44`（raw meta 匹配与拒绝）；`_inspect_source_directory` 早期 UNSAFE 返回即丢 meta（`_fs_source_integrity.py:484-587`）；`FilingManifestItem.from_source_meta` 对空 `internal_document_id` 抛 ValueError → META_UNTRUSTED（`document_models.py:985-989` + `_fs_source_integrity.py:576-587`）；Phase A fail-closed（`cn_download_filing_workflow.py:172-173`）；`_deduplicate`/duplicate 拒绝（`cn_download_identity.py:45-46`）。
- **影响**：生成错误代码；持久数据语义损坏（duplicate 绑定）；后续 run 不可用。
- **建议改法和验证点**：entry 增加与可信业务 meta 分离的 **typed identity observation**（同次 inspection 观察到的 `source_provider/source_id/internal_document_id` 存在性与值 + meta 可读性/identity 一致性），仅用于绑定与拒绝，不冒充可信业务 meta；identity 的 index 构建逐 entry 复刻今日扫描语义（不可读/identity 不一致 → 同族 `FileNotFoundError/ValueError`；可读 → 原匹配/缺 internal ID 拒绝/duplicate 拒绝/allocated 财期纠正 digest 分配，规则一字不放宽）。验证点：owner 测试覆盖 (i) untrusted-but-identifiable + match → 不分配新 ID 且错误投影与今日一致；(ii) unparseable sibling → 扫描期抛错不变；(iii) REPAIR_REQUIRED 可信身份保留、参与绑定；(iv) UNSAFE entry 不为空字典/不跳过。
- **修复风险（低/中/高）**：中（需 storage 投影与 identity 消费两侧对齐，但都在既有 owner 边界内）。
- **严重程度（低/中/高/严重）**：高。

### 4-3-未修复-中-B2 把既有 target-only 重验局限升为新系统验收，goal drift

- **位置**：plan §7 B2；§8 验收行“另一个 document 新绑定同 source 即使旧 target revision 未变也不可错误发布”；§6 表“Phase B/current write”。
- **问题类型**：目标漂移 / 过度验收标准。
- **当前写法**：以“锁外下载期间另一 writer 发布 document B 占用同 source_id”反例，要求新方案证明写入时来源集合唯一性，否则不批单 slice。
- **反例/失败场景（分类）**：(a) **既有局限**——今日 Phase B 仅 target revision 比较（`cn_download_filing_workflow.py:604-610` + `source_integrity.py:262-287`），今日 resolve 在 stream 开始（:164）到 commit 之间同样存在该竞态；这不是批量读取引入的。(b) **新回归（仅 plan 假设设计下）**——若一次索引喂整个 run，staleness 窗口从“单 filing 时长”扩到“全 run 时长”，且若批内同 source_id 候选存在会破坏合并语义；但 A8 已证明 HK 批内 source_id 结构性唯一、CN 不走绑定，(b) 的自碰撞分量不可达，staleness 分量被 per-stream 窗口设计（§7）消除。
- **为什么有问题**：G3 是“保持唯一绑定”（保留既有 duplicate 拒绝规则），不是“写入时事务性集合唯一”。把 (a) 升为本 slice 验收，等于把既有增强议题强制成新持久约束/新系统，违反“不把原有增强议题自动升为当前必须的新系统”与原 F4 范围。
- **直接证据**：A9 全部证据；writer lock 为 ticker 级 begin_batch 才持有（`_fs_storage_infra.py:417-465`），读路径无 writer 串行化——今日结构如此。
- **影响**：范围漂移；实施 Agent 过度建设（commit 集合断言/持久 schema）或被阻断。
- **建议改法和验证点**：验收行改为“保持 resolve 时 duplicate/缺 internal ID/财期纠正分配规则与错误投影不变；Phase B target revision 比较、skip/overwrite、三轮 churn 重试、rollback/commit 所有权不变”；跨 writer 集合唯一性写入 residual 并登记独立 issue 候选（§10）。
- **修复风险（低/中/高）**：低。
- **严重程度（低/中/高/严重）**：中。

### 4-4-未修复-中-plan §4 dataflow 与 G2 自相矛盾，是 B1 反例的设计前提

- **位置**：plan §4 期望 dataflow“selected 一次解析 → 同一结果生成 accepted IDs/repair 排序/filing-start/Phase A”；对照 §6 表 post-repair/new source publication 行“必须新读并重验”。
- **问题类型**：目标漂移 / 契约缺失（不可直接实施）。
- **当前写法**：一次解析覆盖四个消费点；同时又要求 publication 变化后不复用陈旧绑定。
- **反例/失败场景**：company publication 在 filing 循环前发生（`cn_download_workflow.py:282-289`），每个候选 commit 又各是一次 publication；若 filing-start 与 Phase A 消费 window-1 绑定，就是 plan §6 自己禁止的跨发布 stale 绑定复用。plan 为解开该矛盾选择了“要求跨 publication 索引有效性”（B1），而正确解是**缩小共享范围到窗口内**。
- **为什么有问题**：dataflow 矛盾使实现 agent 无论怎么做都违反 plan 自设不变量之一；B1 的“不可能性”实为该矛盾的产物。
- **直接证据**：A1 时序证据；plan §4 与 §6 原文对照。
- **影响**：不可直接实施；阻断被误判为契约能力缺失。
- **建议改法和验证点**：改为 per-window 消费——window-1 inventory 生成 accepted IDs + repair 排序 + preflight 事实；每个 filing stream 的窗口 inventory 生成 FILING_STARTED 的 document_id + resolve 结果（合并 plan §3 指出的 call site 3/4）+ Phase A classification + previous_meta；post-repair 预检保持新读（现状 :396-397）。验证点：任何绑定事实只在其计算窗口内消费，跨窗口零复用。
- **修复风险（低/中/高）**：低。

## 5. B1/B2/B3 直接证据与分类（总控重点）

### 5.1 B1 分类：度量口径问题 + plan 自设矛盾，不是能力缺口

- 今日成本解剖（同一 selected run）：身份侧最多 4S 次 resolve（accepted IDs :258、repair 排序 :272、filing-start :295、stream :164），每次 1 次 list + D 次独立 guard 的 `get_source_meta`——这是 F4 要消掉的**新增**成本；正确性侧 preflight/post-repair `list_source_integrity`（:260, :396）+ 每 filing Phase A classify + Phase B staged classify 各自全树扫描（A3）——这是**既有**成本，goal 非目标不许动。
- 最小设计（§7）把身份读取全部搭在既有扫描事实上：window-1 一次 inventory（替代 list+get 扫描）；每 filing stream 一次 inventory（**替代** Phase A classify + `get_source_meta` + resolve 扫描三窗合一，净读取下降）；身份查询纯内存 O(1)/候选。新增身份读取 = 每窗口 1 次 inventory + O(S) 查询 = O(D+S) 次；锁操作从 O(S·D) 降到 O(S)。既有 Phase A/B 扫描总量不变（仍 O(S·D) 项，但一分不多）。
