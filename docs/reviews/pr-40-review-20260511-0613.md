### 01-未修复-高-repair 路径全量 EventLog 扫描 + 缺少 session_id 索引, 启动延迟 O(m*N)

- **入口/函数**: `DurableConversationMemoryStore._fetch_canonical_events_for_session` / `_collect_missing_session_ids`
- **文件(行号)**: `_conversation_memory_durable.py` (369-402, 349-367); `_durable_event_store.py` (105-112)
- **输入场景**: `startup_reconcile()` -> `repair_missing_session_snapshots` -> 对每个缺失 session 调用 `_fetch_canonical_events_for_session`
- **实际分支**: 第 389-402 行 `while True` 循环, 调用 `event_store.fetch_events_by_position(after=after, limit=256)` 按全局 position 分页拉取**全库所有事件**, 然后在 Python 第 396-399 行按 `session_id` 过滤; `_collect_missing_session_ids` 的 LEFT JOIN 无 `session_id` 索引
- **预期行为**: repair 应高效读取目标 session 的 canonical 事件, SQL 层完成过滤
- **实际行为**: 假设 EventLog 有 N 条事件、目标 session 仅占其中 k 条, 本函数仍需读取并丢弃全部 N 条事件。若有 m 个缺失 session, 总工作量为 O(m * N)。同时 `host_run_events` 表无 `session_id` 索引, JOIN 需全表扫描
- **直接证据**: 第 390-391 行调用 `fetch_events_by_position` (全局 position 顺序, SQL: `WHERE event_position > ? ORDER BY event_position ASC LIMIT ?`, 无 session_id 过滤); `_durable_event_store.py` 第 105-112 行索引仅覆盖 `run_id` 组合, `session_id` 列无独立索引
- **影响**: 生产环境 EventLog 增长到万级以上时, 每次启动 repair 路径会显著拉长 `startup_reconcile` 延迟。多个缺失 session 时延迟线性放大
- **建议改法和验证点**:
  1. 在 `_SCHEMA_STATEMENTS` 新增 `CREATE INDEX IF NOT EXISTS idx_host_run_events_session_kind ON host_run_events (session_id, kind)`
  2. 在 `DurableRunEventStore` 新增 `fetch_canonical_events_by_session(session_id)` 方法, SQL 层直接 `WHERE session_id = ? AND kind = 'canonical' ORDER BY event_position ASC`
  3. 验证: 构造 10 万条事件、3 个缺失 session 的场景, 对比修复前后 `repair_missing_session_snapshots` 耗时; EXPLAIN QUERY PLAN 确认走索引
- **修复风险**: 低。新增索引/方法不影响现有查询路径
- **严重程度**: 高。启动路径性能退化, EventLog 越大越严重

### 03-未修复-中-`update_state_owner_aware` 缺少 target state 校验, 可导致状态机回归

- **入口/函数**: `AttemptLeaseStore.update_state_owner_aware`
- **文件(行号)**: `_run_state_store.py` (629-693)
- **输入场景**: 调用方传入 `state=AttemptState.CREATED` 或 `state=AttemptState.RUNNING` 等非终态

- **影响**: 当前唯一调用方 `close_attempt_with_diagnostic_state` 传入的都是合法终态, 但 store 层缺少自身防线, 未来新增调用方可能误传
- **建议改法和验证点**: 在 `update_state_owner_aware` 开头加 `if state not in _ATTEMPT_FINISHED_STATES: raise ValueError(...)`; 单测验证传入 CREATED/RUNNING 时抛 ValueError
- **修复风险**: 低, 新增校验只拦截非法输入

### 04-未修复-中-compact 失败路径中 attempt 收口语义不一致 (原子 vs 非原子)

- **入口/函数**: `LocalRunHarness._compact_or_fail` 返回 `None` 后的收口路径
- **文件(行号)**: `_run_harness.py` (1096-1113)
- **输入场景**: context compact 失败 (retry limit exceeded / trace missing / decision failed), `_compact_or_fail` 返回 None
- **实际分支**: 原子路径: `_append_terminal_draft_for_active_attempt` 已通过 `_append_terminal_and_close` 关闭 attempt, 设置 `current_active_attempt = None`; 非原子路径: `_compact_or_fail` 内部通过 `_scope_appender().append(draft)` 写入 terminal RunEvent, 但未关闭 attempt, 外层 `_finish_attempt_if_durable` 是唯一关闭入口
- **预期行为**: compact 失败时 attempt 收口路径应一致
- **实际行为**: 两条路径的 attempt 收口职责不同: 原子路径内部完成, 非原子路径依赖外层。`_compact_or_fail` 返回 None 不区分"attempt 已关闭"和"attempt 待关闭", 调用方无法得知

- **建议改法和验证点**: 统一 `_compact_or_fail` 返回 None 时的 attempt 收口责任: 让 `_compact_or_fail` 内部的 `_append_terminal_draft_for_active_attempt` 始终负责 attempt 关闭 (通过返回值告知调用方 attempt 已关闭), 外层 `_run_to_store` 不再重复 `_finish_attempt_if_durable`

- **严重程度**: 中。认知负担 + 诊断噪音, 非功能 bug

## Open Questions

1. **repair 路径的容量评估**: 文档注释提到 "capacity evaluation", 但代码中未见对 EventLog 大小的预检或限流。是否需要在 repair 前检查 EventLog 规模, 超过阈值时跳过 repair 并记录 warning?

2. **recovery scan 调度策略**: `recover_stale_attempts` 仅供 host 内部测试/治理调用, 不自动接入 bootstrap。若生产环境中 harness 异常退出且 diagnostic close 失败, 一个 RUNNING + lease expired 的 attempt 会一直滞留。是否需要 periodic background recovery sweep?

3. **`_task_aware_event_stream` 的 50ms drain 窗口是否足够?** 高负载下 SQLite commit 到 `notify_all` 到 asyncio 调度可能存在 >50ms 延迟。需确认 `_TASK_AWARE_STREAM_DRAIN_SECONDS = 0.05` 在生产负载下的充分性。

4. **`_run_to_store` 中 `engine_events` 迭代器的 `aclose()` 是否总是幂等安全?** 若底层 `WorkerProxy.stream_engine_events` 返回的迭代器 `aclose()` 非幂等, finally 中的二次 close 可能掩盖原始异常。

## Residual Risk

1. **repair 性能 (Finding 01)**: 在 EventLog 增长到十万级以上、且有多个缺失 session 的极端场景下, `startup_reconcile` 延迟可能达到秒级甚至更高。建议在 PR 合并前增加索引 + session-level fetch 方法。

2. **API contract 一致性 (Finding 02 + 05)**: `__init__.py` docstring 与 `__all__` 不一致, 且无正向测试防御 contract 退化。建议在本次 PR 或紧随 PR 中修复。
