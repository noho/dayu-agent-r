## Findings

### 01-未修复-中-outbox reconnect test scenario references non-existent public helper

- **位置**: S2 Exact changes, last bullet: "offline / reconnect 子测试：在 terminal 后用 `read_outbox_terminal_items` 或 `run_entrypoint_startup_reconnect` public helper 从 outbox 补读同一 terminal event"
- **问题类型**: 不可直接实施
- **当前写法**: Plan names `run_entrypoint_startup_reconnect` as a public helper for outbox backfill testing.
- **反例/失败场景**: Implementation agent searches for `run_entrypoint_startup_reconnect`, finds nothing, must improvise. May create a new helper (scope creep), use internal paths (violating constraints), or skip the outbox test entirely.
- **为什么有问题**: The function does not exist. Grep across the entire codebase returns zero matches. The plan presents it as an available public contract, which it is not. Furthermore, `submit_entrypoint_turn_and_wait` submit path sets `allow_outbox_terminal_fallback=False`, meaning the primary submit flow does NOT use outbox backfill — it relies on the live watcher. The outbox fallback in `_wait_for_terminal` only activates when `state.watcher_failure_message is not None` (watcher failure) or `allow_outbox_terminal_fallback=True` (startup reconnect mode).
- **直接证据**: `dayu/service/entrypoint_runtime.py` line 635: `allow_outbox_terminal_fallback=False` in submit path. Lines 1052-1065: `_should_read_outbox_terminal` returns True only when fallback is allowed OR watcher failure is set. `run_entrypoint_startup_reconnect` grep: 0 matches.
- **影响**: Implementation agent either skips outbox test (验收信号 incomplete) or invents a new helper (scope creep beyond plan).
- **建议改法和验证点**: Plan should specify one of: (a) test outbox backfill by directly calling `host.read_outbox_terminal_items` at the Host API level after the run completes, using `OutboxTerminalCursor` and `ReadOutboxTerminalItemsRequest`; (b) test via a different Service path that uses `allow_outbox_terminal_fallback=True` (if such a path exists or can be created within S2 scope); (c) drop the outbox reconnect sub-test from S2 and defer to a separate WU. Option (a) is simplest and stays within public Host contracts.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-中-deterministic poll adapter synchronization is underspecified

- **位置**: S2 Exact changes, third bullet: "poll adapter 通过 production WaitPollAdapterRegistry 注册，返回 WaitPollNotReady 后再返回 WaitPollReady"
- **问题类型**: 测试缺口 / 并发恢复风险
- **当前写法**: Plan says the poll adapter returns `WaitPollNotReady` first, then `WaitPollReady`. No synchronization mechanism is specified.
- **反例/失败场景**: If the poller's `poll_interval_seconds` is very short and the Host processes the `ToolAwaitingOutcome` + creates the wait record + the poller fires all before the test observes `WAITING` via `get_run`, the test may never see `WAITING`. The run could go directly from `IN_PROGRESS` to `SUCCEEDED` in the test's observation window, failing the assertion "断言曾进入 RunStatus.WAITING".
- **为什么有问题**: The plan's Risk R3 acknowledges timing flakiness and suggests "使用短 poll interval、bounded asyncio.wait_for、先断言 WAITING 再等待 terminal，不断言 poll ordering". However, "先断言 WAITING 再等待 terminal" requires the deterministic adapter to HOLD at `NotReady` until the test has observed `WAITING`. Without a synchronization primitive (e.g., `asyncio.Event` that the test sets after observing `WAITING`), the adapter has no way to know when the test is ready for it to return `Ready`.
- **直接证据**: `dayu/host/wait_adapter.py` line 158: `WaitPollNotReady` is a simple dataclass with no state. Line 163: `WaitPollReady` requires `outcome: ResolveWaitOutcome`. The adapter's `poll_wait` method is called by the poller, not by the test — the test cannot directly control when the adapter transitions.
- **影响**: Flaky test — may pass most of the time but fail under fast poller timing or slow CI.
- **建议改法和验证点**: Plan should specify that the deterministic test adapter uses an `asyncio.Event` (or similar) that the test sets after observing `WAITING`. The adapter returns `WaitPollNotReady` until the event is set, then returns `WaitPollReady`. This ensures deterministic ordering: WAITING observed → adapter unlocked → poller resolves → terminal observed. Verification: test passes consistently even with very short poll intervals.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-低-S2 test assembly is independent of S1

- **位置**: S1 Objective / S2 Allowed files
- **问题类型**: 最佳实践偏离（轻微，informational）
- **当前写法**: Plan implies S1 is a prerequisite for S2 ("S1 稳定 assembly contract，S2 写可验证 E2E smoke；两者按依赖顺序和失败风险切分").
- **反例/失败场景**: S2's smoke test constructs its own `OpenHostOptions` directly with deterministic adapter, wait binding registry, wait poll adapter registry, and `WaitPollerRuntimePolicy`. It does NOT use `compose_open_host_options` or `ServiceAssemblyOverrides`. Therefore S2 can run without S1.
- **为什么有问题**: This is not a defect. S1's value is as future production assembly prep — making it possible for real Service deployments to enable the poller via typed override. S2 validates the Host/Service public contract path with a test-controlled assembly. The two slices serve different purposes. But the plan's framing ("两者按依赖顺序") overstates the dependency.
- **直接证据**: S2 Allowed files: "新增 tests/service/test_entrypoint_runtime_awaiting_smoke.py". S2 Exact changes describe constructing `OpenHostOptions` directly, not via `compose_open_host_options`.
- **影响**: None for implementation. Minor clarity issue for plan reader.
- **建议改法和验证点**: Clarify that S1 and S2 can be implemented in parallel (no code dependency), though S1 is logically first because it establishes the production contract that S2's smoke validates the existence of.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/低/严重）**: 低

### 04-未修复-低-forbidden-path grep pattern may miss aliased or indirect references

- **位置**: S2 Exact changes, last bullet: forbidden-path grep
- **问题类型**: 测试缺口
- **当前写法**: `rg -n "open_host_durable_store|read_active_wait_records_for_run|read_wait_record_by_id|ResolveWaitRequest|WaitResolutionSource\\.MANUAL|resolve_wait\\(|ToolRuntime|EngineEvent|dispatch row|scheduler" tests/service/test_entrypoint_runtime_awaiting_smoke.py`
- **反例/失败场景**: If the implementation agent uses an alias like `from dayu.host.api import ResolveWaitRequest as RWR` or stores a reference via `getattr(host, 'resolve_wait')`, the grep would not catch it. Also, `ToolRuntime` and `EngineEvent` as bare substrings could match class names in comments or docstrings rather than actual imports.
- **为什么有问题**: The grep is a useful guardrail but not a formal constraint. An implementation agent determined to use internal paths could evade it.
- **直接证据**: Grep is substring-based, not AST-based. It cannot distinguish imports from comments or string literals.
- **影响**: Low — the grep catches the common case. An adversarial implementation agent is unlikely in this project context.
- **建议改法和验证点**: Acceptable as-is for a practical guardrail. Consider adding `import.*durable|from.*durable` to catch indirect durable store access patterns.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Final Conclusion

**pass-with-risks**

Plan is well-structured, correctly identifies the assembly gap, respects the public-contracts-only constraint, and slices cleanly. Two medium-severity findings need resolution before S2 implementation:

1. The outbox reconnect test references a non-existent helper (`run_entrypoint_startup_reconnect`). Plan should specify the concrete test approach (direct `host.read_outbox_terminal_items` call is the simplest option).
2. The deterministic poll adapter needs a synchronization mechanism to prevent flaky `WAITING` observation. Plan should specify `asyncio.Event` or equivalent.

Neither finding is a structural blocker — both are underspecification issues that can be resolved with minor plan amendments before implementation dispatch.
