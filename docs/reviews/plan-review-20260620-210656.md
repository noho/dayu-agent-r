## Findings

### 01-未修复-中-Slice 4 终端诊断可见性路径未收敛，implementation agent 需自行重新设计

- **位置**: Section 6 "Possible Public Interface Change For Terminal Diagnostic" + Section 7 Decision 7 + Slice 4
- **问题类型**: 不可直接实施
- **当前写法**: Plan 提供两个方案：(1) 在 error_message 文本后缀拼接 `client_correlation_id`；(2) 给 `HostEvent` / `OutboxTerminalItem` / `EntrypointRunTerminalResult` 新增 optional typed fields。Plan 说 "Implementation must choose the smallest existing-boundary solution" 但不推荐具体方案。
- **反例/失败场景**: Implementation agent 选择方案 1（error-message suffix），但 `read_api.py:_failed_host_event` 和 `outbox.py:_error_message` 当前直接从 payload 读 `message` 字段，没有 suffix 拼接逻辑。Agent 需要在两个投影函数中各加一段 suffix 拼接，且要确保 suffix 不被后续 consumer 误解析为 error message 本体。或者 Agent 选方案 2，但需要改 4 个公共 dataclass（HostEvent、OutboxTerminalItem、EntrypointRunTerminalResult、OutboxTerminalItemRow）和 3 个投影函数，这是 plan 未明确列出的 public contract 变更范围。
- **为什么有问题**: Plan 声称 code-generation-ready，但最关键的终端可见性路径把设计决策留给了 implementation agent。两个方案的改动范围、测试策略和 public contract 影响完全不同。
- **直接证据**:
  - `read_api.py:978` — `_optional_payload_text(payload, field_name="message")` 只读 message
  - `outbox.py:395` — `optional_payload_text(event.payload, field_name=_PAYLOAD_FIELD_MESSAGE)` 只读 message
  - `entrypoint_runtime.py:329-345` — `EntrypointRunTerminalResult` 无 correlation fields
  - `api.py:3003-3036` — `HostEvent` 无 correlation fields
  - `api.py:2750-2788` — `OutboxTerminalItem` 无 correlation fields
- **影响**: Implementation agent 可能选择与 plan intent 不一致的方案；或者花大量时间在两个方案间权衡；或者生成的代码在 public contract 边界上不一致。
- **建议改法和验证点**: Plan 应明确推荐一个方案并说明理由。基于当前证据，方案 1（error-message suffix）改动最小且不改 public schema，但 plan 应明确：(a) suffix 在哪个函数拼接；(b) suffix 格式；(c) 测试如何断言 suffix 存在而非解析 error_message 内部结构。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-中-Slice 4 跨层改动范围过宽，超出单一可验证闭环

- **位置**: Slice 4 Files 列表 + Section 5 Affected Files
- **问题类型**: 过度耦合
- **当前写法**: Slice 4 涉及 `dayu/host/read_api.py`、`dayu/host/outbox.py`、`dayu/service/entrypoint_runtime.py`、`dayu/cli/output.py` 四个文件，横跨 Host projection、Service entrypoint、CLI output 三层。
- **反例/失败场景**: 如果 implementation agent 选方案 2（schema extension），需要同时改 Host public dataclass、Service public dataclass、Host projection、Service projection、CLI renderer —— 任何一层遗漏都会导致 pyright 报错或行为不一致。如果选方案 1，仍需在 Host 和 Outbox 两个独立投影路径各加 suffix 逻辑。
- **为什么有问题**: Control doc 的 slice 切分原则要求 "沿稳定模块 ownership、公共契约边界切分"。Slice 4 跨越了 Host / Service / CLI 三个 ownership 边界，且终端诊断可见性的两种方案对这三个边界的侵入方式完全不同。
- **直接证据**: `read_api.py`（Host projection）、`outbox.py`（Host projection）、`entrypoint_runtime.py`（Service）、`cli/output.py`（CLI）—— 四个模块分属不同层。
- **影响**: 实现 agent 在一个 slice 内需要理解三层边界和两种方案，容易遗漏或生成不一致代码。
- **建议改法和验证点**: 如果 plan 收敛为方案 1，可将 suffix 逻辑限定在 `entrypoint_runtime.py` 的 `EntrypointRunTerminalResult` 组装处（从 EventLog payload 读取 correlation fields 并拼入 error_message），下游 CLI renderer 不需改动。如果收敛为方案 2，应拆成两个 sub-slice：先改 Host public dataclass + projection，再改 Service + CLI。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-低-Tool Trace diagnostic_ref=None 风险描述与代码事实不符

- **位置**: Section 7 Decision 6 + Section 11 Risks
- **问题类型**: 契约缺失 / 错误假设
- **当前写法**: "If validation requires a diagnostic ref, use a typed local diagnostic ref such as the source event_id only after confirming existing semantics; do not fake a provider request id."
- **反例/失败场景**: Implementation agent 看到这段话后可能花时间调查 validation 是否拒绝 `None`，甚至提前引入 event_id 作为 diagnostic_ref 的 fallback，增加不必要的复杂度。
- **为什么有问题**: 代码事实证明 `diagnostic_ref=None` 是合法值。`durable/tool_trace.py:988` 使用 `_require_optional_non_empty_text(row.diagnostic_ref, ...)`，允许 None。`find_tool_trace_by_diagnostic_ref` 的 `_require_non_empty_text` 只约束查询参数，不约束存储值。Plan 的风险描述基于未验证的假设。
- **直接证据**: `durable/tool_trace.py:988` — `_require_optional_non_empty_text(row.diagnostic_ref, field_name="diagnostic_ref")` 允许 None。
- **影响**: Implementation agent 可能过度设计 diagnostic_ref fallback 逻辑。
- **建议改法和验证点**: 删除或改写 Decision 6 中关于 validation 可能拒绝 None 的风险描述，明确 `diagnostic_ref=None` 在当前 hot row validation 中是合法值。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-低-Provider header allowlist 缺乏需求证据，属于过度设计

- **位置**: Section 7 Decision 5
- **问题类型**: 过度设计
- **当前写法**: Plan 建议扩展 `_PROVIDER_REQUEST_ID_HEADER_NAMES` 为包含 `x-request-id`、`x-requestid`、`x-correlation-id`、`x-trace-id`、`x-amzn-requestid`、`cf-ray` 的 allowlist。
- **反例/失败场景**: 当前代码只有 `x-request-id`，且 issue #63 的 reopen 证据只涉及 mimo（OpenAI-compatible）。没有证据表明其它 header name 在当前 provider 生态中被使用。Implementation agent 可能花时间实现并测试一个无人使用的 allowlist。
- **为什么有问题**: Plan 自己也承认 "If implementation agent cannot justify a provider-independent allowlist, use an even more conservative bounded response-header diagnostic"。这说明 plan 作者也不确定 allowlist 是否 justified。
- **直接证据**: `runner.py:94` — 当前只有 `("x-request-id",)`。Issue #63 reopen comment 只提到 mimo response 没有 `x-request-id`，没有提到其它 header。
- **影响**: 不必要的代码膨胀和测试维护负担。
- **建议改法和验证点**: 保持当前 `x-request-id` 单一 header，不扩展 allowlist。如果未来有 provider 使用其它 header，由那时的 issue 驱动扩展。Slice 2 的 "bounded header diagnostic" 可以保留为独立后续工作。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 05-未修复-低-Decision 4 日志扩展含 escape hatch，约束不硬

- **位置**: Section 7 Decision 4
- **问题类型**: 不可直接实施
- **当前写法**: "may be extended to include client_correlation_id=%s on the same line if and only if the value is available at that call site" + "If not feasible in this slice, document that terminal / Tool Trace diagnostics satisfy visibility; do not add a new log line."
- **反例/失败场景**: Implementation agent 可能直接跳过日志扩展，因为 plan 给了 "if not feasible" 的 escape hatch。但用户约束明确要求 "logs must be able to show client_correlation_id"。
- **为什么有问题**: 用户约束和 plan 的 escape hatch 之间存在张力。Plan 应明确：如果 Slice 2 不能完成日志扩展，哪个 slice 负责？还是说 terminal / Tool Trace 就足够满足 "logs must be able to show" 的约束？
- **直接证据**: 用户 focus area 明确 "logs must be able to show client_correlation_id, but there must be no new log point, no extra log line, and no log-level change"。
- **影响**: 验收时可能对 "logs must be able to show" 的理解不一致。
- **建议改法和验证点**: Plan 应明确 "logs" 在此上下文中的边界：是否包含 terminal output 和 Tool Trace？如果包含，Slice 3 + Slice 4 已覆盖。如果特指 Python logger 输出，则 Slice 2 的日志扩展是必须的，不应有 escape hatch。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Final Plan Review Conclusion

**conclusion: pass-with-risks**

Plan 的核心设计判断成立：default enablement belongs in Service assembly，typed policy boundary 正确，Tool Trace fallback 保留方向正确，不新增配置项 / 日志点 / 用户概念的约束清晰。Slices 1-3 足够 code-generation-ready。

但 **Slice 4（终端诊断可见性）是 plan 的最大弱点**：两个方案都未收敛，跨层改动范围过宽，implementation agent 需自行做设计决策。这不构成 blocker（两个方案都可行），但会增加实现风险和 review 难度。

建议 controller 裁决后、implementation 前，由 plan author 补充 Slice 4 的推荐方案和具体改动路径。

**material findings count**: 5

**blocking open questions**: 0（OQ1 可在 implementation 前由 controller 裁决收敛，不阻塞 plan 本身）
