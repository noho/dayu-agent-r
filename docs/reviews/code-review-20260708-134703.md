# Code Review — Workspace 路径处理风险专项

## Scope

- **Mode**: current changes (主题深挖，非全量 diff review)
- **Branch**: `phase/host-issues-control`
- **Base**: `main`
- **审查主题**: `dayu-cli prompt` 后创建 `workspace/workspace`，以及总控准备引入 workspace path public contracts
- **审查入口**: CLI → Service → Host 完整路径链
- **Included scope**: `dayu/cli/` (arg_parsing, agent_entrypoint, commands/prompt, commands/interactive, commands/init, session_terminal_cursor, host_context), `dayu/runtime/location.py`, `dayu/service/entrypoint_runtime.py`, `dayu/service/host_assembly.py`, `dayu/host/open_host.py`, `dayu/host/api.py` (OpenHostOptions), `dayu/config/*.json`, `dayu/tools/web/` (storage state), `dayu/fins/` (storage infra, ingestion runtime)
- **Excluded scope**: Engine runners, Fins pipelines (下载/预处理/上传具体业务逻辑), tests, utils/

## Findings

### 1-未修复-严重-init 与 location resolver 的 config overlay 路径不一致

- **入口/函数**: `dayu-cli init` (`dayu/cli/commands/init.py:_copy_current_config_assets`) vs `resolve_runtime_locations` (`dayu/runtime/location.py:51`)
- **文件(行号)**: `dayu/cli/commands/init.py:90` vs `dayu/runtime/location.py:51`
- **输入场景**: 用户使用默认 `--base ./workspace`（CLI 默认值 `DEFAULT_WORKSPACE = "./workspace"`）先执行 `dayu-cli init`，再执行 `dayu-cli prompt "hello"`
- **实际分支**:
  - init: `config_dir = workspace_root / "config"` → 写入 `./workspace/config/`
  - location: `workspace_config = project_root / "workspace" / "config"` → 查找 `./workspace/workspace/config/`
- **预期行为**: init 写入的 workspace config 在 prompt 时能被 `resolve_runtime_locations` 发现并激活为 config overlay
- **实际行为**: init 写入 `./workspace/config/`，但 location resolver 查找 `./workspace/workspace/config/`。由于路径不匹配，`workspace_config.exists()` 返回 `False`，`config_overlay_dir` 被设为 `None`，整个 workspace config overlay 被静默跳过，回落为包内默认配置
- **直接证据**:
  - `dayu/cli/commands/init.py:32`: `_WORKSPACE_CONFIG_DIR_NAME: Final[str] = "config"`，line 90: `config_dir = workspace_root / _WORKSPACE_CONFIG_DIR_NAME`
  - `dayu/runtime/location.py:51`: `workspace_config = project_root / "workspace" / "config"`
  - `dayu/cli/arg_parsing.py:14`: `DEFAULT_WORKSPACE: str = "./workspace"`
  - 两边均接收同一个 `workspace_root`（来自 `--base`），但拼接的尾部子路径不同：init 用 `"config"`，location 用 `"workspace/config"`
- **影响**: 用户执行 `dayu-cli init` 创建并修改了 `workspace/config/` 下的配置文件后，这些修改对 `dayu-cli prompt` 和 `dayu-cli interactive` **完全不可见**。用户所有对 workspace config 的手动定制被静默忽略，极易造成"改了什么配置都不生效"的排障困境
- **建议改法和验证点**:
  1. 统一 init 和 location resolver 的 config overlay 子路径约定。如果约定是 `workspace_root/workspace/config/`，则 init 的 `_WORKSPACE_CONFIG_DIR_NAME` 应改为 `("workspace", "config")`；如果约定是 `workspace_root/config/`，则 `location.py:51` 应去掉 `"workspace"` 分量
  2. 在 `resolve_runtime_locations` 中增加一条 info 级别日志，明确输出 "config_overlay_dir = <path>" 或 "config_overlay_dir = None (not found)"，降低排查难度
  3. 增加冒烟测试：`dayu-cli init --base <tmpdir>` → 修改 `workspace/config/xxx.json` → `dayu-cli prompt --base <tmpdir>` 并验证 assembly diagnostics 中 `config_overlay_dir` 非 None
- **修复风险（中）**: 涉及两处路径约定的对齐，需要确定哪种约定是预期真源；`init --reset` 的白名单路径也需要一并调整
- **严重程度（严重）**: 用户可见的 workspace config 定制完全失效，且无任何错误提示

### 2-未修复-高-playwright_storage_state_dir 未解析 workspace_root

- **入口/函数**: Web tools provider 配置解析与 `_resolve_playwright_storage_state_path`
- **文件(行号)**:
  - `dayu/config/tool_discovery.json:77`: `"playwright_storage_state_dir": "workspace/.dayu/web_tools_storage_states"`
  - `dayu/tools/web/web_playwright_backend.py:760-778`: `_normalize_playwright_storage_state_dir` 只做 `os.path.expanduser()`，不解析 workspace_root
  - `dayu/tools/web/provider.py:103-107`: 配置值直接作为字符串传入 `WebToolsConfig`
- **输入场景**: 用户指定 `--base /custom/path`（非默认 `./workspace`），然后运行 Agent 触发 `fetch_web_page` 工具
- **实际分支**: `playwright_storage_state_dir` 始终使用 config 中的原始相对路径 `"workspace/.dayu/web_tools_storage_states"`，由 `os.path.expanduser()` 处理后（相对路径不受影响），作为最终目录传给 Playwright backend
- **预期行为**: web tools storage state 目录应落在 `--base` 指向的 workspace root 内，即 `<workspace_root>/.dayu/web_tools_storage_states/`
- **实际行为**: storage state 路径为 CWD 相对路径 `workspace/.dayu/web_tools_storage_states`，当 CWD 不等于 workspace_root 或 workspace_root 不叫 `workspace` 时，storage state 不会落在 workspace root 内
- **直接证据**:
  - `dayu/tools/web/web_playwright_backend.py:778`: `return os.path.expanduser(normalized)` — 没有 workspace_root 参数，没有 `_resolve_project_path` 调用
  - 对比 Host durable 路径的处理方式：`dayu/service/host_assembly.py:2044-2062` 中 `_resolve_project_path` 明确将相对配置路径相对于 `workspace_root` 解析
  - `dayu/tools/web/provider.py:103-107`: provider config 解析链路中 `workspace_root` 不可达，`discover_tools` 只接收 `spec.config`（dict），没有 workspace root 参数
- **影响**: 当 `--base` 指向非默认路径时，web tools 的 Playwright storage state 漏到 CWD 下的 `workspace/.dayu/...`，而不是指定的 workspace 内。多 workspace 并行时可能互相覆盖。此外，`init --reset` 的白名单路径（`dayu/cli/commands/init.py:35` `_WEB_TOOLS_STORAGE_STATES_DIR_NAME`）预期清理的是 `workspace_root/.dayu/web_tools_storage_states/`，与实际写入位置不一致
- **建议改法和验证点**:
  1. 将 `workspace_root` 传入 web tools provider 的 effective config 装配流程（类比 Fins provider 的 `_effective_fins_workspace_root_config_value`），在 `host_assembly.py` 的 `assemble_effective_tool_provider_configs` 或 `_effective_tool_provider_config` 中为 web provider 解析 `playwright_storage_state_dir`
  2. `tool_discovery.json` 中 `playwright_storage_state_dir` 默认值应改为不含 `workspace/` 前缀的相对路径（如 `".dayu/web_tools_storage_states"`），然后由 Service 层统一通过 `_resolve_project_path` 解析
  3. 验证命令：设置 `--base /tmp/test_ws`，运行 `fetch_web_page` 后检查 storage state 文件是否落在 `/tmp/test_ws/.dayu/web_tools_storage_states/`
- **修复风险（中）**: 需要在 `ToolsDiscoveryProviderSpec.config` 层面注入 workspace_root，或在 Service assembly 中为 web provider 做 special-case resolution；变更 config schema 默认值需要注意向后兼容
- **严重程度（高）**: 多 workspace 场景下 storage state 路径泄漏到错误位置，且 `init --reset` 清理不到

### 3-未修复-中-`session_terminal_cursor` 变更方向正确但未解决同类问题

- **入口/函数**: `cli_terminal_cursor_file_path` / `advance_cli_terminal_cursor`
- **文件(行号)**: `dayu/cli/session_terminal_cursor.py:24` (当前 diff)
- **输入场景**: 用户使用默认 `--base ./workspace` 运行 interactive 会话
- **实际分支**: 当前 diff 将 `_CURSOR_DIR_PARTS` 从 `("workspace", ".dayu", "cli")` 改为 `(".dayu", "cli")`
- **预期行为**: cursor 文件落在 `workspace_root/.dayu/cli/terminal_cursors.json`
- **实际行为**: 修复后正确落在 `workspace_root/.dayu/cli/`，不再有 `workspace/workspace/.dayu/cli/` 的双重路径
- **直接证据**: diff 只改了一行常量，去掉了硬编码的 `"workspace"` 分量
- **影响**: 本修复是正确的，但它只解决了 cursor store 一处。同类的 `"workspace"` 硬编码问题在 `location.py:51` (`project_root / "workspace" / "config"`) 仍然存在
- **建议改法和验证点**:
  1. 搜索所有在 `workspace_root` 基础上再次拼接 `"workspace"` 字面量的位置，逐一评估是否应去掉
  2. 本修复本身建议合入，但需要与 Finding 1 的 config overlay 路径约定一并决策
- **修复风险（低）**: 当前 diff 本身无风险；但 cursor 文件位置变更意味着旧路径下的 cursor 数据不会自动迁移，对已有 workspace 用户是一次性状态丢失（interactive startup 会按 cursor=0 重新 backfill，影响有限）
- **严重程度（中）**: 修复正确但不完整；迁移路径缺失对已有用户有轻微影响

### 4-未修复-中-`DEFAULT_WORKSPACE = "./workspace"` 导致路径语义混淆

- **入口/函数**: `parse_cli_args` / `_new_default_namespace`
- **文件(行号)**: `dayu/cli/arg_parsing.py:14` (常量), `dayu/cli/arg_parsing.py:244` (默认值赋值)
- **输入场景**: 任何未显式传 `--base` 的 CLI 调用
- **实际分支**: `workspace_root` 默认值为 `"./workspace"`，经 `resolve_workspace_root()` 解析为绝对路径如 `/cwd/workspace`
- **预期行为**: 无特定预期；这是约定设计
- **实际行为**: 因为默认值目录名恰好叫 `workspace`，导致所有在 `workspace_root` 基础上再拼接 `"workspace"` 子目录的代码产生 `.../workspace/workspace/...` 的双重路径
- **直接证据**:
  - `DEFAULT_WORKSPACE = "./workspace"` → `resolve_workspace_root` → `Path("./workspace").expanduser().resolve()` → 绝对路径以 `/workspace` 结尾
  - 任何 `workspace_root / "workspace" / ...` 的拼接都会产生 `.../workspace/workspace/...`
- **影响**: 这是 Finding 1 和已修复的 session_terminal_cursor 问题的根因放大因素。默认值 `"./workspace"` 本身没有错，但它让所有在根下再建 `workspace/` 子目录的代码产生混淆
- **建议改法和验证点**:
  1. **推荐方案**: 保持 `DEFAULT_WORKSPACE = "./workspace"` 不变，但统一所有子系统在 workspace_root 下使用 `.dayu/` 前缀（而非 `workspace/` 前缀）存放内部数据。config overlay 路径也应统一到 `.dayu/config/` 或 `config/`（直接挂在 workspace_root 下）
  2. **备选方案**: 改变默认值为 `"."`（当前目录即项目根），然后所有内部路径统一使用 `workspace/.dayu/...` 前缀。这会改变现有用户的使用习惯
  3. 无论选哪种，都需要在 README 中明确 workspace 目录结构约定
- **修复风险（高）**: 涉及目录结构约定的全项目统一，需要跨模块协调
- **严重程度（中）**: 本身不是 bug，但放大了其他路径 bug 的影响面

### 5-未修复-低-`init --reset` 白名单与部分实际路径不一致

- **入口/函数**: `_reset_whitelist_paths`
- **文件(行号)**: `dayu/cli/commands/init.py:291-305`
- **输入场景**: 用户执行 `dayu-cli init --reset --base ./workspace`
- **实际分支**: reset 白名单路径包括 `dayu_root / _WEB_TOOLS_STORAGE_STATES_DIR_NAME` → `workspace_root/.dayu/web_tools_storage_states/`
- **预期行为**: reset 应能清理所有可重建的 workspace 内部数据
- **实际行为**: 白名单中的 `web_tools_storage_states` 路径与实际 web tools 写入的 `workspace/.dayu/web_tools_storage_states`（来自 config 默认值）不完全一致。由于 config 值带了 `workspace/` 前缀，实际写入路径取决于 CWD，init reset 可能清理不到
- **直接证据**:
  - `init.py:304`: `dayu_root / _WEB_TOOLS_STORAGE_STATES_DIR_NAME` → `<workspace_root>/.dayu/web_tools_storage_states`
  - `tool_discovery.json:77`: `"workspace/.dayu/web_tools_storage_states"` → 相对于 CWD 解析
- **影响**: 与 Finding 2 连锁。如果 web tools storage state 路径被修正为相对于 workspace_root 解析，则 init reset 白名单也需要同步更新
- **建议改法和验证点**: 在解决 Finding 2 后，确认 init reset 白名单与实际 web tools storage state 目录一致
- **修复风险（低）**: 与 Finding 2 联动修复即可
- **严重程度（低）**: 依赖 Finding 2；修复 Finding 2 后自然解决

## Open Questions

1. **workspace config overlay 的预期路径约定**: `workspace_root/config/` 还是 `workspace_root/workspace/config/`？当前 init 和 location resolver 各写一套，需要确定哪个是预期的真源约定。建议以 `workspace_root/config/` 为真源（与 init 对齐），因为 `workspace_root` 本身已经是 workspace 目录，不需要再嵌套一层 `workspace/`。

2. **`DEFAULT_WORKSPACE` 的未来方向**: 是否考虑将默认值从 `"./workspace"` 改为 `"."`？这会影响所有现有用户的工作流和文档。如果改，需要明确的迁移指南。

3. **Fins workspace_root 注入链路**: `host_assembly.py:_effective_fins_workspace_root_config_value` 已经在 provider config 装配阶段注入了 `workspace_root`，但仅对 Fins 相关 provider 生效。是否应该抽象出一个通用的 `workspace_root` 注入机制，让 web tools provider 也能复用？

## Residual Risk

1. **无自动验证**: 当前没有自动化测试验证"指定 `--base /tmp/custom` 后，所有持久化状态都落在该目录下"。建议增加一个集成测试：
   ```bash
   # 建议的验证命令
   tmpdir=$(mktemp -d)
   dayu-cli init --base "$tmpdir"
   dayu-cli prompt --base "$tmpdir" "hello" --ticker AAPL --no-detail --no-thinking
   # 然后断言以下路径均以 $tmpdir 为前缀：
   # - $tmpdir/.dayu/host/dayu_host.sqlite3
   # - $tmpdir/.dayu/artifacts/
   # - $tmpdir/.dayu/runtime/runtime_lanes.sqlite3
   # - $tmpdir/.dayu/cli/terminal_cursors.json
   # - $tmpdir/.dayu/web_tools_storage_states/  (修复后)
   # - $tmpdir/config/ 或 $tmpdir/workspace/config/ (约定统一后)
   find "$tmpdir" -type f -o -type d | sort
   # 确认没有任何路径在 $tmpdir 之外
   ```

2. **config overlay 静默失效**: 当前 `resolve_runtime_locations` 发现 workspace config 目录不存在时只是返回 `config_overlay_dir=None`，没有任何日志。这意味着 config overlay 的配置错误会被静默忽略。建议至少加一条 info 级别日志。

3. **cursor 文件迁移**: `session_terminal_cursor.py` 的目录变更（从 `workspace/.dayu/cli/` 到 `.dayu/cli/`）对已有 workspace 是破坏性的——旧的 cursor 数据不会被自动迁移。对于使用 `--label` 恢复已有 session 的 interactive 用户，startup backfill 会从 cursor=0 开始（等价于新 session），可能输出已看过的 terminal 结果。影响有限（去重逻辑会过滤重复 terminal event id），但用户体验有轻微退化。

4. **Fins storage 路径（无问题）**: `dayu/fins/storage/_fs_storage_infra.py` 中的 Fins 仓储路径直接从 `self.workspace_root` 派生（`.dayu/repo_batches`、`portfolio/` 等），Fins 的 `workspace_root` 来自 provider config 注入的绝对路径（`host_assembly.py` 中 `_effective_fins_workspace_root_config_value`），不经过 `location.py` 的 `"workspace/config"` 二次拼接。**Fins 路径链无问题。**

5. **Host durable 路径（无问题）**: `dayu/host/` 下的 durable store（`db_path`、`artifact_root`、`lane_db_path`、`compact_artifact_root`）全部通过 `_resolve_project_path(workspace_root, configured_path)` 解析，以 workspace_root 为基准解析相对路径，路径链正确。Tool trace projection（`_default_tool_trace_cold_jsonl_path`）从 `artifact_root` 派生，继承正确的 workspace 绑定。**Host durable 路径链无问题。**
