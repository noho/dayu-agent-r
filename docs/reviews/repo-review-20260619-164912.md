## Findings

### 1-未修复-[中]-proactive compact recovery tier 失败不会写入 rejected attempt 事件且 failed attempt_count 被低估

- **入口/函数**: `HostDispatchScheduler._execute_proactive_compaction(...)`
- **文件(行号)**: `dayu/host/dispatch.py:1331`, `dayu/host/dispatch.py:1344`, `dayu/host/dispatch.py:1401`, `dayu/host/dispatch.py:1433`
- **输入场景**: 一个 queued/accepted Run 触发 proactive compaction；normal `run_compaction_operation(...)` 未 accepted；随后 tier 1-3 recovery compaction attempts 也未 accepted，最终 fallback dispatch 生效。
- **实际分支**: normal result 不 accepted 后进入 `for recovery in self._proactive_compaction_recovery_attempts(pending)`，每个 recovery 调 `run_compaction_operation(... max_attempts=1 ...)`；但事务写入阶段只遍历 `result.rejected_attempts`，并在 failed payload 中使用 `len(result.rejected_attempts)`。
- **预期行为**: 同一个 `operation_id` 下所有真实 proposal attempt，包括 normal attempt 和 recovery tier attempt，都应写入 `CONTEXT_COMPACTION_ATTEMPT_REJECTED`，并让 `CONTEXT_COMPACTION_FAILED.attempt_count` 与实际已拒绝 proposal attempt 数一致。compact smoke 依赖 rejected histogram、manifest presence 和 failed attempt_count 来定位 compactor/material 失败。
- **实际行为**: recovery tier 的 `tier_result.rejected_attempts` 只用于更新 `completed_attempt_count`，没有合并到最终要落 EventLog 的 rejected list。all-tier-fail 时 `CONTEXT_COMPACTION_FAILED.attempt_count` 仍来自 initial `result`，不是 normal + tier 1-3 的总数；EventLog 也缺少 recovery tier 对应的 rejected diagnostic artifact / proposal manifest refs。
- **直接证据**:
  - initial operation result 赋给 `result`：`dayu/host/dispatch.py:1331-1338`。
  - recovery failures 只把 `_completed_compaction_proposal_attempt_count(tier_result)` 加到 `completed_attempt_count`：`dayu/host/dispatch.py:1344-1376`，没有把 `tier_result.rejected_attempts` 加入任何后续写入集合。
  - commit 阶段只写 `for rejected in result.rejected_attempts`：`dayu/host/dispatch.py:1401-1407`。
  - failure payload 的 `attempt_count` 和 `retry_repair_budget_exhausted` 只看 initial `result.rejected_attempts`：`dayu/host/dispatch.py:1433-1436`。
  - `_append_compaction_failed_event(...)` 文档声明 `attempt_count` 是“operation 内已拒绝 proposal attempt 数”：`dayu/host/dispatch.py:2240-2242`。
  - 现有 all-tier-fail 测试只断言 `compactor.calls == 4`、failed event 数和 fallback dispatch，没有断言 rejected event 数或 failed payload attempt_count：`tests/host/test_dispatch_scheduler.py:4986-5037`。
- **影响**: compact recovery 失败时诊断事实与真实 proposal call 不一致。`utils/smoke_host_public_conversation_memory_scenarios.py` 会按 operation 聚合 rejected attempts、diagnostic histogram 和 manifest presence；缺失 recovery tier rejected facts 会把 material/proposal failure 定位误导为只发生在 initial operation，降低 compact smoke 对 regression 的诊断价值。主 Run 仍可通过 fallback dispatch 继续执行，因此这是可观测性/稳定性问题，不是直接回答错误。
- **建议改法和验证点**:
  - 在 `_execute_proactive_compaction(...)` 中维护 operation-level rejected attempts collection，包含 initial result 与每个 failed recovery `tier_result.rejected_attempts`。
  - `CONTEXT_COMPACTION_ATTEMPT_REJECTED` 写入、failed `attempt_count`、`retry_repair_budget_exhausted` 和 `budget_after_attempted_compact` 应基于最终 operation-level result，而不是只看 initial `result`。
  - 补充 `test_proactive_compaction_recovery_all_tiers_fail_uses_dispatch_fallback` 断言：rejected event 数覆盖 normal + tier 1-3；failed payload `attempt_count` 与 rejected event 数一致；每个 rejected payload 带 proposal manifest ref/digest；smoke compact audit 能看到 recovery tier histogram。
- **修复风险（低/中/高）**: 中。修复只应改变 diagnostic/EventLog payload 和测试断言，但这些 payload 已被 smoke audit 消费，需要同步验证 public smoke diagnostic parser。
- **严重程度（低/中/高/严重）**: 中
