### 001-未修复-中-filelock release() 部分失败破坏幂等不变量

- **入口/函数**: `RuntimeFileLockToken.release()`
- **文件(行号)**: `dayu/runtime/filelock.py:99-104`
- **输入场景**: 第三方 `_third_party_lock.release()` 成功但后续 `_ensure_lock_file_marker_exists()`（`touch()`）失败时触发。
- **实际分支**: `try` 块内两个操作顺序执行；任一失败走 `except` 抛 `RuntimeFileLockError`。
- **预期行为**: 锁已释放成功时，`self.released` 应被设为 `True`，后续 `release()` 调用应幂等跳过。调用方收到异常时应能区分"释放失败"和"释放成功但 marker 写入失败"。
- **实际行为**: 若 `_third_party_lock.release()` 成功但 `_ensure_lock_file_marker_exists()` 失败，`self.released` 保持 `False`（line 104 未执行）。调用方收到 `RuntimeFileLockError` 但锁已在 OS 层面释放。后续 `release()` 重试会尝试释放已释放的锁。
- **直接证据**: `filelock.py:99-104`：`try` 块内 `self._third_party_lock.release()`（line 100）与 `_ensure_lock_file_marker_exists()`（line 101）在同一 try/except 中；`self.released = True`（line 104）在 try 块之后。
- **影响**: 错误状态。调用方认为释放失败但锁实际已释放；重试 `release()` 可能产生第三方库的未定义行为。
- **建议改法和验证点**: 将 `self.released = True` 移到 `_third_party_lock.release()` 之后、`_ensure_lock_file_marker_exists()` 之前；或将 marker touch 放入独立 try/except，失败时只记录日志不影响 released 状态。验证：构造 marker touch 失败场景，确认 `released=True` 且不抛异常。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
