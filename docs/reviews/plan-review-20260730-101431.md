# CLI CI 第一轮 Oracle Readiness Handbook Plan Review

## Review Metadata

- Gate：`plan review`
- Reviewed target：`docs/cli-ci-first-round-oracle-readiness-plan.md`
- Scope：第一轮 calibration 完成条件、mandatory coverage、Codex UI authority、SQLite evidence、observed report 与
  scenario/oracle registry readiness
- Review posture：adversarial

## Assumptions Tested

1. “所有候选 accepted/rejected”足以证明 oracle registry ready。
2. 当前 registry 叙述足以机械验证 coverage 和 oracle completeness。
3. Parser inventory 能完整拥有交互式选项 inventory。
4. 两个只修改同一 handbook 的 slice 能形成有意义的独立一致 checkpoint。
5. Mandatory SQLite observation 不会把 private schema 升级为产品 contract。
6. 产品 failure 与 calibration readiness 可以保持正交。

## Findings

### PR-01-未修复-高-Readiness 允许 mandatory 场景没有 accepted correctness predicate

- **位置**：`第一轮完成条件` 第 6-8 项
- **问题类型**：契约缺失 / 状态机漏洞
- **当前写法**：要求每个用户相关 predicate 都为 `accepted/rejected`，然后两个 registry 变为 `ready`。
- **反例/失败场景**：某 mandatory 场景只产生一个描述当前行为的 candidate，用户明确 `rejected`，但没有给出或接受
  替代 expected predicate。计划当前文字仍允许因为“没有 unadjudicated”而把 registry 标为 `ready`，但后续 CI 没有
  可用于判定正确性的 oracle。
- **为什么有问题**：用户要求第一轮结束即完成“正确性定义”。“拒绝当前行为”只说明它不正确，不等于已经定义正确
  行为。
- **直接证据**：计划写明“每个用户相关 correctness predicate 都为 accepted/rejected，不能残留
  `unadjudicated`”；当前 `docs/cli_ci_oracles.json` 为空，无法由其它记录补足。
- **影响**：registry 可以形式上 ready、语义上却无法进行后续自动判定。
- **建议改法和验证点**：
  - 每个 mandatory scenario 的每个 correctness surface 必须映射到至少一个适用的 accepted oracle，或明确的
    objective/hard contract；
  - rejected candidate 若留下 correctness gap，必须由 replacement predicate 或明确的 out-of-scope 裁决关闭；
  - readiness 校验必须拒绝 dangling scenario、dangling oracle ref 和 uncovered correctness surface。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：高

### PR-02-未修复-高-Registry 缺少可机械验证的 coverage/readiness proof

- **位置**：`Mandatory 场景矩阵`、`第一轮完成条件`、不修改 `docs/cli_ci_*.json` 的范围决定
- **问题类型**：不可直接实施 / 测试缺口 / 最佳实践偏离
- **当前写法**：要求从多个维度派生场景并在最后把 `registry_status` 设为 `ready`，但没有规定 registry 如何声明并
  校验 inventory identity、coverage obligations、scenario coverage claims 和 readiness proof。
- **反例/失败场景**：维护者添加了新的交互选项或前置状态，只手工保留 `registry_status=ready`。现有 parser 对比只能
  发现 command/parameter drift，发现不了 prompt 选项、workspace state、错误输入类别或跨命令消费缺口。
- **为什么有问题**：一个布尔 status 不能拥有其真实性；readiness 必须能从版本化 obligations 与 accepted coverage
  claims 派生，而不是人工声明。
- **直接证据**：
  - 当前 scenario JSON 只有 `schema_version`、`registry_status`、空 `scenarios`；
  - 当前 handbook 第 414-418 行只要求 parser command/parameter IDs 和 scenario fields；
  - 计划新增的 state/interaction/input/cross-command 维度没有 stable identity 或 closure record。
- **影响**：首轮可能漏跑仍被标记 ready；后续 registry drift 无法自动发现。
- **建议改法和验证点**：
  - 计划必须要求 handbook 定义 scenario record 的 stable coverage claims：command/parameter IDs、
    precondition-state IDs、interaction-option IDs、input-class IDs、combination-policy、高风险组合 IDs、
    cross-command assertions 和 evidence requirements；
  - registry-level readiness proof 必须记录 inventory/version/digest、mandatory obligation count、covered count、
    gap count、用户裁决 identity 和相关 frozen report digests；
  - `registry_status=ready` 必须是上述校验结果的投影，禁止手工翻转绕过。
- **修复风险（低/中/高）**：中
- **严重程度（低/中/高/严重）**：高

### PR-03-未修复-中-交互式选项 inventory 没有闭环 owner

- **位置**：`语义 Owner`、`Mandatory 场景矩阵`
- **问题类型**：架构边界 / 契约缺失
- **当前写法**：把命令、参数和交互入口 inventory 共同归给 parser 与真实 CLI help/interaction surface。
- **反例/失败场景**：某交互选项只在选择前一项或进入特定 workspace 状态后动态出现，parser 和顶层 help 都看不到。
  第一次运行发现该选项，但计划没有规定它会使现有矩阵失效并触发新场景，因而仍可能错误结束 calibration。
- **为什么有问题**：parser 是 command/parameter owner，不是动态 prompt branch owner。把两者混成一个 inventory
  会掩盖 discovery 与 closure 的状态迁移。
- **直接证据**：用户明确要求 `dayu-cli init` 在空/有 workspace 下逐个输入选项和错误选项；这些分支不一定能从
  `build_parser()` 推导。
- **影响**：动态交互分支漏测，coverage completeness 无法证明。
- **建议改法和验证点**：
  - 区分 parser inventory 与 interactive branch inventory；
  - interactive inventory 来自命令拥有的交互声明、当前 help/提示和真实运行发现；
  - 任一新发现 branch 必须生成 stable branch ID、扩展 mandatory obligations，并使当前 readiness 回到
    calibration，直到补跑和裁决完成。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### PR-04-未修复-中-两个同文件 slice 会制造不一致的中间 contract

- **位置**：`Implementation Slices`
- **问题类型**：切片过粗 / 过度设计 / 过度耦合
- **当前写法**：S1 修改 calibration/coverage/readiness，S2 再修改 Codex/evidence/SQLite；两者都修改
  `docs/cli_ci.md` 且共同决定 readiness。
- **反例/失败场景**：S1 commit 后 registry readiness 已收紧，但 evidence owner 仍保留旧的 SQLite gap-only 与
  Codex optional 规则；该中间文档内部自相矛盾，无法作为 accepted contract。
- **为什么有问题**：这是单文件、单语义闭环的 handbook 修改，没有独立发布两个 slice 的收益。
- **直接证据**：计划 S1/S2 的成功信号互相依赖；当前 handbook 的第 4、5、6、7、11、13 节存在交叉引用。
- **影响**：增加 review/commit 成本，并留下可被误用的中间 contract。
- **建议改法和验证点**：合并为一个 documentation slice，一次完成全文一致性修改和 review。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

## Architecture Boundary Review

SQLite 仍被限定为 CI-owned、read-only、bounded internal observation，并明确不能替代 Host/Fins/EventLog owner；方向
成立。修复 PR-02 时不能把 private table/column identity 写成跨版本 mandatory oracle，只能记录场景执行时的实际
schema/rows 与相应限制。

## Best-practice / Optimal-solution Review

以真实 inventory + versioned scenario registry + accepted oracle registry 为真源，比手工维护命令清单更可靠。最优路径
不是增加新的 runtime state machine，而是让 readiness 从现有两个 registry 的稳定 coverage/adjudication metadata
可验证地派生。

## Overengineering / Overcoupling Review

计划没有引入生产 helper、migration 或额外 layer。PR-04 所指出的双 slice 是主要流程性过度设计，合并即可。

## Open Questions

- 无 blocking open question。

## Residual Risks

- 实际 calibration 时真实 provider、外部写入授权、时间和成本可能造成 mandatory gap；应由 campaign run manifest
  记录，不能在 handbook 修改中预先豁免。
- 动态模型输出不适合按完整文本建立 oracle；现有计划已要求只冻结语义不变量，风险可由 implementation review 继续检查。

## Conclusion

`fail`

计划方向符合用户目标，但 PR-01 至 PR-03 会允许不完整 correctness/interaction coverage 被错误标记为 ready，必须在
implementation 前修复；PR-04 应通过合并 slice 消除不一致中间 contract。
