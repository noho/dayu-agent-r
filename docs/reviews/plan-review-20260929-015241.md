## Findings

### F1（必须修订）：空值政策表述与实现步骤①存在语义张力，可能误导实现

- **证据**：plan §实现步骤① 要求 material 分支直接调用 `_validate_optional_upload_iso_date`（`dayu/fins/ingestion_runtime.py:1372-1394`），该 helper 仅对 `None` 跳过；`parse_iso_calendar_date` 对 `""` 与纯空白严格拒绝（`tests/fins/test_fiscal_normalization_contracts.py:322-323` 明确列入 reject 用例）。因此 raw request 的 `filing_date=""` / `"   "` 在 admission 一律按非法日期拒绝。而 plan §投影段称两处投影修改"不创建新空值承诺"、§残余 R2 称 raw request/tool 空值"保持各入口现有策略"。现状是 raw `""` 会穿透 admission 并原样写入 source meta / manifest（`dayu/fins/pipelines/sec_upload_workflow.py:202-203`、`230-231` 直拷贝；CN 同构 `cn_pipeline.py:833-834`），即 raw 空串政策**必然随本修复改变**（从穿透持久化改为 typed 拒绝）。
- **判定**：拒绝 raw 空串是正确方向——空串不是合法日期，原样持久化属 oracle Accepted #2 明确不接受的"非法日期字符串原样持久化"；且与 filing raw admission 完全一致（`dayu/fins/README.md` L698："不把空串或纯空白折叠为缺失"）。CLI `--filing-date ""` → `None` 的 accepted 例外由 CLI 输入投影在请求构造前完成折叠保留（UM-S09），不经 admission，不受影响。
- **风险**：实现者若按 R2 字面"保持 raw 现有策略"去在 admission 做空串→None 折叠，将与 parser 契约、"日期字段本身不重写"、filing/material 同源三者同时冲突，并把 UM-S09 的 CLI 例外偷渡成 request 级新承诺。
- **修复建议**：plan 增加一句显式声明："admission 对非 `None` 的 `""`/纯空白一律按非法日期拒绝（与 filing raw admission 一致）；CLI 显式空值折叠是唯一保留的入口级例外，不在 admission 或 raw request 层折叠"；R2 的"保持各入口现有策略"限定为：CLI 空值折叠与 tool 拒绝结果不变。

### F2（应修）：tool schema 更新目标未细化到 LLM-facing 自足要求

- **证据**：现 schema 仅对 filing 陈述日期格式（`dayu/fins/tools/upload_tools.py:283,287`："上传 filing 时若填写……文本不会自动去除空白，空串、纯空白或首尾空白均非法"）。plan 只写"用业务语言同时说明 filing/material 的可选真实日期与不可填首尾空白"。按 CLAUDE.md LLM-facing 约束（参数说明需自足：字段名、含义、类型、必填性、允许值、最小示例）与本 schema 自身惯例（`form_type` 附"例如 8-K 或 MATERIAL_OTHER"），日期描述尚缺：① 最小合法示例（如 2024-02-29）；② 省略/`null` 表示不提供该日期（tool `null` → `None`，`_optional_raw_nullable_text`，`upload_tools.py:396-418`）；③ 空串/纯空白会被拒绝、不能当"清空日期"用。另注意切换后 tool 侧空串的拒绝原因从参数读取边界消息变为日期语义消息，schema 不应暗示两者是同一类错误。
- **修复建议**：plan §实现步骤③ 明确 schema 文案需含最小示例、省略/null 语义与空串拒绝说明，且 filing/material 两分支同步；对应测试 `tests/fins/test_fins_ingestion_tools.py:1724` 的精确文案断言随文案迁移更新（已在允许测试文件内）。

### F3（低）：README 修复理由措辞不准，存在文档化虚构变化的风险

- **证据**：plan §README 段称"material CLI 用户可见日期拒绝与**空 filing_date 行为变化**，需在上传章节补一段"。实际上空 `--filing-date ""` 行为**不变**（仍 `None` → 成功 → meta/manifest `null`，plan 成功信号自述一致）；变化的只有非空带空白/非法日期从 trim-接受/无校验-接受收紧为拒绝。
- **修复建议**：措辞改为"material 日期拒绝收紧（含带空白原文）+ 既有显式空 `--filing-date ""` → `null` 行为的用户说明"，避免 README 作者文档化不存在的行为变化。

### F4（低）：覆盖率兜底措辞弱于 AGENTS.md 硬目标

- **证据**：plan §验证 #6 对基线不足的处置是"记录单文件数字并按受影响范围补有效测试"；AGENTS.md 要求"单文件测试覆盖率目标为 >= 80%"。`dayu/fins/ingestion_runtime.py`、`dayu/cli/commands/fins.py` 体量大，三个测试文件能否拉平到 80% 依赖既有基线。
- **修复建议**：明确——修改后各生产文件仍须达标；若受影响范围补测后仍不足 80%，必须在实施报告登记为残余并给出数字与原因，不得静默通过，也不得为数字写镜像测试（后半句 plan 已正确保留）。

### F5（低，可选）：monkeypatch 调用观测属实现细节耦合

- **证据**：plan §验证 #1 "用可观测 monkeypatch 断言合法闰日调用 `parse_iso_calendar_date` 两字段，`None` 可选值跳过 parser"。断言"谁被调用/调用几次"会固化实现细节；owner 级行为断言（接受/拒绝/字段明确 message）才是契约本体。
- **修复建议**：以行为断言为主；调用观测仅作同源性辅助护栏（防复制第二套日期逻辑），并允许实现等价调整。

## 重点反证记录（任务指定焦点逐项）

2. **material 与 filing typed code 共享边界**：`INVALID_FILING_DATE`/`INVALID_REPORT_DATE`（`ingestion_runtime.py:693-694`）与 `_USAGE_MESSAGES` 文案（`:1045-1046`）按字段命名、不含 CLI flag（测试 `test_fins_ingestion_tools.py:1735-1740` 断言 message 无 "--"），filing/material/CLI/tool 四处共享同一 code/message/`_validate_optional_upload_iso_date` helper（`:1372-1394`）同源成立；plan"不加新 code"正确。唯一注意：`_normalize_upload_request` 的 Raises docstring（`:7704`）实施时需补日期失败说明（plan"补齐 docstring"条款已覆盖）。
3. **CLI/tool 原文日期投影与空值例外是否扩大 accepted contract**：结论——**不扩大，反而收缩并对齐既有承诺**。filing CLI 早已 raw 透传（`dayu/cli/commands/fins.py:695-696`），material CLI trim（`:736-737`）是唯一不一致源；tool filing 已 raw（`upload_tools.py:345-346`），material trim（`:362-363`），而 tool schema 早已宣称"首尾空白均非法"——现 material trim 行为违反已发布 schema 承诺。plan 的投影修改是把 material 对齐 filing/raw 承诺，非新增拒绝面。空值例外：CLI `""`/纯空白 → `None` 折叠保留（UM-S09 accepted，oracle Accepted #1 仅覆盖 CLI 显式空串）；tool 空串/纯空白改后仍拒绝（今日 `_optional_nullable_text` 对空串抛 ValueError → `invalid_argument`，改后 admission 拒绝 → `invalid_argument`，结果类别不变）；raw `""` 由穿透改为拒绝见 F1。oracle 未裁决的空 `report_date` 未被任何测试固化为成功承诺，处理正确。
