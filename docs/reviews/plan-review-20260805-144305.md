### F01-未修复-严重-Registry `drop-policy-limit@1` accepted status 与 v3 contract 永久矛盾

- **位置**: S5 registry delta; `docs/cli_ci_scenarios.json` `interactive.interactive.g06.drop-policy-limit` v1
- **问题类型**: 契约缺失 / 状态机漏洞
- **当前写法**: Plan 声称 "旧 frozen scenario 不原地改写"，append `cap-constrained-memory-replacement@1` with `supersedes="interactive.interactive.g06.drop-policy-limit@1"`。
- **反例/失败场景**: 任何 registry validation 检查 "所有 accepted scenario 的 required_evidence 是否在最新 evidence 中 satisfied" 时，`drop-policy-limit@1` 仍要求 `policy_limit` branch（其 `oracle_predicate_refs` 包含 `interactive.26-context-compaction-single-flight-and-success`，`correctness_surfaces` 包含 `interactive.30-formal-compactor-tool-trace`，其 `required_evidence` 包含 implicit `policy_limit` accepted branch）。v3 删除 `CompactDropReasonV2.policy_limit`，永远不可能产生该 branch。旧 entry 的 `status=accepted` 成为虚假声明。
- **为什么有问题**: Registry 是 Oracle controller 的 truth source。一个 `status=accepted` 但实际 contract 已被删除的 scenario，会导致任何自动化 registry validation 报告 "accepted but unsatisfiable"。如果 validation 只检查 latest version，那旧 entry 的 `status=accepted` 仍然通过，但 `supersedes` 语义不被 validation 理解。如果 validation 检查 all versions，旧 entry 永远 fail。
- **直接证据**: `docs/cli_ci_scenarios.json` 中 `drop-policy-limit@1` 的 `status=accepted`；plan S5 "旧 core-execution@1 与三个 frozen scenario 的 predicates、required evidence、observed evidence、status、user adjudication 均不原地改写"；plan F12 删除 `CompactDropReasonV2` 及其 `policy_limit`。
- **影响**: Registry 一致性永久受损；自动化 gate 可能产生 false negative 或 false positive；后续 contributor 无法判断旧 scenario 是否仍然 valid。
- **建议改法和验证点**: 明确旧 `drop-policy-limit@1` 的 `status` 应改为 `superseded`（不是原地改写 contract，而是更新 status 以反映事实），或在 plan 中明确说明 registry validation 只检查 latest version 并在 validation 代码中添加 `superseded_by` 跳过逻辑。验证点：registry loader 的 scenario 检查逻辑是否跳过 `superseded_by` 非空的 entry。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 严重

### F02-未修复-高-`AsyncRunner.call` 增加 required keyword-only `structured_output` 是 Protocol breaking change

- **位置**: S2 Engine generic structured output; `dayu/engine/contracts/runner.py` AsyncRunner Protocol
- **问题类型**: 架构边界 / 不可直接实施
- **当前写法**: "`AsyncRunner.call` 增加显式 keyword-only `structured_output`"
- **反例/失败场景**: `AsyncRunner` 是 `@runtime_checkable Protocol`。增加一个新的 required keyword-only parameter `structured_output: StructuredOutputRequest | None` 会改变 Protocol 的 signature。所有现有 `AsyncRunner` 的实现（当前为 `AsyncOpenAIRunner`）必须在同一 checkpoint 更新 call signature，否则 `isinstance(runner, AsyncRunner)` 在 Python 3.11 的 runtime check 下仍会通过（runtime_checkable 只检查方法存在性，不检查签名），但静态类型检查（pyright）会报错。更重要的是，Engine agent 内部调用 `runner.call(...)` 时如果不传 `structured_output`，pyright 会报 missing argument。
- **为什么有问题**: Plan 把 S2 作为一个独立 slice，但 S2 修改 Engine contracts/agent/runner 后，所有 runner 实现必须同步更新。如果 `AsyncOpenAIRunner.call` 不在同一 commit 更新，pyright 会立即失败。Plan 的 allowed files 包含 `dayu/engine/runners/openai/runner.py`，但没有显式说明这是 breaking change 的同步更新要求。
- **直接证据**: `dayu/engine/contracts/runner.py` L22-49 的 `AsyncRunner(Protocol)` 签名；plan S2 "`AsyncRunner.call` 增加显式 keyword-only `structured_output`"。
- **影响**: 如果 implementation agent 没有意识到这是 breaking change，可能只更新 contract 不更新 runner 实现，导致 pyright 失败或 runtime 参数缺失。
- **建议改法和验证点**: 在 S2 中显式标注 "AsyncRunner.call signature change is a Protocol breaking change; all implementations must be updated in the same commit"。或者考虑使用 `structured_output: StructuredOutputRequest | None = None` default value 以降低 breaking impact（但这可能违反 "必填" 的设计意图）。验证点：S2 完成后 pyright 无新增 error。
- **修复风险（低/中/高）**: 低（只要意识到即可）
- **严重程度（低/中/高/严重）**: 高

### F03-未修复-高-`compact_structure.py` 与 `compaction.py` 的 v3 typed dataclass 归属不清

- **位置**: F12 frozen target contracts "单一 structure owner"
- **问题类型**: 架构边界 / 契约缺失
- **当前写法**: "`dayu/host/compact_structure.py` 只拥有 output v3 的 JSON 结构，不拥有 acceptance、caps、durable state、Engine transport 或 prompt 业务文案。固定 public API：`compact_output_template_v3()`、`compact_output_json_schema_v3()`、`parse_compact_candidate_v3(text: str) -> CompactCandidateV3`"
- **反例/失败场景**: `parse_compact_candidate_v3` 返回 `CompactCandidateV3` 类型。该类型是 typed dataclass，包含 `session_summary`、`evidence_facts` 等 typed children。如果 `CompactCandidateV3` 定义在 `compact_structure.py` 中，那该模块既拥有 JSON 结构又拥有 typed dataclass——但 plan 说 "只拥有 output v3 的 JSON 结构"。如果 `CompactCandidateV3` 定义在 `compaction.py` 中，那 `compact_structure.py` 必须 import `compaction.py`，形成 structure→domain 依赖。而 `compaction.py` 当前已经拥有 `CompactCandidateV2` 及其所有子类型（L1383-1424），v3 类型放在同一文件是自然归属，但 plan 没有明确指定。
- **为什么有问题**: Implementation agent 必须自行决定 `CompactCandidateV3` 及其 typed children（`CompactSessionSummaryV3`、`CompactEvidenceFactV3` 等）的定义位置。如果放在 `compact_structure.py`，该模块变成 god module（JSON schema + template + parser + typed dataclass + validation）。如果放在 `compaction.py`，`compact_structure.py` 必须 import 它，但 plan 说 "compact_structure.py 只拥有 JSON 结构"。这个歧义会导致 implementation agent 做出不一致的设计决策。
- **直接证据**: Plan "固定 public API：`parse_compact_candidate_v3(text: str) -> CompactCandidateV3`" vs "只拥有 output v3 的 JSON 结构，不拥有 acceptance、caps、durable state"；当前 `compaction.py` L1383-1424 拥有 `CompactCandidateV2`。
- **建议改法和验证点**: 明确 `CompactCandidateV3` 及其 typed children 的定义位置。建议方案：`compaction.py` 拥有 v3 typed dataclass（与 v2 同源），`compact_structure.py` 拥有 JSON template/schema/parser 并 import v3 types。验证点：`compact_structure.py` 不包含 dataclass 定义，只包含 template/schema/parser。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### F06-未修复-中-structured-output capability 基于文档而非实测证据

### F10-未修复-低-`session_summary: null` 的 JSON Schema required/optional 语义未明确

- **位置**: F12 frozen target contracts "模型输出"
- **问题类型**: 契约缺失
- **当前写法**: "`session_summary` 可为 `null`，含义是完整 replacement 接受后清空旧 summary，不影响同一 candidate 的其它四类语义"
- **反例/失败场景**: v2 的 `CompactCandidateV2` 要求 `session_summary` 字段必须存在（exact-key check），可为 `null`。v3 需要保持相同语义。但如果 JSON Schema 定义 `session_summary` 为 `required` 且 type 为 `object | null`，模型必须总是产出该字段。如果模型省略该字段（而不是显式 `null`），parser 应该 reject（unknown-key/missing-field）。Plan 没有显式说明 v3 的 JSON Schema 是否把 `session_summary` 放入 `required`。
- **为什么有问题**: 这是一个低风险但需要明确的细节。v2 的 exact-key check 已经要求所有字段存在，v3 应该保持一致。但 implementation agent 需要知道 JSON Schema 的 `required` 列表是否包含 `session_summary`。
- **直接证据**: Plan "root exact keys 固定为 schema、session_summary、evidence_facts、answer_anchors、forward_intents、reference_continuity"（暗示 required）；v2 `CompactCandidateV2` 的 exact-key check。
- **建议改法和验证点**: 在 frozen target contracts 中明确：JSON Schema `required` 包含所有 root keys（包括 `session_summary`），`session_summary` 的 type 为 `object | null`。验证点：owner test 证明 template/schema/parser 的 required 列表一致。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
