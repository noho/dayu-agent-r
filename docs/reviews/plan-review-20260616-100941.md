# Plan Review: WU-CLI-FINS-OBS-01 Replacement Plan

## Review Target

- **文件**: `docs/host/wu-cli-fins-obs-01-replacement-plan.md`
- **范围**: 替换 PR #143 的 durable Fins job event sidecar 前提，恢复 CLI direct `AsyncIterator[FinsEvent]`，轻量化 tool awaiting observation handle
- **设计真源**: `docs/host/design.md`、`docs/engine/design.md`
- **总控真源**: `docs/host/issues-implementation-control.md`
- **历史反例**: `docs/host/wu-cli-fins-obs-01-fins-direct-live-events-plan.md`（仅作为历史参考）

## Assumptions Tested

1. CLI direct 没有 durable job 需求 → **成立**，代码证据充分
2. `AsyncIterator[FinsEvent]` 是 CLI direct 的正确模型 → **成立**，OLD 代码证据支撑
3. Tool awaiting 需要保留但不依赖 Fins core durable job system → **方向成立**，但 lightweight handle 欠规格
4. Slices A-E 可按依赖顺序实施 → **有 sequencing 风险**，C→D 存在隐式依赖
5. 不违反 Host/Engine 设计真源 → **成立**，plan 明确守住了不变边界
6. 测试迁移计划覆盖 failure paths → **有缺口**，详见 findings

## Findings

### P001-未修复-高-sync-to-async bridge gap in Slice C

- **位置**: Slice C "Fins ingestion runtime core API convergence" 步骤 3
- **问题类型**: 不可直接实施
- **当前写法**: "用 stream execution APIs 替代 `start_download` / `start_preprocess` / `start_upload` 的 direct-path 使用"
- **反例/失败场景**: 当前 `start_download` / `start_preprocess` / `start_upload` 通过 `self.executor.submit(...)` 在后台线程执行同步 adapter/runner 调用（`SecDownloadAdapter.download(...)` 等）。要把同步阻塞调用包装成 `AsyncIterator[FinsEvent]`，需要在 sync 线程和 async iterator 之间建立 bridge（如 `asyncio.Queue` + 生产者线程 + 消费者 async generator）。这是本 plan 最大的实现风险：旧 plan 明确承认"runtime-owned coarse progress，不改 adapter protocol"，但 replacement plan 的 Slice C 把"direct streaming methods"作为核心目标，却未说明 sync-to-async 桥接策略。
- **为什么有问题**: 实现 agent 进入 Slice C 时，如果发现 `download(...) -> AsyncIterator[FinsEvent]` 需要重构 `FinsIngestionThreadExecutor` 或 adapter protocol，plan 的 stop condition 要求"停止并报告 blocked"。但 plan 没有区分"adapter protocol 变更"（应 blocked）和"executor 内部 queue bridge"（可安全实现），导致实现 agent 可能过度保守（全部 blocked）或过度激进（改 adapter protocol）。
- **直接证据**: `dayu/fins/ingestion_runtime.py` 的 `start_download` (line 1688) 调用 `self._create_queued_record_with_start_lock(...)` 后 `self.executor.submit(...)`；后台线程内的 `_execute_download_request` 调用同步 `adapter.download(request)`。
- **影响**: Slice C 可能无法按 plan 描述实施，被迫退回旧 plan 的"runtime-owned coarse progress"或引入 plan 未覆盖的 executor 重构。
- **建议改法和验证点**: 在 Slice C 的 exact changes 中明确：(1) `FinsIngestionThreadExecutor` 内部使用 `asyncio.Queue` 桥接 sync 线程产出和 async iterator 消费；(2) 不修改 `FinsSourceDownloadAdapter.download(...)` / `FinsUploadRunner.run_upload(...)` protocol 签名；(3) 在 stop condition 中区分"adapter protocol 变更"和"executor 内部 bridge"。验证点：新增测试证明 async iterator 在 sync adapter 执行期间能收到 PROGRESS 事件，且 adapter 异常能正确传播为 iterator 异常或 RESULT(failure)。
- **修复风险**: 中
- **严重程度**: 高

### P002-未修复-中-FinsEvent schema 欠规格

- **位置**: Slice A 步骤 1 "定义 NEW direct FinsEvent contract，至少包含 PROGRESS 与 RESULT"
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: "至少包含 `PROGRESS` 与 `RESULT`。优先复用现有项目内等价 contract；若不存在，新增 Fins-facing typed dataclass / enum"
- **反例/失败场景**: 实现 agent 需要决定 FinsEvent 的字段、类型和语义。当前代码中已存在旧 plan 引入的 `FinsIngestionJobEventType`（含 `JOB_QUEUED`, `JOB_RUNNING`, `PROGRESS`, `CANCEL_REQUESTED`, `JOB_SUCCEEDED`, `JOB_FAILED`, `JOB_CANCELLED`），以及旧 dayu-agent 的 `FinsEventType.PROGRESS / RESULT`。replacement plan 的 FinsEvent 到底复用哪个？如果是全新 contract，`PROGRESS` 和 `RESULT` 的 payload 字段是什么？`RESULT` 携带的"足够映射退出码的业务 summary"具体包含哪些字段？
- **为什么有问题**: 没有 schema 级规格，实现 agent 会自行决定字段，导致不同 slice 之间 FinsEvent 形态不一致，或与旧 `FinsIngestionJobEventType` 产生概念重叠。
- **直接证据**: plan 只说"至少包含 PROGRESS 与 RESULT"和"字段必须自解释、业务可读"，没有给出最小 schema shape。
- **影响**: 实现 agent 可能生成与 plan 意图不一致的 FinsEvent schema，后续 slice（B、C）需要返工。
- **建议改法和验证点**: 在 Slice A 中给出 FinsEvent 的最小 typed shape，至少包括：`event_type: FinsEventType(PROGRESS | RESULT)`、`message: str`、`operation_kind: FinsIngestionOperationKind`、`ticker: str`、`document_id: str | None`、`payload: Mapping[str, JsonValue]`、`emitted_at: str`。对于 `RESULT`，明确 success/failure 的区分方式（typed subclass 或 `is_failure: bool` + `exit_code: int`）。验证点：FinsEvent dataclass 通过 pyright 且有 `__post_init__` 校验。
- **修复风险**: 低
- **严重程度**: 中

### P003-未修复-高-Slice C→D sequencing creates circular dependency risk

- **位置**: Slice C 停止条件 "如果移除 job store 会破坏 awaiting poll/resolve 且没有 lightweight replacement，删除前必须停止并升级到 Slice D 设计裁决" vs Slice D 步骤 5 "如果 implementation 提议保留任何 durable row，coding 前必须补一个 mini-design"
- **问题类型**: 切片过粗 / 状态机漏洞
- **当前写法**: Slice C 默认不保留 durable job store，但 Slice D 需要 lightweight observation handle。如果 Slice D 实现时发现需要某种 durable state（哪怕是 minimal operation row），它必须在 coding 前补 mini-design——但 Slice C 已经移除了 job store。
- **反例/失败场景**: Slice C 实现者按 plan 默认移除 job store → Slice D 实现者发现 wait adapter 的 `poll/resolve/abandon` 需要某种可查询的 operation 状态 → 必须在 Slice D 前停下来设计 lightweight handle → 可能发现需要重新引入某种 minimal durable row → Slice C 的移除决策需要回滚。
- **为什么有问题**: 这不是理论风险。当前 `wait_adapter.py` 使用 `runtime.read_job(job_id)` 来 poll 操作状态（running/succeeded/failed/cancelled）。移除 job store 后，wait adapter 的 poll 目标消失。plan 说"lightweight observation handle"但没有定义它观察什么、存储在哪里、如何被 poll。
- **直接证据**: `dayu/fins/ingestion/wait_adapter.py` line 122 调用 `self.runtime.read_job(job_id)`，line 148 调用 `self.runtime.request_cancel(job_id)`。这些调用的真源是 `FinsIngestionJobStore` 的 durable job record。移除 job store 后，这两个调用失去真源。
- **影响**: Slice C 和 Slice D 无法独立实施；实现 agent 可能在 Slice C 移除 job store 后，在 Slice D 被迫重新引入某种 durable state，导致返工。
- **建议改法和验证点**: 将 Slice C 和 Slice D 合并为一个 slice，或在 Slice C 中明确保留 minimal job record（仅 operation status + terminal result），在 Slice D 中决定是否进一步轻量化。验证点：wait adapter 的 poll/resolve/abandon 测试在 Slice C 完成后仍通过。
- **修复风险**: 中
- **严重程度**: 高

### P004-未修复-中-Cancellation propagation to runtime underspecified

- **位置**: Slice A 步骤 6 "取消应通过 async iterator 关闭 / task cancellation / cancellation token 传播到 runtime"、Slice B 步骤 3
- **问题类型**: 状态机漏洞
- **当前写法**: "不要引入 `request_cancel(job_id)`"
- **反例/失败场景**: 用户按 Ctrl+C → CLI 取消 async iterator task → 但 runtime 内部的后台线程仍在执行同步 adapter 调用（如正在下载一个大文件）。没有 `request_cancel(job_id)` 或等价的 runtime cancel 信号，后台线程会继续执行直到自然完成或超时。当前实现通过 `request_cancel(job_id)` → job record 设 `cancellation_requested=True` → 后台线程内的 `cancellation_checker` 在下一个检查点退出。移除这个机制后，取消语义变成"CLI 不再等待"，但后台工作继续。
- **为什么有问题**: 用户期望 Ctrl+C 停止当前操作。如果 CLI 不再等待但后台线程继续下载/上传，用户可能认为已取消但实际上仍在消耗网络/磁盘资源。更重要的是，如果用户立即重新运行同一命令，可能出现并发操作冲突。
- **直接证据**: `dayu/fins/ingestion_runtime.py` 后台线程内的 cancellation checker 在多个检查点读取 `cancellation_requested` 标志。移除 job store 后，这个标志消失。
- **影响**: 取消语义从"停止当前操作"退化为"CLI 不再等待"，用户体验下降。
- **建议改法和验证点**: 在 Slice C 中保留 runtime 级别的 cancellation token 或 cancel event，不通过 job_id 但通过 operation-scoped cancel signal。CLI 通过 `asyncio.Task.cancel()` 或传入 `CancellationToken` 来传播取消。验证点：测试证明 CLI cancel 后 runtime 后台线程在合理时间内停止（通过 cancellation checker 或 cancel event）。
- **修复风险**: 中
- **严重程度**: 中

### P005-未修复-低-Stream no-result edge case lacks runtime guarantee

- **位置**: Slice B 步骤 2 "stream 结束但没有 result 时失败"
- **问题类型**: 测试缺口
- **当前写法**: CLI consumer 应在 stream 结束但没有 RESULT 时失败
- **反例/失败场景**: 如果 runtime 的 async iterator 因内部异常（如 adapter crash、queue 关闭）而结束但未产出 RESULT，CLI 会将其视为失败。但 plan 没有要求 runtime 保证：无论何种退出路径，都必须产出 RESULT 或显式异常。如果 runtime 的 generator 被 garbage collect 而非显式关闭，Python 的 async generator cleanup 行为可能不触发 finally block。
- **为什么有问题**: 这是一个边界 case，但属于真实 failure mode。实现 agent 可能只在 CLI 侧处理 no-result，但不在 runtime 侧保证 terminal event。
- **直接证据**: plan 对 runtime 侧的 terminal guarantee 没有明确要求。
- **影响**: 边界场景下 CLI 显示模糊错误而非有意义的失败信息。
- **建议改法和验证点**: 在 Slice A 或 C 中增加：runtime 的 `AsyncIterator[FinsEvent]` 必须在任何退出路径（正常完成、异常、取消）产出 RESULT 或显式抛出异常；不允许静默结束。验证点：测试 runtime generator 在 adapter 异常时产出 RESULT(failure) 或抛出异常，而非静默结束。
- **修复风险**: 低
- **严重程度**: 低

### P006-未修复-低-Test gaps for wait adapter lightweight handle

- **位置**: 测试迁移计划 "将 wait adapter 测试从 `read_job(job_id)` / `request_cancel(job_id)` 改写为 lightweight observation polling / abandon 语义"
- **问题类型**: 测试缺口
- **当前写法**: Slice D 预期测试保留 awaiting 语义但改为 lightweight handle
- **反例/失败场景**: plan 没有具体列出 lightweight handle 需要覆盖的 failure paths：(1) handle 对应的 operation 已完成但 handle 未被 poll → 是否有 TTL 清理？(2) handle poll 时 operation 状态不可读（如 storage 错误）→ wait adapter 应返回什么 outcome？(3) handle abandon 后 operation 仍完成 → 是否有 orphane cleanup？(4) 同一 operation 被多个 wait record 引用 → handle 是否支持多消费者？
- **为什么有问题**: 当前 wait adapter 测试覆盖了 `read_job` / `request_cancel` 的 happy path 和部分 failure path。轻量化后，这些 failure path 的覆盖取决于 handle 的具体设计——而 handle 设计尚未确定。
- **直接证据**: plan 的测试迁移计划只提到"改为 lightweight observation polling / abandon 语义"，没有列出具体 failure paths。
- **影响**: Slice D 实现时可能遗漏 failure path 测试，导致 wait adapter 在生产中对异常状态的处理不可预测。
- **建议改法和验证点**: 在 Slice D 的预期测试中明确至少覆盖：operation 完成后 handle poll 返回 terminal、operation 进行中 handle poll 返回 pending、operation 失败后 handle poll 返回 failed、handle abandon 后不再 poll。验证点：wait adapter 测试覆盖上述四种状态转换。
- **修复风险**: 低
- **严重程度**: 低

## Open Questions

1. **FinsIngestionRuntime 的 FinsIngestionThreadExecutor 是否需要重构？** 当前后台线程执行同步调用，replacement plan 要求暴露 `AsyncIterator[FinsEvent]`。如果 executor 内部需要 queue bridge，这是否算"修改 adapter protocol"的 stop condition 触发？
2. **旧 `ingestion_events.py` 中的 `FinsIngestionJobEventType` 如何处理？** Slice A 引入新的 FinsEvent contract，但旧 plan 的 `FinsIngestionJobEventType`（含 `JOB_QUEUED`, `JOB_RUNNING` 等）已在代码中。两者是并存还是替换？
3. **Lightweight observation handle 的最小可行设计是什么？** Slice D 前必须回答：handle 观察什么（in-memory operation state？filesystem marker？minimal DB row？）、存储在哪里、如何被 poll、如何被 abandon。

## Final Plan Review Conclusion

**pass-with-risks**

Plan 的第一性原理判断正确：CLI direct 不需要 durable job system，tool awaiting 方向成立但需轻量化。plan 对 Host/Engine 不变边界的守卫清晰，slice 划分沿模块边界，停止条件合理。

但存在两个高严重度 findings：

1. **P001**: Slice C 的 sync-to-async bridge 问题未被 plan 解决，实现 agent 可能在此处 blocked。
2. **P003**: Slice C→D 的 sequencing 存在 circular dependency risk，job store 移除和 lightweight handle 设计之间有隐式依赖。

建议在进入 implementation 前修复 P001 和 P003：在 Slice C 中明确 executor 内部 bridge 策略，并将 Slice C 和 D 的依赖关系显式化（如合并为一个 slice，或在 C 中保留 minimal job record 直到 D 确认 handle 设计）。
