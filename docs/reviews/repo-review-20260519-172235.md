### 1-[严重]-异步上下文中使用 `threading.Lock` 可导致 event loop 死锁

- **入口/函数**: `_AsyncAgent._acquire_run_slot` / `_release_run_slot`
- **文件(行号)**: `dayu/engine/agent.py:653,1070`
- **输入场景**: 两个 asyncio 任务对同一 `_AsyncAgent` 实例并发调用 `run_messages()`（防御性保护的实现本身有缺陷）
- **实际分支**: `self._run_guard_lock: threading.Lock` — 同一 event loop 线程上的协程竞争锁时，`threading.Lock.acquire()` 阻塞整个 OS 线程而不交还控制权给 event loop
- **预期行为**: 应使用 `asyncio.Lock()`，协程在锁不可用时挂起自身并交还控制权
- **实际行为**: 单线程 event loop 死锁：锁持有者无法继续执行（线程被阻塞），阻塞者永久等待
- **直接证据**: `agent.py:653` `self._run_guard_lock: threading.Lock = threading.Lock()`; `agent.py:1070` `with self._run_guard_lock:`
- **影响**: 虽然正常路径不会并发调用同一 Agent 实例，但防御性锁本身的设计在 async 上下文中是反模式
- **建议改法和验证点**: 将 `threading.Lock` 替换为 `asyncio.Lock`，对应方法改为 `async with`
- **修复风险（中）**: `_acquire_run_slot` 变为 async 后需调整 `run_messages` 中的调用位置
- **严重程度（严重）**: 并发场景下死锁风险

## Open Questions

1. **God object 拆分粒度**: `_AsyncAgent` 和 `HostDispatchScheduler` 的拆分方案（按状态机阶段、按功能关注点、按测试边界）需要团队根据 Phase 里程碑做出权衡。

2. **Engine `__init__.py` 双源 re-export 的未来方向**: 当前模式有合理一面（调用方只需 import `dayu.engine`），但随着契约增长命名空间会继续膨胀。需要决定是否长期维持。

3. **Schema 迁移策略**: HOST_SCHEMA_VERSION=10 暗示存在 v1-v9 的内部迭代版本。是否有生产环境使用这些旧版本？迁移路径需优先处理。

4. **`_NeverCancelledToken` 的设计意图**: 是完全不可取消还是暂时未实现取消传播？如果是前者，Host close 路径需要独立超时保护。

5. **`cancel()` 空操作的设计意图**: 是否有意将所有取消语义完全交给 CancellationToken？如果是，需文档化并确保 Engine 在所有关键点检查 token。

## Residual Risk

- **测试覆盖率**: 测试文件数量充足（80+ 测试文件），但关键路径的边界条件覆盖率需单独验证：Engine Agent iteration loop 异常恢复路径、Host dispatch lane 获取超时路径、ToolRuntime awaiting 截断路径、compaction TOCTOU 场景
- **并发压力测试**: Lane 控制器多进程竞态（`test_lane_multiprocess.py`）、EventLog 多进程并发写入（`test_event_log_multiprocess.py`）有测试，但极端并发（高争用、进程崩溃恢复）行为未验证
- **LLM 交互路径**: `llm_compaction.py` 中的 LLM 调用和 OpenAI Runner 中的 API 调用涉及外部服务依赖，仅覆盖客户端侧逻辑
- **性能边界**: SQLite busy retry（默认 3 次）、EventLog inline payload 阈值（64KB）、Engine message 大小限制（64KB）基于合理假设，未经压力测试校准
- **内存泄漏发现验证**: `_abandoned_cancelled_wait_ids` 无界增长（发现 12）需要在生产负载下验证增长速度
