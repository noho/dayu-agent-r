### S2-CR-F01: request_id 缺失 sentinel 修复

**Controller required fix:**
> If both header and body request id are missing, return a Service-layer 400 response without calling the adapter. Use a deterministic diagnostic code such as `missing_request_id`. Preserve header-over-body priority when request id is present. Add tests for missing request id and body fallback request id.

**Fix implementation（`dayu/service/wait_callback_endpoint.py`）:**

- 新增 `_missing_request_id_response_or_none()`（第 247–271 行），在 `handle_wait_callback_completion` 中第 186–190 行**先于** envelope 构造和 adapter 调用执行。检查逻辑：
  - 若 header `x-dayu-callback-request-id` 存在 → 直接返回 None（放行）。
  - 若 body 非 object → 返回 None（放行给 `_completion_envelope_from_request` 处理）。
  - 若 body `request_id` 字段存在 → 返回 None（放行）。
  - 若两者均缺失 → 返回 `_service_response(status_code=400, status="malformed_payload", diagnostic_code="missing_request_id", ...)`，**不调用 adapter**。
- `_request_id_from_transport()`（第 386–402 行）从原来的 `return "missing"` 改为 `raise ValueError("request_id is required")`。该函数在 `_completion_envelope_from_request` 中被调用，调用前已被预检守卫；若预检被绕过，ValueError 会被主流程 catch 为 malformed_payload——fail closed。

| `test_body_request_id_is_used_when_header_is_missing` | 217–241 | 仅 body 有 request_id → 202, envelope.request_id == "body-request-1" |
| `test_header_request_id_has_priority_over_body_request_id` | 244–255 | header+body 均有 → header 优先, envelope.request_id == "request-1" |

**直接证据走读路径：**

1. `handle_wait_callback_completion` 第 186 行调用 `_missing_request_id_response_or_none(request, headers)`

**S2-CR-F01 结论：已关闭。** request_id 缺失不再折叠为字面 "missing"，Service 层返回确定性 `missing_request_id` 诊断码且不调用 adapter。header 优先和 body fallback 均有直接测试。

## Findings

### F01-未修复-低-非 object body 且无 request_id header 时 diagnostic 回退到 malformed_payload 而非 missing_request_id

- **入口/函数**: `handle_wait_callback_completion` → `_missing_request_id_response_or_none`
- **文件(行号)**: `dayu/service/wait_callback_endpoint.py:259–261`
- **输入场景**: body 为非 object JSON 值（如 array、string）且 header 不含 `X-Dayu-Callback-Request-Id`
- **实际分支**: `_missing_request_id_response_or_none` 第 259 行 `body = _json_object_or_none(request.body)` 对非 object body 返回 None → 第 260 行 `if body is None: return None` 提前返回，不做 request_id 检查 → 最终在 `_completion_envelope_from_request` 第 286 行 `_require_json_object` 抛出 TypeError → 返回 `malformed_payload` 而非 `missing_request_id`
- **预期行为**: 非 object body 本身就是 malformed，返回 `malformed_payload` 在语义上可接受；但 diagnostic_code 从 `missing_request_id` 回退到 `malformed_payload`，可能让消费方无法区分"body 格式错误"与"body 格式正确但缺 request_id"
- **实际行为**: 返回 400 `malformed_payload`，不调用 adapter
- **直接证据**: `_missing_request_id_response_or_none` 第 259–261 行与 `_completion_envelope_from_request` 第 286 行的组合路径；无测试显式覆盖 body 非对象 + 无 request_id header 场景（`test_non_object_body_returns_malformed_payload_without_adapter_call` 使用 `_default_headers()` 含 request_id header）
- **影响**: 极低——两种路径均 fail closed（400，不调用 adapter），仅 diagnostic_code 不同；但若未来调用方依赖 diagnostic_code 做自动分类，可能混淆根因
- **建议改法和验证点**: 可选补充一个测试用例：body 为 list 且 header 不含 request_id，断言返回 400 `malformed_payload`。**当前不阻塞 ship**，因为行为正确（fail closed）且 diagnostic 语义合理（非 object body 确实是 malformed payload）
- **修复风险（低）**: 纯测试补充
