### 2-[HIGH]-Engine 错误码使用裸 `str` 而非类型化枚举

### 4-[HIGH]-Context overflow 检测回退到英文裸字符串匹配

### 5-[HIGH]-Memory snapshot upsert 无版本/过期检测

- **入口/函数**: `durable/memory.py:write_memory_snapshot` + `memory.py:stable_memory_snapshot_id`
- **文件(行号)**:
  - `dayu/host/durable/memory.py:656-715`
  - `dayu/host/memory.py:1095-1116`
- **输入场景**: Memory projection 写入 snapshot。调用方基于 snapshot 的 `latest_compaction_event_ref` 导航到 EventLog 中的 compact 事件。
- **实际分支**: `write_memory_snapshot` 使用 `ON CONFLICT(snapshot_id) DO UPDATE` upsert。`snapshot_id` 由 `(session_id, consumer_id, policy_digest)` 派生——在同一 (session, consumer, policy) 组合下永远相同。新写入静默覆盖旧行。无版本号、无 append-only journal、无机制检测 snapshot 的 EventLog cursor 是否已被后续事件超越。
- **预期行为**: snapshot 应携带其覆盖的 EventLog water mark digest。消费者可检测 snapshot 是否过时。
- **实际行为**: snapshot 的 `latest_compaction_event_ref` 指向某个 compact 事件，但若之后发生了新的 compact 而 projection 未重新运行，该 ref 指向陈旧数据。消费者无法从 snapshot 自身判断 staleness。
- **直接证据**: `durable/memory.py:679-715` — `ON CONFLICT(snapshot_id) DO UPDATE`；`memory.py:1095-1116` — `stable_memory_snapshot_id` 总是返回相同 id。
- **影响**: 下游（RunInputBuilder）可能使用包含陈旧 `latest_compaction_event_ref` 的 snapshot 构建 LLM 输入，导致模型看到不一致的 memory 视图。
- **建议改法和验证点**: 在 snapshot 中加入 `snapshot_event_log_watermark_digest` 字段，编码 snapshot 覆盖的 EventLog cursor 状态。消费者读取后可与当前 EventLog cursor 比较检测 staleness。或改用 append-only 行 + 按 cursor 选择最新版本。
- **修复风险（中）**: 需变更 durable schema 和 snapshot 读写逻辑。
- **严重程度（高）**:

## Open Questions

1. **Import boundary**: Host 的 `local_proxy.py` 和 `llm_compaction.py` 导入 `run_agent_messages` / `run_agent_and_wait` 是历史形成的还是有意为之？README 描述 Engine 为 "单次 run 执行边界"，但未明确 Host 是否能直接调用 Engine 函数式入口。若此导入是经过设计评审的，Finding 3 可降级为 LOW。
2. **FinishReason.ERROR**: `ERROR` 成员仅由程序赋值、永不对应 wire value——这是设计意图还是演进过程中产生的？`CONTENT_FILTER` 也有类似问题（某些 provider 不返回该值）。是否应将 wire-originated 和 programmatic finish reasons 分开？
3. **Fins form type 归一化**: 三处 form type 归一化的分歧是否已知？`SC 13D/G` 复合别名只在 `sec_form_utils.py` 中存在，这是否意味着 `form_type_utils.py` 和 `sec_fiscal_fields.py` 永远不会处理该 form type？
4. **Memory snapshot versioning**: 当前设计明确选择 upsert 而非 append-only，是否因为 memory snapshot 重建成本可控？如果重建确实是 cheap 且正确的，Finding 5 可降级为 LOW（仅限文档增强）。

## Residual Risk

1. **Engine error code pass-through**: Runner 层协议错误码（`"sse_missing_choices"`, `"tool_call_missing_id"` 等）直接作为 `RunFailedData.error_code` 透传给 Host。Host 若按 error_code 分类做自动化决策（自动 retry/recover），可能因不了解 Runner 层错误码而做出错误决策。当前 Host 似乎未对 Engine error_code 做精确分类路由，但此风险会随着 Host 可恢复能力增强而上升。
2. **`_close_worker_lifecycle` 合成 EngineEvent**: 当前 cancel 路径上的 `_late_rejection_reason` 对合成事件的分支覆盖未经充分测试。`tests/host/test_active_cancel_dispatch.py` 和 `tests/host/test_recovery_dispatch.py` 应补充 worker clean EOF + active cancel 并发场景。
3. **Fins document identity 别名解析**: `read_runtime.py` 中的 O(N) 扫描在文档数量大时可能影响工具响应延迟。此路径当前无性能测试覆盖。
4. **hasattr/getattr 审计**: 生产代码中 `hasattr`/`getattr` 使用均为合法的库对象自省（docling、BeautifulSoup、requests），未发现作为 escape hatch 的情况。Engine/Host/Contracts 层完全零使用。风险已排除。
5. **import boundary 审计**: `dayu.runtime` 零违规导入上层包。`dayu.engine` 零违规导入 `dayu.host`。`dayu.host` 零违规导入 `dayu.service`。`dayu.contracts` 零违规导入上层包。除 Finding 3（Host 导入 Engine 实现层函数）外，所有分层边界均得到遵守。
6. **Any/object 类型审计**: `dayu/contracts/`、`dayu/engine/contracts/`、`dayu/host/` 公共签名中零处使用 `Any` 或 `object`。类型安全边界良好。
