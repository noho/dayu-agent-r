## Findings

### 01-未修复-高-`InterruptibleProcessHandle` 方法名错误：plan 写 `spawn` 但代码是 `start`

- **位置**: §5.5 "Canonical cancellation 与 Docling process boundary"，"production runner 使用现有 `InterruptibleProcessHandle`"
- **问题类型**: 不可直接实施
- **当前写法**: plan 反复引用 `InterruptibleProcessHandle` 的 "spawn、terminate/kill、process-group、bounded close" 能力（§4 DL-F09 行、§5.5、§6 Slice 3）
- **反例/失败场景**: implementation agent 搜索 `InterruptibleProcessHandle` 找不到 `spawn` 方法，可能自行添加一个 `spawn` wrapper 或误用 `start` 后在文档/测试中继续写 `spawn`，产生语义漂移
- **为什么有问题**: `dayu.runtime.interruptible_process.InterruptibleProcessHandle` 的公开方法是 `start`（line 313）、`wait`（line 328）、`terminate`（line 362）、`kill`（line 386）、`close`（line 410）。没有 `spawn` 方法。plan 的 §12 "无过度设计说明" 也写"复用现有 runtime child-process primitive"，但引用的方法名与真源不符
- **直接证据**: `dayu/runtime/interruptible_process.py` line 313: `def start(self) -> None:`；类文档字符串和全部公开方法签名均无 `spawn`
- **影响**: implementation agent 可能实现错误的 API 调用；reviewer 无法用 AST 检查验证 plan 声称的 "spawn" 行为
- **建议改法和验证点**: 将 plan 中所有 `spawn` 引用改为 `start`；AST 检查应验证 `InterruptibleProcessHandle.start` 被调用而非 `spawn`
- **修复风险（低/中/高）**: 低
- **严重程度（高）**: 高 — 直接阻塞 Slice 3 实施

### 02-未修复-中-Slice 1 范围过大：18 个 production 文件跨 5 个架构层

- **位置**: §6 Slice 1 "Allowed production files"
- **问题类型**: 切片过粗 / 过度耦合
- **当前写法**: Slice 1 允许修改 18 个 production 文件，横跨 CLI (`arg_parsing.py`, `fins.py`)、Service (`fins_direct.py`)、Fins domain (`download_contract.py`, `filing_semantics.py`)、Fins runtime (`ingestion_runtime.py`)、Fins tools (`download_tools.py`) 和 10 个 pipeline 文件
- **反例/失败场景**: CLI 参数解析变更（DL-F01/F02）与 pipeline 行为变更（DL-F03/F04/F05/F06）耦合在同一 slice，如果 CLI 变更引入类型不匹配，pipeline 测试全部失败，reviewer 无法隔离是 CLI 还是 pipeline 的问题
- **为什么有问题**: §3.2 完成定义要求"每 slice 两路 code review"；18 个文件的 slice 使 reviewer 需要同时理解 CLI contract、Service boundary、Fins request schema、SEC workflow、CN workflow 和 rebuild workflow，违反 review isolation 原则
- **直接证据**: Slice 1 allowlist 包含 `dayu/cli/arg_parsing.py`（CLI 入口）、`dayu/service/fins_direct.py`（Service 边界）、`dayu/fins/download_contract.py`（新建 typed contract）、`dayu/fins/pipelines/sec_download_workflow.py`（SEC workflow）、`dayu/fins/pipelines/cn_download_workflow.py`（CN workflow）等
- **影响**: code review 无法隔离失败来源；单个 pipeline 回归可能阻塞整个 slice 的 review 通过
- **建议改法和验证点**: 考虑将 Slice 1 拆为 1a（typed contract + CLI/Service 验证前置，DL-F01/F02）和 1b（pipeline 行为修复，DL-F03~F06）。1a 的 stop condition 是"CLI 在 workspace/service 初始化前拒绝非法输入"；1b 的 stop condition 是"pipeline 行为符合 accepted predicates"。或者保持单 slice 但明确 1b 依赖 1a 的 typed contract 先稳定
- **修复风险（低/中/高）**: 中
- **严重程度（中）**: 中 — 不阻塞实施但增加 review 失败风险

### 03-未修复-高-rebuild 工作流参数签名与 plan 的集成路径不匹配

- **位置**: §5.3 "Rebuild 与 source mutation"、§6 Slice 1 "Exact changes" 第 4 点
- **问题类型**: 不可直接实施
- **当前写法**: plan 写"rebuild 路由到 local workflows，删除 processed 依赖"；§5.3 写"`rebuild_local_artifacts=True` 直接进入现有 SEC/CN local rebuild workflow"
- **反例/失败场景**: implementation agent 尝试将 `rebuild_local_artifacts=True` 路由到 `sec_rebuild_workflow.rebuild_download_artifacts()`，但该函数的签名是 `(host, ticker, form_type, start_date, end_date, ...)`，它期望一个 `host` 对象（包含 repository 引用）和独立的 form_type/start_date/end_date 参数，不是从 `FinsDownloadRequest` 直接映射的
- **为什么有问题**: 现有 rebuild 工作流是独立设计的，不是从 download adapter 调用的。plan 声称"现有 `sec_rebuild_workflow.py` 与 `cn_download_rebuild.py`...但当前 adapter 没有调用"，但没有指定 adapter 如何调用它们、需要哪些 adapter/bridge 代码、以及 `host` 参数如何从 `FinsDownloadRequest` + storage context 构造
- **直接证据**: `dayu/fins/pipelines/sec_rebuild_workflow.py` line 106: `def rebuild_download_artifacts(host, ticker, form_type, start_date, end_date, ...)` — 参数签名与 `FinsDownloadRequest` 字段不直接对应；`dayu/fins/pipelines/cn_download_rebuild.py` line 37: `def rebuild_cn_download_artifacts(host, ticker, market, form_type, start_date, end_date, ...)` — 同样需要独立的 `host` 参数
- **影响**: implementation agent 可能需要自行设计 adapter/bridge 层，这部分 plan 没有覆盖，导致 review 不可验收
- **建议改法和验证点**: 在 Slice 1 的 "Exact changes" 中明确 rebuild 路由的具体集成路径：(1) download adapter 如何从 `FinsDownloadRequest` 构造 rebuild 工作流所需的参数；(2) `host` 对象如何构造或注入；(3) rebuild 结果如何映射回 download event stream。或者明确 rebuild 路由是"调用 rebuild 工作流的公共函数并适配参数"，而非"直接进入"
- **修复风险（低/中/高）**: 中
- **严重程度（高）**: 高 — 阻塞 Slice 1 中 DL-F05 的实施

### 04-未修复-中-取消后 CLI 等待 producer 的超时与降级行为未指定

- **位置**: §5.5 "Canonical cancellation 与 Docling process boundary"、§6 Slice 3 "Invariants"
- **问题类型**: 状态机漏洞
- **当前写法**: plan 写"CLI SIGINT handler 第一次只幂等请求 operation token，继续 await event consumer；不调用 `event_task.cancel()`"；Slice 3 invariant 写"一次 Ctrl+C 最终只有一个 canonical cancelled terminal 和 exit 130"
- **反例/失败场景**: 如果 producer 在收到 cancellation token 后不响应（例如阻塞在同步 I/O、死锁、或忽略 token），CLI 将无限等待。当前代码在 `event_task.cancel()` 后有 `CancelledError` 处理路径（fins.py:788），plan 删除这条路径后没有替代的超时/降级机制
- **为什么有问题**: plan 正确识别了 `event_task.cancel()` 的问题（它绕过了 Fins terminal owner），但删除它后没有指定：(1) CLI 等待 producer terminal 的最大超时；(2) 超时后的行为（强制 kill？SIGKILL？）；(3) 如果 producer 产出非 cancelled terminal（如 generic failure）时 CLI 是否仍 exit 130
- **直接证据**: 当前代码 fins.py:783-784 先 `request_cancel` 再 `event_task.cancel()`；plan 要求删除后者但没有替代的超时机制
- **影响**: 实现后 Ctrl+C 可能导致 CLI 挂起，用户体验比回退更差
- **建议改法和验证点**: 在 §5.5 或 Slice 3 中增加：(1) CLI 等待 producer terminal 的超时常量（建议 30s~60s）；(2) 超时后的行为（terminate child process if exists, 然后 exit 130）；(3) 明确 producer 非 cancelled terminal 时 CLI 的退出码映射
- **修复风险（低/中/高）**: 中
- **严重程度（中）**: 中 — 不阻塞核心修复但影响取消可靠性

### 06-未修复-中-storage blocking writer lock 与 condition/reservation 的 deadlock 风险

- **位置**: §5.6 "Storage concurrency 与 typed integrity"
- **问题类型**: 并发恢复风险
- **当前写法**: plan 设计了两层协调：(1) 同 process 同 ticker 使用 condition/reservation 等待；(2) 跨 process 使用 blocking writer lock。状态机为 `LOCAL_TICKER_RESERVATION -> BLOCKING_WRITER_LOCK -> STAGING -> COMPLETE_VALIDATION -> SHORT_PUBLICATION_GUARD -> OLD_OR_NEW_SWAP -> RELEASE/NOTIFY`
- **反例/失败场景**: 如果进程 A 持有 blocking writer lock 且在 STAGING 阶段阻塞（例如等待 HTTP 响应），进程 B 的 reservation 会等待进程 A 的 lock 释放。plan 声称"远端 HTTP、PDF 下载、Docling 转换必须发生在 `begin_batch` 前"，但如果实现时某个 workflow 错误地在 batch 内执行了外部 I/O，整个 ticker 的所有 writer 将被阻塞
- **为什么有问题**: plan 的 invariant 声称"owner tests 用 barrier 证明竞争只串行短 staging/publication"，但没有指定：(1) 如果外部 I/O 意外进入 batch 内的检测机制；(2) blocking wait 的最大超时；(3) 超时后的恢复行为
- **直接证据**: 当前代码 `_acquire_ticker_lock` 使用 `blocking=False`（_fs_storage_infra.py:1483），plan 要求改为 blocking，这是一个语义重大变更
- **影响**: 如果实现不当，同 ticker 并发可能从"快速失败"变为"无限阻塞"，用户体验更差
- **建议改法和验证点**: (1) 在 §5.6 中增加 blocking wait 的超时常量（建议 5~10 分钟）；(2) 明确超时后的行为（抛 typed timeout error 而非 RuntimeError）；(3) owner test 必须证明外部 I/O 不在 batch 内
- **修复风险（低/中/高）**: 中
- **严重程度（中）**: 中 — 不阻塞实施但增加并发风险

### 07-未修复-低-`ingestion_runtime.py` 拆分的下游影响未充分评估

- **位置**: §5.1 "Public invocation 与 typed request"
- **问题类型**: 过度耦合
- **当前写法**: plan 写"新增 `dayu/fins/download_contract.py`，从过大的 `ingestion_runtime.py` 抽出 download-only typed contract"；"所有新代码直接导入新真源，旧 `rebuild_processed` 字段和 re-export 全部删除"
- **反例/失败场景**: `FinsDownloadRequest` 当前定义在 `ingestion_runtime.py`（line 285），被 `dayu/fins/tools/download_tools.py`、`dayu/service/fins_direct.py`、`dayu/fins/ingestion_runtime.py` 自身、以及多个测试文件导入。移动它到 `download_contract.py` 后，所有这些导入都需要更新
- **为什么有问题**: plan 的 Slice 1 allowlist 包含 `ingestion_runtime.py` 和 `download_contract.py`，但没有列出所有需要更新导入的文件。如果 implementation agent 只更新 allowlist 中的文件，遗漏的导入会导致 ImportError
- **直接证据**: `dayu/fins/ingestion_runtime.py` line 285 定义 `FinsDownloadRequest`；`dayu/fins/tools/download_tools.py` line 83 调用 `_download_request_from_arguments` 构造 `FinsDownloadRequest`；`dayu/service/fins_direct.py` line 193-200 构造 `FinsDownloadRequest`
- **影响**: 实施时可能出现 ImportError 或导入路径混乱
- **建议改法和验证点**: 在 Slice 1 stop condition 中增加"所有 `FinsDownloadRequest` 的导入路径已更新到 `download_contract.py`"；或者在 `ingestion_runtime.py` 中保留 re-export（但这与 plan 的"旧 re-export 全部删除"矛盾）
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — 可由 pyright 检测

### 08-未修复-低-Docling 子进程临时目录的 crash 清理策略未指定

- **位置**: §5.5 "新增 `dayu/fins/pipelines/cn_docling_process.py`"
- **问题类型**: 并发恢复风险
- **当前写法**: plan 写"parent 在私有临时目录写 PDF input；child 调真实 Docling 并写 output"、"全路径 bounded close"
- **反例/失败场景**: 如果 parent 进程在 child 启动后、close 前被 SIGKILL，临时目录不会被清理。当前 SIGKILL 恢复测试（O14）证明同 workspace 可原样重跑，但没有覆盖"临时目录残留"场景
- **为什么有问题**: plan 声称"success/failure 也必须先 close，再返回或抛 typed error"，但 close 的清理行为在 parent 被 SIGKILL 时不可能执行。需要依赖 tempdir 的 OS 级清理或下次启动时的 stale temp 检测
- **直接证据**: plan 没有指定临时目录的位置（workspace 内 vs system temp）、命名规则（是否含 PID/timestamp 以避免冲突）、或 stale 检测机制
- **影响**: 低 — OS tempdir 通常有清理机制，但如果放在 workspace 内可能累积
- **建议改法和验证点**: 在 §5.5 中明确：(1) 临时目录使用 system tempdir（`tempfile.mkdtemp`）还是 workspace 内目录；(2) 命名规则包含唯一标识以避免冲突；(3) 是否需要 stale 检测（建议：system tempdir + 正常 close 清理即可，不需要 stale 检测）
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — 不阻塞实施
