## Findings

### 1-未修复-高-tool 入口 st_size 重判空文件，plan 以错误事实宣称“tool 无需重判”，同源闭环未覆盖该可达链路
- **位置**: plan「目标、动机和成功信号」第 3 条（“tool 等待结果……只消费同一个 reason”）、「契约与实现决定」（“不修改……tool……”）、同源闭环段（“`upload_tools.py` 只接入共享 runtime：tool 启动返回 awaiting……无需在 tool adapter 重判内容错误”）；对应 goal 成功信号 3 与 O22 oracle「语义 owner」段。
- **问题类型**: 目标漂移（覆盖不足）/ 架构边界（语义所有权）/ 其它（plan 对 HEAD 的事实陈述错误）
- **当前写法**: plan 声明 tool 无需任何修改，因为 tool 只启动 awaiting、结果由 observation/job summary 呈现，不存在 tool adapter 的内容重判；产品白名单明文排除 tool/Service/CLI/runtime，测试计划只验“tool awaiting 后的 observation/job 摘要”。
- **反例/失败场景**: 任何经 tool 上传 0 字节 material（LLM 场景的主入口）。`upload_tools.py:505-506` 在请求构造期以 `st_size<=0` 抢先分类为 `ToolFailedOutcome(error="invalid_argument", message="upload file path must point to a non-empty file")`（既有测试 `tests/fins/test_fins_ingestion_tools.py:2260-2292` 冻结了该行为），job/observation 从未启动，共享 owner 的 `content/empty_input_file`+safe label+“文件为空，无法上传”永远不出现。实施后同一 0 字节输入：CLI 得 content/`empty_input_file`/中文可行动文案/file_label，tool 得 usage/`invalid_argument`/英文文案/无 label——goal 信号 3“tool……只投影同一个 typed reason”“kind/code、label、文案……一致”直接不成立。
- **为什么有问题**: (1) goal 成功信号 3 与 plan 自己的目标 3 都把 tool 列为同一 reason 的消费面；(2) O22 oracle 用户已接受的语义 owner 条款明文禁止该形态——“市场 workflow、CLI/Service/tool 只能投影，不得从异常字符串、**文件大小重算**或用下游特例纠正”，全仓库唯一“从文件大小重算空文件”的代码就是 `upload_tools.py:505`；(3) 与同文件相邻契约自相矛盾：unsupported suffix（`deck.zip`）会让 tool 请求走到 production runner 并投影 owner 的 typed usage reason（`test_fins_ingestion_tools.py:2151-2257`，带 `file_label`），唯独空文件被 tool 层用另一套语义截胡；(4) plan 的“无需重判”是错误事实陈述，且白名单禁止改 tool，planned 测试（awaiting 后摘要）也不会触达该路径，实施 agent 按此 plan 交付后必然过不了 goal 一致性验收。
- **直接证据**: `dayu/fins/tools/upload_tools.py:505-506`（`if candidate.stat().st_size <= 0: raise ValueError("upload file path must point to a non-empty file")`）；`tests/fins/test_fins_ingestion_tools.py:2291-2292`（断言 `ToolFailedOutcome` + `"non-empty file" in outcome.result.message`）；goal 目标与成功信号 3（“tool 与任何 durable failure 摘要只投影同一个 typed reason”）；O22 oracle 语义 owner 段“不得从……文件大小重算”；plan 第 24 行与第 32 行原文。
- **影响**: LLM 主入口的错误分类与文案持续漂移（usage/英文 vs content/中文），违反 goal 验收信号与已接受裁决的所有权重构约束；plan 验收按现状无法证明信号 3；后续必返工，且若在 tool 失败 outcome 上补带 kind/code/file_label 还会牵出公开 schema 变更，触发 goal 停止条件。
- **建议改法和验证点**:
  1. plan 扩白名单纳入 `dayu/fins/tools/upload_tools.py`：删除 `_resolve_upload_file_path` 的 st_size 空内容重判（保留 is_file 等路径使用性校验），让空文件事实只由 `_build_original_assets` owner 分类，经 observation/job summary 投影与 CLI 相同的 `content/empty_input_file`（同 `deck.zip` 格式失败的既有通路）；同步迁移 `test_upload_tool_empty_file_returns_failed_outcome_before_observation_start` 到 owner 级新断言（typed reason JSON 与 CLI 一致、含 safe label）。
  2. 若“observation 启动前 fail-fast”是必须保留的产品契约，则 tool 失败 outcome 必须携带 owner factory 产生的完整 typed reason——那属于公开 tool 输出 schema 变更，按 goal 停止条款先停止并重新确认目标，不得默认实施。
  3. 顺带在 S1 覆盖：tool/direct/CLI 三入口对同一空文件的 `failure` JSON 逐字段一致；并把 `_build_original_assets`/`_build_pending_assets` 的 operator 日志文案从 “Filing upload …” 泛化为 filing/material 共用表述（plan 已要求泛化 docstring，日志同句需同步）。
- **修复风险（低/中/高）**: 低（方案 1，删一处检查+改一条测试）；中（方案 2 涉及 schema/goal 重确认）。
- **严重程度（低/中/高/严重）**: 高

6. **O04/O23 集成条款**：对共享文件串行审 diff、label 只取原件 basename canonicalizer、空字节仍在统一 bytes 准入处、优先顺序按 goal 核对——与 O04-F01/O23-F01 已接受方向同向，且明确不在本项设计资产命名，切分正确。
