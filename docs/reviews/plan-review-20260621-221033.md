## Findings

### 01-未修复-高-digest 计算公式与现有 resolve_wait 不一致

- **位置**: `Contract / Schema / State-machine / Public Interface Changes` — `payload_digest` 描述；`Slice 1` — adapter flow step 4
- **问题类型**: 不可直接实施
- **当前写法**: "`payload_digest` 是 callback sender 对 canonical typed callback payload 的声明摘要。Host adapter 用 `sha256_digest_json` 对 `{wait_id, idempotency_key, completed_at, outcome}` 的 typed JSON 表达重新计算"
- **反例/失败场景**: 现有 `_wait_resolution_digest` 计算 `{wait_id, idempotency_key, outcome}`（不含 `completed_at`）。adapter 的 pre-check digest 使用 `completed_at` 而 `resolve_wait` 内部 digest 不含 `completed_at`，导致：
  1. Replay 时 adapter 计算的 digest 与 idempotency store 中存储的 digest 不同 → adapter 误判为 `DIGEST_MISMATCH` 而非 `REPLAYED`。
  2. 测试 "Same callback replay returns REPLAYED" 将失败，因为 adapter 的 pre-check 在 digest 阶段就拒绝了请求。
- **为什么有问题**: Plan 声称 "outcome 改变仍由 existing wait resolution digest 判为 idempotency conflict"，说明 plan 知道 `resolve_wait` 有自己的 digest 计算。但 plan 在 adapter pre-check 阶段引入了不同的 digest 公式，导致两套 digest 语义冲突。
- **直接证据**: `dayu/host/waiting.py:1132-1146` — `_wait_resolution_digest` 函数体为 `sha256_digest_json({"wait_id": wait_id, "idempotency_key": request.idempotency_key, "outcome": _resolve_outcome_json(request.outcome)})`，不含 `completed_at`。
- **影响**: Implementation agent 按 plan 实现后，replay 测试必然失败；agent 必须重新设计 adapter 的 pre-check digest 策略，导致 plan 不是 code-generation-ready。
- **建议改法和验证点**:
  - 方案 A（推荐）：adapter pre-check 使用与 `_wait_resolution_digest` 相同的公式 `{wait_id, idempotency_key, outcome}`，不含 `completed_at`。`observed_at` / `completed_at` 只传入 `ResolveWaitRequest.observed_at`，不影响 digest。
  - 方案 B：adapter 不做 digest pre-check，完全依赖 `resolve_wait` 内部的 idempotency 判断。adapter 从 `HostApiErrorCode.IDEMPOTENCY_CONFLICT` 区分 conflict 与 replay（conflict 抛错，replay 不抛错）。
  - 验证点：replay 测试必须返回 `REPLAYED`，conflict 测试必须返回 `IDEMPOTENCY_CONFLICT`。
- **修复风险（低/中/高）**: 低 — 只需调整 adapter 的 digest 计算或删除 adapter pre-check。
- **严重程度（高）**: 阻塞 code-generation-ready。

### 02-未修复-中-TRANSPORT_REJECTED 和 MALFORMED_PAYLOAD 不应是 Host adapter 状态

- **位置**: `WaitCallbackAdapterStatus` 枚举定义；`Slice 2` — Service mapper
- **问题类型**: 架构边界
- **当前写法**: `WaitCallbackAdapterStatus` 包含 `TRANSPORT_REJECTED` 和 `MALFORMED_PAYLOAD`，且 plan 在 `Slice 2` 中描述 Service mapper "Reject method / content-type / path / body wait mismatch as `TRANSPORT_REJECTED`" 和 "Catch dataclass validation / JSON shape errors as `MALFORMED_PAYLOAD`"
- **反例/失败场景**: `TRANSPORT_REJECTED`（path/body wait_id mismatch、wrong HTTP method）和 `MALFORMED_PAYLOAD`（JSON parse error、invalid outcome shape）都是 HTTP 传输层问题，Service mapper 应直接返回 HTTP 400，不需要调用 Host adapter。如果这些状态在 `WaitCallbackAdapterStatus` 中，implementation agent 可能会在 Host adapter 中处理 HTTP 传输层逻辑，违反分层边界。
- **为什么有问题**: Plan 自己在 `Slice 2` 中说 "Path `wait_id` and body `wait_id` must match. Mismatch is `TRANSPORT_REJECTED` / HTTP 400 and must not call Host adapter"，说明这些是 Service 层不调用 adapter 直接返回的。但枚举定义在 Host adapter contract 中，造成语义混乱。
- **直接证据**: Plan `Slice 2` 测试列表明确 "Path / body wait mismatch returns 400 `transport_rejected` and does not call adapter"、"Malformed outcome shape returns 400 `malformed_payload`"。
- **影响**: Implementation agent 可能在 Host adapter 中添加 HTTP 传输层逻辑；reviewer 无法从枚举定义区分哪些状态属于 Host、哪些属于 Service。
- **建议改法和验证点**:
  - 从 `WaitCallbackAdapterStatus` 中删除 `TRANSPORT_REJECTED` 和 `MALFORMED_PAYLOAD`。这两个状态是 Service mapper 的内部分类，不需要暴露给 Host adapter contract。
  - Service mapper 在遇到这些情况时直接构造 `WaitCallbackHttpResponse(status_code=400, ...)`，不调用 adapter。
  - 验证点：Host adapter 测试不包含 `TRANSPORT_REJECTED` / `MALFORMED_PAYLOAD` 场景；Service mapper 测试覆盖这些场景。
- **修复风险（低/中/高）**: 低 — 只需从枚举中删除两个成员并在 Service mapper 中直接处理。
- **严重程度（中）**: 不阻塞核心逻辑，但会导致 implementation agent 在错误层级添加代码。

### 03-未修复-中-adapter 直接调用 DefaultHostResolveWaitService 需要注入 Host 内部组件

- **位置**: `Implementation Decisions` — "Host callback adapter should call `DefaultHostResolveWaitService` directly"
- **问题类型**: 过度耦合
- **当前写法**: "Host callback adapter should call `DefaultHostResolveWaitService` directly rather than public `resolve_wait(...)`, because the public command facade returns only `RunSnapshot` and loses `ResolveWaitResult.idempotent_replay`"
- **反例/失败场景**: `DefaultHostResolveWaitService` 构造需要 `transaction_runner`、`event_log_store`、`idempotency_store`、`projection_catchup_port` 四个 Host 内部依赖（见 `dayu/host/command.py:759-765`）。adapter 如果直接构造 service，必须接收这些内部组件，导致 adapter 与 Host durable 层紧耦合。现有的 poller adapter（`dayu/host/wait_adapter.py:143`）使用 `WaitResolvePort` 协议抽象，不需要知道 Host 内部组件。
- **为什么有问题**: 项目约束要求"模块间依赖最小化，优先接口或协议，避免上层直接依赖具体实现细节"。adapter 直接依赖 `DefaultHostResolveWaitService`（具体实现）而非协议，违反此约束。现有 poller adapter 已有 `WaitResolvePort` 协议模式可复用。
- **直接证据**: `dayu/host/wait_adapter.py:143-146` — `WaitResolvePort` 协议定义了 `resolve_wait(wait_id, request) -> RunSnapshot`。poller adapter 通过此协议调用 resolve，不直接依赖 `DefaultHostResolveWaitService`。
- **影响**: adapter 模块需要 import Host durable 层组件，增加耦合度；与现有 poller adapter 的设计模式不一致。
- **建议改法和验证点**:
  - 方案 A（推荐）：复用 `WaitResolvePort` 协议。callback adapter 通过 `WaitResolvePort.resolve_wait(...)` 调用。`idempotent_replay` 的区分通过异常处理实现：`HostApiErrorCode.IDEMPOTENCY_CONFLICT` 表示 conflict（不同 key/digest），无异常表示成功（可能是 replay）。`ResolveWaitResult.idempotent_replay` 的精确区分可以通过扩展 `WaitResolvePort` 返回类型或在 `RunSnapshot` 中添加 `idempotent_replay` 字段来实现。
  - 方案 B：创建 `CallbackWaitResolvePort(Protocol)`，返回 `CallbackResolveResult(run: RunSnapshot, idempotent_replay: bool)`，由 Host command 层实现。
  - 验证点：adapter 模块不 import `dayu/host/durable/` 或 `dayu/host/waiting.py`。
- **修复风险（低/中/高）**: 中 — 需要设计 port 协议的返回类型。
- **严重程度（中）**: 不阻塞核心逻辑，但影响架构一致性。

### 04-未修复-低-stale callback 规则的 deadline_at / expires_at 语义需要明确类型

- **位置**: `Contract / Schema / State-machine / Public Interface Changes` — stale rule
- **问题类型**: 契约缺失
- **当前写法**: "若 wait record 有 `deadline_at` 或 `expires_at`，且 `completed_at` 晚于该边界，adapter 返回 `STALE_CALLBACK`"
- **反例/失败场景**: `WaitRecordRow.deadline_at` 和 `expires_at` 的类型是 `str | None`（`dayu/host/durable/state.py:430-431`），不是 `datetime`。plan 说 `completed_at` 是 `datetime` 类型。adapter 需要将 `str` 解析为 `datetime` 后比较，但 plan 没有指定解析规则（ISO 8601？UTC？格式校验？）。如果解析失败，adapter 应返回什么状态？
- **为什么有问题**: Implementation agent 需要自行决定 str → datetime 解析逻辑和错误处理，可能产生不一致行为。
- **直接证据**: `dayu/host/durable/state.py:430-431` — `deadline_at: str | None`、`expires_at: str | None`。
- **影响**: Implementation agent 可能做出与现有代码不一致的 datetime 解析选择。
- **建议改法和验证点**: 明确 `deadline_at` / `expires_at` 为 ISO 8601 UTC 字符串，解析失败时视为无 deadline（不做 stale rejection）。或引用现有代码中的 datetime 解析 helper。
- **修复风险（低/中/高）**: 低 — 只需补充一行解析规则。
- **严重程度（低）**: 不阻塞核心逻辑。

### 05-未修复-低-401 vs 403 映射规则未指定

- **位置**: `Exact Callback Endpoint Form and Layer Boundary` — HTTP status mapping
- **问题类型**: 契约缺失
- **当前写法**: "`AUTH_FAILED` -> 401 or 403 based on auth reject reason"
- **反例/失败场景**: Implementation agent 需要自行决定 `WaitCallbackAuthRejected.reason_code` 的哪些值映射到 401、哪些映射到 403。不同 agent 可能做出不同选择。
- **为什么有问题**: 测试矩阵中 "Auth rejection returns `AUTH_FAILED` without resolver call" 没有指定 HTTP 状态码，无法验证 Service mapper 的映射正确性。
- **直接证据**: Plan HTTP status mapping 表。
- **影响**: 低 — 401/403 都是合理的 auth 失败响应，不影响功能正确性。
- **建议改法和验证点**: 建议 401 表示 credential 无效/缺失，403 表示 credential 有效但权限不足。或简化为统一 401。
- **修复风险（低/中/高）**: 低 — 只需补充一行映射规则。
- **严重程度（低）**: 不阻塞核心逻辑。

### 06-未修复-低-Host adapter 测试缺少 deadline_at / expires_at 双 None 场景

- **位置**: `Slice 1` — Tests
- **问题类型**: 测试缺口
- **当前写法**: "Stale callback with existing `deadline_at` / `expires_at` returns `STALE_CALLBACK` without EventLog append"
- **反例/失败场景**: Plan 的 stale rule 说 "没有 deadline / expires 时不做 stale rejection"，但测试列表中没有覆盖 `deadline_at=None` 且 `expires_at=None` 时 callback 不被 stale rejection 的场景。这是一个 happy path 变体，需要锁定行为。
- **为什么有问题**: 如果 implementation agent 错误地在 deadline/expires 为 None 时也做 stale rejection，现有测试无法捕获。
- **直接证据**: Plan stale rule 文本 vs Slice 1 测试列表。
- **影响**: 低 — 功能正确性风险小，但测试覆盖不完整。
- **建议改法和验证点**: 补充测试 "callback with wait record having no deadline/expires is not rejected as stale"。
- **修复风险（低/中/高）**: 低 — 只需补充一个测试用例。
- **严重程度（低）**: 不阻塞核心逻辑。

## Open Questions

1. **`idempotent_replay` 精确区分的必要性**: Plan 要求区分 `REPLAYED`（同 key 同 digest）和 `ACCEPTED`（首次成功）。现有 `resolve_wait` 在 replay 时不会抛错，但公共 facade 丢失 `idempotent_replay` 标志。如果改用异常处理（`IDEMPOTENCY_CONFLICT` = conflict，无异常 = success），replay 和首次成功在 adapter 层面无法区分。是否需要扩展 `WaitResolvePort` 返回类型来携带 `idempotent_replay`？这个问题的答案影响 Finding 03 的方案选择。

2. **`INTERNAL_ERROR` 的触发条件**: Plan 列出 `INTERNAL_ERROR` 状态但没有说明何时使用。`resolve_wait` 抛出非 `HostApiError` 异常时？还是 `HostApiError` 的某些错误码？建议明确为"adapter 捕获非预期异常时返回 `INTERNAL_ERROR`"。

## Conclusion

**pass-with-risks**

Plan 整体架构方向正确：callback 作为 transport adapter 进入 existing `resolve_wait` pipeline，不成为第二套状态 owner，分层边界清晰。Non-goals 和 stop conditions 合理。测试矩阵覆盖核心 failure paths。

但存在一个高严重度 finding（digest 计算公式不一致）会直接阻塞 code-generation-ready：implementation agent 按 plan 实现后 replay 测试必然失败，必须重新设计 adapter 的 pre-check 策略。建议在进入 implementation 前修复 Finding 01 和 Finding 02。

Findings 03-06 为中/低严重度，不阻塞 implementation 但会影响架构一致性或测试覆盖完整性。
