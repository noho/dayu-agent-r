## Findings

### F1 [Medium] `_run_to_store` 后台任务静默吞没翻译 / append / 终态推导异常

**文件**：`dayu/host/_run_harness.py:142-202`

`_run_to_store` 的异常处理分为两层：

- 外层 `try/except`（L162-174）：捕获 `proxy.stream_engine_events()` 调用阶段的异常，转为 Host-owned failure。
- 内层 `try/except`（L176-188）：只捕获 `anext(engine_events)` 的异常。

`translate_engine_event`、`event_store.append`、`terminal_result_from_event` 的调用（L190-194）不在任何 `except` 分支中。若它们抛出异常（例如 `TypeError`：终态事件 data 类型不匹配），异常会传播到 `finally` 块后终止协程。

**问题**：`start_run` 通过 `asyncio.create_task(self._run_to_store(...))` 启动后台任务（L122），无人 `await` 该 task。Python asyncio 对未被 await 的 task 异常只发出 `asyncio: Task exception was never retrieved` 警告，异常本身被丢弃。

**后果**：生产路径下，Host 契约违反（如 Engine 产出 data 类型与 event type 不匹配）会静默丢失，不会产生 Host-owned failure 事件，也不会向调用方暴露错误。调用方只能看到事件流在某处截断，无法区分"Engine 主动结束"和"Host 翻译崩溃"。

**注意**：测试 `test_terminal_result_error_does_not_append_host_failure` 直接 `await harness._run_to_store(...)`，所以能看到异常。这掩盖了生产路径的问题。

**建议**：在 `_run_to_store` 的最外层加一个顶层 `except` 分支，至少记录 ERROR 级别日志；或者将后台 task 句柄保存下来供后续检查。

**修复状态**：已修复。`start_run()` 创建的后台 task 已注册 done callback，callback 会取回异常并记录
`host.run.background_task_failed` ERROR 日志，避免 “Task exception was never retrieved”。本修复只增强
诊断观测，不把 Host 翻译 / append / terminal result 契约错误伪装成 Host-owned failure，也不引入 P7
supervisor / governance。

### F2 [Medium] `_DEFAULT_HARNESS_BY_LOOP` 对已关闭 event loop 永久持有强引用

**文件**：`dayu/host/_run_harness.py:275`

```python
_DEFAULT_HARNESS_BY_LOOP: dict[asyncio.AbstractEventLoop, LocalRunHarness] = {}
```

以 `asyncio.AbstractEventLoop` 为 key 存储 `LocalRunHarness` 实例。当 event loop 关闭后（例如 `asyncio.run()` 返回），字典中的条目不会被清除。`LocalRunHarness` 持有 `InMemoryRunEventStore`，其中保留了该 loop 生命周期内所有 run 的全部事件。

**后果**：长生命周期进程或多次调用 `asyncio.run()` 的场景下，事件数据持续累积、永不释放。

**建议**：使用 `WeakValueDictionary` 不适用（value 不是 weakref-safe 的），改为在 loop 关闭时清理条目，或改用不绑定 loop 的单例 + run_id 隔离策略。

**修复状态**：已修复。默认 harness 缓存已从普通 `dict` 改为 `WeakKeyDictionary`，不再对已关闭且无外部引用的
event loop 保持强引用。

### F3 [Low] `RUNNER_CONTENT_COMPLETED` 未被事件分类矩阵测试覆盖

**文件**：`tests/host/test_phase1_5_run_harness_eventlog.py:508-599`

`test_engine_event_kind_classification_matrix` 覆盖了 7 种 `EngineEventType`，但遗漏了 `_PREVIEW_ENGINE_EVENT_TYPES` 中声明的 `RUNNER_CONTENT_COMPLETED`。

**后果**：若 `_classify_event_kind` 对该类型的分类逻辑出错，测试不会发现。

**建议**：在矩阵中补充 `(EngineEventType.RUNNER_CONTENT_COMPLETED, ..., RunEventKind.PREVIEW)` 用例。

**修复状态**：已修复。canonical / preview 分类矩阵已补充 `RUNNER_CONTENT_COMPLETED`，并断言其分类为
`PREVIEW`。

### F4 [Info] `_NeverCancelledToken` 默认实例未隔离

**文件**：`dayu/host/_run_harness.py:42-71`, `dayu/host/_run_harness.py:154`

`_run_to_store` 每次调用都创建新的 `_NeverCancelledToken()` 实例。但 `_build_default_harness()` 创建的 `LocalRunHarness` 在多个 run 间共享（通过 `_DEFAULT_HARNESS_BY_LOOP`），所有 run 的后台任务使用各自独立的 token。

当前无正确性问题。但如果未来需要支持取消，需注意 token 的生命周期管理。

### F5 [Info] `_event_store.py` 的 `_subscribe` 方法内部结构较复杂

**文件**：`dayu/host/_event_store.py:182-252`

`_subscribe` 使用嵌套 `while True` 循环 + condition wait + cursor predicate，逻辑正确但认知负荷较高。当前注释足够清晰，但如果未来需要修改（例如支持取消），需格外注意 replay/follow 之间的竞态窗口。

无需立即修改，仅供后续维护者参考。
