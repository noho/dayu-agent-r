## Findings

### 001-未修复-中-幂等写入缺少 IntegrityError 并发保护

- **入口/函数**: `record_idempotent_result()`
- **文件(行号)**: `dayu/host/durable/idempotency.py`(156-186行)
- **输入场景**: 两个并发事务在同一 scope 内为相同的 `(scope_kind, scope_id, idempotency_key)` 插入幂等记录。
- **实际分支**: 函数先 `read_idempotency_record`（148行），发现不存在后执行 `INSERT`（157行）。如果此时另一个事务已提交了同一 key 的插入，`INSERT` 抛出 `sqlite3.IntegrityError`。
- **预期行为**: 与 `event_log.py` 的 `append_event`（394-402行）一致——捕获 `sqlite3.IntegrityError`，重新读取已有记录并比较 `semantic_input_digest`，返回既有记录或抛出 `HostIdempotencyConflictError`。
- **实际行为**: `INSERT` 语句没有 `try/except sqlite3.IntegrityError` 包裹，`IntegrityError` 会直接穿透到 transaction runner 的 `_classify_sqlite_error`，被分类为通用 `HostUniqueConstraintError("Host durable unique constraint failed")`，丢失了"幂等命中"的语义。
- **直接证据**: `idempotency.py` 157-182行的 `transaction.execute(INSERT ...)` 无 IntegrityError catch；对比 `event_log.py` 394-402行有完整的 IntegrityError 回读 + digest 比较逻辑。
- **影响**: 并发幂等写入场景下，后到的事务不会获得既有的 `IdempotencyRecord`，而是抛出无语义的 `HostUniqueConstraintError`。调用方无法区分"幂等命中"与"真正的唯一约束违反"。
- **建议改法和验证点**: 在 `INSERT` 外包一层 `try/except sqlite3.IntegrityError`，与 `append_event` 对齐：捕获后调用 `read_idempotency_record`，若存在且 digest 匹配则返回既有记录，否则抛出 `HostIdempotencyConflictError`。验证点：补并发写入测试，确认重复 key 返回既有记录而非异常。
- **修复风险（低/中/高）**: 低。逻辑与 event_log 现有模式完全对齐。
- **严重程度（低/中/高/严重）**: 中。单进程单连接场景不会触发；多进程/高并发下会导致幂等语义失效。

## Residual Risk

1. **FK 列索引缺失**（低）: `host_sessions`、`host_runs`、`host_attempts`、`host_wait_records` 等表中大量 FK 列（`session_id`、`run_id`、`attempt_id`、`event_id`）未建独立索引。SQLite 在 DELETE/UPDATE 父表时需扫描子表验证 FK 约束，无索引时退化为全表扫描。当前本地单进程场景影响可忽略，但若后续有 session/run 数据量增长或 purge 删除路径，FK 约束检查将成为性能瓶颈。属防御性改进，CREATE INDEX IF NOT EXISTS 是幂等操作。
2. **context budget estimator 对中文文本不准确**（低）: `DEFAULT_ESTIMATOR_CHARS_PER_TOKEN = 3` 基于英文文本估算，中文 token 化时通常 1-2 token/字符，会低估 token 数。由于 soft threshold 80%、hard threshold 90% 配合 safety margin，实际风险可控，且可通过 `ContextBudgetPolicy` 外部调整 ratio 补偿。
3. **`_budget_after_compact` 使用独立的 overhead 常量副本**（低）: `_POST_COMPACT_SYSTEM_PROMPT_ESTIMATE`、`_POST_COMPACT_BASE_MESSAGE_COUNT = 2`、`_POST_COMPACT_TOOL_SCHEMA_OVERHEAD_COUNT = 1` 是对 post-compact run context 结构的硬编码假设。若 Engine runner 消息结构变化，这些常量不会自动同步。仅影响 proactive compact 的预算估算精度，不影响 dispatch 决策真源。
4. **`CRASHED_SUSPECTED` 枚举值无写入路径**（低）: 该终态枚举在当前代码中无写入路径，仅在 orphan classifier 中被兜底为 `Inconclusive`。属安全的预留设计，建议在 liveness 模块 docstring 中说明其当前状态和未来意图。
