### F01-未修复-高-S1 原子垂直切换过粗，缺少中间验证检查点

- **位置**: Implementation slices > S1
- **问题类型**: 切片过粗
- **当前写法**: S1 一次完成 15 个生产文件和 14 个测试文件的 v3→v4 原子切换，不允许 v3/v4 双路径。migration order 列出 6 步，但无中间验证点。
- **反例/失败场景**: 实现 agent 在完成步骤 1-3（定义类型、更新 structure、实现 governance）后开始步骤 4（切换 artifact/terminal），此时发现步骤 3 的 binding 逻辑有边界错误。由于所有修改尚未完成，无法运行任何测试验证中间状态；agent 必须回退大量已完成工作。
- **为什么有问题**: AGENTS.md 要求"每次代码修改后，都必须补齐或更新对应测试，并优先验证通过"。S1 的 6 步 migration order 中每步都依赖前一步，但无中间测试验证点，违反渐进验证原则。v3/v4 不允许双路径的约束不等于不允许中间验证——新类型定义后可以立即用独立测试验证其构造/校验行为。
- **直接证据**: plan S1 "Required migration order inside the slice" 列出 6 步，最后一步才"同步所有 production call sites、fake 与 owner tests"。15 个生产文件列表见 S1 Allowed production/config files。
- **影响**: 实现 agent 无法渐进验证，bug 在集成阶段才暴露，返工成本高。
- **建议改法和验证点**: 将 S1 拆为两个子 slice：
  - S1a：定义 v4 types（compaction.py）、更新 structure template/schema/parser（compact_structure.py）、实现 governance atomic expansion/binding（context_governance.py）、更新 compact_material.py rolling builder。验证：新增 v4 type 单元测试 + governance unit tests。
  - S1b：切换 artifact/terminal（compact_payload.py, compact_artifact.py）、切换 Memory/reconnect（memory.py, run_input.py）、切换所有 call sites、同步 fake 与 owner tests、全仓 rg residue scan。验证：完整 owner tests + integration tests。
  两个子 slice 之间用 code review gate 隔离，确保 S1a 的类型/逻辑正确后再切换消费者。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### F02-未修复-高-缺少 schema-4 到 schema-5 运营影响显式说明

- **位置**: Residual risks > 第一条
- **问题类型**: 契约缺失
- **当前写法**: "fresh v4/schema-5 不兼容读取旧 compact payload/session；这是已确认的新 schema 边界，不增加 migration 或 dual reader。正式 scenario 必须新建 workspace/session。"
- **反例/失败场景**: 用户有包含 schema-4 compact artifacts 的现有 workspace。升级后首次 rolling compaction 尝试从 schema-4 artifact 重建 previous compacted view。`_previous_compacted_view_pair_from_compacted_event`（compact_material.py:2244）调用 `parse_context_compacted_semantic_payload(payload).accepted_candidate`，但 schema-5 parser 不接受 schema-4 payload，抛出 `HostDurableError`。rolling builder 无法构造 `PREVIOUS_EVIDENCE_FACT` boundary entries，所有旧 facts 被 deterministic fallback 省略。
- **为什么有问题**: Goal Confirmation 确认"per-fact public projection 的最终字段名、schema literal/version 与 slice 划分在 plan gate 固化"。但 plan 的 residual risks 只说了"不兼容读取"，没有说明运营后果：旧 facts 在首次 rolling 时被静默丢弃，用户可能不知道。这不是 blocking issue（已确认 fresh schema 边界），但 plan 应显式说明失败模式和用户感知。
- **直接证据**: compact_material.py:2244-2248 调用 `parse_context_compacted_semantic_payload(payload).accepted_candidate`；schema-5 parser 不接受 schema-4 payload。Goal Confirmation "正式 scenario 必须新建 workspace/session"。
- **影响**: 用户升级后丢失历史 compacted facts，且无明确提示。
- **建议改法和验证点**: 在 residual risks 中补充："升级后首次 rolling compaction 遇到 schema-4 artifact 时，`parse_context_compacted_semantic_payload` 会 typed reject，rolling builder 无法构造 previous boundary entries，系统走 deterministic fallback（tier 4/5），不污染 Memory。用户感知为历史 compacted facts 被省略，新 facts 正常积累。这是已确认的 fresh schema 边界代价。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### F03-未修复-高-PromptLocalProvenanceEntry 新字段设计需明确替换还是共存

- **位置**: Frozen v4 contracts > 1. Host-internal immutable source boundary
- **问题类型**: 架构边界
- **当前写法**: "PromptLocalProvenanceEntry 增加唯一字段 canonical_evidence_refs: tuple[str, ...]：current evidence material 从既有 canonical accepted_evidence_id 机械形成单元素 tuple；两者必须一致。"
- **反例/失败场景**: 实现 agent 同时保留 `accepted_evidence_id` 和 `canonical_evidence_refs`。两个字段表达同一语义（canonical evidence identifier），但形式不同（`str | None` vs `tuple[str, ...]`）。下游消费者有的读 `accepted_evidence_id`，有的读 `canonical_evidence_refs`，出现双真源。
- **为什么有问题**: AGENTS.md 语义所有权约束要求"每个业务事实...都必须有唯一清晰 owner"。`accepted_evidence_id` 和 `canonical_evidence_refs` 都表达"该 provenance entry 对应的 canonical evidence identifiers"。若两者共存，违反单一真源。plan 说"两者必须一致"，但一致性校验本身就是一个额外的不变量，增加复杂度。
- **直接证据**: PromptLocalProvenanceEntry 当前有 `accepted_evidence_id: str | None`（compaction.py:261）。plan 说"增加唯一字段 canonical_evidence_refs: tuple[str, ...]"。compact_payload.py:633 读 `entry.accepted_evidence_id`。compact_pipeline.py:1149 读 `block.accepted_evidence_id`。
- **影响**: 双真源导致下游消费者行为不一致；一致性校验增加复杂度和维护负担。
- **建议改法和验证点**: plan 应明确选择以下方案之一：
  - **方案 A（推荐）**: 将 `accepted_evidence_id: str | None` 替换为 `canonical_evidence_refs: tuple[str, ...]`。单元素 tuple 表示有 evidence，空 tuple 表示无 evidence。下游消费者统一读取新字段。这是 clean replacement，无双真源。
  - **方案 B**: 保留 `accepted_evidence_id` 为 deprecated，新增 `canonical_evidence_refs`。在 `__post_init__` 中校验一致性。仅在 S1 完成后、S2 开始前删除 deprecated 字段。
  方案 A 更符合 AGENTS.md "禁止兼容性代码" 约束。验证：所有读取 `accepted_evidence_id` 的 call sites（compact_payload.py:633, compact_pipeline.py:1149, compact_material.py 多处）统一改为读取 `canonical_evidence_refs`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### F04-未修复-中-v4 类型定义未给出精确 dataclass 规格

- **位置**: Frozen v4 contracts > 3. Host accepted replacement v4
- **问题类型**: 不可直接实施
- **当前写法**: plan 用散文描述 `CompactAcceptedEvidenceFactV4` 和 `CompactAcceptedReplacementV4` 的字段，但未给出精确的 Python dataclass 定义（字段类型、默认值、`__post_init__` 校验规则）。
- **反例/失败场景**: 实现 agent 根据散文描述创建 dataclass，可能遗漏校验规则（如 `canonical_evidence_refs` 必须非空的检查只对 evidence fact 适用，不适用 session_summary 等非 evidence sections）。或字段命名不一致（如 `selection_labels` vs `support_labels`）。
- **为什么有问题**: plan 要求"code-generation-ready"。散文描述的类型定义留给实现 agent 过多推断空间，尤其是校验规则（哪些字段对哪种 fact 类型有非空约束）。
- **直接证据**: plan 3. Host accepted replacement v4 描述 `CompactAcceptedEvidenceFactV4` 固定字段为 claim/selection_labels/context_labels/canonical_evidence_refs，但未给出 `__post_init__` 校验规则。当前 v3 `CompactEvidenceFactV3`（compaction.py:1195）有详细的 `__post_init__` 校验。
- **影响**: 实现 agent 可能遗漏关键校验规则，导致 runtime 错误。
- **建议改法和验证点**: 在 plan 中补充 `CompactAcceptedEvidenceFactV4` 和 `CompactAcceptedReplacementV4` 的完整 dataclass 定义，包括字段类型、默认值和 `__post_init__` 校验规则。至少包括：(1) `claim` 非空 str；(2) `selection_labels` 非空唯一 str tuple；(3) `canonical_evidence_refs` 非空唯一 str tuple；(4) `context_labels` 可空唯一 str tuple。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F05-未修复-中-PREVIOUS_EVIDENCE_FACT boundary entry 首次 rolling 的 canonical_evidence_refs 来源未显式说明

- **位置**: Frozen v4 contracts > 1. Host-internal immutable source boundary; 5. Rolling, Memory, reconnect and public Tool Trace
- **问题类型**: 状态机漏洞
- **当前写法**: "PREVIOUS_EVIDENCE_FACT 与 EVIDENCE_MATERIAL 的 canonical_evidence_refs 必须非空且唯一"。rolling section 说"从 previous typed accepted_replacement.evidence_facts 构造 previous blocks"。
- **反例/失败场景**: 首次使用 v4 schema 进行 rolling compaction 时，prior compact event 是 schema-4 格式，没有 `accepted_replacement` 字段。rolling builder 无法从 prior artifact 读取 per-fact `canonical_evidence_refs`。`PREVIOUS_EVIDENCE_FACT` boundary entry 的 `canonical_evidence_refs` 无法构造为非空。
- **为什么有问题**: 这是 F02 的技术细节。plan 的 rolling section 说"从 previous typed accepted_replacement.evidence_facts 构造 previous blocks"，但没有说明当 prior artifact 是 schema-4 格式时如何处理。v4 boundary contract 要求 `PREVIOUS_EVIDENCE_FACT` 的 refs 非空，但 schema-4 artifact 没有这个信息。
- **直接证据**: compact_material.py:2244-2248 读取 `parse_context_compacted_semantic_payload(payload).accepted_candidate`。schema-4 payload 没有 `accepted_replacement` 字段。v4 boundary contract 要求 `PREVIOUS_EVIDENCE_FACT` 的 `canonical_evidence_refs` 非空。
- **影响**: 实现 agent 需要自行决定如何处理 schema-4 → v4 的 rolling 过渡，可能做出与 plan 意图不一致的决策。
- **建议改法和验证点**: 在 rolling section 明确："当 `parse_context_compacted_semantic_payload` 返回的 payload 不含 `accepted_replacement`（schema-4 格式）时，rolling builder 不构造 `PREVIOUS_EVIDENCE_FACT` boundary entries。所有旧 facts 被 deterministic fallback 省略。这是 fresh schema 边界的已知行为。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F06-未修复-中-缺少 proposal 改写 previous claim 的反向测试

- **位置**: Implementation slices > S1 > Mandatory S1 owner tests
- **问题类型**: 测试缺口
- **当前写法**: S1 owner test #2 说"v4 从结构上无'改写 previous claim'路径；把 previous label 塞入 new fact support strict reject"。这测试了 support_labels 方向的 misuse。
- **反例/失败场景**: 模型在 `evidence_facts` 中创建一个新 fact，其 `claim` 文本恰好与某个 previous fact 的 claim 相同或高度相似，但 `support_labels` 引用的是 current evidence material。Host 按 proposal 展开 new facts，claim 来自 proposal（非 boundary），refs 来自 current evidence。这个"改写"通过了所有 binding 检查，因为 claim 不是从 boundary 复制的。
- **为什么有问题**: Goal Confirmation goal #2 说"LLM 只能显式选择保留哪些旧 facts，未选择即省略，不能提交旧 fact 的改写 claim"。但 plan 的 test #2 只测试了"把 previous label 塞入 new fact support"的情况，没有测试"用 current evidence 包装旧 claim"的情况。v4 架构确实从结构上阻止了"改写 previous claim"（因为 retained facts 的 claim 由 Host 从 boundary 原子复制），但 new facts 的 claim 来自 proposal，理论上可以与 previous claim 相同。
- **直接证据**: Goal Confirmation goal #2。S1 owner test #2。plan 3. "按 proposal 顺序展开 new facts。claim 来自 proposal"。
- **影响**: 这不是真正的 bug（duplicate 检查会处理 exact duplicates），但 test 覆盖不完整。如果 duplicate 检查是 whitespace-canonical 的，近似 duplicates 可能通过。
- **建议改法和验证点**: 补充一个测试："new fact 的 claim 与某个未 retained 的 previous fact claim 相同时，该 new fact 仍可被接受（因为它引用了 current evidence），但 duplicate 检查应在 combined accepted facts 上执行。" 这验证了 duplicate 检查覆盖了 retained + new 的组合。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
