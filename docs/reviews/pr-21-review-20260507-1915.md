## Findings

### 1. [Medium] [已修复，待复查] `compact()` 返回的 `degraded_item_count` 语义与实际来源不一致

**文件**: [dayu/host/_context_compaction.py:127-130](dayu/host/_context_compaction.py#L127-L130) 及 [dayu/host/_context_compaction.py:541-549](dayu/host/_context_compaction.py#L541-L549)

**问题**: `dropped_count` 由 compact 直接计算（丢弃的 raw turn 数），语义正确。但 `degraded_count` 来自 `_count_previous_trace_degraded_items(previous_trace)`，统计的是**上一次 RunInputBuilder.build() 时**被降级/排除的 item 数（reason != "included"），而非本次 compact 动作自身降级的 item 数。

`HostContextCompactCompletedData.degraded_item_count` 的 docstring 写的是"被摘要降级的历史 item 数"，消费者可能理解为 compact 直接降级的 item 数，但实际得到的是上次 RunInput 构造时的 trace 统计。

**建议**: 在 docstring 中明确说明此字段反映的是 compact 前最后一次 RunInput 构造时的降级情况，或者从 compact action 中独立计算降级数。

**修复说明**: 已改为独立表达本次 deterministic compact 的降级数。当前 compact 只显式丢弃 raw turns，不做“保留但降级”的额外动作，因此 `degraded_item_count=0`；`dropped_item_count` 继续记录本次丢弃的 raw turns。已同步 contracts docstring、Host README，并在 compact 测试中断言语义。

### 2. [Low-Medium] [已修复，待复查] `LocalRunHarness.__post_init__` 缺少对 `context_compact_retry_limit` 的负数校验

**文件**: [dayu/host/_run_harness.py:232-241](dayu/host/_run_harness.py#L232-L241)

**问题**: `__post_init__` 校验了 `run_input_trace_cache_limit > 0`，但没有对 `context_compact_retry_limit` 做非负校验。传入负值不会崩溃，但会使 `_compact_or_fail` 中 `attempt_index >= self.context_compact_retry_limit` 对 attempt_index=0 立即为 True，所有 compact 被静默跳过，且没有明确的配置无效错误信息。

**建议**: 在 `__post_init__` 中增加 `if self.context_compact_retry_limit < 0: raise ValueError(...)`。

**修复说明**: `LocalRunHarness.__post_init__` 已增加 `context_compact_retry_limit >= 0` 校验，负数配置 fail fast 为 `context_compact_retry_limit_must_be_non_negative`；已补 Host 测试。

### 3. [Low] [已修复，待复查] `_format_anchor` / `_format_tool_fact` / `_format_claim` 每个 item 重复输出 section header

**文件**: [dayu/host/_context_compaction.py:432-464](dayu/host/_context_compaction.py#L432-L464)

**问题**: 三个格式化函数各自在输出中写入 section header（如 `## Evidence Anchors`、`## Tool Facts`、`## Stable Claim`）。当 snapshot 包含多个 anchor/fact/claim 时，compact block 会包含多个重复的 section header。以 5 个 evidence anchor 为例，compact block 中会出现 5 行 `## Evidence Anchors`。这既浪费 token 预算，也降低了 compact block 对模型的可读性。

**注意**: 同样的问题也存在于 [dayu/host/_run_input_builder.py:963-995](dayu/host/_run_input_builder.py#L963-L995)，属于既有模式。但 compact block 的 token 敏感性更高，建议单独修复。

**修复说明**: compact block 侧已把 section header 移到列表组装层，单 item formatter 只返回正文；`Stable Claims`、`Evidence Anchors`、`Tool Facts` 在多个条目时各只出现一次。已补多个 claim / anchor / tool fact 的 compact 测试。

### 4. [Low] [已修复，待复查] `_check_fidelity` 依赖纯文本子串匹配，与格式化函数之间无编译期约束

**文件**: [dayu/host/_context_compaction.py:494-538](dayu/host/_context_compaction.py#L494-L538)

**问题**: fidelity check 通过构造 `f"source_event_cursor={cursor}"` 模式串并在 combined 文本中做 `in` 匹配。格式化函数（`_format_anchor`、`_format_tool_fact`）使用 f-string 写入 `source_event_cursor={...}`，两者目前一致，但这种一致性完全靠人工保证。如果未来有人修改了格式化函数中的字段名、分隔符或顺序，fidelity check 会静默失败或产生假阳性，没有类型检查或测试能防止这种漂移。

**建议**: 将 checker 模式串和 formatter 格式串提取为共享常量，或至少在同一模块中增加针对格式化输出与 checker 一致性的测试。

**修复说明**: 已提取 `_SOURCE_EVENT_CURSOR_FIELD` 共享常量，formatter 与 `_check_fidelity` 使用同一字段名；新增 compact 多条目测试同时覆盖 `source_event_cursor` 输出与保真通过，降低文本约定漂移风险。

### 5. [Informational] [已修复，待复查] `_run_to_store` 的 overflow 重试循环中，如果 Engine stream 正常结束但 `CONTEXT_COMPACTION_REQUESTED` 之后没有 terminal 事件，仍会尝试 compact

**文件**: [dayu/host/_run_harness.py:393-418](dayu/host/_run_harness.py#L393-L418)

**问题**: 当 `overflow_trigger_seen=True`（由 `CONTEXT_COMPACTION_REQUESTED` 设置）且 inner while 通过 `StopAsyncIteration` 正常结束时，Host 仍会调用 `_compact_or_fail` 尝试 compact。这是合理的兜底行为（Engine 已经明确请求 compact），但该路径不会调用 `_append_overflow_observed`（该函数只在 terminal 路径调用），因此 event log 中缺少 Host 侧的 `CONTEXT_OVERFLOW_OBSERVED` 事实事件。虽然 `CONTEXT_COMPACTION_REQUESTED` 本身的 event 已存储，但两种触发路径产出的可见事件集不完全对称。

**建议**: 确认这是否为预期设计。如果希望事件链路一致，可以在非 terminal compact 触发路径中也写入 `CONTEXT_OVERFLOW_OBSERVED`。

**修复说明**: 已在 `CONTEXT_COMPACTION_REQUESTED` 后 stream 正常结束的兜底 compact 路径追加 Host-owned `context_overflow_observed`，其 `engine_event_type` 指向 `context_compaction_requested`、`engine_error_code=None`、`recoverable=True`。已补 Host 测试确认事件链一致。

### 6. [Informational] [信息记录，不修] `detect_context_overflow` 对 `_parse_json_object` 返回非 dict JSON 值的处理隐含兼容风险

**文件**: [dayu/engine/runners/openai/error_classifier.py:92-117](dayu/engine/runners/openai/error_classifier.py#L92-L117)

**问题**: `_parse_json_object` 在 JSON 解析成功但结果为非 dict（如 list、string）时返回 `None`。此时 `detect_context_overflow` 跳过结构化 code 检查进入 message fallback。如果 future provider 在 context overflow 响应中返回 `{"errors": [{"code": "context_length_exceeded"}]}`（数组包装），结构化检测会漏过，只依赖 message marker fallback。当前 OLD signal matrix 覆盖了常见 provider，但新增 provider 时需要注意这一点。

**建议**: 当前实现对于已知的 provider 矩阵足够，但 `_payload_error_code` 的 docstring 可注明其假设 payload 为 `{"error": {"code": ...}}` 或 `{"code": ...}` 扁平结构。

**修复说明**: 未扩大 provider JSON shape 支持范围；已在 `_parse_json_object` 与 `_payload_error_code` docstring、Engine README 中明确当前只支持顶层 object 与 `{"error":{"code":...}}` / `{"code":...}` 扁平 code，数组包装等 provider-specific shape 不在 P4 范围。

- **`dayu.runtime`**: 本次变更未修改 runtime，runtime 不依赖上层。无违反。
- **反向依赖**: 测试 `test_engine_does_not_import_host_context_compaction` 已验证 Engine 不 import `dayu.host._context_compaction`。
- **类型规范**: 无 `object`、`Any` 使用；所有函数有中文 docstring；新 dataclass 使用 `frozen=True, slots=True`。符合编码硬约束。
- **兼容性代码**: 无兼容性 re-export、wrapper 或 facade。
- **公开 API 边界**: `Host.__init__` 不导出 `ContextCompactCoordinator` 或 `DefaultRunInputBuilder`。符合封装要求。

## 未覆盖项

- Compact 失败后的降级路径（如尝试更激进压缩）未实现——P4 只实现 deterministic compact，失败直接收口为 `RUN_FAILED`。
- Compact 只处理单次 retry（`_CONTEXT_COMPACT_RETRY_LIMIT=1`），多级压缩或指数退避不在 P4 范围内。
- 内部 echo 过滤为基于固定关键词的匹配，不保证覆盖模型改写、翻译或间接引用 Host 内部元数据的场景。
- 没有针对 `detect_context_overflow` 中 `_safe_read_text` 返回空字符串（连接中断等）时的行为测试。
