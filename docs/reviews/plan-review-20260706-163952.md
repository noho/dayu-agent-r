## Findings

### F1-未修复-中-计划未定义第二次 Ctrl+C 计数器复位时机的具体行为契约

- **位置**: Contract / Schema / State-machine / Public-interface Changes 章节；Implementation Decisions #5
- **问题类型**: 契约缺失
- **当前写法**: plan 声称"The idle state must reset after a successful user prompt is submitted or after a clean prompt redisplay, so one old interrupt does not poison later normal input"，但 Risks / Open Questions 又把"first idle Ctrl+C after an empty prompt should reset the 'second Ctrl+C exits' counter immediately after redisplay, or should the second consecutive Ctrl+C exit until the user types input?"留为 open question。
- **反例/失败场景**: Implementation agent 在实现计数器时需要知道：(a) 用户连续按两次 Ctrl+C 之间如果 REPL 成功 redisplay 了 prompt（第一次 Ctrl+C 后 prompt 重新显示），第二次 Ctrl+C 是否应退出？(b) 如果用户在第一次 Ctrl+C 后输入了一行正常文本并成功 submit，后续再按 Ctrl+C 是否从头计数？两种实现路径产生不同的 UX 行为，但 plan 未收敛。
- **为什么有问题**: 计数器复位时机直接决定代码中 `KeyboardInterrupt` catch 后的状态管理逻辑。Implementation agent 面对 open question 会自行猜测，可能产出与用户预期不一致的行为，或在 review 阶段被驳回导致返工。
- **直接证据**: plan 第 119 行 "Second idle Ctrl+C should exit locally with the existing keyboard interrupt exit code"，第 179 行 open question。
- **影响**: 实施 Agent 跑偏 / 生成不符合预期的代码 / review 阶段返工。
- **建议改法和验证点**: 在 plan 的 Implementation Decisions 或 Contract 章节明确：第一次 Ctrl+C 后 prompt redisplay 成功即复位计数器；用户无需输入新文本，只要 REPL 正常回到等待输入状态，下一次 Ctrl+C 又是"第一次"。这符合 Codex / Claude Code 的通用终端 UX：每次 Ctrl+C 是独立的 interrupt-clear 事件，不跨 prompt 累积状态。验证点：连续两次 Ctrl+C 之间无输入 → 第二次应退出；第一次 Ctrl+C → prompt 红色 → 再次 Ctrl+C → 应 clear 而非退出。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F2-未修复-低-plan 未覆盖 prompt_toolkit composer 已有 KeyboardInterrupt 行为对 REPL catch 逻辑的约束

- **位置**: Direct Code Evidence 章节；Implementation Decisions #3
- **问题类型**: 最佳实践偏离
- **当前写法**: plan 提到"Prefer extending the input composer boundary to return a typed interrupt result or raising a CLI-local typed exception over catching broad KeyboardInterrupt at the outer command boundary"，但未分析当前 prompt_toolkit `_clear_or_interrupt` key binding 已经在空 buffer 时通过 `event.app.exit(exception=KeyboardInterrupt)` 抛出 `KeyboardInterrupt`。
- **反例/失败场景**: Implementation agent 可能尝试在 composer 层新增 typed exception 来替代 `KeyboardInterrupt`，但这需要同时修改 prompt_toolkit key binding 的 `exit(exception=...)` 调用和 `_run_interactive_repl` 的 catch 逻辑，增加不必要的改动面。实际上，当前 composer 已经通过 `handle_sigint=False` + key binding 的方式正确产生了 `KeyboardInterrupt`，REPL 层只需 catch 并继续即可。
- **为什么有问题**: plan 的 Implementation Decisions #3 暗示应改 composer 协议，但代码证据显示 composer 行为已经正确：`PromptToolkitInteractiveComposer.read()` 调用 `prompt_async(..., handle_sigint=False)`，Ctrl+C 由 `_clear_or_interrupt` binding 处理，空 buffer 时抛 `KeyboardInterrupt`，非空 buffer 时 reset。实现 agent 可能过度修改 composer 层。
- **直接证据**: `dayu/cli/composer.py:92-96` — `handle_sigint=False`；`dayu/cli/composer.py:117-124` — `_clear_or_interrupt` binding；`tests/cli/test_interactive_composer.py:238-254` — 已有测试覆盖 Ctrl+C 空/非空 buffer 行为。
- **影响**: 实施 Agent 做不必要的 composer 协议修改 / 增加改动面 / 与现有测试冲突。
- **建议改法和验证点**: 在 plan 的 Implementation Decisions #3 中明确：当前 composer 已通过 key binding 正确产出 `KeyboardInterrupt`，不修改 composer 协议或 `InteractiveComposer` 接口。实现只需在 `_run_interactive_repl` 的 `while True` 循环中增加 `except KeyboardInterrupt` catch，配合计数器逻辑继续循环或退出。验证点：composer 测试不需修改。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F3-未修复-低-plan 的验证命令未覆盖第二次 Ctrl+C 退出行为

- **位置**: Tests / Validation Commands 章节
- **问题类型**: 测试缺口
- **当前写法**: Expected assertions 中提到"Same probe or a companion probe records second Ctrl+C exits locally"，但 Validation Commands 的具体命令列表中只列出了 `probe_interactive_ctrl_c.py` 一个 PTY probe 脚本，该脚本当前只验证第一次 Ctrl+C 行为。
- **反例/失败场景**: Implementation agent 修复了第一次 Ctrl+C 后，如果没有验证第二次 Ctrl+C 仍能正常退出，可能引入 regression：例如计数器逻辑错误导致第二次 Ctrl+C 也只 clear 而不退出，用户无法离开 REPL。
- **为什么有问题**: plan 的 expected assertions 提到了 second Ctrl+C 验证，但具体的 validation command 未对应新增或修改 probe 脚本。Implementation agent 可能只修第一次行为、只跑现有 probe、报告通过，而遗漏第二次退出验证。
- **直接证据**: plan 第 159-160 行 expected assertions 和第 151-154 行 validation commands 的不一致。
- **影响**: 验证不完整 / 回归未被捕获。
- **建议改法和验证点**: 在 validation commands 中明确要求 probe 脚本或新增 companion probe 验证：(a) 连续两次 Ctrl+C → 进程退出；(b) 第一次 Ctrl+C → prompt redisplay → 第二次 Ctrl+C → 清空/继续（如果采用 prompt-redisplay 复位策略）。或者在 plan 中要求 implementation agent 扩展现有 probe 脚本以覆盖 second Ctrl+C 场景。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open Questions

1. **Ctrl+C 退出时是否输出诊断信息**: 当前 `main.py:131` catch `KeyboardInterrupt` 后直接返回 `EXIT_KEYBOARD_INTERRUPT`，无任何 stdout 输出。修复后第一次 Ctrl+C 应该 clear 并 redisplay prompt（无额外输出），第二次 Ctrl+C 退出时是否应输出类似 `^C` 的换行？这属于 UX 细节，不阻塞实现，但 plan 未提及。
2. **`_run_interactive_repl` 中 `KeyboardInterrupt` catch 的位置**: 是在 `await effective_composer.read(...)` 调用处 catch，还是在 `while True` 外层 catch？前者更精确但需要区分 composer 抛出的 `KeyboardInterrupt` 和其它来源；后者更简单但可能 catch 到非预期的 `KeyboardInterrupt`。Implementation agent 需要自行判断，plan 未指定。

## Final Conclusion

**pass-with-risks**

Plan 的 root cause 分析正确、分层判断合理、scope 收敛、验证矩阵覆盖核心路径。三个 findings 均非 blocking：F1 是中等严重度的契约缺口，可通过在 plan 中补一句复位规则消除；F2 和 F3 是低严重度的最佳实践和测试覆盖问题，implementation agent 可自行处理。

Plan 可以交给 implementation agent，但建议 controller 在 dispatch 前要求 AgentCodex 在 plan 中补充 F1 的复位行为契约（prompt redisplay 即复位），以消除 implementation agent 的猜测空间。

Blocking finding IDs: 无。
