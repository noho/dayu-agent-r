## Findings

### F01-unfixed-MEDIUM-Playwright cleanup reuse vs mirror is an unresolved design decision

- **位置**: S2 Exact changes, "Update Web Playwright worker cleanup to reuse the same minimal runtime abstraction or mirror the same typed process-group helper, not ad hoc raw constants."
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan uses "reuse ... or mirror" as a disjunction, leaving the implementation agent to decide between two architecturally different paths.
- **反例/失败场景**: If the agent chooses "mirror," Playwright gets its own process-group cleanup implementation separate from `InterruptibleProcessHandle`. Future changes to runtime process-group semantics would need to be synchronized across two code paths. If the agent chooses "reuse," Playwright's raw `multiprocessing.get_context("spawn")` in `_run_playwright_worker_process` must be replaced with `InterruptibleProcessHandle`, which is a larger refactor than the plan implies.
- **为什么有问题**: `dayu/tools/web/web_playwright_backend.py:480-511` shows `_run_playwright_worker_process` creates raw `multiprocessing.Process` directly, not via `InterruptibleProcessHandle`. The plan doesn't explicitly require migrating Playwright to `InterruptibleProcessHandle`, and "mirror" creates maintenance divergence.
- **直接证据**: `web_playwright_backend.py:504-511` creates `ctx.Process(target=_playwright_process_entry, ...)` directly. `interruptible_process.py:131` creates `self._context.Process(target=_run_process_target, ...)` inside `InterruptibleProcessHandle`. These are two independent process creation paths.
- **影响**: Implementation agent may either (a) duplicate process-group cleanup logic in Playwright, creating a maintenance burden, or (b) do a larger refactor to make Playwright use `InterruptibleProcessHandle`, exceeding expected S2 scope.
- **建议改法和验证点**: Resolve the "or" into a single directive. If the intent is "reuse," explicitly state that Playwright must migrate to `InterruptibleProcessHandle` (or a shared process-group helper callable from both). If the intent is "mirror," state that the helper must be extracted to a shared utility callable from both `InterruptibleProcessHandle` and Playwright's raw process path. Either way, the helper should live in `dayu.runtime.interruptible_process` as a module-level function, not embedded in the class.
- **修复风险（低/中/高）**: 中
- **严重程度（中）**: 不阻塞 plan 接受，但需要明确方向后 implementation agent 才能安全执行。

### F02-unfixed-LOW-Grace policy defaults defer tuning to implementation without guidance

- **位置**: S1 Contract / Schema / Runtime Policy Decisions #3, "Defaults should preserve current behavior unless tests prove a larger value is required: 0.2 / 0.2 as named defaults are acceptable."
- **问题类型**: 非最优方案
- **当前写法**: Plan accepts 0.2/0.2 as defaults and defers tuning to "unless tests prove a larger value is required."
- **反例/失败场景**: Playwright browser processes may need more than 0.2s to clean up after SIGTERM before escalating to SIGKILL. If the default is too aggressive, Playwright cleanup smoke may fail intermittently, and the implementation agent would need to iterate on the default value without clear guidance on what "larger value is required" means.
- **为什么有问题**: The reopen decision explicitly requires "process capsule grace tuning" as a must-fix item, not just "make the constants typed." The plan's wording "preserve current behavior unless tests prove otherwise" effectively punts the tuning decision to implementation, where the agent would need to discover the right value empirically. This is acceptable if the plan provides guidance on how to discover the value (e.g., "measure Playwright SIGTERM-to-exit time on the test environment and set grace to 2x that").
- **直接证据**: Reopen decision: "Process capsule grace tuning: Must be fixed in WU-TOOLS-CANCEL-01; avoid raw hard-coded constants, use typed runtime policy/config with defaults and validation." Current `_PROCESS_CAPSULE_TERMINATE_GRACE_SECONDS = 0.2` and `_PROCESS_CAPSULE_KILL_GRACE_SECONDS = 0.2` in `tool_runtime.py:325-326`.
- **影响**: Low risk of implementation iteration; the typed policy structure is correct, but the "tuning" aspect may be under-delivered.
- **建议改法和验证点**: Add a sentence: "S2 Playwright cleanup smoke should measure actual SIGTERM-to-exit time for the nested child and use that to validate or adjust the default grace values. If 0.2s proves insufficient for Playwright, adjust the named default upward."
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 不阻塞 plan 接受。

### F03-unfixed-LOW-`_validate_grace_seconds` doesn't validate NaN/infinity

- **位置**: S1 Contract / Schema / Runtime Policy Decisions #3, "Validation: each field must be finite non-negative numeric, not bool. Negative, nan, and infinite values fail fast."
- **问题类型**: 测试缺口
- **当前写法**: Plan requires NaN/infinity validation for grace policy fields.
- **反例/失败场景**: Current `interruptible_process.py:319-328` only checks `grace_seconds < 0`. If someone passes `float('nan')`, `nan < 0` is `False`, so it passes validation. `float('inf')` also passes. The plan's validation requirement is correct, but the existing code doesn't satisfy it.
- **为什么有问题**: This is a known gap in the existing code, not a plan defect per se. But the plan's S1 tests must explicitly cover NaN/infinity rejection to close this gap. The plan says "Host tooling/options tests cover default policy and invalid values" but doesn't specifically mention NaN/infinity.
- **直接证据**: `interruptible_process.py:327-328`: `if grace_seconds < 0: raise ValueError(...)`. `math.nan < 0` evaluates to `False`. `math.inf < 0` evaluates to `False`.
- **影响**: If the implementation agent doesn't add NaN/infinity checks, the typed policy accepts invalid values.
- **建议改法和验证点**: In S1 Tests, add: "Policy field tests explicitly cover `float('nan')`, `float('inf')`, `float('-inf')`, `bool`, and negative values as rejection cases."
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: Implementation detail; the plan's validation requirement is stated, just needs explicit test enumeration.

### F04-unfixed-LOW-`os.setsid` race window is acknowledged but not designed around

- **位置**: S2 Exact changes, "POSIX behavior: child enters a new process group/session before running the target; terminate/kill sends signal to the process group and then joins the root process."
- **问题类型**: 并发恢复风险
- **当前写法**: Plan describes the desired behavior but doesn't address the race between parent signaling and child calling `os.setsid()`.
- **反例/失败场景**: If the parent sends SIGTERM/SIGKILL before the child calls `os.setsid()`, the child is still in the parent's process group. `os.killpg(parent_pgid, signal.SIGTERM)` would kill the parent itself. The plan should specify: (a) signal the child PID directly first, (b) only switch to process-group signaling after verifying the child has a different pgid, or (c) accept the race window with documented OS-specific behavior.
- **为什么有问题**: `multiprocessing.Process.start()` uses `spawn` context, which forks then execs. Between fork and the child calling `os.setsid()`, the child is in the parent's process group. The window is small (microseconds) but real.
- **直接证据**: `interruptible_process.py:126`: `self._context = multiprocessing.get_context("spawn")`. `web_playwright_backend.py:504`: `ctx = multiprocessing.get_context("spawn")`. Both use spawn context.
- **影响**: In theory, a very unlucky timing could cause the parent to kill itself when trying to clean up the child. In practice, the window is extremely small with spawn context.
- **建议改法和验证点**: S2 should specify the signaling strategy: "Signal the child's PID directly for the initial terminate/kill attempt. If the child has a different pgid (confirmed via `os.getpgid(child_pid)`), also send the signal to the child's process group. Document that if the child hasn't called `os.setsid()` yet, nested children may not be cleaned up."
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: Edge case with very small window; documenting the limitation is sufficient.

### F05-unfixed-LOW-S2 scope could be tightened by splitting Playwright smoke to S3

- **位置**: S2 Objective, "prove cancellation robustness for nested subprocesses, especially Playwright, without optimizing cold start."
- **问题类型**: 切片过粗
- **当前写法**: S2 combines runtime process-group cleanup (new OS-level abstraction) with Playwright cleanup smoke (tool-specific test using a fake picklable worker). These have different failure modes: runtime process-group may hit OS-specific limits, while Playwright smoke depends on the runtime abstraction working correctly.
- **反例/失败场景**: If the runtime process-group cleanup hits an OS-specific blocker (e.g., macOS `os.setsid` behavior differs from Linux), S2's Playwright smoke becomes untestable, blocking the entire slice. Separating them would allow the runtime abstraction to be validated independently.
- **为什么有问题**: The plan's own "Why This Is Not Over-Designed" section says "S2 may hit OS-specific limits and should not block S1 contract cleanup." By the same logic, Playwright smoke should not block runtime process-group validation.
- **直接证据**: S2 allowed files include both `dayu/runtime/interruptible_process.py` (runtime abstraction) and `dayu/tools/web/web_playwright_backend.py` (tool-specific cleanup). These are different layers with different failure modes.
- **影响**: If S2 hits an OS-specific blocker, the entire slice (including Playwright smoke) is blocked. Splitting would allow S2 to complete runtime abstraction and S3 to include Playwright smoke alongside tool migration.
- **建议改法和验证点**: Consider moving Playwright cleanup smoke to S3 ("Tool Migration And Fins AAPL XBRL Fixture Breadth"), since S3 already touches `dayu/tools/web/web_tools.py` and `tests/tools/web/test_web_tools_provider.py`. This keeps S2 focused on runtime process-group abstraction.
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: Not a blocker; the current S2 scope is manageable, just slightly broader than necessary.

## Architecture Boundary Review

The process envelope contract in `dayu.contracts.tool_execution` is the correct placement. `dayu.contracts` is imported by both Host and tools without reverse dependency. The plan correctly states:

- Host may parse the contract (via `dayu.host.tool_runtime`).
- Tools may construct it (via `dayu.tools.doc_tools`, `dayu.fins.tools.fins_tools`, `dayu.tools.web.web_tools`).
- Neither side imports concrete tool packages or Host internals.
- `dayu.runtime` remains layer-neutral and may provide generic process-group primitives.

**Verification**: `dayu/contracts/tool_execution.py` currently has no process envelope helpers. `dayu/host/tool_runtime.py:250-256` defines private `_PROCESS_ENVELOPE_*` constants. `dayu/tools/doc_tools.py:77-82`, `dayu/fins/tools/fins_tools.py:79-84`, `dayu/tools/web/web_tools.py:164-169` each define their own copies. The plan correctly moves these to `dayu.contracts`.

**Layering check**: `dayu.runtime.interruptible_process` can add process-group cleanup without importing Host/Engine/Service/UI/Fins, because it only needs `os` and `signal` from stdlib. ✓

**AGENTS.md check**: The plan proposes no `Any`, `object`, or untyped signatures. `ProcessCapsuleInterruptPolicy` would be a typed dataclass. No reverse dependency is proposed. ✓

## Best-Practice Review

The plan follows project conventions:

- Typed config policy (consistent with `DuplicateGovernancePolicy`, `FrameworkToolPolicyView`)
- Config validation in `dayu.runtime.config_loader` (consistent with existing config parsing)

## Optimal-Solution Review

The plan's approach of adding process-group cleanup at the `dayu.runtime` level is the most practical path. Alternatives considered:
- **Host-level process-tree cleanup**: Would violate layering (Host shouldn't know about OS process semantics).
- **Tool-level cleanup**: Would duplicate logic across Doc/Fins/Web tools.
- **No process-group cleanup**: Would not prove cancellation robustness for Playwright nested subprocesses.

The runtime-level approach is the best balance of correctness and minimal coupling.

## Overengineering Review

The plan is appropriately scoped. It adds only two shared contracts (process envelope, process cleanup policy) that are already implicitly present in multiple places. No registry, generalized job supervisor, new Host state machine, or durable schema is introduced. Four slices are justified by different failure modes and dependency ordering.

## Overcoupling Review

The plan avoids overcoupling:
- S1 (contract/policy) is independent of S2 (runtime process-group).
- S3 (tool migration) depends on S1 but not on S2.
- S4 (docs/validation) depends on all prior slices but adds no coupling.

The only coupling concern is S2 combining runtime process-group with Playwright smoke (see F05).

## Open Questions

None. All user-upgraded must-fix items are addressed by the plan.

## Residual Risks

1. **AAPL XBRL fixture network dependency**: The plan has a stop condition for this, but it's a real risk during implementation. If XBRL taxonomy resolution requires network access, the fixture test may need to be restructured or deferred.
2. **Windows process-group cleanup**: The plan correctly marks Windows as unsupported/fallback. This is acceptable for the current platform target (macOS/Linux).
3. **Playwright live browser cleanup**: The plan correctly defers this to environment-dependent testing, using a deterministic fake worker for the smoke test.

## Plan Review Conclusion

**Verdict: PASS**

The plan is code-generation-ready and addresses all five user-upgraded must-fix items. The findings are low-to-medium severity and can be resolved by the implementation agent with minimal plan revision. No blocking issues were identified.

The plan correctly:
- Places the process envelope contract in `dayu.contracts` without reverse dependency
- Separates `tool_execution_timeout_seconds` (business deadline) from grace policy (cleanup policy)
- Uses typed `ProcessCapsuleInterruptPolicy` with validation
