## Adversarial Pass: Targeted Checks

### 1. Provider ID / Client ID / Per-event Identity 严格分离

**结论：PASS。** `_vendor_group_key()`（行 1250–1262）的三级优先分组使用 provider → client → event，不涉及 run/attempt/iteration/time/order。每一级 fallback 仅在前一级不可用时触发：

- `provider_request_id is not None` → key `("provider", id)` — 只按 provider-native id 归组
- `client_correlation_id is not None` → key `("client", id)` — 只按 typed client id 归组
- 否则 → key `("event", f"{source_path}\0{event_id}")` — 每 event 独立

`_vendor_conflict_fields()`（行 1265–1299）在同 provider group 内独立检查 client、session、run、attempt、execution、iteration 各维度是否冲突。冲突不静默合并，而是通过 `_vendor_conflict_finding()`（行 1302–1338）产生 `engine.vendor_correlation_conflict` ERROR finding。

## Residual Risk

1. **`run_id=None` 的 trigger record 分组跳过路径未经独立测试**：`_engine_vendor_results()` 行 1073–1081 对 `record.run_id is None` 的 trigger record 添加 `vendor_run_id_unavailable` limitation 并跳过分组。现有测试中所有 trigger record 均使用默认 `run_id="run-1"`。此路径的正确性由代码静态分析确认（`_record_limitation` 正确构造 limitation + `continue` 跳过 `_vendor_group_key`），但缺少独立测试覆盖。风险低——触发条件清晰（cold record 缺少 run_id），且此 limitation 的语义是"无法构造冻结 block identity"，行为正确。

2. **`_vendor_partial_signal_status` 中 `signals` 元组迭代范围与 `protocol_records` 不一致**：`signals`（行 1528–1538）从 `records`（全 group 的 trigger records）收集 `partial_tool_call_signal`，而 `LIMITED_SIGNAL` 判定仅基于 `protocol_records`（行 1539–1543）。按 producer contract，只有 `PROVIDER_PROTOCOL_ERROR` 记录应携带 `partial_tool_call_signal`，其他 event type 不会产生此字段，因此此不一致不产生实际行为差异。风险极低——即使未来 producer 意外在非 protocol record 中包含此 signal，`LIMITED_SIGNAL` 判定仍正确（仅受 protocol_records 驱动）。

3. **`_vendor_conflict_fields` 中 None 值不计入冲突**：`_sorted_values()` 过滤 None 后去重。若 group 中一条 record 的 `attempt_id=None`、另一条为 `"attempt-1"`，去重后 `len=1` 不视为冲突。设计上 None="未知"不与已知值冲突——这对 limitation 系统（已有 `vendor_attempt_id_unavailable` 覆盖缺失情况）是一致的。风险低——不会静默丢失真实冲突，因为两条 record 都有显式且不同的 attempt_id 时仍会被检测。
