## 3. Findings

### 1-未修复-低-P0-B 合成向量构造规格欠精确：合法性前置门槛对混合引用图覆盖不明，②绝对 linkbaseRef 宿主文档未指定
- **位置**: 计划 §5 P0-B「另做两个**相互独立**的自包含合成向量：① instance 的绝对 `schemaRef`…② 绝对 `linkbaseRef`…。每个向量分别以 Arelle 离线加载 package、`--validate --validationExitCode` exit 0 且无验证错误确认合法性，之后分别做 Docling Path/Stream 对照」及其前句混合引用图描述。
- **问题类型**: 不可直接实施 / 测试缺口（规格歧义导致误归因风险）。
- **当前写法**: 「每个向量」的 Arelle 合法性先行门槛在句法上只紧跟①②两个「向量」；AAPL 同构混合引用图（goal 3 主路径形态）被称为「混合引用图」，是否同样先过合法性门槛再进 Docling 未明写。②只写「绝对 `linkbaseRef` → catalog 映射的包内 linkbase」，未指定 linkbaseRef 的宿主文档；而 XBRL 2.1 只允许 `link:linkbaseRef` 位于 schema 的 `xs:annotation/xs:appinfo`（Arelle `ModelDocument.py:1020-1023` 对违规位置报 `xbrl.5.1.2.linkbaseRefLocation`），AAPL fixture 也正是把 linkbaseRef 放在 schema appinfo（实读 `aapl-20240928.xsd:19-22`）。
- **反例/失败场景**: 实施者构造的混合引用图有细微非法处（例如 package metadata 不合 TPE），未先过 Arelle 合法性就跑 Docling，Docling 失败被记为「组合布局不可达」——正是 PR2-F1 揭露、本计划自己禁止的「接口/样本缺陷误归因」模式重演；或实施者把②的绝对 linkbaseRef 放进 instance，Arelle 先报 `xbrl.5.1.2` 拒绝，合法性门槛失败，白烧一轮探针并可能把「向量不可达」写进结论。
- **为什么有问题**: 混合引用图是 goal 3 主路径（真实财报相对入口形态）的唯一机制证据载体，其证据链必须与①②同强度防误归因；「若合法性未通过，先修合成样本」总规则虽可事后自纠，但不能替代「门槛先于 Docling 对照」的显式顺序约定，且②宿主留白与本计划「引用解析分工须覆盖全部形状」的自我要求不一致。
- **直接证据**: 计划 §5 P0-B 原文（「另做两个相互独立的…向量…每个向量分别以 Arelle 离线加载 package…」）；`ModelDocument.py:1020-1023` linkbaseRef 位置约束；`aapl-20240928.xsd:19-22` linkbaseRef 实际宿主；probe P2 的 Arelle 合法性先行做法（先 `--validate --validationExitCode` exit 0 再进 Docling）本身即正确范式。
- **影响**: 误归因污染 goal 3 证据链 / 探针循环浪费 / 组合布局可达性结论不可信。
- **建议改法和验证点**: ① 把门槛句改为「**每个合成输入（含混合引用图与①②）**均先以 Arelle 离线加载 package、`--validate --validationExitCode` exit 0 且无验证错误确认合法性，之后才做 Docling Path/Stream 对照」；② 明写②的绝对 linkbaseRef 位于包内（或同根）XSD 的 `xs:annotation/xs:appinfo`，与 AAPL 宿主形态一致，不放 instance。验证点：P0-B 产物对三个输入各自留 Arelle 合法性原始输出在前、Docling 对照在后的时间序证据。
- **修复风险（低/中/高）**: 低（文本定约，不改产品）。
- **严重程度（低/中/高/严重）**: 低。

**pass-with-risks**。
