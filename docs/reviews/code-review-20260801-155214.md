## Findings

### 1-未修复-低-`session resume` help 仍显示 `--config` 但运行时会拒绝

- **入口/函数**: `parse_cli_args()` → `_reject_disallowed_explicit_config()`
- **文件(行号)**: `dayu/cli/arg_parsing.py:289-313`（拒绝逻辑）、`dayu/cli/arg_parsing.py:775-811`（`_register_session_resume_action` 使用 `action_runtime_parent` 作为 `global_parent`）
- **输入场景**: 用户在 `session resume --help` 中看到 `--config`，尝试使用 `session resume --config X --mode interactive` 或 `session resume --config X --mode prompt hello`
- **实际分支**: argparse 在命令和 action 两个层级都接受 `--config`（因为 `session` 命令使用 `command_runtime_parent`，`resume` action 使用 `action_runtime_parent`，两者都含 `--config`）；`parse_cli_args()` 中 `_reject_disallowed_explicit_config()` 在解析后检查 `command_name == COMMAND_SESSION and session_action == SESSION_ACTION_RESUME` 并调用 `parser.error()` 退出
- **预期行为**: help 文本不应显示已被拒绝的参数；或至少 help 应标注该参数在特定 mode 下不可用
- **实际行为**: argparse 的 parents 继承机制使 help 自动包含所有父解析器参数，`--config` 出现在 resume help 中但运行时被拒绝；用户看到 help 与行为不一致
- **直接证据**:
  - `arg_parsing.py:258-262`：`_register_session_command` 接收 `command_parent=command_runtime_parent`、`action_parent=action_runtime_parent`
  - `arg_parsing.py:528-535`：`_build_runtime_arguments_parent()` 注册 `--config` 参数
  - `arg_parsing.py:307-313`：`_reject_disallowed_explicit_config()` 对 `session resume` 执行显式拒绝
  - `test_session_action_help_contains_fixed_parser_shape`（`tests/cli/test_arg_parsing.py:607+`）**未**断言 help 中不含 `--config`
- **影响**: 用户困惑——help 说可用，命令却说不可用；但不会被静默忽略，错误消息清晰（"session resume 命令不接受 --config"）
- **建议改法和验证点**: accepted plan §5.2 F01 已显式选择 "fail closed at validation level" 而非 "remove from parser surface"，这是有意的设计权衡。若要修复，可在 session resume action parser 注册后显式移除 `--config`（需 argparse conflict handler），或为 session resume 提供一个不含 `--config` 的专用 parent。但这会触及 S2-S5 的 parser 重构范围，当前阶段不建议实施。Plan 将 parser help 的一致性留到 S6 统一处理。
- **修复风险（低）**: 若在 S1 中修改 parent parser 继承链，可能影响 session list/purge 的 config 正向行为
- **严重程度（低）**: 不影响正确性、安全性或数据完整性；只是 UX 不一致

### 2-未修复-低-`session resume` help 显示 `--ticker` 但 interactive mode 会拒绝

- **入口/函数**: `_run_session_resume()` → `_reject_interactive_resume_ticker()`
- **文件(行号)**: `dayu/cli/arg_parsing.py:796`（`--ticker` 注册在 resume action parser）、`dayu/cli/commands/session.py:567-578`（拒绝逻辑）
- **输入场景**: 用户查看 `session resume --help`，看到 `--ticker` 参数，尝试 `session resume --mode interactive --ticker AAPL`
- **实际分支**: argparse 在 resume action parser 级别接受 `--ticker` 并赋值给 `args.ticker`；`_run_session_resume()` 在 interactive 分支调用 `_reject_interactive_resume_ticker(args)` ，`args.ticker is not None` 时抛 `CliSessionUsageError`
- **预期行为**: interactive mode 的 help 不应显示 `--ticker`，或至少标注限制
- **实际行为**: `--ticker` 在 resume help 中显示为通用参数，但 interactive mode 下会拒绝，错误消息 "session resume --mode interactive does not accept --ticker"
- **直接证据**:
  - `arg_parsing.py:796`：`parser.add_argument("--ticker", ...)` 在 `_register_session_resume_action` 中
  - `session.py:567-578`：`_reject_interactive_resume_ticker()` 拒绝非 None ticker
  - `session.py:287-288`：interactive 分支在 runtime prepare 前调用拒绝函数
  - `test_session_resume_interactive_rejects_ticker_before_runtime_prepare`（`tests/cli/test_session_command.py:1284+`）验证拒绝行为
- **影响**: 与 Finding 1 同类的 UX 不一致；用户得到清晰错误，不会被静默忽略
- **建议改法和验证点**: 移除 resume action parser 级别的 `--ticker` 注册，改为只在需要它的 mode 中做独立的参数转发。但这需要将 mode 选择从 action 参数提升为子命令，超出 S1 scope。当前实现是 accepted plan 的精确翻译（plan §5.2 F02 item 5）
- **修复风险（低）**: parser 重构风险
- **严重程度（低）**: 不影响正确性
