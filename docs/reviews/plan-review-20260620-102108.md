## Findings

### 001-unfixed-medium-Fallback pressure injection mechanism underspecified

- **位置**: Implementation Decisions item 3 (Fallback suite), Small Slices S3
- **问题类型**: 不可直接实施
- **当前写法**: "Target run crosses the proactive compact threshold using bounded deterministic pressure." "Trigger proactive compact in the target run using bounded deterministic pressure, not real provider overflow."
- **反例/失败场景**: Implementation agent doesn't know what "bounded deterministic pressure" means concretely. The existing fallback test (`test_public_compact_failure_dispatches_deterministic_recent_window`) uses a long prompt string (`_soft_threshold_prompt()` + marker text) to cross the proactive threshold. If the implementation agent uses a different mechanism (e.g., a pressure helper from the smoke script), it may not actually trigger proactive compact, or may trigger it in a way that doesn't match the existing test's proven approach.
- **为什么有问题**: The smoke script has a `PressureMode.AUTO` that uses `_user_pressure_text` to inject padding into prompts, but this is designed for the existing `memory-compact` suite which uses real provider calls. The deterministic fallback suite uses custom worker factories (not real providers), so the pressure mechanism needs to work differently — it needs to make Host's proactive compact threshold estimator believe the input is large enough, not actually send large text to a provider. The plan doesn't clarify this distinction.
- **直接证据**: `test_public_compact_failure_dispatches_deterministic_recent_window` at line 696 uses `_soft_threshold_prompt()` (a long prompt) + `_fake_compact_open_options` with `max_compaction_attempts_per_operation`; the smoke script's `_user_pressure_text` at `PressureMode.AUTO` generates padding for real-provider flows.
- **影响**: Implementation agent may implement a pressure mechanism that doesn't actually trigger proactive compact in the deterministic path, causing the fallback suite to silently skip coverage.
- **建议改法和验证点**: Specify that the fallback suite should reuse the `_soft_threshold_prompt()` pattern from `test_public_compact_smoke.py`, or explicitly state that the long prompt in `RoundSpec.prompt` is the pressure mechanism. Add a completion signal that proves proactive compact was actually triggered (e.g., `audit.requested_proactive >= 1`).
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 002-unfixed-medium-Reactive suite execution model diverges from existing smoke pattern without explicit bridge

- **位置**: Implementation Decisions item 3 (Reactive suite), Small Slices S2
- **问题类型**: 不可直接实施
- **当前写法**: "Add smoke-local final/recovery worker helpers modeled on `tests/host/test_public_compact_smoke.py`." "Capture ordinary `AgentRunRequest`s and dispatch snapshots in a smoke observation object."
- **反例/失败场景**: The existing smoke execution path (`_execute_memory_core_rounds` / `_execute_memory_compact_rounds`) uses the default worker factory (real provider calls) through `submit_followup -> watch -> get_session`. The reactive suite requires a custom worker factory that emits `context_compaction_requested` on first dispatch — this is a fundamentally different execution model. The plan doesn't specify how to wire the custom worker factory into the smoke script's `_execute_*` flow. The smoke script's `open_host` call currently uses `open_host_options(...)` which doesn't accept a custom `worker_factory`.
- **为什么有问题**: The smoke script's execution path goes through `open_host -> ensure_session -> submit_followup -> watch -> get_session`, and the Host internally dispatches to the default worker. To use a custom reactive worker, the smoke would need to pass a `worker_factory` parameter to `open_host_options`. The plan references `_fake_compact_open_options` from the test file, but this helper is defined in `tests/host/test_public_compact_smoke.py`, not in the smoke script. The plan should specify whether to import it, create a smoke-local equivalent, or use a different mechanism.
- **直接证据**: `_fake_compact_open_options` at `test_public_compact_smoke.py:1087` constructs `OpenHostOptions` with a custom `worker_factory`; the smoke script's `open_host_options` at `smoke_host_public_conversation_memory_scenarios.py` does not expose a `worker_factory` parameter; `_round_specs_for_suite` at line 1493 raises `ValueError` for unknown suites.
- **影响**: Implementation agent may not know how to integrate the custom worker factory into the smoke execution flow, leading to either a non-functional reactive suite or a design that doesn't exercise the public Host path.
- **建议改法和验证点**: Specify that the reactive/fallback suites need a new execution path (e.g., `_execute_reactive_compact_rounds` / `_execute_fallback_rounds`) that constructs `OpenHostOptions` with a custom `worker_factory` and deterministic compactor stub. State explicitly whether to import `_fake_compact_open_options` / `FakeCompactorRunAgent` from the test file or create smoke-local equivalents. Add the new execution paths to `_round_specs_for_suite` or an equivalent dispatch.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 003-unfixed-medium-Fallback input window assertion requires infrastructure gap

- **位置**: Implementation Decisions item 6 (Fallback suite assertions), Success Signal
- **问题类型**: 契约缺失
- **当前写法**: "`fallback_input_window` exists and has selected/dropped/current refs" and "final worker request contains selected recent marker and current input marker; final worker request does not contain dropped old marker"
- **反例/失败场景**: The current `CompactFailedOperationAudit` dataclass (smoke script line ~663) does not include a `fallback_input_window` field. The `CONTEXT_COMPACTION_FAILED` EventLog payload does contain `fallback_input_window` as a `Mapping`, but the smoke audit report infrastructure doesn't extract it. The implementation agent would need to either extend `CompactFailedOperationAudit` or add a new extraction path. If neither is done, the assertion cannot be implemented.
- **为什么有问题**: The plan lists `fallback_input_window` inspection as a required assertion, but the current smoke infrastructure only extracts `fallback_action`, `fallback_policy_decision`, `fallback_tier`, and `attempt_count` from the failed operation payload. The `fallback_input_window` is a nested `Mapping` with `selected_block_ids`, `dropped_block_ids`, `current_input_ref` — extracting and asserting on this requires extending the audit infrastructure or reading the EventLog payload directly.
- **直接证据**: `CompactFailedOperationAudit` at smoke script line ~663 has `fallback_action`, `fallback_policy_decision`, `fallback_tier` but no `fallback_input_window`; `CONTEXT_COMPACTION_FAILED` payload in `dayu/host/context_events.py:377` includes `fallback_input_window` as `Mapping[str, JsonValue] | None`; `tests/host/test_dispatch_scheduler.py:5304` accesses `payload["fallback_input_window"]` directly.
- **影响**: Implementation agent may discover mid-implementation that the assertion requires infrastructure changes not accounted for in the plan, causing scope drift or incomplete coverage.
- **建议改法和验证点**: Specify that `CompactFailedOperationAudit` needs a `fallback_input_window: Mapping[str, JsonValue] | None` field, and that `_compact_failed_operation_audit` needs to extract it from the payload. Alternatively, specify that the fallback acceptance helper reads the EventLog payload directly. The plan should also specify the exact shape expected for `fallback_input_window` assertions (e.g., `selected_block_ids` is a non-empty list, `dropped_block_ids` is a list, `current_input_ref` is a non-empty string).
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 004-unfixed-low-Reactive helper test synthetic data shape unspecified

- **位置**: Small Slices S1 "Add pure tests for reactive and fallback acceptance helpers using synthetic EventLog rows"
- **问题类型**: 不可直接实施
- **当前写法**: "Add pure tests for reactive and fallback acceptance helpers using synthetic EventLog rows."
- **反例/失败场景**: The existing test `test_compact_acceptance_requires_event_log_audit_summary` constructs `CompactAuditSummary` directly with numeric fields. But the new reactive/fallback acceptance helpers would need to inspect more than just counts — they'd need `CompactFailedOperationAudit` with `fallback_action`, `fallback_input_window`, etc. The plan doesn't specify what synthetic data shape to use for these tests.
- **为什么有问题**: The implementation agent needs to know whether to construct synthetic `CompactAuditSummary` (already possible) or synthetic `CompactAuditReport` with `CompactFailedOperationAudit` entries (requires understanding the dataclass construction). The plan should specify the minimal synthetic data needed.
- **直接证据**: `test_compact_acceptance_requires_event_log_audit_summary` at assembly test line 368 constructs `CompactAuditSummary(requested_proactive=1, ...)` directly; `CompactFailedOperationAudit` at smoke script line ~663 has many fields.
- **影响**: Minor — implementation agent can figure this out from the existing test patterns, but explicit specification reduces ambiguity.
- **建议改法和验证点**: Specify that reactive helper tests construct `CompactAuditSummary` with `requested_reactive >= 1`, `compacted_reactive >= 1`, `failed_reactive == 0`. Specify that fallback helper tests construct `CompactAuditReport` with a `CompactFailedOperationAudit` entry having `fallback_action="dispatch"`, `fallback_input_window` with required fields, and no `CONTEXT_COMPACTED` for the same operation.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open Questions

None blocking for plan gate. The findings above are actionable refinements that improve code-generation readiness without requiring architectural changes.

## Residual Risks

1. **Monkeypatching `dayu.host.llm_compaction._run_agent_request` in `utils/`**: The plan acknowledges this risk explicitly and provides a stop condition. The existing test infrastructure already does this, so the pattern is proven. But the smoke utility is a standalone script, not a pytest test — runtime monkeypatching in a standalone script is less conventional. Destination: plan's existing stop condition covers this.

2. **Smoke command requires placeholder API key**: The plan notes `DEEPSEEK_API_KEY=test-provider-key` even though no real provider call should occur. This is because the Host assembly may require an API key for runtime initialization. Destination: plan's existing risk section covers this.

3. **Memory policy cap sensitivity**: The fallback smoke may be sensitive to configured memory policy caps. The plan notes this and suggests deterministic bounds. Destination: plan's existing risk section covers this.

## Conclusion

**pass-with-risks**

The plan is directionally correct and well-scoped. The design alignment is sound — reactive compact and fallback are already-designed, already-tested Host paths, and adding public smoke coverage is a bounded test-hardening task. The plan correctly preserves `memory-compact` proactive acceptance and avoids Host/Engine/durable schema changes.

The three medium findings (001-003) are all in the "不可直接实施" / "契约缺失" category — they identify specific gaps where an implementation agent would need to make design decisions that the plan should pre-authorize. All three have low fix risk and can be addressed by adding 1-2 sentences of specification to the plan. The low finding (004) is a minor clarity improvement.

No blocker findings. No architecture boundary violations detected. The plan's non-goals and stop conditions are well-defined.
