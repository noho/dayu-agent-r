## 1. Finding Summary

**DS Finding 01**: `_abandon_cancelled_wait` 中 `adapter.abandon_wait()` 成功后 lifecycle gate 关闭导致 durable `poll_abandoned_at` 标记被跳过，造成 double-abandon。

原始问题：第 921 行 post-abandon gate check 在 `adapter.abandon_wait()` 成功返回后检查 `self._lifecycle_gate.is_closed()`，若为 True 则跳过 `_MarkWaitRecordAbandonedOperation`，以 `SHUTDOWN_SKIPPED` 释放 claim。外部 abandon 已完成但 durable mark 未写入，下轮 poller 会重新 claim 并再次调用 `abandon_wait()`。

## 2. Fix Analysis

### 2.1 Code Change

`dayu/host/wait_adapter.py` — `_abandon_cancelled_wait` 方法：

```diff
-        if self._lifecycle_gate.is_closed():
-            return 0, 0, self._release_shutdown_skipped(record, claim_id), 1
         now = format_utc_timestamp(self._clock.now())
```

**删除了 `adapter.abandon_wait()` 成功后的 lifecycle gate 检查**（原第 921-922 行）。

### 2.2 Preserved Invariants

| Invariant | Status | Evidence |
|---|---|---|
| Pre-adapter gate check 仍存在 | ✅ | 第 877 行 `if self._lifecycle_gate.is_closed():` 在 `adapter.abandon_wait()` 调用前执行，shutdown 在任何外部副作用发生前仍正确释放为 `SHUTDOWN_SKIPPED` |
| Adapter 调用在 Host transaction 外 | ✅ | 第 900 行 `adapter.abandon_wait(record)` 在 `run_write` 之外执行 |

### 2.3 Control Flow After Fix

修复后的 `_abandon_cancelled_wait` 执行路径：

1. **Gate check (pre-adapter)**: 第 877 行 — 若 gate 已关闭，直接 `SHUTDOWN_SKIPPED` 释放，不调用 adapter ✅
2. **Adapter resolve**: 第 879 行 — 查找 adapter；未找到则 `MISSING_ADAPTER` backoff 释放 ✅
3. **adapter.abandon_wait()**: 第 900 行 — 外部 abandon；异常则 `ABANDON_ERROR` backoff 释放 ✅
4. **Durable mark (post-abandon)**: 第 921-932 行 — 直接执行 `_MarkWaitRecordAbandonedOperation`，**不再受 gate 阻挡** ✅
5. **CAS result**: `UPDATED` → `(1, 0, 0, 0)`；`CAS_LOST` → `(0, 0, 1, 0)` ✅

关键改进：步骤 4 不再被 gate 拦截。外部 abandon 成功后，durable mark 总是尝试执行，仅在 CAS 冲突（claim 已被新 owner 取走）时才放弃。

## 3. Invariant Compliance Check

### 3.1 Shutdown 语义 ✅

- **Pre-abandon gate**: 仍然生效。shutdown 发生在 adapter 调用前 → `SHUTDOWN_SKIPPED`，wait 可重试。
- **Post-abandon gate**: 已移除。shutdown 发生在 adapter 返回后 → durable mark 先行写入 → claim 被清除 → wait 不再可被 poll。这是正确的，因为外部副作用已发生，必须持久化。
- **Drain 时间影响**: 最多多等一个单行 CAS write transaction（微秒级），可忽略。

### 3.2 Stale-Claim CAS 行为 ✅

`_MarkWaitRecordAbandonedOperation` 使用 `poll_claim_id = ? AND status = 'cancelled' AND poll_abandoned_at IS NULL` 作为 WHERE 条件：
- 若 claim 仍为当前 owner → `UPDATED`，abandoned 标记写入，claim 清除 ✅
- 若 claim 已被新 owner 取走（CAS 冲突）→ `CAS_LOST`，abandoned 标记不写入，返回 `claim_conflicts=1` ✅

CAS 冲突时外部 abandon 已发生但 durable mark 失败，新 claim owner 可能再次调用 `abandon_wait()`。这是预先存在的 CAS 竞态行为（与 gate 无关），且 `WaitPollAdapter.abandon_wait()` 的 best-effort 语义已接受此风险。

### 3.3 Adapter-outside-transaction 不变量 ✅

`adapter.abandon_wait(record)` 仍在 `self._transaction_runner.run_write()` 之外执行（第 900 行 vs 第 922 行）。修复仅删除了一个控制流检查，未改变 adapter 调用与 transaction 的边界。

### 3.4 `_resolve_claimed_wait` Gate Check 不受影响 ✅

第 806 行的 gate check 保护的是 `poll_wait()` 结果的 resolve 路径（ready/lost），与 abandon 路径独立。该 check 的语义正确：poll_wait 的结果未写入 durable，跳过 resolve 让后续 poller 重试是安全的。
