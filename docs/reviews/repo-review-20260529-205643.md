### 01-未修复-低-engine: `_close_runner_once` 中 CancelledError 导致 `_closed` 标记提前设置

- **入口/函数**: `_AsyncAgent._close_runner_once()`
- **文件(行号)**: `dayu/engine/agent.py:2331-2356`
- **输入场景**: Runner close() 被 asyncio CancelledError 打断
- **实际分支**: `except asyncio.CancelledError` -> 记录 warning -> `finally: self._closed = True` -> re-raise
- **预期行为**: close 操作未完成时，后续应有机会重试 close
- **实际行为**: `_closed = True` 已设置，后续调用直接 return，close 操作可能未完成但被标记为已完成
- **直接证据**: `finally` 块在 `CancelledError` re-raise 前设置 `_closed = True`（第 2355 行）
- **影响**: CancelledError 场景下 task 即将终止，未完成的 close 不会持续泄漏。实际风险极低
- **建议改法和验证点**: 可在 `CancelledError` 路径中不设 `_closed = True`，让 task 取消后的清理路径有机会重试 close；但需评估是否引入新的复杂度
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 02-未修复-低-runtime: Lane `_release_token` CancelledError 路径 token 清理延迟

- **入口/函数**: `_RuntimeLaneController._release_token()`
- **文件(行号)**: `dayu/runtime/lane.py`（release 路径）
- **输入场景**: release token 操作被外层 CancelledError 打断
- **实际分支**: CancelledError 路径不设 `token.released = True`，token 短暂留在 `_held_tokens` 中
- **预期行为**: release 完成后 token 应立即从 held_tokens 移除
- **实际行为**: token 留在 held_tokens 中，等待下次 heartbeat 循环通过 `RuntimeLaneClaimLostError` -> `_mark_token_lost` 清理
- **直接证据**: `_release_token` 的 CancelledError 处理路径不执行 `_mark_token_released`
- **影响**: 短暂的 capacity 误计（held_tokens 中有已释放的 token），下次 heartbeat（默认间隔秒级）自动修正。不影响 capacity 实际分配
- **建议改法和验证点**: 可在 CancelledError 路径中也设 `token.released = True`；但当前保守设计确保 DB row 已删除后才标记释放，避免误判
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 03-未修复-低-memory: Budget estimator chars_per_token 对英文场景偏乐观

- **入口/函数**: `DEFAULT_ESTIMATOR_CHARS_PER_TOKEN` 常量
- **文件(行号)**: `dayu/host/context_budget.py:35-36`
- **输入场景**: 英文为主的文本输入，context window 较小（如 2048 tokens）
- **实际分支**: 使用 `chars_per_token = 3` 估算，英文实际约 4 chars/token
- **预期行为**: 估算应覆盖目标语言的实际 token 密度
- **实际行为**: 英文场景下 token 数被低估约 25%
- **直接证据**: `DEFAULT_ESTIMATOR_CHARS_PER_TOKEN = 3`，中文每 token 约 1-2 字符，英文约 4 字符
- **影响**: soft/hard threshold 默认预留 20%/10% 余量，当前中文财报分析场景安全。纯英文 + 小窗口场景可能提前触发 reactive compaction
- **建议改法和验证点**: 记录为已知限制。如需支持英文场景，可降至 2.5 或按 content type 动态调整
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-低-memory: Evidence chunk 按字符边界分割可能切断语义单元

- **入口/函数**: `_evidence_chunks()`
- **文件(行号)**: `dayu/host/compact_material.py:1656-1698`
- **输入场景**: 长 evidence 文本超过 4096 字符
- **实际分支**: 按 `EVIDENCE_BLOCK_CHUNK_TEXT_MAX_CHARS = 4096` 硬切分

- **影响**: chunk 是 prompt-local material，LLM 可理解被切断的上下文。不影响 correctness，仅影响 LLM 体验
- **建议改法和验证点**: 可在切分点附近寻找句子边界（句号、换行）作为优选切分点
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
