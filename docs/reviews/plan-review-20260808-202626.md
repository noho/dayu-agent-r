## Findings

### F20-PLAN-001-未修复-高-R2父section与子chunk逐字重叠，直接违反no-padding setup边界

- **位置**: §3 Non-goals（plan 55–56）、§5.1 material recipe（139–149）、§5.2 proof R2（167–169）、Binding Goal 44–47。
- **问题类型**: 动机不成立 / 范围漂移 / 最佳实践偏离 / 不可直接实施。
- **当前写法**: plan宣称材料“不是 padding”且是“互不相同的业务 section”，R2固定读取 `s_0013` 后再读取 `s_0013_c03/c04/c11/c27/c36`，每个ref恰好一次；proof和formal共用该recipe。
- **反例/失败场景**: 通过 `dayu.fins.storage` 只读 F19 immutable AAPL processed document，父 `s_0013` 的 `children`明确包含全部五个目标chunk；五个chunk正文长度分别为2,294、5,316、5,575、3,101、3,916 chars，均在父正文中exact出现一次，总计20,202 chars。按plan执行会在81,454 chars的R2读入流中重复约24.8%的正文。`s_0013_c03/c36`包含的FY2025目标值也已经包含在父 `s_0013` 中。
- **为什么有问题**: goal要求合法setup并禁止padding；“参数ref不同”不等于内容不重复。production duplicate governance key包含 normalized arguments digest，不同section ref会生成不同key，不能替scenario阻止父/子内容重复。因此proof可能仅靠重复bytes跨soft，formal MiMo也可能按exact recipe执行一个本质padding的setup，得到的compact不具备目标所要求的合法性。
- **直接证据**: storage owner返回父 `s_0013` 61,252 chars，SHA `d1a11c06db1a08e644946e6869cc152aa55353c5437214c1c2b85a1e62065607`；五个chunk的每段content均满足 `child_content in parent_content`。相对地，R1的 `s_0003_c04/c05/c06` 两两不互相包含。`dayu/host/tool_duplicate_governance.py` 的key按 tool name、normalized arguments digest和semantic key形成，distinct refs不会被归并为同一内容事实。
- **影响**: Slice 1 trigger proof失去合法性；即使两个ordinary boundary达到soft，也不能放行provider。若正式运行后才发现，将浪费真实MiMo budget且formal evidence必须判failed，不能作为B2观察。
- **建议改法和验证点**: 在scenario/material owner处改为内容不重叠的真实AAPL recipe：父section与其任一子chunk二选一；若需要多个chunk，必须从storage bytes直接证明所有selected内容pairwise non-overlap/非包含并说明各自与目标业务问题的相关性。重新跑provider-free完整owner proof，只有不重复、不追加padding的recipe在两条ordinary boundary都满足soft≤predicted<hard才可进入formal。不得修改duplicate governance或产品来迁就recipe。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### F20-PLAN-002-未修复-高-accepted caps上界没有覆盖完整Memory-rendered输入，`< hard`证明不sound

- **位置**: success signal 3（32–34）、§5.2 accepted-output worst case（181–194）、Slice 1 expected assertions（331–337）。
- **问题类型**: 契约缺失 / 架构边界 / open question 未收敛 / 测试缺口。
- **当前写法**: plan用最小合法accepted fact得到完整candidate lower bound，再用 `MemoryProjectionPolicy` 五区字符caps、`estimate_budget_text_tokens`和“deterministic section-header overhead”计算 `accepted_view_max_increment_tokens`，声称这是所有accepted output达到caps时的单调upper bound。
- **反例/失败场景**: Host acceptance对 forward intent只按 `item.text`计入char cap，对reference continuity也只按 `item.text`计入char cap；`CompactForwardIntentV4.intent_type`与`CompactReferenceContinuityV4.reason`只要求non-empty，没有长度cap。RunInput owner实际渲染 `type=...; status=...; text=...` 与 `reason=...; text=...`，因此这两个动态字段进入完整candidate却不在plan的“五区caps+固定header”域内。默认runner config也不提供明确 `max_tokens` owner上限可被plan直接替代为有限字符bound。
- **为什么有问题**: hard decision owner估算完整 `BudgetEstimateInput` 的全部 message/json/tool-schema fragments；单独对业务text caps求和并不拥有完整candidate语义。当前公式证明的只是一个synthetic subset，而非Host可能接受并投影的所有replacement。它不能支持binding goal要求的“accepted replacement最大caps下保守边界”。
- **直接证据**: `dayu/host/context_governance.py:402-420`只把forward/reference的`.text`交给policy cap；`dayu/host/compaction.py:1352-1372,1397-1410`对`intent_type/reason`无长度上限；`dayu/host/run_input.py:4672-4694`把二者渲染给LLM；完整estimator在`dayu/host/context_budget.py:1251-1282`按完整fragments求和。
- **影响**: provider-free self-test可能错误PASS，正式accepted candidate仍可能得到不同于proof的post-compact size；pre-provider hard-safety gate不可审计，implementation agent必须自行发明遗漏字段的bound。
- **建议改法和验证点**: 先明确“最大accepted domain”的现有typed owner。若已有上游总输出/serialized-bytes bound，plan必须绑定其ref/version并覆盖所有最终rendered动态字段；随后构造typed max candidate，完整经过 `accept_compact_candidate_v4`→canonical terminal→Memory projection→`prepare_runner_call_candidate_in_transaction`→`estimate_prepared_runner_call_candidate`，以最终owner estimate证明 `<hard`，不能用下游文本加法替代。若现有产品contract没有有限bound，必须把它列为blocking open question并回到goal/setup裁决；F20 non-goal禁止顺手新增产品cap。
- **修复风险（低/中/高）**: 高。
- **严重程度（低/中/高/严重）**: 高。

### F20-PLAN-003-未修复-高-R4可达第三次proactive operation，Chain 01与全局call cap少算5次compactor调用

- **位置**: §5.3 Chain 01/R4（201–220）、§5.4 deadlines/call caps（225–234）、publication actual≤hard cap（241–256）。
- **问题类型**: 状态机漏洞 / 契约缺失 / 测试缺口。
- **当前写法**: Chain 01执行R1–R4并用fresh reconnect后的最多一个no-tool follow-up证明同一accepted replacement被消费；预算却固定为4 Runs×21 + 2 operations×5 = 94，全F20为240。
- **反例/失败场景**: R4是新的Run/input snapshot，Host设计明确每个ordinary snapshot在soft pressure时可以启动自己唯一的一次proactive operation。plan只证明第二ordinary在R3 admission触发，并没有证明R3 accepted compact、R3 no-tool output与fresh reconnect之后的R4 candidate必为normal。若R4仍达soft，production Host会合法启动第三operation；它可能产生最多5个compactor calls，并可能用第三accepted truth替换原本要验证的第二truth。
- **为什么有问题**: “同一snapshot不得第二次operation”不能推出“同一Session只能两次operation”。R4的新snapshot不受前两次operation限制。现有94/240 cap与self-test的actual≤hard assertion会把合法production分支误报超限，或driver为守住错误cap而在Host owner外阻止/隐藏调用。
- **直接证据**: `docs/host/design.md:3729,3740`明确 ordinary soft为每个Run/input snapshot启动一次operation；plan R4（219–220）创建新的ordinary follow-up，却没有 `decision=allow_dispatch`/operation count仍为2的precondition或第三operation terminal分支。
- **影响**: provider预算可能超出冻结cap；reconnect evidence可能消费第三truth而被误标为消费第二accepted truth；execution index/count publication无法exact对账。
- **建议改法和验证点**: Chain 01至少把第三operation的5次calls计入hard cap（Chain 01=99、全局=245），并在R4 state machine显式规定：只有R4 manifest引用第二accepted compact且R4前后operation count保持2，才可判reconnect observed；R4若启动第三operation，原样seal为needs-more/failed，不得声称same truth。若plan要坚持94，则Slice 1必须继续到“第二accepted→R3 terminal→fresh reconnect R4 ordinary”，由production owner证明R4 normal/allow且零新request后才可放行formal。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### F20-PLAN-004-未修复-中-provider-free的零真实transport/零网络事实没有可审计owner gate

- **位置**: §3 proof/formal boundary（53–56）、§5.2 proof identity（153–179、191–194）、§8 validation（372、390–395）。
- **问题类型**: 契约缺失 / 最佳实践偏离 / 测试缺口。
- **当前写法**: plan称 deterministic no-network Runner/compactor驱动proof，并正确声明proof不是formal evidence、formal禁止fake/mock；但`trigger-proof.json` required facts与self-test没有冻结worker factory identity，也没有断言真实provider transport create/call、socket/network或credential consumption为0。仅publication corruption matrix提到provider spawn=0。
- **反例/失败场景**: implementation若漏注入proof worker factory而走默认LocalProxy/真实Runner，或ordinary与compactor只替换其中一个，proof仍可能产生看似正确的Host EventLog/manifest并在两路actual-tooling review前消耗真实provider。事后凭类名或“deterministic”说明无法证明provider-free。
- **为什么有问题**: `OpenHostOptions.worker_factory`是ordinary与compactor共享的typed construction seam，`open_host`把它装配到Host local execution；plan没有要求从该真源记录proof worker identity/调用账，也没有fail-closed tripwire。formal fake禁令的文字边界虽清楚，proof运行身份仍不可审计。
- **直接证据**: `dayu/host/api.py:1122-1184`把`worker_factory`定义为必填typed port，`dayu/host/open_host.py:2849-2868`用同一factory装配ordinary与compactor runners；plan `trigger-proof.json`字段清单没有factory/transport/network counts。
- **影响**: 可能在provider gate前发生未授权真实调用，破坏proof/formal证据隔离与bounded provider accounting；reviewer无法只用durable artifact验证“no-network”。
- **建议改法和验证点**: 在plan中固定proof-only `OpenHostOptions.worker_factory`实现与file-byte SHA，ordinary/compactor两类调用均由同一可计数deterministic port处理；真实provider transport constructor/call必须由fail-closed tripwire保护。`trigger-proof.json`与self-test记录并断言 deterministic ordinary/compactor invocation counts符合recipe、real provider transport create/call=0、network tripwire hit=0、proof credentials不可用；这些facts仍不得进入formal observation verdict。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。
