## 三、Findings

### 1-未修复-[中]-隔离验证路径的 pyright 命令必然残留 missing-venv 诊断，自设判据强制进入昂贵 fallback，且已有实测可行的轻量替代
- **位置**: `docs/gateflow/fins-hidden-metadata-integrity-plan-20260928.md`「验证路径与预期」章节（pyright 示例命令与“若外部 `--pythonpath` 仍出现 missing-venv/import 诊断……建立本地 `.venv`”段）。
- **问题类型**: 不可直接实施 / 非最优方案（验证可行性）。
- **当前写法**: 主路径用主工作区外部解释器 + `PYTHONPATH="$PWD"` + `pyright --project pyrightconfig.json --pythonpath /Users/leo/workspace/dayu-agent-r/.venv/bin/python`；若出现 missing-venv/import 诊断则“建立符合 Python 3.11/锁定依赖的本地 `.venv`”后按 AGENTS.md 重跑。
- **反例/失败场景**: implementation gate 严格执行 plan 命令 → 实测必现 `venv .venv subdirectory not found in venv path …` → 触发 fallback → 在隔离区从零建重型依赖（该 venv 含 accelerate 等大依赖）本地 `.venv`，耗时且依赖网络；或实施 agent 为省事以主工作区 pyright 结果替代（plan 虽明令禁止，但成本对比强烈诱导）；或在 missing-venv 状态下接受“0 errors”作为验证结论，而 pyright 的 import 静态解析可能经主 venv editable 安装落到主工作区脏源码（主工作区 `dayu/fins/storage/_fs_source_integrity.py` 正有候选改动），基线与修改后诊断对比失真。
- **为什么有问题**: 项目约束要求“任何新增或修改代码都必须通过 pyright”“记录基线与修改后诊断差异”；验证环境自身带歧义诊断时，该结论不可信。plan 的判据（出现 missing-venv 诊断就 fallback）写得对，但主路径按实测不可能满足它，等于把实施 gate 直接推入未计成本的 fallback，属于可预先消除的实施阻塞。
- **直接证据**:
  1. `pyrightconfig.json` 为 `"venvPath": ".", "venv": ".venv"`，隔离 worktree 无 `.venv`（plan 自述“工作区当前没有 `.venv`”）。
  2. 实测 plan 原命令：`PYTHONPATH="$PWD" /Users/leo/workspace/dayu-agent-r/.venv/bin/pyright --project pyrightconfig.json --pythonpath /Users/leo/workspace/dayu-agent-r/.venv/bin/python` → `venv .venv subdirectory not found in venv path /private/tmp/dayu-upload-dotfile.` + `0 errors, 0 warnings, 0 informations`。
  3. 实测轻量替代：`… pyright --project pyrightconfig.json --venvpath /Users/leo/workspace/dayu-agent-r` → `0 errors, 0 warnings, 0 informations`（无任何 venv 诊断）。
  4. 运行时隔离实测可行：`cd /tmp && PYTHONPATH=/private/tmp/dayu-upload-dotfile …/.venv/bin/python -c "import dayu"` → 解析到 worktree（editable finder 为 `sys.meta_path.append`，PYTHONPATH 优先），plan 的 `import dayu` 指向核对是有效硬前置。
- **影响**: 实施/验证 gate 被环境问题阻塞、时间成本失控，或产出不可信的“零新增错误”验证结论；closeout 无法验收。
- **建议改法和验证点**:
  1. 验证路径的 pyright 命令改为 `--venvpath /Users/leo/workspace/dayu-agent-r`（实测干净）并保留 `--pythonpath`；或在隔离区建立 `.venv -> /Users/leo/workspace/dayu-agent-r/.venv` 符号链接后按 AGENTS.md `source .venv/bin/activate` 原样执行。
  2. 把“从零建立本地 `.venv`”降级为最后手段并注明成本（重型依赖、网络）。
  3. 验证点：pyright 输出必须无 `venv … not found` 类诊断才可作为 gate 证据；`import dayu` 指向核对保持为硬前置；基线/修改后诊断对比照旧记录。
- **修复风险（低/中/高）**: 低（只改 plan 验证段，不动设计）。
- **严重程度（低/中/高/严重）**: 中。

### 2-未修复-[低]-反向测试矩阵未显式覆盖 root×exact 与 document×whole 两个象限
- **位置**: plan「唯一实施切片」反向 owner 测试 bullet；主工作区候选测试 `test_source_integrity_hidden_symlink_still_fails_closed`（只断言 whole 的 `list_source_integrity`）。
- **问题类型**: 测试缺口。
- **当前写法**: “root whole 必须继续 typed `UNSAFE_PUBLICATION`，document exact 必须继续 `UNSAFE_FILESYSTEM_ENTRY` 且无 revision，snapshot/commit 不可发布 unsafe”。
- **反例/失败场景**: 实现把隐藏判定插错位置（如 root 循环中 `unassignable_root_fact` 收口之后、或 document 判定越过 declared 短路），导致 exact 模式下 root 隐藏不安全条目不再产生 `CROSS_SOURCE_INCONSISTENCY`/`repair_blocked`，或 whole 模式下 document 级 unsafe 聚合投影漂移；S1 按当前矩阵测试仍全绿。
- **为什么有问题**: goal 成功信号要求 exact/whole/snapshot/batch/commit 同一 inspector 判定；`unassignable_root_fact` 的 whole（typed preflight）与 exact（`_with_unsafe_classification(CROSS_SOURCE_INCONSISTENCY)` + `_derive_repair_blocked_reason`）是同一事实的两种收口，只测一半无法证明“root exact 与 whole 分歧”被正确收敛。候选测试同样只测 root×whole，plan 已声明候选不足但矩阵本身未补齐该象限。
- **直接证据**: `_inspect_source_kind_unguarded` 310–313（whole 抛 `UNSAFE_PUBLICATION`）、349–359（exact 标 `CROSS_SOURCE_INCONSISTENCY`）、360–366（repair_blocked）；候选测试 root 分支只调用 `source.list_source_integrity`（whole）；既有 corruption grid（`test_fins_storage_atomicity.py:6855-6891` 参数网格）含 `cross_source_inconsistency`/`symlink_entry`/`special_entry`，可部分回归补偿，但 grid 构造的是普通条目路径，未断言“点号命名不安全条目”走同一收口。
- **影响**: root exact/whole 分歧回归不可见；closeout 声称“exact、whole 同源”缺少完整测试证据。
- **建议改法和验证点**: 反向断言显式四象限：root×whole = typed `UNSAFE_PUBLICATION`；root×exact = `UNSAFE` + `CROSS_SOURCE_INCONSISTENCY`（并断言 repair_blocked）；document×exact = `UNSAFE_FILESYSTEM_ENTRY` 且 revision 为 None；document×whole 不进入 complete inventory 且 snapshot/commit 拒绝。或在 plan 中写明由 corruption grid 的哪个 case 等价补偿并补“隐藏命名”变体。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。

## 五、Residual risks（含追踪去向）

- **R1 文件系统 TOCTOU**（含隐藏目录在 `lstat` 与递归枚举之间被换成 symlink 的竞态，`Path.iterdir` 会跟随该 symlink）：goal 已声明不扩大为全局无竞态保证，helper 的逐条 `lstat` 与失败关闭已是当前 guard 水位。追踪：gateflow closeout 风险清单（沿用既有 TOCTOU 风险记录）。
- **R2 control/rejected 区隐藏元数据仍可阻塞清理路径**：`.rejections` 内容由 `_preflight_rejected_filing_tree` 双向校验（`_fs_maintenance_core.py:576-590`），`.DS_Store` 落入 rejected artifact 目录会使 `clear_filing_documents` 等抛 `ValueError`。goal 非目标明确排除 control 区，但同一动机模式（环境元数据泄漏）在此仍用户可见。追踪：建议单独 issue（“control/rejected 区隐藏元数据”）或 gateflow residual 风险清单，closeout 时不得声称“点号元数据全部免疫”。
