## Findings

### 1-未修复-[中]-known-no-end 日期来源规则未覆盖 download 写入方，同一事实两写入方落盘标签分裂

- **位置**: 计划 §6 123 行（known-no-end 同事务置 None）、§5（download 工作流契约，未含此规则）、§9 rebuild N02 回归行（仅 rebuild 反例）；root 裁决 known-no-end 矩阵「行/source/processed/两manifest 日期同 None，source/processed 日期来源同 None」。
- **问题类型**: 契约缺失 / 关键漏 caller / 语义所有权。
- **当前写法**: §6 规定 rebuild 对「原标题无唯一截止日」的已确定财期，同事务把 source/processed 的 `report_date` 与 `report_date_source` 显式置 None、两 manifest 投影日期 None；§5 与全文未规定 download 发布路径对同一事实状态的 `report_date_source` 落盘值。
- **反例/失败场景**: 标题只有显式财期无唯一年结日（如「2025年第三季度業績」）的已知报告：download 发布经 `cn_download_source_upsert.py:_build_base_meta:255` 写 `report_date=None` 且 `report_date_source="period_inferred"`；同一文档随后 rebuild（计划新规则）把 `report_date_source` 翻成 None；再次 download/覆盖发布又写回 `period_inferred`。durable 同一业务事实（已知财期、无唯一截止日）的来源标签随写入方/写入顺序在 `"period_inferred"` 与 None 间翻转。
- **为什么有问题**: root 已裁矩阵将「source/processed 日期来源同 None」作为 known-no-end 的 durable 契约；计划只在 rebuild 事务闭合它，遗漏第二写入方 `_build_base_meta`，照写实施即留下跨写入方不一致（违反单一语义 owner/durable 同源一致性约束）。即使 root 本意为 rebuild-transaction-scoped，计划也未写明该范围与 download 侧 `"period_inferred"` 的存留理由，实施 Agent 无法判定该字段的唯一语义。且 §9「known-no-end 旧日期反例」只测 rebuild 路径，回归无法暴露此分裂。
- **直接证据**: `cn_download_source_upsert.py:255`（`"source_title" if candidate.report_date is not None else _REPORT_DATE_SOURCE`，`_REPORT_DATE_SOURCE="period_inferred"`@39）；`hk_download_rebuild.py:110-112`（现保留旧值，计划改置 None）；计划 123 行仅写「同事务 source/processed…置 None」（§6 语境）；root 裁决/任务 binding 矩阵为平铺陈述。
- **影响**: durable 语义分裂、审计不可信、后续消费者/回读校验对同一状态接受两种标签；review 不可验收「日期来源同 None」契约；可能需返工补 writer 与回归。
- **建议改法和验证点**: 在 §5 或 §6 明确 known-no-end 的 `report_date_source` 唯一 owner 规则并覆盖两个写入方：要么 `_build_base_meta` 同步改写 None（download 侧 source/processed 日期来源同 None，§9 增 download 发布反例），要么显式写明该规则仅限 rebuild 既有 metadata 事务、download 保留 `"period_inferred"` 并由 root 确认该例外；验证点为同一文档 download→rebuild→download 三步后 source/processed 日期来源稳定一致。
- **修复风险（低/中/高）**: 低（一处 writer 或一行契约界定 + 一条回归）。
- **严重程度（低/中/高/严重）**: 中。
