## Scope

- Production Host wait poller loop / backoff / fencing / retry plan.
- Existing code has only synchronous single-round `WaitPoller.poll_once()`.
- Plan chooses wait-record-owned durable poll claim/backoff fields, no separate claim table, no lease, no Attempt takeover.
- Plan proposes 3 implementation slices: durable claim/backoff primitive, poller supervisor lifecycle, open_host integration/docs.

## Assumptions Tested

1. **Claim acquisition is atomic and correct for multi-process safety** — plan describes CAS semantics but does not specify the exact SQL acquisition pattern.
2. **Backoff state on wait row is sufficient and does not over-couple** — plan extends wait record with 10 new fields; assessed against separate claim table and runtime-only alternatives.
3. **3 slices follow the control doc slice principle** — assessed against the 2-3 default for medium Host durable/runtime work.
4. **Close drain with synchronous adapters is bounded** — plan acknowledges Python cannot kill sync functions but proposes timeout + structured error.
5. **resolve_wait terminal mutation clears claim fields** — plan states this but does not specify the exact mechanism in the resolve_wait pipeline.
6. **Tests prove multi-poller correctness** — assessed whether claim CAS tests are sufficient without relying on implementation-shaped assertions.
7. **Diagnostics do not leak into EventLog** — plan correctly scopes diagnostics to runtime read view / logs.

## Findings

### 01-未修复-中-claim acquisition atomicity 未明确指定 SQL 模式

- **位置**: Implementation Decisions > Claim / Fencing Placement; Slice 1 > Data flow / state transitions
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan says "CAS set poll_claim_id / owner / claimed_at / expires_at" in a write transaction. The data flow shows: "read eligible wait rows -> CAS set poll_claim_id / owner / claimed_at / expires_at -> adapter call outside Host transaction." The Implementation Decision says "SQLite CAS on the wait row can express acquire, release, expiry takeover, and stale release prevention."
- **反例/失败场景**: The data flow diagram shows "read eligible wait rows" as a separate step from "CAS set poll_claim_id." An implementation agent reading this could implement claim acquisition as: (1) SELECT eligible rows (unclaimed or expired claim), (2) for each row, UPDATE...WHERE wait_id=X AND poll_claim_id IS NULL. Between step (1) and step (2), a concurrent poller in another process could SELECT the same row and also attempt the UPDATE. SQLite write serialization means only one UPDATE succeeds, but the second poller has already decided to process this row and may attempt adapter calls before discovering the CAS failure. If the implementation does the adapter call before the CAS, the claim is not a fence — it is a post-hoc record. The correct pattern is a single atomic UPDATE...WHERE that combines eligibility check and claim setting: `UPDATE host_wait_records SET poll_claim_id=:claim_id, ... WHERE ... AND (poll_claim_id IS NULL OR poll_claim_expires_at <= :now) AND poll_next_observe_at <= :now RETURNING wait_id`. The SELECT that determines which rows to claim and the UPDATE that sets the claim must be the same statement, or the UPDATE must be attempted first with a RETURNING clause to discover which rows were successfully claimed.
- **为什么有问题**: The plan's correctness depends on "at most one unexpired poll claim exists per wait record" and "two pollers cannot concurrently hold an active poll claim." But the plan does not specify the SQL acquisition pattern that ensures this invariant under multi-process contention. An implementation agent might implement SELECT-then-UPDATE, which has a race window even with SQLite write serialization. The existing code in `read_wait_records_for_poll_observation` does a plain SELECT with no claim filtering, and the plan says to "Replace" this call path with claim acquisition — but does not specify whether the replacement is a single atomic statement or a two-step read-then-write.
- **直接证据**: Plan line "read eligible wait rows -> CAS set poll_claim_id" shows two separate steps. Current code `read_wait_records_for_poll_observation` in `dayu/host/durable/state.py` (lines 1910-1937) does a plain SELECT with no claim filtering, no LIMIT, and no claim update. Plan says "Replace `read_wait_records_for_poll_observation(...)` call path with claim acquisition" but does not specify the SQL pattern.
- **影响**: Implementation agent may implement non-atomic claim acquisition, causing concurrent adapter calls in multi-process deployments. The claim would not actually prevent duplicate adapter side effects, defeating a core goal of the plan.
- **建议改法和验证点**: In Slice 1, explicitly specify that claim acquisition must be a single atomic `UPDATE...WHERE` statement (or `UPDATE...RETURNING`) that combines eligibility check (unclaimed or expired claim, `poll_next_observe_at <= now`, correct status) and claim setting in one SQL operation. Add a test that verifies claim acquisition returns only successfully claimed rows (not all eligible rows). Add a comment in the data flow diagram: "atomic UPDATE...WHERE: eligibility check + claim set in one statement."
- **修复风险（低/中/高）**: 低 — 只需在 plan 中明确 SQL 模式，不改变架构设计。
- **严重程度（中）**: 这是 plan 的核心正确性机制；如果实现错误，多进程部署会出现重复 adapter 调用。

### 02-未修复-低-claim batch size 原子性未明确

- **位置**: Contract / Schema / State-Machine / Public Interface Changes > Durable State Helpers; Slice 1
- **问题类型**: 契约缺失
- **当前写法**: Plan introduces `claim_batch_size` in `WaitPollerRuntimePolicy` and `claim_wait_records_for_poll_observation(transaction, *, owner_id, claim_id_factory, now, claim_ttl_seconds, limit)`. The `limit` parameter suggests batch claiming.
- **反例/失败场景**: If batch claiming uses one transaction per row, a partial failure leaves some rows claimed and others unclaimed — this is acceptable but not documented. If batch claiming uses one transaction for all rows, a failure in row 5 of 10 rolls back claims on rows 1-4 — this could cause unnecessary claim loss. The plan does not specify which pattern is intended.
- **为什么有问题**: The implementation agent needs to know whether batch claims are all-or-nothing or best-effort. The plan's helper signature `claim_wait_records_for_poll_observation(transaction, ..., limit)` suggests a single transaction, but does not clarify the failure semantics.
- **直接证据**: Plan defines `claim_wait_records_for_poll_observation(transaction, *, owner_id, claim_id_factory, now, claim_ttl_seconds, limit) -> tuple[WaitPollClaimedRecord, ...]` with a `limit` parameter, but does not specify whether batch claiming is atomic or independent per row.
- **影响**: Low — the difference affects only efficiency and partial-failure behavior, not correctness (each claim is independent). But ambiguity could lead to unnecessary complexity in the implementation.
- **建议改法和验证点**: Clarify that batch claiming should process rows independently within the same transaction (each row's claim is a separate UPDATE...WHERE, failures are isolated per row, successfully claimed rows are returned). Alternatively, simplify to single-row claiming and remove `claim_batch_size` from the policy — the supervisor can call the claim helper in a loop.
- **修复风险（低/中/高）**: 低 — 只需明确语义。
- **严重程度（低）**: 不影响核心正确性，只影响实现细节。

### 03-未修复-低-close drain timeout 触发后行为未明确

- **位置**: Implementation Decisions > Poll Loop Lifecycle > Close drain
- **问题类型**: 契约缺失
- **当前写法**: Plan says "If `close_drain_timeout_seconds` is set and the current poll round does not finish in time, log a structured error and keep the durable store open until the task is fully stopped; do not close the store while a background thread can still use it." And: "close() waits for the current poll round to finish."
- **反例/失败场景**: When the close-drain timeout fires, the plan says to log an error and keep the store open. But what does `close()` return to the caller? If `close()` returns after the timeout (leaving the background task running), the caller may proceed to close the durable store — contradicting "do not close the store while a background thread can still use it." If `close()` waits indefinitely after the timeout, the timeout has no effect. If `close()` raises an exception, the caller's cleanup sequence is disrupted. The plan does not specify which behavior is intended.
- **为什么有问题**: The `open_host` close sequence calls `poller.close()` before `scheduler.close()` before `durable_store.close()`. If `poller.close()` does not actually return after the timeout, the close sequence hangs. If it returns but the background task is still running, the subsequent `durable_store.close()` corrupts in-flight writes.
- **直接证据**: Plan says "close() waits for the current poll round to finish" and "do not close the store while a background thread can still use it" — these two statements are in tension when a timeout fires.
- **影响**: Low — the close-drain timeout is a safety valve, and in practice adapter calls should be short-lived. But ambiguity could cause the implementation to either hang on close or corrupt durable state.
- **建议改法和验证点**: Specify that when the close-drain timeout fires: (1) `close()` logs a structured error with diagnostics, (2) `close()` returns (does not hang), (3) the background task is cancelled (if using `asyncio.Task`) or left to complete (if using `asyncio.to_thread`), (4) the durable store close must wait for the background thread to actually finish (not just for `close()` to return). Alternatively, if the intent is that the durable store close is independent of the poller close, state that explicitly. Add a test for the timeout-fire scenario.
- **修复风险（低/中/高）**: 低 — 只需明确语义和添加一个测试。
- **严重程度（低）**: Close-drain timeout is a safety valve; normal operation should not hit it. But the ambiguity affects the correctness of the close sequence.

## Architecture Boundary Review

**Host vs Engine boundary**: Correctly maintained. Plan explicitly states: "Do not change the Engine awaiting public model. Engine still does not poll, store wait records, or resume old Agent / Runner instances." Poller only submits through `resolve_wait`. No EventLog appender held by poller. No direct Run/Attempt mutation.

**UI/Service vs Host boundary**: Correctly maintained. Plan states: "open_host remains the composition root; Service does not control poll loop or scheduler wakeups." No Service-facing wait APIs added. Diagnostics are runtime-only.

**Durable truth vs runtime diagnostics**: Correctly separated. Poll claim and backoff fields are durable (on wait row). Aggregate counters and loop status are in-memory diagnostics. No new EventLog diagnostic events for ordinary poll health.

**Wait-row extension vs separate claim table**: Well-justified. The plan correctly argues that the claim has one owner at a time and is semantically subordinate to one wait record. SQLite CAS on the wait row can express all needed operations. The design doc explicitly rejects heavy lease/fencing systems, and the plan follows this guidance.

## Best Practice Review

**Durability**: Claim and backoff state are durable on the wait row, surviving process restart. The in-memory `_abandoned_cancelled_wait_ids` is correctly replaced by durable `poll_abandoned_at`. Good.

**Idempotency**: `_poll_idempotency_key` is deterministic and stable across polls for the same wait. The plan correctly requires reusing the same key for every poll resolution attempt. The existing `resolve_wait` idempotency pipeline handles same-key replay and different-outcome conflict.

**Shutdown**: Sleep cancellation via `asyncio.Event` or cancellable sleep. Close gate checked before claiming, after adapter, before resolve. No new adapter calls after close begins. Results observed after close started are not submitted. Good.

**Testability**: `drain_once_for_test()` exposed on supervisor. Injected policy and clock. No wall-clock long sleeps. Claim CAS tests deterministic. Good.

**Schema evolution**: Fresh-schema rule followed. Increment `HOST_SCHEMA_VERSION`. No old DB compatibility reads. Good.

## Optimal Solution Review

**Wait-row extension**: This is the correct choice for the current problem. The claim is semantically subordinate to the wait record, has one owner at a time, and does not need cross-table joins. A separate claim table would add lifecycle surface without a separate semantic owner.

**Runtime-only state**: Insufficient because it does not coordinate multiple Host processes. The plan correctly identifies this and rejects it.

**Durable backoff on wait row**: This is slightly heavier than runtime-only backoff, but justified because: (1) backoff state survives process restart, (2) multiple pollers share the same backoff state, (3) the backoff fields are small (5 fields: next_observe_at, attempts, last_observed_at, last_outcome, last_error_code). The alternative of runtime-only backoff would cause tight-looping after process restart for waits that were previously failing.

## Overengineering Review

The plan is appropriately scoped. No unnecessary abstractions, builders, wrappers, or generalizations. The claim is stored on the wait row, not in a generic lease service. Backoff is one small Host-owned policy, not a generic retry framework. Diagnostics are runtime/log/read-view only, avoiding new EventLog or projection systems.

The 3-slice structure maps to real dependency boundaries (durable CAS → runtime lifecycle → composition/docs) and does not introduce module-count slices.

## Overcoupling Review

The plan does not introduce overcoupling. The poll claim fields are scoped to the wait record and do not affect Run/Attempt state, dispatch records, or Engine contracts. The supervisor lifecycle is independent of the scheduler lifecycle. The backoff policy is injectable and does not couple the poller to specific timing decisions.

The one area to watch: the plan extends `WaitPollOnceResult` with new fields (`claimed`, `claim_conflicts`, `backoff_skipped`, `shutdown_skipped`, etc.) and adds `WaitPollBatchResult`. This increases the surface area of the result type, but it is bounded and does not create cross-layer coupling.

## Slice Principle Assessment

The plan proposes 3 slices. The control doc default for medium Host durable/runtime work is 2-3 slices. Assessment:

- **Slice 1 (durable CAS primitive)**: Closes the durable correctness primitive. Independently verifiable: schema tests, state tests, claim-aware polling tests. Good.
- **Slice 2 (poller supervisor lifecycle)**: Closes single-process poller behavior. Depends on Slice 1. Independently verifiable: lifecycle tests, sleep cancellation, close drain. Good.
- **Slice 3 (open_host integration)**: Closes production composition. Depends on Slice 1 and 2. Independently verifiable: opener construction, close order, default behavior. Good.

3 slices is the correct count for this work unit. Fewer would mix schema/CAS correctness, async runtime lifecycle, and public opener integration in one review loop. More would create gate cost without a separate semantic boundary.

## Plan Review Conclusion

**pass-with-risks**

The plan is well-structured, correctly scoped, and aligns with the design sources and control doc. The core design decisions (wait-row claim extension, durable backoff, diagnostics-as-runtime-only, 3 slices) are sound and well-justified.

The one material finding (claim acquisition atomicity) is medium severity and low fix risk: the plan needs to explicitly specify that claim acquisition must be a single atomic UPDATE...WHERE statement. Without this clarification, an implementation agent might implement SELECT-then-UPDATE, which has a race window under multi-process contention. The fix is a textual clarification in Slice 1, not an architectural change.

The two low-severity findings (batch claim atomicity, close drain timeout semantics) are clarification items that do not block implementation but would benefit from explicit specification.

No blocking open questions. All residual risks have clear owners and destinations.
