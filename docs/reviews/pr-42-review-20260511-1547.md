### F-1-未修复-严重-Tool-call-配对跨越-batch-边界导致永久-BLOCKED_FAILED

- **入口/函数**: `ToolTraceObserver._process_sync`
- **文件(行号)**: `dayu/host/_tool_trace_projection.py:198-222`
- **输入场景**: `TOOL_CALL_REQUESTED` 出现在 batch N，对应的 `TOOL_RESULT_ACCEPTED` 出现在 batch N+1（工具执行慢，Engine 在两次事件之间产生了大量 `RUNNER_CONTENT_DELTA` / `RUNNER_USAGE_RECORDED` 事件，事件位置差 > batch_limit）
- **实际分支**: `_process_sync` 第 198 行为每个 batch 新建局部 `groups` 字典。batch N 中 `group.requested is not None` 但 `group.accepted is None`→第 265 行抛 `ProjectionSchemaError`
- **预期行为**: 投影不应因事件落在不同 batch 中就永久阻塞 checkpoint
- **实际行为**: Coordinator 在 `_process_non_transactional_batch` 中捕获 `Exception`，标记 `BLOCKED_FAILED`。checkpoint 不前进，下一次 `drain()` 读同一 batch，再次失败→无限阻塞
- **直接证据**: `groups` 字典是 `_process_sync` 局部变量（行 198）；`_DEFAULT_BATCH_LIMIT = 64`；投影在 terminal 事件后运行，Engine 在一次工具执行期间可产生大量 `CONTENT_DELTA` 事件
- **影响**: 小 batch_limit、慢工具执行或多 content delta 的 run 可触发此 bug。checkpoint 永久卡住意味着 trace、memory、timeline 等所有 observer 均停止推进
- **建议改法和验证点**: 在 `ToolTraceObserver` 维护跨 batch 的 pending `tool_call_groups` 缓存，或将未配对事件降级为日志警告+跳过而非抛异常。测试：用 batch_limit=2，事件序列 `[TOOL_CALL_REQUESTED, RUNNER_USAGE_RECORDED, TOOL_RESULT_ACCEPTED]` 分三次调用 `_process_sync`
- **修复风险**: 中（需改变投影状态管理，引入跨 batch 缓存）
- **严重程度**: 严重

### F-2-未修复-严重-run_input_raw_payloads表无限增长无生命周期管理

- **入口/函数**: `put_run_input_raw_payloads`
- **文件(行号)**: `dayu/host/_run_input_raw_payload_store.py:201-271`（写入路径）；`dayu/host/_run_harness.py:640-647, 1113-1124`（调用点）
- **输入场景**: 长运行 Host 处理数千 run，每个 run 多次 compact retry，每次 attempt 写入新的 raw payload
- **实际分支**: 表仅有 INSERT 路径，无 DELETE / TRUNCATE / TTL 清理逻辑
- **预期行为**: raw payload 应有基于 run TTL 或 run terminal 的生命周期策略
- **实际行为**: 每行以 ~几 KB 到 ~几十 KB JSON 无限累积
- **直接证据**: DDL（`_run_input_raw_payload_store.py:26-48`）无 TTL 列、无过期索引、无清理触发器；`put_run_input_raw_payloads` 仅执行 INSERT；模块无对应 `delete_*` 函数
- **影响**: 生产环境中不可避免的存储耗尽。每条 `input_messages` payload 包含所有 AgentMessage 的完整序列化 JSON
- **建议改法和验证点**: 添加 `delete_run_input_raw_payloads_by_run_id(storage, run_id)` 并在 run terminal 后调用；或基于 `created_at` 的时间窗口清理
- **修复风险**: 中（需要额外的生命周期钩子，Harness 需在 terminal 后调用清理）
- **严重程度**: 严重

### F-3-未修复-中-_decode_result_success缺失value字段静默返回None

- **入口/函数**: `_decode_result_success`
- **文件(行号)**: `dayu/host/_run_event_serializer.py:830`
- **输入场景**: 持久化数据因 corruption 缺失 "value" 字段：`{"ok": true, "meta": ..., }`
- **实际分支**: `value=value.get("value")` 中 `.get()` 返回 `None`，构造 `ToolResultSuccess(value=None, ...)`
- **预期行为**: 模块 docstring 声明"字段不匹配时必须 fail-fast"，缺失必填字段应抛 `ValueError`
- **实际行为**: 静默返回 `value=None`，工具结果内容丢失
- **直接证据**: 行 830 使用 `.get("value")` 而非强制校验；同文件 `_decode_result_failure` 对 `error`/`message` 使用 `_get_str` 强制校验
- **影响**: 若 EventLog 的 JSON 字节部分损坏，反序列化不报错但工具结果丢失，下游读到错误数据
- **建议改法和验证点**: 添加 "value" 键存在性检查（值可以是 JSON null → None），缺失时抛 `ValueError`
- **修复风险**: 低
- **严重程度**: 中

- **入口/函数**: `ToolTraceObserver._emit_tool_call`

### F-6-未修复-中-JSONL-append_record_line无原子写入保护

- **入口/函数**: `ToolTraceJsonlSink.append_record_line`
- **文件(行号)**: `dayu/host/_tool_trace_jsonl_sink.py:144-149`
- **输入场景**: 进程在 `handle.write(line)` 和 `os.fsync(handle.fileno())` 之间崩溃
- **实际分支**: 追加二进制数据→写换行符→flush→fsync，三步非原子。崩溃可留下部分 JSON 行或缺少尾换行符
- **预期行为**: JSONL 写入应为全有或全无，或应有文档说明不变量
- **实际行为**: 与 `write_raw_payload_blob`（行 176-181，使用 `os.replace` 原子写入）形成对比——同一模块中两种写入策略不一致
- **直接证据**: `append_record_line` 使用直接 `open("ab")` + `write` + `flush` + `fsync`；`write_raw_payload_blob` 使用 `.tmp` + `os.replace`
- **影响**: 崩溃恢复后 JSONL 文件可含损坏行。分析器需实现防御性解析
- **建议改法和验证点**: 在模块文档中明确声明："崩溃恢复后 JSONL 可能包含损坏行；分析器必须跳过无效 JSON 行并依赖 idempotency_key 去重"
- **修复风险**: 低（仅文档）
- **严重程度**: 中
