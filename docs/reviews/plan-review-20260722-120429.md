## PRR-001 复核：Host close 在 execution owner quiesce 前释放 mutex

### 裁决要求回顾

Host close 专用顺序必须改为：关闭 public/new-work gate → stop wait poller → durable actor drain → 等待全部 attachment mutation/pre-start work lease 收口但继续持有 native mutex → 在 mutex 仍持有时完成 scheduler lifecycle close（停止 promotion/background supervisor、传播 active worker lifecycle cancel、关闭本地 worker/task/lane 并完成 host instance stopping/stopped 收口）→ 最后释放 native mutex/关闭 attachment record → 其余 owner close。mandatory cleanup 或 `STOPPED` 失败时保持 `CLOSING`/锁且可重试。fresh RW 同一次 target recovery 不漏恢复。单 attachment close 不得回归。

### 代码直接证据

**当前 close 顺序**（`open_host.py::_close_owned_resources` lines 1419-1545）：

```
health gate → wait poller → actor drain → scheduler.close() → terminal coordinator → delta hub → projection → actor handle → executor → store → mark_closed
```

当前没有 attachment registry 或 native mutex；scheduler close 在 actor drain 之后、其余 owner 之前执行。

**当前 `HostDispatchScheduler.close()`**（`dispatch.py` lines 2747-2797）：

```
_closed = True → best_effort_mark_stopping → cancel heartbeat/drain/promotion/watchdog tasks → cancel_all (token + on_cancel) → cancel active tasks → close worker handles → clear registry → close lane controller → best_effort_mark_stopped → _close_cleanup_done = True
```

关键事实：
- `cancel_all`（line 2780）调用 `_propagate_active_worker_cancel`，先传播 `cancellation_token.request_cancel(reason)`，再调用 `entry.handle.on_cancel(reason)`，hook 异常只 log 不阻断（lines 811-821）。
- `_best_effort_mark_host_instance_stopped`（lines 3029-3051）是 best-effort：异常只 warning log，不 raise。
- 异常路径（lines 2790-2792）：`_close_cleanup_done = True` 然后 re-raise。这意味着 cleanup 异常后重试 `close()` 会因 `_close_cleanup_done = True` 跳过（line 2753-2754 guard）。

**`classify_orphan_candidate`**（`recovery_process.py` lines 235-243）：`STOPPED` status 直接返回 `PositiveOrphanProof`（`_ORPHAN_REASON_OWNER_STOPPED`），不需要进程 probe 或 heartbeat 检查。`STOPPING` 与 `RUNNING` 同等对待，需走 heartbeat staleness 检查。

### Plan 修订评估

**§5.4 Host close 顺序**：Plan 明确冻结为7步：

```
① health gate begin_closing + registry begin_host_close →
② stop wait poller →
③ durable_actor.stop_and_drain() →
④ registry 等待全部 attachment mutation/pre-start lease → 保持 mutex →
⑤ scheduler lifecycle close（stop promotion/background、cancel_all token/hook、close task/handle/lane、mark STOPPED）→
⑥ 成功后才 release mutex / delete attachment record →
⑦ 其余 owner close
```

**修复分析**：

1. **scheduler mandatory quiescence**：步骤⑤要求 scheduler 完整 close 后才进入⑥。当前代码 scheduler close 本身已有完整的 quiescence（cancel background tasks → cancel_all → close handles → close lane → mark stopped）。Plan 正确地把该步骤放在 mutex release 之前。
2. **token/on_cancel 传播**：`cancel_all` 已调用 `cancellation_token.request_cancel` + `handle.on_cancel`。Plan 的"best-effort on_cancel hook 不阻断 token 与其余 mandatory cleanup"与当前代码一致。
3. **worker/task/handle/lane cleanup**：当前 close 已覆盖（lines 2780-2788）。Plan 不改变这些逻辑的内部结构。
4. **durable STOPPED**：`_best_effort_mark_host_instance_stopped` 在 cleanup 末尾调用。Plan 要求"任一 mandatory cleanup 或 `STOPPED` 收口异常时 Host health/attachment 保持 CLOSING、mutex 不 release"。
5. **失败保持 CLOSING/锁且可重试**：Plan 明确要求 cleanup 异常时 `_close_cleanup_done` 不得标真、`mark_closed` 不得调用。当前代码在异常路径设 `_close_cleanup_done = True`（line 2791），Plan 要求删除该行。
6. **fresh RW 同一次 target recovery 不漏恢复**：scheduler 标 `STOPPED` 后 mutex 才 release；fresh RW attach 时 `classify_orphan_candidate` 看到 `STOPPED` 直接返回 `PositiveOrphanProof`，在同一次 target recovery 推进旧 Attempt。不需要第二次 reattach 或 periodic reconcile。
7. **单 attachment close 不得回归**：Plan §5.4 明确"单 attachment close 保持 gate/drain/release 且不关 scheduler"。不受 Host close 顺序变更影响。

**测试覆盖评估**：

- `test_scheduler_close_cancelled_mid_cleanup_can_retry_and_finish`（line 4313）：证明 cleanup 取消后 `_close_cleanup_done = False`，重试可完成。但这是 scheduler 级测试，不覆盖 Host 级 CLOSING/mutex 持有。
- `test_scheduler_close_marks_cleanup_done_when_cleanup_raises`（line 4379）：当前断言 `_close_cleanup_done IS True`。Plan 要求更新此测试（§10 invariants checklist："更新当前'普通cleanup异常即_close_cleanup_done=True'的偶然测试，不保留该行为"）。
- §10 checklist 第8条明确要求："scheduler mandatory cleanup 或 `STOPPED` 写入注入异常时，close 返回错误但 Host health/attachment 保持 `CLOSING`、mutex 仍 busy、第二 opener 仍只能 RO"。

**Gap 识别**：Plan 明确要求的行为（Host 级 cleanup 异常路径 CLOSING/mutex/重试）在 §10 invariants 和 Slice 2 tests 中有文字描述，但没有给出一个独立的、确定性的 Host 级异常注入测试用例名称或伪代码。Scheduler 级测试提供了基础（`_close_cleanup_done` 行为），但 Host 级"cleanup 异常 → CLOSING + mutex busy + 重试 → 成功后 release"的完整 barrier 测试需要在 implementation 阶段显式构造。这不是 blocker（Plan 已在多处明确该行为），但属于实施时需主动验证的点。

### PRR-001 裁决

**已修复**（附低风险 residual）

Plan 正确地把 scheduler lifecycle close 移到 mutex release 之前，完整覆盖 mandatory quiescence、token/hook 传播、worker/task/handle/lane cleanup、durable STOPPED、cleanup 异常 fail-closed/retry 和 single-attachment-close 不回归。`classify_orphan_candidate` 的 `STOPPED` short-circuit 保证 fresh RW 同一次 target recovery 不漏恢复。当前代码异常路径 `_close_cleanup_done = True` 由 Plan 显式要求删除。

Residual：Host 级 cleanup 异常路径的 CLOSING/mutex/retry barrier 测试需在 implementation 阶段显式构造，Plan 已在 §10 和 Slice 2 tests 中明确该行为。

### NEW-002-未修复-低-engine_ingest `pending.policy=None` 时的 signature 适配未显式说明

- **位置**: §5.7 reactive producer 描述；Slice 2 exact changes 第15条
- **问题类型**: 可直接实施但需补充边界
- **当前写法**: Plan 要求 `engine_ingest.py` 以 `first_attempt_number=1`、`max_attempt_number=pending.policy.max_compaction_attempts_per_operation` 调用 `run_compaction_operation`。`pending.policy` 来自 `_start_reactive_context_recovery` 中写入的 `_ReactiveCompactPending.policy`。
- **反例/失败场景**: 当前代码 `_execute_reactive_compaction` 有 `self._context_budget_policy.max_compaction_attempts_per_operation or 1` 的 fallback（line 1986-1998）。若 `pending.policy` 为 `None`（budget 未配置），Plan 的 `pending.policy.max_compaction_attempts_per_operation` 会 raise `AttributeError`。
- **为什么有问题**: 这是机械适配的边界情况。Plan 未显式说明 `pending.policy=None` 时的处理。当前代码有 `or 1` fallback，Plan 要求"不得重新读取 ingestor policy"，但 `pending.policy` 本身可能是 `None`。
- **直接证据**: `engine_ingest.py` lines 1981-1998 中 `max_attempts=self._context_budget_policy.max_compaction_attempts_per_operation or 1`。
- **影响**: 极低。Implementation agent 在机械迁移时会自然处理该分支（要么从 `pending.policy` 读取并 fallback，要么在 `pending.policy=None` 时传默认值）。Plan 的 non-goal "不改 reactive pipeline" 足够指导。
- **建议改法和验证点**: 可在 §5.7 或 Slice 2 exact changes 中补充一句："`pending.policy` 为 `None` 时，`max_attempt_number` 使用既有 fallback 值1，不重新读取 policy。" 验证点：测试覆盖 `budget_state=None` 的 reactive path。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
