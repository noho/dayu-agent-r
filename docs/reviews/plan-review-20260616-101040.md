## Findings

### DS-001-未修复-高-lightweight-observation-handle-欠规格

- **位置**: Slice D 实施步骤 2-3；成功信号 line 76；Residual Risk line 374
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan 定义 lightweight observation handle 为"不透明引用，只标识 wait adapter 观察 completion 所需的信息"，但没有给出具体数据形态、生命周期、poll 协议或 failure mode。Slice D 步骤 2 说"用 lightweight observation handle 替代 `resume_token=start.job_id`"，步骤 3 说"更新 wait adapter，使其 poll lightweight observation source"——但从不定义 observation source 是什么。
- **反例/失败场景**: Implementation agent 进入 Slice D 时面临一个开放设计空间：lightweight handle 可以是 in-memory dict key、文件系统 marker file、最小 SQLite row、runtime-local `asyncio.Event` 或其它形态。agent 可能选择一个在单进程测试中工作但跨进程（Host wait adapter 运行在 Host 进程，Fins runtime 可能在另一个执行上下文）或在进程崩溃后完全丢失的实现。当前 wait adapter (`dayu/fins/ingestion/wait_adapter.py`) 通过 `runtime.read_job(job_id)` 和 `runtime.request_cancel(job_id)` 实现 poll/abandon——如果 lightweight handle 替换了 job_id，wait adapter 需要一个新的 observation source API，但 plan 没有定义该 API 的签名。
- **为什么有问题**: "Lightweight observation handle" 是实现的核心设计决策，不是实现细节。不给 handle 的数据形态、poll API 和跨进程/崩溃语义设定最低规格，就把设计负担从 plan author 转移给了 implementation agent。这与项目约束"plan 必须 code-generation-ready"冲突。
- **直接证据**:
  - Plan line 257: "用 lightweight observation handle 替代 `resume_token=start.job_id`。该 handle 必须是不透明引用，只标识 wait adapter 观察 completion 所需的信息"——没有定义 handle 类型、创建者、poll 方法。
  - Plan line 258: "更新 wait adapter，使其 poll lightweight observation source"——没有定义 observation source 的接口。
  - 当前代码 `dayu/fins/ingestion/wait_adapter.py:80`（截断处）使用 `runtime.read_job(job_id)` 做 poll——新 handle 替换 job_id 后，adapter 需要调用什么？
  - Plan line 374 residual risk 承认: "如果 lightweight handle 无法完全替代当前 wait adapter 对 job record 的 poll/abandon 能力，必须在 Slice D 前提出裁决点"——说明 plan author 自己也意识到这个风险。
- **影响**: 实施 Agent 在 Slice D 中被迫设计轻量 handle 契约，可能选出错误的抽象、引入不可恢复的等待状态或在 process crash 后 orphan 所有 awaiting jobs。如果 implementation agent 选错，review 需要大量返工。
- **建议改法和验证点**:
  1. 在 Slice D 前（或在 plan 中）至少定义 lightweight observation handle 的最小 typed contract：handle 类型（opaque str/int/bytes）、创建者（runtime）、消费者（wait adapter）、poll API 签名、abandon/cancel API 签名。
  2. 明确 handle 是否必须 durability：如果 Host 重启后 wait adapter 需要恢复未完成的 awaiting observation，handle 必须可持久化；如果不需要（跨进程但同生命周期），明确说明并在 stop condition 中记录此限制。
  3. 明确 observation source 是什么：是 runtime-local `dict[str, asyncio.Event]`、是 storage artifact 的 completion marker、还是保留的最小 job record row。
  4. 在 Slice D allowed files 中显式加入新的 contract module（如 `dayu/fins/ingestion/observation_handle.py`）或明确复用现有模块。
- **修复风险（中）**: 需要 small design decision，不涉及 Host/Engine 契约变更。
- **严重程度（高）**: 阻塞 Slice D implementation——没有这个定义，Slice D 无法 code-generation-ready。

### DS-002-未修复-中-Slice-A-C-sequencing-依赖缺口

- **位置**: Slices A 和 C 的 allowed files 与实施步骤
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: Slice A（line 116-152）在 Service boundary 定义 `AsyncIterator[FinsEvent]` 方法并修改 `dayu/fins/ingestion_runtime.py` protocol（步骤 2），但 Slice C（line 200-239）才"拆分 runtime API 语义"和"用 stream execution APIs 替代 `start_download` / `start_preprocess` / `start_upload` 的 direct-path 使用"。两个 slice 都允许修改 `dayu/fins/ingestion_runtime.py`。
- **反例/失败场景**: Implementation agent 在 Slice A 中修改 `FinsDirectIngestionRuntime` protocol 为 streaming 方法，但不知道 runtime 内部如何实现这些方法（那是 Slice C 的职责）。agent 可能：(a) 在 Slice A 中只改 protocol 签名 + 临时 stub，等 Slice C 补实现——但这违反"可独立验证的行为闭环"约束；(b) 在 Slice A 中提前做 Slice C 的 runtime 重构——导致 slice boundary 模糊，review scope 不可控。
- **为什么有问题**: Slice A 和 C 共享 `dayu/fins/ingestion_runtime.py` 作为 allowed file，但 plan 没有定义两个 slice 之间的 contract handoff。控制文档（`issues-implementation-control.md` line 133-136）要求 slice "沿稳定模块 ownership 切分"且"可独立验证的行为闭环"——两个 slice 修改同一模块的不同语义层违反了这一约束。
- **直接证据**:
  - Slice A allowed files: `dayu/fins/ingestion_runtime.py` (line 119)
  - Slice C allowed files: `dayu/fins/ingestion_runtime.py` (line 204)
  - Slice A 步骤 2: "把 `FinsDirectIngestionRuntime` protocol 从 `start_* + read_job/...` 改为 direct streaming methods"
  - Slice C 步骤 2: "从 core runtime 移除或降级 job event sidecar"
  - 两个步骤修改同一模块的不同抽象层，但没有定义谁先谁后、如何 handoff。
- **影响**: 实施 Agent 可能跨越 slice boundary 做额外工作，导致 review scope 不可控。或者 Slice A 的 Service 测试需要 fake runtime，但 fake runtime 的实现依赖于 Slice C 才确定的新 API 形态。
- **建议改法和验证点**:
  1. 将 `FinsDirectIngestionRuntime` protocol 变更明确归属到一个 slice（建议 Slice A），Slice C 只做 runtime 内部实现收敛。
  2. 或者将 Slice A 的 runtime protocol 变更限定为"在 protocol 中新增 streaming 方法签名，不删除旧方法，不修改 runtime 实现"，Slice C 再删除旧方法并重组实现。
  3. 在 plan 中明确 Slice A 产出什么样的 protocol shape 作为 Slice C 的输入契约。
  4. 考虑是否将 Slice A 和 C 合并为一个 slice，或至少 A 的 runtime protocol 变更是纯 type-only change（不改实现）。
- **修复风险（低）**: 澄清 ownership boundary 即可。
- **严重程度（中）**: 不修复会导致 implementation agent 在 slice 边界做本应属于另一 slice 的决定。

### DS-003-未修复-中-Slice-C-D-循环依赖

- **位置**: Slice C 停止条件（line 236-239）与 Slice D 整体
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: Slice C 步骤 6 说"默认 core runtime 不保留 durable job store；若 awaiting 需要保留 row，必须先在 Slice D 说明最小字段和理由"。Slice C 停止条件说"如果移除 job store 会破坏 awaiting poll/resolve 且没有 lightweight replacement，删除前必须停止并升级到 Slice D 设计裁决"。但 Slice D 在 Slice C 之后执行。
- **反例/失败场景**: Implementation agent 在 Slice C 中删除 job store (`.dayu/fins_ingestion/jobs/<job_id>.json`)，但发现 wait adapter 在 Slice D 中依赖 `runtime.read_job(job_id)` 做 poll。agent 有两个坏选择：(a) 在 Slice C 中保留 job store "以防万一"，但 plan 的 non-goal 要求删除它；(b) 在 Slice C 中删除 job store，让 Slice D 的 wait adapter 测试全部失败，等于把 Slice D 变成了"从零重建 awaiting"的大 slice。
- **为什么有问题**: Plan 把"裁决是否需要 durable row"推迟到 Slice D，但"删除 job store"在 Slice C。这创造了一个逻辑死锁：Slice C 不能安全删除 job store 直到 Slice D 决定 lightweight replacement 的形态；但 Slice D 在 Slice C 之后，且 plan 鼓励 Slice C 先删除。
- **直接证据**:
  - Slice C 步骤 6 (line 218): "明确裁决是否保留任何 durable row。默认 core runtime 不保留 durable job store"
  - Slice C 停止条件 (line 237-238): "如果移除 job store 会破坏 awaiting poll/resolve 且没有 lightweight replacement，删除前必须停止并升级到 Slice D 设计裁决"
  - Slice D 的整个 purpose 是设计 lightweight replacement
  - 控制文档 DS-001 finding 指出的：lightweight handle 在 Slice D 才定义，但 Slice C 需要知道 handle 形态才能决定删除什么
- **影响**: Implementation agent 在 Slice C 中要么保守保留 job store（违反 non-goal），要么激进删除（可能在 Slice D 中发现需要恢复部分 job store 能力，造成返工）。
- **建议改法和验证点**:
  1. 将 Slice D 的 lightweight observation handle 最小 typed contract 提前到 Slice C 之前或 Slice C 的 precondition 中定义。
  2. 或者重新排序：先做 Slice D 的 contract-only 部分（只定义 handle 契约和 wait adapter 新 API，不做实现），再做 Slice C 的 job store 删除，最后在 Slice D 中完成 wait adapter 实现。
  3. 或者将 Slice C 的 job store 删除降级为"标记 deprecated + 不再被 direct path 使用"，真正的删除移到 Slice D 之后，等 awaiting 迁移完成再清理。
- **修复风险（中）**: 需要重新思考 C/D 的边界或顺序。
- **严重程度（中）**: 可能导致 implementation agent 在 Slice C 做错误决策或 Slice D 需要大量返工。

### DS-004-未修复-中-wait-adapter-崩溃恢复缺口

- **位置**: Slice D 整体设计；plan 未讨论 wait adapter 进程崩溃/重启场景
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: Plan 讨论 lightweight observation handle 和 wait adapter poll/resolve，但从未提及 Host 重启（或 Fins runtime 进程崩溃）后，orphan 的 awaiting observation handle 如何被发现和恢复。
- **反例/失败场景**: 场景：LLM 调用 Fins download tool → tool 返回 `ToolAwaitingOutcome(EXTERNAL_JOB)` → Host 创建 wait record → wait adapter 开始 poll lightweight handle。此时 Host 进程重启。重启后 Host recovery 扫描 WAITING runs，但 wait adapter 持有的 lightweight handle 如果只是 in-memory reference（例如 `asyncio.Event` 或内存 dict key），handle 已经丢失，wait adapter 无法继续 poll。Run 永远卡在 WAITING 状态。
- **为什么有问题**: 当前代码的 durable job record 提供了最小恢复能力——wait adapter 可以通过 `runtime.read_job(job_id)` 重新发现 job 并继续 poll。如果 lightweight handle 没有持久化（plan 对此沉默），这个恢复能力就丢失了。Engine design（`docs/engine/design.md` line 386-388）明确说"恢复不是恢复旧 Engine 实例；调用方在外部长事务结束后构造新的 `AgentRunRequest`"——这要求 Host wait adapter 能独立于 Engine 恢复等待状态。
- **直接证据**:
  - Plan 全文搜索不到 "recovery"、"restart"、"crash"、"orphan" 在 lightweight handle 上下文中的讨论
  - `docs/host/design.md` 多处提到 Recovery 负责 "Host startup scan、旧 Attempt `LOST` 收口和可恢复 Run 的新 Attempt 创建"——等待中的 Run 也需要 recovery
  - 当前 `dayu/fins/ingestion/wait_adapter.py` 的 poll 依赖 `runtime.read_job(job_id)`——这是一个 durable ref
  - Plan DS-001 指出的：lightweight handle 可能没有 durable row
- **影响**: 如果 lightweight handle 没有持久化，Host 重启后所有 WAITING Fins ingestion Runs 变成不可恢复的 orphan。这比当前"过重"的 durable job 系统更差，因为它失去了恢复能力。
- **建议改法和验证点**:
  1. 在 Slice D 中显式裁决：lightweight handle 是否需要跨进程/跨重启持久化。如果不需要（因为 Fins ingestion 是同步本地操作，只在 tool awaiting path 中临时存在），必须在 plan 中说明这个限制并记录为 deferred risk。
  2. 如果需要持久化，lightweight handle 的最小 durable 形态必须在 plan 中定义（例如一个最小 SQLite row 或文件系统 marker，只包含 handle id + status）。
  3. 新增 recovery 场景测试：wait adapter 在 poll 中被中断后重启，能重新发现并继续 poll 或正确标记 LOST。
- **修复风险（中）**: 需要 lightweight handle durability 的设计裁决。
- **严重程度（中）**: 可能导致生产环境中 awaiting runs 不可恢复。

### DS-005-未修复-低-FinsEvent-contract-欠规格

- **位置**: Slice A 实施步骤 1
- **问题类型**: 契约缺失
- **当前写法**: Plan line 127 说"定义 NEW direct `FinsEvent` contract，至少包含 `PROGRESS` 与 `RESULT`。优先复用现有项目内等价 contract；若不存在，新增 Fins-facing typed dataclass / enum"。但没有给出完整的字段定义、事件类型枚举、或 RESULT 事件如何映射退出码。
- **反例/失败场景**: Implementation agent 进入 Slice A 后，需要决定 `FinsEvent` 的完整 shape：PROGRESS 携带什么 payload？RESULT 如何区分 success/failure/cancelled？是否需要单独的 FAILURE 和 CANCELLED 事件类型？如果 agent 选择的事件模型与 Slice B CLI consumption 的预期不匹配（例如 CLI 期望 RESULT.event_type 来区分 exit code，但 contract 只给了 RESULT），Slice B 需要返工。
- **为什么有问题**: `FinsEvent` 是 Slice A 的核心交付物，也是 Slice B CLI 的输入契约。不给完整 typed contract 就让 implementation agent 自行设计，可能导致 A/B 之间的契约不匹配。项目编码约束要求"禁止使用 `Any`、无类型参数"——如果 contract 在 plan 中不完整，implementation agent 可能为了赶进度而用宽松类型。
- **直接证据**:
  - Plan line 127: "至少包含 `PROGRESS` 与 `RESULT`"——这是最小要求，但不足以 code-generation
  - Plan 没有定义 FinsEvent 的 dataclass 字段
  - OLD agent 代码（plan line 47-48）的 `FinsEvent` 有 `FinsEventType.PROGRESS` 和 `FinsEventType.RESULT`——可以作为参考但没有被 plan 显式引用为复用目标
- **影响**: Slice A 和 B 之间的 contract mismatch 需要在 review 中修复，增加返工。
- **建议改法和验证点**:
  1. 在 plan 中给出 `FinsEvent` 的最小 typed contract：至少包含 event_type enum（PROGRESS, RESULT, FAILURE, CANCELLED 或等价）、各类型的 payload 字段、RESULT exit code 映射规则。
  2. 明确是否复用或参考 OLD agent 的 `FinsEvent` 类型（`FinsEventType.PROGRESS` / `FinsEventType.RESULT`）。
  3. 在 Slice A 和 B 的 handoff 中显式引用这个 contract 作为 shared truth。
- **修复风险（低）**: 只需要在 plan 中补充 typed contract 定义。
- **严重程度（低）**: 不影响 plan 的整体方向，但增加了 implementation 中的设计负担。

### DS-006-未修复-中-测试缺口汇总

- **位置**: Slices A-D 预期测试；测试迁移计划 (line 329-345)
- **问题类型**: 测试缺口
- **当前写法**: Plan 列出了每个 slice 的预期测试，但以下关键场景缺少显式测试覆盖：

  **(a) Stream no-result (无 RESULT 事件)**:
  - Plan line 131 (Slice B 步骤 2): "stream 结束但没有 result 时失败"
  - 但 Slice B 预期测试 (line 179-184) 没有显式列出 "stream yields PROGRESS events but ends without RESULT" 测试用例
  - Slice A 的 terminal RESULT 定义 (line 130) 只说"失败用 typed failure result 或异常边界收口"——但没有定义 stream 正常结束（`StopAsyncIteration`）但没有 RESULT 时的行为

  **(b) Wait adapter poll 失败/retry**:
  - Slice D 预期测试 (line 268-274) 提到 "保留 wait adapter terminal/lost/abandon 覆盖"
  - 但没有显式列出：poll observation source 抛异常、poll 超时、poll 返回 transient error 时的重试/退避行为测试
  - 当前 wait adapter 通过 `runtime.read_job(job_id)` 做 poll——如果 lightweight handle 替换了 job_id，新的 poll 协议需要定义 transient vs permanent failure 分类

  **(c) 并发 cancel + stream close race**:
  - Plan 讨论 cancel（Slice B 步骤 3: "第一次 Ctrl+C 按现有 CLI exit-code policy 取消当前 stream task"）
  - 但没有讨论：cancel 与 stream 自然结束的 race condition（cancel 在 terminal RESULT 已产出但尚未被 CLI 消费时到达）
  - 当前代码 `_wait_for_terminal_handling_sigint` 处理了这个 race——新的 stream-based cancel 需要等价覆盖

  **(d) Storage side effects 测试**:
  - Slice C 步骤 4 说"确保所有 storage writes 仍只通过 `dayu.fins.storage` repositories"
  - Slice C 预期测试 (line 224) 提到 "保留 ticker normalization、download/upload/preprocess storage side effects"
  - 但没有显式测试：CLI direct stream 路径不会绕过 storage repositories 直接写文件

  **(e) Redaction/leakage 边界测试**:
  - Slice C 步骤 5 提到 "leakage guards：user-facing events 不得包含 absolute upload paths、raw provider payload、financial document body 或 large tool result"
  - Slice A 预期测试没有显式列出 redaction/leakage 测试
  - Plan residual risk R3 (line 372) 把 redaction policy 推迟到 future work unit——但当前 plan 仍然要求 bounded progress/result，所以至少需要基本泄漏边界测试

- **为什么有问题**: 这些测试缺口中的 (a)(c)(e) 直接对应 plan 自己声明的 success signal 或 stop condition——如果不测试，就无法证明 plan 的目标达成了。(b)(d) 是实现正确性的关键边界。
- **直接证据**:
  - Plan success signal line 72-77: 六个 direct command 都能以 `RESULT` 收口、Ctrl+C 取消当前 async stream——但没有 stream-no-result 和 cancel-race 测试
  - Plan stop condition line 366: "不得让 CLI 或 Service 绕过 `dayu.fins.storage` 仓储协议直接散落读取财报文件"——但没有对应的边界测试
  - Slice C 步骤 5 line 218: "保留 bounded result summaries 和 leakage guards"——但没有对应的泄漏测试
- **影响**: 关键 failure mode 没有测试覆盖，可能在 review 或生产中发现回归。
- **建议改法和验证点**:
  1. Slice A 或 B 增加: stream yields only PROGRESS then ends → CLI fails with clear error
  2. Slice B 增加: cancel arrives after terminal RESULT yielded but before CLI consumes → terminal result NOT overwritten by cancel
  3. Slice D 增加: poll observation source transient failure → retry; permanent failure → LOST
  4. Slice A 或 C 增加: FinsEvent payload does not contain absolute paths, raw provider payload, financial document body
  5. Slice C 增加: CLI direct stream path writes only through `dayu.fins.storage` repositories
- **修复风险（低）**: 在 plan 中补充测试用例列表即可。
- **严重程度（中）**: 测试缺口覆盖了 plan 自己声明的 success signal 和 stop condition。

### DS-007-未修复-低-Slice-E-README-sync-时机问题

- **位置**: Slice E (line 292-325) 与 Slice A 的 README 触发规则 (line 143-147)
- **问题类型**: 切片过粗
- **当前写法**: Slice E 是"README, design-adjacent docs, and tests synchronization"，在所有实现 slice 之后执行。但 Slice A 的 README 触发 (line 143-147) 说"修改 `dayu/service/` 时检查 `dayu/service/README.md`；修改 `dayu/fins/` 时检查 `dayu/fins/README.md`"。
- **反例/失败场景**: Slice A 引入了新的 `dayu/fins/direct_events.py` 模块和新的 Service streaming API。按照 README 触发规则，这应该触发 `dayu/fins/README.md` 和 `dayu/service/README.md` 的更新。但 plan 把实际 README 编辑推迟到 Slice E。如果 Slice A-D 的实现引入了 README 需要描述的概念（例如新的 `FinsEvent` contract），但 README 直到 Slice E 才更新，中间 slices 的 review agent 看不到 README 同步状态，无法判断 README 描述是否与代码事实一致。
- **为什么有问题**: README 触发规则的设计意图是让 README 与代码变更保持同步——把 README 编辑集中到最后一个 slice 违反了这一意图。中间 slice 的 review 缺少 README 作为上下文。
- **直接证据**:
  - Slice A line 143-147 触发 `dayu/service/README.md` 和 `dayu/fins/README.md` 检查——但 Slice E 才执行编辑
  - 项目 CLAUDE.md README 触发规则: "修改 `dayu/fins/` 修改 -> 检查并按需更新 `dayu/fins/README.md`"
  - Slice E line 307: "除非 implementation 实际改变 public boundaries，否则保持 Host/Engine design 文案不变"——这个判断在 Slice A 就应该做
- **影响**: README 与代码的同步窗口被延迟，中间 slices 的 review agent 缺少 README 作为真源。如果 Slice A 引入的新概念在 README 中没有体现，review 可能漏掉边界问题。
- **建议改法和验证点**:
  1. 将 README 更新分散到各 slice：Slice A 更新 `dayu/fins/README.md` 和 `dayu/service/README.md` 中与 direct event contract 相关的内容；Slice B 更新 `tests/README.md` 的 CLI test 描述；Slice D 更新 awaiting 相关 README 描述；Slice E 只做 cross-README consistency check。
  2. 或者保持 Slice E 集中编辑，但要求每个 slice 的 completion signal 包含"README 影响评估"（不要求实际编辑），确保 review agent 能看到 README gap。
- **修复风险（低）**: 调整 README 编辑时机即可。
- **严重程度（低）**: 不影响实现正确性，但影响 review 效率。

## Final Plan Review Conclusion

**结论: `pass-with-risks`**

### 通过理由

Plan 的核心设计方向是正确的：
1. 真正替换了 PR #143 的 durable Fins job sidecar 前提——CLI direct 改为普通 `AsyncIterator[FinsEvent]`，非目标明确排除 sidecar JSONL、per-job sequence、terminal fallback 和 `request_cancel(job_id)`。
2. Host/Engine 设计边界被严格遵守——不改 Host durable schema、EventLog、Run/Attempt、Engine ToolExecutor 或 ToolAwaitingOutcome union。
3. `ToolAwaitingOutcome(EXTERNAL_JOB)` 被正确保留，等 semantic 与 CLI direct 解耦。
4. Slice 划分总体合理：A（contract + Service boundary）→ B（CLI consumption）→ C（runtime core）→ D（tool awaiting）→ E（README sync），stop condition 明确。
5. 测试迁移计划覆盖了主要测试文件的改写方向。

### Risk Summary

8 findings: 1 高, 4 中, 3 低。核心风险集中在：

- **DS-001 (高)**: Lightweight observation handle 欠规格——这是 Slice D 的核心设计对象，但没有给出最小 typed contract。Implementation agent 无法 code-generation-ready 进入 Slice D。
- **DS-002/DS-003 (中)**: Slice A/C 共享同一模块但职责边界模糊，Slice C/D 存在循环依赖——可能导致 implementation agent 做错误的删除/保留决策。
- **DS-004 (中)**: Wait adapter 崩溃恢复缺口——如果 lightweight handle 没有持久化，Host 重启后 WAITING runs 可能 orphan。
- **DS-006 (中)**: 测试缺口覆盖了 plan 自己声明的 success signal（stream-no-result, cancel race, storage boundary, leakage guard）。

### 建议后续动作

1. Controller 裁决 DS-001: 在进入 implementation 前补充 lightweight observation handle 的最小 typed contract（至少 handle 类型、poll API 签名、是否 durable）。
2. Plan author 修复 DS-002/DS-003: 澄清 Slice A/C 的 ownership boundary 和 C/D 的顺序依赖。
3. Plan author 修复 DS-004: 对 wait adapter recovery 场景做显式裁决（需要/不需要 durable）。
4. Plan author 修复 DS-006: 在测试迁移计划中补充缺失的测试用例。
5. DS-005, DS-007, DS-008 为低严重度，可在 implementation 中自然收敛，建议在 plan 中做小幅澄清即可进入 implementation gate。
