## Findings

### 1-未修复-[中]-`target` 事实的 context/continuation 被错误地按 resources target 分组，合法 Inline XBRL 会丢失 context
- **入口/函数**：`DefaultFinsRuntime.create(...).get_read_runtime().query_original_facts` → `OriginalStructure.query_facts` → `OriginalStructure.reference` / `OriginalStructure.__init__` 的 ID 索引；同样影响 `read_original_structure` 中 fact 的 `continuation`。
- **文件(行号)**：`dayu/fins/processors/original_content.py:189`（`self.ids` 以 `(self.target(index), id)` 建键）、`:207`（context 校验用 target 分组查找）、`:227-244`（`target()` 把 `ix:resources`/`ix:continuation` 的 target 也当作 ID 分组）、`:451`（context/continuation 查找同样带 target 键）、`:491`（continuation 下一跳查找）、`:511-533`（`resource_target_*` 依赖 resources target）；测试 `tests/fins/test_original_read_contract.py:121-128` 固化了错误预期。
- **输入场景**：符合 Inline XBRL 1.1 的多 Target Document 文档，例如 `<ix:nonNumeric name="c:Flag" contextRef="C" target="other">`，context 位于正常 `<ix:resources><xbrli:context id="C">...`（`target` 不允许出现在 `ix:resources`；context/unit 由 conforming processor 自动纳入各 target document）。我用 spec-conforming 合成输入复现：
  ```text
  <html xmlns:z="http://www.xbrl.org/2013/inlineXBRL" xmlns:c="urn:concept"
        xmlns:x="http://www.xbrl.org/2003/instance"><body>
  <z:resources><x:context id="C"><x:period>p</x:period></x:context></z:resources>
  <z:nonNumeric name="c:Flag" contextRef="C" target="other">☐</z:nonNumeric>
  ```
- **实际分支**：fact 的 `target()` 返回 `"other"`；context 的 `target()` 走到无 target 的 `ix:resources` 后返回 `""`；`ids` 键为 `("", "C")`，而 `reference` 查找 `("other", "C")`，未命中。
- **预期行为**：按 Inline XBRL 规范，`contextRef`/`continuedAt` 应在当前 inline document 内按 exact ID 解析并做元素类型校验；`target` 只是 fact 的 Target Document 元数据（raw/origin），不是 ID 命名空间。`ix:resources`/`ix:continuation` 不允许 target，不能据此建立分组；context/unit 自动进入各 target document。
- **实际行为**：公开 API 返回 `target_raw="other"`、`target_origin="explicit"`，但 `context.status="unresolved"`、`reason="target_not_found"`、`parse_status="partial"`；continuation 查找同样失败。直接复现输出：
  ```text
  target_raw other origin explicit
  context unresolved target_not_found parse partial
  ```
- **直接证据**：上述代码路径与公开入口复现；FRC《UKSEF Developers' Guide — Multiple Target Documents 2023》v1.1 第 4 页原文（`https://media.frc.org.uk/documents/UKSEF_Developers_Guide_-_Multiple_Target_Documents.pdf`）："The target attribute MAY be applied to the 'ix:references' container element and to all data mark-up elements in the 'ix' namespace (ix:nonFraction, ix:nonNumeric, ix:footnote). It MUST NOT be applied to the 'ix:resources' container element – a conforming Inline XBRL processor MUST include all required context and unit declarations in the target document(s) automatically. It MUST NOT be applied to 'ix:continuation' or 'ix:exclude' elements."（本地保存 PDF 已读取核对）。现有测试 `mode="target"` 期望 unresolved，正是该错误模型的镜像。
- **影响**：合法的多 Target Document 文档（如 UKSEF 风格）会把所有带 target 的 fact 的 context/continuation 误报为未决，丢失 R1 要求的 context/target/原文证据，并错误标记 `partial`；当前 SEC/CN/HK anchor 样本没有 target 属性，所以现有样例未暴露。不是数据损坏或版本混用。
- **建议改法和验证点**：删除 `target` 参与 ID 键/查找的逻辑；ID 按当前资产内 exact ID + 期望元素类型解析（重复 ID 才 ambiguous）；保留 fact 的 `target_raw`/`target_origin` 作为元数据；移除或按 spec 重新定义 `resource_target_*`（resources target 非法）；更新 `test_original_read_contract.py` 的 target mode 为“context resolved、target explicit”，增加带 target 的 fact/continuation 用例，并用真实公开入口验证。
- **修复风险（低/中/高）**：中（target 语义、测试和可能的 README/plan 说明需同步；当前真实 anchor 无 target，回归面较小但需跑全量 affected tests）。
- **严重程度**：中。

### 2-未修复-[中]-失败 ref/table_ref 的 cross-document 诊断会构建未读过的 processor
- **入口/函数**：`FinsReadRuntime.read_section` / `get_table` 的 KeyError 诊断 → `_diagnose_cross_document_locator` → `_get_cached_processor_borrow_for_diagnosis` → `borrow.processor` → `_get_convenience_processor`。
- **文件(行号)**：`dayu/fins/tools/read_runtime.py:2824-2829`（方法 docstring 承诺“不主动构建新 processor、不扫描磁盘”）、`:2844-2857`（对每个 cached entry 直接访问 `borrow.processor`）、`:3317-3328`（`entry.processor is None` 时构建）、`:3024-3028`（新 source entry 可以以 `processor=None` 发布）。
- **输入场景**：长生命周期 Python runtime 先 `list_document_assets`/`read_original_text` 枚举文档 B（entry 已发布、processor 仍为 `None`），随后对文档 A 调用 `read_section(ref="s_9999")` 或 `get_table` 不存在的 ref，触发诊断。
- **实际分支**：诊断遍历 cache，跳过当前 doc A，借用文档 B 的 entry；`borrow.processor` 发现 `None` 后同步构建 B 的 primary processor，然后才执行 `read_section/read_table` 尝试。
- **预期行为**：诊断只消费已经构建且 revision 匹配的 processor；未构建 entry 应跳过，不能为了“是否存在该 locator”触发新的解析。
- **实际行为**：对未读过的文档 B 执行完整 processor 构建。窄复现（真实 Fs，`workspace/tmp/review-diag-repro/test_diag_builds_processor.py`）：
  ```text
  after enumerate create_count 0 []
  after failed read create_count 2 ['version-one', 'payload:doc-2']
  ```
  `payload:doc-2` 的 processor 完全由失败 ref 的诊断路径创建。
- **直接证据**：上述行号与复现；`_CountingProcessorRegistry.created` 的 label 证明第二次构建对应 doc-2，而不是当前 read 的 doc-1。诊断 borrow 没有传入调用方 cancellation token，因此该构建也不观察本次取消。

- **建议改法和验证点**：在 `_diagnose_cross_document_locator` 进入 borrow 前检查 `entry.processor is None` 并跳过；或增加 non-building accessor（返回 `DocumentProcessor | None`），诊断只读已构建实例。增加“先枚举 B 再对 A 用坏 ref，registry 构建次数不增加”的回归测试；保持 stale revision 诊断行为。
- **修复风险（低/中/高）**：低（诊断提示可能变少，符合其零构建成本约束；不影响正常读路径）。
- **严重程度**：中（直接 Python 公共路径；生产 process 路径通常缓解）。

### 3-未修复-[中]-HTML 可省略 `</head>` 未按规则闭合，合法文档的 body 父链静默错误
- **入口/函数**：`read_original_structure` / `query_original_facts` 的 `OriginalStructure._scan` 与 `_close_optional`。
- **文件(行号)**：`dayu/fins/processors/original_content.py:44-46`（`_OPTIONAL_AT_EOF` 含 head/body，但只在 EOF 处理）、`:320-323`（HTML 模式下每个 start tag 调用 `_close_optional`）、`:371-395`（可选闭合规则缺少 `head` → `body`，也缺少 optgroup/rt/rp/colgroup 等标准规则）。
- **输入场景**：合法 HTML 省略 `</head>`，例如 `<html><head><title>t</title><body><p>x</p></body></html>`（HTML 规范允许 head 结束标签在 body 开始前省略；浏览器/HTML5 解析把 body 作为 html 子节点）。
- **实际分支**：`_close_optional(stack, "body", position)` 对 current=`head` 没有任何闭合条件，body 被压入 head 的子树；随后 `</body>` 显式闭合，`</html>` 才把 head 以 `closure="rule"` 弹出。
- **预期行为**：body 的 parent 应为 html；head 在 body 开始处以规则闭合；结构 `parse_status` 不应因此声称 body 属于 head。
- **实际行为**：复现输出中 body 的 `parent` span 为 head 的 opening（start 6/end 12），`parent_status="resolved"`、`parse_status="complete"`、`diagnostics=[]`；即所有 body 后代节点（段落、表格、fact 节点）都得到错误的 head 祖先。
- **直接证据**：上述窄复现（`OriginalStructure.read_structure`，真实 `LocalFileSource`）与 HTML 可省略结束标签规则；代码对 table row group、li、p 等实现了可选闭合，说明这是遗漏而非有意保留原始 token 栈。
- **影响**：省略 `</head>` 的合法 HTML 会静默给出错误的物理父链/ancestor，且声称完整解析；原始 span 仍可回读，因此不是内容丢失，但 R1 的物理结构/局部关系契约不成立。当前 7 份 anchor HTML 都显式闭合 head，未在真实样例暴露；同类缺失还可能导致 colgroup/optgroup/rt/rp 等边界错误。
- **建议改法和验证点**：在 `_close_optional` 增加 `head` 遇到 `body` 的规则闭合，并补齐本轮声称支持的 HTML 可选结束标签规则；增加 `head` 省略闭合、colgroup/optgroup 等 owner 测试，断言 parent/closure/parse_status；跑 SEC/PDF affected 回归确认 section 边界不退化。
- **修复风险（低/中/高）**：中（parser 闭合规则变化可能影响已有 section/table 边界，需要完整 affected tests）。
- **严重程度**：中（当前真实 anchor 未触发，但合法输入会静默错误父链）。

### 4-未修复-[低]-原始工具对不存在文档/文件返回 `file_not_found` 且提示验证 ref/table_ref，违背 accepted plan 的 `not_found` 与重新枚举动作
- **入口/函数**：四个新工具的 `_invoke_fins_read_business` / process target → `_execute_fins_read_business_value` → `_route_fins_read_business`；runtime `_original_content`/`_source_asset`。
- **文件(行号)**：`dayu/fins/tools/fins_tools.py:88`（`_FILE_NOT_FOUND_HINT` 只提 ticker/document_id/ref/table_ref）、`:1238-1246`（`FileNotFoundError` 统一映射为 `file_not_found` 与该 hint）；`dayu/fins/tools/read_runtime.py:209-219`（`get_content_identity` 对未列入 snapshot 的 filename 抛 `FileNotFoundError`）、`:3265-3272`（`_original_content` 不转换为 typed not_found）。
- **输入场景**：已从 `list_document_assets` 取得合法 hash，但传入一个形状合法、不在 snapshot 清单内的 `filename="nope.html"`；或文档已被删除。
- **实际分支**：storage snapshot 抛 `FileNotFoundError`，tool 边界走 `except FileNotFoundError`，返回 `error="file_not_found"`、`message="source snapshot 不包含该业务文件"`、`hint="Verify the ticker, document_id, ref, or table_ref and retry."`。
- **预期行为**：accepted plan §4.2 要求合法 namespace 内资源不存在/文件不在清单明确返回 `not_found`，并提示从当前 namespace 重新枚举 exact 资产；原始工具不接收 ref/table_ref，错误恢复动作应指向 `list_document_assets`。

- **建议改法和验证点**：在 runtime owner 处捕获 missing document/file（由 `get_content_identity`/snapshot 抛出）并抛 `FinsReadBusinessError(ErrorCode.NOT_FOUND, ...)`，hint 明确“重新调用 list_document_assets 并原样使用新的 filename/expected_sha256”；或至少在 tool 边界按工具名映射，但 owner 应收敛在 runtime。增加缺失文档与缺失文件的 tool-level 测试，断言 code/hint，并区分 source decode/corruption。
- **修复风险（低/中/高）**：低（仅新工具错误分类；不影响既有九工具）。
- **严重程度**：低。

## Open Questions

- **`concepts` 出站 schema 省略 `items` 是否可被实际 LLM provider 接受**：outbound 路径（`dayu/engine/runners/openai/payload.py:206-231`）原样透传 properties；`concepts` 只有 `type=array,minItems,maxItems,description`，没有 `items`，因为共享 `dayu/runtime/tool_call_projection.py:597-615` 的数组 items 校验只支持 scalar，对象 items 会被 Host 参数校验拒绝（`allow_array_items=False`）。我实际构建并序列化了 13 个 definitions，确认 outbound 无 `items`；JSON Schema 语义下 itemless array 合法，`jsonschema` 接受对象数组；Host 参数投影原样接受，runtime owner `query_original_facts`（`read_runtime.py:3164-3184`）严格拒绝非对象、额外键、缺失/非字符串字段。因此**内部已支持调用链可用，未确认缺陷**；不能由 Host 手工构造请求单独证明 provider 出站可用，需后续用真实 provider/真实模型做一次 outbound 调用，或改为在 Host 参数投影中支持对象 items 并显式声明。若 provider 拒绝 itemless array，会表现为工具调用无法发起而不是静默错误，影响为功能不可用。
- **`query_original_facts.parse_status` 的 continuation 完整性是否应 asset-wide**：构造 2 个 Flag occurrence、第一页 limit=1、第二 occurrence `continuedAt="not-there"`，第一页返回 `total_matches=2`、`parse_status=complete`、无 diagnostics；第二页才 `partial`。constructor 对 context 引用做了全资产检查（`original_content.py:198-212`），但 continuation 只在返回 facts 的 `reference_partial` 中检查（`:714-726`）。若 `parse_status` 旨在描述当前资产解析可信范围，应把未返回 occurrence 的 continuation 也纳入；若明确为页级描述，应在 LLM-facing 说明中写清。该问题未升级为 finding，等待语义裁决。
- **close 与 lazy build 的窄竞争**：`close()` 文档称 active borrow 可以完成，但 `_get_convenience_processor`/`_original_content`/`_original_structure` 在构建完成后用 `_ensure_open()` 拒绝发布；若 borrow 已取得但首次构建尚未开始，close 先线性化会让该已开始读取抛 `RuntimeError`。现有 `test_cache_publication_before_runtime_close_preserves_active_borrow` 在 close 前已访问 processor，未覆盖此窗口。当前生产 process-backed 工具每次调用后 close，且 close 通常发生在调用结束后；需要确认该竞态是否需按 close 文档语义修复。
- **XML 结构能力判定与 parser 模式不一致**：`original_capabilities` 对 `application/xml`/`text/xml` 声明 `structure_supported=True`，但 `read_original_structure` 仅以 `filename.lower().endswith(".xml")` 决定 XML 模式（`read_runtime.py:3303`）；一个非 `.xml` 后缀、XML media type 的资产会被按 HTML 模式解析。隔离输入未发现此类真实资产；建议统一为同一格式判定 helper 或收紧 capability。
- **enumerated filename 含 `[ ] * ?` 的可读性**：storage 允许这些字符作为单组件文件名，`list_document_assets` 会返回；但 `_validate_original_asset` 拒绝这些字面字符（`read_runtime.py:3220-3238`），因此这类 exact 资产可枚举却不可读。隔离输入未发现此类名称；若存储层允许，应改为 exact 匹配而非 glob 形状拒绝，或由 storage owner 统一限制。
- **target 真实输入覆盖**：7 份 anchor 与 TSM 主件均无 fact `target` 属性（我扫描了副本中的 fact target，0 命中）；Finding 1 基于规范与合成输入，未在真实 UKSEF 类原件上动态验收。若当前产品范围不处理多 Target Document，可在裁决中明确为非目标/延期 owner。
- **LLM-facing 细节**：共享 `_ORIGINAL_DESCRIPTION` 已覆盖主要字段和两层续读，但未逐一给出 `qname.status` 的 `resolved|unbound|ambiguous`、`attribute.quote/duplicate` 的含义；`get_document_sections` 描述未解释新增 `source_asset` 字段（`read_section` 已解释）。这是文档清晰度问题，未作为 finding。
