## Findings

### 1-未修复-低-`_resolve_outcome_json` 中 outcome kind 字符串硬编码，与 `waiting.py` 常量不同源

- **入口/函数**: `dayu/host/wait_callback.py:694` `_resolve_outcome_json` 与 `dayu/host/waiting.py:1527` `_resolve_outcome_json`
- **文件(行号)**: `dayu/host/wait_callback.py:703,709,714,719`
- **输入场景**: 任何 callback completion envelope 的 digest 计算。
- **实际分支**: `wait_callback.py` 的 `_resolve_outcome_json` 使用硬编码字面量 `"completed"`, `"failed"`, `"cancelled"`, `"lost"` 作为 JSON kind 字段值。
- **预期行为**: callback adapter 的 digest material 与 `waiting.py` 中 `DefaultHostResolveWaitService` 的 digest material 完全同源，避免任何可能的漂移。
- **实际行为**: `waiting.py:122-125` 定义了 `_TOOL_FACT_KIND_COMPLETED = "completed"` 等模块级常量，`waiting.py:1527` 的 `_resolve_outcome_json` 使用这些常量。`wait_callback.py:694` 的同名函数使用字面量字符串而非引用同一真源。
- **直接证据**: `wait_callback.py:703` 使用 `"kind": "completed"`；`waiting.py:1537` 使用 `"kind": _TOOL_FACT_KIND_COMPLETED`。两者当前值相同，但不同源。
- **影响**: 若 `waiting.py` 的常量值变更（虽然概率低，因为它们已进入 durable idempotency store），callback adapter 的 digest 会静默漂移，导致本应 replay 的 callback 被误判为 `IDEMPOTENCY_CONFLICT` 或 `DIGEST_MISMATCH`。当前行为正确，风险为 maintainability 而非 correctness。
- **建议改法和验证点**: 将 `waiting.py` 的 `_TOOL_FACT_KIND_*` 常量提升为 `dayu/host/durable/codec.py` 或 `dayu/host/durable/state.py` 中的公共常量，或直接在 `wait_callback.py` 中 import `waiting._TOOL_FACT_KIND_*`（同层模块私有引用可接受）。验证：`test_callback_completed_resumes_with_same_event_sequence_as_direct_resolve` 会因 event sequence 不一致而捕获 digest 漂移。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Residual Risk

- **Stale check 时序窗口**: `resolve_callback` 中 stale check 在 `read_wait_state` 之后、`resolve_callback_wait` 之前执行。如果在 stale check 通过后、resolve 执行前，另一个并发 resolve 将 wait 推进到终态且该 wait 无 deadline/expires，callback 会进入 resolve pipeline 并被幂等吸收为 replay。这是 approved behavior（plan 明确允许 race collapse 到 `INVALID_WAIT_STATE`），但测试未覆盖此并发路径。并发 race 的行为由 `DefaultHostResolveWaitService` 内部保证，Slice 1 不需要额外测试。
- **`_stale_status_or_none` 边界时间解析失败**: 当 `deadline_at` 或 `expires_at` 持久化值为非法 UTC 字符串时，返回 `INVALID_WAIT_STATE`。测试未覆盖此路径。该路径依赖 durable store 写入正确性，属于 low probability / low impact。
- **`resolve_callback_wait` 的 context identity check**: `command.py:836` 要求 `context is not request.context` 时抛出 `INVALID_STATE`。这是防御性检查，adapter 始终传入同一对象。测试未覆盖该防御路径，但它是编程错误检测而非运行时风险。
- **未测试的 adapter 状态**: `INTERNAL_ERROR`（authenticator 抛出非 `TypeError`/`ValueError` 异常）和 `INVALID_WAIT_STATE`（从 resolver 返回的 race 路径）在 adapter 层未被直接测试。`INVALID_WAIT_STATE` 的 race 路径由 `test_resolve_wait_command.py` 中的已有测试间接覆盖。

## Architecture / Contract Alignment Summary

### Host core 只提供 framework-agnostic typed callback contract / adapter ✅

`wait_callback.py` 无任何 Service/UI/Web framework import。`test_wait_callback_adapter_has_no_service_ui_or_web_framework_dependency` 验证无 `dayu.service`, `dayu.ui`, `fastapi`, `flask`, `starlette`, `django`, `aiohttp` 依赖。

### callback 认证优先、typed result/diagnostic、不解析 HostApiError.message ✅

`DefaultWaitCallbackAdapter.resolve_callback` 优先调用 `_authenticate`；所有错误路径映射为 `WaitCallbackAdapterStatus` 枚举和 `diagnostic_code` 字符串，不解析 `HostApiError.message`。`_result_from_host_api_error` 基于 `error.code` 枚举做确定性映射。

### callback / poller / manual resolve 共用 DefaultHostResolveWaitService pipeline ✅

`HostCommandWaitCallbackPort.resolve_callback_wait` 构造 `DefaultHostResolveWaitService` 实例并调用其 `resolve_wait`，与 `command.py:752` 的 `resolve_wait` 函数使用完全相同的 pipeline。adapter 不直接 append EventLog 或修改 Run/Attempt/wait record。

### HostCommandWaitCallbackPort 保留 dispatch wakeup，replay 不重复唤醒 ✅

`command.py:856`: `if result.dispatch_record is not None and not result.idempotent_replay:` — 与 `command.py:779` 的 `resolve_wait` 逻辑完全一致。`test_callback_accept_wakes_dispatch_once_and_replay_does_not_wake_again` 验证 `dispatch_wakes == 1`。

### digest material 与现有 wait resolution 一致 ✅

callback adapter 的 `_callback_payload_digest` 计算 `sha256({"wait_id", "idempotency_key", "outcome"})`，与 `waiting.py:1140` 的 `_wait_resolution_digest` 使用相同 material 结构。`test_callback_completed_resumes_with_same_event_sequence_as_direct_resolve` 间接验证 digest 一致性（event sequence 匹配依赖 idempotency replay 正确命中）。

### public exports 只暴露稳定 Host callback contract ✅

`__init__.py` 导出 `WaitCallback*` 系列类型和 `CallbackWaitResolvePort`/`CallbackWaitResolveResult`/`WaitCallbackStateReadPort`。`HostCommandWaitCallbackPort`（command-layer 实现）未从 `__init__.py` 导出，仅在 `command.py.__all__` 中可见。`test_wait_callback_symbols_are_exported_from_package_root_only` 验证 callback 符号从包根导出但不进入 `dayu.host.api`。

### tests 覆盖 ✅

11 个测试覆盖：completed resume event sequence、dispatch wakeup + replay 不重复、same key different outcome conflict、unknown wait、late cancelled、late lost、stale callback with deadline、no deadline not stale、digest mismatch、auth rejection、EventLog 不变性。与 `test_resolve_wait_command.py` 和 `test_wait_cancel_late_result.py` 共 54 passed。
