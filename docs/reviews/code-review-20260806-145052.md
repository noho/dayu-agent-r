### 1-未修复-高-evidence material boundary 空 refs 处理缺少 pre-compaction 快速失败路径的显式表述

- **入口/函数**: source boundary 构造（Host-internal immutable snapshot）
- **文件(行号)**: `docs/host/design.md` §24.3（line 3361）
- **输入场景**: accepted evidence material 存在，但其 `canonical_evidence_refs` 因上游 bug（例如 `TOOL_RESULT_ACCEPTED` 缺少 envelope / request atom）而为空
- **实际分支**: 设计声明 "任一 evidence entry refs 为空时 typed fail closed，不得丢弃 entry、填入 compact event ref或继续执行"（line 3361）
- **预期行为**: 设计已正确要求 fail closed
- **实际行为**: 设计正确，但 fail closed 的具体触发时刻有二义性：
  - line 3361 描述的是 "material-pack entry 到 durable boundary entry 必须逐项复制并校验等式"，这发生在 boundary 构造阶段
  - line 3441 描述的是 accept 阶段的 "任一 binding、boundary membership或 non-empty检查失败均在 artifact / terminal / Memory 前 typed reject"
  - 两处均可触发 fail closed，但设计未明确哪一处是 canonical owner：若 boundary 构造阶段已经 fail closed，则不应进入 compactor 调用；若推迟到 accept 阶段才发现，则已浪费一次 LLM proposal 调用
- **直接证据**: line 3361 "任一 evidence entry refs 为空时 typed fail closed" vs line 3441 accept 阶段 "每条 refs 必须非空...任一...失败均在 artifact / terminal / Memory 前 typed reject"。两条路径都可以捕获空 refs，但未显式指定 canonical detection point。
- **影响**: 实现者可能在 boundary 构造处 fail（阻止 compactor 调用）或在 accept 处 fail（浪费 proposal），两条路径的行为差异（是否产生 `CONTEXT_COMPACTION_ATTEMPT_REJECTED`、是否消耗 attempt budget、是否进入 repair）不同。当前设计未裁决。
- **建议改法和验证点**: 在 §24.3 增加显式裁决：空 evidence refs 的 canonical detection 必须在 source boundary 构造阶段，不得进入 compactor proposal 调用。或明确说明 boundary 构造阶段只能做 "best-effort preflight"，canonical enforcement 在 accept 阶段——此时须接受可能浪费一次 proposal attempt 的 trade-off。实现 S1 前必须选定一条路径并在 design 中写明。
- **修复风险（低）**: 仅为设计文本澄清，不改变已冻结的 contract。
- **严重程度（高）**: 边界构造 vs accept 阶段的双重 fail 路径可能导致实现分叉和行为不一致；compactor proposal 预算浪费在 design 阶段应被显式排除。

### 2-未修复-中-`PromptLocalProvenanceEntry` 从 singular `accepted_evidence_id` 到 tuple `canonical_evidence_refs` 的 schema 变更缺少完整 type definition

- **入口/函数**: Host-internal provenance mapping
- **文件(行号)**: `docs/host/design.md` line 3361

- **实际分支**: 设计只声明 "PromptLocalProvenanceEntry 只保留 canonical_evidence_refs: tuple[str, ...]，不再保留 singular accepted_evidence_id"，但 `PromptLocalProvenanceEntry` 的完整 type definition 未出现在本文或已修改的任何段落中

- **直接证据**: line 3361 是 `PromptLocalProvenanceEntry` 在 diff 中的唯一出现位置；全文搜索无完整 type definition。
- **影响**: 实现 S1 时可能对 `PromptLocalProvenanceEntry` 的完整字段集、默认值、校验规则产生歧义。该 type 是 evidence material 到 compact input 的桥梁，定义不完整可能导致 evidence refs 在传递中变形或丢失。

- **严重程度（中）**: 不阻塞 S0 完成，但 S1 实现前必须澄清；当前文档不允许实现者在不猜测的情况下正确定义该 type。

### 4-未修复-低-`compactor_input_projection.v2` descriptor schema 名称与 v4 body content 存在版本号 disjunction

- **入口/函数**: compactor input projection artifact descriptor
- **文件(行号)**: `docs/host/design.md` line 9（diff）、line 3487、line 3735
- **输入场景**: 实现者或 operator 通过 descriptor schema 名称判断 projection body 的 schema version
- **实际分支**: descriptor schema 名称 `compactor_input_projection.v2` 保持不变，但其 body 内容从 `CompactInputV3` 升级为 `CompactInputV4`
- **预期行为**: 该 disjunction 在 v3 时代已存在（`.v2` descriptor 承载 v3 body），此次变更未引入新问题
- **实际行为**: `.v2` 名称与 `v4` body 的差距进一步扩大（跨两个 major version），但这是既有模式，design 明确写明此不变量
- **直接证据**: line 9（diff）"compactor LLM proposal 输入投影使用 payload descriptor / artifact schema `compactor_input_projection.v2`。该投影持久化 v4 input"；line 3487 "compactor input projection 继续使用 `compactor_input_projection.v2` descriptor schema，但 body 持久化完整 `CompactInputV4`"；line 3735 table 中 `compactor_input_projection_ref` 的 validation rule 写 "descriptor schema `compactor_input_projection.v2`"。
- **影响**: 仅文档/理解层面的版本号不一致；descriptor 与 body 的 schema version 在代码中通过不同字段表达，不会导致运行时解析错误。但如果有人通过 descriptor 名称猜测 body schema，可能误判。
- **建议改法和验证点**: 可考虑在 descriptor schema 注释中增加 forward reference：`compactor_input_projection.v2` explicitly carries `CompactInputV4` body as of artifact schema 5。或在 design 中显式记录此 disjunction 为 accepted design debt，避免后续 review 重复提出。不是 blocking issue。
- **修复风险（低）**: 仅注释补充。
- **严重程度（低）**: 既有模式延续，不引入新运行时风险。但作为 design debt 应被显式记录。

### 5-未修复-低-compactor proposal 完全为空（零 retain + 零 new fact + null session_summary + 空其它三区）的语义未被显式裁决

- **入口/函数**: Host accept barrier（combined duplicate/information/caps check）
- **文件(行号)**: `docs/host/design.md` line 3405、3438
- **输入场景**: 模型返回全部为空的 proposal：`retained_previous_evidence_fact_labels=[]`、`evidence_facts=[]`、`session_summary=null`、`answer_anchors=[]`、`forward_intents=[]`、`reference_continuity=[]`
- **实际分支**: line 3405 只定义了 "evidence_facts=[] 且 retain selector 非空是合法 retain-only proposal"，未显式裁决两者均为空的 all-clear proposal 是否合法
- **预期行为**: 按 caps 逻辑，combined facts = 0 items ≤ cap，通过。但业务语义上，一个不保留任何 previous fact、不产生任何新 fact、清空 summary、且无 anchor/intent/continuity 的 replacement 等价于清空全部五类 Memory——这可能是合法行为（session reset），也可能是模型幻觉
- **实际行为**: 当前设计隐式允许：combined duplicate/information/caps 对空集合 vacuously 通过，coverage 会将所有 source 标记为 omitted。行为在技术上是定义良好的，但语义意图未裁决。
- **直接证据**: line 3405 仅裁决 retain-only 合法；line 3438 step 5 "只对 combined facts 执行 exact whitespace-canonical duplicate、information、item / char caps 与 policy usage audit"——对空 combined facts 全部 vacuumously 通过。
- **影响**: 低概率边界情况。若 compactor 返回 all-clear proposal（无论原因是模型理解错误还是 session 确实需要 reset），当前 contract 允许其通过。这不是 provenance 污染问题（因为没有 fact 被错误保留或创建），但可能造成意外的 session memory 清空。
- **建议改法和验证点**: S1 实现前决定：all-clear proposal 是合法行为（session reset）还是应该 reject with diagnostic。若合法，在 §24.3 显式记录 "retain + new 均为空且 session_summary=null 是合法 all-clear，等价于清空全部五类 Memory"。若不合法，增加 minimum bar（例如至少一项非空）并在 prompt 中说明。
- **修复风险（低）**: 设计补充，不改变已冻结的核心 provenance contract。
- **严重程度（低）**: 极端边界情况，不影响核心 evidence provenance 正确性。
