- Source label contract preservation
- Test coverage completeness
- Slice granularity and sequencing

- Over-engineering and over-coupling assessment

## Findings

### F-01-未修复-中-field-path composition mechanism underspecified

- **位置**: Implementation Decisions #4 (line 160-166); Slice 1 "Exact changes" (line 189-191); 成功信号 (line 31-32)
- **问题类型**: 不可直接实施
- **当前写法**: Plan 要求 helpers "accept explicit `field_path` strings and return typed values"，并以 `evidence_backed_facts[0].evidence_kind` 为例说明完整 field-path 诊断。但 plan 未定义 helper 签名规范：`field_path` 是独立参数、作为 key 的前缀拼接，还是通过父级 dataclass 的 field name 推导。
- **反例/失败场景**: 当前 `_required_string(data, "claim_text")` 在 `data` 的 field_name 为 `"evidence_backed_facts[0]"` 时，错误信息为 `"claim_text must be string"`，丢失父路径。实现 Agent 需自行设计 field_path 组合机制。若选错方案（例如每个 helper 接受独立 `field_path` 参数但调用侧忘记传），会出现部分错误路径不完整、回归现有 happy-path 测试仍通过但诊断精度倒退的情况。
- **为什么有问题**: 成功信号明确要求 "错误信息包含业务可读 field path"，但 plan 把 field-path 组合机制的设计决策留给了实现 Agent。这不是 implementation detail——它是 parser 诊断质量的核心契约，应在 plan 阶段显式裁决。
- **直接证据**: Plan Decision 4 仅列出 helper 类别名（"required object / nullable object", "required array with max_items" 等），未给出 helper 签名；对比当前代码 `_required_string(source: Mapping[str, JsonValue], key: str) -> str`（`llm_compaction.py:919-934`），仅用 `key` 作为错误标识。
- **影响**: 实施 Agent 跑偏 / 诊断精度倒退 / 后续返工
- **建议改法和验证点**: 在 plan 中显式定义 helper 签名，至少给出一类 helper 的完整签名示例（例如 `_required_string(source, key, *, field_path: str) -> str`），并说明 field_path 是完整路径（如 `"evidence_backed_facts[0].claim_text"`）而非仅 key。如果选择把 field_path 编码在 key 中（即 key = `"evidence_backed_facts[0].claim_text"`），需说明这样做的 tradeoff：key 不再是 JSON key 原文，section parser 构造调用时需自行拼接。
- **修复风险（低/中/高）**: 低 — 只需在 plan 中补充 helper 签名示例和组合规则，不改变整体设计。
- **严重程度（低/中/高/严重）**: 中

### F-02-未修复-中-private typed proposal DTO 过度设计风险

- **位置**: Internal contract (line 142-153); Implementation Decisions #2, #6 (line 158, 168); "Why This Is Not Over-designed" (line 367-370)
- **问题类型**: 过度设计
- **当前写法**: Plan 计划引入 8 个私有 dataclass（`_LLMCompactionProposalVNext` 到 `_LLMDiagnosticProposalVNext`），作为 raw JSON 与 `ConversationCompactOutputVNext` 之间的中间类型层。Plan 声称这是 "the minimum structure needed"（line 370）。
- **反例/失败场景**: 现有 section parser（如 `_fact_candidates_vnext`，`llm_compaction.py:630-649`）已经能从 `Mapping[str, JsonValue]` 直接构造 `EvidenceBackedFactCandidateVNext`（现有的 Host contract candidate 类型）。一个更简替代方案是：仅改进现有 section parser 的 field-path helper 组合机制（使 `_required_string` 能输出完整路径），保持现有类型流转（`raw JSON -> Mapping[str, JsonValue]（局部） -> existing candidate types -> ConversationCompactOutputVNext`），不引入新的私有 DTO 层。
- **为什么有问题**: 
  1. **同构维护负担**：私有 DTO 镜像已冻结的 vNext JSON shape，但 vNext 是带显式 schema_version 的契约（`conversation_compact_output_v1`），暗示未来可能有 v2。两个同构类型层（私有 proposal DTO + 公共 candidate type）在 shape 变更时需同步修改。
  2. **未论证必要性**：Plan 未解释为什么不直接改进现有 section parser 的 field-path 能力，而要引入新类型层。当前 section parser 已经能产出强类型 candidate，唯一的缺陷是 field-path 诊断不完整——这可以通过改进 helper 函数解决，不需要 8 个新 dataclass。
  3. **与 CLAUDE.md 过度设计约束冲突**：CLAUDE.md 要求 "不做过度设计，以最小化满足需求为标准"。引入与现有公共 candidate type 同构的私有 DTO 层，如果仅用于 field-path 诊断，构成过度抽象。
- **直接证据**: 
  - Plan line 142-148: 8 个私有 dataclass 名称列表，无字段定义
  - `llm_compaction.py:630-649`: 现有 section parser 已能直接产出 `EvidenceBackedFactCandidateVNext`
  - CLAUDE.md: "不做过度设计，以最小化满足需求为标准"
- **影响**: 后续返工 / 实施 Agent 产出冗余类型层
- **建议改法和验证点**: 
  - 优先方案：放弃私有 DTO 层，直接改进现有 section parser 的 helper 签名，使 field-path 完整组合。证明 field-path 诊断可以通过改进 helper 实现后，本 WU 的 scope 缩小为 "改进 field helper + 补齐测试"，不再引入新类型。
  - 备选方案：如果 plan 坚持私有 DTO 层，需论证为什么改进 helper 不够（例如 helper 的组合复杂度在嵌套数组项中失控），并在 plan 中显式定义每个私有类型的字段，避免实施 Agent 自行推断。
- **修复风险（低/中/高）**: 中 — 调整方案需要重新评估 Slice 1 的实现范围。
- **严重程度（低/中/高/严重）**: 中

### F-03-未修复-低-双重校验层的职责边界不明确

- **位置**: Risks (line 361-362); Implementation Decisions #5 (line 167)
- **问题类型**: 契约缺失
- **当前写法**: Plan 承认 `ConversationCompactOutputVNext.__post_init__` 与 parser 存在重复校验风险，mitigation 是 "parser validates raw JSON field type/path/enum/count and then still constructs `ConversationCompactOutputVNext` as the final Host contract; shared constants from `dayu.host.compaction` remain the single limits source."
- **反例/失败场景**: 当前 `parse_conversation_compact_output_vnext` 的 `except (KeyError, TypeError, ValueError) as exc` 包装（`llm_compaction.py:573-574`）会捕获 `__post_init__` 的错误并转为 `LLMCompactionProposalError`。如果 parser 层已完整校验，`__post_init__` 的校验变为 dead code。但如果 parser 有遗漏（例如新增 vNext 字段后只更新了 `__post_init__` 未更新 parser），错误来源不一致：parser 漏掉的字段会由 `__post_init__` 捕获，但错误信息是 `"ConversationCompactOutputVNext.schema_version is invalid"` 而非 field-path 诊断。两个校验层之间的职责边界没有显式契约。
- **为什么有问题**: Plan 未定义哪个层是 primary validator，哪个是 safety net。如果 `__post_init__` 被设为 safety net，它的异常 catch 路径应保持不变；但如果 parser 应成为唯一 validator，`__post_init__` 的校验（或至少其异常消息）需要调整。当前 plan 对二者的关系只作为 "risk" 提及，未作为设计决策裁决。
- **直接证据**: 
  - `compaction.py:1582-1598`: `ConversationCompactOutputVNext.__post_init__` 的完整校验逻辑
  - `llm_compaction.py:573-574`: `except (KeyError, TypeError, ValueError) as exc` 包装
  - Plan line 361-362: 仅作为 risk 提及，未给出设计决策
- **影响**: 实施 Agent 跑偏 / 错误来源不一致
- **建议改法和验证点**: 在 plan 中显式裁决：parser 是 primary validator（产出 field-path 诊断），`__post_init__` 是 safety net（仅在不应该发生的 parser bug 时触发）。建议 `__post_init__` 的异常消息保持不变（作为内部一致性错误），parser 的异常消息使用 field-path 格式。在 Slice 3 中确认 parser 覆盖了 `__post_init__` 的所有校验维度后，保留 `__post_init__` 不变。
- **修复风险（低/中/高）**: 低 — 只需在 plan 中补充一句话裁决。
- **严重程度（低/中/高/严重）**: 低

### F-04-未修复-低-`json.loads()` 返回 `Any` 的类型收窄路径未提供具体模式

- **位置**: Implementation Decisions #3 (line 159-160); Slice 1 stop condition (line 230-232)
- **问题类型**: 不可直接实施
- **当前写法**: Plan 要求 "Keep `json.loads(...)` at the raw external boundary, then immediately validate top-level object and recursively read fields into typed private dataclasses. Do not use `cast(...)` to bless parsed JSON." Stop condition: "If pyright requires introducing `Any`, `object`, untyped parameters, or a broad `cast(...)` to make the parser type-check, stop and redesign."
- **反例/失败场景**: Python 的 `json.loads(raw)` 返回类型为 `Any`。Plan 的"立即 validate"策略描述正确但缺少关键实现模式。例如：`parsed = json.loads(raw)` 为 `Any`，之后 `isinstance(parsed, dict)` 可以将类型 narrow 到 `dict[Any, Any]`（或 `dict[str, Any]`），但从 `dict[str, Any]` 到 `Mapping[str, JsonValue]` 需要逐个值校验。如果实现 Agent 未意识到 `isinstance(parsed, dict)` 不会自动将值类型 narrow 到 `JsonValue`，可能写出通过 pyright 但实际不安全的代码（例如在中间步骤引入 `Any`）。
- **为什么有问题**: Plan 正确识别了问题但未提供类型收窄的参考模式。这个模式是 parser 类型安全的核心——如果收窄路径写错，要么 pyright 报错（触发 stop condition 但浪费时间），要么引入隐性 `Any`（不触发 stop condition 但留下弱类型）。
- **直接证据**: 
  - `json_value.py:22-29`: `JsonValue` 是递归联合类型
  - `llm_compaction.py:590-595`: 当前代码使用 `parsed = json.loads(raw)` + `isinstance(parsed, Mapping)` + `cast(Mapping[str, JsonValue], parsed)` 
  - Plan line 231-232: stop condition 针对 pyright 报错，但未针对 "通过 pyright 但不安全" 的路径
- **影响**: 实施 Agent 跑偏 / 引入隐性 `Any`
- **建议改法和验证点**: 在 plan 中补充一个类型收窄参考模式，例如：
  ```python
  parsed = json.loads(raw)
  if not isinstance(parsed, dict):
      raise ...
  # 然后对每个 key 的 value 用 isinstance 逐层收窄到 JsonValue 联合成员
  ```
  并说明：在递归解析过程中，每个 JSON 值都需通过 `isinstance` 显式收窄到 `JsonValue` 的某个具体成员类型，不得使用 `cast` 或 `# type: ignore` 跳过。
- **修复风险（低/中/高）**: 低 — 补充参考模式不改变设计。
- **严重程度（低/中/高/严重）**: 低

### F-05-未修复-低-私有 DTO 字段结构隐式依赖现有代码反推

- **位置**: Internal contract (line 142-153); Slice 1 "Exact changes" (line 187-189)
- **问题类型**: 不可直接实施
- **当前写法**: Plan 列出私有类型名称（`_LLMCompactionProposalVNext` 等），但未定义各类型的字段名、类型和必填性。Plan 称这些类型 "mirror the already frozen vNext output JSON shape"（line 369）。
- **反例/失败场景**: 实现 Agent 需从现有 section parser（`llm_compaction.py:611-762`）反推每个私有类型应包含哪些字段，以及字段类型（是存储原始 `str` 还是 `SessionSummaryCandidateVNext`？是存储 `tuple[str, ...]` 还是 `tuple[EvidenceBackedFactCandidateVNext, ...]`？）。如果 Agent 理解偏差，可能产出与 plan 意图不一致的类型结构，导致 Slice 3 的 "conversion function" 需要大量返工。
- **为什么有问题**: Plan 作为 code-generation-ready artifact，应提供足够的信息让实现 Agent 无需"反向工程"现有代码即可实现。私有类型的字段定义是 parser 的核心契约，不应隐式引用。
- **直接证据**: Plan line 142-148: 仅列出类型名，无字段定义
- **影响**: 实施 Agent 跑偏 / 后续返工
- **建议改法和验证点**: 为每个私有类型补充字段定义（字段名、类型、必填性）。如果不引入私有 DTO 层（采纳 F-02），此问题自然消除。
- **修复风险（低/中/高）**: 低 — 字段定义可从现有 section parser 直接提取。
- **严重程度（低/中/高/严重）**: 低

## Final Conclusion

**PASS-WITH-RISKS**

本 plan 正确识别了 WU-CM-05 的核心问题（wide mapping / cast boundary 导致的弱类型解析），且非目标边界清晰（不改变 compact 语义、不放宽非法 proposal、不引入 public contract 变更）。架构分层检查通过：Plan 不修改 Engine、Service、Fins、Config 或 durable schema；不违反 LLM-facing 语义约束；source label contract 保留为 accept barrier 后置校验。Patch operation 被正确排除。

但 plan 在 **code-generation-readiness** 上有两个中等严重度缺口：

1. **Field-path 组合机制未定义**（F-01）：这是 parser 诊断质量的核心契约，不能在 implementation gate 中临时设计。
2. **私有 typed DTO 层的必要性未充分论证**（F-02）：引入 8 个与现有 candidate type 同构的中间类型可能构成过度设计，存在更简的替代方案（改进 helper + 保持现有类型流转）。

建议在进入 implementation gate 前裁决这两个问题。如果采纳 F-02 的优先方案（放弃私有 DTO 层，仅改进 helper），本 WU 的 scope 会缩小，slice 结构简化，但仍满足 issue #93 的 hardening 目标。

四个低严重度问题（双重校验边界、JSON type narrowing 模式、字段定义隐式引用、patch operation 测试措辞）不阻塞 implementation gate，但建议在 plan 中就地修复以降低实施 Agent 的决策负担。
