## 3. Findings

### F1-未修复-中-activation 与 cancel_observation 的锁顺序未在 plan 中显式声明

- **位置**: Slice 2 — Fins prepare / activate API 与 Pre-activation cancel
- **问题类型**: 状态机漏洞
- **当前写法**: Plan 要求 "If activation sees a cancelled or terminal prepared record, it must not submit" (Slice 2) 和 "Fins activation checks cancellation/terminal state under lock before submit" (Slice 2)，但未显式要求 `activate_observation` 与 `cancel_observation` 使用同一把 `observation_lock`
- **反例/失败场景**: 如果 `activate_observation` 实现的锁不同于 `cancel_observation` 的 `self._observation_lock`（例如引入新锁或仅在局部临界区内检查），则 `cancel_observation` 写入 CANCELLED 状态与 `activate_observation` 检查状态之间存在 TOCTOU 窗口——两者都认为各自操作合法，导致已取消的 observation 被激活并 submit
- **为什么有问题**: 当前 `cancel_observation` (line 2244) 使用 `self._observation_lock`。如果 implementation agent 未注意此约束，可能为 `activate_observation` 使用不同或更弱的同步机制
- **直接证据**: `ingestion_runtime.py:2244` — `cancel_observation` 的 `with self._observation_lock:` 块；plan 中用词 "atomically marks" 与 "under lock" 暗示但未绑定到具体锁对象名称
- **影响**: 实施 Agent 可能引入并发缺陷，导致取消语义被违反——已取消的 operation 仍被 submit 到 executor
- **建议改法和验证点**: Plan 应显式声明：`activate_observation(handle)` 必须在持有 `self._observation_lock` 时检查 `record.status` 与 `record.cancellation_state.is_cancelled()`，再原子写入 activated/submitted 标志并 submit。测试应覆盖并发 cancel-activate race（例如使用 barrier 或 `_HoldingExecutor` 延迟 submit 以便 cancel 先行到达）
- **修复风险（低）**: 增加一行 plan 文字即可关闭，不改变设计
- **严重程度（中）**: 不修复会导致并发取消不可靠，但实现 agent 极可能自然使用已有 `_observation_lock`（因为 `start_observed_*` 和 `cancel_observation` 已建立模式）。标记为 accepted-candidate

### F2-未修复-低-prepared observation 在 accept reject 路径上的清理缺口

- **位置**: Slice 1 — activation hook placement 与 Slice 2 — Pre-activation cancel
- **问题类型**: 状态机漏洞
- **当前写法**: Plan 列出 accept rejected / timeout / stale execution 不会 activate，但未说明这些路径上已 prepare 的 process-local observation record 如何清理
- **反例/失败场景**: `_accept_awaiting` 收到 `ToolAwaitingRejectedAck` 或 `ToolAwaitingAcceptTimedOut` 后，不创建 Host wait record。现有 `abandon_wait` -> `cancel_observation` / `abandon_observation` 清理链只作用于已有 wait record 的 CANCELLED 路径。rejected accept 路径留下的 observation record 永久残留在 `self._observations` 字典中，直到 FinsIngestionRuntime 被 GC
- **为什么有问题**: process-local 内存泄漏，长期运行的 Host 进程中可能累积。虽然单条 record 内存很小（handle + queue + 少量字段），但缺少明确的 cleanup contract 意味着行为依赖实现细节（dict 的 GC timing）
- **直接证据**: `ingestion_runtime.py:2244-2256` — `cancel_observation` 只在已有 observation record 时操作；`wait_adapter.py:137-155` — `abandon_wait` 只在 Host wait record CANCELLED 时调用。rejected accept 路径无 wait record，因此永远不会触发 `abandon_wait`
- **影响**: 低。process-local 内存，不影响 durable truth 或 LLM-facing 行为。但长期运行的服务可能积累
- **建议改法和验证点**: Plan 可在 Slice 2 的非目标中说明此缺口，或要求 `_accept_awaiting` 在 rejected/timeout 路径上 best-effort 调用 `runtime.abandon_observation(handle)`。或者明确标记为已知限制（与 process-local observation 设计一致），由 runtime GC 兜底
- **修复风险（低）**: 增加一行 abandon 调用或增加一句 non-goal 声明均可
- **严重程度（低）**: 标记为 defer-candidate——可接受作为已知 process-local 限制，或由 Slice 2 implementation 时自然补上
