## Findings

### 1-未修复-高-memory observer 在非终态 checkpoint 后重启会丢失本轮用户输入

- **入口/函数**: `ProjectionCoordinator.drain()` / `MemoryProjectionObserver.process()` / `DurableHarnessBundle.startup_reconcile()`
- **文件(行号)**: `dayu/host/_event_observer.py:256-271`, `dayu/host/_memory_projection.py:122-145`, `dayu/host/_durable_harness.py:172-176`, `dayu/host/_conversation_memory_durable.py:276-301`
- **输入场景**: 某个 run 先写入 `USER_INPUT_ACCEPTED` 等非 terminal canonical event；`coordinator.drain()` 已处理该批并把 memory observer checkpoint 推进到该 event position；进程在 terminal event 到达前重启；之后同一 run 写入 `FINAL_ANSWER` / `RUN_FAILED` 等 terminal event，再执行 `startup_reconcile()` 或 `drain()`。
- **实际分支**: 第一次 drain 时，`MemoryProjectionObserver.process()` 把非终态 event 放入进程内 `_pending_by_run`，但没有写 durable snapshot；同一事务内 `ProjectionCoordinator._run_once_locked()` 仍调用 `projection_store.advance_success(... position=last_position ...)` 推进 checkpoint。重启后 `_pending_by_run` 为空，checkpoint 已越过早先的 user event；后续 terminal 批次只包含 terminal event，observer 将只投影 terminal 批次并写出 snapshot row。
- **预期行为**: durable memory 的事实来源必须能跨进程重启恢复完整 run 事件；只要 EventLog 中有 `USER_INPUT_ACCEPTED` + terminal，最终 session snapshot 必须包含本轮用户输入和对应终态信息。
- **实际行为**: snapshot 会缺少 checkpoint 已越过但只存在于旧进程 `_pending_by_run` 的非终态事件；一旦 terminal 批次写出 snapshot row，`repair_missing_session_snapshots()` 只扫描“EventLog 有 canonical 事件但 snapshot row 缺失”的 session，不会修复这个已经存在但内容不完整的 row。
- **直接证据**: `MemoryProjectionObserver.process()` 在 `dayu/host/_memory_projection.py:126-145` 只把非终态事件放入 `_pending_by_run`，只有遇到 `TERMINAL_RUN_EVENT_TYPES` 才调用 `project_run_events_in_transaction`；`ProjectionCoordinator._run_once_locked()` 在 `dayu/host/_event_observer.py:256-271` 对每个成功 batch 都推进 checkpoint；`DurableHarnessBundle.startup_reconcile()` 在 `dayu/host/_durable_harness.py:172-176` 只先 drain 再调用 repair；repair 在 `dayu/host/_conversation_memory_durable.py:276-301` 仅处理 snapshot row 缺失的 session，并在 row 已存在时跳过。
- **影响**: durable conversation memory 会静默丢失用户输入、工具事实或其它 terminal 前 canonical fact；后续 RunInputBuilder 基于缺失 snapshot 构造上下文，可能让财报分析 Agent 遗忘上一轮用户问题或工具事实。该错误不会表现为异常，属于用户可见的错误上下文 / stale facts 风险。
- **建议改法和验证点**: 不要让 required memory projection 的 checkpoint 越过尚未 durable 化的 pending run facts。可选方案：把 pending-by-run 持久化并与 checkpoint 同事务提交；或在 terminal 投影时从 EventLog 按 run/session 重读该 run 的全部 canonical events，而不是依赖进程内 `_pending_by_run`；或将 checkpoint 推进约束到已 durable projection 的 terminal run 边界。必须补一个回归测试：append `USER_INPUT_ACCEPTED` -> drain 推进 checkpoint 且 snapshot 仍为空 -> close/reopen -> append terminal -> `startup_reconcile()`/`drain()` -> assert snapshot 同时包含 user_text 和 final/failure summary。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-中-已移除的 fetch_more handle 协议仍从 public contracts 模块导出

- **入口/函数**: `from dayu.host.contracts import *` 或调用方直接导入 `ToolFetchMoreHandle*`
- **文件(行号)**: `dayu/host/contracts.py:843-925`, `dayu/host/contracts.py:1000-1024`, `dayu/host/README.md:237-245`, `tests/host/test_phase2_tool_runtime_boundary.py:214-220`, `tests/README.md:260`
- **输入场景**: 上层或第三方调用方按 public contracts 模块发现 / 导入 `ToolFetchMoreHandleRequest`、`ToolFetchMoreHandle`、`ToolFetchMoreHandleResult` 等类型，继续实现旧的两步 public handle fetch_more 流程。
- **实际分支**: PR 已把 Host public fetch_more 收敛到 framework tool call 路径，`dayu.host.__all__` 和测试只断言包根不导出 `ToolFetchMoreHandle`；但 `dayu.host.contracts` 仍定义并在 `__all__` 中导出完整 handle 类型。
- **预期行为**: 当前设计应只暴露 `ToolRuntimeCursor`、`ToolFetchMoreRequest`、`ToolFetchMoreResult`、`ToolFetchMoreSucceededResult`、`ToolFetchMoreFailedResult`；旧 handle 协议不应继续作为 public contract 被发现或推荐。
- **实际行为**: `contracts.py` 的 `__all__` 仍包含 `ToolFetchMoreHandle`、`ToolFetchMoreHandleRequest`、`ToolFetchMoreHandleResult`、`ToolFetchMoreHandleSucceededResult`、`ToolFetchMoreHandleFailedResult`；同文件 docstring 还写着 cursor “仅通过受控 handle 交付”和 scope_token “受控 handle 中携带”，与当前 framework `fetch_more` 通过 tool truncation args 传递的路径不一致。
- **直接证据**: `dayu/host/contracts.py:843-925` 定义 handle 协议类型；`dayu/host/contracts.py:1017-1021` 将这些类型列入 `__all__`；`dayu/host/README.md:237-245` 当前公开接口没有 handle 协议且说明不再有独立 public helper；`tests/host/test_phase2_tool_runtime_boundary.py:217-220` 只检查 `dayu.host.__all__`，没有覆盖 `dayu.host.contracts.__all__`；`tests/README.md:260` 仍残留 `ToolFetchMoreHandle` 旧术语。
- **影响**: public contract drift。调用方可能继续依赖已无执行入口的旧 handle 类型，形成“类型仍公开、实现已删除”的半兼容接口；后续再清理会扩大破坏面，也违反本仓库“概念改名全量清理旧名、禁止兼容性 re-export / wrapper”的约束意图。
- **建议改法和验证点**: 从 `dayu.host.contracts` 删除 `ToolFetchMoreHandle*` 类型及 `__all__` 条目，并同步修正 `ToolRuntimeCursor` / `ToolFetchMoreRequest` docstring 与 `tests/README.md` 旧术语；补测试直接断言 `ToolFetchMoreHandle` 不在 `dayu.host.contracts.__all__` 且不能从 `dayu.host.contracts` 作为推荐 public surface 导入。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
