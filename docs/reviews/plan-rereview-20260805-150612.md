## Adversarial check: revised plan new-blocker scan

### N01 — Registry supersession 从 append-only 改为 status mutation，是否引入新风险？

- **检查**: 原 plan 说 "旧 frozen scenario 不原地改写"；修订后改为 "只把 `status` 改为 `superseded` 并设置 `superseded_by`"。
- **分析**: `docs/cli_ci.md:303,307,444` 明确 "旧 accepted contract 被新版本替代后必须标 superseded 且不参与 current verdict"。修改 `status` 和 `superseded_by` 字段不改变旧 entry 的 predicates、required evidence、observed evidence 或 user adjudication 正文。这是 lifecycle update，不是 contract mutation。
- **结论**: **无新 blocker**。Status lifecycle update 是 registry 设计的预期操作。

### N02 — 611 records / 768 predicate refs 的 stable predicate resolution 是否可实现？

- **检查**: S5 要求 "611 records、768 predicate refs 唯一 current accepted owner、0 dangling、0 duplicate"。
- **分析**: 当前 `accepted_oracle_refs` 历史指向 `core-execution@1`。Resolution 算法是：对每个 `oracle_predicate_refs` 中的 stable predicate id，查找当前 `status=accepted` 且未被 supersede 的 oracle version。Core@2 的 `predicate_id` 列表必须覆盖 core@1 的所有 29 个 unique stable ids。Plan 要求 S5 验证 "0 dangling"，即每个 ref 都能解析到 current accepted oracle。
- **潜在风险**: 如果 core@2 的 predicate 列表与 core@1 不完全一致（新增或删除了 predicate），某些 ref 可能 dangling。但 plan 说 "v2 保留仍有效 predicate 的稳定 `predicate_id`"，暗示 core@2 继承 core@1 的所有 predicate ids。
- **结论**: **无新 blocker**，但 S5 validation 是关键验证点。Implementation agent 必须确保 core@2 的 predicate 列表完整继承 core@1。

### N03 — Host-internal digest 零 LLM 泄漏的 test 覆盖是否充分？

- **检查**: Plan 要求 "owner test 必须对 captured runner input 做反泄漏断言，证明 exact digest values 与 generic digest 字段名均不存在"。
- **分析**: 这要求 test 捕获实际的 runner input（system + user messages），然后搜索其中是否包含 digest hex string 或 digest 相关字段名。Plan 的 S3 owner tests 列表包含 "captured initial/repair 均不含 request/boundary digest value 或字段名"。
- **潜在风险**: Test 必须实际渲染 prompt 并捕获 runner input，而不是只检查 prompt template 源文件。Plan 的 "captured runner input" 措辞暗示这是 integration-level 断言。
- **结论**: **无新 blocker**。Test 要求明确，implementation agent 需要确保 test 使用 rendered prompt 而非 template source。

### N04 — S3 atomic rollback 是否真能回滚？

- **检查**: "保留 durable implementation diagnostic 后丢弃仅该 slice 尚未提交的 intended diff，恢复到 S2 accepted commit"。
- **分析**: S3 在 worktree 中实施。如果 worktree 有未提交的修改，`git checkout` 或 `git stash` 可以丢弃。但如果 implementation agent 已经 stage 了部分文件但未 commit，`git checkout -- .` 可以恢复。Plan 的 rollback 是标准 git 操作。
- **潜在风险**: 如果 implementation agent 在 worktree 中创建了新文件（如 `compact_structure.py`），rollback 时需要手动删除。Plan 没有显式提到新文件的清理。
- **结论**: **无新 blocker**，但 implementation agent 应在 rollback 时检查 `git status` 确保新文件也被清理。

### N05 — S5 "不等 Oracle controller" 是否会导致 registry 状态不一致？

- **检查**: "replacement scenarios 在 S4 observation 后：mandatory evidence 完整则 `status="unadjudicated"`；仍有真实证据缺口则 `status="needs-more-evidence"`"
- **分析**: 新 scenario 的 status 不是 `accepted`，而是 `unadjudicated` 或 `needs-more-evidence`。这意味着 registry 中会同时存在 `status=superseded` 的旧 entry 和 `status=unadjudicated` 的新 entry。Stable predicate resolution 将 611 records 解析到 core@2（`status=accepted`），但 replacement scenarios 本身不是 `accepted`。
- **关键问题**: 611 records 的 `oracle_predicate_refs` 只引用 core-execution 的 predicates，不直接引用 scenarios。Scenarios 的 `accepted_oracle_refs` 引用 core-execution。因此 611 records 的 resolution 不受 scenario status 影响。Scenario 的 status 只影响 scenario 自身的 readiness。
- **结论**: **无新 blocker**。Registry 状态分层清晰：core@2 accepted（满足 611 records），replacement scenarios unadjudicated（等待 Oracle controller）。

### N06 — `CompactOutputCapsV3` 的 projection function 在哪个模块？

- **检查**: "`context_governance.py::compact_output_caps_v3_from_memory_policy(policy)` 机械构造"。
- **分析**: 该函数在 `context_governance.py` 中，因为它需要同时依赖 `MemoryProjectionPolicy`（from `memory.py`）和 `CompactOutputCapsV3`（from `compaction.py`）。`context_governance.py` 已经同时依赖这两个模块，所以它是正确的 projection boundary。
- **依赖方向**: `context_governance.py` → `memory.py`（已有）+ `compaction.py`（已有）。无循环依赖。
- **结论**: **无新 blocker**。

### N07 — `compact_structure.py` 的 JSON Schema digest 是否与 transport payload 同源？

- **检查**: "`compact_output_json_schema_digest_v3()` 使用 Host canonical JSON serialization 计算 SHA-256。`JsonSchemaStructuredOutputRequest.name/schema`、captured runner input manifest 记录的 schema digest 与 transport payload 必须来自同一次 structure projection"。
- **分析**: 这要求：(a) `compact_structure.py` 暴露 canonical schema JSON；(b) schema digest 从该 JSON 计算；(c) `JsonSchemaStructuredOutputRequest` 使用同一 JSON；(d) manifest 记录同一 digest。四者必须同源。
- **潜在风险**: 如果 `compact_structure.py` 每次调用都重新构造 schema JSON（非缓存），digest 在理论上一致但实际计算成本高。如果缓存，需要确保 cache 不被 mutation。
- **Plan 措施**: "JSON Schema 必须以 immutable canonical JSON value 暴露"——暗示是 frozen value，不是每次重建。
- **结论**: **无新 blocker**。Immutable canonical value + digest 同源是合理设计。
