## Findings

### 1-HIGH-S3-slice-too-large-for-reliable-atomic-implementation

- **位置**: Implementation slices → S3 — F12 Host compact v3 纵向切换
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: S3 必须在单个原子 commit 中修改 15 个 production files + 16 个 test files，同时删除 v2 symbols/fields、替换 parser/governance/operation/artifact/event/Memory/RunInput、替换 initial/repair prompt renderer、更新 publication manifest hashes。Plan 明确要求"禁止先保留 v2 public aliases 来换取分步编译"。
- **反例/失败场景**: 若 S3 实现中 compaction.py 已切到 v3 但 context_events.py 的 `CompactAcceptedTruthV2` 引用尚未更新（该文件在 allowed files 列表中），编译失败且无法形成中间 checkpoint。或 prompt renderer 替换后发现 real-provider 行为不符合预期，但 parser 已经删除 v2 读取分支，无法回退到 v2 做 A/B 对比。
- **为什么有问题**: 15 个 production files 的原子迁移违反"小步提交、每步可运行"的工程原则。虽然 plan 引用了 AGENTS.md "一律按全新 schema 起库处理"规则，但该规则不强制要求所有文件在一个 commit 中完成。可以先在 new module 中建立 v3 contract 并通过 owner tests，再分步完成各 consumer 迁移——每步都保持可运行状态，只是中间 checkpoint 可能同时存在 v2 和 v3 类型定义（但不是双 owner，因为 v3 尚未接入 consumer）。
- **直接证据**:
  - Plan S3 allowed production files 列表包含 15 个文件（plan line 248-266）
  - Plan S3 描述："同一次 slice 内把 parser、governance、operation、artifact/event、Memory/RunInput 全部切到 v3 并删除 v2 symbols/fields"（plan line 294）
  - Plan 明确要求"避免 accepted checkpoint 出现 v2/v3 双 owner"（plan line 245）
- **影响**: 实施 Agent 可能在巨型 commit 中迷失，导致部分迁移、编译失败、或引入 subtle bug。Reviewer 也难以有效审查 15 个文件的联动变更。
- **建议改法和验证点**:
  1. S3 拆分为 S3a（建立 `compact_structure.py` + `CompactCandidateV3` + parser + owner tests，v2 代码不删）+ S3b（把 governance/operation/artifact/event 迁移到消费 v3，删除 v2）+ S3c（替换 prompt renderer + manifest hashes）。
  2. S3a accepted checkpoint 中 v3 types 已存在但未接入 consumer，v2 仍在运行——这不是"双 owner"，因为 v3 尚未成为任何 consumer 的 truth source。
  3. S3b accepted checkpoint 中所有 consumer 已切换到 v3，v2 types 已删除。
  4. 或者，plan 应补充一个 explicit risk acceptance：说明为什么必须在一个 commit 中完成，以及如果中途失败的回滚策略。
- **修复风险（低/中/高）**: 低 — 拆 slice 不改变最终设计，只改变 sequencing。
- **严重程度（高/中/低/严重）**: **高** — 当前 S3 的原子性要求显著增加了实施失败概率。

### 2-HIGH-repair-digest-exposure-ambiguity-violates-LLM-facing-constraint

- **位置**: Frozen target contracts → F12 → Initial/repair state machine
- **问题类型**: 架构边界 / LLM-facing 约束违反
- **当前写法**: "repair request 必须包含同一 immutable v3 input、完整 output contract/template、前次 attempt、bounded/redacted issues、**request digest**、**boundary digest** 与 whole-candidate action"（plan line 151）。同一段又说"不得只发 patch 指令或依赖 initial prompt 的隐式上下文"。
- **反例/失败场景**: 若 `request digest` 和 `boundary digest` 被写入 repair prompt 的 LLM-facing JSON 或文本中，模型看到的是两个 hex digest 字符串（如 `a1b2c3...`），既不是业务事实也不是可操作的验证规则。模型可能：(a) 忽略它们（浪费 context）；(b) 尝试"匹配"它们（hallucination）；(c) 认为它们是某种需要返回的 reference。这违反了 AGENTS.md 的 LLM-facing 文本约束："内部治理标识如 label、id、ref、digest、cursor 只有任务必须引用时才可暴露；暴露时必须说明它只是引用标签"。
- **为什么有问题**: Plan 在"模型可见 input"节（line 88-92）定义了 `CompactInputV3` 的字段为 `schema`、`current_input`、`source_boundary`、`output_caps`——其中不包含 digest。但在 repair state machine 节（line 151）又说 repair request 包含 digest。这两个描述之间存在歧义：digest 是进入 LLM-facing repair message body，还是只作为 Host 内部 `CompactionRequest` 的 binding 字段？
- **直接证据**:
  - AGENTS.md line 45-48："内部治理标识如 label、id、ref、digest、cursor 只有任务必须引用时才可暴露；暴露时必须说明它只是引用标签，不是业务事实或推理依据"
  - Host design line 3800-3801："两个治理 digest 只参与 Host 内部 binding、audit 与 request serialization，不进入 LLM-facing repair JSON"
  - Plan line 151：repair request "必须包含...request digest、boundary digest"
- **影响**: 若 digest 进入 LLM-facing repair prompt，违反项目硬约束，且浪费 context window。若 digest 只在 Host 内部使用（与 Host design 一致），plan 措辞有歧义，实施 Agent 可能误将其渲染到 prompt 中。
- **建议改法和验证点**:
  1. 明确区分 "CompactionRequest（Host 内部）" 与 "LLM-facing repair message body（给模型的）"。
  2. 在 plan 中显式声明：request digest 和 boundary digest 只用于 Host 内部 repair binding validation，不进入 LLM-facing prompt JSON。
  3. 增加 owner test：验证 repair prompt 渲染输出中不含 hex digest 字符串。
- **修复风险（低/中/高）**: 低 — 只需澄清措辞，不需要改设计。
- **严重程度（高/中/低/严重）**: **高** — 歧义可能导致实施 Agent 违反 AGENTS.md LLM-facing 约束，产生安全/治理问题。

### 4-MEDIUM-F11-pagination-max-pages-unspecified

- **位置**: Frozen target contracts → F11 → item 4 (resolve sequence)
- **问题类型**: 契约缺失 / 并发恢复风险
- **当前写法**: "使用 `read_run_events_by_types_page` 读取 manifest 中 `parent_host_run_id` 的 canonical `CONTEXT_COMPACTED` 与 `CONTEXT_COMPACTION_ATTEMPT_REJECTED`"（plan line 76）。后续 line 79: "只在确实没有 matching terminal 且没有冲突 terminal 时返回 `None`"。
- **反例/失败场景**: 一个长时间运行的 interactive session 可能积累数千个 EventLog events，`parent_host_run_id` 的 terminal event 可能在很后面的 page。如果 page size 较小（当前 Tool Trace 内部 page size 最大 500，`tool_trace.py:40`），极端情况下可能需要多次分页才能找到 terminal。Plan 没有指定 max pages / scan limit / timeout。若 resolver 无限分页，可能造成 read transaction 长时间持有。
- **为什么有问题**: 没有 max scan bound 的 pagination 是不安全的。要么必须证明 terminal 一定在前 N 页内（因为 terminal 总是在 operation 的 request 之后不久产生），要么必须设定 scan limit 并在超出时返回 `limitation` 而非静默返回 `None`（静默返回 None 会让 analysis 误以为"没有 terminal"）。
- **直接证据**:
  - Plan line 76: 使用 `read_run_events_by_types_page` 但未提 page limit
  - Plan line 79: "只在确实没有 matching terminal 时返回 None" — 但 "确实没有" vs "没扫到" 需要区分
  - `tool_trace.py:40`: `TOOL_TRACE_QUERY_MAX_LIMIT = 500` — 现有 page 上限
- **影响**: 在极端大 session 下，resolver 可能：(a) 长时间持锁影响并发；(b) 因 page limit 提前终止却返回 `None`（实际 terminal 在后面 page），导致 Tool Trace analysis 遗漏 response identity 且不做 `limitation` 标记。
- **建议改法和验证点**:
  1. 为 terminal resolution 设定显式 page limit（如最多扫描 10 页）。
  2. 超出 page limit 时返回 `None` 并附加 `compactor-response-terminal-scan-limit-exceeded` limitation（区别于 "not observed" limitation）。
  3. 论证在合理 operation 生命周期内，terminal 一定在前 N 页内。
- **修复风险（低/中/高）**: 低 — 增加 page limit 和 limitation 类型不影响核心设计。
- **严重程度（高/中/低/严重）**: **中** — 边缘 case 但可能导致生产环境中 response identity 静默缺失。

- **严重程度（高/中/低/严重）**: **中** — 不影响功能正确性，但影响 plan 的证据完整性。

### 6-LOW-superseded-semantic-not-explicitly-preserved-in-v3

- **位置**: Frozen target contracts → F12 → 模型输出
- **问题类型**: 契约缺失
- **当前写法**: v3 输出 root keys 为 `session_summary`、`evidence_facts`、`answer_anchors`、`forward_intents`、`reference_continuity`（plan line 97）。删除 `explicitly_dropped_sources` 和所有 drop reasons。Host 从 accepted provenance 与 immutable source boundary 派生 `omitted`（plan line 115-116）。
- **反例/失败场景**: 观察证据 #61 证实：rolling correction 场景中，模型显式 drop 了旧 source（`superseded`），表示旧事实不再有效。在 v3 中，模型不显式声明 drop——旧 source 不出现在五类语义的 provenance 中，Host 将其归入 `omitted`。但 "该 source 被省略是因为用户纠正了事实" 这一业务语义丢失了——`omitted` 只是一个 label 列表，没有分类。
- **为什么有问题**: `superseded` 在 v2 中有明确的业务含义（"旧信息被新信息取代"），不同于 `redundant`（"信息重复"）或 `out_of_scope`（"超出范围"）。v3 的 `omitted` 是纯补集运算，不区分 superseded vs redundant vs out_of_scope。对于 audit/trace 和用户理解 compaction 行为，知道一个 source 是因为"被取代"还是"被省略"有不同含义。当前 plan 未说明 `superseded` 语义如何保留。
- **直接证据**:
  - Plan line 115: "Host 从 candidate provenance 得到 CompactRepresentedCoverageV3；按 root boundary 顺序计算补集 CompactOmittedCoverageV3，不生成原因、不做财报语义推断"
  - Plan line 97-100: v3 输出无 explicit drop 字段
  - Observed behavior #61: superseded drop 有实际业务价值
  - Host design line 3372-3374: v2 定义 `CompactExplicitDropV2.reason` 四种枚举
- **影响**: 丢失 superseded 语义可能导致：audit log 无法区分"被取代的旧事实"与"因 cap 被省略的材料"；Memory projection 可能错误地将 superseded 材料视为"仍然有效但未代表"。
- **建议改法和验证点**:
  1. Plan 中明确：`superseded` 语义通过 `forward_intents.status="superseded"` 或 `reference_continuity.reason` 保留（如果这是预期路径）。
  2. 或者在 `CompactOmittedCoverageV3` 中增加可选的 `omission_kind` 枚举（从 `superseded` 与 Host-derived 两类开始），其中 `superseded` 由模型通过 provenance 间接表达（Host 可检测：当新事实引用同一 subject 但不同 source 时）。
  3. 至少明确这是一个 deferred design decision，在 S3 实现前通过 goal confirmation 冻结。
- **修复风险（低/中/高）**: 中 — 需要设计决策，但可以 defer 到 implementation 前。
- **严重程度（高/中/低/严重）**: **低** — 不阻止 plan 推进，但需要明确处理策略。

### 7-LOW-repair-prompt-structure-unspecified

- **位置**: Frozen target contracts → F12 → Initial/repair state machine
- **问题类型**: 不可直接实施
- **当前写法**: "repair request 必须包含同一 immutable v3 input、完整 output contract/template、前次 attempt、bounded/redacted issues、request digest、boundary digest 与 whole-candidate action；不得只发 patch 指令或依赖 initial prompt 的隐式上下文"（plan line 151-152）。
- **反例/失败场景**: "完整 output contract/template" 如果与 initial prompt 的 output contract 完全相同，则 repair prompt 会重复整个 v3 schema/template 描述——增加 repair context 消耗但未提供新信息。如果 repair 使用不同的 output contract 描述（更简洁），则有"两个 prompt 描述同一 schema"的漂移风险。
- **为什么有问题**: Plan 正确地要求 repair 自足（模型没有跨调用记忆），但未指定 repair prompt 与 initial prompt 之间的结构关系——是完全独立的两个 prompt asset、还是一个 base template + conditional repair section、还是同一个 template 通过条件渲染切换 initial/repair 模式。实施 Agent 需要自行设计，可能导致：
  - 两个 prompt 中的 output schema 描述漂移
  - Repair prompt 过长（重复 schema + 前次 attempt + issues + 新 instruction）
  - Repair prompt 可能超过模型 context window
- **直接证据**:
  - Plan line 150: "packaged initial user template 实际渲染内容不得包含 repair protocol"
  - Plan line 151: repair request 必须包含"完整 output contract/template"
  - Plan 未指定 repair prompt asset 的组织方式
- **影响**: 实施 Agent 做 prompt engineering 决策，reviewer 无法从 plan 判断 repair prompt 是否合理。可能导致 repair prompt 过长而无法有效使用。
- **建议改法和验证点**:
  1. 明确 repair prompt 的组装方式：是否使用与 initial 相同的 output contract 模板，外加 repair-specific section（前次 attempt summary + bounded issues + whole-candidate 要求）。
  2. 增加验证：owner test 检查 repair prompt 的实际 token estimate 不超过 compactor model context window 的硬上限（例如 70% 用于 input + output_caps + repair feedback，剩余留给模型输出）。
- **修复风险（低/中/高）**: 低 — 可在 S3 实现时具体化。
- **严重程度（高/中/低/严重）**: **低** — 实施细节，不阻止 plan 推进。
