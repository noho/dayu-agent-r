## Findings

### Finding 1 [Low] — `RuntimeFileLock.__exit__` 在 release 失败时可能掩盖 context body 原始异常

- **入口/函数**: `RuntimeFileLock.__exit__`
- **文件(行号)**: `dayu/runtime/filelock.py:176-194`
- **输入场景**: context manager body 抛出异常（如业务逻辑错误）后，`token.release()` 的 `_ensure_lock_file_marker_exists` 因磁盘满或权限错误也抛出 `RuntimeFileLockError`。
- **实际分支**: `__exit__` 无 try/except 包裹 `token.release()`；若 body 已抛异常且 release 再抛异常，Python context manager 协议会用 `__exit__` 的异常替换 body 的原始异常。
- **预期行为**: body 原始异常应优先传播；release 失败应作为次要信息记录或被压制，不应掩盖调用方需要看到的业务错误。
- **实际行为**: body 原始异常被 release 异常替换，调用方只看到 `RuntimeFileLockError`，丢失原始错误上下文。
- **直接证据**: `filelock.py:192-194` — `__exit__` 直接调用 `token.release()` 无 try/except，且 Python 文档明确 `__exit__` 返回 falsy 值时不压制异常，但 `__exit__` 自身异常会替换 body 异常。
- **影响**: 极低概率边缘场景（release 失败需要磁盘满或权限错误），但发生时会让故障定位困难，因为 root cause 被掩盖。
- **建议改法和验证点**: 在 `__exit__` 中加 try/except 包裹 `token.release()`，body 无异常时传播 release 异常，body 有异常时压制 release 异常（可记录日志）。测试需验证 body 异常 + release 失败双重故障下 body 异常优先传播。
- **修复风险**: 低 — 只影响异常传播优先级，不改变正常路径行为。
- **严重程度**: 低

### Finding 2 [Info] — `_require_non_empty` / `_require_optional_non_empty` 在 `api.py` 与 `tooling.py` 中重复定义

- **入口/函数**: 模块级私有 helper
- **文件(行号)**: `dayu/host/api.py:17-42`, `dayu/host/tooling.py:17-42`
- **输入场景**: 两个模块各自定义了语义完全相同的私有校验函数。若后续校验规则需要调整（如拒绝特定 unicode 空白字符），需要同时修改两处，容易遗漏。
- **实际分支**: 两个模块使用独立的函数副本，类型签名和实现完全一致。
- **预期行为**: 同包内共享的校验原语应抽取到包级私有模块（如 `_validation.py`），避免重复定义。
- **实际行为**: 两组相同函数独立存在于两个模块中。
- **直接证据**: `api.py:17-42` 和 `tooling.py:17-42` 的函数体逐字相同。
- **影响**: 维护风险 — 未来校验规则演变可能造成两个模块行为不一致。当前不影响 correctness。
- **建议改法和验证点**: 抽取到 `dayu/host/_validation.py`，两个模块从该模块 import。或在后续 phase 中统一。
- **修复风险**: 低 — 纯重构，不改变行为。
- **严重程度**: 信息

- **filelock `__exit__` 异常掩盖** (Finding 1): 极低概率边缘场景，当前不影响正确性。后续 phase 可通过 `__exit__` 加 try/except 守卫修复。
- **`_require_non_empty` 重复定义** (Finding 2): 后续 phase 重构 `dayu/host/` 时可统一抽取；当前两个模块独立维护，短期风险可控。
- **SQLite 高并发 busy 抖动**: 已通过 capacity invariant 测试，不影响正确性。后续 Phase 11 multi-process hardening 需压力观察。
- **跨进程 clock skew**: 影响 stale cleanup 精确时间，但不影响 capacity eventual cleanup。后续 Phase 11 覆盖。
- **workspace runtime lane DB cleanup**: 未定义清理策略。后续 Host composition root / workspace lifecycle phase 负责。
- **Host public contract 扩展性**: Phase 1 只导出最小 request/snapshot 类型；后续 command path phase 可能需要扩展。当前 contract 已明确 non-goals 和责任边界。
