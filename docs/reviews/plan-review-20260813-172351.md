## Findings

### 01-未修复-中-upload_material 共享被修改 owner，行为变化未声明、无测试、失败投影退化为 str(exc)

- **位置**: §3.1 非目标、§4 owner 表、§6.2 测试文件清单、§11 static audit
- **问题类型**: 范围漂移 / 测试缺口 / 其它（跨命令面语义泄漏）
- **当前写法**: plan 只在 filing 语境描述 action/skip/publication 修复；§3.1 声称"不改变
  delete-with-files、delete-never-existed、重复 action/ticker、amended identity 之外的既有行为"，
  却未提及 material 面；§6.2 无任何 material 测试；§11 audit 无 material 检查项。
- **反例/失败场景**: `run_upload_material_stream`（`sec_upload_workflow.py:430-633`）复用
  同一 `prepare_upload` / `evaluate_upload_overwrite_precondition` / `_can_skip_upload` /
  （S2）`_store_upload_assets`。修复后：
  1) material `update + missing + overwrite=True` 从静默 create（现
     `_resolve_upsert_mode` 分支）变为 `FileNotFoundError`，被 material workflow 的
     `except Exception` 捕获，产出 generic failed event（`message=str(exc)`，
     `sec_upload_workflow.py:606-633`）——material 没有 typed usage 面，错误质量反而
     退化为裸字符串；
  2) material deleted + auto + 相同完整输入从 skipped 变为转换+恢复（S2 重置重建）。
- **为什么有问题**: Goal Confirmation 的目标用词是通用 "source/update 对象"，但全部
  证据、registry predicates、tests、UF-PF02 都是 filing 范围。共享 owner 修复在语义所有权
  上是正确根因（AGENTS.md 禁止按面复制规则），但 plan 完全沉默导致：implementation agent
  无法判断 material 行为变化是否被授权；用户可见的 upload_material 语义变化没有
  evidence/README 覆盖；§11 audit 无法区分"有意的 owner 一致性变化"与"意外的语义泄漏"。
- **直接证据**: `sec_upload_workflow.py:504`（material 调用同一 `resolve_upload_action`）、
  `:543-563`（同一 `prepare_upload`）、`:606-627`（generic `except Exception` +
  `str(exc)`）；`docling_upload_service.py:185/998-1001/475-489`（被修改符号为两命令共享）。
- **影响**: 实施 Agent 跑偏 / 用户可见行为无证据变更 / 错误投影质量回退 / review 不可验收
- **建议改法和验证点**:
  1. §3.1 或 §4 增加一句明确声明：material 与 filing 共享同一 action/skip/publication
     owner，因此 update-missing±overwrite 拒绝与 deleted auto 恢复同步适用于 material（有意
     的 owner 一致性修复）；本 WU 不新增 material typed usage 面、不改 material workflow
     生产代码。
  2. S1/S2 各加 1 个 material parity test：update-missing（±overwrite）在 converter 前失败
     （`_FakeDoclingConverter` call count == 0）；deleted + equal input auto 恢复 active。
  3. `dayu/fins/README.md` 的 upload 合同段补一句 material 共享 owner 的说明（若该 README
     覆盖 material 面）。
- **修复风险（低）**: 只加声明 + 2 个测试，不动生产代码。
- **严重程度（中）**

### 03-未修复-低-reset→create 后 first_ingested_at 保持无任何断言，restore 场景可能静默重置

- **位置**: S2 Tests first 1、§8 validation matrix
- **问题类型**: 测试缺口
- **当前写法**: S2 断言"新 bytes/meta/manifest 同源、版本递增、文件集合精确"与
  "is_deleted=False、deleted_at=None、integrity complete"；§8 同名/改名行断言
  "新 bytes/digest/meta；完整集合精确"。first_ingested_at 保持（`_build_upsert_meta`
  `docling_upload_service.py:774-779` 实现）不在任何断言中。
- **反例/失败场景**: 未来 `_build_upsert_meta` 或 reset→create 重构时，deleted restore /
  改名 update 的 `first_ingested_at` 被静默重置为恢复时间，首次摄入审计语义丢失而所有
  现有测试仍绿。
- **为什么有问题**: 本 WU 的 reset→create 是完整替换语义，first_ingested_at 是"同一 filing
  身份跨版本保持"的派生事实；prompt 明确要求 version/first_ingested/meta/manifest/file
  integrity 全验证，plan 漏掉其中一项。
- **直接证据**: `docling_upload_service.py:774-779`；plan S2 Tests first 1 与 §8 行。
- **影响**: 风险后移 / 审计语义静默漂移
- **建议改法和验证点**: S2 test 1 加断言：改名 update 与 delete→auto restore 成功后
  `meta.first_ingested_at` 等于 v1 create 时值且 ≠ `updated_at`；version 递增断言已有。
- **修复风险（低）**
- **严重程度（低）**

## 主动排除的可疑点（有证据，不构成 finding）

- "UPSERT 只由 auto 拥有"：fix 后 create/update 均无隐式 flip，与 `action-core` predicate 一致。
- "deleted equal input 在 S1 无 reset 的 update 路径也能正确恢复"：blob 同名覆盖 +
  `merged_meta.update(req.meta)` 显式写回 `is_deleted=False/deleted_at=None`，S1 中间态自洽。
- "reset 后 create 的 `created_at` 会刷新"：与现有 create+overwrite 路径语义一致，
  属完整替换语义，非回归。
- "UF-PF02 用 .txt 不可执行"：实测真实 Docling 转换 `.txt` DocumentStream 成功，不成立。
- "CLI exact stderr 断言不可行"：`render_cli_error` 为单行 `print(message, stderr)`，
  格式 `dayu-cli upload_filing: {message}\n` 可精确断言，且 UF-PF01 已证明该证据模式。
- "plan 自标 PLAN PASS 违反 gate 纪律"：本任务明确 plan gate 已由 controller 裁决关闭、
  禁止进入后续 gate，属 Gateflow 惯例，不构成 finding。
