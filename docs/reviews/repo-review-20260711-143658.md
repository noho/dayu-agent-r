## Findings

### 1-未修复-高-Scheduler close leaves CANCELLING runs without durable terminal facts

- **入口/函数**: `HostDispatchScheduler.close()` -> `_consume_worker_events()`
- **文件(行号)**: `dayu/host/dispatch.py:3907-3914` (finally block), `dispatch.py:3801-3811` (StopAsyncIteration handler)
- **输入场景**: Scheduler 正在关闭时，有 active worker 仍在处理 CANCELLING 状态的 Run
- **实际分支**: `self._closed` 为 True 时，StopAsyncIteration handler 中 `not self._closed` 条件不满足，跳过 cancelled EOF ingest；finally block 只做内存清理
- **预期行为**: CANCELLING 状态的 Run 应最终收到 terminal fact (CANCELLED / LOST)，释放 Session active slot
- **实际行为**: Run 保持 CANCELLING 状态，Attempt 保持 RUNNING，无 terminal fact 写入；Session active slot 被永久占用，queued Run 无法 promotion
- **直接证据**:
  - `dispatch.py:3907-3914`: finally block 不检查 `run_terminal_closed`，不写 terminal facts
  - `dispatch.py:3801-3811`: `not self._closed` 条件阻止 scheduler close 期间的 cancelled EOF ingest
  - `tests/host/test_active_cancel_dispatch.py:1011-1044`: 测试显式断言 Run stays CANCELLING, Attempt stays RUNNING, RUN_CANCELLED count is 0
- **影响**: Session active slot 被永久占用；同进程不重启时 queued Run 永远无法 promotion
- **建议改法和验证点**:
  - 在 `_consume_worker_events` finally block 中，当 `run_terminal_closed` 为 False 且 cancellation token active 时，使用 `_safe_close_worker_lost` 路径写入 terminal fact
  - 验证：scheduler close 后 CANCELLING Run 进入 LOST terminal，Session active slot 释放
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-Recovery scan defers CANCELLING runs to watchdog that may not be running

- **入口/函数**: `HostRecoveryScanner._classify_run()` -> `_is_deferred_cancel_state()`
- **文件(行号)**: `dayu/host/recovery.py:288-301`
- **输入场景**: Host 启动 recovery scan 遇到 CANCELLING 状态的 Run 且 `defer_accepted_cancel_to_watchdog=True`
- **实际分支**: `defer_accepted_cancel_to_watchdog` 为 True 时返回 `DEFERRED_TO_ACTIVE_CANCEL_WATCHDOG`，不执行 closeout
- **预期行为**: CANCELLING runs 必须最终进入 terminal state
- **实际行为**: 如果 scheduler 未运行（crash、close、未装配），watchdog 不会执行，CANCELLING runs 永久卡住
- **直接证据**:
  - `recovery.py:288-301`: `DEFERRED_TO_ACTIVE_CANCEL_WATCHDOG` 返回不执行 closeout
  - `dispatch.py:2549-2607`: `_active_cancel_watchdog_loop` 只在 scheduler 内部运行
  - `recovery.py:177`: 默认 `defer_accepted_cancel_to_watchdog=False`，但生产 composition 设为 True
- **影响**: 与 Finding 1 形成闭环：scheduler close 后 CANCELLING runs 被 recovery defer 给 watchdog，但 watchdog 不在运行
- **建议改法和验证点**:
  - Recovery scan 增加 fallback：当 `defer_accepted_cancel_to_watchdog=True` 但 scheduler heartbeat 不存在时，recovery 自行执行 closeout
  - 验证：scheduler crash 后 recovery scan 能正确 closeout CANCELLING runs
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-高-Dual `context_window_size` as independent policy fields with no shared derivation

## Conclusion

核心发现集中在三个领域：

1. **Scheduler close 期间的 CANCELLING run 终态缺失**（Findings 1, 2, 4, 5）：scheduler close 不写 terminal facts，recovery defer 给 watchdog，watchdog 不在运行，CancelledError 跳过 closeout。四个 finding 形成闭环，导致 CANCELLING runs 在 scheduler close 后被永久遗留。

2. **Context governance 双真源**（Findings 3, 7, 9）：`context_window_size` 在 memory policy 和 budget policy 间独立存在；threshold 计算在 `context_policy.py` 和 `context_budget.py` 间重复；raw token 字段与 ratio-first policy 并存。设计文档明确禁止这些模式。

3. **Public contract 边界泄漏**（Findings 8, 10）：内部 worker dispatch 协议暴露在 public namespace；deferred cancel 分类在 admission 事务外读取 durable state。
