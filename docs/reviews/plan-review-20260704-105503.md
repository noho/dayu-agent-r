## Findings

### 01-未修复-高-reopen 路径与现有 StartupRecoveryScanner 冲突：CANCELLING Run 会被 recovery scanner 提前标记为 LOST

- **位置**: Plan §Implementation Decisions "Scheduler close boundary"（line 173-174）；Plan §Slice 2 test `test_active_cancel_watchdog_reopen_closes_existing_cancelling_run`（line 274）
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: Plan 要求 "If Host closes before timeout fires, reopening Host with watchdog enabled should be able to scan existing CANCELLING runs and apply timeout based on durable RUN_CANCELLING / CANCEL_REQUESTED timestamps."
- **反例/失败场景**:
  1. Host cleanly closes（调用 `close()`）while Run 处于 `CANCELLING`，未到 timeout
  2. `close()` 调用 `mark_current_instance_stopping` → `mark_current_instance_stopped`，Host instance status 变为 `STOPPED`
  3. Host 重新 `open_host()` → `StartupRecoveryScanner.scan()` 在 watchdog 启动前执行（open_host.py:891-896）
  4. `_classify_active_or_cancelling()`（recovery.py:341）处理该 `CANCELLING` Run
  5. `_classify_owner()` 读取 owner liveness → status 为 `STOPPED`
  6. `classify_orphan_candidate()`（recovery_process.py:242-250）将 `STOPPED` 直接判定为 `PositiveOrphanProof(reason=OWNER_STOPPED)`
  7. `_close_positive_orphan()`（recovery.py:440-442）：`recoverable = (run.status is RunStatus.RUNNING and ...)` → **False**（Run 是 `CANCELLING`）
  8. Run 被标记为 **`RUN_LOST`**，不是 `RUN_CANCELLED`
  9. Watchdog 启动后扫描时 Run 已是 terminal `LOST`，timeout closeout 无法生效
- **为什么有问题**: Plan 声称 reopen 后 watchdog 可以 timeout-close `CANCELLING` Run，但未提及现有的 `StartupRecoveryScanner` 会在 watchdog 之前运行，且会将 `STOPPED` owner 的 `CANCELLING` Run 提前关闭为 `LOST`。这违反了 plan 声明的 terminal policy：post-cancel timeout 应产出 `CANCELLED`，不是 `LOST`。即使 owner 是 `RUNNING`（心跳 stale 但 inconclusive），recovery scanner 也会跳过该 Run，watchdog 仍可工作——但 plan 未说明这种交互，implementation agent 会自行裁决是先跑 recovery scanner 还是先跑 watchdog，或是否需要在 recovery scanner 中为 `CANCELLING` 增加 skip/defer 分支。
- **直接证据**:
  - `open_host.py:891-896`：`StartupRecoveryScanner(...).scan()` 在 scheduler open 之后、admission service / command handle 创建之前同步执行
  - `recovery.py:281`：`if run.status in (RunStatus.RUNNING, RunStatus.CANCELLING): return self._classify_active_or_cancelling(...)`
  - `recovery.py:440-442`：`recoverable = (run.status is RunStatus.RUNNING and ...)` — `CANCELLING` 永远不会是 recoverable
  - `recovery_process.py:242-250`：`row.status is HostInstanceStatus.STOPPED` → 直接 `PositiveOrphanProof`
  - Host design.md §27 line 3447-3450：recovery scan 对 `RUNNING`/`CANCELLING` 的分类规则，`CANCELLING` + positive orphan proof → `LOST`（不可恢复）
- **影响**: 实施 Agent 跑偏 — watchdog reopen 测试可能仅对 inconclusive/owner-still-live 场景通过，但 clean-close-reopen 场景下 watchdog 永远收不到 `CANCELLING` Run；状态不一致 — 用户 cancel 已被 durable accepted，但 reopen 后 Run 变成 `LOST` 而非 `CANCELLED`，用户看到的结果与 plan 承诺的 "Host policy chooses CANCELLED" 矛盾
- **建议改法和验证点**:
  1. Plan 必须显式裁决 watchdog 与 `StartupRecoveryScanner` 的执行顺序：watchdog 应在 recovery scanner 之前运行以先处理 `CANCELLING` 超时，或 recovery scanner 应 skip `CANCELLING` Run（仅记录 diagnostic），或 recovery scanner 应为 `CANCELLING` Run 调用 timeout closeout 而非 orphan→LOST
  2. 如果选择 "watchdog 在 recovery scanner 之前运行"：需要在 `open_host` 的 `__aenter__` 中插入 watchdog scan（在 `StartupRecoveryScanner.scan()` 之前），确保扫描使用 durable `RUN_CANCELLING` timestamp 判断是否超时
  3. 如果选择 "recovery scanner skip CANCELLING"：修改 `_classify_active_or_cancelling` 使 `CANCELLING` 分支返回 `OWNER_STILL_LIVE` 等价结果（reason 记录为 `deferred_to_watchdog`），让后续 watchdog 处理。Plan 需要证明这不会导致 CANCELLING Run 在无 watchdog 的 Host 配置中永久悬空
  4. 测试 `test_active_cancel_watchdog_reopen_closes_existing_cancelling_run` 必须覆盖 clean-close-reopen 路径（owner STOPPED），不仅是 crash-reopen 路径
- **修复风险（中）**: 改动 `StartupRecoveryScanner` 语义需谨慎；CANCELLING Run 若被 recovery scanner 跳过且 watchdog 未启用（`active_cancel_timeout_seconds=None`），会导致 Run 永久悬空在 CANCELLING。Plan 需要定义这个场景的收口策略
- **严重程度（高）**: 这是 reopen 路径的结构性冲突，不改会导致 plan 承诺的 reopen 行为在 clean-close 场景下系统性失败

### 02-未修复-中高-late terminal 竞态行为未收敛：plan 要求 implementation tests 自行发现而非设计裁决

- **位置**: Plan §Implementation Decisions "Late terminal handling"（line 160-163）
- **问题类型**: 状态机漏洞 / 不可直接实施
- **当前写法**: "Final answer / failed terminal before timeout after RUN_CANCELLING: first commit wins only if current ingest preconditions allow it. The plan does not loosen terminal ingest preconditions; implementation tests must document actual accepted/rejected behavior."
- **反例/失败场景**:
  1. User cancel → `RUN_CANCELLING` durable written → watchdog starts waiting
  2. Before timeout fires, the hung Engine worker suddenly produces `run_failed` terminal event (e.g. provider finally returns error, or Runner idle timeout fires)
  3. `EngineIngestMapper` receives `run_failed` for a `CANCELLING` Run
  4. Current ingest mapping for `run_failed` vs `CANCELLING`: **behavior is unspecified** — the plan itself doesn't know whether ingest accepts or rejects this
  5. Implementation agent must read the ingest mapping code, discover the actual behavior, and write tests documenting it — this is discovery, not implementation
- **为什么有问题**: Plan 不是 code-generation-ready。Implementation agent 需要自行阅读 ingest mapping 代码（`engine_ingest.py` 中 `_close_failed` / `_close_final_answer` 对 `CANCELLING` Run 的前置条件），判断哪些会被接受、哪些会被拒绝，然后决定是否需要修改现有 ingest 逻辑。这等于把设计决策推迟到 implementation 阶段。"Implementation tests must document actual behavior" 暴露了 plan 没有完成必要的 design-time 裁决。
- **直接证据**: Plan line 161-163 原文；`engine_ingest.py` 中 `_close_active_cancel`（line 1131）只处理 `run_cancelled`，不处理 `run_failed`/`final_answer` 在 `CANCELLING` 下的行为
- **影响**: 实施 Agent 跑偏 — 可能在实现时才发现需要修改 ingest mapping 以拒绝 late terminal；风险后移 — late terminal race 的正确性在 implementation review 时才被发现，可能需要返工
- **建议改法和验证点**:
  1. Plan 必须阅读 `EngineIngestMapper` 中 `final_answer`、`run_failed`、`run_suspended` 对 `CANCELLING` Run 的现有 ingest 前置条件，并显式裁决哪些 terminal 在 `CANCELLING` 下应被拒绝（因为 cancel intent 已 durable accepted，不应被 late terminal 改写）
  2. 至少需要明确三种 race 的预期行为：
     - `run_failed` after `RUN_CANCELLING` before timeout: reject（reason=`late_terminal_after_cancel`）还是 accept（作为 cooperative failure closeout）？
     - `final_answer` after `RUN_CANCELLING` before timeout: 必须 reject（用户已 cancel，不应接受最终回答）
     - `run_suspended` after `RUN_CANCELLING` before timeout: 必须 reject（`CANCELLING` 不得变成 `WAITING`）
  3. 如果现有 ingest 逻辑已正确拒绝上述 case，plan 只需声明"已验证现有 ingest 前置条件拒绝 late terminal after CANCELLING"并引用代码行号
- **修复风险（低）**: 只需阅读现有 ingest 代码并记录结论，不需要修改 ingest 逻辑（除非发现 gap）
- **严重程度（中高）**: 这是 plan 完备性问题 — plan 把设计裁决推迟给 implementation，implementation agent 需要在未知领域做设计决策

### 03-未修复-中-watchdog tick/poll 机制未指定：event-based wakeup vs periodic scan 的语义模糊

- **位置**: Plan §Slice 2 "Exact changes"（line 257-259）
- **问题类型**: 不可直接实施
- **当前写法**: "The watchdog may be implemented as a reusable tick method plus loop. Tests should be able to invoke tick deterministically without sleeping where possible." 以及 "On cancel_run / cancel_session_runs commit that produces or replays an active cancel target, wake the watchdog in addition to best-effort active registry propagation, if the selected implementation has an event-based wakeup."
- **反例/失败场景**:
  1. Implementation agent 需要决定 watchdog 是纯 event-driven（仅在 cancel 时被唤醒检查），纯 periodic scan（固定间隔扫描 `CANCELLING` Run），还是 hybrid（event 唤醒 + periodic fallback）
  2. 如果是纯 event-driven 且 wakeup 丢失（例如 commit 成功但 wakeup 调用前进程崩溃），`CANCELLING` Run 会永久悬空直到下次 reopen
  3. 如果是纯 periodic scan，sleep interval 需要 plan 指定（太短浪费 CPU，太长延迟 timeout closeout 精度）
  4. Plan 的 "if the selected implementation has an event-based wakeup" 将决策权完全交给 implementation agent
- **为什么有问题**: Plan 未裁决 watchdog 的调度模型。这直接影响 timeout 精度、reopen 后首次扫描时机、以及 `cancel_run` 后 timeout closeout 的延迟上限。Implementation agent 需要在调度模型上做设计决策，这在 plan review 阶段应已确定。
- **直接证据**: Plan line 257-259 的模糊措辞；`HostDispatchScheduler` 现有 background task 模式（heartbeat loop、drain loop、promotion loop）均为 periodic sleep + wakeup port 唤醒的 hybrid 模式
- **影响**: 实施 Agent 跑偏 — 可能选择过简（纯 event-driven 丢失 wakeup 导致悬空）或过重（独立 periodic loop 增加不必要的 runtime 复杂度）的方案
- **建议改法和验证点**:
  1. 建议采用 hybrid 模型：watchdog tick 在每次 cancel 时通过 event 唤醒，同时以固定 interval（如 `dispatch_poll_interval_seconds` 或独立配置）做 periodic scan 作为 fallback
  2. Plan 应明确 tick interval 的默认值（建议 1-5 秒，或复用 `dispatch_poll_interval_seconds`），并声明该 interval 只影响 timeout 检测延迟，不影响 timeout 阈值本身的语义
  3. `test_active_cancel_watchdog_noops_before_timeout`（line 273）的 "tick before timeout" 语义依赖确定的 tick 触发方式
- **修复风险（低）**: 只需在 plan 中明确调度模型
- **严重程度（中）**: Plan 的 Slice 2 实现依赖此决策；不明确会导致 implementation agent 自行裁决后 review 阶段返工

### 04-未修复-低-中-reopen CANCELLING 超时判断的时钟语义未考虑 durable timestamp 可能来自不同 Host instance

- **位置**: Plan §Implementation Decisions "Scheduler close boundary"（line 173-174）；Plan §Slice 2 test（line 274）
- **问题类型**: 状态机漏洞
- **当前写法**: Plan 要求 reopen 时 "compute elapsed time from latest RUN_CANCELLING or linked CANCEL_REQUESTED timestamp"
- **反例/失败场景**:
  1. Host instance A 在 `T=0` 写入 `RUN_CANCELLING`
  2. Host instance A 的时钟比 Host instance B 快 30 秒（clock skew）
  3. Host instance A 崩溃，Host instance B reopen 执行 watchdog scan
  4. Host instance B 用自己的 `datetime.now(UTC)` 减去 `RUN_CANCELLING` 的 `occurred_at`（来自 instance A 的时钟）
  5. 如果 instance A 时钟快：elapsed 被高估，可能过早 timeout；如果 instance A 时钟慢：elapsed 被低估，timeout 延迟
- **为什么有问题**: Plan 假设所有 Host instance 的 UTC 时钟同步，未考虑 clock skew。在真实多进程/多机部署中，`RUN_CANCELLING` 的 `occurred_at` 由写入方的时钟决定，而 reopen 方的 `now()` 由读取方时钟决定。虽然 plan 假设单 Host instance（composition root 显式共享 registry），但 reopen 语义天然跨 instance。
- **直接证据**: Timestamp 来源于 `RUN_CANCELLING` EventLog row 的 `occurred_at` 字段（由 `request.occurred_at` 写入，run_transition.py:3801）
- **影响**: 轻微 — 当前 Host 设计假设单进程（ActiveWorkerRegistry 是进程内），clock skew 风险限于 reopen 场景且通常 UTC 偏差在秒级。但 plan 应记录此假设
- **建议改法和验证点**: Plan 应在 residual risk 中记录：timeout 判断依赖 Host instance 本地 UTC 时钟；跨 instance reopen 时 clock skew 可能导致 timeout 提前或延迟（量级通常为秒级），不作为 correctness bug 处理
- **修复风险（低）**: 只需记录假设
- **严重程度（低-中）**: 不影响 code-generation-readiness，但应作为 residual risk 记录

### 05-未修复-低-plan 声称 "no schema change" 但 EventLog payload 扩展未被现有 watcher/projection 兼容性检查覆盖

- **位置**: Plan §Contract "Durable schema"（line 97）；Plan §Implementation Decisions "Diagnostic payload"（line 153-156）
- **问题类型**: 契约缺失
- **当前写法**: "Durable schema: no table, index, column, or schema version change is required." Plan 计划在 `ATTEMPT_CANCELLED` / `RUN_CANCELLED` payload 中新增 `timeout_seconds`、`watchdog_owner`、`worker_lifecycle_signal` 等字段
- **反例/失败场景**: 现有 `ATTEMPT_CANCELLED` / `RUN_CANCELLED` payload 已被 cooperative cancel path 写入，watcher/projection 可能对 payload 结构有隐式假设。新增字段不会破坏 SQLite schema，但可能影响：
  - 读取 `ATTEMPT_CANCELLED` payload 做 diagnostic 的 tool trace projection
  - 读取 `reason` 字段做分类的 audit/outbox projection
  - LLM-facing material（如果未来被投影，plan 已声明需改写）
- **为什么有问题**: Plan 说 "no schema change" 是正确的（SQLite 表结构不变），但 EventLog payload 的 contract 扩展（即使是 additive）需要验证现有 consumer 不会因新字段而误判。这不是 blocking issue，但 plan 应在 tests 中验证现有 watcher 对 timeout-CANCELLED payload 的兼容性
- **直接证据**: 现有 cooperative cancel closeout 写入的 `ATTEMPT_CANCELLED` / `RUN_CANCELLED` payload（`_active_attempt_cancelled_event_request` / `_active_run_cancelled_event_request` in run_transaction.py）的 payload 字段集与 plan 规划的 timeout 字段集不同
- **影响**: 低风险 — 新字段是 additive，不会破坏现有 consumer 的字段读取（前提是 consumer 使用 defensive access）。但未经测试验证
- **建议改法和验证点**: Slice 2 的 public smoke test 应包括：watch session events 确认 timeout-CANCELLED 的 `HostEvent` 投影（如 `RunSnapshot`）正确携带 reason，且不因新增 diagnostic 字段而异常
- **修复风险（低）**
- **严重程度（低）**

### 06-未修复-低-`ActiveCancelTimeoutCloseoutInput` 的 `dispatch_record_id` 字段来源未定义

- **位置**: Plan §Contract "Run / Attempt terminal policy"（line 128）
- **问题类型**: 契约缺失
- **当前写法**: "Terminal payload must include at least: ... dispatch_record_id ..."

- **为什么有问题**: `dispatch_record_id` 是 diagnostic payload 的一部分，但 plan 未说明如何获取。Implementation agent 需要确认 `read_dispatch_record_by_attempt_id` 是否已存在（确实存在 — state.py 已导入）并在 timeout closeout helper 中调用它
- **直接证据**: `run_transition.py:2146-2148` — 现有 `active_cancel_closeout_in_transaction` 已经通过 `read_dispatch_record_by_attempt_id` 获取 dispatch record
- **影响**: 轻微 — 现有 helper 已实现此 join，implementation agent 可以参考
- **建议改法和验证点**: Plan 应在 Slice 1 的 "Exact changes" 中明确说明是否需要新增 state reader，或确认现有 reader 足够
- **修复风险（低）**
- **严重程度（低）**

## Final Plan Review Conclusion

**pass-with-risks**

Plan 在架构边界、Slice 切分、CAS 语义和设计真源对齐方面基本正确。两个 slices（durable contract + watchdog integration）构成合理的语义闭环。Plan 正确识别了 non-cooperative worker 场景下的 Host durable truth 缺口，且未过度设计（不引入 provider kill API、不创建第二套 watchdog runtime、不修改 Engine contract）。

但有两个 material issues 阻止 plan 成为完全 code-generation-ready：

1. **Finding 01（高）**：Reopen 路径未考虑与现有 `StartupRecoveryScanner` 的冲突。Clean-close-reopen 场景下 recovery scanner 会将 `CANCELLING` Run 提前标记为 `LOST`，使 watchdog 的 reopen timeout closeout 失效。Plan 必须裁决 watchdog 与 recovery scanner 的执行顺序或分工。

2. **Finding 02（中高）**：Late terminal race（`run_failed`/`final_answer`/`run_suspended` after `RUN_CANCELLING`）的预期行为未在 plan 中裁决，plan 将设计决策推迟给 implementation agent。Plan 应阅读现有 ingest mapping 代码并显式声明这些 race 的 accept/reject 规则。

Finding 03（watchdog 调度模型未指定）和 Finding 04（clock skew）是 lower-severity 的完备性问题，可在 plan fix 中一并处理。
