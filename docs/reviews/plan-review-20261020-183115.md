## 4. Findings

### 1-未修复-中-README wheel 安装的裸 dayu-cli 检查会被本次源码默认入口遮蔽

- **位置**：`docs/gateflow/public-original-read-r1-r3-20261020-install-entry-plan.md:99`（README 更新范围）、`:114`（wheel 语义边界）；`README.md:52-62`（现有 wheel 安装确认）。
- **问题类型**：契约缺失 / 验证缺口（README 语义）。
- **当前写法**：计划要求 macOS 源码安装在 `~/.local/bin/dayu-cli` 发布默认入口，并在 `~/.zshrc` 前置 `$HOME/.local/bin`；同时 plan 只说“不要为本次增量改变 wheel 安装语义”“避免让 macOS 源码默认入口承诺被误读为任意 wheel 安装都会改 shell 配置”，但 README 更新清单没有要求改写 wheel 段落的裸 `dayu-cli --help` 确认命令。
- **反例/失败场景**：用户按 README 1.1 完成 macOS 源码安装，当前交互 shell 的 PATH 前部已有 `~/.local/bin`，且该链接指向本仓 `.venv/bin/dayu-cli`。之后用户按 README 1.2 把 wheel 安装到另一个未激活的 venv 或系统 Python，再执行 README 要求的裸 `dayu-cli --help`；shell 按 PATH 先命中源码安装的 `~/.local/bin/dayu-cli`，help 退出 0，但用户并没有验证 wheel 安装。用户会把“命令存在且 help 成功”误当成 wheel 环境已正确安装。
- **为什么有问题**：本次变更引入了全局默认命令和 PATH 前部目录，裸 `dayu-cli` 不再唯一指向“当前安装环境”；README 1.2 的既有确认命令因此失去辨识力。plan 的 §5 要求 README 只写用户可执行操作，却没有要求消除这一现有用户可见歧义；这与 plan 自己在 `:114` 提出的“避免误读”目标不一致。
- **直接证据**：`README.md:52-62` 的 wheel 段落只有裸 `dayu-cli --help`；plan `:76` 明确将 `$HOME/.local/bin` 放到命令搜索前部；plan `:114` 只说不要改变 wheel 语义，未列 README 1.2 的消歧动作；E2、E5、E6、E8 证明源码入口在未激活 shell 中是可直接成功的真实命令。
- **影响**：用户可见的安装确认失真；排障时会把 wheel 环境、源码环境、默认链接混为一谈；支持成本增加。不会造成数据损坏，也不阻塞源码安装目标，但属于本次新增默认入口引入的 README 回归风险。
- **建议改法和验证点**：在 IE1 的 README 更新中，把 wheel 段落的确认命令改为目标环境的显式命令，例如激活目标 venv 后执行 `python -m pip show dayu-agent` 与 `python -m dayu.cli --help`，或使用该 venv 的绝对 `<venv>/bin/dayu-cli --help`；同时用一句用户可读说明指出：完成 macOS 源码安装后，`~/.local/bin/dayu-cli` 会在交互 shell 中优先于其它同名入口。验证点：README 的 wheel 段落不再依赖裸 PATH 解析；源码安装段落仍明确“新开未激活正常 zsh”；不新增代码/脚本，不改变 wheel 安装语义。
- **修复风险（低/中/高）**：低。
- **严重程度（低/中/高/严重）**：中。

> 该 finding 非 blocking。它不要求扩大 IE1 的代码范围，只要求在计划已经包含的根 README 更新里消除一个由默认入口直接造成的用户可见歧义。若主控认为 wheel 安装不属本轮用户目标，可将其降为 residual risk 并由 README owner 在后续修正；但不能把裸 `dayu-cli --help` 当作 wheel 安装的独立证明。

## 5. Open Questions

1. **Post-acceptance sync 的风险分类标签**：plan `:222` 把“真实正常 shell、实际 metadata 与核收 commit 尚无本次证据”列为 `requiring new issue or explicit user decision`，但 binding goal `:13-15` 和 authorization update `:5` 已经明确授权“工程核收并收到安装通知后 sync”。建议主控把该行改为“sequencing stop / deferred-to-notification，已有授权”，避免被读成新的用户决策或工程阻塞；这不影响 IE1 实施，也不改变真实 sync 前的停点。
2. **隔离集成的“来源 manifest”未定义**：plan `:141` 要求准备“当前待审源码的独立副本和来源 manifest”，但没有定义 manifest 的 schema、生成 owner 或如何绑定到 HEAD。建议实现时直接使用 `git archive` 的精确 HEAD 产物或一个有类型的 tracked-file 哈希 manifest；若只是测试夹具，明确它不承担核收 commit 证明，而由 §7 的真实 sync 证明确。属于实现/代码审核问题，不是 blocking。
3. **`~/.zshrc` 的两个写入 owner**：publisher 将新增 PATH block，`dayu-cli init` 已有 secret block 和 read-modify-write 路径。代码事实（E9、E10）表明不同 marker 顺序执行可互相保留；但 plan 的测试矩阵只明确覆盖“publisher 保留 init block”，没有覆盖“init 在 publisher 之后运行”或两个进程并发读写的 lost update。建议二选一：在 IE1 测试中加一个顺序 init-after-publisher 保留测试；或明确并发写入不在本轮承诺，记录为 residual risk 并指定 owner。不要为此引入跨文件事务或 durable journal。
4. **alias/function 检测边界**：publisher 不解析用户整份 shell 配置，也不改 alias/function；真实 sync 的 `whence -w` 会暴露 alias/function 并诚实失败。若用户环境确实存在 alias，验收会失败而非静默通过；这符合“不猜用户配置”，属于 residual risk，不是确定缺陷。

## 7. 对“最小方案 / owner / 验收扩张”的判断

- **最小方案**：现有 venv/pip 安装 + 一个小型 publisher 是合理最小方案。只补 `ln -s` 不能保证 PATH 持久生效；把 marker 去重、冲突校验、失败处理写进 README 会变成不可测试的内嵌安装程序。计划明确排除平台矩阵、uv 迁移、可配置安装后端、插件、安装数据库、journal、运行期自修复，没有过度设计。
- **Owner**：包名/版本/console script 仍归 `pyproject.toml`；实际安装 metadata 归目标 venv 的 dist-info；默认链接与持久 PATH 归 `scripts/publish_source_entry.py`；其他工具环境与调用方配置不动。分层清晰，没有把安装逻辑塞进业务 CLI 或 `dayu.runtime`。
- **验收扩张**：IE1 的测试矩阵均能映射到 binding goal 的“旧入口/缺席入口转换、重复执行、用户文件保留、新正常 shell、来源绑定”。没有新增业务回归、财报契约、版本 flag 或平台矩阵。Finding 1 只要求修正 README 现有 wheel 段落的确认命令，不新增代码验收项。
- **验证充分性**：工程阶段用隔离 HOME + 源副本真实安装 + 新 zsh + 实际 dist-info 的矩阵，足以证明“新流程”而非现成链接；真实 sync 前的核收/通知停点符合用户授权。writer 的 startup receipt 没有被用作包安装成功证据，界限正确。

## 8. 最终结论

**`pass-with-risks`**。
