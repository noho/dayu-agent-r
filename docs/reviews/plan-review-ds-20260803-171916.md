## Findings

### P1-未修复-中-真实 provider smoke 选择与冻结 Mimo 优先要求冲突

- **位置**: Slice S3 "Exact allowed changes"、Open questions（plan 第 298-305 行、第 409 行）
- **问题类型**: 非最优方案 / 契约缺失
- **当前写法**: plan 明确写 "复用现有 `PROVIDER_CASES[1]`（DeepSeek）和环境开关"；open question 写 "真实 provider smoke 继续使用现有 `PROVIDER_CASES[1]`（DeepSeek）和环境开关，不扩成 provider matrix"
- **反例/失败场景**: 用户 challenge #5 明确指出 "原冻结要求真实 provider 优先 Mimo plan，不可用才 DeepSeek"。生产环境 `compactor_baseline.model_id` 指向 `mimo-v2.5-pro-plan`（`dayu/config/README.md:181`、`dayu/config/README.md:360`），即 compactor 的生产模型是 Mimo。若 smoke 只在 DeepSeek 上运行，则：
  1. smoke 的 provider behavior（temperature sensitivity、instruction following、JSON format adherence）与生产 compactor 不一致；
  2. prompt trust boundary 在 Mimo 上的实际效果未经 smoke 验证；
  3. 用户明确要求优先 Mimo，plan 直接选了 DeepSeek 且未给出偏离理由。
- **为什么有问题**: 与用户冻结要求直接冲突。`PROVIDER_CASES[0]` 是 Mimo（`public_smoke_support.py:815-823`），`PROVIDER_CASES[1]` 是 DeepSeek（`public_smoke_support.py:824-832`）。现有代码 `test_public_compact_smoke.py:947` 使用 `PROVIDER_CASES[1]` 是历史选择，不等于 plan 可以在已知冻结要求的情况下继续沿用而不说明理由。
- **直接证据**:
  - `tests/host/public_smoke_support.py:815-823`: Mimo 是 `PROVIDER_CASES[0]`
  - `tests/host/public_smoke_support.py:824-832`: DeepSeek 是 `PROVIDER_CASES[1]`
  - `tests/host/test_public_compact_smoke.py:947`: 现有 smoke 硬编码 `PROVIDER_CASES[1]`
  - `dayu/config/README.md:181`: `compactor_baseline.model_id` 指向 `mimo-v2.5-pro-plan`
  - 用户 challenge #5 原文
- **影响**: 实施 Agent 若按 plan 字面执行，smoke 结果不能代表生产 compactor 行为；若 Mimo credential 可用但未用，浪费了最有价值的验证机会。
- **建议改法和验证点**:
  1. 改为使用 `PROVIDER_CASES[0]`（Mimo），fallback 到 `PROVIDER_CASES[1]`（DeepSeek），或直接复用 `first_available_provider_case()`（`public_smoke_support.py:863`）但明确 first 即 Mimo。
  2. 若坚持用 DeepSeek，必须在 plan 或 open question 中写明偏离理由（如 "Mimo credential 在 smoke 环境不可用" 或 "Mimo 不支持 compaction 所需的 strict JSON mode"），且理由必须基于事实而非假设。
  3. smoke 结果记录中明确标注使用的实际 provider。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### P2-未修复-低-中-完整 example 内容未在 plan 中给出，实施 Agent 需自行设计，存在返工风险

- **位置**: Slice S1 "Exact allowed changes"（plan 第 241-252 行）、Contract decision #2（plan 第 153-163 行）
- **问题类型**: 不可直接实施 / 切片过粗
- **当前写法**: plan 给出 example labels（PS1/PF1/PA1/PI1/PR1/T1/E1/A1/T2）和覆盖要求，但没有给出 example input JSON 与 example output JSON 的具体内容。
- **反例/失败场景**: 实施 Agent 需自行设计一个覆盖全部 8 种 `source_kind`、展示 session summary/evidence fact/answer anchor/forward intent/reference continuity/diagnostic/drop 的完整 example pair。若设计的 example 不满足以下任一条件，S1 会在 stop condition 触发时失败：
  1. example output 的 label 全部来自 example input 且 exact coverage partition；
  2. example output 被 `parse_conversation_compact_output_vnext` 成功解析；
  3. example output 被 `accept_compact_candidate_v2` 接受（含 policy caps、无 duplicate/contradiction）；
  4. example 足够紧凑，不显著膨胀 prompt token 数。
  实施 Agent 可能反复尝试多次才能通过，而 plan 未提供预验证的 example 草稿作为起点。
- **为什么有问题**: plan 在 contract decision 中描述了 example 的语义要求，但没有给出具体 JSON 文本。从 labels 到 production-valid JSON 之间的设计工作留给了实施 Agent。这不是 plan 的致命缺陷（plan 不需要写最终代码），但对于 "code-generation-ready" 标准，example 是 prompt contract 的核心验收物，至少需要一份通过 production parser 的草稿来降低实施风险。
- **直接证据**: plan 第 161-162 行只写了 label 列表和覆盖要求；plan 第 252 行 stop condition 明确 "example 无法在不改变 output schema 的前提下通过 production owner" 即失败。
- **影响**: 实施 Agent 可能在 example 设计上消耗额外 attempt，或在多次失败后试图放宽 schema 约束来通过验收。
- **建议改法和验证点**:
  1. （推荐）在 plan 中附加一份已验证通过 production parser + `accept_compact_candidate_v2` 的 example pair JSON 草稿。
  2. （备选）在 plan 的 open question 中标注 "example 内容由实施 Agent 设计，首轮必须通过 production parser/governance 验收；若失败，回到 plan 裁决而非放宽 schema"。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低-中（取决于实施 Agent 对 v2 schema 的熟悉程度；本仓库 Agent 应熟悉，故偏轻）

### P3-未修复-低-cap message 精确化与现有 bounded truncation 的张力未量化

- **位置**: Contract decision #4 "Exact policy feedback"（plan 第 175-185 行）、Slice S2 "Error handling/invariants"（plan 第 272-276 行）
- **问题类型**: 契约缺失
- **当前写法**: plan 要求 policy reject message 中加入 "当前字符数/cap" 或 "当前 item 数/cap"。同时承诺 "保留现有脱敏、单 issue 上限、issue count 上限和总体 feedback 上限"。但未分析精确化后的 message 长度是否仍在 `MAX_COMPACT_REPAIR_ISSUE_MESSAGE_CHARS=240` 和 `MAX_COMPACT_REPAIR_FEEDBACK_CHARS=8192` 范围内。
- **反例/失败场景**: 当前 message 如 `"session_summary 超过 Memory policy size cap。"` 约 40 字符。精确化后如 `"session_summary 当前 2847 字符，超过上限 2000 字符；请将 text 缩减至 2000 字符以内，不得截断句子中间。"` 约 80 字符。仍在 240 字符限制内。但当多个 section 同时超限（极端场景：summary size + 4 个 section item + 4 个 section size），feedback 可能包含 9 条 issue。若每条从 ~40 字符膨胀到 ~100 字符，总长从 ~360 增加到 ~900，仍在 8192 内。当前未量化但实际风险低。
- **为什么有问题**: plan 承诺保留边界，但未给实施 Agent 提供量化的安全边际分析。实施 Agent 可能在实现后才发现某些极端 reject 场景下精确 message 被 `_bounded_issue_message` 截断到不可读，或 feedback 整体超过 `MAX_COMPACT_REPAIR_FEEDBACK_CHARS` 导致更多 issue 被丢弃。
- **直接证据**: `compaction.py:1616-1620` 定义 240/8192 边界；`context_governance.py:496` 当前 message 不含数值；plan 第 185 行 "actual 与 cap 均在 `_collect_policy_issues/_section_caps` 已有数据流中产生" 正确但未量化。
- **影响**: 低——现有边界足够宽，精确 message 极不可能触发截断。但如果实施 Agent 写出过长的 message（例如包含完整的缩减指南），可能在边缘场景被截断。
- **建议改法和验证点**:
  1. 在 plan 或 S2 validation 中增加一条断言：精确化后的单条 message 不超过 200 字符（留 40 字符安全边际）。
  2. 或在 S2 contract test 中构造所有 section 同时超限的极端场景，验证 projected feedback 仍在 8192 内且每条 message 完整可读。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### P4-未修复-低-plan 未显式覆盖 prompt 修改后 `_FORBIDDEN_COMPACTOR_PROMPT_TERMS` 与 `_FORBIDDEN_COMPACTOR_MATERIAL_TERMS` 的同步更新

- **位置**: Slice S1 "Allowed files"（plan 第 235-239 行）、plan 全局
- **问题类型**: 测试缺口
- **当前写法**: plan 的 affected test files 包含 `test_public_compact_smoke.py`，变动描述包括 "删除固定未定义 T1 oracle；加入完整 example contract 与 opt-in real-provider injection/cap smoke"。但 plan 未提及 `_FORBIDDEN_COMPACTOR_PROMPT_TERMS` 和 `_FORBIDDEN_COMPACTOR_MATERIAL_TERMS` 这两个黑名单是否需要同步更新。
- **反例/失败场景**: `test_public_compact_smoke.py:138-158` 定义 `_FORBIDDEN_COMPACTOR_PROMPT_TERMS` 包含 `"vNext"`、`"migration"` 等禁止术语。`test_public_compact_smoke.py:159-169` 定义 `_FORBIDDEN_COMPACTOR_MATERIAL_TERMS`。prompt 修改后：
  1. 若新增了黑名单中已有的术语（如 example 中意外出现 `vNext`），测试会失败——这实际是正确行为，测试起到保护作用。
  2. 若 prompt 新增了不应出现的内部术语（如 `CompactRepairFeedbackV2`），但该术语不在现有黑名单中，测试无法捕获。
  3. plan 新增的 LLM-facing 术语（如 `required_action`、八种 source kind 的业务语义）不需要加入黑名单，因为它们是 LLM-facing contract。
- **为什么有问题**: 这不是 plan 的缺陷——现有黑名单测试是被动保护，plan 的 prompt 修改不会引入黑名单中的术语。但 plan 应确认实施 Agent 不会意外引入新内部术语后忘记更新黑名单。这是一个低风险但值得在 plan 中提及的 check point。
- **直接证据**: `test_public_compact_smoke.py:138-158` 黑名单；plan 未提及黑名单同步。
- **影响**: 低——如果实施 Agent 意外引入新内部术语到 prompt，黑名单测试不会捕获；但 prompt owner（实施 Agent）应自行确保不引入内部术语。
- **建议改法和验证点**: 在 S4 validation checklist 中增加一项："确认修改后的 prompt 不包含 `_FORBIDDEN_COMPACTOR_PROMPT_TERMS` 之外的内部实现术语；若有，同步更新黑名单"。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### Challenge 4: 测试是否把静态 contract、deterministic owner behavior、真实 provider observation 正确分层

**裁决: accepted — 分层清晰**

| Layer | Test | 验证对象 |
|---|---|---|
| Static contract | prompt assets static checks | marker 语义、trust boundary、八种 source kind、open-string 业务说明、repair exact schema |
| Deterministic owner behavior | example extraction + production parser/governance | output JSON exact v2；label 同源；coverage exact partition |
| Deterministic owner behavior | renderer adversarial (current/trace/evidence/answer parameterized canaries) | 原文不被过滤；位于 untrusted block；控制规则在 block 外 |
| Deterministic owner behavior | repair projector (internal feedback -> rendered prompt) | block exact keys；不含 attempt/additional count |
| Deterministic owner behavior | policy owner (each section `== cap` accept, `+1` reject) | message actual/cap 与传入 policy instance 一致 |
| Regression | existing strict parser matrix | duplicate/unknown/missing/type/enum/blank 继续 fail closed |
| Opt-in real observation | real provider smoke (DeepSeek/Mimo) | injection 不改变 contract；repair 后 parsed candidate accepted 且落入 cap |
| Static verification | publication frozen manifest + pyright | prompt hash、manifest hash、无类型错误扩散 |

**证据**: plan 第 337-350 行 test matrix；plan S1-S3 validation commands。
