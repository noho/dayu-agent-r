## Reviewed Target and Scope

The plan proposes hardening `dayu-cli interactive` idle-input Ctrl+C behavior: first Ctrl+C should return to a clean prompt, second Ctrl+C should exit. The fix is scoped to CLI UI (`dayu/cli/**`) with no Host/Engine contract changes. One implementation slice is proposed. Running-state cancellation through public Service/Host APIs is preserved.

## Findings

### F01-未修复-中-implementation-decision-3-ambiguous-composer-protocol-overengineering-risk

- **位置**: 计划 "Implementation Decisions" 第 3 条 (line 128)
- **问题类型**: 过度设计 / 不可直接实施
- **当前写法**: "Prefer extending the input composer boundary to return a typed interrupt result or raising a CLI-local typed exception over catching broad KeyboardInterrupt at the outer command boundary."
- **反例/失败场景**: 实施 Agent 解读为要求修改 `InteractiveComposer` 协议，在 `PromptToolkitInteractiveComposer.read()` 内部捕获 `KeyboardInterrupt` 并转换为 typed result 或自定义异常，同步修改 `InputReaderComposer`、协议文档和所有 composer 测试。这比在 input loop 层捕获 `KeyboardInterrupt` 更侵入，且没有行为收益。
- **为什么有问题**: 当前 `InteractiveComposer` 协议已在 docstring 中明确文档化 `KeyboardInterrupt` 为有效异常（`composer.py:30`: "用户在空 draft 中请求中断时抛出"）。prompt_toolkit key binding（`composer.py:117-124`）已正确实现"非空输入→清空，空输入→KeyboardInterrupt"的语义区分。修复应该在 command loop 层（`interactive.py:505-508`）捕获该异常并实现两步计数器，不需要修改 composer 协议。计划写的是"prefer... over..."，但这个偏好表述会让实施 Agent 在两种路径间犹豫，增加不必要的协议变更风险。
- **直接证据**:
  - `composer.py:24-32`: `InteractiveComposer` 协议已声明 `KeyboardInterrupt`
  - `composer.py:117-124`: key binding 已区分非空/空输入
  - `interactive.py:505-508`: input loop 只捕获 `EOFError`
  - `main.py:131`: 顶层捕获 `KeyboardInterrupt` 并返回 130
- **影响**: 实施 Agent 可能对 composer 协议做不必要的侵入式修改，增加变更范围、测试更新量和 review 复杂度；最坏情况下可能破坏非空输入 Ctrl+C 清空缓冲区的现有正确行为。
- **建议改法和验证点**:
  1. 将 decision #3 改为明确指令："在 input loop（`interactive.py:505-508`）捕获 `KeyboardInterrupt`，实现两步空闲中断计数器；不修改 `InteractiveComposer` 协议或 `PromptToolkitInteractiveComposer` 内部行为。"
  2. 或者，如果 typed result 确实有充分理由（例如希望在未来支持非 prompt_toolkit composer），在计划中明确说明为什么捕获标准 Python 异常不够，并给出 typed result 的具体形状。
  3. 无论选哪条路径，验证点应包括：非空输入 Ctrl+C 仍清空缓冲区（现有 key binding 行为不被破坏）。
- **修复风险**: 低
- **严重程度**: 中

### F02-未修复-低-open-ux-counter-reset-semantics-unresolved

- **位置**: 计划 "Risks / Open Questions" 第 4 条 (line 179)
- **问题类型**: open question 未收敛
- **当前写法**: "should first idle Ctrl+C after an empty prompt reset the 'second Ctrl+C exits' counter immediately after redisplay, or should the second consecutive Ctrl+C exit until the user types input?"
- **反例/失败场景**: 实施 Agent 自行选择一种语义实现；review 阶段发现与用户期望不符，需要返工修改状态机逻辑。
- **为什么有问题**: 这个 UX 决策直接影响 idle interrupt 状态机的 reset 条件设计。如果实施 Agent 选错，review 会要求修改状态机逻辑，增加返工。计划应该做出决定并记录理由，而不是把 UX 设计决定推给实施 Agent。
- **直接证据**: 计划 line 179 将此列为 open question；计划 line 120 只写了"second idle Ctrl+C should exit locally"，但没有说明 first interrupt 后什么条件重置计数器。
- **影响**: 实施 Agent 自行裁决 → review 可能拒绝 → 返工。严重程度低因为两种选择都是合理的，且修改成本小。
- **建议改法和验证点**: 在计划中明确选择一种语义并记录理由。推荐对齐 bash/Codex 行为：第一次空闲 Ctrl+C 后 prompt 重显示即重置计数器（用户需要连续两次 Ctrl+C 才能退出，中间有任何非中断行为都重置）。这样用户不会因为一次误触 Ctrl+C 后，下一次（可能几分钟后）再按 Ctrl+C 就意外退出。
- **修复风险**: 低
- **严重程度**: 低

## Open Questions

1. 计划 line 179 的 UX counter reset 语义（同 F02）。建议 controller 在 dispatch implementation 前裁决。
2. 计划 line 178 的多行输入 Ctrl+C 行为："If first idle Ctrl+C should clear a partially composed multiline input rather than only redisplay the prompt"。当前 prompt_toolkit 不支持 multiline（`composer.py:94`: `multiline=False`），因此这个风险实际不存在。计划可以删除或标注为"当前不适用"。
