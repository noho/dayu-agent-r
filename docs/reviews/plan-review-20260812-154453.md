## Material Findings

### 1-needs-evidence-中-`DoclingCancellationInput` Protocol 与公共 `CancellationToken` 重复

- **位置**: §6.1 类型与签名，`DoclingCancellationInput` Protocol 定义
- **问题类型**: 过度设计 / 最佳实践偏离
- **当前写法**: plan 定义新 Protocol `DoclingCancellationInput`，只含 `is_cancelled() -> bool` 一个方法，作为 converter 的 typed cancellation 输入。
- **反例/失败场景**: Engine 公共契约 `dayu.contracts.cancellation.CancellationToken`（`is_cancelled()` + `cancel_reason()` + `requested_at()`）是层中立、`@runtime_checkable` 的 Protocol，已在 `FinsIngestionRuntime` 的 `_DirectCancellationChecker` 和 durable job path 中使用。`DoclingCancellationInput` 是 `CancellationToken` 的严格子集（只取 `is_cancelled()`）。如果 converter 接受 `DoclingCancellationInput`，调用方必须额外适配已有 `CancellationToken` / `_DirectCancellationChecker`，而适配代码只做 `lambda: token.is_cancelled()` 或 `adapter.is_cancelled()` 这类机械投影。这引入了不必要的 Protocol 层次，且未解释为何 converter 不能直接依赖已有的层中立 `CancellationToken`。
- **为什么有问题**: plan §4.1 已将 `dayu.runtime` 定位为层中立 primitive，`CancellationToken` 同样位于 `dayu.contracts` 层中立包，不 import Fins。converter 接受 `CancellationToken | None` 比接受 `DoclingCancellationInput | None` 更朴素、减少一次 adapter 层、消除 "为什么不能用标准 token" 的读者困惑。当前写法增加了 implementation agent 的判断负担：何时用 `DoclingCancellationInput`、何时用 `CancellationToken`、何时用 `Callable[[], bool]`？
- **直接证据**:
  - `dayu/contracts/cancellation.py`: `CancellationToken` Protocol（`is_cancelled()`, `cancel_reason()`, `requested_at()`）
  - `dayu/fins/ingestion_runtime.py` L1306-1328: `_DirectCancellationChecker.__call__` 已同时消费 `CancellationToken` 和 `_DirectStreamCancellationState`
  - plan §6.1: `class DoclingCancellationInput(Protocol): def is_cancelled(self) -> bool: ...`
- **影响**: implementation agent 可能误以为 `DoclingCancellationInput` 是新必需品，额外设计 adapter/wrapper，增加无谓的类型层次。
- **建议改法和验证点**: 将 `DoclingConverter.convert_to_json_bytes` 的 `cancellation` 参数类型直接改为 `CancellationToken | None`（或接受一个含 `is_cancelled()` 的 structural Protocol 但文档中注明 `CancellationToken` 是 canonical 实现）。若坚持保留独立 Protocol，必须在 plan 中明确解释为何 `CancellationToken` 不适用——当前 plan 无此解释。
- **修复风险（低）**: 只需修改类型标注和对应 docstring，不影响实现逻辑。
- **严重程度（中）**: 不阻塞整体架构，但会导致 implementation agent 产生不必要的类型碎片。

### 3-needs-evidence-中-`async prepare_upload` 的可实施性：sync facade `upload_filing()` 中的私有 event loop 与嵌套 async 调用

- **位置**: §6.2 同步 producer 线程与 async handle 的组合；§11.2 upload filing/material 数据流
- **问题类型**: 不可直接实施 / 并发恢复风险
- **当前写法**: plan §6.2 说明 "将 `DoclingUploadService.prepare_upload`、`_build_pending_assets` 改为 async"；"CN/SEC filing/material async upload workflow 直接 `await prepare_upload(...)`"；"现有 sync pipeline facade 继续在 producer 线程内运行整个 async stream；不在 service 内调用 `asyncio.run`，不建立嵌套 event loop"。
- **反例/失败场景**: 当前 `CnPipeline.upload_filing()` (cn_pipeline.py L713) 是同步方法，内部调用 `asyncio.run(self.upload_filing_stream(...))`。`upload_filing_stream()` 是 async generator，内部调用 `self._upload_service.prepare_upload(...)`（L870，当前是同步调用）。plan 把 `prepare_upload` 改为 async 后，`upload_filing_stream` 中必须 `await self._upload_service.prepare_upload(...)`。到这里没问题——async stream 内 await 是自然的。

  但 plan §6.2 说 "不在 service 内调用 `asyncio.run`"，这指的是 `DoclingUploadService` 内部不做 `asyncio.run()`。然而 `ProductionFinsUploadRunner.run_upload()`（service_runtime.py L61）是同步方法，它调用 `self.sec_pipeline.upload_filing()` 或 `self.cn_pipeline.upload_filing()`，这两个 sync facade 用 `asyncio.run()` 包裹 async stream。**这是 pipeline facade 而非 service**，所以不违反 plan 约束。

  真正风险在于：当前 `DoclingUploadService._convert_with_docling` 是一个**同步 callback**，在 producer 线程内直接调用 `convert_pdf_bytes_with_docling`（同步阻塞）。改为 async 后，`prepare_upload` 需要 `await self._docling_converter.convert_to_json_bytes(...)`。这个 await 发生在 producer 线程的私有 event loop 中。`ProcessDoclingConverter.convert_to_json_bytes` 内部 await `InterruptibleProcessHandle.wait()` 等。——这些都可以在私有 event loop 上正常工作。

  但 **跨线程 cancellation token 可见性** 有一个细节：plan §6.2 说 "CLI 主 loop 可继续接收 SIGINT，并通过加锁的 direct cancellation state 让 producer 线程看到 `is_cancelled()`"。当前 `_DirectCancellationState` 使用 `threading.Lock` 保护。converter 的 `is_cancelled()` 在 producer 线程的私有 event loop 中读取同一个 `_DirectCancellationState`——这在 threading 层面是安全的（`Lock` 跨线程可见）。plan 没有明确说明 converter 的 cancellation 参数如何从 `_DirectCancellationChecker` 传递到 `DoclingConverter.convert_to_json_bytes` 的 `cancellation` 参数——这个布线细节留给 implementation agent，可能产生多种不同的 adapter 实现。

- **为什么有问题**: plan §6.2 对同步 facade + 私有 event loop 的描述是正确的方向性指导，但未给出足够具体的 adapter 布线说明。implementation agent 可能对 "谁负责把 `_DirectCancellationChecker` 投影为 converter 的 `cancellation` 参数" 做出不同选择。
- **直接证据**:
  - `dayu/fins/pipelines/cn_pipeline.py` L713-L774: `upload_filing()` sync facade uses `asyncio.run()`
  - `dayu/fins/pipelines/cn_pipeline.py` L870: `self._upload_service.prepare_upload(...)` currently sync
  - `dayu/fins/ingestion_runtime.py` L1306-1328: `_DirectCancellationChecker`
  - plan §6.2 最后一段
- **影响**: implementation agent 可能引入不必要的 adapter 层或把 cancellation wiring 做在错误 owner。
- **建议改法和验证点**: 在 plan §11.2 数据流中明确标注 cancellation token 从 `_DirectCancellationChecker` 到 `DoclingConverter.convert_to_json_bytes(cancellation=...)` 的传递路径（例如：CN/SEC async workflow 在调用 `prepare_upload` 时把 `cancellation_checker` 或 adapt 后的 `DoclingCancellationInput` 传给 upload service，upload service 再原样传给 converter）。不需要重新设计，只需要一条明确的 wiring 说明。
- **修复风险（低）**: 补充 wiring 描述即可。
- **严重程度（中）**: plan 方向正确但 wiring 不够具体，可能导致 implementation agent 做不一致的 ad-hoc 适配。

### 4-accepted-candidate-中-`InterruptibleProcessFailed` → `CHILD_CRASH` 映射丢失 child 内部错误分类信息

- **位置**: §7.3 closed error/cancel 类型映射表；§8.2 状态机
- **问题类型**: 契约缺失 / 状态机漏洞
- **当前写法**: plan §7.3 映射表："runtime `InterruptibleProcessFailed`、无 descriptor 的异常退出或 signal crash → `CHILD_CRASH`，保留 exit code，不解析 error string"。同时 child 产生的 failure descriptor 有 `failure_kind`（`CONVERTER_CONSTRUCTION`、`CONVERTER_EXECUTION`、`RESULT_SERIALIZATION`）。
- **反例/失败场景**: 假设 child 内 Docling `convert()` 调用抛出 `RuntimeError`（例如模型加载 OOM 或被 SIGKILL 前已开始执行）。child 的 `_run_process_target`（interruptible_process.py L621-641）会 catch 该异常并放入 queue 为 `_ProcessFailed(error_type="RuntimeError", message="...")`。父进程 `wait()` 收到后返回 `InterruptibleProcessFailed(error_type="RuntimeError", message="...", exitcode=1)`。按 plan 映射表，这被归为 `CHILD_CRASH`。

  但 child **已经** 正常执行到了 converter.convert()，只是业务执行失败——应该归为 `CONVERTER_EXECUTION`。`InterruptibleProcessFailed` 是 runtime primitive 的通用失败包装，不区分 "child 内部业务执行失败" 和 "child 被外部 signal 杀死"。plan 简单地 "不解析 error string" 把所有 `InterruptibleProcessFailed` 归为 `CHILD_CRASH`，丢失了 child 内 `DoclingConversionError` 的分类能力。

  正确的设计应该是：child 的内部异常在 child 进程中 catch，并按 closed `failure_kind` 写入 descriptor（`status="failure"`），然后 child 以 exit 0 退出（因为 serialization 正常完成）。父进程收到 `InterruptibleProcessCompleted`（而非 `InterruptibleProcessFailed`），再从 descriptor 中读取 `failure_kind`。只有 child 崩溃（queue 无消息、非零 exit、无 descriptor）才是 `CHILD_CRASH`。

  plan §7.2 的 descriptor 设计已经有 `status: success/failure` 和 `failure_kind`，这与上述正确方案一致。但 §7.3 的映射表却把 `InterruptibleProcessFailed` 整体映射为 `CHILD_CRASH`，与 child 内部 try/catch + descriptor 失败路径产生矛盾——如果 child 正确 catch 了异常并写入 failure descriptor，父进程收到的就是 `InterruptibleProcessCompleted`（带 failure descriptor），不是 `InterruptibleProcessFailed`。所以映射表中 `InterruptibleProcessFailed → CHILD_CRASH` 的条目应该**只**在 child 没有产生有效 descriptor 时触发。
- **为什么有问题**: 映射表的文字表述 "runtime `InterruptibleProcessFailed`、无 descriptor 的异常退出或 signal crash → `CHILD_CRASH`" 把两个不同事实合并为一个分类。如果 implementation agent 按字面实现，当 child catch 了业务异常、写入 failure descriptor、但 queue 消息恰好是 `_ProcessFailed`（这不应发生——child 应该 catch 后写 success descriptor），会产生分类错误。
- **直接证据**:
  - `dayu/runtime/interruptible_process.py` L621-641: `_run_process_target` — 子进程异常 → `_ProcessFailed` → 父进程 `InterruptibleProcessFailed`
  - plan §7.2 descriptor: `status: success/failure`, `failure_kind` 闭集
  - plan §7.3 映射表第 5 行
- **影响**: 中等。如果 implementation agent 正确理解 child 内 try/catch 语义（业务异常 → failure descriptor → `InterruptibleProcessCompleted`），则不受影响。但如果机械按映射表实现（所有 `InterruptibleProcessFailed` → `CHILD_CRASH`），会错误分类可通过 descriptor 表达的 failure。
- **建议改法和验证点**: 澄清映射表：`InterruptibleProcessFailed` 只在无有效 descriptor 时归 `CHILD_CRASH`；child 内的业务异常（construction/execution/serialization）必须在 child 进程内 catch 并写入 `status=failure` descriptor，child 以 exit 0 退出，父进程收到 `InterruptibleProcessCompleted` 后从 descriptor 读取 `failure_kind`。
- **修复风险（低）**: 只需澄清文字，不改变设计。
- **严重程度（中）**: 文字歧义可能导致 implementation 分类错误。

### 5-needs-evidence-低-5.05s 阈值在 CI 环境中的可靠性未验证

- **位置**: §13.3 focused-real UF-PF09 第 4 条
- **问题类型**: 测试缺口
- **当前写法**: `poll 0.05 + terminate 2.0 + kill 1.0 + 2.0s harness margin = 5.05s` 为硬上限。
- **反例/失败场景**: CI runner 在 macOS 上 `asyncio.to_thread(process.join, grace_seconds)` 的 wall-clock 精度可能受系统负载影响。2.0s harness margin 在开发机器上足够，但在 CI 共享 runner 上（高 CPU steal、I/O 拥塞）可能不够。若 UF-PF09 因环境抖动超时而 fail，会阻塞 WU——plan §13.3 明确说 "若 5.05s 阈值失败，先报告 terminate/kill/cleanup 所处状态和进程树，不提高阈值掩盖缺陷"。这本身是正确的阻塞策略，但 plan 应该说明阈值是否包含 `asyncio.to_thread` 的调度延迟。
- **为什么有问题**: `asyncio.to_thread(process.join, grace_seconds)` 的实际等待时间是 `grace_seconds + thread-pool 调度延迟 + join 系统调用延迟`。在极端负载下这可能是几百 ms。5.05s 的 2.0s margin 应对几百 ms 的抖动绰绰有余，所以这不是强 finding。
- **直接证据**: plan §13.3 第 4 条；`dayu/runtime/interruptible_process.py` L696: `await asyncio.to_thread(process.join, grace_seconds)`
- **影响**: 低。2.0s margin 充足；只在极端 CI 环境可能触发 false positive。
- **建议改法和验证点**: 在 plan 中注明 "2.0s harness margin 已覆盖 `asyncio.to_thread` 调度延迟和 macOS process join 精度抖动；若 CI 环境超时，优先检查系统负载而非直接判定为缺陷"。
- **修复风险（低）**: 补充说明即可。
- **严重程度（低）**: 不足以阻塞 plan。

### 6-accepted-candidate-中-`_store_upload_assets` 内逐文件 cancel checkpoint 导致 partial write 后的 cancelled result 语义不明确

- **位置**: §9.1 publication first-committer boundary；§11.2 upload 数据流
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**: plan §9.1 规则 2："converter 返回后、source batch commit 前观察到 cancel：rollback 当前 document batch，不发布 original/docling/meta/manifest"。plan §11.2 数据流中 `publish_prepared_upload` → commit。

- **为什么有问题**: plan §9.1 规则 2 正确描述了意图（cancel → rollback → no publication），但 `publish_prepared_upload` 的 cancel 路径实现细节（谁负责 rollback？service 内部做还是 caller 做？）在 plan 中未明确。caller（CN/SEC upload workflow）当前使用 `_rollback_batch_before_commit`（ingestion_runtime.py L159-184），所以 caller 有能力 rollback。但 plan 未把这个职责分配写进 §11.2 的数据流。

- **建议改法和验证点**: 在 §11.2 数据流中标注："publish_prepared_upload 返回 cancelled 时，caller 负责 rollback batch；service 内不做 rollback"，或反之 "service 内部在 cancelled 分支自行 rollback batch 后返回 cancelled result"。二选一并写入 plan。

### 7-accepted-candidate-低-`DefaultFinsRuntime` 需创建单一 shared converter 实例并注入两个 pipeline——plan 未明确该实例创建位置

- **位置**: §5 生产 Docling call-site inventory；§11.2 upload filing/material 迁移；§12 S2
- **问题类型**: 不可直接实施
- **当前写法**: plan §5 裁决表最后一行："创建一个无跨调用可变状态的 `ProcessDoclingConverter` 实例并显式传入所有 Fins 路径"。plan §11.2 最后一段："`DefaultFinsRuntime` 建立并注入唯一 shared instance；standalone pipeline 构造若允许 `None`，只在明确 `is None` 时构造同一个 concrete class，不保留第二实现或 factory。"
- **反例/失败场景**: 当前 `DefaultFinsRuntime.get_ingestion_runtime()` (service_runtime.py L451-551) 分别创建 `sec_upload_pipeline` (L509) 和 `cn_upload_pipeline` (L519)，再创建 `ProductionFinsUploadRunner` (L528)。CN pipeline 的 `__init__` (cn_pipeline.py L316-403) 接受可选的 `docling_conversion_runner` 参数，默认创建 `ProcessCnDoclingConversionRunner()`。SEC pipeline 的 `__init__` (sec_pipeline.py L475-554) **没有** `docling_conversion_runner` 参数——它只创建 `DoclingUploadService` 而不创建任何 converter。

  plan 要求 S2 在 `DefaultFinsRuntime` 中创建一个 shared converter 并注入两个 pipeline。但 SEC pipeline 的 `__init__` 当前不接受 converter 参数——S2 需要给 `SecPipeline.__init__` 增加 `docling_converter` 参数。此外，CN pipeline 的 download workflow（通过 `build_cn_download_adapter` 创建）也需要注入 shared converter——但 `build_cn_download_adapter` 当前创建独立的 `CnPipeline` 实例用于 download 路径。plan 未说明 download adapter 的 `CnPipeline` 是否复用同一个 converter 实例（应该复用，否则仍是两套 runner）。

  实际上，当前代码中 download adapter 的 `CnPipeline` 和 upload 的 `CnPipeline` 是**两个独立实例**（service_runtime.py: `build_cn_download_adapter` 内部创建了一个 `CnPipeline`，L519 又创建了另一个 `CnPipeline`）。plan 要求 shared converter——但如果 download 和 upload 用的是不同的 `CnPipeline` 实例，shared converter 必须在创建两个 pipeline 实例**之前**创建，然后分别注入。plan 的文字 "`DefaultFinsRuntime` 建立并注入唯一 shared instance" 方向正确但未描述这个装配顺序。

- **为什么有问题**: plan 未明确 shared converter 实例到底在 `DefaultFinsRuntime` 的哪个方法中创建、如何同时注入 download adapter pipeline 和 upload pipeline。implementation agent 需要自己设计这个装配顺序，可能做错。
- **直接证据**:
  - `dayu/fins/service_runtime.py` L470-531: `get_ingestion_runtime()` 创建多个 pipeline 实例
  - `dayu/fins/pipelines/sec_pipeline.py` L475-554: `SecPipeline.__init__` 不接受 converter 参数
  - `dayu/fins/pipelines/cn_pipeline.py` L316-403: `CnPipeline.__init__` 接受 `docling_conversion_runner`
  - plan §5 最后一行、§11.2 最后一段
- **影响**: implementation agent 需自行决定装配顺序，可能做错，且测试中 standalone pipeline 构造也可能不一致。
- **建议改法和验证点**: 在 S2 exact allowed changes 中明确：(a) `SecPipeline.__init__` 增加 `docling_converter: DoclingConverter | None` 参数，(b) `CnPipeline.__init__` 的 `docling_conversion_runner` 参数替换为 `docling_converter: DoclingConverter | None`，(c) `DefaultFinsRuntime.get_ingestion_runtime()` 中在创建 pipeline 之前创建单一 `ProcessDoclingConverter()` 实例并传给 download adapter pipeline 和 upload pipeline，(d) download adapter 的 `CnPipeline` 和 upload 的 `CnPipeline` 是否合并为同一实例——如果不合并，至少共享同一 converter 实例。
- **修复风险（低）**: 补充装配说明。
- **严重程度（低）**: plan 已有方向性描述，细节可补充。
