### publishes_new_corpus 冻结时点与锁序（代码证据）

- 冻结时点正确：`begin_batch` 先 `_acquire_ticker_lock`（`:516`，跨进程阻塞）再判断 `target_ticker_dir.exists() or is_symlink()`（`:529`）。plan §7.2 要求 "在持有 same-ticker writer 并确认 target 是否存在后冻结" 与代码顺序一致。
- commit 时 target 状态不变：同 ticker 其它 writer 被阻塞；recovery 对活动 ticker 只做 nonblocking try-lock（`_recover_single_batch_dir:1687`）会跳过；不同 ticker 有不同目录名。因此 `publishes_new_corpus=True` 的 commit 时 target 必然仍不存在，plan step 6 的 defensive "若既有 target 存在则 strict 验证 descriptor canonical" 是理论不可达防御分支。
- 锁图无环（独立复核四路径）：identity-changing commit `writer → recovery → sweep(nonblocking try-lock) → identity → publication(s)`；read `identity → sorted publication`；recovery `recovery → try-writer → identity → publication`；document-only commit `writer → target publication`（不取 identity/recovery）。commit 持 recovery 等 identity 时，recovery 进程被同一 recovery lock 阻塞，不构成环；read 不取 recovery；document-only 不取 identity。与 plan §7.3 一致。
- `publishes_new_corpus` 是 transaction-local fact，不进入 journal；recovery 不依赖它（R1 保持全量 guard），plan §7.5 一致，无恢复窗口。
- identity guard 锁文件放 `.dayu` 根而非 `batch_locks/` 的理由经代码验证成立：`_published_ticker_candidate_keys`（`_fs_company_meta_core.py:412-424`）会枚举 `batch_locks/` 下 `.lock`/`.publication.lock` 后缀文件并投影为 ticker candidate；`.dayu` 根只被 `_RECOVERY_LOCK_FILENAME` 专用。plan §7.2 的规避正确。
- 锁序中的一个非问题细节：read 持 identity guard 期间，document-only commit（无 identity guard）可与 read 并发 swap，但 read 的 scan 枚举到的该 ticker 目录会令 read 对其取 publication guard 而等待 swap 完成，不观察中间 tree。

## Findings

### F1-未修复-低-invalid_descriptor 分型措辞与现有 `_read_identity_descriptor` 的异常折叠语义不一致，机械实现会把 permission 误报为 durable corruption

- **位置**: plan §5.6 `invalid_descriptor` 定义（"scan 把相应 `FileNotFoundError`/validation `ValueError` 收敛为此 kind"）；§11.3 "Published invalid fail-closed"（"permission/I/O failure 不误投影 corruption"）；P5 fix-2 同段表述
- **问题类型**: 不可直接实施 / 分型精度
- **当前写法**: plan 要求 scan 把 descriptor 相关的 `FileNotFoundError`/`ValueError` 收敛为 `invalid_descriptor`，普通 permission/I/O 失败沿 storage unavailable/storage_io 投影，但未指定 scan 复用的 descriptor 校验 helper 或区分机制。
- **反例/失败场景**: 现有 `_read_identity_descriptor`（`_fs_identity.py:255-266`）的两个行为与 plan 措辞冲突：
  1. 它**从不传播** `FileNotFoundError`：`if not directory.exists(): raise FileNotFoundError(...)`（`:256-257`）抛出的自造 `FileNotFoundError` 会被同函数 `except OSError`（`:263-266`）捕获并转为 path-free storage 错误。即 "目录消失/不可访问" 已自动走 storage unavailable（符合分型），但 plan 的 "FileNotFoundError → invalid_descriptor" 措辞会让实现者误以为存在一个需要捕获的 FileNotFoundError 路径，或自己新写扫描逻辑时把目录级 ENOENT 错误收敛为 corruption。
  2. Python 3.11 下 `Path.exists()/is_symlink()/is_file()` 对 stat 失败（如 descriptor 文件 permission 000、目录 permission 000）**返回 False 而不抛错**。因此 "descriptor 文件存在但不可访问" 会走 `not descriptor_path.is_file()` → `ValueError("identity descriptor 必须为 non-symlink regular file")`——若实现者按 plan 直译把该 `ValueError` 收敛为 `invalid_descriptor`，permission 问题会被误报为 durable workspace corruption，read 全 workspace fail closed 且用户无物可修。
- **为什么有问题**: 用户点名的 "invalid_descriptor 和 I/O 是否正确分型" 是本 WU 的验收核心（P5）；plan 的语义要求正确、closed kind 正确、测试方向正确，但留给实现 Agent 的异常分型机制未冻结，而最自然复用的现有 helper 的折叠语义是陷阱。测试矩阵的 "permission/I/O failure 不误投影 corruption" 能抓住错误实现，但若测试只对目录 chmod 而不对 descriptor 文件 chmod，第 2 条路径不会被触达。
- **直接证据**: `dayu/fins/storage/_fs_identity.py:255-266`（FileNotFoundError 被自身 except OSError 转换；exists/is_file 无显式 stat 区分）；plan §5.6 与 §11.3 对应措辞。
- **影响**: 实施 Agent 需要自行发明分型机制或踩中折叠陷阱；误报 corruption 会在 permission 场景造成 read 停机与错误提示。
- **建议改法和验证点**: plan 或 S2 实现约束中明确 scan 的 descriptor 校验机制二选一：(a) 新增/指定 scan 专用 helper，显式用 `os.lstat`/`os.stat` 区分 `ENOENT`（descriptor 缺失 → `invalid_descriptor`）与 `EACCES`/其它 `OSError`（→ storage unavailable），不依赖 `Path.exists()/is_file()` 的布尔折叠；(b) 若复用 `_read_identity_descriptor`，明文冻结其异常契约——自造 FileNotFoundError 已被转为 storage 错误、ValueError 中需以 "文件系统不可访问" 判定先行排除 permission 场景。测试至少覆盖 "descriptor 文件存在但不可读" 与 "目录不可访问" 两个 permission 注入。
- **修复风险（低）**: 只影响 S2 一个 helper 的异常收敛实现与一个测试注入，不动锁序/merge/intent 架构。
- **严重程度（低）**: plan 已有正确分型要求与测试断言兜底，实现可做对；本 finding 是把它从"实现者可自由发挥"降为"已冻结"。
