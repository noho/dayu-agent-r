## Findings

### F-01-未修复-中-deterministic-worker-injection-path-not-documented-in-plan

- **位置**: Slice S2 "Exact changes" bullet 1, "Add smoke-local final/recovery worker helpers"
- **问题类型**: 不可直接实施
- **当前写法**: Plan says "Add smoke-local final/recovery worker helpers modeled on `tests/host/test_public_compact_smoke.py`" but does not state how `OpenHostOptions.worker_factory` will be replaced after `compose_open_host_options()` returns.
- **反例/失败场景**: Implementation agent reads the plan, sees no mention of `replace()` or `worker_factory` injection, and either: (a) modifies `compose_open_host_options()` to accept a worker factory parameter (violating "no Host/Service API change"), or (b) adds monkeypatching of `DefaultLocalEngineWorkerFactory` (adding another private-API dependency), or (c) spends time rediscovering the `replace()` pattern.
- **为什么有问题**: The smoke script currently imports only `dataclass` (singular), not `replace`. The plan should explicitly state that `replace(options, worker_factory=...)` will be used after `compose_open_host_options()` returns. This is a one-line instruction that prevents implementation drift.
- **直接证据**: `dayu/host/api.py:984` — `@dataclass(frozen=True, slots=True)`; `dayu/host/api.py:1038` — `worker_factory: LocalEngineWorkerFactory`; `dayu/service/host_assembly.py:651` — `worker_factory=DefaultLocalEngineWorkerFactory()`; `utils/smoke_host_public_conversation_memory_scenarios.py:26` — `from dataclasses import dataclass` (no `replace`).
- **影响**: 实施 Agent 跑偏 / 后续返工
- **建议改法和验证点**: Add to Slice S2 "Exact changes" a concrete line: "After `compose_open_host_options()`, use `replace(options, worker_factory=DeterministicSmokeWorkerFactory())` to inject deterministic workers for reactive/fallback suites. Import `replace` from `dataclasses`." Validate by confirming `worker_factory` type annotation is `LocalEngineWorkerFactory` and the replacement produces no pyright errors.
- **修复风险（低）**:
- **严重程度（中）**:

### F-04-未修复-低-fallback-suite-pressure-tuning-underspecified

- **位置**: Slice S3 "Exact changes" bullet 2: "Trigger proactive compact in the target run using bounded deterministic pressure, not real provider overflow."
- **问题类型**: 不可直接实施
- **当前写法**: Plan says to use "bounded deterministic pressure" but doesn't specify how many seed rounds or what pressure multiplier ensures the proactive threshold is crossed without exceeding the hard threshold.
- **反例/失败场景**: Implementation agent uses default pressure values, proactive compact doesn't trigger (pressure too low), or hard threshold is exceeded (pressure too high causing fail-closed). Smoke fails for configuration reasons, not semantic reasons.
- **为什么有问题**: The fallback suite needs the compactor to be called AND rejected. If pressure doesn't cross soft threshold, proactive compact never triggers and the fallback path isn't exercised. If pressure exceeds hard threshold, Host may fail closed before compact. The plan should specify that existing pressure estimation helpers (`_estimate_chars_as_tokens`, `_threshold_tokens`, `_compact_pressure_padding`) will be used to tune pressure for the fallback suite's context window size.
- **直接证据**: `utils/smoke_host_public_conversation_memory_scenarios.py:165-169` — `_COMPACT_PRESSURE_TARGET_EXTRA_TOKENS`, `_COMPACT_PRESSURE_HARD_MARGIN_TOKENS`, `_COMPACT_PRESSURE_RESERVE_TOKENS` exist. `tests/runtime/test_smoke_host_public_conversation_memory_scenarios_assembly.py:350-365` — `test_pressure_off_and_padding_helper_cover_runtime_pressure_bounds` already validates `soft_threshold_tokens <= pressure_tokens < hard_threshold_tokens`.
- **影响**: 实施 Agent 跑偏
- **建议改法和验证点**: Add to Slice S3: "Use existing `_compact_pressure_padding()` and `_estimate_chars_as_tokens()` to compute pressure that lands between soft and hard thresholds for the suite's context window. The existing test `test_pressure_off_and_padding_helper_cover_runtime_pressure_bounds` proves this pattern works." Implementation should assert `soft_threshold < pressure_tokens < hard_threshold` before running the fallback scenario.

Or split into S2a (shared infrastructure) and S2b/S3 (suite-specific workers and assertions). The current sequencing is acceptable if the implementation agent is aware of the shared foundation — the plan just needs to state it.

## Architecture Boundary Review

**Layering**: The plan stays within `utils/` and `tests/`. No Host, Engine, Service, or Fins production code is modified. The `worker_factory` injection uses a public `OpenHostOptions` field — no layering violation. **PASS**.

**Dependency direction**: Smoke script already depends on `dayu.host` (public API), `dayu.service.host_assembly` (assembly helpers), `dayu.runtime` (config/locations). Adding deterministic workers follows the same dependency direction. The compactor monkeypatch (`dayu.host.llm_compaction._run_agent_request`) is a private-API dependency, but the plan correctly identifies this as a risk with a stop condition. **PASS with noted risk**.

**Public contracts**: `OpenHostOptions.worker_factory` is already a public typed field. No new contract, schema, or state machine changes. **PASS**.

**Storage**: Smoke reads EventLog via `open_host_durable_store` (already done in `_compact_audit_report`). No new storage access patterns. **PASS**.

## Best-Practice Review

**Testability**: New acceptance helpers are tested with synthetic EventLog rows (Slice S1). New suites are validated via deterministic smoke commands (Slice S4). This separates helper-level correctness from integration-level behavior. **PASS**.

**Maintainability**: Adding suite-specific helpers (`_assert_reactive_compact_acceptance`, `_assert_fallback_dispatch_acceptance`) rather than parameterizing `_assert_compact_acceptance` with flags is the right call — it keeps each helper simple and prevents `memory-compact` from accidentally absorbing fallback semantics. **PASS**.

**Failure handling**: Each slice has explicit stop conditions. The plan's risk section correctly identifies compactor stubbing as a binary gate. **PASS**.

**Observability**: Smoke stdout remains bounded. Compact audit, operation, and fallback signals are printed with `SMOKE ` prefix — consistent with existing output. **PASS**.

## Optimal-Solution Review

The plan's approach — adding two suite modes with deterministic workers — is the most practical path:
- **Alternative considered**: Folding reactive/fallback into `memory-compact` with flags. Correctly rejected because `memory-compact` treats any `CONTEXT_COMPACTION_FAILED` as hard failure.
- **Alternative considered**: Using real provider overflow for reactive smoke. Correctly rejected because it's non-deterministic and requires specific provider behavior.
- **Alternative considered**: Building a separate smoke script. Unnecessary — reusing the existing script's assembly, EventLog audit, and stdout infrastructure is the right call.

**PASS**.

## Overengineering Review

The plan adds exactly two suite modes, two acceptance helpers, and deterministic worker/compactor stubs. No new framework, abstraction layer, configuration DSL, or generalization. The "Why This Is Not Over-Designed" section (plan lines 452-456) is accurate. **PASS**.

## Overcoupling Review

The new suites are independent of each other and of `memory-compact`. They share the smoke script's assembly and audit infrastructure, but this is reuse, not coupling. The deterministic workers are smoke-local and don't create production dependencies. **PASS**.

## Conclusion

**PASS-WITH-RISKS**

The plan is code-generation-ready. It correctly:
- Scopes the work to smoke coverage only, with no production changes
- Preserves `memory-compact` proactive acceptance and `failed_total == 0` invariant
- Avoids Host/Engine public API, durable schema, EventLog semantic, provider contract, and production state-machine changes
- Specifies concrete, falsifiable assertions for reactive and fallback suites
- Sequences slices safely (S1 routing → S2 reactive → S3 fallback → S4 validation)
- Provides sufficient validation commands
- Includes explicit stop conditions for each slice and for the overall scope boundary

Five low-to-medium findings identified (F-01 through F-05). None are blockers. F-01 (worker injection path) is the most actionable — a one-line clarification in Slice S2 resolves it. F-02 (compactor stub location) and F-03 (request capture mechanism) are minor specification gaps that won't cause implementation failure but may cause rework. F-04 and F-05 are low-severity.

The key architectural question — whether `OpenHostOptions.worker_factory` can be injected without Host API changes — is resolved affirmatively by direct code evidence: `OpenHostOptions` is a frozen dataclass with a public `worker_factory: LocalEngineWorkerFactory` field, and `replace()` can swap it after assembly.

No findings challenge the plan's core viability. All risks are correctly identified with stop conditions.
