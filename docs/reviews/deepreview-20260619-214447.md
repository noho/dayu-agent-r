## 2. Correctness Review

### 2.1 Frozen material semantics preserved

The critical reactive invariant — "frozen material from the overflow moment" — is preserved:

- `_frozen_reactive_material_blocks(...)` constructs frozen blocks at EventLog append time (used for audit payload fields `frozen_material_list_digest` and `frozen_material_refs`).
- `compact_pipeline_source_snapshot_from_pre_dispatch_view(...)` creates `source_snapshot` from the same `material_view` and frozen `run` facts — capturing `input_event_sequence`, `material_blocks`, `previous_compacted_view`, and `source_boundary` at the same frozen moment.
- The old code's `frozen_material_blocks` included a synthetic current input block for fallback consumption. The new code separates concerns: `source_snapshot.material_blocks` carries only post-compact delta material; `build_fallback_decision_input` → `_fallback_material_blocks(source_snapshot)` creates the current input block internally. This is cleaner — the pipeline owns current-input-anchor handling, not the caller.

### 2.2 policy_digest migration

Old code: `_reactive_compaction_request` used `policy_digest=pending.frozen_material_list_digest` in `select_compact_segment`. This was the frozen material list digest — a material-provenance value, not a policy-config value.

New code: `build_normal_compact_request_plan` uses `selection_policy_digest=digest_memory_projection_policy(memory_policy)` — a true policy-config digest. This matches Slice 2a's proactive path and resolves the policy_digest semantic inconsistency identified in plan review N2.

### 2.3 Source snapshot construction in reactive flow

At `engine_ingest.py:1314-1317`, the source snapshot is constructed inside the same write transaction that constructs frozen material blocks:
```python
source_snapshot = compact_pipeline_source_snapshot_from_pre_dispatch_view(
    trigger_source=ContextCompactionTriggerSource.REACTIVE,
    run=context.run,
    material_view=material_view,
)
```
The `material_view` is from `build_pre_dispatch_compact_material_view(...)` (line ~1334), which is the same read transaction as `_display_text_from_input_event(...)`. The `context.run` is from the validated Engine candidate. All facts are frozen at the same moment — no stale data risk.

### 2.4 `attempt_count` and `retry_repair_budget_exhausted` computation

```python
attempt_count = len(operation_result.rejected_attempts)
retry_repair_budget_exhausted = attempt_count > 0
```
These are computed as local variables before the `build_fallback_decision_input` call (lines 1720-1721). The old code inlined `len(operation_result.rejected_attempts)` and `len(operation_result.rejected_attempts) > 0` directly in the `_append_reactive_compaction_failed_event` and `_reactive_fallback_decision` calls. The new code is semantically identical.

### 2.5 Stale/cursor/execution guards: all untouched

The commit guard logic at lines 1664-1701 (stale validation, cursor mismatch, RECOVERING status check, attempt terminal event check) is completely unchanged from the old code. These guards are the reactive-specific lifecycle protection — they were never in the scope of Slice 2b to modify, and the diff confirms they are untouched.

### 2.6 Recovery Attempt creation: all untouched

- Accepted compact path: `_append_reactive_compacted_event` → `_ReactiveRecoveryAccepted` (lines 1806-1837) — unchanged.
- Fallback dispatch path: `_ReactiveRecoveryAccepted` (lines 1754-1773) — unchanged except fallback fields now come from `failed_input`.
