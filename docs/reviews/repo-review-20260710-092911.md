# 全仓库语义所有权漂移审查

## 范围

- 模式：`$deepreview --all`
- 目标：全仓库 semantic ownership drift / minimum-design trap 审查
- 代码状态：只读审查；未修改生产代码
- 重点范围：`dayu/host/**`、`dayu/engine/**`、`dayu/fins/**`、`dayu/contracts/**`、`dayu/runtime/**`、`dayu/service/**`、`dayu/cli/**`、`tests/**`、`pyproject.toml`、README 中的公开入口契约
- 排除范围：`.git/**`、`.venv/**`、`__pycache__/**`、历史 `docs/reviews/**` artifact、生成物与大体量 fixture 的逐字审查
- 并行审查：使用 subagents 分别覆盖 Host、Engine、Fins、Contracts/Runtime/Config、CLI/Service/Tests；主审复核、去重后只保留有直接证据的 finding
- 验证：本次是只读审查，未运行测试或 pyright

## 结论

发现 12 个证据充分的 ownership drift。最严重的问题集中在：Host terminal final answer 投影不一致、Fins source/blob 状态真源错位、Engine protocol error 与 terminal success 混用、公开入口脚本声明了不存在的模块。这些不是风格问题，而是同一语义事实已经由下游补、猜、重算或以兼容形状掩盖。

## Findings

### 01. 高：成功终态 Outbox item 丢失 descriptor-backed final answer

- 语义事实或 contract：成功终态的最终回答。`HostEvent` 成功终态要求 `final_answer`，Host README 也声明 succeeded terminal 必须携带 final answer（`dayu/host/api.py:3116`、`dayu/host/README.md:539`）。
- 正确 owner：Host terminal answer continuity resolver，即 `assistant_final_answer_continuity_text`。它明确先读 inline `RUN_SUCCEEDED.final_answer`，再按 `terminal_summary_ref` / `terminal_summary_digest` 读取 descriptor payload 顶层 `content`（`dayu/host/_terminal_answer.py:35`）。
- 所有权漂移位置：Outbox projection 没用这个 owner。`_outbox_row_from_event` 调 `_final_answer_json(event.payload, terminal_status)`（`dayu/host/outbox.py:275`），而 `_final_answer_json` 只读 inline `final_answer`，缺失就返回 `None`（`dayu/host/outbox.py:346`、`dayu/host/outbox.py:360`）。`OutboxTerminalItem` 校验只禁止 succeeded 带 error/cancel，没有要求 succeeded 必须带 `final_answer`（`dayu/host/api.py:3157`）。
- 直接证据：生产 Engine final answer closeout 把内容写入 terminal descriptor payload 的 `content`（`dayu/host/engine_ingest.py:4328`、`dayu/host/engine_ingest.py:4333`），closeout 只把 `terminal_summary_ref/digest` 传入 run terminal payload（`dayu/host/engine_ingest.py:1086`、`dayu/host/engine_ingest.py:1106`），run terminal payload 本身不含 `final_answer`（`dayu/host/durable/run_transition.py:4575`）。Outbox read API 又从 `row.final_answer_json` 还原 public item（`dayu/host/read_api.py:814`）。
- 失败/成本：同一个成功回答在 live HostEvent、Memory、RunInputBuilder、compact material 可见，但离线 Outbox terminal notification 可能是 succeeded 且 `final_answer=None`。下游若要补洞，就必须跟随 descriptor refs 自行重建 Host 语义。
- 推荐收束：Outbox projection 必须复用 terminal continuity owner，或抽出统一 `HostFinalAnswerView` projection helper 给 HostEvent、Outbox、Memory、RunInputBuilder 共用。succeeded outbox item 应在 public validation 中要求 final answer 非空。
- 验证点：增加生产路径 smoke，断言 `read_outbox_terminal_items(...).items[0].final_answer.content` 等于最终回答；增加 descriptor-only `RUN_SUCCEEDED` outbox projection 单测；保留 failed/cancelled/lost 不携带 final answer 的负向测试；做 propagation audit：`FinalAnswerData.content -> terminal descriptor content -> RUN_SUCCEEDED refs -> HostEvent / Outbox / Memory / RunInputBuilder`。

### 02. 高：公开 console script 声明的 Web/WeChat/Render 模块不存在

- 语义事实或 contract：安装包公开能力入口 `dayu-web`、`dayu-wechat`、`dayu-render` 是否存在并可 import。
- 正确 owner：packaging entrypoint 与实际 Python package module。README 只能投影已存在、已验证的入口能力。
- 所有权漂移位置：`pyproject.toml` 声明 `dayu-web = "dayu.web.__main__:main"`、`dayu-wechat = "dayu.wechat.main:main"`、`dayu-render = "dayu.render.render:main"`（`pyproject.toml:99`、`pyproject.toml:100`、`pyproject.toml:101`），但当前 `dayu/` 下没有 `web`、`wechat`、`render` package。README 仍要求安装后验证这些命令（`README.md:160`、`README.md:161`、`README.md:167`），并继续文档化 `python -m dayu.web` 与 `dayu-render` 用法（`README.md:329`、`README.md:335`、`README.md:1088`）。
- 直接证据：`find dayu -maxdepth 2 -type d` 只列出 `dayu/tools`、`host`、`config`、`contracts`、`fins`、`runtime`、`cli`、`documents`、`service`、`engine`，没有上述三个 package。测试里 `tests/tools/web/test_diagnose_web_access.py:984` 反而断言诊断脚本不得恢复旧 `dayu.web` / UI 路径。
- 失败/成本：安装后的 console script 会在 import 阶段失败；用户文档、package metadata 与代码真源分裂。新增或删除入口能力需要同步修改 packaging、README、测试，当前没有一个 owner 能保证入口存在性。
- 推荐收束：若这些入口已经下线，删除 `pyproject.toml` scripts、package data 与 README 对应章节；若仍是产品能力，则恢复实际 modules 并补入口 smoke 测试。入口可用性应由 package/module smoke 驱动，README 只跟随该 contract。
- 验证点：新增 console scripts import smoke；对 `python -m dayu.web`、`dayu-wechat --help`、`dayu-render --help` 做最低限度 CLI contract 测试，或删除所有对应公开声明并测试不存在的入口不会被文档引用。

### 03. 高：Fins blob repository 可写入 source repository 不承认的文档文件

- 语义事实或 contract：source document 的存在、`ingest_complete`、`files`、`primary_document` 必须由 source repository/source document state 拥有；blob repository 只能写入已存在 source/processed 文档的文件。
- 正确 owner：`SourceDocumentRepositoryProtocol` / source document upsert state。`FsDocumentBlobRepository.store_file` 的 docstring 也声明 handle 对应文档不存在时应抛 `FileNotFoundError`（`dayu/fins/storage/_fs_blob_core.py:114`、`dayu/fins/storage/_fs_blob_core.py:136`）。
- 所有权漂移位置：SEC download 手工构造尚未落盘 meta 的 `SourceHandle`，先写 blob，再成功后 upsert source meta（`dayu/fins/pipelines/sec_download_filing_workflow.py:409`、`dayu/fins/pipelines/sec_download_filing_workflow.py:425`、`dayu/fins/pipelines/sec_download_filing_workflow.py:552`）。失败路径明确“不落盘 meta”并返回（`dayu/fins/pipelines/sec_download_filing_workflow.py:481`）。upload service 同样先构造 `SourceHandle` 写 blob，最后才 `_upsert_source_document`（`dayu/fins/pipelines/docling_upload_service.py:252`、`dayu/fins/pipelines/docling_upload_service.py:260`、`dayu/fins/pipelines/docling_upload_service.py:294`）。
- 直接证据：blob 实现没有验证 meta 是否存在，只 normalize ticker、build key、put object（`dayu/fins/storage/_fs_blob_core.py:140`、`dayu/fins/storage/_fs_blob_core.py:151`）。SEC 失败测试只断言 `meta.json` 不存在，没有断言已写 blob 被清理或 staging 状态存在（`tests/fins/test_sec_pipeline_download.py:1109`）。
- 失败/成本：产生 orphan blob。storage 层有文件事实，但 source repository 不承认该文档存在；retry、cleanup、审计、容量治理都必须扫描裸路径才能解释这些文件。`store_file` 的协议承诺也被实现本身破坏。
- 推荐收束：SEC/upload 先通过 source repository 创建 `ingest_complete=False` 的 staging source，再把 blob 写入该 source；成功时由 source owner commit 为 `ingest_complete=True` 并写 `files/primary_document/source_fingerprint`。或者显式引入 staging handle contract，并让 `store_file` 对普通不存在 handle fail fast。
- 验证点：SEC 部分文件成功后失败时，不应留下无 source meta 的 blob；upload 部分写入后取消/失败同理；`list_documents`、preprocess/read 不应看到 incomplete source；storage `store_file` 对不存在 handle 有测试覆盖。

### 04. 高：Engine `PROVIDER_PROTOCOL_ERROR` 同时表示 fatal error 和 non-fatal warning

- 语义事实或 contract：`PROVIDER_PROTOCOL_ERROR` 是 runner/provider 协议错误，测试契约要求它出现后必须 `RunnerDoneData(ERROR)`，且不得再出现成功 completed 事件（`tests/engine/runners/openai/test_event_flow_ordering.py:15`）。
- 正确 owner：OpenAI adapter / tool-call aggregator 应区分 fatal protocol error 与非终止 diagnostic。
- 所有权漂移位置：`ToolCallAggregator` 把未知 provider namespace / unknown google key 放进 `RunnerProtocolErrorData` warnings（`dayu/engine/runners/openai/tool_call_aggregator.py:101`、`dayu/engine/runners/openai/tool_call_aggregator.py:303`）。SSE finalize 先 yield warnings，再继续 yield `RunnerToolCallsCompletedData` 与 `RunnerDoneData(TOOL_CALLS/STOP)`（`dayu/engine/runners/openai/sse_parser.py:676`、`dayu/engine/runners/openai/sse_parser.py:692`、`dayu/engine/runners/openai/sse_parser.py:707`）。
- 直接证据：Agent 对任何 `RunnerProtocolErrorData` 都提升为 `EngineEventType.PROVIDER_PROTOCOL_ERROR` 并设置 `failure_candidate`（`dayu/engine/agent.py:1359`、`dayu/engine/agent.py:1371`）。因此同一 runner stream 可同时出现 provider protocol error event 与成功 tool-calls terminal。
- 失败/成本：调用方和审计链无法只凭事件类型判断 run 是否失败。错误事件语义被下游 Agent 和上游 parser 分别解释：parser 认为 warning 可成功，Agent 认为 protocol error 是 failure candidate。
- 推荐收束：若 unknown provider state 会破坏 roundtrip，就归为 fatal protocol error；若确实可忽略，新增独立 non-fatal diagnostic/warning event，不复用 `PROVIDER_PROTOCOL_ERROR`。
- 验证点：新增 unknown namespace / unknown google key 流式用例。若产 `PROVIDER_PROTOCOL_ERROR`，必须 `Done(ERROR)` 且没有 success completed；若成功收口，则只能产 diagnostic/warning event。

### 05. 高：SSE 多 choices 合并多个候选，non-stream 只取第一个候选

- 语义事实或 contract：Runner event stream 表达单个 assistant response，stream 与 non-stream 对 provider `choices` 的选择规则应一致。
- 正确 owner：OpenAI protocol adapter 的 choice normalizer。
- 所有权漂移位置：SSE parser 遍历所有 `choices` 并把每个 choice 的 delta 写入同一 content/reasoning/tool buffer（`dayu/engine/runners/openai/sse_parser.py:464`、`dayu/engine/runners/openai/sse_parser.py:466`、`dayu/engine/runners/openai/sse_parser.py:506`）。`finish_reason` 由后处理 choice 覆盖（`dayu/engine/runners/openai/sse_parser.py:538`、`dayu/engine/runners/openai/sse_parser.py:542`）。non-stream parser 固定 `choice = choices[0]`（`dayu/engine/runners/openai/non_stream_parser.py:252`、`dayu/engine/runners/openai/non_stream_parser.py:269`）。
- 直接证据：同样的 provider 语义如果有两个 choices，SSE 会拼接 A+B 并采用最后一个 finish reason，non-stream 只采用 A。现有 parity 测试只覆盖单 choice 的 finish reason（`tests/engine/runners/openai/test_stream_non_stream_terminal_parity.py:139`）。
- 失败/成本：可能拼出 provider 从未作为单一候选返回的答案，且可能错误触发 `length` continuation 或 tool-call state。新增一个 choice 语义需要同步修改 stream/non-stream/tests。
- 推荐收束：统一 choice contract：只接受 `index=0` / 第一个有效 choice，或明确拒绝多 choice。该规则应在 OpenAI adapter owner 处实现，不由 Agent 从拼接结果推断。
- 验证点：新增 stream/non-stream 多 choices parity 测试，覆盖 content、reasoning、tool_calls 与 finish_reason 冲突。

### 06. 高：Fins citation 的 source_type 由 document_id 前缀和 ingest_method 猜测

- 语义事实或 contract：tool-facing citation 的 `source_type` 是 LLM 可见来源事实，不能由 `document_id` 前缀或 `ingest_method` 猜测。
- 正确 owner：source kind 应来自 source repository/storage location；外部下载 provider 应来自 SEC/CN/HK adapter 写入的 typed provider metadata，例如 `source_provider`。
- 所有权漂移位置：`_build_citation` 先读 `meta["source_kind"]`，但 source upsert 并不写该字段；随后按 `document_id.startswith("fil_")` 与 `ingest_method == download` 推断 `SEC_EDGAR`（`dayu/fins/tools/read_runtime.py:1691`、`dayu/fins/tools/read_runtime.py:1695`、`dayu/fins/tools/read_runtime.py:1703`）。source meta upsert 写 `document_id/internal_document_id/form_type/ingest_complete/...`，但不写 `source_kind`（`dayu/fins/storage/_fs_source_document_core.py:713`）。
- 直接证据：CN/HK filing id 也是 `fil_cn_*`（`dayu/fins/pipelines/docling_upload_service.py:990`、`dayu/fins/pipelines/docling_upload_service.py:1029`），其 provider 真源是 `cninfo` / `hkexnews`（`dayu/fins/pipelines/cn_download_models.py:39`）并写入 meta 的 `source_provider`（`dayu/fins/pipelines/cn_download_source_upsert.py:315`）。material id 是 `mat_*`（`dayu/fins/pipelines/docling_upload_service.py:891`），但 `_build_citation` 读不到 `source_kind` 时会落到 `UPLOADED`，而 `SourceType.SUPPLEMENTARY` 明确定义了补充材料（`dayu/fins/domain/tool_models.py:20`、`dayu/fins/domain/tool_models.py:26`）。
- 失败/成本：LLM-facing citation 会把 CN/HK 披露来源说成 SEC EDGAR，或把补充材料说成 uploaded filing。这个错误发生在统一 read runtime 投影层，会影响所有携带 citation 的工具输出。
- 推荐收束：citation 构造复用一个 source-of-truth helper，基于 `source_repository` 的 source kind 与 provider metadata 构造 citation；禁止从 `document_id` 前缀推断来源。若现有 `SourceType` 无法表达 CN/HK 下载 filing，应扩展枚举或增加 provider 字段。
- 验证点：CNINFO/HKEXNEWS 下载 filing citation 不再是 `SEC_EDGAR`；material citation 是 `SUPPLEMENTARY`；SEC downloaded filing 仍是 `SEC_EDGAR`；uploaded filing 仍是 `UPLOADED`；所有 read/search/table/financial/xbrl 工具使用同一 helper。

### 07. 中：CLI terminal cursor 用进程退出成功代理“terminal 已展示”

- 语义事实或 contract：`CliTerminalCursorRecord` 记录的是 CLI 已成功展示的 terminal event watermark，而不是 Host run 成败（`dayu/cli/session_terminal_cursor.py:36`、`dayu/cli/session_terminal_cursor.py:39`）。
- 正确 owner：CLI display delivery/cursor 层拥有“已展示”事实；Host terminal status 只拥有 run 结果。
- 所有权漂移位置：prompt 路径只有 `render_exit_code == EXIT_SUCCESS` 才推进 cursor（`dayu/cli/session_execution.py:373`、`dayu/cli/session_execution.py:374`）；interactive startup/repl 路径遇到非成功 render exit code 直接 return，不推进 cursor（`dayu/cli/session_execution.py:522`、`dayu/cli/session_execution.py:523`、`dayu/cli/session_execution.py:851`、`dayu/cli/session_execution.py:854`）。
- 直接证据：render 已经被调用后才因失败/取消/lost exit code return。cursor owner 的“已成功展示”事实被 command process exit code 覆盖。
- 失败/成本：FAILED/CANCELLED/LOST terminal 已经显示给用户，但 cursor 不前进；下一次 startup reconnect 会按旧 cursor 重新拉取并重复展示。测试主要覆盖成功 cursor 推进（`tests/cli/test_prompt_command.py:923`、`tests/cli/test_interactive_command.py:893`），失败 terminal replay 没有保护。
- 推荐收束：把“render 正常返回”与“命令 exit code”拆开。terminal render 没抛 I/O 异常即推进 cursor，然后再按 terminal status 返回进程退出码或决定 REPL 是否继续。
- 验证点：补 prompt FAILED/CANCELLED/LOST、interactive startup LOST/FAILED/CANCELLED 测试，断言输出已展示后 cursor 文件包含对应 terminal event id/sequence，后续 reconnect 不再重复返回。

### 08. 中：Fins direct service 在缺失 RESULT 时制造业务失败结果

- 语义事实或 contract：Fins direct stream 应产生且只产生一个 `RESULT`；CLI 已定义 stream 结束但无 `RESULT` 是 service stream contract violation（`dayu/cli/commands/fins.py:96`、`dayu/cli/commands/fins.py:720`、`dayu/cli/commands/fins.py:736`）。
- 正确 owner：Fins runtime/producer 拥有真实业务终态；Service adapter 只能校验 stream protocol，不应制造 Fins 业务结果。
- 所有权漂移位置：`_ensure_result_event` 在 runtime stream 正常结束但无 `RESULT` 时 yield `_missing_result_event`（`dayu/service/fins_direct.py:477`、`dayu/service/fins_direct.py:505`），后者构造 `FinsResultSummary(status=FAILURE, error_kind=EXECUTION)`（`dayu/service/fins_direct.py:531`、`dayu/service/fins_direct.py:538`）。
- 直接证据：service 测试把 missing RESULT 固化为“Service 必须产出清晰 failure”（`tests/service/test_fins_direct.py:500`、`tests/service/test_fins_direct.py:509`），而 CLI fake service 测试仍认为无 RESULT 应报告 contract violation 且不能输出 `Fins failure`（`tests/cli/test_fins_commands.py:883`、`tests/cli/test_fins_commands.py:898`）。
- 失败/成本：producer 协议错误被持久化/展示成 Fins 执行业务失败。排障会误判为财报任务失败，而不是 runtime/service contract 破坏。
- 推荐收束：缺失或重复 `RESULT` 都作为 typed protocol error 抛出；CLI 边界再把 protocol error 渲染为命令错误，不生成 `FinsResultSummary`。
- 验证点：改 `tests/service/test_fins_direct.py` missing RESULT 期望为异常；保留 CLI fake service 缺失 RESULT 测试，确认不会输出业务 `Fins failure`。

### 09. 中：wait callback endpoint 用 bare string provider_status_ref 伪造 adapter_key

- 语义事实或 contract：`WaitProviderStatusRef.adapter_key` 是产生该状态引用的 Host wait adapter key。
- 正确 owner：wait provider/adapter 拥有 adapter identity；HTTP callback mapper 不拥有 provider 的 adapter key。
- 所有权漂移位置：`_provider_status_ref_from_json` 接受 bare string，并构造 `WaitProviderStatusRef(adapter_key=WaitAdapterKey("callback"), status_ref=...)`（`dayu/service/wait_callback_endpoint.py:542`、`dayu/service/wait_callback_endpoint.py:552`、`dayu/service/wait_callback_endpoint.py:555`）。
- 直接证据：durable digest 对 provider status ref 的标准 JSON 是对象 `{adapter_key, status_ref, status_digest}`（`dayu/host/durable/wait_resolution_digest.py:177`、`dayu/host/durable/wait_resolution_digest.py:189`）。测试 fixture 直接使用 bare string `"provider_status_ref": "jobs/provider-1/status"`（`tests/service/test_wait_callback_endpoint.py:606`、`tests/service/test_wait_callback_endpoint.py:616`）。
- 失败/成本：durable trace/audit 中 provider status ref 的 adapter identity 被污染为 `"callback"`；后续诊断或恢复无法知道真实 provider owner。
- 推荐收束：callback JSON 只接受自描述对象 `{adapter_key, status_ref, status_digest}`，或由具体认证/provider adapter 显式解析 shorthand。通用 endpoint 不默认 `"callback"`。
- 验证点：补 object form 保留 adapter key/digest 的测试；bare string 应被拒绝，或必须通过 owner-provided resolver。

### 10. 中：ToolResult 的 ok 判别字段由下游补校验，contract owner 没有强制

- 语义事实或 contract：`ToolResultSuccess.ok` 必须为 `True`，`ToolResultFailure.ok` 必须为 `False`；模块文档也把 `ok` 称为判别字段（`dayu/contracts/tool_result.py:5`、`dayu/contracts/tool_result.py:8`）。
- 正确 owner：`dayu.contracts.tool_result`。
- 所有权漂移位置：`ToolResultSuccess` 没有 `__post_init__`（`dayu/contracts/tool_result.py:64`）；`ToolResultFailure.__post_init__` 只校验 `error/message/hint` 非空，不校验 `ok is False`（`dayu/contracts/tool_result.py:94`、`dayu/contracts/tool_result.py:103`）。
- 直接证据：service callback parser 必须在下游重新检查 completed result `ok is True`（`dayu/service/wait_callback_endpoint.py:487`、`dayu/service/wait_callback_endpoint.py:495`）。Host public outcome wrapper 只校验 result 是 `ToolResultSuccess` / `ToolResultFailure` 实例（`dayu/host/api.py:448`、`dayu/host/api.py:478`），因此可构造 wrapper kind 与内部 `ok` 矛盾的对象。
- 失败/成本：durable state、trace、audit 可能出现 `kind=completed` 但 `ok=false`，或 `kind=failed` 但 `ok=true`；消费者按 wrapper kind 与按 result envelope 会得到不同事实。
- 推荐收束：在 `ToolResultSuccess/Failure` 构造时强制 literal invariant。callback 解析只做 transport 输入清洗，不承担判别事实 owner。
- 验证点：contracts 测试拒绝 `ToolResultSuccess(ok=False)` 与 `ToolResultFailure(ok=True)`；Host digest/projection 回归确认不可能记录矛盾状态。

### 11. 中：XBRL facts result 的 total 由 read runtime 重算并掩盖 processor contract violation

- 语义事实或 contract：`query_xbrl_facts` 的结果必须包含 `query_params`、`facts`、`total`（`dayu/fins/processors/financial_base.py:31`）。
- 正确 owner：`FinancialDataProcessor.query_xbrl_facts` / processor typed result contract。
- 所有权漂移位置：read runtime 调 processor 后把结果 `cast(dict[str, Any])`（`dayu/fins/tools/read_runtime.py:1307`、`dayu/fins/tools/read_runtime.py:1317`），再传给 `_normalize_xbrl_query_payload`。normalizer 缺失/非法 `query_params` 时给 `{}`，缺失/非法 `facts` 时给 `[]`，并把 `total` 重算为 `len(deduped_facts)`（`dayu/fins/tools/read_runtime_helpers.py:1374`、`dayu/fins/tools/read_runtime_helpers.py:1392`、`dayu/fins/tools/read_runtime_helpers.py:1396`、`dayu/fins/tools/read_runtime_helpers.py:1413`）。
- 直接证据：测试 fake `_XbrlFactsProcessor.query_xbrl_facts` 返回 `query_params` 与 `facts`，但没有 required `total`（`tests/fins/test_fins_storage_provider.py:489`、`tests/fins/test_fins_storage_provider.py:523`）。生产 normalizer 让这个违约 fake 成功通过。
- 失败/成本：processor 少算/错算 `total` 或返回 malformed facts 时，工具对 LLM 仍可能显示“成功的空/重算结果”，调用方无法区分“没有 facts”和“processor contract broken”。
- 推荐收束：processor return 使用 typed builder/validator；read runtime 只做 owner-level 校验或调用同一个 owner helper，不能重算 required semantic field 掩盖违约。测试 fake 必须补齐 required `total`，或显式断言 owner-level contract violation。
- 验证点：新增 processor 缺 `total`、`facts` 非 list 的失败测试；新增正常 processor `total` 与 facts 一致性 owner 测试。

### 12. 中：Host Run lifecycle event type 的代码真源被 durable transition 复制

- 语义事实或 contract：Host Run lifecycle event type、terminal event set 与 terminal status 映射。
- 正确 owner：`dayu.host.lifecycle_events`。模块文档明确声明它是 lifecycle event type、terminal event set 与 public outbox terminal item set 的代码真源，避免 projection/read API/dispatch/durable helper 各自复制 terminal 集合（`dayu/host/lifecycle_events.py:1`、`dayu/host/lifecycle_events.py:3`）。
- 所有权漂移位置：`dayu/host/durable/run_transition.py` 仍独立定义 `_EVENT_TYPE_RUN_SUCCEEDED/_FAILED/_CANCELLED/_LOST` 裸字符串（`dayu/host/durable/run_transition.py:88`、`dayu/host/durable/run_transition.py:101`），并用 `_run_terminal_event_type` 独立把 `RunStatus` 映射回这些字符串（`dayu/host/durable/run_transition.py:5553`、`dayu/host/durable/run_transition.py:5564`）。
- 直接证据：owner 模块已经有 `_RUN_STATUS_BY_TERMINAL_EVENT_TYPE` 与 `_HOST_TERMINAL_STATUS_BY_EVENT_TYPE`（`dayu/host/lifecycle_events.py:57`、`dayu/host/lifecycle_events.py:63`），durable transition producer 没复用这个真源。
- 失败/成本：新增/调整 terminal event/status 时，EventLog producer、lifecycle projection、outbox/read API 需要同步改多个映射；producer 可能写出 lifecycle owner 不识别或投影错误的 event type。
- 推荐收束：durable transition producer 使用 `HostRunEventType` / lifecycle helper 生成 terminal event type。消费者若必须匹配具体 event，也应引用 enum/helper，不重复裸字符串。
- 验证点：新增测试校验 durable transition 生成的 run terminal event types 与 `lifecycle_events` owner 的 terminal event set 全量一致；新增 unsupported status fail-fast 测试。
