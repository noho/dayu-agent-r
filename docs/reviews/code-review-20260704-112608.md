### 02-未修复-低-`_active_timeout_cancelled_payload` 中 `cancel_requested_at` 取自原始数据库字符串未经格式化

- **入口/函数**: `_active_timeout_cancelled_payload` (run_transition.py:4405)
- **文件(行号)**: `dayu/host/durable/run_transition.py:4438`
- **输入场景**: 任何 `active_cancel_timeout_closeout_in_transaction` 成功路径
- **实际分支**: `payload["cancel_requested_at"] = cancelling.occurred_at` 直接使用 `EventLogRow.occurred_at` 原始值
- **预期行为**: `cancel_requested_at` 应使用 `format_utc_timestamp(parse_utc_timestamp(cancelling.occurred_at))` 格式化，与 `timed_out_at` 使用 `format_utc_timestamp(request.timed_out_at)` 保持一致的格式保证
- **实际行为**: `cancel_requested_at` 直接取原始数据库字符串，`timed_out_at` 通过 `format_utc_timestamp` 格式化。两者在 payload 中格式可能不一致（取决于数据库存储格式）。`_cancel_request_event_id_from_cancelling` 已经验证了 `occurred_at` 可解析，但未将解析结果传递到 payload 构造。
- **直接证据**:
  - `run_transition.py:4438`: `"cancel_requested_at": cancelling.occurred_at` — 原始字符串
  - `run_transition.py:4439`: `"timed_out_at": format_utc_timestamp(request.timed_out_at)` — 格式化后字符串
  - 测试断言 `payload["cancel_requested_at"] == "2026-05-14T01:02:03.000000Z"` 暗示数据库存储格式已匹配，但这依赖于 seed helper 的写入格式，不是 production 保证
- **影响**: 低。当前测试通过说明 seed 写入的格式恰好一致。但若 `RUN_CANCELLING` 事件由不同写入路径产生（如旧版本代码或 migration），`occurred_at` 格式可能与 `format_utc_timestamp` 输出不同，导致下游 projection/outbox 消费 payload 时格式不一致
- **建议改法和验证点**:
  1. 将 `cancel_requested_at` 改为 `format_utc_timestamp(parse_utc_timestamp(cancelling.occurred_at))` 以保证格式一致
  2. 或在 docstring 中注明 `cancel_requested_at` 格式依赖 `RUN_CANCELLING` 事件写入时的格式
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
