8. 三 slices 可独立 review 且无序列冲突。
9. zero-side-effect 断言覆盖所有必要路径。
10. coverage/pyright/README 决策充分。

## Findings

### 01-未修复-中-`parse_calendar_year` 接受 `JsonValue` 导致 API 过宽

- **位置**: §5 Exact APIs, `parse_calendar_year` 签名
- **问题类型**: 架构边界
- **当前写法**: `parse_calendar_year(value: JsonValue, *, field_name: str = "year") -> int`，接受任意 JSON 值。
- **反例/失败场景**: 实际调用方只传 `int | None`：upload 来自 argparse `type=int`（`int`），download 来自 `int(value)` 转换（`int`），`normalize_fiscal_year` 来自 `JsonValue | None`。`JsonValue` 包含 `list`、`dict`、`str`、`float` 等类型，函数内部用 `isinstance(value, bool) or not isinstance(value, int)` 拒绝非 int，但签名暗示接受任意 JSON 结构。
- **为什么有问题**: 违反编码硬约束"禁止使用 `object`、`Any`、无类型参数"。签名过宽让 pyright 无法在调用点捕获类型错误，也让 API 使用者误以为可以传任意 JSON 值。
- **直接证据**:
  - `dayu/fins/domain/filing_semantics.py:327` 现有 `normalize_fiscal_year(value: JsonValue | None)` 签名。
  - `dayu/fins/ingestion_runtime.py:909` 现有 static validator 使用 `request.fiscal_year`（来自 argparse `type=int`）。
  - `dayu/fins/download_contract.py:798-800` 现有 `_parse_date_bound` 使用 `int(value)` 转换。
  - `dayu/fins/tools/read_runtime.py:627` 现有 `normalize_fiscal_year(raw_meta.get("fiscal_year"))` 传入 `JsonValue`。
- **影响**: pyright 无法在调用点捕获类型错误；API 使用者可能误用。
- **建议改法和验证点**: `parse_calendar_year` 签名改为 `int | None`（与 `normalize_fiscal_year` 的 `None` 语义一致），或拆分为 `parse_required_calendar_year(value: int, ...)` 和 `parse_optional_calendar_year(value: int | None, ...)`。验证：pyright 在所有调用点通过。
- **修复风险（低/中/高）**: 低——签名变更是纯类型层面修改，不改变运行时行为。
- **严重程度（低/中/高/严重）**: 中

### 02-未修复-中-`1000..9999` 范围超出冻结契约的明确支持

- **位置**: §5 Exact APIs, `parse_calendar_year` contract, §1 Test matrix
- **问题类型**: 目标漂移
- **当前写法**: 冻结 oracle `upload_filing.date-and-year-domain` 要求"fiscal-year 必须是业务有效的正四位年份"，plan 将其解释为 `1000..9999` 闭区间。
- **反例/失败场景**: "正四位年份"字面意义是"正整数且四位数"，即 `1000..9999`。但如果 oracle 意图是"正整数且最多四位"（即 `1..9999`），则 `1000` 下界是 plan 自行添加的约束。目前无直接用户裁决支持 `1000` 下界。
- **为什么有问题**: oracle 使用中文"正四位年份"，字面意义是"四位数的正整数"，即 `1000..9999`。但该措辞未显式排除 `1..999`。plan 的 `1000..9999` 解释是合理推断，但不是 oracle 的逐字复述。如果未来用户发现 `1..999` 有合法业务用途（如历史数据），则需要重新做 goal confirmation。
- **直接证据**:
  - `docs/cli_ci_oracles.json` line 2573: `"filing-date/report-date 必须是实际存在的 ISO YYYY-MM-DD calendar date；fiscal-year 必须是业务有效的正四位年份。"`
  - plan §5: `parse_calendar_year` 只接受闭区间 `1000..9999`。
- **影响**: 如果 `1000` 下界被证伪，需要重新做 goal confirmation 和 plan review。
- **建议改法和验证点**: 当前解释可接受，但 plan 应在 §4 Direct evidence 中显式注明"正四位年份"→`1000..9999` 的推断步骤。验证：goal confirmation artifact 中的 success signal 已包含 `1000` 和 `9999` 边界测试，说明 controller 已间接确认。
- **修复风险（低/中/高）**: 低——补充文档说明即可。
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-低-download full-date 委托 `parse_iso_calendar_date` 的同源性需验证

- **位置**: §6 Download preservation strategy, full-date 段
- **问题类型**: 契约缺失
- **当前写法**: download `_parse_date_bound` 对 full-date 拆分后用 `f"{year:04d}-{month:02d}-{day:02d}"` 构造 canonical 文本，再调用 `parse_iso_calendar_date`。因此 download 的 `2024-2-9` 仍接受并投影为 `2024-02-09`，而 upload 的同一原始文本严格拒绝。
- **反例/失败场景**: 如果 implementation agent 错误地在 `_parse_date_bound` 的 full-date 分支直接调用 `parse_iso_calendar_date(value)`（原始非补零文本），则 `2024-2-9` 会被拒绝，破坏 download 的非补零 shape 接受行为。
- **为什么有问题**: plan 的文字描述正确，但 `_parse_date_bound` 的 full-date 分支需要先 canonicalize 再调用 owner，这个步骤容易被 implementation agent 遗漏。
- **直接证据**:
  - `dayu/fins/download_contract.py:806-808`: 现有 `_parse_date_bound` 直接用 `int()` 解析非补零 month/day。
  - plan §5 `parse_iso_calendar_date` contract: "必须 exact-match ASCII digit 的 `YYYY-MM-DD`，月日各两位，不调用 `strip`"。
- **影响**: 如果 implementation agent 忽略 canonicalize 步骤，download 的 `2024-2-9` 会被拒绝，破坏既有 download 行为。
- **建议改法和验证点**: plan §6 应显式写出 `_parse_date_bound` full-date 分支的伪代码：`canonical = f"{year:04d}-{month:02d}-{day:02d}"; parse_iso_calendar_date(canonical, field_name=...)`。测试矩阵 §11 Download tests 应包含 `2024-2-9` → accept 的回归测试。
- **修复风险（低/中/高）**: 低——补充 plan 文字和测试即可。
- **严重程度（低/中/高/严重）**: 低

### 04-未修复-中-`tests/cli/test_fins_commands.py` 出现在两个 slices 的 allowed files 中

- **位置**: §10 Slice 2 和 Slice 3 的 Allowed files
- **问题类型**: 切片过粗
- **当前写法**: `tests/cli/test_fins_commands.py` 同时出现在 S2（upload CLI tests）和 S3（download CLI tests + regression）的 allowed files 中。
- **反例/失败场景**: 如果 S2 和 S3 由不同 implementation agent 或不同时间实现，S2 添加的 upload CLI tests 和 S3 添加的 download CLI tests 可能在同一文件中产生合并冲突。S2 修改的 usage matrix test（删除 `filing_date_too_long`/`report_date_too_long`，新增 `invalid_filing_date`/`invalid_report_date`）和 S3 添加的 download regression tests 在同一文件中。
- **为什么有问题**: 两个 slices 对同一文件的修改没有明确的顺序约定。虽然 S3 依赖 S2（prerequisites），但两个 slice 的 CLI tests 在同一文件中，implementation agent 需要小心合并。
- **直接证据**:
  - plan §10 S2 Allowed files: `tests/cli/test_fins_commands.py`
  - plan §10 S3 Allowed files: `tests/cli/test_fins_commands.py`
  - plan §10 S3 Prerequisites: `S1、S2 accepted`
- **影响**: implementation agent 需要在 S3 开始前确保 S2 的 CLI tests 已合并；否则可能产生冲突。
- **建议改法和验证点**: 可接受当前设计（S3 依赖 S2，implementation agent 按序执行），但 plan 应在 S3 的 Exact allowed changes 中注明"在 S2 已修改的 CLI test 文件基础上追加 download regression tests"。验证：S3 的 completion signal 包含 S2 的 upload tests 回归。
- **修复风险（低/中/高）**: 低——补充 plan 文字即可。
- **严重程度（低/中/高/严重）**: 中

### 05-未修复-低-`normalize_fiscal_year` 收紧影响 read runtime 但 plan 未显式覆盖 read path 测试

- **位置**: §8 Contract / error changes, Domain contract 段
- **问题类型**: 测试缺口
- **当前写法**: `normalize_fiscal_year` 从"任意正整数"收紧为"缺失或 `1000..9999` 非 bool 整数"。plan 在 §14 Risks 中提到"历史 `1..999` 或 `>9999` metadata不再可读为合法事实"，但未在测试矩阵中显式覆盖 read runtime 的 fail-closed 行为。
- **反例/失败场景**: read runtime 使用 `normalize_fiscal_year` 解析 source document metadata 中的 `fiscal_year`。如果历史 durable state 包含 `fiscal_year=500`，收紧后的 `normalize_fiscal_year` 会抛 `ValueError`，导致 read runtime 在解析该文档时失败。
- **为什么有问题**: plan 的 goal confirmation 只要求 upload 和 download 共享 owner，未显式要求 read runtime 也遵循 `1000..9999`。收紧 `normalize_fiscal_year` 是正确方向（语义 owner 应一致），但 plan 应在测试矩阵中显式覆盖 read runtime 对非法历史年份的 fail-closed 行为。
- **直接证据**:
  - `dayu/fins/tools/read_runtime.py:627`: `fiscal_year = normalize_fiscal_year(raw_meta.get("fiscal_year"))`
  - plan §14 Risks #1: "历史 `1..999` 或 `>9999` metadata不再可读为合法事实"
  - plan §11 Test matrix: 未包含 read runtime 的 fail-closed 测试
- **影响**: 如果 read runtime 对非法历史年份没有显式 fail-closed 测试，收紧后的 `normalize_fiscal_year` 可能导致意外的 read 失败。
- **建议改法和验证点**: plan §11 Regression tests 应增加：`normalize_fiscal_year(500)` → `ValueError`，以及 read runtime 对包含非法年份的 metadata 的 fail-closed 行为。验证：read runtime 在遇到非法年份时抛出明确错误，不静默忽略。
- **修复风险（低/中/高）**: 低——补充测试即可。
- **严重程度（低/中/高/严重）**: 低

## Open questions

1. **`1000..9999` 下界是否需要用户显式确认？** 当前 plan 将"正四位年份"解释为 `1000..9999`，goal confirmation 的 success signal 已包含 `1000` 和 `9999` 边界测试，说明 controller 已间接确认。但如果未来用户发现 `1..999` 有合法业务用途，需要重新做 goal confirmation。**结论：当前解释可接受，无需阻塞。**

2. **`parse_calendar_year` 的签名是否应与 `normalize_fiscal_year` 保持一致？** `normalize_fiscal_year` 当前接受 `JsonValue | None`，是因为它被 `read_runtime.py` 传入 raw JSON 值。`parse_calendar_year` 作为 required parser，不应接受 `None`。但接受 `JsonValue` 是为了与 `normalize_fiscal_year` 的类型系统一致。**结论：签名过宽是已识别的 finding，但不阻塞 implementation。**

## Residual risks

1. **历史非法 durable state fail-closed**：`normalize_fiscal_year` 收紧后，包含 `1..999` 或 `>9999` 的历史 metadata 会在 read 时抛 `ValueError`。这是新 contract 的预期结果，plan 已明确"按全新设计处理"。**分类：fixed in current slice；无需额外 action。**

2. **CLI 过去静默 strip upload date**：显式外围空白将从接受变为 usage error。这是 strict optional input requirement 的必要 contract change。**分类：fixed in current slice。**

3. **download 与 upload 格式严格度不同**：download 保留 wrapper-owned non-padded shape，upload 严格 canonical ISO。shared owner 只拥有合法年份和 canonical full-date 真实性；download 先按自己的 shape 规范化，再调用 owner。**分类：fixed in current slice。**

4. **UF-PF04 真实 CLI evidence 未执行**：明确由用户排除，owner=UF-PF04 later work unit。**分类：assigned to later work unit。**

5. **其它 upload findings**：UF-FIX01/02/03/05... 各自 work unit。**分类：assigned to later work unit。**

Plan 整体设计合理，唯一语义 owner 正确，API 边界清晰，三 slices 可独立 review，zero-side-effect 断言覆盖充分。主要风险是 `parse_calendar_year` 签名过宽（可修复）和 `1000..9999` 范围超出冻结契约的逐字支持（已有间接确认）。所有 findings 均为低/中严重程度，无 blocker。
