## Findings

### DS-DESIGN-F01 — Service relay 删除的替换协调原语未指定（中）

- **位置**: Codex review §"未来 Implementation WU 范围" item 6；design.md diff line 64-65 "任务协调可以使用不持有事件副本的 readiness / cancellation primitive"；Codex review Open Question #3。
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Design 要求"Service / UI adapter 必须直接消费该 iterator，不得再建立第二个保留 `HostSessionEvent` 的 relay queue"，并允许"不持有事件副本的 readiness / cancellation primitive"。Codex review 将此列为 Open Question #3："terminal observation / UI callback 并发如何用无事件副本的 signaling primitive 保持取消、Outbox fallback 与 renderer close 语义；不得借机建立替代队列。"
- **反例/失败场景**: 当前 `_WatchAndWaitRuntime.queue` 是 Service 内部三个消费者的唯一同步点：(a) `_observe_terminal` 从 queue 读取事件判断终态；(b) UI callbacks（`on_thinking`、`on_activity` 等）从 queue 读取事件驱动渲染；(c) `_WatcherFailure` 通过 queue 传递以触发 Outbox fallback。若直接删除 relay queue，(a)/(b)/(c) 需要各自直接消费 Host iterator——但 `AsyncIterator` 只能有一个消费者。若改为广播原语（如 `asyncio.Condition` + 共享状态），可能变相成为第二 buffer。若用多个独立 watcher subscription 各自 consume，每个 subscription 各自占用一个 Host mailbox。
- **为什么有问题**: 当前 design 正确指出了"不得建立第二个 event-retaining relay queue"，但没有给出一个经过验证的、不持有事件副本的协调模式。实施 agent 将在没有明确模式的情况下自行设计，有较大概率：(1) 引入 disguised second buffer；(2) 破坏 Outbox fallback 触发时序；(3) 让 terminal observation 错过 terminal event。
- **直接证据**: `entrypoint_runtime.py:500-511` 的 `_WatchAndWaitRuntime` 绑定 watcher/queue/drain task 三元组；`entrypoint_runtime.py:1036-1054` 的 `_drain_host_events` 把 iterator 事件顺序 relay 到 queue。当前 Service 的 `_observe_until_terminal` 等方法从该 queue 消费。
- **影响**: 实施 Agent 可能引入 disguised buffer 或破坏 Outbox fallback / renderer close / cancel 语义。
- **建议改法和验证点**:
  1. Design 或 codex review 中应给出至少一个 concrete coordination pattern 示例（如 "为 terminal observer 和 UI callbacks 各创建一个独立 Host subscription，复用 readiness primitive 而非 event buffer 做同步"），但不强制该示例为最终实现。
  2. 未来 implementation WU 的 plan review 必须显式验证替换方案不引入 disguised event-retaining buffer，并覆盖 multi-consumer、Outbox fallback、renderer close 与 cancel path 的 owner-level tests。
- **修复风险**: 低（只需补充 design rationale / pattern 示例，不改 normative rules）。
- **严重程度**: 中

### DS-DESIGN-F02 — byte accounting scope 与 concurrency model 不够精确（低）

- **位置**: Codex review §"Byte accounting"；design.md diff line 67-68。
- **问题类型**: 契约缺失
- **当前写法**: "Session Event Delivery 使用唯一 deterministic helper 计算：对 public envelope 与其 typed payload 中每个 string field occurrence 计算 `len(value.encode("utf-8"))` 后求和，optional `None` 计零"。同时要求 "prospective offer 会让任一累计值超过 policy 时即判定 overflow"。
- **反例/失败场景**:
  - (a) "每个 string field occurrence" 是否包括 identity 字段（`session_id`、`run_id`、`runtime_id`、`dedupe_key` 等）？这些字段相对固定且较小，但计入与否会影响 byte accounting 的可复现性。设计未明确区分 payload string vs identity string。
  - (b) "prospective offer" 的 byte check 与 `put_nowait` 之间：当前 `_offer` 方法（transient_delta.py:321-336）先检查 closed/overflowed/terminal_fenced，再 `put_nowait`。byte check 必须插入在 `put_nowait` 之前且与 item count check 一起原子判定，但设计未说明是否需要 lock 或是否依赖 asyncio 单线程执行模型。
- **为什么有问题**: 实施 agent 可能对 "哪些 string field 参与 byte accounting" 做出不同选择，导致 byte accounting 不可复现或与 design intent 偏离。prospective offer 的并发语义若不明确，可能产生 TOCTOU（byte check 通过后、put_nowait 前的状态变化）。
- **直接证据**: `HostTransientDelta` 包含 10 个字段（api.py:2989+），其中 7 个是 string（`runtime_id`、`session_id`、`run_id`、`attempt_id`、`execution_id`、`dedupe_key`、payload 内 text_delta/name_delta/arguments_delta）。`HostTransientDeltaHub.publish`（transient_delta.py:434-464）在单次同步调用中构造 envelope 并 fanout，当前 asyncio 单线程模型天然序列化，byte check 不需要额外锁，但 design 应显式声明这一依赖。
- **影响**: 实施偏差（byte accounting 计算结果不一致）或过度保守（不必要地加锁）。
- **建议改法和验证点**:
  1. 明确 byte accounting 计算 envelope 全部 string field（包括 identity），还是只计算 payload variable string。两种选择均可接受，但必须二选一并写进 public contract。
  2. 显式声明 prospective offer 依赖 asyncio 单线程协作式调度模型（publish → _offer → byte check + put_nowait 在同一同步调用栈），不需要额外锁。
  3. 在 byte accounting helper 的 docstring 中列举参与计算的字段清单。
- **修复风险**: 低。
- **严重程度**: 低

### DS-DESIGN-F03 — `HostSessionEventDeliveryPolicy` opener-wide 语义与 per-subscription 邮箱的关系未充分阐明（低）

- **位置**: Codex review §"Public interface" item 4；design.md diff line 64-66。
- **问题类型**: 契约缺失
- **当前写法**: "每次 attach 创建一个 Session Event Delivery subscription，并快照本 `open_host` runtime 的 `HostSessionEventDeliveryPolicy`"。policy 是 construction-time、opener-wide 的，但 mailbox 是 per-subscription 的。policy 的 items/bytes 值应用到每个 subscription 的独立 mailbox。
- **反例/失败场景**: 一个 `open_host` runtime 内可能同时存在多个 subscription（多客户端、多 Service adapter）。opener-wide policy 意味着所有 subscription 共享同一 capacity 配置。如果未来需要为不同 consumer 类型（CLI vs Web vs background task）设置不同 capacity，opener-wide policy 不够灵活。但这不是当前需求——当前只有单一 Service consumer。
- **为什么有问题**: 不是 design bug，而是 tradeoff 未被显式讨论。若未来有 heterogeneous consumer 需求，需要从 opener-wide policy 演进为 per-attach policy override，这涉及 `watch_session_events` 签名变更或 policy 分层。当前 design 冻结 opener-wide 是合理的，但应记录该 tradeoff 以指导未来演进。
- **直接证据**: design.md diff line 66: "`watch_session_events(...)` 不增加 policy 参数，单个 Run 也不能覆盖它"。这意味着 policy 无法 per-subscription 差异化。
- **影响**: 未来若需要 per-consumer policy，需要新的 design gate。
- **建议改法和验证点**: 在 design 或 codex review 中增加一句 tradeoff note："第一版 policy 是 opener-wide 的；若未来需要 per-consumer 差异化容量，必须通过新的 public contract design gate 在 `watch_session_events` 或 subscription attach 层面增加 policy override，不得绕过 typed contract。"
- **修复风险**: 低（只加一句 design rationale）。
- **严重程度**: 低

### DS-DESIGN-F04 — overflow error 的 `retryable=True` 语义与实际可恢复性存在张力（低）

- **位置**: Codex review §"Overflow / degraded / disconnect"；design.md diff line 68-69。
- **问题类型**: 最佳实践偏离
- **当前写法**: overflow 时抛 `HostApiError(code=UNAVAILABLE, retryable=True, detail=HostUnavailableDetail(component="session_event_delivery", reason_code="transient_mailbox_overflow"))`。错误 "只说明本 subscription 的 transient 展示投递已不连续，不归因于 consumer 动机或速度"。
- **反例/失败场景**: `retryable=True` 暗示调用方重试（重新 attach watch）可能成功。但如果 policy 不变且 delta burst 特征不变，重试会再次 overflow。调用方可能陷入 retry→overflow→retry 循环。`UNAVAILABLE` 通常表示"服务暂时不可用，稍后重试可能恢复"——但 mailbox overflow 本身不会自行恢复（除非 consumer drain 了足够多的事件，但 disconnect 后 consumer 已无法 drain）。
- **为什么有问题**: `retryable=True` 是技术上正确的（reattach 会创建新 subscription，新 mailbox 从零开始），但缺乏对 root cause 的指引。调用方看到 `UNAVAILABLE` + `retryable=True` 的合理反应是立即重试——这可能加剧问题。当前 `slow_consumer` → `transient_mailbox_overflow` 的 reason_code 改名是正确的（不再归因 consumer speed），但 error code 层面的可恢复性语义未同步审视。
- **直接证据**: 当前 `_slow_consumer_error()`（transient_delta.py:96-111）返回 `HostApiError(code=UNAVAILABLE, retryable=True)`。Design correction 只改了 `component` 从 `session_live_stream` 到 `session_event_delivery` 和 `reason_code` 从 `slow_consumer` 到 `transient_mailbox_overflow`，`code` 和 `retryable` 未变。
- **影响**: 调用方可能做出次优的 retry 决策（立即重试 vs 增大 policy 后重试 vs 降级到 Outbox-only）。
- **建议改法和验证点**:
  1. 考虑将 `retryable` 改为 `False`，或增加 `retryable_with_policy_increase` 语义（但这需要新的 error code design gate）。
  2. 最低限度：在 error detail 或 operator diagnostic 中显式记录命中维度（`max_items` / `max_bytes`），帮助调用方判断是否需要调整 policy。Codex review Open Question #4 已触及该点——建议将其从 open question 提升为 design decision（至少暴露命中维度）。
  3. 若保持 `retryable=True`，补充说明：retry 仅在新 subscription 从零开始的意义上成立；若不调整 policy，同一 delta burst 将再次触发 overflow。
- **修复风险**: 低（澄清语义或调整一个 bool）。
- **严重程度**: 低

### DS-DESIGN-F05 — 未来 implementation WU 范围缺少 config schema 变更的具体文件清单（低）

- **位置**: Codex review §"未来 Implementation WU 范围" item 2。
- **问题类型**: 不可直接实施
- **当前写法**: "扩展 `host_runtime.json` typed schema、ConfigLoader view 与 Service host assembly，使 effective policy 由 caller / Service composition 显式传入；删除 Host capacity fallback。"
- **反例/失败场景**: `host_runtime.json` 的 typed schema 定义、ConfigLoader 的 typed config dataclass、Service 的 `compose_open_host_options` 函数各自在不同文件中。若不明确指出哪些文件需要修改，实施 agent 可能遗漏 ConfigLoader 的 typed config view 或 `compose_open_host_options` 的 policy mapping。
- **为什么有问题**: 当前 scope 描述是 high-level 的，但 config → typed config → Host policy 的装配链涉及多个模块。遗漏任一步骤都会导致 policy 无法端到端生效。
- **直接证据**: Codex review item 2 只有一句话；未列出具体文件。对比 item 3/4/5/6 明确列出了 `dayu/host/transient_delta.py`、`dayu/host/engine_ingest.py`、`dayu/host/open_host.py`、`dayu/service/entrypoint_runtime.py`。
- **影响**: 实施遗漏或 config assembly 不完整。
- **建议改法和验证点**: 在 future WU scope item 2 中补充至少以下文件清单：`dayu/host/api.py`（新增 `HostSessionEventDeliveryPolicy` 导出）、`dayu/host/open_host.py`（`OpenHostOptions` 增加字段）、`dayu/service/host_assembly.py`（`compose_open_host_options` 映射 config → policy）、ConfigLoader typed config dataclass、`host_runtime.json` schema 定义文件。这只是 scope 描述精度提升，不改变 design。
- **修复风险**: 低。
- **严重程度**: 低

## Verified Correct Design Aspects

以下方面经直接代码证据与设计真源核对，确认设计自洽且无 material issue：

1. **Session Event Delivery owner 清晰**：Design 将 publish/fanout/mailbox/overflow/disconnect 全部归属 Session Event Delivery，与 EngineEvent ingest（只做 validation + typed candidate + non-blocking handoff）的边界清晰。Codex review ownership table（8 行）与 `HostTransientDeltaPublisher` Protocol 的现有代码一致。

2. **Unified iterator + single mailbox 可行**：当前 `_watch_session_events_after` 已在 iterator facade 内合流 durable reader + transient drain。Design correction 只改变 mailbox capacity 来源（hard-coded → policy）和增加 byte accounting，不改变合流结构。Service relay 删除后的 iterator 直接消费在技术上是可行的——风险在于替换协调原语（见 DS-DESIGN-F01），而非 iterator 结构本身。

3. **max_items + max_bytes 双界设计正确**：在 Engine public contract 没有单事件 byte bound 的前提下（已通过 Engine design.md 和代码核对确认），单独 item count 不足以形成内存边界。Byte accounting 使用 `len(value.encode("utf-8"))` 是合理的近似——捕获了主要可变成本（字符串 payload 大小）。

4. **Overflow disconnect 不与用户"调用者决定"矛盾**：调用方通过 `HostSessionEventDeliveryPolicy` 显式决定了 capacity。Overflow 是该 capacity 的确定性后果。Disconnect（而非 silent drop）是正确的安全默认——消费者不会误以为收到了连续流。

5. **terminal fence + Outbox recovery 自洽**：Overflow disconnect 后 iterator 不保证观察 durable terminal，但 terminal 仍由 EventLog/Outbox 持久拥有，调用方按既有 Outbox/`get_run` 恢复。这正确分离了 delivery failure 与 durable truth。

6. **不反压 Agent/Engine 的设计完整**：从 EngineEvent ingest（non-blocking handoff）→ publisher（non-blocking offer）→ subscription mailbox（overflow detach，不等待 consumer），整条链路没有 await consumer 的点。现有代码（`_offer` 使用 `put_nowait`、`publish` 同步 fanout）已满足此约束。

7. **没有 semantic ownership drift**：Design correction 将原本模糊归属于 "transient hub" 的 delivery ownership 精确拆分为 publisher owner 和 subscription owner，且不与 EventLog、Run/Attempt、EngineEvent ingest 的 ownership 交叉。对照 `semantic_ownership_drift_review_20260711` 的 16 个 finding pattern，本次 design 没有引入新的跨 owner 泄漏。

8. **HostTransientDelta 的 live-only 边界保持**：Design 未将 transient delta 写入 EventLog、未承诺 replay、未进入 projection/Outbox/memory/audit/Tool Trace。这与 Engine design.md §1.1 的术语边界和 Host design.md 的既有 live-only contract 一致。

## Open Questions (from codex review, re-verified)

以下问题 codex review 已列为 Open Question，本 review 确认它们不阻塞 design correction gate（design correction 是 normative design，不是 implementation plan），但必须在未来 implementation WU 中用证据收口：

1. **Packaged default values**：`transient_mailbox_max_items` / `transient_mailbox_max_bytes` 应取何值。需要代表性 provider delta burst、consumer latency SLO 与 per-subscription memory budget。

2. **Python overhead margin**：logical UTF-8 byte accounting 已冻结，但 packaged default 需要 resident-memory benchmark 校准。

## Conclusion

**Verdict: pass-with-risks**

### Summary

- **Total material findings**: 5（DS-DESIGN-F01 至 F05）。
- **Severity breakdown**: 中 1、低 4。
- **Blocking findings**: 0。无 finding 阻止 design correction 作为 normative design 进入 `final-closeout-pass`。
- **Design fix required**: 建议但不强制。DS-DESIGN-F02（byte accounting scope 精确化）和 DS-DESIGN-F04（overflow error retryable 语义审视）可以在 design.md 或 codex review 中以最小改动澄清，不改变架构方向。DS-DESIGN-F01（Service relay 替换原语）是未来 implementation WU 的前置条件，不是 design correction gate 的阻塞项。
- **Re-review required**: 不建议对 design correction 本身做 re-review。5 个 finding 均为 design 精度提升建议，不构成"必须回到 design gate 重新设计"的级别。建议在未来 implementation WU 的 plan review gate 中验证 DS-DESIGN-F01 的协调模式方案。

### Key Strengths

1. Ownership boundary 清晰且与已有代码结构一致（`HostTransientDeltaPublisher` Protocol → `HostTransientDeltaHub` → `HostTransientDeltaSubscription` 的现成分层）。
2. 不反压 Agent/Engine 的整条链路已由现有 `put_nowait` + non-blocking offer + 异常隔离代码证明可行。
3. 6 个 alternatives（A-F）已系统性评估并拒绝，选择（G）有充分理由。
4. live-only、不与 EventLog 混淆、不承诺 replay 的边界保持与 Engine design.md 和 Host design.md 既有 contract 一致。
5. overflow → disconnect（而非 silent drop）的安全默认是正确的。

### Primary Residual Concern

DS-DESIGN-F01（Service relay 删除的替换协调原语未指定）是未来 implementation 的最高风险项。当前 codex review 将其列为 Open Question #3 是诚实的，但 design correction 作为 normative design 应至少给出一个 concrete coordination pattern 的方向性示例，以降低实施 agent 引入 disguised buffer 的概率。
