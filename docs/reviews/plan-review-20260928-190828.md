## Findings

### 1-未修复-中-S2 日志 helper 缺少自身失败的兜底归属，helper 抛错会吞掉原始公共失败

- **位置**: plan S2 "诊断产生点有两个"节与 `safe_exception_trace` 设计段（"路径解析或帧元数据校验失败即视为外部，不让日志 helper 失败覆盖原始公共失败"）
- **问题类型**: 契约缺失
- **当前写法**: plan 把该属性写成结果要求，但只规定 per-frame 校验失败降级 `[external]`、无 traceback 输出 `[unavailable]`；没有规定 helper 整体抛出计划外异常时由谁 try/except、失败时输出什么。
- **反例/失败场景**: 未知下载异常进入 `_run_direct_stream_producer` 的 `except Exception as exc:` 处理块后，`safe_exception_trace` 因计划外原因抛出二次异常（奇异 `co_filename`/`Path.resolve` OSError/模块字典并发变动等实现边界外情形）→ `_emit_direct_result` 不执行 → producer `finally` 只投递 `ProducerDone` 而无 RESULT 终态 → CLI 端流协议失败逃到外层 catch，投影成 `_FINS_DIRECT_UNKNOWN_FAILURE_MESSAGE` 通用失败。用户看到的终态与真实失败原因完全脱钩——恰是本 work unit 要修的病灶在失败路径上复发。
- **为什么有问题**: goal 成功信号要求"未知异常仍保持安全的 generic 公共失败，但有脱敏……诊断"——公共失败是第一位的，诊断是附加物；plan 的属性声明无实施归属，implementation agent 很可能按 helper 不抛错实现，失败路径（本 work unit 的主题）没有保险。S2 测试清单也没有"helper 抛错仍发 RESULT"的注入用例。
- **直接证据**: `ingestion_runtime.py:4305-4344` producer except 块内 RESULT 发射与后续诊断调用同处一个异常处理块；plan S2 测试清单（URL/token/外部帧/动态类名/深栈/无 traceback）未覆盖 helper 自身异常。
- **影响**: 失败路径测试与真实事故下把 typed/unknown 失败升级为更难诊断的无 RESULT 终态；review 不可验收"失败投影保真"。
- **建议改法和验证点**: plan 明确 call-site 兜底（producer 与 CLI 两处）：`try: trace = safe_exception_trace(...) except Exception: trace = "[unavailable]"`（或等价地在 helper 内部全捕获并返回固定 `[unavailable]`），保证诊断永不先于 RESULT 发射抛出；S2 测试补"注入 helper 抛错"用例，断言 RESULT/公共失败照常发射、退出码不变、日志为 `[unavailable]`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-自定义异常类型名全量抑制削弱 goal 的"脱敏的异常类型/可定位"

- **位置**: plan 边界与契约节 `safe_exception_trace` 类型输出段（"沿 `type(exc).__mro__` 只取第一个……内建异常类型，并对自定义类型加固定 `custom_type=redacted`；不输出任何自定义类名或模块名"）
- **问题类型**: 非最优方案
- **当前写法**: 所有自定义异常（含项目自定义与第三方库类型）的类型名被完全丢弃，只保留最近内建祖先名加固定标记。
- **反例/失败场景**: 真正未知的下载失败若来自未包装的第三方异常（项目使用 aiohttp/httpx/urllib3，见 `runtime/log.py:_DEFAULT_THIRD_PARTY_SUPPRESSIONS`）：抛出点在外部帧（仅 `[external]`），日志只剩 `exception_type=OSError custom_type=redacted stack=[external]... dayu/fins/pipelines/cn_download_workflow.py:NNN`。operator 能看到异常从哪个 dayu 调用点逸出，但看不到异常是什么；两个不同依赖异常在同一调用点逸出时不可区分。
- **为什么有问题**: goal 成功信号与 issue #198 期望行为 2 都要求"脱敏后的**异常类型**与调用栈"；plan 保住了调用栈却把类型压到几乎无信息量，且风险节只承认"16 帧截断"取舍，未承认类型名取舍。动态类名泄密的威胁真实但罕见，全量抑制是用常态诊断价值换罕见威胁。
- **直接证据**: goal"真正未知的 direct download 异常在 operator 日志中留下脱敏的异常类型与调用栈……有脱敏且可定位的 operator 诊断"；issue #198"必须在日志中留下脱敏后的异常类型与 traceback"；`runtime/log.py` 第三方依赖清单证明外部库异常真实存在。
- **影响**: 未知异常排障成本回升（虽然低于现状）；goal"可定位"只由帧承担，类型维度被静默让渡。
- **建议改法和验证点**: 对无法证实为内建的类型输出稳定假名而非全抹平，例如 `custom_type=<sha256("__module__.__qualname__")[:8]>`（不可逆、无泄漏、同类型可关联/不同类可区分）；或允许通过严格标识符正则 + 长度上限的自定义名。若坚持全抑制，须在 plan 明确写出该取舍并经 goal 层确认"异常类型"允许只保留内建祖先。验证点：S2 测试断言两个不同自定义异常类在日志中可区分。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
