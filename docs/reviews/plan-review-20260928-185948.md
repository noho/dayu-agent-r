## Findings

### F1-未修复-中-safe_exception_trace 永不抛出总契约欠规格且 S2 测试清单无对应用例

- **位置**: plan「边界、语义 owner 与契约」第 5 段（`safe_exception_trace` 设计段）与 S2 slice 测试枚举。
- **问题类型**: 契约缺失 / 测试缺口。
- **当前写法**: plan 规定"路径解析或帧元数据校验失败即视为外部，不让日志 helper 失败覆盖原始公共失败"。per-frame 降级规则明确，但 helper 对**未预期运行期意外**（迭代期间 `sys.modules` 被并发 import 变异导致 `RuntimeError`、损坏/异构造的 traceback 链、`frame.f_code`/`f_globals` 为 exotic 对象、`walk_tb` 行为差异）是否必须整体吞掉并降级为固定安全输出，没有写成可测试契约；S2 测试枚举（URL/token/用户路径 message 与 cause、外部帧文件名、动态异常类名、深栈、无 traceback）不含 helper 自身失败用例。
- **反例/失败场景**: （a）CLI 最后一支 catch 中 helper 抛出 → 新异常逃出 `run_fins_direct_command`（fins.py:216-222 块内没有再兜底）→ 解释器顶层把原始 traceback（绝对路径 + 异常文本）打印到 stderr；（b）producer except 块中 helper 抛出 → producer 线程死亡 → threading 默认 excepthook 把原始 traceback 打到 stderr，CLI 只见 MISSING_RESULT。两个场景恰好落在本 work unit 要消除的泄漏与"日志无记录"区域。
- **为什么有问题**: 本 work unit 的成功信号是"脱敏且可定位"；helper 是两个诊断点共用的唯一安全屏障，其自身失败模式却留给 implementation agent 自由裁量。plan 的设计意图句（"不让日志 helper 失败覆盖原始公共失败"）是意图陈述而非 owner 级可断言契约，与 AGENTS.md「测试必须断言 owner 级 contract 行为」不匹配。
- **直接证据**: fins.py:216-222 控制流；ingestion_runtime.py:4305-4344 producer except/finally 结构；plan S2 测试枚举原文。
- **影响**: 低概率、高对称性损失——恰在被保护的 path 上重新引入原始 traceback；review gate 无法验收"helper 永不泄漏"。
- **建议改法和验证点**: plan 补一句硬契约："`safe_exception_trace` 对任意输入不抛出；未预期内部失败整体降级为固定 `exception_type=redacted stack=[unavailable]` 形输出"；S2 测试增加 adversarial 用例（迭代中变更 `sys.modules`、伪造缺元数据 frame/坏 traceback 链）断言不抛出且输出仍只含受信片段。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。

### F2-未修复-低-producer 投影机制自身失败落在两个诊断点之外，原始 traceback 经 threading.excepthook 落 stderr

- **位置**: plan「诊断产生点有两个」段与 S2 slice；风险段未覆盖。
- **问题类型**: 脱敏边界欠声明 / open question 未收敛。
- **当前写法**: plan 规定诊断产生点=（producer 捕获的 download EXECUTION 异常）+（CLI 外层 download catch），未提及投影机制自身（`_download_public_failure_from_exception` 契约构造、`_emit_direct_result`、helper 调用）在 producer except 块内失败时的行为。
- **反例/失败场景**: except 块内任一调用抛出（如未来映射 bug、`FinsPublicFailure` 契约拒绝）→ `finally` 仍投 Done → bridge clean 结束 → CLI 收 `FinsDirectStreamProtocolError(MISSING_RESULT)` typed 错误；线程异常由 threading 默认 excepthook 打**原始 traceback（绝对路径、源码行、异常文本）到 stderr**；operator 按"查看日志"提示找不到任何记录。
- **为什么有问题**: 触发需要投影机制自身有 bug，概率低；但泄漏面（stderr 原始 traceback）与诊断真空面都正落在 issue #198 的目标区域，plan 既未声明接受也未规定兜底，属边界欠声明。
- **直接证据**: ingestion_runtime.py:4305-4344（except 块内连续调用 + finally 投 Done）；`_direct_queue_get`（6354-6377）线程死亡不传播异常；plan 全文未提及 threading.excepthook 路径。
- **影响**: 实施 Agent 不知道该路径是 accepted residual 还是需防护；closeout 风险登记缺一项。
- **建议改法和验证点**: 二选一——（a）plan 风险段显式登记为 accepted residual risk（触发前提=投影机制自身缺陷，真实 CLI 检查已含 stderr 无绝对路径断言可作偶然发现）；（b）规定最小兜底：producer except 块内对投影失败再包一层，失败时对原 exc 做一次安全记录并投固定 EXECUTION RESULT。建议选（a），符合最小化约束。验证点：风险段新增条目即可，无需新测试。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。

### F3-未修复-低-两个同类 typed storage 异常仍落 EXECUTION 兜底并以 unexpected_failure 名义记日志，plan 未声明语义与去向

- **位置**: plan「边界」段（仅映射 `SourceIntegrityPreflightError`）与「风险、PR 边界与报告」段。
- **问题类型**: open question 未收敛 / 文档缺口。

- **反例/失败场景**: staged repair 被其它 publication 阻断或 Phase A/B identity 冲突 → 落 catch-all → public 仍是 `execution / 下载执行失败`（与 issue #198 控诉的误导同类），诊断日志把 typed 阻断记为 `fins.download.unexpected_failure`；closeout 若只读 plan，会误以为所有 storage typed 错误均已保真投影。
- **为什么有问题**: 按 goal 非目标（"public reason 只能由对应 typed owner 提供"、goal 只点名 preflight error）把它们排除在 S1 映射之外是**正确的 goal-bound 最小设计**，不构成 scope 错误；但 plan 有责任把该语义决策和后续去向写明白，否则 review/closeout/operator 三方都会误读日志事件名。
- **直接证据**: source_integrity.py:211-259；`_download_public_failure_from_exception`（ingestion_runtime.py:6824-6887）无对应分支；goal 非目标第 3 条。

- **建议改法和验证点**: plan 风险段补一条：这两个 typed 错误在本 work unit 保持 EXECUTION+安全诊断日志（可经 `custom_type=redacted`+受信帧定位），是否公开 reason 留待单独 issue 评估。验证点：风险段新增条目。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。

## 总体评估（非 finding 的确认项）

- **Goal-bound minimal design**：两个 slice 均直接映射 goal 成功信号（typed reason 保真 + 未知异常脱敏可定位）；CLI 外层 catch 改动由 goal"让 CLI 的查看日志提示有实际对应记录"直接支撑且有代码证据（A3/A4），不构成 goal drift；无新 schema、无通用异常注册框架、无状态机，符合最小化。
- **语义 owner**：storage 拥有封闭事实 enum；`direct_events.py` 拥有公共词汇 enum；`ingestion_runtime.py` 唯一投影点做显式全覆盖映射并直接消费 `exc.reason`，测试断言映射键集合等于 storage enum 全集；CLI/wait 只取 `.value`；无字符串反推、无第二消费者重算。owner 链条成立（A1/A7）。
- **过度耦合检查**：`FinsPublicFailure` 不 import storage（A1 核实重依赖风险真实存在），双层 enum 的语义镜像由穷尽映射测试门控，属刻意 ACL 而非偶合穿透；slices、测试、rollout 步骤无跨层绑定。
- **过度设计检查**：`FinsDownloadFailureReason` 公共 enum 相对 `str | None` 的收益是构造期封闭性 + 穷尽映射测试锚点 + LLM-facing 封闭词汇，成本是双 enum 同步（已被测试门控），与本模块既有风格（`FinsPublicFailureKind` 等封闭 enum）一致，判定合理；`safe_exception_trace` 的受信帧校验每一项都对应真实 spoof/泄漏向量，建设性构造优于事后正则（A8），判定非过度设计。
- **CLI 控制流**：分流条件 `args.command_name == COMMAND_DOWNLOAD` 与既有 dispatch（fins.py:553）同一常量；typed except 先于最后 catch，不改动；producer RESULT 路径与外层 catch 无交集，无重复记录（A5）。
- **slice 与验证**：S1→S2 依赖方向正确（S2 的"EXECUTION 即未知"谓词依赖 S1 映射）；两 slice 均 code-generation-ready（helper 签名、事件名、校验规则、测试期望均已给出）；真实 CLI 验证步骤含来源确认、复现机制（已提交代码路径 A2）、预期断言与清理责任，未知异常明确用注入测试而非伪称真实复现。

## 结论

**pass-with-risks**。

Plan 的证据基础、owner 边界、slice 可实施性与 adversarial 测试设计整体扎实，四个 focus area 均未见结构性缺陷。F1（中）建议在进入实施 gate 前补进 plan（一句硬契约 + 一个 adversarial 用例）；F2/F3 为文档级补登，F4 为验证命令补两个文件。全部 finding 修复成本低、不改设计。若总控裁决 F1 不需回写 plan，也应将其作为实施验收的显式检查项。
