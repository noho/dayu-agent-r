## Findings

### F-01-未修复-中-second-ctrl-c-queued-followup 语义越界

- **位置**: S2（§6.5）TTY REPL state machine 表格 "exit-after-cancel" 行
- **问题类型**: 目标漂移 / open question 未收敛
- **当前写法**: "exit-after-cancel" 行规定："等待...所有本invocation已经durable accepted的sole queued follow-up收口，停止接收新输入，完成display/composer/attachment清理后130"
- **反例/失败场景**: 用户在 active Run 期间按 Enter 创建 queued follow-up，随后立即连续按两次 Ctrl+C。当前 active Run 的 cancel 需要等待 provider/tool 返回后再收口（可能数秒），然后 queued follow-up 还需执行完整的 provider 调用和 terminal（可能数十秒）。用户期望"连续两次 Ctrl+C = 尽快退出"，但 plan 强制等待 queued follow-up 完全执行完毕，用户观感是第二次 Ctrl+C 被忽略。
- **为什么有问题**: 冻结 interactive oracle `interactive.12`（`running-ctrl-c-graceful-closeout`）的 expected behavior 是："连续 Ctrl+C 表达取消完成后退出"、"CLI 等待 Host 将 Run/Attempt 持久化为 terminal cancelled，并完成 watcher、attachment、display、key monitor、runtime、日志和锁清理后 exit 130"。该 oracle 只提到等待**当前 Run** 的 cancel terminal，没有提及等待已经 queued 的 follow-up Run 也完成。Plan 将 exit-after-cancel 的等待范围从"当前 Run 的 cancel terminal"扩展到"所有已 queued follow-up 的完整 terminal"，这改变了冻结 oracle 的语义边界。
- **直接证据**:
  - Oracle `interactive.12` expected: "CLI 等待 Host 将 Run/Attempt 持久化为 terminal cancelled" — 单数 Run，非复数
  - Oracle `interactive.12` forbidden: "第二次 Ctrl+C 先关闭进程而留下 running Run/Attempt或缺失 RUN_CANCELLED" — 只说不能留下 running Run，未说必须执行 queued follow-up
  - Plan §6.5 表格 exit-after-cancel 行: "等当前cancel target canonical terminal与所有本invocation已经durable accepted的sole queued follow-up收口" — 新增了"所有...queued follow-up"
  - 裁决文档 § "已冻结产品语义" 中 "未终结执行恢复" 表格: "QUEUED: 保持同一 queued Run identity，fresh writer 唤醒 ordinary governance" — queued Run 的恢复语义是跨 invocation 的，fresh writer 可以接管，不是必须在当前 invocation 内完成
- **影响**: 实施 Agent 实现后产生不符合用户预期的行为：用户连续两次 Ctrl+C 后被强制等待 queued follow-up 的完整 provider 调用，用户体验显著退化。若后续被用户裁决为错误，需返工修改状态机。
- **建议改法和验证点**:
  1. 明确区分 "exit-after-cancel" 的两个子场景：有 queued follow-up 和无 queued follow-up
  2. 有 queued follow-up 时：取消当前 Run，等待 cancel terminal 收口，保留 queued follow-up 的 durable 事实（使其可被后续 fresh writer 恢复），然后清理并 exit 130
  3. 或者提交该语义扩展给用户裁决，确认"exit-after-cancel 必须等待 queued follow-up 执行完毕"是否为预期行为
  4. 无论选择哪种方案，需在状态机表格中明确记录决策和对应的 oracle predicate 引用
- **修复风险（中）**: 需澄清语义后修改状态机表格和对应 owner-level tests
- **严重程度（中）**: 这是用户可见交互行为，若实现错误会导致用户不满和返工；但因为 queued follow-up 已被 durable 接受，fresh writer 可以接管，实际数据安全性不受影响

### F-02-未修复-中-F13-engine-identity-repair-串线风险

- **位置**: S5（§9.2）Engine contract/schema changes 第 3 项与 §9.3 Host compactor 第 4 项
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**:
  - §9.2.3: "`_classify_iteration()` 只能从同一个 `_IterationState.request_identity`、同一个 `runner_done.provider_request_id` 与本次 `AgentRunRequest.runner_spec.provider/model` 构造。normal final、content-filter final、length continuation最终call、force-answer final都必须携带实际产出该terminal content的成功call identity。"
  - §9.3.4: "repair/multi-pass循环每次iteration重置local response identity；第二attempt accepted只能带第二attempt identity，普通Run或第一attempt identity不能泄漏。"
- **反例/失败场景**: Host compaction operation 的 attempt 1 发生 semantic reject，compactor 在同一 Engine run 内进入 repair 重试。Engine `_IterationState.request_identity` 在 Agent 构造时设置（`attempt_id=X, execution_id=Y`），repair 重试不会改变 `attempt_id`/`execution_id`（因为 repair 是同一 attempt 内的重试），只会递增 `runner_call_index`。如果 second attempt（Host 层面的 attempt 2）使用新的 `AgentRunRequest`（新的 `attempt_id=Z`），那么 Engine 产出的 `response_identity.request_identity.attempt_id` 会正确为 `Z`。但如果 repair 发生在同一 Host attempt 内（同一 `AgentRunRequest`），那么 `attempt_id` 不变，只 `runner_call_index` 递增——此时"第二attempt"的 Engine identity 与第一 attempt 的 identity 共享 `run_id`/`attempt_id`/`execution_id`，只有 `runner_call_index` 不同。
- **为什么有问题**: Plan §9.3.4 说"第二attempt accepted只能带第二attempt identity"，但 Engine 层面，同一 Host attempt 内的多次 Runner 调用（包括 repair）共享同一 `attempt_id`。Host 层面的"attempt"（`CompactionAttempt`）和 Engine 层面的 `RunnerRequestIdentity.attempt_id` 是两个不同概念。Plan 未明确区分这两者，可能导致 implementation agent 错误地将 Engine `attempt_id` 与 Host `CompactionAttempt` number 直接映射，产生串线。
- **直接证据**:
  - `dayu/engine/agent.py` L521-548: `_IterationState.request_identity` 在 Agent 构造时设置，整个 run 生命周期不变
  - `dayu/engine/contracts/agent_run.py` L96-98: `AgentRunRequest.attempt_id` / `execution_id` 必须成对出现
  - `dayu/engine/contracts/runner_identity.py` L27-47: `RunnerRequestIdentity` 同时包含 `attempt_id`/`execution_id` 和 `runner_call_index`
  - Plan §9.2.3 描述 Engine 侧 identity 构造，§9.3.4 描述 Host 侧 compactor attempt 隔离 —— 两处使用不同语义的 "attempt"
- **影响**: 实施 Agent 可能将 Engine `attempt_id`（单次 Engine run 内不变）误解为 Host `CompactionAttempt` number，导致 accepted/rejected event 中的 `successful_response_identity` 与实际 compactor proposal attempt 绑定错误
- **建议改法和验证点**:
  1. 在 §9.2 或 §9.3 明确区分两套 "attempt" 语义：Engine `RunnerRequestIdentity.attempt_id`（Engine run 级）vs Host `CompactionAttempt` number（compaction operation 级）
  2. 明确说明：同一 Host compaction attempt 内的多次 Engine repair 调用共享同一 `attempt_id` 但 `runner_call_index` 递增；不同 Host compaction attempt 使用不同的 `attempt_id`
  3. 在 accepted/rejected event payload 中，`successful_response_identity` 的 `engine_run_id` + `runner_call_index` 足以唯一定位该次 Engine 调用，`attempt_id`/`execution_id` 表达 Host 层级身份
  4. 添加 owner-level test 覆盖 "Host attempt 1 repair → Host attempt 2 accepted" 场景，验证两个 accepted event 的 `response_identity.attempt_id` 不同
- **修复风险（低）**: 只需在 plan 中澄清术语，不改变设计方案
- **严重程度（中）**: 若不澄清，implementation agent 可能错误实现 identity 绑定，导致 durable evidence 不可信；但概念区分本身不复杂

## Open Questions

### OQ-01: `session resume --mode interactive` 的 ticker 拒绝逻辑

Plan §5.2.5 要求 "`--mode interactive` 若携带 ticker，在 `_run_session_resume()` 进入 runtime前由明确 validation拒绝，删除 `_resume_interactive_ticker()`"。当前代码中 `_resume_interactive_ticker()` 函数的存在性和调用路径需要 implementation agent 在 S1 实施前确认。若该函数不存在或已被其他提交删除，则此项无需实现。

### OQ-02: F11 compaction terminal guard 是否覆盖 reactive 路径

Plan §8.2 将所有 proactive 路径统一走 `_commit_proactive_compaction_terminal(...)`。当前 Host 是否存在 reactive compaction 路径（非 proactive 触发的 context compaction）？如果存在，这些路径是否也需要 terminal guard？Plan 的 non-goals 提到"不重写reactive compaction状态机"，但未明确说明 reactive 路径是否已有独立的 terminal 保护。

### OQ-03: POSIX PTY smoke 测试的 CI 环境依赖

Plan §10.5 要求 "POSIX PTY smoke：真实PTY exact bytes与terminal restore；非POSIX记录capability/skip，不拿pipe代替"。Implementation agent 需要可编程 PTY 环境和 VT100/xterm 终端模拟器。这些依赖是否已在 CI 环境中配置？若未配置，PTY smoke 无法执行，应记录为 explicit validation gap。

## Final Plan Review Conclusion

**结论: pass-with-risks**

该 plan 整体质量高，具备以下优势：
- F01-F13 每项均有直接代码证据和冻结裁决支持，动机成立
- 6 个 slice 的依赖关系清晰，实施顺序合理
- 分层语义 owner 表明确，符合 `AGENTS.md` 的语义所有权约束
- Non-goals 边界明确，有效防止 scope creep
- Test 策略、验证命令、覆盖率要求和 secret canary 检查均具体可执行
- 所有引用的 test 文件路径经验证存在
- 17 条待删除 scenario ID 均存在于 `cli_ci_scenarios.json`

存在两个已识别但 plan 未处理的风险点：
1. **second Ctrl+C + queued follow-up 语义**（F-01，严重程度中）：plan 将 exit-after-cancel 的等待范围扩展到已 queued follow-up，这超出了冻结 oracle `interactive.12` 的明确语义。需用户裁决或 plan 修订。
2. **F13 "attempt" 术语歧义**（F-02，严重程度中）：Engine `RunnerRequestIdentity.attempt_id` 与 Host `CompactionAttempt` number 是两个概念，plan 未明确区分，可能导致 implementation agent 错误绑定 identity。

另外有两个低严重度 findings 和一个已消除的路径验证问题（OQ-01、OQ-02 为 open questions，不阻塞 plan 通过）。

**建议**: Controller 应要求 plan 对 F-01 和 F-02 给出明确处理方案后再进入 implementation gate。其他 findings 和 open questions 不构成 gate blocker，可在 implementation 过程中处理。

**Gate blocker 判断**: F-01 是 accepted gate blocker（涉及用户可见交互语义偏离冻结 oracle），F-02 是 accepted gate blocker（可能导致 durable evidence identity 绑定错误）。
