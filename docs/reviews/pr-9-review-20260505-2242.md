## Finding 1 — `run_agent_messages` 未迭代时 Runner 资源泄漏（低风险）

**修复状态**：已修复。已在 `dayu/engine/agent.py::run_agent_messages`
中文 docstring 中标注调用方必须迭代至生成器结束，或在提前停止时显式
调用 `aclose()`；`run_agent_and_wait` 会完整消费。已同步更新
`dayu/engine/README.md` 的函数式入口边界说明。

**文件**: `dayu/engine/agent.py:666-681`

`run_agent_messages` 在函数体顶部通过 `_build_runner(request)` 创建 Runner，但 Runner 的关闭依赖 `agent.run_messages()` 的 `finally` 块——该块仅在异步生成器被迭代（至少一次 `next()`）后才执行。如果调用方获取了 `AsyncIterator` 但从未迭代（例如构造后被取消、或赋值后被忽略），Runner 不会被关闭，仅依赖 GC 的 `__del__` 回收。

```python
async def run_agent_messages(request: AgentRunRequest) -> AsyncIterator[EngineEvent]:
    runner = _build_runner(request)        # Runner 创建
    agent = _AsyncAgent(request=request, runner=runner)
    async for event in agent.run_messages():  # 如果永远不迭代，finally 不执行
        yield event
```

**实际风险**：低。正常路径（`run_agent_and_wait`）一定会完整迭代，且 `_close_runner_once` 是幂等的。但如果上层在 Phase 3+ 出现取消竞态，可能产生连接泄漏。建议在 docstring 中明确标注"必须迭代至生成器耗尽或显式 `.aclose()`"的前置条件。

## Finding 2 — `_ITERATION_INDEX` 硬编码为 0（设计瑕疵）

**修复状态**：已修复。`_ITERATION_INDEX` 已重命名为
`_FIRST_ITERATION_INDEX`，值保持为 `0`；`_FIRST_ITERATION_ORDINAL = 1`
保持不变，分别表达 0-based index 与 1-based ordinal。

**文件**: `dayu/engine/agent.py:62`

```python
_ITERATION_INDEX: int = 0
```

Phase 2 只有单轮迭代，所以 `iteration_index=0` 语义正确。但常量命名 `_ITERATION_INDEX` 暗示它是"当前迭代索引"，与 `_FIRST_ITERATION_ORDINAL = 1` 的命名形成不对称——一个叫 index（0-based），一个叫 ordinal（1-based），但实际语义都是"第一轮"。后续 Phase 引入多轮迭代时需要将此常量改为运行时状态，当前命名可能产生误导。

## Finding 3 — `_close_runner_once` 被 terminal 方法和外层 `finally` 双重调用（冗余但安全）

**修复状态**：已修复。保留 `_close_runner_once` 幂等 close 与外层
`finally` close；将 `_make_cancelled_terminal_after_close` /
`_make_failed_or_cancelled_after_close` 重命名为
`_make_cancelled_terminal_with_close` /
`_make_failed_or_cancelled_terminal_with_close`，明确方法内部会先 close 再
产出 terminal。

**文件**: `dayu/engine/agent.py:476-499`, `dayu/engine/agent.py:180-182`

`_make_cancelled_terminal_after_close`、`_make_failed_or_cancelled_after_close` 在返回 terminal 前调用 `_close_runner_once`，而外层 `run_messages` 的 `finally` 也调用 `_close_runner_once`。由于 `_closed` 幂等守卫，不会出错——但方法名中的 `_after_close` 暗示"调用方应先 close 再调用我"，而实际是"我内部会先 close"。命名意图与实现不一致，阅读成本偏高。
