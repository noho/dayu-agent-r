## Findings

### 1-未修复-低-pre-state dirty check 未定义显式 stop condition

- **位置**: 第 6 节 Exact edit sequencing，步骤 1 "记录 pre-state 与 mismatch audit"
- **问题类型**: 切片过粗
- **当前写法**: "运行 `git status --short`，保存 pre-existing paths；预期至少包含只读输入 `docs/gateflow/pr-190-f17-goal-confirmation-20260807.md`，不得把它归为本 slice 产品修改"
- **反例/失败场景**: 若工作树中存在无关 dirty tracked 文件（并发编辑残留、editor swap file、未跟踪的临时文件），当前步骤只记录但未要求 stop。实施 Agent 可能在脏工作树上执行编辑，导致：
  - manifest 或测试文件的编辑与无关变更产生交集
  - `git diff` 输出混杂，changed-file guard 可能漏判或误判
  - 若后续 commit/push（本 plan 目前禁止，但 future gate 会做），无关变更可能被误卷入
- **为什么有问题**: plan 的 stop conditions 在 section 5 中描述为 post-state 验证（"第二个 path/digest/model-pointer mismatch、count 漂移、unexpected changed file...时立即停止"），但 pre-state 脏工作树本身就是一个应在编辑前停止的条件。Section 5 的 prerequisites 提到"不得覆盖用户已有 goal-confirmation artifact 或其它 dirty work"，该约束暗示了 pre-state check，但步骤 1 未将其操作化为显式 stop condition。
- **直接证据**: plan 第 74 行 "不得覆盖用户已有 goal-confirmation artifact 或其它 dirty work"；步骤 1 第 84 行 "保存 pre-existing paths" 但无 "若存在非预期 dirty file 则停止" 的显式指令
- **影响**: 实施 Agent 跑偏——在脏工作树上执行两处精确编辑，后续 diff guard 仍可能通过但工作树状态已被污染
- **建议改法和验证点**: 在步骤 1 中增加显式 check：若 `git status --short` 输出中除了 `docs/gateflow/pr-190-f17-goal-confirmation-20260807.md`（untracked）外存在任何 modified/deleted 条目，立即停止并要求用户清理。验证点：`git status --short` 输出仅为预期的 untracked gateflow artifacts
- **修复风险（低）**: 仅补充一个 pre-condition check，不影响编辑逻辑
- **严重程度（低）**: 实施 Agent 有经验的不会在脏树上操作；但 plan 的"可 code-generation-ready"要求应对此做显式约束

### 2-未修复-低-旧 digest 校验方法未指定，substring 匹配风险

- **位置**: 第 6 节步骤 2 "只更新 manifest owner entry"
- **问题类型**: 不可直接实施
- **当前写法**: "在 `docs/cli_init_workspace_manifest_v1.json` 中确认旧 digest 恰好出现一次，且绑定路径恰为 `config/prompts/scenes/conversation_compaction_user.md`"
- **反例/失败场景**: 若实施 Agent 使用 `grep -c` 统计旧 digest 出现次数，而文件中恰存在以该 64-char hex 为前缀的更长的 hex 字符串（如 128-char SHA-512），`grep -c` 会将其计为一次匹配。虽然当前 manifest 中不存在该情况（已验证所有 SHA-256 均为唯一 64-char），但 plan 未指定校验方法，留给实施 Agent 自行选择可能不够精确的工具。
- **为什么有问题**: plan 应足够具体以避免实施 Agent 做出不安全选择。manifest 是 JSON，精确校验应通过 JSON parser 按 `path` 定位并比对 `content_sha256` 值，而非对 raw text 做 grep
- **直接证据**: plan 第 96 行；manifest JSON 第 40 行；已验证文件中不存在该 hex 为前缀的更长子串
- **影响**: 实施 Agent 跑偏——在极端边缘情况下使用了不精确的匹配方法，但实际发生概率极低
- **建议改法和验证点**: 将"确认旧 digest 恰好出现一次"明确为：用 JSON parser 读取 manifest，按 `path == "config/prompts/scenes/conversation_compaction_user.md"` 精确定位 entry，并断言 `content_sha256 == "59b50e...87b76"`。同时验证该旧值在其余 42 个 entries 中均不出现。
- **修复风险（低）**: 仅澄清方法，不改变范围
- **严重程度（低）**: 当前 manifest 中实际不存在 substring 匹配风险，更多是 plan 精确度问题

### 3-未修复-低-rollback 验证未独立于正向验证

- **位置**: 第 9 节 Rollback，步骤 3
- **问题类型**: 状态机漏洞
- **当前写法**: "重算 raw digests，运行 `git diff --check` 与 changed-file guard，确认回滚没有影响 pre-existing goal-confirmation / Gateflow artifacts"
- **反例/失败场景**: 若正向编辑意外引入了非 digest 相关的 bytes 变化（如 BOM、trailing newline、不可见 Unicode），反向 patch 恢复两个 digest hunk 后这些额外变化仍残留。`git diff --check` 检查 whitespace 错误但不检查内容完整性。changed-file guard 对照的是 `git diff` 输出——若回滚后的 `git diff` 为零（因为反向 patch 精确恢复了两个 hunk），但额外 bytes 变化仍在文件尾部，`git diff` 不会显示这些变化（它们从未被 committed）。
- **为什么有问题**: rollback 的目标是恢复 pre-edit 状态，但验证手段只覆盖了"两个 digest hunk 是否恢复"而非"文件是否与 pre-edit 完全一致"。在当前场景下：manifest 和测试文件的 raw digest 必须在回滚后与 pre-edit 值相等——这是比 `git diff` 更强的验证。
- **直接证据**: plan 第 190-193 行；pre-edit 的 manifest raw SHA-256 为 `d95de6...a9f8`，测试常量值为 `d95de6...a9f8`
- **影响**: 回滚不完整——若额外 bytes 残留，下一次 pre-state audit 会发现 digest 不匹配
- **建议改法和验证点**: rollback 验证增加独立 raw digest check：manifest `read_bytes()` SHA-256 必须重新等于 `d95de6...a9f8`，测试文件中 `FROZEN_MANIFEST_SHA256` 必须重新等于 `d95de6...a9f8`。这与正向验证对称：正向用保存后 bytes 计算新值，回滚用恢复后 bytes 验证旧值。
- **修复风险（低）**: 增加一行 digest assert，不改变 rollback 逻辑
- **严重程度（低）**: 当前 plan 的回滚步骤已足够精确（精确反向 patch），额外 bytes 变化的概率极低；但 digest-based 验证更可靠且与正向验证对称

## Best-Practice / Optimal-Solution / Overengineering / Overcoupling Review

- **最小方案**: 两处精确 digest 替换是满足 owner contract 的最小变更。不引入新抽象、helper、schema、兼容分支或自动化。
