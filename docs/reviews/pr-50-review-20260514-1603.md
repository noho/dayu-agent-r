## Findings

### 1-未修复-[高]-Active release 后的 queue promotion 被非持久 wakeup 异常阻断

- **入口/函数**: `HostAdmissionService.cancel_run`, `HostAdmissionService.closeout_attempt_terminal`, `_promote_after_release`
- **文件(行号)**:
  - `dayu/host/admission.py:465-477`
  - `dayu/host/admission.py:501-510`
  - `dayu/host/admission.py:136-159`
  - `dayu/host/admission.py:1608-1609`
  - `dayu/host/admission.py:1506-1513`
  - `tests/host/test_admission_queue.py:104-127`
  - `tests/host/test_admission_queue.py:832-897`
- **问题描述**: active Run 被 cancel 或 terminal closeout 后，主事务已经提交并释放 active slot，但 `_promote_after_release` 先调用 `service.wakeup_port.wake_queue_promotion(session_id)`，随后才调用 `service.promote_next_queued_run(session_id)`。`AdmissionWakeupPort` 明确允许具体实现抛出 `RuntimeError`，而 Phase 3 README/计划也把 wakeup 定位为 no-op 或测试挂点，不应成为 durable promotion 的前置条件。
- **直接证据**:
  - `cancel_run` 在 `result.released_active_slot` 为真时调用 `_promote_after_release`，并把返回值作为 promotion 结果。
  - `closeout_attempt_terminal` 对所有 terminal closeout 都调用 `_promote_after_release`。
  - `_promote_after_release` 的实际顺序是先 `wake_queue_promotion`，再 `promote_next_queued_run`。
  - `AdmissionWakeupPort.wake_queue_promotion` 的 docstring 允许测试或上层实现抛出自身错误。
  - `_idempotent_cancel_result` 对重复 cancel 返回 `promotion=None` 且 `released_active_slot=False`，因此若第一次 cancel 已提交但 wakeup 抛错导致 promotion 未执行，使用相同幂等键重试不会补做 promotion。
  - 现有测试只覆盖 happy path spy 和“事务回滚前不 wake/promote”，没有覆盖“事务提交后 wakeup 失败”的路径。
- **可复现场景**:
  1. 同一 Session 已有一个 active `RUNNING` Run 和至少一个 `QUEUED` Run。
  2. 上层注入的 `AdmissionWakeupPort.wake_queue_promotion` 在通知路径抛出异常。
  3. 调用 `cancel_run` 取消 active pre-dispatch Run，或调用 `closeout_attempt_terminal` 关闭 active Attempt/Run。
  4. cancel/terminal 事务提交成功，active slot 已释放。
  5. `_promote_after_release` 在 wakeup 处抛出，`promote_next_queued_run` 没有启动。
- **期望行为**: durable promotion check 应在 active release 之后独立执行，非持久 wakeup 失败不能阻断同事务之后的新事务 promotion。至少应保证 promotion transaction 先执行，或者 wakeup 异常被隔离为 after-commit diagnostic，不破坏 durable queue convergence。
- **实际行为**: wakeup 异常直接传播，promotion transaction 不会执行；当前 Phase 3 明确没有 queue scanning、scheduler 或 recovery，queued Run 会停留在 `QUEUED`，直到后续另有手工或外部路径触发 promotion。
- **影响**: 这是 liveness/stability 问题。调用方可能收到异常，但底层 cancel/terminal 已提交；队列从用户视角卡住，并且同一幂等键重试不会自动修复 active release 后丢失的 promotion。
- **建议改法**: 将 durable promotion 与 wakeup 解耦。优先在 `_promote_after_release` 中执行 `promote_next_queued_run`，再把 wakeup 作为非阻塞通知；或者捕获并记录 wakeup 失败，但仍执行 promotion。若要保留 wakeup 失败上抛语义，也应让返回/错误模型明确区分“主事务已提交但通知失败”，并提供可重试的 promotion convergence 路径。
- **建议验证**: 新增一个会在 `wake_queue_promotion` 抛错的 wakeup port 测试，分别覆盖 active cancel 和 terminal closeout，断言主事务已提交、queued Run 能 promotion 或有明确可恢复路径。另补一个“提交后、promotion 前失败，再用相同幂等键重试”的测试，确保不会永久卡队列。
