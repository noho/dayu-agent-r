## Findings

### 1-未修复-严重-long25 失败暴露的是 smoke 断言层问题，不是 compact 子系统缺陷

- **位置**: `_assert_compact_acceptance` — `utils/smoke_host_public_conversation_memory_scenarios.py:2911-2948`
- **问题类型**: 动机不成立
- **当前写法**: `memory-compact` suite 要求 `failed_total == 0`。任何 `CONTEXT_COMPACTION_FAILED` 都触发 `RuntimeError("memory-compact observed CONTEXT_COMPACTION_FAILED")`。
- **反例/失败场景**:
  - **场景 A (compaction 成功)**: proactive trigger → LLM proposal → quality gate accept → `CONTEXT_COMPACTED` → dispatch with compacted context → 后续轮回答正确 → smoke PASS
  - **场景 B (fallback dispatch 成功)**: proactive trigger → LLM proposal → quality gate reject → `CONTEXT_COMPACTION_FAILED` + `FALLBACK_ACTION_DISPATCH` → dispatch with tier 4/5 fallback context → 后续轮回答正确 → smoke **FAIL** (因为 `failed_total > 0`)
  - **场景 C (真正失败)**: proactive trigger → LLM proposal → quality gate reject → `CONTEXT_COMPACTION_FAILED` + `FALLBACK_ACTION_FAIL_CLOSED` → 无法 dispatch → session 中断 → smoke FAIL
  - 场景 B 和场景 A 的 conversation continuity outcome 完全相同（后续轮 hard_answer_contains 均通过），但 smoke 只在场景 B 报告失败。**场景 B 的失败是误报**——系统按设计执行了 tier 4/5 fallback dispatch，conversation continuity 未受损。
- **为什么有问题**:
  1. `CONTEXT_COMPACTION_FAILED` 后接 `FALLBACK_ACTION_DISPATCH` 是设计状态机的**正常恢复路径**（Fact C），不是 bug。tier 4/5 的设计意图就是"compact 失败后降级继续服务"。
  2. smoke 把"compaction 失败"等同于"系统失败"，但这个等式在设计上不成立。
  3. 真正需要 smoke 报告失败的是：`FALLBACK_ACTION_FAIL_CLOSED`（fallback 也失败）或 fallback dispatch 后 conversation continuity 受损。
  4. 之前的两个 plan review（20260619-094608 Finding 1、20260619-094619 Finding 01）也都指出此问题——compaction failure 不等于系统 failure。
- **直接证据**:
  - Fact A: smoke 已有能力区分 `compacted_proactive` 和 `failed_proactive`
  - Fact B: 断言 `failed_total == 0` 过于严格
  - Fact C: tier 4/5 dispatch fallback 是设计状态机的合法收口
  - Fact E: `fallback_action` 字段可以区分 `dispatch` vs `fail_closed`
  - `dayu/host/dispatch.py:2154-2157` — `fallback_action = FALLBACK_ACTION_DISPATCH if budget.hard_budget_passed else FALLBACK_ACTION_FAIL_CLOSED`
- **影响**: 
  - 实施 Agent 可能把正常的 fallback 行为当作 bug 去修
  - 运维人员看到 `SMOKE FAIL` 后无法判断是否需要立即处理
  - 长期 flaky smoke 会导致运维对 compact 健康信号失去信任
- **建议改法和验证点**:
  1. **区分 compaction 失败的影响层级**：
     - `FALLBACK_ACTION_FAIL_CLOSED` → 硬失败（Run 无法 dispatch，系统无法服务）
     - `FALLBACK_ACTION_DISPATCH` + conversation continuity 受损 → 软警告（compact 失败导致了信息丢失）
     - `FALLBACK_ACTION_DISPATCH` + conversation continuity 正常 → 通过（系统按设计降级运行）
  2. 修改 `_assert_compact_acceptance`：不再简单断言 `failed_total == 0`，改为检查 `failed_proactive` 中 `fallback_action == "fail_closed"` 的数量
  3. 在 `_compact_audit_summary_from_rows` 中增加 `fallback_action` 字段的读取
  4. 验证：构造含 `CONTEXT_COMPACTION_FAILED + fallback_action=dispatch` 的 EventLog rows，断言 smoke 通过（或软警告）；含 `fallback_action=fail_closed` 的 rows，断言 smoke 硬失败
- **修复风险（中）**: 需要扩展 `CompactAuditSummary` 和 EventLog payload 读取逻辑；不影响已有 production code
- **严重程度（严重）**: 当前断言逻辑将设计内的恢复路径误判为系统失败，若不修正，smoke 的 compact 验收信号将不可用

### 2-未修复-高-CONTEXT_COMPACTION_FAILED 诊断字段完全未暴露，无法不查 SQLite 定位 root cause

- **位置**: `_compact_audit_summary_from_rows` (line 3038-3096)、`_assert_compact_acceptance` (line 2911-2948)、`_print_compact_audit_summary` (line 2890-2908)
- **问题类型**: 可观测性缺口 / 契约缺失
- **当前写法**: smoke 从 EventLog 读取 compact event rows，但 `_compact_audit_summary_from_rows` **只做 event type + trigger_source 计数**，完全丢弃了 `CONTEXT_COMPACTION_FAILED` payload 中的 `failure_reason`、`attempt_count`、`retryable`、`budget_after_attempted_compact`、`fallback_action`、`policy_decision`、`diagnostic_refs` 等诊断字段。`_assert_compact_acceptance` 在 `failed_total > 0` 时只打印 `"memory-compact observed CONTEXT_COMPACTION_FAILED"`，不包含任何 failure detail。
- **反例/失败场景**: CI 中 long25 smoke 报 `CONTEXT_COMPACTION_FAILED`，开发者必须：(1) 保留 workspace，(2) 手动打开 SQLite，(3) 定位 EventLog row，(4) 解析 JSON payload，才能知道是 LLM proposal 质量不通过、retry 预算耗尽、还是 budget 压力过大。这完全违反了 smoke 自诊断的目标。
- **为什么有问题**: 
  - Fact E 显示 EventLog payload 包含丰富的结构化诊断字段
  - smoke 读了 EventLog 却只取计数，浪费了已有的丰富诊断信息
  - `CONTEXT_COMPACTION_FAILED` 的不同 `failure_reason` 对应完全不同的根因：
    - `QUALITY_CHECK_REJECTED` → compactor prompt/instruction 质量
    - `PROPOSAL_FAILED` → LLM provider 可用性
    - `HARD_THRESHOLD_AFTER_COMPACT` → budget policy 配置
    - `MAX_ATTEMPTS_EXHAUSTED` → repair 策略
- **直接证据**:
  - Fact E: `build_context_compaction_failed_payload` 定义了完整的诊断 payload 结构
  - `utils/smoke_host_public_conversation_memory_scenarios.py:3038-3096` — 只计数，不读诊断字段
  - `utils/smoke_host_public_conversation_memory_scenarios.py:2938-2939` — RuntimeError message 不包含任何 failure detail
- **影响**: 长期 smoke flaky 无法快速定位 root cause；开发者被迫查 SQLite，违背 smoke 自诊断目标
- **建议改法和验证点**:
  1. 新增 `CompactFailureDetail` dataclass，包含 `failure_reason`、`attempt_count`、`fallback_action`、`budget_after_attempted_compact`
  2. `CompactAuditSummary` 新增 `failure_details: tuple[CompactFailureDetail, ...]` 字段
  3. `_compact_audit_summary_from_rows` 在遍历 `CONTEXT_COMPACTION_FAILED` rows 时提取 payload 诊断字段
  4. `_print_compact_audit_summary` 打印每条 failure detail
  5. `_assert_compact_acceptance` 的 RuntimeError message 包含 failure detail 摘要
- **修复风险（低）**: 纯增量字段，不改变现有断言逻辑；`_compact_row_trigger_source` 已证明读取 EventLog payload 字段可行
- **严重程度（高）**: 缺少结构化诊断输出是 root cause 定位的主要障碍

### 2b-未修复-严重-material pack vNext 转换失败是确定性 bug，不是 LLM 不稳定

- **位置**: `_previous_compacted_references_vnext` (compact_material.py L3370-L3391)、`_parse_previous_reference_continuity_text` (compact_material.py L3467-L3484)、`_log_rejected_attempt` (compaction_operation.py L1351-L1389)
- **问题类型**: observability gap / 测试缺口 / root cause 误判风险
- **当前写法**: long25 的两个 `CONTEXT_COMPACTION_FAILED` 的 `proposal_manifest_ref` 为空。根因异常链路为：`conversation_compact_input_vnext_from_material_pack` (compact_material.py L598) → `_previous_compacted_view_vnext` (L3394) → `_previous_compacted_references_vnext` (L3370) → `_parse_previous_reference_continuity_text` (L3467) → `ValueError("previous reference continuity text is invalid")`。这是 **pre-proposal 失败**——发生在 LLM compactor 被调用之前，Host material pack → vNext 转换阶段。
- **反例/失败场景**:
  1. `_parse_previous_reference_continuity_text` 要求文本格式为 `"<prefix>reason; <prefix>text"` 两个 `"; "` 分隔段（L3477-L3483）。如果 previous compact 产出的 `REFERENCE_CONTINUITY` block 的某行 text 格式不符合这个约定，parse 直接 raise `ValueError`。
  2. 在 `compaction_operation.py` L507-L579 的 try/except 中，这个 `ValueError` 被 `except Exception as exc:` (L551) 捕获，归类为 `_FAILURE_PROPOSAL_FAILED`。但 `proposal_manifest_reference` 仍为 `None`（L478 初始化值），因为 manifest 记录发生在 `_prepare_compactor_proposal` 内部（L770），而异常在进入该函数之前的 L777 `conversation_compact_input_vnext_from_material_pack` 就已抛出。
  3. `_exception_diagnostic_suffix` (L1324-L1334) 产生的诊断后缀为 `"ValueError:previous reference continuity text is invalid"`，**不包含 offending text 内容**。
  4. `_log_rejected_attempt` (L1366-L1389) 记录的 `message` 是 `_safe_exception_message(exc)`，即 `str(exc)` = `"previous reference continuity text is invalid"`，被截断到 `_MAX_SAFE_EXCEPTION_MESSAGE_CHARS`。
  5. 此 failure mode **重试无意义**：同一 material pack 会再次触发同一 parse 失败。但 `attempt_number < max_attempts` 时 `repairable=True`，代码会 retry，浪费 compactor 调用。
- **为什么有问题**:
  1. **root cause 误判**: `failure_category=PROPOSAL_FAILED` + 空 `proposal_manifest_ref` 看起来像是 "LLM compactor 调用失败"，但实际是 Host 内部 material pack → vNext 转换的确定性 parse bug。开发者可能花时间调查 LLM provider 可用性或 compactor prompt 质量，而真正的 bug 在 memory snapshot 的 reference continuity text 生成逻辑。
  2. **offending text 不可见**: 即使看到 `"previous reference continuity text is invalid"` 日志，也无法知道是哪个 `CompactMaterialBlock` 的哪行 text 格式异常。必须查 SQLite 定位具体的 `REFERENCE_CONTINUITY` material block。
  3. **无效重试**: 同一 snapshot → 同一 material pack → 同一 parse 失败。`max_attempts > 1` 时会白白重试。
  4. **smoke 无法区分**: 当前 smoke 只看到 `CONTEXT_COMPACTION_FAILED` 计数 +1，无法区分这是 "pre-proposal material pack bug" 还是 "LLM proposal 质量问题"。
- **直接证据**:
  - compact_material.py L3467-L3484: `_parse_previous_reference_continuity_text` 要求 `"; "` 分隔的两段文本，prefix 必须匹配
  - compact_material.py L3382-L3383: 遍历 `block.text.splitlines()` 逐行解析，无 try/except 保护单行
  - compaction_operation.py L551-L577: `except Exception` 捕获，归类为 `_FAILURE_PROPOSAL_FAILED`
  - compaction_operation.py L478: `proposal_manifest_reference` 初始化为 `None`
  - compaction_operation.py L777: material pack 构造在 compactor 调用之前
  - compaction_operation.py L1324-L1334: `_exception_diagnostic_suffix` 只含异常类型和消息
- **影响**: (1) 确定性 bug 被掩盖为 LLM 不稳定；(2) 无效重试浪费资源；(3) CI flaky 无法快速定位；(4) 开发者 root cause 分析方向错误
- **建议改法和验证点**:
  - **Host 侧（根本修复）**:
    1. `_previous_compacted_references_vnext` 中对每行 parse 加 try/except，失败时记录 warning 并跳过该行（用 fallback reason+text），而不是让整个 material pack 构造崩溃
    2. 或者 `_parse_previous_reference_continuity_text` 的 ValueError message 中包含 offending text 前 N 个字符，如 `f"previous reference continuity text is invalid: {text[:80]!r}"`
    3. compaction_operation 中对 material pack 构造失败应标记为 `repairable=False`（同一 snapshot 重试无意义）
  - **Smoke 侧（诊断增强）**:
    1. 从 `CONTEXT_COMPACTION_FAILED` payload 中提取 `failure_reason` 和 `diagnostic_refs`
    2. 对 `failure_reason=proposal_failed` + `proposal_manifest_ref=None` 的组合输出专项 warning：`"SMOKE COMPACT_DIAGNOSTIC pre-proposal failure (material pack), proposal_manifest_ref=none, retry will not help"`
    3. 在 stdout 中打印 `diagnostic_refs` 完整内容，其中包含异常类型和消息
  - 验证：构造 reference continuity text 格式异常的 previous compacted view material pack，确认 Host 侧不再崩溃，smoke 侧日志能定位 offending block
- **修复风险**: 中（Host 侧涉及 compact material parse 的容错策略变更）
- **严重程度**: 严重（确定性 bug 被掩盖为 LLM 不稳定，重试无意义，root cause 无法从 smoke 日志定位）

### 3-未修复-中-smoke 运行中 compact 状态不可见——HostEvent.activity 未被消费

- **位置**: `_next_terminal_for_run` — `utils/smoke_host_public_conversation_memory_scenarios.py:2361-2377`
- **问题类型**: 可观测性缺口
- **当前写法**: `_next_terminal_for_run` 只消费 `terminal_status is not None` 的事件。中间所有 PROGRESS 事件——包括 `activity.kind == CONTEXT_COMPACTION` 的 HostEvent——被完全丢弃。
- **反例/失败场景**: 
  - 运行 L08 margin pressure 轮次时，Host dispatch 内部触发 proactive compaction。PROGRESS event 携带 `HostActivityView(kind=CONTEXT_COMPACTION, status=STARTED)` 和后续 `COMPLETED` 或 `FAILED`。但这些事件在 `_next_terminal_for_run` 中被 `if event.terminal_status is not None` 过滤掉。
  - smoke 等到全部 42 轮跑完后才在 `_compact_audit_summary` 中看到 compact 发生了，但**不知道是在哪一轮触发的、compact 花了多久、是在 compacted context 还是 fallback context 下回答的**。
  - 这导致：无法判断 L25 constraint assert 是在 compacted context 还是 fallback context 下做出的——两种情况的语义完全不同。
- **为什么有问题**:
  1. `HostEvent.activity` 是 public API 的一部分（Fact D），不消费它就是浪费已有的可观测性信号
  2. 无法在运行中判断"这一轮回答是在 compacted context 还是 fallback context 下产生的"
  3. 无法判断 conversation continuity 是通过 compact 维持的还是通过 fallback 维持的
- **直接证据**:
  - Fact D: `HostEvent.activity` 支持 `kind=CONTEXT_COMPACTION`
  - `utils/smoke_host_public_conversation_memory_scenarios.py:2376` — `if event.run_id == run_id and event.terminal_status is not None` 过滤掉所有 PROGRESS
- **影响**: running 中 compact 行为完全盲视
- **建议改法和验证点**:
  1. 在 `_run_round` 中增加对 watcher 流的非 terminal event 观测：消费所有 `event.run_id == run_id` 的事件
  2. 当 `event.activity is not None and event.activity.kind == HostActivityKind.CONTEXT_COMPACTION` 时打印 `SMOKE COMPACT_ACTIVITY status=<status> title=<title>`
  3. 不改变 `_next_terminal_for_run` 的现有行为（仍返回 terminal event），activity 消费作为纯观测 side channel
  4. 验证：`--suite memory-compact` 输出中应出现 `SMOKE COMPACT_ACTIVITY` 行，且时机应在某轮 L01-L25 期间（而非 smoke 结束后）
- **修复风险（低）**: 对 watcher 消费逻辑的增量修改，不影响现有断言
- **严重程度（中）**: 不阻塞 smoke 运行，但严重削弱运行中诊断能力

### 4-未修复-中-daily smoke / diagnostic smoke / eval 三层已有自然边界，新增 suite 与现有架构重叠

- **位置**: 方案中的 smoke 分层讨论
- **问题类型**: 非最优方案 / 过度设计 / 架构边界
- **当前写法**: 方案可能倾向在 smoke 脚本中新增多个 suite（如 `memory-proactive-compact`、`memory-reactive-compact`、`memory-compact-fallback`）
- **反例/失败场景**:
  - **Public API 层不可区分 compact 路径**: proactive/reactive/fallback 三个 suite 在 public Host API 层面的 observable outcome 几乎相同（session 存活 + marker 通过）。区分它们需要读 EventLog 的 `trigger_source` 和 `fallback_action` 字段——这已经是 `_compact_audit_summary` 在做的事。
  - **Reactive compaction 无法被 deterministic mock tool 触发**: reactive compaction 需要 Engine provider overflow（`dayu/host/engine_ingest.py:1264`），当前 mock 工具返回固定大小响应。

### 7-未修复-低-`_compact_pressure_reserve_tokens` 对多窗口模型的分支实际无区分

- **位置**: `_compact_pressure_reserve_tokens` — `utils/smoke_host_public_conversation_memory_scenarios.py:2692-2702`
