No other construction sites exist.

### 2.2 Fallback path: error handling preserved

Old code (try/except → manual `_append_compaction_failed_event` in both branches):
- Success: `build_recent_window_fallback_selection` → `estimate_recent_window_fallback_budget` → dispatch/fail_closed
- Exception: `build_selection_failure_window_payload` → `_append_compaction_failed_event(action=FALLBACK_ACTION_FAIL_CLOSED)`

New code (single `build_fallback_decision_input` → inspect `fallback_decision`):
- `build_fallback_decision_input` internally catches exceptions and returns `selection=None, fallback_handoff=None, action_hint=FALLBACK_ACTION_FAIL_CLOSED`
- dispatch.py inspects `fallback_decision.selection is None` → `_LOGGER.error` → `_append_compaction_failed_event` with `failed_input` fields
- dispatch.py inspects `fallback_decision.action_hint != FALLBACK_ACTION_DISPATCH` → `return None` (fail-unstarted)

Semantically equivalent to old behavior. The exception propagation is replaced by structured error payload in `CompactPipelineFallbackDecisionInput`, which is more auditable.

### 2.3 `_append_compaction_failed_event` receives identical payload shape

Old code constructed fields from local variables (`selection.to_window_payload()`, `selection.digest`, `budget.to_payload()`, `FALLBACK_ACTION_DISPATCH`). New code sources same semantic values from `failed_input: CompactPipelineFailedPayloadInput` produced by `build_fallback_decision_input`. The payload schema (`fallback_input_window`, `fallback_input_digest`, `fallback_budget_result`, `fallback_action`) is identical.

### 2.4 No stale/cursor guard weakening

`_GovernanceCompactPending` continues to carry `expected_status` and `expected_input_event_sequence`. The guard at line 1388 (`run.status != pending.expected_status`) and the cursor guard at line ~1395 (expected_input_event_sequence check) are untouched by this diff.

### 2.5 Log observability: minor `exc_info` loss in error path

- **位置**: `dispatch.py:2007-2014`
- **当前代码**: `_LOGGER.error("dispatch.compact.fallback_selection_failed session_id=%s run_id=%s failure_reason=%s", run.session_id, run.run_id, failed_input.fallback_policy_decision)` — no `exc_info=True`.
- **旧代码**: `_LOGGER.error("dispatch.compact.fallback_selection_failed session_id=%s run_id=%s failure_reason=%s", ..., exc_info=True)` — had `exc_info=True` with `type(exc).__name__`.
- **影响**: 旧的 exc_info 打印完整 traceback，新的 log 只打印 `failed_input.fallback_policy_decision`（字符串常量 `"deterministic_recent_window_selection_failed"`）。不过异常详情已进入 `fallback_input_window.failure_reason` payload 字段（由 `build_fallback_decision_input` 中 `_fallback_selection_failure_reason` 构造），因此 EventLog payload 保留了完整诊断。日志层面的 traceback 丢失不影响审计能力。
- **严重程度（低）**: 不影响正确性；仅影响运维排障时的日志详细度。EventLog payload 比日志 traceback 更适合审计。
