## First-principles assessment

修改动机成立，而且严重性没有被高估。当前链路确实存在 Host 每订阅者 256 项 mailbox 与 Service 256 项 relay queue 两层瞬态缓冲；两处容量均为私有常量，`slow_consumer` 不能精确说明溢出发生在哪一层；只按条目计数也无法约束大字符串 delta 的逻辑负载。把唯一瞬态事件 mailbox 收回 Host、由 Host 拥有 fan-out、顺序、terminal fence、overflow 和 detach 语义，是与 Engine/Host 边界一致的正确方向。

但当前草案尚不能作为实现真源。它把“一个 mailbox”写成了架构结论，却没有冻结删除 Service relay 后 command wait、event consumption、Outbox fallback、取消和 renderer close 的可执行状态机；同时把“非等待式入队”扩大成了当前单事件循环实现无法兑现的“永不反压”承诺。公共错误语义、控制文档和运行时 policy owner 也仍互相冲突。因此本轮不能 `pass-with-risks`。

## Verified ownership map

- Engine owner：单次 run 的事件产生与 generator 内顺序；不拥有 session 观察、cursor、fan-out 或 replay。
- EngineEvent Ingest owner：Host 持久化接纳与从 Engine event 到 Host 事实的投影；持久化提交后才可发布 transient delta。
- Session Event Delivery owner：应为 Host，负责订阅身份、publication sequence、per-subscription mailbox、terminal fence、overflow、detach 和统一 iterator 投影。
- Durable recovery owner：EventLog/Outbox 与 `get_run` 的既有 Host/Service 合同；transient mailbox 不得变成 replay 真源。
- Runtime capacity owner：在冻结 watcher 签名下，最小且一致的 owner 是 `open_host` composition/runtime operator，而不是某个 UI callback 或单次订阅者。
- UI/Service owner：选择需要展示的业务事件、消费/渲染、依据 typed delivery failure 触发 durable recovery；不拥有 Host fan-out 或第二份事件队列。

## Material findings

### CODEX-DESIGN-F01-未修复-[高]-删除 Service relay 后的消费、取消与关闭状态机没有闭合

- **状态**：accepted-candidate
- **位置**：`docs/host/design.md:362,1018-1022`；`docs/reviews/wu-transient-delivery-ownership-design-codex.md:113-129,155-166,234-242`。
- **问题类型**：状态机缺口、资源生命周期、公共 contract 不完整。
- **当前 wording**：Service 直接消费统一 iterator，不得再创建 event-copy queue；任务协调可以使用不复制事件的 primitive；提前停止时取消任务或“若对象支持”则调用 `aclose()`。源 artifact 同时把删除 relay 列入未来实现范围，却把 terminal observation、UI callback、cancel、Outbox fallback 和 renderer close 的精确并发关系留在 open question。
- **具体失败场景**：Service 先 attach watcher 后 submit，随后必须同时消费 live event、等待 terminal、轮询 `get_run`，并在 iterator failure 时进入 Outbox recovery。若单协程直接 `async for`，命令等待和 durable fallback 无法并行；若另起 task 但未定义 sole-`anext` owner 与 close 顺序，取消时可能并发执行 `anext()`/`aclose()`，或在 submit 失败、cancel terminal race、startup Outbox backfill、renderer closing 时泄漏 subscription/吞掉 terminal。当前实现正是通过“先取消并 await drain task，再 `aclose` watcher”避免 active async generator 并发关闭。
- **为什么这是问题**：这是移除第二队列的核心实现问题，不是可延后的参数选择。设计若不拥有该状态机，未来实现者只能在 Service 层重新发明 relay queue、用私有 cast/fallback 补洞，或改变 attach-before-submit 和 Outbox 语义。
- **直接证据**：`entrypoint_runtime.py:459-487` 额外定义 private closable iterator protocol；`entrypoint_runtime.py:646-959,1013-1076` 依赖立即启动的 drain task 和严格关闭顺序；`entrypoint_runtime.py:1079-1212,1470-1530,1711-1771` 把 live terminal、`get_run` 与 Outbox recovery 合并；`tests/service/test_entrypoint_runtime.py:745-765,1121-1152,1155-1210,1523-1563,1675-1777,1819-1907` 固化 attach、race、fallback 与 cleanup contract。Host 公共签名在 `api.py:3902-3911` 只承诺 `AsyncIterator`，并不承诺 `aclose`。
- **影响**：可能重新产生隐性队列/任务、subscription 泄漏、cancel 卡住、terminal 丢失或重复、Outbox fallback 时序漂移、renderer 未正常收尾；直接违反冻结目标与 semantic owner 约束。
- **建议修正 / 验证**：在设计中冻结无 event-copy queue 的 Service 协调状态机：一个 consumer task 是唯一 `anext` owner；它直接处理 callback 并只更新有界语义状态（例如 terminal/failure slot + `asyncio.Event`/Future），不得缓存事件；command task 与 durable probe 只读取该状态；关闭顺序必须明确为请求停止/取消 consumer、await consumer、再按公开 contract detach。分别写清 submit、cancel、startup reconnect、watcher error、terminal race、never-started 与 normal close 的 transition。冻结 iterator cleanup contract：若必须保持精确 `AsyncIterator[...]` 返回注解，则设计不得依赖不可见的 `aclose`；若允许保持统一 iterator 外观但公开一个可关闭子协议，则应由 Host API 明确承诺，而不是 Service 私有 cast。增加上述每条 race 的 owner-level 测试，并禁止 fake 自带队列掩盖生产时序。
- **修正风险**：中。任务仍然必要，但可以只传递 terminal/failure 信号而不复制事件；必须避免把该 task 误判为“双重 buffer”。

### CODEX-DESIGN-F02-未修复-[高]-“慢 UI/Service 永不反压 Agent/Engine”超出了当前执行模型能够证明的边界

- **状态**：accepted-candidate
- **位置**：`docs/host/design.md:358,362,370,1921`；源 artifact 的目标、时序与测试范围。
- **问题类型**：不成立的安全/性能不变量、event-loop 耦合。
- **当前 wording**：Host ingest 只做同步、非阻塞、非抛异常的 handoff；任何 watcher 都不得影响 ingest、EventLog、run terminal 或 cancellation；慢 UI 只会延迟自身 durable pull 或耗尽 mailbox budget，永不反压 Agent/Engine。
- **具体失败场景**：CLI/Service 与 Host actor/Engine event consumer 运行在同一 asyncio event loop。一个同步 renderer callback 阻塞，或大量 watcher 使 Hub 对每个订阅者同步执行 offer/byte accounting，都会占用该 loop；`_consume_worker_events()` 无法获得调度，Engine generator 的后续 `anext()` 被间接延迟。队列没有 `await put()` 并不能消除 event-loop starvation。
- **为什么这是问题**：草案把“生产者不等待消费者队列腾位”与“消费者永远不能影响生产者进展”混为一谈。前者当前可实现，后者需要线程/进程或调度域隔离、订阅者 admission/fan-out 上界等更强机制。若 public design 承诺后者而实现只满足前者，生产故障会被错误归因。
- **直接证据**：`open_host.py:1460-1493` 以当前 running loop 装配 Hub 与 scheduler；`dispatch.py:3387-3397,3887-4090` 在该 loop 上创建并运行 Engine event consumer task；`transient_delta.py:434-465` 在 publish 调用栈同步遍历全部 subscription；`entrypoint_runtime.py:1157-1212,1239,1297,1434` 在消费路径同步调用展示/诊断 callback；当前慢消费者测试主要阻塞 Service 消费或 `get_run`，没有覆盖阻塞 callback 和高 fan-out。
- **影响**：冻结目标在 adversarial workload 下不可兑现；延迟可能传播到 Engine consumption、terminal publication 和 cancellation，且现有测试会给出虚假安全感。
- **建议修正 / 验证**：先明确冻结语义。若目标是“被动不读取或异步读取慢的订阅者不得通过容量等待反压生产者”，将 contract 精确收窄为 Host publish 从不 await consumer、满则 detach，并把 blocking callback/loop starvation 作为 adapter 责任与受测约束；每个 event 的 byte size 必须只计算一次再 fan-out。若“永远”也覆盖阻塞 callback 和任意 watcher 数量，则必须设计独立执行域以及订阅者 admission/总 fan-out 上界，不能只靠 mailbox。新增至少两类测试：callback 阻塞时 Engine/terminal 的调度边界；多 watcher fan-out 下 publish latency/不变量。
- **修正风险**：高。若坚持字面“永远”，会显著扩大架构范围；较安全的最小方案是收窄承诺并明确同步 callback 必须快速返回或由上层在隔离执行域运行。

### CODEX-DESIGN-F03-未修复-[高]-overflow 使用 `HostUnavailableDetail` 造成公共错误语义所有权漂移

- **状态**：accepted-candidate
- **位置**：`docs/host/design.md:368,1324-1340`；`docs/reviews/wu-transient-delivery-ownership-design-codex.md:139-146`。
- **问题类型**：公共错误 contract 冲突、semantic ownership drift。
- **当前 wording**：overflow 固定抛出 `HostApiError(UNAVAILABLE, retryable=True, HostUnavailableDetail(component="session_event_delivery", reason_code="transient_mailbox_overflow"))`；同一 design 的错误章节仍规定 `unavailable` 只用于 execution scheduler fatal error 或 Host startup failure，且 `HostUnavailableDetail` 表示 Host 执行可用性。
- **具体失败场景**：某一订阅者因自身 budget 耗尽而断开，但 Host、run、其他 watcher 和 durable recovery 都健康。上层看到 `UNAVAILABLE/retryable=True` 后可能按 Host 故障执行重启、退避或全局告警，而不是只 detach 当前 iterator 并从 Outbox/`get_run` 恢复。
- **为什么这是问题**：overflow 事实的 owner 是 Session Event Delivery subscription，不是 execution Host availability。复用一个“看起来接近”的 detail 会污染跨层治理语义，也使 metrics、用户诊断和 retry policy 无法区分局部观察缺口与 Host 不可用。
- **直接证据**：`dayu/host/api.py:1367-1394` 将 `HostUnavailableDetail` 描述为 Host availability；`docs/host/design.md:1324` 将 `unavailable` 的允许来源限定为 scheduler fatal/startup；当前 `transient_delta.py:96-111` 正是历史 `slow_consumer` 复用该错误，新草案没有修正其语义 owner。
- **影响**：错误恢复范围过大、可观测性失真、Service 可能采用错误重试策略；design 内部自相矛盾。
- **建议修正 / 验证**：由 Host API 定义 delivery/subscription 专属 typed detail（以及与既有错误码集合一致的明确 code），字段直接表达 watcher 已 detach、live continuity 不再保证、durable recovery 可用；同步更新 design 的 error union、Service mapping、日志/metrics 和 owner-level tests。“调用者决定”应只指预算选择；drop/disconnect/continuity 语义必须继续由 Host 固定拥有。若坚持复用 `UNAVAILABLE`，必须显式重写其公共含义和所有消费者 contract，而不能只新增 `reason_code`。
- **修正风险**：中。会触及公共 schema，但这是新设计且项目禁止以兼容分支掩盖错误语义。

- **建议修正 / 验证**：在目标 design 中删除或精确限定 `:124` 的旧限制，使新 policy 成为明确例外且只存在一个 typed source of truth；在 correction artifact 中把“由 control owner 更新/替换冲突 WU 后才能进入实现”列为硬前置条件。未来范围应明确列出 Host public API/export、strict config schema/parser/packaged JSON、Service assembly、Host/Service/config/tests README、error schema 与 owner-level/E2E tests。当前评审不要求也不授权修改只读 control。
- **修正风险**：低到中。主要是契约对齐；不修则实现风险为高。

### CODEX-DESIGN-F05-未修复-[中]-opener-wide policy 是最小方案，但 caller 表述与总资源边界尚未归一

- **状态**：accepted-candidate
- **位置**：`docs/host/design.md:346,364-370,1302-1304,1921`；源 artifact 的 policy、byte accounting、lifecycle 与测试范围。
- **问题类型**：owner 表述不一致、资源模型不完整、过度承诺。
- **当前 wording**：一处称 Service/UI/CLI 选择运行时 delivery policy，另一处规定整个 `open_host` 只有一个 construction-time policy，`watch_session_events` 无 per-subscription 参数；每个 mailbox 由 `max_items + max_bytes` 有界，因此描述为 caller-owned capacity 和受控内存。
- **具体失败场景**：同一 Host 中交互式 CLI 与后台 Service watcher 有不同消费速度，却只能共享同一预算；更重要的是，攻击者或错误上层可创建大量 watcher，每个都合法占满其独立 budget，publish 还要同步 O(N) fan-out。当前 subscription 的 `_terminal_run_ids` 会随长生命周期 watcher 观察到的 terminal run 增长，也不计入 byte/item budget。于是单 mailbox 有界并不等于 Host 总瞬态内存或 ingest 工作量有界。
- **为什么这是问题**：per-subscription override 并非必然更优；在冻结 watcher API 下，它会扩大 contract 并引入“谁可突破 Host 上限”的新问题。真正缺失的是对 owner 和边界的精确定义，而不是简单把 policy 下放给每次订阅。
- **直接证据**：`transient_delta.py:204-220` 为每个 subscription 建独立队列并维护无容量约束的 terminal run set；`transient_delta.py:388-465` 的 Hub 无订阅 admission 上界且同步遍历；草案只有 per-mailbox item/byte budget，没有 aggregate/subscriber/fence 生命周期规则。
- **影响**：caller ownership 容易被误解为每个 UI 可定制；容量指标不能推导 Host 总资源上界，高 fan-out 或长 session 仍可能拖慢 ingest/增长内存。
- **建议修正 / 验证**：保留 opener-wide policy 作为本 WU 的最小方案，并明确其 caller 是 runtime composer/operator，policy 是所有 subscription 的统一默认/上限；删除“UI/CLI 各自选择 policy”的歧义，把 per-subscription override 明确列为非目标。另行冻结 terminal fence 的有界生命周期，并说明 subscription admission/aggregate budget 是本 WU contract 还是带 owner、触发条件和测试的 residual work。测试应覆盖长生命周期多 run、多个异速 watcher、oversized single event、items/bytes 精确边界、subscription detach 后资源回收以及 fan-out 上界。UTF-8 逻辑字节应在每个 event 上只计算一次并随 queue entry 保存/精确扣减。
- **修正风险**：中。给 Host 增加全局复杂 quota 可能过度设计；最小修正是诚实限定单订阅资源合同、约束 fence，并为 aggregate risk 建立明确 owner/后续 gate。

## Decisions that survive adversarial review

以下方向不构成 finding，建议保留：

- **Host 是 Session Event Delivery owner**：与 Engine 只拥有 run-local event generation 的边界一致，没有理由把 session fan-out 或 replay 下沉到 Engine。
- **统一 iterator = durable bounded pull + 唯一 transient mailbox**：这是保留调用外观并消除双 buffer 的最小结构；不应把 transient delta durable 化，也不应在 Service 再复制事件。
- **`max_items + max_bytes` 合理且必要**：items 限制对象/排队固定成本，UTF-8 logical bytes 限制大字符串变量负载。它不是 Python heap 精确计量，设计已经正确避免作此承诺。实现时需要一个 canonical public-event byte accounting helper、一次计算、多订阅复用及边界 fixture。
- **overflow 后交付已入队 prefix，再抛 typed disconnect**：在没有 gap marker/ack/replay 的前提下，比 silent drop-and-continue 更安全；该行为与“调用者选择预算”不冲突，因为 continuity policy 应由 Host 固定拥有。
- **terminal fence 与 durable recovery 分工**：accepted-and-enqueued delta 必须先于 durable terminal；overflow 后 iterator 不再承诺观察 terminal，调用者转向 Outbox/`get_run`。Host 层逻辑基本自洽，缺口主要在 F01 的 Service 编排与 F03 的错误类型。
- **不需要 per-watcher background task**：Host mailbox 可以用 level-trigger readiness 和 pull iterator 实现；必要的 Service consumer task 只要不复制事件，就不等于第二 buffer。

## Public config, schema, README and test scope audit

源 artifact 已识别 API type/export、strict runtime config、Service assembly、Host mailbox、Service relay 删除、README、coverage 与 pyright，方向基本完整。但在进入实现前还需把以下项显式纳入 future WU acceptance criteria：

- 公共 delivery-specific error detail/code 及 Service recovery mapping。
- `AsyncIterator` 的 detach/close contract，或不依赖 `aclose` 的完整状态机。
- `docs/host/design.md:124` 与新 public option/export 的内部矛盾消除。
- control owner 对既有两个冲突 deferred WU 的重登记/替换。
- `dayu/config/README.md`、`dayu/service/README.md` 与 tests README 的职责检查；现有 Service README 仍公开 relay queue 256 行为。
- 不只测试 passive slow reader，还测试同步 callback 阻塞、高 fan-out、长生命周期 terminal fence、aggregate assumption 与 cleanup races。
- 测试 fake/fixture 不得自建无界队列来掩盖新的唯一 mailbox owner。
- packaged 默认值必须由 workload/SLO 证据选择；未有证据前不应把任意数字写成架构真理。

## Open questions requiring owner decisions

1. 冻结的 `AsyncIterator[HostSessionEvent]` 是要求精确返回注解，还是只冻结统一迭代外观、允许返回一个公开的 closable subtype？若是前者，cleanup 必须完全通过 iterator execution/cancellation contract 闭合。
2. “慢 UI/Service 永不反压”是否只指被动慢读和 mailbox 容量等待，还是也包括阻塞同步 callback、event-loop starvation 和任意订阅者数量？两种含义需要完全不同的实现边界。
3. 运行时 policy 的 caller 是否明确为 `open_host` runtime composer/operator？若未来确需 per-subscription 差异，谁拥有不可突破的 Host 上限？
4. terminal fence 如何在长生命周期 session、多 run 情况下有界回收，同时继续禁止 post-terminal transient delta？
5. subscription admission/aggregate memory 与 O(N) fan-out 是本次未来 WU 的验收项，还是由哪个明确后续 WU、什么触发阈值承接？
6. `transient_mailbox_max_items` 与 `transient_mailbox_max_bytes` 的 packaged 默认值、metrics 维度和 heap safety margin 由哪组真实 workload/SLO 证据确定？

## Residual risks and tracking destination

- 若按建议把 guarantee 收窄为“Host 不 await 被动消费者”，同步 callback 的调度风险仍需由 UI/Service adapter contract 和性能测试承接，不能留成无 owner 注释。
- UTF-8 logical bytes 只能是稳定预算单位，不等于实际 heap；heap margin 应由监控和负载测试校准，而不是在 accounting helper 中猜测对象开销。
- opener-wide budget 不能独自约束 Host aggregate memory；若生产 topology 允许不受信任的多 watcher，必须在 Host admission owner 处建立独立 follow-up gate。
- durable recovery 只能恢复 terminal/run state，不能恢复 transient thinking/activity prefix；用户可见诊断必须明确这是 live continuity loss，而不是完整事件 replay。
- control 文档当前只读，因此本 artifact 仅记录冲突；在 control owner 完成裁决前，不应启动实现 WU。

## Final conclusion

**Verdict：fail。**

草案选择 Host 单 mailbox、统一 iterator、显式 item/byte policy、overflow 后 typed disconnect 与 durable fallback 的总体方向正确，也比保留双 buffer、Service-only buffer、unbounded queue 或 silent drop 更简单安全。但 5 个 material findings 中有 4 个高严重度问题：Service 单邮箱切换状态机未闭合；字面“永不反压”无法由同 event-loop + 同步 fan-out 模型证明；overflow 错误复用了错误的 Host availability 语义；目标设计与只读控制约束存在直接冲突。另有 1 个中严重度问题：opener-wide policy 虽是当前最小方案，但 caller owner 与 aggregate resource 边界尚未归一。

在进入代码实现前必须完成 design fix，并对修订后的设计做独立 re-review。re-review 至少要看到：F01 的可执行状态机和 cleanup contract、F02 的精确定义或执行域方案、F03 的 delivery-specific public error、F04 的 authoritative contract/control handoff，以及 F05 的 runtime owner 与资源边界。默认值和 heap margin 可以在有 owner、有验证计划的前提下保留为后续证据驱动决策；上述四个高严重度问题不能降级为普通 residual risk。
