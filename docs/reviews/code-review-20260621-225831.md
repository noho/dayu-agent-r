### S1-CR-F01: digest outcome JSON projection is duplicated → **已关闭**

**入口/函数**: `callback_payload_digest` (wait_callback.py:494)、`_wait_resolution_digest` (waiting.py:1138)

**验证路径**:

1. `wait_callback.py:518` (`_callback_payload_digest`) 调用 `wait_resolution_digest(envelope.wait_id, envelope.idempotency_key, envelope.outcome)`。
2. `waiting.py:1146` (`_wait_resolution_digest`) 调用同一个 `wait_resolution_digest(wait_id, request.idempotency_key, request.outcome)`。
3. 两者都从 `dayu/host/durable/wait_resolution_digest.py` import（wait_callback.py:32、waiting.py:97）。
4. `wait_resolution_digest` (wait_resolution_digest.py:30-48) 统一构造 `{"wait_id", "idempotency_key", "outcome": resolve_wait_outcome_json(...)}` 并调用 `sha256_digest_json`。
5. `resolve_wait_outcome_json` (wait_resolution_digest.py:51-82) 的 completed/lost JSON shape 与原 `waiting.py` 及 `wait_callback.py` 的实现逐字段一致——`kind`、`result` 各子字段、`payload_ref` 结构均未变。
6. late rejection diagnostic digest (waiting.py:1180) 改用 `resolve_wait_outcome_json(request.outcome)`，原语义不变。
7. `waiting.py` 中原 `_resolve_outcome_json`、`_tool_success_json`、`_tool_failure_json`、`_tool_cancelled_json`、`_tool_lost_json`、`_tool_result_meta_json`、`_host_payload_ref_json`、`_provider_status_ref_json` 全部删除，改为从共享模块 import（waiting.py:87-97）。
8. 测试 `test_callback_digest_matches_resolve_wait_digest_for_completed_and_lost` (test_wait_callback.py:216-241) 直接验证 `callback_payload_digest(envelope) == _wait_resolution_digest(wait_id, request)` 对 completed 和 lost outcome 成立。

**结论**: 两处 digest 计算现在调用同一 `wait_resolution_digest` 实现，outcome JSON shape 未变，late rejection diagnostic digest 语义保持。closed。

### S1-CR-F02: callback stale timestamp parser does not reuse Host timestamp helper → **已关闭**

**入口/函数**: `_stale_status_or_none` (wait_callback.py:525)

**验证路径**:

1. wait_callback.py:543 调用 `parse_utc_timestamp(boundary_text)`，从 `dayu.host.durable.codec` import（wait_callback.py:31）。

## Residual Risk

1. **failed/cancelled outcome 的 callback↔resolve  digest 对齐无独立专项测试**：`test_callback_digest_matches_resolve_wait_digest_for_completed_and_lost` 仅覆盖 completed 与 lost。由于两路径调用完全相同的 `wait_resolution_digest(...)` 函数且该函数为纯函数（相同输入必定相同输出），对齐由实现保证而非测试单独证明。分类：residual risk（低），由共享实现覆盖。

2. **stale check 与 resolve 之间的并发窗口**：`_stale_status_or_none` 在 `read_wait_state` 后、`resolve_callback_wait` 前执行。若在此窗口内另一个并发操作将 wait 推进到终态（且 deadline 为 None），callback 会进入 resolver 并被幂等吸收。这是 plan 明确允许的行为（race collapse 到 `INVALID_WAIT_STATE`），不属于 fix 引入的新风险。分类：residual risk（低），tracked by accepted Slice 1 design behavior。

3. **`_callback_wait_state_from_status` 对未映射 `WaitRecordStatus` 抛出 `ValueError`**：`HostCommandWaitCallbackPort.read_wait_state` (command.py:805-823) 未捕获此 `ValueError`。当前 `WaitRecordStatus` 只有 5 个值（WAITING、RESOLVED、FAILED、CANCELLED、LOST）全部有映射，此路径仅在新增 status 而未同步更新映射时可达——属于编程错误检测而非运行时风险。分类：residual risk（极低）。

4. **`parse_utc_timestamp` 拒绝 `+00:00` 格式而 plan 提到"accepted input is Z or explicit +00:00"**：plan (line 194) 写 "accepted input is an ISO-8601 UTC timestamp (Z or explicit +00:00)"。当前 `parse_utc_timestamp` 仅接受 `Z` 格式。由于 `deadline_at`/`expires_at` 由 `format_utc_timestamp` 写入（固定 `Z` 格式），正常持久化值不会出现 `+00:00`。若持久化层出现 `+00:00`，当前行为是正确拒绝（`INVALID_WAIT_STATE`）而非静默接受异常边界。此行为与 controller 对 S1-CR-F02 的裁决一致（"非法固定格式边界映射为 INVALID_WAIT_STATE"）。分类：residual risk（极低），plan 文字与实现严格性之间的轻微差异，当前行为更安全。
