# Plan Review: Conversation Memory Smoke Suite 拆分方案

- **Reviewed target**: 拟定方向——用 `--suite` 表达验收目标（memory-core / memory-proactive-compact / memory-reactive-compact / memory-compact-fallback / all），用 `--pressure-mode` 表达施压方式
- **Scope**: `utils/smoke_host_public_conversation_memory_scenarios.py` 的 suite 拆分与 compact 验收信号设计
- **Reviewer**: AgentMiMo (adversarial plan review)
- **Date**: 2026-06-19

---

## Assumptions Tested

1. compact 验收信号可通过 public Host API 获取
2. proactive 与 reactive compact 可通过 public smoke 区分
3. fallback 可独立于 compact success 验证
4. utils 脚本边界（不读 EventLog）应保持
5. 现有 `--suite=core/long/all` 不足以证明 compact 子系统健康

---

## Findings

### 01-未修复-严重-fallback 与 compact success 在 public Host API 层不可区分

- **位置**: 拟定方向 memory-compact-fallback / memory-proactive-compact / memory-reactive-compact 的验收信号
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: 方案要求"显式验 compact trigger source、accepted/failed/fallback 信号"
- **反例/失败场景**:
  - 场景 A: compact 成功 → CONTEXT_COMPACTED event → session 继续正常 → 后续轮回答正确
  - 场景 B: compact 失败 + fallback_action=dispatch → CONTEXT_COMPACTION_FAILED event + fallback window → session 继续正常 → 后续轮回答可能正确
  - 场景 C: compact 根本未触发（context 未达 soft threshold）→ session 正常
  - 从 public Host API 看，三个场景的 observable outcome 完全相同：session 仍 open、后续轮 terminal 是 SUCCEEDED、回答可能包含 marker
- **为什么有问题**:
  - compact acceptance 的 ground truth 在 EventLog 的 `CONTEXT_COMPACTED` canonical fact（含 `accepted_candidate`、`quality_check_result`、`compact_artifact_ref`）
  - fallback 的 ground truth 在 EventLog 的 `CONTEXT_COMPACTION_FAILED` payload 的 `fallback_action` 字段
  - trigger source 的 ground truth 在 `CONTEXT_COMPACTION_REQUESTED` payload 的 `trigger_source` 字段
  - **public Host API 层面没有直接暴露这些字段**
- **直接证据**:
  - `dayu/host/context_events.py:22-31` 定义四种 canonical event type，payload 中的 `trigger_source`、`fallback_action`、`accepted_candidate` 等字段只写入 EventLog
  - `dayu/host/api.py:3031` HostEvent 有 `activity: HostActivityView | None`，但 `_compact_activity()` 只映射 status/severity/title，不暴露 trigger_source 或 fallback_action
  - `utils/smoke_host_public_conversation_memory_scenarios.py:2295-2311` `_next_terminal_for_run` 只消费 terminal event（`terminal_status is not None`），中间的 compact activity event 被跳过
- **影响**: 实施 Agent 无法按方案写出能区分 compact success / fallback / not-triggered 的验收代码；若强行用"session 正常 + marker 存活"做断言，会把 fallback 当 success 通过
- **建议改法和验证点**:
  - **方案 A（推荐）**: 承认 compact 验收信号必须来自 durable 层，将 compact trigger/accept/fallback 验证保留在 `tests/host/test_public_compact_smoke.py`（已有且完备），不纳入 public smoke suite
  - **方案 B**: 修改 smoke script 的 event 消费逻辑，增加对 intermediate HostEvent 的 activity 观测（不读 EventLog，只读 public HostEvent.activity），打印 `SMOKE COMPACT_ACTIVITY kind=... status=...` 行；然后在 suite 中用 stdout 解析做软观测。但这只能观测到"compact 发生了"和"其 status 是 COMPLETED/FAILED"，无法区分 trigger source 和 fallback_action
- **修复风险（低/中/高）**: 高——需要决定是否突破 utils 脚本不读 durable 的边界
- **严重程度（严重）**: 方案的核心验收目标（区分 compact success/fallback/trigger source）在当前架构约束下不可直接实施

### 02-未修复-中-proactive 与 reactive 在 public smoke 层不可区分

- **位置**: memory-proactive-compact vs memory-reactive-compact 的 suite 分离
- **问题类型**: 过度设计
- **当前写法**: 方案把 proactive 和 reactive 拆成两个独立 suite
- **反例/失败场景**: 两个 suite 的 observable outcome 完全相同——都是"施加压力 → session 继续正常 → marker 存活"。区分它们的唯一方式是检查 EventLog 的 `trigger_source` 字段
- **为什么有问题**:
  - proactive 触发条件：dispatch pre-start governance 时 estimated context > soft threshold（`dayu/host/dispatch.py:1029`）
  - reactive 触发条件：Engine provider overflow 时发出 `CONTEXT_COMPACTION_REQUESTED`（`dayu/host/engine_ingest.py:1269`）
  - 两者的触发路径不同，但从 public smoke 角度看，只要 context budget policy 存在且 pressure 足够大，Host 内部会选择哪个路径取决于 context 估算时序，smoke script 无法控制
  - 拆成两个 suite 意味着需要为每个 suite 设计不同的 prompt sequence 来强制触发特定路径，但 public API 不提供这种控制粒度
- **直接证据**:
  - `dayu/host/context_policy.py:27-37` ContextCompactionTriggerSource 只有两个值，且只写入 EventLog payload
  - `dayu/host/dispatch.py:1029` proactive 在 `_run_pre_start_governance()` 内触发，是 Host 内部调度逻辑
  - `dayu/host/engine_ingest.py:1269` reactive 在 `_handle_context_compaction_requested()` 内触发，是 Engine provider 回调
- **影响**: 实施 Agent 被迫为两个 suite 设计本质上相同的 prompt sequence，增加维护成本但不增加验收覆盖
- **建议改法和验证点**: 合并为单一 `memory-compact` suite，验证"compact 在压力下发生且 session 继续健康"。trigger source 的区分留给 `tests/host/` 下的单元测试
- **修复风险（低/中/高）**: 低——减少 suite 数量
- **严重程度（中）**: 增加维护成本，不增加验收价值

### 03-未修复-中-utils 脚本是否应读 EventLog 的边界未收敛

- **位置**: "现有 utils 脚本边界是否应保持不读 EventLog"的 open question
- **问题类型**: 架构边界 / open question 未收敛
- **当前写法**: 方案提出但未回答此问题
- **反例/失败场景**:
  - 如果保持不读 EventLog → Findings 01 和 02 成立，compact suite 不可实施
  - 如果读 EventLog → utils 脚本从"black-box public API smoke"变成"gray-box integration test"，与现有 `tests/host/test_public_compact_smoke.py` 职责重叠
- **为什么有问题**:
  - 现有 utils 脚本的 docstring 明确声明"脚本不读取 durable store、EventLog、memory 表、compact payload 内容或 private Host implementation"（`utils/smoke_host_public_conversation_memory_scenarios.py:9-11`）
  - `tests/host/test_public_compact_smoke.py` 已经覆盖了 compact 的 EventLog 验证（CONTEXT_COMPACTED event、artifact kind、candidate_id、forbidden terms）
  - 如果 utils 脚本也读 EventLog，两套测试做同一件事，违反数据处理职责分离
- **直接证据**:
  - `utils/smoke_host_public_conversation_memory_scenarios.py:9-11` docstring 约束
  - `tests/host/test_public_compact_smoke.py` 已有完整 compact EventLog 验证覆盖
  - `dayu/README.md` 或 `AGENTS.md` 中 utils/ 定位为"分析辅助代码"
- **影响**: 若不收敛此问题，实施 Agent 要么无法写 compact 验收断言，要么写出来的断言与 tests/ 重叠
- **建议改法和验证点**: 显式决策——utils 脚本保持不读 EventLog，compact 验收信号的验证保留在 `tests/host/`。方案应明确声明 memory-compact-* suite 的验收边界是"compact 发生且 session 继续健康"，不声称验证 trigger source / fallback_action
- **修复风险（低/中/高）**: 低——只需在方案中明确边界
- **严重程度（中）**: 不收敛会导致实施方向漂移

### 04-未修复-低-HostEvent.activity 可用于 compact 软观测但方案未提及

- **位置**: 验收信号来源设计
- **问题类型**: 非最优方案
- **当前写法**: 方案未提及 HostEvent.activity 这一 public API 层的 compact 信号
- **反例/失败场景**: 方案可能走向"读 EventLog"或"只看 session 存活"两个极端，而忽略中间路径
- **为什么有问题**:
  - `dayu/host/api.py:3031` HostEvent 有 `activity: HostActivityView | None`
  - `dayu/host/read_api.py:1285-1313` `_compact_activity()` 将 EventLog compact event 映射为 `HostActivityView(kind=CONTEXT_COMPACTION, status=COMPLETED/FAILED/STARTED, title=..., severity=...)`
  - smoke script 的 watcher 已经在消费 HostEvent 流，只需增加对非 terminal event 的 activity 观测
  - 这条路径不需要读 EventLog，只使用 public Host API
- **直接证据**:
  - `dayu/host/api.py:3031` HostEvent.activity 字段
  - `dayu/host/read_api.py:1285-1313` compact activity 映射
  - `utils/smoke_host_public_conversation_memory_scenarios.py:2295-2311` 当前只消费 terminal event
- **影响**: 方案错过了一个不突破 utils 边界也能增加 compact 可观测性的路径
- **建议改法和验证点**: 在 smoke script 中增加对 watcher 流的 activity 观测，打印 `SMOKE COMPACT_ACTIVITY status=... title=...`，作为 soft observation 而非 hard assertion。这为 compact suite 提供"compact 确实发生了"的 public API 层证据，但不声称验证 trigger source / fallback
- **修复风险（低/中/高）**: 低——对现有脚本的增量修改
- **严重程度（低）**: 不阻塞方案，但提升验收质量

## Open Questions

1. **memory-core suite 是否需要修改？**: 方案说"memory-core 验公开多轮记忆且 pressure off"，但当前 `--suite=core --pressure-mode=off` 已经能做到。方案是否意味着 core suite 的 prompt sequence 需要调整？
2. **`--suite=all` 的组合策略**: 方案说"all 组合但独立输出验收信号"。独立输出是指每个 sub-suite 有独立的 `SMOKE PASS/FAIL` 行，还是在一个 run 内按 section 输出？前者需要多次 open_host，后者改变 stdout 格式。
3. **compact suite 的 long_rounds 参数**: 当前 long suite 的 20-25 轮是为了在 context budget 内施加足够压力。compact suite 的轮数如何确定？太少可能不触发 compact，太多浪费 token。

---

## Residual Risks

1. **compact 触发的不确定性**: 即使 pressure-mode=auto，compact 是否触发取决于 Host 内部 context 估算，smoke script 无法保证。compact suite 可能在某些模型/配置下不触发 compact，导致"false pass"（compact suite 通过但 compact 根本没发生）。建议用 HostEvent.activity 软观测作为 compact 发生的证据。
2. **与 tests/host/test_public_compact_smoke.py 的职责边界**: 如果 compact suite 声称验证 compact 健康，但实际只验证 session 存活，会产生误导性的验收信号。方案应显式声明验收边界。

---

## Final Plan Review Conclusion: **fail**

方案的核心验收目标——区分 compact accepted / failed / fallback、区分 proactive / reactive trigger source——在"utils 脚本不读 EventLog"的约束下不可直接实施。方案未回答是否突破此边界，也未利用 public Host API 已有的 `HostEvent.activity` 信号。

**建议方案修订方向**:
1. 显式声明 compact suite 的验收边界是"compact 发生且 session 继续健康"，不声称验证 trigger source / fallback_action
2. 合并 proactive-compact 和 reactive-compact 为单一 compact suite
3. compact-fallback 作为独立 suite 的动机不成立——从 public API 层无法区分 compact success 和 fallback success
4. 利用 HostEvent.activity 增加 compact 发生的 soft observation
5. trigger source / fallback_action / accepted_candidate 的验证保留在 `tests/host/test_public_compact_smoke.py`
