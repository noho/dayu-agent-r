## 2. Findings

### F1-未修复-高-preparation 直接返回 skipped 绕过最终 fresh arbitration（early skip 未仲裁）
- **位置**: plan §7.1.2、§7.3；SEC `sec_upload_workflow.py:231-232`；CN `cn_pipeline.py:862-863`；`docling_upload_service.py:388-410`
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**: §7.1.2：“preparation若已返回sequential `UploadOperationResult`（skip/cancel），沿现有路径终结，不开启batch。”§7.3 只对“prepared mutation 进入 batch”的路径定义 canonical skip 必要且充分条件。
- **反例/失败场景**: 请求 C 为 exact `auto`，pre-prepare 时目标 `COMPLETE` 且 fingerprint 与 C 的文件相同 → validator 解析为 update → `prepare_upload` 在 `_can_skip_upload(previous_meta, ...)`（`docling_upload_service.py:388-410`）基于 **pre-prepare 时捕获的 stale `previous_meta`**（SEC `:185`/`:216-217`；CN `:816`/`:847-848` 传入）返回 `status="skipped"`，workflow 直接发 completed terminal。窗口内（pre-prepare fresh read → 本地文件 hashing/指纹计算）另一请求对同一 document 执行 delete / update / repair 后，C 仍回报 `skip_reason="already_uploaded"` —— 用户可见的 false success：宣称“你的文件已发布”，而当前 published source 已是别的版本或已不存在。这正是本 work unit 要消灭的 stale-observation 决策类 bug，只是发生在另一个 checkpoint。
- **为什么有问题**: 与 work unit 自身成功信号 2 冲突（“loser skip 前 fresh target 必须为 COMPLETE；identity exact 相等；fresh company decision 必须为 keep”）——early-skip 不做 fresh read、不做 identity equality、不做 company keep 检查。§13.1 声称“skip条件……均已在本plan冻结”，但 plan 实际并存两套不相容的 skip 条件且未解释豁免理由。窗口非零：`_build_original_assets` 对全部用户文件计算 sha256 后才到达 skip 判定，大文件下可达秒级。
- **直接证据**: `docling_upload_service.py:1264-1296` `_can_skip_upload` 只消费 stale `previous_meta`；`sec_upload_workflow.py:231-232`/`cn_pipeline.py:862-863` 短路终结不开启 batch；plan §7.1.2 明确保留该路径；plan §3.2 成功信号 2 的 fresh 条件无法覆盖该路径。
- **影响**: 用户可见 false success；与 work unit 宣称的“skip 必须以 fresh authoritative view 裁决”目标自相矛盾；后续 review 无法验收“所有 skip 均经仲裁”。
- **建议改法和验证点**: 二选一并由 controller 裁决：(a) 推荐——`_can_skip_upload` 命中时不再返回终态 `UploadOperationResult`，而返回“candidate skip”携带 prepared identity，workflow 照常 `begin_batch` → batch fresh read → 复用同一仲裁（fresh COMPLETE + identity exact + company keep → canonical skip；否则 CONFLICT/PUBLISH 按规则）；新增测试：pre-prepare 时 COMPLETE-F1，准备期间另一请求 delete/update 目标，candidate skip 必须转为 conflict 或 publish，绝不报告 already_uploaded。(b) 或显式把该路径登记为 residual risk 并写明窗口大小与 owner 的豁免论证（当前 plan 两者皆无）。
- **修复风险（低）**: (a) 为 identical 重传多开一次短 batch，成本低且与 §7.4 线性化模型一致。
- **严重程度（高）**

### F2-未修复-中-batch-time validator usage/prevalidation failure 的映射与 explicit create 失败 terminal 真源未冻结
- **位置**: plan §7.1.4-7.1.5、§7.1.9-7.1.10、§6.4；S2 test 3
- **问题类型**: 契约缺失 / open question 未收敛
- **当前写法**: §7.1.5：“任何 fresh read/validator operational、corruption或usage结果在此batch-time边界转为现有typed failure或新增`SOURCE_PUBLICATION_CONFLICT`”——“或”字把映射决策留给实现者；而 §13.1 声明“failure code……均已在本plan冻结；实现者不得重新发明”。
- **反例/失败场景**: 显式 `create` loser 在 batch fresh validator 抛出 `FinsUploadUsageError(CREATE_TARGET_EXISTS)`（`ingestion_runtime.py:1500-1503`）。若 owner 不转换，该异常进入 workflow `except Exception` 通用 handler（`sec_upload_workflow.py:305-313`、`cn_pipeline.py:936-944`）→ `UNEXPECTED_RUNTIME`，违反成功信号 4/5 与 S2 test 3（要求 exact `SOURCE_PUBLICATION_CONFLICT` 且 `requested=create` 保持）。同理未冻结：batch-time `UNSAFE`（`FinsUploadPrevalidationError`）映射到既有 `source_integrity_unsafe` 还是 conflict；`COMPANY_NAME_REQUIRED`（fresh company decision 因并发 alias 增长从 keep 变 stage 且无 company_name，`ingestion_runtime.py:1513-1514`）映射到哪里；operational I/O 映射 `storage_io` 还是 conflict。
- **为什么有问题**: owner 问题本身可以成立——`FinsUploadUsageError` 属于 ingestion_runtime usage owner（当前仅 CLI 捕获，`dayu/cli/commands/fins.py:197`），新的 conflict code 属于 upload_failure storage owner，只要转换发生在 publication owner 边界、reason 由 upload_failure owner 构造，即不违反现有 usage/action failure owner。但 plan 必须 pin 转换表，因为“该请求已通过 pre-prepare validation，batch-time 出现的 usage 错误全部由并发 publication 造成”这一语义区分是仲裁正确性的核心；此外 conflict 路径 validator 抛错时不存在“batch fresh authoritative request”，§7.1.10 的“outcome携带batch fresh authoritative request”对 failed terminal 不可用，plan 未指定 failed terminal 的 `resolved_action/filing_action` 取哪一侧（当前 failure builder 只用 initial authoritative request，会投影 stale resolved_action，如 auto 初始 create 而 fresh 已是 update）。
- **直接证据**: `ingestion_runtime.py:1468-1504` usage raise 点；`upload_failure.py:181-189` STORAGE 分组需新增 code；`sec_upload_workflow.py:341-392` failure builder 只接受单个 validated request；plan §7.1.5 的“或”与 S2 test 3 的单一断言不一致。
- **影响**: 实现 Agent 在 plan 明令“不得重新发明”的面上自行拍板；显式 create loser 可能投影为 `UNEXPECTED_RUNTIME` 或 usage 而非 typed conflict；terminal action 真源不一致导致 review 不可验收。
- **建议改法和验证点**: 在 §6.4/§7.1 增加封闭映射表：batch-time 全部 validator usage 错误（请求已过 pre-prepare）→ `SOURCE_PUBLICATION_CONFLICT`；`UNSAFE` → 既有 `source_integrity_unsafe`（或明确 conflict，二选一）；operational/corruption → 既有 prevalidation `storage_io`。并 pin failed terminal：`requested_action` 来自 raw request，`resolved_action/filing_action` 取 batch fresh validated request（存在时），conflict 无 fresh request 时取 initial 并明确写进 §7.1.10。测试断言三种 mapping 各一条。
- **修复风险（低）**
- **严重程度（中）**

### F6-未修复-低-新仲裁路径缺少跨进程 winner/loser 竞争覆盖
- **位置**: plan §10.1 exact tests 8、§10.2 exact tests 1-8
- **问题类型**: 测试缺口
- **当前写法**: 全部新并发测试为 `ThreadPoolExecutor`/`Event`/`Barrier`（禁止 sleep，符合 `tests/README.md:431` 约定）；跨进程覆盖只在既有 `test_fins_storage_atomicity.py` 的 lock invariants 中。
- **反例/失败场景**: per-ticker writer 是跨进程锁（`_fs_storage_infra.py:1743-1761`），同 ticker 两个进程的 winner/loser 仲裁路径从未被真实跑过；实现若在文件锁外意外引入进程内假设，同进程测试无法发现。
- **为什么有问题**: 该 work unit 的核心主张是“全序由跨进程 writer 确定”；只测线程不测进程，覆盖主张与证据差一档。风险较低（仲裁逻辑本身进程无关，且既有跨进程锁测试存在——`test_fins_storage_atomicity.py:3480/3709/8131` 已有 spawn multiprocessing 基础设施可复用）。
- **直接证据**: plan S1/S2 测试清单全为线程级；storage 测试已有 multiprocessing 基建。
- **影响**: 跨进程回归窗口敞开。
- **建议改法和验证点**: 复用现有 spawn 基建，在 `test_fins_storage_atomicity.py` 增加一条跨进程同 ticker 双请求（exact auto）winner/skip 测试；若成本不可接受，则作为 open question 显式记录豁免理由。
- **修复风险（低）**
- **严重程度（低）**

### F7-未修复-低-SKIP 路径未指定 cancellation 观察点
- **位置**: plan §7.1.8、§6.5（`execute_prepared_filing_publication` 带 `cancellation` 参数但 §7 未定义其观察点）
- **问题类型**: 状态机漏洞
- **当前写法**: SKIP 分支直接 rollback 并构造 skip result，无取消检查；`begin_batch` 的 writer 等待是 unbounded blocking（`:453` blocking=True）。
- **反例/失败场景**: 请求在 `begin_batch` 阻塞等待期间被取消；赢得 writer 后仲裁为 skip，terminal 返回 completed `skipped`。现有 prepare 路径在 skip 判定前观察取消（`docling_upload_service.py:376-377`），commit 路径在 publish 内观察取消——SKIP 分支缺失该 checkpoint，产生“已取消请求返回成功终态”的语义漂移。
- **为什么有问题**: 与 Engine cancellation commit boundary（`docs/engine/design.md:477-489`）及现有 checkpoint 纪律不一致；取消是 run 的 terminal reason。
- **直接证据**: plan §7.1.8 无取消检查；`docling_upload_service.py:354/376/424` 现有三处取消 checkpoint 模式。
- **影响**: 取消语义漏损；测试无法断言“cancel 后不 completed”。
- **建议改法和验证点**: §7.1.8 增加：仲裁为 SKIP 前观察 `cancellation`，已取消则返回 cancelled result + rollback（与 commit 路径一致）；S1 补一条 cancel-during-batch 测试。
- **修复风险（低）**
- **严重程度（低）**

## 5. 结论

**pass-with-risks**
