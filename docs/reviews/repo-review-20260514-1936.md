## Findings

### 1-未修复-严重-`_classify_sqlite_error` 丢失约束上下文，破坏 EventLog 幂等契约

- **入口/函数**: `event_log.append_event` -> `_classify_sqlite_error`
- **文件(行号)**: `transaction.py`(341-355), `event_log.py`(230-236)
- **输入场景**: 两个并发进程同时对同一个 `event_id` 追加相同事件体。第一个 INSERT 成功；第二个在 `read_event_by_id` 返回 `None`（因第一个尚未 COMMIT），执行 INSERT 时触发 `event_id` UNIQUE 约束。
- **实际分支**: `run_write` 的 `except sqlite3.Error` 分支捕获异常，调用 `_classify_sqlite_error`，将所有 `SQLITE_CONSTRAINT_UNIQUE` 统一归类为 `HostUniqueConstraintError("Host durable unique constraint failed")`。
- **预期行为**: `append_event` 的公共契约是：同体 event_id 返回 `inserted=False`，异体 event_id 返回 `HostEventIdentityConflictError`。
- **实际行为**: UNIQUE 冲突走 `_classify_sqlite_error` 路径而非 `append_event` 内部的 `if existing` 分支，调用方只能收到通用 `HostUniqueConstraintError`，无法区分"同体重复"和"异体冲突"。
- **直接证据**: `event_log.py:230-236` 的 check-then-act 路径与 `transaction.py:349-350` 的统一分类路径不相交。并发写入时 `read_event_by_id` 看不到未 COMMIT 的 row，INSERT 触发 UNIQUE 冲突后被统一分类。
- **影响**: 并发写入场景下 EventLog 幂等保证失效。调用方无法正确处理重复事件，可能导致事件丢失或状态不一致。
- **建议改法和验证点**: 让 `_classify_sqlite_error` 接受可选的 `table_name` 上下文，或在 `run_write` 中允许 operation 捕获 `sqlite3.IntegrityError` 后自行处理。验证：多进程并发写入同 `event_id` 时返回 `inserted=False` 而非 `HostUniqueConstraintError`。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 严重

### 2-未修复-高-`run_write` COMMIT 失败后重试整个 operation 无幂等保证

- **入口/函数**: `HostTransactionRunner.run_write`
- **文件(行号)**: `transaction.py`(234-264)
- **输入场景**: `operation()` 成功返回，但 `COMMIT` 失败抛出 `SQLITE_BUSY`（如 WAL checkpoint 阻塞）。
- **实际分支**: `_is_busy_or_locked` 判断后 `continue` 重试。
- **预期行为**: 对于非幂等 operation，重试应有明确保证。通用基础设施应约束调用方提供幂等 operation，或文档声明该约束。
- **实际行为**: `BEGIN IMMEDIATE` -> `operation()` -> `COMMIT` 在同一 try 块。COMMIT 失败后 operation 的副作用已施加到 SQLite 内部事务中（未持久化），重试时 operation 被再次调用。无文档约束调用方必须提供幂等 operation。
- **直接证据**: 行 237-239 顺序执行 `BEGIN IMMEDIATE` / `operation()` / `COMMIT`；行 243-255 `_is_busy_or_locked` 判断后 `continue`。
- **影响**: 上层使用非幂等 operation 时，COMMIT 失败重试会导致重复执行。与 Finding 1 叠加时，EventLog 的幂等保护失效后重试 INSERT 直接抛出 `HostUniqueConstraintError`。
- **建议改法和验证点**: 在 `run_write` docstring 中明确声明 operation 必须幂等；或让 `run_write` 在 COMMIT 失败时不重试 operation 本身，而是重试整个 BEGIN-COMMIT 块（需要 operation 支持 reset/retry）。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 4-未修复-严重-`await_or_cancel` 对自定义 `__await__` 对象 fast-path 未做 cleanup

- **入口/函数**: `await_or_cancel`, `await_or_cancel_or_timeout`
- **文件(行号)**: `runtime/cancellation.py`(115-121, 236-242)
- **输入场景**: token 已被取消时，调用方传入一个既非 coroutine 也非 Future/Task，但实现了 `__await__` 的自定义 awaitable 对象。
- **实际分支**: `asyncio.iscoroutine` 返回 False，`asyncio.ensure_future` 将其包装为 Task 并立即 cancel。
- **预期行为**: 所有 awaitable 类型在 fast-path 都应被正确 cleanup。对于非 coroutine、非 Future 的 awaitable，应尝试调用 `close()`。
- **实际行为**: 原始 awaitable 对象本身没有被 close/cleanup。`ensure_future` 包装后 cancel 只取消了 wrapper Task，不触发原始对象的 cleanup。如果该对象持有资源（如文件句柄、网络连接），资源会泄漏。
- **直接证据**: `asyncio.iscoroutine` 仅对原生协程返回 True。PEP 492 coroutine-like objects 不会被命中。
- **影响**: 当前 Dayu 调用路径传入的都是 coroutine 或 Task，大概率不触发。但作为公共 runtime helper，第三方或未来调用方可能传入自定义 awaitable。
- **建议改法和验证点**: 在 fast-path 中对非 coroutine 的 awaitable 尝试调用 `close()`（`hasattr(awaitable, 'close')`），或通过类型约束要求传入必须是 coroutine 或 Task。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 严重（公共 runtime contract 缺陷，但当前调用路径不触发）

### 5-未修复-中-`bootstrap_host_durable_store` DDL 执行不在事务内

- **入口/函数**: `bootstrap_host_durable_store`
- **文件(行号)**: `schema.py`(448-451), `connection.py`(194)
- **输入场景**: DDL 执行中途失败（如磁盘满）。

- **影响**: 磁盘满或权限异常时 schema 可能处于半初始化状态。
- **建议改法和验证点**: 在 DDL 循环前后包裹 `BEGIN` / `COMMIT`，或使用 `connection.executescript()` 一次性执行。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
