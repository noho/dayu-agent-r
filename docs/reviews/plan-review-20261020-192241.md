## 3. BP1–3 计划层逐项判断

### 3.1 BP1：commit 收录 / 字节一致 / 额外未跟踪安装输入

**计划层结论：核心契约已修复（可关闭 tracked-only 漏检），但 §7 的具体未跟踪命令在真实仓库存在确定性假阳性，需在真实 sync 前补一项具名 allowlist/exclude。**

直接证据：

- §7 同时要求 `git ls-files --error-unmatch`、对核收 OID 的 `git diff --exit-code`、以及限定输入路径的 `git ls-files --others`，并明确“不能把‘仅 index 收录’当作‘已在 commit’”。
- 我在 `$TMPDIR` 独立 git 仓库复现：
  - `git add` 一个新 `scripts/install-source.sh` 后，`git ls-files --error-unmatch` 返回 0（仅 index 收录），但 `git diff --exit-code <OID> -- …` 返回 1，联合检查可拒绝；
  - 忽略的 `dayu/ignored.py` 在不用 `--exclude-standard` 时被 `git ls-files --others` 列出；
  - commit 中被删除的 tracked 文件由 diff 返回 1；
  - 已存在的 `.DS_Store` 问题见 Finding 1。
- 作者 `bp1-raw-byte-equality.json` 的五个 blob 与真实仓库 `git rev-parse HEAD:<文件>` 逐项一致（`pyproject.toml` `d3016d26…`、`README.md` `5f324da1…`、`LICENSE` `261eeb9e…`、`dayu/__init__.py` `ac720a1f…`、`constraints/lock-common-py311.txt` `ef89d339…`）。

### 3.3 BP3：有效 ZDOTDIR 的真实启动后检查

**计划层结论：已修复。**

直接证据：

- §4.1 第 1 项把 zsh 的 ZDOTDIR 核验列为预检，并要求“上述预检在创建/复用安装环境及任何入口/profile 写入之前完成”。
- §4.3 明确检测点：保留用户真实启动配置及继承的 ZDOTDIR，按源外 cwd/去 venv 环境的 `zsh -ic`、`zsh -lic` 启动，查询启动完成后的 `${ZDOTDIR:-$HOME}`（含 `.zshenv` 设置），并在 shell 内用 `[[ "${ZDOTDIR:-$HOME}" -ef "$HOME" ]]` 断言；查询/断言非零即失败；只接受与 HOME 同一目录，不接受 HOME 子目录；不另找 profile、不用 `ZDOTDIR=$HOME` 或 `-f`。
- 作者六次探针：标准 HOME 的 `-ic`/`-lic` 均 exit 0；继承非 HOME ZDOTDIR 与 `.zshenv` 重定向场景均实际读取 alternate `.zshrc` 后 exit 1；两种反例的合成配置前后 SHA 一致（没有安装脚本写入）。stdout 直接显示 `effective_zdotdir=…/alternate`、`home_rc=`、`alternate_rc=yes`。

- §6.1 测试 3 要求覆盖继承非 HOME ZDOTDIR 和 `.zshenv` 设置另一目录（含另一份 `.zshrc` 恰好提供正确 PATH 的反例），在任何安装/发布写入前失败，入口与配置原字节不变；标准 HOME 通过、发布后两种正常模式也断言有效值。这与 §4.3/§7 的计划层契约一致，且没有引入通用 profile 探测框架。

## 4. Findings

### 1-未修复-[中]-§7 BP1 的未跟踪检查在真实仓库被既有 ignored `.DS_Store` 假阳性阻断

- **位置**: v2 §7 BP1，未跟踪检查命令与判定（`public-original-read-r1-r3-20261020-install-entry-bash-plan-v2.md` 第 194–198 行命令，第 201 行“未跟踪检查限定安装输入路径…只排除具名的非输入缓存目录”）。
- **问题类型**: 验收证据不可执行 / 过度拒绝非输入文件（计划层命令与真实仓库状态不一致）。
- **当前写法**: `git ls-files --others --exclude=__pycache__/ --exclude=.pytest_cache/ --exclude=.mypy_cache/ --exclude=.ruff_cache/ -- "${entry_install_paths[@]}"` 必须为空，否则 `exit 1`；prose 只允许排除具名非输入缓存目录，并强调不能用 `--exclude-standard` 放过 ignored 源码。
- **反例/失败场景**: 在真实仓库 `/Users/leo/workspace/dayu-agent-r` 原样执行该命令（`entry_install_paths` 含 `dayu`），输出为：
  ```
  dayu/.DS_Store
  dayu/config/.DS_Store
  ```
  `entry_untracked_inputs` 非空，`[[ -z "$entry_untracked_inputs" ]] || exit 1` 必然失败。该失败发生在真实安装之前，正式 sync 被阻断；执行者若按计划“不扩大成整工作树强制 clean”，又没有 `.DS_Store` 的具名排除项，就会把两个 macOS 元数据文件误当未核收输入，或被迫计划外删除用户文件。
- **为什么有问题**: `git ls-files --others` 在未给 `--exclude-standard` 时会把 `.gitignore` 忽略的文件也列出（这是 BP1 想保留的能力），但 `.DS_Store` 是 `.gitignore:1` 的既有 ignored 元数据，不是安装源码/脚本/包资源。计划 prose 的目标是拒绝“相关路径内其它未跟踪源码/脚本/包资源”，而当前命令无法区分 `.DS_Store` 与此类输入。直接证据表明这不是假设性边缘：两个文件分别创建于 2026-05-05 和 2026-05-13，长期存在于真实仓库；`pyproject.toml` 的 `dayu.config`/`dayu.assets` package-data 模式（`*.json`、`prompts/**/*.md`、`*.md` 等）也不包含 `.DS_Store`，因此把它排除不会削弱安装输入检查。
- **直接证据**:
  - `git check-ignore -v dayu/.DS_Store dayu/config/.DS_Store` → `.gitignore:1:.DS_Store`（两者均 ignored）。
  - `git ls-files --error-unmatch -- dayu/.DS_Store` → exit 1（untracked）。
  - 原样执行计划命令 → 输出上述两个路径，`guard_exit=0`（命令本身成功，但输出非空，按计划下一步 exit 1）。
  - 在同一命令加 `--exclude=.DS_Store` → 输出为空，`guard2_exit=0`。
  - 作者证据 `bp1-cache-and-unrelated-allowed` 只覆盖 `dayu/__pycache__` 与路径外 `workspace/tmp/evidence.txt`，未覆盖真实仓库的 ignored `.DS_Store`。
- **影响**: 按原文执行 §7 BP1 会稳定 false-fail（不是 false-pass），因此 source binding 的完整性没有被破坏，但正式 sync 无法开始，或执行者会做计划外清理；这会把一个非输入元数据问题误报为“未核收安装输入”，增加主控裁决和返工成本。BP1 的核心目标（关闭 tracked-only 漏检）本身已经达成。
- **建议改法和验证点**: 在 §7 的具名排除项中加入 `.DS_Store`（以及经确认的同类 OS 元数据，如 `._*`；不要改用 `--exclude-standard`），或在 prose 中明确“仅对源码/脚本/包资源扩展名和必需文件路径做未跟踪检查”，并给出真实仓库的验证：原样命令输出为空；再注入未跟踪 `dayu/unapproved.py` 与 `scripts/install-source.sh`，确认仍被拒绝；保留 ignored 源码反例（`.gitignore` 中的 `dayu/ignored_source.py`）必须仍被列出。若主控选择在 sync 前显式删除 `.DS_Store`，也应在计划/回执中写明该动作与范围，不能静默做。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。
- **状态**: accepted-candidate；不重新打开 tracked-only 漏检，也不阻塞 IE-B1 实现；但按当前命令不能直接执行 §7，需在真实 sync 前做这一项窄修。主控如要求 §7 命令原样可执行，则应要求计划层补 exclude/allowlist 后再放行 sync。

## 8. 结论

**pass-with-risks**

BP1–3 的计划层修订均针对已裁决的直接反例，且证据链可追溯：

- **BP1：计划层核心已修复**。commit 收录（`ls-files --error-unmatch` 与 OID diff 联合）、工作树字节一致（raw-blob 要求）和限定输入路径的未跟踪检查能够关闭 tracked-only 漏检；独立 git 探针确认 staged-new、ignored 源码和删除的 tracked 文件都会被拒绝。**但 §7 的具体未跟踪命令在真实仓库被既有 ignored `dayu/.DS_Store`、`dayu/config/.DS_Store` 假阳性阻断（Finding 1，中）**；按当前命令不能直接执行真实 sync，需补具名 exclude/allowlist 或显式删除动作后再执行。该问题不重新打开 tracked-only 漏检，不阻塞 IE-B1 实现。
- **BP2：已修复**。`-E -P` 保留该解释器正常启用的 user-site，排除 cwd/PYTHONPATH，源码 venv 的 `-I` 检查保留，README 不再用裸 PATH `dayu-cli --help` 证明 wheel 安装；未强制新增 wheel venv。
- **BP3：已修复**。有效 ZDOTDIR 按真实启动后值查询，非 HOME 在变更前失败，发布后与正式验收复用同一断言，且不强制重设 ZDOTDIR 或 `-f` 绕开用户配置；作者六次探针与测试要求一致。

Q1（目的地父目录 symlink 明确拒绝）与 Q2（隔离配置与缓存复用记录）已按裁决澄清；两者实现细节交 IE-B1/完整代码审核，本报告不因未实现本身判计划失败。
