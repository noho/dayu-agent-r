### Deferred to Recovery-Tier Audit Diagnostics

以下 7 条 findings 均基于 `dayu/host/dispatch.py` recovery tier 代码的直接证据，已在 prior aggregate deepreview 中完整记录。它们属于 recovery tier 审计语义范畴，与当前 diagnostic artifact slice 无耦合阻塞：

#### 1-未修复-高-Recovery tier rejected attempts 不写入 EventLog，审计链断裂

- **入口/函数**: `HostDispatchScheduler._execute_proactive_compaction()` → `_operation()` transaction
- **文件(行号)**: `dayu/host/dispatch.py:1343-1407`
- **输入场景**: proactive compaction 初始 operation 全部 rejected，进入 recovery tier；recovery tier 也全部/部分 rejected
- **实际分支**: `for rejected in result.rejected_attempts:` (行 1401) 只遍历初始 operation 的 rejected attempts；recovery tier 的 `tier_result.rejected_attempts` 未收集、未写入 EventLog
- **预期行为**: 所有 proposal attempt 的 rejected 事件（含 recovery tier）均应写入 EventLog，否则 recovery tier 的 `CompactionRejectedAttemptDiagnostic` artifact ref 从 durable 审计链中消失
- **实际行为**: recovery tier rejected attempts 被丢弃
- **直接证据**: 行 1343-1376 recovery loop 只保存 `accepted_result` 和 `accepted_request`；行 1401 只读初始 `result`；行 1416/1433 `attempt_count=len(result.rejected_attempts)` 只计初始 result
- **影响**: recovery tier 1-3 全部失败时，EventLog 中只有初始 operation 的 rejected attempts，丢失 3 个 recovery tier 诊断信息
- **建议改法和验证点**: 合并所有 recovery tier rejected attempts 到统一列表，transaction 内遍历全部写入 EventLog；`attempt_count` 使用合并后总数
- **修复风险（中）**: 需调整 recovery loop 与 transaction 间数据传递结构
- **严重程度（高）**: 审计完整性缺陷
