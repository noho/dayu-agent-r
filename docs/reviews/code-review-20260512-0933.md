### 1-未修复-中-agent.py `_handle_final_decision` 调用方存在不可达死代码

- **入口/函数**: `_AsyncAgent.run_messages()` → `_handle_final_decision` 返回值消费
- **文件(行号)**: `dayu/engine/agent.py:623`
- **输入场景**: `_classify_iteration` 返回 `_FinalDecision`，`continuation_active=False`，`decision.finish_reason != LENGTH`，且无累积的 `continuation_content_parts`
- **实际分支**: `_handle_final_decision` 返回 `decision`（即传入的 `_FinalDecision`），类型注解为 `_FinalDecision | None`。调用方先检查 `isinstance(continuation_decision, _FinalDecision)`（line 591），再检查 `continuation_decision is None`（line 608）。两个检查覆盖了 `_FinalDecision | None` 的全部可能值。
- **预期行为**: 不可达分支应被消除或以 `assert_never` 守卫。
- **实际行为**: line 623 `yield await self._make_final_after_close(decision)` 是不可达死代码。若未来 `_handle_final_decision` 返回类型扩展（如增加第三种返回值），该分支将在没有编译期保护的情况下被意外激活，且此时 `_make_final_after_close(decision)` 不检查取消状态（与 `_make_final_or_cancelled_after_close` 已删除的取消检查的区别），可能产生错误终态。
- **直接证据**: `_handle_final_decision` 返回类型为 `_FinalDecision | None`（line 732），调用方已完整覆盖两个分支（line 591, 608），line 623 落在两个 if 之后无法到达。
- **影响**: 当前行为正确（死代码不执行），但增加维护风险。未来修改 `_handle_final_decision` 返回值时缺少编译期保护。
- **建议改法和验证点**: 在 line 608 `continue` 之后、line 623 之前插入 `assert_never(continuation_decision)` 或删除不可达代码块。验证：类型检查通过、现有测试通过。
- **修复风险（低）**: 纯代码清理，不影响运行时行为。
- **严重程度（中）**: 死代码本身无 bug，但缺少 `assert_never` 守卫使未来变更缺少类型安全网。

### 2-未修复-中-runner.py `_is_sse_response` fallback 逻辑过于激进

- **入口/函数**: `AsyncOpenAIRunner._do_attempt()` → `_is_sse_response()`
- **文件(行号)**: `dayu/engine/runners/openai/runner.py:113-126`
- **输入场景**: provider 对 `stream=True` 请求返回 HTTP 200，但 `Content-Type` 不含 `text/event-stream` 也不含 `json`（例如 `text/html` 错误页、`text/plain` 或未知类型）
- **实际分支**: `_is_sse_response` 在 `stream=True` 且 `Content-Type` 不含 `text/event-stream` 时进入 `_JSON_CONTENT_TYPE_FRAGMENT not in content_type` 分支（line 126），结果为 `True`，走 SSE parser。
- **预期行为**: 非 JSON、非 SSE 的 200 响应应当作为非流式响应处理（读取完整 body 后尝试 JSON 解析），由协议错误路径产生明确错误事件。
- **实际行为**: SSE parser 会尝试按 SSE 行协议解析 HTML/纯文本 body，产出 `sse_invalid_json` 协议错误事件。虽然终态仍为 `RunnerDone(ERROR)`，但错误分类粒度丢失（本应是 `non_stream_invalid_json` 或更准确的协议错误码），且 SSE parser 的 `partial_tool_calls` 等上下文信息不适用于此类错误。
- **直接证据**: `_is_sse_response` line 126 的 fallback 条件 `_JSON_CONTENT_TYPE_FRAGMENT not in content_type` 会将所有不含 `json` 字符串的 Content-Type 归类为 SSE。而运行环境中 `response.status != 200` 的检查（line 450）先于 `_is_sse_response` 调用（line 492），意味着 200 + 非标准 Content-Type 会落入此 fallback。
- **影响**: 错误分类粒度降低，provider 异常返回的诊断信息被 SSE parser 框架非正确地解释。若 provider 返回 200 + `text/html`（某些反向代理行为），错误事件会标记为 `sse_invalid_json` 而非更准确的描述。
- **建议改法和验证点**: 方案 A：在 `_is_sse_response` 中增加白名单/更精确的 fallback 条件（例如只对空 Content-Type 或不含已知非流式标记做 SSE fallback）。方案 B：在 `_do_attempt` 中先读取少量 body 做 content-type sniffing。推荐方案 A（改动最小）：在 `stream=True` 时只有 Content-Type 为空或不含常见非流式标记（如 `html`、`xml`、`plain` 且不含 `event-stream`）时才走 SSE。验证点：新增 `_is_sse_response` 单元测试覆盖 `text/html`、`text/plain`、空 Content-Type 场景。
- **修复风险（低）**: 新增 Content-Type 判断条件，仅影响流式请求的解析路径选择。
- **严重程度（中）**: 不导致数据丢失或错误终态，但错误分类精度下降会直接影响运维诊断和告警质量。

### 3-未修复-低-agent.py 工具执行超时与 ToolExecutionContext.timeout_seconds 形成双重超时

- **入口/函数**: `_AsyncAgent._execute_one_tool()` / `_AsyncAgent._execute_tool_batch()`
- **文件(行号)**: `dayu/engine/agent.py:1405-1408` (context timeout), `1528-1533` (Engine timeout)
- **输入场景**: `agent_policy.tool_execution_timeout_seconds` 为同一值，同时注入 `ToolExecutionContext.timeout_seconds` 和 `await_or_cancel_or_timeout` 的 `timeout_seconds`
- **实际分支**: Engine 层面的 `await_or_cancel_or_timeout` 与 ToolExecutor 内部对 `context.timeout_seconds` 的解读可能产生竞速。
- **预期行为**: 应明确超时真源（Engine 层 vs ToolExecutor 层），避免两层同时计时的非确定性行为。
- **实际行为**: Engine 在 `await_or_cancel_or_timeout` 中通过 `target_task.cancel()` 强制取消工具执行，而 ToolExecutor 可能同时在内部基于 `context.timeout_seconds` 做超时收尾。两个超时机制同时生效可能导致 ToolExecutor 的清理逻辑被 Engine 的强制取消打断，产生不完整的工具结果或日志。
- **直接证据**: `agent.py:1405-1408` 将 `tool_execution_timeout_seconds` 写入 `ToolExecutionContext.timeout_seconds`；`agent.py:1528-1533` 将同一值传给 `await_or_cancel_or_timeout`。两层同时使用相同的超时值。
- **影响**: 工具执行在超时边界上可能出现非确定性的清理行为。当前 Engine 的 `target_task.cancel()` 会抛出 `CancelledError` 到工具协程，若工具内部也在做超时收尾，可能形成竞态。
- **建议改法和验证点**: 二选一：(a) Engine 超时作为唯一超时源，ToolExecutionContext.timeout_seconds 改为 `None` 或删除该字段；(b) ToolExecutor 内部超时作为唯一源，Engine 仅依赖 `await_or_cancel`（token cancellation），不施加额外 timeout。当前双重超时虽不会导致数据错误，但增加了非确定性。验证：明确超时归属后在测试中注入不同超时值观察行为。
- **修复风险（低）**: 需要协调 Engine 与 ToolExecutor 契约。
- **严重程度（低）**: 实际场景中 Engine 的强制取消通常先于或同步于 ToolExecutor 内部超时，不会出现实质冲突。但文档缺失使后续维护者不清楚超时真源。

### 4-未修复-低-agent.py `_call_tool_executor` CancelledError 归因依赖 `is_cancelled()` 间接信号

- **入口/函数**: `_AsyncAgent._call_tool_executor()`
- **文件(行号)**: `dayu/engine/agent.py:1550-1573`
- **输入场景**: `ToolExecutor.execute()` 内部代码显式 `raise asyncio.CancelledError()`（非 Task.cancel() 注入），且此时 `cancellation_token.is_cancelled()` 碰巧返回 `True`（因并发 token 取消）
- **实际分支**: line 1563 `if self._request.cancellation_token.is_cancelled(): raise` — 将工具内部的自发 CancelledError 误判为 run-level 取消并透传。
- **预期行为**: 工具内部的自发异常应作为工具失败记录，不应被误判为 run-level 取消。
- **实际行为**: 工具内部 raise CancelledError + token 同时被取消时，异常被透传为 run-level cancellation 而非 `ToolFailedOutcome`。
- **直接证据**: line 1562-1564: `except asyncio.CancelledError: if self._request.cancellation_token.is_cancelled(): raise`。`is_cancelled()` 是间接信号，无法区分 "CancelledError 来自 Task.cancel(token 触发)" 和 "CancelledError 来自工具内部 + token 碰巧已取消"。
- **影响**: 极低概率的误归因。实际场景中工具代码不应显式 raise CancelledError（违反 Python 惯例），且并发 token 取消+工具自发 CancelledError 同时发生几乎不可能。
- **建议改法和验证点**: 当前实现可接受。若希望更精确，可以在 `_call_tool_executor` 中将 CancelledError 的来源 task 与 token 取消 task 做身份比对，但实现复杂度显著增加，性价比不合理。建议在 docstring 中记录此归因限制。
- **修复风险（低）**: 仅文档补充。
- **严重程度（低）**: 极端边界场景，实际触发概率趋近于零。

### 5-未修复-低-committed `await_or_cancel` 对已取消 token 的 coroutine 清理路径变更

- **入口/函数**: `dayu.runtime.cancellation.await_or_cancel()`
- **文件(行号)**: `dayu/runtime/cancellation.py:110-116`
- **输入场景**: 调用 `await_or_cancel(awaitable, token=token)` 时 `token.is_cancelled()` 为 `True`，`awaitable` 为未启动的 coroutine 对象
- **实际分支**: 原实现直接返回 `WaitCancelled`（不清理 coroutine）；新实现对 coroutine 调用 `awaitable.close()` 后返回，对非 coroutine 先 `ensure_future` 再 `cancel + await`。
- **预期行为**: 已取消状态下不应留下可能被后续 `await` 的 coroutine 对象。
- **实际行为**: 新实现正确关闭 coroutine 或取消 task。这是对原实现遗留问题的修复。
- **直接证据**: 原代码 `dayu/runtime/cancellation.py` 旧版本在 `token.is_cancelled()` 时直接返回 `WaitCancelled`，不清理 awaitable。
- **影响**: 正向修复。原实现可能导致 coroutine 对象被重复 await（触发 `RuntimeError: cannot reuse already awaited coroutine`）。
- **建议改法和验证点**: 已在 `await_or_cancel_or_timeout` 中保持一致的清理模式。建议确认 `tests/runtime/test_cancellation.py` 覆盖此路径。无需额外修改。
- **修复风险**: 不适用（这是已完成的正确修复）。
- **严重程度（低）**: 正向改进，无需修复。
