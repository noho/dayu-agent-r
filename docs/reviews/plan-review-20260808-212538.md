## Findings

### F20-RR3-DS-001-未修复-高-Parent audit child allowlist看不到production multiprocessing spawn且漏建模resource tracker

- **位置**: plan §5.2 第232–269行的audit event判定、child exact allowlist/union、`proof-safety.json`；§7 Slice 1；§8 trigger-proof validation。
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口。
- **当前写法**: parent Python audit hook把child创建事件冻结为`subprocess.Popen`、`os.posix_spawn`、`os.system`，只允许run-owned bootstrap与production ToolRuntime Fins process target两类exact identity；actual child events的两个subset union必须穷尽全部children，且每个ToolRuntime child要绑定executable、argv、target module/qualname/canonical digest与tool-call identity。
- **反例/失败场景**: production Fins read tool进入`ProcessBackedToolExecutionCapability`后，`InterruptibleProcessHandle`使用`multiprocessing.get_context("spawn")`、`Queue`与`Process`。在当前项目Python 3.11.15中，对同一`spawn`路径安装parent audit hook并只记录计划列出的三个事件，启动并join一个真实`multiprocessing.Process`后，child-create audit event集合为`[]`。进一步读取同一parent的真实OS child table可见至少一个`multiprocessing.resource_tracker`与一个`multiprocessing.spawn_main`child；前者不属于计划允许的bootstrap或ToolRuntime-target两类。即使某平台产生可见exec event，spawn argv也只有`spawn_main(tracker_fd=..., pipe_handle=...)`，target对象通过pickle/pipe传入，不包含target module/qualname或canonical digest。因此实现要么看不到child而错误报告union穷尽，要么按missing/extra/unknown child规则使每次真实Fins tool proof必然FAIL。
- **为什么有问题**: RR2要求的是OS deny-network覆盖真实process tree，并由直接owner证据审计production ToolRuntime child；当前计划把网络enforcement、Python outbound audit与child target identity混在一个audit-hook allowlist中。Python audit hook可以观察/拒绝socket与DNS事件，但它不是本项目`multiprocessing.spawn`的child-creation owner，不能提供计划声称的target identity。用预期recipe或进程ordinal回填actual target又违反exact direct evidence要求。
- **直接证据**:
  1. `dayu/host/tool_runtime.py:1608-1616`只要execution是`ProcessBackedToolExecutionCapability`就构造target并创建`ProcessBackedToolExecutionCapsule`。
  2. `dayu/runtime/interruptible_process.py:289-304`明确使用`multiprocessing.get_context("spawn")`、context Queue与context Process；`dayu/runtime/interruptible_process.py:313-326`由`Process.start()`启动。
  3. provider-free runtime probe（Python 3.11.15）：`multiprocessing.get_context("spawn").Process(target=time.sleep, ...)`成功退出为0，但parent hook捕获的`subprocess.Popen|os.posix_spawn|os.system`事件为`[]`；扩大到event name含spawn/fork/process仍为`[]`。
  4. 同一probe的OS child table直接出现`multiprocessing.resource_tracker main(...)`和`multiprocessing.spawn_main(...) --multiprocessing-fork`两个child；`multiprocessing.spawn.get_command_line(...)`的argv不包含业务target identity。
- **影响**: Slice 1的mandatory zero-network/child exact gate不可按计划实现；正常production tool执行会被误判、漏审或迫使实现Agent引入被禁止的monkeypatch/`sitecustomize`/产品wrapper。因为Slice 1是formal provider前blocking gate，当前plan不能安全交给implementation。
- **建议改法和验证点**:
  1. 把Python audit hook职责收窄为parent outbound socket/DNS/UDP audit，不再把它冒充multiprocessing child-creation或target-identity owner；OS sandbox继续独立拥有process-tree deny-network enforcement。
  2. 明确选择一个真实可观察的child identity owner。若只依赖现有产品边界，应由production ToolDefinition/process-target construction、固定产品代码SHA、canonical tool-call/terminal与OS child executable/process-tree证据共同派生，并显式建模`resource_tracker`与`spawn_main`基础设施child；不得声称audit hook看到了target。如果这仍不足以满足“actual target exact identity”，登记为blocking owner question，不得实现私有hook补偿。
  3. 修订后的provider-free self-test必须启动与`InterruptibleProcessHandle`完全同路的真实Fins read process-backed tool，证明observer确实看到resource tracker与worker child、不会把它们记成bootstrap、能解释target不在argv的边界，并对missing/extra/unknown infrastructure/worker child二值FAIL。该self-test仍不得访问network或provider。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。
