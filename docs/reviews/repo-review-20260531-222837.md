### 1-未修复-中-cancel_waiting_run_in_transaction 在 wait records 已 resolve 后返回 INVALID_STATE

- **入口/函数**: `cancel_waiting_run_in_transaction`
- **文件(行号)**: `/Users/leo/workspace/dayu-agent-r/dayu/host/durable/run_transition.py` (2298-2306)
- **输入场景**: Run 处于 WAITING 状态，但其 wait records 已被外部 resolve（状态变为 RESOLVED），此时用户发起 cancel
- **实际分支**: `active_waits = read_active_wait_records_for_run(...)` 返回空列表，`not active_waits` 为 True，返回 `INVALID_STATE`
- **预期行为**: WAITING Run 应始终可被 cancel，即使 wait records 已被 resolve
- **实际行为**: 函数要求 `attempt.status == AttemptStatus.SUSPENDED and active_waits` 同时满足。如果所有 wait records 已被 resolve（但 Run 尚未 resume），cancel 会失败
- **直接证据**: run_transition.py:2299-2300: `active_waits = read_active_wait_records_for_run(transaction, run.run_id)` 后 `if attempt is None or attempt.status != AttemptStatus.SUSPENDED or not active_waits: return INVALID_STATE`；`cancel_waiting_run_row`（state.py:3237）本身只要求 `status = 'waiting'`，不要求 active wait records 存在
- **影响**: 在 wait resolve 和 resume 之间存在一个窗口期，在此窗口内 cancel 会失败。用户需要等待 resume 完成后才能 cancel，或者需要等 Run 重新进入 RUNNING 状态
- **建议改法和验证点**: 将 active_waits 检查改为非必须：如果 active_waits 为空，跳过 `cancel_active_wait_records_for_run` 调用，直接执行 Run cancel。验证点：构造 WAITING Run + 所有 wait records 已 RESOLVED 的场景，确认 cancel 成功
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
