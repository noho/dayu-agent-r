### 1-未修复-HIGH-`_accept_awaiting_with_retry` 类型标注错误导致二轮 timeout 运行时崩溃

- **入口/函数**: `ToolRuntimeExecutor._accept_awaiting_with_retry`
- **文件(行号)**: `dayu/host/tool_runtime.py` (2829, 2845, 2860)
- **输入场景**: 业务工具返回 `ToolAwaitingOutcome`，Host awaiting accept port 两轮都抛出 `HostTransactionRetryExhaustedError`
- **实际分支**: 第一轮 timeout -> `diagnostics = result.diagnostic_refs`（赋值为 `tuple[ToolTraceDiagnosticRef, ...]`）-> 第二轮 timeout -> 构造 `ToolAwaitingAcceptTimedOut(diagnostic_refs=diagnostics)`
- **预期行为**: `diagnostics` 类型与 `ToolAwaitingAcceptTimedOut.diagnostic_refs: tuple[str, ...]` 一致
- **实际行为**:
  1. 第 2829 行声明 `diagnostics: tuple[str, ...] = ()`，但第 2845 行 `diagnostics = result.diagnostic_refs` 将其赋值为 `tuple[ToolTraceDiagnosticRef, ...]`
  2. 第 2860 行 `diagnostic_refs=(*diagnostics, timeout_ref.ref_id)` 拼接 `ToolTraceDiagnosticRef` 对象与 `str`，类型不一致
  3. 构造出的 `ToolAwaitingAcceptTimedOut.diagnostic_refs` 混合了 `ToolTraceDiagnosticRef` 对象和 `str`
- **直接证据**:
  - 第 2829 行: `diagnostics: tuple[str, ...] = ()`
  - 第 2845 行: `diagnostics = result.diagnostic_refs`
  - 第 2860 行: `diagnostic_refs=(*diagnostics, timeout_ref.ref_id)`
  - `waiting.py` 第 307 行: `diagnostic_refs: tuple[str, ...] = ()`
  - `tool_runtime.py` 第 493 行: `ToolFactAcceptTimedOut.diagnostic_refs: tuple[ToolTraceDiagnosticRef, ...]`
- **影响**: 只在两轮都 timeout 时触发（`max_attempts` 默认为 2）。二轮 timeout 路径构造的 `ToolAwaitingAcceptTimedOut` 混合类型，下游消费 `diagnostic_refs` 时会遇到 `str` 与 `ToolTraceDiagnosticRef` 属性访问不兼容。如果 Python 严格类型检查或下游代码依赖 `.ref_id` 属性，会运行时崩溃。
- **建议改法**: 将 `diagnostics` 类型改为 `tuple[ToolTraceDiagnosticRef, ...]`（与 `_accept_with_retry` 一致），第 2860 行改为 `diagnostic_refs=(*diagnostics, timeout_ref)`（传入 `ToolTraceDiagnosticRef` 对象而非 `.ref_id`）。同时需要将 `ToolAwaitingAcceptTimedOut.diagnostic_refs` 类型从 `tuple[str, ...]` 升级为 `tuple[ToolTraceDiagnosticRef, ...]`，或在 `_accept_awaiting_with_retry` 中统一用 `.ref_id` 提取。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: HIGH

### 2-未修复-HIGH-`_release_token` 外层取消路径中 task 失败导致 token 状态损坏

- **入口/函数**: `LaneController._release_token`
- **文件(行号)**: `dayu/runtime/lane.py` (728-757)
- **输入场景**: 外层 task 被取消，且 `_release_claim_sync` 在线程中抛出 `RuntimeLaneError`（如 SQLite 写入失败）
- **实际分支**:
  1. `asyncio.shield(release_task)` 抛出 `CancelledError`（行 743）
  2. 进入 `except asyncio.CancelledError` 分支（行 743）
  3. `_await_task_after_outer_cancellation(release_task)` 内部：task 已 done，`task.result()` 重抛 `RuntimeLaneError`
  4. `RuntimeLaneError` **不是** `CancelledError`，不被 `except asyncio.CancelledError`（行 743）捕获
  5. `RuntimeLaneError` 直接传播给调用方
- **预期行为**: 与 `_refresh_token`（行 648-684）一致——捕获底层错误，记录日志，以 `CancelledError` 形式传播给调用方，并保持 token 状态一致
- **实际行为**:
  - `RuntimeLaneError` 直接逃逸，调用方收到非预期异常类型
  - `_mark_token_released(token)`（行 757）**未被调用**
  - token 留在 `_held_tokens` 中（`released=False`），但 DB row 可能已被删除
  - 内存与 DB 状态不一致
- **直接证据**:
  ```python
  # lane.py:728-757
  async def _release_token(self, token: LaneClaimToken) -> None:
      ...
      try:
          await asyncio.shield(release_task)       # line 742
      except asyncio.CancelledError as cancelled:   # line 743
          try:
              await _await_task_after_outer_cancellation(release_task)  # line 745
              # 若此行抛出 RuntimeLaneError，它不被 line 743 的 except 捕获
          except RuntimeLaneError:                   # line 746 — 仅捕获日志路径
              _LOGGER.exception(...)
              raise cancelled                        # line 754 — 重新抛出 CancelledError
          self._mark_token_released(token)           # line 755 — 跳过
          raise                                      # line 756 — 跳过
      self._mark_token_released(token)               # line 757 — 跳过
  ```
- **影响**: release 失败后 token 状态损坏。后续 heartbeat 可能继续刷新已不存在的 DB claim；close() 可能重复尝试释放已删除的 claim。
- **建议改法**: 在 `_release_token` 的 `CancelledError` handler 中添加 `except RuntimeLaneError` 捕获分支，与 `_refresh_token` 保持一致的异常处理模式。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: HIGH

### 6-未修复-MEDIUM-`_await_task_after_outer_cancellation` 将 task 自身的 `CancelledError` 误解释为外层取消

- **入口/函数**: `_await_task_after_outer_cancellation`
- **文件(行号)**: `dayu/runtime/lane.py` (994-1016)
- **输入场景**: shielded task 自身被取消（`task.cancel()` 被调用），task 以 `CancelledError` 完成
- **实际分支**:
  1. `asyncio.shield(task)` 抛出 `CancelledError`（可能是因为外层取消，也可能是 shield 自身传播 task 的 CancelledError）
  2. 进入 `except asyncio.CancelledError`
  3. `task.done()` 为 `True`
  4. `task.result()` 重抛 `CancelledError`（task 自身的取消）
  5. 该 `CancelledError` 逃逸 helper，被上层 `except asyncio.CancelledError` **误捕获**
- **预期行为**: helper 应区分「外层 task 取消」与「task 自身以 CancelledError 完成」
- **实际行为**: `task.result()` 抛出的 `CancelledError` 与外层取消的 `CancelledError` 无法区分，上层代码将其视为外层取消
- **直接证据**:
  ```python
  # lane.py:994-1016
  async def _await_task_after_outer_cancellation(task):
      while True:
          try:
              return await asyncio.shield(task)
          except asyncio.CancelledError:
              if task.done():
                  return task.result()  # 若 task 以 CancelledError 完成，
                                        # 此行重抛 CancelledError，
                                        # 被上层误认为外层取消
              await asyncio.sleep(...)
              continue
  ```
- **影响**: 在 `_try_claim_once`（行 555-584）中，若 claim task 自身被取消，`CancelledError` 逃逸后被 `except asyncio.CancelledError`（行 570）捕获，代码会尝试 release untracked claim——但 task 的实际结果是 `CancelledError` 而非 `RuntimeLaneError`，release 逻辑基于错误假设执行
- **建议改法**: 在 `task.done()` 分支中，先检查 `task.cancelled()`：若 task 自身被取消，应抛出 `RuntimeLaneError("shielded task was cancelled")` 而非让 `CancelledError` 逃逸
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: MEDIUM

## Open Questions

1. **`stop_worker_stream` 的完整契约是什么？** 当 ingestor 返回 `stop_worker_stream=True` 时，是否保证同时提供 `terminal_closeout`？如果不是，dispatch 层需要 fallback 机制。

2. **Phase 11 recovery 对 `close()` 遗留的非终态 Run 的处理时效？** 如果 recovery 延迟或有缺陷，用户会看到"卡住"的 Run。

3. **`_open_questions_retained` 的 CLEAR 语义是有意设计还是 bug？** 如果设计意图是 "compactor 主动处理了 open questions（包括清除）就算 retained"，那么函数名应改为 `_open_questions_addressed`。

4. **`MemoryProjectionPolicy` 是否应传入 quality checker？** 当前 quality gate 完全不知道 memory policy limits，导致语义断层。

5. **Runner 事件流契约的隐式依赖**: `_consume_runner_event` 在处理 `RunnerDoneData` 时假设 `RunnerContentCompletedData` 总是在 `RunnerDoneData` 之前到达。`AsyncRunner` 协议文档未明确约束事件顺序。

6. **`ToolAwaitingAcceptTimedOut.diagnostic_refs` 与 `ToolFactAcceptTimedOut.diagnostic_refs` 类型不一致的根因**: 两个 "TimedOut" ack 的 diagnostic_refs 类型不一致是设计意图还是历史遗留？

## Residual Risk

1. **RUNNING+STARTING+DISPATCHING 取消盲区**: 窗口虽窄（`worker.accept()` 异步期间），但在高频 cancel 场景下可能命中。当前行为是返回不可重试错误，用户需自行重试。风险等级：中。

2. **scheduler close 后非终态 Run**: 每次 scheduler 重启都依赖 recovery 机制清理孤儿 Run。如果 recovery 有 bug 或延迟，用户体验受损。风险等级：低（有 recovery 兜底）。

3. **`_release_token` 外层取消 + release 失败时的状态损坏**: SQLite 写入失败（磁盘满、权限问题）在生产环境中并非不可能。修复范围小，风险低。

4. **EventLog 治理语义准确性**: spurious governed event 会通过 projection 传播到 read model，影响审计和下游消费者对 "治理" 语义的理解。

5. **单文件过大**: `tool_runtime.py` (5395 行)、`dispatch.py` (3400+ 行)、`admission.py` (4800+ 行) 承载了多个职责。虽然当前模块内部分工清晰，但维护成本高。

6. **测试覆盖率缺口**: `_release_token` 失败取消路径、`_await_task_after_outer_cancellation` task 自身取消路径均无测试覆盖。

7. **contracts 层完整性良好**: CancellationToken Protocol、ToolExecutor Protocol、工具 outcome 封闭联合均无遗漏。

8. **runtime 层中立性通过**: runtime 仅 import `dayu.contracts.cancellation`（Protocol，层中立）和 `dayu.runtime.log_levels`（常量，层中立）。无反向依赖。

9. **架构边界未发现违反**: dispatch.py 和 admission.py 均只依赖同层或下层模块，无反向依赖。
