## Findings

### Finding 1 — 低风险：Phase 2 测试 error_code 变更可能掩盖协议错误路径

**文件**: `tests/engine/test_agent_phase2.py:723`

Phase 2 测试 `test_tool_call_delta_and_completed_fail_closed` 原断言 `error_code == "tool_call_not_supported_in_phase2"`，现改为 `"runner_abnormal_stop"`。

**原因**: runner 脚本仅产出 `RunnerToolCallDeltaData` / `RunnerToolCallsCompletedData`，无 `RunnerDoneData`。Phase 3 `_classify_iteration` 首先检查 `done_seen`，为 `False` 时直接返回 `"runner_abnormal_stop"`，不会走到 `tool_call_signal_seen` 的 `"runner_tool_calls_missing"` 分支。

**后果**: 测试通过，行为 fail-closed 无回归。但"runner 发了 tool call 信号且有 done event 但缺少实际 tool_calls 数据"的协议错误路径（`error_code == "runner_tool_calls_missing"`）在现有测试中无覆盖。

**建议**: 在 `test_agent_phase3_tool_call.py` 中补一个场景：`RunnerToolCallDeltaData` + `RunnerDoneData(finish_reason=TOOL_CALLS)` 但无 `RunnerToolCallsCompletedData`，断言 `error_code == "runner_tool_calls_missing"`。

### Finding 2 — 低风险：runner 异常在多轮 tool calling 循环中的行为无直接测试

**文件**: `dayu/engine/agent.py` `_run_runner_iteration` 异常处理

Phase 3 重构后，runner 异常不再立即 yield terminal，而是存入 `state.failure_candidate`，由 `_classify_iteration` 后续分类。Phase 2 测试 `test_runner_exception_is_run_failed` 覆盖了单轮场景，但 Phase 3 测试文件中没有直接测试：第 N 轮（N > 1）runner 调用抛异常时，已执行的 tool batch 结果是否正确保留、异常是否正确收口为 `run_failed("runner_exception")`。

**后果**: 行为与 Phase 2 一致（`_classify_iteration` 对 `failure_candidate` 的处理路径相同），不会引入回归。但多轮场景下的异常边界缺少专门覆盖。

**建议**: 可选补测，不阻塞合入。

### Finding 3 — 信息：force-answer fallback 只尝试一次，失败即终态

**文件**: `dayu/engine/agent.py` `_fallback_after_tools` / `_run_force_answer`

当 `FORCE_ANSWER` 模式的 force-answer runner 也产出 tool calls（模型无视"不要再调用工具"指令）时，直接 `run_failed("tool_call_not_enabled")`，不会重试 force-answer。同理，force-answer 产出空内容时直接 `run_failed("force_answer_empty")`。

**评估**: 这是 Phase 3 的合理设计决策。force-answer 本身已是降级路径，对其再加重试逻辑会增加状态机复杂度，收益有限。当前 fail-closed 行为明确。

**建议**: 在 README Tool Calling 段落中明确："force-answer 失败是终态，不重试"。

### Finding 4 — 信息：`_PlainJsonValue` TypeAlias 语义覆盖

**文件**: `dayu/engine/agent.py:134-136`

```python
_PlainJsonValue: TypeAlias = (
    None | bool | int | float | str | list["_PlainJsonValue"] | dict[str, "_PlainJsonValue"]
)
```

`_plain_json_value` 函数对 `Mapping` 输入返回 `dict`，对 `list` 输入返回 `list`，语义正确。类型签名中 `dict` 是 `Mapping` 的子类型，无类型错误。但若传入非 `dict` 的 `Mapping`（如 `OrderedDict`），返回值会丢失原始容器类型——对于 LLM-facing JSON 投影这是正确行为（JSON 不区分 dict 子类型），仅标注。
