## Findings

### 1-未修复-[低]-`requested_action` 事件/result 投影未钉死，同一 auto 请求在 runner 与独立 façade 两条入口的 durable 事实分叉，实施者有二义空间
- **位置**: 契约与实施决策 §33（"`requested_action` 事件字段如保留原始请求表示，须与 canonical/resolved action 的含义分别明确，不能另起动作判定规则"）；测试 §43/§47（仅断言 summary 保留 `"auto"` 与 resolve 结果，无 `requested_action` 取值断言）。
- **问题类型**: 契约缺失（durable 业务事实投影未在 owner 层定案）
- **当前写法**: plan 用条件句把 `requested_action` 的投影规则留给实施者："如保留原始请求表示，须……分别明确"，未选定取值方案，也未在测试清单锁定。
- **反例/失败场景**: 同一用户请求 `action="auto"`+文件：经 CLI/runtime/runner 路径时 workflow 入口收到的是 owner 已归一的 `None`（plan §30 保留 runner 预解析），`UPLOAD_STARTED` payload 与 `_build_result` 的 `requested_action=None`；经独立 façade `upload_material(action="auto", ...)` 时（本 slice 新增的成功路径，现状该调用在 `resolve_upload_action` 处崩溃）若实施者保留现有 echo（`str(action or "").strip().lower() or None`，sec:487 / cn:1103），则同一事实记为 `"auto"`。同一业务请求在 durable result/事件中出现两种表示；而 filing 同字段的既有约定是 raw echo（sec:166，auto→`"auto"`），material runner 路径却是 `None`，三处表示互相矛盾。下游 trace/memory/LLM 投影若按 `requested_action` 模式匹配将得到入口相关结论。
- **为什么有问题**: 违反 AGENTS.md 语义所有权约束"durable state、trace、memory……中出现同一业务事实时必须从同一真源派生并保持一致"。plan §33 只禁止"另起动作判定规则"（正确，`requested_action == "delete"` 的 selection 分支 sec:492/cn:1108 确实必须让位给 owner 返回值），但对字段取值的二义会让实施者在"raw echo"与"canonical 一致化"之间自裁，后续 gate 可能判 durable 不一致而返工；plan 已对 summary 公共表示（§43）、canonical 返回值（§47）分别锁定，唯独这个同源字段没有断言。

## Open Questions

1. **runtime/tool 未知与空 action 的错误类型未钉死**：runtime `_normalize_upload_action` 对空串/未知 action 现状抛 plain ValueError（7737-7754，经 `_bounded_text`/集合判断），tool `_required_upload_action` 抛 plain ValueError（455-457）；owner 契约则是 typed `FinsUploadUsageError(INVALID_ACTION)`（§22）。plan §28 只钉"既有未知 action 优先级保持"，§43 的"runtime 未知 action+非法组合先报 action"未写期望类型。若实施者把断言写成 typed，将倒逼改 `_normalize_upload_action` 为 typed（超出裁决"入口本地契约保持"）；若写成 plain，需明确 plain ValueError 在 direct API 属可接受投影。建议 §43 断言显式写明两类入口的期望异常类型。
