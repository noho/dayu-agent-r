## Findings

### F-01 [Low] `_bounded_preprocess_summary` 不校验 `selected_count == sum(其它计数)`

**文件**: `dayu/fins/ingestion_runtime.py`, `_bounded_preprocess_summary` (line ~5779)

**证据**: `_bounded_preprocess_summary` 校验了每个 `*_count` 非负、每个 `*_count == len(*_document_ids)`，但不校验 `selected_count == processed_count + skipped_count + not_supported_count + failed_count`。这意味着可以构造一个 `selected_count=5, processed_count=1, skipped_count=1` 的摘要通过校验，尽管 3 个文档未被分类。

**实际影响**: 低。生产代码中 `_execute_preprocess_request` 的构造逻辑保证了 `selected_count == len(document_ids)` 且每个 document 恰好进入一个分类列表（除非循环被 cancellation `break`，此时未处理文档不计入任何分类）。`result_status()` 的判定逻辑对这种 incomplete 状态仍能正确返回 `FAILED`（因为 `processed_count == 0` 且 `selected_count > 0`）。

**建议**: 在 `_bounded_preprocess_summary` 中增加 `selected_count >= processed_count + skipped_count + not_supported_count + failed_count` 的断言，使校验函数成为 count 一致性的完整 owner。当前状态不阻塞，但会使边界更自洽。

**严重性**: Low — 不影响当前生产正确性，属于防御性增强。

### F-02 [Low] `result_status()` 对 `selected_count > 0` 且全部 skipped 的场景语义依赖 fallthrough

**文件**: `dayu/fins/ingestion_runtime.py`, `FinsPreprocessResultSummary.result_status()` (line 629)

**证据**:

```python
def result_status(self) -> FinsPreprocessResultStatus:
    _bounded_preprocess_summary(self)
    if self.processed_count > 0:
        return FinsPreprocessResultStatus.SUCCEEDED
    if self.selected_count == 0 or self.failed_count > 0 or self.not_supported_count > 0:
        return FinsPreprocessResultStatus.FAILED
    return FinsPreprocessResultStatus.SUCCEEDED  # <-- fallthrough
```

当 `selected_count > 0, processed_count == 0, skipped_count > 0, failed_count == 0, not_supported_count == 0` 时，代码 fallthrough 到最后的 `return SUCCEEDED`。这个语义是正确的（全部因已有产物跳过 = 成功），但依赖隐式 fallthrough 而非显式条件。

**实际影响**: 无。语义正确，只是可读性可改进。

**建议**: 可选地将最后的 `return` 改为带注释的显式条件 `if skipped_count > 0: return SUCCEEDED`，或保留现状并在 docstring 中说明 fallthrough 语义。不阻塞。

**严重性**: Low — 可读性建议，不影响正确性。

### F-03 [Info] `FinsUploadPipelineResult.status` 是 `str` 而非 typed enum

**文件**: `dayu/fins/ingestion_runtime.py`, `FinsUploadPipelineResult` (line 700)

**证据**: `status: str` 字段接受任意非空字符串。`_required_upload_result_text` 只校验非空，不校验业务合法值。pipeline 可以传入 `"ok"`, `"uploaded"`, `"deleted"`, `"skipped"`, `"failed"` 等不同值，但没有 typed enum 约束。

**对比**: `FinsPreprocessResultStatus` 使用了 `str, Enum`。upload status 没有对等的 typed 约束。

**实际影响**: 当前生产 pipeline（SEC/CN）使用 `_resolve_upload_status()` 将 `"uploaded"` 映射为 `"uploaded"`，其它值透传。`FinsUploadResultSummary.status` 直接消费该值。无当前生产错误。

**建议**: 记录为后续改进。当前 P0-B 的 typed validation boundary 已经消除了 `"unknown"` fallback，`status` 必须由 pipeline 显式提供，这是核心目标。进一步 enum 化可以作为后续 sub WU 的改进。

**严重性**: Info — 不阻塞，当前目标已达成。

## Edge Case 验证

### `read_runtime.py` missing meta fallback

**文件**: `dayu/fins/tools/read_runtime.py`, line 1697

```python
ingest_method = (
    FinsIngestMethod.from_storage_value(str(meta["ingest_method"]))
    if meta
    else FinsIngestMethod.UPLOAD
)
```

**分析**:
- `meta is None` → fallback `FinsIngestMethod.UPLOAD`：合理，未知文档默认为上传。
- `meta is not None` 但缺少 `ingest_method` → `KeyError`：full-new-schema 规则下的正确 fail-fast 行为。
- `meta` 存在且 `ingest_method` 非法值 → `ValueError`：正确的 fail-fast。

**结论**: 符合 full-new-schema / semantic ownership 要求。不存在兼容性 fallback。

**结论**: 正确。

## Open Questions

1. **`FinsUploadPipelineResult.status` 是否需要 typed enum?** 当前 `str` 类型已消除了 `"unknown"` fallback，但未约束业务合法值。后续 sub WU 可以考虑引入 upload status enum（如 `FinsUploadStatus`），但不阻塞 P0-B。

2. **`_bounded_preprocess_summary` 是否需要校验 `selected_count >= sum(other counts)`?** 当前不校验。生产构造逻辑保证了一致性，但校验函数作为 validation boundary 应该更完整。建议作为 Low 优先级改进。

3. **`deleted: bool | None` 在 JSON summary 中的 `None` 值是否需要下游消费者适配?** 当前 `_upload_result_details` 不消费 `deleted` 字段，job record 存储 `None` 是合法 JSON。若有下游代码从 job record 读取 `deleted` 并期望 `bool`，需要确认。当前搜索未发现此类消费者。

## Residual Risk

- **SEC `SecPipeline._build_result` download 路径仍有 `"ok"` 默认值**: 不在 P0-B scope 内（upload typed result 只保护 upload 路径）。download 路径的 `_build_result` 用于下载结果，非上传结果。记录为后续 owner。
- **测试未覆盖 `FinsIngestMethod.from_storage_value()` 对非法值的 ValueError**: 当前测试只覆盖了 `FinsUploadPipelineResult.from_pipeline_json()` 的 status 缺失场景。`FinsIngestMethod.from_storage_value()` 的非法值测试可作为补充。
- **`FinsUploadResultSummary.deleted` 从 `bool` (default `False`) 改为 `bool | None` (default `None`) 是语义变更**: pipeline 未声明删除动作时，旧代码报告 `deleted=False`（伪造），新代码报告 `deleted=None`（诚实）。若有消费者依赖 `deleted` 为 `bool`，需要确认兼容性。当前搜索未发现此类消费者。

## Conclusion

P0-B 实现正确地完成了三个核心目标：

1. **Preprocess result status 单一真源**: `FinsPreprocessResultSummary.result_status()` 消除了 direct/job 路径的重复成功规则。`skipped_count` 和 `not_supported_count` 语义彻底分离，全链路同源。
2. **Upload typed result contract**: `FinsUploadPipelineResult.from_pipeline_json()` 是真正的 typed validation boundary，消除了 `"unknown"` / `False` fallback 伪造。
3. **`ingest_method` source-of-truth**: `FinsIngestMethod` enum 覆盖了全部生产读写点，storage JSON 保持业务可读字符串。

未发现阻塞性问题。F-01 和 F-02 为 Low 严重性改进项，可在后续迭代中处理。
