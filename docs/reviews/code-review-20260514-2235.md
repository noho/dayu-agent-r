## Findings

### 1-已修复-[中]-admission-backed public facade 绕过 closed handle guard

- **入口/函数**: `start_run`、`submit_followup`、`cancel_run`、`cancel_session_runs`
- **文件(行号)**: `dayu/host/command.py:287`、`dayu/host/command.py:303`、`dayu/host/command.py:352`、`dayu/host/command.py:390`
- **输入场景**: 调用方创建 `HostCommandHandle`，完成一次正常操作后调用 `host.close()`，随后误用同一个 handle 再调用 `start_run`、`submit_followup`、`cancel_run` 或 `cancel_session_runs`。
- **实际分支**: `HostCommandHandle.close()` 会关闭 durable store 并设置 `_closed=True`（`dayu/host/command.py:138`）；`_transaction_runner()` 才会调用 `_raise_if_closed()`（`dayu/host/command.py:149`、`dayu/host/command.py:179`）。但上述 Run command facade 直接调用 `host._admission_service.*`（例如 `start_run` 在 `dayu/host/command.py:296`），没有先经过 `_transaction_runner()` 或 `_raise_if_closed()`。
- **预期行为**: `dayu/host/README.md:28` 明确关闭 handle 后再次调用 public facade 应返回 `HostApiError(code=INVALID_STATE, retryable=False)`；Host command handle 是 public lifecycle 边界，所有 public command 应先由该边界拒绝 closed handle。
- **实际行为**: admission service 持有创建时缓存的 `HostTransactionRunner`，closed 后仍会进入 `run_write` 使用已关闭 SQLite connection；错误会从 durable transaction 层以 `HostDurableError` 等形式冒出，而不是稳定的 `HostApiError(INVALID_STATE)`。这让 public API 的错误契约依赖底层连接状态，而不是 Host handle lifecycle 真源。
- **直接证据**: `start_run` 直接调用 `host._admission_service.start_run(...)` 并返回 `run_snapshot_from_row(result.run)`（`dayu/host/command.py:296` 到 `dayu/host/command.py:300`）；`submit_followup`、`cancel_run`、`cancel_session_runs` 同样直接走 admission service（`dayu/host/command.py:332`、`dayu/host/command.py:368`、`dayu/host/command.py:408`）。现有 close 回归测试只覆盖 `ensure_session`（`tests/host/test_command_handle.py:156` 到 `tests/host/test_command_handle.py:169`），没有覆盖这些 admission-backed facade。
- **影响**: public error contract 破坏；调用方无法只按 `HostApiErrorCode.INVALID_STATE` 处理 closed handle；后续若 admission service 增加非 SQLite 副作用，也会继续绕过 Host handle lifecycle gate。
- **建议改法和验证点**: 在所有 public facade 入口先调用 `host._raise_if_closed()`，或让 admission-backed facade 通过 handle 提供的 guarded runner / service access 进入；补充 close 后调用 `start_run`、`submit_followup`、`cancel_run`、`cancel_session_runs` 的测试，断言统一返回 `HostApiErrorCode.INVALID_STATE` 且不写 EventLog / idempotency。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-已修复-[中]-terminal RunSnapshot 在 command path 与 read path 中不一致

- **入口/函数**: `cancel_run` 返回值、`start_run` 幂等重放返回值、`get_run`
- **文件(行号)**: `dayu/host/command.py:300`、`dayu/host/command.py:387`、`dayu/host/read_api.py:221`、`dayu/host/durable/state.py:1822`
- **输入场景**: 调用方 `start_run` 后对 queued 或 pre-dispatch running Run 调用 `cancel_run`，随后立即使用 `cancel_run` 返回的 `RunSnapshot`；或在 Run 已被取消 / 终态后，用同一 `start_run` 幂等 key 重放并读取返回 snapshot。
- **实际分支**: command path 直接调用 `run_snapshot_from_row(result.run)`（`dayu/host/command.py:300`、`dayu/host/command.py:387`）。该 durable helper 固定构造 `terminal_result_summary=None`（`dayu/host/durable/state.py:1822` 到 `dayu/host/durable/state.py:1831`）。
- **预期行为**: 同一个 public `RunSnapshot` 对同一 durable terminal Run 应有一致语义；`get_run` 的 public read path 已把终态 row 映射为 status-only `TerminalResultSummary`（`dayu/host/read_api.py:221` 到 `dayu/host/read_api.py:238`），README 也记录终态 Run 返回 status-only summary（`dayu/host/README.md:46`）。
- **实际行为**: 同一条 terminal Run 事实，通过 command 返回时 `terminal_result_summary is None`，通过 `get_run` 读取时 `terminal_result_summary.status == RunStatus.CANCELLED/FAILED/...`。现有测试只断言 `get_run` 的终态 summary（`tests/host/test_public_run_api.py:329` 到 `tests/host/test_public_run_api.py:349`），而 `cancel_run` 返回值测试只检查 status（`tests/host/test_public_run_api.py:471` 到 `tests/host/test_public_run_api.py:479`）。
- **直接证据**: `read_api._run_snapshot_from_public_read_row` 专门为 terminal statuses 包装 `TerminalResultSummary`（`dayu/host/read_api.py:224` 到 `dayu/host/read_api.py:233`），但该转换是 `read_api` 私有 helper，command path 没有复用。
- **影响**: public API 对外可见状态不一致；调用方如果基于 command 返回值判断 terminal summary 是否存在，会得到与随后 `get_run` 不同的结果，容易产生重复读取、错误展示或错误分支。
- **建议改法和验证点**: 把 public `RunSnapshot` row conversion 提升为单一共享 helper，并让 command path 与 read path 都使用同一转换；或者若 command response 有意不同，应引入明确的不同返回契约而不是复用同一 `RunSnapshot` 类型。补充 `cancel_run` 返回 snapshot 与后续 `get_run` snapshot 在 terminal summary 上一致的测试，并覆盖 start-run 幂等重放 terminal Run。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
