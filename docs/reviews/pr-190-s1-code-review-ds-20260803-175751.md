## Findings

### 1. 未修复-中-repair 路径在 S1 处于断裂状态：prompt 描述 REPAIR_FEEDBACK_JSON_BEGIN/END 但 renderer 仍输出 PREVIOUS_VALIDATION_REPORT_JSON

- **入口/函数**: `_user_prompt_vnext` → model reads both prompt template and rendered marker
- **文件(行号)**:
  - `dayu/host/llm_compaction.py:667` — renderer 输出 `PREVIOUS_VALIDATION_REPORT_JSON`
  - `dayu/config/prompts/scenes/conversation_compaction.md:17` — system prompt 描述 `REPAIR_FEEDBACK_JSON_BEGIN/END`
  - `dayu/config/prompts/scenes/conversation_compaction_user.md:72-80` — user prompt 描述 `REPAIR_FEEDBACK_JSON_BEGIN/END` 及 `required_action`/`issues` schema
- **输入场景**: Compactor 首次 attempt 失败，Host 通过 `build_compact_repair_feedback_v2` 构造 repair feedback，调用 `_user_prompt_vnext(..., repair_feedback=feedback)` 渲染下一次 attempt 的 prompt
- **实际分支**: renderer 在 `llm_compaction.py:667` 追加 `\n\nPREVIOUS_VALIDATION_REPORT_JSON\n{feedback.to_json()}`；没有 `REPAIR_FEEDBACK_JSON_BEGIN/END` 包裹，也没有 `required_action`/`issues` 的 exact-key 投影
- **预期行为**: prompt 文本应对模型说明它实际将收到的 marker 与数据格式；或者 S2 应先于 prompt 修改落地，避免中间态断裂
- **实际行为**:
  - 旧 system prompt 的 `收到 repair_feedback 时...` 指令已被替换为 `收到由 REPAIR_FEEDBACK_JSON_BEGIN 与 REPAIR_FEEDBACK_JSON_END 包围的修复反馈时...`
  - 旧 user prompt 的 `如果请求末尾包含 repair_feedback，它是...按其中的 code、json_path、message 修复` 指令已被替换为描述 `REPAIR_FEEDBACK_JSON_BEGIN/END` 与 `required_action`/`issues` 的文本
  - renderer 仍输出 `PREVIOUS_VEALIDATION_REPORT_JSON`（裸 marker，无 begin/end 包裹），且 `feedback.to_json()` 的字段结构（含 `previous_attempt_number`、`additional_issue_count`、`required_action`、`issues`）与 prompt 描述的 markup 不同
  - 模型看到的 rendered prompt 中，`PREVIOUS_VALIDATION_REPORT_JSON` 不被 prompt 中任何规则解释；新的 `REPAIR_FEEDBACK_JSON_BEGIN/END` 条件永远不成立，规则永远不触发
- **直接证据**:
  - `llm_compaction.py:667`: `+ "\n\nPREVIOUS_VALIDATION_REPORT_JSON\n"` — 仍存在，未被替换
  - `llm_compaction.py:669`: `repair_feedback.to_json()` — 仍使用 internal serialization，不是 projector
  - `conversation_compaction.md:17`: 明确写 `REPAIR_FEEDBACK_JSON_BEGIN/END` — 该字符串在 renderer 中不存在
  - `conversation_compaction_user.md:72`: 写 `如果请求末尾出现 REPAIR_FEEDBACK_JSON_BEGIN 与 REPAIR_FEEDBACK_JSON_END` — 条件在 renderer 当前输出下永远不成立
  - `test_repair_feedback_is_separate_and_requires_whole_candidate` (`test_llm_compaction.py:260-261`): 仍断言 `"PREVIOUS_VALIDATION_REPORT_JSON" in repair_prompt` — 测试与 renderer 当前行为一致，但与 prompt 文本不一致
- **影响**: 如果 S1 在 S2 之前被部署或测试，compactor repair attempt 路径中模型不知道如何解读 `PREVIOUS_VALIDATION_REPORT_JSON` 及其中 internal 格式的 feedback JSON。模型可能忽略 repair 指令、尝试自行解释 raw JSON、或产生不符合 whole-candidate 规则的行为。在 S1+S2 同 PR 同批次部署的场景下实际影响有限，但中间态的测试覆盖率存在缺口（没有测试验证修复路径的 prompt/model 一致性）。
- **建议改法和验证点**:
  - 方案 A（推荐）: 确认 S1 与 S2 在同 PR 内不可分割地合并，不作为独立 commit 交付。在 S2 的 renderer/projector 变更中一并修改 `test_repair_feedback_is_separate_and_requires_whole_candidate` 的 marker 断言为 `REPAIR_FEEDBACK_JSON_BEGIN/END`
  - 方案 B: 在 S1 prompt 中增加临时兼容说明："当前实现暂用 `PREVIOUS_VALIDATION_REPORT_JSON` 标记修复反馈，其格式将统一为下文描述的 `REPAIR_FEEDBACK_JSON_BEGIN/END`"。不推荐，因为增加后续需要回退的临时文本
  - 验证点: S2 完成后确认 `llm_compaction.py` 中不再有 `PREVIOUS_VALIDATION_REPORT_JSON` 字符串；系统 prompt 与 user prompt 中的 `REPAIR_FEEDBACK_JSON_BEGIN/END` 与 renderer 输出一致
- **修复风险（低）**: 此 finding 本质是 staged implementation 的 temporal coupling，S2 已计划在相同 PR 内闭合。如果在 S2 实施前确认 S1+S2 绑定交付，则此 finding 可降级为 "accepted known residual"
- **严重程度（中）**: finding 有效但 deferred to S2。如果 S1 单独 ship 则为高
