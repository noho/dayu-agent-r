## Findings

### 001-未修复-[高]-`start_run` 在 admission 失败前已写入用户输入，导致无终态半提交 Run

- **入口/函数**: `LocalRunHarness.start_run()` / `_engine_visible_request()` / `_run_to_store()`
- **文件(行号)**: `dayu/host/_run_harness.py:615`, `dayu/host/_run_harness.py:639`, `dayu/host/_run_harness.py:792`, `dayu/host/_tool_runtime.py:264`
- **输入场景**: durable run 启动时出现 admission 失败，例如调用方业务 `ToolSchema.function.name == "fetch_more"`，或同一 `run_id` 已存在 `attempt_index=0` 导致初始 attempt acquire 返回 BUSY / fencing。
- **实际分支**: `start_run()` 先 append `USER_INPUT_ACCEPTED`，之后才调用 `_engine_visible_request()`；该函数会通过 `HostToolRuntime.engine_visible_tool_schemas()` 检测 framework schema 冲突并抛 `ValueError`。另一条路径中，后台 `_run_to_store()` 在外层 `try` 之前执行 `_begin_attempt_if_durable()`，初始 acquire 失败会直接逃出后台 task。
- **预期行为**: durable admission 必须在第一个不可逆 EventLog 写入前完成；若已经接纳用户输入，则后续 schema / attempt admission 失败必须写入可观察 Host terminal failure，并保证 `RunResult`、stream 与 attempt 状态收口。
- **实际行为**: EventLog 可只留下 `USER_INPUT_ACCEPTED`，没有 terminal RunEvent；schema 冲突路径同步抛异常，initial acquire 失败路径后台 task 结束，`_task_aware_event_stream()` 短暂 drain 后自然结束，调用方拿不到 terminal result。
- **直接证据**: `start_run()` 在 `dayu/host/_run_harness.py:615-624` append 用户输入；schema provider 增强在 `dayu/host/_run_harness.py:639` 之后才执行，冲突判断在 `dayu/host/_tool_runtime.py:264-272`；initial attempt acquire 在 `dayu/host/_run_harness.py:792-795`，外层 `try` 从 `dayu/host/_run_harness.py:802` 才开始；`_begin_attempt_if_durable()` 直接进入 `lease_context()`，没有 acquire 失败收口分支。
- **影响**: durable run 进入“已接纳用户输入、无终态、无 RunResult”的半提交状态；重试同一 `run_id` 还可能继续撞 `attempt_index=0`，恢复语义被卡住。
- **建议改法和验证点**: 将 schema projection / framework tool name conflict / durable attempt admission 前置到 `USER_INPUT_ACCEPTED` 写入前；或把这些失败纳入 Host-owned terminal failure 收口事务。补端到端测试覆盖业务 schema 名为 `fetch_more`、重复 `run_id` / initial acquire BUSY，断言不会留下无 terminal 的 run。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 002-未修复-[高]-ToolTrace request/result 配对只在内存中，checkpoint 可越过未配对事件并在重启后永久丢 trace

- **入口/函数**: `ProjectionCoordinator._process_non_transactional_batch()` -> `ToolTraceObserver.process_non_transactional()` -> `_collect_tool_call()`
- **文件(行号)**: `dayu/host/_event_observer.py:391`, `dayu/host/_event_observer.py:412`, `dayu/host/_tool_trace_projection.py:126`, `dayu/host/_tool_trace_projection.py:241`, `tests/host/test_phase7_tool_trace_projection.py:277`
- **输入场景**: checkpoint batch 只包含某个 tool call 的 `TOOL_CALL_REQUESTED`，对应 `TOOL_RESULT_ACCEPTED` 在后续 batch；进程在第一个 batch checkpoint 成功后、第二个 batch 前重启。
- **实际分支**: trace observer 把 request 存入 `_pending_tool_call_groups` 内存 dict，不写 JSONL；coordinator 认为 non-transactional process 成功并把 checkpoint 推进到 batch 最后 position。
- **预期行为**: EventLog 是 trace 唯一来源且 projection 可 replay 时，checkpoint 不应越过只能靠进程内 pending 状态解释的事件；重启后仍应能从 durable facts 生成 tool_call record。
- **实际行为**: 重启后 pending dict 丢失；后续只看到 accepted 半边，无法与已 checkpoint 的 requested 配对，最终没有任何 `tool_call` trace record，且 checkpoint 继续推进。
- **直接证据**: `_pending_tool_call_groups` 是 dataclass 内存字段（`dayu/host/_tool_trace_projection.py:126-129`）；配对完成才 `_emit_tool_call()`（`dayu/host/_tool_trace_projection.py:241-253`）；non-required observer 成功后 checkpoint 推进在 `dayu/host/_event_observer.py:412-420`。现有测试只验证同一 observer 实例跨 batch 暂存，不覆盖进程重启。
- **影响**: trace JSONL 与 EventLog 产生永久不一致；P8.5 引入的 at-least-once replay / idempotency key 只能覆盖 sink 成功 checkpoint 失败，不能覆盖未落盘 pending pair。
- **建议改法和验证点**: 在 accepted 到达时从 durable EventLog 回查同 `run_id / iteration_id / tool_call_id` 的 requested，或把 pending pair 状态落 durable side-store 并与 checkpoint 绑定；补测试模拟 checkpoint 越过 requested 后新建 `ToolTraceObserver` 再处理 accepted，断言仍生成 trace 或 checkpoint 不推进。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 003-未修复-[中]-`partial_tool_calls` 摘要没有限制 provider-controlled `tool_call_id` 长度

- **入口/函数**: `SSEParser._handle_choice()` -> `ToolCallAggregator.feed()` -> `partial_summaries()` -> `RunnerProtocolErrorData`
- **文件(行号)**: `dayu/engine/runners/openai/tool_call_aggregator.py:205`, `dayu/engine/runners/openai/tool_call_aggregator.py:335`, `dayu/engine/runners/openai/tool_call_aggregator.py:355`, `dayu/engine/contracts/partial_tool_call.py:10`
- **输入场景**: provider SSE 先发送超长 `tool_calls[0].id`，随后发送非法 JSON、malformed usage 或 invalid UTF-8 触发 protocol error。
- **实际分支**: aggregator 原样保存 `partial.tool_call_id`，`partial_summaries()` 只限制 item 数和 `name_fragment`，但把 `tool_call_id` 原样放进 `PartialToolCallSummary`。
- **预期行为**: 既然契约声明 `partial_tool_calls` 是有界诊断摘要，所有 provider-controlled 字符串都必须有硬边界，或使用 fragment + hash 表达。
- **实际行为**: 超长 provider id 可进入 Engine event、Host RunEvent serializer、durable EventLog 与 trace analyzer payload。
- **直接证据**: `partial_summaries()` 在 `dayu/engine/runners/openai/tool_call_aggregator.py:342-365` 构造摘要，`name_fragment` 经过 `_bounded_name_fragment()`，但 `tool_call_id=partial.tool_call_id` 没有等价截断；`PartialToolCallSummary` docstring 称为“有界诊断摘要”。
- **影响**: malformed stream 可放大诊断事件体，削弱 provider protocol error boundary 与持久化大小可控性。
- **建议改法和验证点**: 将 schema 改为 `tool_call_id_fragment` + `tool_call_id_sha256`，或至少在 `partial_summaries()` 截断 `tool_call_id` 并保留 hash；补测试覆盖超长 id 不会原样进入 serialized `partial_tool_calls`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 004-未修复-[中]-Host 反序列化静默接受缺失 `partial_tool_calls` 字段，掩盖 schema drift

- **入口/函数**: `deserialize_run_event_data()` / `_decode_fields()` for `PROVIDER_PROTOCOL_ERROR`
- **文件(行号)**: `dayu/host/_run_event_serializer.py:481`, `dayu/host/_run_event_serializer.py:662`, `dayu/engine/contracts/engine_events.py:188`
- **输入场景**: durable EventLog 中 `PROVIDER_PROTOCOL_ERROR` 的 serialized `fields` 缺少新增的 `partial_tool_calls` 字段。
- **实际分支**: decoder 使用 `fields.get("partial_tool_calls")`，缺失时传入 `None`；`_decode_partial_tool_call_summaries(None)` 返回空 tuple。
- **预期行为**: 当前 schema 变更按全新 schema 起库处理；显式契约字段缺失应 fail-fast，空列表才表示“没有 partial tool calls”。
- **实际行为**: 写入端遗漏、schema drift 或旧 payload 混入会被解读为空摘要，protocol failure 前的 partial diagnostic 丢失。
- **直接证据**: `ProviderProtocolErrorData` 现在包含 `partial_tool_calls` 字段；`dayu/host/_run_event_serializer.py:481-483` 用 `.get()` 解码；`dayu/host/_run_event_serializer.py:662-663` 对 `None` 返回 `()`。
- **影响**: replay / repair 无法发现新旧 schema 混用，用户调试 provider stream failure 时看到的是“无 partial”而不是“payload 缺字段”。
- **建议改法和验证点**: 对 `PROVIDER_PROTOCOL_ERROR` 解码先检查 `"partial_tool_calls" in fields`；缺失抛 `ValueError`，字段存在且为 `[]` 才解读为空。补 serializer 缺字段失败测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
