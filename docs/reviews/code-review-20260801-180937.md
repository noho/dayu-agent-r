### S2-CR-001 — PASS — 同步 signal fallback 安装与恢复

**验证目标**：`CliSigintMonitor` 在 `loop.add_signal_handler` 不可用时，应使用 `signal.signal` fallback，使 `notify()`/`count`/`wait_next()`/`close()` 在同一 owner 内保持一致，不回退为原生 `KeyboardInterrupt`。

**直接证据**：

1. `agent_entrypoint.py:32-37` 新增 `_CliSigintInstallationMode` 枚举，三种状态：`NONE`、`ASYNCIO`、`SYNCHRONOUS`。
2. `agent_entrypoint.py:80-90`：`install()` 在 `add_signal_handler` 抛出 `NotImplementedError`/`RuntimeError` 时，直接调用 `signal.signal(signal.SIGINT, self.notify)`，设置 `_installation_mode = SYNCHRONOUS`、`_loop = None`、`_previous_handler = previous_handler`（在 try 之前捕获）。
3. `agent_entrypoint.py:101-112`：`close()` 按模式分支——ASYNCIO 才调用 `remove_signal_handler`，SYNCHRONOUS 只恢复 `_previous_handler`，两条路径都回到 `NONE`。
4. `notify()` 签名 `(self, _signal_number: int | None = None, _frame: FrameType | None = None)` 兼容 `signal.signal` 回调格式。`self.count += 1` 在 CPython GIL 下对简单 int 增量是安全的；`self._event.set()` 在同步模式下（`_loop = None`）直接设置内部 flag 并唤醒 waiters，不调用 `call_soon_threadsafe`。

**幂等/异常路径**：

- `install()` 中 `_previous_handler` 在 `try` 之前捕获（`agent_entrypoint.py:77`），因此即使 `add_signal_handler` 失败，`_previous_handler` 已正确保存。
- `close()` 对 `NONE` 模式不做任何操作（不进入 if/elif 分支），直接设置 `_installation_mode = NONE`，不泄漏。
- 若 `_previous_handler is None`（理论上不应该发生，因为 `install()` 在 `getsignal` 返回 `None` 时已 raise），`close()` 会 raise `RuntimeError`，不会静默跳过恢复。

**测试覆盖**：

- `_SyncSigintFallbackHarness`（`test_interactive_command.py:946`）确定性让 `add_signal_handler` 抛出 `NotImplementedError`，并让 `remove_signal_handler` 抛出 `AssertionError` 防止同步模式误调用 asyncio remove API。
- `test_interactive_startup_single_sigint_cleans_up_and_returns_130`（`test_interactive_command.py:1484`）使用真实 `CliSigintMonitor` fallback handler 触发 startup SIGINT，断言：count=1、startup observation 被取消、0 submit、0 Host cancel、attachment 恰好关闭一次、exit 130、handler 恢复为 `signal.SIG_IGN`。
- `test_interactive_os_sigint_first_second_and_third_follow_same_lifecycle`（`test_interactive_command.py:2483`）三次触发 active lifecycle，断言：single canonical cancel、cancel waiter 未被取消、count=3、handler 恢复。
- 既有 asyncio-supported 回归 `test_prompt_sigint_monitor_restores_previous_process_handler` 仍通过。

**prompt/Fins 既有语义**：`CliSigintMonitor` 的 `notify`/`wait_next`/`close` 接口未改变；同步 fallback 只替换安装/恢复的底层机制，不改变 interactive 状态机的 SIGINT 计数和 waiter 语义。prompt one-shot 路径不使用 `CliSigintMonitor`，不受影响。

**Residual risk**：真实 Windows console delivery 由 Windows CI owner 验证；同步 fallback 的 owner contract 已确定性覆盖。

### S2-CR-002 — PASS — PTY raw-mode readiness 与 ordinary Enter

**验证目标**：用可观察的 PTY mode/readiness 条件替换固定 `sleep(0.05)`，并在真实 PTY 中证明普通 Enter 不被猜成 Shift+Enter。

**直接证据**：

1. `test_interactive_composer.py:496-511` 新增 `_wait_for_pty_raw_mode(slave_fd)`，直接读取 `termios.tcgetattr(slave_fd)[3]`，只有 ECHO/ICANON/ISIG/IEXTEN 四项均关闭才返回。timeout=2s，poll=5ms。
2. `test_real_posix_pty_exact_sequences_and_terminal_mode_restore`（`test_interactive_composer.py:377`）三次写入前全部使用 `_wait_for_pty_raw_mode`，不再使用固定 `sleep(0.05)`。
3. 同一真实 PTY 在 exact Shift+Enter 组合提交后，单独写入 `b"ordinary\r"`，断言 `kind is SUBMIT` 且 `draft == "ordinary"`（`test_interactive_composer.py:430-431`）。因此普通 Enter 在真实 PTY 中被正确识别为提交，不被误判为 Shift+Enter。
4. 每轮 submit 后调用 `accept_submit`，随后再次进入 raw mode；每轮退出都断言 terminal local flags 恢复到原值（`test_interactive_composer.py:433-435`）。

**可移植性**：`termios.tcgetattr` 在 POSIX 平台可移植；测试用 `@pytest.mark.skipif(os.name != "posix")` 保护。PTY master/slave 共享 terminal settings，prompt_toolkit 在 slave 侧设置 raw mode 后 `tcgetattr(slave_fd)` 可观察到。

**Residual risk**：非 POSIX 平台继续按既有 capability skip；Windows console 的 Shift+Enter 可区分能力不由本机 PTY 冒充。
