## 2. Assumptions Tested

### 2.1 Semantic Owner Assumption

**Claim**: `convert_pdf_bytes_with_docling` is the sole semantic owner for "immutable PDF bytes -> attempt-local DocumentStream" assembly.

**Evidence**:
- `dayu/documents/docling_runtime.py:629-667`: `convert_pdf_bytes_with_docling` constructs stream and passes to `run_docling_pdf_conversion`
- `dayu/documents/docling_runtime.py:510-602`: `run_docling_pdf_conversion` owns attempt ordering, converter construction, logging, and first/last exception semantics
- `dayu/fins/pipelines/cn_docling_process.py:66-80`: Production runner calls `convert_pdf_bytes_with_docling` but does not own attempt stream lifecycle
- `dayu/fins/pipelines/docling_upload_service.py` and `dayu/tools/web/web_fetch_orchestrator.py`: Other callers also consume same owner

**Verdict**: ✅ Correct. Owner boundary is well-defined.

### 2.2 Root Cause Assumption

**Claim**: Current code shares a mutable `BytesIO` across attempts, causing "I/O operation on closed file" when first attempt closes it.

**Evidence**:
- `dayu/documents/docling_runtime.py:660-662`: `stream = _build_docling_document_stream(...)` is called once outside lambda
- `dayu/documents/docling_runtime.py:662`: Lambda `lambda converter: converter.convert(stream)` reuses same stream for all attempts
- Evidence from 0066 and 0700 scenarios confirms: attempt 1 fails with SSL error, attempt 2 fails with "I/O operation on closed file"

**Verdict**: ✅ Correct. Root cause is clearly identified.

### 2.3 Fix Strategy Assumption

**Claim**: Moving stream construction inside lambda will create attempt-local streams.

**Evidence**:
- `run_docling_pdf_conversion` calls `convert_operation(converter)` in loop (line 570)
- Lambda will be invoked once per attempt
- Each invocation will call `_build_docling_document_stream(raw_bytes, stream_name=stream_name)`
- `_build_docling_document_stream` creates new `BytesIO(raw_bytes)` each time (line 626)

**Verdict**: ✅ Correct. Fix strategy is sound.

### 2.4 Production Runner Invariance Assumption

**Claim**: `ProcessCnDoclingConversionRunner` and other callers remain unchanged.

**Evidence**:
- `cn_docling_process.py` only calls `convert_pdf_bytes_with_docling` (line 68)
- Plan §6.1 restricts changes to `docling_runtime.py` and new test file
- Plan §9.3 includes `git diff --exit-code` for production callers

**Verdict**: ✅ Correct. Production runner is properly protected.

## 3. Findings

- **问题类型**: 不可直接实施
- **当前写法**: Plan 声称 `run_docling_pdf_conversion(...)` 在 `dayu/documents/docling_runtime.py:538-602`
- **反例/失败场景**: Implementation agent 按行号查找代码时可能困惑
- **为什么有问题**: 实际 baseline 代码中 `run_docling_pdf_conversion` 从第 510 行开始，不是 538 行。偏差约 28 行。
- **直接证据**:
  ```bash
  $ git show 54dd750a:dayu/documents/docling_runtime.py | grep -n "def run_docling_pdf_conversion"
  510:def run_docling_pdf_conversion(
  ```
- **影响**: Implementation agent 可能需要额外时间定位正确代码位置，但不阻塞实施
- **建议改法和验证点**: 更新行号引用为 `510-602`；验证时确认 `run_docling_pdf_conversion` 函数签名在第 510 行
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 3.2 未修复-中-Coverage Tests 是否 Goal-Bound

- **位置**: §8.5 Coverage-supporting owner cases
- **问题类型**: 目标漂移
- **当前写法**: Plan 列出 6 类 coverage-supporting tests：`resolve_docling_device_name`、`_plan_conversion_attempts` 参数化矩阵、`build_docling_pdf_pipeline_options`、`build_docling_pdf_converter` / `_resolve_backend_class`、`_build_attempt_converter`、`_build_docling_document_stream`
- **反例/失败场景**: Implementation agent 可能花费大量时间编写和调试这些 coverage tests，而这些 tests 不直接验证 DL-F15 的核心 goal（每个 attempt 使用独立 stream）
- **为什么有问题**:
  - DL-F15 Goal Confirmation 的唯一目标是："让一次 `convert_pdf_bytes_with_docling` 调用中的每个 Docling attempt 都从同一份 immutable `raw_bytes` 新建独立、仍可读的 `DocumentStream`"
  - §8.4 的两项核心 owner tests 直接验证这个 goal
  - §8.5 的 coverage-supporting tests 验证的是 device/backend 规划逻辑、pipeline options 构造、converter 初始化等，这些是 `docling_runtime.py` 的既有功能，不是 DL-F15 修复引入的新行为
  - Goal Confirmation 确实要求"修改生产文件单文件 coverage >=80%"，但这应该是 residual requirement，不应驱动 implementation agent 为不相关的分支编写详细测试
- **直接证据**:
  - Goal Confirmation §成功信号 4："受影响测试、完整 pyright、changed-files Ruff/format、compileall、`git diff --check` 通过；修改生产文件单文件 coverage 不低于 80%"
  - Plan §8.5 列出的 tests 不覆盖 DL-F15 修复的代码路径（lambda 内 stream 构造）
- **影响**: Implementation agent 可能花费 30-50% 的时间在不直接验证 goal 的 tests上，降低交付效率
- **建议改法和验证点**:
  - 将 §8.5 标记为 "optional/deferred"，明确这些 tests 是为了满足 coverage requirement，不是 DL-F15 goal 的必要验证
  - 或者，将 coverage requirement 从 DL-F15 goal 中分离，作为独立 follow-upissue
  - 验证时确认 §8.4 的两项核心 tests 通过即可判断 DL-F15 goal 达成
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 3.3 未修复-低-真实 Evidence Run 的分类风险

- **位置**: §9.4 独立 production CLI + 真实 Docling evidence
- **问题类型**: 其它
- **当前写法**: Plan 要求在修复 commit 后运行真实 CLI download + process，使用 0700 Q3 或 0066 Q2 文档
- **反例/失败场景**: 如果 provider 返回的文档内容、分类或 metadata 与之前 frozen evidence 不同，可能会产生新的分类问题
- **为什么有问题**:
  - Plan 声称"不扩展 DL-F12～F14、分类或其它设施"
  - 但 §9.4 的真实 run 会 download 和 process 真实文档，这些操作可能触发分类逻辑
  - 如果 0700 Q3 或 0066 Q2 的 provider 返回内容与之前不同，可能会产生新的 HK 分类结果
  - Plan 有防护："不重做或裁决 DL-F12～F14、HK 分类、Oracle/readiness"
  - 但"不裁决"和"不产生新结果"是两回事
- **直接证据**:
  - 0700 public-summary: Q3 document `fil_cn_54602897a720227b36458950300dffda20b5cd66` disposition=failed
  - 0066 public-summary: Q2 document `fil_cn_16b441c52063506c3331e06f84cd884882402075` disposition=failed
  - 这些文档之前 failed，修复后可能成功，成功后会触发分类逻辑
- **影响**: 如果分类逻辑产生与之前不同的结果，可能会引发新的裁决需求
- **建议改法和验证点**:
  - 在 §9.4 的裁决规则中增加："如果新 run 的分类结果与 frozen evidence 不一致，记录差异但不裁决，作为 external evidence gap"
  - 验证时确认新 run 的 public summary 与 frozen evidence 的分类字段一致
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## 4. Open Questions

1. **Coverage requirement 的优先级**：Goal Confirmation 要求"修改生产文件单文件 coverage >=80%"，但 DL-F15 的核心 goal 只需要 §8.4 的两项 tests。如果 §8.4 的两项 tests 加上 §8.5 的部分 tests 就能达到 80%，是否可以只实现部分 §8.5 tests？

2. **真实 evidence run 的时机**：Plan §9.4 说"在修复被接受后的独立 commit 环境运行"。这是否意味着 implementation agent 需要先完成所有 deterministic tests，然后创建一个独立 commit，再运行真实 evidence？还是可以在同一个 commit 中运行？

## 5. Residual Risks

1. **第三方 converter 未来继续关闭输入**：Plan 在 owner boundary 消除跨 attempt 共享，但第三方 converter 的行为是外部实现细节。Risk: 低。
2. **真实网络/model cache 使首 attempt 直接成功**：deterministic owner test 已证明 contract；真实 fallback 缺口标为 `requiring explicit user decision`。Risk: 低。
3. **Provider 不再返回冻结的 0700 Q3/0066 Q2**：Plan 有防护："使用既有 0066 Q2 作为同 root-cause 的替代样本；若两者均不可用，标为 external evidence gap"。Risk: 低。

## 6. Plan Review Conclusion

**结论**: `pass-with-risks`

Plan 整体设计合理，semantic owner 清楚，root cause 明确，fix strategy 正确，production runner 保护到位。主要风险是：

1. §8.5 的 coverage-supporting tests 可能导致 implementation agent 花费过多时间在不直接验证 goal 的 tests上（中风险）
2. 行号引用偏差可能让 implementation agent 困惑（低风险）
3. 真实 evidence run 可能产生新的分类结果（低风险）

建议 controller 裁决：
- 如果 DL-F15 的 goal 是"修复 closed-file bug"，则 §8.5 应标记为 optional/deferred
- 如果 DL-F15 的 goal 是"修复 closed-file bug + 达到 80% coverage"，则 §8.5 是必要的，但 implementation agent 应优先完成 §8.4再处理 §8.5
