## Findings

### 001-未修复-中-冻结场景 UF-A08 与 oracle predicate 矛盾

- **位置**: §3.1（明确不做）；§11（diff/static audit）；frozen registry `upload_filing.UF-A08-update-missing-overwrite-creates`
- **问题类型**: 契约缺失
- **当前写法**: "不刷新 `docs/cli_ci_scenarios.json`、`docs/cli_ci_oracles.json`，不重写第一轮 observed evidence，不登记 post-fix conformance refresh。"
- **反例/失败场景**: plan 将 `update + missing + overwrite=True` 的行为从 "静默创建" 改为 "typed UPDATE_TARGET_MISSING"。frozen scenario `UF-A08-update-missing-overwrite-creates` 记录了旧行为且 status=accepted。oracle predicate `upload_filing.action-core` 已明确禁止 "update missing + overwrite 静默创建"。实施后 UF-A08 成为过时证据，但 plan 声称不刷新 registry。实现 agent 无法判断是否应更新 scenario status。
- **为什么有问题**: 冻结 scenario 是 observed evidence，不是 correctness contract；oracle 才是 contract。但 plan 的 "不刷新" 声明同时覆盖了 scenario 和 oracle。如果实现 agent 严格遵守 "不刷新"，UF-A08 保持 accepted 但行为已变，后续 CI 或 conformance 验证会产生 false negative。
- **直接证据**:
  - `docs/cli_ci_scenarios.json` 第 131293 行：`UF-A08-update-missing-overwrite-creates`，status=accepted
  - `docs/cli_ci_oracles.json` oracle `upload_filing.action-core` forbidden clause："update missing + overwrite 静默创建，或用本地文件名替代 filing identity。"
  - plan §3.1："不刷新 `docs/cli_ci_scenarios.json`、`docs/cli_ci_oracles.json`"
- **影响**: 实现 agent 困惑于是否更新 scenario status；后续 conformance 验证可能因 stale scenario 产生错误结果。
- **建议改法和验证点**: 在 plan §3.1 或 §12 中明确：实施后 UF-A08 的 observed behavior 将与新行为不一致，scenario status 应标记为 `superseded-by-fix` 或等价状态；oracle predicate 不变（因为它已经禁止该行为）。同时确认其它冻结场景（UF-A07, UF-A12 等）的行为与 plan 一致。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 002-未修复-低-reset→create 同 batch 错误路径未显式文档化

- **位置**: §5.2（Publication transition）
- **问题类型**: 状态机漏洞
- **当前写法**: "begin one ticker batch → reset exact source tree → store every new blob → create one complete source meta → commit batch"
- **反例/失败场景**: 如果 `reset_source_document` 成功但后续 `store_file` 或 `_upsert_source_document`（create-only）失败，batch 应被丢弃，old state 应保留。plan 未显式描述此错误路径。S2 测试提到了 "staged final mutation failure / precommit cancel: published tree SHA still equals old"，但 plan 的 publication transition 流程图没有对应的错误分支。
- **为什么有问题**: 实现 agent 可能遗漏 batch rollback 时 reset 的恢复语义。依赖 storage batch 的隐式 rollback 行为。
- **直接证据**: plan §5.2 publication transition 无 error branch；S2 tests-first 提到了 cancel/failure assertion 但未在流程图中体现
- **影响**: 低。storage batch 已有 atomic commit 语义，reset 在 batch 内，batch 丢弃即回滚。但如果 storage 实现有 edge case，可能残留半 reset 状态。
- **建议改法和验证点**: 在 §5.2 流程图中增加错误分支："任何 store/create 步骤失败 → 丢弃 batch → old state 完整保留"。S2 测试已有对应 assertion，只需 plan 文档化。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 003-未修复-低-版本号与 first_ingested 语义在 reset→create 路径下的契约未显式说明

- **位置**: §5.2（Publication transition）、§5.3（Observable state transitions）
- **问题类型**: 契约缺失
- **当前写法**: "create one complete source meta/manifest with is_deleted=False"
- **反例/失败场景**: reset→create 路径下，`_resolve_document_version` 接收 `previous_meta`（非 None），会按 fingerprint 比较决定版本递增还是保持。但 reset 后 source tree 已清空，`previous_meta` 是 reset 前读取的旧 meta。如果实现 agent 错误地在 reset 后清除 `previous_meta` 引用，版本号可能回到 v1。`first_ingested` 字段应在 update 时保持原值，reset→create 不应重置。
- **为什么有问题**: plan 声称 "版本递增" 但未显式说明 reset→create 路径下 `previous_meta` 的存活语义和 `first_ingested` 的保持规则。
- **直接证据**: plan §5.3 "active, changed same basename: 新 bytes/digest/meta；版本递增"；`_resolve_document_version` 代码使用 `previous_meta` 判断
- **影响**: 低。实现 agent 大概率正确处理，但缺乏显式契约可能导致 edge case 错误。
- **建议改法和验证点**: 在 §5.2 或 §5.3 中增加一句："reset→create 路径下 `previous_meta` 仍用于版本号解析和 `first_ingested` 保持；reset 只清空 storage blob 和 file entries，不丢弃 caller 已持有的 meta 引用。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
