# UF-FIX11 company-metadata-ignored-change-warning Plan Review

## Review Target and Scope

- **Reviewed target**: `docs/gateflow/uf-fix11-company-meta-warning-plan-20260817.md`
- **Scope**: 严格 adversarial review，验证 warning 是否真正由 publication-lock final company state owner 产生、name-only commit 是否造成不必要 durable mutation、skip alias commit 与 UF-FIX10 一致性、commit_batch 返回类型完整性、UploadOperationResult 语义漂移、warnings JSON 缺失兼容 fallback、LLM/CLI 文案准确性、material/Host/Engine 范围泄漏、slices/allowed files/测试可实施性。

## Assumptions Tested

1. Warning 由 publication-lock final company state owner 产生
2. name-only commit 不造成不必要 durable mutation
3. skip alias commit 与 UF-FIX10 arbitration/cancel/rollback 一致
4. commit_batch 返回类型变更覆盖所有 callsites/fakes
5. UploadOperationResult 不发生 semantic ownership drift
6. warnings JSON 缺失不被错误当空数组形成兼容 fallback
7. LLM/CLI 文案明确说明提交名称未生效且保留现有名称
8. material/Host/Engine 范围不泄漏
9. slices/allowed files/测试可直接实施

## Findings

### 001-未修复-高-name-only commit 造成不必要 durable mutation

- **位置**: Section 8.3 Skip 时 alias 原子持久化
- **问题类型**: 过度耦合 / 非最优方案
- **当前写法**: "若 intent 只承载不同 submitted name 而没有 identity 变化，仍需进入 commit owner，以 publication-final truth 判断 warning。这个 commit 是为生成受锁保护的业务结果所必需；等价名称/no-op alias 会在 fresh decision 阶段保持 keep + rollback，避免常见 no-op commit。"
- **反例/失败场景**: 用户提交一个与 canonical name 不同但 NFKC+casefold 等价的名称时，系统会执行 metadata-only commit，即使没有实际 identity 变化。这会产生无意义的 durable mutation（updated_at 时间戳被刷新），并且在高并发场景下增加不必要的锁竞争。
- **为什么有问题**: 根据 UF-FIX10 closeout，skip 语义是 "no durable mutation"。Plan 引入了一个例外：当 submitted name 与 canonical name 不等价时，即使没有 identity 变化，也要执行 metadata-only commit。这与 UF-FIX10 的 skip 语义不一致，且违反了 "minimal durable mutation" 原则。
- **直接证据**:
  - `dayu/fins/pipelines/filing_upload_publication.py::_canonical_skip_requirements_are_met` 当前要求 `decision.disposition == "keep"` 且 `decision.company_meta_intent is None`
  - UF-FIX10 closeout 明确："no durable mutation" 是 skip 的核心语义
  - Plan 8.3 承认 "等价名称/no-op alias 会在 fresh decision 阶段保持 keep + rollback"，但又为不等价名称开了例外
- **影响**: 违反 UF-FIX10 established contract；可能在并发场景下引入不必要的锁竞争；updated_at 被无意义刷新
- **建议改法和验证点**:
  1. 在 `resolve_upload_company_meta_decision` 中，如果 submitted name 与 canonical name 不等价但没有 identity 变化，应保持 `keep + no intent`，不构造 `preserve_published` intent
  2. Warning 应在 commit 前通过比较 submitted name 与 current published name 生成，而不是依赖 commit outcome
  3. 验证：测试 name-only 不等价场景应保持 rollback，不产生 durable mutation
- **修复风险（低/中/高）**: 中
- **严重程度（高）**: 高

### 002-未修复-中-skip alias commit 与 UF-FIX10 语义不一致

- **位置**: Section 8.1/8.2/8.3 Skip 状态机细化
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**: Plan 细化 skip 为两种：`SKIP + keep` 保持 rollback；`SKIP + preserve intent` 只 stage company intent 并 commit metadata batch。
- **反例/失败场景**: UF-FIX10 的 skip 语义是 "no durable mutation"。Plan 引入了 `SKIP + preserve intent` 分支，这会执行 metadata-only commit。如果两个并发请求都对同一个 ticker 提交不同 alias，一个可能被裁决为 skip（因为 source identity exact），但 plan 允许它执行 metadata commit，这可能与 UF-FIX10 的 arbitration 语义冲突。
- **为什么有问题**: UF-FIX10 closeout 明确："先取得 batch 的 caller 在 fresh state 仍缺失时发布；后取得 batch 的 caller 在任何 company/source mutation 前从 batch-protected authoritative view 重放同一 validator，并且只有在 fresh COMPLETE、company durable facts 已满足、prepared/durable publication identity exact equal 时收敛为 canonical skip。" Plan 的 `SKIP + preserve intent` 分支改变了这个语义。
- **直接证据**:
  - `dayu/fins/pipelines/filing_upload_publication.py::_canonical_skip_requirements_are_met` 当前要求 `decision.disposition == "keep"` 且 `decision.company_meta_intent is None`
  - UF-FIX10 closeout："winner 报告实际 stored originals；loser 保留 requested count、stored=0，不新增 source version，不重写 assets/meta/manifest，不误报 conversion events"
  - Plan 8.2 引入了 `stage` disposition 进入 skip，这在 UF-FIX10 中不存在
- **影响**: 可能导致 UF-FIX10 established arbitration 语义漂移；并发场景下可能出现意外的 durable mutation
- **建议改法和验证点**:
  1. 明确 `SKIP + preserve intent` 是否真的需要执行 metadata commit，还是可以通过其他方式生成 warning
  2. 如果必须执行 metadata commit，需要更新 UF-FIX10 的 skip 语义定义，并验证与现有并发测试的兼容性
  3. 验证：测试两个并发请求，一个 skip 一个 publish，验证 skip 的 metadata commit 不会与 publish 的 metadata commit 冲突
- **修复风险（低/中/高）**: 中
- **严重程度（中）**: 中

### 003-未修复-中-commit_batch 返回类型变更覆盖不完整风险

- **位置**: Section 6.4 Batch commit contract
- **问题类型**: 不可直接实施
- **当前写法**: Plan 要求 `commit_batch` 返回 `CompanyMetaCommitOutcome | None`，并说 "所有 repository implementation 与 test fake 的签名同步更新"。
- **反例/失败场景**: 当前 `commit_batch` 返回 `None`。Plan 列出了需要修改的文件，但没有列出所有 callsites。例如，`upload_filing_test_support.py` 中的 `TrackingBatchingRepository.commit_batch` 需要同步更新，但 plan 的 allowed files 列表中没有明确列出所有测试支持文件。
- **为什么有问题**: `commit_batch` 是一个广泛使用的 protocol method。如果只修改 plan 列出的文件，可能会遗漏某些 callsites，导致类型错误或运行时异常。
- **直接证据**:
  - `tests/fins/upload_filing_test_support.py::TrackingBatchingRepository.commit_batch` 当前返回 `None`
  - `dayu/fins/storage/repository_protocols.py::BatchingRepositoryProtocol.commit_batch` 当前返回 `None`
  - Plan 9.2 列出了 `tests/fins/upload_filing_test_support.py`，但没有明确说明需要更新其 `commit_batch` 签名
- **影响**: 可能导致 pyright 类型错误；可能在运行时出现 unexpected None 返回值
- **建议改法和验证点**:
  1. 在 plan 中明确列出所有需要更新 `commit_batch` 签名的文件，包括测试支持文件
  2. 在 validation plan 中增加一个步骤：`rg -n "def commit_batch" dayu tests` 以确保所有实现都被更新
  3. 验证：pyright 通过，无新增类型错误
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中

### 004-未修复-低-warnings JSON 缺失兼容 fallback 风险

- **位置**: Section 6.6 Pipeline/direct/service public contracts
- **问题类型**: 契约缺失
- **当前写法**: "pipeline parser 对 warnings 做 closed typed parse；缺失按'该 completed result 没有 warning'处理，非数组/未知对象/重复或超过 1 个均 fail-closed。这里的 optional 是当前业务状态的显式可选字段，不是旧 schema 兼容 shim。"
- **反例/失败场景**: Plan 说 "缺失按'该 completed result 没有 warning'处理"，但没有明确说明在 JSON 解析时如何区分 "字段不存在" 和 "字段为 null"。如果解析器对这两种情况都返回空 tuple，可能会掩盖 schema 错误。
- **为什么有问题**: 根据编码硬约束，禁止兼容性代码。Plan 声称 "这里的 optional 是当前业务状态的显式可选字段，不是旧 schema 兼容 shim"，但没有提供足够的细节来验证这一点。
- **直接证据**:
  - Plan 6.6："pipeline parser 对 warnings 做 closed typed parse；缺失按'该 completed result 没有 warning'处理"
  - 编码硬约束："禁止兼容性代码"
  - Plan 没有提供 JSON 解析的具体实现细节
- **影响**: 可能引入隐式的兼容 fallback；可能掩盖 schema 错误
- **建议改法和验证点**:
  1. 在 plan 中明确 JSON 解析的具体行为：`warnings` 字段必须存在，可以是空数组 `[]`，但不能是 `null` 或缺失
  2. 如果允许缺失，需要明确说明这是业务需求，不是兼容 shim，并提供测试用例
  3. 验证：测试 warnings 字段缺失、null、空数组、正常数组、非法值等场景
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低

### 005-未修复-低-LLM/CLI 文案准确性

- **位置**: Section 6.3 Public warning contract
- **问题类型**: 最佳实践偏离
- **当前写法**: 固定文案为 "本次上传未修改已有公司名称；提交的名称与当前名称不同，请确认上传目标公司是否正确。"
- **反例/失败场景**: 文案说 "提交的名称与当前名称不同"，但没有明确说明 "提交名称未生效且保留现有名称"。用户可能误解为 "系统接受了提交的名称，只是和当前不同"。
- **为什么有问题**: 根据 LLM-facing 文本约束，文案必须让模型在最低认知负担下稳定做对下一步动作。当前文案没有明确说明 "提交名称未生效"，可能导致用户误解。
- **直接证据**:
  - Plan 6.3 固定文案："本次上传未修改已有公司名称；提交的名称与当前名称不同，请确认上传目标公司是否正确。"
  - LLM-facing 文本约束："只写模型完成当前任务所需的动作、输入、输出、判断规则和禁止事项"
  - 用户要求："LLM/CLI 文案是否明确说明提交名称未生效且保留现有名称"
- **影响**: 可能导致用户误解；可能让 LLM 无法准确判断下一步动作
- **建议改法和验证点**:
  1. 修改文案为更明确的表述，例如："本次上传未修改已有公司名称；您提交的名称 'X' 与当前名称 'Y' 不同，已保留当前名称。请确认上传目标公司是否正确。"
  2. 或者更简洁："公司名称未变更；提交的名称与现有名称不同，请确认。"
  3. 验证：文案明确传达 "提交名称未生效" 和 "保留现有名称" 两个关键信息
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低

### 006-未修复-低-UploadOperationResult 语义漂移风险

- **位置**: Section 6.5 Internal upload/publication contracts
- **问题类型**: 架构边界
- **当前写法**: `UploadOperationResult` 新增内部字段 `company_meta_commit_outcome: CompanyMetaCommitOutcome | None = None`，并说 "该字段不直接进入 JSON"。
- **反例/失败场景**: `UploadOperationResult` 当前是一个通用的上传操作结果，承载 status、document_id、stored_file_count、file_events、payload。新增 `company_meta_commit_outcome` 字段会把 company-meta 特定语义注入到通用结果类型中，可能导致 semantic ownership drift。
- **为什么有问题**: 根据架构硬约束，"设计下层组件接口时，必须假设上层组件不存在，只考虑上层调用需求，不向上泄漏实现细节"。`UploadOperationResult` 是一个下层组件接口，不应该承载 company-meta 特定语义。
- **直接证据**:
  - `dayu/fins/pipelines/docling_upload_service.py::UploadOperationResult` 当前定义
  - Plan 6.5："`UploadOperationResult` 新增内部字段：`company_meta_commit_outcome: CompanyMetaCommitOutcome | None = None`"
  - 架构硬约束："设计下层组件接口时，必须假设上层组件不存在"
- **影响**: 可能导致 semantic ownership drift；可能让 `UploadOperationResult` 变成 god object
- **建议改法和验证点**:
  1. 考虑使用单独的结果类型或 wrapper 来承载 company-meta commit outcome，而不是修改通用 `UploadOperationResult`
  2. 或者明确 `UploadOperationResult` 的职责扩展，并更新其 docstring
  3. 验证：`UploadOperationResult` 的所有消费者都不直接访问 `company_meta_commit_outcome`，只通过 projection helper
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低

## Open Questions

1. **name-only commit 的必要性**: Plan 声称 "若 intent 只承载不同 submitted name 而没有 identity 变化，仍需进入 commit owner，以 publication-final truth 判断 warning"，但没有充分论证为什么不能在 commit 前通过比较 submitted name 与 current published name 生成 warning。这是否是过度设计？

2. **skip alias commit 与 UF-FIX10 的兼容性**: Plan 引入了 `SKIP + preserve intent` 分支，但没有提供足够的证据证明这与 UF-FIX10 的并发测试兼容。需要验证 UF-FIX10 的现有测试是否会被这个变更破坏。

3. **warnings JSON 缺失的业务需求**: Plan 声称 "缺失按'该 completed result 没有 warning'处理"，但没有明确这是业务需求还是兼容 shim。需要澄清。

## Residual Risks

1. **commit_batch 返回类型变更覆盖不完整**: 可能遗漏某些 callsites，导致类型错误。建议在 validation plan 中增加全面的 callsites 搜索。
2. **skip alias commit 与 UF-FIX10 并发语义**: 可能导致 UF-FIX10 established arbitration 语义漂移。建议增加并发测试覆盖。
3. **name-only commit 的性能影响**: 在高并发场景下，不必要的 metadata-only commit 可能增加锁竞争。建议评估性能影响。

## Plan Review Conclusion

**pass-with-risks**

Plan 整体设计合理，semantic owner 清晰，typed contracts 完整，slices 划分合理。但存在以下风险：

1. **高风险 (001)**: name-only commit 造成不必要 durable mutation，违反 UF-FIX10 "no durable mutation" 语义
2. **中风险 (002)**: skip alias commit 与 UF-FIX10 语义不一致
3. **中风险 (003)**: commit_batch 返回类型变更覆盖不完整风险

建议 implementation agent 在开始前与用户确认：
1. name-only commit 是否真的必要，还是可以在 commit 前生成 warning
2. skip alias commit 是否需要更新 UF-FIX10 的 skip 语义定义
3. commit_batch 返回类型变更的完整 callsites 列表

如果上述风险被接受或有明确解决方案，plan 可以进入 implementation。
