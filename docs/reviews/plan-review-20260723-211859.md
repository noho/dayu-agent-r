## Assumptions tested

1. **Plan assumption**: pre-start candidate freeze 可以在 RUN_STARTED 前产生与 actual AgentRunRequest 完全同源的 digest-verified projection。
   **Tested against**: `start_governed_run_with_starting_attempt_in_transaction` (run_transition.py:1287-1322) 在当前事务内生成 attempt/execution identity，而 manifest 的 `attempt_id`/`execution_id` 是必填 paired 字段。若 sizing 决定 compact 而非 start，该 identity 不会被消耗，但 manifest 已写入了包含该 identity 的 sizing snapshot。
   **Verdict**: 存在时序矛盾 — manifest 需要 attempt identity，但 sizing decision 在 attempt 创建之前。

2. **Plan assumption**: 同一事务内 manifest+fact+start 可以在 CAS miss 时整体 rollback。
   **Tested against**: 当前 `run_write` transaction 在 `_operation` lambda 正常返回（即使返回 `pending_dispatch=None`）后仍会 commit。CAS miss 不抛异常。
   **Verdict**: 若在 `_start_governed_in_transaction` 之前 append manifest+fact，CAS miss 后 manifest+fact 会成为孤立 durable truth。需要显式 rollback 机制。

3. **Plan assumption**: older-anchor keyset scan 可以确定性验证中间 iteration 已完成。
   **Tested against**: 当前 `ITERATION_COMPLETED` 是 `HostPreviewEventType`（lifecycle_events.py:104-109），不是 canonical fact。Engine iteration completion 没有 durable canonical event。
   **Verdict**: 迭代完成不是 durable canonical fact — anchor resolver 无法仅从 durable truth 判定中间 call 是否完成。

4. **Plan assumption**: manifest v2 全量 cutover 只影响 `_runner_call_manifest.py` 单一 owner。
   **Tested against**: manifest 由 `engine_ingest.py` 的 `_runner_call_input_assembled_event_request` 构造 hot payload；hot payload 格式变化影响所有读取 `RUNNER_CALL_INPUT_ASSEMBLED` 的 consumer（tool_trace, dispatch, etc.）。
   **Verdict**: manifest 生产者和消费者分布在 engine_ingest、tool_trace、dispatch 等多个模块；全量 cutover 的 blast radius 比 plan 表述的更宽。

5. **Plan assumption**: fallback 升级为 complete candidate 后，estimator 行为等价于既有 material_view.budget_fragments。
   **Tested against**: `_run_pre_start_governance` (dispatch.py:1746-1754) 使用 `material_view.budget_fragments` 估算，不包含 system message、tool schema overhead 等。complete candidate 会包含这些额外内容。
   **Verdict**: 不是等价替换 — fallback 估算值会系统性增大，可能触发更多 compaction。plan 在 §8.2 expected outcome #4 将其表述为"升级"是诚实的，但行为变化需要更明确的验收信号。

## Findings

### DS-01-未修复-高-pre-start candidate manifest 与 attempt identity 预生成的时序矛盾

- **位置**: Plan §5.3 manifest v2、§5.6 event ordering、§8.2 Slice 1 exact changes #2-#4
- **问题类型**: 状态机漏洞 / 切片过粗
- **当前写法**: Plan 要求 "ordinary pre-start allow candidate 使用预生成的 attempt/execution id写 complete manifest"，同事务内按 `RUNNER_CALL_INPUT_ASSEMBLED -> CONTEXT_BUDGET_EVALUATED -> RUN_STARTED -> ATTEMPT_STARTED` 提交。若 sizing decision 先要求 compact，"该 candidate不是实际 runner call，因此不伪造 RUNNER_CALL_INPUT_ASSEMBLED"。
- **反例/失败场景**:
  1. 为 ordinary candidate 计算 sizing 时，需要完整的 `PreparedRunnerCallCandidate`（含 attempt_id/execution_id）来构造 manifest 的 `sizing_snapshot`。
  2. 但 sizing 结果决定是否 compact 或 dispatch — 如果 compact，该 attempt identity 已生成但不会被任何实际 Runner call 消费，成为废弃 identity。
  3. 如果不在 sizing 前生成 attempt identity，manifest 无法写入 `attempt_id`/`execution_id`（当前 manifest schema 的 required paired fields），导致 manifest 不完整。
  4. 如果先写不含 attempt identity 的 manifest，再在 start 后补充，则 manifest digest 变化 — sizing snapshot 引用的 digest 与最终 manifest 不一致。
- **为什么有问题**: Plan 要求 "actual AgentRunRequest 构造阶段必须读取该 frozen candidate，复核 digest" — 但如果 compact decision 后形成了不同的 candidate（post-compact），该 frozen candidate 的 identity chain 断裂。manifest、candidate、attempt identity 三者之间存在循环依赖：manifest 需要 identity → identity 只在 start 时创建 → start 只在 sizing decision 为 allow 时发生 → sizing 需要 manifest 中的 `E_current`。
- **直接证据**:
  - `RunnerCallHotAtoms` 的 `attempt_id`/`execution_id` 是 required paired fields（`_runner_call_manifest.py:275-276`, `_validate_hot_atoms:1327-1328`）：`if (atoms.attempt_id is None) != (atoms.execution_id is None): raise HostDurableError`
  - `start_governed_run_with_starting_attempt_in_transaction`（run_transition.py:1255-1331）在事务内用 `_new_event_id("attempt")` / `_new_event_id("execution")` 生成 identity
  - `_run_pre_start_governance`（dispatch.py:1636-1839）先估算 sizing，再根据 decision 调用 `_start_governed_in_transaction` 或触发 compact
- **影响**: Slice 1 可能因时序矛盾阻塞 — implementation agent 会发现无法同时满足 "manifest 包含 attempt identity" 和 "sizing decision 在 attempt 创建前" 两个约束。需要 plan 明确解决循环依赖的具体方案。
- **建议改法和验证点**:
  方案 A：将 attempt_id/execution_id 从 manifest required fields 改为 optional（仅 ordinary dispatch manifest 携带），compactor proposal 和 pre-decision candidate 不携带。但这会改变 `_validate_hot_atoms` 的 paired invariant。
  方案 B：引入独立的 `candidate_id`（不绑定 attempt），manifest 的 identity 通过 `candidate_id` 引用 frozen candidate，attempt/execution identity 只在 RUN_STARTED 时分配并通过 `candidate_id` 关联。
  方案 C：在 sizing 前生成 attempt identity，若 compact 则废弃该 identity（不泄露到 durable state 之外）。
  验证：Slice 1 的 stop condition 必须覆盖 "无法在 RUN_STARTED 前冻结与 actual request 严格同一的 candidate"。
- **修复风险（中）**: 需要调整 manifest identity 设计或 sizing 时序，但不触及 sizing formula 本身。
- **严重程度（高）**: Blocking — plan 描述的时序在当前 manifest identity contract 下无法线性实现。

### DS-02-未修复-中-同事务内 manifest+fact append 与 CAS miss rollback 的语义缺口

- **位置**: Plan §5.6 "start CAS/precondition若未更新...transaction必须整体rollback"、§8.3 Slice 2 exact changes #4
- **问题类型**: 状态机漏洞
- **当前写法**: "start CAS/precondition若未更新，包含prepared manifest与fact的transaction必须整体rollback（可用private stale-candidate sentinel退出transaction）；不得像普通 status != UPDATED 返回那样提交孤立manifest/fact。"
- **反例/失败场景**: 在 `_run_pre_start_governance` 的 lambda `_operation` 中，若先 append `RUNNER_CALL_INPUT_ASSEMBLED` + `CONTEXT_BUDGET_EVALUATED`，再调用 `_start_governed_in_transaction`。当 CAS miss（run 状态已被另一个 opener 改变），`_start_governed_in_transaction` 返回 `None`（dispatch.py:2270-2277），lambda 正常返回 `_GovernanceStageResult(pending_dispatch=None)`。`run_write` 收到正常返回值后 commit transaction — manifest 和 fact 被持久化，但没有任何 Run start 消费它们。
- **为什么有问题**: 当前 `run_write` 的语义是 "lambda 正常返回 = commit"；没有 sentinel 机制让 lambda 信号 "本次应 rollback"。plan 提出了 "private stale-candidate sentinel" 但没有描述具体实现方式（自定义异常？特殊返回值？）。
- **直接证据**:
  - `dispatch.py:2270-2277`: `if result.status != StateMutationStatus.UPDATED: return None` — 静默返回 None
  - `dispatch.py:1651`: lambda `_operation` 返回 `_GovernanceStageResult`，不抛异常
  - `run_transition.py:1279-1286`: CAS 检查返回 `INVALID_STATE`，不抛异常
- **影响**: orphan fact 留在 EventLog 中，可能导致 replay/recovery 时发现未消费的 `CONTEXT_BUDGET_EVALUATED` — plan 的 idempotency 逻辑可以处理 "相同 identity 复用"，但 "不同 candidate identity 的孤立 fact" 需要明确分类为 no-op 还是 error。
- **建议改法和验证点**:
  方案：定义专用异常（如 `_StaleCandidateRollback`），在 CAS miss 时抛出；`run_write` 或调用方的 except 子句捕获后 rollback 不 commit。或在 append manifest+fact 之前先执行 CAS，仅 CAS 通过后才 append manifest+fact（此时 fact ordering 变为 start → fact，而非 fact → start）。
  验证：Slice 2 测试必须覆盖 "CAS miss 后 EventLog 中无孤立 CONTEXT_BUDGET_EVALUATED"。
- **修复风险（低）**: 机制选择明确（custom exception 或 reorder），不影响 public contract。
- **严重程度（中）**: 可在 implementation 中解决，但 plan 未提供足够具体的机制描述。

### DS-03-未修复-中-iteration completion 不是 durable canonical fact — older-anchor 扫描缺乏可终止性判定

- **位置**: Plan §5.4 "anchor在**使用时**还必须证明同iteration已有 completed observation"、§5.4 keyset scan "中间 call完全没有 usage时，只要 manifest/link/input lineage都complete，可继续向旧 compatible anchor查找"
- **问题类型**: 契约缺失 / 状态机漏洞
- **当前写法**: anchor resolver 需要证明同 iteration 已有 completed observation；中间 call 的 manifest/link/input lineage 必须都 complete 才可继续向旧 anchor 查找。
- **反例/失败场景**: Engine 在一个 Run 内可能有多次 iteration（tool-calling loop）。若 iteration 0 有合法 usage 但 iteration 尚未结束（`IterationCompletedData` 尚未 emit），Host 尚未收到 `ITERATION_COMPLETED` 事件。此时 resolver 无法从 durable truth 判定该 iteration 是否 "completed" — `ITERATION_COMPLETED` 只是 HostPreviewEventType（lifecycle_events.py:104），不是 canonical fact。如果 resolver 将尚未完成的 iteration 的 usage 当作 completed observation 使用，会使用不完整调用的 usage 作为 anchor。
- **为什么有问题**: plan 的 "iteration completed" 前提条件没有 durable canonical fact 支撑。要么需要把 iteration completion 提升为 canonical fact（扩展 scope），要么需要从现有 durable truth 推导（但当前没有等效信号）。Tool-calling 场景下，一个 Run 可能有多达数十次 iteration，只有最后一次是 "completed ordinary call"。
- **直接证据**:
  - `lifecycle_events.py:104-109`: `HostPreviewEventType.ITERATION_COMPLETED = "ITERATION_COMPLETED"` — preview event，不是 canonical fact
  - `HostContextGovernanceEventType`、`HostRunEventType` 均不含 iteration-level canonical completion event
  - plan §5.4: "usage到达但iteration尚未完成时只是候选 observation，不立即改变当前或过去decision"
- **影响**: anchor resolver 的 "iteration completed" 判定缺少 durable truth 基础。要么需要在 plan 中明确推导方式（如 "ordinary runner call 的 terminal event RUN_SUCCEEDED/RUN_FAILED 隐含 iteration completion"），要么需要将 iteration completion 纳入 scope。
- **建议改法和验证点**:
  在 plan 中明确定义 "iteration completed" 的 durable 判定方式。最简单方案：ordinary runner call 的 terminal state（RUN_SUCCEEDED/RUN_FAILED 等）隐含该 Run 的所有 iteration 已完成。runner-call manifest 的 `runner_call_kind` 区分 ordinary vs. tool_result_continuation 等。
  验证：测试必须覆盖 "tool-calling Run 中 usage 来自尚未完成的 iteration" 场景。
- **修复风险（低）**: 只需 plan 层面的语义澄清，不改变 anchor formula。
- **严重程度（中）**: 可在 plan fix 中收敛，但当前描述不够精确。

### DS-04-未修复-中-fallback 从 material_view.budget_fragments 升级为 complete candidate 的行为变化缺少显式验收信号

- **位置**: Plan §8.2 Slice 1 expected outcome #4 "existing conservative decision行为保持，输入从subset升级为complete candidate"、§5.1 complete candidate adapter
- **问题类型**: 契约缺失
- **当前写法**: "existing conservative decision行为保持" — 暗示 fallback 决策与当前等价。
- **反例/失败场景**: 当前 `_run_pre_start_governance` (dispatch.py:1746-1754) 的 `BudgetEstimateInput` 使用 `material_view.budget_fragments`（不含 system message、tool schema overhead）。complete candidate adapter 按 §5.1 的定义会包含每条 message 的 overhead + tool schema overhead。以典型场景估算：system message (~200 tokens) + tool schemas (~500 tokens per tool × N tools) 可能额外增加 1000-3000 tokens。在 `context_window_size=100000, soft_threshold=65000` 的场景下，这额外 1000-3000 tokens 可能将原本低于 soft threshold 的估算推至 soft threshold 以上，触发原本不会触发的 proactive compaction。
- **为什么有问题**: plan 将行为变化表述为 "输入从subset升级为complete candidate" 并声称 "behavior保持"，但实际估算值会系统性增大。这本身是正确方向（用完整输入替代子集），但需要显式的验收信号来区分 "因为 estimator 输入范围扩大导致的决策变化" 和 "因为 anchor formula 引入的决策变化"。
- **直接证据**:
  - `dispatch.py:1746-1754`: 当前只用 `material_view.budget_fragments`
  - plan §5.1: "每条实际 message 的业务文本作为一个 BudgetTextFragment，每条仍使用既有 message overhead" + "selected tool schema逐项作为既有 tool_schema_fragments"
  - 两者 token 估算差异来自 system message overhead + tool schema overhead + JSON fragment overhead
- **影响**: Slice 1 完成后，即使 method 固定为 conservative_fallback，决策行为也可能与当前不同。Slice 3 集成 anchor 后的 end-to-end 行为对比基准被污染。
- **建议改法和验证点**:
  Slice 1 增加显式验收信号："complete candidate fallback 的 estimated_input_tokens >= 既有 material_view.budget_fragments 的估算值，差值来自 system message overhead + tool schema overhead"。增加对比测试：同一场景下新旧估算值的差异在可解释范围内。
- **修复风险（低）**: 只需增加验证信号。
- **严重程度（中）**: 不阻塞实现，但 review/validation 时可能产生 false positive（把 candidate 范围扩大导致的决策变化误判为 bug）。

### DS-05-未修复-低-context_anchor.py 的 import boundary — 新文件是否可 import durable store

- **位置**: Plan §5.4 "新增 dayu/host/context_anchor.py，只承载 Host-private durable anchor读取与compatibility判定；不进入 Host public API"、§8.4 allowed production files
- **问题类型**: 架构边界
- **当前写法**: context_anchor.py 需要 "按 session event sequence倒序、固定页大小 keyset扫描" 读取 committed manifests、links、usage。
- **反例/失败场景**: 当前 Host 模块中读取 EventLog 的组件（如 `read_api.py`、`dispatch.py`）都通过 `EventLogStore` + `HostTransaction` 访问 durable state。`context_anchor.py` 作为新模块，需要同样的访问模式。但 plan 将其描述为 "Host-private" 且 "不进入 Host public API" — 如果它需要 `EventLogStore` 引用，它必须通过某种方式获取（构造注入？模块级 singleton？）。plan 没有说明 `context_anchor.py` 如何获取 `EventLogStore`。
- **为什么有问题**: 所有需要读 durable state 的 Host 组件目前都通过显式参数传入 `EventLogStore`。plan 应说明 anchor resolver 的依赖注入方式。
- **直接证据**:
  - `dispatch.py`: `self._event_log_store` 通过构造器注入
  - `read_api.py`: 函数接收 `transaction: HostTransaction` 参数
  - `engine_ingest.py`: `self._event_log_store` 通过构造器注入
- **影响**: 低 — implementation agent 可以按现有模式（构造器注入或函数参数）解决。但 plan 应说明 resolver 的 exact interface，避免 implementation agent 引入全局状态或绕过 transaction discipline。
- **建议改法和验证点**: plan §5.4 或 §8.4 明确 context_anchor.py 的函数签名：接收 `HostTransaction` + `EventLogStore` 参数，不持有模块级 mutable state。
- **修复风险（低）**: interface 澄清。
- **严重程度（低）**: 不阻塞。

### DS-06-未修复-低-Slice 2 "policy缺失时不伪造fact" 与 Slice 1 "所有预算仍为conservative" 的语义覆盖

- **位置**: Plan §5.6 "policy缺失时没有合法 sizing result，不产生伪造 fact；existing Run行为保持 'budget governance unavailable'"、§8.2 Slice 1 completion signal
- **问题类型**: 切片过粗
- **当前写法**: Slice 1 只做 candidate/manifest/pairing contract；Slice 2 做 canonical fact + public projection。Slice 2 要求 "conservative fact在完全无usage的session成立"。
- **反例/失败场景**: Slice 1 完成后，`_run_pre_start_governance` 在 policy=None 时走 "allow_without_budget" 路径，直接调用 `_start_governed_in_transaction` 而不做任何 sizing。Slice 2 引入 `CONTEXT_BUDGET_EVALUATED` 后，policy=None 时不能产生 fact。但 Slice 2 的 sizing result 构建需要 policy 来派生 thresholds — policy=None 时 `ContextSizingResult` 的 soft/hard thresholds、utilization、pressure 都无法计算。plan §5.6 说 "existing Run行为保持 'budget governance unavailable'。public activity中的 context_usage 为 None" — 这意味着 policy=None 时既不产生 fact 也不产生 activity，Run 行为与当前完全一致。这是正确的，但 Slice 2 的 owner-level assertion "conservative fact在完全无usage的session成立" 需要限定：仅在 policy 存在时成立。
- **为什么有问题**: assertion 的表述暗示 fact 在所有场景成立，但 policy=None 是合法的生产路径（`dispatch.py:1659-1671`）。
- **直接证据**:
  - `dispatch.py:1659-1671`: `if policy is None: ... return _GovernanceStageResult(pending_dispatch=self._start_governed_in_transaction(...))` — 跳过所有 sizing
  - plan §5.6: "policy缺失时没有合法 sizing result，不产生伪造 fact"

### DS-08-未修复-低-request_semantics_digest 中 supports_stream_usage 的双重角色风险

- **位置**: Plan §5.2 "supports_stream_usage 出现在 request semantics snapshot只表示 request shape 可能变化；**它不参与 usage presence判断**"
- **问题类型**: 契约缺失 / 过度耦合风险
- **当前写法**: plan 明确 `supports_stream_usage` 不参与 usage presence 判断，只作为 request semantics digest 的一部分影响 anchor compatibility。
- **反例/失败场景**: `supports_stream_usage` 出现在 request semantics digest 中意味着：如果 provider 不变但 `supports_stream_usage` 从 True 变为 False（例如配置变更），request semantics digest 改变 → anchor 失效 → fallback。但实际上 provider 可能仍在流式响应中返回 usage（如 MiMo），`supports_stream_usage=False` 只是不发送 `include_usage=true` 扩展参数，不影响 usage 是否实际返回。这种情况下 anchor 失效是 false negative — 本应 compatible 的 anchor 被误判为 incompatible。
- **为什么有问题**: plan 已明确 "supports_stream_usage 不参与 usage presence判断"，但把它放入 request semantics digest 意味着它仍影响 compatibility。这是一个 subtle tension：request shape 变了（不再发送 stream_options），但 actual usage behavior 没变（provider 本来就不需要 include_usage 才返回 usage）。当前设计会导致不必要的 fallback。
- **直接证据**:
  - plan §5.2: request_semantics_digest 覆盖 `supports_stream_usage`
  - plan §5.4: compatible 必须全部相等 → 包括 request semantics digest → 包括 `supports_stream_usage`
  - design.md §25: "supports_stream_usage 只门控是否发送 OpenAI stream_options.include_usage=true 扩展，不是 usage availability predicate"
- **影响**: 低 — 配置变更场景不常见；即使 fallback 也只是回退到 conservative estimate，不会导致 Run 失败。但这是 plan 自洽性上的一个 tension。
- **建议改法和验证点**: 考虑将 `supports_stream_usage` 从 request_semantics_digest 中排除，或将其标记为 "informational, not affecting compatibility"。如果保留在 digest 中，需在 plan 中说明理由（"request shape 的任何变化都应 invalidate anchor，即使 usage presence behavior 不变"）。
- **修复风险（低）**: 从 digest 中移除一个字段，或增加一条说明。
- **严重程度（低）**: 不阻塞 — 设计 choice 在 spec 层面是 conservative-safe 的。

## Coupling assessment: 两项独立修改是否被重新耦合

plan 将两项独立修改（usage-anchored adaptive sizing 与 CONTEXT_BUDGET_EVALUATED + Host→Service projection）通过共享 `ContextSizingResult` 关联。这个共享是必要的 — fact 的 `predicted_input_tokens` 必须等于 sizing 决策的实际依据。plan 正确地通过 "Slice 2 只用 conservative_fallback 交付 fact+projection" 来证明事实独立于 anchor 算法。两项修改在三层上独立：

1. **类型层面**: `ContextSizingResult` 的 method 字段在 Slice 2 固定为 `conservative_fallback`，Slice 3 才引入 `usage_anchored`
2. **测试层面**: Slice 2 要求 "conservative fact在完全无usage的session成立" — 绕过 anchor 代码路径
3. **回滚层面**: Slice 3 可以单独回滚到 conservative，不破坏已交付的 fact/public contract

**结论**: 没有发现重新耦合的证据。共享 `ContextSizingResult` 是符合 semantic ownership 的正确设计（fact 和 decision 必须同源）。

## Overengineering review

plan 没有引入 tokenizer、provider adapter、动态 ratio、background scheduler、新数据库表、或 migration framework。新增的 `context_anchor.py` 是单一职责的 durable anchor 读取模块，`ContextSizingResult` 是单一 typed result，`HostContextUsageView` 是 7 字段的 public DTO。这些都是设计明确要求的最小增量。

未发现过度设计。

## Optimal-solution review

plan 的核心选择是 signed-delta formula：`P_current = U_anchor + (E_current - E_anchor)`。替代方案包括：
- 纯 usage-based：直接用上次 usage 作为预测（不响应输入变化）
- 纯 estimator-based：忽略 usage，始终用 conservative estimate
- 混合 ratio：在 usage 和 estimate 之间做加权

plan 的 signed-delta 方案是最小、最可解释的选择：它只用 usage 校正 estimator 的基线偏差，用 estimator 的 signed delta 跟踪输入变化。比纯 usage-based 更 responsive，比加权方案更简单。
