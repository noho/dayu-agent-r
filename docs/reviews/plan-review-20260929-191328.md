### F1（阻塞，高）：O14/O15 依赖合同无法确认；且 O14 显式弃权 plan 委派给它的那一格

**主张**：plan 把「显式 create/update × 目标存在性 × overwrite × tombstone 组合」整体委派给「已实施的 O14/O15 共享 action/target owner」，并把「O14/O15 已接受且实现已集成」列为实施硬前提。该委派与硬前提在本机**没有可核实的对象**，且被委派的 owner 明确声明不覆盖其中一格。

**直接证据**：
1. 本机不存在 O14/O15 工作区：`ls -d /private/tmp/dayu-upload-o14 /private/tmp/dayu-upload-o15` → `No such file or directory`；`ls -d /private/tmp/*o14* /private/tmp/*o15*` → 零匹配（O12 工作区则存在并可实读）。
2. 主工作区只有裁决、没有计划：`/Users/leo/workspace/dayu-agent-r/docs/reviews/` 有 `upload-material-um-o14-oracle-adjudication.md`、`upload-material-um-o15-oracle-adjudication.md`；`docs/gateflow/` 中 `o14`/`o15` 零匹配。对比 plan §2 对 O12 给出精确绝对路径 + SHA，对 O14/O15 **没有任何 artifact 路径或 SHA**。
3. O14 状态与弃权原文：O14 文件头「本文件登记最终裁决与修复方向，**不代表产品修复已获执行授权**」，`UM-O14-F01` 状态「**用户接受修复方向，尚未实施**」；Accepted 行为第 4 条：「**已删除 tombstone 上的显式 `create` 未经本组覆盖，本项不推断其语义。**」
4. plan 的委派原文（§3 第二表第一行）：「显式 create / update 的目标存在性、overwrite 与 tombstone 组合 | **由已实施的 O14/O15 共享 action/target owner 先裁决**；active create-existing 无 overwrite 在该 owner 前置 typed conflict，不进入 O18 preparation | O18 不定义过渡 skip、`FileExistsError` 或临时动作表」。
5. 其余上游 owner 也不接这一格：O13 accepted 只覆盖重复 delete 的 `deleted_at` 幂等（`UM-A08`）；O12 accepted 只覆盖 tombstone 的 `auto`→`update`（O12 plan `:89`）与 material 的 source/post-company guard，未定义 tombstone 上的显式 `create`。

**失败场景**：若按 plan 实现并进入验收，`tombstone + 显式 create`（无 overwrite）这一格在 O14/O15 已集成后仍无 owner 承诺：既可能继续落进 O18 的 prepare 期 skip 路径（违反 O14 已接受的「create 不得 skip」精神与第二表自身「O18 不定义过渡 skip」的边界），也可能被某市场入口自行 typed 拒绝而与另一市场不一致。plan §4.1 要求「实施前核对 O14/O15 action/target 准入的实际 public 签名」，但没有可核对的签名；一旦 O14/O15 的最终实现在该格上做出与 plan 第二表不同的选择，plan 的表与验收测试（§6 的八格与 11 步 canary）会在 implementation gate 才暴露矛盾。

**为何算 blocker 而非风格**：本轮停止条件明确「依赖合同无法确认时停止正向通过，报告直接证据，不补兼容猜测」。这一条既无法确认（无 artifact、无 SHA、非 accepted plan），又被上游 owner 自己划出范围外，属于 plan 自己的 §5 规则「若核对调用图发现必需路径不在白名单／依赖不足，先修订 plan 并 review」应当触发的场景。

**建议最小修订**：
1. plan §2/§4.1/§7 给出 O14/O15 计划 artifact 的绝对路径 + SHA（若已存在），或明确写成「O14/O15 目前只有 oracle accepted 方向、尚无 plan/实现」，并把实施硬前提改写为「O14/O15 plan accepted 且 implementation 集成后，以其实际 public contract 重核本 plan 第二表」。不得把 oracle 裁决的「修复方向」当作已实施的准入真源。
2. 第二表第一行显式标注 `tombstone + 显式 create` 无 owner，或把该行收窄为「active 目标存在性（create-existing）」，并把 tombstone×create 登记为 plan 级开放项与下一 owner 裁决点（O13/O14/O15 交界），不留在「由 O14/O15 先裁决」的模糊表述里。

### F2（中）：O12 材料 batch precondition 的注册范围只写了 skip 与 metadata mutation，未覆盖 delete 与常规内容发布 batch

**主张**：plan §4.3 把「O12 precondition 注册 owner」的叙述只落在两条新路径（拟 skip 的只读比较、metadata mutation 的短 batch），§7 进一步把 O12 guard 的职责限定为这两处；但 O12 的 accepted 合同是**每个材料 batch** 都注册两项 precondition，而 delete 与常规内容发布同样走 `commit_prepared_upload_batch` → 同一个材料 batch 契约。

**直接证据**：
1. O12 accepted plan（SHA `48e0598b…`）`:47`：「写侧只增加两种直接参数化、batch-scoped precondition：公司 batch 注册 admission 的 `expected_company_meta`…；**材料 batch** 注册 admission 的 `expected_source_state`…和公司阶段完成后的 `expected_company_meta`」；`:67`：「返回 prepared mutation 时开启**材料自己的 batch**，注册 admission expected source 与 post-company expected meta」——未把 delete 或 `ok` 排除在外。
2. 现行代码：delete 也经 `_PreparedDeleteMutation` → `publish_prepared_upload` → `commit_prepared_upload_batch`（`docling_upload_service.py:583-600`、`:1382-1435`），即同一材料 batch 形态；`_PreparedDeleteMutation` 目前**不携带**任何 admission 快照或 precondition。
3. plan 侧：§4.3 的注册表述只出现于「拟 skip 无 mutation 时」与「metadata mutation 时」两处；§7 写成「O12 guard 同时保护本项 metadata-only 条件发布和 prepare 期拟 identical skip 的报告前 source/company 同版验证」；§6 的真实仓储交错只有 ①metadata-only ②skip 两条，**delete 路径既无 precondition 叙述也无交错验收**。
4. 但 §3 终态表仍承诺 `deleted` 的 `published_amended` 为「取 tombstone 上最后发布 meta」。

**失败场景**：A 持 admission 快照发起 delete；B 在 A 的材料 commit 前成功切换 amended（`true`）并发布；A 的 delete batch 若未注册 `expected_source_state`，storage 不会 typed 拒绝，A 会把 tombstone 写在 B 的新状态之上，且 A 报告的 `deleted/published_amended` 来源（admission 快照 vs 提交后 tombstone）在 plan 中未钉死。这正是 plan 已对 `metadata_updated` 与 `skipped` 显式关闭的同一类陈旧窗口，delete 却留着。同一问题也适用于 `ok` 的常规内容发布 batch（异指纹四格）。

**建议最小修订**：§4.3 改写为「**每个材料 batch**（metadata mutation、delete、常规内容发布）都在批次内注册同一组 `expected_source_state` 与 post-company `expected_company_meta`；admission 持有的 typed 快照是唯一输入」，并在 §6 增加 ③ delete 交错的真实仓储验收（A 拟 delete / B 切换标记 commit / A commit 必须 typed stale 且 B 的业务树不变），或显式说明 delete 为何可以不注册（需给出与 O12 合同一致的论证，而不是省略）。

### F6（低）：§3 的「不安全指纹」例外对 material 不可达，与现行 fingerprint owner 不同源

**主张**：§3 末段与 §8 为「`identical_skip_safe` 不成立」保留了例外路径（「则八格的『同指纹』路径不适用…不能保证保版」），但现行 owner 对 material 恒置 `identical_skip_safe=True`，该例外永远不会触发。

**失败场景**：implementation gate 按 §6 要求「实施前以真实构造与测试核对」该例外时，会发现无法在 material 上构造出该状态；若实现者据此为 material 加一条指纹安全性分支，反而会改动现有 fingerprint owner 的语义（plan 明确说「不另造 O18 版本规则」）。

### F7（低）：§8 对 O13 交界事实的定性不准确

**主张**：§8 写「O13 重删 `skipped` 的 0 文件结果若与本项 `skipped requested>=1` 相撞，合流时回到终态 owner 裁决」，把一个未经 O13 裁决的状态记为既有事实，且未能识别该计数约束本来就是现行代码。

**直接证据**：

**建议最小修订**：改为「O13 重复 delete 的终态为 `deleted`、`stored=0`、`requested=0`；本项 `skipped` 的 `requested>=1` 是现行 `FinsUploadResultSummary` 既有约束，O18 不改。合流只需回归 O13 首次/重复 delete 与本项 delete 的 `published_amended` 同源」。

## 4. Open questions

1. **`UploadOperationResult.status` 与终态字符串的关系**：§3 写「`UploadOperationResult.status`、SEC/CN/HK pipeline JSON `status`、`FinsUploadPipelineResult.status`、`FinsUploadResultSummary.status` 均为此精确字符串」（主语为 `metadata_updated`），这一句对 `metadata_updated` 成立；但现行 `UploadOperationResult` 的成功态字符串是 `"uploaded"`（`docling_upload_service.py:782`），由 `_resolve_upload_status` 转成 `"ok"`。请 plan 明确：material 的成功态是否保持 `UploadOperationResult.status="uploaded"`（不得为了「统一字符串」把它改成 `ok`，那会改动 filing 行为，与「material 外原有状态与计数合同不变」冲突）。当前文本不构成错误，但容易被实现者读成「四个表面共用一个字符串」。
2. **metadata-only 的 staged meta 构造与 `previous_meta` 传递**：§4.2 说 `_PreparedMaterialMetaMutation`「只携稳定身份、业务目标 amended 与构造 staged meta 必需的业务字段；不携、也不从 `previous_meta` 或 raw JSON 推断 opaque revision」。请明确「必需的业务字段」是否等于 admission business meta 的全量（`replace_source_meta` → `_prepare_complete_source_meta` → `MaterialManifestItem.from_source_meta` 需要完整 provenance/身份/时间/文件字段才能通过严格校验）。若只传子集，`from_source_meta` 与 provenance 校验会失败；建议改成「携带 admission 的完整 business meta（不含 opaque revision）」并保持同时不违反「不推断 revision」。
3. **§3 混合列表的分键名方案**：material 用 `published_amended`、filing 用 `amended` 同列于一个列表，是否需要 §6 追加「同 `document_id` 概念在列表项上可能只出现一个键」的负向断言（即确保 material 项不出现裸 `amended`、filing 项不出现 `published_amended`）？plan §3 的正反名单已足够，但 §6 只说「逐面检查键名」，未说明是否逐项断言「另一键必须缺席」。
4. **`metadata_updated` 是否需要进入 `warnings` 白名单**：现行 `FinsUploadResultSummary`/`FinsUploadPipelineResult` 只允许 `ok`/`skipped` 携带 warning（`:1873-1877`、`:1744-1748`）。material 目前不产生 company metadata warning（`from_pipeline_json` 对 material 显式禁止，`:1780-1781`），故预计不需要扩展；请 plan 确认，避免实现者为 `metadata_updated` 顺手放宽该闭集。

## 6. 判定

**fail**

理由：
1. F1 属本轮停止条件「依赖合同无法确认」：O14/O15 无任何可核实计划 artifact（无工作区、无 `docs/gateflow` 计划、无论文路径/SHA），且 O14 的 accepted 文本显式弃权 plan 委派给它的 `tombstone × 显式 create` 格。plan 若不修订该依赖表述与第二表范围，implementation gate 的硬门槛无对象、表内有一格无 owner。
2. F2/F3/F4 是同一类问题在另外三处的表现：guard 契约的注册范围与 O12 合同不一致（delete/内容发布批漏注册）、LLM-facing read 说明无可落地白名单表面、以及被反复引用的 read「详情」表面不存在——都会在 implementation/验收 gate 才暴露，属于应当在 plan gate 闭合的缺口。
3. plan 的核心机制（同字节切标记无 overwrite metadata-only、带 overwrite 强制重转重发而版本按指纹保版、八格与现行 `_can_skip_upload`/`_resolve_document_version` 同源、`requested_amended`/`published_amended` 的三域拆分、`metadata_updated` 的计数与 completed 映射、A16/A17 形态的 CLI canary、fresh schema fail closed）经 C1–C22 核对**成立**，无需推翻方向；F5–F8 为低严重度或信息级，可在同一轮修订中一并处理。

**建议下一 entry**：Sol 仅修 plan（F1–F4 必需，F5–F8 建议一并），再对同 SHA 做 Kimi/MiMo 双路 re-review；未通过前不实施、不提交。本 review 不构成 plan gate 通过，也不代表双路有效复审完成。
