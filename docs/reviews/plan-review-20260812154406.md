### Finding F01：`DoclingCancellationInput` Protocol 与现有 `Callable[[], bool]` 存在接口漂移

**攻击目标**：plan §6.1 的 `DoclingCancellationInput(Protocol)` 定义 `is_cancelled()` 方法。

**直接证据**：

- `cn_download_protocols.py:44-70` 的 `CnDoclingConversionRunner` 使用 `cancellation_checker: Callable[[], bool]` 作为参数。
- `docling_upload_service.py:40` 定义 `UploadCancellationChecker: TypeAlias = Callable[[], bool]`。
- `cn_docling_process.py:99` 的 `convert_pdf_to_docling_json` 接收 `cancellation_checker: Callable[[], bool]`。
- `ingestion_runtime.py` 的 `_RuntimeJobCancellationChecker` 和 `_DirectCancellationChecker` 实现 `__call__() -> bool`。

**问题**：plan 要求新增 `DoclingCancellationInput.is_cancelled()` 方法，但现有整个取消协议使用 `Callable[[], bool]`（即 `__call__`）。plan §6.1 提到 "`_RuntimeJobCancellationChecker`、`_DirectCancellationChecker` 增加显式 `is_cancelled()`"，但这创造了**双接口问题**：

1. download workflow 的 `_required_cancellation_checker` 返回 `Callable[[], bool]`。
2. upload service 的 `UploadCancellationChecker` 是 `Callable[[], bool]`。
3. 新 converter 接收 `DoclingCancellationInput`（`is_cancelled()` 方法）。
4. 需要为每个 consumer 写 adapter 将 `Callable` 转为 `DoclingCancellationInput`。

这违反了 AGENTS.md "设计公共契约优先使用直接传参数的朴素接口"。一个 `Callable[[], bool]` 已经是 typed、closed、无歧义的取消信号；新增 Protocol 只为加一层 `is_cancelled()` 包装没有充分理由。

**material-finding / needs-evidence**：plan 应说明为何 `Callable[[], bool]` 不足以作为 converter 的取消输入，或者将 `cancellation` 参数类型改为 `Callable[[], bool] | None`，与现有生态一致。

### Finding F02：`DoclingConversionFailureKind` 的 child 异常到 kind 映射未定义

**攻击目标**：plan §7.3 的 closed error enum 和 IPC descriptor failure mapping。

**直接证据**：

- `cn_docling_process.py:54-88` 的 `_CnDoclingProcessTarget.__call__` 捕获 `DoclingRuntimeInitializationError` 后重新 raise，其它异常包装为 `RuntimeError("Docling conversion failed")`。
- `cn_docling_process.py:234-240` 的 `_read_and_validate_output` 对 `InterruptibleProcessFailed` 只检查 `error_type` 和 `exitcode`，不区分 failure kind。

**问题**：plan 定义了六种 `DoclingConversionFailureKind`（`CONVERTER_CONSTRUCTION`、`CONVERTER_EXECUTION`、`RESULT_SERIALIZATION`、`IPC_PROTOCOL`、`CHILD_CRASH`、`CLEANUP`），但**没有定义 child 内部如何产生 failure kind 到 IPC descriptor 的映射**。

child target 当前只抛 `DoclingRuntimeInitializationError`（construction）或 `RuntimeError`（execution）。但 child 如何区分 `CONVERTER_EXECUTION` 和 `RESULT_SERIALIZATION`？如果 `json.dumps` 失败是 `RESULT_SERIALIZATION`，那 child 需要在 catch 中分类异常并写入 descriptor。plan 没有说明 child 的异常捕获和分类策略。

如果 child 不主动分类，所有异常都变成 `CHILD_CRASH`（runtime 的 `InterruptibleProcessFailed`），那么 `CONVERTER_CONSTRUCTION`、`CONVERTER_EXECUTION`、`RESULT_SERIALIZATION` 三种 kind 就永远无法通过 IPC descriptor 产生，变成死代码。

**material-finding / needs-evidence**：plan 应补充 child target 的异常捕获和 descriptor 写入策略，明确哪些异常映射到哪种 kind，以及 child 如何在不泄漏 traceback/path 的前提下产生 bounded message。

### Finding F03：`prepare_upload` async 化与 sync producer thread 私有 loop 的跨线程 token 可见性

**攻击目标**：plan §6.2 的 "将 `DoclingUploadService.prepare_upload`、`_build_pending_assets` 改为 async"。

**直接证据**：

- `ingestion_runtime.py:3024-3105` 的 `_produce_direct_upload` 在 producer thread 内同步调用 `self.upload_runner.run_upload(request, cancellation_checker=...)`。
- `ProductionFinsUploadRunner.run_upload` 是同步方法，内部调用 pipeline 的同步 upload workflow。
- `docling_upload_service.py:184-300` 的 `prepare_upload` 是同步方法。
- plan §6.2 说 "现有 sync pipeline facade 继续在 producer 线程内运行整个 async stream"。

**问题**：plan 要求 `prepare_upload` 变为 async，但 `_produce_direct_upload` 运行在同步 producer thread 中。plan 说 "不在 service 内调用 `asyncio.run`，不建立嵌套 event loop"，但没有说明：

1. **谁创建 producer thread 的私有 event loop？** 当前代码中，producer thread 由 `threading.Thread` 启动，运行同步 `_produce_direct_upload`。如果 `prepare_upload` 变为 async，producer thread 需要一个 event loop 来 await 它。
2. **`DoclingConverter.convert_to_json_bytes` 是 async 的**（plan §6.1），它在私有 loop 上 await `InterruptibleProcessHandle.wait()`。但 CLI 主 loop 的 `CancellationToken` 如何传播到 producer thread 的私有 loop？plan 说 "通过加锁的 direct cancellation state 让 producer 线程看到 `is_cancelled()`"，但没有说明这个 "加锁的 direct cancellation state" 的具体实现。
3. **`_DirectCancellationChecker` 当前是 `__call__` 方法**，它读取 CLI 主线程设置的 cancellation flag。如果 converter 在 producer thread 的私有 loop 上运行，`is_cancelled()` 需要跨线程读取同一个 flag。Python 的 `threading.Event` 或 `bool` 在 CPython 下由于 GIL 是安全的，但 plan 没有明确这个保证。

**material-finding / needs-evidence**：plan 应补充：(a) producer thread 如何获得 event loop；(b) 跨线程 cancellation state 的具体同步机制；(c) `asyncio.run_until_complete` 或等价机制在 producer thread 中的使用方式。

### Finding F04：late cancel 与 committed summary 的竞态窗口未完整覆盖

**攻击目标**：plan §9-10 的 publication first-committer boundary 和 terminal arbitration。

**直接证据**：

- `ingestion_runtime.py:3076-3105` 的 `_produce_direct_upload`：先 `run_upload` 获取 summary，然后 `_upload_completed_progress_type(summary)` 发 progress，然后检查 `cancellation_checker()`。
- plan §10.2 说 "返回 `FAILED`/`COMPLETED` 即表示 workflow terminal 已经 first-commit。因而 `claim_upload_summary` 不得再用随后读取到的 cancellation flag 重解释非 cancelled summary"。

**问题**：plan 的 first-committer 规则假设 workflow 在返回 summary 前已完成 publication commit。但当前代码中：

1. `DoclingUploadService.publish_prepared_upload` 在 `_store_upload_assets` 中执行 storage 写入，返回 `UploadOperationResult`。
2. caller（如 `sec_upload_workflow`）拿到 result 后构建 `FinsUploadResultSummary` 并返回。
3. `_produce_direct_upload` 拿到 summary 后，先发 progress，再检查 cancellation。

**竞态窗口**：如果 `commit_batch` 成功后、summary 返回前 cancellation 到达，workflow 应该返回 `COMPLETED` summary（因为 commit 已成功）。但 plan 没有明确 workflow 层如何在 commit 后阻止 cancellation 把 summary 改为 `CANCELLED`。

具体来说，`_PreparedAssetMutation` 保存了 `cancellation_checker`，`publish_prepared_upload` 在 `_store_upload_assets` 中多次调用 `_is_cancelled(cancellation_checker)`。如果 cancel 在 commit 成功后、`publish_prepared_upload` 返回前到达，`_store_upload_assets` 可能在 commit 后的 `_is_cancelled` 检查中返回 cancelled result，覆盖已成功的 commit。

**material-finding / needs-evidence**：plan 应明确：(a) workflow 在 commit 成功后必须忽略 cancellation 并返回 `COMPLETED`；(b) `publish_prepared_upload` 中 commit 后的 `_is_cancelled` 检查应删除或改为只影响 pre-commit 路径；(c) 或者 `commit_started` 标志的具体设置时机和传播方式。

### Finding F14：`ProcessDoclingConverter` 的 "无跨调用可变状态" 保证与并发安全

**攻击目标**：plan §6.1 的 "`ProcessDoclingConverter` 不保存 operation process/temp/cancellation 状态"。

**直接证据**：

- plan §6.1 说 "所有状态均为单次调用局部变量。因此 DefaultFinsRuntime 可以共享同一实例，而无需引入并发调度器"。
- plan §3.2 说 "并发行为本身仍是非目标"。

**问题**：plan 假设 `ProcessDoclingConverter` 的无状态设计使其可以安全共享。但 `convert_to_json_bytes` 会创建 temp directory、spawn child process、使用 IPC queue。如果两个调用同时发生，它们各自的 temp directory 和 child process 是独立的，不会冲突。

但 plan 没有明确 `InterruptibleProcessHandle` 是否线程安全。如果两个 async 调用在同一个 event loop 上并发运行，`InterruptibleProcessHandle` 的内部状态（如 `_process`、`_queue`）是否需要同步？

从 `interruptible_process.py` 的实现看，每个 `InterruptibleProcessHandle` 实例管理一个独立的 child process，实例间无共享状态。因此并发调用是安全的，只要每次调用创建新的 handle 实例。

**material-finding / accepted-candidate**：plan 的假设正确，但应在 §6.1 或 §8 中明确 "每次 `convert_to_json_bytes` 调用创建新的 `InterruptibleProcessHandle` 实例，实例间无共享状态"。

**攻击目标**：plan §10.3 的 durable job terminal 修正。

**直接证据**：

- `ingestion_runtime.py:3522-3537` 的 `_run_upload_job`：先 `run_upload` 获取 summary，再 `_upload_completed_progress_type(summary)` 发 progress，再 `self.job_store.read_job(job_id)` 检查 `cancellation_requested`。
- plan §10.3 说 "移除 runner 返回后先 completed 再读 job record 的顺序"。

**问题**：这是 plan 要修复的核心 bug 之一。当前代码中，如果 runner 返回 `status="uploaded"` 的 summary，先发 `_PROGRESS_UPLOAD_COMPLETED`，然后读 job record 发现 `cancellation_requested=True`，再发 `_save_cancelled`。这导致 job 既有 completed progress 又有 cancelled terminal。

plan 说 "cancelled summary 调用 `save_cancelled_if_active`，且不追加 completed progress"。但 plan 没有明确：如果 runner 返回 `status="uploaded"`（非 cancelled），但 job record 显示 `cancellation_requested`，应该怎么处理？

按 plan 的 first-committer 规则，runner 返回非 cancelled summary 意味着 workflow 已完成 publication commit。此时 late cancel 不应回滚。但当前代码在 `_run_upload_job` 中，runner 返回后读 job record 的 `cancellation_requested` 会覆盖 summary。

**material-finding / needs-evidence**：plan 应明确：runner 返回非 cancelled summary 后，`_run_upload_job` 应忽略 `cancellation_requested`，直接按 summary 的 terminal disposition 保存。这与 direct path 的 late cancel 处理一致。

## 3. 特殊 Lens 评估

### Architecture Boundary

- plan 正确遵守 `UI -> Service -> Host -> Engine` 分层。
- `dayu.runtime` 不 import Fins/documents，Fins converter 可依赖 runtime 和 documents。
- Host/Engine 不参与 direct upload lifecycle。
- **评估**：architecture boundary 正确。

### Best Practice

- 使用 Protocol 而非 ABC 定义 converter 接口。
- frozen dataclass 用于 config/result。
- closed enum 用于 failure kind。
- **评估**：整体 best practice 良好，但 `DoclingCancellationInput` Protocol 的必要性存疑（见 F01）。

### Optimal Solution

- 共享 converter 替代两套 runner 是正确方向。
- first-committer boundary 是正确的 publication 语义。
- **评估**：方向正确，但 async 化的实施路径需要更详细的 bridge 设计（见 F03）。

### Overengineering

- `DoclingCancellationInput` Protocol 可能过度设计（F01）。
- `DoclingConversionFailureKind` 六种 kind 中，`CONVERTER_CONSTRUCTION`、`CONVERTER_EXECUTION`、`RESULT_SERIALIZATION` 可能无法通过 IPC 产生（F02）。
- child descriptor 的 versioned schema 可能过度设计（当前 runtime 已有 size/digest 校验）。
- **评估**：轻度过度设计，主要集中在 cancellation input 和 failure kind。

### Overcoupling

- `cn_download_protocols.py` 在 S1 和 S2 中都出现，可能导致 slice 间耦合（F05）。
- S2 修改大量既有测试文件，可能引入过度耦合。
- **评估**：slice 间的文件耦合需要更清晰的边界。
