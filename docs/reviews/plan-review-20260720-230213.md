## Findings

### 01-未修复-中-切片原子性论证不成立，三步迁移更安全

- **位置**: §7 Slice 1 "切分理由"
- **问题类型**: 非最优方案
- **当前写法**: plan 声称"不能把'删除 reasoning durable row'和'CLI 接入 transient reasoning'分成两个可接受 production commit；前者先落地会直接丢失 `--thinking`，后者先落地会产生 durable/transient 双真源或重复输出"，因此必须一次性原子完成 10 个生产文件的修改。
- **反例/失败场景**: 三步迁移完全可行且更安全：
  1. **Step A**: 新增 transient hub / publisher / subscription / public types；`_ingest_validated` 对三类 delta 统一走 transient publish，但**保留** `REASONING_DELTA → PREVIEW` 的 durable 分支。此时 CLI 从 EventLog 读到 reasoning row，thinking 正常工作；transient fanout 存在但 Service/CLI 尚未消费。无用户行为变化。
  2. **Step B**: Service/CLI 迁移到消费 `HostTransientDelta` 中的 `HostReasoningDelta`。由于 Step A 已让 transient hub 生产 reasoning delta，CLI 可以从新路径读到 thinking。durable PREVIEW row 仍在，形成冗余但不是双真源——Service 只从一个路径消费。
  3. **Step C**: 删除 `REASONING_DELTA → PREVIEW` 分支和相关投影。CLI 已从 transient 路径消费，删 row 不影响 thinking。
- **为什么有问题**: plan 的论证逻辑有漏洞："后者先落地会产生 durable/transient 双真源"——但 Service 只从一个路径消费（transient），durable row 存在但不被读取，不是"双真源"。原子方案一次性修改 10 个文件，implementation agent 上下文负担大，任何一步出错都会导致整个 slice 不可用。三步迁移每步都可独立验证、独立回滚。
- **直接证据**: plan §7 Slice 1 切分理由全文；`engine_ingest.py` 中 `_ingest_validated` 的分支结构允许 REASONING_DELTA 同时走 durable 和 transient 两条路径。
- **影响**: implementation agent 在 10 个文件中同步修改时容易出错；reviewer 上下文过大可能遗漏边界问题；若 Slice 1 实现失败，回滚成本高。
- **建议改法和验证点**: 将 Slice 1 拆为 2–3 个子步骤（可仍在同一个 plan slice 内按序实施，但每个子步骤有独立验证点）。Step A 验证：三类 delta 的 recording publisher 均收到调用，EventLog reasoning row 仍存在，CLI thinking 正常。Step B 验证：CLI 从 transient 路径收到 thinking，`--thinking` 正常，`--no-thinking` 抑制。Step C 验证：reasoning row 为 0，thinking 仍正常。
- **修复风险（低/中/高）**: 低。不改变 plan 的目标或非目标，只调整实施顺序。
- **严重程度（低/中/高/中）**: 中。不阻塞 plan 可行性，但增加实施风险。

### 02-未修复-低-durable cursor future 失败路径未明确

- **位置**: §4.2 Public watch API、§5.3 Watcher 并发与生命周期
- **问题类型**: 契约缺失
- **当前写法**: plan 描述 attach 语义为"调用 `watch_session_events` 时必须同步完成 public lifecycle gate、Session 存在性检查所需 durable cursor 请求以及 transient subscription 注册，再返回 iterator"。但未说明 durable cursor future 失败时消费者看到什么。
- **反例/失败场景**: 当前代码 `watch_session_events` 通过 `_durable_actor.submit(lambda: _session_live_event_start_cursor(...))` 获取起始 cursor。若 durable actor 已关闭或 Session 不存在，该 future 会抛异常。plan 要求"验证失败时 `finally` detach"，但未明确消费者看到的错误类型：是 `HostApiError`、`HostClosedError`、`NoSuchSessionError` 还是 generator 首次 `__anext__` 时的裸异常？
- **为什么有问题**: implementation agent 需要知道 cursor 失败时 iterator 的精确行为才能正确实现 `finally` 清理和错误传播。若实现不一致，Service 可能收到未预期的异常类型。
- **直接证据**: `open_host.py` `watch_session_events` 当前实现中 cursor future 的 done callback `_observe_watch_cursor_future` 不处理异常；`_watch_session_events` 内部 await cursor_future 时异常会直接传播到 generator。
- **影响**: 低。当前代码已有异常传播路径，plan 只需确认不改变该行为。但若 implementation agent 试图"改进"错误处理，可能引入不一致。
- **建议改法和验证点**: 在 §4.2 或 §5.3 补一句："cursor future 失败时，iterator 在首次 `__anext__` 时抛出 cursor 解析异常（当前为 durable actor 异常或 Session not found），subscription 在 generator `finally` 中 detach。不改变当前错误传播语义。"验证点：测试覆盖 cursor 失败时 subscription 被正确 detach。
- **修复风险（低/中/高）**: 低。只需补一句明确说明。
- **严重程度（低/中/高/低）**: 低。

## Residual Risks

1. **容量 256 缺少真实负载数据**：plan 已在 §12.2 承认为"首版内部安全值"，未来需基于观测调优。风险等级：低，不影响当前实现正确性。

2. **transient delta 大小不受限**：单个 Engine chunk 可能较大，plan 不引入截断语义。风险等级：低，属于既有 Engine/provider contract。

3. **跨进程/跨 Host instance 多 watcher 不可见**：plan 明确为非目标。风险等级：低，不影响当前 WU。

4. **Service bounded relay 的 `_ENTRYPOINT_LIVE_EVENT_BUFFER_CAPACITY = 256` 与 hub 容量一致**：若未来调优 hub 容量，Service relay 需同步调整。风险等级：低，有名常量便于追踪。
