### RR-01-未修复-低：`path_kind=crash` 的派生是单向的，无 kill 事实的行也可标 crash

- **入口/函数**: `_crash_path_kind`（`utils/cli_ci_upload_material_registry.py:636-639`），由 `_assignment_guard` 第 851 行对每条 old-source formal row 调用。
- **文件(行号)**: `utils/cli_ci_upload_material_registry.py:636-639`（调用点 851）。
- **输入场景**: 任意 old-source formal scenario 的 `path_kind` 被改为 `'crash'`，而其原始 `result.json` 的 `process_outcome` 不含 `signal=9 / actual_wait_returncode=-9 / harness_deadline_kill=false`（probe P5：`upload_material.LOG-CONFLICT-00-00`，原件 `process_outcome={"kind":"exited","actual_wait_returncode":2,"signal":null,"harness_deadline_kill":false}`）。
- **实际分支**: `process.get('signal')==signal.SIGKILL` 为假 → 整个 `if` 不成立 → 函数无任何断言 → 校验继续并在其余检查上通过。
- **预期行为**: C04 要求 `path_kind=crash` 由原始 `process_outcome` 的 signal=9、actual_wait_returncode=-9、非 deadline 事实派生（"由实际 signal/harness-deadline 事实判断"）；事实不成立时不应接受 `crash` 标签。
- **实际行为**: producer 返回 `accepted`（errors=()、counts 正常），伪造的 `crash` 标签可进入 registry/proof 投影。
- **直接证据**: 代码 636-639 只有 kill-facts ⇒ crash 的蕴含方向，无反方向断言；probe P5 在真实冻结输入上 `accepted=true`（stdout SHA `98ba9aeb6527acb04377d7ca3d14c38a5aab37cc10007f0926c783812af1ab95`）。
- **影响**: 治理编辑一旦发生，登记 registry 与 proof 可持久化无原始事实支撑的 crash 业务事实，且 audit 仍显示 ready。当前注册无实例（799 新 scenario 中 `crash` 仅 2 条，均有真实 signal=9 事实；old 1328 的 `crash-precondition` 等旧词表不受影响）。
- **建议改法和验证点**: 在 `_crash_path_kind` 补反方向：kill 事实成立 ⇒ 必须 crash；否则 `path_kind=='crash'` 时 `raise RegistryValidationError(location+'.path_kind: crash requires SIGKILL facts')`。验证点：现两崩溃行仍 pass、P5 反例转为拒绝、补一条负例测试。
- **修复风险（低/中/高）**: 低（只增加严格性；已确认现注册仅 2 条 crash 且均有事实）。
- **严重程度（低/中/高/严重）**: 低。
- **说明**: 该缺口不属于 root 登记的四项反例；REG-C04 登记项本身已验证修复（见下）。此处按 deepreview 格式给出可执行观察，由 controller 裁决本轮小修或显式延期。
