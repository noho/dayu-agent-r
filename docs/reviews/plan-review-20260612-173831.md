## 1. Challenge Assessment

### Challenge 1: Is `run_storage_maintenance` the correct operator-facing surface?

**Verdict: Yes, with sufficient justification.**

The plan's choice to attach classification to `run_storage_maintenance` is defensible on multiple grounds:

1. **Design source alignment.** `docs/host/design.md` line 979 explicitly defines `run_storage_maintenance(host, request) -> HostStorageMaintenanceResult` as the operator-facing maintenance entry point. Line 1201 further documents it as read-only diagnostics + optional orphan reclaim. Adding a read-only integrity classification field to the existing result type is a natural extension, not a new surface.

2. **Read-only semantics preserved.** The plan explicitly states: "不删除 SQLite row，不 quarantine，不 rebuild，不 overwrite." This aligns with the existing `run_storage_maintenance` contract: dry-run by default, opt-in destructive only for orphan artifacts.

3. **Transaction reuse.** The plan says the classifier reads in the same transaction state as usage report and artifact refs (`_ReadStorageMaintenanceStateOperation`). This avoids a separate durable connection and keeps the maintenance surface unified.

4. **No alternative surface is more natural.** An independent entry point (e.g., `inspect_memory_snapshot_integrity(host)`) would add a new public API surface for a diagnostic that is only meaningful in the context of storage health. The existing maintenance surface is the right home.

**One concern noted:** If future WUs (e.g., WU-RET-00 follow-ups) add more integrity classifiers (audit JSONL, tool trace cold JSONL), the `HostStorageMaintenanceResult` type could grow into a god dataclass. The plan does not address this growth path. This is a non-blocking observation for now — the current addition is one field — but the implementation agent should keep the result type flat and avoid nesting further diagnostic subtypes without explicit design review.

### Challenge 2: Is classification based on direct evidence? Can it cover all six categories?

**Verdict: Yes, with one naming gap.**

The plan defines five classification categories, each grounded in direct parse/validation evidence:

| Plan Category | Direct Evidence | Issue #41 Acceptance Signal |
|---|---|---|
| `invalid_json` | `json.loads()` raises `JSONDecodeError` | ✅ invalid JSON |
| `schema_mismatch` | `conversation_memory_snapshot_from_json_value()` raises `TypeError`/`ValueError` | ✅ schema-mismatched JSON |
| `digest_mismatch` | `snapshot_digest != calculate_memory_snapshot_digest(snapshot)` | ✅ digest mismatch |
| `unsupported_item_kind` | `item_kind == "verified_fact"` or not in allowed set | ✅ unsupported item kind |
| `storage_read_failed` | SQLite fetch/column access raises unexpected error | ✅ storage-read failure |

**Gap: `manual corruption` is not a distinct failure kind.** Issue #41's acceptance signals list six categories: invalid JSON, schema-mismatched JSON, digest mismatch, unsupported item kind, manual corruption, and storage-read failure. The plan's five categories do not include `manual corruption` as a separate kind.

This is likely intentional — manual corruption (e.g., direct SQLite `UPDATE` to alter `snapshot_json`) would manifest as one of the existing five categories (invalid JSON, schema mismatch, or digest mismatch). The plan should explicitly state this mapping rather than leaving it implicit, because the acceptance signal reviewer will check for six categories.

### Challenge 3: Will it elevate snapshot to truth or induce silent rebuild/overwrite?

**Verdict: No. The plan correctly preserves EventLog as truth.**

The plan explicitly addresses this in multiple places:

- Design Boundary: "memory snapshot 仍是 EventLog 派生 read model，可重建、可修复，不是 Host durable truth。"
- Non-Goals: "不自动覆盖 damaged snapshot row"; "不让 command path 静默触发 rebuild / overwrite"
- Review Checklist: "Does any command path silently rebuild or overwrite a corrupt snapshot? It must not."
- Classifier semantics: "classifier 不抛出单个 row 的损坏错误；它返回 issue tuple"

The existing code already preserves this invariant: `read_memory_snapshot()` fails closed on corruption, `RunInputBuilder` converts to `MemoryProjectionRepairRequired`, and projection catch-up records failure rows. The plan's classifier is purely additive read-only diagnostics.

### Challenge 4: Are public result/export/README triggers complete?

**Verdict: Mostly complete, with one structural concern (Finding 1).**

The plan covers:
- `HostStorageMaintenanceResult` extension (S2)
- `json_value()` inclusion (S2)
- Root exports in `dayu/host/__init__.py` (S2)
- `docs/host/design.md` update (S3)
- `dayu/host/README.md` update (S3)
- `tests/README.md` conditional update (S3)
- Control doc update (S3)

### Challenge 5: Is the slice too large or over-designed?

**Verdict: No. The three-slice decomposition is well-structured.**

- S1 is a clean, self-contained module with types and a read-only classifier. It touches one new file, one existing durable module, and one test file.
- S2 extends an existing result type and facade function. It touches existing files with well-defined seams.
- S3 is documentation closure.

The slices respect code dependency boundaries: S1 produces typed output that S2 consumes. S3 is pure documentation. Each slice is independently verifiable.

## 2. Findings

### Finding 1 (Medium) — Type module placement creates layer violation risk

**Evidence:** The plan states:

> S1 Files: `dayu/host/memory_snapshot_integrity.py`

And:

> 新增 Host-internal typed enum/dataclass: `MemorySnapshotIntegrityFailureKind`, `MemorySnapshotIntegrityIssue`

And:

> 在 `dayu.host.durable.memory` 新增 read-only classifier，例如 `inspect_memory_snapshot_integrity(transaction) -> tuple[MemorySnapshotIntegrityIssue, ...]`

This creates a structural problem: if `MemorySnapshotIntegrityIssue` is defined in `dayu/host/memory_snapshot_integrity.py` (host level) and the classifier function in `dayu/host/durable/memory.py` (durable level) returns it, then `durable.memory` must import from `host.memory_snapshot_integrity`. This violates the architecture hard constraint: durable layer must not import from host layer.

**Risk:** The implementation agent may either:
- Create a layer violation (durable imports host-level types)
- Put the types in `dayu/host/durable/` instead, which changes the module placement implied by the plan's "Files" list
- Put both types and classifier in `dayu/host/memory_snapshot_integrity.py`, which removes the classifier from the durable layer where it logically belongs

**Recommendation:** Clarify the module placement:
- **Option A (recommended):** Put `MemorySnapshotIntegrityFailureKind` and `MemorySnapshotIntegrityIssue` in `dayu/host/durable/memory.py` alongside the classifier. The host-level `storage_maintenance.py` already imports from `dayu.host.durable.*` (line 20-35), so this import direction is correct.
- **Option B:** Create `dayu/host/durable/memory_snapshot_integrity.py` for types and classifier, import from `dayu/host/storage_maintenance.py`.

In either case, remove `dayu/host/memory_snapshot_integrity.py` from the S1 files list, or explicitly state it is only a re-export facade (which would be a compatibility code violation per coding hard constraints).

### Finding 2 (Low) — `manual corruption` acceptance signal mapping is implicit

**Evidence:** Issue #41's acceptance signals require coverage of six categories: invalid JSON, schema-mismatched JSON, digest mismatch, unsupported item kind, manual corruption, and storage-read failure. The plan defines five classifier categories but does not explicitly map `manual corruption` to one of them.

**Risk:** The acceptance signal reviewer may flag that `manual corruption` is not covered, even though it would be caught by existing categories (e.g., if someone manually edits `snapshot_json` to invalid JSON, it would be caught as `invalid_json` or `schema_mismatch`).

**Recommendation:** Add a sentence to the S1 section: "Issue #41 的 `manual corruption` 类别不作为独立 failure kind；手动修改 durable row 导致的损坏会被 `invalid_json`、`schema_mismatch` 或 `digest_mismatch` 捕获。classifier 的五类已覆盖全部 acceptance signal。"

### Finding 3 (Low) — `storage_read_failed` test strategy needs concrete trigger

**Evidence:** The plan's S2 test list includes:

> storage-read failure classification through a controlled test monkeypatch of the classifier/read operation, without changing production corruption semantics.

But the S1 classifier design says:

> classifier 不抛出单个 row 的损坏错误；它返回 issue tuple。只有查询自身失败才抛出 `HostDurableError`。

This means `storage_read_failed` is only produced when the classifier's own SQL query or column access fails — not when individual row parsing fails. The plan should specify which operation to monkeypatch (e.g., `transaction.fetchone` for the classifier's own query, or a column `.get()` on the result row) and what exception to simulate.

**Recommendation:** Add a concrete test trigger to S2, e.g.: "monkeypatch `HostTransaction.fetchone` to raise `sqlite3.OperationalError` during the classifier's snapshot scan, verify `storage_read_failed` classification is returned in the result tuple."

## 7. Additional Observations (Non-Binding)

1. **`HostStorageMaintenanceResult` growth path.** If future WUs add more integrity classifiers (audit JSONL, tool trace cold JSONL), the result type could grow. The current addition is one field, which is fine. But the implementation agent should keep the type flat and resist nesting further diagnostic subtypes.

2. **S1 classifier scan scope.** The plan says "classifier 扫描 `host_memory_snapshots`，逐 row 分类." This implies a full table scan. For large databases with many sessions, this could be slow. The plan does not address pagination or session-scoped filtering. This is acceptable for a first version (maintenance is an explicit operator action, not a command-path operation), but the implementation agent should consider adding an optional `session_id` filter to the classifier for future use.

3. **S2 test count.** The plan lists 7 test scenarios for S2, which is comprehensive. The `json_value()` key set test is particularly valuable for preventing accidental field omission.

4. **S3 control doc update timing.** The plan should specify that control doc updates happen after each slice (not just after S3), consistent with the workflow in `issues-implementation-control.md` line 175: "每个 work unit 进入 plan、implementation、review、ready-to-open-draft-PR 或 draft-PR-pass 时，必须更新'当前状态'。"
