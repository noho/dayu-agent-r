## 审查过的关键假设与结论（assumptions tested）

2. **共同 admission 是否覆盖全部入口**——成立。生产代码仅两处构造 `FinsUploadMaterialRequest`（`tools/upload_tools.py:351`、`service/fins_direct.py:341`）；`upload()`（3651）、`start_upload()`（4658）、`prepare_observed_upload()`（3848）、`start_observed_upload()`（3820）均在创建 stream/observation/queued record 之前调用 `_validate_runtime_upload_request()`（4714），material 分支转 `_normalize_upload_request()`（7694，现仅 ticker/action/source-kind）。tool 经 `prepare_observed_upload`（upload_tools.py:103），Service/CLI 经 `runtime.upload`。`upload_batch` 仅生成可重放 CLI argv（fins.py:387+），执行仍走上述入口。`dayu/host`、`dayu/ui` 无 upload_material 直连。job record 在校验之后创建，准入失败不会产生失败 job。
3. **typed usage code 是否足够且不漂移**——基本成立。`FinsUploadUsageError` 是 `ValueError` 子类（ingestion_runtime.py:743），`_raise_upload_usage`/`fins_upload_usage_failure` 为既有 typed 通道；CLI 已映射 `FinsUploadUsageError.failure.message` 到 exit 2（fins.py:198-200，`EXIT_USAGE_ERROR=2`）；tool 已把 `ValueError` 映为 `invalid_argument` 且 `message=str(exc)` 即 owner 文案（upload_tools.py:117-123）。`FinsUploadUsageCode` 唯一非测试消费者 `filing_upload_publication.py:73-76` 只引用具体 filing code，新增枚举成员不破坏穷尽匹配；`test_fins_upload_usage_failure_mapping_is_closed_bounded_and_path_free`（test_fins_ingestion_runtime.py:1389）断言精确 code 集合与文案，plan 已声明更新。新增两个 code + 文案属既有 closed 通道的枚举扩展，不是新公开 schema 字段。
4. **CLI 空白 `--forms` 的 parser 行为**——当前 `--forms` 为 `nargs="+"` 无 choices（arg_parsing.py:958）；`_single_optional_form` → `_normalized_text_tuple`（fins.py:1144-1175）对逗号分项、strip、空项抛 `CliFinsUsageError(_EMPTY_FORM_MESSAGE)`（"--forms must not contain empty item"）。即今日空白 `--forms` 已被 CLI 结构校验前置拒绝（exit 2），UM-031 冻结的 `upload.started` 迟到失败来自 **缺参**（→ `None`），不是空白串。plan 要把空白改道到 owner 以获得 typed 语义并消除 CLI 业务规则重复，方向与 goal 一致；但改道的 parser 边界未定义（见 Finding 1）。

6. **旧 fixture 修正是否弱化测试**——plan 的方向（补合法 form/name 保留用例意图、不加生产兼容分支、ticker/source-kind 错误先行的用例维持原断言）不天然弱化断言；核查的断点见 Finding 3。无现存 tool/CLI 测试断言 `_required_text` 的 form/name 旧文案（全仓 `must be a non-empty string` 仅见 host 测试），tool 改动基本只新增断言。

## Findings

### 1-未修复-中-CLI 空白 `--forms` 改道的 parser 边界欠规格，且与共享结构解析器的允许变更范围冲突
- **位置**: 范围表 `dayu/cli/commands/fins.py` 行（"`_single_optional_form()` 对单个空串/纯空白 `--forms` 值机械保留 raw 字符串传给 owner；缺值仍为 `None`，多个 form/逗号列表的现有结构校验不变"）。
- **问题类型**: 不可直接实施 / 契约缺失
- **当前写法**: 只允许改 `_single_optional_form()`（含 docstring），并冻结"逗号列表的现有结构校验不变"。
- **反例/失败场景**: 逗号/空项边界未定义——`--forms ","`、`--forms " ,"`、`--forms "A,"` 既是"含空白的单值"又是"含空项的逗号列表"。若实现把它们当单值原样透传，owner 会把 `"A,"` 当合法 form_type 放行并生成身份；若当结构错误，则与"单个空串/纯空白机械保留"的字面规则矛盾。更直接的失败：空项拒绝逻辑在共享的 `_normalized_text_tuple`（fins.py:1160-1175），同时服务 `_single_batch_material_form`（`upload_filings_from --material-forms`，fins.py:1193-1210）；实现者只有三条路——改共享 helper（可能连带 batch 入口行为）、在 `_single_optional_form` 里复制逗号拆分/多值拒绝逻辑（重复结构解析、日后漂移）、或给 helper 加参数（参数化行为未在 plan 声明）。三条路都超出"精确允许变更"文本，需实施 Agent 当场发明规则。
- **为什么有问题**: plan 的完成信号要求真实 CLI 对 `--forms ""`/`"  "` 断言 owner typed 文案，但边界样例（`","`、`"A,"`、`"A, "`）既无规格也无测试计划；Goal Confirmation 要求"入口一致、不让 CLI 重复业务校验"，而 batch `--material-forms` 入口的结构校验语义可能被连带改变。违反 plan 必须 code-generation-ready 的要求。
- **直接证据**: `dayu/cli/commands/fins.py:1144-1175`（`_normalized_text_tuple`：逗号拆分 + strip + 空项抛 `_EMPTY_FORM_MESSAGE`/field 错误）、`:1177-1190`（`_single_optional_form` 全部逻辑委托它）、`:1193-1210`（batch 同一 helper 且 `.upper()`）；`dayu/cli/arg_parsing.py:958`（`--forms` 为 `nargs="+"` 无 choices）；plan 范围表 cli 行。
- **影响**: 实施 Agent 跑偏；`--forms "A,"` 等输入的结构校验静默漂移；batch `--material-forms` 行为被连带修改后 `tests/cli` 回归面扩大；review 无法验收边界行为。
- **建议改法和验证点**: plan 明确写死规则——仅当 `args.forms` 为单个不含逗号的原始值且 `strip()==""` 时原样透传给 owner；任何含逗号的值维持 `_normalized_text_tuple` 现有结构校验（空项/多值拒绝文案不变）；`_single_batch_material_form` 行为逐字不变。指定实现落点（在 `_single_optional_form` 内判定单值空白，不改共享 helper；若参数化 helper 须同时声明 batch 调用方不变）。S1 的 CLI 测试矩阵补边界样例：`""`、`"  "`、`","`、`" ,"`、`"A,"`、`"A,B"`、缺值 7 类的期望（owner 文案 vs 结构错误）逐条列明。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-tool helper 切换静默改变合法非空值的投影，与 plan 声明的"有效输入稳定"不变量冲突
- **位置**: 范围表 `dayu/fins/tools/upload_tools.py` 行（"`_required_text()` 改用现有 `_optional_raw_nullable_text()`"）；目标节"合法材料的现有值传递、身份生成和上传行为保持稳定"；S1 验证第 2 条"request 原值、job summary/事件输入与既有稳定 ID 语义不变"。
- **问题类型**: 非最优方案
- **当前写法**: 两字段改用 raw helper，owner "只检查空值，不改写非空原值"，并以干净 US/CN 样本断言值传递与稳定 ID 不变。
- **反例/失败场景**: tool 调用传 `form_type=" 8-K "`、`material_name=" Deck "`：今日 `_required_text` 返回 `value.strip()`（_ingestion_tool_helpers.py:95-113），request/`UploadMaterialEvent` payload/publication meta 均为 strip 后值；改后 `_optional_raw_nullable_text` 原样返回（upload_tools.py:417-418），raw 带空白值进入事件 payload（sec_upload_workflow.py:509-510）与后续 meta 写入调用（:543、:582-583、:610-611）。同一输入经 CLI 仍被 `_normalized_text_tuple`/`_optional_stripped_text` strip，形成 CLI-strip 与 tool-raw 的入口间投影分叉。plan 的验证样本是干净值，测不出该漂移；plan 却断言"现有值传递...保持稳定"，该断言对这类合法输入为假。
- **为什么有问题**: Goal Confirmation 的成功信号是"合法输入保持原有处理和 material ID 稳定语义"。ID 虽稳定（`build_material_ids` 内部 strip），但"原有处理"（adapter strip 后投影）被无声改变，且无测试钉住新旧行为之一。存在更小行为变化的替代方案：保留 tool 对非空值的 strip 投影、只让缺失/null/空白抵达 owner（空白 strip 后为空串或透传 raw 均被 owner 拒绝），即可 100% 满足 goal 而零值漂移；或 plan 明确把 raw 透传接受为新契约并改写稳定性声明。当前写法两者皆无。
- **直接证据**: `_ingestion_tool_helpers.py:95-113`（`_required_text` strip）；`upload_tools.py:396-418`（`_optional_raw_nullable_text` 原样返回，非字符串拒）；`ingestion_runtime.py:7460-7482`（`_bounded_text` summary 侧 strip——job summary 不漂移，但事件/meta 用 raw）；plan 目标句与验证第 2 条。
- **影响**: 实施后合法输入的行为/持久化内容静默漂移；测试按 plan 只用干净样本会固化错误不变量；入口间值投影不一致，后续 O09 form canonical 裁决被污染。
- **建议改法和验证点**: 二选一并写进 plan：(a) tool 侧对非空值维持 strip、仅缺失/null/空白透传 owner（推荐，goal 等价、零漂移）；(b) 接受 raw 透传，则删除/改写"现有值传递保持稳定"声明，S1 增加 padded 值用例断言 request/事件/meta 的 raw 投影与稳定 ID，并声明 CLI strip 与 tool raw 的入口差异为已接受契约。无论哪种，补一条 tool 空白/缺失/padded 三类输入的投影断言。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
