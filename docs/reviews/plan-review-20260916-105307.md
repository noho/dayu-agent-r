- 评审对象：`docs/plans/docling-2-127-upgrade.md`（2026-09-16，状态：待用户确认后实施）
- 评审时间：2026-09-16 10:53:07（系统时钟）
- 评审范围：全 plan（目标/非目标、依赖盘点、API 兼容性、平台可行性、行为变化风险、实施步骤 1-4、回退方案、风险清单）

## 2. Assumptions Tested

1. **「三平台 CI 安装冒烟」存在可执行的载体**（步骤 3.3、风险表两处引用）——**证伪**：仓库无 `.github/`、无任何 CI yml；仅有的 `utils/smoke_web_ci.py` / `docs/cli_ci*` 是 web 冒烟与 CLI 语义回归，与三平台安装无关。
2. **250 样本回归足以覆盖升级的行为风险面**（步骤 2 为本 plan 核心验证）——**部分证伪**：回归仅在执行机器上跑；macOS 上 OCR auto 选 ocrmac（plan 2.3 自述），rapidocr 3.9.2 + PP-OCRv6（Linux/Windows 唯一 OCR 主力）在本机回归中零覆盖。
3. **「constraints 纯版本锁定变更、无代码改动」**（回退方案前提）——**与步骤 2.3 自相矛盾**：步骤 2.3 明确计划内可能产生 `dayu.documents.docling_runtime` 代码适配。
4. **升级期间写入的资产与回退无交互**——**未论证**：新 docling json 持久化进库后回退，LLM 消费侧将混合新旧 schema 文档（透传消费，无版本标注）。
5. **min-py311.txt「同步上述变更」无损文件使命**——**证伪**：文件头注释声明「最低支持边界验证」，当前锁 torch 2.2.2（恰为最低边界）；plan 将其升至 2.14.0 且未解释最低边界为何失效。
6. **样本覆盖「A 股、港股、美股（TSM 等）中文财报」**——**证伪**：美股 10 家公司目录（TSM/GOOGL 等）filings 全为 SEC `.htm`，0 份 PDF；且 SEC .htm 不经过 docling 转换（grep 无转换路径），plan 的样本代表性描述与事实不符。
7. **语义 diff 的判定可执行**（「对每处差异判定修复/退化/中性」）——**未规格化**：抽样规模、分层、判定粒度、判定人、产出位置全部未定义；基线含 15076 张表格，「每处差异」判定的工作量与机制缺失。

## 3. Findings

### F01-未修复-高-「三平台 CI 安装冒烟」引用不存在的设施，步骤 3.3 无法执行

- **位置**: 步骤 3 第 3 条；风险清单第 6 行（Linux CUDA）与第 9 行（新增依赖）的缓解列
- **问题类型**: 不可直接实施 / 契约缺失
- **当前写法**: 「3. 三平台 CI 安装冒烟（constraints 锁定组合可解、可 import、单样本转换通过）」；风险缓解「Linux CI/部署磁盘配额需提前确认」「CI 安装验证兜底」
- **反例/失败场景**: 实施 agent 按步骤 3.3 寻找三平台 CI 时，仓库内无任何 CI 定义；「Linux CI」不存在，磁盘配额无人确认；Windows/Linux 平台的可安装性在本轮实际无人验证。
- **为什么有问题**: plan 把验证动作委托给不存在的设施；「三平台可安装可运行」是 plan 自己声明的目标，但其验证步骤没有执行载体。
- **直接证据**: 仓库根目录无 `.github/`，`find . -maxdepth 2 -name "*.yml"` 无结果；唯一 CI 相关资产是 `utils/smoke_web_ci.py`（web 冒烟）与 `docs/cli_ci.md`（CLI 语义回归），均非三平台安装冒烟。
- **影响**: 步骤 3.3 无法执行 / 三平台目标未验证 / 风险后移
- **建议改法和验证点**: 把步骤 3.3 改写为明确的手动三平台验证清单：指定执行机器（本机 macOS arm64；Windows 机器、Linux 机器分别由谁执行）、每平台验证命令（`pip install -e . -c <lock>` + import 冒烟 + 单样本转换）、验收输出与回填方式；或在 plan 中明确本轮只验证 macOS arm64，其余两平台以「用户侧手动验证清单」形式交付并在风险表如实登记为残余风险。
- **修复风险（低/中/高）**: 低（仅改写步骤 3.3 与风险表措辞）
- **严重程度（低/中/高/严重）**: 高

### F02-未修复-高-样本回归平台单一：rapidocr 3.9.2 / PP-OCRv6 路径（Linux/Windows OCR 主力）零行为回归

- **位置**: 步骤 2（样本库输出回归）；风险清单第 8 行「OCR 引擎行为变化导致扫描件提取质量波动」
- **问题类型**: 测试缺口 / 契约缺失
- **当前写法**: 步骤 2 未指明回归执行平台；风险缓解写「样本库含扫描件；`do_ocr` 路径专项回归；rapidocr PP-OCRv6 升级属预期收益」
- **反例/失败场景**: 回归在本机 macOS arm64 执行。`OcrAutoOptions` 在 macOS 优先选 ocrmac（plan 2.3 自述），31 份扫描件样本全部走 Apple Vision OCR；rapidocr 3.9.2 的 PP-OCRv6 模型集在回归中一次都不会被调用。Linux/Windows 用户首跑即直接用未回归的 rapidocr 路径，OCR 质量退化无提前发现窗口。
- **为什么有问题**: 风险登记了「OCR 引擎行为变化」，但缓解动作（样本 diff）与风险所在的执行平台错配；plan 声称三平台可运行，行为回归却只在单平台验证。
- **直接证据**: `dayu/fins/pipelines/docling_process_converter.py` 默认 `do_ocr=True`（`DEFAULT_FINS_DOCLING_CONVERSION_CONFIG`）；ocrmac 仅 darwin 平台安装（lock-macos-arm64 含 ocrmac==1.0.1，linux lock 无）；样本库实测 31 份 pictures>50 的扫描件样本；plan 2.3「macOS 上 auto 选择优先 ocrmac」。
- **影响**: 三平台中两平台的 OCR 行为零验证 / 用户可见质量退化风险后移 / 风险表「中」级缓解实为空转
- **建议改法和验证点**: 明确回归平台矩阵；至少在一台 Linux x64 机器上对扫描件子集（31 份或抽样 ≥10 份）跑新旧输出对比（旧版环境产物可与旧基线 json 对比，或先用 2.90.0 在 Linux 生成基线）；若不可行，把「rapidocr 路径仅冒烟级验证」如实写入残余风险并在上线后安排首周抽检。
- **修复风险（低/中/高）**: 中（需要 Linux 机器与新旧两套环境）
- **严重程度（低/中/高/严重）**: 高

### F03-未修复-高-回退方案与计划内代码适配自相矛盾，且未覆盖升级窗口内写入的资产

- **位置**: 第 5 节（回退方案）；步骤 2 第 3 条；非目标第 3 条
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: 「constraints 文件为纯版本锁定变更、无代码改动；回滚 constraints 并重建环境即可回到 2.90.0 基线」。而步骤 2.3 写「差异判定为退化的样本……再决定是否需要在 `dayu.documents.docling_runtime` 的受控配置层做适配」——即计划内明确可能产生代码改动。
- **反例/失败场景**: 实施 agent 做了配置层适配后触发回滚，按第 5 节只回滚 constraints，代码适配残留——2.90.0 环境下运行适配代码，行为不可预期。另一面：升级窗口内新上传的 docling json（新 schema）已持久化进库；回退后 `doc_tools` 继续把 `*_docling.json` 全文透传给 LLM，同一持仓的文档新旧 schema 混合，无版本标注、无隔离、无重建策略。
- **为什么有问题**: 回退是安全网，网本身有洞；「durable state 版本偏差」在 schema 变更场景下是核心风险（项目 CLAUDE.md 语义所有权与 schema 变更约束明确要求新起库/明确迁移策略），plan 完全没有提及回退时的资产状态。
- **直接证据**: plan 步骤 2 第 3 条原文；非目标 3「不在本轮处理 `_docling.json` 历史资产的 schema 迁移」；`doc_tools.py:59` 透传消费；`docling_upload_service.py` 把 docling json 作为 primary_document 持久化并记录 sha256。
- **影响**: 回退后环境不一致 / LLM 消费混合 schema 文档 / 不可恢复的数据语义混乱
- **建议改法和验证点**: 回退方案改写为三层：(a) git 回滚本轮全部提交（constraints + pyproject + 可能产生的代码适配）；(b) 重建环境；(c) 升级窗口内写入的 docling json 处理策略需显式声明（接受混合 / 重建 / 标记隔离三选一，并写明 LLM 消费侧影响）。
- **修复风险（低/中/高）**: 低（文档改写）
- **严重程度（低/中/高/严重）**: 高

### F04-未修复-中-docling-ibm-models 3.13.0→4.0.2 跨 major 的模型权重/架构变化未单列为风险项

- **位置**: 第 2.4 节第 5 条；风险清单
- **问题类型**: 风险清单遗漏
- **当前写法**: 2.4.5 只覆盖「模型栈升级（torch 2.4.1→2.14.0、transformers 4.57.6→5.16/5.17）引起表格结构识别数值级变化」——讲的是推理栈；风险清单同样只有这一行。
- **反例/失败场景**: docling-ibm-models 跨 major（3.13→4.0）大概率伴随 layout/tableformer 模型权重 revision 或架构更新。若权重更新，250 份样本的输出将**全量**产生差异（而非少量数值级扰动），步骤 2「对每处差异判定修复/退化/中性」的工作量超出实施预期一个量级，「意外退化」的判定基准（与旧基线对比）也会失真。
- **为什么有问题**: 差异量级直接决定回归方案的可行性与判定工作量；plan 把「权重变化」与「推理栈数值变化」混为一谈，实施 agent 无法据此规划 diff 期望量。
- **直接证据**: plan 依赖表 docling-ibm-models 3.13.0→4.0.2（跨 major）；plan 2.4.5 原文只提 torch/transformers；基线样本实测 15076 张表格（tables>=10 的样本 216 份），任何权重级变化都会放大 diff 规模。
- **影响**: diff 判定工作量失控 / 回归结论置信度下降 / 实施超期
- **建议改法和验证点**: 风险清单单列「docling-ibm-models 跨 major 模型权重/架构变化」；实施前先核对 3.13.0 与 4.0.2 的模型 revision/架构差异作为先导信息，据此确定语义抽样的规模下限。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F05-未修复-中-回归设计不可直接实施：抽样规模、判定粒度、判定人与产出物全部未定义，且「适配」对解析质量退化无可行出口

- **位置**: 步骤 2 第 1、2、3 条
- **问题类型**: 不可直接实施 / 测试缺口 / 切片过粗
- **当前写法**: 「语义层：抽样 diff 文本、表格（含数字单元格）、heading 结构、阅读顺序；对每处差异判定『修复/退化/中性』」「差异判定为退化的样本……再决定是否需要在 `dayu.documents.docling_runtime` 的受控配置层做适配」。
- **反例/失败场景**: 实施 agent 无法回答：抽样多少份？按什么分层？「每处差异」是文档级、表格级还是单元格级？由人判还是 LLM 判？判定结果记录在哪？另外，若退化根因是 docling 内部解析质量（docling-parse 7.x 回归），`docling_runtime` 配置层（backend/device/参数装配）没有修复出口——plan 未给出该分支的可行动作（回滚/降级/pin 中间版本），「决定是否适配」把设计压力甩给了实施 agent。
- **为什么有问题**: 这是 plan 的核心验证步骤，却处于「抽样」+「再决定」两级未规格化状态，不满足 code-generation-ready；语义层恰是真正的风险面（项目代码不解析 docling json 内部字段，程序级风险已被 closed-JSON 校验兜底，破坏面集中在 LLM 透传消费的语义质量），却只获得最弱的验证规格。
- **直接证据**: plan 步骤 2 原文；`docling_process_converter.py:294-305` 的 `_is_closed_json_value` 校验说明程序级 schema 破坏会显性失败而非静默；`doc_tools.py:59` 透传消费说明 LLM 语义是真实破坏面。
- **影响**: 实施 Agent 重新设计验证方案 / 回归结论不可验收 / 最大风险面验证最弱
- **建议改法和验证点**: 明确 (a) 抽样规模与分层：如每公司 ≥2 份 + 全部 31 份扫描件 + 按表格密度分层补足；(b) 判定粒度取文档级（差异聚合后整档判定）并给出判定清单（数字保真、表格结构、heading 层级、阅读顺序）；(c) 判定人：人工或 LLM（LLM 判定需附判定 prompt 与人工抽查机制）；(d) diff 脚本入 `utils/`、判定报告入 `docs/` 的固定路径；(e) 补充「docling 内部回归且配置层无法适配」分支的动作：明确回滚或 pin 候选版本的决策条件。
- **修复风险（低/中/高）**: 低（plan 改写）
- **严重程度（低/中/高/严重）**: 中

### F06-未修复-中-PPTX/DOCX 覆盖缺口缓解与风险不匹配：单元测试不执行真实转换，自建样本无标准，人工抽检无量化

- **位置**: 步骤 2 覆盖缺口说明；风险清单第 4 行
- **问题类型**: 测试缺口 / 非最优方案
- **当前写法**: 「该两格式的回归降级为单元测试 + 自建最小样本（含表格、图片、列表的演示文档）」；缓解「升级后首批真实上传人工抽检」。
- **反例/失败场景**: (a) 现有 docling 测试用 monkeypatch 替换 `build_docling_pdf_converter`，只测协议装配，不执行真实 docling 转换——单元测试对「版本升级导致 PPTX/DOCX 输出变化」零覆盖；(b) 自建样本的内容标准、数量、判定标准未定义；(c) 「首批真实上传人工抽检」无触发条件（首批多少份）、无抽检维度清单、无记录方式。同时，plan 背景列出的升级收益近半是 PPTX/DOCX 增强（v2.113/2.118/2.118.1/2.122），收益宣称与验证资源倒挂。
- **为什么有问题**: PPTX/DOCX 是产品声明的 primary 支持格式（`DOCLING_CONVERTER_CAPABILITY` 含 .pptx/.docx），真实财报 PPT（业绩说明会）/DOCX 上传即生产；无真实样本是客观约束，但缓解手段必须真实有效，「单元测试」项在该测试体系下是空转。
- **直接证据**: `tests/documents/test_docling_runtime.py` 使用 `monkeypatch.setattr(docling_runtime, "build_docling_pdf_converter", factory)` 等替换，无真实转换测试；样本库与 materials 全库 find 0 份 pptx/docx（实测）。
- **影响**: PPTX/DOCX 退化无提前发现窗口 / 人工抽检不可验收 / 风险表「中」级缓解名存实亡
- **建议改法和验证点**: (a) 明确自建样本规格：≥5 份、覆盖复杂合并单元格表格/多图表/分栏/页眉页脚，判定标准为「转换成功 + 表格数字保真 + schema 有效」；(b) 把「单元测试」改为「真实转换冒烟脚本」（utils/ 下，跑自建样本集）；(c) 人工抽检量化：首批 N 份、抽检维度清单（表格数字/阅读顺序/图片保留）、结果记录位置；(d) 或从公开渠道获取 2-3 份真实财报 PPT/DOCX 入样本库。
- **修复风险（低/中/高）**: 中（需构建样本）
- **严重程度（低/中/高/严重）**: 中

### F07-未修复-中-min-py311.txt 语义冲突：「最低支持边界验证」文件被改成统一 2.14.0 锁定，且注释不改

- **位置**: 步骤 1 第 2 条

### F09-未修复-中-Linux 强制 CUDA 依赖链成本被低估：无量化、无替代方案评估、缓解动作载体不存在

- **位置**: 第 2.3 节 Linux x64 段；风险清单第 6 行
- **问题类型**: 非最优方案 / 风险清单遗漏
- **当前写法**: 「安装体积显著增大，Linux 平台 lock 需补充锁定这些包」「Linux CI/部署磁盘配额需提前确认」。

- **建议改法和验证点**: (a) 量化：列出各 nvidia 包近似体积与总和；(b) 明确 Linux 环境形态（谁的机器、是否部署、是否 GPU）后，评估 CPU-only index 选项并记录取舍；(c) 锁定清单补全 extras；(d) 若接受 PyPI 默认，把下载源/镜像纳入验证清单。
- **修复风险（低/中/高）**: 低
