### 1-未修复-高-自定义类型全塌缩 `custom_exception` 且尾 16 帧窗口可吞掉唯一定位帧，不满足 #198「异常类型 + 栈定位」诊断目标

- **问题类型**: 目标对齐不足 / 非最优方案（被项目内已裁决的更优解支配）/ 测试缺口（blocking validation 不覆盖深栈）。
- **当前写法**: 「异常类型只输出由内建类身份确认的安全内建异常名；自定义类型输出固定 `custom_exception`，不输出其任意 `__name__/__module__`」；「命名常量限制最多 16 个末端帧」；「自定义类的具体名称不暴露是安全取舍，代码位置提供定位线索」；blocking validation 仅要求「当前布局测试必须证明至少一个真实 `dayu` 帧和抛出行号可见」。
- **反例/失败场景**: 真实未知 download 失败的主形态是第三方自定义异常（Docling 转换、httpx/lxml/pydantic 内部错误——adapter 未包装成 typed 的正是未知档）。其 traceback 从 Fins producer 到 raise 点常超 16 帧且抛出点在库深处：尾 16 帧窗口保留的全是 `[external]`，`dayu` 调用点帧从头部掉出，输出形如 `custom_exception [external]×16 truncated`——**既无类型、也无定位**。goal 成功信号 1 要求「异常类型与有界调用栈线索足以找到代码发生点」，两要素在该形态下同时落空；issue #198 的期望（总控 C1 转述：脱敏后仍有原始异常**类型**和栈定位）也不满足。
- **为什么有问题**: (a) 对秘密类名的威胁模型是自我加压（计划把「自定义异常类名含秘密」写进自己的测试场景）；为它付出丢掉全部自定义类型标签的代价，而目标只要求不泄漏消息/URL/密钥/路径，未禁止类型名。(b) 该设计已被本项目裁决过一次并给出更优解：S1 计划 fix 记录明文「MiMo F2：自定义类型全抑制 → 已修复（计划层）：规定内建祖先 + `__module__`/`__qualname__` 的 16 hex SHA-256 指纹」；指纹方案对任何类名（含秘密类名）零泄漏且可区分类型，严格支配常量塌缩。(c) 计划把 goal 的「异常类型」验收偷换成自设的浅栈「至少一个 dayu 帧」检查，深栈场景不在验收面内。
- **直接证据**: goal 信号 1/2 原文；主工作区 S1 fix10 计划 fix 记录表「MiMo F2」行与其边界合同 `safe_exception_trace` 输出格式 `exception_type=<安全类型> custom_type=<安全指纹或 redacted> stack=<帧列表>`（16 hex SHA-256(`module + "\0" + qualname`)，元数据失败回 `redacted`）；本候选 decision 3 的塌缩与「末端帧」截断；EXECUTION 档收口点 `ingestion_runtime.py:6871-6877`。

- **建议改法和验证点**: 采用已裁决指纹方案（内建身份名 + 自定义类型 SHA-256 指纹 16 hex + 失败 `redacted`），或对通过与帧同级信任校验的 `dayu.*` 类输出精确类名、第三方输出有界安全类别；帧窗口改为 dayu 帧优先或头尾混合（保留抛出点 + 保留最深可信 dayu 帧）；blocking validation 增加深外部栈用例，断言「至少一个可信 `dayu` 帧 + 类型标签可区分两类不同自定义异常」。验证点：两类不同自定义异常的指纹不同且无原名；深度 >16 帧的外部栈注入仍有 dayu 帧。
- **修复风险（低/中/高）**: 低（formatter 内部规格修订）。

## Open questions

- **OQ1（handler 失败泄漏边界）**: stdlib `logging.Handler.handleError` 在 handler `emit` 抛错时会向 `sys.stderr` 自行打印 `--- Logging error ---` + handler 异常 traceback + `Message: %r`/`Arguments: %s`（`raiseExceptions` 默认 True）。在本设计下 record 参数仅为固定事件名与 formatter 安全串，不泄漏原文；但计划断言「Logger handler 抛错时…不产生线程原始异常输出」的可观测边界需明确为 threading.excepthook 通道，否则实施者对 stderr 断言过宽会误报。建议测试显式核对 handleError 输出中的 record 参数为安全串，并把「stderr 无任何 Traceback」限定到本 S2 事件行。
- **OQ2（S1 依赖的现实可满足性）**: S1 目前是 fix10 候选、未通过双路 re-review、未实施（主工作区三产品文件为未提交候选 diff，`git diff … | shasum` = `d9af4d09…`）。本 S2 硬前置在可预见期内不可满足；且 S1 合同已改 10 轮仍可能再变。plan gate 通过后实施派发的「S1 合同冻结点」与重审触点需要总控明确——本 review 对一切 S1 后置行为只作条件判断（conditional/unknown until integration），不以当前旧代码断言未来接口。
- **OQ3（direct unsupported 文案现状）**: `_UnsupportedDownloadSourceError` 在 direct 落 EXECUTION/「下载执行失败」、在 job 是「不支持的下载来源: source=…」。S2 不改文案（正确），但 direct/job 公开文案不一致是否另立 issue，交总控登记。
