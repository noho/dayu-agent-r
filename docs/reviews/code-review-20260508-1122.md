- **输入场景**: 以后调整 `dayu.runtime.log` 的 VERBOSE 注册数值 / 名称，或在未导入 `dayu.runtime.log` 的测试、嵌入式调用、worker 入口里直接启用这些 logger。
- **实际分支**: 各模块没有复用 runtime 日志级别真源，而是在本层定义 `_VERBOSE_LEVEL_NUMBER: int = 15`，然后用 `_LOGGER.log(_VERBOSE_LEVEL_NUMBER, ...)` 发日志。
- **预期行为**: VERBOSE 级别应只有一个层中立真源；Engine 仍不应 import `dayu.runtime.log` 装配模块，但可以通过更小的层中立常量 / helper 避免每个业务层模块手写数值。
- **实际行为**: `dayu.runtime.log` 注册 `VERBOSE=15` 的同时，Engine 和 7 个 Host 模块各自复制 `15`。注释只说明“与 dayu.runtime.log 注册的 VERBOSE=15 对齐”，但没有代码级约束保证持续对齐。
- **直接证据**: `dayu/runtime/log.py:37` 是 runtime 内部 `_VERBOSE_LEVEL_NUMBER: Final[int] = 15`；`dayu/engine/agent.py:100` 与多个 `dayu/host/*` 模块重复定义同名常量并直接作为 `_LOGGER.log` 的 level 参数。当前测试只验证 `LogLevel.VERBOSE` 和 CRITICAL 解析，没有覆盖这些层内复制常量与 runtime 真源的一致性。
- **影响**: 当前行为未直接泄漏 payload，也不会立刻导致日志缺失；但日志装配能力的真源被复制后，后续调整 runtime 级别或拆分日志装配时，Engine / Host 的 VERBOSE 日志可能被错误过滤、显示为错误 level name，或与 CLI `--verbose` 语义漂移。这违反“公共运行时能力优先复用或扩展 `dayu.runtime`，禁止各层自行实现语义不一致 runtime helper”的约束。
- **建议改法和验证点**: 抽出不装配 handler、无业务语义的层中立日志级别常量模块，例如 `dayu.runtime.log_levels`，只承载 `VERBOSE_LOG_LEVEL` 数值；Engine 不 import `dayu.runtime.log`，Host / Engine 统一 import 该常量。补一个 import-boundary 测试，确认 Engine 不 import `dayu.runtime.log`，同时确认所有新增 VERBOSE 日志使用同一常量真源。
- **修复说明**: 已新增 `dayu.runtime.log_levels` 作为层中立数值常量真源，`dayu.runtime.log` 从该模块读取数值并注册 stdlib level name；Engine / Host 已落地 VERBOSE 日志路径统一导入 `VERBOSE_LOG_LEVEL`，不再本层复制 `15`。新增 runtime 测试覆盖常量稳定性、`log.py` 与公共常量一致性，以及常量模块导入无 stdlib 注册副作用。

## 重点结论

- 未发现新增日志直接输出 prompt、delta 全量、工具参数 / 结果、raw ToolRuntime cursor 或 `scope_token`。
- EventStore 当前在 DEBUG 下跳过 preview append 和 subscribe wait / batch，terminal append 与 canonical append 仍保留可观察边界。

- Engine 新增 VERBOSE 基本能串起 run、iteration、runner call、decision、tool loop、tool batch、tool message 注入、continuation / fallback、terminal 主路径；DEBUG 主要是 runner event 分类、usage、finish reason、tool outcome 等有界细节。
- 未发现 Engine import `dayu.runtime.log`，也未发现 `dayu.runtime` 反向 import Engine / Host / Service / UI / fins 或承载业务语义。
