### 01-未修复-高-source_kind 八种业务语义定义在 prompt 中完全缺失

- **入口/函数**: `dayu/config/prompts/scenes/conversation_compaction_user.md:26-29`
- **文件(行号)**: `conversation_compaction_user.md:26-29`
- **输入场景**: 任何 compaction request；prompt 的五类字段来源规则引用了 `evidence_material`、`previous_evidence_fact` 等八种 `source_kind` 值
- **实际分支**: user prompt 第 26 行写 `support_labels 必须非空且只能引用 evidence_material 或 previous_evidence_fact`，但没有任何地方解释这些 kind 代表什么业务来源
- **预期行为**: prompt 应自足说明每种 source_kind 的业务含义，让无状态模型能判断某个 source 是否属于允许的 kind
- **实际行为**: v2 user prompt 曾有完整的八种 source_kind 语义定义；v3 迁移中该段被完全删除，但五类字段的来源引用规则仍依赖这些 kind 值
- **直接证据**: 基线 HEAD 的 `conversation_compaction_user.md` 包含 `source_kind: 字符串，只可能为以下八种业务来源：previous_session_summary: 上一次已接受整理结果中的会话摘要...` 段落；当前版本该段落不存在。输入数据 `CompactSourceBoundaryEntryV3.to_json()` 确实注入 `source_kind` 值，但 prompt 不解释
- **影响**: 模型看到 `source_kind: trace_material` 但不知道它代表"历史对话和用户可见进展"，只能凭字面猜测是否可作为 `support_labels` 引用
- **建议改法和验证点**: 在 user prompt 的"材料边界"段或"五类字段"段前恢复 `source_kind` 的精简语义定义；验证 captured runner input 包含定义
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 02-未修复-中-system prompt 缺少修复反馈处理规则

- **入口/函数**: `dayu/config/prompts/scenes/conversation_compaction.md`
- **文件(行号)**: `conversation_compaction.md` 全文
- **输入场景**: compaction repair attempt（前次输出被拒绝后）
- **实际分支**: system prompt 完全不提及修复反馈的存在和处理规则
- **预期行为**: system prompt 应包含修复反馈的基本行为约束（whole-candidate 重产，不得 patch）
- **实际行为**: 修复反馈由 `llm_compaction.py:714-730` 在 user prompt 末尾追加，包含 `REPAIR_FEEDBACK_JSON_BEGIN/END` marker 和修复动作说明。但 system prompt 不知道修复反馈的存在
- **直接证据**: 旧版 `conversation_compaction.md` 包含 `收到修复反馈后，执行 required_action，基于同一输入重新生成整个 JSON object`；当前版本无此规则。`llm_compaction.py:714-718` 追加了 `"修复动作：前一次完整输出未通过校验。必须根据本消息中的同一输入、完整字段规则与 concrete template 重新生成整个 JSON object"` 文本，部分缓解了风险
- **影响**: 模型收到 `REPAIR_FEEDBACK_JSON_BEGIN` 时，system prompt 无规则约束其行为；user prompt 末尾的修复动作说明是唯一行为指导
- **建议改法和验证点**: 在 system prompt 硬性要求中增加一条修复反馈规则
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-中-CompactOutputCapsV3 缺少 __post_init__ 非负校验

- **入口/函数**: `dayu/host/compaction.py:1024-1065` (`CompactOutputCapsV3`)
- **文件(行号)**: `compaction.py:1024-1065`
- **输入场景**: 上游 `MemoryProjectionPolicy` 因 bug 产生负值 cap 时
- **实际分支**: `CompactOutputCapsV3` 无 `__post_init__`，9 个 `int` 字段均无非负校验
- **预期行为**: DTO 应自校验值域，负值 cap 语义荒谬

- **建议改法和验证点**: 添加 `__post_init__` 对 9 个字段做 `>= 0` 校验；构造负值 caps 时抛 ValueError
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
