## Findings

### 01-未修复-[低]-判据第 3 条 basename 比较的名址真源（原名 vs 解析后名）未钉死

- **位置**: plan「C01 增补 → 最小确定判据」第 3 条（当前 plan 第 134 行）。
- **问题类型**: 契约缺失（名址真源歧义）。
- **当前写法**: 「若解析后 parent 相等，或两 parent 都存在且 `samefile()` 为真，则仅对**两者** ASCII basename 作上述大小写比较，覆盖汇总链接指向尚不存在的 `ALIAS.json`、样本目标为 `alias.json` 的同目标情况」。「两者」可被读成 `target.name` 与 `summary_path.name`（原路径名），也可被读成两个 `resolve()` 结果的 name；判据 2 的对照式用的是 `target.name`（原名），易诱导实现者在判据 3 沿用原名。
- **反例/失败场景**: 本轮独立探针（`criterion-probe-result.json` case A，本卷实测）：`digests/_manifest.json` 为指向 absent `ALIAS.json` 的 symlink，样本目标 `digests/alias.json`。`resolve()` 不相等（`alias.json` vs `ALIAS.json`）、解析后 parent 相等；**按原名比较** `alias.json` vs `_manifest.json` 大小写不匹配 → 漏拒（`would_reject_if_original_names: false`）；**按解析后 name 比较** `alias.json` vs `ALIAS.json` 匹配 → 拒绝（`would_reject_if_resolved_names: true`）。plan 自己声称覆盖的正是这一场景，只有解析后 basename 读法能兑现。
- **为什么有问题**: 「最小确定判据」是实施契约；同一句两种读法只有一个与 plan 自述覆盖一致，实现 agent 按原名实现会在该场景静默放过冲突（样本 digest 写入与汇总同一物理目标，`numbers` 覆盖丢失——即 C01 原缺陷在 dangling-alias 变体上存活）。N5 验收用例能在修后验收时兜住错误实现，但会造成一次可避免的 fix/re-review 循环，且若 N5 被弱实现则缺口直达产品。
- **直接证据**: plan 第 134 行原文；上述探针输出 `original_basenames_case_match: false / resolved_basenames_case_match: true`；amendment `target-design-result.json` 的 `dangling-ascii` 用例在设计层被拒（设计意图正确，但判据文本未把 name 取值写死）。
- **影响**: 实施 Agent 误读 → dangling-alias 冲突漏拒 → 覆盖固定汇总；或 N5 失败返工。
- **建议改法和验证点**: 判据 3 一句话钉死比较对象为解析后 name，例如将「仅对两者 ASCII basename 作上述大小写比较」改为「仅对 `target.resolve().name` 与 `summary_path.resolve().name` 作 ASCII 小写比较（比较的是解析后路径的 basename，不是原路径名）」；同步确认第二 disjunct 的「两 parent」指解析后 parent。验证点：N5 明确断言该场景 exit2 且两链接文本保持；判据 3 三个分支各有一条具名用例（resolve 相等/解析后 parent 相等+解析后 name 大小写匹配/samefile）。
- **修复风险（低）**: 仅 plan 文本一句话，无技术方案变化。
- **严重程度（低）**: N5 为兜底；设计意图已正确，缺的是 name 取值的唯一读法。

### 02-未修复-[中]-同清单样本间大小写变体 stem 的产物互撞未登记也未预检

- **位置**: plan「最小 CLI 与样本清单 contract」stem 唯一规则（第 81 行）、C01 预检范围（第 112/123 行）、风险表（第 587–597 行）。
- **问题类型**: 契约缺失 / 风险登记缺口（物理别名家族，样本-vs-样本方向）。
- **当前写法**: 清单规则要求「resolved PDF 路径与 stem 均须唯一」，loader（`analysis_sample_inputs.py:115-118`）以精确字符串 `set[str]` 查重；C01 预检只查**样本目标 vs 固定汇总**；风险表登记了「同 stem 跨运行缓存误复用」（跨运行）与非 ASCII absent 别名，但**没有登记同一清单内样本间大小写变体 stem 的产物互撞**。
- **反例/失败场景**: 本轮独立探针（同文件 case C，本卷实测，本卷即大小写不敏感卷）：清单含 `s1/Alias.pdf` 与 `s2/alias.pdf` 两条记录，stems 为 `Alias`/`alias`——**通过现有精确字符串唯一性**；两者 digest 目标 `digests/Alias.json` 与 `digests/alias.json` 为同一物理文件（`samefile: true`），后写覆盖前写（`silent_overwrite_same_physical_file: true`）。cache-miss 并行时两 worker 写同一文件属静默分析产物损坏/错归属；四个入口的产物都是 stem 命名，schema `results/`、verify `verify-cache/`、A/B `r/ v/` 同样暴露。
- **为什么有问题**: 原 plan 的唯一性意图（「两个目录中同 stem 会覆盖/错误复用，必须在输入 owner 拒绝」）在大小写变体上失效；C01 的证据（本卷大小写不敏感）同样适用于样本-vs-样本方向，但当前 amendment 只闭合样本-vs-汇总方向且未把另一方向登记为已知风险。静默丢产物比 exit2 更难发现，与本 slice「缺必需输入明确拒绝、产物保持」的成功信号相悖。
- **直接证据**: 上述探针输出；loader `:115-118` 精确字符串查重；四入口 stem 拼接写址（digest `:425/:435/:444`、schema `:127`、verify `:115`、A/B `:123-124`）；amendment/plan 风险表逐行核对无此条目。
- **影响**: 同一运行内一份样本 digest（或 schema result/arm JSON）被另一份静默覆盖，分析结论错归属且无错误信号。
- **建议改法和验证点**: 本 amendment 权限内的最小改法是**风险登记**：在 plan 风险表新增一行，分类 `requiring new issue or explicit user decision`，owner/destination 总控（与非 ASCII absent 别名同级），附本探针反例描述；不得默认当已修。若总控愿意把该方向并入本 slice，则可选的同源最小实现是 `_require_distinct_digest_targets` 对全部样本目标按同一 name/samefile 判据做两两互查（仍只在 digest producer，不改 loader）；但这超出 C01 裁决「优先只在…与固定汇总冲突」的边界，须总控明示扩权后才可实施，且四个入口的同名暴露无法仅靠 digest 预检闭合，完整闭合更宜另立 goal。验证点：具名反例 `s1/Alias.pdf`+`s2/alias.pdf` 在所选方案下要么 exit2 拒绝、要么在风险表可追踪。
- **修复风险（低）**: 登记为一行风险描述；若扩预检则为低到中（digest 单文件内，判据复用）。
- **严重程度（中）**: 静默分析产物损坏；但为存量缺口（`a88dcf8e` 已存在、双路原审未覆盖），不属本 amendment 引入的回归。
