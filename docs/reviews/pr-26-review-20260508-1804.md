## Findings

### 1-已修复-低-`ensure_host_schema` / `_configure_row_factory` 绕过 `HostStorage` 封装直接访问 `_connection`

- **入口/函数**: `ensure_host_schema()` (L148-164) 和 `_configure_row_factory()` (L769-779) in `dayu/host/_durable_event_store.py`
- **文件(行号)**: `dayu/host/_durable_event_store.py:160`, `dayu/host/_durable_event_store.py:778`
- **输入场景**: 任何调用 `open_durable_event_store()` 或 `DurableRunEventStore.__post_init__()` 的路径
- **实际分支**: 两个函数都通过 `storage._connection` 直接访问 SQLite 连接，绕过 `HostStorage` 提供的 `execute_read()` / `transaction()` 抽象
- **预期行为**: `HostStorage` 作为连接拥有者，外部模块应通过其公开方法操作连接，不直接访问内部字段
- **实际行为**: `ensure_host_schema` 在无连接锁保护下直接执行 DDL；`_configure_row_factory` 直接修改 `row_factory` 属性
- **直接证据**: `_durable_event_store.py:160` — `connection = storage._connection  # noqa: SLF001`；`_durable_event_store.py:778` — `storage._connection.row_factory = sqlite3.Row  # noqa: SLF001`
- **影响**: 当前单进程初始化场景下无实际危害，但破坏了 `HostStorage` 封装边界；若未来 `HostStorage` 内部实现变化（如连接池化），这些直接访问会静默失效
- **建议改法和验证点**: 在 `HostStorage` 上增加 `execute_schema(statements)` 方法，内部持有 `_connection_lock` 执行 DDL；`_configure_row_factory` 合并到 `HostStorage.open()` 的 PRAGMA 配置阶段
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 2-无需修复-低-`_begin_attempt_if_durable` 用 INSERT + UPDATE 两步完成一步即可的 attempt 创建 [无需修复-说明]

- **入口/函数**: `_begin_attempt_if_durable()` in `dayu/host/_run_harness.py`

- **严重程度（低/中/高/严重）**: 低
