### 002-未修复-高-单个 validation WU 生成多个候选 WU，用户确认后无法按同一 Phaseflow 状态机继续

- **输入场景**: 一次 full-real CI 同时发现 UI、memory 和财报分析三个不同语义 owner 的问题，文档据此生成多个候选 WU。
- **实际分支**: per-run control_doc 的 current work unit 是 generic `validation / goal discovery`；总控随后要求用户确认“某个候选 WU”，再让“该 WU”从 `plan` gate 继续，并把 per-run control artifact 指向另一个正式项目 control_doc。
- **预期行为**: Phaseflow 的 `phase = work unit`；goal confirmation、用户确认、`plan` 和后续 gates 必须属于同一个稳定 WU identity 与 control_doc next entry point。
- **实际行为**: 当前 WU 是 validation assessment，但用户确认的是后生成的另一个 WU；多个候选还无法同时成为唯一 active WU。文档通过“指向正式 control doc”跨越状态机，没有定义 assessment WU 的 terminal 状态，也没有为每个候选重新执行独立 Phaseflow startup/goal confirmation。

### 003-未修复-高-full-real verdict 未排除未裁决 oracle，且设计冲突的 failure 语义自相矛盾
- **入口/函数**: 场景与 run 的最终 verdict 聚合
- **文件(行号)**: `docs/cli_ci.md:109`, `docs/cli_ci.md:145-159`, `docs/cli_ci.md:203-230`, `docs/cli_ci.md:553-581`
- **输入场景**: 所有命令均执行成功，但一个 UI 行为只有 `unadjudicated` oracle；另一个 Host 行为偏离当前设计，但 reviewers 同时质疑设计本身。
- **实际分支**: `full-real-pass` 只排除 blocked/not-run；同一列表又允许 `oracle-review-required`。Oracle 规则称只有 objective fact、hard contract 或 accepted oracle 可形成 formal failure，但 pass 规则又无条件要求 Host 符合当前设计，goal artifact 还把 design conflict 直接整理为候选 WU。
- **预期行为**: 同一 run 必须有唯一、有优先级的 verdict；未裁决 oracle 不能 pass/fail；design mismatch 与 design-invalid candidate 必须分别表达，不能同时被算作 formal product failure 和未裁决设计问题。
- **实际行为**: 文档允许含 unresolved oracle 的 run 满足 `full-real-pass` 字面条件，也没有规定 `fail`、`blocked`、`oracle-review-required`、`limited-signal` 的聚合优先级。设计偏差是否 formal failure 存在两套规则。
- **直接证据**: 第 147 行的 full pass 定义仅检查 blocked/not-run；第 152 行定义 oracle-review-required；第 230 行限制 formal failure 来源；第 558 行要求 Host 无条件符合设计；第 109 行把 design conflict 进入候选 WU。
- **影响**: 相同 evidence 可被不同总控裁决为 pass、fail 或 oracle-review-required，CI 历史结果无法比较，后续修复目标也可能选错 owner。
- **建议改法和验证点**: 定义唯一聚合优先级和互斥矩阵，例如 `fail > blocked > oracle-review-required > limited-signal > pass`；`full-real-pass` 必须要求所有 mandatory scenarios 都由 objective/hard/accepted oracle 覆盖且无 unresolved candidate。为 current-design mismatch 单独定义状态：规范仍有效时是 contract failure；设计被正式 reopen 时是 design-review-required，修复方向待用户裁决。用表格覆盖上述两个输入场景。
- **修复风险（低/中/高）**: 中
