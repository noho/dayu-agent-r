## Findings

### 1-未修复-中-delete 携带 files 的静态校验路径未冻结，实现 Agent 必须自行猜测

- **位置**：plan §6.2 第 4/8 步；goal confirmation goal #2「及其它静态组合错误」；frozen `UF-A14-delete-with-files-ignored`。
- **问题类型**：契约缺失 / 不可直接实施
- **当前写法**：§6.2 第 4 步「delete 必须同时满足 `files=()` 与 `primary_selectors=()`；有 selector 抛 `PRIMARY_NOT_ALLOWED_FOR_DELETE`」只定义了 selector 半边的 closed code；第 8 步「primary 使用 primary suffix capability，其余使用 companion capability，不得再使用 enumerate index 分配角色」对 delete-with-files 无角色判定规则。五个新 usage code 中没有 delete-with-files 的 code。
- **反例/失败场景**：用户执行 `dayu-cli upload_filing --action delete --files a.txt b.txt`（frozen UF-A14 记录的正是 delete-with-files 被明确忽略）。当前实现（`ingestion_runtime.py:994-1011`）先按 index-0=primary 校验每个文件、再构造 `for_delete()` 空 selection，即「校验后忽略」。计划删除 index 角色后，第 8 步对该组合无定义；若实现者选择「拒绝」，需要 plan 未列出的新 usage code，且直接推翻 UF-A14 已接受的 ignore 语义（oracle `irrelevant-and-repeated-options` 只要求「明确拒绝或明确忽略」二者之一，但必须明确）；若选择「忽略」，则 basename/exists/regular 之外是否还做 suffix 校验、按什么角色，无依据。第 3 步的重复路径拒绝还会使「delete + 重复 files」从今天的可忽略变为 exit 2，这一行为变化也未声明。
- **为什么有问题**：plan 自称 code-generation-ready，但该组合在 oracle、frozen scenario 与现有代码三方约束下是必须显式冻结的语义，缺失会导致实现跑偏或与冻结证据语义漂移。
- **直接证据**：`ingestion_runtime.py:992-1011`（delete 分支仍走 per-file 循环 + index 角色 + `for_delete()`）；`docs/cli_ci_oracles.json` predicate `upload_filing.irrelevant-and-repeated-options`「delete 的无效文件组合必须明确拒绝或明确忽略」；scenario `upload_filing.UF-A14-delete-with-files-ignored` status=accepted。
- **影响**：实施 Agent 跑偏 / 与 frozen scenario 语义冲突 / 后续返工。
- **建议改法和验证点**：在 §6.2 显式冻结一种：优先保持现有语义（delete-with-files：仍做 normalized basename/exists/regular 校验与 duplicate 拒绝，不做角色 suffix 校验，selection 恒为 `for_delete()`，不新增 usage code），或新增 `FILES_NOT_ALLOWED_FOR_DELETE` closed code 并明确 UF-A14 语义变化。二选一写入 plan，并补一条 delete-with-files 的 owner test 断言 exact code/message 或忽略行为。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### 2-未修复-中-identity 进入 source_fingerprint 使 auto-identical-skip 变为路径敏感，plan 未声明该可观察后果且缺测试

- **位置**：plan §6.6（identity 规则）与 §6.4/§6.7（source fingerprint「继续从 typed original assets 的 identity/hash/size/source 派生」）、Slice 3 测试清单、Slice 4 README 范围。
- **问题类型**：契约缺失 / 测试缺口
- **当前写法**：plan 保留 fingerprint 公式（含 `name` 字段），`name` 改为 path-digest identity；§12 只把「同一内容从不同 normalized path 上传产生不同 identity」标为 contract 而非缺陷，但全文未声明 skip/version 语义的连带变化。
- **反例/失败场景**：用户把同一份 10-Q 从 `/downloads/msft.docx` 移动到 `/data/msft.docx` 后重跑 `--action auto`。今天 `name=basename`，content 不变 → fingerprint 相等 → skip（oracle `action-core`「相同完整输入=skip」）。修复后 `name` 是 path-digest → fingerprint 变化 → `_can_skip_upload` 不跳过 → 走 update：`_resolve_document_version` 版本 +1、`reset_source_document` 全树替换。frozen UF-A02 因同一 argv 路径不变仍 skip，不会暴露该漂移。
- **为什么有问题**：这是用户可见行为变化（skip→update+版本号+整树替换），且 `renamed-update` predicate 只冻结了「内容变化+改名」方向，未覆盖「内容相同+改名」方向；plan 的 Slice 3 测试没有 renamed-identical-content 用例，Slice 4 README 范围也未列该规则。
- **直接证据**：`docling_upload_service.py:1087-1110`（fingerprint payload 含 `asset.name`）、`:1059-1084`（fingerprint 相等才 skip）、`:1113-1133`（fingerprint 不等 → version 递增）；plan §6.6 指纹表述。
- **影响**：用户可见语义漂移无文档、无测试固化，后续 evidence work unit 可能将其误判为回归。
- **建议改法和验证点**：二选一并写入 plan：a) 声明「identical skip 仅对同一规范化输入路径成立；同内容不同路径按 update」并在 Slice 3 增加 renamed-identical-content → update（version+1、旧业务文件移除）的 owner test；b) 若「相同完整输入」应按内容判定，则把 `name` 移出 fingerprint payload（只留 sha256/size/source），并补相应测试。README 同步声明该规则。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### 3-未修复-低-macOS 大小写不敏感文件系统下 membership/duplicate 判定与「规范路径不同」契约存在未冻结的边缘语义

- **位置**：plan §6.2 第 2/3/6/7 步；§3.2「symlink 与 `..` alias 经 canonical resolve 后视为同一路径」。
- **问题类型**：契约缺失
- **当前写法**：duplicate 与 membership 均按 `expanduser().resolve(strict=False)` 后的 `Path` 相等判定；§3.2 只声明「业务事实是规范路径不同」，未冻结 case 变体语义。
- **反例/失败场景**：开发平台 macOS（APFS 默认大小写不敏感）上，`--files /data/A.TXT --primary /data/a.txt` 指向同一物理文件：`Path.resolve()` 不 canonicalize case，`PurePosixPath` 相等是字符串语义 → membership 判定不命中 → `PRIMARY_NOT_IN_FILES` exit 2，用户看到的是「同一个文件」却被告知 primary 不属于 files；反过来 `--files /data/A.TXT /data/a.txt` 不会被判 duplicate，同一物理文件以两个 identity 入库。
- **为什么有问题**：该语义直接决定两个新 usage code 的用户可理解性，且「同一物理文件两个 identity」与 oracle 的 collision-free 目标在物理层面张力；plan 的 stop condition #1（normalized-path 定义需要改变时停止）正覆盖此情形，说明计划自己也认为该定义是裁决点。
- **直接证据**：`Path.resolve` 行为与 `PurePosixPath` 字符串相等语义（Python 3.11 标准行为）；plan §3.2 与 §11 stop condition #1。
- **影响**：用户困惑 / 两个 identity 指向同一 inode / 后续 evidence 工作单元再裁决。
- **建议改法和验证点**：显式冻结：case 变体按「规范路径不同」处理（与 hardlink 同理，文档声明），并补一条 case-variant membership/duplicate 测试固化行为；或声明按平台 `normcase` 归一（需评估跨平台 identity 稳定性）。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低

### 4-未修复-低-material 路径触发 identity 唯一性断言时的失败契约未指定

- **位置**：plan §6.6「生成 original identities 后做一次 request-local uniqueness assertion……必须在 converter/publication 前 fail closed」；§6.6 末段 material 复用同一规则。
- **问题类型**：契约缺失
- **当前写法**：唯一性断言失败只说了「fail closed」，未指定异常类型、错误分类与文案；material 请求不在 filing static validator 覆盖内（`_normalize_upload_request` 对 material 只做 ticker/action/source_kind，`ingestion_runtime.py:7266-7286`），且 material 无 duplicate path 前置拒绝。
- **反例/失败场景**：material 上传 `--files /data/a.txt /data/a.txt`（重复路径）。今天：同名 blob 同批两次写入 + files[] 重复 name → commit validator 拒绝（fail late）。修复后：两个相同 identity → 断言在 `prepare_upload` 阶段（workspace read 之后、converter 之前）抛出，但用户/LLM 看到的是未分类的 ValueError/RuntimeError 而不是 bounded typed failure。
- **为什么有问题**：oracle `malformed-and-empty-input` 与 `error-classification` 要求 typed、有界、可行动错误；断言抛出的未分类异常会从工具路径落入 `Exception` 兜底「上传任务未能启动」，用户不可行动。
- **直接证据**：`ingestion_runtime.py:7266-7286`（material 无文件级静态校验）；plan §6.6 唯一性断言无异常契约。
- **影响**：用户不可行动的失败投影 / 后续返工。
- **建议改法和验证点**：为 material 复用路径指定断言失败的 closed failure（typed `FinsUploadFailureError` 或明确「内部不变量，RuntimeError + operator log」），或把 material duplicate-path 拒绝前移到 material 校验边界；补一条 material duplicate-path 测试。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：低
