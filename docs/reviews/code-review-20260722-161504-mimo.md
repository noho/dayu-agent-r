## Findings

### MIMO-REVIEW-001 [P2] `_close_owned_resources` mandatory step 缺少 try/except 保护，release_host_close 失败会跳过全部 best-effort cleanup

**文件**: `dayu/host/open_host.py:1518-1529`

**描述**:
`_close_owned_resources` 的 docstring 声称 "cleanup 首个错误在全部 owner cleanup 尝试后传播"。但实际实现中，lines 1518-1529 是 mandatory 步骤（无 try/except），lines 1531-1603 是 best-effort 步骤（每个都有 try/except）。

当 `release_host_close()` (line 1529) 因 native mutex release 失败而抛出 `StrictNativeMutexUnavailableError` 时，异常会跳过以下全部 best-effort cleanup：
- `terminal_post_commit_coordinator.close()`
- `transient_delta_hub.close()`
- `projection_catchup_port.catch_up_projection()`
- `durable_actor.close_handle()`
- `durable_actor.shutdown_executor()`
- `scheduler_store.close()` ← SQLite 连接泄漏
- `health_gate.mark_closed()` ← health gate 永不进入 CLOSED

**可执行失败场景**:
1. Session native mutex 文件所在文件系统变为只读。
2. 进程信号中断导致 mutex handle close 操作失败。
3. 任一 record 的 mutex handle 已被外部删除。

**Root cause**: mandatory/best-effort 分界线应把 `release_host_close()` 也纳入 try/except 保护，或将其移入 best-effort 区域。docstring 的 "全部 owner cleanup 尝试后传播" 承诺与实现不一致。

**Semantic owner**: `open_host.py::_PublicHostHandle._close_owned_resources`

**Fix boundary**: 在 `release_host_close()` 调用外包一层 try/except，与后续 best-effort 步骤使用相同的 `close_error` 收集模式。

**Severity rationale**: P2 而非 P1，因为：
- mutex release 失败是罕见边界条件（正常运行不触发）。
- scheduler_store 泄漏的 SQLite 连接在进程退出时会被 OS 回收。
- health gate 未 mark_closed 不影响已关闭的 Host handle 实例。
- 重试 close 时 `begin_host_close()` 幂等返回，但 `release_host_close()` 中 `_records` 已被清空所以不重试 mutex release，导致 `_host_close_released=True` 但 `scheduler_store` 仍然泄漏。

## Areas Reviewed — No Blocking Findings

### 1. 两 opener 同 Session RW/RO、重复 attach、actor/work lease、caller cancellation、consumer-start barrier、close/retry/mutex release

**结论**: 无 blocking findings。

- **跨 opener 互斥**: 每个 opener 独立 `HostSessionAttachmentRegistry`，跨 opener 由 `dayu.runtime.native_mutex` 文件锁保证 RW/RO 降级。设计正确。
- **同 handle 重复 attach**: `begin_attachment` 检查 `self._records` dict，duplicate 抛出 `CONFLICT`。正确。
- **RECOVERING 阻止 new-work**: `try_acquire_new_work_lease` 在 `RECOVERING` + `new_work_lease_count == 0` 时返回 None。recovery 期间 lease count > 0（`acquire_recovery_work_lease` 保持），完成后 release + activate。状态机正确。
- **caller cancellation 安全**: `_invoke_session_mutation` 用 `release_when_done(future)` 绑定 lease 到 actor future 而非 caller awaiter。`asyncio.shield(future)` 防止 caller cancel 传播到 actor。正确。
- **consumer-start barrier**: 四事件同步（started → continue → ready → stream_continue）确保 consumer 建立 durable closeout owner 后再处理 stream，dispatch caller 安装取消处理后才开放 stream 消费。barrier 设计正确，无死锁路径。注意：barrier 无显式单元测试，但 92 个 dispatch scheduler 测试隐式覆盖了完整 dispatch → consume → complete 流程。

### 2. Scheduler mandatory cleanup、residual worker handle、STOPPING→STOPPED、best-effort on_cancel 真实顺序

**结论**: 无 blocking findings。

- **close() 重入安全**: `_closed` + `_close_cleanup_done` 双标志，mandatory 步骤各自有 `_xxx_marked` / `_xxx_done` 标志。重试时已完成步骤跳过，未完成步骤重试。正确。
- **mandatory vs best-effort**: `_mark_host_instance_stopping()` 和 `_mark_host_instance_stopped()` 是 mandatory（失败传播），worker handle close 是 mandatory（`_close_worker_handle_mandatory` 超时传播），lane close 是 mandatory。正确区分。
- **active handle 残留**: `_safe_close_worker_handle` 返回 bool 标识成功/失败，成功时才 `discard` handle。`_close_worker_handle_mandatory` 确保 close 成功后才继续 lifecycle。正确。
- **STOPPING→STOPPED 顺序**: close 先 STOPPING，再取消任务，再关闭 handle/lane，最后 STOPPED。步骤间有 `_xxx_marked` 标志保证重试幂等。正确。

### 4. Proactive request 唯一性、root/root-repair/tier1-3 frozen schedule、per-attempt request digest、manifest/rejection/terminal cross-field、crash resume/exhaustion、后续 reactive operation 隔离

**结论**: 无 blocking findings。

- **cross-field**: `_validate_compacted_manifest_reference` 验证 accepted attempt 是最新 prepared、未 rejected、manifest ref/digest 一致。`_validate_failed_attempt_count` 验证 count 与 prepared|rejected 并集一致。正确。

- **reactive 隔离**: `_project_state` 跳过 `trigger_source=REACTIVE` 的 rows。proactive 和 reactive 使用不同的 operation_id 域。正确。
