## Findings

### F1 — 未修复 — 高 — S4 tier 1-3 recovery loop 缺少 cancellation/stale-state 观测机制

- **位置**: Plan §8 S4 "Error handling/invariants"、design.md:3190
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: Plan §8 S4 写 "Tier fallback must recheck Run status/input cursor before committing accepted output"，但没有说明 recovery loop 在遍历 tier 1-3 期间如何观测 cancellation 或 Run state 变更。
- **反例/失败场景**: proactive compaction 没有 active worker token（design.md:3190）。如果 Run 在 tier 2 compact proposal 执行期间被用户取消，且 tier 1 已失败，recovery loop 继续执行 tier 2 的 compactor 调用而不检查 Run 当前是否仍然允许 compaction，则可能对已取消的 Run 提交 `CONTEXT_COMPACTED`。
- **为什么有问题**: design.md:3190 明确要求 "proactive compaction 在 worker 启动前没有 active worker token，必须使用 durable Run 状态观察 token"，且 "stale / cancelled / session closed / execution replaced / cursor mismatch 不是可 repair 错误；Host 必须丢弃 stale proposal，不写 `CONTEXT_COMPACTED`"。Plan 的 S4 没有引用这一机制，也没有在每次 tier 尝试前后指定 Run state recheck 的具体方式。
- **直接证据**:
  - design.md:3190: "proactive compaction 在 worker 启动前没有 active worker token，必须使用 durable Run 状态观察 token；reactive compaction 必须复用 Engine envelope 中的 run-local cancellation token"
  - design.md:3190: "stale / cancelled / session closed / execution replaced / cursor mismatch 不是可 repair 错误；Host 必须丢弃 stale proposal，不写 CONTEXT_COMPACTED"
  - Plan §8 S4: "Tier fallback must recheck Run status/input cursor before committing accepted output" — 仅在 commit 前检查，未覆盖 proposal 执行期间的 cancellation 观测
- **影响**: 实施 Agent 可能写出不检查 Run state 的 recovery loop；tier 失败后盲跑下一 tier，在 Run 已取消/stale 后仍提交 `CONTEXT_COMPACTED`，造成状态不一致。
- **建议改法和验证点**:
  1. S4 的 "Error handling/invariants" 中补充：每次 tier 尝试前必须通过 durable Run 状态观察 token 检查 Run 仍处于可 compaction 状态；stale/cancelled/closed 时立即停止 recovery loop 并走 tier 4/5 或 fail closed。
  2. S4 测试应包含：Run 在 tier 1 失败后、tier 2 执行前被取消，验证不写 `CONTEXT_COMPACTED` 且正确处理。
- **修复风险**: 低 — plan 文本补全，不涉及代码
- **严重程度**: 高

### F2 — 未修复 — 中 — S2 fallback selected caps 与现有 budget estimator loop 的集成方式未指定

- **位置**: Plan §8 S2 "Exact allowed changes"、`context_fallback.py:333-413`
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan §8 S2 写 "Apply `fallback_selected_recent_window_item_cap` and `fallback_selected_recent_window_char_cap` from `MemoryProjectionPolicy` in fallback selection." 但没有说明这两个 cap 与现有 `build_recent_window_fallback_selection` 中 budget-estimator-based loop 的集成方式。
- **反例/失败场景**: 现有 fallback selection 使用 budget estimator 循环：先取 floor blocks，如果 `hard_budget_passed`，再逐个追加 reverse chronological raw blocks 直到下一 block 触发 hard threshold（`context_fallback.py:384-400`）。如果新加 `item_cap` 和 `char_cap`，实施 Agent 面临两个选择：
  - (a) 先按 cap 裁剪，再通过 budget estimator 验证：cap 与 budget estimator 是两层过滤，但 cap 可能过紧导致 floor 被裁；
  - (b) 先通过 budget estimator 选择，再按 cap 裁剪：cap 可能裁掉 estimator 认为安全的 blocks。
  无论哪种，plan 都没有说明 floor vs cap vs budget estimator 的三方优先级。
- **为什么有问题**: Plan §8 S2 的 invariant 写 "Floor wins over item/char caps" 但这是在 selection 内部的规则；budget estimator 的 hard threshold 是外部约束。当 floor + cap 内 blocks 的 estimated budget 超过 hard threshold 时，行为未定义——是继续裁 cap 内 blocks、降 floor、还是进入 tier 5？
- **直接证据**:
  - `context_fallback.py:384-400`: budget estimator loop 以 hard_budget_passed 为停止条件
  - Plan §8 S2: "Apply fallback_selected_recent_window_item_cap and fallback_selected_recent_window_char_cap"
  - Plan §8 S2 invariant: "Floor wins over item/char caps. If floor set itself exceeds hard budget, fallback action becomes fail closed or tier 5 according to dispatch state."
  - 但 invariant 只覆盖 "floor 本身超标" 的情况，未覆盖 "floor + cap 内 blocks 超标" 的情况
- **影响**: 实施 Agent 可能需要自行设计 cap/budget/floor 三方交互语义，违反 plan 的 "不让 implementation agent 重新设计 contract" 约束。
- **建议改法和验证点**:
  1. Plan §8 S2 补充 cap/budget/floor 三方优先级：先按 floor 保护 blocks；在 floor 基础上按 item_cap / char_cap 追加 blocks；追加结果通过 budget estimator 验证；若 hard_budget_passed，按 char_cap 降序裁剪已选 blocks 直到通过或只剩 floor；floor 单独超标则进入 tier 5/fail closed。
  2. S2 测试应包含：floor + cap 内 blocks 的 estimated budget 超过 hard threshold 的场景。
- **修复风险**: 低 — plan 文本补全
- **严重程度**: 中

### F3 — 未修复 — 中 — S3 的 selected-id/source-ref provenance drift 测试策略不够 adversarial

- **位置**: Plan §8 S3 "Completion signal"、§9 "Expected Assertions"
- **问题类型**: 测试缺口
- **当前写法**: Plan §8 S3 的 completion signal 为 "Tests prove selected ids render all and only selected blocks, source refs are preserved, missing selected ids fail closed." Plan §9 补充 "Selected block ids in fallback payload all exist in the rendering material view; missing ids fail closed."
- **反例/失败场景**: 当前 `_fallback_context_messages`（`run_input.py:2723-2730`）的 fail-closed 检查是：selected block id 不在 material view → `HostDurableError`。Plan §8 S3 要扩展检查 "current input source ref, duplicate ids, selected source refs and fallback digest consistency when available"。但构造一个 source ref mismatch 的测试需要：
  - 要么并发修改 material view（不可测试，因为 view 是 frozen tuple）；
  - 要么在 test fixture 中故意注入 mismatched refs。
  如果实施 Agent 只写 happy-path 测试（所有 refs 匹配），则 source ref check 代码虽然有，但从未在 mismatch 场景下被 exercised。
- **为什么有问题**: Plan 的目标是 "fail closed when selected ids / source refs drift"。但如果测试不包含 deliberately mismatched fixtures，fail-closed 路径只是 dead code，真正的 drift 可能在集成中静默通过。
- **直接证据**:
  - Plan §8 S3: "Strengthen `_fallback_context_messages` to check not only missing ids but also current input source ref, duplicate ids, selected source refs and fallback digest consistency"
  - Plan 未指定如何构造 source ref mismatch 的 test fixture
  - `run_input.py:2723-2730` 当前只检查 id presence 和 uniqueness
- **影响**: source ref check 代码可能被写但从未被 adversarial fixture 验证；真正的 provenance drift 在生产中可能被漏掉。
- **建议改法和验证点**:
  1. Plan §8 S3 补充测试策略：构造 deliberately mismatched fallback payload（例如 `selected_block_ids` 包含不存在 id、`current_input_ref` 指向错误 block、`source_refs` 与 material view 不一致），验证每种 mismatch 都 raise `HostDurableError`。
  2. Plan §9 补充：测试必须包含至少一个 selected-id 不存在、一个 current_input_ref 不匹配、一个 source_ref 不匹配的 fail-closed case。
- **修复风险**: 低 — plan 补全测试策略
- **严重程度**: 中

### F4 — 未修复 — 中 — S4 section-aware degrade "禁止动作未发生" 的测试需要具体 fixture 设计

- **位置**: Plan §8 S4 "Completion signal"、§9 "Expected Assertions"
- **问题类型**: 测试缺口
- **当前写法**: Plan §8 S4 completion signal: "all section-aware degrade forbidden actions are asserted absent." Plan §9: "Section-aware degrade never truncates semantic item text, rewrites summary/fact/anchor/intent/reference continuity, creates a new summary or creates Session Semantic Memory."
- **反例/失败场景**: "assert truncation did not happen" 需要测试构造一个语义 item 文本长于任何合理 cap 的场景，然后验证 degrade 后该 item 的文本与原始文本 byte-exact 相同（未被截断）或整个 item 被 drop（不是部分截断）。如果测试只构造短文本 item 然后检查 `len(text) <= some_cap`，则截断行为（如 `text[:cap]`）会通过测试，因为短文本不受截断影响。
- **为什么有问题**: 验证 "禁止动作未发生" 比验证 "允许动作已发生" 更难。没有具体 fixture 设计，实施 Agent 可能写弱测试——例如只用不超过 cap 的短文本验证 degrade 后文本不变，但这不能检测截断 bug。
- **直接证据**:
  - Plan §9: "Section-aware degrade never truncates semantic item text"
  - design.md:3263 degrade 禁止列表第一条："禁止截断 semantic item text"
  - Plan 未指定如何构造会触发截断的 fixture（长文本 semantic item）
- **影响**: degrade 截断 bug 可能在测试中漏过，在生产中被长文本触发。
- **建议改法和验证点**:
  1. Plan §8 S4 或 §9 补充：degrade 测试必须包含至少一个 semantic item 的 `claim_text` / `text` / `display_text` 超过 policy cap 的 fixture；验证 degrade 后该 item 要么完整保留（text byte-exact 相等），要么整体 drop（不在 degrade 输出中），不得出现部分保留（text 是原始 text 的前缀但不等长）。
  2. 同样构造 summary rewrite 的 fixture：验证 degrade 后的 summary_text（如果有）与原始 `latest_accepted_compacted_view` 中的 summary text 逐字相同，不是 rewrite。
- **修复风险**: 低 — plan 补全 fixture 设计
- **严重程度**: 中

### F5 — 未修复 — 低 — S2 缺少 "material block 缺少 run_id 时不应静默丢弃" 的测试

- **位置**: Plan §11 "Risks / Open Questions"、§8 S2
- **问题类型**: 测试缺口
- **当前写法**: Plan §11: "If any material path lacks `run_id` for eligible raw turn blocks, implementation must trace the EventLog source and fix the projection path. Do not add nullable fallbacks that silently remove the block from protected floor."
- **反例/失败场景**: S1 给 `RunInputMaterialBlock` 加 `turn_group_id: str | None`，S2 用 `turn_group_id` 计算 protected turn groups。如果某个 raw turn block 的 `turn_group_id` 为 `None`（因为其来源 EventLog 路径缺少 `run_id`），S2 的 turn-group selector 会跳过该 block。当前没有任何测试验证这种缺失会被检测到（例如通过 log/diagnostic）而非静默丢弃。
- **为什么有问题**: Plan 自己识别了这个风险（§11）但 S2 的 completion signal 和 §9 expected assertions 都没有包含 "缺少 run_id 的 eligible block 应产生 diagnostic" 的测试要求。实施 Agent 可能实现为 `if turn_group_id is None: continue`，使受保护 block 静默丢失。
- **直接证据**:
  - Plan §11: "If any material path lacks run_id ... Do not add nullable fallbacks that silently remove the block from protected floor"
  - Plan §8 S2 completion signal: "Tests create at least two Host Run groups with multiple blocks per group and prove the floor preserves all eligible blocks from the newest N groups" — 仅覆盖 happy path
  - Plan §9: 未要求 "missing turn_group_id for eligible block produces diagnostic"
- **影响**: 生产环境中 material block 来源路径若缺少 `run_id`，block 静默丢失，protected floor 缩小，且无 diagnostic 痕迹。
- **建议改法和验证点**: Plan §8 S2 completion signal 或 §9 补充：测试验证 eligible raw turn block 若 `turn_group_id=None`，行为是 "记录 diagnostic 并仍纳入保护" 或 "fail closed"，不得静默丢弃。
- **修复风险**: 低 — plan 补全
- **严重程度**: 低

- Single policy owner 模式符合项目已有 `MemoryProjectionPolicy` 设计
- Slice 切分沿模块边界，每个 slice 有可独立验证的 completion signal
- 每个 slice 有 stop condition，防止 scope creep

## Optimal-Solution Review

Plan 的方案是最小路径：不引入新 abstraction、不新增 public API、不新增 schema/EventLog 类型、复用已有 policy/builder/selector/renderer infrastructure。相比替代方案（如：保持多个 policy owner、保持 item-based floor、保持 tier 4/5-only fallback），plan 的方案更安全且与设计真源对齐。

**结论**: plan 是 credible alternatives 中最实际的路径。
