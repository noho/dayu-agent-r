## Challenge: test-only fallback helper

### 背景

Plan S3 "Exact allowed changes" 引入新要求：

> 若既有 skip helper 当前以 `pytest.skip` 作为控制流，则只在 `public_smoke_support.py` 的测试基础设施 owner 内抽取可复用的"分类结果/原因"helper，让既有 skip helper 与 Mimo -> DeepSeek selector 共用同一组 marker 真源；不得在 smoke 测试复制 marker 或解析 skip 文本。

### 代码事实

- `public_smoke_support.py:129-184`：四组环境分类 marker（`_NETWORK_FAILURE_MARKERS`、`_TEMPORARY_PROVIDER_UNAVAILABLE_MARKERS`、`_EXPLICIT_UNAVAILABLE_MARKERS`、`_TEMPORARY_PROVIDER_RATE_LIMIT_MARKERS`）是模块级常量，构成环境分类的唯一真源。
- `public_smoke_support.py:1251-1286`：`_skip_if_provider_failure_message()` 将分类逻辑与 `pytest.skip()` 控制流耦合在同一函数中。当前无法在不触发 skip 的前提下获取分类结果。
- `public_smoke_support.py:1220-1248`：`skip_if_provider_terminal_failed()` 和 `skip_if_provider_exception()` 是公开 API，均委托到 `_skip_if_provider_failure_message()`。
- Plan 只在 `public_smoke_support.py`（测试基础设施）内修改，不触及任何 production provider 路由代码。

### 裁决: 方案自足，无新增 production 语义风险，存在一处轻微欠规格

**唯一环境分类真源判断**：四组 marker 常量已是唯一真源。plan 要求的"共用同一组 marker 真源"意味着新 helper 读取同一组 marker 常量，不复制、不分叉。分类结果（network_unavailable / server_overloaded_or_transient / explicit_unavailable / resource_exhausted）与既有 `pytest.skip` message 中的 `provider_availability` 标签一致。这保持了唯一真源。

**不扩 production provider 语义判断**：
- Plan 的 affected files 表中 `public_smoke_support.py` 的变动描述为："复用既有精确环境失败分类，为 Mimo -> DeepSeek 测试级 fallback 暴露非跳过式分类结果；不改 production provider 路由"。
- Plan non-goal 第 7 条明确不修改 "provider/model selection"。
- 新 helper 只影响 smoke 测试中 provider 不可用时的 fallback 决策，与 production 的 provider 选择（由 `execution_profiles.json` + `RunnerSpec` 控制）完全正交。
- 没有证据表明 plan 会将分类逻辑移入 `dayu/runtime/`、`dayu/host/` 或任何 production package。

**轻微欠规格**：plan 未明确新 helper 的返回契约（签名、返回类型、分类类别枚举）。当前 `_skip_if_provider_failure_message()` 通过调用 `pytest.skip()` 隐式表达分类；新 helper 需要显式返回结构化分类结果。实施 agent 需自行设计该契约。但由于：
1. 修改范围限定在 `public_smoke_support.py` 单文件内（测试基础设施），
2. 既有 skip helper 与新 selector 的调用方都在同一 smoke 测试文件中，
3. 分类类别已由四组 marker 常量定义，
此欠规格不影响 plan 的 code-generation-readiness，实施 agent 可合理完成设计。

**结论**：test-only fallback helper 方案保持唯一环境分类真源，不扩 production provider 语义。不构成 blocker。

## 新发现问题

### R1-新发现-低-"发起一次真实 provider proposal"与 Mimo-first fallback 的两次调用可能

- **位置**: plan S3 "Exact allowed changes" 第 5 条
- **问题类型**: 表述歧义
- **当前写法**: plan S3 写"构造单个 typed input...再用 production prompt renderer 发起一次真实 provider proposal"。同时 S3 的 Mimo-first fallback 逻辑允许：先尝试 Mimo → 若 Mimo 真实调用失败且被分类为环境不可用 → 改用 DeepSeek。这意味着最坏情况下会有两次 provider API 调用（Mimo 失败 → DeepSeek），与"发起一次"的字面含义存在轻微张力。
- **为什么有问题**: 实施 agent 可能对"一次"做字面解读（只允许一次 API 调用），与 Mimo-first-with-fallback 的两次潜在调用冲突。但 plan 的 Mimo-first fallback 描述已足够明确（"只有 Mimo...失败被...精确分类判定为环境不可用时，才改用 DeepSeek"），实际意图清楚。
- **直接证据**: plan S3 "Exact allowed changes" 第 5 条 vs 第 1-4 条。
- **影响**: 低——plan 的 Mimo-first fallback 规则已明确两次调用的条件与顺序，"一次 proposal"的表述歧义不会导致实施 agent 做出错误实现。
- **建议**: 实施时将"发起一次真实 provider proposal"理解为"最终产生一次成功的 provider proposal"或在 implementation artifact 中澄清实际调用次数。
- **严重程度（低/中/高/严重）**: 低
