### 2.1 C-R1 typed initial disposition

- **disposition 产生与既有 skip 语义同源**：`_can_skip_upload`（`docling_upload_service.py:1264-1296`）无 action 参数；其返回 True 的门槛是 repair=False、`overwrite=False`、`previous_meta is not None`、`is_deleted=False`、`identical_skip_safe=True`、fingerprint 相等。explicit `update` identical sequential 重传（overwrite=False、target COMPLETE、fingerprint 相同）命中返回 True → preparation owner 在同一点产生 `IDENTICAL_PUBLICATION`。**explicit update identical stable skip 被真实保留**，且该 disposition 不经 action/fingerprint/bool 在下游重算（§6.3 冻结）。
- **changed `COMPLETE -> COMPLETE` 不会误 skip**：predicate A（§7.3.A）要求 observation 按 §7.2 stable，即 status 不变且 `has_same_source_publication_identity()` 为真；该函数只比较 opaque revision（`source_integrity.py:262-287`），而 revision 由 `_fs_source_document_core.py:1931` 在每次 source 发布时写入 `uuid4().hex` —— 任何并发 winner 发布必然改变 revision，changed `COMPLETE -> COMPLETE` 结构性不满足 A。predicate B 要求 initial 精确 `MISSING -> COMPLETE`，同样不命中。§7.4 表第 8 行显式冻结 changed `COMPLETE -> COMPLETE` 即使 identity exact equal 也固定 `SOURCE_PUBLICATION_CONFLICT`。**不误 skip 由 revision 机制 + 封闭表双重保证**。
- overwrite=True / previous_meta=None / deleted / repair 情形 `_can_skip_upload` 固定 False → disposition 为 `NOT_ELIGIBLE`，predicate A 不可能改写它们，与 §6.3 声明一致。
- 测试覆盖：S1 exact test 5（explicit update 与 auto sequential 重传均 skipped、stored=0、revision/version/tree 不变）、test 6（changed `COMPLETE -> COMPLETE` 即使 identity equal 也 conflict）、S2 test 10（concurrent changed explicit update 后 writer typed conflict）。**覆盖充分**。

### 2.2 explicit create/no-overwrite conflict 与 create-overwrite rebase

- **conflict 分支**：`evaluate_upload_overwrite_precondition`（`docling_upload_service.py:215-241`）对 create + exists + `not overwrite` 返回 `CREATE_TARGET_EXISTS`；batch fresh validator（`ingestion_runtime.py:1490-1504`）用同一 helper 复检，显式 create + `overwrite=False` + fresh COMPLETE 必然 raise `FinsUploadUsageError(CREATE_TARGET_EXISTS)`，§6.4 映射表将其封闭改写为 `SOURCE_PUBLICATION_CONFLICT`。action 真源：validator 抛错时无 fresh validated request，failed terminal 按 plan 取 initial prepared action；`resolve_upload_action`（`docling_upload_service.py:1557-1562`）显式动作恒保持 `create`，因此 requested/resolved/filing 恒为 `create/create`，绝不改写为 auto/update。**owner 正确**。
- **create-overwrite rebase 分支**：validator 对 create + `overwrite=True` + COMPLETE 返回 `ALLOWED`（precondition 只在前者缺 overwrite 时触发），resolved action 保持 `create` → §7.4 第 3 行 rebase 后 `PUBLISH` 可达，不与 §6.4 的 conflict 映射冲突。
- **fresh previous_meta 来源存在**：`FilingUploadPublishedState.source_meta`（`repository_protocols.py:151`）携带 raw meta，且 `__post_init__`（`:175-176`）强制 COMPLETE 状态必带 source_meta —— `rebase_prepared_filing_create_overwrite(prepared, *, fresh_previous_meta: JsonObject)` 的输入在 batch fresh state 上可得，无需再读 published 路径。
- **版本/修订不使用 stale plan**：`_resolve_document_version`（`:1393-1418`）为模块级函数，以 fresh meta + prepared fingerprint 重算 version（同 fingerprint 保持 winner 版本、不同 fingerprint 递增）；`_store_upload_assets` 的 `replace_existing` 判定（`:577`）依赖 rebase 后 `previous_meta` 非 None 走 reset + blob-first 重建，`_create_source_document` 写入的 meta 携带新的 revision uuid（storage owner 写入）。prepared bytes/fingerprint 复用无版本污染。**方向正确**，唯一残留的规格空隙见 F-2。

### 2.3 C-R2 双 cancel checkpoint

- **checkpoint 1**（§7.1 步骤 4）：`begin_batch` 在 `_acquire_ticker_lock`（`_fs_storage_infra.py:1743-1761`，`blocking=True`）等待期间无 token；token 取得后、任何 fresh read/arbitration 前立即观察 cancel —— 此时裁决尚未计算，SKIP/CONFLICT/PUBLISH 三类 prospective 候选统一 cancel-first，命中即 rollback（`rollback_batch` `:1363-1397` 消费 token、journal + rmtree、释放 writer）。**等待 writer 期间取消不会投影为任何业务 terminal**。

- 测试覆盖：S1 exact test 9/10、S2 test 12 均要求用 deterministic writer barrier 覆盖三类候选在两个 checkpoint 的取消、rollback 失败 `STORAGE_IO` 与 late-cancel 边界。**可实现**（loser 阻塞在 blocking lock 等待期间从测试线程 set cancel，时序确定、无 sleep）。

### F-2-未修复-低（non-blocker）-create-overwrite rebase 的 staging meta 重建未 pin 到唯一构造 owner，模块级签名与既有 `_build_upsert_meta` 实例方法之间存在一条未规格的实现路径

- **位置**: plan §6.3 `rebase_prepared_filing_create_overwrite` 签名、§5 ownership 表「create-overwrite fresh rebase与staging write」行
- **问题类型**: 契约缺失 / 语义所有权
- **当前写法**: §6.3 给出模块级签名 `rebase_prepared_filing_create_overwrite(prepared, *, fresh_previous_meta: JsonObject) -> PreparedDoclingUpload`，说明「由Docling owner重算document version/staging meta」；但 staging meta 的唯一既有构造器 `_build_upsert_meta` 是 `DoclingUploadService` 的实例方法（`docling_upload_service.py:943-981`，覆盖 updated_at/first_ingested_at/created_at/document_version/source_fingerprint/ingest_complete/source_provider/is_deleted/deleted_at 九个字段）。模块级 helper 无法直接调用实例方法。
- **反例/失败场景**: 实现 Agent 按冻结签名落地时要么在模块级复制一份 meta 构造逻辑，要么自行决定把 `_build_upsert_meta` 提升为模块级 helper。前者产生两份 meta 构造真源：任一漂移（例如漏掉 `first_ingested_at` 的 fresh 继承）会让 create-overwrite 的 durable meta 语义与既有 replace-existing 不一致——这正是本 work unit 要消灭的 stale plan 类错误在另一个字段上的重演；后者则意味着 plan 未写入的实现改动。
- **为什么有问题**: AGENTS.md 要求「重复逻辑必须抽取」「每个派生值必须有唯一 owner」；plan 已把 version 重算 pin 到模块级 `_resolve_document_version`（明确、无歧义），但 meta 重建走哪条路径未 pin，是四项用户核对项（create-overwrite rebase）内唯一的规格空隙。
- **直接证据**: plan §6.3 模块级签名；`docling_upload_service.py:943`（实例方法）与 `:1393`（模块级函数）的形态差异；`:967-981` 的九字段构造清单。
- **影响**: 最坏情况 create-overwrite 重放丢失 first_ingested_at/created_at 或写入错误的 document_version —— durable meta 语义分裂；大概率只是实现期的一次小改版。
- **建议改法和验证点**: pin 二选一：(a) 将 `_build_upsert_meta` 提升为模块级 helper（它不使用 self 状态），`rebase` 与 `prepare_upload` 共用；(b) rebase 由 `DoclingUploadService` 方法承载并直接复用 `_build_upsert_meta`。S1 exact test 7 增加断言：rebase 后 candidate 的 `meta.first_ingested_at/created_at` 与 fresh previous_meta 一致、`document_version` 按 fingerprint 正确（与 winner 版本一致或递增），`previous_meta is fresh meta`。
- **修复风险（低）**
- **严重程度（低）**；**blocker: 否**
