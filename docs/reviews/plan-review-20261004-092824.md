## Findings

### 1-未修复-高-canonical digest basis 既定公式与计划文字不符：按计划实现会产生与全部冻结 digest 值不同的定义

- **位置**：§4「Schema、data flow 与唯一owner」Digest 段（计划第 125 行；与 plan-before 第 98 行逐字相同，此前从未经过 planreview）。
- **问题类型**：契约缺失 / 事实错误（digest 契约）。
- **当前写法**："registry digest basis去掉**顶层**registry_status/readiness_proof后canonical全值（两个文件各自），不递归删record业务字段；两个proof相互引用对方basis，无自hash循环。"
- **反例/失败场景**：实施者照此实现 validator 的 basis 计算与 `--check` 复算：新 proof 的 `registry_digest_basis` 将为 sha256(canonical(整文件去顶层 status/proof))，实测 oracle 文件 = `9561322d…`、scenarios 文件 = `264b42be…`（后者还把顶层 `readiness_proof_history_20260802` 纳入覆盖）。而两 registry 现有 proof 的 4 个冻结值全部等于"仅 records 数组"的 canonical digest：`canonical(oracles数组)` = `b99a7339…`、`canonical(scenarios数组)` = `9de64adb…`；且交叉字段严格互指（oracle proof 的 `scenario_registry_digest_basis` 与 scenario proof 的 `registry_digest_basis` 同为 `9de64adb…`；scenario proof 的 `accepted_oracle_registry_digest_basis` 与 oracle proof 的 `registry_digest_basis` 同为 `b99a7339…`）。带 key 包裹（`{"oracles":[…]}`）也不等于冻结值——规则唯一地是"records 数组本身"。
- **为什么有问题**：同一字段名将出现两套互不相等的公式（v5 冻结值 vs v6 新值）而计划未声明重定义。docs/cli_ci.md §4.6 要求"新总控必须重新计算并校验两个 registry 的 proof"——按历史证据复算的独立复核会判新 proof 不一致（或反向判 6 个历史值不一致），迫使 v5/v6 兼容分支（AGENTS 禁止 compat），甚至误导实现者"修正"冻结值；这正是本 WU 要消除的不可复核性。注意 plan §6 "两个proof registry digest相互正确"的断言不能自发现该问题：producer 与 checker 共用同一错误公式时自洽。
- **直接证据**：只读复算（`json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",",":"))` + SHA-256）：records 数组两值精确命中全部 4 个冻结值；"整文件去顶层 status/proof"两值 `9561322d…`/`264b42be…` 与任何冻结值不等。冻结值另由 `.before` 与当前文件字节相等、F/fact-check `proof_exact_equal`、root audit `old_registry_complete_value_equals_before` 佐证。
- **影响**：validator/proof/registry 产出与历史语义冲突的 digest；未来 conformance/root/第三方复核可能错误判 ready registry invalid，或引入兼容分支；复核成本外溢到后续所有 gate。
- **建议改法和验证点**：将该句改写为可复现公式："`registry_digest_basis` = 该文件 records 数组（`oracles` / `scenarios`）的 canonical digest；跨文件字段 `scenario_registry_digest_basis` / `accepted_oracle_registry_digest_basis` = 对方 registry records 数组的同法 digest；不读取、不递归删改 record 业务字段"。验证：validator 契约测试用未变更的现文件复算必须精确得到 `b99a7339…`/`9de64adb…`；S1 首次 `--check` 前先对两个冻结值断言。若确为有意重定义，必须显式标注 proof_version=6 起生效、旧值不迁移并同步 docs/cli_ci.md，禁止两定义并存而无数说明。
- **修复风险**：低（一段改写 + 一条断言）。
- **严重程度**：高。
