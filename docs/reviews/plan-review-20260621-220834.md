## Findings

### DS-F01-未修复-高-dispatch-wakeup-gap

- **位置**: Plan §Implementation Decisions, 第 218-219 行；§Slice 1 adapter flow step 7-8
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: Plan 要求 Host callback adapter 直接调用 `DefaultHostResolveWaitService` 而非公共 `resolve_wait(...)` facade，理由是后者返回 `RunSnapshot` 丢失 `idempotent_replay` 字段。Plan 未提及 dispatch wakeup 逻辑。
- **反例/失败场景**: 当 callback adapter 调用 `DefaultHostResolveWaitService.resolve_wait()` 返回非 replay 的 `ResolveWaitResult`（含新的 `dispatch_record`）时，没有任何代码触发 `wake_dispatch(...)`。该唤醒逻辑当前仅在 `command.py:769-770` 中——检查 `result.dispatch_record is not None and not result.idempotent_replay` 后调用 `host._admission_service.wakeup_port.wake_dispatch(...)`。缺少此唤醒意味着 resumed/dispatched attempt 的 dispatch record 已持久化但永远不会被 worker 拾取执行。Run 会卡在 WAITING 状态，表面上看已 resolve，但 resume 永远不开始。
- **为什么有问题**: Plan 正确识别了 facade 丢失 `idempotent_replay` 的问题，但提出的绕过方案（直接调用 service）破坏了 resume dispatch 的完整性。这不是一个可以被 follow-up slice 修复的次要遗漏——它直接导致 callback 触发的 resume 静默失败。
- **直接证据**: `command.py:769-770` 在 `resolve_wait()` 命令路径中显式条件唤醒 dispatch。plan 的 adapter flow 完全未引用 dispatch wakeup、HostCommandHandle 或 wakeup_port。
- **影响**: 实施 Agent 若严格按 plan 实现，callback resolve 创建的 resume dispatch 将永远不会被执行——callback "成功"返回 ACCEPTED 但 Run 实际上永远卡在未调度的 resume 状态。
- **建议改法和验证点**:
  1. Plan 必须明确 adapter 如何触发 dispatch wakeup。可行方案包括：(a) adapter 接收 `wakeup_port` 注入并在非 replay 且 `dispatch_record is not None` 时调用 `wake_dispatch`；(b) 扩展公共 facade 返回包含 `idempotent_replay` 的结果类型，adapter 走公共 facade 路径；(c) 在 adapter 文档化中明确说明它必须复制 command.py 的 dispatch wakeup 逻辑。
  2. Slice 1 测试必须包含：callback resolve 产生新 dispatch 时，wakeup port 被实际调用。
  3. Slice 1 测试必须包含：replay 时 wakeup port 不被调用。
- **修复风险**: 低——仅需补充 adapter 接口注入和一条条件调用。
- **严重程度**: 高——未修复会导致 callback-triggered resume 静默失败，是生产不可用级别的缺陷。

### DS-F02-未修复-中-error-disambiguation-fragile

- **位置**: Plan §Slice 1 adapter flow step 9, 第 250 行
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: "Map `HostApiErrorCode.NOT_FOUND` to `UNKNOWN_WAIT`; `IDEMPOTENCY_CONFLICT` to `IDEMPOTENCY_CONFLICT`; invalid state plus wait status to `LATE_WAIT_CANCELLED`, `LATE_WAIT_LOST`, or `INVALID_WAIT_STATE`"
- **反例/失败场景**: `DefaultHostResolveWaitService.resolve_wait()` 对多种不同原因均抛出 `HostApiError(code=INVALID_STATE, message="...")`：empty wait_id、wait already resolved by another key（非 replay 非 conflict）、late rejection（cancelled/lost/run terminal/invalid state）、以及 "wait record is no longer resolvable"。adapter 只能拿到一个 `INVALID_STATE` 错误码和一个人类可读 `message` 字符串。Plan 要求按 "invalid state plus wait status" 做 secondary classification，但 adapter 在 resolver 抛出异常后无法可靠获知 resolver 内部判定的 wait status——pre-read（step 3）存在 TOCTOU 窗口（pre-read 显示 CANCELLED，但 resolver 事务内状态可能已变为 RESOLVED）。
- **为什么有问题**: 把状态映射依赖于异常消息解析或 TOCTOU 外部读取，是不可靠的实现策略。adapter 可能在 wait 被另一个并发 resolve 提前处理时将 `LATE_WAIT_CANCELLED` 误判为 `INVALID_WAIT_STATE`，或反之。
- **直接证据**: `waiting.py:620-653` 中 `resolve_wait()` 抛出多种 `INVALID_STATE` HostApiError，message 不包含稳定机器可读的状态码；adapter step 3 的 pre-read 在 resolver 事务外执行，无法保证与事务内状态一致。
- **影响**: 实施 Agent 需自行设计错误分类方案，可能产生不可靠的 status mapping 或为弥补此缺口引入 resolver 内部修改（违反 plan 的 "不修改 resolve_wait 状态机" 约束）。
- **建议改法和验证点**:
  1. Plan 应明确 adapter 如何区分不同 `INVALID_STATE` 场景。最简方案：adapter pre-read wait status 用于 `STALE_CALLBACK` 和 `UNKNOWN_WAIT`（不进入 resolver），但对所有其他 `INVALID_STATE` 统一映射为 `INVALID_WAIT_STATE`，不做 secondary 细分——除非 `HostApiError` 增加稳定子码或 resolver 返回结构化拒绝原因。
  2. 或者：plan 明确要求 `DefaultHostResolveWaitService` 对 late rejection 抛出更具体的错误子类型（但 plan 说"不修改 resolve_wait 状态机"——需要裁决这个矛盾）。
  3. 至少：plan 应列出 `INVALID_STATE` 的每种可能原因和适配器的默认 safe mapping（如全部映射为 `INVALID_WAIT_STATE` 并保留 message），避免实现 agent 自行发明不可靠的分类逻辑。
- **修复风险**: 低——缩小 adapter 的 status mapping 语义即可，不需要修改 resolver。
- **严重程度**: 中——不会导致数据损坏，但会导致不准确的 status 分类和 diagnostic。

### DS-F03-未修复-中-json-outcome-mapping-underspecified

- **位置**: Plan §Exact Callback Endpoint Form, 第 194-200 行；§Slice 2
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan 给出 `outcome.kind = "completed"` 的 JSON 示例，并声明四种 `outcome.kind` 值一对一映射到 `ResolveWaitCompletedOutcome` / `ResolveWaitFailedOutcome` / `ResolveWaitCancelledOutcome` / `ResolveWaitLostOutcome`。
- **反例/失败场景**: 仅 `completed` 给出了完整 JSON 示例。`failed` 需要构造 `ToolResultFailure`（含 `error_code`、`message`、`meta`），`cancelled` 需要构造 `ToolCancelledOutcome`（含 `reason_code`、`message`），`lost` 需要构造 `ResolveWaitLostOutcome`（含 `reason_code`、`message`、`provider_status_ref`）。这些内部类型的 JSON 形状未在 plan 中定义。Service mapper 实现者需要自行推断 JSON schema，可能与 callback sender 的期望不匹配。
- **为什么有问题**: Service mapper 是 callback endpoint 的唯一 typed 入口。如果 JSON-to-outcome 映射未充分规格化，implementation agent 需要自行设计每种 outcome kind 的 JSON shape——这个决策会影响 callback sender 的集成契约，不应留给 implementation agent 猜测。
- **直接证据**: `ResolveWaitFailedOutcome` 需要 `ToolResultFailure`（`api.py:470-494`），`ResolveWaitCancelledOutcome` 需要 `ToolCancelledOutcome`（`api.py:497-524`），`ResolveWaitLostOutcome` 需要 `reason_code` + `message`（`api.py:527-539`）。Plan 的 JSON body 示例仅覆盖 `completed`。
- **影响**: 实施 Agent 可能为 `failed`/`cancelled`/`lost` 选择与实际 callback sender 不兼容的 JSON shape，导致集成返工；Service mapper 测试可能只覆盖一种 outcome kind。
- **建议改法和验证点**:
  1. Plan 必须为 `failed`/`cancelled`/`lost` 三种 outcome kind 各提供一个完整 JSON body 示例。
  2. Slice 2 测试必须覆盖全部四种 outcome kind 的解析。
- **修复风险**: 低——仅补充规格，不改变实现方案。
- **严重程度**: 中——不阻塞 Host 侧实现，但会让 Service mapper 实现在缺少规格的情况下猜错契约。

### DS-F04-未修复-中-stale-check-expires-at-never-populated

- **位置**: Plan §Contract, stale rule 第 162 行；§Risks 第 374 行
- **问题类型**: 契约缺失
- **当前写法**: "若 wait record 有 `deadline_at` 或 `expires_at`，且 `completed_at` 晚于该边界，adapter 返回 `STALE_CALLBACK`"。Plan 的风险章节承认 "如果 current wait records 很少 populate 那些字段，测试必须显式 seed"。
- **反例/失败场景**: `expires_at` 在 wait record 创建时始终设为 `None`（`waiting.py:2008`）。当前代码路径中没有任何位置将 wait record 的 `expires_at` 设置为非 `None` 值（`tool_runtime.py` 中的 `expires_at` 是 duplicate governance cursor 的 TTL，不是 wait record 的字段）。因此 `expires_at` 在当前系统中对 wait record 永远是 `None`，stale check 实际只依赖 `deadline_at`。
- **为什么有问题**: Plan 同时提及 `deadline_at` 和 `expires_at` 但未解释二者语义区别，也未明确当两者均存在时的 precedence。更关键的是，`expires_at` 作为一个永远不会被写入的 schema 字段出现在 stale check 逻辑中，会给 implementation agent 造成困惑——它是否需要实现实际上永远不会触发的 `expires_at` stale check？
- **直接证据**: `waiting.py:2007-2008`（`deadline_at=deadline_at, expires_at=None`），`durable/state.py:430-431`。对 `expires_at=` 赋值的 grep 仅在 `waiting.py:2008`（`None`）和 `durable/state.py` 解码中出现。
- **影响**: 轻微——不会导致错误行为，但增加了实现的不确定性。implementation agent 需要自行决定是否为从未有值的字段编写 stale check 测试。
- **建议改法和验证点**:
  1. Plan 应显式声明：当前仅 `deadline_at` 可能为非 `None`；`expires_at` 是 schema 预留字段，当前始终为 `None`。stale check 对 `expires_at` 的检查仅当字段未来被 populate 时才生效。
  2. 或者从 stale rule 中移除 `expires_at` 引用，仅保留 `deadline_at`，避免实现 agent 为 dead code 编写测试。
- **修复风险**: 低。
- **严重程度**: 中——不会导致错误，但表明 plan 对现有 schema 字段实际使用情况的信息不完整。

### DS-F05-未修复-低-observed-at-vs-completed-at-in-resolve-request

- **位置**: Plan §Contract, `WaitCallbackCompletionEnvelope` fields 与 `ResolveWaitRequest` mapping
- **问题类型**: 契约缺失
- **当前写法**: Envelope 同时携带 `observed_at: datetime` 和 `completed_at: datetime`。Plan 说明 `completed_at` 是 callback sender 声明的实际完成时间，`observed_at` 是 callback 被 Host 观测的时间。但 adapter 构造 `ResolveWaitRequest(observed_at=envelope.observed_at, ...)` 时仅传递 `observed_at`，不传递 `completed_at`。
- **反例/失败场景**: 当 callback sender 的 `completed_at` 与 `observed_at` 有显著偏差（例如 sender 延迟数小时才回传）时，`ResolveWaitRequest.observed_at` 传递的是 Host 收到 callback 的观测时间，而非业务完成时间。这会反映在 EventLog 的 `occurred_at` 时间戳中（`waiting.py:998`：`occurred_at=request.observed_at`），可能导致工具结果的 EventLog 时间戳与实际外部 job 完成时间不一致。虽然这在语义上是 Host 观测时间（Host 只能记录自己观测到的时间），但 plan 未解释为什么 `completed_at` 被收集但最终被丢弃。
- **为什么有问题**: 给 implementation agent 造成不确定性——`completed_at` 是否需要进入 EventLog payload 作为附加元数据？如果需要，plan 未说明；如果不需要，收集它只是为了 stale check 和 digest verification，plan 未明确解释。
- **直接证据**: Plan 第 146-148 行（envelope 含 `completed_at`），第 247 行（adapter 构造 `ResolveWaitRequest(observed_at=envelope.observed_at, ...)` 无 `completed_at`），`waiting.py:998`（EventLog 时间戳使用 `request.observed_at`）。
- **影响**: 轻微——不影响正确性，但 `completed_at` 的用途不够透明。
- **建议改法和验证点**: Plan 应补充说明 `completed_at` 仅用于 stale check 和 `payload_digest` 验证，不进入 EventLog；或者如果未来审计需要，明确 `completed_at` 以何种形式保留（如作为 EventLog payload 内的附加字段）。
- **修复风险**: 低。
- **严重程度**: 低——语义澄清性质，不影响代码生成。

### DS-F06-未修复-低-run-field-type-inconsistency

- **位置**: Plan §Contract, `WaitCallbackAdapterResult` dataclass, 第 154 行
- **问题类型**: 契约缺失
- **当前写法**: `run: RunSnapshot | None`
- **反例/失败场景**: Plan 要求 adapter 直接调用 `DefaultHostResolveWaitService.resolve_wait()`，它返回 `ResolveWaitResult`，其中 `run: RunRow`（`waiting.py:325`），不是 `RunSnapshot`。公共 facade 通过 `run_snapshot_from_row(result.run)`（`command.py:783`）做转换。Adapter 需要执行相同的转换，但 plan 未提及此步骤。
- **为什么有问题**: Implementation agent 可能直接在 `WaitCallbackAdapterResult` 中填入 `RunRow` 而类型检查失败，或需要自行发现 `run_snapshot_from_row` 转换。
- **直接证据**: `waiting.py:317-327`（`ResolveWaitResult.run: RunRow`），`command.py:783`（`run_snapshot_from_row(result.run)`）。
- **影响**: 轻微——implementation agent 在实现时即可发现并修正。
- **建议改法和验证点**: Plan 应注明 adapter 需要将 `RunRow` 转为 `RunSnapshot`（通过 `run_snapshot_from_row`），或改为 `run: RunRow | None` 然后在 Service mapper 中转换。
- **修复风险**: 低。
- **严重程度**: 低——implementation agent 在实现时即可发现。

## Open Questions

1. **Adapter 依赖注入边界**：Adapter 需要 `HostTransactionRunner`（用于 pre-read wait record）和 `DefaultHostResolveWaitService`（用于 resolve）。Plan 未指定 adapter 如何获得这些依赖——是通过构造函数注入，还是通过一个 factory/assembly 函数？这应在 implementation 前明确，否则 implementation agent 需要自行设计装配方式。

2. **Pre-read wait record 的事务语义**：Adapter 的 pre-read（step 3）是否需要在一个 read transaction 中执行？如果需要，adapter 需要 `HostTransactionRunner` 或等效的 read-only 访问；如果不需要（直接读 SQLite），则可能读到未提交的中间状态。Plan 未指定。

3. **`WaitCallbackAdapterResult` 中 `diagnostic_code` 与 `status` 的关系**：Plan 定义了 `status: WaitCallbackAdapterStatus` 和 `diagnostic_code: str`，但未解释 `diagnostic_code` 与 `status` 的区别——`status` 本身就是诊断性枚举，`diagnostic_code` 是否需要更细粒度的区分？如果不需要，`diagnostic_code` 是否冗余？

## Final Plan Review Conclusion

**Verdict: `pass-with-risks`**

Plan 的核心架构决策——callback 进入现有 `resolve_wait` pipeline、Host core 保持 framework-independent、Service 负责 transport mapping、stale check 使用现有 `deadline_at`——是正确的。

一个 high-severity finding（DS-F01 dispatch wakeup gap）是真正的 blocking concern：如果 implementation agent 按 plan 的当前描述直接调用 `DefaultHostResolveWaitService` 而不处理 dispatch wakeup，callback-triggered resume 将永远不执行。这不影响 plan 的整体方向，但必须在 plan fix 中解决。

两个 medium-severity findings（DS-F02 error disambiguation fragility、DS-F03 JSON outcome mapping underspecified）是 implementation agent 会遇到的实际歧义，应在 plan 中补充规格。

三个 low-severity findings 是文档化/澄清性问题，不阻碍 implementation。
