### CR-DS-001 — fixed — 双失败异常链结构化保留

**总控裁决**: `accepted`，severity 低。修复要求：外层 `StrictNativeMutexUnavailableError` 类型不变；prior native error + partial close error 双存在时 cause 必须结构化保留两个原始异常及 traceback；普通 busy + close failure fail-closed 不变；新增精确单测。

**修复验证**:

1. **外层异常类型不变**: `_close_partial_file_descriptor`（行 355）始终抛出 `StrictNativeMutexUnavailableError("关闭 partial strict-native mutex file descriptor 失败")`。验证通过：`test_native_lock_and_partial_close_failures_preserve_structured_chain` 行 438 断言 `match="关闭"` 命中该外层类型。

2. **ExceptionGroup cause 结构化保留两个原始异常**: 行 360-364：
   ```python
   combined_error = ExceptionGroup(
       "strict-native mutex native 操作与 partial descriptor cleanup 均失败",
       [prior_error, exc],
   )
   raise cleanup_error from combined_error
   ```
   `ExceptionGroup` 是 Python 3.11 stdlib 内建类型，`[prior_error, exc]` 顺序保留两个独立失败事实。验证通过：行 442-443 断言 `isinstance(combined_error, ExceptionGroup)` 且 `len(combined_error.exceptions) == 2`。

3. **两个原始异常 identity 可达**: 行 444-447：
   ```python
   prior_error, close_error = combined_error.exceptions
   assert isinstance(prior_error, StrictNativeMutexUnavailableError)
   assert prior_error.__cause__ is locking.error
   assert close_error is closer.error
   ```
   `prior_error` 是 `_lock_file_descriptor` 行 284 抛出的 `StrictNativeMutexUnavailableError`，其 `__cause__` 是 `flock()` 原始 `OSError`（`locking.error`）。`close_error` 是 `_CloseAfterFailure.__call__` 中 `self._real_close(file_descriptor)` 后抛出的 `self.error`。两个异常对象均通过 `is` identity 断言，非字符串拼接或类型名替代。

4. **traceback 均非空**: 行 448-450：
   ```python
   assert prior_error.__traceback__ is not None
   assert locking.error.__traceback__ is not None
   assert close_error.__traceback__ is not None
   ```
   三个异常的 traceback 均在 raise 时由 Python 自动设置，验证通过。

5. **partial descriptor close 只调用一次**: 行 451 断言 `len(closer.file_descriptors) == 1`。`_CloseAfterFailure.__call__` 先执行 `_real_close`（真实 `os.close`）再抛出异常，确认 fd 已消费且不重试。

6. **普通 busy + close failure fail-closed 不变**: `test_partial_fd_cleanup_failure_overrides_busy_outcome`（行 401-418）覆盖 `prior_error=None` 路径。行 356-357：
   ```python
   if prior_error is None:
       raise cleanup_error from exc
   ```
   外层仍为 `StrictNativeMutexUnavailableError`，`__cause__` 直接指向 close `OSError`。验证通过：行 416 断言 `match="关闭"` 且 `len(closer.file_descriptors) == 1`。

**CR-DS-001 结论**: **fixed**。修复发生在正确 owner boundary（`_close_partial_file_descriptor`），使用 stdlib `ExceptionGroup` 是表达两个独立 exception/traceback 的最小严格设计，未新增 public type、schema、Host state 或兼容 shim。

### 回归检查

回归检查范围：沿 `try_acquire_strict_native_mutex` 主链路逐行走读，重点检查 fix 是否引入新异常契约、typing、资源清理或测试固化问题。

**1. `_close_partial_file_descriptor` signature 收窄**

fix artifact 记录 `prior_error` 从 `BaseException | None` 收窄为 `Exception | None`。当前代码行 342 确认类型为 `Exception | None`。所有调用点（行 184、190、193、197）的 `prior_error` 来源均为 `except Exception as exc` 捕获的异常，与签名一致。`StrictNativeMutexUnavailableError` 继承 `RuntimeError` → `Exception`，`OSError` 继承 `Exception`，均满足约束。**无回归**。

**2. `ExceptionGroup` 作为 `__cause__` 的 downstream 兼容性**

`ExceptionGroup` 继承 `Exception`。现有 `except StrictNativeMutexUnavailableError` 捕获链（`try_acquire_strict_native_mutex` 行 189、192 的 caller）不受影响——外层异常类型未变。`ExceptionGroup` 作为 `__cause__` 是 Python 标准异常链机制，不改变 catch 语义。`Handle.close()`（行 123-158）的双失败路径使用 `add_note` 模式，与 `_close_partial_file_descriptor` 的 `ExceptionGroup` 模式独立，互不影响。**无回归**。

**3. 资源清理安全性**

`_close_partial_file_descriptor` 的 fd 消费顺序未变：行 353 先调用 `_close_file_descriptor(file_descriptor)`（执行 `os.close`），失败后才构造异常链。`_CloseAfterFailure` 测试 fake 也先执行 `_real_close` 再抛异常（行 185-186），确保 fd 已消费。descriptor 不会被重试或泄漏。**无回归**。

**4. test 固化检查**

新测试 `test_native_lock_and_partial_close_failures_preserve_structured_chain` 断言的是 owner 级 contract 行为（外层类型、cause 结构、identity、traceback），不是偶然实现细节。既有测试 `test_partial_fd_cleanup_failure_overrides_busy_outcome` 未被修改、未被弱化，继续证明 fail-closed 语义。**无测试固化**。

**5. `Handle.close()` 双失败路径未被 fix 波及**

`Handle.close()` 行 139-158 的 unlock + close 双失败路径使用 `first_error.add_note(str(close_error))`。这是独立于 `_close_partial_file_descriptor` 的另一错误处理路径（handle 持有的 descriptor，非 partial descriptor）。该路径不在 CR-DS-001 修复范围内，行为未变。**无回归**。
