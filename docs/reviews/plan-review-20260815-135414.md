## Findings

### 1-未修复-高-material 的 suffix admission owner 在 Slice 3 后出现空洞（LLM tool 路径无校验）

- **位置**：plan §5.4、§6.2、Slice 3 Exact changes #1、goal 5；以及 plan §10 "没有未分类风险、没有需要实现 agent 自行猜测的 open question"。
- **问题类型**：架构边界 / 契约缺失 / 目标漂移（与 goal 5 冲突）。
- **当前写法**：Slice 3 要求"删除 `SUPPORTED_UPLOAD_SUFFIXES` 与 Service 自校验；filing 必须消费 typed selection，material 仍消费全部 paths"；material 的校验迁移只出现在 §6.2"CLI material 校验复用同一 `accepts_primary`"（Slice 2 只改 `dayu/cli/commands/fins.py::_validated_upload_files`）。
- **反例/失败场景**：LLM 通过 upload tool 以 `upload_kind=material` 上传任意后缀文件（`FinsUploadMaterialRequest` → `ProductionFinsUploadRunner._run_material_upload` → sec/cn pipeline `upload_material` → `prepare_upload(files=file_list)`）。当前该路径由 Service `_validate_source_files` 用 `SUPPORTED_UPLOAD_SUFFIXES` 做 admission（docling_upload_service.py:1000-1002）；Slice 3 删除后，material 在 tool 路径上没有任何 suffix admission，`.doc/.bin/任意后缀` 直接进入 converter，在转换深处以 `DoclingConversionError`（material 分支 re-raise，docling_upload_service.py:775-777）或内容失败收场。SEC material 流还会先 stage company meta（sec_upload_workflow.py:486-499）再失败。
- **为什么有问题**：plan goal 5 声称"help、CLI/Fins 静态校验、batch scanner、Service、LLM-facing tool schema 使用同一 typed contract/projection"——删除后 Service 对 material 不再消费 contract，tool 路径无 owner；这直接违反 CLAUDE.md 语义所有权约束（"每个业务事实必须有唯一清晰 owner"、"若正确 owner 不清楚，先停止实现并澄清所有权"）。同时实现 agent 面临两种互斥解读：A) Service 保留一个只针对 material 的 `accepts_primary` 校验（与"删除 Service 自校验"文本冲突）；B) 完全删除（material 失去 admission）。两解读的行为不同（usage failure 时机 vs content failure 时机），正是 plan 宣称不存在的"需要自行猜测"点。
- **直接证据**：docling_upload_service.py:57-71、980-1004；sec_upload_workflow.py:500-510；cn_pipeline.py:1115 附近 material 流；service_runtime.py:146-153（material 无 Fins validator）；upload_tools.py:334-350（tool 构造 material request）；plan Slice 3 #1、§6.2、goal 5。
- **影响**：实施 Agent 跑偏 / 语义 owner 空洞 / goal 5 落空 / review 不可验收。
- **建议改法和验证点**：在 plan 中明确 material admission 的唯一 owner。最简方案：Service 保留 material 专属 admission（`FinsUploadFormatCapability.accepts_primary` 逐项校验 + exists/regular 保留），删除的只是常量与 filing 的重复 allow-list，不是 admission 职责本身；或把 material request 也纳入 Fins validator。验证点：tool 路径 material 非法后缀在转换前以 usage 语义失败、合法后缀全部转换的既有回归继续通过；在 Slice 3 Tests / assertions 中显式列出。
- **修复风险（低）**：plan 层面增加一段 owner 声明即可收敛。
- **严重程度（高）**：语义所有权最高约束的直接违反，且与 plan 自身 goal 5 自相矛盾。

### 2-未修复-中-`prepare_upload` 公共签名如何 typed 收紧未指定，实现 agent 需自行设计

- **位置**：plan §5.4、Slice 3 Exact changes #1/#4。
- **问题类型**：不可直接实施 / 契约缺失。
- **当前写法**："`DoclingUploadService.prepare_upload` 不新增 facade。直接把 filing 输入收紧为 typed `FinsUploadFilingFiles`，material 保持 path list；用一个私有严格类型 preparation value 表达：有序 originals、需转换的 inputs、明确 primary input。"
- **反例/失败场景**：`prepare_upload(files: list[Path])` 是公共方法（被 sec_upload_workflow.py:201、cn_pipeline.py:830、material 流三处调用）。"收紧"至少有三种互斥实现：a) `files: FinsUploadFilingFiles | list[Path]` union（弱化严格类型要求，且需按 source_kind 做 closed 分支）；b) 新增独立参数如 `file_selection: FinsUploadFilingFiles | None` 与 `files` 并存（两个输入可能互相矛盾，需要一致性断言）；c) workflow 侧构造"私有 preparation value"直接传入（改变公共边界，接近新 facade，与"不新增 facade"矛盾）。plan 未给出签名或调用约定，Slice 3 测试只断言行为（"selection 被实际消费"），不断言接口形状。
- **为什么有问题**：plan §12 声称 4 个 slices 是 code-generation-ready 且"没有需要实现 agent 自行猜测的 open question"；而该处正是需要自行设计公共契约的点，违反 planreview 的可实施性标准。
- **直接证据**：plan §5.4 原文；docling_upload_service.py:241-255 现有签名与三处调用点。
- **影响**：实施 Agent 跑偏 / 后续返工 / review 不可验收。
- **建议改法和验证点**：在 plan 中写明确切签名（推荐单一参数并显式声明 filing/material 分支的类型约束，如 `files: FinsUploadFilingFiles | tuple[Path, ...]` + source_kind 一致性断言），并在 Slice 3 测试中加一条接口形状断言（非法组合在 service 入口以 ValueError 拒绝）。
- **修复风险（低）**。
- **严重程度（中）**。

### 3-未修复-中-「精确相等」校验把第三方元数据变成双向硬契约：产品被迫全量开放所选格式的第三方 suffix，且 Docling 任意 patch 升级可使全部上传 fail-fast

- **位置**：plan §5.1（"把声明的扩展名集合与该安装版本的 `FormatToExtensions` 精确比较"）、Slice 1 Tests / assertions、§10 Capability residual。
- **问题类型**：非最优方案 / 过度设计（过度约束）。
- **当前写法**：capability 每个格式的 suffix 集合必须与安装版本 `FormatToExtensions[fmt]` **精确相等**；Slice 1 测试断言"每个被宣布格式的 format id 与完整 suffix 集合和安装的 `FormatToExtensions` 精确一致"。
- **反例/失败场景**：实测 Docling 2.90.0：`md → [Rmd, md, qmd, rmd, text, txt]`、`xlsx → [xlsm, xlsx]`、`pptx → [potm, potx, ppsm, ppsx, pptm, pptx]`、`docx → [docm, docx, dotm, dotx]`。按精确相等：(a) 选择"Markdown/text"即被迫把 `.text/.Rmd/.qmd/.rmd` 宣布为产品 primary 能力并写进 `--help` 与 LLM-facing schema——这与 plan 自己"不把 Docling 默认枚举自动开放为产品承诺"的姿态相反（后者被用于排除图片/音频，但同逻辑未用于所选格式的超集）；(b) Docling 任意 patch 为任一已选格式新增一个 suffix，构造期精确比对即失败 → `CONVERTER_CONSTRUCTION` → 所有上传与共享 converter 调用全部不可用，一个第三方 patch 升级成为整链路可用性单点。
- **为什么有问题**：单一 source of truth 的目标只需要"产品声明 ⊆ 第三方真实能力"（子集校验 + fail-fast on missing），不需要反向断言第三方集合与产品声明逐项相等。精确相等把只读第三方元数据升级为双向硬契约，获得不了额外的 ownership 收益，只带来可用性风险和产品语义过度开放。plan §10 虽把后者标为"有意安全失败"，但"有意"的代价没有与更廉价的子集校验方案做过对比。
- **直接证据**：`.venv` 实测 `FormatToExtensions`（本 review 输出见上）；plan §5.1、Slice 1 测试第 1 条。
- **影响**：后续返工 / 部署风险 / 产品语义被第三方映射反向锁定。
- **建议改法和验证点**：改为子集校验（每个声明 suffix ∈ `FormatToExtensions[fmt]`，缺失即 typed fail-fast），或精确相等但 capability 显式声明产品选择子集并逐一给出产品理由；Slice 1 测试相应断言"声明集合是第三方映射的子集且构造允许集合与声明一致"。若坚持精确相等，请在 plan 中写明接受 `.text/.Rmd/.qmd/.xlsm/.potx…` 等进入 help 的产品决策记录。
- **修复风险（中）**：需要一次 design 取舍裁决，改动集中在 Slice 1 常量与测试。
- **严重程度（中）**。

### 4-未修复-中-batch 入口的 companion 语义未声明，goal 目标 5（XBRL 主文档与 companion 同一原子 publication）在 batch 模式落空

- **位置**：plan §6.2、goal confirmation 目标 5、非目标/UF-FIX07 边界。
- **问题类型**：目标覆盖缺口 / 切片边界不清。
- **当前写法**：§6.2"`upload_batch` 的每个扫描文件会生成独立 upload 命令，因此每个候选都必须满足 `accepts_primary`；`.xsd` 不作为 standalone candidate"。plan 未说明 batch 入口下 XBRL companion 如何（或是否）进入同一 publication。
- **反例/失败场景**：用户用 `upload_filings_from` 扫描含 `cme_html.htm` + `cme_schema.xsd` 的目录：`.xsd` 被 `_discover_source_files` 以 `unsupported_suffix` 跳过（upload_batch.py:436-441），生成的命令只含 HTML——companion 原样保存的修复语义在 batch 入口不可达。goal confirmation 目标 5 与 UF-C06 冻结场景在 CLI `--files` 手动列出时可达成，但 batch 是同一产品的公开入口，plan 未声明该缺口属于 UF-FIX07 还是本 work unit 需要把同目录 companion 纳入规划。
- **为什么有问题**：goal-bound minimal design 要求每个验收与 goal 直接映射；batch 的 companion 行为是 goal 覆盖范围的问题，plan 直接跳过会使 implementation agent 自行决定（跳过即静默丢弃，或自行设计 companion 归组——后者越出 Slice 2 allowed files 的边界语义）。
- **直接证据**：plan §6.2 原文；upload_batch.py:430-441；goal confirmation 目标 5。
- **影响**：目标落空 / 实施 Agent 跑偏 / 后续返工。
- **建议改法和验证点**：在 plan 中显式声明 batch 模式 companion 的语义边界（例如：本 work unit 中 batch 对 `.xsd` 保持 skip 并记入 UF-FIX07 residual；或要求 batch 规划把同 stem 的已声明 companion 并入生成命令——若选后者需扩 Slice 2 的 allowed files 与测试）。测试点：batch 扫描含 xsd 目录的规划行为按声明冻结。
- **修复风险（低）**：一句话声明即可收敛。
- **严重程度（中）**。

### 5-未修复-低-companion 的文件级事件契约未定义，用户可见进度流存在误导投影风险

- **位置**：plan §5.4、Slice 3 Tests / assertions；docling_upload_service.py `_build_pending_assets`。
- **问题类型**：契约缺失 / 测试缺口。
- **当前写法**：当前 `_build_pending_assets` 对每个文件先发 `conversion_started` 事件再转换（docling_upload_service.py:758-767）。plan 只说"companions 不生成 Docling 资产"，未规定 companion 是否仍发 `conversion_started`、最终发什么文件事件（`file_uploaded` 之外是否出现"跳过转换"语义）。
- **反例/失败场景**：实现 agent 保留原循环结构、仅跳过转换——companion 会投影出 `conversion_started`（"正在 convert"）却永不转换，`Fins progress` 事件流（用户可见、LLM 可读）声称正在转换一个只原样保存的附件；或相反地完全不发事件，破坏事件流完整性。Slice 3 测试没有 companion 事件断言（只有资产与计数断言），两种实现都能通过测试。
- **为什么有问题**：事件流是 upload 的用户可见进度与 durable audit 面，LLM-facing 文本约束禁止把未发生的动作伪装成事实；事件契约属于 owner 级 contract，测试必须断言，不能留给实现自行选择。
- **直接证据**：docling_upload_service.py:754-802；plan Slice 3 Tests / assertions 清单（无 companion 事件断言）。
- **影响**：用户可见误导 / audit 不一致 / 测试无法锁住契约。
- **建议改法和验证点**：plan 中规定 companion 的事件序列（建议：仅 `file_uploaded`，或新增显式"附件原样保存"事件语义），并在 Slice 3 测试断言 companion 无 `conversion_started`、事件名与 source 字段一致。
- **修复风险（低）**。
- **严重程度（低）**。

## Open Questions

- **O1**：oracle `upload_filing.multi-file-and-primary` 的 expected 用词是"多文件 filing 必须有**显式且稳定**的 primary 规则"，plan goal 3 用"**隐式** primary"。用户对 UF-O14 的裁决接受"清楚承诺首文件为 primary"路径（oracle-adjudication.md §14），argv 顺序是用户显式控制而非文件系统顺序，故实质合规；但 plan 未单列验收项断言 `--help`、LLM-facing schema、README 三个用户可见面一致承诺"首文件是 primary、后续附件原样保存"——建议在 Slice 2/4 验收中显式固化，避免"清楚承诺"降级为只在代码注释里成立。
- **O2**：UF-C05 类输入（DOCX+XLSX+DOCX 多 primary 能力文件）在改造后 XLSX 与第二个 DOCX 变为 companion 原样保存、不再生成 Docling 派生资产——这是相对冻结 evidence 的有意行为变化（与 oracle UF-O14 裁决方向一致），但 Slice 3 测试只覆盖 HTML+XSD 单一 fixture。建议补充 service 级断言：多 primary 能力文件只转换首文件、其余原样存储、`primary_document` 仍指向首文件派生资产。

## Final plan review conclusion

**fail**

核验确认 plan 的根因判断、证据链（SHA-256 全部一致）、primary-companion 数据链方向、atomicity/cancellation/requested-stored/typed bounded failure 不变式与现有代码真源对齐，Slice 1/2 的 sequencing 与 stop conditions 合理。但存在两个实现 Agent 无法自行裁决的结构性缺口（F1 material admission owner 空洞——直接违反语义所有权最高约束并与 goal 5 自相矛盾；F2 `prepare_upload` 公共签名未指定），一个 goal 覆盖缺口（F4 batch 入口 companion 语义未声明），一个需要 design 取舍的过度约束（F3 精确相等校验），以及一个低严重度的事件契约缺口（F5）。plan §10"没有需要实现 agent 自行猜测的 open question"的主张与上述事实不符。以上问题均可通过小幅 plan 修订收敛，不需要结构性重写：F1/F2/F4 各需一段明确 owner/签名/边界声明，F3 需要一次校验策略取舍，F5 需一条事件断言。建议修订后重新进入 plan review。
