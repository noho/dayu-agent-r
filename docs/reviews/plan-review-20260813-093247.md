## Findings

### F01-未修复-中-publication guard bypass 机制未在 plan 中显式描述

- **位置**: 6.3 最小 non-mutating storage contract, 6.2 step 6
- **问题类型**: 不可直接实施
- **当前写法**: plan 要求 "若 canonical published ticker root 明确不存在，storage owner 内部直接返回 `(None, None)`，不创建 `.dayu`、`portfolio`、lock"；同时要求 "FS 实现在同一个 ticker publication guard 内调用既有 unguarded company/source readers"
- **反例/失败场景**: 当前 `_FsStorageInfra` 的 publication guard 是 file-lock-based，所有 published-tree reads 都经过 guard。如果实现 agent 直接复用现有 guard 路径，fresh absent ticker 会触发 lock acquire，可能创建 `batch_locks/{TICKER}.publication.lock` 文件。即使 guard 内部检查 ticker root 不存在，lock acquire 本身可能已经创建了 lock 文件
- **为什么有问题**: plan 的 success criteria 和 UF-PF01 明确要求 fresh workspace before/after tree 完全相同，无 `.dayu`、`portfolio`、lock。如果 implementation agent 没有明确的 bypass 策略，可能在 guard acquire 后才发现 ticker absent，此时 lock 文件已创建
- **直接证据**: plan section 6.3: "若 canonical published ticker root 明确不存在，storage owner 内部直接返回 `(None, None)`，不创建 `.dayu`、`portfolio`、lock；只有 storage 实现知道物理路径"；plan section 12.1: "existing lock artifacts：existing workspace 的短 publication guard 是一致读协议的一部分；PF01 fresh absent fast path 不创建 lock"
- **影响**: 实施 agent 可能在 fresh absent 路径创建 lock artifact，导致 UF-PF01 测试失败
- **建议改法和验证点**: 在 section 6.3 或 6.2 step 6 中显式描述 bypass 策略：先检查 canonical published ticker root 是否存在（`Path.exists()`），不存在则直接返回 `(None, None)`，不进入 publication guard。验证点：S1 测试中断言 `lock acquire helper 未调用`（plan 已有此断言，但实现策略需显式）
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F02-未修复-低-FinsUploadUsageCode 闭集未显式枚举

- **位置**: 6.1 Fins typed usage contract
- **问题类型**: 不可直接实施
- **当前写法**: plan 说 "usage code 闭集至少覆盖：ticker/csv-invalid、missing/invalid year、missing/invalid period、missing files、file missing/not-regular、batch suffix rejected、converter suffix rejected、company name required、create target exists、update target missing"
- **反例/失败场景**: implementation agent 需要为每个 UF scenario 分配精确的 usage code。如果闭集枚举不完整，agent 可能遗漏某些场景的 code 映射，或在实现中引入 ad-hoc code
- **为什么有问题**: plan 的 S2 exact assertions 要求 "UF-003–006、015–019、021–024、026–038 参数逐项返回 exact `FinsUploadUsageCode` 和 bounded message"。如果 code 枚举不完整，agent 需要自行决定每个 UF 场景的 code，可能产生不一致
- **直接证据**: plan section 6.1: "usage code 闭集至少覆盖：ticker/csv-invalid、missing/invalid year、missing/invalid period、missing files、file missing/not-regular、batch suffix rejected、converter suffix rejected、company name required、create target exists、update target missing"
- **影响**: 实施 agent 需要自行补全 code 枚举，可能产生不一致或遗漏
- **建议改法和验证点**: 在 section 6.1 中显式列出每个 UF scenario 到 usage code 的映射表（至少覆盖 UF-003–006、015–019、021–024、026–038）。验证点：S2 测试逐项断言 exact code
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F03-未修复-低-lazy bootstrap 回归验证需覆盖 download/preprocess 路径

- **位置**: 6.4 Lazy bootstrap contract, S1 exact assertions
- **问题类型**: 测试缺口
- **当前写法**: plan 要求 `FsFinsIngestionJobStore.__post_init__` 不创建目录，`create_job` 在获取 job lock 前调用私有 `_ensure_root_for_write()`。S1 断言 "download/preprocess/legacy job 的首次真实写仍成功，schema 与 recovery assertions 不变"
- **反例/失败场景**: 当前 `FsFinsIngestionJobStore.__post_init__` 通过 `mkdir(parents=True, exist_ok=True)` 创建 `root_dir`。如果改为 lazy，download/preprocess 路径中的 `create_job` 需要确保目录存在。如果某些 download/preprocess 路径不经过 `create_job`（如 direct download），可能遗漏目录创建
- **为什么有问题**: plan 的 S1 断言提到 "download/preprocess/legacy job 的首次真实写仍成功"，但没有显式列出哪些路径需要覆盖。当前 `test_fins_ingestion_runtime.py` 有 download/preprocess 测试，但需要确认它们在 lazy bootstrap 后仍然通过
- **直接证据**: plan section 6.4: "该变化只消除 eager side effect，不改变 batch recovery、download/preprocess 写路径或 durable legacy job schema"；plan section 8 S1: "download/preprocess/legacy job 的首次真实写仍成功，schema 与 recovery assertions 不变"
- **影响**: 如果 lazy bootstrap 改动遗漏某些写路径，download/preprocess 可能在 fresh workspace 失败
- **建议改法和验证点**: 在 S1 测试中显式列出需要覆盖的 download/preprocess 路径（direct download、runtime download、preprocess），并断言它们在 fresh workspace 中成功创建必要的目录。验证点：现有 `test_fins_ingestion_runtime.py` 中的 download/preprocess 测试全部通过
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F04-未修复-低-CLI stderr 格式模板未在 plan 中显式定义

- **位置**: 2.3 Success criteria, S2 exact assertions
- **问题类型**: 契约缺失
- **当前写法**: plan 说 "stderr 恰一行 `dayu-cli upload_filing: <reason>\n`"，但没有定义 `<reason>` 的格式模板
- **反例/失败场景**: implementation agent 可能为不同类型的 usage error 使用不同的 stderr 格式（如 "upload_filing: ticker is empty" vs "upload_filing: missing required --fiscal-year"），导致 UF-PF01 测试不稳定
- **为什么有问题**: UF-PF01 要求 "stderr exact one actionable line"，但没有定义 "actionable line" 的格式模板。如果格式不一致，测试可能需要 fuzzy matching 而非 exact matching
- **直接证据**: plan section 2.3: "stderr 为一个具体可行动 reason"；plan section 8 S2: "stderr 恰一行 `dayu-cli upload_filing: <reason>\n`"
- **影响**: 实施 agent 可能产生不一致的 stderr 格式，导致 UF-PF01 测试需要调整
- **建议改法和验证点**: 在 section 6.1 或 6.6 中定义 stderr 格式模板：`"dayu-cli upload_filing: {failure.message}\n"`，其中 `failure.message` 是 `FinsUploadFailureReason.message`（最大 240 字符）。验证点：S2 测试断言 stderr 匹配此模板
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Plan Review Conclusion

**pass-with-risks**

plan 整体结构清晰、动机成立、scope 控制得当。五个 slice 的依赖顺序合理（S1 storage read → S2 validation → S3 atomic publication → S4 typed failure → S5 documentation），每个 slice 的 owner test assertions 直接绑定 frozen evidence 的 UF scenario。

plan 正确识别了当前代码的核心问题：
- eager bootstrap 创建不必要的 workspace 副作用（UF-003–006 等）
- usage error 被投影为 runtime exit=1 而非 typed exit=2（UF-015–019 等）
- company meta 和 source 在独立 batch 中发布，导致 orphaned company meta（UF-017、UF-I11–I13）
- failure message 包含 traceback 和绝对路径（UF-I11–I13）

plan 的设计决策（pure published-state read protocol、lazy bootstrap、single BatchToken、typed failure reason）均基于直接代码证据，且与 AGENTS.md 的语义所有权约束一致。

四个 findings 均为低/中严重程度，不构成 blocker。F01（publication guard bypass）是最需关注的，但实现策略简单（先检查 existence 再决定是否进入 guard），且 plan 的 S1 测试已断言 "lock acquire helper 未调用"。

建议在实施前补充 F01 的显式 bypass 策略描述，其余 findings 可在实现过程中解决。
