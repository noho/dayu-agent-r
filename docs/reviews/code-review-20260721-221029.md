## Findings

### F1-[中]-同一 durable page 内连续非 PROGRESS event 均走 `current_terminal_event` 单槽，逐一处理行为无独立测试覆盖

- **入口/函数**: `_PublicHostHandle._watch_session_events_after`
- **文件(行号)**: `dayu/host/open_host.py:1090-1101`
- **输入场景**: 一个 bounded durable page 内包含两个连续的非 PROGRESS event（例：Run A terminal 在 seq=15，Run B terminal 在 seq=20），且 mailbox 内有 Run A 的 transient prefix 与 Run B 的 transient entry
- **实际分支**: step 5 逐 row 处理：第一个 non-PROGRESS 设 `current_terminal_event`（Run A）并 `continue`；下一轮 step 4 交付 Run A 同 Run prefix + terminal；再下一轮 step 5 处理第二个 non-PROGRESS（Run B）设 `current_terminal_event` 并重复 handoff
- **预期行为**: Run A terminal 及 prefix 先交付，Run B entry 保留到下一轮 handoff 后才交付；两个 terminal 均不应丢失、不应合并、不应交换顺序
- **实际行为**: 代码逻辑逐一处理是正确的——`current_terminal_event` 是单槽，每次只存一个 terminal；step 4 yield terminal 后清空该槽，step 5 才能存入下一个。**但当前 18 个测试用例中没有任何一个构造"同一 durable page 内 ≥2 个 non-PROGRESS event"场景**，该正确性仅由代码阅读推断，缺乏确定性 barrier 证明
- **直接证据**: `test_same_run_prefix_hands_off_to_terminal_before_different_run_head` 只覆盖单个 terminal + 异 Run transient handoff；`test_dual_opener_b_fence_catches_up_pages_before_terminal_handoff` 的 `diagnostic_count=140` 产出的 durable events 全是 PROGRESS (`PROVIDER_DIAGNOSTIC`)，final answer 是唯一的 non-PROGRESS event
- **影响**: 当前代码逻辑正确，但若未来对 step 4/step 5 交互做重构（例如将 terminal 处理从单槽改为列表），可能在多 terminal 同页场景出现 terminal 丢失或顺序交换，且无测试捕获
- **建议改法和验证点**: 在 `tests/host/test_watch_session_events.py` 新增 `_WORKER_MODE_MULTI_TERMINAL` factory mode 或扩展现有 `_PagedFinalAnswerHandle`，产出一个 durable page 内包含 ≥2 个非 PROGRESS event（例如 `PROVIDER_DIAGNOSTIC` + `RUN_SUCCEEDED` + `PROVIDER_DIAGNOSTIC` + 第二个 `RUN_SUCCEEDED`），断言 terminal 序列与 transient handoff 顺序；该测试应独立于 Slice 3 terminal coordinator，只验证 S2 merge state machine 的多 terminal 单页处理能力
- **修复风险（低）**: 新增测试，不改生产代码
- **严重程度（中）**: 代码逻辑经走读确认正确，但缺少确定性多 terminal 同页测试，属于测试覆盖缺口

### F2-[低]-post-terminal 同 Run transient 不再被 subscription offer 层过滤，完全依赖 engine_ingest durable validation 阻止此类 entry 产生，该跨层防护链未在 S2 测试中显式证明

- **入口/函数**: `HostTransientDeltaSubscription._offer` / `EngineEventIngestor._validated_transient_delta_candidate`
- **文件(行号)**: `dayu/host/transient_delta.py:643-668`（offer 不再检查 `run_id in _terminal_run_ids`）；`dayu/host/engine_ingest.py:5264-5276`
- **输入场景**: Engine worker 产出 transient delta 后、final answer 已提交并写入 EventLog、但 transient delta 的 ingest 尚未被 durable validation 的 late-state 检查拒绝的竞态窗口
- **实际分支**: Slice 1 的 `_offer` 通过 `event.run_id in self._terminal_run_ids` 在 offer 层直接丢弃 post-terminal 同 Run transient；Slice 2 删除了 `_terminal_run_ids` set 与 `mark_run_terminal`，`_offer` 不再做此过滤。若 post-terminal transient entry 进入 mailbox，step 7 的 fence 比较机制 (`next_cursor >= head.durable_causal_fence_event_sequence`) 不保证阻止其交付（fence 是 Attempt start sequence，terminal 后 cursor 已超过该 fence）
- **预期行为**: post-terminal 同 Run transient 不应交付给 watcher
- **实际行为**: 代码依赖 engine_ingest 的 durable validation（`_validated_transient_delta_candidate` 上下文中对 Attempt/Run 状态的校验）在实际提交 terminal 后拒绝后续 transient candidate。该依赖是正确的——同一个 durable validation transaction 内 terminal commit 和 transient validation 是互斥的——但跨层防护链（durable validation → candidate 不产生 → offer 不执行）未在 S2 测试中显式端到端证明
- **直接证据**: `dayu/host/transient_delta.py:651` 的 `if self._closed or self._overflowed:` 不再包含 `event.run_id in self._terminal_run_ids`；`dayu/host/transient_delta.py:712-720` 的 `_clear_retained_state` 不再清空 `_terminal_run_ids`；测试 `test_owner_exposes_no_batch_pop_or_byte_accounting_shape` 断言了 `mark_run_terminal` 和 `_terminal_run_ids` 的删除，但未构造 post-terminal transient 场景验证 offer 层不再过滤
- **影响**: 正常流程下 durable validation 阻止 post-terminal transient candidate，watcher 不会看到 post-terminal 同 Run entry。但如果 durable validation 存在未发现的竞态窗口，post-terminal transient 可能漏入 mailbox 并被交付，产生语义上错误的"terminal 后仍有同 Run transient"观察
- **建议改法和验证点**: 可考虑在 `tests/host/test_watch_session_events.py` 增加一个端到端测试：先通过正常流程让 Run 到达 terminal，再通过 `_publish_fenced_reasoning_delta` helper 直接向同一 hub 发布一个 fenced candidate（跳过 durable validation），断言该 entry 要么被 offer 层拒绝（若保留过滤），要么被 fence/cursor 机制阻止交付。当前若直接 publish 会被 delivered，确认这是设计意图而非遗漏
- **修复风险（低）**: 若确认该场景为有意设计（durable validation 是真源），只需补充测试或设计注释；若确认为防护缺口，可在 `_offer` 或 merge 状态机中恢复过滤
- **严重程度（低）**: plan 明确要求删除 terminal run-id set，设计真源在 durable validation 层；正常流程不受影响
