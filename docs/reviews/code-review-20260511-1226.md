## Findings

### 1-未修复-中-RuntimeTruncateManager.apply_truncation 与 fetch_more 之间缺乏并发保护

- **入口/函数**: `RuntimeTruncateManager.apply_truncation` 与 `RuntimeTruncateManager.fetch_more`
- **文件(行号)**: `dayu/host/_runtime_truncate_manager.py:222-265` (`apply_truncation`), `:267-349` (`fetch_more`)
- **输入场景**: 两个异步 task 共享同一个 `HostToolRuntime` 实例，task A 执行普通工具调用触发 `apply_truncation`，task B 执行 `fetch_more` framework 工具。task B 在 `fetch_more` 中持有 `_read_lock` 后 await `terminal_checker.is_terminal()` 时 yield；task A 的 `apply_truncation` 没有 await 点且不获取任何锁，直接修改 `_records_by_cursor` / `_cursor_by_fingerprint`。
- **实际分支**: `apply_truncation` 调用 `_commit_cursor`（行 250），直接写 dict；`fetch_more` 在 `async with self._read_lock` 内（行 278）读取并修改同一批 dict。`_read_lock` 是 `asyncio.Lock`，只保护 `fetch_more` 自身，不保护 `apply_truncation` 的写入路径。
- **预期行为**: 对共享可变 map 的并发写入应有明确保护或架构级保证（例如文档声明单 task 约束），且 `_read_lock` 不应给人"已全面保护"的错觉。
- **实际行为**: 当前架构下（单 Engine loop、单 run、工具调用串行）不会被触发，但代码结构未文档化这个约束，未来引入并发工具执行或并行 run 时可能触发 dict 并发修改（Python dict 在并发修改下可能抛出 `RuntimeError: dictionary changed size during iteration` 或产生静默数据不一致）。
- **直接证据**: `apply_truncation:250` `self._commit_cursor(record)` -> `:593-594` `self._records_by_cursor[record.cursor] = record`；`fetch_more:278` `async with self._read_lock:` -> `:282` `record = self._records_by_cursor.get(parsed.cursor)`。`_read_lock` 不覆盖 `apply_truncation` 路径。
- **影响**: 当前无实际触发条件，属于潜伏并发缺陷；一旦触发可能导致 cursor 注册丢失、cursor 查找返回过期数据或 dict 迭代异常。
- **建议改法和验证点**:
  1. 在 `RuntimeTruncateManager` 类 docstring 中明确声明"所有 mutation 假定在单 async task 内串行，不得并发调用 `apply_truncation` 与 `fetch_more`"；
  2. 或将 `_commit_cursor` / `_remove_cursor` 也纳入 `_read_lock` 保护（需确认 `apply_truncation` 是同步方法，获取 asyncio.Lock 需要改为 async，或改用 `threading.Lock`）。
- **修复风险**: 低（当前无实际并发场景，文档化即可；若加锁需注意不要引入死锁）
- **严重程度**: 中

### 3-未修复-中-FrameworkToolSet.fetch_more_definition 每次调用创建新闭包和 ToolDefinition

- **入口/函数**: `FrameworkToolSet.fetch_more_definition` / `FrameworkToolSet.tool_schemas`
- **文件(行号)**: `dayu/host/_framework_tools.py:36-95` (`fetch_more_definition`), `:97-104` (`tool_schemas`)
- **输入场景**: `tool_schemas()` 在每次 `engine_visible_tool_schemas()` 调用时被执行（每个 run 启动至少一次）；`execute_tool_call()` 在每次 `fetch_more` 工具调用时调用 `fetch_more_definition()`。每次调用创建新的 `@tool(...)` 装饰函数闭包、新的 `ToolDefinition`、新的 `FunctionToolExecutor`，并运行 `ToolDefinition.__post_init__` 中的 `name == schema.function.name` 校验。
- **实际分支**: `tool_schemas:104` `return (self.fetch_more_definition().to_tool_schema(),)` — 每次调用都完整构造；`execute_tool_call:312` `await self._framework_tools.fetch_more_definition().executor.execute(request)` — 每次 fetch_more 调用都重新构造。
- **预期行为**: framework tool definition 应在构造时缓存，不随每次调用重建。
- **实际行为**: 重复分配闭包 + ToolDefinition + FunctionToolExecutor，且 `__post_init__` 校验在每次 fetch_more 执行时都运行一次。功能正确但浪费分配、增加 GC 压力，且若 `__post_init__` 未来加入副作用逻辑会意外重复执行。
- **直接证据**: 行 36-95 方法体每次调用都执行 `@tool(...)` 装饰器 + 闭包创建；`HostToolRuntime.__post_init__:232` 构造 `FrameworkToolSet(manager=manager)` 但不缓存 definition。
- **影响**: 功能正确，纯性能和维护性风险。
- **建议改法和验证点**: 在 `FrameworkToolSet.__post_init__` 或 `__init__` 中预先构造 `_fetch_more_definition: ToolDefinition` 并缓存；`fetch_more_definition()` 和 `tool_schemas()` 改为返回缓存值。
- **修复风险**: 低（纯内部重构，行为不变）
- **严重程度**: 低

## Open Questions

1. `_runtime_truncate_manager.py` 中 `_cleanup_expired` 在每次 `_build_cursor`（即每次截断）时 O(n) 遍历全量 cursor 记录。当前 cursor 数量预期很小（每 run 数个），但若工具频繁截断且 TTL 较长，是否可能积累大量过期 cursor？建议确认预期 cursor 并发量。
2. `_tool_trace_projection.py:278-279` trace record 中的 `truncation_scope_token` 和 `truncation_cursor` 明文写入 JSONL。当前设计意图是 trace 用于调试，明文 cursor/scope_token 可接受；但需确认 trace 文件的访问控制和保留策略是否匹配该敏感度。
3. `HostToolRuntime` 同时实现了 `EngineToolSchemaProvider` 协议（`engine_visible_tool_schemas`），但 `_engine_tool_schema_provider.py` 中 `EngineToolSchemaProvider` 是 Protocol 而非显式接口。`HostToolRuntime` 没有显式声明 implements 该 Protocol — Python 的 structural subtyping 使之自然满足，但缺少显式声明可能让未来维护者困惑。是否需要在 docstring 中注明？

## Residual Risk

1. **RuntimeTruncateManager 并发安全**：Finding 1 描述的风险当前无触发条件，但若 P8-S7（multiprocessing）或 future 引入并行工具执行，必须先解决。
2. **测试覆盖**：`_runtime_truncate_manager.py`（1095 行）是本次改动中最高风险的新模块，包含截断状态机、cursor registry、scope 校验、TTL、chunk 构造等复杂逻辑。需要确认测试覆盖了以下场景：
   - 所有四种截断策略（text_chars / text_lines / list_items / binary_bytes）的正确截断和未超限路径
   - cursor 过期（TTL 到期后 fetch_more 返回 `cursor_expired`）
   - scope token 不匹配拒绝
   - cursor 单次消费（fetch_more 成功后原 cursor 不可复用）
   - 多页补读（连续 fetch_more 直到 has_more=False）
   - `apply_truncation` 在 spec 为 None / spec.enabled=False / limit 非法时的不截断路径
   - run 终态后 fetch_more 拒绝
   - 嵌套字段路径截断（wrapper dict + field_path）
3. **Credential scrub 测试**：`_credential_scrub.py` 需要覆盖嵌套 dict、list 内凭证、文本内凭证赋值、非凭证字段（cursor/scope_token/token）不误伤等场景。
4. **端到端回归**：`utils/smoke_host_tool_runtime.py` 和 `utils/smoke_host_p7_tool_trace.py` 已修改，需确认 smoke 测试通过。
