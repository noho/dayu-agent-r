## Assumptions Tested

1. The four target constants exist at the claimed locations with the claimed values.
2. `CurrentInputAnchorVNext.text` and `EvidenceReadableItemVNext.response_text` use `_require_bounded_non_empty_text` with private max_chars constants.
3. `_evidence_chunks` is called by default in `_pack_evidence_blocks` and `_provenance_from_evidence_blocks`.
4. `_ACCEPTED_TOOL_EVIDENCE_MATERIAL_LIMIT = 8` is used as default in `DurableAcceptedToolEvidenceMaterialProvider.__init__` and `build_accepted_tool_evidence_material_blocks`, and flows to `_recent_accepted_tool_result_rows(... LIMIT ?)`.
5. `build_pre_dispatch_compact_material_view` is already used by `context_fallback.py` proactive fallback, proving it can serve as a single EventLog truth source.
6. The plan's slice sequencing is safe: Slice 1 (DTO guards + chunking) and Slice 2 (row limit removal) are independent.
7. The plan does not introduce public API, durable schema, EventLog canonical semantic, or Engine contract changes.
8. The `MAX_VNEXT_*` output parser safety guards are correctly identified as distinct from input material guards.

## Findings

### F1-Unfixed-Low-Plan slice 2 未明确 `build_pre_dispatch_compact_material_view` 与现有 provider 读取语义的差异

- **位置**: Section 6, Slice 2, "具体改动" 第 5 条
- **问题类型**: 契约缺失
- **当前写法**: Plan 要求 provider 调用 `build_pre_dispatch_compact_material_view(transaction, event_log_store, run=current_facts.run, current_display_text=current_facts.user_prompt)` 并从返回的 `material_blocks` 中选取 `CompactMaterialBlockKind.ACCEPTED_TOOL_EVIDENCE`，再排除 memory / compact 已代表 evidence refs。
- **反例/失败场景**: `build_pre_dispatch_compact_material_view` 返回的 `material_blocks` 包含 `RunInputMaterialBlock`，其字段集（`readable_tool_name`、`readable_query_text`、`readable_source_text`、`text`、`accepted_evidence_id`、`tool_result_event_ref`、`tool_call_event_ref` 等）由 `_pre_dispatch_delta_material_blocks` 内部构造。当前 `build_accepted_tool_evidence_material_blocks` 也构造 `RunInputMaterialBlock`，但字段来源路径不同（直接 SQL → `compaction_evidence` reader vs. delta rows → `_pre_dispatch_delta_material_blocks`）。如果两条路径对同一 accepted evidence 产出的 `RunInputMaterialBlock` 字段不一致（例如 `readable_query_text` 解析逻辑不同），新 provider 会产出语义不同的 material blocks。
- **为什么有问题**: Plan 假设两条路径的 `RunInputMaterialBlock` 语义等价，但未验证。Implementation agent 需要确认字段级一致性或显式选择权威路径。
- **直接证据**: `dayu/host/run_input.py:1397-1404` 当前 provider 通过 `build_accepted_tool_evidence_material_blocks` → `_recent_accepted_tool_result_rows` → `compaction_evidence` reader 构造 blocks；`dayu/host/compact_material.py:457-553` 的 `build_pre_dispatch_compact_material_view` 通过 `_pre_dispatch_delta_material_blocks` 构造 blocks。两条路径的 `RunInputMaterialBlock` 字段赋值逻辑在各自模块内。
- **影响**: 实施 agent 可能忽略字段差异，产出与旧路径不等价的 material blocks，导致 compactor 输入变化。
- **建议改法和验证点**: 在 Slice 2 测试中增加一个断言：对同一组 accepted evidence events，分别通过旧 `build_accepted_tool_evidence_material_blocks` 和新 `build_pre_dispatch_compact_material_view` 路径构造 blocks，断言 `text`、`readable_tool_name`、`readable_query_text`、`accepted_evidence_id`、`canonical_source_refs` 等关键字段一致。或在 plan 中明确声明新路径是权威路径，旧路径被删除。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F2-Unfixed-Low-Plan Slice 1 允许保留 chunk helper 与 Slice 3 rg 预期存在轻度张力

- **位置**: Section 6, Slice 1 "具体改动" 第 4-5 条；Slice 3 验证命令 rg 预期
- **问题类型**: open question 未收敛
- **当前写法**: Slice 1 允许保留 chunk helper 作为显式 budget chunk helper，但要求当前默认路径不得调用。Slice 3 rg 预期四个旧常量不应在 production code 中出现，并补充"若 `EVIDENCE_BLOCK_CHUNK_TEXT_MAX_CHARS` 被保留为显式 budget chunk helper 常量，必须失败回到 review，除非它已由 `memory_projection_policy` 定义"。
- **反例/失败场景**: 如果 implementation agent 在 Slice 1 保留了 `_evidence_chunks` helper 并重命名 `EVIDENCE_BLOCK_CHUNK_TEXT_MAX_CHARS` 为新名字，Slice 3 rg 不会命中旧名字，但实质上保留了未由 policy 定义的产量常量。如果 agent 删除了 helper 和常量，则没有问题。
- **为什么有问题**: 两条指令存在方向性张力：一个允许保留（作为显式 budget helper），一个要求 production code 中不出现旧常量。Implementation agent 需要自行判断"保留但重命名"是否满足 rg 检查。
- **直接证据**: Slice 1 "若保留 chunk helper，必须改名为显式 budget chunk helper"；Slice 3 "四个旧常量不应在 production code 中出现。若 `EVIDENCE_BLOCK_CHUNK_TEXT_MAX_CHARS` 被保留为显式 budget chunk helper 常量，必须失败回到 review"。
- **影响**: Implementation agent 可能保留 helper 但重命名常量，绕过 rg 检查，实质上未完成移除。或 agent 可能过度删除，移除未来显式 budget chunking 可能需要的基础设施。
- **建议改法和验证点**: 在 plan 中明确裁决：本 WU 删除 `_evidence_chunks` helper 和 `EVIDENCE_BLOCK_CHUNK_TEXT_MAX_CHARS` 常量，不保留显式 budget chunk helper。未来若需要显式 budget chunking，在 WU-CM-13 或后续 WU 中新建。这样消除张力，让 implementation agent 有唯一明确路径。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F3-Unfixed-Low-Plan Slice 2 performance regression risk 已被 plan 识别但未给出具体防御

- **位置**: Section 8, "风险 / Open Questions" 第 2 条
- **问题类型**: 风险已识别但防御不足
- **当前写法**: Plan 承认"移除 `_ACCEPTED_TOOL_EVIDENCE_MATERIAL_LIMIT` 后，EventLog delta 很大时 material view 构造成本上升"，裁决"当前已有 `build_pre_dispatch_compact_material_view` 作为 EventLog truth source；如未来需要 page size，只能是 transaction 粒度 helper"。
- **反例/失败场景**: 一个长期运行的 Session 积累了数百条 `TOOL_RESULT_ACCEPTED` events。每次 dispatch 时，新 provider 调用 `build_pre_dispatch_compact_material_view` 加载全量 delta truth，构造所有 material blocks，再过滤出 accepted evidence。这比旧的 SQL `LIMIT 8` 查询慢一个数量级。
- **为什么有问题**: Plan 把性能风险推迟到"未来"，但未定义触发条件（多少条 evidence 时需要优化）或 owner。这不是 blocker，但属于 plan completeness gap。
- **直接证据**: `dayu/host/compact_material.py:457-553` 的 `build_pre_dispatch_compact_material_view` 加载全量 delta rows；`dayu/host/run_input.py:3280-3337` 的 `_recent_accepted_tool_result_rows` 使用 `LIMIT ?`。
- **影响**: 生产环境长 Session 可能出现 dispatch 延迟。不阻塞当前 WU，但应在 plan 中明确 deferred owner。
- **建议改法和验证点**: 在 Section 8 风险中追加 deferred owner：`deferred-with-owner: WU-CM-13 或后续 performance hardening WU`。或在 plan 中说明当前 Session 生命周期（财报分析 Agent）的 evidence 数量级不会触发此问题。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Architecture Boundary Review

Plan 正确遵守架构边界：

- 不修改 `dayu.contracts` 公共契约。
- 不修改 Engine `ToolExecutor`、`AgentRunRequest` 或 `RunnerEvent` contract。
- 不修改 EventLog canonical event 定义或 schema。
- 不新增 `dayu.runtime` 依赖。
- 所有改动在 `dayu/host/compaction.py`、`dayu/host/compact_material.py`、`dayu/host/run_input.py` 内部，属于 Host context governance 内部职责。
- Plan 正确保留 `MAX_VNEXT_*` output parser safety guards，区分 input material legality 与 output candidate accept barrier。

## Best-Practice Review

- Plan 采用删除优先策略（删除 guard、删除常量、删除默认 chunking），符合最小化原则。
- Plan 复用现有 `build_pre_dispatch_compact_material_view` 作为 EventLog truth source，避免新增第二套 retrieval-volume truth。
- Plan 的 slice 切分合理：Slice 1（DTO + chunking）和 Slice 2（row limit）独立可验证；Slice 3（regression + audit）是合并验证。
- 常量审计要求来自控制文档，不是 plan 自行添加的 scope creep。

## Overengineering Review

Plan 没有过度设计。它只删除私有 guard，复用现有基础设施，不新增 framework、policy schema、service callback 或 public API。常量审计是控制文档已明确要求的 final closeout gate 条件。

## Overcoupling Review

Plan 没有引入过度耦合。Slice 1 和 Slice 2 改动文件不重叠（`compaction.py` / `compact_material.py` vs. `run_input.py`）。Slice 2 的 `build_pre_dispatch_compact_material_view` 依赖是已有依赖方向（`run_input.py` → `compact_material.py`），不引入反向依赖。

## Conclusion

**pass-with-risks**

Plan 是 code-generation-ready 的，动机成立，scope 合理，slice 可独立验证，不引入 public API / durable schema / EventLog canonical semantic / Engine contract 变更。三个 findings 均为低严重程度：F1 是实施时需验证的字段一致性问题，F2 是指令张力可通过明确裁决消除，F3 是已识别的性能风险可通过 deferred owner 跟踪。Plan 的停止条件清晰，non-goals 正确排除了 WU-CM-13 scope。建议 controller 裁决 F2 的张力（删除 vs. 保留 chunk helper），其余 findings 可在实施时处理。
