## Findings

### 1. [未修复] [低] Host 对 final_answer 内容空性使用不同判据重新校验

- **入口/函数**: `_final_answer_plan` → `dayu/host/engine_ingest.py:4966`
- **文件(行号)**:
  - 生产：`dayu/host/engine_ingest.py:4966`（Host 侧）
  - 对比：`dayu/engine/agent.py:1790`（Engine `_classify_iteration`）
- **输入场景**: Runner 产出一个仅包含空白字符（如 `"  "`）的最终回答
- **实际分支**:
  - Engine 路径：`_classify_iteration` line 1790 检查 `content == ""` → 仅空白串 `"  "` **通过**检查 → 产出 `final_answer`
  - `run_agent_and_wait` line 2900-2910：`EngineEventType.FINAL_ANSWER` → 构造 `EngineRunOutcomeFinalAnswer(content="  ")`
  - Host 路径：`_final_answer_plan` line 4966 检查 `data.content.strip() == ""` → **拒绝** → 转换为 `_failed_plan(reason=_REASON_EMPTY_FINAL_ANSWER)`
- **预期行为**: 内容有效性判据应由唯一 owner 定义。Engine 作为 `final_answer` 的生产者，是内容有效性的自然 owner。若 Engine 接受 `"  "` 为有效内容，Host 不应重新裁决
- **实际行为**: Host 用更严格的 `.strip()` 判据覆盖了 Engine 的 `== ""` 判据，将 Engine 报告的成功终态改写为失败终态
- **直接证据**:
  - Engine `agent.py:1790`: `if reject_empty_final_content and content == ""`
  - Host `engine_ingest.py:4966`: `if data.content.strip() == ""`
  - 两个判据不一致：`"  ".strip() == ""` 但 `"  " != ""`
- **Semantic fact or contract involved**: "final_answer 内容是否可展示/有效"
- **Correct owner**: Engine（`agent.py:_classify_iteration`），因为它是 `final_answer` 的唯一生产者，拥有内容有效性的判定权
- **Where ownership drifted**: Host `engine_ingest.py:_final_answer_plan`（下游消费者）用不同判据重新裁决
- **Why the local-minimum design can fail**: 当前 Engine 判据已在正常路径（`reject_empty_final_content=True`）和 force-answer 路径（`reject_empty_final_content=False` → 显式 `FORCE_ANSWER_EMPTY` 检查）中充分覆盖。Host 的额外 `.strip()` 检查意味着：如 Engine 未来修改内容判据（例如接受仅空白串作为某些降级场景的有效回答），Host 会静默改写为失败，导致"Engine 说成功但 Host 记失败"的不一致
- **Recommended minimum owner-level correction**: 二选一：
  - (A) 将判据所有权完全归 Engine：Engine `_classify_iteration` 同时使用 `.strip()` 判据拒绝仅空白内容，Host 删除重复检查
  - (B) 将判据显式化为跨层 contract：在 `FinalAnswerData` 或 `AgentRunResult` 上添加 `content_valid: bool` 字段，由 Engine 设置，Host 只消费
- **Downstream repair to remove**: Host `engine_ingest.py:4966-4978` 的空白内容拒绝逻辑（如选方案 A）
- **Owner-level tests to add**: Engine 侧测试验证 `_classify_iteration` 拒绝仅空白内容（含 `"  "`, `"\n"`, `"\t"` 等仅空白串）
- **Verification points**:
  - Engine `_classify_iteration` reject_empty_final_content 分支断言
  - Host `_final_answer_plan` 不再做独立空白判定
  - 端到端测试：仅空白回答在各层一致表现为失败

### 总体评估

Engine 层的语义所有权 discipline 整体优秀：

- **公共契约边界清晰**：`AsyncRunner` Protocol、`ToolExecutor` Protocol、`CancellationToken` Protocol 均以 Protocol 定义，Engine 只消费协议面
- **错误码所有权明确**：`EngineRunErrorCode`（Engine-owned 闭集）+ `RunnerSpecificErrorCode`（provider/adapter 专有码）通过 `EngineErrorCode` 联合和 `serialize_engine_error_code` 统一序列化，Host 不重新解释
- **状态机推进权单一**：Agent 是唯一有权推进 run 状态、产出 terminal event 的 owner；Runner 只产出 `RunnerEvent`，不参与 run 终态决策
- **取消观察语义分层正确**：`CancellationToken` 是纯观察协议（`dayu/contracts/`），`dayu/runtime/cancellation` 提供层中立 race helper，Runner 内部用私有 `_RunnerInterrupted` 翻译取消信号
- **工具执行批式握手协议正确**：Engine 只调用 `ToolExecutor.execute` 一次，输入输出双射校验归 Engine，batch 内并发/审批/超时归 Host/ToolRuntime
- **导入边界严格**：`tests/engine/test_import_boundary.py` 通过 AST 扫描确保 Engine 不导入 `dayu.host`/`dayu.service`/`dayu.ui`/`dayu.fins` 等上层模块

两个 Low severity findings 均属于边界情况：
1. Host 对 final_answer 的空性重判据（`.strip()` vs `== ""`）在极端输入下会造成 Engine-Host 终态不一致
2. Engine Agent 测试对 runner 实现模块的直接导入增加了测试与实现的隐性耦合
