### Finding 5: close_drain_timeout_seconds behavior and durable-store close safety — FIXED ✅

- **Controller requirement**: "Clarify what `close()` does after `close_drain_timeout_seconds` fires, and how durable store close is prevented while a background task / thread can still touch the store."
- **Verification evidence**:
  - Plan line 277-281 (Close drain): "After the timeout fires, `close()` logs a structured error with the current diagnostics snapshot, keeps the close gate closed, continues waiting for the in-flight poll task or worker thread to finish, and does not return while that task/thread can still touch the durable store.   - Plan line 528-529 (Slice 2 Error handling): "If `close_drain_timeout_seconds` fires, `close()` records/logs the timeout and continues waiting until the running poll task/thread is stopped; it must not return while the poller can still access the durable store."
  - Plan line 543-544 (Slice 2 Tests): "Close drain timeout records/logs a timeout and still prevents durable store close until the in-flight poll path has actually stopped."
  - The explicit tradeoff (sync adapter hang → Host close hang) is documented as a safety choice.
- **Status**: Fully fixed. The timeout is correctly scoped as operator-visibility threshold, not a detach mechanism. The causal chain (close() blocks → durable store stays open → no SQL-after-close) is explicit.

### Marginal Observations (Not Blockers)

These are not findings but observations the implementation agent should be aware of:

1. **Batch claim two-option ambiguity (line 372-373)**: The plan offers "repeated single-row claim attempts up to `limit`" OR "per-row isolated CAS attempts inside one write transaction." Both produce correct independent claims. The implementation agent should pick one and be consistent. The plan's invariant (line 167: "A separate read result must never authorize an adapter call") resolves any ambiguity about SELECT-then-UPDATE — regardless of transaction boundary, each claim must be authorized by its own atomic write.

2. **Missing adapter not in data flow diagram (lines 390-410)**: The data flow diagram shows the claim → adapter call → release path but does not show the missing-adapter branch (claim → detect missing → release with backoff). This is covered in the error handling section (line 406-407) and is not a correctness gap. The implementation agent should follow the error handling text, not treat the data flow diagram as exhaustive.

3. **Close gate vs resolve_wait race window (lines 520-522 vs 534)**: The plan says gate check is before resolve_wait (line 520-522), and if close begins after resolve_wait entered the command path, let it finish (line 534). There is an inherent race window between gate check and resolve_wait entry where close could begin. The plan correctly handles both outcomes: if gate is closed at check time, skip and release as `shutdown_skipped`; if resolve_wait already entered, let it finish. This is the correct approach for a non-preemptible command path.

None of these observations rise to the level of a material blocker. They are clarifications the implementation agent can resolve with the existing plan text.
