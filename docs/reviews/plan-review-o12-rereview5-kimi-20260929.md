## 3. Findings

### 1-未修复-[低]-upload job 新 typed 终态保存路径未钉死"已 terminal 不覆盖"语义

- **位置**: plan §2 O12-PR4-F3（"upload job 的 `except Exception` 在 `ingestion_runtime.py:_run_upload_job` 调用 upload 专属 typed 终态保存路径……一次保存为同一 failed terminal"）；测试 3。
- **问题类型**: 契约缺失（终态原子性）/ 测试缺口。
- **当前写法**: plan 钉死了新保存路径的 reason 来源（failure owner、按 filing/material 语境）、summary 形状（`source_kind`/请求文件数/`stored_file_count=0`/`status=failed`/`failure_reason=reason`）与"一次保存为同一 failed terminal"，但未说明该保存仅在 record 仍 active 时生效、已 terminal（含并发取消、正常终态已落盘后后续步骤异常）不覆盖。
- **反例/失败场景**: `_run_upload_job` 的 `except Exception`（`ingestion_runtime.py:5051-5052`）覆盖整个 try 体，包括正常终态保存（:5029-5035 `save_accepted_upload_terminal_if_active` 成功落盘 SUCCEEDED/FAILED）之后的 `_emit_progress_event`（:5039-5049，event store 写失败可抛 OSError）与 `_upload_terminal_disposition_from_job_record`（:5036，parse 可抛）。若实施 Agent 把新 typed 保存写成无条件覆写，已成功终态会被改写成 `stored_file_count=0` 的 failed record——与 durable manifest 直接矛盾，恰好制造本 WU 反对的"显示失败但事实已发布"不一致。并发取消窗口同理（cancel 桥接先把 record 终态化为 CANCELLED，上传体随后抛错进入 catch）。
- **为什么有问题**: 现有共享 `_save_failed_from_exception` 以 read-check（:6001-6003 已 terminal 直接 return）+ 底层 `save_failed_or_cancelled_if_active` 双层保证不覆盖终态；plan 用一个**新函数**替换该 catch 却不复述该不变量。虽然 job store 终态 API 族统一为 `*_if_active`（:2104/:2126/:2994/:3030），自然实施大概率结构性安全，但按本 gate"owner 契约须在 plan gate 定死"的既定口径，终态不覆写是 job terminal owner 的核心契约条款，不应留给实施 Agent 从邻近代码推断。
