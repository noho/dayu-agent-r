### F02-未修复-高-`_resolve_ttl_seconds` 对 `float('inf')` timeout 抛出 `OverflowError`

- **预期行为**: `float('inf')` 作为"无超时"语义应回退到 `_DEFAULT_CURSOR_TTL_SECONDS`，不应抛异常。

### F10-未修复-中-Cursor 存储在进程内存中，不跨进程共享

### F11-未修复-中-Repair 扫描使用 `BEGIN IMMEDIATE` 可能阻塞并发写入

### F15-未修复-低-`scrub_tool_execution_outcome` 缺少 `assert_never` 守卫

### F16-未修复-低-blob_id 使用 `sha256[:16]` 前缀，碰撞概率非零

## Open Questions

1. **`_NeverCancelledToken` 是永久设计还是占位？** 当前 Engine 调用无超时保护——若 Engine 无限期不返回事件，RunStream 永久挂起。`_NeverCancelledToken` 无实际取消能力。

2. **`_task_aware_event_stream` 的 0.05s drain 窗口是否基于测量？** 若网络延迟或磁盘 I/O 导致事件推送滞后超过 50ms，stream 可能提前终止。

3. **`_append_run_input_context_snapshot_fact` 在第一个 attempt（`start_run` L640）调用时 `active_attempt=None`，不受 owner CAS 保护。是否预期？还是应统一走 scoped 路径？**

4. **Cursor 存储是否计划在后续 slice 持久化至 SQLite？** 当前进程内存方案在单进程部署下正确，但 phase8.5-plan 未明确多进程部署约束。

5. **`ProviderProtocolErrorData.message` 的 credential scrub 是否在后续 slice 计划中？** 当前设计仅在 tool-call 路径执行 scrub，provider 错误路径未覆盖。若设计意图是"EventLog/trace 仅 scrub tool 数据"，应在 plan/design 中明确声明。

## Residual Risk

1. **Provider 错误响应凭据泄漏**: 若 provider 在 HTTP 错误响应体中包含 API key，当前 `message` 和 `raw_payload` 持久化路径不清洗。

2. **多进程 cursor 不可用**: 若无需多进程部署则可接受；若需要，`RuntimeTruncateManager` 的进程内 cursor store 是阻塞项。

3. **Compact retry 路径 snapshot fact 写入无异常保护**: 极端竞态下可能导致无 terminal RunEvent 的 run（F06）。

4. **`_resolve_ttl_seconds` 对 `float('inf')` 的 OverflowError**: 无超时 + 无显式 TTL 的工具在截断后 cursor 构建失败（F02）。

5. **Repair 路径的 TOCTOU 窗口**: 事务外读取 EventLog 可能产生不一致的 snapshot 修复（F07）。

6. **`BEGIN IMMEDIATE` 在只读 recovery 扫描中阻塞并发写入**: 大规模 session 恢复时影响写入吞吐（F11）。

7. **Test 覆盖缺口**（来自子 agent 测试专项 review）:
   - Cursor TTL 过期清理缺少测试覆盖
   - `fetch_more` 参数校验（非法 cursor、非法 limit）缺少边界测试
   - 多进程并发安全性无测试覆盖
   - Crash recovery 端到端测试缺失
   - ToolTraceObserver 的 raw payload 生命周期 gap

8. **`_NeverCancelledToken` 无超时**: 若 Engine 挂起，无 deadline 或 cancel 机制保护 RunStream。
