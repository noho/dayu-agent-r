### Finding 1 — 非阻塞-高 — `assert_never` 掩盖未处理联合变体导致的 crash

- **入口/函数**: `_consume_runner_event` / `run_messages`
- **文件(行号)**: `dayu/engine/agent.py:1445`, `dayu/engine/agent.py:840`
- **输入场景**: 新增 `RunnerEventData` 变体或 `_IterationDecision` 变体但未更新对应 match 分支
- **实际分支**: 所有 `isinstance` 检查未命中后落入 `assert_never(data)`，触发 `AssertionError`
- **预期行为**: 产生结构化诊断，明确报告未处理的类型名称
- **实际行为**: `AssertionError` 被外层的 `except Exception` 吞没，转换为通用 `RunFailedData(error_code="runner_exception", recoverable=False)`，丢失所有诊断信息
- **直接证据**:
  - agent.py:1445: 在所有 `isinstance` 检查之后 `assert_never(data)` 无 message 参数
  - agent.py:1180: `except Exception` 捕获 `AssertionError`，仅记录 `type(exc).__name__`（为 `AssertionError`），不记录实际 data 类型
  - agent.py:840: `assert_never(decision)` 同模式
- **影响**: 未来新增联合成员时 crash 被静默掩盖为通用 runner 异常，导致线上无法定位根因
- **建议改法和验证点**: 将 `assert_never(data)` 替换为 `raise RuntimeError(f"unhandled RunnerEventData type: {type(data).__name__}")` 或产出 `RunnerProtocolErrorData`。同样处理 `assert_never(decision)`。验证：新增测试枚举联合成员后触发明确报错
- **修复风险**: 低
- **严重程度**: 高

### Finding 2 — 非阻塞-高 — `_RunnerInterrupted` 跨越模块边界可能泄漏为不可恢复异常

- **入口/函数**: `_run_runner_iteration` / agent 主循环
- **文件(行号)**: `dayu/engine/agent.py:1178-1214`, `dayu/engine/runners/openai/runner.py:453`
- **输入场景**: 未来 Runner 实现变更或 bug 导致 `_RunnerInterrupted` 未在 Runner 内部捕获而传播到 agent 事件循环
- **实际分支**: `except asyncio.CancelledError` 未命中（`_RunnerInterrupted` 显式不继承 CancelledError），落入 `except Exception`，转换为 `_ERROR_RUNNER_EXCEPTION` + `recoverable=False`
- **预期行为**: `_RunnerInterrupted` 是 cancel 语义，应被识别为可恢复/可重试的 cancel 终止
- **实际行为**: 被误分类为不可恢复 runner 异常，导致 Run 直接失败而非正常 cancel 收口
- **直接证据**:
  - `cancellation_helpers.py:21`: `class _RunnerInterrupted(Exception)` — 不继承 `asyncio.CancelledError`
  - agent.py:1178: `except asyncio.CancelledError: raise` — 不匹配
  - agent.py:1180: `except Exception` — 匹配，产出 `_ERROR_RUNNER_EXCEPTION`
  - 当前 `runner.py:453` 内部捕获了 `_RunnerInterrupted`，但这是跨 private 模块的实现细节
- **影响**: 当前未触发，但跨组件脆弱耦合。Runner 实现变更可能导致 cancel 语义误分类
- **建议改法和验证点**: 在 agent 事件循环的 `_run_runner_iteration` 中增加显式 `except _RunnerInterrupted` handler，产出 `_make_cancelled_terminal_with_close()` 代替回退到 `except Exception`
- **修复风险**: 低
- **严重程度**: 高

### Finding 3 — 非阻塞-中 — Session CLOSED 检查缺失于 public API facade 层

- **入口/函数**: `submit_followup`
- **文件(行号)**: `dayu/host/command.py:421-484`
- **输入场景**: 对已 CLOSED 或不存在的 session 调用 `submit_followup`
- **实际分支**: 仅检查 `session_id != request.session_id`（字符串相等），然后调用 `host._admission_service.submit_followup_queue()`。不读取 session 状态
- **预期行为**: facade 层应显式读取 session 状态，CLOSED 时返回清晰的 `HostApiError` + `INVALID_STATE` 语义
- **实际行为**: 错误可能从 durable 层以较低层错误码（如 `NOT_FOUND`）传播，丢失 session-closed 语义
- **直接证据**: command.py:421 入口不读取 session state；对比 api.py:2758 Protocol 定义的错误契约（`HostApiError` 但未约定 session-state-specific 错误语义）
- **影响**: 调用方难以区分 "session 不存在" vs "session 已关闭" vs "session 正常但请求非法"
- **建议改法和验证点**: 在 facade 层 admission 前增加 session 状态显式读取，CLOSED 时返回 `HostApiError(INVALID_STATE, "session is closed")`
- **修复风险**: 低（只读操作，不改变状态）
- **严重程度**: 中

### Finding 4 — 非阻塞-中 — `StdlibPidLivenessProbe` 未提供进程身份证明字段

- **入口/函数**: `collect` / `_classify_stale_owner`
- **文件(行号)**: `dayu/host/recovery_process.py:68-114`, `dayu/host/recovery_process.py:260-339`
- **输入场景**: 原 owner 进程死亡，pid 被新进程复用（Linux pid reuse）
- **实际分支**: `observed_start_token` 和 `observed_boot_id` 始终为 `None`（collect 不读取 `/proc/<pid>/stat`），`_classify_stale_owner` 跳过 identity 比对（`observed_start_token is not None` 为 False），返回 `OrphanProofInconclusive`
- **预期行为**: pid 复用应被检测为 positive orphan，触发 recovery

- **影响**: pid 复用场景下孤儿 Run 延迟发现
- **建议改法和验证点**: 增强 `StdlibPidLivenessProbe` 在 Linux 上读取 `/proc/<pid>/stat` 的 start_time，或文档化此 probe 在 pid-reuse 场景下不完整
- **修复风险**: 中（平台差异）
- **严重程度**: 中
