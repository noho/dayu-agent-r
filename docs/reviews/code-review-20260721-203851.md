- **建议改法和验证点**: 当前实现可接受。若需严格"同一个"语义，可在 `HostTransientDeltaSubscription.__init__` 中预构造并缓存。验证点：确认 S4 Service observation 成员存储不依赖对象 identity
- **修复风险（低）**: 缓存后需注意 error 实例不可变（`HostApiErrorDetail` 已是 frozen/slots dataclass）

### 2-未修复-低-`pop_next_nowait()` 不按 `_terminal_run_ids` 过滤，依赖调用方维持 invariant

- **入口/函数**: `HostTransientDeltaSubscription.pop_next_nowait()`
- **文件(行号)**: `dayu/host/transient_delta.py:415-433`
- **输入场景**: mailbox 中存在已 `mark_run_terminal` 的 Run 的 transient，且调用方在 pop 前未先排空 mailbox
- **实际分支**: `pop_next_nowait()` 直接从 `_mailbox.popleft()` 取出 event，不检查 `_terminal_run_ids`
- **预期行为**: 按当前 generator 实现，mailbox 总是在 durable event 处理前被排空（`pop_next_nowait()` loop 直到返回 `None`），`mark_run_terminal()` 之后的 `_offer()` 已被 filter 阻塞 — 所以该 invariant 在唯一调用路径（`_watch_session_events_after`）上始终成立
- **实际行为**: 当前无 caller 违反 invariant；但方法本身不防护，未来若新增调用路径可能误用
- **直接证据**: `pop_next_nowait()` 行 430 `event = self._mailbox.popleft()` 无任何 `_terminal_run_ids` 检查；对比旧实现 `drain_nowait()` 行 930-931 `if item.run_id not in self._terminal_run_ids: drained.append(item)` 有过滤
- **影响**: 当前无实际影响。若未来有代码在 `mark_run_terminal()` 之后直接调用 `pop_next_nowait()` 而不先排空，会 delivery 已终态 Run 的 stale transient。S2 引入 causal fence 后，该 invariant 可能需重新审视
- **建议改法和验证点**: 建议在 `pop_next_nowait()` docstring 明确说明 "caller must drain mailbox before mark_run_terminal()" 的 invariant。S2 实施时需检查是否需在 pop 层加入 `_terminal_run_ids` 过滤。验证点：S2 test 覆盖 mark_run_terminal 后仍有 mailbox residual 的场景
- **修复风险（低）**: 仅文档补充，无行为变更

### 3-未修复-低-Host close 时 pending durable events 静默丢弃，caller 仅收到正常 EOF

- **入口/函数**: `_PublicHostHandle._watch_session_events_after()`
- **文件(行号)**: `dayu/host/open_host.py:983-1031`
- **输入场景**: generator 已读取 durable batch 存入 `pending_durable_events`，但尚未逐条 yield 完毕时 Hub 被 `close()` → `_close_from_hub()` → `_closed = True`
- **实际分支**: 下一次 loop 迭代顶部的 `release_in_flight()` 和 `pop_next_nowait()`（返回 None）之后，`subscription.is_closed` 为 True → `return`（正常 StopAsyncIteration），未进入 `pending_durable_index < len(pending_durable_events)` 分支
- **预期行为**: 按 plan §4.4 "Host close 使 iterator 正常 EOF 并释放全部资源，不写 EventLog、不取消 Run"，正常 EOF 意味着不保证剩余 pending 事件的交付；未交付的 durable event 可由新 subscription 重新读取（durable store 特性）
- **实际行为**: pending durable events 被丢弃，generator 正常返回，`aclose()` → `subscription.close()` 清理状态
- **直接证据**: 行 986-988 `subscription.is_closed → return` 位于 pending durable check（行 989-995）之前；Host close 的 `_close_from_hub()` 行 547-552 先设 `_closed=True` 再 set ready
- **影响**: 正常 EOF 语义下无数据损失（durable event 可重读）；但 callers 需注意：Host close 期间 `anext()` 的最后一次调用可能看不到已在内存中的 durable batch 剩余部分。S4 Service exact-five 需要 `ITERATOR_ENDED` 处置此场景，当前 S1 行为与之兼容
- **建议改法和验证点**: 可考虑在 Host close 路径中先 yield 完 `pending_durable_events` 再允许 `is_closed` return，减少跨实现差异。但 plan §4.5 已接受当前语义，且与 S4 `ITERATOR_ENDED` 处置兼容。建议 S4 测试专门覆盖"Host close 时 pending durable events 未交付 → ITERATOR_ENDED → durable recovery 成功"路径
- **修复风险（低）**: 若改为先 drain pending，需确保 close 不会因 pending 过多而长时间阻塞
- **严重程度（低）**:

## Open Questions

1. **`_SESSION_WATCH_POLL_INTERVAL_SECONDS = 0.02` 的 CPU 影响**：在大量 Session 同时处于 CLOSING polling 的极端场景（per-Session cap=4，多 Session 同时关闭），N × 20ms polling 的累积 CPU 开销是否需要关注？当前 stress test 仅覆盖单 Session 场景，建议 S2/S3 在双 opener + 多 Session 的 stress 中加入此维度。

2. **`unwatched_runtime` 测试场景**：`test_hub_fanout_reuses_envelope_and_late_attach_has_no_replay` 中创建 `unwatched_runtime = _hub()` 并 publish 后再 attach。该 hub 的 reservation 和 subscription 生命周期未显式 close。当前测试中 hub 对象在测试结束即被 GC，reservation 泄漏不影响生产。但若未来引入 hub-wide resource tracking，此模式可能需要显式 cleanup。

3. **entrypoint_runtime.py S1 冻结符号与 S4 删除计划的对应**：当前 `_ENTRYPOINT_LIVE_EVENT_BUFFER_CAPACITY=256` 等符号在代码中保留，但 `_attach_watcher` 和 `_create_watch_and_wait_runtime` 已改为 async。这导致 relay drain task 仍以旧容量运行，但上游 Host delivery 已改为 512 item-bound。S1→S4 之间的过渡期没有中间态测试覆盖 relay 满 256 但 mailbox 未满 512 的交叉场景。建议确认 S2/S3 期间此中间态无实际影响。

## Residual Risk

1. **S2 causal fence 对 S1 基础设施的依赖**：S1 的 reservation/mailbox/in-flight/overflow 状态机是 S2 causal merge 的基础。当前 S1 测试覆盖了单 opener 的边界场景，但未覆盖 cross-opener 双独立 Hub 实例间的行为（这是 S2 的测试范围）。若 S1 的 reservation counting 或 in-flight accounting 有未被发现的 off-by-one，S2 的跨 opener reconciliation 可能将其放大为 ordering 错误。

2. **Service relay 过渡期**：`entrypoint_runtime.py` 的 `asyncio.Queue(maxsize=256)` relay 在 S1-S3 期间继续运行。上游 Host delivery 已改为 512 item-bound mailbox，下游 Service relay 队列仅有 256 容量。若 Host mailbox 在 Service relay queue 满之前先 drain，则无问题；但若 Service consumer 极慢（callback 阻塞），relay queue 先满（256）而 Host mailbox 尚未满（512），可能导致 relay `QueueFull` 行为不同于设计预期。S4 删除 relay 后此风险清除。

3. **`test_watch_factory_cancellation_close_race_and_allocation_failure_release`（行 544-693）** 将三个独立 failure scenario（factory cancellation、Host close race、iterator allocation failure）合并为一个 test function。若其中任一 scenario 的 assertion 因 regression 失败，需排查三个 scenario 的共享 monkeypatch 和 shared Host instance，降低故障隔离效率。建议 S2 实施时拆分为三个独立 test functions。

4. **`_clear_retained_state()` 同时清除 `_terminal_run_ids`**（`dayu/host/transient_delta.py:584-586`）：旧实现 `_clear_queue()` 不清除 `_terminal_run_ids`（因为 close 后 subscription 不再被使用）。新实现增加了 `_terminal_run_ids.clear()`，虽在功能上等价（close 后无 consumer 再访问），但语义上属于 cleanup 范围扩大。确认无 caller 在 close 后仍访问 `_terminal_run_ids`（当前无）。

5. **Packaged config `512/4` 硬编码在 JSON 和所有测试夹具中**：若需变更默认值，需修改 `host_runtime.json` + `tests/runtime/test_config_loader.py` 的 packaged assertion + 所有测试的 `_options()` helper 中的 policy 构造。当前无 DRY 风险（各层独立构造，是 plan 要求的"无 hidden fallback"），但变更时需全量搜索。
