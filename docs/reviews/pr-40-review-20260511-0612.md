## Findings

### 1-未修复-中-`_compact_or_fail` retry limit 路径两次 append 非原子导致不一致事件轨迹

- **入口/函数**: `_compact_or_fail` → `_run_to_store` 调用方
- **文件(行号)**: `dayu/host/_run_harness.py:1478-1495`
- **输入场景**: compact retry 次数达到 `context_compact_retry_limit` 上限时，先写 `context_compact_failed_draft` 诊断事件，再写 `host_context_compact_failure_terminal_draft` 终端事件。
- **实际分支**: 两次 `await self._scope_appender().append(...)` 分别在独立事务中执行。第一步 `context_compact_failed_draft` 落库成功后，第二步 `_append_terminal_draft_for_active_attempt` 可能因 owner CAS 命中 `AttemptFencingError` 而失败。
- **预期行为**: 要么两条事件都落库，要么都不落库；terminal 写入失败时整条事实链应原子回滚。
- **实际行为**: 第一步的 `context_compact_failed_draft` 已提交，EventLog 残留孤立的 CONTEXT_COMPACT_FAILED 事件，缺少配对 terminal 事件。虽然调用方 `_run_to_store` 在外层 catch `AttemptFencingError` 后走 `_handle_owner_lost` 尝试补写 `RUN_FAILED(attempt_lease_lost)`，但这两条事件语义不同（一条是 compact 失败，一条是 lease lost），下游 read model 投影或 audit 可能观察到不一致的事件序列。
- **直接证据**: `_run_harness.py:1478` `await self._scope_appender().append(context_compact_failed_draft(...))` 与 `_run_harness.py:1486-1495` `await self._append_terminal_draft_for_active_attempt(...)` 之间无事务边界包裹；第二步失败时第一步已提交（`_scope_appender().append` 内部开独立 `BEGIN IMMEDIATE` 事务，`_attempt_supervisor.py:251-260`）。
- **影响**: 不一致事件轨迹——compact 失败诊断事件孤悬，可能影响 audit 日志完整性。实际概率低（retry limit 路径仅在生产 compact 反复失败时触发），但一旦触发难以事后修复。
- **建议改法和验证点**: 将这两次 append 合并到同一 `BEGIN IMMEDIATE` 事务内，或先写 terminal 再写诊断事件（terminal 失败时不写诊断）；compact 路径的其它"诊断事件 + terminal 事件"配对（如 `_run_harness.py:1520-1537` 的 trace_missing 分支、`_run_harness.py:1568-1586` 的 decision_failed 分支）存在同样模式，应一并修复。
- **修复风险（低）**: 合并事务只影响 retry limit 和 compact 失败路径，正常路径不受影响；这些路径本身已被测试覆盖（`test_phase8_attempt_supervisor.py` 中有 compact 相关用例）。
- **严重程度（中）**:

### 2-未修复-中-repair 路径每个缺失 session 全量扫描 EventLog，O(S×E) 启动开销

- **入口/函数**: `_fetch_canonical_events_for_session`
- **文件(行号)**: `dayu/host/_conversation_memory_durable.py:369-402`
- **输入场景**: `repair_missing_session_snapshots` 发现 N 个 session 在 EventLog 中有 canonical 事件但 `host_conversation_memory_snapshots` 中无对应行时（如运维误删 snapshot 行、read model 损坏后重建）。
- **实际分支**: 对每个缺失 session，`_fetch_canonical_events_for_session` 调用 `event_store.fetch_events_by_position(after=after, limit=256)` 从 EventLog 起始位置全量扫描，每次 batch 迭代后 `after = position` 按全局 position 推进，直至扫完整个 EventLog。对 S 个缺失 session，执行 S 次全表扫描。
- **预期行为**: 一次 SQL 查询按 `session_id` 过滤后批量拉取该 session 的事件，或至少复用单次全扫描的结果为所有缺失 session 分组。
- **实际行为**: S=1 时仅多一次全扫描，影响有限；但若运维批量清理 snapshot 行（如迁移后 rebuild）导致 S 较大，startup 时 repair 阶段耗时 O(S×E)，可能显著延长启动时间。
- **直接证据**: `_conversation_memory_durable.py:389-402` 的 `while True` 循环对同一 session 内的事件逐 position batch 拉取，`after` 在每次迭代更新但 session 过滤在 Python 侧完成——无法利用 SQLite 索引跳过无关 session 的事件。SQL 查询无 `WHERE session_id = ?` 条件下推。
- **影响**: 启动性能退化。仅在 snapshot 异常缺失时触发，正常路径（`missing_session_ids` 为空）不受影响。若缺失 session 数超过 ~10 且 EventLog > 10 万条，启动可能显著变慢。
- **建议改法和验证点**: 在 `_collect_missing_session_ids` 中同时收集每个缺失 session 的 EventLog position 范围，然后在 `_fetch_canonical_events_for_session` 中按 position 范围直接 `SELECT ... WHERE session_id=? AND position BETWEEN ? AND ?`。或改为单次全扫描 + 按 session_id 分组的实现。
- **修复风险（低）**: repair 路径为纯诊断恢复路径，不参与主执行链路；修改后需验证 `test_phase8_durable_memory_recovery.py` 中 repair 相关用例。
- **严重程度（中）**:

### 3-未修复-低-`_renew_loop` 的 `except Exception` 过宽，可能将编程错误误归类为 STORAGE_ERROR

- **入口/函数**: `_renew_loop`
- **文件(行号)**: `dayu/host/_attempt_supervisor.py:979`
- **输入场景**: `self.lease_store.renew()` 或 `self.storage.transaction()` 内部因非存储层 bug（如 AttributeError: `self.lease_store` 意外为 None、TypeError 参数类型错误等）抛出异常。
- **实际分支**: `except Exception as exc:  # noqa: BLE001` 捕获所有 `Exception` 子类，调用 `_mark_owner_lost(session, STORAGE_ERROR)` 后 `return`。
- **预期行为**: 存储层异常（`sqlite3.DatabaseError`、`sqlite3.OperationalError` 等）应归类为 STORAGE_ERROR；编程错误（`AttributeError`、`TypeError` 等）应传播到 task 层面让 `_stop_session` 的 `task.exception()` 捕获并记录，而非被静默转换为 STORAGE_ERROR。
- **实际行为**: 任何非 `CancelledError` 异常都被吞并转为 STORAGE_ERROR。这会导致真正的代码缺陷被掩盖为"存储故障"，误导运维排查方向。
- **直接证据**: `_attempt_supervisor.py:979` `except Exception as exc:  # noqa: BLE001` 注释已表明作者意识到宽度问题，但仍选择 catch-all。同文件 `_stop_session:1110-1131` 的 done-task 路径也读取 `task.exception()`，但此时 exception 已被内层吞掉（task 正常 return，无 exception）。
- **影响**: 错误分类导致告警误报（STORAGE_ERROR 可能触发存储层告警而非代码缺陷告警），且丢失原始异常堆栈信息。实际触发概率低（需要 `lease_store` 或 `storage` 内部有 bug）。
- **建议改法和验证点**: 将 `except Exception` 限制为 `except (sqlite3.DatabaseError, sqlite3.OperationalError, OSError)` 或项目自定义的存储异常基类；其他异常通过 `raise` 重新抛出，让 asyncio task 的异常传播机制处理。`CancelledError` 已在 `except asyncio.CancelledError: raise` 中正确处理。
- **修复风险（低）**: 仅改窄异常捕获范围；已有测试中 renew loop 的 FENCED/STORAGE_ERROR 分支通过 mock 触发，不受影响。
- **严重程度（低）**:

## Open Questions

1. **`_stop_session` 为何在 lease_context 正常退出时无条件将 `loss_reason` 置为 FENCED？**
   `_attempt_supervisor.py:1138-1141` 在 `owner_lost_event` 尚未 set 时将其 set 并将 `loss_reason` 设为 FENCED。若 attempt 因正常 terminal（SUCCEEDED）而关闭，此时 `_sessions` 中该 attempt 的 session 被标记为 FENCED，但事实上 attempt 是成功完成而非被 fencing 驱逐。当前无代码在 attempt 关闭后查询 `loss_reason`，故无功能影响，但语义不精确。确认这是"安全兜底"设计（确保任何残留 waiter 立即返回）而非疏忽。

2. **`DurableConversationMemoryStore.repair_missing_session_snapshots` 调用时机是否需与 `ProjectionCoordinator.startup_reconcile` 之间有内存屏障？**
   `_durable_harness.py:172-176` 先 `await self.coordinator.startup_reconcile()` 再 `await self.memory_store.repair_missing_session_snapshots()`。两者操作同一 SQLite 数据库但不同表（projection checkpoint vs snapshot），且 repair 使用独立 `BEGIN IMMEDIATE` 事务，应无隔离问题。确认现有 WAL 模式 + BEGIN IMMEDIATE 足够保证 repair 读取的 EventLog 状态是最新的。

3. **多进程测试中 `multiprocessing.Barrier` 超时后行为未显式测试**
   `test_phase8_multiprocess_stress.py` 使用 Barrier 同步子进程，但未覆盖 Barrier 超时或子进程异常退出场景。生产环境中若 spawn 的子进程因 OOM 等原因僵死，barrier 永久阻塞会如何影响 harness？当前测试仅覆盖 happy path 并发。

## Residual Risk

1. **Service 层重试联动未测试**: P8 D2 规定 recovery 仅做诊断收口（MARK_LOST），不创建新 attempt，上游 retry 必须由 Service 层发起新 `StartRunRequest`。但 Service 层如何检测 attempt 变为 LOST、如何决定 retry、如何构造新 `StartRunRequest` 的完整闭环无测试覆盖。若 Service 层实现遗漏 `is_run_terminal` 检查直接重试，可能在同一 run 上创建竞争 attempt。

2. **长稳运行下的 lease 时钟漂移**: 测试全部使用 fake clock，无法暴露真实 wall clock 下 `datetime.now(timezone.utc)` 的单调性假设破缺场景（NTP 回调、容器暂停恢复）。当前 `FencingToken` 严格单调递增 + `lease_expires_at > now` 双重 CAS 可在大多数情况下防御，但 NTP 大幅回调时 `_compute_lease_expiry` 可能计算出比当前库内 `lease_expires_at` 更早的值。

3. **ConversationMemorySnapshot JSON 序列化的向后兼容**: `DurableConversationMemoryStore` 在读写 snapshot 时使用 `schema_version` 字段，但 `project_run_events` / `apply_patch` 内部使用 `json.dumps` / `json.loads` 直接序列化 dataclass。未来若 `ConversationMemorySnapshot` 或 `MemoryPatch` 的字段类型变化（如新增必填字段），旧 snapshot 反序列化将失败，且无 migration 机制。

4. **多进程 WAL 模式下的 checkpoint 争用**: SQLite WAL 模式允许多读单写，但 WAL 文件增长后需 passive/active checkpoint 回收空间。当前代码未显式管理 WAL checkpoint，依赖 SQLite 默认 `wal_autocheckpoint=1000` 页。高并发多进程场景下 WAL 可能膨胀。

5. **测试覆盖率盲区**:
   - `STORAGE_CONFLICT` 和 `RUN_TERMINAL` fence reason 仅在 store 层 map 中存在，无专门测试触发这些分支
   - `_task_aware_event_stream` 的 drain 超时路径（0.1s 窗口无事件则流自然结束）边界行为仅通过间接测试覆盖
   - `_renew_loop` 的真实 `sqlite3.DatabaseError` 异常路径（非 mock）未被测试
