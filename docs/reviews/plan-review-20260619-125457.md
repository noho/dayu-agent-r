# Plan Review: Compact Rejected Attempt Diagnostic Artifact

- **Reviewed target**: `docs/reviews/wu-cm-compact-rejected-diagnostic-plan-20260619-124435.md`
- **Work unit**: Compact rejected attempt diagnostic artifact
- **Reviewer posture**: adversarial plan review
- **Date**: 2026-06-19

## Assumptions Tested

1. **Recorder 只在 proposal failure 分支调用**: plan 在 Implementation Decisions #2 中说 "called from `run_compaction_operation()` only on proposal failure branches"。代码中有两个 proposal failure 分支：`except _CompactorProposalExecutionError` 和 `except Exception`。Plan 没有明确说明两个分支都需要接入 recorder。
2. **failure_stage 可从异常类型/消息确定**: plan 定义了 3 个 `failure_stage` 值但未指定判断规则。代码中 `conversation_compact_input_vnext_from_material_pack()` 可能抛出多种异常，不仅限于 `ValueError("previous reference continuity text is invalid")`。
3. **Recorder failure 不影响 rejected attempt 语义**: plan 说 "catch, log a warning, and continue"。但未要求测试验证此行为。
4. **EventLog payload 足够诊断**: plan 只把 `diagnostic_suffix` 放在 artifact JSON 中，不在 EventLog payload 中。`diagnostic_suffix` 包含脱敏异常消息。
5. **CompactMaterialBlock 可直接序列化为 JSON**: plan 说 artifact 包含 `previous_compacted_view: list of compact material block JSON, including raw text`。`CompactMaterialBlock` 是 frozen dataclass，plan 未指定序列化方式。

## Findings

### 1-未修复-高-failure_stage 判断规则未定义

- **位置**: Implementation Decisions, Contract / Schema / State-Machine Changes
- **问题类型**: 契约缺失
- **当前写法**: Plan 定义了 3 个 stable `failure_stage` 值 (`material_pack_to_compact_input`, `previous_compacted_view_parse`, `proposal_execution`)，但未指定如何从异常类型、消息或调用位置确定正确的 stage。
- **反例/失败场景**: `_parse_previous_reference_continuity_text()` 抛出 `ValueError("previous reference continuity text is invalid")`。但 `_previous_compacted_references_vnext()` 中还可能因 `ReferenceContinuityReasonVNext(reason_text)` 枚举转换失败抛出 `ValueError`。`_previous_compacted_view_vnext()` 调用的其他 `_previous_compacted_*_vnext()` 函数也可能抛出不同异常。Implementation agent 无法确定哪些异常应标记为 `previous_compacted_view_parse`，哪些应标记为 `material_pack_to_compact_input`。
- **为什么有问题**: Implementation agent 需要为每个 proposal failure 分支选择 `failure_stage`。没有判断规则会导致：(a) agent 自行推断，可能不一致；(b) 所有异常都用同一个 stage，降低诊断精度；(c) 不同 implementation slice 使用不同逻辑。
- **直接证据**: `compact_material.py:3467-3484` 中 `_parse_previous_reference_continuity_text()` 有两个 `raise ValueError` 分支（parts 长度非法和 prefix 不匹配）。`compact_material.py:3438-3464` 中 `_parse_previous_forward_intent_text()` 也有类似 ValueError。这些异常是否都应归为 `previous_compacted_view_parse`？
- **影响**: Implementation agent 跑偏 / 生成不一致的 stage 判断逻辑 / 后续新增 failure_stage 时无扩展规则
- **建议改法和验证点**: 在 plan 中增加明确的 stage 判断规则，例如：(a) 异常来自 `_previous_compacted_*_vnext()` 或 `_parse_previous_*_text()` 时 stage 为 `previous_compacted_view_parse`；(b) 异常来自 `conversation_compact_input_vnext_from_material_pack()` 的其他部分时 stage 为 `material_pack_to_compact_input`；(c) 异常来自 `run_prepared_compactor_proposal()` 或后续执行时 stage 为 `proposal_execution`。或者定义 stage 由调用位置决定（catch block 位置），不由异常类型决定。
- **修复风险（低/中/高）**: 低
- **严重程度（高）**: 高 — 影响所有 failure path 的诊断精度

### 2-未修复-中-prepared compactor 路径的 recorder 接入点未明确

- **位置**: Implementation Decisions #7, Implementation Slices Slice 1 Data flow
- **问题类型**: 架构边界 / 契约缺失
- **当前写法**: Plan 说 "In `dispatch.py`, construct a diagnostic recorder alongside the proposal manifest recorder"。但 `run_compaction_operation()` 中有两个异常处理分支处理 proposal failure：(a) `except _CompactorProposalExecutionError` (prepared compactor 的 `run_prepared_compactor_proposal()` 失败)；(b) `except Exception` (包括 prepared compactor 的 `prepare_compactor_proposal_run_input()` 失败和 generic path 的 `conversation_compact_input_vnext_from_material_pack()` 失败)。
- **反例/失败场景**: 当 compactor 是 `CompactorProposalPreparedCompactor` 时，`prepare_compactor_proposal_run_input()` 内部调用 `conversation_compact_input_vnext_from_material_pack()`。如果此时抛出 `ValueError`，异常不会被包装为 `_CompactorProposalExecutionError`（该包装只在 `run_prepared_compactor_proposal()` 的 `except Exception` 中发生）。因此异常落入 `run_compaction_operation()` 的 generic `except Exception` 分支。Plan 没有明确说明这个分支也需要接入 recorder。
- **为什么有问题**: `compaction_operation.py:519-538` 的 `_CompactorProposalExecutionError` 分支和 `compaction_operation.py:551-578` 的 generic `Exception` 分支是两个独立的代码路径。如果 plan 只暗示 "proposal failure branches" 而不明确列出两个分支，implementation agent 可能只在一个分支接入 recorder。
- **直接证据**: `compaction_operation.py:749-776` 中 `_prepare_compactor_proposal()` 的 prepared compactor 路径：`prepare_compactor_proposal_run_input()` 在 line 750-755 调用，如果失败，异常在 line 767 的 `except Exception` 中被包装为 `_CompactorProposalExecutionError`。但等等，我需要再看一遍代码。`prepare_compactor_proposal_run_input()` 的调用在 line 750-755，它在 `_CompactorProposalExecutionError` 的 `try` 块之外。所以如果它失败，异常不会被 `_CompactorProposalExecutionError` 的 `except` 捕获，而是直接传播到 `run_compaction_operation()` 的 generic `except Exception` 分支。
- **影响**: Implementation agent 可能只在一个分支接入 recorder，导致 prepared compactor 路径的 material projection failure 无法生成 diagnostic artifact
- **建议改法和验证点**: 在 plan 中明确列出 `run_compaction_operation()` 中需要接入 recorder 的两个分支：(a) `except _CompactorProposalExecutionError` 分支；(b) `except Exception` 分支。说明 prepared compactor 的 `prepare_compactor_proposal_run_input()` 失败落入后者。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中 — 影响一个特定路径的诊断覆盖

### 3-未修复-中-recorder failure 测试缺失

- **位置**: Implementation Slices Slice 1 Tests
- **问题类型**: 测试缺口
- **当前写法**: Plan 列出的测试场景包括：(a) 有效 `REFERENCE_CONTINUITY` block 产生 diagnostic ref；(b) descriptor metadata kind 正确；(c) artifact JSON 包含 raw text；(d) EventLog payload 不含 raw text。Plan 在 State-Machine invariant 中说 "Diagnostic recorder failure is best-effort: catch, log a warning with structured context, and continue returning a rejected attempt without `diagnostic_reference`"。
- **反例/失败场景**: 没有测试验证 recorder failure 的 graceful degradation。如果 `LocalArtifactStore.write_artifact_bytes()` 抛出异常（例如磁盘满、权限问题），recorder 应该 catch 并返回 `None`，不影响 rejected attempt 生成。但没有测试证明这个行为。
- **为什么有问题**: Plan 要求 "catch, log a warning, and continue"，但不要求测试验证。Implementation agent 可能忽略 catch 逻辑，或 catch 后的 log 格式不符合预期。
- **直接证据**: Plan Slice 1 Tests 列出 5 个测试场景，none 覆盖 recorder failure。`DurableCompactorProposalManifestRecorder` 的现有测试也没有覆盖 artifact store failure 场景（通过 grep 确认）。
- **影响**: Recorder failure 可能导致整个 rejected attempt 生成失败，违反 "recorder failure must not turn a rejected attempt into accepted compact" 的 invariant
- **建议改法和验证点**: 在 Slice 1 Tests 中增加一个测试：mock `LocalArtifactStore.write_artifact_bytes()` 抛出异常，验证 `run_compaction_operation()` 仍然返回 rejected attempt，`diagnostic_reference` 为 `None`，且 log 包含 warning。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中 — 影响 failure graceful degradation 的可验证性

### 4-未修复-低-diagnostic_suffix 未进入 EventLog payload

- **位置**: Contract / Schema / State-Machine Changes, EventLog payload contract
- **问题类型**: 最佳实践偏离
- **当前写法**: Plan 的 EventLog payload 新增字段包括 `failure_stage`, `parser_or_validator`, `exception_class`, `exception_message`, `offending_block_*` 等，但不包括 `diagnostic_suffix`。`diagnostic_suffix` 只出现在 artifact JSON 中。
- **反例/失败场景**: `diagnostic_suffix` 由 `_exception_diagnostic_suffix()` 生成，包含异常类型和脱敏后的异常消息（例如 `ValueError:previous reference continuity text is invalid`）。这个信息对快速 log 诊断很有价值。EventLog payload 已经有 `exception_class` 和 `exception_message`，但 `diagnostic_suffix` 是两者组合后的格式化版本，与现有 `diagnostic_refs` 的格式一致。
- **为什么有问题**: 现有 `diagnostic_refs` 的格式是 `diagnostic:<failure_category>:<operation_ref>:<diagnostic_suffix>`。如果 EventLog payload 有 `exception_class` 和 `exception_message` 但没有 `diagnostic_suffix`，operator 需要手动拼接才能与 `diagnostic_refs` 中的后缀对应。
- **直接证据**: `compaction_operation.py:1294-1296` 中 `diagnostic_refs` 的格式包含 `diagnostic_suffix`。Plan 的 EventLog payload 不包含该字段。
- **影响**: 低 — operator 可以从 `exception_class` + `exception_message` 推断，但与 `diagnostic_refs` 格式的不一致增加认知负担
- **建议改法和验证点**: 考虑在 EventLog payload 中增加 `diagnostic_suffix` 字段，或者在 plan 中说明为什么不需要（例如 `exception_class` + `exception_message` 已经足够）。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — 不影响核心诊断能力

### 5-未修复-低-CompactMaterialBlock 序列化方式未指定

- **位置**: Artifact JSON schema v1, `previous_compacted_view` 字段
- **问题类型**: 契约缺失
- **当前写法**: Plan 说 artifact JSON 包含 `previous_compacted_view: list of compact material block JSON, including raw text`。但 `CompactMaterialBlock` 是 frozen dataclass（来自 `dayu/host/compaction.py`），plan 未指定如何将其序列化为 JSON。
- **反例/失败场景**: `CompactMaterialBlock` 包含 `kind: CompactMaterialBlockKind`（StrEnum）和 `section: CompactMaterialSection`（StrEnum）等字段。如果 implementation agent 使用 `dataclasses.asdict()`，StrEnum 值会自动转为字符串。但如果 agent 尝试使用自定义 `to_json()` 方法，可能不存在。
- **为什么有问题**: Implementation agent 需要知道序列化方式。如果 `CompactMaterialBlock` 没有 `to_json()` 方法，agent 需要自行实现。Plan 中其他 artifact（如 compactor proposal manifest）使用 `canonical_json_dumps()`，但那是针对 `Mapping[str, JsonValue]` 的，不是 dataclass。
- **直接证据**: `compact_material.py` 中 `CompactMaterialBlock` 定义（通过 grep 确认是 frozen dataclass）。`compaction_operation.py:253-255` 中 `canonical_json_dumps(prepared_input.compactor_input_projection)` 用于 Mapping，不是 dataclass。
- **影响**: 低 — implementation agent 可以自行选择序列化方式，但可能导致不同 slice 使用不同方式
- **建议改法和验证点**: 在 plan 中指定序列化方式，例如使用 `dataclasses.asdict()` 后通过 `canonical_json_dumps()` 序列化，或者在 `compact_material.py` 中增加 `CompactMaterialBlock.to_json()` 方法。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — implementation agent 可以自行解决

## Open Questions

无 blocking open questions。

## Residual Risks

1. **Parser root cause 未修复**: Plan 正确地将此标记为后续 work unit。诊断 artifact 只提供更好的可观测性，不修复 `_parse_previous_reference_continuity_text()` 的脆弱 `split("; ")` 协议。
2. **long25 仍可能失败**: 诊断 artifact 让失败更容易定位，但不改变 compact success/failure 决策。
3. **`previous_compacted_view` 大小未限制**: 如果 `previous_compacted_view` 包含大量 blocks，artifact JSON 可能很大。Plan 未指定大小限制。建议后续监控 artifact 大小。

## Plan Review Conclusion

**pass-with-risks**

Plan 的架构方向正确：使用 artifact-backed diagnostic、EventLog 作为 compact index、reusing existing storage pattern。Scope 窄且明确，non-goals 合理。

主要风险是 `failure_stage` 判断规则未定义（Finding #1），可能导致 implementation agent 在多个 failure path 中做出不一致的 stage 判断。建议在 plan 中增加明确的 stage 判断规则。

次要风险是 prepared compactor 路径的 recorder 接入点未明确（Finding #2）和 recorder failure 测试缺失（Finding #3）。这两个风险不影响 plan 的整体方向，但需要在 implementation 前澄清。

Findings #4 和 #5 是低严重度的契约完善项，不阻塞 implementation。
