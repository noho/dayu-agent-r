### 1-未修复-中高-AttemptScopedRunEventAppender.append_in_transaction 生产路径零测试覆盖

- **入口/函数**: `AttemptScopedRunEventAppender.append_in_transaction`
- **文件(行号)**: `dayu/host/_attempt_supervisor.py:262-294`
- **输入场景**: harness 在其主循环中已持有外层 `HostStorageTransaction`（如 `_append_run_input_context_snapshot_fact` 路径），通过 `append_in_transaction` 在同事务内执行 `verify_owner` + EventLog append
- **实际分支**: `append_in_transaction` 是独立代码路径，与 `async append`（自己开事务）重复了 `_verify_run_id_matches` + `verify_owner` + `append_with_position_in_transaction` 的组合逻辑，但不走同一个 async 事务管理路径
- **预期行为**: 与 `async append` 语义一致——verify_owner CAS miss 抛 `AttemptFencingError` 回滚、run_id mismatch 抛 `AttemptFencingError(reason=OWNER_MISMATCH)`、正常 append 写入成功
- **实际行为**: 全仓库零测试覆盖此方法。`grep -rn "append_in_transaction" tests/` 返回空。生产路径 `_run_harness.py:2071` 确认使用此方法（`_append_run_input_context_snapshot_fact` → scoped appender → `append_in_transaction`）
- **直接证据**: `_attempt_supervisor.py:286-293` 内的 `verify_owner` + `append_with_position_in_transaction` 组合独立于 `async append`（line 251-260）的事务管理逻辑；两个方法各自维护相同语义但不同代码路径
- **影响**: 若 `append_in_transaction` 内 verify_owner → append 调用顺序、异常处理、或 CAS miss 回滚行为与 `async append` 路径产生回归差异，无法被测试发现。该方法是 harness 主执行循环中 `_append_run_input_context_snapshot_fact` 的实际写入路径
- **建议改法和验证点**: 补充测试：
  1. 在已有事务内调用 `append_in_transaction`，验证正常 append 写入成功
  2. verify_owner CAS miss（expired lease）时抛 `AttemptFencingError`，事务内 EventLog 无残留
  3. run_id mismatch 抛 `AttemptFencingError(reason=OWNER_MISMATCH)`
  4. terminal type draft 被拒绝（`ValueError`）
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中高

### 2-未修复-中-update_state_owner_aware 绕过注入的 UtcClock

- **入口/函数**: `AttemptLeaseStore.update_state_owner_aware`
- **文件(行号)**: `dayu/host/_run_state_store.py:598-599`
- **输入场景**: supervisor diagnostic close（`close_attempt_with_diagnostic_state` → `update_state_owner_aware`）或 harness `_finish_attempt_if_durable` 路径（state 在 `_ATTEMPT_FINISHED_STATES` 中）
- **实际分支**: `state in _ATTEMPT_FINISHED_STATES` 为 True 时，`finished_at` 使用 `datetime.now(tz=timezone.utc).isoformat()` 直接取系统时钟
- **预期行为**: `AttemptLeaseStore` 契约（line 389）声明"所有时间使用 timezone-aware UTC，由 UtcClock 注入"，且同类的 `renew`（line 519）、`verify_owner`（line 726）、`close_terminal`（line 664）、`_diagnose_fence`（line 921）均使用 `self.clock.now()`
- **实际行为**: `finished_at` 时间戳绕过注入的 `UtcClock`，使用真实系统墙钟
- **直接证据**: `_run_state_store.py:598-599` — `datetime.now(tz=timezone.utc).isoformat()`；对比同文件 line 519 `now = self.clock.now()`（renew）、line 664 `now = self.clock.now()`（close_terminal）
- **影响**: 测试中使用 `_FakeClock` 时 `finished_at` 写入真实墙钟，导致时间断言不可靠（`finished_at` 无法与 fake clock 的推进对齐）；生产环境无功能影响（wall clock 与 `UtcClock.now()` 在正确注入时等价）
- **建议改法和验证点**: 改为 `self.clock.now().isoformat()`；补测试断言 `finished_at` 与 fake clock 一致
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-低-IntegrityError 捕获范围大于文档说明

- **入口/函数**: `AttemptLeaseStore.acquire_new_attempt`
- **文件(行号)**: `dayu/host/_run_state_store.py:470`
- **输入场景**: `INSERT INTO host_attempts` 触发 `sqlite3.IntegrityError`
- **实际分支**: `except sqlite3.IntegrityError` 捕获所有 IntegrityError 子类，包括 `UNIQUE(run_id, attempt_index)` 冲突和 `PRIMARY KEY(attempt_id)` 碰撞
- **预期行为**: 文档（line 414-415）只说明 `UNIQUE(run_id, attempt_index)` 冲突触发 BUSY
- **实际行为**: PK 碰撞也走 BUSY 路径，`_build_busy_result` 查询 `(run_id, attempt_index)` 可能返回不同 attempt 的诊断信息
- **直接证据**: `_run_state_store.py:470` — `except sqlite3.IntegrityError:` 无进一步区分约束名
- **影响**: 极低概率（UUID v4 PK 碰撞概率可忽略）；诊断 payload 可能描述错误的 attempt
- **建议改法和验证点**: 可在 `except` 内检查异常消息是否包含对应 UNIQUE 约束名，或接受当前行为并更新方法 docstring 说明 IntegrityError 的完整语义
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 5-未修复-低-context overflow retry 时 acquire 失败导致 Run 无 terminal event

- **入口/函数**: `LocalRunHarness._run_to_store` context overflow retry 路径
- **文件(行号)**: `dayu/host/_run_harness.py:936-949`
- **输入场景**: context overflow 触发 compact，旧 attempt 标记为 STALE 后，`_begin_attempt_if_durable` 创建新 attempt 时 acquire 失败（如 `AttemptFencingError`）
- **实际分支**: 异常传播到 `except Exception` 层 → `_append_worker_failure_if_needed` → 尝试 append `RUN_FAILED` → 但此时 `current_active_attempt` 已被 `_finish_attempt_if_durable(STALE)` 关闭，新 attempt 未创建成功
- **预期行为**: Run 应有 terminal event 以正确终止 RunStream
- **实际行为**: `_append_worker_failure_if_needed` 的 append 走 `_resolve_attempt_appender(active_attempt=None)` → durable 路径下可能 `RuntimeError` fail fast（line 557-560）或 legacy 路径下写到错误 context
- **直接证据**: `_run_harness.py:936-949` — `_finish_attempt_if_durable(STALE)` 后 `_begin_attempt_if_durable` 失败；line 802-811 — `except Exception` 直接走 `_append_worker_failure_if_needed`
- **影响**: 极低概率（需要 acquire 在全新 attempt_index 上失败，且发生在 context overflow retry 路径）；Run EventLog 可能缺少 terminal event
- **建议改法和验证点**: `_begin_attempt_if_durable` 失败时，在 except 分支直接追加 Host-owned `RUN_FAILED` terminal event（不经 scoped appender），确保 RunStream 订阅方收到 terminal 信号
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 6-未修复-低-`get_snapshot` 可能读到未提交的 observer 事务数据

- **入口/函数**: `DurableConversationMemoryStore.get_snapshot`
- **文件(行号)**: `dayu/host/_conversation_memory_durable.py:172-182`
- **输入场景**: `ProjectionCoordinator.drain()` 正在 observer 事务中执行 `project_run_events_in_transaction`，已通过 `_write_snapshot`（UPSERT）写入但事务尚未提交。同时另一个协程调用 `get_snapshot` 读取同一 session
- **实际分支**: `get_snapshot` 通过 `self.storage.execute_read()` 在**同一连接**上执行 SELECT。SQLite 在同一连接内，SELECT 可见本连接未提交事务中已做的 DML 修改
- **预期行为**: `get_snapshot` 应返回已提交的数据（consistent read），特别是在 observer 事务回滚场景下不应泄露未提交的"幽灵数据"
- **实际行为**: 若 observer 事务后续因其他 sink 失败而回滚，`get_snapshot` 返回的快照数据从未真实存在
- **直接证据**: `_conversation_memory_durable.py:172-182` — `execute_read` 在 observer 事务的同一连接上执行；SQLite 同一连接同一事务内 DML 修改对 SELECT 可见
- **影响**: 正常流程（observer 事务最终提交）下无害。回滚场景下调用方可能基于不存在的数据做决策；实际触发概率低（observer drain 很少回滚）
- **建议改法和验证点**: WAL 模式下可通过第二个只读连接实现读已提交；或在 docstring 中注明当前隔离级别
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Resolved from Prior Review

以下前次 review（`pr-40-review-20260510-1546.md`）中的 findings 经复查已修复或不适用：

- **原 Finding 5 (double AttemptFencingError)**: `_handle_owner_lost`（`_run_harness.py:1078-1194`）现使用原子 `append_terminal_and_close`，CAS miss 时整事务回滚、EventLog 不残留 stale event，且正确捕获 `AttemptFencingError` 后关闭 `lease_exit_stack`。不再有"裸 append 失败后再 append failure event 也失败"的双重错误模式。

- **原 Finding 3 (multiprocess terminal close race)**: 当前测试设计受 `UNIQUE(run_id, attempt_index)` 约束限制，两个独立进程无法同时持有同一 attempt 的有效 owner token（acquire 阶段即冲突）。真实多进程竞争发生在"不同 attempt 竞争同一 run 的 attempt_index"层面，而非同一 attempt 行。测试的当前覆盖是合理的。

## Open Questions

1. **`AttemptStateStore` 是否应注入 `UtcClock`？** 当前 `AttemptStateStore` 是 P6 legacy 入口，不参与 fencing 时间判断。其 `create` 方法的 `started_at` 使用 `datetime.now()` 而非注入 clock。若认为这是 legacy 代码不再演进，可接受现状；若要求一致性，应注入 clock。建议在 docstring 中明确说明 legacy 路径的时间源策略。

2. **`AttemptOwnerToken.__repr__` 是否应覆写？** 当前 `AttemptOwnerToken` 的 `value` 字段是公开属性（`dataclass(frozen=True)`），虽然契约要求"明文不入库、不进日志"，但 enforcement 纯靠 convention。若 stack trace / debugger / logging framework 意外打印 `AttemptOwnerToken` 实例，明文会泄漏。覆写 `__repr__` 返回 `masked()` 可降低此风险。

3. **`recover_stale_attempts(run_id=None)` 全库扫描路径是否需要 smoke 覆盖？** 当前 recovery 测试均指定 `run_id`，全局扫描路径（`run_id=None`）的 SQL WHERE 子句结构与过滤扫描不同（`_run_state_store.py:808-831`），虽结构相似但未直接测试。

## Residual Risk

1. **`append_in_transaction` 生产路径零测试覆盖**：见 Finding 1。harness 主执行循环中非终态 scoped append 通过此方法写入，任何回归不可检测。

2. **`update_state_owner_aware` clock 绕过**：见 Finding 2。测试中使用 fake clock 时 `finished_at` 时间断言不可靠。

3. **`_finish_attempt_if_durable` 中 `close_attempt_with_diagnostic_state` 抛 `DatabaseError` 时 `lease_exit_stack` 泄漏**（`_run_harness.py:1921-1927`）：若 `close_attempt_with_diagnostic_state` 抛非 `AttemptFencingError` 的 `sqlite3.DatabaseError`，`aclose()` 不被调用，renew loop 继续运行最多 TTL 秒（默认 30s）后自然过期退出。非静默泄漏——renew loop 的 `CancelledError` 处理 + lease 自然过期确保最终收敛。

4. **`next_attempt_index` 无直接单测**：`MAX(attempt_index) + 1` 逻辑简单但回归会导致 attempt_index 碰撞 → `acquire_new_attempt` 返回 BUSY。

5. **durable conversation memory repair 的大 EventLog 扫描性能**：`_repair_missing_session_snapshots_locked` 对每个缺失 session 做全事件扫描（`_fetch_canonical_events_for_session`，`_conversation_memory_durable.py:352-364`），虽已分页（batch size 256），但 session 数量多时仍为 O(sessions × events) 复杂度。PR 已在 Notes 中标记为 P9 评估项。

6. **`get_snapshot` 的 SQLite 隔离级别**（Finding 6）：同一连接上 SELECT 可看到未提交事务的 DML 修改。正常流程下无害（observer 事务最终提交），但 observer 回滚场景下可能泄露"幽灵数据"。建议通过 WAL 模式第二只读连接实现读已提交。

7. **`_FakeClock` 在 5+ 测试文件中重复定义**：每个 P8 测试文件自行定义了语义完全相同的 fake clock 类。若需调整 fake clock 行为需要跨文件同步，建议抽取到 `tests/host/conftest.py` 作为共享 fixture。

8. **`ToolFetchMoreHandle*` 系列类型仍在 `__init__.py` 导出**：对�� handle 路径已在 P8-S2 从 `InMemoryToolRuntime` 完全移除，但这些类型（`ToolFetchMoreHandle`、`ToolFetchMoreHandleResult` 等）仍在 `__all__` 中，属于 dead API surface。

9. **`_has_terminal_event` docstring 与实际逻辑不完全一致**（`_conversation_memory_durable.py:366-383`）：docstring 说 "仅 USER_INPUT_ACCEPTED 单独存在视为 session 仍在进行"，但实际实现只检查 `TERMINAL_RUN_EVENT_TYPES`，不区分工具事实（`TOOL_RESULT_ACCEPTED` 等）。当前行为正确但描述不够精确。

## Architecture Assessment

整体架构设计优秀，核心机制经得起 adversarial review：

- **Fencing token 全局单调递增**：通过 SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` 保证，允许 gap（回滚场景），禁止倒退/复用——与 fencing token 契约一致
- **Terminal close 同事务原子性**：`append_terminal_and_close` 在单 `BEGIN IMMEDIATE` 事务内完成 verify_owner → append → close_terminal，任一步 CAS miss 整事务回滚，EventLog 不残留 stale terminal event
- **Owner-lost signal race 机制**：`_next_engine_event_or_lose_owner` 使用 `asyncio.wait` 实现正确的 race 语义——owner-lost 优先于 stale engine event
- **Recovery 诊断收口**：P8 D2 将 recovery 收窄为诊断动作（MARK_LOST/NOOP_TERMINAL），不创建新 attempt，避免 recovery cascade；上游 retry 由 Service 层显式发起新 `StartRunRequest`
- **ToolRuntime ContextVar 隔离**：使用 `contextvars.ContextVar` 传递 owner-bound appender，避免通过 `ToolExecutionContext` 泄漏 owner secret；`asyncio.Task` 级别隔离保证并发安全
- **Public API surface 干净**：`__init__.py` 仅暴露 contracts 类型 + `LocalRunHarness` + `build_durable_harness`，移除了 5 个 legacy package-level 函数
- **分层合规**：`dayu.runtime` 未被穿透；Host internal 契约（`_internal_contracts.py`、`_attempt_lease.py`）不进入 public `__all__`；supervisor 通过 store 层 CAS 访问数据库，不写裸 SQL
