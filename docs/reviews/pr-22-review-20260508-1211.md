## Findings

### 1. [已修复][Medium] `_project_truncation_for_llm` 对 `ttl_seconds` 的投影未按 spec 守卫 `has_more`

**文件**: [dayu/engine/agent.py](dayu/engine/agent.py) （`_project_truncation_for_llm` 函数）

**问题**: 当 `ToolTruncationInfo.has_more=False` 时，代码仍会在 `ttl_seconds is not None` 的情况下将 `ttl_seconds` 投影给 LLM：

```python
# agent.py 中新增的 _project_truncation_for_llm
if truncation.has_more:
    # ... 构建 next_action / fetch_more_args ...
    pass
if truncation.ttl_seconds is not None:    # <-- 无条件
    projected["ttl_seconds"] = truncation.ttl_seconds
```

但是 [dayu/engine/README.md](dayu/engine/README.md) 明确写了：

> 当 `has_more=False` 时不投影 `next_action`、`fetch_more_args` 或 `ttl_seconds`

当 `has_more=False` 时，scope 没有更多数据可读，`ttl_seconds` 对 LLM 无意义，反而可能误导模型。

**为什么当前未被触发**: `InMemoryToolRuntime` 只在 `has_more=True` 时构造 `ToolTruncationInfo`；`has_more=False` 场景下直接设 `truncation=None`，所以该路径当前是 dead code。

**但是**:
- 现有测试 `test_llm_truncation_projection_without_more_hides_fetch_hint` 刻意构造了 `has_more=False` 的 `ToolTruncationInfo` 来验证 spec，但测试用了 `ttl_seconds=None`，恰好没命中 bug。
- 如果未来某层在 `has_more=False` 时仍保留 `ttl_seconds`（例如用于内部 cursor TTL 记录），该值会被泄漏到 LLM context。

**后果**: 当前不触发，未来可能泄漏无意义的 `ttl_seconds` 给 LLM，造成困惑。

**建议修复**:
```python
# _project_truncation_for_llm 应改为
if truncation.has_more and truncation.ttl_seconds is not None:
    projected["ttl_seconds"] = truncation.ttl_seconds
```

同时补充测试用例：`has_more=False, ttl_seconds=60` → 断言 `"ttl_seconds" not in payload["truncation"]`。

### 3. [已处理][Info] `_event_store.py` 的 `_should_log_append` 使用 `is` 比较 StrEnum

**文件**: [dayu/host/_event_store.py](dayu/host/_event_store.py) （`_should_log_append` 函数）

**问题**:
```python
return (
    event.kind is RunEventKind.CANONICAL
    or event.type in TERMINAL_RUN_EVENT_TYPES
)
```

`event.kind is RunEventKind.CANONICAL` 依赖 StrEnum 成员的单例性。在 Python 3.11+ 中，`StrEnum` 成员是单例，同进程内 `is` 比较是安全的。但如果将来 RunEvent 在跨进程或序列化/反序列化边界上重建（例如未来 Remote / Outbox），`StrEnum(value)` 可能创建不同实例，此时 `is` 会失败，导致 preview delta append 被错误记录到 DEBUG 日志。

**当前影响**: 无。当前所有 RunEvent 消费都在同进程内，`kind` 字段直接使用枚举成员构造。

**建议**: 改为 `event.kind == RunEventKind.CANONICAL`，成本可忽略，但消除未来风险。
