## Findings

### 1-后移-P15-低-`_append_compact_exception_failure` 在 compact 成功后 append 失败时的错误语义

- **入口/函数**: `LocalRunHarness._run_to_store` -> `_compact_or_fail` -> `except Exception` -> `_append_compact_exception_failure`
- **文件(行号)**: `dayu/host/_run_harness.py:508-522`, `dayu/host/_run_harness.py:776-824`
- **输入场景**: `_compact_or_fail` 中 compact 决策成功（`decision.status is SUCCEEDED`），但在 append `context_compact_completed_draft` 或 `context_attempt_retrying_draft` 时 event store 写入失败
- **实际分支**: 异常被 line 514 `except Exception` 捕获，进入 `_append_compact_exception_failure`，写入 `context_compact_failed`（reason=INTERNAL_ERROR）+ `host_context_compact_failure_terminal`
- **预期行为**: compact 本身成功但写入失败时，事件历史应反映"compact 完成、append 失败"而非"compact 内部错误"
- **实际行为**: 事件历史记录为"compact 因 INTERNAL_ERROR 失败"，掩盖了真正的根因——event store 写入失败
- **直接证据**: `_run_harness.py:807-823` 使用 `reason=ContextCompactFailureReason.INTERNAL_ERROR`，未区分 compact 逻辑失败与 event store append 失败
- **影响**: 仅影响诊断/审计事件历史准确性；在生产环境中 event store 写入失败通常是不可恢复的存储层故障，此时 `_append_compact_exception_failure` 的后续 append 同样大概率失败，故此问题几乎不会实际持久化。属低影响理论缺陷
- **建议改法和验证点**: 在 `except Exception` 块内判断上游是否已有事件 append（例如检查 `_compact_or_fail` 中是否已 append `context_compact_requested_draft`），若有则使用更精确的 failure reason；此改进非 P6 阻塞项
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
