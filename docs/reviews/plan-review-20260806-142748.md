## Controller rejected-with-reason 裁决挑战

### Challenge 1: request/accepted union 关系

**Controller 裁决**: request 是可选集，output 是已选集；omit 时不相等。固定 output exact 逐 fact union 且为 request boundary 有序子集。

**修订 plan 文本**（第 88-91 行）:

> "该 request union 表示'可选 evidence boundary'，允许包含最终被省略的 prior fact refs；accepted aggregate 表示'实际 retained/new facts 的 refs'，因此正确不变量是 accepted aggregate 为 request union 的有序子集，而不是二者恒等。accepted aggregate 自身必须 exact 等于 replacement 中逐 fact refs 的 ordered unique union。"

**adversarial challenge**: 这个不变量是否在 durable parser 中可验证？parser 如何判断 accepted aggregate 是 request union 的子集？

**challenge 结论**: parser 可以：
1. 从 persisted boundary 重建 request union（所有 `canonical_evidence_refs` 的 unique union）
2. 从 persisted replacement 重建 accepted aggregate（逐 fact refs 的 unique union）
3. 验证 `set(accepted_aggregate) <= set(request_union)` 且 `accepted_aggregate == ordered_unique_union(per_fact_refs)`

这是确定性、可验证的不变量。合法 omit 使 request union 为真超集的逻辑正确。Controller 的拒绝理由成立。**Challenge 通过**。

### Challenge 2: fresh schema fail-closed

**Controller 裁决**: 拒绝"schema-4 rolling 时静默省略旧 facts 并走 fallback"；fresh schema 只允许 strict fail closed。

**修订 plan 文本**（residual risks 第 424 行）:

> "strict reader 遇到 schema-4 compact 必须 fail closed 并保留原 durable 数据；本 work unit 的实现验证与后续 formal scenario 必须新建 workspace/session。旧 workspace 的升级/迁移与用户工作流不在本 work unit 承诺内。"

**adversarial challenge**: "fail closed" 是否比"静默省略"更好？用户可能更希望系统能降级运行（省略旧 facts）而不是完全失败。

**challenge 结论**: 这里有两条路径：
- **路径 A（静默省略）**: schema-4 artifact → rolling builder 跳过 previous facts → boundary 只有 current evidence → compaction 继续但丢失历史 facts → 用户不知道历史 facts 被丢弃
- **路径 B（fail closed）**: schema-4 artifact → strict parser fail → `HostDurableError` → compaction 失败 → 用户看到错误 → 必须新建 workspace/session

路径 A 的问题是：(1) 用户不知道数据丢失；(2) 形成了未确认的兼容语义（"旧 schema 可以降级运行"）；(3) 如果后续 compaction 成功，丢失的历史 facts 无法恢复。路径 B 虽然用户体验更差，但：(1) 错误是可见的；(2) 不形成隐式兼容语义；(3) 原始数据保留在 durable store 中。

AGENTS.md 约束"禁止兼容性代码"和"默认按全新设计处理，不为旧实现、旧接口、旧测试保留兼容逻辑"。路径 B 更符合这些约束。Controller 的拒绝理由成立。**Challenge 通过**。

### Challenge 3: S1 C1-C3 alternative

**Controller 裁决**: 拒绝拆成可提交 S1a/S1b；采用同一未提交 slice 内 C1-C3 focused validation/review。

**adversarial challenge**: C1-C3 不是独立 committable 的，这意味着如果 C3 失败，agent 需要回退到 C2 状态。这与拆成 S1a/S1b 的回退成本相比如何？

**challenge 结论**:

- **S1a/S1b 模式**: S1a commit（删 v3 types，加 v4 types，更新 governance/material）→ S1b commit（切 consumers）。如果 S1b 失败，S1a 已 commit 但 consumers 未切，此时代码处于 v3 types 已删但 consumers 仍读 v3 的不一致状态。要回退必须 revert S1a。
- **C1-C3 模式**: C1 通过 → C2 通过 → C3 失败。此时所有修改都在工作树中未 commit。agent 可以直接修改代码修复 C3 问题，无需 revert 任何 commit。回退成本更低。

实际上 C1-C3 模式的回退成本比 S1a/S1b 更低，因为没有需要 revert 的 commit。Controller 的拒绝理由（"制造编译不完整 checkpoint 或短暂 v3/v4 双 owner"）是正确的。**Challenge 通过**。

## 新增发现

### F08-未修复-低-rolling builder 从 replacement 读取 per-fact refs 的边界构造链未显式串联

- **位置**: Frozen v4 contracts > 1 和 5
- **问题类型**: 契约缺失
- **当前写法**: section 1 说 boundary constructor 对 `PREVIOUS_EVIDENCE_FACT` 的 `canonical_evidence_refs` 必须非空；section 5 说 rolling builder 从 `accepted_replacement.evidence_facts` 构造 previous blocks。但两者之间的链路（rolling block refs → material provenance → boundary constructor → governance validator）未在单一位置串联。
- **反例/失败场景**: 实现 agent 可能在 rolling builder 中正确读取了 per-fact refs，但在 boundary constructor 中错误地从 material block 的 `canonical_source_refs`（即 compact event id）读取，而不是从 `canonical_evidence_refs` 读取。
- **为什么有问题**: 当前代码中 rolling builder 的 `canonical_source_refs=(event_id,)`（compact_material.py:2279/2291）。v4 修复后，material block 应同时携带 `canonical_source_refs=(event_id,)` 和 `canonical_evidence_refs=(per_fact_refs)`。boundary constructor 需要从后者读取 evidence refs，而不是前者。plan 没有显式说明这个区分。
- **直接证据**: compact_material.py:2279 `canonical_source_refs=(event_id,)`；plan section 1 说 `source_refs` 与 `canonical_evidence_refs` 是不同字段。
- **影响**: 实现 agent 可能混淆 `source_refs`（来源 event ref）和 `canonical_evidence_refs`（evidence ref），导致 boundary entry 的 evidence refs 错误。
- **建议改法和验证点**: 在 section 5 的 rolling 描述中补充："material block 的 `canonical_source_refs` 仍为 compact event id（来源标识），新增的 `canonical_evidence_refs` 为该 fact atom 的 per-fact evidence refs（provenance 标识）。boundary constructor 从 `canonical_evidence_refs` 构造 `PREVIOUS_EVIDENCE_FACT` entry 的 evidence refs。"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
