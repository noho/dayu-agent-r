## Findings

### 1-未修复-中-commit_batch 返回类型收敛不受 pyright 强制，12.5 静态检查存在盲区

- **位置**: §6.4 / §9.2 / §12.4 / §12.5
- **问题类型**: 测试缺口 / 验证盲区
- **当前写法**: "所有 repository implementation 与 test fake 的签名同步更新；不得用 `object`、`Any` 或 `getattr` 逃避类型"；12.4 gate 条件为 "`commit_batch` 新返回类型必须在 production implementation、callers 和 fakes 全部收敛"，靠 pyright + download regression 关闭。
- **反例/失败场景**: 结构性 fake（`_FixedBatchStateRepository`）或继承 `FsBatchingRepository` 的 override 若保持 `-> None`，在 Python 类型系统中 `None` 是 `CompanyMetaCommitOutcome | None` 的子类型，属于合法的返回类型协变——pyright 对 override 与 protocol 结构匹配都不会报错。未被更新的 fake 静默通过 pyright 与 regression，相关 workflow 测试永远拿不到 outcome，warning 断言缺失而不产生任何 red。
- **为什么有问题**: plan 声称 pyright 关闭"类型扩散"风险，但该风险恰恰落在 pyright 无法区分的盲区；12.5 的 `rg` 扫描只查 `hasattr|getattr|Any|object`，不检查 `commit_batch` override 的返回注解。
- **直接证据**: `tests/fins/test_filing_upload_publication.py:107` 的结构性 fake；`tests/fins/test_docling_upload_service.py:367/465/507` 等继承 override；pyright 对 `-> None` 覆盖 `-> CompanyMetaCommitOutcome | None` 无诊断。
- **影响**: fake 未收敛时 warning 语义被静默吞掉，正是本 work unit 要消灭的"下游无证据"复现；review 不可验收。
- **建议改法和验证点**: 在 §12.5 静态边界检查中增加一条：枚举仓库内全部 `def commit_batch`，逐一确认返回注解与 protocol 一致且 commit 成功路径返回 outcome 的 fake 有对应断言；或在 §9.2 增加"fake 收敛清单"逐文件打勾。验证点：`rg -n "def commit_batch" tests/ dayu/` 输出与注解逐项核对。
- **修复风险（低）**: 仅改 plan 验证章节。

### 2-未修复-中-SKIP+preserve 的 metadata commit 继承 whole-tree COMPLETE 校验，既往成功 skip 会在无关 source 非 COMPLETE 时转为失败

- **位置**: §8.3 / §13.2.1 / §8.4 状态表
- **问题类型**: 并发恢复风险 / 未声明的行为变化
- **当前写法**: §8.3 只描述"stage company intent → 调用同一个 `commit_batch`"；§13.2.1 只把"内容不变的 metadata batch publication"列为接受权衡，未讨论 commit 路径上的 whole-tree 校验后果。
- **反例/失败场景**: published ticker tree 中存在任一非 COMPLETE source（如 `REPAIR_REQUIRED`：source meta 存在但文件缺失，`FilingUploadPublishedState` 明确建模该 published 状态）。当前代码 SKIP 分支不 commit，该请求成功返回 skipped；按 plan 改造后，同一请求走 `commit_batch` → `_validate_complete_source_tree` 要求 staging 树内全部 filing/material source COMPLETE，整个上传转为 typed failure，alias/name 语义反而无法达成。
- **为什么有问题**: 成功→失败的语义漂移超出"refine SKIP 终结方式"的声明范围；该窗口真实存在（degraded source 到 repair 完成之间），且 plan 未把它列入接受权衡或测试矩阵，implementation agent 会在测试中"意外"撞见它并可能做出临时 fallback。
- **直接证据**: `_fs_storage_infra.py:555-560`（commit_batch 无条件先执行 `_validate_complete_source_tree`）、`:1080-1144`（要求每种 source kind 的每个 source COMPLETE）；`repository_protocols.py:436-445`（`REPAIR_REQUIRED` 是合法 published 状态）；当前 `filing_upload_publication.py:703-712`（SKIP 不 commit）。
- **影响**: 特定窗口内用户可见的成功请求变失败；或实现者为绕过校验引入错误路径。
- **建议改法和验证点**: 在 §13.2 显式接受该权衡（fail-closed 方向正确，但必须声明），并加一条测试：ticker 树含 REPAIR_REQUIRED 无关 source 时，SKIP+preserve 请求以 typed failure 结束且无 warning、无部分 mutation。验证点：`commit_tokens==[]` 或 commit 失败后 tree 不变。

## 用户指定五个审查点的结论

1. **commit_batch typed return 覆盖**：文件覆盖完整（7 个 fake 文件全部落入 plan 9.2 三个清单；production 仅两处实现均已列出），但 pyright 因返回类型协变无法强制 fake 收敛，属于验证盲区 → Finding 1。
2. **name-only skip full-tree commit**：final truth 正确（merge 在 writer+identity+publication guard 内重读 published meta 生成 outcome，且 writer 锁使 fresh 决策视图 == commit 时真值）；name-only 时 final meta 与 published meta 逐字段相等、`updated_at` 不变，无不当 mutation。但 skip 路径首次引入 whole-tree COMPLETE 校验，存在未声明的失败耦合 → Finding 2。
3. **缺失 warnings 当空值**：**不违反** fresh schema/禁止兼容。`from_pipeline_json` 的输入是进程内 fresh dict，且同一 parser 服务 material 流程（material 永远无 warnings，属 out-of-scope），缺失当空是跨流程的结构性可选字段而非旧库兼容；plan 的自我辩护成立，建议把"material 共享 parser"这一理由写进 plan 以便 review 可追溯（非 finding）。
4. **UploadOperationResult 承载 company outcome**：作为内部载体可接受（material 路径 outcome 恒为 `None`，字段默认值无行为影响，避免 tuple 返回签名扩散）；真正的问题是双载体冗余与早退/delete 分支绕过 → Finding 5。
5. **固定 warning 文案 vs oracle**：满足 oracle。文案"本次上传未修改已有公司名称；提交的名称与当前名称不同，请确认上传目标公司是否正确。"对 §8.4 全部 warning 行事实为真（preserve-published 恒保留名称）、可行动、无路径/raw names；exit code 0 + stdout/stderr 分流符合 oracle allowed_variants 的"终端文案微调"边界。oracle 中"忽略 alias update 时 warning"的字面分支已由 goal confirmation（`confirmed-by-user`，2026-08-17）授权为"合法 alias 持久化而非忽略后警告"的实现解释，plan 不修改 oracle 的做法正确。
