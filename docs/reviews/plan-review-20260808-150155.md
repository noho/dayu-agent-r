# F18 B2 fixed-profile 替代路径专项复核

## Reviewed target and scope

- Target：用户最新提出的 F18 专项替代路径——旧 Trial2 sequence 327 保留为 unresolved residual，不再作为
  `cap-constrained-memory-replacement@1` formal observation / readiness 的前置；从完全 fresh workspace 第一个
  opener 起固定 constrained profile，先形成 cap 内 accepted baseline，再用真实 FY2025 evidence自然形成超 cap
  replacement，并用独立 fresh real chains观察 repair、exhausted fallback和 reconnect。
- Binding authority：用户最新 follow-up；既有 Gateflow artifact 仅用于识别需要同步的旧 gate state。
- Contract sources：`docs/cli_ci_scenarios.json` 的目标 scenario record、`docs/cli_ci_oracles.json` 的 accepted
  predicates 29/30、`docs/cli_ci.md`、`docs/host/design.md`。
- Review boundary：只复核该替代方向是否可合法替代旧 root-cause hard gate；不编辑 plan/代码、不运行 provider、
  不裁决 B2，也不读取另一专项 reviewer artifact。

## Direct contract result

没有找到任何 accepted Oracle、scenario registry或 CLI CI handbook条款把以下内容列为 B2 mandatory evidence：

- wide profile 建立 baseline后 hot-switch到 constrained profile；
- 重放 Trial2 sequence 325-327；
- 在执行 fresh B2前先恢复 sequence 327 的原始 exception class/traceback；
- 将 `runner_candidate_invalid` root cause关闭为 accepted scenario的一部分。

目标 scenario 的 precondition 是 `relevant-material-over-initial-output-caps`，input class 是
`initial-request-with-real-caps`；五项 required evidence仅覆盖真实 caps、Host cap/usage audit、accepted provenance与
omitted exact complement、same-boundary repair + exhausted fallback、accepted truth跨 artifact/Memory/RunInput/reconnect
同源（`docs/cli_ci_scenarios.json:113260-113335`）。accepted predicates 29/30同样只约束 initial request、previous
EvidenceFact retain/omit、新 evidence provenance、bounded repair/fallback和同源 projection
（`docs/cli_ci_oracles.json:1869-1903`）。

`docs/cli_ci.md:886-898` 明确允许使用 CI-owned、较小但真实受支持的 context profile控制成本，只要求该 profile经
production config loader / Service assembly生效，并禁止 memory/output/EventLog/SQLite injection；它没有要求先用 wide
profile。`docs/cli_ci.md:533-539` 只要求当前 HEAD fresh补跑并交用户裁决。

因此，旧 root-cause closure不是 B2 registry/readiness的 mandatory前置。用户最新决定可以把它降为独立 unresolved
residual；此前专项 review把它当成 provider hard gate的 blocker应被推翻。该结论不等于 seq327已解释，也不允许把旧失败
重标 PASS。

## Assumptions tested

1. fresh fixed constrained profile是否被 scenario / handbook允许。
2. 不经过 wide baseline能否产生真实 `previous_evidence_fact`。
3. cap内 baseline + 新 FY2025 evidence能否构造“relevant material over initial output caps”。
4. accepted replacement、repair、exhausted fallback能否由不同 fresh real chains共同覆盖 scenario evidence。
5. stochastic MiMo branch未自然出现时能否仍声明 mandatory closure。
6. 旧 Trial2 residual与新 formal evidence能否保持 public/private和 verdict隔离。

## Findings

### DS-F18-RC01-未修复-高-现有 binding gate artifacts仍把已被用户撤销的 root-cause hard gate写成前置

- **位置**: `docs/gateflow/pr-190-f18-goal-confirmation-20260808.md:25-29,67-76`；
  `docs/gateflow/pr-190-f18-plan-20260808.md:20-22,99-129`
- **问题类型**: 目标漂移 / open question 未收敛 / 不可直接实施
- **当前写法**: Goal Confirmation要求 Trial2 root cause闭合后才 formal observation；plan在 root cause不复现时明确禁止
  Slice 3和真实 provider。
- **反例/失败场景**: Controller按用户最新 follow-up派发 fixed-profile run，但 implementation/review Agent仍按旧 artifact
  判定 unauthorized；或者 implementation Agent忽略旧 artifact直接运行，导致 Gateflow binding scope与实际执行不一致。
- **为什么有问题**: 最新用户决定已经重新定义 B2 readiness前置，而 registry/predicates/handbook没有支持旧 hard gate。
  Gateflow却要求 Goal Confirmation作为 binding scope contract，不能让相互矛盾的两个 gate truth并存。
- **直接证据**: 目标 scenario `required_evidence`（`docs/cli_ci_scenarios.json:113330-113335`）不含 root cause；
  predicates 29/30（`docs/cli_ci_oracles.json:1869-1903`）不含 Trial2；现有 goal/plan仍显式 hard gate。
- **影响**: 执行授权歧义、真实 provider gate误阻塞，或后续 reviewer无法判断 implementation是否越权。
- **建议改法和验证点**:
  1. Controller先用用户最新决定更新 F18 Goal Confirmation / gate adjudication：seq327降为 unresolved residual，不计入
     B2 mandatory coverage，也不再阻止 fresh fixed-profile observation。
  2. plan删除 Slice 2 -> Slice 3 hard dependency；保留“旧 failure不可解释、不能重标、不得用其证明产品正确”的
     residual条款。
  3. 更新后的 plan review必须逐项确认 B2仍为 `unadjudicated`、overall非 ready，直到新 evidence交用户裁决。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DS-F18-RC02-未修复-中-cap内 baseline必须先成为 accepted previous EvidenceFact而非普通历史文本

- **位置**: 替代路径的“cap内 baseline + 新 FY2025 evidence自然越 cap”步骤
- **问题类型**: 契约缺失 / 测试缺口 / 不可直接实施
- **当前写法**: 方向说明先建立 baseline，再加入 FY2025 evidence，但未冻结 baseline何时、以什么 owner fact成为下一次
  initial compactor input中的 `previous_evidence_fact`。
- **反例/失败场景**: FY2024只存在于 raw recent window、assistant answer或普通 memory text，尚未产生 accepted compact；
  第二次 compaction input便没有 previous EvidenceFact atom，无法观察 retain/omit，也不能证明 accepted provenance与omitted
  对 previous atom构成 exact complement。另一失败方式是新 FY2025 material仍受 recent-window保护，尚未进入当前 compact
  source boundary，所谓“两项超过 item cap”并未真正成立。
- **为什么有问题**: predicate 29要求 initial input含 previous EvidenceFact immutable atoms，模型只按 label keep/omit
  （`docs/cli_ci_oracles.json:1871-1875`）。Host design规定 previous atom只能从上一轮 typed accepted replacement原样投影，
  新 fact只能选择当前 evidence material（`docs/host/design.md:3377-3379,3423,3749-3753`）。普通历史文本不能替代。
- **直接证据**: `docs/cli_ci_oracles.json:1871-1875`；`docs/host/design.md:3377-3379,3423,3749-3753`；
  scenario precondition `relevant-material-over-initial-output-caps`。
- **影响**: fixed-profile链可能真实触发 compact却没有命中目标 predicate，浪费 provider并生成不可裁决 evidence。
- **建议改法和验证点**:
  1. replacement chain先完成并 seal一次同一 constrained policy下的 accepted FY2024 compact；从 compact artifact、canonical
     event与Memory直接验证 FY2024 fact及accepted provenance。
  2. 在第二次 provider call前，用 persisted compactor input/source boundary证明 FY2024以
     `previous_evidence_fact`出现、FY2025以当前 `evidence_material`出现，且 combined candidate空间真实超过同源 item/char cap。
  3. 若 FY2025仍在 protected recent window，只通过真实 follow-up使完整 turn自然离开窗口；不得编辑 memory、cursor或
     EventLog，也不得用 terminal sequence猜测已进入 boundary。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### DS-F18-RC03-未修复-中-自然模型分支不能在运行前承诺 repair和exhausted fallback都闭合

- **位置**: 替代路径的独立 repair/fallback real chains与“从而满足 mandatory evidence”结论
- **问题类型**: 过度验收标准 / 测试缺口 / 最佳实践偏离
- **当前写法**: 计划由独立 fresh real chains覆盖 same-boundary repair、budget-exhausted fallback和 reconnect，但尚未给出
  每条链的最大 Run数、ordinary/compactor model-call数、wall time、precondition probe与未触发 disposition。
- **反例/失败场景**: MiMo第一次 proposal就合法 accepted，则没有 repair；第一次 reject后第二次 accepted，则没有 exhausted
  fallback；连续调用也可能不再触发 compaction。禁止 output injection/fake意味着执行者不能为了凑齐分支继续无界试跑。
- **为什么有问题**: scenario确实把 repair和exhausted fallback列为 required evidence
  （`docs/cli_ci_scenarios.json:113330-113335`），Host operation attempt总数由 policy bounded
  （`docs/host/design.md:3740-3744`）。但用户同时要求 bounded最小观察、自然未触发就 `needs-more-evidence`。因此路径可执行，
  结果却只能是 conditional，不可预先承诺 mandatory closure。
- **直接证据**: `docs/cli_ci_scenarios.json:113326-113335`；`docs/host/design.md:3740-3744,3771-3775`；
  用户最新 follow-up与既有“自然未触发则 needs-more-evidence”约束。
- **影响**: 若没有预先冻结预算，执行 Agent可能过量消耗 provider或挑选/覆盖失败结果；若把 non-trigger写 PASS，则 B2
  evidence被错误升级。
- **建议改法和验证点**:
  1. 三类 chain在运行前分别冻结 fresh workspace/config digest、PTY动作、最大 Run/model-call/wall-time和停止条件；registry
     timeout 1800秒是上限，不是无限尝试授权。
  2. replacement+reconnect必须在同一 accepted truth chain内；repair/fallback可以独立 fresh chain聚合，但每条 outcome和
     digest都单独 seal，不覆盖。
  3. bounded窗口内未自然出现的 branch明确写 `needs-more-evidence`，B2继续 unadjudicated；只在实际两类 terminal均被观察时
     才声明对应 mandatory evidence sufficient。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Feasibility judgment

fixed-profile替代路径在架构与 scenario语义上可行：

1. 在 fresh workspace第一次 opener前写入完整 constrained execution profile；之后所有 invocation / reconnect复用相同
   config digest。该 setup满足 `open_host` construction-time policy owner，也满足 handbook允许的 CI-owned小 context
   profile路径。
2. 同一 constrained caps不阻止建立 baseline。第一次 accepted compact可以只保存 cap内容纳的 FY2024 EvidenceFact；该
   accepted replacement经同一 policy projection后成为下一次 compact的 previous atom。
3. 之后用生产 Fins tools取得真实 FY2025 evidence，再让完整 evidence turn自然进入 post-compact delta boundary。若 evidence
   fact item cap为 1，则一个 previous FY2024 atom加一个 new FY2025 atom已经形成真实 combined over-cap选择；Host可观察
   retain/omit、accepted provenance和omitted exact complement，无需 wide profile。
4. registry现有 evidence本就聚合多条真实路径；用户也明确允许 repair/fallback由独立 fresh real chains覆盖。每条链仍须
   使用生产 CLI、POSIX PTY、MiMo与真实 AAPL corpus，并单独 seal失败/成功 evidence。

## Public/private evidence boundary

- 新 formal bundle只从 public Host Tool Trace resolver/analysis、canonical EventLog/artifact projection、Memory/RunInput和
  bounded redacted SQLite observation形成可分发事实；raw SQLite、traceback、credential和绝对私有路径不进入 repo。
- 旧 Trial2 sequence 327保留原 immutable失败 evidence，在 human report中只作为独立
  `unresolved-residual/not-used-for-B2-mandatory-coverage`；不得合并到新 chain、删除、覆盖或改名 PASS。
- 新 B2 evidence即使 complete，也只能更新 scenario evidence refs/status evidence语义；`status`与
  `user_adjudication_identity`在用户裁决前仍为 `unadjudicated` / pending，overall readiness不得标 ready。

## Lens conclusions

- **Goal-bound minimal design**：最新用户决定把不可恢复的旧 exception从 B2 mandatory path剥离，减少了无 registry依据的
  额外 gate；这是 scope correction，不是降低 accepted scenario标准。
- **Architecture boundary**：固定 profile从 Service assembly到 Host typed policy同源，无需动态 per-Run profile、schema、
  adapter fallback或产品迁就。
- **Best practice / optimal solution**：fresh fixed-profile chain直接证明当前 scenario，旧失败单独留作 residual，是比 synthetic
  SQLite replay更可审查的路径。
- **Overengineering**：无需新增 typed cause、profile registry或 migration来取得 B2 evidence；是否另行调查 cross-opener
  policy continuity应进入独立 follow-up，不混入本 scenario。
- **Overcoupling**：replacement+reconnect必须同链；repair和fallback允许拆成独立 fresh chains，降低随机分支之间的耦合。

## Open questions

1. updated execution plan将冻结哪些 exact constrained caps、soft/hard ratio和 selected recent turn floor？这些值必须在首个
   opener前通过 production config loader验证，并在全链保持同一 digest。
2. 每条 real chain的最大 ordinary Run数、ordinary/compactor provider call数和 wall time是多少？
3. 复用哪个已审查 PTY harness、owner exporter与 public publication projector？其 digest和 failure sealing顺序是什么？
4. cross-opener policy continuity / seq327后续跟踪放入哪个独立 issue或 residual artifact？这不是 B2 mandatory gate，但不能
   被 final closeout遗忘。

## Residual risks and suggested tracking destination

- seq327具体异常仍未知：记录到 F18 final closeout residual / 独立 cross-opener policy-continuity follow-up；不计入 B2
  mandatory coverage，不声称已修复。
- MiMo自然行为可能不产生 repair或exhaustion：对应 chain标 `needs-more-evidence`，B2继续 unadjudicated。
- first compact未accepted、FY2025未离开 protected recent window或combined material未实际越 cap：立即 seal当前失败 chain，
  不把普通 context trigger冒充 target precondition。
- public/private publication任一 secret/path scan失败：该 evidence bundle不得进入 registry refs。

## Final plan review conclusion

`pass-with-risks`。

该专项方向推翻上一轮“必须先闭合旧 seq327 root cause才能运行 B2”的 blocker：没有 registry、handbook、Host design或
accepted predicate为该 hard gate提供依据。进入真实 provider前仍必须先同步 Goal Confirmation/plan，并把 baseline atom、
per-chain budget、natural non-trigger和publication步骤写成可执行 contract；这三项是 plan fix，不是恢复旧 root-cause hard
gate的理由。
