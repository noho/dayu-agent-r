### 001-未修复-高-resume path test fixture 未适配新 request atom 路径

- **入口/函数**: `_resume_wait_messages_from_current_start` → `_resume_wait_accepted_arguments`
- **文件(行号)**: `tests/host/test_run_input_builder.py:5311` (`_append_resume_wait_projection_events` helper); 生产代码 `dayu/host/run_input.py:3938`
- **输入场景**: 现有 resume wait 测试使用旧格式 fixture（`TOOL_RESULT_ACCEPTED` payload 不含 `accepted_evidence_envelope`，EventLog 中无 `TOOL_CALL_REQUESTED` event）
- **实际分支**: `_resume_wait_accepted_arguments` 调用 `accepted_evidence_envelope_from_payload` → envelope 为 `None` → 返回 `None` → 走 fallback guidance path
- **预期行为**: 测试 fixture 应创建 `TOOL_CALL_REQUESTED` request atom 和含 `accepted_evidence_envelope` 的 `TOOL_RESULT_ACCEPTED` payload，使 resume 路径走 happy path（3 条消息：user / assistant tool_call / tool result）
- **实际行为**: 4 个 resume wait 测试 FAIL（`test_resume_wait_messages_rebuild_tool_result_roundtrip`、`test_resume_wait_rejects_digest_mismatch_after_new_arguments_fields`、`test_resume_wait_completed_tool_content_wraps_non_object_value`、`test_resume_wait_replays_only_llm_safe_arguments`），全部因 envelope 缺失降级为 1 条 fallback system message
- **直接证据**: `tests/host/test_run_input_builder.py:424` — `assert len(messages) == 3` 失败，实际 `len(messages) == 1`；fixture `_append_resume_wait_projection_events` 未写入 `TOOL_CALL_REQUESTED` event 或 `accepted_evidence_envelope`
- **影响**: resume 路径的核心 happy-path 测试完全失效；生产代码行为正确但测试不能证明。同时意味着旧格式 wait-resolution 事件（无 envelope）会静默降级为 fallback guidance，丢失 tool_call + tool_message 闭环——这在旧数据库升级场景下是真实的用户体验退化
- **建议改法和验证点**:
  1. 更新 `_append_resume_wait_projection_events` fixture：追加 `TOOL_CALL_REQUESTED` event（event_class=CANONICAL_FACT, session/run/attempt/execution 与 result 一致, payload 含 LLM-safe arguments），在 `TOOL_RESULT_ACCEPTED` payload 中添加 `accepted_evidence_envelope` 和 `raw_tool_outcome`
  2. 4 个 FAIL 测试应全部恢复 PASS
  3. 新增一个专门测试：旧格式事件（无 envelope）确实降级为 fallback guidance 且不 crash
- **修复风险（低/中/高）**: 低——只需更新 test fixture，不涉及生产代码变更
- **严重程度（高）**: 阻断——违反 AGENTS.md "测试必须跟着实现边界迁移"；且 resume path 是用户可感知的恢复消息质量

### 002-未修复-中-`_wait_tool_call_requested_event` 缺少 `normalized_arguments_digest` 身份校验

- **入口/函数**: `_wait_tool_call_requested_event`（`dayu/host/waiting.py:1495`）
- **文件(行号)**: `dayu/host/waiting.py:1522-1533`
- **输入场景**: wait-resolution 读取 `TOOL_CALL_REQUESTED` request atom
- **实际分支**: 校验 event_type、session_id、run_id、attempt_id、execution_id、tool_call_id、tool_name；**不校验** `normalized_arguments_digest`
- **预期行为**: 作为 request/result 配对的关键入口，应校验 `normalized_arguments_digest` 与 wait_record 一致，防止跨调用 digest 拼接
- **实际行为**: `normalized_arguments_digest` 校验推迟到 `_wait_resolution_evidence_envelope` 内部（通过 request_payload 间接读取），不在 `_wait_tool_call_requested_event` 入口处 fail-fast
- **直接证据**: `dayu/host/waiting.py:1522-1533` — identity check block 校验了 session/run/attempt/execution/tool_call_id/tool_name，但未读取或校验 payload 中的 `normalized_arguments_digest`
- **影响**: 若 `TOOL_CALL_REQUESTED` event 因 idempotency key 碰撞或 future code path 被错误复用，且 `normalized_arguments_digest` 不一致，`_wait_tool_call_requested_event` 不会拒绝，而是在 envelope 构造时静默使用错误 digest。当前实际风险低（event_id 由 semantic_input_digest 派生，碰撞概率极低），但作为 fail-fast 防御应补上
- **建议改法和验证点**: 在 `_wait_tool_call_requested_event` 的 identity check block 中追加 payload `normalized_arguments_digest` 与 `wait_record.resolve_semantic_digest`（或等价 digest 来源）的校验；若 wait_record 无 digest 可比对则记录 open question
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 防御性缺陷，当前实际路径不触发

### 003-未修复-低-`_tool_result_resolution_payload` 从 request atom 读取 digest 未做 fallback 说明

- **入口/函数**: `_tool_result_resolution_payload`（`dayu/host/waiting.py:1420`）
- **文件(行号)**: `dayu/host/waiting.py:1454-1462`
- **输入场景**: wait-resolution payload 构造
- **实际分支**: `tool_schema_digest`、`tool_identity_digest`、`normalized_arguments_digest` 从 `request_payload`（即 `TOOL_CALL_REQUESTED` payload）的 required field 读取
- **预期行为**: 这三个 digest 应与 wait_record 中的对应字段一致；若 request atom 缺失这些字段，应有明确的 fallback 或 error
- **实际行为**: 使用 `required_payload_text` 读取——字段缺失时 raise `HostDurableError`。行为正确，但旧 request atom（在本次变更前由不同 code path 创建）可能不含 `tool_schema_digest` 或 `tool_identity_digest`，导致升级后首次 wait-resolution crash
- **直接证据**: `dayu/host/waiting.py:1454-1462` — `required_payload_text(request_payload, field_name="tool_schema_digest")`
- **影响**: 若存在在本次变更前创建的 `TOOL_CALL_REQUESTED` event（仅在 awaiting path 中不存在，因为本次变更前 awaiting path 不创建此 event），不存在实际风险。但设计文档应说明 request atom payload contract 的 required field 演化
- **建议改法和验证点**: 确认 `TOOL_CALL_REQUESTED` event 只由本次变更后的 awaiting path 创建，不存在旧格式 event 的兼容读取需求；若确认则此 finding 可关闭
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 当前无实际触发路径

### 004-未修复-低-SEC pipeline `summary.failed_count` fallback 可能掩盖 pipeline bug

- **入口/函数**: `_summary_from_pipeline_result`（`dayu/fins/pipelines/sec_pipeline.py:1900`）
- **文件(行号)**: `dayu/fins/pipelines/sec_pipeline.py:1924-1926`
- **输入场景**: SEC download pipeline 结果 summary 中 `summary.failed` 与 filing-level `status=failed` 计数不一致
- **实际分支**: `if summary_failed_count != failed_count: failed_count = summary_failed_count`
- **预期行为**: filing-level 互斥分类是真源，summary.failed 是 pipeline 聚合层的冗余字段
- **实际行为**: 当两者不一致时，用 summary.failed 覆盖 filing-level 计数——这意味着 pipeline summary 的 `failed` 字段优先于 filing-level status
- **直接证据**: `dayu/fins/pipelines/sec_pipeline.py:1924-1926`
- **影响**: 若 pipeline summary 的 `failed` 字段有 bug（例如包含非 failed filing），filing-level 的正确计数会被静默覆盖。当前 `discovered_count` 仍来自 `result.total`，不等于 `downloaded + skipped + rejected + failed` 时无断言
- **建议改法和验证点**: 考虑在 fallback 时记录 warning log 或 diagnostic event，而非静默覆盖；或明确设计文档中 `summary.failed` 与 filing-level `status=failed` 的优先级关系
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 防御性，当前 SEC pipeline summary 通常一致

## Open Questions

1. `TOOL_CALL_REQUESTED` 在 awaiting path 中的创建时机：当前是在 accept 时创建（即工具进入等待状态时），而非在 Engine 发起 tool_call intent 时。对于非 awaiting 工具，`TOOL_CALL_REQUESTED` 是何时创建的？如果两条路径创建时机不同，`occurred_at` 语义是否一致？设计文档说"记录工具调用 intent"，但 awaiting path 实际记录的是"工具调用被接受进入等待"。

## Residual Risk

- **resume path 测试缺口**: 4 个 FAIL 测试证明 happy path 未覆盖；修复 fixture 后需确认所有 9 个 resume_wait 测试 PASS
- **旧数据库升级**: 若用户 DB 中存在旧格式 `TOOL_RESULT_ACCEPTED`（无 envelope），resume 会静默降级为 fallback guidance。这是可接受的降级行为，但应在 README 或 migration notes 中说明

## Positive Checks

1. **TOOL_CALL_REQUESTED 与 TOOL_AWAITING 的 owner boundary 隔离正确**: `TOOL_CALL_REQUESTED` 是 `CANONICAL_FACT`，承载 LLM-safe 业务事实；`TOOL_AWAITING` 是 Host/ToolRuntime 治理事实。两者在同一事务中创建但语义隔离。设计文档明确"TOOL_AWAITING 不得成为 Conversation Memory producer"。✅
2. **LLM-safe arguments projection 与 normalized raw arguments digest 的双 digest 设计正确**: `normalized_arguments_digest` 绑定原始参数（不存储 preimage），`arguments_payload_digest` 校验安全投影。`payload_resolution.py` 移除两者相等检查是正确的。✅
3. **wait-resolution accepted evidence envelope 与普通 tool result 路径一致**: `_wait_resolution_evidence_envelope` 构造的 envelope 结构与 `engine_ingest.py` 中的普通路径一致，都使用 `AcceptedEvidenceEnvelope`。✅
4. **request/result 身份校验足够严谨**: `_resume_wait_request_event_matches_result` 校验 event_class、event_type、session_id、run_id、attempt_id、execution_id（允许 result execution 为空）。`_tool_result_query_text` 额外校验 tool_call_id、tool_name、normalized_arguments_digest。✅
5. **`_same_run_attempt_compatible_execution` 允许 result execution 为空**: 这是正确的，因为 wait-resolution `TOOL_RESULT_ACCEPTED` 由 Run transition 写在 suspended attempt 上，execution_id 可为空。✅
6. **Fins tool schema/prompt 清理移除了 Host 内部治理术语**: download/preprocess/upload 工具描述不再包含 "external-job wait state"、"observation handle"、"poll"、"next_step.action"、"轮询"。✅
7. **SEC pipeline 互斥分类修复**: `_summary_from_pipeline_result` 现在按 filing-level status 互斥计数 downloaded/skipped/rejected/failed，测试 `test_sec_download_adapter_summary_classifies_skipped_and_rejected_exclusively` 验证了 `discovered == downloaded + skipped + rejected + failed`。✅
8. **AGENTS.md "实现策略" 合规**: 本次变更修的是 shared boundary（request atom / envelope / resume path / tool schema），不是局部止血。root cause 是 wait-resolution 缺少 self-explaining evidence。✅
9. **无胶水 seam 或兼容分支**: `llm_safe_replay_arguments` 是从 `_llm_safe_replay_arguments` 重命名为 public，不是 wrapper。`payload_object` 和 `required_payload_text` 是新 helper，不是 compatibility facade。✅
