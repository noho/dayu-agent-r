### 2. Poll Claim / Backoff State Machine

Traced all state transitions across slices for a WAITING poll wait:

```
[NEW WAIT]
  ↓ open_host creates supervisor + factory
  ↓ _OpenHostWaitPollerFactory.create_wait_poller() → new SQLite connection in poller thread
  ↓ WaitPoller.poll_once() → claim_wait_record_for_poll()
  ↓ UPDATE SET poll_claim_id/owner/claimed_at/expires_at WHERE eligibility predicates
  ├─ [NOT FOUND] → break batch (no eligible waits)
  ├─ [CAS_LOST] → claim_conflicts++, continue
  └─ [UPDATED] → claim held

[ADAPTER CALL]  ← outside Host transaction
  ├─ [not-ready] → release_wait_record_poll_claim() → poll_next_observe_at=now+backoff
  ├─ [adapter error] → same release + ADAPTER_ERROR outcome
  ├─ [missing adapter] → same release + MISSING_ADAPTER outcome, no resolve_wait
  ├─ [ready/lost] → _CommandHandleWaitResolver.resolve_wait()
  │   → _resolve_wait(command_handle, ...)  ← same command path as public resolve_wait
  │   → admission → durable write → after-commit → _ThreadsafeSchedulerWakeupPort
  │   → call_soon_threadsafe → event loop → scheduler.wake_dispatch()
  │   → resolve_wait terminal mutation clears poll claim fields
  └─ [cancelled] → _abandon_cancelled_wait()
      → adapter.abandon_wait() → mark_wait_record_poll_abandoned() → poll_abandoned_at set

[CLOSE GATE CHECK]  ← 5 checkpoints in poll_once()
  ├─ gate.is_closed() before claim → return None (no new claims)
  ├─ gate.is_closed() before adapter → release_shutdown_skipped
  ├─ gate.is_closed() before abandon → release_shutdown_skipped
  ├─ gate.is_closed() after abandon → release_shutdown_skipped (skip durable mark)
  └─ gate.is_closed() before resolve → release_shutdown_skipped

[PER-ROUND CLEANUP]
  → _ClosingWaitPoller.poll_once() finally: command_handle.close() → durable_store.close()
```

**No cross-slice state machine inconsistencies found.** Every path terminates in a well-defined state (claim released or terminal cleared). Backoff state is durable and shared across poller instances per design.

### 3. Thread Safety Boundary

The single cross-thread bridge is `_ThreadsafeSchedulerWakeupPort._run_on_loop`:

```python
# Poller thread calls wake_dispatch(record)
# → _run_on_loop(lambda: scheduler.wake_dispatch(record))
# → loop.call_soon_threadsafe(run_callback)
# → Future.result()  ← blocks poller thread

# Event loop processes callback
# → run_callback() → scheduler.wake_dispatch(record)
# → future.set_result(None)  ← unblocks poller thread
```

**Verified safety:**
- `call_soon_threadsafe` is the only mechanism — no direct cross-thread scheduler access
- `Future.result()` deadlock analyzed: `asyncio.to_thread` (used in `close()`) does not block event loop → callback always schedules
- Event loop is alive during all poller operations (poller closes before event loop closes)
- `active_registry` not accessed from poller thread (only passed through to command handle; resolve_wait path doesn't touch it)
- Per-round SQLite connections are opened AND closed in the poller thread — no cross-thread connection reuse

**No deadlock, race, or thread-safety defect found.**

### 4. Lifecycle Ordering

**Open sequence** (`_OpenHostContextManager.__aenter__`):
```
1. durable_store = open_host_durable_store(...)
2. scheduler = HostDispatchScheduler(...)
3. recovery scan (leaves WAITING runs in place)
4. command_handle = HostCommandHandle(...)
5. wait_poller = _wait_poller_supervisor_from_open_host_options(...)
6. if wait_poller: wait_poller.open()  ← starts background daemon thread
7. _PublicHostHandle(..., wait_poller=wait_poller)
```

**Close sequence** (`_PublicHostHandle.close()`):
```
1. public gate (_raise_if_closed)
2. if wait_poller: await asyncio.to_thread(wait_poller.close)
3. await scheduler.close()
4. projection catch-up
5. command_handle.close()  → durable_store.close()
```

**Open failure cleanup** (`except Exception` after step 4):
```
1. if wait_poller: await asyncio.to_thread(wait_poller.close)
2. if scheduler: await scheduler.close()
3. projection catch-up
4. durable_store.close()
```

Both sequences follow poller → scheduler → projection → durable store. ✅

### 5. Resolve_wait Idempotency & Wakeup

`_CommandHandleWaitResolver.resolve_wait()` calls `_resolve_wait(command_handle, ...)`. This is the same internal function used by the public `resolve_wait` facade. **No separate resolve path exists for the poller.** The `_poll_idempotency_key` is stable (based on `{source: "poll", wait_id}`) and reused across retries. The test `test_resolve_failure_releases_with_backoff_and_reuses_idempotency_key` confirms the same key is used on retry.
