## Findings

### F1-未修复-高-missing_meta 被定义为 workspace 级 corruption，与合法"无 meta.json corpus"状态直接冲突

- **位置**: §5.5 step 2/4、§5.6 `CompanyTickerIdentityCorruptionKind`（`missing_meta`）、§7.4 step 6/8、§11.3 "Published invalid fail-closed" 测试
- **问题类型**: 契约缺失 / 状态机漏洞 / 范围漂移
- **当前写法**: 修订后 plan 把 `missing_meta`（corpus 目录存在但无 `meta.json`）定义为 typed corruption：read route "若实际 published corpus 缺失/损坏 CompanyMeta…抛 typed corruption"（§5.5 step 4）；commit 扫描 "任何实际 published corpus 的 missing/invalid meta、descriptor mismatch 均抛 typed corruption"（§7.4 step 8）；incoming canonical "target 存在但…meta.json…无效则立即抛 corruption"（§7.4 step 6）；§11.3 明确把 "missing meta" 列为任何 meta commit fail-closed 的触发条件。该规则源自 controller A6 的 required fix 措辞，plan 如实执行。
- **反例/失败场景（全部有直接代码证据）**:
  1. `FinsUploadMaterialRequest`（`ingestion_runtime.py:1074-1111`）不含 company meta decision，`validate`（`:4233-4236`）直接返回 normalized material request；material workflow（`sec_upload_material_workflow.py`）无任何 company_meta 写入。**material create 是生产可达的、合法的无 meta.json corpus 来源**。
  2. `read_filing_upload_state`（`_fs_filing_upload_state_core.py:83-86`）显式把 `meta.json` 缺失建模为合法 published state：`except FileNotFoundError: company_meta = None`，prevalidation 因此支持 "corpus 已存在、company meta 后到" 的合法流程。
  3. 既有 storage 测试 `test_fins_storage_atomicity.py:1009-1025` 通过公开 `begin_batch("MISSING")` + `commit_batch` 提交一个空 corpus，再断言 inventory 把 `missing_meta`/`invalid_meta` 报告为**诊断状态**而非错误——今天这些状态与正常读写共存。
  4. 今天的 read 路径对无 meta corpus 是优雅的：direct canonical probe（`_fs_company_meta_core.py:262-265` 只查 `ticker_dir.exists()`）可命中其 canonical；alias index 构建（`:345-349`）只过滤 `status == "available"`，无 meta corpus 只被静默排除。
- **失败后果（若按 plan 实现）**:
  - 工作区存在任一 material-only corpus 时，**所有** `list_documents`/alias read 全部失败为 `workspace_identity_corrupted`——单个无关 corpus 造成 workspace 级 read 停机；
  - 任一 meta commit 被无关的 meta-less corpus 阻断（§7.4 step 8）；
  - 给既有 meta-less corpus 补 company meta 的合法流程被 §7.4 step 6 阻断（target 存在 + meta.json 缺失 → corruption）——即 `FilingUploadPublishedState.company_meta=None` 明确支持的 "文档先行、meta 后到" 流程被永久拒绝，且错误文案 "工作区公司元数据损坏" 对用户不可行动（无物可修）。
- **为什么有问题**: plan 自身 §2.1 的唯一性原则建立在 durable facts 上（"一个 normalized lookup ticker 只能属于一个 canonical corpus"）。无 meta.json 的 corpus 没有持久化任何 alias 声明，不构成冲突来源；把"尚未声明任何事实"当作 corruption，与 durable-fact 原则自相矛盾。plan 未提供任何证据说明 meta.json 在 fresh-schema 工作区是强制存在的（material upload 反证），也未把 "让 material 流程写 meta" 列入 §9.1/§3——这是一个未声明前提上的设计决策。§11.3 还会把该错误语义固化进测试，违反"测试不得固化偶然行为"约束。
- **直接证据**:
  - `dayu/fins/storage/_fs_filing_upload_state_core.py:79-86`：`company_meta=None` 合法 published state；
  - `dayu/fins/ingestion_runtime.py:1074-1111/4233-4236`：material request 无 company meta 决策路径；
  - `tests/fins/test_fins_storage_atomicity.py:1009-1025`：公开提交空 MISSING corpus + inventory 诊断状态断言；
  - `dayu/fins/storage/_fs_company_meta_core.py:262-265/345-349`：今天 direct probe 与 available 过滤的语义；
  - plan §5.5 step 4、§5.6、§7.4 step 6/8、§11.3 "Published invalid fail-closed"。
- **影响**: 实施 Agent 按 plan 生成代码后，material-first 工作区全部 read 停机且无法通过正常流程修复；现有 storage 测试语义被倒逼改写为固化回归；review 不可验收。
- **建议改法和验证点**:
  1. 把 `missing_meta` 从 corruption kind 移除，重新定义为合法状态：无 meta.json 的 corpus 不贡献任何 lookup ticker（commit 扫描跳过不视为冲突，或仅对 incoming canonical 缺失时以 `current_published=None` 走 create 分支）；

  3. 决定 meta-less corpus 自身 canonical 的 read 语义：保留 descriptor 直查（保持今天 `list_documents("MISSING")` 可用）或在 §5.5 明确改为 NOT_FOUND 并同步 README——两者都必须显式写进 plan，不能留给实施 Agent；
  4. `invalid_meta`（JSON 不可解析/字段非法）与 `identity_mismatch`、`duplicate_owner` 维持 fail-closed 不变；
  5. 新增测试：material-only corpus 与健康 corpus 共存时 alias read 正常；对 meta-less corpus 补 meta 的 update 提交成功且 conflict 校验生效。
- **修复风险（低）**: 语义收窄是局部的（§5.5/§5.6/§7.4/§11.3 四处措辞 + 一个测试语义），不推翻锁序/merge/intent 架构。
