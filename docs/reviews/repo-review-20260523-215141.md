### 1-未修复-严重-_DurableRunCancellationToken 在 DB 不可用时静默返回"未取消"

- **入口/函数**: `_DurableRunCancellationToken.cancel_reason()` → `is_cancelled()`
- **文件(行号)**: dayu/host/dispatch.py:558-575
- **输入场景**: proactive compaction 执行期间，durable SQLite store 因锁争用超限（`HostTransactionRetryExhaustedError`）无法读取 Run 状态。
- **实际分支**: `except HostTransactionRetryExhaustedError: return None`，`is_cancelled()` 返回 `False`。
- **预期行为**: DB 不可用时，应视为"无法确认安全"，compaction 应被阻止（返回一个明确的 cancel reason 如 `"durable_unavailable"`）。
- **实际行为**: compactor 收到 `is_cancelled() == False`，继续对状态未知的 Run 执行压缩，可能将 stale facts 写入已被取消或已终态的 Run。
- **直接证据**: 行 574-575 `except HostTransactionRetryExhaustedError: return None`；行 556 `return self.cancel_reason() is not None` —— DB 失败与"Run 仍满足条件"不可区分。
- **影响**: 在 DB 故障时，compaction 可能对已取消/已终态 Run 继续写入压缩产物，导致外部可见不一致（压缩产物对应的 Run 已不存在或已终态）。
- **建议改法和验证点**: 将 `cancel_reason()` 返回值改为 `tuple[str | None, bool]`（原因 + DB 可用标志），或新增 `can_read_state()` 方法。compaction 路径在 DB 不可用时直接 abort。需要验证：模拟 DB 锁超限场景下 compaction 是否正确 abort。
- **修复风险（低）**: 改动仅影响 compaction cancel 判定路径，不影响正常执行路径。
- **严重程度（严重）**:

### 2-未修复-中-Compaction 重试循环迭代间未检查取消

- **入口/函数**: `run_compaction_operation()`
- **文件(行号)**: dayu/host/compaction_operation.py:103-198
- **输入场景**: 在第 N 次 compaction 尝试完成后、第 N+1 次尝试开始前，外部取消请求到达。
- **实际分支**: 循环直接进入第 N+1 次 `compactor.compact()`，无 `cancellation_token.is_cancelled()` 检查。
- **预期行为**: 每次迭代开始前应检查取消状态，已取消时立即中止。
- **实际行为**: 第 N+1 次 LLM 调用被发起，消耗 token 和时间，最终可能因 Run 状态已变更而 CAS 失败——浪费资源。
- **直接证据**: 循环体 (行 103-198) 中 `cancellation_token` 只传入 `compactor.compact()`，循环控制条件仅检查 `attempt < max_attempts`，无取消检查。
- **影响**: 浪费 LLM 调用预算，延迟取消响应。
- **建议改法和验证点**: 在每次 `for` 循环体开头增加 `if cancellation_token.is_cancelled(): break`。验证：在 compaction retry 间隔注入取消信号。
- **修复风险（低）**:

### 3-未修复-中-SSE _finalize_success 在 fatal tool call 路径上事件序列不完整

### 4-未修复-中-_safe_read_error_body_bytes 静默吞掉网络异常导致 context overflow 误分类

- **文件(行号)**: dayu/engine/runners/openai/runner.py:892-915 → dayu/engine/runners/openai/error_classifier.py
- **输入场景**: 读取 HTTP 错误响应 body 时发生网络异常（连接断开、读超时）。

- **预期行为**: context overflow（如 `context_length_exceeded`）本应被正确检测为可恢复错误。
- **实际行为**: 因 body 读取失败，结构化 JSON code 检测和 marker 匹配均不命中，context overflow 被降级为普通不可恢复错误。在 context_length_exceeded + 网络瞬间断开场景下，可恢复错误被误判为不可恢复。

### 5-未修复-中-ActiveWorkerRegistry 使用 threading.RLock 保护 asyncio 路径

### 6-未修复-中-HostTransactionRunner 所有读写共享单一 SQLite 连接

- **入口/函数**: `HostTransactionRunner` —— `run_write()` / `run_read()` / `_DurableRunCancellationToken.cancel_reason()`
- **文件(行号)**: dayu/host/durable/transaction.py:208-344, dispatch.py:564-575
- **输入场景**: `_DurableRunCancellationToken.cancel_reason()` 在 compaction 期间通过 `run_read` 查询 Run 状态，而此时主写入事务正在同一连接上执行。
- **实际分支**: WAL 模式下 `run_read` 可以并发，但同一个 sqlite3.Connection 上的 `run_write` BEGIN IMMEDIATE 期间，`run_read` 只能读取 write 事务开始前的快照。若 read 发生在 write commit 前且 write 需要 retry，read 读取的是旧状态。
- **预期行为**: stale read 可能导致 cancel_reason 返回过时信息。
- **直接证据**: transaction.py 中 `HostTransactionRunner` 持有单一 `sqlite3.Connection`（connection.py:198-201）；所有读写操作共享此连接。
- **影响**: cancel_reason 在 compaction write retry 期间可能读到旧 Run 状态，影响 cancel 判定时效性。
- **建议改法和验证点**: 为 cancel_reason 等只读快照查询分配独立只读连接；或接受 WAL 快照语义并在文档中明确说明。
- **修复风险（中）**: 引入多连接需要仔细管理连接生命周期。
- **严重程度（中）**:

### 7-未修复-低中-Token 估算器对 CJK 文本低估 2-3 倍
