## Findings

### 1-未修复-[高]-三态输入下 create/update+tombstone 强制格未收敛，共享纯函数无法同时“双保持”
- **位置**: 最小设计 §2 动作表与“filing 当前契约必须保留；tombstoned create 不在本项设新规则”；边界 §“tombstoned create 不写新验收预期…如果共享 evaluator 的改动无法隔离该分支，停止并请求该分支最小裁决”；owner 测试 §“tombstoned create 只做隔离回归”。
- **问题类型**: 状态机漏洞 / 契约缺失 / 不可直接实施
- **当前写法**: 动作表只列 `create+active`、`update+missing`、`delete+missing`、`delete+tombstone` 等已裁决格；`create+tombstone`、`update+tombstone` 两个被三态输入强制暴露的格子不给映射，以“停止条件”推迟到实施期。
- **反例/失败场景**: 现 evaluator 输入是 `previous_meta is not None`（`docling_upload_service.py:281-284`）。filing 侧 `validate_fins_upload_filing_request` 对 tombstone meta（`previous_meta` 非空）+ create + 无 overwrite 确定性返回 `CREATE_TARGET_EXISTS`（`ingestion_runtime.py:1506-1512`）；material 侧同输入今天不拒绝，落到 `_can_skip_upload`（tombstone 不 skip）→ `_upsert_source_document(is_create=True)` → `meta_path.exists()` 为真 → `FileExistsError` → `storage_io`（`_fs_source_document_core.py:1748-1749`）。若新 evaluator 把“exists”定义为含 tombstone → material create+tombstone 从 `storage_io` 变 typed conflict（改变了 plan 宣誓不改的现行路径，且等于偷偷新定义 tombstoned create 语义）；若“exists”只算 active → filing create+tombstone 变 ALLOWED（打破“filing 当前契约必须保留”）。一个纯函数若无 kind/策略输入，数学上无法同时满足两条保持约束。
- **为什么有问题**: 该格子的裁决是可从代码事实预先确定的（filing 确定、material 未裁决但现行结果可枚举），推迟到实施期会迫使 implementation agent 要么重新设计 evaluator 输入形状，要么在无意中替用户裁决 tombstoned create 语义——恰好是 goal 明文禁止的“臆造”。S2 的 writer 重检“复用同一 precondition”也会继承同一未定义格。
- **直接证据**: `docling_upload_service.py:259-285`（输入为 previous_meta 存在性）、`ingestion_runtime.py:1506-1512`（filing tombstone=create conflict）、`docling_upload_service.py:462/1643/1748-1751`（material 现行落 storage 异常）、plan §2/边界 § 原文。
- **影响**: 实施 Agent 跑偏 / 偷偷新定义 accepted 行为 / filing 回归 / S1、S2 各自返工
- **建议改法和验证点**:
  1. 把 evaluator 输入定为 closed 三态（missing/active/tombstone，由 `require_source_meta_is_deleted` 解析），显式给出全部强制格：`update+tombstone -> ALLOWED`（两 kind 现行一致，保持）；`create+tombstone` 在 plan 文本中明确“隔离”方案——filing 保持 `CREATE_TARGET_EXISTS`，material 保持现行 fallthrough（或现在就请求 tombstoned create 最小裁决，二选一，写死）。
  2. 隔离回归测试：filing create+tombstone 结果不变、material create+tombstone 行为字节级不变、update+tombstone 不变。
  3. 验证点：pure owner 测试矩阵补 `create/update × tombstone` 行，并注明各 kind 期望值来源（现行行为 vs 新裁决）。
- **修复风险（低/中/高）**: 低（改 plan 文本与测试矩阵即可，不改架构）
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-[高]-O12 依赖缺席，且 typed validated material request / MaterialUploadPublishedState 未给公司决策留契约槽位
- **位置**: 边界与前置依赖 §（只列 O16 与 O05/O07/O09/O10/O17，无 O12）；最小设计 §1（state 只含 “exact ticker/document ID、SourceIntegrityClassification、可信业务 meta”）；§3（typed validated material request 只保留“raw action、resolved action、exact target、初始状态及 meta”）。
- **问题类型**: 目标漂移风险 / 契约缺失 / 过度耦合
- **当前写法**: plan 把 O12 排除在依赖图外，并把 state/validated request 契约塑造成不含公司决策的形状。
- **反例/失败场景**: O12-F01（主工作区裁决）明确“Fins material 请求的状态感知前置校验应复用公司决策真源（`resolve_upload_company_meta_decision`），并将缺名映射为明确的 typed usage 原因”——它要插入的正是本 plan 新建的 admission owner。filing 对应物 `ValidatedFinsUploadFilingRequest` 携带 `company_meta_decision`（`ingestion_runtime.py:777`），`FilingUploadPublishedState` 捆绑 `company_meta`（`repository_protocols.py:400-413`），filing 顺序是先状态 precondition 后公司决策（`ingestion_runtime.py:1506-1525`）。material 若按 plan 现契约落地，O12 只能：(a) 给 validated request/state 加字段返工本项契约；或 (b) 在 admission 之外单独读公司 meta——把“同版读取”拆成两次，正是 §1 自己禁止的“两个独立读操作拼同版”。另外缺名 vs 目标缺失的错误优先级未定；O16 已要求“非法文件组合不被缺目标错误遮蔽”，O12 的组合错误同样需要优先级裁决。
- **为什么有问题**: 语义所有权约束要求同一事实唯一 owner、多消费者复用同一真源。company_meta_decision 的真源是公司 meta owner，但其“状态条件必填”判定必须与目标状态判定同批、同序；契约形状现在不定，后续 work unit 必然回改本项的 protocol/dataclass/validated request 三处。
- **直接证据**: 主工作区 `upload-material-um-o12-oracle-adjudication.md` “语义 owner/修复要求”；`ingestion_runtime.py:766-831`（filing validated request 含 `company_meta_decision`）、`1506-1525`（顺序）；`repository_protocols.py:400-448`；plan §1/§3 原文。
- **影响**: 后续返工 / 同版读取被破坏 / 错误优先级不定导致测试无法断言 / 跨 work unit 扯皮
- **建议改法和验证点**:
  1. 依赖图补 O12：明确 O12-F01 是本项 admission owner 的 follower，不实现 O12 规则，但为其预留契约槽位——`MaterialUploadPublishedState` 像 filing 一样捆绑 `company_meta`（同版一次读取），typed validated material request 预留 `company_meta_decision` 字段或明确“O12 落地时以何种形状进入”。
  2. 锁定错误优先级并加混合用例（如缺公司名 + missing target、无文件 + missing target），断言稳定的第一错误；与 filing 现序（files/static → state → company）保持一致或写明差异理由。
  3. 验证点：owner 测试断言“一次稳定 view 读取同时产出状态与公司事实”；错误优先级用例进入 Admission 测试组。
- **修复风险（低/中/高）**: 低-中（契约补字段 + 依赖注记，不动架构）
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-[中]-S2 单批/重检编排未指定唯一共享 owner，SEC/CN 双 workflow 复制状态机的风险
- **位置**: 最小设计 §4（“material workflow 先准备/转换…再开启一个 caller-owned batch…”）；切片 S2 允许改动列（`docling_upload_service.py`、`sec_upload_workflow.py`、`cn_pipeline.py`）；白名单说明（禁止新增生产文件，`filing_upload_publication.py` 不准入列）。
- **问题类型**: 过度耦合 / 最佳实践偏离
- **当前写法**: 编排以“material workflow”为主语描述，未说明单批+重检+rebase+冲突映射的状态机放在哪个共享 owner；白名单又禁止新建 material publication 模块。
- **反例/失败场景**: filing 的同构逻辑由唯一入口 `execute_prepared_filing_publication`（`filing_upload_publication.py:676+`）承载，SEC/CN 共用；而 material 的两市场 workflow 目前各自复制了两段 batch 流程（`sec_upload_workflow.py:523-568` 与 `cn_pipeline.py:1139-1181` 逐行同构）。若 S2 的“begin → fresh 重检 → company stage → publish → 单次 commit”按 workflow 各写一份，未来任何重检/冲突映射修复都要改两处并可能漂移，违反“重复逻辑必须抽取/同一 owner”。现有 `commit_prepared_upload_batch`（`docling_upload_service.py:1382`，docstring 自称“上传 publication 生命周期的唯一 owner”）已是两市场共享的 publication 入口，天然可承接该编排。
- **为什么有问题**: 这是 plan 内部“同一纯函数、同一 owner、不复制状态表”原则与 S2 落点描述之间的不一致；实施 agent 按字面会把状态机写进两个 workflow。
- **直接证据**: `filing_upload_publication.py:620-724`（filing 唯一 publication lifecycle + in-batch fresh 读取 + `_begin_publication_batch_or_raise`/`_read_fresh_state_or_raise`）；`docling_upload_service.py:1382-1438`；`sec_upload_workflow.py:523-568` vs `cn_pipeline.py:1139-1181`；plan §4 与 S2 白名单原文。
- **影响**: 实施 Agent 生成重复状态机 / 后续修复分叉 / review 不可验收
- **建议改法和验证点**:
  1. 明确 S2 编排的唯一 owner：在 `docling_upload_service.py` 扩展/邻接 `commit_prepared_upload_batch`（或新增共享 material publication 函数，仍在白名单文件内），SEC/CN workflow 只供给市场参数与事件映射；把 filing `execute_prepared_filing_publication` 的阶段划分（fresh 读取→裁决→rebase→同批 company staging→单次 commit、取消/回滚纪律）写为机制先例。
  2. 明确 rebase 语义落在该共享 owner：prepared mutation 不携带最终 staging meta，在 fresh 状态稳定后以 fresh meta 重建版本/`first_ingested_at` 等（对应 plan“以 fresh state 对应 meta 作为后续 reset/版本依据”），并定义变更键为 `SourceIntegrityClassification.revision`（plan 现文只写“可信 revision”，未指名字段）。
  3. 验证点：Publication 测试断言 SEC 与 CN 入口走同一共享函数（可通过对共享 owner 的 contract 测试实现，不逐市场复制夹具）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-[中]-writer 阶段 typed 原因的文案/归属未钉死，错误投影 owner 位置含糊
- **位置**: 最小设计 §5（“writer 阶段的状态漂移用已存在的 typed `SOURCE_PUBLICATION_CONFLICT` 或动作明确的 typed 原因”“`FinsUploadFailureError` 已携带 public reason 时须在通用 exception 分类前原样投影”“避免让 `upload_failure.py` 反向 import ingestion runtime 形成循环”）；§4 两段冲突/缺失投影的优先关系。
- **问题类型**: 契约缺失 / LLM-facing 文本 / 测试缺口
- **当前写法**: 用“或”把两种投影留给实施者；`FinsUploadFailureError` 直通只要求结果（不落入 `unexpected_runtime`），未指明归属函数。
- **反例/失败场景**:
  1. 现存 `SOURCE_PUBLICATION_CONFLICT`/`SOURCE_REVISION_STALE` 的 public 文案写死“目标 filing…”（`upload_failure.py:393、415`）。material 复用会向用户/工具投影“目标 filing 在上传准备期间已由另一请求发布”——材料上传被伪装成 filing 事实，违反 LLM-facing/用户可见语义约束；若新增 material 专属 code，又扩大枚举面，plan 未二选一。
  2. §4 第一句“presence、精确 deletion state 或可信 revision 变化 → typed publication conflict”与第二句“fresh active create → 原动作 typed 冲突”在 missing→active（presence 变化）上重叠；不写明“先以 fresh 态跑动作表，命中动作表投影原动作 typed；未命中但 revision 漂移才投影 publication conflict”的优先序，两处测试会各写各的。
  3. `fins_upload_failure_from_exception`（分类 owner，在 `upload_failure.py`）今日不识别 `FinsUploadFailureError`/`FinsUploadUsageError`，material workflow catch（`sec_upload_workflow.py:602-603`、`cn_pipeline.py:1219`）会把它们归入 `unexpected_runtime`；filing 靠 workflow 层 `except FinsUploadFailureError`（`sec_upload_workflow.py:311`）补救。plan 要求直通是正确的，但直通的 owner 应钉死为 `fins_upload_failure_from_exception` 顶部同模块直通（无需任何 import，无循环），usage→failure 映射才放 `ingestion_runtime.py`（其本就 import `upload_failure`，`ingestion_runtime.py:136`）。
- **为什么有问题**: 错误投影是本项核心验收面（O15 裁决点名误导性 `storage_io` 文案）；code/文案/priority/owner 四处不定，则 tool/CLI 断言无从写起。
- **直接证据**: `upload_failure.py:214-286`（分类顺序无两异常）、`377-418`（“目标 filing”文案）、`sec_upload_workflow.py:311/602-603`、`cn_pipeline.py:942/1219`；plan §4/§5 原文。
- **影响**: 测试无法断言 / 用户与工具收到误导文案 / 三市场投影分叉
- **建议改法和验证点**:
  1. 钉死映射表：动作表违反（fresh 态）→ `FinsUploadUsageCode` 三码（含新增 `DELETE_TARGET_MISSING`）→ `FinsUploadFailureKind.USAGE` + 三个新增 public code；纯 revision 漂移 → `SOURCE_REVISION_STALE`/`SOURCE_PUBLICATION_CONFLICT`；并写明动作表优先。
  2. 文案归属：要么把“目标 filing…”泛化为“目标文档…”，要么为 material 增加动作明确的 typed 原因（§5 的“或”收敛为一）；tool 断言业务可读文本。
  3. 直通 owner 写明 `fins_upload_failure_from_exception` 首分支返回 `error.failure`；SEC/CN/HK catch 统一改调该分类 owner（filing 既有 workflow 特例可保留或顺带收敛，不在本项强制）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 5-未修复-[中]-REPAIR_REQUIRED/UNSAFE 与 delete、重复 delete 的交叉格未钉死
- **位置**: 边界 §“`REPAIR_REQUIRED`/`UNSAFE`、无法证明 source meta 的情形按现有 integrity/operational typed 边界失败关闭；不能判作目标缺失”；§1 “`COMPLETE`/`REPAIR_REQUIRED` 必须有 meta”；owner 测试 §（只测健康 active/tombstone）；矩阵（无降级完整性行）。
- **问题类型**: 状态机漏洞 / 测试缺口
- **当前写法**: 失败关闭规则与“tombstone 重复 delete 仍成功”并列陈述，但对“REPAIR_REQUIRED 且 `is_deleted=true` 的 tombstone + 重复 delete”“UNSAFE + delete”没有单元格归属。
- **反例/失败场景**: 目标是损坏/不完整的 tombstone（内容树缺文件 → REPAIR_REQUIRED，但 meta 可信 `is_deleted=true`）：按“失败关闭”应 typed operational/integrity 失败；按“重复 delete 仍成功且不误判”应允许（删除一个已删除目标，内容完整性与删除无关）。两者直接冲突。UNSAFE + delete 则因 meta 不可信确实无法证明 tombstone，失败关闭合理——但必须明确它不投影为 `DELETE_TARGET_MISSING`。若不钉死，实施 agent 大概率按“REPAIR_REQUIRED 一律失败关闭”写死，导致合法删除/重复删除被阻断，且与 O13 后续的 tombstone 幂等修复打架。
- **为什么有问题**: O15 裁决把“tombstone 不等同 never-existed”列为 accepted 行为；失败关闭条款的适用面（全部动作 vs 仅内容动作）不界定，会侵蚀该 accepted 行为。
- **直接证据**: plan 边界 §与 §1 原文；goal §2 “已删除 tombstone 的重复 delete 仍成功且不被误判 never-existed”；`_fs_source_integrity.py:1647-1702`（MISSING/UNSAFE 无 meta 的构造）、`repository_protocols.py:431-439`（REPAIR_REQUIRED 必须有 meta）。
- **影响**: 合法删除被拒 / 与 O13 责任边界冲突 / 测试留下盲格
- **建议改法和验证点**:
  1. 给出降级完整性 × 动作矩阵：建议 delete（含重复 delete）只要求可信 meta 的 deletion 状态可判（REPAIR_REQUIRED tombstone → ALLOWED；REPAIR_REQUIRED active → 允许删除还是失败关闭，二选一写死）；UNSAFE 一律 typed integrity/operational 失败关闭，禁止投影 missing；create/update 遇 REPAIR_REQUIRED 维持失败关闭、不擅自授权 repair。
  2. owner 测试补两行：REPAIR_REQUIRED-tombstone 重复 delete、UNSAFE + delete/update 的投影断言。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open questions
