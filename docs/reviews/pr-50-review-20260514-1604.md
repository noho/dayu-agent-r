## Findings

### 01-未修复-高-promotion 异常掩盖已成功的主操作（closeout / cancel）

- **入口/函数**: `HostAdmissionService.closeout_attempt_terminal` 和 `HostAdmissionService.cancel_run`
- **文件(行号)**: `admission.py(493-510)`, `admission.py(454-478)`
- **输入场景**: closeout 或 cancel 的主事务已成功提交，随后 `_promote_after_release` 在新事务中因 durable 错误抛异常
- **实际分支**: 主操作事务已提交 -> `_promote_after_release` 抛异常 -> 异常传播到调用方
- **预期行为**: 主操作成功后，promotion 作为 side effect 的失败不应掩盖主操作结果。调用方应收到主操作成功的结果，promotion 失败应通过独立路径处理
- **实际行为**: 调用方收到异常，误以为 closeout/cancel 失败。重试 closeout 时 Run 已是终态，`_invalid_terminal_precondition` 返回 `INVALID_STATE` 抛出 `HostApiError`
- **直接证据**: `admission.py:501` `_promote_after_release` 在 `run_write` 事务外调用，异常直接传播；`run_transition.py:1469-1474` `_invalid_terminal_precondition` 检查 `run.status != RunStatus.RUNNING`，重试时已终态
- **影响**: 调用方收到与事实不符的错误。Engine dispatch 路径中可能导致误判。重试 closeout 会收到 `INVALID_STATE`
- **建议改法和验证点**: 在 `_promote_after_release` 中 catch 异常并返回 `PromotionResult(skipped=True)` 而非传播；或在 `closeout_attempt_terminal` / `cancel_run` 中将 promotion 包裹在 try/except 中，记录 warning 但返回主操作成功结果
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 02-未修复-高-cancel 幂等重放不重试 promotion -- queued Run 可能饿死

- **入口/函数**: `HostAdmissionService.cancel_run` 幂等重放路径
- **文件(行号)**: `admission.py(454-478)`, `admission.py(1482-1513)`
- **输入场景**: cancel 取消 pre-dispatch STARTING Run（`released_active_slot=True`）。第一次调用成功写入幂等记录后 `_promote_after_release` 抛异常
- **实际分支**: cancel 事务已提交 -> 幂等记录已写入 -> `_promote_after_release` 抛异常 -> 重试时幂等重放返回 `released_active_slot=False, promotion=None`
- **预期行为**: promotion 失败后应有重试或补偿机制，确保已释放的 active slot 能被队列中下一个 Run 获取
- **实际行为**: `_idempotent_cancel_result` 固定返回 `released_active_slot=False`，不再触发 promotion。队列中下一个 Run 永远不会被推进
- **直接证据**: `admission.py:1512` 幂等重放固定 `released_active_slot=False`；`admission.py:1509` `promotion=None`
- **影响**: 队列中的 Run 可能永久饿死，除非有外部 queue scanner 补偿。Phase 3 的 `NoopAdmissionWakeupPort` 不提供此能力
- **建议改法和验证点**: 与 Finding 01 合并解决——如果 promotion 失败被 catch 并记录，幂等重放时也应触发 promotion（检查 Run 是否仍为终态且 Session 有 queued Run）
- **修复风险（低/中/高）**: 低（与 01 共用修复方案）
- **严重程度（低/中/高/严重）**: 高

### 03-未修复-中-cancel CAS 语义不一致：cancel_running_run_row 返回 CAS_LOST，cancel_queued_run_row / cancel_starting_attempt_row 返回 INVALID_STATE

- **入口/函数**: `cancel_running_run_row`, `cancel_queued_run_row`, `cancel_starting_attempt_row`
- **文件(行号)**: `state.py(1462-1468)`, `state.py(1400-1406)`, `state.py(1654-1660)`
- **输入场景**: 并发取消同一 Run/Attempt，rowcount=0 且 row 仍处于期望源状态
- **实际分支**: `cancel_running_run_row` 使用 `cas_lost_when_expected=True`（行 1467）返回 `CAS_LOST`；`cancel_queued_run_row` 使用 `cas_lost_when_expected=False`（行 1405）返回 `INVALID_STATE`；`cancel_starting_attempt_row` 使用 `cas_lost_when_expected=False`（行 1659）返回 `INVALID_STATE`
- **预期行为**: 三个 cancel 函数应有统一的 CAS 语义
- **实际行为**: 同一语义场景（并发竞争、row 仍处于期望源状态但更新失败）返回不同状态码
- **直接证据**: `state.py:1467` `cas_lost_when_expected=True` vs `state.py:1405` `cas_lost_when_expected=False` vs `state.py:1659` `cas_lost_when_expected=False`
- **影响**: 调用方无法用统一错误处理逻辑处理三种 cancel 的竞争失败。admission 层 `_raise_for_cancel_transition_status` 只区分 UPDATED/NOT_FOUND/其它，当前不会崩溃，但语义不精确
- **建议改法和验证点**: 统一三者的 `cas_lost_when_expected` 参数为 `True`，使并发竞争返回 `CAS_LOST` 而非 `INVALID_STATE`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 04-未修复-中-REJECT policy 不写幂等记录，重试行为不确定

- **入口/函数**: `_StartRunOperation._handle_active_run`
- **文件(行号)**: `admission.py(639-644)`
- **输入场景**: start_run 使用 REJECT policy，存在 active Run。第一次抛出 CONFLICT。active Run 结束后以相同 client_request_id 重试
- **实际分支**: `HostApiError` 不是 `HostDurableError`，落入 `run_write` 的 `except Exception` 分支，事务回滚，幂等记录未写入
- **预期行为**: 同一 client_request_id 应产生一致结果。若首次被 REJECT，重试应返回同一 REJECT 或调用方明确知道 REJECT 不做幂等保护
- **实际行为**: 重试时幂等检查返回 None，发现无 active Run，创建新 Run
- **直接证据**: `admission.py:640` raise HostApiError(CONFLICT)；`transaction.py:241-243` except Exception -> rollback -> raise；`admission.py:594-597` 幂等检查在 REJECT 之前但 REJECT 不写记录
- **影响**: 调用方使用 client_request_id 做幂等保证时，REJECT 的重试语义不明确，可能意外创建重复 Run
- **建议改法和验证点**: 在 REJECT 之前写幂等记录（result_kind=reject），或在文档中明确 REJECT 不受幂等保护
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 05-未修复-中-ATTACH_ACTIVE 幂等重放返回可能已完成的 Run

- **入口/函数**: `_idempotent_run_result`
- **文件(行号)**: `admission.py(646-666)`, `admission.py(1461-1479)`
- **输入场景**: start_run 使用 ATTACH_ACTIVE policy，返回 active Run 并写入幂等记录。该 Run 随后完成。以相同 client_request_id 重试
- **实际分支**: 幂等重放读取 `record.result_ref` 指向的 Run，该 Run 已是终态
- **预期行为**: `attached_active=True` 语义上暗示"附加到了 active Run"，但实际返回的是已完成的 Run
- **实际行为**: 返回 `RunAdmissionResult(run=terminal_run, attached_active=True, ...)`
- **直接证据**: `admission.py:651` `result_ref=active.run_id`；`admission.py:1461` `read_run_by_id` 读取该 Run（可能已终态）；`admission.py:1477` `attached_active=record.created_event_id is None`（ATTACH_ACTIVE 固定为 None）
- **影响**: 调用方收到语义矛盾的结果。若基于 `attached_active=True` 假设 Run 仍在执行，会得出错误结论
- **建议改法和验证点**: 幂等重放时检查 Run 是否仍为 active 状态，若已终态则 `attached_active=False`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 06-未修复-中-Attempt DDL 定义了 Python 层不可达的终态 suspended / steered，且 cancelled 终态被 terminal_attempt_row 排除

- **入口/函数**: schema DDL + `terminal_attempt_row`
- **文件(行号)**: `schema.py(301-338)`, `state.py(1565-1570)`
- **输入场景**: 任何调用方试图将 Attempt 转入 suspended/steered 状态，或将 RUNNING Attempt 转为 cancelled
- **实际分支**: DDL CHECK 允许 suspended/steered/cancelled 作为终态（要求 terminal refs 非 NULL），但 `terminal_attempt_row` 只接受 SUCCEEDED/FAILED/LOST，`cancel_starting_attempt_row` 只接受 STARTING->CANCELLED
- **预期行为**: DDL 和应用层状态机应一致
- **实际行为**: RUNNING Attempt 无法被取消；suspended/steered 在 DDL 中存在但 Python 层永远写不到
- **直接证据**: `schema.py:303` `'suspended', 'steered'` 出现在 status IN 列表中；`state.py:1565-1570` CANCELLED 不在允许列表中
- **影响**: DDL 承载了当前无法验证的语义承诺。Phase 3 不支持 running->cancelled 但 DDL 不拦截
- **建议改法和验证点**: 从 DDL 中移除 Phase 3 不使用的状态值，或在 Python 层添加 NotImplementedError 占位
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 07-未修复-中-closeout_attempt_terminal 无幂等保护，与 start_run / cancel_run 的幂等模式不一致

- **入口/函数**: `HostAdmissionService.closeout_attempt_terminal`
- **文件(行号)**: `admission.py(480-510)`
- **输入场景**: Engine 调用 closeout，因网络超时未收到响应，重试同一 closeout
- **实际分支**: 第一次 closeout 成功提交。重试时 `_invalid_terminal_precondition` 检测到 Run 已终态，返回 INVALID_STATE 抛出 HostApiError
- **预期行为**: 作为内部操作，closeout 应支持幂等重放——对已完成的 closeout 应返回成功结果而非错误
- **实际行为**: 重试收到 INVALID_STATE 错误
- **直接证据**: `admission.py:480-510` 方法体内无幂等检查逻辑；`run_transition.py:1469-1474` Run 已终态返回 INVALID_STATE
- **影响**: Engine 对 closeout 的重试会收到错误，需要 Engine 层特殊处理。与 start_run/cancel_run 的幂等模式不一致
- **建议改法和验证点**: 添加幂等检查，或在 Run 已终态时返回成功结果
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Residual Risk

- `cancel_running_run_row` 不清除 `current_attempt_id`，终态 Run 保留对已取消 Attempt 的引用。语义不明确但不影响正确性。
- `_run_mutation_result` 的 `cas_lost_when_expected=False` 路径将"仍处于期望源状态但更新失败"归为 `INVALID_STATE` 而非 `CAS_LOST`，语义不够精确。
- DDL CHECK 约束缺少对 `running` 状态 `current_attempt_id IS NOT NULL` 的约束，以及 `waiting/cancelling/recovering` 状态的必填字段约束。
- `promote_queued_run_row` 不验证 `started_event_sequence > accepted_event_sequence` 的单调性（依赖 EventLog AUTOINCREMENT 保护）。
- 终态集在 DDL、`_validate_run_for_insert`、`_is_terminal_run_status` 三处独立定义，维护风险。
