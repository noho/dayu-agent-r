## Findings

### DS-PR-001-未修复-高-CONTINUATION stage 尚未进入 production enum

- **位置**: §5.5 5-stage/15-cell action table; §8.2 Slice 1 exact changes #3
- **问题类型**: 状态机漏洞
- **当前写法**: Plan §5.5 定义 `ContextSizingStage.CONTINUATION = "continuation"` 并要求 `_pressure_and_decision` 处理 15-cell
- **反例/失败场景**:
  1. 当前 production `ContextSizingStage` enum (`context_budget.py:83-89`) 只有 4 个值：`ORDINARY`, `POST_COMPACT`, `REACTIVE_POST_COMPACT`, `DISPATCH_FALLBACK`
  2. 当前 `_pressure_and_decision` (L815-852) 的 hard branch 只对 `REACTIVE_POST_COMPACT` 特殊返回 ALLOW（L834-837），soft branch 只对 `ORDINARY` 特殊返回 COMPACT（L844-846）。`POST_COMPACT` 和 `DISPATCH_FALLBACK` 都走 generic 分支。没有 CONTINUATION 的 case
  3. 添加 CONTINUATION 后，若不改 `_pressure_and_decision`，hard 会落入 generic `BLOCK_HARD_THRESHOLD`（L836 else 分支），soft 会落入 generic `ALLOW_DISPATCH`（L846 else 分支）。这恰好与 plan 要求一致（hard→ALLOW, soft→ALLOW），但**不是显式 total function**，而是靠 fall-through luck
  4. Plan §5.5 的 `action(stage, pressure)` table 固定 15-cell，但未明确要求实现用 exhaustive `match`/`if-elif-else` 还是可以依赖 default branch
- **为什么有问题**: 靠 default branch 巧合满足 CONTINUATION 语义会在未来 stage 变更时静默错误。`_pressure_and_decision` 目前在 `REACTIVE_POST_COMPACT` 和 `ORDINARY` 上有显式特殊 case，但 `POST_COMPACT`/`DISPATCH_FALLBACK`/未来 `CONTINUATION` 都依赖 default。这是**非穷举状态机**——Plan 要求 15-cell total function，但现有代码结构和 plan 均未约束实现必须 exhaustive match
- **直接证据**:
  - `context_budget.py:83-89` — enum 缺 CONTINUATION
  - `context_budget.py:815-852` — `_pressure_and_decision` 非穷举，hard/soft 两个 branch 各只有 1 个显式 stage check
  - Plan §5.5 L1162-1189 — 15-cell action table 定义清晰但未加 exhaustive-match 实现约束
  - Design §25 L3626-3632 — 已明确五阶段 behavior
- **影响**: implementation agent 可能用 default branch 实现 CONTINUATION（巧合正确），但后续 stage 增删时产生静默错误 action；测试可能只覆盖 15-cell 的 expected outputs 而漏掉 default-branch 反例
- **建议改法和验证点**:
  1. 在 §8.2 exact change #3 或 §5.5 增加显式约束：`_pressure_and_decision` 必须对 5 个 stage 做 exhaustive match（Python 3.11 用 `if-elif-else` + `assert_never` 或显式 raise on unknown stage）
  2. owner test 增加 "unknown stage" 反例：传入不在 enum 内的 stage value 必须 fail closed
  3. 15-cell test matrix 必须包括 CONTINUATION normal/soft/hard 全部 3 个 cell
- **修复风险**: 低（实现时加 `assert_never` 或 exhaustive check）
- **严重程度**: 高（当前 plan 已描述目标 behavior 但缺少实现级别的穷举约束，implementation agent 可能交付语义正确但结构脆弱的状态机）

**原 blocker disposition**: 对应 Controller stop §4.3 "Sizing stage/action completeness"。Plan 已定义 CONTINUATION 语义和目标 action table，但缺少实现 exhaustive-match 约束。本 finding 属于 implementation-level guard，不要求 plan 重新设计。

### DS-PR-003-未修复-中-queue promotion 删除的时序与测试影响未详述

- **位置**: §5.3.1 pending producer 表 "queued promotion" row；§8.2 exact change #19

  - 还是完全删除 promotion pending 创建，让 `promote_queued_run_in_transaction` 不再被调用
  - 已存在的 `promote_queued_run_in_transaction` durable transition 是否需要修改

- **直接证据**:

  - `admission.py:1476-1537` — `_PromoteNextQueuedRunOperation` 调用 `promote_queued_run_in_transaction` 创建 RUN_STARTED/ATTEMPT_STARTED/pending
  - `dispatch.py:5624-5640` — `_read_startable_run` 已支持 QUEUED Run 选择

  - Plan §7.1: "`run_transition.py` 零 diff" — 但若 `promote_queued_run_in_transaction` 不再被调用，这本身不是 diff 但 transition 函数变成 dead code
- **影响**: implementation agent 需要在 `promote_queued_run_in_transaction`（保留/修改/删除）、test migration、poll timing 三个维度自行判断；可能错误保留 dead code 或删除仍被 test 引用的 transition

  1. 明确 `promote_next_queued_run` 的新行为：是否只将 QUEUED→ACCEPTED（不创建 Attempt），或完全废弃该 public method

  4. 若 `promote_queued_run_in_transition` 成为 dead code，在 plan 中明确是保留（零 diff 承诺）还是允许移除

### DS-PR-005-未修复-低-manifest recorder 改为 direct identity 后丢失 type-safety

- **位置**: §5.3.1 recorder signature L692-706
- **问题类型**: 契约缺失
- **当前写法**: `record_prepared_runner_call_candidate_in_transaction(..., *, run, attempt_id, execution_id, occurred_at, candidate, sizing_snapshot)`
- **反例/失败场景**: 当前 recorder (`run_input.py:985-994`) 接受 `start_input: RunnerCallStartInput`，内部使用 `start_input.attempt_id` 和 `start_input.execution_id`。改为 direct `attempt_id: str, execution_id: str` 后：
  1. 调用方不再被类型系统约束"必须提供与 start transition 相同的 identity"
  2. 若某个 producer 传了与后续 start transition 不同的 `attempt_id`，类型检查器无法发现
  3. 当前 union 类型虽然耦合但提供了编译期保证：manifest 和 transition 消费的是同一个 typed object
- **为什么有问题**: Plan 的 design rationale（"移除对 start input union 的偶然依赖"）是正确的——recorder 不应知道 start input 的完整 shape。但改为 bare `str` 参数后，正确性完全依赖调用方的 discipline 和测试覆盖，失去了类型系统的 guard。这不是 blocker，但需要在 plan 中承认这是 type-safety 的 tradeoff
- **直接证据**:
  - `run_input.py:195` — `RunnerCallStartInput = StartGovernedRunInput | StartRecoveryRunInput`
  - `run_input.py:991` — recorder 当前接受 `start_input: RunnerCallStartInput`
  - Plan L692-706 — 新签名只有 bare str identity
- **影响**: 类型安全性从编译期 guarantee 降级为 runtime validation。plan 未讨论这个 tradeoff
- **建议改法和验证点**:
  1. 可选：定义一个轻量 `RunnerCallIdentity(attempt_id, execution_id)` value object 而不是 bare str
  2. 至少：在 recorder docstring 中明确"caller must ensure these identities match the subsequent start transition"
  3. test 覆盖 identity mismatch 场景
- **修复风险**: 低
- **严重程度**: 低

**原 blocker disposition**: 对应 Controller stop §4.4 recorder union coupling。Plan 已正确识别问题并给出方向，本 finding 只是 tradeoff 未声明。

### DS-PR-006-未修复-低-project_wait_resume_continuity 的 tool_result_payload 类型过于宽泛

- **位置**: §5.3.1 wait continuity helper L768-778
- **问题类型**: 契约缺失
- **当前写法**:
  ```python
  def project_wait_resume_continuity(
      *, user_prompt, tool_call_id, tool_name,
      request_arguments: Mapping[str, JsonValue],
      tool_result_payload: Mapping[str, JsonValue],
      source_refs: tuple[str, ...],
  ) -> SessionContinuityView
  ```
- **反例/失败场景**: `tool_result_payload: Mapping[str, JsonValue]` 接受任意 JSON 结构。实际的 tool result payload 有明确的 typed shape（工具返回的 content/status 等）。`JsonValue` 类型下，`project_wait_resume_continuity` 需要自行解析和验证 payload 内部结构才能投影出正确的 `tool(result)` message。若 payload 结构非法，函数应 fail closed 但不能在 continuation 构造阶段静默产生错误消息。
- **为什么有问题**: 函数签名接受 `Mapping[str, JsonValue]` 但没有定义该 mapping 中哪些 key 是必需的、哪些是可选的、以及如何投影到 AgentMessage。plan 只说 "project_wait_resume_continuity 唯一拥有 accepted arguments 与 completed/failed/cancelled tool-message 内容投影"，但没有指定投影规则（例如：result content 字段名、是否包含 tool_call_id 在投影消息中等）
- **直接证据**:
  - Plan L768-778 — helper signature
  - Plan §5.3.1 L782-785 — "它唯一拥有accepted arguments与completed/failed/cancelled tool-message内容投影" 但没有具体投影规则
  - 当前 waiting.py `_tool_result_resolution_payload` (L1860) 和 `tool_result_wait_resolution_payload` 已定义了 tool result payload 的生产规则
- **影响**: implementation agent 需要自行决定 tool result 到 AgentMessage 的投影规则。若投影规则与 waiting.py 现有 `_tool_result_resolution_payload` 不一致，可能导致 pre-start candidate 和 post-start reader 产生不同的消息内容
- **建议改法和验证点**:
  1. 在 §5.3.1 或 §8.2 中补充 tool_result_payload → AgentMessage(tool) 的投影规则（至少：role="tool"、content 字段来源、tool_call_id 字段来源）
  2. 明确与 `_tool_result_resolution_payload` 的关系（复用还是独立）
  3. owner test 验证 projected message 的 role/content/tool_call_id
- **修复风险**: 低
- **严重程度**: 低

**原 blocker disposition**: 对应 Controller stop §4.2 "wait resume增加LLM-facing continuity"。Plan 已定义函数签名和所有权，但投影规则不够具体。本 finding 属于 plan 内部实现细节缺失。

### DS-PR-007-未修复-低-steer 事务中 USER_INPUT_ACCEPTED 回滚与幂等的交互未详述

- **位置**: §5.3.1 steering 行 "running steer" + failure matrix "steer effective execution/tool facts非法或candidate/manifest失败"
- **问题类型**: 并发恢复风险
- **当前写法**: "整个 admission transaction rollback；新input/steer/旧Attempt close/wait cancellation均不残留"
- **反例/失败场景**:
  1. steer 在一个 transaction 内做：append 新的 `USER_INPUT_ACCEPTED` → 关闭旧 Attempt → freeze candidate → write manifest → create start facts → pending row
  2. 若 candidate/manifest 失败，整笔 rollback。但 admission service 在 transaction 外有 idempotency guard：用户以相同的 `semantic_digest` 重试 steer 时，idempotency store 不认为这是 replay（因为第一次没 commit）
  3. 这是预期行为（retry 创建新 transaction），但 plan 未说明 admission idempotency 与新 candidate/manifest 阶段的交互。当前 `_create_steer_attempt_result` (L3035) 在 transaction 内记录 idempotency result (L3153-3162)，但这是在 transaction 末尾。如果 candidate/manifest 失败发生在 idempotency record 之前，retry 会重新执行整个流程。
  4. 边界 case: `USER_INPUT_ACCEPTED` 已 append 但 manifest 写入失败 → rollback。用户重试相同 input → 第二次 append 相同的 `USER_INPUT_ACCEPTED`。EventLog 去重通过 deterministic event id（基于 input digest），所以第二次 append 应返回已有 row 或去重。Plan 未确认 `USER_INPUT_ACCEPTED` 的 event id 是否可以 deterministic replay。
- **为什么有问题**: 当前 `USER_INPUT_ACCEPTED` event id 可能包含 random/nonce 成分，rollback 后 retry 会产生不同的 event id。这本身不影响 correctness（两个 event 只有一个 commit），但在 design 层面，plan 应确认 steer 路径中的 event id 生成策略
- **直接证据**:
  - `admission.py:3035-3164` — `_create_steer_attempt_result` 当前不写 candidate/manifest
  - Plan §5.3.1 failure matrix "steer effective execution/tool facts非法或candidate/manifest失败" — "整个admission transaction rollback"
  - Plan 未讨论 steer event id determinism
- **影响**: 在正确的实现下影响极低（rollback + retry = 正常重试）。但如果 implementation agent 为 `USER_INPUT_ACCEPTED` 使用了 random event id，可能在 retry 时产生不同的 durable event
- **建议改法和验证点**:
  1. 确认 steer `USER_INPUT_ACCEPTED` event id 在相同 input 下 deterministic
  2. 或确认 idempotency store 在 transaction 最早期（candidate/manifest 之前）记录，使得 retry 直接返回已有结果
- **修复风险**: 低
- **严重程度**: 低

**原 blocker disposition**: 属于 plan 的 retry/replay 细节。现有 admission idempotency 机制已提供基础保护，本 finding 不影响 plan approval。

### DS-PR-009-未修复-中-两个独立修改中 compact source boundary + memory 修改属于第三个隐式修改

- **位置**: §1.1 "两项修改只共享 Host-owned exact candidate sizing result" + Slice 1 compact/memory 修改
- **问题类型**: 范围漂移
- **当前写法**: Plan §1.1 声明两个独立产品修改：(1) usage-anchored sizing, (2) durable fact + public projection。然后说 "Slice 1 对 compact source boundary 与 Conversation Memory projection 的修正不是第三项产品修改；它是 complete candidate foundation 满足既有 compact/delta design truth 的前置 owner 修复"
- **反例/失败场景**:
  1. Compact source boundary parser (`compact_payload.py`) 和 Conversation Memory projection (`memory.py`) 的修改会影响所有现有 compact event 的语义解释，**独立于** usage-anchored sizing
  2. 这些修改使 post-compact conservative size 可能下降（因为 covered raw 被移除），这会影响所有 sizing decision 的输入，不限于 anchor 算法
  3. 即使 Slice 3 的 anchor 算法从未实现，compact/memory 修改也会改变 ordinary conservative sizing 的结果
  4. 因此 compact/memory 修改在语义上是独立的产品变更，plan 将其归类为 "前置 owner 修复" 是合理的工程判断（不修会导致 post-compact candidate 携带 covered raw，造成 sizing 不准确），但从"两个独立产品修改"的对外承诺来看，实际上是三个
- **为什么有问题**: Plan 声明 "两项修改只共享..." 但实际交付三个语义独立的变更。这不是 correctness 问题，但在 Controller 或 PM 视角下，compact/memory 修改是用户可见的行为变化（post-compact sizing 值可能改变）。Plan 应诚实声明或解释为何不需要单独计数
- **直接证据**:
  - Plan §1.1 L82-87 — 声明 "不是第三项产品修改"
  - Plan §5.8 — 详细定义了 compact source boundary 和 memory projection contract
  - Plan §8.2 exact changes #1, #2 — compact/memory 是 Slice 1 的前两个 exact changes
  - `compact_payload.py` 和 `memory.py` 的修改已在 partial implementation 中（blocked evidence §3）
- **影响**: 对外沟通层面。不影响实现正确性
- **建议改法和验证点**:
  1. 将声明改为 "两项主要产品修改 + 一项必要的 owner 修复" 或直接承认三项修改
  2. 或在 §3.2 non-goals 中明确 compact/memory 修改的边界：它们只修复既有 design truth 的实现偏差，不引入新语义
- **修复风险**: 低
- **严重程度**: 中（对外承诺准确性，不影响技术正确性）

## Plan Review Conclusion

**结论: `pass-with-risks`**

### 通过理由

1. **Pending producer 双向全集**已穷举：initial/queued ordinary、proactive post-compact/fallback、reactive accepted compact、startup recovery、running/waiting steer、wait resume、Engine continuation——每个 producer 都有 exact source、frozen policy/tools/mode、sizing stage、manifest/start transaction ordering、replay/CAS/rollback 和 owner tests。Production grep audit 确认了全部真实 producer。

2. **CONTINUATION 第五 stage 的第一性原理裁决**成立：四类 active-run path 确实无法执行 ORDINARY 的 soft compact/hard block（无 unstarted Run owner、无 proactive operation target）。Plan 的 5-stage/15-cell total function 与 design §25 一致。

3. **Unused direct promotion 删除**安全：scheduler `_read_startable_run` 已支持 QUEUED Run 选择；`create_running_run_with_starting_attempt_in_transaction` 确无 production caller；删除路径后无 manifest-before-start 的 gap 被消除。

4. **Steer/wait 在现有 transaction 内构建 exact candidate**可行：两个 producer 的 transaction 已包含 event creation 和 row mutation；添加 candidate freeze + manifest writing 不超出 transaction scope。

5. **Manifest recorder 改为 direct identity**降低耦合：移除对 `StartGovernedRunInput | StartRecoveryRunInput` union 的依赖，所有 producer 可以统一使用 bare identity 参数。

6. **`dispatch_record_id` 无需进入 manifest**：manifest hot fields 和 strict loader 均只用 `attempt_id/execution_id`；pending row 通过相同 identity 匹配。Worker 不需要 `dispatch_record_id`。

7. **HostAdmissionService/Waiting/Recovery/OpenHost wiring**最小：plan 只添加 direct fields（`PayloadStore`、context policy、memory policy 等），不新增 bag/ callback/ service locator。`command.py` 用模块级 helper 从 admission service 逐项装配。

8. **Failure/replay/CAS tests**覆盖完整：包括 startup source missing/mismatch、steer rollback、wait idempotency、reactive catch-up failure、precondition miss、CAS lost、winner/no-winner recovery competition。

9. **3 slices 切分**合理：按依赖（candidate foundation → durable fact → anchor algorithm）、回滚风险和验证矩阵独立切分。Slice 2 的 fact 即使只有 conservative_fallback 也完整成立。

10. **两个独立修改**的目标 clear：usage-anchored adaptive sizing 和 durable context-budget fact/public projection。

2. **DS-PR-002 (中)**：`SessionContinuityView.source_refs` 字段变更未列出全部 construction site 审计。

3. **DS-PR-003 (中)**：queue promotion 删除的 transition 路径和 test migration 粒度不足。

4. **DS-PR-004 (中)**：test allowlist 有 5 个重复文件。

5. **Q1-Q3**：3 个 open questions 不影响 plan approval 但应在 implementation 前澄清。
