### 001-未修复-中-_close_partial_file_descriptor 在 native 操作失败后 cleanup 也失败时丢弃原始错误信息

- **入口/函数**: `try_acquire_strict_native_mutex` → `_close_partial_file_descriptor`
- **文件(行号)**: `dayu/runtime/native_mutex.py:339-359`
- **输入场景**: native lock 操作抛出异常（如 Windows lock-byte 准备失败、非 busy OSError 或意外异常），随后 `os.close(fd)` 也失败
- **实际分支**: `_close_partial_file_descriptor` 的 `except Exception` 分支（行 354），`prior_error` 不为 `None`
- **预期行为**: 下游 caller 应能通过异常链获取原始操作失败的原因与完整 traceback，以便诊断是 native lock 本身失败还是 cleanup 失败
- **实际行为**: `cleanup_error` 抛出时只通过 `add_note` 记录 `prior_error` 的 `__class__.__name__`（行 358），原始异常的 message、traceback 均丢失；`cleanup_error.__cause__` 指向的是 `os.close` 的异常（行 356-357），不是原始操作异常
- **直接证据**:
  - 行 355: `cleanup_error = StrictNativeMutexUnavailableError("关闭 partial strict-native mutex file descriptor 失败")`
  - 行 356: `cleanup_error.__cause__ = exc` —— `exc` 是 `os.close` 的异常，不是 `prior_error`
  - 行 357-358: `prior_error` 仅以类型名出现在 note 中
  - 调用方行 184-185 / 189-191 / 192-194 的原始异常只有在 cleanup 成功时才能通过后续 `raise ... from exc` 保留
- **影响**: 生产环境中同时发生 native lock 失败和 fd close 失败时，运维只能看到"关闭 partial fd 失败"和 prior_error 的类型名，无法得知原始操作失败的具体原因（如 errno、路径、业务上下文），排障困难
- **建议改法和验证点**:
  1. 在 `_close_partial_file_descriptor` 内，当 `prior_error is not None` 且 close 也失败时，使用 `cleanup_error.__cause__ = prior_error` 并将 close 异常作为 note 或通过 `add_note` 附加；或使用 exception group 同时携带两个错误。
  2. 修改后新增测试：mock 同时触发 native lock 失败与 `os.close` 失败，断言异常链同时包含原始错误与 cleanup 错误
- **修复风险（低）**: 仅改变异常链结构，不改变 fail-closed 语义与资源清理行为
- **严重程度（中）**:

### 003-未修复-低-acquire_mutation_lease 在 Host closing 且无 record 时的 rejection reason 语义不够精确

- **入口/函数**: `HostSessionAttachmentRegistry.acquire_mutation_lease`
- **文件(行号)**: `dayu/host/session_attachment.py:455-461`
- **输入场景**: `begin_host_close` 已调用，对从未 attach 过的 `session_id` 调用 `acquire_mutation_lease`
- **实际分支**: 行 455 `record is None` 为 True，行 457-461 因为 `self._host_closing` 为 True，返回 `ATTACHMENT_CLOSING`
- **预期行为**: 无 record 意味着从未有过 attachment，`ATTACHMENT_REQUIRED` 比 `ATTACHMENT_CLOSING` 更精确地表达"需要先 attach"
- **实际行为**: 返回 `ATTACHMENT_CLOSING`，暗示曾有一个正在关闭的 attachment，实际上并没有
- **直接证据**:
  - 行 457-461: `reason = HostSessionMutationRejectionReason.ATTACHMENT_CLOSING if self._host_closing else HostSessionMutationRejectionReason.ATTACHMENT_REQUIRED`
  - `_host_closing` 为 True 并不意味着该 session_id 曾有过 attachment
- **影响**: 调用方收到 `ATTACHMENT_CLOSING` 可能误以为 attachment 正在关闭并等待，但实际是 never-attached；对行为无影响（均不可重试、均被拒绝），仅语义标签不够精确
- **建议改法和验证点**:
  1. 当 `record is None` 时始终返回 `ATTACHMENT_REQUIRED`（无论 `_host_closing` 状态），因为 closing 状态应绑定具体 record
  2. 测试：Host closing 后对从未 attach 的 session 调用 `acquire_mutation_lease`，断言 `ATTACHMENT_REQUIRED`
- **修复风险（低）**: 仅修改一个 rejection reason 字符串，不改变控制流
- **严重程度（低）**:

- **`_release_record` 对已缓存 `close_error` 的无重试行为未独立单测**: 现有测试通过 `release_host_close` 幂等性间接覆盖（行 531），但没有独立测试直接验证 `_release_record` 在 `close_error` 已存在时的返回行为。
