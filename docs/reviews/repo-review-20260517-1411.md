### F-01-未修复-高-advance_projection_checkpoint 的 UPDATE 未对旧 checkpoint 值做 CAS 保护

- **入口/函数**: `advance_projection_checkpoint`
- **文件(行号)**: `dayu/host/durable/projection.py:165-176`
- **输入场景**: 两个投影消费者在不同连接上并发推进同一个 consumer 的 checkpoint
- **实际分支**: UPDATE 只带 `WHERE consumer_id = ?`，不校验旧 `checkpoint_event_sequence`
- **预期行为**: UPDATE 应包含对旧 `checkpoint_event_sequence` 的 CAS where 条件，防止 checkpoint 回退
- **实际行为**: UPDATE 无条件覆盖。若连接 A 要推到 10，连接 B 要推到 8，B 可能在 A 之后执行 UPDATE，将 checkpoint 从 10 回退到 8
- **直接证据**: `projection.py:165-176` — `UPDATE {TABLE_HOST_PROJECTION_CHECKPOINTS} SET checkpoint_event_sequence = ?, checkpoint_event_id = ?, ... WHERE consumer_id = ?`，不校验旧值
- **影响**: 如果未来引入多连接投影，checkpoint 回退将导致事件重复消费或投映缺失。当前单连接模式下被 BEGIN IMMEDIATE 序列化保护，但函数是公共 API
- **建议改法和验证点**: UPDATE 增加 `WHERE checkpoint_event_sequence = ?` 绑定旧值，rowcount==0 时分类为 CAS_LOST；在 tests/ 下增加并发 checkpoint 推进测试
- **修复风险**: 低。只需加一个 WHERE 条件和结果处理，不影响现有单连接路径
- **严重程度**: 高

### F-02-未修复-高-SSE/非流式 finish_reason 不一致导致 tool_calls 在非流式路径被误判为协议失败

- **入口/函数**: `_emit_from_dict` vs `_finalize_success`
- **文件(行号)**: `dayu/engine/runners/openai/non_stream_parser.py:306-310`; `sse_parser.py:545-549`
- **输入场景**: provider 在非流式响应中返回 tool_calls 但 choice 的 `finish_reason` 缺失或非 `tool_calls`
- **实际分支**: SSE 路径 fallback 到 `TOOL_CALLS`（`sse_parser.py:545-549`）；非流式路径直接使用 `_resolve_finish_reason` 结果（默认 `STOP`），无等价 fallback
- **预期行为**: 两条路径在 terminal 语义上等价，非流式在有 tool_calls 时也应以 `TOOL_CALLS` 收口
- **实际行为**: 非流式路径可能产出 `RunnerDoneData(finish_reason=STOP)` + tool_calls，被 `_classify_iteration` 判定为 `runner_tool_calls_finish_reason_mismatch` → `run_failed`
- **直接证据**: `sse_parser.py:545-549` — `finish = self._finish_reason or (FinishReason.TOOL_CALLS if self._tool_calls_seen else FinishReason.STOP)`；`non_stream_parser.py:306-310` — 无等价 fallback
- **影响**: 正常工作的非流式 provider（尤其兼容 gateway 未严格返回 finish_reason）可能在 engine 层被错误标记为协议失败
- **建议改法和验证点**: 在 `_emit_from_dict` 中，当 `tool_calls_emitted` 为 True 时覆盖 `finish_reason` 为 `FinishReason.TOOL_CALLS`。添加非流式 tool_calls 集成测试
- **修复风险**: 低。纯粹是补全 SSE 路径已有的 fallback 逻辑
- **严重程度**: 高

### F-03-未修复-高-tool_calls_content="" 覆盖 completed_content 导致 AssistantMessage 正文丢失

### F-04-未修复-中-await_or_cancel_or_timeout 中 target_task 完成与 cancel_watcher 同时命中时取消优先

- **入口/函数**: `await_or_cancel_or_timeout` → `_execute_batch`
- **文件(行号)**: `dayu/runtime/cancellation.py:250-257`; `dayu/engine/agent.py:1542-1545`
- **输入场景**: 工具执行 task 已完成，cancel_watcher 在 `asyncio.wait` 返回前也同时检测到 token 取消
- **实际分支**: `cancel_watcher in done and token.is_cancelled()` (行 255) 优先于 `target_task in done` (行 258)，返回 `WaitCancelled`
- **预期行为**: 取决于设计意图——若取消语义是"阻止未来工作，不覆盖已接受事实"，则已完成工具结果应被接受；若取消语义是"Host 已不再需要该 run 的结果"，丢弃已完成工具结果可能正是期望行为

- **影响**: 工具执行成本被浪费，且违反"取消阻止未来工作，不覆盖已接受事实"的设计承诺（如该承诺适用）
- **建议改法和验证点**: 需与 Host 层确认取消语义后再决定是否调整优先级。若确认应优先接受已完成结果，将 `target_task in done` 检查移到 cancel_watcher 之前
- **修复风险**: 中。若 Host 层依赖"取消后不存在已完成工具结果"的语义，此改法会破坏
- **严重程度**: 中

### F-05-未修复-中-await_or_cancel_or_timeout 的 elapsed_seconds 计算包含 target task 取消等待时间

- **入口/函数**: `await_or_cancel_or_timeout`
- **文件(行号)**: `dayu/runtime/cancellation.py:263-264`
- **输入场景**: `awaitable` 超时，其对应的 target task 在被 `_cancel_task_and_wait` 等待时花了额外的 2 秒才真正退出
- **实际分支**: 先 `await _cancel_task_and_wait(target_task)` 耗时不确定，然后才计算 `time.monotonic() - started_at`

- **建议改法和验证点**: 在 `_cancel_task_and_wait` 之前先 snapshot elapsed 值
- **修复风险**: 极低。只改元数据字段值，不影响控制流
- **严重程度**: 中

- **修复风险**: 低-中。需修改 admission 层 cancel 事务内逻辑
- **严重程度**: 低
