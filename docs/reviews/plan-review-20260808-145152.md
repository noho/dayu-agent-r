# F18 Implementation Plan 对抗性评审

## Reviewed target and scope

- Target：`docs/gateflow/pr-190-f18-plan-20260808.md`。
- Binding scope：`docs/gateflow/pr-190-f18-goal-confirmation-20260808.md` 与用户已确认的 F18 A-E 要求。
- Design truth：`docs/host/design.md`、`docs/engine/design.md`。
- Owner code：`dayu/cli/commands/interactive.py`、`dayu/host/dispatch.py`、
  `dayu/host/run_input.py`、`dayu/host/durable/memory.py`、`dayu/host/durable/schema.py`、
  `dayu/host/admission.py`。
- Direct evidence：Trial2 immutable EventLog / typed owner evidence、segment11 process bundle，以及
  `workspace/tmp/f18_owner_reproduction.py` 和隔离 diagnostic clone。private evidence 仅用于验证计划假设，
  本文不发布 raw SQLite、绝对私有路径、异常原文或 credential。
- Review boundary：只评审 plan；不实施修复、不运行真实 provider、不裁决 B2。

## Assumptions tested

1. `open_host` construction-time policy 约束是否同时等价于“同一 durable Session 跨不同 opener 不得改变
   memory/context/compactor policy”。
2. sequence 324 的隔离 clone 是否能通过 public attach/follow-up 重建原 sequence 325/326 的同一 pre-start
   owner 输入与状态。
3. segment11 是否真的存在可与 sequence 325 tool facts 对照的 runner-call manifest。
4. `candidate_prepared` / provider sentinel 是否足以证明或排除 sequence 327 的具体 root cause。
5. fixed-profile fresh MiMo observation 是否已具体到执行 Agent 无需重新设计场景、预算、证据采集和 publication。
6. B1 accepted 与 B2 unadjudicated / overall non-ready 是否保持隔离。
7. public/private evidence 边界是否避免用 private SQLite 或 ephemeral traceback 代替 owner contract。

## Findings

### DS-F18-PR01-未修复-高-把单 opener 的 construction-time 约束外推成跨 opener Session 禁令

- **位置**: First-principles judgment 第 33-39 行；Slice 3 fixed-profile setup 第 135-137 行
- **问题类型**: 契约缺失 / 动机不成立 / 架构边界
- **当前写法**: 计划根据 context/memory/compactor policy 不在 per-Run override 闭集中，直接裁定 Trial2 在
  同一 attached Session 的相邻 CLI 进程之间切换 profile/caps “不是正式 scenario 可接受的固定 setup”。
- **反例/失败场景**: CLI invocation A 关闭其 Host handle，workspace config 合法更新后，invocation B 用全新的
  `open_host(options)` attach 同一 durable Session。两个 handle 内都没有发生 per-Run policy mutation；如果公共契约没有
  冻结 Session-level profile identity，这是一条可能合法的 production reattach 路径。此时只用 fixed-profile fresh run
  绕开它，会让跨 opener memory projection discontinuity 留在产品中，同时把 setup correction 错报成 root-cause closure。
- **为什么有问题**: `docs/host/design.md:1204-1208` 只说明一个 `open_host(options)` 的 construction-time baseline、
  当前 per-Run request 闭集和同一 handle 内的 compactor接线；没有声明 durable Session 跨 opener 绑定不变的
  context/memory policy identity。`dayu/cli/commands/interactive.py:106-113` 也证明每次 CLI invocation 都重新 open Host。
  更重要的是，plan 自己引用的 typed rows 已显示 wide policy snapshot 在 sequence 324 有 compact/3 个 EvidenceFact，而新
  policy snapshot 在 sequence 325 从空 view 开始。`ConversationMemoryProjectionConsumer` 按 policy digest 读取 previous
  snapshot（`dayu/host/durable/memory.py:267-305`），但 durable projection checkpoint 的主键只有 `consumer_id`
  （`dayu/host/durable/schema.py:927-943`），snapshot 才包含 `policy_digest`
  （`dayu/host/durable/schema.py:1017-1027`）。这是一项直接的跨 opener 连续性风险，不是“setup 已证明非法”的证据。
- **直接证据**: `docs/host/design.md:1204-1208`；`dayu/cli/commands/interactive.py:106-113`；
  `dayu/host/durable/memory.py:267-315`；`dayu/host/durable/schema.py:927-943,1017-1027`；plan 第 44-50 行记录的
  Trial2 typed snapshot 差异。
- **影响**: 实施 Agent 会跳过用户明确要求优先验证的 frozen-configuration / manifest / runner-input contract，可能把
  合法跨 opener 路径中的产品缺陷隐藏为 harness 错误；root cause 和唯一 owner 都无法闭合。
- **建议改法和验证点**:
  1. 将“正式 observation 必须从首个 Run 固定 profile”（用户已明确要求）与“Trial2 跨 opener 切换是否违反产品
     contract”（尚未证明）分成两个结论。
  2. 增加明确 contract-decision gate：从 existing public attach/request contract、Session durable identity 和 policy
     ownership 证明跨 opener policy change 是 rejected、supported 或 currently unspecified。
  3. 若要 reject，必须回 Controller 重新确认 Session-level frozen policy identity、拒绝 owner 与 typed failure；若要
     support，必须在 projection owner 证明 checkpoint/snapshot 如何按同一 policy identity replay，不能只跑 fixed profile。
  4. owner test 至少覆盖“新 opener + 同 Session + 不同 memory policy”并断言唯一的 typed contract outcome。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### DS-F18-PR02-未修复-高-seq324 重放既不状态等价也不能作为原异常的因果证明

- **位置**: Slice 2 第 99-124 行
- **问题类型**: 不可直接实施 / 状态机漏洞 / 最佳实践偏离
- **当前写法**: 从 Trial2 sequence 324 的隔离 SQLite clone “恢复 typed Session/Run/memory/checkpoint state”，再走
  public attach/follow-up 进入完整 `_run_pre_start_governance`；复现时用 exception chain 裁决 root cause。
- **反例/失败场景**:
  - seq324 的数据库中尚不存在原 sequence 325 `USER_INPUT_ACCEPTED` 和 sequence 326 `RUN_ACCEPTED`。走 public
    follow-up 会生成新的 Run/event/idempotency/timestamp/effective facts，因而是 counterfactual new Run，不是原 Run 重放。
  - 若从现有终态库删除 sequence 327 并回写 run/projection rows来得到“seq326”，则必须跨 EventLog、run、outbox、audit、
    Tool Trace、memory 与 projection checkpoints 完整回滚。现有 diagnostic clone 的 EventLog max sequence 已是 326，
    但 audit/outbox/tool-trace checkpoint 仍为 327；它不是 owner state machine 可达的一致快照。
  - 在这种 clone 上重新得到同类异常，只能证明人为状态可触发它；得不到异常也不能排除原进程中的瞬态 I/O、payload、
    transaction snapshot 或 runtime resource failure。
- **为什么有问题**: `prepare_runner_call_candidate_in_transaction` 的输入包括 current Run/input identity、当前 transaction 的
  session-wide candidate cursor、policy-frozen payload、compact/fallback/payload state
  （`dayu/host/run_input.py:2227-2333`），不是只由 sequence 324 的 memory snapshot 决定。CLI CI handbook 还明确禁止用
  private SQLite mutation 伪造目标 state（`docs/cli_ci.md:820-821,833-835`），mandatory SQLite observation 本身只能读
  （`docs/cli_ci.md:1531-1534`）。隔离 mutation 可以作为标记清楚的 hypothesis experiment，但不能成为 formal root-cause truth。
- **直接证据**: Trial2 immutable chain 只有 325 `USER_INPUT_ACCEPTED`、326 `RUN_ACCEPTED`、327 `RUN_FAILED`；
  `dayu/host/dispatch.py:1852-1927`；`dayu/host/run_input.py:2227-2333`；`docs/cli_ci.md:820-821,833-835,1531-1534`；
  当前 F18 diagnostic clone 的 max EventLog sequence / projection checkpoint 交叉核验。
- **影响**: 可能把 clone artifact 或 counterfactual new Run 的异常错归为原 sequence 327 根因，或把不复现错当作产品
  无缺陷；review 无法区分真实 owner cause 与 harness 造出的 state skew。
- **建议改法和验证点**:
  1. 只有真实存在、自然采集的 sequence 326 point-in-time consistent snapshot 才能声称 exact-state replay；先证明
     `PRAGMA integrity_check`、FK、EventLog max cursor、run row、全部 projection checkpoint/outbox/audit/trace identity 一致。
  2. 若只能做 SQL rollback，必须改名为 counterfactual diagnostic，列出每个 mutation 和不一致检查结果，并明确禁止用其
     exception 直接裁决原 root cause。
  3. 将“原 immutable DB 上 direct candidate read”“synthetic counterfactual”“fresh public-path sentinel”分成三个实验，
     分别写清可证明与不可证明的命题；任何 sentinel reached 只证明本次 candidate 越界成功。
  4. 原 logger/point-in-time evidence仍不可恢复且三次 bounded owner replay均不复现时，Slice 2 应明确交 Controller 形成
     blocker verdict，不能解锁 Slice 3或用 fixed-profile observation替代 root-cause closure。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DS-F18-PR03-未修复-中-工具同源门引用了失败路径上不存在的 manifest 与错误字段名

- **位置**: Slice 2 第 112-115 行
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: 从 sequence 325 `USER_INPUT_ACCEPTED.effective_tool_facts` 与 production `HostToolingOptions` 构造
  tool bundle，并与“segment11 captured manifest”逐项核对 tool count 13、schema/source identity。
- **反例/失败场景**: 原 Run 在 candidate freeze 前失败，没有 Attempt，也没有
  `RUNNER_CALL_INPUT_ASSEMBLED` manifest。segment11 process bundle只保存 command/actions/screen/runtime/filesystem/SQLite
  before-after/terminal；不存在该 Run 的 runner-call manifest。实际 durable payload 字段是 `effective_tool_set`，不是
  `effective_tool_facts`。实现 Agent若按当前步骤执行，只能借用别的 Run manifest或当前 runtime tool bundle，形成跨 Run
  的错误同源证明。
- **为什么有问题**: `dayu/host/dispatch.py:1881-1908` 先从 `effective_tool_set` 解析 decision、构造 selected schemas，
  然后才尝试 candidate；manifest 只有 candidate成功并进入 allow commit后才可产生。Trial2 的 325-327 EventLog 也直接显示
  中间没有 runner-call manifest event。
- **直接证据**: Trial2 sequence 325-327 typed EventLog；segment11 evidence file inventory；
  `dayu/host/dispatch.py:1881-1908`；`dayu/host/admission.py:3929-4120` 的 `effective_tool_set` producer/parser/runtime
  validation contract。
- **影响**: Slice 2 的 13-tool identity prerequisite 无法按文档完成，或会用另一 Run/当前装配的偶然事实替代原 admission
  truth，使任何后续 exception comparison失去同源性。
- **建议改法和验证点**:
  1. 删除不存在的 segment11 manifest 依赖，改用 sequence 325 `effective_tool_set` 的完整 frozen names、bundle digest、
     selected schema digest、source refs、display names与tool snapshot ref。
  2. 用 target commit、segment11 before/after config inventory及 production `HostToolingOptions` 重新装配 runtime，再调用
     `validate_effective_tool_facts_runtime` 做全字段 exact validation；把 callable 未进入 durable facts列为明确 limitation。
  3. 先验证 `disable_tools` 与 `ToolExecutionMode` 也与原 `_candidate_tool_selection` 一致，不在诊断脚本中硬编码
     `TOOL_ENABLED`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### DS-F18-PR04-未修复-高-Slice3 仍是验收清单而非可执行的 bounded observation plan

- **位置**: Slice 3 第 126-160 行；Verification matrix 第 162-190 行
- **问题类型**: 切片过粗 / 不可直接实施 / 过度耦合 / 测试缺口
- **当前写法**: 计划只要求每条 chain 从第一轮起固定 constrained profile，然后把 accepted replacement、repair、fallback、
  reconnect 和十类 evidence列为 assertions；没有给出各 chain 的 typed precondition builder、Run/input 序列、触发条件、
  provider-call/wall-time上限、stop condition、public projector命令或 artifact schema/path owner。
- **反例/失败场景**: constrained caps 从首个 Run 生效后，baseline可能在形成足够 FY2024/FY2025 protected material之前就
  触发 compact；自然 MiMo可能先产出 accepted candidate，导致 repair/fallback链不出现；也可能多轮都不触发 compactor。
  在没有每条 chain 的最大 Run/model-call数、prompt作用、trigger ratio、expected precondition query和停止规则时，执行 Agent
  只能边消耗真实 provider边重新设计场景。把三个独立 real chains、fresh reconnect、SQLite前后、public Tool Trace、
  publication scan与registry更新放在一个 slice，也使失败无法独立审查和保留。
- **为什么有问题**: 用户要求 bounded observation只允许取得 mandatory evidence的最小次数，并要求失败原样保留；
  `docs/cli_ci.md:1241-1290,1386-1429,1497-1546` 还冻结了 evidence bundle、public/private projection、run completion、
  Tool Trace与SQLite query manifest边界。当前 plan没有把这些 contract转成 Agent 可逐步执行和 reviewer 可验收的设计。
- **直接证据**: plan 第 135-160 行只有 setup原则和结果断言；Verification matrix 对 Slice 3 没有命令或 per-chain
  assertion；用户 F18 C 的十项 mandatory evidence与 bounded限制；`docs/cli_ci.md:1241-1290,1386-1429,1497-1546`。
- **影响**: 高成本 real run 不可复现，可能过量消耗 provider、遗漏失败 evidence、让不同链共享可变 state，或在 run 后才
  发现 publication/SQLite/reconnect evidence无法补采；实施 Agent被迫在 implementation gate重新做 plan。
- **建议改法和验证点**:
  1. 拆成至少三个 independently reviewable execution units：replacement+reconnect、same-boundary repair、exhausted
     fallback；每条链各有 fresh workspace/config digest、precondition query、PTY action timeline、最大 Run/model-call/wall-time、
     natural-nontrigger stop disposition。
  2. 对 replacement chain 明确 FY2024 baseline、FY2025 production tool evidence、无 provenance 数字输入和触发 compact 的
     Run顺序；在进入 compactor前用 public/durable typed query确认“relevant material over initial caps”。
  3. 指定复用 handbook 中哪个已有 harness/projector及其 immutable digest；列出 public report/index/secret-scan/path-scan/
     run-completion文件名与 private raw owner，禁止临场新建第二套 analyzer。
  4. 把每条失败链立即 seal/digest 的步骤放在下一链之前；最后再做 cross-chain report/registry projection，并断言 B2
     `status`、adjudication identity、overall readiness均不变。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Lens conclusions

- **Goal-bound minimal design**：B1 slice 与 Goal Confirmation 对齐且保持 B2隔离；B2 slice却把尚未证明的
  cross-opener illegality当成既定裁决，偏离“先验证假设”的 binding goal。
- **Architecture boundary**：Engine排除正确；candidate freeze在 Host owner正确。Session-level policy identity和
  projection checkpoint ownership尚未收敛。
- **Best practice / optimal solution**：先区分 immutable original evidence、consistent point-in-time replay与
  counterfactual experiment是更安全的路径；当前 synthetic clone不足以承载因果裁决。
- **Overengineering**：未发现需要新增 profile registry、动态 per-Run policy或公共 traceback字段的理由；这些应继续排除。
- **Overcoupling**：Slice 3把三条真实链、reconnect、全部 publication和registry更新绑定成一个 gate，导致局部失败无法独立
  seal和review。

## Open questions

1. durable Session 跨新 opener 的 memory/context/compactor policy change 当前究竟是 supported、rejected，还是 public
   contract未定义？正确 owner必须在进入 implementation前裁决。
2. Trial2 是否存在自然采集、未经过 DML rollback 的 sequence 326 point-in-time SQLite/WAL/backup？若不存在，原 exception
   是否还有同一 invocation 的 debug log、audit sidecar或 process stderr可恢复？
3. segment11 config before/after evidence是否包含 execution profile完整内容/digest，足以把当前 production
   `HostToolingOptions` 与 sequence 325 `effective_tool_set` 做 exact runtime validation？
4. 正式 observation准备复用哪一个已经审查过的 PTY harness、typed owner exporter和 public publication projector？其 digest、
   per-chain预算和失败 sealing规则是什么？

## Residual risks and tracking destination

- B1 cold analyzer `compactor_responses=0` 与 provider-native request id unavailable：按用户裁决保留为 residual evidence
  question，跟踪在 B1 observation limitation；不阻塞 B1 accepted。
- 原 sequence 327 exception若无自然日志/consistent snapshot，可能永久不可恢复：应由 F18 Controller记录为 root-cause
  blocker，不得转成“fixed-profile setup已修复”。
- 真实 MiMo未自然触发 repair/fallback：保留在 B2 observed report 为 `needs-more-evidence`，B2继续
  `unadjudicated`，overall readiness非 ready。
- cross-opener policy continuity若需要 public contract/schema变化：必须回 Goal Confirmation/design gate，不得由当前 plan
  暗中实现。

## Final plan review conclusion

`fail`。

当前计划对 B1 可实施，但 B2 的关键 contract judgment、seq324/326 replay epistemic boundary、tool bundle同源门和三条
real-chain execution design均未收敛。修复上述 findings并完成两路独立 re-review前，不应进入 implementation，也不得运行
真实 provider。
