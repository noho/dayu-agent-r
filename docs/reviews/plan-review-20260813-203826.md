## Findings

### F1-未修复-高-material 先发布 company meta 再 prepare，与 plan 自述 zero-publication 矛盾

- **位置**: plan §2.3 success signals（"company/source/blob published tree不变"）、§5.6 invariants、S2 Tests first 第 1/3 条、§5.1；goal-confirmation goal #5
- **问题类型**: 状态机漏洞 / 反例未覆盖 / 计划内部矛盾
- **当前写法**: plan 承诺"有效+损坏混合输入：…Fins publication batch `0`，company/source/blob published tree不变"；S2 test 1/3 断言 "batch begin/commit/rollback均 `0`、published tree为空/保持旧SHA"、"batch begin `0`、company/source stage `0`"，且未限定 filing；§3.1 又声明"不新增 material 业务规则"
- **反例/失败场景**: fresh workspace 执行 material 上传，输入文件为空或损坏 → `run_upload_material_stream` 先 `begin_batch` + `upsert_company_meta_for_upload` + `commit_batch`（SEC: 528-543 行；CN: 1137-1150 行），随后 `prepare_upload` 才读取/转换并抛出 typed failure → 公司 meta 已持久化，published tree 已变化，terminal 才报 stored=0。与 plan §2.3 的"published tree不变"直接矛盾
- **为什么有问题**: goal #5（用户已确认）"损坏 PDF、损坏 DOCX、有效+损坏混合输入整批失败，且不发布 filing、company/source state 或任何非零 stored count"是 binding goal；material 在本 WU 范围内（§6.1.2/§6.1.3 明确修改 material terminal 构造，§5.4 typed catch 含 material）。plan 未给出任何方案弥合该顺序与 goal 的冲突
- **直接证据**: `sec_upload_workflow.py:528-543`（company_batch commit 在 prepare_upload 之前）、`cn_pipeline.py:1137-1150`（同形）；对比 filing 路径 prepare→begin_batch→stage company（`sec_upload_workflow.py:208-253`、`cn_pipeline.py:828-873`）已验证 plan §4 的原子性论证只对 filing 成立
- **影响**: implementation agent 只能三选一：(a) 违反 goal 保留现状 → success signal 不可验收；(b) 静默重排 material company 顺序 → 违反 §3.1"不新增 material 业务规则"且未获确认；(c) S2 测试对 material 必然失败。三种结果都使 plan gate 产出的 artifact 不可直接实施
- **建议改法和验证点**: 二选一并在 plan/controller 明确裁决：① 将 material company upsert 移到 prepare 成功后（与 filing 同构；需把该顺序修正显式写入 §6.1.2/§6.1.3 与 §5.6，并修订 §3.1 措辞，同时为 material 增加 corrupt/empty 时 company tree 不变断言）；② 在 goal-confirmation 补充确认 zero-publication 仅覆盖 filing，material 的 company 先行作为既有行为记录为 residual risk。无论哪种，S2 test 1/3 必须写明断言对象是 filing workflow，material 另立其实际契约断言
- **修复风险（低）**: plan 文本修订或小幅重排，不涉及新机制
- **严重程度（高）**: 与 binding goal 直接冲突且 plan 内部自相矛盾，实施前必须收敛

### F2-未修复-高-material 失败路径 raw `str(exc)` 未明确收口，且 material 测试文件不在 allowed 列表

- **位置**: plan §5.4、§6.1.2/§6.1.3、§7 S1/S2 allowed test files、§8.2/§8.6
- **问题类型**: 契约缺失 / 切片边界不一致 / 测试缺口
- **当前写法**: S1 对 material 只写"success/cancel/failure 构造点机械补齐 count/error；不新增 material 行为"；S2 只要求"filing/material typed catch与failure terminal构造"；plan 全文没有一处明确要求 material 的 generic `except Exception` 停止写入 `str(exc)`
- **反例/失败场景**: 现状 SEC material generic catch（`sec_upload_workflow.py:606-633`）写 `message=str(exc)` 与 `payload={"error": str(exc)}`，且**没有 `_LOGGER.exception`**；CN material（`cn_pipeline.py:1213-1239`）同形。implementation agent 按 plan 字面只补 count 与 typed catch 时：(a) goal #6 的"public event 无 raw 文本"对 material 不成立；(b) material 失败在 operator log 中无完整 cause，与 goal #6 "operator log 使用异常链保留完整 traceback/cause" 冲突；(c) §8.6 broader regression 会执行 `tests/fins/test_sec_pipeline_upload_material_stream.py`，该文件不在任何 allowed 列表，且其 217-222 行现有断言依赖 `result["message"]`/`payload["error"]` 的 raw 文本行为，不迁移必挂
- **为什么有问题**: 与 filing 的 typed 投影（`sec_upload_workflow.py:341-349`、`cn_pipeline.py:961-968` 使用 `fins_upload_failure_from_exception` + `_LOGGER.exception`）形成同包双标准；plan 的允许文件边界无法完成"所有 producer/consumer 编译通过、测试通过"的 S1 expected outcome
- **直接证据**: 上述代码行；`tests/fins/test_sec_pipeline_upload_material_stream.py:217-222`；plan §7 S1/S2 allowed test files 均未包含该文件
- **影响**: goal #6 对 material 不成立；review 无法验收 §8.6；实施受阻或被迫越界改测试文件
- **建议改法和验证点**: §5.4/§6.1.2/§6.1.3 明确：material generic catch 必须改为 `_LOGGER.exception(...)` + typed failure 字段（复用 `fins_upload_failure_from_exception`），删除 `message=str(exc)` 与 `payload.error=str(exc)`；S1/S2 allowed test files 加入 `tests/fins/test_sec_pipeline_upload_material_stream.py` 并列出需迁移的断言（message/error 行为断言改为 typed failure 断言）；S2 增加 material bounded reason 的精确断言
- **修复风险（低）**: 文本修订与既有测试迁移，无新机制
- **严重程度（高）**: 允许文件边界硬伤 + goal #6 未收口，直接阻塞 code-generation

### F3-未修复-高-file_label 安全契约与 direct 投影守卫不一致，合法文件名可击穿 typed 失败

- **位置**: plan §5.4 label 校验规则、§5.5 details 投影（"非空时再包含 `retry hint` 与 `file`"）、S2 Tests first 第 4/5 条
- **问题类型**: 契约缺失 / 跨 owner 不一致 / 语义所有权漂移
- **当前写法**: label 校验 = 非空、长度 `<=240`、不含控制字符、`/`、`\\`、不是 `.`/`..`；details 投影用 `FinsEventDetail("file", file_label)`；plan 未提及 `FinsEventDetail` 的既有 safe-text 守卫，也未定义"控制字符"的具体字符类
- **反例/失败场景**: 合法 POSIX basename `财报正文.pdf` 或 `job_id_notes.pdf`（`upload_filing.path-and-name-input` predicate 要求 Unicode/普通文件名可接受）损坏后：failure owner 按 §5.4 校验通过并生成 label → `_upload_result_details` 构造 `FinsEventDetail` 时 `_validate_safe_text` 命中 fragment 禁令（`"job_id"`、`"财报正文"`，direct_events.py:1093-1104）抛 ValueError → 已分类的 typed content failure 崩塌为 unknown/generic CLI 失败，用户丢失可行动原因；而 durable summary（`to_json_summary` 不经过该守卫）却能正常持久化同一 label → 同一业务事实两种投影不一致。另一方向：label 的"控制字符"若按现有 `_validate_failure_reason_text` 语义实现（仅 `ord<32`，upload_failure.py:296），U+2028/U+202E/0x7F 等格式控制字符可通过并被单行渲染成换行/双向注入，bounded stderr 边界被绕过
- **为什么有问题**: 两个 owner（failure owner 与 direct event owner）各自持有标签安全规则且接受集不一致；plan 未指定唯一共享 contract，违反 CLAUDE.md 语义所有权约束（同一业务事实必须从同一真源投影且一致）；"控制字符"未定义会诱导 implementation agent 复制现有不完整实现
- **直接证据**: `direct_events.py:45-59, 1067-1104`（fragment 禁令与守卫）；`upload_failure.py:280-297`（现有文本校验仅 ord<32）；`ingestion_runtime.py:6254-6286`（现 details 构造点，plan §6.1.5 将在此加入 `file` detail）
- **影响**: 用户可构造的合法输入触发分类崩塌；typed failure 契约对 Unicode 文件名不稳定；direct/durable 语义漂移
- **建议改法和验证点**: plan 必须指定唯一 label 安全契约并二选一：① file_label 投影走专用 bounded 渲染，不复用 `_validate_safe_text` 的 fragment 禁令（fragment 禁令面向内部治理泄漏，不应作用于用户文件名），并在 failure owner 与 direct/durable 三处共享同一 validator；② 在 failure owner 生成 label 前判定"不可安全投影"的 basename 使用固定有界标签（如"输入文件"）并在 operator log 保留原始名——必须写明这是 owner 级决策而非下游 fallback。同时把"控制字符"定义为具体字符类（推荐 Unicode category Cc+Cf 或保守允许集），与单行渲染边界一致。补 S2 测试：含禁用 fragment 或格式控制字符 basename 的损坏文件仍产出 typed failure 且 stderr 有界、无换行注入
- **修复风险（中）**: 需要新增共享 validator 或投影分支，但不涉及架构变更
- **严重程度（高）**: 直击 direct path 的 typed 投影可靠性，且为三个 accepted predicates 的目标面

### F4-未修复-低-commit 失败终态 `stored_file_count=0` 缺显式精确测试

- **位置**: plan §5.1（"commit 抛错时不得投影 stored count"）、§8.1 matrix（"storage failure … no result count"）、S1/S2 Tests first 列表
- **问题类型**: 测试缺口
- **当前写法**: §8.1 有矩阵级描述，但 S1 Tests first 第 1-6 条没有任何 commit_batch raise 场景；§4 引用的既有 rollback SHA 测试（`tests/fins/test_sec_pipeline_upload_filing_stream.py:445-485` 等）证明的是树不变，不是新 failure terminal 的 stored=0 契约
- **反例/失败场景**: `commit_batch` 抛错 → workflow 走 `except OSError`/generic → failure builder 若漏写 `stored_file_count`，`from_pipeline_json` 因 required 字段拒收并抛 ValueError → 用户的 typed storage failure 退化为 unknown 失败；该路径当前无测试锁定
- **为什么有问题**: 本 WU 核心交付之一就是"commit 失败不投影 stored count 且 failure terminal 显式 stored=0"，plan §5.1 已把它列为 contract 但未配 owner-level 精确断言
- **直接证据**: `commit_prepared_upload_batch`（docling_upload_service.py:868-892）commit 抛错路径；plan S1 Tests first 列表缺失该条
- **影响**: 回归时该契约可能静默漂移为 fail-closed 但错误分类
- **建议改法和验证点**: S1 或 S2 增加精确断言：commit raise → terminal status=failed、failure kind=storage（或既有分类）、`stored_file_count=0`、既有 published tree SHA 断言保持
- **修复风险（低）**
- **严重程度（低）**

### F5-未修复-低-direct no-artifact 负断言缺 positive control，"证明"措辞过强

- **位置**: plan §2.3 success signals 最后一条、S3 Tests first 第 4 条
- **问题类型**: 测试有效性 / 措辞精度
- **当前写法**: "direct upload 后 `.dayu/fins_ingestion/jobs` 无 JSON/JSONL record，且不存在 Host Run/Attempt/EventLog/Memory/ToolTrace/runtime SQLite artifact"；S3 test 4 未要求先断言 upload 成功
- **反例/失败场景**: upload 提前失败（如 runner unavailable、typed failure 早退）时，job/Host artifact 同样不存在 → 负断言空转通过，测试在"从未真正执行成功上传"的状态下绿灯；"证明"一词对文件系统观察断言过强——它只证明被测 workspace 与流程未产生 artifact，不构成对代码路径的完备证明
- **为什么有问题**: 测试失去证伪力；plan 自身的 S3 invariant 已正确写明"不 mock Host 来'证明'未调用"，但 §2.3 的措辞与之不一致
- **直接证据**: plan §2.3 末条、§7 S3 test 4、S3 invariant；`tests/README.md:367` 已存在"direct stream 不创建 durable job record 或 sidecar"的既有覆盖（说明该断言是回归护栏而非新证明）
- **影响**: 测试存在空转风险，completion report 可能误报边界成立
- **建议改法和验证点**: S3 test 4 先断言 upload terminal 为 success（positive control）再执行 artifacts 负断言；§2.3 措辞由"证明"改为"regression 断言"；写明检查的具体路径（workspace `.dayu` 树），保持可证伪
- **修复风险（低）**
- **严重程度（低）**

## Final plan review conclusion

**fail**

核心判断：plan 的 count 链路、typed failure 贯通、CLI bounded stderr 与 direct no-artifact 方向全部有直接代码证据支撑，三个 accepted predicates 的覆盖意图正确，A1/A8/A9 等关键假设成立；但存在三个 plan-gate blocker：

- F1：plan 自述的 material zero-publication 与生产代码中 material company-meta 先行 commit 的顺序直接矛盾，且与用户已确认的 goal #5 冲突，需要 controller/用户裁决口径后才能实施；
- F2：material 失败路径的 raw `str(exc)` 与缺失 operator log 未明确收口（goal #6 对 material 不成立），且 `tests/fins/test_sec_pipeline_upload_material_stream.py` 不在任何 slice 的 allowed 列表，§8.6 回归必挂；
- F3：file_label 安全契约与 `FinsEventDetail` 投影守卫接受集不一致，合法 Unicode 文件名可击穿 typed 失败，违反语义所有权约束。

F4/F5 为低严重度补强项，可随修订一并落地。修复均为 plan 文本修订或小幅实现重排，不涉及架构推翻；收敛 F1-F3 后本 plan 具备进入 implementation gate 的条件。
