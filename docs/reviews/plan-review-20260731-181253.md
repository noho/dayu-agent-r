## Goal / Non-goals / Success Signal Review

Plan 的总体 goal、六项 finding、Host cancellation 真源、冻结 registry 不可修改及
process/interactive/compaction 非目标与用户确认一致。S1、S2、S4 的主要 owner 选择成立；
S5 把 ordinary policy 与 stream admission 分成两个事实的方向也成立。

但是 plan 尚不能进入 implementation：日志 selector 的核心解析算法已被最小反例直接证伪；
startup slice 只处理 import boundary，却把更晚、仍在 Run accepted 前的阶段留在默认
`KeyboardInterrupt`/`asyncio.run` 路径；runtime handler 的第二道 level gate 没有进入 exact
change；已裁决必须更新的 README 也没有任何允许修改它们的 slice。

## Assumptions Tested

1. built-in `append` / `append_const` 能否在 argparse root parser 与 subparser 之间共享并累积
   同一个 occurrence list。
2. 轻量 bootstrap 的 `try/except KeyboardInterrupt` 是否同时覆盖 import、parser、配置装配、
   Host open、Session ensure 与 command-local signal monitor 安装前的完整启动生命周期。
3. lowering logger threshold + handler filter 是否足以放行 exact `STREAM_DEBUG`，而不修改现有
   handler level gate。
4. prompt 的 second-SIGINT waiter 删除后，Host terminal wait 与 local cleanup ordering 是否仍由
   当前 owner 保持。
5. strict UTF-8 validation 是否位于 argparse/primary operation 前，且静态错误自身可编码。
6. log-file 空路径 usage 与合法路径 `OSError` resource failure 是否由 typed error 分开。
7. 每个 declared docs decision 是否存在可执行 slice、allowed files 与 validation。
8. architecture、best practice、optimal solution、overengineering 与 overcoupling lenses：方案是否
   保持 `UI -> Service -> Host -> Engine`、是否在 runtime 引入 CLI 反向依赖、是否新增无需求的
   signal/log registry、是否把 prompt-only 行为塞进共享层。

## Findings

### PR-001-未修复-高-root/subparser 同 dest accumulation 假设已被直接证伪
- **位置**: `Contract / Public Interface Decisions` 第 132-134 行；S5 第 246-251 行；
  `Risks / Open Questions` 第 310-311 行
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: Plan 指定用 built-in `append` / `append_const`，让 root/subparser 的 selector
  都追加到“同一个 typed occurrence list”，再按 count 拒绝冲突，并声称该设计覆盖 command
  前后位置。
- **反例/失败场景**: 使用与当前 parser 相同的 parent + subparser 结构执行最小实验：
  `--debug prompt x --info` 最终得到 `levels=['info']`；而同一 subparser scope 的
  `prompt x --debug --info` 才得到 `['debug', 'info']`。因此 root 阶段 occurrence 会在 subparser
  namespace 合并时被覆盖，跨 command 的两个 selector 被误判为只有一个。
- **为什么有问题**: frozen contract 要求任意两个 selector entry 无论 argv 顺序、语义是否相同、
  是否跨 command 位置都在 primary operation 前 exit 2。当前算法会静默接受跨 scope 冲突，
  直接复现被 oracle 禁止的 last/inner value wins。
- **直接证据**: Plan 第 132-134 行的算法声明；当前 `build_parser()` 在
  `dayu/cli/arg_parsing.py:193-210` 同时把 common/runtime parent 用于 root 和 command
  subparser；本次只读最小实验输出为
  `Namespace(levels=['info'], cmd='prompt', x='x')` 与
  `Namespace(levels=['debug', 'info'], cmd='prompt', x='x')`。`docs/cli_ci.md` 5.1.3 和
  `prompt.19-log-selector-exclusion-and-debug-stream` 要求全部有序双 entry 冲突 exit 2。
- **影响**: implementation Agent 按 plan 写出的 parser 无法通过跨 root/subparser 矩阵；若测试
  只把两个 selector 都放在 prompt 后，还会假通过 owner tests，真实共享 CLI contract 继续错误。
- **建议改法和验证点**:
  - 先修改 plan，不要再依赖跨 parser scope 的同 dest append。
  - 用单一 option/spec 真源注册 selector，但为 root、command、二级 action 使用各自明确的 typed
    occurrence dest；parse 完成后由公共 parser owner 合并这些 scope-local occurrences，再做唯一
    selector 与 quiet/debug-stream 校验。不要扫描 raw argv，也不要使用进程全局 mutable collector。
  - owner tests 必须至少覆盖 `selector-before-command + selector-after-command` 两个顺序；共享 contract
    还需覆盖 `session` 这类二级 action 的 root/command/action 三层位置，证明中间层不会再次覆盖。
  - frozen PC-LC 256 条仍全部运行，但不能用它们替代跨 scope owner tests，因为当前 registry 中这些
    invocation 的两个 selector 均位于 `prompt` 之后。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-002-未修复-高-startup slice 只覆盖 import，未覆盖 monitor 安装前的完整启动生命周期
- **位置**: `Startup signal boundary` 第 89-95 行；S3 第 203-218 行；
  `Prompt accepted-Run cancellation state machine` 第 85-87 行
- **问题类型**: 状态机漏洞 / 契约缺失 / 测试缺口 / open question 未收敛
- **当前写法**: S3 将 finding 3 收窄为“import/startup signal gap”，只让轻量
  `run_module` 在 lazy import 周围捕获 `KeyboardInterrupt` 并返回 130；单元测试也只在 lazy import
  阶段注入中断。
- **反例/失败场景**: `run_prompt_command()` 进入 `asyncio.run()` 后，依次执行 runtime/config
  preparation、`open_host`、`_ensure_prompt_session`，最后才进入
  `execute_prompt_on_session()`；运行阶段 `CliSigintMonitor.install()` 更晚才在
  `session_execution.py:860-864` 执行。SIGINT 若发生在 main 已导入、但这些阶段尚未完成时，
  bootstrap 只能把最终 `KeyboardInterrupt` 映射成 130，不能证明未产生 Session/Run/attempt 业务
  状态，也没有 typed startup intent 与阶段 cleanup contract。
- **为什么有问题**: 用户确认目标与 `prompt.14-startup-sigint-graceful-exit` 覆盖“从进程启动到
  Run accepted 前的任意阶段”，并要求不产生半初始化业务状态、按实际 ownership 清理资源。
  exit code 正确并不证明该 contract。Plan 自己在 goal success signal 中也承诺 Run 创建前不创建
  Session/Run/attempt，但 S3 的 exact changes 没有实现这个承诺。
- **直接证据**: `dayu/cli/commands/prompt.py:105-128` 在创建 `CliSigintMonitor`/执行
  `execute_prompt_on_session` 前已完成 prepare、Host open 与 Session ensure；
  `dayu/cli/session_execution.py:860-864` 才安装 signal handler。S3 第 209-214 行仅处理 lazy
  import 并只断言 process returncode/traceback。冻结 P47、PC-CN-01..06 的 required evidence 还包含
  filesystem、SQLite 与 Host state，不是纯 process-exit 测试。
- **影响**: implementation 可能让所有 startup scenario 显示为 exit 130，却在某个 phase 留下空
  Session、accepted Run 或未完全关闭的 Host/runtime resource；该偏差直到昂贵 final real run 才暴露，
  slice review 无法验收。
- **建议改法和验证点**:
  - Plan 必须先明确一个最小 startup signal owner，覆盖 bootstrap import 后到 command-local monitor
    takeover 前的阶段；不得仅靠最外层 exit-code catch，也不得新增 Host rollback/SQLite 补偿。
  - 若在“不新增 submission race/transaction rollback”的约束下无法同时保证 Run accepted 前所有阶段
    零业务副作用，应把具体冲突列为 blocking open question，而不是声明 None。
  - S3 增加受控 phase tests：分别在 parser/log resource、runtime prepare、Host open、Session ensure、
    monitor takeover 前注入 SIGINT；逐项断言 exit 130、无 traceback、资源 close 次数与 Host/SQLite
    before-after。再用 P47、PC-CN-01..06 的真实 exact timing 作端到端证明。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-003-未修复-中-debug-stream 方案漏写现有 handler level gate
- **位置**: `Logging public selector and runtime admission` 第 127-131 行；S5 第 246-257 行
- **问题类型**: 不可直接实施 / 最佳实践偏离 / 测试缺口
- **当前写法**: Plan 要求把 namespace logger threshold 降到 ordinary 与 `STREAM_DEBUG` 的较低值，
  再给自有 handler 增加 exact stream-or-ordinary filter；没有规定 handler 自身的 level。
- **反例/失败场景**: 当前 `_build_marker_handler(level, stream)` 在
  `dayu/runtime/log.py:262-273` 仍执行 `handler.setLevel(int(level))`。若 ordinary 为 INFO，即使 logger
  threshold 已降到 STREAM_DEBUG、filter 允许 exact STREAM_DEBUG，stdlib `Logger.callHandlers` 也会先因
  `record.levelno < handler.level` 跳过 handler，filter 根本不会运行。
- **为什么有问题**: `--info --debug-stream` 会继续丢失 stream records；这正是 plan 要修复的二维
  admission contract。测试虽然计划断言该组合，但 exact implementation recipe 不完整，Agent 必须在
  实现时重新设计。
- **直接证据**: Plan 第 127-130 行只描述 logger threshold 与 filter；当前 handler level gate 位于
  `dayu/runtime/log.py:270-272`。`prompt.19` 要求默认/info ordinary policy 不变，同时额外启用 exact
  stream diagnostics。
- **影响**: S5 可能首轮实现必然失败，或为了放行 stream 将 handler level 永久降到 STREAM_DEBUG 而
  忘记 filter/quiet/configure_root 对称处理，造成普通 DEBUG/VERBOSE 泄漏。
- **建议改法和验证点**:
  - 在 plan exact changes 中明确 handler admission level：debug-stream 开启时 handler 与 logger gate
    都必须允许 STREAM_DEBUG 到达 filter；关闭时保持 ordinary threshold。namespace/root 两条
    `configure` 路径复用同一个 filter/handler builder。
  - 明确 quiet without stream 的 handler/logger gate，及 quiet+stream 在配置前 fail closed。
  - runtime tests 同一 handler 依次发出 level 9/10/15/20/30/40/50，覆盖每个 ordinary policy 和
    debug-stream 开关，而不只检查 logger.level。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Architecture Boundary Review

- S1 在 CLI typed terminal projection owner 丢弃 raw reason，未修改 Host durable reason，边界正确。
- S2 保留 Service/Host cancel-and-terminal owner，CLI 只编排 accepted Run，方向正确；但必须维持
  prompt-only change，不改 interactive 的二次中断 state machine。
- S4 的 UTF-8 拒绝位于 CLI invocation text boundary、resource error 位于 process output destination
  boundary，未向 Host/Engine 下沉，边界正确。
- S5 将 canonical ordinary policy 与 stream diagnostic admission 放在层中立 runtime，且 runtime 不
  import CLI，方向正确；PR-001 是 parser scope 合并算法错误，不应通过 prompt-only shim 绕过。
- S3 的 owner boundary 尚未闭合，见 PR-002。

## Best-practice / Optimal-solution / Overengineering / Overcoupling Review

- 采用 typed ordinary log policy、typed resource error、strict UTF-8 validation、Host terminal waiter 均是
  当前项目内更直接且可测试的路径。
- 不需要通用 signal framework、logger registry、migration、Host cancel rewrite 或 argv raw-string scan；
  PR-001 的 scope-local occurrence 合并和 PR-003 的单一 handler filter 足以解决当前问题。
- 五个业务 slice 的 owner 拆分总体合理；README 应作为窄 docs step 纳入，不应与 Host/Engine 绑定。
- 当前最大 overcoupling 风险是用同一个 argparse dest 假设贯穿不同 parser namespace；应以 parser
  scope-local事实合并替代共享可变状态。

## Open Questions

1. controller 必须裁决：在不新增 Host transaction rollback/submission race 语义的前提下，startup
   signal owner 如何覆盖 main import 完成后、command-local monitor 安装前的 runtime/Host/Session 阶段，
   并满足已确认的业务副作用 contract。该问题在 revised plan 前属于 blocking。

## Residual Risks and Suggested Tracking Destination

- editable console launcher 的旧 entrypoint cache：保留在 S3/final real validation，记录 executable 与
  installed entrypoint identity。
- 真实 provider availability：保留为 final evidence residual risk，不能替代 parser/cancel correctness。
- POSIX startup timing 的调度抖动：除 wall-clock accepted scenarios 外，必须由 phase-controlled tests
  锚定 owner contract；跟踪在 S3 tests/review，不另建 feature。
- frozen scenario registry 的 PC-LC 双 selector 当前都在 command 后：跨 root/command/action 的 owner
  regression 必须进入 deterministic parser tests，不能误称 frozen real matrix已覆盖。

## Final Plan Review Conclusion

`fail`

Plan 方向大体正确，但 PR-001 已直接证伪核心 selector 实现算法，PR-002 又使 startup contract 的一部分
没有实现 owner；二者都足以阻止进入 implementation。controller 应先修订 plan，随后对 revised plan 做
同一 gate 的 fix/re-review。PR-003、PR-004 应在同次修订中收口，避免把可预见失败后移到 slice 或 final
validation。
