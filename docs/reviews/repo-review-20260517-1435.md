### 1-未修复-中-BatchToolExecutionOutcome 缺少双射不变量运行期校验

- **入口/函数**: `BatchToolExecutionOutcome.__init__`
- **文件(行号)**: `dayu/contracts/tool_outcome.py:150-166`
- **输入场景**: Host ToolRuntime 构造 `BatchToolExecutionOutcome` 时传入 records 与原始 calls 不双射（长度不匹配、重复 tool_call_id、缺失 id）
- **实际分支**: `__post_init__` 不存在，无任何校验
- **预期行为**: contracts 层在构造期拦截非法 outcome，fail fast
- **实际行为**: 非法 outcome 静默构造成功，错误延迟到 Engine 状态机层（`_execute_tool_batch` 中校验）
- **直接证据**: docstring 第 154-158 行明确承诺双射不变量，第 160-161 行写"任何违反双射的输出由 Engine 转为 `tool_batch_outcome_mismatch` 终态失败"——docstring 自身承认了 Engine 兜底而非 contracts 层拦截
- **影响**: 错误延迟发现；若 Engine 校验逻辑变更，可能静默接受非法 outcome
- **建议改法和验证点**: 补充 `__post_init__` 校验 records 非空、tool_call_id 唯一性；或修改 docstring 澄清"双射由 Engine 验证，contracts 层不做强制校验"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-RunnerSpec 缺少 default_timeout_seconds 和 max_retries 边界校验

- **入口/函数**: `RunnerSpec.__post_init__`
- **文件(行号)**: `dayu/engine/contracts/runner_spec.py:267-304`
- **输入场景**: 调用方构造 `RunnerSpec(default_timeout_seconds=0, max_retries=-1)` 或 `default_timeout_seconds=-5`
- **实际分支**: `__post_init__` 只校验 `stream_idle_*` 字段，`default_timeout_seconds` 和 `max_retries` 无校验

- **影响**: 调用方构造非法 spec 不会 fail fast，运行时行为异常且难以诊断
- **建议改法和验证点**: 在 `__post_init__` 中添加 `default_timeout_seconds > 0` 和 `max_retries >= 0` 校验
- **修复风险（低/中/高）**: 低

## Open Questions

1. **`BatchToolExecutionOutcome` 双射校验的分层归属**: docstring 承诺 contracts 层校验，同时承认 Engine 兜底。应明确在哪一层做强制校验，避免两层都不做或都做导致语义不一致。

2. **`lane.py` 每次 SQLite 操作都新建 connection 的设计意图**: 高频 acquire/release 场景下是否有意避免长连接？当前设计在极端并发下可能触发 `SQLITE_BUSY`。

3. **`tool_runtime.py` 文件体积（3700+ 行）**: 单一模块承载 accept barrier、截断管理、duplicate governance、policy port、ToolRuntime factory 等多个职责，是否需要拆分？

## Residual Risk

1. **Schema v7 无迁移路径**: 旧 v6 DB 用户需要手动删除重建。符合项目约束（全新 schema 起库），但需在 release notes 提示。
2. **`or` 链语义变更缺少边界测试**: `content_chunks` 包含空字符串的边界场景无覆盖。
3. **EventLog partial index 写入开销**: 新增 `(run_id, event_type, event_sequence)` partial index 会略微增加写入 I/O，但 CREATE INDEX 在 bootstrap 时执行，不影响运行时。
4. **`lane.py` 心跳错误处理的不可恢复性**: 单次 SQLite 瞬态错误会导致 controller 永久关闭，需上层重建。
5. **dispatch scheduler `_drain_loop` 使用 `asyncio.sleep` 轮询**: 空闲时产生不必要 CPU 唤醒；`put_nowait` 后 drain task 可能已进入 sleep，有延迟。
6. **`_cancel_pending_readany` 吞掉所有异常**: 极端 edge case（event loop 关闭期间）的 `RuntimeError` 被静默吞掉，debug 时难以追踪。
