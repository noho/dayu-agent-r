## Findings

### MIMO-DESIGN-F01-unfixed-MEDIUM-Service coordination primitives after relay removal are unspecified

- **位置**: Codex artifact "State 与 lifecycle" bullet "Session Event Delivery 不创建 per-watcher background task"；control doc residual `WU-SVC-ENTRYPOINT-RELAY-CAPACITY-01`
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: design correction 要求删除 `dayu/service/entrypoint_runtime.py` 的 event-retaining relay queue / drain task（`_WatchAndWaitRuntime`），并声明"任务协调可以使用不持有事件副本的 readiness / cancellation primitive"；Future WU scope 第 6 项同样只说"用不保存 event 副本的 primitive 完成 terminal observation、cancellation 与 UI callback coordination"
- **反例/失败场景**: Service 当前 `_drain_host_events()` drain task 承担三个职责：(1) 将 Host iterator 事件 `await queue.put(event)` 中继到 Service 消费循环；(2) 捕获 watcher 异常并转为 `_WatcherFailure`；(3) 使 `_consume_until_terminal()` 能通过 `await queue.get()` 顺序消费并同步观察 terminal、触发 UI callback（`on_activity`、`on_thinking`、`on_run_accepted`）和写 Outbox。删除 relay queue 后，如果 Service 直接 `async for event in watcher`，它仍然是在创建一个隐式的消费循环；如果要同时做 terminal observation + UI callback + cancellation，要么 (a) 在消费循环内联处理——此时 `_consume_until_terminal()` 变成直接消费 Host iterator，不需要 queue 但需要重构整个消费函数；要么 (b) 使用 `asyncio.Event` / `asyncio.Condition` 做 signaling——但这些 primitive 不传递事件，Service 仍然需要某种方式拿到 terminal event。两种路径在 design correction 中都没有具体说明，留给 implementation agent 自行设计。
- **为什么有问题**: Future WU scope 第 6 项是 implementation agent 的直接工作指令。如果 agent 不知道用什么具体 primitive 替换 relay queue，它要么保留部分 queue 语义（违反 design），要么自行设计一套新 coordination（可能引入第二类 event-retaining 结构或 overcoupling）。当前 control doc 的 Open Questions 第 3 项承认了这个 gap，但把它标记为"不阻塞本 design correction"——对于 design correction 本身这是对的，但对于进入 implementation WU 来说这是一个 code-generation-ready blocker。
- **直接证据**:
  - `entrypoint_runtime.py:500-511`：`_WatchAndWaitRuntime` 绑定 watcher + queue + drain_task
  - `entrypoint_runtime.py:1036-1054`：`_drain_host_events()` 从 watcher 读取并 `await queue.put(event)`
  - `entrypoint_runtime.py` 消费循环通过 `await runtime.queue.get()` 顺序处理事件并触发 UI callbacks
  - Codex artifact Open Questions #3："删除 Service relay 后，当前 terminal observation / UI callback 并发如何用无事件副本的 signaling primitive 保持取消、Outbox fallback 与 renderer close 语义"
- **影响**: implementation agent 可能引入未在 design 中审核的替代结构，或保留部分 relay 语义导致 double-buffer 未真正消除
- **建议改法和验证点**: 在 design correction 或 Future WU scope 中至少指定 Service replacement primitive 的 direction：(a) Service 直接消费 Host iterator（`async for event in watcher`）并在消费循环内联 terminal observation / UI callback，不需要中间 queue 或 drain task；或 (b) 使用轻量 signaling（`asyncio.Event` 表示"有新事件"）加 direct drain 但不保留 event 副本。无论哪种，必须明确：Service 不再有第二条 event queue、不再有 drain task、terminal observation 通过 iterator 消费本身完成。验证点：implementation 后 `_WatchAndWaitRuntime` 被删除、`_ENTRYPOINT_LIVE_EVENT_BUFFER_CAPACITY` 被删除、Service 不再持有 `asyncio.Queue[HostSessionEvent]`。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### MIMO-DESIGN-F02-unfixed-LOW-Byte accounting helper boundary is under-specified

- **位置**: Codex artifact "Byte accounting"；design.md diff "Session Event Delivery 提供唯一 deterministic `delivery_size_bytes` helper"
- **问题类型**: 契约缺失
- **当前写法**: "对 `HostTransientDelta` public envelope 与 typed payload 中每个 string field occurrence 计算 `len(value.encode("utf-8"))` 后求和，optional `None` 计零"
- **反例/失败场景**: `HostTransientDelta` public envelope 包含 `runtime_id`、`session_id`、`run_id`、`attempt_id`、`execution_id`、`dedupe_key`（6 个字符串 identity 字段）加上 `observed_at`（datetime，非字符串）。typed payload 中 `content_delta` 有 `iteration_id` + `text_delta`；`reasoning_delta` 同；`tool_call_delta` 有 `iteration_id` + 可选的 `tool_call_id`、`name_delta`、`arguments_delta`。design 说"每个 string field occurrence"，但没有明确 (a) envelope 的 identity 字段是否计入——如果计入，每个事件有 ~6×20-40 字节的固定开销，这对 byte budget 的意义不同于 payload strings；(b) `observed_at` 是 datetime 不是 string，不计入是正确的但 design 没有显式排除。implementation agent 可能实现只计算 payload strings（忽略 envelope），或计算所有字段（包括 identity），两种结果差异 ~150-250 字节/事件。
- **为什么有问题**: 如果 implementation agent 选择只计算 payload strings，`max_bytes` 的语义与 design 意图不一致；如果计算所有 strings，identity 字段的固定开销会让 byte budget 更快耗尽。两种选择都不"错误"，但必须一致。
- **直接证据**:
  - `dayu/host/api.py` 中 `HostTransientDelta` dataclass 有 `runtime_id`、`runtime_sequence`(int)、`session_id`、`run_id`、`attempt_id`、`execution_id`、`worker_event_index`(int)、`observed_at`(datetime)、`type`、`data`、`dedupe_key`
  - payload 闭集：`HostContentDeltaData(text_delta, iteration_id)`、`HostReasoningDeltaData(text_delta, iteration_id)`、`HostToolCallDeltaData(iteration_id, tool_call_index, tool_call_id?, name_delta?, arguments_delta?)`
- **影响**: implementation agent 面对模糊 spec 可能做出与 design 意图不一致的选择，导致 byte budget 语义漂移
- **建议改法和验证点**: 在 design 中明确 `delivery_size_bytes` 计算边界：只计算 typed payload 中的 string fields（`text_delta`、`iteration_id`、`tool_call_id`、`name_delta`、`arguments_delta`），不计算 envelope identity 字段。理由：identity 字段是 bounded-length opaque ids，其大小不随 token 数增长；真正 unbounded 的是 payload 中的 `text_delta` 和 `arguments_delta`。验证点：helper 实现与 design 声明一致、测试覆盖各 delta type 的 byte 计算。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### MIMO-DESIGN-F03-unfixed-LOW-Error constant terminology shift needs explicit tracking

- **位置**: design.md diff "component=`session_event_delivery`, reason_code=`transient_mailbox_overflow`"；current code `transient_delta.py:27-28`
- **问题类型**: 最佳实践偏离
- **当前写法**: design 将 overflow error 的 `component` 从 `"session_live_stream"` 改为 `"session_event_delivery"`，`reason_code` 从 `"slow_consumer"` 改为 `"transient_mailbox_overflow"`
- **反例/失败场景**: 当前代码中 `_LIVE_STREAM_COMPONENT = "session_live_stream"` 和 `_SLOW_CONSUMER_REASON_CODE = "slow_consumer"` 是 module-level constants。任何 consumer（包括 Service、CLI、tests）如果通过 `detail.component` 或 `detail.reason_code` 做 error routing 或 logging，都需要同步更新。design correction 没有在 Future WU scope 中显式列出这个 terminology migration 作为 implementation item。
- **为什么有问题**: 这不是 design 错误——terminology 改进是正确的。但 Future WU scope 作为 implementation agent 的工作指令，应显式列出 error constant 的变更，避免 agent 忘记更新或测试遗漏。
- **直接证据**:
  - `transient_delta.py:27`：`_LIVE_STREAM_COMPONENT: Final[str] = "session_live_stream"`
  - `transient_delta.py:28`：`_SLOW_CONSUMER_REASON_CODE: Final[str] = "slow_consumer"`
  - design diff 中新值为 `"session_event_delivery"` 和 `"transient_mailbox_overflow"`
- **影响**: implementation agent 可能忘记更新 error constants 或遗漏 consumer-side 适配
- **建议改法和验证点**: 在 Future WU scope 中增加一项：更新 `_LIVE_STREAM_COMPONENT`、`_SLOW_CONSUMER_REASON_CODE`、`_slow_consumer_error()` 及其所有 consumer reference。验证点：`rg "slow_consumer\|session_live_stream" --include="*.py"` 在 implementation 后返回零命中（排除 test fixtures 中的 historical reference）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Positive Design Decisions (not findings)

以下设计选择经审查为正确，不构成 finding：

1. **Overflow = typed disconnect only**：design 明确禁止 silent drop-and-continue，要求未来 drop 策略必须先扩展 `HostSessionEvent` 的 typed gap notice。这与用户 frozen goal"调用者决定"不矛盾——disconnect 本身就是对 overflow 的 caller-visible 安全响应，不是设计替 caller 做了隐藏选择。

2. **EngineEvent ingest 不知道 policy**：ingest 只做 validation + typed candidate + non-blocking handoff，不读取 mailbox capacity。这正确隔离了 durable ingest 与 transient delivery。

3. **Durable reader 是 pull-based 而非第二 buffer**：iterator facade 中 EventLog reader 按 `event_sequence` cursor 分页拉取，不复制 rows 进 transient mailbox。这避免了 durable events 占用 transient budget。

4. **Terminal fence before overflow disconnect**：`drain_nowait()` 中 `mark_run_terminal` 过滤逻辑确保同一 Run 的 terminal 之后不再投递 delta，即使 mailbox 中有存量。

5. **`HostSessionEventDeliveryPolicy` 是 construction-time，不是 per-Run**：delivery capacity 是 runtime 级资源约束，不是 per-Run tuning knob。这与 `WaitPollerRuntimePolicy` 放在 `OpenHostOptions` 的模式一致。

## Open Questions

1. **Service replacement primitive direction**: design 需要在 implementation WU 前至少给出 Service 消费模式的方向性指导（直接消费 vs. signaling primitive），否则 implementation agent 面对 `_WatchAndWaitRuntime` 删除时缺乏 spec。（关联 MIMO-DESIGN-F01）

2. **Packaged default values**: `transient_mailbox_max_items` 和 `transient_mailbox_max_bytes` 的默认值需要 workload / SLO / memory benchmark 证据。当前代码中 `256` (item-only) 是唯一参考点。这是 design 正确 defer 的问题，不阻塞 design correction。

3. **`delivery_size_bytes` 与 Python object overhead**: byte accounting 是 logical UTF-8 bytes，不等于 Python heap resident bytes。implementation 需要 benchmark 校准 default values 时的 margin。design 正确声明了这个 gap。

## Verdict

**pass-with-risks**

Design correction 的核心架构决定（Session Event Delivery 单一 owner、per-subscription mailbox、typed policy、byte accounting、typed disconnect overflow、Engine ingest 不知道 policy）均基于直接代码证据，与用户 frozen goals 一致，不违反 Engine design truth source 或 Host 分层约束。

主要风险是 MIMO-DESIGN-F01：Service relay removal 后的具体 coordination primitive 未指定。这不是 design correction 本身的 scope（它 correctly defers to future WU），但对 implementation WU 的 code-generation-ready 程度构成中等风险。Future WU scope 第 6 项应补充方向性 primitive 指导。

其余 findings 为低严重度的 spec 细节或 terminology tracking，不阻塞 design correction 进入 review / implementation gate。
