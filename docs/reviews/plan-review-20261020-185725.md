## 4. Findings

### 1-未修复-[高]-§7 真实 sync 的“已核收源码”检查会漏掉未跟踪文件

- **位置**: §7 正式 sync/验收，计划第 183–184 行 `git status --porcelain --untracked-files=no`；与 §6.2 第 159 行“不能把 dirty 副本自称已核收 commit”对照。
- **问题类型**: 契约缺失 / 验收证据不可靠 / 来源绑定。
- **当前写法**: 保存当次核收完整 OID、当前 HEAD、tracked clean 指纹；命令使用 `--untracked-files=no`，并声称“所有交付的源码/脚本无偏离”“源码与核收版本不符即失败”。
- **反例/失败场景**: 实现新增 `scripts/install-source.sh` 或修改 `dayu/**` 后遗漏 `git add`。真实 sync 时 `git rev-parse HEAD` 等于核收 OID，`git status --porcelain --untracked-files=no` 为空；随后 README 的安装命令执行未跟踪脚本，editable 安装从工作树导入未跟踪源码。回执却声称安装的是核收 commit。
- **为什么有问题**: editable 安装的导入源是工作树而不是 commit 内容；未跟踪文件虽然不是 commit 的一部分，却会真实进入安装。计划 §6.2 明确要求 dirty 副本不能自称核收 commit，而 §7 的唯一 source guard 恰好忽略 untracked，两个契约互相矛盾。该问题不是实现细节，而是正式验收的 source binding 证据缺口。
- **直接证据**: 计划 §7 第 183–184 行；隔离 git probe 中 `git status --porcelain --untracked-files=no` 输出为空，`git status --porcelain --untracked-files=all` 输出 `?? scripts/install-source.sh`，`git ls-files --others --exclude-standard` 输出该路径；`pyproject.toml` 的 editable 安装和 `direct_url` 机制；计划 §6.2 第 159 行。
- **影响**: 未核收代码可能被当作已核收来源安装；正式验收 false pass，后续追溯、回滚和“源码 commit 绑定”结论失真。
- **建议改法和验证点**: 在 §7 增加未跟踪交付文件检查：使用 `git status --porcelain --untracked-files=all` 并对 evidence/ignored 路径设显式 allowlist，或使用 `git ls-files --others --exclude-standard` 限定 `scripts/ dayu/ tests/ README.md tests/README.md pyproject.toml` 必须为空；再对 `scripts/install-source.sh` 和交付文件执行 `git ls-files --error-unmatch` 并核对工作树 blob 与 HEAD 一致。验证：在隔离副本中放置一个未跟踪的 `scripts/install-source.sh`，确认新检查失败；删除后确认通过。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 高。
- **状态**: accepted-candidate；阻塞 §7 正式验收。计划总体方向成立，但 source binding 的验收命令必须修正后才可放行真实 sync。

### 2-未修复-[中]-README wheel 段的 `-I` 检查没有闭合“目标环境”语义

- **位置**: §5 第 115 行（关闭 DS F1）；README §1.2 当前第 52–62 行。
- **问题类型**: 契约缺失 / 用户可见检查不诚实 / 验收标准不完整。
- **当前写法**: “wheel 的安装和检查始终使用同一明确目标解释器，检查使用 `"<目标Python路径>" -I -m dayu.cli --help`，同时核验该解释器实际安装 metadata”。计划没有要求 §1.2 使用专用 venv 或明确目标 site。
- **反例/失败场景**: README §1.2 仍用 `python3.11 -m pip install /path/to/*.whl`；在 python.org/framework Python 或 Windows 上 pip 可能把 wheel 安装到 user site。随后 `python3.11 -I -m dayu.cli --help` 因 `-I` 隐含 `-s` 看不到 user site，报 `No module named dayu`。安装实际成功，README 却宣称检查失败；反过来，如果实现者选用了另一个解释器，检查证明的又不是 wheel 的安装目标。
- **为什么有问题**: DS F1 要解决的是“裸 PATH 命令可能命中源码入口”，不是“用 `-I` 无条件隐藏 user site”。`-I` 与 user site 的冲突是真实语义，不是风格问题；计划把“同一明确目标解释器”写成要求，却没有定义 §1.2 的目标环境是什么，导致实现者可能生成自相矛盾或误报的 README。
- **直接证据**: README §1.2 的安装命令；`pip install --help` 的 `--user`；实际 probe `python3.11 -I -c 'import site,sys; ...'` 输出 `no_user_site 1`、`ENABLE_USER_SITE False`；`python3.11 -m site` 显示 user site 路径；计划 §5 第 115 行。
- **影响**: 用户按 README 安装 wheel 后检查失败，误判安装失败；或不同目标环境的 metadata 被混用；DS F1 的关闭证据不诚实。
- **建议改法和验证点**: 在 §1.2 明确目标环境，优先推荐专用 venv（例如 `python3.11 -m venv .venv-wheel`），安装与检查都使用该 venv 的绝对解释器；如果保留非 venv 目标，不要用 `-I` 作为唯一检查（它会排除 user site），改为从源外 cwd 用 `env -u PYTHONPATH <target> -E -m dayu.cli --help`，并显式验证 `sys.path`/metadata 与 wheel 安装目标一致。README 核对应覆盖 venv 目标；若声明只支持 venv，则说明 user-site 不在支持范围。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。
- **状态**: accepted-candidate；不阻塞源码安装主目标，但建议在 IE-B1 的 README 文档核对中一并修正。

### 3-未修复-[中]-§7 的 `zsh -lic` 检查未处理 `.zshenv` 设置的 ZDOTDIR

- **位置**: §4.3 第 94 行“非标准 ZDOTDIR 明确失败”；§7 第 186–197 行真实 sync 的 `zsh -lic` 命令。
- **问题类型**: 契约缺失 / 新正常 shell 证据不可靠。
- **当前写法**: 只配置标准 HOME 的 `.zshrc`，非标准 ZDOTDIR 明确失败；§7 检查只移除 `VIRTUAL_ENV`、`PYTHONPATH`、`PYTHONHOME`，没有清除或检测 `ZDOTDIR`。
- **反例/失败场景**: 用户 `.zshenv` 设置 `ZDOTDIR=$HOME/zdotdir`。安装脚本写入 `$HOME/.zshrc`；真实 sync 的 `zsh -lic` 读取 `$ZDOTDIR/.zshrc`，不读取 `$HOME/.zshrc`。若 `$ZDOTDIR/.zshrc` 恰好已有 `~/.local/bin` PATH，检查通过，但证书证明的不是本次写入的 block；若没有，检查失败，尽管 `$HOME/.zshrc` 的 block 本身正确。计划承诺的“非标准 ZDOTDIR 明确失败”也没有被检查执行。
- **为什么有问题**: 计划把“非标准 ZDOTDIR 明确失败”作为 zsh 的安全契约，同时把 `zsh -lic` 的解析结果作为真实 sync 证据；两者没有通过同一个检测点连接。结果是验收证据可能来自用户的另一份 ZDOTDIR 配置，或者出现与本次写入无关的失败。
- **直接证据**: 隔离 zsh probe：`.zshenv` 设置 ZDOTDIR 后，`$ZDOTDIR/.zshrc` 无 PATH 时 `command -v dayu-cli` 为空；有 PATH 时解析到隔离 `.local/bin`；`$HOME/.zshrc` 未被执行。计划 §4.3、§7 命令。
- **影响**: 真实 sync 可能 false pass（由既有 ZDOTDIR 配置提供 PATH）或 false fail（block 正确但不被读取）；无法证明本次安装的 PATH block 是生效来源。
- **建议改法和验证点**: 在安装前检测有效 ZDOTDIR（至少 `ZDOTDIR` 环境变量；对 `.zshenv` 场景可用 `zsh -ic 'print -r -- "${ZDOTDIR:-$HOME}"'` 查询），有效值不是 `$HOME` 时明确失败；或在 §7 用受控 `ZDOTDIR=$HOME` 启动，并在检查中确认读取的是 `$HOME/.zshrc`。增加一个 `.zshenv` 设置 ZDOTDIR 的隔离测试；不扩展到通用 profile 探测框架。
- **修复风险（低/中/高）**: 中（需要额外 zsh 查询或受控启动，但不改安装主结构）。
- **严重程度（低/中/高/严重）**: 中。
- **状态**: accepted-candidate；建议在 §4.3/§7 修正后复评。

## 5. Open questions

1. **`$HOME/.local/bin` 本身是 symlink 时如何处理？** 计划明确拒绝 profile symlink、要求不沿旧符号链接写目标，也对入口路径的目录型链接定义冲突；但没有单独说明 PATH 目标目录本身是 symlink 的情形。若直接 `mkdir -p` 后写入，会跟随该目录链接写到用户管理的其它位置。建议在 §4.1 预检中明确：拒绝、解析后显式确认，或按用户可接受策略处理，并加入对应测试。此项不是当前用户环境的已知事实，不据此阻塞计划。
2. **§6.2 的 pip cache/config 隔离与“可复用普通下载缓存提高效率”是否矛盾？** 一处要求 HOME、pip cache/config 与证据都隔离，另一处允许复用普通下载缓存。建议明确是否设置 `PIP_CACHE_DIR`/`PIP_CONFIG_FILE`，并在工程回执中记录实际值；否则“隔离”与“复用”无法同时成立。
3. **README 源码安装后的当前 shell 连续性**：脚本不能修改父 shell 的 PATH；README 必须明确“重新打开终端后再运行 `dayu-cli init`”，否则用户在同一终端继续 §2 会得到 command not found。计划 §5 已提到“新终端检查”，实现时应在 README 的操作顺序中写清楚。
4. **§7 的 `/private/tmp` 和 `/bin/zsh` 是 macOS 轮廓**：计划已说其它 OS 使用正常启动 shell 与系统初始 PATH；真实 sync 是本机 macOS 时不构成问题，但 README/回执不应把它当成跨平台命令。
5. **profile 为 symlink、非标准 ZDOTDIR、未知入口普通文件等用户环境冲突**：计划选择明确失败并保留用户文件，这是正确的 fail-closed 行为，但真实 sync 可能因此停在需要主控裁决的具体冲突上；建议在工程核收回执中提前列出这些“已定义失败”，避免真实 sync 时被误认为安装实现缺陷。
