## Scope of Review

Review 覆盖以下维度（按用户指令）：

## Findings

### 001-未修复-中-read_api projection 路径未经测试覆盖 policy matrix

- **位置**: Plan Slice 1，"Confirm non-success terminal public events still reject inline `HostFinalAnswerView`" 段落
- **问题类型**: 测试缺口
- **当前写法**: Slice 1 说 "only add assertions if current tests do not already cover FAILED, CANCELLED, and LOST"
- **反例/失败场景**:
  - 当前 `test_public_host_event.py` 的 `test_failed_and_cancelled_events_reject_final_answer_payload` 和 `test_lost_event_rejects_final_answer_payload` 测试的是 **typed dataclass 构造层面的 ValueError**（`HostEvent` 的 `__post_init__` 拒绝在非 SUCCEEDED 状态设置 final_answer）。
  - 但 `read_api.py` 的 `_failed_host_event`、`_cancelled_host_event`、`_lost_host_event` 是**独立的投影代码路径**——它们直接构造 `HostEvent(final_answer=None)`，不走 typed dataclass 的 ValueError 校验路径。
  - 如果未来有人修改 `_failed_host_event` 错误地从某个字段构造 final_answer，现有测试不会捕获，因为 typed dataclass 测试只覆盖构造约束，不覆盖投影逻辑本身。
- **为什么有问题**: Plan 把 typed dataclass 测试等价于投影路径测试，但这是两条不同的代码路径。Plan 的 policy matrix 要求验证 "RUN_FAILED / governance failure → no assistant final answer"，但没有要求验证 read_api 投影实际产出 `final_answer=None`。
- **直接证据**:
  - `test_public_host_event.py:63-100` 测试 `HostEvent(...)` 构造拒绝 final_answer——不是 `read_api.py:_failed_host_event()` 的投影逻辑
  - `read_api.py:820-843` `_failed_host_event` 是独立的投影函数，直接设 `final_answer=None`
  - Plan 的 `tests/host/test_public_host_event.py` 在 Slice 1 allowed files 中但未要求新增投影路径断言
- **影响**: 实施 Agent 可能跳过 read_api 投影路径验证，导致 policy matrix 中 FAILED/CANCELLED/LOST 行的 "no assistant final answer" 只在 dataclass 层验证，不在投影层验证
- **建议改法和验证点**:
  - Slice 1 应增加至少一个测试：构造 mock EventLogRow（或使用 fake row）验证 `_host_event_from_row` 对 FAILED/CANCELLED/LOST 事件返回 `HostEvent(final_answer=None)`
  - 或者 Plan 应在 allowed files 中增加 `tests/host/test_read_api_projection.py`（如果 read_api 投影测试文件不存在），并明确列出需要的断言
  - 验证：`pytest tests/host/test_public_host_event.py -q` 加上新增的投影路径测试
- **修复风险（低）**: 添加投影路径测试不改变生产代码
- **严重程度（中）**: 如果投影路径不被测试，policy matrix 的一个核心行没有代码证据支撑

### 002-未修复-低-memory.py 使用 payload reader 而非 continuity resolver 的差异未在 plan 中显式说明

- **位置**: Plan 的 Policy Target 表格，Conversation Memory / compaction continuity 行
- **问题类型**: 契约缺失
- **当前写法**: Policy matrix 表格写 "Conversation Memory / compaction continuity: may use assistant final-answer continuity for recent-window continuity"
- **反例/失败场景**:
  - 当前 `memory.py:1625-1627` 使用 `assistant_final_answer_text_from_run_payload()`（只读 `final_answer` 字段）——**不是** `assistant_final_answer_continuity_text()`（完整 continuity resolver，包含 terminal summary artifact fallback）。
  - 换句话说，memory projection 的 selected recent window **永远不会**从 terminal summary artifact `content` 读取 assistant 回答。这与 compact_material.py 和 run_input.py 不同，后者使用完整的 continuity resolver。
  - 如果未来有人"统一" memory projection 改用 continuity resolver，可能意外引入 terminal summary artifact 内容进入 memory，而 plan 的政策矩阵并未对此差异给出明确指导。
- **为什么有问题**: Plan 没有识别出 memory.py 当前使用的是更窄的 reader（只读 `final_answer` 字段）而非完整 resolver。policy matrix 的 "may use assistant final-answer continuity" 措辞模糊，没有明确 "continuity" 在 memory 上下文中是否包含 terminal summary artifact fallback。
- **直接证据**:
  - `memory.py:18-21` import `assistant_final_answer_text_from_run_payload`（非 `assistant_final_answer_continuity_text`）
  - `memory.py:1625-1627` 调用 `assistant_final_answer_text_from_run_payload(payload, ...)` 只检查 `final_answer` 字段
  - `compact_material.py:2012` 使用 `assistant_final_answer_continuity_text()`（完整 resolver）
- **影响**: 实施 Agent 或后续维护者可能在 docstring 收敛时错误描述 memory 的文本来源，或未来错误"统一"为完整 resolver
- **建议改法和验证点**:
  - Plan 的 policy matrix 表格中 Conversation Memory 行应显式说明 "uses `RUN_SUCCEEDED.final_answer` only, does NOT fall back to terminal summary artifact content"
  - 或者：若 plan 意图是 memory 也应使用完整 continuity，需在 Slice 1 中显式列出修改 `memory.py` 调用
  - 当前行为（只用 `final_answer` 字段）本身是合理的——memory 不应依赖 artifact 回退——但需要在 plan 中显式确认
- **修复风险（低）**: 只需在 plan 中新增一行说明，或在 policy matrix 中细化 memory 行
- **严重程度（低）**: 当前代码行为正确，但 plan 措辞不够精确，可能误导 future work

### 003-未修复-低-empty_final_answer 转为 RUN_FAILED 的 governance 决策未在 policy matrix 中显式建模

- **位置**: Plan 的 Policy Target 表格，RUN_FAILED / governance failure 行
- **问题类型**: 测试缺口 / 契约缺失
- **当前写法**: Policy matrix 表格写 "RUN_FAILED / governance failure: no assistant final answer; terminal summary remains diagnostic only"
- **反例/失败场景**:
  - `engine_ingest.py:4394-4413` 中 `_final_answer_plan()` 对空 `final_answer.content` 转投 `RUN_FAILED`（reason: `empty_final_answer`）而非 `RUN_SUCCEEDED`。
  - 这是一个 **Host governance 决策**：Engine 产出 `final_answer`，但 Host ingest 因为内容为空而降级为失败。该路径的 terminal summary payload 只包含 `error_code` 和 `message`，不包含 `content`。
  - Plan 的 policy matrix 把 `RUN_FAILED` 和 "governance failure" 放在同一行，但没有区分：Engine 自身 run_failed（如 runner exception）、Engine final_answer 被 Host 治理拒绝（empty_final_answer）、以及未来可能引入的 `REJECTED` 状态（WU-GOV-01 / GitHub Issue #88）。
- **为什么有问题**: 当前 policy matrix 用 "RUN_FAILED / governance failure" 合并了两个不同来源的失败路径。虽然两者最终都是 `HostEvent(final_answer=None)`，但 terminal summary 内容不同（Engine failure 有 provider diagnostics；empty_final_answer 有 Host governance reason）。Plan 没有要求测试 empty_final_answer 路径下 terminal summary 不包含可显示的 final answer content。
- **直接证据**:
  - `engine_ingest.py:4394-4413` `_final_answer_plan()` → empty content → `_REASON_EMPTY_FINAL_ANSWER` → `_failed_plan(...)`
  - Plan 的 policy matrix 没有区分 Engine native failure 与 Host governance-driven failure
- **影响**: 如果 empty_final_answer 的 terminal summary 某天被错误地包含 content 字段（例如有人"修复"了 final_answer 为空时的行为），现有测试可能不捕获
- **建议改法和验证点**:
  - Slice 1 应增加一个测试（或在现有测试文件中）验证 `empty_final_answer` 路径的 terminal summary 不含 content 字段，且 read_api 投影为 `final_answer=None`
  - Policy matrix 可将 "RUN_FAILED" 行拆分为 "Engine RUN_FAILED" 和 "Host governance failure (empty final answer / future REJECTED)" 子行，或至少在注释中说明 empty_final_answer 归入此行
  - 注意：`empty_final_answer` 的测试可能需要在 `engine_ingest` 级别或 read_api 投影级别，不一定在 `test_terminal_summary_payload.py`
- **修复风险（中）**: 测试 empty_final_answer 路径可能需要更多 mock infrastructure
- **严重程度（低）**: 当前代码行为正确，属于 plan 对代码事实的描述不够完整

### 004-未修复-低-overlong text policy 归属合理但缺少 caller-side 验证点

- **位置**: Plan 的 "Text handling" 段和 Slice 1 overlong 测试
- **问题类型**: 最佳实践偏离
- **当前写法**: "Overlong allowed text is preserved by this policy helper; truncation belongs to display, storage, or budget-specific callers, not to terminal text source selection."
- **反例/失败场景**:
  - Plan 声称 overlong text 应被保留，但 `_text_field()` 函数（`terminal_summary_payload.py:58-82`）对任何长度文本都返回完整字符串——确实不截断。所以"overlong text is preserved"实际上是当前实现的默认行为，没有特殊逻辑。
  - Slice 1 说 "Add tests that overlong final_answer and overlong artifact content are preserved by the source-selection helper"——这个测试实际上只是验证 helper 不截断，与验证"普通长度文本被保留"是同一个代码路径。
  - Plan 没有说明哪些 caller 负责截断，也没有要求 caller-side 测试证明截断确实发生。如果未来有人错误地在 source-selection helper 中添加截断逻辑，测试会捕获；但如果截断逻辑被遗漏在 caller 中，当前 plan 不会发现。
- **为什么有问题**: "Truncation belongs to display, storage, or budget-specific callers" 是一个架构决策，但 plan 没有要求 caller-side 验证。如果 memory projection 的 char cap 或 compact material 的 budget cap 在某处失败，这个 plan 不会发现。
- **直接证据**: Plan 的 Slice 1 overlong 测试只验证 source-selection helper 保留长文本，不验证 caller 的截断行为
- **影响**: 低——plan 正确识别了关注点分离，只是 caller-side 验证不在 scope 内
- **建议改法和验证点**:
  - 在 plan 的 Non-Goals 或 Residual Risk 中显式说明"caller-side truncation 验证不属于本条 scope，由各 caller 自身的测试覆盖"
  - 或者：在 Slice 1 的 overlong 测试中增加一条注释，说明 overlong 测试只覆盖 source-selection 层
- **修复风险（低）**: 只需补充文档说明
- **严重程度（低）**: 不对实施构成阻塞

### 005-未修复-低-memory projection evidence-backed fact 分离测试可能被 skip

- **位置**: Plan Slice 1，"Confirm memory projection does not turn terminal summary / assistant final answer into an evidence-backed fact; only add a focused assertion if current coverage is missing."
- **问题类型**: 测试缺口
- **当前写法**: "only add a focused assertion if current coverage is missing"
- **反例/失败场景**:
  - 当前 `memory.py` 的 `_selected_assistant_item()` 只从 `RUN_SUCCEEDED.final_answer` 构造 `SelectedRecentWindowItem`（role=ASSISTANT, included_reason=SELECTED_RECENT_WINDOW），不创建 `EvidenceBackedFact`。
  - `test_memory_projection.py` (823 行) 覆盖了 memory projection 的很多路径，但**没有显式断言** assistant final answer item 的 `included_reason` 是 `SELECTED_RECENT_WINDOW` 而非 `EVIDENCE_BACKED_FACT`。
  - 如果未来有人错误地添加从 terminal summary 创建 evidence-backed fact 的路径，现有测试可能不捕获。
- **为什么有问题**: Plan 把这条测试设为 conditional ("only if...missing")，但没有先确认现有测试是否覆盖。从代码阅读来看，现有 `test_memory_projection.py` 可能没有显式断言这一点。
- **直接证据**:
  - `memory.py:1625-1642` `_selected_assistant_item` 只创建 `SelectedRecentWindowItem`（非 `EvidenceBackedFact`）
  - `test_memory_projection.py` grep 未发现 "evidence_backed" 与 "terminal_summary" 或 "assistant" 同现的断言
- **影响**: 低——当前代码不会错误创建 evidence-backed fact，但缺少回归保护
- **建议改法和验证点**:
  - Slice 1 应改为 "add a focused assertion that memory projection's selected recent window assistant item has `included_reason=SELECTED_RECENT_WINDOW` (not evidence-backed fact)"
  - 或至少先 grep 确认现有测试是否已覆盖，然后明确记录结论
- **修复风险（低）**: 新增一条断言即可
- **严重程度（低）**: 不对实施构成阻塞

## Plan Review Conclusion

**PASS-WITH-FINDINGS**

Plan 的动机成立、scope 适当、slice sequencing 合理、不违反架构分层、不引入兼容 wrapper 风险。Plan 正确识别了当前代码已部分实现 policy 但缺少完整 policy matrix 测试覆盖的 gap。

5 个 findings 均为低到中等严重程度，不阻塞进入 implementation gate：

- **Finding 001（中）**: read_api 投影路径缺少直接的 policy matrix 验证——typed dataclass 测试不等价于投影逻辑测试
- **Finding 002（低）**: memory.py 使用窄 reader（`assistant_final_answer_text_from_run_payload`）而非完整 continuity resolver，plan 未显式说明此差异
- **Finding 003（低）**: `empty_final_answer` 转为 `RUN_FAILED` 的 Host governance 决策未在 policy matrix 中显式建模
- **Finding 004（低）**: overlong text policy 归属合理，但缺少 caller-side 验证点说明
- **Finding 005（低）**: memory projection evidence-backed fact 分离测试 conditional 措辞可能导致遗漏

建议在进入 implementation gate 前至少修复 Finding 001（在 Slice 1 中明确要求 read_api 投影路径的 policy matrix 断言），并在 plan 中收敛 Open Questions Q1-Q3。
