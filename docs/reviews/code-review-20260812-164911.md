### 1-未修复-中-`_close_handle` 反复取消重试无限循环风险

- **入口/函数**: `_close_handle` → `convert_to_json_bytes` 主方法
- **文件(行号)**: `docling_process_converter.py:641`
- **输入场景**: 外层 event loop 持续注入 `CancelledError`（例如 task group 反复 cancel，或 signal handler 在每个 event loop tick 重入取消），同时 runtime cleanup task 因外部原因长时间未完成
- **实际分支**: `except asyncio.CancelledError` 分支（line 644-647）捕获后 `continue` 重回 `while True`（line 641）
- **预期行为**: cleanup task 必然在有限时间内完成（kill/join/queue close 各步均有有界 timeout），因此重试最终会观察到 `_cleanup_completed = True` 并立即返回；循环在实际上有界
- **实际行为**: 若 runtime cleanup task 因 bug 或极端 OS 状态无法完成，`_close_handle` 的 `while True` 会成为真正无限循环，无超时、无重试上限、无诊断日志记录重试次数
- **直接证据**: line 641 `while True:` 无退出条件，line 644 `continue` 无退避或计数；对比 runtime `_run_cleanup_attempt`（`interruptible_process.py:447-541`）各步均有 bounded timeout，正常场景下 cleanup task 确实会完成，但 `_close_handle` 未防御 cleanup task 不完成的退化场景
- **影响**: 若 runtime cleanup 异常挂起，converter 调用方永久阻塞，无超时保护；系统性风险低（需 runtime bug + 持续取消双重条件）
- **建议改法和验证点**: 增加最大重试次数（例如 100 次）或最大等待时间（例如 30s 总预算），超出后以 `_CloseOutcome(failure=RuntimeError("close retry exhausted"), ...)` 退出；验证点：模拟 close 永久抛 CancelledError 的 fake handle
- **修复风险（低）**: 新增超时后现有 close-before-output、temp cleanup、error priority 语义不变
- **严重程度（中）**: 退化场景概率极低（需 runtime bug），但一旦命中即为无界阻塞，属于应防御而未防御的边界

## Open Questions

1. **line 411-412（`except Exception as exc` 在 `_wait_for_terminal` 调用外围）**: 此路径覆盖 `_wait_for_terminal` 中 `CanceledError`/`DoclingConversionError` 以外的意外异常。当前 coverage 显示未覆盖。问题是：runtime `InterruptibleProcessHandle.wait()` 的异常面究竟是哪些？文档只列出 `ValueError`（非法 timeout）和 `RuntimeError`（未 start）——这两者均在正常流程中不会触发（timeout 为模块常量且 handle 已 start）。若 runtime 未来新增异常类型，当前 catch-all 是正确的，但无法在测试中触发。**是否应保留此 catch-all 作为防御？** —— 建议保留，当前已有正确的错误映射（→CHILD_CRASH），但应确认 `_wait_for_terminal` 异常面与 catch-all 语义一致。

2. **`_validate_conversion_request` 调用 `config.__post_init__()` 第二次**: line 905 显式二次调用 `__post_init__`。计划未明确要求此行为，代码注释说明目的是 "避免绕过初始化得到非法实例"。对于 frozen dataclass，`__post_init__` 已在构造时调用一次，二次调用是纯防御。**是否应改为在 `DoclingConversionConfig` 上提供独立的 `validate()` 方法而非复用 `__post_init__`？** —— 当前行为无害，但复用 dunder 方法作为公开校验入口略显非惯用。

3. **`_read_terminal_result` 中 `exitcode=0` 的 `InterruptibleProcessFailed` 映射为 `IPC_PROTOCOL`**: line 691-692。此映射的语义是 "clean exit without result → IPC loss"。当 runtime 的 worker 线程因 `queue.Full` 或 pickle 失败而无法放入结果消息，但进程本身正常退出（exitcode 0），这会触发。问题是：**exitcode=0 是否可能来自 Docling 内部 catching 了所有异常并调用 `sys.exit(0)`？** —— 由于 child target 在顶层 catch 了 `DoclingRuntimeInitializationError`（→CONVERTER_CONSTRUCTION descriptor）和 `Exception`（→CONVERTER_EXECUTION descriptor）并正常返回，此场景不应发生。但若 child 进程因 OOM killer 被杀死，exitcode 会是非零（→CHILD_CRASH，正确）。此映射成立。
