## Findings

### 1-已修复-低-`_detect_truncation_gaps()` 使用 run 级别而非 tool_call 级别追踪 fetch_more，造成跨工具调用误抑制截断缺口

- **入口/函数**: `_detect_truncation_gaps()` in `utils/analyze_tool_trace_host.py`
- **文件(行号)**: [utils/analyze_tool_trace_host.py:400-440](utils/analyze_tool_trace_host.py#L400-L440)
- **输入场景**: 同一 run 内 tool_call_A 发生 truncation 但用户未发起 fetch_more 续读，tool_call_B 发生了 fetch_more 续读。两工具独立无关。
- **实际分支**: 代码使用 `has_fetch_more_by_run` (dict key 为 `run_id`)，在 421 行检测到任意 tool_call 有 `fetch_more_consumed_cursor` 时，将 `run_id` 对应的条目设为 `True`。在 432 行判断时以 `run_id` 键查找——只要该 run 内任一 tool 有过 fetch_more，该 run 内所有 truncation 工具都被视为已续读。
- **预期行为**: tool_call_A 的 truncation_has_more=True 且无对应 fetch_more 续读，应被识别为截断缺口。仅 tool_call_B 的 fetch_more 不应覆盖 tool_call_A 的判定。
- **实际行为**: tool_call_A 的截断缺口被静默忽略，`TruncationGap` 不出现在输出中。
- **直接证据**: 410 行 `has_fetch_more_by_run: dict[str, bool] = {}` key 为 `run_id` 而非 `(run_id, tool_call_id)`；421 行 `has_fetch_more_by_run[run_id] = True` 在遇任一 fetch_more 时设置；432 行 `if not has_fetch_more_by_run.get(run_id, False)` 按 run 级别判定。
- **影响**: 分析器遗漏真实的截断缺口——实际场景中 tool_call_A 结果被截断且未补齐，但分析报告显示无缺口，可能误导对数据完整性的判断。
- **建议改法和验证点**: 将 `has_fetch_more_by_run` 改为 `dict[tuple[str, str], bool]`，key 为 `(run_id, tool_call_id)`。在 421 行和 424 行对应改 key 为 `(run_id, tool_call_id_for_fetch_more)`。需要注意当前循环中 `fetch_more_consumed` 仅在 `trace_type == "tool_call"` 分支内读取，对应 tool_call_id 即为当前记录的 `tool_call_id`，改法直接。添加测试：同一 run 内 tool_A truncation+无 fetch_more，tool_B 有 fetch_more，断言 tool_A 的 TruncationGap 被正确检出。
- **修复风险（低）**: 局部变量替换，不改变数据结构输出契约，不涉及跨模块接口。
- **严重程度（低）**: 仅影响分析器诊断准确性，不阻塞投影写入、不回写 EventLog，不影响 Engine 运行期行为。

## Open Questions

- `TOOL_FETCH_MORE_FAILED` 事件出现在 `dayu/host/_tool_trace_projection.py:135-137` 的注释中说明不投影。这是有意设计（fetch_more 失败可在 tool_call 记录中通过 `fetch_more_error` 字段反映），但如果 tool_call 记录被覆写时丢失了失败信息，trace 消费者将无法感知 fetch_more 失败。建议确认 `tool_call` 记录更新逻辑确保 `fetch_more_error` 在最终状态中保留。
- `final_response` 记录的 `iteration_id` 恒为空字符串——`FinalAnswerData` 不含此字段。在逐 run 过滤 trace 记录时需要额外处理，是否值得在 `FinalAnswerData` 中增加 `iteration_id` 使记录自包含？

## Residual Risk

- 测试覆盖充分（50 个新测试通过），pyright 0 错误。`_select_jsonl_file()` 的文件滚动逻辑（按 `_MAX_FILE_BYTES ≈ 10MB` 分片）假设序号连续无空洞，在单 writer 场景下安全，但在外部写手或手动删除中间文件时可能回退到错误文件号。当前架构是单 writer，风险可接受。
- `_scrub_provider_secret()` 的 `_PROVIDER_SECRET_KEYS` frozenset 采用白名单模式，新增 provider 的敏感 key 需手动维护此列表。若遗漏，provider 密钥可能以明文写入 JSONL 文件或 raw payload blob。后续考虑从 provider 配置自动派生敏感 key 列表。
- Analyzer 中 `_detect_repeated_tool_calls()` 仅比较 `(run_id, tool_name, arguments_json)`——若同一工具同一参数因结果截断而合理重复调用，也会被标记为重复。这是已知的 analyzer 语义边界，不影响投影正确性。
