## Findings

### 001-未修复-低-S1 hint 清理中 `last_error_code` 语义迁移未明确

- **位置**: S1 Implementation details `_accept_failure_outcome` / `_awaiting_accept_failure_outcome` timeout 分支
- **问题类型**: 契约缺失
- **当前写法**: plan 说 "use `hint=None` for rejected / timed out accept failures"，stop condition 说 "If diagnostics are only available through hint and not through trace/failure metadata, stop and fix diagnostic propagation"。
- **反例/失败场景**: `_accept_failure_outcome` 的 timeout 分支当前 `hint=result.last_error_code or _TOOL_RUNTIME_ACCEPT_TIMEOUT_REASON`。`last_error_code` 是 accept pipeline 返回的最后错误码（如 `"evidence_write_conflict"`）。设为 None 后，若 `message` 字段未包含该信息，LLM 和用户均丢失该诊断。`_awaiting_accept_failure_outcome` timeout 分支同理，且额外丢失 `_hint_with_diagnostic_refs` 中的 base_hint。
- **为什么有问题**: plan 的 stop condition 是防御性的，但未明确 `last_error_code` 应迁移到 `message` 还是只保留在 trace。implementation agent 需要逐一验证每个 timeout 分支的 `message` 是否已覆盖 `last_error_code` 语义。
- **直接证据**: `dayu/host/tool_runtime.py:7527-7533` timeout 分支 `hint=result.last_error_code or _TOOL_RUNTIME_ACCEPT_TIMEOUT_REASON`；`dayu/host/tool_runtime.py:7555-7561` awaiting timeout 分支 `hint=_hint_with_diagnostic_refs(base_hint=result.last_error_code or ..., diagnostic_refs=result.diagnostic_refs)`。
- **影响**: 实施 agent 可能机械地设 `hint=None` 而不验证 `message` 是否已携带 `last_error_code`，导致诊断信息丢失。
- **建议改法和验证点**: 在 plan S1 中为 timeout 分支明确指定：(1) 若 `last_error_code` 不为 None，将其追加到 `message` 尾部（如 `f"tool accept timed out (last_error={result.last_error_code})"`）；(2) 验证点：`grep -n "last_error_code" dayu/host/tool_runtime.py` 确认每个 timeout 路径的 `last_error_code` 已进入 `message` 或 `failure_metadata`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 002-未修复-低-S2 accepted status UNKNOWN 下游 consumer 无显式测试

- **位置**: S2 Stop conditions 及 Tests
- **问题类型**: 测试缺口
- **当前写法**: plan 说 "If a downstream consumer cannot tolerate `UNKNOWN`, stop and fix that consumer to consume typed projection state rather than raw outcome."
- **反例/失败场景**: `dayu/host/read_api.py:1284-1297` 的 `_accepted_result_activity_state` 对 UNKNOWN 走 fallthrough 路径返回 `(FAILED, ERROR)`。这是 fail-closed 设计，但无测试覆盖。`dayu/host/run_input.py:3527` 将 `status.value` 直接插入 LLM prompt（`"完成状态：unknown"`），也无测试。若未来有人修改 `_accepted_result_activity_state` 的 fallthrough 逻辑，UNKNOWN 行为会静默变化。
- **为什么有问题**: plan 的 stop condition 假设 consumer 会 tolerate UNKNOWN，但未要求验证。当前 fallthrough 行为是正确的（fail-closed），但缺少 regression guard。
- **直接证据**: `dayu/host/read_api.py:1297` fallthrough 到 `(FAILED, ERROR)`；全库无 test 覆盖 UNKNOWN → FAILED/ERROR activity mapping。
- **影响**: 低。当前行为正确，但缺少 regression 测试。
- **建议改法和验证点**: 在 S2 tests 中增加一个 test：seed `tool_fact_kind=None` + `raw_tool_outcome=None`，断言 `projection.status is UNKNOWN`，然后断言 `_accepted_result_activity_state(projection)` 返回 `(FAILED, ERROR)`。或在 plan 中记录为 implementation residual，由 controller 在 aggregate validation 时确认。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 003-未修复-低-S3 Fins RESULT buffering 改变 producer 生命周期语义

- **位置**: S3 Implementation details、Stop conditions
- **问题类型**: 状态机漏洞
- **当前写法**: plan 说 "Continue draining until `_DirectStreamProducerDone` so duplicate `RESULT` can be detected"。
- **反例/失败场景**: 当前 `_run_direct_stream` 在 yield 第一个 `RESULT` 后立即 `break`，不等待 producer 线程结束。新行为需要继续 drain queue 直到 producer done。如果 producer 在 emit RESULT 后不退出（例如挂起或继续产出非-RESULT 事件），runtime 会阻塞在 `queue.get()` 上。plan 的 stop condition 覆盖了这个场景（"stop and fix producer termination at Fins runtime owner"），但未要求 implementation agent 先验证当前 producer 的终止行为。
- **为什么有问题**: `_DirectStreamProducerDone` sentinel 是否保证 producer 线程在 emit RESULT 后一定会 put 该 sentinel？需要验证 producer 实现。若 producer 依赖外部 I/O 或有异常路径未 put sentinel，新行为会引入 deadlock。
- **直接证据**: `dayu/fins/ingestion_runtime.py:2643-2719` 的 `_run_direct_stream` 使用 thread + queue 模型；当前 break 后不 drain。
- **影响**: 低。plan 已有 stop condition，但 implementation agent 需要先验证 producer 终止保证。
- **建议改法和验证点**: 在 S3 Implementation details 开头增加一步：先审查 `_DirectStreamProducerDone` 的 put 位置，确认所有 producer 路径（正常完成、异常、RESULT emit 后）均保证 put sentinel。验证点：`grep -n "_DirectStreamProducerDone" dayu/fins/ingestion_runtime.py` 确认 put 位置覆盖所有退出路径。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/严重）**: 低

### 004-未修复-低-`_hint_with_diagnostic_refs` 及相关常量应显式删除

- **位置**: S1 Implementation details
- **问题类型**: 最佳实践偏离
- **当前写法**: plan 说 "remove `_hint_with_diagnostic_refs` if it becomes unused"。
- **反例/失败场景**: `_hint_with_diagnostic_refs` 当前只被 `_awaiting_accept_failure_outcome` timeout 分支调用（line 7555）。S1 将该分支的 `hint` 设为 None 后，该函数变为 dead code。同理 `_TOOL_RUNTIME_DIAGNOSTIC_REFS_HINT_KEY`、`_TOOL_RUNTIME_HINT_SECTION_SEPARATOR`、`_TOOL_RUNTIME_DIAGNOSTIC_REF_SEPARATOR` 三个常量也变为 dead code。"if it becomes unused" 的措辞过于保守，implementation agent 可能跳过清理。
- **为什么有问题**: dead code 违反编码硬约束（禁止兼容性代码），且常量名暗示 hint 中仍可编码 diagnostic refs，可能误导后续开发者。
- **直接证据**: `dayu/host/tool_runtime.py:7496-7512` 函数体；lines 274-276 三个常量；全库无其他调用者。
- **影响**: 极低。dead code cleanup，不影响行为。
- **建议改法和验证点**: 将 "if it becomes unused" 改为 "delete `_hint_with_diagnostic_refs` and its three private constants (`_TOOL_RUNTIME_DIAGNOSTIC_REFS_HINT_KEY`, `_TOOL_RUNTIME_HINT_SECTION_SEPARATOR`, `_TOOL_RUNTIME_DIAGNOSTIC_REF_SEPARATOR`)"。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Residual Risks

1. **Fins producer 终止保证**：S3 的 RESULT buffering 依赖 producer 线程在所有路径上 put `_DirectStreamProducerDone` sentinel。plan 已有 stop condition，但 implementation agent 应先验证。建议跟踪至 S3 实施前 producer lifecycle audit。

2. **UNKNOWN status 在 LLM prompt 中的呈现**：`run_input.py:3527` 将 `status.value` 直接插入 LLM system prompt。`"完成状态：unknown"` 对 LLM 是否足够清晰？这不是 plan 的 bug，但属于 LLM-facing 文本约束的边界。建议在 propagation audit 时确认。

3. **S1 message 质量**：移除 hint 后，`message` 成为 LLM 唯一可读的失败描述。plan 要求 "messages remain business-readable"，但未逐一列出每个 failure helper 的 message 内容。implementation agent 需在 S1 实施时验证每个 message 自足可理解。

4. **`_TOOL_RUNTIME_ACCEPT_REJECTED_REASON` 和 `_TOOL_RUNTIME_ACCEPT_TIMEOUT_REASON` 常量**：hint 设为 None 后，这些常量是否仍被 `error` 或 `message` 引用？若未引用，也应清理。建议在 S1 validation 中 `grep` 确认。

## Conclusion

**pass-with-risks**

Plan 整体质量高：动机成立，owner boundary 正确，3 个 slice 语义连贯，架构边界清晰（contracts / Host projection / Service mapper / Fins runtime / Engine LLM projection），无过度设计（无 resolver framework、无 Fins ledger、无 schema migration），实现细节具体到文件和测试。

4 个 finding 均为低严重程度，不构成 blocker：
- 001 要求 S1 明确 `last_error_code` 语义迁移路径，避免诊断信息丢失。
- 002 要求 S2 增加 UNKNOWN 下游 consumer 的 regression test 或记录为 residual。
- 003 要求 S3 先验证 producer 终止保证再实施 buffering。
- 004 要求显式删除 dead code 而非条件性删除。

这些 finding 均可在 implementation 阶段解决，不需要 plan 重写。
