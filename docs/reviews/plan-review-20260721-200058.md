## 1. 4 个 utils caller 真实性核验

### 1.1 代码证据

`rg -n 'watch_session_events\(' utils/` 输出：

```
utils/smoke_host_public_r03_semantic_ownership.py:405
utils/smoke_host_public_conversation_memory.py:437
utils/smoke_host_public_conversation_memory_scenarios.py:3011
utils/smoke_host_public_conversation_memory_scenarios.py:3110
utils/smoke_host_public_multiturn.py:388
```

共 5 个 callsites，分布在 4 个文件中（`conversation_memory_scenarios.py` 有 2 个）。

### 1.2 调用模式分析

所有 5 个 callsites 遵循同一模式：

```python
async with open_host(assembly.options) as host:
    session = await host.ensure_session(...)
    watcher = host.watch_session_events(session.session_id)  # ← 同步调用
    ...
    result = await _run_round(host=host, watcher=watcher, ...)
```

其中 `_run_round` 将 `watcher` 参数标注为 `AsyncIterator[HostSessionEvent]`，内部调用 `_next_terminal_for_run(watcher, ...)` 执行 `async for event in iterator:`。

### 1.3 Owner-boundary 判定

`Host.watch_session_events(...)` 的 async public contract 由 `dayu.host.api` 拥有。plan §4.2.4 明确：

> `Host.watch_session_events(session_id)`：public async factory，返回 `HostSessionEventIterator`。只有 successful await return 后订阅才对调用方生效。

当前 4 个文件中所有 5 个 callsites 都执行同步调用 `watcher = host.watch_session_events(...)`，把返回的 coroutine 对象直接传给期望 `AsyncIterator[HostSessionEvent]` 的 consumer。这会导致：

- pyright type error（coroutine 不满足 `AsyncIterator` protocol）
- runtime failure（coroutine 不能 `async for`）

**机械 `await`（`watcher = await host.watch_session_events(...)`）是正确 owner-boundary fix**：caller 消费的是 Host public API 的 activation contract，`await` 是 consuming async factory 的唯一正确方式。这不是下游兼容 shim、不是 `cast`/`getattr` 绕过、不是同步 compatibility branch。

### 1.4 返回值兼容性

`await host.watch_session_events(...)` 返回 `HostSessionEventIterator`（plan §4.2.3 定义），该 Protocol 声明 `__aiter__() -> HostSessionEventIterator`、`__anext__() -> HostSessionEvent`、`async aclose() -> None`。utils 文件的 helper 函数（`_run_round`、`_next_terminal_for_run`）参数类型为 `AsyncIterator[HostSessionEvent]`。`HostSessionEventIterator` 在结构上满足 `AsyncIterator[HostSessionEvent]` 的 `__aiter__`/`__anext__` 要求，额外的 `aclose()` 不造成冲突。

**判定：✓ PASS**。4 个文件（5 个 callsites）是 async factory contract 的真实 direct callers。机械 `await` 是正确 owner-boundary fix，无下游兼容问题。

## 2. Allowed Scope 精确性核验

### 2.1 Plan 当前措辞

§7 S1 "Allowed utils public smoke callers"：

> 上述4个文件只允许把async factory/public iterator contract机械传播到现有direct callsites并显式`await`；不得修改smoke场景、断言、数据流、Service relay或任何其它行为。

§7 S1 Exact changes #8：

> 4个utils direct callers只执行上一段授权的机械传播。

§7 S1 Non-goals：

> 禁止同步compatibility、lazy attach、下游识别或兼容coroutine，以及`cast`/`getattr` shim；caller必须直接消费async factory/public iterator contract。

### 2.2 边界分析

| 允许 | 禁止 |
|---|---|
| 在 `watch_session_events(...)` callsite 加 `await` | 修改 smoke 场景/断言/数据流 |
| 机械传播 async factory/public iterator contract | Service relay 修改 |
| — | 同步 compatibility branch |
| — | lazy attach / pending future |
| — | 下游 coroutine 兼容识别 |
| — | `cast`/`getattr` shim |

边界精确、可执行、可验证。negative scope（禁止项）逐项枚举，不给 implementation agent 留下模糊解释空间。

### 2.3 多 callsite 文件覆盖

`smoke_host_public_conversation_memory_scenarios.py` 有 2 个 callsites（line 3011, 3110），分属不同的 `run_*` 函数（一个是主 smoke runner，另一个是 deterministic compact runner）。plan 说 "4个文件" 和 "现有direct callsites"，语义上覆盖文件内所有 callsites，不限于每文件一个。措辞可更精确（"上述4个文件中的所有direct callsites"），但 "direct callsites" 是复数且在 §5.2 闭集清单中每文件被列出一次，实施时 `rg 'watch_session_events\(' utils/` 会自然发现全部 5 个 callsites。**不构成 material finding**。

**判定：✓ PASS**。allowed scope 足够精确，禁止项明确。
