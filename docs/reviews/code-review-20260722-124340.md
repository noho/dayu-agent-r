## Findings

### 001-未修复-中-Windows busy errno 白名单与测试 fake 使用错误 OS errno

- **入口/函数**: `native_mutex._is_busy_error` / `native_mutex._lock_file_descriptor`
- **文件(行号)**: `dayu/runtime/native_mutex.py:298`, `tests/runtime/test_native_mutex.py:133-150`
- **输入场景**: Windows 平台上 `msvcrt.locking(file_descriptor, LK_NBLCK, 1)` 遇到文件已被另一进程锁定时
- **实际分支**: `_lock_file_descriptor` 捕获 `OSError`，调用 `_is_busy_error(exc, WINDOWS_LOCKING)` 判断 `error.errno in {errno.EACCES, errno.EDEADLK}`
- **预期行为**: Windows `msvcrt.locking` 在 contention 时抛出 `BlockingIOError`，其 `errno` 设置为 `errno.EDEADLK`（MSVC `_locking` 文档与 CPython `PC/msvcrtmodule.c` 一致）。白名单应以 `EDEADLK` 为主要 busy 信号
- **实际行为**: 代码白名单包含 `EACCES` 和 `EDEADLK`，因此实际运行时 `EDEADLK` 会被正确匹配。但测试 `_BusyWindowsLocking` 使用 `errno.EACCES`（行 150）而非 `errno.EDEADLK`，导致测试通过的路径不是真实 Windows contention 路径。implementation artifact 声称"Windows backend 已通过强类型 fake 验证 lock-byte、nonblocking/busy、unlock、truncate/close failure 路径"，但 busy 路径验证基于错误的 errno
- **直接证据**: `dayu/runtime/native_mutex.py:298` → `return error.errno in {errno.EACCES, errno.EDEADLK}`；`tests/runtime/test_native_mutex.py:150` → `raise OSError(errno.EACCES, "lock violation")`；CPython `PC/msvcrtmodule.c` locking 实现使用 `EDEADLK`
- **影响**: 生产代码在 Windows 上能正确工作（因为 `EDEADLK` 在白名单中），但测试未验证真实路径。若未来有人从白名单移除 `EDEADLK`（因为测试只证明 `EACCES` 路径），Windows busy 检测将静默失效，contention 被错误包装为 `StrictNativeMutexUnavailableError` 而非返回 `None`
- **建议改法和验证点**:
  1. 将 `_BusyWindowsLocking.locking` 改为 `raise OSError(errno.EDEADLK, "lock violation")`
  2. 同步将 `test_windows_busy_and_truncate_failure_are_distinct` 中 busy 断言路径验证为 `EDEADLK`
  3. 可选：在 `_is_busy_error` 的 Windows 分支添加行内注释说明 `EDEADLK` 来源
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 002-未修复-低-release_host_close 首次 error 后可重试但不区分已处理 record

- **入口/函数**: `HostSessionAttachmentRegistry.release_host_close`
- **文件(行号)**: `dayu/host/session_attachment.py:560-591`
- **输入场景**: `release_host_close` 首次调用时某个 record 的 `mutex_handle.close()` 抛出 `StrictNativeMutexUnavailableError`
- **实际分支**: 行 578-579 捕获 `_release_record` 返回的 error 并保存为 `first_error`；行 587-588 检查 `self._records` 是否为空来设置 `_host_close_released`；行 589-590 抛出 `first_error`
- **预期行为**: Host close 失败后应允许 caller 重试；重试时应快速识别已处理 record 避免重复操作
- **实际行为**: 首次失败后 `_host_close_released` 保持 `False`，`_host_close_drained` 保持 `True`。重试时跳过 `begin_host_close`（行 535-536），跳过 `drain_host_close`（行 571-572），重新进入 `release_host_close`。`_release_record` 对已 CLOSED record 返回 `close_error`（行 759-760），对 CLOSING + prior error 的 record 设置 `close_completed` 并返回缓存 error（行 764-765）。行为正确且幂等，但每次重试仍遍历全部 record 并 await 所有 `close_task`
- **直接证据**: `session_attachment.py:587-588` → `if not self._records: self._host_close_released = True`；`session_attachment.py:759-760` → `if record.state is CLOSED: return record.close_error`；`session_attachment.py:763-765` → prior error 缓存路径
- **影响**: 仅影响重试效率，不影响正确性。对于典型 Host 生命周期（少量 Session），遍历开销可忽略
- **建议改法和验证点**: 当前行为可接受。若未来需要区分"部分成功"状态，可增加 `_release_attempted` 标志跳过已处理 record
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
