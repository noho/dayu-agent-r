# Plan Review: UF-FIX07 multi-file-primary-and-collision

## Reviewed target

- **Plan artifact**: `docs/gateflow/uf-fix07-multi-file-primary-collision-plan-20260815.md`
- **Goal confirmation**: `docs/gateflow/uf-fix07-multi-file-primary-collision-goal-confirmation-20260815.md`
- **Scope**: primary selector contract、validated selection、deterministic asset identity、storage primary、process consumption

## Review posture

第一路独立 adversarial reviewer。使用 architecture boundary、best-practice、optimal-solution、overengineering、overcoupling lenses。

## Assumptions tested

1. `primary_selectors` tuple 是保留 CLI 重复 `--primary` cardinality 的唯一 owner 最优形状。
2. `_validate_fins_upload_filing_static` 可以在 workspace read 前完成所有 primary 校验。
3. SHA-256 path-derived identity 满足 stable/path-free/security 要求。
4. `_PendingFileAsset` 扩展与 `_build_stored_file_entry` 投影可以正确传递 `original_filename`/`derived_from`。
5. storage snapshot `_parse_snapshot_files` 的 duplicate name 检查与新的 identity scheme 兼容。
6. `process_filing` 和 read runtime 不需要修改。
7. material 行为不被无意改变。
8. 100 文件原子性由现有 batch commit/rollback 保证。

## Findings

### 1-未修复-低-`FinsUploadUsageCode` 新增固定消息的实现路径未明确

- **位置**: §6.2 usage codes/messages
- **问题类型**: 不可直接实施
- **当前写法**: plan 声明新增五个 `FinsUploadUsageCode` 成员，每个有固定的中文消息（<=240 字符），且"不得复用 generic invalid argument 掩盖这些语义"。
- **反例/失败场景**: 现有 `FinsUploadUsageCode` 使用 `message_template` 模板模式（如 `"filing 文件数量超过上限：{limit}"`），新 code 使用固定消息而非模板。实现 agent 可能不确定是添加可选 `message_template` 字段、创建新的固定消息映射表、还是复用模板但不传参数。
- **为什么有问题**: 不同实现路径会导致不同的 `FinsUploadUsageError` 构造方式和 `_USAGE_MESSAGES` 字典结构，影响错误消息的一致性和可测试性。
- **直接证据**: `ingestion_runtime.py` 中 `FinsUploadUsageCode` 枚举和 `_USAGE_MESSAGES` 字典的现有模式是 template-based。Plan 的五个新 code 使用固定字符串。
- **影响**: 实现 agent 可能需要自行设计消息分发机制，导致不同 agent 产出不同结构。
- **建议改法和验证点**: 在 plan 中明确新 code 的消息是固定字符串还是模板。如果是固定字符串，说明 `_USAGE_MESSAGES` 的扩展方式（如新增 `_FIXED_USAGE_MESSAGES` 或在现有字典中使用无参数模板）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 2-未修复-低-`_PendingFileAsset` 字段扩展的传递链未完全显式

- **位置**: §6.6 asset identity 与 `_build_stored_file_entry` 投影
- **问题类型**: 不可直接实施
- **当前写法**: plan 要求"扩展 `_PendingFileAsset` 为严格 typed preparation fact"，新增 `original_filename` 和 `derived_from` 字段。同时要求 `_build_stored_file_entry()` 投影这些字段到 storage entry。但 plan 未明确 `_build_original_assets` 和 `_build_pending_assets` 如何填充这些新字段。
- **反例/失败场景**: 实现 agent 可能在 `_PendingFileAsset` 上添加字段但忘记在 `_build_original_assets` 中填充 `original_filename`（因为当前代码只设置 `name=file_path.name`），导致 `original_filename` 为 `None` 或缺失。
- **为什么有问题**: `_build_original_assets` 是 original asset 的唯一构造点。如果它不填充 `original_filename`，`_build_stored_file_entry` 就没有数据可投影。
- **直接证据**: `docling_upload_service.py:721-729` 当前 `_build_original_assets` 只设置 `name=file_path.name`，无 `original_filename` 字段。
- **影响**: storage entry 缺少 `original_filename`，用户无法理解文件来源。
- **建议改法和验证点**: 在 plan 中明确 `_build_original_assets` 需要将 `file_path.name` 同时赋给 `name`（改为 identity）和 `original_filename`（保留 basename）。类似地，`_build_pending_assets` 中的 derived asset 需要从对应的 original asset 继承 `original_filename`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 3-未修复-低-`file_uploaded` 事件的 `name` 投影变更需显式说明

- **位置**: §6.6 用户事件投影
- **问题类型**: 最佳实践偏离
- **当前写法**: plan 声明"`file_uploaded` 用户事件的 `name` 使用 `original_filename`"。但当前 `_store_upload_assets` 中 `file_uploaded` 事件使用 `asset.name`（即 storage identity）。
- **反例/失败场景**: 实现 agent 可能只修改 `_build_stored_file_entry` 而忘记修改 `_store_upload_assets` 中的 `file_uploaded` 事件构造，导致用户事件仍然显示 SHA-256 identity 而非可读文件名。
- **为什么有问题**: 用户事件是用户理解上传状态的主要途径。如果事件显示 `original-a1b2c3...x7y8z9.pdf` 而非 `report.pdf`，用户体验显著下降。
- **直接证据**: `docling_upload_service.py:543-554` 当前 `file_uploaded` 事件使用 `name=asset.name`。
- **影响**: 用户/LLM 看到不可读的 identity 而非文件名。
- **建议改法和验证点**: plan 已声明此要求，但应确认实现 agent 会将 `_store_upload_assets` 中的 `file_uploaded` 事件的 `name` 从 `asset.name` 改为 `asset.original_filename`。在 Slice 3 tests 中增加断言验证事件 `name` 是可读 basename。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 4-未修复-低-Slice 2 CLI `--primary` help 文案需与 tool schema 同步验证

- **位置**: §6.4 CLI `--primary`、§6.5 LLM-facing tool `primary`
- **问题类型**: 最佳实践偏离
- **当前写法**: plan 要求 CLI help 和 tool schema 都从 `project_fins_upload_format_text()` 消费文案，但未明确在 Slice 2 tests 中断言二者的文案一致性。
- **反例/失败场景**: 如果 `project_fins_upload_format_text()` 只更新了 `filing_files` 而没有新增 `primary` 相关文案字段，CLI help 和 tool schema 可能各自硬编码不同的 primary 规则描述。
- **为什么有问题**: 两个入口的规则描述不一致会导致用户和 LLM 对 primary 规则的理解不同。
- **直接证据**: `upload_format_contract.py:549-588` 当前 `project_fins_upload_format_text()` 返回 `FinsUploadFormatTextProjection`，只有 `filing_files`、`material_files`、`upload_tool_files` 三个字段。Plan 要求新增 primary 规则，但未明确是否需要新增字段或修改现有字段。
- **影响**: CLI 和 tool schema 的 primary 规则描述可能不一致。
- **建议改法和验证点**: 明确 `FinsUploadFormatTextProjection` 是否需要新增 `primary` 字段，或 primary 规则是否嵌入现有 `filing_files`/`upload_tool_files` 字段。在 tests 中断言 CLI `--primary` help 和 tool schema `primary` description 包含相同的规则关键词。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/严重）**: 低

## Architecture boundary review

- **分层**: plan 严格遵守 `UI(CLI) -> Service -> Fins` 分层。CLI 只做机械投影，Service 只传递，Fins validator 是唯一校验 owner。
- **依赖方向**: 无反向依赖。`dayu.runtime`、`dayu.engine`、`dayu.host`、`dayu.service` 均不被修改。
- **Storage boundary**: storage public protocol 不变。`_PendingFileAsset` 是 service-internal 类型，`_build_stored_file_entry` 是 private helper。新增的 `original_filename`/`derived_from` 只进入 storage metadata，不改变 storage protocol。
- **Schema boundary**: tool schema 变更（新增 `primary` 字段、`maxItems`）不涉及 Engine/Host contract，因为 `ToolParametersSchema` 已支持这些属性。

## Best-practice review

- **Testability**: 每个 slice 有明确的测试文件和 assertions。覆盖 happy path 和 failure path。
- **Maintainability**: identity helper 是模块级私有函数，使用 `Final` 常量。无全局 registry。
- **Failure handling**: 所有静态错误在 workspace read 前拒绝。batch failure 使用现有 rollback 机制。
- **Minimal dependency**: 只修改 Fins 内部模块，不引入新外部依赖。

## Optimal-solution review

- `primary_selectors` tuple 方案优于 `Path | None`：保留了 CLI 重复 occurrence 的原始 cardinality，允许 validator 一次拒绝。
- SHA-256 path-derived identity 优于 UUID/sequence/basename：确定性、无碰撞、无路径泄漏、request-order-independent。
- 删除 `from_upsert_paths` 而非保留兼容 wrapper：符合项目"禁止兼容性代码"约束。

## Overengineering review

- 无过度设计。plan 只在三个现有 owner boundary 增加必要事实，不建立新层或新抽象。
- identity namespace `"fins-upload-asset-v1"` 为未来 schema 演进预留，但不增加当前复杂度。

## Overcoupling review

- 四个 slice 的依赖链合理：contract → projection → storage → docs。
- 每个 slice 的 allowed files 限制严格，不会跨层穿透。
- material 复用同一 identity helper 是消除重复实现，不是过度耦合。

## Plan Review Conclusion

**pass-with-risks**

Plan 设计合理、证据充分、owner 边界清晰、slice 划分得当。四个低严重度 findings 均为实现细节层面的澄清需求，不构成结构性 blocker。实现 agent 在执行时应注意：

1. `FinsUploadUsageCode` 新增固定消息的扩展方式需与现有 template 模式保持一致。
2. `_PendingFileAsset` 的 `original_filename` 字段必须在 `_build_original_assets` 中填充。
3. `_store_upload_assets` 中的 `file_uploaded` 事件必须使用 `original_filename` 而非 `asset.name`。
4. `FinsUploadFormatTextProjection` 的 primary 文案字段结构需在实现前确定。
