## Findings

### Finding 1 — 中风险：runner 异常丢失原始 traceback，无诊断日志

**文件**: [agent.py:537-544](dayu/engine/agent.py#L537-L544)

```python
except Exception as exc:
    self._last_iteration_state.failure_candidate = RunFailedData(
        error_code=_ERROR_RUNNER_EXCEPTION,
        message=type(exc).__name__,
        recoverable=False,
    )
```

当 Runner 执行过程中抛出异常时，只捕获了 `type(exc).__name__`（如 `RuntimeError`），原始异常的 `message`、`traceback` 全部丢失，且没有任何 `_LOGGER` 调用记录该异常。

**后果**: 生产环境中 Runner 异常（如网络库内部错误、JSON 解析异常）发生时，`run_failed` 事件只携带 `"RuntimeError"` 这样的类型名，无法定位根因。对比 `_close_runner_once` 中 close 失败有 `_LOGGER.warning`，此处是诊断盲区。

**建议**: 在 `except` 分支增加 `_LOGGER.warning("agent.runner_exception run_id=%s exc=%s", ..., exc_info=True)` 或至少把 `str(exc)` 写入 `RunFailedData.message`。

### Finding 2 — 中风险：`_fallback_after_tools` RAISE_ERROR 模式用 error_code 当 message

**文件**: [agent.py:936-944](dayu/engine/agent.py#L936-L944)

```python
if mode is AgentFallbackMode.RAISE_ERROR:
    yield await self._make_failed_or_cancelled_terminal_with_close(
        RunFailedData(
            error_code=error_code,
            message=error_code,  # 与 error_code 完全相同
            recoverable=False,
        )
    )
```

`message` 直接使用 `error_code` 常量值（如 `"max_iterations_exceeded"`、`"consecutive_failed_tool_batches"`），不是人类可读的消息。

**后果**: Host 或上层 UI 展示 `RunFailedData.message` 时，用户看到的是内部错误码而非可理解的描述。对比 FORCE_ANSWER 路径的 `_FORCE_ANSWER_EMPTY_MESSAGE` 有清晰描述，RAISE_ERROR 路径缺失。

**建议**: 为 RAISE_ERROR 路径提供独立的可读 message，例如 `"agent policy max_iterations exhausted"` / `"consecutive failed tool batches threshold reached"`。

### Finding 3 — 低风险：`_classify_iteration` 对 final answer 空内容未做归一化

**文件**: [agent.py:745-754](dayu/engine/agent.py#L745-L754)

```python
content = state.completed_content
if content is None:
    content = "".join(state.content_chunks)
filtered = finish_reason is FinishReason.CONTENT_FILTER
return _FinalDecision(
    content=content,  # 可能是 ""
    ...
)
```

对于 tool calls 路径，代码有 `if content == "": content = None` 归一化（[agent.py:718-719](dayu/engine/agent.py#L718-L719)）。但对于 final answer 路径，空字符串 `""` 会直接进入 `FinalAnswerData(content="")`。`_run_force_answer` 有 `if decision.content == ""` 检查，但普通迭代路径没有。

**后果**: 普通迭代中模型产出空内容时，`FinalAnswerData.content` 为 `""` 而非 `None`。语义上空内容与无内容不同，但当前行为是否符合预期需确认。force-answer 和普通迭代对此的处理不一致。

**建议**: 统一空内容处理策略。如果 `""` 应视为有效内容则两处都保留；如果 `""` 应视为无内容则两处都归一化为 `None`。

### Finding 5 — 信息：`_PlainJsonValue` TypeAlias 与运行时行为的类型不一致

**文件**: [agent.py:134-136](dayu/engine/agent.py#L134-L136)

```python
_PlainJsonValue: TypeAlias = (
    None | bool | int | float | str | list["_PlainJsonValue"] | dict[str, "_PlainJsonValue"]
)
```

`_plain_json_value` 对 `list` 输入返回 `list`，对 `Mapping` 输入返回 `dict`，语义正确。但 `JsonValue` 包含 `Sequence`（含 `tuple`），而 `_plain_json_value` 只检查 `isinstance(value, list)`，不检查 `tuple`。若传入 `tuple`，会 fall through 到 `return value`，返回原始 `tuple`。

**后果**: `json.dumps` 可以正常序列化 `tuple` 为 JSON array，运行时无异常。但返回值类型标注为 `_PlainJsonValue`（不含 `tuple`），pyright 不会报错因为 `tuple` 是 `JsonValue` 的子类型。这是一个类型标注与运行时行为的微小不一致，不影响正确性。

**建议**: 无需修改。`json.dumps` 对 `tuple` 的处理是 Python 标准行为，当前实现在运行时正确。

### Finding 6 — 信息：`_run_runner_iteration` 和 `_run_force_answer` 中的 terminal 检查是死代码

**文件**: [agent.py:354-362](dayu/engine/agent.py#L354-L362), [agent.py:978-986](dayu/engine/agent.py#L978-L986)

```python
async for event in self._run_runner_iteration(...):
    yield event
    if self._is_terminal(event):  # 永远不会为 True
        return
```

`_run_runner_iteration` 只产出 `ITERATION_STARTED`、`RUNNER_CONTENT_DELTA`、`RUNNER_REASONING_DELTA`、`RUNNER_CONTENT_COMPLETED`、`RUNNER_USAGE_RECORDED`、`PROVIDER_PROTOCOL_ERROR`、`RUNNER_DONE`，这些都不是 terminal 事件。`_is_terminal` 检查 `FINAL_ANSWER`、`RUN_FAILED`、`RUN_CANCELLED`、`RUN_SUSPENDED`，永远不会匹配。

**后果**: 无功能影响。这是防御性编程，但如果 `_run_runner_iteration` 将来被修改为产出 terminal 事件，这个检查会生效。当前作为安全网保留是合理的。

**建议**: 无需修改。可选添加行内注释说明意图。
