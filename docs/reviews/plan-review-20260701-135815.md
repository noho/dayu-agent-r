## Review Summary

The plan is well-structured, evidence-driven, and correctly scoped within Host architecture boundaries. The three-slice decomposition (durable claim/backoff primitive → supervisor lifecycle → open_host integration) has clear dependency order and each slice delivers an independently verifiable behavioral closure. The architectural decision to extend the wait record row rather than introduce a separate claim table is defensible given the 1:1 ownership relationship.

However, the plan has one high-severity finding where a claimed invariant (terminal resolve must clear poll claim fields) is not mapped to any concrete implementation step in the slice, creating risk that an implementation agent would add the columns but forget the terminal-clear path. Two medium findings address underspecified CAS race handling and the missing-adapter indefinite-retry problem. Below medium, the residual risks are acknowledged by the plan itself or are low-impact.

## Findings

### F01-未修复-高-terminal-resolve-clearing-claim-fields-gap

- **位置**: Slice 1 "Exact changes" (lines 362-379), Slice 1 "Required CAS invariants" (line 164-165)
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan 在 line 164-165 声明 invariant："Terminal wait record transitions in `resolve_wait` must clear poll claim fields so terminal rows are not left with active in-flight diagnostics." 该 invariant 正确且必要，但 Slice 1 的 "Exact changes" 条目中**没有显式列出**更新 `_mark_wait_record_terminal_row` 或其等价 UPDATE SQL 来清空新增的 poll claim 字段。
- **反例/失败场景**: Implementation agent 按 Slice 1 指令添加了 `poll_claim_id`、`poll_claim_owner_id` 等列到 `host_wait_records`，更新了 `read_wait_records_for_poll_observation` 查询，增加了 claim/release helpers，并修改了 `poll_once()`。但由于 "Exact changes" 没有提到 terminal resolve 路径的清空动作，agent 可能漏掉对 `_mark_wait_record_terminal_row`（`state.py:5408`）的修改。结果：resolved/failed/lost 的 wait record 行上残留僵尸 `poll_claim_id`、`poll_claimed_at` 等字段。这不会导致功能错误（因为这些行不再被 poll 查询选中），但违反计划自己的 invariant，且会使 `poll_claim_expires_at` 在终端行上无限期存在，混淆 operator 通过 diagnostic query 理解 wait 生命周期。
- **为什么有问题**: Plan 声明的正确性 invariant 没有对应的实现步骤。Slice 1 的 "Exact changes" 列表应当逐项映射到 invariant，但第 164-165 行的 invariant 在 362-379 行没有对应条目。Implementation agent 不应该从 invariant 自行推断需要修改哪些函数。
- **直接证据**:
  1. Plan line 164-165: "Terminal wait record transitions in `resolve_wait` must clear poll claim fields so terminal rows are not left with active in-flight diagnostics."
  2. Plan lines 362-379 (Slice 1 Exact changes): 列出的修改包括 add columns, extend WaitRecordRow, replace read path, add release helpers, update poll_once()。**未提及** `_mark_wait_record_terminal_row` 或任何 terminal 路径的清空动作。
  3. 当前代码 `state.py:5408-5468` (`_mark_wait_record_terminal_row`): UPDATE 只设置 `status`, `resolve_idempotency_key`, `resolve_semantic_digest`, `updated_*`, `terminal_at`。新增 poll claim 字段后，此 SQL 不会自动清空它们。
- **影响**: 实施 Agent 跑偏 / 后续返工 — 终端行残留僵尸 claim 字段，虽不影响功能正确性但违反计划 invariant，需在 review 或 aggregate deepreview 阶段发现并修复。
- **建议改法和验证点**:
  1. 在 Slice 1 "Exact changes" 中显式增加一条："Update `_mark_wait_record_terminal_row` to also set `poll_claim_id=NULL, poll_claim_owner_id=NULL, poll_claimed_at=NULL, poll_claim_expires_at=NULL` when transitioning a wait record to terminal status."
  2. 在 Slice 1 tests 的 "terminal wait transition clears claim fields" 中添加断言：resolved wait record 的 poll claim 字段全部为 NULL。
  3. 同步检查 `mark_wait_record_failed_row`、`mark_wait_record_lost_row`、`mark_wait_record_cancelled_row` 是否都复用了 `_mark_wait_record_terminal_row`（它们确实复用，`state.py:2453`、`state.py:2490`），所以修改一处即可。
- **修复风险（低）**: 修改是机械性的——在 UPDATE 的 SET 子句中增加四列 NULL。
- **严重程度（高）**: 高，因为这是 plan 自身声明的正确性 invariant，且缺失会导致 invariant 系统性违反。但功能影响有限（终端行不再被 poll 选中，僵尸字段仅影响 diagnostics）。

### F02-未修复-中-read-then-claim-race-underspecified

- **位置**: Slice 1 "Exact changes" (lines 366-368), "Data flow / state transitions" (lines 382-384)
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: Plan 说 "claim only eligible waiting poll rows... allow takeover only when poll_claim_expires_at <= now; set claim fields by CAS in a write transaction" (lines 367-370)。Data flow 写 "read eligible wait rows -> CAS set poll_claim_id / owner / claimed_at / expires_at" (lines 383-384)。
- **反例/失败场景**: 当前 `poll_once()` 通过 `transaction_runner.run_read(...)` 读取 eligible rows（`wait_adapter.py:420-422`），然后在 transaction 外逐个处理。两个进程的 poller 可能同时执行 `run_read` 读到相同的 eligible rows。每个进程随后在自己的 write transaction 中执行 CAS UPDATE（例如 `UPDATE host_wait_records SET poll_claim_id=?, ... WHERE wait_id=? AND (poll_claim_id IS NULL OR poll_claim_expires_at <= ?)`）。只有一个进程的 UPDATE 匹配 1 行（CAS 成功），另一个匹配 0 行（CAS 失败）。Plan 没有描述 CAS 失败时的处理流程：是否静默跳过该 wait、是否递增 `claim_conflicts` counter、是否需要重读 wait record 以确认是否被另一个 poller 已 resolve。
- **为什么有问题**: Plan 在 line 398-402 描述了 "Stale claim release returns CAS conflict and must not clear a newer claim"，但没有对称地描述 claim acquisition 的 CAS 冲突处理。测试 "two poller instances: second does not call adapter while first claim is active" 隐含了正确行为，但不指定 CAS 冲突在 `poll_once()` 内部的 exact code path（是 `continue` 到下一个 record？还是返回特定 result 字段？），implementation agent 需要自行设计这个分支。
- **直接证据**:
  1. 当前 `poll_once()` 在 line 420-422 使用 `run_read` 读取，在 line 429-498 的 for 循环中处理。新方案在读取后增加了 CAS claim 步骤，但读取仍在 write transaction 之外。
  2. Plan line 372 只说 "claim before adapter calls"，未描述 claim 失败时的分支。
  3. Plan line 367-370 描述了 claim 的 WHERE 条件（unexpired or null），但不描述 execute() 返回 rowcount=0 时的处理。
- **影响**: 实施 Agent 跑偏 — implementation agent 可能在 CAS 失败时抛出异常而非静默跳过，或者错误地认为 CAS 失败意味着 wait 已 resolve 而跳过 backoff release。最坏情况：CAS 失败时 agent 没有 release claim（因为根本没拿到），也没有更新 diagnostics，导致 `claim_conflicts` counter 不准确。
- **建议改法和验证点**:
  1. 在 Slice 1 "Exact changes" 或 "Error handling" 中增加一条："CAS claim acquisition returning 0 updated rows means another poller holds an active claim. Treat it as a claim conflict: skip adapter call for this wait, increment claim_conflicts diagnostic counter, and continue to next wait."
  2. 对应的测试应覆盖：两个 poller 同时尝试 claim 同一 wait，只有一个成功调用 adapter，另一个记录 claim_conflict 并跳过。
  3. 测试还应覆盖：claim conflict 后 release 逻辑不得执行（因为没有 claim_id 可释放）。
- **修复风险（低）**: 只需在 error handling 段增加一个明确的处理分支描述。
- **严重程度（中）**: 中等，因为 CAS 语义本身是明确的（SQLite UPDATE 返回 rowcount），问题只在 plan 对 failure branch 的描述不够具体，implementation agent 大概率能自行做出正确选择，但缺少 plan 级明确指引增加了 review 时发现偏差的几率。

### F03-未修复-中-missing-adapter-indefinite-retry

- **位置**: Slice 1 "Error handling" (line 398), Slice 2 "Error handling" (lines 508-515)
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: Plan line 398: "Missing adapter is a retryable poller error with backoff; it must not call resolve_wait." Plan 的其他部分没有为永久缺失 adapter 的 wait record 定义 terminal outcome。
- **反例/失败场景**: 假设一个 wait record 的 `adapter_key` 指向某个被部署环境移除的 adapter（例如配置错误、provider 下线）。Production poller 在每次循环中都会选中该 wait，发现 adapter 为 None，递增 `poll_backoff_attempts`，设置 `poll_next_observe_at` 到未来，然后跳过。下一轮 `poll_next_observe_at` 到期后，重复相同流程。Wait 永远停留在 WAITING 状态，持续消耗 poller 资源（每轮都要查询、claim、发现 missing adapter、release with backoff），且 `poll_backoff_attempts` 无限增长直到达到 `backoff_max_delay_seconds`，之后以最大间隔无限重试。
- **为什么有问题**: Plan 已经在 wait row 上设计了 `poll_backoff_attempts`、`poll_last_outcome` 和 `poll_last_error_code`（lines 126-129），这些字段足以支持 "max retries exceeded" 判定。不定义 terminal 条件意味着生产部署中配置错误会导致静默资源泄漏——wait 永久挂起，poller 每轮浪费一个 claim/release 事务周期。这与 plan 自身的 success signal "Repeated not-ready, missing adapter, adapter exception... are throttled by a Host-owned backoff policy with finite maximum delay" (line 40) 存在语义张力：backoff 最大延迟是有限的，但重试次数是无限的。
- **直接证据**:
  1. Plan line 40: "backoff policy with finite maximum delay" — 只限制了 delay，不限制总重试次数。
  2. Plan line 398: "Missing adapter is a retryable poller error with backoff."
  3. Plan lines 126-129: 存在 `poll_backoff_attempts` 和 `poll_last_error_code` 字段，但 plan 没有定义 `max_backoff_attempts` 或等价 terminal 条件。
  4. Plan line 179-181 (`WaitPollerRuntimePolicy`): 包含 `backoff_initial_delay_seconds`、`backoff_multiplier`、`backoff_max_delay_seconds`，但没有 `max_backoff_attempts` 或 `max_adapter_error_retries`。
- **影响**: 风险后移 — 永久缺失 adapter 的 wait 变为静默资源泄漏，需要 operator 通过 diagnostics 发现 `missing_adapter` 持续计数增长后手动干预。目前不阻塞 Slice 1-2 实施，但应在 WU-WAIT-02 或 WU-WAIT-03 中作为已知限制文档化，或增加可选的 terminal condition。
- **建议改法和验证点**:
  1. 选项 A（推荐）: 在 `WaitPollerRuntimePolicy` 中增加 `max_consecutive_adapter_errors: int | None`。当 `poll_backoff_attempts` 中连续 `missing_adapter` 或 `adapter_error` 达到阈值时，poller 调用 `resolve_wait` 以 failed/lost outcome 终止 wait。
  2. 选项 B: 至少作为已知 residual risk 明确记录："Missing adapters cause indefinite retry with capped backoff delay. Operator must monitor `missing_adapters` diagnostic counter and fix adapter registration."
  3. 如果选择 B，在 control doc residual risk 表中增加条目，owner 为 WU-WAIT-03 或 future provider lifecycle work。
- **修复风险（中）**: 选项 A 需要定义新的 policy 字段、terminal transition 语义和测试，可能超出 Slice 1 范围；选项 B 是纯文档化，风险低。
- **严重程度（中）**: 中等，因为这是一个静默资源泄漏风险，不属于数据损坏或状态不一致，但会在生产环境中累积。

### F04-未修复-低-backoff-attempts-drift-on-claim-takeover

- **位置**: Slice 1 "Backoff Policy" 概念 (lines 290-309), Slice 1 tests "expired claim allows retry" (line 424)
- **问题类型**: 并发恢复风险
- **当前写法**: Plan 在 line 296-297 说 "Per-wait durable fields on host_wait_records store poll_next_observe_at, poll_backoff_attempts, ..." 该设计意味着 backoff attempts 是 per-wait 的全局计数器，由所有 poller 实例共享。
- **反例/失败场景**: Poller A 持有 claim，adapter 返回 not-ready，release with backoff（attempts=1, next_observe_at=+2s）。Poller A 进程崩溃。Claim 过期后，Poller B 接管这个 wait，此时 `poll_backoff_attempts=1`，backoff delay 为 `initial * multiplier^1`。如果部署环境 poller 进程频繁重启，backoff attempts 会因 claim-expiry-then-retakeover 而快速累积，超过实际 adapter 观察次数。在极端情况下（例如在 Kubernetes 中每 10 秒重启一次，每次接管后 adapter 返回 not-ready），backoff 可能在几分钟内就达到 max_delay。
- **为什么有问题**: Backoff attempts 应该是 "连续 not-ready / error 的观察次数"，但 claim takeover 导致计数在未发生新观察的情况下递增。不过，由于 `backoff_max_delay_seconds` 提供了上界，这种漂移的影响是有限的——它只会导致 wait 提前到达最大延迟，而不是无限增长。Plan 在 line 302 的正确判断 "backoff delay is per wait" 意味着这是有意的设计选择（shared backoff state across processes），但这个选择没有在 plan 讨论中显式记录。
- **直接证据**:
  1. Plan line 296-297: backoff state 在 wait row 上，没有 per-poller 分量。
  2. Plan line 423: "expired claim allows retry" — 接管后的 backoff 行为未指定。
  3. Plan line 302: "backoff delay is per wait" — 确认了共享设计。
- **影响**: 风险后移 — backoff 提前饱和到 max_delay，在极高频 crash 场景下可能导致 wait 的实际重试间隔大于理想值（如果 initial 小的话），但不会导致数据损坏。
- **建议改法和验证点**:
  1. 在 plan 中显式记录这个 tradeoff："Backoff attempts are shared across poller instances. If pollers crash frequently, the backoff counter may accumulate faster than actual adapter observations. This is bounded by backoff_max_delay_seconds and is an acceptable tradeoff vs. per-poller backoff state that would require a separate claim table."
  2. 如果需要更精确的控制，可以在 claim takeover 时重置 `poll_backoff_attempts=0`（因为新 poller 的第一观察应该从 initial delay 开始）。但这会引入新的 DoS 向量（恶意 poller 频繁 claim+release 保持低 backoff），所以当前设计可能是有意的。Plan 应在讨论中明确这个设计选择。
- **修复风险（低）**: 纯文档化。
- **严重程度（低）**: 低，因为有 max_delay 上界，且触发条件（高频率进程崩溃 + 连续 not-ready）在生产中不常见。

### F05-未修复-低-schema-check-poll-abandoned-at-must-note-race-condition

- **位置**: Slice 1 "Schema checks" (line 138)
- **问题类型**: 状态机漏洞
- **当前写法**: Plan line 138: "poll_abandoned_at is only allowed for status='cancelled'."
- **反例/失败场景**: 如果 `cancel_run` 和 poller 的 `abandon_wait` 在同一个 write transaction 内竞争（它们不会在同一个 transaction，但各自在不同 Host process 或线程中），可能出现：poller 读到的 wait 状态是 `cancelled`，于是执行 `abandon_wait` 并尝试 `UPDATE ... SET poll_abandoned_at=... WHERE wait_id=? AND status='cancelled'`。此时如果 wait 的状态尚未被另一个事务改为 cancelled（因为 cancel_run 的事务在 poller 读取之后才提交），abandon_wait 的 CAS 会失败。Plan 需要在 abandon 的 error handling 中覆盖这个 CAS 冲突场景。
- **为什么有问题**: Plan 在 line 375 说 "mark cancelled abandon success durably"，但没有描述当 wait 在 `poll_once` 读取快照和 abandon CAS 之间状态变化时的处理。这种情况在生产环境的 racing cancel + poll 场景中会发生。
- **直接证据**:
  1. Plan line 138: schema CHECK 约束。
  2. Plan line 375: "mark cancelled abandon success durably."
  3. Plan line 430-431: `poll_once` 当前在读取后逐条处理，不在 write transaction 内持有快照锁。
- **影响**: 风险后移 — abandon CAS 可能在 racing cancel 场景下失败，poller 误以为 abandon 成功（如果 CAS 不检查 rowcount）或错误地重试（如果 CAS 正确检测到 0 rows updated）。Plan 应明确这个场景的预期行为。
- **建议改法和验证点**:
  1. 在 Slice 1 "Error handling" 中增加："Abandon CAS may return 0 updated rows if the wait record status changed between read and write. Treat this as a skipped abandon (the wait was not yet cancelled or was already resolved by another path). Do not retry immediately; release the claim and move on."
  2. 如果 wait 状态从 waiting 变为 cancelled（由另一个 `cancel_run` 提交），下一轮 poll 会重新选中它并重试 abandon。这是正确的恢复行为。
- **修复风险（低）**: 正常的 CAS 语义处理。
- **严重程度（低）**: 低，因为 racing cancel + poll 是已知且可恢复的场景，CAS 冲突的默认行为（跳过本轮，下轮重试）已经是安全的。

## Slice Principle Verification

Plan 使用 3 slices，consistent with control doc line 145-146 "中型跨 contract / provider / projection work: 3-5 个 implementation slices"。

- Slice 1 (durable claim/backoff primitive): 语义闭环清晰——schema + CAS + 单轮 poll 变更。可独立验证。
- Slice 2 (supervisor lifecycle): 依赖 Slice 1 的 claim-aware `poll_once()`。引入 async runtime 但可在 `open_host` 外部测试。
- Slice 3 (open_host integration + docs): 纯组合层。依赖 Slice 2 的 supervisor。

3 slices 是合理的——合并 Slice 2+3 会让 implementation agent 同时处理 async lifecycle、close drain、sleep cancellation 和 open_host composition，上下文负载过高。进一步拆分（例如把 supervisor 拆成 lifecycle + diagnostics）缺乏独立语义边界，会增加 gate 成本却无相应的风险隔离收益。
