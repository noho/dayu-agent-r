## Findings

### 01-未修复-高-recovery.py startup source read 缺失 manifest 准备步骤

- **位置**: §5.3.1 Pending producer总表 startup/orphan recovery行，§4.3 Source、replay与failure
- **问题类型**: 不可直接实施 / 契约缺失
- **当前写法**: plan 要求 startup recovery "strict source candidate+sizing → new manifest(stage=continuation) → recovery RUN_STARTED → ATTEMPT_STARTED → pending row"。§5.3.1 要求 `recovery.py` 在自己的 transaction 内先写 matching manifest 再调用 existing recovery start transition。
- **反例/失败场景**: production `recovery.py::_start_recovery_dispatch_or_ready`（line 707）直接调用 `start_recovery_run_with_starting_attempt_in_transaction`，在此之前没有读取 source manifest / candidate / sizing 的任何代码。它不 import `run_input.py` 的 `load_prepared_runner_call_source_in_transaction` 或 `record_prepared_runner_call_candidate_in_transaction`。partial implementation 中这些新 helper 已存在（`run_input.py` line 985, 2116），但 recovery.py 完全未消费。按当前 plan 实施时，实现 agent 必须在 `_start_recovery_dispatch_or_ready` 中新增 source strict read + manifest write 步骤，但 plan 没有给出 `SessionAttachmentRecoveryScanner` 需要新增哪些字段来获得 `payload_store` / `memory_projection_policy` 等依赖。
- **为什么有问题**: plan §5.3.1 composition wiring 要求 `SessionAttachmentRecoveryScanner` "只增加 payload store，不接收 current baseline/tooling/context policy"，但 startup replay 的 candidate 需要 `policy_snapshot` 参数传给 `prepare_runner_call_candidate_in_transaction`。recovery 的 policy snapshot 来源在哪？plan 说"全部 execution/sizing source 来自 strict prepared source"，但 source manifest 里的 `sizing_snapshot.policy_ref` / `policy_snapshot_digest` 如何解析为 `PolicySnapshot` typed object？当前 `run_input.py::load_prepared_runner_call_source_in_transaction` 签名要求 `policy_snapshot: PolicySnapshot` 参数显式传入。recovery scanner 当前构造函数没有 policy 相关字段。
- **直接证据**: `recovery.py` line 707-749（`_start_recovery_dispatch_or_ready` 直接调 recovery start transition 无 manifest 准备）；`run_input.py` line 2116 `prepare_runner_call_candidate_in_transaction` 要求 `policy_snapshot: PolicySnapshot`；`recovery.py` imports（line 20-54）不包含 `run_input` 任何符号。
- **影响**: 实现 agent 面对 recovery.py 时需要自行决定 policy snapshot 如何获得，可能引入当前 config fallback 或额外 constructor 字段，违反 plan 约束。
- **建议改法和验证点**: 在 §5.3.1 composition wiring 中明确：`SessionAttachmentRecoveryScanner` 新增 `context_budget_policy: ContextBudgetPolicy | None` 字段；startup replay 从 source manifest 的 `sizing_snapshot` strict 解析 typed `PolicySnapshot`，不从 current config 取。或明确 startup replay 不需要 `prepare_runner_call_candidate_in_transaction`，而是直接从 source candidate payload 反序列化并只做 stage 重绑定。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 02-未修复-中-CONTINUATION stage 枚举值在 partial implementation 中不存在

- **位置**: §5.3.1 第五stage裁决、§5.5 `ContextSizingStage`枚举
- **问题类型**: 不可直接实施
- **当前写法**: plan 定义 `ContextSizingStage.CONTINUATION = "continuation"` 为第五stage，与 ORDINARY/POST_COMPACT/REACTIVE_POST_COMPACT/DISPATCH_FALLBACK 并列。5-stage/15-cell total function 固定 CONTINUATION 三 pressure 均 allow。
- **反例/失败场景**: production `context_budget.py` line 83-90 的 `ContextSizingStage` 只有四个值，没有 `CONTINUATION`。`_continuation_sizing_snapshot`（engine_ingest.py line 6509）当前硬编码 `sizing_stage=ContextSizingStage.ORDINARY`。`_pressure_and_decision`（line 815-852）实现的是 4-stage/12-cell total function，没有 CONTINUATION 分支。partial implementation 已有 `RunnerCallSizingUnavailableReason.CONTINUATION_*`（line 105-109）作为 unavailable reason，但 stage enum 本身未扩展。
- **为什么有问题**: 这是 plan 明确要求的结构性改动，当前 partial 实现恰好证明了 plan 的诊断正确（continuation 机械落入 ORDINARY）。实现 agent 需要先加 enum 值再改 `_pressure_and_decision`，但 plan 没有指出 partial implementation 已存在的这个 gap 需要如何迁移。
- **直接证据**: `context_budget.py` line 83-90（4个枚举值）；line 815-852（`_pressure_and_decision` 无 CONTINUATION 分支）；`engine_ingest.py` line 6509（`sizing_stage=ContextSizingStage.ORDINARY`）；line 6462/6467（unavailable snapshot 也写 `ORDINARY`）。
- **影响**: 实现 agent 知道要加枚举值，但可能遗漏 unavailable snapshot 和 `_pressure_and_decision` 的同步修改，导致 CONTINUATION hard pressure 错误地走 BLOCK 分支。
- **建议改法和验证点**: plan 可以在 §5.3.1 或 §5.5 中注明 partial implementation 的具体 gap 文件和行号，确保实现 agent 不只加枚举值而是完整更新 total function 和所有 sizing snapshot 构造点。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 03-未修复-中-steer candidate 的 policy_snapshot 来源链路未明确

- **位置**: §5.3.1 Pending producer总表 running steer / waiting steer行
- **问题类型**: 契约缺失
- **当前写法**: plan 要求 steer "新`USER_INPUT_ACCEPTED` durable effective facts + current memory/compact + 新input" 构造 candidate，使用 `prepare_runner_call_candidate_in_transaction`，需传 `policy_snapshot: PolicySnapshot`。§5.3.1 说 "initial admission 必须把实际 baseline/tools/mode 冻结进去，后续 producer 只读 durable facts"。
- **反例/失败场景**: steer 的 `policy_snapshot` 应来自新 append 的 `USER_INPUT_ACCEPTED.effective_execution_config`。plan 提到 `_execution_config_projection.effective_execution_snapshot_from_json` 已有共享 strict parser。但 admission.py 的 `_create_steer_attempt_result`（line 3035）当前直接写 start facts，没有先 parse effective execution config 为 `PolicySnapshot`。实现 agent 需要在 admission.py 中新增 config → policy snapshot 解析步骤，但 plan 没有给出这个 helper 是否需要在 steer transaction 内调用以及它需要哪些参数。
- **为什么有问题**: `effective_execution_snapshot_from_json` 的输入是 `USER_INPUT_ACCEPTED` payload 中的 JSON，输出包含 `PolicySnapshot`。plan §5.3.1 说 "policy snapshot 只能由对应 `USER_INPUT_ACCEPTED.effective_execution_config` 经 existing parser strict 解析"。但如果 steer 的新 `USER_INPUT_ACCEPTED` 还没 commit 就需要 parse 其 payload 来构造 policy snapshot 用于 candidate preparation，而 candidate preparation 又发生在 steer transaction 内——这个顺序是否可行取决于 `USER_INPUT_ACCEPTED` event 在同一 transaction 内是否可读。
- **直接证据**: `admission.py` line 3035（`_create_steer_attempt_result` 当前实现不包含 policy snapshot 解析）；plan §5.3.1 "policy snapshot 只能由对应 `USER_INPUT_ACCEPTED.effective_execution_config` 经 existing `effective_execution_snapshot_from_json` strict 解析"。
- **影响**: 实现 agent 可能跳过 policy snapshot 解析直接传 `None`，或从 current config fallback，违反 "后续 producer 只读 durable facts" 约束。
- **建议改法和验证点**: plan 应明确 steer transaction 中的时序：先 append `USER_INPUT_ACCEPTED` → 从刚写入的 event payload 解析 `PolicySnapshot` → 传入 `prepare_runner_call_candidate_in_transaction` → 写 manifest → start。或说明 `effective_execution_snapshot_from_json` 是否接受尚未 commit 的 event payload JSON（在同一 transaction 的写入 buffer 中可读）。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 04-未修复-中-wait resume continuity 的 event_plan 与 transaction 原子性边界

- **位置**: §5.3.1 wait resume producer ordering，§5.3.1 `project_wait_resume_continuity` 签名
- **问题类型**: 并发恢复风险 / 契约缺失
- **当前写法**: plan 要求 wait resume "validate wait/request atom + freeze planned accepted-result continuity → candidate → manifest(continuation) → existing transition appends RESUME_REQUESTED → TOOL_RESULT_ACCEPTED → RUN_STARTED → ATTEMPT_STARTED → pending row"。planned tool-result event id 是 deterministic 的，manifest 可引用它。
- **反例/失败场景**: plan 说 "manifest、后续 canonical result 与 start rows 在同一 transaction 全有或全无"。但 existing `_resolve_resume` 调用的 transition 是 `run_transition.py` 的函数，它在自己的逻辑内 append `RESUME_REQUESTED` / `TOOL_RESULT_ACCEPTED` / `RUN_STARTED` / `ATTEMPT_STARTED`。如果 manifest 先于 transition 写入（plan ordering 要求），但 transition 返回 precondition miss，manifest 会随 transaction rollback——这没问题。但 plan 没有明确 `project_wait_resume_continuity` 是否需要读取已写入的 `TOOL_RESULT_ACCEPTED` event（它在 transition 内部写入）。如果 continuity helper 需要读取 tool result 的 event id / payload，而该 event 还没写入（因为它在 transition 内部 append），就会形成循环依赖。
- **为什么有问题**: `project_wait_resume_continuity` 的签名接受 `tool_result_payload: Mapping[str, JsonValue]` 和 `source_refs: tuple[str, ...]`，这些是调用方 planner 提供的。但 plan 也说 "existing `_resume_wait_messages_from_current_start` 读取 committed event 后也委托该 helper"。pre-start path 用 planned payload，post-start path 用 committed event——两个 path 的输入来源不同，但 helper 是同一个。如果 post-start reader 依赖 committed event 的 `event_id`，而 pre-start planner 用的是 deterministic planned id，`source_refs` 的语义就不同。
- **直接证据**: plan §5.3.1 "waiting producer 传 strict `_wait_tool_call_requested_event` atoms、planned `TOOL_RESULT_ACCEPTED` payload、`event_plan.tool_result_event_id` 与 resolution digest"；"existing `_resume_wait_messages_from_current_start` 读取 committed event 后也委托该 helper"。
- **影响**: 如果 `source_refs` 在两条 path 中语义不一致（planned event id vs committed event id），candidate digest 会不同，导致 pre-start manifest 和 post-start committed reader 产生两个不同的 candidate identity。
- **建议改法和验证点**: plan 应明确：pre-start path 的 `source_refs` 使用 deterministic planned event id（与 manifest 和后续 committed event 一致），post-start reader 的 `source_refs` 使用 committed event id（应与 planned id 相同，因为是 deterministic）。并明确两者在正常情况下产生相同 digest。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 05-未修复-低-composition wiring 对 HostCommandHandle 的描述与当前实现有 gap

- **位置**: §5.3.1 Composition wiring
- **问题类型**: 不可直接实施
- **当前写法**: plan 说 "`command.py` 不在 `HostCommandHandle` 复制这些字段，只在构造 waiting/recovery producer 时从其唯一 `_admission_service` 读取并逐项传入"。`HostAdmissionService` 目标签名新增 `payload_store`、`context_budget_policy`、`memory_projection_policy`、`enable_truncation_manager`、`owner_host_instance_id`。
- **反例/失败场景**: 当前 `HostAdmissionService`（admission.py line 525-548）没有 `payload_store`、`context_budget_policy`、`memory_projection_policy`、`enable_truncation_manager`、`owner_host_instance_id` 字段。plan 要求新增这些字段，但没说 `open_host.py::_ExecutionCommandHandleFactory` 如何获得 `context_budget_policy`——它是否从 `HostOptions` 来？当前 `HostOptions` 是否已有该字段？如果 `context_budget_policy` 是 None，steer/wait 生产的 continuation manifest 的 `sizing_snapshot` 会是 `unavailable`，但 plan 没有说明 unavailable continuation 对 worker 的影响。
- **为什么有问题**: 实现 agent 需要在 `open_host.py` 中把 `context_budget_policy` 传入 `HostAdmissionService`，但如果 `HostOptions` 当前没有这个字段，就需要先在 `HostOptions` 加字段——这超出了 plan 的 production allowlist。
- **直接证据**: `admission.py` line 525-548（当前 `HostAdmissionService` 无 `context_budget_policy` 字段）；plan §5.3.1 target signature 列出 `context_budget_policy: ContextBudgetPolicy | None`。
- **影响**: 实现 agent 可能需要修改 `HostOptions` 或 `open_host.py` 的构造逻辑，但 plan 说 "不新增 public option"。
- **建议改法和验证点**: 确认 `HostOptions` / composition root 当前是否已有 `context_budget_policy` 的传入路径。如果没有，plan 需要说明这个字段如何流入 `HostAdmissionService`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 06-未修复-低-Engine continuation manifest 不写 candidate payload

- **位置**: §5.3.1 Engine within-Attempt continuation producer行
- **问题类型**: 契约缺失
- **当前写法**: plan 说 Engine continuation "accepted complete observed projection → continuation manifest → Slice 2 budget fact → iteration link/preview"。§5.3 说 "continuation 的唯一 frozen source 固定为：current messages projection、selected tool schema、context policy、request semantics"。
- **反例/失败场景**: Engine continuation 不创建新 Attempt，不经过 worker，不走 `load_prepared_runner_call_candidate`。但 plan §5.3.1 说 "Engine continuation 不是新 pending dispatch，因此不经过 worker first-call loader"。那 continuation manifest 的 consumer是谁？如果只有 Slice 2 budget fact 和 anchor resolver 需要读它，manifest 的 candidate payload 是否需要写入？当前 partial implementation 的 `_continuation_sizing_snapshot` 已经直接构造 sizing snapshot 并写入 manifest，但 plan 没有明确 continuation manifest 是否也需要写 `PreparedRunnerCallCandidate` payload。
- **为什么有问题**: `record_prepared_runner_call_candidate_in_transaction` 签名要求 `candidate: PreparedRunnerCallCandidate` 参数。Engine continuation 的 "candidate" 是 observed `IterationStartedData.input_projection`，它不经过 `prepare_runner_call_candidate_in_transaction`。plan 需要明确 continuation manifest 是否使用同一个 recorder 还是用不同的 manifest-only path。
- **直接证据**: `run_input.py` line 985 `record_prepared_runner_call_candidate_in_transaction` 要求 `candidate: PreparedRunnerCallCandidate`；plan §5.3.1 "Engine within-Attempt continuation 不是新 pending dispatch"。
- **影响**: 实现 agent 可能尝试构造一个完整的 `PreparedRunnerCallCandidate`（包含 `session_id`/`run_id` 等字段）只为了调用 recorder，但 continuation 没有完整的 candidate 语义。
- **建议改法和验证点**: plan 应明确 continuation manifest 是否用同一个 `record_prepared_runner_call_candidate_in_transaction` 或用一个更轻量的 manifest-only writer。如果用同一个，continuation 的 `PreparedRunnerCallCandidate` 从哪些字段构造。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open questions

1. **startup recovery policy snapshot 来源**：startup replay 不接收 current baseline/tooling/context policy，但 `prepare_runner_call_candidate_in_transaction` 要求 `policy_snapshot: PolicySnapshot`。source manifest 的 `sizing_snapshot` 只有 `policy_ref` + `policy_snapshot_digest`，如何反向得到 typed `PolicySnapshot`？是否需要一个从 ref+digest → `PolicySnapshot` 的 strict loader？

2. **wait pre-start vs post-start continuity digest 一致性**：两条 path 使用同一个 `project_wait_resume_continuity` helper，但 `source_refs` 的值来源不同（planned vs committed event id）。需要确认 deterministic event id 机制是否保证两者相同。

3. **`context_budget_policy` 如何流入 `HostAdmissionService`**：当前 `HostAdmissionService` 无此字段。plan 要求新增但不新增 public option。`open_host.py` 的 composition root 是否已有该值的来源？

## Plan review conclusion

**pass-with-risks**

plan 的总体架构方向正确，pending producer 双向审计已闭合，CONTINUATION stage 的第一性原理裁决成立，5-stage/15-cell total function 无重叠/无非法 terminal owner，CAS/rollback 设计合理，composition wiring 不引入 bag/callback seam，Slice 2/3 仍独立。

主要风险集中在：

1. **recovery.py startup source read 的 policy snapshot 来源链路**（finding 01）：这是最高的实施障碍，plan 给出了正确的方向但缺少具体 helper 调用链路。
2. **CONTINUATION 枚举和 total function 的 partial implementation gap**（finding 02）：已确认 partial code 确实存在 plan 诊断的问题，实施 agent 需要同步修改。
3. **steer policy snapshot 解析时序**（finding 03）和 **wait continuity digest 一致性**（finding 04）：中等风险，可通过 plan 或 implementation 阶段明确解决。

上述 finding 均不构成结构性 blocker——plan 的方向和约束足够清晰，实现 agent 可以在合理判断下完成。但 finding 01 的 policy snapshot 来源链路缺失可能导致实现 agent 临场引入不优方案，建议 Controller 在裁决时或 plan 进一步 amendment 中补充。

Original blocker disposition：Controller stop 的核心 blocker（pending producer 遗漏、CONTINUATION stage 缺失、manifest-before-start 未闭合）已通过本次 amendment 的 §5.3.1 全部收敛。本 review 不发现新的结构性 blocker。
