## Findings

### DL-PR-01-未修复-高-Slice 4 integrity repair 与 "HTTP 在 begin_batch 前" 的设计矛盾

- **位置**：Plan 5.6 节（Storage concurrency 与 typed integrity）+ 6 节 Slice 4
- **问题类型**：契约缺失 / 状态机漏洞
- **当前写法**：
  - Plan 5.6 节明确规定 "远端 HTTP、PDF下载、Docling转换必须发生在 `begin_batch` 前"
  - 同时规定 "`SourceDocumentRepositoryProtocol.classify_source_integrity(...)` 在 publication guard 下读取同一 published view"
  - Slice 4 exact changes 第 2-3 步：在 publication-guard 下查询 integrity → `REPAIR_REQUIRED` 强制 remote refetch 并在 staging 中 reset 目标
- **反例/失败场景**：
  1. `begin_batch` 获取 ticker lock
  2. 在 publication guard 下执行 `classify_source_integrity` → 返回 `REPAIR_REQUIRED`
  3. Plan 要求 "强制 remote refetch"（HTTP 操作）
  4. 此时 ticker lock 仍被持有，违反了 "HTTP 必须在 `begin_batch` 前" 的硬约束
  5. 如果 refetch 耗时数十秒（SEC 真实请求），同 ticker 的第二个并发进程会阻塞在 ticker lock 上等待整个 HTTP 周期——这正是 plan 声称要避免的
- **为什么有问题**：Plan 同时断言两个互斥的不变量：integrity 检查在 publication guard 下（需要已持有 lock）且 HTTP 在 `begin_batch` 前（不能持有 lock）。Implementation agent 必须自行裁决哪个不变量让步，可能做出错误选择（如在持锁期间做 HTTP）或引入 plan 未设计的 two-phase 重试（rollback → unlock → download → re-lock → re-stage），导致 Slice 4 实现偏离 plan 的 stop condition。
- **直接证据**：
  - Plan 5.6 节原文："远端 HTTP、PDF下载、Docling转换必须发生在 `begin_batch` 前"
  - Plan 5.6 节原文："`classify_source_integrity(...)` 在 publication guard 下读取"
  - Plan Slice 4 exact changes 第 3 步："`repair_required` 强制 remote target refresh 并在 staging reset 目标"
  - Plan Slice 4 stop condition："若 batch 在 HTTP/Docling 期间持锁...立即停止"
  - 代码证据：`_fs_storage_infra.py` L1464-1488，`_acquire_ticker_lock` 当前使用 `blocking=False`；改为 blocking 后，持锁期间的 HTTP 会导致第二个进程无界等待
- **影响**：实施 Agent 跑偏 / 生成错误代码（持锁做 HTTP）/ 并发性能退化 / 后续返工
- **建议改法和验证点**：
  1. 明确 Slice 4 的 integrity repair 采用 two-phase 方案：phase 1 在 `begin_batch` 前查询 integrity（使用只读 snapshot，不要求 publication guard），phase 2 在 `begin_batch` 后只做 staging + atomic commit
  2. 或者：将 `classify_source_integrity` 从 "publication guard 下" 移到 "`begin_batch` 前，基于 committed published view 的只读查询"
  3. 在 Slice 4 stop condition 中增加显式断言：production path 中 `begin_batch` 后不得发起 HTTP
  4. Owner test 用 barrier 证明：integrity check → repair download → begin_batch → staging → commit 全路径中，HTTP 发生在 lock 获取之前
- **修复风险（中）**：需要重新设计 integrity check 的调用时机，但不改变核心类型和 repair 逻辑
- **严重程度（高）**：不修复会导致 Slice 4 实现同时违反 plan 自身的并发约束，或引入未计划的 two-phase 复杂度

### DL-PR-02-未修复-中-Slice 3 Docling 临时目录 cleanup 所有权不明确

- **位置**：Plan 5.5 节（Canonical cancellation 与 Docling process boundary）+ 6 节 Slice 3
- **问题类型**：契约缺失
- **当前写法**：
  - "parent 在私有临时目录写 PDF input；child 调真实 Docling并写 output"
  - "命中后 terminate，必要时 kill，最后 `close()` 完成 join/queue drain，再抛 `CnDownloadCancelledError`"
  - Slice 3 invariants："cancelled/failure/success均无活 child、未观察 queue异常或late output"
  - Slice 3 allowed tests："真实 spawn 的 success/failure/cancel、terminate->kill、nested process-group cleanup、temp cleanup、no late result"
- **反例/失败场景**：
  1. Parent 创建临时目录，写入 PDF input
  2. Child 启动，开始 Docling conversion
  3. Ctrl+C → parent 对 child 执行 terminate → kill → close
  4. Child 进程被清理，但临时目录中的 PDF input 和可能的 partial output 未被删除
  5. 多次取消后临时目录堆积，或下次 run 误读旧临时文件
- **为什么有问题**：Plan 在 invariants 和 tests 中提到了 "temp cleanup"，但在 5.5 节的 data flow 描述中没有指定 cleanup 的 owner（是 parent 在 close 后清理？是 child 在启动时清理？是 `atexit` handler？）、cleanup 的时机（cancel 路径 vs success 路径 vs crash 路径）和失败处理（cleanup 失败是否 block terminal？）。Implementation agent 需要自行设计 cleanup 策略，可能导致遗漏或与 `InterruptibleProcessHandle.close()` 的异步 cleanup 语义冲突。
- **直接证据**：
  - Plan 5.5 节：临时目录写 PDF 的表述，但没有对应的 cleanup 步骤
  - Plan Slice 3 invariants：只提 "无活 child"，不提 "无残留临时文件"
  - Plan Slice 3 allowed tests：提到 "temp cleanup" 但只在测试描述中，不在 production data flow 中
- **影响**：实施 Agent 自行设计 cleanup 策略 / 磁盘泄漏 / 后续返工
- **建议改法和验证点**：
  1. 在 5.5 节明确：临时目录由 parent 在 `CnDoclingConversionRunner` 的 context manager (`__exit__`) 或 finally 块中清理
  2. 明确 cleanup 发生在 `InterruptibleProcessHandle.close()` 之后，且与 cancel/failure/success 路径无关（总是执行）
  3. 明确 cleanup 失败不阻止 terminal（best-effort），但记录 warning
  4. 在 Slice 3 owner tests 中增加：cancel 后临时目录不存在、success 后临时目录不存在、crash 后临时目录可能残留（OS 级限制，记录为 limitation）
- **修复风险（低）**：只需补充 cleanup 语义说明，不改变核心架构
- **严重程度（中）**：不修复会导致 production 中临时文件泄漏，但不会导致正确性失败

### DL-PR-03-未修复-中-DL-G02 等价覆盖标准欠规格

- **位置**：Plan 10 节 DL-G02 + Handoff DL-G02
- **问题类型**：open question 未收敛
- **当前写法**：
  - "CN 或 HK 至少选择一个市场，执行不带 forms、start、end 的裸 download"
  - "另一个市场只有在同owner/同branch加pairwise real evidence成立时才可等价覆盖，并写出直接证据"
  - "不能仅称'相似'"
- **反例/失败场景**：
  1. Implementation agent 运行 CN 裸 download 成功
  2. 声称 HK 由 "同 owner（`cn_pipeline.py`）、同 branch、pairwise evidence（CN 和 HK 共享同一套 download workflow 代码路径）" 等价覆盖
  3. 但实际上 HK 和 CN 使用不同的 provider（HKEX vs CNInfo）、不同的 HTML 解析、不同的 PDF 来源——仅共享 pipeline 框架代码
  4. "pairwise real evidence" 的标准没有定义：是代码路径覆盖？是同一测试类的 test case？是同一 source adapter interface 的不同实现？
- **为什么有问题**：这是一个需要在 plan 阶段收敛的 open question，不能在 implementation 或 DL-G 执行阶段才裁决。如果标准过松，HK 高成本路径可能被虚假覆盖；如果标准过严，DL-G02 永远需要运行两个市场（与 plan 的成本控制意图冲突）。
- **直接证据**：
  - Plan 10 节 DL-G02 原文
  - Handoff DL-G02 原文："另一个市场若由同 owner、同代码分支和已有 pairwise evidence 可等价覆盖，必须在报告中给出直接代码/运行证据，不能仅称'相似'"
  - 代码事实：CN 和 HK 共享 `cn_pipeline.py` 和 `cn_download_workflow.py`，但使用不同的 downloader（CNInfo vs HKEX）和不同的 HTML→PDF 提取逻辑
- **影响**：DL-G 阶段争议 / Oracle pause 时用户无法裁决等价性 / 可能需要补跑
- **建议改法和验证点**：
  1. 在 plan 中给出 "pairwise real evidence" 的最小可判定标准，例如：
     - 两个市场共享相同的 `FinsDownloadSource` adapter interface 实现类
     - 两个市场的 download workflow 通过相同的 code path（相同的函数调用链，不含 source-specific branch）
     - 已有的 focused-real evidence（DL-G01）证明两个市场对 bare default 的关键行为一致（相同的 event type 序列、相同的 terminal schema、相同的 error classification）
  2. 如果无法在 plan 阶段确定等价性，将 DL-G02 的第二个市场标记为 "待 DL-G01 证据后再裁决"，不作为 plan 的 blocking question 但作为 explicit deferred decision
- **修复风险（低）**：只需补充判定标准
- **严重程度（中）**：不修复会导致 DL-G 阶段的争议和潜在补跑，但不影响 implementation slice 的正确性

### DL-PR-04-未修复-中-`SourceDocumentRepositoryProtocol.classify_source_integrity` 对既有实现的破坏性

- **位置**：Plan 5.6 节 + Slice 4 allowed production files
- **问题类型**：架构边界 / 契约缺失
- **当前写法**：
  - "`SourceDocumentRepositoryProtocol.classify_source_integrity(...)` 在 publication guard 下读取同一 published view"
  - Slice 4 在 `repository_protocols.py` 中增加该方法
- **反例/失败场景**：
  1. `SourceDocumentRepositoryProtocol` 是一个 Protocol，当前有多个实现（`_fs_source_document_core.py` 中的 production 实现、测试中的 fake/mock 实现）
  2. 向 Protocol 增加新方法 `classify_source_integrity` 后，所有未实现该方法的既有实现会在类型检查时失败
  3. 当前 `ingestion_runtime.py` 和测试中使用的 fake repository 可能没有实现此方法
  4. 如果 plan 本意是新增一个独立 Protocol（如 `SourceIntegrityRepositoryProtocol`）而不是修改既有 Protocol，plan 没有明确说明
- **为什么有问题**：Protocol 変更是 breaking change。Plan 没有评估影响范围：有多少个 `SourceDocumentRepositoryProtocol` 的实现者需要同步更新？测试 fake 是否需要新增方法？如果新增独立 Protocol，则现有 consumer（SEC/CN workflow）需要注入新的依赖，这在 Slice 4 的 allowed files 中没有体现。
- **直接证据**：
  - Plan 5.6 节直接写 "`SourceDocumentRepositoryProtocol.classify_source_integrity(...)`"
  - Plan Slice 4 allowed production files 包含 `repository_protocols.py`
  - Plan 没有列出受影响的既有 Protocol 实现者清单
- **影响**：类型检查失败 / 测试 fake 编译失败 / 实施 Agent 需要额外发现和修复所有实现者
- **建议改法和验证点**：
  1. 明确 `classify_source_integrity` 是新增到既有 `SourceDocumentRepositoryProtocol` 还是新增独立 Protocol
  2. 如果是前者，列出所有需要同步更新的实现者和测试 fake，并在 Slice 4 allowed files 中补充
  3. 如果是后者，在 Slice 4 exact changes 中明确新的 Protocol 定义和注入点
- **修复风险（低）**：只需补充影响范围分析
- **严重程度（中）**：不修复会导致实施时发现额外的修改范围，但不会导致设计返工

## Open Questions

1. **DL-G04 publication 中断的可达性**：Plan 正确地将 DL-G04 标记为 "优先调查是否存在公开稳定路径"，并在不可达时登记 `defensive/unreachable`。但 plan 没有定义 "公开稳定路径" 的判定标准——是通过代码分析证明 publication 窗口的 wall-clock 时间？还是通过 OS 级信号送达时序？如果 implementation agent 和 reviewer 对 "不可达" 的标准不一致，DL-G04 的终态会有争议。

2. **`rebuild_processed` 删除对 preprocess/upload 的影响**：Plan 的 non-goal 明确 "不处理 process/upload 自身 UI 或 Oracle"，但 `rebuild_processed` 字段同时存在于 `FinsPreprocessRequest`（`ingestion_runtime.py` L493-500）和 `FinsUploadRequest` 中。Plan Slice 1 从 `FinsDownloadRequest` 删除 `rebuild_processed`，但 preprocess/upload 中的同名字段是否一并清理？如果保留，download contract 的 "processed 语义污染" 修复是否完整？

3. **CN/HK fiscal-period alias 归一化的迁移范围**：Plan 5.1 节提到 "CN/HK fiscal-period alias 归一从 pipeline 私有 mapping 迁到 `dayu/fins/domain/filing_semantics.py`"。当前 `cn_form_utils.py` 中有 `FY`、`Q1`、`年报` 等 alias 映射。迁移后，既有 `cn_form_utils` 是否删除私有 mapping 并改为 import 公共 parser？这在 Slice 1 exact changes 中没有明确描述。

## 最终结论

**Pass-with-risks**

Plan 的动机（DL-F01～DL-F11）全部由直接代码证据和用户裁决支持，root cause 判定正确。语义 owner 分配符合 `AGENTS.md` 的语义所有权约束和 `UI -> Service -> Fins` 分层架构。四个 slice 的划分合理，各自形成可验证的行为增量。非目标明确，过度设计控制得当（三个新模块各自对应唯一缺失 owner）。DL-G01～DL-G05 的 real coverage 计划与 Oracle pause 机制正确。

但存在一个 **高严重性设计矛盾**（DL-PR-01）：Slice 4 的 integrity repair 要求 HTTP 在持锁状态下执行，与 plan 自身的 "HTTP 在 `begin_batch` 前" 硬约束冲突。该矛盾应在 Slice 4 实施前解决——要么将 integrity check 移到 `begin_batch` 前，要么明确 two-phase 方案。

此外有三个中严重性 gap（DL-PR-02/03/04）和一个低严重性措辞问题（DL-PR-05）和一个低严重性测试缺口（DL-PR-06），均可在 implementation 阶段以较低成本收敛，不阻塞 plan gate 通过。

Plan review 的结论是 **pass-with-risks**（非 fail），因为核心设计正确、语义 owner 清晰、slice 可实施，且所有 finding 都有明确的修复路径。建议在 AgentCodex 裁决 DL-PR-01 后再进入 implementation。
