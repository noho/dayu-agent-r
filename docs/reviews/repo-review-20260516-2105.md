### 1-未修复-中-IdempotencyStore 并发 INSERT 时错误类型不精确

- **入口/函数**: `record_idempotent_result`
- **文件(行号)**: `dayu/host/durable/idempotency.py` (148-154, 157-186)
- **输入场景**: 两个独立 HostTransaction 在 BEGIN IMMEDIATE 序列化窗口外并发写入同一 `(scope_kind, scope_id, idempotency_key)` 且 semantic digest 相同
- **实际分支**: 两个事务都读到 `existing is None`，都执行 INSERT。后到事务因 `PRIMARY KEY` 唯一约束触发 `sqlite3.IntegrityError`，被分类为 `HostUniqueConstraintError`
- **预期行为**: 同 key 同 digest 的并发插入应表现为幂等返回（或至少抛出 `HostIdempotencyConflictError`），语义与同一事务内重复写入一致
- **实际行为**: 抛出 `HostUniqueConstraintError`，与"同 key 不同 digest"的 `HostIdempotencyConflictError` 不同。调用方需同时处理两种错误类型
- **直接证据**: `idempotency.py:148-154` 只检查 `existing is not None` 时的 digest 冲突；`idempotency.py:157-186` 的 INSERT 未 catch `HostUniqueConstraintError`；`transaction.py:241-257` 将 UNIQUE constraint 错误分类为 `HostUniqueConstraintError`
- **影响**: 并发调用方收到意外错误类型，可能被误判为非幂等场景
- **建议改法和验证点**: 在 `record_idempotent_result` 的 INSERT 处 catch `HostUniqueConstraintError`，re-read 既有记录；若 digest 一致则返回既有记录，若不一致则抛 `HostIdempotencyConflictError`。补充并发幂等测试
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-scheduler close 时 CancelledError 路径导致 Run 状态泄漏

- **入口/函数**: `HostDispatchScheduler._consume_worker_events`
- **文件(行号)**: `dayu/host/dispatch.py` (951-952, 995-1004)
- **输入场景**: scheduler close 导致 consume task 被取消，且此时 worker 尚未产出 terminal event
- **实际分支**: L951-952 捕获 `asyncio.CancelledError` 后直接 re-raise，不调用 `close_worker_lost`。finally 块 (L995-1004) 执行 unregister、close handle、release token，但不执行 terminal closeout
- **预期行为**: scheduler close 时，active worker 的 Run 应被标记为适当终态或进入可恢复状态
- **实际行为**: 若 task 在 worker 产出 terminal event 前被取消，Run 停留在 RUNNING 状态，没有 terminal closeout

- **影响**: Run 停留在 RUNNING 状态需要外部恢复机制（Phase 11 RECOVERING）处理。当前 Phase 8 无自动恢复
- **建议改法和验证点**: 在 finally 块中检查 `run_terminal_closed`，为 False 时调用 `close_worker_lost`。或在设计文档中明确 scheduler close 的 best-effort 语义并记录对 Phase 11 的依赖

- **严重程度（低/中/高/严重）**: 中

### 3-未修复-中-cancel_session_runs 单事务内循环取消多 Run 时部分失败导致全部回滚

## Open Questions

1. **Host API 对 Engine 具体类型的依赖是否为终态设计？** 当前 `api.py` 直接依赖 5 个 Engine 具体类型。设计文档允许 Host 依赖 Engine contracts，但未明确这些类型是"稳定公共契约"还是"实现细节"。需在后续 phase 中明确 Engine contracts 的稳定性承诺。

2. **Phase 11 RECOVERING 恢复机制**：多处代码（scheduler close 状态泄漏、RECOVERING Run 的 cancel deferred）依赖 Phase 11 的 RECOVERING 状态。当前 Phase 8 无自动恢复路径，scheduler close 时丢失的 Run 需要外部恢复。

3. **runner 单事件事务开销**：`run_once` 对每个 EventLog row 开启独立 `run_write` 事务。repair 全量 replay 时会产生大量短事务。Phase 8 consumer 写入量小可接受，Phase 13 heavy sink 可能需要 batch transaction 策略。

4. **EventLog event_body_digest 的 digest_input 包含 `payload_ref` 和 `payload_digest`**：若未来 payload descriptor 被 purge，digest 中的 payload_ref 将指向不存在的行。这是有意设计还是需要在 purge 时特殊处理？

5. **`HOST_SCHEMA_VERSION = 5`**：当前 bootstrap 逻辑只接受 version 0 或当前版本，不做兼容迁移。后续 phase 新增表或修改 CHECK 约束是否继续 bump 版本号需团队约定。
