### 1-未修复-中-`CONTEXT_COMPACTION_FAILED` 的 `attempt_count` 在 recovery tier 场景下不准确

- **入口/函数**: `HostDispatchScheduler._execute_proactive_compaction()` → `_operation` transaction
- **文件(行号)**: `dayu/host/dispatch.py:1416, 1433`
- **输入场景**: proactive compaction 初始 operation 有 1 个 rejected attempt，随后 recovery tier 1-3 全部失败（各 1 个 rejected attempt）。实际共 4 次 proposal attempt，但 recovery tier 的 3 次拒绝均未进入 EventLog（F1）。
- **实际分支**: 行 1408-1423 stale session 路径：`attempt_count=len(result.rejected_attempts)` → 只计初始 operation 的 1 次；行 1424-1456 fallback 路径：`attempt_count=len(result.rejected_attempts)` → 同样只计 1 次。
- **预期行为**: `attempt_count` 应反映实际完成的 proposal attempt 总数（包括 recovery tier），或至少在语义上自洽——当前因为 recovery tier rejects 不写入 EventLog，`attempt_count` 与 EventLog 中的 `CONTEXT_COMPACTION_ATTEMPT_REJECTED` 行数一致（都是 1），但 `CONTEXT_COMPACTION_FAILED` 事件用于审计时无法从此数字得知实际发生了 4 次 attempt。
- **实际行为**: `attempt_count=1` 在 EventLog 中记录，掩盖了 3 次 recovery tier 失败。
- **直接证据**: 行 1416 `attempt_count=len(result.rejected_attempts)` 与行 1433 `attempt_count=len(result.rejected_attempts)` 均使用 `result`（初始 operation）而非合并后的 attempts。
- **影响**: 审计不准确。通过 `CONTEXT_COMPACTION_FAILED` 追踪操作成本时，attempt_count 低估了实际 LLM 调用次数。对当前 diagnostic artifact slice 非阻塞——diagnostic artifact 字段在 `CONTEXT_COMPACTION_ATTEMPT_REJECTED` 上，不在 `CONTEXT_COMPACTION_FAILED` 上。
- **建议改法和验证点**: 在 recovery tier audit work unit 中，将 `attempt_count` 改为使用合并后的 attempt 总数（含 recovery tier rejects）。
- **修复风险（低）**: 纯数值修正，不改变状态机。
- **严重程度（中）**: 数据质量 issue，但不影响当前 slice 功能。

**分类**: **deferred to recovery-tier audit diagnostics** — 与 AgentMiMo F1 同属 recovery tier EventLog 审计语义范畴。
