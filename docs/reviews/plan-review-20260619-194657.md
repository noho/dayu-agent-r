# WU-CM-13 Plan Adversarial Review

## Reviewed Target

- **Plan**: `docs/host/host-issues/wu-cm-13-unified-compact-pipeline-plan.md`
- **Scope**: Host 内部 unified compact pipeline owner 收敛；不改 public API、schema、EventLog event type、provider contract 或 durable payload contract。
- **Review date**: 2026-06-19
- **Reviewer posture**: constructively adversarial

## Assumptions Tested

1. Plan 是否 code-generation-ready，还是把核心设计留给 implementation agent。
2. `compact_pipeline.py` 是否过度设计或过度耦合。
3. proactive / reactive outer lifecycle boundary 是否清楚。
4. WU-CM-14 protected recent raw tail provider 是否被合理纳入 shared path。
5. `compaction_evidence.py` 删除/迁移策略是否可实施。
6. Tier 4/5 fallback 是否已在代码中实现。
7. 测试是否可验收。
8. 是否存在隐性 public API / schema / contract 变更需求。

## Findings

### 1-未修复-高-tier 4/5 fallback 在代码中不存在，plan 要求 implementation agent 新增未验证行为

- **位置**: §5.5 Fallback Ordering, §9 Test Plan item 9, §12 Blocking Questions
- **问题类型**: 不可直接实施 / 契约缺失
- **当前写法**: Plan §5.5 定义了 tier 4 floor-only dispatch fallback 和 tier 5 current-input-only dispatch fallback，并在 §9 要求测试覆盖 tier 4/5。§12 说"若代码证据证明现有 payload/schema 无法表达 tier 5，停下列 blocking question"。
- **反例/失败场景**: 代码搜索确认：整个 `dayu/host/` 中不存在 `tier_4`、`tier_5`、`floor_only`、`current_input_only` 任何引用。现有 fallback 只到 tier 3（`tier_1_fallback_caps`、`tier_2_section_degrade`、`tier_3_delta_only`，均在 `dispatch.py:1531-1567`）。`context_fallback.py` 的 `build_recent_window_fallback_selection(...)` 是一个通用 recent-window selection helper，不区分 tier 4/5。`CONTEXT_COMPACTION_FAILED` payload 有 `fallback_action` 字段（`dispatch` / `fail_closed` / `not_applicable`），但没有 `fallback_tier` 字段。Plan 要求 implementation agent 实现 tier 4/5，这不再是"收敛共享 owner"，而是新增未在当前代码中验证过的 fallback 行为。
- **为什么有问题**: Plan 的 scope 声明是"统一从 frozen material view 到 compact operation result decision 的纯语义装配"，但 tier 4/5 是全新 fallback 行为，不在"收敛"范围内。如果 implementation agent 在 Slice 2 中实现 tier 4/5，它同时在做收敛和新增行为，违反 slice 边界约束。
- **直接证据**: `dispatch.py:1531-1567` 只有 tier 1-3；`context_fallback.py:481-580` 的 `build_recent_window_fallback_selection` 是 tier-agnostic 的 selection helper，不区分 4/5；代码中无 `fallback_tier` payload 字段。
- **影响**: Implementation agent 可能把 tier 4/5 实现为"和现有 fallback 一样的 recent-window selection，只是 caps 不同"，但 design doc §3243-3258 定义的 tier 4/5 语义是 floor-only 和 current-input-only，与现有 recent-window selection 语义不同。如果 agent 简单复用 `build_recent_window_fallback_selection`，可能生成不符合设计真源的代码。
- **建议改法和验证点**: Plan 应在 §5.5 明确：(a) tier 4/5 是否属于本 WU scope，还是应 deferred 到后续 WU；(b) 如果属于本 WU，应作为独立 Slice 0 先验证 payload schema 能承载 `fallback_tier` 字段，再在 Slice 1/2 中实现；(c) 如果不属于本 WU，§9 测试计划应删除 tier 4/5 测试要求。验证点：`rg "tier_4\|tier_5\|floor_only\|current_input_only" dayu/host/` 返回零结果时，plan 必须明确是新增还是不新增。
- **修复风险（低/中/高）**: 中
- **严重程度（高）**: 高 — 如果 implementation agent 在没有明确裁决的情况下新增 tier 4/5，可能引入不符合设计真源的 fallback 行为，或在 payload schema 不支持时被迫做 blocking question，导致 slice 进度受阻。

### 2-未修复-中-CompactPipelineRenderHandoff 是全新抽象，RunInputBuilder 消费路径未验证

- **位置**: §5.2 Result Shape, §5.6 Session Semantic Memory 与 Rendering, §6 WU-CM-14 Preservation Audit
- **问题类型**: 不可直接实施 / 过度耦合
- **当前写法**: Plan 定义 `CompactPipelineRenderHandoff` 包含"ordinary post-compaction raw tail blocks/messages, fallback selected blocks/messages, source refs, material view digest, selected recent floor, selected raw turn count"。§5.6 说"RunInputBuilder 普通 post-compaction branch 只消费 pipeline handoff 或 pipeline-owned provider result"。§6 说"WU-CM-14 raw tail provider 不再在 RunInputBuilder 内独立二次决定 floor；它应消费 pipeline 产出的 CompactPipelineRenderHandoff"。
- **反例/失败场景**: 当前 `RunInputBuilder.build()` 在 `run_input.py:1891-2088` 的 ordinary branch 直接拼接 `memory.messages + compact.messages + protected_recent_raw_tail.messages + continuity.messages`。它消费的是 `_ProtectedRecentRawTailView(messages, material_blocks, source_refs)`（run_input.py:1396-1498），不是 `CompactPipelineRenderHandoff`。如果 implementation agent 要让 RunInputBuilder 消费 `CompactPipelineRenderHandoff`，需要：(a) 在 `RunInputBuilder.__init__` 中注入 pipeline handoff provider；(b) 修改 `build()` 的 ordinary branch 消费 handoff 而不是独立 provider；(c) 确保 fallback branch 不双重渲染。这三步的代码路径和当前实现之间有显著 gap，plan 没有给出具体的 wiring 方案。
- **为什么有问题**: Plan 把 `CompactPipelineRenderHandoff` 定义为"包含 ordinary raw tail blocks/messages, fallback selected blocks/messages"，但 RunInputBuilder 的 ordinary 和 fallback 是两个完全不同的代码分支（run_input.py:1891-2088 vs run_input.py:2650-2859）。把两个分支的 rendering 输入统一到一个 handoff 类型，可能迫使 implementation agent 重构 RunInputBuilder 的分支结构，超出"收敛 compact pipeline owner"的 scope。
- **直接证据**: `run_input.py:1891-2088` ordinary branch 拼接四段 messages；`run_input.py:2650-2859` fallback branch 调用 `_fallback_context_messages(...)`；`run_input.py:1396-1498` `_DurableProtectedRecentRawTailProvider` 返回 `_ProtectedRecentRawTailView`。三者是独立的 rendering 路径。
- **影响**: Implementation agent 可能把 `CompactPipelineRenderHandoff` 设计成 god bag（包含 ordinary 和 fallback 的所有 rendering 输入），导致 RunInputBuilder 被迫接受一个过宽的接口。或者 agent 在 wiring 时发现需要拆分 handoff 为 ordinary-specific 和 fallback-specific 两个子类型，增加 plan 未预见的复杂度。
- **建议改法和验证点**: Plan 应在 §5.2 和 §5.6 明确 `CompactPipelineRenderHandoff` 的消费边界：(a) ordinary 和 fallback 是否共享同一个 handoff 类型，还是各有一个；(b) RunInputBuilder 的 wiring 方案是替换现有 provider injection，还是在 `build()` 内部消费 handoff；(c) 如果 handoff 包含 fallback selected blocks，fallback branch 的 `_fallback_context_messages(...)` 如何消费它。验证点：在 implementation 前，用伪代码写出 `RunInputBuilder.build()` 的 ordinary branch 和 fallback branch 如何消费 handoff，确认不引入 god bag 或过宽接口。
- **修复风险（低/中/高）**: 中
- **严重程度（中）**: 中 — 不会导致数据损坏，但可能迫使 implementation agent 在 wiring 阶段重新设计 handoff 接口，导致 slice 进度延迟或引入过度耦合。

### 3-未修复-中-Proactive / Reactive 的 fallback event payload construction 仍分散，shared pipeline 是否真正统一未验证

- **位置**: §5.2 Result Shape, §5.5 Fallback Ordering
- **问题类型**: 过度耦合 / 不可直接实施
- **当前写法**: Plan §5.2 定义 `CompactPipelineFallbackDecision` 包含 `fallback_policy_decision, fallback window, digest, budget payload, fallback_action=dispatch|fail_closed, selected material_blocks handoff`。§5.5 说"统一 fallback order"。Plan 声称 shared pipeline 统一生成 fallback decision input，但"append event 的 actor/source/event identity 和 lifecycle ordering 仍由 caller 保持"。
- **反例/失败场景**: 当前 proactive fallback 在 `dispatch.py:2079-2228` 的 `_append_compaction_failed_with_proactive_fallback(...)` 中写 `CONTEXT_COMPACTION_FAILED` event，包含 fallback tier/window/digest/budget/action payload。Reactive fallback 在 `engine_ingest.py:1732-1815` 的 `_operation` inner function 中写 `CONTEXT_COMPACTION_FAILED` event。两者的 payload construction 是独立的。Plan 说 shared pipeline 统一生成"payload input"，但"append event 留在 caller"。这意味着 shared pipeline 只产出 payload 字段值，caller 自己组装 event 并 append。如果 proactive 和 reactive caller 的组装逻辑不同（例如 proactive 有 `FALLBACK_ACTION_DISPATCH` 的特殊路径，reactive 有 `RUN_RECOVERING` 状态转换），shared pipeline 产出的"统一 payload input"可能无法覆盖两条路径的差异。
- **为什么有问题**: Design doc §3369-3370 明确区分 proactive 和 reactive 的 fallback 后续动作：proactive fallback 通过后"可继续 dispatch"，reactive fallback 通过后"创建新的 recovery Attempt"。如果 shared pipeline 只统一 payload 字段但不统一后续动作，caller 仍需要各自的 fallback 后续逻辑，shared pipeline 的统一价值有限。
- **直接证据**: `dispatch.py:2167-2193` proactive fallback 决定 `FALLBACK_ACTION_DISPATCH` 或 `FAIL_CLOSED`，然后决定是否 dispatch；`engine_ingest.py:1732-1815` reactive fallback 决定是否 dispatch 或 fail recovering run。两者共享 `build_recent_window_fallback_selection(...)` 和 `estimate_recent_window_fallback_budget(...)` helper，但后续动作不同。
- **影响**: 如果 shared pipeline 只统一 helper 调用但不统一后续动作，proactive 和 reactive 仍各自维护 fallback decision 逻辑，plan 声称的"统一 fallback"实际上只是把 helper 调用从两个文件移到一个文件，没有真正消除漂移风险。
- **建议改法和验证点**: Plan 应在 §5.5 明确：(a) shared pipeline 是否只产出 payload 字段值（caller 组装 event），还是产出完整的 fallback decision（包括后续动作建议）；(b) proactive 和 reactive caller 各自的 fallback 后续逻辑是否仍在 caller 中，还是 pipeline 应产出 `fallback_action` hint 供 caller 消费；(c) 如果 caller 仍各自维护后续逻辑，plan 应承认 shared pipeline 的统一范围限于 payload construction 和 selection，不覆盖后续动作。验证点：在 implementation 前，写出 proactive 和 reactive fallback 的 caller-side 伪代码，确认 shared pipeline 产出的 `CompactPipelineFallbackDecision` 是否足够让 caller 消费而不需额外本地逻辑。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中 — 不会导致错误行为，但可能让 plan 声称的"统一 fallback"收敛效果被高估。

### 4-未修复-中-WU-CM-14 protected recent raw tail provider 迁移策略二选一未收敛

- **位置**: §6 WU-CM-14 Preservation Audit, §5.1 Pipeline 输入
- **问题类型**: open question 未收敛
- **当前写法**: Plan §6 rule 4 说"如果为了最小改动暂时保留 EventLog second read provider，provider 必须移动到 compact_pipeline.py"。§5.1 说"WU-CM-14 raw tail provider 不再在 RunInputBuilder 内独立二次决定 floor；它应消费 pipeline 产出的 CompactPipelineRenderHandoff，或在无法一次传递时使用 pipeline-owned provider 重新读取并校验同一 source_boundary / input_cursor / compact event"。
- **反例/失败场景**: Plan 给出两个选项但没有裁决选哪个：(a) provider 消费 pipeline handoff（不再独立读 EventLog）；(b) provider 移到 `compact_pipeline.py` 但仍独立读 EventLog。WU-CM-14 plan 明确说"Re-reading EventLog in this provider is acceptable for WU-CM-14: EventLog / payload truth is immutable after commit"。WU-CM-14 的 review artifacts 也接受了 second read。如果 implementation agent 选 (b)，它只是把 provider 从 `run_input.py` 移到 `compact_pipeline.py`，没有实质改变 EventLog 读取模式，plan §6 的"纳入 shared path"变成"换文件名"。如果选 (a)，需要 pipeline 在 compact 时产出 handoff 并传递到 RunInputBuilder 的 post-compaction dispatch，这涉及跨 dispatch lifecycle 的状态传递，复杂度更高。
- **为什么有问题**: Plan 没有明确裁决 (a) 和 (b) 的选择标准，把决策留给 implementation agent。Implementation agent 在 Slice 2 wiring 阶段可能倾向于 (b)（更简单），但这样 WU-CM-14 provider 仍然是"独立读 EventLog 决定 floor"的模式，只是换了文件位置。Plan 声称的"WU-CM-14 preservation 必须纳入 shared path"实际上没有改变 EventLog 读取模式。
- **直接证据**: WU-CM-14 plan §2 说"Re-reading EventLog in this provider is acceptable for WU-CM-14"；WU-CM-14 review artifacts 接受了 second read；`run_input.py:1474-1498` 的 `_DurableProtectedRecentRawTailProvider` 在 read transaction 中独立调用 `build_pre_dispatch_compact_material_view(...)`。
- **影响**: 如果 implementation agent 选 (b)，WU-CM-14 provider 的 EventLog 读取模式不变，只是文件位置变了。这不会引入 bug，但 plan 声称的"纳入 shared path"收敛效果被高估。如果选 (a)，需要额外的跨 lifecycle 状态传递机制，plan 没有给出具体方案。
- **建议改法和验证点**: Plan 应在 §6 明确裁决：(a) 本 WU 选择哪个选项；(b) 如果选 (b)，明确承认"provider 移到 pipeline 文件但读取模式不变"是可接受的最小改动，不声称"纳入 shared material handoff"；(c) 如果选 (a)，给出 pipeline 产出 handoff 到 RunInputBuilder 的具体传递方案。验证点：在 implementation 前，确认 provider 的 EventLog 读取调用是否仍在独立 transaction 中，还是由 pipeline 统一管理。
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 中 — 不会导致 bug，但会影响 plan 的收敛效果评估。

### 5-未修复-低-compaction_evidence.py 删除策略安全，但测试迁移细节不足

- **位置**: §7 compaction_evidence.py 收口策略
- **问题类型**: 测试缺口
- **当前写法**: Plan §7 说"首选策略：删除 dayu/host/compaction_evidence.py，迁移到 shared pipeline / compact_material.py"。迁移规则说"仍有价值的能力已由 compact_material.py 的 post-compact delta material builder 覆盖大部分"。
- **反例/失败场景**: Code search 确认 `compaction_evidence.py` 有零 production import，只有 `tests/host/test_compaction_operation.py` 调用 `collect_selected_compaction_request_evidence_inputs(...)`。Plan 说"将有价值测试改写为 build_pre_dispatch_compact_material_view(...) 产生同等 accepted tool evidence material"，但没有列出哪些具体 test cases 需要改写、哪些可以删除、改写后的断言应该验证什么。
- **为什么有问题**: `compaction_evidence.py` 有 658 行、24 个函数/类。测试迁移不是简单的 import 替换，因为 `collect_selected_compaction_request_evidence_inputs(...)` 和 `build_pre_dispatch_compact_material_view(...)` 的接口不同。如果 implementation agent 在 Slice 1 中删除 `compaction_evidence.py` 但没有完整迁移测试，可能导致 evidence material 相关的测试覆盖下降。
- **直接证据**: `compaction_evidence.py` 有 658 行，`__all__` 导出 3 个符号；`tests/host/test_compaction_operation.py` 调用 `collect_selected_compaction_request_evidence_inputs(...)`。
- **影响**: 测试覆盖可能下降，但不会影响 production 行为。Plan §9 test item 13 要求"rg 验证旧 module/function 无引用"，但没有要求"迁移后的测试覆盖不低于迁移前"。
- **建议改法和验证点**: Plan 应在 §7 补充：(a) 列出 `tests/host/test_compaction_operation.py` 中调用 `compaction_evidence` 的具体 test cases；(b) 对每个 test case 裁决"删除"或"改写为 compact_material / compact_pipeline 测试"；(c) 改写后的断言应验证什么等价行为。验证点：迁移后 `pytest tests/host/test_compaction_operation.py` 的 test count 不低于迁移前。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — production 行为不受影响，但测试覆盖可能下降。

### 6-未修复-低-Slice 2 wiring 方案不够 code-generation-ready

- **位置**: §8 Implementation Slice Structure, Slice 2
- **问题类型**: 不可直接实施
- **当前写法**: Plan Slice 2 说"dispatch.py 调用 shared pipeline，删除本地 duplicated request / recovery / fallback construction"。"engine_ingest.py 调用 shared pipeline，删除本地 root request / pass queue / fallback decision construction"。"run_input.py 消费 shared render handoff"。
- **反例/失败场景**: `dispatch.py` 有 4616 行，`engine_ingest.py` 有 6314 行，`run_input.py` 有 5015 行。Plan 说"调用 shared pipeline，删除本地 construction"，但没有指定：(a) 哪些具体函数/方法被替换；(b) 替换后的调用签名是什么；(c) 保留的 outer lifecycle 代码如何与 pipeline 的 result shape 交互。Implementation agent 需要在这三个大文件中定位具体的替换点，并确保替换后 proactive / reactive / RunInput 的行为等价。
- **为什么有问题**: Slice 2 的描述是 direction-level（"调用 shared pipeline"），不是 code-generation-ready（"在 dispatch.py:1265 处替换 self._prepare_compact_before_dispatch(...) 为 CompactPipeline.prepare_request(...)"）。Implementation agent 可能在 wiring 阶段发现需要重构 dispatch / ingest 的内部方法结构，超出 slice scope。
- **直接证据**: `dispatch.py` 4616 行、`engine_ingest.py` 6314 行、`run_input.py` 5015 行；plan Slice 2 没有列出具体的函数替换点。
- **影响**: Implementation agent 可能在 wiring 阶段花费大量时间定位替换点，或在替换时引入 unintended behavior changes。
- **建议改法和验证点**: Plan 应在 Slice 2 补充一个"替换点清单"，列出每个被替换的函数/方法、替换后的 pipeline 调用签名、以及 caller-side 的 result shape 消费方式。这不需要逐行代码，但需要足够的具体性让 implementation agent 不需重新设计。
- **修复风险（低/中/高）**: 中
- **严重程度（低）**: 低 — 不会导致错误行为，但会增加 implementation agent 的设计负担。

### 7-未修复-低-五类 Session Semantic Memory 测试等价性验证标准未定义

- **位置**: §9 Test Plan item 10
- **问题类型**: 测试缺口
- **当前写法**: Plan §9 item 10 说"proactive / reactive accepted compact 使用同一 candidate 时 memory projection 等价"。
- **反例/失败场景**: "等价"没有定义。`project_conversation_memory_event(...)` 的输入是 `CONTEXT_COMPACTED` event payload。如果 proactive 和 reactive 的 payload 字段值完全相同（operation_id、accepted attempt number、compact artifact ref、candidate digest、label mapping refs、source boundary refs、evidence mapping refs、quality check、budget after compact），memory projection 结果必然等价。但如果某些字段因 lifecycle 差异而不同（例如 proactive 没有 `attempt_id`，reactive 有），plan 没有说明如何验证"等价"。
- **为什么有问题**: 测试需要一个可操作的"等价"定义。如果 plan 不定义，implementation agent 可能写一个弱断言（例如只检查 memory kind 数量相同），或写一个过强的断言（逐字段比较，包括 lifecycle-specific 字段）。
- **直接证据**: Design doc §3193-3265 定义五类 Session Semantic Memory 的输入是 `CONTEXT_COMPACTED` payload 的 semantic sections。
- **影响**: 测试可能无法有效验证 shared pipeline 的收敛效果。
- **建议改法和验证点**: Plan 应在 §9 item 10 定义"等价"：(a) proactive 和 reactive 使用相同 `CompactionRequest` 输入时，accepted compact payload 的 semantic sections 必须逐字段相同；(b) lifecycle-specific 字段（`attempt_id`、`execution_id`、`trigger_source`）允许不同，但不影响 memory projection 输入。验证点：测试用相同 material view 和 policy 分别构造 proactive 和 reactive compact，比较 memory projection 输出。
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 低 — 不会导致 production bug，但测试可能无法有效验证收敛。
