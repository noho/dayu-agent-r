## Findings

### F20-PR-001-未修复-高-R2 recipe 把父 section 与其完整子 chunk 同时作为触发材料

- **位置**: §5.1 `Fixed profile 与真实 material recipe`、§5.2 two-boundary proof、§5.3 R2 formal contract
- **问题类型**: 动机不成立 / 范围漂移 / 最佳实践偏离 / 测试缺口
- **当前写法**: R2 固定依次、各一次读取 `s_0013`、`s_0013_c03`、`s_0013_c04`、`s_0013_c11`、`s_0013_c27`、`s_0013_c36`，并声称这些是“互不相同的业务 section”、不是 padding。
- **反例/失败场景**: 真实 corpus 中 `s_0013` 的 61,252 字符正文逐字包含上述五个子 chunk 的完整正文；五个子 chunk 合计 20,202 字符。production `read_section_max_chars=80,000`，因此父 section 和所有子 chunk 都可完整返回。同一 Run 读取它们会把至少 20,202 字符的相同财报正文以不同 canonical refs 重复加入材料。F19 Chain 02 R2 ordinary 距 soft threshold 仅 `18,874 - 15,371 = 3,503` tokens，而 20,202 个非 CJK 字符仅按 estimator 最低折算也约 6,734 tokens；重复部分本身足以成为跨阈值的决定因素。
- **为什么有问题**: binding goal 要求合法场景、禁止 padding；Host design 又明确 selected packer 不做文本去重，并要求 canonical ref 不同的相同文本保留。不同 `ref` 也产生不同 normalized argument digest，现有 attempt-scoped duplicate key不会把这些调用视作同一次 exact duplicate。也就是说，production governance 不会替 scenario 修正这个 recipe；若 proof/formal 因它触发，只能证明“重复喂入父子正文可触发”，不能证明真实、非重复业务材料在合法 setup 下可触发。
- **直接证据**:
  - `docs/gateflow/pr-190-f20-plan-20260808.md` §5.1 同时列出父 `s_0013` 和五个子 ref。
  - F19 clean seed 的真实 `sections.json`：五个 child `exact_child_inside_parent=true`；字符数分别为 2,294、5,316、5,575、3,101、3,916。
  - `dayu/config/tool_discovery.json:16` 与 `dayu/fins/tools/fins_tools.py:562`：`read_section` 正文上限 80,000 字符。
  - `dayu/host/tool_duplicate_governance.py:689-707`：duplicate key包含 normalized arguments digest与可选 semantic key；不同 `ref` 不会命中同一 exact key。
  - `docs/host/design.md` §25 material selection：相同文本但 canonical ref 不同的 selected block 必须保留，selected packer 禁止文本去重。
  - 对照检查中，R1 的 `s_0003_c04/c05/c06` 互不包含，未发现相同级别的父子全文重复；问题可收窄到 R2 recipe。
- **影响**: provider-free proof可能错误放行；三条真实 MiMo chain 会在违反 goal 的 setup 上消耗预算；即便观察到两次 compact，B2 evidence 也会因 trigger 被 padding 污染而不可裁决。
- **建议改法和验证点**:
  1. R2 只选择互不为 ancestor/descendant、正文不重叠的 refs；父 section 与其任一 child 必须二选一。最小修正优先删除 `s_0013` 父 ref，保留能独立支持 FY2025 事实的非重叠 children，再由 owner proof 判断材料是否仍足够。
  2. preflight 增加 ancestry 与正文覆盖断言：选定 ref pair 不得存在 parent-child；不得存在一方全文包含另一方或相同正文 digest。结果写入 trigger proof。
  3. 用修正后的唯一内容重新证明两次 ordinary boundary；若不能跨 soft，应 fail closed并重新做 setup goal，而不是追加重叠 section、降低 threshold或修改 duplicate governance。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### F20-PR-002-未修复-高-max-caps 上界公式没有覆盖 usage-anchored prediction 与完整 candidate estimator

- **位置**: §2 success signal 3、§5.2 `accepted-output worst case` 公式
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: 计划用最小合法 accepted fact 得到 `owner_candidate_lower_tokens`，再以 `estimate_budget_text_tokens`、section cap 和 header overhead 计算 `accepted_view_max_increment_tokens`，断言 `owner_candidate_lower_tokens + increment < hard`。
- **反例/失败场景**: Host 的 dispatch truth不是恒等于 conservative text estimate。compatible usage anchor 存在时，owner 公式是 `P_current = U_anchor + (E_current - E_anchor)`；只有 fallback 时 `P_current = E_current`。此外 complete candidate estimator对每个非空 message增加 message overhead，并计入 structured JSON与tool schemas。把五区正文的 text-token increment直接加到一个未定义的 `owner_candidate_lower_tokens` 上，既没有说明 lower 是 `E_lower`还是`P_lower`，也没有覆盖最大视图新增 system messages的 message overhead。该式可在分析文件中显示 `< hard`，但 production `ContextSizingResult.predicted_input_tokens` 的同一上界并未被证明。
- **为什么有问题**: binding goal明确要求“最大 caps 下的保守边界”，且 soft/hard action只由 typed `predicted_input_tokens`裁决。当前 plan 让 implementation agent自行决定 estimator domain和 anchor处理，破坏了 plan 的 code-generation-ready 要求。第一 ordinary boundary可能使用 R1 usage anchor；accepted compact又会使 immediate post-compact sizing失效旧 anchor，两类 stage不能用一个含糊变量统一代替。
- **直接证据**:
  - `docs/host/design.md` §25 Usage-Anchored Adaptive Context Sizing 明确 `P=U_anchor+(E_current-E_anchor)`，accepted compact后的 immediate post-compact sizing必须 conservative fallback。
  - `dayu/host/context_budget.py:951-1046` 从 anchor atoms派生 typed `predicted_input_tokens`；`dayu/host/context_budget.py:1251-1290` 的 complete estimator除文本外还计 message overhead、JSON与tool schema。
  - `dayu/host/run_input.py:2467-2487` 规定唯一完整输入估算入口是 `estimate_prepared_runner_call_candidate`，不是独立 section text estimator。
  - F19 direct evidence已经出现 `conservative_input_tokens != predicted_input_tokens` 的 usage-anchored记录，例如 Chain 01 seq20 为 `15,184 != 13,880`，证明两者不能混称。
- **影响**: pre-provider proof可能低估 hard upper，或无法证明 max accepted first replacement 后的第二 boundary仍是 soft而非 hard；formal run可能进入 block/fallback，导致 provider预算浪费或错误解释为产品行为。
- **建议改法和验证点**:
  1. 对每个 boundary显式冻结 `E_lower`、`P_lower`、estimate method、anchor identity与threshold；禁止使用未定义的 `owner_candidate_lower_tokens`。
  2. 用 production renderer构造与 lower 同源的结构性 max-cap memory view，并通过完整 `PreparedRunnerCallCandidate` estimator得到 `E_upper`；必须覆盖新增非空 section的message overhead、结构化 atoms与不变tool schemas，而非只算正文字符。
  3. fallback 分支断言 `P_upper=E_upper<hard`；usage-anchored分支断言同一 compatible anchor下 `P_upper=U_anchor+(E_upper-E_anchor)<hard`，并证明 `E_upper>=E_lower`、`P_upper>=P_lower>=soft`。accepted compact导致 anchor失效的 stage必须单独按 conservative fallback验证。
  4. `trigger-proof.json`保存上述 atoms、公式分支、完整 candidate digests和 production `ContextSizingResult` equality；corruption self-test对任一 atom变化必须FAIL。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### F20-PR-003-未修复-高-publication self-test 未封闭 canonical counts/terminal exhaustion 与 skipped-chain deadline 分支

- **位置**: §5.5 `observation-summary.json` exact contract、§5.6 publication、§7 Slice 2/3
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施 / 测试缺口
- **当前写法**: `chains[]`要求 actual counts、`terminal_refs`、chain/global deadline ref与SHA；self-test只明确校验 keyset/type/non-negative、`actual<=hard cap`、membership、terminal/seal存在及hash。provider-not-started只对`terminal_refs`给了空列表例外；计划同时允许 chain 因deadline合法skip，却没有定义此时 chain deadline owner ref/SHA 的合法值与状态。
- **反例/失败场景**:
  1. summary 把 actual ordinary count从6改成5，同时重新生成其自身SHA；只要5仍非负且不超过cap，现有明文断言不会把它与最终 typed SQLite projection重新相等校验。
  2. `terminal_refs`只列一个真实terminal而遗漏同链其它 Run/operation terminal；“non-empty + file exists + hash matches”仍可能通过，因为没有声明按 allocated run/operation做完整keyset exhaustion。
  3. global cutoff到达前第三链尚未创建active chain deadline。Slice 2允许其合法skip，schema却仍要求 non-null chain deadline ref/SHA，又没有 typed `not_started` deadline-owner artifact；实现只能留下null、伪造deadline或自行发明兼容分支。
- **为什么有问题**: F19刚因public summary缺少逐链budget/deadline owner refs与actual count/terminal contract而被Controller裁决 publication FAIL。F20虽然补了字段名和corruption目标，却没有规定字段与canonical source truth之间的exact equation，也没有关闭合法skip状态；同类问题可能再次延后到final evidence gate。
- **直接证据**:
  - F19 closeout明确记录 publication nonconforming 的根因是逐链budget/deadline owner ref/SHA缺失。
  - F19真实 Chain 03 seal为`provider_started=false`、`deadline_created=false`，证明“allocated但未创建active deadline”是已发生的现实状态。
  - F20 plan §5.5仅写 `terminal_refs` non-empty例外与存在/hash检查；没有要求其与`actual_run_count`、operation counts及最终typed projection做双向exact partition。
  - F20 plan §7允许三条 chain “已attempt或按deadline/role合法skip”，但 summary required-key contract没有对应discriminated branch。
- **影响**: publication self-test可能对遗漏/错误count或terminal假阳性；合法skip无法按schema表达；再次产生sealed后不可修的nonconforming bundle，迫使新publication identity返工。
- **建议改法和验证点**:
  1. 为 `attempted` 与 `provider_not_started` 定义互斥、穷尽的 chain summary variant。每条allocated chain都必须有 immutable deadline-owner decision artifact及ref/SHA；未启动分支记录`deadline_created=false`、global-cutoff/role stop owner ref与skip seal，不能伪造active deadline。
  2. 明确 source equations：actual run/ordinary/compactor/operation counts必须逐字段等于final typed SQLite projection；terminal refs必须与 allocated且实际开始的 Run/operation canonical terminal keyset双向完全相等，无遗漏、无额外、无duplicate。
  3. self-test必须从digest-verified private typed projection与seal重新计算summary，而不是信任summary自身；逐项修改count、删/换terminal、替换deadline状态都必须在不依赖预存expected文本的情况下FAIL。
  4. 在 Slice 2创建任何 provider前先运行 attempted/skip 两个variant的schema与corruption tests，确保 Slice 3无需重新设计publication contract。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
