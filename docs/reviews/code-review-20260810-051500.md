## 3. Findings

### Finding R01 — `_terminal_disposition_from_counts` 存在不可达 dead code【低严重度 / correctness】

**直接代码证据：**

`dayu/fins/download_contract.py:480-508`，函数 `_terminal_disposition_from_counts`：

```python
def _terminal_disposition_from_counts(*, discovered_count, downloaded_count, rejected_count, failed_count):
    if failed_count == 0:
        return FinsDownloadTerminalDisposition.SUCCEEDED
    if downloaded_count == 0 and rejected_count == 0:
        return FinsDownloadTerminalDisposition.FAILED
    if discovered_count > 0:
        return FinsDownloadTerminalDisposition.PARTIAL_FAILURE
    return FinsDownloadTerminalDisposition.FAILED  # ← 不可达
```

**分析：**

由 `FinsDownloadResultSummary.__post_init__` 不变量保证 `discovered_count == downloaded + skipped + rejected + failed`。当 `failed_count > 0`（通过第一个 if）且 “not (downloaded==0 and rejected==0)”（通过第二个 if），意味着 `downloaded > 0` 或 `rejected > 0`，加之所有 counts 非负，必有 `discovered_count > 0`。因此第三个 if 条件恒真，最后的 `return FAILED` 不可达。

**影响：**

不产生运行时错误，但表明推理不完整。若将来放宽 `__post_init__` 不变量（例如允许 `discovered_count=0`），该 dead code 会意外激活并返回错误终态。

**Owner 修法：**

在 `download_contract.py` 中将最后的 `return FAILED` 替换为 `assert_never` 或直接删除该行并加注释说明 reachability 由 invariant 保证。

### Finding R02 — CN/HK adapter 将所有 workflow 级失败统一映射为 `UNKNOWN` transport category【中严重度 / correctness】

**直接代码证据：**

`dayu/fins/pipelines/cn_pipeline.py:1394-1400`，`CnDownloadAdapter.download()`：

```python
if _required_cn_text(result, "status") == "failed":
    raise FinsDownloadProviderError(
        source=request.source,
        transport_category=FinsDownloadTransportCategory.UNKNOWN,
        retryable=True,
        safe_message="财报来源请求失败",
    )
```

**分析：**

CN/HK workflow 的 status=`"failed"` 可源于多种不同性质的故障：网络超时、连接拒绝、HTTP 状态码异常、响应解析失败等。当前实现将所有 CN/HK 来源故障统一映射为 `UNKNOWN` + `retryable=True`。

与 SEC 侧对比：SEC downloader 在 `_execute_sec_request` 中精细区分 `TIMEOUT` / `CONNECTION` / `HTTP_STATUS` / `PROTOCOL` / `UNKNOWN` 五类 transport category，并各自给出针对性 `retryable` 判断。

**影响：**

- 对于 CN/HK 来源的非可重试故障（如持久性 403/404），`retryable=True` 会误导重试建议。
- `safe_message` 固定为"财报来源请求失败"，不区分具体故障性质，降低了用户排障效率。
- public failure 的 `retry_hint` 分支因此会给出"请稍后重试"的建议（因为 `retryable=True`），对不可重试故障不准确。

**Owner 修法：**

在 CN/HK downloader（`cninfo_downloader.py` / `hkexnews_downloader.py`）的异常抛出点增加 typed error 映射，或在 `cn_pipeline.py` 的 adapter 层增加对 workflow 私有错误码的解析，区分 `TIMEOUT` / `CONNECTION` / `HTTP_STATUS` / `PROTOCOL` 并设置正确的 `retryable`。若 CN/HK downloader 当前确实没有 granular error typing，应在代码中加注释说明这是已知限制，并把 `retryable` 设为保守值。

### Finding R03 — `_classify_direct_error` 将 CONFIGURATION 失败归入 PROVIDER 分类【低严重度 / semantic】

**直接代码证据：**

`dayu/fins/ingestion_runtime.py:5205-5206`：

```python
if isinstance(exc, FinsDownloadProviderError):
    return FinsErrorKind.PROVIDER
```

而 `SecUserAgentConfigurationError` 是 `FinsDownloadProviderError` 的子类，其 `transport_category=UNCONFIGURED`。在 `_download_public_failure_from_exception` 中正确地映射为 `FinsPublicFailureKind.CONFIGURATION`，但 `_classify_direct_error` 始终返回 `FinsErrorKind.PROVIDER`。

**分析：**

`FinsErrorKind` 与 `FinsPublicFailureKind` 是两个独立的分类体系：
- `FinsErrorKind` 用于 `FinsResultSummary.error_kind`（内部 direct event 分类）
- `FinsPublicFailureKind` 用于 `FinsPublicFailure.kind`（对 CLI/LLM 公开的分类）

虽然 `FinsResultSummary.__post_init__` 不强制 `error_kind` 与 `failure.kind` 一致，但语义上 `error_kind=PROVIDER` 对未配置 User-Agent 的场景不够精确——这不是 provider 侧的问题，而是部署配置问题。

**影响：**

仅在 `error_kind` 字段层面产生语义偏差；public failure 投影正确（使用 `FinsPublicFailureKind.CONFIGURATION`）。CLI 和 wait adapter 均直接消费 public failure，不依赖 `error_kind`。

**Owner 修法：**

在 `_classify_direct_error` 中增加对 `SecUserAgentConfigurationError` 的特判，或增加 `FinsErrorKind` 的 CONFIGURATION 成员。如果认为这不是当前优先事项，至少在代码中加注释说明此分类差异是有意为之。

### Finding R04 — download_contract `_validate_public_text` 与 direct_events `_validate_safe_text` 命名与检查集不一致【低严重度 / maintainability】

**直接代码证据：**

`dayu/fins/download_contract.py:832-835`，`_validate_public_text` 的禁止内容检查：

```python
lowered = stripped.lower()
if "://" in lowered or "raw payload" in lowered or "provider payload" in lowered:
    raise ValueError(f"{field_name} contains disallowed transport content")
if stripped.startswith(("/", "\\")) or re.match(r"^[A-Za-z]:\\", stripped):
    raise ValueError(f"{field_name} contains an absolute path")
```

`dayu/fins/direct_events.py:1071-1082`，`_validate_safe_text` 的禁止内容检查：

```python
lower = value.lower()
if "://" in lower:
    raise ValueError(f"{field_name} contains a URL")
for fragment in _DISALLOWED_TEXT_FRAGMENTS:
    if fragment in lower:
        raise ValueError(f"{field_name} contains disallowed internal text")
if _FINS_JOB_ID_PATTERN.search(value):
    raise ValueError(f"{field_name} contains a job id")
if _ABSOLUTE_POSIX_PATH_PATTERN.search(value):
    raise ValueError(f"{field_name} contains an absolute path")
if _ABSOLUTE_WINDOWS_PATH_PATTERN.search(value):
    raise ValueError(f"{field_name} contains an absolute path")
```

**分析：**

1. **命名混乱**：`_validate_public_text` 名字暗示是"公开文本校验"，但实际上用于 download contract 的内部字段校验（`document_id`、`reason_message` 等）。这些字段不会直接进入 LLM 上下文。真正进入 LLM 上下文的校验是 `_validate_safe_text`。命名与职责不匹配，容易导致 future contributor 误用。

2. **检查集差异**：
   - `_validate_public_text` 不检查 job ID、内部治理标识（如 "job_id", "event sequence", "cursor" 等），因为它用于内部 contract 字段。这是正确的，但需要文档说明。
   - `_validate_safe_text` 使用正则匹配绝对路径，比 `_validate_public_text` 的简单前缀匹配更严格。两者应至少对齐路径检查策略。
   - `_validate_public_text` 使用 `"raw payload" in lowered` 子串匹配，但 `_validate_safe_text` 使用 `_DISALLOWED_TEXT_FRAGMENTS` tuple（其中包含 "raw payload"），语义等价但实现不同。

3. **风险**：若将来有人把 `_validate_public_text` 用于 LLM-facing content（被函数名误导），会绕过 job ID 和内部标识的泄漏守卫。

**Owner 修法：**

- 重命名 `_validate_public_text` 为 `_validate_contract_text` 或 `_validate_download_field`，明确其内部 contract 校验职责。
- 在 docstring 中明确两个函数的适用边界：`_validate_safe_text` 用于 LLM-facing / external consumer 可见内容；`_validate_contract_text` 用于 internal typed contract 字段。
- 考虑将两个函数的公共检查逻辑抽取为共享 helper（如路径检查），避免未来一边更新另一边遗漏。

### Finding R05 — `SecDownloader.configure()` 与 workflow host 的二次 UA 配置存在潜在不一致风险【低严重度 / robustness】

**直接代码证据：**

`dayu/fins/downloaders/sec_downloader.py:1069-1103`，`configure()` 方法：

```python
def configure(self, user_agent, sleep_seconds, max_retries):
    ...
    configured_value = None if user_agent is None else user_agent.strip()
    if configured_value and configured_value != self._user_agent:
        raise ValueError("SEC User-Agent 必须在 downloader 构造时一次性配置")
```

`dayu/fins/pipelines/sec_download_workflow.py:378`：

```python
host._downloader.configure(
    user_agent=host._user_agent,
    sleep_seconds=host._sleep_seconds,
    max_retries=host._max_retries,
)
```

**分析：**

`SecPipeline.__init__` 现在将 `user_agent` 直接传给 `SecDownloader` 构造函数，使得 UA 在构造时解析。但 `sec_download_workflow.py` 仍然通过 `configure()` 二次传入 `host._user_agent`。

当前逻辑下，如果 `host._user_agent` 与构造时解析值一致（同为 None 或同一字符串），configure 静默通过。但如果 workflow host 的 `_user_agent` 为非 None 且与构造时解析值不同，`configure()` 会抛出 `ValueError`——这是一个运行时故障，表明 pipeline 构造与 workflow host 之间的 UA 来源不一致。

虽然 plan 已将 workflow 的二次 configure 视为调参（调整 sleep_seconds、max_retries），但 `user_agent` 参数仍然存在并参与校验，构成了一个隐式契约：workflow host 的 UA 必须与 downloader 构造时 UA 一致。这个契约没有被显式文档化或测试覆盖。

**影响：**

如果将来有人修改 workflow host 的 UA 来源而不更新 pipeline 构造函数，会在运行时触发 ValueError。当前所有已知路径一致，但缺乏防御性测试。

**Owner 修法：**

- 在 `configure()` 的 docstring 中显式说明 `user_agent=None` 表示"不改动已配置身份"的语义。
- 或在 workflow 中不再传递 `user_agent` 给 `configure()`，仅传递 `sleep_seconds`、`max_retries`，从根本上消除不一致风险。
- 增加一个 owner test：构造 downloader 时传入 UA="A"，然后用 `configure(user_agent=None)` 确认不抛异常、UA 保持 "A"。

### Finding R06 — Test 覆盖缺口：CN/HK rebuild path 的 missing_periods 条件分支【中严重度 / coverage】

**直接代码证据：**

`dayu/fins/pipelines/cn_pipeline.py:1453-1457`：

```python
missing_periods = (
    ()
    if request.rebuild_local_artifacts and "missing_periods" not in result
    else _required_cn_text_list(result, "missing_periods")
)
```

**分析：**

此分支有两路：
1. `rebuild=True` 且 `missing_periods` 字段不在 result 中 → 返回空 tuple
2. 其他情况 → 从 result 严格读取 `missing_periods` 列表

当前测试 `tests/fins/test_cn_download_runtime.py` 的 CN pipeline 测试覆盖了正常的 missing_periods 路径（路径 2），但没有覆盖 `rebuild=True` 且 workflow result 不包含 `missing_periods` 字段的路径（路径 1）。如果 workflow 在 rebuild 模式下确实不产出 `missing_periods`，则 production 行为正确但未被测试证明；如果 workflow 在 rebuild 模式下实际产出了空 `missing_periods` 列表（而非不包含该 key），则条件 `"missing_periods" not in result` 为 False，会进入 `_required_cn_text_list` 并正常返回空 tuple——两路等价，无实际 bug；但如果 workflow 在 rebuild 模式下产出非空 `missing_periods`，则第一个分支不会激活，这是正确的（因为 rebuild 也可能有 missing periods）。

**影响：**

主要是 coverage gap——测试未显式验证 rebuild 路径的 behavior。不是 correctness bug。

**Owner 修法：**

在 `tests/fins/test_cn_download_runtime.py` 中增加一个 CN rebuild 测试 case：构造 workflow result，设置 `rebuild_local_artifacts=True`，不包含 `missing_periods` 字段，断言返回的 summary 中 `missing_periods=()`。

### Finding R07 — `FinsDownloadResultSummary` 零-candidate + FAILED/CANCELLED 终态的 `__post_init__` 校验逻辑正确但隐含语义需文档化【低严重度 / maintainability】

**直接代码证据：**

`dayu/fins/download_contract.py:355-358`：

```python
empty_terminal_override = self.discovered_count == 0 and self.terminal_disposition in {
    FinsDownloadTerminalDisposition.FAILED,
    FinsDownloadTerminalDisposition.CANCELLED,
}
if self.terminal_disposition is not expected_terminal and not empty_terminal_override:
    raise ValueError("terminal_disposition does not match download outcome")
```

**分析：**

当 `discovered_count=0` 时，`_terminal_disposition_from_counts(0,0,0,0)` 返回 `SUCCEEDED`，但 `empty_terminal_override` 允许 FAILED/CANCELLED 覆盖。这使得 `_empty_download_summary_from_request` 可以构造 `terminal_disposition=FAILED` 或 `CANCELLED` 的零-candidate summary。

这个设计的语义是：零 candidate + FAILED = adapter 未完成之前就失败了（如找不到 adapter、unsupported source）；零 candidate + CANCELLED = 取消发生在 adapter 启动前。

语义合理，但 `empty_terminal_override` 的 docstring 和注释未解释何时应该用 FAILED vs CANCELLED for zero-candidate。且该 override 只允许 FAILED 和 CANCELLED，不允许 SUCCEEDED 之外的其他值，这是正确的约束。

**Owner 修法：**

在 `__post_init__` 或类 docstring 中增加对 zero-candidate 终态 override 的语义说明。

### Finding R09 — Storage locator 查询在 publication guard 内执行，但异常安全边界需验证【低严重度 / robustness】

**直接代码证据：**

`dayu/fins/storage/_fs_source_document_core.py:444-451`：

```python
guard_token = self._acquire_publication_guard(external_ticker)
try:
    self._get_persisted_source_meta_unguarded(external_ticker, external_document_id, normalized_source_kind)
    document_dir = self._source_meta_path_for_read(...).parent
    relative = document_dir.relative_to(self.workspace_root)
    return PurePosixPath(*relative.parts)
finally:
    self._release_lock_token(guard_token)
```

**分析：**

`get_source_document_locator` 先获取 meta（验证 published 身份），再构造相对路径。publication guard 保护了 meta 读取与路径构造之间的原子性。这是正确的。

但 `relative_to` 在 `document_dir` 不是 `workspace_root` 的子目录时会抛出 `ValueError`（不是 `OSError`），而函数签名只声明可能抛出 `OSError`。如果 storage 内部状态异常导致 document_dir 不在 workspace_root 下，会以未声明的异常类型失败。

**影响：**

极低概率的 storage corruption 场景。当前 production 路径下 document_dir 始终在 workspace_root 内，因为这个约束由 storage 内部强制执行。

**Owner 修法：**

在 docstring 的 Raises 部分增加 `ValueError`（当 document 目录不在 workspace 内时），或在 `relative_to` 调用处捕获 `ValueError` 并包装为有意义的错误消息。
