### 1-HEAD-existing-中-watchdog `request_cancel` exact-count 间歇性失败

- **入口/函数**: `test_open_host_active_cancel_watchdog_public_watch_observes_cancelled`
- **文件(行号)**: `tests/host/test_open_host_runtime.py:1652`
- **输入场景**: 6-file suite 联合运行时，`_HostCancellationToken.request_cancel` 被同线程调用两次而非预期一次。5-file suite（不含 `test_session_attachment_registry.py`）2 次运行均通过。
- **实际分支**: `token_threads == [8267718016, 8267718016]`，`request_cancel` 在同线程被调用两次。
- **预期行为**: cancel 操作恰好触发一次 `request_cancel`。
- **实际行为**: 间歇性两次调用，导致 `assert token_threads == [opener_thread_id]` 失败。
- **直接证据**:
  - HEAD 的 active cancel 同时有 commit 后 `ActiveWorkerRegistry.cancel` 直接调用和每 0.01s `reconcile_active_worker_cancels_once` best-effort 重传播两条路径。
  - `_HostCancellationToken.request_cancel` 自身幂等（重复调用不改变 durable 状态），但测试 monkeypatch 的 `record_token_cancel` 计数器不幂等。
  - S3 diff 未改变 `request_cancel`、`ActiveWorkerRegistry.cancel`、`reconcile_active_worker_cancels_once`、`wake_active_cancel_watchdog` 或任何 cancel/watchdog owner。plan §7.6 明确声明"不改变 accepted cancel watchdog owner"。
  - 6-file suite 5 次运行中 2 次失败、3 次通过，典型的 monkeypatch 计数器在 asyncio 竞态下的 exact-count race。
- **影响**: 不影响生产代码正确性。降低 CI 稳定性 — 若 CI 以随机顺序运行 test 文件可能偶尔触发误报失败。
- **建议改法和验证点**: 本项是 HEAD-existing test exact-count race。S3 不应修改 production cancel owner 或测试 oracle。修复方向应在后续独立迭代中将 `record_token_cancel` 改为 set-based 去重或增加容差断言，而非在本 slice 改动。
