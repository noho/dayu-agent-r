## Findings

### FS-1-中等-Slice 2 集成 `build_pre_dispatch_compact_material_view` 的具体映射 underspecified

- **位置**: Slice 2 — "在 provider 读 transaction 中调用 `build_pre_dispatch_compact_material_view`"
- **问题类型**: 不可直接实施
- **当前写法**: 计划要求 `DurableAcceptedToolEvidenceMaterialProvider` 在 read transaction 内调用 `build_pre_dispatch_compact_material_view`，从返回的 `material_blocks` 选取 `ACCEPTED_TOOL_EVIDENCE`，再排除 represented refs。
- **反例/失败场景**: 实施 Agent 可能在以下细节上犯错：
  1. `build_pre_dispatch_compact_material_view` 构造了 `PreDispatchCompactMaterialView` 的全部内容（previous_compacted_view、budget_fragments、current_input_text 等），但证据 provider 只需要 `material_blocks`。多余构造增加了计算开销（读取 latest compacted event、构造 previous view、构建 budget fragments）。虽然对于 evidence provider 的单次调用成本可接受，但如果未来在 hot path 上调用，需要关注。
  2. `build_pre_dispatch_compact_material_view` 内部调用 `_validated_current_input_event(transaction, event_log_store, run=run, current_display_text=current_display_text)` 重新读取 `USER_INPUT_ACCEPTED` 事件，但 `CurrentRunFacts` 已经持有 `user_input_event` EventLogRow（run_input.py:290）。存在冗余 EventLog read。
  3. `build_pre_dispatch_compact_material_view` 内部的 represented_refs 过滤只基于 previous compaction event。provider 还需要额外按 `_represented_evidence_refs(memory, compact)` 再次过滤（因为 memory/compact provider view 可能包含比 previous compaction 更新的 refs）。计划提到了这步，但实施 Agent 可能漏掉。
- **为什么有问题**: 计划当前给了正确方向但未给出实施 Agent 需要的精确接口映射。实施 Agent 需要自己推断 mapping 细节，可能引入不必要的读开销或漏掉过滤步骤。
- **直接证据**: 
  - `CurrentRunFacts` 定义于 run_input.py:273-295，`run: RunRow` 字段可用。
  - `build_pre_dispatch_compact_material_view` 定义于 compact_material.py:432-553，返回 `PreDispatchCompactMaterialView`，其中 `material_blocks: tuple[RunInputMaterialBlock, ...]` 包含所有 section blocks。
  - 当前 `run_input.py` 中不存在对 `build_pre_dispatch_compact_material_view` 的调用（grep 确认）。
  - 当前 `build_accepted_tool_evidence_material_blocks` 在 run_input.py:1407-1484 通过 `_recent_accepted_tool_result_rows` + `collect_selected_compaction_request_evidence_inputs` 构造 blocks，已复用 evidence input reader 但未复用 material view builder。
- **影响**: 实施 Agent 可能做多余 EventLog 读或漏掉 represented refs 二次过滤，导致重复 evidence 进入 compact input。
- **建议改法和验证点**:
  1. 在 plan 中明确：`build_pre_dispatch_compact_material_view` 的 `current_display_text` 参数取 `current_facts.user_prompt`（与当前 material construction 同源）。
  2. 确认 `build_pre_dispatch_compact_material_view` 内部的 `_validated_current_input_event` 对已持有 EventLogRow 的场景是否需要 bypass；若不需 bypass，接受冗余读并在 implementation report 中记录。
  3. 在 plan 中明确 provider 的二次过滤步骤：`represented_refs = _represented_evidence_refs(memory, compact)`，然后用 `frozenset(represented_refs)` 过滤 `material_blocks` 中的 `ACCEPTED_TOOL_EVIDENCE` blocks。
  4. 验证：provider 测试应确认 memory/compact represented refs 正确排除 evidence blocks，不重复进入。
- **修复风险**: 低（只需补充 plan 中的映射细节，不改变架构方向）
- **严重程度**: 中等（不影响架构正确性，但影响实施 Agent 的一次成功率）

### FS-2-低-`_evidence_chunks` helper 的保留决策存在歧义

- **位置**: Slice 1 — "若实施中保留 chunk helper，只能作为显式预算触发 helper"
- **问题类型**: 范围漂移 / 过度设计
- **当前写法**: 计划说删除默认 chunking，但允许保留 `_evidence_chunks` 作为"显式预算触发 helper"；同时又明确"本 WU 不要求新增该预算触发路径"。
- **反例/失败场景**: 实施 Agent 可能保留 `_evidence_chunks`、`_EvidenceChunk` dataclass、`evidence_chunk_label` helper 及相关测试作为 dead code，等待一个本 WU 已明确不实现的未来预算触发路径。这会留下未经调用验证的半成品代码，增加后续维护负担和 pyright 误报风险。
- **为什么有问题**: 计划在两个方向间摇摆：一方面说删除默认 chunking，另一方面允许保留 helper。如果当前没有生产调用、也没有本 WU 的预算触发路径，保留代码就是 dead code，违反编码硬约束"禁止兼容性代码"。正确的裁决应该是：要么删除，要么明确写出 production caller。
- **直接证据**:
  - `_evidence_chunks`（compact_material.py:2937-2979）当前只被 `_pack_evidence_blocks`（line 2852）和 `_provenance_from_evidence_blocks`（line 2915）调用。如果这两处都不再 chunk，`_evidence_chunks` 没有其他调用者。
  - `_EvidenceChunk` dataclass 和相关 helper（`evidence_chunk_label`、`_text_digest`）也会变为 dead code。
  - 计划说 chunk helper 可以为显式预算触发保留，但本 WU 不实现该路径。这意味着代码在修复完成后无生产调用者。
- **影响**: 留下未经调用验证的 dead code，增加 pyright 扫描负担和后续维护误解风险。但不影响修复的正确性——即使保留 dead code，默认路径已经不再 chunk。
- **建议改法和验证点**: 裁决二选一：
  - A：完全删除 `_evidence_chunks`、`_EvidenceChunk`、`evidence_chunk_label` 及相关测试，等 WU-CM-13 需要时再按需求重新设计预算 chunk helper。
  - B：接受保留 dead code，在常量审计中标注为 `deferred-with-owner`（owner: WU-CM-13），并在代码上加 `# deferred: WU-CM-13 explicit budget chunk helper` 注释。
  - 推荐 A，符合编码硬约束"禁止兼容性代码"。
- **修复风险**: 低
- **严重程度**: 低（不影响正确性，cleanup 级别）

## Architecture boundary review

**Pass.** The plan correctly maintains:

- **Host ↔ Engine boundary**: No changes to Engine contract. The constants being removed are Host-local DTO validation guards. Engine's `context_compaction_requested` + `run_failed(recoverable=True)` remains the sole provider context overflow signal.
- **Host ↔ Service boundary**: No new Service seam. No public API changes.
- **Layer ownership**: DTO validation remains in `compaction.py`; material construction remains in `compact_material.py`; evidence provider remains in `run_input.py`. No cross-layer ownership transfer.
- **Durable truth boundary**: EventLog remains single durable truth. The fix removes private DTO caps that were acting as a second, lower-quality truth filter.
- **Context Governance boundary**: Budget/selection/floor/fail-closed remains the sole material sizing authority. The fix removes DTO field-length as a competing authority.

## Best-practice review

**Pass.** The plan:

- Removes illegal guards rather than patching around them (root cause fix).
- Reuses `build_pre_dispatch_compact_material_view` as single EventLog truth source rather than inventing parallel retrieval.
- Tests cover both DTO conversion layer and real provider entry, not just internal helpers.
- Clear stop conditions: if implementation requires public schema/Engine contract changes, stop and return to plan gate.

## Optimal-solution review

**Pass.** The plan's approach is the simplest path that achieves the goal:

- Delete four private constants and their enforcement sites.
- Change bounded checks to non-empty checks.
- Reuse existing truth source (`build_pre_dispatch_compact_material_view`) instead of building a new one.
- No new abstractions, no new policy fields.

Alternative considered and rejected: keeping the constants but raising them to very large values. This would preserve dead code and maintain the architectural confusion of DTO-as-budget-guard. The plan's approach is superior.

## Overengineering review

**Pass.** The plan explicitly resists overengineering:

- No new policy schema fields.
- No new Host/Service seam.
- No summary/preview/truncation of large evidence.
- No second material budget truth (uses existing `memory_projection_policy` and `build_pre_dispatch_compact_material_view`).
- WU-CM-13 reactive recovery is explicitly deferred, not partially implemented.

The plan correctly identifies that "字段超过 1200/4096" or "第 9 条 accepted evidence" are not hard stop conditions and that Context Governance budget is the correct answer.

## Overcoupling review

**Pass.** The slice decomposition is clean:

- Slice 1 touches `compaction.py` + `compact_material.py` (DTO guards + chunking) — same material output pipeline.
- Slice 2 touches `run_input.py` (evidence provider limit) — independent retrieval path.
- Slice 3 is validation-only (tests + constant audit).

No cross-slice coupling. Each slice is independently verifiable. No shared mutable state introduced. No widened public contracts.
