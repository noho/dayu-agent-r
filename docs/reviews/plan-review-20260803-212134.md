## Findings

### F01-未修复-高-`session_summary: null` 的 proposed 语义与 Memory replacement owner 相反

- **位置**: Goal Confirmation 的 `session_summary / null` 定义。
- **问题类型**: 契约缺失 / 状态语义错误。
- **当前写法**: “本 candidate 不提供新的总体摘要 replacement，不表示删除已有摘要。”
- **反例/失败场景**: 已有 accepted summary 后，下一次 accepted candidate 返回 `session_summary: null`。模型按 proposed prompt 认为旧摘要仍保留，但 Memory projection 实际清空旧 summary。
- **为什么有问题**: accepted compact candidate 是五类 Session Semantic Memory 的完整 replacement，不是 patch。LLM-facing prompt 若承诺 preserve，而持久化 owner 执行 clear，会产生“prompt 正确、durable memory 相反”的同源违规，并丢失跨轮摘要。
- **直接证据**: `dayu/host/memory.py:1229-1255` 在 `CONTEXT_COMPACTED` 上整体替换五类 memory；`dayu/host/memory.py:1720-1739` 对 `session_summary is None` 返回 empty view；`tests/host/test_memory_projection.py:1408-1442` 明确锁定 “without summary clears prior session summary”。
- **影响**: 实施后模型可能基于错误 contract 返回 null，Host 却清空既有摘要，造成 durable conversation continuity 丢失。
- **建议改法和验证点**: 冻结为：“`null` 表示本次完整 replacement 不包含 session summary；candidate 被接受后，当前 Session Summary Memory 变为空，包括清除既有摘要。它不影响 candidate 中其它四类业务语义项。” Prompt owner test 必须断言该语义，并继续引用既有 Memory owner regression。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 高。

### F02-未修复-中-`evidence_facts.claim` 与 `policy_limit` 的 proposed 条件尚未和模型实际可见输入同源

- **位置**: Goal Confirmation 的 `evidence_facts.claim` 与 `policy_limit` 定义。
- **问题类型**: 契约缺失 / open question 未收敛。
- **当前写法**: claim 被描述为“由工具证据直接支持”；`policy_limit` 被描述为“满足明确 memory policy 上限时必须舍弃”。
- **反例/失败场景**: `support_labels` 合法引用 `previous_evidence_fact` 而不是当前 `evidence_material`；或首次 proposal 没有 repair feedback/cap 数值，模型仍从 enum 名猜测并使用 `policy_limit`。
- **为什么有问题**: typed contract 明确允许 `evidence_material` 和 `previous_evidence_fact` 两种 support kind，不能把后者隐式排除。精确 Memory cap 只在 Context Governance reject 后经 repair feedback 投影给模型；首次 proposal 没有 cap 数值，因此“明确上限”必须说明其可见来源，不能要求模型猜 policy。
- **直接证据**: 当前 prompt 对 `support_labels` 允许两种 source kind；`dayu/host/context_governance.py` 只在 candidate 验收超 cap 后生成 actual/cap repair message；首次请求按 prompt contract 不含 repair feedback。
- **影响**: 模型可能无故丢弃合法 previous fact，或在无 cap 证据时滥用 `policy_limit`；drop audit 仍不具备可执行、互斥语义。
- **建议改法和验证点**:
  - `claim` 改为“可独立阅读、且由 `support_labels` 对应的 accepted `evidence_material` 或 `previous_evidence_fact` 直接支持的业务事实”。
  - `policy_limit` 改为“内容仍相关，但当前 repair feedback 已给出具体 cap，且为把完整 replacement 降到该 cap 内必须舍弃；首次请求或没有具体 cap 的反馈时不得猜测使用。”保留“不得隐藏冲突、无依据内容或分类困难”。
  - 测试同时锁定 previous-evidence support 与无 cap 不得使用 `policy_limit` 的文字 contract；不增加 Host semantic verifier。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。

- Prompt 拥有 LLM-facing 解释、typed contract 拥有 shape/enum、Context Governance 独占 accept/reject、Memory 独占 projection：边界正确，无需新增 verifier 或修改 schema。
- 仅修改 packaged user prompt、prompt owner tests 与派生 hash/manifest 是最小且可维护的路径；没有必要扩张 provider/model 或 readiness proof scope。
- `docs/reviews/pr-190-review-20260803-203709.md` 是本 finding 的历史 review artifact，应原样保留并可随修复提交；修复后另产 rereview/closeout，不应回写旧 artifact。
