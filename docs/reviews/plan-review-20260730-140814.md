## Findings

### 1-未修复-中-PERSIST_CONFIRM 退出码 1 与 RESET_CONFIRM 退出码 0 不一致

- **位置**: §6.4 Init interaction state machine
- **问题类型**: 契约缺失 / 状态机漏洞
- **当前写法**:
  ```
  RESET_CONFIRM?  -- Enter/No --> CANCELLED_SUCCESS(0)
  PERSIST_CONFIRM? -- Enter/No --> FAILURE(1), no workspace publication
  ```
- **反例/失败场景**: 用户完成模型选择、endpoint、context window、secret 输入，走到 PERSIST_CONFIRM 时改变主意按 Enter（默认 No）。此时 init 已完成 staging validation（`prepare_workspace_transaction` 在 PERSIST_CONFIRM 之后），staging 被 abort。用户看到 exit 1 表示"失败"，但实际上用户只是主动取消了一个可选步骤。而 RESET 确认时按 Enter 同样是"不做了"，却 exit 0。
- **为什么有问题**: Oracle `init.secret-handling` 说"拒绝或 EOF 时 workspace 不发生部分发布"，但未指定退出码。Oracle `init.interactive-validation-and-exit` 对 RESET 明确要求 Enter=No→0。两者同为"用户拒绝继续"，退出码不同会导致脚本/CI 难以区分"用户主动取消"与"真实 transaction failure"。
- **直接证据**:
  - Oracle: `init.interactive-validation-and-exit` expected: "reset 确认时直接 Enter 选择默认 No，workspace 不变并退出 0"
  - Oracle: `init.secret-handling` expected: "拒绝或 EOF 时 workspace 不发生部分发布"（未指定退出码）
  - Plan §6.4 状态机 PERSIST_CONFIRM: Enter/No → FAILURE(1)
- **影响**: 实施 Agent 可能实现不一致的用户契约；CI automation 难以区分主动取消与故障
- **建议改法和验证点**: 明确定义 PERSIST_CONFIRM Enter/No 的退出码语义并在 plan 中显式记录决策。建议与 RESET_CONFIRM 保持一致（exit 0），因为两者都是用户主动拒绝。若坚持 exit 1，须在 plan 中写明理由
- **修复风险**: 低 — 仅需澄清决策，不改变实现结构
- **严重程度**: 中

### 2-未修复-中-S1 dual-parent argparse 方案缺少非-init `--config` 行为回归测试

- **位置**: §9 S1 — "invariants: 非-init 的 `--config` 在 command 前/后仍可用"
- **问题类型**: 测试缺口
- **当前写法**: S1 tests 只列出 "init help absence; init config before/after command exit 2; prompt/interactive/session resume help 与 long/short form; `--model-name` exit 2; conversion 精确为 model id"
- **反例/失败场景**: common/runtime parent 重构后，`dayu-cli prompt --config /tmp "hello"` 或 `dayu-cli --config /tmp prompt "hello"` 的 `--config` 行为可能被 argparse parent 继承链意外改变。当前 S1 tests 没有一条断言 "非-init 命令的 `--config` 仍正常工作"。
- **为什么有问题**: S1 改变的是所有命令共享的 parent 结构。Plan 声称非-init `--config` 不变作为 invariant，但没有对应的测试用例来封闭。如果 implementation agent 在重构 parent 时引入回归，现有测试套件不会捕获。
- **直接证据**:
  - Plan §9 S1 invariants: "非-init 的 `--config` 在 command 前/后仍可用"
  - Plan §9 S1 tests: 无对应测试项
  - 生产代码 `arg_parsing.py:308`: `--config` 在 global parent 中注册，被所有命令继承
- **影响**: 非-init 命令的 `--config` 行为可能被静默破坏
- **建议改法和验证点**: S1 tests 中新增至少一项：`prompt --config <path> "hello"` 成功解析且 `config_dir` 正确映射
- **修复风险**: 低 — 增加一条参数化测试
- **严重程度**: 中

### 3-未修复-中-S2 context window 校验引入 execution profile 加载依赖，未指定加载范围

- **位置**: §9 S2 exact changes #4: "catalog validation 返回/提供 package default execution profile typed minimum，不增加 loose JSON read"
- **问题类型**: 不可直接实施 / 架构边界
- **当前写法**: Plan 说应从 ConfigLoader typed default profile 读取 minimum（262144），但未指定具体 API 调用路径。当前 `_select_model()` 只通过 `validate_init_catalog` 加载 `ModelsConfig`；`ExecutionProfileConfig` 的加载需要 `ConfigLoader.load()` 或至少 `ConfigLoader.load_execution_profiles()`，这会引入 `execution_profiles.json` schema 校验到 init 交互的最早阶段。
- **反例/失败场景**: 如果 package `execution_profiles.json` 存在 schema 问题（如字段缺失），当前 init 流程仍可正常展示模型选择并进入 staging（staging 阶段才加载完整 RuntimeConfig）。Plan 方案下，init 会在展示模型选择之前就因 execution profile 加载失败而退出。这是行为回归 — 用户无法通过 init 修复一个已损坏的 workspace config（因为 package config 是只读的）。
- **为什么有问题**: Plan 把 profile 兼容性校验从"staging 后的最终 fail-fast"提前到"交互过程的第一步"，但 profile 属于 package 只读资产而非 workspace 可变资产。用户不能通过交互修正 package 问题，所以提前失败没有收益，只会阻止用户完成 init 流程的其他步骤。
- **直接证据**:
  - 生产代码 `commands/init.py:395`: `validate_init_catalog(_PACKAGE_CONFIG_ROOT, _PACKAGE_MANIFEST_ROOT)` 只加载 ModelsConfig
  - 生产代码 `init_workspace.py:467`: `ConfigLoader(package_config_dir=staged_config_root).load()` 加载完整 RuntimeConfig，仅在 staging 阶段发生
  - Plan §5 语义 owner: "default profile minimum: ConfigLoader typed execution profile"
  - Plan §4.3: "init 不复制 profile 分档常量；它从真实 ConfigLoader typed default profile 取得 minimum"
- **影响**: 实施 Agent 可能错误地在 `_select_model()` 之前加载完整 RuntimeConfig，引入不必要的 schema 依赖和不正确的 fail-early 行为
- **建议改法和验证点**:
  1. 明确定义 context minimum 的数据流：是从 `ConfigLoader(package_config_dir=...).load()` 的 `RuntimeConfig` 中提取，还是有更轻量的路径？
  2. 若 package execution_profiles.json 损坏，context minimum 应降级为合理上限（如 262144）还是 fail closed？
  3. Plan 应明确加载发生在哪个函数、哪个 try/except 边界
- **修复风险**: 中 — 需要澄清 API 调用路径与错误处理语义
- **严重程度**: 中

### 4-未修复-低-S5 版本化 publication manifest 生成机制未指定

- **位置**: §9 S5 exact changes #1: "versioned manifest 固定 oracle id/version、5 dirs、43 files、全部 relative paths、package-source digests、16 个 model projection owner paths"
- **问题类型**: 不可直接实施
- **当前写法**: Plan 要求 manifest 包含精确的文件数量、路径和摘要，但未说明 manifest 的生成方式。43 个文件是 oracle 在 2026-07-30 的 observed behavior 快照值，随着 scene/prompt 演进会变化。
- **反例/失败场景**: Implementation agent 手工编写 manifest，后续 package 增加 prompt 文件但忘记更新 manifest。Smoke 校验因 manifest 与实际 package 不匹配而误报失败，或者 agent 为了通过校验而放宽为"只检查目录存在"。
- **为什么有问题**: Oracle 的 `allowed_variants` 明确说"package managed-file 数量随正式 schema/scene 版本演进，但必须通过新 oracle/scenario version 更新 manifest，而不是放宽为只检查目录存在"。Plan 没有为 manifest 生成提供自动化手段，增加了维护负担和漂移风险。
- **直接证据**:
  - Oracle `allowed_variants[1]`: "package managed-file 数量随正式 schema/scene 版本演进，但必须通过新 oracle/scenario version 更新 manifest"
  - Plan §9 S5: manifest 内容详细列出但无生成说明
- **影响**: 后续维护负担，manifest 漂移导致 smoke false positive/negative
- **建议改法和验证点**: Plan 或 S5 implementation artifact 中明确 manifest 的生成/校验流程（例如从 package config 目录自动生成）及版本号升级触发条件
- **修复风险**: 低 — 可在 implementation artifact 中补充
- **严重程度**: 低

### 5-未修复-低-S4 ordinary-file quarantine 后 unlink 路径与 directory rmtree 路径的代码分叉未充分展开

- **位置**: §6.5 Workspace mode / repair state machine — "ordinary-file backup cleanup 使用与目录相同的 containment、identity-lock、同父 quarantine 边界"
- **问题类型**: 不可直接实施
- **当前写法**: Plan 说普通文件 cleanup 复用目录的 containment/identity-lock/quarantine 边界，quarantine 后 "regular file: no-follow unlink; ordinary directory: 现有 fd-safe recursive delete"
- **反例/失败场景**: 当前 `_cleanup_private_path` (init_workspace.py:1267) 的流程是 `_require_ordinary_directory` → quarantine via `os.replace` → `shutil.rmtree`。对于普通文件：`_require_ordinary_directory` 会在第一步就 fail（文件不是目录）。Plan 说"复用"同一边界，但实现上需要在 `_require_ordinary_directory` 之前分叉，或者在 `_cleanup_private_path` 中增加文件路径。这个分叉点的具体位置和 contract 未指定。
- **为什么有问题**: Plan 说"复用"但当前代码不支持普通文件路径进入 `_cleanup_private_path`。Implementation agent 需要在 `_cleanup_private_path` 或调用方增加 type dispatch。未指定分叉位置可能导致 agent 引入新的 cleanup helper（违反"不新建 mutation helper"约束）或在错误层级处理文件/目录差异。
- **直接证据**:
  - 生产代码 `init_workspace.py:1304`: `_require_ordinary_directory(path, actual_identity, ...)` — 要求路径必须是目录
  - 生产代码 `init_workspace.py:1369`: `shutil.rmtree(quarantine)` — 只能删除目录
  - Plan §6.5: "regular file：no-follow unlink; ordinary directory：现有 fd-safe recursive delete"
  - Plan §5 语义 owner: managed tree/mode/rollback/repair 唯一 owner = `dayu.cli.init_workspace`
- **影响**: Implementation agent 可能在错误的位置引入文件/目录分叉，或创建新的 cleanup helper
- **建议改法和验证点**: Plan 应明确 `_cleanup_private_path` 的扩展方式：是增加 `expected_type: str` 参数做内部 dispatch，还是在调用方分叉后走不同路径
- **修复风险**: 低 — implementation 阶段可自然解决，但 plan 应提供更精确的 guidance
- **严重程度**: 低

## Architecture boundary review

- **分层**: `ModelFamilyIdentity` 放置在 `dayu.runtime.assembly` 是正确选择 — runtime-neutral 层，不依赖 Host/Engine/Service
- **依赖方向**: Parser → Service override 的映射路径 (`args.model → ServiceAssemblyOverrides.model_id`) 保持 UI→Service 正向依赖，不反向
- **Compactor assembly**: Plan 正确地识别了 `compose_open_host_options` 中 compactor selection 传 `scene_model_hints=None` 的问题，并指定通过 compactor scene model hints 修复。Service 层不直接读取 JSON，只通过 `select_runner_option_hint` 做 selection — 符合分层约束
- **No boundary violations detected**

## Best-practice review

- **复用优于重建**: Plan 大量复用 `ConfigLoader`、`select_runner_option_hint`、现有 workspace transaction、`prepare_scene` — 符合项目"不过度设计"约束
- **测试覆盖**: 每个 slice 有明确 test files 和 validation command；单文件 80% 覆盖率目标明确
- **Error handling**: EOF/SIGINT/parser exit codes 有明确 contract；交互重试 loop 有 bounded scope
- **Minimal surface**: 不新增 JSON 字段、不修改 Host lifecycle、不做 migration — 符合最小化变更原则

## Overengineering review

- `ModelFamilyIdentity` 是四字段 frozen dataclass + 一个构造 helper — 没有过度抽象
- S5 smoke 是窄职责 `utils/` 脚本 — 没有抽象成测试平台
- primary default selection 的额外 `select_runner_option_hint` 调用是区分 workspace truth 与 invocation override 的必要状态 — 不是 premature generalization
- **No overengineering detected**

## Overcoupling review

- S1-S6 slice 顺序有合理的依赖链：S1 (parser) → S2 (family + interaction) → S3 (package + Service) → S4 (transaction) → S5 (smoke) → S6 (docs)
- S4 依赖 S2+S3 是必要的（PRESERVE 需要正确的 model projection）
- 每个 slice 的 allowed files 边界清晰，文件所有权不重叠
- **No overcoupling detected**

## Optimal-solution review

- Parser common/runtime parent 方案比在 `run_init_command` 中静默忽略 `config_dir` 更符合 owner boundary 原则 — 正确选择
- 不修改 `models.json` 而是修改引用方的 `default_model_id` — 改动面更小，正确
- 复用现有 workspace transaction 扩展 repair 而非新建 helper — 正确选择

## Final conclusion

**Pass-with-risks**

Plan 对目标、语义 owner、分层边界和实现 slice 的定义总体精确且可实施。发现 5 个 findings（2 个中、3 个低），主要在以下方面需要澄清：
