## Findings

### ADR-01-未修复-中-Evidence 与 suggestion identity 仍落在旧 leaf/path 粒度

- **入口/函数**: 第 4.5.1 owner 表、第 4.5.2 adjudication 输入
- **文件(行号)**: `docs/cli_ci.md:376-377`、`docs/cli_ci.md:411-413`
- **输入场景**: 同一个 `dayu-cli init` leaf 在空 workspace/已有 workspace 下分别执行合法 option、错误 option 和
  Ctrl+C scenario。
- **实际分支**: Coverage/readiness/report 已以 mandatory scenario/correctness surface 为 owner，但 owner 表仍把
  `execution_outcome`、`evidence_status/gap_kind` 定义为 `per-leaf/path`，suggestion 也只要求引用 `leaf/path`。
- **预期行为**: 每个 scenario identity 独立拥有 outcome/evidence/gap；suggestion/adjudication 必须引用具体
  scenario/correctness surface，leaf/path 只能作为分组维度。
- **实际行为**: 执行 Agent 可以把同一 leaf 的多个 workspace/option scenarios 合并到一个 path status，导致一个成功
  scenario 掩盖另一个 blocked/evidence-missing scenario；suggestion 也无法绑定用户实际裁决的前置状态。
- **直接证据**:
  - 第 493-545 行 mandatory matrix 以 scenario coverage claims 为 owner；
  - 第 927-1015 行 report schema 以 scenario 为最小记录；
  - 第 376-377、411-413 行仍使用旧 `per-leaf/path` identity。
- **影响**: readiness proof 可能丢失 state/option/input 维度，用户裁决与 accepted oracle scope 错配。
- **建议改法和验证点**:
  - owner 表改为 per-scenario raw process/evidence records；
  - suggestion 必须引用 scenario/correctness surface，保留 leaf/path 仅作导航；
  - 全文扫描不再把 leaf/path 定义为 outcome/evidence/adjudication 的最小 owner。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
