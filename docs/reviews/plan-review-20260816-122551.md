## 新增发现

### N1-未修复-低-snapshot integrity check 与 ingest_complete check 的语义差异

- **位置**: §7.2 snapshot 行为、§6.1 `_require_complete_source_for_snapshot_unguarded`
- **问题类型**: 契约细节
- **当前写法**: plan 要求 snapshot 对 `REPAIR_REQUIRED/UNSAFE` 抛 `ValueError`。但当前 snapshot 实现检查的是 `provenance.ingest_complete`（`_fs_source_snapshot.py:763-764`），不是 integrity classification。plan 的重构将 snapshot 改为消费 inspection，`_require_complete_source_for_snapshot_unguarded` 要求 inspection=`COMPLETE`。
- **反例/失败场景**: 如果 snapshot 在 plan 重构后仍然检查 `ingest_complete` 而非 `classification.status`，可能出现 `ingest_complete=True` 但 `status=REPAIR_REQUIRED` 的情况（例如文件缺失但 provenance 标记完成），snapshot 会错误地允许读取损坏 source。
- **为什么有问题**: plan §6.1 已指定 snapshot 改为消费 inspection，§7.2 的 ValueError 契约基于 status 而非 ingest_complete。这不是 plan 设计缺陷，而是 implementation agent 需要注意的语义切换点。
- **直接证据**: `_fs_source_snapshot.py:763-764` 当前检查 `ingest_complete`；plan §6.1 要求 snapshot "直接用同一 inspection 构造 meta/provenance/revision/files/primary"。
- **影响**: 极低——plan 已正确设计，implementation agent 按 §6.1 实现即可。
- **建议改法和验证点**: 无需 plan 修改。§11.4 的 snapshot 测试断言已覆盖此场景。
- **修复风险**: 低
- **严重程度**: 低
