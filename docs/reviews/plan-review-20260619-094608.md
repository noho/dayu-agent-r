# Plan Review: Conversation Memory Smoke Suite 拆分方案

- **Reviewed target**: 口头提案 — 用 `--suite` 区分 `memory-core` / `memory-proactive-compact` / `memory-reactive-compact` / `memory-compact-fallback`，用 `--pressure-mode` 控制施压，新增明确日志信号和断言
- **Review date**: 2026-06-19
- **Reviewer**: planreview skill (adversarial)

## Reviewed Assumptions

1. 当前 smoke `--suite all --long-rounds 25 --log-level DEBUG` PASS 但日志中有 `proactive compact proposal rejected` 和 `fail_compaction` 是待修复问题
2. 通过拆分 suite 可以区分 compaction 路径（proactive / reactive / fallback）
3. 当前 smoke 脚本（`utils/smoke_host_public_conversation_memory_scenarios.py`）有能力观察 compaction 状态
4. `--pressure-mode` 可以控制 compaction 触发条件
5. 日志信号可以直接作为断言依据
6. daily smoke 和 compact certification 可能需要分离

## Findings

### 1-未修复-高-motivation 部分误诊：proactive compact proposal rejected + fail_compaction 在 smoke PASS 时未必是 bug

- **位置**: 提案背景描述
- **问题类型**: 动机不成立
- **当前写法**: 当前 smoke PASS 但日志有 `proactive compact proposal rejected` 和 `fail_compaction`，被当作需要 suite 拆分来诊断的问题
- **反例/失败场景**: compaction 系统设计中，proposal rejected 是 quality gate 的正常行为（LLM 产出质量不达标被拒），`fail_compaction` 后系统进入 tier 4/5 deterministic recent-window fallback 并成功 dispatch。smoke PASS 且 conversation continuity 断言通过，恰恰证明 fallback 路径工作正常
- **为什么有问题**: 把"正常工作的 fallback 路径产生预期日志"误诊为需要修复的问题，会导向不必要的 suite 拆分，而非真正需要解决的可观测性缺口（smoke 无法区分"compaction 成功"和"compaction 失败但 fallback 成功"）
- **直接证据**:
  - `dayu/host/dispatch.py:1337` — `_append_compaction_failed_with_proactive_fallback()` 在 compaction 失败后进入 deterministic recent-window fallback
  - `dayu/host/compaction_operation.py:349-353` — `FAIL_COMPACTION` 是 `CompactionNextPolicyDecision` 的正常枚举值
  - `docs/host/design.md:3261` — tier 4-5 dispatch fallback 是设计状态机的正常收口路径
  - 当前 smoke 的 hard_answer_contains 断言在 core suite 轮次（如 `_ASSERT_A`, `_ASSERT_B_CFO`, `_ASSERT_D_NIM`）和 long suite 轮次（如 `_ASSERT_E_CONSTRAINTS`）均通过，说明 fallback 后的 conversation continuity 未受损
- **影响**: 实施 Agent 可能基于错误前提做不必要的 suite 拆分，浪费工程资源
- **建议改法和验证点**: 先确认 compaction failure 是否真的导致 conversation continuity 受损（而非仅日志存在）。若未受损，真正缺口是可观测性——smoke 无法区分"compaction 成功直接 dispatch"和"compaction 失败经 fallback dispatch"
- **修复风险（低）**:
- **严重程度（高）**:

### 2-未修复-严重-公共 API 层 smoke 无法观察内部 compaction 状态机，proposed suites 不可区分

- **位置**: suite 拆分方案整体
- **问题类型**: 架构边界 / 不可直接实施
- **当前写法**: 提议在 `utils/smoke_host_public_conversation_memory_scenarios.py` 中用 `--suite` 区分 memory-core / memory-proactive-compact / memory-reactive-compact / memory-compact-fallback
- **反例/失败场景**: smoke 脚本通过 `open_host` → `ensure_session` → `submit_followup` → `watch_session_events` 操作，只观察 public `HostEvent`（`SUCCEEDED`、`FAILED` 等）。内部 compaction 状态机事件（`CONTEXT_COMPACTION_REQUESTED`、`CONTEXT_COMPACTED`、`CONTEXT_COMPACTION_FAILED`、`CONTEXT_COMPACTION_ATTEMPT_REJECTED`）是 EventLog canonical facts，**不是** public HostEvent。smoke 脚本无法判断：
  - 是否触发了 proactive 还是 reactive compaction
  - compaction proposal 是否被 accept 还是 reject
  - 最终 dispatch 是通过 compacted context 还是 fallback recent-window
  - 因此 `memory-proactive-compact`、`memory-reactive-compact`、`memory-compact-fallback` 三个 suite 在 public API 层完全不可区分
- **为什么有问题**: 实施 Agent 要么无法实现区分断言（suite 名不同但实际覆盖完全相同路径），要么被迫穿透 public API 读取内部状态（违反架构分层）
- **直接证据**:
  - `utils/smoke_host_public_conversation_memory_scenarios.py:1855-1861` — smoke 只通过 `open_host`、`ensure_session`、`watch_session_events` 操作
  - `utils/smoke_host_public_conversation_memory_scenarios.py:2314-2357` — `_assert_round_result` 只检查 tool usage + answer content，不检查 compaction 状态
  - `utils/smoke_host_public_conversation_memory_scenarios.py:2824-2845` — `_print_compact_summary` 只打印 compact artifact 文件数，**不做断言**
  - `dayu/host/dispatch.py:1301` — `_execute_proactive_compaction()` 是 Host 内部方法，不暴露给 public handle
  - `dayu/host/engine_ingest.py:1264` — `_start_reactive_context_recovery()` 同样是内部方法
  - `docs/host/design.md:3280` — "`CONTEXT_COMPACTION_REQUESTED`、最终 `CONTEXT_COMPACTED`、最终 `CONTEXT_COMPACTION_FAILED` 应作为 Service-facing HostEvent 可观察"（当前实现中这些事件是否已作为 public HostEvent 暴露需要确认，但 smoke 脚本当前并未消费它们）
- **影响**: 实施 Agent 跑偏——要么产出无法区分的 suite，要么引入架构违规
- **建议改法和验证点**:
  1. 确认当前 Host public API 是否已暴露 compaction 相关 HostEvent（检查 `HostEventKind` 枚举）
  2. 若已暴露：在 smoke 脚本中消费这些事件，区分 compaction 路径
  3. 若未暴露：compaction 行为测试应留在 `tests/host/test_public_compact_smoke.py`（已有 fake compactor 注入机制），不应强行塞入 public conversation memory smoke
  4. conversation memory smoke 的职责应保持为：验证 public Host API 下的多轮对话连续性、事实召回、anti-drift 和约束保持
- **修复风险（中）**:
- **严重程度（严重）**:

### 3-未修复-高-reactive compaction 无法被 deterministic mock tool 触发

- **位置**: `memory-reactive-compact` suite
- **问题类型**: 范围漂移 / 不可直接实施
- **当前写法**: 提议新增 `memory-reactive-compact` suite
- **反例/失败场景**: Reactive compaction 的触发条件是 Engine 发出 `ContextCompactionRequestedData` 事件（provider context overflow）。`MockFinanceMemoryTool` 返回确定性、固定大小的响应，不会触发 provider overflow。任何使用当前 mock tool 的 reactive suite 都将得到零次 reactive trigger——正是当前状态
- **为什么有问题**: 要在 smoke 中触发 reactive compaction，需要要么替换为真实 provider（不稳定、慢），要么在 mock tool / Engine 层模拟 overflow 信号（超出 smoke 脚本设计范围）
- **直接证据**:
  - `dayu/host/engine_ingest.py:1264` — `_start_reactive_context_recovery()` 由 Engine 的 `ContextCompactionRequestedData` 事件触发
  - `utils/smoke_host_public_conversation_memory_scenarios.py:1089-1141` — `MockFinanceMemoryTool.__call__` 返回固定 payload，无 overflow 机制
  - 当前 `--log-level DEBUG` 日志中无 reactive trigger 证据，证实此路径未被当前 smoke 覆盖
- **影响**: 实施 Agent 产出空 suite 或被迫大幅扩展 mock tool / Engine 模拟能力
- **建议改法和验证点**: Reactive compaction 测试应留在 `tests/host/test_dispatch_scheduler.py`（已有 reactive fallback dispatch 测试，如 line 5045 附近）。若确实需要 public API 层的 reactive smoke，需先在 Engine/Host 边界设计 overflow 注入 seam
- **修复风险（高）**:
- **严重程度（高）**:

### 4-未修复-中-`--pressure-mode` 控制面 underspecified，不足以支撑 compaction 路径区分

- **位置**: `--pressure-mode` 参数设计
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: 用 `--pressure-mode` 控制施压
- **反例/失败场景**: 当前 `PressureMode` 只有 `auto` 和 `off` 两个值。`auto` 模式生成使估算落在 soft/hard threshold 之间的 padding，触发 proactive compaction proposal。但：
  - 无法控制"恰好触发 compaction 且 proposal 一定被 accept"（依赖 LLM compactor 质量，不可确定）
  - 无法控制"触发 compaction 且 proposal 一定被 reject"（同样依赖 LLM）
  - 无法控制 reactive 路径
  - 无法控制 tier 1-3 recovery 路径
- **为什么有问题**: 压力模式只控制 prompt/tool 压力文本量，但 compaction proposal 的 accept/reject 取决于 LLM compactor 输出质量，无法通过压力文本量确定性控制。`memory-proactive-compact` suite 可能需要"compaction 成功"的确定性场景，但压力文本量无法保证这一点
- **直接证据**:
  - `utils/smoke_host_public_conversation_memory_scenarios.py:448-455` — `PressureMode` 只有 `AUTO` / `OFF`
  - `utils/smoke_host_public_conversation_memory_scenarios.py:2579-2611` — `_compact_pressure_padding` 只控制 padding 大小，不控制 compaction outcome
  - `dayu/host/compaction_operation.py:443` — `run_compaction_operation` 的 accept/reject 由 quality check 决定，不受外部压力参数控制
- **影响**: 实施 Agent 需要自行设计 pressure mode 语义，可能引入与现有系统不一致的控制面
- **建议改法和验证点**: 若需确定性控制 compaction 行为，应使用 `tests/host/fake_compaction.py` 中的 `FakeContextCompactor` 注入机制（已在 `test_public_compact_smoke.py` 中使用），而非通过 pressure mode
- **修复风险（中）**:
- **严重程度（中）**:

### 5-未修复-中-日志信号方案缺乏结构定义，无法指导实施

- **位置**: "新增明确日志信号和断言"
- **问题类型**: 契约缺失
- **当前写法**: 提议新增明确日志信号和断言
- **反例/失败场景**: 当前 smoke 已有大量结构化 stdout 信号（`SMOKE ROUND_START`、`SMOKE ROUND_DONE`、`SMOKE TOOL_DELTA`、`SMOKE COMPACT_ARTIFACT_ROOT` 等），但：
  - `_print_compact_summary` 只打印 compact artifact 文件数，**不做断言**（即使 compact 完全没发生也不会失败）
  - 没有消费 Host 内部 compaction 事件的机制
  - 没有将日志信号转化为硬断言的路径
- **为什么有问题**: "新增日志信号"如果没有配套的断言消费逻辑，只是增加 stdout 噪音，不解决"smoke PASS 但 compaction 状态未知"的核心缺口
- **直接证据**:
  - `utils/smoke_host_public_conversation_memory_scenarios.py:2824-2845` — `_print_compact_summary` 只打印不断言
  - `utils/smoke_host_public_conversation_memory_scenarios.py:1847-1898` — `run_smoke` 的 compact 相关输出全是 print，无 assert
  - 整个 smoke 脚本中没有任何对 compact artifact 数量、compact event 出现、或 compaction 路径的硬断言
- **影响**: 实施 Agent 可能只增加 print 语句而不增加断言，suite 拆分后仍无法区分 compaction 路径
- **建议改法和验证点**:
  1. 确认 public HostEvent 中是否已有 compaction 相关事件类型
  2. 若有：在 smoke 中消费这些事件并做硬断言（如：proactive suite 中必须出现 `CONTEXT_COMPACTED` 事件）
  3. 若没有：日志信号只能作为 diagnostics，真正的 compaction 行为断言需要通过 `test_public_compact_smoke.py` 的 fake compactor 注入或 `test_dispatch_scheduler.py` 的单元测试覆盖
- **修复风险（低）**:
- **严重程度（中）**:

### 6-未修复-中-daily smoke 与 compact certification 的分离已由现有测试架构支持，proposed suite 拆分方向与现有架构重叠

- **位置**: "是否需要 daily smoke 与 compact certification 分离"
- **问题类型**: 非最优方案
- **当前写法**: 通过 suite 拆分在同一 smoke 脚本中实现分离
- **反例/失败场景**: 现有测试架构已经自然分离：
  - **Daily smoke（快速、确定性、应始终 PASS）**: `--suite core`（~17 轮，不触发 compaction），可在 CI 每次提交运行
  - **Long session smoke（较慢、可能触发 compaction）**: `--suite all --long-rounds 25`（~42 轮），可在 daily 运行
  - **Compact unit tests（快速、确定性、全面）**: `tests/host/test_compact_material.py`、`tests/host/test_compaction_operation.py`、`tests/host/test_dispatch_scheduler.py`、`tests/host/test_context_compact_events.py`
  - **Compact public smoke（可用 fake compactor 确定性测试）**: `tests/host/test_public_compact_smoke.py`
  - **Real compactor certification（慢、需真实 provider）**: `DAYU_RUN_REAL_COMPACTOR_SMOKE=1 pytest tests/host/test_public_compact_smoke.py`
- **为什么有问题**: 在 conversation memory smoke 中新增 `memory-proactive-compact` 等 suite 会与 `test_public_compact_smoke.py` 的职责重叠，且后者已有成熟的 fake compactor 注入机制和 compact-specific 断言
- **直接证据**:
  - `tests/host/test_public_compact_smoke.py:1` — "P10.5 Slice 5 public real-compactor smoke"
  - `tests/host/test_public_compact_smoke.py` — 包含 fake compactor 注入（`fake_compaction_proposal_from_material_json`）、prompt contract 验证、compaction 后 continuity 验证
  - `tests/host/fake_compaction.py` — `FakeContextCompactor` 提供确定性 compact output
  - `tests/host/test_dispatch_scheduler.py:4550` — proactive fallback dispatch 测试
  - `tests/host/test_dispatch_scheduler.py:5045` — reactive fallback dispatch 测试
- **影响**: 重复建设、维护两份 compact smoke、职责边界模糊
- **建议改法和验证点**: 保持现有分离：
  - conversation memory smoke → 多轮对话 continuity 验证
  - compact public smoke (fake/real) → compaction 行为验证
  - dispatch scheduler 单元测试 → proactive/reactive/fallback 路径覆盖
  若确实需要一个新的 daily compact certification suite，应在 `tests/host/test_public_compact_smoke.py` 中扩展，而非在 conversation memory smoke 中新增 suite

- **严重程度（中）**:

## Open Questions

1. **Host public API 是否已暴露 compaction 相关 HostEvent？** 需要检查 `HostEventKind` 枚举是否包含 compaction 相关事件类型。设计文档（design.md:3280）声明应暴露，但需要代码验证。如果已暴露，smoke 可以消费这些事件做断言；如果未暴露，需要确认是否是 WU-CM-12 的实现范围。

2. **当前 smoke 中 compaction failure 是否真的导致 conversation continuity 受损？** 需要对比"pressure=off（不触发 compaction）"和"pressure=auto（触发 compaction 但可能失败）"两种模式下的回答质量。如果连续性未受损，说明 fallback 工作正常，拆 suite 的动机更弱。

3. **`--log-level DEBUG` 日志中的 `proactive compact proposal rejected` 的具体 failure category 是什么？** 是 quality check 拒绝（LLM 输出格式/内容问题）还是 budget 拒绝（compact 后仍超 threshold）？不同 failure category 对应不同的问题根因，修复方向完全不同。quality check 拒绝可能是 prompt/instruction 问题，budget 拒绝可能是 policy 配置问题。

4. **WU-CM-12 plan 的 S4（Tier 1-3 Compact Recovery Fallback）实现后，compaction 成功率预期会提高多少？** 如果 tier 1-3 能显著降低 fail_compaction 率，那么当前 smoke 中观察到的 `fail_compaction` 可能在 WU-CM-12 完成后自然消失，suite 拆分可能不再必要。

## Plan Review Conclusion: **fail**

**理由**: 提案方向存在两个 blocker-level 问题：

1. **Finding 2（严重）**: 公共 API 层 smoke 无法观察内部 compaction 状态机。`memory-proactive-compact`、`memory-reactive-compact`、`memory-compact-fallback` 三个 suite 在 public Host API 层面不可区分，实施 Agent 无法实现有意义的区分断言。

2. **Finding 3（高）**: Reactive compaction 无法被 deterministic mock tool 触发。`memory-reactive-compact` suite 在当前 mock 架构下将得到零次 reactive trigger。

此外，Finding 1（动机部分误诊）和 Finding 6（与现有测试架构重叠）表明提案方向需要重新审视其要解决的真实问题。

**建议的替代方向**:

1. 保持 conversation memory smoke 的职责为"public Host API 下的多轮对话 continuity 验证"
2. 在 smoke 脚本中增加对已有的 `_print_compact_summary` 输出的**硬断言**（如：pressure=auto 时 compact artifact 数量 > 0）
3. 若 public HostEvent 已暴露 compaction 事件，消费这些事件区分"compaction 成功"和"fallback 成功"
4. Compaction 行为验证（proactive/reactive/fallback/tier 1-3 recovery）继续由 `tests/host/test_public_compact_smoke.py`（fake compactor 注入）+ `tests/host/test_dispatch_scheduler.py`（单元测试）覆盖
5. 若需要 daily compact certification，扩展 `tests/host/test_public_compact_smoke.py` 而非 conversation memory smoke
