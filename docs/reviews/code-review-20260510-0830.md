### 1-未修复-[accepted→S3]-中-`_handle_owner_lost` 绕过 fencing 直接 append RUN_FAILED 到 EventLog

- **入口/函数**: `LocalRunHarness._handle_owner_lost`
- **文件(行号)**: [dayu/host/_run_harness.py:1060-1068](dayu/host/_run_harness.py#L1060-L1068)
- **输入场景**: supervisor 路径下 owner-lost 命中，当前 Run 尚未写入终态事件（`terminal_seen=False`）
- **实际分支**: `_handle_owner_lost` 先调用 `_finish_attempt_if_durable` 走 owner-aware diagnostic close（把 `host_attempts` 收口到 `LOST`），然后直接通过 `self.event_store.append(host_failure_draft(...))` 追加一条 RUN_FAILED 到 EventLog——注意此处用的是 `self.event_store.append` 而非 scoped appender，不经过 `verify_owner` CAS
- **预期行为**: owner-lost 后不能再向该 attempt 的 EventLog 写入任何 fact。若另一个进程的 recovery scan 已接管该 attempt 并创建了新的 recovery attempt，EventLog 不应再出现旧 owner 的 RUN_FAILED
- **实际行为**: 旧 owner 的 `_handle_owner_lost` 在 `host_attempts` 已被 recovery 推进到 `RECOVERING`（即 `close_attempt_with_diagnostic_state` 的 CAS 已 miss 返回 False）后，仍会向 EventLog 追加一条 `host_failure_draft`，导致 EventLog 中出现一条与当前 attempt 所有权不一致的 stale RUN_FAILED
- **直接证据**: [line 1060](dayu/host/_run_harness.py#L1060): `stored_event = await self.event_store.append(host_failure_draft(...))`，该调用在 `_finish_attempt_if_durable` 之后但无任何 owner CAS 保护。而 `_finish_attempt_if_durable` 的 supervisor 路径在 CAS miss 时仅返回 `False`（[line 631-632](dayu/host/_attempt_supervisor.py#L631-L632)），`_handle_owner_lost` 不检查该返回值就继续 append
- **影响**: 多进程恢复场景下 EventLog 出现与 attempt 所有权不一致的 stale 诊断事实，破坏 EventLog 作为 "当前 owner 是唯一写入者" 的不变量。对 read model 投影的正确性有潜在影响（两次 RUN_FAILED 或 RUN_FAILED 与 recovery 终态并存）
- **建议改法和验证点**: `_handle_owner_lost` 应检查 `_finish_attempt_if_durable` 的返回值（或前置检查 supervisor.is_owner_active）。若 `close_attempt_with_diagnostic_state` 已返回 False（owner 已被替换），不应再向 EventLog 追加任何事件。验证：构造 recovery scan 与 harness owner-lost 并发场景，断言 EventLog 不会出现 2 条 RUN_FAILED
- **修复风险（低）**: owner-lost 后不写 RUN_FAILED 意味着 Run 订阅方可能收不到终态信号；但 recovery 路径会由新 attempt 输出正确的终态。需确认 RunStream 订阅方在 owner-lost 场景下的超时/重连策略
- **严重程度（中）**:

### 2-未修复-[accepted→S6]-低-`list_recovery_candidates` SQL 排除 `CREATED` 孤儿但 supervisor 有相应用处理分支

- **入口/函数**: `AttemptLeaseStore.list_recovery_candidates`
- **文件(行号)**: [dayu/host/_run_state_store.py:832-862](dayu/host/_run_state_store.py#L832-L862)
- **输入场景**: `AttemptStateStore.create()`（legacy P6 路径）创建了 `CREATED` 状态、`lease_expires_at IS NULL` 的 attempt 行，随后进程崩溃
- **实际分支**: `list_recovery_candidates` 的 WHERE 条件为 `state IN ('running', 'created') AND lease_expires_at IS NOT NULL AND lease_expires_at <= ?`。`CREATED` 行因 `lease_expires_at IS NULL` 被 SQL 过滤掉，不进入候选列表
- **预期行为**: supervisor `_process_recovery_candidate` 有显式的 `CREATED` 孤儿处理分支（[line 821-824](dayu/host/_attempt_supervisor.py#L821-L824)），意图是 `CREATED` 孤儿应被标记为 `LOST`。但该分支永远不会被 `recover_stale_attempts` 触发，因为候选列表不包含这些行
- **实际行为**: `CREATED` 且 `lease_expires_at IS NULL` 的孤儿行永远不会被 recovery scan 发现和清理，成为 `host_attempts` 中的永久僵尸行
- **直接证据**: SQL at [line 838-841](dayu/host/_run_state_store.py#L838-L841): `AND lease_expires_at IS NOT NULL AND lease_expires_at <= ?`。P8 的 `acquire_new_attempt` 路径不产生 CREATED 状态（直接 INSERT RUNNING + lease），但 legacy `AttemptStateStore.create()` 产生 CREATED 且 lease 全 NULL（[line 285-302](dayu/host/_run_state_store.py#L285-L302)）
- **影响**: P6 legacy 路径与 P8 attempt_state_store 兼容路径下，进程崩溃后 CREATED 孤儿无法自动清理。对 P8 主线路径无影响（acquire_new_attempt 不产生 CREATED）。影响范围限于 P6 兼容装配
- **建议改法和验证点**: 两条路径选其一：(a) 在 `list_recovery_candidates` 中额外包含 `state='created' AND lease_expires_at IS NULL` 的孤儿行；(b) 移除 `_process_recovery_candidate` 中不可达的 CREATED 分支并注释说明 P8 主路径不产生该状态。倾向 (a)，配合测试验证 CREATED 孤儿可被 recovery
- **修复风险（低）**: 仅影响 P6 兼容路径，P8 主线不变
- **严重程度（低）**:

### 3-未修复-[accepted→S7]-低-`_allocate_fencing_token` 对 `cursor.lastrowid` 的 None 兜底不满足 `FencingToken(value > 0)` 契约

- **入口/函数**: `AttemptLeaseStore._allocate_fencing_token`
- **文件(行号)**: [dayu/host/_run_state_store.py:1186](dayu/host/_run_state_store.py#L1186)
- **输入场景**: `INSERT INTO host_fencing_tokens` 成功，但 `cursor.lastrowid` 返回 0 或 None（SQLite 的 `INTEGER PRIMARY KEY AUTOINCREMENT` 正常情况下不会，但规范未承诺绝对不返回 0）
- **实际分支**: `FencingToken(value=int(cursor.lastrowid or 0))`——若 `lastrowid` 为 None/0，`or 0` 产生 0，`FencingToken(0)` 在 `__post_init__` 中 raise `ValueError("fencing token value must be positive")`
- **预期行为**: 分配 fencing token 不应因 SQLite cursor 实现细节而抛未捕获异常
- **实际行为**: 极端情况下抛 `ValueError` 且调用方（`acquire_new_attempt` / `mark_recovering_and_create_attempt`）未捕获该异常，导致整个事务回滚
- **直接证据**: [line 1186](dayu/host/_run_state_store.py#L1186): `FencingToken(value=int(cursor.lastrowid or 0))` + [line 51-59](dayu/host/_internal_contracts.py#L51-L59): `if self.value <= 0: raise ValueError`
- **影响**: 低概率。正常情况下 AUTOINCREMENT 从 1 开始；但在 SQLite 极端边缘条件（如损坏恢复后的数据库）下可能触发。影响面为 acquire 或 recovery 路径的整事务回滚
- **建议改法和验证点**: 在 `_allocate_fencing_token` 中加显式 `if cursor.lastrowid is None or cursor.lastrowid < 1: raise RuntimeError(...)` 并给出清晰的错误消息。或者在 `FencingToken.__post_init__` 中将 value <= 0 的异常消息包含上下文以便定位
- **修复风险（低）**: 纯粹防御性改进
- **严重程度（低）**:

### 4-未修复-[accepted→S8]-低-Durable memory snapshot 缺失 schema_version 校验

- **文件(行号)**: [dayu/host/_conversation_memory_durable.py:593-628](dayu/host/_conversation_memory_durable.py#L593-L628)
- **输入场景**: `host_conversation_memory_snapshots` 表中存在由未来版本代码写入的、schema_version 更高的 snapshot（例如回滚部署后旧代码读取新格式）

- **实际行为**: 字段映射不匹配时可能成功解析出语义错误的 `ConversationMemorySnapshot`（字段默认值 vs 实际值），或抛 `"snapshot_decode_failed:<key>"` 让排查困难

## Open Questions

1. **`list_recovery_candidates` 扫描范围是否应排除 `RECOVERING` 状态？** 当前查询条件为 `state IN ('running', 'created') AND lease_expires_at <= now`，不包含 RECOVERING。但如果 `mark_recovering_and_create_attempt` 的旧 attempt CAS 成功但新 attempt INSERT 失败（非 UNIQUE 冲突的其他原因），旧 attempt 处于 RECOVERING 且无人继续推进。建议在 `list_recovery_candidates` 中增加 `state='recovering'` 的超时重扫（例如 `stale_marked_at` 超过某阈值），或确认 SQLite 事务语义下不可能出现该半状态。

2. **Recovery scan 无自动调度。** `recover_stale_attempts` 是显式调用入口，不接入 `build_durable_harness` bootstrap 流程。多进程部署下谁负责周期性调用 recovery scan？若依赖外部 cron/调度器，文档应明确说明调度契约与幂等保证。

3. **Multiprocess stress 测试覆盖的时序窗口。** `test_phase8_multiprocess_stress.py`（1081 行）的并发模型是多个 asyncio task 在同一进程内操作同一 SQLite `:memory:` 数据库。这能覆盖 SQLite 事务级 CAS 竞态，但不能覆盖真正多进程下的文件锁、WAL 模式、OS 级别排序差异。是否需要至少 1 个使用 `tmp_path` 文件 SQLite + 真实 `multiprocessing.Process` 的集成测试？

4. **`_conversation_memory_durable._REPAIR_FETCH_BATCH_LIMIT` 固定为 256。** 对于 EventLog 很大的 session，修复时间可能较长。是否需要为 repair 路径增加总超时或进度日志？

5. **`host_fencing_tokens` 表无定期清理机制。** 每次 acquire + recovery 都会新增行（token gap 不回缩）。长期运行的数据库该表会持续增长。是否需要增加保留策略（例如仅保留最近 N 条或最近 N 天的 token 记录）？

## Residual Risk

- **Recovery scan 调度缺失：** P8-S6 实现了完整的 CAS recovery 机制，但 recovery scan 未被集成到 bootstrap 或任何自动化路径。在 recovery scan 被外部调度器触发之前，过期 attempt 的 recovery 不会自动发生。这是已知的 scope 限制（S6 文档注明 "不自动接入 build_durable_harness"），但需要明确由哪一层负责触发。

- **无 schema migration 测试：** `host_attempts` 表新增了 `owner_id` / `owner_token_hash` / `fencing_token` / `lease_expires_at` / `lease_renewed_at` / `recovered_from_attempt_id` / `stale_marked_at` 列。如果现有部署的数据库缺少这些列，首次启动会因 SQL 引用不存在的列而失败。未见 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 或迁移脚本。

- **tests/host/_memory_store_fake.py 与 tests/host/_multiprocess_platform.py 未纳入覆盖率统计。** 这些文件是测试基础设施，其正确性直接影响测试结果的可信度。建议至少对 `_memory_store_fake` 的行为一致性做基本断言（例如 fake store 的 snapshot round-trip 与 durable store 一致）。

- **`_conversation_memory_durable.py` 的 `_REPAIR_FETCH_BATCH_LIMIT=256` 未与 `DurableRunEventStore` 的 batch 读取能力做对齐校验。** 若 event store 的 `fetch_events_by_position` 实现变更（如引入自己的 batch 上限），repair 路径可能出现行为不一致。
