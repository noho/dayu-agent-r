## Findings

### 1-未修复-中-测试仅覆盖 happy path，缺少错误路径和边界断言

- **位置**: Slice 1 → Tests 段（行 196-204）
- **问题类型**: 测试缺口
- **当前写法**: 测试要求断言 operation timeline、histogram、manifest missing stage、failed event hard fail。全部是正常输入 + 预期输出的 happy path。
- **反例/失败场景**:
  - `_compact_audit_report_from_rows(())` — 空 tuple 输入，返回的 `CompactAuditReport.operations` 应为空 tuple，但 plan 未要求此断言。
  - `payload_json` 是无效 JSON（如 `"not-json"`）时，`_compact_row_payload` 应如何行为？plan 未定义错误契约。
  - `diagnostic_refs` 为 `[]`（空列表）时，`_compact_normalized_diagnostic_suffix` 应如何处理？plan 实现决策第 4 条提到"实现必须对短 refs 退化为完整 ref"，但未说明空列表行为。
  - `operation_id` 在 failed event 中缺失时，`CompactFailedOperationAudit.operation_id` 应填入占位符 `_COMPACT_OPERATION_MISSING_ID`，但测试未覆盖此路径。
  - `_compact_payload_int` 对非 int 字段（如 `"123"` 字符串）的行为未定义——应返回 `None` 还是抛出？
- **为什么有问题**: 当 implementation agent 自行决定错误处理策略时，可能与 plan 的"不抛出无关异常"约束冲突，或产生静默数据丢失。
- **直接证据**: plan 行 196-204 的测试列表全部是正常数据构造 + 预期断言，无 malformed/empty/missing 输入。
- **影响**: 实施 Agent 可能遗漏错误处理，导致 smoke 在真实 long25 遇到异常 payload 时崩溃而非优雅降级。
- **建议改法和验证点**:
  - 至少增加 3 个错误路径测试：空 rows 输入、payload 非 object、diagnostic_refs 空列表。
  - 为 `_compact_payload_int` / `_compact_payload_bool` 的类型不匹配行为明确契约（返回 `None` 是合理默认）。
  - 为 `_compact_normalized_diagnostic_suffix` 的空输入/超短输入增加退化断言。
- **修复风险（低）**: 仅增加测试，不改生产逻辑。
- **严重程度（中）**: 不会导致 production 问题，但会让 smoke 在边界条件下行为不确定。

### 2-未修复-中-plan 内部签名不一致：`_compact_audit_report` 的 `session_id` 参数

- **位置**: Slice 1 Exact allowed changes（行 176）vs Data Flow（行 148）
- **问题类型**: 不可直接实施
- **当前写法**:
  - Slice 1 行 176：`_compact_audit_report(options: OpenHostOptions, *, session_id: str) -> CompactAuditReport`（keyword-only）
  - Data Flow 行 148：`_compact_audit_report(assembly.options, session_id=session_id)`（与 Slice 1 一致）
  - 但实际 call site 行 2095（当前代码）：`_compact_audit_report(assembly.options, session_id=session_id)`
- **反例/失败场景**: 如果 implementation agent 按 Slice 1 的 keyword-only 签名实现，call site 恰好兼容（因为现有调用也用了 keyword）。但如果有人按 Data Flow 的描述误实现为 positional，会导致调用歧义。
- **为什么有问题**: 当前 call site 已经是 `session_id=session_id` 的 keyword 形式，所以 Slice 1 的 keyword-only 签名与现有调用一致。但 plan 的 Data Flow 段写的是 `(assembly.options, session_id=session_id)` 没有 `*`，可能误导 implementation agent。
- **直接证据**: plan 行 176 vs 行 148，以及当前代码行 2095。
- **影响**: 轻微——实际调用已使用 keyword 形式，但签名不规范会增加 implementation agent 的认知负担。
- **建议改法和验证点**: 统一为 keyword-only `*, session_id: str`，与现有 call site 一致且最安全。
- **修复风险（低）**: 纯文档修整。
- **严重程度（中）**: 不影响正确性但影响 code-generation-readiness。

### 3-未修复-低-`_compact_audit_report` 与现有 `_compact_audit_summary` 存在逻辑重复但 plan 未约定去重策略

- **位置**: Slice 1 Data Flow（行 148-153）vs 现有 `_compact_audit_summary`（行 3099-3118）
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: Plan 的 Data Flow 描述 `_compact_audit_report` 打开 durable store、读取 rows、调用 `_compact_audit_summary_from_rows` 生成 summary、构造 per-operation audit。但这与现有 `_compact_audit_summary(options, *, session_id)` 的前半段逻辑（打开 store → 读取 rows → 调用 `_compact_audit_summary_from_rows`）完全重复。
- **反例/失败场景**: implementation agent 实现了 `_compact_audit_report` 后，`_compact_audit_summary` 成为死代码（当前已无 `run_smoke()` 内调用——它只在测试路径通过 `_compact_audit_summary_from_rows` 间接存在）。如果 agent 保留 `_compact_audit_summary` 不删，后续维护者需要理解两个函数的关系。
- **为什么有问题**: plan 没有说明 `_compact_audit_summary` 是保留、重构为调用 `_compact_audit_report` 再取 `.summary`、还是直接删除。这给 implementation agent 留下未收敛的设计决策。
- **直接证据**: 现有代码行 3099-3118 定义了 `_compact_audit_summary(options, *, session_id)`；plan 行 148-153 描述的 `_compact_audit_report` 逻辑包含完全相同的 durable store 打开 + row 读取步骤。
- **影响**: 实施 Agent 可能保留重复逻辑，或不确定是否可以删除 `_compact_audit_summary`。
- **建议改法和验证点**: 在 plan 中明确：`_compact_audit_report` 替代 `_compact_audit_summary` 在 smoke flow 中的角色；`_compact_audit_summary` 保留为 `_compact_audit_report` 的薄包装（或标记为 deprecated，仅测试使用）。
- **修复风险（低）**: 只需 plan 文档澄清。
- **严重程度（低）**: 不阻塞实施，但有产生死代码的风险。

### 4-未修复-低-diagnostic suffix 提取算法依赖未文档化的常量语义

- **位置**: Implementation Decisions 第 4 条（行 117-126）与常量定义（行 215-216）
- **问题类型**: 不可直接实施
- **当前写法**: plan 说"diagnostic suffix 从 `diagnostic_refs` 提取；沿用 `_DIAGNOSTIC_REF_SEPARATOR` 和 `_DIAGNOSTIC_REF_SUFFIX_OFFSET`，但实现必须对短 refs 退化为完整 ref"。
- **反例/失败场景**: `_DIAGNOSTIC_REF_SEPARATOR = ":"` 和 `_DIAGNOSTIC_REF_SUFFIX_OFFSET = 4` 的语义没有在 plan 或代码中解释。例如 diagnostic ref `ValueError:previous reference continuity text is invalid` 有 1 个冒号。offset=4 是指从第 4 个冒号后截取？还是指截断前 4 个字符？implementation agent 需要从上下文猜测算法意图。
- **为什么有问题**: plan 没有给出 diagnostic ref 的格式规范和 suffix 提取算法的伪代码或示例，implementation agent 必须自行推断——这违反了 code-generation-ready 的要求。
- **直接证据**: plan 行 117-126 描述了规则但未给算法示例；代码行 215-216 定义了常量但无文档。
- **影响**: implementation agent 可能实现出与设计意图不同的 suffix 提取逻辑，导致 histogram 分组错误。
- **建议改法和验证点**: 在 plan 中补充至少 2 个 diagnostic ref → expected suffix 的示例，或给出提取算法的伪代码。
- **修复风险（低）**: 补充文档即可。
- **严重程度（低）**: 影响可控——即使 suffix 提取不准，full ref 仍作为 fallback 可见。

### 5-未修复-低-`_compact_payload_int` 和 `_compact_payload_bool` 的类型不匹配行为未定义

- **位置**: Slice 1 Exact allowed changes（行 182-183）
- **问题类型**: 契约缺失
- **当前写法**: `_compact_payload_int(payload, field_name) -> int | None` 和 `_compact_payload_bool(payload, field_name) -> bool | None`。plan 未说明当 field 存在但类型不匹配时（如 `"attempt_count": "5"` 字符串）应返回 `None` 还是抛出异常。
- **反例/失败场景**: EventLog payload 中的 `attempt_count` 理论上是正整数（由 `_required_non_negative_int` 校验），但如果未来的 Host 版本变更了字段类型，smoke 应优雅降级（返回 `None` 并标记 `<none>`）还是 fail fast（抛出 `TypeError`）？
- **为什么有问题**: 参照 plan 的总体策略（"不抛出无关异常"、"格式错误不应阻断 smoke"），应返回 `None` 而非抛出。但 plan 未明确此契约。
- **直接证据**: plan 行 182-183 只给了函数签名，无行为说明。
- **影响**: implementation agent 可能选择不同的错误处理策略。
- **建议改法和验证点**: 为 typed payload helpers 补充行为契约：类型不匹配时返回 `None`（与字段缺失一致），不抛出。
- **修复风险（低）**: 文档补全。
- **严重程度（低）**: 影响可控，两种选择都不会导致 production 问题。

## Open Questions

1. **`_compact_manifest_presence` 的返回值是什么？** Plan 说 "classified 为 present 或 missing"，但未给出具体的字符串常量。建议明确为 `"present"` / `"missing"` 或复用已有常量。

2. **`_compact_audit_report_from_rows` 是否需要与 `_compact_audit_summary_from_rows` 共享 request_trigger_sources 构建逻辑？** 两个函数都需要根据 request rows 归因 trigger source。如果各自构建，会产生重复逻辑。建议 `_compact_audit_report_from_rows` 内部复用 `_compact_request_trigger_sources`。

3. **Slice 2 的 README 更新是否需要在 `tests/README.md` 的 `Agent更新约束` 不存在时遵循 CL AUDE.md 的触发规则？** CL AUDE.md 说"若目标 README 尚未定义该约束，先只按本节触发规则判断是否需要更新，不要自行扩写目标文档职责"。`tests/README.md` 修改触发条件（`tests/` 修改）已满足，但 plan 应在 Slice 2 执行前确认不违反此约束。

## Over-engineering Verdict

Plan 新增 ~12 个模块级私有 helper，每个都有明确的单一职责：
- 5 个 typed payload helpers 消除重复的 `json.loads` + `isinstance` 检查
- 5 个 formatting helpers 各自处理一种特定的诊断输出转换
- 2 个 report 函数是核心交付物

无新增 abstraction layer、protocol、builder、wrapper 或 migration。所有 helper 只服务于 compact audit report 的构造和打印。**无过度设计。**
