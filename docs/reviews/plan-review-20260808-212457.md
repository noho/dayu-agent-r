### F20-RR3-MIMO-001-未修复-高-binding Goal要求的pre-dispatch hard guard被post-segment evidence gate替换
- **位置**: binding goal success signal 2；plan §2 signal 4、§3 formal non-goals、§5.2 formal chain、Slice 2与§10。
- **问题类型**: 目标漂移 / 过度削弱验收标准 / open question 未收敛。
- **当前写法**: binding goal `docs/gateflow/pr-190-f20-goal-confirmation-20260808.md:44-51`仍明确要求：每个actual accepted
  snapshot必须在下一ordinary dispatch前执行production完整renderer/estimator的fail-closed hard-bound guard。修订plan
  `:335-341`则明确不拦截dispatch、不形成pre-forward guard，只在segment结束后用canonical sizing truth决定该观察是否计入B2。
  RR2 adjudication `:46-59`把原要求称为“计划自增约束”并指示删除，但本轮仍将原goal artifact及同一SHA声明为binding，未提供新的
  Goal Confirmation或用户接受验收降级的记录。
- **反例/失败场景**: actual accepted snapshot在下一ordinary boundary达到或超过hard；stock CLI已经把该segment交给真实provider，
  之后publication再将链seal为`needs-more-evidence`。证据发布是fail closed的，但请求转发并没有按confirmed goal fail closed。
- **为什么有问题**: post-segment evidence acceptance能防止错误结论，却不能实现“dispatch前guard”这一明确的时序/安全行为。
  planreview必须把Goal Confirmation作为binding scope contract；review adjudication不能静默把未实现的success signal改写成较弱证据门。
- **直接证据**: goal `:38-51`；RR2 adjudication `:46-59`；plan `:335-341`。当前代码事实也已证明stock production CLI没有合法
  wrapper installation seam，因此这不是简单文字修正，而是需要goal层裁决的真实冲突。
- **影响**: implementation可以在未完成confirmed success signal的情况下被判PASS并消耗真实provider；final closeout无法诚实宣称
  F20 goal完成，后续B2报告会把“证据未接纳”和“请求未发送”两种不同事实混淆。
- **建议改法和验证点**: 二选一并重新冻结scope：
  1. 若pre-dispatch guard仍是目标，回到Goal/owner design gate，先解决stock CLI无合法seam的问题，再审plan；或
  2. 若用户接受stock CLI + post-segment evidence gate，把这一变化写入新的Goal Confirmation并明确其风险与非保证，再让plan绑定新SHA。
  不得仅靠RR2 review adjudication覆盖旧binding goal。
- **修复风险（高）**: 会改变正式观察的安全/证据语义，必须由Controller走goal confirmation，不能由implementation自行选择。
- **严重程度（高）**: 未修复时plan不满足其声明的binding goal。

### F20-RR3-MIMO-002-未修复-高-parent audit event无法直接证明production process-target identity
- **位置**: plan §5.2 proof bootstrap/audit allowlist、`proof-safety.json` child ledger、Slice 1 validation。
- **问题类型**: 不可直接实施 / 契约缺失 / observability gap。
- **当前写法**: plan `§5.2`要求parent audit hook在child创建事件发生时，只允许同时绑定executable resolved path/SHA、完整argv、
  target module+qualname和target canonical digest的production ToolRuntime child；随后还要求该event集合与“production process-target
  ledger”exact equality。计划没有给出这个target ledger的owner symbol或无侵入生成路径。
- **反例/失败场景**: production Fins tool走`multiprocessing` spawn。parent的`subprocess.Popen` audit event只暴露executable、argv、
  cwd、env；Fins target对象不在argv中，而是在spawn已经发起后经pipe写入child。因此两个拥有相同Python executable/通用spawn argv
  但携带不同pickled target的child，在当前audit event边界不可区分，hook无法按计划在spawn时以target digest fail closed。
- **为什么有问题**: `dayu/host/tool_runtime.py:1608-1616`先构造process target并交给capsule；
  `dayu/runtime/interruptible_process.py:296-304`实际创建的multiprocessing process target恒为`_run_process_target`，业务target只是其
  参数；本机Python `multiprocessing.popen_spawn_posix.Popen._launch`先以通用`spawn.get_command_line(...)`执行
  `spawnv_passfds`，随后才把包含`process_obj`/业务target的pickle写入pipe。直接audit探针也只得到
  `subprocess.Popen(executable, argv, cwd, env)`四项，不含target module/qualname/digest。仓库中没有production process-target
  manifest/ledger owner可供plan所称的exact equality使用。
- **直接证据**: `dayu/host/tool_runtime.py:1608-1616`；`dayu/runtime/interruptible_process.py:289-325,621-640`；当前Python
  stdlib `multiprocessing.popen_spawn_posix.Popen._launch`与`multiprocessing.util.spawnv_passfds`的本地源码；parent audit event参数的
  本地只读诊断。OS deny-network本身仍可覆盖descendants，本finding不否定该enforcement owner。
- **影响**: implementation必须临场选择私有frame/pickle introspection、target-factory wrapper或产品instrumentation才能满足文档；这些
  方案均未获计划授权，且可能违反“不替换production symbol/tool”的边界。否则`proof-safety.json`只能记录expected target，而不是actual
  spawned target，child exact-identity PASS不可审计，Slice 1会永久阻断或产生伪PASS。
- **建议改法和验证点**: 把spawn-time allow predicate限制为audit event真正可见且可冻结的executable/argv/env/count/ordering，并让
  OS sandbox继续独占network enforcement；若target identity仍是mandatory，必须在plan中指定唯一typed observation seam及owner：例如
  明确允许并冻结一个只记录、原样返回同一target对象的run-owned target-factory delegate，同时证明production ToolDefinition/ToolRuntime
  仍消费同一对象、target digest在spawn前已登记、audit event与登记项一一消费，且unknown/extra spawn fail closed。若不存在这种合法
  seam，就删除不可观测的target-level spawn claim，改为从canonical ToolCall + production factory input/output另行做post-run equality，
  不能说audit event本身证明target。
- **修复风险（中）**: 不需要改产品语义，但需要收敛proof instrumentation边界并补充negative test，避免把expected值冒充actual值。
- **严重程度（高）**: 当前契约是Slice 1/provider前blocking gate，却没有可实现的source of truth。
