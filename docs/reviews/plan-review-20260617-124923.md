## Findings

### 1-未修复-中-Host-owned tool display lookup 无代码证据支撑、现有效 snapshot 无 display metadata

- **位置**: 5. Public contract "Tool display lookup"、7.1 "Host public activity event projection"、11. Risks RR-ACT-01
- **问题类型**: 不可直接实施 / open question 未收敛
- **当前写法**: plan 写 "Host 侧必须在 run / attempt 可解释配置中拥有 effective tool metadata snapshot 或等价 Host-owned lookup，供 public activity projection 根据 stable tool_name 找到 ToolDisplayInfo.name。"；Allowed files 写 "Host-owned tool metadata lookup 所在模块，implementation agent 必须先基于代码事实定位。"
- **反例/失败场景**: 实现 agent 进入 Slice A 后，发现：
  1. `ToolSchemaSnapshot`（run_input.py:394）只有 `tool_schemas: tuple[ToolSchema, ...]`、`disable_tools: bool`、`tool_runtime_handle: ToolRuntimeHandle | None`——**没有任何 display metadata**。
  2. `ToolRuntimeHandle` 只暴露 `tool_schemas` 和 `tool_executor`，也没有 display 映射。
  3. `ToolDefinition.display`（tool_declaration.py:98）存在但位于 contracts 层，且 Engine/Host runtime snapshot 均未携带它。
  4. 实现 agent 只能在三个路径中选一个：(a) 扩展 `ToolSchemaSnapshot` 加 display mapping（但 plan 说"不改 durable schema"，而 ToolSchemaSnapshot 不是 durable schema，这是合法的）；(b) 在 Host 层新增 `tool_name -> display_name` 的最小映射表，基于 ToolBundle 装配时 snapshot；(c) 在 read_api projection 时访问 ToolRuntime（需要新的 Host 内部依赖）。
  5. 任意路径都涉及 plan 未预先裁决的设计决策，导致实现 agent 被迫重新设计。
- **为什么有问题**: plan 将"定位代码位置"委派给 implementation agent，但该位置在当前代码结构中不存在。这不是"找到代码"的问题，而是"需要新增 Host 层 capability"的问题——属于 Slice A 范围但未在设计层面收敛。
- **直接证据**:
  - `ToolSchemaSnapshot`（run_input.py:394-405）：三个字段，无 display
  - `ToolRuntimeSchemaSnapshotProvider.load_tool_schema_snapshot`（run_input.py:1672-1689）：只构造 ToolSchemaSnapshot，不附加 display metadata
  - 全 Host 层 grepping `ToolDisplayInfo` / `tool_display_name` / `effective_tool` 未找到已存在的 display lookup
- **影响**: 实施 Agent 跑偏——可能选错路径（如在 Engine 侧 import ToolDefinition 或把 display 塞进 durable schema），导致返工；或在 Slice A 停滞
- **建议改法和验证点**:
  - plan 应在 Slice A 的 exact allowed changes 中给出 **最少一种** 可实施的 display lookup 方案（推荐：在 Host assembly 阶段从 ToolBundle.definitions 提取 `{tool_name: display_name}` mapping，注入 run 上下文的 snapshot；或扩展 ToolSchemaSnapshot 新增 `tool_display_names: Mapping[str, str]` 字段）。
  - 验证：Slice A 实现后，`test_public_event_api.py` 能证明有 display metadata 时 activity.tool_display_name 非空
- **修复风险（低/中/高）**: 低——只需在 plan 中补充一个明确路径，不必改代码
- **严重程度（低/中/高/严重）**: 中——会导致实现 agent 在 Slice A 的第一阶段就停滞或走错方向

### 2-未修复-中-`HostEvent` 新增 `event_class`/`event_type` 与 `HostEventView` 存在字段重叠、未明确是否违反 Agent 语义约束

- **位置**: 5. Public contract "扩展 Host public HostEvent"、7.1 "Host public activity event projection"
- **问题类型**: 架构边界 / 过度耦合
- **当前写法**: plan 写 "为 HostEvent 增加：event_class: HostEventClass、event_type: str、activity: HostActivityView | None"，并说 "event_class / event_type 是 public identity，供 Service / UI 识别事件来源类别和去重 / 排序辅助；它们不是业务事实，也不是 UI 文案。"
- **反例/失败场景**: `HostEventView`（api.py:2515）已有 `event_class: HostEventClass`、`event_type: str`。`HostEventView` 是 `stream_run_events` 的内部视图，带 `payload_ref`/`payload_digest`（均属于 Host durable internals）。`HostEvent` 是 Service-facing public event。在 `HostEvent` 上新增 `event_class`/`event_type` 会使两个类型共享相同的 identity 字段但语义边界不同——Service/CLI 可以合法地根据 `HostEvent.event_class == "preview"` 做分支判断，但 plan 说它不是"业务事实"。如果 implementation agent 或未来的 UI developer 基于 `event_class` 做 UI 行为分支（如"preview 事件显示为 spinner，canonical_fact 事件显示为历史记录"），就违反了 Agent 语义约束中"不得让模型依赖隐式规则"的原则——因为 `event_class` 是一个治理标识，不是用户可见的业务语义。
- **为什么有问题**: AGENTS.md Agent 语义约束要求"内部治理标识如 label、id、ref、digest、cursor 只有任务必须引用时才可暴露；暴露时必须说明它只是引用标签，不是业务事实或推理依据。"plan 确实声明了它们不是业务事实，但未明确 **为什么 Service/CLI 需要 `event_class`**——如果只是为了 activity allowlist projection 中分类，那分类已经通过 `HostActivityView.kind` 表达了。`event_class` 泄露到 Service/CLI 层面可能被误用于 UI 决策。
- **直接证据**:
  - `HostEventView`（api.py:2515）已携带 `event_class`/`event_type`，但仅供 Host 内部 stream_run_events 使用
  - `HostEvent`（api.py:2973）当前不含 event_class/event_type，其 `kind: HostEventKind` 表达粗粒度生命周期
  - plan 未解释为什么 `HostEvent` 需要 event_class/event_type，而不仅仅通过 `HostActivityView.kind` 区分 activity 类别
- **影响**: Service/CLI 可能开始依赖 `event_class` 做业务判断；未来修改 HostEventClass 枚举时被迫联动 CLI；违反 Agent 语义约束的"不得让外部依赖内部治理标识"
- **建议改法和验证点**:
  - 方案 A（推荐）：`HostEvent` 不新增 `event_class`/`event_type`，activity 分类全部由 `HostActivityView.kind` 承载；`event_class`/`event_type` 只保留在 `HostEventView` 内
  - 方案 B：如果必须加，在 plan 中明确：`event_class`/`event_type` **只能用于去重/日志/诊断**，禁止 CLI/Service 根据它们做 UI 分支；并给出一个反例说明什么算误用
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中——如果保持现状，可能导致 CLI/Service 依赖内部治理标识做业务判断

### 3-未修复-中-Ctrl+C/Esc cancel 与 terminal 到达的竞态未在状态机中明确

- **位置**: 7.4 "Run-state key handling" 状态机、7.6 "Cancel semantics"
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: "Ctrl+C：运行态第一次请求 cancel_run(...)；若 cancel 已发出但 terminal 未返回，第二次 Ctrl+C 立即本地退出 130。"状态机显示 CANCELLING_VISIBLE/HIDDEN -> Ctrl+C -> 本地退出 130。
- **反例/失败场景**: 用户按 Ctrl+C 请求 cancel -> Host cancel_run RPC 已发出但尚未返回 -> 此时 terminal result（如 run_succeeded）先于 cancel confirmation 到达 watcher queue -> 状态机收到 terminal result，应进入 TERMINAL_RENDERING 还是继续等 cancel？如果 terminal result 已被 renderer 接受展示，用户再按 Ctrl+C（第二次）执行本地退出 130——此时 terminal result 已被消费但未展示给用户（因为 exit(130) 先执行了），用户看到 exit 130 而不是 final answer。
- **为什么有问题**: plan 7.6 写 "terminal 已先到达时，cancel 快捷键不得覆盖 terminal result"，但状态机中 CANCELLING 状态只定义了 Ctrl+C -> 本地退出，没有定义 "terminal 在 CANCELLING 期间到达" 的转换。实现 agent 需要自行裁决 terminal-vs-second-ctrl-c 的优先级。
- **直接证据**: plan 第 364 行状态机：`CANCELLING_VISIBLE / CANCELLING_HIDDEN：cancel 已请求，继续等 terminal；Ctrl+C -> 本地退出 130；Ctrl+T 仍可切换可见性。`——只说了"继续等 terminal"，但没说明 terminal 到达时从 CANCELLING 转换到 TERMINAL_RENDERING 以及此时应忽略第二个 Ctrl+C
- **影响**: 用户在 cancel 请求后、terminal 到达前按第二次 Ctrl+C 时可能丢失已成功的 terminal result；实现 agent 可能选择不当的竞态处理导致用户困惑
- **建议改法和验证点**:
  - 状态机中明确：CANCELLING 状态下收到 terminal event → TERMINAL_RENDERING（取消仍挂起的 cancel 等待），且此时 Ctrl+C 不再响应（terminal 已优先）
  - 测试：cancel RPC 延迟到达 + terminal 先到达场景；cancel RPC 先到达 + terminal 后到达场景
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中——可能导致用户可见的 terminal 丢失

### 4-未修复-低-HostActivityCounts 字段定义完全委派给 implementation agent、可能扩散 Any 风险

- **位置**: 5. Public contract "新增窄 enum / value objects"、7.1 "Host public activity event projection"
- **问题类型**: 契约缺失
- **当前写法**: "HostActivityCounts：强类型可选计数字段，至少支持 tool batch 的 total / completed / failed / cancelled；禁止用 dict[str, Any] 或 object。"
- **反例/失败场景**: 实现 agent 可能添加一个过于宽泛的可选字段（如 `extra: Mapping[str, int] | None`）绕过"强类型"约束。或不同 event type 的 counts 有不同字段（如 tool batch 有 completed/failed/cancelled，context compaction 可能有 before/after token counts），如果全塞进同一个 `HostActivityCounts` 会导致 God dataclass。
- **为什么有问题**: plan 说"至少支持 tool batch"，但没有给出具体字段清单和类型。实现 agent 需要自己决定是否按 event type 拆分 counts 类型（`ToolBatchCounts`、`CompactionCounts` 等）还是做一个通用 counts dataclass。两种选择对后续维护影响不同。AGENTS.md 禁止 God dataclass。
- **直接证据**: plan 第 185-186 行："HostActivityCounts：强类型可选计数字段，至少支持 tool batch 的 total / completed / failed / cancelled；禁止用 dict[str, Any] 或 object。"——只说"至少"，没给上限、字段名或类型的完整清单
- **影响**: 实施 Agent 可能做出次优设计（God counts 或过度拆分）；后续 slice 需要返工调整
- **建议改法和验证点**:
  - 在 plan 中明确 `HostActivityCounts` 的具体字段：`total: int`、`completed: int`、`failed: int`、`cancelled: int`，全部必填。若未来有其他 event type 需要不同计数字段，新增独立类型而非扩展 `HostActivityCounts`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低——窄化即可

### 5-未修复-低-non-TTY 模式下 Ctrl 键行为未定义

- **位置**: 7.3 "Renderer and TTY / non-TTY"、7.4 "Run-state key handling"
- **问题类型**: 契约缺失
- **当前写法**: "non-TTY stderr：默认 suppress live activity，只输出 terminal error/cancel"
- **反例/失败场景**: non-TTY 下（如 `dayu-cli prompt "..." | tee output.log`），用户按 Ctrl+C 期望取消——但 non-TTY 下 Ctrl+C 的行为（SIGINT）与 TTY 下 prompt_toolkit 的 Ctrl+C handler 不同。plan 没有区分 TTY 和 non-TTY 下的键盘处理路径。如果 non-TTY 下 prompt 命令使用了 `input()` 或 prompt_toolkit，Ctrl+C 会触发 KeyboardInterrupt，但 plan 定义的状态机（Ctrl+C 第一次 cancel，第二次退出）依赖 TTY 下的 custom handler。non-TTY 中这个状态机不可用。
- **为什么有问题**: 当前 `prompt` 命令不经过 composer（non-goal 明确不做 prompt composer），所以 Ctrl+C 在 prompt 的 non-TTY 模式下只会触发 SIGINT -> 退出 130。这与 plan 定义的"第一次 Ctrl+C cancel，第二次退出"语义冲突。plan 没有区分 prompt 的 TTY/non-TTY key handling。
- **直接证据**: plan 2. Non-goals 写 "不新增 prompt composer" —— prompt 没有 prompt_toolkit，所以 prompt 的键盘处理完全依赖 SIGINT handler。当前 prompt.py 已有 `sigint_monitor` 机制（plan 3. 引用 `_submit_prompt_turn_handling_sigint`）。plan Slice C 的 Ctrl+T toggle 只有 TTY 下有意义，non-TTY 下应无 toggle。
- **影响**: non-TTY prompt 用户按 Ctrl+C 行为与 TTY 不一致；用户困惑
- **建议改法和验证点**:
  - 在 plan 7.4 中明确区分 prompt（无 composer、SIGINT handler）和 interactive（composer、prompt_toolkit key binding）的键盘处理路径
  - prompt: TTY 下 Ctrl+T toggle、Ctrl+C 走现有 SIGINT monitor 语义；non-TTY 下 Ctrl+T 无操作、Ctrl+C SIGINT 退出
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低——用户可见但不常见

### 6-未修复-低-状态机定义与 slice 分配之间缺少跨 slice 集成测试

- **位置**: 7.4 "Run-state key handling"、8. Slice C/D/E
- **问题类型**: 切片过粗 / 测试缺口
- **当前写法**: 状态机在 7.4 中定义一次，但实现分散在 Slice C（prompt activity）、Slice D（composer）、Slice E（interactive activity）。每个 slice 有自己的 tests 小节。
- **反例/失败场景**: Slice C 实现 RUNNING_VISIBLE -> RUNNING_HIDDEN (Ctrl+T) 转换；Slice D 实现 INPUT -> RUNNING_* (Enter submit) 转换；Slice E 实现 INPUT -> RUNNING_VISIBLE -> ... -> TERMINAL_RENDERING -> INPUT。但在 Slice E 的测试中才会真正覆盖全状态机——如果 Slice C 或 D 的状态转换有 bug，到 Slice E 才发现，增加了返工成本。
- **为什么有问题**: 状态机是一个语义整体，但 plan 的 slice 按模块边界切分，不是按状态机边界切分。Slice C 测试只覆盖 prompt 路径的状态转换，Slice E 测试才覆盖 interactive 全路径。如果 C 和 D 之间的状态机边界有冲突（如 Ctrl+T handler 与 composer Enter handler 的优先级），要到 Slice E 才会暴露。
- **直接证据**: plan Slice C tests（第 526-533 行）没有提到与 composer 状态机的交互测试；Slice D tests（第 568-578 行）没有提到 Ctrl+T 交互；Slice E tests（第 609-613 行）才覆盖两轮 interactive
- **影响**: 返工——Slice C/D 的状态机冲突在 Slice E 才暴露
- **建议改法和验证点**:
  - 在 Slice C 的 exact allowed changes 中要求：状态机转换封装为独立模块/函数，各 slice 只调用转换函数而不自行实现状态逻辑
  - 或：在 plan 中接受此风险为已知 tradeoff（按模块切分而非状态机切分），并在 RR 中记录
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Architecture Boundary Review

- **分层**: plan 保持 `UI(CLI) → Service → Host → Engine`，CLI 不直接读取 Host durable internals，Engine 不 import Host 类型。通过。
- **公共契约变更**: `HostEvent` 扩展是 Host → Service 契约变更；`EntrypointActivity`/`EntrypointActivityCallback` 是 Service → CLI 契约新增。均在其所属层内定义。通过。
- **反向依赖**: 无。plan 明确 Engine 不 import ToolDefinition/ToolBundle；CLI 不读取 EventLog payload。通过。
- **过度耦合风险**: `HostActivityView` 与 Service `EntrypointActivity` 可能存在字段级耦合——plan 7.2 要求 Service DTO 独立定义，避免直接透传 HostActivityView。这是正确的解耦。通过。
- **durable schema**: plan 声称不改 durable schema——从现有 preview payload 字段（engine_ingest.py:4728-4769）看，activity projection 可以只读现有 payload 而不改写入路径。前提成立。通过。
- **`HostEventClass` 已在 public API 中存在**：plan 不需要新增该 enum。但 Finding 2 关注的是将其加入 `HostEvent` 的必要性。

## Best-Practice Review

- **强类型**: plan 要求 HostActivityView/HostActivityCounts 等均为强类型，禁止 Any/object/dict[str, Any]。Finding 4 关注 HostActivityCounts 字段定义不够具体。整体方向正确。
- **中文 docstring**: plan 要求所有 public dataclass/function 有中文 docstring、完整类型和 validation。AGENTS.md 编码硬约束对齐。通过。
- **测试覆盖率**: plan 要求新增模块 >= 80% 单文件覆盖率，符合 AGENTS.md。通过。
- **禁止兼容 wrapper**: plan stop conditions 明确 "需要保留旧 public event contract 兼容别名/wrapper 才能通过旧测试时停止"。通过。
- **README 触发检查**: plan 10 节列出触发规则，Slice F 负责执行。通过。
- **pyright**: plan 验证命令包含 pyright 全量检查。通过。

## Optimal-Solution Review

- plan 选择修正 Host session live watch 的 public event projection（root cause），而不是在 CLI 层读取 EventLog/Tool Trace 做 activity。这是正确的 root cause 修复。
- plan 选择 `HostActivityView` 作为 Host public display projection，而非暴露 raw preview payload。这保持了分层安全。
- plan 选择在 interactive 中引入 composer（多行/历史/外部编辑器），但不在 prompt 中引入。这符合各自的用户场景（one-shot vs REPL）。
- plan 选择 Ctrl+T 作为 toggle key，避免了与 Codex Ctrl+O 冲突（plan 2 已确认）。

## Overengineering Review

- plan 不引入 curses/TUI、durable activity store、background projection。范围恰当。
- `HostActivityView` 字段最小化：kind/status/title/summary/severity/tool_name/tool_display_name/counts。无冗余字段。
- Service EntrypointActivity DTO 独立于 HostActivityView，防止 Host 内部字段泄漏到 CLI。正确。
- Composer 封装为 CLI 层窄模块，不扩散 prompt_toolkit 类型到 Service/Host。正确。

## Overcoupling Review

- plan 将 `HostActivityView`、`EntrypointActivity`、CLI renderer state 作为三个独立类型，各自有明确的 ownership 边界。无跨层穿透。
- 状态机跨 Slice C/D/E 拆分（见 Finding 6），存在一定耦合风险但通过模块边界隔离。
