### 3.2 O(1) 临界区的 open/fstat/same-handle exact-prefix 方案在现有 append-only producer 下是否正确

**验证结论：通过**

直接证据：
- Plan §7.4 精确规定临界区："获取锁后只执行一次 binary open，立即对同一 handle `fstat`，记录 `prefix_byte_length=st_size` 与用于解释本次 snapshot 的必要 file identity...随后释放 lock。不得在锁内做任何 O(file-size) read、解析、SQLite、resolver 或 report 工作。"
- Plan §7.4 规定锁外读取："释放 lock 后只从上述同一 binary handle 循环读取精确 `prefix_byte_length` bytes，然后关闭 handle；不得重新打开 path，不得读取动态 EOF，也不得包含 prefix capture 后追加的 bytes。追加到 prefix 之后的数据留待下一次分析。"
- Plan §7.4 规定 fatal 条件："若在读满 prefix 前返回 EOF/short read、同一 handle 的 file identity 变化、`fstat` 显示文件被截断到 prefix 以下...则 fatal `cold_snapshot_read_failed`，不得用已读短前缀继续分析。"
- Plan §7.4 明确 append-only 语义："该边界确保 reader 不以全文件持锁反向消耗 producer 的 5 秒 lock timeout，同时让并发 append 具有确定的下一次可见语义。"

**append-only producer 下的正确性分析**：

POSIX 语义下，`open()` 返回的 fd 持有打开时的 inode 快照。`fstat()` 在锁内捕获 `st_size`（当前文件边界）。释放锁后，从同一 fd `read()` 只会读到 `fstat` 时的文件内容，不会包含后续 append。这是 POSIX 的标准行为，不依赖 OS append atomicity。

现有 producer（`tool_trace.py:468-501`）使用独占锁 + `_append_text_if_absent` 完成 append。当 reader 持有锁时，producer 等待（最多 5 秒）。当 reader 释放锁后，producer 获取锁并 append。append 的内容不会进入 reader 已捕获的 prefix，因为 reader 的 fd 是 `open()` 时的快照。

**关键验证点**：
- 不读 dynamic EOF ✓ — 只读精确 `prefix_byte_length`
- 不持锁做 O(file-size) I/O ✓ — 锁内只有 open + fstat
- Short read/truncate fatal ✓ — 明确的 fatal 条件
- Append 留到下次 ✓ — "追加到 prefix 之后的数据留待下一次分析"

**Live producer 测试验证**：
- Plan S1 tests："live producer concurrency：用 barrier 将 reader 的 prefix read 阻塞在释放 lock 之后，启动真实 producer append；断言 writer 在其既有 5 秒 timeout 前完成且无 `RuntimeFileLockTimeoutError`，再释放 reader，并断言本次 snapshot 不含新 append、下一次包含。"
- Plan §14.1 验证矩阵："live producer during slow prefix read — reader 释放锁后被 barrier 阻塞；真实 writer 在既有 5 秒 timeout 前完成，无 timeout；新 bytes 本次不可见、下次可见"

这证明了 non-interference，且不依赖 OS append atomicity（依赖 POSIX fd snapshot 语义）。
