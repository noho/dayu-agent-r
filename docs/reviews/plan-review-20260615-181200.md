### DS-003 / MiMo-003: progress event failure propagation

**Adjudication requirement**: Non-terminal progress event append failure logs bounded WARN and continues. Terminal event append failure also warns. Terminal job record remains truth.

**Plan evidence**:

- L253: "non-terminal progress / observation event append 失败不得导致 job failed；记录 bounded `WARN` 日志并继续执行业务路径。日志只能包含 job id、operation kind、event type、bounded payload keys/counts、异常类型和简短错误文本，不输出原文、绝对路径或 raw payload。"
- L254: "terminal event append 失败不得回滚已经保存的 terminal job record；记录 bounded `WARN` 日志，Service terminal fallback 仍可通过 `read_job()` 结束等待。"
- L309: "单个 progress event 映射或写入失败不得使对应 job failed；这类事件是观测/UI 信号，不是业务 terminal truth。runtime 记录 bounded `WARN` 并继续执行业务路径。"
- L310: "terminal job record 仍是业务状态真源。terminal event append 失败也只记录 bounded `WARN`，Service terminal fallback 仍可结束等待。"
- L319 (tests): "progress event append failure 后，如果业务 adapter/runner 成功，job 仍按业务结果成功或失败，不因 progress 写入失败被强制 failed；测试必须断言 WARN 存在。"

**Verdict**: 故障传播策略已完全修正。progress event failure 不再影响业务终态，WARN + continue 策略有测试覆盖。

### MiMo-004: sidecar file locking

**Adjudication requirement**: Event sidecar append/read sequence allocation uses the same FsFinsIngestionJobStore runtime file lock as job record operations.

**Plan evidence**:

- L136-138: "事件持久化建议使用 sidecar JSONL：`.dayu/fins_ingestion/jobs/<job_id>.events.jsonl`。不嵌入 job record，避免让 job terminal summary 变成 growing payload。event sidecar append/read sequence allocation 必须使用 `FsFinsIngestionJobStore` 已有同一把 runtime file lock，与 job record operations 共享锁保护。除非 implementation 以并发测试证明更窄锁不会导致 sequence race、terminal/event race 或 read-after-terminal gap，否则不得引入独立 sidecar lock。"
- L233: "`FsFinsIngestionJobStore` 使用 `<job_id>.events.jsonl` sidecar 追加事件；append/read sequence allocation 使用与 job record operations 相同的 `RuntimeFileLock`，在该锁下读取最后 sequence 并写入下一条。不得默认引入独立 sidecar lock，除非以并发测试证明更窄锁安全。"

**Verdict**: 锁策略已明确。sidecar 与 job record 共享同一 RuntimeFileLock，有并发测试验证要求。

### MiMo-008: status vs observation/progress event semantics

**Adjudication requirement**: Clarify event type semantics. Single enum acceptable if docstrings/helpers distinguish status events from observation/progress events.

**Plan evidence**:

- L114-123: "建议新增 `FinsIngestionJobEventType`。可以使用单个 enum，但必须用中文 docstring 或 helper 明确区分 status transition events 与 observation/progress events"。随后明确列出：
  - status transition events: `JOB_QUEUED`, `JOB_RUNNING`, `JOB_SUCCEEDED`, `JOB_FAILED`, `JOB_CANCELLED` — "只表示 job record 状态已发生对应转换；状态真源仍是 terminal job record，不是 event sidecar"
  - observation/progress events: `PROGRESS`, `CANCEL_REQUESTED` — "只表示用户可见观察信号或 cancel 请求观察信号，不推进 job state"
- L231: "`FinsIngestionJobEventType` 的 docstring/helper 必须把 status transition events 与 observation/progress events 分类清楚；单 enum 可接受，但不得让 `PROGRESS` / `CANCEL_REQUESTED` 被实现为 job state transition。"

**Verdict**: 事件类型语义已明确区分，单 enum + docstring/helper 分类方案符合 adjudication 要求。
