## Findings

### F01-未修复-低-`forward_intents.status` 与 `reference_continuity.reason` 语义仍为隐式

- **位置**: plan 的 Goal 与 Exact LLM-facing wording semantics 章节
- **问题类型**: open question 未收敛 / 范围边界可争议
- **当前写法**: plan 明确将 scope 限定为 `session_summary`、`evidence_facts`、`answer_anchors` 与四种 drop reason；不覆盖 `forward_intents` 的 `status`（`open`/`blocked`/`superseded`）或 `reference_continuity.reason` 的通用业务语义
- **反例/失败场景**: fresh model 看到 `forward_intents.status` 只允许 `open`、`blocked`、`superseded` 三个枚举值，但没有定义各值的业务含义；`superseded` 同时出现在 drop reason 和 forward_intents.status 中，模型可能将 drop reason 的"被替代"语义错误迁移到 intent status
- **为什么有问题**: 当前 prompt 对 `forward_intents.status` 只列枚举字面量（line 48），对 `reference_continuity.reason` 只给示例（line 52），与 PR 190 review F01 指出的 drop reason 缺口属于同一类问题。plan 将 scope 限定为 Goal Confirmation 已确认的字段是合理的范围约束，但该缺口仍会导致真实模型在 status 分类和 reason 语义上产生分歧
- **直接证据**: `conversation_compaction_user.md:48` 只写 "`status`: 字符串，只能为 `open`、`blocked`、`superseded`"，无业务定义；line 52 `reason` 有示例 "后续问题中的'该公司'需继续指向甲公司" 但无通用定义；`superseded` 同时出现在 line 48 和 line 60
- **影响**: 模型可能错误分类 intent status，或将 drop reason 的 `superseded` 语义套用到 intent status；drop audit 的互斥性不受影响，但 intent tracking 可能产生歧义
- **建议改法和验证点**: 可作为后续独立 work unit 补齐 `forward_intents.status` 与 `reference_continuity.reason` 的业务语义；不在当前 slice 中扩大 scope。若需在当前 slice 中处理，应先回到 goal confirmation
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低 — 因为 plan 明确将 scope 限定为已确认字段，且 first-review F01 与 PR 190 review F01 均只列出当前 scope 内的字段；此 gap 属于 deferred scope，不是 plan 设计缺陷

### F02-未修复-低-实现序列中 hash 更新步骤的 encoding 一致性未明确约束

- **位置**: Manifest and hash update procedure（lines 232-244）与 Implementation sequence 步骤 5-6
- **问题类型**: 可实施性不完整
- **当前写法**: 使用 `sha256sum` 命令行计算 digest，写入 manifest JSON 和 `FROZEN_MANIFEST_SHA256`
- **反例/失败场景**: 若实现 Agent 使用编辑器手动修改 JSON manifest，可能无意中改变文件末尾换行符（trailing newline present/absent），导致 `sha256sum` 计算的 digest 与编辑器保存的 bytes 不同。此时 `FROZEN_MANIFEST_SHA256` 常量与测试中 `_sha256_path(FROZEN_MANIFEST_PATH)` 的结果一致（因为都读同一个文件），但 plan 记录的"先算 prompt hash → 写 manifest → 再算 manifest hash"的顺序依赖中间文件状态稳定
- **为什么有问题**: 该风险很低——`sha256sum` 和 Python `_sha256_path` 都读 raw bytes，只要 manifest 文件保存后不再被编辑器修改，digest 就是确定性的。但 plan 未明确说明"保存 manifest 后立即计算 digest，不要再编辑"
- **直接证据**: plan line 243: "保存 manifest 后重新计算第二条 digest"；test line 741-748 使用 `_sha256_path` 读 raw bytes
- **影响**: 极低概率的 hash 漂移，会被 publication test 立即捕获
- **建议改法和验证点**: 在实施说明中补充"保存 manifest 后立即运行 `sha256sum`，不要再编辑文件"；或直接使用 Python 脚本统一计算两步 hash
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低 — publication test 会在 hash 不一致时立即失败，提供充分安全网

### `policy_limit` 可见条件

- **Plan 声明**（line 126）: "当前 repair feedback 已明确给出一个具体 cap，并且为使完整 replacement 落入该 cap 而必须舍弃它。首次请求、没有 repair feedback、或当前 feedback 没有明示具体 cap 时禁止猜测或使用 `policy_limit`"
- **Context Governance 验证**: `context_governance.py:492-504` — session_summary 超 cap 时生成含具体数值的 issue message（例如 "当前为 600 个字符，上限 500 个字符"）；`context_governance.py:540-577` — 各 section 的 item/char cap 均生成含具体数值的 issue
- **首次请求验证**: 当前 prompt line 72 明确 "首次请求没有修复反馈"；plan line 193 的不变量明确 "首次请求没有 repair feedback，因此没有具体 cap 时模型不能使用 `policy_limit`"
- **跨 section cap 匹配**: plan 的 "该 cap" 指向当前 repair feedback 中的具体 cap；模型可通过 issue 的 `json_path`（如 `$["evidence_facts"]`）识别被 cap 限制的 section，应只对属于该 section 的 source 使用 `policy_limit`。该匹配由模型自行完成，不在 prompt 中显式约束，但属于合理预期
- **结论**: ✅ Plan 正确将对 `policy_limit` 的判断锚定到 repair feedback 中的具体 cap 数值。`context_governance.py` 只在 candidate 超限后才生成 cap issue，首次请求不存在 cap 可见来源

### 四种 drop reason 自足性与互斥性

- **Plan 声明**（lines 123-127）: 四个 reason 各有独立定义，包含正向适用条件与负向禁止误用
- **Mutual exclusivity 验证**:
  - `superseded`: "被更新、更完整或更权威的 source 替代" — source 内容已过时
  - `redundant`: "内容仍然有效，但必要信息已被完整表达" — source 仍有效但已覆盖
  - `out_of_scope`: "与当前输入、当前会话任务及可预见后续对话无关" — source 有效但不相关
  - `policy_limit`: "内容仍相关且原本应保留，但为满足 cap 必须舍弃" — source 相关但受 cap 限制
- **互斥性边界清晰**: 四个 reason 覆盖了 source 的四种互斥状态：过时/重复/无关/被 cap 挤出。每个 reason 的负向约束进一步防止误用（如 `redundant` 不得掩盖冲突，`out_of_scope` 不得因难分类而滥用，`policy_limit` 不得隐藏冲突或无依据内容）
- **结论**: ✅ 四种 reason 的定义可区分且互斥。plan line 127 明确 "它们是对 source 实际业务关系的互斥解释"，现有 coverage 规则确保每个 source 恰好被保留或显式丢弃
