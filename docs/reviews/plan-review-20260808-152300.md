## Findings

### MIMO-F18-RR-001-未修复-高-R9 被 protected floor排除，R13 initial input不可能同时包含unsupported percentages

- **位置**: Slice 2 Shared PTY Run state machine 第5-7步。
- **问题类型**: 状态机漏洞 / 不可直接实施
- **当前写法**: R9写入 unsupported `21.7%/18.2%`；R10-R12后在R13断言R8 FY2025 evidence与R9 unsupported
  material都已进入同一 initial compact boundary。
- **反例/失败场景**: R13开始前 completed groups为R1-R12；floor=4精确保护最近R9、R10、R11、R12。R8刚好变为eligible，
  但R9仍被排除。因此四项 initial-input gate最多只能同时满足caps、previous atom、R8 FY2025 evidence三项，第四项必缺。
- **为什么有问题**: `select_compact_segment`先计算protected group ids，再将对应atomic units记为excluded；current input又单独作为
  protected anchor，不会把R9重新变成evidence/source-boundary material。计划要求的同boundary unsupported non-upgrade证据不可达。
- **直接证据**: `dayu/host/compact_material.py:1074-1135,2254-2295`；plan自己也明确R13时floor保护R9-R12。
- **影响**: replacement chain必然在R13按计划自身规则seal `needs-more-evidence`，三条链都无法形成完整B2 mandatory input。
- **建议改法和验证点**:
  1. 最小修复是把target后移一轮：R9输入unsupported percentages，R10-R13作为四个completed aging turns，R14 target，
     target accepted后R15 reconnect；同步重算Runs/calls/wall预算。
  2. 另一可行路径是让unsupported material与R8 FY2025 evidence同属R8 completed turn group，但必须证明没有把用户数字伪装成
     tool evidence，且 initial boundary仍按source kind区分。
  3. 目标operation开始前直接断言selected segment/source boundary包含R8与R9（或修订后的同组材料），不能只看Session raw history。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### MIMO-F18-RR-002-未修复-高-0.001 soft ratio使R6及baseline后的每轮都可发起operation，两operation matrix在R13前必然耗尽

- **位置**: Slice 2 Global frozen setup、R2-R7、premature compaction规则及三链matrix。
- **问题类型**: 状态机漏洞 / sequencing / 不可直接实施
- **当前写法**: 固定soft ratio `0.001`，预期R7创建baseline operation、R13创建target operation；R7-R13间出现额外request才seal。
- **反例/失败场景**:
  - MiMo context window为1,048,576时soft threshold是1048。Trial2 owner rows显示R1 candidate已9048 tokens，R2-R6为
    20363-21318，均远超threshold。
  - R1-R5期间即使超threshold，floor可令boundary为空而fallback dispatch；到R6时R1已离开最近4个completed groups，boundary首次
    非空，故第一个operation会在R6而非R7触发。
  - baseline一旦accepted，`build_compact_material_pack`在后续request始终带`previous_compacted_view`；candidate仍远超1048，
    所以下一Run即可形成第二operation。即使不在R6，R7 accepted后的R8也会触发；两operation cap远在R13前耗尽。
- **为什么有问题**: plan把memory output caps与context trigger threshold绑定成旧Trial transition值，却没有验证fixed-from-start的
  operation cadence。`max_reactive_compactions_per_run=2`是per-Run policy，不是整条chain的operation cap，也不能阻止逐Run proactive
  operations。
- **直接证据**:
  - Trial2 `CONTEXT_BUDGET_EVALUATED`：sequence 5 candidate=9048；sequence 125-181 candidate=20363-21318；constrained
    sequence 194的soft threshold=1048并决策`compact_soft_threshold`。
  - `dispatch.py::_prepare_compact_before_dispatch`只在`compact_input.source_boundary`为空时不创建operation；previous view由
    `compact_pipeline._request_plan_from_segment -> build_compact_material_pack`无条件带入。
- **影响**: 所有chain都会premature seal，`2/10` operation/call budget与R7/R13 preconditions不可同时成立，执行只会浪费provider。
- **建议改法和验证点**:
  1. 在首provider前用production candidate estimator和selection owner逐R dry-plan trigger cadence；禁止直接沿用0.001。
  2. 将context trigger policy与constrained output caps分开设计为同一个首-opener固定完整profile：memory caps保持1/160，context
     soft ratio选择能在预定baseline/target boundaries触发的值；不得运行中切换。
  3. 修订后必须证明每个R的`predicted_input_tokens`相对threshold、selected boundary emptiness和operation count上界；仅引用旧Trial
     “R7曾compact”不足，因为旧Trial在R7前使用soft threshold 681574、只在R7切到1048。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### MIMO-F18-RR-003-未修复-高-ordinary-call与wall-time所谓硬预算不能由现有执行机制保证

- **位置**: Evidence-calibrated execution matrix、Global frozen setup与Validation。
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: 将旧Trial sample推导出的`29/28` ordinary calls声明为hard cap；三条chain各600秒且总cap 1800秒。
- **反例/失败场景**: 新MiMo Run可因工具规划、continuation或重试在单个Run内超过旧sample call数。harness按Run terminal归档，无法在
  第29次前阻止该Run发出第30次；profile允许单Run最多24 iterations。即使三条chain恰好各在600秒停止，setup、进程cleanup、
  private/public projection、digest和final scan仍会使总wall time超过1800秒。
- **为什么有问题**: sample count是预算估计，不是enforcement contract。计划的validation却要求actual counts不超过matrix，存在无法
  由production CLI/harness实现的承诺；wall预算也没有finalization reserve。
- **直接证据**: plan冻结`AgentPolicy.max_iterations=24`且明确不改tooling；`29/28`来自Trial2的10-call与7-call samples，不是typed
  upper bound。三乘600等于registry全部1800秒。
- **影响**: bounded observation可能实际越界；或者为了守cap中断active Run，产生非目标cancel/不完整evidence并破坏chain。
- **建议改法和验证点**:
  1. 区分“expected sample budget”和“可强制hard bound”。hard ordinary-call上界必须从每Run frozen `max_iterations`乘Run数派生，
     或给出public-path实时计数/停止机制；不得把29/28继续写成绝对上界。
  2. Run数、compactor attempt/operation数仍可保持硬cap；每个Run terminal后核对actual call并决定是否启动下一Run，overshoot必须原样
     seal，不能声称未超过。
  3. 总1800秒采用remaining-time allocator：预留明确setup/finalizer/cleanup窗口，每条chain使用
     `min(600, total_remaining - reserve)`；reserve不足时不启动下一chain。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### MIMO-F18-RR-004-未修复-中-final scan只能在全部provider之后发现问题，不能同时作为“停止后续provider”的per-chain gate

- **位置**: Slice 2全局stop list与Slice 3 finalizer顺序。
- **问题类型**: sequencing / 可观测性缺口
- **当前写法**: secret/path scan失败被列为任一chain后“不得继续后续provider”的stop；但唯一冻结流程是全部report/projection写完后
  才写digest，最后写一次secret/path scan。
- **反例/失败场景**: replacement chain public projection若带入绝对路径，adaptive runner仍可能启动repair/fallback chains；最终scan
  才发现违规，已经额外消费provider。最终scan本身又不在先写的digest manifest中，registry需另有其digest owner才能冻结该结果。
- **为什么有问题**: final publication scan作为最后writer是正确的，但它不能兼任较早的per-chain continuation gate；两个时序职责
  被合并。
- **直接证据**: plan finalizer顺序固定为reports/projections → digest（排除self/final scan）→ final scan；stop list却要求scan
  failure阻止后续provider。
- **影响**: provider stop承诺不成立，或agent为提前scan而破坏“final scan是最后writer”不变量。
- **建议改法和验证点**:
  1. 每条chain seal后、启动下一chain前运行只读incremental hygiene precheck；它不是最终publication verdict。
  2. 全部写入结束后仍重新执行唯一final digest+scan流程，scan为最后writer；registry显式记录final scan文件自身的独立SHA256，
     不声称它被自引用manifest覆盖。
  3. final scan后任何写入都必须重新finalize，保留现有规则。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
