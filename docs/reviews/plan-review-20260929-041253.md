### 1-未修复-高-tool 验收/测试/证据配方把 observation-only 链路写成 durable job 链路，断言面不存在且与 13 处冻结断言冲突，并自带误触发停止条件
- **位置**: plan「测试、验证和证据」测试迁移段（`激活并等待 observation 后 job 为 failed，result_summary.failure 与 failure_summary 是 owner 的 exact content/empty_input_file JSON`）与 tool 真实入口验证段（`job record 的 result_summary.failure/failure_summary`、`若……job 无 typed failure，记录真实路径并按停止条件处理`）、「实施文件白名单与行为切片」S2 完成信号（`激活 observation 后 job failed`、`durable result_summary.failure/failure_summary 保持同一 JSON`）、停止条件（`tool awaiting→job failed 链`）。
- **问题类型**: 其它（plan 对 HEAD 的事实陈述错误）/ 测试缺口 / 不可直接实施
- **当前写法**: plan 假定 tool 的 awaiting→activation→终态链路会产出 durable job record，并把迁移后的 tool 测试与真实 tool 证据都锚定在 job record 的 `result_summary.failure`/`failure_summary` 两个字段上，要求其为 owner 的 exact typed JSON 并与 CLI 逐字段一致；同时把“job 无 typed failure”列为停止条件触发器。
- **反例/失败场景**: 实施 agent 按字面迁移 `test_upload_tool_empty_file_returns_failed_outcome_before_observation_start`：tool callable 只调用 `runtime.prepare_observed_upload`（`upload_tools.py:103-106`），该方法经 `_prepare_observed_stream` 登记 process-local observation 时显式 `job_record=None`（`ingestion_runtime.py:4050`），模块注释写明该设计是为了“避免 direct path 依赖 durable job store”（:2727-2729）；`activate_observation` 只把 `handle.handle_id` 当作 executor 诊断名提交后台线程（:3988-3990），全程不写 `FinsIngestionJobRecord`。因此不存在任何可断言的 `result_summary.failure`/`failure_summary`。三条可能的歪路全都出错：(a) 保留同测试文件既有 `assert not tuple(_job_store_root(...).glob("*.json"))`（:2293，该测试自身及另外 12 处共 13 处冻结“tool 调用后无 job record”）则新断言永远失败；(b) 为 tool 链路新增 durable job 持久化则打破 13 处冻结断言，且属 goal 未授权的 tool 可观测性语义变更；(c) 把 `start_upload` 塞进 tool 路径则改变 tool 启动语义。即便把“job”宽读为 observation，upload 终态 `FinsResultSummary.failure` 也恒为 `None`（`ingestion_runtime.py:6582`），typed 五字段只出现在 `details`（failure kind/code/file/failure message/retry hint）与 `error_message`。真实 tool 证据段的“job record……”要求同样落空，而 plan 自己写的“若……job 无 typed failure，记录真实路径并按停止条件处理”会被现实确定性触发，导致误停或私自造 job 语义。
- **为什么有问题**: (1) 与代码事实直接冲突：`result_summary`/`failure_summary` 仅属 `FinsIngestionJobRecord`（`ingestion_runtime.py:2019-2026`），tool 链路按设计不产生该对象；(2) 与同一测试文件内 13 处冻结断言自相矛盾，实施必然二选一破坏其一；(3) 与 goal 成功信号 3 的实际可满足面错位——goal 要求“tool……只投影同一个 typed reason；kind/code、label、文案、提示与 requested/stored 一致”，其真实投影面是 observation 终态 `FinsResultSummary` 的 details/error_message（`_upload_result_details` 正好给全 kind/code/file/message/hint 与 requested/stored），不需要也不该虚构 job record；(4) 停止条件措辞把“job 摘要存在”当同源前提，正确的同源断言在 observation 终态即可闭环。
- **直接证据**: `dayu/fins/tools/upload_tools.py:103-106,141`；`dayu/fins/ingestion_runtime.py:3848-3886`（`prepare_observed_upload`→`_prepare_observed_stream`，producer 为 `_DirectUploadProducer`）、`:4050`（`job_record=None`）、`:2727-2729`（context 注释）、`:3988-3990`（executor submit 仅用 handle id）、`:4658-4707` 与 `:5019-5033`（只有 `start_upload`/`_run_upload_job` 写 `result_summary`/`failure_summary`）、`:2025-2026`（字段归属）、`:6582`（upload RESULT `failure=None`）、全仓 `grep start_upload(` 无生产调用方；`tests/fins/test_fins_ingestion_tools.py:1238,1352,1440,1569,1866,1976,2077,2112,2293,2328,2347,2366,2394`（13 处无 job 断言）、`:1501-1514`（awaiting→activate→runner 调用且无 job 的既有模式）、`:2260-2293`（被迁移测试现状）。
- **影响**: S2 迁移测试与真实 tool 证据不可按字面实施；实施 agent 要么误触停止条件停工，要么为 tool 新增 durable job 语义（未授权行为变更、打破 13 处冻结断言、可能牵出 Host/tool 可观测性契约），验收将围绕不存在的字段扯皮并返工。
- **建议改法和验证点**:
  1. 把 tool 验收面改写为实际存在的投影：`ToolAwaitingOutcome` → `activate_observation` → `poll_observation` 终态快照——断言 observation status 为 FAILED、`result.details` 携带 failure kind=`content`、failure code=`empty_input_file`、file=实际 safe label、failure message/ retry hint 与 owner 固定文案一致、requested/stored 计数正确、`result.error_message` 同文案；安全 label 与“隐藏名/长度上界”断言照旧。
