## Findings

### 1-未修复-中-`_run_after_commit` 静默吞掉后续 callback 异常

- **入口/函数**: `_run_after_commit`
- **文件(行号)**: `dayu/host/durable/transaction.py` (行 324-346)
- **输入场景**: 多个 after-commit callback，第一个失败、后续也有失败
- **实际分支**: `for` 循环中 `except Exception` 只记录 `first_error`，后续异常被完全丢弃
- **预期行为**: 调用方应能感知所有 callback 失败，至少通过日志
- **实际行为**: 后续 callback 异常被完全吞掉，无任何日志。若 projection catchup callback 失败，调用方完全不知道
- **直接证据**: 行 335-341 — `except Exception as exc: if first_error is None: first_error = exc`；后续异常不 log、不收集
- **影响**: 可能导致 silent projection lag，projection checkpoint 滞后但无诊断信号
- **建议改法**: 收集所有异常到 list，至少用 `_LOGGER.error` 记录后续失败；或在 docstring 中明确这是 best-effort 语义且后续失败不记录
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-Duplicate Governance decide-then-record 存在 TOCTOU 竞态窗口

- **入口/函数**: `ToolRuntimeExecutor._execute_one()`
- **文件(行号)**: `dayu/host/tool_runtime.py` (行 2338-2421)
- **输入场景**: 同一 Run 的多个 `ToolRuntimeExecutor` 实例通过 `InMemoryRunScopedDuplicateGovernanceRegistry` 共享 state，并发执行相同工具调用
- **实际分支**: executor A 和 B 都在 `decide_duplicate()` 返回 `ALLOW` 后执行 callable + accept + record，因为 `RLock` 只保护 `find()` 和 `record()` 单次操作（行 1574、1587），不保护 decide-execute-accept-record 整个序列
- **预期行为**: `decide_duplicate()` 返回 `ALLOW` 后应预留占位，阻止并发 executor 重复执行
- **实际行为**: 两个 executor 都执行 callable 产生侧效应，Host accept barrier 幂等键阻止双重持久化写入，但 callable 侧效应已发生
- **直接证据**: `tool_runtime.py:1567-1588` — `find()` 和 `record()` 各自独立加锁；`tool_runtime.py:2338-2421` — decide 与 record 之间隔了整个 callable 执行
- **影响**: 当前 Engine 单 Attempt 顺序执行不触发；但 `InMemoryRunScopedDuplicateGovernanceRegistry` 的设计意图（跨 handle 共享）明确支持并发场景
- **建议改法**: 方案 A: 在 `_RunLocalDuplicateGovernanceState` 上提供原子 `decide_or_reserve(key) -> ALLOW | EXISTING`；方案 B: 将 decide + execute + record 纳入同一锁域
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-低-Lane `close()` 释放失败的 token 未标记 lost，heartbeat loop 可能持续无效刷新

- **入口/函数**: `LaneController.close()` -> `LaneController._release_token()`
- **文件(行号)**: `dayu/runtime/lane.py` (行 515-537, 706-728)
- **输入场景**: controller 持有多个 token，`close()` 逐一释放；某个 token 的 `_release_claim_sync` 抛出 `RuntimeLaneError`
- **实际分支**: `_release_token` 第 712 行 `await asyncio.shield(release_task)` 抛出 `RuntimeLaneError`，异常向上传播，`_mark_token_released` 未被调用
- **预期行为**: release 失败的 token 应被标记为 lost 或从 `_held_tokens` 移除
- **实际行为**: token 仍留在 `_held_tokens` 中（`released=False`），heartbeat loop 可能对该 token 发起无效 refresh
- **直接证据**: 第 524-529 行 `close()` 捕获异常但未标记 token 为 lost；第 728 行 `_mark_token_released` 只在 success path 调用；第 847-853 行 heartbeat loop 对未 released token 调用 refresh
- **影响**: heartbeat loop 可能产生 `ClaimLostError` 日志噪音；极端情况下触发 controller 级别关闭。但 `close()` 随后会 cancel heartbeat task，窗口有限
- **建议改法**: 在 `close()` 捕获 `RuntimeLaneError` 后显式调用 `_mark_token_lost(token)` 清理 Python 侧状态
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 5-未修复-低-WaitPoller 缺少并发保护

- **入口/函数**: `WaitPoller.poll_once()`
- **文件(行号)**: `dayu/host/wait_adapter.py` (行 327-400)
- **输入场景**: 两个定时器或调度任务同时调用同一 `WaitPoller` 实例的 `poll_once()`
- **实际分支**: 两次调用都读取同一批 active wait records，都对同一 record 调用 `adapter.poll_wait()`（可能涉及外部 HTTP 请求）
- **预期行为**: 同一 wait record 在同一轮 poll 中只被处理一次
- **实际行为**: `WaitPoller` 无任何锁或 CAS 机制。`resolve_wait` 内部幂等键阻止双重持久化写入，但 `poll_wait()` 外部调用会被执行两次
- **直接证据**: `wait_adapter.py:295-400` — `WaitPoller` 类无锁；`wait_adapter.py:333-335` — `run_read` 获取快照后在 transaction 外迭代处理
- **影响**: 当前单线程调度不触发；但缺少防护边界
- **建议改法**: 在 `WaitPoller` 中添加 `threading.Lock` 保护 `poll_once()`；或文档化不可并发调用的前置条件
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 6-未修复-低-TruncationManager `_cleanup_expired_cursors` 按插入序扫描，可能遗漏已过期 cursor

- **入口/函数**: `TruncationManager._cleanup_expired_cursors()`
- **文件(行号)**: `dayu/host/tool_runtime.py` (行 1443-1462)
- **输入场景**: Run 内累积大量 cursor，早期插入的 cursor 未过期，后期插入的已过期
- **实际分支**: `dict.items()` 按插入序迭代，扫描窗口 `_TRUNCATION_EXPIRED_CLEANUP_SCAN_LIMIT=256` 可能被未过期 cursor 占满
- **预期行为**: 清理应优先清理最老的 cursor
- **实际行为**: 250 个未过期 cursor + 100 个已过期 cursor → 只能扫到 6 个过期 cursor
- **直接证据**: `tool_runtime.py:1452` — `self._cursors.items()` 使用默认插入序；`tool_runtime.py:1454` — `scanned_count >= limit` 硬性截断
- **影响**: 过期 cursor 滞留内存直到被后续 `fetch_more` 调用触及。默认 TTL=600s 兜底
- **建议改法**: 改用 `sorted(..., key=lambda kv: kv[1].expires_at)` 按过期时间排序后扫描
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
