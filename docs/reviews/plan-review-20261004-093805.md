## 3. Findings

### 1-未修复-中-focused-source.json 的 retention_receipt 缺少解析 root，且与 --source-root 职责句矛盾
- **位置**: §4「两个固定 evidence source 的朴素接线与只读验收」focused-source.json schema 表 `retention_receipt` 行，及同节 `--source-root` 职责句。
- **问题类型**: 契约缺失 / 不可直接实施。
- **当前写法**: `retention_receipt={relative_path,sha256}` 定位 `workspace/tmp/upload-material-converter-diagnostics-20261003/root-code-fix-sol-01-retention.json`；但 validator 四个 evidence root 只按 `source_id` 选 root 对，而 `--source-root`“仅用于 strict 校验所引用的相对源码，不能代替 publicroot 或读取任意 private 证据”。
- **反例/失败场景**: 该 receipt 不在任何 public root 内，唯一可解析处是 source_root；实现 agent 要么越过 source_root 职责句解析它（与 plan 自身纪律冲突），要么不校验该字段（必填成装饰品，“缺任意 root/source/SHA…均拒绝”落空）。
- **为什么有问题**: plan 要求 code-generation-ready、必填缺失直接异常；此处把语义决定留给实现 agent 发明，正是 planreview 要拦的形态。
- **直接证据**: plan §4 两处原文；`ls` 实测 receipt 位于 D（workspace/tmp），不在 E/B/focused roots。
- **影响**: 实现语义分叉 / provenance gap 漏检 / review 无法验收该字段。
- **建议改法和验证点**: 明确 retention_receipt 解析规则（推荐：固定 repo 相对路径，在 source_root 下严格校验 SHA，并把 source_root 职责句改为“相对源码与列明的治理 receipt”；或把它改为只存 label+SHA 不读取并注明 validator 不校验）；补负例：receipt SHA 错/缺 → exit1 且 row 定位。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。

### 2-未修复-中-两条语义类负例没有机器可判定的 owner contract
- **位置**: §4 末段负例清单「观察报告混裁决」「用 WARN 条数或 Docling hash 作为业务 threshold」；§6 pytest contract 负例列表同名项。
- **问题类型**: 测试缺口 / 契约缺失。
- **当前写法**: 要求“每项最小破坏一个 owner contract 并断言 row/file 定位与 exit”；但纯观察报告是叙述性投影，新 oracle `expected/forbidden` 是自由文本数组，focused-source schema 闭合并不能约束报告正文。
- **反例/失败场景**: 实现只能发明字符串启发式（违反“自适应/严格 typed”纪律）或写空断言假覆盖；两种都使“有意义 owner 负例”落空，且 review 无法验证。
- **为什么有问题**: 与任务要求“唯一 strict-readonly readiness producer / 有意义 owner 负例”直接冲突；负例清单其余项（SHA 错、root 错接、symlink、duplicate sourceID 等）均可判定，唯此两项无契约。
- **直接证据**: plan §4/§6 原文；schema 表仅对 descriptor 闭合，未定义报告/expected-forbidden 的禁入字段或禁用字面量。
- **影响**: 假覆盖 / 测试固化偶然行为 / 业务 threshold 被悄悄写进 oracle 无人拦。
- **建议改法和验证点**: 二选一并写进 plan：(a) 定义可判定契约——typed 投影拒绝 verdict 类键；冻结样本字面量清单（848/22231/129/`96de32a7…` 等）禁止进入新 oracle expected/forbidden，violation 经 validator exit1 定位；(b) 明确这两项改为 review-time 人工检查、不进 validator 负例。验证：正/负例各一条可断言的 typed 破坏。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。
