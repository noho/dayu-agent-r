## Findings

### MIMO-001-未修复-高-事件重排序未作为兼容性关注点显式处理

- **位置**: §5.3 "ordinary pre-start allow candidate uses pre-generated attempt/execution id to write complete manifest; same transaction ordering: RUNNER_CALL_INPUT_ASSEMBLED → CONTEXT_BUDGET_EVALUATED → RUN_STARTED → ATTEMPT_STARTED"
- **问题类型**: 架构边界 / 状态机漏洞
- **当前写法**: Plan 将 `RUNNER_CALL_INPUT_ASSEMBLED` 从当前 `RUN_STARTED/ATTEMPT_STARTED` 之后移到之前，但只在 §5.3 中以 ordering block 形式陈述，未将此事件重排序作为独立兼容性/消费者影响进行分析。
- **反例/失败场景**:
  1. `dispatch.py::_start_governed_in_transaction` (line 2241) 当前调用 `start_governed_run_with_starting_attempt_in_transaction` 写 `RUN_STARTED → ATTEMPT_STARTED`，`RUNNER_CALL_INPUT_ASSEMBLED` 由 `RunInputBuilder.build()` 在 start 之后写入。整个 dispatch flow 从 `_run_pre_start_governance` 到 `_start_governed_in_transaction` 假设 start 事件先于 manifest 事件。重排序要求在同一个 transaction 中先写 manifest，再写 start——这改变了 `_run_pre_start_governance` 内部的 transaction composition。
  2. `read_api.py::_activity_from_row` 的 allowlist 对 `RUN_STARTED` 产生 `RUN_LIFECYCLE` activity。如果 `RUNNER_CALL_INPUT_ASSEMBLED` 现在出现在 `RUN_STARTED` 之前，下游按 event_sequence 排序的 projection consumer（如 stream_run_events）会先看到 manifest 事件，再看到 lifecycle 事件。虽然 manifest 本身不在 activity allowlist 中（返回 None），但任何按 sequence 做 ordering-sensitive 处理的逻辑都受影响。
  3. 现有测试（如 `test_dispatch_scheduler.py`）验证当前 event ordering。这些测试必须更新以反映新 ordering，但 plan 只说"更新测试"，没有将 ordering 变更作为 breaking change 显式追踪。
- **为什么有问题**: 设计真源 §25.1 明确了 proactive path 的 ordering（compact events → RUN_STARTED → ATTEMPT_STARTED），但没有明确 `RUNNER_CALL_INPUT_ASSEMBLED` 相对于 start 事件的位置。Plan 将其移到 start 之前是一个未被设计真源显式授权的状态机变更。虽然这在逻辑上是正确的（manifest 应先于 start），但缺少对消费者影响的显式评估。
- **直接证据**:
  - `dispatch.py` line 2241: `start_governed_run_with_starting_attempt_in_transaction` 在 governance allow 后立即调用。
  - `run_input.py` line 170: `_EVENT_TYPE_RUNNER_CALL_INPUT_ASSEMBLED` 定义存在，当前在 start 后写入。
  - `read_api.py` line 1059: `_activity_from_row` 按 event_type 路由，不感知 ordering。
  - Design §25.1: "proactive trigger → append CONTEXT_COMPACTION_REQUESTED → ... → append RUN_STARTED / ATTEMPT_STARTED → dispatch Engine"——没有提到 `RUNNER_CALL_INPUT_ASSEMBLED` 在此序列中的位置。
- **影响**: 实施 Agent 可能低估 ordering 变更的影响范围，遗漏 projection consumer 或测试更新。虽然 manifest 事件不在 public activity allowlist 中，但 internal projection、recovery scan 和 test assertions 都依赖当前 ordering。
- **建议改法和验证点**: Plan 应在 §5.3 或 §6 中增加一个显式段落，标题类似"Event Ordering Compatibility Impact"，列出所有消费 event_sequence ordering 的代码路径（dispatch、read_api、recovery、tests），并说明每个路径如何适应新 ordering。验证点：`rg -n "event_sequence|RUNNER_CALL_INPUT_ASSEMBLED" dayu/host tests/host` 确认所有消费者已更新。
- **修复风险（低/中/高）**: 低——只是增加显式文档和 checklist，不改变方案。
- **严重程度（低/中/高/严重）**: 高——ordering 变更是状态机级别的变更，遗漏消费者会导致 silent regression。

### MIMO-002-未修复-中-anchor scan 在并发 compaction 下的边界条件未明确

- **位置**: §5.4 "resolver按 session event sequence倒序、固定页大小 keyset扫描，遇到 latest accepted CONTEXT_COMPACTED boundary即停止"
- **问题类型**: 并发恢复风险 / 切片实施细节不足
- **当前写法**: Plan 描述了 keyset pagination scan 和 compact boundary stop，但没有说明当 compact 在 scan 进行中发生时的行为。
- **反例/失败场景**: Anchor scan 从 event_sequence=N 开始读第一页。此时另一个 scheduler 完成了一次 proactive compaction 并提交了 `CONTEXT_COMPACTED` 在 event_sequence=N+50。Scan 读第二页时会看到这个新 compact event。如果 scan 的 stop condition 是"遇到 latest accepted CONTEXT_COMPACTED 即停"，它会在第二页看到新 compact 并正确停止。但如果 scan 的实现是先读完所有页再判断 boundary，它可能会继续读到更旧的事件并找到一个已经被 compact 覆盖的旧 anchor。更微妙的是：如果 scan 在 compact 之前已经读到了一个 compatible anchor，但 compact 发生后该 anchor 的 baseline 已失效，scan 是否应该 re-validate？Plan 说"accepted compact是hard baseline barrier"，但没有说明 scan 内部是否需要在每个 candidate 上 re-check compact boundary。
- **为什么有问题**: 这不是功能正确性问题（最终会 fallback），而是实施 Agent 需要明确的边界条件。如果 scan 实现不检查中间 compact，它可能返回一个已经被 compact invalidation 的 anchor，导致使用过时的 baseline。虽然 range validation 和 P_current 计算仍会通过（只是预测不准），但这违反了"accepted compact 使旧 anchor 失效"的设计不变量。
- **直接证据**: Design §25: "accepted compact 改变上下文基线"是 anchor 失效条件。Plan §5.4: "遇到 latest accepted CONTEXT_COMPACTED boundary即停止"。但 scan 是按 page 读取的，每页之间可能有 compaction 发生。
- **影响**: 实施 Agent 可能写出一个在并发 compaction 下返回过时 anchor 的 scan 实现。虽然后果是预测偏差而非功能错误，但违反了设计不变量。
- **建议改法和验证点**: Plan 应在 §5.4 增加一句："scan 每页读取后必须 re-check 当前 latest accepted compact boundary；若 boundary 在 scan 过程中前进，已读取的 candidate 中被 boundary 覆盖的部分必须丢弃，scan 从新 boundary 之后重新开始或直接 fallback。"验证点：测试中构造"scan 进行中发生 compaction"的场景，确认 resolver 正确处理。
- **修复风险（低/中/高）**: 低——增加一句规格说明。
- **严重程度（低/中/高/严重）**: 中——影响预测准确性但不导致功能错误或数据损坏。

### MIMO-003-未修复-中-Engine continuation manifest v2 "complete" 条件的具体重建路径未规格化

- **位置**: §5.3 "Engine continuation只有在完整 projection、selected tool schema、effective policy 和 request semantics均可重建时写 complete；否则写明确 unavailable"
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan 对 ordinary 和 compactor proposal 的 manifest v2 producer 有明确规格（ordinary 写 complete，compactor 写 not_applicable），但对 Engine continuation 只给了高层原则。
- **反例/失败场景**: Engine continuation（tool_result_continuation kind）发生在同一 Run 的后续 iteration。Plan 要求 continuation 的 manifest 必须包含 `sizing_snapshot`，且 status=complete 时所有 nullable value 字段必须非空。问题是：continuation 是否总是能重建 `selected tool schemas`？如果 tool schema 在两次 iteration 之间变化（例如 Service 动态修改了 tool bundle），continuation 的 tool schema snapshot 可能与初始 dispatch 不同。此时 continuation 的 `request_semantics_digest` 和 `input_snapshot_digest` 会不同，但它仍然可以是 compatible anchor（因为 request semantics 实际上没变，只是 tool schema snapshot 不同）。Plan 没有明确 continuation 的 tool schema 从哪里获取——是从 Attempt runtime handle 的 frozen snapshot 读取，还是从当前 effective bundle 重新选择？
- **为什么有问题**: 实施 Agent 在 Slice 1 中需要让三个 producer 都写 v2 manifest。如果 continuation 的 tool schema 来源不明确，实施者可能做出与 ordinary producer 不一致的选择，导致 anchor compatibility 判断出错。
- **直接证据**: Plan §5.1: "tool-enabled path同样先从 admission冻结的 effective bundle 产生 selected tool-schema snapshot，Attempt-scoped ToolRuntime / executor handle 仍在 start 后按同一 snapshot 创建"。这说明 tool schema 是在 admission 时冻结的。但 continuation 的 tool schema 是否也从同一个 frozen snapshot 读取？Plan 没有显式说明。
- **影响**: 实施 Agent 可能对 continuation 的 tool schema 来源做出错误假设，导致 manifest v2 的 sizing_snapshot 不一致。
- **建议改法和验证点**: Plan 应在 §5.3 的 Engine continuation 段落增加："continuation 的 selected tool schema 必须从 Attempt runtime handle 持有的 frozen tool-schema snapshot 读取，与初始 ordinary dispatch 使用同一 snapshot。若 frozen snapshot 不可用（例如 crash recovery 后），continuation 必须写 status=unavailable 并附明确 reason。"验证点：测试 continuation manifest 的 tool schema digest 与初始 ordinary manifest 一致。
- **修复风险（低/中/高）**: 低——增加一句规格说明。
- **严重程度（低/中/高/严重）**: 中——影响 anchor quality 但不导致功能错误。

### MIMO-004-未修复-低-candidate_input_digest 与 manifest sizing_snapshot digest 的关系未明确

- **位置**: §5.1 "input_snapshot_digest：覆盖 messages projection、selected tool schema snapshot 与 request-semantics digest" vs §5.3 "complete ordinary manifest、hot payload、projection descriptor、tool schema descriptor 与 sizing snapshot 必须通过同一 manifest digest 保护"
- **问题类型**: 契约缺失
- **当前写法**: Plan 定义了两个 digest：candidate 的 `input_snapshot_digest`（覆盖 messages + tool schemas + request semantics）和 manifest 的整体 digest（覆盖 manifest 全部内容包括 sizing_snapshot）。Fact identity 使用 `candidate_input_digest`，但 manifest digest 包含 sizing_snapshot 而 candidate 的 input_snapshot_digest 不包含。
- **反例/失败场景**: 如果同一个 candidate 被 evaluate 两次（例如第一次 conservative fallback，第二次有了 anchor），两次的 sizing_snapshot 不同（method 不同），因此 manifest digest 不同。但 candidate_input_digest 相同（因为 messages/tool schemas/request semantics 没变），所以 fact identity 相同——这正是幂等性所期望的。然而，如果 manifest digest 被用于 pairing（例如 anchor resolver 通过 manifest event id 读取 manifest），两个不同 digest 的 manifest 可能导致 confusion。
- **为什么有问题**: 这不是功能错误（plan 的设计是自洽的），但实施 Agent 需要明确 input_snapshot_digest 和 manifest digest 的关系，避免在 anchor resolver 中错误地用 manifest digest 代替 input_snapshot_digest 做 compatibility 判断。
- **直接证据**: Plan §5.1 定义 input_snapshot_digest 覆盖范围。Plan §5.3 定义 manifest digest 覆盖范围。两者不同。
- **影响**: 低——主要是实施 clarity。
- **建议改法和验证点**: Plan 应在 §5.1 或 §5.3 增加一句明确区分："input_snapshot_digest 是 candidate 级 identity，不包含 sizing_snapshot；manifest digest 是 manifest 级 identity，包含 sizing_snapshot。Anchor compatibility 判断使用 manifest 中的 input_snapshot_digest 字段，不使用 manifest digest。"
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 低。
