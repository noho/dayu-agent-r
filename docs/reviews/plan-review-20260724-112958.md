## 4. 七个指定攻击面深度验证

### 4.1 Attack Surface 1 — cold_lock_path 共享 helper 的 import/call path

**验证目标**: Service path discovery → Host public Source 构造的完整路径，确认共享 helper 公开可达且不让 Service 依赖 `dayu.host` 内部模块，不产生 compat wrapper/facade。

**直接证据**:

- 当前 `_default_tool_trace_lock_path` 位于 `dayu/host/open_host.py:2621`，是模块私有函数。
- 当前 `_LOCK_TIMEOUT_SECONDS = 5.0` 位于 `dayu/host/tool_trace.py:224`，是模块私有常量。
- Plan §7.4 规定共享 helper 由 `dayu.host.tool_trace` projection owner 拥有，命名为 `tool_trace_cold_lock_path(cold_jsonl_path: Path) -> Path` 和 `TOOL_TRACE_COLD_FILE_LOCK_TIMEOUT_SECONDS = 5.0`。
- Plan §7.3 规定 `cold_lock_path` 字段"必须严格等于 Host Tool Trace owner 的 `tool_trace_cold_lock_path(cold_jsonl_path)` 结果；不是调用方可任选的另一把锁"。
- Plan §7.4 规定 "Service/CLI 只传/展示 Source，不复制 path 或 timeout 规则"。

**分析**:

`ToolTraceAnalysisSource` 是 Host-owned public dataclass，定义在 `dayu/host/tool_trace_analysis_contracts.py`（S1 新建）。Service 的 `discover_tool_trace_analysis_source(input_path)` 需要构造完整的 Source 实例。对于 `cold_lock_path` 字段，有两种合法实现路径：

- **路径 A**: Service 自行派生 lock path（如 `cold_jsonl_path.with_name(cold_jsonl_path.name + '.lock')`），Source 在 Host boundary 做第二次校验确认其等于 `tool_trace_cold_lock_path(cold_jsonl_path)`。
- **路径 B**: `ToolTraceAnalysisSource` 提供一个 Host public factory/constructor（如 `from_discovery(...)` classmethod），内部调用 `tool_trace_cold_lock_path` 填充锁路径；Service 调用该 factory。

Plan 当前只有 dataclass 声明，没有 factory 方法。路径 A 要求 Service 知道 lock path 派生规则（`.lock` suffix），这构成了隐式知识重复——与 plan 自身 "Service/CLI 不复制 path 规则" 的约束存在张力。路径 B 更干净但 plan 未明确。

**实际风险**: implementation agent 可能选择路径 A（在 Service 中写 `cold_jsonl_path.with_suffix('.lock')` 或等价逻辑），导致 lock path 规则在 Service 和 Host 两处重复。如果未来 lock path 规则改变（如改为 `.tool-trace.lock` 或移到子目录），两处需要同步修改。

但这不是 hard blocker：plan §7.3 的 Source boundary 二次校验机制可以在 Host 侧拒绝 lock path 不匹配的 Source，从而在运行时捕获不一致。代价是运行时错误而非编译期保证。

**结论**: 路径可达，但 plan 缺少 Source factory/constructor 的明确签名。建议在 S1 contract 中补充 `ToolTraceAnalysisSource` 的构造方法签名，明确 lock path 由 Host 内部 helper 填充而非 Service 派生。**不影响 plan pass**，属 residual risk。

### 4.2 Attack Surface 2 — Read-only opener busy timeout 配置真源

**验证目标**: `configure_read_only_connection_pragmas` 的 `busy_timeout_seconds` 参数来源是否明确；全局 `--base/--config` 不参与时不能隐式取运行 Host 配置。

**直接证据**:

- Plan §7.1: "全局 `--base/--config` 对此命令不参与输入发现；Analyzer 的输入只由显式 `INPUT` 决定"
- Plan §8.4: "`configure_read_only_connection_pragmas(connection, *, busy_timeout_seconds)` helper，只按以下顺序设置并校验：`PRAGMA busy_timeout=<由 Host storage policy 秒数转换的非负整数毫秒>`"
- Plan §8.4 同时说: "read-only opener 禁止调用现有写侧 `configure_connection_pragmas`"
- 当前 `configure_connection_pragmas`（`transaction.py:457`）从 `HostSQLiteStoragePolicy.busy_timeout_seconds` 取值。
- `HostSQLiteStoragePolicy` 由 `HostCommandHandleOptions` 派生，而 `HostCommandHandleOptions` 由 `OpenHostOptions.sqlite_busy_timeout_seconds` 填入。

**分析**:

Plan §8.4 说 busy_timeout 来源是 "Host storage policy"，但 Analyzer CLI 命令是 standalone 工具，不使用 `--base/--config`，不存在运行中 Host 实例。`HostSQLiteStoragePolicy` 不存在于 Analyzer 进程中。

Plan 没有为 `configure_read_only_connection_pragmas` 的 `busy_timeout_seconds` 参数指定具体默认值。implementation agent 面临选择：(a) 硬编码一个值（如 5.0 秒），(b) 从某处读取配置，(c) 设为 0（不等待）。

**实际风险**: implementation agent 可能自行决定一个值（如 5.0 秒），但该值未被 plan 或 contract 固定。未来变更可能导致不一致行为。更严重的是，如果 implementation agent 选择 0 或极小值，在 live producer 持有写锁时 read-only opener 可能立即失败。

**建议**: 在 §8.4 中为 `busy_timeout_seconds` 明确一个 Analyzer 专用默认常量（如 `DEFAULT_TOOL_TRACE_ANALYSIS_SQLITE_BUSY_TIMEOUT_SECONDS = 5.0`），并在 `ToolTraceAnalysisPolicy` 或 read-only opener contract 中声明该常量是配置真源。该常量与 producer 的 lock timeout（也是 5.0）语义不同（一个是 SQLite busy wait，一个是 file lock timeout），不应混用同一个常量名。

**严重程度**: 中 — 缺少配置真源可能导致 implementation agent 做不一致选择。

### 4.3 Attack Surface 3 — 独占 cold lock 覆盖全文件复制 vs live producer

**验证目标**: Reader 持 `RuntimeFileLock` 覆盖整个 cold 文件 copy 是否会让 live producer 的 5 秒 lock timeout 失败；评估临界区缩小方案。

**直接证据**:

- Plan §7.4: "reader 持锁期间只打开一次 cold file、读取到 EOF 并复制 immutable bytes snapshot；解析、join 与规则执行在释放锁后进行"
- Plan §7.4: "随后 cold reader 对 `source.cold_lock_path` 调用 `dayu.runtime.filelock.file_lock`，使用上述 5 秒 timeout"
- 当前 producer `_append_line`（`tool_trace.py:491-501`）使用同一 `_LOCK_TIMEOUT_SECONDS = 5.0`，且持锁期间完成 `_append_text_if_absent`（含 file read 查重 + append write）
- Plan §17.1 risk table: "live producer导致跨hot/cold观察窗口 | fixed in current WU by watermark/lock rule；极端持续写入为limited | 不做distributed snapshot"
- Plan §17.1 risk table: "极大cold文件的内存/运行时成本 | tracked by Issue #36；首版stream parse但聚合仍驻内存 | report cold-line size；不建stream processor"

**分析**:

Plan 当前的锁策略是 reader 持锁期间完成"打开 cold file → 读取到 EOF → 复制全部 bytes"。对于当前 workspace（9 行，约 25 KiB），这是瞬时的。但对于生产环境的大 cold 文件（例如 Issue #36 尚未治理的长期累积 JSONL），全文件复制可能耗时数秒甚至更长。

**失败场景**: cold JSONL 文件 10 MiB，reader 持锁复制耗时 ~3 秒（慢盘）。此时 producer 尝试 append 新行 → `file_lock.acquire(timeout=5.0)` → 等待 reader 释放 → 3 秒后 reader 释放 → producer 在 timeout 内获取锁 → append 成功。这个场景是安全的。

**危险场景**: cold JSONL 文件 500 MiB，reader 持锁复制耗时 ~30 秒。Producer 的 5 秒 timeout 到期 → `RuntimeFileLockTimeoutError` → cold append 失败。这是 **live producer 的反向阻塞**。

**关键 POSIX 语义**: 在 POSIX 系统上，`open()` 返回的 fd 持有打开时的 inode 快照。后续 `read()` 从该快照读取，即使其他进程在 `open()` 之后追加/截断文件。因此，**临界区只需要保护 `open()` + `fstat()` 以确定 fd 对应的文件边界**。后续的 `read()` 可以安全地在释放锁之后进行——fd 保证读取一致性。

**当前 plan 的保守设计**: "持锁期间读取到 EOF 并复制 immutable bytes snapshot"——这把临界区扩展到了全文件读取，不必要地延长了持锁时间。

**评估**: 对于当前 workspace（9 行），这不是实际问题。但 plan 没有在 §7.4 中讨论临界区缩小策略，也没有在 §17.1 risk table 中显式记录"reader 持全文件复制锁可能反向阻塞 producer"这一风险。Issue #36 的 risk entry 只覆盖 analyzer 自身的内存/运行时成本，不覆盖 producer 阻塞。

**建议**: 在 §7.4 中明确临界区边界：(1) 持锁 → open cold file → fstat 获取 inode 大小 → 释放锁；(2) 无锁状态下从已打开的 fd 读取到 fstat 记录的边界；(3) 关闭 fd。或者，至少在当前 plan 中承认此风险并在 §17.1 新增一条 residual risk："reader 全文件锁复制在极大 cold 文件时可能超过 producer 5 秒 lock timeout，导致 producer cold append 失败；临界区缩小到 open+fstat 在 POSIX 上可解决此问题，首版可保守复制但需在 risk 中记录"。

**严重程度**: 中高 — 对当前 workspace 无影响，但生产环境（未经 Issue #36 治理的大 cold 文件）存在真实 producer 阻塞风险。

### 4.4 Attack Surface 4 — Cold/hot discovery 与 load 之间 TOCTOU

**验证目标**: 各场景的 fatal/finding/limitation 分类是否一致。

**直接证据与逐场景验证**:

| 场景 | Plan 规定 | 分类 | 一致性 |
|---|---|---|---|
| Hot 在 discovery 时缺失 + cold 存在（目录模式） | §7.2: `hot_store_unavailable` limitation | limitation | ✓ |
| Hot 在 discovery 时存在，load 时消失 | §8.4: "directory discovery 后 expected hot path 已存在，但不再是 regular file..." → fatal analysis, CLI 1 | fatal | ✓ |
| Cold 在 discovery 时缺失 + hot 存在（目录模式） | §7.2: "产生 confirmed `missing_cold_trace` findings"；§7.4: "workspace/dayu mode 若 cold expected path 在 discovery/load 两次都不存在且 hot 可用，保持 hot-only" | finding | ✓ |
| Cold 在 discovery 时存在，load 时消失 | §7.4: "cold path 曾存在但 load 时消失是 fatal `cold_snapshot_read_failed`" | fatal | ✓ |
| Cold-file/trace mode cold 缺失 | §7.4: "cold-file/trace mode 的 cold 缺失始终失败" | fatal | ✓ |
| Hot store 可用但无 rows | §7.4: "watermark 固定为 0"；§8.3: join 可正常执行（无 rows 可 join） | normal | ✓ |
| Cold-only row 的 `event_sequence > hot_watermark` | §7.4: `reason_code=input_changed_during_analysis` limitation | limitation | ✓ |
| Cold-only row 的 `event_sequence <= hot_watermark` | §8.3: `integrity.missing_hot_trace` | finding | ✓ |
| Hot-only row（有 hot 无 cold） | §8.3: `integrity.missing_cold_trace` | finding | ✓ |
| 目录模式 hot 和 cold 在 discovery 时都缺失 | §7.3: "directory mode 的 hot/cold 都缺失" → Source reject | usage error | ✓ |
| Hot 和 cold 都在 discovery 后、load 前消失 | Plan 未显式覆盖此组合 | — | **见下文** |

**边界场景分析**: "hot 和 cold 在 discovery 后都消失"——在 load 阶段，hot DB open 首先尝试。若 hot 路径的 regular file 已消失 → `open_host_durable_read_store` 的 pre-check 会发现文件不存在。按 §8.4，directory mode 下 expected hot path "在 load 时确实不存在，且 cold 可读，才允许产生 `hot_store_unavailable` limitation"。但此时 cold 也可能已消失。若 cold 也消失 → `cold_snapshot_read_failed` fatal。由于 hot DB 先于 cold lock 打开（§7.4: "read transaction 必须在获取 cold lock 前关闭"），执行顺序是：open hot → read hot pages → close hot transaction → acquire cold lock → open cold file。若 hot 失败后不继续 cold（因 hot fatal），则不会观察到 cold 的消失。若 hot 成功但 cold 消失 → cold fatal。两种路径下都是 fatal。**无分类漂移风险**。

**结论**: TOCTOU 分类矩阵一致，无 gap。

### 4.5 Attack Surface 5 — Structured JSON 字段单复数、Source fields、report schema、renderer、tests 同源

- Plan §10.1: `ToolTraceVendorDebuggingBlock` 的 12 个字段 contract 与 §9.6 完全一致。

**S2→S3 稳定性检查**:

Plan §8.1: "S3 不修改 `tool_trace_analysis_contracts.py`，不改变 S2 顶层字段、枚举、nullable 语义、finding ordering/id assignment、Host/Tool rule 语义或 vendor block shape；只在 `tool_trace_analysis_rules.py`/orchestration 中追加 Engine/provider findings、vendor block instances 和对应 limitations。"

**单复数冲突问题**:

**严重程度**: 中 — schema contract 不一致会导致 implementation agent 做不同选择，影响 report JSON 的稳定 schema。

### 4.6 Attack Surface 6 — S1 scope 与 "不修改 producer/schema" 一致性

**验证目标**: S1 改 `tool_trace`/`open_host` 共享 helper 与 scope 表述、allowed files、README 触发、测试矩阵是否一致。

**直接证据**:

- Plan §3.1: "不修改 Tool Trace event filter、extract/render、hot/cold producer 或 line schema"
- Plan §13 S1 Prerequisites: "不修改 producer/schema"
- Plan §13 S1 Allowed files 包含: `dayu/host/tool_trace.py`、`dayu/host/open_host.py`
- Plan §5.1.6: "S1 将该既有行为收敛为 Host Tool Trace projection owner 的共享内部 contract，producer 和 cold reader 都调用同一个 path/timeout 真源；不改变 cold line、event filter 或 append 语义"

### 4.7 Attack Surface 7 — Dual publish typed error 路径完整性

**验证目标**: 第一次 replace 失败、第二次 replace 失败、cleanup failure 时是否能保持原错误和路径真源。

**直接证据**:

Plan §10.3 定义了 `ServiceToolTraceAnalysisPublishError`:
- `published_paths: tuple[Path, ...]`
- `failed_path: Path`
- `temporary_paths_cleaned: bool`
- underlying error summary

**逐路径追踪**:

**路径 1 — JSON replace 失败（第一次 replace）**:
1. Service 在 output dir 创建 temp JSON file → UTF-8 write + flush ✓
2. `os.replace(temp_json, json_path)` 失败（如 permission denied）
3. Error 构造: `published_paths=()`, `failed_path=json_path`
4. Best-effort cleanup temp_json
5. 若 cleanup 成功: `temporary_paths_cleaned=True`
6. 若 cleanup 失败: `temporary_paths_cleaned=False`，但 **不覆盖** `failed_path=json_path` ✓
7. 不删除旧 JSON 文件 ✓
8. 不尝试 Markdown publish ✓
9. CLI exit 1，stderr 打印失败原因 ✓

**路径 2 — Markdown replace 失败（第二次 replace，旧 Markdown 存在）**:
1. JSON temp write + replace 成功 → `published_paths=(json_path,)` ✓
2. Markdown temp write + flush 成功
3. `os.replace(temp_md, md_path)` 失败
4. Error 构造: `published_paths=(json_path,)`, `failed_path=md_path` ✓
5. 新 JSON **保留**（不删除/不回滚）✓
6. 旧 Markdown **保留**（未被 replace 覆盖）✓
7. Best-effort cleanup temp_md
8. CLI exit 1，stderr 分别打印 "已发布: json_path" 和 "发布失败: md_path" ✓

**路径 3 — Markdown replace 失败（第二次 replace，旧 Markdown 不存在）**:
1. JSON temp write + replace 成功 → `published_paths=(json_path,)` ✓
2. Markdown temp write + flush 成功
3. `os.replace(temp_md, md_path)` 失败
4. Error 构造: `published_paths=(json_path,)`, `failed_path=md_path` ✓
5. 新 JSON **保留** ✓
6. Markdown 目标路径**不存在**（旧 Markdown 本就不存在，replace 失败意味着目标路径未被修改）✓
7. Best-effort cleanup temp_md
8. CLI exit 1 ✓

**路径 4 — Cleanup 自身失败**:
Plan §10.3: "cleanup 自身失败也保留在 typed error 中，不覆盖原 failed path"。这意味着 typed error 需要同时承载 "原始 publish error" 和 "cleanup error"。但当前 `ServiceToolTraceAnalysisPublishError` 只有一个 underlying error summary 字段。如果 cleanup error 需要保留，plan 需要明确是两个独立错误还是 cleanup error 作为 suppressed secondary。

**建议**: 在 typed error 中增加可选的 `cleanup_error: str | None` 字段，或在 error summary 中明确分离 "原始错误" 和 "cleanup 错误"。只记录 cleanup 失败到日志中也是可接受的方案。

**严重程度**: 低 — cleanup 失败是罕见场景，主错误信息已保留。

**结论**: 三条主路径的 published/failed path 真源正确。Cleanup failure 的 secondary error 保留方式可进一步明确，但不影响 correctness。

## 5. Findings

### F-R1 — 中高 — Reader 全文件锁复制可能阻塞 live producer

- **位置**: §7.4 File consistency and concurrent writers
- **问题类型**: 并发恢复风险
- **当前写法**: "reader 持锁期间只打开一次 cold file、读取到 EOF 并复制 immutable bytes snapshot；解析、join 与规则执行在释放锁后进行"
- **反例/失败场景**: 生产环境 cold JSONL 文件经长期累积达到数百 MiB。Reader 持 `RuntimeFileLock` 复制全文件耗时超过 producer 的 5 秒 lock timeout → producer `_append_line` 获取锁超时 → `RuntimeFileLockTimeoutError` → cold append 失败。这是 Analyzer（只读工具）反向阻塞了生产路径。
- **为什么有问题**: Plan 的锁策略不必要地把临界区扩大到了全文件读取。POSIX fd 在 `open()` 时获取 inode 快照，后续 `read()` 无需持锁即可从该快照安全读取。临界区只需要覆盖 `open()` + `fstat()`。当前策略对当前 9 行 workspace 无影响，但对未治理的大 cold 文件存在真实风险。Plan §17.1 risk table 未记录此风险（issue #36 entry 只覆盖 analyzer 内存/运行时，不覆盖 producer 阻塞）。
- **直接证据**: Plan §7.4 line 407-411；`tool_trace.py:491-501` producer `_append_line` 使用 5s timeout；`dayu/runtime/filelock.py` 确认 lock 为同步互斥。
- **影响**: 生产环境可能导致 cold JSONL append 失败，丢失 Tool Trace 记录。
- **建议改法和验证点**: (1) 在 §7.4 将临界区缩小为 `acquire lock → open cold file → fstat → release lock → read from fd → close fd`；(2) 或在 §17.1 新增 residual risk "全文件锁复制在极大 cold 文件时可能超过 producer lock timeout；首版可接受但需在 Issue #36 治理后评估临界区缩小"。
- **修复风险**: 低（临界区缩小的 POSIX 语义可靠）
- **严重程度**: 中高

### F-R2 — 中 — Read-only opener busy_timeout 配置真源缺失

- **位置**: §8.4 Read-only durable opener
- **问题类型**: 契约缺失
- **当前写法**: "`PRAGMA busy_timeout=<由 Host storage policy 秒数转换的非负整数毫秒>`"
- **反例/失败场景**: Analyzer 是 standalone CLI 工具，不使用 `--base/--config`，不存在运行中 Host 实例。`HostSQLiteStoragePolicy` 不存在于 Analyzer 进程中。Implementation agent 面临选择：硬编码 5.0 秒？设为 0？从某处读取？不同选择导致不同的 SQLite busy 等待行为。如果设为 0 且 live producer 正持有写锁，read-only open 立即失败。
- **为什么有问题**: `configure_read_only_connection_pragmas(connection, *, busy_timeout_seconds)` 的 typed signature 已定义，但该参数的实际值来源未定义。Plan 说 "由 Host storage policy 秒数转换" 但 Analyzer 上下文中不存在 Host storage policy。
- **直接证据**: Plan §7.1 明确 `--base/--config` 不参与；§8.4 "由 Host storage policy" 与 Analyzer standalone 语境矛盾。
- **影响**: Implementation agent 可能做不一致选择；测试无法验证预期 busy_timeout 值。
- **建议改法和验证点**: 在 §8.4 或 `ToolTraceAnalysisPolicy` 中定义 Analyzer 专用 SQLite busy timeout 默认常量（如 5.0 秒），并明确该常量独立于生产 Host storage policy。在 S1 tests 中验证 read-only PRAGMA trace 包含预期的 busy_timeout 值。
- **修复风险**: 低（增加一个命名常量并引用）
- **严重程度**: 中

### F-R3 — 中 — JSON report `input` 字段与 Source contract 单复数不一致

- **位置**: §7.3 Source contract vs §10.1 JSON 示例
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: §7.3 `ToolTraceAnalysisSource` 定义 `cold_jsonl_path: Path`（单数）、`cold_lock_path: Path`（单数）。§10.1 JSON 示例使用 `"cold_jsonl_paths": ["..."]`（复数数组）、`"cold_lock_paths": ["..."]`（复数数组）。
- **反例/失败场景**: Implementation agent 在实现 report JSON renderer 时，选择跟随 Source contract（单数 string）还是 JSON 示例（复数 array）。两种选择导致不同的 JSON schema。若 Reviewer 按 §10.1 示例验收，按 Source contract 实现的 agent 会被要求返工。
- **为什么有问题**: Source contract 和 report schema 是两个不同层（pre-analysis input vs post-analysis output），但命名冲突会导致实现歧义。Report `input` section 投影自 Source，应使用一致的字段名。首版只有单文件输入，使用单数或单元素数组均可，但必须明确。
- **直接证据**: §7.3 六个字段均为单数 Path；§10.1 JSON 示例使用复数数组名。
- **影响**: JSON report schema 不稳定；implementation agent 可能做不一致选择。
- **建议改法和验证点**: 统一 report `input` section 的字段名为单数（`cold_jsonl_path`、`cold_lock_path`、`hot_db_path`、`artifact_root`）以匹配 Source contract；或保留复数但显式注释"首版为单元素数组，预留未来多文件扩展"。
- **修复风险**: 低（plan 文本修正）
- **严重程度**: 中

### F-R4 — 低 — `cold_lock_path` 由谁调用共享 helper 填充未明确

- **位置**: §7.3 Source contract、§7.4 lock ownership、§12.2 Service entrypoint
- **问题类型**: 架构边界
- **当前写法**: §7.3 要求 `cold_lock_path` "必须严格等于 Host Tool Trace owner 的 `tool_trace_cold_lock_path(cold_jsonl_path)` 结果"。§7.4 说 "Service/CLI 只传/展示 Source，不复制 path 或 timeout 规则"。§12.2 的 Service entrypoint `discover_tool_trace_analysis_source(input_path) -> ToolTraceAnalysisSource` 需要构造完整 Source。
- **反例/失败场景**: Implementation agent 在 Service 层实现 `discover_tool_trace_analysis_source` 时，需要设置 `cold_lock_path`。若在 Service 中写 `cold_jsonl_path.with_name(cold_jsonl_path.name + '.lock')`，则 lock path 规则在 Service 层重复。若 Source boundary 校验不通过（比如 Service 的派生与 Host helper 结果不一致），则 runtime 报错——这是 fail-safe 但体验不佳。
- **为什么有问题**: Plan 没有提供 Host public factory/constructor 让 Service 在不复制规则的前提下构造 Source。当前只有 dataclass 声明。Service 要么导入 `dayu.host.tool_trace`（内部模块）调用共享 helper，要么在 Source boundary 做二次校验。
- **直接证据**: §7.3 dataclass 无 factory 方法；§12.2 Service entrypoint 签名；§7.4 "不复制 path 或 timeout 规则"。
- **影响**: 低。Implementation agent 可以通过在 Host contract 模块提供 factory 方法解决；或在 Service 中做简单路径拼接后由 Source boundary 校验。两种方案都可行。
- **建议改法和验证点**: 在 §7.3 补充 `ToolTraceAnalysisSource` 的构造方法（如 `@classmethod def from_discovery(...)`），内部调用共享 helper 填充 lock path，Service 直接调用该 factory。
- **修复风险**: 低
- **严重程度**: 低

### F-R5 — 低 — S3 allowed files 遗漏 `tool_trace_analysis_contracts.py` vs S2 contract freeze 语义

- **位置**: §13 Slice 3 Allowed files
- **问题类型**: 切片过粗
- **当前写法**: S3 allowed files 为 `dayu/host/tool_trace_analysis_rules.py`、`dayu/host/tool_trace_analysis.py` 和对应测试。Plan §8.1 说 "S3 不修改 `tool_trace_analysis_contracts.py`"。
- **反例/失败场景**: S3 实现 Engine/provider rules 时，发现需要在 `ToolTraceVendorDebuggingBlock` 增加字段（如新的 limitation 类别）。按 plan 规则，S3 不能修改 contracts，应作为 limitation 处理。但若 implementation agent 认为该字段是 S2 遗漏的必要字段，会产生 scope 冲突。
- **为什么有问题**: S3 的 stop condition 已覆盖此场景（§13 S3: "若当前 trace 无法区分一个计划中声称 available 的 provider identity，停止并降为 limitation；若 success signal 必须依赖新 producer field，则回 Controller"）。但这只覆盖 provider signal 缺失场景，不覆盖 vendor block 字段遗漏。缺乏对 contract 修改的显式 stop condition。
- **直接证据**: §13 S3 allowed files 不含 contracts.py；§8.1 规定 S3 不修改 contracts。
- **影响**: 低。S3 实现大概率不需要修改 contracts（plan 的 vendor block 字段已足够详细）。但缺少显式的 "contract 修改需回 Controller" stop condition。
- **建议改法和验证点**: 在 §13 S3 stop condition 中增加："若 S3 发现必须修改 S2 冻结的 contract 字段、枚举或 nullable 语义才能完成 Engine/provider rules，停止并回 Controller"。
- **修复风险**: 低
- **严重程度**: 低
