## Findings

### DL-PA-01-未修复-低-amendment 未显式声明三个已有 call sites 的 `start_is_explicit` 预期值

- **位置**: Amendment §3、§6（plan §14.7）
- **问题类型**: 不可直接实施（implementation agent 需自行推断参数值）
- **当前写法**: Amendment 指出 "更新 required `start_is_explicit` 的真实 `CnPipeline.download/download_stream` call sites"，但未说明三个已有 calls 应传 `True` 还是需要根据场景区分
- **反例/失败场景**: Implementation agent 对 line 337（`start_date="2025-01-01"`）、line 402（`start_date="2024-01-01"`）、line 454（`start_date="2025-01-01"`）的 `start_is_explicit` 取值有歧义——虽然从语义上所有显式传入 `start_date` 的调用都应传 `True`，但 amendment 未锁死这一推断
- **为什么有问题**: Plan 要求 "code-generation-ready"，精确参数映射是 code-generation-ready 的基本要求。amend 后 implementation agent 仍需自行判断
- **直接证据**:
  - `test_cn_pipeline.py:337` — `start_date="2025-01-01"`，无 `start_is_explicit`
  - `test_cn_pipeline.py:402` — `start_date="2024-01-01"`，无 `start_is_explicit`
  - `test_cn_pipeline.py:454` — `start_date="2025-01-01"`，无 `start_is_explicit`
  - Amendment 原文："更新 required `start_is_explicit` 的真实 `CnPipeline.download/download_stream` call sites"（无 per-site mapping）
- **影响**: Implementation agent 推断正确（均 `True`）时无实际影响；推断错误或犹豫时增加修复迭代
- **建议改法和验证点**: 在 amendment 中显式声明：line 337/402 `download()` → `start_is_explicit=True`；line 454 `download_stream()` → `start_is_explicit=True`。或在 accepted amendment commit 的 message 中锁定该映射
- **修复风险（低）**: 仅文档补全，不改变 scope 或实现
- **严重程度（低）**: 语义推断几乎唯一（显式传入 date → explicit=True），实际偏航概率极低

### DL-PA-02-未修复-低-`start_date` 非空且 `start_is_explicit=False` 的 owner 反例测试场景不可通过当前 public API 构造

- **位置**: Amendment §3、"验证 `start_date` 非空但 `start_is_explicit=False` 时 CN workflow仍启用默认业务限制"
- **问题类型**: 测试缺口 / 契约缺失
- **当前写法**: Amendment 要求新增 owner 断言，验证 `start_is_explicit=False` 且 `start_date` 非空时 CN pipeline 仍启用默认业务限制
- **反例/失败场景**: 当前 `download_contract.py:155` 定义 `start_is_explicit=start is not None`，因此 `start_is_explicit=False` ⇔ `start_date=None`。该测试场景必须绕过 `build_fins_download_request()` 直接调用 `CnPipeline.download(start_date="2025-01-01", start_is_explicit=False)`，即用"不可能通过公开 API 到达"的参数组合测试内部行为
- **为什么有问题**: Owner test 直接验证 pipeline 对 typed field 的消费行为是合理的（证明 pipeline 不反推 date 存在性），但当前 plan 未区分"pipeline 层 owner test（直接调用内部 API，合法）"与"端到端 contract test（仅通过公开 API，合法）"。若不标注该测试为 pipeline-layer direct contract test，未来维护者可能误认为 `start_is_explicit=False + start_date="2025-01-01"` 是合法端到端场景
- **直接证据**:
  - `download_contract.py:155` — builder 中 `start_is_explicit` 与 `start_date` 存在性绑定
  - Amendment §3 — "验证 `start_date` 非空但 `start_is_explicit=False` 时 CN workflow仍启用默认业务限制"
  - Plan §9 static check — "不构造 `start_is_explicit=True` 且start bound为空的非法date-range组合"（仅禁止了反向非法组合，未标注正向测试为 internal contract test）
- **影响**: 该测试被误读为端到端场景时，可能误导 builder 设计或 test 演化方向
- **建议改法和验证点**: Amendment 或 implementation artifact 中标注该测试为 "pipeline-layer direct contract test：绕过 builder 直接验证 pipeline 对 typed field 的消费行为"。不改变测试本身或 scope
- **修复风险（低）**: 仅注释/文档补全
- **严重程度（低）**: 不影响正确性；不加标注不会导致错误，只影响长期可维护性

- **直接证据**:

- **影响**: 若 review 未严格执行，upload 测试区域可能被附带修改，造成 diff 膨胀和 review 焦点分散
- **建议改法和验证点**: Amendment 或下一 gate 的 implementation instruction 中要求 implementation agent 在 commit message 中声明"未修改 upload 测试区域"，code review 用 `git diff HEAD -- tests/fins/test_cn_pipeline.py | grep -c "test_upload"` 零增量作为 hard stop
