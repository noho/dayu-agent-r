### DS-01 — identity-free candidate sizing + allow 后同事务 identity allocation/consumption

- **Controller 要求**: "sizing 不依赖 manifest；decision 为 allow 后，在同一 write transaction 内生成实际将被 start transition 消费的 identity，随后写 manifest / budget fact / start facts。compact/block candidate 不生成 runner-call manifest 或未消费的 durable Attempt identity。不得引入新 durable candidate table 或兼容 shim。"
- **修订 plan 位置**: §1.3、§5.1、§5.3、§8.2、§14、§15
- **最终复审状态**: **已修复**

**证据链**:

1. **identity-free candidate**：Plan §5.1 的 `PreparedRunnerCallCandidate` 显式不含 `attempt_id`、`execution_id`、`dispatch_record_id` 字段。其字段为 `session_id`、`run_id`、`candidate_input_cursor`、`candidate_input_projection_ref/digest`、`input_snapshot_digest`、`messages`、`tool_schemas`、`disable_tools`、`policy_snapshot`、`source_cursor_refs`、`memory_snapshot_cursor_ref`、`compact_artifact_refs`、`context_fallback_decision_ref`、`request_semantics_digest`。无任何 Attempt/execution/dispatch identity 字段。
   - Plan §5.1 明确："`PreparedRunnerCallCandidate` 不包含、预留或分配 Attempt/execution/dispatch identity，也不依赖 `RUNNER_CALL_INPUT_ASSEMBLED`。它只拥有完整 logical input、policy/request semantics 和 source watermark，足以计算 `E_current` 与 sizing decision。"

2. **allow 后同事务 identity allocation**：Plan §5.3 线性时序：
   ```text
   -> if allow:
        construct one StartGovernedRunInput (allocate identities now)
        -> finalize candidate projection/complete manifest with that input's
           attempt_id/execution_id
        -> append RUNNER_CALL_INPUT_ASSEMBLED
        -> append CONTEXT_BUDGET_EVALUATED
        -> call existing start_governed_run_with_starting_attempt_in_transaction(...)
        -> transition appends RUN_STARTED -> ATTEMPT_STARTED and inserts dispatch row
        -> commit
   ```
   Plan §5.3 定义 `_new_governed_start_input(run, occurred_at) -> StartGovernedRunInput` 和 tagged union `DispatchStartPlan = BudgetedDispatchStart | NoBudgetDispatchStart`。identity 在 allow decision 之后、manifest 写入之前分配，manifest 与 transition 消费同一 `StartGovernedRunInput` 中的 identity。

3. **soft/hard 零 manifest/Attempt identity**：Plan §5.3：
   ```text
   -> if soft/hard:
        append CONTEXT_BUDGET_EVALUATED
        -> append compaction/fail-close transition
        -> commit
        (no runner-call manifest, no Attempt/execution/dispatch identity allocation)
   ```
   Plan §1.3："soft/hard candidate 不写 runner-call manifest，也不分配 durable Attempt identity。"

4. **代码事实验证**：`StartGovernedRunInput`（run_transition.py:297-327）的全部 identity 字段均由 caller 提供，transition 内部不生成 identity。这直接证明了 plan 的方案可行：caller（dispatch.py）在 allow 后生成 identity → 传入 `StartGovernedRunInput` → manifest 和 transition 消费同一 identity → 无循环依赖。

5. **无新 candidate table/shim**：Plan §3.2 non-goals 和 §14 DS-01 disposition 均明确不引入新 durable candidate table 或兼容 shim。`PreparedRunnerCallCandidate` 是内存中的 frozen dataclass，不持久化。

**结论**: DS-01 完全修复。Plan 以 identity-free candidate 打破"manifest 需要 identity ↔ identity 只在 start 时创建 ↔ start 只在 allow 时发生 ↔ allow 需要 sizing ↔ sizing 需要 manifest 中的 E_current"的循环依赖。方案使用代码中已存在的 caller-owned identity contract（`StartGovernedRunInput`），无需修改 durable transition。

- **Controller 要求**: "Fix 必须选择一个具体 transaction 方案，说明 CAS/precondition、identity allocation、append ordering、rollback/normal return 与 caller handling；测试必须断言 CAS miss 后 EventLog 零孤立 manifest/fact。"

1. **唯一 private exception rollback 方案**（Plan §5.6 steps 1-5）：

   - Step 4: transition 返回 `NOT_FOUND|INVALID_STATE` 或 `UPDATED` 却缺完整 rows → `_commit_dispatch_candidate_in_transaction` 抛私有 `_StartCandidateCasMissRollback(Exception)` → `run_write` rollback
   - Step 5: `_run_pre_start_governance` 在 `run_write` 外捕获该私有异常 → debug log → 返回无 dispatch；其他异常不吞掉

2. **低层 CAS_LOST**：Plan §5.6 明确 `_require_run_mutation_updated`（run_transition.py:3330-3346）在 `status != UPDATED` 时通过 `_raise_after_event_append_mutation_failure`（run_transition.py:3406-3419）抛 `HostDurableError`。该异常同样触发 `run_write` rollback（transaction.py:347-352），并向调用方传播为 durable concurrency/integrity failure。

3. **本 re-review 独立验证**：
   - `HostTransactionRunner.run_write`（transaction.py:317-358）：正常返回 → `COMMIT`（line 325）；任意异常（lines 347-358）→ rollback 后透传。✅
   - `_raise_after_event_append_mutation_failure`（run_transition.py:3406-3419）：总是抛 `HostDurableError`。✅
   - 因此，precondition miss（抛 `_StartCandidateCasMissRollback`）和低层 CAS_LOST（抛 `HostDurableError`）都在同一 transaction 内触发 rollback，projection payload、manifest、fact、start facts、state rows 全部回滚。✅

4. **测试要求**：Plan §5.6："测试分别注入 precondition `INVALID_STATE` 与低层 `CAS_LOST`：两者都必须在新 transaction 断言 candidate projection payload、`RUNNER_CALL_INPUT_ASSEMBLED`、`CONTEXT_BUDGET_EVALUATED`、`RUN_STARTED`、`ATTEMPT_STARTED` 与 dispatch/Attempt rows 均为零"。

5. **不修改通用 transaction runner**：Plan §5.6 明确"不得修改 `HostTransactionRunner`、不得让 transition 抛业务无关异常、不得以特殊正常返回值请求 rollback"。

**结论**: DS-02 完全修复。Plan 选择了与现有 `run_write` 异常即 rollback 语义天然契合的方案：precondition miss 抛私有异常 → rollback → caller 转无 dispatch；低层 CAS_LOST 抛既有 `HostDurableError` → rollback → 传播。不修改通用 transaction runner，不引入 sentinel 返回协议。
