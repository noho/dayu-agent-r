### F1-严重 — SSE 流式重试导致事件层数据重复

- **入口/函数**: `AsyncOpenAIRunner._call_impl` → `_do_attempt`
- **文件(行号)**: `dayu/engine/runners/openai/runner.py:285-299`
- **输入场景**: SSE 流式 200 响应已产出部分事件（content delta / tool_call delta）后，网络中断触发 `_AttemptFailedRetriable`（来自 `_iter_response_bytes_no_idle:627` 或 `_iter_response_bytes_with_idle:691/735`）
- **实际分支**: `_call_impl` 的 `except _AttemptFailedRetriable`（L326）捕获后 sleep 并重试，重试的 `_do_attempt` 产生全新响应，事件流两段拼接
- **预期行为**: 已部分产出事件的流应直接终态收口，不做重试。重试只应在连接级失败（无事件产出）时发生
- **实际行为**: `async for event in self._do_attempt(...): yield event`（L296-299）已将第一段事件 yield 给 Agent。Agent 的 `_consume_runner_event` 副效应（`state.content_chunks.append`、`state.tool_calls = ...`）已执行。重试后第二段事件在同一 Agent iteration 内继续被消费，导致 `content_chunks` 包含两段拼接的重复/乱序文本，`tool_calls` 可能被第二段覆盖
- **直接证据**: `_call_impl:285` `while True` 重试循环包装了 `_do_attempt:296`；`_AttemptFailedRetriable` 可从流中间抛出；无任何机制阻挡事件已产出后的重试
- **影响**: 内容重复或损坏，tool call 参数异常，LLM context 注入错误数据
- **建议改法**: `_call_impl` 跟踪 `_has_yielded` 标志，若已向 Agent yield 过事件，跳过重试循环直接 emit terminal error event
- **修复风险**: 中低 — 改动范围在 runner.py 内部，不涉及 Agent 层契约。会改变流式场景重试语义
- **严重程度**: 严重

### F2-严重 — SSE 路径与非流式路径 finish_reason 处理不一致

- **入口/函数**: 非流式: `_emit_from_dict`；SSE: `_finalize_success`
- **文件(行号)**: `dayu/engine/runners/openai/non_stream_parser.py:317-318`；`dayu/engine/runners/openai/sse_parser.py:545-549`
- **输入场景**: provider 发送 `finish_reason=stop` 且携带 tool_calls
- **实际分支**:
  - 非流式（L317-318）: `if tool_calls_emitted: finish_reason = FinishReason.TOOL_CALLS` — 强制覆盖
  - SSE（L545-549）: `finish = self._finish_reason or (FinishReason.TOOL_CALLS if self._tool_calls_seen else FinishReason.STOP)` — `or` 短路使 provider 的 `stop` 优先于 `TOOL_CALLS`
- **预期行为**: 两种解析路径行为一致。当 tool_calls 存在时，finish_reason 应统一修正为 `TOOL_CALLS`
- **实际行为**: 非流式强制覆盖为 `TOOL_CALLS`；SSE 保持 provider 原始 `stop`。Agent 层 `_classify_iteration`（agent.py:1374-1380）检测到 mismatch 并以 `ERROR_RUNNER_TOOL_CALLS_FINISH_REASON_MISMATCH` 不可恢复失败
- **直接证据**: 两段代码的 finish_reason 逻辑不同；Agent 层 L1374-1380 的验证会捕获此不一致
- **影响**: 同批 tool call 在非流式模式成功、流式模式失败，对用户表现为偶发不可恢复失败
- **建议改法**: SSE `_finalize_success` 中，当 `_tool_calls_seen` 且 result.tool_calls 非空时，把 finish 强制设为 `FinishReason.TOOL_CALLS`
- **修复风险**: 低
- **严重程度**: 严重

### F19-中 — `event_log.append_event` 并发插入冲突后错误不可重试

- **修复风险**: 低
- **严重程度**: 中

## 审查总结

全仓走读覆盖 6 个主要分层/子系统，各层通过 6 个并行 subagent 独立审查。共发现 **4 个严重**、**9 个高**、**8 个中等**、**7 个低** 级别问题。

**最应优先修复的 4 个严重问题：**

1. **SSE 流式重试数据损坏**（F1）— 网络中断后的重试导致 Agent 收到两段拼接的事件流，内容/工具调用数据损坏
2. **SSE 与非流式 finish_reason 不一致**（F2）— 同批 tool call 在流式模式不可恢复失败、非流式模式成功
3. **`reset_minimal_read_model_projection` 无 consumer 隔离**（F3）— 任一 consumer 的 reset 破坏所有 consumer 的投影数据
4. **`RuntimeFileLock` release 失败后实例死锁**（F4）— 一次 I/O 错误导致实例永久不可用

**架构整体评价：** 分层边界清晰，无反向依赖。契约层的 Protocol/ABC 设计正确。Engine 的状态机（`_IterationState` / `_IterationDecision`）建模扎实。Host durable 的事件溯源 + CAS 并发控制设计合理。主要残存风险集中在 Engine SSE 重试语义的跨层不透明性，以及 Durable schema 的运维升级路径缺失。

**各层质量排序（从高到低）：** contracts > runtime > engine（非 runner）> host/durable > host（非 durable）> engine/runners/openai
