## 1. Scope and Goals

Plan claims to deliver a shared Host compact pipeline owner (`compact_pipeline.py`) that unifies proactive/reactive material-to-compact-result semantics without changing outer lifecycle, public API, EventLog contracts, or durable schemas. Two implementation slices: S1 (shared pipeline + evidence cleanup), S2 (wire call sites).

Key non-goals explicitly stated:
- No public API/schema/EventLog/durable contract changes
- No merging proactive/reactive outer lifecycle
- No new reactive-only implementation

### 002-未修复-高-compact_pipeline 可能过度设计且过度耦合

- **位置**: Section 4 "Minimal Implementation Boundary" + Section 5 全章
- **问题类型**: 过度设计 / 过度耦合
- **当前写法**: Plan 新增 `compact_pipeline.py`，承担 6 种职责：request construction (normal + recovery + pass queue)、accepted/failed payload input、fallback decision input、render handoff、commit guard fields、WU-CM-14 raw tail provider ownership。同时其上游依赖 3 个模块 (`compact_material.py`、`context_fallback.py`、`compaction_operation.py`)，下游被 3 个模块消费 (`dispatch.py`、`engine_ingest.py`、`run_input.py`)。
- **反例/失败场景**:
  1. `compact_pipeline.py` 成为一个新 God module — 如果它内部协调 6 种职责但 plan 没有分层，未来一次 fallback ordering 改动可能需要理解 material view、operation context、render handoff 的所有内部实现。
  2. 当前 4 个 compact 模块已经 3648+1025+2117+658 = ~7.4k 行；新增 pipeline 可能再加 1k+ 行，让 compact subsystem 总行数接近 9k，而核心语义是 "统一两个路径的材料到结果装配" — 这个比例不匹配。
  3. 如果 pipeline 暴露的 result type 与 dispatch/ingest 的 caller 逻辑耦合过紧（例如 Accepted result 包含 EventLog payload dict 而不仅是 semantic field），未来 payload schema 变更需要同时修改 pipeline 和两个 caller。
- **为什么有问题**: 按第一性原理，问题本质是 proactive 和 reactive 各自重复实现 `CompactionRequest` 构造、tier 1-3 recovery request 构造、fallback decision。更小、更安全的解法是：
  - 将 shared construction functions 迁入 `compact_material.py`（它已经是 material owner），或
  - 新增一个极薄模块（<500 行），只输出 3-4 个纯函数：`build_compaction_request(...)`、`build_recovery_requests(...)`、`build_fallback_decision_input(...)`、`build_render_handoff(...)`。
  - 不需要 result union、pipeline trigger enum、operation context、commit guard hack。
  当前 plan 的 pipeline "owner" 抽象对 "两处重复构造" 问题过度设计了。
- **直接证据**:
  - Plan Section 4 lists 7 allowed production files with 7 allowed test files — 共 14 个 file boundary 受影响。
  - Plan Section 5.1–5.2 定义了 6 个 input type + 6 个 result type，但核心问题只是 "两次重复写 `CompactionRequest(...)` 和 tier construction"。
  - Plan Section 5.4 说 "shared pipeline 必须暴露 caller commit guard 所需字段" — 这意味着 pipeline 需要知道 lifecycle semantics 才能决定暴露哪些字段，这是跨层泄漏。
- **影响**: 后续返工 — 如果 implementation 完成后发现 pipeline 太厚，回退到更简单方案的成本很高（tests 重写、两个 lifecycle path 同时回归）。
- **建议改法和验证点**:
  1. 先做一次 "最小 shared helper" spike：在 `compact_material.py`（或一个 <500 行的 `_compact_shared.py`）中抽取 dispatch.py 和 engine_ingest.py 中重复的 `CompactionRequest(...)` 构造逻辑、tier 构造逻辑、fallback decision 逻辑。
  2. 验证 proactive / reactive tests 仍通过。
  3. 再判断是否需要独立 pipeline module。
- **修复风险（中）**：改变模块边界需要重新 review allowed files。
- **严重程度（高）**：如果 pipeline 过度设计，会在后续 WU（CM-15 或 memory 变更）中变成瓶颈。

### 003-未修复-高-outer-lifecycle-boundary-模糊且 commit guard 语义不清晰

- **位置**: Section 5.3 "Outer Lifecycle Boundary" + Section 5.4 "Commit Guard 输入"
- **问题类型**: 架构边界 / 状态机漏洞
- **当前写法**: Section 5.3 说 shared pipeline "不创建或关闭 Attempt，不设置 Run status，不写 Session active slot"，但 Section 5.4 要求 pipeline 暴露 `expected_run_status` 或 "caller-specific expected lifecycle state"。
- **反例/失败场景**:
  1. `expected_run_status` 语义在 proactive（Run unstarted）和 reactive（Run RECOVERING）中不同。Pipeline 如果设计一个通用 `expected_run_status` 字段，它必须理解 "proactive 时是 QUEUED/READY，reactive 时是 RECOVERING" — 这就是生命周期知识。如果 pipeline 不区分而 caller 自己解释，那这个字段不应叫 `expected_run_status`，应叫 `caller_expected_lifecycle_guard_value`，语义完全不同。
  2. `expected_input_event_sequence` 同样：proactive 是 `run.input_event_sequence`，reactive 是引擎 ingest 进入时的 `run.input_event_sequence`（在 closeout 前冻结）。Pipeline 如果产出这个值，它就需要知道调用方 freeze cursor 的时机 — 这是 outer lifecycle 时序知识。
  3. 如果 pipeline 暴露的字段被一个 caller 正确使用而另一个 caller 误用（例如 proactive 误用 reactive 的 `attempt_id`），Shared pipeline 不会检测，因为它 "不偷偷读取状态"。这意味着 commit guard 的正确性完全依赖两个 caller 各自实现一致性 — 这正是 plan 声称要解决的问题。
- **为什么有问题**: Commit guard 字段的设计违反了 "shared pipeline 不知道 lifecycle" 的声明。实际上，要么 pipeline 知道足够多的 lifecycle 来保证两个 caller 一致性（变成 lifecycle-aware），要么 pipeline 不暴露这些字段而让 caller 自己构造 guard（回到当前分散状态）。Plan 想走中间路径但语义不成立。
- **直接证据**:
  - Plan Section 5.4: "Shared pipeline 必须暴露 caller commit guard 所需字段，不自己偷偷读取状态" — 但字段语义本身需要 lifecycle 知识。
  - Plan Section 5.3: "proactive caller 用这些字段检查未启动 Run 是否仍允许 commit；reactive caller 用这些字段检查 recovering Run / source Attempt / input cursor 是否仍匹配" — 两种 caller 对同一组字段的校验逻辑完全不同。
- **影响**: 状态不一致 — 如果 pipeline 产出的 commit guard 值被一个 caller 误读，可能导致 stale compact result 被错误提交 `CONTEXT_COMPACTED`。
- **建议改法和验证点**:
  1. 明确区分：pipeline 产出 `pipeline_execution_snapshot`（material view digest、operation id、frozen cursor、request digest），caller 各自用自己的 lifecycle state 与 snapshot 做校验。
  2. 不在 pipeline 中放 `expected_run_status` 或 `expected_input_event_sequence`。
  3. 分别在 dispatch 和 ingest 的 caller side 测试 commit guard。
- **修复风险（低）**：只影响 commit guard 字段的设计。
- **严重程度（高）**：commit guard 错误可能导致双重提交或丢失 compact event。

### 004-未修复-高-WU-CM-14-preservation 集成策略存在跳过风险

- **问题类型**: 范围漂移 / 不可直接实施

### 007-未修复-中-RenderHandoff 可能改变 RunInputBuilder 内部契约

- **位置**: Section 5.2 "Result Shape" — `CompactPipelineRenderHandoff` + Section 6
- **问题类型**: 契约缺失 / 架构边界
- **当前写法**: Plan 提出 `CompactPipelineRenderHandoff` 包含 "ordinary post-compaction raw tail blocks/messages, fallback selected blocks/messages, source refs, material view digest, selected recent floor, selected raw turn count."
- **反例/失败场景**:
  1. 当前 `RunInputBuilder.build()` (run_input.py:1958-2088) 通过 10 个 typed provider 独立读取各自数据（current run facts、session continuity、memory snapshot、compact artifact、accepted evidence、context fallback、tool schema、tool executor、scene parameter、policy snapshot + 可选的 protected raw tail provider）。这些 provider 各自管理自己的 read transaction、cache、校验逻辑。
  2. 如果 pipeline 的 `RenderHandoff` 取代这些 provider 的部分输出 — 具体是 compact artifact + context fallback + protected raw tail — 那 `RunInputBuilder.build()` 的内部组装逻辑需要改变。这不是 "consuming handoff" 的简单改动，而是改变了 RunInputBuilder 的依赖注入 graph。
  3. Plan 说 "渲染仍由 RunInputBuilder 完成" 但 handoff 携带了 "selected blocks / source refs / digest / protected floor consistency。" 这意味着 RunInputBuilder 不再独立验证这些值，而是信任 pipeline output。如果 pipeline output 有 bug（例如 digest mismatch），RunInputBuilder 不会检测。
- **为什么有问题**: Handoff 改变 RunInputBuilder 的 trust boundary。当前 RunInputBuilder 每个 provider 独立做 durable read + validation。RenderHandoff 让 compact 相关数据先经过 pipeline 处理，再传给 RunInputBuilder。这是一个内部 provider contract 变更，虽然不触及 public API，但改变了 Host internal trust model。
- **直接证据**:
  - `run_input.py:1894-1911`: `RunInputBuilder.__init__` 接收 10 个 provider + 1 个 optional raw tail provider。
  - `run_input.py:1988-2009`: 当前 RunInputBuilder 自己组装 `bounded_context_messages` 来自 memory + compact + protected raw tail + continuity。
  - Plan Section 5.2: RenderHandoff 带 "ordinary post-compaction raw tail blocks/messages, fallback selected blocks/messages" — 这绕过了 RunInputBuilder 的 provider 组装。
- **影响**: 实施 Agent 跑偏 — 如果没有明确定义 RenderHandoff 与现有 provider 的关系，agent 可能创建一个绕过 provider graph 的 shortcut，或创建 circular dependency。
- **建议改法和验证点**:
  1. 在 plan 中明确：RenderHandoff 是 provider 的替代还是补充。
  2. 如果是替代，列出被替代的 provider 和新的调用链。
  3. 如果是补充，说明 RunInputBuilder 如何使用 handoff 与现有 provider output 做 cross-validation。
- **修复风险（低）**：plan 澄清。
- **严重程度（中）**：不导致 immediate bug，但影响 RunInputBuilder 的长期 maintainability。

### 008-未修复-中-reactive fallback 代码路径当前不支持 multi-tier dispatch fallback

- **位置**: Section 5.5 "Fallback Ordering" vs code facts in `engine_ingest.py:3879-3943`
- **问题类型**: 状态机漏洞 / 切片过粗
- **当前写法**: Plan Section 5.5 定义 8-step unified fallback ordering (tier 1→2→3→4→5→fail closed)。
- **反例/失败场景**:
  1. 当前 `_reactive_fallback_decision(...)` (engine_ingest.py:3879-3943) 只做一层 recent-window fallback（plan 中的 tier 4），不迭代 tier 1-3 compact recovery。Reactive compact recovery tier 1-3 的尝试在 engine_ingest.py 的 operation loop 中完成（`_execute_reactive_context_compaction` 等），但 tier 4/5 dispatch fallback 在 `_reactive_fallback_decision` 中，且只用了一层 budget pass/fail。
  2. Plan 的 unified fallback ordering 需要 pipeline 协调 tier 1-3 recovery（用 compactor）→ tier 4 floor-only（不用 compactor）→ tier 5 current-input-only（不用 compactor）。但 tier 1-3 需要 `CompactionRequest` → `compaction_operation` → proposal → quality check，tier 4/5 不需要 compactor 调用。Pipeline 如果统一管这个 fallback chain，它必须知道何时调用 `compaction_operation.py` 的 operation loop，何时跳过 — 这对 "纯语义装配" pipeline 过重。
- **为什么有问题**:
  - 当前 proactive 和 reactive 的 tier fallback 路径结构不同。Proactive 从 `_proactive_compaction_recovery_attempts` (dispatch.py:1502) 直接构造 recovery request chain；reactive 从 operation loop → fallback decision。Unified ordering 不能只靠 "统一的 fallback 步骤列表" 实现，需要实际统一两种代码路径的控制流 — 这可能超出 "shared pipeline 不拥有 outer lifecycle" 的约束。
- **直接证据**:
  - `dispatch.py:1502-1568`: proactive tier 1-3 recovery 是 `_proactive_compaction_recovery_attempts` 在 operation loop 中尝试。
  - `engine_ingest.py:3879-3943`: reactive 只有一个 fallback decision，不迭代 tier 1-3。
  - Plan Section 5.5: 要求 8 步统一 ordering。
- **影响**: 实施 Agent 跑偏 — Agent 可能在 pipeline 中实现一个完整的 tier 状态机，但这会与 compaction_operation 的 operation loop 冲突（或重复）。
- **建议改法和验证点**:
  1. 明确定义 pipeline 在 fallback ordering 中的角色：pipeline 只决定 "给定 frozen material view、policy、operation result，下一步应尝试什么配置"（纯决策），还是控制整个 fallback loop（控制流）。
  2. 如果是纯决策，定义 `CompactPipelineNextStep` 枚举作为返回值。
  3. 如果是控制流，必须解释如何与 `compaction_operation.py` 的 operation loop 共存。
- **修复风险（低）**：plan 澄清职责边界。
- **严重程度（中）**：fallback 实现可能走偏，但不会破坏现有 proactive path。

## 4. Architecture Boundary Review

### Layering
- Plan 正确识别了 `compact_pipeline.py` 不跨越 `UI → Service → Host → Engine` 分层边界。所有改动在 Host 内。
- **Concern**: Pipeline 如果知道 Run/Attempt lifecycle 语义（通过 `expected_run_status`、`attempt_id`），它向上侵犯了 outer lifecycle owner（dispatch/ingest）的决策空间。

### Ownership
- 当前 compact material owner 是 `compact_material.py`，fallback helper 是 `context_fallback.py`，operation loop 是 `compaction_operation.py`。Plan 新增 `compact_pipeline.py` 作为协调 owner，但 4 个模块的职责边界变得模糊。
- **Concern**: `compact_material.py` (3648 lines) 已经承担了大量职责。如果 pipeline 成为 "smart coordinator"，`compact_material.py` 可能降级为 data access layer。这本身不坏，但 plan 没有明确声明这是预期的 refactoring 方向。

### Dependency Direction
- Plan 的依赖方向：`dispatch.py / engine_ingest.py → compact_pipeline.py → compact_material.py / context_fallback.py / compaction_operation.py`。方向正确（Host 内部→shared helper→lower level）。
- **Concern**: `run_input.py → compact_pipeline.py` （通过 RenderHandoff）引入 `run_input.py` 对 pipeline 的依赖，而 pipeline 依赖 material view builder。如果 pipeline 又需要 RunInputBuilder 的某些输出，会形成循环。

### Public Contracts
- Plan claims no public API/schema/EventLog changes. Plausible for external APIs but the internal RenderHandoff effectively changes the contract between compact and RunInput subsystems.

## 5. Best-Practice Review

- **Testability**: Plan 的 pipeline 用 result union 收口，比分散在 dispatch/ingest 中更容易单元测试。但如果没有具体类型定义，测试无法写 mock/stub。
- **Maintainability**: 集中化 request/recovery/fallback construction 是好的。但过度集中的 pipeline 可能变成 "修改 fallback ordering 需要理解 whole pipeline" 的 god coordinator。
- **Observability**: Plan 未涉及 logging/diagnostic changes。Shared pipeline 如果取代了 dispatch/ingest 中的 construction 逻辑，相关的 diagnostic log 是否也迁移？未明确。
- **Failure handling**: Plan Section 5.5 fallback ordering 提到 fail closed 条件，但没有说明 pipeline 自身在内部异常（如 material view corrupt、policy missing）时如何 fail。

## 6. Optimal-Solution Review

Plan 的方案是按 "shared pipeline owner" 收敛。更轻量的替代方案是：

**替代 A — Shared construction functions in `compact_material.py`**:
- 在已有的 `compact_material.py` 中新增 3-4 个模块级函数：`build_compaction_request_for_trigger(...)`、`build_tier_recovery_requests(...)`、`build_compact_result_handoff(...)`。
- Proactive/reactive 调用这些函数后自己 append event / 推进状态。
- 不需要新模块、result union、pipeline trigger enum、commit guard hack。
- 缺点：`compact_material.py` 已经 3648 行，再加可能到 ~4k 行。
- 优点：不需要设计新模块契约，review surface 小，改动量更少。

**替代 B — Thin `<500 line` `_compact_shared.py`**:
- 只导出 4 个函数，不定义 result union。
- 类似 `context_fallback.py` (1025 lines) 的 scope。

Plan 没有评估这两种替代方案，直接选择了 "shared pipeline owner" 作为唯一方案。在当前问题规模下（主要就是两处 `CompactionRequest` 构造重复），方案 A 或 B 可能更合适。

## 7. Overengineering Review

- **Pipeline trigger enum**: `CompactPipelineTrigger.PROACTIVE | REACTIVE` — 如果 pipeline 只是做 material→request 装配，trigger source 可以是调用方的参数，不需要 pipeline 内部 enum。
- **Result union with 5 variants**: 当前只有 2-3 种实际结果（success with compact、failed with/without fallback、fallback only dispatch）。5 种 result type 对应 plan section 5.2 的 RequestPrepared / Accepted / Failed / FallbackDecision / RenderHandoff。但 RenderHandoff 不是 compact "result" — 它是给 RunInputBuilder 用的 side output。把它放进同一个 result union 混淆了 "compact operation result" 和 "render input" 的语义。
- **Pipeline-owned WU-CM-14 provider**: Plan 建议把 `_DurableProtectedRecentRawTailProvider` 移到 `compact_pipeline.py`。如果 provider 最终只被 RunInputBuilder 调用，放在 pipeline 中会造成 pipeline 既有 compact entry 又有 RunInput entry — 两个不同的 consumer 和 lifecycle。

## 8. Overcoupling Review

Plan 可能引入以下耦合：

1. **Pipeline ↔ RunInputBuilder**: RenderHandoff 如果替代 compactArtifact + contextFallback + protectedRawTail 三个 provider 的输出，RunInputBuilder 的内部组装从 10-provider 模型变成 7-provider + 1-handoff 混合模型。未来如果要替换某个 provider（如 compact artifact provider），需要同时理解 handoff 的语义。
2. **Pipeline ↔ dispatch + ingest**: Pipeline 如果暴露 commit guard 字段，两个 caller 必须各自解释这些字段。如果未来需要增加新的 guard 条件（如 "compact 后 budget 必须低于新的 policy 阈值"），pipeline 和两个 caller 都需要改。
3. **Pipeline ↔ compaction_operation**: Pipeline 负责 fallback ordering 决策，但 operation loop 在 `compaction_operation.py` 中。Pipeline 可能需要 "invoke operation loop with recovery request" 的能力 — 这要么让 pipeline 依赖 operation 模块，要么让 caller 在 pipeline 和 operation 之间做 mediator。

## 9. Implementation Sequencing Review

Plan 的两片结构（S1: pipeline + evidence cleanup; S2: wire call sites）合理，但：

- **S1 风险**: 没有 caller 集成前，pipeline 的 tests 只能用 mock material view / policy。如果 mock 与真实 dispatch/ingest context 不一致，pipeline 可能在 S1 测试通过但 S2 集成失败。
- **S2 风险**: 同时改 `dispatch.py`、`engine_ingest.py`、`run_input.py` 三个消费点。如果 S2 按 "完全替换" 做但遇到问题，回退成本高。建议 S2 进一步拆成 S2a (proactive only)、S2b (reactive only)、S2c (RunInput handoff)。

1. **Tier 5 existence**: 当前代码中是否已有 tier 5 current-input-only 实现？如果没有，是否在当前 WU 中实现，还是 deferred to future WU？Plan Section 5.5 说 "实施必须核对...若没有...在 shared pipeline 内显式实现...并补测试" 但 Section 12 Blocking Questions 又说 "If code evidence shows current payload fields cannot express tier 5 fallback...that is a blocking question." Implementation agent 在 S1 前需要这个问题的答案。

2. **RenderHandoff 替代哪些 provider？** Plan 说 RunInputBuilder "消费 shared render handoff" 但没有说明是替代还是补充现有的 compact artifact provider、context fallback provider 和 protected raw tail provider。

3. **Pipeline 入口是单函数还是多函数？** Plan 没有给出方法签名。如果是单入口，如何区分 "正常 compact" vs "recovery" vs "fallback decision"？如果是多入口，边界如何保证不互相绕过？

4. **Pipeline 内部异常处理？** 如果 `CompactPipelineMaterialView` 的字段不全或 policy 缺失，pipeline 返回什么？异常？Failed result？由 caller 决定？

5. **`compaction_evidence.py` 的 `SelectedEvidenceBlockRef` 和 `CompactionRequestEvidenceInputs` 类型是否被任何类型注解或 `__all__` 引用？** 虽然生产代码无 import，但 `dayu/host/__init__.py` 是否可能 re-export？删除前需要确认。

6. **Smoke 覆盖边界**: Plan Item 14 说 smoke "必须真实成功"，但 smoke 不经过 compact pipeline 内部路径。如果 pipeline 引入 bug 但 public API behavior 不退化（例如 tier 1-3 recovery 失败但 fallback dispatch 成功），smoke 能发现吗？

## 12. Final Plan Review Conclusion

**Verdict: FAIL**

The plan correctly diagnoses the root cause (dispersed compact pipeline semantics owner across 6 modules) and proposes a reasonable direction (unification). However, it **is not code-generation-ready** because:

1. **No concrete type definitions or method signatures** for the proposed pipeline module — Sections 5.1–5.2 describe 6 input types and 5 result types only in prose, leaving the type system design to the implementation agent.
2. **Tier 5 existence is an open question** that materially affects implementation scope, but the plan defers it to "implementation must check" rather than resolving it in plan phase.
3. **The "temporarily keep WU-CM-14 EventLog second read provider" escape hatch** (Section 6.4) undermines the plan's core goal of pipeline ownership convergence.
4. **Commit guard semantics are contradictory** — pipeline claims to not know lifecycle but must expose lifecycle-dependent fields.

To reach `pass-with-risks`, the plan needs at minimum:
- Concrete `CompactPipelineMaterialView` and at least 2 key result type dataclass definitions (addressing Finding 1).
- A definitive decision on tier 5 (addressing Finding 8).
- Removal of the "temporarily keep EventLog second read" escape hatch (addressing Finding 4).
- Clarification of commit guard semantics (addressing Finding 3).
- A justification for full pipeline module over alternative A/B (addressing Finding 2).
