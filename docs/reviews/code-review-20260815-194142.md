## DS Finding 1 修复验证：OSError/RuntimeError → FILE_NOT_FOUND

### 修复内容

`_normalize_fins_upload_path`（ingestion_runtime.py:959-982）新增 `except (OSError, RuntimeError)` catch，映射为 `FinsUploadUsageCode.FILE_NOT_FOUND` 携带 `path.name`（raw basename）。

### 直接证据

**owner boundary 正确性**：

- 修复前：`expanduser().resolve(strict=False)` 的 `OSError`（文件系统错误、home 目录不可用）或 `RuntimeError`（symlink loop）会逃出 `_validate_fins_upload_filing_static` 的 closed `FinsUploadUsageError` contract，以裸系统异常到达 caller。
- 修复后：所有路径规范化失败统一由 static admission owner 捕获，映射为 closed usage code。caller 只需处理 `FinsUploadUsageError`，不需要处理系统异常。

**path.name 安全性**：

- `path.name` 是 `Path` 的最后一段组件，不含父路径。
- `fins_upload_usage_failure`（行 842-850）对 `file_name` 做三重校验：非空、`Path(file_name).name == file_name`、无 `/` 或 `\`。
- 测试 `test_filing_symlink_loop_is_typed_file_not_found_before_all_side_effects`（行 1744）断言 `str(tmp_path) not in exc_info.value.failure.message`。

**symlink loop 覆盖**：

- 测试创建 `loop.symlink_to(loop.name)`（相对自引用 symlink），`resolve(strict=False)` 检测 loop 后抛出 `RuntimeError`。
- `loop_is_selector` 参数化覆盖两种场景：loop 作为 raw file、loop 作为 primary selector。
- 两种场景均断言 `FILE_NOT_FOUND`、message 为 `"上传文件不存在：loop.pdf"`、零副作用。

**catch 范围评估**：

- `OSError`：涵盖 `expanduser()` 的 home 目录不可用、`resolve()` 的文件系统错误、`ENAMETOOLONG` 等。从业务角度，这些均为「路径不可解析→用户需修正」，映射为 `FILE_NOT_FOUND` 可接受。
- `RuntimeError`：仅 `resolve(strict=False)` 的 symlink loop 会抛出，catch 精确。
- 无过宽 catch 风险：`ValueError`、`TypeError` 等未被捕获，仍按原路径传播。

### 裁决

DS Finding 1 已修复。修复正确、安全、无新回归。
