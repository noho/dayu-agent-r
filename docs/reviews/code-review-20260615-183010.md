### 001-未修复-中-测试声称覆盖 non-terminal event append failure WARN 但实际未测试

- **入口/函数**: `test_terminal_event_append_failure_warns_without_rolling_back_terminal_record`
- **文件(行号)**: `tests/fins/test_fins_ingestion_runtime.py:1625-1687`
- **输入场景**: 后台 job 执行过程中，非终态事件（如 `JOB_QUEUED`、`JOB_RUNNING`）的 sidecar 写入失败
- **实际分支**: monkeypatch 只在 `event.event_type is FinsIngestionJobEventType.JOB_SUCCEEDED` 时抛出 `OSError`；`JOB_QUEUED` 和 `JOB_RUNNING` 事件走正常 `original_append` 路径
- **预期行为**: plan S1 tests/validation 明确要求"non-terminal progress event append 失败只产生 WARN，业务成功时 job 仍可 SUCCEEDED；terminal event append 失败产生 WARN 且不回滚 terminal job record"。测试应覆盖 non-terminal event（如 `JOB_QUEUED`、`JOB_RUNNING`）写入失败时的 WARN 行为
- **实际行为**: 测试只验证了 terminal event（`JOB_SUCCEEDED`）写入失败的 WARN 行为。`JOB_QUEUED` 和 `JOB_RUNNING` 事件在测试中正常写入成功，从未触发 WARN 路径
- **直接证据**: `raise_for_terminal_event` 函数（第 1662 行）仅对 `JOB_SUCCEEDED` 生效；assertion（第 1680-1683 行）确认 `JOB_QUEUED` 和 `JOB_RUNNING` 事件成功写入 sidecar
- **影响**: `_append_job_event_warn` 中 `except Exception` 的 WARN-and-continue 策略对 non-terminal 事件从未被测试验证。如果该策略对 non-terminal 事件存在边界问题（例如影响 job 正常执行流程），当前测试无法发现
- **建议改法和验证点**:
  1. 新增测试：monkeypatch 使 `JOB_QUEUED` 或 `JOB_RUNNING` 的 `append_job_event` 抛出 `OSError`
  2. 断言：job 仍正常进入终态（`SUCCEEDED`），sidecar 中缺少对应事件，caplog 包含 `fins.ingestion.job_event_append_failed` WARN
  3. 验证业务路径不因 non-terminal 事件写入失败被中断
- **修复风险（低/中/高）**: 低
- **严重程度（中）**: 测试覆盖缺口与 plan 要求不一致；implementation codex 声称覆盖但实际只覆盖了 terminal 路径

### 002-未修复-低-_event_record_from_json 双重序列化做 round-trip 校验

- **入口/函数**: `_event_record_from_json`
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:3519-3552`
- **输入场景**: 从 JSONL sidecar 读取并反序列化每条事件记录
- **实际分支**: 第 3551 行调用 `_event_record_to_json(record)` 做 round-trip 校验，丢弃返回值
- **预期行为**: 反序列化后的 record 应通过校验以确认 sidecar 数据完整
- **实际行为**: `_event_record_to_json` 内部执行完整字段校验 + `json.dumps` 编码，但返回值被丢弃。每次 read 操作对每条记录都付出完整序列化成本
- **直接证据**: `_event_record_to_json` 内部调用 `_validate_job_id`、`_validate_event_sequence`、`validate_bounded_job_event_payload`，并执行 `json.dumps`（第 3493-3516 行）
- **影响**: 性能问题，非正确性问题。`read_job_events` 在持锁期间读取全部事件，每条事件的 round-trip 校验增加锁持有时间。当事件数量增长时，锁内 O(n) 读取 + O(n) 校验会放大延迟
- **建议改法和验证点**:
  1. 考虑抽取轻量级 `_validate_event_record_fields(record)` 只做字段级校验，不做 JSON 编码
  2. 或在 `_iter_event_records_locked` 中只做结构校验，把 round-trip 保留在写入路径
  3. 当前实现正确性无问题，此 finding 为 maintainability / performance 建议
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 性能优化建议，当前正确性不受影响

### 003-未修复-低-_append_job_event_warn 对空 payload 仍记录 payload_keys 日志字段

- **入口/函数**: `_append_job_event_warn`
- **文件(行号)**: `dayu/fins/ingestion_runtime.py:2808-2821`
- **输入场景**: terminal event append 失败时写 WARN 日志
- **实际分支**: `except Exception` 分支执行（第 2808 行）
- **预期行为**: WARN 日志应简洁且只包含有诊断价值的字段
- **实际行为**: 当 `payload={}` 时（所有 terminal 事件都传空 payload），日志输出 `payload_key_count=0 payload_keys=`，信息冗余

- **影响**: 日志可读性微降，不影响功能
- **建议改法和验证点**: 可选优化：当 `payload_key_count == 0` 时省略 `payload_keys` 字段。不影响 review 结论
- **修复风险（低/中/高）**: 低
- **严重程度（低）**: 日志格式微调

## Residual Risk

1. **Non-terminal event failure WARN 路径未被测试验证**（对应 Finding 001）。当前 monkeypatch 只覆盖 terminal event failure，non-terminal event（`JOB_QUEUED`、`JOB_RUNNING`）写入失败的 WARN-and-continue 行为依赖实现正确但未经测试证明。
